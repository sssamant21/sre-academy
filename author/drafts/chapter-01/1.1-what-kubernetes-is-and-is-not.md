# 1.1 What Kubernetes Is and Is Not

## Purpose of This Section

This section establishes the operating model for the entire Kubernetes SRE Engineering Handbook.

Before an engineer can operate Kubernetes well, they need a precise mental model of what Kubernetes is, what it is not, and where its responsibilities end. Many production incidents start because teams expect Kubernetes to solve problems that are outside its scope: poor application design, missing observability, unsafe rollout practices, weak security boundaries, or unmanaged cloud dependencies.

By the end of this section, the reader should be able to explain Kubernetes as a platform API and distributed control system, not merely as a tool that runs containers.

## What Kubernetes Is

Kubernetes is an open source platform for managing containerized workloads and services. It provides declarative configuration, automation, scheduling, service discovery, rollout control, self-healing behavior, and an extensible API model.

In production terms, Kubernetes is a control system for application infrastructure.

An engineer declares desired state through the Kubernetes API. The control plane stores that state, validates it, and coordinates controllers, schedulers, and node agents that continuously work to make actual cluster state converge toward the desired state.

```text
Desired State        Kubernetes Control Plane        Actual State
-------------        ------------------------        ------------
Deployment YAML ---> API Server / Controllers ----> Pods on Nodes
Replica Count  ----> Scheduler / Kubelet      ----> Running Workloads
Service Spec   ----> Endpoint Controllers     ----> Reachable Backends
```

Kubernetes is not valuable because it starts containers. Container runtimes can start containers. Kubernetes is valuable because it provides a shared API, reconciliation model, and distributed operating system for running many workloads across many machines with consistent operational behavior.

## What Kubernetes Is Not

Kubernetes is not an all-inclusive platform-as-a-service. It does not build source code, decide an organization's CI/CD process, provide a full application framework, replace databases, or automatically create a complete logging, monitoring, or alerting strategy.

Kubernetes also does not guarantee reliability by itself. It gives teams mechanisms for reliability, but teams must still design, configure, test, observe, and operate the platform correctly.

| Misconception | Reality |
| --- | --- |
| Kubernetes makes applications highly available automatically. | Kubernetes can restart and reschedule workloads, but the application must tolerate restarts, replication, network changes, and dependency failures. |
| Kubernetes replaces SRE work. | Kubernetes changes the SRE work. Engineers still own reliability, capacity, upgrades, security, incident response, and cost. |
| Managed Kubernetes removes cluster operations. | EKS, AKS, and GKE reduce control-plane burden, but platform teams still operate workloads, nodes, networking, identity, policy, observability, and upgrades. |
| Running on Kubernetes means cloud portability is solved. | Kubernetes APIs help portability, but storage, load balancing, identity, networking, observability, and managed services often remain provider-specific. |
| Kubernetes solves bad architecture. | Kubernetes can expose architectural weaknesses faster because it restarts, moves, and scales workloads dynamically. |

## Why Kubernetes Exists

Containers made application packaging more consistent, but production container operations created new problems:

- Where should each workload run?
- What happens when a process fails?
- What happens when a node disappears?
- How should traffic reach changing Pod IPs?
- How do teams roll out new versions safely?
- How do teams scale under changing load?
- How do platform teams expose infrastructure without giving every team direct access to machines?

Kubernetes exists to provide a common platform answer to those problems.

It introduces an API-driven model where users describe desired state and control-plane components reconcile actual state. That model is what allows Kubernetes to support automation, GitOps, admission control, policy enforcement, rollout strategies, scheduling, service discovery, and platform extensibility.

## Kubernetes as a Platform API

The Kubernetes API is the center of the system.

Users, controllers, schedulers, node agents, admission webhooks, GitOps tools, operators, and cloud integrations communicate through the API. This design avoids tight coupling between components and gives platform teams a stable contract for automation.

```text
                 +-------------------------+
                 |   Kubernetes API Server |
                 +-----------+-------------+
                             |
        +--------------------+--------------------+
        |                    |                    |
    kubectl              Controllers           kubelets
    GitOps               Operators             Schedulers
    CI/CD                Webhooks              Cloud controllers
```

For SREs, this means API health is platform health. If the API server is slow, unavailable, overloaded, or blocked by failing admission webhooks, the cluster might still run existing workloads, but operations degrade quickly. Deployments stall, controllers fall behind, autoscaling becomes delayed, and incident response becomes harder.

## Kubernetes as a Distributed Control System

Kubernetes works through control loops.

A controller watches the API, compares desired state with actual state, and takes action to reduce the difference. This is different from a script that performs a fixed sequence once and exits.

For example, a Deployment does not directly create a Pod and forget about it. The Deployment controller observes the Deployment object, creates or updates ReplicaSets, and those ReplicaSets drive the desired number of Pods. The scheduler assigns unscheduled Pods to nodes. The kubelet on each node starts containers and reports status.

```text
Deployment
    |
    v
ReplicaSet
    |
    v
Pod ----> Scheduler ----> Node
                    |
                    v
                 kubelet
```

This is the SRE mental model: Kubernetes is a set of cooperating control loops centered on the API.

## What Kubernetes Automates

Kubernetes can automate common operational concerns for containerized workloads.

| Capability | What Kubernetes Provides | SRE Meaning |
| --- | --- | --- |
| Scheduling | Places Pods onto suitable nodes. | Capacity, taints, tolerations, affinity, and resource requests affect placement. |
| Self-healing | Restarts containers and replaces Pods when configured health checks fail. | Workloads must expose accurate readiness and liveness signals. |
| Rollouts | Updates workloads toward a declared desired state. | Rollout strategy, surge, unavailable limits, and rollback plans matter. |
| Service discovery | Provides stable Service abstractions over changing Pods. | Traffic can reach healthy backends even as Pods move. |
| Scaling | Supports manual and automated scaling patterns. | Metrics quality and resource sizing determine scaling reliability. |
| Configuration delivery | Provides ConfigMaps and Secrets as Kubernetes objects. | Teams must still protect secrets and manage change safely. |
| Extensibility | Supports CRDs, admission webhooks, operators, and aggregated APIs. | Platform teams can build higher-level abstractions without modifying core Kubernetes. |

## What Kubernetes Does Not Automatically Solve

Kubernetes does not remove the need for engineering discipline.

It does not automatically solve:

- Poor application startup or shutdown behavior
- Missing readiness or liveness probes
- Unsafe database failover design
- Unbounded memory usage
- Weak container image security
- Poor network dependency management
- Missing observability and alerting
- Bad rollout strategy
- Cloud quota exhaustion
- Cost governance
- Multi-tenant isolation by default
- Disaster recovery planning

Kubernetes provides mechanisms. Engineers provide architecture, guardrails, validation, and operations.

## Real-World Production Use Cases

### Use Case 1: Stateless Web Service Rollout

A retail platform runs a stateless checkout API across multiple nodes. The team uses a Deployment with readiness probes and a rolling update strategy.

Kubernetes helps by:

- Keeping the desired number of Pods running
- Removing unready Pods from Service endpoints
- Rolling out new versions gradually
- Recreating Pods after node failure

The team still owns:

- Backward-compatible API changes
- Database migration safety
- Error-budget policy
- Canary or progressive delivery logic
- Observability and rollback criteria

### Use Case 2: Traffic Spike During a Product Launch

A media company expects a traffic spike during a live event. The platform team uses Horizontal Pod Autoscaling and cluster autoscaling.

Kubernetes helps by:

- Increasing replica count based on metrics
- Scheduling new Pods when capacity exists
- Rebalancing traffic through Services

The team still owns:

- Correct resource requests
- Reliable metrics pipeline
- Cloud provider quota
- Node provisioning time expectations
- Load testing before the event

### Use Case 3: Node Failure in a Managed Cluster

A node fails in EKS, AKS, or GKE. Kubernetes marks Pods on the failed node unavailable and schedules replacements when capacity exists.

Kubernetes helps by:

- Detecting node health changes
- Replacing Pods managed by controllers
- Updating endpoint membership

The team still owns:

- Pod disruption budgets
- Multi-zone capacity
- Persistent storage recovery behavior
- Alert routing
- Application-level retry and timeout behavior

### Use Case 4: Platform API for Internal Developers

A platform team exposes Kubernetes through GitOps. Developers submit pull requests for Deployment, Service, and Ingress changes.

Kubernetes helps by:

- Providing a declarative API
- Enabling policy admission
- Supporting reconciliation
- Giving controllers a stable resource model

The team still owns:

- Repository standards
- Review rules
- Security boundaries
- Namespace and RBAC design
- Release promotion flow

## Managed Kubernetes Reality: EKS, AKS, and GKE

Managed Kubernetes services reduce operational burden, but they do not remove platform ownership.

| Provider | What the service manages | What teams still operate |
| --- | --- | --- |
| Amazon EKS | Managed Kubernetes control plane, AWS integration, and optional EKS Auto Mode capabilities. | Workloads, access, networking choices, node strategy, observability, upgrades, cost, security posture, and AWS service integration. |
| Azure AKS | Managed Kubernetes service for deploying and operating containerized applications on Azure, with modes such as AKS Automatic and AKS Standard. | Workload reliability, node pool choices, Azure identity and networking, policies, monitoring, upgrades, and production architecture. |
| Google GKE | Managed Kubernetes with Autopilot and Standard modes, including managed control plane and, in Autopilot, more node management by Google Cloud. | Workload design, platform boundaries, networking, policy, observability, reliability targets, provider-specific features, and release safety. |

The practical SRE rule is simple: managed Kubernetes changes the responsibility boundary; it does not eliminate responsibility.

## Production Engineering Implications

Kubernetes introduces powerful abstractions, but production safety depends on how teams use them.

A production-grade Kubernetes platform needs:

- Clear ownership between application teams and platform teams
- Standardized workload manifests
- Resource requests and limits policy
- Health probes that reflect real readiness
- Namespace and RBAC boundaries
- Network policy and ingress standards
- Secrets management strategy
- Observability baselines
- Upgrade and rollback procedures
- Backup and disaster recovery planning
- Incident runbooks
- Cost visibility

Kubernetes is not the platform by itself. Kubernetes is the API and control system on which the platform is built.

## SRE Mental Model

An SRE should reason about Kubernetes using four questions:

1. What desired state did we declare?
2. What actual state exists now?
3. Which controller or component is responsible for convergence?
4. What signal tells us why convergence is slow, blocked, or unsafe?

This mental model works for Deployments, Services, Ingress, StatefulSets, Jobs, custom resources, and many operator-managed systems.

When troubleshooting, avoid starting with a single command. Start with ownership and state:

```text
Object declared -> Controller responsible -> Event emitted -> Status updated -> Workload changed
```

That flow keeps incident response focused.

## Failure Scenarios

### Failure Scenario 1: Kubernetes Restarts a Broken Application Forever

A container exits because the application cannot connect to its database.

Kubernetes may restart the container repeatedly. That restart loop is useful because the desired state says the workload should run, but it does not fix the database dependency, credentials, DNS issue, or network policy.

SRE response:

- Inspect Pod status and restart count.
- Read container logs.
- Check Events for probe failures or image pull problems.
- Verify dependent Service, Secret, DNS, and network policy.
- Escalate to the owning team if application configuration is invalid.

### Failure Scenario 2: Deployment Rolls Out but Users See Errors

Kubernetes can roll out Pods successfully from an infrastructure point of view while the application returns HTTP 500 responses.

This happens when readiness checks are too shallow. A Pod can be marked ready even when it cannot serve real traffic correctly.

SRE response:

- Compare rollout status with user-facing metrics.
- Inspect readiness probe design.
- Check service-level indicators such as latency, error rate, and saturation.
- Roll back if the release violates the error budget.
- Improve readiness checks before the next rollout.

### Failure Scenario 3: Autoscaling Does Not Save the System

A workload uses HPA, but traffic increases faster than nodes can be provisioned or the metric pipeline becomes delayed.

Kubernetes can request more replicas, but scheduling depends on available capacity and accurate metrics.

SRE response:

- Check HPA status and scaling events.
- Confirm resource requests are realistic.
- Check pending Pods and scheduler reasons.
- Check cluster autoscaler or provider autoscaling events.
- Pre-scale critical workloads for known demand spikes.

## SRE Signals

Track signals by layer.

| Layer | Signals |
| --- | --- |
| API | API server request latency, error rate, admission latency, watch health. |
| Scheduling | Pending Pods, unschedulable reasons, node capacity, taints, affinity conflicts. |
| Workload | Pod readiness, restart count, rollout status, probe failures, container logs. |
| Node | CPU, memory, disk pressure, network errors, kubelet status, node readiness. |
| Service | Endpoint availability, traffic errors, DNS resolution, ingress or gateway health. |
| Platform | Cluster version, add-on health, certificate status, cloud quota, autoscaler behavior. |

## Runbook: First Five Minutes of a Kubernetes Workload Incident

Use this runbook when a workload is degraded or unavailable.

1. Identify the impacted namespace and workload.

   ```bash
   kubectl get deploy,rs,pod,svc -n <namespace>
   ```

2. Check rollout and desired state.

   ```bash
   kubectl rollout status deployment/<name> -n <namespace>
   kubectl describe deployment/<name> -n <namespace>
   ```

3. Inspect Pods and Events.

   ```bash
   kubectl get pods -n <namespace> -o wide
   kubectl get events -n <namespace> --sort-by=.lastTimestamp
   ```

4. Check logs for the current and previous container instance.

   ```bash
   kubectl logs deployment/<name> -n <namespace>
   kubectl logs deployment/<name> -n <namespace> --previous
   ```

5. Check Service endpoints.

   ```bash
   kubectl get endpointslice -n <namespace>
   kubectl describe service/<name> -n <namespace>
   ```

6. Decide whether this is an application failure, platform failure, capacity failure, or dependency failure.

7. Mitigate first, then preserve evidence for root-cause analysis.

## Best Practices

- Treat Kubernetes as a platform API, not only as a runtime.
- Define ownership boundaries between platform and application teams.
- Require readiness probes for production traffic safety.
- Use resource requests for every production workload.
- Use rollout strategies and rollback criteria.
- Standardize labels, annotations, namespaces, and RBAC patterns.
- Validate manifests before merge.
- Prefer GitOps or controlled delivery pipelines over direct manual changes.
- Monitor both Kubernetes health and application health.
- Test failure behavior before production incidents.

## Common Pitfalls

- Treating a running Pod as proof that the application is healthy.
- Using liveness probes to check dependencies and causing restart storms.
- Setting no resource requests and expecting predictable scheduling.
- Ignoring Events during incident response.
- Assuming managed Kubernetes means no upgrade planning.
- Running stateful systems without backup and restore validation.
- Allowing every team to invent its own Kubernetes patterns.
- Publishing manifests without policy, review, or validation.

## Lab 1: Inspect Kubernetes as an API-Driven Platform

### Goal

Observe Kubernetes as an API, not only as a command-line tool.

### Prerequisites

- Access to a non-production Kubernetes cluster.
- `kubectl` installed and configured.
- Permission to create resources in a test namespace.

### Steps

1. List available API resources.

   ```bash
   kubectl api-resources
   ```

2. Inspect API versions for common workload resources.

   ```bash
   kubectl api-resources | grep -E 'deployments|replicasets|pods|services'
   ```

3. Create a test namespace.

   ```bash
   kubectl create namespace sre-book-lab
   ```

4. Create a Deployment.

   ```bash
   kubectl create deployment web --image=nginx:1.27 --replicas=2 -n sre-book-lab
   ```

5. Observe related objects.

   ```bash
   kubectl get deployment,replicaset,pod -n sre-book-lab
   ```

### Expected Observations

- The Deployment creates a ReplicaSet.
- The ReplicaSet creates Pods.
- Kubernetes stores and exposes all of these as API objects.
- `kubectl` is a client that talks to the API server.

### Cleanup

```bash
kubectl delete namespace sre-book-lab
```

## Lab 2: Observe Desired State Reconciliation

### Goal

Prove that Kubernetes continuously reconciles desired state.

### Steps

1. Create the namespace and Deployment again if needed.

   ```bash
   kubectl create namespace sre-book-lab
   kubectl create deployment web --image=nginx:1.27 --replicas=2 -n sre-book-lab
   ```

2. List Pods.

   ```bash
   kubectl get pods -n sre-book-lab
   ```

3. Delete one Pod.

   ```bash
   kubectl delete pod <pod-name> -n sre-book-lab
   ```

4. Watch reconciliation.

   ```bash
   kubectl get pods -n sre-book-lab --watch
   ```

### Expected Observations

- One Pod terminates.
- A replacement Pod appears.
- The ReplicaSet restores the desired replica count.
- Kubernetes is reconciling desired state, not executing a one-time script.

### Cleanup

```bash
kubectl delete namespace sre-book-lab
```

## Section Summary

Kubernetes is a portable, extensible platform for managing containerized workloads and services through declarative configuration and automation. In production, it is best understood as an API-centered distributed control system.

Kubernetes provides powerful building blocks for scheduling, rollout control, service discovery, scaling, self-healing, and extensibility. It does not replace application architecture, observability, security design, cost governance, incident response, or SRE ownership.

The professional Kubernetes SRE mindset is to reason from declared state, observed state, responsible controller, and convergence signals.
