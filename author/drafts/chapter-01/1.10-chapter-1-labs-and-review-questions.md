# 1.10 Chapter 1 Labs and Review Questions

## Purpose of This Section

This section closes Chapter 1 by turning the foundational concepts into hands-on practice and engineering review.

The goal is not to memorize Kubernetes object names. The goal is to prove that the reader can reason like a Kubernetes SRE:

- Explain what Kubernetes is and is not.
- Read desired state and compare it with actual state.
- Understand architecture and responsibility boundaries.
- Trace basic networking, storage, security, and reliability behavior.
- Recognize production-ready workload design.
- Identify common anti-patterns before they become incidents.

By the end of this section, the reader should be able to complete the labs, answer the review questions, and perform a first-pass production readiness review for a Kubernetes workload.

## Lab Safety Rules

Run these labs only in a test cluster or a namespace that is safe to delete.

Do not run these exercises directly in a production namespace.

Before starting:

```bash
kubectl config current-context
kubectl get nodes
```

Confirm that the current context points to the intended test cluster.

Use a dedicated namespace:

```bash
kubectl create namespace chapter-01-lab
```

Clean up when finished:

```bash
kubectl delete namespace chapter-01-lab
```

If a lab creates storage, always confirm reclaim policy and cleanup behavior before deleting claims.

## Lab 1: Desired State and Reconciliation

### Goal

Observe how Kubernetes reconciles a Deployment back to the requested replica count.

### Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reconcile-demo
  namespace: chapter-01-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: reconcile-demo
  template:
    metadata:
      labels:
        app: reconcile-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```

### Steps

Apply the manifest:

```bash
kubectl apply -f reconcile-demo.yaml
kubectl get deployment,pod -n chapter-01-lab
```

Delete one Pod:

```bash
kubectl delete pod -n chapter-01-lab -l app=reconcile-demo
```

Watch the controller create replacement Pods:

```bash
kubectl get pods -n chapter-01-lab -w
```

### Expected Observations

- The Deployment declares three desired replicas.
- Deleting a Pod does not change the desired state.
- The Deployment controller creates replacement Pods.
- Kubernetes repairs the replica count, not the original Pod identity.

### Review Questions

1. What object stores the desired replica count?
2. Why does the replacement Pod have a different name?
3. What would happen if the Deployment were deleted instead of a Pod?
4. Why is this model useful for production operations?

## Lab 2: Readiness and Service Endpoints

### Goal

Observe how readiness affects whether a Pod receives Service traffic.

### Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: readiness-demo
  namespace: chapter-01-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: readiness-demo
  template:
    metadata:
      labels:
        app: readiness-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: readiness-demo
  namespace: chapter-01-lab
spec:
  selector:
    app: readiness-demo
  ports:
    - port: 80
      targetPort: 80
```

### Steps

Apply the manifest:

```bash
kubectl apply -f readiness-demo.yaml
kubectl rollout status deployment/readiness-demo -n chapter-01-lab
kubectl get endpointslice -n chapter-01-lab
```

Inspect Pods and Service:

```bash
kubectl get pods -n chapter-01-lab
kubectl describe service readiness-demo -n chapter-01-lab
```

### Expected Observations

- Ready Pods become Service endpoints.
- The Service selector links the Service to Pods by label.
- EndpointSlices reflect backend endpoint state.

### Review Questions

1. What happens when a Pod fails readiness?
2. Why is readiness different from liveness?
3. What production outage can happen if readiness is missing or wrong?
4. Why should readiness reflect traffic-serving ability?

## Lab 3: Resource Requests and Scheduling

### Goal

Understand how resource requests affect scheduling decisions.

### Manifest

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: resource-demo
  namespace: chapter-01-lab
spec:
  containers:
    - name: web
      image: nginx:1.27
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "500m"
          memory: "256Mi"
```

### Steps

Apply the manifest:

```bash
kubectl apply -f resource-demo.yaml
kubectl describe pod resource-demo -n chapter-01-lab
```

Check node placement:

```bash
kubectl get pod resource-demo -n chapter-01-lab -o wide
```

### Expected Observations

- The scheduler uses requests when placing the Pod.
- The kubelet and runtime enforce limits.
- Requests and limits become part of workload reliability and capacity planning.

### Review Questions

1. Why are resource requests scheduling contracts?
2. What can happen when memory limits are too low?
3. What can happen when requests are missing?
4. Why should requests be based on evidence rather than guesses?

## Lab 4: Service Account and RBAC Basics

### Goal

Create a read-only ServiceAccount and verify its permissions.

### Steps

Create a ServiceAccount:

```bash
kubectl create serviceaccount chapter-reader -n chapter-01-lab
```

Create a Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: chapter-01-lab
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

Create a RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: chapter-reader-pod-reader
  namespace: chapter-01-lab
subjects:
  - kind: ServiceAccount
    name: chapter-reader
    namespace: chapter-01-lab
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Verify access:

```bash
kubectl auth can-i list pods \
  --as system:serviceaccount:chapter-01-lab:chapter-reader \
  -n chapter-01-lab

kubectl auth can-i list secrets \
  --as system:serviceaccount:chapter-01-lab:chapter-reader \
  -n chapter-01-lab
```

### Expected Observations

- The ServiceAccount can list Pods.
- The ServiceAccount cannot list Secrets.
- RBAC grants specific verbs on specific resources.

### Review Questions

1. Why is Secret access sensitive?
2. Why should workloads use dedicated ServiceAccounts?
3. What is the difference between RoleBinding and ClusterRoleBinding?
4. Why is `cluster-admin` dangerous for application workloads?

## Lab 5: PodDisruptionBudget Review

### Goal

Create a PodDisruptionBudget and interpret its status.

### Manifest

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: reconcile-demo
  namespace: chapter-01-lab
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: reconcile-demo
```

### Steps

Apply the PDB after Lab 1:

```bash
kubectl apply -f reconcile-demo-pdb.yaml
kubectl describe pdb reconcile-demo -n chapter-01-lab
```

### Expected Observations

- The PDB selects Pods by label.
- The PDB reports current healthy Pods and allowed disruptions.
- The PDB affects voluntary evictions, not every possible deletion or failure.

### Review Questions

1. What does `minAvailable: 2` mean for a three-replica workload?
2. What does a PDB protect against?
3. What does a PDB not protect against?
4. Why can a strict PDB block node maintenance?

## Lab 6: Production Readiness Review Exercise

### Goal

Review a manifest and identify production risks.

### Scenario Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: api
          image: example/payments-api:latest
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            timeoutSeconds: 1
```

### Review Prompts

Identify the risks:

- Namespace choice.
- Replica count.
- Image tag.
- Missing readiness probe.
- Missing startup probe.
- Liveness semantics.
- Missing resources.
- Missing security context.
- Missing Service and ingress model.
- Missing NetworkPolicy.
- Missing PDB.
- Missing ownership labels.
- Missing rollout and rollback plan.
- Missing dependency and storage assumptions.

### Expected Outcome

The manifest should not be approved for production without more information.

The reviewer should ask for application behavior, SLO, resource evidence, health-check semantics, dependency behavior, rollout compatibility, security posture, and observability.

## Scenario Review 1: Node Drain During Business Hours

A platform engineer drains a node during business hours. A critical API has three replicas and a PDB requiring `minAvailable: 3`.

The drain blocks.

### Questions

1. Why did the drain block?
2. Is the PDB wrong, or is the replica count wrong?
3. What tradeoff is the application owner expressing with `minAvailable: 3`?
4. What should the SRE check before changing the PDB?
5. What would happen if the engineer directly deleted Pods instead of using eviction?

### Expected Reasoning

The PDB requires all three replicas to remain available during voluntary disruption. That may be intentional for a critical service, but it means there is no disruption budget. The team must either increase replicas, accept maintenance constraints, or adjust availability expectations. Direct deletion can bypass PDB protection and should not be used as a casual workaround.

## Scenario Review 2: Storage Incident After Rescheduling

A database Pod moves to a new node and remains stuck in `ContainerCreating` with volume attach errors.

### Questions

1. What Kubernetes objects should be inspected first?
2. What storage topology issue might cause this?
3. Why might `WaitForFirstConsumer` matter?
4. What should the SRE avoid deleting during the incident?
5. Why is a PVC not the same thing as a backup?

### Expected Reasoning

Inspect the Pod, PVC, PV, StorageClass, events, node zone, and CSI components. Zonal storage, node affinity, or an already attached volume may block the Pod. Avoid deleting PVCs, PVs, or backend volumes without understanding reclaim policy and data impact.

## Scenario Review 3: Service Outage with Running Pods

A Service is returning errors. The Deployment has all desired replicas, and all Pods show `Running`.

### Questions

1. Why is `Running` not enough to prove service health?
2. What should be checked next?
3. How can readiness affect Service routing?
4. What role do EndpointSlices play?
5. What application signals should be checked?

### Expected Reasoning

Running means the Pod is scheduled and containers may be running; it does not prove the application is ready or serving correctly. Check readiness, Service selectors, EndpointSlices, Pod logs, events, dependency health, request latency, error rate, and user-facing checks.

## Scenario Review 4: Over-Permissive Service Account

A workload ServiceAccount is bound to `cluster-admin` because the team had trouble installing a controller.

### Questions

1. What is the blast-radius risk?
2. How should permissions be reduced?
3. What commands help inspect effective access?
4. Why is a dedicated ServiceAccount important?
5. What should be monitored after changing RBAC?

### Expected Reasoning

A compromised Pod could perform cluster-wide actions. Replace broad permissions with minimal Roles or ClusterRoles, verify with `kubectl auth can-i`, and monitor controller health after narrowing access.

## Practical Review: Production Approval Checklist

Use this checklist before approving a Chapter 1-level workload for production.

| Area | Required Evidence |
| --- | --- |
| Ownership | Service owner, on-call owner, escalation path. |
| Criticality | Service tier, SLO, user impact. |
| Architecture | Stateless or stateful model documented. |
| Replicas | Replica count matches availability target. |
| Probes | Startup, readiness, and liveness semantics reviewed. |
| Resources | Requests and limits based on test or production evidence. |
| Rollout | Rolling update and rollback behavior understood. |
| Network | Service, DNS, ingress, egress, and policy documented. |
| Storage | PVCs, reclaim policy, backups, and restore path understood. |
| Security | ServiceAccount, RBAC, Pod security, and Secrets reviewed. |
| Reliability | PDB, topology, failure domains, and autoscaling reviewed. |
| Observability | Logs, metrics, traces, alerts, and dashboards ready. |
| Dependencies | External dependency failure behavior documented. |
| Operations | Runbook, incident response, and maintenance expectations defined. |

Produce a short engineering review with these sections:


The goal is to practice professional judgment. Kubernetes production readiness is not a binary property of a YAML file. It is the result of design, evidence, ownership, and operational readiness.

## Chapter 1 Completion Criteria

A reader is ready to move beyond Chapter 1 when they can:

- Explain Kubernetes as an API-driven control system.
- Distinguish Kubernetes responsibilities from application, platform, and provider responsibilities.
- Read common workload manifests and identify production risks.
- Explain Pods, Deployments, Services, PVCs, StorageClasses, ServiceAccounts, RBAC, probes, PDBs, and resource requests.
- Troubleshoot a basic workload failure using `kubectl describe`, events, logs, and object status.
- Recognize common anti-patterns before they reach production.
- Ask better questions during design reviews and incidents.
