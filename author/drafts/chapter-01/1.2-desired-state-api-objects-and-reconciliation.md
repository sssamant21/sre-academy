# 1.2 Desired State, API Objects, and Reconciliation

## Purpose of This Section

This section explains the most important operating idea in Kubernetes: engineers do not usually tell Kubernetes every step to perform. They describe the desired state of the system through API objects, and Kubernetes control loops continuously work to move the actual state closer to that desired state.

This model is simple to describe, but it is responsible for many production behaviors that surprise teams:

- Pods may be recreated after deletion.
- A rollout may continue even after a single command returns successfully.
- A Service may stop sending traffic to a Pod even though the Pod still exists.
- A controller may replace a failed workload without a human operator taking action.
- A cluster may remain functional while some components are retrying, reconciling, or waiting for capacity.

For SREs, Kubernetes is not only a container platform. It is an API-driven reconciliation system.

By the end of this section, the reader should be able to explain how Kubernetes uses objects, specs, status, metadata, controllers, and reconciliation loops to operate production workloads.

## The Core Kubernetes Contract

The core contract in Kubernetes is:

```text
Declare desired state.
Store it through the Kubernetes API.
Let controllers observe actual state.
Let controllers take action to reduce the difference.
Report current state back through status.
Repeat continuously.
```

This is different from a traditional imperative operations model.

In an imperative model, an operator might say:

```text
Start three application processes on these three machines.
Add them to a load balancer.
Restart a failed process.
Remove bad instances from rotation.
Run the upgrade in this order.
```

In Kubernetes, the operator usually says:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: payments-api
          image: example.com/payments-api:1.0.0
          ports:
            - containerPort: 8080
```

The Deployment is the desired state. Kubernetes components decide how to make that state real, observe whether it remains true, and take corrective action when reality changes.

## Kubernetes Objects

Kubernetes objects are persistent records stored through the Kubernetes API. They represent the state of the cluster and the intent of the users or automation systems that created them.

A Kubernetes object can describe many kinds of intent:

- A workload that should run.
- A stable network identity for changing Pods.
- A configuration value that should be mounted into a workload.
- A storage claim that should be bound to persistent storage.
- A policy that controls what a workload is allowed to do.
- A custom platform resource created by an operator.

Common object kinds include:

| Object Kind | Production Purpose |
| --- | --- |
| Pod | Represents one or more containers scheduled together on a node. |
| Deployment | Manages stateless replicated application rollout and replacement. |
| ReplicaSet | Maintains a stable number of matching Pods, usually controlled by a Deployment. |
| StatefulSet | Manages ordered, identity-aware workloads such as databases and clustered systems. |
| DaemonSet | Runs one Pod per matching node, often for agents such as logging or monitoring. |
| Job | Runs finite work until completion. |
| CronJob | Runs Jobs on a schedule. |
| Service | Provides stable network access to changing Pod backends. |
| ConfigMap | Stores non-secret configuration data. |
| Secret | Stores sensitive data that workloads can consume. |
| PersistentVolumeClaim | Requests persistent storage for a workload. |
| Ingress | Exposes HTTP or HTTPS routes through an ingress controller. |
| Namespace | Provides a logical boundary for names, policies, and resource organization. |

SREs should think of these objects as operational contracts. A Deployment is not just YAML. It is a contract that says a certain number of application replicas should exist, match a template, and roll forward according to a configured strategy.

## Spec and Status

Most Kubernetes objects have a `spec` and a `status`.

The `spec` describes desired state. It is usually written by a human, CI/CD pipeline, GitOps controller, operator, or another automation system.

The `status` describes observed state. It is usually written by Kubernetes controllers or components that report what is actually happening.

```text
+-------------------------------+
| Kubernetes Object             |
+-------------------------------+
| metadata: name, labels, uid   |
| spec: desired state           |
| status: observed state        |
+-------------------------------+
```

For a Deployment, the `spec` might say that three replicas should run. The `status` might report how many replicas exist, how many are ready, how many are available, and whether rollout conditions are progressing.

This separation is one of the reasons Kubernetes is useful for operations. Engineers can compare intent against reality.

```bash
kubectl get deployment payments-api
kubectl describe deployment payments-api
kubectl get deployment payments-api -o yaml
```

A healthy system is not one where every object is perfectly still. A healthy Kubernetes system is one where controllers can observe changes, act on them, and report status accurately enough for operators and automation to make decisions.

## Metadata, Labels, and Ownership

Kubernetes objects also include metadata. Metadata is not decoration. In production, metadata is part of the operating model.

Important metadata includes:

- `name`: the object name within its scope.
- `namespace`: the namespace where the object lives, when applicable.
- `uid`: the unique identity assigned by Kubernetes.
- `labels`: key-value pairs used for selection and grouping.
- `annotations`: key-value metadata used by tools, controllers, and integrations.
- `ownerReferences`: relationships that connect dependent objects to their owners.

Labels are especially important because many Kubernetes controllers and Services use selectors.

```yaml
selector:
  matchLabels:
    app: payments-api
```

A Service does not usually send traffic to Pods because of their names. It sends traffic to endpoints selected through labels. A Deployment does not manage arbitrary Pods. It manages Pods that match its selector and template relationship.

This is why label mistakes can become production incidents.

## Reconciliation

Reconciliation is the process of comparing desired state with actual state and taking action to reduce the difference.

A controller usually follows this pattern:

```text
Watch objects.
Read desired state from spec.
Observe actual state.
Calculate the difference.
Create, update, delete, or report as needed.
Update status.
Repeat.
```

A Deployment controller does not run containers directly. It manages ReplicaSets. ReplicaSets manage Pods. The scheduler assigns unscheduled Pods to nodes. The kubelet on each node asks the container runtime to run containers.

```text
Deployment spec
      |
      v
Deployment controller
      |
      v
ReplicaSet
      |
      v
Pods
      |
      v
Scheduler assigns Pods to Nodes
      |
      v
Kubelet runs containers through container runtime
```

The important SRE lesson is that Kubernetes behavior is distributed across multiple controllers and components. When a workload does not reach the desired state, there may not be one single failing command. There may be a broken step in the reconciliation chain.

## Production Example: Deployment Replacement

Assume a Deployment declares three replicas:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
    spec:
      containers:
        - name: checkout-api
          image: example.com/checkout-api:2.4.1
```

If one Pod exits because the node loses power, Kubernetes does not treat the deleted Pod as the desired state. The desired state is still three replicas.

A simplified flow looks like this:

```text
1. Node failure changes actual state.
2. Node and Pod status eventually reflect the failure.
3. ReplicaSet observes fewer available matching Pods than desired.
4. ReplicaSet creates a replacement Pod object.
5. Scheduler assigns the new Pod to a suitable node.
6. Kubelet starts the containers.
7. Status updates report progress back through the API.
```

This behavior is powerful, but it is not magic. Replacement depends on scheduling capacity, image availability, storage attach behavior, networking, quotas, policies, and application readiness.

## Real-Time Use Case: Traffic Safety During Rollout

A team deploys a new version of an API. The Deployment controller creates new Pods. The kubelet starts containers. The readiness probe decides whether each new Pod should receive traffic.

If the application process starts but cannot connect to its database, the container may be running while the readiness probe fails.

That distinction matters.

```text
Container running: yes
Application ready: no
Service traffic: no
```

The Service should not route normal traffic to an unready Pod. This lets Kubernetes separate process existence from service readiness.

For SREs, this creates a practical rule: do not treat `Running` as the same thing as healthy. A Pod can be running and still be unavailable to users.

## Common Failure Scenarios

### Desired State Cannot Be Scheduled

A Deployment may ask for more replicas than the cluster can place.

Common causes include:

- CPU or memory requests are too high.
- Node selectors do not match any nodes.
- Taints require tolerations that the Pod does not have.
- Persistent volumes cannot attach in the target zone.
- Pod topology spread rules are too strict for available capacity.
- Quotas prevent new objects from being created.

Useful commands:

```bash
kubectl get pods -n production
kubectl describe pod <pod-name> -n production
kubectl get events -n production --sort-by=.lastTimestamp
```

### Desired State Is Wrong

Kubernetes can faithfully reconcile a bad desired state.

Examples:

- The image tag points to a broken build.
- The readiness probe checks the wrong path.
- The Service selector matches no Pods.
- The Deployment selector matches unexpected Pods.
- Resource requests are too small, causing CPU throttling or eviction pressure.
- A configuration value is syntactically valid but operationally wrong.

Kubernetes does not know business intent. It can converge on the state it was given, even when that state causes an outage.

### Status Is Delayed or Incomplete

Status is reported by controllers and node agents. During failures, status may lag behind reality.

Examples:

- A node is partitioned from the API server.
- A kubelet cannot post status updates.
- A controller is delayed because of API server pressure.
- An admission webhook slows or blocks object updates.
- A cloud provider API is slow to report load balancer or volume state.

SREs should understand that Kubernetes status is an observed signal, not an omniscient truth.

## SRE Insight

Kubernetes incidents often happen in the gap between desired state and actual state.

A strong incident response starts by identifying which part of the contract is broken:

| Question | What It Tells You |
| --- | --- |
| What did we ask Kubernetes to do? | Desired state from `spec`. |
| What does Kubernetes report? | Observed state from `status`. |
| Which controller owns the object? | The reconciliation path. |
| What events were emitted? | Recent scheduling, pulling, probing, or policy failures. |
| What changed most recently? | The likely source of new desired state. |
| Is the workload ready or only running? | Whether users should receive traffic. |

Do not start by deleting random Pods. Start by understanding the controller that will recreate them.

## Engineering Note: Declarative Does Not Mean Hands-Off

Declarative infrastructure reduces repetitive manual operations, but it does not remove engineering responsibility.

Engineers still need to design:

- Safe rollout strategies.
- Useful readiness and liveness probes.
- Correct resource requests and limits.
- Clear ownership labels.
- Alerting based on user impact and control-plane signals.
- Runbooks for failed reconciliation.
- Capacity plans for peak demand and failure recovery.

Kubernetes gives the platform a control model. SREs still own whether that model is safe for production.

## Lab: Observe Desired State and Status

This lab is safe for a local or non-production cluster.

### Prerequisites

- Access to a Kubernetes cluster.
- `kubectl` configured for the target cluster.
- Permission to create and delete objects in a test namespace.

### Create a Namespace

```bash
kubectl create namespace sre-lab
```

### Create a Deployment

```bash
kubectl create deployment desired-state-demo \
  --image=nginx:1.27 \
  --replicas=3 \
  --namespace=sre-lab
```

### Compare Spec and Status

```bash
kubectl get deployment desired-state-demo -n sre-lab -o yaml
kubectl get pods -n sre-lab -l app=desired-state-demo
```

Look for:

- `.spec.replicas`
- `.status.replicas`
- `.status.readyReplicas`
- `.status.availableReplicas`
- Pod labels
- Owner references

### Delete One Pod

```bash
kubectl delete pod -n sre-lab -l app=desired-state-demo
kubectl get pods -n sre-lab -l app=desired-state-demo --watch
```

Expected behavior:

- The selected Pods are deleted.
- The ReplicaSet creates replacement Pods.
- The Deployment returns toward three replicas.

Stop the watch with `Ctrl+C`.

### Scale the Deployment

```bash
kubectl scale deployment desired-state-demo \
  --replicas=5 \
  --namespace=sre-lab

kubectl get deployment desired-state-demo -n sre-lab
kubectl get pods -n sre-lab -l app=desired-state-demo
```

Expected behavior:

- The Deployment desired state changes to five replicas.
- Kubernetes creates additional Pods.
- Status catches up after scheduling and startup complete.

### Clean Up

```bash
kubectl delete namespace sre-lab
```

## Runbook: Workload Not Converging

Use this when a Deployment, StatefulSet, DaemonSet, Job, or other controller-managed workload is not reaching its desired state.

### 1. Confirm Desired State

```bash
kubectl get deployment <name> -n <namespace> -o yaml
```

Check:

- `spec.replicas`
- selectors
- Pod template labels
- image
- probes
- resource requests
- node selectors, affinity, and tolerations

### 2. Confirm Observed State

```bash
kubectl get deployment <name> -n <namespace>
kubectl describe deployment <name> -n <namespace>
```

Check:

- ready replicas
- available replicas
- unavailable replicas
- rollout conditions
- events

### 3. Inspect Pods

```bash
kubectl get pods -n <namespace> -l <selector-key>=<selector-value>
kubectl describe pod <pod-name> -n <namespace>
```

Look for:

- `Pending`
- `ImagePullBackOff`
- `CrashLoopBackOff`
- readiness failures
- eviction messages
- scheduling failures

### 4. Inspect Events

```bash
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

Events often show the first useful clue: failed scheduling, failed image pull, failed mount, failed probe, or denied admission.

### 5. Identify the Broken Reconciliation Step

| Symptom | Likely Area |
| --- | --- |
| Pods are not created | Controller, quota, admission, selector issue. |
| Pods are Pending | Scheduler, capacity, affinity, taints, volumes. |
| Pods are running but not ready | Readiness probe, application dependency, startup timing. |
| Pods restart repeatedly | Application crash, liveness probe, config, secret, resource pressure. |
| Service has no endpoints | Labels, readiness, selector mismatch. |
| Status is stale | Kubelet, controller delay, API server pressure, node partition. |

## Common Pitfalls

- Treating YAML as static configuration instead of an API object contract.
- Assuming `Running` means ready for user traffic.
- Debugging a child Pod without checking the owning controller.
- Changing labels without understanding selector impact.
- Deleting Pods repeatedly instead of fixing the desired state or controller issue.
- Assuming managed Kubernetes providers remove responsibility for workload reconciliation.
- Trusting a single status field without checking events and controller ownership.

## Summary

Kubernetes operates through API objects and reconciliation loops. Engineers declare desired state in object specs. Kubernetes components observe actual state, take action, and report status back through the API.

This model is the foundation for scheduling, rollouts, self-healing, service discovery, autoscaling, operators, GitOps, and platform automation.

For SREs, the practical skill is learning how to read the gap between desired state and actual state. That gap is where most Kubernetes troubleshooting begins.
