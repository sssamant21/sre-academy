# 1.3 Kubernetes Architecture at Production Scale

## Purpose of This Section

This section explains Kubernetes architecture from the perspective of engineers who operate production clusters.

Many introductions describe Kubernetes as a control plane and a set of worker nodes. That description is true, but it is not enough for SRE work. In production, architecture determines failure behavior, upgrade risk, troubleshooting paths, blast radius, security boundaries, and operational ownership.

A production engineer needs to understand:

- Which components make decisions.
- Which components store state.
- Which components run workloads.
- Which components report health.
- Which dependencies sit outside Kubernetes.
- Which failures Kubernetes can tolerate.
- Which failures require platform or provider intervention.

By the end of this section, the reader should be able to explain Kubernetes cluster architecture as an operational system, not only as a component diagram.

## The Production Architecture Mental Model

A Kubernetes cluster has two major areas:

- The control plane, which stores desired state, exposes the API, and runs control loops.
- Worker nodes, which run Pods and report node and workload state back to the control plane.

At a high level:

```text
Users, CI/CD, GitOps, Operators
              |
              v
+-----------------------------+
| Kubernetes API Server       |
+-------------+---------------+
              |
              v
+-----------------------------+
| etcd                        |
| Cluster state store         |
+-----------------------------+
              ^
              |
+-------------+---------------+
| Controllers and Scheduler   |
+-------------+---------------+
              |
              v
+-----------------------------+
| Worker Nodes                |
| kubelet + runtime + Pods    |
+-----------------------------+
```

This diagram is intentionally simple. The important idea is that nearly all durable cluster intent flows through the Kubernetes API. Components do not usually coordinate by directly calling each other as a tightly coupled monolith. They coordinate by reading and writing API objects and status.

## Control Plane Responsibilities

The control plane manages the overall state of the cluster.

It does not normally run application containers directly. It accepts API requests, stores state, schedules unscheduled Pods, runs controllers, and coordinates cluster behavior.

Core control-plane components include:

| Component | Production Responsibility |
| --- | --- |
| kube-apiserver | Exposes the Kubernetes HTTP API and acts as the front door for users, controllers, nodes, and integrations. |
| etcd | Stores Kubernetes API data as a consistent and highly available key-value store. |
| kube-scheduler | Watches for Pods that do not have a node assignment and selects suitable nodes. |
| kube-controller-manager | Runs built-in controllers that implement Kubernetes API behavior. |
| cloud-controller-manager | Integrates Kubernetes with cloud provider APIs when cloud integration is used. |

In production, control-plane health matters because every automation path depends on it. Existing workloads may continue running during some control-plane failures, but scheduling, rollouts, scaling, status updates, admission decisions, and many operational workflows can degrade or stop.

## kube-apiserver

The API Server is the front door of Kubernetes.

Every normal Kubernetes operation goes through it:

- `kubectl` commands.
- CI/CD deployments.
- GitOps reconciliation.
- Controller reads and writes.
- Scheduler decisions.
- Kubelet status updates.
- Admission webhooks.
- Operators and custom controllers.

The API Server validates requests, applies authentication and authorization, runs admission, handles API versioning, and persists accepted state to etcd.

Production implications:

- API Server latency can slow rollouts, controllers, autoscaling, and status visibility.
- API Server unavailability can block new changes even when existing Pods keep running.
- Poorly behaving controllers or clients can create excessive API load.
- Admission webhooks can become part of the critical path for object creation and updates.
- API access is a security boundary and must be monitored carefully.

SREs should treat the API Server as both a platform endpoint and a control-plane dependency.

## etcd

etcd is the persistent state store behind the Kubernetes API.

The API Server stores Kubernetes API data in etcd. That data includes objects such as Deployments, Pods, Services, Secrets, ConfigMaps, Nodes, and custom resources.

Production implications:

- etcd health directly affects the ability to read and write cluster state.
- etcd quorum matters in highly available clusters.
- Disk latency can affect etcd performance and therefore API Server behavior.
- Backups are critical because etcd contains the durable cluster state.
- Restores are operationally sensitive and must be practiced before a real incident.

A production Kubernetes backup strategy is incomplete without an etcd backup and restore strategy for clusters where the platform team owns etcd.

In managed Kubernetes services, the provider often operates the control plane and etcd, but the customer still needs to understand what data is represented in Kubernetes API objects and what must be backed up separately, such as application databases and persistent volumes.

## kube-scheduler

The scheduler assigns unscheduled Pods to suitable nodes.

A Pod is not placed on a node simply because capacity exists somewhere. The scheduler considers constraints and signals such as:

- Resource requests.
- Node selectors.
- Node affinity and anti-affinity.
- Taints and tolerations.
- Topology spread constraints.
- Persistent volume topology.
- Pod priority and preemption behavior.

Production implications:

- A workload can be healthy in configuration but remain Pending because no node satisfies its constraints.
- Overly strict placement rules can reduce resilience during failure.
- Missing resource requests can cause poor scheduling decisions.
- Zone-aware workloads require capacity in the correct zones.
- Storage topology can make a Pod unschedulable even when CPU and memory exist elsewhere.

SREs should troubleshoot `Pending` Pods as scheduling problems, not application runtime problems.

## kube-controller-manager

The controller manager runs built-in controllers that implement Kubernetes behavior.

Controllers continuously watch cluster state and take action to move actual state closer to desired state. Examples include controllers for Deployments, ReplicaSets, Jobs, Nodes, namespaces, endpoints, and service accounts.

Production implications:

- Controllers are responsible for much of the self-healing behavior that teams expect from Kubernetes.
- If controllers are delayed or unavailable, objects may stop converging.
- Controller behavior is eventually consistent, not instantaneous.
- The API may accept desired state before all side effects are complete.
- Controllers can create, update, or delete other objects as part of reconciliation.

A common incident mistake is assuming a successful API request means the system has already reached the requested state. In Kubernetes, acceptance and convergence are different phases.

## cloud-controller-manager

The cloud-controller-manager separates cloud-provider integration from the core Kubernetes control plane.

When enabled, cloud-specific controllers can integrate Kubernetes with provider APIs for behavior such as:

- Node lifecycle integration.
- Load balancer provisioning.
- Route management.
- Cloud-specific metadata and addresses.

Production implications:

- Cloud API rate limits or outages can affect Kubernetes operations.
- A Service of type `LoadBalancer` may depend on provider-side resources.
- Node lifecycle behavior can depend on cloud instance state.
- Network and storage behavior often crosses the Kubernetes and cloud-provider boundary.

Managed Kubernetes reduces the burden of operating these integrations, but it does not remove the need to understand them during incidents.

## Worker Node Responsibilities

Worker nodes run application workloads.

A node may be a virtual machine or a physical machine. Each node is managed by the control plane and includes services necessary to run Pods.

Core node components include:

| Component | Production Responsibility |
| --- | --- |
| kubelet | Node agent that communicates with the API Server and ensures assigned Pods are running. |
| container runtime | Runs containers for Pods through the Container Runtime Interface. |
| kube-proxy | Implements part of the Service networking behavior on nodes, depending on the cluster configuration. |
| CNI plugin | Provides Pod networking and network policy behavior, depending on the chosen implementation. |
| CSI plugin | Provides storage integration when Container Storage Interface drivers are used. |
| Node OS and kernel | Provide process isolation, networking, filesystem, cgroups, and resource enforcement primitives. |

A production node is not just compute capacity. It is a reliability boundary, security boundary, scheduling target, network participant, and storage attachment point.

## kubelet

The kubelet is the primary node agent.

It registers or works with the Node object, watches for Pods assigned to its node, starts containers through the container runtime, reports status, runs probes, and manages local Pod lifecycle behavior.

Production implications:

- If kubelet cannot reach the API Server, status updates may become stale.
- If kubelet is unhealthy, Pods on the node may not be managed correctly.
- Probe configuration affects whether workloads restart or receive traffic.
- Node pressure can lead to eviction decisions.
- Node identity and permissions are security-sensitive.

The kubelet is where desired state becomes running containers on a specific machine.

## Container Runtime

The container runtime runs containers.

Kubernetes does not run containers by itself. The kubelet uses a container runtime through the Container Runtime Interface.

Production implications:

- Runtime failures can prevent Pods from starting.
- Image pull failures often appear at the node/runtime boundary.
- Runtime storage pressure can affect workload startup and stability.
- Runtime logs and node-level diagnostics are important for deep incident response.

Common runtimes include containerd and CRI-O. Docker Engine is not the direct Kubernetes runtime interface in modern Kubernetes clusters unless a compatible CRI layer is present.

## kube-proxy, CNI, and Networking Dependencies

Kubernetes networking is implemented by a combination of Kubernetes objects and networking components.

Services, EndpointSlices, kube-proxy, CNI plugins, DNS, load balancers, ingress controllers, and cloud networking all contribute to traffic flow.

Production implications:

- A Service can exist even when it has no healthy endpoints.
- A Pod can be running while network policy blocks traffic.
- DNS failures can look like application failures.
- Node-level packet forwarding issues can affect only part of a cluster.
- Ingress or load balancer failures may sit outside the core Kubernetes API.

Networking architecture is one of the most important production design choices in a Kubernetes platform.

## Storage Dependencies

Kubernetes storage behavior depends on API objects, controllers, node plugins, and external storage systems.

PersistentVolumeClaims, PersistentVolumes, StorageClasses, CSI controllers, CSI node plugins, cloud disks, network filesystems, and backup systems all participate in production storage behavior.

Production implications:

- A Pod may be unschedulable because its volume can only attach in a specific zone.
- A volume attach or mount failure can block workload startup.
- Storage latency can become application latency.
- Persistent volume backup is separate from Kubernetes object backup.
- Stateful workloads require stronger architecture review than stateless workloads.

Kubernetes can orchestrate storage attachment and mounting, but it does not make every storage system highly available by default.

## Control Plane High Availability

A production cluster should avoid a single control-plane machine as a critical failure point.

Kubernetes high availability commonly includes:

- Multiple control-plane nodes.
- A stable API Server endpoint behind a load balancer.
- An odd number of etcd members for quorum.
- Control-plane components distributed across failure domains where possible.
- A tested etcd backup and restore plan.
- Upgrade and rollback procedures.

Two common self-managed HA topologies are:

| Topology | Description | Operational Trade-Off |
| --- | --- | --- |
| Stacked etcd | etcd members run on the same machines as control-plane components. | Simpler infrastructure, but a control-plane node failure also removes an etcd member. |
| External etcd | etcd members run on separate machines from control-plane components. | More infrastructure and operational complexity, but separates API/control-plane failure from etcd member placement. |

Managed Kubernetes services usually hide much of this control-plane implementation. SREs still need to understand the managed service SLA, upgrade model, maintenance behavior, API endpoint exposure, private cluster options, and limits.

## Production Cluster Topology Example

A typical production cluster might look like this:

```text
                         +----------------------+
                         | CI/CD and GitOps     |
                         +----------+-----------+
                                    |
                                    v
                         +----------------------+
                         | API Load Balancer    |
                         +----------+-----------+
                                    |
               +--------------------+--------------------+
               |                    |                    |
               v                    v                    v
      +----------------+    +----------------+    +----------------+
      | Control Plane  |    | Control Plane  |    | Control Plane  |
      | API/Controller |    | API/Controller |    | API/Controller |
      | Scheduler/etcd |    | Scheduler/etcd |    | Scheduler/etcd |
      +-------+--------+    +-------+--------+    +-------+--------+
              |                     |                     |
              +----------+----------+----------+----------+
                         |                     |
                         v                     v
            +----------------------+  +----------------------+
            | Worker Node Pool A   |  | Worker Node Pool B   |
            | App Pods             |  | App Pods             |
            | kubelet/runtime/CNI  |  | kubelet/runtime/CNI  |
            +----------------------+  +----------------------+
```

This example is simplified, but it highlights the operating relationships:

- Users and automation target the API endpoint.
- Control-plane instances must remain available enough to accept and reconcile changes.
- etcd must maintain quorum and durable state.
- Worker nodes must have enough capacity and healthy node services.
- Networking and storage dependencies must work across the selected failure domains.

## Managed Kubernetes Architecture

In managed Kubernetes, the cloud provider usually operates some or all of the control plane.

Examples include Amazon EKS, Azure AKS, and Google Kubernetes Engine.

The exact responsibility model depends on the service and mode. A provider may manage the API Server, scheduler, controllers, etcd, upgrades, and control-plane availability, while the customer remains responsible for workloads, namespaces, policies, nodes or node pools, networking choices, application reliability, and observability.

SREs should avoid two false assumptions:

| False Assumption | Better Operating View |
| --- | --- |
| Managed Kubernetes means no operations. | Managed Kubernetes shifts responsibility boundaries. It does not remove workload, networking, security, capacity, and incident ownership. |
| The provider owns every outage. | The provider owns managed service components. The platform team still owns configuration, workload behavior, dependencies, and many data-plane choices. |

A managed cluster still needs SLOs, runbooks, capacity planning, security review, backup strategy, and upgrade testing.

## Failure Domains

Production architecture is largely about failure domains.

A failure domain is a boundary where a failure can occur and affect some part of the system. Examples include:

- A single Pod.
- A node.
- A node pool.
- A rack.
- An availability zone.
- A region.
- An API Server instance.
- An etcd member.
- A network path.
- A cloud provider API.
- A storage backend.

Good Kubernetes architecture spreads risk across failure domains and avoids hidden single points of failure.

Examples:

- Multiple replicas across nodes protect against a single node failure.
- Zone-aware scheduling can protect against zone failure when capacity exists in other zones.
- Multiple control-plane nodes protect API availability in self-managed clusters.
- Multiple etcd members protect state availability when quorum remains.
- Multiple ingress replicas protect the edge path.
- Multiple CoreDNS replicas protect service discovery.

A cluster can have three worker nodes and still be fragile if all critical workloads land on one node, all nodes are in one zone, CoreDNS has one replica, or storage exists in only one failure domain.

## What Continues During Control Plane Failure

A common production question is: what happens if the control plane is unavailable?

The exact behavior depends on the failure, but the general pattern is:

| Capability | Expected Behavior During Control Plane Outage |
| --- | --- |
| Existing containers already running on healthy nodes | Often continue running. |
| Existing Service traffic between available endpoints | May continue if node networking and proxies are healthy. |
| New deployments | Usually blocked or delayed. |
| Scaling changes | Usually blocked or delayed. |
| New scheduling decisions | Blocked because scheduler and API state are unavailable. |
| Status visibility | Degraded or stale. |
| Controller-driven repair | Degraded or stopped. |
| Admission and policy decisions | Blocked for new API writes. |

This distinction matters during incidents. A cluster can continue serving some traffic while being unable to safely change state.

## What Fails During Node Failure

When a node fails, the behavior depends on workload design and cluster configuration.

Typical sequence:

```text
1. Kubelet heartbeats stop or become unreachable.
2. Node status eventually changes.
3. Node controller marks the node condition as Unknown or NotReady.
4. Pods on that node may be marked unavailable or evicted after configured timing.
5. Controllers create or maintain replacement Pods for controller-managed workloads.
6. Scheduler places replacements if suitable capacity exists.
7. Service endpoints update based on Pod readiness.
```

Important constraints:

- Standalone Pods are not replaced like Deployment-managed Pods.
- Stateful workloads may have storage and identity constraints.
- Replacement requires available capacity.
- Replacement requires schedulable nodes.
- Replacement may be delayed by image pulls, probes, admission, or storage attach.
- Application availability depends on replicas, readiness, and dependency behavior.

Node failure recovery is a system behavior, not a single feature.

## Observability Signals for Architecture Health

Architecture should be observable. SREs need signals for both the control plane and data plane.

Useful control-plane signals include:

- API Server availability and latency.
- API request rate and error rate.
- etcd leader changes, latency, database size, and quorum health.
- Scheduler pending Pod count and scheduling latency.
- Controller workqueue depth and reconciliation errors.
- Admission webhook latency and rejection rates.

Useful node and workload signals include:

- Node Ready condition.
- Node pressure conditions.
- Kubelet health and status update freshness.
- Pod restart count.
- Pending Pods.
- Image pull failures.
- Readiness and liveness probe failures.
- Service endpoint availability.
- CoreDNS errors and latency.
- CNI and CSI plugin errors.

The goal is not to collect every metric. The goal is to know whether the cluster can accept desired state, reconcile it, schedule it, run it, and serve traffic.

## Real-Time Use Case: Regional E-Commerce Platform

Consider an e-commerce platform running checkout, catalog, inventory, payments, and order processing services.

A production Kubernetes architecture might include:

- Separate node pools for stateless APIs, batch workers, ingress, and observability agents.
- Pod disruption budgets for critical services.
- Topology spread constraints across zones.
- Multiple CoreDNS replicas.
- Multiple ingress controller replicas.
- Dedicated monitoring for API Server latency, node readiness, and workload availability.
- Separate cloud-managed databases outside the cluster.
- GitOps-based deployment through the Kubernetes API.
- Backup coverage for Kubernetes objects, persistent volumes, and application databases.

During a zone failure, the platform should not depend on Kubernetes alone. It needs spare capacity in healthy zones, correct scheduling constraints, storage that supports the desired recovery model, and applications that tolerate dependency errors.

This is where architecture becomes SRE work.

## Common Failure Scenarios

### API Server Is Slow or Unavailable

Symptoms:

- `kubectl` commands hang or time out.
- CI/CD deployments fail.
- GitOps controllers report API errors.
- Controllers fall behind.
- Status appears stale.

Likely areas:

- API Server availability.
- etcd latency or quorum.
- Excessive API client traffic.
- Admission webhook latency.
- Network path to the API endpoint.
- Provider control-plane incident in managed services.

### etcd Is Unhealthy

Symptoms:

- API writes fail or become slow.
- Control-plane components report storage errors.
- Leader changes occur frequently.
- Cluster state reads are slow.

Likely areas:

- etcd quorum.
- Disk latency.
- Network latency between members.
- Database size and compaction.
- Certificate or peer communication issues.

### Pods Are Pending

Symptoms:

- Workload rollout starts but Pods never run.
- Deployment status shows unavailable replicas.
- Events mention scheduling failures.

Likely areas:

- Insufficient CPU or memory.
- Taints and tolerations.
- Affinity or topology constraints.
- Volume zone constraints.
- Namespace quota.
- Admission policy.

### Pods Run but Traffic Fails

Symptoms:

- Pods show `Running`.
- Users receive errors.
- Service has no endpoints or only some endpoints.
- Readiness probes fail.

Likely areas:

- Readiness probe configuration.
- Service selectors.
- EndpointSlice updates.
- Network policy.
- DNS.
- Ingress or load balancer path.
- Application dependency failure.

### Node Pool Is Unstable

Symptoms:

- Nodes repeatedly become NotReady.
- Pods are evicted.
- Image pulls are slow or failing.
- Disk, memory, or PID pressure appears.

Likely areas:

- Node OS health.
- Kubelet health.
- Container runtime health.
- CNI plugin health.
- Disk pressure.
- Cloud instance or autoscaler behavior.

## SRE Insight

A Kubernetes incident should be mapped onto architecture before it is mapped onto commands.

Ask these questions first:

| Question | Why It Matters |
| --- | --- |
| Is the API reachable? | Determines whether new desired state can be accepted. |
| Is etcd healthy? | Determines whether cluster state can be stored and read. |
| Are controllers reconciling? | Determines whether accepted state becomes action. |
| Is the scheduler placing Pods? | Determines whether workloads can move to nodes. |
| Are kubelets reporting status? | Determines whether node and Pod state is fresh. |
| Are Pods ready, not only running? | Determines whether traffic should flow. |
| Are networking and DNS healthy? | Determines whether services can communicate. |
| Are storage systems healthy? | Determines whether stateful workloads can start and recover. |

This architecture map prevents random troubleshooting and helps isolate the layer where the system is failing.

## Engineering Note: Architecture Is a Reliability Contract

A production Kubernetes architecture is a reliability contract between teams.

The platform team may own cluster components, node pools, admission policy, networking, storage integration, and upgrade process. Application teams may own manifests, probes, resource requests, rollout strategy, and application behavior. Security teams may own identity, policy, secrets, and audit review. Cloud teams may own account structure, VPCs, IAM, load balancers, and managed service configuration.

If these boundaries are unclear, incidents become slower because every failure becomes an ownership debate.

Good architecture documentation should answer:

- Who owns the API endpoint?
- Who owns node lifecycle?
- Who owns ingress and load balancer behavior?
- Who owns DNS?
- Who owns persistent volume backup and restore?
- Who owns admission policies?
- Who owns cluster upgrades?
- Who owns cloud provider limits and quotas?
- Who owns incident response for each layer?

## Best Practices

- Use multiple control-plane nodes for self-managed production clusters.
- Use an odd number of etcd members when operating etcd directly.
- Put the API Server behind a stable endpoint.
- Spread critical workloads across nodes and zones where the platform supports it.
- Keep CoreDNS, ingress controllers, CNI, CSI, and observability agents highly available.
- Define separate node pools when workloads have different isolation, scaling, or hardware needs.
- Use resource requests so the scheduler can make meaningful placement decisions.
- Monitor both control-plane and node-level health.
- Document managed-service responsibility boundaries.
- Practice restore procedures before a production incident.

## Common Pitfalls

- Treating a single-node cluster as a production architecture.
- Assuming existing Pods mean the control plane is healthy.
- Assuming a healthy API means workloads can schedule.
- Ignoring etcd backups in self-managed clusters.
- Running all critical addons as single replicas.
- Spreading Pods across nodes but not across zones.
- Designing topology without spare capacity for failure recovery.
- Treating cloud load balancers, DNS, and storage as invisible dependencies.
- Missing node pool ownership and upgrade responsibility.
- Debugging application symptoms without checking the architecture layer beneath them.

## Lab: Map a Cluster Architecture

This lab is safe for a local or non-production cluster.

### Prerequisites

- Access to a Kubernetes cluster.
- `kubectl` configured for the target cluster.
- Permission to read nodes, Pods, Services, and events.

### Inspect Nodes

```bash
kubectl get nodes -o wide
kubectl describe node <node-name>
```

Look for:

- Node roles.
- Kubernetes version.
- Container runtime.
- Internal and external addresses.
- Capacity and allocatable resources.
- Node conditions.
- Taints.
- Labels.

### Inspect Control-Plane Components

For clusters where control-plane components are visible as Pods:

```bash
kubectl get pods -n kube-system -o wide
```

Look for components such as:

- `kube-apiserver`
- `etcd`
- `kube-scheduler`
- `kube-controller-manager`
- `coredns`
- CNI Pods
- CSI Pods

Managed Kubernetes services may hide some control-plane components. In that case, record what the provider exposes and which dashboards, APIs, or service health pages are used instead.

### Inspect Workload Placement

```bash
kubectl get pods -A -o wide
```

Look for:

- Whether critical system Pods are spread across nodes.
- Whether application replicas are concentrated on one node.
- Whether Pods are stuck Pending.
- Whether node pools or zones are visible through labels.

### Inspect Services and Endpoints

```bash
kubectl get services -A
kubectl get endpointslices -A
```

Look for:

- Services without endpoints.
- LoadBalancer Services.
- Ingress or Gateway-related Services.
- Namespace ownership patterns.

### Inspect Recent Events

```bash
kubectl get events -A --sort-by=.lastTimestamp
```

Look for architecture-related failures:

- Failed scheduling.
- Failed image pulls.
- Failed mounts.
- Probe failures.
- Node readiness changes.
- Admission denials.

## Runbook: Identify the Failing Architecture Layer

Use this runbook when a Kubernetes incident is unclear.

### 1. Confirm API Access

```bash
kubectl version
kubectl get --raw=/readyz
```

If API access fails, check network path, credentials, API endpoint health, provider status, and control-plane monitoring.

### 2. Check Nodes

```bash
kubectl get nodes
kubectl describe node <node-name>
```

Look for:

- `Ready` condition.
- Memory pressure.
- Disk pressure.
- PID pressure.
- Network unavailable.
- Kubelet status freshness.

### 3. Check Pending and Failing Pods

```bash
kubectl get pods -A --field-selector=status.phase=Pending
kubectl get pods -A | grep -E "CrashLoopBackOff|ImagePullBackOff|Error|Evicted"
```

PowerShell alternative:

```powershell
kubectl get pods -A | Select-String "CrashLoopBackOff|ImagePullBackOff|Error|Evicted"
```

### 4. Check Events

```bash
kubectl get events -A --sort-by=.lastTimestamp
```

Events often identify scheduling, volume, image, probe, and admission failures.

### 5. Check System Addons

```bash
kubectl get pods -n kube-system
kubectl get deployment -n kube-system
kubectl get daemonset -n kube-system
```

Pay attention to CoreDNS, CNI, CSI, kube-proxy, metrics components, and provider-specific agents.

### 6. Map the Failure

| Evidence | Likely Layer |
| --- | --- |
| API timeout | API endpoint, API Server, etcd, network, provider control plane. |
| Pods Pending | Scheduler, capacity, constraints, storage topology, quota. |
| Nodes NotReady | Kubelet, node OS, runtime, CNI, cloud instance, network. |
| Pods Running but not Ready | Application health, readiness probe, dependencies. |
| Service has no endpoints | Labels, readiness, EndpointSlice controller, selector mismatch. |
| DNS failures | CoreDNS, node DNS configuration, network policy, upstream DNS. |
| Volume attach failures | CSI, cloud provider API, zone topology, storage backend. |

## Summary

Kubernetes architecture is a distributed operating model built around an API-driven control plane and worker nodes that run workloads.

The control plane accepts and stores desired state, schedules Pods, and runs controllers. Worker nodes run Pods through kubelet, a container runtime, and supporting networking and storage components.

At production scale, reliability depends on more than the core Kubernetes binaries. It also depends on etcd health, API availability, node health, CNI, CSI, DNS, ingress, cloud-provider integrations, capacity, failure-domain design, and clear ownership boundaries.

SREs operate Kubernetes well when they can map symptoms to architecture layers and understand which component is responsible for the next action.
