# 1.4 Control Plane and Node Responsibility Boundaries

## Purpose of This Section

This section explains who is responsible for what inside a Kubernetes cluster.

Kubernetes is a distributed system. A workload reaches production only after several components accept, store, schedule, start, route, observe, and reconcile state. During an incident, engineers often lose time because they treat Kubernetes as one thing instead of a set of responsibility boundaries.

A Pod that is not serving traffic might involve:

- The API Server accepting the object.
- Admission allowing or rejecting the request.
- etcd storing cluster state.
- The scheduler assigning a node.
- The kubelet starting containers.
- The container runtime pulling and running images.
- CNI providing networking.
- kube-proxy or an alternative dataplane implementing Service behavior.
- EndpointSlice controllers reflecting readiness.
- CSI attaching and mounting storage.
- Cloud controllers provisioning external infrastructure.
- The application becoming ready.

Each layer has a different owner, failure mode, and troubleshooting path.

By the end of this section, the reader should be able to map Kubernetes symptoms to the responsible component or team boundary.

## The Boundary Model

A useful production model is:

```text
Intent Boundary
  Humans, CI/CD, GitOps, operators, policies

API Boundary
  kube-apiserver, authentication, authorization, admission

State Boundary
  etcd, API objects, status, events

Decision Boundary
  scheduler, controllers, cloud controllers

Node Boundary
  kubelet, container runtime, node OS, CNI, CSI, kube-proxy

Application Boundary
  application process, probes, config, dependencies, data

Provider Boundary
  cloud APIs, load balancers, disks, IAM, networks, managed control plane
```

This model helps SREs avoid random debugging. When something fails, ask which boundary stopped making progress.

## Responsibility Matrix

| Layer | Owns | Does Not Own |
| --- | --- | --- |
| User or automation | Desired state, manifests, deployment timing, configuration intent. | Internal controller implementation or node runtime behavior. |
| API Server | API endpoint, validation, authentication, authorization, admission flow, accepted writes. | Running containers or making application code healthy. |
| etcd | Durable Kubernetes API data. | Application databases, persistent volume contents, or external systems. |
| Scheduler | Assigning unscheduled Pods to suitable nodes. | Starting containers or making nodes healthy. |
| Controllers | Reconciling API objects toward desired state. | Guaranteeing infinite capacity or fixing bad desired state. |
| Cloud controllers | Translating selected Kubernetes objects into cloud-provider actions. | Owning all cloud account, quota, IAM, or network design choices. |
| Kubelet | Managing assigned Pods on a node and reporting node and Pod status. | Scheduling Pods or providing cluster-wide policy. |
| Container runtime | Pulling images and running containers. | Kubernetes API policy, Service routing, or application correctness. |
| CNI | Pod networking implementation and often NetworkPolicy behavior. | Application protocol correctness or DNS records outside its scope. |
| CSI | Storage attach, mount, and volume integration behavior. | Application-level data backup and database consistency. |
| Application team | Code, readiness behavior, dependency handling, resource needs, release safety. | Control-plane availability or provider infrastructure health. |
| Platform team | Cluster configuration, addons, node pools, policies, upgrades, observability, reliability guardrails. | Application business logic or every workload-specific failure. |
| Cloud provider | Managed service components according to the service contract. | Customer workload design, RBAC, manifests, many data-plane choices, and application operations. |

The exact boundary changes depending on whether the cluster is self-managed, partially managed, or fully managed.

## API Server Boundary

The API Server owns the Kubernetes API boundary.

It receives requests from users and components, authenticates callers, authorizes actions, applies admission, validates objects, and persists accepted state.

The API Server is responsible for:

- Exposing the Kubernetes HTTP API.
- Enforcing authentication and authorization decisions.
- Running admission control in the request path.
- Serving object reads and writes.
- Coordinating access to stored API data.
- Providing the interface used by controllers, scheduler, kubelets, clients, and operators.

The API Server is not responsible for:

- Making a bad manifest safe.
- Creating cloud capacity by itself.
- Starting containers on nodes.
- Making an application pass readiness.
- Ensuring external databases are reachable.
- Fixing webhook services that are unavailable.

Production interpretation:

If an object is rejected, inspect authentication, authorization, schema validation, admission, quotas, and policies. If an object is accepted but not converging, move downstream to controllers, scheduler, nodes, networking, storage, or application readiness.

## etcd Boundary

etcd owns durable Kubernetes API state.

It stores the data that the API Server accepts. This includes built-in resources and custom resources. In self-managed clusters, etcd operation is one of the most critical platform responsibilities.

etcd is responsible for:

- Persisting Kubernetes API data.
- Supporting consistent reads and writes for the API Server.
- Maintaining quorum in an HA etcd cluster.
- Preserving cluster state across control-plane restarts when healthy.

etcd is not responsible for:

- Application database contents.
- Files inside persistent volumes.
- Container image registry state.
- Object correctness.
- Workload readiness.
- External provider configuration.

Production interpretation:

If etcd is unhealthy, Kubernetes may not reliably read or write cluster state. Existing workloads can continue for a time, but the cluster control model is impaired. Backups and restore procedures must be designed and tested before incidents.

## Scheduler Boundary

The scheduler owns Pod placement decisions for Pods that are not yet assigned to nodes.

The scheduler is responsible for:

- Watching for unscheduled Pods.
- Filtering and scoring candidate nodes.
- Respecting resource requests and scheduling constraints.
- Binding Pods to selected nodes.

The scheduler is not responsible for:

- Starting containers after placement.
- Pulling images.
- Making storage attach successfully.
- Making an unhealthy node healthy.
- Rewriting impossible constraints.
- Guaranteeing that cluster capacity exists.

Production interpretation:

A `Pending` Pod is often a scheduler or capacity signal. Look at events before debugging application logs, because a Pending Pod usually has no running application process to inspect.

## Controller Boundary

Controllers own reconciliation.

A controller watches cluster state and makes or requests changes that move current state closer to desired state.

Controllers are responsible for:

- Observing API objects.
- Comparing desired and observed state.
- Creating, updating, or deleting dependent objects.
- Updating status.
- Retrying reconciliation when possible.

Controllers are not responsible for:

- Guaranteeing immediate convergence.
- Fixing invalid business intent.
- Overriding admission policy.
- Creating unlimited infrastructure capacity.
- Making external dependencies healthy.

Production interpretation:

When an API write succeeds but the expected side effect does not happen, ask which controller owns the next step. A Deployment, Job, Service, Node, endpoint, volume, or cloud resource may each involve a different controller.

## Cloud Controller Boundary

The cloud-controller-manager connects Kubernetes to cloud-provider APIs.

It separates cloud-specific control logic from the core Kubernetes control plane. Depending on the provider and cluster configuration, it may participate in node lifecycle, route management, and load balancer provisioning.

Cloud controllers are responsible for:

- Translating selected Kubernetes intent into provider API actions.
- Updating Kubernetes objects with cloud-specific information.
- Coordinating provider-backed resources such as load balancers where supported.
- Participating in cloud-aware node lifecycle behavior.

Cloud controllers are not responsible for:

- All cloud account design.
- All IAM design.
- All network design.
- Provider quota planning unless the managed service explicitly owns it.
- Application dependency reliability.
- Business continuity outside the Kubernetes integration path.

Production interpretation:

If a `LoadBalancer` Service is stuck pending, the problem may be outside core Kubernetes. Check cloud quotas, permissions, subnet tags, routes, security rules, and provider events.

## Kubelet Boundary

The kubelet owns node-local Pod execution for Pods assigned to its node.

The kubelet is responsible for:

- Registering or working with the Node object.
- Watching assigned Pods.
- Asking the container runtime to run containers.
- Running configured probes.
- Reporting Pod and Node status.
- Managing node-local Pod lifecycle behavior.

The kubelet is not responsible for:

- Selecting which node should run a Pod.
- Creating Deployments or ReplicaSets.
- Managing cluster-wide desired state.
- Provisioning cloud load balancers.
- Making application dependencies healthy.

Production interpretation:

If a Pod is assigned to a node but not running correctly, inspect kubelet events, container runtime behavior, image pulls, probes, mounts, node pressure, and node conditions.

## Container Runtime Boundary

The container runtime owns container execution.

Kubernetes relies on a runtime that implements the Container Runtime Interface. Common runtimes include containerd and CRI-O.

The runtime is responsible for:

- Pulling container images when required.
- Creating and starting containers.
- Managing container lifecycle at runtime level.
- Exposing runtime status to kubelet.

The runtime is not responsible for:

- Kubernetes scheduling decisions.
- Kubernetes API authorization.
- Service endpoint selection.
- Application correctness.
- Cluster-level rollout strategy.

Production interpretation:

Image pull errors, container start failures, and low-level runtime failures often belong at the kubelet/runtime/node boundary, not the scheduler boundary.

## CNI Boundary

The Container Network Interface implementation owns Pod networking behavior for the cluster.

The exact behavior depends on the CNI plugin. Some CNIs also implement NetworkPolicy, encryption, routing, observability, or eBPF-based dataplanes.

The CNI layer is responsible for:

- Pod network attachment.
- Pod IP assignment, depending on implementation.
- Node-to-Pod and Pod-to-Pod routing behavior.
- NetworkPolicy enforcement, when supported and enabled.
- Provider or overlay network integration, depending on implementation.

The CNI layer is not responsible for:

- Application-level protocol correctness.
- DNS records outside the cluster.
- Service selector correctness.
- Ingress controller configuration unless the product combines those features.
- Cloud firewall rules outside its configured scope.

Production interpretation:

If Pods are running but cannot communicate, check Service selectors, EndpointSlices, DNS, NetworkPolicy, CNI health, node routing, and cloud network controls.

## kube-proxy and Service Dataplane Boundary

kube-proxy is one implementation path for Kubernetes Service networking on nodes.

Depending on the cluster, Service dataplane behavior may be implemented through iptables, IPVS, eBPF, or provider-specific mechanisms.

The Service dataplane is responsible for:

- Implementing traffic forwarding for Service virtual IPs or equivalent behavior.
- Keeping node-level routing or forwarding rules aligned with Service and endpoint state.
- Supporting Service access patterns according to the cluster implementation.

The Service dataplane is not responsible for:

- Making Pods ready.
- Choosing correct labels.
- Fixing application listener ports.
- Fixing ingress, DNS, or load balancer configuration outside its scope.

Production interpretation:

If a Service exists but traffic fails, separate three questions: does the Service select endpoints, are endpoints ready, and does the dataplane forward traffic correctly?

## CSI Boundary

The Container Storage Interface layer owns storage integration between Kubernetes and storage providers.

The exact responsibility depends on the CSI driver and storage backend.

CSI components are responsible for:

- Provisioning volumes when dynamic provisioning is configured.
- Attaching and detaching volumes where the storage system requires it.
- Mounting volumes on nodes.
- Reporting storage operation failures through Kubernetes events and status.

CSI components are not responsible for:

- Application-level data consistency.
- Database backup correctness.
- Choosing a recovery point objective.
- Making every volume multi-zone or multi-writer.
- Protecting against accidental data deletion unless the storage system and policy support it.

Production interpretation:

If a stateful Pod is Pending or stuck creating, check PVC binding, StorageClass, volume topology, attach events, mount events, CSI controller health, CSI node plugin health, and storage backend status.

## Application Boundary

Application teams own the behavior of the application running inside Kubernetes.

Kubernetes can restart, reschedule, route, and observe workloads, but it cannot make an unsafe application safe.

Application teams are responsible for:

- Application code behavior.
- Container image contents.
- Startup behavior.
- Readiness and liveness semantics.
- Graceful shutdown.
- Resource request accuracy.
- Dependency timeouts and retries.
- Backward-compatible releases.
- Data migration safety.
- Application SLOs and user-impact signals.

Application teams are not responsible for:

- Control-plane implementation.
- etcd operation in managed clusters.
- Node OS patching when the platform owns node images.
- Cluster-wide admission policy implementation.
- Cloud provider service availability.

Production interpretation:

If Kubernetes starts the container and routes only ready endpoints, but the application returns errors, the incident may have moved above the Kubernetes platform boundary.

## Platform Team Boundary

The platform team owns the Kubernetes platform as a product.

Platform responsibilities usually include:

- Cluster lifecycle.
- Node pool design.
- Addon lifecycle.
- CNI and CSI integration.
- Ingress and Gateway architecture.
- Admission policies.
- RBAC guardrails.
- Namespace and tenancy model.
- Observability baseline.
- Upgrade process.
- Backup and restore strategy.
- Incident runbooks.
- Capacity and quota management.

The platform team should not own every application incident by default. Instead, it should provide clear contracts, safe defaults, and escalation paths.

Production interpretation:

A mature platform team does not only run clusters. It defines the operational contract that lets application teams use Kubernetes safely.

## Managed Kubernetes Boundary

Managed Kubernetes changes responsibility boundaries.

In self-managed Kubernetes, the platform team may own the API Server, etcd, scheduler, controller manager, cloud controller manager, certificates, upgrades, operating system, nodes, networking, storage plugins, and addons.

In managed Kubernetes, the provider usually owns more of the control plane. The customer still owns workload design, access configuration, many data-plane choices, application reliability, and incident response for customer-controlled configuration.

Examples:

| Service | Provider Responsibility Examples | Customer Responsibility Examples |
| --- | --- | --- |
| Amazon EKS | Managed Kubernetes control plane, API Server and etcd availability, control-plane scaling and replacement, service-specific managed capabilities. | Workloads, access configuration, many node/data-plane choices, managed node updates initiation, self-managed node patching, application security and reliability. |
| Azure AKS | Managed control plane components including API Server, etcd, scheduler, controller manager, and cloud controller manager. | Workloads, node pool choices, networking configuration, policies, application operations, and cluster configuration choices. |
| Google GKE | Managed control plane hardening and patching, Google-operated control-plane components, selected Google Cloud integrations. | Workloads, RBAC/IAM policy, cluster credential rotation, monitoring response, Standard node pool upgrade posture, application security and reliability. |

The exact boundary depends on the provider, cluster mode, node mode, and enabled features. Always validate against the current provider documentation for the cluster you operate.

## Real-Time Use Case: Failed Production Deployment

A team deploys a new version of `payments-api`. The deployment command succeeds, but users still see errors.

A weak response is:

```text
Kubernetes is broken.
```

A better response maps the failure boundary:

| Observation | Boundary |
| --- | --- |
| Deployment object exists | API Server accepted desired state. |
| ReplicaSet was created | Deployment controller reconciled. |
| Pods are Pending | Scheduler, capacity, constraints, quota, or storage topology. |
| Pods are assigned but not starting | Kubelet, runtime, image pull, mount, node pressure. |
| Pods are Running but not Ready | Application readiness, dependency, probe configuration. |
| Pods are Ready but Service has no endpoints | Selector or EndpointSlice issue. |
| Service has endpoints but traffic fails | kube-proxy/dataplane, CNI, DNS, ingress, load balancer, app protocol. |
| Only one zone fails | Zone, node pool, CNI, storage, or provider dependency. |

This approach reduces noise during incidents because every symptom points to a smaller set of owners and signals.

## Common Failure Scenarios

### API Request Rejected

Symptoms:

- `kubectl apply` fails.
- CI/CD reports forbidden, invalid, denied, or quota exceeded.
- GitOps sync fails before objects are created.

Likely boundary:

- API Server.
- Authentication.
- Authorization.
- Admission.
- Resource quota.
- Schema validation.

### Object Accepted but Nothing Happens

Symptoms:

- Object exists.
- Expected child objects do not appear.
- Status does not progress.

Likely boundary:

- Controller ownership.
- Controller manager health.
- Custom controller or operator health.
- API pressure.
- Invalid selector or ownership relationship.

### Pod Is Pending

Symptoms:

- Pod object exists.
- No node is assigned.
- Events mention scheduling failures.

Likely boundary:

- Scheduler.
- Capacity.
- Taints and tolerations.
- Affinity or topology rules.
- PVC binding or storage topology.
- Quota or admission.

### Pod Is Assigned but Not Running

Symptoms:

- Pod has a node name.
- Containers are waiting.
- Events mention image pull, mount, runtime, or sandbox failures.

Likely boundary:

- Kubelet.
- Container runtime.
- Image registry.
- CSI node plugin.
- CNI plugin.
- Node OS.

### Pod Is Running but Not Serving

Symptoms:

- Pod phase is `Running`.
- Readiness is false.
- Service traffic does not reach the Pod.
- Users see errors.

Likely boundary:

- Readiness probe.
- Application startup.
- Application dependency.
- Service selector.
- EndpointSlice update.
- Network policy.
- Service dataplane.

### Load Balancer Is Pending

Symptoms:

- Service type is `LoadBalancer`.
- External IP or hostname is missing.
- Events mention provider errors.

Likely boundary:

- Cloud controller.
- Cloud provider API.
- IAM or service identity.
- Subnet or tagging requirements.
- Quotas.
- Security rules.

## SRE Insight

Ownership is not blame. Ownership is routing.

During an incident, responsibility boundaries tell you where to look first and who needs to be involved. A good SRE does not simply say, "the Pod is broken." A good SRE asks:

- Was the desired state accepted?
- Was the state stored?
- Which controller owns the next action?
- Did the scheduler assign the Pod?
- Did the kubelet start it?
- Did the runtime pull and run the image?
- Did networking attach correctly?
- Did storage mount correctly?
- Did readiness pass?
- Did traffic reach a ready endpoint?
- Is the remaining failure inside the application or outside the cluster?

This discipline turns Kubernetes troubleshooting from guesswork into system analysis.

## Engineering Note: Define Boundaries Before Incidents

Responsibility boundaries should be documented before production incidents.

At minimum, a production platform should define:

- Who owns cluster upgrades.
- Who owns node image updates.
- Who owns CNI and network policy.
- Who owns CSI drivers and storage classes.
- Who owns ingress and external load balancers.
- Who owns DNS.
- Who owns admission policies.
- Who owns namespace guardrails.
- Who owns application resource requests.
- Who owns readiness and liveness probes.
- Who owns Kubernetes object backup.
- Who owns persistent volume backup.
- Who owns cloud-provider quotas.
- Who owns escalation to the managed Kubernetes provider.

Without this, every serious incident becomes both a technical outage and an ownership outage.

## Best Practices

- Maintain a responsibility matrix for each production cluster.
- Separate platform-owned signals from application-owned signals.
- Document managed-service boundaries for EKS, AKS, and GKE separately.
- Require application teams to define readiness, graceful shutdown, resource requests, and SLOs.
- Require platform teams to define node pool, CNI, CSI, ingress, DNS, and upgrade ownership.
- Keep cloud quota, IAM, subnet, and load balancer ownership explicit.
- Teach incident responders to map symptoms to boundaries before taking action.
- Avoid deleting resources until you understand the owning controller.
- Use events and status to identify which boundary is failing.
- Review boundaries after major incidents and platform changes.

## Common Pitfalls

- Treating Kubernetes as a single ownerless system.
- Assuming the platform team owns all application failures.
- Assuming application teams can debug control-plane or CNI failures alone.
- Assuming managed Kubernetes means the provider owns everything.
- Ignoring cloud-provider quota and IAM boundaries.
- Debugging logs before checking whether the Pod was ever scheduled.
- Debugging the scheduler when the Pod was already assigned to a node.
- Debugging the application when readiness is failing because of a missing Secret or ConfigMap.
- Treating Service existence as proof that traffic has a healthy backend.
- Missing the difference between accepted desired state and completed reconciliation.

## Lab: Build a Responsibility Map

This lab is safe for a local or non-production cluster.

### Prerequisites

- Access to a Kubernetes cluster.
- `kubectl` configured for the target cluster.
- Permission to read common cluster resources.

### Step 1: Identify Cluster Ownership

Record the cluster type:

```text
Cluster name:
Environment:
Self-managed or managed:
Provider:
Control-plane owner:
Node owner:
CNI owner:
CSI owner:
Ingress owner:
DNS owner:
Monitoring owner:
```

### Step 2: Inspect Nodes

```bash
kubectl get nodes -o wide
kubectl describe node <node-name>
```

Record:

- Node roles.
- Node labels.
- Node taints.
- Container runtime.
- Kubernetes version.
- Conditions.
- Capacity and allocatable resources.

### Step 3: Inspect System Components

```bash
kubectl get pods -n kube-system -o wide
kubectl get daemonsets -n kube-system
kubectl get deployments -n kube-system
```

Record which components are visible and which are hidden by the provider.

### Step 4: Inspect a Workload Path

Choose a non-production workload and inspect the path from desired state to traffic:

```bash
kubectl get deployment <name> -n <namespace> -o yaml
kubectl get replicaset -n <namespace>
kubectl get pods -n <namespace> -o wide
kubectl get service -n <namespace>
kubectl get endpointslices -n <namespace>
```

Map each object to an owner:

| Object or Signal | Boundary | Owner |
| --- | --- | --- |
| Deployment spec | Intent | Application or delivery team |
| ReplicaSet | Controller | Kubernetes controller |
| Pod scheduling | Scheduler | Platform/control plane |
| Container start | Node | kubelet/runtime/platform |
| Readiness | Application | Application team |
| Service endpoints | Controller/network | Platform and application labels |
| Traffic path | Network/ingress | Platform, provider, application protocol |

### Step 5: Create an Incident Routing Table

Create a table for your environment:

```text
Symptom:
First command:
Likely boundary:
Primary owner:
Escalation owner:
Dashboard or logs:
Runbook link:
```

## Runbook: Route a Kubernetes Incident by Boundary

Use this runbook when an incident begins with unclear ownership.

### 1. Check API Acceptance

```bash
kubectl auth can-i get pods -n <namespace>
kubectl get deployment <name> -n <namespace>
kubectl describe deployment <name> -n <namespace>
```

If the object does not exist or the request is denied, start at the API, RBAC, admission, quota, or GitOps boundary.

### 2. Check Controller Progress

```bash
kubectl get deployment <name> -n <namespace>
kubectl get replicaset -n <namespace>
kubectl describe deployment <name> -n <namespace>
```

If expected child objects are missing, inspect controller ownership, selectors, events, and controller health.

### 3. Check Scheduling

```bash
kubectl get pods -n <namespace> -o wide
kubectl describe pod <pod-name> -n <namespace>
```

If the Pod has no node, inspect scheduler events, capacity, taints, affinity, topology, quotas, and volume binding.

### 4. Check Node Execution

```bash
kubectl describe node <node-name>
kubectl describe pod <pod-name> -n <namespace>
```

If the Pod is assigned but not running, inspect kubelet, runtime, image pull, mounts, CNI, CSI, and node pressure.

### 5. Check Readiness and Traffic

```bash
kubectl get pod <pod-name> -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl get service <service-name> -n <namespace>
kubectl get endpointslices -n <namespace>
```

If the Pod runs but traffic fails, inspect readiness, labels, endpoint updates, Service ports, network policy, DNS, ingress, and load balancer behavior.

### 6. Assign Ownership

| Boundary | First Owner to Engage |
| --- | --- |
| API, RBAC, admission, quota | Platform team or security/platform policy owner |
| Controller reconciliation | Platform team or custom controller owner |
| Scheduling and capacity | Platform team or capacity owner |
| Kubelet/runtime/node pressure | Platform team or node operations owner |
| CNI, Service dataplane, NetworkPolicy | Platform networking owner |
| CSI, PVC, mount, attach | Platform storage owner |
| Cloud load balancer or provider API | Cloud platform owner |
| Readiness, crashes, dependency behavior | Application team |
| Business errors after healthy routing | Application team and service owner |

## Interview Questions

1. What is the difference between API acceptance and workload convergence?
2. What does the scheduler own, and what does the kubelet own?
3. Why does a `Pending` Pod usually point away from application logs?
4. Why can a Pod be assigned to a node but still fail before containers start?
5. What is the cloud-controller-manager responsible for?
6. Why does managed Kubernetes not remove customer responsibility?
7. What does etcd store, and what does it not store?
8. How would you route ownership for a Service of type `LoadBalancer` stuck in pending state?
9. How would you distinguish CNI failure from readiness failure?
10. Why should responsibility boundaries be documented before incidents?

## Summary

Kubernetes reliability depends on clear responsibility boundaries.

The API Server owns request handling and API access. etcd owns Kubernetes API state. The scheduler owns Pod placement. Controllers own reconciliation. The kubelet owns node-local Pod execution. The runtime owns container execution. CNI and CSI integrate networking and storage. Cloud controllers and providers own selected infrastructure integration. Application teams own application behavior and readiness. Platform teams own the cluster product and its operational contracts.

SREs troubleshoot Kubernetes effectively when they can map a symptom to the boundary that owns the next action.
