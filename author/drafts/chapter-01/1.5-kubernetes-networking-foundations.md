# 1.5 Kubernetes Networking Foundations

## Purpose of This Section

This section explains the networking foundation that every Kubernetes SRE needs before operating production clusters.

Kubernetes networking is often misunderstood because it looks simple from the application view. A Pod calls a Service name. A user reaches an ingress hostname. A Deployment rollout changes backend Pods without changing the frontend configuration.

Underneath that simplicity is a layered network system involving Pod IPs, Services, EndpointSlices, DNS, kube-proxy or an alternative service dataplane, CNI plugins, NetworkPolicy, ingress controllers, Gateway API implementations, cloud load balancers, node routing, and application readiness.

Most Kubernetes incidents that look like application problems eventually require networking judgment.

By the end of this section, the reader should be able to explain the Kubernetes network model, how Services find Pods, how DNS works, where NetworkPolicy applies, and how to troubleshoot traffic from client to backend.

## The Kubernetes Network Contract

Kubernetes expects a cluster network where Pods can communicate without every application carrying cluster-specific discovery logic.

The core network contract is:

```text
Each Pod gets an IP address.
Pods can communicate with other Pods across nodes.
Containers in the same Pod share a network namespace.
Services provide stable virtual access to changing Pods.
EndpointSlices track the current backend endpoints.
DNS gives workloads stable names for Services.
NetworkPolicy can restrict allowed traffic when implemented.
Ingress or Gateway exposes selected Services outside the cluster.
```

This contract is simple. The implementation is not.

A production cluster must still choose and operate the networking components that make the contract true.

## Pod Networking

A Pod is the basic Kubernetes network identity for a workload.

Each Pod receives its own IP address inside the cluster network. Containers inside the same Pod share the Pod network namespace, so they can communicate with each other over `localhost`.

```text
Pod: checkout-api-abc123

+--------------------------------+
| Pod network namespace          |
|                                |
|  Container A   Container B     |
|  127.0.0.1     127.0.0.1       |
|       \           /            |
|        \         /             |
|       Pod IP: 10.42.3.17       |
+--------------------------------+
```

Production implications:

- A Pod IP is not a durable service address.
- Pod IPs change when Pods are recreated.
- A Pod IP belongs to a Pod lifecycle, not an application identity.
- Containers in the same Pod share port space.
- Sidecars communicate with application containers over localhost or the Pod IP.
- NetworkPolicy usually selects Pods using labels.

SREs should avoid designing systems that depend on stable Pod IPs unless the workload has a specific identity model, such as a StatefulSet with stable DNS names.

## Cluster Networking Across Nodes

The Pod network must allow Pods on different nodes to communicate according to the Kubernetes network model.

A simplified path looks like this:

```text
Pod A on Node 1
      |
      v
Node 1 network stack
      |
      v
CNI / routing / overlay / provider network
      |
      v
Node 2 network stack
      |
      v
Pod B on Node 2
```

The exact implementation depends on the CNI plugin and infrastructure.

Some clusters use overlay networking. Some use cloud VPC-native Pod IPs. Some use eBPF dataplanes. Some rely on routes, tunnels, encapsulation, or provider-specific integrations.

The Kubernetes API defines the desired network model. The CNI implementation makes it real.

## CNI Responsibility

Kubernetes uses Container Network Interface plugins for cluster networking.

A CNI plugin is required to implement the Kubernetes network model. The chosen plugin affects routing behavior, NetworkPolicy support, performance, observability, encryption, IP address management, and operational failure modes.

CNI responsibilities can include:

- Creating Pod network interfaces.
- Assigning or coordinating Pod IP addresses.
- Connecting Pods to the node and cluster network.
- Programming routes or overlays.
- Enforcing NetworkPolicy when supported.
- Integrating with cloud networking or eBPF dataplanes.

CNI does not automatically own every network problem.

Before blaming CNI, check whether:

- The Pod is ready.
- The Service selector matches the Pod labels.
- EndpointSlices contain ready endpoints.
- DNS resolves the expected name.
- NetworkPolicy permits the traffic.
- The application is listening on the expected port.
- The ingress or load balancer is routing to the correct Service.

## Services

A Kubernetes Service provides a stable abstraction for reaching a set of backend endpoints, usually Pods.

Pods are ephemeral. Services are how clients avoid tracking changing Pod IPs directly.

```text
Client Pod
   |
   v
Service: payments-api
   |
   v
EndpointSlices
   |
   +--> Pod IP 10.42.1.10:8080
   +--> Pod IP 10.42.2.11:8080
   +--> Pod IP 10.42.3.12:8080
```

A Service usually selects Pods using labels:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payments-api
spec:
  selector:
    app: payments-api
  ports:
    - name: http
      port: 80
      targetPort: 8080
```

The Service receives traffic on `port: 80` and forwards to selected backend endpoints on `targetPort: 8080`.

Production implications:

- A Service can exist with zero endpoints.
- A selector mistake can route traffic nowhere.
- A port mismatch can make healthy Pods unreachable.
- Readiness affects whether Pods should appear as ready endpoints.
- Services decouple clients from Pod churn, not from application failure.

## EndpointSlices

EndpointSlices represent the backend network endpoints for a Service.

Kubernetes automatically creates EndpointSlices for Services with selectors. EndpointSlices help Kubernetes scale Service backend tracking more efficiently than the older Endpoints API.

For SREs, EndpointSlices are one of the most useful troubleshooting tools in Kubernetes networking.

```bash
kubectl get endpointslices -n <namespace>
kubectl describe endpointslice <name> -n <namespace>
```

Use EndpointSlices to answer:

- Does the Service have backends?
- Which Pod IPs are selected?
- Which ports are listed?
- Are endpoints ready?
- Is the Service selector matching the intended Pods?

If a Service has no ready endpoints, traffic failure may be caused by labels, readiness, Pod startup, or endpoint controller behavior before it is caused by the network dataplane.

## Service Types

Kubernetes supports several Service types. Each type has different exposure and operational meaning.

| Service Type | Purpose | Production Notes |
| --- | --- | --- |
| ClusterIP | Exposes a Service on an internal cluster IP. | Default type. Usually used for service-to-service traffic inside the cluster. |
| NodePort | Exposes a port on each node and builds on ClusterIP behavior. | Useful for simple exposure and some load balancer integrations, but often not the preferred user-facing abstraction. |
| LoadBalancer | Asks an external load balancer provider to expose the Service. | Requires provider support. Provisioning is asynchronous and may depend on cloud permissions, quota, subnets, and annotations. |
| ExternalName | Maps a Service name to an external DNS name. | DNS CNAME behavior only; no proxying is configured. |
| Headless Service | Uses `clusterIP: None` for direct endpoint discovery patterns. | Common with StatefulSets and systems that need endpoint identity. |

A Service of type `LoadBalancer` does not mean Kubernetes itself has created a universal load balancer. Kubernetes relies on an implementation, commonly a cloud provider or a load balancer controller.

## Service Dataplane

A Service is an API object. Traffic forwarding requires a dataplane implementation.

The Kubernetes default service proxy is kube-proxy, but some networking implementations provide their own service proxy or dataplane.

A simplified Service path:

```text
Client Pod
   |
   v
Service virtual IP or service name
   |
   v
Node service dataplane
   |
   v
Selected backend Pod IP
```

Production implications:

- The Service API object can be correct while dataplane programming is broken.
- kube-proxy or an alternative dataplane must observe Services and EndpointSlices.
- Endpoint readiness affects which backends should receive traffic.
- Node-local network rules can diverge during failures.
- eBPF, IPVS, iptables, or provider-specific implementations have different debugging tools.

When debugging Services, separate API correctness from dataplane behavior.

## DNS for Services and Pods

Kubernetes DNS lets workloads discover Services by name instead of hardcoding IP addresses.

A Service named `payments-api` in namespace `production` can usually be resolved as:

```text
payments-api
payments-api.production
payments-api.production.svc
payments-api.production.svc.cluster.local
```

A Pod's DNS search path affects how short names resolve. A query for `payments-api` from the `production` namespace is different from the same short query in another namespace.

Production implications:

- Namespace matters for DNS resolution.
- DNS failure can look like application or network failure.
- CoreDNS availability is part of service discovery reliability.
- ExternalName Services depend on DNS behavior and do not proxy traffic.
- Search path expansion can create noisy DNS query patterns.

Useful commands:

```bash
kubectl get service -n production payments-api
kubectl get endpointslices -n production
kubectl get pods -n kube-system -l k8s-app=kube-dns
```

The CoreDNS label may vary by distribution or provider, so verify labels in your cluster.

## NetworkPolicy

NetworkPolicy is a Kubernetes API for controlling traffic between Pods or between Pods and external destinations.

NetworkPolicy is important, but it has one critical operational caveat: the API object is only effective if the cluster's network implementation supports NetworkPolicy enforcement.

A simple default-deny ingress policy looks like this:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

Production implications:

- A NetworkPolicy object may exist but have no effect if the CNI does not enforce it.
- NetworkPolicy is label-driven, so label mistakes can change traffic behavior.
- Ingress and egress policies are separate concepts.
- DNS egress must be considered when applying restrictive egress policies.
- NetworkPolicy usually operates at Layer 3 and Layer 4, not full application-layer authorization.

SREs should verify both the policy objects and the network implementation before relying on NetworkPolicy for isolation.

## Ingress

Ingress exposes HTTP and HTTPS routes from outside the cluster to Services inside the cluster.

Ingress is an API object, but it requires an ingress controller to do anything. The controller may configure a load balancer, proxy, gateway, or other edge component.

A simplified path:

```text
External Client
      |
      v
DNS name
      |
      v
External load balancer or edge router
      |
      v
Ingress controller
      |
      v
Service
      |
      v
Ready backend Pods
```

Production implications:

- Creating an Ingress object is not enough; an ingress controller must watch and implement it.
- TLS termination, redirects, path matching, headers, and timeouts depend on the controller.
- Ingress is HTTP and HTTPS focused.
- Non-HTTP protocols often use Service type `LoadBalancer`, NodePort, Gateway API, or implementation-specific features.
- The Kubernetes project recommends Gateway API for newer use cases, while Ingress remains stable but frozen.

## Gateway API

Gateway API is a newer family of Kubernetes APIs for dynamic infrastructure provisioning and advanced traffic routing.

Gateway API is role-oriented. It separates concerns among infrastructure providers, cluster operators, and application developers.

This matters in production because network ownership is rarely one team.

```text
Infrastructure Provider -> GatewayClass
Cluster Operator        -> Gateway
Application Team        -> HTTPRoute / TCPRoute / other routes
```

Production implications:

- Gateway API can model shared platform networking more clearly than Ingress.
- It still requires an implementation controller.
- Roles and ownership boundaries should be defined before teams depend on it.
- Gateway support varies by implementation and provider.

## Load Balancers and Cloud Provider Boundaries

A Kubernetes Service of type `LoadBalancer` commonly depends on cloud-provider integration.

The Kubernetes API stores the Service object. A controller or provider integration provisions external infrastructure and reports the result in Service status.

Production implications:

- Provisioning may be asynchronous.
- Provider quotas can block load balancer creation.
- IAM or service identity problems can block provisioning.
- Subnet tags or network configuration can affect load balancer placement.
- Firewall or security rules can block traffic even after provisioning succeeds.
- Provider health checks may not match application readiness unless configured correctly.

SREs should treat cloud load balancers as part of the Kubernetes traffic path, but not as purely Kubernetes-owned resources.

## North-South and East-West Traffic

Kubernetes networking is often discussed in two directions:

| Traffic Pattern | Meaning | Common Components |
| --- | --- | --- |
| East-west | Traffic between services inside the cluster. | Pod network, Services, EndpointSlices, DNS, NetworkPolicy, service mesh when used. |
| North-south | Traffic entering or leaving the cluster. | Ingress, Gateway, LoadBalancer Services, DNS, cloud load balancers, firewalls, NAT, egress gateways. |

Both directions matter for reliability.

A service can have healthy east-west traffic while external users fail because the ingress path is broken. Another service can have a healthy ingress path but fail internally because DNS, NetworkPolicy, or backend readiness is broken.

## Dual-Stack Networking

Kubernetes supports IPv4, IPv6, and dual-stack networking when the cluster, provider, and network plugin support it.

Dual-stack can assign both IPv4 and IPv6 addresses to Pods and Services. It requires provider and network plugin support and correct cluster configuration.

Production implications:

- Do not assume every cluster is IPv4-only.
- Do not assume every provider or plugin supports all dual-stack features equally.
- Service IP family behavior affects clients and load balancers.
- Observability tools and policies must understand both address families.
- DNS and firewall behavior may differ across IPv4 and IPv6.

If your organization plans IPv6 adoption, Kubernetes networking design must include cluster CIDRs, Service CIDRs, CNI support, load balancer behavior, policy enforcement, and observability coverage.

## Real-Time Use Case: Checkout API Cannot Reach Payments API

A production checkout service returns payment errors after a deployment.

The application team says `payments-api` is down. The platform team says all Pods are running. The incident bridge is noisy.

A boundary-based network investigation looks like this:

| Check | Command | Interpretation |
| --- | --- | --- |
| Does DNS resolve? | `nslookup payments-api.production.svc.cluster.local` | If this fails, check CoreDNS and namespace naming. |
| Does the Service exist? | `kubectl get svc payments-api -n production` | Confirms the Service API object exists. |
| Does it have endpoints? | `kubectl get endpointslices -n production` | Confirms backend Pods are selected and ready. |
| Are Pods ready? | `kubectl get pods -n production -l app=payments-api` | Separates running from ready. |
| Is NetworkPolicy blocking? | `kubectl get networkpolicy -n production` | Checks whether policy may deny traffic. |
| Is the app listening? | `kubectl describe pod <pod> -n production` | Checks ports, probes, and container status. |
| Does traffic work from a test Pod? | `curl http://payments-api.production.svc.cluster.local` | Confirms client-side path from inside the cluster. |

Possible outcomes:

- DNS fails: service discovery boundary.
- Service has no endpoints: selector or readiness boundary.
- Endpoints exist but traffic times out: dataplane, CNI, NetworkPolicy, or app listener boundary.
- Only checkout fails: client config, namespace, policy, or application dependency behavior.
- Only one node fails: node-local dataplane, CNI, kube-proxy, or routing boundary.

## Common Failure Scenarios

### Service Has No Endpoints

Symptoms:

- Service exists.
- DNS resolves.
- Requests fail or hang.
- EndpointSlices show no ready endpoints.

Likely causes:

- Service selector does not match Pod labels.
- Pods are not ready.
- Pods are in another namespace.
- Target workload is not running.
- EndpointSlice controller is delayed.

### DNS Fails

Symptoms:

- Application errors mention name resolution.
- `curl` by IP works but by name fails.
- CoreDNS Pods are unavailable or overloaded.

Likely causes:

- CoreDNS outage.
- Incorrect namespace name.
- Incorrect Service name.
- Restrictive egress NetworkPolicy blocking DNS.
- Node DNS configuration issue.
- Search path assumptions.

### NetworkPolicy Blocks Traffic

Symptoms:

- Service and endpoints look correct.
- Traffic times out between selected Pods.
- Failures begin after policy changes.

Likely causes:

- Missing ingress allow rule.
- Missing egress allow rule.
- Label selector mismatch.
- DNS egress omitted.
- Policy enforced by CNI differently than expected.

### LoadBalancer Service Is Pending

Symptoms:

- Service exists.
- External IP or hostname is missing.
- Events mention provider or provisioning errors.

Likely causes:

- Cloud quota.
- IAM or service identity.
- Unsupported annotations.
- Subnet or tagging issue.
- Unsupported load balancer mode.
- Provider outage or delayed provisioning.

### Ingress Returns 404 or 503

Symptoms:

- DNS reaches the ingress endpoint.
- TLS may work.
- Application returns 404, 503, or gateway errors.

Likely causes:

- Host or path rule mismatch.
- Ingress class mismatch.
- Service has no endpoints.
- Backend port mismatch.
- Ingress controller cannot reach Service backends.
- Controller-specific configuration issue.

### Only One Node Has Traffic Failures

Symptoms:

- Requests fail only from or to Pods on a specific node.
- Other nodes work.
- Restarting application Pods does not fix root cause.

Likely causes:

- Node-local CNI issue.
- kube-proxy or service dataplane issue.
- Node route or firewall issue.
- Node DNS issue.
- Runtime sandbox networking issue.

## SRE Insight

Kubernetes networking troubleshooting should follow the packet and the API object model.

Do not start with the most complex theory. Start with the chain:

```text
Client -> DNS -> Service -> EndpointSlice -> Ready Pod -> Port -> Policy -> Dataplane -> Application
```

For external traffic, extend the chain:

```text
User -> Public DNS -> Load Balancer -> Ingress or Gateway -> Service -> EndpointSlice -> Ready Pod -> Application
```

Every hop has a responsible component and an observable signal.

## Engineering Note: Networking Is a Platform Product

Kubernetes networking is not only a technical subsystem. It is a platform product that application teams depend on.

A production platform should document:

- Cluster CIDR and Service CIDR ownership.
- CNI plugin and version.
- NetworkPolicy support and enforcement model.
- Service exposure standards.
- Ingress or Gateway ownership.
- Load balancer controller ownership.
- DNS ownership and escalation path.
- Egress model and NAT ownership.
- Allowed cross-namespace communication patterns.
- Observability signals for DNS, CNI, ingress, and load balancers.
- Provider-specific network constraints.

Without this, application teams will make assumptions that turn into incidents.

## Best Practices

- Use Services for stable workload access instead of Pod IPs.
- Use clear and consistent labels for Service selectors.
- Check EndpointSlices during every Service traffic incident.
- Treat readiness as part of the traffic path.
- Keep CoreDNS highly available and monitored.
- Verify that the selected CNI enforces the policies you depend on.
- Start with least-privilege NetworkPolicy in controlled environments before broad rollout.
- Use Ingress or Gateway for HTTP and HTTPS exposure instead of ad hoc NodePorts.
- Document provider requirements for LoadBalancer Services.
- Monitor both API objects and dataplane health.
- Test cross-node and cross-zone traffic paths.
- Include DNS and NetworkPolicy checks in application runbooks.

## Common Pitfalls

- Assuming a Service has healthy backends because the Service object exists.
- Assuming DNS failure is an application bug.
- Assuming `Running` Pods should receive traffic even when readiness fails.
- Creating NetworkPolicy objects on a CNI that does not enforce them.
- Forgetting to allow DNS egress under restrictive policies.
- Exposing production traffic through NodePort without a clear reason.
- Treating cloud load balancer provisioning as instantaneous.
- Debugging ingress before checking Service endpoints.
- Using short DNS names across namespaces and expecting them to resolve globally.
- Ignoring node-local networking when failures affect only some Pods.

## Lab: Trace Service Traffic

This lab is safe for a local or non-production cluster.

### Prerequisites

- Access to a Kubernetes cluster.
- `kubectl` configured for the target cluster.
- Permission to create and delete objects in a test namespace.

### Create a Namespace

```bash
kubectl create namespace sre-network-lab
```

### Deploy a Test Backend

```bash
kubectl create deployment echo-backend \
  --image=hashicorp/http-echo:1.0 \
  --replicas=2 \
  --namespace=sre-network-lab \
  -- -text="hello from kubernetes networking"
```

### Expose the Backend

```bash
kubectl expose deployment echo-backend \
  --port=80 \
  --target-port=5678 \
  --namespace=sre-network-lab
```

### Inspect the Service and EndpointSlices

```bash
kubectl get service echo-backend -n sre-network-lab
kubectl get endpointslices -n sre-network-lab
kubectl describe service echo-backend -n sre-network-lab
```

Expected behavior:

- The Service has a ClusterIP.
- EndpointSlices list backend Pod IPs.
- Service selector matches Pod labels.

### Start a Temporary Client Pod

```bash
kubectl run network-client \
  --image=curlimages/curl:8.10.1 \
  --restart=Never \
  --namespace=sre-network-lab \
  --command -- sleep 3600
```

Wait for the client Pod:

```bash
kubectl wait --for=condition=Ready pod/network-client \
  --namespace=sre-network-lab \
  --timeout=120s
```

### Test DNS and Service Traffic

```bash
kubectl exec -n sre-network-lab network-client -- \
  curl -s http://echo-backend.sre-network-lab.svc.cluster.local
```

Expected output:

```text
hello from kubernetes networking
```

### Break the Service Selector

Patch the Service selector so it no longer matches the Pods:

```bash
kubectl patch service echo-backend \
  --namespace=sre-network-lab \
  --type=merge \
  -p '{"spec":{"selector":{"app":"does-not-match"}}}'
```

Inspect EndpointSlices again:

```bash
kubectl get endpointslices -n sre-network-lab
kubectl describe service echo-backend -n sre-network-lab
```

Expected behavior:

- The Service still exists.
- Ready endpoints disappear.
- Traffic to the Service fails or hangs.

### Restore the Selector

```bash
kubectl patch service echo-backend \
  --namespace=sre-network-lab \
  --type=merge \
  -p '{"spec":{"selector":{"app":"echo-backend"}}}'
```

Retest traffic:

```bash
kubectl exec -n sre-network-lab network-client -- \
  curl -s http://echo-backend.sre-network-lab.svc.cluster.local
```

### Clean Up

```bash
kubectl delete namespace sre-network-lab
```

## Runbook: Service Traffic Failure

Use this runbook when a client cannot reach a Kubernetes Service.

### 1. Confirm the Service Exists

```bash
kubectl get service <service-name> -n <namespace>
kubectl describe service <service-name> -n <namespace>
```

Check:

- Service type.
- ClusterIP.
- Ports.
- Target ports.
- Selector.
- Events.

### 2. Confirm Backend Endpoints

```bash
kubectl get endpointslices -n <namespace>
kubectl describe endpointslice <endpointslice-name> -n <namespace>
```

Check:

- Backend addresses.
- Ready conditions.
- Port names and numbers.
- Service-name labels.

### 3. Confirm Pods and Readiness

```bash
kubectl get pods -n <namespace> --show-labels
kubectl describe pod <pod-name> -n <namespace>
```

Check:

- Labels match the Service selector.
- Pods are Ready.
- Containers listen on the expected port.
- Readiness probes pass.

### 4. Confirm DNS

From a client Pod:

```bash
nslookup <service-name>.<namespace>.svc.cluster.local
```

If DNS fails, check CoreDNS, namespace, Service name, and NetworkPolicy egress.

### 5. Confirm NetworkPolicy

```bash
kubectl get networkpolicy -n <namespace>
kubectl describe networkpolicy <policy-name> -n <namespace>
```

Check:

- Pod selectors.
- Namespace selectors.
- Ingress rules.
- Egress rules.
- DNS allow rules.

### 6. Confirm Node and Dataplane Health

```bash
kubectl get pods -A -o wide
kubectl get pods -n kube-system
kubectl get nodes
```

Check:

- Failures limited to one node.
- CNI Pods healthy.
- kube-proxy or replacement dataplane healthy.
- Node Ready conditions.

### 7. Confirm External Path if Needed

For Ingress, Gateway, or LoadBalancer traffic, also check:

```bash
kubectl get ingress -A
kubectl get gateway -A
kubectl get httproute -A
kubectl get service -A --field-selector spec.type=LoadBalancer
```

The `field-selector` example may not be supported for every field or distribution. If it fails, list Services normally and filter the output.

## Summary

Kubernetes networking gives workloads stable ways to communicate even though Pods are ephemeral.

Pods receive IP addresses. Services provide stable virtual access to changing backend Pods. EndpointSlices track the current endpoints. DNS provides service discovery. NetworkPolicy can restrict traffic when implemented by the network plugin. Ingress and Gateway expose selected Services outside the cluster. LoadBalancer Services depend on provider or controller integration.

For SREs, networking incidents should be debugged as a chain: client, DNS, Service, EndpointSlice, readiness, policy, dataplane, node, provider, and application.

The fastest path to resolution is usually not guessing. It is following the traffic path one boundary at a time.
