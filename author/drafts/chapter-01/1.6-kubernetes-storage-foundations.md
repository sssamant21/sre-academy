# 1.6 Kubernetes Storage Foundations

## Purpose of This Section

This section explains the storage foundation that every Kubernetes SRE needs before operating production workloads that keep state.

Kubernetes makes stateless workloads feel simple because Pods can be replaced freely. Storage changes that model. Once data is attached to a workload, the platform must preserve data across Pod restarts, node failures, rescheduling, upgrades, backups, restores, and disaster recovery events.

Storage incidents are rarely isolated to one object. A failed StatefulSet rollout may involve a PersistentVolumeClaim, PersistentVolume, StorageClass, Container Storage Interface driver, cloud disk, node topology, attach limit, filesystem, application startup logic, and backup policy.

By the end of this section, the reader should be able to explain the difference between ephemeral and persistent storage, how PersistentVolumes and PersistentVolumeClaims work, how StorageClasses enable dynamic provisioning, how CSI drivers connect Kubernetes to storage systems, and how to troubleshoot common storage failures.

## The Kubernetes Storage Problem

Containers are temporary. Data often is not.

A container filesystem is not a reliable place for durable application state. When a container is restarted, rescheduled, or replaced, anything written only inside the writable container layer may disappear or become inaccessible.

Kubernetes solves this by separating workload lifecycle from storage lifecycle.

```text
Application process   -> container filesystem -> temporary process-local state
Pod                   -> volumes              -> data mounted into containers
PersistentVolumeClaim -> PersistentVolume     -> durable storage resource
StorageClass          -> provisioner policy   -> storage backend behavior
CSI driver            -> storage API          -> cloud disk, SAN, NAS, local disk, or other backend
```

This separation lets Kubernetes restart or reschedule a workload while giving the application a way to reattach the storage it requires.

It also creates a production responsibility boundary. Kubernetes can model, bind, attach, and mount storage, but it does not make every storage backend reliable, fast, replicated, encrypted, backed up, or recoverable by default.

## Storage Mental Model

A useful SRE mental model is to divide Kubernetes storage into four layers.

```text
+---------------------------------------------------------+
| Workload layer                                          |
| Pods, Deployments, StatefulSets, Jobs, application I/O  |
+-----------------------------+---------------------------+
                              |
+-----------------------------v---------------------------+
| Kubernetes API layer                                     |
| Volumes, PVCs, PVs, StorageClasses, VolumeSnapshots      |
+-----------------------------+---------------------------+
                              |
+-----------------------------v---------------------------+
| Integration layer                                        |
| CSI controller, CSI node plugin, external sidecars       |
+-----------------------------+---------------------------+
                              |
+-----------------------------v---------------------------+
| Storage provider layer                                   |
| Cloud disks, block storage, file storage, local storage   |
+---------------------------------------------------------+
```

When an incident happens, SREs should identify which layer is failing before changing configuration.

A Pod stuck in `ContainerCreating` may be blocked by a volume mount. A PVC stuck in `Pending` may be blocked by missing dynamic provisioning. A StatefulSet stuck during rollout may be blocked by a ReadWriteOnce volume already attached to another node. A backup failure may be caused by a snapshot controller, a CSI driver, application write activity, or backend provider limits.

## Ephemeral Storage

Ephemeral storage follows the lifetime of the Pod or node. It is useful for scratch data, caches, temporary files, projected configuration, secrets, and runtime working directories.

Common ephemeral volume types include:

| Volume Type | Typical Use | Production Warning |
| --- | --- | --- |
| `emptyDir` | Scratch space shared by containers in one Pod | Data is removed when the Pod is removed from the node. |
| `configMap` | Mount application configuration | Not for large files or confidential data. |
| `secret` | Mount sensitive configuration | Requires separate secret-management controls and encryption-at-rest decisions. |
| `downwardAPI` | Expose Pod metadata to containers | Good for metadata, not durable application state. |
| Generic ephemeral volume | Per-Pod temporary storage backed by dynamic provisioning | Requires storage driver support and capacity planning. |

An `emptyDir` is often used for temporary processing:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: scratch-example
spec:
  containers:
    - name: worker
      image: busybox:1.36
      command: ["sh", "-c", "echo work > /scratch/output.txt && sleep 3600"]
      volumeMounts:
        - name: scratch
          mountPath: /scratch
  volumes:
    - name: scratch
      emptyDir: {}
```

This is not durable storage. If the Pod is deleted and recreated, the scratch data is gone.

Production implications:

- Do not use `emptyDir` for durable application state.
- Monitor node ephemeral storage pressure because kubelet can evict Pods when nodes run out of local ephemeral storage.
- Treat projected `secret` and `configMap` volumes as configuration inputs, not databases.
- Use size limits where appropriate for `emptyDir` to reduce node exhaustion risk.
- Use persistent storage or external services when data must survive Pod replacement.

## Persistent Storage

Persistent storage is represented through PersistentVolumes and PersistentVolumeClaims.

A PersistentVolume is a cluster resource representing storage. It can be statically created by an administrator or dynamically created by a storage provisioner.

A PersistentVolumeClaim is a user's request for storage. The workload references the claim, not the backend storage details.

```text
Pod -> volumeMount -> PersistentVolumeClaim -> PersistentVolume -> storage backend
```

This abstraction matters because application teams should not need to know how to create a specific cloud disk or storage array volume for every workload. They request storage through Kubernetes, and the platform maps that request to provider-specific implementation.

## PersistentVolumeClaims

A PVC describes what the workload needs.

Common PVC fields include:

| Field | Meaning | SRE Question |
| --- | --- | --- |
| `resources.requests.storage` | Requested capacity | Is the size realistic for growth and restore operations? |
| `accessModes` | How the volume can be mounted | Does the backend support the required access pattern? |
| `storageClassName` | Storage policy to use | Is this the correct class for performance, topology, and cost? |
| `volumeMode` | Filesystem or raw block | Does the application expect a filesystem or block device? |
| `dataSource` | Optional clone or snapshot source | Is the source valid, available, and in the correct namespace or scope? |

Example PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard-rwo
  resources:
    requests:
      storage: 20Gi
```

A Pod can mount the claim:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: postgres-storage-check
spec:
  containers:
    - name: postgres
      image: postgres:16
      env:
        - name: POSTGRES_PASSWORD
          value: example
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: postgres-data
```

In production, the PVC is part of the application contract. Accidentally deleting a PVC can delete or orphan the backing storage depending on reclaim policy and provider behavior.

## PersistentVolumes

A PV represents the actual storage resource known to Kubernetes.

Important PV properties include:

| Property | Meaning |
| --- | --- |
| Capacity | Size exposed to Kubernetes. |
| Access modes | Supported mount semantics. |
| Reclaim policy | What happens when the claim is deleted. |
| StorageClass | Storage policy associated with the volume. |
| Claim reference | Binding relationship to a PVC. |
| CSI source | CSI driver and provider-specific volume handle. |
| Node affinity | Topology restrictions for where the volume can be used. |

The PV lifecycle normally moves through phases such as available, bound, released, or failed.

For SREs, the most important point is this: a PV is not the data itself. It is the Kubernetes API object that represents and tracks access to the storage backend. The real data exists in the backend volume, disk, share, or storage system.

## Access Modes

Access modes describe how a volume can be mounted by nodes and Pods.

Common modes include:

| Access Mode | Meaning | Common Example |
| --- | --- | --- |
| `ReadWriteOnce` | Mounted as read-write by a single node | Cloud block disks for databases. |
| `ReadOnlyMany` | Mounted read-only by many nodes | Shared read-only datasets. |
| `ReadWriteMany` | Mounted read-write by many nodes | Shared file storage when supported. |
| `ReadWriteOncePod` | Mounted read-write by a single Pod | Stronger single-Pod access semantics for supported CSI volumes. |

Access mode is not an application-level locking system. It describes mount capability, not whether multiple application processes can safely write to the same files.

Production implications:

- Many cloud block volumes are `ReadWriteOnce` and cannot be mounted read-write by many nodes at the same time.
- `ReadWriteMany` usually requires a file storage backend or a storage system designed for shared access.
- Applications must still implement correct concurrency behavior.
- A StatefulSet replica should usually have its own PVC unless the application is designed for shared storage.
- Access mode support depends on the storage provider and CSI driver.

## StorageClasses

A StorageClass describes a class of storage offered by the platform.

StorageClasses let platform teams expose storage policies without exposing every provider detail to application teams.

Example:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-rwo
provisioner: example.csi.driver
parameters:
  type: fast
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

Important fields:

| Field | Why It Matters |
| --- | --- |
| `provisioner` | Selects the storage plugin or CSI driver. |
| `parameters` | Passes driver-specific settings such as disk type or filesystem behavior. |
| `reclaimPolicy` | Controls delete or retain behavior for dynamically provisioned PVs. |
| `allowVolumeExpansion` | Allows PVC resize when supported by the driver. |
| `volumeBindingMode` | Controls when binding and provisioning happen. |
| `mountOptions` | Adds mount options when supported. |

A StorageClass is a production policy object. It should be reviewed like infrastructure code.

Questions for every production StorageClass:

- What backend does it use?
- Is it zonal, regional, replicated, or shared?
- What performance class does it map to?
- What reclaim policy does it use?
- Does it allow expansion?
- Does it support snapshots?
- Does it support volume cloning?
- Does it use `WaitForFirstConsumer` when topology matters?
- Who is allowed to use it?
- How is cost tracked?

## Dynamic Provisioning

Dynamic provisioning creates a PV automatically when a PVC requests storage through a StorageClass.

The high-level flow is:

```text
1. User creates PVC.
2. Kubernetes observes the claim.
3. Provisioner creates backend storage.
4. PV object is created.
5. PVC binds to PV.
6. Pod mounts the claim.
7. CSI driver attaches and mounts the volume on the node.
```

Dynamic provisioning is the normal model for most production clusters because it allows teams to request storage declaratively.

It also means PVC creation can trigger real provider resources, real cost, and real deletion behavior.

## Volume Binding Mode and Topology

Storage location matters.

A cloud block disk might exist in one zone. A Pod scheduled to a different zone cannot mount it. A local persistent volume might exist on only one node. A multi-zone file service may be accessible across zones but have different latency and throughput behavior.

StorageClasses can use `volumeBindingMode`:

| Mode | Behavior | Operational Use |
| --- | --- | --- |
| `Immediate` | Provision or bind the volume as soon as the PVC is created | Useful when topology does not matter or backend is broadly accessible. |
| `WaitForFirstConsumer` | Delay binding until a Pod using the PVC is scheduled | Useful when volume topology must align with Pod placement. |

For zonal block storage, `WaitForFirstConsumer` is often the safer production default because scheduling and storage provisioning can be coordinated.

Failure pattern:

```text
PVC created with Immediate binding
PV created in zone us-east-1a
Pod scheduled to node in us-east-1b
Volume cannot attach
Pod remains Pending or ContainerCreating
```

SRE response:

- Check the PVC and PV binding.
- Check PV node affinity or topology labels.
- Check the Pod's selected node and zone.
- Check StorageClass `volumeBindingMode`.
- Check whether the workload uses node selectors, affinities, or topology spread constraints that conflict with storage topology.

## CSI Drivers

The Container Storage Interface is the common integration point between Kubernetes and storage systems.

Kubernetes uses CSI drivers so storage vendors and cloud providers can implement provisioning, attachment, mounting, expansion, snapshots, cloning, and health behavior outside the core Kubernetes codebase.

A production CSI deployment commonly includes:

| Component | Responsibility |
| --- | --- |
| CSI controller plugin | Handles controller-side operations such as provisioning, attaching, detaching, resizing, and snapshots when supported. |
| CSI node plugin | Runs on nodes and handles node-side staging, publishing, and unmounting. |
| External provisioner | Watches PVCs and creates PVs through the CSI driver. |
| External attacher | Handles attach and detach operations when required. |
| External resizer | Handles volume expansion when supported. |
| External snapshotter | Handles VolumeSnapshot resources when installed. |

SREs do not need to memorize every CSI sidecar in Chapter 1, but they must know that storage behavior often depends on CSI driver health.

When storage breaks, check both Kubernetes objects and CSI components.

Useful commands:

```bash
kubectl get storageclass
kubectl get pvc -A
kubectl get pv
kubectl describe pvc <claim-name> -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl get pods -A | grep -i csi
kubectl get events -A --sort-by=.lastTimestamp
```

## StatefulSets and Storage Identity

StatefulSets are commonly used for workloads that need stable identity and stable storage.

A StatefulSet can use `volumeClaimTemplates` so each replica receives its own PVC.

Simplified example:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: cache
spec:
  serviceName: cache
  replicas: 3
  selector:
    matchLabels:
      app: cache
  template:
    metadata:
      labels:
        app: cache
    spec:
      containers:
        - name: redis
          image: redis:7
          volumeMounts:
            - name: data
              mountPath: /data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: standard-rwo
        resources:
          requests:
            storage: 10Gi
```

This creates PVCs such as:

```text
data-cache-0
data-cache-1
data-cache-2
```

Each replica has independent storage identity. If `cache-1` is recreated, it can remount `data-cache-1`.

Production implications:

- Do not manually delete StatefulSet PVCs unless the data deletion is intentional.
- StatefulSet scale-down does not automatically delete PVCs by default in many common workflows, which helps protect data but can leave cost behind.
- Volume access mode and zone placement affect rescheduling behavior.
- Stateful workloads still require backup, restore, upgrade, and disaster recovery planning.
- Kubernetes storage identity is not a replacement for database replication or application-level consistency.

## Reclaim Policies

The reclaim policy controls what happens to the PV and backend storage after a PVC is deleted.

Common reclaim policies:

| Policy | Behavior | Production Use |
| --- | --- | --- |
| `Delete` | Delete the PV and usually the backend storage when the claim is deleted | Common for disposable or automatically managed environments. |
| `Retain` | Keep the PV and backend storage after the claim is deleted | Safer for critical data, recovery workflows, and manual review. |

Reclaim policy is one of the most important storage safety settings in a cluster.

A development cluster might accept `Delete`. A production database StorageClass may require `Retain`, strict RBAC, backups, and manual deletion controls.

SREs should know the default reclaim policy for every StorageClass in the cluster.

## Volume Expansion

Many CSI drivers support expanding PVCs.

A typical expansion starts by increasing the requested storage size in the PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  resources:
    requests:
      storage: 40Gi
```

Expansion depends on:

- `allowVolumeExpansion` on the StorageClass.
- CSI driver support.
- Backend provider support.
- Filesystem support.
- Whether online expansion is supported for the workload and driver.

Production expansion checklist:

- Confirm the StorageClass allows expansion.
- Confirm the provider supports the requested size and type.
- Confirm the application can tolerate filesystem resize behavior.
- Check events on the PVC and Pod.
- Confirm monitoring thresholds are updated after expansion.
- Confirm backups and restore procedures support the new size.

## VolumeSnapshots

VolumeSnapshots provide a Kubernetes API for requesting point-in-time snapshots of a volume when the snapshot CRDs, controller, snapshotter sidecar, CSI driver, and storage backend support the feature.

The common snapshot objects are:

| Object | Role |
| --- | --- |
| `VolumeSnapshot` | User request for a snapshot. |
| `VolumeSnapshotContent` | Cluster resource representing the actual snapshot. |
| `VolumeSnapshotClass` | Snapshot policy and driver-specific parameters. |

Example:

```yaml
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata:
  name: postgres-data-before-upgrade
spec:
  volumeSnapshotClassName: csi-snapshot-class
  source:
    persistentVolumeClaimName: postgres-data
```

Snapshots are useful, but they are not automatically complete backup strategy.

Production considerations:

- Application consistency matters. A crash-consistent storage snapshot may not be enough for a database restore target.
- Snapshot support depends on the CSI driver and backend.
- Snapshot deletion policy must be understood.
- Snapshot restore must be tested.
- Snapshots should be tied to retention, compliance, and recovery objectives.
- Cross-region or cross-account disaster recovery may require provider-specific backup tooling outside Kubernetes.

## Cloning and Data Sources

Some CSI drivers support creating a new PVC from an existing PVC or snapshot.

Use cases include:

- Creating a test database from a production-like snapshot.
- Restoring an application volume after a failed migration.
- Creating a copy for forensic analysis.
- Seeding a workload with existing data.

SRE warning: cloning is not a substitute for understanding application consistency. A cloned volume can faithfully copy corrupt, incomplete, or inconsistent data.

## Local Persistent Volumes

Local persistent volumes expose storage that exists on a specific node.

They can be useful for high-performance workloads where local disk latency matters, but they change failure behavior:

- The volume is tied to a node.
- If the node fails, the data may be unavailable until the node returns or recovery is performed.
- Scheduling must respect node affinity.
- Backup and replication must be designed separately.
- Cluster autoscaling and node replacement require extra care.

Local persistent volumes are not magic high-availability storage. They are a deliberate tradeoff: performance and locality in exchange for tighter node coupling.

## Storage and Scheduling Failure Modes

Storage can block scheduling or startup in multiple ways.

| Symptom | Possible Cause | First Checks |
| --- | --- | --- |
| PVC is `Pending` | No default StorageClass, invalid StorageClass, provisioner down, quota, capacity, topology | `kubectl describe pvc`, StorageClass, events, CSI controller logs |
| Pod is `Pending` | PVC not bound, topology conflict, volume binding waiting for first consumer | Pod events, PVC events, scheduler events |
| Pod is `ContainerCreating` | Volume attach or mount failure | Pod describe output, kubelet events, CSI node plugin logs |
| Attach timeout | Backend API issue, volume already attached, node-zone mismatch, provider limit | PV, node zone, cloud volume state, CSI controller logs |
| Mount failure | Filesystem issue, permission issue, missing driver, node plugin problem | kubelet logs, CSI node logs, mount options |
| Read-only filesystem | Backend fault, filesystem remount, wrong access mode, node issue | Pod logs, node logs, storage backend health |
| Slow I/O | Storage class mismatch, throttling, noisy neighbors, backend saturation | Application metrics, volume metrics, provider metrics |
| Data missing after restart | Used ephemeral storage, wrong PVC, new claim created, restore error | Pod spec, PVC name, StatefulSet claim template, events |

SREs should work from the API outward: Pod, PVC, PV, StorageClass, CSI components, node, provider.

## Real-Time Production Use Case: Database Rollout Blocked by Storage Attachment

A payments team runs PostgreSQL on Kubernetes for a staging environment. The database runs as a single-replica StatefulSet using a `ReadWriteOnce` PVC backed by zonal block storage.

A node upgrade starts. The old node is drained, and Kubernetes attempts to recreate the database Pod on a new node.

The Pod remains stuck in `ContainerCreating`.

The application team sees downtime and assumes PostgreSQL is broken. The platform team checks the Pod events:

```text
Warning  FailedAttachVolume  AttachVolume.Attach failed for volume "pvc-abc123"
Warning  FailedMount         Unable to attach or mount volumes
```

The investigation finds:

- The volume is a zonal block volume.
- The replacement Pod was scheduled to a node in a different zone.
- The StorageClass used immediate binding.
- The workload did not constrain Pod scheduling to the volume zone.

Corrective actions:

- Move the workload to a StorageClass using `WaitForFirstConsumer` where appropriate.
- Review StatefulSet scheduling and topology rules.
- Confirm managed node groups span zones intentionally.
- Document recovery steps for stuck volume attachments.
- Evaluate whether staging requires multi-zone database architecture or managed database service instead of single-disk persistence.

This incident is not just a storage problem. It is a scheduling, topology, platform policy, and reliability-design problem.

## Failure Scenarios

### Scenario 1: PVC Stuck in Pending

Likely causes:

- No default StorageClass exists.
- The PVC references a StorageClass name that does not exist.
- The CSI provisioner is not running or lacks permissions.
- Namespace quota blocks PVC creation.
- Storage capacity is unavailable for the requested class.
- `WaitForFirstConsumer` is waiting for a Pod to use the PVC.

First response:

```bash
kubectl describe pvc <claim-name> -n <namespace>
kubectl get storageclass
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl get pods -A | grep -i csi
```

### Scenario 2: Pod Stuck in ContainerCreating

Likely causes:

- Volume attachment failed.
- Volume mount failed on the node.
- The CSI node plugin is unhealthy.
- The backend volume is already attached elsewhere.
- Node topology does not match the PV.
- Filesystem check or resize is failing.

First response:

```bash
kubectl describe pod <pod-name> -n <namespace>
kubectl describe pvc <claim-name> -n <namespace>
kubectl describe pv <pv-name>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

### Scenario 3: Data Lost After Pod Restart

Likely causes:

- The workload wrote data to the container filesystem.
- The workload used `emptyDir` instead of a PVC.
- The Pod mounted the wrong path.
- A new PVC was created unexpectedly.
- The application initialized an empty data directory over an expected mount.

First response:

- Check the Pod volume mounts.
- Confirm the application data path.
- Confirm PVC name and binding.
- Check StatefulSet `volumeClaimTemplates`.
- Review recent rollouts and manifests.
- Stop automated restarts if they risk overwriting recoverable state.

### Scenario 4: Snapshot Exists but Restore Fails

Likely causes:

- Snapshot is not ready to use.
- SnapshotClass or restore StorageClass is wrong.
- CSI driver does not support restore from snapshot.
- Namespace, data source, or permissions are incorrect.
- Restored filesystem is valid but application state is inconsistent.

First response:

```bash
kubectl get volumesnapshot -n <namespace>
kubectl describe volumesnapshot <snapshot-name> -n <namespace>
kubectl get volumesnapshotclass
kubectl describe pvc <restore-claim> -n <namespace>
```

## SRE Insight

Kubernetes storage is where declarative infrastructure meets irreversible data risk.

A Deployment can be rolled back. A Service selector can be corrected. A bad ConfigMap can be replaced.

A deleted production volume is different.

For this reason, storage changes require stronger operational controls than many stateless workload changes. SREs should treat StorageClasses, PVC deletion, snapshot policies, backup retention, and restore workflows as production safety systems.

Good Kubernetes storage operations are built on four habits:

- Know which data is durable and which data is disposable.
- Know which component owns each storage operation.
- Know what happens when a claim is deleted.
- Test restore before an incident forces a restore.

## Lab: Observe PVC Binding and Pod Mount Behavior

### Goal

Create a PVC, mount it into a Pod, write data, delete the Pod, and confirm that the data survives Pod recreation when the PVC is reused.

### Prerequisites

- A test Kubernetes cluster.
- A working default StorageClass or a known StorageClass name.
- Permission to create Pods and PVCs in a test namespace.

### Steps

Create a namespace:

```bash
kubectl create namespace storage-lab
```

Check available StorageClasses:

```bash
kubectl get storageclass
```

Create a PVC. Replace `standard-rwo` if your cluster uses a different StorageClass.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: lab-data
  namespace: storage-lab
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard-rwo
  resources:
    requests:
      storage: 1Gi
```

Apply it:

```bash
kubectl apply -f pvc.yaml
kubectl get pvc -n storage-lab
```

Create a Pod that writes a file:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: writer
  namespace: storage-lab
spec:
  containers:
    - name: writer
      image: busybox:1.36
      command: ["sh", "-c", "date > /data/created-at.txt && sleep 3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: lab-data
```

Apply it and verify the file:

```bash
kubectl apply -f writer.yaml
kubectl exec -n storage-lab writer -- cat /data/created-at.txt
```

Delete the Pod:

```bash
kubectl delete pod writer -n storage-lab
```

Create a new Pod that mounts the same PVC:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: reader
  namespace: storage-lab
spec:
  containers:
    - name: reader
      image: busybox:1.36
      command: ["sh", "-c", "cat /data/created-at.txt && sleep 3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: lab-data
```

Apply it:

```bash
kubectl apply -f reader.yaml
kubectl logs -n storage-lab reader
```

### Expected Observations

- The PVC should bind to a PV.
- The first Pod should write data to the mounted volume.
- Deleting the Pod should not delete the PVC.
- The second Pod should read the data written by the first Pod.
- The PV and backend volume remain tied to the PVC until the claim is deleted or otherwise modified.

### Cleanup

Delete the namespace:

```bash
kubectl delete namespace storage-lab
```

Before running cleanup in a real environment, confirm that the namespace contains only lab resources. Deleting the PVC may delete the backend storage depending on the reclaim policy.

## Runbook: Persistent Volume Claim or Mount Failure

### When to Use This Runbook

Use this runbook when a workload cannot start because a PVC is pending, a volume cannot attach, or a volume cannot mount.

### Step 1: Identify the Affected Workload

```bash
kubectl get pod <pod-name> -n <namespace> -o wide
kubectl describe pod <pod-name> -n <namespace>
```

Look for events containing:

- `FailedScheduling`
- `FailedAttachVolume`
- `FailedMount`
- `MountVolume.SetUp failed`
- `pod has unbound immediate PersistentVolumeClaims`

### Step 2: Inspect the Claim

```bash
kubectl get pvc -n <namespace>
kubectl describe pvc <claim-name> -n <namespace>
```

Check:

- PVC phase.
- Requested size.
- Access mode.
- StorageClass.
- Events.
- Bound PV name.

### Step 3: Inspect the PersistentVolume

```bash
kubectl get pv
kubectl describe pv <pv-name>
```

Check:

- Reclaim policy.
- Claim reference.
- CSI driver.
- Volume handle.
- Node affinity.
- Access modes.

### Step 4: Inspect the StorageClass

```bash
kubectl get storageclass <storage-class-name> -o yaml
```

Check:

- Provisioner.
- Parameters.
- Reclaim policy.
- Volume binding mode.
- Expansion setting.

### Step 5: Inspect CSI Components

```bash
kubectl get pods -A | grep -i csi
kubectl get events -A --sort-by=.lastTimestamp | tail -50
```

Check CSI controller and node plugin health. On managed Kubernetes, also check the provider add-on or managed driver status.

### Step 6: Inspect Node and Topology

```bash
kubectl get pod <pod-name> -n <namespace> -o wide
kubectl get node <node-name> --show-labels
```

Check zone, region, node readiness, taints, and volume limits.

### Step 7: Check Provider Backend

Use the cloud or storage provider console, CLI, or monitoring system to confirm:

- Backend volume exists.
- Volume is attached or detached as expected.
- Volume is in the expected zone.
- Provider API is healthy.
- Account or project limits are not exceeded.
- Encryption keys or permissions are valid.

### Step 8: Recover Safely

Possible recovery actions include:

- Restarting unhealthy CSI Pods if allowed by operational policy.
- Moving workload scheduling back to the correct topology.
- Correcting StorageClass references.
- Expanding capacity when supported.
- Restoring from a validated snapshot or backup.
- Escalating to storage provider support when backend state is inconsistent.

Do not delete PVCs, PVs, or backend volumes during an incident unless the data deletion or detachment behavior is fully understood and approved.

## Common Pitfalls

| Pitfall | Why It Hurts | Better Practice |
| --- | --- | --- |
| Writing durable data to the container filesystem | Data disappears when containers are replaced | Use PVCs or external durable services. |
| Treating `emptyDir` as persistent | Data follows Pod/node lifetime only | Use `emptyDir` only for scratch data. |
| Ignoring reclaim policy | PVC deletion can delete backend storage | Review reclaim policy before production use. |
| Using one shared PVC for replicas without application support | Corruption or write conflicts can occur | Use per-replica PVCs or a backend that supports shared access safely. |
| Assuming all StorageClasses are equivalent | Performance, topology, cost, and durability differ | Document StorageClass intent and limits. |
| Forgetting topology | Zonal disks can block rescheduling | Use appropriate binding mode and scheduling rules. |
| Assuming snapshots are backups | Snapshots may be crash-consistent only and provider-scoped | Test restore and define backup policy. |
| Deleting PVCs during incidents | May destroy or orphan production data | Pause, inspect reclaim policy, and get approval. |
| Ignoring CSI health | Kubernetes objects may be fine while CSI components are broken | Monitor CSI controller and node components. |
| Not testing restore | Backups are unproven until restored | Run scheduled restore drills. |
