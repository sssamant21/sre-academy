# 1.7 Kubernetes Security Foundations

## Purpose of This Section

This section establishes the security foundation that every Kubernetes SRE needs before operating production clusters.

Kubernetes security is not one feature. It is a system of controls across identity, API access, admission, workload isolation, secrets, network boundaries, node hardening, image supply chain, auditability, and operational process.

A secure cluster is not secure because one control is enabled. It is secure because many controls reduce blast radius when something fails.

By the end of this section, the reader should be able to explain the Kubernetes security model, identify the major control planes for security decisions, reason about workload identity and permissions, apply Pod Security Standards, understand the limits of Secrets and NetworkPolicy, and respond to common security incidents without making the situation worse.

## Kubernetes Security Mental Model

Kubernetes is an API-driven distributed system. Most security decisions eventually flow through the API server or through agents that enforce decisions on nodes.

A practical security mental model is:

```text
Who is calling?        -> authentication
What can they do?      -> authorization
Should this be allowed? -> admission control
Where can it run?      -> scheduling and node controls
How does it run?       -> Pod security context and runtime controls
What can it reach?     -> NetworkPolicy and service boundaries
What secrets can it see? -> Secrets, service accounts, and external identity
What happened?         -> audit logs, events, metrics, and forensic records
```

SREs should avoid treating Kubernetes security as a checklist that ends at cluster creation. Security posture changes every time a team adds a namespace, service account, RoleBinding, admission exception, container image, node group, ingress, Secret, or controller.

## The Kubernetes Security Boundary

Kubernetes provides mechanisms for security. It does not automatically make every workload secure.

Important boundaries:

| Boundary | Kubernetes Provides | Still Owned by Platform and Application Teams |
| --- | --- | --- |
| API access | Authentication, authorization, admission, audit | Identity lifecycle, least privilege, break-glass process, review discipline |
| Workload isolation | Namespaces, Pod Security Admission, security context, runtime integration | Application design, tenant model, policy exceptions, node isolation |
| Secret delivery | Secret API, mounted volumes, environment variables, optional encryption at rest | Secret rotation, external secret source, application handling, exposure prevention |
| Network segmentation | NetworkPolicy API | Network plugin support, default-deny design, egress controls, service mesh policy where used |
| Node security | kubelet configuration, node authorization, runtime controls | OS hardening, patching, host access, kernel security, cloud instance security |
| Supply chain | Image references, admission integration points | Image signing, scanning, registry policy, provenance, dependency governance |
| Auditability | Kubernetes audit policy and logs | Log retention, alerting, investigation process, evidence handling |

A production Kubernetes security program must define who owns each boundary.

## Authentication

Authentication answers: who is making the request?

Every Kubernetes API request is associated with a user identity, service account identity, or anonymous identity if anonymous access is enabled and accepted by configuration.

Common authentication sources include:

- Client certificates.
- Bearer tokens.
- Service account tokens.
- OpenID Connect integration.
- Webhook token authentication.
- Cloud-provider identity integration in managed Kubernetes.

SRE implications:

- Human users should authenticate through centrally managed identity, not long-lived shared credentials.
- Service accounts should be scoped to workloads and controllers, not reused across unrelated applications.
- Anonymous access should be understood and restricted according to cluster policy.
- Certificate and token lifetime should be part of operational review.
- Break-glass access should be logged, time-bound, and reviewed.

Security incidents often begin with a simple question: which identity performed the action?

If the team cannot answer that from audit logs and identity records, security operations are already behind.

## Authorization and RBAC

Authorization answers: what is this identity allowed to do?

Kubernetes commonly uses Role-Based Access Control. RBAC grants permissions through Roles, ClusterRoles, RoleBindings, and ClusterRoleBindings.

```text
Subject -> RoleBinding -> Role -> allowed verbs on resources
Subject -> ClusterRoleBinding -> ClusterRole -> cluster-wide allowed verbs on resources
```

Example Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: payments
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

Example RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payments-pod-reader
  namespace: payments
subjects:
  - kind: ServiceAccount
    name: diagnostics
    namespace: payments
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Production RBAC principles:

- Prefer namespace-scoped Roles over ClusterRoles where possible.
- Avoid broad verbs such as `*` unless there is a strong operational reason.
- Avoid broad resources such as `*` unless reviewed and time-bound.
- Treat `create pods`, `exec`, `port-forward`, `impersonate`, `bind`, `escalate`, and Secret access as sensitive permissions.
- Review ClusterRoleBindings carefully because they can grant cluster-wide access.
- Separate human access, workload access, controller access, and emergency access.
- Test permissions with `kubectl auth can-i` before granting broader rights.

Useful commands:

```bash
kubectl auth can-i get pods -n payments
kubectl auth can-i create deployments -n payments --as system:serviceaccount:payments:diagnostics
kubectl get rolebinding,clusterrolebinding -A
kubectl describe clusterrolebinding <name>
```

RBAC is a blast-radius control. A bad RoleBinding can turn one compromised workload into a cluster-wide incident.

## Service Accounts and Workload Identity

A ServiceAccount provides an identity for processes running in Pods.

Every namespace has a default ServiceAccount. If a Pod does not specify a ServiceAccount, Kubernetes uses the namespace default.

That default behavior is convenient, but it is dangerous when teams do not review it.

Production guidance:

- Create a dedicated ServiceAccount per workload or controller when it needs API access.
- Do not grant permissions to the default ServiceAccount by habit.
- Set `automountServiceAccountToken: false` for workloads that do not need the Kubernetes API.
- Keep service account permissions minimal and namespace-scoped when possible.
- Prefer cloud workload identity mechanisms over static cloud credentials stored in Kubernetes Secrets.

Example:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: invoice-api
  namespace: payments
automountServiceAccountToken: false
```

In production, many Pods do not need to call the Kubernetes API. If they do not need it, they should not receive an API token.

## Admission Control

Admission control answers: should this request be accepted after authentication and authorization?

Admission controllers can validate, mutate, or reject API requests. They are critical for enforcing cluster policy.

Examples of admission decisions:

- Reject privileged Pods.
- Require resource requests and limits.
- Require approved image registries.
- Add default labels or tolerations.
- Enforce Pod Security Admission profiles.
- Prevent unsafe hostPath mounts.
- Require a specific runtime class.
- Validate ingress or service configuration.

Admission control is where platform rules become enforceable.

SRE warning: admission webhooks are also part of the availability path for the API. A broken webhook can block deployments or cluster operations.

Operational rules for admission:

- Keep webhook timeouts short and explicit.
- Define failure policy intentionally.
- Monitor webhook latency and error rates.
- Avoid circular dependencies where a webhook depends on workloads that cannot start without the webhook.
- Test policy changes in audit or warn mode before enforcing when possible.
- Document emergency bypass or rollback procedures.

## Pod Security Standards

Pod Security Standards define three policy levels for Pods:

| Level | Intent | Typical Use |
| --- | --- | --- |
| Privileged | Unrestricted policy | Infrastructure components that require elevated host access. |
| Baseline | Prevents known privilege escalations while allowing common workloads | General workloads that are not ready for Restricted. |
| Restricted | Stronger hardening profile following current Pod hardening practices | Production application workloads where feasible. |

Pod Security Admission enforces Pod Security Standards at namespace level through labels.

Example namespace labels:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

SRE implications:

- Apply policy by namespace and workload class.
- Use `warn` and `audit` before `enforce` during migration.
- Keep privileged workloads isolated in dedicated namespaces.
- Require justification and review for exceptions.
- Do not run business application workloads in privileged namespaces.

Pod security is not just about malicious containers. It also prevents routine configuration mistakes from giving a workload host-level power.

## Security Contexts

Security context fields define how a Pod or container runs from an operating system and runtime perspective.

Important fields include:

| Field | Purpose |
| --- | --- |
| `runAsNonRoot` | Prevents running as root when supported by the image. |
| `runAsUser` | Sets the user ID for processes. |
| `allowPrivilegeEscalation` | Controls whether a process can gain more privileges. |
| `readOnlyRootFilesystem` | Reduces writable filesystem surface. |
| `capabilities.drop` | Removes Linux capabilities from containers. |
| `seccompProfile` | Applies a seccomp profile. |
| `privileged` | Grants broad host-level privileges and should be exceptional. |
| `hostNetwork`, `hostPID`, `hostIPC` | Shares host namespaces and should be tightly controlled. |
| `hostPath` | Mounts host filesystem paths and should be exceptional. |

Example hardened container posture:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-example
  namespace: payments
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: nginx:1.27
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop:
            - ALL
```

This example is a starting point, not a universal manifest. Some images need writable paths, specific users, or capabilities. The SRE job is to make those requirements explicit and reviewed.

## Secrets

Kubernetes Secrets store sensitive data as Kubernetes API objects.

Secrets are not automatically a complete secret-management system. They reduce accidental exposure compared with plain ConfigMaps, but they still require careful handling.

Production guidance:

- Enable and verify encryption at rest for Secrets.
- Limit Secret access through RBAC.
- Avoid exposing Secrets through environment variables when possible because they can be easier to leak in process metadata, debug output, or crash reports.
- Prefer mounted Secret volumes where appropriate.
- Rotate Secrets regularly.
- Avoid long-lived cloud credentials in Kubernetes Secrets when workload identity is available.
- Prevent broad `list` or `watch` access to Secrets.
- Treat logs, metrics, traces, and support bundles as possible secret exposure paths.

Example Secret mount:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secret-mount-example
  namespace: payments
spec:
  containers:
    - name: app
      image: busybox:1.36
      command: ["sh", "-c", "ls /var/run/app-secret && sleep 3600"]
      volumeMounts:
        - name: app-secret
          mountPath: /var/run/app-secret
          readOnly: true
  volumes:
    - name: app-secret
      secret:
        secretName: app-secret
```

SRE rule: anyone who can read Secrets in a namespace can often impersonate workloads or access downstream systems used by those workloads.

## Network Security

NetworkPolicy controls allowed traffic to and from Pods when the cluster network plugin supports NetworkPolicy enforcement.

A common production pattern is default deny plus explicit allow.

Example default deny ingress policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: payments
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

Example allow policy:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Production caveats:

- NetworkPolicy requires support from the network plugin.
- Policies are namespace-scoped.
- Default behavior is allow unless a policy selects the Pod for a direction.
- Egress control requires explicit egress policies.
- DNS egress must be considered when applying default-deny egress.
- NetworkPolicy is not an identity-aware application authorization system.

Network segmentation reduces blast radius. It does not remove the need for authentication and authorization inside applications.

## Image and Supply Chain Security

Kubernetes runs container images. If the image is unsafe, the workload starts unsafe.

Core production controls:

- Use trusted registries.
- Pin images by digest for high-risk workloads.
- Scan images for vulnerabilities and malware.
- Remove unused tools from runtime images.
- Use minimal base images where practical.
- Run as non-root.
- Sign images and verify signatures when the platform supports it.
- Enforce registry and signature policy through admission.
- Track provenance and build pipeline integrity.

SREs should treat image policy as a deployment safety control. A cluster that allows arbitrary images from public registries in production is accepting uncontrolled supply-chain risk.

## Node Security

Nodes are part of the security boundary. A compromised node can expose workloads, credentials, logs, volumes, and network traffic on that node.

Production node controls include:

- Keep node operating systems patched.
- Restrict SSH and administrative access.
- Use hardened images or managed node images.
- Protect kubelet configuration and credentials.
- Restrict access to the container runtime socket.
- Avoid privileged Pods except for reviewed infrastructure components.
- Isolate high-risk or privileged workloads onto dedicated nodes.
- Monitor node readiness, file integrity where available, runtime events, and suspicious process behavior.

SRE warning: granting a Pod host access is often equivalent to granting access to the node. Treat `privileged`, broad `hostPath`, `hostPID`, and container runtime socket mounts as high-risk exceptions.

## API Server and etcd Security

The API server is the front door of the cluster. etcd stores cluster state.

Production priorities:

- Use strong authentication.
- Use least-privilege authorization.
- Enable audit logging with a useful policy.
- Encrypt Secrets at rest.
- Restrict direct etcd access.
- Protect API server certificates and keys.
- Restrict network access to control-plane endpoints.
- Monitor API authorization failures, admission failures, and unusual access patterns.
- Keep control-plane components patched.

A direct etcd compromise can bypass normal Kubernetes API controls. A weak API server policy can make every other control easier to bypass.

## Multi-Tenancy and Namespace Boundaries

Namespaces are an organizational boundary. They are not a complete security boundary by themselves.

Namespaces help group resources, RBAC, policies, quotas, and service accounts. Strong multi-tenancy requires more controls:

- RBAC isolation.
- Pod Security Admission labels.
- NetworkPolicy isolation.
- ResourceQuota and LimitRange.
- Separate service accounts.
- Admission policies.
- Node isolation for sensitive or untrusted workloads.
- Secret access boundaries.
- Separate clusters for strong isolation requirements.

If two tenants cannot trust each other at all, a shared namespace model is not enough. In some cases, a shared cluster is also not enough.

## Observability and Auditability

Security controls need evidence.

Important signals:

| Signal | Why It Matters |
| --- | --- |
| Audit logs | Show API requests, identities, resources, and decisions. |
| Kubernetes events | Show scheduling, admission, and runtime failures. |
| RBAC inventory | Shows who can do what. |
| Admission metrics | Shows policy rejections and webhook health. |
| Network flow logs | Help investigate unexpected connectivity. |
| Runtime security events | Detect suspicious process, filesystem, or network activity. |
| Image scan results | Track known vulnerability exposure. |
| Node logs | Support host-level investigation. |

A security incident without logs becomes guesswork. A production cluster should define retention, access controls, and escalation paths for security evidence before an incident.

## Real-Time Production Use Case: Over-Permissive Service Account

A platform team deploys a custom controller into the `payments` namespace. The controller needs to read ConfigMaps and update a custom resource.

During a rushed rollout, the team binds the controller ServiceAccount to `cluster-admin` because the controller failed during testing.

Weeks later, an application vulnerability allows an attacker to execute commands inside the controller Pod. The attacker reads the mounted service account token, uses it against the Kubernetes API, lists Secrets across the cluster, and creates a privileged Pod in another namespace.

The incident investigation finds:

- The controller had cluster-wide permissions it did not need.
- The service account token was automatically mounted.
- No alert existed for `cluster-admin` bindings.
- Audit logs showed the unusual access, but no one reviewed them until after impact.
- NetworkPolicy did not restrict egress to the API server or sensitive services.

Corrective actions:

- Replace `cluster-admin` with a minimal Role or ClusterRole.
- Add alerts for new ClusterRoleBindings to high-privilege roles.
- Review all service accounts with broad permissions.
- Disable token automounting where workloads do not need the API.
- Add admission policy for privileged Pods.
- Review audit log retention and alerting.
- Add a break-glass process so teams do not use permanent broad permissions during incidents.

This incident is not only an RBAC problem. It is a workload identity, admission, audit, network, and operational process failure.

## Failure Scenarios

### Scenario 1: Developer Cannot Deploy a Workload

Possible causes:

- RBAC denies the request.
- Pod Security Admission rejects the Pod.
- Admission webhook rejects the manifest.
- Namespace quota blocks creation.
- Required image registry is denied.

First response:

```bash
kubectl auth can-i create deployment -n <namespace>
kubectl describe namespace <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl apply --dry-run=server -f workload.yaml
```

### Scenario 2: Pod Rejected by Pod Security Admission

Possible causes:

- Pod requests privileged mode.
- Container runs as root where Restricted policy is enforced.
- `allowPrivilegeEscalation` is not disabled.
- Required seccomp profile is missing.
- Host namespace or hostPath usage violates policy.

First response:

- Read the admission error carefully.
- Compare the workload against the namespace Pod Security labels.
- Decide whether the workload should be hardened or moved to a reviewed exception namespace.
- Avoid weakening the namespace policy for unrelated workloads.

### Scenario 3: Workload Has Too Much Kubernetes API Access

Possible causes:

- Default ServiceAccount has permissions.
- Broad RoleBinding or ClusterRoleBinding.
- Reused ServiceAccount across workloads.
- Controller installed with excessive permissions.

First response:

```bash
kubectl get serviceaccount -n <namespace>
kubectl get rolebinding,clusterrolebinding -A | grep <service-account-name>
kubectl auth can-i list secrets --as system:serviceaccount:<namespace>:<service-account-name> -A
```

### Scenario 4: Secret Exposure Suspected

Possible causes:

- Secret printed in logs.
- Secret mounted into a compromised Pod.
- User or ServiceAccount has broad Secret read access.
- Secret passed as an environment variable and exposed through debugging.
- Support bundle or crash report captured sensitive data.

First response:

- Identify the exposed Secret and consumers.
- Rotate the downstream credential.
- Review RBAC access to the Secret.
- Review logs and support artifacts for exposure.
- Check audit logs for Secret reads.
- Remove unnecessary mounts or environment variables.

## SRE Insight

Kubernetes security is mostly blast-radius engineering.

You should assume mistakes will happen: a vulnerable app, a bad image, a leaked token, a rushed RoleBinding, a misconfigured ingress, or an overly permissive admission exception.

The goal is to make each mistake smaller.

Strong Kubernetes security posture usually comes from ordinary controls applied consistently:

- Least privilege.
- Default deny where practical.
- Explicit workload identity.
- Hardened Pod defaults.
- Small exception paths.
- Good audit records.
- Tested incident response.

Security that depends on everyone remembering every rule under pressure will fail. Security that is encoded into platform defaults has a chance.

## Lab: Apply RBAC and Pod Security Foundations

### Goal

Create a namespace with Pod Security Admission labels, create a read-only ServiceAccount, verify its permissions, and observe how a restricted namespace rejects an unsafe Pod.

### Prerequisites

- A test Kubernetes cluster.
- Permission to create namespaces, Roles, RoleBindings, ServiceAccounts, and Pods.
- A cluster version that supports Pod Security Admission.

### Steps

Create a namespace with restricted Pod Security labels:

```bash
kubectl create namespace security-lab
kubectl label namespace security-lab \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted
```

Create a ServiceAccount:

```bash
kubectl create serviceaccount diagnostics -n security-lab
```

Create a read-only Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: security-lab
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

Create a RoleBinding:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: diagnostics-pod-reader
  namespace: security-lab
subjects:
  - kind: ServiceAccount
    name: diagnostics
    namespace: security-lab
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Verify permissions:

```bash
kubectl auth can-i list pods \
  --as system:serviceaccount:security-lab:diagnostics \
  -n security-lab

kubectl auth can-i list secrets \
  --as system:serviceaccount:security-lab:diagnostics \
  -n security-lab
```

Try to create an unsafe Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: unsafe-pod
  namespace: security-lab
spec:
  containers:
    - name: shell
      image: busybox:1.36
      command: ["sh", "-c", "sleep 3600"]
      securityContext:
        privileged: true
```

Apply it:

```bash
kubectl apply -f unsafe-pod.yaml
```

Create a safer Pod shape:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: safer-pod
  namespace: security-lab
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: nginx:1.27
      securityContext:
        allowPrivilegeEscalation: false
        capabilities:
          drop:
            - ALL
```

Apply it:

```bash
kubectl apply -f safer-pod.yaml
kubectl get pods -n security-lab
```

### Expected Observations

- The diagnostics ServiceAccount can list Pods but cannot list Secrets.
- The unsafe privileged Pod should be rejected in the restricted namespace.
- The safer Pod shape should pass the restricted controls only if the image and security context satisfy the policy on the test cluster.
- Admission errors should explain which Pod Security rule failed.

### Cleanup

```bash
kubectl delete namespace security-lab
```

Run this lab only in a test cluster or a safe namespace. Do not loosen production namespace security labels for experimentation.

## Runbook: Suspected Kubernetes Permission or Policy Incident

### When to Use This Runbook

Use this runbook when a user, workload, or controller appears to have excessive access, when a workload is rejected by security policy, or when a Kubernetes credential may have been exposed.

### Step 1: Preserve Evidence

- Record the namespace, workload, user, ServiceAccount, and time window.
- Preserve relevant audit logs, events, controller logs, and admission errors.
- Avoid deleting Pods or bindings until evidence is captured unless active harm is ongoing.

### Step 2: Identify the Identity

```bash
kubectl get pod <pod-name> -n <namespace> -o jsonpath='{.spec.serviceAccountName}'
kubectl get serviceaccount -n <namespace>
```

For human access, inspect identity provider records and audit logs.

### Step 3: Check Effective Permissions

```bash
kubectl auth can-i --list --as system:serviceaccount:<namespace>:<service-account>
kubectl get rolebinding -n <namespace>
kubectl get clusterrolebinding
```

Look for broad permissions, especially access to Secrets, Pods, exec, impersonation, bind, escalate, and cluster-wide resources.

### Step 4: Inspect Admission and Pod Security Controls

```bash
kubectl get namespace <namespace> --show-labels
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

Check whether Pod Security Admission, validating policies, or webhooks are enforcing the expected rules.

### Step 5: Reduce Blast Radius

Possible containment actions:

- Remove or narrow a RoleBinding.
- Disable or rotate a ServiceAccount token.
- Scale down a compromised workload.
- Block egress with NetworkPolicy or provider controls.
- Revoke downstream credentials stored in Secrets.
- Isolate affected nodes if host compromise is suspected.

Choose containment actions carefully. Removing a controller permission can stop production reconciliation. Deleting a Secret can break applications. Isolating a node can move workloads and change evidence.

### Step 6: Rotate and Recover

- Rotate exposed credentials.
- Replace compromised images or Pods.
- Recreate service account tokens if needed.
- Review audit logs for lateral movement.
- Validate that admission and RBAC changes did not break critical controllers.
- Document the final root cause and control gaps.

## Common Pitfalls

| Pitfall | Why It Hurts | Better Practice |
| --- | --- | --- |
| Binding workloads to `cluster-admin` | One Pod compromise becomes cluster compromise | Create minimal Roles and review ClusterRoleBindings. |
| Granting permissions to the default ServiceAccount | Every Pod using the default account inherits access | Use dedicated ServiceAccounts per workload. |
| Leaving service account tokens mounted everywhere | Workloads that do not need the API still receive credentials | Set `automountServiceAccountToken: false` where possible. |
| Treating Secrets as fully safe by default | Secret access depends on RBAC, encryption, logs, and application handling | Encrypt, restrict, rotate, and monitor Secret access. |
| Running production apps as privileged | Container breakout risk and host impact increase | Use restricted security contexts and isolate exceptions. |
| Applying Pod Security labels without testing | Deployments can fail unexpectedly | Use warn/audit modes before enforce. |
| Assuming NetworkPolicy works in every cluster | Enforcement depends on the network plugin | Confirm plugin support and test policies. |
| Allowing arbitrary public images | Supply-chain risk enters production | Enforce trusted registries and image policy. |
| Ignoring audit logs | Incidents become hard to reconstruct | Enable useful audit policy and retention. |
| Treating namespaces as hard tenant isolation | Shared cluster components and node resources remain risk areas | Add RBAC, policy, network, node, and sometimes cluster isolation. |
