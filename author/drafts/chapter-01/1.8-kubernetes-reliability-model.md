# 1.8 Kubernetes Reliability Model

## Purpose of This Section

This section explains how Kubernetes reliability works in production and where Kubernetes reliability ends.

Kubernetes gives engineers powerful mechanisms for keeping workloads running: reconciliation, controllers, replica management, scheduling, health probes, rollouts, self-healing, disruption budgets, resource requests, autoscaling, and failure-domain-aware placement.

Those mechanisms are not the same thing as reliability.

A reliable Kubernetes platform requires correct application design, correct workload configuration, healthy nodes, safe rollouts, tested recovery procedures, enough capacity, observability, and operational discipline.

By the end of this section, the reader should be able to explain the Kubernetes reliability model, identify common failure domains, design workloads for replacement and disruption, use health checks safely, reason about Pod disruption budgets, and troubleshoot reliability incidents without assuming Kubernetes will automatically solve application or infrastructure problems.

## Reliability Is a System Property

Reliability is the ability of a system to continue providing its intended service under expected and unexpected conditions.

In Kubernetes, reliability is produced by the interaction of several layers:

```text
Application behavior
  -> workload configuration
  -> Kubernetes controllers
  -> scheduler and node capacity
  -> networking and storage
  -> control plane availability
  -> cloud or infrastructure dependencies
  -> observability and incident response
```

If any layer is weak, the user-facing service can fail.

A Deployment with three replicas does not make a broken application reliable. A PodDisruptionBudget does not save an application that cannot tolerate one replica going away. A readiness probe does not help if it returns success before the application can actually serve traffic. A multi-zone cluster does not help if all replicas are scheduled into one zone or all data depends on one zonal disk.

Kubernetes gives the platform a reliability vocabulary. Engineers must still build the reliability model.

## What Kubernetes Can and Cannot Guarantee

| Kubernetes Can Help With | Kubernetes Cannot Guarantee By Itself |
| --- | --- |
| Restarting failed containers | Correct application recovery after restart |
| Recreating Pods after deletion | Durable state unless storage is designed correctly |
| Maintaining desired replica count | End-to-end application availability |
| Scheduling Pods onto available nodes | Enough capacity under every traffic or failure scenario |
| Removing unready Pods from Service endpoints | Correct health-check implementation |
| Rolling out new versions gradually | Safe application compatibility or migration behavior |
| Respecting PodDisruptionBudgets for voluntary evictions | Protection from every kind of deletion or involuntary failure |
| Spreading Pods when configured | Correct failure-domain design without labels and constraints |
| Autoscaling workloads when metrics are available | Good scaling behavior without useful metrics and limits |
| Reporting object status and events | Complete observability without metrics, logs, traces, and alerts |

The strongest Kubernetes reliability posture starts with a clear sentence:

```text
Kubernetes will replace failed units, but the application must tolerate replacement.
```

## Desired State and Reconciliation as Reliability Tools

Kubernetes reliability starts with the desired-state model.

Users define the intended state of the system. Controllers continuously compare desired state with observed state and attempt to reduce the difference.

Example:

```text
Desired state: Deployment has 3 replicas.
Observed state: 2 Pods are running, 1 Pod was deleted.
Controller action: create a replacement Pod.
Scheduler action: place replacement Pod on a suitable node.
Kubelet action: start containers on that node.
Service action: route only to ready endpoints.
```

This model improves reliability because recovery is automated. However, reconciliation is not instant and not magic.

Recovery can be delayed by:

- Insufficient node capacity.
- Image pull failures.
- Bad configuration.
- Failed admission policy.
- Missing Secret or ConfigMap.
- Storage attach failure.
- Node or zone outage.
- Broken container startup.
- Readiness probe failure.
- Controller or API server availability problems.

SREs should measure recovery time from the user's perspective, not only from Kubernetes object creation time.

## Failure Domains

A failure domain is a boundary within which failures are likely to be correlated.

Common Kubernetes failure domains include:

| Failure Domain | Example Failure | Reliability Control |
| --- | --- | --- |
| Container | Process crash, memory leak, deadlock | Restart policy, liveness probe, application fix |
| Pod | Bad config, init failure, sidecar failure | Replica count, rollout control, readiness probe |
| Node | Kernel panic, disk pressure, kubelet failure | Multiple nodes, node health monitoring, rescheduling |
| Zone | Cloud zone outage, zonal disk unavailable | Multi-zone nodes, topology spread, regional services |
| Cluster | Control-plane outage, network plugin failure | HA control plane, backup, failover architecture |
| Region | Regional cloud outage | Multi-region design, external traffic management |
| Dependency | Database, DNS, registry, identity provider failure | Timeouts, retries, fallback, dependency SLOs |
| Human operation | Bad rollout, unsafe drain, wrong policy change | Change control, PDBs, validation, rollback |

Kubernetes can help manage some failure domains. It cannot remove all correlated risk.

If every replica uses the same unhealthy image, every replica can fail. If every Pod depends on one external database, the Kubernetes Deployment can be healthy while the service is unavailable. If every node uses the same broken kernel version, adding replicas may not help.

## Pod Lifecycle and Replacement

Pods are disposable units of execution.

Kubernetes does not repair an individual Pod back into a pristine state forever. Controllers usually replace failed Pods with new Pods.

This has important design implications:

- Applications must tolerate process restarts.
- Pods must not depend on local container filesystem state for durable data.
- Startup must be repeatable.
- Shutdown should be graceful.
- Readiness should reflect ability to serve traffic.
- Long-running requests should drain safely during termination.
- Work queues should tolerate duplicate work or interrupted work.
- Leader election should tolerate Pod replacement.

A reliable Kubernetes application behaves well when Pods are created, stopped, moved, restarted, and replaced.

## Replication and Availability

Replicas are the basic availability mechanism for stateless workloads.

A single replica is a single point of failure. If that Pod is deleted, evicted, stuck, or scheduled onto a failed node, the service is unavailable until recovery completes.

A replicated Deployment spreads risk:

```text
1 replica  -> one Pod failure can be outage
2 replicas -> one Pod failure can be tolerated if both are healthy and reachable
3 replicas -> safer rollout and disruption behavior when configured correctly
```

Replication only works when the application supports it.

Questions for every replicated workload:

- Can multiple replicas safely serve the same traffic?
- Is session state externalized or replicated?
- Are requests idempotent where retries can happen?
- Are caches warm enough before readiness succeeds?
- Can a replica be terminated without corrupting work?
- Are downstream dependencies sized for all replicas?
- Are replicas spread across nodes and zones?

Replication is not only a Kubernetes setting. It is an application architecture decision.

## Health Checks: Startup, Readiness, and Liveness

Kubernetes probes are reliability controls when they measure the right thing.

| Probe | Purpose | Reliability Role |
| --- | --- | --- |
| Startup probe | Determines whether the container has started successfully | Protects slow-starting apps from premature liveness restarts. |
| Readiness probe | Determines whether the Pod should receive traffic | Prevents traffic to Pods that cannot serve correctly. |
| Liveness probe | Determines whether the container should be restarted | Recovers from unrecoverable stuck states. |

Readiness probes are traffic-safety tools. Liveness probes are restart tools.

This distinction matters. A failing database dependency should often make a Pod not ready, but it should not always make the Pod restart. Restarting every Pod during a database outage can amplify the incident.

Bad liveness probes are a common reliability hazard.

Failure pattern:

```text
Traffic increases.
Application slows down.
Liveness endpoint times out.
Kubelet restarts Pods.
Remaining Pods receive more traffic.
More liveness probes fail.
Cluster enters restart storm.
```

Better design:

- Use startup probes for slow initialization.
- Use readiness probes for traffic eligibility.
- Use liveness probes only for states that restart can fix.
- Keep probe endpoints cheap and local to the application.
- Avoid checking every downstream dependency in liveness.
- Tune timeouts and failure thresholds based on real startup and latency behavior.

Example probe shape:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
    spec:
      containers:
        - name: app
          image: example.com/checkout-api:v1
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
```

The endpoint names are examples. The application must implement them with correct semantics.

## Graceful Termination

Reliable workloads must shut down cleanly.

When a Pod is deleted, Kubernetes starts termination. The Pod should stop accepting new work, complete or hand off in-flight work, and exit before the grace period expires.

Important controls:

- Readiness probe behavior.
- EndpointSlice readiness updates.
- `terminationGracePeriodSeconds`.
- Application signal handling.
- PreStop hooks where appropriate.
- Load balancer drain behavior outside Kubernetes.
- Queue visibility timeout or lease behavior for workers.

SREs should test termination, not assume it works.

A graceful shutdown test is simple:

```bash
kubectl delete pod <pod-name> -n <namespace>
```

Then observe:

- Does the Pod stop receiving traffic?
- Are in-flight requests completed or retried safely?
- Does the process handle SIGTERM?
- Does the Pod exit before the grace period?
- Are errors visible to users?

## Rolling Updates and Rollbacks

Deployments support rolling updates. Rolling updates help reduce risk by replacing Pods gradually.

Important settings:

| Setting | Reliability Impact |
| --- | --- |
| `replicas` | Determines how many instances can serve traffic. |
| `maxUnavailable` | Limits how many Pods can be unavailable during rollout. |
| `maxSurge` | Allows extra Pods during rollout. |
| `progressDeadlineSeconds` | Detects rollout progress failure. |
| Readiness probe | Controls whether new Pods receive traffic. |

A rollout is only safe if the new Pods become ready for the right reasons.

If readiness is too shallow, broken Pods can receive traffic. If readiness is too strict, a rollout can stall. If resource requests are wrong, surge Pods may not schedule. If database migrations are not backward compatible, old and new Pods may not safely run together.

SRE rollout questions:

- Can old and new versions run at the same time?
- Are database changes backward compatible?
- Is readiness meaningful?
- Is rollback safe after the new version starts writing data?
- Is there enough capacity for surge Pods?
- Are alerts tied to rollout health?

## Disruptions and PodDisruptionBudgets

A disruption is an event that causes one or more Pods to stop.

Kubernetes distinguishes voluntary disruptions from involuntary disruptions.

Voluntary disruptions include:

- Node drain for maintenance.
- Cluster upgrade.
- Autoscaler removing a node.
- Administrator-initiated eviction.

Involuntary disruptions include:

- Node failure.
- Hardware failure.
- Kernel panic.
- Cloud instance loss.
- Resource-pressure eviction.
- Network partition.

A PodDisruptionBudget limits how many Pods of an application can be down simultaneously during voluntary disruptions.

Example:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: checkout-api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: checkout-api
```

This budget says at least two selected Pods should remain available during voluntary evictions.

Production caveats:

- PDBs do not prevent all disruptions.
- PDBs do not protect against node hardware failure.
- PDBs do not protect against someone directly deleting a Deployment.
- PDBs can block node drains when configured too strictly.
- A PDB for a single-replica workload can make maintenance difficult without providing high availability.
- PDB selectors must match the intended Pods.

PDBs are a reliability contract between application owners and cluster operators. They should be reviewed during application onboarding.

## Scheduling, Placement, and Failure-Domain Awareness

Kubernetes can schedule Pods across nodes and zones, but only when the cluster and workload provide the right constraints.

Useful placement controls include:

- Node selectors.
- Node affinity.
- Pod affinity and anti-affinity.
- Topology spread constraints.
- Taints and tolerations.
- PriorityClasses.

Reliability-focused placement questions:

- Are replicas spread across nodes?
- Are replicas spread across zones?
- Are critical workloads isolated from noisy or risky workloads?
- Can the scheduler place replacement Pods during a zone or node failure?
- Do storage topology constraints conflict with availability goals?
- Do topology spread constraints block scheduling during partial outages?

A workload with three replicas all on one node is not meaningfully highly available. A workload with three replicas across three zones but one zonal database dependency may still have a single dependency failure point.

## Resource Requests, Limits, and Eviction

Resource configuration is a reliability control.

Requests help the scheduler place Pods onto nodes with enough reserved capacity. Limits constrain runtime resource usage. Missing or wrong values can cause reliability problems.

Common patterns:

| Configuration Issue | Reliability Impact |
| --- | --- |
| No CPU request | Scheduler cannot reserve CPU capacity accurately. |
| No memory request | Pod may be packed onto nodes unsafely. |
| Memory limit too low | Container can be OOMKilled under normal load. |
| CPU limit too low | Container can be throttled and fail latency SLOs. |
| Request too high | Pod may be unschedulable or waste capacity. |
| No ephemeral storage awareness | Node disk pressure can evict Pods. |

SREs should treat resource requests as reliability requirements, not only cost settings.

Useful commands:

```bash
kubectl top pods -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl describe node <node-name>
```

## Autoscaling and Reliability

Autoscaling helps reliability when demand changes, but autoscaling is not instant protection.

Common autoscaling layers:

| Layer | What It Scales | Reliability Consideration |
| --- | --- | --- |
| HorizontalPodAutoscaler | Number of Pods | Needs good metrics and enough node capacity. |
| Vertical Pod Autoscaler | Pod resource recommendations or updates | Can require Pod restarts depending on mode. |
| Cluster autoscaler or node autoscaling | Number of nodes | Node provisioning takes time and depends on cloud capacity. |

Autoscaling failure patterns:

- HPA cannot scale because metrics are missing.
- HPA scales Pods but no nodes have capacity.
- Cluster autoscaler adds nodes too slowly for sudden traffic.
- Readiness delays mean new Pods exist but do not serve traffic yet.
- Downstream dependencies cannot handle increased replicas.
- Scaling down removes too much warm capacity.

Reliable systems combine autoscaling with headroom, load shedding, rate limits, and dependency capacity planning.

## Stateful Reliability

Stateful workloads require a different reliability model.

A stateless web application can often recover by creating a new Pod. A database or queue may require quorum, replication, ordered startup, durable volumes, and careful failover.

Kubernetes objects can help:

- StatefulSets provide stable Pod identity.
- PVCs provide stable storage identity.
- PodDisruptionBudgets can protect quorum during voluntary disruptions.
- Topology spread can reduce correlated placement risk.
- Readiness probes can prevent traffic before recovery completes.

Kubernetes does not automatically make a database highly available.

Stateful reliability questions:

- What is the replication model?
- What is the quorum requirement?
- What happens when one replica is lost?
- What happens when a zone is lost?
- Can the workload tolerate node drain?
- Are backups tested?
- Is restore time acceptable?
- Does the application operator handle failover safely?

## Control Plane Reliability

The control plane manages desired state, scheduling, API access, and controller behavior.

If the control plane is unavailable, already running workloads may continue serving traffic, but many operations can fail or stall:

- New Pods may not be scheduled.
- Deployments may not progress.
- Autoscaling decisions may stop.
- Node status updates may be delayed.
- Controllers may not reconcile.
- Operators may not act.
- Users may not be able to inspect or change state.

Production clusters should consider:

- Multiple control-plane nodes where self-managed.
- Highly available API server endpoint.
- etcd backup and restore plan.
- Control-plane monitoring.
- Certificate and upgrade operations.
- Managed-service control-plane SLOs and responsibility boundaries.

Managed Kubernetes reduces some control-plane burden, but it does not remove workload reliability responsibility.

## Dependency Reliability

Most Kubernetes applications depend on services outside their Pod:

- Databases.
- Object storage.
- DNS.
- Identity providers.
- Message brokers.
- Container registries.
- External APIs.
- Cloud load balancers.
- Certificate authorities.

Kubernetes might show all Pods as Running and Ready while the user-facing service is broken because a dependency is failing.

Application reliability requires:

- Timeouts.
- Retries with backoff.
- Circuit breakers.
- Connection pooling discipline.
- Graceful degradation.
- Queue-based buffering where appropriate.
- Dependency SLOs.
- Synthetic checks that exercise real user paths.

SREs should avoid measuring Kubernetes health as a substitute for service health.

## Observability for Reliability

Reliability needs signals from Kubernetes and from the application.

Important Kubernetes signals:

| Signal | Why It Matters |
| --- | --- |
| Pod restarts | Indicates crashes, liveness failures, OOMKills, or node disruptions. |
| Pod readiness | Shows whether Pods are eligible for traffic. |
| Deployment availability | Shows rollout and replica health. |
| Events | Explain scheduling, image, probe, and eviction problems. |
| Node conditions | Reveal pressure, readiness, and infrastructure issues. |
| HPA status | Shows scaling decisions and metric availability. |
| PDB status | Shows whether voluntary evictions are allowed. |
| EndpointSlice state | Shows whether Services have ready backends. |

Application signals:

- Request rate.
- Error rate.
- Latency.
- Saturation.
- Queue depth.
- Dependency errors.
- Business transaction success.

A reliable alert usually combines Kubernetes symptoms with user-impact signals. Alerting on every Pod restart can be noisy. Ignoring restart storms can be dangerous. The art is in connecting platform behavior to service impact.

## Real-Time Production Use Case: Restart Storm During Traffic Spike

A checkout service runs on Kubernetes with three replicas. Each Pod has a liveness probe pointed at `/health`, which checks database connectivity, cache connectivity, and a downstream payment gateway.

During a sale event, payment gateway latency increases. The `/health` endpoint starts timing out. Kubelet marks liveness probes failed and restarts Pods.

The restart storm causes:

- Fewer ready Pods.
- More traffic on remaining Pods.
- More probe failures.
- Cold caches after restart.
- Increased database connection churn.
- Higher user-facing latency and errors.

The team initially scales the Deployment from 3 to 10 replicas, but many new Pods also fail liveness during startup because the same endpoint is used for liveness and readiness.

Root causes:

- Liveness probe checked downstream dependencies.
- No startup probe existed.
- Readiness and liveness had the same behavior.
- Resource requests were too low for sale traffic.
- HPA was based on CPU only and reacted late.
- Payment gateway latency was not part of pre-event capacity testing.

Corrective actions:

- Make liveness local and only detect unrecoverable process failure.
- Make readiness reflect whether the Pod should receive traffic.
- Add a startup probe for warm-up.
- Increase baseline replicas before known events.
- Tune HPA metrics and thresholds.
- Add dependency latency alerts.
- Run load tests before sale events.
- Add graceful degradation for payment gateway slowness.

This was not just a probe problem. It was a reliability model problem.

## Failure Scenarios

### Scenario 1: Deployment Has Desired Replicas but Service Is Down

Possible causes:

- Pods are Running but not Ready.
- Service selector does not match Pod labels.
- EndpointSlices have no ready endpoints.
- Readiness probe is wrong.
- Application dependency is failing.
- Ingress or load balancer is misrouting traffic.

First response:

```bash
kubectl get deploy,pod,svc,endpointslice -n <namespace>
kubectl describe deploy <deployment-name> -n <namespace>
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

### Scenario 2: Rollout Stuck

Possible causes:

- New Pods fail readiness.
- New Pods cannot schedule.
- Image pull failure.
- Admission rejection.
- Missing Secret or ConfigMap.
- Resource requests exceed available capacity.
- `maxUnavailable` and `maxSurge` settings leave no room for progress.

First response:

```bash
kubectl rollout status deployment/<deployment-name> -n <namespace>
kubectl describe deployment <deployment-name> -n <namespace>
kubectl get rs,pod -n <namespace>
kubectl describe pod <new-pod-name> -n <namespace>
```

### Scenario 3: Node Drain Blocked

Possible causes:

- PodDisruptionBudget does not allow eviction.
- Single-replica workload has strict PDB.
- Pods are not managed by a controller.
- Stateful workload cannot safely move.
- DaemonSet or static Pods require drain flags or special handling.

First response:

```bash
kubectl get pdb -A
kubectl describe pdb <pdb-name> -n <namespace>
kubectl get pods -o wide -n <namespace>
```

### Scenario 4: Pods Repeatedly OOMKilled

Possible causes:

- Memory limit too low.
- Memory leak.
- Traffic increase.
- Cache growth.
- Batch workload larger than expected.
- Sidecar memory usage not accounted for.

First response:

```bash
kubectl describe pod <pod-name> -n <namespace>
kubectl top pod <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous
kubectl describe node <node-name>
```

### Scenario 5: Autoscaling Does Not Protect the Service

Possible causes:

- Metrics API unavailable.
- HPA metric does not represent load.
- HPA max replicas too low.
- Node capacity unavailable.
- Cluster autoscaler too slow.
- New Pods fail readiness.
- Dependency bottleneck outside Kubernetes.

First response:

```bash
kubectl get hpa -n <namespace>
kubectl describe hpa <hpa-name> -n <namespace>
kubectl get pods -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

## SRE Insight

Kubernetes reliability is replacement-oriented.

The platform assumes that Pods can fail, nodes can fail, and controllers can create replacements. That model works beautifully when the application is designed for replacement.

It fails painfully when the application secretly depends on local state, slow manual startup, single replicas, unsafe migrations, unbounded memory, shared mutable files, fragile dependencies, or human-only recovery.

The SRE job is to turn hidden assumptions into explicit reliability contracts.

Every production workload should answer:

- How many failures can it tolerate?
- How quickly should it recover?
- What can Kubernetes repair automatically?
- What requires application logic?
- What requires human intervention?
- What evidence proves the recovery works?

## Lab: Observe Readiness, Rollout, and Disruption Behavior

### Goal

Create a small Deployment with readiness behavior, observe how Kubernetes routes only to ready Pods, and inspect how a PodDisruptionBudget affects voluntary disruption.

### Prerequisites

- A test Kubernetes cluster.
- Permission to create Deployments, Services, and PodDisruptionBudgets.
- `kubectl` configured for the test cluster.

### Steps

Create a namespace:

```bash
kubectl create namespace reliability-lab
```

Create a Deployment and Service:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: reliability-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
            failureThreshold: 2
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: reliability-lab
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

Apply it:

```bash
kubectl apply -f web.yaml
kubectl rollout status deployment/web -n reliability-lab
kubectl get pods -n reliability-lab
kubectl get endpointslice -n reliability-lab
```

Create a PodDisruptionBudget:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web
  namespace: reliability-lab
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
```

Apply it:

```bash
kubectl apply -f pdb.yaml
kubectl describe pdb web -n reliability-lab
```

Delete one Pod and observe replacement:

```bash
kubectl delete pod -n reliability-lab -l app=web --field-selector=status.phase=Running
kubectl get pods -n reliability-lab -w
```

In another terminal, inspect the Deployment and PDB:

```bash
kubectl get deployment web -n reliability-lab
kubectl describe pdb web -n reliability-lab
```

### Expected Observations

- The Deployment should maintain three desired replicas.
- The Service should use ready endpoints.
- Deleting a Pod directly causes the Deployment controller to create a replacement.
- The PDB represents voluntary disruption budget, not protection from every direct deletion.
- The PDB should show allowed disruptions based on current healthy replicas.

### Cleanup

```bash
kubectl delete namespace reliability-lab
```

Run this lab only in a test cluster or safe namespace.

## Runbook: Kubernetes Workload Reliability Incident

### When to Use This Runbook

Use this runbook when a Kubernetes workload is unavailable, degraded, stuck during rollout, repeatedly restarting, or failing during disruption.

### Step 1: Confirm User Impact

Check service-level signals first:

- Error rate.
- Latency.
- Request volume.
- Successful transactions.
- Synthetic checks.
- Dependency health.

Do not assume Running Pods mean the service is healthy.

### Step 2: Inspect Workload State

```bash
kubectl get deploy,rs,pod,svc,endpointslice -n <namespace>
kubectl describe deployment <deployment-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

Look for unavailable replicas, failed scheduling, image pull errors, readiness failures, restarts, and missing endpoints.

### Step 3: Inspect Pods

```bash
kubectl describe pod <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous
```

Check:

- Restart count.
- Last termination reason.
- Probe failures.
- OOMKilled status.
- Node placement.
- Mounted volumes.
- Missing Secrets or ConfigMaps.

### Step 4: Inspect Rollout Status

```bash
kubectl rollout status deployment/<deployment-name> -n <namespace>
kubectl rollout history deployment/<deployment-name> -n <namespace>
```

If a new rollout caused the incident, evaluate rollback safety before rolling back. Database migrations, message formats, and external side effects can make rollback unsafe.

### Step 5: Inspect Capacity and Scheduling

```bash
kubectl top pods -n <namespace>
kubectl top nodes
kubectl describe node <node-name>
```

Check node pressure, unschedulable Pods, resource requests, and cluster capacity.

### Step 6: Inspect Disruption and Placement

```bash
kubectl get pdb -n <namespace>
kubectl describe pdb <pdb-name> -n <namespace>
kubectl get pods -n <namespace> -o wide
```

Check whether replicas are spread and whether disruption settings match operational needs.

### Step 7: Stabilize Before Optimizing

Possible stabilization actions:

- Pause a bad rollout.
- Roll back if safe.
- Scale replicas if capacity and dependencies allow.
- Increase resources if OOM or throttling is confirmed.
- Disable unsafe liveness behavior through a reviewed patch.
- Route traffic away from a broken version.
- Stop voluntary disruption such as node drains.

Avoid making multiple uncontrolled changes at once. Reliability incidents need fast action, but they still need evidence.

## Common Pitfalls

| Pitfall | Why It Hurts | Better Practice |
| --- | --- | --- |
| Treating replica count as reliability | Replicas do not help if the app cannot tolerate replacement | Design for restart, drain, and dependency failure. |
| Using the same endpoint for liveness and readiness | Dependency failures can trigger restart storms | Separate live, ready, and startup semantics. |
| No readiness probe | Traffic can reach Pods before they can serve | Add meaningful readiness checks. |
| Overly aggressive liveness probe | Temporary slowness becomes restarts | Use conservative liveness checks for unrecoverable states. |
| No resource requests | Scheduler cannot make reliable placement decisions | Define realistic CPU and memory requests. |
| Strict PDB on single replica | Maintenance can be blocked without real HA | Use replicas or accept maintenance disruption explicitly. |
| Ignoring topology | Replicas can share one node or zone | Use spread constraints or anti-affinity where appropriate. |
| Assuming HPA solves all spikes | Scaling takes time and needs metrics and capacity | Keep headroom and test scaling behavior. |
| Rolling out incompatible changes | Old and new versions cannot safely coexist | Use backward-compatible migrations and rollout plans. |
| Monitoring only Kubernetes status | User-facing failures can hide behind healthy objects | Monitor service-level indicators and dependencies. |
