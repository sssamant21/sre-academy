# 1.9 Production Use Cases and Anti-Patterns

## Purpose of This Section

This section connects the Chapter 1 foundations to real production decisions.

Kubernetes is useful when teams understand what kind of platform problem they are solving. It is risky when teams adopt it as a universal answer for every infrastructure, deployment, scaling, security, or reliability problem.

A production Kubernetes SRE must recognize two things quickly:

- A use case where Kubernetes is a good fit.
- An anti-pattern where Kubernetes adds complexity without solving the real problem.

By the end of this section, the reader should be able to identify production workloads that fit Kubernetes well, identify workloads that require extra design before moving to Kubernetes, recognize common operational anti-patterns, and ask the right questions before approving a Kubernetes production deployment.

## The Production Fit Question

Before a workload runs on Kubernetes, ask:

```text
What does Kubernetes make better for this workload?
```

Good answers include:

- The workload benefits from declarative deployment.
- The workload can run as replaceable Pods.
- The workload needs standardized rollout and rollback behavior.
- The workload benefits from service discovery and stable Service names.
- The workload can scale horizontally.
- The team needs consistent runtime, policy, and observability standards.
- The platform team wants to expose infrastructure through a common API.

Weak answers include:

- Everyone else is using Kubernetes.
- We want to avoid understanding our application architecture.
- We expect Kubernetes to make an unreliable application reliable.
- We want to run stateful systems without designing storage, backup, and recovery.
- We want cloud portability without changing provider-specific dependencies.
- We want to hide operational complexity from teams without building platform ownership.

Kubernetes is not automatically the best home for every workload. It is a powerful operating model when the workload can use the model well.

## Use Case 1: Stateless Web Services

Stateless web services are often a strong Kubernetes fit.

Typical characteristics:

- Multiple identical replicas can serve traffic.
- State is stored outside the Pod.
- Instances can be replaced safely.
- Health checks can identify traffic readiness.
- Rolling updates can safely run old and new versions together.
- Horizontal scaling can help with traffic growth.

Production design checklist:

| Area | Question |
| --- | --- |
| Readiness | Does the readiness probe reflect real traffic serving ability? |
| Liveness | Does liveness detect only restartable stuck states? |
| Rollouts | Can old and new versions coexist? |
| Configuration | Are ConfigMaps and Secrets versioned and reviewed? |
| Resources | Are CPU and memory requests realistic? |
| Scaling | Does HPA use a meaningful signal? |
| Network | Is ingress, Service, DNS, and NetworkPolicy behavior understood? |
| Observability | Are latency, errors, traffic, and saturation visible? |

Good fit example:

```text
Checkout API
- 6 replicas across 3 zones
- readiness checks local app readiness and required critical dependency state
- liveness checks process health only
- HPA scales on request rate or CPU with conservative limits
- PDB allows one replica disruption at a time
- rollout uses maxSurge and maxUnavailable tuned for capacity
```

Anti-pattern version:

```text
Checkout API
- 1 replica
- no readiness probe
- liveness checks database and payment gateway
- no resource requests
- latest image tag
- database migration runs during app startup
- no rollback plan
```

The same application can be a good Kubernetes workload or a fragile Kubernetes workload depending on design.

## Use Case 2: Internal Platform Services

Kubernetes is often useful for internal platform services such as controllers, admission webhooks, metrics collectors, gateways, DNS add-ons, certificate managers, and operators.

These workloads are close to the platform and often need Kubernetes API access.

Production requirements are higher because platform services can affect many teams.

Checklist:

- Use dedicated ServiceAccounts.
- Keep RBAC minimal.
- Avoid `cluster-admin` unless explicitly justified.
- Set resource requests and limits.
- Use high availability where the service is on the request path.
- Define failure policy for admission webhooks intentionally.
- Monitor latency, errors, queue depth, and reconciliation lag.
- Document safe rollback and emergency disable procedure.

Anti-patterns:

- Installing every controller with default broad permissions.
- Running admission webhooks with no timeout strategy.
- Depending on a webhook to admit the Pods that run the webhook itself.
- Not monitoring controller work queues.
- Treating platform add-ons as invisible infrastructure.

If a platform service breaks, application teams experience Kubernetes as broken. SREs must treat these components as production services.

## Use Case 3: Batch Jobs and Workers

Kubernetes works well for many batch jobs, workers, and asynchronous processors.

Good fit characteristics:

- Work is restartable or idempotent.
- Work can be split across Pods.
- Jobs can tolerate node or Pod replacement.
- Queue visibility timeout or lease logic handles interrupted work.
- Resource needs are known enough to schedule safely.

Common examples:

- Data processing workers.
- Image or video processing.
- Report generation.
- Queue consumers.
- Scheduled maintenance tasks.
- CI task runners when isolation and scheduling are required.

Reliability questions:

- What happens if the Pod dies halfway through a task?
- Can the same task run twice safely?
- How is failed work retried?
- Is work progress checkpointed?
- Are CPU, memory, and ephemeral storage requests realistic?
- Does scale-out overload the downstream database or queue?

Anti-patterns:

- A worker acknowledges a message before work is durable.
- A Job writes critical output only to local container filesystem.
- A CronJob has no concurrency policy and overlaps with itself.
- Hundreds of Jobs start at once and exhaust API server or node capacity.
- Batch workloads run with no quotas in shared namespaces.

Kubernetes can schedule work. It cannot make unsafe work semantics safe.

## Use Case 4: Stateful Applications

Stateful applications can run on Kubernetes, but they require more maturity.

Examples:

- Databases.
- Message brokers.
- Search clusters.
- Caches with persistence.
- Stateful coordination systems.

Kubernetes provides useful primitives:

- StatefulSets for stable Pod identity.
- PersistentVolumeClaims for stable storage identity.
- Services for discovery.
- PodDisruptionBudgets for voluntary disruption control.
- Topology spread and affinity for placement.
- Operators for domain-specific automation.

But Kubernetes does not automatically provide:

- Correct database replication.
- Backup and restore correctness.
- Application-consistent snapshots.
- Quorum safety.
- Multi-region disaster recovery.
- Zero-data-loss failover.
- Safe version upgrade semantics.

Production questions:

- What is the recovery point objective?
- What is the recovery time objective?
- Is replication synchronous or asynchronous?
- What happens during node, zone, and cluster failure?
- How are backups created, validated, and restored?
- Who owns the operator and its upgrade lifecycle?
- What is the manual break-glass process?

Anti-patterns:

- Running a single-replica production database on a single zonal disk and calling it highly available.
- Assuming VolumeSnapshots are complete backups without restore testing.
- Using shared writable storage for replicas without application support.
- Running a complex database operator without understanding its failure modes.
- Treating StatefulSet identity as a substitute for data architecture.

Stateful Kubernetes can be excellent. It is not beginner-mode Kubernetes.

## Use Case 5: Multi-Team Application Platform

Kubernetes can be a strong foundation for a shared internal platform.

Good platform characteristics:

- Standard namespace model.
- Clear team ownership.
- RBAC boundaries.
- ResourceQuota and LimitRange policies.
- Pod Security Admission standards.
- NetworkPolicy baseline.
- Approved ingress patterns.
- Standard logging, metrics, and tracing.
- Common deployment workflow.
- Documented support model.

The platform value is consistency.

Application teams should not need to reinvent deployment, discovery, runtime policy, and observability for every service.

Anti-patterns:

- Every team creates its own namespace conventions.
- No clear owner for cluster add-ons.
- No onboarding checklist.
- No resource quotas.
- No default security posture.
- No standard debugging access.
- Platform team owns the cluster but not the developer experience.
- Application teams can deploy but cannot understand failures.

A Kubernetes platform is a product. If it is not designed as a product, it becomes a shared pile of YAML.

## Anti-Pattern 1: Lift-and-Shift Without Redesign

A common mistake is moving an application to Kubernetes without changing the assumptions that made it fragile outside Kubernetes.

Symptoms:

- Application writes durable state to local disk.
- Startup requires manual steps.
- Configuration is changed by shelling into servers.
- Logs live only on the node.
- Health checks do not exist.
- Shutdown is not graceful.
- Scaling requires manual coordination.

Kubernetes will expose these weaknesses quickly.

A lift-and-shift workload may run, but it will not operate like a cloud-native workload until the application lifecycle is redesigned.

Better approach:

- Identify state, configuration, logs, and dependencies.
- Add health endpoints.
- Externalize durable state.
- Make startup repeatable.
- Make shutdown graceful.
- Define resources and scaling behavior.
- Build rollout and rollback plans.

## Anti-Pattern 2: YAML Without Ownership

Kubernetes makes it easy to apply YAML. It does not make that YAML correct.

Symptoms:

- Manifests copied from tutorials.
- No owner for resource requests.
- No owner for probes.
- No one knows why a Service is type LoadBalancer.
- RBAC rules are copied from an installation guide.
- PDBs exist but do not match actual availability goals.
- Labels are inconsistent.
- Namespaces become dumping grounds.

Every production Kubernetes object should have ownership and intent.

SRE review questions:

- Who owns this object?
- What user-facing service depends on it?
- What happens if it is deleted?
- What happens if it is misconfigured?
- How is it tested?
- How is it rolled back?

## Anti-Pattern 3: No Resource Requests

Missing resource requests are one of the most common production problems.

Without requests, the scheduler cannot make reliable placement decisions. The cluster may appear healthy until traffic increases, then multiple Pods compete for CPU, memory, or ephemeral storage.

Common results:

- Latency spikes.
- CPU throttling.
- OOMKills.
- Node pressure evictions.
- Unfair tenant behavior.
- Autoscaling based on misleading signals.

Better practice:

- Set realistic CPU and memory requests.
- Monitor actual usage against requests.
- Use limits intentionally.
- Use namespace quotas.
- Review requests during load testing.
- Adjust requests as application behavior changes.

Resource requests are not paperwork. They are scheduling contracts.

## Anti-Pattern 4: Health Checks That Hurt Reliability

Health probes are powerful and dangerous.

Common mistakes:

- No readiness probe.
- Liveness and readiness use the same endpoint.
- Liveness checks downstream dependencies.
- Probe timeout is shorter than normal latency under load.
- Startup probe is missing for slow-starting applications.
- Readiness succeeds before caches, migrations, or connections are ready.

Bad health checks can create restart storms, route traffic to broken Pods, or block healthy Pods from serving.

Better practice:

- Startup probe protects initialization.
- Readiness controls traffic eligibility.
- Liveness detects unrecoverable local process failure.
- Probe endpoints are cheap and intentional.
- Probe settings are validated under load.

## Anti-Pattern 5: Single Replica Production

A production service with one replica has a single Pod failure domain.

Possible outage triggers:

- Pod deletion.
- Node drain.
- Node failure.
- Image pull during replacement.
- Startup delay.
- Readiness failure.
- Resource eviction.

Single replica may be acceptable for non-critical workloads if downtime is explicitly accepted. It is not high availability.

Better practice:

- Run multiple replicas for stateless services.
- Spread replicas across nodes and zones where appropriate.
- Use readiness probes and PDBs.
- Confirm downstream dependencies can handle replicas.
- Document exceptions for intentionally single-replica workloads.

## Anti-Pattern 6: Using Kubernetes to Avoid Platform Decisions

Kubernetes does not remove the need for platform decisions. It concentrates them.

Teams still need to decide:

- Identity model.
- Network model.
- Ingress model.
- Storage classes.
- Backup approach.
- Runtime security baseline.
- Observability stack.
- Upgrade strategy.
- Incident response process.
- Cost ownership.

If those decisions are not made deliberately, teams will make them accidentally through inconsistent YAML and emergency fixes.

## Anti-Pattern 7: Treating Managed Kubernetes as No-Ops

Managed Kubernetes reduces operational burden, especially for control planes. It does not eliminate operations.

Platform teams still own:

- Workload configuration.
- Node pools or compute profiles.
- IAM and workload identity.
- Networking and ingress behavior.
- Storage choices.
- Security policy.
- Observability.
- Upgrades and compatibility.
- Cost and capacity.
- Incident response.

Managed Kubernetes changes the responsibility boundary. It does not remove the boundary.

## Production Admission Checklist

Before approving a workload for production, ask:

| Area | Question |
| --- | --- |
| Ownership | Who owns the workload and its manifests? |
| Criticality | What is the service tier and SLO? |
| Replicas | How many failures can it tolerate? |
| Probes | Are startup, readiness, and liveness checks correct? |
| Resources | Are requests and limits defined from evidence? |
| Rollout | Can old and new versions coexist? |
| Rollback | Is rollback safe after data changes? |
| Security | Does it run with least privilege and Pod security controls? |
| Network | Is ingress, egress, and service discovery understood? |
| Storage | Is durable state externalized or protected? |
| Disruption | Is a PDB needed and correctly configured? |
| Observability | Are service-level and Kubernetes signals visible? |
| Dependencies | Are downstream dependency limits known? |
| Recovery | Are restore or failover steps tested? |
| Cost | Is resource usage accountable? |

This checklist should be answered before the first production incident, not during it.

## Real-Time Production Use Case: A Simple API Done Well

A team wants to deploy a customer profile API.

Good production design:

- Stateless API Pods.
- Three replicas across multiple nodes.
- Readiness checks local service readiness and critical dependency availability.
- Liveness checks local process health only.
- Startup probe covers cache warm-up.
- CPU and memory requests come from load testing.
- HPA scales on request load and CPU.
- PDB keeps at least two replicas available during voluntary disruptions.
- NetworkPolicy allows only required ingress and egress.
- Secrets come from approved secret management workflow.
- Logs, metrics, traces, and synthetic checks are in place.
- Database migrations are backward compatible.
- Rollback is tested.

This is Kubernetes as an operating model, not just Kubernetes as a container launcher.

## Real-Time Production Use Case: A Platform Incident Caused by an Anti-Pattern

A team deploys a public API with two replicas, no resource requests, and a liveness probe that checks a downstream payment provider.

During a payment provider slowdown:

- Liveness probes fail.
- Pods restart.
- Remaining Pods get more traffic.
- CPU usage spikes.
- New Pods are scheduled onto already busy nodes because requests are missing.
- The HPA reacts late because metrics lag.
- Users see errors even though Kubernetes keeps recreating Pods.

The incident review finds that Kubernetes behaved as configured. The configuration encoded the wrong reliability model.

Corrective actions:

- Separate liveness and readiness semantics.
- Add startup probe.
- Add resource requests.
- Add load testing.
- Add dependency timeout and degradation behavior.
- Add PDB and topology spread.
- Add dependency-aware alerts.

The lesson is not that Kubernetes failed. The lesson is that production intent was missing.

## SRE Insight

Kubernetes rewards explicit engineering.

If a workload has clear ownership, health semantics, resource contracts, rollout rules, security boundaries, and recovery procedures, Kubernetes can make operations consistent and automatable.

If a workload has hidden state, vague ownership, copied YAML, no probes, no requests, broad permissions, and no rollback plan, Kubernetes will faithfully automate the fragility.

SREs should not ask only, "Can this run on Kubernetes?"

They should ask:

```text
Can this fail safely on Kubernetes?
Can this recover predictably on Kubernetes?
Can humans understand what Kubernetes is doing during an incident?
```

## Lab: Review a Workload for Production Readiness

### Goal

Practice reviewing a Kubernetes workload manifest for production readiness and identifying anti-patterns before deployment.

### Scenario Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: api
          image: example/orders-api:latest
          ports:
            - containerPort: 8080
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            timeoutSeconds: 1
```

### Review Tasks

Identify the production risks:

- Namespace choice.
- Replica count.
- Image tag.
- Missing readiness probe.
- Liveness behavior.
- Missing startup probe.
- Missing resource requests and limits.
- Missing security context.
- Missing Service, ingress, or traffic model.
- Missing PDB.
- Missing NetworkPolicy.
- Missing ownership labels.
- Missing rollout and rollback context.

### Improved Direction

Do not blindly patch the manifest. First write down the questions the application team must answer:

- Is this service stateless?
- What is the required availability target?
- What should readiness mean?
- What should liveness mean?
- What resources did load testing show?
- Can old and new versions coexist?
- What dependencies does it require?
- What happens during provider or database slowness?
- What security context can the image support?
- What observability exists?

### Expected Outcome

The learner should conclude that production readiness is not a YAML beautification exercise. It is a design review.

## Runbook: Production Readiness Review for a Kubernetes Workload

### When to Use This Runbook

Use this runbook before approving a new workload for production or when reviewing a workload that has repeated incidents.

### Step 1: Identify Ownership and Criticality

- Service owner.
- On-call team.
- Business function.
- SLO or availability target.
- Data classification.
- Dependencies.

### Step 2: Review Runtime Shape

```bash
kubectl get deploy,statefulset,daemonset,job,cronjob -n <namespace>
kubectl get pod -n <namespace> -o wide
```

Check workload type, replicas, labels, namespaces, and placement.

### Step 3: Review Health and Rollout Behavior

```bash
kubectl describe deployment <name> -n <namespace>
kubectl rollout history deployment/<name> -n <namespace>
```

Check probes, rollout strategy, availability, and rollback assumptions.

### Step 4: Review Resources and Scaling

```bash
kubectl top pods -n <namespace>
kubectl get hpa -n <namespace>
kubectl describe quota -n <namespace>
```

Check requests, limits, quotas, HPA, and evidence from load testing.

### Step 5: Review Security and Network Boundaries

```bash
kubectl get serviceaccount,rolebinding,networkpolicy -n <namespace>
kubectl auth can-i --list --as system:serviceaccount:<namespace>:<service-account>
```

Check least privilege, token usage, NetworkPolicy, and Pod security posture.

### Step 6: Review Recovery

Confirm:

- Rollback path.
- Backup and restore path if stateful.
- Dependency failure behavior.
- PDB behavior.
- Node drain behavior.
- Observability and alerting.

## Common Pitfalls

| Pitfall | Why It Hurts | Better Practice |
| --- | --- | --- |
| Treating Kubernetes as the goal | The workload problem may remain unsolved | Define what Kubernetes improves. |
| Lift-and-shift without redesign | Old operational assumptions break under Pod replacement | Redesign startup, state, health, logs, and shutdown. |
| Copying YAML | Hidden defaults become production behavior | Require ownership and intent for every object. |
| No resource requests | Scheduler cannot place reliably | Define requests from testing and observation. |
| One replica for critical service | One Pod failure becomes outage | Use replicas and spread them. |
| Overbroad RBAC | Workload compromise becomes cluster compromise | Use least privilege. |
| No PDB for critical replicated app | Maintenance can reduce availability unexpectedly | Configure PDB from availability goals. |
| PDB too strict | Maintenance and autoscaling can block | Align PDB with real replica count and disruption tolerance. |
| No rollback plan | Bad releases become prolonged incidents | Validate rollback and data compatibility. |
| No owner for platform decisions | Teams invent inconsistent patterns | Build platform standards and review gates. |
