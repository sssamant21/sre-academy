# 2.10 Chapter 2 Labs and Review Questions

## Purpose of This Section

This section closes Chapter 2 with hands-on labs, architecture review drills, troubleshooting scenarios, and review questions.

Chapter 2 covered Kubernetes cluster architecture from the perspective of production operations. The goal was not only to name Kubernetes
components, but to understand how they behave together when real systems are deployed, upgraded, secured, scaled, and debugged.

By completing this section, you should be able to:

- Inspect a Kubernetes cluster and explain its architecture.
- Trace control-plane and node responsibilities.
- Review cluster networking, storage, security, and upgrade readiness.
- Diagnose common architecture-level failure modes.
- Use Kubernetes CLI commands carefully in a non-production environment.
- Prepare for engineering review or SRE interview discussions about cluster architecture.

## Lab Environment Guidance

Use a non-production cluster for these labs.

Good options include:

- A local cluster such as kind, minikube, or k3d.
- A sandbox managed Kubernetes cluster.
- A dedicated training cluster.

Do not run destructive commands against production clusters while learning. Some labs include dry-run commands or read-only inspection commands.
When a command can change cluster state, the lab calls that out explicitly.

Before starting, confirm your context.

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes
```

If the current context is production, stop and switch to a safe environment.

## Lab 1: Build a Cluster Architecture Inventory

### Goal

Create a written inventory of the major architectural parts of a Kubernetes cluster.

### Commands

```bash
kubectl version
kubectl cluster-info
kubectl get nodes -o wide
kubectl get namespaces
kubectl get pods -A -o wide
kubectl get services -A
kubectl get endpointslices -A
kubectl get storageclass
kubectl get validatingwebhookconfigurations
kubectl get mutatingwebhookconfigurations
```

### Tasks

1. Record the Kubernetes server version.
2. Record the number of nodes and their roles.
3. Identify system namespaces.
4. Identify DNS, networking, storage, metrics, and admission components.
5. Identify whether the cluster has multiple zones or node pools.
6. Identify the default StorageClass, if one exists.
7. Identify admission webhooks in the API write path.

### Deliverable

Write a one-page architecture inventory with these sections:

- Cluster version.
- Control-plane visibility.
- Node layout.
- System add-ons.
- Networking components.
- Storage components.
- Security and admission components.
- Unknowns requiring platform-owner confirmation.

### Review Prompts

- Which components are Kubernetes core components?
- Which components are provider or distribution add-ons?
- Which components would be involved in a failed Pod startup?
- Which components would be involved in a failed Service connection?

## Lab 2: Trace a Pod from Scheduling to Running

### Goal

Understand how a Pod moves through scheduling, kubelet execution, readiness, and Service endpoint registration.

### Manifest

Apply this manifest in a non-production namespace.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: chapter-2-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: chapter-2-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 3
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: chapter-2-lab
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 80
```

### Commands

```bash
kubectl apply -f web.yaml
kubectl get pods -n chapter-2-lab -o wide
kubectl describe pod -n chapter-2-lab -l app=web
kubectl get deployment -n chapter-2-lab web
kubectl get replicaset -n chapter-2-lab
kubectl get service -n chapter-2-lab web
kubectl get endpointslices -n chapter-2-lab
```

### Tasks

1. Identify which node each Pod runs on.
2. Find the ReplicaSet that owns the Pods.
3. Confirm the Service selector matches the Pod labels.
4. Confirm EndpointSlices include ready Pod endpoints.
5. Explain what would happen if the readiness probe failed.

### Expected Learning

A running application is not one object. It is a chain of Deployment, ReplicaSet, Pod, node assignment, kubelet execution, readiness, Service, and
EndpointSlice state.

## Lab 3: Diagnose a Scheduling Failure

### Goal

Practice reading scheduler and node signals when a Pod cannot be scheduled.

### Manifest

This Pod requests an intentionally large amount of CPU. Adjust the value if your lab cluster is very large.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: oversized-pod
  namespace: chapter-2-lab
spec:
  containers:
    - name: pause
      image: registry.k8s.io/pause:3.10
      resources:
        requests:
          cpu: "1000"
          memory: 1Gi
```

### Commands

```bash
kubectl apply -f oversized-pod.yaml
kubectl get pod -n chapter-2-lab oversized-pod
kubectl describe pod -n chapter-2-lab oversized-pod
kubectl get nodes
kubectl describe nodes
```

### Tasks

1. Identify the scheduling event message.
2. Identify which resource blocks scheduling.
3. Explain why the Pod stays `Pending`.
4. Explain what the scheduler can and cannot fix.
5. Delete the test Pod after the lab.

```bash
kubectl delete pod -n chapter-2-lab oversized-pod
```

### Expected Learning

A `Pending` Pod is often not a kubelet problem. If the Pod has not been assigned to a node, begin with scheduler events, node capacity,
requests, taints, affinity, and topology constraints.

## Lab 4: Trace Service and Endpoint Architecture

### Goal

Understand how Services decouple clients from ephemeral Pods.

### Commands

```bash
kubectl get service -n chapter-2-lab web -o yaml
kubectl get endpointslices -n chapter-2-lab -l kubernetes.io/service-name=web -o yaml
kubectl get pods -n chapter-2-lab -l app=web --show-labels
```

### Tasks

1. Record the Service selector.
2. Record the Pod labels.
3. Record EndpointSlice addresses.
4. Temporarily change the Deployment label so the Service no longer selects the Pods.
5. Observe EndpointSlice changes.
6. Revert the label change.

### Discussion

Answer these questions:

- Why can a Service exist with no working backend Pods?
- What should an SRE check first when a Service has no endpoints?
- How do readiness probes affect endpoint availability?

## Lab 5: Review Storage Readiness

### Goal

Practice storage architecture inspection without creating production risk.

### Commands

```bash
kubectl get storageclass
kubectl describe storageclass
kubectl get pvc -A
kubectl get pv
```

### Tasks

1. Identify the default StorageClass.
2. Record whether volume expansion is enabled.
3. Record reclaim policy.
4. Record volume binding mode.
5. Identify whether `WaitForFirstConsumer` is used for topology-aware provisioning.
6. Explain what could go wrong if a zonal volume is provisioned before the Pod is scheduled.

## Lab 6: Build a Namespace Security Baseline

### Goal

Connect namespace scope, service accounts, RBAC, Pod Security Admission, and NetworkPolicy.

### Commands

```bash
kubectl label namespace chapter-2-lab \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted --overwrite

kubectl create serviceaccount readonly -n chapter-2-lab
kubectl create role pod-reader -n chapter-2-lab --verb=get,list,watch --resource=pods
kubectl create rolebinding readonly-pod-reader -n chapter-2-lab \
  --role=pod-reader \
  --serviceaccount=chapter-2-lab:readonly

kubectl auth can-i --as=system:serviceaccount:chapter-2-lab:readonly list pods -n chapter-2-lab
kubectl auth can-i --as=system:serviceaccount:chapter-2-lab:readonly list secrets -n chapter-2-lab
```

### NetworkPolicy Manifest

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: chapter-2-lab
spec:
  podSelector: {}
  policyTypes:
    - Ingress
```

### Tasks

1. Confirm the service account can list Pods.
2. Confirm the service account cannot list Secrets.
3. Apply default-deny ingress if your CNI supports NetworkPolicy.
4. Explain why NetworkPolicy objects require CNI enforcement.
5. Explain why namespace labels alone are not complete tenant isolation.

## Lab 7: Simulate Upgrade Readiness Review

### Goal

Create a pre-upgrade readiness report for a cluster.

### Commands

```bash
kubectl version
kubectl get nodes -o wide
kubectl get pods -A
kubectl get pdb -A
kubectl get validatingwebhookconfigurations
kubectl get mutatingwebhookconfigurations
kubectl api-resources
```

Pick one non-critical node and test drain planning without changing state.

```bash
kubectl drain <node-name> --ignore-daemonsets --dry-run=server
```

### Tasks

1. Record current Kubernetes server version.
2. Record node versions.
3. Identify whether any node appears unhealthy.
4. Identify PDBs that may block drains.
5. Identify admission webhooks that could affect writes during an upgrade.
6. Identify system add-ons that need compatibility review.
7. Record which Kubernetes target version would be allowed by the upstream version-skew policy.

### Expected Learning

Upgrade readiness is a cluster architecture review. It includes components, workloads, add-ons, policies, disruption controls, and recovery plans.

## Troubleshooting Drill 1: Pod Is Pending

### Scenario

A team reports that a new application is stuck in `Pending`.

### Investigation Path

```bash
kubectl get pod -n <namespace> <pod-name> -o wide
kubectl describe pod -n <namespace> <pod-name>
kubectl get nodes
kubectl describe nodes
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

### Questions

1. Has the Pod been assigned to a node?
2. Do events mention insufficient CPU, memory, taints, affinity, or volume binding?
3. Are nodes Ready?
4. Are topology or storage constraints involved?
5. Is this a scheduler problem, a node capacity problem, or a workload specification problem?

## Troubleshooting Drill 2: Pod Is Running but Service Fails

### Scenario

A Deployment shows healthy Pods, but clients cannot reach the Service.

### Investigation Path

```bash
kubectl get service -n <namespace> <service-name> -o yaml
kubectl get endpointslices -n <namespace> -l kubernetes.io/service-name=<service-name>
kubectl get pods -n <namespace> --show-labels
kubectl describe pod -n <namespace> <pod-name>
```

### Questions

1. Does the Service selector match Pod labels?
2. Are EndpointSlices populated?
3. Are endpoints ready?
4. Is DNS resolving the Service name?
5. Is NetworkPolicy blocking traffic?
6. Is the problem inside Kubernetes or at the external load balancer or ingress layer?

## Troubleshooting Drill 3: Node Becomes NotReady

### Scenario

A node changes to `NotReady`, and workloads are affected.

### Investigation Path

```bash
kubectl get nodes
kubectl describe node <node-name>
kubectl get pods -A -o wide --field-selector spec.nodeName=<node-name>
kubectl get events -A --sort-by=.lastTimestamp
```

### Questions

1. Which node condition changed?
2. Are kubelet heartbeats missing?
3. Are Pods still running on the node?
4. Are critical DaemonSets healthy on other nodes?
5. Does the cluster have enough capacity to reschedule affected workloads?
6. Are PDBs preventing or allowing voluntary evictions?

## Troubleshooting Drill 4: PVC Is Pending

### Scenario

A StatefulSet cannot start because its PVC remains `Pending`.

### Investigation Path

```bash
kubectl get pvc -n <namespace>
kubectl describe pvc -n <namespace> <pvc-name>
kubectl get storageclass
kubectl get pods -n <namespace> -o wide
```

### Questions

1. Does the PVC reference a valid StorageClass?
2. Is dynamic provisioning enabled for that StorageClass?
3. Does quota block the claim?
4. Is volume binding waiting for first consumer?
5. Is the scheduler blocked by storage topology?
6. Is backend capacity or CSI health involved?

## Troubleshooting Drill 5: Deployment Blocked During Upgrade

### Scenario

A deployment fails during a cluster upgrade window because the API server rejects the workload.

### Investigation Path

```bash
kubectl describe deployment -n <namespace> <deployment-name>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
kubectl get validatingwebhookconfigurations
kubectl get mutatingwebhookconfigurations
kubectl get namespace <namespace> --show-labels
```

### Questions

1. Is the rejection from Pod Security Admission, a validating webhook, or API schema validation?
2. Did the target Kubernetes version remove or change an API version used by the workload?
3. Are admission webhooks healthy and compatible?
4. Is the failure policy blocking writes?
5. Should the upgrade continue, pause, or roll forward with a policy fix?

## Architecture Review Scenario 1: New Production Cluster

A platform team is designing a new production Kubernetes cluster.

Review the design using these questions:

- How many control-plane instances exist, and where are they placed?
- Who manages etcd, and how is it backed up?
- How many worker node pools exist, and what workloads run on each?
- How are failure domains represented with zones, labels, and topology constraints?
- Which CNI plugin is used, and does it enforce NetworkPolicy?
- Which CSI drivers and StorageClasses are approved?
- Which namespaces get baseline or restricted Pod Security Admission?
- How are service accounts and RBAC reviewed?
- What add-ons are installed, and who owns each one?
- How are upgrades tested and rolled out?
- What are the top five failure modes the team is prepared to handle?

## Architecture Review Scenario 2: Shared Internal Platform

A company wants many teams to share one Kubernetes cluster.

Review the design using these questions:

- Are namespaces enough for the trust model, or are separate clusters needed?
- How are team RBAC permissions scoped?
- Can teams create privileged Pods?
- Can teams read Secrets outside their namespace?
- Are NetworkPolicies required between teams?
- Are resource quotas applied per team?
- Are noisy workloads isolated with node pools, taints, or quotas?
- How are cluster-wide resources such as CRDs and webhooks governed?
- How are incidents attributed to the owning team?
- What is the process for exception approval?

## Architecture Review Scenario 3: Upgrade Readiness Gate

A cluster is scheduled for a minor version upgrade next week.

Review the upgrade using these questions:

- Is the current version still supported?
- Is the target version supported by the provider or distribution?
- Are API deprecations and removals checked?
- Are all node pools ready for rollout?
- Is there enough spare capacity for drains?
- Are PDBs configured for critical workloads?
- Are admission webhooks compatible and highly available?
- Are CNI, CSI, CoreDNS, ingress, observability, and autoscaling add-ons compatible?
- Is rollback or recovery realistic?
- What is the abort criterion for the upgrade window?

## Key Takeaways

- Cluster architecture knowledge becomes useful when you can inspect and troubleshoot a real cluster.
- Most Kubernetes incidents cross component boundaries: API, scheduler, kubelet, CNI, CSI, DNS, admission, and workload behavior.
- `kubectl describe`, events, labels, selectors, EndpointSlices, node conditions, PVC events, and admission errors are core SRE tools.
- Safe maintenance requires workload health, PDBs, capacity, topology, and careful rollout control.
- A professional cluster review includes control plane, nodes, networking, storage, security, add-ons, upgrade policy, and ownership.
- Chapter 2 should leave you ready to reason about where a Kubernetes failure lives before jumping into workload-specific debugging.
