# 3.10 Chapter 3 Labs and Review Questions

## Purpose of This Section

This section closes Chapter 3 by turning workload and scheduling concepts into hands-on practice, production review drills, troubleshooting scenarios, and interview-style review questions.

Chapter 3 covered how Kubernetes runs application workloads and how SREs should reason about Pods, controllers, scheduling, resource management, autoscaling, rollouts, disruption, and graceful termination.

The goal is not to memorize object definitions. The goal is to prove that you can inspect a workload, explain how Kubernetes is managing it, identify weak production assumptions, and build a safe operational response when the workload does not behave as expected.

By completing this section, you should be able to:

- Inspect Deployments, ReplicaSets, Pods, Jobs, CronJobs, DaemonSets, and StatefulSets.
- Explain how Pods move from desired state to scheduled and running state.
- Diagnose scheduling failures caused by resource requests, node selectors, taints, tolerations, affinity, and topology constraints.
- Review requests, limits, QoS class, and eviction risk.
- Inspect HPA status and explain why autoscaling did or did not happen.
- Review PodDisruptionBudgets, probes, rollout strategy, and graceful termination behavior.
- Build a production readiness review for a Kubernetes workload.

## Lab Environment Guidance

Use a non-production cluster for these labs.

Good options include:

- kind
- minikube
- k3d
- a sandbox managed Kubernetes cluster
- a dedicated training namespace in a shared non-production cluster

Do not run these labs in production.

Before starting, confirm the active context:

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
```

Create a dedicated namespace:

```bash
kubectl create namespace chapter-3-lab
```

Use this namespace for all mutable exercises unless a lab explicitly says otherwise.

Cleanup command:

```bash
kubectl delete namespace chapter-3-lab
```

If a lab uses cluster-wide objects such as node labels, avoid changing real node labels in shared clusters. Prefer a local cluster or skip the mutation step and perform the inspection-only parts.

## Lab 1: Trace a Deployment Through ReplicaSet and Pod State

### Goal

Understand how a Deployment manages ReplicaSets and Pods during normal operation.

### Manifest

Save this as `deployment-lab.yaml`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: chapter-3-lab
  labels:
    app.kubernetes.io/name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: web
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web
    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
```

### Commands

```bash
kubectl apply -f deployment-lab.yaml
kubectl rollout status deployment/web -n chapter-3-lab
kubectl get deployment web -n chapter-3-lab
kubectl get replicaset -n chapter-3-lab
kubectl get pods -n chapter-3-lab -o wide
kubectl describe deployment web -n chapter-3-lab
```

### Tasks

1. Identify the Deployment desired replica count.
2. Identify the ReplicaSet created by the Deployment.
3. Identify which Pods are owned by the ReplicaSet.
4. Identify which nodes the Pods were scheduled onto.
5. Delete one Pod and observe reconciliation.

```bash
kubectl delete pod -n chapter-3-lab -l app.kubernetes.io/name=web
kubectl get pods -n chapter-3-lab -w
```

### Expected Learning

- The Deployment owns the rollout intent.
- The ReplicaSet owns replica count for a specific Pod template revision.
- Pods are replaceable workload instances.
- Deleting a Pod does not change Deployment desired state.
- Kubernetes creates a replacement Pod to restore desired state.

### Review Prompts

- Why should production teams avoid managing individual Pods directly for long-running services?
- What changes when the Deployment Pod template changes?
- Which object would you inspect first during a failed rollout?

## Lab 2: Observe a Rolling Update

### Goal

Observe how a Deployment rollout creates a new ReplicaSet and gradually replaces old Pods.

### Commands

Update the image:

```bash
kubectl set image deployment/web web=nginx:1.28 -n chapter-3-lab
kubectl rollout status deployment/web -n chapter-3-lab
kubectl get replicaset -n chapter-3-lab
kubectl get pods -n chapter-3-lab -o wide
kubectl describe deployment web -n chapter-3-lab
```

Inspect rollout history:

```bash
kubectl rollout history deployment/web -n chapter-3-lab
```

Rollback in the lab namespace:

```bash
kubectl rollout undo deployment/web -n chapter-3-lab
kubectl rollout status deployment/web -n chapter-3-lab
```

### Tasks

1. Identify the old ReplicaSet.
2. Identify the new ReplicaSet.
3. Confirm that Pods from the old version are reduced.
4. Confirm that Pods from the new version become Ready.
5. Explain how `maxUnavailable` and `maxSurge` would affect the rollout.

### Expected Learning

A rollout is a controlled transition between ReplicaSets. The Deployment controller manages overlap between old and new Pods, but the rollout is only safe if Pods become Ready and the cluster has enough capacity.

## Lab 3: Diagnose a Scheduling Failure

### Goal

Practice diagnosing why a Pod stays Pending.

### Manifest

Save this as `pending-pod.yaml`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: oversized-pod
  namespace: chapter-3-lab
spec:
  containers:
    - name: pause
      image: registry.k8s.io/pause:3.10
      resources:
        requests:
          cpu: "1000"
          memory: 1Gi
```

The CPU request is intentionally too large for most lab clusters.

### Commands

```bash
kubectl apply -f pending-pod.yaml
kubectl get pod oversized-pod -n chapter-3-lab
kubectl describe pod oversized-pod -n chapter-3-lab
kubectl get events -n chapter-3-lab --sort-by=.lastTimestamp
kubectl describe nodes
```

### Tasks

1. Find the scheduler event explaining why the Pod is Pending.
2. Identify whether CPU, memory, taints, affinity, or another constraint blocked scheduling.
3. Compare the Pod request with node allocatable resources.
4. Delete the Pod after the lab.

```bash
kubectl delete pod oversized-pod -n chapter-3-lab
```

### Expected Learning

The scheduler does not schedule based on observed CPU usage. It schedules based on declared requests, node allocatable resources, and scheduling constraints.

## Lab 4: Compare Requests, Limits, and QoS Class

### Goal

Observe how resource requests and limits influence Pod QoS class.

### Manifest

Save this as `qos-lab.yaml`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-pod
  namespace: chapter-3-lab
spec:
  containers:
    - name: pause
      image: registry.k8s.io/pause:3.10

kind: Pod

  name: burstable-pod
  namespace: chapter-3-lab

      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          memory: 256Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
  namespace: chapter-3-lab
spec:
  containers:
    - name: pause
      image: registry.k8s.io/pause:3.10
      resources:
        requests:
          cpu: 100m
          memory: 128Mi
        limits:
          cpu: 100m
          memory: 128Mi
```

### Commands

```bash
kubectl apply -f qos-lab.yaml
kubectl get pods -n chapter-3-lab
kubectl get pod besteffort-pod -n chapter-3-lab -o jsonpath='{.status.qosClass}{"\n"}'
kubectl get pod burstable-pod -n chapter-3-lab -o jsonpath='{.status.qosClass}{"\n"}'
kubectl get pod guaranteed-pod -n chapter-3-lab -o jsonpath='{.status.qosClass}{"\n"}'
```

### Tasks

1. Record the QoS class for each Pod.
2. Explain why each Pod received that class.
3. Explain which Pods are more likely to be evicted first under node pressure.
4. Delete the lab Pods.

```bash
kubectl delete -f qos-lab.yaml
```

### Expected Learning

QoS class is derived from resource requests and limits. It affects eviction order under node pressure, so resource configuration is an availability decision.

## Lab 5: Work with Jobs and CronJobs

### Goal

Understand the operational difference between long-running controllers and batch controllers.

### Manifest

Save this as `job-cronjob-lab.yaml`.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: one-time-job
  namespace: chapter-3-lab
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: task
          image: busybox:1.36
          command: ["sh", "-c", "echo starting; sleep 5; echo complete"]
---
apiVersion: batch/v1
kind: CronJob
metadata:
  name: scheduled-job
  namespace: chapter-3-lab
spec:
  schedule: "*/5 * * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 2
  failedJobsHistoryLimit: 2
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: task
              image: busybox:1.36
              command: ["sh", "-c", "date; echo scheduled task"]
```

### Commands

```bash
kubectl apply -f job-cronjob-lab.yaml
kubectl get jobs -n chapter-3-lab
kubectl get pods -n chapter-3-lab
kubectl logs job/one-time-job -n chapter-3-lab
kubectl get cronjob scheduled-job -n chapter-3-lab
kubectl describe cronjob scheduled-job -n chapter-3-lab
```

### Tasks

1. Observe the Job complete.
2. Identify the Pod created by the Job.
3. Inspect CronJob schedule and concurrency policy.
4. Explain why `concurrencyPolicy` matters in production.
5. Delete the Job and CronJob.

```bash
kubectl delete -f job-cronjob-lab.yaml
```

### Expected Learning

Jobs and CronJobs are completion-oriented workload controllers. They need different operational review than Deployments because retry policy, concurrency, deadlines, and history limits affect production reliability.

## Lab 6: Inspect HPA Signals

### Goal

Learn how to inspect a HorizontalPodAutoscaler and identify whether it has the metrics needed to scale.

### Manifest

Save this as `hpa-lab.yaml`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo
  namespace: chapter-3-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hpa-demo
  template:
    metadata:
      labels:
        app: hpa-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 256Mi
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-demo
  namespace: chapter-3-lab
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-demo
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
```

### Commands

```bash
kubectl apply -f hpa-lab.yaml
kubectl get hpa hpa-demo -n chapter-3-lab
kubectl describe hpa hpa-demo -n chapter-3-lab
kubectl top pods -n chapter-3-lab
kubectl top nodes
```

### Tasks

1. Identify the HPA target reference.
2. Identify `minReplicas` and `maxReplicas`.
3. Check whether current CPU metrics are available.
4. Explain why CPU requests are required for CPU utilization targets.
5. Explain what you would inspect if HPA reports unknown metrics.

### Expected Learning

HPA is a control loop that depends on a healthy metrics pipeline and meaningful resource requests. It changes desired replicas, but it does not guarantee that new Pods can schedule or become Ready.

## Lab 7: Validate PodDisruptionBudget Behavior

### Goal

Understand how a PDB limits voluntary disruption.

### Manifest

Save this as `pdb-lab.yaml`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pdb-demo
  namespace: chapter-3-lab
spec:
  replicas: 3
  selector:
    matchLabels:
      app: pdb-demo
  template:
    metadata:
      labels:
        app: pdb-demo
    spec:
      containers:
        - name: web
          image: nginx:1.27
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: pdb-demo
  namespace: chapter-3-lab
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: pdb-demo
```

### Commands

```bash
kubectl apply -f pdb-lab.yaml
kubectl rollout status deployment/pdb-demo -n chapter-3-lab
kubectl get pdb pdb-demo -n chapter-3-lab
kubectl get pdb pdb-demo -n chapter-3-lab -o yaml
```

If your lab cluster has multiple nodes, run a server-side dry run for drain:

```bash
kubectl get pods -n chapter-3-lab -o wide
kubectl drain <node-name> --ignore-daemonsets --dry-run=server
```

### Tasks

1. Record `currentHealthy`, `desiredHealthy`, and `disruptionsAllowed`.
2. Scale the Deployment to one replica and inspect the PDB again.

```bash
kubectl scale deployment pdb-demo --replicas=1 -n chapter-3-lab
kubectl get pdb pdb-demo -n chapter-3-lab
```

3. Explain why a one-replica workload cannot be highly available just because it has a PDB.
4. Delete the lab resources.

```bash
kubectl delete -f pdb-lab.yaml
```

### Expected Learning

A PDB constrains voluntary disruption. It does not create replicas, capacity, readiness, or resilience against involuntary failures.

## Lab 8: Review Graceful Termination Configuration

### Goal

Review a workload lifecycle configuration for safe termination.

### Manifest

Save this as `termination-lab.yaml`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: termination-demo
  namespace: chapter-3-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: termination-demo
  template:
    metadata:
      labels:
        app: termination-demo
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 10
            failureThreshold: 6
```

### Commands

```bash
kubectl apply -f termination-lab.yaml
kubectl rollout status deployment/termination-demo -n chapter-3-lab
kubectl delete pod -n chapter-3-lab -l app=termination-demo
kubectl get pods -n chapter-3-lab -w
```

### Tasks

1. Explain what `terminationGracePeriodSeconds` controls.
2. Explain when the `preStop` hook runs.
3. Explain what the application should do after SIGTERM.
4. Explain why external load balancer drain behavior may still matter.

### Expected Learning

Graceful termination is a contract between Kubernetes, the application process, and traffic routing systems. A lifecycle hook alone is not a complete shutdown design.

## Production Workload Review Drill

Review this workload as if it were being proposed for production.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: production
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: api
          image: example.com/orders-api:2026.08.03
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              memory: 512Mi
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
```

### Review Questions

1. Is two replicas enough for production? What information is missing?
2. Is `maxUnavailable: 1` safe for a two-replica workload?
3. Should readiness and liveness use the same endpoint?
4. Are CPU and memory requests likely to be accurate? How would you validate them?
5. Is there enough information to decide whether HPA should be used?
6. What PodDisruptionBudget would you propose?
7. What termination behavior is missing?
8. What scheduling or topology constraints might be needed?
9. What metrics would you require before approving this workload?
10. What runbook entries should exist before launch?

### Example Review Findings

| Finding | Risk | Suggested improvement |
| --- | --- | --- |
| Only two replicas | One unavailable Pod leaves little capacity buffer | Validate load and consider at least three replicas for critical services |
| `maxUnavailable: 1` with two replicas | Rollout can remove 50 percent of desired capacity | Consider `maxUnavailable: 0` with surge if capacity allows |
| Same endpoint for readiness and liveness | Overload can trigger restarts instead of traffic removal | Separate traffic readiness from process liveness |
| No startup probe | Slow startup can be killed by liveness | Add startup probe if warmup can exceed liveness tolerance |
| No PDB | Node drain can remove capacity too freely | Add a PDB aligned with replica count and SLO |
| No termination settings | In-flight requests may be dropped | Define graceful shutdown behavior and grace period |
| No topology spread | Replicas may colocate on one node or zone | Add topology spread or anti-affinity when needed |

## Troubleshooting Scenario 1: Rollout Is Stuck

### Symptoms

- `kubectl rollout status` does not complete.
- New Pods are not Ready.
- Old ReplicaSet remains scaled.

### Investigation Commands

```bash
kubectl get deployment <name> -n <namespace>
kubectl describe deployment <name> -n <namespace>
kubectl get replicaset -n <namespace>
kubectl get pods -n <namespace> -l app=<app> -o wide
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

### Questions to Answer

1. Are new Pods Pending, CrashLoopBackOff, ImagePullBackOff, or Running but not Ready?
2. Did scheduling fail because of resource requests or placement rules?
3. Did readiness fail because the new version is unhealthy?
4. Is `progressDeadlineSeconds` exceeded?
5. Should the rollout be paused or rolled back?

## Troubleshooting Scenario 2: HPA Scales but Pods Stay Pending

### Symptoms

- HPA increases desired replicas.
- Deployment desired replica count increases.
- New Pods remain Pending.
- User-facing latency remains high.

### Investigation Commands

```bash
kubectl describe hpa <name> -n <namespace>
kubectl get deployment <name> -n <namespace>
kubectl get pods -n <namespace> -l app=<app> -o wide
kubectl describe pod <pending-pod> -n <namespace>
kubectl describe nodes
kubectl get events -n <namespace> --sort-by=.lastTimestamp
```

### Questions to Answer

1. Did HPA receive valid metrics?
2. Are new Pods blocked by CPU, memory, taints, affinity, or topology spread constraints?
3. Is node autoscaling expected to add capacity?
4. Are Pods slow to start or slow to become Ready?
5. Is the maximum replica count too low for the traffic spike?

## Troubleshooting Scenario 3: Node Drain Is Blocked

### Symptoms

- Node maintenance or upgrade automation is stuck.
- `kubectl drain` reports eviction failures.
- PDB `disruptionsAllowed` is zero.

### Investigation Commands

```bash
kubectl get pods --all-namespaces -o wide --field-selector spec.nodeName=<node-name>
kubectl get pdb --all-namespaces
kubectl describe pdb <pdb-name> -n <namespace>
kubectl get deployment,statefulset -n <namespace>
kubectl get pods -n <namespace> -l <selector> -o wide
```

### Questions to Answer

1. Which workload is blocking drain?
2. Is the PDB selector correct?
3. Are enough Pods Ready?
4. Is the workload replica count too low for the budget?
5. Is it safer to scale the workload, fix readiness, postpone maintenance, or follow an incident override process?

## Chapter 3 Production Readiness Checklist

Use this checklist when reviewing a Kubernetes workload before production.

| Area | Review question |
| --- | --- |
| Controller choice | Is the workload using the right controller type for its lifecycle? |
| Pod template | Are labels, selectors, ports, and container commands correct? |
| Replicas | Is the replica count aligned with availability and load requirements? |
| Rollout | Are `maxUnavailable`, `maxSurge`, and rollback behavior safe? |
| Requests | Are CPU and memory requests based on measured behavior? |
| Limits | Are limits intentional and not causing avoidable restarts or throttling? |
| QoS | Is the QoS class acceptable for the workload criticality? |
| Scheduling | Are node selectors, affinity, taints, tolerations, and topology constraints justified? |
| Spread | Are replicas spread across nodes or zones when required? |
| Readiness | Does readiness reflect ability to serve production traffic? |
| Liveness | Does liveness detect unrecoverable states without restarting during overload? |
| Startup | Are slow-starting containers protected by startup probes? |
| Autoscaling | Are HPA metrics, resource requests, and max replicas aligned with demand? |
| Disruption | Is there a PDB for critical replicated workloads? |
| Termination | Is graceful shutdown tested with real traffic behavior? |
| Batch behavior | For Jobs and CronJobs, are retries, deadlines, and concurrency configured? |
| Observability | Are workload health, saturation, restarts, throttling, and rollout metrics visible? |
| Runbooks | Are rollout, scheduling, autoscaling, drain, and termination runbooks available? |

## Interview-Style Prompts

Use these prompts for deeper engineering discussion.

1. A Deployment has ten replicas, but all Pods are running on two nodes. What risks do you see and how would you fix placement?
2. A Pod is Pending with an event saying no nodes have enough CPU. The cluster CPU graph looks mostly idle. Explain the mismatch.
3. A service has an HPA, but traffic spikes still cause errors. Walk through your investigation.
4. A node drain is blocked by a PDB during a cluster upgrade. What is your decision process?
5. A new release passes liveness but fails readiness. What does that mean operationally?
6. A CronJob sometimes runs two copies of the same task at once. Which fields would you inspect?
7. A Pod restarts every few minutes only under high traffic. How would you evaluate the liveness probe and resource limits?
8. A StatefulSet Pod is stuck terminating after node failure. What additional risks exist compared with a stateless Deployment?
9. A rollout creates new Pods, but they remain Pending because of topology spread constraints. What tradeoff is Kubernetes enforcing?
10. A team wants `minAvailable: 100%` for every PDB. What operational problem can that create?

## Key Takeaways

- Chapter 3 is about workload behavior under real operational pressure.
- Controllers manage desired state, but SREs must understand what each controller guarantees and what it does not.
- Scheduling is based on requests, constraints, and node state, not only observed utilization.
- Resource requests and limits influence scheduling, QoS, eviction, autoscaling, and reliability.
- Autoscaling depends on useful metrics and available capacity.
- Availability during disruption requires replicas, readiness, rollout settings, PDBs, capacity, and graceful termination working together.
- Production readiness review should happen before incidents, not after the first failed rollout.
