# 2.3 — Linux Preparation

**Workflow Status:** Draft  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades

## Purpose

A production MongoDB deployment depends on the operating system being prepared deliberately before `mongod` is installed or admitted into service. Linux defaults are designed for broad compatibility, not specifically for database latency, durability, predictable memory behavior, or sustained storage I/O. This section establishes a repeatable Linux baseline for self-managed MongoDB hosts while keeping distribution-, platform-, and MongoDB-version-specific settings subject to validation against the deployment's supported configuration.

The operating-system baseline should be treated as infrastructure configuration: documented, version-controlled, automated where practical, and validated after provisioning and after major OS, kernel, image, or MongoDB changes.

## 2.3.1 Preparation Objectives

Linux preparation should provide the following outcomes before MongoDB is deployed:

- a supported 64-bit Linux platform and kernel;
- predictable CPU, memory, storage, and networking behavior;
- correctly sized and mounted database and log filesystems;
- appropriate file-descriptor and process limits;
- time synchronization and stable hostname/DNS configuration;
- a dedicated MongoDB service identity with least privilege;
- required packages, repositories, and trust configuration;
- security controls that do not unintentionally prevent MongoDB from operating;
- operating-system telemetry suitable for production troubleshooting;
- an automated and auditable host baseline.

Do not copy kernel or tuning values blindly between environments. A value that is appropriate for a dedicated physical host can be unnecessary or counterproductive on a cloud VM, container host, or a newer Linux/MongoDB release.

## 2.3.2 Validate the Supported Platform

Before installation, record and validate:

```bash
uname -a
uname -m
cat /etc/os-release
getconf LONG_BIT
```

Confirm that the selected Linux distribution, architecture, and MongoDB edition/version form a supported combination. Standardize the production image wherever possible rather than allowing nodes in the same replica set or sharded cluster to drift across unrelated distributions or kernel families.

Operationally, capture at least:

- distribution and release;
- kernel version;
- CPU architecture;
- virtualization/cloud instance type;
- filesystem and storage type;
- MongoDB version and package source.

This inventory becomes important during incident correlation and rolling upgrades.

## 2.3.3 Establish the Service Account

Package-based installations normally create the service account required by MongoDB. When building hosts through another installation method, use a dedicated non-login account rather than running `mongod` as `root`.

Example validation:

```bash
id mongod
getent passwd mongod
```

Database, journal, diagnostic, audit, and log paths must be owned by the intended service identity and should not be generally writable.

Example:

```bash
sudo chown -R mongod:mongod /var/lib/mongo /var/log/mongodb
sudo chmod 0750 /var/lib/mongo /var/log/mongodb
```

Use the actual paths and ownership model defined by the deployment rather than assuming these example paths.

## 2.3.4 Filesystem and Storage Preparation

Storage preparation has direct consequences for latency, recovery behavior, and capacity management. Provision database storage before starting MongoDB and verify the effective filesystem and mount configuration.

Useful checks include:

```bash
lsblk -f
df -hT
findmnt
mount | column -t
```

Keep sufficient free space for normal growth, index builds, maintenance, recovery, and operational headroom. Avoid allowing the database volume to approach exhaustion before remediation begins.

For production systems, separate storage decisions should explicitly cover:

- MongoDB `dbPath`;
- log destination;
- filesystem type;
- underlying block/storage class;
- volume throughput and IOPS limits;
- cloud burst-credit behavior where applicable;
- snapshot/backup interaction;
- encryption requirements;
- expansion procedure and monitoring thresholds.

Use the filesystem recommendations supported for the exact MongoDB version and storage engine. Filesystem choice should be decided during architecture review, not changed casually on an established node.

## 2.3.5 File Descriptors and Process Limits

MongoDB can maintain many files and network connections. Production hosts must not inherit restrictive interactive-shell defaults.

Inspect the current limits:

```bash
ulimit -a
ulimit -n
ulimit -u
```

For a running service, inspect the effective limits rather than assuming the shell's values apply:

```bash
cat /proc/$(pidof mongod)/limits
```

When MongoDB is managed by `systemd`, configure required service limits through the supported unit/drop-in mechanism and validate them after restart.

Example inspection:

```bash
systemctl show mongod -p LimitNOFILE -p LimitNPROC
```

The production standard should define minimum acceptable values based on the supported MongoDB guidance and expected connection/workload profile. Excessively low limits can manifest as connection failures or inability to open files under load.

## 2.3.6 Memory and Swap Behavior

MongoDB relies heavily on the operating-system page cache in addition to the WiredTiger cache. Memory planning must therefore leave adequate capacity for the OS, connections, filesystem cache, agents, and other processes.

Inspect memory and swap configuration:

```bash
free -h
swapon --show
cat /proc/sys/vm/swappiness
```

Avoid uncontrolled swapping because storage-backed memory pressure can produce severe and unpredictable database latency. At the same time, do not apply a universal swap rule without considering the MongoDB version, Linux platform, organizational recovery policy, and the consequences of out-of-memory termination.

Monitor at least:

- available memory;
- swap use and swap-in/swap-out activity;
- page faults;
- OOM events;
- WiredTiger cache pressure;
- process resident memory.

Any change to `vm.swappiness` or related virtual-memory controls should be documented, tested, and persisted through the host configuration system.

## 2.3.7 Transparent Huge Pages

Transparent Huge Pages (THP) behavior has historically been an important MongoDB host consideration, but the correct configuration depends on MongoDB and operating-system versions. Do not preserve an old tuning rule indefinitely without revalidating it against current MongoDB guidance.

Inspect the host:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/defrag
```

If the supported MongoDB guidance for the deployed version requires a THP change, implement it persistently through the distribution's supported boot, `systemd`, or tuning mechanism. Validate the effective state after reboot.

This setting should be represented in configuration management so replacement nodes receive the same validated policy.

## 2.3.8 CPU and NUMA Considerations

Record the processor topology and NUMA layout:

```bash
lscpu
numactl --hardware 2>/dev/null || true
```

On multi-socket or NUMA systems, memory locality can affect database behavior. Follow MongoDB's current platform guidance when NUMA is present. Cloud instances often abstract these details differently from large physical hosts, so validate the actual topology rather than assuming it.

Production monitoring should distinguish total CPU utilization from saturation symptoms such as sustained run queue, steal time, throttling, or a single constrained VM entitlement.

## 2.3.9 Network and Name Resolution

Replica-set and sharded-cluster members depend on stable network identity. Before MongoDB installation, validate hostname resolution and required routes between nodes.

```bash
hostnamectl
hostname -f
getent hosts "$(hostname -f)"
ip addr
ip route
```

Use resolvable hostnames appropriate for the deployment architecture. Avoid designs that depend on transient addresses when stable DNS names are available.

Validate firewall/security-group paths for MongoDB traffic, monitoring, backup, administration, and required infrastructure services. Do not expose MongoDB listeners broadly simply to make connectivity tests pass.

## 2.3.10 Time Synchronization

Clock synchronization is essential for reliable operations, logs, authentication mechanisms, monitoring correlation, and incident analysis.

Check the configured service:

```bash
timedatectl
chronyc tracking 2>/dev/null || true
chronyc sources -v 2>/dev/null || true
```

Production nodes should use the organization's approved NTP/time source and alert on material clock drift. Avoid manually adjusting clocks on database nodes as an operational practice.

## 2.3.11 Security Controls

Linux security hardening and MongoDB requirements must be designed together. Review:

- host firewall policy;
- SELinux/AppArmor state and policy;
- file and directory permissions;
- service-account privileges;
- SSH/administrative access;
- package repository trust;
- encryption and key access;
- audit requirements;
- vulnerability and patching controls.

Do not disable SELinux, AppArmor, or host firewalls as a default troubleshooting technique. If a security control blocks MongoDB, identify the required policy or rule and make the narrowest supported correction.

## 2.3.12 Package and Repository Readiness

Before installation:

```bash
# RHEL-family examples
rpm --version
dnf --version 2>/dev/null || yum --version

# Debian/Ubuntu examples
dpkg --version
apt --version
```

Configure only approved MongoDB repositories and signing keys. Pin or otherwise control package versions according to the organization's upgrade process so an unrelated OS maintenance action does not unexpectedly move MongoDB to a new release.

Production patching should distinguish:

1. routine user-space package updates;
2. kernel/security updates requiring reboot;
3. MongoDB package upgrades;
4. major distribution upgrades.

These changes have different rollback and replica-set sequencing requirements and should not be treated as a single generic patch operation.

## 2.3.13 Disable Unnecessary Host Workloads

A database node should not become a general-purpose application server. Identify agents and services that consume significant CPU, memory, disk bandwidth, or file-scanning activity.

Useful baseline commands include:

```bash
systemctl --type=service --state=running
ps -eo pid,ppid,user,%cpu,%mem,comm --sort=-%cpu | head
```

Security, monitoring, backup, and management agents may be required, but their impact should be understood. Coordinate antivirus/EDR filesystem scanning rules with security teams when scanning database data files could materially interfere with I/O or file operations.

## 2.3.14 Observability Baseline

OS telemetry must exist before the first production incident. At minimum collect or expose:

- CPU utilization, load, run queue, steal/throttle signals;
- memory available, swap, faults, OOM events;
- filesystem capacity and inode usage;
- disk latency, throughput, IOPS, queue depth, utilization;
- network throughput, retransmits, errors, and drops;
- process state and restarts;
- time synchronization health;
- kernel/system logs.

During troubleshooting, common commands include:

```bash
vmstat 1
iostat -xz 1
pidstat 1
ss -s
dmesg -T | tail -100
journalctl -u mongod
```

Install required diagnostic packages during provisioning rather than waiting for an outage, subject to the organization's hardened-image policy.

## 2.3.15 Reboot Validation

A Linux configuration is not complete until it survives reboot. After the baseline is applied and before the host enters production, reboot during the build/validation process and confirm:

- required filesystems mount correctly;
- persistent kernel/THP settings remain effective;
- limits remain correct;
- DNS and networking are healthy;
- time synchronization returns healthy;
- ownership and permissions are intact;
- monitoring/management agents start;
- the host reports no unexpected boot errors.

Once MongoDB is installed, also validate the intended service start policy and database health after a controlled reboot.

## 2.3.16 Production Readiness Checklist

A node is ready for the MongoDB installation stage when all of the following are true:

- [ ] Supported Linux distribution, architecture, and kernel are verified.
- [ ] Host image/version is recorded and standardized.
- [ ] Dedicated MongoDB service identity is defined.
- [ ] Database and log paths are provisioned with correct ownership.
- [ ] Filesystem/storage configuration is validated.
- [ ] Capacity headroom and expansion procedure are defined.
- [ ] File-descriptor/process limits meet the approved baseline.
- [ ] Memory and swap policy is validated.
- [ ] THP policy is validated for the deployed MongoDB/OS versions.
- [ ] CPU/NUMA topology has been reviewed where applicable.
- [ ] Stable hostname, DNS, routing, and required ports are validated.
- [ ] Time synchronization is healthy.
- [ ] SELinux/AppArmor/firewall policies are intentionally configured.
- [ ] Approved package repository and version-control policy are ready.
- [ ] OS monitoring and diagnostic tooling are available.
- [ ] Persistent settings have been validated after reboot.
- [ ] Configuration is captured in automation/configuration management where practical.

## 2.3.17 SRE/DBRE Operational Guidance

Treat Linux drift as a reliability risk. Hosts in the same MongoDB topology should be comparable enough that an incident on one node can be interpreted against its peers. Differences in kernel, mount options, storage limits, agents, or tuning parameters can otherwise create intermittent behavior that appears to be a MongoDB problem.

For production fleets, maintain a machine-readable baseline and continuously detect deviations. Couple OS metrics with MongoDB metrics so incident responders can distinguish database contention from host-level memory pressure, I/O saturation, network loss, or CPU throttling.

Changes to kernel, filesystem, storage, security, or resource-limit configuration should follow the same change-control discipline as important MongoDB configuration changes: documented intent, staged validation, rollback plan, and post-change health verification.

## 2.3.18 Draft Review Notes

This draft intentionally avoids hard-coding tuning values that may differ by MongoDB release, Linux distribution, deployment model, or vendor guidance. During **Technical + Source Review**, validate the recommendations against the exact supported MongoDB documentation, especially filesystem guidance, THP behavior, NUMA, swap, and resource-limit recommendations. Distribution-specific persistence examples should also be reviewed before the section becomes canonical.
