# 2.3 — Linux Preparation

**Workflow Status:** Technical + Source Review Complete  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades

## Purpose

A production MongoDB deployment depends on the operating system being prepared deliberately before `mongod` is installed or admitted into service. Linux defaults target general-purpose workloads, not specifically database latency, predictable memory behavior, sustained random I/O, or high connection counts. This section defines a production baseline for self-managed MongoDB hosts and identifies settings that must be validated against the exact MongoDB major version, Linux distribution, kernel, and deployment model.

The Linux baseline should be treated as infrastructure configuration: documented, version-controlled, automated where practical, and revalidated after OS, kernel, image, storage, or MongoDB changes.

## 2.3.1 Preparation Objectives

Linux preparation should provide the following outcomes before MongoDB is deployed:

- a supported Linux distribution, kernel, CPU architecture, and MongoDB version combination;
- predictable CPU, memory, storage, and network behavior;
- correctly sized and mounted database and log filesystems;
- resource limits suitable for MongoDB's files, threads, and connections;
- MongoDB-version-appropriate Transparent Huge Pages configuration;
- validated NUMA behavior where applicable;
- time synchronization and stable hostname/DNS configuration;
- a dedicated MongoDB service identity with least privilege;
- approved repositories, package-signing trust, and version-control policy;
- host security controls intentionally configured for MongoDB;
- operating-system telemetry available before production cutover;
- persistent, repeatable configuration after reboot.

Do not copy tuning parameters blindly between environments. A setting that was appropriate for MongoDB 6.0 or 7.0 may be explicitly wrong for MongoDB 8.0, and a physical NUMA server may require different operating-system treatment from a cloud VM.

## 2.3.2 Validate Platform and Kernel Support

Before installation, capture the platform baseline:

```bash
uname -a
uname -r
uname -m
cat /etc/os-release
getconf LONG_BIT
```

Confirm that the selected Linux distribution, CPU architecture, kernel, MongoDB edition, and MongoDB release form a supported combination. MongoDB's production notes should be checked during every major-version installation or upgrade because platform requirements and known kernel incompatibilities can change.

Operational inventory should include at least:

- Linux distribution and release;
- kernel version;
- CPU architecture and microarchitecture where relevant;
- virtualization or cloud instance type;
- filesystem and storage type;
- MongoDB edition and version;
- MongoDB package source;
- image/build identifier.

Standardize the host image across members of the same replica set or sharded-cluster role wherever possible. Kernel or image drift complicates incident comparison and may expose only part of a cluster to an OS-specific defect.

## 2.3.3 Establish the Service Account

Package installations normally create the service identity required by MongoDB. For custom installation methods, run MongoDB under a dedicated non-login account rather than `root`.

Validate the account:

```bash
id mongod
getent passwd mongod
```

Database, journal, diagnostic, audit, and log paths must be owned by the intended MongoDB service identity and should not be generally writable.

Example:

```bash
sudo chown -R mongod:mongod /var/lib/mongo /var/log/mongodb
sudo chmod 0750 /var/lib/mongo /var/log/mongodb
```

Use the paths and account names defined by the actual package and deployment design rather than assuming the examples above.

## 2.3.4 Filesystem and Storage Preparation

Storage configuration directly affects latency, recovery time, and production stability. Provision and validate database storage before starting MongoDB.

Useful checks include:

```bash
lsblk -f
df -hT
findmnt
mount | column -t
```

MongoDB production guidance supports XFS and EXT4 on Linux and strongly recommends XFS for WiredTiger data-bearing nodes because EXT4 can exhibit performance issues with WiredTiger. For XFS-backed data volumes, disable access-time updates (`atime`) unless a platform-specific requirement prevents doing so.

The production storage design should explicitly document:

- MongoDB `dbPath`;
- log destination;
- filesystem type and mount options;
- underlying block/storage class;
- provisioned and effective IOPS/throughput;
- cloud burst-credit or throttling behavior where applicable;
- encryption requirements;
- snapshot/backup interaction;
- capacity expansion procedure;
- warning and critical free-space thresholds.

Keep sufficient free space for normal growth, index builds, maintenance, rollback/recovery operations, and temporary operational overhead. Do not operate a production database with disk-exhaustion as the normal capacity trigger.

For WiredTiger, also validate device readahead. MongoDB currently recommends a readahead value between 8 and 32 unless testing demonstrates a repeatable benefit from another value.

Example inspection:

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,RA
blockdev --getra /dev/<device>
```

Any readahead change should be made through the platform-supported persistent mechanism and verified after reboot.

## 2.3.5 File Descriptors and Process Limits

`mongod` and `mongos` use file descriptors and threads for network connections and internal activity. Restrictive OS limits can lead to failed connections or service degradation under load.

Inspect shell limits:

```bash
ulimit -a
ulimit -n
ulimit -u
```

For a running process, inspect the effective limits:

```bash
cat /proc/$(pidof mongod)/limits
```

When MongoDB runs under `systemd`, inspect the service limits directly:

```bash
systemctl show mongod -p LimitNOFILE -p LimitNPROC
```

MongoDB emits a startup warning when the open-files limit is below 64,000. Treat that as a minimum-warning boundary rather than blindly using the same number for every workload. Connection count, number of data files, monitoring agents, and other service characteristics should be considered when establishing the host standard.

Persist limits through the supported `systemd` unit/drop-in or distribution mechanism and validate them after restart.

## 2.3.6 Memory, WiredTiger Cache, and Swap

MongoDB with WiredTiger uses both the WiredTiger internal cache and the operating-system filesystem cache. Host memory must therefore accommodate MongoDB cache, filesystem cache, connections, operating-system processes, and required agents.

Inspect memory and swap:

```bash
free -h
swapon --show
cat /proc/sys/vm/swappiness
```

Avoid sustained swap activity because it can cause severe and unpredictable database latency. However, do not apply a universal "disable swap" rule. MongoDB's current production guidance distinguishes between dedicated MongoDB hosts and hosts sharing memory with other software, and the correct policy should account for the consequences of both swapping and OOM termination.

Monitor at least:

- available memory;
- swap occupancy;
- swap-in/swap-out rate;
- major page faults;
- OOM events;
- MongoDB resident memory;
- WiredTiger cache utilization and eviction pressure.

Do not increase the WiredTiger cache above its default simply because free RAM exists. MongoDB intentionally leaves memory available for the filesystem cache and other consumers. Containers and constrained cgroups require additional validation because visible host memory and the process memory limit may differ.

Any change to `vm.swappiness` or related virtual-memory controls must be documented, tested, persisted, and rechecked after reboot.

## 2.3.7 Transparent Huge Pages: Version-Specific Requirement

Transparent Huge Pages (THP) must be configured according to the MongoDB major version.

**MongoDB 8.0 and later:** enable THP. MongoDB 8.0 introduced an upgraded TCMalloc implementation for which MongoDB recommends THP enabled.

**MongoDB 7.0 and earlier:** disable THP for best performance.

Inspect the host:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/defrag
```

Do not carry a pre-8.0 "always disable THP" standard forward into MongoDB 8.0+ deployments. Conversely, do not enable THP on a 7.0-or-earlier deployment merely because the operating system defaults to it.

Implement the required state persistently using the distribution's supported `systemd`, boot, or tuning mechanism and verify it after reboot. On some Red Hat-derived systems, THP controls may appear under `/sys/kernel/mm/redhat_transparent_hugepage/` rather than the generic path.

For MongoDB 8.0+, use the current MongoDB THP/TCMalloc instructions for the complete required settings rather than setting only `enabled=always` manually.

## 2.3.8 CPU and NUMA Considerations

MongoDB's WiredTiger storage engine is multithreaded and benefits from multiple CPU cores. MongoDB production guidance recommends that a `mongod` or `mongos` have access to at least two real cores or one multi-core physical CPU.

Inspect topology:

```bash
lscpu
numactl --hardware 2>/dev/null || true
```

MongoDB recommends disabling NUMA in BIOS when possible. If that is not possible, follow MongoDB's NUMA-specific guidance rather than relying on default memory placement. This is particularly important on large multi-socket physical systems.

Production CPU monitoring should distinguish ordinary utilization from saturation indicators such as:

- sustained run queue;
- CPU steal time;
- VM or container throttling;
- cgroup quota exhaustion;
- uneven NUMA behavior;
- CPU-intensive encryption/compression workloads.

For MongoDB Enterprise deployments using encryption, CPUs with AES-NI can materially improve encryption performance.

## 2.3.9 Network and Name Resolution

Replica-set and sharded-cluster members depend on stable network identity and predictable name resolution.

Validate:

```bash
hostnamectl
hostname -f
getent hosts "$(hostname -f)"
ip addr
ip route
```

Use resolvable hostnames appropriate for the deployment architecture. Avoid depending on transient addresses when stable DNS names are available.

Before installation or cluster formation, validate required paths for:

- MongoDB member-to-member traffic;
- application connectivity;
- monitoring;
- backup;
- administration;
- DNS and NTP infrastructure.

Do not expose MongoDB listeners broadly simply to make connectivity testing easier. Security-group and firewall rules should implement the minimum required reachability.

## 2.3.10 Time Synchronization

Reliable time synchronization is required for operational logs, incident correlation, authentication mechanisms, monitoring, and distributed-system troubleshooting.

Check the active configuration:

```bash
timedatectl
chronyc tracking 2>/dev/null || true
chronyc sources -v 2>/dev/null || true
```

Production nodes should use the organization's approved NTP/time source and alert on material clock drift. Manual clock changes should not be a routine database-node operation.

## 2.3.11 SELinux, AppArmor, and Host Security

Linux security hardening and MongoDB requirements must be designed together. Review:

- host firewall policy;
- SELinux or AppArmor state and policy;
- file and directory permissions;
- service-account privileges;
- SSH/administrative access;
- repository/signing-key trust;
- encryption and key access;
- audit requirements;
- vulnerability and patching controls.

MongoDB supports SELinux configuration, but non-default data paths or ports can require additional policy work. Do not disable SELinux, AppArmor, or host firewalls as a default remediation step. Determine the blocked operation and apply the narrowest supported policy change.

When SELinux is enabled, review MongoDB's current production notes for server-side JavaScript restrictions and any version-specific caveats.

## 2.3.12 Package and Repository Readiness

Before installation, confirm the expected package tools exist:

```bash
# RHEL-family examples
rpm --version
dnf --version 2>/dev/null || yum --version

# Debian/Ubuntu examples
dpkg --version
apt --version
```

Configure only approved MongoDB repositories and signing keys. Control MongoDB package versions so a generic OS patch operation does not unexpectedly perform a database major or minor upgrade outside the approved change window.

Operationally distinguish:

1. routine user-space OS package updates;
2. kernel/security updates requiring reboot;
3. MongoDB package upgrades;
4. major Linux distribution upgrades.

These activities have different validation, replica-set sequencing, rollback, and compatibility requirements.

## 2.3.13 Keep Database Hosts Purpose-Built

MongoDB production guidance recommends dedicated systems when possible. Avoid using production database hosts as general-purpose application servers.

Review active services and heavy consumers:

```bash
systemctl --type=service --state=running
ps -eo pid,ppid,user,%cpu,%mem,comm --sort=-%cpu | head
```

Security, observability, backup, and management agents may be necessary, but their resource impact must be understood. Coordinate EDR/antivirus scanning behavior with security teams if filesystem scanning can materially interfere with database I/O.

In virtualized environments, avoid dynamic memory features such as ballooning for production MongoDB unless the platform and architecture have been explicitly validated for them.

## 2.3.14 Observability Baseline

OS telemetry must exist before the first production incident. At minimum collect or expose:

- CPU utilization, load, run queue, steal/throttle indicators;
- memory available, swap activity, faults, OOM events;
- filesystem capacity and inode usage;
- disk latency, throughput, IOPS, queue depth, utilization;
- network throughput, retransmits, errors, and drops;
- process state and service restarts;
- time synchronization health;
- kernel and system logs.

Useful Linux troubleshooting tools include:

```bash
vmstat 1
iostat -xz 1
pidstat 1
ss -s
dmesg -T | tail -100
journalctl -u mongod
```

Install approved diagnostic packages during provisioning rather than discovering they are absent during an outage.

## 2.3.15 Reboot Validation

A Linux baseline is not production-ready until persistent configuration survives reboot. During the host build process, perform a controlled reboot and verify:

- database filesystems mount correctly;
- XFS/EXT4 mount options remain as designed;
- readahead remains correct;
- THP state matches the MongoDB major version;
- resource limits remain correct;
- DNS and routing are healthy;
- time synchronization returns healthy;
- ownership and permissions are intact;
- required monitoring/management agents start;
- no unexpected boot or kernel errors appear.

After MongoDB is installed, also validate the intended `mongod` service start policy and database health after a controlled reboot.

## 2.3.16 Production Readiness Checklist

A node is ready for the MongoDB installation stage when all of the following are true:

- [ ] Supported Linux distribution, architecture, kernel, and MongoDB version are verified.
- [ ] Known kernel incompatibilities for the selected MongoDB release have been checked.
- [ ] Host image/version is recorded and standardized.
- [ ] Dedicated MongoDB service identity is defined.
- [ ] Database and log paths are provisioned with correct ownership.
- [ ] XFS or EXT4 filesystem configuration is validated; XFS is preferred for WiredTiger data-bearing nodes.
- [ ] `atime` policy is validated for database storage.
- [ ] Storage latency, IOPS, throughput, and capacity headroom are understood.
- [ ] WiredTiger device readahead is within the approved range or supported by workload testing.
- [ ] Open-file and process limits meet the approved production baseline.
- [ ] Memory and swap policy is validated.
- [ ] WiredTiger cache is not oversized without an explicit reason.
- [ ] THP configuration matches the MongoDB major version.
- [ ] CPU and NUMA topology have been reviewed.
- [ ] Stable hostname, DNS, routing, and required ports are validated.
- [ ] Time synchronization is healthy.
- [ ] SELinux/AppArmor/firewall policies are intentionally configured.
- [ ] Approved package repository and version-control policy are ready.
- [ ] OS monitoring and diagnostic tooling are available.
- [ ] Persistent settings have been verified after reboot.
- [ ] Configuration is captured in automation/configuration management where practical.

## 2.3.17 SRE/DBRE Operational Guidance

Treat Linux configuration drift as a reliability risk. Hosts in the same MongoDB topology should be sufficiently comparable that an incident on one node can be evaluated against its peers. Differences in kernel level, THP policy, mount options, storage settings, resource limits, or security agents can create intermittent behavior that appears to be a MongoDB defect.

Maintain a machine-readable production baseline and continuously detect deviations. Couple host metrics with MongoDB metrics so responders can distinguish database contention from host memory pressure, I/O saturation, network loss, CPU throttling, or OS-level resource exhaustion.

Kernel, filesystem, storage, THP, NUMA, security, and resource-limit changes should follow the same change-control discipline as important MongoDB configuration changes: documented intent, staged validation, rollback plan, and post-change health verification.

## 2.3.18 Technical + Source Review Findings

**Review result: PASS WITH TECHNICAL REVISIONS.**

The draft's overall architecture and operational guidance were sound, but the review identified several areas where explicit version-aware guidance was required. The section has been revised accordingly.

Key corrections and confirmations:

- Clarified that MongoDB 8.0+ should run with THP enabled, while MongoDB 7.0 and earlier should run with THP disabled.
- Added MongoDB's strong XFS recommendation for WiredTiger data-bearing nodes and retained EXT4 as supported.
- Added the current WiredTiger readahead recommendation of 8–32.
- Added the MongoDB startup-warning threshold for open-files limits below 64,000.
- Strengthened NUMA guidance to reflect MongoDB's recommendation to disable NUMA in BIOS when possible.
- Confirmed that WiredTiger uses both its internal cache and the Linux filesystem cache and that cache should not be enlarged casually.
- Strengthened swap wording to avoid an unsafe universal "swap off" rule.
- Added minimum CPU guidance and virtual-machine memory-ballooning considerations.
- Added explicit requirement to check current production notes for kernel/version incompatibilities during installation and upgrades.
- Clarified SELinux handling instead of recommending security-control disablement.
