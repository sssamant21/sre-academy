## Replica-Set Client Architecture

MongoDB replica sets provide redundancy and automatic primary election, but applications should not implement their own primary-discovery or failover logic. Supported MongoDB drivers are topology-aware.

```text
Application
     │
     ▼
MongoDB Driver
     │
     ▼
Seed / SRV Discovery
     │
     ▼
SDAM
     │
     ▼
Runtime Topology
     │
     ▼
Operation Requirements
     │
     ▼
Server Selection
     │
     ▼
Selected Server
     │
     ▼
Connection Pool
     │
     ▼
Operation
```

> **Replica-set availability is a collaboration between the MongoDB deployment, the driver, the application, and the network connecting them.**

A healthy replica set alone does not guarantee application-visible database availability.

## Seed Lists and Initial Discovery

A standard replica-set URI can provide multiple initial endpoints:

```text
mongodb://mongo01.example.com:27017,mongo02.example.com:27017,mongo03.example.com:27017/?replicaSet=rs0
```

These hosts are seed endpoints. They answer where the driver can begin discovery; they do not permanently determine which member handles future operations.

> **Replica-set seed lists are discovery entry points, not static routing tables.**

Multiple seeds improve startup resilience because topology discovery cannot begin until the client can reach an initial discovery endpoint. SRV-based connectivity provides a different initial discovery mechanism but leads into the same topology-aware driver architecture.

## Server Discovery and Monitoring — SDAM

MongoDB drivers use Server Discovery and Monitoring (SDAM) to discover deployment topology and track changes over time.

```text
MongoDB Driver
      │
      ▼
SDAM
      │
      ├── Discover Servers
      ├── Identify Server Types
      ├── Monitor Servers
      ├── Maintain Topology View
      └── Supply Selection Information
```

SDAM is not merely a startup operation. Members can become primary or secondary, restart, become unreachable, recover, be added or removed, or enter transitional states. The driver's topology view must evolve with those changes.

Discovery asks what servers exist. Monitoring tracks their current state.

## Runtime Topology

A simplified replica-set view might be:

```text
Replica Set rs0
      │
      ├── mongo01 — PRIMARY
      ├── mongo02 — SECONDARY
      └── mongo03 — SECONDARY
```

The driver maintains its own runtime representation of this topology. The application normally does not need to know which hostname is primary.

> **Applications should target the replica-set topology through a supported MongoDB driver rather than permanently assuming that a particular hostname is the primary.**

## Topology Discovery vs. Server Selection

Topology discovery asks what servers exist and what their current state is. Server selection asks which currently known server is suitable for a particular operation.

```text
SDAM
 │
 ▼
Runtime Topology
 │
 ▼
Operation Requirements
 │
 ▼
Server Selection
 │
 ▼
Suitable Server
```

A driver can successfully discover a replica set while still being unable to find a suitable server for a particular operation.

> **Discovery determines what MongoDB servers the driver knows about; server selection determines which suitable server should handle a particular operation.**

## Server Selection Is Operation-Specific

Server selection is evaluated against the driver's current topology view in the context of an operation. Requirements can include whether the operation is a read or write, read preference, topology state, staleness rules, tag requirements, and latency eligibility.

> **Being connected to MongoDB does not guarantee that a suitable server is currently available for every operation.**

## Write Server Selection

For normal replica-set writes, server selection requires the current writable primary.

```text
Write Operation
      │
      ▼
Runtime Topology
      │
      ▼
Writable PRIMARY?
      │
      ├── Yes → Write
      └── No  → Selection Wait / Failure
```

The application should not need to discover or track the primary itself.

## Read Preference Architecture

| Mode | Primary Eligible? | Secondary Eligible? | Basic Intent |
|---|---:|---:|---|
| `primary` | Yes | No | Read from primary |
| `primaryPreferred` | Preferred | Fallback | Prefer primary |
| `secondary` | No | Yes | Read from eligible secondaries |
| `secondaryPreferred` | Fallback | Preferred | Prefer eligible secondaries |
| `nearest` | Yes | Yes | Select among latency-eligible members |

This table describes basic member eligibility only. Depending on mode and configuration, the candidate set can be further restricted by `maxStalenessSeconds`, replica-set member tag sets, topology state, and latency-window rules.

A useful read-selection model is:

```text
Read Operation
      │
      ▼
Read Preference Mode
      │
      ▼
Staleness Eligibility
      │
      ▼
Tag Eligibility
      │
      ▼
Latency Window
      │
      ▼
Candidate Servers
      │
      ▼
Server Selection
```

Not every stage applies identically to every read-preference mode.

### `primary`

`primary` is the default read preference. If a suitable primary is unavailable, the operation does not simply fall back to a secondary. `primary` cannot be combined with secondary-selection features such as tag sets or `maxStalenessSeconds`.

### `primaryPreferred`

`primaryPreferred` first attempts to use the primary. If no primary is available, applicable staleness, tag, and latency rules determine eligible secondary candidates.

### `secondary`

`secondary` restricts reads to eligible secondary members. If no suitable secondary remains after applicable selection rules, the read cannot simply use the primary.

### `secondaryPreferred`

`secondaryPreferred` prefers eligible secondary members and can fall back to the primary when no suitable secondary is available. A secondary can exist but still be excluded because of staleness, tag requirements, topology state, or other applicable selection rules.

### `nearest`

`nearest` can select among eligible primary and secondary members according to latency-selection rules.

> **`nearest` refers to network-latency eligibility, not geographic distance.**

It does not directly measure MongoDB CPU utilization, disk latency, WiredTiger cache pressure, storage saturation, or workload intensity.

## Non-Primary Reads and Data Freshness

Replica-set secondaries apply replicated changes asynchronously.

> **Non-primary read preference is not simply a load-balancing choice. It changes the possible freshness characteristics of application reads.**

Detailed read preference and read concern semantics belong in Chapter 4.

## `maxStalenessSeconds`

`maxStalenessSeconds` can restrict secondary eligibility based on estimated replication staleness.

```text
Secondary Candidates
        │
        ▼
Estimated Staleness
        │
        ├── Within Limit → Eligible
        └── Too Stale    → Excluded
```

It can participate in secondary selection for applicable non-`primary` read-preference modes and cannot be used with `primary`. For the MongoDB 8.x baseline, the minimum permitted positive value is 90 seconds. Validate version- and driver-specific behavior when establishing production standards.

> **`maxStalenessSeconds` is an eligibility filter; it does not guarantee that a selected secondary contains the latest data available on the primary.**

## Replica-Set Member Tag Sets

Replica-set members can carry tags representing placement or operational characteristics, such as `region=east` or `workload=reporting`. Read preference can use tag requirements to narrow eligible candidates.

Tags can support regional, availability-zone, data-center, workload-placement, or application-specific read policies. Tag-based routing should be governed carefully because topology changes can alter which members satisfy a tag requirement.

## Latency-Aware Server Selection

After other eligibility rules are applied, network latency can participate in candidate selection. MongoDB does not simply require the driver to always choose the single server with the lowest observed latency.

### `localThresholdMS`

`localThresholdMS` defines the latency window used when identifying latency-eligible servers. For the MongoDB 8.x documented baseline, the value is 15 ms. Driver APIs and version-specific behavior should be validated against the deployed driver.

> **Latency-aware selection does not mean the driver always selects the single lowest-latency member. Network latency is not a direct measurement of database workload or server health.**

## Transactions and Server Selection

Transactions impose additional routing constraints. Transactions containing reads require `primary` read preference, and transaction operations remain associated with the appropriate selected member according to MongoDB transaction semantics.

> **Transactional server selection is more constrained than independent nontransactional read selection.**

Detailed transaction behavior belongs in Chapter 4.

## Elections and Client Failover

Before an election:

```text
mongo01 → PRIMARY
mongo02 → SECONDARY
mongo03 → SECONDARY
```

If the primary becomes unavailable, there can temporarily be no writable primary. After election, another member can become primary, and the driver learns the changed topology so subsequent server selection can use it.

```text
Primary Failure
      │
      ▼
Failure Detection
      │
      ▼
Election
      │
      ▼
New Primary
      │
      ▼
Driver Learns New Topology
      │
      ▼
Server Selection Recovers
```

During this interval, writes can fail or wait, server selection can temporarily find no primary, retryable operations can retry where eligible, applications can receive transient errors, and latency can increase.

> **Automatic failover reduces outage duration; it does not guarantee zero application interruption.**

There is no universal application-visible failover duration. It depends on topology, monitoring, election behavior, network conditions, driver behavior, retry configuration, and workload state.

## Topology Convergence Across Application Instances

Different application processes maintain independent driver topology views and can observe topology changes at slightly different moments.

> **Topology convergence occurs independently across client processes.**

A production incident should therefore be analyzed across the application fleet rather than from a single client process alone.

## Temporarily Out-of-Date Topology Views

During a topology transition, a driver can temporarily hold information that has not yet converged with the latest deployment state. SDAM monitoring and operation results help the topology view converge. Applications should rely on supported driver topology management instead of implementing static member-role mappings.

## Application-Visible Availability

Different clients can have different network visibility to the same replica set. A replica set can be healthy while an application cannot use the topology correctly.

> **Replica-set health and application-visible MongoDB availability are not the same measurement.**

## Member Discoverability

During topology discovery, a client learns member addresses from MongoDB. Initial seed reachability does not guarantee that those discovered addresses are resolvable and reachable from the client's network.

This is especially relevant with NAT, containers, Kubernetes, split DNS, VPNs, hybrid networks, private/public DNS, and cross-network connectivity.

> **Initial seed reachability does not guarantee topology-member reachability.**

Detailed DNS and connectivity engineering belongs in Section 1.12.

## SDAM vs. Connection Pools

Topology management and connection pooling solve different problems.

```text
SDAM
 │
 ▼
Runtime Topology
 │
 ▼
Server Selection
 │
 ▼
Selected Server
 │
 ▼
Connection Pool
 │
 ▼
Connection
 │
 ▼
Operation
```

> **Failure to find a suitable server and failure to obtain a connection from the selected server's pool are different failure classes.**

Connection-pool architecture is covered in Section 1.11.

## `serverSelectionTimeoutMS`

Server selection cannot wait indefinitely for a suitable target. `serverSelectionTimeoutMS` limits how long the driver waits while attempting to identify a suitable server. For the MongoDB 8.x documented baseline, the value is 30,000 ms. Driver-specific defaults and API behavior should be validated against the deployed driver/version.

> **A server-selection timeout means the driver could not identify a suitable server within the permitted selection period. It does not identify the underlying root cause.**

Increasing the timeout changes how long the application waits. It does not repair the condition preventing server selection.

Possible underlying causes include no primary, no eligible secondary, read-preference constraints, staleness constraints, tag constraints, wrong `replicaSet`, DNS or network failure, TLS failure, member discoverability problems, and topology transitions.

## Representative Failure Scenarios

### Seed Unavailable

If no usable seed is reachable, topology discovery cannot begin. Investigate seed configuration, DNS, routing, firewall, TLS, MongoDB listener/process health, and environment correctness.

### No Primary

A write can fail server selection during an active election, loss of voting majority, member failures, network partition, maintenance, application network isolation, or topology convergence. Do not automatically classify this as a driver failure.

### No Eligible Secondary

A strict `secondary` read preference can have no eligible target even when the primary is healthy. Staleness, tags, topology state, and other selection rules can remove secondaries from the candidate set.

### Wrong Replica-Set Identity

Network connectivity can succeed while topology establishment fails when the URI specifies the wrong replica-set identity.

### Members Discovered but Unreachable

A seed can be reachable while the member addresses learned through topology discovery are not reachable from the application network. Diagnose from the application's network location, not only from database hosts.

### Election Storm

Repeated elections can create write disruption, latency spikes, retry activity, topology churn, server-selection failures, and connection churn.

> **Repeated elections are a topology-stability problem; increasing client timeouts does not correct the underlying instability.**

### Retry Storm

A topology transition can trigger synchronized retries across an application fleet. Distinguish driver-supported retry behavior from application-level retry loops. Application retry policies should use appropriate bounded attempts, timeout budgets, backoff, jitter, and observability.

### Partial Network Partition

Different application instances can have different reachability to replica-set members and therefore experience different MongoDB availability at the same time. Centralized database health alone is insufficient to diagnose client-visible failures.

## Server-Selection Observability

Effective diagnosis requires evidence from multiple layers:

```text
Application
    │
    ▼
Driver / SDAM
    │
    ▼
DNS / Network / TLS
    │
    ▼
MongoDB Replica Set
    │
    ▼
OS / Container / Infrastructure
```

Useful evidence includes application timestamps and errors, affected operations, read preference, retry behavior, driver/version, topology or SDAM events where supported, server-selection errors, sanitized configuration, DNS results, endpoint reachability, TLS errors, replica-set state, election events, MongoDB logs, replication condition, and infrastructure events.

Never collect plaintext credentials or complete credential-bearing URIs as routine troubleshooting evidence.

## Server-Selection Governance

Production standards should define supported MongoDB drivers and versions, approved connection architecture, seed/SRV configuration, expected replica-set identity, read-preference policy, tag policy, `maxStalenessSeconds` policy, latency-selection policy, `serverSelectionTimeoutMS` policy, retry policy, DNS/network ownership, topology observability, failover testing, application-side monitoring, and escalation responsibilities.

> **Read preference should be treated as an application consistency and workload-design decision—not merely as a performance switch.**

## Replica-Set Discovery and Selection Anti-Patterns

Avoid hard-coding a permanently assumed primary, implementing custom primary-discovery logic, relying on one fragile seed without justification, bypassing replica-set discovery, using `directConnection=true` to hide topology problems, assuming seed reachability means every member is reachable, advertising client-unreachable member hostnames, ignoring SDAM/server-selection errors, treating selection timeout as proof MongoDB is down, increasing `serverSelectionTimeoutMS` without root-cause analysis, assuming a healthy primary satisfies every read preference, using secondary reads without understanding freshness, using tag policies without validating failover, treating `maxStalenessSeconds` as a freshness guarantee, interpreting `nearest` as geographic proximity, assuming lowest latency means lowest server load, treating elections as zero-impact events, allowing uncontrolled retry storms, diagnosing connectivity only from the database network, ignoring driver versions, or restarting MongoDB before preserving topology/network evidence.

## DBA Replica-Set Discovery Checklist

Before approving production replica-set client connectivity, verify:

- replica-set identity is correct;
- seed/SRV discovery is resilient;
- `directConnection` is not unintentionally enabled;
- advertised member names resolve from application networks;
- required members are network-reachable;
- TLS succeeds to discovered endpoints;
- supported driver/version is documented;
- primary and secondary discovery works;
- read preference is intentional;
- non-primary read freshness implications are understood;
- tag and staleness requirements are intentional where configured;
- latency-selection and selection-timeout policy are understood;
- retry behavior is bounded and observable;
- failover behavior has been tested;
- client-side SDAM/selection telemetry is available where supported;
- network/DNS ownership is documented; and
- escalation ownership is defined.

13. `nearest` refers to latency eligibility rather than geography.
14. Network latency is not equivalent to server workload or health.
