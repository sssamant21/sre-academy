# 1.12 — DNS and Connectivity Considerations

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 1:** MongoDB Architecture and Internals  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to:

- explain MongoDB's end-to-end connectivity architecture;
- distinguish `mongodb://` from `mongodb+srv://` discovery;
- understand DNS SRV and TXT behavior;
- explain the relationship among DNS identity, MongoDB topology identity, and TLS identity;
- distinguish seed-host reachability from deployment reachability;
- understand client-to-member and member-to-member connectivity requirements;
- recognize DNS caching and runtime-convergence problems;
- distinguish DNS, routing, TCP, TLS, authentication, topology, server-selection, pool, and operation failures;
- understand self-managed, Atlas, private-network, and Kubernetes connectivity considerations;
- troubleshoot connectivity from the actual failing client context; and
- design production connectivity monitoring and governance.

## 1. MongoDB Connectivity Architecture

MongoDB connectivity is a layered process rather than a single network connection.

```text
Connection String
      ↓
DNS
      ↓
Network Route
      ↓
TCP
      ↓
TLS
      ↓
MongoDB Protocol
      ↓
Authentication
      ↓
Topology Discovery
      ↓
Server Selection
      ↓
Pool Checkout
      ↓
MongoDB Operation
```

Every layer represents a separate potential failure domain. Successful DNS resolution does not prove that a route exists, TCP is reachable, TLS succeeds, authentication succeeds, the topology is usable, a suitable server exists, a pool connection is available, or the requested database operation will succeed.

> **"Cannot connect to MongoDB" is a symptom description, not a root-cause diagnosis.**

## 2. Client and Replica-Set Connectivity

Production connectivity requires both appropriate client-to-member reachability and healthy member-to-member communication.

```text
Client → Required MongoDB Members

             AND

MongoDB Member ↔ MongoDB Member
```

A client reaching one member does not prove replica-set communication is healthy, and healthy replication does not prove application networks can reach the required members.

## 3. Standard vs. SRV Connection Discovery

| Characteristic | `mongodb://` | `mongodb+srv://` |
|---|---|---|
| Initial discovery | URI seed hosts | DNS SRV |
| Hostname resolution | Standard DNS | SRV plus hostname resolution |
| DNS TXT integration | No SRV TXT discovery | Supported |
| TLS default | URI/driver configuration | Enabled by default unless overridden |
| Topology discovery | MongoDB driver | MongoDB driver |
| Server selection | MongoDB driver | MongoDB driver |

A standard replica-set URI commonly supplies multiple seed hosts. The driver uses them to discover the runtime topology; the seed list is not a permanent routing table.

An SRV URI such as `mongodb+srv://cluster.example.com/` uses DNS service discovery to obtain seed targets. SRV discovery can allow seed information to evolve through DNS, but successful SRV lookup does not prove end-to-end MongoDB connectivity.

## 4. SRV, TXT, and TLS

`mongodb+srv://` enables TLS by default unless explicitly overridden. This creates a close operational relationship among SRV discovery, DNS host identity, and TLS certificate identity.

MongoDB DNS seed-list discovery can also use a TXT record for supported configuration. Current supported TXT options include `replicaSet` and `authSource`. TXT records are not general-purpose storage for arbitrary MongoDB URI options. The documented mechanism expects a single TXT record; unsupported options can cause connection errors, and URI query parameters can override TXT-supplied settings where defined.

An SRV record existing is not sufficient evidence of valid MongoDB SRV discovery. Drivers apply validation requirements to discovered targets, and each accepted target must still resolve and be reachable.

## 5. DNS as a Database Dependency

DNS is part of application-visible database availability. MongoDB can be healthy while applications cannot use it because DNS is unavailable, stale, scoped incorrectly, or returning unreachable addresses.

> **Database health and application-visible database availability are different measurements.**

This applies to self-managed MongoDB, Atlas, VMs, Kubernetes, private endpoints, hybrid networks, and multi-region deployments.

## 6. MongoDB Hostname and Topology Identity

A MongoDB hostname can participate in DNS resolution, network reachability, replica-set identity, member-to-member communication, client topology discovery, and TLS identity.

Configured member identities should be resolvable and reachable by the required MongoDB members and meaningful to the required client network contexts. They must also align with the deployment's TLS identity model.

### Seed Reachability vs. Deployment Reachability

> **Seed reachability does not prove that every required discovered member is reachable.**

A client may successfully contact a seed and then discover member names that it cannot resolve or route to. This is common in Kubernetes, NAT, VPN, hybrid-cloud, private-DNS, and split-view DNS architectures.

### Member-to-Member Connectivity

Replica-set members must also resolve and communicate with one another. Problems can arise from member hostname resolution, routing, firewalls, TLS, certificate identity, replica-set configuration, or network partitions.

## 7. Prefer Stable DNS Hostnames

Production replica-set and sharded-cluster member identities should use stable, resolvable DNS hostnames rather than depending on raw IP addresses. MongoDB 5.0 and later perform additional startup validation associated with split-horizon DNS and IP-only member configurations.

Stable DNS identity is operationally preferable because addresses can change during node replacement, infrastructure migration, cloud recovery, Kubernetes rescheduling, and network redesign.

## 8. Split-View DNS and MongoDB Validation

DNS split-view means different network contexts can receive different answers for the same hostname. This can be intentional, but MongoDB separately applies requirements to configured topology member identities. DNS split-view and MongoDB split-horizon/topology validation interact but are not the same mechanism.

The important troubleshooting question is not merely, "What IP does this hostname resolve to?" It is:

> **What address does this hostname resolve to from the failing application environment?**

## 9. DNS Resolution, Search Domains, and Caching

Resolution can fail because of missing records, unavailable resolvers, incorrect zones, private-zone association, search-domain behavior, stale caches, incorrect A/AAAA data, or forwarding problems.

Short names can depend on environment-specific search domains and may resolve differently from pods, VMs, bastions, and developer workstations. Production topology identity should not accidentally depend on a local search path unavailable elsewhere.

DNS responses can be cached by the application/runtime, operating system, local resolver, and DNS infrastructure. Refresh behavior can depend on the driver, runtime, OS, resolver, URI type, DNS TTL, and infrastructure. Do not assume every client refreshes DNS identically.

## 10. DNS Changes and Runtime Convergence

A DNS change creates a convergence process:

```text
DNS Change
    ↓
Resolver / Runtime Cache
    ↓
Driver DNS Refresh
    ↓
Topology Discovery
    ↓
Connection / Pool Convergence
```

Changing DNS does not guarantee every running application immediately uses the new destination. This matters during migration, failover, endpoint replacement, private-endpoint changes, Kubernetes replacement, and disaster recovery.

Migration plans should consider TTL, driver/runtime behavior, existing pooled connections, connection draining, validation, rollback, and convergence time. Some environments may require client or connection recycling; validate actual behavior rather than assuming a restart is universally required.

> **DNS cutover is not necessarily instantaneous application cutover.**

## 11. Network Routing and TCP

After DNS resolution, the client still requires a valid route through the applicable security controls to a MongoDB listener.

Potential failure points include subnets, VPC/VNet routing, peering, transit routing, VPNs, overlapping address space, security groups, NSGs, ACLs, host firewalls, Kubernetes NetworkPolicy, and regional network failures.

TCP port `27017` is the common/default MongoDB server port for standard self-managed connectivity when another port is not configured. It is not universal. In particular, do not assume port 27017 for Atlas private-endpoint connectivity; use Atlas-generated connection information.

A successful ping does not prove MongoDB TCP reachability, and successful TCP reachability does not prove TLS, authentication, topology, or operation success.

## 12. Listener Architecture and `net.bindIp`

A MongoDB process can be running while listening only on an interface unavailable to the application.

```text
Process Running
      ≠
Listening Correctly
      ≠
Reachable from Client
```

`net.bindIp` controls relevant self-managed listener behavior. Do not solve listener problems by broadly exposing `mongod` or `mongos`. Listener scope, authentication, TLS, and network access controls must be engineered together.

## 13. IPv4 and IPv6

DNS can return A records for IPv4 and AAAA records for IPv6. A hostname can resolve successfully while the selected address family lacks a working route or security path.

Self-managed IPv6 operation also requires appropriate MongoDB configuration, including `net.ipv6: true` where applicable. An AAAA record alone does not prove end-to-end IPv6 readiness.

## 14. Firewalls and Network Security

Production access can traverse routing, cloud security groups or NSGs, ACLs, host firewalls, NetworkPolicy, and other controls before reaching the MongoDB listener.

Connectivity remediation should not require unrestricted public exposure, unnecessarily broad CIDR rules, disabled authentication, or removal of segmentation.

> **Reachable does not mean secure.**

## 15. TLS Connectivity and Hostname Validation

TCP can succeed while TLS fails because of certificate expiration, untrusted CA, incomplete chains, hostname mismatch, client-certificate problems, TLS configuration mismatch, or interception/proxy behavior.

The correct production relationship is:

```text
DNS Identity
     ↕
Connection Hostname
     ↕
Certificate Identity
```

Replacing a hostname with a raw IP to bypass DNS can create certificate mismatch, brittle topology configuration, and failover problems.

Options such as `tlsAllowInvalidHostnames`, `tlsInsecure`, or equivalent controls should not be used as routine production fixes. Repair DNS, hostname configuration, certificate identity, trust, or the connectivity architecture instead.

## 16. Authentication, Topology, and Pool Boundaries

A client can complete DNS, TCP, TLS, and the MongoDB protocol handshake and still fail authentication. Authentication failure is therefore a separate diagnostic domain.

Likewise, transport connectivity can succeed while topology discovery or server selection fails because of no primary, unreachable members, a wrong replica-set name, read-preference constraints, or topology transitions. Section 1.10 remains authoritative for server-selection architecture.

Even after a suitable server is selected, pool checkout can wait or fail. Section 1.11 remains authoritative for connection pools and timeout architecture.

```text
DNS Failure
    ≠
Network Failure
    ≠
TLS Failure
    ≠
Authentication Failure
    ≠
Server Selection Failure
    ≠
Pool Checkout Failure
```

Do not use `directConnection=true` as a generic workaround for broken replica-set DNS or topology discovery. Use direct connectivity only when the intended deployment or diagnostic scenario specifically requires it.

## 17. Private Connectivity

A representative private path is:

```text
Application Network
       ↓
Private DNS
       ↓
Private Routing
       ↓
Private Endpoint / Peering / Private Path
       ↓
MongoDB
```

Private connectivity can improve segmentation and reduce public exposure, but it introduces dependencies on private DNS, routing, peering, private endpoints, VPN/transit architecture, security controls, and provider infrastructure.

> **Private connectivity is a dependency chain, not merely an endpoint object.**

## 18. NAT and Proxy Considerations

NAT can create different address views and can conflict with topology-aware addressing when the seed address differs from the topology identity. Potential issues include unreachable discovered members, TLS hostname mismatch, return-path problems, connection tracking limits, and idle connection behavior.

Do not introduce an application-managed generic proxy or load balancer in front of a topology-aware MongoDB deployment unless the architecture is explicitly supported and validated. Managed MongoDB services can use provider-managed load-balancing mechanisms as part of their supported architecture; these are different from arbitrary application-managed intermediaries.

## 19. Kubernetes Connectivity

A representative self-managed/operator-managed Kubernetes pattern is:

```text
Application Pod
      ↓
Cluster DNS
      ↓
Service / Headless Service
      ↓
MongoDB Pod
```

Exact architecture varies. Stateful deployments can provide stable DNS identities while underlying pod IPs change.

> **Topology-aware MongoDB deployments should rely on stable, resolvable identities rather than ephemeral pod IP addresses.**

DNS can also succeed while NetworkPolicy blocks application traffic. Connectivity should therefore be tested from the same network and runtime context as the failing application whenever possible.

## 20. MongoDB Atlas Connectivity

Atlas connectivity can depend on DNS, SRV discovery, TLS, network access controls, public connectivity, peering, private endpoints, cloud routing, and provider DNS.

> **Use the Atlas-generated connection string appropriate to the configured connectivity method rather than constructing hostnames or ports manually.**

Atlas private endpoints can use provider-specific DNS and port architectures. Multi-region private connectivity can require endpoint coverage appropriate to each region used by the cluster. Detailed cloud implementation belongs in Book 4.

## 21. Connectivity Health Checks

Validate progressively:

```text
1. Connection String
        ↓
2. DNS
        ↓
3. Address / Route
        ↓
4. TCP
        ↓
5. TLS
        ↓
6. MongoDB Protocol
        ↓
7. Authentication
        ↓
8. Topology Discovery
        ↓
9. Server Selection
        ↓
10. Pool Checkout
        ↓
11. MongoDB Operation
```

For replica sets and sharded deployments, also validate member-to-member communication. A client-only test is not a complete database-network health check.

## 22. Representative Failure Patterns

### DNS Failure

DNS lookup fails because of a missing record, resolver outage, wrong zone, private-DNS issue, Kubernetes DNS problem, or stale/incorrect configuration. Do not restart MongoDB first.

### Network Failure

DNS succeeds but route or TCP fails. Investigate routing, firewall, security groups/NSGs, ACLs, NetworkPolicy, VPN, peering, private endpoints, and listener configuration.

### TLS Failure

DNS and TCP succeed but TLS fails. Investigate certificate identity, expiration, CA trust, chain, TLS configuration, and client-certificate requirements.

### Authentication Failure

Transport succeeds but authentication fails. Treat this as an authentication domain until evidence identifies another layer.

### Topology Failure

A seed is reachable but required discovered members are not. Investigate discovered hostnames, DNS scope, routing, firewall, TLS identity, and replica-set configuration.

### Runtime Convergence Failure

After a DNS change, some clients reach the new destination while others remain on old information. Investigate TTL, runtime caching, driver behavior, existing pools, and application configuration/version differences.

## 23. Test from the Failing Client Context

A common misleading result is:

```text
DBA Bastion → MongoDB ✓
Application Pod → MongoDB ✗
```

The bastion result proves only that the bastion path works. DNS resolver, source subnet, security rules, routing, NetworkPolicy, TLS trust, connection string, driver, and source IP can all differ.

> **Test from the failing client context.**

## 24. Troubleshooting Workflow

Use the following sequence:

```text
MongoDB Connectivity Failure
          ↓
Connection String Correct?
          ↓
DNS Resolution Correct?
          ↓
Correct Address Returned?
          ↓
Route Exists?
          ↓
TCP Reachable?
          ↓
TLS Successful?
          ↓
MongoDB Handshake?
          ↓
Authentication Successful?
          ↓
Topology Discovered?
          ↓
Suitable Server Selected?
          ↓
Pool Checkout Successful?
          ↓
Operation Successful?
```

> **Stop at the first failed layer and investigate that failure domain before changing downstream configuration.**

For replica sets, also ask whether member-to-member connectivity and replica-set health are intact.

## 25. Evidence Collection

Before restarting services or changing multiple layers, collect:

### Application / Driver

- complete error and timestamp;
- affected instance or pod;
- driver/version;
- sanitized URI structure;
- standard vs. SRV mode;
- timeout/deadline that fired;
- recent deployment/configuration changes.

### DNS

- resolver;
- A/AAAA results;
- SRV results;
- TXT results where applicable;
- TTL;
- working vs. failing client results;
- public/private DNS scope.

### Network

- source address/network;
- destination address;
- route;
- port;
- firewall/security controls;
- NetworkPolicy;
- VPN/peering/private-endpoint state.

### TLS

- certificate identities;
- issuer;
- validity period;
- chain;
- trust configuration;
- exact TLS error.

### MongoDB

- listener configuration;
- replica-set member identities;
- replica-set state;
- logs;
- connection metrics;
- authentication errors;
- topology errors.

Correlate evidence by timestamp.

## 26. Production Monitoring

Monitor both MongoDB and connectivity dependencies. Useful signals include DNS lookup failures and latency, resolver/private-zone health, connection failures, network latency and packet loss, VPN/peering/private-endpoint health, certificate expiration and handshake failures, MongoDB connection counts, topology state, elections, replication health, server-selection errors, pool failures, and application connectivity errors.

## 27. Production Connectivity Matrix

Maintain a connectivity inventory such as:

| Source | Destination | URI Type | DNS Scope | Port | TLS | Topology | Owner |
|---|---|---|---|---:|---|---|---|
| API Pods | MongoDB Prod | SRV | Private | Generated/configured | Required | Replica Set | Platform |
| Batch Workers | MongoDB Prod | Standard/SRV | Private | Configured | Required | Replica Set | Data |
| DBA Bastion | MongoDB Prod | Standard/SRV | Private | Configured | Required | Replica Set | DBA |

Useful additional fields include driver/version, source and destination networks, DNS zone/resolver, private-endpoint identifier, firewall owner, certificate owner, replica-set name, connection-string owner, last validation, and escalation path.

## 28. Governance

Production standards should define hostname strategy, URI type, DNS and SRV/TXT ownership, public/private DNS policy, replica-set naming, DNS change procedures, private connectivity, network access policy, TLS/certificate ownership, certificate rotation, IPv4/IPv6 policy, Kubernetes DNS/service design, Atlas connectivity method, proxy/load-balancer policy, migration/cutover validation, monitoring, and escalation ownership.

Connectivity remediation must preserve authentication, TLS validation, least-privilege network access, and topology correctness.

## 29. Anti-Patterns

Avoid:

- assuming DNS success proves MongoDB connectivity;
- assuming TCP success proves TLS/authentication success;
- assuming seed reachability proves deployment reachability;
- configuring topology identities required peers or clients cannot resolve/use;
- depending on raw IPs where stable DNS identity is appropriate;
- hard-coding the current primary;
- using `directConnection=true` to hide broken topology design;
- treating TXT records as arbitrary configuration storage;
- ignoring SRV validation or DNS caching;
- assuming DNS changes immediately affect all clients;
- testing only from a bastion or wrong network context;
- assuming ping proves MongoDB availability;
- assuming port 27017 applies to every architecture;
- broadly exposing `mongod`/`mongos` to fix listener problems;
- disabling TLS hostname/certificate validation to fix DNS;
- ignoring IPv6 or NetworkPolicy;
- treating authentication errors as generic network failures;
- inserting unsupported generic proxies/load balancers;
- manually constructing Atlas private-endpoint hostnames/ports;
- restarting MongoDB before collecting evidence; or
- changing multiple connectivity layers simultaneously during RCA.

## 30. DBA Production Checklist

Before approving production connectivity, verify:

- [ ] URI type is intentional.
- [ ] Production hostnames are stable and resolvable.
- [ ] DNS ownership is documented.
- [ ] SRV/TXT configuration is validated where applicable.
- [ ] `mongodb+srv://` TLS behavior is understood.
- [ ] Required discovered member identities resolve appropriately.
- [ ] Member-to-member connectivity is validated.
- [ ] Client-to-required-member connectivity is validated.
- [ ] Routes and listener configuration are correct.
- [ ] Firewall/security controls are documented.
- [ ] NetworkPolicy is validated where applicable.
- [ ] Private endpoint/peering/VPN dependencies are documented.
- [ ] Atlas-generated connectivity information is used where applicable.
- [ ] TLS hostname validation succeeds.
- [ ] Insecure TLS bypasses are not normal remediation.
- [ ] Certificate expiration/rotation is monitored.
- [ ] IPv4/IPv6 behavior is understood.
- [ ] DNS caching/convergence behavior is considered.
- [ ] Migration/failover DNS behavior is tested.
- [ ] Connectivity is tested from actual application contexts.
- [ ] Topology discovery and server selection succeed.
- [ ] Connection-pool behavior is healthy.
- [ ] Connectivity monitoring and escalation ownership exist.

## 31. Key DBA Takeaways

1. MongoDB connectivity is layered, not a single socket test.
2. DNS is part of application-visible database availability.
3. `mongodb://` and `mongodb+srv://` use different initial discovery mechanisms.
4. `mongodb+srv://` enables TLS by default unless explicitly overridden.
5. SRV provides seed discovery; it does not replace topology discovery.
6. TXT records support defined DNS seed-list options rather than arbitrary configuration.
7. SRV existence does not guarantee driver acceptance or reachability.
8. DNS success does not prove routing or TCP connectivity.
9. Seed reachability does not prove deployment reachability.
10. Topology identities must align with DNS and network architecture.
11. Replica-set health requires member-to-member communication.
12. Prefer stable, resolvable hostnames over IP-only topology identities.
13. DNS split-view and MongoDB topology validation are related but distinct.
14. DNS answers and caching behavior can differ by client environment.
15. Test connectivity from the actual failing client context.
16. DNS cutover is not necessarily instantaneous application cutover.
17. TCP 27017 is common but not universal.
18. A running MongoDB process does not prove correct listener reachability.
19. IPv6 requires complete DNS, MongoDB, routing, and security support.
20. DNS identity and TLS certificate identity must align.
21. Disabling certificate validation is not a normal connectivity fix.
22. Authentication, server selection, and pool checkout are distinct failure domains.
23. Private connectivity is a chain of DNS, routing, endpoints, and security dependencies.
24. NAT and generic proxies can conflict with topology-aware addressing.
25. Kubernetes should use stable topology identities rather than ephemeral pod IPs.
26. Atlas private connectivity should use Atlas-generated connection information.
27. Managed MongoDB does not eliminate application DNS/network dependencies.
28. Validate connectivity progressively through a real MongoDB operation.
29. Validate both client connectivity and member-to-member communication.
30. Preserve evidence before restarts or broad configuration changes.
