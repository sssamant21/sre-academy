# 1.13 — MongoDB Memory Architecture

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 1:** MongoDB Architecture and Internals  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to:

- explain MongoDB's end-to-end memory architecture;
- distinguish WiredTiger cache from total `mongod` memory;
- explain the relationship between WiredTiger cache and the operating-system filesystem cache;
- understand MongoDB's default WiredTiger cache-sizing model;
- distinguish resident memory, virtual memory, allocator memory, and actual system pressure;
- understand working-set behavior;
- recognize WiredTiger cache pressure, eviction, and dirty-cache behavior;
- understand memory consumed outside WiredTiger by queries, aggregations, index builds, connections, transactions, and replication;
- understand MongoDB 8.x TCMalloc considerations;
- evaluate swap and OOM conditions correctly;
- understand container/cgroup and Kubernetes memory boundaries;
- recognize memory effects during restart, failover, recovery, and cache warming;
- monitor MongoDB memory across database, operating-system, container, storage, and workload layers; and
- troubleshoot memory incidents using a production-safe workflow.

## 1. MongoDB Memory Architecture

MongoDB memory is a layered architecture.

```text
Physical / Effective Memory Boundary
          │
          ├── MongoDB Process
          │      │
          │      ├── WiredTiger Cache
          │      ├── Query / Aggregation Memory
          │      ├── Index-Build Memory
          │      ├── Connections / Sessions
          │      ├── Transactions
          │      ├── Replication / Recovery
          │      ├── TCMalloc / Allocator
          │      └── Other Process Memory
          │
          ├── OS / Filesystem Cache
          ├── Kernel / Runtime Memory
          ├── Other Required Processes
          └── Safety Headroom
```

The first principle of MongoDB memory administration is therefore:

> **WiredTiger cache is not MongoDB's total memory consumption.**

A healthy memory assessment must consider the MongoDB process, WiredTiger, allocator, operating system, filesystem cache, container/cgroup boundary, storage behavior, and workload together.

## 2. WiredTiger Internal Cache

WiredTiger maintains an internal cache used by MongoDB for actively accessed database content and storage-engine operations.

```text
MongoDB Operations
        │
        ▼
WiredTiger
        │
        ▼
Internal Cache
        │
        ├── Data
        ├── Indexes
        ├── Dirty Content
        └── Internal Structures
```

MongoDB automatically calculates a default cache size unless administrators explicitly override it.

For the reviewed MongoDB 8.x baseline, the default WiredTiger cache is approximately the larger of:

```text
50% × (RAM - 1 GB)

or

0.256 GB
```

Conceptually:

```text
Default WiredTiger Cache
=
max(
    50% × (RAM - 1 GB),
    0.256 GB
)
```

For example, with approximately 16 GB of effective memory:

```text
50% × (16 GB - 1 GB)
=
7.5 GB
```

The precise effective memory MongoDB detects is especially important in containerized environments.

## 3. Why WiredTiger Does Not Consume All RAM

The default sizing deliberately leaves memory outside the internal cache.

```text
Effective Memory
      │
      ├── WiredTiger Internal Cache
      ├── MongoDB Non-Cache Memory
      ├── OS / Filesystem Cache
      ├── Kernel / Runtime
      └── Safety Headroom
```

MongoDB needs memory outside WiredTiger for queries, connections, index builds, replication, transactions, runtime structures, allocator behavior, and other operations.

The operating system also benefits from memory for filesystem caching.

> **Do not increase the WiredTiger cache merely because host memory appears available.**

An oversized internal cache can reduce memory available to other MongoDB and operating-system consumers. Cache overrides should be treated as production configuration changes requiring evidence, capacity analysis, monitoring, and rollback planning.

## 4. WiredTiger and the Filesystem Cache

MongoDB benefits from two important caching layers:

```text
MongoDB
   │
   ▼
WiredTiger Internal Cache
   │
   ▼
Filesystem
   │
   ▼
Operating-System Filesystem Cache
   │
   ▼
Storage
```

WiredTiger manages its own internal cache while the operating system can use otherwise available memory for filesystem caching.

These caches do not represent identical copies with identical purposes. WiredTiger's internal representation and the filesystem's on-disk representation can differ. The filesystem cache also benefits from the storage representation and compression used by WiredTiger.

Consequently:

```text
Compressed Disk Size
        ≠
Required WiredTiger Cache
        ≠
Total MongoDB RAM
```

A collection occupying 500 GB on storage does not automatically require 500 GB of physical RAM.

## 5. MongoDB Memory Outside WiredTiger

The `mongod` process requires memory beyond the internal cache.

Representative consumers include queries, aggregation pipelines, sorts, index builds, connections, sessions, transactions, replication, recovery operations, compression/decompression, metadata, diagnostics, networking, TLS, allocator structures, and other runtime structures.

Therefore:

```text
mongod RSS
    ≠
WiredTiger Cache Bytes
```

This distinction is critical when investigating apparently unexplained MongoDB process growth.

## 6. MongoDB 8.x Memory Allocator and TCMalloc

MongoDB uses TCMalloc for process memory allocation. MongoDB 8.0 includes an updated TCMalloc implementation intended to improve memory-management behavior.

```text
mongod
  │
  ▼
TCMalloc / Memory Allocator
  │
  ├── WiredTiger-Related Allocations
  ├── Query / Runtime Allocations
  ├── Connections
  ├── Metadata
  └── Other Process Allocations
```

Allocator behavior is another reason that process RSS should not be interpreted as WiredTiger cache usage. MongoDB 8.x exposes allocator information through `serverStatus`, including TCMalloc-related statistics.

Deep allocator internals belong in the DBRE and performance material rather than Chapter 1.

## 7. Resident and Virtual Memory

MongoDB exposes process memory information including resident and virtual memory.

```text
Resident Memory
=
Process pages currently resident in physical memory
```

whereas:

```text
Virtual Memory
=
Process virtual address space
```

Therefore:

```text
Virtual Memory ≠ Physical RAM Consumption
Resident Memory ≠ Complete System Memory Pressure
```

A large virtual-memory value should not by itself be classified as a memory leak. Likewise, high resident memory can be normal on a dedicated database host.

## 8. Utilization vs. Memory Pressure

A host can show very high memory utilization and remain healthy.

```text
Memory Used: High
Available/Reclaimable Memory: Healthy
Swap Activity: Minimal
WiredTiger: Healthy
Storage Latency: Normal
Application Latency: Normal
```

This is fundamentally different from:

```text
Available Memory ↓
        +
Swap / Reclaim ↑
        +
WiredTiger Pressure ↑
        +
Storage I/O ↑
        +
Latency ↑
        +
OOM / Cgroup Events
```

> **High memory utilization is not automatically memory pressure.**

Alerting and troubleshooting should identify pressure and impact rather than simply a large used-memory percentage.

## 9. MongoDB Working Set

The operational working set is the data and indexes frequently required by the active workload.

```text
Total Database
──────────────────────────────────────

Frequently Accessed Data + Indexes
──────── Operational Working Set ─────
```

The working set depends on query patterns, index design, read/write mix, access locality, collection size, document size, index footprint, aggregation patterns, concurrency, and workload changes.

The working set should be treated as a workload/capacity concept rather than one single authoritative MongoDB metric.

> **The entire MongoDB database does not necessarily need to fit in RAM.**

What matters is whether available memory and storage performance can support the active workload.

## 10. Data and Index Memory Demand

Both data and indexes participate in workload memory demand.

```text
WiredTiger Cache
      │
      ├── Data
      ├── Indexes
      ├── Dirty Content
      └── Internal Structures
```

Poor indexing can increase memory and storage pressure because queries may examine substantially more data than necessary. Excessive indexes also consume cache, storage, write I/O, maintenance resources, and index-build resources.

Memory engineering and index engineering are therefore closely related.

## 11. Cache Pressure, Eviction, and Dirty Content

```text
Workload
   │
   ▼
WiredTiger Cache
   │
   ├── Clean Content
   └── Dirty Content
           │
           ▼
Eviction / Reconciliation
           │
           ▼
Storage
```

Eviction is a normal part of WiredTiger operation.

```text
Eviction Exists ≠ Incident
Cache Near Capacity ≠ Cache Pressure
```

The important question is whether WiredTiger can maintain healthy cache turnover while preserving acceptable application performance.

Evidence of problematic pressure can include correlated increases in eviction activity, pages read into cache, disk I/O, storage latency, dirty-cache pressure, query latency, and application response time.

## 12. Dirty Cache and Write Workloads

Writes create dirty content that must eventually be reconciled with persistent storage.

```text
Writes
  │
  ▼
Dirty Cache Content
  │
  ▼
Reconciliation / Checkpoint Activity
  │
  ▼
Storage
```

Write-heavy workloads can therefore create a different memory profile from read-heavy workloads. Useful evidence includes dirty bytes, total cache bytes, eviction, checkpoint activity, write throughput, storage latency, and long-running transactions.

Detailed eviction and reconciliation internals belong in later storage-engine material.

## 13. Query and Aggregation Execution Memory

Database operations consume memory outside the WiredTiger cache. Representative consumers include query execution state, cursor state, sorting, grouping, aggregation intermediate state, window calculations, lookup processing, and result processing.

The important production relationship is:

```text
Memory per Operation
        ×
Concurrent Operations
        =
Potential Aggregate Memory Demand
```

A query that is inexpensive when executed once can become significant when hundreds of copies execute concurrently.

## 14. Aggregation Memory and Disk Spill

Beginning with MongoDB 6.0, `allowDiskUseByDefault` controls whether aggregation pipeline stages that exceed the applicable 100 MB in-memory threshold may write temporary files to disk by default or instead raise an error, subject to stage-specific behavior and command-level overrides.

Representative memory-intensive stages can include `$group`, `$sort` when an index cannot provide the required ordering, `$setWindowFields`, `$bucket`, `$bucketAuto`, and `$sortByCount`.

```text
Aggregation Memory Pressure
          │
          ▼
Temporary Disk Spill
          │
          ▼
Additional Storage I/O
          │
          ▼
Potential Latency Impact
```

A memory-management mechanism can therefore become a storage-performance issue.

`$search` is an important exception to the same aggregation-stage memory restriction because its execution architecture uses a separate process. Detailed aggregation optimization belongs in Chapter 7.

## 15. Index-Build Memory

Index builds consume resources outside ordinary WiredTiger cache usage.

For the reviewed MongoDB 8.x baseline, the default index-build memory budget is approximately:

```text
200 MB per createIndexes command
```

When one `createIndexes` command creates multiple indexes, those indexes share the command's applicable memory budget. If required, index-building work can use temporary disk files.

> **Index-build memory is separate from the WiredTiger cache.**

```text
WiredTiger Cache
       +
Index-Build Memory
       +
Other Process Memory
       =
Combined Process Demand
```

Concurrent index-build activity can further increase demand:

```text
Concurrent createIndexes Commands
             ×
Per-Command Memory Budget
             =
Potential Additional Memory Demand
```

Increasing index-build memory without considering concurrency can contribute to process or host memory exhaustion. Production index creation should therefore be treated as a capacity event.

## 16. Connection Memory

Connections consume server resources beyond the WiredTiger cache, including process memory, file descriptors, TLS state, network buffers, authentication/session state, and execution resources.

```text
More Application Instances
          ↓
More MongoClient Pools
          ↓
More MongoDB Connections
          ↓
Additional Server Resource Demand
```

> **Application autoscaling can become a MongoDB memory-capacity event.**

Detailed pool architecture remains in **1.11 — Connection Pools and Timeout Architecture**.

## 17. Transactions, Replication, and Recovery

Long-running transactions and replication/recovery workloads can retain or create additional database state and resource demand. Representative workloads include transactions, oplog processing, replication catch-up, initial synchronization, rollback, recovery, and member state transitions.

> **Recovery itself can be a resource-intensive workload.**

A recovered node should not be considered capacity-neutral merely because it is returning to service.

## 18. Memory and Storage Are Coupled

When useful data cannot be served effectively from memory, storage interaction can increase.

```text
Effective Cache Misses ↑
        │
Storage Reads ↑
        │
Storage Latency ↑
        │
Query Latency ↑
```

Fast storage reduces the penalty associated with cache misses. It does not eliminate memory requirements. Likewise, increasing memory can reduce storage pressure but cannot repair poor storage architecture, inefficient queries, or inappropriate indexes.

## 19. Swap

MongoDB generally performs best when active database memory is not repeatedly swapped. However, production swap policy requires more nuance than simply disabling swap.

Two controlled strategies can be appropriate for self-managed Linux deployments:

1. retain swap while configuring the system to avoid using it aggressively; or
2. operate without swap when capacity engineering and operational requirements intentionally support that model.

Swap can sometimes provide protection against immediate OOM termination, particularly when memory demand temporarily exceeds physical RAM. For shared hosts running other software, retaining controlled swap can also be operationally important.

Current MongoDB production guidance discusses low `vm.swappiness` settings such as `1` or, depending on the intended architecture, `0`. These should not be treated as universal values independent of OS version, cgroup behavior, and deployment architecture.

Detailed Linux tuning belongs in Chapter 2.

## 20. Out-of-Memory Conditions

```text
Memory Demand
      │
      ▼
Effective Memory Exhausted
      │
      ▼
OS / Cgroup Enforcement
      │
      ▼
Process Termination
```

On Linux this can involve the OOM killer. In a container, the process can be terminated because the container exceeds its cgroup memory limit.

Most importantly:

```text
OOM = Failure Mechanism / Outcome
OOM ≠ Root Cause
```

Possible underlying causes include undersized infrastructure, inappropriate cache configuration, workload growth, connection storms, expensive concurrent aggregations, index builds, retry storms, maintenance activity, colocated workloads, configuration mistakes, or unexplained process/allocator growth.

An RCA that ends with "MongoDB was OOMKilled" is incomplete.

## 21. Containers and Cgroups

Containerized MongoDB introduces an explicit effective-memory boundary.

```text
Physical Node RAM
       │
       ▼
Cgroup / Container Limit
       │
       ▼
Effective MongoDB Memory Boundary
       │
       ▼
mongod
```

> **Node RAM is not necessarily MongoDB-available RAM.**

MongoDB administrators should verify the memory boundary actually visible to MongoDB rather than assuming the physical node's capacity applies.

`hostInfo` can provide useful evidence:

```javascript
db.hostInfo()
```

including memory-limit information such as `memLimitMB` where exposed for the environment.

## 22. Container Cache Sizing

If a container cannot access all host RAM, WiredTiger cache sizing must align with the memory actually available to that container.

Relevant controls include `storage.wiredTiger.engineConfig.cacheSizeGB` and applicable percentage-based configuration.

A dangerous architecture is:

```text
Container Memory Limit ≈ WiredTiger Cache
```

because MongoDB still requires memory for queries, aggregations, connections, index builds, replication, allocator/runtime state, and other process requirements.

```text
Container Memory
│
├── WiredTiger
├── Non-Cache MongoDB Memory
└── Safety Headroom
```

must be designed explicitly.

## 23. Multiple `mongod` Processes on One Host

The default cache-sizing model assumes a normal deployment in which a `mongod` instance has appropriate access to the machine's memory resources.

If multiple `mongod` processes share one host, administrators must account for their combined cache and non-cache memory requirements.

```text
Host Memory
│
├── mongod A
│    ├── WiredTiger
│    └── Other Memory
├── mongod B
│    ├── WiredTiger
│    └── Other Memory
├── OS / Filesystem Cache
└── Headroom
```

Blindly allowing every instance to size itself as though it owns the host can create memory pressure.

## 24. Kubernetes Memory Architecture

A representative Kubernetes deployment adds several boundaries:

```text
Kubernetes Node
      │
      ▼
Pod
      │
      ▼
Container Memory Limit
      │
      ▼
mongod
      │
      ├── WiredTiger
      └── Non-Cache Memory
```

Kubernetes commonly distinguishes `resources.requests.memory` from `resources.limits.memory`. The detailed Kubernetes scheduling semantics belong in Book 4.

> **Size MongoDB against its effective container/cgroup memory boundary, not merely the Kubernetes node's total RAM.**

Also verify effective cgroup memory and swap behavior rather than assuming host-level settings automatically apply unchanged.

## 25. Production Memory Headroom

Production systems need headroom.

```text
Effective Memory Boundary
│
├── WiredTiger Cache
├── MongoDB Non-Cache Memory
├── OS / Runtime
├── Other Required Processes
└── Safety Headroom
```

Do not allocate every theoretical byte to steady-state workload. Headroom helps absorb workload bursts, application autoscaling, connection storms, index builds, maintenance, failover, cache warming, replication catch-up, recovery, and temporary workload imbalance.

## 26. Memory During Restart, Failover, and Recovery

Restart and failover can create simultaneous resource demands.

```text
Restart / Failover
       │
       ▼
Connections Re-established
       +
Cache Initially Cold
       +
Queries / Writes Resume
       +
Replication / Recovery
       │
       ▼
CPU + Memory + Storage-I/O Burst
```

After restart, frequently accessed pages may need to be loaded again:

```text
Cold Cache
    │
    ▼
Workload Arrives
    │
    ▼
Storage Reads Increase
    │
    ▼
Cache Warms
    │
    ▼
Steady State
```

Temporary post-restart I/O or latency increases do not automatically indicate a storage failure. The question is whether the platform can support the cold-cache workload until steady state returns.

## 27. Memory Growth vs. Memory Leak

Increasing process memory does not automatically prove a memory leak.

Expected causes can include cache warming, workload growth, connection growth, index operations, aggregation activity, allocator behavior, or changed access patterns.

A useful investigation asks whether memory stabilizes, correlates with workload, is explained by WiredTiger, is explained by TCMalloc/allocator statistics, tracks connection growth, tracks query or index activity, approaches the cgroup/host limit, falls or stabilizes after workload reduction, and reproduces consistently.

> **Growth is evidence. Unbounded unexplained growth is the problem.**

## 28. MongoDB Memory Monitoring

Production memory diagnosis requires several evidence domains.

```text
MongoDB Metrics
      +
Allocator Metrics
      +
OS / Cgroup Metrics
      +
Storage Metrics
      +
Workload Metrics
      =
Memory Diagnosis
```

Representative MongoDB 8.x evidence includes:

```text
mem.resident
mem.virtual

wiredTiger.cache.maximum bytes configured
wiredTiger.cache.bytes currently in the cache
wiredTiger.cache.tracked dirty bytes in the cache
wiredTiger.cache.pages read into cache
wiredTiger.cache.pages written from cache
```

MongoDB exposes many additional WiredTiger statistics. Allocator evidence can also be inspected through TCMalloc information exposed by `serverStatus`.

Exact metric names should always be validated against the deployed MongoDB release when building monitoring automation.

## 29. Operating-System and Container Monitoring

Useful host evidence includes total memory, available memory, filesystem cache, swap usage, swap-in/swap-out, process RSS, page activity, OOM events, CPU, disk I/O, and storage latency.

Common Linux tools include:

```text
free
vmstat
top
ps
pidstat
sar
journalctl
```

For containers/Kubernetes, additionally capture memory usage, memory request, memory limit, cgroup memory events, restart count, termination reason, node memory pressure, and pod eviction events.

Detailed commands and runbooks belong in Chapter 22.

## 30. Memory Alerting

Avoid a universal alert such as:

```text
Memory Used > 80% = Critical
```

MongoDB can legitimately use a large portion of available memory.

A stronger alerting model correlates:

```text
Available Memory
      +
Swap / Reclaim
      +
WiredTiger Pressure
      +
Allocator / RSS
      +
Storage I/O
      +
Application Latency
      +
OOM / Cgroup Events
```

The objective is to alert on actionable pressure and impact rather than normal memory utilization. Specific warning and critical thresholds belong in Chapter 15.

## 31. Production Failure Patterns

### 31.1 High Utilization but Healthy

```text
Memory Utilization High
Pressure Low
Swap Minimal
Latency Normal
I/O Normal
```

Likely interpretation: memory is being used effectively. Do not restart MongoDB simply to make memory utilization appear lower.

### 31.2 WiredTiger Cache Pressure

Potential evidence:

```text
Eviction ↑
Pages Read ↑
Storage I/O ↑
Latency ↑
```

Investigate workload changes, working-set growth, query/index efficiency, cache pressure, storage latency, and effective memory capacity. Do not immediately increase the cache.

### 31.3 Non-Cache Process Pressure

If process RSS increases while WiredTiger cache remains stable, investigate TCMalloc, connections, aggregations, query concurrency, index builds, transactions, replication/recovery, and recent application changes.

### 31.4 Swap Pressure

```text
Memory Pressure
      ↓
Swap Activity
      ↓
Page Retrieval
      ↓
Storage I/O
      ↓
Latency
```

Determine whether the underlying issue is insufficient capacity, cache sizing, workload concurrency, colocated processes, or configuration.

### 31.5 Container OOM

```text
Container Limit
      ↓
Memory Demand Exceeds Limit
      ↓
OOMKilled
      ↓
MongoDB Restart
```

Investigate the effective cgroup limit, WiredTiger sizing, RSS, allocator statistics, connection count, query/aggregation concurrency, index builds, and workload at the time of failure. Do not increase the container limit without understanding the cause.

### 31.6 Failover / Recovery Pressure

```text
Failover
   ↓
Reconnect
   +
Cache Warm
   +
Workload Resume
   +
Replication / Recovery
   ↓
Resource Burst
```

Capacity planning must include this recovery workload.

## 32. Memory Troubleshooting Workflow

```text
Memory Alert / Performance Problem
             │
             ▼
Actual Memory Pressure?
             │
             ▼
What Is the Effective Memory Boundary?
             │
             ▼
OOM / Swap / Reclaim?
             │
             ▼
WiredTiger Cache Pressure?
             │
             ▼
Non-Cache Process Growth?
             │
             ▼
Allocator / TCMalloc?
             │
             ▼
Connections / Queries /
Aggregations / Index Builds?
             │
             ▼
Working Set Changed?
             │
             ▼
Storage I/O Increased?
             │
             ▼
Recent Workload / Deployment Change?
             │
             ▼
Root Cause
```

> **Do not begin memory troubleshooting by changing the WiredTiger cache.**

Identify the actual pressure domain first.

## 33. Evidence Collection

Collect evidence before restart whenever operationally safe.

### MongoDB

Capture `serverStatus`, WiredTiger cache metrics, TCMalloc/allocator metrics, connections, active operations, replication state, and logs.

### Process

Capture RSS, virtual memory, uptime, threads, and relevant file-descriptor information.

### OS

Capture total/available RAM, filesystem cache, swap, page activity, OOM evidence, CPU, and storage I/O and latency.

### Containers / Kubernetes

Capture memory request, memory limit, current usage, cgroup events, restart count, termination reason, node pressure, and eviction events.

### Workload

Capture traffic, query mix, connection count, aggregation concurrency, index builds, batch activity, backups, deployments, autoscaling, and failover/recovery events.

Correlate all evidence by timestamp.

## 34. Capacity Planning

Production memory capacity should consider:

```text
Steady-State Workload
        +
Operational Working Set
        +
Indexes
        +
Connections
        +
Query / Aggregation Concurrency
        +
Index Builds
        +
Transactions / Replication
        +
Maintenance
        +
Failover / Recovery
        +
Safety Headroom
```

Do not size production MongoDB only for average steady-state utilization.

## 35. Scaling and Remediation

When evidence confirms memory pressure, possible responses include:

### Workload Optimization

- improve queries;
- improve indexes;
- reduce unnecessary concurrency;
- correct connection-pool behavior;
- isolate expensive batch workloads.

### Vertical Scaling

Increase effective memory available to MongoDB.

### Horizontal Scaling

Where appropriate, distribute workload or data across additional resources.

### Storage Engineering

Improve storage performance where cache misses are unavoidable.

### Configuration

Adjust cache or execution-related settings only when evidence supports the change.

### Architecture

Reevaluate workload placement, sharding, analytics isolation, maintenance scheduling, or application behavior.

Capacity changes should address the identified bottleneck rather than merely increase resources.

## 36. Production Governance

Production standards should define effective memory sizing, minimum headroom, WiredTiger cache-change controls, container memory sizing, Kubernetes requests/limits, swap policy, OOM monitoring, memory alerts, connection capacity, query/aggregation concurrency, index-build procedures, capacity reviews, failover testing, evidence collection, and escalation ownership.

WiredTiger cache overrides should be controlled changes, not ad hoc tuning.

## 37. Memory Anti-Patterns

Avoid:

- treating high used-memory percentage as an incident by itself;
- assuming WiredTiger cache equals total `mongod` memory;
- assuming the entire database must fit in RAM;
- treating virtual memory as physical RAM consumption;
- ignoring filesystem cache;
- ignoring allocator/TCMalloc behavior;
- ignoring swap activity;
- ignoring cgroup limits;
- sizing WiredTiger cache near the entire container limit;
- ignoring non-cache process memory;
- assuming every memory problem is a WiredTiger problem;
- increasing WiredTiger cache without evidence;
- increasing container memory without RCA;
- restarting MongoDB merely to reduce RSS;
- ignoring connection growth;
- ignoring aggregation concurrency;
- ignoring index-build memory;
- running concurrent large index builds without capacity review;
- ignoring cold-cache behavior after restart;
- treating OOM as the final root cause;
- ignoring storage performance;
- monitoring only MongoDB metrics;
- monitoring only host metrics;
- applying one `vm.swappiness` value universally;
- running multiple `mongod` instances without shared-memory planning; or
- changing several memory parameters simultaneously during troubleshooting.

## 38. DBA Production Checklist

Before approving MongoDB memory architecture for production, verify:

- [ ] effective host/container memory boundary is known;
- [ ] WiredTiger cache configuration is understood;
- [ ] default cache sizing is used unless evidence supports an override;
- [ ] sufficient non-cache headroom exists;
- [ ] filesystem-cache behavior is considered;
- [ ] allocator/TCMalloc monitoring is available where needed;
- [ ] swap policy is documented;
- [ ] OOM monitoring exists;
- [ ] container/cgroup limits align with MongoDB sizing;
- [ ] Kubernetes requests/limits are understood where applicable;
- [ ] working-set behavior is understood;
- [ ] index footprint is reviewed;
- [ ] query/aggregation concurrency is considered;
- [ ] index-build memory is considered;
- [ ] connection capacity is considered;
- [ ] transaction/replication/recovery workloads are considered;
- [ ] maintenance workload is considered;
- [ ] failover capacity is tested;
- [ ] cold-cache behavior is understood;
- [ ] storage supports expected cache misses;
- [ ] MongoDB memory/cache metrics are monitored;
- [ ] OS/container metrics are monitored;
- [ ] alerts distinguish utilization from pressure;
- [ ] safety headroom is maintained; and
- [ ] escalation ownership is documented.

5. MongoDB benefits from both WiredTiger and operating-system filesystem caching.
6. Compressed disk size is not a direct RAM-sizing formula.

9. Virtual memory is not equivalent to physical RAM usage.
10. High memory utilization is not automatically memory pressure.
11. The entire database does not necessarily need to fit in RAM.
12. The operational working set is determined by actual workload behavior.
13. Data and indexes both create cache demand.

21. Concurrent index builds can materially increase memory demand.
22. Connections consume memory and other server resources.
23. Application autoscaling can become a database memory-capacity event.
24. Transactions, replication, and recovery can increase resource pressure.
25. Memory and storage performance are coupled.
26. Swap should be deliberately engineered rather than treated with a universal rule.
27. OOM is generally an outcome requiring deeper RCA.
28. Container/cgroup limits can matter more than physical node RAM.
29. MongoDB cache sizing must leave headroom inside containers.
30. Multiple `mongod` processes require shared-host memory planning.
31. Production systems require safety headroom.
32. Failover and recovery create resource bursts.
33. Cold-cache behavior after restart is expected but must be supportable.
34. Increasing RSS does not automatically prove a memory leak.
35. MongoDB, allocator, OS, container, storage, and workload evidence must be correlated.
36. Memory alerts should identify pressure and impact rather than normal utilization.
37. Do not start memory troubleshooting by changing WiredTiger cache.
38. Capacity planning must include maintenance, failover, recovery, and workload bursts.
