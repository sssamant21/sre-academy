## 1. WiredTiger's Role in MongoDB

A MongoDB storage engine manages how database information is represented and persisted in memory and on storage.

For this handbook, **WiredTiger is the production storage-engine baseline**. It is MongoDB's default storage engine, and MongoDB Atlas deployments use WiredTiger.

```text
MongoDB Logical Operations
          │
          ▼
WiredTiger
          │
          ├── Cache / Pages
          ├── MVCC / Snapshots
          ├── History Store
          ├── Eviction
          ├── Reconciliation
          ├── Compression
          ├── Checkpoints
          ├── Journal Integration
          └── Concurrency Control
          │
          ▼
Filesystem / OS Cache
          │
          ▼
Persistent Storage
```

A database symptom does not necessarily originate at the query layer. Slow operations can result from query/index problems, cache pressure, version retention, eviction/reconciliation, checkpoint pressure, or storage latency. A DBA therefore needs to understand the complete database-to-storage path.

## 2. Logical MongoDB Objects and Physical Storage

Applications interact with databases, collections, documents, and indexes. MongoDB's catalog associates these logical objects with underlying storage-engine structures.

```text
Database / Collection / Index
            │
            ▼
      MongoDB Catalog
            │
            ▼
       WiredTiger Ident
            │
            ▼
   WiredTiger Storage Object
            │
            ▼
       Files / Blocks
```

An **ident** is an internal identifier used in MongoDB's storage architecture. WiredTiger idents are implementation details; applications and routine administration must not depend on ident names.

## 3. WiredTiger Files and dbPath

In a self-managed MongoDB deployment, the configured `dbPath` contains MongoDB/WiredTiger storage and runtime files. Exact filenames and layouts can vary by MongoDB release and configuration and are not stable application interfaces.

> **Never manually edit, delete, rename, replace, or selectively copy WiredTiger internal files as a routine recovery or migration procedure.**

This includes collection storage files, index storage files, WiredTiger metadata, history-store files, and journal files. Use supported backup/restore, replica-set resynchronization, repair, migration, or documented recovery workflows.

## 4. Tree and Page Architecture

WiredTiger organizes persistent information using tree-oriented structures. For DBA purposes, the important concept is that WiredTiger works with **pages** rather than loading entire collections into memory. Pages can represent collection data, index information, internal tree structures, and storage-engine metadata/version information. Exact internal structures are implementation details.

## 5. Page Lifecycle

```text
Persistent Representation
          │
          ▼
     Read Into Cache
          │
          ▼
In-Memory Representation
          │
          ▼
      Modification
          │
          ▼
       Dirty State
          │
          ▼
    Reconciliation
          │
          ▼
Persistent Representation
```

This lifecycle connects cache, page reads, writes, dirty data, reconciliation, eviction, checkpoints, and persistent storage.

## 6. In-Memory vs. On-Disk Representation

A WiredTiger page does not necessarily have the same representation in memory as it does on disk. Collection data stored in the WiredTiger internal cache uses an in-memory representation different from its compressed persistent representation. The operating-system filesystem cache can retain the filesystem's compressed representation. Indexes have their own storage and in-memory characteristics and can benefit from prefix compression.

```text
Logical Data Size
        ≠
Compressed Disk Size
        ≠
WiredTiger Cache Footprint
```

A storage compression ratio should never be used directly as a MongoDB RAM-sizing formula.

## 7. One WiredTiger Cache per mongod

The WiredTiger cache belongs to the `mongod` instance. It is not independently allocated per database or collection.

```text
mongod
  │
  ▼
WiredTiger Cache
  │
  ├── Database A
  ├── Database B
  ├── Collections
  ├── Indexes
  └── Internal Storage Structures
```

A hot workload in one database can therefore influence cache behavior experienced by another workload on the same instance. WiredTiger does not reserve fixed independent portions of its cache for reads and writes. Detailed cache sizing is covered in **1.13 — MongoDB Memory Architecture**.

## 8. WiredTiger Cache and Filesystem Cache

MongoDB benefits from both the WiredTiger internal cache and the operating-system filesystem cache.

```text
MongoDB Operation
       │
       ▼
WiredTiger Internal Cache
       │
       ▼
Filesystem
       │
       ▼
OS Filesystem Cache
       │
       ▼
Persistent Storage
```

The WiredTiger cache manages active storage-engine content. The filesystem cache can reduce physical storage access when relevant filesystem pages remain available in OS memory.

## 9. Page Reads

When required information is not already in the WiredTiger cache, WiredTiger may obtain it through the filesystem/storage path and load the relevant page into cache. Increasing page reads can result from cold-cache conditions, working-set growth, workload changes, inefficient queries, changing index usage, or reduced effective memory.

> **Page reads are not automatically evidence of a problem.**

They must be correlated with workload, cache behavior, storage activity, and application latency.

## 10. Dirty Content

Writes modify content held by WiredTiger. Dirty content must eventually be reconciled and persisted. Write-heavy workloads can therefore increase dirty-cache content, reconciliation work, checkpoint activity, journal activity, and storage writes.

## 11. Reconciliation

**Reconciliation** converts modified in-memory page state into a representation suitable for persistence. It participates in activities such as dirty-page eviction and checkpoint processing. Detailed reconciliation algorithms belong in the MongoDB DBRE & Performance Engineering Handbook.

## 12. Eviction

The WiredTiger cache has finite capacity. When space is required, WiredTiger selects content that can leave the cache. Clean content can be removed when appropriate; dirty content requires reconciliation before the relevant cache space can be reclaimed.

```text
Eviction Exists
      ≠
Incident
```

Likewise:

```text
Cache Near Capacity
      ≠
Cache Pressure
```

The production concern is sustained eviction pressure correlated with increased page reads, CPU pressure, storage I/O, dirty-cache pressure, operation latency, or throughput degradation.

## 13. Application Work and Eviction Pressure

Under sufficient cache pressure, application threads can participate in or wait on work required to restore cache availability, which can increase operation latency. The existence of eviction activity alone does not establish this condition.

## 14. Checkpoints

A WiredTiger checkpoint establishes a consistent persistent view of database state. During normal MongoDB operation, WiredTiger performs checkpoints approximately every **60 seconds**.

```text
Checkpoint N
     │
     │ remains valid
     ▼
Checkpoint N+1 Being Written
     │
     ▼
Metadata Updated Atomically
     │
     ▼
Checkpoint N+1 Becomes Current
```

While a new checkpoint is being prepared, the previous valid checkpoint remains available. Detailed checkpoint behavior is covered in **1.16 — Checkpoints and Recovery Architecture**.

## 15. Journaling and Checkpoints

WiredTiger integrates write-ahead journaling with checkpoints. The checkpoint provides a consistent persistent base; the journal allows durable modifications made after the last checkpoint to be recovered.

```text
Last Valid Checkpoint
          +
Required Journal Records
After That Checkpoint
          │
          ▼
Recovery Processing
          │
          ▼
Consistent Recovered State
```

Journaling should not be thought of as another full copy of the database. MongoDB 8.x uses compression for WiredTiger journal records, with Snappy as the default journal compressor. Detailed durability and journal configuration are covered in **1.15 — Journaling and Durability Architecture**.

## 16. MVCC and Snapshots

WiredTiger supports MongoDB concurrency using multi-version concurrency control concepts. A database operation can work with a point-in-time view of data appropriate to its visibility semantics. MongoDB's higher-level read concern, write concern, transaction, replication, and consistency semantics determine how these capabilities are exposed to applications.

## 17. Timestamps and Version Visibility

MongoDB and WiredTiger use timestamp-based mechanisms to coordinate version visibility and recovery semantics. Architecturally relevant concepts include read timestamps, commit timestamps, stable timestamps, and oldest timestamps. These are internal coordination mechanisms rather than routine DBA tuning controls.

## 18. WiredTiger History Store

When older versions must remain available beyond their normal location in the storage structure, WiredTiger can preserve them through its history-store architecture. In self-managed deployments, DBAs may encounter the internal `WiredTigerHS.wt` file during storage investigations.

> **`WiredTigerHS.wt` is an internal WiredTiger file and must never be manipulated directly.**

Its behavior should be interpreted through transaction, snapshot, and version-retention activity.

## 19. Snapshot History Window

MongoDB provides `minSnapshotHistoryWindowInSeconds` to influence the minimum snapshot-history window maintained by WiredTiger.

```text
Snapshot History Window ↑
          │
          ▼
Historical Version Retention ↑
          │
          ▼
Potential Disk Usage ↑
```

Increasing historical retention can therefore have storage consequences. Detailed transaction and snapshot administration belongs in later chapters.

## 20. Long-Running Transactions

Long-running transactions or snapshot operations can require older versions to remain available longer, increasing history-store activity, cache impact, reconciliation work, and storage growth.

> **A long-running transaction can become a storage-engine capacity problem, not merely a transaction-duration problem.**

## 21. Concurrency Architecture

WiredTiger uses optimistic concurrency mechanisms for many operations, while MongoDB maintains additional locking and coordination above the storage-engine layer. MongoDB uses intent locks at broader resource levels while WiredTiger provides fine-grained concurrency for storage operations. When competing writes conflict, MongoDB can transparently retry storage-engine write conflicts where appropriate.

Neither "MongoDB has no locks" nor "WiredTiger makes all operations lock-free" is correct. Detailed concurrency behavior belongs in **1.17 — Concurrency and Locking Fundamentals**.

## 22. WiredTiger Read and Write Tickets

MongoDB 7.x and 8.x dynamically manage storage-engine concurrency for read and write transactions. Current concurrency-ticket visibility is available through execution-queue metrics including `queues.execution`.

> **Low available ticket count alone does not prove storage-engine saturation.**

More meaningful evidence includes queued reads/writes, operation latency, throughput, cache pressure, and storage latency. Detailed ticket analysis belongs in Chapter 16.

## 23. Compression Architecture

For the MongoDB 8.x baseline:

| Storage Object | Typical Default |
|---|---|
| Most collections | Snappy block compression |
| Time-series collections | zstd block compression |
| Indexes | Prefix compression enabled |
| Journal | Snappy compression |

Compression behavior is version-specific and should be validated against the deployed MongoDB release before configuration changes. Alternative collection compression algorithms can include `zlib` and `zstd`.

## 24. Compression Configuration Lifecycle

A global compression configuration change generally affects newly created storage objects; it does not automatically rewrite all existing collections or indexes. Changing compression of existing data may require an appropriate rewrite or migration procedure.

## 25. Logical Size vs. Physical Storage

```text
Logical Data Size
      ≠
Allocated WiredTiger Storage
      ≠
Filesystem Used Space
```

Physical usage can also include indexes, journal, diagnostic files, temporary files, metadata, historical versions, and reusable internal space.

## 26. Deleted Data and Reusable Space

Deleting MongoDB documents does not guarantee an equivalent immediate reduction in filesystem usage.

```text
Data Written
     │
     ▼
WiredTiger File Grows
     │
     ▼
Data Deleted / Changed
     │
     ▼
Internal Space Becomes Reusable
     │
     ├────► Future WiredTiger Reuse
     └────► Possible Reclamation
                    │
                    ▼
           Filesystem Space Return
```

`DELETE 100 GB` does not imply that the filesystem immediately gains 100 GB.

## 27. Reusable Space vs. Filesystem Free Space

Reusable internal WiredTiger space and filesystem free space are different capacity concepts. Reusable internal space is not necessarily waste; it can reduce future file growth because WiredTiger can reuse it. The relevant capacity question is whether that space should remain available for database reuse or must be returned to the filesystem.

## 28. Fragmentation

Over time, a WiredTiger file can contain both live data and reusable internal space. Do not label all reusable space as harmful fragmentation. Distinguish allocated storage, live data, internally reusable space, reclaimable space, and filesystem free space.

## 29. Compaction and Space Reclamation

For MongoDB 8.x, relevant storage-reclamation concepts include `compact`, `dryRun: true`, `freeSpaceTargetMB`, and `autoCompact`. `dryRun` can help estimate reclaimable space without performing the actual compaction, while MongoDB 8.0 also provides background automatic compaction capabilities through `autoCompact`.

Compaction is a controlled reclamation mechanism, not a universal fix or an instant database shrink operation. Modern MongoDB compaction can remain resource-intensive even when normal CRUD operations continue. Detailed procedures, replica-set considerations, backup interactions, and maintenance planning belong in Chapter 12.

## 30. Catalog and Storage Consistency

MongoDB's logical catalog and WiredTiger's storage objects form one consistent architecture.

```text
MongoDB Namespace
       │
       ▼
Catalog Metadata
       │
       ▼
WiredTiger Ident
       │
       ▼
Storage Object
```

This is why manually copying a collection storage file does not constitute a valid logical migration. Use supported migration and recovery mechanisms.

## 31. End-to-End Storage Path

```text
Application
     │
     ▼
MongoDB
     │
     ▼
WiredTiger
     │
     ▼
Filesystem Cache
     │
     ▼
Filesystem
     │
     ▼
Volume / Block Device
     │
     ▼
Cloud / Physical Storage
```

Database performance can be affected by storage latency, IOPS, throughput, queueing, filesystem behavior, volume limits, cloud burst limits, and disk capacity. A WiredTiger investigation that stops at MongoDB metrics is incomplete.

## 32. Storage Latency

When a required page cannot be served from available cache layers, physical storage latency can become operation latency. This can surface as slow reads/writes, slow cache warming, checkpoint pressure, replication lag, slow initial sync, or slow recovery. Correlation is required before assigning root cause.

## 33. Checkpoint and Storage Pressure

If the storage subsystem cannot sustain required writes, checkpoint duration can increase. Representative MongoDB evidence includes the WiredTiger transaction statistic for the most recent checkpoint duration. Validate exact metric names against the deployed release when building monitoring automation, and correlate checkpoint duration with write throughput, IOPS, storage latency, queue depth, and dirty-cache behavior.

## 34. WiredTiger Monitoring Architecture

Representative `serverStatus` groups include:

```text
wiredTiger.cache
wiredTiger.transaction
wiredTiger.log
wiredTiger.reconciliation
wiredTiger.block-manager
```

For current storage-engine read/write execution-queue information, `queues.execution` can provide relevant concurrency evidence. Chapter 1 treats these as diagnostic categories rather than reproducing the complete MongoDB metric schema.

## 35. Representative Cache Evidence

Useful evidence can include maximum configured cache bytes, bytes currently in cache, dirty bytes, pages read into cache, pages written from cache, and eviction-related counters.

Many WiredTiger statistics are cumulative counters. A large absolute counter does not prove a current incident. Evaluate rates such as `Δcounter / Δtime` and correlate them with workload, latency, CPU, storage I/O, and cache pressure.

## 36. Avoid Universal WiredTiger Thresholds

Do not assume rules such as `Cache > 80% = Critical` or `Eviction > X = Incident` are universally valid. Storage-engine behavior depends on workload, working set, read/write mix, storage performance, transaction behavior, and MongoDB release. Chapter 15 establishes production alerting strategy.

## 37. Failure Pattern — Cache and Eviction Pressure

```text
Working Set / Workload ↑
          │
          ▼
Page Reads / Eviction ↑
          │
          ▼
Storage I/O ↑
          │
          ▼
Operation Latency ↑
```

Investigate workload changes, query patterns, indexes, effective memory, page-read rate, dirty-cache behavior, storage latency, and long-running transactions. Do not immediately increase WiredTiger cache.

## 38. Failure Pattern — Storage Latency

A bottleneck can exist below MongoDB in the filesystem, block device, or cloud storage layer. Symptoms can include slow reads/writes, checkpoint duration growth, replication lag, slow recovery, and slow cache warming.

## 39. Failure Pattern — Disk Full

A disk-full condition can affect data-file growth, journal activity, checkpoints, index builds, temporary files, diagnostics, and logs.

> **Disk-full conditions are production availability risks.**

Do not assume deleting documents will immediately return sufficient filesystem space.

## 40. Failure Pattern — Version-Retention Pressure

Long transactions or snapshots can retain historical versions and increase history-store, cache, and storage pressure. Investigate transaction duration, snapshot behavior, history-store activity, storage growth, cache behavior, and application workload.

## 41. Failure Pattern — Cold Cache

After restart, failover, or node recovery, page reads and storage demand can temporarily increase while the cache warms. This is normal architecture.

> **A production storage subsystem should be capable of supporting cache warming after restart, failover, or recovery.**

## 42. Failure Pattern — Space-Reclamation Misunderstanding

A large delete can reduce logical data size while increasing reusable internal space without materially changing filesystem usage. Before considering compaction or migration, determine logical data size, allocated storage, reusable space, filesystem free space, expected future growth, and the actual capacity requirement.

## 43. WiredTiger Troubleshooting Workflow

```text
MongoDB Performance / Storage Problem
                │
                ▼
Workload / Query Change?
                │
                ▼
WiredTiger Cache Pressure?
                │
                ▼
Version / History Retention?
                │
                ▼
Eviction / Reconciliation?
                │
                ▼
Checkpoint / Journal Pressure?
                │
                ▼
Filesystem Cache?
                │
                ▼
Filesystem Capacity?
                │
                ▼
Storage Latency / IOPS / Throughput?
                │
                ▼
Root Cause
```

> **Do not begin a WiredTiger incident by changing cache settings, running compaction, or restarting MongoDB.**

Identify the pressure domain first.

## 44. Evidence Collection

Collect evidence before restart whenever operationally safe.

### MongoDB

Capture `serverStatus`, database/collection statistics, active operations, transaction activity, replication state, and MongoDB logs.

### WiredTiger

Capture cache utilization, dirty-cache information, page-read/write rates, eviction/reconciliation evidence, checkpoint duration, and transaction/history-store evidence.

### Operating System and Storage

Capture available memory, filesystem cache, disk utilization, filesystem free space, IOPS, throughput, latency, queueing, provisioned storage limits, throttling, and cloud burst/balance metrics where applicable.

### Workload

Capture read/write throughput, query changes, batch operations, index builds, backups, deployments, failover, recovery, and maintenance activity. Correlate all evidence by timestamp.

## 45. WiredTiger Production Anti-Patterns

Avoid treating WiredTiger as MongoDB's entire architecture; treating cache as total `mongod` memory; increasing cache merely because RAM appears available; treating high cache utilization or all eviction as incidents; diagnosing cumulative counters without rates; applying universal thresholds; assuming disk size equals cache footprint; assuming logical size equals filesystem usage; assuming deleted data immediately returns disk space; treating all reusable space as waste; ignoring filesystem caching, storage latency, dirty-cache behavior, long-running transactions, or history-store growth; assuming low available tickets alone means saturation; manually modifying WiredTiger files; copying individual storage files as migration; using compaction reflexively; restarting before collecting evidence; or tuning several WiredTiger parameters simultaneously.

## 46. DBA Production Checklist

Before approving WiredTiger architecture for production, verify:

- [ ] WiredTiger is the expected storage-engine baseline;
- [ ] logical objects and physical storage are clearly distinguished;
- [ ] WiredTiger internal files are treated as implementation details;
- [ ] no operational process manually manipulates WiredTiger files;
- [ ] WiredTiger cache and filesystem-cache architecture is understood;
- [ ] collection and index growth is monitored;
- [ ] compression defaults are documented;
- [ ] logical and physical storage metrics are distinguished;
- [ ] reusable internal space is understood;
- [ ] disk-capacity alerts exist;
- [ ] storage latency, IOPS, and throughput are monitored;
- [ ] dirty-cache, eviction, reconciliation, and checkpoint evidence is available;
- [ ] long-running transactions and history-store growth can be investigated;
- [ ] execution queues can be monitored;
- [ ] counters are converted to rates where appropriate;
- [ ] cache warming is considered during failover/recovery;
- [ ] compaction is controlled by change management;
- [ ] backups use supported mechanisms;
- [ ] diagnostic evidence is collected before restart when safe; and
- [ ] storage failure ownership and escalation are documented.

## 47. Key DBA Takeaways

1. WiredTiger is MongoDB's default storage engine and this handbook's production baseline.
2. MongoDB Atlas deployments use WiredTiger, while low-level host administration is service-managed.
3. Logical MongoDB objects map through catalog metadata to internal WiredTiger storage structures.
4. WiredTiger idents and files are implementation details and must not be manually manipulated.
5. WiredTiger works with tree-oriented page structures whose persistent and in-memory representations can differ.
6. A `mongod` uses a shared WiredTiger cache across its databases and collections and also benefits from the OS filesystem cache.
7. Page reads and eviction are normal and must be interpreted in context.
8. Dirty content requires reconciliation before appropriate persistence.
9. WiredTiger normally checkpoints approximately every 60 seconds, with the previous checkpoint remaining valid while a new checkpoint is created.
10. Journaling and checkpoints provide complementary durability mechanisms.
11. MVCC, snapshots, timestamps, and the history store support version visibility and concurrent operations.
12. Long-running transactions can become storage-engine capacity problems.
13. MongoDB combines broader locking/coordination with WiredTiger optimistic concurrency.
14. Low available read/write tickets alone do not prove saturation.
15. MongoDB 8.x uses compression for collections, indexes, and journal storage, and configuration changes do not automatically rewrite existing objects.
16. Logical size, allocated WiredTiger storage, reusable internal space, and filesystem usage are different measurements.
17. Compaction is a controlled reclamation mechanism, not a universal fix.
18. Storage performance must be investigated end to end.
19. WiredTiger counters should often be interpreted as rates rather than absolute values.
20. Disk-full conditions are availability risks and cache warming after restart/failover is a capacity consideration.
21. Do not start WiredTiger troubleshooting by tuning cache, running compaction, or restarting MongoDB.
22. Collect MongoDB, WiredTiger, OS, storage-platform, and workload evidence together.
