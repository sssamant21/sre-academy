## Learning Objectives

After completing this section, you should be able to:

- explain WiredTiger checkpoint architecture;
- distinguish checkpoints from journaling and backups;
- understand checkpoint lifecycle and atomic checkpoint transitions;
- explain the relationship among cache, dirty content, reconciliation, eviction, and checkpoints;
- monitor checkpoint duration and recognize storage-related degradation;
- understand snapshot-history retention at an architectural level;
- explain clean versus unclean shutdown behavior;
- describe normal WiredTiger crash recovery;
- distinguish crash recovery from restore, initial sync, and replica-set rollback;
- understand recovery, replication catch-up, and cache warming as separate operational phases;
- recognize common checkpoint and recovery failure patterns; and
- troubleshoot recovery safely without manipulating WiredTiger internal files.

## 1. Checkpoint Architecture

A WiredTiger checkpoint is a consistent, durable storage-engine recovery point written across the database's data files.

```text
MongoDB Writes
      │
      ▼
WiredTiger Cache
      │
      ▼
Modified / Dirty State
      │
      ▼
Reconciliation
      │
      ▼
Checkpoint
      │
      ▼
Persistent Data Files
```

Checkpoints are fundamental to storage consistency, crash recovery, journal-based recovery, persistent data-file state, and MongoDB startup after interruption. A checkpoint is part of MongoDB's local durability architecture; it is not an independent copy of the database.

## 2. Checkpoints vs. Journaling and Backup

```text
Checkpoint ≠ Journal
Checkpoint ≠ Backup
Journal    ≠ Backup
```

A checkpoint provides a consistent persistent storage-engine recovery base. The journal allows WiredTiger to recover appropriate durable modifications made after the last checkpoint. A backup provides an independent recovery source when active database storage cannot or should not be used.

```text
Last Valid Checkpoint
          +
Required Journal Records
          │
          ▼
WiredTiger Recovery
          │
          ▼
Consistent Recovered State
```

A checkpoint alone can provide a consistent recovery point. Journaling enables recovery of appropriate durable changes after that checkpoint. A checkpoint is not a substitute for backup because it normally resides within the same active storage environment as the database.

## 3. Checkpoint Lifecycle

MongoDB configures WiredTiger to create checkpoints at approximately 60-second intervals during normal operation.

```text
Checkpoint Begins
       │
       ▼
Required State Reconciled
       │
       ▼
Persistent Checkpoint Written
       │
       ▼
Metadata Atomically Updated
       │
       ▼
New Checkpoint Becomes
Valid Recovery Point
```

The exact storage-engine algorithms are internal implementation details.

### Previous Checkpoint Protection

While WiredTiger creates a new checkpoint, the previous valid checkpoint remains available. If the process terminates while constructing the new checkpoint, the partially created checkpoint does not simply replace the last known valid recovery point.

### Atomic Metadata Transition

A new checkpoint becomes the persistent recovery point only after WiredTiger atomically updates its metadata to reference that checkpoint. This transition is fundamental to crash-safe checkpoint architecture.

## 4. Cache, Reconciliation, and Checkpoints

MongoDB writes normally modify state represented in the WiredTiger cache. Modified cached state is commonly described as dirty until the relevant storage-engine persistence work occurs.

```text
Application Write
       │
       ▼
Modified Cached State
       │
       ▼
Reconciliation
       │
       ▼
Persistent Representation
       │
       ▼
Checkpoint
```

Dirty content is normal. Administrators should evaluate dirty-content trends together with reconciliation activity, checkpoint duration, eviction behavior, storage latency, and workload changes.

Eviction and checkpointing are related but have different primary purposes. Eviction helps maintain cache availability; checkpointing establishes a durable consistent recovery state. Both can involve reconciliation and storage activity.

## 5. Checkpoint I/O Architecture

Checkpoint persistence ultimately depends on the complete storage path.

```text
MongoDB
   │
   ▼
WiredTiger
   │
   ▼
Filesystem
   │
   ▼
Volume / Device
   │
   ▼
Persistent Storage
```

Checkpoint I/O exists alongside journal and other database I/O. During sustained write workloads, write activity, journal I/O, checkpoint I/O, and other database I/O can create shared storage demand.

Higher sustained write activity can increase reconciliation and checkpoint persistence work, but observed checkpoint performance depends on the workload and storage system together. Large batch operations such as bulk inserts, mass updates, backfills, migrations, large deletes, and maintenance operations can temporarily amplify this demand.

Do not universally prescribe separate devices for journal and data files. Storage design is platform- and workload-dependent.

## 6. Checkpoint Duration and Monitoring

Checkpoint interval and checkpoint duration are different measurements.

```text
Checkpoint Interval ≠ Checkpoint Duration
```

The interval describes checkpoint cadence. Duration describes how long checkpoint creation takes.

A useful MongoDB 8.x WiredTiger statistic is:

```text
wiredTiger.transaction.transaction checkpoint most recent time (msecs)
```

Additional checkpoint statistics can expose checkpoint counts, current checkpoint activity, minimum/maximum checkpoint time, and cumulative checkpoint time.

> **Production Rule:** Increasing checkpoint duration under comparable or steady write load can indicate storage I/O saturation and should be correlated with workload and storage evidence.

Correlate checkpoint duration with write throughput, dirty-cache trends, reconciliation, journal activity, disk latency, IOPS, throughput, queue depth, and cloud-volume throttling. Do not define a universal warning or critical checkpoint-duration threshold.

## 7. Snapshot History and Version Retention

MongoDB and WiredTiger maintain historical versions to support appropriate snapshot visibility. MongoDB 8.x normally uses a minimum snapshot-history window of approximately 300 seconds. The parameter `minSnapshotHistoryWindowInSeconds` controls the minimum history window.

Increasing the retained history window can increase disk consumption, particularly under workloads that modify data rapidly. A checkpoint completing does not mean every historical version can immediately be removed. History retention is driven by visibility and storage-engine requirements, not simply by checkpoint completion.

### WiredTiger History Store

WiredTiger uses an internal history store for older versions required by snapshot visibility. A DBA may encounter `WiredTigerHS.wt` under the configured storage path.

> **Production Rule:** Never manually delete, truncate, replace, move, or edit `WiredTigerHS.wt`.

If history-store growth becomes significant, investigate snapshot workload, history-window configuration, update volume, long-running operations, cache behavior, and disk behavior. MongoDB and WiredTiger also maintain internal timestamp boundaries that coordinate snapshot visibility, recovery, and historical-version retention; detailed timestamp internals belong in advanced storage and replication coverage.

## 8. Shutdown and Recovery Boundaries

Use MongoDB's supported shutdown mechanisms whenever possible. A supported shutdown allows MongoDB to quiesce activity and clean up database resources before process termination. Production automation and orchestration should prefer graceful MongoDB termination.

An unclean shutdown can result from process crash, OOM kill, forced process termination, host failure, kernel failure, VM termination, container termination, or infrastructure failure. It can require WiredTiger recovery on the next startup, but it does not automatically imply database corruption.

## 9. Crash-Recovery Architecture

After an unexpected shutdown, WiredTiger can recover using the last valid checkpoint together with required journal records.

```text
Unexpected Shutdown
       │
       ▼
Last Valid Checkpoint
       +
Required Journal Records
       │
       ▼
WiredTiger Recovery
       │
       ▼
Consistent Database State
```

When journal replay is required, it occurs during startup before MongoDB becomes normally available.

```text
mongod Starts
     │
     ▼
WiredTiger Opens
     │
     ▼
Last Valid Checkpoint
     │
     ▼
Required Journal Recovery
     │
     ▼
Recovery Completes
     │
     ▼
MongoDB Available
```

This is an operational model rather than a specification of every internal WiredTiger startup step.

> **Critical Recovery Rule:** Do not run `mongod --repair` merely because MongoDB experienced an unclean shutdown. Allow normal WiredTiger checkpoint/journal recovery to run first.

`--repair` is specialized recovery tooling, not the normal crash-recovery path.

## 10. Recovery vs. Restore, Initial Sync, and Rollback

| Mechanism | Primary Purpose |
|---|---|
| Crash recovery | Recover existing local storage after interruption |
| Restore | Recover data from an external backup/recovery source |
| Initial sync | Build or synchronize a replica-set member from another member |
| Replica-set rollback | Resolve divergent replicated history |

```text
Crash Recovery ≠ Restore ≠ Initial Sync ≠ Replica-Set Rollback
```

Do not escalate from normal crash recovery to restore, member rebuild, or repair merely because startup takes longer than expected. Determine what mechanism is actually required.

## 11. Recovery, Replica Catch-Up, and Cache Warming

Operational recovery consists of multiple phases.

```text
Local WiredTiger Recovery
          │
          ▼
MongoDB Available
          │
          ▼
Replication Catch-Up
          │
          ▼
Cache Warming
          │
          ▼
Steady-State Operation
```

Local recovery restores the local WiredTiger storage state. A restarted replica-set member may still need to process replicated changes that occurred while it was unavailable. The WiredTiger process cache starts cold after a process restart and repopulates as workload resumes.

> **Production Rule:** Recovery completion does not mean the member is fully caught up or that application performance has returned to steady state.

## 12. Cloud and Kubernetes Recovery Considerations

The WiredTiger recovery model remains conceptually the same in cloud and containerized deployments, but additional infrastructure stages can influence recovery.

In Kubernetes, pod or node events, persistent-volume availability, CSI/storage behavior, OOM kills, health probes, and infrastructure maintenance can affect the path from restart to steady state. In cloud environments, storage attachment, latency, IOPS, throughput, queueing, throttling, VM/node health, and infrastructure availability can influence operational recovery.

> **Production Rule:** A slow MongoDB recovery is not necessarily a MongoDB-only problem.

Detailed platform recovery belongs in the MongoDB Cloud & Kubernetes Production Handbook.

## 13. Production Failure Patterns

### Pattern 1 — Increasing Checkpoint Duration

Correlate increasing checkpoint duration with write workload, dirty cache, reconciliation, journal activity, storage latency, IOPS, throughput, and throttling. Increasing duration under comparable workload is evidence requiring investigation; do not assume the checkpoint itself is the root cause.

### Pattern 2 — Journal + Checkpoint I/O Saturation

Write load can increase journal I/O and modified state, which can increase reconciliation and checkpoint I/O. Shared storage saturation can manifest as write latency, increasing checkpoint duration, storage queueing, replication lag, and cache/eviction pressure. Investigate storage capacity before weakening durability controls.

### Pattern 3 — Recovery Takes Longer Than Expected

Read MongoDB startup and recovery logs before intervening. Determine whether recovery is progressing, then evaluate storage latency, filesystem errors, IOPS/throughput, throttling, and host resource pressure.

### Pattern 4 — Recovery Loop

If MongoDB repeatedly starts, enters recovery, and terminates again, investigate the original termination cause. Potential causes include OOM kills, storage failure, filesystem errors, host instability, configuration/startup problems, orchestration behavior, and operator action.

### Pattern 5 — Disk Full

Disk exhaustion can affect checkpoint, journal, history-store, index, and general data-file activity. Treat filesystem exhaustion as an emergency condition. Never delete WiredTiger internal files to create emergency filesystem space.

### Pattern 6 — Cold Cache After Recovery

Temporary latency after restart can reflect expected cache warming. Severe or prolonged warming latency can reveal insufficient underlying storage performance.

### Pattern 7 — Excessive Historical-Version Retention

Investigate snapshot workload, update volume, history-window configuration, and long-running operations. Never manipulate `WiredTigerHS.wt` directly.

## 14. Checkpoint Troubleshooting

Use a layered workflow:

```text
Checkpoint Degradation
        │
        ▼
Comparable Workload?
        │
        ▼
Checkpoint Duration Trend
        │
        ▼
Dirty Cache / Reconciliation
        │
        ▼
Journal + Database I/O
        │
        ▼
Filesystem Capacity
        │
        ▼
Latency / IOPS / Throughput
        │
        ▼
Infrastructure Constraints
        │
        ▼
Root Cause
```

> **Production Rule:** Do not begin a checkpoint incident by changing WiredTiger cache sizing, internal storage-engine parameters, or durability settings. Determine whether the actual constraint is workload, storage, cache behavior, filesystem capacity, or infrastructure.

## 15. Recovery Troubleshooting

```text
Unexpected Restart
       │
       ▼
Determine Original Stop Cause
       │
       ▼
Read Startup / Recovery Logs
       │
       ▼
Is Normal Recovery Progressing?
       │
       ▼
Allow Recovery to Complete
       │
       ▼
MongoDB Available
       │
       ▼
Replication Catch-Up
       │
       ▼
Cache Warming
       │
       ▼
Steady State
```

A critical safety gate is to determine whether normal WiredTiger recovery is progressing. If yes, wait and monitor unless another safety condition requires intervention. If not, collect evidence before escalating.

> **Production Rule:** Do not escalate from normal crash recovery to `--repair`, manual file manipulation, restore, or member rebuild merely because startup is taking longer than expected.

## 16. Evidence Collection

Before invasive recovery actions, collect evidence whenever operationally safe.

### Workload / Application

Capture write rate, batch operations, application latency, transaction activity, and recent workload changes.

### MongoDB

Capture startup/recovery logs, `serverStatus`, current operations, and shutdown/restart evidence.

### WiredTiger

Representative areas include:

```text
serverStatus().wiredTiger.transaction
serverStatus().wiredTiger.reconciliation
serverStatus().wiredTiger.cache
serverStatus().wiredTiger.log
```

Capture checkpoint duration, checkpoint activity, dirty-cache trends, reconciliation evidence, and journal evidence.

### Replication

Capture replica-set member state, replication lag, catch-up progress, elections, and redundancy.

### Operating System / Storage

Capture filesystem capacity, CPU, memory, disk latency, IOPS, throughput, queue depth, filesystem/kernel errors, and OOM events.

### Infrastructure

Capture pod restart reasons, Kubernetes node events, volume attachment events, cloud-volume throttling, VM/host failures, and infrastructure incidents where relevant.

Correlate evidence by timestamp. Capture the original process-termination cause separately from subsequent recovery symptoms.

## 17. Production Anti-Patterns

Avoid:

- treating checkpoint and journal as the same mechanism;
- treating a checkpoint as a backup;
- assuming checkpoint completion removes all historical versions;
- treating dirty content or eviction activity as automatically abnormal;
- declaring storage failure from one long checkpoint;
- defining universal checkpoint-duration thresholds;
- changing WiredTiger cache to solve every checkpoint problem;
- treating `fsync` as equivalent to normal checkpoint architecture;
- assuming unclean shutdown means corruption;
- automatically running `mongod --repair` after an unclean shutdown;
- confusing crash recovery with restore, initial sync, or replica-set rollback;
- assuming recovery completion means replication catch-up or steady-state performance has completed;
- deleting `WiredTigerHS.wt` or active journal files;
- manipulating collection/index `.wt` files;
- repeatedly interrupting healthy recovery;
- restarting repeatedly before collecting evidence;
- ignoring filesystem capacity or cloud/storage throttling.

## 19. Key DBA Takeaways

1. A WiredTiger checkpoint is a consistent, durable local recovery point.
2. A checkpoint is not the journal or a backup.
3. MongoDB normally creates WiredTiger checkpoints at approximately 60-second intervals.
4. Checkpoint interval and checkpoint duration are different.
5. The previous valid checkpoint remains available while a new checkpoint is created.
6. A new checkpoint becomes authoritative after persistent work and atomic metadata transition.
7. Reconciliation prepares modified state for persistent representation.
8. Dirty content is normal and must be interpreted contextually.
9. Eviction and checkpointing serve different purposes.
10. Journal and checkpoint I/O can compete for the same storage resources.
11. Increasing checkpoint duration under comparable workload can indicate storage I/O saturation.
12. Do not use universal checkpoint-duration thresholds.
13. Snapshot-history requirements can retain older versions beyond checkpoint completion.
14. MongoDB 8.x normally uses a minimum snapshot-history window of approximately 300 seconds.
15. `WiredTigerHS.wt` is an internal storage-engine file and must not be manually manipulated.
16. An unclean shutdown does not automatically imply corruption.
17. Normal crash recovery uses the last valid checkpoint plus required journal records.
18. Required recovery occurs before MongoDB becomes normally available.
19. Do not run `mongod --repair` merely because an unclean shutdown occurred.
20. Crash recovery, restore, initial sync, and replica-set rollback are different mechanisms.
21. Local recovery completion does not mean a replica is fully caught up or performance is at steady state.
22. Cache warming can create temporary post-restart I/O and latency.
23. A slow recovery can indicate underlying storage or infrastructure problems.
24. Disk exhaustion threatens the storage-engine recovery path.
25. Never delete WiredTiger internal files to solve capacity or recovery incidents.
26. Repeated recovery loops require investigation of the original termination cause.
27. Diagnose checkpoint degradation across workload, WiredTiger, filesystem, storage, and infrastructure.
28. Collect evidence before tuning, restarting, repairing, restoring, or rebuilding.
