## Learning Objectives

After completing this section, you should be able to:

- explain MongoDB's concurrency architecture;
- understand multi-granularity locking;
- distinguish `IS`, `IX`, `S`, and `X` lock concepts from MongoDB monitoring symbols;
- explain intent locks without confusing them with exclusive blocking;
- understand WiredTiger document-level and optimistic concurrency;
- recognize write conflicts and hot-document contention;
- distinguish normal lock waiting from operational contention;
- understand transaction concurrency fundamentals;
- distinguish lock waits, execution queueing, and flow-control waits;
- interpret MongoDB concurrency evidence; and
- troubleshoot concurrency safely before tuning or terminating operations.

## 1. Concurrency Architecture

Concurrency describes the ability of multiple operations to make progress during overlapping periods. MongoDB's concurrency architecture combines MongoDB resource locking with WiredTiger storage-engine concurrency.

```text
Application Operations
         │
         ▼
MongoDB Lock Manager
         │
         ├── Global
         ├── Database
         └── Collection
                │
                ▼
            WiredTiger
                │
                ├── Document-Level Concurrency
                ├── Optimistic Concurrency
                └── Write-Conflict Handling
```

For most read and write operations using WiredTiger, MongoDB uses intent locks at global, database, and collection levels while WiredTiger provides document-level concurrency control for writes.

Concurrency means operations can make progress during overlapping periods. Parallelism means operations physically execute simultaneously on different execution resources. For a DBA, the more useful question is usually where work is waiting, why it is waiting, and whether that waiting materially affects the workload.

## 2. Multi-Granularity Locking

MongoDB uses multi-granularity locking.

```text
Global
  │
  ▼
Database
  │
  ▼
Collection
  │
  ▼
WiredTiger Document Concurrency
```

Higher-level intent locks communicate that an operation intends to access a more specific resource lower in the hierarchy. This allows MongoDB to coordinate database and collection operations without requiring ordinary document modifications to exclusively lock an entire collection.

## 3. Lock Modes and Intent Locks

| Conceptual Mode | Meaning | Monitoring Symbol |
|---|---|---|
| `IS` | Intent Shared | `r` |
| `IX` | Intent Exclusive | `w` |
| `S` | Shared | `R` |
| `X` | Exclusive | `W` |

For a normal document modification, MongoDB can hold intent-exclusive locks at higher levels while WiredTiger coordinates the document modification.

```text
Database IX ≠ Database Exclusively Blocked
Global Lock Statistic ≠ Entire Server Blocked
```

Intent locks indicate lower-level access intent. They do not mean all concurrent activity against the resource is blocked.

## 4. WiredTiger Document-Level and Optimistic Concurrency

WiredTiger provides document-level write concurrency.

```text
Collection
   │
   ├── Document A ← Writer 1
   ├── Document B ← Writer 2
   └── Document C ← Writer 3
```

Multiple clients can normally modify different documents within the same collection concurrently.

WiredTiger uses optimistic concurrency for most read and write operations. Rather than pessimistically preventing every potential conflict in advance, WiredTiger can detect conflicts when concurrent operations interact. MongoDB can transparently retry certain write conflicts.

## 5. Write Conflicts and Hot Documents

Occasional write conflicts are an expected consequence of optimistic concurrency and are not automatically incidents. Investigate when conflict rates rise materially, operation latency increases, retries become significant, throughput falls, or conflicts correlate with hot data.

```text
Many Writers
     │
     ▼
Same Document / Hot Key
     │
     ▼
Write Conflicts ↑
     │
     ▼
Retries / Latency ↑
```

Examples include centralized counters, shared status documents, queue-control records, and concentrated update patterns. The correct remediation may require application or data-model changes rather than additional hardware.

## 6. Lock Waiting and Contention

When MongoDB cannot immediately acquire a compatible lock, an operation can wait. Lock waiting is part of normal resource coordination. It becomes operationally significant when waiting is sustained, increasing, affecting many operations, causing material latency, reducing throughput, or associated with long-lived blocking work.

```text
Lock Wait Exists ≠ Locking Incident
```

The DBA must determine the blocker and operational impact.

## 7. Lock Contention Can Be a Secondary Symptom

Apparent lock contention may originate elsewhere.

```text
Storage / CPU / Query Problem
          │
          ▼
Operation Duration ↑
          │
          ▼
Resource Occupancy ↑
          │
          ▼
Waiting May Increase
```

The same can occur with CPU saturation, inefficient query plans, cache pressure, overloaded execution queues, and excessively long transactions.

> **Production Rule:** Do not diagnose the root cause merely from the presence of waiting operations.

## 8. Yielding and Stronger Coordination

MongoDB operations can periodically yield. With WiredTiger, yielding is not generally required merely to let ordinary readers and writers bypass intent locks. Yielding also supports storage-transaction lifecycle management, interruption points, and operations requiring stronger resource access.

Some administrative, DDL, metadata, and global operations require stronger coordination than ordinary CRUD. Examples can include collection operations, database operations, metadata changes, and index lifecycle operations.

> **Production Rule:** Online does not mean zero impact.

An operation can allow concurrent workload activity while still consuming CPU, memory, storage I/O, and coordination resources.

## 9. Transactions and Concurrency

Multi-document transactions can span multiple operations, documents, and collections, maintain snapshot state, encounter write conflicts, and wait for required locks.

By default, a transaction waits up to approximately 5 milliseconds to acquire required locks. If required locks cannot be acquired within that interval, the transaction aborts. Transaction locks are released when the transaction commits or aborts.

Unnecessarily long transactions can increase conflict opportunity, snapshot/version retention, resource lifetime, and operational latency. Detailed transaction administration belongs in Chapter 4.

## 10. Waiting Does Not Mean Deadlock

A waiting operation is not automatically deadlocked. MongoDB can report deadlocks encountered during lock acquisition through evidence such as `deadlockCount`.

Distinguish ordinary lock waiting, sustained lock contention, and actual deadlock evidence.

## 11. Concurrency Observability

Production concurrency diagnosis requires multiple evidence sources.

```text
Application Latency
        │
        ▼
$currentOp
        │
        ├── waitingForLock
        ├── locks
        ├── lockStats
        ├── waitingForFlowControl
        └── flowControlStats
        │
        ▼
serverStatus
        │
        ├── locks
        ├── globalLock
        └── queues.execution [MongoDB 8.x]
        │
        ▼
WiredTiger / Query / Replication
        │
        ▼
CPU / Storage / Infrastructure
```

No single metric should be used to diagnose a concurrency incident in isolation.

## 12. `$currentOp` Evidence

Representative fields include:

```text
waitingForLock
locks
lockStats
waitingForFlowControl
flowControlStats
```

`waitingForLock` and `waitingForFlowControl` describe different conditions. Detailed `$currentOp` administration belongs in Chapter 7.

## 13. Lock Metrics

MongoDB exposes lock statistics through `serverStatus().locks`.

Important fields include:

```text
acquireCount
acquireWaitCount
timeAcquiringMicros
deadlockCount
```

| Metric | Interpretation |
|---|---|
| `acquireCount` | Number of lock acquisitions |
| `acquireWaitCount` | Acquisitions that required waiting |
| `timeAcquiringMicros` | Cumulative acquisition wait time |
| `deadlockCount` | Deadlocks encountered during acquisition |

A high `acquireCount` does not itself mean contention.

When `acquireWaitCount > 0`, a useful approximation is:

```text
Approximate Average Lock Wait
=
timeAcquiringMicros / acquireWaitCount
```

Interpret it alongside workload and latency.

## 14. Counters vs. Rates

Many concurrency statistics are cumulative. A large lifetime counter does not prove a current incident.

```text
Rate = Δcounter / Δtime
```

Correlate rates with workload volume, application latency, operation type, query behavior, CPU, storage, cache, and replication state.

## 15. Global Lock Statistics

Do not interpret the term global lock as meaning MongoDB serializes all operations behind one exclusive instance-wide lock.

```text
Global Lock Statistic ≠ Entire Server Blocked
```

`globalLock.currentQueue` can provide information about operations queued while waiting for locks, but a small queue of short-lived operations is not automatically an incident.

## 16. Execution Queues

MongoDB also manages storage-engine execution capacity. MongoDB 8.0 introduced `serverStatus().queues.execution` for observing operations waiting to be scheduled for storage-engine execution.

Representative evidence can include queue length, queued time, currently processing work, available capacity, and total execution capacity.

Starting with MongoDB 7.0, the default storage-engine transaction-ticket behavior dynamically adjusts concurrency to optimize throughput under workload pressure.

> **Production Rule:** Low or zero available execution tickets alone does not establish overload on MongoDB 7.0+.

Persistent queueing, increasing queue wait, and application latency provide stronger evidence.

## 17. Lock Waiting vs. Execution Queueing

Locks and execution queues solve different problems.

```text
Lock Wait ≠ Execution Queue
```

A lock wait means an incompatible resource lock prevents progress. Execution queueing means an operation is waiting to be scheduled for storage-engine execution. Their remediation can be completely different.

## 18. Flow Control and Other Wait Sources

Replica-set write latency can also be affected by MongoDB flow control.

```text
Primary Writes
      │
      ▼
Replication Sustainability
      │
      ▼
Flow Control
      │
      ▼
Write Latency
```

Flow-control waiting is not lock waiting. `$currentOp` can expose `waitingForFlowControl` and `flowControlStats`.

Replica-set writes also interact with replication and oplog coordination, so write latency should not be interpreted solely through collection-level locking. Connection pressure and version-specific ingress/admission mechanisms can create additional sources of delay and should not automatically be diagnosed as lock contention.

## 19. Production Failure Patterns

### Pattern 1 — Hot Document / Write Conflicts

Many writers targeting the same document can increase write conflicts, retries, and latency. Investigate hot-key access patterns, update frequency, application design, conflict rate, and latency.

### Pattern 2 — Blocking Administrative / DDL Operation

Administrative or DDL work can require stronger coordination and cause temporary concurrent waiting. Investigate operation type, namespace, lock mode, duration, and workload timing.

### Pattern 3 — Transaction Lock Contention

A transaction that cannot acquire required locks can wait and then abort. Investigate transaction duration, touched namespaces, conflicting operations, write conflicts, and application transaction design.

### Pattern 4 — Storage Bottleneck Appears as Locking

Storage latency can extend operation duration and resource occupancy, which may increase waiting. The root cause may be storage rather than MongoDB locking.

### Pattern 5 — CPU Saturation / Concurrency Backlog

CPU saturation can slow operation progress and create backlog and latency without lock-manager contention.

### Pattern 6 — Persistent Execution Queueing

Persistent execution queues can indicate demand exceeding available execution capacity. Correlate queue length and wait time with CPU, storage, WiredTiger cache, workload concurrency, and query efficiency.

### Pattern 7 — Flow Control Mistaken for Locking

Replication pressure can activate flow control and increase write latency. Check flow-control evidence before treating collection locks as the root cause.

## 20. Concurrency Troubleshooting

Use the following diagnostic workflow:

```text
Latency / Throughput Problem
          │
          ▼
$currentOp + serverStatus
          │
          ▼
Where Is Waiting Occurring?
          │
   ┌──────┼──────────┬────────────┐
   ▼      ▼          ▼            ▼
 Lock   Execution   Flow        Neither
 Wait    Queue      Control
   │      │          │            │
   ▼      ▼          ▼            ▼
Blocker  Capacity  Replication   Query /
Context  Context    Context      CPU /
                                Storage
          │
          ▼
       Root Cause
```

Do not assume a slow MongoDB workload must be a locking problem.

## 21. Lock-Specific Troubleshooting

Once actual lock waiting is confirmed:

```text
Waiting Operation
       │
       ▼
Identify Namespace
       │
       ▼
Identify Requested Lock
       │
       ▼
Identify Conflicting Work
       │
       ▼
Why Is the Blocker Long-Lived?
       │
       ├── Query
       ├── Transaction
       ├── DDL / Administration
       └── Underlying Resource
```

> **Production Rule:** The blocker is often more important than the waiter.

Killing waiting operations without identifying the blocker may provide little benefit.

## 22. Evidence Collection

Collect evidence before invasive intervention whenever operationally safe.

### Application / Workload

Capture latency, throughput, operation mix, workload changes, and hot-key behavior.

### MongoDB

Capture `$currentOp`, `serverStatus()`, `serverStatus().locks`, `serverStatus().globalLock`, `serverStatus().queues.execution` on MongoDB 8.x, logs, active operation runtime, namespaces, and waiting state.

### Query / Transaction

Capture namespace, operation/query shape, runtime, explain evidence where appropriate, transaction/session context, and conflict/abort evidence.

### WiredTiger

Capture write conflicts, cache pressure, execution-queue evidence, and relevant storage-engine metrics.

### OS / Infrastructure

Capture CPU, memory, disk latency, IOPS, throughput, queue depth, filesystem problems, and cloud-volume throttling.

Correlate evidence by timestamp.

## 23. Safe Operation Termination

Before terminating an operation, determine what it is doing, how long it has run, whether it is waiting or blocking, which namespace it affects, whether it is making progress, application retry behavior, transaction implications, and business impact.

> **Production Rule:** Collect enough evidence to identify the operation and likely root cause before terminating it whenever operationally safe.

Killing a waiter without addressing the blocker or constrained resource may not resolve the incident. Detailed operation termination belongs in Chapter 7.

## 24. Monitoring and Alerting Strategy

A production concurrency monitoring model should correlate application latency and throughput with `$currentOp`, locks and waits, execution queues, flow control, WiredTiger, CPU, storage, and replication.

Avoid simplistic alerts based only on `acquireCount` or the existence of any waiting operation. Prefer sustained waiting plus increasing wait time plus application impact. Thresholds should be established from workload baselines rather than universal values.

## 25. Production Anti-Patterns

Avoid:

- assuming MongoDB uses one giant global lock;
- assuming global-lock statistics mean the whole server is blocked;
- assuming every slow operation is lock contention;
- assuming every waiting operation is a deadlock;
- treating every write conflict as an incident;
- using `acquireCount` alone as a contention metric;
- ignoring `acquireWaitCount`;
- treating `available == 0` execution tickets as automatic overload on MongoDB 7.0+;
- confusing lock waits with execution queueing;
- treating `waitingForFlowControl` as lock waiting;
- confusing connection pressure with lock contention;
- ignoring hot-document access patterns, query design, storage latency, or CPU saturation;
- blindly increasing execution concurrency;
- killing operations before collecting evidence;
- allowing unnecessarily long transactions;
- scheduling high-impact DDL during peak workload without assessment;
- defining universal lock thresholds; and
- changing multiple concurrency parameters simultaneously during an incident.

## 27. Key DBA Takeaways

1. MongoDB concurrency combines MongoDB locking with WiredTiger concurrency.
2. MongoDB uses multi-granularity locking across global, database, and collection resources.
3. Intent locks do not imply exclusive database or collection blocking.
4. `IS`, `IX`, `S`, and `X` map operationally to monitoring symbols `r`, `w`, `R`, and `W`.
5. WiredTiger provides document-level write concurrency and optimistic concurrency for most reads and writes.
6. Occasional write conflicts are not automatically incidents, but hot documents can create genuine concurrency bottlenecks.
7. Lock waiting is normal until it becomes sustained or materially affects the workload.
8. A waiting operation is not automatically deadlocked.
9. Storage latency and CPU saturation can produce apparent concurrency problems without lock-manager contention.
10. DDL and administrative operations can require stronger coordination, and online operations can still have production impact.
11. Long transactions can increase concurrency and resource pressure.
12. `$currentOp` and `serverStatus().locks` provide important active-operation and cumulative lock evidence.
13. `acquireWaitCount` and `timeAcquiringMicros` are more informative about waiting than `acquireCount` alone.
14. MongoDB 8.0 introduced `serverStatus().queues.execution`.
15. MongoDB 7.0+ dynamically manages storage-engine transaction-ticket concurrency by default.
16. Zero available execution tickets alone does not prove overload.
17. Lock waiting, execution queueing, and flow-control waiting are different conditions.
18. The blocker is often more important than the waiter.
19. Collect lock, queue, query, CPU, storage, and replication evidence before tuning or terminating operations.
