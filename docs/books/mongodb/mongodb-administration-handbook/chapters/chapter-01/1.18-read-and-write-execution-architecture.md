# 1.18 — Read and Write Execution Architecture

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 1:** MongoDB Architecture and Internals  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to:

- trace MongoDB reads and writes from application request to response;
- separate driver, network, server, storage, replication, and acknowledgement latency;
- explain MongoDB read execution at an administrator level;
- understand query planning, plan-cache, index, collection, cursor, and storage interactions;
- explain MongoDB write execution without treating journal, checkpoint, replication, and acknowledgement as one serial pipeline;
- distinguish read preference, read concern, and write concern;
- understand MongoDB 8.x majority-write acknowledgement semantics;
- explain targeted and broadcast operations in sharded clusters;
- identify common production read/write bottlenecks; and
- troubleshoot slow reads and writes using end-to-end evidence.

## 1. End-to-End Execution Architecture

A MongoDB operation crosses several architectural layers before the application receives its result.

```text
Application
    │
    ▼
MongoDB Driver
    │
    ▼
Server Selection / Connection
    │
    ▼
Network
    │
    ▼
mongod / mongos
    │
    ▼
Command / Query Execution
    │
    ▼
Concurrency Coordination
    │
    ▼
WiredTiger
    │
    ├── Cache
    ├── Index / Data
    ├── Journal / Durability
    └── Persistent Storage
    │
    ▼
Replication / Acknowledgement
    │
    ▼
Response
```

Not every operation traverses every component in exactly the same way. Reads, writes, transactions, replica-set operations, and sharded operations introduce different paths.

> **Production Rule:** Application latency is not equivalent to MongoDB server execution time.

End-to-end latency can include server selection, connection acquisition, networking, query or write execution, storage access, replication, acknowledgement requirements, result transfer, and application-side processing.

## 2. Driver, Connection, and Command Reception

Before MongoDB executes an operation, the driver selects an appropriate server and obtains a usable connection.

```text
Application
     │
     ▼
Driver
     │
     ▼
Topology / Server Selection
     │
     ▼
Connection Pool
     │
     ▼
Network
     │
     ▼
MongoDB Server
```

Depending on topology and operation, selection can consider primary/secondary state, read preference, topology discovery, server availability, latency, and session or transaction requirements.

A useful model is:

```text
End-to-End Latency
       =
Server Selection
       +
Connection Acquisition
       +
Network
       +
MongoDB Execution
       +
Response Transfer
```

Server-selection failures, pool exhaustion, DNS problems, or network latency can therefore appear as database latency even when query execution is healthy. Detailed connection architecture is covered in Sections 1.8–1.12.

## 3. Read Execution Architecture

A high-level read path is:

```text
Client Read
    │
    ▼
Driver / Server Selection
    │
    ▼
MongoDB Command
    │
    ▼
Query Planning / Plan Cache
    │
    ▼
Execution Plan
    │
    ▼
Index / Collection Access
    │
    ▼
WiredTiger Cache
    │
    ├── Resident
    │
    └── Storage Access
    │
    ▼
Cursor / Batch
    │
    ▼
Client
```

Read performance can depend on query shape, execution plan, index suitability, keys/documents examined, working-set locality, cache behavior, storage latency, sorting or aggregation, concurrency, result size, cursor batching, and network latency.

## 4. Query Planning, Plan Cache, and `explain()`

For queries requiring planning, MongoDB determines an execution plan using mechanisms appropriate to the query and server version.

```text
Query
  │
  ▼
Query Shape
  │
  ▼
Plan Selection / Plan Cache
  │
  ▼
Execution
```

Execution can involve index scans, collection scans, document fetches, sorting, filtering, aggregation stages, and other stages appropriate to the operation. The plan cache can allow reuse of previously selected plans for matching query shapes. MongoDB 8.x also provides query settings for supported query shapes; detailed administration belongs in Chapter 7.

`explain()` is essential diagnostic evidence, but it should not be treated as a perfect replay of an application's existing cached execution path. For an explained operation, MongoDB does not simply use an existing plan-cache entry as ordinary application execution would.

## 5. Index, Collection, Cache, and Storage Access

MongoDB can obtain required data through different access paths.

```text
Query
  │
  ├── Index-Assisted Access
  │       │
  │       ▼
  │    Matching Keys
  │       │
  │       ▼
  │    Document Fetch if Required
  │
  └── Collection Access
          │
          ▼
       Documents Examined
```

Important rules are:

```text
Index Used ≠ Query Automatically Efficient
COLLSCAN ≠ Automatically Wrong
Index Used ≠ No Document Fetch
```

A collection scan can be reasonable for small collections, queries returning much of a collection, or certain administrative and analytical workloads. The correct DBA question is whether the access path is appropriate for the workload and result set.

Required pages can already be resident in the WiredTiger cache or require storage access.

```text
Required Page
     │
     ▼
WiredTiger Cache
     │
 ┌───┴──────────┐
 ▼              ▼
Resident     Not Resident
 │              │
 ▼              ▼
Use         Storage Access
```

Do not reduce this to one document read equaling one disk read. WiredTiger operates through storage-engine pages and cache structures. Cache misses are normal; they become operationally important when the access pattern produces sustained storage demand and material latency.

## 6. Cursor and Batch Execution

Many reads return results through cursors.

```text
Initial Query
     │
     ▼
Initial Batch
     │
     ▼
Cursor
     │
     ├── getMore
     ├── getMore
     └── getMore
```

A user-visible query can span multiple MongoDB requests. Large results can therefore create costs from initial execution, subsequent `getMore` operations, repeated network transfers, cursor lifetime, and client-side processing.

## 7. Read Preference and Read Concern

| Mechanism | Primary Question |
|---|---|
| Read Preference | Where may the read run? |
| Read Concern | What visibility/consistency semantics are requested? |

Read preference does not itself determine data visibility. Replica-set secondaries replicate asynchronously, so modes permitting secondary reads can return data stale relative to the primary. Changing read preference is therefore not merely a performance-routing decision. Transactions containing reads have additional routing constraints; detailed behavior belongs in Chapter 4.

## 8. Write Execution Architecture

A conceptual write path is:

```text
Client Write
     │
     ▼
Driver / Target Selection
     │
     ▼
MongoDB Command
     │
     ▼
Locate / Validate Target
     │
     ▼
Concurrency Coordination
     │
     ▼
MongoDB + WiredTiger Modification
     │
     ├── Document State
     ├── Index State
     ├── Journal / Durability
     └── Replica-Set Oplog
               │
               ▼
        Secondary Replication
               │
               ▼
      Write Concern Condition
               │
               ▼
       Client Acknowledgement
```

Journal activity, checkpoint activity, oplog processing, secondary replication, and acknowledgement should not be interpreted as one universally serialized pipeline. The exact path depends on operation type, topology, indexes, write concern, journaling, transactions, and sharding.

## 9. Target Lookup and Index Maintenance

Updates and deletes can first require MongoDB to locate matching documents.

```text
Update / Delete
      │
      ▼
Query Predicate
      │
      ▼
Access Path
      │
      ▼
Target Document
      │
      ▼
Modification
```

A slow update can therefore be a slow query followed by a write.

A write can modify both document and index state.

```text
Document Modification
        │
        ├── Data
        ├── Index A
        ├── Index B
        └── Index C
```

Indexes can improve reads while increasing write-side maintenance cost. Additional or low-value indexes can consume CPU, memory/cache, storage capacity, storage I/O, and index-maintenance work.

## 10. WiredTiger, Journal, and Checkpoint Interaction

Writes primarily modify storage-engine state rather than synchronously writing every changed page directly to its final data-file location before acknowledgement.

```text
Write
  │
  ▼
WiredTiger Modified State
  │
  ├── Journal / Recovery Path
  │
  └── Checkpoint / Data-File Path
```

```text
Journal ≠ Checkpoint
```

The journal supports durability and crash recovery between checkpoints. Checkpoints establish consistent storage-engine recovery points in persistent data files. Detailed behavior is covered in Sections 1.15 and 1.16.

## 11. Oplog and Replication Execution

For a replica-set primary, write processing also participates in replication.

```text
Client Write
     │
     ▼
Primary
     │
     ├── Database Modification
     └── Oplog Record
             │
             ▼
       Secondary Members
             │
             ▼
       Copy Oplog Entry
             │
             ▼
        Apply Operation
```

Secondary members replicate the primary's oplog and apply operations to their own data.

```text
Write Executed
      ≠
Write Acknowledged
      ≠
Applied Everywhere
```

The acknowledgement point depends on effective write concern and version-specific acknowledgement semantics.

## 12. Write Concern and MongoDB 8.x Majority Semantics

Write concern defines acknowledgement conditions.

```text
Write Concern
      │
      ├── Acknowledgement / replication requirement
      ├── Journal requirement where applicable
      └── Timeout behavior
```

The effective policy can be determined by the operation and deployment configuration. DBAs should verify it rather than assume it.

### MongoDB 8.0 Majority Acknowledgement

MongoDB 8.0 introduced an important change to `{ w: "majority" }` acknowledgement semantics. At a high level, a majority write can be acknowledged after the required majority of data-bearing replica-set members have durably written the corresponding oplog entry. Secondary application of that operation to the user collection can proceed asynchronously.

```text
Majority Acknowledged
        ≠
Applied to User Collection
on Every Acknowledging Secondary
```

This distinction matters when an application performs a majority write and then immediately reads from a secondary. Applications requiring specific immediate post-write visibility semantics need an appropriate consistency design, potentially including session and causal-consistency mechanisms. Detailed implementation belongs in Chapter 4.

## 13. Read and Write Semantic Boundaries

| Mechanism | Primary Question |
|---|---|
| Read Preference | Where may the read run? |
| Read Concern | What read visibility/consistency semantics are requested? |
| Write Concern | What acknowledgement conditions must the write satisfy? |

Do not treat these as interchangeable consistency settings.

```text
Acknowledged ≠ Applied Everywhere
Acknowledged ≠ Every Possible Durability Guarantee
```

The meaning of acknowledgement depends on topology, write concern, journaling, and transaction context.

## 14. Concurrency and Execution Queueing

A slow operation can be waiting for very different reasons.

```text
Slow Operation
     │
     ├── Lock Wait?
     ├── Execution Queue?
     ├── Flow Control?
     ├── Query Execution?
     ├── Cache / Storage?
     └── CPU?
```

These conditions should not be conflated. MongoDB 8.x provides execution-queue observability separately from lock evidence. Flow-control waiting is also distinct from lock waiting and relates to replica-set replication sustainability. Detailed concurrency architecture is covered in Section 1.17.

## 15. Sharded Read and Write Execution

Applications communicate with sharded clusters through `mongos`.

```text
Client
  │
  ▼
mongos
  │
  ├── Targeted Operation
  │       └── One / Subset of Shards
  │
  └── Broadcast Operation
          └── All Relevant Shards
```

Multi-shard reads can require distributed work and result merging, so latency can include shard-local execution, network communication, and merge cost.

Writes also use routing metadata.

```text
Client Write
     │
     ▼
mongos
     │
     ▼
Routing Metadata
     │
     ├── Targeted Shard(s)
     └── Multi-Shard / Broadcast when required
```

Do not assume every sharded write targets exactly one shard. Required shards depend on operation type and shard-key targeting information. Shard-key design influences targeting, distribution, write concentration, hot shards, and scalability. Detailed administration belongs in Chapter 11.

## 16. Transaction Execution Boundaries

Transactions introduce additional execution state.

```text
Client
  │
  ▼
Session
  │
  ▼
Transaction
  │
  ├── Read
  ├── Write
  ├── Read
  └── Write
       │
       ▼
Commit / Abort
```

Transaction execution can interact with snapshot state, locking, write conflicts, read concern, write concern, replication, and multiple shards. Detailed administration belongs in Chapter 4.

## 17. Production Failure Patterns

### 17.1 Poor Read Access Path

Poor plans or access paths can increase keys/documents examined, CPU, cache demand, storage work, and latency. Investigate query shape, plan, cardinality, and index suitability.

### 17.2 Cache / Storage Pressure

Insufficient cache residency for the active access pattern can increase storage demand and latency. A dataset larger than cache is not automatically unhealthy; locality and actual demand matter.

### 17.3 Large Result Set / Cursor Amplification

Large results can require multiple batches, `getMore` calls, network transfer, and client processing.

### 17.4 Excess Write-Side Index Maintenance

Writes touching many indexes can increase CPU, cache, and storage work. Investigate index value before removal.

### 17.5 Hot Document / Write Conflict

Many writers targeting the same data can increase conflicts, retries, and latency. The root cause may be application or data-model design rather than infrastructure capacity.

### 17.6 Storage Saturation

Write workloads can increase cache, journal, checkpoint, and storage pressure. Investigate latency, IOPS, throughput, queue depth, WiredTiger behavior, and cloud-volume limits.

### 17.7 Replication / Flow-Control Pressure

Replication lag pressure can activate flow control and affect primary throughput/write latency. Do not diagnose this automatically as locking.

### 17.8 Acknowledgement-Policy Latency

Higher acknowledgement latency does not automatically indicate an unhealthy server; it can reflect the requested replication/durability contract.

### 17.9 Sharded Broadcast Amplification

Multi-shard operations can introduce distributed work, coordination, and merge costs. Investigate shard targeting before treating each shard independently.

## 20. Evidence Collection

### Application / Driver

Capture application latency, operation type, selected server, topology state, effective read preference, connection-pool waiting, timeout behavior, and retry behavior.

### MongoDB Operation

Capture namespace, command/query shape, operation duration, `$currentOp`, profiler or slow-operation evidence where appropriate, and cursor/`getMore` activity.

### Query / Access Path

Capture execution plan, plan-cache context, keys examined, documents examined, returned documents, and sort/aggregation behavior.

### WiredTiger / Storage

Capture cache pressure, read/write activity, write conflicts, execution queues, checkpoint evidence, storage latency, IOPS, throughput, and queue depth.

### Replication / Write Semantics

Capture replica-set state, replication lag, flow-control evidence, effective write concern, journal requirement where relevant, and acknowledgement latency.

### Sharding

Capture router context, targeted shards, targeted vs. broadcast execution, merge behavior, and shard distribution when relevant.

Correlate evidence by timestamp.

## 21. Monitoring and Alerting Strategy

A production monitoring hierarchy should follow the execution path:

```text
Application
    │
    ▼
Driver / Network
    │
    ▼
MongoDB Operation
    │
    ▼
Query / Write Execution
    │
    ▼
Concurrency
    │
    ▼
WiredTiger
    │
    ▼
Replication / Sharding
    │
    ▼
CPU / Storage / Network
```

Alerting should emphasize sustained workload impact rather than isolated counters or events. Useful signals include application latency, operation duration, query efficiency, cursor behavior, execution queues, lock waits, write conflicts, cache pressure, storage latency, replication lag, flow control, acknowledgement latency, and shard targeting. Thresholds should be derived from workload baselines rather than universal values.

## 22. Production Anti-Patterns

Avoid:

- assuming application latency equals MongoDB execution time;
- assuming every read must use an index;
- assuming `COLLSCAN` is automatically wrong;
- assuming index usage guarantees an efficient query or no document fetch;
- assuming `explain()` perfectly reproduces an application's existing cached execution path;
- ignoring cursor and `getMore` behavior;
- treating read preference as read consistency;
- treating read preference and read concern as interchangeable;
- treating write concern and durability as interchangeable;
- assuming acknowledgement means a write has been applied everywhere;
- assuming MongoDB 8.x majority acknowledgement means every acknowledging secondary has already applied the user-document change;
- assuming application writes go directly to final data files;
- confusing journal and checkpoint responsibilities;
- assuming slow writes are always storage or lock problems;
- ignoring target lookup cost, index-maintenance cost, hot-document contention, execution queueing, or flow control;
- assuming every sharded operation targets one shard;
- assuming a working set larger than WiredTiger cache automatically means the workload is unhealthy;
- changing read/write concern merely to hide latency;
- dropping indexes without workload analysis; and
- scaling hardware before locating the constrained layer.

## 24. Key DBA Takeaways

1. MongoDB read/write execution is an end-to-end path, not simply client-to-disk activity.
2. Application latency is not equivalent to MongoDB server execution time.
3. Driver server selection and connection acquisition occur before command execution.
4. Reads can use indexes, collection scans, or more complex execution paths.
5. Index usage does not automatically mean a query is efficient, and a collection scan is not automatically wrong.
6. `explain()` is diagnostic evidence but does not simply replay an existing cached application plan.
7. WiredTiger cache residency and access locality strongly influence read behavior.
8. A user-visible query can span multiple cursor batches and `getMore` operations.
9. Read preference determines eligible routing targets; read concern addresses a different semantic dimension.
10. Secondary reads can return stale data because replication is asynchronous.
11. Updates and deletes can spend substantial time locating targets before modification.
12. Writes can modify both document and index state; additional indexes can increase write-side maintenance cost.
13. Journal and checkpoint responsibilities are different.
14. Replica-set writes create oplog state that secondaries copy and apply.
15. Write execution, acknowledgement, and application on all replica-set members are different milestones.
16. Write concern defines acknowledgement conditions.
17. MongoDB 8.x majority acknowledgement does not necessarily mean the user-document change has already been applied on every acknowledging secondary.
18. Read preference, read concern, and write concern solve different problems.
19. Lock waiting, execution queueing, and flow-control waiting are different conditions.
20. Sharded operations can be targeted or broadcast, and multi-shard execution can introduce distributed work and merge cost.
21. Transactions add snapshot, concurrency, replication, and commit/abort context.
22. Production troubleshooting should locate the constrained execution layer before configuration or capacity changes.
