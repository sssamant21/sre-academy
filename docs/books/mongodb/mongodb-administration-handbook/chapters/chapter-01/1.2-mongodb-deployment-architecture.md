## Learning Objectives

After completing this section, you should be able to distinguish standalone, replica-set, and sharded-cluster deployments; explain how `mongod`, `mongos`, replica-set members, shards, and the configuration role fit into each topology; explain quorum, voting majority, data redundancy, and failure domains; distinguish high availability from horizontal scaling; understand MongoDB 8.0 config-shard architecture; identify DNS and network dependencies; understand how topology affects connectivity, maintenance, backup, monitoring, and recovery; recognize common production anti-patterns; and evaluate a topology against production requirements.

## Deployment Architecture Overview

MongoDB supports three fundamental deployment architectures: standalone, replica set, and sharded cluster. Standalone prioritizes simplicity, replica sets provide redundancy and high availability, and sharded clusters provide horizontal distribution together with replica-set-based availability.

Topology affects application connectivity, availability, maintenance, monitoring, backup and restore, capacity planning, upgrades, security, incident response, disaster recovery, and cost. It should therefore be treated as an architectural decision rather than merely an installation option.

## Standalone Architecture

A standalone deployment consists of a single `mongod` process. It provides no MongoDB-level redundancy. Failure of `mongod`, the host, storage, network path, or maintenance of the server can make the database unavailable.

Standalone deployments can be appropriate for development, testing, training, proof-of-concept environments, temporary systems, specialized administrative operations, and workloads where database-level availability is not required.

A small dataset does not automatically justify a standalone production database. The architectural question is whether the required service can tolerate the MongoDB server becoming unavailable. If not, a replica-set architecture should normally be evaluated.

## Replica Set Architecture

A replica set is a group of `mongod` processes that maintain copies of the same dataset. A common production topology uses three data-bearing voting members: one primary and two secondaries. For typical self-managed production environments, data-bearing voting members are preferred, subject to workload, geographic, durability, latency, and availability requirements.

### Primary and Secondary Roles

In normal replica-set operation, the primary receives write operations. Reads default to the primary, while configured read preferences can allow eligible reads from other members. Secondaries replicate the replica set's operation history and maintain copies of the dataset.

Replica-set members primarily provide redundancy and topology options; adding members does not automatically multiply write throughput.

### Failover

If the primary becomes unavailable, eligible voting members can participate in an election. The simplified sequence is failure detection → election → new primary selection → driver topology discovery → application recovery. Automatic election does not mean zero-duration or interruption-free failover, so applications and drivers must tolerate appropriate transient failures.

### Voting Majority

Replica-set availability depends heavily on the ability of voting members to communicate and maintain the required majority. Three voting members require a majority of two; five require three. A replica set can contain more members than can participate in voting, and MongoDB limits the number of voting members to seven.

Replica-set availability therefore depends on quorum architecture and connectivity, not merely on the number of running MongoDB processes.

### Quorum vs. Data Redundancy

Quorum and data redundancy are related but different properties. A primary-secondary-secondary topology has three data-bearing members, whereas a primary-secondary-arbiter topology has only two data-bearing members even though three participants can vote.

Resilience depends on voting/quorum, data redundancy, network connectivity, and failure-domain placement together.

### Failure Domains

Production members should be distributed according to the failures the architecture is expected to survive. Failure domains can include physical hosts, hypervisors, racks, power domains, network segments, availability zones, data centers, and geographic regions.

Three `mongod` processes on the same physical infrastructure do not provide the same resilience as members distributed across independent failure domains. Place voting members so that loss of an expected failure domain does not unnecessarily remove the majority required to maintain the intended service level.

### Network Partitions

During a network partition, database availability is determined by voting membership, connectivity, topology state, and election behavior rather than simply whether each `mongod` process remains running. Connected members may elect a primary when election requirements are satisfied. This is one reason MongoDB must be administered as a distributed system.

### Arbiter Considerations

An arbiter participates in replica-set elections but does not maintain application data. Prefer data-bearing voting members for new production architectures when practical. Use an arbiter only after its architectural tradeoffs have been explicitly evaluated and justified. An arbiter should not be treated as an inexpensive substitute for another data-bearing member.

## DNS and Inter-Node Connectivity

Distributed MongoDB architecture depends on stable hostnames, reliable DNS, required network paths, firewall and security rules, TLS identity, and appropriate latency. Production deployments should use stable hostname-based identities and reliable name resolution.

A logically correct database topology can still fail when DNS, routing, firewall rules, TLS identity, or network latency prevents members and clients from communicating correctly. Application-to-database connectivity must also be considered separately from inter-node connectivity.

## Sharded Cluster Architecture

Replica sets provide redundancy but do not horizontally partition a dataset across independent shards. MongoDB uses sharding when data or workload must be distributed horizontally. Each shard is deployed as a replica set.

For MongoDB 8.x, a sharded cluster consists of `mongos` query routers, replica-set shards, and a configuration role implemented by either a dedicated config server replica set or a config shard introduced in MongoDB 8.0.

### `mongos` Query Routers

`mongos` provides the routing layer between applications and the sharded cluster. Applications should use `mongos` for normal cluster-level operations rather than directly targeting individual shards. Direct shard access should be limited to specifically supported administrative or maintenance scenarios.

### Shards

Shards store application data and each shard is deployed as a replica set. A sharded cluster therefore combines replica sets for redundancy/high availability with sharding for horizontal distribution. Administrators must monitor both individual shard replica sets and the cluster as a distributed whole.

### Configuration Role

Sharded clusters require configuration metadata describing cluster state and data placement. Traditionally this function is provided by a dedicated config server replica set. MongoDB 8.0 also allows the configuration role to coexist with application-data shard functionality through a config shard.

Administrators working with MongoDB 8.x should therefore explicitly document whether a sharded cluster uses a dedicated config server replica set or a config shard. Config-server replica sets have topology-specific requirements and should not simply be treated as arbitrary application replica sets.

If the configuration-role primary becomes unavailable and no replacement can be elected, configuration metadata can become read-only and metadata-changing operations can be restricted. Complete loss of configuration functionality can significantly affect cluster operation. Detailed recovery is covered in the sharding administration chapters.

### Shard-Key Architecture

MongoDB distributes sharded data according to a collection's shard key. Shard-key design influences data distribution, write distribution, query routing, hotspots, scalability, and operational flexibility. A poor shard key can create a large cluster in which most work remains concentrated on a small subset of infrastructure.

Not every collection in a sharded cluster must itself be sharded. Modern MongoDB deployments can also use placement of unsharded collections to organize workloads and resource usage.

## When to Evaluate Sharding

Sharding should not be the first response to every performance problem. First determine whether an appropriately sized and optimized replica set can meet requirements. Investigate query efficiency, index design, schema design, storage performance, hardware sizing, WiredTiger cache behavior, application access patterns, and capacity constraints before introducing sharding.

If one replica set cannot meet requirements, evaluate sharding and validate shard-key design, distribution behavior, routing, configuration architecture, backup, monitoring, disaster recovery, and operational complexity.

## `mongos` Redundancy

Production architectures should avoid making a single query router an unnecessary point of failure. Application connectivity should be designed so that loss of an individual `mongos` process does not unnecessarily make the database service inaccessible.

## Deployment Architecture and Application Connectivity

Standalone applications connect to a `mongod`. Replica-set clients use topology-aware connection information so the driver can discover members and perform server selection. Sharded-cluster clients normally connect through `mongos` routers. Incorrect connection configuration can undermine an otherwise resilient database architecture.

## Deployment Architecture and Maintenance

Stopping a standalone `mongod` normally makes that database unavailable. Healthy replica sets can allow many maintenance operations to proceed incrementally, typically maintaining a secondary, returning and validating it, and then proceeding to another member.

Rolling maintenance is not risk-free. Administrators must verify member state, replication health, lag, voting majority, application health, storage health, and rollback criteria throughout the operation.

## Deployment Architecture and Backup

Backup procedures must understand topology. Standalone, replica-set, and sharded-cluster backup strategies have different consistency and coordination requirements. A procedure appropriate for a standalone database should not automatically be assumed safe for a distributed sharded cluster.

Replication is not a replacement for backup.

## Deployment Architecture and Monitoring

Standalone monitoring should cover `mongod`, OS resources, storage, queries, and connections. Replica-set monitoring adds member states, replication lag, oplog health, elections, heartbeat/connectivity, and majority availability. Sharded-cluster monitoring additionally covers `mongos`, the configuration role, shard health, replica-set health per shard, data distribution, balancer activity, shard capacity, and routing behavior.

Monitoring must reflect the architecture actually deployed.

## Production Reference Architecture — Replica Set

A production replica set should combine appropriate failure-domain separation, data-bearing redundancy, suitable voting configuration, reliable DNS/networking, adequate storage, independent backup, monitoring, security controls, and tested recovery procedures.

## Production Reference Architecture — Sharded Cluster

A production sharded architecture should use redundant application routing, replica-set shards with deliberate failure-domain strategies, and an explicitly selected configuration-role architecture: dedicated config server replica set or MongoDB 8.0+ config shard. Availability must be evaluated at every layer rather than merely by counting shards.

## Architecture Selection Framework

Start by determining whether database-level redundancy is required. If not, standalone may be acceptable. If redundancy is required, determine whether an appropriately sized and optimized replica set can satisfy workload requirements. If it can, use a replica-set architecture. If it cannot, evaluate sharding and validate shard key, distribution, routing, configuration role, backup, monitoring, disaster recovery, and operational complexity.

Real production decisions should also consider availability objectives, RPO, RTO, dataset size, growth rate, working-set size, read/write throughput, latency, geography, maintenance, backup/restore, security, operational skills, and cost.

## Architecture Anti-Patterns

Avoid single `mongod` deployments when HA is required; placing all replica members in one failure domain; treating primary-secondary-arbiter as three data copies; using sharding to compensate for poor query/index/schema design; normal application connections directly to individual shards; treating replicas as backups; making one `mongos` an avoidable dependency; and declaring a topology highly available without testing failover behavior.

An HA topology without failure testing is unverified HA.

## DBA Production Architecture Checklist

Before approving production architecture, verify:

- deployment type, availability requirements, RPO, and RTO are documented;
- replica-set topology and voting architecture are understood;
- quorum and data redundancy are evaluated separately;
- expected failure domains are documented and members appropriately distributed;
- DNS, stable hostnames, required network paths, firewall/security rules, and TLS identity are validated;
- majority behavior, primary failover, and application-driver failover are tested;
- shard architecture and shard-key strategy are reviewed where applicable;
- `mongos` redundancy is considered;
- configuration-role architecture is documented;
- MongoDB 8.x config-shard vs. dedicated-config-server decision is documented where applicable;
- storage capacity and growth forecasts are adequate;
- backup is independent of replication and restore procedures are tested;
- monitoring covers every topology component;
- security, maintenance, upgrade, and disaster-recovery procedures are documented;
- failure scenarios are tested; and
- architectural assumptions and exceptions are documented.

## Key DBA Takeaways

1. MongoDB supports standalone, replica-set, and sharded-cluster architectures.
2. Standalone MongoDB provides no MongoDB-level high availability.
3. Replica sets provide data redundancy, elections, and high-availability capabilities.
4. Prefer appropriate data-bearing voting members for typical production designs.
5. Replica-set availability depends on voting majority, connectivity, and topology state, not merely server count.
6. Quorum and data redundancy are different properties.
7. Arbiters vote but do not contain application data.
8. Failure-domain design is fundamental to meaningful high availability.
9. DNS, routing, firewall rules, TLS identity, and inter-node connectivity are part of database architecture.
10. Replica sets do not automatically multiply write throughput.
11. Sharding provides horizontal distribution and introduces additional operational complexity.
12. Each shard is deployed as a replica set.
13. `mongos` provides the normal application routing layer for sharded clusters.
14. MongoDB 8.0 supports dedicated config server replica sets and config-shard architecture for the configuration role.
15. Shard-key engineering is fundamental to effective workload distribution.
16. Not every collection in a sharded cluster must itself be sharded.
17. Sharding should not substitute for proper query, index, schema, storage, or capacity engineering.
18. Replication does not replace backup.
19. High availability should be tested rather than assumed.
20. Architecture must ultimately be driven by business availability, RPO/RTO, workload, growth, failure domains, operations, security, and cost.
