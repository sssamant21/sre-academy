- explain why MongoDB uses sharding;
- distinguish sharding from replication;
- identify shards, `mongos`, and the config-server role;
- explain MongoDB 8.x config-shard architecture;
- understand shard keys and shard-key ranges;
- distinguish ranged, hashed, and compound shard-key strategies;
- explain targeted and broadcast operations;
- understand data distribution versus workload distribution;
- recognize hot shards and hot ranges;

- understand zones and placement constraints;
- identify sharded-cluster failure domains; and
- troubleshoot sharding using routing, distribution, metadata, replica-set, resource, and application evidence.

## 1. Sharding Architecture and Purpose

MongoDB uses **sharding** to distribute application data horizontally across multiple shards.

```text
                         Applications
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
                 mongos A            mongos B
                    │                   │
                    └─────────┬─────────┘
                              │
                       Query Routing
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
           Shard A         Shard B         Shard C
         Replica Set     Replica Set     Replica Set
              ▲               ▲               ▲
              └───────────────┼───────────────┘
                              │
                       Cluster Metadata
                              │
                              ▼
                     Config Server Role
```

Sharding can help when a workload exceeds the practical capacity of a single replica set in storage, working-set capacity, read/write throughput, data growth, or operational scaling.

**Sharding ≠ Automatic Performance.** A poorly designed shard key or badly distributed workload can produce a large cluster that still concentrates work on a small portion of the infrastructure.

## 2. Sharding vs. Replication

Replication and sharding solve different architectural problems:

```text
Replication → Availability + Redundancy
Sharding    → Horizontal Data Distribution
```

Production MongoDB sharding combines them. Each shard uses replica-set architecture, so a sharded cluster combines horizontal distribution with replica-set availability.

Sharding does not replace replication, and neither sharding nor replication replaces independent backup and recovery.

## 3. Sharded Cluster Components

A MongoDB sharded cluster contains three fundamental architectural roles:

1. **shards**;
2. **`mongos` query routers**;
3. **config-server functionality**.

`mongos` performs routing, coordination, and result merging; shards hold application data; the config-server role maintains critical cluster metadata. MongoDB 8.x adds an important nuance: the replica set providing the config-server role can also participate as a **config shard** and store sharded application data.

## 4. Shards and Replica-Set Architecture

A shard stores a subset of a sharded collection's data. A shard in a supported production sharded-cluster architecture uses a **replica set**.

Each shard therefore has its own primary, secondaries, oplog, elections, replication state, write acknowledgement behavior, and member-level failure domains.

```text
Sharded Write = Routing Decision + Replica-Set Write
```

The replication architecture beneath each shard is covered in **1.19 — Replication Architecture Overview**.

## 5. `mongos` Query Router Architecture

Applications normally access a sharded cluster through `mongos`. It uses cluster metadata and operation predicates to determine which shards must participate.

```text
Application
     │
     ▼
   mongos
     │
     ├── Routing
     ├── Coordination
     └── Result Merging
```

`mongos` is not durable application-data storage. Production environments can use multiple routers for availability, maintenance, and connection distribution.

### Direct-Shard-Access Safety

Applications should normally access a sharded cluster through `mongos`, not directly through individual shard members. Direct shard access can bypass cluster-wide routing semantics, expose only that shard's subset of data, and create serious operational risks when inappropriate administrative or write operations are performed.

## 6. Config Servers and MongoDB 8.x Config Shards

The config-server role maintains critical sharded-cluster metadata, including topology, shards, sharded collections, shard-key ranges, zones, data placement, and routing state.

MongoDB 8.x supports two architectural patterns:

```text
               Config Server Role
                      │
               ┌──────┴──────┐
               ▼             ▼
         Dedicated CSRS   Config Shard
               │             │
            Metadata       Metadata
                            +
                       Sharded User Data
```

A **config shard** allows the replica set providing config-server functionality to also store application data. Therefore the older simplification `Shards = Data; Config Servers = Metadata` is not universally correct for MongoDB 8.x.

Config-server replica sets have additional topology restrictions because they maintain authoritative sharded-cluster metadata. Detailed deployment decisions belong in Chapter 11.

## 7. Cluster Metadata Architecture

`mongos` depends on sharded-cluster metadata to make routing decisions. Data placement can change as balancing, range migration, resharding, or administrative operations occur, so routers require current routing state.

Temporary routing-state refresh conditions are distributed metadata events and should not automatically be interpreted as data corruption.

A useful SRE model is to think in terms of **data plane** and **control plane**, but these are conceptual operational categories rather than strict MongoDB component boundaries. This is especially important with MongoDB 8.x config shards, which can participate in both metadata management and application-data storage.

## 8. Shard-Key Architecture and Quality

A sharded collection uses a **shard key** to help determine data distribution and query routing. The shard key is supported by the appropriate index architecture.

Shard-key design affects data distribution, write distribution, query targeting, hotspot risk, locality, balancing, and scalability.

> **The shard key becomes part of the cluster's physical scaling architecture.**

Important design characteristics include cardinality, value-frequency distribution, monotonicity, query patterns, write patterns, tenant distribution, locality, and zone requirements.

A poor shard key can create hot shards, hot ranges, uneven writes, broadcast queries, and scaling constraints.

> **Adding shards cannot compensate for a shard key that continually directs the dominant workload to the same shard.**

## 9. Ranged, Hashed, and Compound Shard Keys

### Ranged Sharding

Ranged sharding organizes data according to shard-key ranges and can preserve useful value locality. Poorly chosen monotonic access patterns can create hotspot pressure.

### Hashed Sharding

Hashed sharding distributes data according to a hash of the shard-key value. It can improve distribution where raw key values would otherwise concentrate writes, but can reduce natural range locality and make some range-oriented queries less targeted.

### Compound Shard Keys

A shard key can contain multiple fields. Field order matters because it influences routing and distribution behavior.

**Hashed ≠ Always Better. Ranged ≠ Always Better.** Shard-key design must follow the actual workload.

## 10. Shard-Key Ranges and Chunks

MongoDB partitions sharded data into logical **shard-key ranges**, commonly represented and discussed as **chunks**. These are logical distribution units, not replica-set members or physical disk partitions.

Range ownership and placement are represented in cluster metadata. Modern operational discussion should generally think in terms of **ranges** when discussing movement and placement while recognizing the traditional MongoDB term **chunk**.

## 11. Targeted vs. Broadcast Operations

When routing information allows `mongos` to determine the relevant subset of shards, the operation is **targeted**. A shard-key predicate does not necessarily mean exactly one shard; the target set depends on the predicate and current distribution.

When `mongos` cannot sufficiently narrow the target set, it can send the operation to multiple or all relevant shards. This is a **broadcast operation**, commonly understood as a scatter-gather pattern.

Broadcast operations are not automatically incorrect, but frequent broad fan-out can increase CPU, network traffic, shard work, router work, result-merging cost, and latency.

```text
More Shards + Broad Broadcast Queries = Potentially More Distributed Work
```

> **Horizontal scaling can amplify inefficient routing.**

## 12. Read and Write Routing

For reads, `mongos` evaluates routing metadata, determines whether the operation can be targeted or must be broadcast, coordinates the participating shards, and merges results where required.

For writes:

```text
Application Write
       │
       ▼
     mongos
       │
       ▼
Routing Decision
       │
       ▼
Target Shard
       │
       ▼
Shard Primary
       │
       ▼
Replica-Set Write Path
```

Sharding therefore does not remove replication, durability, write-concern, or storage behavior.

## 13. Data Distribution vs. Workload Distribution

A cluster can have balanced storage while having severely unbalanced workload.

```text
             Data       Workload
Shard A      1 TB         80%
Shard B      1 TB         10%
Shard C      1 TB         10%
```

**Balanced Storage ≠ Balanced Workload.**

Capacity analysis should evaluate storage, operations, CPU, memory, WiredTiger cache pressure, disk I/O, network, query latency, tenant concentration, and shard-key access distribution. Aggregate cluster metrics can hide severe shard-level imbalance.

## 14. Hot Shards and Hot Ranges

A **hot shard** receives disproportionately high workload. Causes can include shard-key design, tenant skew, monotonic access patterns, hot ranges, query concentration, zones, and application behavior.

A **hot range** is a finer-grained concentration within shard-key space. A cluster can appear balanced by storage while a small logical range dominates workload.

> **Capacity must be analyzed by workload distribution, not only by database size.**

## 15. Balancer and Range Migration

MongoDB provides balancing mechanisms to redistribute sharded data. Range migration consumes real network, storage I/O, CPU, and replication resources.

> **Shard balancing creates real production workload.**

**Balancer Completed ≠ Workload Balanced.** The balancer addresses data-placement objectives; it does not guarantee equal CPU, query rate, cache pressure, I/O, or application latency.

A range can also be difficult to redistribute because of placement or operational constraints. Version-specific legacy `jumbo` behavior belongs in Chapter 11 rather than being treated as a fundamental Chapter 1 concept.

## 16. MongoDB 8.x Redistribution and Resharding

Traditional range migration is not the only modern redistribution mechanism. MongoDB supports resharding to redistribute a collection according to a different shard-key strategy, and MongoDB 8.x supports redistribution using the **same shard key** in supported resharding workflows.

```text
Data Redistribution
       │
       ├── Balancer / Range Migration
       └── Resharding
             ├── New Shard Key
             └── Same Shard Key — MongoDB 8.x
```

**Resharding Capability ≠ Shard-Key Design Is Unimportant.**

Treat resharding as a **capacity-sensitive distributed operation** whose resource profile must be evaluated for MongoDB version, collection size, shard count, topology, storage, network, replication capacity, and resharding method.

## 17. Zones and Placement Constraints

MongoDB zones allow shard-key ranges to be associated with eligible shards. Zones can support geographic placement, regulatory boundaries, tenant placement, hardware specialization, and workload isolation.

Zones constrain placement freedom and therefore become part of capacity architecture. A zone with insufficient eligible shard capacity can become a bottleneck even when unused capacity exists elsewhere in the cluster.

## 18. Failure-Domain Architecture

A sharded cluster contains multiple overlapping failure domains: application, router, shard member, shard replica set, config-server member, config-role replica set, storage, network, availability zone, and region.

```text
Member Failure ≠ Shard Failure ≠ Cluster Failure ≠ Application Outage
```

Loss of one shard secondary may leave the shard fully operational. Loss of a shard's ability to maintain a primary can affect operations requiring that shard. Loss of one `mongos` may have little application impact when other routers remain reachable.

**Cluster Healthy ≠ Application Can Reach Cluster.** Application-path availability must be monitored independently.

## 19. Production Failure Patterns

1. **Poor Shard Key** — routing/distribution architecture does not fit workload.
2. **Broadcast Amplification** — queries fan across excessive shards.
3. **Hot Shard** — workload concentrates on one shard.
4. **Hot Range** — workload concentrates within part of shard-key space.
5. **Uneven Data or Workload Distribution** — balance differs across dimensions.
6. **Balancer / Redistribution Pressure** — movement competes with application workload.
7. **Zone Capacity Constraint** — placement rules limit eligible capacity.
8. **Shard Replica-Set Unavailability** — required shard cannot serve operations.
9. **Config-Role / Routing Metadata Failure** — control metadata availability or routing is impaired.
10. **Router / Application Connectivity Failure** — database may be healthy while applications cannot reach it.

## 20. Sharding Troubleshooting

Use an evidence-driven model:

```text
Sharded-Cluster Problem
          │
          ▼
Application / mongos
          │
          ▼
Query Routing
          │
          ├── Targeted?
          └── Broadcast?
          │
          ▼
Distribution
          │
          ├── Data?
          ├── Workload?
          ├── Hot Shard?
          └── Hot Range?
          │
          ▼
Shard Health
          │
          ├── Primary?
          ├── Replication?
          └── Capacity?
          │
          ▼
Config / Routing Metadata
          │
          ▼
Balancer / Redistribution
          │
          ▼
Infrastructure
          │
          ▼
Root Cause
```

Do not begin troubleshooting by adding shards. First identify whether the constrained layer is application connectivity, router, query routing, shard-key design, workload distribution, data placement, shard replica set, config metadata, redistribution, storage, network, or infrastructure capacity.

## 21. Evidence Collection

Collect evidence across six domains:

- **Application / Router:** latency, connection failures, `mongos` availability, server selection, retries, router logs.
- **Routing:** query predicates, shard-key use, targeted shard count, broadcast behavior, result merging.
- **Distribution:** data and operations per shard, ranges, hot shards/ranges, zones, placement constraints.
- **Shard Health:** replica-set state, primary availability, replication lag, oplog health, CPU, memory, WiredTiger, storage I/O.
- **Config / Redistribution:** config-role health, config-shard role where applicable, routing state, metadata changes, balancer, migrations, resharding.
- **Infrastructure:** CPU, memory, disk latency, IOPS, throughput, network latency, packet loss, cloud throttling, and zone/region events.

Always correlate evidence by timestamp.

## 22. Monitoring and Alerting

Production monitoring should include `mongos` availability, config-role health, shard replica-set health, query targeting, broadcast operations, data distribution, workload distribution, hot shards/ranges, balancer activity, range migration, redistribution/resharding, zone capacity, and infrastructure.

Alert thresholds should reflect workload baselines, capacity objectives, failure-domain design, SLOs, RPO/RTO, and maintenance patterns rather than universal fixed values.

## 23. Production Anti-Patterns

Avoid:

- treating sharding as a universal performance fix;
- sharding before understanding workload;
- choosing a shard key only by cardinality;
- ignoring query patterns or write distribution;
- assuming hashed or ranged sharding is always superior;
- assuming more shards automatically mean more throughput;
- ignoring broadcast amplification;
- measuring only aggregate cluster CPU or storage;
- treating balanced storage as balanced workload;
- treating balancer completion as workload balance;
- assuming balancing is free;
- ignoring migration and redistribution cost;
- ignoring zone-capacity constraints;
- treating `mongos` as application-data storage;
- using direct application access to individual shards as the normal cluster path;
- treating config servers as unimportant metadata helpers;
- ignoring MongoDB 8.x config-shard architecture;
- immediately adding shards when one shard becomes hot;
- resharding without capacity analysis;
- ignoring shard-level replica-set health;
- assuming cluster health guarantees application connectivity;
- treating routing-state problems automatically as data corruption; and
- ignoring router-to-cluster and member-to-member network dependencies.

## 24. DBA Production Checklist and Key Takeaways

### DBA Production Checklist

Verify:

- [ ] the business reason for sharding is documented;
- [ ] shard-key design is workload-validated;
- [ ] ranged, hashed, or compound strategy is justified;
- [ ] every shard uses appropriate replica-set architecture;
- [ ] config-server architecture is documented;
- [ ] MongoDB 8.x config-shard usage is documented where applicable;
- [ ] applications normally access the cluster through `mongos`;
- [ ] router availability is monitored;
- [ ] targeted versus broadcast behavior is understood;
- [ ] data and workload distribution are monitored per shard;
- [ ] hot shards and hot ranges are monitored;
- [ ] balancer, migration, and resharding activity are monitored;
- [ ] zone placement and capacity constraints are documented;
- [ ] shard replica-set and config-role health are monitored;
- [ ] CPU, memory, WiredTiger, storage, and network are measured per shard;
- [ ] failure-domain placement is documented;
- [ ] application-observed availability is monitored separately from database health; and
- [ ] sharding is not treated as a substitute for indexing or query optimization.

### Key DBA Takeaways

1. Replication and sharding solve different problems.
2. Sharding horizontally distributes application data.
3. Shards use replica-set architecture.
4. `mongos` is the normal application-facing query router and does not provide durable application-data storage.
5. Config-server functionality is critical to cluster metadata and routing.
6. MongoDB 8.x can use a config shard that stores metadata and application data.
7. The shard key is part of the physical scaling architecture.
8. Targeted operations reduce unnecessary distributed work; broadcast operations can amplify it.
9. Balanced storage does not guarantee balanced workload.
10. Balancing consumes production resources and does not guarantee workload balance.
11. Zones affect both placement and capacity.
12. Member failure, shard failure, cluster failure, and application outage are different conditions.
13. Aggregate cluster metrics can hide shard-level bottlenecks.
14. Horizontal scaling does not replace query optimization.
15. Adding shards should follow root-cause analysis, not replace it.
