## 1. Deployment Topology as an Architecture Decision

MongoDB deployment topology describes how MongoDB processes, roles, data copies, votes, and infrastructure dependencies are arranged.

```text
MongoDB Deployment
       |
       +-- Standalone
       |
       +-- Replica Set
       |
       +-- Sharded Cluster
```

Topology influences availability, data redundancy, election behavior, durability, maintenance, scaling, application connectivity, failure blast radius, backup integration, and disaster recovery.

> **Topology is a reliability decision, not merely a deployment-layout decision.**

A diagram containing many servers does not automatically represent a highly available system.

## 2. Core MongoDB Deployment Models

### Standalone

```text
Application

   mongod
```

### Replica Set

```text
             Application
                  |
                  v
             Replica Set
                  |
         +--------+--------+
         |        |        |
         v        v        v
      Primary  Secondary Secondary
```

### Sharded Cluster

```text
                    Applications
                         |
                         v
                       mongos
                         |
              +----------+----------+
              |          |          |
              v          v          v
           Shard A    Shard B    Shard C
             RS         RS         RS
                         |
                         v
                    Config Role
```

The appropriate model depends on availability, durability, scale, performance, RPO/RTO, and operational requirements.

## 3. Standalone Topology

A standalone deployment contains one `mongod`. A failure of the process, host, operating system, storage, or critical network path can make the database unavailable.

```text
Standalone != High Availability
```

Standalone deployments are generally appropriate for development, testing, demonstrations, disposable environments, specialized administrative or recovery tasks, and explicitly accepted non-HA workloads. Production systems requiring high availability normally use replica-set architecture.

## 4. Replica-Set Topology

A replica set consists of multiple `mongod` members maintaining copies of the dataset.

```text
                  Replica Set
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Primary     Secondary    Secondary
```

The primary normally accepts writes. Secondaries replicate changes through the oplog architecture covered in **1.19 — Replication Architecture Overview**. If the primary becomes unavailable, an eligible secondary can be elected when the replica set retains the required voting majority.

```text
Data Redundancy
      +
Election Capability
      +
Failure-Domain Placement
      =
Replica-Set Availability Architecture
```

## 5. Preferred Three-Data-Bearing-Member Baseline

A preferred production baseline is one primary and two secondaries, all data-bearing.

```text
               Replica Set
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
     Primary     Secondary    Secondary
        P             S            S
```

This supports redundant dataset copies, election capability, member maintenance, rolling operations, and member-level failure tolerance.

```text
Three Members != Automatically Resilient Topology
```

Placement determines whether those members represent independent failure domains.

## 6. Members, Votes, Data Copies, and Electability

MongoDB topology contains several related but different concepts.

```text
Replica Set
    |
    +-- Members
    +-- Data-Bearing Members
    +-- Voting Members
    +-- Electable Members
```

```text
Member Count
     !=
Data Copy Count
     !=
Voting Count
     !=
Electable Member Count
```

A replica set can contain up to 50 members, but at most 7 members can vote. Members beyond the voting limit must be non-voting.

Election capability depends on the voting configuration and majority. A deployment can contain many running processes and still lack the voting majority required to maintain a primary.

```text
Processes Running != Primary Availability
```

Voting topology should be designed around majority availability. Adding an even-numbered voter does not necessarily increase the number of voting-member failures the replica set can tolerate.

## 7. Priority and Primary Preference

Member priority affects primary preference.

```text
priority > 0 -> Potentially Electable
priority = 0 -> Cannot Become Primary
```

Priority influences primary preference; it does not override majority, member health, freshness, or other election-eligibility requirements.

```text
High Priority != Permanent Primary Guarantee
```

Priority should support topology objectives rather than compensate for poor failure-domain design.

## 8. Hidden and Delayed Members

A hidden member is a secondary that is not normally exposed to clients through replica-set discovery. A hidden member has `priority: 0` and therefore cannot become primary. It can still be configured as a voting member.

```text
Hidden != Non-Voting
```

A delayed member intentionally applies replicated operations later than normal members. A production-oriented delayed-member design should normally use `priority: 0`, `hidden: true`, and `votes: 0`.

```text
Configured Delay < Available Oplog Window
Delayed Member != Backup
```

Independent backup remains necessary.

## 9. Arbiter and PSA Topologies

An arbiter participates in elections but does not maintain the application dataset.

```text
             Replica Set
                  |
        +---------+---------+
        |         |         |
        v         v         v
     Primary   Secondary   Arbiter
       Data      Data       Vote
```

```text
Arbiter != Data-Bearing Secondary
Arbiter != Data Redundancy
PSA != Three Data-Bearing Members
```

A P-S-S topology provides three data-bearing members and is the preferred production baseline. A P-S-A topology provides two data-bearing members and one arbiter, resulting in reduced data redundancy. If the only data-bearing secondary is unavailable or significantly lagging, PSA can encounter important `"majority"` write and operational limitations, particularly when PSA architecture is used beneath a shard.

Multiple arbiters are not a normal high-availability strategy.

> **Election majority and data redundancy are different properties.**

## 10. Failure-Domain Architecture

MongoDB members exist inside layers of infrastructure.

```text
MongoDB Member
      |
      v
Compute Host / VM
      |
      v
Storage
      |
      v
Network
      |
      v
Rack / Node
      |
      v
Availability Zone
      |
      v
Region
```

Multiple MongoDB processes do not necessarily represent independent failure domains.

```text
Member Count != Failure-Domain Diversity
```

Topology must be evaluated against the failures the system is expected to survive.

## 11. Single-Region / Multi-AZ Topology

A common production topology distributes members across availability zones within one region.

```text
                 Region
                   |
      +------------+------------+
      |            |            |
      v            v            v
     AZ-A         AZ-B         AZ-C
      |            |            |
      v            v            v
    Member A     Member B     Member C
```

This can provide protection against a single-zone failure, relatively low inter-member latency, straightforward application locality, and maintenance flexibility.

A topology with two members in AZ-A and one member in AZ-B is not symmetrically zone-failure tolerant: failure of AZ-A removes two of three votes.

> **Evaluate topology against the actual failure unit, not merely the number of locations appearing in the diagram.**

## 12. Geographic / Multi-Region Topology

Members can be distributed across geographically separated infrastructure.

```text
Region A        Region B        Region C
   |               |               |
   v               v               v
Member A         Member B         Member C
```

Geographic diversity can improve resilience against larger infrastructure failures but introduces WAN latency, greater latency variability, network partitions, cross-region cost, replication considerations, election complexity, and operational complexity.

```text
Greater Geographic Failure-Domain Diversity
                    <->
Greater Network, Latency, and Operational Complexity
```

```text
Multi-Region != Automatically Region-Failure Tolerant
```

Actual tolerance depends on voting placement, data placement, member electability, network behavior, application placement, and backup/DR architecture.

## 13. Network Latency, Elections, and Write Acknowledgement

Remote topology can influence replication lag, write acknowledgement latency, election behavior, timeout pressure, and application recovery. The exact impact on a write depends on write concern and which members must participate in acknowledgement or commit behavior.

```text
Remote Members != Every Write Automatically Waits for Every Remote Member
```

Topology analysis must account for both MongoDB semantics and actual network round-trip time.

## 14. Application Locality

Database topology should not be designed independently of application topology. Observed latency can depend on application region, primary location, read preference, write concern, driver topology discovery, DNS, connection pools, cross-zone paths, cross-region paths, and timeouts.

```text
Database Topology
      +
Application Topology
      =
Observed Application Behavior
```

A healthy database can still produce poor user experience when application and database locality are misaligned.

## 15. Maintenance-Oriented Topology

Production topology should permit planned maintenance without turning every maintenance operation into a service outage. Relevant operations include MongoDB patching, version upgrades, OS patching, certificate rotation, storage maintenance, host replacement, and infrastructure maintenance.

> **Maintenance capability is part of topology design.**

Multiple data-bearing members provide not only failure tolerance but also operational flexibility.

## 16. Sharded-Cluster Topology

A production sharded cluster contains multiple distributed availability domains.

```text
                       Applications
                            |
                    +-------+-------+
                    |               |
                    v               v
                 mongos A        mongos B
                    |               |
                    +-------+-------+
                            |
              +-------------+-------------+
              |             |             |
              v             v             v
           Shard A       Shard B       Shard C
          Replica Set   Replica Set   Replica Set
                            |
                            v
                       Config Role
                       Replica Set
```

A common production baseline uses each shard as a three-member replica set, config-server functionality through a three-member replica set, and one or more `mongos` routers according to availability and application requirements.

```text
Sharded Cluster != One Replica Set with More Servers
```

Each shard's replica-set health must be evaluated independently.

## 17. Replica-Set Primary vs. Database Primary Shard

MongoDB uses the word **primary** for two unrelated concepts in sharded environments.

```text
Replica-Set Primary != Database Primary Shard
```

A **replica-set primary** is the elected writable member of a replica set.

A **database primary shard** is a sharded-cluster concept identifying the shard associated with a database for placement of certain unsharded data.

These meanings are not related.

> **Never use “primary” without context during sharded-cluster troubleshooting.**

Use explicit terms: **replica-set primary** and **database primary shard**.

## 18. Config Role and MongoDB 8.x Config Shard

A sharded cluster requires config-server functionality for authoritative cluster metadata.

```text
Config Role
    |
    +-- Dedicated Config Server
    |
    +-- Config Shard (MongoDB 8.x)
```

A config shard combines cluster metadata responsibilities with sharded application-data storage. Its topology must therefore account for both metadata availability and application workload/capacity. Detailed configuration belongs in Chapter 11.

## 19. `mongos` Placement and Availability

Applications normally access a sharded cluster through `mongos`. Multiple routers can support application-path availability, maintenance, connection distribution, and application locality.

```text
Applications
     |
 +---+---+
 |       |
 v       v
mongos A mongos B
   |       |
   +---+---+
       |
       v
Sharded Cluster
```

```text
More mongos != Automatically Better
```

Router count and placement should reflect application locality, availability requirements, connection architecture, config-role communication, and operational manageability. Applications should normally communicate with the sharded cluster through `mongos`, not directly with individual shards.

## 20. Kubernetes and Layered Failure Domains

Kubernetes introduces additional infrastructure layers.

```text
MongoDB Member
      |
      v
     Pod
      |
      v
Kubernetes Node
      |
      v
Persistent Storage
      |
      v
Availability Zone
      |
      v
Region
```

Three MongoDB pods scheduled onto one Kubernetes node provide three pods but only one node failure domain.

```text
Pod Count != Node Diversity != Zone Diversity
```

MongoDB-on-Kubernetes reliability must account for pod placement, node placement, persistent storage, availability zones, services, DNS, network policies, and underlying cloud infrastructure. Implementation-specific Kubernetes design belongs in Book 4.

## 21. Storage, Network, DNS, and Service-Discovery Dependencies

MongoDB availability extends beyond MongoDB processes.

```text
Application Availability
          |
          +-- MongoDB Process
          +-- Voting Topology
          +-- Storage
          +-- Network
          +-- DNS
          +-- Service Discovery
          +-- Application Path
```

Compute diversity does not guarantee storage diversity. Replica-set members require network communication, and a partition can leave every process running while removing voting majority.

```text
All Processes Running != Cluster Available
```

Applications also depend on connection discovery through mechanisms such as standard connection strings, SRV records, DNS, Atlas endpoints, Kubernetes Services, private networking, and application-side service discovery.

```text
Healthy MongoDB + Broken Discovery = Application Outage
```

## 22. High Availability vs. Backup vs. Disaster Recovery

These concepts must remain separate.

```text
High Availability -> Continue Service Through Expected Failures
Backup            -> Recover Independent Historical Data
Disaster Recovery -> Restore Service After Major Failure
```

Replication creates redundant data copies, but logical changes such as an accidental deletion can propagate through the oplog to secondaries.

```text
Replication != Backup
High Availability != Backup
High Availability != Disaster Recovery
```

A multi-AZ replica set may provide excellent local high availability while still requiring independent backup and regional disaster-recovery planning.

## 23. RPO/RTO and Topology Selection

RPO defines the amount of data loss the business can tolerate. RTO defines how long service can remain unavailable.

Topology should be selected from business requirements rather than server count or infrastructure cost alone.

```text
Business Requirements
        |
        v
     RPO / RTO
        |
        v
+---------------------+
| Topology            |
| Backup              |
| Recovery Procedures |
| Application Failover|
| Operational Readiness|
+---------------------+
        |
        v
Achievable Recovery Characteristics
```

> **Topology, backup, recovery procedures, application failover, and operational readiness collectively determine whether RPO/RTO objectives can be achieved.**

The objective is the minimum architecture that reliably satisfies availability, durability, performance, scale, RPO, RTO, maintenance, and operational requirements.

## 24. Production Failure Patterns, Troubleshooting, and Monitoring

### Production Failure Patterns

1. **Shared Failure Domain** — multiple members depend on the same host, node, storage, zone, or infrastructure dependency.
2. **Voting Majority Concentration** — the topology spans failure domains but most votes reside in one domain.
3. **PSA / Arbiter Limitation** — voting availability is mistaken for data redundancy.
4. **Geographic Latency or Partition** — remote placement causes replication, acknowledgement, election, or connectivity problems.
5. **Application / Primary Locality Mismatch** — database health is good but application latency is poor because network placement is wrong.
6. **Router / Service-Discovery Failure** — the database remains healthy while the application path fails.
7. **Kubernetes / Shared-Infrastructure Co-Location** — multiple logical members share one physical failure domain.
8. **Voting Placement Misaligned With Data Placement** — surviving data-bearing capacity exists, but the topology cannot maintain the required voting majority.

### Troubleshooting Model

```text
MongoDB Availability Problem
           |
           v
Application Path
           |
           +-- DNS?
           +-- Network?
           +-- Driver?
           +-- mongos?
           |
           v
Deployment Type
           |
     +-----+-----+
     |     |     |
     v     v     v
Standalone RS  Sharded
           |
           v
Member State
           |
           v
Voting Topology
           |
           v
Failure Domains
           |
           v
Application Locality
           |
           v
Infrastructure Dependencies
           |
           v
Root Cause
```

> **Do not begin by restarting every MongoDB process. First identify the failed topology layer.**

Collect evidence across MongoDB topology, infrastructure placement, storage, network, application behavior, and the failure timeline. Always correlate evidence by timestamp.

Monitor primary availability, voting majority, member health, elections, replication, failure-domain health, `mongos` availability, config-role health, DNS/discovery, storage, network, and application availability.

The important operational question is not merely whether MongoDB processes are running, but whether the surviving topology can still satisfy the required availability, durability, and application-access objectives.
