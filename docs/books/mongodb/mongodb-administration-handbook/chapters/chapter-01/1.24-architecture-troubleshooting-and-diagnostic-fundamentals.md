# 1.24 — Architecture Troubleshooting and Diagnostic Fundamentals

**Book:** MongoDB Administration Handbook  
**Chapter 1:** MongoDB Architecture and Internals  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Revised Final / Canonical Edition

## Learning Objectives

After completing this section, you should be able to:

- troubleshoot MongoDB using an architecture-first methodology;
- distinguish symptoms, immediate causes, and root causes;
- identify whether failures originate in the application, driver, network, MongoDB process, storage, replication, sharding, or infrastructure;
- establish incident scope and timeline before making changes;
- collect useful diagnostic evidence without unnecessarily destroying incident state;
- use MongoDB logs, `serverStatus`, `$currentOp`, `$queryStats`, profiler data, `explain()`, and replica-set status appropriately;
- interpret MongoDB 8.x replication diagnostics correctly;
- distinguish normal replication lag, intentional delay, and initial-sync behavior;
- correlate MongoDB evidence with OS, storage, network, application, and platform evidence;
- understand diagnostic overhead and production safety;
- distinguish mitigation from permanent corrective action; and
- build high-quality incident evidence and escalation packages.

## 1. Troubleshooting as an Architecture Discipline

MongoDB troubleshooting should begin by identifying which architectural layer is failing.

```text
Application
     |
     v
Driver / Connection Pool
     |
     v
DNS / Network / TLS / Authentication
     |
     v
Topology Discovery / Server Selection
     |
     v
mongos / mongod
     |
     v
Query / Transaction
     |
     v
WiredTiger / Storage
     |
     +-----------+
     |           |
     v           v
Replication   Sharding
     |           |
     +-----+-----+
           |
           v
Infrastructure / Platform
```

A timeout observed by an application does not automatically mean MongoDB query execution is slow. High CPU does not automatically identify the root cause. A running `mongod` process does not prove the database topology is healthy.

> **Identify the Failing Architectural Layer Before Changing the System**

MongoDB should be diagnosed as a distributed production system rather than as one isolated database process.

## 2. Symptom, Cause, and Root Cause

A symptom is what users, applications, or monitoring observe: timeout, latency, high CPU, connection failure, replication lag, or disk-full alerts. The immediate cause is the technical condition directly producing the symptom. The root cause is the underlying condition responsible for the failure.

```text
Symptom
Application Timeout
       |
       v
Immediate Cause
Server Selection Timeout
       |
       v
Root Cause
Network Policy Prevented
Replica-Set Member Reachability
```

> **Symptom ≠ Root Cause**

A mitigation can remove the symptom without correcting the underlying failure.

## 3. Hypothesis-Driven Troubleshooting

Troubleshooting should be evidence-driven rather than a sequence of unrelated commands.

```text
Observe
   |
   v
Form Hypothesis
   |
   v
Collect Evidence
   |
   v
Test
   |
 +---+---+
 |       |
 v       v
Supported Rejected
 |       |
 v       v
Act   New Hypothesis
```

For example, application latency may increase while MongoDB execution latency remains normal and server-selection latency rises. That evidence rejects query execution as the primary cause and redirects investigation toward connectivity or topology selection.

## 4. Incident Scope and Timeline

Before deep diagnosis, establish scope and time. Determine affected users and applications, reads versus writes, databases or collections, query patterns, members or shards, availability zones, regions, and infrastructure domains.

Build a timeline:

```text
Last Known Good
      |
      v
Change / Event
      |
      v
First Symptom
      |
      v
Detection
      |
      v
Investigation
      |
      v
Mitigation
      |
      v
Recovery
```

Capture exact timestamps wherever possible. Investigate deployments, configuration changes, elections, restarts, traffic changes, infrastructure events, security changes, and network changes near the incident.

> **Correlation ≠ Causation**

Timeline correlation narrows hypotheses; evidence must still establish causality.

## 5. Evidence Before Intervention

Restarting can destroy or alter active-operation evidence, connections, cache state, process state, temporary error conditions, and resource-pressure patterns.

Prefer:

```text
Detect
  |
  v
Scope
  |
  v
Collect Evidence
  |
  v
Analyze
  |
  v
Mitigate
```

when operational conditions permit.

> **Evidence Before Intervention — Unless Intervention Is Required to Protect the System**

Evidence preservation must never take priority over urgent actions required to protect data durability, security, availability, infrastructure, or the system from catastrophic resource exhaustion.

## 6. Diagnostic Evidence Matrix

| Layer | Typical Evidence |
|---|---|
| Application | errors, latency, retries |
| Driver | topology discovery, server selection, connection pools |
| DNS / Network | resolution, reachability, latency |
| TLS / Authentication | handshake and authentication failures |
| MongoDB Process | logs, process state |
| Operations | `$currentOp` |
| Queries | `$queryStats`, profiler, `explain()` |
| WiredTiger | cache, eviction, checkpoints |
| Storage | latency, throughput, IOPS, capacity |
| Replication | `rs.status()`, optimes, lag, oplog |
| Sharding | routing, shard health, distribution |
| OS | CPU, memory, disk, network |
| Platform | VM, container, Kubernetes, cloud events |

A strong investigation correlates evidence rather than treating any one metric as universal truth.

> **Absence of One Diagnostic Signal ≠ Proof That the Layer Is Healthy**

## 7. MongoDB Logs and Structured Logging

MongoDB logs are a primary source of diagnostic evidence. They can provide information about startup and shutdown, configuration, connections, authentication, TLS, replication, elections, storage, WiredTiger, checkpoints, slow operations, sharding, assertions, and warnings.

Modern MongoDB logging uses structured JSON fields that support machine processing and event correlation.

```text
Incident Time
      +
Component
      +
Context
      +
Message
      =
Correlated Diagnostic Evidence
```

Focus on a time window around the incident. Do not search only for `ERROR`; warnings, topology events, storage events, connection messages, and informational state transitions can contain critical causal evidence.

## 8. `serverStatus` and Metric Interpretation

`serverStatus` provides broad visibility into server activity.

```javascript
db.serverStatus()
```

Relevant areas can include connections, network, operations, memory, WiredTiger, locks, transactions, replication-related metrics, and other server counters.

Prefer interpreting counters as deltas, rates, and trends rather than isolated snapshots.

> **Single Snapshot ≠ Performance Trend**

> **Counters Become More Useful as Rates, Deltas, and Trends**

Correlate `serverStatus` with workload, topology, OS, storage, and application evidence.

## 9. `$currentOp` and Active Operations

For modern MongoDB administration, use the `$currentOp` aggregation stage as the preferred interface for current-operation visibility.

```javascript
db.getSiblingDB("admin").aggregate([
  {
    $currentOp: {
      allUsers: true,
      idleConnections: false
    }
  }
])
```

It can help identify long-running operations, client information, namespaces, operation types, waits, transactions, and administrative work.

> **Long Running ≠ Automatically Bad**

Before terminating an operation, identify its owner and purpose, determine impact, and validate safe termination.

> **Visible Operation ≠ Safe Operation to Kill**

Detailed operation termination belongs in Chapter 7.

## 10. Database Profiler, `$queryStats`, and Query Evidence

Query investigation should use the least intrusive evidence source capable of answering the diagnostic question.

```text
Need Query Evidence
       |
       v
Existing Metrics / $queryStats /
Managed Tooling Sufficient?
       |
    +--+--+
   Yes   No
    |     |
    v     v
 Use   Evaluate
Them   Profiler
```

`$queryStats` can provide query-shape execution statistics where supported and appropriate. The database profiler provides detailed operation information and stores profiler records in `system.profile`.

> **Database Profiler = Powerful Diagnostic Tool + Potential Production Overhead**

> **Diagnostic Instrumentation Has Operational Cost**

Do not automatically enable aggressive profiling during an already overloaded production incident.

## 11. `explain()` and Query Diagnosis

`explain()` helps analyze query execution. Useful evidence can include winning plan, index use, collection scans, keys examined, documents examined, execution statistics, and sorting behavior.

A useful comparison is documents returned versus documents examined versus keys examined. Large differences can indicate inefficient access patterns, but interpretation requires workload context.

> **COLLSCAN ≠ Automatically a Production Incident**

A collection scan over a tiny collection can be completely reasonable.

## 12. Application, Driver, and Connection Diagnostics

Client-observed database latency contains multiple components.

```text
Application Request
       |
       +-- Pool Acquisition
       +-- DNS / SRV
       +-- Network
       +-- TLS
       +-- Authentication
       +-- Topology Discovery
       +-- Server Selection
       +-- MongoDB Execution
       +-- Result Transfer
```

> **Application Database Latency ≠ MongoDB Query Execution Time**

A query can execute quickly while an application experiences a timeout because of connection-pool exhaustion, DNS delays, network problems, topology discovery, or server selection.

> **Endpoint Reachable ≠ MongoDB Topology Usable**

A client might successfully contact one endpoint yet fail to discover or select a usable replica-set or sharded-cluster member.

## 13. DNS, Network, TLS, and Authentication

Troubleshoot connectivity in layers.

```text
DNS
 |
 v
TCP
 |
 v
TLS
 |
 v
MongoDB Protocol
 |
 v
Authentication
 |
 v
Authorization
```

TCP, TLS, authentication, and authorization failures require different evidence and remediation. Do not categorize every connection problem simply as MongoDB unavailable. Replica-set and sharded-cluster communication also depends on reliable member-to-member networking.

## 14. CPU, Memory, and Resource Pressure

High resource utilization is an observation, not a diagnosis.

For CPU, determine which process, operations, and workload are consuming resources and why the work is expensive. Possible contributors include expensive queries, scans, aggregation, index work, compression, replication, batch writes, and connection activity.

> **High CPU ≠ Root Cause**

Memory diagnosis must distinguish MongoDB process memory, WiredTiger cache, filesystem cache, OS memory, swap, and container/cgroup limits.

> **High Memory Usage ≠ Memory Pressure**

> **Resource Utilization ≠ Resource Saturation**

## 15. WiredTiger and Storage Diagnostics

WiredTiger sits directly between MongoDB workload behavior and storage.

```text
Workload
   |
   v
WiredTiger Cache
   |
   +-- Reads
   +-- Writes
   +-- Dirty Data
   +-- Eviction
   +-- Checkpoints
   |
   v
Storage
```

Cache pressure can originate from working-set growth, expensive scans, workload changes, storage latency, write pressure, or concurrency.

> **WiredTiger Cache Pressure ≠ Automatically a Cache-Sizing Problem**

Storage diagnosis should evaluate latency, IOPS, throughput, queueing, capacity, filesystem condition, and underlying cloud/storage limits.

> **Disk Free Space ≠ Storage Performance**

> **Never Delete MongoDB-Managed Data Files as an Emergency Space-Reclamation Shortcut**

Determine file ownership and use MongoDB-safe recovery procedures.

## 16. Replica-Set Status and Member Perspective

Replica-set troubleshooting should begin with topology state.

```javascript
rs.status()
```

It exposes replica-set status information from the perspective of the member where it is executed. Useful evidence includes member states, primary, health, optimes, heartbeat information, synchronization state, and initial-sync information where applicable.

> **Replica-Set Status Is Member-Perspective Evidence**

During network partitions, different members can have different visibility. One member's status output should not automatically be interpreted as infallible global truth.

> **Processes Running ≠ Primary Availability**

## 17. Replication Lag, Oplog Window, and Recovery Headroom

Replication lag is a symptom. Possible contributors include secondary storage latency, CPU pressure, network latency, heavy write load, resource contention, maintenance, and synchronization activity.

For MongoDB 8.x, diagnosis should recognize the distinction between replication state being written locally and changes being applied to user data.

> **Oplog Written on Secondary ≠ Operation Applied to User Data**

Detailed MongoDB 8.x written/applied metrics belong in Chapter 10.

Lag should be evaluated against available oplog history.

```text
Secondary Lag
      |
      v
Available Oplog Window
      |
      v
Recovery Headroom
      |
   +--+--+
   |     |
Healthy Shrinking
         |
         v
     Stale Risk
```

> **Replication Lag Without Oplog-Window Context Is Incomplete Evidence**

A common causal chain is storage latency increasing, secondary apply rate decreasing, replication lag increasing, and recovery headroom shrinking. The operational question is not merely how far behind the secondary is, but how much recovery margin remains before required oplog history becomes unavailable.

## 18. Initial Sync, Delayed Members, and Election Diagnostics

Initial sync creates a data-bearing member's initial dataset and differs fundamentally from routine steady-state replication.

> **Initial Sync Problem ≠ Normal Replication-Lag Problem**

Initial sync can create substantial network, storage, CPU, and source-member load and should be treated as a capacity event.

A deliberately delayed secondary is intentionally behind current primary state.

> **Configured Replication Delay ≠ Unintended Replication Lag**

Monitoring must know which members are intentionally delayed to avoid false-positive alerts.

When an election occurs, investigate whether the trigger was a planned stepdown, process failure, network issue, voting-majority problem, or resource pressure. Do not automatically classify every election as a MongoDB defect.

## 19. Sharded-Cluster Diagnostics

Sharded clusters add routing and distributed-placement layers.

```text
Application
     |
     v
mongos
     |
     v
Routing Metadata
     |
     v
Shard Selection
     |
     v
Shard Replica Set
     |
     v
Storage
```

Investigate `mongos` availability, config-role health, shard availability, routing, targeted versus broadcast operations, shard distribution, hot shards, balancing/redistribution, and zones.

> **Cluster Healthy ≠ Workload Balanced**

> **Storage Imbalance ≠ Workload Imbalance**

A small shard can be hot, and a large shard can be relatively idle. Detailed sharding troubleshooting belongs in Chapter 11.

## 20. Infrastructure and Kubernetes Diagnostic Layers

MongoDB can appear unhealthy because the infrastructure underneath it is unhealthy. Investigate compute saturation/throttling, memory pressure, OOM events, storage latency and limits, network latency or packet loss, DNS, firewall/security policy, VM events, cloud maintenance, node failures, autoscaling, and orchestration events.

> **Database Incident ≠ Necessarily Database-Engine Failure**

When MongoDB runs on Kubernetes:

```text
MongoDB
   |
   v
Container
   |
   v
Pod
   |
   v
Node
   |
   v
Storage / Network
   |
   v
Kubernetes
   |
   v
Cloud / Infrastructure
```

> **Pod Running ≠ MongoDB Healthy**

> **Replica Count ≠ Failure-Domain Diversity**

Detailed Kubernetes diagnosis belongs in the MongoDB Cloud & Kubernetes Production Handbook.

## 21. Baselines, Rates, Trends, and Cross-Layer Correlation

Maintain baselines for CPU, memory, WiredTiger, storage latency, connections, operations, query latency, replication lag, oplog window, network behavior, and data/index growth.

Compare current state with known normal rather than with a guess.

> **A Metric Without a Baseline Has Limited Diagnostic Value**

Prefer rates and trends over isolated values. Cross-layer correlation strengthens hypotheses. For example, simultaneous application latency, MongoDB latency, storage latency, and WiredTiger pressure create a stronger storage/I/O hypothesis than any single signal.

Conversely, application latency increasing while MongoDB execution remains normal should redirect investigation toward the driver, pool, DNS, network, or server selection.

> **Absence of One Diagnostic Signal ≠ Proof That the Layer Is Healthy**

## 22. Diagnostic Safety and Operational Overhead

Troubleshooting itself creates workload. Before running a diagnostic action, determine whether it is read-only, scans large data, increases I/O, acquires locks, changes state, or can affect availability.

Classify actions as:

```text
Read-Only Diagnostic
        |
State-Changing Diagnostic
        |
Corrective Action
        |
Destructive Action
```

The deeper down this list an action falls, the stronger the operational controls should be.

> **Observability ≠ Zero Cost**

> **Troubleshooting Activity Is Part of Production Workload**

Prefer the least intrusive diagnostic technique that can answer the question. When operational conditions permit, make one controlled change, observe the result, and validate the hypothesis rather than changing several variables simultaneously.

## 23. Mitigation, Recovery, and Root-Cause Correction

Incident response has several distinct stages.

```text
Incident
   |
   +-- Immediate Mitigation
   +-- Recovery Validation
   +-- Root-Cause Analysis
   +-- Permanent Corrective Action
   +-- Preventive Engineering
```

Scaling an instance may restore service during a high-CPU incident while leaving an inefficient query or missing index unresolved.

> **Service Restored ≠ Root Cause Resolved**

After mitigation, determine why the incident occurred, why monitoring did or did not detect it, why existing controls did not prevent it, whether the failure can recur, and what permanent engineering change is required.

## 24. Failure Patterns, Evidence Packages, and Escalation

Canonical failure patterns include:

1. **Restart-First Troubleshooting** — service is restarted before relevant evidence is collected.
2. **High CPU Misdiagnosed as Capacity Shortage** — scaling mitigates a symptom while an inefficient workload remains.
3. **Replication Lag Diagnosed Without Oplog Context** — lag is monitored without recovery headroom.
4. **Application Timeout Misdiagnosed as Slow Query** — server execution is normal while DNS, pool, or server-selection delay causes the timeout.
5. **Disk Emergency Handled With Unsafe File Deletion** — MongoDB-managed files are manually removed, creating integrity risk.
6. **Diagnostic Activity Amplifies the Incident** — aggressive profiling or broad diagnostics add significant load.
7. **Intentional Delayed Member Misdiagnosed as Replication Failure** — configured delay triggers an incorrect lag diagnosis.
8. **Initial Sync Problem Misdiagnosed as Normal Replication Lag** — synchronization load is interpreted as a steady-state replication issue.

For significant incidents, collect a standardized evidence package containing incident metadata, MongoDB version and FCV, topology, configuration, logs, relevant metrics, active operations, replication/sharding evidence, infrastructure evidence, application/driver evidence, recent changes, mitigation actions, and a timestamped timeline.

A useful escalation communicates:

> **Scope + Timeline + Architecture + Evidence + Changes + Actions + Impact**

Avoid vague escalation statements such as "MongoDB is slow." Provide baseline deviation, affected topology, timestamps, correlated metrics, relevant logs, recent changes, and actions already taken.

## 25. DBA Checklist, Key Takeaways, Applicability, and Canonical Status

### DBA Production Checklist

**Scope and Timeline**

- [ ] User/application impact identified.
- [ ] Reads/writes affected identified.
- [ ] Database/collection scope identified.
- [ ] Members/shards affected identified.
- [ ] Infrastructure/geographic scope identified.
- [ ] Last known good and first symptom recorded.
- [ ] Recent changes identified.
- [ ] Mitigation actions timestamped.

**MongoDB Evidence**

- [ ] Binary version and FCV recorded.
- [ ] Topology verified.
- [ ] Logs reviewed.
- [ ] `serverStatus` evidence evaluated.
- [ ] `$currentOp` reviewed where applicable.
- [ ] Query evidence collected where applicable.
- [ ] Replica-set state reviewed.
- [ ] Replication lag evaluated with oplog context.
- [ ] Initial-sync/delayed-member state considered.
- [ ] Sharding state reviewed where applicable.

**Infrastructure and Application**

- [ ] CPU and memory pressure checked.
- [ ] Storage latency and capacity checked.
- [ ] Network and DNS checked.
- [ ] OS/platform events reviewed.
- [ ] Driver version known.
- [ ] Application errors collected.
- [ ] Connection-pool and server-selection behavior considered.
- [ ] Client latency compared with MongoDB execution evidence.

**Safety**

- [ ] Evidence captured before intervention where practical.
- [ ] Diagnostic overhead evaluated.
- [ ] State-changing commands identified.
- [ ] Corrective actions recorded.
- [ ] Uncontrolled simultaneous changes avoided where possible.
- [ ] No unvalidated MongoDB-managed file deletion performed.
