# 1.3 — `mongod`, `mongos`, and Supporting Components

**Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 1:** MongoDB Architecture and Internals  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant

## Learning Objectives

After completing this section, you should be able to distinguish `mongod`, `mongos`, `mongosh`, and MongoDB Database Tools; explain the principal responsibilities and topology roles of `mongod`; understand that primary and secondary are replica-set roles rather than separate executables; explain the routing and stateless architecture of `mongos`; distinguish dedicated config servers from MongoDB 8.0+ config shards; understand the relationship between `mongod`, WiredTiger, the filesystem, and storage; distinguish OS process health from MongoDB service health; understand configuration, networking, security, logging, and infrastructure dependencies; and apply production validation principles during incident triage.

## MongoDB Software Component Model

MongoDB environments contain server, routing, interactive administration, and database-tool components. `mongod` provides database-server functionality. `mongos` provides sharded-cluster routing. `mongosh` and MongoDB Database Tools are client-side administrative software.

MongoDB Database Tools include `mongodump`, `mongorestore`, `mongoexport`, `mongoimport`, `bsondump`, `mongostat`, `mongotop`, and `mongofiles`.

## `mongod`

`mongod` is MongoDB's primary server daemon. It handles data requests, manages access to data, and performs background database-management operations. Its exact responsibilities depend on the deployment role in which the process participates.

A `mongod` can operate as a standalone server, replica-set primary or secondary, shard replica-set member, dedicated config-server replica-set member, or MongoDB 8.0+ config-shard member. The executable alone does not determine the architectural role; configuration, cluster membership, and topology state determine the role.

Depending on topology and configuration, `mongod` participates in client connections, authentication and authorization, command processing, reads and writes, collection and index management, transactions, storage-engine interaction, replication, elections, durability, sessions, logging, metrics, diagnostics, and sharded-cluster responsibilities.

## Process Identity vs. Topology Role

Primary and secondary are replica-set roles or states, not different MongoDB server programs. A member can transition from secondary to primary following an election while continuing to run the same `mongod` executable. Monitoring should therefore track both process identity and current topology role.

## Standalone and Replica-Set `mongod`

A standalone deployment has one `mongod`; if it becomes unavailable there is no replica-set member available to assume the database role automatically.

A replica set consists of multiple independent `mongod` processes coordinating replicated database state. Each member has its own operating-system process, memory, network listeners, runtime state, logs, WiredTiger instance, and persistent files where applicable. A replica set is therefore a distributed topology of independent MongoDB server processes rather than one process stretched across multiple machines.

In normal replica-set operation, the primary receives writes while secondaries maintain replicated copies and participate in topology behavior according to configuration. Eligible secondaries can later become primary through elections.

## `mongod` and WiredTiger

MongoDB 8.x `mongod` processes use WiredTiger for persistent database storage. Stored state depends on topology role and can include application data, replicated data, indexes, sharded-cluster metadata, or a combination of configuration and application data in a config shard.

The operational stack is application → driver → `mongod` → WiredTiger → filesystem → storage. A problem visible at the MongoDB layer can originate below it, such as storage latency or resource pressure.

## `mongos`

`mongos` is the query-routing process for a MongoDB sharded cluster. It provides the application-facing routing layer between clients and the distributed cluster.

Unlike a data-bearing `mongod`, `mongos` does not persist application datasets and has no persistent database state of its own. It maintains routing-related information in memory, including cached cluster metadata used to determine where operations should be sent.

Its responsibilities include accepting client operations, consulting cached metadata, routing operations to appropriate shards, coordinating distributed operations, and coordinating results returned to clients. Depending on shard key, query shape, data placement, and metadata, an operation can target one shard or multiple shards.

## `mongos` vs. `mongod`

`mongod` provides database-server functionality and persistent database state. `mongos` provides sharded-cluster routing and coordination. They are complementary rather than interchangeable components.

Production sharded deployments should avoid unnecessary dependence on a single `mongos`. Router capacity planning should consider connection volume, CPU, memory, operation rate, network throughput, routing workload, distributed aggregation/merge work, placement relative to applications, and availability of multiple routing paths.

Normal sharded-cluster application traffic should use `mongos`. Do not build ordinary application access around direct shard connections. Direct shard access should be limited to specifically supported administrative or maintenance scenarios.

## Configuration Components

Sharded clusters require a configuration role that maintains critical cluster metadata. MongoDB 8.x can use either dedicated config servers or a MongoDB 8.0+ config shard.

A traditional dedicated config server replica set consists of `mongod` instances configured for the config-server role. These maintain critical sharded-cluster metadata rather than operating as ordinary application-data shards. Dedicated config-server replica sets have role-specific topology restrictions and should not be administered as arbitrary application-data replica sets.

MongoDB 8.0 introduced config-shard architecture, in which configuration infrastructure can also participate as an application-data shard. A config shard combines config-server functionality with shard-server functionality. A dedicated config-server architecture separates those responsibilities. The selected architecture should be explicitly documented because operational requirements and feature constraints can differ.

## `mongosh`

`mongosh` is the MongoDB Shell and an interactive administrative client. It connects to MongoDB deployment endpoints for administration and troubleshooting. It is not a database server, storage engine, replica-set member, or query router.

## MongoDB Database Tools

MongoDB Database Tools are separate command-line utilities:

| Tool | Primary purpose |
|---|---|
| `mongodump` | Creates BSON-format dumps for logical dump/restore workflows |
| `mongorestore` | Restores data from `mongodump` output |
| `mongoexport` | Exports collection data to JSON or CSV |
| `mongoimport` | Imports JSON, CSV, or TSV-style data |
| `bsondump` | Inspects or converts BSON dump content |
| `mongostat` | Provides a quick operational statistics view |
| `mongotop` | Reports time spent reading and writing collection data |
| `mongofiles` | Provides command-line interaction with GridFS files |

MongoDB Database Tools have their own release lifecycle. Do not assume their version number should numerically match the MongoDB Server version. Compatibility should be validated during installation, upgrades, migrations, backup procedures, and tooling certification.

## Logical Dump vs. Data Export

`mongodump` creates BSON-format logical dumps intended for dump/restore workflows with `mongorestore`. `mongoexport` produces JSON or CSV data primarily for interchange. Data export is not automatically a production backup strategy, and even a logical dump should not automatically be assumed to satisfy every production backup requirement.

Backup design must consider topology, consistency, RPO, RTO, database size, backup and restore duration, recovery validation, and operational scale.

## Process Configuration

`mongod` and `mongos` behavior can be controlled through configuration files and supported command-line options. For self-managed production deployments, prefer managed configuration files rather than long ad hoc command-line option sets. Configuration-file governance improves repeatability, peer review, source control, auditability, automation, drift detection, and predictable restart behavior.

## Process Lifecycle and `systemd`

On applicable self-managed Linux package installations using `systemd`, MongoDB services are commonly managed with commands such as:

```bash
sudo systemctl status mongod
sudo systemctl start mongod
sudo systemctl stop mongod
sudo systemctl restart mongod
```

These commands manage the operating-system service. They do not prove database health. Process control and database-health validation are different activities.

## Process Health vs. Database Health

A running process is not necessarily a healthy MongoDB service. A running `mongod` can still be lagging, recovering, isolated, storage-stalled, unable to form a majority, or unavailable to the application.

A production validation chain should confirm: process running → intended connection succeeds → authentication succeeds → topology role/state is correct → replication or routing is healthy → storage is healthy → application path works.

Checking only `systemctl status mongod` is insufficient.

## Process Identity and Permissions

Self-managed MongoDB processes should run under controlled operating-system identities with required access to configuration, database paths, logs, certificates, keys, secrets, storage mounts, and backup locations without unnecessary OS privilege. Incorrect ownership or permissions can cause startup or runtime failures.

## Network Listeners and Connectivity

A MongoDB process must listen on appropriate interfaces and be reachable through the paths required by its topology. A process may appear healthy locally but remain unavailable remotely because of bind configuration, DNS, routing, firewall rules, security groups, TLS identity, certificate problems, or blocked ports. Network configuration is both a security and availability concern.

## Security Boundary

A running MongoDB process should not automatically be considered production-ready. Production readiness requires deliberate network exposure, authentication, authorization, TLS, secrets management, OS permissions, encryption controls where required, auditing, monitoring, and recovery capability. An open TCP listener does not prove the database is secure.

## Logging and Diagnostics

Both `mongod` and `mongos` generate diagnostic logs. Logs can contain evidence related to startup/shutdown, connections, authentication, elections, replication, networking, storage, checkpoints, queries, slow operations, sharding, configuration, warnings, assertions, and failures.

Logs should be correlated with topology state, MongoDB metrics, OS evidence, network evidence, storage evidence, and the incident timeline. Logs are evidence, not the complete definition of health.

## Monitoring by Component

For `mongod`, monitor process availability, CPU, memory, connections, file descriptors, operation rates, query latency, WiredTiger cache, disk latency/capacity, replication state/lag, oplog health, and errors.

For `mongos`, monitor process availability, CPU, memory, connection volume, operation latency, network throughput, routing behavior, distributed operation workload, errors, shard reachability, and configuration-role connectivity.

Monitoring should reflect component responsibility.

## Supporting Infrastructure

MongoDB reliability depends on the operating system, CPU, memory, filesystem, storage, DNS, network, time synchronization, certificates, and secrets. A reported MongoDB incident can originate at any of these layers. Effective troubleshooting therefore crosses database and infrastructure boundaries.

## Component Failure Model

When an application reports a MongoDB problem, identify the deployment type and entry component (`mongod` or `mongos`), inspect member/router state, inspect overall topology state, and then inspect dependencies such as storage, network, and OS resources.

Representative `mongod` problems include startup failure, crash, OOM termination, storage stall, replication failure, connection exhaustion, resource pressure, network isolation, and topology problems. Representative `mongos` problems include router unavailability, connection/resource pressure, shard or configuration-role connectivity failures, routing issues, and inefficient distributed operations.

The failed architectural layer should be identified before remediation is selected.

## Evidence Before Restart

Restarting a MongoDB process can be an appropriate service-restoration action, but restart should not automatically substitute for diagnosis. When service conditions permit, collect relevant topology state, logs, MongoDB metrics, process/OS evidence, memory evidence, storage evidence, and network evidence before restarting. Balance service restoration with evidence preservation and root-cause analysis.

## Version and Upgrade Awareness

MongoDB lifecycle management involves multiple version dimensions: `mongod`, `mongos`, Feature Compatibility Version, `mongosh`, and Database Tools. These should not be treated as one undifferentiated version number. Compatibility and upgrade ordering should be explicitly validated, especially for sharded-cluster lifecycle operations.

## Production Component Inventory

| Component | Architectural role | Key dependencies |
|---|---|---|
| `mongod` | Database server | OS, storage, DNS, network, security |
| `mongos` | Sharded-cluster query router | Shards, configuration role, DNS, network |
| `mongosh` | Administrative client | Network, authentication, TLS |
| Database Tools | Operational utilities | Network, credentials, tool/server compatibility |

For server components, also document environment, topology, version, configuration source, service identity, storage path where applicable, logging destination, monitoring, ownership, and recovery procedure.

## Component Anti-Patterns

Avoid monitoring only process state; treating `mongos` as a storage server; treating every `mongod` identically; using restart as generic remediation; running MongoDB with unnecessary OS privileges; assuming an open port means a healthy database; treating client utilities as server components; and ignoring tool/server compatibility.

## Production Component Validation Checklist

Before approving or validating a production component, verify:

- component type and topology role are documented;
- MongoDB/tool versions and FCV where relevant are known;
- configuration source is managed and reviewable;
- service account and filesystem permissions are appropriate;
- data and log paths are correct where applicable;
- DNS, listeners, required network paths, firewall rules, TLS, authentication, and authorization are validated;
- storage is mounted and healthy;
- process/resource limits are appropriate;
- monitoring and logging are enabled;
- restart and topology-aware post-restart validation procedures exist;
- client/tool compatibility is validated;
- backup implications are understood;
- failure behavior has been tested; and
- escalation procedures are documented.

1. `mongod` is MongoDB's primary database-server daemon.
2. The same `mongod` executable can perform different topology roles.
3. Primary and secondary are replica-set roles/states, not different executables.
4. A replica set is composed of independent `mongod` processes coordinating replicated state.
5. MongoDB 8.x `mongod` uses WiredTiger for persistent database storage.
6. Stored state depends on topology role.
7. `mongos` is the query-routing process for sharded clusters.
8. `mongos` does not persist application datasets and has no persistent database state of its own.
9. Normal sharded-cluster application traffic should use `mongos`.
10. Production routing should avoid unnecessary dependence on a single router.
11. Dedicated config-server members are `mongod` processes performing a specialized configuration role.
12. MongoDB 8.0+ config shards combine configuration and application-data shard responsibilities.
13. `mongosh` is an administrative client, not a server component.
14. MongoDB Database Tools have their own release lifecycle.
15. `mongodump` and `mongoexport` serve different purposes.
16. Data export is not automatically a production backup strategy.
17. Production self-managed configuration should be managed and repeatable.
18. Process control and database-health validation are different activities.
19. A running `mongod` does not prove that the database is healthy.
20. DNS, networking, storage, TLS, OS resources, permissions, certificates, and secrets are part of MongoDB reliability.

22. Restart can restore service but should not automatically replace diagnosis.
23. `mongod`, `mongos`, FCV, `mongosh`, and Database Tools require compatibility awareness during lifecycle operations.
