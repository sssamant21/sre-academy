# 1.4 — Database, Collection, Document, and Field Architecture

## Learning Objectives

After completing this section, you should be able to explain MongoDB's logical data hierarchy; distinguish databases, collections, documents, fields, and values; understand flexible-schema architecture; explain embedded documents and arrays; understand `_id` and business identity; evaluate embedding versus referencing; understand single-document atomicity; recognize document growth, nesting, and size limits; understand GridFS boundaries; explain collection validation, schema evolution, and schema drift; understand multikey-index implications; distinguish logical objects from physical storage; and evaluate the operational impact of data architecture.

## MongoDB Logical Data Hierarchy

MongoDB organizes application data as deployment → database → collection → document → field → value.

For administrators familiar with relational systems, database approximately maps to database, collection to table, document to row, field to column, and `_id` plus an application identity strategy to the primary-key concept. This comparison is only an orientation aid: a MongoDB document can contain embedded documents, arrays, and rich BSON values and should not be treated merely as a relational row encoded differently.

## Database Architecture

A MongoDB database is a logical container for collections. A deployment can contain multiple databases. Database boundaries can affect namespaces, authorization, administrative operations, backup/restore procedures, monitoring, migration, naming, automation, and operational ownership. A database should not automatically be interpreted as a hard infrastructure-isolation boundary equivalent to an independent deployment.

MongoDB also uses system or administrative databases such as `admin`, `config`, and `local` for administrative, topology, metadata, or instance-local purposes. Their exact contents and semantics depend on deployment topology and MongoDB version. Do not use MongoDB system databases as general-purpose application storage.

## Collection Architecture

A collection is a logical grouping of MongoDB documents. Documents in an ordinary collection do not need identical field structures by default. This flexibility is intentional, but production systems still require data-model governance.

MongoDB also supports specialized collection models such as standard, capped, clustered, and time-series collections. Collection type is part of the data architecture and should be chosen deliberately because storage, indexing, lifecycle, creation, and administrative behavior can differ.

Production collections requiring deliberate validation, collation, capped behavior, clustered options, time-series behavior, or other collection-level settings should be managed explicitly rather than treated merely as a side effect of the application's first write.

## Flexible Schema Does Not Mean No Schema

MongoDB permits structural flexibility; production engineering determines how much flexibility is appropriate. Applications and administrators still need deliberate decisions around required fields, BSON types, naming conventions, nested structures, arrays, document growth, indexes, validation, compatibility, schema evolution, and application expectations. Without governance, flexibility can become schema drift.

## Document and Field Architecture

The document is MongoDB's fundamental application-data structure and is represented using BSON. A document can contain scalar fields, embedded documents, arrays, and other BSON values.

```javascript
{
  _id: ObjectId("64f000000000000000000001"),
  customer_id: "C10001",
  active: true,
  balance: 245.75,
  address: {
    city: "Charlotte",
    state: "NC"
  },
  tags: ["premium", "online"]
}
```

Detailed BSON types and their semantics are covered in Section 1.5.

## The `_id` Field

In standard MongoDB collections, each stored document requires a unique `_id` value, and MongoDB normally creates the corresponding unique `_id` index. When an application does not supply `_id`, MongoDB drivers commonly generate an `ObjectId`. Applications can also supply their own supported `_id` values; `ObjectId` is common but not the only possible strategy.

Specialized collection types can behave differently. Time-series collections are an important exception to the ordinary `_id` model and should not be assumed to behave like standard collections.

MongoDB document identity and business identity are separate concerns. An application might use `_id` as MongoDB identity while a field such as `customer_number` represents business identity. If a business identifier must also be unique, it can require an appropriate unique index. `_id` does not automatically enforce uniqueness for unrelated business identifiers.

## Field Naming and Governance

Field names become part of the persisted data model and should be deliberate and consistent. Uncontrolled variants such as `customerId`, `customer_id`, `CustomerID`, and `cust_id` for the same concept can create query, indexing, analytics, migration, application, and governance problems.

Some field names involving special characters such as `$` or `.` have operational restrictions and compatibility considerations. Production naming standards should avoid unnecessary complexity.

## Hierarchical Data and Arrays

MongoDB documents can represent hierarchical structures directly through embedded documents and arrays. Embedding can colocate related data while arrays can model lists, tags, repeated values, embedded child objects, attributes, and bounded one-to-many relationships.

An array that grows indefinitely is a significant production risk. Continuous growth can increase document size, storage, cache usage, index impact, and write cost and can eventually encounter document-size constraints. Do not design an array that can grow indefinitely without evaluating lifetime cardinality and document-size consequences.

MongoDB supports BSON documents with a maximum nesting depth of 100 levels. A supported maximum is not a recommended design depth. Excessive nesting can complicate queries, indexes, schema evolution, application mapping, analytics, and troubleshooting. Production models should normally remain far shallower than the hard limit.

## Embedding vs. References

Relationships can be represented by embedding related data or storing references. The decision should consider whether data is read together, updated together, has the same lifecycle, has bounded cardinality and growth, tolerates duplication, and has shared atomicity requirements.

Embedding can provide useful data locality and natural single-document atomicity. References can be preferable where entities have independent lifecycles, high cardinality, frequent independent updates, excessive duplication, or growth patterns unsuitable for one document.

Data locality is valuable only when the document boundary matches actual access, update, and lifecycle patterns. Detailed modeling patterns are covered in Chapter 5.

## Single-Document Atomicity

MongoDB provides atomicity for writes affecting a single document, making document boundaries architecturally important. When fields that must change together naturally belong in one document, a suitable boundary can simplify consistency. MongoDB supports multi-document transactions when required, but transactions should not substitute for evaluating whether related data naturally belongs in one document.

## Document Size and Growth

Normal BSON documents have a maximum size of 16 MiB. This is a hard compatibility boundary, not a document-sizing recommendation. Applications should maintain substantial headroom rather than designing documents to approach the maximum.

Document growth can affect working set, indexes, write cost, replication, backup/restore, and storage. Risks include unbounded arrays, embedded histories, large text payloads, excessive nested data, binary content, and indefinitely growing audit information. Production reviews should evaluate expected lifetime document size, not merely current sample size.

## Large Binary Data and GridFS

Large binary objects should not automatically be embedded as large BSON fields. MongoDB provides GridFS, which stores files using metadata plus chunks and can be appropriate for files larger than the BSON document limit and certain streaming or partial-access requirements.

GridFS should not automatically be selected simply because an application stores files. It does not support multi-document transactions and is not an appropriate model when an entire file must be updated atomically as one operation. The existence of GridFS does not imply that MongoDB should replace object storage for every binary-file workload.

## Collection Validation

MongoDB collections can enforce validation rules. At an architectural level, a collection validator combines validation rules with `validationLevel` and `validationAction`. Validators can enforce expectations around required fields, BSON types, ranges, allowed structures, and application invariants. Validation level influences how rules are applied, while validation action controls handling of validation failures. Detailed syntax and administration are covered in Chapter 3.

## Schema Evolution

Production schemas change as applications evolve. A schema change can affect existing documents, new documents, old and new application versions, validators, indexes, and rollback compatibility. Schema evolution therefore requires backward-compatibility planning, application rollout sequencing, data migration, validator/index changes, mixed-schema handling, rollback, and cleanup.

Changing a collection validator does not automatically transform existing documents. Flexible schema can facilitate staged evolution, but it does not eliminate lifecycle management.

## Schema Drift

Schema evolution is intentional controlled change; schema drift is uncontrolled structural divergence. Uncontrolled variants of the same logical attribute can cause incomplete query results, index inefficiency, analytics inconsistencies, validation problems, application defects, and difficult migrations. DBAs should distinguish planned compatibility periods from accidental drift.

## Data Architecture and Indexes

Document structure directly influences index architecture, including index count, size, memory usage, write overhead, query efficiency, and maintenance. Schema and index design should not be reviewed independently.

When an indexed field contains an array, MongoDB automatically uses multikey index behavior. Array-heavy schemas can constrain compound-index design because multikey indexes have rules governing combinations of indexed array fields. Detailed multikey behavior belongs in Chapter 6.

## Database and Collection Namespaces

Collections have logical namespaces commonly represented as `database.collection`, for example `healthcare.patients`. Namespace architecture is covered in greater detail in Section 1.6.

## Logical vs. Physical Storage

Logical MongoDB objects should not be confused with physical storage implementation. The logical hierarchy database → collection → document → field is different from the persistence stack `mongod` → WiredTiger → storage structures → filesystem → storage device.

Do not assume a database maps to one operating-system file or a collection maps to one simple filesystem file. Do not infer physical storage layout directly from logical MongoDB object names.

## Production Data Architecture Example

Consider a commerce database with `customers`, `products`, `orders`, and `payments`. An order document might contain MongoDB identity, an application order number, customer reference, status, embedded item array, shipping address, monetary values, and timestamps.

A production DBA/DBRE should ask: How large can item arrays become? How often does embedded data change? Should historical values remain fixed? Which fields need indexes? Which values must be unique? What must update atomically? How will the document grow? How will the schema evolve? What happens during mixed application versions? How will the design affect backup and replication? Could future sharding change the requirements?

These questions turn document syntax into production data architecture.

## Operational Impact of Data Architecture

Data architecture affects query performance, index design, working set, WiredTiger cache, write cost, replication, backup/restore, sharding, storage growth, schema evolution, and application reliability. A poor data model cannot always be repaired later by adding CPU, memory, storage, or database nodes. DBAs and DBREs should participate in data architecture before production scale exposes structural weaknesses.

## Production Anti-Patterns

Avoid treating flexible schema as no schema; creating important production collections accidentally; inconsistent field naming; unbounded arrays; embedding everything; referencing everything; ignoring business uniqueness; treating 16 MiB as a target; designing near the 100-level nesting limit; ignoring document growth; treating GridFS as the default binary-storage solution; ignoring validator compatibility during deployments; and assuming logical objects map directly to filesystem files.

## DBA Data Architecture Checklist

Before approving a production collection, verify that database purpose, collection purpose/type, naming conventions, document structure, `_id` strategy, specialized collection behavior, business identifiers, uniqueness requirements, required fields, BSON types, embedding/reference decisions, array cardinality/bounds, nesting depth, lifetime growth, the 16 MiB limit, binary/file strategy, atomicity, indexes, multikey implications, schema validation, rollout compatibility, schema evolution, backward compatibility, retention, backup/restore, sharding implications, growth monitoring, and operational ownership are understood and documented.

## Key DBA Takeaways

1. MongoDB's logical hierarchy is database → collection → document → field → value.
2. A database is a logical container, not automatically a hard infrastructure-isolation boundary.
3. System databases have specialized purposes.
4. Collection type is an architectural choice.
5. Documents are MongoDB's fundamental application-data structures and use BSON.
6. Flexible schema still requires governance.
7. Standard collection documents require unique `_id` values; specialized types can differ.
8. MongoDB identity and business identity can be different.
9. Field naming is part of persistent schema governance.
10. Embedding can improve locality; references can suit independently managed/high-cardinality relationships.
11. Single-document atomicity makes document boundaries important.
12. Unbounded arrays are a significant production risk.
13. MongoDB supports up to 100 levels of BSON nesting, but production designs should normally be much shallower.
14. BSON documents have a 16 MiB hard maximum size; the limit is not a target.
15. GridFS is useful for appropriate chunked file-storage workloads but is not automatically preferable to object storage.
16. Validators can enforce structural/type expectations and must be coordinated with application evolution.
17. Schema evolution should be controlled; schema drift should be prevented.
18. Array fields can cause automatic multikey behavior and constrain index architecture.
19. Logical MongoDB objects should not be assumed to map directly to filesystem objects.
20. Data architecture affects indexes, working set, storage, replication, backup, sharding, and reliability.
21. Production modeling should evaluate lifetime growth, not only current size.
22. A poor data model cannot always be repaired by adding infrastructure.
