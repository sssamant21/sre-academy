## Learning Objectives

After completing this section, you should be able to explain BSON's role in MongoDB; distinguish BSON, standard JSON, Extended JSON, and `mongosh` representations; understand fields, values, field ordering, and duplicate-field restrictions; identify production-relevant BSON data types; choose appropriate numeric representations; understand ObjectId, BSON Date, BSON Timestamp, binary data, and UUID representation; explain BSON type ordering and type-aware comparison behavior; understand how BSON types affect queries, indexes, aggregation, and validation; identify driver serialization and numeric-precision risks; understand type drift and controlled type migration; and establish BSON governance standards for production systems.

## BSON in MongoDB Architecture

BSON, or Binary JSON, is MongoDB's native binary document serialization format.

```text
Application Type
      │
      ▼
MongoDB Driver
      │
      ▼
BSON Type
      │
      ▼
Stored Document
      │
      ├── Query Semantics
      ├── Index Semantics
      ├── Aggregation
      ├── Validation
      └── Downstream Interoperability
```

A BSON type is part of the persisted data contract. Type decisions can therefore affect applications long after the original document was written.

## BSON, JSON, Extended JSON, and mongosh

```text
BSON          → Native typed binary representation
Extended JSON → JSON-compatible BSON representation
mongosh       → Human-oriented shell representation
Standard JSON → Smaller type system
```

BSON extends JSON's model with database-oriented types including multiple numeric representations, ObjectId, Date, Timestamp, binary values, Decimal128, regular expressions, MinKey, MaxKey, and other specialized types. Careless conversion through ordinary JSON can change or lose BSON type information.

## BSON Document Architecture

A BSON document consists of ordered field/value elements. The type belongs to the stored value, so `{ customer_id: "1001" }` and `{ customer_id: 1001 }` represent different BSON types. This distinction can affect queries, sorting, validation, indexes, aggregation, drivers, and downstream systems.

### BSON Field Ordering

BSON documents have field ordering. MongoDB preserves field ordering in many document operations, although some operations can alter ordering and `_id` receives special handling. Ordinary application correctness should not depend on incidental field ordering unless a documented operation explicitly makes order significant.

### Duplicate Field Names

A production BSON document must not intentionally contain duplicate field names. Different tools, drivers, and operations can handle malformed duplicate-field documents unpredictably. **Production rule: field names must be unique within a document.** Integrity validation should include detection where legacy or externally generated BSON is suspected.

## Core BSON Types

| Category | Important BSON types |
|---|---|
| Text | String |
| Numeric | Int32, Int64, Double, Decimal128 |
| Logical | Boolean |
| Temporal | Date, Timestamp |
| Identity | ObjectId |
| Structural | Document, Array |
| Binary | Binary / BinData |
| Empty value | Null |
| Pattern | Regular Expression |
| Boundary/special | MinKey, MaxKey |
| Legacy/deprecated | Undefined, DBPointer, Symbol, JavaScript with Scope |

Supported BSON capability does not automatically mean recommended production application type.

## String

BSON strings contain UTF-8 character data. Strings are appropriate for textual information and identifiers intentionally modeled as text. They should not become the universal serialization type. Choose BSON types according to data semantics, not serialization convenience.

## Numeric Architecture

MongoDB supports Int32, Int64, Double, and Decimal128. They differ in range, precision, storage representation, driver mapping, and application semantics.

### Int32

Int32 is a signed 32-bit integer with range **-2,147,483,648 through 2,147,483,647**. Select it only when the value's expected lifetime range fits.

### Int64

Int64 is a signed 64-bit integer with range **-9,223,372,036,854,775,808 through 9,223,372,036,854,775,807**. Some programming-language number types cannot exactly represent every Int64 value, so driver/application compatibility must be validated.

### Double

BSON Double uses IEEE 754 binary floating-point representation. It is appropriate where binary floating-point behavior is acceptable, but decimal fractions cannot always be represented exactly.

### Decimal128

BSON Decimal128 provides decimal floating-point representation with **34 decimal digits of precision**. It is especially useful where decimal precision and rounding semantics matter, including currency, accounting, financial reconciliation, and precise decimal measurements.

Financial values should have an explicit numeric-type standard.

### Numeric Comparison and Type Consistency

MongoDB treats numeric BSON types as a common numeric category for many comparison purposes. That does not make Int32, Int64, Double, and Decimal128 architecturally interchangeable; they still differ in range, precision, representation, driver behavior, serialization, arithmetic characteristics, and downstream interoperability. Numeric comparison compatibility does not eliminate the need for numeric type consistency.

## Boolean

Use consistent Boolean representation. Uncontrolled mixtures such as `true`, `"true"`, `"Y"`, and `1` for one logical field complicate queries, validation, analytics, and migrations.

## Null and Missing Fields

A field explicitly containing `null` is structurally different from a document in which the field does not exist. Specific MongoDB query or sorting semantics can sometimes treat missing and null similarly, but they remain different document states. Production schemas should define whether null means unknown, not yet populated, intentionally empty, not applicable, or legacy compatibility.

## ObjectId

ObjectId is a 12-byte BSON type commonly used for MongoDB document identifiers:

```text
ObjectId — 12 bytes
       ├── 4-byte timestamp
       ├── 5-byte random process value
       └── 3-byte incrementing counter
```

ObjectIds are designed to be small, efficiently generated, and highly likely to be unique without a central sequence generator. ObjectId is a MongoDB identifier strategy, not automatically the application's business identity strategy.

### ObjectId and Time

ObjectId includes a timestamp component, but it should not be treated as the authoritative business-event timestamp. Timestamp resolution is one second, values generated within the same second do not provide guaranteed chronological event ordering, and client clock differences can invalidate assumptions. Use explicit application timestamps where temporal meaning matters.

## Temporal Architecture

BSON Date normally represents application time; BSON Timestamp is a specialized type used heavily by MongoDB sequencing and internal mechanisms.

### BSON Date

BSON Date represents an instant using a signed 64-bit integer containing milliseconds relative to the Unix epoch. The BSON specification describes this as UTC datetime. Timezone presentation is generally an application concern, so production systems should establish consistent timestamp and timezone conventions.

Avoid representing operational dates as arbitrary strings when temporal comparisons, sorting, TTL behavior, aggregation, validation, or interoperability are required.

### BSON Timestamp

BSON Timestamp is a specialized 64-bit type used heavily by MongoDB internal sequencing mechanisms, including replication-related operations. **Do not use BSON Timestamp merely because a field represents time.** For ordinary application time, BSON Date is normally appropriate.

## Structural Types

BSON supports embedded documents and arrays. MongoDB supports a maximum BSON nesting depth of **100 levels**. The maximum is a hard boundary, not a recommended design depth. Arrays affect document growth, query semantics, updates, aggregation, indexes, and multikey behavior.

## Binary Architecture

BSON supports binary values through BinData representations. Relevant categories include generic binary, legacy UUID, UUID, encrypted, time-series, sensitive, vector, and custom/specialized data. Binary subtype is part of the stored representation and can affect application and driver interoperability.

### UUID Representation

BSON distinguishes legacy UUID representation from standard UUID representation. Legacy UUID data may use subtype `3`, while standard UUID representation uses subtype `4`. New production systems should standardize UUID representation across all participating drivers and languages. UUID representation is a driver-and-schema contract.

## Specialized and Deprecated BSON Types

BSON supports specialized values such as Regular Expression, MinKey, and MaxKey. Legacy/deprecated types include Undefined, DBPointer, Symbol, and JavaScript with Scope. Do not select deprecated BSON types for new schemas without a specific compatibility requirement.

## BSON Comparison Architecture

MongoDB defines an ordering between BSON type categories:

```text
MinKey
  ↓
Null
  ↓
Numbers
  ↓
String / Symbol
  ↓
Object
  ↓
Array
  ↓
BinData
  ↓
ObjectId
  ↓
Boolean
  ↓
Date
  ↓
Timestamp
  ↓
Regular Expression
  ↓
JavaScript
  ↓
JavaScript with Scope
  ↓
MaxKey
```

Readers do not need to memorize this sequence. The production lesson is that mixed BSON types can produce valid but surprising comparison and sorting results.

### Type Bracketing

MongoDB comparison predicates are type-aware. Numeric BSON types form an important special category because MongoDB can compare numeric values across numeric BSON representations. A numeric value such as `42` and string `"42"` remain fundamentally different representations. A missing query result can therefore be a data-type problem rather than an engine or indexing problem.

## BSON Effects on Database Operations

BSON types influence query matching, comparison, sorting, index keys, aggregation, and validation. A type mismatch can surface as a query, index, aggregation, validation, or application problem even when the root cause is inconsistent stored data.

### BSON and Indexes

Indexes derive keys from BSON values. Type consistency matters for range predicates, sorting, index scans, query selectivity, uniqueness assumptions, and application expectations.

### BSON and Aggregation

Aggregation expressions are type-sensitive. Production pipelines should not become permanent compensation layers for uncontrolled type drift. When the data contract is wrong, correcting the data model is often preferable to indefinitely expanding query workarounds.

### BSON and Validation

Collection validators can enforce BSON type expectations and provide database-side enforcement rather than relying exclusively on application discipline. Detailed validation administration belongs in Chapter 3.

## Driver Type Mapping

```text
Programming-Language Type
           │
           ▼
      MongoDB Driver
           │
           ▼
        BSON Type
           │
           ▼
Stored Representation
```

Programming languages differ substantially in their native type systems. **Application-language type → driver serialization → BSON type is a production contract.** This is especially important for Int64, Decimal128, Date, UUID, Binary, and ObjectId.

### Numeric Precision Across Drivers

A database can store a correct Int64 or Decimal128 value while an application changes it during serialization or deserialization if the application numeric type cannot preserve it. This is particularly serious for financial values, large counters, identifiers, scientific measurements, and reconciliation workloads.

## Extended JSON

Standard JSON cannot directly represent every BSON type while preserving exact BSON semantics. MongoDB therefore provides Extended JSON, particularly important for ObjectId, Int64, Decimal128, Date, Timestamp, binary data, and other BSON-specific values.

### Canonical vs. Relaxed Extended JSON

Canonical Extended JSON emphasizes maximum type fidelity. Relaxed Extended JSON favors greater human readability where simpler JSON can safely represent the value. Production teams should know which representation their APIs, migration tools, exports, test fixtures, automation, and downstream applications produce and consume. Plain JSON interchange can silently change BSON semantics when the conversion pipeline does not preserve BSON-specific types.

## BSON Document Size

A normal BSON document has a maximum size of **16 MiB**. Document size includes field names, type information, values, arrays, embedded documents, and structural overhead. The 16 MiB maximum is a hard boundary, not a production sizing target.

BSON document size is not equivalent to WiredTiger physical disk usage, which also involves storage representation, compression, indexes, allocation, journaling, checkpoints, and filesystem behavior.

## Production Type Governance

Modern MongoDB environments commonly have multiple writers such as applications, batch processes, ETL pipelines, admin scripts, and migration tools. Every writer must follow the same persisted type contract. Collection validation can provide an important database-side control.

## BSON Type Drift

Type drift is a form of schema drift. It can be introduced by multiple application versions, different drivers, manual writes, ETL pipelines, imports, migration scripts, generic JSON transformations, or missing validation. Consequences include incomplete queries, incorrect sorting, aggregation complexity, index inefficiency, precision problems, analytics inconsistencies, and migration difficulty. **Preventing type drift is generally cheaper and safer than repairing it later.**

## BSON Type Migration

Changing the BSON type of a production field should be treated as a controlled data migration, not merely an application-code change. A production type migration must consider existing documents, new writes, old/new application versions, validators, indexes, aggregations, APIs, downstream consumers, and rollback. A compatibility period may be required while old and new application versions coexist.

## Failure Scenarios and Troubleshooting

When MongoDB returns an unexpected application or query result, inspect the actual BSON representation before assuming an engine problem.

```text
Unexpected Application / Query Behavior
              │
              ▼
        Inspect Field
              │
      ┌───────┼─────────┐
      ▼       ▼         ▼
 Missing?   Null?    Wrong Type?
                       │
                       ▼
                  Mixed Types?
                       │
                       ▼
                 Which Producer?
                       │
                       ▼
              Driver Serialization?
                       │
                       ▼
               Import / Migration?
                       │
                       ▼
                 Validator Gap?
```

Representative incidents include numeric fields stored as strings, mixed date or Boolean representations, precision loss, UUID mismatch, null/missing confusion, JSON conversion loss, and duplicate field names.

### Diagnostic Approach

Verify whether the field exists; whether it contains null; its actual BSON type; whether multiple types exist; whether malformed duplicate fields are present; which producer and driver wrote it; whether import/export or generic JSON changed it; whether validators permitted it; and whether old application versions still write legacy data. MongoDB's `$type` capabilities can assist with identifying stored BSON types.

## Production BSON Standards

| Data category | Example production approach |
|---|---|
| MongoDB identity | ObjectId unless requirements dictate another supported strategy |
| Business identifiers | Explicit documented type |
| Money | Decimal128 when decimal precision is required |
| Counters | Int32 or Int64 based on expected lifetime range |
| Measurements | Double or Decimal128 according to precision needs |
| Boolean state | Boolean |
| Application timestamps | BSON Date |
| UUID | Standardized representation across drivers |
| Optional fields | Explicit null/missing semantics |
| Binary data | Explicit BinData subtype/architecture |
| Large files | Deliberate GridFS or object-storage decision |

These are architecture examples rather than universal mandates; the correct standard depends on the workload.

## Production Anti-Patterns

Avoid storing every value as a string; mixing numeric types without an architectural reason; using Double automatically for financial data; allowing large Int64 values through unsafe application numeric types; using ObjectId time as authoritative business chronology; using BSON Timestamp for ordinary application dates; storing operational dates as arbitrary strings; mixing legacy and standard UUID representations; treating null and missing as automatically equivalent; intentionally creating duplicate field names; relying on incidental field order; passing BSON through generic JSON without type preservation; ignoring driver serialization; allowing each producer to select its own representation; fixing permanent type drift only with increasingly complex queries; and confusing BSON document size with physical WiredTiger storage.

## DBA BSON Architecture Checklist

Before approving a production schema, verify BSON types for critical fields; unique field names; field-order assumptions; Int32/Int64 lifetime ranges; application support for large Int64 values; financial precision and Decimal128 requirements; appropriate Double usage; Boolean consistency; null/missing semantics; ObjectId strategy; explicit business chronology; Date/Timestamp semantics; timezone conventions; UUID representation; binary subtypes; Extended JSON strategy; driver/ETL/import/export type preservation; validation controls; mixed-type detection; controlled type migrations; document-size and nesting boundaries; index compatibility; downstream mappings; and a common persisted type contract for every writer.
