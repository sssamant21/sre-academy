## Learning Objectives

After completing this section, you should be able to:

- explain MongoDB server-process architecture;
- distinguish `mongod` and `mongos`;
- distinguish an operating-system process from its MongoDB topology role;
- understand process placement in standalone, replica-set, and sharded-cluster deployments;
- understand high-level startup, runtime, and shutdown architecture;
- explain the relationship between `mongod` and WiredTiger;
- distinguish WiredTiger cache, other MongoDB memory, and filesystem cache;
- understand MongoDB process behavior under container memory limits;
- recognize FTDC as part of MongoDB diagnostic architecture;
- distinguish process availability from topology, database-service, and application availability;
- understand supported clean-shutdown behavior;
- recognize important CPU, memory, disk, file-descriptor, NUMA, and THP considerations;
- monitor and troubleshoot MongoDB processes systematically; and
- design safe process lifecycle and production maintenance procedures.

## MongoDB Process Architecture

MongoDB deployments are built from server processes whose responsibilities depend on configuration and topology.

```text
MongoDB Deployment
        │
        ├── mongod
        │      ├── Database Operations
        │      ├── Storage Engine
        │      ├── Replication
        │      └── Internal Services
        │
        └── mongos
               ├── Client Connections
               ├── Routing
               ├── Metadata Cache
               └── Distributed Coordination
```

> **A MongoDB server process is not the same thing as the topology role that process currently performs.**

## Process vs. Topology Role

Primary and secondary are replica-set states or roles of `mongod`; they are not separate executables.

```text
mongod → PRIMARY
mongod → SECONDARY
mongod → shard member
mongod → config server
```

During an election, existing server processes remain while their topology states can change. Process identity and topology identity are different operational dimensions.

## The `mongod` Process

`mongod` is MongoDB's primary database server process. Depending on configuration and deployment architecture, it can participate as a standalone server, replica-set member, shard-server member, config-server member, or config-shard member.

Core responsibilities can include accepting connections, authentication and authorization, command processing, query and write execution, transactions, indexes, storage-engine interaction, replication, topology responsibilities, diagnostics, logging, and internal/background work.

## The `mongos` Process

`mongos` is MongoDB's routing process for sharded clusters. It accepts client connections, caches sharding metadata, routes requests, and coordinates distributed operations.

Unlike a data-bearing `mongod`, `mongos` maintains no persistent database state.

> **Stateless does not mean noncritical or resource-free.**

An unavailable or saturated `mongos` tier can make healthy shards inaccessible to applications.

## Sharded-Cluster Application Path

Applications should access sharded MongoDB clusters through `mongos`.

```text
Application
     │
     ▼
   mongos
     │
     ▼
Sharded Cluster
     ├── Shard A
     ├── Shard B
     └── Shard C
```

> **Direct shard connections are exceptional administrative or maintenance paths, not normal application architecture.**

MongoDB 8.x places additional controls around direct shard operations. Detailed direct-shard administration belongs in Chapter 11.

## Deployment Process Architecture

### Standalone

A standalone deployment uses one `mongod` and does not provide replica-set failover. Production workloads requiring high availability should normally use an appropriate replicated architecture.

### Replica Set

A replica set consists of multiple `mongod` processes. Each data-bearing member has its own process, memory, WiredTiger instance, storage, logs, connections, runtime state, and OS/container resources. Replication coordinates these processes into one logical database service.

### Sharded Cluster

A sharded cluster introduces routing, shard, and configuration responsibilities. Each shard is normally a replica set of `mongod` processes. Config-server functionality maintains sharded-cluster metadata, while `mongos` uses cluster metadata for routing and distributed coordination.

### MongoDB 8.x Config Shard

MongoDB 8.0 introduced config-shard architecture. A config shard combines config-server and shard-server responsibilities and can store both cluster metadata and application data. Some capabilities can still require dedicated config-server architecture, so topology requirements must be validated before choosing a config shard. Detailed architecture belongs in Chapter 11.

## Process Startup Architecture

A conceptual startup sequence is:

```text
Process Start
     │
     ▼
Load Configuration
     │
     ▼
Validate Environment
     │
     ▼
Initialize Storage / Runtime
     │
     ▼
Initialize Networking
     │
     ▼
Initialize Topology Services
     │
     ▼
Initialize Diagnostics
     │
     ▼
Accept Work
```

Startup depends on configuration, filesystem access, permissions, storage, network/ports, TLS/keyfiles, OS resources, version/compatibility state, and diagnostic paths.

> **"`mongod` will not start" is a symptom category, not a root cause.**

## Production Configuration

Self-managed production deployments should normally use controlled configuration files. Configuration should be version controlled, reviewed, repeatable, auditable, automated where appropriate, and protected against drift.

> **Use controlled, version-managed configuration rather than ad hoc command-line startup for production processes.**

Detailed configuration architecture belongs in Chapter 2.

## Operating-System Identity and PID

MongoDB processes should run under appropriately least-privileged OS identities with access to required data, log, configuration, certificate, keyfile, runtime, and diagnostic paths.

A PID identifies a particular OS process instance. It is not the replica-set member identity, hostname, shard identity, topology role, or MongoDB namespace. A restart normally creates a new PID while the configured MongoDB member continues to represent the same topology member.

## FTDC — Full Time Diagnostic Data Capture

MongoDB server processes include Full Time Diagnostic Data Capture (FTDC), which continuously captures diagnostic information useful for troubleshooting.

```text
mongod / mongos
      │
      ├── Runtime Services
      └── FTDC
           │
           ▼
      diagnostic.data
```

For `mongod`, diagnostic data is associated with the database path; `mongos` diagnostic storage is associated with its logging environment. Permissions to diagnostic locations are operationally important, and FTDC subsystem failure can affect the originating process.

> **Diagnostic-directory permissions are part of process availability—not merely monitoring configuration.**

## MongoDB Runtime Architecture

```text
                    mongod
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   Connections    Operations    Internal Work
        │             │             │
 Networking        Queries       Replication
 Authentication    Writes        Diagnostics
 Sessions          Indexes       Maintenance
                   Transactions
                      │
                      ▼
                  WiredTiger
```

This is a conceptual architecture, not a fixed one-thread-per-component implementation.

## Connection and Operation Processing

Drivers commonly use connection pools, so connection pressure can grow with application instances, pools per instance, and connections per pool. Connection architecture is covered in Sections 1.8–1.12.

MongoDB processes handle reads, writes, aggregations, transactions, index operations, administrative commands, and monitoring operations. Detailed query execution architecture is covered later in Chapter 1.

## `mongod` and WiredTiger

For the MongoDB 8.x baseline, WiredTiger provides persistent storage-engine functionality within `mongod`.

```text
mongod
   │
   ▼
MongoDB Server Layer
   │
   ▼
WiredTiger
   ├── Internal Cache
   ├── Checkpoints
   ├── Compression
   ├── Storage Management
   └── Durability Integration
   │
   ▼
Filesystem / Storage
```

WiredTiger is not a separate database daemon. Consequently, `mongod` CPU and memory usage include storage-engine activity.

## MongoDB Memory Architecture

```text
Host / Container Memory
         │
         ├── mongod
         │      ├── WiredTiger Internal Cache
         │      └── Other MongoDB Memory
         ├── Filesystem Cache
         ├── Operating System
         └── Other Processes / Agents
```

MongoDB memory analysis must account for more than the WiredTiger internal cache. Other consumers include connections, query and aggregation execution, indexes, replication, runtime metadata, encryption, internal services, and process overhead.

### Container Memory Boundary

Physical host RAM can substantially exceed memory available to a MongoDB container.

> **Do not size MongoDB memory from physical host RAM alone when `mongod` is constrained by a container memory limit.**

WiredTiger cache and total process memory must be evaluated against effective memory available to MongoDB.

## Internal and Background Work

A MongoDB process performs foreground client work and internal/background activity such as replication, storage-engine maintenance, checkpoints, cache eviction, diagnostic capture, TTL processing, session maintenance, and other runtime services. These are categories of activity rather than promises about fixed thread implementations.

> **Low application traffic does not imply an idle MongoDB process.**

## Thread and Concurrency Architecture

MongoDB server processes perform concurrent work using multiple execution threads and internal concurrency mechanisms. Exact implementation can evolve between versions.

> **One `mongod` process does not mean one execution thread.**

## CPU Architecture

High `mongod` CPU can originate from queries, aggregations, writes, indexing, replication, compression, encryption, storage-engine work, and internal maintenance.

> **High `mongod` CPU is evidence, not a root-cause statement.**

A production RCA should identify the workload or subsystem causing the CPU demand.

## Disk and I/O Architecture

For a data-bearing `mongod`, I/O flows through WiredTiger to the filesystem and underlying storage. Performance depends on latency, throughput, IOPS, queueing, filesystem behavior, free space, cache efficiency, and workload patterns.

Storage problems can surface as slow queries, write latency, checkpoint pressure, replication lag, slow startup, slow recovery, and database instability.

## File Descriptor Architecture

MongoDB requires OS file descriptors for files, sockets, and related resources. Low limits can cause failed connections, file-open failures, degradation, and availability problems.

MongoDB generates a startup warning when the open-files limit is below **64,000**. This is a warning boundary, not a universal production sizing target. Production limits must be validated against deployment and workload.

## NUMA Considerations

NUMA can materially influence database performance on some multi-socket systems. Poor NUMA configuration can contribute to uneven memory access, high system CPU, inconsistent latency, and unexpected process behavior.

> **NUMA configuration belongs in production host validation rather than being treated only as an application-level issue.**

## Transparent Huge Pages

THP guidance is version-sensitive:

```text
MongoDB 8.0         → THP guidance: enable
MongoDB 7.0 earlier → THP guidance: disable
```

> **Do not apply legacy MongoDB host-tuning runbooks to MongoDB 8.x without revalidation.**

Detailed host preparation belongs in Chapter 2.

## Process Lifecycle and Process Managers

Process lifecycle can be controlled by systemd, container runtimes, Kubernetes, MongoDB operators, automation, or managed services. Understanding the controlling layer is important during restart and crash-loop troubleshooting.

On applicable self-managed Linux package installations, `systemctl status/start/stop/restart mongod` manages the OS service. An active service does not prove replica-set health, primary availability, authentication, storage health, or application reachability.

> **A running service is not equivalent to a healthy database service.**

## Clean Shutdown Architecture

MongoDB should normally be stopped using supported clean-shutdown mechanisms. For a replica-set primary, shutdown can include an attempt to step down before process termination.

```text
Shutdown Requested
       │
       ▼
Replica-Set Primary?
       │
       ├── Yes → Attempt Stepdown
       │
       ▼
Quiesce
       │
       ▼
Finish / End Remaining Work
       │
       ▼
Storage / Runtime Shutdown
       │
       ▼
Process Exit
```

Depending on platform and deployment, supported clean-shutdown mechanisms can include the MongoDB shutdown command, `mongod --shutdown`, `SIGTERM`, `CTRL-C`, and `systemd stop`.

A normal Linux `kill <pid>` sends `SIGTERM`, which MongoDB handles as a clean-shutdown request.

### `SIGKILL` / `kill -9`

`SIGKILL` immediately terminates the OS process without allowing MongoDB to execute its normal shutdown path.

> **Do not use `SIGKILL` (`kill -9`) as a MongoDB shutdown method. Use supported clean-shutdown mechanisms.**

An extraordinary host-level emergency where clean control is impossible should be treated as an abnormal failure scenario, not routine procedure.

## Evidence Before Restart

Restarting MongoDB can restore service but can also remove valuable incident evidence. Where incident severity and recovery requirements allow, capture timestamps, process status, logs, FTDC, CPU/memory, disk usage, storage latency, network state, replica-set state, current operations, connections, recent errors, and application symptoms.

```text
Incident
   │
   ▼
Capture Evidence
   │
   ▼
Stabilize / Recover
   │
   ▼
Root-Cause Analysis
```

> **A restart may restore service, but it should not automatically substitute for diagnosis. Preserve evidence when practical.**

On supported systems, advanced signal-based thread-backtrace capture can provide additional evidence before restart; such procedures should be documented and tested before emergency use.

## Restart and Replica Sets

Restarting a replica-set primary can cause an election. Operational impact depends on replica-set health, voting majority, member eligibility, replication state, driver topology discovery, application retry behavior, and connection configuration. Detailed election architecture belongs in Chapters 9 and 10.

## Rolling Process Maintenance

Many replica-set maintenance procedures can be performed member by member. A safe rolling procedure requires each maintained member to return healthy, replication and topology to be validated, and only then proceeding to the next member.

> **"Rolling" does not automatically mean "safe." Safety depends on health validation between steps.**

## Process Health vs. Database-Service Health

```text
Process Running
      │
      ▼
Listener Reachable
      │
      ▼
MongoDB Responding
      │
      ▼
Authentication Working
      │
      ▼
Topology Healthy
      │
      ▼
Storage Healthy
      │
      ▼
Capacity Available
      │
      ▼
Application Path Healthy
```

A running PID proves process existence. It does not prove database-service health. Conversely, a single failed `mongod` does not necessarily make a logical database unavailable when a healthy replica set can fail over.

## Kubernetes and Container Process Model

In containerized environments, MongoDB process health exists within container, pod, node, and Kubernetes-cluster health layers. Pod restarts, probes, StatefulSets, operators, node eviction, resource limits, and persistent volumes add orchestration behavior.

> **Pod health is not equivalent to replica-set health or application health. A restarted pod is an orchestration event—not proof of MongoDB recovery.**

Detailed Kubernetes operation belongs in Book 4.

## Managed-Service Process Model

Managed services such as MongoDB Atlas abstract some direct OS and process controls, but process-vs.-topology role, routing-vs.-data tier, resource pressure, replica health, storage health, and database-service availability remain relevant architectural concepts.

## Process Security Architecture

Process security spans OS identity, filesystem permissions, network exposure, TLS, authentication, authorization, and secrets/keys. Failures at any layer can prevent a running process from providing usable service.

## Process Resource Isolation

MongoDB requires predictable CPU, memory, storage, file descriptors, network capacity, and OS/container resources. Monitoring agents, security agents, backup processes, log forwarders, and other workloads compete for the same resources. Capacity planning must account for the entire host/container environment, not `mongod` alone.

## Logging, Monitoring, and Alerting

Production observability should correlate four layers:

```text
Application
     │
MongoDB
     │
Process / OS / Container
     │
Infrastructure
```

Useful signals include application latency/errors; MongoDB operations, connections, WiredTiger, replication, topology, errors, and FTDC; process availability, restarts, CPU, memory, file descriptors, I/O, network, OOM events, and container limits; and infrastructure host/node, storage, network, cloud, and Kubernetes health.

Useful alerts include `mongod`/`mongos` unavailable, unexpected or repeated restarts, high CPU, sustained memory pressure, OOM kills, file-descriptor pressure, disk-space or storage-latency pressure, connection pressure, unhealthy replica members, replication lag, and primary unavailability. Thresholds should be based on workload baselines and service objectives rather than universal constants.

## Common Process Failure Scenarios

Representative failure categories include:

1. process will not start;
2. process running but listener unreachable;
3. listener reachable but application cannot connect;
4. repeated restart or crash loop;
5. OOM kill;
6. high CPU;
7. disk full or high storage latency;
8. file-descriptor exhaustion;
9. unhealthy replica-set member; and
10. unhealthy `mongos` tier.

For repeated restarts, identify the initiator: `mongod` failure, systemd, OOM killer, container runtime, Kubernetes, operator, health probe, automation, host reboot, or human operator.

> **Identify what restarted the process before assuming MongoDB restarted itself.**

## Process Troubleshooting Workflow

```text
MongoDB Unavailable
      │
      ▼
Process Running?
      │
      ▼
Listener Reachable?
      │
      ▼
MongoDB Responding?
      │
      ▼
Authentication Working?
      │
      ▼
Topology Healthy?
      │
      ▼
Storage / Capacity Healthy?
      │
      ▼
Application Path Healthy?
```

On self-managed Linux, an initial pass may include `systemctl status mongod`, process inspection, listener inspection, filesystem capacity/inode checks, memory, and load, followed by MongoDB logs, FTDC, connectivity, replica-set state, connections, current operations, storage latency, and application behavior.

## Production Process Inventory

Maintain a process/topology inventory including deployment, environment, host/pod, process, role, version, process manager, restart policy, owner, replica-set/shard identity, zone/AZ, port, data path, OS/container, CPU/memory, storage, TLS, monitoring, backup coverage, and maintenance ownership.

## Process Architecture Anti-Patterns

Avoid:

- confusing `mongod` with the primary role;
- treating `mongos` as data-bearing;
- assuming stateless means noncritical;
- allowing normal application traffic to bypass `mongos` in sharded clusters;
- assuming a running PID means MongoDB is healthy;
- monitoring only service status;
- repeatedly restarting without investigating evidence;
- using `SIGKILL` as a shutdown procedure;
- treating high CPU as the final RCA;
- ignoring background/internal work or filesystem cache;
- sizing containerized MongoDB from host RAM alone;
- applying MongoDB 7.x THP guidance blindly to MongoDB 8.x;
- ignoring NUMA or file-descriptor limits;
- assuming pod health equals replica-set health;
- performing rolling maintenance without health validation;
- failing to identify the source of repeated restarts;
- running MongoDB with unnecessary OS privilege; and
- failing to inventory process versions, roles, managers, and restart policies.

## DBA Process Architecture Checklist

Before approving or changing production MongoDB process architecture, verify topology and roles are documented; application routing is correct; versions and configuration are controlled; OS identities and permissions follow least privilege; FTDC paths are healthy; network/TLS/secrets are correct; CPU, memory, cache, container limits, disk, file descriptors, NUMA, and THP are validated; restart/OOM/topology monitoring exists; clean-shutdown and evidence-capture procedures exist; rolling maintenance has health gates; orchestration behavior is understood; supporting agents are included in capacity planning; and process inventory is current.

## Key DBA Takeaways

1. MongoDB deployments are built primarily from `mongod` and, for sharded clusters, `mongos`.
2. A process is not the same thing as its topology role.
3. Primary and secondary are replica-set states of `mongod`.
4. `mongos` is a stateless but operationally critical routing tier.
5. Applications should access sharded clusters through `mongos`.
6. Each data-bearing replica member has its own `mongod`, WiredTiger instance, memory, storage, and runtime state.
7. MongoDB 8.x can use config-shard architecture.
8. Startup depends on configuration, permissions, storage, networking, security material, OS resources, compatibility state, and diagnostics.
9. Production configuration should be controlled, repeatable, and versioned.
10. OS identity, PID, member identity, and topology role are distinct concepts.
11. FTDC is part of process diagnostic architecture and its storage permissions matter to availability.
12. WiredTiger operates within `mongod`; process resource usage includes storage-engine activity.
13. Memory analysis must include WiredTiger cache, other MongoDB memory, filesystem cache, OS, and other processes.
14. Container memory limits must be considered separately from physical host RAM.
15. Low application traffic does not imply an idle MongoDB process.
16. MongoDB is concurrent and multithreaded.
17. High `mongod` CPU is evidence, not a final RCA.
18. Storage latency can manifest across queries, writes, checkpoints, replication, startup, and recovery.
19. The open-files warning boundary below 64,000 is not a universal sizing target.
20. NUMA belongs in host validation.
21. MongoDB 8.0 THP guidance differs from MongoDB 7.0 and earlier.
22. Process state and topology state should be monitored independently.
23. A running service does not prove database-service health.
24. Supported clean shutdown can include `SIGTERM`.
25. Primary shutdown can involve stepdown and quiesce behavior.
26. `SIGKILL` / `kill -9` must not be used as a normal shutdown procedure.
27. Preserve incident evidence before restart when practical.
28. Restarting a primary can trigger an election.
29. Rolling maintenance requires health validation between steps.
30. Pod health is not equivalent to replica-set or application health.
31. Monitoring should correlate application, MongoDB, process/container, and infrastructure signals.
32. Repeated restarts require identifying the initiating component.
33. Production inventories should include process manager and restart policy.
34. Troubleshooting should progress process → listener → MongoDB response → authentication → topology → storage/capacity → application path.
