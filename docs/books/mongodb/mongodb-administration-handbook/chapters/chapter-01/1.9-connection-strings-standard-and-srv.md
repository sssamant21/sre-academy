## Learning Objectives

After completing this section, you should be able to:

- explain the role of MongoDB connection strings;
- distinguish `mongodb://` from `mongodb+srv://`;
- construct connection strings for standalone, replica-set, and sharded deployments;
- understand seed-list discovery and replica-set identity;
- explain `directConnection`;
- understand SRV and TXT discovery architecture;
- explain SRV hostname, port, and TLS behavior;
- understand `/defaultauthdb` and `authSource`;
- safely handle URI credentials and percent encoding;
- distinguish connection configuration from runtime topology;
- recognize topology-discoverability problems;
- understand the boundary between topology-aware and explicit load-balanced connectivity;
- manage connection strings securely across environments;
- validate connection strings before production deployment; and
- troubleshoot URI failures systematically.

## MongoDB Connection-String Architecture

A MongoDB connection string, commonly called a MongoDB URI, provides the initial configuration a client needs to locate and connect to a MongoDB deployment.

```text
Application
     │
     ▼
MongoDB Connection String
     │
     ├── URI Scheme
     ├── Credentials
     ├── Hosts / Discovery Name
     ├── Authentication Database
     └── Connection Options
     │
     ▼
MongoDB Driver
     │
     ▼
Initial Discovery
     │
     ▼
MongoDB Deployment
```

A connection string can influence initial server discovery, topology expectations, authentication, TLS, read behavior, retry behavior, timeout behavior, and driver-specific connection behavior.

> **A MongoDB connection string defines initial connectivity and discovery configuration; it is not necessarily a static description of the deployment topology used throughout the client's lifetime.**

## MongoDB URI Schemes

MongoDB supports two principal connection-string schemes:

```text
MongoDB URI
    │
    ├── mongodb://
    │      └── Explicit initial hosts
    │
    └── mongodb+srv://
           └── DNS-based discovery
```

## Standard Connection String — `mongodb://`

General form:

```text
mongodb://[username:password@]host1[:port1][,hostN[:portN]][/[defaultauthdb][?options]]
```

When options are specified without `/defaultauthdb`, preserve the `/` between the host list and the query string:

```text
mongodb://mongo01.example.com,mongo02.example.com/?replicaSet=rs0
```

### Standalone

```text
mongodb://mongo01.example.com:27017/
```

A standalone URI does not provide replica-set failover.

### Replica Set

A standard replica-set URI should provide an appropriate seed list and identify the expected replica set:

```text
mongodb://mongo01.example.com:27017,mongo02.example.com:27017,mongo03.example.com:27017/?replicaSet=rs0
```

```text
Standard Replica-Set URI
          │
          ▼
Seed List
          │
          ▼
Initial Reachability
          │
          ▼
SDAM
          │
          ▼
Runtime Replica-Set Topology
```

> **Replica-set hosts in a standard URI are discovery seeds rather than a permanent client-side routing table.**

Multiple initial seeds improve startup resilience because topology discovery cannot begin until the client reaches an initial discovery endpoint.

### `replicaSet`

The `replicaSet` option identifies the expected topology:

```text
replicaSet=rs0
```

An incorrect replica-set name can allow initial network contact while preventing establishment of the intended topology.

### `directConnection`

`directConnection=true` targets the specified server rather than performing normal replica-set discovery.

> **Do not use `directConnection=true` to compensate for incorrectly exposed or incorrectly configured production replica-set networking.**

### Sharded Clusters

Normal sharded application traffic connects through `mongos`:

```text
Application
     │
     ▼
Driver
     │
     ▼
mongos
     │
     ▼
Sharded Cluster
```

> **Normal sharded application connection strings identify `mongos` routing endpoints, not individual shard members.**

## DNS Seed-List Connection String — `mongodb+srv://`

The SRV format delegates initial endpoint discovery to DNS:

```text
mongodb+srv://cluster.example.com/
```

```text
MongoDB URI
     │
     ▼
DNS Discovery Root
     │
     ▼
DNS SRV
     │
     ▼
MongoDB Endpoints
     │
     ▼
Driver
     │
     ▼
MongoDB Deployment
```

Where supported and operationally appropriate, SRV connection strings simplify endpoint discovery and management.

### SRV URI Rules

A `mongodb+srv://` URI:

- uses one DNS hostname as its discovery root;
- does not contain a comma-separated seed list;
- does not specify an explicit port in the URI;
- obtains hosts and ports through DNS SRV records;
- can obtain supported configuration through DNS TXT records; and
- enables TLS by default.

```text
Standard
mongodb://host1:27017,host2:27017/

SRV
mongodb+srv://cluster.example.com/
```

> **An SRV URI identifies one DNS discovery root—not a manually enumerated host list.**

## DNS SRV Architecture

```text
mongodb+srv://cluster.example.com
               │
               ▼
             DNS
               │
               ▼
          SRV Records
               │
        ┌──────┼──────┐
        ▼      ▼      ▼
      Host A Host B Host C
        │      │      │
       Port   Port   Port
```

Applications should allow supported MongoDB drivers to process MongoDB SRV discovery rather than implementing it manually.

## DNS TXT Architecture

```text
DNS
 │
 ├── SRV
 │     └── Hosts + Ports
 │
 └── TXT
       └── Supported Connection Options
```

For MongoDB 8.x connection-string discovery, relevant TXT options are:

```text
replicaSet
authSource
```

Do not assume arbitrary MongoDB connection options can be stored in the TXT record. A valid configuration should not depend on multiple conflicting TXT records.

> **With SRV connectivity, DNS becomes both discovery infrastructure and part of the connection configuration.**

## URI vs. TXT Precedence

When the same supported option is available through DNS TXT and the URI, the explicit URI value takes precedence.

```text
DNS TXT Value
      │
      ▼
Connection Configuration
      ▲
      │
Explicit URI Value
      └── Overrides matching TXT value
```

## SRV and TLS

The URI schemes have different documented TLS defaults:

```text
mongodb://
    └── TLS default: false

mongodb+srv://
    └── TLS default: true
```

Production TLS policy should be explicitly governed rather than relying only on URI defaults. Validate CA trust, certificate identity, hostname validation, certificate expiration, client TLS configuration, and deployment-specific trust requirements.

> **Successful SRV discovery does not prove successful TLS connectivity.**

## Authentication in the URI

Credentials can be represented in a URI, but a credential-bearing URI must be treated as a secret. Production credentials should normally originate from approved secret-management mechanisms rather than application source code.

## Authentication Database Selection

```text
authSource specified?
        │
        ├── Yes → Use authSource
        │
        └── No
              │
              ▼
      defaultauthdb present?
              │
              ├── Yes → Use defaultauthdb
              └── No  → Use admin
```

> **When credentials are supplied, `authSource` explicitly identifies the authentication database. If `authSource` is absent, `/defaultauthdb` is used when present. If neither is supplied, authentication defaults to `admin`.**

Some clients, including `mongosh`, can also use the URI database component as their initial/default database. Application-driver behavior outside authentication semantics should be checked against the specific driver.

### `authSource`

```text
mongodb://appuser:<redacted>@mongo01.example.com/appdb?authSource=admin
```

A valid username and password can still fail authentication when `authSource` is incorrect.

### Atlas and `authSource`

MongoDB Atlas commonly uses SRV-based connection strings, and Atlas SRV configuration can provide `authSource=admin` through DNS TXT configuration. Detailed Atlas networking and security architecture belongs in Book 4.

## Authentication Mechanisms

Authentication mechanisms and required URI options depend on MongoDB edition or service, server version, driver, authentication architecture, and identity provider. Implementation details belong in Chapter 8.

## URI Credential Encoding

URI-sensitive username/password characters include:

```text
$  :  /  ?  #  [  ]  @
```

They require appropriate percent encoding when used in URI credential components.

```text
Raw:      P@ssword
URI-safe: P%40ssword
```

Do not use unsecured online tools to transform production secrets.

## Credential Exposure Risk

Credential-bearing URIs can leak through source code, Git repositories, application logs, exception messages, environment dumps, process arguments, shell history, monitoring systems, support tickets, screenshots, and chat messages.

> **Treat a credential-bearing MongoDB URI as a secret.**

Sanitize connection strings before logging, documenting, or sharing them.

## Connection Options

URI options can influence topology, TLS, authentication, read behavior, retry behavior, pooling, and timeouts. Exact option support, defaults, and behavior can depend on the driver and driver version.

> **Do not assume that every MongoDB driver exposes every connection option identically.**

### URI Parsing Notes

- follow the documented URI grammar;
- preserve the `/` before `?` where required;
- percent-encode URI-sensitive credential characters;
- separate multiple options with `&`;
- do not assume option values are case-insensitive;
- validate option support against the actual driver/version; and
- do not infer driver defaults from another programming language's driver.

### Read Preference

Read preference participates in driver server selection. Detailed behavior belongs in Section 1.10 and Chapter 4.

### Retry Configuration

Retries can improve resilience for supported operations, but they are not a substitute for healthy topology, sufficient capacity, or correct application error handling. Poorly controlled retries can amplify incidents.

### Timeout Configuration

Connection configuration can influence server-selection, connection-establishment, pool-checkout, network-I/O, and operation-execution timeout domains. Detailed pool and timeout architecture belongs in Section 1.11.

## Connection String vs. Runtime Topology

```text
Connection String
       │
       ▼
Initial Discovery
       │
       ▼
SDAM
       │
       ▼
Runtime Topology
```

A replica-set primary election normally does not require rewriting the application's replica-set connection string.

> **Connection configuration and runtime topology are related but distinct concepts.**

## Topology Discoverability

A client can reach a seed while being unable to reach the members discovered from that seed:

```text
Client
  │
  ▼
Seed Reachable
  │
  ▼
Replica Set Advertises Members
  │
  ├── mongo01.internal
  ├── mongo02.internal
  └── mongo03.internal
          │
          X
Client Cannot Resolve / Reach
```

This is especially relevant with NAT, containers, Kubernetes, split DNS, private/public DNS, VPNs, hybrid networks, and cross-network connectivity.

> **Initial seed reachability does not guarantee topology reachability.**

The hostnames advertised by the MongoDB topology must be meaningful to the clients expected to use them.

## Load Balancing and MongoDB

Normal topology-aware MongoDB clients should not be placed behind arbitrary generic load-balancing designs that hide topology semantics. MongoDB also supports an explicit load-balanced connection mode for supported architectures:

```text
loadBalanced=true
```

This is a separate connection model with specific compatibility and topology constraints.

> **Do not treat generic network load balancing and MongoDB's documented load-balanced connection mode as the same architecture.**

## Kubernetes Considerations

Kubernetes adds DNS and service-discovery layers. A connection string that works inside a cluster may not work from an external network.

> **MongoDB topology hostnames must be resolvable and reachable from the clients expected to use that topology.**

Detailed Kubernetes deployment architecture belongs in Book 4.

## Environment Isolation

```text
Development URI
      ≠
Staging URI
      ≠
Production URI
```

> **A connection string pointing to the wrong environment can be more dangerous than one that fails completely.**

Connectivity success does not prove environment correctness.

## Configuration and Secret Management

Production connection strings should be managed through controlled configuration and approved secret-management mechanisms. Avoid uncontrolled URI copies in scripts, personal files, documentation, tickets, chat, shell history, and source repositories.

## Connection-String Rotation

```text
Prepare New Configuration
          │
          ▼
Deploy / Reload
          │
          ▼
Validate Connectivity
          │
          ▼
Observe
          │
          ▼
Retire Old Configuration
```

Avoid invalidating old configuration before confirming successful replacement connectivity unless the security situation requires immediate revocation.

## Connection-String Validation

```text
URI Syntax
   │
   ▼
Environment Identity
   │
   ▼
DNS
   │
   ▼
Network
   │
   ▼
TLS
   │
   ▼
Authentication
   │
   ▼
Topology
   │
   ▼
Server Selection
   │
   ▼
Application Operation
```

> **A connection string is not production-valid merely because it parses successfully.**

Where appropriate, connectivity can be validated with `mongosh`, while avoiding plaintext production credentials in shell history, process inspection, terminal recordings, screenshots, or support evidence.

## Connection-String Failure Taxonomy

```text
Connection-String Failure
          │
          ├── Wrong Environment
          ├── Invalid URI Syntax
          ├── Wrong Scheme
          ├── Credential Encoding
          ├── Wrong Host / Port
          ├── DNS / SRV
          ├── TXT Configuration
          ├── TLS
          ├── Authentication
          ├── authSource
          ├── replicaSet
          ├── directConnection
          ├── Unsupported Option
          ├── Driver Compatibility
          ├── Member Discoverability
          └── Secret / Configuration Error
```

### Representative Failure Scenarios

- Invalid URI encoding can make valid credentials appear invalid or make the URI malformed.
- An incorrect `authSource` is an authentication configuration failure, not a network failure.
- An incorrect `replicaSet` value can allow network contact while preventing expected topology establishment.
- A seed can be reachable while advertised replica-set members remain unreachable.
- SRV lookup failure can prevent discovery while MongoDB servers remain healthy.
- Incorrect TXT configuration can produce authentication or topology failures.
- A valid URI can successfully connect to the wrong environment.
- Credential-bearing URI exposure must be treated as a potential security incident according to organizational policy.

## Troubleshooting Workflow

```text
Connection Failure
      │
      ▼
Correct Environment?
      │
      ▼
Correct URI Scheme?
      │
      ▼
URI Syntax Valid?
      │
      ▼
Credentials Encoded Correctly?
      │
      ▼
Correct Host / SRV Name?
      │
      ▼
DNS Resolves?
      │
      ▼
SRV / TXT Correct?
      │
      ▼
Network Reachable?
      │
      ▼
TLS Valid?
      │
      ▼
Authentication Correct?
      │
      ▼
authSource Correct?
      │
      ▼
replicaSet Correct?
      │
      ▼
Topology Members Reachable?
      │
      ▼
Suitable Server Selected?
      │
      ▼

```

Capture timestamp, application, environment, deployment, driver/version, sanitized URI, URI scheme, DNS/SRV/TXT results, network reachability, TLS errors, authentication errors, `authSource`, expected replica-set name, topology/SDAM errors, server-selection errors, member discoverability, MongoDB logs, and recent configuration changes. Never collect plaintext credentials as routine troubleshooting evidence.

## Connection-String Governance

Production standards should define approved URI schemes, standard-vs-SRV selection, DNS ownership, environment naming, replica-set naming, TLS requirements, authentication-source standards, credential storage, URI encoding requirements, permitted options, supported drivers/versions, configuration ownership, secret rotation, DNS change control, validation procedures, logging redaction, and emergency change procedures.

Ownership is shared across Application Engineering, DBA/DBRE, SRE/Platform, Network/DNS, and Security.

## Connection-String Anti-Patterns

Avoid:

- hard-coding production MongoDB credentials;
- committing credential-bearing URIs to Git;
- logging or sharing complete credential-bearing URIs;
- reusing nonproduction URIs in production;
- depending on one fragile replica-set seed when resilient startup is required;
- treating seed hosts as permanent routing targets;
- using `directConnection=true` to hide topology problems;
- connecting normal sharded application traffic directly to shard members;
- constructing SRV URIs with multiple hosts or explicit ports;
- assuming arbitrary URI options can be supplied through TXT;
- ignoring URI-over-TXT precedence;
- confusing `/defaultauthdb` with `authSource`;
- ignoring URI percent encoding;
- blindly copying connection options between drivers;
- assuming driver defaults are universal;
- ignoring member hostname discoverability;
- placing topology-aware connections behind arbitrary generic load balancers;
- making unmanaged DNS changes;
- assuming SRV removes DNS operational risk;
- assuming URI syntax validation proves connectivity; and
- assuming successful connectivity proves environment correctness.

## DBA Connection-String Checklist

Before approving production connectivity, verify the environment/deployment, URI scheme and syntax, standard-vs-SRV choice, hosts/ports, SRV one-host/no-port rule, replica-set identity, seed resilience, intentional `directConnection`, `mongos` use for sharded applications, DNS/SRV/TXT correctness, URI/TXT precedence, topology member reachability, TLS/certificate policy, authentication mechanism/source, credential encoding and secret storage, driver compatibility, retry/timeout/read-preference policy, load-balanced mode where applicable, environment identity, ownership, rotation, and escalation procedures.

## Key DBA Takeaways

1. A MongoDB URI defines initial connectivity and discovery configuration.
2. `mongodb://` explicitly provides initial hosts; `mongodb+srv://` delegates discovery to DNS.
3. Standard replica-set hosts are discovery seeds rather than permanent routing entries.
4. Multiple seeds improve initial discovery resilience.
5. `replicaSet` identifies the expected replica-set topology.
6. `directConnection=true` changes normal topology discovery and should not hide production networking defects.
7. Sharded applications normally connect through `mongos`.
8. An SRV URI contains one discovery hostname and no explicit port.
9. DNS SRV provides endpoint/port discovery; DNS TXT can provide supported `replicaSet` and `authSource` configuration.
10. Explicit URI options override matching TXT configuration.
11. `mongodb+srv://` enables TLS by default; production TLS policy should still be explicitly governed.
12. `authSource` explicitly selects the authentication database; otherwise `/defaultauthdb`, then `admin`, provides the fallback sequence.
13. URI-sensitive credential characters require percent encoding, and credential-bearing URIs must be treated as secrets.
14. Connection-option support/defaults can be driver-specific.
15. The URI initializes discovery while SDAM maintains runtime topology.
16. Primary elections normally do not require rewriting replica-set URIs.
17. Seed reachability does not guarantee topology-member reachability.
18. Generic network load balancing is different from MongoDB's documented load-balanced connection mode.
19. A valid URI can still point to the wrong environment.
20. A URI is not production-valid merely because it parses.
21. Troubleshooting should progress from environment → scheme → syntax → encoding → DNS/SRV/TXT → network → TLS → authentication → topology → server selection → operation.
