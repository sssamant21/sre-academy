# 2.1 — Production Installation Planning

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to plan a production MongoDB deployment before installing software; translate business requirements into availability, performance, security, RPO, and RTO requirements; characterize workloads and forecast capacity; select an appropriate edition, operating model, release, platform, and topology; design replica-set membership and failure-domain placement; plan compute, memory, storage, network, security, backup, monitoring, lifecycle, automation, migration, and production acceptance requirements; and determine whether a MongoDB deployment is genuinely ready for production.

## 1. Production Installation as an Architecture Decision

Production installation should not begin by installing MongoDB packages.

```text
Business Requirements
        |
        v
SLO / RPO / RTO
        |
        v
Workload
        |
        v
Topology + Failure Domains
        |
        v
Capacity + Platform
        |
        v
Security
        |
        v
Backup + Monitoring
        |
        v
Lifecycle + Automation
        |
        v
Application Validation
        |
        v
Production Acceptance
        |
        v
Installation
```

Starting `mongod` successfully proves that a process can run. It does not prove that the resulting database service is production-ready.

> **Production Installation = Architecture + Capacity + Security + Reliability + Operations**

> **Design the MongoDB service first; install the MongoDB software second.**

## 2. Business Requirements, SLO, RPO, and RTO

Document business criticality, availability, latency, throughput, acceptable downtime/data loss, maintenance constraints, compliance, data residency, growth, and recovery expectations. Translate these into engineering requirements for topology, durability, backup, recovery, geographic placement, operations, and cost.

RPO defines acceptable data loss measured in time. RTO defines how quickly service must be restored. These are service objectives; topology alone does not guarantee them.

> **Backup Strategy Should Follow RPO/RTO—not Define Them**

> **High Availability ≠ Backup**

> **Replication ≠ Disaster Recovery by Itself**

## 3. Workload Characterization

Characterize current logical data and index size, document behavior, collection count, growth, reads, writes, aggregation, sorting, reporting, batch activity, connections, transactions, replication, backups, index builds, migrations, maintenance, initial synchronization, monitoring, and recovery operations.

Production workload is larger than normal application traffic.

## 4. Capacity Planning and Growth

```text
Required Production Capacity
          =
Application Workload
          +
Data / Index Growth
          +
Replication
          +
Maintenance
          +
Backup
          +
Failure Headroom
```

Include current requirements, expected growth, peaks, seasonal demand, new applications/users, maintenance, migrations, and recovery.

> **Average Load ≠ Required Production Capacity**

## 5. Edition, Operating Model, and Responsibility Boundaries

Select Community, Enterprise Advanced, Atlas, or another approved operating model deliberately. The choice affects security, auditing, encryption, backup, tooling, support, infrastructure ownership, and lifecycle responsibility.

| Responsibility | Self-Managed | Managed Service |
|---|---|---|
| Application design | Organization | Organization |
| Driver configuration | Organization | Organization |
| Query/index design | Organization | Organization |
| RPO/RTO definition | Organization | Organization |
| Access/RBAC design | Organization | Shared |
| MongoDB lifecycle | Organization | Provider/Shared |
| OS lifecycle | Organization | Provider in fully managed models |
| Infrastructure | Organization | Provider/Shared |
| Backup policy | Organization | Shared |
| Recovery validation | Organization | Shared |

Exact boundaries depend on service and support model.

> **Managed Service ≠ No Operational Responsibility**

## 6. MongoDB Release, Platform, and FCV Baseline

Record the validated deployment combination:

```text
MongoDB Release
      +
Edition
      +
OS Distribution / Version
      +
CPU Architecture
      +
FCV
      +
Driver Versions
      =
Validated Deployment Baseline
```

Verify current platform support before installation.

> **Supported Release ≠ Supported Platform Combination**

> **Binary Version ≠ Feature Compatibility Version**

## 7. Deployment Topology Selection

Choose standalone, replica set, or sharded cluster from availability and scaling requirements. Standalone is primarily appropriate for development, testing, or explicitly accepted non-HA workloads. Replica sets are the normal HA foundation where horizontal sharding is unnecessary. Sharding should solve a defined horizontal-scaling/distribution requirement.

> **Operational Importance ≠ Requirement for Sharding**

## 8. Replica-Set Membership, Voting, and Arbiters

For a typical self-managed production deployment, prefer at least a three-member replica set with three data-bearing members, with placement determined by latency, quorum, infrastructure, geography, cost, and required failure tolerance.

> **Prefer Three Data-Bearing Members for a Typical Production Replica Set**

Replica-set availability depends on voting majority rather than process count.

> **Member Count ≠ Voting Majority ≠ Fault Tolerance**

An arbiter participates in elections but does not store application data.

> **Arbiter Vote ≠ Data Redundancy**

> **Prefer Data-Bearing Members Over Arbiters for Production Resilience When Feasible**

## 9. Failure-Domain Architecture

Evaluate process, host/VM/node, rack/infrastructure domain, availability zone, data center, and region. Ask what happens if an entire required failure domain disappears.

> **Replica Count ≠ Failure-Domain Diversity**

Design placement according to the failures the service must survive; do not prescribe a universal three-AZ or multi-region design without considering latency, voting, durability, RTO, and cost.

## 10. Compute, Memory, and Failure-State Capacity

Plan CPU, memory, concurrency, network, storage bandwidth, and operational overhead. Memory must accommodate WiredTiger, filesystem cache, the OS, connections, MongoDB overhead, and operational agents.

> **Installed RAM ≠ Entirely Available to WiredTiger**

The surviving architecture must be able to sustain production traffic while recovery is occurring.

> **Normal-State Capacity ≠ Failure-State Capacity**

## 11. Storage Capacity and Performance

Storage planning must independently evaluate capacity, latency, IOPS, throughput, durability, expansion, and operational headroom. Account for data, indexes, journal activity, oplog requirements, logs, maintenance demand, and growth. These categories do not imply separate physical volumes.

> **Enough Disk Space ≠ Enough Storage Performance**

## 12. Filesystem, Disk Layout, and Expansion Planning

Define the data path, log path, approved filesystem, mount configuration, ownership, permissions, volume architecture, monitoring, and expansion procedure. Plan expansion before capacity becomes an emergency. Detailed filesystem requirements belong in 2.4.

## 13. Network, DNS, and Topology Discoverability

Plan application, replica-set member, `mongos`, shard, config-role, monitoring, backup, and administrative communication. Evaluate subnets, routing, firewalls/security groups, DNS, bandwidth, latency, TLS, and member-to-member connectivity.

> **Application-to-Primary Connectivity Alone ≠ Healthy Replica-Set Networking**

A client can reach a seed member yet fail to reach members discovered through topology discovery.

> **Reachable Seed Host ≠ Discoverable Replica Set**

Evaluate standard and SRV connection models where appropriate.

## 14. Time Synchronization and Host Identity

Plan stable hostnames, DNS records, certificate identity, naming standards, and reliable time synchronization. Consistent time supports logs, incident correlation, monitoring, certificates, and distributed diagnosis.

> **Reliable Time = Reliable Operational Evidence**

## 15. Security Architecture Before Installation

Plan authentication, authorization, network controls, TLS, encryption at rest, in-use encryption where applicable, secrets, auditing, administrative access, and certificate lifecycle before production exposure. Plan TLS across required client/server and internal MongoDB communication paths.

> **Security Hardening Is Part of Installation—not a Post-Installation Project**

## 16. Administrative Access and Certificate Lifecycle

Administrative access should be authenticated, authorized, logged, reviewable, and revocable. Avoid unrestricted exposure, shared administrator accounts, unmanaged credentials, and unnecessary permanent privilege.

Define certificate authority, identity requirements, issuance, storage, expiration monitoring, renewal, rotation, and emergency replacement.

> **TLS Enabled ≠ Certificate Lifecycle Managed**

## 17. Backup, Recovery, RPO, and Disaster-Recovery Planning

Plan backup method, frequency, retention, encryption, storage, access, monitoring, restore procedures, testing, and recovery validation.

```text
Backup
   |
   v
Restore Test
   |
   v
Data Validation
   |
   v
Recovery-Time Measurement
   |
   v
Recovery Confidence
```

> **Backup Success ≠ Restore Success**

> **High Availability ≠ Backup**

> **Replication ≠ Disaster Recovery by Itself**

## 18. Monitoring, Alerting, Logging, and Diagnostic Retention

Monitoring should exist before production traffic. Monitor availability, topology, connections, queries, replication, oplog, WiredTiger, storage, CPU, memory, network, backups, capacity, certificate expiration, and topology changes. Establish a known-good baseline.

Plan log location, rotation, retention, centralized collection, access controls, and storage requirements.

> **Diagnostic Value + Security + Storage Cost**

## 19. Maintenance, Patching, Upgrade, and FCV Lifecycle

Plan patching, MongoDB upgrades, FCV transitions, certificate/credential rotation, storage expansion, node replacement, and configuration changes.

```text
Approved Release
      |
      v
Staging / Compatibility Validation
      |
      v
Production Binary Upgrade
      |
      v
Post-Upgrade Validation
      |
      v
Burn-In
      |
      v
FCV Advancement
      |
      v
Final Validation
```

> **Binary Version ≠ Feature Compatibility Version**

> **Binary Upgrade Complete ≠ Lifecycle Transition Complete**

Detailed lifecycle procedures belong in 2.19–2.28.

## 20. Automation, Configuration Ownership, and Drift Control

Production deployments should be reproducible: defined, reviewed, automatically deployed, validated, and monitored for drift. Define canonical `mongod.conf`, source of truth, approval process, automation/IaC, environment variables, secret handling, validation, and drift detection.

> **Reproducible Infrastructure + Reproducible MongoDB Configuration**

Do not place secrets in ordinary source-controlled configuration merely to achieve reproducibility.

## 21. Application and Driver Compatibility

Inventory application runtime, driver, framework/ODM, connection model, authentication, TLS, retries, read/write concerns, read preference, connection pools, and timeouts. Validate connectivity, topology discovery, MongoDB operations, application functionality, and failover behavior where applicable.

> **MongoDB Server Ready ≠ Application Ready**

## 22. Initial Data Load, Migration, Cutover, and Rollback

Define source inventory, transfer method, synchronization or write quiescence, validation, downtime, cutover, application verification, acceptance criteria, and rollback. Detailed migration procedures belong in Chapter 20.

## 23. Production Acceptance and Go-Live Criteria

Production readiness must be demonstrated through evidence covering platform support, architecture, failure domains, voting/fault tolerance, capacity, binary version, FCV, drivers, security, monitoring, logging, backups, restore testing, application compatibility, performance, failover behavior, recovery requirements, and rollback.

> **Go-Live Should Be an Evidence-Based Decision**

## 24. Failure Scenarios and Production Anti-Patterns

A three-member replica set placed entirely in one major failure domain can lose all members during that domain's failure. The installation succeeds technically while the availability architecture fails.

> **High Availability Is Determined by Failure-Domain Architecture—not by Process Count**

Avoid: install-first/design-later; standalone for critical HA without explicit risk acceptance; replica members sharing one failure domain; arbiters mistaken for redundancy; average-only capacity sizing; capacity without storage-performance analysis; security after exposure; replica sets mistaken for backup/DR; production before monitoring/restore validation; unsupported platform/driver combinations; manual configuration without a source of truth; upgrades without staging/burn-in/FCV/downgrade analysis; seed-host reachability mistaken for topology health; normal-state capacity mistaken for failure-state capacity; and go-live without measurable evidence.

## 25. DBA Pre-Installation Checklist, Key Takeaways, and Applicability

### Checklist

- [ ] Business criticality, availability, RPO, RTO, performance, compliance, and residency requirements documented.
- [ ] Data/index size, growth, reads, writes, peaks, connections, maintenance, backup, and failure-state capacity understood.
- [ ] Edition, MongoDB release, platform, FCV, topology, replica-set membership, voting, failure domains, and sharding requirements validated.
- [ ] CPU, memory, storage capacity/performance, filesystem, expansion, network, DNS, topology discoverability, and time synchronization planned.
- [ ] Authentication, RBAC, TLS, encryption, administrative access, secrets, certificates, and auditing designed.
- [ ] Monitoring, alerts, logging, backup, restore testing, and capacity thresholds designed.
- [ ] Patch, upgrade, staging, FCV, burn-in, downgrade, source-of-truth, drift, and automation strategies defined.
- [ ] Driver, connection model, TLS/authentication, pools/timeouts, functional/performance validation, migration, cutover, rollback, and operational ownership defined.

### Key Takeaways

Production installation begins with architecture and requirements rather than packages. HA, backup, and DR solve different problems. Average load is not required capacity. Validate the exact MongoDB/platform combination. Binary version and FCV are distinct. Prefer three data-bearing members for a typical production replica set. Arbiter votes are not data redundancy. Failure-domain diversity matters more than process count. Storage capacity and performance are independent. Security, backup, monitoring, lifecycle management, configuration reproducibility, application compatibility, and recovery validation belong in the production design. Go-live should be evidence-based.
