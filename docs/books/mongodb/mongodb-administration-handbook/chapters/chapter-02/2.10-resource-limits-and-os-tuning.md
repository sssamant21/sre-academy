# 2.10 — Resource Limits and OS Tuning

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly noted  
**Status:** Canonical

> **Provisioned Capacity ≠ Effective MongoDB Capacity**

## Learning Objectives

After completing this section, you should be able to determine effective CPU, memory, file-descriptor, process/thread, and cgroup limits available to `mongod`; distinguish kernel-wide, systemd, cgroup, and process limits; validate file-descriptor capacity; understand MongoDB/WiredTiger memory consumption; identify CPU throttling, memory pressure, swapping, and OOM conditions; account for containers/Kubernetes; establish a MongoDB-aware Linux baseline; manage sysctl safely; understand version-sensitive OS behavior; diagnose exhaustion incidents; perform controlled tuning; and validate tuning after reboot, patching, replacement, and upgrades.

## 1. Resource-Control Architecture

```text
Physical / Cloud Infrastructure
              |
              v
          Linux Kernel
              |
              v
      systemd / cgroups
              |
              v
            mongod
              |
              v
           MongoDB
              |
              v
         Application
```

Host CPU, RAM, and storage specifications do not prove what `mongod` can consume. File descriptors, process/thread ceilings, cgroup memory, CPU quotas, container limits, kernel parameters, storage bandwidth, and network bandwidth may impose lower effective boundaries.

> **Host Capacity ≠ MongoDB Effective Capacity**

## 2. Production Tuning Philosophy

Do not build MongoDB hosts by copying generic database-tuning scripts. Establish a validated baseline from the MongoDB release, Linux distribution/kernel, deployment model, hardware/VM, workload, topology, and current authoritative guidance. Every tuning change must have evidence, expected effect, restart/reboot requirements, validation, rollback, and drift controls.

> **Tuning Without Measurement Is Configuration Risk**

## 3. Capture the Host Baseline

```bash
lscpu
nproc
free -h
cat /proc/meminfo
lsblk
df -h
df -i
findmnt
uname -a
cat /etc/os-release
```

Prefer targeted kernel inspection:

```bash
sysctl vm.swappiness
sysctl vm.max_map_count
sysctl fs.file-max
sysctl kernel.pid_max
sysctl kernel.threads-max
```

A full `sysctl -a` can be useful for forensic snapshots or comparisons but is unnecessarily noisy for routine diagnosis.

## 4. Validate the Running mongod

```bash
systemctl status mongod
systemctl show mongod
systemctl show mongod -p MainPID
PID=$(pidof mongod)
cat /proc/$PID/limits
```

```text
Configured value != systemd value != cgroup value != running-process value
```

Always validate effective runtime state.

## 5. Resource-Limit Hierarchy

```text
Kernel-wide ceiling
       |
       v
systemd / cgroup ceiling
       |
       v
mongod effective limit
       |
       v
actual utilization
```

Relevant controls include `fs.file-max`, `kernel.pid_max`, `kernel.threads-max`, `vm.max_map_count`, `LimitNOFILE`, `LimitNPROC`, `TasksMax`, `MemoryMax`, and `CPUQuota`, depending on platform.

## 6. File Descriptors

MongoDB uses descriptors for client/internal connections, sockets, data/index-related files, logs, and diagnostic activity.

```bash
systemctl show mongod -p LimitNOFILE
PID=$(pidof mongod)
cat /proc/$PID/limits
ls /proc/$PID/fd | wc -l
```

The interactive `ulimit -n` does not prove what systemd-managed `mongod` inherited.

> **Shell ulimit ≠ MongoDB Runtime Limit**

## 7. MongoDB Open-Files Warning

For the supported baseline, an open-files limit below MongoDB's documented warning threshold of 64,000 should trigger investigation. This is a warning baseline, not a universal production capacity target. Capacity must account for workload, connections, operational tooling, monitoring, internal usage, growth, and safety margin.

## 8. Connections and Resources

Connections consume sockets/file descriptors, memory, CPU scheduling, and network resources. Inspect `db.serverStatus().connections` and monitor current connections, available capacity, growth, churn, and FD utilization. Connection-pool design is an application/database architecture concern, not solely an OS-limit problem.

## 9. File-Descriptor Exhaustion

When FD demand approaches the effective limit, allocation can fail and affect connections/files. Inspect runtime limits and FD count, correlate with MongoDB connections/logs, and determine why usage changed before increasing capacity.

## 10. Configuring Service Limits

Use supported systemd overrides instead of casually editing package-owned units:

```bash
sudo systemctl edit mongod
```

Example concept:

```ini
[Service]
LimitNOFILE=<validated-value>
```

Then:

```bash
sudo systemctl daemon-reload
sudo systemctl restart mongod
PID=$(pidof mongod)
cat /proc/$PID/limits
```

> **Configuration Written ≠ Configuration Effective**

## 11. Kernel-Wide Resource Ceilings

Review `fs.file-max`, `kernel.pid_max`, `kernel.threads-max`, and `vm.max_map_count`. Do not assign arbitrary universal values; validate against the MongoDB release, Linux platform, topology, workload, and number of database processes.

## 12. Process and Thread Limits

MongoDB is multithreaded. Potential constraints include `LimitNPROC`, `TasksMax`, kernel PID/thread ceilings, and cgroup PID controls.

```bash
systemctl show mongod -p LimitNPROC -p TasksMax
ps -o pid,nlwp,cmd -p "$(pidof mongod)"
```

A thread/process ceiling can become a bottleneck while CPU and memory remain available.

## 13. CPU Architecture

Effective CPU follows infrastructure/vCPU → hypervisor/cloud → Linux scheduler → cgroup/systemd → `mongod`. Monitor utilization, per-CPU load, run queue, user/system CPU, I/O wait, steal time where relevant, and throttling.

```bash
lscpu
nproc
uptime
vmstat 1
mpstat -P ALL 1
```

## 14. CPU Saturation

High CPU can originate from expensive queries, inefficient indexes, aggregation, compression/encryption, connection churn, replication, index builds, maintenance, or workload growth.

> **High CPU ≠ CPU Root Cause**

Ask what work consumes CPU and why before scaling.

## 15. CPU Quotas and Throttling

`CPUQuota`, CPU weights, cpusets, container limits, and Kubernetes CPU limits may restrict MongoDB below host capacity.

> **Host CPU Available ≠ MongoDB CPU Available**

Before scaling the VM, confirm `mongod` can consume existing resources.

## 16. CPU Affinity

Avoid CPU pinning without validated requirements. Document reason, CPU set, NUMA implications, benchmark evidence, monitoring, and rollback. Detailed NUMA engineering belongs in 2.11.

## 17. MongoDB Memory Architecture

Effective RAM supports WiredTiger internal cache, filesystem-cache interaction, process overhead, connections, thread stacks, and other allocations.

> **WiredTiger Cache ≠ Total MongoDB Memory**

> **High Memory Utilization ≠ Memory Leak**

Focus on memory pressure, reclaim, swap, OOM risk, cgroup constraints, storage amplification, and application impact.

## 18. WiredTiger Cache

For MongoDB 8.x, WiredTiger's documented default internal cache sizing is based on the larger of approximately 50% × (RAM - 1 GB) or 0.256 GB. Exact behavior is version-sensitive. The default should generally remain unless a justified workload/resource-boundary requirement exists. Increasing cache reduces headroom for filesystem cache, connections, process overhead, other processes, and the OS.

> **More WiredTiger Cache ≠ Automatically Better Performance**

## 19. Memory Pressure

```bash
free -h
vmstat 1
cat /proc/meminfo
```

Evaluate available memory, swap usage/activity, reclaim, RSS, cgroup memory, and OOM events. Memory pressure can reduce cache effectiveness, increase physical I/O, raise storage latency, and increase MongoDB/application latency.

## 20. Container and cgroup Memory

```text
Node RAM
   |
   v
Container / cgroup memory boundary
   |
   v
Memory available to MongoDB
   |
   v
WiredTiger cache sizing
   |
   v
Remaining process headroom
```

Never size MongoDB from node RAM when a lower pod/container limit applies. Validate the memory MongoDB recognizes and resulting WiredTiger behavior. Explicit cache configuration may be necessary where the default calculation does not align with the effective container boundary.

> **Node Memory ≠ Container Memory**

## 21. Swap

MongoDB production design should minimize harmful swapping. Monitor `swapon --show`, `free -h`, and `vmstat 1`; distinguish configured swap from sustained paging and correlate with latency, memory sizing, and cgroup constraints.

> **Swap Configuration ≠ Swap Pressure**

## 22. vm.swappiness

Follow current guidance for the exact MongoDB release/deployment. MongoDB 8.x guidance generally favors minimizing swapping and documents `vm.swappiness` values of 1 or 0 depending on application/cluster requirements, with additional considerations for shared hosts. Do not treat swappiness as a substitute for adequate memory, and validate cgroup/distribution-specific effective behavior.

> **Swappiness Tuning ≠ Memory Capacity**

## 23. Out-of-Memory Conditions

Memory demand can progress through reclaim/swap pressure to OOM termination, systemd restart, database recovery, and topology impact.

```bash
journalctl -k
dmesg
systemctl status mongod
journalctl -u mongod
```

Monitor OOM events, unexpected restart, uptime reset, and replica transitions together.

> **Automatic Recovery ≠ Incident Resolution**

## 24. Transparent Huge Pages — Critical Version Boundary

| MongoDB Version | THP Baseline |
|---|---|
| MongoDB 8.0+ | Enable THP according to current MongoDB guidance |
| MongoDB 7.0 and earlier | Disable THP according to guidance applicable to those releases |

Do not copy a MongoDB 7.x-era THP configuration into MongoDB 8.x without revalidation. Detailed implementation belongs in 2.12.

## 25. NUMA Boundary

Capture NUMA topology with `lscpu` and, where available, `numactl --hardware`. Do not apply generic NUMA tuning blindly. Detailed treatment belongs in 2.11.

## 26. Storage Readahead

For WiredTiger, current MongoDB guidance recommends relatively low storage-device readahead, commonly 8–32, unless repeatable testing demonstrates benefit from another setting. Validate device/platform implementation. Detailed storage engineering remains in 2.8 and later storage chapters.

## 27. I/O Scheduler

Scheduler selection must follow current MongoDB guidance for the actual storage technology, kernel, and virtualization model. Relevant modern SSD/NVMe and virtualized deployments may use scheduler choices such as `none`; other environments may differ. Verify the effective scheduler after reboot or image replacement.

## 28. Filesystem atime

The dbPath volume should use validated filesystem/mount options. Current production guidance includes avoiding unnecessary access-time updates for database storage. Detailed filesystem configuration remains in 2.8.

## 29. RHEL/Rocky/AlmaLinux tuned

Automated tuning frameworks such as `tuned` can alter effective OS configuration. Validate that the active profile does not undo/conflict with MongoDB-specific settings such as THP, readahead, or other approved controls.

> **Configured Baseline ≠ Effective Baseline When Another Tuning Layer Exists**

## 30. Network Resources

MongoDB consumes network capacity through application connections, replication, sharded traffic, initial sync, backup, and monitoring.

```bash
ss -s
ss -lntp
ip -s link
```

Monitor connections, churn, errors, drops, bandwidth, latency, and replication traffic. Avoid broad `net.*` tuning without evidence.

## 31. Evidence-Based Kernel Tuning

Observed problem → measure → identify limiting resource → check MongoDB guidance → check OS/cloud guidance → change one bounded control → measure → retain or rollback.

> **MongoDB-Documented Baseline ≠ Generic Database Tuning Script**

## 32. Persistent sysctl Configuration

Runtime `sysctl -w` changes may not survive reboot. Test runtime changes, validate, add approved settings to distribution-supported managed persistent configuration, reload/reboot, validate again, and monitor drift.

> **Runtime sysctl ≠ Persistent Configuration**

## 33. Time Synchronization Boundary

The OS baseline must verify the approved time-synchronization mechanism is healthy. Detailed implementation belongs in 2.13.

## 34. Kubernetes Resource Boundaries

Node capacity → pod requests/limits → container cgroup → `mongod`. Review CPU/memory requests and limits, QoS, throttling, OOMKilled, node pressure, and eviction. A node may have unused resources while MongoDB remains constrained by its pod/container limits.

## 35. Cloud VM Boundaries

Consider vCPU, RAM, network bandwidth, storage bandwidth, IOPS, throughput, and burst behavior where applicable.

> **Guest OS Tuning ≠ Cloud Capacity Increase**

## 36. Resource Monitoring Model

Monitor application latency/errors/timeouts; MongoDB connections, operation latency, WiredTiger pressure, replication lag/elections; Linux/cgroup CPU, run queue, throttling, memory, swap, FD usage, threads, OOM and I/O wait; and infrastructure VM/storage/network/node limits.

## 37. Monitor Utilization Against Effective Limits

Track FD used/FD limit, memory used/cgroup memory limit, CPU throttling/allocation, and disk used/filesystem capacity. Limit utilization is more predictive than absolute usage alone.

## 38. Recommended Dashboard

| Domain | Signals |
|---|---|
| CPU | utilization, run queue, per-CPU, throttling |
| Memory | available, RSS, swap, OOM, cgroup boundary |
| Process | uptime, threads, FDs, restart count |
| Storage | capacity, latency, IOPS, throughput, queue |
| Network | connections, errors, drops, bandwidth |
| MongoDB | connections, latency, WT metrics, replication |
| Application | latency, errors, timeouts |

## 39. Alerting Strategy

Alert on FD utilization approaching limits, unexpected connection growth, process/thread pressure, sustained CPU saturation/throttling, low available memory, sustained swap activity, OOM, unexpected restart, I/O wait, storage pressure, network errors/drops, and replication lag correlated with host pressure. Combine baseline, growth rate, effective limit, time to exhaustion, and MongoDB impact rather than relying solely on universal percentages.

## 40. Failure Scenario — File Descriptor Exhaustion

Inspect runtime limits, FD count, service `LimitNOFILE`, MongoDB connections, and logs. Determine why usage changed before increasing capacity.

## 41. Failure Scenario — CPU Saturation

Use `uptime`, `vmstat`, `mpstat`, and `top`; correlate with slow operations, query workload, indexes, aggregation, connections, replication, index builds, and maintenance. Remediation may include query/index optimization, workload reduction, scaling, limit correction, or architecture changes.

> **Increasing CPU Does Not Fix an Unbounded Bad Query Pattern**

## 42. Failure Scenario — CPU Throttling

Host CPU may remain unsaturated while MongoDB latency is high because cgroup CPU is constrained. Inspect host CPU, cgroup allocation/throttling, and `mongod` behavior before scaling.

## 43. Failure Scenario — Memory Pressure

Inspect memory, swap, WiredTiger cache, RSS, filesystem cache, other processes, cgroup limits, OOM, storage I/O, and application latency. Do not immediately change WiredTiger cache or swap policy before identifying the resource condition.

## 44. Failure Scenario — OOM Kill

`mongod` may disappear while MongoDB logs lack the root cause; kernel/cgroup evidence is required. In Kubernetes inspect pod events for `OOMKilled`. Recovery must correct both database health and the resource condition.

## 45. Failure Scenario — Resource Drift

OS patches, kernel/package upgrades, image rebuilds, systemd/configuration-management changes, and container manifest changes can revert resource settings. Post-change validation must inspect effective runtime limits.

## 46. Kernel and OS Upgrade Compatibility Gate

Before OS/kernel upgrades identify the exact MongoDB release and proposed OS/kernel, check MongoDB release notes, validate compatibility, test a representative member, then perform controlled rollout.

> **Before OS/kernel upgrades, check release notes for the exact MongoDB release being operated.**

## 47. Production Tuning Safety Gate

Before: verify environment/member, MongoDB/OS/kernel versions, configured/effective values, evidence, current MongoDB/platform guidance, expected effect, restart/reboot requirement, rollback, and monitoring. Change one bounded control on a controlled member. Validate effective value, `mongod`, topology, replication, resource behavior, application, warnings/errors, and persistence. Stop if the member does not recover, replication/resource pressure worsens, OOM/restarts occur, application impact worsens, or root cause becomes uncertain.

> **Never roll OS tuning fleet-wide before validating it on a controlled representative member.**

## 48. Post-Reboot Validation

```bash
systemctl status mongod
PID=$(pidof mongod)
cat /proc/$PID/limits
sysctl vm.swappiness
free -h
swapon --show
```

Validate storage mount, MongoDB reachability, replica state, replication, resource limits, OS tuning, application, and monitoring.

> **Configuration Written ≠ Configuration Persisted**

## 49. Post-Patching Validation

Verify kernel version, MongoDB service, units/drop-ins, runtime/kernel-wide limits, sysctl baseline, swap, THP, NUMA, storage mounts/options, readahead, I/O scheduler, network state, MongoDB health, replication, and monitoring.

## 50. Production Anti-Patterns

Avoid generic tuning scripts; mass sysctl changes without evidence; shell-only ulimit checks; ignoring cgroups; treating 64K open files as universal capacity; increasing limits without demand analysis; treating high CPU as root cause; treating high memory as leak; equating WT cache with total memory; blindly increasing cache; sizing containers from node RAM; using swappiness instead of capacity; ignoring OOM; carrying 7.x THP settings into 8.x; unvalidated readahead/schedulers; ignoring tuned/equivalent layers; evidence-free network tuning; assuming runtime sysctls persist; fleet-wide tuning without staged validation; skipping post-patch validation; and kernel upgrades without MongoDB compatibility review.

## 51. Production Readiness Checklist

Validate MongoDB/Linux/kernel versions, CPU/RAM/cgroups/cloud/container limits, kernel/service/runtime file/process limits, FD/connection monitoring, CPU/run queue/quota/throttling, effective memory boundary, WT cache, swap/swappiness/OOM, THP version alignment, NUMA state, readahead, scheduler, dbPath mount options, tuned/equivalent profile, managed sysctl baseline, tuning/rollback/staged rollout/reboot/patch runbooks, kernel compatibility gates, and drift detection.

## 52. Key SRE/DBRE Principles

```text
Provisioned Capacity != Effective MongoDB Capacity
Shell ulimit != mongod Runtime Limit
Configured Limit != Effective Limit
High CPU != CPU Root Cause
High Memory Utilization != Memory Leak
WiredTiger Cache != Total MongoDB Memory
Swappiness Tuning != Memory Capacity
Node Memory != Container Memory
OS Tuning != Cloud Capacity
Runtime sysctl != Persistent Configuration
Automatic Recovery != Incident Resolution
More Resources != Fixed Workload Design
```

> **Measure the effective resource boundary seen by `mongod`, correlate it with MongoDB and application behavior, and change only controls supported by evidence, current MongoDB/platform guidance, controlled testing, and repeatable validation.**
