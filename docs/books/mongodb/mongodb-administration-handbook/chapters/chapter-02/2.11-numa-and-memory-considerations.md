# 2.11 — NUMA and Memory Considerations

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly noted  
**Status:** Canonical

> **Installed Memory ≠ Uniformly Accessible Memory**

NUMA is an operating-system and hardware architecture concern that can become a MongoDB reliability issue on multi-socket, large-memory, high-core-count, virtualized, and certain cloud systems. Production engineering must consider not only how much memory exists, but where that memory resides, how CPUs access it, what memory boundary MongoDB actually sees, and whether the effective NUMA policy matches the approved MongoDB baseline.

## Learning Objectives

After completing this section, you should be able to explain NUMA and local versus remote memory; identify the topology visible to MongoDB; understand NUMA/WiredTiger interaction; implement the preferred MongoDB NUMA architecture or documented Linux mitigation; validate `vm.zone_reclaim_mode`; understand memory interleaving; distinguish NUMA policy from CPU affinity and strict memory binding; diagnose uneven allocation, reclaim, swap, and OOM; account for VMs, cloud, containers, and Kubernetes; monitor NUMA behavior; safely roll changes through database topology; and detect drift after reboot, patching, or infrastructure replacement.

## 1. NUMA Architecture

NUMA means Non-Uniform Memory Access. A CPU generally accesses memory attached to its own NUMA node differently from memory attached to another node.

```text
NUMA Node 0                 NUMA Node 1
+----------------+          +----------------+
| CPUs           |<-------->| CPUs           |
| Local Memory   |          | Local Memory   |
+----------------+          +----------------+
```

> **Total RAM ≠ Uniform Memory Access**

## 2. Why NUMA Matters to MongoDB

MongoDB memory includes WiredTiger cache, connections, threads, query execution, internal allocations, compression/decompression and other process memory, while Linux also uses memory for filesystem cache, kernel activity and other services. On NUMA hosts these allocations map to physical or virtual NUMA nodes. Inefficient configuration can contribute to uneven memory pressure, reclaim, additional I/O, swap pressure, latency variation, system CPU, OOM, and unstable database performance.

> **NUMA Exists ≠ NUMA Is the Root Cause**

## 3. NUMA Reliability Model

```text
NUMA Topology
      ↓
Memory Placement
      ↓
Memory Locality / Reclaim
      ↓
Cache Behavior
      ↓
Physical I/O
      ↓
MongoDB Latency
      ↓
Application Impact
```

NUMA observations must be correlated with MongoDB, Linux, storage, and application evidence.

## 4. Detect and Baseline NUMA Topology

```bash
lscpu
numactl --hardware
cat /sys/devices/system/node/online
ls -d /sys/devices/system/node/node*
numastat
free -h
uname -a
cat /etc/os-release
sysctl vm.zone_reclaim_mode
```

Where operationally relevant:

```bash
sysctl kernel.numa_balancing
```

Record node count, CPU distribution, memory per node, socket/core/thread count, virtualization model, MongoDB version, kernel, and process placement. Do not infer topology solely from total CPU/RAM or cloud instance specifications.

For systemd-managed MongoDB:

```bash
PID=$(systemctl show -p MainPID --value mongod)
test "$PID" -gt 0 || { echo "mongod MainPID is not active"; exit 1; }
numastat -p "$PID"
```

## 5. MongoDB NUMA Configuration Hierarchy

For the MongoDB 8.x baseline:

```text
Preferred
   ↓
Disable NUMA in BIOS / firmware
   |
   +-- Not feasible?
           ↓
MongoDB-documented Linux mitigation
           |
           +-- Disable zone reclaim
           +-- Interleave MongoDB memory
           +-- Manage through service lifecycle
           +-- Validate runtime behavior
```

> **Firmware NUMA Disablement ≠ Linux NUMA Mitigation**

## 6. Preferred Architecture — Disable NUMA in Firmware

Where the hardware/platform supports it and current MongoDB guidance applies, prefer disabling NUMA behavior at firmware/BIOS level. Before changing firmware, validate MongoDB version, server/CPU architecture, OS/kernel, current MongoDB guidance, hardware-vendor guidance, maintenance impact, and rollback. Firmware changes are host-wide and typically require reboot; never roll them fleet-wide without staged validation.

## 7. When NUMA Cannot Be Disabled

When firmware-level disablement is unavailable, use the MongoDB-documented Linux mitigation appropriate to the exact release and platform:

```text
NUMA remains enabled
        |
        +--> zone reclaim disabled
        +--> MongoDB memory interleaved
        +--> service-managed startup
        +--> runtime validation
```

This is NUMA mitigation, not hardware NUMA disablement.

## 8. `vm.zone_reclaim_mode`

Inspect:

```bash
sysctl vm.zone_reclaim_mode
```

For the documented MongoDB Linux fallback architecture, validate the approved configuration uses `vm.zone_reclaim_mode = 0` according to the MongoDB/platform baseline being operated. Local NUMA-node pressure with zone reclaim can drive page reclaim, cache disruption, physical I/O and MongoDB latency.

> **NUMA Interleaving Alone ≠ Complete MongoDB NUMA Mitigation**

## 9. Persisting NUMA Configuration

Runtime changes are not sufficient for production. Test a runtime setting, validate it, manage it persistently through the organization's supported configuration-management mechanism, restart/reboot where required, and validate again.

> **Runtime NUMA Configuration ≠ Persistent NUMA Configuration**

## 10. Memory Interleaving

When NUMA cannot be disabled, current MongoDB guidance uses an interleaved memory policy as part of the Linux mitigation. The Linux concept can be illustrated as:

```bash
numactl --interleave=all <process>
```

Production MongoDB implementation must remain integrated with the approved service-management architecture.

> **Interleaving Here Is a MongoDB NUMA Mitigation — Not a Universal Linux Performance Optimization**

## 11. systemd Integration

Keep MongoDB lifecycle under systemd:

```text
systemd
   ↓
Approved NUMA Execution Policy
   ↓
mongod
```

Do not bypass systemd by manually launching production `mongod` merely to apply `numactl`. Preserve controlled startup/shutdown, restart policy, logging, boot enablement, monitoring, package integration, and configuration management. Prefer managed overrides/drop-ins where technically supported rather than casually modifying package-owned unit files.

## 12. Validate Effective Runtime State

After configuration changes validate the service path, NUMA policy, `vm.zone_reclaim_mode`, MongoDB startup logs, database health, replica state, replication, and application health.

```bash
PID=$(systemctl show -p MainPID --value mongod)
test "$PID" -gt 0 || { echo "mongod MainPID is not active"; exit 1; }
numastat -p "$PID"
journalctl -u mongod
```

> **Configured NUMA Policy ≠ Effective NUMA Policy**

> **Service Running ≠ Database Configuration Validated**

## 13. Local and Remote Memory

Remote memory is not automatically an incident. Compare local/remote activity against the healthy baseline, workload, memory pressure, reclaim, swap, storage I/O, MongoDB latency, and application latency.

> **Remote Memory ≠ Automatic Incident**

## 14. WiredTiger and NUMA

WiredTiger engineering asks how much memory is available/appropriate; NUMA engineering asks how memory is physically accessed. Do not change `storage.wiredTiger.engineConfig.cacheSizeGB` solely because the server uses NUMA.

> **WiredTiger Cache ≠ Total MongoDB Memory**

## 15. Memory Pressure, Reclaim, and Storage

Aggregate host memory can hide node-local pressure:

```text
Total Host Memory Healthy
          +
One NUMA Node Under Pressure
          ↓
Reclaim / Remote Access
          ↓
Physical I/O Increase
          ↓
Storage Latency
          ↓
MongoDB Latency
```

> **Storage Symptom ≠ Storage Root Cause**

Do not resize storage or provision additional IOPS before understanding why physical I/O changed.

## 16. NUMA, Swap, and OOM

Investigate:

```bash
free -h
vmstat 1
swapon --show
numactl --hardware
numastat
journalctl -k
```

Kernel logs may require elevated privileges. Correlate total available memory, per-node memory, swap/reclaim, MongoDB memory, cgroup boundaries, and application latency. OOM may result from true host exhaustion, cgroup limits, NUMA placement, strict memory binding, workload growth, other processes, or drift.

> **Swap Activity ≠ Automatically Insufficient Total RAM**

> **OOM ≠ Automatically Insufficient Physical RAM**

## 17. CPU Affinity and Strict Binding

Avoid generic CPU pinning or strict memory binding without architecture-specific justification. CPU affinity and NUMA are related but not equivalent, and restrictive policies can strand usable capacity on other nodes. Specialized binding requires benchmark evidence, capacity analysis, monitoring, failure testing, and rollback.

> **CPU Affinity ≠ NUMA Optimization**

## 18. Linux Automatic NUMA Balancing

Where relevant, inspect:

```bash
sysctl kernel.numa_balancing
```

Treat this as inventory/diagnostic information unless exact MongoDB/Linux guidance requires a particular configuration. Do not create an arbitrary handbook-wide value.

> **Generic Linux Tuning ≠ MongoDB Production Guidance**

## 19. Large-Memory Systems

NUMA is particularly relevant on multi-socket, high-core-count, large-memory, large-VM, and specialized bare-metal systems. Larger machines can introduce additional topology complexity.

> **More RAM ≠ Correct NUMA Policy**

## 20. Virtual Machines and Cloud

Virtualized environments can expose vNUMA:

```text
Physical NUMA
     ↓
Hypervisor
     ↓
vNUMA
     ↓
Guest Linux
     ↓
MongoDB
```

Inspect `lscpu` and `numactl --hardware` inside the guest. Do not infer topology solely from VM specifications. Where current MongoDB production guidance applies, avoid dynamic-memory mechanisms such as ballooning that make database memory availability unpredictable. Revalidate after VM/instance-family replacement.

## 21. Kubernetes Architecture

```text
Physical NUMA
      ↓
Kubernetes Node
      ↓
CPU / Topology Management
      ↓
Pod cgroup
      ↓
MongoDB Container
```

NUMA placement and cgroup memory are independent constraints. A topology-correct pod can still OOM due to its container memory boundary. Aggregate pod metrics such as `kubectl top` (when the metrics API is available) do not by themselves explain NUMA locality. Detailed Topology Manager, CPU Manager, cpuset and scheduling engineering belongs in Kubernetes-specific material.

> **NUMA-Correct Placement ≠ Adequate Container Memory**

## 22. Replica-Set Infrastructure Consistency

Where practical, non-hidden replica-set members should use consistent infrastructure characteristics. Differences in NUMA topology or memory architecture can create asymmetric behavior after failover. A member adequate as a secondary may be insufficient when promoted under primary workload.

> **Replica Healthy as Secondary ≠ Capacity Validated as Primary**

## 23. Monitoring and Alerting

Monitor application latency/errors; MongoDB operation latency, WiredTiger pressure, connections, replication lag/elections/restarts; Linux per-node memory, NUMA statistics, reclaim, swap, OOM, CPU distribution and effective policy; and infrastructure topology/capacity changes.

Do not alert solely on `Remote NUMA Memory > X`. Prefer correlation between NUMA distribution changes, memory pressure, reclaim/swap, MongoDB latency, and application impact. NUMA data is especially valuable as diagnostic context attached to broader reliability alerts.

## 24. Failure Scenarios

### Uneven NUMA memory usage

Use `numactl --hardware`, `numastat`, `free -h`, `vmstat 1`, and process-specific `numastat`; correlate with storage, MongoDB, replication and application behavior before changing policy.

### NUMA misdiagnosed as storage

NUMA pressure can cause reclaim, increased physical I/O, storage latency and MongoDB latency. Determine why I/O increased before simply adding IOPS.

### NUMA misdiagnosed as capacity

If placement/reclaim is the problem, adding RAM may not solve it.

### Incorrect binding

A process bound to one node may remain constrained while another node has capacity. Inspect process execution policy and systemd configuration.

### OOM followed by automatic restart

Do not stop investigation when systemd restarts `mongod`. Review kernel/cgroup evidence, NUMA distribution, reclaim, swap, MongoDB logs, replica transitions, and application impact.

> **Automatic Restart ≠ Incident Resolution**

### Configuration lost after reboot

Runtime NUMA mitigation must be persistent and managed.

### Infrastructure replacement

Rediscover topology and revalidate policy after cloud instance replacement, VM rebuild, hardware replacement, or Kubernetes node rotation.

## 25. NUMA Troubleshooting Workflow

```text
Application / MongoDB Latency
            ↓
Check CPU / Memory / Storage
            ↓
Identify NUMA Topology
            ↓
Check Per-Node Memory
            ↓
Check mongod NUMA Statistics
            ↓
Check vm.zone_reclaim_mode
            ↓
Check Reclaim / Swap / OOM
            ↓
Check cgroup / CPU Placement
            ↓
Correlate with MongoDB
            ↓
Identify Root Cause
```

> **Measure First. Tune Second.**

## 26. Production NUMA Safety Gate

### BEFORE

Verify correct environment/member, MongoDB and OS/kernel versions, hardware/vNUMA topology, current NUMA policy, `vm.zone_reclaim_mode`, `mongod` runtime policy, `numastat` baseline, MongoDB/application baselines, current MongoDB/platform guidance, rollback, and monitoring.

### CHANGE

Use one representative member, one bounded change, understood maintenance impact, and restart/reboot only when required.

### VALIDATE

Confirm expected topology/policy/zone-reclaim value, healthy `mongod`, acceptable startup logs, correct replica state, healthy replication, acceptable memory/reclaim/swap/storage behavior, healthy application, and healthy monitoring.

### STOP

Stop rollout if `mongod` fails to recover, member state or replication deteriorates, an unexpected election occurs, memory/reclaim/swap worsens, OOM occurs, storage/application latency deteriorates, the effective policy is unexpected, or root cause becomes uncertain.

> **Successful Reboot ≠ Successful NUMA Change**

## 27. Replica-Set-Aware Rollout and Burn-In

```text
Validate Replica Set
       ↓
Select One Member
       ↓
Apply NUMA Change
       ↓
Restart / Reboot
       ↓
Validate Member
       ↓
Validate Replication
       ↓
Burn-In
       ↓
Proceed to Next Member
```

During burn-in compare MongoDB latency, WiredTiger pressure, replication lag, CPU, NUMA memory distribution, reclaim, swap, storage latency, application latency/errors, and unexpected restarts. Duration should reflect workload cycles and risk rather than a universal fixed interval.

Primary maintenance must account for elections, reconnect behavior, driver topology discovery, write interruption, replication state, and maintenance windows. Sharded clusters require the same one-member-at-a-time discipline within each replica set; do not simultaneously modify multiple voting members without an architecture-specific plan.

## 28. Configuration Drift

Drift sources include BIOS changes, OS/kernel updates, VM replacement, instance-family changes, systemd changes, configuration management, containers, and Kubernetes nodes. Compare approved baseline with observed runtime state and investigate differences before rollout.

## 29. Post-Reboot and Post-Patching Validation

After reboot/patching validate:

```bash
lscpu
numactl --hardware
numastat
sysctl vm.zone_reclaim_mode
systemctl status mongod
systemctl show mongod -p MainPID
```

Where relevant:

```bash
sysctl kernel.numa_balancing
```

Then validate topology, NUMA policy, zone reclaim, startup logs, MongoDB reachability, replica state, replication, memory distribution, swap/reclaim, storage behavior, application and monitoring.

## 30. Kernel and OS Upgrade Compatibility Gate

Before changing OS/kernel, identify the exact MongoDB release, target OS/kernel, review MongoDB release notes, validate compatibility, test a representative member, and perform controlled rollout.

> **Before OS/kernel upgrades, validate compatibility against release notes for the exact MongoDB version being operated.**

Do not permanently encode transient kernel defects into the handbook baseline.

## 31. Transparent Huge Pages Boundary

NUMA and THP are related OS memory concerns but separate configuration domains. MongoDB THP guidance is version-sensitive. Detailed architecture/configuration/validation belongs in **2.12 — Transparent Huge Pages Considerations**.

## 32. Automation

Automated inventory should capture hostname, MongoDB version, OS/kernel, NUMA nodes, CPU/node, memory/node, `vm.zone_reclaim_mode`, `kernel.numa_balancing` where relevant, MongoDB service configuration, container/cgroup boundary, and timestamp. Compare expected/observed values, but do not automatically remediate NUMA drift across the production fleet without controlled validation.

## 33. Production Anti-Patterns

Avoid assuming total RAM is uniformly accessible; assuming every NUMA host needs arbitrary tuning; copying historical MongoDB NUMA commands without version validation; manually launching production `mongod` outside service management; casually editing package-owned units; applying interleaving while ignoring zone reclaim; nonpersistent zone-reclaim changes; inventing universal `kernel.numa_balancing` settings; CPU pinning or strict binding without topology/capacity analysis; changing WiredTiger cache merely because NUMA exists; treating remote memory, storage latency, swap, or OOM as proof of a single root cause; inferring VM/Kubernetes topology from aggregate specifications/metrics; rolling changes across members simultaneously; skipping burn-in; assuming reboot success means database success; and failing to rebaseline after upgrades/replacement.

## 34. Production Readiness Checklist

Validate NUMA presence/node count/CPU and memory mapping; physical/vNUMA architecture; MongoDB version and current guidance; selected preferred/fallback architecture; `numactl`/`numastat` availability; `vm.zone_reclaim_mode`; persistent configuration; `kernel.numa_balancing` inventory where relevant; swap/reclaim/OOM monitoring; systemd-managed lifecycle; effective process policy; guest/cloud topology; container memory and CPU boundaries; healthy baseline; monitoring; safety gate; rollback; replica-aware rollout; burn-in; stop conditions; reboot/patch validation; and drift detection.

## 35. Key SRE/DBRE Principles

```text
Installed Memory != Uniformly Accessible Memory
Total RAM != NUMA-Local RAM
NUMA Exists != NUMA Root Cause
Firmware NUMA Disablement != Linux NUMA Mitigation
Configured NUMA Policy != Effective NUMA Policy
NUMA Interleaving Alone != Complete NUMA Mitigation
Remote Memory != Automatic Incident
WiredTiger Cache != Total MongoDB Memory
CPU Affinity != NUMA Optimization
More RAM != Correct NUMA Policy
Swap Activity != Automatically Insufficient RAM
OOM != Automatically Insufficient Physical RAM
Storage Symptom != Storage Root Cause
Runtime NUMA Configuration != Persistent NUMA Configuration

Service Running != Database Configuration Validated
Successful Reboot != Successful NUMA Change

```

> **Understand the CPU and memory topology visible to MongoDB, use the NUMA architecture recommended for the exact MongoDB and platform versions, validate the effective runtime state, and roll changes through the database topology only after controlled testing and burn-in.**
