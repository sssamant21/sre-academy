# 2.12 — Transparent Huge Pages Considerations

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly noted  
**Platform Scope:** Self-managed MongoDB on Linux  
**Status:** Canonical

> **THP Guidance Is Version- and Architecture-Sensitive**

Transparent Huge Pages (THP) is a Linux kernel memory-management capability that allows larger memory pages to be used transparently. MongoDB 8.0 changed the production recommendation for supported Linux architectures after introducing an updated TCMalloc allocator. A configuration appropriate for MongoDB 7.x can therefore be incorrect for MongoDB 8.x.

## 1. Canonical Decision Model

```text
MongoDB Version
       |
       +---- 7.x and earlier -> Disable THP
       |
       +---- 8.x
                  |
                  v
             Architecture
                  |
        +---------+---------+
        |                   |
        v                   v
 x86_64 / ARM64       PPC64LE / s390x
        |                   |
 Updated TCMalloc      Legacy TCMalloc
        |                   |
        v                   v
 MongoDB 8.x THP       Disable THP
 baseline
```

> **MongoDB Major Version Alone ≠ Complete THP Decision**

## 2. MongoDB 8.x Updated-TCMalloc Baseline

For supported MongoDB 8.x Linux deployments on x86_64/ARM64, validate the combined baseline:

```text
enabled             = always
defrag               = defer+madvise
max_ptes_none        = 0
vm.overcommit_memory = 1
```

THP enabled does not mean every THP control should be set to `always`.

## 3. Validate Architecture and THP State

```bash
uname -m
uname -r

if [ -d /sys/kernel/mm/transparent_hugepage ]; then
    THP=/sys/kernel/mm/transparent_hugepage
elif [ -d /sys/kernel/mm/redhat_transparent_hugepage ]; then
    THP=/sys/kernel/mm/redhat_transparent_hugepage
else
    echo "THP control path not found"
    exit 1
fi

cat "$THP/enabled"
cat "$THP/defrag"

if [ -r "$THP/khugepaged/max_ptes_none" ]; then
    cat "$THP/khugepaged/max_ptes_none"
fi

sysctl vm.overcommit_memory
```

For the supported MongoDB 8.x updated-TCMalloc baseline, the logical expected values are `always`, `defer+madvise`, `0`, and `1` respectively.

> **One Correct THP Setting ≠ Complete MongoDB Memory Baseline**

## 4. MongoDB 7.x and Legacy Allocator Boundary

MongoDB 7.x and earlier Linux deployments use the applicable legacy THP-disabled guidance. MongoDB 8.x PPC64LE and s390x deployments use legacy TCMalloc and must not blindly inherit the updated-TCMalloc THP baseline.

The historical disabled baseline uses:

```text
enabled = never
defrag  = never
```

Validate against the exact MongoDB release and platform being operated.

## 5. Binary Version vs. FCV

Feature Compatibility Version does not select the memory allocator. THP decisions follow the MongoDB binary, allocator implementation, architecture, and platform—not FCV alone.

> **FCV ≠ MongoDB Memory Allocator Version**

## 6. Host-Level Scope

THP is a Linux host/kernel policy and can affect MongoDB and other workloads on the host. Avoid unnecessary workload colocation when applications require conflicting THP policies.

> **MongoDB Host Tuning ≠ MongoDB-Process-Only Tuning**

## 7. Persistence and Configuration Ownership

Runtime THP state is not necessarily persistent across reboot. Maintain one authoritative version-aware configuration mechanism and validate the effective state after reboot.

Avoid multiple independent mechanisms—bootloader, systemd, tuned, cloud-init, and configuration management—competing to manage the same controls.

Where systemd establishes the host policy, ensure the required THP baseline is applied before `mongod` enters production operation. Avoid casually modifying package-owned MongoDB service files.

## 8. tuned and OS Profiles

On RHEL-family systems, inspect the active tuning profile where applicable:

```bash
tuned-adm active
systemctl status tuned
```

Determine whether the profile preserves or overrides the approved MongoDB THP baseline.

## 9. MongoDB Startup and Runtime Validation

After restart or reboot:

```bash
systemctl status mongod
journalctl -u mongod
```

Review MongoDB startup warnings and validate database reachability, replica state, replication, memory behavior, CPU, storage latency, application health, and monitoring.

> **Service Active ≠ Host Baseline Validated**

## 10. WiredTiger and NUMA Boundaries

THP is not a WiredTiger cache-sizing control and should not be used as a reason to arbitrarily change WiredTiger cache size. NUMA is a separate Linux memory domain covered in Section 2.11.

```text
Linux Memory Architecture
       |
       +---- NUMA -> Section 2.11
       |
       +---- THP  -> Section 2.12
```

## 11. Monitoring and Troubleshooting

Correlate THP state with MongoDB latency, WiredTiger pressure, replication lag, CPU, memory pressure, page faults, reclaim, swap, storage I/O, and application latency.

Useful Linux evidence can include:

```bash
grep -i huge /proc/meminfo
grep -i thp /proc/vmstat
```

Exact counters vary by kernel. Do not invent universal THP-counter alert thresholds.

> **THP State ≠ Proven Incident Root Cause**

## 12. Cloud and Kubernetes

Cloud images can retain an obsolete MongoDB-era THP baseline. Validate MongoDB version, architecture, kernel, effective THP state, and persistence whenever instances are replaced.

In Kubernetes, THP is primarily a node/kernel-level concern. Prefer node images, bootstrap configuration, node pools, and infrastructure automation over privileged per-pod mutation of THP controls.

MongoDB 7.x and MongoDB 8.x workloads requiring conflicting THP states may need separate node pools during migration.

## 13. Upgrade and Rollback Integration

THP is part of major-version upgrade planning:

```text
Current Binary
     |
Current Allocator / THP Baseline
     |
Target Binary
     |
Target Allocator / THP Baseline
     |
Transition Plan
     |
Rollback Plan
```

During rolling upgrades, each member host should use the baseline appropriate to the binary/allocator running on that member. Avoid mixed MongoDB major versions with conflicting THP requirements on the same host.

A complete rollback may require both binary rollback and restoration of the previous host THP baseline.

> **Binary Rollback ≠ Complete MongoDB Rollback**

## 14. Production THP Safety Gate

### Before

```text
[ ] Correct environment/member
[ ] Binary version verified
[ ] FCV recorded separately
[ ] CPU architecture verified
[ ] Allocator baseline identified
[ ] OS/kernel recorded
[ ] Current THP state captured
[ ] vm.overcommit_memory captured
[ ] Persistence mechanism identified
[ ] tuned/profile state understood
[ ] Replica health verified
[ ] Rollback documented
```

### Change

```text
[ ] One representative member/host
[ ] Correct version/architecture baseline selected
[ ] Persistent configuration updated
[ ] Runtime configuration verified
[ ] Restart/reboot only where required
```

### Validate

```text
[ ] enabled correct
[ ] defrag correct
[ ] max_ptes_none correct where applicable
[ ] vm.overcommit_memory correct
[ ] mongod healthy
[ ] Startup logs acceptable
[ ] Replica state correct
[ ] Replication healthy
[ ] Memory/CPU/storage behavior acceptable
[ ] Application healthy
```

### Stop

Stop rollout if the THP state differs from expected, `mongod` fails to recover, replica/replication health deteriorates, unexpected elections occur, resource behavior materially worsens, application impact increases, or the rollback path becomes uncertain.

> **Successful THP Write ≠ Successful MongoDB Change**

## 15. Replica-Set and Sharded-Cluster Rollout

Apply host changes one member at a time, validate the member and replication, perform an appropriate burn-in, and only then proceed. Account for elections and application reconnect behavior when primary maintenance is required.

For sharded clusters, roll changes separately through shard replica sets, the config server replica set, and relevant `mongos` infrastructure. Avoid simultaneous maintenance of multiple voting members in the same replica set.

## 16. Post-Reboot and Post-Patching Validation

Revalidate architecture, kernel, THP path, all applicable THP controls, `vm.overcommit_memory`, persistence/tuned state, MongoDB startup logs, replica health, replication, memory/CPU/storage behavior, application health, and monitoring.

Kernel upgrades require validation against guidance for the exact MongoDB release rather than assuming identical configuration values guarantee identical behavior.

## 17. Configuration Drift and Automation

Inventory should include:

```text
Hostname
MongoDB binary version
FCV
Architecture
Expected allocator
OS/kernel
THP control path
enabled
defrag
max_ptes_none
vm.overcommit_memory
Persistence mechanism
tuned profile
Timestamp
```

Automation must be version- and architecture-aware. Drift detection should not blindly remediate production hosts during unsafe mixed-version upgrade phases.

## 18. Production Anti-Patterns

Avoid applying 7.x guidance to 8.x, applying the updated 8.x baseline to unsupported architectures, using FCV as the THP selector, setting every THP control to `always`, checking only `enabled`, ignoring persistence or tuned, confusing THP with HugeTLB/NUMA/WiredTiger sizing, colocating workloads with conflicting THP requirements, blindly changing all replica members, or blaming THP without evidence.

## 19. Key SRE/DBRE Principles

```text
THP Guidance Is Version-Sensitive
THP Guidance Is Architecture-Sensitive
Historical MongoDB Guidance != Current MongoDB Guidance
MongoDB Major Version Alone != Complete THP Decision
FCV != MongoDB Memory Allocator Version
THP Enabled != Every THP Control Set to always
One Correct THP Setting != Complete MongoDB Memory Baseline
THP Configuration != WiredTiger Cache Configuration
THP Configuration != NUMA Configuration
Runtime THP State != Persistent THP State
MongoDB Host Tuning != MongoDB-Process-Only Tuning
Configured THP State != Validated MongoDB State
High CPU != THP Root Cause
Storage Symptom != Storage Root Cause
Binary Rollback != Complete MongoDB Rollback
Service Active != Host Baseline Validated
Host Healthy != Replica Member Healthy
Successful THP Write != Successful MongoDB Change
```

> **Determine the MongoDB binary version, CPU architecture, allocator implementation, and effective Linux state before selecting the THP baseline; manage that baseline persistently and treat changes as part of the database upgrade, rollback, and topology lifecycle rather than generic Linux tuning.**
