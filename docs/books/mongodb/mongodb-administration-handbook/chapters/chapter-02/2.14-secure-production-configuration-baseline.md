# 2.14 — Secure Production Configuration Baseline

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly relevant  
**Platform Scope:** Self-managed MongoDB on Linux, cloud VMs, and Kubernetes  
**Status:** Canonical

> **Installed MongoDB ≠ Production-Eligible MongoDB**

A MongoDB process should become production-eligible only after its effective network exposure, TLS, authentication, authorization, internal membership authentication, host and filesystem controls, secrets, backup and monitoring access, and infrastructure security boundaries have been validated.

A secure configuration file alone is insufficient. Production validation must prove both that authorized behavior succeeds and that unauthorized behavior fails.

## 3. Network Exposure

MongoDB should normally be accessible only through explicitly approved network paths: applications, replica/config members, mongos, administrators, monitoring, backup, and automation. Direct Internet exposure should not be the normal architecture.

Self-managed MongoDB normally binds to localhost by default. Production deployments often require additional interfaces, but these should be explicitly understood and protected.

Example:

```yaml
net:
  port: 27017
  bindIp: 127.0.0.1,10.10.20.15
```

Broad binding such as `0.0.0.0` or `net.bindIpAll` expands listener exposure. It does not by itself prove Internet reachability because routing and infrastructure controls also matter.

> **Broad Listener Binding Increases the Security Boundary That Must Be Defended**

Defense in depth combines listener restriction, host/network firewalls, cloud SG/NSG/firewall controls, segmentation, TLS, authentication, and authorization.

> **Firewall Protected ≠ Authentication Optional**

> **Authentication Enabled ≠ Network Segmentation Optional**

MongoDB commonly uses port `27017`. Changing it may reduce noise but is not a security boundary.

## 4. Authentication and Authorization

Authentication answers who an identity is; authorization determines what that identity may do.

A common standalone client access-control setting is:

```yaml
security:
  authorization: enabled
```

MongoDB internal membership authentication also enables client authorization, so validate effective access control rather than merely looking for one configuration line.

## 5. Localhost Bootstrap Exception

When access control is enabled and no users or roles exist, MongoDB provides a controlled localhost bootstrap mechanism for initial administrative setup. It can also participate in initial replica-set bootstrap. Treat it as bootstrap-only, not as a persistent administrative bypass.

> **Bootstrap Mechanism ≠ Persistent Administrative Access Path**

## 6. Identity Separation and Least Privilege

Use separate attributable identities for human administrators, applications, monitoring, backups, automation, and emergency break-glass access. Each should have an owner, purpose, privilege boundary, credential lifecycle, rotation process, and auditability.

> **Shared Credential ≠ Accountable Administration**

Applications should receive only the resources and actions they require. Built-in roles such as `read`, `readWrite`, `dbAdmin`, `userAdmin`, `clusterMonitor`, `backup`, and `restore` are examples, not universal prescriptions. Use custom roles when built-in roles are broader than necessary.

> **Application Connectivity ≠ Administrative Privilege**

## 7. Internal Membership Authentication

Replica-set and sharded-cluster members authenticate one another independently from application clients. Common self-managed approaches are keyfile and X.509 authentication.

> **Client Authentication ≠ Internal Membership Authentication**

### Keyfiles

MongoDB keyfiles provide shared membership credentials. Supported key material follows MongoDB's documented 6–1024 character and Base64-character requirements. YAML-formatted keyfiles can contain multiple keys, and members must retain at least one common valid key.

Keyfiles must be securely generated/distributed, excluded from source control, readable only as required by the MongoDB service identity, and rotated through a controlled procedure. On UNIX, MongoDB requires membership keyfiles not to have group or world permissions.

```bash
ls -l /path/to/keyfile
stat /path/to/keyfile
```

> **Keyfile Present ≠ Keyfile Secure**

### Rolling Key Rotation

```text
OLD everywhere
      |
      v
OLD + NEW deployed gradually
      |
      v
Validate NEW everywhere
      |
      v
Remove OLD gradually
```

> **Members Must Retain a Common Authentication Key Throughout Rotation**

## 8. X.509 Membership Authentication

X.509 membership security depends on trusted CA architecture, certificate identity, membership attributes, SAN, intended certificate usage/EKU, validity, and private-key protection.

> **Valid Certificate ≠ Correct MongoDB Certificate**

Relevant membership distinguished-name attributes can include `O`, `OU`, and `DC` according to the MongoDB/PKI design. Prefer correct SAN-based host identity rather than legacy CN fallback. Certificate preflight must validate intended server/member usage; a trusted, unexpired certificate can still be inappropriate for its MongoDB role.

## 9. TLS Production Baseline

TLS can protect application, administrative, monitoring, backup, mongos-to-mongod, and mongod-to-mongod communication.

Where the security architecture requires TLS, transitional modes such as `allowTLS`/`preferTLS` should lead to an encrypted end state such as:

```yaml
net:
  tls:
    mode: requireTLS
```

> **Migration TLS Mode ≠ Production End State**

TLS validation includes CA trust, certificate identity, SAN, intended usage, validity window, private-key protection, and approved protocol policy. Never disable validation merely to make connectivity work.

Troubleshoot CA/chain, SAN, EKU, validity, host time, private key, permissions, and DNS before weakening security.

## 10. Certificate Lifecycle

Certificates require issuance, deployment, validation, expiration monitoring, controlled rotation, burn-in, and retirement of old trust. MongoDB certificate warnings are supplemental signals, not a complete monitoring strategy.

> **Certificate Expiry Is Both a Security and Availability Concern**

TLS behavior can depend on exact MongoDB release, OS, cryptographic library, and policy. Revalidate after MongoDB, OS, or OpenSSL/crypto-library updates.

Private keys must have restrictive ownership/permissions, approved secret delivery, secure backup, rotation, and auditability. Never commit private keys to Git.

## 11. Secrets Management

Prefer approved secret stores and runtime delivery. Do not place production passwords, keyfiles, private keys, or secret values in Git, plaintext Helm/GitOps values, Terraform source, container images, CI logs, tickets, or documentation. Repositories may contain secret references, not secret material.

## 12. Host and Filesystem Security

Validate ownership and permissions for `mongod.conf`, `dbPath`, logs, keyfiles, and TLS private keys. MongoDB RBAC cannot protect files from unauthorized privileged OS access.

```bash
ls -l /etc/mongod.conf
stat /etc/mongod.conf
ls -ld /var/lib/mongo
stat /var/lib/mongo
```

> **MongoDB RBAC ≠ Host Filesystem Security**

`mongod` should normally run under a dedicated non-root OS identity. Inspect systemd state with:

```bash
systemctl cat mongod
systemctl show mongod
```

Avoid command-line/environment secret leakage through shell history, process listings, CI logs, crash dumps, diagnostics, or support bundles.

## 13. Host Administrative Access

Use attributable user identities, controlled SSH/session management, least-privilege sudo, MFA through surrounding access architecture where appropriate, access logging, and removal of unnecessary accounts.

> **MongoDB Admin Rights ≠ Linux Root Rights**

Inventory unnecessary listening/running services:

```bash
ss -lntup
systemctl --type=service --state=running
```

## 14. Cloud Security Boundary

AWS security groups, Azure NSGs, GCP firewall policies, routing, and private networking form part of the MongoDB security boundary. Avoid unrestricted `0.0.0.0/0 -> 27017` production access unless an exceptional architecture is explicitly reviewed and approved.

## 15. Kubernetes Security Boundary

MongoDB on Kubernetes adds Kubernetes RBAC, ServiceAccounts, Secrets, NetworkPolicy, pod security, node security, and persistent-volume security.

> **Kubernetes Secret ≠ Automatically Secure Secret**

Where enforced by the networking implementation, NetworkPolicy should restrict MongoDB paths, but it does not replace MongoDB authentication.

Review container controls such as `runAsUser`, `runAsGroup`, `fsGroup`, privilege, capabilities, read-only root filesystem, and seccomp against the supported MongoDB/operator architecture rather than applying generic hardening blindly.

## 16. Backup, Monitoring, and Automation Security

Backups can contain the entire production dataset and must have encryption, access control, dedicated identities, secure transport, retention/deletion controls, and auditability.

> **Database Secure + Backup Exposed = Database Not Secure**

Monitoring should use a dedicated least-privilege identity; `clusterMonitor` may form part of the design depending on product requirements. Backup and automation should likewise use dedicated machine identities rather than personal DBA credentials.

Break-glass access should be rarely used, strongly protected, independently audited, tested, rotated, and owned.

## 17. Auditing

MongoDB operational logging is not the same as a dedicated audit facility. Audit capabilities vary by edition/deployment. Enterprise capabilities can provide dedicated security auditing and supported structured audit formats. Detailed audit architecture belongs in later security chapters.

## 18. Patch Level Is Part of Security

A secure baseline is not defined by `MongoDB 8.x` alone.

```text
Supported MongoDB Version
          +
Approved Current Patch
          +
Security Advisory Review
          +
OS / Crypto Compatibility
          =
Supported Security Baseline
```

Cross-reference Section 2.19.

## 19. Declared vs. Effective Security

Correct configuration in source control does not prove runtime state. Command-line overrides, stale images, failed rollouts, alternate configuration files, pod differences, or manual changes can alter behavior.

> **Declared Secure Configuration ≠ Effective Secure Runtime**

Validate the running listener, authentication, authorization, TLS, member health, and externally observed network boundary.

## 20. Positive and Negative Security Tests

Positive tests prove authorized clients and required operations succeed. Negative tests prove unauthenticated/invalid identities, forbidden operations, and unapproved network sources fail.

> **Successful Authorized Access Alone ≠ Security Validation**

Host-side `ss -lntp` does not prove external reachability policy. Validate from approved and unapproved network locations where feasible.

## 21. Security Drift Inventory

Track environment, host/pod, MongoDB role/version/patch, configuration source/version, listeners/port, authorization state, authentication mechanisms, `clusterAuthMode`, `keyFile` path, TLS mode, CA/certificate identity, SAN, EKU, expiration, service identity, sensitive file permissions, users/roles/privileged roles, firewall/SG/NSG state, external exposure, NetworkPolicy where applicable, and last validation.

Never record passwords, keyfile contents, private keys, or secret values in compliance inventory.

## 22. Monitoring and Alerting

Correlate MongoDB, OS, network, cloud, Kubernetes, identity, and secrets-platform telemetry. Monitor authentication/authorization failures, TLS failures, membership-auth failures, certificate expiration/identity drift, unexpected users or privileged roles, privilege changes, external exposure, configuration drift, and rotation failures.

Critical event examples include authorization unexpectedly disabled, TLS enforcement removed, unexpected public exposure, membership-auth failure, unexpected privileged identity, or critical certificate-expiry condition. Exact thresholds should follow organizational policy.

## 23. Failure Scenarios

Important scenarios include authorization disabled while the process remains healthy; broad listener drift; cloud firewall exposure; certificate expiry; incorrect certificate rotation; keyfile permission drift; secret committed to Git; overprivileged application; shared administrator identity; Kubernetes secret exposure; and backup credential/storage compromise.

A secret committed to Git should be treated as exposed: rotate/revoke it, assess exposure, remediate repository history according to policy, and validate consumers.

## 24. Security Troubleshooting Workflow

```text
Security Failure
      |
      v
Identify Layer
      |
      +--> Network
      +--> TLS
      +--> Authentication
      +--> Authorization
      +--> Membership Authentication
      +--> Filesystem / Secret / Host
      +--> Cloud / Kubernetes
      |
      v
Collect Evidence
      |
      v
Correct Minimum Required Layer
      |
      v
Positive Test
      |
      v
Negative Test
      |
      v
Validate Availability
```

> **Connectivity Restored ≠ Security Correctly Restored**

Authentication troubleshooting includes identity, mechanism/database, credential/certificate, TLS, time, DNS, network, and logs. Authorization troubleshooting follows authenticated identity -> roles -> inherited privileges -> requested resource/action and fixes the smallest missing privilege. Membership troubleshooting includes `clusterAuthMode`, key/certificate, common-key availability, permissions, SAN/EKU, CA, TLS, DNS, time, and logs.

## 25. Security Change Safety Gate

Every security change can affect availability.

> **Every Security Change Is Also an Availability Change**

Before changing, capture environment/topology, version/patch, current security/network state, authentication/authorization/member-auth/TLS state, certificate expiry, secret ownership, MongoDB/replica/application/monitoring/backup health, and rollback.

During change, modify one security dimension where practical, never print secrets, update the persistent source of truth, preserve least privilege, use a representative/canary member, and follow topology-aware rollout.

Validate expected listeners, approved and denied network access, valid and invalid authentication, required and forbidden operations, TLS, member authentication, replica/shard health, application, monitoring, and backup.

Stop if a member cannot start/rejoin, TLS/member auth fails, required application access is lost, unauthorized access succeeds, exposure expands, security must be disabled to continue, or rollback becomes uncertain.

## 26. Topology-Aware Rollout and Burn-In

For replica sets, prefer secondary -> change -> restart/validate -> burn-in -> next secondary -> primary-aware final stage. For sharded clusters account for config server replica set, shard replica sets, mongos, applications, monitoring, backup, and automation.

After changes observe authentication, authorization, TLS, member authentication, replication, elections, application errors, monitoring, backups, certificate errors, network denials, and MongoDB logs.

> **Successful Restart ≠ Successful Security Change**

## 27. Post-Reboot / Post-Patching Validation

After reboot:

```bash
systemctl status mongod
journalctl -u mongod
ss -lntp
```

Then validate effective configuration/listeners, authentication, authorization, member authentication, TLS/certificates, sensitive permissions, replica state, application, monitoring, and backup.

Repeat after MongoDB/OS/crypto patches, certificate/key rotation, image/node replacement, operator/chart upgrades, firewall changes, or secret-management changes.

> **Patch Successful ≠ Security Baseline Preserved**

## 28. Upgrade Security Compatibility Gate

Before upgrade review exact target patch, advisories, authentication mechanisms, TLS behavior, OS/crypto compatibility, certificate requirements, security parameters, deprecated options, role/audit behavior, driver compatibility, and membership authentication. Cross-reference Sections 2.19–2.27.

## 29. Production Eligibility Gate

```text
[ ] Supported MongoDB patch validated
[ ] Applicable security advisories reviewed
[ ] Network exposure validated
[ ] TLS enforcement and certificate identity/expiry validated
[ ] Client authentication validated
[ ] Authorization validated
[ ] Membership authentication validated
[ ] OS service identity and sensitive file permissions validated
[ ] Secrets delivered securely
[ ] Approved connectivity succeeds
[ ] Unauthorized connectivity fails
[ ] Required operations succeed
[ ] Forbidden operations fail
[ ] Monitoring and drift detection registered
[ ] Backup path validated
[ ] Recovery/rollback understood
```

Only then: **PRODUCTION ELIGIBLE**.

## 30. Production Anti-Patterns

Reject unintended public exposure; assuming private networking replaces authentication; relying only on bind/firewall controls; treating port changes as hardening; running without access control; granting applications root; shared DBA credentials; human credentials in automation; secrets/private keys in Git; plaintext GitOps secrets; permissive UNIX membership keyfiles; key replacement without overlap; unsuitable certificates; reliance on legacy CN; ignored EKU; indefinite transitional TLS; disabled certificate validation; ignored expiry; MongoDB warning as sole certificate monitor; stale TLS assumptions; routine root execution; assuming Kubernetes Secrets solve secrets management; admin monitoring/backup identities; changing multiple security layers simultaneously; testing only successful access; no denied-access tests; host-only network validation; trusting declared configuration; ignoring infrastructure drift; assuming restart proves security correctness; or assuming major version alone defines security posture.

> **A MongoDB member becomes production-eligible only after its effective network exposure, TLS, authentication, authorization, internal membership authentication, host and filesystem controls, secrets, backup and monitoring access, and infrastructure security boundaries have been validated with both positive and negative tests and registered for continuous drift detection.**
