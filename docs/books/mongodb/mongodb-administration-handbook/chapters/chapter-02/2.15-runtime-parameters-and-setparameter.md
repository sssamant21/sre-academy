# 2.15 — Runtime Parameters and `setParameter`

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly relevant  
**Platform Scope:** Self-managed MongoDB on Linux, cloud VMs, containers, and Kubernetes  
**Status:** Canonical

> **A Runtime Change Is a Production Change Even When It Does Not Require a Restart**

MongoDB exposes server parameters that influence runtime behavior, diagnostics, security, replication, query processing, resource management, observability, and other server functions. Some parameters can be configured at startup, some can be modified while the process is running, and some support both mechanisms. Their availability and behavior can vary by MongoDB release and process type.

The operational objective is not merely knowing the syntax of `setParameter`. SRE/DBRE teams must understand version, parameter semantics, mutability, persistence, process scope, topology scope, rollback, and drift before changing a running MongoDB process.

## Learning Objectives

After completing this section, you should be able to:

- distinguish server parameters from ordinary MongoDB configuration settings;
- use `getParameter` to inspect runtime state;
- use MongoDB 8.x parameter metadata to evaluate startup/runtime mutability;
- safely use `setParameter`;
- distinguish runtime state from persistent startup configuration;
- understand process-local and topology implications;
- prevent restart-induced parameter reversion;
- distinguish server parameters from cluster parameters;
- safely canary and roll parameter changes;
- manage parameter changes in replica sets and sharded clusters;
- integrate runtime changes with GitOps and configuration management;
- detect member-to-member and runtime-to-source drift;
- define rollback procedures; and
- validate explicit overrides during upgrades.

## 1. MongoDB Parameter Architecture

```text
MongoDB Configuration
        |
        +--> General Configuration Options
        +--> Server Parameters
        +--> Cluster Parameters
        +--> Dedicated Administrative Commands
        +--> Deployment-Platform Configuration
```

These mechanisms are not interchangeable.

> **Configurable Behavior ≠ `setParameter` Target**

## 2. Server Parameters

Server parameters expose configurable behavior within `mongod` or `mongos`.

```text
Server Parameter
      |
      +--> Startup-Settable
      +--> Runtime-Settable
      +--> Startup + Runtime
```

The exact classification depends on the parameter and MongoDB release. A parameter can be introduced, deprecated, removed, have its default or range changed, or have its scope, mutability, or behavior changed between releases.

> **Parameter Exists ≠ Parameter Is Safe to Change**

## 3. Product Default, Persistent State, and Runtime State

```text
MongoDB Product Default
          |
          v
Persistent Startup Configuration
          |
          | process startup
          v
Effective Runtime State
          |
          | setParameter
          v
Runtime Override
```

For example, if persistent configuration specifies `A` and an operator changes the runtime value to `B`, the process can run with `B` while persistent configuration remains `A`.

> **Runtime State ≠ Persistent State**

## 4. `getParameter`

Use `getParameter` through the `admin` database to inspect server-parameter state.

```javascript
db.adminCommand({
  getParameter: 1,
  parameterName: 1
})
```

Operational sequence:

```text
GET -> RECORD -> UNDERSTAND -> CHANGE
```

> **Never Change a Runtime Parameter Without Recording Its Previous Value**

## 5. MongoDB 8.x Parameter Metadata

MongoDB 8.x provides useful parameter metadata through detailed `getParameter` inspection.

```javascript
db.adminCommand({
  getParameter: { showDetails: true },
  parameterName: 1
})
```

Relevant details can include the current `value`, `settableAtRuntime`, and `settableAtStartup`. Use this metadata as a production preflight, then validate the parameter against official documentation for the exact MongoDB release.

> **Runtime Metadata + Release Documentation = Change Preflight**

## 6. Parameter Inventory and Filtering

MongoDB 8.x provides mechanisms for broader parameter inventory and filtering according to where parameters can be set. Broad retrieval can use supported forms such as:

```javascript
db.adminCommand({
  getParameter: "*"
})
```

This can help with upgrade analysis, automation, runtime audits, and drift detection, but it should not become the compliance contract.

> **Available Parameter Inventory ≠ Approved Production Baseline**

## 7. Curated Production Baseline

Track operationally significant parameters, especially explicit overrides and security-, availability-, and performance-critical settings. Useful inventory fields include parameter, expected/runtime/persistent/default values, runtime/startup mutability, MongoDB version, process applicability, reason, owner, change reference, rollback value, persistence requirement, and last compatibility review.

Never store secrets in this inventory.

## 8. `setParameter`

The runtime command follows this pattern:

```javascript
db.adminCommand({
  setParameter: 1,
  parameterName: newValue
})
```

It is an administrative operation and must be issued through the `admin` database using appropriately authorized access. Only use it when the exact parameter supports runtime modification.

> **Runtime-Settable ≠ Risk-Free**

## 9. Runtime Changes Are Not Persistent

```text
Persistent Config = A
        |
        | startup
        v
Runtime = A
        |
        | setParameter
        v
Runtime = B
        |
        | restart
        v
Runtime = A
```

A runtime `setParameter` change does not itself make the value persistent across server restart.

> **Runtime Change ≠ Persistent Configuration Change**

## 10. Persistent Server Parameters

Where a server parameter supports startup configuration, persistence can be established through the supported configuration mechanism:

```yaml
setParameter:
  parameterName: value
```

or a supported startup option such as:

```bash
mongod --setParameter parameterName=value
```

and, where applicable, the corresponding `mongos` option. Always verify that the specific parameter supports startup configuration.

## 11. Startup-Only Parameters

Some parameters cannot be modified dynamically. They require persistent configuration and a controlled process restart. Do not infer runtime mutability from the parameter name, type, similarity to another parameter, or behavior in an older MongoDB version.

## 12. Readable ≠ Writable

A value returned through parameter inspection does not necessarily imply that `setParameter` is the correct mechanism for modifying it.

> **Readable Through `getParameter` ≠ Modified Through `setParameter`**

Feature Compatibility Version is a key example: it can participate in parameter inspection, but MongoDB changes FCV through the dedicated `setFeatureCompatibilityVersion` workflow. FCV is covered in Sections 2.21–2.23.

## 13. Server Parameters vs. Cluster Parameters

```text
setParameter
     |
     v
Server / Process Parameter

setClusterParameter
       |
       v
Cluster Parameter
```

> **Server Parameter ≠ Cluster Parameter**

Cluster parameters are covered in 2.16 — Cluster Parameters and `setClusterParameter`.

## 14. Dedicated Configuration Mechanisms

Before choosing `setParameter`, determine whether the behavior is actually a server parameter. The correct mechanism may instead be a configuration-file option, cluster parameter, dedicated MongoDB command, deployment-platform setting, or managed-service configuration interface.

## 15. Stable API Consideration

Administrative automation must account for Stable API behavior. When clients operate using Stable API V1 with strict API behavior, administrative commands such as `setParameter` can be restricted. Troubleshooting should distinguish unsupported parameter semantics, authorization problems, wrong process targeting, runtime mutability restrictions, and client/API restrictions.

> **Parameter Capability ≠ Client API Permission to Invoke the Command**

## 16. MongoDB Atlas Boundary

This section primarily applies to self-managed MongoDB. Runtime `setParameter` is not supported on MongoDB Atlas clusters; use Atlas-supported configuration mechanisms instead.

## 17. Process-Local Scope

A runtime server-parameter change applies to the targeted process unless the parameter documentation explicitly defines otherwise.

```text
Replica Set
Member A = X
Member B = X
Member C = X

Change Member B

Member A = X
Member B = Y
Member C = X
```

> **Changed on One Member ≠ Changed on the Replica Set**

## 18. Replica-Set Implications

Before changing a parameter determine whether all members should match, whether mixed values can safely coexist, whether the parameter affects replication, elections, query execution, or resources, and what happens after failover.

## 19. Failover Behavior Drift

```text
Primary      = Y
Secondary 1  = X
Secondary 2  = X
        |
        v
Primary Failure / Election
        |
        v
New Primary = X
```

> **Runtime Parameter Drift Can Become Failover Behavior Drift**

## 20. Replica-Set Rollout

Where documented semantics permit mixed values, use a staged rollout through representative secondaries, validation, burn-in, and primary-aware completion. However:

> **Secondary-First Is a Safety Pattern, Not a Universal Rule**

Do not create an unsupported mixed-state topology merely to follow a generic rolling-change pattern.

## 21. Sharded Clusters

A sharded deployment can contain `mongos`, the config server replica set, and multiple shard replica sets. A server parameter may apply to `mongod`, `mongos`, particular roles, or particular features. Never assume a change on `mongos` changes shards or that a change on one shard is cluster-wide.

## 22. Temporary vs. Persistent Changes

Classify every runtime change as temporary or intended persistent baseline. Temporary examples include incident mitigation, diagnostic testing, controlled experiments, and short-term workarounds. Persistent changes require deliberate promotion.

## 23. Experimental → Persistent Lifecycle

```text
EXPERIMENTAL
     |
     v
Runtime Change
     |
     v
Validate
     |
     v
Burn-In
     |
  +--+--+
  |     |
FAIL   PASS
 |      |
 v      v
Revert Promote
        |
        v
Persistent Configuration
        |
        v
Source of Truth
        |
        v
Fleet Validation
```

> **Successful Experiment ≠ Persistent Baseline Until Explicitly Promoted**

## 24. Restart Reversion Failure

A common incident sequence is: incident → runtime mitigation → stable service → persistent configuration not updated → maintenance restart → old value returns → incident reappears.

Every runtime change must answer:

> **Should This Change Survive Restart?**

## 25. Persistent Configuration Updated Too Early

The reverse failure is possible when an experimental runtime change is immediately added to persistent configuration, then runtime is rolled back after the experiment fails but the persistent configuration is forgotten. The next restart reintroduces the bad value. Promotion to persistent state should therefore be deliberate.

## 26. Runtime Rollback

Capture the previous value before change. Roll back through the supported runtime interface when appropriate and verify it with `getParameter`. Persistent configuration and the infrastructure source of truth must also be reconciled.

> **Runtime Rollback ≠ Complete Rollback**

## 27. GitOps and Configuration Management

Production persistent state should flow through an approved source of truth.

```text
Git / Configuration Management
             |
             v
Deployment Mechanism
             |
             v
MongoDB Startup Configuration
             |
             v
Runtime
```

An emergency runtime change may temporarily create `Git = X` and `Runtime = Y`. After stabilization, explicitly revert the runtime change or promote the validated value into the source of truth.

## 28. Kubernetes

A runtime parameter belongs to the running MongoDB process, while pods are replaceable. Pod recreation can therefore restore startup configuration and remove an unpersisted runtime override.

> **Pod-Local Runtime Change ≠ Kubernetes-Persistent Configuration**

If persistence is intended, update the supported operator, Helm, configuration, or GitOps source of truth.

## 29. Immutable VM Replacement

The same principle applies to immutable infrastructure. A VM-local runtime override disappears when a replacement VM starts from its image and persistent configuration unless the intended value has been promoted into the infrastructure source of truth.

## 30. MongoDB Version Sensitivity

Before using any parameter, capture the exact MongoDB version, confirm the parameter exists for that release and process, determine runtime/startup mutability, validate the value, and understand behavior. Do not reuse old tuning without validating the target release.

## 31. Explicit Overrides and Product Defaults

A later MongoDB release can change a default while an old explicit override remains. The override can therefore preserve behavior chosen for an older release and prevent adoption of an improved product default.

> **Explicit Parameter ≠ Automatically Better Than Product Default**

> **Old Tuning ≠ Future Best Practice**

## 32. Parameter Ownership

Every explicit production override should record its parameter, current value, product default, reason, owner, date introduced, MongoDB version, change reference, expected benefit, known risk, rollback value, persistence requirement, review date, and last compatibility review.

## 34. Health Baseline

Capture timestamp, environment, host/pod, MongoDB version, process type, replica/shard role, parameter value, persistent value, MongoDB and replication health, application health, CPU, memory, disk, network, relevant latency, error rate, and rollback value.

## 35. Execute and Read Back

```text
READ -> UNDERSTAND -> RECORD -> CHANGE -> READ BACK
```

Conceptual example:

```javascript
db.adminCommand({ getParameter: 1, parameterName: 1 })
db.adminCommand({ setParameter: 1, parameterName: newValue })
db.adminCommand({ getParameter: 1, parameterName: 1 })
```

The parameter and value must be validated against the exact MongoDB release.

## 36. Command Success vs. Operational Success

A command can return success and the parameter can read back correctly while latency, replication, or application behavior deteriorates.

> **Command Success ≠ Operational Success**

Validate parameter state together with MongoDB metrics, logs, application behavior, and replication/sharding health.

## 37. Burn-In

Observe MongoDB health, replication lag, elections, CPU, memory, disk, network, query latency, error rate, application health, and logs. Burn-in should cover the workload affected by the change.

> **Burn-In Should Cover the Relevant Workload Cycle**

## 38. Parameter Drift

Drift can be member-to-member, source-of-truth versus runtime, persistent configuration versus runtime, or expected value versus product default. These represent different operational failures and should be classified separately.

## 39. Drift Detection

Compare an approved curated baseline with actual runtime state. When drift is detected, investigate according to parameter risk and policy.

> **Detecting Drift ≠ Permission to Automatically Correct Drift**

For high-risk settings, alert-and-review can be safer than immediate automated remediation.

## 40. Monitoring

Monitor important parameters for unexpected values or changes, member-to-member differences, runtime-versus-persistent differences, runtime-versus-Git differences, restart reversion, and version-incompatible overrides. Correlate parameter changes with MongoDB and application metrics, replication, elections, CPU, memory, storage, network, and logs.

## 41. Failure Scenario — Unsupported Parameter

An old runbook can reference a parameter valid on MongoDB version A that has been removed or changed in version B. Parameter compatibility therefore belongs in upgrade prechecks.

## 42. Failure Scenario — Valid but Dangerous Value

A syntactically accepted value can still cause CPU, memory, latency, or replication regression.

> **Accepted Value ≠ Safe Value**

## 43. Failure Scenario — Member Drift

A topology can remain apparently healthy while one member is tuned differently, until an election, maintenance operation, workload redistribution, or member replacement exposes the difference.

## 44. Failure Scenario — Failover Drift

If the primary has a runtime override and secondaries do not, an election can immediately change production behavior. Parameter consistency is therefore part of failover readiness.

## 45. Failure Scenario — Pod Recreation

A pod-local runtime override disappears after eviction/restart if the startup baseline does not contain the same value.

## 46. Failure Scenario — Configuration Reconciliation

Configuration management may intentionally restore the approved baseline after a manual change. The operational failure occurs when operators do not understand that reconciliation will happen.

## 47. Failure Scenario — Obsolete Override After Upgrade

An explicit override selected for an old product default can remain after an upgrade and defeat a better new default. Re-review all explicit overrides during upgrades.

## 49. Emergency Runtime Change Runbook

1. **IDENTIFY** — record incident, parameter, reason, target process, and expected outcome.
2. **READ** — capture the current value.
3. **VALIDATE** — confirm exact MongoDB version, parameter existence, correct process, runtime mutability, valid value, and topology implications.
4. **BASELINE** — capture MongoDB, replication, application, and infrastructure health.
5. **CHANGE** — apply the approved runtime value.
6. **VERIFY** — read the parameter back.
7. **OBSERVE** — check metrics, logs, topology, and application behavior.
8. **DECIDE** — classify the change as temporary or a candidate for persistent promotion.
9. **BURN IN** — observe through the relevant workload cycle.
10. **RECONCILE** — align runtime state, persistent configuration, Git/configuration management, replica/shard fleet, and operational documentation.
11. **CLOSE** — record final value, outcome, persistent state, rollback state, fleet state, and follow-up owner.

## 51. Production Change Safety Gate

### BEFORE

- [ ] Correct environment
- [ ] Exact MongoDB version captured
- [ ] Correct `mongod`/`mongos` target
- [ ] Parameter documented for this version
- [ ] Runtime/startup mutability understood
- [ ] Current runtime value captured
- [ ] Persistent value captured
- [ ] Product default understood
- [ ] Topology scope identified
- [ ] Mixed-state safety understood
- [ ] Temporary/persistent intent decided
- [ ] Health baseline captured
- [ ] Rollback defined

### CHANGE

- [ ] Correct target selected
- [ ] One controlled change where practical
- [ ] Command response checked
- [ ] New value read back
- [ ] Change timestamp/reference recorded

### VALIDATE

- [ ] MongoDB healthy
- [ ] Replication healthy
- [ ] Elections stable
- [ ] Application healthy
- [ ] Metrics stable/improved
- [ ] Logs reviewed
- [ ] Fleet consistency correct
- [ ] Persistent state aligned if required

### STOP

- [ ] MongoDB health deteriorates
- [ ] Replication lag increases unexpectedly
- [ ] Election instability appears
- [ ] Resource behavior degrades
- [ ] Application errors increase
- [ ] Behavior differs from expectation
- [ ] Unsupported mixed state discovered
- [ ] Rollback becomes uncertain

Never blindly execute the same `setParameter` operation across an entire MongoDB fleet.

## 53. Idempotency

If expected and actual values already match, automation should make no change. When they differ, the correct response can be alert, investigation, approval, and remediation rather than immediate automatic correction.

## 54. Parameter Baseline as Code

Conceptually:

```yaml
mongodb_server_parameters:
  parameterA:
    expected: valueA
    persistence: persistent
    owner: database-platform
    reason: approved-change-reference
```

This is an organizational inventory format, not MongoDB configuration syntax. It supports review, ownership, drift detection, automation, and upgrade analysis.

## 55. Upgrade Precheck

For every explicit override in the target MongoDB version, determine whether the parameter still exists, whether its default, mutability, scope, or behavior changed, and whether the override remains necessary.

## 56. Post-Upgrade / Post-Restart Validation

After MongoDB upgrade/restart, OS patching, VM replacement, pod recreation, restore, or DR activation, read critical parameters and compare them with the approved baseline.

> **MongoDB Started Successfully ≠ Runtime Baseline Restored**

## 57. Production Anti-Patterns

Avoid:

1. changing a parameter without reading its existing value;
2. assuming every parameter supports `setParameter`;
3. treating every `getParameter` result as writable;
4. confusing server parameters with cluster parameters;
5. using `setParameter` when MongoDB provides a dedicated command;
6. assuming runtime changes persist through restart;
7. assuming one member's change propagates to the replica set;
8. changing only the current primary;
9. ignoring failover behavior;
10. creating unsupported mixed-member states;
11. copying tuning from old blogs or MongoDB versions;
12. casually using undocumented/internal parameters;
13. assuming explicit overrides are always better than defaults;
14. changing multiple parameters simultaneously during diagnosis;
15. treating command success as operational success;
16. skipping burn-in;
17. failing to define rollback;
18. rolling back runtime but not persistent configuration;
19. prematurely promoting an experiment to persistent configuration;
20. leaving emergency runtime changes outside the source of truth;
21. assuming pod-local changes survive recreation;
22. assuming VM-local changes survive replacement;
23. granting applications parameter-modification authority;
24. blindly auto-remediating high-risk drift;
25. failing to reconcile members after incident changes;
26. failing to revalidate overrides during upgrades;
27. applying self-managed `setParameter` procedures to Atlas;
28. ignoring Stable API restrictions in administrative tooling;
29. treating the complete parameter inventory as a compliance baseline; and
30. assuming successful process startup restores the intended parameter state.


> **Treat every MongoDB server-parameter change as a controlled production change: verify the exact release and parameter semantics, inspect runtime and startup capabilities, capture existing runtime and persistent state, understand process and topology scope, define rollback and persistence intent, change incrementally, validate actual behavior, burn in through the relevant workload cycle, reconcile the source of truth and fleet state, and continuously detect drift against the approved production baseline.**
