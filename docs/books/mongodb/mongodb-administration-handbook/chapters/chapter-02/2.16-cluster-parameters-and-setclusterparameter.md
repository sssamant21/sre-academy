# 2.16 — Cluster Parameters and `setClusterParameter`

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where explicitly relevant  
**Platform Scope:** Primarily self-managed MongoDB; managed-service boundaries must be validated  
**Status:** Canonical

> **Cluster-Level Configuration Is a Production Change**

MongoDB configuration operates at multiple scopes. Server parameters managed with `setParameter` are associated with a MongoDB server process. Cluster parameters provide a distinct mechanism for configuration whose logical scope extends across a replica set or sharded cluster. MongoDB introduced cluster parameters and the `setClusterParameter` / `getClusterParameter` commands in MongoDB 6.0.

The operational objective is not merely knowing the command syntax. SRE/DBRE teams must understand version and FCV compatibility, topology, command-routing requirements, authorization, application impact, storage impact, rollback, observability, and configuration ownership before modifying cluster-level state.

## Learning Objectives

After completing this section, you should be able to:

- distinguish server parameters from cluster parameters;
- inspect cluster parameters with `getClusterParameter`;
- safely modify supported parameters with `setClusterParameter`;
- distinguish configuration scope from command execution target;
- evaluate `changeStreamOptions` retention implications;
- understand `defaultMaxTimeMS` and operation-level overrides;
- validate replica-set and sharded-cluster health before changes;
- manage upgrade and FCV interactions;
- define rollback and observability requirements;
- detect and prevent configuration drift; and
- implement idempotent desired-state automation.

## 1. Configuration Scope

```text
setParameter
     |
     v
Server / Process Configuration

setClusterParameter
       |
       v
Cluster-Level Configuration
```

These mechanisms are not interchangeable.

> **A Parameter Documented for `setParameter` Is Not Automatically Valid for `setClusterParameter`, and Vice Versa**

Always validate the exact parameter against documentation for the MongoDB release being operated.

## 2. Why Cluster Parameters Exist

Some configuration logically belongs to the deployment rather than to one `mongod` or `mongos` process.

```text
                MongoDB Deployment
                       |
              Cluster Parameter
                       |
          +------------+------------+
          |            |            |
       Member A     Member B     Member C
          |            |            |
          +----- Consistent State --+
```

Cluster parameters reduce the need to reproduce logical deployment-wide settings independently on individual processes and reduce one class of configuration drift.

## 3. Discover Before Change

Use the `admin` database and inspect current state before making a production modification.

```javascript
use admin

db.adminCommand({
  getClusterParameter: "*"
})
```

Inspect a specific parameter with:

```javascript
db.adminCommand({
  getClusterParameter: "changeStreamOptions"
})
```

or:

```javascript
db.adminCommand({
  getClusterParameter: "defaultMaxTimeMS"
})
```

Operational sequence:

```text
DISCOVER -> READ -> RECORD -> VALIDATE -> CHANGE -> READ BACK
```

> **Never Modify a Production Cluster Parameter Without Recording Its Existing Value**

## 4. `setClusterParameter`

The general command structure is:

```javascript
db.adminCommand({
  setClusterParameter: {
    parameterName: parameterValue
  }
})
```

After modification, retrieve the parameter again and validate the effective state.

> **Command Success ≠ Operational Success**

Validation must cover configuration, cluster health, application behavior, and observability.

## 5. Configuration Scope vs. Command Target

Cluster-level scope does not mean that every cluster-parameter command can be issued against an arbitrary process. Individual parameters can impose topology-specific command-routing requirements.

```text
Configuration Scope
        !=
Command Execution Target
```

For example, `changeStreamOptions` is set against the replica-set primary or through `mongos` for a sharded cluster. Always validate parameter-specific routing requirements for the exact MongoDB release.

## 6. `changeStreamOptions`

`changeStreamOptions` controls cluster-level options associated with change streams, including retention of pre- and post-images.

Example:

```javascript
db.adminCommand({
  setClusterParameter: {
    changeStreamOptions: {
      preAndPostImages: {
        expireAfterSeconds: 86400
      }
    }
  }
})
```

This example configures a 24-hour retention period.

MongoDB also supports:

```javascript
expireAfterSeconds: "off"
```

which is the default behavior. With this setting, pre/post-image retention is associated with the corresponding change-stream events' availability in the oplog.

## 7. Capacity Impact of Change-Stream Images

Pre- and post-images consume storage.

```text
Change Rate
    x
Average Image Size
    x
Retention Duration
    |
    v
Potential Storage Footprint
```

Before increasing retention, evaluate change rate, image/document sizes, storage growth, available capacity, disk latency, oplog behavior, and change-stream consumer requirements. After modification, storage growth must be part of post-change monitoring.

> **Retention Policy Is Also a Capacity Policy**

## 8. `defaultMaxTimeMS`

MongoDB 8.0 introduced `defaultMaxTimeMS`, which can establish a default time limit for supported individual read operations.

Example:

```javascript
db.adminCommand({
  setClusterParameter: {
    defaultMaxTimeMS: {
      readOperations: 5000
    }
  }
})
```

The default value is:

```text
defaultMaxTimeMS.readOperations = 0
```

A value of `0` means this cluster parameter does not impose a default read-operation timeout.

Applicable operations include supported forms of `find`, `aggregate`, `count`, `distinct`, and `dbHash`; validate release-specific exclusions such as aggregation pipelines using `$merge` or `$out`.

## 9. Operation-Level Overrides

An explicitly supplied operation-level `maxTimeMS` can take precedence over the cluster default for that operation.

```javascript
db.orders.find({ status: "OPEN" }).maxTimeMS(15000)
```

Conceptually:

```text
           defaultMaxTimeMS
                  |
                  v
        Operation Specifies
             maxTimeMS?
            /         \
          No           Yes
          |             |
          v             v
      Cluster       Explicit
      Default       Operation Value
```

A cluster timeout can protect resources, but it does not fix inefficient query architecture. Investigate query plans, indexes, workload legitimacy, analytical behavior, contention, and resource saturation before treating timeout configuration as performance remediation.

## 10. Production Impact Analysis

Before modification evaluate:

```text
Application
  +-- Query behavior
  +-- Error handling
  +-- Retries
  +-- Change-stream consumers
  +-- Background processing

Cluster
  +-- Replication
  +-- Storage
  +-- CPU
  +-- Memory
  +-- Disk latency

Operations
  +-- Upgrade compatibility
  +-- FCV compatibility
  +-- Monitoring
  +-- Rollback
```

The exact impact model depends on the parameter.

## 11. Replica-Set Preflight

Before changing a production replica-set cluster parameter, verify:

```text
[ ] Primary stable
[ ] Expected members present
[ ] Secondaries healthy
[ ] Replication lag acceptable
[ ] No unexpected elections
[ ] No risky recovery/resync operation
[ ] MongoDB version verified
[ ] FCV verified
[ ] Current parameter value recorded
```

Use appropriate health inspection such as `rs.status()` as part of the evidence set.

Do not introduce a routine configuration change into an already degraded replica set unless the modification is specifically part of an approved recovery procedure.

## 12. Sharded-Cluster Preflight

A sharded deployment expands the potential blast radius.

```text
                  Applications
                       |
                     mongos
                       |
          +------------+------------+
          |            |            |
        Shard 1      Shard 2      Shard 3
          |            |            |
       Replica      Replica      Replica
         Set          Set          Set

               Config Server RS
```

Validate `mongos` connectivity, shard health, replica-set health, config-server health, replication lag, MongoDB versions, FCV, and current parameter state before change.

## 13. Managed-Service Boundary

This section primarily targets self-managed MongoDB. Do not assume that a self-managed `setClusterParameter` procedure can be transferred directly to MongoDB Atlas or another managed service. Use only configuration mechanisms supported by the target service and validate feature parity during migration planning.

> **Same Database Product ≠ Same Administrative Surface**

## 14. Authentication and Authorization

Cluster-parameter modification is privileged administrative activity. Production access should follow least privilege, strong authentication, controlled administrative identities, change authorization, and auditability.

Required privileges can depend on the parameter and MongoDB release. Verify the documented authorization requirements for the exact parameter before execution rather than assuming a permanent generic role requirement.

## 15. Audit Evidence

Operational evidence should answer:

```text
Who changed it?
What changed?
When?
From what value?
To what value?
Why?
Under which change?
Was validation successful?
```

Capture cluster, environment, MongoDB version, FCV, topology, parameter, previous value, proposed value, final value, timestamp, change reference, operator/automation identity, validation result, and rollback value.

## 16. Upgrade and FCV Safety

Cluster parameters are version-sensitive. A parameter may be unavailable in an older release, introduced in a particular version, change semantics, depend on FCV, or complicate downgrade planning.

Active `setClusterParameter` activity must not be intentionally overlapped with FCV transitions.

```text
Binary Upgrade
      |
      v
Cluster Validation
      |
      v
Operational Burn-In
      |
      v
Confirm Administrative Stability
      |
      v
Confirm No Conflicting Parameter Operation
      |
      v
FCV Transition
      |
      v
Post-FCV Validation
```

> **Do Not Schedule Cluster-Parameter Changes Concurrently With FCV Transitions**

## 17. Configuration Drift

Cluster parameters reduce some member-level drift but do not eliminate environment drift.

```text
Development = 0
Test        = 5000
Production  = 10000
```

Those differences can be intentional or uncontrolled. Operationally important cluster parameters should therefore have a documented desired state.

Example conceptual inventory:

```yaml
mongodb_cluster_parameters:
  defaultMaxTimeMS:
    readOperations: 5000

  changeStreamOptions:
    preAndPostImages:
      expireAfterSeconds: 86400
```

The configuration repository is the desired-state record; MongoDB is the source of actual runtime state.

## 18. Idempotent Automation

Automation should compare before writing.

```text
Read Desired State
       |
       v
Read Actual State
       |
       v
    Compare
    /    \
 Same    Different
  |          |
  v          v
 Exit    Validate Preconditions
             |
             v
         Produce Diff
             |
             v
       Approval / Policy Gate
             |
             v
      setClusterParameter
             |
             v
       Read Back State
             |
             v
          Validate
```

This provides idempotency, visible configuration differences, safer automation, and improved auditing.

Use a single authoritative configuration owner. Multiple independent automation systems managing the same parameter can create configuration oscillation.

## 19. Canary Limitations

Cluster-scoped settings may not support a traditional node-by-node canary rollout.

> **Do Not Assume Node-by-Node Canary Deployment Is Available for a Cluster Parameter**

Reduce risk through representative non-production testing, workload replay where practical, application-level canaries, maintenance-window selection, enhanced monitoring, and prevalidated rollback.

## 20. Production Change Procedure

1. Record cluster, environment, topology, MongoDB version, FCV, parameter, and change reference.
2. Validate cluster health.
3. Retrieve and record the existing parameter state.
4. Confirm version, FCV, topology, deployment, routing, authorization, and syntax support.
5. Test the exact proposed configuration outside production.
6. Assess application, availability, and capacity impact.
7. Record current, proposed, and rollback values.
8. Execute the documented parameter-specific change.
9. Read the parameter back immediately.
10. Validate replica-set or sharded-cluster health.
11. Validate representative application behavior.
12. Observe relevant technical and business signals.
13. Record final evidence and completion state.

## 21. Observability

Post-change monitoring must be parameter-specific.

Cluster health can include replica state, elections, replication lag, shard availability, and config-server health. Workload signals can include operation latency, failed operations, timeouts, throughput, connections, and slow operations. Resource signals can include CPU, memory, disk usage, growth, latency, and IOPS. Application signals can include API errors, retries, latency, background-job failures, and change-stream consumer health.

For `defaultMaxTimeMS`, focus on timeouts, query failures, retry rate, application errors, and query latency. For `changeStreamOptions`, focus on storage growth, disk pressure, change-stream health, and pre/post-image behavior.

> **Define Observability Before the Change, Not After the Incident**

## 22. Rollback

Every production change requires a known rollback value before execution.

Example:

```text
Previous: 0
Proposed: 5000
Rollback: 0
```

Rollback controls immediate risk; troubleshooting determines root cause. They are related but distinct activities.

```text
Unexpected Behavior
       |
       v
Immediate Service Risk?
      /        \
    Yes         No
     |           |
     v           v
 Roll Back    Investigate
     |           |
     v           v
 Validate      Observe
```

## 23. Failure Scenario — Unsupported Parameter

A command can fail because the parameter is unavailable in the MongoDB release, invalid for the deployment, incompatible with FCV, incorrectly routed, or supplied with an unsupported value. Validate the exact release and topology rather than reusing an old runbook blindly.

## 24. Failure Scenario — Application Timeout Regression

After introducing `defaultMaxTimeMS`, previously successful reads can fail. Investigate poor query plans, missing indexes, legitimate long-running workloads, analytical operations, resource saturation, and application defects before simply increasing the timeout.

## 25. Failure Scenario — Unexpected Storage Growth

After changing `changeStreamOptions`, disk consumption can rise. Investigate change rate, average image size, retention duration, available capacity, disk growth, oplog behavior, and consumer requirements. Roll back if storage risk becomes unacceptable.

## 26. Failure Scenario — FCV Conflict

If an FCV transition encounters problems while cluster-parameter administrative activity is occurring, identify and safely resolve the conflicting operation, verify cluster health, and retry FCV only when the deployment is stable.

## 27. Failure Scenario — Automation Oscillation

Repeated configuration writes can indicate multiple configuration owners, serialization differences, incorrect comparison logic, environment overrides, manual changes, or non-idempotent automation. Establish one authoritative desired-state source and use semantic comparison before writes.

```text
[ ] MongoDB version verified
[ ] FCV verified
[ ] Parameter supported
[ ] Deployment support verified
[ ] Correct command target identified
[ ] Authorization verified
[ ] Cluster health verified
[ ] Current value captured

[ ] Application impact assessed

[ ] Rollback value recorded

```

## 30. Key Takeaways

Cluster parameters provide a configuration mechanism for settings whose logical scope extends beyond an individual MongoDB server process. Their broader scope increases their potential production blast radius.

Use this operating pattern:

```text
DISCOVER
   |
BASELINE
   |
VERIFY COMPATIBILITY
   |
TEST
   |
PEER REVIEW
   |
CHANGE
   |
VERIFY
   |
OBSERVE
   |
RECORD
```

For SRE/DBRE-managed environments, important cluster parameters should be represented as desired state, changed through controlled and preferably idempotent automation, monitored after deployment, and backed by documented rollback.

The objective is not merely to make MongoDB accept a command. The objective is to make the change predictable, reproducible, observable, reversible, and safe for the production workload.
