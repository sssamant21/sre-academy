# 2.17 — Restart-Required vs. Runtime Changes

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

> **A MongoDB configuration change must be classified by activation mechanism, persistence behavior, topology scope, and availability impact before it is executed.**

MongoDB configuration changes do not all behave alike. Some settings can be changed dynamically on a running process, some are established at process startup, some support both mechanisms, and others use cluster-level or dedicated administrative commands.

For production SRE/DBRE operations, incorrectly classifying a change can result in unnecessary outages, restart reversion, member-to-member drift, failed maintenance, unavailable write concerns, application failover failures, or configuration that appears correct until the next restart, pod replacement, or infrastructure reconciliation.

The operational questions are: how is the setting changed, when does it become effective, what scope does it affect, does it require restart, will it survive restart, what happens during failover, and how is it rolled back?

## Learning Objectives

After completing this section, you should be able to classify MongoDB configuration changes by activation mechanism; distinguish runtime from persistent startup state; identify runtime- and startup-settable server parameters; understand restart-reversion risk; safely promote temporary runtime changes into persistent configuration; plan restart-required changes for standalone, replica-set, and sharded deployments; preserve voting majority, electability, and write-concern capability; recognize PSA maintenance risks; execute controlled primary transitions; validate replication catch-up between rolling-maintenance steps; manage configuration in Kubernetes and immutable infrastructure; design complete rollback procedures; integrate changes with GitOps and automation; and define production restart gates and post-change validation.

## 1. MongoDB Configuration Change Model

```text
MongoDB Change
     |
     +--> Runtime Change
     +--> Startup Configuration
     +--> Dedicated / Cluster Mechanism
```

These are operational classifications, not mutually exclusive product categories. A server parameter can be both runtime-settable and startup-settable.

> **Configuration Mechanisms Are Not Interchangeable**

## 2. Four-State Configuration Model

```text
Product Default
      |
      v
Desired State
      |
      v
Persistent Startup State
      |
      v
Effective Runtime State
```

Under steady-state operations, desired, persistent, and runtime values should agree. Temporary differences may exist during controlled changes but must not become permanent undocumented drift.

## 3. Runtime Changes

For a supported runtime-settable server parameter:

```javascript
db.adminCommand({
  setParameter: 1,
  parameterName: newValue
})
```

A runtime modification can immediately affect performance, memory, CPU, query behavior, diagnostics, security, replication, and application behavior.

> **No Restart Required ≠ No Production Risk**

Runtime changes still require change control, baseline capture, monitoring, and rollback.

## 4. Runtime Changes Are Not Automatically Persistent

A runtime `setParameter` change does not automatically survive server restart. If persistent startup configuration remains at value A while runtime is changed to B, a later restart can restore A.

> **Runtime Change ≠ Persistent Change**

When a validated runtime value should survive restart, deliberately promote it through the supported persistent startup mechanism.

## 5. Restart-Reversion Risk

```text
Production incident
       |
       v
Runtime parameter changed
       |
       v
Service stabilizes
       |
       v
Persistent configuration forgotten
       |
       v
Later restart / replacement
       |
       v
Original value returns
       |
       v
Incident returns
```

Every runtime change must answer: **Should this value survive restart?**

## 6. Startup Configuration

Startup-oriented settings are read when the MongoDB process starts. Changing a startup configuration value does not automatically modify an already-running process. When MongoDB provides no supported runtime mechanism for the setting, the affected process must restart for the startup configuration change to become effective.

Do not assume every setting appearing in a configuration file always requires restart; some server parameters support both startup and runtime mechanisms.

## 7. Runtime and Startup Mutability

MongoDB 8.x parameter metadata can help determine mutability:

```javascript
db.adminCommand({
  getParameter: {
    showDetails: true
  },
  parameterName: 1
})
```

Relevant metadata can include `value`, `settableAtRuntime`, and `settableAtStartup`.

Use runtime metadata together with exact-version documentation.

> **Readable ≠ Runtime-Settable**

## 8. Runtime Experiment to Persistent Promotion

A parameter supporting both mechanisms can sometimes be validated at runtime before persistence:

```text
Desired/Persistent/Runtime = A
        |
Runtime experiment = B
        |
Validate + burn-in
      /     \
   FAIL     PASS
    |         |
Rollback   Promote B to desired + persistent state
```

Valid final states are full rollback to A or full promotion to B. Avoid indefinite undocumented middle states.

## 9. Persistent-First Risk

If persistent configuration is changed to B, runtime testing fails, and runtime is reverted to A while persistent state remains B, the next restart can reintroduce B.

> **Runtime Rollback Is Incomplete Until Persistent and Desired State Are Reconciled**

## 10. Source of Truth

Production configuration should have an authoritative owner such as Git, Ansible, Terraform, Helm, a Kubernetes Operator, configuration management, or an immutable infrastructure pipeline.

```text
Source of Truth
      |
Deployment Mechanism
      |
Persistent Configuration
      |
Running MongoDB
```

Emergency runtime changes must eventually become either an approved promotion or rollback.

## 11. Restart Is an Availability Event

A restart-required configuration change affects both configuration and process availability.

> **Command Complexity ≠ Operational Complexity**

The blast radius depends on whether the target is a standalone, replica-set secondary or primary, shard member, config-server member, or `mongos`.

## 12. Standalone MongoDB

A standalone server has no replica-set peer capable of continuing service during restart. Restart-required maintenance normally requires application downtime or another architecture-level continuity mechanism.

If routine restart-required maintenance cannot tolerate database downtime, a standalone topology is inconsistent with that availability requirement.

## 13. Replica-Set Maintenance Safety

Maintenance safety depends on:

```text
Voting majority
      +
Electability
      +
Replication state
      +
Write-concern capability
      +
Remaining workload capacity
```

> **Member Count Alone Does Not Prove Maintenance Safety**

Before planned maintenance verify that voting majority remains available, an electable secondary exists where required, the candidate is sufficiently caught up, required write concern remains satisfiable, replication lag is acceptable, and remaining members have adequate capacity.

## 14. Voting Majority vs. Write Capability

Voting majority and write-concern capability are related but distinct.

> **Voting Majority Available ≠ Required Write Concern Guaranteed**

Production maintenance must validate both.

## 15. PSA Maintenance Warning

In a Primary-Secondary-Arbiter topology, the arbiter participates in voting but does not store application data. Maintenance of the only secondary can therefore produce materially different election and data-bearing acknowledgement characteristics.

> **Voting Majority Does Not Necessarily Mean the Deployment Can Satisfy the Application's Required Write Concern**

Before PSA maintenance evaluate write concern, `wtimeout`, secondary availability, replication state, application behavior, and maintenance duration.

## 16. Rolling Replica-Set Maintenance

When MongoDB and the specific configuration change support rolling application, a common pattern is secondary A, validate and catch up, secondary B, validate and catch up, controlled primary transition, then maintain the former primary.

> **Secondary-First Is a Safety Pattern, Not Permission to Create an Unsupported Mixed Configuration**

## 17. Member Advancement Gate

Never advance to the next member merely because the restarted process is running.

```text
Process running
      |
MongoDB reachable
      |
Correct replica state
      |
Replication resumed
      |
Lag acceptable
      |
Logs + metrics acceptable
      |
Application healthy
      |
Proceed
```

> **Process Running ≠ Member Ready for the Next Maintenance Step**

## 18. Planned Primary Maintenance

Use controlled primary transition where appropriate:

```text
Secondaries healthy
       |
Controlled stepdown
       |
Election
       |
Verify new PRIMARY
       |
Verify replication
       |
Verify application recovery
       |
Maintain former primary
```

MongoDB provides `rs.stepDown()` for controlled primary stepdown. Command success alone does not prove successful application failover.

## 19. Degraded-Mode Capacity

High availability does not automatically imply adequate capacity while a member is unavailable. Evaluate CPU, memory, disk IOPS and latency, network, connections, replication, read workload, backup activity, and batch processing.

> **HA ≠ Guaranteed Degraded-Mode Capacity**

## 20. Sharded Cluster Maintenance

A sharded cluster contains `mongos`, shard replica sets, and a config server replica set. A restart-required change may apply to one or more component classes. Use component-specific rolling procedures rather than a generic "restart MongoDB cluster" procedure.

## 21. `mongos` Maintenance

`mongos` routers do not form a replica set and do not use replica-set election semantics. Before restarting a router verify remaining router capacity, application connection behavior, load-balancer and DNS behavior where relevant, connection pools, and timeouts.

## 22. Config Server Maintenance

Config servers hold critical sharded-cluster metadata and operate as a replica set.

> **Never Intentionally Restart All Config-Server Members Simultaneously During Routine Maintenance**

Use a supported member-by-member procedure and verify replica state, voting majority, primary availability, replication, logs, cluster metadata operations, and router connectivity before progressing.

## 23. Kubernetes

A runtime change modifies the process inside the current pod, but pod replacement can recreate MongoDB from persistent desired configuration.

> **Pod Runtime State ≠ Infrastructure Desired State**

Persistent changes should flow through the supported operator, Helm, manifest, configuration, or GitOps mechanism.

## 24. Immutable Infrastructure

The same principle applies to replaceable VMs. A runtime override existing only on one VM is temporary even if the VM remains alive for months; replacement restores declared startup configuration.

## 25. Configuration Validation Before Restart

A malformed or incompatible configuration can prevent MongoDB from starting. Validate the proposed configuration through peer review, exact-version compatibility review, syntax/configuration review, paths and permissions, configuration-management validation, and representative non-production validation where practical.

Do not assume there is one universal offline MongoDB command capable of validating every possible configuration change.

## 26. Known-Good Configuration

Prefer version-controlled desired state as the rollback source, then known-good deployment artifacts. Local backups can provide emergency convenience but should not replace configuration management.

## 27. systemd Operations

For Linux installations managed through systemd, `systemctl restart mongod`, `systemctl status mongod`, and `journalctl -u mongod` can provide process-level control and evidence.

But:

```text
systemd healthy
       !=
MongoDB healthy
       !=
Application healthy
```

All layers require validation.

## 28. Post-Restart Validation

Validate process startup, MongoDB connectivity, correct replica/shard role, replication health and lag, logs, metrics, and application behavior. For replica sets, `rs.status()` can form part of the evidence.

Do not proceed to the next member until the restarted member reaches an acceptable operational state.

## 29. Startup Duration and Panic Restarts

Do not encode fixed restart-duration assumptions. Startup time depends on storage state, recovery work, hardware, dataset, workload, deployment state, and operating system.

> **Slow Startup ≠ Failed Startup**

Observe logs, process state, and storage/recovery behavior rather than repeatedly restarting a slow-starting process.

## 30. Application Availability

Applications must correctly tolerate connection interruption, primary transition, server discovery, pool refresh, retry and timeout behavior, DNS, and load balancing where relevant.

> **Database HA ≠ Application HA**

Application validation is mandatory during rolling maintenance.

## 31. Maintenance Window Selection

Prefer periods with lower workload, no major batch processing, no conflicting backup activity, no deployment conflict, no FCV transition, no unrelated infrastructure change, and adequate engineering coverage. Avoid combining unrelated high-risk changes in one maintenance window.

## 32. Complete Rollback Model

Rollback may need to reconcile runtime, persistent configuration, desired/source-of-truth configuration, and deployment automation.

> **Rollback Is Complete Only When All Relevant Configuration Layers Are Reconciled**

## 33. Failure Scenarios

Key failure patterns include MongoDB not starting after configuration change, runtime changes disappearing after restart or replacement, member configuration drift, primary maintenance causing an unexpected outage, automation reconciliation restoring old configuration, and rolling maintenance causing capacity pressure.

When MongoDB does not start, capture evidence before repeated restart attempts. Check MongoDB logs, systemd journal, configuration, paths and permissions, storage, network/ports, and version compatibility, then recover or roll back.

## 34. Observability During Maintenance

Monitor MongoDB member state, elections, replication lag, sharding health, logs and connections; infrastructure CPU, memory, disk, IOPS, latency and network; application latency, errors, retries and connection failures; and change-state information such as configuration value, member progression, restart timestamps, validation results, and rollback state.

Compare these signals to the pre-change baseline after every rolling-maintenance step.

## 35. Automation Guardrails

```text
Discover topology
       |
Discover version + FCV
       |
Read current configuration
       |
Determine activation mechanism
       |
Determine restart requirement
       |
Validate majority/electability/write concern
       |
Validate capacity
       |
Generate diff
       |
Approval gate
       |
Change one safe target
       |
Restart if required
       |
Validate + replication catch-up
       |
Burn-in
       |
Continue
```

Automation should fail closed when topology safety cannot be established.

> **Unknown State ≠ Permission to Continue**

## 36. Production Configuration / Restart Change Gate

```text
[ ] Environment identified
[ ] Exact MongoDB version verified
[ ] FCV verified
[ ] Configuration mechanism identified
[ ] Runtime/startup mutability verified
[ ] Restart requirement verified
[ ] Current runtime value captured
[ ] Persistent value captured
[ ] Desired state defined
[ ] Configuration reviewed/validated
[ ] Rollback prepared
[ ] Replica/shard health verified
[ ] Voting majority preserved
[ ] Electable secondary available where required
[ ] Required write concern remains satisfiable
[ ] Replication lag acceptable
[ ] Remaining workload capacity verified
[ ] Application failover behavior reviewed
[ ] Monitoring ready
[ ] Maintenance conflicts checked
[ ] Change approval obtained
```

For standalone MongoDB, topology-specific items should be explicitly marked N/A rather than silently skipped.

## 37. Production Restart Workflow

```text
Change Request
      |
Classify Change
      |
Verify Version / FCV
      |
Determine Runtime vs Startup
      |
Capture Desired / Persistent / Runtime State
      |
Validate Configuration + Prepare Rollback
      |
Validate Cluster Health
      |
Validate Majority / Electability / Write Concern
      |
Validate Capacity
      |
Select Safe Target
      |
Apply Configuration
      |
Restart if Required
      |
Validate Process + MongoDB
      |
Wait for Replication Catch-Up
      |
Validate Application
      |
Burn-In
      |
Proceed to Next Target
      |
Final Fleet Validation
      |
Reconcile Desired / Persistent / Runtime State
      |
Close Change
```

## 38. Production Standard

Every MongoDB configuration change should identify the setting, exact MongoDB version and FCV, owning configuration mechanism, runtime/startup mutability, restart requirement, topology scope, persistence requirement, source of truth, rolling compatibility, voting-majority and electability requirements, write-concern capability, degraded-mode capacity, failover behavior, pod/VM replacement behavior, rollback, success metrics, and final configuration-alignment verification.

If these questions cannot be answered, the change is not production-ready.

## 39. Key Takeaways

Remember:

> **Runtime Change ≠ Persistent Change**

> **Configuration File Updated ≠ Running Process Updated**

> **Readable ≠ Runtime-Settable**

> **No Restart Required ≠ No Production Risk**

> **Restart Is an Availability Event**

> **Member Count Alone ≠ Maintenance Safety**

> **Voting Majority ≠ Guaranteed Write-Concern Capability**

> **Stepdown Success ≠ Successful Application Failover**

> **Process Running ≠ Member Ready for the Next Maintenance Step**

> **Database HA ≠ Application HA**

> **Pod/VM Runtime State ≠ Infrastructure Desired State**

> **Rollback Is Incomplete Until Relevant Configuration Layers Agree**

The desired steady state is:

```text
Approved Desired State
          =
Persistent Configuration
          =
Effective Runtime State
```

except during explicitly controlled change windows.

Maintaining that alignment makes MongoDB configuration predictable across restarts, elections, failovers, rolling maintenance, Kubernetes pod recreation, VM replacement, patching, upgrades, automation reconciliation, and disaster recovery.
