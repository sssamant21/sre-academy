# 2.18 — Configuration Drift Detection

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

> **Configuration drift exists whenever the configuration MongoDB is actually running differs from the approved state the organization expects it to run.**

Configuration drift is a hidden production risk. A deployment may remain apparently healthy while members, runtime parameters, startup options, binaries, operating systems, storage, Kubernetes definitions, or infrastructure gradually diverge. The difference may become visible only during an election, failover, restart, upgrade, pod recreation, VM replacement, incident recovery, or disaster recovery.

> **Configuration Drift Is a State-Reconciliation Problem**

## Learning Objectives

After completing this section, you should be able to define MongoDB configuration drift; distinguish desired, persistent, startup, runtime, and fleet state; detect process-level and cluster-level drift; inspect parsed startup configuration; track configuration provenance; detect replica-set and sharding topology drift; detect binary, build, and FCV differences; incorporate OS, storage, Kubernetes, and IaC state; distinguish intentional from unauthorized drift; manage temporary exceptions safely; protect secrets during collection; design severity and alerting policies; prevent unsafe automatic remediation; detect control-plane oscillation; validate configuration after restart or replacement; and build production drift-detection runbooks and gates.

## 1. Configuration Compliance Model

```text
Approved Desired State
        |
Configuration Source
        |
Persistent Configuration
        |
Parsed Startup Configuration
        |
Effective Runtime State
        |
Fleet Comparison
```

Each layer answers a different question: what should run, where intent is defined, what will be available at startup, what the current process actually started with, what governs it now, and whether equivalent fleet members comply with policy.

## 2. Compliance Is Policy-Based

The ideal relationship is desired = persistent = expected startup = effective runtime = expected fleet state. Legitimate temporary differences can exist during rolling upgrades, canaries, runtime experiments, incident mitigation, or staged rollout. Therefore actual state should belong to the approved state set, including only explicitly controlled exceptions.

## 3. Drift Is Multi-Layered

Drift can exist across binary/build identity, persistent startup configuration, parsed startup configuration, runtime parameters, cluster parameters, replica-set configuration, sharding configuration, security, OS, storage, Kubernetes, infrastructure, and automation.

> **Healthy Cluster ≠ Consistent Cluster**

## 4. Configuration Provenance

For important settings capture the setting, value, source, explicit/implicit status, scope, MongoDB version, and collection time. A value inherited from a MongoDB default is operationally different from the same value explicitly configured in `mongod.conf`, because a future product-default change can affect only the implicit case.

> **Same Effective Value ≠ Same Configuration Intent**

## 5. Runtime Drift

Runtime drift occurs when desired and persistent state remain A while effective runtime becomes B, commonly through an emergency `setParameter` change. A restart can then restore A. Every temporary runtime change should eventually be promoted or rolled back.

## 6. Persistent Drift

Persistent drift occurs when desired state is A but persistent and runtime state are B. Common causes include manual `mongod.conf` edits, untracked automation, stale configuration artifacts, and failed deployments. Later reconciliation may restore A long after the original change.

## 7. Fleet Drift

A deployment can have members A and B compliant while member C differs. The inconsistency may become important during election, failover, restart, traffic redistribution, or maintenance.

> **Configuration Consistency Is Part of Failover Readiness**

## 8. Inspect Parsed Startup Configuration

For self-managed MongoDB, configuration-file inspection alone is incomplete. `db.adminCommand({ getCmdLineOpts: 1 })` can provide evidence about options used to start the current `mongod` or `mongos`, including parsed startup configuration.

Distinguish declared configuration, persistent definition, parsed startup configuration, and runtime state.

> **`mongod.conf` Alone Is Not Sufficient Evidence of Effective Startup Configuration**

Use `getCmdLineOpts` as operational evidence, not as the desired-state source of truth.

## 9. Configuration File Drift

For self-managed deployments, checksums such as `sha256sum /etc/mongod.conf` can detect byte changes but cannot explain what changed, whether it is meaningful, effective, or approved.

> **Checksum Monitoring Alone Is Not Configuration Drift Detection**

A stronger inventory stores checksum, normalized configuration, provenance, Git revision, deployment artifact/version, host identity, and collection timestamp.

## 10. File State vs. Startup State vs. Runtime State

Treat these separately: file state describes persistent configuration; startup state describes what the process actually started with; runtime state describes mutable effective state. All three may differ.

## 11. External Configuration Sources

Supported external configuration sources can cause identical local configuration files to produce different startup values. Record safe source metadata without unnecessarily persisting secret values.

> **Identical Configuration Files Do Not Necessarily Guarantee Identical Effective Configuration**

## 12. Runtime Parameter Inventory

For MongoDB 8.x, `getParameter` with detailed parameter metadata can support drift inventory. Discover, filter, redact, normalize, and compare rather than blindly storing every available value. Parameter availability and metadata can vary with MongoDB version and configuration.

> **Collect What Is Operationally Useful, Not Everything Merely Because It Is Available**

## 13. Version-Aware Parameter Baselines

Expected parameter state should be derived from MongoDB version, deployment type, and approved parameter policy rather than one universal baseline.

## 14. Cluster Parameter Drift

Server parameters and cluster parameters have different scopes. Maintain separate namespaces such as `serverParameter.*`, `clusterParameter.*`, `startupOption.*`, `replicaSetConfig.*`, `os.*`, and `storage.*`.

## 15. Replica-Set Configuration Drift

Use supported inspection such as `rs.conf()` and compare policy-relevant member identity, hosts, votes, priority, hidden status, arbiter status, tags, and delayed-member configuration. Unexpected differences can alter election behavior, read routing, write availability, failover, and maintenance safety.

## 16. Compare Replica Configuration Semantically

Do not require raw BSON equality. Normalize operational metadata and determine whether actual replica-set configuration conforms to approved topology policy.

## 17. Sharded Cluster Drift

Track routers, config server replica set, shard replica sets, shard membership, zones, relevant sharding configuration, and cluster parameters using topology-aware comparison rather than flattening all processes into one configuration document.

## 18. Binary and Build Drift

Structured inventory through `buildInfo` can provide version/build evidence such as `version`, `versionArray`, and `gitVersion`. Track exact build identity where packaging or compliance policy requires it; otherwise use an approved version policy.

## 19. Binary Version and FCV Are Different

Always track binary version and Feature Compatibility Version separately. During an approved upgrade, new binaries with the previous FCV may be intentional during burn-in.

> **Never Automatically Change FCV Merely to Resolve a Drift Alert**

## 20. Intentional vs. Unauthorized Drift

Intentional drift includes rolling upgrades, canaries, runtime experiments, incident mitigation, and staged rollout. Unintentional drift includes manual changes, incomplete deployment, failed automation, stale templates, unexpected node replacement, or unauthorized modification. A maintenance window must not suppress unrelated drift.

## 21. Drift Exception Model

Every intentional exception should include owner, reason, exact scope, baseline state, approved temporary state, start time, expiration, rollback, and change/incident reference. If B is approved temporarily, observing C must still alert.

## 22. Exceptions Must Expire

Temporary exceptions require explicit expiration and deliberate renewal. Expired exceptions should produce actionable findings rather than becoming permanent suppressions.

## 23. Normalize Before Comparing

Collect, parse, normalize, canonicalize, add provenance, then compare. Remove irrelevant ordering, formatting, serialization, and non-functional metadata while preserving meaningful intent.

> **Text Difference ≠ Configuration Difference**

## 24. Preserve Explicit vs. Default State

Normalization should preserve effective value, explicit/implicit state, and source where operationally relevant. An absent setting using a product default and an explicitly configured value equal to today's default may diverge after upgrade.

## 25. OS Drift

Relevant SRE/DBRE environmental controls can include kernel version, THP, NUMA, sysctl, ulimits, filesystem, mount options, disk layout, time synchronization, and systemd configuration. These are environmental controls surrounding MongoDB, not MongoDB server parameters.

## 26. Storage Drift

Track policy-relevant disk type, filesystem, volume size, provisioned IOPS, throughput, mount options, and storage class. Storage asymmetry can cause asymmetric latency, checkpoint behavior, replication lag, recovery time, and capacity.

## 27. Kubernetes Drift

A Kubernetes desired-state chain can be Git -> Helm/Operator/Manifest -> Kubernetes API -> Pod specification -> MongoDB process. Drift can include manual `kubectl` edits, runtime parameters, stale Helm releases, different images, resource settings, PVC/storage class, or operator overrides.

> **Detect Before Blindly Remediating**

## 28. Container Image Drift

Track image repository, tag, digest, MongoDB binary version, and approved image identity. Immutable image identifiers improve reproducibility; mutable tags can produce different image contents from an unchanged manifest.

## 29. Infrastructure-as-Code Drift

Infrastructure can diverge through manual instance, disk, network, IAM, security, or Kubernetes resource changes. IaC tooling can identify differences, but a detected difference is not permission for immediate destructive reconciliation.

## 30. Managed-Service Ownership Boundary

Self-managed teams may control MongoDB configuration files, command-line startup options, systemd, OS, filesystem, packages, kernel, and storage. Managed-service drift policy must monitor only configuration and infrastructure surfaces exposed and supported by the service.

> **Drift Policy Must Respect the Deployment's Ownership Boundary**

## 31. Security Drift

Unexpected changes to authentication, authorization, TLS, certificate references, network exposure, `bindIp`, audit configuration, key-file references, firewall/security controls, and privileged roles deserve elevated priority based on actual risk.

## 32. Secret-Safe Drift Detection

Do not unnecessarily collect passwords, private keys, tokens, secret contents, or sensitive connection strings. Prefer safe metadata such as identifiers, certificate fingerprints, expiration, key version, and references.

> **Drift Detection Must Not Become a Secret-Exfiltration System**

## 33. Drift Severity

Severity should consider security, availability, durability, failover, performance, scope, and persistence. Critical examples may include authentication unexpectedly disabled or dangerous topology/network exposure changes; high examples may include unexpected binary/storage or reliability-sensitive drift. Severity is organizational policy, not MongoDB-defined behavior.

## 34. Detection Frequency

Choose cadence from risk, change frequency, and detection capability. Add event-driven checks after deployments, restarts, failovers, upgrades, node replacements, pod recreation, incident mitigation, and configuration-management runs.

## 35. Restart and Replacement Verification

Capture expected state, perform restart/replacement, recollect startup and runtime state, compare, and validate. This reveals state that existed only in process memory or on the replaced host.

> **Replacement Is a Configuration-Reproducibility Test**

## 36. Drift Detection Pipeline

```text
Approved Baseline
      |
Collect
      |
Normalize
      |
Redact
      |
Add Provenance
      |
Compare
      |
Classify
   /       \
Expected  Unexpected
   |          |
Record     Investigate
              |
       Rollback / Promote
              |
          Reconcile
              |
           Validate
```

## 37. Recommended Collector Architecture

A production collector can combine `buildInfo`, `getCmdLineOpts`, `getParameter`, `getClusterParameter`, replica/sharding configuration, and OS/storage/IaC evidence, then normalize, redact, add provenance, compare, and classify.

## 38. Drift Evidence Record

Capture safe metadata such as timestamp, environment, cluster, process/member, namespace, setting, expected and observed values/sources, explicit/implicit state, MongoDB version, FCV, severity, approved exception, expiration, change ticket, owner, and remediation status. Redact sensitive values.

## 39. Alert Design

Alerts should identify cluster/member, namespace, setting, expected state, observed state, severity, and exception status. Avoid vague messages such as "MongoDB configuration changed."

## 40. Aggregate Fleet Alerts

Aggregate equivalent findings at fleet or replica-set level while preserving member-level evidence. This prevents alert storms without losing diagnostic detail.

## 41. Unauthorized Manual Changes

Correlate configuration comparison with audit evidence, deployment history, and change-management records to identify both what changed and how it changed. Common bypass paths include SSH edits, `setParameter`, `kubectl edit`, cloud-console modifications, and systemd overrides.

## 42. Auto-Remediation

Automatic remediation should require a known authoritative desired state, known drift classification, low-risk remediation, no conflicting active incident, and post-change validation. Otherwise route through a controlled change process.

> **Drift Detected ≠ Safe to Auto-Remediate**

## 43. Fail-Closed Automation

If automation cannot establish expected state, actual state, topology, version, FCV, change ownership, or exception status, it should not modify production.

> **Unknown State ≠ Permission to Modify Production**

## 44. Failure Scenario — Automation Oscillation

If an SRE changes A to B while a drift controller continuously restores B to A, repeated reconciliation can cause restarts, instability, alert storms, operational confusion, and incident prolongation. Detect repeated transitions and escalate instead of allowing competing control planes to fight indefinitely.

> **Repeated Drift Can Indicate Control-Plane Conflict**

## 45. Incident Response

Emergency changes can legitimately create temporary drift. Record the drift, restore service, then deliberately promote or roll back and reconcile. Incident closure should include verification that emergency configuration changes have been reconciled.

## 46. Node Replacement

A replacement node behaving differently may expose undocumented state on existing nodes rather than a fault in the new node. Compare desired, persistent, startup, runtime, OS, storage, and infrastructure state before remediation.

## 47. Disaster Recovery

Validate MongoDB version/build, FCV, startup configuration, runtime parameters, cluster parameters, replica/shard topology, security, OS, storage, network, and automation against the approved recovery baseline.

> **Data Restore ≠ Configuration Restore**

## 48. Production Drift Dashboard

A useful dashboard should show compliant clusters/members, critical/high/medium findings, approved and expired exceptions, and drift categories such as runtime, startup, persistent, version/build, OS/storage, and security. The objective is rapid risk identification, not merely a compliance percentage.

## 49. Example Internal Detection Objectives

Organizations may define internal objectives such as critical unauthorized drift detection within 15 minutes, high-risk drift within one hour, and expired exception detection within one hour. These are example SRE objectives, not MongoDB product requirements.

## 50. Production Drift Runbook

1. Identify environment, cluster, replica set/shard, member/router, host/pod, and infrastructure scope.
2. Capture relevant and safe actual state.
3. Retrieve authoritative desired state.
4. Capture parsed startup state where applicable.
5. Normalize and redact while preserving provenance.
6. Generate a semantic comparison.
7. Classify expected, unexpected, security-sensitive, availability-sensitive, performance-sensitive, or unknown drift.
8. Correlate with change tickets, deployments, incidents, maintenance windows, audit evidence, and exceptions.
9. Decide whether to temporarily accept, promote, rollback, remediate, or escalate.
10. Validate MongoDB, topology, application, infrastructure, and compliance state.
11. Reconcile desired, persistent, startup, and runtime state.
12. Record evidence and remove expired exceptions.

## 51. Production Drift Gate

```text
[ ] Binary/version matches approved policy
[ ] Build identity complies where required
[ ] FCV matches approved upgrade stage
[ ] Configuration source identified
[ ] Persistent configuration matches policy
[ ] Parsed startup configuration matches policy
[ ] Runtime parameters match policy
[ ] Cluster parameters match policy
[ ] Replica-set topology matches approved state
[ ] Sharding configuration matches approved state
[ ] Security configuration matches policy
[ ] OS/storage baseline matches policy
[ ] Infrastructure matches desired state
[ ] Kubernetes/image state matches desired state
[ ] Configuration provenance recorded
[ ] No unexplained manual changes
[ ] Exceptions have exact scope
[ ] Exceptions define approved temporary state
[ ] Exceptions have owners
[ ] Exceptions have expiration
[ ] No expired suppressions remain
```

## 52. SRE/DBRE Operating Model

```text
Define -> Version -> Review -> Deploy -> Collect -> Normalize -> Compare
       -> Detect Drift -> Classify -> Remediate/Temporarily Accept
       -> Validate -> Reconcile
```

This turns configuration from static documentation into an actively verified production control.

## 53. Key Takeaways

Configuration drift extends beyond `mongod.conf` to binary/build identity, persistent configuration, parsed startup configuration, runtime parameters, cluster parameters, replica-set and sharding topology, security, OS, storage, Kubernetes, infrastructure, and automation.

Remember:

> **Healthy Cluster ≠ Consistent Cluster**

> **Configuration Drift Is a State-Reconciliation Problem**

> **`mongod.conf` Alone ≠ Complete Startup-State Evidence**

> **Text Difference ≠ Configuration Difference**

> **Checksum Monitoring Alone ≠ Drift Detection**

> **Same Effective Value ≠ Same Configuration Intent**

> **Configuration Consistency Is Part of Failover Readiness**

> **Intentional Drift Must Have Exact Scope, Owner, Expected State, and Expiration**

> **Security Drift Deserves Elevated Priority**

> **Drift Detection Must Not Become a Secret-Exfiltration System**

> **Drift Detected ≠ Safe to Auto-Remediate**

> **Unknown State ≠ Permission to Modify Production**

> **Repeated Drift Can Indicate Control-Plane Conflict**

> **Replacement Is a Configuration-Reproducibility Test**

> **Incident Closure Must Include Configuration Reconciliation**

> **Data Restore ≠ Configuration Restore**

The desired steady state is approved desired state = persistent state = expected startup state = effective runtime state = expected fleet state, except for explicitly approved, scoped, and time-bounded exceptions.

Continuous drift detection makes MongoDB behavior more predictable during elections, failovers, restarts, patching, upgrades, Kubernetes reconciliation, node replacement, incident recovery, and disaster recovery.
