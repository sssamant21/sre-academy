# 2.19 — MongoDB Version Management and Patch Management

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

> **MongoDB version management is a reliability discipline, not merely a package-management task.**

A production estate must know which binaries are running, which release track and series are approved, which stable patches are expected, how version transitions will be executed, and how database and application health will be validated afterward.

## 1. Version-Management Model

```text
Vendor Release
      |
Release Classification
      |
Technical Assessment
      |
Qualification
      |
Approval
      |
Controlled Deployment
      |
Validation
      |
Fleet Compliance
```

A successful production change requires an approved binary, healthy topology, healthy application, expected performance, and a known recovery state.

## 2. Classify the Version Change

Treat same-series patches, minor-series transitions, major-series upgrades, and emergency/security remediation as distinct change classes. The exact supported classification and path must be validated against documentation for the source and target versions.

> **Same Operational Pattern ≠ Same Vendor Upgrade Procedure**

MongoDB versions generally use `X.Y.Z`; `X.Y` identifies a release series and `Z` a patch within that series. Do not treat every MongoDB 8.x transition as a same-series patch.

> **Same Leading Major Number ≠ Same Patch Series**

## 3. Release Track and Desired State

Release track is an architecture decision. Define release track, release series, and approved stable patch explicitly rather than declaring an ambiguous `8.x` target.

```yaml
mongodb:
  production:
    release_track: major
    release_series: "8.0"
    approved_patch: "<approved-patch>"
```

Within the selected supported release series, patch currency is part of production hygiene. The newest release series is not automatically the correct production track.

Release candidates belong in controlled evaluation environments rather than normal production baselines.

## 4. Version Inventory and Provenance

Use process-level evidence such as:

```javascript
db.adminCommand({ buildInfo: 1 })
```

or interactive `db.version()` checks. Package inventory is useful but does not prove which binary is currently serving workload.

> **Installed Version ≠ Running Version**

Inventory every replica-set member, config-server member, shard member, and relevant `mongos` router. Capture environment, cluster, replica set/shard, member, role, host/pod, binary version, release track/series, build identity where relevant, package/image identity, FCV, OS/image identity, desired-state revision, and collection time.

Production version state should be declared in Git, Helm, an Operator specification, Ansible, Terraform, an image pipeline, or another authoritative configuration-management source.

> **Production Version Must Be Declared, Not Discovered Accidentally**

Useful compliance states include `COMPLIANT`, `APPROVED_TRANSITION`, `PATCH_BEHIND`, `EOL`, `UNAPPROVED_OLD`, `UNAPPROVED_NEW`, `RC_BUILD`, and `UNKNOWN`.

> **Unknown Version State ≠ Compliant State**

## 5. Release Assessment and Compatibility

Before approving a release, review release notes, bug and security fixes, known issues, behavior changes, compatibility, performance implications, operational changes, driver/tool requirements, and upgrade/downgrade restrictions.

Compatibility review should include MongoDB Server, drivers, `mongosh`, Database Tools, backup tooling, monitoring, automation, Kubernetes Operator, OS, and container image.

> **Database Compatibility Includes the Operational Ecosystem**

Representative testing should exercise applicable CRUD, transactions, indexes, aggregation, change streams, replication, sharding, backup/restore, authentication, TLS, monitoring, failover, and application connection pools. `mongod` merely starting is not sufficient validation.

## 6. Patch Rings

Use controlled blast-radius expansion such as engineering/lab → development → test → production-like staging → limited production canary → production fleet. The exact number of rings depends on organizational scale and risk.

## 7. Resolve the Exact Supported Path

Automation and runbooks must determine current version, target version, transition class, required intermediate releases, and the exact supported vendor procedure before execution.

> **The Supported Upgrade Path Must Be Determined from the Exact Source and Target Versions**

Do not infer arbitrary version skipping.

## 8. Binary Version and FCV

Always track binary version and Feature Compatibility Version independently.

> **Binary Version ≠ FCV**

A deployment may intentionally run newer binaries while retaining an earlier FCV during an approved upgrade stage. Binary rollout completion therefore does not necessarily mean the upgrade lifecycle is complete. Do not let patch automation modify FCV merely because binary versions changed.

## 9. Package and Repository Governance

Production systems should use controlled repositories, signing/trust configuration, package identity, exact versions, and controlled deployment mechanisms. Generic OS maintenance must not unexpectedly change MongoDB packages.

Possible safeguards include version locks, package pinning, repository restrictions, controlled automation, and immutable images.

> **OS Patching Must Not Accidentally Become a MongoDB Upgrade**

## 10. Security Patch Management

Security fixes may require accelerated handling: confirm exposure, assess severity, identify remediation, perform accelerated representative testing, deploy to the smallest safe production scope, observe, expand, validate, and retain evidence.

> **Urgent ≠ Uncontrolled**

Emergency maintenance should compress unnecessary delay, not eliminate engineering controls.

## 11. Pre-Maintenance Baseline

Capture MongoDB topology, member state, replication lag, connections, latency, errors, and cache/storage metrics; infrastructure CPU, memory, disk utilization/latency, IOPS, network, and filesystem capacity; and application request rate, errors, latency, timeouts, connection failures, and critical-workflow success.

Without a baseline, post-change comparison becomes subjective.

## 12. Production Preflight

Before touching the first production member confirm release track/current/target versions, transition classification, supported path, stable target, EOL state, release notes, known issues, security impact, driver/tool compatibility, required members running, FCV, backup/recovery posture, topology health, replication lag, voting majority, electability, required write concern, degraded-mode capacity, monitoring, application failover behavior, recovery strategy, downgrade eligibility, maintenance conflicts, and approval.

## 13. Replica-Set Maintenance

Patch one safe failure domain at a time. For a conventional replica set, an appropriate secondary is normally the first candidate during a supported rolling procedure. Validate health, replication, majority, write-concern capability, and capacity before maintenance.

After change/restart, verify correct version, correct member state, replication, catch-up, logs, metrics, application health, and an appropriate burn-in period before advancing.

> **Maintenance Speed Must Not Consume the Redundancy Protecting the Maintenance**

For primary maintenance, verify a healthy electable secondary, perform controlled stepdown, verify election and new PRIMARY, verify replication and application recovery, then maintain the former primary.

> **Stepdown Command Success ≠ Successful Application Failover**

> **Process Running ≠ Member Ready for the Next Maintenance Step**

## 14. PSA and Degraded-Mode Safety

Primary-Secondary-Arbiter deployments need additional care because an arbiter votes but stores no data.

> **Voting Majority ≠ Guaranteed Write-Concern Capability**

Evaluate required write concern, `wtimeout`, secondary availability, replication state, application behavior, and maintenance duration.

Also verify remaining CPU, memory, disk latency/IOPS, network, connections, reads, replication, backups, and batch workload capacity.

> **High Availability ≠ Adequate Degraded-Mode Capacity**

## 15. Sharded-Cluster Version Changes

Treat the Config Server Replica Set, shard replica sets, and `mongos` fleet as distinct operational domains. Select the exact topology-specific MongoDB procedure for the source and target releases.

For the documented MongoDB 7.0 → 8.0 sharded-cluster upgrade, the high-level component order is CSRS → shards → `mongos`. Do not generalize this sequence to every future patch or transition without checking the applicable release documentation.

> **Topology-Specific Sequencing Must Come from the Exact Source/Target Release Procedure**

Config-server maintenance is high-risk infrastructure work. Do not intentionally make multiple CSRS members unavailable simultaneously during routine rolling maintenance. Maintain each shard replica set with the same health, safe-member, validation, catch-up, and burn-in discipline. Treat `mongos` as a router fleet and validate remaining router capacity, load balancing, connection pools, service discovery, and retry behavior.

## 16. Kubernetes and Immutable Infrastructure

In Kubernetes, version identity belongs in durable desired state such as Helm values, Operator specifications, manifests, or GitOps—not manual package replacement inside a running pod. Prefer approved image → desired-state update → controlled pod replacement → MongoDB validation. Use immutable image digests where practical.

For immutable VMs, build and test an approved image, deploy one safe replacement, join/validate it, then remove the old member.

> **Version Deployment Must Converge Both Binary State and Configuration State**

## 17. Managed-Service Boundary

Managed MongoDB services may control binary maintenance. SRE/DBRE responsibility then shifts toward provider maintenance policy, scheduled maintenance, release awareness, application compatibility, change coordination, observability, post-maintenance validation, and customer-controlled configuration. Do not apply self-managed package-manager or host procedures to provider-owned infrastructure.

## 18. Mixed-Version and Incomplete Maintenance

Repeat fleet inventory after maintenance. Mixed versions can be expected during a supported rolling transition, but persistent mixed state must have a reason, compatibility status, owner, expected duration, recovery plan, and expiration.

> **Mixed Version ≠ Automatically Broken, but Mixed Version Must Be Explainable**

Unexplained mixed-version state is drift and should integrate with Section 2.18's exception model.

## 19. Post-Maintenance Validation

Validate four layers: process (correct running binary/startup state), MongoDB (topology/replication/lag/elections/errors), infrastructure (CPU/memory/disk/network/filesystem), and application (connectivity/errors/latency/timeouts/critical workflows).

> **Database Health ≠ Application Health**

Compare post-change results with the pre-maintenance baseline and look for regressions, not only outright failures.

## 20. Failure Handling

If MongoDB does not start, replication does not recover, application behavior regresses, or performance becomes unacceptable, stop rollout expansion. Capture evidence before repeated restart attempts. Investigate logs, binary/package state, configuration compatibility, permissions, storage, network, dependencies, replication state, resource pressure, TLS/authentication, and application metrics as applicable.

Restore health before touching another member.

## 21. Rollback vs. Binary Downgrade

Operational rollback can mean stopping rollout, keeping untouched members unchanged, removing a canary from service, restoring configuration or traffic, replacing failed infrastructure, escalating, or using an approved recovery path.

> **Rollback ≠ Binary Downgrade**

> **Do Not Treat Binary Downgrade as the Default Patch Rollback Mechanism**

Never assume the existence of an older package means downgrade is supported. Downgrade eligibility depends on the exact source and target versions, edition, FCV state, features/data state, and documented MongoDB procedure. MongoDB 8.x downgrade behavior is release-sensitive.

Record FCV before, during, and after the transition, whether backward-incompatible features/data were introduced, downgrade eligibility, and any support requirement.

## 22. Version Drift and Compliance

Automated inventory should compare observed binary state with approved version policy and classify findings. After maintenance require final fleet inventory, configuration drift scan, topology validation, application validation, and reconciliation of temporary exceptions.

A useful dashboard shows compliant clusters/members, approved transitions, patch-behind systems, EOL versions, RC builds, unknown versions, and overdue critical/routine patches.

Organizations may define internal remediation objectives by severity; these are organizational SRE/security objectives, not MongoDB product requirements.

## 23. Patch Evidence

Retain change ID, release track, old/target versions, transition classification, release assessment, known-issues and compatibility reviews, test evidence, baseline, timestamps, changed components, validation results, exceptions, recovery events, final inventory, and approvals.

## 24. Automation Architecture

A production orchestrator should discover topology, inventory versions/FCV, read desired policy, classify the transition, resolve the supported path, select the exact procedure, validate prerequisites/topology/capacity, select one safe target, patch or replace it, validate process/member state, wait for catch-up, validate the application, burn in, and only then continue.

For primary maintenance include controlled stepdown, election validation, and application recovery before maintaining the former primary.

Automation should be idempotent and recognize states such as `ALREADY_COMPLIANT`, `READY`, `IN_PROGRESS`, `VALIDATING`, `FAILED`, `APPROVED_TRANSITION`, and `UNKNOWN`.

Stop when topology, version, release track, FCV, supported path, majority, write concern, electability, replication lag, capacity, application health, recovery strategy, or state is unsafe or unknown.

> **Unknown State ≠ Permission to Continue**

## 25. Production Version / Patch Gate

```text
[ ] Release track/current/target series and patches identified
[ ] Transition classified
[ ] Exact supported path verified
[ ] Target stable / not RC
[ ] EOL and patch currency evaluated
[ ] Release notes / known issues / security reviewed
[ ] Drivers and tools validated
[ ] Required members running
[ ] FCV recorded
[ ] Topology-specific procedure selected
[ ] Package/image source trusted
[ ] Representative testing passed
[ ] Backup/recovery posture verified
[ ] Topology, majority, write concern and electability verified
[ ] Degraded-mode capacity verified
[ ] Application failover understood
[ ] Baseline and monitoring active
[ ] Rollback strategy documented
[ ] Binary downgrade eligibility explicitly verified
[ ] Edition-specific restrictions reviewed
[ ] Maintenance conflicts checked
[ ] Change approved
```

## 26. Post-Maintenance Completion Gate

```text
[ ] All intended components changed
[ ] Running versions verified
[ ] No unintended RC/EOL/wrong-series state
[ ] FCV matches approved lifecycle stage
[ ] Replica/shard topology healthy
[ ] Replication and lag acceptable
[ ] Elections stable
[ ] Logs and infrastructure metrics normal
[ ] Application metrics/workflows normal
[ ] Configuration and version drift scans passed
[ ] No unintended package/config changes
[ ] Temporary exceptions reconciled
[ ] Final fleet inventory recorded
[ ] Change evidence retained
```

> **Maintenance Is Complete Only When the Fleet Returns to a Known and Approved State**

## 27. Key Takeaways

- MongoDB version management is a reliability discipline.
- Release track is an architecture decision.
- Same leading major number does not mean same patch series.
- Same operational pattern does not mean the same vendor upgrade procedure.
- Installed version is not necessarily running version.
- Binary version and FCV are separate lifecycle dimensions.
- OS patching must not accidentally become a MongoDB upgrade.
- Compatibility includes the operational ecosystem.
- Urgent does not mean uncontrolled.
- Maintenance must preserve redundancy, write-concern capability, electability, and degraded-mode capacity.
- Database health does not prove application health.
- Mixed versions must be explainable and time-bounded.
- Rollback and binary downgrade are different concepts.
- Binary downgrade eligibility must be verified for the exact version, edition, and FCV state.
- Unknown state is not permission to continue.

The desired lifecycle is approved release track → approved release series → approved stable patch → representative testing → controlled deployment → per-member validation → application validation → fleet compliance.
