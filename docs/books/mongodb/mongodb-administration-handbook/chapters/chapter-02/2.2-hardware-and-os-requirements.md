# 2.2 — Hardware and OS Requirements

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to translate MongoDB workload requirements into host-level resource requirements; validate release, CPU architecture/microarchitecture, OS, kernel, and runtime compatibility; plan CPU, memory, storage, and network capacity; account for peak and failure-state demand; understand WiredTiger, filesystem cache, working-set, swap, NUMA, THP, and container-memory relationships; evaluate the complete storage I/O path; understand virtualization/cloud/container boundaries; establish host monitoring and baseline testing; and determine whether a MongoDB host is ready for production installation.

## 1. Hardware and OS Requirements as Workload Requirements

There is no universal production MongoDB server size.

```text
Workload
   |
   +-- Data + Indexes
   +-- Reads / Writes
   +-- Query Complexity
   +-- Connections
   +-- Replication
   +-- Maintenance
   +-- Backup / Recovery
   +-- Growth
   |
   v
Host Requirements
   |
   +-- CPU
   +-- Memory
   +-- Storage
   +-- Network
   +-- Operating System
```

A machine satisfying minimum installation requirements is not necessarily capable of operating the workload safely in production.

> **Supported Hardware ≠ Adequately Sized Hardware**

## 2. MongoDB Platform Compatibility and Host Preflight

Validate the complete platform, not merely the MongoDB major release.

```text
MongoDB Host
    |
    +-- MongoDB Release / Edition
    +-- CPU Architecture / Microarchitecture
    +-- OS Distribution / Version
    +-- Kernel / Runtime Libraries
    +-- NUMA / THP
    +-- Memory / Swap
    +-- Filesystem / Directory fsync()
    +-- Storage Performance / I/O Path
    +-- OS Resource Limits
    +-- Network / Time Synchronization
    +-- Security / Monitoring
    |
    v
Production Host Ready
```

Record MongoDB release and edition, CPU architecture/microarchitecture compatibility, OS distribution/version, kernel, relevant runtime libraries, package/repository source, and operational-tooling compatibility.

> **Supported Release ≠ Supported Platform Combination**

> **Supported OS Distribution ≠ Automatically Supported Kernel State**

Check current MongoDB production/platform-support documentation before provisioning and after significant OS/kernel lifecycle changes.

## 3. CPU Architecture, Microarchitecture, and Capacity

MongoDB CPU validation includes both architecture and microarchitecture/required instructions.

> **64-bit CPU Architecture ≠ Automatically Compatible CPU**

Record the processor/platform and validate it against the intended MongoDB release. For applicable Enterprise encryption-at-rest workloads, consider CPU cryptographic acceleration such as AES-NI.

CPU demand can originate from queries, aggregation, sorting, BSON processing, writes, index maintenance, compression, encryption, replication, background activity, and operational tooling.

> **Average CPU ≠ Required CPU Capacity**

> **High CPU ≠ CPU Shortage**

> **More vCPU ≠ Automatic Query Optimization**

## 4. CPU Headroom and Failure-State Capacity

Production sizing must account for component failure. Remaining infrastructure may need to carry production traffic, replication, election/topology activity, recovery, monitoring, and maintenance simultaneously.

> **Normal-State Capacity ≠ Failure-State Capacity**

This applies to CPU, memory, connections, storage, network, and operational capacity.

## 5. Physical Memory and WiredTiger

Physical/available memory is shared among WiredTiger cache, filesystem cache, MongoDB process overhead, connections, query/aggregation activity, the operating system, and operational agents.

> **Installed RAM ≠ MongoDB Cache Size**

> **MongoDB Cache ≠ Total MongoDB Memory Consumption**

Memory planning must consider both database and operating-system caching.

## 6. Working Set and Memory Pressure

The working set is the frequently accessed portion of data and indexes. The entire dataset does not necessarily need to fit in RAM.

> **Dataset Size ≠ Required RAM**

Distinguish memory utilization from actual memory pressure. Pressure evidence may include sustained swapping, eviction pressure, increased physical reads, latency increases, OOM events, or host contention.

> **High Memory Usage ≠ Memory Pressure**

## 7. Swap and OOM Risk

MongoDB production hosts should avoid or minimize sustained swapping. Swap policy must balance storage-latency risk against OOM risk and be validated for the release, OS, memory architecture, and workload.

> **MongoDB Performs Best When Swapping Is Avoided or Kept to a Minimum**

> **Swap Configuration Must Balance Latency Risk Against OOM-Killer Risk**

Detailed implementation belongs in 2.10.

## 8. NUMA Architecture

Large multi-socket systems may use NUMA, where memory-access characteristics differ by locality. Inappropriate NUMA policy can contribute to unpredictable performance and memory behavior.

> **NUMA Hardware Requires Explicit MongoDB-Aware Configuration**

> **Do Not Deploy MongoDB on NUMA Hardware Without Validating the NUMA Policy**

Detailed Linux configuration belongs in 2.11.

## 9. Transparent Huge Pages

THP guidance is version-specific. For this handbook baseline, current validated guidance is:

```text
MongoDB 8.0 -> Enable THP
MongoDB 7.0 and Earlier -> Disable THP
```

Administrators must still verify guidance for the exact MongoDB release before implementation.

> **THP Guidance Is MongoDB-Version-Specific**

> **Historical MongoDB Tuning Advice ≠ Current MongoDB Requirement**

Detailed configuration belongs in 2.12.

## 10. Storage Capacity and Performance

Storage must be evaluated for capacity, latency, IOPS, throughput, durability, filesystem behavior, I/O path, and expansion. Demand includes data, indexes, journal/oplog activity, checkpoints, queries, writes, replication, index builds, initial sync, backups, maintenance, and recovery.

> **Enough Disk Space ≠ Enough Storage Performance**

## 11. Storage Latency, IOPS, and Throughput

Latency, IOPS, and throughput are distinct. Workload behavior also depends on concurrency, I/O size, and read/write mix.

> **IOPS Alone ≠ Storage Performance**

Avoid universal latency/IOPS/throughput thresholds without workload and platform context.

> **Storage Performance Should Be Baselined Against the Actual Workload**

## 12. Filesystem Requirements and XFS

For self-managed Linux data-bearing nodes using WiredTiger, XFS should generally be the preferred filesystem under current MongoDB guidance, while exact support must be validated for the selected release/platform.

> **Supported Filesystem ≠ Preferred Production Filesystem**

Validate support, durability semantics, performance, mount behavior, ownership/permissions, snapshot behavior, and expansion.

> **Filesystem Mountable ≠ Filesystem Suitable for MongoDB**

Detailed implementation belongs in 2.4.

## 13. Filesystem Semantics, Readahead, and I/O Path

MongoDB requires appropriate filesystem durability semantics, including required directory `fsync()` behavior. The complete storage path includes filesystem, durability semantics, Linux readahead, I/O scheduler, block device/volume, and storage platform.

> **Volume Performance ≠ Complete I/O-Path Configuration**

Exact readahead and scheduler configuration belongs in 2.4/2.10.

## 14. Storage Headroom and Expansion

Headroom is needed for growth, indexes, oplog requirements, maintenance, temporary activity, initial synchronization, recovery, and operational safety. Capacity management should trigger warning, review, expansion, and validation before exhaustion.

> **Filesystem Full Is a Failure Condition—not a Capacity Strategy**

Avoid universal free-space percentages in this planning section.

## 15. Local, Remote, Cloud, and RAID-Backed Storage

Evaluate storage by filesystem semantics, latency, IOPS, throughput, durability, failure behavior, expansion, and snapshot behavior rather than location alone.

> **Storage Location ≠ Storage Suitability**

Remote storage requires explicit validation. For directly managed RAID-backed environments, current MongoDB guidance favors RAID-10 for performance-sensitive database storage; do not mechanically apply this to cloud platforms that abstract physical RAID.

## 16. Network Capacity and Distributed-System Latency

MongoDB network demand includes application traffic, replication, heartbeats, sharding, monitoring, backup, migration, initial sync, and recovery.

> **Application Traffic ≠ Total MongoDB Network Traffic**

Plan bandwidth, latency, packet loss, reliability, and failure domains. Geographic separation can improve failure isolation while increasing latency.

> **Greater Geographic Distance ≠ Automatically Better Availability Architecture**

## 17. Virtual Machines and Cloud Instances

Validate processor model, shared/dedicated CPU, burst behavior, sustained compute, memory guarantees, storage bandwidth, volume IOPS/throughput, instance-level limits, network bandwidth, and virtualization contention.

> **Advertised Instance Size ≠ Guaranteed Sustained Performance**

Provider-specific recommendations belong in Book 4.

## 18. Resource Isolation and Overcommitment

MongoDB latency can become unpredictable when CPU, memory, storage, or network resources are heavily shared with other workloads.

> **Logical Resource Allocation ≠ Physical Resource Isolation**

Avoid uncontrolled noisy-neighbor contention for critical workloads where practical.

## 19. Containers and Kubernetes Resource Boundaries

Containerized MongoDB introduces a resource boundary between node capacity and resources visible to `mongod`.

> **Node Capacity ≠ Container Capacity**

> **Host RAM ≠ Memory Available to a Containerized `mongod`**

> **Pod Running ≠ MongoDB Properly Sized**

WiredTiger planning must respect resources actually available to the process. Detailed Kubernetes implementation belongs in Book 4.

## 20. OS Resource Limits and Service Management

MongoDB can fail despite available hardware if OS limits such as open files, processes/threads, virtual memory, service-manager limits, or cgroup limits are inadequate.

> **Hardware Capacity ≠ Usable Capacity When OS Limits Are Incorrect**

For the MongoDB 8.x baseline, validate the effective open-files limit before production deployment; MongoDB can warn when it is below 64,000. Detailed configuration belongs in 2.10.

Self-managed Linux deployments should use controlled service management for startup, shutdown, restart, boot behavior, process identity, logging, and failure handling. Detailed `systemd` implementation belongs in 2.9.

## 21. OS Security, Kernel, Runtime Libraries, and Lifecycle

Plan supported OS/kernel/runtime libraries, security patches, service identity, permissions, administrative access, firewalling, logging, and security monitoring.

> **Database Security ≠ Only Database Configuration**

> **Supported MongoDB + Unsupported OS ≠ Supported Production Platform**

> **Supported OS Distribution ≠ Automatically Supported Kernel State**

Check current MongoDB production notes before significant OS/kernel changes rather than freezing transient advisory ranges into standards.

## 22. Time Synchronization

Production hosts should use an approved NTP-compatible time-synchronization architecture. Reliable time supports logs, monitoring, incident correlation, certificates, and distributed diagnosis.

> **Reliable Time = Reliable Operational Evidence**

Detailed configuration belongs in 2.13.

## 23. Host Monitoring and Baseline Testing

Before go-live, monitor CPU utilization/saturation/throttling; memory, swap and OOM; storage capacity, latency, IOPS and throughput; network throughput/errors/drops; process/filesystem state; kernel events; and effective resource limits.

```text
MongoDB Metric
      +
OS Metric
      +
Infrastructure Metric
      +
Application Metric
      |
      v
Production Diagnosis
```

> **Database Metrics Without Host Metrics Provide an Incomplete Production View**

Baseline validation should combine infrastructure tests, representative workload tests, MongoDB metrics, and application metrics.

> **Benchmark Result ≠ Production Performance Guarantee**

Do not run uncontrolled synthetic load against an active production environment.

## 24. Hardware/OS Failure Scenarios and Anti-Patterns

Representative scenarios include: large free disk with saturated I/O (**Capacity ≠ Performance**); burstable compute exhausting credits (**Advertised vCPU ≠ Sustained Compute Guarantee**); host/container memory mismatch (**Host RAM ≠ Container RAM**); a healthy `mongod` with critically full filesystem (**Process Running ≠ Storage Healthy**); and adding hardware to a poor query access path (**Hardware Expansion ≠ Query Optimization**).

Avoid: hardware before workload analysis; minimum requirements as production sizing; release validation without exact platform/CPU validation; average-only capacity; treating high CPU as automatic CPU shortage; treating installed RAM as WiredTiger cache; direct dataset-to-RAM formulas; obsolete THP/NUMA guidance; storage sized only in GB/TB; unvalidated filesystems; network sized only for application traffic; cloud labels treated as sustained guarantees; ignored VM/container boundaries; ignored OS/kernel/lifecycle limits; and production without host monitoring/baseline validation.

## 25. DBA Readiness Checklist, Key Takeaways, and Applicability

### Checklist

- [ ] MongoDB release/edition, CPU architecture/microarchitecture, OS, kernel, runtime libraries, and repository source validated.
- [ ] CPU peak, operational, and failure-state demand considered.
- [ ] WiredTiger, filesystem cache, OS/agent memory, working set, swap/OOM, and container boundaries understood.
- [ ] NUMA identified and MongoDB-aware policy planned.
- [ ] THP configuration matched to MongoDB version.
- [ ] Storage capacity, latency, IOPS, throughput, filesystem, directory `fsync()`, readahead, scheduler, expansion, and monitoring validated.
- [ ] Application, replication, initial-sync, and recovery network requirements considered.
- [ ] OS resource limits, service management, security, time synchronization, patch/reboot process, and kernel advisories reviewed.
- [ ] Virtualization/container resource guarantees and failure-domain placement reviewed.
- [ ] Host monitoring and representative baseline validation completed.

### Key Takeaways

Hardware sizing begins with workload behavior. Minimum requirements are not production sizing recommendations. Validate the complete MongoDB/CPU/OS/kernel/runtime combination. CPU and memory sizing must include peak and failure-state headroom. NUMA and THP are version/platform-sensitive. Storage capacity and performance are independent; filesystem semantics and the entire I/O path matter. Network demand includes replication/recovery. Cloud and container resource labels do not guarantee physical capacity. OS limits and lifecycle state can constrain MongoDB despite available hardware. Production readiness requires host monitoring and evidence-based baseline validation.
