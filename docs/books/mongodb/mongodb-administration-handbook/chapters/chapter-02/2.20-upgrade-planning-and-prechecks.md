# 2.20 — Upgrade Planning and Prechecks

## Revised Final / Canonical Edition

**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

> **A MongoDB upgrade should become predictable before the first production binary is changed.**

Upgrade planning converts a risky production change into a controlled, observable, and recoverable operation. Production readiness requires MongoDB vendor requirements, topology safety, capacity safety, application compatibility, recovery readiness, and operational controls.

## 1. Upgrade Control Classes

Classify prechecks as MongoDB requirements, SRE/DBRE production safety gates, or organizational policy. Vendor-supported does not automatically mean production-ready.

## 2. Exact Source and Target State

Inventory the exact source binary/build, edition, FCV, topology, drivers, tools, OS/image, automation and configuration revision. Define the exact target release track, release series, patch, edition, expected rollout/final FCV, drivers, tools, package/image and configuration revision.

## 3. Transition Classification and Supported Path

Classify each transition as same-series patch, minor-series transition, or major-series upgrade. Resolve the exact supported source-to-target path from current MongoDB documentation rather than assuming any newer release is directly reachable.

> **Upgrade Path Must Be Proven, Not Assumed.**

If authoritative source guidance conflicts, classify the prerequisite as `CONFLICT`, stop automation, cross-check authoritative sources and escalate until resolved.

## 4. FCV Readiness

Binary version and Feature Compatibility Version are independent state. Verify FCV explicitly across the relevant deployment scope and detect unresolved FCV transition state. For the classic MongoDB 7.0 to 8.0 transition, validate the documented source requirement of MongoDB 7.0 binaries with FCV 7.0 before the binary upgrade, while always checking the exact current procedure.

> **FCV Readiness Is a Deployment-State Check.**

> **Expected FCV Value ≠ Proven FCV Transition Completion.**

## 5. Binary Rollout and FCV Advancement

Keep binary rollout and FCV advancement as separate lifecycle stages:

```text
Old Binary + Old FCV
        |
        v
Binary Upgrade
        |
        v
Topology Validation
        |
        v
Application Validation
        |
        v
Burn-In
        |
        v
FCV Advancement Gate
        |
        v
FCV Transition
```

Binary rollout complete does not mean the upgrade lifecycle is complete.

## 6. Release and Compatibility Assessment

Review the exact release notes, upgrade procedure, compatibility changes, known issues, security changes, deprecated/removed behavior, driver requirements, operational changes, FCV requirements and downgrade restrictions. Maintain an Upgrade Impact Register with change, component, usage, affected workload, severity, remediation, validation evidence and owner.

## 7. Driver, Tool and Configuration Compatibility

Validate application drivers, mongosh, Database Tools, backup agents, monitoring, automation, configuration management, Kubernetes operators, security tooling and custom scripts. Review `mongod.conf`, `mongos` configuration, startup options, `setParameter`, cluster parameters, TLS, authentication, auditing, storage, replication and sharding configuration against target-version support and approved desired state.

> **Operational Tooling Is Part of Database Compatibility.**

Review explicit and implicit defaults because the same value before an upgrade does not necessarily preserve the same configuration intent afterward.

## 8. Topology and Replica-Set Prechecks

Discover the deployment topology before choosing an upgrade procedure. For replica sets validate PRIMARY/SECONDARY health, replication progress, acceptable lag, member configuration and absence of unexplained abnormal states. `rs.status()` is useful evidence, but command success alone does not prove a healthy topology.

Where required by the applicable procedure, all required members must be running. Detect unexpected initial sync before proceeding.

## 9. Voting, Write Concern and Electability

Verify voting majority safety independently from application write-concern safety. Evaluate data-bearing members, arbiters, required write concern, `wtimeout`, maintenance target and expected availability. Before primary maintenance verify an appropriate secondary is electable by checking state, priority, votes, hidden/delay configuration, lag, network and capacity.

> **Voting Majority Available ≠ Required Write Concern Guaranteed.**

## 10. Replication, Oplog and Rejoin Risk

Do not carry existing replication debt into planned maintenance. Evaluate current/normal/peak lag, write rate, storage latency, network latency and sync stability. As an SRE/DBRE recovery-resilience gate, ensure the safe oplog window reasonably exceeds expected downtime, deployment, startup, validation and contingency time. Understand dataset size, initial-sync duration, network/disk throughput and source-member impact if a member requires rebuild.

## 11. Degraded-Mode Capacity

Validate CPU, memory, disk latency, IOPS, throughput, network, connections, reads, writes, replication, backup and batch workloads while one unit is unavailable.

> **High Availability ≠ Adequate Degraded-Mode Capacity.**

## 12. Application Readiness

Test primary election, transient disconnects, server selection, connection-pool recovery, retry/timeout behavior and critical workflows. Capture performance baselines for query/application latency, throughput, errors, CPU, disk latency, connections and replication lag. Include change-stream and transaction behavior where used.

> **Database HA ≠ Application HA.**

## 13. Sharded-Cluster Readiness

Inventory the config server replica set, all shard replica sets/members, `mongos` fleet, zones, critical distributed workloads and balancer state. Derive component sequencing from the exact source/target MongoDB procedure. For the documented MongoDB 7.0 to 8.0 transition, the high-level sequence is config server replica set, shards, then `mongos`.

Record balancer state before maintenance, expected maintenance state, owner, change point, restoration point and verification. Temporary maintenance state must not become permanent drift.

## 14. Backup, Restore and Recovery

Verify recent successful backups, retention, accessibility, encryption/key access and restore procedures. Where risk warrants, retain restore-test evidence, duration, integrity/application validation and RTO/RPO results.

> **Backup Exists ≠ Recovery Proven.**

Compare upgrade, rollback, resync and restore durations against the maintenance window, RTO and business tolerance.

## 15. Rollback and Binary Downgrade

Define operational rollback before maintenance: stop rollout, preserve untouched members, remove changed units from service, restore configuration/traffic, replace failed infrastructure, escalate or invoke another approved recovery path.

> **Rollback ≠ Binary Downgrade.**

Binary downgrade eligibility must be verified separately using exact source/target versions, edition, FCV, feature/data state, documented downgrade path and support requirements.

## 16. Monitoring and Change Controls

Ensure monitoring covers MongoDB availability, member state, elections, replication/lag, connections, latency/errors, CPU, memory, disk, network and application health. Scope alert suppression to the exact alert, component and maintenance interval.

> **Maintenance Window ≠ Monitoring Blind Spot.**

Avoid collisions with major application releases, migrations, infrastructure/network/security changes, heavy batch work or DR exercises. Identify GO, PAUSE, ABORT, ROLLBACK and ESCALATE authority before maintenance.

## 17. Canary, Burn-In and Abort Criteria

A MongoDB canary is valid only where the documented upgrade procedure permits the resulting mixed-version state and the topology remains safe. Burn-in should be an evidence gate based on topology, replication, lag, errors, resource behavior, application latency and critical workflows—not merely a timer.

Predefine abort conditions such as startup/rejoin failure, replication failure, unsafe lag, election instability, impaired write availability, critical application failure, severe performance regression, storage instability, unknown state or conflicting prerequisite evidence.

## 18. FCV Advancement Gate

Before advancing FCV require:

```text
[ ] All intended binaries upgraded
[ ] Running versions verified
[ ] Topology healthy
[ ] Replication healthy
[ ] Lag acceptable
[ ] Application healthy
[ ] Critical workflows validated
[ ] Burn-in completed
[ ] No unexpected initial sync
[ ] FCV transition state clean
[ ] Downgrade implications reviewed
[ ] Explicit approval obtained
```

## 19. Version-Specific Precheck Modules

Use common prechecks for source/target, topology, capacity, recovery and application readiness, then apply a version-specific module containing the supported source version, required FCV, compatibility changes, special prerequisites, component order and downgrade constraints.

## 20. Automated Result Model

Use `PASS`, `WARN`, `FAIL`, `UNKNOWN` and `CONFLICT`. Mandatory `UNKNOWN` and `CONFLICT` states fail closed.

Do not automatically start an upgrade when source/target/path/FCV is unknown, vendor guidance conflicts, FCV transition is unresolved, topology or replication is unhealthy, a required member is unavailable, unexpected initial sync exists, voting/write-concern/electability safety is unknown, capacity is inadequate, recovery readiness is unknown or application readiness is unknown.

> **Unknown State ≠ Permission to Upgrade Production.**

## 21. Production Upgrade Readiness Gate

Before GO verify exact source/target state, transition classification, supported path, stable approved target, internally consistent vendor guidance, deployment-wide FCV readiness, compatibility, topology health, initial-sync state, replication/lag, voting/write-concern/electability safety, exact sharded sequence, balancer lifecycle, degraded-mode capacity, storage, oplog/rejoin risk, backup/restore readiness, rollback/downgrade eligibility, monitoring, burn-in/abort criteria, decision authority, absence of conflicting changes and change approval.

Immediately before the first production change, rerun volatile checks. Approval from an earlier review does not override an unsafe runtime state.

> **Approval Does Not Override an Unsafe Runtime State.**

## 22. Upgrade Evidence Package

Retain the change ID, source/target versions, transition classification, release assessment, known issues, compatibility register, FCV evidence, topology inventory, capacity assessment, driver/tool/configuration assessment, backup/restore evidence, application tests, baseline metrics, supported procedure, rollback/downgrade assessment, monitoring references, burn-in/abort criteria, owners, approvals and final precheck result.

## Key Takeaways

- A MongoDB upgrade should become predictable before the first production binary is changed.
- Vendor-supported does not automatically mean production-ready.
- Upgrade path must be proven, not assumed.
- Conflicting source state is not permission to upgrade.
- Binary version and FCV are independent state.
- Binary rollout complete does not mean the lifecycle is complete.
- Upgrade compatibility must be proven at the workload level.
- Operational tooling is part of database compatibility.
- Voting majority does not guarantee required write-concern capability.
- Existing replication debt should not be carried into planned maintenance.
- High availability does not guarantee adequate degraded-mode capacity.
- Database HA does not guarantee application HA.
- Backup exists does not mean recovery is proven.
- Rollback is not synonymous with binary downgrade.
- Burn-in is an evidence gate, not merely a timer.
- `UNKNOWN` is not `PASS`.
- Approval does not override an unsafe runtime state.

The production invariant is:

```text
Known Source State
        +
Supported Upgrade Path
        +
Compatible Workload
        +
Healthy Topology
        +
Adequate Capacity
        +
Proven Recovery
        +
Operational Readiness
        =
GO
```

Anything materially unknown or contradictory results in `NO-GO` until resolved.
