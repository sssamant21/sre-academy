# 2.21 — Feature Compatibility Version Architecture

## Revised Final / Canonical Edition

**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

> **Treat the MongoDB binary upgrade as a software deployment and the FCV transition as a separate compatibility commitment.**

Feature Compatibility Version (FCV) is a major-version lifecycle control. It separates the MongoDB binaries currently executing from the compatibility state that governs use of features and persisted metadata that may be incompatible with an earlier release.

## 1. Binary Version and FCV Are Separate State

During a MongoDB 7.0 to 8.0 upgrade, an intentional intermediate state is:

```text
MongoDB binaries: 8.0
FCV:              7.0
```

This separation lets operators complete the supported binary rollout, validate production behavior, and only then advance FCV.

```text
Binary version != FCV
FCV != driver compatibility
FCV != application compatibility
FCV != rollback
```

## 2. FCV Upgrade State Machine

```text
7.0 binaries + FCV 7.0
        |
        v
Rolling binary upgrade
        |
        v
Mixed 7.0 / 8.0 binaries + FCV 7.0
        |
        v
8.0 binaries + FCV 7.0
        |
        v
Burn-in / production validation
        |
        v
Explicit FCV approval gate
        |
        v
setFeatureCompatibilityVersion("8.0")
        |
        v
Verify stable FCV
        |
        v
8.0 binaries + FCV 8.0
        |
        v
Post-FCV validation
```

Binary rollout completion and upgrade-lifecycle completion are therefore different events.

## 3. Query FCV Explicitly

Use the admin command rather than inferring FCV from the binary:

```javascript
db.adminCommand({
  getParameter: 1,
  featureCompatibilityVersion: 1
})
```

A deployment running MongoDB 8.0 binaries while reporting FCV 7.0 can be healthy when it is in an approved burn-in stage.

## 4. Change FCV Explicitly

For the MongoDB 7.0 to 8.0 transition:

```javascript
db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true
})
```

For the release baseline covered here, `confirm: true` is required for FCV changes. Run the command against the standalone `mongod`, the primary of a replica set, or a `mongos` for a sharded cluster as applicable.

> **FCV Change Is a Deployment Operation, Not a Local Host Setting.**

## 5. Replica-Set Architecture

After binary rollout, a normal validation state can be:

```text
PRIMARY      8.0
SECONDARY    8.0
SECONDARY    8.0
FCV          7.0
```

Before FCV advancement, verify topology, majority availability, replication health, lag, member state, initial-sync state, application health, and recovery readiness.

For the MongoDB 8.0 FCV transition, MongoDB performs additional replica-set configuration work associated with FCV advancement, including propagation of the relevant configuration to a majority. FCV must therefore not be treated as a cosmetic metadata write.

## 6. Initial Sync and Unhealthy Members

Use `rs.status()` and other operational evidence to identify abnormal states. Unexpected `STARTUP2`, `RECOVERING`, `ROLLBACK`, initial sync, unstable elections, or unsafe replication should block production FCV advancement until understood and remediated.

MongoDB documents interactions between FCV changes and initial synchronization. An SRE/DBRE production policy should fail closed when initial sync or topology health is uncertain.

## 7. Arbiter-Specific Behavior

Arbiters do not behave like data-bearing members for FCV metadata. They do not replicate `admin.system.version` in the same manner as data-bearing members. Monitoring must therefore be topology-aware:

```text
Replica-set member
       |
       +-- data-bearing -> evaluate FCV normally
       |
       +-- arbiter      -> apply arbiter-specific logic
```

Do not generate false compliance incidents by assuming every replica-set member exposes identical FCV state.

## 8. Sharded-Cluster Architecture

A sharded deployment includes the config server replica set, shard replica sets, and the `mongos` fleet. For the documented MongoDB 7.0 to 8.0 upgrade, complete the required binary sequence while retaining the previous FCV, validate the deployment, then issue the FCV command through `mongos`.

```javascript
db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true
})
```

Inventory every relevant router and server component. Ephemeral or autoscaled routers must not be omitted from compatibility validation.

## 9. Background and Sharding Operations

FCV changes can conflict with other cluster work. Inspect active operations with supported tooling such as `currentOp` where appropriate. Review initial synchronization, replica-set maintenance, sharding metadata work, chunk movement, and other potentially conflicting operations.

Do not automatically kill an operation merely because it blocks FCV. Identify the owner and impact, allow completion or remediate safely, revalidate, and retry only when appropriate.

## 10. Transitional FCV State

Do not model FCV internally as only a single static value. A transition can involve internal work before reaching the stable target state.

```text
STABLE_SOURCE
      |
TRANSITION_REQUESTED
      |
TRANSITIONING
      |
VERIFYING
      |
STABLE_TARGET
```

A successful client invocation alone is not sufficient evidence that the FCV lifecycle is complete. Always re-query FCV and verify the stable intended state.

## 11. CannotUpgrade and CannotDowngrade

Persisted features or metadata can prevent FCV transitions. Important failure classes include `CannotUpgrade` and `CannotDowngrade`.

```text
FCV request
    |
Compatibility validation
   / \
PASS FAIL
 |    |
 v    v
Transition   CannotUpgrade / CannotDowngrade
```

Capture the exact error, identify the incompatible feature/object/state, consult the exact release documentation, determine and validate remediation, remediate safely, and retry only when justified.

> **Compatibility Failure Requires Investigation, Not Blind Retry.**

## 12. Idempotency and Retry Safety

`setFeatureCompatibilityVersion` is idempotent, which supports recovery from uncertain client outcomes. The safe pattern is execute, observe the result, re-query FCV, determine actual server state, investigate any failure, retry when appropriate, and verify.

Idempotency does not mean every FCV error should be retried automatically or indefinitely.

## 13. Write-Concern Timeout

FCV operations have write-concern considerations. MongoDB documents a default `writeConcern.wtimeout` of 60 seconds for the relevant command baseline. A larger value may be appropriate in some deployments, but it must be justified by topology, network, replication, delayed members, maintenance conditions, and current vendor guidance.

Example only:

```javascript
db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true,
  writeConcern: { wtimeout: 120000 }
})
```

`120000` is not a universal production recommendation. A timeout also does not prove that the server performed no FCV work; always query resulting state.

## 14. Burn-In Architecture

MongoDB recommends allowing the upgraded deployment to run before enabling backward-incompatible new-version features.

```text
Binary upgrade complete
        |
Keep previous FCV
        |
Observe production
        |
Validate database and application
        |
Validate recovery posture
        |
FCV approval
        |
Advance FCV
```

The duration is organization-defined. Examples such as 24 hours, 48–72 hours, or several days are SRE policy choices, not MongoDB product requirements. Burn-in should be evidence-based rather than merely timer-based.

## 15. Production FCV Approval Gate

Before FCV advancement verify:

```text
[ ] Approved change exists
[ ] Current and target binaries documented
[ ] Current and target FCV documented
[ ] Required binary rollout complete
[ ] PRIMARY / SECONDARY topology healthy
[ ] Replication lag acceptable
[ ] No unexpected RECOVERING / ROLLBACK state
[ ] No initial sync in progress
[ ] mongos fleet validated where applicable
[ ] Config server and shard state healthy where applicable
[ ] Conflicting operations reviewed
[ ] Application smoke tests passed
[ ] Error and latency baselines acceptable
[ ] Driver compatibility confirmed
[ ] Recent backup successful
[ ] Recovery procedure available
[ ] Downgrade restrictions reviewed
[ ] Burn-in requirement satisfied
[ ] Explicit FCV approval obtained
```

These approval controls are SRE/DBRE production policy unless explicitly identified as MongoDB requirements.

## 16. Downgrade Safety

Lowering FCV, downgrading MongoDB binaries, restoring data, and rolling back an application are distinct operations.

```text
Lower FCV
   !=
Binary downgrade
   !=
Backup/PITR restore
   !=
Application rollback
```

FCV must not be presented as a general-purpose rollback switch. Downgrade eligibility depends on exact source and target releases, edition, FCV, persisted incompatible features/data, release-specific restrictions, and the documented procedure.

Never infer binary downgrade eligibility solely from current FCV.

## 17. FCV Is Not Backup or Recovery

FCV does not replace snapshots, logical backups, PITR, restore testing, recovery procedures, disaster recovery, or rollback planning. Changing FCV does not restore prior application data or guarantee reversal of all new-version effects.

> **Compatibility Control != Recovery Mechanism.**

## 18. FCV Is Not Application Compatibility

FCV 8.0 does not prove that an application is compatible with MongoDB 8.0. Validate drivers, authentication, connection behavior, deprecated/removed functionality, queries, aggregations, indexes, read/write concerns, transactions, change streams, frameworks, and application assumptions independently.

## 19. Monitoring Model

Inventory and dashboard state should include cluster, environment, observed binaries, desired binary, current FCV, desired FCV, upgrade phase, burn-in age, topology health, replication health, application validation, backup validation, and approval state.

Example:

```text
Cluster:             payments-prod
Observed binaries:   8.0.x
Current FCV:         7.0
Desired FCV:         8.0
Upgrade phase:       BURN_IN
Topology:            HEALTHY
Replication:         HEALTHY
Application:         PASS
Backup:              PASS
FCV approval:        PENDING
```

## 20. Alerting and Drift Detection

Do not alert solely because binary major version and FCV differ. That state can be expected during a supported upgrade.

```text
Binary/FCV mismatch
       |
Approved upgrade active?
     /   \
   YES    NO
    |      |
Expected  Investigate drift
    |
Burn-in exceeded?
  /   \
 NO   YES
 |     |
INFO  WARNING
```

Useful findings include mismatch outside an approved change, burn-in exceeding policy, transition failing to reach stable target, `CannotUpgrade`, `CannotDowngrade`, unexplained mixed binaries, repeated FCV failures, or unhealthy topology during FCV work.

> **Never Automatically Change FCV Merely to Resolve a Drift Alert.**

## 21. Automation Architecture

A mature orchestrator should discover topology, capture binary/FCV state, validate prerequisites, perform the supported binary rollout, validate topology/replication/application/recovery, execute burn-in, obtain policy approval, set FCV, verify stable FCV, perform post-FCV validation, retain evidence, and only then declare the upgrade complete.

Production FCV advancement should remain behind an explicit policy-controlled approval gate unless the organization has deliberately implemented and validated an equivalent automated change-control mechanism.

## 22. Production FCV Runbook

1. Record environment, topology, binaries, current FCV, target FCV, and change record.
2. Query FCV explicitly.
3. Validate topology and replication.
4. Confirm no unexpected initial sync or unsafe member state.
5. Inspect conflicting active operations where applicable.
6. Validate application health and critical workflows.
7. Validate backup/recovery posture and downgrade restrictions.
8. Confirm burn-in and obtain FCV approval.
9. Execute `setFeatureCompatibilityVersion` against the correct topology endpoint.
10. Re-query and verify stable target FCV.
11. Revalidate topology, replication, application, logs, latency, errors, and alerts.
12. Retain evidence and close the upgrade only after successful post-FCV validation.

## 23. Failure Scenarios

### FCV Raised Too Early

Raising FCV immediately after binary rollout removes the intended compatibility-validation boundary before sufficient production evidence exists. Keep the previous FCV during approved burn-in and advance only after validation and approval.

### FCV Never Advanced

A deployment can remain indefinitely on newer binaries with an old FCV because the binary ticket was closed too early. Monitoring must distinguish an approved burn-in from stale unfinished upgrade state.

### Binary-Only Validation

`mongod --version` proves neither FCV nor upgrade completion. Completion evidence must include binary inventory, FCV, topology, replication, application validation, recovery validation, and post-FCV checks.

## 24. Audit Evidence

Retain cluster/environment, previous and target binary versions, previous and target FCV, rollout timestamps, burn-in timestamps, topology/replication/application/backup validation, FCV command timestamp/result, independently verified FCV, post-FCV validation, change ticket, operator, approver, and final status.

## 25. Production Guardrails

- Do not equate binary version with FCV.
- Do not automatically advance FCV immediately after binary rollout.
- Use an evidence-based production burn-in and validation gate.
- Do not advance FCV during unsafe initial sync or unhealthy topology.
- Inventory all relevant sharded-cluster components.
- Apply arbiter-specific FCV monitoring logic.
- Investigate `CannotUpgrade` and `CannotDowngrade` rather than blindly retrying.
- Do not automatically kill conflicting operations.
- Re-query FCV after every transition.
- Do not interpret timeout as proof that nothing changed.
- Do not treat lowering FCV as equivalent to binary rollback.
- Maintain independent backup and recovery protection.
- Monitor persistent binary/FCV mismatch.
- Close the upgrade only after post-FCV validation.

## 26. Key Takeaways

FCV is part of a layered compatibility architecture:

```text
Application Compatibility
        |
Driver Compatibility
        |
Feature Compatibility Version
        |
MongoDB Binary Version
        |
Persisted Data / Metadata
        |
Platform / Infrastructure
```

For a MongoDB 7.0 to 8.0 upgrade, the production lifecycle is:

```text
7.0 binaries + FCV 7.0
        |
rolling binary upgrade
        |
8.0 binaries + FCV 7.0
        |
burn-in and production validation
        |
approval
        |
FCV 8.0
        |
post-FCV validation
        |
COMPLETE
```

The production invariant is:

> **Treat the MongoDB binary upgrade as a software deployment and the FCV transition as a separate compatibility commitment.**
