# 2.22 — Binary Version vs. FCV

**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Technical Baseline:** MongoDB 8.x, with MongoDB 7.x behavior where required for upgrade-path context  
**Edition:** Revised Final / Canonical  
**Status:** Canonical

> **A new MongoDB binary proves that new software is running. It does not, by itself, prove that the deployment has committed to the new compatibility level or that the production upgrade lifecycle is complete.**

## 2.22.1 Purpose and Scope

MongoDB production version state cannot safely be represented by a single version number. Administrators must distinguish the MongoDB binary version, Feature Compatibility Version (FCV), topology state, upgrade lifecycle state, driver/application compatibility, and infrastructure configuration capable of recreating MongoDB processes.

```text
Production MongoDB Version State
        =
Observed Binary Versions
        +
Observed FCV
        +
Topology State
        +
Upgrade Lifecycle State
        +
Deployment-Source State
        +
Application Compatibility
```

A deployment may intentionally operate with MongoDB 8.0 binaries and FCV 7.0 during validation and burn-in of a supported 7.0 → 8.0 upgrade. That state does not automatically indicate drift.

## 2.22.2 Binary Version

The binary version identifies the MongoDB server software executing on a particular process.

```javascript
db.version()
```

For detailed build information:

```javascript
db.adminCommand({ buildInfo: 1 })
```

At the operating-system level:

```bash
mongod --version
mongos --version
```

The binary determines the server implementation being executed. It does not independently establish FCV.

**Binary Version ≠ FCV.**

## 2.22.3 Feature Compatibility Version

FCV is a persistent MongoDB deployment setting used to control compatibility behavior associated with version-specific features that can persist data or metadata incompatible with earlier MongoDB versions.

Inspect FCV on an applicable `mongod`:

```javascript
db.adminCommand({
  getParameter: 1,
  featureCompatibilityVersion: 1
})
```

FCV is a separate compatibility dimension rather than another representation of the server binary version.

## 2.22.4 Independent Version Dimensions

A supported major upgrade can move through these states:

| Stage | Binary State | FCV | Meaning |
|---|---|---:|---|
| Pre-upgrade | 7.0 | 7.0 | Original deployment |
| Binary rollout | 7.0 + 8.0 | 7.0 | Supported temporary mixed state |
| Burn-in | 8.0 | 7.0 | New software, previous compatibility boundary |
| Committed | 8.0 | 8.0 | Target binary and compatibility state |

From an SRE/DBRE perspective, binary rollout is software deployment while FCV advancement is compatibility commitment. This is an operational model, not MongoDB product terminology.

## 2.22.5 Burn-In State

For a supported 7.0 → 8.0 transition, all binaries may be 8.0 while FCV remains 7.0. This creates a production validation checkpoint before target-version compatibility behavior is enabled.

```text
7.0 binaries / FCV 7.0
        ↓
Rolling binary upgrade
        ↓
8.0 binaries / FCV 7.0
        ↓
Burn-in
        ↓
FCV approval
        ↓
8.0 binaries / FCV 8.0
```

Burn-in must be evidence based. Organization-specific durations are policy, not MongoDB requirements. Completion should consider topology, replication, application behavior, performance, regression evidence, and recovery readiness.

## 2.22.6 Binary Version Does Not Imply FCV

`db.version()` returning 8.0.x is not sufficient evidence that FCV is 8.0 or that the upgrade is complete. Check FCV independently.

## 2.22.7 FCV Does Not Prove Binary Uniformity

FCV alone cannot prove that every MongoDB process is running the intended binary. Inventory all relevant members and components. A replica set can temporarily contain 7.0 and 8.0 binaries while FCV remains 7.0 during a documented rolling transition.

## 2.22.8 Mixed Binary Versions

Mixed-version operation is acceptable only when the exact source/target MongoDB procedure explicitly supports that transition. Before a major upgrade, establish source binary, target binary, current and required FCV, edition, topology, and supported upgrade path. Release-specific documentation takes precedence over generic assumptions.

## 2.22.9 Exact Binary Builds and Patch Changes

FCV generally identifies a compatibility generation rather than an exact patch build. Patch maintenance can change binaries while FCV remains unchanged. Production inventory should therefore capture the exact observed binary/build separately from FCV.

## 2.22.10 Replica-Set Inventory

Use `rs.status()` and per-member binary/build evidence. Determine primary/secondary roles, exact binary versions, FCV, replication health, lag, initial sync, RECOVERING/ROLLBACK states, and whether any mixed-version state is expected.

## 2.22.11 Arbiter-Specific FCV Handling

Arbiters require topology-aware FCV monitoring. Do not require every replica-set member to expose identical FCV evidence. Evaluate ordinary data-bearing members normally and apply MongoDB-specific arbiter semantics to arbiters.

## 2.22.12 Sharded-Cluster Inventory and FCV Inspection

Inventory the `mongos` fleet, config-server members, and every shard replica-set member. FCV inspection using `getParameter` is directed at applicable `mongod` processes; do not assume identical inspection semantics through `mongos`. FCV advancement for a sharded cluster is performed through the appropriate `mongos` according to the documented procedure.

## 2.22.13 Deployment-Source Compliance

Runtime compliance is not sufficient when infrastructure can recreate MongoDB processes. Validate container images, Helm values, operator specifications, package pins, repositories, VM images, Terraform variables, and configuration-management state where applicable.

**Runtime compliance without deployment-source compliance may only be temporary compliance.**

## 2.22.14 Driver and Application Compatibility

Driver version and application compatibility are independent dimensions. FCV does not certify driver compatibility, and binary+FCV compliance does not prove application health. Validate connections, authentication, pooling, reads/writes, retries, transactions, change streams, aggregation, timeouts, failover, framework behavior, and critical business workflows as applicable.

## 2.22.15 Lifecycle State

Binary 8.0 + FCV 7.0 could mean approved burn-in, abandoned upgrade, failed FCV advancement, or unauthorized drift. Track an independent SRE/DBRE lifecycle state such as `PRE_UPGRADE`, `BINARY_ROLLOUT`, `BURN_IN`, `FCV_PENDING`, `FCV_TRANSITIONING`, `POST_FCV_VALIDATION`, `COMMITTED`, `ROLLBACK_EVALUATION`, or `FAILED`. These are handbook operational classifications, not MongoDB product states.

## 2.22.16 Desired-State Architecture

A production desired-state model should separately record desired binary, desired FCV, lifecycle, change authorization, and FCV approval. This prevents automation from treating a deliberate FCV hold as ordinary configuration drift.

## 2.22.17 Operational State Matrix

| Binary | FCV | Lifecycle | Interpretation |
|---|---|---|---|
| Old | Old | PRE_UPGRADE | Expected |
| Mixed | Old | BINARY_ROLLOUT | Allowed only by supported procedure |
| New | Old | BURN_IN | Expected when authorized |
| New | Old | Unknown | Investigate |
| New | Transitioning | FCV_TRANSITIONING | Monitor closely |
| New | New | POST_FCV_VALIDATION | Validation required |
| New | New | COMMITTED | Target state |
| Unexpected mixed | Any | None | Investigate/escalate |

The correct question is whether the observed binary/FCV combination is consistent with the approved lifecycle.

## 2.22.18 Initial Sync Protection

MongoDB documents an interaction between FCV changes and replica-set initial sync. As an SRE/DBRE safeguard, block FCV advancement while initial sync is active, stabilize the topology, validate replication, and then re-enter the FCV approval gate.

## 2.22.19 FCV Advancement

For the MongoDB 8.0 baseline:

```javascript
db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true
})
```

For a replica set, execute against the appropriate primary according to documented requirements. For a sharded cluster, execute through `mongos`. FCV advancement is distributed work and can involve replica-set configuration/propagation behavior; it is not merely a local variable assignment.

## 2.22.20 FCV Advancement Gate

Before advancing FCV, verify complete binary inventory, expected topology, healthy replication, acceptable lag, absence of unexpected initial sync/RECOVERING/ROLLBACK, application and driver validation, evidence-based burn-in, backup/recovery readiness, downgrade implications, change authorization, and explicit FCV approval. This checklist is an SRE/DBRE production control rather than a MongoDB-mandated checklist.

## 2.22.21 Command Uncertainty and Idempotency

A client timeout does not prove FCV remained unchanged. Re-query authoritative state, inspect topology and logs, and retry only when safe. Idempotency does not mean retry forever.

## 2.22.22 FCV Transition Failures

Important failure classes include `CannotUpgrade` and `CannotDowngrade`. Capture the exact error, identify the blocking state, consult exact version documentation, determine supported remediation, assess impact, remediate, retry safely, and verify. Do not blindly retry.

## 2.22.23 Downgrade Boundary

Lower FCV is not equivalent to binary downgrade, application rollback, configuration rollback, or backup restore. MongoDB downgrade support is release- and edition-specific and can be restrictive. Always consult exact source/target documentation before binary downgrade. FCV advancement can increase downgrade complexity because target-version persisted features may become usable.

## 2.22.24 Drift Detection

Never implement `desired FCV != observed FCV → automatically set FCV`. Detect the mismatch, classify lifecycle, find the approved change, check burn-in, validate topology/application, review downgrade implications, and determine authorized remediation.

## 2.22.25 UNKNOWN and CONFLICT

Automation should support `EXPECTED`, `WARN`, `DRIFT`, `FAILED`, `UNKNOWN`, and `CONFLICT`. UNKNOWN is not PASS. Conflicting authoritative evidence is a stop condition until exact version documentation resolves the conflict.

## 2.22.26 Upgrade-Age Monitoring

Track binary rollout timestamps, burn-in start, current/target FCV, expected completion, change ID, owner, and lifecycle. Alert when new binaries + previous FCV exists without approved burn-in, or when an approved intermediate state exceeds organization-defined policy.

## 2.22.27 Monitoring and Alerting

Fleet dashboards should expose cluster, environment, topology, component/member, role, exact and desired binary, observed and desired FCV, lifecycle, drift age, change ID, owner, and health. Avoid a simplistic `BinaryMajor != FCV → CRITICAL` alert because legitimate burn-in would create false positives.

## 2.22.28 Failure Scenarios

### Forgotten member

If one replica-set member remains on the old binary, inventory every member, identify why it was missed, validate the supported transition, complete rollout, validate topology/replication, and reinventory.

### FCV left behind

If all binaries are 8.0 but FCV remains 7.0 long after the change, determine whether this is a forgotten step, failed FCV command, abandoned upgrade, compatibility hold, or application issue. Do not automatically repair FCV.

### FCV raised too early

Immediate FCV advancement after binary rollout removes the intended compatibility checkpoint before sufficient production validation. Prefer binary rollout → previous FCV → burn-in → topology/application/recovery validation → approval → FCV advancement.

### Stale deployment source

A running 8.0 fleet can regress if Helm, operator, image, package, or IaC configuration still references 7.0. Sustainable compliance requires both running-state and deployment-source compliance.

## 2.22.29 Automation Architecture

```text
DISCOVER
   ↓
INVENTORY
   ↓
CLASSIFY
   ↓
VALIDATE SUPPORTED TRANSITION
   ↓
COMPARE DESIRED/OBSERVED STATE
   ↓
CHECK CHANGE AUTHORIZATION
   ↓
CHECK LIFECYCLE STATE
   ↓
EXECUTE ALLOWED ACTION
   ↓
VERIFY
   ↓
RECORD EVIDENCE
```

Production FCV advancement should remain behind explicit policy-controlled approval unless an equivalent validated automated change-control mechanism exists.

## 2.22.30 Production Validation Runbook

1. Record cluster, environment, topology, change ID, expected binary, expected FCV, and expected lifecycle.
2. Inspect binary with `db.version()` and detailed build information where required.
3. Inventory all relevant topology components using `rs.status()` and topology-specific discovery.
4. Inspect FCV on applicable `mongod` components.
5. Compare desired and observed binary/FCV/lifecycle state.
6. Validate topology and replication health.
7. Validate deployment-source configuration.
8. Validate application behavior.
9. Classify state as EXPECTED/WARN/DRIFT/FAILED/UNKNOWN/CONFLICT.
10. Record evidence before proceeding.

## 2.22.31 Audit Evidence

Retain cluster/environment/change ID, source and target binaries, per-member versions, source/target/observed FCV, topology inventory, deployment-source versions, replication/application/driver validation, burn-in evidence, FCV authorization and command result, post-FCV validation, exceptions, operator, approver, timestamps, and final lifecycle state.

## 2.22.32 Production Guardrails

1. Track binary version and FCV independently.
2. Never infer FCV from `db.version()`.
3. Never infer complete binary rollout from FCV.
4. Inventory every relevant topology component.
5. Track exact patch/build versions.
6. Permit mixed versions only for documented supported transitions.
7. Treat binary rollout and FCV advancement as separate lifecycle events.
8. Preserve evidence-based burn-in where appropriate.
9. Track SRE lifecycle independently from MongoDB state.
10. Apply arbiter-specific FCV monitoring.
11. Use topology-aware FCV inspection in sharded deployments.
12. Block FCV advancement during initial sync as a production safeguard.
13. Validate drivers and applications independently.
14. Validate deployment-source state.
15. Never automatically repair FCV without lifecycle classification.
16. Verify state after uncertain command results.
17. Investigate `CannotUpgrade`/`CannotDowngrade`; do not blindly retry.
18. Never equate lower FCV with binary downgrade.
19. Review downgrade implications before FCV advancement.
20. Monitor long-lived binary/FCV mismatches.
21. Treat UNKNOWN and conflicting evidence as unresolved.
22. Record evidence for every major transition.
23. Declare upgrade completion only after post-FCV validation.

## 2.22.33 Production Case Study

A production three-member replica set moves from 7.0 binaries/FCV 7.0 through a supported rolling binary transition to 8.0 binaries/FCV 7.0. During burn-in, SRE validates replica-set health, replication, lag, application transactions, connection behavior, performance, logs, backup/recovery readiness, and deployment-source state. After the evidence-based burn-in and FCV approval gate pass, FCV is advanced according to the documented procedure. Topology, replication, application, performance, logs, and monitoring are revalidated before lifecycle state becomes `COMMITTED`.

By contrast, 8.0 binaries + FCV 7.0 with no active change, no burn-in owner, no documented compatibility hold, and a long mismatch age should be investigated as lifecycle drift.

## 2.22.34 Key Takeaways

Binary version answers what MongoDB software is running. FCV answers which persisted-feature compatibility boundary is active. Neither alone describes complete production state.

```text
MongoDB Version State
        =
Binary Versions
        +
FCV
        +
Topology
        +
Lifecycle
        +
Driver Compatibility
        +
Application Compatibility
        +
Deployment-Source Compliance
```

A safe lifecycle is:

```text
Old binaries + old FCV
        ↓
Supported mixed binaries + old FCV
        ↓
New binaries + old FCV
        ↓
Evidence-based burn-in
        ↓
FCV approval gate
        ↓
New binaries + new FCV
        ↓
Post-FCV validation
        ↓
COMMITTED
```

> **Binary rollout establishes the software version. FCV advancement establishes the compatibility commitment. Production upgrade completion requires both, plus successful operational and application validation.**
