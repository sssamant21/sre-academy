# 2.23 — FCV Upgrade Procedure and Burn-In Period

**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Technical Baseline:** MongoDB 8.x, with MongoDB 7.x behavior where required for upgrade-path context  
**Edition:** Revised Final / Canonical  
**Status:** Canonical

> A MongoDB major-version upgrade is not complete merely because every process is running the new binary. Production acceptance requires an intentional burn-in period, evidence-based validation, controlled FCV advancement, and post-FCV verification.

## Purpose

Feature Compatibility Version (FCV) is a distinct control boundary during a MongoDB major-version upgrade. For the supported 7.0 → 8.0 path, operators should separate software deployment, production validation, and compatibility commitment.

```text
MongoDB 7.0 binaries / FCV 7.0
              ↓
       Binary upgrade
              ↓
MongoDB 8.0 binaries / FCV 7.0
              ↓
           Burn-in
              ↓
     FCV approval gate
              ↓
MongoDB 8.0 binaries / FCV 8.0
              ↓
   Post-FCV validation
              ↓
          COMMITTED
```

The 8.0-binaries/7.0-FCV state is therefore an expected, controlled intermediate state during an authorized upgrade rather than configuration drift.

## Upgrade Lifecycle

The handbook uses these SRE/DBRE lifecycle states: `PRE_UPGRADE`, `BINARY_ROLLOUT`, `BURN_IN`, `FCV_PENDING`, `FCV_TRANSITIONING`, `POST_FCV_VALIDATION`, `COMMITTED`, `ROLLBACK_EVALUATION`, and `FAILED`. These are handbook operational classifications, not MongoDB product states.

## Pre-Upgrade Readiness Gate

Before binary rollout, verify the supported source-to-target path, exact current builds, source FCV, topology health, replication health, absence of unexplained `RECOVERING` or `ROLLBACK`, backup/recovery readiness, driver and application compatibility, authentication/TLS compatibility, release-specific behavior changes, package/image availability, deployment-source desired state, monitoring readiness, and change authorization.

For this baseline:

```text
Source binaries = MongoDB 7.0
Source FCV      = 7.0
Target binaries = MongoDB 8.0
Target FCV      = 8.0
```

Do not infer FCV from the binary version.

## Baseline Evidence

Capture version and FCV state before the change:

```javascript
db.version()
```

```javascript
db.adminCommand({ buildInfo: 1 })
```

```javascript
db.adminCommand({
  getParameter: 1,
  featureCompatibilityVersion: 1
})
```

For replica sets, also capture `rs.status()`. Record topology, roles, versions, replication lag, application SLIs, error rates, latency, CPU, memory, disk, WiredTiger/cache behavior, and other workload-specific indicators.

## Binary Rollout Completion Gate

Do not enter burn-in until every intended `mongod` and `mongos` is running the approved target build, topology is healthy, replication is healthy, and the authoritative deployment source—package pins, image tags, Helm, operator configuration, Terraform, or other IaC—also points to the target release.

A runtime-only upgrade can be reversed by the next restart or reconciliation if desired state still references the previous release.

## Sharded-Cluster Upgrade Context

For the documented 7.0 → 8.0 sharded-cluster procedure, follow the release-specific ordering and balancer requirements. Operationally, the binary rollout accounts for the config server replica set, shard replica sets, and then the `mongos` fleet, with balancer handling performed according to the exact MongoDB procedure. Never generalize this ordering blindly to future releases.

## Burn-In

Once target binaries are deployed and FCV intentionally remains at the previous level, transition to `BURN_IN`. Record the target binary, current FCV, target FCV, burn-in start, change ID, owner, and approval authority.

MongoDB does not impose a handbook-wide 24-, 48-, or 72-hour burn-in duration. Organizations may define minimum observation periods, but elapsed time alone does not establish readiness.

```text
TIME ELAPSED ≠ BURN-IN COMPLETE
```

Burn-in completion requires evidence, acceptance criteria, no unresolved blockers, and authorization.

## Topology and Replication Validation

During burn-in, validate primary and secondary availability, replication lag, heartbeats, elections, member state changes, rollback, initial sync, and reachability. For sharded deployments also validate config-server health, shard replica sets, `mongos`, routing behavior, and balancing state where applicable.

Unexpected topology instability blocks FCV advancement.

### Initial Sync Protection

If initial sync is detected, block FCV approval, allow the synchronization condition to be resolved, stabilize topology, and re-enter the acceptance process. FCV advancement should not be treated as routine while topology is in an unsuitable synchronization state.

## Application Validation

Burn-in must validate representative production behavior, including connection/authentication, reads, writes, updates, deletes, aggregation, transactions and change streams where used, retry behavior, failover/reconnect behavior, TLS, connection pools, drivers, frameworks, and critical business workflows.

Compatibility testing should occur before production; burn-in confirms production behavior against that expectation.

## Performance and Recovery Validation

Compare p50/p95/p99 latency, throughput, application error rate, connections, CPU, memory, WiredTiger cache, disk latency, IOPS, replication lag, oplog behavior, network throughput, and slow operations with the recorded baseline. A material unexplained regression blocks FCV advancement.

Confirm recent backup availability, backup-job health, restore procedure, credentials, encryption/key dependencies, snapshot availability, RPO/RTO assumptions, and responsible recovery personnel. A successful backup job alone is not proof of recoverability.

## Burn-In Acceptance Gate

The handbook production gate requires target binaries fully deployed, deployment source updated, healthy topology and replication, acceptable lag, no unexpected initial sync or unresolved rollback/recovery state, validated application workflows and drivers, validated authentication/TLS, transactions/change streams validated where applicable, acceptable performance/error rate, confirmed backup/recovery readiness, no unresolved upgrade regression, understood downgrade implications, and complete change evidence.

This is an SRE/DBRE production-control framework, not a claim that MongoDB mandates this exact checklist.

## Stop Conditions

Block FCV advancement for an unexpected old binary, unexplained mixed versions, initial sync, `ROLLBACK`, unexplained `RECOVERING`, replication instability, abnormal lag, application or driver regression, authentication failure, significant performance regression, recovery uncertainty, deployment-source mismatch, unresolved upgrade error, missing authorization, or conflicting evidence.

```text
UNKNOWN ≠ PASS
WARNING ≠ APPROVAL
TIME ELAPSED ≠ BURN-IN COMPLETE
BINARY UPGRADE COMPLETE ≠ FCV APPROVED
```

## FCV Approval and Advancement

FCV advancement is a separate compatibility commitment. Record the change ID, current/target binaries, current/target FCV, burn-in evidence, outstanding risks, downgrade implications, approval identity, and approval timestamp before execution.

For MongoDB 8.0:

```javascript
db.adminCommand({
  setFeatureCompatibilityVersion: "8.0",
  confirm: true
})
```

Execute from the topology endpoint required by the applicable release documentation: the appropriate primary for a replica set and through `mongos` for a sharded cluster.

Treat FCV advancement as distributed topology-dependent work, not as a local variable assignment.

## Uncertain Result and Retry Safety

A client timeout does not prove FCV advancement failed. MongoDB documents FCV advancement as idempotent/safely retryable, but production automation should still inspect authoritative state and failure context before repeated retries.

```text
Command issued
      ↓
Response uncertain
      ↓
Inspect authoritative FCV
      ↓
Inspect topology and logs
      ↓
Classify actual state
      ↓
Remediate/retry when justified
      ↓
Verify again
```

Errors such as `CannotUpgrade` are diagnostic signals. Capture the exact error, identify the blocker, consult the exact-version procedure, remediate safely, revalidate topology, and retry only when justified.

## Verify FCV

After completion, independently query:

```javascript
db.adminCommand({
  getParameter: 1,
  featureCompatibilityVersion: 1
})
```

Command submission is not evidence of success. Record observed FCV, binary inventory, topology and replication state, command result, timestamp, and change ID.

## Post-FCV Validation

Transition to `POST_FCV_VALIDATION` and repeat critical topology, replication, application, authentication, transaction/change-stream, performance, logging, monitoring, and backup checks. Only after acceptance should the lifecycle become `COMMITTED`.

## Rollback and Downgrade Boundary

```text
FCV downgrade
      ≠
Binary downgrade
      ≠
Application rollback
      ≠
Configuration rollback
      ≠
Backup restore
```

Holding FCV at the previous level provides an operational decision point; it does not guarantee that binary downgrade is supported or trivial. Downgrade capabilities depend on release, edition, topology, persisted state, features used, and the exact documented procedure. Never improvise a major-version downgrade.

## Monitoring and Automation

Fleet dashboards should expose cluster, environment, topology, member/component, role, observed and desired binary, observed and desired FCV, lifecycle, burn-in age, replication health, lag, application health, change ID, owner, and approval state.

Do not alert merely on `BinaryMajor != FCV`; legitimate burn-in would be misclassified. Classify lifecycle-aware states such as `EXPECTED`, `WARN`, `DRIFT`, `FAILED`, `UNKNOWN`, and `CONFLICT`. `UNKNOWN` must never be treated as `PASS`.

Safe automation can perform inventory, version/FCV discovery, topology and replication checks, SLI collection, burn-in evidence collection, deployment-source validation, drift detection, and reporting. Binary rollout and remediation are policy-controlled. FCV advancement remains approval-controlled unless an organization has an equivalent validated automated change-control mechanism.

## Production Runbook

1. Confirm supported source → target path and source FCV.
2. Inventory binaries/topology and validate replication.
3. Validate drivers/applications and backup/recovery readiness.
4. Capture baseline and confirm deployment-source target version.
5. Execute the documented binary upgrade.
6. Inventory every component and confirm target binaries with previous FCV intentionally retained.
7. Enter `BURN_IN` and record evidence.
8. Exercise application workflows and monitor database/application SLIs.
9. Investigate every material regression and evaluate the acceptance gate.
10. Review downgrade implications and obtain FCV approval.
11. Recheck topology immediately before FCV advancement.
12. Execute `setFeatureCompatibilityVersion` from the correct topology endpoint.
13. Handle uncertain results by inspecting authoritative state before retry.
14. Verify FCV independently.
15. Enter `POST_FCV_VALIDATION`, repeat critical checks, and mark `COMMITTED` only after acceptance.

## Key Principles

```text
Binary rollout is not upgrade completion.
FCV is a compatibility commitment.
Burn-in is evidence based.
Time alone does not prove readiness.
Unknown is not healthy.
A timeout is not proof of failure.
Runtime and deployment source must agree.
Application health is part of database upgrade validation.
Rollback and downgrade are separate concepts.
Release-specific MongoDB documentation overrides generic runbooks.
FCV advancement requires an explicit production decision.
```

## Canonical Decision

The canonical production model is `PRECHECK → BINARY ROLLOUT → VERIFY → BURN-IN → COLLECT EVIDENCE → ACCEPTANCE GATE → APPROVAL → ADVANCE FCV → VERIFY → POST-FCV VALIDATION → COMMIT`.
