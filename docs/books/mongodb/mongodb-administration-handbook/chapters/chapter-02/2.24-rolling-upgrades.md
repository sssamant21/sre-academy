# 2.24 — Rolling Upgrades

**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Technical Baseline:** MongoDB 8.x, with MongoDB 7.x → 8.x upgrade context  
**Edition:** Revised Final / Canonical  
**Status:** Canonical

> A MongoDB rolling upgrade is a topology-aware production change. Its objective is to replace binaries incrementally while preserving replication, voting majority, application availability, recoverability, and a controlled transition into the FCV burn-in phase.

## Purpose

Rolling upgrades allow replicated MongoDB deployments to move to a supported newer release without intentionally stopping the entire deployment simultaneously.

```text
PRECHECK
   ↓
BASELINE
   ↓
BINARY_ROLLOUT
   ↓
CHANGE ONE MEMBER
   ↓
REJOIN + CATCH UP
   ↓
MEMBER ACCEPTANCE
   ↓
GLOBAL HEALTH GATE
   ↓
NEXT MEMBER
   ↓
CONTROLLED PRIMARY TRANSITION
   ↓
COMPLETE BINARY FLEET
   ↓
BURN_IN
   ↓
FCV PROCEDURE
   ↓
POST-FCV VALIDATION
```

Rolling upgrades minimize disruption; they do not automatically guarantee zero user-visible downtime because elections, reconnections, transactions, drivers, and application retry behavior can produce transient impact.

## Binary Rollout and FCV Are Separate

A rolling upgrade changes executable software. FCV advancement changes the deployment's compatibility commitment.

```text
Rolling upgrade = Binary deployment
FCV advancement = Compatibility commitment
```

For the 7.0 → 8.0 baseline, the intended post-rollout state is all intended binaries at 8.0, FCV still 7.0, and lifecycle `BURN_IN`. Section 2.23 governs the subsequent burn-in and FCV transition.

## Supported Upgrade Path and Compatibility Review

Before production work, validate the exact source and target releases. For this baseline, source binaries are MongoDB 7.0 with FCV 7.0 and target binaries are MongoDB 8.0. Review target release notes, compatibility changes, critical advisories, driver compatibility, application behavior, deprecated/removed behavior, and operational tooling compatibility. Test important workload patterns before production.

## Pre-Upgrade Production Gate

Before changing the first member, verify all expected members are identified and running; exact builds and source FCV are known; topology, primary/secondaries, voting majority, replication, lag, and oplog window are healthy; there is no unexplained initial sync, `ROLLBACK`, or `RECOVERING`; backup/recovery readiness is confirmed; drivers/applications and authentication/TLS are compatible; target packages/images and desired-state configuration are ready; monitoring is active; and change authorization exists.

`UNKNOWN ≠ PASS`. An incomplete topology inventory blocks the rollout.

## Establish the Baseline

Useful checks include:

```javascript
rs.status()
```

```javascript
db.adminCommand({ buildInfo: 1 })
```

```javascript
db.adminCommand({
  getParameter: 1,
  featureCompatibilityVersion: 1
})
```

Record cluster, environment, member, role, binary/build, FCV, replica state, votes, priority, health, replication lag, oplog position, change ID, and timestamp. Capture workload baselines such as p50/p95/p99 latency, throughput, errors, connections, CPU, memory, WiredTiger cache, disk latency/IOPS, network, replication lag, and slow operations.

## Voting Majority and Maintenance Safety

Server count alone does not determine safe concurrency. Inventory voting and non-voting members, data-bearing members, arbiters, priorities, hidden/delayed members, failure domains, and already unhealthy members.

Before each member, recalculate current topology, confirm maintenance preserves required majority, evaluate tolerance for another failure, and proceed only when safe. An already degraded deployment has a smaller safety envelope.

## One Member at a Time

For the standard production rolling procedure, change one replica-set member at a time.

```text
SECONDARY
   ↓
Upgrade
   ↓
Restart
   ↓
Wait for SECONDARY
   ↓
Catch up
   ↓
Validate
   ↓
Accept member
   ↓
Recheck global topology
   ↓
Next SECONDARY
```

After eligible secondaries are upgraded, perform a controlled primary transition, confirm the new primary, and upgrade the former primary. Do not progress merely because an install/restart command returned successfully.

## Secondary Upgrade Procedure

For each eligible secondary: recheck cluster health; confirm member identity and `SECONDARY` state; confirm replication and majority safety; stop/drain as required; install or reconcile the target binary; start MongoDB; confirm target build; wait for replica-set rejoin and `SECONDARY`; wait for catch-up; inspect logs and metrics; validate authentication/TLS and deployment source; run the member acceptance gate; and recheck global topology before continuing.

## Member Acceptance Gate

```text
Correct target binary/build
          +
Expected replica-set state
          +
Replication resumed
          +
Catch-up acceptable
          +
No unresolved startup errors
          +
Authentication/TLS healthy
          +
Storage healthy
          +
Deployment source correct
          =
MEMBER ACCEPTED
```

For an upgraded secondary, reaching the expected `SECONDARY` state is a hard progression requirement.

## Failure to Rejoin and Failure Containment

If a member fails to return normally, stop rollout progression. Investigate MongoDB logs, configuration, package/image, TLS/certificates/keyfiles, authentication, network/DNS/firewall, filesystem permissions, storage, startup options, replication state, compatibility errors, and resource exhaustion.

```text
Unexpected result
       ↓
STOP
       ↓
Preserve healthy topology
       ↓
Collect evidence
       ↓
Diagnose and stabilize
       ↓
Determine supported recovery
       ↓
Revalidate
       ↓
Resume only when approved
```

Do not continue through failures merely because majority still exists or the maintenance window is closing.

## Replication Catch-Up and Oplog Safety

After restart, verify member state, optime, replication lag, heartbeat health, sync behavior, and replication errors before removing another member from service. Acceptance thresholds should reflect workload, topology, RPO, and normal baseline rather than a universal number.

Ensure replication history comfortably covers shutdown, upgrade, restart, troubleshooting, catch-up, and an operational safety margin. If the margin becomes unsafe, pause the rollout.

Unexpected initial sync during routine rolling maintenance is a significant event: stop normal progression, determine the cause, stabilize topology, re-evaluate replication capacity, and re-enter the acceptance process.

## Primary Transition

Before primary transition, confirm upgraded secondaries are healthy and current, no unresolved errors remain, application monitoring is active, failover capacity and majority are protected, and change authorization remains valid.

For applicable procedures, controlled stepdown can use:

```javascript
rs.stepDown()
```

Then verify with:

```javascript
rs.status()
```

Do not maintain the former primary until another member has successfully assumed `PRIMARY` and the deployment has stabilized. Validate application reconnection, reads/writes, error rate, latency, and replication after election.

## Application Impact During Elections

Applications can observe connection interruption, server-selection delay, write retries, transaction aborts, connection-pool churn, latency spikes, or temporary errors. Production readiness depends on compatible drivers and correct retry/reconnection behavior. Test these behaviors before production and monitor them during the change.

## Mixed-Version State

A supported rolling major-version upgrade temporarily creates mixed binaries, for example a 7.0 primary with 8.0 secondaries while FCV remains 7.0. Such a state is acceptable only when it is supported, expected, authorized, monitored, and temporary. It must not become indefinite steady state.

Lifecycle-aware drift detection should consider observed and desired versions, FCV, lifecycle, and active change authorization. Classify states as `EXPECTED`, `WARN`, `DRIFT`, `FAILED`, `UNKNOWN`, or `CONFLICT`; never treat `UNKNOWN` as healthy.

## Special Replica-Set Members

Arbiters participate in voting but are not ordinary data-bearing secondaries; quorum calculations must account for their voting role. Hidden, non-voting, and delayed members may support reporting, backup, analytics, or recovery patterns. Capture `hidden`, `votes`, `priority`, `secondaryDelaySecs`, tags, and other relevant configuration before maintenance and verify that the intended topology design remains intact afterward.

## Sharded-Cluster Rolling Upgrade

A sharded deployment combines the config server replica set, one or more shard replica sets, and the `mongos` fleet. The overall procedure combines replica-set rolling maintenance with release-specific sharded-cluster sequencing.

For the 7.0 → 8.0 baseline, follow the documented sequence:

```text
Validate cluster
      ↓
Disable balancer
      ↓
Upgrade Config Server Replica Set
      ↓
Validate CSRS
      ↓
Upgrade shard replica sets
      ↓
Validate shards
      ↓
Upgrade mongos fleet
      ↓
Validate routing/applications
      ↓
Re-enable balancer
      ↓
Verify balancer state
```

Do not upgrade `mongos` ahead of the required config-server and shard stages. This ordering is release-specific and must be revalidated for future MongoDB releases.

### Config Server Replica Set

Treat the CSRS as a dedicated change stage. Upgrade one eligible secondary, restart, wait for `SECONDARY`, catch up, validate, and recheck the entire CSRS before proceeding. Perform the controlled primary transition and former-primary upgrade according to the applicable procedure. Do not begin the next cluster stage with unresolved CSRS instability.

### Shard Replica Sets

Within each shard replica set use the same secondary → upgrade → `SECONDARY` → catch-up → acceptance → primary transition → former-primary upgrade pattern. Validate each shard and suitable cluster-wide application checkpoints.

### mongos Fleet

Inventory all `mongos` processes across application hosts, Kubernetes, VMs, load-balanced tiers, regions, and administrative hosts. Track expected/observed count, build, deployment source, reachability, application usage, and routing health. A forgotten `mongos` is version drift.

## Kubernetes and Operator Deployments

Containerized MongoDB adds desired-state layers:

```text
Git / Helm / Operator CR
          ↓
Controller desired state
          ↓
Workload controller
          ↓
Pod/container image
          ↓
mongod/mongos runtime
```

The production invariant is `Desired-state version = Runtime version`. Do not manually upgrade a running container while GitOps still declares the old version. Review StatefulSet/operator upgrade strategy, PodDisruptionBudget, probes, node disruption, anti-affinity, persistent volumes, image availability, resource capacity, and termination behavior. Orchestrator readiness does not replace MongoDB topology validation.

## VM and Package Deployments

For host-based deployments verify repository, package pin, installed package, binary path, systemd unit, `mongod.conf`, startup options, filesystem permissions, and service account. Verify the running build independently rather than relying only on package-manager output.

## Stop Conditions

Immediately block progression for a missing member, failure to reach `SECONDARY`, unexpected initial sync, `ROLLBACK`, unexplained `RECOVERING`, replication instability or excessive lag, majority risk, abnormal election behavior, absence of a primary, application impact outside tolerance, authentication/TLS failure, storage error, wrong build, deployment-source mismatch, CSRS instability, routing failure, or unexplained MongoDB errors.

```text
UNKNOWN ≠ PASS
DEGRADED ≠ SAFE TO CONTINUE
PROCESS RUNNING ≠ MEMBER HEALTHY
MEMBER HEALTHY ≠ CLUSTER HEALTHY
MEMBER UPGRADED ≠ MEMBER ACCEPTED
ALL BINARIES UPGRADED ≠ FCV ADVANCED
FCV ADVANCED ≠ CHANGE COMPLETE
```

## Recovery and Downgrade Boundary

A failed rolling upgrade does not automatically authorize reinstalling the previous binary. Recovery depends on source/target release, current binary distribution, FCV, edition, topology, persisted state, features used, completed steps, and the supported downgrade procedure. Never improvise a major-version downgrade. Detailed treatment belongs in Sections 2.25 and 2.27.

## Binary Fleet Completion and Burn-In Handoff

After the final process, perform a fresh inventory. Require every expected `mongod` and `mongos` at the target binary, deployment source at the target binary, healthy topology and replication, healthy applications, and FCV intentionally at the previous level.

For the baseline:

```text
Binaries  = 8.0
FCV       = 7.0
Lifecycle = BINARY_ROLLOUT COMPLETE
```

Then transition to `BURN_IN`; Section 2.23 governs evidence, acceptance, FCV approval, FCV advancement, verification, and post-FCV validation. The final binary upgrade must not implicitly trigger FCV advancement.

## Monitoring and Automation

Expose cluster, environment, topology, member, role, observed/desired build, FCV, replica state, health, lag, last restart, upgrade state, deployment-source version, change ID, and owner. Useful member states include `PENDING`, `PRECHECK`, `DRAINING`, `STOPPED`, `UPGRADING`, `STARTING`, `REJOINING`, `CATCHING_UP`, `VALIDATING`, `ACCEPTED`, `BLOCKED`, `FAILED`, and `UNKNOWN`.

Safe orchestration is state-driven:

```text
DISCOVER
   ↓
GLOBAL PRECHECK
   ↓
SELECT SAFE MEMBER
   ↓
MEMBER PRECHECK
   ↓
CHANGE MEMBER
   ↓
WAIT FOR PROCESS
   ↓
WAIT FOR EXPECTED REPLICA STATE
   ↓
WAIT FOR REPLICATION
   ↓
VALIDATE MEMBER
   ↓
MEMBER ACCEPTANCE
   ↓
GLOBAL HEALTH GATE
   ↓
SELECT NEXT MEMBER
```

Do not use `restart → sleep N → upgrade next member` as a production algorithm. Timers can support orchestration, but observed state determines progression.

## Audit Evidence

For each member record cluster/change ID, member, previous role/build, target build, maintenance start, shutdown/startup/rejoin times, expected-state confirmation, catch-up time, validation result, warnings/errors, operator identity, and final state. At cluster level retain source/target versions and FCV, precheck, topology before/after, application validation, fleet completion, exceptions, burn-in handoff, and final change status.

## Production Runbook

1. Confirm supported source → target path and review compatibility changes.
2. Verify all expected members, source builds and FCV.
3. Inventory voting topology and validate replica-set health, replication, and oplog margin.
4. Confirm backup/recovery readiness, drivers/applications, baseline, target packages/images, and desired state.
5. For each eligible secondary: recheck global topology and majority safety, upgrade one member, confirm target build, wait for `SECONDARY` and catch-up, validate logs/metrics/authentication/deployment source, run member acceptance, then recheck global topology.
6. Before primary transition, confirm upgraded secondaries and replication are healthy; perform controlled stepdown; confirm new primary and application recovery; upgrade the former primary; wait for rejoin/catch-up and acceptance.
7. For sharded clusters, apply the release-specific balancer, CSRS, shard, and `mongos` sequence and validate each stage.
8. Inventory the complete fleet, confirm target binaries and desired state, validate topology/replication/applications, confirm previous FCV remains intentionally, and enter `BURN_IN`.
9. Hand off to Section 2.23 for FCV commitment.

## Key SRE/DBRE Principles

```text
Health before speed.
Change one member at a time.
Preserve voting majority.
Recalculate safety before every member.
Process running does not mean member accepted.
SECONDARY recovery is an explicit gate.
Replication catch-up is an explicit gate.
A degraded cluster is not safe for routine progression.
Mixed versions require lifecycle context.
Primary transition is an application event.
Rolling upgrade minimizes disruption; it does not promise zero downtime.
Desired state must match runtime.
Sharded-cluster component ordering is release-specific.
Do not advance FCV after the final binary automatically.
Never improvise binary downgrade.
Release-specific MongoDB documentation overrides generic runbooks.
```

## Canonical Decision

The canonical production model is `PRECHECK → BASELINE → SECONDARY ROLLING UPGRADES → MEMBER ACCEPTANCE AFTER EACH CHANGE → PRIMARY TRANSITION → FORMER PRIMARY UPGRADE → FLEET VERIFICATION → BURN-IN → FCV APPROVAL → POST-FCV VALIDATION → COMMITTED`.

The critical operational principle is: **a rolling upgrade progresses according to verified topology state, not command completion or elapsed time. Every member must return to an acceptable state before the next failure domain is deliberately disturbed.**
