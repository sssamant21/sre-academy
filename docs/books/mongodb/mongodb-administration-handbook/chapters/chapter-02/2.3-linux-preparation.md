# 2.3 — Linux Preparation

**Workflow Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades

## Purpose

A production MongoDB deployment depends on the operating system being prepared deliberately before `mongod` is installed or admitted into service. Linux defaults target general-purpose workloads, not specifically database latency, predictable memory behavior, sustained random I/O, or high connection counts. This section defines a production baseline for self-managed MongoDB hosts and identifies settings that must be validated against the exact MongoDB major version, Linux distribution, kernel, and deployment model.

Treat the Linux baseline as infrastructure configuration: document it, version-control it, automate it where practical, and revalidate it after OS, kernel, image, storage, or MongoDB changes.

## 2.3.1 Preparation Objectives

Before MongoDB is deployed, Linux preparation should provide:

- a supported Linux distribution, kernel, CPU architecture, and MongoDB version combination;
- predictable CPU, memory, storage, and network behavior;
- correctly sized and mounted database and log filesystems;
- resource limits suitable for MongoDB files, threads, and connections;
- MongoDB-version-appropriate Transparent Huge Pages configuration;
- validated NUMA behavior where applicable;
- time synchronization and stable hostname/DNS configuration;
- a dedicated MongoDB service identity with least privilege;
- approved repositories, package-signing trust, and version-control policy;
- host security controls intentionally configured for MongoDB;
- operating-system telemetry available before production cutover;
- persistent, repeatable configuration after reboot.

Do not copy tuning parameters blindly between environments. A setting appropriate for MongoDB 7.0 can be wrong for MongoDB 8.0+, and a physical NUMA server may require different treatment from a cloud VM.

## 2.3.2 Validate Platform and Kernel Support

Capture the platform baseline:

```bash
uname -a
uname -r
uname -m
cat /etc/os-release
getconf LONG_BIT
```

Confirm that the Linux distribution, CPU architecture, kernel, MongoDB edition, and MongoDB release form a supported combination. Recheck MongoDB production notes during every major-version installation or upgrade because platform requirements and kernel compatibility can change.

Record at least:

- Linux distribution and release;
- kernel version;
- CPU architecture and microarchitecture where relevant;
- virtualization or cloud instance type;
- filesystem and storage type;
- MongoDB edition and version;
- MongoDB package source;
- image/build identifier.

Standardize the host image across members of the same replica set or sharded-cluster role wherever possible. Kernel or image drift complicates incident comparison and can expose only part of a cluster to an OS-specific defect.

## 2.3.3 Establish the Service Account

Package installations normally create the MongoDB service identity. For custom installation methods, run MongoDB under a dedicated non-login account rather than `root`.

Validate the account:

```bash
id mongod
getent passwd mongod
```

Database, journal, diagnostic, audit, and log paths must be owned by the intended MongoDB service identity and should not be generally writable.

Example:

```bash
sudo chown -R mongod:mongod /var/lib/mongo /var/log/mongodb
sudo chmod 0750 /var/lib/mongo /var/log/mongodb
```

Use the paths and account names defined by the actual package and deployment design rather than assuming these examples.

## 2.3.4 Filesystem and Storage Preparation

Storage configuration directly affects latency, recovery time, and production stability. Provision and validate database storage before starting MongoDB.

```bash
lsblk -f
df -hT
findmnt
mount | column -t
```

MongoDB supports XFS and EXT4 on Linux and strongly recommends XFS for WiredTiger data-bearing nodes. For database storage, use mount options that avoid unnecessary access-time updates according to current MongoDB and platform guidance.

Document:

- MongoDB `dbPath`;
- log destination;
- filesystem type and mount options;
- underlying block/storage class;
- provisioned and effective IOPS/throughput;
- cloud burst-credit or throttling behavior where applicable;
- encryption requirements;
- snapshot/backup interaction;
- capacity expansion procedure;
- warning and critical free-space thresholds.

Maintain headroom for growth, index builds, maintenance, rollback/recovery, and temporary operational overhead. Disk exhaustion must not be the normal capacity trigger.

For WiredTiger, validate device readahead. Current MongoDB guidance recommends a readahead value between 8 and 32 unless workload testing demonstrates a repeatable benefit from another value.

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,RA
blockdev --getra /dev/<device>
```

Persist any approved readahead change through the platform-supported mechanism and verify it after reboot.

## 2.3.5 File Descriptors and Process Limits

`mongod` and `mongos` consume file descriptors and threads for connections and internal activity. Restrictive limits can lead to failed connections or loss of service under load.

```bash
ulimit -a
ulimit -n
ulimit -u
```

For a running process, inspect effective limits:

```bash
cat /proc/$(pidof mongod)/limits
```

For `systemd` deployments:

```bash
systemctl show mongod -p LimitNOFILE -p LimitNPROC
```

MongoDB emits a startup warning when the open-files limit is below 64,000. Treat that as a warning boundary, not as a universal capacity target. Establish production limits based on expected connections, workload, file usage, and service characteristics.

Persist limits through the supported `systemd` unit/drop-in or distribution mechanism and validate them after restart.

## 2.3.6 Memory, WiredTiger Cache, and Swap

WiredTiger uses both its internal cache and the operating-system filesystem cache. Host memory must accommodate MongoDB cache, filesystem cache, connections, operating-system processes, and required agents.

```bash
free -h
swapon --show
cat /proc/sys/vm/swappiness
```

MongoDB performs best when swapping is avoided or minimized. Current Linux production guidance recommends selecting `vm.swappiness` of `1` or `0` according to application needs and cluster configuration. Do not apply a universal swap policy without considering co-located workloads, cgroups, and the operational consequences of OOM termination.

Monitor available memory, swap occupancy and swap-in/swap-out rate, major page faults, OOM events, MongoDB resident memory, and WiredTiger cache utilization and eviction pressure.

Do not enlarge the WiredTiger cache merely because RAM appears unused. MongoDB intentionally leaves memory available for the filesystem cache and other consumers. Containers and constrained cgroups require additional validation because host memory and process limits may differ.

## 2.3.7 Transparent Huge Pages

THP configuration is MongoDB-version-specific.

**MongoDB 8.0 and later:** enable THP and apply the complete current MongoDB TCMalloc/THP configuration.

**MongoDB 7.0 and earlier:** disable THP for best performance.

Inspect the host:

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled
cat /sys/kernel/mm/transparent_hugepage/defrag
```

Do not carry a pre-8.0 "always disable THP" standard into MongoDB 8.0+ deployments. Conversely, do not enable THP on MongoDB 7.0 or earlier merely because the operating system defaults to it.

Implement the required state persistently through the distribution's supported initialization or tuning mechanism and verify it after reboot.

## 2.3.8 CPU and NUMA Considerations

WiredTiger is multithreaded and benefits from multiple CPU cores. Validate CPU and NUMA topology:

```bash
lscpu
numactl --hardware 2>/dev/null || true
```

For NUMA systems, follow current MongoDB production guidance. On Linux this includes disabling zone reclaim and starting `mongod`/`mongos` with the appropriate `numactl` memory-interleave policy when NUMA cannot be eliminated at the platform level. Ensure `numad` is not degrading MongoDB performance.

Monitor CPU saturation using more than aggregate utilization. Include run queue, steal time, VM/container throttling, cgroup quota exhaustion, and NUMA-related imbalance.

## 2.3.9 Network and Name Resolution

Replica-set and sharded-cluster members require stable network identity and predictable name resolution.

```bash
hostnamectl
hostname -f
getent hosts "$(hostname -f)"
ip addr
ip route
```

Use stable, resolvable hostnames appropriate for the architecture. Validate required paths for member-to-member traffic, applications, monitoring, backup, administration, DNS, and NTP.

Do not expose MongoDB listeners broadly for convenience. Security-group and firewall rules should implement minimum required reachability.

## 2.3.10 Time Synchronization

Reliable time synchronization supports operational logs, incident correlation, authentication, monitoring, and distributed-system behavior.

```bash
timedatectl
chronyc tracking 2>/dev/null || true
chronyc sources -v 2>/dev/null || true
```

Use approved NTP/time sources and alert on material clock drift. Manual clock changes should not be a routine database-node operation.

## 2.3.11 SELinux, AppArmor, and Host Security

Review host firewall policy, SELinux or AppArmor state and policy, file and directory permissions, service-account privileges, SSH/administrative access, repository/signing-key trust, encryption and key access, audit requirements, and vulnerability/patching controls.

Do not disable SELinux, AppArmor, or host firewalls as a default remediation step. Determine the blocked operation and apply the narrowest supported policy change. Non-default MongoDB paths or ports can require additional SELinux policy configuration. Review current MongoDB documentation for version-specific SELinux caveats.

## 2.3.12 Package and Repository Readiness

Confirm package tooling and configure only approved MongoDB repositories and signing keys. Control MongoDB package versions so generic OS patching does not unexpectedly perform a database upgrade outside the approved change window.

Operationally distinguish routine user-space OS updates, kernel/security updates requiring reboot, MongoDB package upgrades, and major Linux distribution upgrades. Each requires its own validation, sequencing, rollback, and compatibility plan.

## 2.3.13 Keep Database Hosts Purpose-Built

Use dedicated MongoDB systems when practical. Avoid turning production database hosts into general-purpose application servers. Security, observability, backup, and management agents may be required, but their resource impact must be understood.

For AV/EDR products, follow current MongoDB guidance for database storage and log paths so scanning does not create material I/O overhead or risk quarantine/deletion of database files. Avoid unvalidated dynamic-memory features such as VM ballooning for production MongoDB.

## 2.3.14 Observability Baseline

OS telemetry must exist before the first production incident. Collect CPU utilization, load, run queue, steal/throttle indicators; available memory, swap activity, faults, and OOM events; filesystem capacity and inode usage; disk latency, throughput, IOPS, queue depth, and utilization; network throughput, retransmits, errors, and drops; process state and service restarts; time synchronization health; and kernel/system logs.

Useful troubleshooting commands include:

```bash
vmstat 1
iostat -xz 1
pidstat 1
ss -s
dmesg -T | tail -100
journalctl -u mongod
```

Install approved diagnostic packages during provisioning rather than discovering they are absent during an outage.

## 2.3.15 Reboot Validation

A Linux baseline is not production-ready until persistent configuration survives reboot. Perform a controlled reboot during host validation and confirm database filesystems mount correctly; filesystem mount options remain as designed; readahead remains correct; THP state matches the MongoDB major version; resource limits remain correct; DNS/routing and time synchronization are healthy; ownership and permissions are intact; required agents start; and no unexpected boot/kernel errors appear.

After MongoDB is installed, also validate the intended `mongod` service start policy and database health after a controlled reboot.

## 2.3.16 Production Readiness Checklist

- [ ] Supported Linux distribution, architecture, kernel, and MongoDB version are verified.
- [ ] Current MongoDB production notes and known kernel incompatibilities are checked.
- [ ] Host image/version is recorded and standardized.
- [ ] Dedicated MongoDB service identity is defined.
- [ ] Database and log paths are provisioned with correct ownership.
- [ ] XFS or EXT4 filesystem configuration is validated; XFS is preferred for WiredTiger data-bearing nodes.
- [ ] Access-time mount policy is validated for database storage.
- [ ] Storage latency, IOPS, throughput, and capacity headroom are understood.
- [ ] WiredTiger device readahead is within the approved range or supported by workload testing.
- [ ] Open-file and process limits meet the approved production baseline.
- [ ] Memory and swap policy is validated.
- [ ] WiredTiger cache is not oversized without an explicit reason.
- [ ] THP configuration matches the MongoDB major version.
- [ ] CPU and NUMA topology are reviewed.
- [ ] Stable hostname, DNS, routing, and required ports are validated.
- [ ] Time synchronization is healthy.
- [ ] SELinux/AppArmor/firewall policies are intentionally configured.
- [ ] Approved package repository and version-control policy are ready.
- [ ] OS monitoring and diagnostic tooling are available.
- [ ] Persistent settings are verified after reboot.
- [ ] Configuration is captured in automation/configuration management where practical.

## 2.3.17 SRE/DBRE Operational Guidance

Treat Linux configuration drift as a reliability risk. Hosts in the same MongoDB topology should be comparable enough that an incident on one node can be evaluated against its peers. Differences in kernel level, THP policy, mount options, storage settings, resource limits, or security agents can create intermittent behavior that appears to be a MongoDB defect.

Maintain a machine-readable production baseline and continuously detect deviations. Couple host metrics with MongoDB metrics so responders can distinguish database contention from host memory pressure, I/O saturation, network loss, CPU throttling, or OS-level resource exhaustion.

Kernel, filesystem, storage, THP, NUMA, security, and resource-limit changes should follow the same change-control discipline as important MongoDB configuration changes: documented intent, staged validation, rollback plan, and post-change health verification.

## 2.3.18 Canonical Technical Notes

The canonical edition incorporates the Technical + Source Review and Production + Copyright Review. Key version-sensitive requirements include:

- MongoDB 8.0+ uses THP enabled; MongoDB 7.0 and earlier use THP disabled.
- XFS is strongly recommended for WiredTiger data-bearing nodes; EXT4 remains supported.
- WiredTiger device readahead should normally be 8–32 unless workload testing justifies another value.
- Open-file limits below 64,000 generate a MongoDB startup warning.
- Swap should be minimized and `vm.swappiness` selected according to current MongoDB and workload guidance rather than by an unqualified fleet-wide rule.
- NUMA systems require explicit MongoDB-aware configuration.
- Platform, kernel, filesystem, SELinux, and TCMalloc guidance is version-sensitive and must be revalidated during major upgrades.
