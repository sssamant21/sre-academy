# 2.4 — Filesystem and Storage Preparation

**Workflow Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades

## Purpose

MongoDB storage architecture directly affects database latency, throughput, durability, replication health, recovery time, backup behavior, maintenance operations, and overall service reliability.

For WiredTiger deployments, storage preparation involves substantially more than creating a directory for `dbPath`. Production systems require deliberate decisions about filesystem type, block devices, storage latency, IOPS, throughput, mount configuration, readahead, I/O scheduling, capacity headroom, journaling, snapshots, cloud-storage characteristics, failure domains, monitoring, and recovery.

The storage layer should therefore be treated as a reliability subsystem with measurable service characteristics and documented operational procedures.

---

## 2.4.1 Storage Architecture

A typical MongoDB storage path is:

```text
MongoDB
   │
   ▼
WiredTiger
   │
   ▼
Filesystem
   │
   ▼
LVM / RAID / Volume Layer
   │
   ▼
Block Device
   │
   ▼
Cloud Volume / SAN / Local SSD
   │
   ▼
Physical Storage
```

Performance or reliability problems at any layer can surface as MongoDB symptoms.

For example:

```text
Storage latency increases
        ↓
WiredTiger persistence slows
        ↓
Checkpoint / eviction pressure increases
        ↓
Operation latency increases
        ↓
Secondary may fall behind
        ↓
HA margin decreases
```

SRE/DBRE teams must therefore monitor MongoDB and the underlying storage infrastructure together.

---

## 2.4.2 Filesystem Selection

For production MongoDB on Linux, use a MongoDB-supported filesystem.

The principal choices are:

- XFS
- EXT4

For WiredTiger data-bearing nodes, **XFS is strongly recommended**.

The preferred production standard is therefore:

```text
MongoDB + WiredTiger + Linux
             │
             ├── Strongly preferred → XFS
             │
             └── Supported          → EXT4
```

Standardize filesystem configuration across equivalent replica-set members wherever practical.

Filesystem differences between otherwise equivalent members make performance comparison, capacity analysis, and incident troubleshooting more difficult.

Always verify filesystem requirements against the production notes for the MongoDB major version being deployed.

---

## 2.4.3 Inspect the Storage Baseline

Before installing MongoDB, capture the host's storage topology.

```bash
lsblk -f
df -hT
findmnt
```

Inspect device characteristics:

```bash
lsblk -o NAME,TYPE,SIZE,FSTYPE,MOUNTPOINTS,RA
```

Example:

```text
NAME      TYPE  SIZE FSTYPE MOUNTPOINTS RA
nvme0n1   disk  100G
└─nvme0n1p1
          part  100G xfs    /          128
nvme1n1   disk    1T xfs    /data       16
```

Never assume that the presence of `/data` means the intended volume is mounted there.

Verify explicitly:

```bash
findmnt /data
```

Record:

- device;
- filesystem;
- mount point;
- volume/storage class;
- capacity;
- IOPS;
- throughput;
- readahead;
- I/O scheduler;
- encryption state;
- snapshot capability;
- failure domain.

---

## 2.4.4 MongoDB Data Path

MongoDB's database location is configured with `storage.dbPath`.

Example:

```yaml
storage:
  dbPath: /data/mongodb
```

For production deployments, the database should generally reside on dedicated database storage rather than the operating-system root filesystem.

Example:

```text
/
├── Operating system
├── Packages
└── System logs

/data
└── mongodb
    ├── WiredTiger files
    ├── Collections
    ├── Indexes
    ├── Journal
    └── diagnostic.data
```

Separating database storage provides several operational advantages:

- independent capacity management;
- clearer storage monitoring;
- reduced risk of MongoDB filling `/`;
- simpler volume expansion;
- better performance isolation;
- clearer backup architecture;
- easier troubleshooting.

---

## 2.4.5 Directory Ownership and Permissions

MongoDB must have appropriate access to its database and log directories.

Verify the service account:

```bash
id mongod
```

For custom paths:

```bash
sudo mkdir -p /data/mongodb
sudo chown -R mongod:mongod /data/mongodb
sudo chmod 0750 /data/mongodb
```

Validate the entire path:

```bash
namei -l /data/mongodb
```

The exact account, group, and directory paths depend on the installation method and operating system.

Never use broad permissions such as:

```bash
chmod -R 777 /data/mongodb
```

as a routine troubleshooting technique.

Correct the actual ownership, SELinux/AppArmor policy, ACL, or mount problem instead.

---

## 2.4.6 Persistent Mount Configuration

Database volumes must mount reliably after reboot.

Inspect:

```bash
cat /etc/fstab
findmnt
```

Example conceptual entry:

```text
UUID=<volume-uuid> /data xfs defaults,noatime 0 2
```

The actual options must be validated for the operating system, filesystem, storage platform, and MongoDB version.

Before rebooting:

```bash
sudo mount -a
```

Then verify:

```bash
findmnt /data
df -hT /data
```

A production MongoDB host should not depend on an administrator manually mounting its database volume after restart.

---

## 2.4.7 Mount Options

Review the active mount options rather than relying only on `/etc/fstab`.

```bash
findmnt -no OPTIONS /data
```

Database-storage mount options should be intentionally selected and documented.

Avoid unnecessary metadata activity where supported by the platform. For example, disabling unnecessary access-time updates can reduce filesystem metadata writes.

Do not blindly copy mount options from another database technology or Linux environment.

Changes to filesystem behavior should be validated under representative MongoDB workloads.

---

## 2.4.8 WiredTiger Readahead

MongoDB disk access is generally more random than sequential.

Excessive device readahead can therefore consume storage bandwidth without producing useful database reads.

Inspect:

```bash
lsblk -o NAME,TYPE,SIZE,RA,MOUNTPOINTS
```

or:

```bash
blockdev --getra /dev/<device>
```

For WiredTiger, MongoDB recommends readahead between:

```text
8–32
```

regardless of storage media type unless controlled testing demonstrates a measurable, repeatable, and reliable benefit from another value.

Any approved change must be persisted using the platform-supported mechanism.

After reboot, verify it again.

---

## 2.4.9 I/O Scheduler

Linux I/O scheduler configuration can materially affect database latency.

Inspect:

```bash
cat /sys/block/<device>/queue/scheduler
```

MongoDB's current production guidance recommends:

```text
Virtual/cloud block devices       → none

Physical NVMe/SSD                 → none

Physical spinning disks           → mq-deadline
```

For certain environments with multiple workloads, MongoDB also documents `kyber` as an option.

The exact scheduler must be validated against:

- Linux kernel;
- device technology;
- virtualization layer;
- cloud platform;
- workload characteristics;
- current MongoDB production guidance.

Persist the selected scheduler and verify it after reboot.

---

## 2.4.10 Storage Latency

Storage latency is one of the most important MongoDB infrastructure signals.

Monitor:

- read latency;
- write latency;
- IOPS;
- throughput;
- queue depth;
- device utilization.

A standard Linux diagnostic command is:

```bash
iostat -xz 1
```

Important fields can include:

```text
r/s
w/s
r_await
w_await
aqu-sz
%util
```

Do not diagnose storage health from `%util` alone.

A device can have acceptable utilization while delivering unacceptable latency, or report high utilization while still meeting the workload's service requirements.

Latency must be interpreted together with IOPS, throughput, queue depth, workload, and MongoDB behavior.

---

## 2.4.11 IOPS and Throughput

IOPS and throughput describe different storage constraints.

Small random operations commonly stress IOPS.

Large sequential operations can stress throughput.

MongoDB storage must support more than normal application traffic.

Capacity planning should consider:

```text
Application workload
+
Replication
+
Checkpoints
+
Index builds
+
Backups
+
Initial sync
+
Recovery
+
Maintenance
+
Operational headroom
```

Provisioning only for average application traffic can result in severe degradation during recovery or maintenance.

---

## 2.4.12 Storage Benchmarking

Before accepting a new production storage design, validate it under representative conditions.

Benchmark:

- sustained read IOPS;
- sustained write IOPS;
- mixed workload behavior;
- read latency;
- write latency;
- throughput;
- queue behavior;
- performance under expected database capacity;
- burst versus sustained behavior.

Testing should approximate the expected MongoDB workload rather than relying solely on a storage vendor's advertised maximum.

The goal is not merely to determine peak performance.

The more important question is whether storage can provide **predictable latency at the expected production workload with adequate recovery headroom**.

---

## 2.4.13 SSD and NVMe Storage

SSD-backed storage should normally be preferred for production MongoDB workloads requiring predictable low latency.

Possible technologies include:

```text
Local NVMe
Cloud block SSD
Provisioned-IOPS SSD
Enterprise SAN SSD
```

Evaluate:

- latency;
- IOPS;
- throughput;
- durability;
- persistence;
- snapshot capability;
- replacement behavior;
- failure domain;
- cost;
- recovery architecture.

Local NVMe can provide extremely high performance but may be ephemeral on some platforms.

MongoDB replication and backup design must account for that characteristic.

---

## 2.4.14 Network-Attached Block Storage

Network-attached block storage is common in cloud deployments.

The storage path becomes:

```text
MongoDB
   ↓
Guest filesystem
   ↓
Virtual block device
   ↓
Network
   ↓
Cloud storage service
```

Possible constraints include:

- volume IOPS limit;
- volume throughput limit;
- instance-level storage bandwidth;
- burst-credit exhaustion;
- network congestion;
- storage-service throttling.

A volume can therefore have substantial free disk space while still being performance-saturated.

Monitor both Linux and cloud-provider storage telemetry.

---

## 2.4.15 Remote and Network Filesystems

Do not treat remote filesystems as equivalent to local or block storage simply because they can be mounted by Linux.

If a network filesystem is considered for MongoDB database files, validate:

- MongoDB support requirements;
- filesystem semantics;
- locking behavior;
- durability guarantees;
- latency;
- failure handling;
- recovery behavior;
- snapshot consistency.

For latency-sensitive production `dbPath` storage, local or appropriately provisioned block storage is generally the safer architecture.

Do not deploy a network filesystem merely for administrative convenience.

---

## 2.4.16 RAID Considerations

Where physical infrastructure uses RAID, storage engineering must consider:

- RAID level;
- stripe size;
- filesystem alignment;
- controller cache;
- battery/flash-backed cache;
- disk failure behavior;
- rebuild performance;
- degraded-mode latency.

A RAID rebuild can significantly increase database latency even when the filesystem remains available.

MongoDB production guidance should be reviewed when selecting RAID and filesystem combinations.

---

## 2.4.17 WiredTiger Journaling

WiredTiger uses journaling as part of MongoDB's durability and crash-recovery architecture.

Conceptually:

```text
Application write
      │
      ▼
WiredTiger
   ├──────→ Journal
   │
   └──────→ Checkpointed data
```

Journal behavior must be considered when designing:

- storage latency;
- durability;
- snapshots;
- backup;
- recovery.

Do not delete or manipulate journal files manually as an operating procedure.

---

## 2.4.18 Data and Journal Placement

Data and journal placement is an architectural decision.

They can reside on different storage devices, but doing so changes snapshot and recovery requirements.

If data files and journal files reside on separate volumes, the backup procedure must guarantee a coherent recovery point using MongoDB-supported mechanisms.

For filesystem snapshots with the journal on a separate volume, MongoDB documents procedures that require flushing writes and suspending database writes while the snapshot is captured.

Therefore:

```text
Separate journal storage
        ↓
Potential performance/isolation benefit
        ↓
Additional backup consistency requirements
```

Do not separate the journal solely because that architecture was historically common with another database platform.

Benchmark the benefit and validate recovery.

---

## 2.4.19 WiredTiger Checkpoints

WiredTiger periodically creates checkpoints representing consistent on-disk states.

Storage must therefore absorb both foreground database workload and background persistence activity.

Conceptually:

```text
Application writes
       ↓
WiredTiger cache
       │
       ├── Journal
       │
       └── Checkpoint
              ↓
           Storage
```

Storage latency can therefore affect checkpoint behavior, cache pressure, and application latency.

Correlate storage telemetry with WiredTiger cache and checkpoint metrics during performance incidents.

---

## 2.4.20 Replication and Storage Performance

Replica-set secondaries must persist incoming changes fast enough to remain current.

If a secondary's storage cannot flush dirty data at the rate required by the workload, replication lag can increase.

Example:

```text
Primary
   │
   │ replication
   ▼
Secondary
   │
   ▼
Under-provisioned storage
   │
   ▼
Replication lag
```

MongoDB identifies disk performance as a common replication-lag cause.

Electable secondaries should therefore normally have storage capability comparable to, or better than, the primary.

Do not deliberately build an HA architecture where a secondary cannot sustain the primary's normal write workload.

---

## 2.4.21 Capacity Planning

Disk capacity must account for more than current collection data.

Plan for:

```text
Current data
+
Indexes
+
Oplog
+
Journal
+
Diagnostic data
+
Expected growth
+
Index builds
+
Maintenance
+
Recovery
+
Operational headroom
```

Example:

```text
Current storage consumption     500 GB
Expected 12-month growth        480 GB
Expected operational dataset    980 GB
Maintenance/recovery headroom   additional capacity
```

Do not make disk exhaustion the trigger for expansion.

---

## 2.4.22 Capacity Monitoring

Monitor both:

```bash
df -h
df -ih
```

because filesystem capacity and inode exhaustion are separate failure modes.

Alerting should consider:

- percentage used;
- absolute free capacity;
- growth rate;
- expansion lead time.

A percentage alone can be misleading.

For a 20-TB filesystem:

```text
10% free = 2 TB
```

while on a 200-GB filesystem:

```text
10% free = 20 GB
```

Operational urgency is different.

---

## 2.4.23 Days-to-Full Forecasting

Capacity monitoring should calculate approximate time remaining.

Conceptually:

```text
Days to full =
Remaining usable capacity
─────────────────────────
Average daily growth
```

Example:

```text
Remaining capacity = 400 GB
Growth              = 20 GB/day

Estimated runway ≈ 20 days
```

Growth forecasting gives SRE/DBRE teams substantially more planning time than static utilization alerts alone.

Use both.

---

## 2.4.24 Cloud Storage Limits

Cloud storage often has several independent limits:

```text
Volume capacity
Volume IOPS
Volume throughput
Instance storage bandwidth
Network bandwidth
Burst credits
Provider quotas
```

These must not be treated as a single storage-capacity number.

For example:

```text
Volume IOPS capability       = 20,000
Instance storage capability  = 10,000

Effective ceiling may be constrained by the instance.
```

Monitor the complete path.

A volume can be correctly provisioned while the compute instance remains the bottleneck.

---

## 2.4.25 Storage Failure Domains

MongoDB replication provides redundancy only when replica members do not share an unacceptable common failure domain.

Avoid:

```text
Primary ────┐
Secondary ──┼── Single storage failure domain
Secondary ──┘
```

Prefer:

```text
Primary   → Failure Domain A
Secondary → Failure Domain B
Secondary → Failure Domain C
```

Depending on the platform, failure domains may include:

- physical disk;
- storage array;
- host;
- rack;
- availability zone;
- network path;
- cloud storage subsystem.

Failure-domain design must align with the application's RPO and RTO objectives.

---

## 2.4.26 Filesystem Snapshots

Filesystem or volume snapshots can provide efficient backup mechanisms when implemented correctly.

Snapshot consistency depends on:

- journaling;
- volume layout;
- MongoDB topology;
- storage platform;
- snapshot mechanism.

For straightforward volume-level snapshots of a running WiredTiger instance, follow MongoDB's documented consistency requirements.

When data and journal files span separate volumes, additional coordination is required.

Never assume that two independently initiated storage snapshots represent exactly the same recoverable database point.

Backup procedures must be tested by restoration.

---

A production MongoDB storage dashboard should include:

|---|---|

| Absolute free space | Expansion planning |

| Days to full | Capacity runway |
| Read latency | Read-path health |

| Write IOPS | Workload characterization |

| Replication lag | Secondary persistence health |
| WiredTiger cache pressure | Cache/storage correlation |

## 2.4.28 Storage Troubleshooting Workflow

When MongoDB latency increases:

### Step 1 — Check MongoDB health

Inspect operations, WiredTiger, and replication.

```javascript
db.serverStatus().wiredTiger
```

For replica sets:

```javascript
rs.status()
rs.printSecondaryReplicationInfo()
```

### Step 2 — Check filesystem capacity

```bash
df -hT
df -ih
```

### Step 3 — Check storage latency

```bash
iostat -xz 1
```

### Step 4 — Check system pressure

```bash
vmstat 1
```

### Step 5 — Check kernel/storage errors

```bash
dmesg -T
journalctl -k
```

Look for:

```text
I/O errors
Filesystem errors
Device resets
NVMe errors
Block timeouts
Multipath failures
```

### Step 6 — Check infrastructure metrics

For cloud/SAN environments inspect:

- throttling;
- IOPS consumption;
- throughput consumption;
- queue depth;
- burst credits;
- instance storage bandwidth;
- provider events.

The objective is to determine whether MongoDB is generating storage pressure or waiting on an unhealthy or under-provisioned storage subsystem.

## 2.4.29 Failure Scenario — Disk Full

A typical failure chain is:

```text
Database growth
      ↓
Filesystem utilization rises
      ↓
Capacity warning missed
      ↓
Critical free-space condition
      ↓
MongoDB instability / write impact
      ↓
Application impact
```

During recovery, **do not manually delete MongoDB-managed database files**.

This includes files such as:

```text
collection-*.wt
index-*.wt
WiredTiger*
journal/*
```

Manual deletion can make the database unrecoverable.

Instead:

1. assess replica-set health;
2. stop uncontrolled capacity growth if necessary;
3. determine the cause;
4. expand or safely provide additional storage;
5. validate filesystem integrity;
6. validate MongoDB;
7. validate replication;
8. confirm capacity monitoring.

---

## 2.4.30 Failure Scenario — Storage Latency Spike

Possible symptoms include:

```text
Application latency
Slow writes
Replication lag
Checkpoint pressure
Cache pressure
Slow shutdown
Slow startup
```

Investigate:

```bash
iostat -xz 1
vmstat 1
```

Possible infrastructure causes include:

- cloud-volume throttling;
- burst-credit exhaustion;
- SAN congestion;
- noisy neighbors;
- RAID rebuild;
- failing device;
- network-storage congestion;
- backup or snapshot activity.

Do not immediately change WiredTiger cache sizing or query parameters before validating the storage subsystem.

---

## 2.4.31 Failure Scenario — Slow Secondary

A secondary can fall behind even when network connectivity appears healthy.

Check:

```javascript
rs.printSecondaryReplicationInfo()
```

and correlate the result with storage metrics.

If:

```text
Primary storage latency   → healthy
Secondary storage latency → high
```

the secondary may simply be unable to persist replicated changes quickly enough.

Remediation may require:

- increasing provisioned IOPS;
- increasing throughput;
- upgrading storage;
- upgrading the host/instance;
- eliminating storage contention;
- replacing unhealthy infrastructure.

The visible MongoDB symptom is replication lag, but the root cause can be storage provisioning.

## 2.4.32 Storage Expansion Runbook

Use a controlled expansion workflow:

```text
Capacity alert
      ↓
Validate growth
      ↓
Check backup health
      ↓
Check replica-set health
      ↓
Expand storage
      ↓
Expand partition/LVM if required
      ↓
Expand filesystem
      ↓
Validate MongoDB path
      ↓
Validate latency
      ↓
Validate replication
      ↓
Update capacity forecast
```

Pre-change validation:

```bash
lsblk
findmnt
df -hT
```

Post-change validation:

```bash
lsblk
findmnt
df -hT
df -ih
```

Then validate MongoDB and replica-set health.

Storage expansion procedures are platform-specific. Always use the supported procedure for the operating system and storage provider.

## 2.4.33 Reboot Validation

Storage configuration is not production-ready until it survives reboot.

After a controlled reboot verify:

```bash
lsblk -f
findmnt
df -hT
```

Then verify:

- expected filesystems mounted;
- correct mount points;
- expected mount options;
- readahead;
- I/O scheduler;
- ownership;
- permissions;
- MongoDB service access;
- monitoring agents;
- storage telemetry.

After MongoDB installation, also verify database startup and replica-set health.

## 2.4.35 SRE/DBRE Operational Standard

Production MongoDB storage should be managed as a measurable reliability subsystem.

Operations teams should always be able to answer:

```text
How much capacity remains?

How quickly is it growing?

When will expansion be required?

What read and write latency is MongoDB experiencing?

Are IOPS constrained?

Is throughput constrained?

Is the host/instance limiting the volume?

Is storage being throttled?

Are secondaries keeping up?

Are snapshots affecting performance?

Can storage be expanded without unacceptable downtime?

Are replica members independent of common storage failures?

Can the database actually be restored from backup?
```

The objective is not merely to keep the filesystem online.

The objective is to maintain predictable MongoDB performance, durability, recoverability, and replication health during:

- normal traffic;
- peak traffic;
- maintenance;
- backup;
- index operations;
- initial synchronization;
- failover;
- recovery;
- disaster scenarios.

## 2.4.36 Canonical Technical Notes

The Technical + Source Review and Production + Copyright Review established the following canonical principles:

- XFS is strongly recommended for WiredTiger data-bearing nodes.
- EXT4 remains a supported Linux filesystem where appropriate.
- WiredTiger readahead should normally be configured between 8 and 32 unless repeatable workload testing justifies another value.
- I/O scheduler selection depends on the device and deployment model.
- Storage latency, IOPS, throughput, queueing, and capacity must be evaluated together.
- Secondary storage must be capable of sustaining the replication workload.
- Data and journal placement affects snapshot architecture.
- Multi-volume snapshots require MongoDB-supported consistency procedures.
- Cloud storage limits exist at both volume and compute-instance layers.
- Capacity monitoring should combine utilization, absolute free capacity, growth rate, and time-to-full forecasting.
- MongoDB-managed WiredTiger and journal files must never be manually deleted as routine disk-space remediation.
- Backup success is not sufficient evidence of recoverability; restoration must be tested.
- Version-sensitive filesystem and storage recommendations must be revalidated against current MongoDB production documentation during major upgrades.
