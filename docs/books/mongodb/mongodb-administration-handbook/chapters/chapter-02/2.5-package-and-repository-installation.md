# 2.5 — Package and Repository Installation

**Workflow Status:** Revised Final / Canonical Edition
**Book:** MongoDB Administration Handbook
**Chapter 2:** Installation, Configuration, Patching, and Upgrades
**Baseline:** MongoDB 8.x; revalidate version-sensitive platform and package guidance before deployment.

## Purpose

Installing MongoDB in production is a software supply-chain and lifecycle-management operation, not merely a package-manager command.

A production installation must establish an approved MongoDB distribution and edition; a supported operating-system, CPU, and kernel combination; trusted package repositories; cryptographic verification; deterministic package versions; protection against unintended upgrades; controlled service activation; configuration ownership; repeatable provisioning; drift detection; and post-installation verification.

The desired production model is:

```text
Supported platform
        ↓
Approved MongoDB repository
        ↓
Cryptographic verification
        ↓
Approved package versions
        ↓
Controlled installation
        ↓
Production configuration
        ↓
Explicit service activation
        ↓
Post-install verification
```

A package-manager success message alone does not prove that a MongoDB node is production-ready.

---

## 2.5.1 Production Installation Model

For conventional Linux hosts, prefer the official or approved MongoDB repository, native OS package management, an explicit MongoDB version, configuration management, and independent validation. Native package management provides dependency handling, repository metadata, package inventory, service integration, standard paths, package verification, repeatable upgrades, and automation support.

Archive or tarball installations remain useful in specialized environments, but they transfer more responsibility to operations for binary placement, PATH management, service definitions, dependencies, ownership, upgrades, rollback, and inventory. Standardize one installation model per deployment class.

## 2.5.2 Trusted Package Sources

MongoDB software should originate from an approved source. For normal self-managed deployments, use the official MongoDB repository appropriate for the selected edition, major version, Linux distribution/release, and CPU architecture.

Do not build production installations from unknown third-party repositories, unverified mirrors, manually copied binaries of uncertain provenance, unofficial images, developer workstations, or repositories intended for another OS release. Repository provenance is part of the production baseline.

## 2.5.3 Repository and Signature Verification

Repository trust must be cryptographically validated. Validate the approved repository, signing key, repository metadata, and packages. Do not routinely bypass GPG/signature validation, TLS certificate validation, or repository metadata validation. A signature failure should cause installation automation to fail closed.

## 2.5.4 Community and Enterprise Package Families

MongoDB Community and MongoDB Enterprise Advanced use different package families. MongoDB 8.x packaging separates components such as the metapackage, server, mongos, mongosh, Database Tools, and supporting packages. Community commonly uses the `mongodb-org` family; Enterprise uses corresponding Enterprise packages and may include additional components.

Production automation must explicitly define edition, major version, exact package set, and approved package versions. Do not accidentally combine Community and Enterprise packages. Validate current component names against official documentation for the target platform.

## 2.5.5 OS, CPU, and Kernel Preflight

Before installation inspect:

```bash
cat /etc/os-release
uname -r
uname -m
```

Validate Linux distribution/release, CPU architecture and requirements, MongoDB edition/version, kernel compatibility, and filesystem preparation. Support matrices and production requirements change between releases. Check current MongoDB Production Notes and installation documentation before every production installation and major OS/kernel change. Treat compatibility as a hard prerequisite.

## 2.5.6 Current Platform Baseline Is Version-Sensitive

Supported Linux and architecture combinations change over time. Record the combinations approved by the organization, but revalidate them against current MongoDB documentation during new platform onboarding, MongoDB major upgrades, OS major upgrades, and architecture changes.

## 2.5.7 RPM-Based Installation

Supported RPM-family platforms normally use DNF or YUM with an explicit MongoDB repository definition. Repository definitions normally reside under `/etc/yum.repos.d/`. After configuration inspect repositories with `dnf repolist` or the applicable package-manager command. Inspect candidate MongoDB packages before installation. Repository URL, distribution identifier, signing key, package names, and supported releases must come from current MongoDB documentation.

## 2.5.8 DEB-Based Installation

Supported Debian/Ubuntu-family systems normally use APT. Validate the host with `cat /etc/os-release` and `dpkg --print-architecture`. Repository configuration is typically maintained under `/etc/apt/sources.list.d/`. Refresh metadata and inspect the selected source and candidate package version before installation. Production automation should not depend on an unspecified candidate version when deterministic installation is required.

## 2.5.9 Deterministic Version Installation

Production installation must be deterministic. Install the organization-approved release, not whatever is newest at execution time. Do not assume specifying only a top-level MongoDB metapackage version guarantees that every component resolves exactly as intended. Where official installation documentation requires explicit component versions, specify them. After installation inventory packages and independently verify the `mongod` binary.

## 2.5.10 Package Holds and Version Control

MongoDB packages must not change unexpectedly during routine OS maintenance. APT environments should use an approved package-hold or repository-promotion mechanism when packages must remain fixed. RPM environments should use the organization's approved DNF/YUM version-control strategy. The desired MongoDB package version should be represented in configuration management.

## 2.5.11 OS Patching vs. MongoDB Patching

OS patching and MongoDB patching are related but separate lifecycle operations. They may share a maintenance window, but MongoDB binary changes require MongoDB-specific validation. Do not allow a generic OS patch job to become an uncontrolled MongoDB upgrade mechanism.

## 2.5.12 Installation Paths and Configuration Ownership

Package installation creates or references standard locations for binaries, `mongod.conf`, data, logs, and service definitions. Exact paths depend on platform. Production environments may use custom data or log paths. The package manager should own software installation; configuration management should own production desired state.

## 2.5.13 Configuration Preservation

Package operations can interact with locally modified configuration files. Depending on platform, upgrades may preserve existing configuration, install a new default alongside it, create replacement/save files, or prompt for conflict resolution. After package changes inspect effective MongoDB configuration and package-generated artifacts. Never assume a successful package upgrade means `mongod.conf` is unchanged.

## 2.5.14 systemd Integration and Startup Control

On supported systemd-based Linux distributions inspect MongoDB service integration with:

```bash
systemctl status mongod
systemctl cat mongod
```

Where site-specific changes are required, prefer supported systemd override mechanisms over casually editing vendor-owned unit files. Detailed systemd configuration is covered later in this chapter.

## 2.5.15 Service Activation Must Be Intentional

Do not assume package installation universally starts MongoDB. Explicitly inspect and control service state. Install software, apply `mongod.conf`, validate storage and permissions, apply the security baseline, validate OS settings and effective configuration, and only then explicitly start `mongod`. This prevents initialization with the wrong data path, networking, logging, authentication, or permissions.

## 2.5.16 Binary Version vs. FCV

MongoDB binary version is not Feature Compatibility Version (FCV). A controlled major-version workflow upgrades binaries, validates the cluster, operates through an appropriate burn-in period, and makes a separate explicit FCV decision. Package automation must never automatically raise FCV simply because binaries were upgraded.

## 2.5.17 Major-Version Upgrade Guardrail

Package availability does not authorize a major-version upgrade. MongoDB supports defined upgrade paths and may require sequential progression through supported intermediate versions. Automation must reject arbitrary major-version replacement unless the upgrade path has been validated against official upgrade documentation.

## 2.5.18 Repository and Package Drift

Repository configuration is production configuration. Monitor repository definitions and enforce repository identity, major version, edition, signing configuration, package versions, and package holds/version locks. After installation capture package inventory and verify `mongod --version`. Package inventory and binary version must agree with the approved deployment manifest.

## 2.5.19 Conflicting and Mixed Installations

Before installation identify existing MongoDB-related packages and binaries. Check executable resolution with commands such as `which mongod` and `type -a mongod`. Mixed package, tarball, manually copied binary, and multiple-repository installations create ambiguity in patching, troubleshooting, rollback, PATH resolution, dependencies, and automation. Never remove existing software before determining whether the host contains MongoDB data or a functioning deployment.

## 2.5.20 Restricted and Air-Gapped Environments

Restricted environments should use controlled artifact promotion: official MongoDB source → controlled ingestion → signature/checksum validation → approved internal artifact repository → production. Preserve provenance, package version, signing information, checksums where applicable, and approval metadata. Air-gapping requires stronger supply-chain controls, not weaker ones.

## 2.5.21 Proxy and Certificate Considerations

Repository access may depend on DNS, firewall rules, proxies, enterprise CAs, TLS inspection, system time, and CA bundles. Investigate TLS failures instead of disabling validation. Where enterprise CAs are required, manage them through the organization's approved trust-store process.

## 2.5.22 Installation Automation

Automate production installation wherever practical using configuration management, machine-image pipelines, cloud provisioning, bootstrap automation, or controlled host-management systems. Automation should be idempotent: repeated execution must not unexpectedly change MongoDB major version or FCV, replace production configuration, start an unconfigured service, delete data, or change repositories.

Desired state should explicitly represent edition, major version, approved package version, repository, and service-start policy.

## 2.5.23 Immutable Image Model

Organizations using immutable infrastructure may install MongoDB into validated machine images: approved base OS → security updates → approved MongoDB repository/packages → validation → versioned image. Production changes then replace nodes using validated images rather than repeatedly mutating long-lived servers. Replica-set architecture can support this model when node replacement respects health and redundancy controls.

## 2.5.24 Replica-Set-Aware Package Operations

Package changes to existing replica-set members must respect availability. Validate replica-set health, select one member, perform approved maintenance, start and validate the member, confirm replication health, and only then proceed. Major-version rolling upgrades require additional sequencing covered later in this chapter.

## 2.5.25 Pre-Installation Validation

Before installation validate the approved OS/release, CPU architecture and requirements, current MongoDB Production Notes, kernel compatibility, filesystem/storage preparation, time synchronization, repository connectivity, signing configuration, certificate trust, package-manager health, conflicting packages, existing MongoDB binaries, and available capacity. Failure of a mandatory prerequisite must stop installation.

## 2.5.26 Post-Installation Validation

Immediately after installation run `mongod --version`, verify package inventory using the platform package manager, and inspect service integration with `systemctl cat mongod`. Validate exact binary and package versions, edition, repository source, configuration location, service unit/account, data/log paths, ownership, permissions, and service state. Installation is complete only when the resulting node matches the approved baseline.

## 2.5.27 Troubleshooting Workflow

Troubleshoot in a controlled sequence: platform compatibility → repository configuration → DNS/network/proxy → TLS/certificate trust → signing verification → package dependencies → version selection → filesystem/capacity → service integration. Avoid changing multiple controls simultaneously and preserve package-manager and automation logs.

## 2.5.28 Failure Scenario — Repository Unreachable

Investigate DNS, network, proxy, TLS, repository URL, OS/release selection, and vendor availability. Do not immediately substitute an unapproved repository.

## 2.5.29 Failure Scenario — Signature Verification Failure

Possible causes include incorrect signing key, repository configuration error, key rotation, stale metadata, corrupt artifacts, incorrect system time, or repository-integrity problems. Stop installation, validate repository identity/signing configuration/time/TLS, refresh trusted metadata, and retry only after trust is restored. Do not disable signature verification.

## 2.5.30 Failure Scenario — Unsupported Platform

If preflight detects an unsupported OS, release, CPU, architecture, or kernel combination, stop installation. Check current MongoDB documentation and select a supported platform or explicitly approved remediation. Compatibility failures must not be downgraded to informational warnings.

## 2.5.31 Failure Scenario — Wrong MongoDB Version

If the installed version differs from the approved release, do not admit the node to production. Determine why selection failed, inspect repositories/version controls, and determine whether `mongod` started or opened database files. Once binaries have operated against database files, the problem may no longer be a simple package replacement.

## 2.5.32 Failure Scenario — Wrong Configuration Used

If MongoDB starts with default or unintended configuration, follow the incident procedure to stop the affected service and determine which configuration loaded, whether files were created, whether the intended data path was touched, which interfaces were exposed, and whether authentication/security settings were active. Correct and validate configuration before restarting.

## 2.5.33 Failure Scenario — Configuration Changed During Package Maintenance

After package maintenance compare effective configuration with the approved baseline and inspect service definitions and package-manager-generated alternate/saved configuration artifacts. Do not return the node to service until configuration integrity is confirmed.

## 2.5.34 Package Rollback Is Not Database Downgrade

Reinstalling an older package is not equivalent to a safe MongoDB downgrade. Downgrade eligibility can depend on source/target versions, FCV, features enabled, metadata changes, and documented downgrade support. Never assume replacing packages safely reverses a MongoDB upgrade. Detailed downgrade planning is covered later in this chapter.

## 2.5.35 Production Installation Runbook

Use this controlled sequence:

```text
Confirm approved MongoDB release
             ↓
Validate OS / CPU / kernel
             ↓
Validate current Production Notes
             ↓
Validate filesystem/storage
             ↓
Validate repository trust
             ↓
Configure approved repository
             ↓
Inspect package candidates
             ↓
Install explicit approved versions
             ↓
Apply package hold/version control
             ↓
Verify package inventory and binary
             ↓
Apply production mongod.conf
             ↓
Validate service, paths, permissions, security
             ↓
Explicitly start MongoDB
             ↓
Validate MongoDB health
             ↓
Record deployment state
```

For an existing replica set, insert topology and redundancy checks before and after each member's maintenance operation.

## 2.5.37 SRE/DBRE Operational Standard

Operations should always be able to answer: What MongoDB version and edition are approved and installed? Which component packages are installed and where did they originate? Were they cryptographically verified? Is the OS/CPU/kernel combination supported? Can routine OS patching alter MongoDB, and how is that prevented? Can the node be rebuilt identically? Who owns `mongod.conf`? Can package maintenance alter configuration? Can `mongod` start before production configuration is ready? Can repository drift be detected? Does binary installation change FCV? What is the supported upgrade path? What happens if installation fails halfway through?

A production installation is successful when software state is trusted, supported, deterministic, reproducible, observable, and recoverable.

## 2.5.38 Canonical Technical Notes

The Draft, Technical + Source Review, and Production + Copyright Review establish these canonical principles:

- Prefer official/approved MongoDB repositories and native package management for conventional Linux deployments.
- Validate repository and package authenticity cryptographically.
- Explicitly select MongoDB edition and major version.
- Use deterministic component package versions where required.
- Prevent routine OS maintenance from silently changing MongoDB.
- Validate OS, CPU architecture/requirements, and current kernel compatibility before installation.
- Treat current MongoDB Production Notes as part of installation preflight.
- Treat repository configuration as production desired state.
- Keep package management and production configuration ownership separate.
- Explicitly control MongoDB service activation.
- Independently verify installed packages and `mongod` binary version.
- Avoid mixed package/tarball/manual binary installations.
- Maintain artifact provenance in restricted environments.
- Keep MongoDB binary version and FCV as separate lifecycle controls.
- Never allow package automation to automatically raise FCV.
- Validate supported major-version upgrade paths before replacing binaries.
- Package rollback must not be confused with MongoDB database downgrade.
- Apply package operations to replica-set members with topology-aware maintenance procedures.
- Revalidate version-sensitive platform and packaging recommendations whenever MongoDB or the OS baseline changes.
