# 2.6 — `mongod.conf` Architecture

**Workflow Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x; version-sensitive configuration behavior must be revalidated against the target MongoDB release.

## Purpose

`mongod.conf` is one of the most important operational artifacts in a self-managed MongoDB deployment.

It controls or participates in the configuration of storage, logging, networking, TLS, authentication and authorization, replication, sharding roles, process management, diagnostic profiling, selected server parameters, and Enterprise-specific capabilities where applicable.

A production `mongod.conf` must therefore be treated as **version-controlled infrastructure configuration**, not as an independently maintained text file on each server.

The production architecture is:

```text
Version-controlled desired state
            ↓
Version-specific validation
            ↓
Controlled configuration generation
            ↓
Predeployment validation
            ↓
Deployment
            ↓
mongod startup
            ↓
Runtime verification
            ↓
Configuration drift detection
```

A syntactically valid configuration is not necessarily a safe production configuration.

---

## 2.6.1 Configuration Model

MongoDB server options can generally be supplied using command-line arguments or a configuration file.

For production deployments, prefer a controlled configuration file because it provides readability, repeatability, reviewability, version control, automation, rollback, and drift detection.

Linux package-manager installations normally use:

```text
/etc/mongod.conf
```

as the primary packaged configuration location.

The exact effective configuration must still be verified because service definitions or startup arguments may reference another file or provide overrides.

The production objective is:

```text
Desired configuration
        ↓
Deployed configuration
        ↓
Startup configuration
        ↓
Runtime state
```

These layers should agree unless an explicitly documented runtime difference exists.

## 2.6.2 YAML and File Encoding

MongoDB configuration files use YAML syntax.

For example:

```yaml
storage:
  dbPath: /data/mongodb
```

YAML indentation is significant.

Production configuration generation must protect against incorrect indentation, tab-based indentation, duplicate or misplaced keys, incorrect value types, unsupported options, and accidental formatting corruption.

For the MongoDB 8.x baseline used by this handbook, configuration-file encoding requirements must also be respected. Keep the deployed configuration ASCII-safe unless current target-version documentation explicitly establishes otherwise.

Therefore the operational model is:

```text
mongod.conf
=
valid YAML
+
spaces for indentation
+
supported encoding
+
MongoDB-valid options
```

Do not place decorative Unicode symbols, smart quotes, or copied formatting into the actual production configuration artifact.

## 2.6.3 Configuration Ownership and Layering

Every production MongoDB node should have one authoritative desired-state source.

Recommended architecture:

```text
Git / controlled configuration repository
                 ↓
Configuration automation
                 ↓
/etc/mongod.conf
                 ↓
mongod
```

Avoid independent manual configuration such as:

```text
Node 1 → engineer modification
Node 2 → different engineer modification
Node 3 → automation
```

This creates uncontrolled topology drift.

Large estates may use layered configuration:

```text
Organization baseline
        +
Environment baseline
        +
Cluster configuration
        +
Node-specific values
        =
Effective configuration
```

Examples of organization-wide settings include logging standards, security standards, TLS policy, and monitoring requirements.

Cluster-level values may include replica-set name, sharding role, and security mode.

Node-specific configuration should be limited to genuine node differences such as addresses or storage paths.

## 2.6.4 Major Configuration Domains

A production configuration commonly contains domains such as:

```text
mongod.conf
    │
    ├── systemLog
    ├── storage
    ├── processManagement
    ├── net
    ├── security
    ├── replication
    ├── sharding
    ├── operationProfiling
    ├── setParameter
    └── auditLog          # Enterprise where supported
```

Not every deployment requires every section.

Prefer minimal, explicit, documented configuration over a large configuration containing historical tuning parameters whose purpose is no longer understood.

Configuration options are version-sensitive. A setting valid for an older MongoDB release may be renamed, removed, deprecated, unnecessary, or behave differently in a later release.

## 2.6.5 `systemLog` Architecture

The `systemLog` section controls MongoDB diagnostic logging.

A simplified file-based model is:

```yaml
systemLog:
  destination: file
  path: /log/mongodb/mongod.log
  logAppend: true
```

The exact configuration must match the deployment's package, service, filesystem, and logging architecture.

Production logging must define destination, ownership, rotation, retention, central collection, capacity monitoring, and alerting.

A MongoDB node should not lose availability because unmanaged diagnostic logs fill a filesystem.

### Log rotation

MongoDB supports log-rotation behavior including `rename` and `reopen`.

When an external Unix/Linux `logrotate` architecture uses MongoDB's documented `reopen` model, configure the associated append behavior as required by the target MongoDB release.

The important production principle is one clearly defined rotation architecture. Avoid multiple uncontrolled systems manipulating the same log file.

### Structured diagnostic information

Modern MongoDB diagnostic logging contains structured information useful for severity analysis, component filtering, message identifiers, incident correlation, and performance troubleshooting.

Central logging should preserve useful structured metadata wherever the ingestion platform supports it.

## 2.6.6 `storage` and `dbPath`

The `storage` section controls storage-related behavior.

A production deployment commonly defines an explicit data path:

```yaml
storage:
  dbPath: /data/mongodb
```

The configured path must agree with filesystem preparation, mount configuration, storage class, ownership, permissions, capacity monitoring, backup architecture, and recovery procedures.

### `dbPath` is a critical identity setting

Treat `storage.dbPath` as a critical configuration property.

Changing `/data/mongodb` to `/var/lib/mongo` does **not** move MongoDB data. It changes where MongoDB expects its database files.

A mismatch can cause apparent missing data, initialization of an unintended directory, permission errors, startup failure, and unexpected replica synchronization.

A `dbPath` change requires an explicit migration procedure.

## 2.6.7 WiredTiger Configuration

WiredTiger is the default storage engine for contemporary MongoDB deployments.

WiredTiger-related configuration can affect cache behavior, compression, journal behavior, and engine-specific options.

The correct production tuning model is:

```text
MongoDB default
       ↓
Measure workload
       ↓
Identify bottleneck
       ↓
Validate supported setting
       ↓
Test
       ↓
Change
       ↓
Measure again
```

Do not copy storage-engine tuning parameters from unrelated deployments or older MongoDB releases.

### WiredTiger cache

For the MongoDB 8.x baseline, MongoDB derives a default WiredTiger cache from available memory. The current documented formula should be checked against the exact target release before encoding it into operational tooling.

Increasing the cache without understanding the complete MongoDB memory model can reduce memory available for filesystem cache, connections, aggregation, indexes and supporting structures, MongoDB process overhead, and operating-system processes.

Containerized environments require particular attention because host memory and effective container memory limits may differ.

Leave cache sizing at MongoDB's supported default unless measured workload evidence justifies an override.

### Compression

MongoDB/WiredTiger supplies release-specific defaults for collection, index, journal, and time-series compression.

Treat these as defaults rather than universal tuning recommendations. Understand current default before overriding current default.

### Historical configuration

Do not carry obsolete storage settings forward.

For example, older configurations may contain journal-enablement options that are no longer applicable to modern WiredTiger releases.

Every major-version upgrade must validate the storage configuration against the target release.

## 2.6.8 Network Configuration

The `net` section defines MongoDB network behavior.

Typical properties include:

```yaml
net:
  port: 27017
  bindIp: <approved-addresses>
```

MongoDB network exposure should follow minimum required exposure rather than listen on every interface for convenience.

Relevant controls include `net.bindIp` and `net.bindIpAll`.

Production network security should combine MongoDB bind configuration, host firewall, cloud/network security controls, routing and segmentation, authentication, and TLS.

Changing MongoDB's default port is not a substitute for these controls.

## 2.6.9 TLS Architecture

Use modern `net.tls.*` configuration terminology for current MongoDB deployments.

A simplified architecture is:

```yaml
net:
  tls:
    mode: requireTLS
    certificateKeyFile: /secure/path/server.pem
    CAFile: /secure/path/ca.pem
```

Exact TLS options, certificate requirements, and supported modes must be validated against the target MongoDB release.

Production TLS architecture should define TLS mode, server identity, CA trust, certificate lifecycle, private-key protection, client compatibility, certificate rotation, and expiration monitoring.

Where TLS is the required production end state, the final configuration should enforce that requirement rather than leaving optional plaintext connectivity indefinitely.

## 2.6.10 Security and Internal Authentication

A production MongoDB deployment requires an explicit security architecture.

For example:

```yaml
security:
  authorization: enabled
```

Security configuration may also control member-to-member authentication.

Replica sets and sharded clusters can use mechanisms such as keyfiles, X.509 certificates, and other supported Enterprise mechanisms.

### Keyfiles

Keyfiles are secret material.

They must remain outside ordinary source control, be distributed securely, use restrictive filesystem permissions, be readable by the MongoDB service account, and support an approved rotation process.

On Unix-like systems, MongoDB requires restrictive keyfile permissions and does not accept group/world-accessible keyfiles under the documented security model.

### X.509

MongoDB can use X.509 certificates for internal cluster authentication.

A representative architecture may involve:

```yaml
security:
  clusterAuthMode: x509

net:
  tls:
    certificateKeyFile: /secure/path/server.pem
    clusterFile: /secure/path/cluster.pem
    CAFile: /secure/path/ca.pem
```

Exact certificate identity, EKU, trust, and membership requirements must be validated against current MongoDB documentation.

Detailed authentication and PKI architecture belongs in the security chapters.

## 2.6.11 Replication and Sharding Identity

Replica-set members require a consistent replica-set identity:

```yaml
replication:
  replSetName: production-rs
```

Treat `replication.replSetName` as a critical topology property.

A typo or accidental change can prevent a member from participating in the intended replica set.

Equivalent members should normally share the same security baseline, logging policy, storage architecture, replica-set identity, and operational defaults while keeping legitimate node-specific values explicit.

### Sharding

Processes in a sharded cluster can require role-specific configuration identifying shard-server or config-server behavior.

Sharding-role settings are critical identity settings.

Do not reuse a generic replica-set configuration for a config-server replica set or shard without validating its required role.

## 2.6.12 systemd and `processManagement`

On systemd-managed Linux hosts, the MongoDB package configuration, service unit, environment overrides, and `mongod.conf` form one integrated startup architecture.

Do not independently change `processManagement` settings, `systemLog.path`, `storage.dbPath`, or package service behavior without validating their interaction with the vendor-packaged systemd integration.

Inspect:

```bash
systemctl cat mongod
systemctl status mongod
```

The operational objective is to prove the expected `mongod` binary, expected configuration file, expected service account, and expected service behavior.

Detailed process management is covered in Section 2.9.

## 2.6.13 Profiling and Diagnostic Configuration

MongoDB provides database profiling capabilities through `operationProfiling`.

Relevant settings can include:

```yaml
operationProfiling:
  mode: ...
  slowOpThresholdMs: ...
  slowOpSampleRate: ...
  filter: ...
```

Profiling should be treated as a diagnostic capability, not automatically as an always-on observability solution.

Aggressive profiling can add overhead, generate additional writes, consume storage, and capture sensitive query information.

The MongoDB 8.x baseline has documented defaults for profiling mode and slow-operation thresholds, but these values are version-sensitive.

Operational thresholds should align with application SLO, workload behavior, diagnostic requirements, and observability cost.

## 2.6.14 `setParameter` and Version-Sensitive Settings

Selected server parameters can be configured through:

```yaml
setParameter:
  <parameter>: <value>
```

These settings vary substantially in supportability, lifecycle, restart requirements, runtime mutability, release compatibility, and operational risk.

Every non-default server parameter should have an owner, reason, authoritative source, target versions, expected effect, monitoring, and rollback procedure.

Do not populate `setParameter` using undocumented or copied internet tuning recommendations.

Runtime server parameters are covered in Section 2.15.

### Version compatibility

Never assume an old `mongod.conf` is a valid new-version `mongod.conf`.

During every major upgrade:

1. inventory non-default options;
2. validate each option against the target version;
3. identify removed or renamed settings;
4. identify changed defaults;
5. remove obsolete workarounds;
6. test the resulting configuration before rollout.

## 2.6.15 Secrets and Configuration Expansion

`mongod.conf` should not be treated as a general-purpose secrets store.

Separate configuration repository non-secret desired state from secrets-platform or protected-filesystem secret material.

Sensitive assets include keyfiles, TLS private keys, certificate passphrases, and external credentials.

MongoDB supports configuration expansion mechanisms for externally sourced values in supported releases.

Where these mechanisms are used, their corresponding startup controls must also be configured correctly. A configuration containing expansion directives without the required expansion mode can fail during startup.

Configuration expansion is an optional architectural mechanism, not a universal secrets solution.

Evaluate it against secrets-management architecture, service supervision, auditing requirements, failure behavior, and CI/CD controls.

## 2.6.16 Configuration Permissions

The MongoDB service account must be able to read the deployed configuration while unauthorized users must not be able to modify it.

Inspect:

```bash
ls -l /etc/mongod.conf
```

The objective is that `mongod` can read it, approved automation/administrators can manage it, and unprivileged users cannot modify it.

Apply stricter permissions to secret-bearing artifacts such as keyfiles and private keys.

## 2.6.17 Predeployment Validation

A production change should never follow edit → restart → see what happens.

Use prepare candidate → review diff → validate → test → controlled rollout.

MongoDB provides a useful configuration parsing mechanism through:

```bash
mongod --config /etc/mongod.conf --outputConfig
```

for supported releases.

This can help detect configuration parsing problems before production startup.

### Security warning

Where external configuration expansion is used, resolved output can contain sensitive values.

Therefore `--outputConfig` provides useful validation but can also create potential secret exposure.

Do not indiscriminately send its output to CI logs, chat systems, tickets, monitoring platforms, or shared build artifacts.

A successful parse also does not prove that the configuration is operationally safe. Storage, networking, security, topology, and permissions still require independent validation.

## 2.6.18 Runtime Configuration Verification

The configuration file on disk is only one source of evidence.

MongoDB provides runtime startup-option introspection through:

```javascript
db.adminCommand({ getCmdLineOpts: 1 })
```

Use this to help verify the options actually parsed for the running process.

The verification model is desired state → deployed file → systemd/startup command → `getCmdLineOpts` → runtime parameters → cluster parameters.

No single layer proves the complete runtime state.

For systemd deployments also inspect:

```bash
systemctl cat mongod
```

This catches situations where the process uses a different configuration file, command-line overrides, unexpected environment settings, or a different binary.

## 2.6.19 Restart vs. Runtime Lifecycle

MongoDB settings do not all share the same lifecycle.

Conceptually:

```text
Configuration property
      │
      ├── Startup-only
      │       ↓
      │    Restart
      │
      └── Runtime-capable
              ↓
          Dynamic change
```

Editing `mongod.conf` does not automatically change a running MongoDB process.

Likewise, a runtime change may not persist across restart unless desired state is updated appropriately.

Section 2.17 covers restart-required versus runtime configuration in detail.

## 2.6.20 Configuration Drift

Configuration drift exists whenever desired state differs from actual state.

Production MongoDB has several drift classes: repository drift, file drift, startup-option drift, runtime parameter drift, and cluster-parameter drift.

Common causes include emergency manual edits, incomplete automation, failed deployments, package changes, node replacement, systemd overrides, and runtime server changes.

File comparison alone cannot detect all runtime drift.

### Fingerprinting

Two useful approaches are exact artifact hash, which proves exact file identity, and normalized semantic comparison, which detects meaningful configuration differences.

Choose according to the objective.

Never expose secrets while normalizing, hashing, or exporting configuration state.

## 2.6.21 Promotion and Rollback

Configuration changes should move through controlled environments:

```text
Source control
     ↓
Peer review
     ↓
Development/test
     ↓
Staging
     ↓
Production canary/member
     ↓
Health validation
     ↓
Controlled rollout
```

For replica sets requiring restarts, validate replica health, change one member, validate startup, validate replication, validate monitoring/application behavior, and only then proceed.

Do not continue if remaining healthy members cannot maintain required quorum or availability.

### Rollback

Every production configuration change should define the previous configuration version, rollback trigger, restart requirement, topology prerequisites, and validation criteria.

However, previous configuration is not automatically a safe rollback.

An older configuration may be incompatible after MongoDB binary upgrades, certificate changes, topology changes, storage migrations, or removal of old configuration options.

Rollback must be compatible with the current binary and cluster state.

## 2.6.22 Failure Scenarios

### YAML or configuration syntax error

Preserve startup logs, inspect the configuration error, compare the deployment diff, validate YAML and MongoDB options, correct or restore the candidate, and retry only after validation.

### Unsupported or removed parameter

Read the exact startup error, identify the option, check target-version documentation, correct configuration, and validate. Do not repeatedly restart without addressing the underlying configuration problem.

### Wrong `dbPath`

Verify configured `dbPath`, mounted filesystem, expected production data, and actual WiredTiger files. Do not allow substantial new writes until the discrepancy is understood.

### Wrong replica-set identity

Compare `mongod.conf`, expected topology, and replica-set configuration. Treat identity correction as a topology operation.

### Incorrect network binding

Inspect MongoDB bind configuration, OS listening sockets, host firewall, cloud network controls, routing, and DNS. Do not automatically solve connectivity by exposing MongoDB on every interface.

### Drift between members

Determine the intended state, identify legitimate node-specific differences, restore desired state, and roll changes safely.

### Secret or certificate inaccessible

Possible symptoms include startup failure, TLS initialization errors, keyfile authentication failure, permission errors, or configuration-expansion failure.

Validate that the reference/file exists, the service account can access it, permissions are correct, format is valid, certificate/key is current, and the secret backend is reachable where required.

Do not broadly weaken permissions as a troubleshooting shortcut.

### Candidate validates but runtime differs

A configuration may parse correctly while systemd or startup arguments alter runtime behavior.

Inspect `systemctl cat mongod`, inspect process invocation, run `getCmdLineOpts`, compare against desired state, identify the override, and correct the authoritative configuration layer.

### Restart failure after configuration change

Preserve logs, identify the change, assess rollback compatibility, restore safe known-good state, restart, validate MongoDB, and validate replication. Maintain replica-set quorum and required redundancy throughout the response.

## 2.6.23 Production Configuration Change Runbook

Use the following workflow:

```text
Identify requirement
        ↓
Identify target MongoDB version
        ↓
Check current documentation
        ↓
Classify change risk
        ↓
Modify desired-state source
        ↓
Peer review
        ↓
Validate YAML / encoding / options
        ↓
Run safe configuration preflight
        ↓
Test outside production
        ↓
Capture cluster health baseline
        ↓
Deploy to one controlled member
        ↓
Restart if required
        ↓
Verify startup
        ↓
Run runtime configuration verification
        ↓
Verify replication
        ↓
Verify security / networking / storage
        ↓
Verify application and monitoring
        ↓
Continue controlled rollout
        ↓
Run drift validation
        ↓
Record completed change
```

Critical identity changes require dedicated architecture-specific procedures rather than this generic runbook alone.

## 2.6.25 SRE/DBRE Operational Standard

For every production MongoDB node, operations should be able to answer: Where is the authoritative configuration? Which version is deployed? Which MongoDB release is it intended for? Which configuration file is `mongod` actually reading? Which startup arguments are active? Who changed the desired state? What differs between replica-set members? Which settings require restart? Which settings can change dynamically? Are runtime parameters different from desired state? Which values are security-sensitive? Are non-default parameters documented? Does `dbPath` match mounted production storage? Does `replSetName` match the intended topology? Is network exposure intentional? Are TLS and internal-authentication assets valid? Can configuration drift be detected automatically? Can the previous configuration be restored safely? Can the node be rebuilt entirely from controlled desired state?

The desired production state is version controlled, version validated, minimal, secure, reproducible, topology aware, runtime verifiable, drift detectable, and recoverable.

## 2.6.26 Canonical Technical Notes

The Draft, Technical + Source Review, and Production + Copyright Review establish these canonical principles:

- Prefer configuration files over extensive production command-line configuration.
- Treat `/etc/mongod.conf` as the normal Linux package configuration location while verifying the actual service invocation.
- Validate YAML, supported encoding, and MongoDB option semantics before deployment.
- Treat the configuration repository as authoritative desired state.
- Keep environment and node-specific differences explicit.
- Minimize unexplained non-default settings.
- Treat `storage.dbPath` as a critical storage identity property.
- Do not confuse changing `dbPath` with moving data.
- Keep WiredTiger defaults unless measured evidence justifies overrides.
- Revalidate WiredTiger settings and defaults against each target release.
- Restrict network exposure to required interfaces.
- Use modern `net.tls.*` terminology for current deployments.
- Protect keyfiles, certificate private keys, and other secrets outside ordinary source control.
- Treat replica-set names and sharding roles as critical topology identity.
- Validate `processManagement`, storage paths, log paths, and systemd/package integration together.
- Use profiling carefully because of overhead and diagnostic-data sensitivity.
- Document every non-default server parameter.
- Never carry an old `mongod.conf` unchanged into a major-version upgrade without validation.
- Use MongoDB-native configuration parsing/preflight capabilities where appropriate.
- Protect configuration output when expansion can resolve secrets.
- Verify active startup options using runtime introspection such as `getCmdLineOpts`.
- Distinguish repository, file, startup, runtime-server, and cluster-parameter drift.
- Roll restart-required changes through replica-set members safely.
- Do not assume an older configuration is automatically a safe rollback after binary or topology changes.
- Treat Enterprise-only configuration capabilities, including auditing where applicable, distinctly from Community functionality.
