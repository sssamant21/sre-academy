# 2.7 — Network Configuration

**Workflow Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x; version-sensitive networking, TLS, connection, and topology behavior must be revalidated against the exact target MongoDB release and driver versions.

## Purpose

MongoDB network configuration determines how applications, administrators, monitoring systems, backup platforms, automation, replica-set members, `mongos` routers, config servers, and shard servers communicate.

Production networking must satisfy two objectives simultaneously:

```text
Required connectivity
        +
Minimum necessary exposure
```

The production architecture is:

```text
Applications / Operations / Cluster Members
                    ↓
             DNS / Discovery
                    ↓
          Routing / Segmentation
                    ↓
        Firewall / Security Policy
                    ↓
           MongoDB Bind Policy
                    ↓
                  TLS
                    ↓
        Authentication / Authorization
                    ↓
          MongoDB Topology Discovery
                    ↓
              mongod / mongos
```

A running `mongod` process does not prove that the MongoDB service is reachable, secure, or healthy.

Production network health requires the database and its surrounding network dependencies to function together.

## 2.7.1 Purpose and Network Architecture

MongoDB communication paths vary by topology.

A replica-set deployment commonly contains:

```text
                    ┌────────────────┐
                    │ Applications   │
                    └───────┬────────┘
                            │
                            ▼
                     MongoDB Driver
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           mongod         mongod        mongod
           Member 1       Member 2      Member 3
              ▲             ▲             ▲
              └──── replication / ────────┘
                    heartbeat traffic

        Monitoring / Backup / Operations
                     │
                     └──────► MongoDB
```

A sharded deployment adds additional communication paths:

```text
Applications
     ↓
   mongos
     ↓
 ┌───┴─────────────┐
 ↓                 ↓
Shard A           Shard B
 ↓                 ↓
Replica Set      Replica Set
      \           /
       \         /
       Config Server
        Replica Set
```

Every required path should be documented.

Operators should be able to identify source, destination, port, protocol, DNS dependency, TLS requirement, authentication requirement, firewall/security policy, expected latency, and monitoring coverage. Unknown communication paths are an operational risk.

## 2.7.2 Production Network Principles

The production standard is:

```text
Private by default
+
Least privilege
+
Stable identity
+
Encrypted where required
+
Authenticated
+
Topology aware
+
Observable
+
Capacity planned
+
Failure aware
```

Avoid architectures based on:

```text
Public database exposure
+
0.0.0.0/0 firewall rules
+
bind-all by convenience
+
unencrypted traffic
+
weak authentication
```

Self-managed production MongoDB nodes should normally reside on private networks.

Any direct public exposure should require explicit architecture approval, security review, documented business justification, strong authentication, TLS, restricted network policy, monitoring, and documented compensating controls.

MongoDB technically supporting a listener on an address does not make that address appropriate for production exposure.

## 2.7.3 Bind Addresses, IPv4, and IPv6

MongoDB network listener configuration is primarily controlled through the `net` configuration domain.

```yaml
net:
  port: 27017
  bindIp: 127.0.0.1,10.20.30.15
```

`net.bindIp` determines the addresses/interfaces on which the MongoDB process accepts network connections. The production objective is required interfaces only with explicit bind configuration.

A node might require connectivity from applications, replica-set peers, `mongos`, monitoring, backup systems, and administrative networks. All required paths must be considered before changing binding.

### Localhost defaults

Package-managed MongoDB installations commonly start with localhost-oriented binding for safety. A locally successful `mongosh` therefore does not prove remote connectivity. Always verify the effective production binding.

### `bindIpAll`

MongoDB provides:

```yaml
net:
  bindIpAll: true
```

for architectures intentionally requiring listening on all applicable interfaces. Do not use this merely because a client cannot connect.

Instead diagnose MongoDB binding, OS listener state, routing, firewall policy, cloud network policy, DNS, TLS, and client configuration. `bindIpAll` expands network exposure and does not replace network security. Use one intentional binding architecture rather than conflicting bind definitions.

### IPv6

IPv6 requires explicit consideration. For supported MongoDB releases, IPv6 configuration includes:

```yaml
net:
  ipv6: true
```

where IPv6 is required.

Validate IPv6 enablement, bind configuration, routing, firewall rules, DNS AAAA records, TLS identity, and client support as one architecture. For the MongoDB 8.x baseline, the documented `net.ipv6` default is disabled. Revalidate this against the exact target release.

## 2.7.4 Ports and Listener Configuration

MongoDB uses role-dependent default ports.

| MongoDB role | Default port |
|---|---:|
| Standard `mongod` | `27017` |
| `mongos` | `27017` |
| Shard-server `mongod` | `27018` |
| Config-server `mongod` | `27019` |

Explicit configuration may use:

```yaml
net:
  port: 27017
```

Production estates should standardize ports where practical. This simplifies firewall rules, monitoring, automation, documentation, and troubleshooting.

MongoDB can also support configurations in which the operating system selects a port. Such behavior is generally unsuitable for normal production endpoints requiring predictable discovery and security policy.

A non-default port is not a security control. Changing `27017` to another number does not replace TLS, authentication, authorization, segmentation, or firewall policy.

### Runtime listener verification

After starting MongoDB, verify the actual listener, for example:

```bash
ss -lntp
ss -lntp | grep 27017
```

Validate the chain from `mongod.conf`, to startup options, to OS listener, to remote connectivity.

## 2.7.5 Private Placement and Segmentation

Production MongoDB should normally use private network placement.

```text
Internet
   │
   X
   │
Approved application ingress
            ↓
Private application network
            ↓
Private MongoDB network
```

Administrative access should use controlled mechanisms such as bastion hosts, VPN, private connectivity, approved management networks, or zero-trust access platforms.

Database traffic can be logically separated by purpose for application access, administration, monitoring, backup, and internal cluster communication. Physical interface separation is not always necessary; policy separation is.

## 2.7.6 Firewall and Cloud Network Controls

Network policy should answer who may connect to which MongoDB node, on which port, and for which purpose. Use least-privilege rules and avoid broad access unless the architecture genuinely requires it.

Defense in depth can include MongoDB bind configuration, host firewall, subnet/VPC/VNet policy, cloud security controls, routing, TLS, and authentication.

Cloud implementations may use AWS Security Groups, Azure Network Security Groups, Google Cloud firewall policies, or Kubernetes NetworkPolicy. Cloud-specific implementation belongs in the corresponding cloud handbook.

Temporary troubleshooting rules must have an owner, reason, expiration, and removal verification. Temporary unrestricted access should never quietly become permanent architecture.

## 2.7.7 DNS and Replica-Set Identity

DNS is a production MongoDB dependency.

Modern MongoDB replica-set and sharded-cluster architectures should use stable, resolvable DNS hostnames for member identity rather than treating ephemeral IP addresses as durable topology identifiers.

```text
mongo01.prod.example
mongo02.prod.example
mongo03.prod.example
```

The production relationship is stable DNS identity → MongoDB topology identity → TLS certificate identity → driver discovery.

Modern MongoDB releases have stricter hostname and split-horizon validation than older releases. Do not design new production replica sets around IP-only member identity. Validate target-version hostname requirements before deployment or upgrade.

A healthy MongoDB process can become operationally inaccessible if required DNS resolution fails. Monitor critical database DNS names.

Review forward lookup, reverse lookup where required, TTL, private DNS zones, split-horizon behavior, cross-network resolution, SRV records, TXT records where used, and certificate names.

Useful validation commands include:

```bash
getent hosts mongo01.prod.example
dig mongo01.prod.example
dig -x <ip-address>
```

## 2.7.8 Seed Lists and SRV Discovery

MongoDB drivers perform topology discovery. A standard connection can begin with multiple seed hosts:

```text
mongodb://mongo01,mongo02,mongo03/...
```

Conceptually, seed hosts bootstrap initial connection and MongoDB topology discovery; they should not be confused with the complete steady-state topology maintained by the driver.

MongoDB also supports SRV-style connection strings:

```text
mongodb+srv://...
```

SRV records can simplify discovery and endpoint management. TXT records can carry supported connection options according to deployed driver and server rules. Because SRV makes DNS an even more direct availability dependency, monitor that path accordingly.

## 2.7.9 Unix Domain Sockets

On supported Unix-like systems, MongoDB can use Unix domain sockets for local communication.

```yaml
net:
  unixDomainSocket:
    enabled: true
    pathPrefix: /tmp
    filePermissions: 0700
```

For the MongoDB 8.x baseline, current defaults and conditions should be revalidated before relying on them. Unix sockets can be useful for local administration, host-local tooling, and restricted local access.

Review socket path, ownership, permissions, interaction with bind configuration, and local security policy. Do not assume a Unix socket replaces the TCP architecture required by replica-set members or remote applications.

## 2.7.10 TLS Network Architecture

TLS protects MongoDB traffic in transit.

```yaml
net:
  tls:
    mode: requireTLS
    certificateKeyFile: /secure/mongodb/server.pem
    CAFile: /secure/mongodb/ca.pem
```

Exact options and certificate requirements are version-sensitive.

Production security should combine network reachability controls, TLS, authentication, and authorization. No one layer replaces the others.

TLS architecture should define server identity, member identity, CA trust, TLS mode, private-key protection, protocol policy, certificate expiration, certificate rotation, client compatibility, and monitoring.

Certificates must represent the names clients and MongoDB members use according to current MongoDB certificate-validation requirements. DNS, certificate identity, replica-set identity, clients, monitoring, and backup systems must be treated as coordinated infrastructure dependencies.

## 2.7.11 Certificate and CA Lifecycle

Certificates are availability dependencies. The production lifecycle is issue → deploy → validate → monitor lifetime → renew early → rotate → validate again.

Do not discover certificate expiration through an outage. MongoDB can emit expiration-related warnings, but external certificate-lifecycle monitoring should provide earlier operational warning.

Supported MongoDB releases provide certificate rotation functionality through operations such as:

```javascript
db.runCommand({ rotateCertificates: 1 })
```

where applicable. The exact procedure must be validated against the target release. Production rotation should verify expected certificate paths, replacement certificate validity, private-key access, CA trust, member connectivity, and new client connections.

Certificate replacement is not the same as CA migration. CA migration can affect applications, `mongod`, `mongos`, replica-set peers, monitoring, backup, and automation. An overlapping trust period may be required depending on the PKI design and MongoDB version.

Where TLS uses OCSP, include the relevant OCSP responder in the network dependency inventory, especially in restricted-egress environments.

## 2.7.12 Member-to-Member Connectivity

Replica-set members must communicate reliably. Internal traffic includes heartbeats, oplog replication, elections, synchronization, and administrative cluster communication.

Every required member should be able to reach the other members according to the supported topology.

| From / To | db01 | db02 | db03 |
|---|---:|---:|---:|
| db01 | — | ✓ | ✓ |
| db02 | ✓ | — | ✓ |
| db03 | ✓ | ✓ | — |

Validate member connectivity after firewall changes, DNS changes, certificate changes, node replacement, subnet migration, and routing changes. Application connectivity alone is insufficient.

Member-to-member paths should provide low latency, low packet loss, predictable routing, and sufficient bandwidth. A process can remain healthy while replica-set connectivity is unhealthy.

## 2.7.13 Sharded-Cluster Connectivity

Sharded deployments add communication requirements among applications, `mongos`, shard replica sets, and the config server replica set.

Do not validate only application-to-`mongos` connectivity and assume the cluster is healthy. Also validate `mongos` to config servers, `mongos` to shards, shard member to shard member, and config server to config server according to the target MongoDB architecture.

The exact connectivity matrix should be documented for the environment.

## 2.7.14 Load Balancers and Proxies

Do not place an ordinary MongoDB replica-set connection behind a generic TCP or application load balancer as a substitute for MongoDB driver topology discovery. MongoDB drivers are topology-aware and need to understand primary, secondaries, elections, read preference, and topology changes.

MongoDB also supports intentional load-balanced connection behavior for specific architectures and compatible drivers. Options such as `loadBalanced=true` have specific connection-string and topology requirements.

```text
Generic LB used to hide replica set → avoid
MongoDB-supported load-balanced architecture → validate and configure intentionally
```

Any proxy inserted into the database path must be reviewed for topology awareness, TLS behavior, idle timeouts, connection persistence, failure handling, source-address behavior, and monitoring.

## 2.7.15 Network Compression

MongoDB supports network compression configuration, including `net.compression.compressors`. Supported algorithms and defaults are version-sensitive.

Compression trades network bandwidth for CPU work. Use the current default, measure, identify a bottleneck, test, and change only if justified. Evaluate CPU utilization, latency, bandwidth, document characteristics, and workload throughput.

## 2.7.16 Connection Capacity and Pooling

MongoDB connection capacity must be planned together with application behavior. A production estate may include connections from applications, monitoring, backup systems, administrative clients, automation, and internal MongoDB communication.

MongoDB exposes `net.maxIncomingConnections` for applicable server versions. Do not assign an arbitrary universal value.

Capacity depends on MongoDB connection limits, OS file-descriptor capacity, application connection pools, number of application instances, monitoring, and administrative demand.

MongoDB drivers normally maintain connection pools. Applications should reuse pooled connections rather than create a new connection for every database operation. Poor pooling can cause repeated TLS handshakes, repeated authentication, socket churn, ephemeral-port pressure, higher latency, and connection storms.

Pool sizing requires coordination between application engineering, SRE/platform engineering, and MongoDB administration. A rough `application instances × max pool size` calculation can assist initial reasoning but should not be treated as an exact prediction because driver topology, monitoring connections, and pool behavior are more nuanced.

## 2.7.17 TCP, NAT, Conntrack, and MTU

MongoDB makes extensive use of TCP connections. Production infrastructure must support long-lived connections, expected idle behavior, adequate ephemeral ports, connection tracking, and retry/reconnection behavior.

TCP keepalive can interact with MongoDB drivers, OS networking, firewalls, NAT, load balancers, proxies, and application pools. Do not copy a universal keepalive value from a generic tuning guide.

Large application estates can pressure NAT tables, conntrack, firewall state tables, and ephemeral port ranges. This can produce MongoDB-looking connection failures even when MongoDB is healthy. Treat these as infrastructure dependencies rather than MongoDB server settings.

MTU problems are particularly relevant across VPNs, Kubernetes overlays, cloud transit, cross-region networking, and hybrid connectivity. Validate MTU end to end before changing it.

## 2.7.18 Latency, Packet Loss, and Bandwidth

MongoDB performance depends on network quality. Measure application-to-MongoDB, member-to-member, `mongos`-to-shard, and `mongos`-to-config-server paths where applicable.

Network latency affects client response time, replication, elections, write concern, distributed operations, and sharded queries. Avoid universal latency thresholds. Measure the environment and align targets with application SLOs and topology requirements.

Packet loss can cause TCP retransmission, heartbeat failure, replication instability, latency spikes, connection reset, and elections. Do not classify every such symptom as a database engine failure.

Plan bandwidth for normal workload, replication, peak traffic, backup, initial sync, recovery, and migration. Steady-state bandwidth can be far lower than recovery demand.

## 2.7.19 Cross-AZ and Cross-Region Networking

Replica-set members are commonly distributed across availability zones to reduce correlated infrastructure failure. The tradeoff is failure-domain separation versus network latency and cost. Measure both normal and degraded conditions.

Cross-region replica-set placement adds latency, packet-loss exposure, bandwidth cost, complex failure domains, election implications, and potential write-latency impact. Do not create voting topology across regions without modeling voting majority, failure scenarios, latency, write concern, and RPO/RTO.

MongoDB elections and heartbeat behavior are affected by network conditions. Do not lower election or heartbeat timeouts merely to compensate for a poorly designed WAN topology. More aggressive timeout behavior can increase sensitivity to transient network latency and cause unnecessary elections.

## 2.7.20 Network Monitoring and Alerting

Network monitoring should span MongoDB and the surrounding platform.

Current MongoDB releases expose connection telemetry through `serverStatus`, including version-dependent fields such as:

```text
connections.current
connections.available
connections.totalCreated
connections.rejected
connections.active
```

Current, available, rejected, and total-created rate together are more informative than current connections alone. Rapid growth in `totalCreated` can indicate connection churn even if current connections remain moderate.

Useful version-dependent network telemetry includes bytes in/out, request counts, network compression statistics, slow DNS operations, slow TLS operations, and related network/replication metrics. Inspect mechanisms such as:

```javascript
db.serverStatus().network
```

where appropriate.

Also monitor TCP resets, retransmissions, packet loss, latency, socket usage, conntrack, NAT, firewall denies, DNS health, PKI, certificate expiration, and OCSP where applicable.

Alert on connection rejection, sustained connection saturation, abnormal connection creation, member connectivity loss, abnormal replication lag caused by network conditions, DNS failure, TLS failure, approaching certificate expiration, packet loss, excessive retransmission, and database-path firewall denies. Thresholds should be calibrated to workload and SLOs rather than copied universally.

## 2.7.21 Connectivity Validation

Network validation should prove each layer independently:

```text
DNS
 ↓
Route
 ↓
Firewall
 ↓
TCP
 ↓
TLS
 ↓
MongoDB handshake
 ↓
Authentication
 ↓
Topology discovery
 ↓
Application operation
```

Depending on installed tools, useful Linux diagnostics include:

```bash
getent hosts mongo01.prod.example
ss -lntp
nc -vz mongo01.prod.example 27017
ip addr
ip route
tracepath mongo01.prod.example
```

Use approved TLS/certificate tools when investigating encrypted connections. Validate from representative application, operations, monitoring, backup, replica-set peer, and `mongos` networks as applicable.

## 2.7.22 Failure Scenarios

### MongoDB listening only on localhost

If local connections succeed but remote ones fail, check `net.bindIp`, startup configuration, and the runtime listener. Do not automatically enable bind-all.

### Port reachable but application cannot connect

A TCP connection proves only one layer. Investigate DNS, TCP, TLS, MongoDB handshake, authentication, topology discovery, and application configuration.

### Replica member cannot communicate

Validate DNS, bidirectional TCP connectivity, TLS, internal authentication, replica-set hostname, and firewall policy. A one-direction connectivity test is insufficient.

### Intermittent resets

Investigate packet loss, firewall idle timeout, NAT, conntrack, proxy/load balancer behavior, TCP keepalive, application pools, and node instability. Do not increase MongoDB timeouts before identifying the failing layer.

### TLS handshake failure

Validate certificate validity, certificate identity, CA trust, TLS mode, client compatibility, and system time. Do not permanently disable certificate verification to restore connectivity.

### Certificate expiration

Confirm expiration, identify affected endpoints, use the approved renewal procedure, validate trust, deploy/rotate safely, validate new connections, and investigate why monitoring failed.

### DNS failure or SRV corruption

Investigate DNS service availability, record correctness, cache, private-zone association, split-horizon behavior, SRV/TXT records, A/AAAA resolution, and driver interpretation.

### IPv6 mismatch

If DNS returns IPv6 but MongoDB IPv6 support, routing, or firewall policy is incomplete, validate the complete IPv6 path rather than disabling IPv6 blindly.

### Incorrect load balancer

If an endpoint connects but topology awareness, failover, or read preference behaves incorrectly, verify whether the deployment expects ordinary replica-set discovery or explicit MongoDB-supported load-balanced mode.

### Connection limit reached

Inspect current connections, available capacity, rejected connections, OS file descriptors, application pools, and connection creation rate. Do not merely increase limits without understanding the source.

### Connection storm

A restart or outage can cause many clients to disconnect and reconnect simultaneously, creating network, TLS, authentication, and MongoDB load. Inspect `current`, `totalCreated` rate, rejected connections, and application retry behavior. Stabilize client backoff rather than only raising server limits.

### NAT/conntrack exhaustion

MongoDB can remain healthy while clients cannot establish new connections. Inspect network infrastructure before changing MongoDB limits.

### OCSP unavailable

Where TLS depends on OCSP, validate egress and responder availability according to the configured security model.

### Network partition

Determine the connectivity matrix, voting majority, and current writable primary. Avoid unnecessary topology manipulation, restore connectivity, and validate replication convergence.

### Firewall rule removed

Restore the approved least-privilege rule and validate TCP, TLS, MongoDB, replication, and applications. Do not replace a missing narrow rule with a permanent broad allow rule.

## 2.7.23 Network Troubleshooting Workflow

Use this sequence:

```text
1. DNS
   ↓
2. Routing
   ↓
3. Firewall / security policy
   ↓
4. TCP listener
   ↓
5. TLS
   ↓
6. MongoDB handshake
   ↓
7. Authentication
   ↓
8. Topology discovery
   ↓
9. Application behavior
```

For cluster-specific problems also inspect member-to-member connectivity, replication health, voting majority, and election state. This prevents unnecessary MongoDB configuration changes when the actual problem resides elsewhere.

## 2.7.26 SRE/DBRE Operational Standard

For every production MongoDB deployment, operations should be able to answer where MongoDB nodes are located; whether they are publicly reachable; which interfaces and ports are used; which sources may connect; which controls permit access; how applications discover MongoDB; which DNS records define identity; whether every member resolves and reaches its peers; whether TLS is enabled; which CA establishes trust; when certificates expire; how certificates and CAs are rotated; whether OCSP is required; whether proxies or load balancers exist; what normal latency and packet loss look like; whether NAT/conntrack can become exhausted; whether MongoDB connections are being rejected; whether connection creation is abnormal; how reconnect storms behave; whether DNS failure can cause an outage; whether network partitions can remove voting majority; and whether every connectivity layer can be tested and rolled back safely.

The desired state is:

Private
+
Least privilege
+
Stable identity
+
Resolvable
+
Encrypted
+
Authenticated
+

Low loss

## 2.7.27 Canonical Technical Notes

- Treat networking as part of MongoDB availability architecture, not merely connectivity configuration.
- Keep self-managed production MongoDB private by default and require explicit review for direct public exposure.
- Bind MongoDB only according to the intended architecture; do not use `bindIpAll` as a generic connectivity fix.
- Treat IPv4 and IPv6 as explicit architectural decisions.
- Document role-specific default ports and do not treat custom ports as security controls.
- Use stable resolvable DNS hostnames for replica-set and sharded-cluster identity; do not design modern production MongoDB around IP-only topology identity.
- Treat DNS as a monitored production dependency.
- Distinguish seed discovery from steady-state driver topology discovery and validate SRV/TXT records where used.
- Review Unix domain sockets as a separate local-connectivity mechanism.
- Use TLS as part of defense in depth, treat certificate lifetime as an availability concern, distinguish certificate rotation from CA migration, and account for OCSP where applicable.
- Require bidirectional member connectivity and document all sharded-cluster communication paths.
- Do not hide ordinary replica sets behind generic load balancers as a substitute for topology-aware drivers; use MongoDB-supported load-balanced behavior only intentionally.
- Tune network compression only with workload evidence.
- Plan MongoDB connection capacity together with OS and application pools and monitor connection creation and rejection, not only current connections.
- Treat TCP, NAT, conntrack, ephemeral ports, and MTU as infrastructure dependencies.
- Measure latency, packet loss, and bandwidth and capacity-plan for initial sync, recovery, backup, and migration traffic.
- Model cross-region topology against voting majority, write concern, RPO/RTO, latency, and failure scenarios.
- Do not casually tune election or heartbeat timeouts to compensate for network architecture.
- Use MongoDB network telemetry together with OS and network-platform telemetry.
- Troubleshoot connectivity layer by layer and validate changes from representative remote networks.
- Treat DNS, TLS, firewall, and network identity changes as controlled production changes.
