# 2.7 — Network Configuration

**Workflow Status:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x; version-sensitive networking, TLS, connection, and topology behavior must be revalidated against the exact target MongoDB release and driver versions.

## Purpose

MongoDB network configuration determines how applications, administrators, monitoring systems, backup platforms, automation, replica-set members, `mongos` routers, config servers, and shard servers communicate.

Production networking must satisfy two objectives simultaneously:

```text
Required connectivity
        +
Minimum necessary exposure
```

The production architecture is:

```text
Applications / Operations / Cluster Members
                    ↓
             DNS / Discovery
                    ↓
          Routing / Segmentation
                    ↓
        Firewall / Security Policy
                    ↓
           MongoDB Bind Policy
                    ↓
                  TLS
                    ↓
        Authentication / Authorization
                    ↓
          MongoDB Topology Discovery
                    ↓
              mongod / mongos
```

A running `mongod` process does not prove that the MongoDB service is reachable, secure, or healthy.

Production network health requires the database and its surrounding network dependencies to function together.

## 2.7.1 Purpose and Network Architecture

MongoDB communication paths vary by topology.

A replica-set deployment commonly contains:

```text
                    ┌────────────────┐
                    │ Applications   │
                    └───────┬────────┘
                            │
                            ▼
                     MongoDB Driver
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           mongod         mongod        mongod
           Member 1       Member 2      Member 3
              ▲             ▲             ▲
              └──── replication / ────────┘
                    heartbeat traffic

        Monitoring / Backup / Operations
                     │
                     └──────► MongoDB
```

A sharded deployment adds additional communication paths:

```text
Applications
     ↓
   mongos
     ↓
 ┌───┴─────────────┐
 ↓                 ↓
Shard A           Shard B
 ↓                 ↓
Replica Set      Replica Set
      \           /
       \         /
       Config Server
        Replica Set
```

Every required path should be documented.

Operators should be able to identify:

- source;
- destination;
- port;
- protocol;
- DNS dependency;
- TLS requirement;
- authentication requirement;
- firewall/security policy;
- expected latency;
- monitoring coverage.

Unknown communication paths are an operational risk.

## 2.7.2 Production Network Principles

The production standard is:

```text
Private by default
+
Least privilege
+
Stable identity
+
Encrypted where required
+
Authenticated
+
Topology aware
+
Observable
+
Capacity planned
+
Failure aware
```

Avoid architectures based on:

```text
Public database exposure
+
0.0.0.0/0 firewall rules
+
bind-all by convenience
+
un
encrypted traffic
+
weak authentication
```

Self-managed production MongoDB nodes should normally reside on private networks.

Any direct public exposure should require:

- explicit architecture approval;
- security review;
- documented business justification;
- strong authentication;
- TLS;
- restricted network policy;
- monitoring;
- documented compensating controls.

MongoDB technically supporting a listener on an address does not make that address appropriate for production exposure.

## 2.7.3 Bind Addresses, IPv4, and IPv6

MongoDB network listener configuration is primarily controlled through the `net` configuration domain.

For example:

```yaml
net:
  port: 27017
  bindIp: 127.0.0.1,10.20.30.15
```

`net.bindIp` determines the addresses/interfaces on which the MongoDB process accepts network connections.

The production objective is:

```text
Required interfaces only
        ↓
Explicit bind configuration
```

A node might require connectivity from:

- applications;
- replica-set peers;
- `mongos`;
- monitoring;
- backup systems;
- administrative networks.

All required paths must be considered before changing binding.

### Localhost defaults

Package-managed MongoDB installations commonly start with localhost-oriented binding for safety.

A locally successful:

```bash
mongosh
```

therefore does not prove remote connectivity.

Always verify the effective production binding.

### `bindIpAll`

MongoDB provides:

```yaml
net:
  bindIpAll: true
```

for architectures intentionally requiring listening on all applicable interfaces.

Do not use this merely because a client cannot connect.

Instead diagnose:

```text
MongoDB bind
     ↓
OS listener
     ↓
Routing
     ↓
Firewall
     ↓
Cloud network policy
     ↓
DNS
     ↓
TLS
     ↓
Client configuration
```

`bindIpAll` expands network exposure. It does not replace network security.

Use one intentional binding architecture rather than conflicting bind definitions.

### IPv6

IPv6 requires explicit consideration.

For supported MongoDB releases, IPv6 configuration includes:

```yaml
net:
  ipv6: true
```

where IPv6 is required.

An IPv6 address appearing in binding configuration should not be assumed to enable complete IPv6 behavior automatically.

Validate:

```text
IPv6 enabled
+
correct bind
+
IPv6 routing
+
firewall rules
+
DNS AAAA records
+
TLS identity
+
client support
```

as one architecture.

For the MongoDB 8.x baseline, the documented `net.ipv6` default is disabled. Revalidate this against the exact target release.

## 2.7.4 Ports and Listener Configuration

MongoDB uses role-dependent default ports.

For the MongoDB 8.x baseline:

| MongoDB role | Default port |
|---|---:|
| Standard `mongod` | `27017` |
| `mongos` | `27017` |
| Shard-server `mongod` | `27018` |
| Config-server `mongod` | `27019` |

Explicit configuration may use:

```yaml
net:
  port: 27017
```

Production estates should standardize ports where practical.

This simplifies:

- firewall rules;
- monitoring;
- automation;
- documentation;
- troubleshooting.

MongoDB also supports configurations in which the operating system selects a port. Such behavior is generally unsuitable for normal production endpoints that require predictable discovery and security policy.

Most importantly:

```text
Non-default port
      ≠
security control
```

Changing `27017` to another number does not replace:

- TLS;
- authentication;
- authorization;
- segmentation;
- firewall policy.

### Runtime listener verification

After starting MongoDB, verify the actual listener.

For example:

```bash
ss -lntp
```

or:

```bash
ss -lntp | grep 27017
```

The validation chain should be:

```text
mongod.conf
     ↓
startup options
     ↓
OS listener
     ↓
remote connectivity
```

## 2.7.5 Private Placement and Segmentation

Production MongoDB should normally use private network placement.

Preferred architecture:

```text
Internet
   │
   X
   │
Approved application ingress
            ↓
Private application network
            ↓
Private MongoDB network
```

Administrative access should use controlled mechanisms such as:

- bastion hosts;
- VPN;
- private connectivity;
- approved management networks;
- zero-trust access platforms.

### Segmentation

Database traffic can be logically separated by purpose:

```text
Application network
       ↓
MongoDB application access

Operations network
       ↓
Administrative access

Monitoring network
       ↓
Telemetry access

Backup infrastructure
       ↓
Backup access

MongoDB members
       ↓
Internal cluster communication
```

Physical interface separation is not always necessary.

Policy separation is.

## 2.7.6 Firewall and Cloud Network Controls

Network policy should answer:

```text
Who
 ↓
may connect to which MongoDB node
 ↓
on which port
 ↓
for which purpose?
```

Use least-privilege rules.

Avoid:

```text
Entire enterprise network
          ↓
      TCP 27017
          ↓
     all MongoDB nodes
```

unless the architecture genuinely requires it.

### Defense in depth

Depending on environment, controls can include:

```text
MongoDB bind configuration
        +
host firewall
        +
subnet/VPC/VNet policy
        +
cloud security controls
        +
routing
        +
TLS
        +
authentication
```

Cloud implementations may use:

- AWS Security Groups;
- Azure Network Security Groups;
- Google Cloud firewall policies;
- Kubernetes NetworkPolicy.

Cloud-specific implementations belong in the corresponding cloud handbook.

### Temporary rules

Troubleshooting rules such as broad temporary allows must have:

- owner;
- reason;
- expiration;
- removal verification.

Temporary unrestricted access should never quietly become permanent architecture.

## 2.7.7 DNS and Replica-Set Identity

DNS is a production MongoDB dependency.

Modern MongoDB replica-set and sharded-cluster architectures should use stable, resolvable DNS hostnames for member identity rather than treating ephemeral IP addresses as durable topology identifiers.

Example:

```text
mongo01.prod.example
mongo02.prod.example
mongo03.prod.example
```

The production relationship is:

```text
Stable DNS identity
       ↓
MongoDB topology identity
       ↓
TLS certificate identity
       ↓
Driver discovery
```

These layers should be designed together.

### IP-only topology configuration

Modern MongoDB releases have stricter hostname and split-horizon validation than older releases.

Do not design new production replica sets around IP-only member identity.

Validate target-version hostname requirements before deployment or upgrade.

### DNS availability

A healthy MongoDB process can become operationally inaccessible if required DNS resolution fails.

Therefore:

```text
mongod healthy
      ≠
MongoDB service available
```

Monitor critical database DNS names.

### DNS design

Review:

- forward lookup;
- reverse lookup where required;
- TTL;
- private DNS zones;
- split-horizon behavior;
- cross-network resolution;
- SRV records;
- TXT records where used;
- certificate names.

Test from the networks that actually consume MongoDB.

For example:

```bash
getent hosts mongo01.prod.example
```

and where required:

```bash
dig mongo01.prod.example
```

```bash
dig -x <ip-address>
```

## 2.7.8 Seed Lists and SRV Discovery

MongoDB drivers perform topology discovery.

A standard connection can begin with multiple seed hosts:

```text
mongodb://mongo01,mongo02,mongo03/...
```

Conceptually:

```text
Seed list
    ↓
Initial connection
    ↓
MongoDB topology discovery
    ↓
Actual replica-set membership
```

The seed list bootstraps discovery. It should not be confused with the complete steady-state topology model maintained by the driver.

Provide enough reachable discovery paths that application startup does not depend unnecessarily on one hostname.

### SRV discovery

MongoDB supports SRV-style connection strings:

```text
mongodb+srv://...
```

SRV records can simplify discovery and endpoint management.

Relevant DNS architecture may include:

```text
SRV record
    ↓
MongoDB hosts

TXT record
    ↓
supported connection options
```

Exact supported TXT options and driver behavior must be validated against the deployed MongoDB drivers.

Using SRV makes DNS availability even more important.

Monitor it accordingly.

## 2.7.9 Unix Domain Sockets

On supported Unix-like systems, MongoDB can use Unix domain sockets for local communication.

Relevant configuration resides under:

```yaml
net:
  unixDomainSocket:
    enabled: true
    pathPrefix: /tmp
    filePermissions: 0700
```

For the MongoDB 8.x baseline, current defaults and conditions should be revalidated before relying on them.

Unix sockets can be useful for:

- local administration;
- host-local tooling;
- restricted local access.

Review:

- socket path;
- ownership;
- permissions;
- interaction with bind configuration;
- local security policy.

Do not assume a Unix socket replaces the TCP architecture required by replica-set members or remote applications.

## 2.7.10 TLS Network Architecture

TLS protects MongoDB traffic in transit.

A simplified configuration is:

```yaml
net:
  tls:
    mode: requireTLS
    certificateKeyFile: /secure/mongodb/server.pem
    CAFile: /secure/mongodb/ca.pem
```

Exact options and certificate requirements are version-sensitive.

Production security should follow:

```text
Network reachability
        +
TLS
        +
Authentication
        +
Authorization
```

No one layer replaces the others.

TLS architecture should define:

- server identity;
- member identity;
- CA trust;
- TLS mode;
- private-key protection;
- protocol policy;
- certificate expiration;
- certificate rotation;
- client compatibility;
- monitoring.

### Certificate identity

Certificates must represent the names clients and MongoDB members use according to current MongoDB certificate-validation requirements.

Changing:

```text
mongo01.old.example
```

to:

```text
mongo01.new.example
```

can affect:

```text
DNS
+
TLS certificate
+
replica-set identity
+
clients
+
monitoring
+
backup systems
```

Treat such changes as coordinated infrastructure changes.

## 2.7.11 Certificate and CA Lifecycle

Certificates are availability dependencies.

The production lifecycle should be:

```text
Issue
 ↓
Deploy
 ↓
Validate
 ↓
Monitor lifetime
 ↓
Renew early
 ↓
Rotate
 ↓
Validate again
```

Do not discover certificate expiration through an outage.

MongoDB can emit expiration-related warnings, but external certificate-lifecycle monitoring should provide earlier operational warning.

### Certificate rotation

Supported MongoDB releases provide certificate rotation functionality through operations such as:

```javascript
db.runCommand({
  rotateCertificates: 1
})
```

where applicable.

The exact procedure must be validated against the target release.

Production rotation should verify:

- expected certificate paths;
- replacement certificate validity;
- private-key access;
- CA trust;
- member connectivity;
- new client connections.

Existing and new connections can have different certificate lifecycle behavior during rotation, so validation must include new connections.

### Certificate rotation is not CA migration

Keep these as separate procedures:

```text
Certificate replacement
        ≠
CA migration
```

CA migration can affect:

- applications;
- `mongod`;
- `mongos`;
- replica-set peers;
- monitoring;
- backup;
- automation.

An overlapping trust period may be required depending on the PKI design and MongoDB version.

### OCSP

Where the TLS architecture uses OCSP, MongoDB may depend on network access to the appropriate OCSP infrastructure.

In restricted-egress environments, include:

```text
MongoDB / relevant TLS participant
               ↓
          OCSP responder
```

in the network dependency inventory.

## 2.7.12 Member-to-Member Connectivity

Replica-set members must communicate reliably.

Internal traffic includes:

- heartbeats;
- oplog replication;
- elections;
- synchronization;
- administrative cluster communication.

Every required member should be able to reach the other members according to the supported topology.

Use a connectivity matrix:

| From / To | db01 | db02 | db03 |
|---|---:|---:|---:|
| db01 | — | ✓ | ✓ |
| db02 | ✓ | — | ✓ |
| db03 | ✓ | ✓ | — |

Validate member connectivity after:

- firewall changes;
- DNS changes;
- certificate changes;
- node replacement;
- subnet migration;
- routing changes.

Application connectivity alone is insufficient.

### Member network quality

Member-to-member paths should provide:

```text
Low latency
+
Low packet loss
+
Predictable routing
+
Sufficient bandwidth
```

A process can remain healthy while its replica-set connectivity is unhealthy.

## 2.7.13 Sharded-Cluster Connectivity

Sharded deployments add communication requirements among:

```text
Applications
      ↓
    mongos
      ↓
Shard replica sets
      ↕
Config server replica set
```

Production network policy must account for all required paths.

Do not validate only:

```text
Application → mongos
```

and assume the cluster is healthy.

Also validate:

```text
mongos ↔ config servers
mongos ↔ shards
shard member ↔ shard member
config server ↔ config server
```

according to the target MongoDB architecture.

The exact connectivity matrix should be documented for the environment.

## 2.7.14 Load Balancers and Proxies

Do not place an ordinary MongoDB replica-set connection behind a generic TCP or application load balancer as a substitute for MongoDB driver topology discovery.

MongoDB drivers are topology-aware.

They need to understand:

- primary;
- secondaries;
- elections;
- read preference;
- topology changes.

A generic endpoint can obscure that model.

### Supported load-balanced architectures

MongoDB also supports intentional load-balanced connection behavior for specific architectures and compatible drivers.

For such designs, options such as:

```text
loadBalanced=true
```

have specific connection-string and topology requirements.

Therefore:

```text
Generic LB used to hide replica set
        → avoid

MongoDB-supported load-balanced architecture
        → validate and configure intentionally
```

Do not generalize one model into the other.

### Proxies

Any proxy inserted into the database path must be reviewed for:

- topology awareness;
- TLS behavior;
- idle timeouts;
- connection persistence;
- failure handling;
- source-address behavior;
- monitoring.

## 2.7.15 Network Compression

MongoDB supports network compression configuration, including settings under:

```text
net.compression.compressors
```

Supported algorithms and defaults are version-sensitive.

Compression creates a tradeoff:

```text
Less network traffic
        ↔
More CPU work
```

Use:

```text
Current default
      ↓
Measure
      ↓
Identify bottleneck
      ↓
Test
      ↓
Change only if justified
```

Do not select a compressor merely because it produces the highest compression ratio in isolation.

Evaluate actual:

- CPU utilization;
- latency;
- bandwidth;
- document characteristics;
- workload throughput.

## 2.7.16 Connection Capacity and Pooling

MongoDB connection capacity must be planned together with application behavior.

A production estate may include connections from:

- applications;
- monitoring;
- backup systems;
- administrative clients;
- automation;
- internal MongoDB communication.

MongoDB exposes a control such as:

```text
net.maxIncomingConnections
```

for applicable server versions.

Do not assign an arbitrary universal value.

Capacity depends on:

```text
MongoDB connection limits
        +
OS file-descriptor capacity
        +
application connection pools
        +
number of application instances
        +
monitoring
        +
administrative demand
```

### Application pooling

MongoDB drivers normally maintain connection pools.

Applications should reuse pooled connections rather than create a new connection for every database operation.

Poor pooling can cause:

- repeated TLS handshakes;
- repeated authentication;
- socket churn;
- ephemeral-port pressure;
- higher latency;
- connection storms.

Pool sizing requires coordination between:

```text
Application Engineering
+
SRE / Platform
+
MongoDB Administration
```

### Avoid simplistic calculations

A rough calculation such as:

```text
application instances × max pool size
```

can be useful for initial capacity reasoning, but should not be treated as an exact prediction of all MongoDB connections.

Driver topology, monitoring connections, and pool implementation can make actual behavior more complex.

## 2.7.17 TCP, NAT, Conntrack, and MTU

MongoDB makes extensive use of TCP connections.

Production infrastructure must support:

- long-lived connections;
- expected idle behavior;
- adequate ephemeral ports;
- connection tracking;
- retry/reconnection behavior.

### TCP keepalive

Keepalive settings can interact with:

- MongoDB drivers;
- OS networking;
- firewalls;
- NAT;
- load balancers;
- proxies;
- application pools.

Do not copy a universal keepalive value from a generic tuning guide.

Tune only after understanding the full path.

### NAT and conntrack

Large application estates can pressure:

- NAT tables;
- conntrack;
- firewall state tables;
- ephemeral port ranges.

This can produce MongoDB-looking connection failures even when MongoDB is healthy.

Treat these as infrastructure dependencies rather than MongoDB server settings.

### MTU

MTU problems are particularly relevant across:

- VPNs;
- Kubernetes overlays;
- cloud transit;
- cross-region networking;
- hybrid connectivity.

Symptoms may include:

- intermittent connection failure;
- TLS handshake problems;
- retransmissions;
- failures involving larger packets.

Validate MTU end to end before changing it.

## 2.7.18 Latency, Packet Loss, and Bandwidth

MongoDB performance depends on network quality.

Measure:

```text
Application ↔ MongoDB
MongoDB ↔ MongoDB
mongos ↔ shard
mongos ↔ config server
```

where applicable.

### Latency

Network latency affects:

- client response time;
- replication;
- elections;
- write concern;
- distributed operations;
- sharded queries.

Avoid universal latency thresholds.

Measure the environment and align limits with application SLOs and topology requirements.

### Packet loss

Packet loss can cause:

- TCP retransmission;
- heartbeat failure;
- replication instability;
- latency spikes;
- connection reset;
- elections.

Do not classify every such symptom as a database engine failure.

### Bandwidth

Plan for:

```text
Normal workload
+
replication
+
peak traffic
+
backup
+
initial sync
+
recovery
+
migration
```

Steady-state bandwidth can be far lower than recovery demand.

## 2.7.19 Cross-AZ and Cross-Region Networking

### Cross-AZ

Replica-set members are commonly distributed across availability zones to reduce correlated infrastructure failure.

The tradeoff is:

```text
Failure-domain separation
          ↔
Network latency + network cost
```

Measure both normal and degraded conditions.

### Cross-region

Cross-region replica-set placement adds:

- latency;
- packet-loss exposure;
- bandwidth cost;
- complex failure domains;
- election implications;
- potential write-latency impact.

Do not create voting topology across regions without modeling:

```text
Voting majority
+
failure scenarios
+
latency
+
write concern
+
RPO/RTO
```

### Election sensitivity

MongoDB elections and heartbeat behavior are affected by network conditions.

Do not lower election or heartbeat timeouts merely to compensate for a poorly designed WAN topology.

More aggressive timeout behavior can increase sensitivity to transient network latency and cause unnecessary elections.

Detailed election tuning and DR topology belong in the replication chapters.

## 2.7.20 Network Monitoring and Alerting

Network monitoring should span MongoDB and the surrounding platform.

### MongoDB connection metrics

Current MongoDB releases expose connection telemetry through `serverStatus`, including version-dependent fields such as:

```text
connections.current
connections.available
connections.totalCreated
connections.rejected
connections.active
```

Use multiple indicators.

For example:

```text
Current
+
Available
+
Rejected
+
Total-created rate
```

is more informative than current connections alone.

Rapid growth in `totalCreated` can indicate connection churn even if current connections remain moderate.

### MongoDB network metrics

Useful version-dependent network telemetry includes:

```text
bytesIn
bytesOut
numRequests
network compression statistics
slow DNS operations
slow TLS operations
```

and related network/replication metrics.

Inspect using mechanisms such as:

```javascript
db.serverStatus().network
```

where appropriate.

### Infrastructure telemetry

Also monitor:

- TCP resets;
- retransmissions;
- packet loss;
- latency;
- socket usage;
- conntrack;
- NAT;
- firewall denies;
- DNS health.

### External dependencies

Monitor:

```text
DNS
PKI
Certificate expiration
OCSP where applicable
```

### Alerting principles

Alert on conditions such as:

- connection rejection;
- sustained connection saturation;
- abnormal connection creation;
- member connectivity loss;
- abnormal replication lag caused by network conditions;
- DNS failure;
- TLS failure;
- approaching certificate expiration;
- packet loss;
- excessive retransmission;
- database-path firewall denies.

Thresholds should be calibrated to workload and SLOs rather than copied universally.

## 2.7.22 Failure Scenarios

### MongoDB listening only on localhost

Symptoms:

- local connection succeeds;
- remote connection fails.

Check:

```text
net.bindIp
     ↓
startup configuration
     ↓
runtime listener
```

Do not automatically enable bind-all.

Add only required interfaces.

### Port reachable but application cannot connect

A TCP connection proves only one layer.

Investigate:

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
MongoDB handshake
 ↓
Authentication
 ↓
Topology discovery
 ↓
Application configuration
```

### Replica member cannot communicate

Validate:

- DNS;
- bidirectional TCP connectivity;
- TLS;
- internal authentication;
- replica-set hostname;
- firewall policy.

A one-direction connectivity test is insufficient.

### Intermittent resets

Investigate:

- packet loss;
- firewall idle timeout;
- NAT;
- conntrack;
- proxy/load balancer;
- TCP keepalive;
- application pools;
- node instability.

Do not increase MongoDB timeouts before identifying the failing layer.

### TLS handshake failure

Validate:

```text
Certificate validity
       ↓
Certificate identity
       ↓
CA trust
       ↓
TLS mode
       ↓
Client compatibility
       ↓
System time
```

Do not permanently disable certificate verification to restore connectivity.

### Certificate expiration

1. confirm expiration;
2. identify affected endpoints;
3. use the approved renewal procedure;
4. validate trust;
5. deploy/rotate safely;
6. validate new connections;
7. investigate why monitoring failed.

### DNS failure

Investigate:

- DNS service availability;
- record correctness;
- cache;
- private-zone association;
- split-horizon behavior;
- SRV/TXT records;
- client resolver behavior.

### DNS/SRV corruption

SRV-based clients can fail topology discovery even when direct host connectivity still works.

Validate:

```text
SRV
+
TXT
+
individual A/AAAA resolution
+
driver interpretation
```

### IPv6 mismatch

Symptoms can occur when:

- DNS returns IPv6;
- MongoDB IPv6 support is not enabled correctly;
- routing is incomplete;
- firewall policy lacks IPv6 rules.

Validate the complete IPv6 path rather than disabling IPv6 blindly.

### Incorrect load balancer

Symptoms may include successful endpoint connection but broken topology awareness, failover, or read preference.

Verify whether the architecture is:

```text
ordinary replica-set discovery
```

or:

```text
explicit MongoDB-supported load-balanced mode
```

and correct the client/network design accordingly.

### Connection limit reached

Investigate:

- current connections;
- available capacity;
- rejected connections;
- OS file descriptors;
- application pools;
- connection creation rate.

Do not merely increase limits without understanding the source.

### Connection storm

A common sequence is:

```text
Outage / restart
       ↓
Many clients disconnect
       ↓
Connectivity restored
       ↓
Clients reconnect together
       ↓
Network + TLS + authentication + MongoDB spike
```

Response:

1. determine trigger;
2. inspect `current`;
3. inspect `totalCreated` rate;
4. inspect rejected connections;
5. inspect application retry behavior;
6. stabilize clients;
7. validate backoff;
8. restore normal pool behavior.

### NAT/conntrack exhaustion

MongoDB may remain healthy while clients cannot create connections.

Inspect network infrastructure before changing MongoDB limits.

### OCSP unavailable

Where TLS depends on OCSP, inability to reach the responder can affect TLS behavior.

Validate egress and responder availability according to the configured security model.

### Network partition

A network partition can divide a replica set while every process remains running.

Response:

```text
Determine connectivity matrix
        ↓
Determine voting majority
        ↓
Identify current writable primary
        ↓
Avoid unnecessary topology manipulation
        ↓
Restore network
        ↓
Validate replication convergence
```

Detailed election behavior belongs in the replication chapter.

### Firewall rule removed

Restore the approved least-privilege rule, then validate:

```text
TCP
 ↓
TLS
 ↓
MongoDB
 ↓
replication
 ↓
applications
```

Do not replace a missing narrow rule with a permanent broad allow rule.

## 2.7.27 Canonical Technical Notes

The Draft, Technical + Source Review, and Production + Copyright Review establish the following canonical principles:

- Treat networking as part of MongoDB availability architecture, not merely connectivity configuration.
- Keep self-managed production MongoDB private by default.
- Require explicit review for direct public exposure.
- Bind MongoDB only according to the intended architecture.
- Do not use `bindIpAll` as a generic connectivity fix.
- Treat IPv4 and IPv6 as explicit architectural decisions.
- Document role-specific default ports and avoid treating custom ports as security controls.
- Use stable resolvable DNS hostnames for replica-set and sharded-cluster identity.
- Do not design modern production MongoDB around IP-only topology identity.
- Treat DNS as a monitored production dependency.
- Distinguish seed discovery from steady-state driver topology discovery.
- Validate SRV and TXT records where `mongodb+srv` is used.
- Review Unix domain sockets as a separate local-connectivity mechanism.
- Use TLS as part of defense in depth rather than as a replacement for authentication or segmentation.
- Treat certificate lifetime as an availability concern.
- Distinguish certificate rotation from CA migration.
- Account for OCSP network dependencies where applicable.
- Require bidirectional member connectivity according to the topology.
- Document all sharded-cluster communication paths.
- Do not hide ordinary replica sets behind generic load balancers as a substitute for topology-aware drivers.
- Use MongoDB-supported load-balanced behavior only in architectures designed for it.
- Tune network compression only with workload evidence.
- Plan MongoDB connection capacity together with OS and application pools.
- Monitor connection creation and rejection, not only current connections.
- Treat TCP, NAT, conntrack, ephemeral ports, and MTU as infrastructure dependencies.
- Measure latency, packet loss, and bandwidth.
- Capacity-plan for initial sync, recovery, backup, and migration traffic.
- Model cross-region topology against voting majority, write concern, RPO/RTO, latency, and failure scenarios.
- Do not casually tune election or heartbeat timeouts to compensate for network architecture.
- Use MongoDB network telemetry together with OS and network-platform telemetry.
- Troubleshoot connectivity layer by layer.
- Validate changes from representative remote networks.
- Treat DNS, TLS, firewall, and network identity changes as controlled production changes.
