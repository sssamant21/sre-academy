**Compatibility:** MongoDB 7.x where operationally relevant

## Learning Objectives

After completing this section, you should be able to design MongoDB storage for predictable latency, sufficient capacity, recoverability, and independent failure domains; understand WiredTiger cache, filesystem cache, journaling, checkpoints, and persistent-storage relationships; size capacity for data, indexes, growth, maintenance, and recovery; distinguish capacity, IOPS, throughput, latency, and growth; evaluate AWS, Azure, Google Cloud, and Kubernetes storage paths; monitor and alert across application, MongoDB, host/Kubernetes, and storage-platform layers; and execute safe production response for disk-full, storage-latency, IOPS/throughput saturation, and member-storage-loss scenarios.

## 1. Production Storage Architecture

Storage is a core MongoDB reliability component. It directly affects read/write latency, WiredTiger checkpoints, journaling, replication, initial synchronization, restart/recovery time, index builds, backups/restores, and application tail latency.

```text
Application
    |
    v
MongoDB
    |
    v
WiredTiger
    |
    +-- WiredTiger Cache
    +-- Journal
    +-- Checkpoints
    |
    v
Filesystem
    |
    v
OS / Container
    |
    v
Block Device / Persistent Volume
    |
    v
Cloud or Physical Storage
```

A bottleneck at any layer can become a MongoDB bottleneck.

> **MongoDB storage must be engineered for predictable latency, sufficient capacity, recoverability, and independent failure domains—not simply enough disk space for the current dataset.**

## 2. WiredTiger Storage and Memory Relationship

WiredTiger manages its own cache while the operating system may independently use available memory for filesystem caching.

```text
                 System RAM
                     |
          +----------+----------+
          |                     |
          v                     v
   WiredTiger Cache      OS Filesystem Cache
          |                     |
          +----------+----------+
                     |
                     v
              Persistent Storage
```

> **High Host Memory Utilization ≠ MongoDB Memory Leak**

When the working set cannot be efficiently served from memory, physical reads and eviction pressure can increase. Do not casually increase WiredTiger cache: excessive allocation can reduce memory available to the OS and other processes, increasing swap or OOM risk. Cache sizing must follow the exact MongoDB release, host architecture, and container memory boundary.

## 3. Database Path and Dedicated Storage

MongoDB's data directory is configured through `storage.dbPath`.

```yaml
storage:
  dbPath: /data/mongodb
```

For production systems, use a dedicated filesystem or storage volume where practical and validate it before startup.

```bash
findmnt /data/mongodb
df -h /data/mongodb
lsblk
```

Avoid placing production database data on the OS root filesystem. Database growth should not be allowed to consume the storage required by SSH, system logging, monitoring agents, package management, temporary files, or core OS services.

> **OS Failure Domain ≠ MongoDB Capacity Failure Domain**

## 4. Filesystem Selection

Filesystem selection must follow the requirements and recommendations for the exact MongoDB release and operating system. For self-managed Linux data-bearing nodes using WiredTiger, XFS should generally be the preferred filesystem under current MongoDB production guidance; deviations should be explicitly validated.

Record MongoDB version, OS/kernel, filesystem, mount options, block-device configuration, storage type, volume size, IOPS, throughput, and encryption.

> **Supported Filesystem ≠ Preferred Production Filesystem**

Detailed filesystem preparation belongs in 2.4.

## 5. Storage Capacity Engineering

Do not size a MongoDB volume from logical collection size alone.

```text
Required Capacity
      =
Current physical data
+ Indexes
+ Expected growth
+ Index-build headroom
+ Operational temporary space
+ Recovery / resynchronization requirements
+ Fragmentation / storage-reuse behavior
+ Backup / snapshot considerations
+ Safety margin
```

> **Current Dataset Size ≠ Required Production Volume Size**

Capacity, performance, and growth are separate dimensions. A volume can have substantial free capacity but inadequate IOPS, excellent performance but dangerously rapid growth, or adequate IOPS but insufficient throughput.

## 6. Predictive Capacity Management

Static thresholds are useful operational examples, not MongoDB product requirements.

| Utilization | Example Operational Response |
|---|---|
| `<70%` | Normal |
| `70–80%` | Monitor trend |
| `80–85%` | Warning / review |
| `85–90%` | Expansion should be active |
| `>90%` | Critical risk |

Predictive capacity monitoring is more useful than utilization alone.

```text
Days to exhaustion = Available storage / Average daily growth
```

A 70%-full filesystem growing rapidly can be more urgent than an 85%-full stable filesystem.

## 7. IOPS, Throughput, and Latency

Disk capacity does not represent storage performance. MongoDB workloads generate random reads/writes, journal writes, checkpoint activity, index I/O, initial-sync traffic, and backup/maintenance activity.

Monitor read/write IOPS, read/write latency, throughput, queue depth, I/O utilization, and I/O wait.

> **Capacity ≠ Performance**

IOPS and throughput are distinct. Many small operations may be IOPS/latency constrained, while larger operations may reach throughput ceilings. Effective performance can also be capped by VM/instance storage bandwidth, network/storage architecture, or platform limits.

There is no single universal storage-latency threshold suitable for every MongoDB workload. Establish workload-specific baselines and alert on sustained meaningful deviations.

## 8. Journaling, Write Concern, Checkpoints, and Replication

These mechanisms solve different reliability problems.

```text
Application Write
       |
       v
Write Concern ---- acknowledgement expectations
       |
       v
MongoDB / WiredTiger
       |
       +-- Journal ---- durability/recovery behavior
       +-- Checkpoint - consistent persistent WiredTiger state
       +-- Replication - additional database copies
```

Application-visible durability is not reducible to a single `journal = durable` rule. SRE/DBRE teams must understand how write concern, journaling, checkpoints, replication, and persistent storage interact for the deployed release and topology.

## 9. Compression

Compression can reduce physical storage and I/O at the cost of additional CPU work. Evaluate compression through workload testing and measure compression ratio, CPU utilization, IOPS, latency, working-set behavior, and query performance. Collection and index compression capabilities are version-specific.

## 10. Storage Redundancy and Failure Domains

MongoDB replica sets provide database-level redundancy but do not automatically guarantee infrastructure independence.

```text
Replica Set
   |
   +-- Member A -> Failure Domain A
   +-- Member B -> Failure Domain B
   +-- Member C -> Failure Domain C
```

Evaluate host, physical storage, rack where applicable, availability zone, Kubernetes node/topology, and cloud infrastructure.

> **Replication Redundancy ≠ Infrastructure Independence**

For directly managed RAID-backed environments, evaluate RAID according to current MongoDB/platform guidance and workload needs; do not mechanically apply physical RAID recommendations to cloud platforms that abstract it.

## 11. AWS Storage Architecture

A common self-managed path is `MongoDB -> EC2 -> EBS -> filesystem`. Validate EBS type, provisioned IOPS/throughput, capacity, latency, queue behavior, encryption, snapshot design, AZ placement, and EC2 EBS performance limits.

A high-performance volume does not guarantee that the EC2 instance can consume all of its capability.

> **EBS Capability ≠ Effective MongoDB Capability**

## 12. Azure Storage Architecture

For self-managed MongoDB on Azure VMs, evaluate Managed Disk type, provisioned IOPS/throughput, latency, VM storage limits, caching configuration, availability-zone placement, encryption, and snapshot/backup architecture.

> **Managed Disk Capability ≠ VM Effective Storage Capability**

## 13. Google Cloud Storage Architecture

For self-managed MongoDB on Google Cloud, evaluate the supported storage technology appropriate to the workload along with capacity, IOPS, throughput, latency, machine-level limits, topology, encryption, and snapshot architecture.

> **Storage Service Capability ≠ Compute Instance Effective Capability**

Cloud limits change; validate current provider documentation instead of freezing transient limits into operational standards.

## 14. Kubernetes Storage Architecture

Kubernetes adds storage abstraction layers.

```text
MongoDB
   |
   v
Pod
   |
   v
PVC
   |
   v
PV
   |
   v
CSI Driver
   |
   v
Cloud / Physical Storage
```

Investigations may need to cover MongoDB, pod, node, PVC, PV, StorageClass, CSI, cloud volume, and infrastructure.

Production design should evaluate StatefulSet/operator behavior, pod anti-affinity, topology constraints, storage topology, volume binding, access modes, StorageClasses, PVC expansion, reclaim policy, CSI availability, snapshots, and attach/detach behavior.

Where supported, place replica-set members and their persistent volumes across appropriate failure domains.

## 15. Kubernetes Attach/Detach and Recovery

Pod rescheduling does not imply instantaneous database recovery.

```text
Pod fails
   |
   v
Scheduler selects node
   |
   v
Volume detaches
   |
   v
Volume attaches
   |
   v
Filesystem mounts
   |
   v
MongoDB starts and recovers
   |
   v
Replica catches up
```

Volume attach/detach behavior can contribute directly to RTO and must be considered when defining recovery expectations.

## 16. Storage Classes

Do not accept a cluster's default StorageClass blindly for production MongoDB.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mongodb-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Ti
  storageClassName: mongodb-production
```

Understand the underlying storage, IOPS, throughput, topology, volume binding, expansion, reclaim policy, snapshot capability, and attach/detach behavior before approval.

## 17. Storage Expansion

Storage expansion should be a tested runbook rather than an emergency experiment.

```text
Capacity Alert
      |
      v
Confirm growth
      |
      v
Determine target capacity
      |
      v
Expand volume / PVC
      |
      v
Expand partition/filesystem if required
      |
      v
Validate filesystem
      |
      v
Validate MongoDB + replication + application + backups
      |
      v
Update capacity forecast
```

## 18. Initial Synchronization and Recovery Demand

Replica-set initial synchronization can create substantial source reads, network transfer, destination writes, index work, and catch-up activity. Storage that is adequate in steady state may become constrained during a member rebuild.

Capacity and performance planning must include recovery-state demand.

> **Normal-State Storage Demand ≠ Recovery-State Storage Demand**

## 19. Backups and Storage Snapshots

Infrastructure snapshots and MongoDB backups are not automatically equivalent. Backup architecture must consider database/application consistency, topology, RPO/RTO, encryption, retention, restore procedures, and restore testing.

> **Storage Snapshot ≠ Automatically Valid MongoDB Backup**

> **Backup Created ≠ Recovery Validated**

Detailed backup and recovery architecture belongs in the dedicated backup chapters.

## 20. Four-Layer Monitoring Model

Monitor storage across four layers.

| Layer | Examples |
|---|---|
| Application | latency, errors, timeouts |
| MongoDB | operation latency, WiredTiger cache/eviction, checkpoints, replication lag |
| OS/Kubernetes | memory, swap, I/O wait, filesystem, PVC/node behavior |
| Storage platform | IOPS, throughput, latency, queueing, throttling/limits |

Correlate metrics before assigning root cause.

```text
Application P99 ↑
MongoDB write latency ↑
Replication lag ↑
Disk queue ↑
Storage/instance ceiling reached
```

> **Correlate First. Conclude Second.**

## 21. Recommended Storage Dashboard and Alerts

A production dashboard should include filesystem utilization/free capacity, growth/day, days to exhaustion, read/write IOPS, read/write latency, throughput, queue depth, I/O wait, MongoDB operation latency, WiredTiger cache/eviction/checkpoint behavior, replication lag, memory/swap, platform limits, and PVC/PV health where applicable.

Use static and predictive alerts. Example organizational signals include warning/critical filesystem utilization, projected exhaustion inside the provisioning lead time, sustained storage latency above baseline, and replication lag correlated with storage degradation.

Thresholds must be tuned to workload, growth velocity, recovery requirements, and infrastructure lead time.

## 22. Failure Scenario — Filesystem Full

Initial investigation can include:

```bash
df -h
df -i
findmnt /data/mongodb
lsblk
lsof +L1
```

`lsof +L1` helps identify deleted files that remain open and still consume filesystem capacity.

> **Do not manually delete MongoDB/WiredTiger-managed database files from `dbPath` to reclaim production storage.**

Doing so can convert a capacity incident into a corruption or recovery incident.

## 23. Production Caution with Recursive Scans

A command such as `du -xhd1 /data/mongodb` can be useful, but broad scans of multi-terabyte database filesystems can create substantial I/O. During an active latency incident, prefer existing monitoring, cloud/storage metrics, filesystem metadata, and targeted investigation before expensive recursive scans.

> **Troubleshooting Must Not Materially Worsen the Incident**

## 24. Failure Scenario — Storage Latency

A production investigation should correlate application impact, MongoDB operation latency, replication lag, WiredTiger cache/eviction behavior, host memory/swap, I/O wait, storage latency, IOPS, throughput, queue depth, and cloud/VM limits against the same incident timeline.

Storage symptoms can originate from memory pressure. Useful host diagnostics include:

```bash
free -h
vmstat 1
swapon --show
```

> **Storage Symptoms ≠ Automatically Storage Root Cause**

## 25. Failure Scenario — IOPS or Throughput Ceiling

```text
Workload increases
      |
      v
Storage demand increases
      |
      v
IOPS / throughput ceiling reached
      |
      v
Queueing and latency increase
      |
      v
MongoDB and application performance degrade
```

Possible remediation includes increasing provisioned performance, changing storage tier, increasing VM/instance capability, optimizing indexes/access paths, reducing unnecessary I/O, redistributing workload, or scaling the MongoDB architecture. Determine why demand increased before simply adding capacity.

## 26. Failure Scenario — Member Storage Loss

If sufficient healthy replica-set members remain, recovery from one member's storage loss may involve isolating the failed member, provisioning replacement storage/member, performing initial synchronization, catching up, and validating replica-set health rather than restoring that individual member from backup.

```text
Storage failure
      |
      v
Confirm healthy replica-set majority/state
      |
      v
Isolate failed member
      |
      v
Provision replacement
      |
      v
Initial synchronization
      |
      v
Catch up and validate
```

Backup restoration remains essential for failures replication cannot solve.

## 27. Replication, Backup, and Storage Redundancy

These controls solve different problems.

```text
Replication       -> Availability / redundancy
Backup            -> Historical recovery
Storage redundancy-> Infrastructure resilience
Snapshots         -> Point-in-time infrastructure capability
```

Accidental deletion or destructive application behavior can replicate to all members.

> **Replication ≠ Backup**

## 28. Production Troubleshooting Toolkit

Useful host commands include:

```bash
df -h
df -i
lsblk
findmnt
mount
free -h
vmstat 1
swapon --show
iostat -xz 1
lsof +L1
```

Use targeted `du` operations carefully when necessary.

MongoDB-side diagnostics can include:

```javascript
db.serverStatus()
db.serverStatus().wiredTiger
rs.status()
```

Available fields differ across releases, so dashboards and runbooks must remain version-aware.

## 30. Production Validation Checklist

### Architecture
- [ ] Dedicated database storage validated.
- [ ] `dbPath` verified.
- [ ] Filesystem validated for the exact MongoDB release/platform.
- [ ] Encryption requirements satisfied.
- [ ] Failure domains documented.

### Capacity and Performance
- [ ] Current physical footprint and indexes measured.
- [ ] Growth and operational/recovery headroom modeled.
- [ ] Time-to-exhaustion monitoring enabled.
- [ ] IOPS, throughput, latency, queueing, and instance/VM limits validated.
- [ ] Recovery-state demand considered.

### Memory
- [ ] WiredTiger cache monitored.
- [ ] Host/container memory boundary validated.
- [ ] Swap behavior reviewed.
- [ ] Memory/storage interaction understood.

### Replication and Kubernetes
- [ ] Replica storage failure domains validated.
- [ ] Initial-sync procedure understood/tested.
- [ ] StorageClass/PVC/CSI/topology/expansion/reclaim policy reviewed where applicable.
- [ ] Attach/detach recovery behavior understood where applicable.

### Operations
- [ ] Disk-full and predictive-capacity alerts configured.
- [ ] Latency/performance alerts configured.
- [ ] Storage dashboard available.
- [ ] Expansion and storage-loss runbooks tested.
- [ ] Backup restore tested.
- [ ] Incident escalation path documented.

## 31. Key SRE/DBRE Principles

```text
Capacity != Performance
Replication != Backup
Disk redundancy != Database redundancy
Provisioned IOPS != Effective MongoDB IOPS
High memory utilization != Memory leak
Cloud volume capability != VM capability
Pod rescheduling != Immediate database recovery
Snapshot != Automatically valid MongoDB backup
```

> **Correlate application, MongoDB, operating-system/Kubernetes, and storage-platform telemetry before concluding that storage itself is the root cause.**
