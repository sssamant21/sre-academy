# 2.9 — Process Management with systemd

**Workflow Stage:** Revised Final / Canonical Edition  
**Book:** MongoDB Administration Handbook  
**Chapter 2:** Installation, Configuration, Patching, and Upgrades  
**Baseline:** MongoDB 8.x  
**Compatibility:** MongoDB 7.x where operationally relevant  
**Status:** Canonical

## Learning Objectives

After completing this section, you should be able to manage MongoDB safely through `systemd`; distinguish MongoDB configuration from service-manager configuration; understand package-managed versus custom services; understand `processManagement.fork` and PID ownership; safely start, stop, and restart `mongod`; inspect effective service configuration; manage boot behavior and dependencies; execute replica-set-aware maintenance; diagnose startup, shutdown, permission, storage, and restart-loop failures; integrate systemd with patching/upgrades; monitor unexpected restarts; manage drift; and execute production lifecycle runbooks.

> **A Running Process ≠ A Healthy MongoDB Deployment**

## 1. Process Management Architecture

MongoDB is a long-running stateful database service. Production operations require a lifecycle manager rather than an administrator's interactive shell.

```text
Linux
  |
  v
systemd
  |
  v
mongod.service
  |
  +-- Process lifecycle
  +-- Service identity
  +-- Startup / shutdown
  +-- Dependencies
  +-- Resource limits
  +-- Restart behavior
  +-- Logging
  |
  v
mongod
  |
  v
MongoDB
  |
  v
Replica / Sharded Topology
  |
  v
Application
```

```text
systemd active != MongoDB healthy != Topology healthy != Application healthy
```

## 2. Prefer Official Package Management

For supported self-managed Linux platforms, prefer MongoDB's official package-management installation procedure unless an operational requirement justifies a custom installation. Custom binary installation transfers additional responsibility for service units, process supervision, configuration paths, permissions, logging, upgrades, rollback, and drift management.

> **Custom Installation = Additional Operational Ownership**

## 3. Package-Managed vs. Custom Services

Determine who owns the effective service definition. Package-managed units should remain package-owned, with organization drop-ins where justified. Custom installations require organization-owned unit definitions and lifecycle procedures. Operators must know who owns, updates, tests, versions, and audits the unit and overrides.

## 4. MongoDB Configuration vs. systemd Configuration

For official Linux package installations, MongoDB configuration is commonly `/etc/mongod.conf`; custom installations may use an organization-defined path. The systemd unit controls executable invocation, configuration-file argument, service identity, lifecycle, and OS-level limits, while MongoDB configuration controls database storage, networking, logging, security, replication, and other runtime settings.

> **systemd Configuration ≠ MongoDB Configuration**

## 5. `processManagement.fork` and systemd

MongoDB exposes daemonization behavior through `processManagement.fork`, while systemd-managed deployments use an external lifecycle manager according to the installed service definition. Do not independently change `processManagement.fork` in a package-managed deployment without validating the installed service's expectations.

> **Do Not Combine Independent Daemonization Models Without Validation**

## 6. PID Management

For normal systemd-managed MongoDB deployments, systemd tracks the service process lifecycle. Inspect the main process with:

```bash
systemctl show mongod -p MainPID
```

Custom PID-file architecture is generally unnecessary merely to determine whether the package-managed service is running. `processManagement.pidFilePath` is more relevant where an external init/service manager is not already handling lifecycle tracking.

> **One MongoDB Instance Should Have One Clearly Defined Lifecycle Owner**

## 7. Inspecting Service State

```bash
systemctl status mongod
systemctl is-active mongod
systemctl is-enabled mongod
```

`is-active` answers whether the service runs now; `is-enabled` answers whether boot startup is configured. Active and enabled are not equivalent, and neither proves database health.

## 8. Inspecting the Effective Unit

```bash
systemctl cat mongod
systemctl show mongod
```

Useful properties may include `ExecStart`, `User`, `Group`, `MainPID`, `Restart`, timeouts, `LimitNOFILE`, environment, fragment path, and drop-in paths.

> **Remembered Configuration ≠ Effective Configuration**

## 9. Service Identity and Permissions

MongoDB should normally run under the dedicated service identity established by the supported installation architecture rather than as root.

```bash
systemctl show mongod -p User -p Group
ps -ef | grep '[m]ongod'
```

Validate access to `dbPath`, logs, configuration, certificates, private keys, key files, and runtime directories. Never solve permission failures by making database directories broadly writable.

## 10. Storage Mount Dependencies

A dangerous boot-time failure occurs when the MongoDB data volume fails to mount but the mount-point directory still exists, allowing `mongod` to start on unintended storage.

```bash
findmnt /data/mongodb
df -h /data/mongodb
lsblk
```

Service architecture must account for required storage availability and ordering.

> **Directory Exists ≠ Correct MongoDB Storage Mounted**

## 11. Starting MongoDB

```bash
sudo systemctl start mongod
systemctl status mongod
systemctl is-active mongod
```

Continue to database and topology validation:

```javascript
db.adminCommand({ ping: 1 })
rs.status()
```

A production startup is complete only after service, MongoDB connectivity, authentication, topology, replication, and application health are validated.

## 12. Stopping MongoDB

```bash
sudo systemctl stop mongod
```

Before stopping a production member, verify the correct environment/host/instance, identify member role, confirm other members are healthy, replication is acceptable, quorum remains safe, maintenance is approved, and application impact is understood.

## 13. Forced Termination

Do not use `kill -9` as routine shutdown. `SIGKILL` prevents normal graceful shutdown handling. Forceful termination is an incident escalation action requiring understanding of why graceful shutdown failed, storage/database state, replica-set redundancy, availability impact, and recovery implications.

> **Process Termination ≠ Controlled Database Shutdown**

## 14. Restarting MongoDB

```bash
sudo systemctl restart mongod
```

Before production restart, identify the member and role, confirm topology and quorum, understand election/application implications, and ensure rollback is available. Treat restart as a controlled database change.

## 15. Replica-Set-Aware Restart

Use one-member-at-a-time maintenance where required: validate the replica set, select one member, apply change, restart, validate service, wait for expected state, validate replication, observe, then proceed.

> **Do not proceed to the next member if the restarted member has not returned to the expected healthy topology state.**

Also stop if replication is unhealthy, quorum is at risk, application impact is unexpected, or recovery differs materially from plan.

## 16. Primary-Aware Maintenance

Restarting a primary can trigger an election, driver topology discovery, reconnection, and retry activity. Understand current primary, eligible secondaries, voting configuration, priorities, replication lag, election implications, and application retry behavior.

> **Primary Restart ≠ Isolated Host Restart**

## 17. Sharded Cluster Awareness

A sharded deployment can include `mongos`, a config-server replica set, and multiple shard replica sets. Identify the process's topology role before maintenance. Detailed rolling-upgrade sequencing is covered later in Chapter 2.

## 18. Boot-Time Enablement

```bash
systemctl is-enabled mongod
sudo systemctl enable mongod
sudo systemctl enable --now mongod
```

Production architecture should deliberately determine whether MongoDB starts automatically after reboot, considering storage, networking, secrets/certificates, recovery behavior, operational gating, and monitoring readiness.

> **Auto-Start Convenience ≠ Production Readiness**

## 19. `daemon-reload`

When a systemd unit or drop-in changes, or when an installed unit is not initially recognized:

```bash
sudo systemctl daemon-reload
```

`daemon-reload` reloads systemd unit definitions; it does not restart MongoDB.

> **`daemon-reload` ≠ MongoDB Restart**

## 20. Applying `mongod.conf` Changes

Editing file-based configuration does not itself change the running process. Normal package-managed file changes require controlled restart when the setting is restart-bound. Runtime-supported mechanisms are covered in sections 2.15–2.17.

> **Configuration File Change ≠ Runtime Change**

## 21. Unit Overrides

Avoid casually modifying package-managed unit files. Use supported drop-in overrides where organization-specific customization is required:

```bash
sudo systemctl edit mongod
systemctl cat mongod
```

This improves ownership clarity, upgrade resilience, rollback, and drift detection.

## 22. Resource Limits

Physical host resources can be constrained by OS/systemd/cgroup controls before reaching `mongod`. Relevant controls can include `LimitNOFILE`, `LimitNPROC`, `TasksMax`, `MemoryMax`, and `CPUQuota` depending on platform.

> **Physical Capacity ≠ Effective MongoDB Capacity**

Detailed tuning belongs in 2.10.

## 23. Restart Policies

Do not establish a universal `Restart=` policy without evaluating the failure model. Persistent configuration, permission, storage, binary, or resource failures can create restart loops, repeated recovery attempts, log storms, and alert storms.

> **Automatic Restart ≠ Automatic Recovery**

## 24. Startup and Shutdown Timeouts

Do not apply arbitrary generic application timeouts. Baseline normal startup, recovery startup, normal shutdown, high-load shutdown, and degraded-storage shutdown behavior. There is no universal timeout suitable for every MongoDB deployment.

## 25. Logging Architecture

Troubleshooting can require systemd/journald, MongoDB logs, OS evidence, storage telemetry, and topology information.

```bash
journalctl -u mongod
journalctl -u mongod -n 100
journalctl -u mongod -b
journalctl -u mongod -f
```

Package-managed deployments commonly use `/var/log/mongodb/mongod.log` when file logging is configured; always inspect effective `systemLog` configuration.

## 26. Boot-Specific Troubleshooting

```bash
journalctl -u mongod -b
```

Validate storage mounts, permissions, network state, secrets/certificates, configuration readability, and dependencies.

> **Manual Start Works ≠ Boot-Time Architecture Correct**

## 27. Failure Scenario — Invalid Configuration

On startup failure after configuration change, inspect `systemctl status mongod`, `journalctl -u mongod -n 100`, and MongoDB logs. Identify and correct/rollback the change, start once, and validate database, topology, and application. Do not repeatedly restart without understanding the failure.

## 28. Failure Scenario — Permissions

```bash
namei -l /data/mongodb
ls -ld /data/mongodb
ls -ld /var/log/mongodb
```

Investigate `dbPath`, logs, certificates, key files, configuration, and security policy.

> **Permission Fix ≠ Disable Security**

## 29. Failure Scenario — Data Volume Missing

Validate the expected volume before MongoDB startup:

```bash
findmnt /data/mongodb
df -h /data/mongodb
```

Production architecture should fail safely rather than silently accepting unintended storage.

## 30. Failure Scenario — Port Conflict

```bash
ss -lntp
ss -lntp | grep ':27017'
```

Determine what owns the port before terminating any process. Check for manually launched/duplicate `mongod` instances or incorrect configuration.

## 31. Failure Scenario — Active but Unhealthy

A service may be `active` while MongoDB connectivity, replication, storage, authentication, or application health is degraded. Validate systemd, process, MongoDB, topology, and application as separate layers.

## 32. Failure Scenario — Restart Loop

```bash
systemctl status mongod
journalctl -u mongod
systemctl show mongod -p Restart -p NRestarts
```

Persistent failure should transition from restart to diagnosis. Investigate configuration, permissions, storage, port conflicts, resource limits, binary/library problems, and security policy.

## 33. Unexpected Restart Detection

Monitor service state, process start time, restart count, MongoDB uptime, replica-set state, replication lag, and application impact. A currently active service may have restarted unexpectedly minutes earlier.

> **Currently Active ≠ Continuously Healthy**

## 34. Slow Shutdown

Do not immediately force-kill a slow shutdown. Inspect MongoDB logs, service state, storage, and shutdown progress. Forceful termination remains a deliberate incident decision.

## 35. Configuration Change Safety Gate

Before change verify correct environment/member, approval, primary identity, topology health, quorum, replication lag, recovery posture, rollback, and monitoring. If unit definitions changed, run `daemon-reload`; restart only when required. Validate systemd, `mongod`, MongoDB connectivity, expected member state, replication, logs, and application health.

Stop the rollout if the member does not recover, replication is unhealthy, quorum is at risk, topology problems persist, application impact exceeds plan, or root cause is not understood.

## 36. OS Patching and Reboots

Before reboot confirm replica-set health, no conflicting outage, acceptable lag, recovery posture, application impact, and monitoring. After reboot validate correct storage, service state, MongoDB reachability, expected member state, replication, logs, application, and monitoring.

> **Host Reboot Complete ≠ Database Maintenance Complete**

## 37. MongoDB Upgrade Integration

Before and after package/binary upgrades verify executable, package ownership, `ExecStart`, configuration path, service identity, unit file, drop-ins, resource limits, and enablement.

```bash
systemctl cat mongod
systemctl status mongod
```

Do not assume a package upgrade leaves every effective service behavior unchanged.

## 38. Automation

Manage package state, unit/drop-ins, `mongod.conf`, service identity, permissions, directories, enablement, service state, and validation declaratively where practical. Avoid automation whose only behavior is to restart MongoDB forever whenever it is down.

## 39. Configuration Drift

Drift can occur in unit files, drop-ins, environment files, permissions, enablement, resource limits, and configuration paths.

```bash
systemctl cat mongod
systemctl show mongod
systemctl is-enabled mongod
```

Approved service configuration should be represented in source control or configuration management. Detailed drift engineering continues in 2.18.

## 40. Monitoring and Alerting

Monitor systemd state/restarts, process PID/uptime, MongoDB connectivity, replica state/lag/elections, storage, host resources, and application errors/latency. Alert on service failure, unexpected/repeated restarts, MongoDB unreachability, unhealthy members, post-restart lag, unexpected primary transitions, and abnormal startup/shutdown duration.

> **Process Exists ≠ Healthy Service**

## 41. Production Start Runbook

Precheck correct host/environment, storage mount, configuration, permissions, and topology impact; start with `systemctl start mongod`; validate service state, database connectivity/ping/logs, topology/replication, and application health.

## 42. Production Stop Runbook

Precheck member identity/role, topology health, quorum, approval, and impact; execute `systemctl stop mongod`; verify service inactive, process stopped, and logs reviewed before maintenance.

## 43. Production Restart Runbook

Confirm reason, topology, redundancy/quorum, restart one member, validate systemd and MongoDB, wait for expected state, validate replication/application, observe burn-in, and continue only when healthy.


```javascript

```

Adapt commands to distribution, security policy, topology, and release.

## 45. Production Anti-Patterns

Avoid manually launching production `mongod` from SSH; running as root without justification; changing `processManagement.fork` without service validation; unnecessary custom PID management; casually editing package units; assuming active means healthy; repeated blind restarts; restarting multiple replica members together; routine `kill -9`; ignoring mount dependencies; generic stateless timeout policies; assuming restart means recovery; ignoring drop-ins during upgrades; aggressive automatic restart without analysis; confusing `daemon-reload` with restart; process-only health checks; and continuing rolling maintenance after a member fails to recover.

## 46. Production Readiness Checklist

Validate package/custom ownership, effective unit, `ExecStart`, configuration path, service identity, `processManagement.fork`, PID ownership, drop-ins, boot policy, storage dependency, network/secrets, timeouts, graceful shutdown, forced-termination escalation, replica rolling restart/quorum, primary behavior, sharded roles, service/restart/uptime monitoring, connectivity/topology monitoring, configuration management, drift detection, upgrade validation, and restart-loop protection.

## 47. Key SRE/DBRE Principles

```text
Process Running != Database Healthy
Service Active != Replica Set Healthy
Service Restarted != Database Recovered
Enabled != Active
Directory Exists != Correct Filesystem Mounted
Automatic Restart != Automatic Recovery
daemon-reload != MongoDB Restart
Package Upgrade != Service Configuration Validated
kill -9 != Controlled Shutdown
```

> **Use systemd as the operating-system lifecycle manager for MongoDB, but validate the service, MongoDB process, database, topology, storage, and application as separate reliability layers.**
