# Chapter 1 — PostgreSQL Architecture and Internals

## 1.1 — PostgreSQL Architecture Overview

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## 1.1.1 Purpose

PostgreSQL is a process-oriented relational database system built around several cooperating architectural layers: client connections, backend processes, shared memory, background processes, query processing, buffer management, MVCC, WAL, locking, storage, replication, and recovery.

```text
Applications / Clients
        |
        v
Connection Interface
        |
        v
PostgreSQL Server
        |
        +-- Client Backend Processes
        +-- Shared Memory Architecture
        +-- Background Processes
        |
        v
Query Processing
        |
        +-- Parser
        +-- Planner / Optimizer
        +-- Executor
        |
        v
Buffer Manager
        |
        +-- MVCC
        +-- WAL
        +-- Locking
        |
        v
Storage Manager
        |
        v
PostgreSQL Storage
```

PostgreSQL's architecture is deliberately modular. Query execution, memory management, concurrency, durability, storage, maintenance, replication, and recovery cooperate but remain distinct subsystems.

## 1.1.2 PostgreSQL Instance vs Database Cluster

A PostgreSQL server instance manages one database cluster, where a PostgreSQL database cluster means a collection of databases managed by a single server instance and data directory. This must be distinguished from an infrastructure or HA cluster containing multiple PostgreSQL nodes.

```text
Database Cluster != HA Cluster
```

## 1.1.3 Process-Based Architecture

PostgreSQL uses operating-system processes extensively. A normal client connection is handled by a dedicated server backend process. This provides process isolation, but also makes connection count an important memory and operating-system capacity concern.

## 1.1.4 Primary Server Process

The `postgres` server program establishes the PostgreSQL instance, initializes required shared resources, listens for connections, and coordinates server processes.

Conceptually:

```text
postgres startup
      |
      +-- Read configuration
      +-- Initialize shared resources
      +-- Initialize shared memory
      +-- Initialize synchronization structures
      +-- Open/listen on configured endpoints
      +-- Start required background processes
      |
      v
Ready for connections
```

## 1.1.5 Shared Memory Architecture

Although PostgreSQL sessions use separate processes, server processes cooperate through shared memory and synchronization mechanisms.

Important shared-memory consumers include shared buffers, WAL buffers, and shared server state.

## 1.1.6 Shared Buffers

`shared_buffers` controls PostgreSQL's principal shared database buffer cache. The buffer manager attempts to satisfy page requests from shared buffers and reads required pages from storage when they are not cached.

PostgreSQL buffering also operates alongside operating-system filesystem caching, so database cache behavior must not be evaluated in isolation from the OS.

## 1.1.7 WAL Architecture

Write-Ahead Logging is a central PostgreSQL durability mechanism. Changes generate WAL records, and the required WAL must reach the configured durability boundary before PostgreSQL can safely consider the corresponding transaction durable. Modified data pages can be written later.

WAL supports crash recovery and forms the foundation for archiving and replication.

## 1.1.8 Storage Architecture

A PostgreSQL data directory contains database storage and critical subsystem directories such as:

```text
PGDATA
 |
 +-- base/       per-database storage
 +-- global/     cluster-wide relations
 +-- pg_wal/     WAL
 +-- pg_xact/    transaction commit status
 +-- pg_tblspc/  tablespace links
 +-- pg_subtrans/
 +-- pg_twophase/
 +-- configuration/state files
```

These are PostgreSQL-managed internal structures. They must not be treated as ordinary application files or manually removed during incidents.

## 1.1.9 Query Processing Architecture

A SQL statement passes through major processing stages:

```text
Client SQL
    |
    v
Parser
    |
    v
Rewrite Processing
    |
    v
Planner / Optimizer
    |
    v
Execution Plan
    |
    v
Executor
    |
    v
Storage / Buffer / MVCC
    |
    v
Results
```

This pipeline is expanded in Section 1.10.

## 1.1.10 MVCC Architecture

PostgreSQL uses Multi-Version Concurrency Control (MVCC). Transactions observe row versions according to snapshot visibility rules, allowing substantial concurrency between readers and writers.

Obsolete tuple versions eventually require cleanup, directly connecting transaction architecture with VACUUM and autovacuum.

## 1.1.11 Background Process Architecture

PostgreSQL uses background processes for durability, maintenance, recovery, WAL handling, autovacuum, archiving, replication, and other responsibilities. PostgreSQL also provides background-worker infrastructure for supported extensions and server-side workers.

Individual processes are covered in later Chapter 1 sections.

## 1.1.12 Connection Architecture

A simplified connection path is:

```text
Application
    |
    v
TCP/IP or Unix-domain socket
    |
    v
PostgreSQL Listener
    |
    v
Authentication / Authorization
    |
    v
Backend Process
    |
    v
Database Session
```

Authentication and access rules include `pg_hba.conf` and the configured authentication methods.

## 1.1.13 Architecture and Connection Pooling

Production environments commonly place a connection pooler between application clients and PostgreSQL to reduce connection churn and limit the number of active PostgreSQL sessions.

```text
Application Fleet
       |
       v
Connection Pool
       |
       v
PostgreSQL
```

PgBouncer is a common example and is covered later in the handbook.

## 1.1.14 High Availability Architecture

PostgreSQL provides mechanisms from which HA solutions are built, including WAL streaming, standby recovery, replication, promotion, and recovery tooling. A complete production HA architecture must additionally address failure detection, leader selection, fencing, traffic routing, RPO, RTO, and failed-node rejoin procedures.

## 1.1.15 Observability Architecture

PostgreSQL exposes internal state through statistics views, logs, wait events, replication views, and other monitoring interfaces. These should be correlated with operating-system, storage, network, and application telemetry.

A core diagnostic view is `pg_stat_activity`.

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity;
```

## 1.1.16 SRE Failure-Domain Model

PostgreSQL should be viewed as interconnected reliability domains rather than as one black box.

For example:

```text
Replication consumer failure
        -> WAL retention
        -> pg_wal growth
        -> filesystem exhaustion
        -> primary availability incident
```

Another common chain is:

```text
Long transaction
        -> old MVCC horizon
        -> vacuum cleanup delayed
        -> dead tuples retained
        -> bloat
        -> increased I/O
        -> higher latency
```

Understanding these dependencies is central to the DBRE/SRE approach used throughout this handbook.

## 1.1.17 Architecture → Reliability Principle

PostgreSQL reliability cannot be managed by monitoring the database as a single black box. SREs and DBREs must understand the interaction among processes, memory, connections, query execution, storage, MVCC, locks, WAL, checkpoints, vacuum, replication, and recovery.

A symptom exposed by one subsystem can originate in another.

## 1.1.18 Production Architecture Checklist

For every production PostgreSQL environment, teams should know:

- PostgreSQL major/minor version
- hosting model
- PGDATA and storage architecture
- database and tablespace layout
- CPU and memory allocation
- `shared_buffers` configuration
- connection limits and pooling architecture
- WAL generation baseline and storage capacity
- checkpoint configuration
- vacuum/autovacuum behavior
- replication topology and replication slots
- backup and WAL archival architecture
- PITR capability
- HA/failover mechanism
- RPO and RTO
- monitoring and alerting architecture
- capacity headroom
- upgrade strategy
- recovery runbooks
- last successful restore and failover tests

## 1.1.19 Production Case Study — “Database Is Slow”

When an application reports increased database latency, checking CPU alone is insufficient. A production investigation should evaluate connection saturation, query plans, blocking, memory/cache behavior, storage latency, WAL pressure, checkpoint activity, and related dependencies.

The architectural model turns a generic performance complaint into a structured diagnostic process.

## 1.1.20 Section Summary

PostgreSQL combines a process-based server model with shared memory, query-processing components, buffer management, MVCC, WAL, locking, storage, maintenance, replication, and recovery subsystems.

This section establishes the architectural map that the remaining Chapter 1 sections progressively decompose.

### SRE/DBRE Principle

> PostgreSQL reliability must be understood as the behavior of interconnected subsystems. A healthy process or metric in one layer does not prove that the complete database reliability path is healthy.
