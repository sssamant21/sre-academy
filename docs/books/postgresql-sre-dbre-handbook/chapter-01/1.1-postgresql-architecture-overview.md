# Chapter 1 — PostgreSQL Architecture and Internals

## 1.1 — PostgreSQL Architecture Overview

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.1.1 Purpose

PostgreSQL is a process-oriented relational database system built from cooperating subsystems: client/backend processes, shared memory, auxiliary and background workers, query processing, buffer management, MVCC, locking, WAL, storage, maintenance, replication, backup, and recovery.

```text
Applications / Clients
        |
        v
Connection Interface
        |
        v
PostgreSQL Server
        |
        +-- Client Backend Processes
        +-- Shared Memory / IPC
        +-- Auxiliary & Background Processes
        |
        v
Query Processing
        |
        +-- Parser / Analysis
        +-- Rewrite System
        +-- Planner / Optimizer
        +-- Executor
        |
        v
Buffer / Storage Access
        |
        +-- MVCC / Locks
        +-- WAL / Checkpoints
        +-- Vacuum / Autovacuum
        |
        v
Physical Storage / Replication / Recovery
```

The purpose of this overview is to establish the dependency map. Later sections own the implementation details so this section intentionally avoids duplicating deep tuning guidance.

## 1.1.2 PostgreSQL Instance vs Database Cluster

A PostgreSQL database cluster is a collection of databases managed by one PostgreSQL server installation/data directory. This is different from the infrastructure use of the word “cluster,” where multiple hosts or database nodes form an HA topology.

```text
PostgreSQL database cluster != multi-node HA cluster
```

This distinction matters in incident communication, backup/restore procedures, upgrades, and cloud-service discussions.

## 1.1.3 Process-Based Architecture

PostgreSQL uses operating-system processes extensively. Normal client sessions are served by backend processes, while specialized server processes perform tasks such as checkpointing, background writing, WAL writing, archiving, recovery, WAL receiving, and autovacuum coordination.

Connection count therefore has real process, memory, file-descriptor, and shared-resource consequences. A high `max_connections` value is not free capacity.

## 1.1.4 Server and Auxiliary Processes

The `postgres` server program initializes the instance, establishes shared resources, listens for connections, and coordinates server operation.

PostgreSQL 18 terminology distinguishes auxiliary processes from other backend/background worker types. Important auxiliary processes include the autovacuum launcher, background writer, checkpointer, logger when enabled, startup process during recovery, WAL archiver, WAL receiver, WAL summarizer when enabled, and WAL writer. WAL senders and autovacuum workers are separate backend types rather than members of that auxiliary-process list.

PostgreSQL 18 also includes I/O worker activity as part of its asynchronous I/O architecture.

## 1.1.5 Shared Memory and IPC

Separate PostgreSQL processes cooperate through shared memory, synchronization primitives, and inter-process communication. Important shared structures include the shared buffer cache, WAL buffers, lock and process state, and other server-wide data structures.

Shared memory must be sized together with backend-private memory, worker concurrency, the operating system, and workload requirements.

## 1.1.6 Buffer and I/O Architecture

`shared_buffers` controls PostgreSQL's primary shared database buffer cache. PostgreSQL statistics do not by themselves distinguish every kernel I/O call that required physical media access from one satisfied by the operating-system page cache, so database I/O metrics should be correlated with OS or cloud-storage telemetry.

PostgreSQL 18 adds a major asynchronous I/O subsystem and expands I/O observability. `pg_stat_io` reports cluster-wide I/O by backend type, object, context, and operation, including WAL-related I/O in PostgreSQL 18.

## 1.1.7 WAL and Durability Architecture

Write-Ahead Logging (WAL) is central to crash recovery and also underpins continuous archiving, physical replication, and logical decoding. The default PostgreSQL 18 `wal_level` is `replica`; `logical` adds information required for logical decoding.

PostgreSQL 18 also supports WAL summarization for incremental backups. When `summarize_wal=on`, the WAL summarizer generates summary information under `pg_wal/summaries`; this requires WAL generated at `wal_level=replica` or higher to produce usable summaries.

WAL durability, checkpoint behavior, archiving, summarization, replication retention, and recovery are treated separately in later sections.

## 1.1.8 Physical Storage Architecture

A PostgreSQL data directory contains database storage plus critical subsystem state. Important locations include:

```text
PGDATA
 |
 +-- base/               per-database default-tablespace relations
 +-- global/             cluster-wide relations
 +-- pg_wal/             WAL
 |    +-- summaries/     WAL summaries when generated
 +-- pg_xact/            transaction commit-status data
 +-- pg_tblspc/          tablespace symbolic links
 +-- pg_subtrans/        subtransaction status
 +-- pg_twophase/        prepared-transaction state
 +-- configuration/state files
```

These are PostgreSQL-managed structures. Manually deleting files from `PGDATA`, especially `pg_wal`, is not an acceptable emergency capacity procedure.

## 1.1.9 Query Processing Architecture

A SQL statement conceptually moves through:

```text
Client SQL
   -> Parse / Analyze
   -> Rewrite
   -> Planner / Optimizer
   -> Plan Tree
   -> Executor
   -> Buffer / Storage / MVCC / Locking
   -> Results
```

A slow request can therefore originate in connection establishment, planning, blocking, CPU execution, memory spill, storage I/O, WAL/commit latency, or client result consumption. Section 1.10 owns the detailed lifecycle.

## 1.1.10 Transaction and MVCC Architecture

PostgreSQL uses Multi-Version Concurrency Control (MVCC). Transactions see tuple versions according to snapshot visibility rules. Updates and deletes can leave obsolete tuple versions that later become reclaimable by VACUUM.

Long transactions can retain old visibility horizons even when they consume little CPU, connecting transaction management directly to vacuum health, bloat, storage consumption, and transaction-ID protection.

## 1.1.11 Locking and Concurrency

MVCC reduces many reader/writer conflicts but does not eliminate locking. PostgreSQL uses relation locks, row locks, transaction-related waits, advisory locks, lightweight locks, buffer pins, and other synchronization mechanisms.

During latency incidents, `state='active'` does not prove that a backend is consuming CPU; inspect `wait_event_type` and `wait_event`.

## 1.1.12 Connection Architecture

A simplified connection path is:

```text
Application
   -> TCP/IP or Unix-domain socket
   -> PostgreSQL listener
   -> startup/authentication exchange
   -> backend session
   -> database workload
```

`pg_hba.conf`, authentication configuration, TLS/GSS settings where used, role privileges, connection limits, reserved connection capacity, and pooling all influence this path. Sections 1.7 and 1.9 own the detailed connection discussion.

## 1.1.13 Background Maintenance Architecture

PostgreSQL availability depends on continuous maintenance and persistence work, not only foreground SQL. Major functions include:

- checkpoint processing
- background dirty-buffer writing
- WAL writing
- autovacuum and autoanalyze
- WAL archiving
- recovery and WAL receiving
- WAL summarization when enabled
- replication workers
- parallel workers
- extension/background workers
- PostgreSQL 18 asynchronous I/O workers

These process types compete for CPU, memory, worker capacity, and storage throughput with application traffic.

## 1.1.14 High Availability and Recovery Architecture

PostgreSQL provides primitives for standby recovery, WAL streaming, promotion, backup, archiving, and point-in-time recovery. A production HA solution additionally needs safe failure detection, fencing, writer routing, RPO/RTO policy, failed-node reconciliation, and tested recovery procedures.

Replication alone is not a complete HA architecture.

## 1.1.15 Observability Architecture

PostgreSQL 18.4 provides a broad observability surface. Important views and functions include:

- `pg_stat_activity`
- `pg_stat_replication`
- `pg_stat_wal_receiver`
- `pg_replication_slots`
- `pg_stat_subscription` and `pg_stat_subscription_stats`
- `pg_stat_archiver`
- `pg_stat_io`
- `pg_stat_bgwriter`
- `pg_stat_checkpointer`
- `pg_stat_wal`
- progress views for VACUUM, ANALYZE, CREATE INDEX, COPY, base backup, and related operations
- per-backend I/O and WAL statistics functions introduced/expanded in PostgreSQL 18

Example session inspection:

```sql
SELECT pid,
       backend_type,
       usename,
       datname,
       state,
       wait_event_type,
       wait_event,
       xact_start,
       query_start,
       query
FROM pg_stat_activity
ORDER BY pid;
```

For I/O timing, remember that `track_io_timing` and `track_wal_io_timing` are disabled by default and can add platform-dependent timing overhead. PostgreSQL 18 reports WAL timing through `pg_stat_io` rather than the older PostgreSQL-version assumptions around `pg_stat_wal` timing columns.

## 1.1.16 SRE Failure-Domain Model

PostgreSQL should be treated as interconnected reliability domains.

```text
Replication consumer failure
   -> WAL retention
   -> pg_wal growth
   -> storage exhaustion risk
   -> primary availability risk
```

```text
Long transaction
   -> old visibility horizon
   -> vacuum cleanup delayed
   -> dead tuples retained
   -> bloat / more I/O
   -> latency and capacity pressure
```

```text
Archive failure
   -> recovery-chain risk
   -> WAL backlog
   -> pg_wal capacity pressure
```

```text
Worker / I/O saturation
   -> maintenance or query progress slows
   -> queues and lag increase
   -> application latency rises
```

The visible symptom is often several dependencies away from the original cause.

## 1.1.17 Architecture → Reliability Principle

PostgreSQL reliability cannot be managed as a single black box. SRE/DBRE teams must understand how connections, processes, memory, workers, query execution, storage, MVCC, locks, WAL, checkpoints, vacuum, backup, replication, and recovery interact.

A healthy CPU graph or a running `postgres` process does not prove that the database service is healthy.

## 1.1.18 Production Architecture Checklist

For every production PostgreSQL environment, maintain an authoritative record of:

- exact PostgreSQL major/minor version and build/provider
- hosting model and failure domains
- PGDATA, tablespaces, storage type, IOPS/throughput/latency limits
- CPU and memory allocation
- connection limits, reserved capacity, and pooling architecture
- shared-memory and concurrency-sensitive memory settings
- WAL generation baseline and `pg_wal` capacity
- checkpoint behavior and baseline
- vacuum/autovacuum health and transaction-age baseline
- replication topology, slots, synchronous-replication policy, and lag objectives
- backup type, retention, WAL/archive design, and incremental-backup dependencies if used
- PITR capability and tested restore procedure
- HA/failover mechanism, fencing, writer routing, RPO, and RTO
- monitoring, logs, wait events, I/O telemetry, and alert thresholds
- capacity headroom and growth forecast
- extension inventory and worker dependencies
- upgrade strategy
- recovery and incident runbooks
- date/result of the last successful restore test
- date/result of the last successful failover test

## 1.1.19 Production Case Study — “Database Is Slow”

An application reports increased database latency while host CPU remains moderate. A production investigation should not jump directly to query tuning.

A structured path is:

```text
Latency
  -> connection/pool saturation?
  -> blocking or transaction-age issue?
  -> query-plan/cardinality regression?
  -> CPU or worker saturation?
  -> shared-buffer / storage read pressure?
  -> temp spill?
  -> WAL flush or checkpoint pressure?
  -> vacuum/maintenance contention?
  -> replication/synchronous-commit dependency?
  -> client/network result-consumption delay?
```

The architecture model converts “PostgreSQL is slow” into a set of measurable failure domains.
