# 1.10 — PostgreSQL Query Execution Lifecycle

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

A PostgreSQL SQL request moves through a defined lifecycle from client protocol handling to parsing, analysis/rewrite, planning, execution, storage access, transaction handling, and result delivery. For SRE/DBRE work, identifying the stage consuming time is essential to separating connection latency, planning latency, lock waits, CPU execution, memory pressure, and storage I/O.

## Lifecycle

```text
Client SQL
  -> Backend session
  -> Parse / analyze
  -> Rewrite
  -> Planner / optimizer
  -> Plan tree
  -> Executor
  -> Access methods / buffer manager / MVCC
  -> WAL and transaction processing where required
  -> Result serialization
  -> Client
```

PostgreSQL internals document the parser, rule system, planner/optimizer, and executor as distinct stages of query processing.

## Parse and Analysis

The parser checks SQL syntax and transforms the statement into PostgreSQL's internal representation. Semantic analysis resolves objects, types, operators, and other database metadata required for later stages. Failures here normally surface as syntax, object-resolution, permission, or type errors rather than execution-time performance problems.

## Rewrite System

PostgreSQL's rewrite system can transform the parsed query before planning. Views and rules are important examples. DBRE investigations should therefore remember that the statement submitted by the application is not always identical to the effective query tree passed to the planner.

## Planner / Optimizer

The planner evaluates alternative access paths and join strategies using relation statistics and cost estimates. It produces a plan tree for the executor. Planner decisions are influenced by table/index statistics, estimated cardinality, cost constants, available indexes, query structure, parallel-query eligibility, and configuration.

`effective_cache_size` is a planner estimate; it does not allocate PostgreSQL memory or reserve operating-system cache.

## Executor

The executor runs the selected plan tree and requests tuples through plan nodes and access methods. Runtime can involve CPU processing, shared-buffer lookups, filesystem reads, temporary-file I/O, locks, MVCC visibility checks, WAL generation for writes, and synchronization with other processes.

## EXPLAIN and EXPLAIN ANALYZE

Use `EXPLAIN` to inspect the planned execution strategy. `EXPLAIN (ANALYZE, BUFFERS)` executes the statement and reports actual runtime information and buffer activity, so it must be used carefully with modifying statements in production.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

For write statements, use a safe test environment or an explicitly controlled transaction when appropriate; do not casually execute production-changing statements merely to obtain an execution plan.

## Parallel Query

When the planner chooses parallel execution, a plan can contain `Gather` or `Gather Merge`. The session leader requests parallel workers, subject to limits including `max_parallel_workers_per_gather`, `max_parallel_workers`, and `max_worker_processes`. A query can receive fewer workers than planned, including zero, when workers are unavailable.

## Waits During Execution

A query shown as active can still be waiting rather than consuming CPU. Always correlate query state with `wait_event_type` and `wait_event` in `pg_stat_activity`.

```sql
SELECT pid, datname, usename, state,
       wait_event_type, wait_event,
       query_start, xact_start, query
FROM pg_stat_activity
WHERE state <> 'idle';
```

Important diagnostic categories include locks, client communication, WAL, I/O, IPC, and other synchronization waits.

## SRE/DBRE Diagnostic Model

```text
Slow SQL
  |
  +-- connection/startup delay?
  +-- lock wait?
  +-- planning problem?
  +-- cardinality-estimation problem?
  +-- CPU-heavy executor node?
  +-- cache miss / storage I/O?
  +-- temporary spill?
  +-- WAL/commit latency?
  +-- parallel-worker shortage?
  +-- client unable to consume results?
```

Do not label every slow statement a “bad query.” Determine where time is actually spent.

## Monitoring and Alerting

Monitor active-query duration, transaction duration, wait-event distribution, temporary-file generation, database I/O, lock waits, plan regressions, and workload-level latency percentiles. Where `pg_stat_statements` is deployed, use it to identify high-total-time and high-mean-time statement families rather than relying only on instantaneous activity snapshots.

Alerting should be workload-aware. Prefer sustained abnormal latency, blocking chains, transaction-age growth, spill growth, or resource saturation over a single universal query-duration threshold.

## Failure Scenarios

Common production patterns include stale statistics causing poor cardinality estimates, missing or unsuitable indexes, lock contention, excessive sorts/hashes spilling to disk, connection storms increasing concurrency, storage latency, checkpoint-related I/O pressure, parallel-worker exhaustion, and long transactions retaining MVCC state.

## Troubleshooting Workflow

1. Identify the affected workload and latency window.
2. Inspect `pg_stat_activity` and wait events.
3. Identify blocking sessions when lock waits exist.
4. Compare database, CPU, memory, storage, WAL, and checkpoint telemetry.
5. Inspect representative plans with `EXPLAIN`; use `ANALYZE` only when safe.
6. Validate planner statistics and row-estimate accuracy.
7. Check temporary I/O and memory-sensitive plan nodes.
8. Compare the current plan/latency with the known-good baseline.
9. Fix the root cause rather than terminating sessions as the default response.

## Production Case Study — Query Latency Spike

An API latency incident can initially appear to be a query-plan regression. `pg_stat_activity` may instead show many sessions waiting on locks behind one long-running transaction. In that case, adding an index does not address the incident. The correct response is to identify the blocker, determine whether cancellation/termination is safe, restore transaction hygiene, and prevent recurrence through application timeouts and monitoring.

## SRE/DBRE Principle

> Query performance is the result of the entire execution lifecycle. Diagnose the stage and wait condition before tuning SQL, indexes, memory, or storage.
