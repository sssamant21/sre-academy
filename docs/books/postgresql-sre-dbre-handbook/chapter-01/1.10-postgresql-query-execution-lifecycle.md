# 1.10 — PostgreSQL Query Execution Lifecycle

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

A PostgreSQL SQL request moves through a defined backend lifecycle: protocol handling, parsing and semantic transformation, query rewriting, planning/optimization, execution, storage/MVCC access, and result delivery. For SRE/DBRE work, identifying the stage consuming time is essential to separating connection latency, planning latency, lock waits, CPU execution, memory pressure, storage I/O, WAL/commit latency, and client-side result consumption.

## Lifecycle

```text
Client SQL
  -> Backend session
  -> Parse / semantic transformation
  -> Rewrite
  -> Planner / optimizer
  -> Plan tree
  -> Executor
  -> Access methods / buffer manager / MVCC
  -> WAL and transaction processing where required
  -> Result serialization / protocol delivery
  -> Client
```

PostgreSQL internals document the parser, rule system, planner/optimizer, and executor as distinct query-processing stages.

## Parse and Semantic Transformation

The parser first performs lexical/syntactic processing and builds an internal parse tree. PostgreSQL then transforms that raw representation into a query tree, resolving objects, types, operators, expressions, and other semantic information required by later stages.

Failures here normally surface as syntax, object-resolution, permission, or type errors rather than executor-time performance problems.

## Rewrite System

PostgreSQL's rule system performs query rewriting between parsing/transformation and planning. Both the input and output of the rewriter are query trees. Views and rules are important examples of constructs that can alter the effective query tree.

For DBRE investigations, the SQL submitted by an application is therefore not always identical to the effective query tree ultimately passed to the planner.

## Planner / Optimizer

The planner/optimizer evaluates possible execution strategies and selects the plan expected to have the lowest estimated cost. Decisions can depend on:

- table and column statistics
- cardinality/selectivity estimates
- available indexes and access methods
- join ordering and algorithms
- planner cost constants
- query structure and predicates
- partition pruning
- parallel-query eligibility
- memory-related planning assumptions
- configuration and extension-provided planner behavior

For sufficiently complex join problems, PostgreSQL can use the Genetic Query Optimizer (GEQO) rather than exhaustively considering all join orders.

`effective_cache_size` is a planner estimate of cache likely to be available to a query. It does **not** allocate PostgreSQL memory or reserve operating-system cache.

Planner method switches such as `enable_seqscan` are diagnostic/tactical controls, not the preferred long-term fix for poor plans. Better remedies normally include accurate statistics, appropriate indexes, correct SQL design, and evidence-based planner cost configuration.

## Executor

The executor runs the selected plan tree. Plan nodes request tuples from their child nodes and ultimately from table/index access methods.

Runtime can involve:

- CPU processing
- shared-buffer hits and reads
- filesystem/storage I/O
- temporary-file I/O
- sorts and hashes
- locks and synchronization
- MVCC visibility checks
- WAL generation for writes
- trigger execution
- parallel workers
- client/protocol result serialization

The executor is therefore only one part of end-to-end SQL latency.

## EXPLAIN and EXPLAIN ANALYZE

Use `EXPLAIN` to inspect the plan selected by the optimizer without executing the statement.

```sql
EXPLAIN
SELECT ...;
```

`EXPLAIN (ANALYZE, BUFFERS)` actually executes the statement and reports runtime information and buffer activity:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

For data-modifying statements, `ANALYZE` causes the modification and other side effects to occur. In a safe diagnostic context, a transaction can sometimes be used to roll back the data changes:

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE ...;
ROLLBACK;
```

This is not universally side-effect-free: external effects, volatile functions, sequence changes, locking, workload impact, and other behaviors must still be considered. Prefer representative staging/replay environments for risky statements.

PostgreSQL 18 `EXPLAIN` also supports useful options including `WAL`, `SERIALIZE`, `SETTINGS`, and `MEMORY`. `MEMORY` reports memory consumed by the **planning phase**, not total executor memory.

A production-safe plan investigation often starts with:

```sql
EXPLAIN (VERBOSE, SETTINGS)
SELECT ...;
```

and escalates to `ANALYZE` only when execution risk is understood.

## Understanding EXPLAIN Timing Boundaries

`EXPLAIN ANALYZE` planning time covers plan generation/optimization but does not include parsing or rewriting. Its execution time includes executor startup/shutdown and relevant trigger execution, but normal top-level node timing does not include sending result rows to a remote client.

PostgreSQL 18's `SERIALIZE` option can measure the cost of converting output into protocol/displayable form, helping separate executor work from result-serialization overhead.

This distinction matters when the database plan is fast but an application still observes high end-to-end latency.

## Cardinality Estimation

Large differences between estimated and actual row counts are often a key sign of planner-estimation problems.

Potential causes include:

- stale statistics
- insufficient statistics target
- correlated columns not represented by ordinary statistics
- highly skewed distributions
- expression/predicate characteristics
- rapidly changing data

Do not immediately force an access method. First determine why the planner's model differs from reality.

## Parallel Query

When the optimizer determines that parallel execution is beneficial, the plan contains `Gather` or `Gather Merge` above the parallel portion.

The leader backend requests parallel workers subject to limits including:

```text
max_parallel_workers_per_gather
max_parallel_workers
max_worker_processes
```

A query can launch fewer workers than planned, including zero, when workers are unavailable. This can produce latency variation even when the SQL and stored plan shape appear unchanged.

`Gather Merge` preserves sorted worker output through a merge, while `Gather` does not preserve such ordering.

Detailed parallel-query architecture remains in Section 1.21.

## Waits During Execution

A query whose `state` is `active` can still be waiting rather than consuming CPU. Always correlate state with `wait_event_type` and `wait_event`.

```sql
SELECT pid,
       datname,
       usename,
       application_name,
       state,
       wait_event_type,
       wait_event,
       query_start,
       xact_start,
       query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

Important diagnostic domains include locks, client communication, WAL, I/O, IPC, lightweight locks, and other synchronization waits.

## Prepared Statements and Plan Reuse

Prepared statements can use custom or generic plans depending on PostgreSQL's plan-cache behavior. This matters when parameter selectivity differs substantially between executions: a plan appropriate for one parameter distribution may not be ideal for another.

When diagnosing unexplained plan behavior, determine whether the application is using prepared statements, server-side plan caching, or a pooler/proxy that changes session behavior.

## JIT

PostgreSQL can use Just-in-Time compilation for eligible queries when built/configured with JIT support and when planner cost thresholds justify it. JIT can reduce CPU execution cost for sufficiently expensive queries but adds compilation overhead.

For short OLTP statements, compilation overhead can outweigh the benefit. Diagnose JIT from the actual plan and workload rather than enabling/disabling it globally as a generic tuning response.

## SRE/DBRE Diagnostic Model

```text
Slow SQL
  |
  +-- connection/startup delay?
  +-- parse/rewrite/planning overhead?
  +-- cardinality-estimation problem?
  +-- plan-cache / parameter sensitivity?
  +-- lock or synchronization wait?
  +-- CPU-heavy executor node?
  +-- cache miss / storage I/O?
  +-- temporary spill?
  +-- WAL/commit latency?
  +-- parallel-worker shortage?
  +-- JIT overhead?
  +-- serialization/result-volume cost?
  +-- client unable to consume results?
```

Do not label every slow statement a “bad query.” Determine where time is actually spent.

## Monitoring

Monitor at least:

- active query duration
- transaction duration
- wait-event distribution
- blocked sessions and blocker age
- temporary files/bytes
- database and backend I/O
- WAL generation and write/flush latency
- checkpoint activity
- CPU saturation
- parallel worker availability
- plan changes/regressions
- query latency percentiles

Where `pg_stat_statements` is installed and enabled, use normalized statement statistics to identify high-total-time, high-mean-time, high-call-count, and I/O-heavy statement families rather than relying only on instantaneous `pg_stat_activity` snapshots.

## Alerting

Prefer workload-aware alerts for sustained abnormal latency, blocking chains, transaction-age growth, temporary-spill growth, I/O saturation, or plan regressions.

Avoid one universal query-duration threshold for all workloads. Batch jobs, reporting queries, OLTP calls, maintenance SQL, and replication/administrative work have different expected latency envelopes.

## Failure Scenarios

Common production patterns include:

- stale/inadequate statistics causing poor cardinality estimates
- missing or unsuitable indexes
- lock contention
- sorts/hashes spilling to temporary storage
- connection storms increasing concurrency
- storage latency
- checkpoint-related I/O pressure
- parallel-worker exhaustion
- long transactions retaining MVCC state
- generic/custom plan mismatch
- excessive result volume or slow clients
- JIT overhead on unsuitable workloads

## Troubleshooting Workflow

1. Identify the affected workload, statement family, and latency window.
2. Determine whether delay occurs before execution, during execution, at commit, or during result delivery.
3. Inspect `pg_stat_activity`, wait events, and blocking relationships.
4. Compare CPU, memory, storage, WAL, checkpoint, and network telemetry.
5. Inspect a representative plan with `EXPLAIN`; use `ANALYZE` only when safe.
6. Compare estimated and actual row counts where execution is measured.
7. Validate statistics freshness and whether extended statistics are appropriate.
8. Check temporary I/O and memory-sensitive plan nodes.
9. Check prepared/generic-plan behavior where relevant.
10. Compare current plan/latency with a known-good baseline.
11. Fix the root cause rather than terminating sessions or disabling planner features as the default response.

## Production Case Study — Query Latency Spike

An API latency incident initially appears to be a plan regression because many SQL calls are slow. CPU and storage remain normal. `pg_stat_activity` shows the affected backends are active but waiting on locks behind one old transaction.

Adding an index or raising `work_mem` would not address the incident. The correct response is to identify the root blocker, determine whether cancellation/termination is safe, restore transaction hygiene, validate latency recovery, and prevent recurrence with transaction timeout/monitoring controls.

## Production Readiness Checklist

- planner statistics are maintained and monitored
- slow-query diagnostics include wait events
- `pg_stat_statements` is deployed where operationally appropriate
- representative plans are retained for critical queries
- plan-regression procedures are documented
- `EXPLAIN ANALYZE` production guardrails are documented
- temporary I/O is monitored
- blocking-chain diagnostics are automated
- parallel-worker capacity is monitored
- prepared-statement behavior is understood for critical applications
- JIT behavior is validated for applicable workloads
- database telemetry can be correlated with application latency

## SRE/DBRE Principle

> Query performance is the result of the entire execution lifecycle. Diagnose the stage, plan, resource path, and wait condition before tuning SQL, indexes, memory, storage, or PostgreSQL planner settings.
