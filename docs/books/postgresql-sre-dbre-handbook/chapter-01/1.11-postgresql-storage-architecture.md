# 1.11 — PostgreSQL Storage Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL storage architecture maps logical database objects to relation forks, file segments, pages, tablespaces, transaction-state directories, WAL, temporary files, the buffer/I/O subsystem, the operating-system filesystem/cache, and ultimately persistent storage. For SRE/DBRE teams, this architecture is fundamental to diagnosing capacity exhaustion, latency, temporary spill, WAL growth, checkpoint pressure, relation bloat, tablespace failures, and corruption symptoms.

## Logical-to-Physical Model

```text
Database cluster
  -> databases / tablespaces
     -> relations (tables, indexes, TOAST relations)
        -> forks
           -> file segments
              -> PostgreSQL pages
                 -> buffer / I/O subsystem
                    -> filesystem / OS cache
                       -> block or managed storage
```

A PostgreSQL server instance manages one database cluster. The cluster's data directory is commonly referred to as `PGDATA`.

## PGDATA Layout

Important storage domains include:

- `base/` — per-database storage in the default tablespace
- `global/` — cluster-wide relations
- `pg_wal/` — write-ahead log
- `pg_xact/` — transaction commit status
- `pg_multixact/` — multitransaction status used for shared row locks
- `pg_replslot/` — replication-slot state
- `pg_logical/` — logical-decoding state
- `pg_tblspc/` — symbolic links to user-defined tablespaces
- `pg_twophase/` — prepared-transaction state
- `pg_stat/` and related statistics storage

Treat these as PostgreSQL-managed state. Never remove internal files or directories as an ad-hoc capacity-remediation technique.

## Relations, Filenodes, and Segments

Ordinary tables and indexes are represented by relation files. PostgreSQL identifies the physical relation file using a filenode number. A relation's filenode is not guaranteed to equal its OID, and operations such as `TRUNCATE`, `REINDEX`, `CLUSTER`, and some forms of `ALTER TABLE` can change the filenode without changing the logical object identity.

Use PostgreSQL functions rather than guessing physical paths:

```sql
SELECT pg_relation_filenode('public.orders'::regclass),
       pg_relation_filepath('public.orders'::regclass);
```

With the standard build configuration, relation files larger than 1 GiB are split into segments such as:

```text
12345
12345.1
12345.2
```

The segment size is a build-time characteristic and should not be hard-coded into automation without validation.

## Relation Forks

PostgreSQL stores different kinds of relation metadata in forks.

### Main fork

Contains the primary table or index pages.

### Free Space Map (`_fsm`)

Tracks available space within heap and most index relations so PostgreSQL can locate pages suitable for new tuples or index entries.

### Visibility Map (`_vm`)

Heap relations use a visibility map with two bits per heap page: all-visible and all-frozen. Visibility-map state is important for vacuum behavior, freezing, and index-only scans. Indexes do not have visibility maps.

### Initialization fork (`_init`)

Unlogged tables and indexes have an initialization fork used to restore their empty state after crash recovery.

## PostgreSQL Page Architecture

Tables and indexes are arrays of fixed-size pages. The standard PostgreSQL build uses 8 KiB pages, although page size can be selected when PostgreSQL is compiled.

A typical page contains:

```text
+---------------------------+
| PageHeaderData            |
+---------------------------+
| ItemIdData array          |
+---------------------------+
| Free space                |
+---------------------------+
| Tuple / index items       |
+---------------------------+
| Special space (if used)   |
+---------------------------+
```

For heap tuples, a CTID identifies a tuple using a page/block number and item identifier. CTIDs are physical locations and can change after row updates or table rewrites; they are not durable application identifiers.

## TOAST Architecture

PostgreSQL uses TOAST to handle values too large to fit conveniently inside normal heap tuples. A table containing potentially wide values can have an associated TOAST relation referenced through `pg_class.reltoastrelid`.

Capacity analysis must therefore consider:

```text
base table
+ indexes
+ TOAST table
+ TOAST index
```

Large-value workloads can have significantly different storage and I/O behavior from what the visible base-table row width suggests.

## Tablespaces

User-defined tablespaces place database objects outside the default `PGDATA/base` location. PostgreSQL represents them through links under `PGDATA/pg_tblspc` to the physical tablespace locations.

Tablespaces create independent operational failure domains. A PostgreSQL instance can remain running while objects in one tablespace become unavailable because its filesystem, volume, mount, or storage service has failed.

Production controls should validate:

- mount availability before PostgreSQL startup
- ownership and permissions
- capacity and inode headroom where relevant
- latency, IOPS, throughput, and queue depth
- backup/restore coverage
- monitoring coverage
- behavior after host reboot or failover

Do not remove or relocate tablespace directories manually while PostgreSQL is using them.

## Temporary File Architecture

Queries that cannot complete memory-sensitive operations within their memory budget can write temporary files. PostgreSQL normally places temporary files under a `pgsql_tmp` directory in the relevant database/tablespace storage location.

Typical sources include:

- sorts
- hashes
- materialization
- temporary query results
- index/maintenance operations where applicable

A temporary-file surge can exhaust storage even when permanent relation size is stable.

Do not respond by globally increasing `work_mem` without concurrency-aware memory modeling; doing so can replace a disk-pressure incident with an OOM incident.

## Buffer and Storage I/O Path

A simplified relation read path is:

```text
Executor / access method
   -> PostgreSQL buffer manager
      -> shared_buffers hit
         OR
      -> PostgreSQL I/O subsystem
         -> filesystem / OS cache
            -> persistent storage
```

Writes involve dirty shared buffers, WAL durability ordering, background/checkpoint writes, filesystem behavior, and the persistent storage layer.

A buffer hit does not mean that the entire database workload is independent of storage. WAL, temporary files, checkpoints, vacuum, relation extension, cache misses, and maintenance can all generate substantial I/O.

## PostgreSQL 18 Asynchronous I/O

PostgreSQL 18 introduces an asynchronous I/O subsystem. Eligible operations can queue multiple I/O requests rather than waiting for each request serially. PostgreSQL 18 uses this capability for operations including sequential scans, bitmap heap scans, and vacuum.

Important PostgreSQL 18 settings include:

- `io_method`
- `io_workers` when using the worker implementation
- `io_max_concurrency`
- `effective_io_concurrency`
- `maintenance_io_concurrency`

`io_method` can use supported implementations such as worker-based AIO, `io_uring` when PostgreSQL is built appropriately, or synchronous execution of AIO-eligible work.

Do not carry pre-18 storage-tuning assumptions into PostgreSQL 18 without retesting.

## PostgreSQL 18 I/O Observability

`pg_stat_io` provides cluster-wide I/O statistics by backend type, I/O object, and I/O context. PostgreSQL 18 adds byte counters and WAL I/O activity to this view.

PostgreSQL 18 also provides:

```sql
SELECT * FROM pg_aios;
```

for in-use asynchronous-I/O handles, and per-backend I/O statistics through PostgreSQL statistics functions.

Important caveat: `pg_stat_io` does not represent every possible filesystem operation. For example, some relation I/O that bypasses shared buffers is not currently tracked. Always correlate PostgreSQL statistics with OS/cloud storage telemetry.

## Dirty Pages, WAL, and Checkpoints

A committed change does not require its modified heap/index page to have already reached the data file. WAL provides the required durability ordering, while dirty buffers can be written later by PostgreSQL processes and checkpoint activity.

```text
change data page
   -> generate WAL
   -> WAL durability requirements satisfied
   -> commit acknowledgement according to configuration
   -> dirty data page persisted later
```

Checkpoint architecture, WAL durability, and buffer management are covered in dedicated sections; this section focuses on their storage relationship.

## Storage Capacity Domains

Monitor storage independently by failure domain:

1. PGDATA/default tablespace
2. `pg_wal`
3. every user-defined tablespace
4. temporary-file locations
5. WAL archive destination where self-managed
6. backup/staging storage
7. operating-system/root filesystem where separate

One aggregate filesystem percentage can hide a critical PostgreSQL storage domain approaching exhaustion.

## Capacity and Growth Queries

Database sizes:

```sql
SELECT datname,
       pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;
```

Largest relations in the current database:

```sql
SELECT n.nspname AS schema_name,
       c.relname,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','m')
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;
```

Tablespace usage should be monitored both logically through PostgreSQL and physically at the storage layer.

## Monitoring Architecture

Correlate PostgreSQL and infrastructure telemetry.

### PostgreSQL

- database/relation/index/TOAST growth
- `pg_stat_io`
- temporary bytes/files
- WAL generation
- checkpoint activity
- vacuum activity
- replication-slot retention
- archiver state
- relation extension/write behavior

### OS / cloud storage

- used and free capacity
- growth rate
- read/write latency
- IOPS
- throughput
- queue depth
- burst-credit or provisioned-performance limits where applicable
- filesystem errors
- mount health
- inode usage where relevant

## Alerting Strategy

Prefer trend-aware and failure-domain-specific alerts.

### Warning

- projected storage exhaustion approaching the operational response window
- sustained latency above the workload baseline
- unusual temporary-file growth
- abnormal relation growth
- WAL retention increasing

### Critical

- projected exhaustion before operators can safely remediate
- filesystem or volume unavailable
- write errors
- tablespace unavailable
- WAL storage approaching exhaustion
- storage latency causing database-wide availability impact

Static percentage thresholds can still be useful as guardrails, but they should not replace growth-rate and time-to-exhaustion alerts.

## Failure Scenarios

### 1. Replication slot retains WAL

A failed or abandoned consumer prevents required WAL from being released. `pg_wal` grows despite stable table size.

### 2. Archive pipeline failure

Completed WAL cannot be archived successfully and WAL retention grows.

### 3. Temporary-file explosion

Concurrent sorts/hashes spill heavily and fill the temporary storage domain.

### 4. Tablespace mount failure

PostgreSQL remains reachable, but relations located in the affected tablespace fail when accessed.

### 5. Checkpoint/storage saturation

Dirty-page persistence competes with application, WAL, vacuum, and maintenance I/O, increasing latency.

### 6. Managed-storage performance ceiling

A cloud volume reaches provisioned IOPS/throughput or burst limits even though free capacity remains high.

### 7. Unsafe manual cleanup

An operator deletes PostgreSQL-managed files to recover space, converting a capacity incident into corruption or unrecoverable data loss.

## Troubleshooting Workflow

1. Identify the affected storage failure domain.
2. Measure free capacity and time to exhaustion.
3. Measure latency, IOPS, throughput, and queue depth.
4. Identify whether growth is relation data, indexes/TOAST, WAL, temporary files, or another domain.
5. Inspect replication slots and archiving before any WAL remediation.
6. Correlate checkpoint, vacuum, query, backup, and replication activity.
7. Check mount/filesystem/storage-service health.
8. Validate cloud provisioned-performance limits where applicable.
9. Preserve database integrity; never delete PostgreSQL-managed files as an emergency shortcut.
10. Verify growth and latency return to baseline after remediation.

## Recovery Guidance

Storage recovery depends on the failed domain:

- **capacity pressure:** stop or reduce the source safely, extend storage where supported, and correct the retention/growth cause
- **tablespace failure:** restore the underlying storage/mount before attempting object-level remediation
- **WAL pressure:** resolve archiving/replication retention while preserving recovery requirements
- **temporary-file pressure:** control offending workload/concurrency and restore headroom
- **corruption/storage error:** preserve evidence and follow validated backup/recovery procedures rather than attempting file-level repair by guesswork

## Automation Guardrails

Safe automation can:

- forecast time to storage exhaustion
- inventory tablespaces and mount targets
- rank relation growth
- detect abnormal WAL retention
- correlate temporary-file growth with query workload
- validate storage mounts before database startup
- verify storage headroom before maintenance operations

Automation must not delete WAL, relation files, transaction-status files, or tablespace contents based solely on filesystem age or utilization.

## Production Case Study — Stable Database Size, Rapid Disk Growth

A primary database reports almost unchanged table sizes while its WAL filesystem grows rapidly. Investigation shows an inactive replication slot whose consumer has been offline. Because the slot protects WAL required by that consumer, PostgreSQL retains the WAL rather than recycling it.

The correct response is:

1. identify the slot and consumer
2. quantify retained WAL and time to exhaustion
3. determine whether the consumer can safely resume
4. preserve the required RPO/recovery contract
5. intentionally remove or recreate the slot only when the data-loss/resynchronization implications are understood
6. verify WAL recycling and filesystem recovery

Deleting files directly from `pg_wal` is not an acceptable remediation.

- [ ] checkpoint/storage latency correlated

- [ ] `pg_stat_io` included in observability

## SRE/DBRE Principle

> PostgreSQL storage must be operated as multiple interacting failure domains. Diagnose what is consuming or delaying storage—relation data, WAL, temporary I/O, checkpoints, vacuum, replication retention, or the storage service itself—before choosing remediation.
