# 1.11 — PostgreSQL Storage Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL storage architecture connects logical database objects to physical files, pages, forks, tablespaces, WAL, transaction-status data, temporary I/O, and the operating-system storage stack. DBRE/SRE teams must understand this path because storage latency, capacity exhaustion, corruption, WAL growth, temporary spills, and checkpoint pressure can all present as database availability or performance incidents.

## Logical-to-Physical Model

```text
Database objects
  -> relations
  -> relation forks
  -> segments/files
  -> PostgreSQL pages
  -> filesystem
  -> block/storage layer
```

The PostgreSQL data directory includes per-database relation storage under `base`, cluster-wide relations under `global`, WAL under `pg_wal`, transaction commit status under `pg_xact`, and tablespace links under `pg_tblspc`.

## Relation Storage

Tables and indexes are represented by relation files. Large relations are divided into file segments rather than stored as one indefinitely growing file. PostgreSQL also uses multiple forks for particular relation metadata and behavior, including the main fork and auxiliary forks such as free-space and visibility information.

Do not manipulate relation files directly while PostgreSQL is running. SQL-level object identity must not be inferred solely from a filename without understanding PostgreSQL relfilenode/storage behavior.

## Pages and Blocks

PostgreSQL reads and writes relations in fixed-size pages, commonly 8 KiB in standard builds. The buffer manager operates on these pages. A logical row operation can therefore involve page access, visibility checks, index access, WAL generation, and later dirty-page flushing.

## Tablespaces

Tablespaces allow database objects to be located outside the default data-directory storage location. They are operationally significant because failure, latency, mount errors, or capacity exhaustion on a tablespace filesystem can affect only a subset of database objects while the PostgreSQL process itself remains running.

Treat tablespace paths, mounts, ownership, backup coverage, and capacity as production dependencies.

## TOAST

PostgreSQL can store oversized field values using TOAST mechanisms. Large-value workloads can therefore have storage and I/O characteristics that are not obvious from the apparent logical row width. DBRE capacity analysis should include associated TOAST relations.

## Storage I/O Path

```text
Executor / access method
  -> Buffer Manager
  -> shared_buffers
  -> PostgreSQL I/O subsystem
  -> OS page cache / filesystem
  -> block device or managed storage
```

PostgreSQL 18 introduces an asynchronous I/O subsystem that can improve selected operations, including sequential scans, bitmap heap scans, and vacuum. Version-sensitive I/O behavior must therefore be reviewed when comparing PostgreSQL 18 with older releases.

## Dirty Pages, WAL, and Checkpoints

Data-page modification does not imply immediate data-file persistence. WAL establishes the durability ordering, while dirty buffers are written by background activity and checkpoints. Checkpoint behavior can create substantial write I/O and interacts with WAL volume, `max_wal_size`, `checkpoint_timeout`, and `checkpoint_completion_target`.

## Temporary I/O

Sorts, hashes, materialization, and other operations can spill to temporary files when memory is insufficient for the operation. A database can therefore experience high storage utilization even when permanent-table growth is modest.

Monitor temporary-file generation and do not solve spill problems by increasing `work_mem` globally without concurrency-aware memory modeling.

## Capacity Domains

Monitor capacity separately for:

- PGDATA / primary data storage
- `pg_wal`
- tablespaces
- temporary-file locations
- archive destinations where locally managed
- backup/staging areas where applicable

A single aggregate filesystem percentage can hide a critical domain approaching exhaustion.

## Monitoring

Use PostgreSQL statistics together with OS/cloud storage telemetry. PostgreSQL 18 provides `pg_stat_io` for cluster-wide I/O statistics by backend type, object, and context. Also monitor database size, relation growth, temporary bytes/files, WAL generation, checkpoint writes, storage latency, queueing, throughput, IOPS, filesystem capacity, and inode exhaustion where relevant.

Example size inspection:

```sql
SELECT datname, pg_size_pretty(pg_database_size(datname))
FROM pg_database
ORDER BY pg_database_size(datname) DESC;
```

## Alerting

Alert on capacity trend and projected exhaustion, not only a fixed percentage. Include WAL growth rate, tablespace-specific capacity, sustained storage latency, temporary-file surges, abnormal checkpoint write pressure, and storage errors.

## Failure Scenarios

Common storage incidents include:

- `pg_wal` growth from replication-slot or archiving problems
- tablespace filesystem full
- temporary-file explosion from query spills
- checkpoint I/O saturation
- cloud-volume latency/throughput limits
- filesystem or mount failure
- unsafe manual deletion of PostgreSQL-managed files
- storage corruption or underlying hardware/media errors

## Troubleshooting Workflow

1. Determine which storage domain is affected.
2. Measure capacity, growth rate, latency, IOPS, throughput, and queue depth.
3. Correlate with WAL, checkpoint, vacuum, query, and replication activity.
4. Identify the largest relations and active growth sources.
5. Check replication slots and archiving before touching `pg_wal`.
6. Check temporary-file generation and spilling queries.
7. Verify filesystem/mount health and cloud-volume limits.
8. Never delete PostgreSQL internal files as an emergency cleanup shortcut.

## Production Case Study — WAL Filesystem Growth

A primary can approach disk exhaustion even when table growth is flat. An inactive logical or physical replication consumer can retain WAL through a replication slot. The correct investigation starts with replication-slot retention and consumer health, not manual deletion from `pg_wal`. Resolve the retention cause, restore or intentionally remove the consumer/slot according to recovery requirements, and verify WAL recycling resumes.

## SRE/DBRE Principle

> PostgreSQL storage incidents must be diagnosed by storage domain and write source. “Disk full” is a symptom; WAL retention, temporary spill, relation growth, checkpoint pressure, or a failed mount may be the actual cause.
