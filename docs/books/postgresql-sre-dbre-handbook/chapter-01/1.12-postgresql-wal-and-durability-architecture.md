# 1.12 — PostgreSQL WAL and Durability Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

Write-Ahead Logging (WAL) is PostgreSQL's central durability and recovery mechanism. It supports crash recovery, physical replication, continuous archiving, point-in-time recovery (PITR), logical decoding, and several backup/recovery workflows. For SRE/DBRE teams, WAL must be understood as both a correctness mechanism and a live production pipeline with latency, capacity, retention, and recovery dependencies.

## Write-Ahead Principle

The fundamental rule is that WAL describing a change must reach the required durability point before the corresponding modified data page is allowed to become the authoritative durable representation of that change.

```text
SQL change
   -> modify buffer/page in memory
   -> generate WAL record
   -> insert WAL into WAL buffers
   -> write WAL toward storage
   -> flush/synchronize WAL when durability requires it
   -> acknowledge COMMIT according to synchronous_commit
   -> dirty data page can be persisted later
```

This ordering allows PostgreSQL to reconstruct a consistent database state after a crash even when dirty heap or index pages had not yet reached durable storage.

## WAL Records and LSNs

WAL is an ordered sequence of records. PostgreSQL identifies positions in that stream using Log Sequence Numbers (LSNs). LSNs are fundamental to replication, recovery, backup, lag measurement, and operational troubleshooting.

Useful functions include:

```sql
SELECT pg_current_wal_lsn();
SELECT pg_current_wal_insert_lsn();
SELECT pg_current_wal_flush_lsn();
```

Interpret these functions according to server role and operational context; do not treat every LSN difference as replication lag without identifying the relevant send, receive, flush, or replay stage.

## WAL Levels

PostgreSQL 18 supports:

- `minimal`
- `replica` — default
- `logical`

`replica` records enough information for WAL archiving and physical replication. `logical` adds information required for logical decoding. `minimal` reduces WAL information but is incompatible with architectures that require the additional WAL needed for continuous archiving or streaming replication.

`wal_level` is an architectural setting and should be governed through change control rather than used as a routine performance knob.

## WAL Buffers and WAL Insertion

Backends generate WAL records and insert them into shared WAL buffers. WAL must then be written from those buffers to WAL segment files. Under heavy WAL generation, insufficient WAL-buffer capacity can cause foreground activity to participate more frequently in WAL writes.

`wal_buffers` should therefore be tuned only from measured WAL behavior, commit latency, workload characteristics, and PostgreSQL statistics—not from a fixed percentage rule.

## WAL Write vs WAL Flush

A critical operational distinction is:

```text
WAL write
   -> data reaches the operating-system/filesystem path

WAL flush/sync
   -> PostgreSQL requests the required durability guarantee
```

The exact mechanism depends on `wal_sync_method` and platform support. On Linux and FreeBSD, PostgreSQL 18 normally defaults to `fdatasync`. Other supported methods include `open_datasync`, `fsync`, `fsync_writethrough`, and `open_sync` where available.

Use `pg_test_fsync` when evaluating platform-specific WAL synchronization methods. Never assume the fastest-looking method is safe without validating the complete storage stack and power-loss behavior.

## fsync

With `fsync = on`, PostgreSQL attempts to ensure updates reach durable storage in the required order. Turning `fsync` off can result in unrecoverable database corruption after an operating-system or hardware crash.

Therefore:

> `fsync = off` is not an acceptable routine production performance optimization.

PostgreSQL documents only specialized situations where the entire database can readily be recreated as reasonable candidates for disabling it.

## synchronous_commit

`synchronous_commit` controls how much WAL processing must complete before PostgreSQL reports transaction success to the client.

PostgreSQL 18 supports:

- `remote_apply`
- `on` — default
- `remote_write`
- `local`
- `off`

Without synchronous standbys configured, the primary practical distinction is usually between waiting for local WAL durability and asynchronous commit behavior.

With `synchronous_commit = off`, PostgreSQL can report success before the transaction's WAL is durably flushed. A crash can therefore lose some recently acknowledged transactions, but PostgreSQL preserves database consistency; this is fundamentally different from `fsync = off`, which can expose the database to corruption after OS/hardware failure.

Because `synchronous_commit` can be set per transaction, applications can selectively trade durability latency for performance when business semantics permit it.

## Synchronous Replication Durability Levels

When synchronous standbys are configured, `synchronous_commit` also controls the remote acknowledgement level.

```text
local
  -> wait for local durable WAL only

remote_write
  -> standby has written WAL to its filesystem

on
  -> synchronous standby has flushed WAL durably

remote_apply
  -> synchronous standby has durably received and replayed the commit
```

Higher durability guarantees generally increase commit latency. Select the mode from explicit RPO, read-after-failover, and latency requirements rather than assuming one setting fits every workload.

## Asynchronous Commit Risk Window

For asynchronous commit, the WAL writer periodically flushes unwritten WAL. PostgreSQL documents the maximum risk window as up to three times `wal_writer_delay` under the WAL writer's batching behavior.

An immediate shutdown behaves like a crash with respect to unflushed asynchronous commits and can therefore lose transactions that had already been acknowledged under asynchronous commit.

## Full-Page Writes

With `full_page_writes = on`—the default—PostgreSQL logs the full contents of a data page on its first modification after a checkpoint when required to protect against partial/torn page writes.

```text
checkpoint
   -> first subsequent change to page
      -> full-page image may enter WAL
   -> later changes before next checkpoint
      -> normal WAL records
```

This means more frequent checkpoints can increase WAL volume because more pages cross the "first change after checkpoint" boundary.

Turning `full_page_writes` off can expose the cluster to unrecoverable or silent corruption after system failure and is not a normal production tuning technique.

## WAL Compression

`wal_compression` can compress full-page images using supported methods such as `pglz`, `lz4`, or `zstd` when the PostgreSQL build supports them. This can reduce WAL volume at the cost of additional CPU during WAL generation and replay.

Evaluate WAL compression using workload-level CPU, WAL throughput, archive bandwidth, replication bandwidth, and recovery/replay measurements.

## Checkpoints and Recovery Boundaries

Checkpoints establish recovery boundaries. PostgreSQL ensures the relevant dirty heap and index pages are flushed, writes checkpoint information to WAL, and advances the point from which crash recovery needs to begin redo.

Checkpoint frequency is driven primarily by:

- `checkpoint_timeout`
- WAL growth relative to `max_wal_size`
- explicit administrative checkpoint requests

More frequent checkpoints can reduce crash-recovery work but increase dirty-page write pressure and full-page-image WAL generation. Section 1.16 covers checkpoint architecture in depth.

## WAL Segments and pg_wal

WAL is stored in segment files under `pg_wal`. Segment size is selected when the cluster is initialized and is not an ordinary runtime tuning parameter.

A WAL segment can be recycled or removed only when PostgreSQL no longer needs it for relevant recovery, checkpoint, archive, backup, replication, or slot-retention requirements.

> Never manually delete files from `pg_wal` to recover disk space on a running or recoverable PostgreSQL cluster.

Doing so can destroy crash recovery, replication, backup recovery, or cluster integrity.

## WAL Archiving

When continuous archiving is enabled, completed WAL segments are copied to the configured archive destination. Persistent archive failure can cause WAL to accumulate locally while the database continues serving traffic.

Therefore archive health is both:

1. a recoverability concern, and
2. a primary-storage-capacity concern.

Monitor archive success, failures, backlog, destination capacity, and time since the last successful archive in the context of actual WAL generation.

## Replication Slots and WAL Retention

Physical and logical replication slots can retain WAL required by consumers. This is intentional, but a failed or abandoned consumer can turn replication failure into primary disk exhaustion.

Inspect slot state and retained WAL before treating `pg_wal` growth as a storage-only problem.

Example diagnostic pattern:

```sql
SELECT slot_name,
       slot_type,
       active,
       restart_lsn,
       confirmed_flush_lsn,
       wal_status,
       safe_wal_size
FROM pg_replication_slots;
```

Columns vary by slot type and configuration; interpret them according to physical vs logical replication semantics.

## PostgreSQL 18 WAL I/O Observability

PostgreSQL 18 changed WAL I/O observability in important ways.

`pg_stat_io` now includes WAL I/O activity, including byte counts. When `track_wal_io_timing` is enabled, WAL write and synchronization timing is reported through `pg_stat_io` for WAL objects rather than through the older `pg_stat_wal` timing model.

Use both views for their intended purposes:

```sql
SELECT * FROM pg_stat_wal;

SELECT backend_type,
       object,
       context,
       reads,
       read_bytes,
       writes,
       write_bytes,
       write_time,
       fsyncs,
       fsync_time
FROM pg_stat_io
WHERE object = 'wal';
```

Not every column is populated for every backend/object/context combination.

## WAL Wait Events

Relevant PostgreSQL 18 wait events include WAL read, write, initialization, copying, and synchronization events such as `WalRead`, `WalWrite`, and `WalSync`.

When commit latency rises, correlate backend wait events with WAL I/O statistics and underlying storage latency rather than assuming query execution itself is slow.

## Group Commit

Multiple concurrently committing sessions can share WAL flush work. PostgreSQL can achieve group-commit effects even with the default `commit_delay = 0` when commits overlap naturally.

`commit_delay` and `commit_siblings` are specialized tuning parameters. They should be changed only after proving that commit throughput is limited by synchronization latency and validating the effect under representative concurrency.

## WAL Generation Sources

High WAL volume can result from many legitimate activities:

- INSERT/UPDATE/DELETE workload
- bulk loading
- index creation or maintenance
- full-page images after checkpoints
- `REPLICA IDENTITY FULL` workloads
- logical replication requirements
- hint-bit logging when required
- backup-related activity
- maintenance operations

Do not diagnose "too much WAL" without identifying the workload and WAL amplification mechanism.

## Monitoring Model

Monitor the complete pipeline:

```text
application writes
   -> WAL generation rate
   -> WAL buffers
   -> WAL write latency
   -> WAL flush/sync latency
   -> pg_wal capacity
   -> archive pipeline
   -> replication send/receive/replay
   -> slot retention
   -> recovery readiness
```

Core signals include:

- WAL bytes generated per second/minute
- `pg_stat_wal`
- WAL rows in `pg_stat_io`
- WAL write/fsync latency
- WAL-related wait events
- `pg_wal` filesystem utilization and growth rate
- archive success/failure/backlog
- replication send/flush/replay positions
- replication-slot retained WAL
- checkpoint frequency
- full-page-image volume
- backup/recovery pipeline health

## Alerting Strategy

Avoid a single static "WAL high" alert. Prefer layered alerts.

### Warning

- sustained WAL generation materially above baseline
- increasing archive backlog
- increasing replication lag
- inactive slot retaining WAL
- elevated WAL write/sync latency
- projected `pg_wal` exhaustion entering the operational response window

### Critical

- archive pipeline failed with rapidly shrinking WAL headroom
- slot retention threatens primary capacity
- WAL storage near exhaustion
- synchronous replication causes sustained commit unavailability/latency beyond SLO
- WAL/storage errors threaten durability

Time-to-exhaustion is usually more actionable than percentage-full alone.

## Failure Scenarios

### 1. Slow WAL Storage

Symptoms:

- commit latency increases
- `WalSync`/`WalWrite` waits rise
- WAL I/O timing increases
- CPU may remain normal

Investigate the storage path before tuning SQL.

### 2. Replication Slot Retention

A disconnected consumer leaves its slot behind and retained WAL grows until primary capacity is threatened.

### 3. Archive Failure

The archive destination becomes unavailable or full. Completed WAL cannot be archived and local retention increases.

### 4. Excessive Checkpoint Frequency

Frequent checkpoints increase full-page-image generation and dirty-page write pressure, amplifying WAL and storage I/O.

### 5. Unsafe Durability Change

A performance incident leads to disabling `fsync` or `full_page_writes`. This trades a latency problem for potential unrecoverable corruption and must be prohibited by production change controls.

### 6. Synchronous Standby Failure

A required synchronous standby becomes unavailable or slow. Depending on synchronous-replication configuration, commits can block or become significantly slower even though the primary process remains healthy.

## Troubleshooting Workflow

1. Determine whether the symptom is latency, capacity, replication, archive, or recovery related.
2. Measure WAL generation rate and `pg_wal` headroom.
3. Inspect `pg_stat_wal` and WAL rows in `pg_stat_io`.
4. Check WAL-related wait events and storage latency.
5. Inspect replication slots and retained WAL.
6. Inspect physical/logical replication state and lag stages.
7. Verify archiving and archive-destination health.
8. Correlate checkpoint frequency and full-page-image generation.
9. Review recent workload, maintenance, backup, and configuration changes.
10. Preserve RPO/PITR requirements before dropping slots or altering archive/replication behavior.
11. Never delete WAL manually as an emergency shortcut.
12. Validate that WAL recycling, archive progress, and replication recovery resume after remediation.

## Production Case Study — Inactive Logical Slot

A logical replication consumer stops while the publisher continues a heavy write workload. The slot correctly retains WAL needed by the consumer, but `pg_wal` usage begins increasing rapidly.

A weak response would be to delete WAL files or immediately drop the slot.

The DBRE response is:

1. identify the retaining slot and affected consumer;
2. measure WAL generation and retained bytes;
3. calculate time to storage exhaustion;
4. determine whether the consumer can resume safely;
5. validate whether the replication stream is still required for RPO/migration/business purposes;
6. add temporary capacity if necessary to preserve the recovery window;
7. drop/recreate the slot only after explicitly accepting the resynchronization/data-continuity consequences;
8. verify WAL recycling resumes and establish slot-retention alerting.

The root cause is not "PostgreSQL failed to delete WAL." PostgreSQL is correctly honoring a retention contract whose consumer stopped progressing.

## Production Guardrails

- Keep `fsync` enabled for durable production clusters.
- Keep `full_page_writes` enabled unless a narrowly justified disposable/rebuildable use case has been formally accepted.
- Treat `synchronous_commit` as a business-durability policy, not just a latency knob.
- Protect `pg_wal` with independent capacity monitoring.
- Alert on replication-slot retention and archive backlog.
- Benchmark storage durability behavior before production deployment.
- Include WAL/archive/replication state in backup and DR validation.
- Test crash recovery and restore procedures regularly.
- Review WAL behavior after PostgreSQL major upgrades because observability and I/O implementation details can change.

## SRE/DBRE Principle

> WAL is simultaneously PostgreSQL's durability journal, recovery stream, replication source, and a production capacity dependency. Diagnose and operate it end to end: generation → write → flush → archive → replication → retention → recovery.
