# 1.13 — PostgreSQL Transaction & MVCC Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL uses transactions and Multi-Version Concurrency Control (MVCC) to provide isolation while allowing high concurrency. Understanding snapshots, tuple versions, transaction IDs, visibility, long transactions, and cleanup horizons is essential for diagnosing blocking, bloat, vacuum delay, replica conflicts, and transaction-ID risk.

## Transaction Model

A transaction groups database operations into an atomic unit. PostgreSQL provides transaction isolation levels and uses snapshots/visibility rules to determine which row versions a statement or transaction can observe.

```text
BEGIN
  -> transaction state
  -> snapshot/visibility rules
  -> reads and writes
  -> COMMIT or ROLLBACK
```

## MVCC

An `UPDATE` generally creates a new row version rather than overwriting the old version in place. A `DELETE` marks a version as no longer visible to future snapshots, but the physical tuple cannot necessarily be removed immediately because an older transaction might still need to see it.

```text
old tuple version
       |
       +-- visible to older snapshot
       |
new tuple version
       +-- visible to newer snapshot
```

This is why PostgreSQL requires VACUUM to reclaim obsolete tuple versions.

## Snapshots and Visibility

Visibility depends on transaction state and the snapshot used by the statement/transaction. Isolation level changes when snapshots are acquired and reused. DBREs should distinguish logical application consistency requirements from physical tuple cleanup behavior.

## Transaction IDs

PostgreSQL uses transaction identifiers as part of MVCC visibility. Transaction IDs have finite space and require freezing/maintenance to prevent wraparound problems. Autovacuum therefore performs both space-reclamation work and mandatory transaction-ID protection.

## Long-Running Transactions

Long transactions are a major reliability concern because they can preserve old visibility horizons and prevent cleanup of dead tuples.

```text
long transaction
  -> old snapshot retained
  -> cleanup horizon held back
  -> dead tuples retained
  -> bloat / I/O growth
  -> vacuum pressure
```

Monitor `xact_start`, not merely query duration.

## Idle in Transaction

A session can stop executing SQL while remaining inside an open transaction. `idle in transaction` sessions can therefore retain transaction state and locks despite appearing inactive at the application layer.

Use `idle_in_transaction_session_timeout` carefully as a guardrail where application behavior permits it.

## Isolation Levels

PostgreSQL supports Read Committed, Repeatable Read, and Serializable behavior; Read Uncommitted is treated as Read Committed. Higher isolation provides stronger guarantees but can introduce serialization failures that applications must be prepared to retry.

## Read-Only Transactions

Read-only does not mean operationally harmless. A long-running read transaction can retain an old snapshot and interfere with cleanup. Long analytical queries should therefore be included in vacuum/bloat investigations.

## Monitoring

```sql
SELECT pid, usename, datname, state,
       xact_start, query_start,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Monitor oldest transaction age, idle-in-transaction duration, dead-tuple trends, autovacuum activity, relation transaction-age indicators, replication conflicts, and transaction-ID consumption.

## Alerting

Use separate alerts for long active transactions, idle-in-transaction sessions, approaching transaction-ID maintenance thresholds, and sustained dead-tuple/bloat growth. Thresholds must reflect workload and maintenance design.

## Failure Scenarios

Common MVCC-related incidents include abandoned transactions, long analytical snapshots, autovacuum blocked or unable to keep up, transaction-ID wraparound risk, dead-tuple accumulation, and application retry failures at Serializable isolation.

## Troubleshooting Workflow

1. Identify the oldest transactions and snapshots.
2. Determine whether sessions are active, waiting, or idle in transaction.
3. Inspect blocking relationships and held locks.
4. Check autovacuum progress and relation age.
5. Correlate dead tuples, table/index growth, and I/O.
6. Decide whether transaction cancellation is safe based on business impact.
7. Fix application transaction boundaries and timeout policy.
8. Verify vacuum can advance after the blocker is removed.

## Production Case Study — Forgotten Transaction

An application opens a transaction, executes a small query, and leaves the session idle for days. The database remains available, but dead tuples accumulate on high-update tables and vacuum cannot reclaim them as expected. The incident is resolved by safely ending the abandoned transaction, verifying vacuum progress, and adding transaction timeout/connection-pool controls so the condition cannot silently recur.

## SRE/DBRE Principle

> In PostgreSQL, transaction age is a capacity and maintenance variable. A transaction can harm the system even when it consumes almost no CPU.
