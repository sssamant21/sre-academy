# 1.13 — PostgreSQL Transaction & MVCC Architecture

**Status:** Technical Review ✓ → Production Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation; reviewed against PostgreSQL 18 behavior

## Purpose

PostgreSQL uses transactions and Multi-Version Concurrency Control (MVCC) to provide transactional consistency while allowing readers and writers to operate concurrently. For SRE/DBRE teams, MVCC is not only a concurrency mechanism: snapshots, transaction IDs, tuple versions, transaction horizons, long-running transactions, prepared transactions, replication slots, and vacuum all interact with storage growth, performance, availability, and transaction-ID safety.

## Transaction Model

A PostgreSQL transaction groups database operations into an atomic unit and ends with `COMMIT` or `ROLLBACK`.

```text
BEGIN
  -> transaction state established
  -> statements acquire snapshots according to isolation level
  -> reads observe visible tuple versions
  -> writes create/change tuple versions and generate WAL
  -> COMMIT or ROLLBACK
```

Autocommit clients normally execute each standalone statement as its own transaction unless an explicit transaction block is opened.

## MVCC Architecture

PostgreSQL does not normally overwrite a row version in place in the logical sense. An `UPDATE` creates a new tuple version and makes the previous version obsolete for future snapshots. A `DELETE` makes the existing tuple version invisible to future transactions once the deleting transaction is visible, but the physical tuple can remain until it is no longer needed by any relevant snapshot and VACUUM can reclaim it.

```text
Tuple version V1
  xmin = transaction that created V1
  xmax = transaction that deleted/replaced V1, when applicable
        |
        +--> may remain visible to an older snapshot

Tuple version V2
  xmin = updating transaction
        |
        +--> visible to snapshots for which that transaction is visible
```

This architecture allows ordinary readers and writers to avoid many direct conflicts, but it creates a maintenance requirement: obsolete tuple versions must eventually be vacuumed.

## Tuple Visibility Metadata

Heap tuples contain transaction-related metadata used by MVCC, including `xmin` and `xmax`. These values participate in visibility decisions together with transaction status and the active snapshot.

Do not interpret tuple-header XIDs as simple timestamps. Visibility depends on PostgreSQL transaction semantics, commit state, snapshot boundaries, and special/frozen transaction states.

## Snapshots and Visibility

A snapshot represents the transaction visibility horizon used to determine which tuple versions a statement can see.

The snapshot lifecycle depends on transaction isolation:

- **Read Committed** — each command obtains a new snapshot, so two statements in the same transaction can observe different committed database states.
- **Repeatable Read** — the transaction sees a stable snapshot established for the transaction's reads, subject to PostgreSQL's isolation semantics.
- **Serializable** — PostgreSQL provides serializable execution using Serializable Snapshot Isolation (SSI) and can abort transactions when necessary to prevent serialization anomalies.

Applications using Repeatable Read or Serializable must therefore be designed for the semantics and retry behavior of those isolation levels.

## Isolation Levels

PostgreSQL accepts the SQL isolation-level names:

- Read Uncommitted
- Read Committed
- Repeatable Read
- Serializable

Internally, PostgreSQL treats Read Uncommitted as Read Committed because MVCC does not expose uncommitted changes from other transactions.

Read Committed is the default isolation level.

Higher isolation does not simply mean “more locking.” Snapshot behavior and, for Serializable, predicate/SSI conflict tracking are fundamental parts of the implementation.

## Transaction IDs (XIDs)

PostgreSQL uses 32-bit transaction IDs for MVCC transaction identity. Because the XID space is finite and wraps, PostgreSQL must periodically freeze sufficiently old tuple XIDs so that their visibility remains correct as the transaction counter advances.

This makes XID age an availability concern rather than merely an internal implementation detail.

```text
transaction workload
   -> XIDs consumed
   -> tuple XIDs age
   -> VACUUM freezes sufficiently old tuples
   -> relfrozenxid advances
   -> wraparound safety maintained
```

PostgreSQL must vacuum every table often enough to avoid transaction-ID wraparound. Autovacuum performs anti-wraparound work even in circumstances where ordinary autovacuum behavior has been disabled.

## Frozen Tuples and relfrozenxid

`pg_class.relfrozenxid` records a lower bound on unfrozen XIDs that might still exist in a relation. Database-level `pg_database.datfrozenxid` reflects the oldest relevant relation horizon for the database.

DBRE monitoring should therefore track XID age at both database and relation level rather than relying only on dead-tuple counts.

Example database-level inspection:

```sql
SELECT datname,
       age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

Example relation-level inspection:

```sql
SELECT n.nspname,
       c.relname,
       age(c.relfrozenxid) AS xid_age
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','m','t')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 50;
```

## Multixact IDs

PostgreSQL also uses multixact IDs (MXIDs) when multiple transactions participate in row-level locking. MXIDs have their own finite ID space and freezing/aging requirements.

`pg_class.relminmxid` is therefore another maintenance horizon that matters for production reliability. XID monitoring alone is incomplete for systems with substantial row-locking activity.

## Long-Running Transactions

Long-running transactions are a major MVCC reliability risk because they can retain old snapshots and transaction horizons.

```text
old transaction / snapshot
  -> old xmin horizon remains relevant
  -> VACUUM cannot remove some obsolete tuples
  -> dead tuples remain
  -> table/index working set grows
  -> more I/O and cache pressure
  -> autovacuum must process more data
```

Monitor transaction age (`xact_start`) separately from statement age (`query_start`). A query can finish while its transaction remains open.

## Idle in Transaction

A backend in `idle in transaction` state is not executing a query, but the transaction remains open.

Such a session can:

- retain an old snapshot/horizon,
- hold locks,
- delay cleanup of dead tuples,
- contribute to table/index bloat,
- interfere with DDL,
- increase operational risk without consuming significant CPU.

`idle_in_transaction_session_timeout` can be an effective production guardrail when application semantics permit it. Configure it deliberately and test application retry/error behavior.

## Prepared Transactions

Two-phase commit can leave prepared transactions present after the originating session has disappeared. Prepared transactions can retain transaction state and locks for long periods and are especially dangerous when operational ownership is unclear.

If `max_prepared_transactions` and two-phase commit are used, monitor `pg_prepared_xacts` and establish explicit ownership and recovery procedures.

## Replication Slots and MVCC Horizons

Replication slots can retain more than WAL. Logical slots can expose `xmin` or `catalog_xmin` horizons that prevent removal of tuples or catalog rows still required by the consumer.

A stale logical replication slot can therefore create two separate capacity risks:

1. WAL retention in `pg_wal`.
2. MVCC/catalog cleanup horizons that delay vacuum cleanup.

Slot monitoring must include both WAL retention and XID/catalog horizons.

## Read-Only Transactions Are Not Necessarily Harmless

A transaction can be read-only and still hold an old snapshot for a long period. Large analytical queries, reporting sessions, backup-related activity, or forgotten read-only transactions can therefore delay vacuum cleanup even though they never modify application rows.

DBRE investigations should classify transactions by **age and horizon impact**, not only by whether they are writing.

## HOT Updates and MVCC

Heap-Only Tuple (HOT) updates can avoid creating new index entries when PostgreSQL can keep the updated tuple on the same heap page and indexed columns are not changed in a way that prevents HOT.

HOT can substantially reduce index write amplification and later index-cleanup work on update-heavy tables. Fillfactor, tuple size, page free space, indexed columns, and update patterns influence HOT effectiveness.

Monitor HOT behavior as part of high-update-table tuning rather than assuming every UPDATE has identical storage cost.

## VACUUM Relationship

MVCC and VACUUM are inseparable operationally.

Routine VACUUM:

- identifies removable dead tuple versions,
- makes their storage reusable,
- maintains the visibility map,
- freezes old tuple XIDs when required,
- contributes to XID/MXID wraparound protection.

Standard VACUUM generally makes space reusable inside the relation; it does not normally return that space to the operating system. `VACUUM FULL` rewrites the table and requires an `ACCESS EXCLUSIVE` lock, so it must not be treated as routine MVCC maintenance.

Detailed vacuum/autovacuum architecture is covered in Section 1.17.

## Transaction-ID Wraparound Protection

XID wraparound is an availability-critical condition. PostgreSQL begins warning as the system approaches the wraparound limit and will eventually refuse commands that need new XIDs in order to protect data visibility.

Operational response must focus on the actual horizon blockers:

- old prepared transactions,
- long-running/open transactions,
- stale replication slots,
- relations that have not been frozen adequately,
- autovacuum inability to make progress.

Do not wait for the final wraparound-protection shutdown behavior before acting.

## PostgreSQL 18 Freezing Considerations

PostgreSQL 18 includes eager-freezing behavior that can scan selected all-visible but not all-frozen pages during normal vacuum activity. The goal is to amortize freezing work and reduce the amount of work required by future aggressive vacuums.

`vacuum_max_eager_freeze_failure_rate` controls when eager scanning is abandoned because too many scanned pages fail to become all-frozen.

This is a version-sensitive maintenance behavior and should be considered when carrying vacuum/freezing assumptions from older PostgreSQL releases into PostgreSQL 18.

## Monitoring

### Oldest Open Transactions

```sql
SELECT pid,
       usename,
       datname,
       application_name,
       client_addr,
       state,
       xact_start,
       query_start,
       now() - xact_start AS transaction_age,
       backend_xid,
       backend_xmin,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

### Prepared Transactions

```sql
SELECT transaction,
       gid,
       prepared,
       owner,
       database
FROM pg_prepared_xacts
ORDER BY prepared;
```

### Replication Slot Horizons

```sql
SELECT slot_name,
       slot_type,
       active,
       xmin,
       catalog_xmin,
       restart_lsn,
       wal_status
FROM pg_replication_slots
ORDER BY slot_name;
```

### Table Maintenance Signals

Monitor at minimum:

- oldest transaction age,
- oldest `backend_xmin`,
- idle-in-transaction age,
- prepared-transaction age,
- database `datfrozenxid` age,
- relation `relfrozenxid` age,
- relation `relminmxid` age,
- replication-slot `xmin` / `catalog_xmin`,
- dead tuple trends,
- autovacuum activity and progress,
- table/index growth,
- HOT update ratio where relevant.

## Alerting Strategy

Use separate alert classes rather than one generic “long transaction” alarm.

**Warning examples:**

- transaction older than the workload's expected maximum,
- idle-in-transaction session persisting beyond policy,
- prepared transaction older than the approved two-phase-commit window,
- sustained dead-tuple growth,
- relation/database XID age approaching internal operational thresholds,
- logical slot retaining an old catalog horizon.

**Critical examples:**

- rapidly approaching anti-wraparound limits,
- autovacuum unable to advance XID/MXID horizons,
- very old transaction/prepared transaction blocking freeze progress,
- PostgreSQL wraparound warnings,
- write availability threatened by XID or MXID exhaustion.

Thresholds must be based on transaction consumption rate and time-to-exhaustion, not only static XID counts.

## Failure Scenarios

### 1. Forgotten Idle Transaction

An application opens a transaction, executes a query, and returns the connection to a broken pool state without committing or rolling back. The backend remains idle in transaction and holds an old MVCC horizon.

### 2. Long Analytical Snapshot

A reporting transaction runs for hours while heavily updated tables accumulate obsolete tuple versions. Vacuum runs but cannot remove versions still potentially visible to the old snapshot.

### 3. Stale Logical Replication Slot

A retired logical consumer leaves a slot behind. `catalog_xmin` remains old, delaying catalog cleanup while the slot can also retain WAL.

### 4. Forgotten Prepared Transaction

A distributed transaction is prepared but never resolved. Locks and transaction state survive the client session and can remain until explicitly committed or rolled back.

### 5. Transaction-ID Wraparound Pressure

High transaction throughput combined with ineffective vacuum/freezing causes database and relation XID ages to approach safety limits. PostgreSQL begins anti-wraparound activity and eventually protects itself by refusing XID-consuming operations if the condition is not resolved.

## Troubleshooting Workflow

1. Identify the oldest transactions by `xact_start`.
2. Inspect `backend_xid` and `backend_xmin` to find sessions holding old horizons.
3. Check `idle in transaction` sessions separately from actively executing queries.
4. Inspect `pg_prepared_xacts` for unresolved two-phase transactions.
5. Inspect replication-slot `xmin` and `catalog_xmin` horizons.
6. Check database `datfrozenxid` and relation `relfrozenxid` / `relminmxid` ages.
7. Inspect autovacuum and vacuum progress.
8. Correlate dead tuples with table/index growth and storage I/O.
9. Determine the business impact before canceling or terminating sessions.
10. Resolve the root horizon blocker before attempting aggressive space-reclamation work.
11. Verify that vacuum/freezing horizons advance after remediation.
12. Correct application transaction boundaries, pool behavior, slot lifecycle, and timeout policy to prevent recurrence.

## Production Case Study — Forgotten Transaction Causes Bloat

An application begins a transaction, executes a small `SELECT`, and leaves the connection idle in transaction for several days. CPU remains normal and the session appears inactive from the application perspective.

Meanwhile, a high-update table continues generating new tuple versions. Autovacuum runs, but tuple versions that may still be visible to the old snapshot cannot be removed. The table and indexes grow, cache efficiency falls, and storage I/O increases.

The incident response is:

1. identify the old transaction and confirm its application owner,
2. determine whether termination is safe,
3. end the abandoned transaction,
4. verify that the cleanup horizon advances,
5. monitor vacuum catch-up and relation growth,
6. add `idle_in_transaction_session_timeout` and pool/application transaction controls where appropriate.

Adding CPU or simply running repeated manual VACUUM commands before removing the horizon blocker does not solve the underlying problem.

## Production Guardrails

- Keep transactions as short as business semantics permit.
- Never leave transaction ownership ambiguous in connection pools.
- Monitor transaction age independently of query execution time.
- Treat prepared transactions as durable operational objects requiring ownership.
- Monitor logical replication slot horizons as well as retained WAL.
- Keep autovacuum enabled and capacity it for transaction/update volume.
- Alert on XID/MXID time-to-exhaustion well before PostgreSQL safety limits.
- Test application retry behavior for serialization failures.
- Do not use `VACUUM FULL` as a first response to an MVCC horizon problem.
- Resolve the transaction/snapshot blocker before attempting bloat remediation.

## SRE/DBRE Principle

> In PostgreSQL, transaction age is a capacity, maintenance, and availability variable. A transaction can consume almost no CPU and still prevent vacuum progress, retain storage, block DDL, or push the cluster toward transaction-ID exhaustion.
