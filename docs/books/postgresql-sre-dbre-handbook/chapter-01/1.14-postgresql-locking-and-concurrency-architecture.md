# 1.14 — PostgreSQL Locking & Concurrency Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

MVCC reduces many reader/writer conflicts, but PostgreSQL still uses locks for relations, rows, transaction identifiers, advisory coordination, schema changes, and internal synchronization. Production reliability requires understanding blocking chains, lock compatibility, deadlocks, transaction scope, and the difference between waiting and CPU execution.

## Locking Model

PostgreSQL exposes table-level lock modes with defined compatibility rules. SQL operations acquire the modes required to protect database consistency. Stronger DDL operations can conflict with ordinary workload activity and vice versa.

Row-level locks protect rows from conflicting modifications without blocking ordinary reads of those rows.

## MVCC and Locks

MVCC and locking complement one another:

```text
MVCC -> version visibility and reader/writer concurrency
Locks -> conflicting operation coordination
```

Do not assume “PostgreSQL uses MVCC” means locks are unimportant.

## Blocking Chains

A blocked session can cause downstream queueing:

```text
Session A holds lock
   -> Session B waits
      -> Session C waits behind B
         -> application pool fills
            -> latency / timeout incident
```

The original blocker may be idle in transaction and consume almost no CPU.

## Deadlocks

A deadlock occurs when transactions wait on one another in a cycle. PostgreSQL detects deadlocks and aborts one transaction so progress can continue. Applications must handle the resulting error and retry the complete transaction when appropriate.

`deadlock_timeout` influences when PostgreSQL checks/logs lock-wait conditions and should not be tuned casually as a substitute for fixing transaction design.

## Lock Monitoring

Use `pg_locks` together with `pg_stat_activity` and `pg_blocking_pids()`.

```sql
SELECT pid, usename, state, xact_start,
       wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocking_pids,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Investigate the root blocker, not only the most visible blocked query.

## DDL Concurrency

Schema changes can require strong locks. A migration that is harmless in a development database can queue behind long transactions in production and then block new application work once it obtains or waits for a conflicting lock.

Use `lock_timeout` and controlled migration procedures where appropriate.

## Row Locking

`SELECT ... FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, and `FOR KEY SHARE` provide explicit row-locking behaviors. Work-queue patterns sometimes use `SKIP LOCKED`, but its semantics must match the application requirement; it intentionally skips rows that cannot immediately be locked.

## Advisory Locks

PostgreSQL advisory locks provide application-defined coordination. They are powerful but can create hidden dependencies if ownership, key conventions, and release behavior are not documented and monitored.

## Monitoring and Alerting

Monitor sustained lock waits, blocker age, blocked-session count, deadlock rate, long transactions, idle-in-transaction sessions, DDL wait duration, and application pool saturation. Alert on sustained blocking chains rather than every transient lock wait.

## Failure Scenarios

Typical incidents include forgotten transactions holding locks, large batch updates, inconsistent application lock ordering, DDL migrations waiting behind long queries, work queues with contention, and connection pools exhausted by blocked sessions.

## Troubleshooting Workflow

1. Identify blocked sessions.
2. Resolve blocking PIDs and build the chain to the root blocker.
3. Inspect transaction age, state, user, application, and SQL.
4. Determine business impact of canceling or terminating the blocker.
5. Preserve evidence before intervention.
6. Restore service using the least disruptive safe action.
7. Correct transaction boundaries, lock ordering, migration design, or query scope.

## Production Case Study — DDL Queue

A deployment issues a schema change while an old application transaction remains open. The DDL waits for a strong lock, and new sessions begin queueing behind conflicting operations. CPU remains normal while API latency rises sharply. Lock-chain analysis identifies the old transaction as the root cause. The long-term fix is migration lock-timeout policy plus transaction-age guardrails, not additional CPU.

## SRE/DBRE Principle

> When PostgreSQL latency rises with normal CPU, inspect waits and blocking before assuming a compute bottleneck.
