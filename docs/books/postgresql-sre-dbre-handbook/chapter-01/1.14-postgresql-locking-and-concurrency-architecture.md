# 1.14 — PostgreSQL Locking & Concurrency Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL MVCC allows many readers and writers to proceed concurrently, but it does not eliminate locking. PostgreSQL uses heavyweight locks, row-level locks, transaction-ID and virtual-transaction waits, predicate locks, advisory locks, and short-lived internal page/buffer synchronization to protect correctness. For SRE/DBRE teams, the central operational problem is not simply whether locks exist, but whether lock waits form sustained blocking chains that consume latency budgets, connection-pool capacity, and transaction headroom.

## Concurrency Architecture

```text
Application transactions
        |
        +-- MVCC snapshots / tuple visibility
        |
        +-- heavyweight lock manager
        |      +-- relation/object locks
        |      +-- transactionid / virtualxid waits
        |      +-- advisory locks
        |
        +-- row locks stored with tuples
        |
        +-- predicate locks for Serializable isolation
        |
        +-- short-lived internal page/buffer synchronization
```

MVCC and locks solve different problems. MVCC determines which tuple versions a transaction can see; locking coordinates operations that cannot safely proceed concurrently.

## Table-Level Lock Modes

PostgreSQL defines eight table-level lock modes:

- `ACCESS SHARE`
- `ROW SHARE`
- `ROW EXCLUSIVE`
- `SHARE UPDATE EXCLUSIVE`
- `SHARE`
- `SHARE ROW EXCLUSIVE`
- `EXCLUSIVE`
- `ACCESS EXCLUSIVE`

The names containing `ROW` are still table-level lock modes; they do not mean that the lock itself is a row lock. PostgreSQL commands automatically acquire the least restrictive table lock required for their operation, while `LOCK TABLE` can request an explicit mode.

`ACCESS EXCLUSIVE` conflicts with every table-level mode and is required by operations such as `TRUNCATE` and many forms of DDL. This is why apparently small schema changes can become availability incidents when long transactions are present.

Locks acquired by normal SQL transactions are generally held until transaction end. Keeping transactions short is therefore one of the most effective concurrency controls.

## Row-Level Locks

PostgreSQL supports row-locking clauses:

```sql
SELECT ... FOR UPDATE;
SELECT ... FOR NO KEY UPDATE;
SELECT ... FOR SHARE;
SELECT ... FOR KEY SHARE;
```

Row-level locks block conflicting writers and lockers but do not block ordinary MVCC reads of the row.

Two operational details matter:

1. Row locks are represented in tuple state rather than as one permanent heavyweight-lock-table entry per locked row.
2. A process waiting for another transaction's row modification can appear as a wait on a transaction ID rather than as an intuitive tuple lock in `pg_locks`.

This is why `pg_blocking_pids()` and transaction context are usually more useful than trying to infer every blocking relationship directly from `pg_locks` rows.

## NOWAIT and SKIP LOCKED

`NOWAIT` fails immediately rather than waiting for a conflicting row/table lock where supported. `SKIP LOCKED` skips rows that cannot immediately be locked.

`SKIP LOCKED` is useful for queue-like workloads in which multiple workers intentionally claim independent jobs, but it provides an intentionally inconsistent view of locked rows and should not be used as a generic cure for contention.

## Transaction IDs and Virtual Transactions

`pg_locks` exposes both permanent transaction-ID and virtual-transaction lock targets. Read-only transactions can have a virtual transaction ID without yet receiving a permanent transaction ID.

This matters during DDL and other operations that wait for transactions to finish. The visible wait may be on `virtualxid` or `transactionid`, even when the business symptom is described as “the table is locked.”

## Predicate Locks and Serializable Isolation

Serializable Snapshot Isolation uses predicate locking to detect dangerous read/write dependency patterns. Predicate locks are different from ordinary blocking row/table locks: they help detect serialization anomalies rather than simply blocking every conflicting access.

Applications using `SERIALIZABLE` must be prepared to retry complete transactions after serialization failures.

Relevant capacity settings include:

- `max_pred_locks_per_transaction`
- `max_pred_locks_per_relation`
- `max_pred_locks_per_page`

Do not increase these blindly. Determine whether the workload truly needs large serializable read/write footprints.

## Advisory Locks

Advisory locks allow applications to coordinate using application-defined 64-bit or two-part 32-bit keys. They can be session-level or transaction-level.

They are useful for leader election, job coordination, singleton maintenance, and application-level mutual exclusion, but PostgreSQL cannot infer the business meaning of the key. Production systems should document key ownership, acquisition order, lifetime, and failure behavior.

Prefer transaction-level advisory locks when the lock should naturally disappear with transaction completion. Session-level advisory locks require disciplined release and connection-pool behavior.

## Blocking Chains

The production impact of locking is often multiplicative:

```text
root blocker
   |
   +-- waiter A
   |     +-- waiter B
   |           +-- application requests queue
   |
   +-- DDL waiter
         +-- later requests can queue behind incompatible lock requests

connection pool fills
   -> request latency rises
   -> retries increase concurrency
   -> outage can amplify
```

The root blocker can be `idle in transaction`, consume almost no CPU, and still cause severe application latency.

## Detecting Blockers

Start with `pg_stat_activity` and `pg_blocking_pids()`:

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.state,
    a.xact_start,
    a.query_start,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.xact_start NULLS LAST;
```

Then inspect the lock inventory:

```sql
SELECT
    l.pid,
    l.locktype,
    l.mode,
    l.granted,
    l.database,
    l.relation,
    l.page,
    l.tuple,
    l.virtualxid,
    l.transactionid,
    l.waitstart
FROM pg_locks AS l
ORDER BY l.granted, l.waitstart NULLS LAST;
```

`pg_locks` is cluster-wide. Relation OIDs can be resolved against `pg_class` only for relations in the current database (or shared objects where applicable), so cross-database tooling must account for database identity.

## Wait Events

A backend waiting for a lock normally reports `wait_event_type = 'Lock'`, but not every concurrency stall should be diagnosed solely from this field. Combine:

- `state`
- `wait_event_type`
- `wait_event`
- `xact_start`
- `query_start`
- blocking PID relationships
- lock mode/object
- application and connection-pool telemetry

An `active` backend can be waiting rather than consuming CPU.

## Deadlocks

A deadlock is a cycle in which transactions each wait for resources held by another member of the cycle.

```text
T1 holds A -> waits for B
T2 holds B -> waits for A
```

PostgreSQL detects deadlocks and aborts one transaction so the others can proceed. Applications must not depend on which transaction PostgreSQL chooses as the victim.

The primary prevention technique is deterministic lock ordering: transactions that need multiple objects should acquire them in a consistent order and should acquire the strongest lock mode they know they will need rather than attempting risky lock upgrades later.

Applications should retry the entire failed transaction when retry semantics are safe.

## deadlock_timeout and log_lock_waits

`deadlock_timeout` controls how long PostgreSQL waits before performing deadlock detection. Deadlock detection has cost, so reducing it aggressively on a busy production system can add unnecessary overhead.

When `log_lock_waits` is enabled, `deadlock_timeout` also determines when a lock-wait log message is emitted. Temporarily lowering `deadlock_timeout` can therefore be useful during a targeted contention investigation, but it is not a substitute for fixing long transactions or poor lock ordering.

## lock_timeout, statement_timeout, and transaction_timeout

`lock_timeout` aborts a statement when an individual lock acquisition waits longer than the configured duration. It is particularly useful as a deployment/migration guardrail.

```sql
SET lock_timeout = '5s';
ALTER TABLE ...;
```

If the required lock cannot be obtained quickly, failing the deployment step is often safer than allowing it to wait indefinitely and participate in a production blocking queue.

`statement_timeout` limits statement execution time, while PostgreSQL 18 `transaction_timeout` limits the total duration of a transaction. These controls solve different problems. Global settings should be applied carefully because workload classes often need different limits.

Prepared transactions are not subject to `transaction_timeout`, so two-phase-commit environments require explicit prepared-transaction monitoring.

## DDL Concurrency

DDL deserves special operational treatment because many commands require strong relation locks.

Before a production migration:

1. identify long-running transactions;
2. determine the required lock mode;
3. configure a bounded `lock_timeout`;
4. test on production-scale data;
5. understand whether the command rewrites a relation or performs long validation;
6. have a rollback/abort procedure;
7. monitor blockers during execution.

A DDL statement waiting for a lock is not harmless merely because it has not started changing data. It can become part of a queue that affects later workload requests.

## Lock Manager Capacity

`max_locks_per_transaction` sizes the shared lock table based on the expected average number of distinct lockable objects per server process or prepared transaction. It is not a limit on the number of rows that can be locked.

Workloads touching very large partition hierarchies or many relations in one transaction may require additional capacity. Increasing the setting increases shared-memory requirements and requires restart.

Standbys must have `max_locks_per_transaction` set to at least the primary's value so recovery and standby queries can operate correctly.

## Prepared Transactions

A prepared two-phase transaction can continue holding locks after the original client session has disappeared.

```sql
SELECT *
FROM pg_prepared_xacts
ORDER BY prepared;
```

During unexplained blocking, include prepared transactions in the investigation. They can be especially confusing because there is no ordinary active client backend to terminate.

## Monitoring Strategy

Continuously observe:

- count of sessions waiting on `Lock`
- age of the oldest lock wait
- age/state of root blockers
- blocked sessions per root blocker
- deadlocks per database
- idle-in-transaction duration
- long transaction duration
- prepared-transaction age
- DDL lock-wait duration
- connection-pool utilization and queue depth
- transaction/statement timeout rates

Use lock waits as an application SLO signal: a short lock wait can be normal; a sustained blocking chain that consumes the request latency budget is an incident.

## Alerting Strategy

Recommended alert classes:

### Warning

- sustained lock waits above workload baseline
- root blocker older than expected transaction SLO
- growing blocked-session count
- old `idle in transaction` session
- unexpected prepared transaction

### Critical

- blocking chain causing application SLO breach
- DDL blocking a high-volume workload
- connection pool approaching exhaustion because of lock waits
- repeated deadlocks indicating application ordering defects
- blocker cannot be safely resolved before outage threshold

Avoid alerting on every lock. Locks are normal; pathological waiting is not.

## Failure Scenarios

### Scenario 1 — Idle-in-Transaction Blocker

An application modifies rows and then leaves the transaction open. The backend becomes idle but retains locks until commit or rollback. Other transactions queue while CPU remains low.

### Scenario 2 — DDL Queue Amplification

A migration requests a strong table lock behind a long transaction. New requests requiring incompatible locks begin accumulating behind the migration, rapidly converting one old transaction into an application outage.

### Scenario 3 — Inconsistent Lock Ordering

Two application code paths update the same business objects in opposite order. Under concurrency they deadlock. PostgreSQL aborts one transaction, but the application does not retry correctly, surfacing intermittent failures to users.

### Scenario 4 — Prepared Transaction Holds Locks

A two-phase transaction is prepared but never committed or rolled back. It retains locks even though the initiating connection no longer exists.

### Scenario 5 — Queue Worker Contention

Many workers select the same pending jobs with `FOR UPDATE` and wait on one another. A deliberate `FOR UPDATE SKIP LOCKED` queue design may improve throughput if skipping locked jobs is semantically acceptable.

## Troubleshooting Runbook

1. Confirm that the latency is lock-related using wait events.
2. List blocked sessions with `pg_blocking_pids()`.
3. Walk the chain to the root blocker rather than terminating arbitrary waiters.
4. Record PID, user, application, transaction age, SQL, lock object/mode, and business owner.
5. Check for idle-in-transaction and prepared transactions.
6. Determine whether the blocker is performing useful work or is abandoned.
7. Prefer `pg_cancel_backend()` when canceling the current statement is sufficient.
8. Use `pg_terminate_backend()` only when ending the session/transaction is required and business impact is understood.
9. Verify blocked sessions drain and pool saturation recovers.
10. Correct the underlying transaction scope, lock order, DDL procedure, timeout, or queue design.
11. Capture the blocking graph and timeline for RCA.

Do not automatically terminate the oldest transaction without understanding its role. It could be a migration, financial transaction, maintenance operation, or other workload whose rollback has significant cost.

## Recovery

Lock incidents normally recover when the blocking transaction commits, rolls back, is canceled/terminated as appropriate, or when PostgreSQL resolves a deadlock by aborting a participant.

After intervention, validate:

```text
blocked session count -> decreasing to baseline
oldest lock wait      -> cleared
connection pool       -> draining/recovering
transaction age       -> normal
application latency   -> recovered
error/retry rate      -> normal
```

A recovered database is not the end of the incident. Confirm that retry storms or queued requests do not cause a secondary saturation event.

## Automation Guardrails

Useful automation can:

- detect and visualize blocker trees;
- annotate blockers with application/user/transaction age;
- alert on sustained chains rather than isolated waits;
- enforce bounded `lock_timeout` in deployment tooling;
- flag stale prepared transactions;
- detect idle-in-transaction sessions;
- capture lock evidence automatically during an incident.

Automatic backend termination should be highly constrained. Prefer notification and evidence capture unless ownership, transaction class, age, and safe termination policy are explicitly known.

## Production Case Study — DDL Blocking Cascade

A deployment issues `ALTER TABLE` while an application transaction has been open for several minutes. The DDL waits for its required strong lock. New application requests then accumulate behind the lock queue. CPU and storage metrics remain normal, but request latency and pool utilization rise sharply.

The DBRE identifies the root transaction using `pg_blocking_pids()`, confirms it is an abandoned application transaction, terminates it under the incident procedure, and the queue drains. The deployment is stopped and rescheduled.

Permanent controls are added:

- bounded migration `lock_timeout`;
- pre-deployment long-transaction check;
- idle-in-transaction alerting;
- transaction-duration SLOs;
- blocker-tree dashboards;
- application ownership metadata in connection settings.

The lesson is that lock incidents are frequently queueing incidents rather than compute incidents.

## SRE/DBRE Principles

> Locks are normal PostgreSQL behavior; sustained lock waits and uncontrolled blocking chains are the reliability problem.

> Find the root blocker before taking action. Killing waiters treats symptoms and can increase retry pressure.

> Transaction duration is a concurrency control. Short, deterministic transactions reduce lock exposure, vacuum interference, rollback cost, and outage amplification.
