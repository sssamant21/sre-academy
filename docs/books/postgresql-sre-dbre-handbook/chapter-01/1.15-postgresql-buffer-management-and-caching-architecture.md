# 1.15 — PostgreSQL Buffer Management and Caching Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL buffer management sits between execution/access methods and persistent relation storage. Production DBRE/SRE teams must understand shared buffers, the operating-system page cache, buffer replacement, dirty-page handling, background/checkpoint writes, asynchronous I/O, and the limits of cache-hit metrics. A cache problem can appear as query latency, storage saturation, checkpoint pressure, backend writes, or unpredictable performance after working-set changes.

## Architecture

```text
Executor / access method
        |
        v
PostgreSQL buffer manager
        |
        +--> page present in shared_buffers -> buffer hit
        |
        +--> page absent
                |
                v
          PostgreSQL I/O subsystem
                |
                v
          kernel/filesystem cache
                |
                v
          persistent storage

Modified shared buffer
        -> dirty buffer
        -> background writer / checkpointer / backend write
        -> filesystem/storage persistence
```

The standard PostgreSQL block size is normally 8 KiB, although it is a build-time property and should be verified with `SHOW block_size` rather than assumed for nonstandard builds.

## shared_buffers

`shared_buffers` defines the memory PostgreSQL dedicates to its shared database buffer cache. It is allocated at server start and is shared across database sessions.

PostgreSQL documentation describes approximately 25% of system memory as a reasonable starting point for a dedicated database server with at least 1 GB RAM, while also noting that allocations above roughly 40% are unlikely to outperform smaller settings because PostgreSQL relies on the operating-system cache as well. These values are starting guidance, not universal production targets.

Large `shared_buffers` settings can also require WAL/checkpoint sizing changes because more dirty data can accumulate between writes.

## PostgreSQL Cache and Operating-System Cache

PostgreSQL shared buffers are not the complete caching picture. Relation reads can also benefit from the kernel/filesystem page cache.

Therefore:

```text
PostgreSQL buffer miss != guaranteed physical-disk read
```

A PostgreSQL read request can miss `shared_buffers` but still be satisfied from the operating-system cache. PostgreSQL statistics do not always distinguish kernel-cache hits from actual device reads, so OS/cloud storage telemetry is required for complete diagnosis.

## effective_cache_size

`effective_cache_size` does **not** allocate memory and is not a cache-size limit. It is a planner estimate of the cache that is likely to be available to an individual query, including PostgreSQL shared buffers and relevant operating-system cache.

Incorrect values can influence the planner's relative preference for index-based versus scan-heavy plans, but changing `effective_cache_size` does not itself create or remove cached pages.

## Buffer Lookup and Replacement

When a requested relation page is already in shared buffers, PostgreSQL can use the cached buffer. When it is absent, PostgreSQL must obtain a reusable buffer and initiate the required read path.

PostgreSQL uses usage information in its shared-buffer replacement strategy. The `pg_buffercache` extension exposes a `usagecount` for each shared buffer and can help inspect real-time cache state.

A working set substantially larger than useful cache capacity can cause repeated eviction and rereading. Large scans, OLTP point lookups, maintenance jobs, and analytical workloads can therefore interact very differently with the cache.

## Buffer Pins and Contention

A backend can pin a shared buffer while using it. A pinned buffer cannot simply be reused until the pin is released. Production diagnosis should distinguish ordinary cache pressure from buffer contention or waits involving PostgreSQL's buffer-management synchronization mechanisms.

Use wait events together with I/O statistics rather than interpreting every latency increase as a cache miss problem.

## Dirty Buffers

A page modified in shared buffers becomes dirty. The page does not have to be written to its relation file before every transaction commits. PostgreSQL WAL provides the required durability ordering: WAL describing a change must reach the appropriate durability point before a dirty data page can safely become the durable representation of that change.

Dirty buffers can later be written by:

- the background writer,
- the checkpointer,
- client backends when required,
- other applicable backend types during their work.

A high rate of client-backend writes can indicate that background/checkpoint writing or overall buffer/storage configuration deserves investigation.

## Background Writer

The background writer scans shared buffers and writes selected dirty buffers so that cleaner reusable buffers are more likely to be available when backends need them.

Its objective is not to guarantee durability at transaction commit and it does not replace the checkpointer. Evaluate background-writer behavior together with checkpoint activity, backend writes, WAL behavior, storage latency, and workload shape.

## Checkpoint Interaction

Checkpoints establish recovery boundaries and require dirty buffers covered by the checkpoint to be written according to PostgreSQL's checkpoint process.

Excessively frequent checkpoints can cause:

- additional data-file write pressure,
- more first-change-after-checkpoint full-page images when `full_page_writes` is enabled,
- storage latency spikes,
- increased competition with application and maintenance I/O.

Buffer tuning and checkpoint tuning therefore cannot be treated as independent exercises.

## PostgreSQL 18 Asynchronous I/O

PostgreSQL 18 introduced an asynchronous I/O subsystem. Eligible operations can issue multiple I/O requests without waiting for each request synchronously before proceeding.

Important PostgreSQL 18 controls include:

- `io_method`
- `io_workers` when `io_method = worker`
- `io_max_concurrency`
- `effective_io_concurrency`
- `maintenance_io_concurrency`

PostgreSQL 18 supports `worker`, `io_uring` where the server was built with the required support, and `sync` I/O methods. The default is `worker`.

Increasing I/O concurrency is not automatically beneficial. Excessive concurrency can increase device queueing and latency for other queries. Tune it against the actual storage platform and workload.

## Observability with pg_stat_io

PostgreSQL 18 `pg_stat_io` reports cluster-wide I/O statistics by combinations of backend type, I/O object, and context. PostgreSQL 18 also added byte counters and WAL I/O rows.

Useful signals include:

- reads and `read_bytes`
- writes and `write_bytes`
- extends and `extend_bytes`
- evictions
- reuses
- fsyncs
- read/write/fsync timing when timing collection is enabled
- backend type
- I/O context
- target object

A high eviction count can indicate shared-buffer pressure, but the conclusion must be validated against working-set size, OS cache behavior, query plans, and storage telemetry.

## Database-Level Cache Metrics

`pg_stat_database` exposes `blks_hit` and `blks_read`. A basic PostgreSQL shared-buffer hit ratio can be calculated as:

```sql
SELECT datname,
       blks_hit,
       blks_read,
       round(
         100.0 * blks_hit /
         NULLIF(blks_hit + blks_read, 0),
         2
       ) AS shared_buffer_hit_pct
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;
```

This metric describes PostgreSQL shared-buffer behavior only. It does **not** prove whether `blks_read` required physical device I/O because data might already have been present in the kernel page cache.

Do not establish a universal production SLO such as “cache hit ratio must exceed 99%.” Workload type matters.

## pg_buffercache

The supplied `pg_buffercache` extension provides real-time inspection of shared-buffer contents. It can expose relation identity, block number, dirty state, usage count, and pinning-backend counts.

PostgreSQL 18 also provides cache-eviction functions including `pg_buffercache_evict_relation()` and `pg_buffercache_evict_all()`.

These eviction functions are primarily diagnostic/testing capabilities. **Do not use cache eviction casually in production** because deliberately cold caches can create severe latency and I/O spikes.

Example summary where the extension is approved and installed:

```sql
SELECT * FROM pg_buffercache_summary();
```

## EXPLAIN and Buffer Analysis

For query-level investigation use `EXPLAIN (ANALYZE, BUFFERS)` where it is operationally safe.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Buffer information helps distinguish cache-heavy execution from plans performing significant reads/writes. Remember that `ANALYZE` executes the statement; do not run write statements or expensive production queries casually merely to collect diagnostics.

## Working-Set Analysis

The useful question is not simply “How large is the database?” but:

```text
How much of the actively accessed working set
must remain hot to meet the latency objective?
```

A multi-terabyte database can perform well with a much smaller hot working set, while a smaller database with random access across most pages can generate significant cache churn.

Track cache behavior during representative peak periods rather than only after quiet periods or immediately after restart.

## Cold Cache and Restart Behavior

A PostgreSQL restart clears `shared_buffers`. Depending on operating-system behavior, some filesystem cache may remain, but SREs should not assume identical warm-cache performance immediately after restart, failover, host replacement, or storage migration.

Capacity and failover tests should include cold/warming-cache behavior when latency objectives depend heavily on caching.

## Memory Sizing Guardrails

Do not maximize `shared_buffers` simply because RAM is available. The total server/container memory envelope must also account for:

- backend-private memory,
- `work_mem` operations,
- maintenance memory,
- autovacuum workers,
- parallel workers,
- connection/process overhead,
- dynamic shared memory,
- extension memory,
- operating-system/kernel memory,
- filesystem cache.

On Linux, explicit huge pages can reduce overhead for a large main shared-memory region. This is different from Transparent Huge Pages (THP), which PostgreSQL documentation generally discourages for some Linux environments because of performance degradation.

## Monitoring Model

A production dashboard should correlate at least:

```text
Query latency / throughput
        |
        +-- pg_stat_io
        +-- pg_stat_database blocks
        +-- pg_stat_bgwriter
        +-- pg_stat_checkpointer
        +-- WAL I/O
        +-- temporary I/O
        +-- EXPLAIN BUFFERS samples
        +-- OS page-cache / memory pressure
        +-- device/cloud latency, IOPS, throughput, queue depth
```

Never diagnose the buffer manager from one PostgreSQL ratio alone.

## Alerting

Useful alert conditions include:

- sustained increase in shared-buffer evictions combined with latency/I/O degradation,
- abnormal client-backend writes or fsyncs,
- sustained storage read/write latency,
- checkpoint write/sync pressure,
- memory pressure or swap/OOM risk,
- large temporary-I/O increase,
- post-restart/failover latency that fails to recover,
- I/O concurrency saturation or queue-depth growth.

Use workload-aware baselines and trend alerts rather than arbitrary universal hit-ratio thresholds.

## Failure Scenarios

### 1. Working Set Exceeds Effective Cache

A workload change causes random access across a much larger set of pages. Evictions and reads rise, storage latency becomes visible, and query latency increases.

### 2. Oversized shared_buffers

A server allocates too much RAM to shared buffers, leaving insufficient headroom for backend-private memory, the OS, and filesystem cache. Memory pressure or OOM risk rises even though the database cache itself is large.

### 3. Checkpoint Write Pressure

Dirty buffers accumulate and checkpoint activity competes with application I/O. Read cache metrics may remain excellent while write latency deteriorates.

### 4. Backend Write Pressure

Client backends frequently perform writes because cleaner reusable buffers are not available when needed. Investigate background writer, checkpoint behavior, workload churn, and storage performance.

### 5. Query Plan Regression

A planner/statistics change causes a query to read far more pages. The symptom appears as “cache pressure,” but the root cause is an inefficient access path.

### 6. Cold Cache After Failover

A promoted/restarted instance initially has a cold PostgreSQL cache. Application latency spikes while the active working set is repopulated.

### 7. Excessive AIO Concurrency

I/O concurrency is increased aggressively on storage that cannot efficiently absorb the queue depth. Individual I/O latency rises and neighboring workloads degrade.

## Troubleshooting Workflow

1. Confirm whether the latency is read, write, WAL, lock, CPU, or temporary-I/O related.
2. Inspect `pg_stat_io` by backend type, object, and context.
3. Compare `blks_hit` and `blks_read` trends, not only lifetime totals.
4. Inspect `pg_stat_bgwriter` and `pg_stat_checkpointer`.
5. Correlate PostgreSQL statistics with OS/cloud storage latency, IOPS, throughput, and queue depth.
6. Identify query-plan or working-set changes.
7. Use `EXPLAIN (ANALYZE, BUFFERS)` only where operationally safe.
8. Inspect `pg_buffercache` selectively when deeper cache-state evidence is required.
9. Review `shared_buffers`, checkpoint configuration, AIO settings, and total memory headroom as a system.
10. Make one controlled change at a time and compare against a representative baseline.

## Recovery and Mitigation

Possible mitigations depend on the diagnosed cause and can include:

- correcting a query/index/statistics regression,
- reducing workload concurrency,
- rescheduling I/O-heavy maintenance,
- adjusting `shared_buffers` after evidence-based testing,
- correcting checkpoint/WAL sizing,
- tuning I/O concurrency for the storage platform,
- increasing storage performance/capacity,
- improving connection/workload isolation,
- prewarming selected relations where operationally justified and supported.

Do not use cache flushing as a routine performance remediation.

## Automation and SRE Controls

Automate collection of:

- `shared_buffers` and total memory/container limits,
- `pg_stat_io` deltas,
- database block-hit/read deltas,
- checkpoint/background-writer statistics,
- storage latency/IOPS/throughput,
- temporary-file activity,
- restart/failover timestamps,
- top queries by I/O.

Configuration review automation should flag extreme `shared_buffers` percentages, missing memory headroom, unvalidated AIO changes, and cache recommendations based only on hit ratio.

## Production Case Study — High Hit Ratio, Slow Database

A production database reports a 99%+ PostgreSQL shared-buffer hit ratio, yet application write latency increases sharply.

The investigation finds:

```text
shared-buffer hit ratio -> still high
checkpoint frequency    -> increased
checkpoint writes       -> elevated
storage write latency   -> elevated
WAL/data write pressure -> elevated
```

The hit ratio is accurate but irrelevant to the dominant failure path. It describes many read requests being satisfied from PostgreSQL's cache; it says nothing about whether WAL flushes and dirty-page persistence are healthy.

The incident is resolved by correcting checkpoint/WAL sizing and validating storage write capacity rather than increasing `shared_buffers`.

## Production Review Checklist

Before approving buffer/cache changes:

- [ ] Confirm the active working-set pattern.
- [ ] Review `pg_stat_io`, not only cache-hit ratio.
- [ ] Correlate with OS/cloud storage telemetry.
- [ ] Verify total memory headroom.
- [ ] Review checkpoint and WAL behavior.
- [ ] Validate AIO configuration against the storage platform.
- [ ] Test representative concurrency.
- [ ] Test restart/failover cache-warming behavior where relevant.
- [ ] Document rollback criteria.

## SRE/DBRE Principle

> Cache metrics are evidence, not a verdict. Diagnose PostgreSQL shared buffers, operating-system caching, query access patterns, WAL, temporary I/O, checkpoint writes, and the storage device as one end-to-end I/O system.
