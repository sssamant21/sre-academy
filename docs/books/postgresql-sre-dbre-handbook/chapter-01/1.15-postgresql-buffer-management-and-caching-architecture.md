# 1.15 — PostgreSQL Buffer Management and Caching Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL uses shared buffers together with operating-system caching and its storage I/O subsystem. Understanding buffer hits, physical reads, dirty buffers, eviction pressure, planner cache assumptions, and PostgreSQL 18 asynchronous I/O is essential for production performance analysis.

## Buffer Path

```text
Executor / access method
  -> buffer lookup
     -> hit in shared_buffers: use cached page
     -> miss: read page through storage I/O path
  -> page may become dirty after modification
  -> background/checkpoint writing eventually persists dirty page
```

`shared_buffers` defines PostgreSQL's main shared database buffer cache.

## PostgreSQL Cache and OS Cache

PostgreSQL does not bypass the operating system for all ordinary data-file caching. Effective database caching can therefore include both PostgreSQL shared buffers and filesystem/kernel cache. Some pages can exist in both layers.

`effective_cache_size` does not allocate cache. It is a planner estimate of cache likely to be available to a query.

## Buffer Replacement

PostgreSQL manages a finite shared-buffer pool. Workloads that touch more pages than can remain useful in cache will generate churn and physical I/O. Large scans can have very different cache behavior from small indexed OLTP workloads.

## Dirty Buffers

A modified buffer becomes dirty. WAL durability ordering protects the change, while dirty pages can be written later by backend activity, the background writer, or checkpoint processing as required.

## Background Writer

The background writer attempts to write dirty shared buffers so backends are less likely to need to perform those writes themselves. Its behavior should be evaluated together with checkpoint and workload I/O rather than tuned in isolation.

## Checkpoint Interaction

Checkpoints require dirty pages covered by the checkpoint to be flushed according to PostgreSQL's checkpoint algorithm. Excessive checkpoint frequency can increase write pressure and WAL full-page-image generation.

## PostgreSQL 18 Asynchronous I/O

PostgreSQL 18 introduces an asynchronous I/O subsystem that can improve operations including sequential scans, bitmap heap scans, and vacuum. When comparing performance across major versions, DBRE teams should account for version-specific I/O behavior and configuration rather than assuming identical read paths.

## Observability

PostgreSQL 18 provides `pg_stat_io` for I/O statistics by backend type, object, context, and operation. Combine it with relation/database statistics, `EXPLAIN (ANALYZE, BUFFERS)`, checkpoint statistics, OS cache/storage telemetry, and workload latency.

Do not interpret a high PostgreSQL buffer-hit ratio as proof that storage is healthy; WAL, temporary files, checkpoints, and uncached working sets can still generate critical I/O.

## Cache Diagnosis

```text
latency increase
  -> check wait events
  -> check pg_stat_io / buffer reads
  -> check storage latency
  -> check working-set change
  -> check plan change
  -> check checkpoint/write activity
  -> check temp spill
```

## Tuning Guardrails

Do not maximize `shared_buffers` simply because memory exists. Leave capacity for backend/private memory, OS caching, connection overhead, maintenance operations, parallel workers, and the operating system. Memory sizing must be concurrency-aware.

## Failure Scenarios

Common patterns include cache churn after workload changes, oversized shared memory reducing OS headroom, high physical reads from plan regression, dirty-buffer pressure, checkpoint write bursts, temporary I/O mistaken for table-read pressure, and storage latency despite acceptable cache metrics.

## Production Case Study — High Hit Ratio, Slow Database

A database reports a high shared-buffer hit ratio while write latency is poor. Investigation shows frequent checkpoints and saturated storage writes. The hit ratio describes many read requests but does not explain WAL flush and dirty-page persistence latency. Correct diagnosis requires end-to-end I/O telemetry.

## SRE/DBRE Principle

> Cache metrics are context, not a verdict. Diagnose PostgreSQL read, write, WAL, temporary, and checkpoint I/O as separate but interacting paths.
