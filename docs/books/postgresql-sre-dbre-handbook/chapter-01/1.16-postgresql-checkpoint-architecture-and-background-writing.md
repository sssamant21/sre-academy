# 1.16 — PostgreSQL Checkpoint Architecture and Background Writing

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

Checkpoints bound crash-recovery work and coordinate persistence of dirty database pages. Their frequency and write pattern affect foreground latency, storage throughput, WAL volume, recovery time, and production stability. The background writer is related to dirty-buffer management but has a different purpose and must be monitored and tuned separately from the checkpointer.

## Architecture

```text
Backends modify shared buffers
        |
        +--> WAL records generated and flushed as durability requires
        |
        +--> shared buffers become dirty
                    |
                    +--> background writer may clean reusable buffers
                    |
                    +--> checkpointer writes checkpoint-required buffers
                                   |
                                   +--> data files synchronized
                                   +--> checkpoint record establishes recovery boundary
```

A checkpoint is a point in the WAL sequence at which PostgreSQL guarantees that heap and index data files contain all changes required before the checkpoint's redo position. After a crash, recovery starts from the appropriate redo location rather than replaying all historical WAL.

The checkpointer is a dedicated PostgreSQL auxiliary process. The background writer is a separate auxiliary process whose purpose is to make clean reusable shared buffers available and reduce the likelihood that foreground backends must write dirty buffers themselves.

## Checkpoint Triggers

Automatic checkpoints are driven primarily by:

- `checkpoint_timeout`
- WAL volume approaching `max_wal_size`
- explicit or internally requested checkpoints for operations that require them

If no WAL has been written since the previous checkpoint, a timeout does not necessarily produce a new checkpoint.

`CHECKPOINT` forces an immediate checkpoint and is not intended as a routine production tuning mechanism. During recovery, the command requests a restartpoint instead.

## `checkpoint_timeout`

`checkpoint_timeout` sets the maximum interval between automatic checkpoints. Increasing it can reduce checkpoint frequency but can increase crash-recovery work and the amount of WAL that must be retained for recovery.

A shorter interval is not automatically safer operationally: frequent checkpoints increase dirty-page write frequency and can increase WAL generation because of full-page images.

## `max_wal_size`

`max_wal_size` is a soft WAL-size target that influences checkpoint frequency; it is not a hard cap on `pg_wal`. WAL can exceed it under several conditions, including heavy WAL generation, archiving delays, replication retention requirements, and checkpoint timing.

Never size the `pg_wal` filesystem on the assumption that PostgreSQL will stop at `max_wal_size`.

## `checkpoint_completion_target`

PostgreSQL throttles checkpoint writes so that checkpoint I/O is spread over much of the interval instead of being issued as one large burst. `checkpoint_completion_target` controls the target completion point as a fraction of the estimated interval between checkpoints.

PostgreSQL 18 defaults this parameter to `0.9`. Reducing it generally causes checkpoint writes to complete more aggressively, increasing instantaneous I/O pressure rather than solving an underlying storage-capacity problem.

## `checkpoint_flush_after`

`checkpoint_flush_after` can ask the operating system to begin writeback after a configured amount of checkpoint data has been written. This can reduce large kernel dirty-page accumulation and end-of-checkpoint synchronization stalls on supported platforms.

Treat it as storage- and OS-dependent tuning. Validate changes with actual latency and throughput telemetry.

## Full-Page Writes and WAL Amplification

With `full_page_writes` enabled, PostgreSQL can log a full-page image on the first modification of a page after a checkpoint. Therefore:

```text
more frequent checkpoints
        -> more first-page modifications after checkpoints
        -> potentially more full-page images
        -> higher WAL volume
        -> additional archive/replication/storage pressure
```

This is one reason checkpoint tuning must consider WAL generation as well as data-file writes.

## Background Writer Architecture

The background writer periodically writes dirty shared buffers and marks them clean so that backends are more likely to find reusable buffers without performing their own writes.

Important controls include:

- `bgwriter_delay`
- `bgwriter_lru_maxpages`
- `bgwriter_lru_multiplier`
- `bgwriter_flush_after`

The background writer intentionally does not replace checkpoint processing. It can also increase total I/O because a page that is dirtied repeatedly might be written by the background writer and then dirtied again before the next checkpoint.

The tuning objective is therefore not "maximize background writing." It is to reduce disruptive backend writes while avoiding unnecessary write amplification.

## Backend Writes

When PostgreSQL needs a reusable shared buffer and no clean buffer is available, a foreground backend may need to write a dirty buffer itself. This can add latency directly to application work.

Use `pg_stat_io` together with `pg_stat_bgwriter` and `pg_stat_checkpointer` to determine whether foreground processes, the background writer, or the checkpointer are responsible for write pressure. Do not infer this from a single counter.

## Checkpoints vs Restartpoints

On a primary, PostgreSQL performs checkpoints. During recovery or standby operation, PostgreSQL performs restartpoints based on checkpoint records encountered during WAL replay.

PostgreSQL 18 exposes restartpoint statistics through `pg_stat_checkpointer`, including timed, requested, and completed restartpoints. This distinction matters when diagnosing standby storage pressure and recovery performance.

## PostgreSQL 18 Observability

PostgreSQL 18 separates checkpointer and background-writer statistics:

### `pg_stat_checkpointer`

Important fields include:

- `num_timed`
- `num_requested`
- `num_done`
- `restartpoints_timed`
- `restartpoints_req`
- `restartpoints_done`
- `write_time`
- `sync_time`
- `buffers_written`
- `slru_written`

`num_timed` and `num_requested` should not be interpreted as identical to completed checkpoints; PostgreSQL 18 provides `num_done` explicitly for completed checkpoints.

### `pg_stat_bgwriter`

Important fields include:

- `buffers_clean`
- `maxwritten_clean`
- `buffers_alloc`

### `pg_stat_io`

Use `pg_stat_io` to analyze I/O by backend type, object, context, and operation. PostgreSQL-level I/O statistics should be correlated with operating-system and storage telemetry because the OS page cache and device layer remain part of the path.

## Baseline SQL

```sql
SELECT * FROM pg_stat_checkpointer;

SELECT * FROM pg_stat_bgwriter;

SELECT backend_type,
       object,
       context,
       reads,
       read_bytes,
       writes,
       write_bytes,
       write_time,
       fsyncs,
       fsync_time
FROM pg_stat_io
ORDER BY backend_type, object, context;
```

Timing columns depend on the applicable I/O timing configuration and should be interpreted with awareness of when statistics were enabled/reset.

## Monitoring Model

Monitor at least:

1. checkpoint frequency and requested-vs-timed behavior
2. completed checkpoints
3. checkpoint write and synchronization time
4. restartpoint behavior on standbys
5. buffers and SLRU buffers written by checkpoints
6. background-writer cleaned buffers and `maxwritten_clean`
7. WAL generation rate
8. full-page-image/WAL trends where available
9. `pg_wal` filesystem utilization and projected exhaustion
10. storage write latency, IOPS, throughput, queue depth, and fsync behavior
11. application commit and query latency
12. bulk loads, VACUUM, backup activity, and other competing I/O workloads

Always analyze rates over intervals rather than treating cumulative counters as instantaneous values.

## Alerting Strategy

Useful alerts include:

- sustained unexpected checkpoint frequency
- high requested-checkpoint rate relative to workload baseline
- rising checkpoint `write_time` or `sync_time`
- repeated storage saturation during checkpoint windows
- WAL generation exceeding planned capacity
- `pg_wal` time-to-exhaustion risk
- standby restartpoint/replay problems
- application latency strongly correlated with checkpoint or writeback activity

Avoid universal thresholds such as "more than N checkpoints per hour is always bad." A bulk-ingest platform and a low-write OLTP database have different legitimate baselines.

## Failure Scenario 1 — `max_wal_size` Undersized for Burst Workload

```text
bulk ingestion
   -> WAL generation spikes
   -> max_wal_size pressure
   -> checkpoints requested frequently
   -> dirty pages written more often
   -> full-page-image frequency can increase
   -> storage latency rises
   -> foreground latency rises
```

Corrective action is workload-aware WAL/checkpoint/storage sizing, not simply adding CPU.

## Failure Scenario 2 — Slow Storage Extends Checkpoint Synchronization

The database generates a manageable amount of WAL, but storage fsync latency increases. Checkpoint `sync_time` rises and latency spikes appear around checkpoint completion.

Investigate the storage layer, competing workloads, kernel writeback, and infrastructure throttling before changing PostgreSQL parameters.

## Failure Scenario 3 — Background Writer Cannot Keep Up

A high-churn workload rapidly consumes clean buffers. The background writer repeatedly reaches its configured cleaning limit and foreground backends perform more write work.

Review `pg_stat_bgwriter`, `pg_stat_io`, shared-buffer allocation behavior, storage headroom, and the background-writer parameters together. Increasing `bgwriter_lru_maxpages` without checking storage capacity can merely move the bottleneck.

## Failure Scenario 4 — Checkpoint Tuning Hides `pg_wal` Capacity Risk

An operator increases `max_wal_size` to reduce checkpoint frequency but does not increase `pg_wal` filesystem headroom or account for replication slots and archive failures. A later consumer outage retains WAL and fills the filesystem.

Checkpoint tuning must always be reviewed with WAL retention and disk-capacity models.

## Troubleshooting Workflow

1. Confirm whether the system is primary, standby, or in recovery.
2. Capture `pg_stat_checkpointer`, `pg_stat_bgwriter`, and relevant `pg_stat_io` statistics.
3. Determine whether checkpoints are predominantly timed or requested.
4. Measure WAL generation rate and `pg_wal` headroom.
5. Review `checkpoint_timeout`, `max_wal_size`, `checkpoint_completion_target`, and flush-after settings.
6. Inspect background-writer behavior and foreground write activity.
7. Correlate checkpoint/writeback timing with storage latency and application latency.
8. Check for bulk ingestion, VACUUM, backup, index build, or other competing I/O workloads.
9. Check replication slots and archiving before assuming WAL size is controlled by checkpoint settings alone.
10. Change one dimension at a time and compare rates over representative workload windows.
11. Validate crash-recovery and storage-capacity implications after tuning.

## Recovery and Operational Guardrails

- Never delete files from `pg_wal` to relieve checkpoint or WAL pressure.
- Do not disable `fsync` or `full_page_writes` as routine checkpoint-performance fixes.
- Do not issue repeated manual `CHECKPOINT` commands to "flush" a busy production database.
- Preserve enough WAL/storage capacity for replication, archiving, backups, and recovery objectives.
- Test parameter changes under representative concurrency and storage behavior.
- For managed PostgreSQL services, validate which checkpoint/background-writer parameters and metrics the provider exposes before applying self-managed assumptions.

## Automation

Production automation should collect checkpoint/background-writer deltas and correlate them with WAL and storage metrics.

Example derived metrics:

```text
checkpoint_rate = delta(num_done) / interval
requested_checkpoint_rate = delta(num_requested) / interval
checkpoint_write_ms_per_sec = delta(write_time) / interval_seconds
checkpoint_sync_ms_per_sec = delta(sync_time) / interval_seconds
bgwriter_clean_rate = delta(buffers_clean) / interval
```

Alerting systems should use rate, latency, workload, and capacity context rather than raw cumulative values.

## Production Case Study — Checkpoint Storm During Bulk Ingestion

A production PostgreSQL cluster normally handles moderate OLTP traffic. A new ingestion pipeline begins loading a large batch and WAL generation increases several-fold. `max_wal_size` was sized for the normal workload, so checkpoints are requested much more frequently.

Storage write throughput and queue depth rise, full-page-image-related WAL overhead increases, and API latency degrades even though CPU has significant headroom.

The DBRE investigation compares `pg_stat_checkpointer`, WAL-generation rate, `pg_stat_io`, and infrastructure storage metrics. The durable remediation is to size WAL/checkpoint capacity for the real burst profile, verify `pg_wal` headroom, and ensure storage can sustain both foreground and checkpoint writes. Increasing CPU would not address the limiting resource.

## SRE/DBRE Principle

> Checkpoint tuning is a balance among steady-state write I/O, WAL capacity, foreground latency, and crash-recovery time. The background writer can reduce foreground dirty-buffer writes, but neither component can compensate for an undersized or throttled storage architecture.
