# 1.16 — PostgreSQL Checkpoint Architecture and Background Writing

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

Checkpoints bound crash-recovery work and coordinate persistence of dirty database pages. Their frequency and write pattern directly affect I/O latency, WAL volume, recovery time, and production stability.

## Checkpoint Architecture

A checkpoint is a point in the WAL sequence at which PostgreSQL ensures the relevant heap and index data files contain changes required before that checkpoint boundary. PostgreSQL writes a checkpoint record to WAL and crash recovery uses the checkpoint information to determine where redo must begin.

```text
WAL changes
  -> dirty buffers accumulate
  -> checkpoint begins
  -> required dirty pages written
  -> checkpoint WAL record / synchronization
  -> recovery boundary advances
```

## Checkpoint Triggers

The checkpointer starts checkpoints based primarily on elapsed time (`checkpoint_timeout`) or WAL volume approaching `max_wal_size`. PostgreSQL can also perform requested checkpoints for specific administrative operations.

Frequent forced checkpoints are usually a signal to investigate workload and configuration rather than a normal steady state.

## checkpoint_completion_target

PostgreSQL spreads checkpoint writes across the checkpoint interval to reduce bursty I/O. `checkpoint_completion_target` controls how much of the interval is targeted for completing checkpoint work.

## Full-Page-Write Relationship

With `full_page_writes` enabled, the first modification of a page after a checkpoint can require a full-page image in WAL. More frequent checkpoints can therefore increase WAL volume as well as data-file write activity.

## Background Writer

The background writer writes dirty shared buffers to reduce the chance that server backends must write them themselves. It is distinct from the checkpointer and must not be treated as a replacement for checkpoint processing.

## Monitoring

PostgreSQL 18 provides `pg_stat_checkpointer` and `pg_stat_bgwriter` as separate views. Monitor checkpoint counts/reasons, checkpoint write/sync timing, buffers written, backend writes, WAL rate, storage latency, and application latency.

## Alerting

Alert on sustained checkpoint frequency, repeated checkpoint warnings, increasing checkpoint write/sync time, backend-write pressure, storage saturation, and latency correlated with checkpoint cycles. Tune from measured behavior rather than generic percentages.

## Failure Scenarios

Typical patterns include `max_wal_size` too small for workload bursts, slow storage extending checkpoint work, bulk loads causing repeated checkpoints, aggressive timeout settings, and I/O contention among checkpoint writes, WAL, vacuum, and application reads/writes.

## Troubleshooting Workflow

1. Determine checkpoint trigger frequency and cause.
2. Measure WAL generation rate.
3. Review `checkpoint_timeout`, `max_wal_size`, and `checkpoint_completion_target`.
4. Inspect checkpoint write/sync time and storage telemetry.
5. Correlate with bulk jobs, vacuum, backups, and application latency.
6. Verify storage headroom before increasing WAL/checkpoint targets.
7. Change configuration gradually and validate recovery/capacity implications.

## Production Case Study — Checkpoint Storm

A bulk ingestion job sharply increases WAL generation. `max_wal_size` is sized for normal OLTP traffic, so checkpoints are triggered repeatedly. Storage write latency rises and API response time degrades. Increasing CPU does not help. The durable fix is to size checkpoint/WAL capacity for the actual burst profile and ensure the storage layer can sustain the resulting write workload.

## SRE/DBRE Principle

> Checkpoint tuning is a three-way balance among steady-state I/O, WAL/storage capacity, and crash-recovery time. Optimize the system, not a single checkpoint metric.
