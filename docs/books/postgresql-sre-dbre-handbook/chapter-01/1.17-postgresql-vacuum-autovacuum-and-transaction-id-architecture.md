# 1.17 — PostgreSQL Vacuum, Autovacuum, and Transaction ID Architecture

**Status:** Technical Review Complete → Production Review Pending  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

VACUUM is part of PostgreSQL's correctness, availability, performance, and capacity architecture. MVCC creates obsolete tuple versions; VACUUM makes reusable space available, maintains the visibility map, freezes old transaction and multixact identifiers, and protects the cluster from wraparound. Autovacuum provides the continuous maintenance capacity required to perform this work without depending on manual intervention.

## Architecture

```text
INSERT / UPDATE / DELETE
        |
        v
MVCC tuple versions + transaction identifiers
        |
        +--> dead tuples / changed tuples
        |
        +--> XID and MultiXact age
        |
        v
Autovacuum launcher
        |
        +--> autovacuum workers
        |       |
        |       +--> VACUUM: prune/freeze/reclaim/update VM
        |       +--> ANALYZE: refresh planner statistics
        |
        v
Reusable relation space + safe frozen horizons + current statistics
```

The autovacuum launcher schedules maintenance across databases and starts autovacuum workers. In PostgreSQL 18, `autovacuum_worker_slots` defines the number of autovacuum worker slots PostgreSQL reserves, while `autovacuum_max_workers` controls how many workers may run concurrently. Capacity planning must therefore consider both settings.

## Why VACUUM Exists

PostgreSQL MVCC generally does not overwrite an existing tuple version in place. UPDATE creates a new version and DELETE leaves a version that cannot be removed until no relevant snapshot can see it. Ordinary VACUUM identifies versions that are no longer needed and makes their space reusable inside the relation.

VACUUM is therefore responsible for multiple independent jobs:

1. reclaiming reusable heap space;
2. removing dead index entries where appropriate;
3. maintaining the visibility map;
4. freezing sufficiently old XIDs and MultiXacts;
5. advancing relation/database frozen-ID horizons;
6. supporting transaction-ID wraparound protection.

`VACUUM FULL` is fundamentally different. It rewrites the relation into a new physical copy, requires `ACCESS EXCLUSIVE`, needs additional temporary disk capacity, and should not be used as routine dead-tuple maintenance.

## Autovacuum Trigger Architecture

Autovacuum evaluates VACUUM and ANALYZE independently. For ordinary vacuuming, the trigger is based on the configured threshold plus a scale-factor component derived from relation size. PostgreSQL 18 also provides `autovacuum_vacuum_max_threshold`, which can cap the scale-factor-derived vacuum threshold for large tables.

This is operationally important for very large relations: percentage-only thresholds can otherwise permit a very large number of dead tuples before maintenance begins.

Per-table storage parameters can override cluster defaults. High-churn, very large, append-heavy, or latency-sensitive tables should be tuned according to observed modification rate and vacuum duration rather than relying blindly on global defaults.

## Transaction ID and MultiXact Architecture

Normal transaction IDs are finite 32-bit identifiers and PostgreSQL uses modulo arithmetic for visibility. Old tuple XIDs therefore must eventually be frozen before the identifier space wraps far enough to make old and future transactions ambiguous.

Key horizons include:

- `pg_class.relfrozenxid` — oldest normal XID that might remain unfrozen in a relation;
- `pg_database.datfrozenxid` — database-level lower bound derived from its relations;
- `pg_class.relminmxid` — oldest potentially unfrozen MultiXact ID in a relation;
- `pg_database.datminmxid` — database-level MultiXact horizon.

Monitor age, not merely raw identifier values. `age(datfrozenxid)` and `age(relfrozenxid)` provide operationally useful XID-age views.

Anti-wraparound autovacuum is a safety mechanism. PostgreSQL can initiate wraparound-prevention vacuum work even when normal autovacuum processing has been disabled. Repeatedly terminating anti-wraparound workers can convert a maintenance problem into an availability incident.

## Freezing and PostgreSQL 18 Eager Freezing

Freezing marks old tuple transaction information so that it no longer depends on the normal XID visibility window. Historically, aggressive vacuum scans performed much of this work when age thresholds demanded it.

PostgreSQL 18 adds eager freezing behavior that can opportunistically scan and freeze eligible all-visible pages before an aggressive vacuum becomes mandatory. `vacuum_max_eager_freeze_failure_rate` controls how much unsuccessful eager-freeze scanning is tolerated. This can amortize future anti-wraparound work, but it still consumes I/O and must be evaluated as part of the production maintenance workload.

## Vacuum Failsafe

As XID or MultiXact age approaches dangerous limits, PostgreSQL can enter vacuum failsafe behavior. The priority changes from normal cost-controlled cleanup toward completing wraparound-protection work. SREs should treat activation of failsafe behavior as evidence that maintenance headroom has become inadequate, not as normal steady-state operation.

## Visibility Map and Index-Only Scans

The visibility map tracks pages known to contain tuples visible to all transactions and pages whose tuples are frozen. VACUUM maintains these bits. Index-only scans can avoid heap visits when the visibility map proves that a referenced heap page is all-visible.

Vacuum health therefore affects more than bloat: insufficient maintenance can reduce the effectiveness of index-only scans and increase heap I/O.

## HOT, Pruning, and Space Reuse

Heap-only tuple (HOT) updates can avoid creating new index entries when PostgreSQL's HOT conditions are satisfied. Page pruning can remove obsolete tuple chains when safe. VACUUM complements these mechanisms by performing broader relation maintenance, index cleanup, freezing, and visibility-map work.

Do not equate `n_dead_tup` with exact physical bloat. It is an estimate useful for trends and prioritization; relation/index size, workload behavior, free space, and query performance must also be considered.

## Long-Running Transactions and Horizon Blockers

VACUUM cannot remove tuple versions that may still be visible to an old snapshot. Common horizon blockers include:

- long-running transactions;
- `idle in transaction` sessions;
- prepared transactions;
- replication slots holding `xmin` or `catalog_xmin`;
- long-lived logical decoding requirements.

During an incident, increasing autovacuum worker count without identifying the horizon blocker can add I/O while accomplishing little cleanup.

## Monitoring

### Database XID age

```sql
SELECT datname,
       age(datfrozenxid) AS xid_age,
       mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY xid_age DESC;
```

### Old relations

```sql
SELECT c.oid::regclass AS relation,
       age(c.relfrozenxid) AS xid_age,
       mxid_age(c.relminmxid) AS mxid_age,
       s.n_live_tup,
       s.n_dead_tup,
       s.last_autovacuum,
       s.last_vacuum
FROM pg_class c
LEFT JOIN pg_stat_user_tables s ON s.relid = c.oid
WHERE c.relkind IN ('r','m')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 50;
```

### Active vacuum progress

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

### Long transactions and old snapshots

```sql
SELECT pid,
       usename,
       state,
       xact_start,
       backend_xmin,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Also monitor autovacuum worker utilization, table/index growth, vacuum duration, vacuum/analyze timestamps, WAL generation during maintenance, storage latency, replica lag, and replication-slot horizons.

## Alerting

Use multi-stage alerting rather than one generic dead-tuple threshold.

**Warning:**
- XID/MXID age is rising faster than maintenance can reduce it;
- high-churn tables repeatedly exceed expected dead-tuple envelopes;
- autovacuum workers remain saturated;
- maintenance duration approaches the table's modification interval;
- long transactions or slots persistently hold old horizons.

**Critical:**
- database/relation XID age approaches configured freeze limits with insufficient maintenance progress;
- anti-wraparound vacuum repeatedly fails or is blocked;
- storage/I/O constraints prevent required vacuum progress;
- PostgreSQL reports imminent transaction-ID wraparound protection conditions.

Alert thresholds should leave enough time to vacuum the largest affected relations under realistic production I/O limits.

## Failure Scenarios

### 1. High-Churn Large Table

A very large table receives continuous UPDATE/DELETE traffic. Percentage-based thresholds allow excessive dead tuples to accumulate before vacuum starts. Tune table-specific thresholds/scale factors and PostgreSQL 18's maximum threshold where appropriate, then verify that vacuum completes faster than debt accumulates.

### 2. Long Transaction Prevents Cleanup

Autovacuum runs repeatedly but dead tuples remain. An hours-old transaction or idle-in-transaction session retains an old snapshot. Identify and remediate the blocker according to application safety requirements before increasing vacuum aggressiveness.

### 3. Replication Slot Holds Horizon

A stale logical slot retains `xmin`/`catalog_xmin` and WAL. Vacuum cleanup and `pg_wal` capacity can both be affected. Determine whether the consumer can recover; never drop a slot merely to clear an alert without validating data-consistency requirements.

### 4. Worker Saturation

A few large tables occupy all available autovacuum workers while smaller high-churn tables accumulate debt. Tune per-table settings, worker capacity, and cost/I/O controls based on workload concurrency and storage capability.

### 5. Anti-Wraparound Emergency

A database has accumulated extreme XID age after maintenance was disabled or repeatedly canceled. Protect availability first: remove horizon blockers, preserve storage headroom, allow wraparound-prevention vacuum to run, and avoid unnecessary DDL or workload amplification.

## Troubleshooting and Recovery Runbook

1. Measure database XID and MXID ages.
2. Identify the oldest relations and their maintenance history.
3. Inspect active vacuum progress and autovacuum worker saturation.
4. Identify old transactions, idle-in-transaction sessions, prepared transactions, and slot horizons.
5. Check storage latency, free capacity, WAL generation, and replica lag.
6. Determine whether vacuum is blocked, throttled, repeatedly canceled, or simply unable to keep pace with churn.
7. Apply table-specific autovacuum tuning where evidence supports it.
8. For wraparound risk, prioritize freezing progress over cosmetic bloat reduction.
9. Validate that `relfrozenxid`/`datfrozenxid` and MultiXact ages advance after remediation.
10. Keep monitoring until maintenance debt is demonstrably falling.

## Automation and Production Guardrails

Production automation should continuously inventory:

- database and relation XID/MXID age;
- autovacuum configuration overrides;
- long-running transactions;
- prepared transactions;
- replication-slot horizons;
- vacuum progress/duration;
- dead-tuple and relation-growth trends;
- worker saturation;
- time-to-wraparound safety margin.

Configuration management should prevent accidental disabling of autovacuum or unsafe freeze-age changes without explicit review. Capacity models should include autovacuum CPU, memory, I/O, WAL, and replica impact as first-class workload demand.

## Production Case Study — Vacuum Debt on a Large OLTP Table

A large OLTP table receives continuous updates. Default percentage-based thresholds allow maintenance debt to grow faster than one worker can remove it. Index size and heap reads increase, while a long-lived application transaction further delays tuple removal.

The remediation is not `VACUUM FULL` during peak traffic. The DBRE team first removes the transaction-horizon blocker, then applies table-specific autovacuum thresholds, verifies worker and I/O headroom, and monitors XID age, dead-tuple trend, vacuum duration, WAL generation, and replica lag. PostgreSQL 18's threshold cap and eager-freezing behavior are evaluated as part of the long-term maintenance design.

## SRE/DBRE Principle

> Autovacuum is a continuous production workload and a database safety system. Size it, observe it, and protect its ability to advance transaction horizons before maintenance debt becomes an availability incident.
