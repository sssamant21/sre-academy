# 1.17 — PostgreSQL Vacuum, Autovacuum, and Transaction ID Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

VACUUM is fundamental PostgreSQL maintenance, not optional housekeeping. It reclaims reusable space from obsolete tuple versions, maintains visibility information, supports planner statistics through ANALYZE, and protects against transaction-ID and multixact wraparound.

## Why Vacuum Exists

MVCC retains old tuple versions while they might still be visible. Once they are no longer visible to any relevant transaction, VACUUM can reclaim their space for reuse.

```text
UPDATE / DELETE
  -> old tuple version
  -> visibility horizon advances
  -> VACUUM identifies removable tuples
  -> space becomes reusable
```

Standard VACUUM normally makes space reusable within the relation rather than returning it to the operating system.

## VACUUM vs VACUUM FULL

Routine `VACUUM` can operate alongside normal reads and writes. `VACUUM FULL` rewrites the relation, requires an `ACCESS EXCLUSIVE` lock, takes longer, and needs additional disk space during the rewrite. It is not the routine solution for normal dead-tuple cleanup.

## Autovacuum Architecture

The autovacuum launcher starts worker processes that evaluate tables and run VACUUM and/or ANALYZE when thresholds require it. Worker concurrency is controlled separately from normal client connection limits.

Per-table storage parameters can override global autovacuum behavior for tables whose churn characteristics require special treatment.

## Transaction-ID Protection

PostgreSQL transaction IDs have finite range. Vacuum freezing and anti-wraparound maintenance ensure old tuples can remain safely visible as transaction IDs advance. Anti-wraparound autovacuum is therefore an availability/safety mechanism and should not be casually killed.

## Visibility Map

VACUUM updates visibility information used by PostgreSQL, including information that can enable index-only scans. Vacuum health can therefore affect both storage reuse and query performance.

## ANALYZE

Planner statistics must remain representative of table contents. Autovacuum also schedules automatic ANALYZE based on data-change thresholds. A vacuum problem and a statistics problem can coexist but are not identical.

## PostgreSQL 18 Considerations

PostgreSQL 18 adds vacuum-related improvements, including additional reporting and eager-freezing behavior. Major-version-specific behavior should be validated during upgrades rather than carrying tuning assumptions forward unchanged.

## Monitoring

Monitor:

- `pg_stat_progress_vacuum`
- last vacuum/autovacuum and analyze/autoanalyze times
- dead tuple trends
- table/index size growth
- relation transaction age
- oldest active transactions
- autovacuum worker utilization
- vacuum duration and I/O
- blocked or canceled vacuum activity

PostgreSQL 18 expands statistics around vacuum/analyze time and delay reporting.

## Alerting

Critical alerts should cover transaction-ID wraparound risk and inability of autovacuum to advance. Warning alerts should cover sustained dead-tuple growth, tables repeatedly missing maintenance windows, worker saturation, and long transactions blocking cleanup.

## Failure Scenarios

Common incidents include long transactions preventing cleanup, high-churn tables exceeding default autovacuum thresholds, worker saturation by large relations, vacuum I/O pressure, autovacuum repeatedly canceled by conflicting DDL, and emergency anti-wraparound maintenance after prolonged neglect.

## Troubleshooting Workflow

1. Identify tables with high dead-tuple counts and old maintenance timestamps.
2. Check oldest transactions/snapshots.
3. Check autovacuum workers and progress.
4. Inspect per-table autovacuum settings.
5. Check relation transaction age and wraparound risk.
6. Correlate vacuum I/O with storage headroom.
7. Tune thresholds/cost behavior for table churn where justified.
8. Verify maintenance catches up after remediation.

## Production Case Study — Large High-Churn Table

A very large table receives continuous updates. Default percentage-based thresholds allow too many changed tuples to accumulate before autovacuum starts, and workers take a long time to catch up. Dead tuples and index size grow while query I/O increases. The correct response is table-specific autovacuum tuning, transaction-horizon cleanup, and capacity validation—not disabling autovacuum.

## SRE/DBRE Principle

> Autovacuum is part of PostgreSQL's correctness and availability architecture. Treat it as a production workload with capacity, latency, and observability requirements.
