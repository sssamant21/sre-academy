# 1.18 — PostgreSQL Replication Architecture and WAL Streaming Internals

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

Physical streaming replication transfers WAL from a primary to standby systems that replay the WAL to maintain a physical copy of the database cluster. SRE/DBRE teams must understand sender/receiver processes, WAL positions, slots, lag, retention, synchronous replication, and recovery behavior.

## Physical Replication Flow

```text
Primary workload
  -> WAL generation
  -> WAL sender
  -> network
  -> WAL receiver on standby
  -> WAL storage/replay
  -> standby data state advances
```

Physical replication operates on WAL records and maintains a physical database-cluster copy rather than replicating selected logical table changes.

## WAL Sender and Receiver

The primary uses WAL sender processes for streaming replication connections. A standby uses a WAL receiver to receive WAL and the recovery/startup machinery to replay it.

Replication connections require appropriate server configuration and authentication.

## Replication Lag

Lag is not one number. Distinguish:

- WAL generated but not sent
- sent but not received
- received but not flushed
- flushed but not replayed
- replay timestamp delay

The bottleneck may be primary WAL generation, network, standby storage, or replay capacity.

## Replication Slots

Physical replication slots protect WAL required by a consumer from being removed prematurely. This improves continuity but creates a storage-retention dependency on the primary.

Monitor slot activity and retained WAL continuously.

## Synchronous Replication

Synchronous replication can make transaction commit wait for configured standby acknowledgement. It can reduce data-loss exposure for failover designs but couples primary commit latency/availability to synchronous-standby health according to configuration.

Design synchronous replication from explicit RPO and failure-mode requirements.

## Hot Standby

A standby can serve read-only queries when hot standby is enabled. Recovery can conflict with long-running standby queries because WAL replay must apply primary changes. Understand recovery-conflict behavior before using standbys for long analytical workloads.

## Monitoring

On the primary, monitor `pg_stat_replication` and replication slots. On the standby, monitor WAL receiver state and replay positions. Correlate with network, storage, CPU, WAL rate, and application read workload.

## Alerting

Alert separately for disconnected replication, increasing send/flush/replay lag, inactive slots retaining WAL, standby replay stalled, synchronous standby loss, and projected WAL-storage exhaustion.

## Failure Scenarios

Common patterns include network partition, standby disk saturation, replay unable to match primary WAL generation, abandoned slot retention, long standby queries conflicting with recovery, and synchronous-standby failure increasing commit latency.

## Troubleshooting Workflow

1. Confirm primary/standby role and timeline.
2. Inspect sender/receiver state.
3. Compare WAL positions to locate the lag stage.
4. Check network and standby storage latency.
5. Inspect replication slots and WAL retention.
6. Check recovery conflicts and long standby queries.
7. Verify synchronous-replication state where configured.
8. Protect recovery requirements before reinitializing a standby.

## Production Case Study — Replay Lag

A standby remains connected but replay lag grows. Network throughput is normal and WAL is received promptly. Standby storage latency is elevated, so received WAL cannot be replayed quickly enough. The correct fix is to address standby I/O/replay capacity rather than changing primary query plans or network settings.

## SRE/DBRE Principle

> Replication health is a pipeline. Measure generation, send, receive, flush, replay, and retention separately before declaring “replication lag.”
