# 1.18 — PostgreSQL Replication Architecture and WAL Streaming Internals

**Status:** Technical Review ✓  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL physical streaming replication transfers WAL from a primary or upstream standby to downstream standby systems, where WAL is persisted and replayed to maintain a physical copy of the database cluster. Production SRE/DBRE operation requires understanding WAL sender/receiver processes, startup/replay behavior, LSN positions, replication slots, retention, cascading replication, synchronous replication, hot-standby conflicts, timelines, and failure recovery.

## Physical Replication Flow

```text
Primary workload
  -> WAL generation / WAL flush
  -> WAL sender (walsender)
  -> streaming replication protocol
  -> network
  -> WAL receiver (walreceiver) on standby
  -> WAL written/flushed on standby
  -> startup process replays WAL
  -> standby data state advances
```

Physical replication operates on WAL records and reproduces the physical database-cluster state. It is distinct from logical replication, which decodes and transfers logical changes for selected replicated objects.

## Standby Recovery Architecture

A server enters standby mode when `standby.signal` exists at startup. The standby remains in continuous recovery and can obtain WAL from three sources:

1. an archive through `restore_command`;
2. WAL already present in `pg_wal`;
3. streaming replication from an upstream server configured through `primary_conninfo`.

The standby repeatedly attempts available recovery sources as necessary. Promotion ends standby mode and establishes a new primary timeline.

For HA designs, `recovery_target_timeline = 'latest'` is normally required so a standby can follow timeline changes after failover; `latest` is the default.

## WAL Sender and WAL Receiver

A WAL sender is a special backend process on a sending server. Each active physical streaming connection normally consumes a WAL sender slot controlled by `max_wal_senders`.

A WAL receiver is an auxiliary process on a standby. It connects to the upstream server, receives WAL, and reports receive/write/flush progress. The startup process is responsible for replaying WAL into the standby database state.

This distinction matters operationally:

```text
WAL received quickly + replay slow
  != network replication problem
  -> investigate replay / standby I/O / recovery conflicts
```

Replication connections require a role with `REPLICATION` privilege (or appropriate superuser privileges), suitable `pg_hba.conf` rules using the replication connection type, and sufficient sender capacity.

## Core Sending-Side Configuration

Important settings include:

- `wal_level = replica` or higher for physical replication;
- `max_wal_senders` — concurrent WAL sender/base-backup streaming capacity;
- `max_replication_slots` — available replication-slot capacity;
- `wal_keep_size` — minimum past WAL retained for standby catch-up;
- `max_slot_wal_keep_size` — optional limit on WAL retained by replication slots;
- `wal_sender_timeout` — sender-side inactivity timeout.

Capacity should include operational headroom for reconnects, base backups, cascading designs, and administrative activity rather than sizing exactly to the normal number of replicas.

A standby intended to be promoted must be configured with compatible sending capacity because after promotion it may need to serve existing downstream replicas.

## Streaming Replication Protocol

Streaming replication sends WAL records incrementally without waiting for an entire WAL segment to fill. The standby initiates a replication connection and the sending server enters physical replication WAL-sender mode.

Streaming replication is asynchronous by default. Consequently, a transaction acknowledged on the primary can be lost after catastrophic primary failure if its WAL has not reached the failover target.

## Replication Lag Is a Pipeline

Do not reduce replication health to a single time value. Distinguish the following stages:

```text
Primary WAL generated
      |
      v
sent_lsn
      |
      v
write_lsn       WAL received/written on standby
      |
      v
flush_lsn       WAL durably flushed on standby
      |
      v
replay_lsn      WAL applied by standby startup process
```

On the primary, `pg_stat_replication` exposes sender state and LSN progress including `sent_lsn`, `write_lsn`, `flush_lsn`, and `replay_lsn`, plus lag estimates where available.

Lag can therefore originate from different failure domains:

| Lag stage | Likely investigation area |
|---|---|
| generation → send | sender scheduling, network, sender capacity |
| send → write | network or standby receive/write path |
| write → flush | standby storage/fsync latency |
| flush → replay | recovery replay capacity, standby CPU/I/O, conflicts |
| replay timestamp delay | workload/WAL rate plus all downstream stages |

Time-based lag columns are estimates of recent synchronization delay and must not be treated as guaranteed data-loss measurements.

## Standby-Side Observability

Use standby-side functions and views to determine whether WAL is being received and replayed:

```sql
SELECT pg_is_in_recovery();
SELECT pg_last_wal_receive_lsn();
SELECT pg_last_wal_replay_lsn();
SELECT pg_last_xact_replay_timestamp();
SELECT * FROM pg_stat_wal_receiver;
```

Interpret them together with storage latency, CPU, wait events, recovery conflicts, and WAL generation rate.

## Replication Slots and WAL Retention

A physical replication slot prevents required WAL from being removed while the consumer still needs it. This improves continuity but creates a potentially serious primary-storage dependency.

Monitor `pg_replication_slots`, especially:

- `active` / `active_pid`;
- `restart_lsn`;
- `wal_status`;
- `safe_wal_size` when available;
- retained WAL distance from the current WAL position.

`wal_status` can progress through states such as `reserved`, `extended`, `unreserved`, and `lost`. A slot in `lost` state is no longer usable.

Never assume an inactive slot is harmless. An abandoned slot can retain WAL until `pg_wal` capacity becomes a production incident.

Where appropriate, use `max_slot_wal_keep_size` as a containment control, while recognizing that exceeding the limit can invalidate a lagging slot and force recovery/reinitialization work.

## `wal_keep_size` Versus Replication Slots

These mechanisms solve related but different problems:

- `wal_keep_size` establishes a minimum amount of old WAL retained for streaming standbys;
- a replication slot tracks a specific consumer's required WAL position;
- a WAL archive provides another recovery source when sufficiently retained.

If a standby falls behind beyond available WAL and no usable archive can supply the missing records, the standby must be reinitialized from a new base backup.

## Cascading Replication

A standby can act as an upstream server and stream WAL to downstream standbys. Cascading replication can reduce direct connection and network load on the primary.

```text
Primary
  -> Standby A
       -> Standby B
       -> Standby C
```

Cascading replication is asynchronous. Each additional hop adds another failure domain and potentially additional lag. SRE monitoring should identify the complete upstream/downstream topology rather than treating every replica as directly attached to the primary.

## Synchronous Replication

Streaming replication is asynchronous unless synchronous replication is explicitly configured.

With synchronous replication, transaction completion can wait for configured standby acknowledgements. The exact guarantee depends on `synchronous_commit` and synchronous-standby selection.

Relevant `synchronous_commit` modes include:

- `remote_apply` — wait until the synchronous standby has replayed the transaction;
- `on` — wait for required remote WAL flush acknowledgement;
- `remote_write` — wait until the remote operating system has accepted the WAL write;
- `local` — wait only for local WAL flush;
- `off` — asynchronous local commit behavior.

Synchronous replication can reduce RPO exposure, but it deliberately couples commit latency and potentially write availability to the health and latency of synchronous standby candidates.

Design it from explicit RPO/RTO requirements rather than enabling it as a generic HA checkbox.

## Hot Standby and Recovery Conflicts

With hot standby enabled, read-only queries can execute while WAL replay continues. However, standby queries can conflict with recovery operations required to reproduce primary changes.

Monitor recovery conflicts and understand the trade-off among:

- query duration on replicas;
- replay freshness;
- `max_standby_streaming_delay` / archive delay behavior;
- `hot_standby_feedback`;
- primary-side dead-tuple retention and bloat.

`hot_standby_feedback` can reduce query cancellations on a standby but can increase table bloat on the primary by preserving row versions needed by standby snapshots. It is therefore a cross-node storage/concurrency trade-off, not a free reliability setting.

## Timelines and Promotion

Promotion creates a new timeline. Timeline awareness is essential during failover, rewind, recovery, and reattachment of replicas.

Before attaching an old primary or divergent standby to a new primary, verify timeline/history compatibility. Never simply restart a former primary as though it were still a valid replica after another node has accepted writes.

Depending on divergence and retained WAL, recovery may require `pg_rewind` or a fresh base backup.

## Base Backup and Standby Bootstrap

A standby requires a physically consistent starting copy, commonly produced with `pg_basebackup` or another supported physical-backup method, plus all WAL needed to reach a consistent recovery point.

A base backup alone is not an HA strategy. Validate:

- backup consistency;
- required WAL availability;
- restore procedure;
- replication credentials;
- slot behavior;
- timeline behavior;
- actual promotion and application reconnection.

## Production Monitoring

### Primary

```sql
SELECT
    pid,
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication;
```

### Replication slots

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots;
```

### Standby

```sql
SELECT
    pg_is_in_recovery(),
    pg_last_wal_receive_lsn(),
    pg_last_wal_replay_lsn(),
    pg_last_xact_replay_timestamp();
```

Use these with `pg_stat_wal_receiver`, `pg_stat_database_conflicts`, WAL-rate telemetry, network metrics, filesystem capacity, storage latency/IOPS/throughput, CPU, and application read latency.

## Lag Measurement Guardrails

LSN distance is often more useful than a single time-lag metric when diagnosing a growing backlog.

Example primary-side byte distance:

```sql
SELECT
    application_name,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication;
```

Treat this as a backlog quantity, not an RPO guarantee. Actual failover data-loss exposure depends on what WAL reached the failover target and on the durability/acknowledgement policy.

## Alerting Model

Alert independently for:

- expected standby disconnected;
- sender/receiver not streaming;
- WAL backlog growing persistently;
- replay not advancing;
- synchronous standby unavailable;
- replication slot inactive unexpectedly;
- slot-retained WAL growth;
- `wal_status` approaching unsafe/lost state;
- projected `pg_wal` filesystem exhaustion;
- standby storage saturation;
- excessive recovery conflicts;
- timeline/topology mismatch after failover.

Prefer rate and time-to-exhaustion alerts over fixed lag thresholds alone.

## Failure Scenarios

### Network partition

The standby disconnects while the primary continues generating WAL. Recovery depends on retained WAL through slots, `wal_keep_size`, or archive availability.

### Standby disk saturation

WAL can arrive slowly or flush/replay can fall behind. Diagnose receive, flush, and replay positions separately.

### Replay cannot match WAL generation

The standby remains connected but backlog grows continuously. Investigate standby CPU, I/O, recovery conflicts, and workload characteristics.

### Abandoned replication slot

The consumer disappears but its slot continues retaining WAL. `pg_wal` grows until capacity pressure develops unless bounded or remediated.

### Missing WAL

A lagging standby requests WAL already recycled and unavailable from archive. Reinitialization is required.

### Synchronous standby failure

Primary commits may wait because required synchronous acknowledgement cannot be obtained. Validate synchronous candidate design and failure policy before production deployment.

### Long-running hot-standby query

Replay conflicts with a query snapshot. Depending on configuration, replay is delayed or the standby query is canceled. `hot_standby_feedback` can shift the cost to primary bloat.

## Troubleshooting Workflow

1. Confirm which node is primary and which nodes are in recovery.
2. Confirm current timeline and recent promotion history.
3. Inspect `pg_stat_replication` on the sending server.
4. Inspect `pg_stat_wal_receiver` on the standby.
5. Compare send/write/flush/replay LSN positions.
6. Calculate WAL backlog in bytes and its growth rate.
7. Check network latency/loss and standby storage latency.
8. Inspect replication slots and retained WAL.
9. Check `pg_wal` capacity and projected exhaustion time.
10. Inspect recovery conflicts and long-running standby queries.
11. Verify synchronous replication state and `sync_state` where configured.
12. Verify archive availability if streaming WAL is missing.
13. Protect recovery evidence and required WAL before dropping slots or rebuilding a standby.
14. Reinitialize only after determining why the standby could not recover normally.

## Production Case Study — Connected Replica with Growing Replay Lag

A standby remains in `streaming` state and the WAL receiver is current, but `replay_lsn` falls progressively behind `flush_lsn`. Network throughput is healthy and received WAL is flushed promptly. Storage latency and recovery work on the standby are elevated.

The key observation is:

```text
receive healthy
flush healthy
replay unhealthy
```

The correct remediation is therefore on the standby replay path—storage capacity, CPU, recovery conflicts, or workload pressure—not on the primary network path.

## SRE/DBRE Production Guardrails

- Monitor replication as a multi-stage WAL pipeline.
- Monitor slot retention as a primary-storage risk.
- Maintain WAL/archive capacity sufficient for realistic outage duration.
- Keep sender/slot capacity above normal topology requirements.
- Test promotion, application reconnection, and replica reattachment.
- Understand timeline divergence before reusing a former primary.
- Never delete WAL manually to resolve replication-driven disk pressure.
- Never drop a replication slot during an incident until its consumer and recovery consequences are understood.
- Treat synchronous replication as a durability/latency/availability design decision.
- Treat replica read workloads and replay freshness as competing resources when recovery conflicts occur.

## SRE/DBRE Principle

> Replication health is a pipeline, not a single lag number. Measure WAL generation, send, receive, flush, replay, retention, storage capacity, and timeline state independently before deciding where the failure actually exists.
