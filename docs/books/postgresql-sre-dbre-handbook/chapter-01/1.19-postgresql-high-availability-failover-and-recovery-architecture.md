# 1.19 — PostgreSQL High Availability, Failover, and Recovery Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL provides replication, standby recovery, promotion, backup, WAL archiving, and point-in-time recovery primitives. A complete HA system additionally requires failure detection, safe leader selection, fencing, client routing, recovery procedures, and tested RPO/RTO objectives.

## HA Architecture

```text
Applications
   -> routing / endpoint layer
      -> primary
          -> WAL -> standby A
          -> WAL -> standby B

HA control plane
   -> health detection
   -> promotion decision
   -> fencing
   -> routing update
   -> failed-node rejoin
```

Core PostgreSQL does not by itself provide every distributed-system control needed for automatic failover orchestration.

## Failure Detection

Do not equate a failed health check with proof that the primary is permanently unavailable. Network partitions can isolate a healthy primary from an HA manager. Unsafe promotion without fencing can create split-brain conditions.

## Promotion

A standby can be promoted to leave recovery and become writable. Promotion changes the replication topology and timeline. Clients must be redirected safely and remaining standbys may require reconfiguration/rejoin handling.

## RPO and RTO

RPO defines acceptable data-loss exposure; RTO defines acceptable restoration time. Asynchronous replication can leave recent WAL not yet present/replayed on the promoted standby. Synchronous replication can reduce this exposure but introduces latency and availability tradeoffs.

## Crash Recovery vs Failover vs PITR

These are different operations:

- crash recovery: restart the same database cluster and replay local WAL
- failover: promote another server/instance to primary role
- PITR: restore a base backup and replay archived WAL to a selected recovery target

Runbooks must not use these terms interchangeably.

## Fencing

Before accepting writes on a replacement primary, HA automation must ensure the old primary cannot independently continue serving writes or be reachable through stale routing. The exact fencing mechanism depends on infrastructure and HA tooling.

## Client Routing

HA is incomplete unless applications can reach the new primary. Routing can involve VIPs, proxies, DNS, service discovery, cloud endpoints, or HA tooling. Connection pools must detect broken connections and reconnect to the correct writer.

## Recovery and Rejoin

After failover, the old primary cannot simply be assumed safe to restart as a standby. Validate timeline/state and use supported rejoin/rebuild mechanisms such as `pg_rewind` where prerequisites are satisfied, or restore/reinitialize as required.

## Monitoring

Monitor role, replication state, lag, timeline changes, WAL/archive health, endpoint routing, synchronous standby state, backup freshness, restore-test status, and HA-manager quorum/health where external tooling is used.

## Alerting

Alert on loss of redundancy before total outage, disconnected standbys, RPO breach, synchronous-standby loss, archive failure, failed backup, routing inconsistency, repeated failover, and inability to rejoin nodes.

## Failure Scenarios

Critical scenarios include primary process failure, host/storage failure, network partition, availability-zone loss, standby lag beyond RPO, split-brain risk, failed promotion, stale routing, and failed-node rejoin.

## Failover Runbook Model

1. Confirm the failure domain and avoid duplicate promotion.
2. Determine primary reachability and fence if required.
3. Select the best eligible standby using recovery/RPO state.
4. Promote using supported mechanisms.
5. Update/verify routing.
6. Validate writes, reads, WAL, and application health.
7. Reconfigure remaining replicas.
8. Preserve evidence and reconcile the old primary safely.
9. Measure actual RPO/RTO and complete RCA.

## Production Case Study — Network Partition

An HA manager loses network connectivity to the primary while the application network can still reach it. Blind promotion of a standby would create two writable primaries. Correct HA design requires quorum/fencing semantics that prevent promotion until the old writer is safely excluded.

## SRE/DBRE Principle

> Replication is not HA by itself. HA requires safe failure detection, fencing, promotion, routing, recovery, and regular failover testing.
