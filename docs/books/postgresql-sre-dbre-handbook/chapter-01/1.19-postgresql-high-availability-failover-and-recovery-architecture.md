# 1.19 — PostgreSQL High Availability, Failover, and Recovery Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL provides the database primitives required to build highly available systems: WAL, physical and logical replication, standby recovery, synchronous replication, promotion, continuous archiving, base backups, point-in-time recovery, timelines, and `pg_rewind`. Production HA additionally requires failure detection, safe promotion policy, fencing, client routing, topology reconciliation, and regularly tested RPO/RTO objectives.

Replication alone is not HA. The operational control plane around PostgreSQL determines whether a failure becomes a controlled failover or a split-brain/data-loss incident.

## HA Architecture

```text
                         +----------------------+
                         | HA control plane     |
                         | health / quorum      |
                         | fencing / promotion  |
                         +----------+-----------+
                                    |
Applications -> writer endpoint -> PRIMARY
                                  |     |
                                  |     +--> WAL archive / backups
                                  |
                                  +--> STANDBY A
                                  |      receive -> flush -> replay
                                  |
                                  +--> STANDBY B
                                         receive -> flush -> replay

After failover:
old primary -> fenced -> rewind/rebuild -> new standby
clients     -> writer endpoint -> promoted primary
```

Core PostgreSQL deliberately does not provide a complete automatic failover manager. Failure detection, leader election/quorum, fencing, routing, and orchestration are normally supplied by infrastructure or HA software.

## Availability Is a System Property

A production PostgreSQL HA design should treat the following as separate failure domains:

- PostgreSQL process
- host or VM
- storage
- network path
- availability zone / data center
- DNS, VIP, proxy, or service-discovery layer
- HA control plane
- backup/WAL archive
- application connection pools

A healthy standby is useful only if it is sufficiently current, promotable, reachable, correctly configured, and applications can be redirected to it.

## Failure Detection and Promotion Safety

A failed health check is evidence of lost reachability, not proof that the primary is dead. Network partitions can isolate a healthy writer from the HA manager while applications or another network segment can still reach it.

Before promotion, automation should answer:

1. Is the current primary truly unavailable or merely unreachable from one observer?
2. Can the old primary still accept writes?
3. Has fencing succeeded?
4. Which standby has the best eligible recovery position?
5. Does promotion satisfy the defined RPO?
6. Can the writer endpoint be moved safely?

Unsafe promotion can produce two writable PostgreSQL clusters with divergent timelines. PostgreSQL documentation explicitly calls out the need for a mechanism such as STONITH/fencing to prevent the old primary from returning as another writer after failover.

## Standby Eligibility

Do not select a failover target only because its PostgreSQL process is running. Validate at least:

- server is actually in recovery before promotion
- WAL receiver/recovery state
- receive, flush, and replay positions
- replay delay and whether lag is growing
- required WAL availability
- storage and filesystem health
- timeline ancestry
- configuration parity
- synchronous-replication role where applicable
- application/network reachability

Useful checks include:

```sql
SELECT pg_is_in_recovery();
SELECT pg_last_wal_receive_lsn();
SELECT pg_last_wal_replay_lsn();
SELECT pg_last_xact_replay_timestamp();
```

Lag should be measured in WAL bytes/positions as well as elapsed time. Timestamp lag alone can be misleading when the primary is idle.

## Promotion

A physical standby can be promoted with supported mechanisms such as:

```bash
pg_ctl promote -D "$PGDATA"
```

or:

```sql
SELECT pg_promote();
```

Promotion ends standby recovery and allows the server to become writable. A new timeline is created as recovery completes, preserving the history of the WAL branch.

Promotion is only one step in failover. The complete operation also requires fencing, routing, validation, replica reconciliation, and restoration of redundancy.

## Timelines

PostgreSQL timelines prevent WAL generated after one recovery/failover branch from overwriting the history of another branch. Timeline history is therefore central to safe failover, PITR, and rejoining a former primary.

For HA standbys, `recovery_target_timeline = 'latest'` is normally appropriate and is the default, allowing a standby to follow timeline changes created when another standby is promoted.

Never treat two clusters that have accepted writes on different timelines as interchangeable copies.

## RPO and RTO

**Recovery Point Objective (RPO)** defines the acceptable amount of committed data that may be lost.

**Recovery Time Objective (RTO)** defines how long service can remain unavailable before recovery/failover must restore acceptable operation.

Asynchronous physical replication normally provides excellent performance but can leave committed WAL that has not reached the standby when the primary is catastrophically lost.

Synchronous replication can reduce the acknowledged-transaction loss window, but its guarantee depends on `synchronous_commit`, `synchronous_standby_names`, standby health, and the acknowledgement stage selected. It also introduces commit-latency and availability coupling.

RPO and RTO must therefore be measured during controlled failover tests, not inferred from architecture diagrams.

## Synchronous HA Tradeoffs

With synchronous replication, commits can wait for acknowledgements from configured synchronous standbys. PostgreSQL supports priority-based and quorum-based synchronous standby selection.

A synchronous standby is not eligible to act synchronously until it has reached the `streaming` state. Loss of the required synchronous acknowledgements can stall commits depending on configuration.

Monitor:

```sql
SELECT application_name,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn
FROM pg_stat_replication;
```

The HA policy must explicitly define whether preserving write availability or preserving a stronger RPO takes precedence during degraded synchronous-replication conditions.

## Crash Recovery vs Failover vs Switchover vs PITR

These operations solve different problems.

### Crash recovery

Restart the same PostgreSQL cluster after an unclean shutdown and replay local WAL until the database reaches a consistent state.

### Failover

Promote a standby because the existing primary is unavailable or unsafe to continue using.

### Switchover

Intentionally transfer the primary role during a controlled maintenance event. A switchover should normally minimize or eliminate data loss by confirming the target is caught up and controlling writes before role transition.

### Point-in-Time Recovery

Restore a base backup and replay archived WAL to a selected recovery target after logical corruption, accidental deletion, or another recovery event.

A replica is not a substitute for PITR: destructive SQL can replicate perfectly to every standby.

## Standby Recovery Sources

A standby can obtain WAL from multiple sources. PostgreSQL recovery can use archived WAL, WAL already present in `pg_wal`, and streaming replication from the primary.

A server enters standby mode when `standby.signal` exists at startup. PostgreSQL 12 and later no longer use `recovery.conf`; recovery parameters are normal server configuration parameters.

For HA systems using an archive, ensure the archive remains valid after promotion and that the new primary is able to archive WAL correctly.

## Hot Standby and Recovery Conflicts

A hot standby can serve read-only queries after it reaches a consistent recovery state. Those queries can conflict with WAL replay when the primary removes or changes data needed by standby snapshots.

HA monitoring should therefore distinguish:

- receive lag
- flush lag
- replay lag
- replay blocked/delayed by recovery conflicts
- deliberate `recovery_min_apply_delay`

Standby read scalability must never silently compromise the failover RPO/RTO objective.

## Fencing and Split-Brain Prevention

Fencing is the process of ensuring the former primary cannot continue accepting writes before another server is established as authoritative.

Possible implementations include infrastructure power fencing, storage fencing, network/security controls, orchestrator-level node isolation, or another strongly authoritative mechanism.

The exact implementation is environment-specific, but the invariant is universal:

> At most one authoritative PostgreSQL writer should be able to serve production writes.

Do not rely only on DNS changes as fencing. DNS changes redirect clients but do not necessarily prevent the old primary from accepting writes through stale connections, cached records, or alternate network paths.

## Client Routing and Connection Pools

Database failover is not complete until applications are connected to the correct writer.

Routing may use:

- virtual IPs
- TCP proxies
- service discovery
- DNS
- Kubernetes Services
- cloud database endpoints
- HA-manager-managed endpoints

Connection pools must discard broken or stale writer connections and establish new sessions against the promoted primary. Applications should use bounded retries with backoff and jitter rather than uncontrolled retry storms.

After failover, validate that no production client continues sending writes to the old node.

## Rejoining the Former Primary

After promotion, the former primary may have diverged from the new primary. Do not simply restart it as a standby.

Two supported recovery patterns are common:

1. rebuild the former primary from a fresh base backup; or
2. use `pg_rewind` when its prerequisites and WAL history are satisfied.

`pg_rewind` determines the divergence point using timeline history and copies the blocks/files required to make the target consistent with the source. It requires the target to have data checksums enabled or `wal_log_hints=on`; `full_page_writes` must also be enabled.

Example pattern:

```bash
pg_rewind \
  --target-pgdata="$PGDATA" \
  --source-server="host=new-primary dbname=postgres user=rewind_user" \
  --write-recovery-conf
```

The target must then complete WAL replay before it is considered a healthy standby.

If `pg_rewind` fails during processing, treat the target data directory as unsafe and rebuild it rather than improvising filesystem repair.

## Restoring Redundancy

Failover commonly leaves the system in a degraded state: one former standby is now primary and the failed/old primary is unavailable.

Recovery is not complete until redundancy is restored.

After promotion:

1. verify the new primary
2. reconnect/reconfigure surviving standbys
3. rewind or rebuild the old primary
4. validate WAL streaming and archive health
5. validate synchronous topology if used
6. verify backups from the new primary
7. verify client routing
8. return HA monitoring to normal state

## Backup and PITR Architecture

HA protects availability. Backups and WAL archives protect recoverability.

Production systems should continuously verify:

- successful base backups
- WAL archive continuity
- backup retention
- recovery credentials and encryption keys
- restore tooling
- actual restore tests
- measured restore RTO

A successful backup job is not equivalent to a successful recovery capability.

## Monitoring

A production HA dashboard should include:

### Role and topology

```sql
SELECT pg_is_in_recovery();
```

Primary-side replication:

```sql
SELECT application_name,
       client_addr,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn
FROM pg_stat_replication;
```

Standby-side receiver state:

```sql
SELECT status,
       sender_host,
       sender_port,
       written_lsn,
       flushed_lsn,
       latest_end_lsn,
       latest_end_time
FROM pg_stat_wal_receiver;
```

Also monitor:

- WAL generation rate
- archive success/failure
- replication-slot retention
- timeline changes
- recovery conflicts
- standby storage/CPU/network
- synchronous standby availability
- HA-manager/quorum health
- endpoint ownership
- backup age and restore-test age

## Alerting Strategy

Alert on conditions that threaten availability or recoverability rather than only process uptime.

High-priority conditions include:

- no eligible failover standby
- replication disconnected beyond tolerance
- replay/flush lag exceeds RPO
- WAL retention threatens `pg_wal` capacity
- required synchronous standby unavailable
- repeated promotions/failovers
- archive failure
- backup or restore-test failure
- HA control-plane quorum loss
- fencing failure
- writer endpoint disagrees with authoritative primary
- former primary becomes reachable without approved rejoin

Alert thresholds should derive from explicit RPO/RTO and storage-exhaustion budgets.

## Failure Scenarios

### Primary process failure

The host remains healthy but PostgreSQL stops. Determine whether restart/crash recovery is faster and safer than failover according to the HA policy.

### Host or storage failure

Promote an eligible standby only after ensuring the old writer cannot return unexpectedly.

### Network partition

The most dangerous case for naive automation. Loss of connectivity between HA components does not prove loss of the primary. Quorum and fencing must prevent dual-writer operation.

### Availability-zone failure

Ensure standby placement, routing, quorum, and dependent services do not share the same failure domain.

### Standby behind RPO

Promotion may restore service quickly while violating the business data-loss objective. The incident commander must understand that tradeoff before promotion.

### Synchronous standby failure

Commit latency can increase or commits can wait indefinitely for the required acknowledgement depending on topology and configuration. Do not disable synchronous guarantees reflexively without understanding the RPO consequence.

### Failed promotion

Do not issue repeated promotion actions blindly. Establish actual node role and timeline before another attempt.

### Stale routing

The database role changes correctly but applications continue using the former endpoint or stale pooled connections.

### Split brain

Two nodes accept writes on divergent timelines. Stop writes, establish the authoritative history, preserve evidence, and rebuild/rewind the non-authoritative node. Do not attempt to merge physical timelines manually.

## Failover Runbook

1. Declare the incident and freeze conflicting automation if necessary.
2. Confirm the failure domain and authoritative topology.
3. Check whether the old primary can still accept writes.
4. Fence the old primary using the approved mechanism.
5. Evaluate standby receive/flush/replay positions and RPO.
6. Select exactly one eligible promotion target.
7. Promote using `pg_ctl promote` or `pg_promote()` through the HA system.
8. Verify the promoted server is no longer in recovery.
9. Verify timeline transition and WAL generation.
10. Move/validate the writer endpoint.
11. Validate application writes and critical reads.
12. Validate WAL archiving and backups on the new primary.
13. Reconnect/reconfigure surviving replicas.
14. Rewind or rebuild the former primary.
15. Restore the required redundancy level.
16. Measure actual RPO and RTO.
17. Preserve logs/timeline/LSN evidence and complete RCA.

## Switchover Runbook

For planned maintenance:

1. verify target standby health
2. verify target is caught up
3. stop or tightly control application writes
4. wait for required WAL to flush/replay
5. prevent new writes on the old primary
6. promote the target
7. move writer routing
8. validate applications
9. rewind/reconfigure the former primary as standby
10. restore redundancy and resume normal operations

A planned switchover is one of the best ways to test the failover mechanism before an emergency.

## Automation Guardrails

HA automation should enforce invariants rather than merely execute commands.

Recommended controls include:

- one authoritative promotion decision
- quorum where architecture requires it
- fencing before writer activation
- RPO-aware candidate selection
- bounded promotion retries
- explicit endpoint ownership
- automatic post-promotion validation
- rejoin safety checks
- audit logging of node roles, timelines, and LSNs
- regular automated failover exercises in representative environments

Never automate `pg_rewind`, destructive rebuilds, or former-primary startup without verifying node identity and direction of synchronization.

## Production Case Study — Network Partition

An HA manager loses connectivity to the primary while application servers can still reach it. A naive controller interprets the failed health check as primary death and promotes a standby. Both nodes then accept writes, creating divergent timelines and a severe recovery problem.

The durable correction is architectural: authoritative quorum/fencing, promotion preconditions, explicit writer ownership, and validation that the old primary cannot serve production writes before the new primary is exposed.

## Production Case Study — Failover Succeeds but Service Remains Down

A standby is promoted successfully and begins generating WAL, but application connection pools continue using the failed primary address. Database-level RTO is seconds while application-level RTO is several minutes.

The remediation is to include routing and connection-pool convergence in the HA SLO and failover test. Promotion time alone is not the service RTO.

## Production Review Checklist

Before this architecture is considered production-ready, verify:

- RPO and RTO are documented and tested
- at least one eligible standby exists
- failure domains are intentionally separated
- fencing is implemented and tested
- promotion is deterministic
- routing follows the authoritative writer
- standby configuration supports promotion
- WAL archive continues across failover
- backup/restore is tested independently of replication
- former-primary rejoin is documented
- `pg_rewind` prerequisites are known
- split-brain procedure exists
- failover and switchover exercises are scheduled
- monitoring measures loss of redundancy before total outage

## SRE/DBRE Principle

> Replication is a data-movement primitive. High availability is the engineered system that safely detects failure, prevents dual writers, promotes the correct copy, redirects clients, restores redundancy, and proves recovery through testing.
