# Chapter 1 — PostgreSQL Architecture and Internals

## 1.2 — PostgreSQL Server Process Architecture

> **Reconstruction note:** The original locked 1.2 title could not be recovered. The locked section position is preserved; this working title remains subject to final title confirmation during the chapter-wide production review.

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.2.1 Purpose

PostgreSQL uses a process-based client/server architecture. The server program is `postgres`; one supervising server process accepts connection requests and manages the server lifecycle, while normal client sessions are serviced by separate backend processes. PostgreSQL also runs auxiliary processes and background workers that cooperate through shared memory, synchronization primitives, WAL, and storage.

```text
Clients
   |
   v
Supervising postgres process (historically: postmaster)
   |
   +-- Backend process A <-> Client A
   +-- Backend process B <-> Client B
   +-- Backend process C <-> Client C
   |
   +-- Auxiliary processes
   +-- Background workers
   |
   v
Shared Memory / IPC / WAL / Storage
```

For SRE/DBRE work, this process model directly connects connection capacity to operating-system processes, memory, file descriptors, worker capacity, shared resources, and failure behavior.

## 1.2.2 PostgreSQL Instance Process Model

A running PostgreSQL server instance manages one PostgreSQL database cluster (one data directory). Multiple independent PostgreSQL instances can run on one host when their data directories and communication endpoints do not conflict.

```text
Host / VM
   |
   +-- postgres instance A -> PGDATA A -> port/socket A
   +-- postgres instance B -> PGDATA B -> port/socket B
```

Do not confuse a PostgreSQL *database cluster* (the databases managed by one server instance) with an HA cluster composed of multiple PostgreSQL nodes.

## 1.2.3 Supervising Server Process

PostgreSQL documentation calls the database server program `postgres`; the historical term `postmaster` is still widely used for the supervising server process. The supervisor initializes server resources, listens on configured TCP/IP and/or Unix-domain sockets, accepts connection requests, starts the process that services each normal connection, launches required auxiliary processes, and coordinates shutdown and crash recovery behavior.

```text
postgres supervisor
   |
   +-- initialize shared resources
   +-- open listening sockets
   +-- accept connection requests
   +-- establish client backends
   +-- launch/supervise auxiliary processes
   +-- coordinate shutdown/crash handling
```

## 1.2.4 Process per Client Connection

PostgreSQL normally uses one server backend process per established client connection. After connection establishment, the client communicates with its backend process without the supervising process mediating normal SQL traffic.

```text
Application A <------> Backend PID 101
Application B <------> Backend PID 102
DBA Session   <------> Backend PID 103
```

This is a critical capacity property. Connection count contributes to process count, private memory demand, file-descriptor usage, scheduling overhead, and shared-resource requirements.

## 1.2.5 Backend Processes

A client backend acts on behalf of one database session. It receives frontend/backend protocol messages, processes SQL, participates in transactions and locking, accesses shared buffers and WAL-related facilities as required, and returns results to the client.

Use `pg_stat_activity` as the primary database-side view of client backend state:

```sql
SELECT
    pid,
    backend_type,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
ORDER BY backend_start;
```

An `active` backend can still be waiting. Always interpret `state` together with `wait_event_type` and `wait_event`.

## 1.2.6 Private Memory, Shared Memory, and IPC

Each PostgreSQL process has private address space while cooperating server processes also use shared memory and synchronization facilities.

```text
Backend A -- private memory --\
Backend B -- private memory ---+--> PostgreSQL shared state
Backend C -- private memory --/       |
                                      +-- shared buffers
                                      +-- WAL buffers
                                      +-- lock/shared control state
                                      +-- process coordination
```

PostgreSQL 18 normally uses a large anonymous `mmap` shared-memory region for its main shared memory on supported Unix-like systems, plus a small amount of System V shared memory. Dynamic shared memory can also be used by features such as parallel query. Platform-specific implementations differ.

## 1.2.7 Semaphores and Kernel Resources

PostgreSQL requires operating-system IPC facilities. The exact implementation is platform dependent. On Linux and FreeBSD, PostgreSQL 18 uses POSIX semaphores rather than System V semaphores for normal semaphore requirements; other supported Unix-derived platforms can use System V semaphores.

When System V semaphores are used, PostgreSQL 18's required count depends on configured capacities including `max_connections`, `autovacuum_worker_slots`, `max_wal_senders`, and `max_worker_processes`. The runtime-computed `num_os_semaphores` value can be inspected before startup when troubleshooting platform limits.

```bash
postgres -D "$PGDATA" -C num_os_semaphores
```

An IPC error containing `No space left on device` can refer to semaphore exhaustion rather than filesystem capacity.

## 1.2.8 Auxiliary Processes

PostgreSQL runs specialized auxiliary processes according to configuration and server state. Examples include the checkpointer, background writer, WAL writer, autovacuum launcher, archiver, startup/recovery process, WAL receiver, WAL sender processes, logging collector when enabled, and WAL summarizer when WAL summarization is enabled.

These are not ordinary client sessions. Their health must be evaluated according to the subsystem they serve. Section 1.8 provides the detailed background-process taxonomy; Sections 1.23 and 1.24 cover archiving and replication processes specifically.

## 1.2.9 Background Workers

PostgreSQL provides a background-worker framework for server functionality and extensions. Worker capacity is shared across features and must be planned globally rather than one feature at a time.

Important capacity settings include `max_worker_processes` and feature-specific limits for parallelism and logical replication.

```text
Global worker capacity
   |
   +-- parallel workers
   +-- logical replication workers
   +-- extension background workers
   +-- other worker-based functionality
```

Worker exhaustion can result in a feature receiving fewer workers than expected without implying that the PostgreSQL server itself is down.

## 1.2.10 Operating-System Process and File Capacity

Because PostgreSQL normally uses a process per client connection, host-level capacity must cover client backends plus auxiliary processes, workers, monitoring/backup processes, and other host workloads.

Production capacity planning should account for:

- `max_connections`
- reserved connection capacity
- `max_worker_processes`
- `max_wal_senders`
- autovacuum worker capacity
- logical-replication and parallel-worker limits
- extension workers
- OS process limits
- open-file limits
- IPC/shared-memory requirements
- private and shared memory
- CPU scheduling capacity

Increasing `max_connections` increases resource requirements and should not be treated as a free way to increase application throughput.

## 1.2.11 Linux Memory-Overcommit Failure Domain

Linux memory overcommit deserves explicit SRE attention. Under severe memory pressure, the kernel OOM killer can terminate a PostgreSQL process. PostgreSQL documentation specifically discusses protecting the supervising server process while allowing child processes to retain normal OOM eligibility.

A process-level memory incident can therefore become a database-wide availability event even when no PostgreSQL memory-allocation error appeared first.

Monitor host memory, swap policy, OOM events, cgroup/container limits where applicable, and PostgreSQL concurrency-driven memory demand together.

## 1.2.12 Connection Explosion Failure Scenario

```text
Application autoscaling
   -> more application instances
   -> aggregate pool capacity multiplies
   -> backend process count rises
   -> memory / scheduling / connection pressure
   -> connection rejection or latency
```

The corrective action is normally to engineer aggregate connection demand: right-size pools, use appropriate pooling architecture, shorten transactions, remove leaks, and preserve administrative headroom. Raising `max_connections` alone can move the failure from connection rejection to memory or CPU exhaustion.

## 1.2.13 Backend Crash and Server Recovery Behavior

An unexpected server-process exit can be treated as a crash because PostgreSQL processes share critical state. The supervising process can terminate remaining server processes and perform recovery before accepting normal work again.

Do not use arbitrary OS-level `kill -9` as a routine session-management tool. Prefer PostgreSQL-supported controls:

```sql
SELECT pg_cancel_backend(<pid>);
SELECT pg_terminate_backend(<pid>);
```

Cancellation requests the current query to stop; termination ends the session. Both require appropriate privileges and production-impact assessment.

## 1.2.14 Process Monitoring Model

Correlate database and OS telemetry by PID:

```text
PostgreSQL PID
   |
   +-- backend_type / session identity
   +-- state and wait event
   +-- query and transaction age
   +-- blocking relationship
   +-- CPU
   +-- memory
   +-- I/O
   +-- file descriptors
   +-- OS process state
```

This distinguishes CPU-bound execution from lock waits, client waits, storage waits, memory pressure, and process-capacity incidents.

## 1.2.15 Long Transactions and Idle-in-Transaction Backends

Process monitoring must include transaction age. A session can be doing little or no CPU work while an old transaction continues to retain locks or an old MVCC horizon.

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

`idle in transaction` is particularly important because the backend is waiting for the client while the transaction remains open. Alert on age and impact rather than treating all idle sessions as equivalent.

## 1.2.16 Process-Level Monitoring and Alerting

Monitor and trend:

- backend count and connection utilization
- connection creation rate
- sessions by application/user/database
- active vs idle vs idle-in-transaction state
- oldest transaction and query age
- wait-event distribution
- abnormal server-process exits
- restart/crash-recovery events
- worker utilization and worker shortages
- WAL sender utilization
- host process and file-descriptor usage
- memory pressure, swap, OOM/cgroup events
- startup IPC/shared-memory errors

Alert thresholds should be workload-specific and should preserve enough context to identify the application or subsystem creating pressure.

## 1.2.17 Failure Scenario — Connection Capacity Exhausted

When normal connection capacity is consumed, new application connections can be rejected while PostgreSQL preserves configured reserved capacity for privileged/administrative access.

Troubleshooting questions:

1. Which applications/users own the connections?
2. How many are active, idle, or idle in transaction?
3. Is aggregate pool configuration larger than database capacity?
4. Did application autoscaling multiply connection demand?
5. Is there a leak or retry storm?
6. Are transactions unnecessarily long?
7. Is a transaction-pooling layer appropriate?

The permanent fix should reduce or deliberately provision demand rather than simply raising the limit.

## 1.2.18 Failure Scenario — Startup Resource Failure

PostgreSQL can fail at startup when it cannot allocate required sockets, shared memory, or semaphore resources. Diagnostic messages must be interpreted by subsystem.

Examples:

```text
could not create any TCP/IP sockets
could not create shared memory segment
could not create semaphores: No space left on device
```

These represent different failure domains. Validate port/address configuration, shared-memory implementation and limits, semaphore limits where applicable, and host resource configuration before changing database settings.

## 1.2.19 Failure Scenario — Worker Capacity Exhaustion

```text
max_worker_processes capacity
   |
   +-- parallel work
   +-- logical replication
   +-- extension workers
   |
   v
insufficient available workers
   -> degraded parallelism or worker-dependent feature impact
```

Troubleshoot the global worker pool and competing consumers before increasing a feature-specific limit.

## 1.2.20 Troubleshooting Workflow

```text
Process / connection symptom
        |
        v
Inspect pg_stat_activity and logs
        |
        v
Identify backend_type and subsystem
        |
        +-- client backend
        +-- auxiliary process
        +-- worker
        +-- replication process
        |
        v
Check state / waits / transaction age
        |
        v
Correlate PID with OS telemetry
        |
        v
Check PostgreSQL capacity settings
        |
        v
Check OS/cgroup IPC, process, file and memory limits
        |
        v
Remediate root cause and verify recovery
```

Preserve logs and process/session evidence before terminating sessions or restarting the server whenever incident urgency permits.

## 1.2.21 Recovery Principles

Recovery depends on the failure domain. Appropriate actions can include canceling a statement, terminating a session through PostgreSQL, correcting connection-pool configuration, restoring worker capacity, fixing host limits, or restarting PostgreSQL when startup/crash recovery genuinely requires it.

A restart is not a default cure for process saturation. It can clear sessions temporarily while preserving the underlying connection leak, autoscaling mismatch, or resource configuration error.

## 1.2.22 Automation and Guardrails

Automate collection of process/session baselines and enforce guardrails around aggregate application pool capacity. Useful automation includes:

- backend count by application/user/database
- connection-rate and connection-utilization trends
- transaction/query age
- idle-in-transaction age
- wait-event distributions
- worker and WAL-sender utilization
- PostgreSQL crash/restart events
- host process/file-descriptor capacity
- memory/OOM/cgroup events

For deployment automation, calculate potential database connections as the product of application replicas and per-replica pool size, then compare it with deliberately available PostgreSQL capacity before rollout.

## 1.2.23 Production Case Study — Application Connection Storm

A Kubernetes application scales from 20 to 100 pods. Each pod is configured for a 20-connection pool.

```text
20 pods x 20 = 400 potential connections
100 pods x 20 = 2,000 potential connections
```

The database configuration did not change, so application scaling silently multiplied database process demand fivefold. PostgreSQL begins rejecting connections and host memory pressure increases.

### Root Cause

Application autoscaling and database connection capacity were engineered independently despite PostgreSQL's process-per-connection architecture.

### Corrective Actions

- right-size per-pod pools
- cap aggregate application concurrency
- introduce or tune a suitable connection pooler
- maintain reserved operational headroom
- test autoscaling against database connection and memory capacity
- alert on connection-rate and utilization changes before exhaustion

### Reliability Lesson

> Application replicas and per-replica connection pools form one database-capacity equation.

## 1.2.24 SRE/DBRE Best Practices

1. Treat connection count as process, memory, and scheduling capacity.
2. Monitor backend state and waits, not only total count.
3. Preserve administrative connection headroom.
4. Monitor transaction age and idle-in-transaction age.
5. Correlate PostgreSQL PIDs with OS telemetry.
6. Use PostgreSQL-supported cancellation/termination before OS-level process killing.
7. Size worker capacity globally across features.
8. Validate OS/cgroup process, memory, IPC, and file limits.
9. Test application autoscaling against aggregate database connection demand.
10. Treat repeated backend crashes and OOM kills as reliability incidents requiring RCA.
11. Do not use `max_connections` increases as the default response to pool misconfiguration.
12. Revalidate process/resource assumptions after PostgreSQL major-version and platform changes.

## 1.2.26 Section Summary

PostgreSQL's server architecture is process based: a supervising `postgres` process manages the server, normal client connections are serviced by separate backend processes, auxiliary processes run instance-wide subsystems, and background workers provide additional execution capacity.

The production model is therefore:

```text
Client / subsystem demand
        |
        v
PostgreSQL processes
        |
        +-- private memory
        +-- shared memory / IPC
        +-- worker capacity
        +-- OS scheduling / files / memory
        |
        v
Database reliability
```

### SRE/DBRE Principle

> PostgreSQL process capacity is database capacity. Connections, workers, replication processes, shared resources, private memory, and operating-system limits must be engineered as one system.
