## 1.2 — PostgreSQL Server Process Architecture

## 1.2.1 Purpose

PostgreSQL uses a process-based client/server architecture. A PostgreSQL instance consists of cooperating backend and auxiliary processes that share instance-wide memory and synchronization resources. One supervising server process manages the instance, while client sessions are serviced by separate backend processes.

```text
Clients
   |
   v
Supervising postgres/postmaster process
   |
   +-- Backend process A -> Client A
   +-- Backend process B -> Client B
   +-- Backend process C -> Client C
   |
   +-- Auxiliary/background processes
   |
   +-- Background workers
   |
   v
Shared Memory / IPC / Storage
```

This process model is fundamental to PostgreSQL capacity planning, connection management, failure isolation, monitoring, and SRE troubleshooting.

## 1.2.2 PostgreSQL Instance Process Model

A PostgreSQL instance is a group of backend and auxiliary processes that communicate through a common shared-memory area. One supervising process manages the instance, and one instance manages exactly one PostgreSQL database cluster.

This distinction is important operationally:

```text
Host / VM / Container
       |
       +-- PostgreSQL Instance A -> PGDATA A
       |
       +-- PostgreSQL Instance B -> PGDATA B
```

Multiple PostgreSQL instances can run on the same operating system when they use separate data areas and non-conflicting communication endpoints.

## 1.2.3 Supervising Server Process

The PostgreSQL server program starts and manages the database instance. Historically and throughout PostgreSQL internals documentation, the supervising role is commonly called the postmaster.

Its responsibilities include accepting incoming connection requests, starting backend processes, coordinating server lifecycle, and supervising child processes.

Conceptually:

```text
postgres / postmaster
        |
        +-- listen for connections
        +-- start backend processes
        +-- supervise server processes
        +-- coordinate shutdown/restart behavior
        |
        v
PostgreSQL Instance
```

## 1.2.4 Process per Client Connection

PostgreSQL implements a process-per-client model. Each established client session communicates with one backend process.

```text
Application A -------- Backend PID 101
Application B -------- Backend PID 102
Application C -------- Backend PID 103
DBA Session   -------- Backend PID 104
```

The backend parses queries, plans them, executes them, and returns results over the established client connection.

This architecture has important SRE consequences: connection count affects process count, memory demand, file descriptors, semaphores/IPC requirements, context switching, and overall operating-system resource consumption.

## 1.2.5 Backend Processes

A backend process acts on behalf of a client session and handles that session's requests.

A backend can move through operational states such as active, idle, idle in transaction, or waiting on another resource. SREs should therefore evaluate backend processes not only by count but also by state, transaction age, query age, and wait events.

A core monitoring query is:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity;
```

## 1.2.6 Backend Isolation and Shared State

Backend processes have private process memory, but PostgreSQL also requires instance-wide shared state.

```text
Backend A ----\
Backend B -----+---- Shared Memory / IPC
Backend C ----/          |
                          +-- shared buffers
                          +-- WAL buffers
                          +-- locks / shared state
                          +-- process coordination
```

PostgreSQL uses shared memory and synchronization primitives such as semaphores to coordinate concurrent access and preserve data integrity.

## 1.2.7 Auxiliary Processes

PostgreSQL also runs auxiliary processes responsible for specialized instance-wide work. Depending on configuration and server state, these include processes associated with checkpointing, background writing, WAL writing, autovacuum launching, archiving, recovery, WAL receiving, logging, and other server functions.

These processes are not ordinary application sessions and should be monitored according to their subsystem responsibilities.

Later Chapter 1 sections examine the major PostgreSQL background and replication processes in depth.

## 1.2.8 Background Workers

PostgreSQL provides a background-worker infrastructure used by built-in functionality and extensions. Logical replication and parallel processing are examples of PostgreSQL features that use worker processes, and extensions can register additional workers.

Worker capacity is governed by server configuration and therefore becomes a shared resource across multiple PostgreSQL features.

This creates an SRE capacity relationship:

```text
Worker Process Capacity
        |
        +-- Parallel query workers
        +-- Logical replication workers
        +-- Extension workers
        +-- Other background workers
```

Worker-process sizing must therefore be evaluated at the PostgreSQL-instance level rather than feature by feature.

## 1.2.9 Shared Memory and IPC

PostgreSQL requires operating-system inter-process communication facilities. On Unix-derived platforms this includes shared-memory and semaphore mechanisms.

The main shared-memory area contains shared buffers and other shared server data. PostgreSQL can also use dynamic shared memory for features such as parallel processing.

OS-level IPC configuration and limits can therefore prevent PostgreSQL from starting or can constrain large installations.

## 1.2.10 Operating-System Process Capacity

Because PostgreSQL uses one server process per connection, the operating system must support at least the number of processes implied by configured client connections plus PostgreSQL's auxiliary and worker processes and other system workloads.

Production capacity planning should consider:

- `max_connections`
- `max_worker_processes`
- `max_wal_senders`
- autovacuum worker capacity
- parallel worker configuration
- logical replication workers
- extension workers
- operating-system process limits
- semaphore/IPC limits
- file-descriptor limits
- per-process memory

## 1.2.11 Connection Explosion Failure Scenario

Consider an application deployment where hundreds or thousands of application instances independently create database connections.

```text
Application Fleet
      |
      v
Connection Storm
      |
      v
Large Backend Process Count
      |
      +-- memory pressure
      +-- process scheduling overhead
      +-- IPC/semaphore pressure
      +-- database connection exhaustion
      |
      v
Latency / connection failures
```

Increasing `max_connections` alone is not a complete solution. The SRE should investigate connection pooling, application pool configuration, transaction duration, idle sessions, and instance resource capacity.

## 1.2.12 Backend Crash Behavior

PostgreSQL treats unexpected backend-process termination seriously because server processes share critical state. Unsafe operating-system termination such as `SIGKILL` can cause the supervising server process to interpret the event as a crash and terminate sibling processes so PostgreSQL can recover to a consistent state.

Operational rule:

> Do not use arbitrary OS-level kill commands against PostgreSQL processes when supported PostgreSQL cancellation and termination mechanisms are available.

For query cancellation and session termination, prefer PostgreSQL-supported mechanisms such as `pg_cancel_backend()` and `pg_terminate_backend()` according to the incident requirement.

## 1.2.13 Process Monitoring

At the database layer, process/session monitoring starts with `pg_stat_activity`.

At the operating-system layer, correlate PostgreSQL PIDs with CPU, memory, I/O, scheduling, and open-file information.

A useful investigation model is:

```text
PostgreSQL PID
     |
     +-- SQL/session state
     +-- current query
     +-- transaction age
     +-- wait event
     +-- CPU usage
     +-- memory usage
     +-- I/O behavior
     +-- OS process state
```

This correlation helps distinguish query problems from lock waits, storage waits, CPU saturation, or process/resource exhaustion.

## 1.2.14 Monitoring Long-Running Transactions

Long-running transactions are particularly important because they can affect MVCC cleanup and operational stability.

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

The SRE should distinguish a legitimately long transaction from an abandoned `idle in transaction` session.

## 1.2.15 Monitoring Idle-in-Transaction Backends

An idle-in-transaction backend has an open transaction but is not currently executing a statement.

Potential consequences include delayed MVCC cleanup, retained locks, increased bloat risk, and transaction-ID horizon pressure.

Operational monitoring should alert on transaction age rather than simply counting idle sessions.

## 1.2.16 Process-Level Alerting

Useful alert categories include:

- backend count approaching connection capacity
- sudden connection-rate spikes
- long-running active transactions
- long-running idle-in-transaction sessions
- abnormal backend termination
- repeated server-process crashes/restarts
- worker-process exhaustion
- WAL sender exhaustion
- excessive process or file-descriptor consumption
- PostgreSQL unable to allocate required IPC resources

Thresholds should be workload- and environment-specific.

## 1.2.17 Failure Scenario — max_connections Exhausted

```text
Applications
     |
     v
All connection slots consumed
     |
     v
New sessions rejected
     |
     v
Application errors / outage
```

Troubleshooting should answer:

1. How many backends exist?
2. Which applications own them?
3. How many are active?
4. How many are idle?
5. How many are idle in transaction?
6. Are pools oversized?
7. Is there a connection leak?
8. Is database-side pooling required?

The solution should address connection demand, not merely raise the server limit.

## 1.2.18 Failure Scenario — OS Resource Exhaustion

PostgreSQL can fail to start or operate correctly when operating-system IPC, process, memory, or file limits are insufficient.

Examples include failures allocating shared memory or semaphores and errors related to open-file limits.

SRE troubleshooting should correlate PostgreSQL configuration with host-level limits rather than interpreting every `No space left on device` style IPC error as filesystem exhaustion.

## 1.2.19 Failure Scenario — Worker Pool Exhaustion

Multiple PostgreSQL subsystems can depend on background-worker capacity.

```text
max_worker_processes
       |
       +-- logical replication
       +-- parallel processing
       +-- extensions
       |
       v
Capacity exhausted
       |
       v
Requested workers unavailable
```

This can degrade parallel-query performance or prevent worker-dependent features from obtaining expected capacity.

## 1.2.20 Troubleshooting Workflow

When process-related symptoms occur:

```text
Connection/process alert
        |
        v
Check pg_stat_activity
        |
        v
Identify process/session type
        |
        +-- backend session
        +-- auxiliary process
        +-- background worker
        +-- replication process
        |
        v
Check state / wait event / age
        |
        v
Correlate with OS PID metrics
        |
        v
Check configured process limits
        |
        v
Check IPC / memory / file limits
        |
        v
Identify root cause
```

## 1.2.21 Recovery Principles

Recovery actions depend on the failure mode. Options can include canceling a query, terminating a problematic session using PostgreSQL-supported functions, correcting application connection pools, restoring worker capacity, fixing host limits, or restarting the instance when genuinely required.

A restart should not be the default response to process saturation. It can temporarily remove symptoms while leaving the root cause unchanged.

## 1.2.22 Automation

Automate collection and trending of:

- backend count by database/application/user
- active vs idle vs idle-in-transaction sessions
- connection creation rate
- transaction age
- query age
- wait events
- worker-process utilization
- WAL sender utilization
- PostgreSQL restart/crash events
- OS process count
- file-descriptor utilization
- memory pressure

Automation should preserve enough context to identify which workload created the process pressure.

## 1.2.23 Production Case Study — Application Connection Storm

An application deployment increases pod count dramatically. Each pod opens a large local database pool.

```text
More application pods
        |
        v
More configured pool slots
        |
        v
PostgreSQL backend count spikes
        |
        v
max_connections approached
        |
        v
New connection failures
```

### Root Cause

Application-side connection capacity was multiplied by horizontal scaling without considering PostgreSQL's process-per-connection architecture.

### Corrective Actions

- right-size application pools
- use a suitable connection-pooling architecture
- monitor total potential connection demand
- maintain connection headroom
- test autoscaling behavior against database capacity

### Reliability Lesson

> Application scaling and database connection scaling are not independent capacity dimensions.

## 1.2.24 SRE/DBRE Best Practices

1. Treat connection count as a capacity resource.
2. Monitor backend state, not only total backend count.
3. Alert on long-running transactions.
4. Alert on idle-in-transaction age.
5. Correlate PostgreSQL PIDs with OS telemetry.
6. Prefer supported PostgreSQL cancellation/termination functions over unsafe OS kills.
7. Size worker capacity globally across features.
8. Maintain connection and worker headroom.
9. Validate host process, IPC, memory, and file limits.
10. Use connection pooling where workload architecture requires it.
11. Test connection storms during scaling exercises.
12. Investigate repeated backend crashes as reliability incidents.
13. Do not treat raising `max_connections` as the default fix for connection pressure.
14. Document process-related recovery procedures.

## 1.2.26 Section Summary

PostgreSQL's server architecture is process based. A supervising server process manages the instance, normal client sessions are handled by individual backend processes, auxiliary processes perform specialized server work, and background workers provide capacity for built-in and extension functionality.

The SRE/DBRE model is therefore:

```text
Client Demand
     |
     v
Backend Processes
     |
     +-- private process resources
     +-- shared memory / IPC
     +-- OS scheduling/resources
     |
     v
PostgreSQL Reliability
```

### SRE/DBRE Principle

> PostgreSQL process capacity is part of database capacity. Connections, background workers, replication processes, IPC resources, memory, and operating-system limits must be engineered as one system.
