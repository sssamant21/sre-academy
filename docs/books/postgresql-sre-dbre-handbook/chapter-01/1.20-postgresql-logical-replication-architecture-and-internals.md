# 1.20 — PostgreSQL Logical Replication Architecture and Internals

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

Logical replication decodes logical changes from WAL on a publisher and applies them to selected tables on a subscriber. It enables selective replication and upgrade/migration patterns but introduces publication, subscription, replica-identity, slot, schema, apply-worker, and conflict-management responsibilities.

## Architecture

```text
Publisher
  -> WAL
  -> walsender
  -> logical decoding
  -> pgoutput / logical replication protocol
  -> network
  -> subscriber apply worker
  -> local target tables
```

PostgreSQL's built-in logical replication uses WAL sender and apply processes. The publisher decodes WAL and filters changes according to the publication; the subscriber maps and applies changes in transactional order.

## Publications

A publication defines the set of changes/tables to publish. Publication membership does not automatically solve target schema compatibility. DDL/schema management remains an operational concern.

## Subscriptions

A subscription defines the subscriber-side relationship to a publication. Initial synchronization can copy existing table data before ongoing logical changes are applied.

## Replication Slots

Logical replication normally uses logical replication slots to retain required WAL until consumed. Slot health is therefore a primary-capacity concern. A disconnected subscriber can cause WAL retention on the publisher.

## Replica Identity

UPDATE and DELETE replication requires a way to identify the target row. Primary keys are commonly used; replica-identity configuration affects what old-row information is available. `REPLICA IDENTITY FULL` can increase WAL volume and has performance implications.

## Schema Compatibility

Built-in logical replication does not provide general automatic DDL replication. Ensure target tables, columns, types, constraints, and operational changes remain compatible with the replicated data stream.

## Apply Behavior

The subscriber apply process runs with `session_replication_role` set to `replica`. Understand trigger/constraint behavior and test application semantics before using logical replication as a transparent substitute for physical replication.

## Monitoring

Monitor subscription state, worker activity, publisher slots, retained WAL, replication origin/progress, initial table synchronization, apply lag, errors, and target-side conflicts. Correlate subscriber apply capacity with publisher change rate.

## Alerting

Alert on stopped subscriptions, apply errors, slot retention growth, initial-sync failures, lag beyond migration/RPO objectives, schema incompatibility, and target storage/CPU saturation.

## Failure Scenarios

Typical incidents include subscriber outage causing WAL retention, missing replica identity for UPDATE/DELETE patterns, incompatible schema change, apply conflict, insufficient subscriber capacity, and dropped/invalidated slot requiring resynchronization.

## Troubleshooting Workflow

1. Check subscription and worker state.
2. Inspect publisher replication slot and retained WAL.
3. Verify publication membership and table synchronization state.
4. Inspect subscriber logs for apply errors/conflicts.
5. Validate replica identity and schema compatibility.
6. Compare publisher change rate with subscriber apply throughput.
7. Preserve data-consistency requirements before recreating subscriptions or slots.

## Production Case Study — Migration Subscriber Offline

During a migration, the target subscriber is stopped for maintenance while the source continues heavy writes. The logical slot retains WAL on the publisher and `pg_wal` usage rises. The safe plan includes slot-retention capacity monitoring and a maximum allowed outage window; otherwise a target-side maintenance event can threaten source availability.

## SRE/DBRE Principle

> Logical replication decouples data movement from physical cluster replication, but it does not decouple the publisher from WAL retention. Treat every logical slot as a capacity contract.
