# 1.20 — PostgreSQL Logical Replication Architecture and Internals

**Status:** Technical Review ✓  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

Logical replication replicates data changes according to logical replication identity rather than copying physical blocks. PostgreSQL's built-in implementation uses a publish/subscribe model and supports selective table replication, cross-major-version migration, data distribution, consolidation, and other architectures that cannot be modeled as physical standby replication.

For SRE/DBRE teams, logical replication introduces distinct operational dependencies: WAL decoding, logical replication slots, publications, subscriptions, initial table synchronization, replica identity, schema compatibility, worker capacity, apply conflicts, failover continuity, and publisher WAL retention.

## Architecture

```text
Publisher database
  -> transaction changes
  -> WAL
  -> logical decoding
  -> WAL sender
  -> pgoutput / logical replication protocol
  -> network
  -> subscriber leader apply worker
       -> optional parallel apply workers
       -> subscriber target tables

Initial synchronization
  -> table synchronization worker(s)
  -> snapshot/copy existing rows
  -> transition to ongoing replication
```

Logical replication operates at database/table/change level rather than reproducing the publisher's physical cluster layout. PostgreSQL can use physical and logical replication concurrently.

## Publication Architecture

A publication defines which table changes are exposed by a publisher. Publications can select tables and operation types and can additionally use row filters and column lists where supported.

Publication design is therefore part of the data contract. SRE/DBRE review should include:

- intended tables and schemas
- INSERT/UPDATE/DELETE/TRUNCATE publication behavior
- partition publication behavior and `publish_via_partition_root`
- row filters
- column lists
- replica identity requirements
- generated-column publication behavior

A publication does not replicate general schema DDL. Schema lifecycle remains a separate deployment responsibility.

## Subscription Architecture

A subscription is the downstream relationship to one or more publications. It stores publisher connection information and controls replication behavior on the subscriber.

Normally an active subscription consumes changes through one logical replication slot on the publisher. Initial table synchronization can require additional temporary synchronization slots and workers.

Operationally important subscription options include `copy_data`, `create_slot`, `enabled`, `slot_name`, `binary`, `streaming`, `two_phase`, `disable_on_error`, `origin`, and `failover` where applicable. Changes to these options should be treated as controlled production changes rather than tuning shortcuts.

## Initial Data Synchronization

Logical replication commonly starts by copying existing table contents using a consistent snapshot, followed by continuous application of changes generated while the copy was in progress.

Initial synchronization can be one of the most resource-intensive phases of a migration. Monitor publisher read I/O, network throughput, subscriber write I/O, synchronization workers, temporary slots, table synchronization state, WAL generation, and retained WAL.

Do not assume publication operation filters and initial-copy semantics are identical. Validate the intended initial dataset explicitly, especially when publications use row filters or restricted operation sets.

## Logical Decoding and WAL

Logical decoding reconstructs database-level changes from WAL. PostgreSQL's built-in logical replication uses the `pgoutput` output plugin.

Logical decoding is not free: publisher workload, transaction size, WAL generation, decoding throughput, network bandwidth, and subscriber apply capacity all influence end-to-end lag.

Large transactions deserve special attention because they can create bursts of decoded changes and substantial apply pressure. Subscription streaming modes can allow in-progress transaction changes to be transferred/applied with different worker behavior rather than requiring every large transaction to be handled only after commit.

## Replication Slots and WAL Retention

Logical replication normally depends on logical replication slots. A slot prevents required WAL from being removed before the consumer has safely consumed it.

This creates a direct source-capacity dependency:

```text
subscriber/apply outage
      -> slot restart position stops advancing
      -> retained WAL grows
      -> pg_wal pressure grows
      -> filesystem exhaustion risk
      -> publisher availability risk
```

Monitor `pg_replication_slots` continuously. Important fields include slot activity, `restart_lsn`, `confirmed_flush_lsn`, `wal_status`, `safe_wal_size`, invalidation state/reason where exposed, and failover synchronization properties.

`max_slot_wal_keep_size` can bound slot WAL retention, but exceeding the available retention can make a consumer unable to continue from its slot. A retention limit converts unbounded disk-growth risk into a possible resynchronization requirement; it does not eliminate the operational tradeoff.

## Replica Identity

Logical UPDATE and DELETE replication needs enough information to identify the corresponding subscriber row.

A primary key is the usual replica identity. PostgreSQL also supports explicit replica-identity indexes and `REPLICA IDENTITY FULL`.

`REPLICA IDENTITY FULL` should not be treated as a universal fix. It increases the amount of old-row information that may need to be logged and can make subscriber row lookup more expensive. Prefer a stable, appropriate key when the data model allows one.

Publication row filters used for UPDATE/DELETE are also constrained by replica-identity requirements.

## Row Filters and Column Lists

Row filters allow a publication to publish only rows satisfying an expression. They are evaluated before publishing the change. For UPDATE/DELETE publications, filter columns must be covered by replica identity.

Column lists allow only selected columns to be published. Treat row filters and column lists as production data-contract configuration: changing them can change downstream semantics without changing the application schema itself.

When the same table is included through multiple publications in one subscription, carefully validate combined filter/list behavior and PostgreSQL restrictions before deployment.

## PostgreSQL 18 Generated-Column Replication

PostgreSQL 18 adds the ability to publish stored generated columns when explicitly requested, either through publication configuration (`publish_generated_columns = stored`) or an applicable column list.

Generated columns are not published by default. Compatibility also depends on the subscriber schema: publishing a generated value into another generated column is not the same as publishing into a regular target column, and unsupported combinations can fail.

This is a PostgreSQL 18-specific behavior that must be version-gated in migration runbooks involving older subscribers.

## Schema Compatibility and DDL

Built-in logical replication does not provide general automatic DDL replication. The subscriber tables must exist and remain compatible with incoming changes.

Tables are matched by fully qualified name and columns by name. Operational schema changes therefore require sequencing. A safe migration process normally makes subscriber-compatible schema changes before publisher changes that begin emitting data requiring the new schema.

Common failure patterns include:

- publisher column added before subscriber compatibility
- incompatible data-type changes
- renamed/dropped columns
- replica identity removed
- constraints or target defaults producing unexpected behavior
- partition topology assumptions differing between publisher and subscriber

Treat DDL deployment and logical replication as one coordinated change-management system.

## Apply Workers and Worker Capacity

The subscriber uses a leader apply worker for a subscription and may use table synchronization and parallel apply workers depending on phase and configuration.

Worker exhaustion can appear as replication lag or stalled synchronization even when the publisher and network are healthy. Capacity planning must account for logical replication workers alongside other PostgreSQL background-worker consumers.

Review settings such as `max_worker_processes`, `max_logical_replication_workers`, `max_sync_workers_per_subscription`, and `max_parallel_apply_workers_per_subscription` in the context of the entire instance.

## Apply Semantics, Triggers, and Constraints

Logical replication apply operates with replication-specific session semantics. Subscriber-side triggers and constraints do not necessarily behave exactly like ordinary application DML.

Do not assume logical replication is a transparent replay of application SQL. Test trigger behavior, constraints, defaults, generated values, identity behavior, permissions, and any subscriber-side transformations explicitly.

## Conflicts

Logical replication can encounter conflicts when subscriber state is incompatible with an incoming change—for example, uniqueness violations, missing target rows, constraint violations, or incompatible schema/data.

Conflicts are especially likely when applications or multiple replication sources write to the same target tables. PostgreSQL logical replication is not automatically a general-purpose conflict-free multi-writer system.

Operational response should preserve evidence, identify the conflicting transaction/table/key, determine authoritative data ownership, repair state deliberately, and only then resume replication.

## Logical Replication and Failover

Logical replication availability must be designed independently from physical primary failover. If a publisher fails over, the logical consumer needs a valid logical replication position on the promoted primary.

PostgreSQL supports failover-enabled logical slots/subscriptions so relevant logical slots can be synchronized to physical standbys and made available after promotion when the architecture and configuration prerequisites are satisfied.

The `failover` subscription property and corresponding publisher-slot property must agree. Validate slot synchronization state as part of HA readiness rather than discovering the dependency during an outage.

Logical-replication failover should be exercised in planned failover testing together with endpoint/routing changes and consumer reconnection.

## Monitoring

Monitor both sides of the pipeline.

### Publisher

- `pg_replication_slots`
- WAL generation rate
- retained WAL bytes/time
- logical slot activity
- `restart_lsn`
- `confirmed_flush_lsn`
- slot `wal_status` / `safe_wal_size`
- WAL filesystem capacity and time-to-exhaustion
- WAL sender state

### Subscriber

- `pg_stat_subscription`
- subscription worker state
- received/end LSN and timing fields where applicable
- `pg_subscription_rel` synchronization state
- apply errors/conflicts in logs/statistics
- subscriber CPU, memory and storage latency
- target table growth and constraints

Always correlate logical lag with publisher WAL rate and subscriber apply throughput.

## Alerting

Production alerts should cover:

- subscription worker unexpectedly absent
- apply/synchronization errors
- lag exceeding migration/RPO objectives
- logical slot inactive unexpectedly
- retained WAL growth
- projected `pg_wal` exhaustion
- slot approaching retention limit or invalidation
- initial table synchronization stalled
- repeated conflicts
- subscriber resource saturation
- failover slot not synchronized/ready where HA depends on it

Prefer rate and time-to-exhaustion alerts over static WAL-byte thresholds alone.

## Failure Scenarios

### Subscriber outage

The slot retains WAL while the subscriber is unavailable. Source disk usage can become the dominant incident risk.

### Subscriber cannot keep up

If publisher change rate persistently exceeds apply throughput, lag and retained WAL grow even though the subscription remains connected.

### Missing or unsuitable replica identity

UPDATE/DELETE replication can fail or become operationally expensive.

### Schema incompatibility

A publisher deployment emits changes the subscriber cannot apply, stopping replication until compatibility is restored.

### Apply conflict

Subscriber-local data collides with incoming replicated data. Blindly skipping or deleting data can create silent divergence.

### Slot invalidation or loss

Required WAL is no longer available. The consumer may need controlled resynchronization rather than simply restarting the worker.

### Publisher failover without logical-slot continuity

Physical HA succeeds but the logical consumer cannot resume at the required logical position on the new primary.

## Troubleshooting Workflow

1. Confirm publisher/subscriber roles and subscription configuration.
2. Inspect `pg_stat_subscription` and worker presence.
3. Inspect `pg_subscription_rel` for initial-sync/table state.
4. Inspect the publisher logical slot and retained WAL.
5. Compare publisher WAL/change rate with subscriber apply capacity.
6. Inspect subscriber logs and conflict information.
7. Validate publication membership, row filters, column lists, and replica identity.
8. Validate subscriber schema compatibility.
9. Check worker-process capacity and subscriber CPU/storage pressure.
10. Check publisher `pg_wal` capacity and slot retention trajectory.
11. If failover occurred, validate logical-slot continuity on the promoted publisher.
12. Preserve consistency requirements before recreating slots/subscriptions or resynchronizing tables.

## Recovery Guidance

Do not drop a logical replication slot merely to relieve disk pressure unless the consequences are understood. Dropping the slot releases retained WAL but destroys that consumer's protected restart position.

Safer incident handling is to identify whether the subscriber can catch up, restore subscriber/apply capacity, add emergency storage where appropriate, or perform a controlled resynchronization if the protected position can no longer be maintained.

Any manual conflict resolution or transaction skipping must be documented with the exact consistency impact and followed by data reconciliation.

## Automation and Guardrails

Production automation should:

- inventory every logical slot and its owner/consumer
- calculate retained WAL and growth rate
- estimate time to WAL-storage exhaustion
- detect inactive/orphaned slots
- monitor subscription/table-sync state
- validate replica identity for published UPDATE/DELETE tables
- validate schema compatibility before deployments
- verify failover-slot readiness where required
- require explicit approval before destructive slot recreation

Every production logical slot should have an owner, purpose, expected consumer, retention budget, outage budget, alert policy, and recovery procedure.

## Production Case Study — Migration Subscriber Offline

A migration subscriber is stopped for target maintenance while the publisher continues a high write rate. The logical slot correctly protects the consumer's WAL position, but this causes `pg_wal` usage on the source to grow rapidly.

The correct SRE response is not to delete WAL or immediately drop the slot. First determine the WAL generation rate, available storage headroom, expected target recovery time, slot restart position, and whether the subscriber can catch up before the source reaches its capacity limit.

The permanent remediation is to define a source-side WAL retention budget and maximum subscriber outage window before migration begins, with time-to-exhaustion alerts and a documented resynchronization decision point.

## Production Case Study — HA Failover Breaks Logical Consumer

A publisher has physical standbys and an external logical subscriber. Physical failover succeeds, but the logical subscriber cannot resume because its logical slot position was not prepared on the promoted standby.

The lesson is architectural: physical HA does not automatically provide logical replication HA. Logical slot continuity must be designed, monitored, and tested as part of the failover architecture.

## SRE/DBRE Principle

> Logical replication is a data pipeline backed by WAL retention. Operate the publication, slot, decoding path, network, apply workers, schema contract, and failover position as one end-to-end reliability system.
