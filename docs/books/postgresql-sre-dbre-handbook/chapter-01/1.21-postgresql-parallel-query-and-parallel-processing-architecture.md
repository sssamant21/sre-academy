# 1.21 — PostgreSQL Parallel Query and Parallel Processing Architecture

**Status:** Technical Review ✓ → Production Review Pending  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL can execute eligible portions of query plans using multiple processes. Parallel query can substantially reduce elapsed time for suitable large scans, joins, and aggregations, but parallelism is shared cluster capacity rather than free performance. Every parallel worker competes for worker slots, CPU, memory, cache, I/O bandwidth, and temporary-storage capacity.

For SRE/DBRE teams, parallel-query engineering therefore requires understanding both query-level speedup and workload-level resource amplification.

## Parallel Query Architecture

When the optimizer decides that a parallel strategy is cheapest, the plan contains a `Gather` or `Gather Merge` node. The plan below that node is the parallel portion.

```text
Client
  -> leader backend
      -> serial plan nodes above Gather
      -> Gather / Gather Merge
          -> leader participation (normally enabled)
          -> parallel worker 1
          -> parallel worker 2
          -> ...
              -> parallel-aware scan/join/aggregate work
```

`Gather` consumes tuples from workers without preserving a pre-existing worker sort order. `Gather Merge` requires each participant to produce sorted tuples and performs an order-preserving merge in the leader.

Parallel execution is process based: workers are separate PostgreSQL processes, not threads inside the leader backend.

## Leader Process

The backend serving the client becomes the parallel-group leader. It requests workers and coordinates execution. By default, `parallel_leader_participation=on`, so the leader can also execute the parallel portion.

Leader participation is workload dependent. When workers produce relatively few tuples, the leader can behave much like another worker. When workers produce many tuples, the leader can spend most of its time consuming worker output and executing serial work above `Gather`, limiting further speedup.

This creates an important scaling principle: doubling workers does not imply halving query latency.

## Worker Capacity Hierarchy

Parallel query is bounded by several configuration layers:

- `max_worker_processes` — cluster-wide ceiling for background worker processes.
- `max_parallel_workers` — cluster-wide ceiling for workers used by parallel operations.
- `max_parallel_workers_per_gather` — maximum workers a single `Gather`/`Gather Merge` can request.
- `max_parallel_maintenance_workers` — per-command limit for supported parallel maintenance operations.

`max_parallel_workers` cannot provide capacity beyond `max_worker_processes`.

The number shown as `Workers Planned` is not a reservation. At execution time PostgreSQL can obtain fewer workers than planned, or none. The leader then executes the parallel portion with the workers actually available. Consequently, an unchanged plan can have different latency under worker-pool contention.

## Planner Cost Model

The planner considers parallel execution only when its estimated benefit exceeds its overhead. Important controls include:

- `parallel_setup_cost`
- `parallel_tuple_cost`
- `min_parallel_table_scan_size`
- `min_parallel_index_scan_size`
- `max_parallel_workers_per_gather`

These are planner inputs, not guaranteed performance knobs. Arbitrarily lowering parallel costs can cause excessive parallelism and degrade cluster-wide throughput.

Before changing them, validate cardinality estimates, table statistics, query shape, CPU availability, storage throughput, and representative concurrency.

## Parallel-Aware Plan Operations

PostgreSQL can use parallel execution for eligible plan operations including parallel scans, joins, aggregation, and append operations.

Typical plan structures include:

```text
Gather
  -> Parallel Seq Scan
```

```text
Finalize Aggregate
  -> Gather
       -> Partial Aggregate
            -> Parallel Seq Scan
```

Parallel aggregation commonly divides work into partial aggregation in participants and final aggregation above `Gather`. Parallelism is therefore often partial rather than end-to-end; serial sections can become the limiting stage as worker count increases.

## Parallel Safety

PostgreSQL classifies operations as:

- **parallel safe** — may execute in parallel workers;
- **parallel restricted** — may participate in a parallel query but must execute in the leader;
- **parallel unsafe** — disables parallel execution for the query.

User-defined functions are `PARALLEL UNSAFE` by default unless explicitly labeled otherwise. Do not mark application or extension functions `PARALLEL SAFE` merely to obtain a parallel plan. Incorrect labeling can cause errors or incorrect behavior.

Functions that modify database state, change transaction state, access sequences, or persistently alter settings must be treated as unsafe. Functions that depend on backend-local state such as temporary tables, cursors, prepared statements, or client connection state generally require restricted treatment.

## Conditions That Prevent Parallel Query

Parallel plans are not available for every statement. Important restrictions include data-modifying statements/operations, row-locking behavior, parallel-unsafe functions, certain cursor/incremental-execution scenarios, and queries executing inside an already parallel query.

`max_parallel_workers_per_gather = 0` disables parallel query execution.

Some commands that create/populate an object can still use parallelism for an underlying eligible `SELECT`, so operational diagnosis should rely on the actual plan rather than assumptions based only on command type.

## Memory Amplification

Parallel query can dramatically increase aggregate memory demand because workers are independent processes and many resource limits apply to each worker.

A useful capacity model is:

```text
Approximate query resource exposure
  ~= leader demand
   + worker count × per-worker demand
```

This is intentionally an engineering envelope, not an exact PostgreSQL allocation formula.

`work_mem`, for example, applies to eligible operations within each process. Multiple memory-intensive plan nodes plus multiple workers plus concurrent sessions can therefore multiply memory consumption far beyond a simple `connections × work_mem` estimate.

A parallel query using four workers can involve the leader plus four worker processes, potentially creating roughly five process-level consumers of CPU, memory, and I/O resources for the parallel portion.

## CPU and I/O Amplification

Parallel query reduces elapsed time only when sufficient capacity exists underneath it.

Increasing workers on a CPU-saturated host can increase scheduling contention rather than throughput. Increasing workers against saturated storage can raise queue depth and latency. Parallel scans can also change cache behavior by touching large working sets rapidly.

Evaluate:

- CPU utilization and run queue;
- storage latency, IOPS, throughput, and queue depth;
- PostgreSQL and OS cache pressure;
- temporary-file generation;
- NUMA/container CPU constraints where applicable;
- competing maintenance and background work.

PostgreSQL 18 asynchronous I/O can improve the ability of eligible operations to keep storage busy, but AIO and parallel query are separate dimensions. More workers should not be used as a substitute for diagnosing storage latency or inappropriate I/O-concurrency settings.

## Parallel Maintenance

Parallel query and parallel maintenance share parts of the worker-capacity hierarchy but have different resource semantics.

Supported parallel utility operations include parallel index building for eligible index types and parallel `VACUUM` index processing. They are bounded by `max_parallel_maintenance_workers` as well as the relevant global worker ceilings.

Unlike ordinary parallel query, `maintenance_work_mem` is generally a command-level limit for a parallel utility command rather than a separate full allocation per maintenance worker. CPU and I/O consumption can still rise substantially with worker count.

## Observability

Start with the actual execution plan:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT ...;
```

For production systems, use `EXPLAIN ANALYZE` carefully because it executes the statement.

Inspect:

- `Gather` / `Gather Merge` placement;
- `Workers Planned`;
- `Workers Launched`;
- per-worker rows and timing where shown;
- partial/final aggregate stages;
- buffer and temporary-I/O behavior;
- serial plan sections above the parallel boundary;
- planner settings that materially influenced the test.

Correlate plan evidence with `pg_stat_activity`, `pg_stat_io`, OS CPU scheduling, memory pressure, storage latency/throughput, and workload concurrency.

## Diagnosing Worker Starvation

A query repeatedly showing fewer `Workers Launched` than `Workers Planned` should trigger cluster-level investigation rather than immediate query-plan tuning.

Check:

```sql
SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW max_parallel_workers_per_gather;
SHOW max_parallel_maintenance_workers;
```

Then inspect competing workloads and background workers. Increasing worker limits is appropriate only when CPU, memory, and I/O headroom support the additional concurrency.

## Production Guardrails

1. Do not maximize workers per query by default.
2. Size parallelism for concurrent workload throughput, not isolated benchmark latency.
3. Include leader plus worker resource amplification in memory and CPU capacity models.
4. Preserve worker headroom for concurrent queries and required background work.
5. Treat `Workers Planned` as planner intent, not guaranteed capacity.
6. Validate function parallel-safety labels, especially extension/application functions.
7. Compare serial and parallel behavior under representative production concurrency.
8. Do not compensate for stale statistics or poor cardinality estimates by blindly forcing parallel plans.
9. Monitor temporary I/O and storage saturation when increasing parallelism.
10. Revalidate settings after CPU/memory/storage or container-limit changes.

## Alerting

Parallel-worker usage itself is not an incident. Alert on symptoms that threaten workload objectives, such as:

- sustained CPU saturation associated with parallel workload bursts;
- repeated worker starvation for latency-critical queries;
- memory pressure/OOM risk caused by parallel amplification;
- sustained temporary-I/O growth;
- storage saturation correlated with parallel scans;
- major latency variance caused by inconsistent worker availability.

Alerts should be tied to SLO impact and capacity pressure rather than the mere presence of parallel workers.

## Troubleshooting Workflow

1. Capture the actual plan and identify `Gather`/`Gather Merge` boundaries.
2. Compare workers planned with workers launched.
3. Identify serial sections that limit parallel speedup.
4. Check the global worker-capacity hierarchy.
5. Check concurrent parallel queries and maintenance operations.
6. Validate CPU headroom and scheduling pressure.
7. Validate memory amplification, sorts/hashes, and temporary spills.
8. Check storage latency, throughput, queue depth, and `pg_stat_io` evidence.
9. Validate statistics and planner estimates before changing parallel cost parameters.
10. Verify functions/operators are correctly labeled for parallel safety.
11. Compare serial and parallel plans under representative concurrency.
12. Tune for stable workload throughput and latency, then document the tested operating envelope.

## Production Case Study — Parallel Worker Starvation

A reporting workload is configured to request many workers per query. A single report performs well during an isolated benchmark. During the production reporting window, several reports run concurrently and exhaust the cluster's parallel-worker pool.

Later queries retain plans expecting multiple workers but launch fewer workers than planned. Their latency becomes inconsistent while CPU and storage utilization remain bursty.

The remediation is not necessarily to raise every worker limit. The DBRE team reduces `max_parallel_workers_per_gather` for the reporting workload, validates global worker headroom, and tests concurrent throughput. Individual queries receive fewer CPUs, but aggregate throughput and tail latency become more predictable.

The lesson is architectural: parallelism is a shared concurrency budget.

## SRE/DBRE Principle

> Parallel query converts cluster resources into lower query latency. Engineer the worker, CPU, memory, and I/O budget for the whole workload—not the fastest possible execution of one query.
