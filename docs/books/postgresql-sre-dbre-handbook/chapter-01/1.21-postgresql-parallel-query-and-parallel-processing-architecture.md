# 1.21 — PostgreSQL Parallel Query and Parallel Processing Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL can execute eligible portions of query plans using parallel workers. Parallelism can reduce elapsed time for suitable large operations, but it consumes worker, CPU, memory, and I/O capacity and can execute with fewer workers than the planner expected.

## Parallel Plan Architecture

When the optimizer chooses parallel execution, the plan contains `Gather` or `Gather Merge` above the parallel portion.

```text
Leader backend
   -> Gather / Gather Merge
      -> parallel worker 1
      -> parallel worker 2
      -> ...
```

`Gather` combines tuples without preserving worker ordering. `Gather Merge` merges sorted worker output while preserving ordering requirements.

## Leader Process

The session backend acts as leader. It can participate in the parallel portion while also consuming tuples from workers and executing plan nodes above the Gather boundary. For plans producing many tuples, leader coordination can become substantial.

## Worker Limits

Worker availability is constrained by settings including:

- `max_worker_processes`
- `max_parallel_workers`
- `max_parallel_workers_per_gather`

A plan can execute with fewer workers than planned, even zero, if workers are unavailable. This can create latency variability despite an unchanged plan.

## Parallel Safety

Not every operation or function is safe/eligible for parallel execution. PostgreSQL classifies plan operations and functions according to parallel-safety rules. Extension and application functions must be declared correctly.

## Memory and I/O

Parallel execution is not free capacity. Multiple workers can increase aggregate CPU, memory, and I/O demand. A query that becomes faster individually can still reduce overall workload throughput if concurrency is high.

## Parallel Maintenance

PostgreSQL also supports parallelism in selected maintenance/index operations. VACUUM can use parallel workers for eligible index phases, and other maintenance operations have their own worker limits/configuration.

## Monitoring

Use `EXPLAIN (ANALYZE, BUFFERS)` to compare workers planned vs launched and actual work distribution. Monitor worker saturation, CPU, storage throughput, temporary I/O, memory pressure, and workload concurrency.

## Alerting

Avoid alerting merely because parallel workers are used. Alert when worker exhaustion, CPU saturation, memory pressure, or I/O saturation causes sustained workload degradation, or when important queries repeatedly receive fewer workers than planned.

## Failure Scenarios

Common issues include global worker exhaustion, too much parallelism under high concurrency, memory amplification, I/O saturation, parallel-unsafe functions preventing expected plans, and planner estimates favoring parallel execution where workload-level throughput suffers.

## Troubleshooting Workflow

1. Inspect the actual plan and worker counts.
2. Compare workers planned vs launched.
3. Check global worker limits and competing background work.
4. Check CPU, memory, and I/O saturation.
5. Compare serial and parallel plans under representative concurrency.
6. Tune workload-level limits rather than maximizing workers per query.

## Production Case Study — Parallel Worker Starvation

A reporting workload is tuned to request many workers per query. During concurrent reports, the global worker pool is exhausted and later queries launch fewer workers than planned. Their latency becomes unpredictable. Reducing per-query worker demand can improve total throughput and consistency even though a single isolated query uses fewer CPUs.

## SRE/DBRE Principle

> Parallel query is a shared-capacity feature. Optimize parallelism for workload throughput and predictability, not the fastest possible execution of one isolated query.
