# 1.22 — PostgreSQL Extension Architecture and Shared Libraries

**Status:** Technical Review ✓ → Production Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL is deliberately extensible. Extensions can package SQL objects and can also integrate compiled shared-library code that runs inside PostgreSQL server processes. This makes extensions powerful, but it also makes them part of the database security, availability, memory, worker-capacity, patching, backup/restore, and upgrade dependency graph.

For SRE/DBRE teams, an extension must therefore be operated as server software rather than treated as ordinary application DDL.

## PostgreSQL Extensibility Model

PostgreSQL is catalog-driven and permits new functions, data types, operators, aggregates, index operator classes, access methods, and other capabilities to be integrated with the server. Dynamically loadable code can implement functionality that behaves much like built-in PostgreSQL functionality.

An extension packages related database objects so PostgreSQL understands that those objects belong together.

```text
Extension source/package
   -> control file
   -> installation/update SQL scripts
   -> optional native shared library
   -> optional background-worker/hooks integration

Installed on PostgreSQL host/image
   -> CREATE EXTENSION
   -> objects registered in current database
   -> membership tracked by PostgreSQL catalogs
```

This creates two distinct operational layers:

1. **Server/package availability** — required control files, SQL scripts, and native libraries must exist on the PostgreSQL installation.
2. **Database registration** — `CREATE EXTENSION` installs/registers the extension objects in a particular database.

Installing an operating-system package alone does not mean the extension is installed in every database, and an extension recorded in a backup cannot necessarily be restored unless the required extension files exist on the destination server.

## Extension Files

A packaged extension normally includes a primary `.control` file and one or more SQL installation/update scripts. Native extensions can additionally include a compiled shared library.

Typical layout:

```text
SHAREDIR/extension/
   myext.control
   myext--1.0.sql
   myext--1.0--1.1.sql

PKGLIBDIR/
   myext.so                 # platform-specific suffix may differ
```

The control file can define properties such as the default version, relocatability, dependencies, and `module_pathname` used by SQL scripts to refer to the extension's native library.

PostgreSQL 18 also supports `extension_control_path`, allowing additional locations to be searched for extension control files. If native libraries are stored outside the standard library directory, `dynamic_library_path` normally needs corresponding configuration.

Treat both paths as controlled server configuration; untrusted writable directories must never be introduced into the production library/extension search path.

## CREATE EXTENSION and Extension Membership

`CREATE EXTENSION` executes the extension's installation script and records the resulting objects as members of the extension. PostgreSQL can then manage those related objects as a unit.

Example inventory:

```sql
SELECT extname,
       extversion,
       extnamespace::regnamespace AS extension_schema
FROM pg_extension
ORDER BY extname;
```

`CREATE EXTENSION` operates in the current database. An extension required in multiple databases generally must be created in each required database unless its design/documentation states otherwise.

Backups normally represent extension membership through extension creation rather than independently dumping every member object. Consequently, restore testing must verify that compatible extension files and binaries are present on the restore target.

## Extension Dependencies and Versioning

An extension control file can declare dependencies on other extensions. Those dependencies must be available and installed appropriately before the dependent extension can be created.

Extensions can provide version-specific update scripts and can be upgraded with:

```sql
ALTER EXTENSION extension_name UPDATE;
```

or, when supported:

```sql
ALTER EXTENSION extension_name UPDATE TO 'target_version';
```

Never assume an extension upgrade is equivalent to a PostgreSQL package upgrade. Validate the extension vendor/project's supported PostgreSQL versions, upgrade path, downgrade/rollback limitations, SQL migration behavior, and binary compatibility.

## Native Shared Libraries

C-language extensions can load compiled shared libraries into PostgreSQL server processes. PostgreSQL checks a compatibility "magic block" in supported dynamically loaded modules, but that mechanism does not turn arbitrary native code into safe code.

Native extension code executes inside PostgreSQL's address space. A defect can therefore cause outcomes such as:

- backend crashes
- memory corruption
- excessive CPU or memory consumption
- server-wide instability depending on where/how code executes
- security exposure
- incorrect query results or persistent data damage

Production extension governance must therefore control both SQL installation privileges and who can place/replace binaries on the PostgreSQL hosts or container images.

## Dynamic Library Resolution

When a dynamically loadable module is referenced without an explicit directory, PostgreSQL uses `dynamic_library_path` to search for it. `$libdir` represents PostgreSQL's compiled-in package-library directory and is the default search location.

Useful server-side verification includes:

```sql
SHOW dynamic_library_path;
SHOW extension_control_path;
```

At the operating-system level, `pg_config --pkglibdir` identifies PostgreSQL's package library directory and `pg_config --sharedir` identifies the shared-data directory used by the installation.

Avoid hard-coding version-specific filesystem paths into extension definitions when the extension supports `$libdir`/`MODULE_PATHNAME` conventions. This makes PostgreSQL installation and major-version transitions safer.

## Shared-Library Preloading

PostgreSQL provides three distinct preload mechanisms. They are not interchangeable.

### `shared_preload_libraries`

Libraries listed here are loaded when the PostgreSQL server starts. Some modules require this because they must perform work during postmaster initialization, such as allocating shared memory, reserving lightweight-lock resources, or registering background workers.

Important properties:

- takes effect only at server start
- changing it requires a PostgreSQL restart
- a missing/invalid configured library can prevent PostgreSQL startup
- should be used only when the module requires or explicitly recommends server-start loading

Before changing it, record the current value and maintain a configuration rollback method that works even if PostgreSQL cannot start.

### `session_preload_libraries`

These libraries are loaded when a client session starts. This can be useful for session-scoped debugging or instrumentation modules and does not require a full server restart to change configuration, although existing sessions are unaffected.

### `local_preload_libraries`

This is also applied at connection start but is intentionally restricted to libraries in PostgreSQL's `plugins` subdirectory because ordinary users can set it. Only libraries specifically designed and administered as safe for this mechanism should be installed there.

Operationally, never move an extension into a different preload mechanism merely to avoid a restart. Follow the module's documented loading requirements.

## Background Workers and Shared Memory

Extensions can register background workers. Depending on their design, workers can attach to shared memory, initialize libraries, and connect to databases.

Extension workers share PostgreSQL's global worker-process capacity. Their resource requirements must therefore be included when sizing and reviewing:

- `max_worker_processes`
- parallel-query worker requirements
- logical-replication workers
- extension-specific worker counts
- CPU and memory headroom

A preload extension that allocates shared memory or registers workers changes PostgreSQL's startup-time resource requirements. Test these changes under the same configuration and extension inventory used in production.

## PGXS and Extension Build Architecture

PostgreSQL supplies PGXS as build infrastructure for many external extensions, especially extensions containing C code. PGXS builds against an installed PostgreSQL server/development environment using `pg_config` to locate PostgreSQL headers, libraries, and build configuration.

A successful compile is not sufficient evidence of production compatibility. Native extensions must be rebuilt or obtained from packages specifically compatible with the target PostgreSQL major version, operating system, CPU architecture, and extension release.

For PostgreSQL builds with LLVM JIT support, PGXS can also install extension bitcode used for JIT inlining where applicable.

## Security Architecture

Extension installation is a privileged software-supply-chain operation.

An extension installation script can create powerful database objects, and native extensions execute server-side machine code. PostgreSQL documentation specifically warns that extension installation scripts can carry security risk, particularly when they are installed by privileged users.

Production controls should include:

- approved extension allowlist
- trusted package/vendor/source repository
- pinned and reviewed versions
- package signature/provenance controls where available
- controlled OS/container-image modification
- restricted `CREATE EXTENSION` privileges
- controlled extension/library search paths
- vulnerability tracking for PostgreSQL and extensions
- staged upgrade and rollback testing

Never install an unknown extension directly into production simply because `CREATE EXTENSION` succeeds in a development database.

## Major PostgreSQL Upgrade Architecture

Extensions are a formal gate for every major PostgreSQL upgrade.

Before upgrading:

1. Inventory every extension and version in every database.
2. Identify native/shared-library extensions.
3. Verify target PostgreSQL-major support from the extension's official documentation/vendor.
4. Install compatible target-version packages/binaries before restore or `pg_upgrade` completion as required by the upgrade procedure.
5. Verify preload configuration against the target installation.
6. Validate extension update scripts and required post-upgrade actions.
7. Test application behavior and extension-specific indexes/data structures.
8. Test rollback/rebuild strategy.

Useful inventory query:

```sql
SELECT d.datname,
       e.extname,
       e.extversion
FROM pg_database d
CROSS JOIN LATERAL (
    SELECT extname, extversion
    FROM pg_extension
) e
WHERE d.datname = current_database();
```

Run equivalent inventory against each database rather than assuming extension state is cluster-global.

## Backup, Restore, and Disaster Recovery

Database backups do not replace extension software distribution.

A DR environment must have compatible extension packages, control files, SQL scripts, shared libraries, preload settings, and required external dependencies available before the database can be considered restorable.

Include extension restoration in DR exercises:

```text
restore infrastructure/image
   -> verify PostgreSQL version
   -> verify extension packages/binaries
   -> verify preload configuration
   -> start PostgreSQL
   -> restore database
   -> verify CREATE EXTENSION/extension versions
   -> validate extension functionality
```

An untested extension dependency can turn an otherwise valid backup into an unusable recovery path.

## Managed PostgreSQL Services

Managed PostgreSQL platforms generally restrict extensions, server filesystem access, preload libraries, superuser capabilities, and extension versions. Availability also differs by provider, service tier, region, and PostgreSQL major version.

Cloud-specific handbook chapters must validate extension support against current AWS, Azure, and Google Cloud documentation rather than carrying assumptions from self-managed PostgreSQL.

## Observability and Inventory

At minimum, production inventory should capture:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;

SHOW shared_preload_libraries;
SHOW session_preload_libraries;
SHOW local_preload_libraries;
SHOW dynamic_library_path;
SHOW extension_control_path;
```

Also correlate extension configuration with:

- `pg_stat_activity.backend_type` for worker/process visibility where exposed
- PostgreSQL startup/server logs
- OS package/container-image versions
- extension-specific statistics/views
- worker utilization
- memory/shared-memory consumption
- crash/restart frequency

Maintain the inventory in configuration management rather than relying solely on an emergency-time SQL query.

## Alerting and Production Guardrails

Alert or gate changes when:

- PostgreSQL cannot start after a preload change
- required extension workers disappear
- extension worker demand exhausts global worker capacity
- installed extension versions drift across HA nodes/environments
- a target PostgreSQL upgrade lacks a compatible extension build
- DR/restore targets lack required extension packages
- security advisories affect installed native extensions
- preload/library configuration differs unexpectedly between HA peers

Extension changes that require server restart should follow the same change-management discipline as core PostgreSQL configuration changes.

## Failure Scenario 1 — Invalid `shared_preload_libraries`

A new monitoring library is added directly to `shared_preload_libraries`. The binary is missing on one HA node. On restart, PostgreSQL cannot load the configured library and startup fails.

Correct response:

1. identify the failing library in startup logs
2. restore the known-good preload configuration or install the validated compatible binary
3. restart and verify PostgreSQL health
4. verify all HA nodes have identical required software
5. correct deployment automation so package installation precedes configuration activation

Do not repeatedly restart without correcting the startup dependency.

## Failure Scenario 2 — Major Upgrade Blocked by Native Extension

A PostgreSQL major upgrade passes core database testing, but a required C extension has no supported build for the target major release.

The upgrade is **not production-ready**. Options include waiting for a supported extension release, replacing/removing the dependency through an approved migration, or changing the PostgreSQL upgrade target. Bypassing compatibility validation risks startup failure, backend crashes, or incorrect behavior.

## Failure Scenario 3 — Restore Fails on Missing Extension

A backup is restored onto a clean DR host, but the extension control/library files are absent. The dump contains the logical requirement to create the extension, not the extension software itself.

Corrective action is to install the approved compatible extension package on the DR PostgreSQL installation and repeat/continue the supported restore workflow. Do not manually fabricate extension catalog rows or copy arbitrary binaries from another PostgreSQL major version.

## Troubleshooting Workflow

1. Identify the extension name and installed database version.
2. Determine whether it is SQL-only or uses native shared libraries.
3. Determine whether it requires `shared_preload_libraries`, session loading, hooks, shared memory, or background workers.
4. Check PostgreSQL logs for load, symbol, compatibility, worker, or startup errors.
5. Verify control/SQL/library files on the actual PostgreSQL installation.
6. Inspect `extension_control_path` and `dynamic_library_path` when resolution fails.
7. Verify PostgreSQL-major, OS, architecture, and extension-version compatibility.
8. Check global worker and memory capacity for worker-based extensions.
9. Compare package and configuration inventory across HA peers.
10. Reproduce upgrades/remediation in staging before production.
11. Use the documented extension upgrade/removal procedure; never manipulate extension catalogs manually as a shortcut.

## SRE/DBRE Production Checklist

Before approving an extension for production, confirm:

- business/technical owner exists
- extension source/vendor is approved
- PostgreSQL 18 compatibility is documented/tested
- security implications are reviewed
- binary/package provenance is controlled
- required preload behavior is documented
- restart requirements are understood
- worker/shared-memory requirements are capacity-tested
- HA nodes contain matching packages/configuration
- backup/restore is tested
- major-upgrade path is documented
- vulnerability/patch ownership is assigned
- rollback/removal procedure is tested

## SRE/DBRE Principle

> An extension is executable database infrastructure. Once installed, it becomes part of PostgreSQL's security boundary, process model, recovery path, and upgrade contract. Inventory, patch, test, and govern it with the same discipline as PostgreSQL itself.
