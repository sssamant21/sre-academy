# 1.22 — PostgreSQL Extension Architecture and Shared Libraries

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL extensions can add SQL objects, data types, functions, operators, access methods, background workers, hooks, and shared-library code. Extensions greatly expand PostgreSQL capabilities but also extend the trusted-code and upgrade surface of the database server.

## Extension Model

`CREATE EXTENSION` installs an extension into a database using extension control and SQL files available to the PostgreSQL installation.

```text
extension package on server
  -> control / SQL / shared library files
  -> CREATE EXTENSION
  -> database objects registered as extension members
```

Installed extension availability is therefore partly an operating-system/package/container-image concern and partly a database concern.

## Shared Libraries

Extensions can load native shared libraries into PostgreSQL server processes. Native code runs inside the database server process context and can affect stability, memory safety, and security. Only trusted and controlled extension binaries should be installed in production.

## Preloading

PostgreSQL provides shared-library preload settings for libraries that must be loaded at server or session startup. `shared_preload_libraries` requires server restart for changes and is commonly needed by extensions that require shared memory, hooks, or background workers initialized at server start.

Do not add libraries to preload configuration without validating startup compatibility and rollback procedure.

## Background Workers

Extensions can register background workers. Background workers can attach to shared memory and may connect to databases. They consume `max_worker_processes` capacity and become part of the PostgreSQL process/reliability architecture.

## Extension Versioning

Extensions have versions and can provide upgrade scripts. PostgreSQL major upgrades require validation that every required extension version and binary is supported on the target release before cutover.

## Security

Extension installation can execute privileged SQL and native code depending on extension design. Restrict extension-management privileges and maintain an approved extension inventory. Do not treat arbitrary extension installation as ordinary application DDL.

## Managed PostgreSQL

Cloud-managed PostgreSQL services typically restrict which extensions and shared-library features are available. Later cloud-specific chapters must validate extension support against the provider's current official documentation rather than assuming parity with self-managed PostgreSQL.

## Monitoring

Maintain inventory of installed extensions, versions, preload configuration, extension background workers, package/library versions, and PostgreSQL compatibility. Include extensions in patching, vulnerability, upgrade, backup/restore, and DR testing.

Example:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

## Failure Scenarios

Common problems include PostgreSQL failing to start after an invalid preload-library change, extension binary mismatch after upgrade, missing extension package during restore, worker exhaustion, extension bugs crashing a backend, and unsupported extension behavior on a managed service.

## Troubleshooting Workflow

1. Identify installed extension and version.
2. Determine whether it uses native libraries, preload hooks, or workers.
3. Check PostgreSQL/server logs and binary/package compatibility.
4. Validate target PostgreSQL-version support.
5. Reproduce upgrades in staging with identical extension inventory.
6. Maintain a rollback path for preload changes and extension upgrades.

## Production Case Study — Upgrade Blocked by Extension

A PostgreSQL major upgrade is technically ready, but a required native extension does not yet support the target major version. Proceeding would risk startup or application failure. The extension compatibility matrix must therefore be a formal gate in the database upgrade process.

## SRE/DBRE Principle

> An extension becomes part of the database server's operational dependency graph. Inventory, patch, test, and upgrade it with the same discipline as PostgreSQL itself.
