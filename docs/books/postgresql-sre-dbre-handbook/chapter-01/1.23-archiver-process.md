# 1.23 — Archiver Process

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

The PostgreSQL archiver process is a critical component of continuous WAL archiving and point-in-time recovery architectures. Its job is to archive completed WAL segments according to configured archive behavior. Archive health directly affects recoverability and can indirectly affect primary storage capacity when WAL cannot be recycled as expected.

## Architecture

```text
WAL generation
  -> completed WAL segment
  -> archiver
  -> archive command/library
  -> durable archive destination
  -> WAL available for PITR / restore workflows
```

Continuous archiving requires an appropriate `wal_level` and archive configuration.

## archive_mode

`archive_mode` enables WAL archiving behavior and is a server-start setting. Archiving also requires a configured archive mechanism such as `archive_command` or supported archive-library behavior.

## Archive Command Contract

An archive command must copy a completed WAL segment safely to durable archive storage and return success only when the archive operation has actually succeeded according to the recovery design. Commands must handle duplicate/archive-retry behavior safely.

## Retry Behavior

If archiving fails, PostgreSQL retries. Persistent failure can create a growing backlog of WAL segments awaiting successful archive. The database may continue serving traffic while the recoverability and capacity situation worsens.

## Monitoring

Use `pg_stat_archiver` and storage/archive-system telemetry. Monitor:

- archived count
- failed count
- last archived WAL and time
- last failed WAL and time
- age since last successful archive
- archive destination availability
- `pg_wal` usage and growth rate
- WAL generation rate

## Alerting

Alert on repeated archive failures, no successful archive beyond an expected workload-aware interval, archive destination capacity/permission errors, and projected primary WAL-storage exhaustion.

Do not use a simplistic “no archive for N minutes” rule on a database that generates little or no WAL; correlate with WAL activity.

## Recovery Dependency

A backup is not sufficient for arbitrary PITR without the required WAL chain. Archive monitoring is therefore part of backup monitoring. Restore tests must verify that archived WAL can actually be retrieved and replayed.

## Failure Scenarios

Common archiver incidents include destination full, network/object-store outage, permission/credential failure, invalid command path, archive script bug, duplicate-file handling error, and archive throughput lower than WAL generation.

## Troubleshooting Workflow

1. Inspect `pg_stat_archiver` and PostgreSQL logs.
2. Verify archive destination availability and capacity.
3. Validate permissions/credentials and command/library execution.
4. Compare WAL generation rate with archive throughput.
5. Measure `pg_wal` backlog and time to exhaustion.
6. Restore archive service without deleting unarchived WAL.
7. Verify backlog drains and run/maintain recovery validation.

## Production Case Study — Archive Destination Full

The archive filesystem reaches capacity. The archiver repeatedly fails while the primary continues generating WAL. `pg_wal` grows and threatens the primary filesystem. The correct response is to restore archive-destination capacity/service, verify successful archive retries, and confirm WAL recycling resumes. Manually deleting WAL from the primary would jeopardize recovery and database safety.

## SRE/DBRE Principle

> WAL archiving is a live production pipeline, not a passive backup feature. Monitor both recoverability and the primary-capacity consequences of archive failure.
