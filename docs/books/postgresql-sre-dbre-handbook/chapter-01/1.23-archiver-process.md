# 1.23 — Archiver Process

**Status:** Technical Review ✓  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

The PostgreSQL WAL archiver is an auxiliary server process used by continuous WAL archiving. It transfers completed WAL segment files from `pg_wal` to an archive destination through either `archive_command` or `archive_library`. A healthy archive pipeline is fundamental to point-in-time recovery (PITR), backup recoverability, disaster recovery, and WAL-capacity safety.

The archiver is not the WAL writer and is not a replication sender. The WAL writer writes WAL buffers to local WAL files; WAL senders stream WAL to replication clients; the archiver handles completed WAL segments for archive storage.

## Architecture

```text
transactions
   -> WAL generation
   -> pg_wal segment
   -> completed WAL segment
   -> WAL archiver process
        -> archive_command
        OR
        -> archive_library
   -> durable archive destination
   -> restore/PITR/DR WAL chain
```

The archiver is supervised by the PostgreSQL server process. PostgreSQL 18 classifies the WAL archiver as an auxiliary process.

## Enabling Continuous WAL Archiving

Continuous archiving requires:

- `wal_level = replica` or `logical`
- `archive_mode = on` for a normal primary archive configuration, or `always` where archive behavior is intentionally required during recovery/standby operation
- exactly one active archive mechanism: `archive_command` or `archive_library`

`archive_mode` is a server-start parameter. `archive_command` and `archive_library` can be changed independently of enabling archive mode.

`wal_level = minimal` cannot support continuous archiving/PITR and cannot be used with `archive_mode` enabled.

## archive_mode Semantics

PostgreSQL 18 supports:

- `off` — archiving disabled
- `on` — completed WAL segments are archived during normal operation
- `always` — archiving also occurs during archive recovery or standby operation

`always` must be designed carefully because WAL restored from archive or received through streaming replication can be archived again. Archive naming, destination design, and duplicate handling must therefore remain safe and deterministic.

## archive_command Architecture

When `archive_library` is empty, PostgreSQL uses `archive_command`.

PostgreSQL substitutes:

- `%p` with the path of the WAL file relative to the cluster data directory
- `%f` with the WAL file name
- `%%` with a literal `%`

The command runs as the operating-system account running PostgreSQL.

### Success Contract

The command must return exit status zero **only after the WAL file has been archived successfully** according to the recovery design.

A zero exit status tells PostgreSQL that the segment is safely archived and may eventually be recycled or removed when no longer otherwise required. A nonzero result causes PostgreSQL to retry periodically.

This makes the archive command's exit status part of PostgreSQL's durability/recovery contract.

## Idempotency and Duplicate Handling

Archive operations must be idempotent.

Retries are normal, and the destination might already contain a file with the same WAL segment name. A production archive implementation should:

1. detect an existing destination object/file;
2. verify that it represents the same WAL content where practical;
3. return success only when the required WAL segment is safely present;
4. never silently overwrite conflicting WAL content.

A duplicate filename with different content is a serious recovery-integrity condition.

## archive_library Architecture

PostgreSQL can use a loadable archive module through `archive_library` instead of executing a shell command.

Archive modules execute inside PostgreSQL's archiving infrastructure and implement defined callbacks. They can provide better integration and performance than shell-based archiving, but native modules also become trusted server dependencies and require the same software-supply-chain, compatibility, testing, and upgrade discipline as other server-side C modules.

`archive_command` and `archive_library` must not both be configured as active archive mechanisms.

## Retry and Failure Behavior

When ordinary archive attempts fail, PostgreSQL continues retrying. The primary can continue processing transactions while completed WAL accumulates in `pg_wal`.

This creates two simultaneous risks:

1. **Recovery risk** — the recoverable WAL archive chain is not advancing.
2. **Capacity risk** — WAL that still requires archiving cannot be recycled solely as though archiving had succeeded, so `pg_wal` can continue growing.

Archive incidents must therefore be treated as both backup/DR incidents and production-capacity incidents.

Certain abnormal archive-command failures can cause the archiver process itself to exit and be restarted by the postmaster. PostgreSQL documentation notes that some such failures are not reflected as ordinary failures in `pg_stat_archiver`, so server logs must always be included in diagnosis.

## Archive Throughput and Backlog

A healthy archive destination is not sufficient if sustained archive throughput is below WAL generation rate.

Operationally:

```text
backlog growth rate ≈ WAL generation rate - successful archive throughput
```

If the value remains positive, the system eventually reaches a storage incident even though individual archive operations might still succeed.

DBRE/SRE monitoring should therefore track both archive errors and archive throughput/capacity trends.

## archive_timeout

Normally a WAL file becomes eligible for archiving after the segment is completed. On low-WAL systems, this can leave a long interval before the current segment is archived.

`archive_timeout` can force periodic WAL segment switches after activity so that WAL reaches archive storage sooner.

It should not be configured unnecessarily low. Forced switches still produce full-sized WAL segment files in archive storage and can significantly increase archive object/file count and storage consumption.

Streaming replication should be used when the requirement is rapid replica transport rather than abusing very short archive timeouts.

## pg_stat_archiver

`pg_stat_archiver` is the primary PostgreSQL statistics view for archive activity.

Important fields include:

- `archived_count`
- `last_archived_wal`
- `last_archived_time`
- `failed_count`
- `last_failed_wal`
- `last_failed_time`
- `stats_reset`

Interpret counters relative to `stats_reset`; absolute values without that context can be misleading.

### Example

```sql
SELECT archived_count,
       last_archived_wal,
       last_archived_time,
       failed_count,
       last_failed_wal,
       last_failed_time,
       stats_reset
FROM pg_stat_archiver;
```

Do not rely on `pg_stat_archiver` alone. Correlate it with PostgreSQL logs, WAL generation, `pg_wal` filesystem usage, archive destination telemetry, and backup/restore validation.

## Monitoring Model

Monitor at minimum:

- archive success/failure rate
- time since last successful archive
- time since last failed archive
- WAL generation rate
- archive throughput
- archive backlog
- `pg_wal` bytes used
- `pg_wal` filesystem free space
- projected time to filesystem exhaustion
- archive destination availability
- archive destination free capacity/quota
- command/module latency
- authentication/credential failures
- backup/PITR restore-test results

For low-activity systems, time since last archive must be correlated with whether new WAL segments actually became eligible for archiving.

## Capacity Alerting

Archive alerting should be multi-dimensional.

### Warning

Examples:

- repeated archive failures
- archive backlog increasing
- archive throughput consistently below WAL generation
- archive destination approaching capacity/quota
- last successful archive older than the workload's expected archive cadence while WAL is being generated

### Critical

Examples:

- sustained archive failure with rapidly growing `pg_wal`
- archive destination unavailable with insufficient local WAL headroom
- projected `pg_wal` filesystem exhaustion inside the incident-response window
- archive chain required for RPO/PITR is no longer advancing

A time-to-exhaustion calculation is more operationally useful than a filesystem-percentage alert alone.

## Relationship to Backups and PITR

Continuous archive recovery combines a base backup with the required WAL sequence.

```text
base backup
   +
continuous WAL archive
   -> recovery to selected point
```

A successful base backup does not prove arbitrary PITR recoverability. The required WAL files must exist, be readable, be ordered correctly, and be replayable.

Archive monitoring is therefore inseparable from backup validation.

The strongest validation is a recurring restore/PITR test into an isolated environment.

## Security Architecture

Archived WAL contains database changes and must be protected as sensitive production data.

Production controls should include:

- encryption in transit where remote transport is used
- encryption at rest
- least-privilege archive credentials
- restricted filesystem/object-store access
- credential rotation
- retention controls
- immutability/object-lock controls where required by policy
- audit logging
- separation between production write access and backup/DR administration where practical

Archive scripts must also protect credentials from process listings, shell history, logs, and world-readable configuration files.

## HA and Standby Considerations

Archiving and streaming replication solve related but different problems.

Streaming replication moves WAL to replicas. Continuous archiving preserves WAL for recovery workflows. A production HA architecture may use both.

When `archive_mode = always` is used on a standby, the team must understand that received/restored WAL can be archived from that standby. Duplicate handling and archive-destination architecture must be validated before enabling this behavior.

Failover procedures must also verify that the promoted server has the intended archive configuration and credentials. HA is incomplete if promotion succeeds but the new primary silently stops advancing the recovery archive.

## Archive Failure Scenarios

### Destination Full

Symptoms:

- archive failures
- growing `pg_wal`
- destination capacity at or near zero

Response:

1. restore destination capacity;
2. verify archive operations resume;
3. monitor backlog drain rate;
4. verify `pg_wal` growth reverses;
5. validate archive continuity.

### Credential or Permission Failure

Symptoms:

- authentication/authorization errors in logs or archive tooling
- repeated archive retries
- increasing WAL backlog

Response:

1. validate credential expiry/rotation;
2. restore least-privilege access;
3. test the archive path safely;
4. verify retries succeed;
5. confirm the backlog drains.

### Network/Object-Store Outage

Treat the archive destination as an external dependency. Measure local WAL headroom against expected outage duration and WAL generation rate.

### Archive Throughput Saturation

If the destination is available but cannot ingest WAL as quickly as PostgreSQL generates it, investigate archive-command serialization, network throughput, storage/object-store latency, compression/encryption overhead, and destination throttling.

### Invalid Archive Command or Library

Configuration changes should be tested in staging and deployed with rollback procedures. Monitor PostgreSQL logs immediately after changing archive behavior.

## Emergency Guardrails

During an archive backlog incident:

**Do not manually delete WAL files from `pg_wal`.**

Manual deletion can destroy crash recovery, replication, backup, or PITR requirements and can make the database unrecoverable.

Instead:

1. reduce avoidable WAL generation if operationally safe;
2. restore archive service/destination capacity;
3. add storage headroom using supported infrastructure procedures when necessary;
4. monitor backlog drain;
5. validate recovery continuity after the incident.

## Troubleshooting Workflow

1. Confirm `archive_mode`, `wal_level`, and active archive mechanism.
2. Inspect `pg_stat_archiver`.
3. Inspect PostgreSQL server logs.
4. Check archive destination health, quota, permissions, credentials, and network path.
5. Measure WAL generation rate.
6. Measure archive success throughput.
7. Measure `pg_wal` usage and free space.
8. Calculate time to exhaustion.
9. Restore the failed archive stage without deleting required WAL.
10. Verify successful retries and backlog reduction.
11. Verify WAL recycling resumes normally.
12. Perform or schedule restore/PITR validation.
13. Document root cause and prevention controls.

## Production Case Study — Archive Destination Full

A PostgreSQL primary continuously generates WAL while its archive filesystem reaches capacity. The archiver begins failing and retries each completed WAL segment. Application traffic remains healthy initially, which causes the incident to be underestimated.

Meanwhile `pg_wal` continues growing. The database is now exposed to both a degraded PITR chain and primary-filesystem exhaustion.

The safe response is to restore archive destination capacity, verify archive retries succeed, measure the backlog drain rate, and confirm `pg_wal` returns to a safe trajectory. Deleting WAL files from the primary is not an acceptable capacity remediation.

## Production Case Study — Successful Backups, Broken Archive Chain

Scheduled base backups report success, but archive credentials expired days earlier. No restore test was running, so the organization assumes PITR is healthy.

A later recovery request discovers that required WAL is missing from the archive destination.

The failure is not merely an archive-script problem; it is an observability and recovery-validation failure. Backup success, archive continuity, and restore testing must be monitored as one recovery system.

## SRE/DBRE Principles

> WAL archiving is a live durability and recovery pipeline. Monitor it like production data movement, not like a passive filesystem copy.

> Archive success is not proven by process presence. Prove forward progress, sustainable throughput, destination durability, local WAL headroom, and successful recovery tests.

> Never solve an archive backlog by manually deleting PostgreSQL-managed WAL files.
