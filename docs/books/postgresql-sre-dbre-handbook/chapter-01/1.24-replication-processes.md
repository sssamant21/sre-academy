# 1.24 — Replication Processes

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

## Purpose

PostgreSQL replication is implemented by cooperating server processes whose roles differ between physical streaming replication and logical replication. This section consolidates the process-level view so DBRE/SRE teams can diagnose replication by process and pipeline stage.

## Physical Replication Processes

```text
PRIMARY
  backend changes
     -> WAL generation
     -> WAL sender
          |
          v
STANDBY
     WAL receiver
          -> WAL storage
          -> startup/recovery process
          -> WAL replay
```

### WAL Sender

A WAL sender runs on the sending server for streaming replication connections. It sends WAL or participates in replication-protocol operations. Sender capacity is governed by replication configuration including `max_wal_senders`.

### WAL Receiver

A standby WAL receiver connects upstream and receives WAL. Its health helps distinguish network/receive problems from replay problems.

### Startup / Recovery Process

During standby recovery, the startup process applies WAL records to advance the standby database state. A standby can therefore receive WAL successfully while replay still falls behind.

## Logical Replication Processes

```text
PUBLISHER
  WAL sender
    -> logical decoding / pgoutput
       -> logical replication stream

SUBSCRIBER
  apply worker
    -> target tables
  + table synchronization workers when required
```

The logical WAL sender decodes WAL according to the publication. Subscriber workers receive and apply changes. Initial synchronization can involve additional table-sync activity.

## Parallel Apply and Worker Capacity

Logical replication worker behavior is version/configuration dependent. Worker availability is part of the shared PostgreSQL worker-capacity model and must be monitored alongside other background/parallel workers.

## Replication Slots

Slots are not processes, but they are tightly coupled to replication-process health. When a consumer process is absent or stalled, the slot can retain WAL. Always correlate worker/process state with slot state and retained WAL.

## Monitoring Process State

Use PostgreSQL statistics views rather than relying only on OS process names:

- `pg_stat_replication`
- `pg_stat_wal_receiver`
- `pg_replication_slots`
- logical subscription statistics/views
- `pg_stat_activity` backend types

Correlate with WAL generation, network, storage, CPU, replay/apply lag, and logs.

## Process-Oriented Diagnostic Model

```text
replication lag
  -> sender healthy?
  -> network flowing?
  -> receiver healthy?
  -> WAL flushed?
  -> recovery/apply worker progressing?
  -> target storage healthy?
  -> slot retention increasing?
```

This prevents the generic and often misleading diagnosis “replication is slow.”

## Failure Scenarios

Important process failures include WAL sender unavailable, authentication/configuration preventing receiver connection, receiver repeatedly reconnecting, startup/recovery replay stalled, logical apply worker stopped by conflict, worker-capacity exhaustion, and process absence combined with growing slot retention.

## Troubleshooting Workflow

1. Identify replication type: physical or logical.
2. Identify expected sender/receiver/apply processes.
3. Inspect PostgreSQL replication views and logs.
4. Locate the exact pipeline stage where progress stops.
5. Check slot retention and primary WAL headroom.
6. Check network, target storage, CPU, and worker availability.
7. Restore the failed stage using supported PostgreSQL mechanisms.
8. Verify lag decreases and retained WAL is released safely.

## Production Case Study — Connected but Not Replaying

A standby WAL receiver remains connected and the primary WAL sender reports normal streaming. Replay lag continues growing. Process-level diagnosis shows receive progress advancing while replay does not. This focuses investigation on standby recovery conflicts, storage/replay capacity, or startup-process state rather than the network connection.

## Chapter 1 Process Map

```text
postgres server
  |
  +-- client backends
  +-- checkpointer
  +-- background writer
  +-- WAL writer
  +-- autovacuum launcher/workers
  +-- archiver
  +-- startup/recovery
  +-- WAL sender(s)
  +-- WAL receiver
  +-- logical replication workers
  +-- parallel workers
  +-- extension/background workers
```

Together with memory, storage, WAL, MVCC, locking, vacuum, and recovery architecture, these processes form the operational core of PostgreSQL.

## SRE/DBRE Principle

> Diagnose replication as cooperating processes and WAL positions. Process presence alone does not prove progress; measure send, receive, flush, replay/apply, and retention.
