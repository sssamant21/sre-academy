# 1.24 — Replication Processes

**Status:** Technical Review Complete → Production Review Pending  
**Validation baseline:** PostgreSQL 18.4 official documentation

## Purpose

PostgreSQL replication is implemented by cooperating processes whose roles differ across physical streaming replication and logical replication. SRE/DBRE diagnosis should identify the exact process and WAL/progress stage that has stopped advancing rather than treating all replication lag as one failure mode.

## Physical Streaming Replication Process Architecture

```text
PRIMARY
application backend
      |
      v
WAL generation / flush
      |
      v
WAL sender (walsender)
      |
      | replication protocol / COPY stream
      v
STANDBY
WAL receiver (walreceiver)
      |
      v
pg_wal write + flush
      |
      v
startup / recovery process
      |
      v
WAL replay -> standby data state
```

### WAL Sender

A WAL sender is created on the sending server for a replication connection. It is similar to a normal backend in that one sender corresponds to one replication connection, but it executes replication-protocol commands rather than ordinary SQL. `START_REPLICATION` begins WAL streaming.

`max_wal_senders` limits concurrent WAL sender processes. Capacity must include physical standbys, logical replication connections, base-backup/replication-protocol requirements where applicable, and operational headroom for reconnects.

Monitor physical senders with `pg_stat_replication`, including `sent_lsn`, `write_lsn`, `flush_lsn`, `replay_lsn`, sender state, sync state, and reply timing.

### WAL Receiver

The WAL receiver is an auxiliary process on a physical standby. The startup process requests it when streaming is needed. The receiver connects to the upstream server, receives WAL, writes it into the standby's WAL storage, flushes progress, and communicates receive state through shared memory.

`pg_stat_wal_receiver` exposes receiver connection and streaming state. A healthy receiver proves that WAL is arriving; it does not prove that replay is keeping pace.

### Startup / Recovery Process

The startup process performs recovery and WAL replay. On a standby, it applies available WAL records to advance database state. This creates an essential diagnostic distinction:

```text
receive lag != replay lag
```

A standby can receive and flush WAL quickly while replay remains delayed by storage throughput, CPU, recovery conflicts, replay workload, or other standby conditions.

## Physical Replication Feedback Path

The standby periodically reports write, flush, and replay progress to the sender. These positions support replication monitoring and synchronous replication behavior.

Operationally, measure the pipeline as separate stages:

```text
primary current WAL
   -> sent
   -> standby received/written
   -> standby flushed
   -> standby replayed
```

The difference between adjacent stages is more useful than one generic lag number because it identifies where the backlog resides.

## Cascading Replication

A cascading standby acts in both directions: it runs a WAL receiver from its upstream server and WAL sender processes for downstream standbys. Failure or resource pressure on an intermediate standby can therefore affect an entire downstream replication tree.

Monitor cascading nodes as both consumers and producers.

## Logical Replication Process Architecture

```text
PUBLISHER
WAL
 |
 v
WAL sender
 |
 +--> logical decoding
      |
      +--> publication filtering / output plugin
             |
             v
SUBSCRIBER
logical replication launcher
      |
      +--> apply worker
      +--> table synchronization worker(s)
      +--> parallel apply workers when used
             |
             v
        target tables
```

Logical replication does not use the physical standby WAL receiver process for subscription apply. The publisher uses a WAL sender in logical replication mode, while subscriber-side logical replication workers receive and apply logical changes.

### Logical Replication Launcher

The logical replication launcher coordinates subscription workers on the subscriber. Logical worker capacity is governed by settings such as `max_logical_replication_workers` and is also constrained by the broader background-worker capacity controlled by `max_worker_processes`.

### Apply Worker

The apply worker handles the subscription's ongoing logical change stream and applies transactions to subscriber tables. Apply errors, schema incompatibility, replica-identity problems, constraint conflicts, or resource exhaustion can stop progress even when the publisher-side sender remains healthy.

### Table Synchronization Workers

Initial table synchronization can use table-sync workers to copy existing table contents while the subscription establishes consistent ongoing replication. Initial-copy failures should therefore be distinguished from steady-state apply failures.

### Parallel Apply

PostgreSQL can use parallel apply workers for suitable logical replication transactions/configurations. Parallel apply consumes additional worker capacity. SRE capacity models should treat logical replication workers as part of the shared PostgreSQL process budget rather than assuming replication capacity is isolated from other background-worker demand.

## Replication Slots and Process Health

Replication slots are persistent state, not server processes, but their operational behavior is inseparable from consumer health. When the consumer process is disconnected, stopped, or unable to advance, the slot can retain WAL on the publisher.

Monitor:

- slot `active` state;
- `restart_lsn`;
- `confirmed_flush_lsn` for logical slots;
- `wal_status`;
- `safe_wal_size` where available;
- `xmin` and `catalog_xmin` horizons;
- retained WAL and `pg_wal` filesystem headroom.

A missing consumer plus growing slot retention is a source-cluster capacity incident, not merely a replication incident.

## Process and View Mapping

| Replication stage | Primary PostgreSQL observability |
|---|---|
| Physical sender | `pg_stat_replication` |
| Physical receiver | `pg_stat_wal_receiver` |
| Slot retention | `pg_replication_slots` |
| Recovery/replay | recovery functions, WAL positions, `pg_stat_activity`/logs |
| Logical subscription workers | `pg_stat_subscription` and related subscription views |
| Logical subscription errors/conflicts | subscription statistics and PostgreSQL logs |
| Backend/process classification | `pg_stat_activity.backend_type` |

Use OS process inspection as supporting evidence, not as the source of truth for replication progress.

## Monitoring Model

For physical replication, continuously observe:

- current primary WAL position;
- sender state and WAL positions;
- network/reply health;
- receiver state;
- receive/write/flush/replay positions;
- replay timestamp lag where meaningful;
- replication-slot retention;
- standby storage latency and CPU;
- recovery conflicts.

For logical replication, observe:

- subscription worker presence/state;
- publisher slot activity and retained WAL;
- latest received/applied progress;
- table synchronization state;
- apply errors/conflicts;
- subscriber CPU/storage capacity;
- worker-pool saturation.

## Alerting

Alert on lack of **progress**, not process existence alone.

Useful conditions include:

- sender/receiver disconnected beyond expected reconnect tolerance;
- receive position stops advancing while primary WAL continues growing;
- receive advances but replay does not;
- logical apply stops advancing;
- slot retained WAL grows toward capacity limits;
- expected workers cannot start because worker pools are exhausted;
- repeated replication reconnects or authentication failures;
- synchronous replication waits threaten application availability.

Lag thresholds should reflect workload RPO/RTO requirements and WAL generation rate.

## Failure Scenarios

### WAL Sender Capacity Exhausted

A new standby or logical consumer cannot establish replication because sender capacity is exhausted. Check `max_wal_senders`, current sender usage, backup/replication connections, and reconnect behavior before increasing the limit.

### WAL Receiver Reconnect Loop

The standby repeatedly reconnects due to authentication, TLS, DNS/network, upstream availability, timeline, or configuration problems. Diagnose receiver logs and connection configuration rather than rebuilding the standby immediately.

### Receive Healthy, Replay Stalled

`pg_stat_wal_receiver` shows incoming WAL and receive/flush progress, while replay lag grows. Investigate startup/recovery progress, storage latency, CPU, recovery conflicts, and replay workload.

### Logical Apply Worker Stopped

The publisher slot remains active or retains WAL, but the subscriber apply worker has failed because of a constraint conflict, missing relation/schema mismatch, replica identity issue, or worker/resource failure. Fix the root cause and validate consistency before recreating subscription state.

### Slot Retention During Consumer Outage

A consumer is intentionally offline, but its slot retains WAL until source storage approaches exhaustion. The outage window must be bounded by WAL generation rate and source WAL capacity.

### Cascading Standby Failure

An intermediate standby stops receiving or sending WAL. Downstream replicas lag even though the primary itself is healthy. Treat the intermediate node as both a replication target and a replication source during diagnosis.

## Troubleshooting and Recovery Workflow

1. Identify replication type: physical or logical.
2. Identify expected sender, receiver, recovery, launcher, apply, and synchronization processes.
3. Verify process/backend state through PostgreSQL statistics views.
4. Compare WAL/progress positions to locate the exact stalled stage.
5. Inspect replication slots and retained-WAL headroom.
6. Check PostgreSQL logs for authentication, protocol, timeline, conflict, schema, or worker errors.
7. Check network path, CPU, storage latency/throughput, memory, and worker capacity.
8. Correct the failed stage using supported PostgreSQL mechanisms.
9. Verify that the relevant positions begin advancing again.
10. Confirm lag and retained WAL decrease at a sustainable rate.
11. Validate RPO/RTO and redundancy after recovery.

## Automation and Production Guardrails

Automated health checks should distinguish at least:

```text
sender availability
receiver availability
receive progress
flush progress
replay/apply progress
slot retention
worker capacity
source/target storage headroom
```

Do not automatically drop replication slots, terminate replication processes, promote standbys, or rebuild subscribers solely because lag crosses a threshold. Those actions can affect durability, data consistency, or HA topology and require context-aware runbooks.

## Production Case Study — Connected but Not Replaying

A standby's WAL receiver remains connected and the primary WAL sender continues streaming. Monitoring based only on connection state reports the replica as healthy, but replay lag grows continuously.

Stage-by-stage WAL-position analysis shows that receive and flush positions advance while replay does not. Investigation therefore shifts away from networking toward standby recovery: storage latency, startup-process progress, recovery conflicts, and replay capacity. This shortens diagnosis and avoids an unnecessary replica rebuild.

## SRE/DBRE Principle

> Diagnose replication as a pipeline of cooperating processes and progress positions. A process can be alive while replication is stalled; health means WAL or logical progress is advancing safely and retained state remains within capacity.
