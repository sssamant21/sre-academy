# Chapter 1 — PostgreSQL Architecture and Internals

## 1.3 — PostgreSQL Backend Process Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.3.1 Purpose

A PostgreSQL backend process is the server-side execution context for a client session. PostgreSQL uses a process-per-connection architecture: the supervising `postgres` process accepts connection requests and creates a dedicated backend for each normal client connection. After connection establishment, the client communicates directly with its backend for ordinary protocol and SQL processing.

```text
Client A <----> Backend PID A --\
Client B <----> Backend PID B ----+--> Shared PostgreSQL state
Client C <----> Backend PID C --/      + shared buffers
                                      + WAL buffers
                                      + locks / synchronization
                                      + shared statistics/state
```

For SRE/DBRE work, a backend must be understood simultaneously as a database session, operating-system process, transaction participant, memory consumer, lock participant, and I/O consumer.

## 1.3.2 Backend Lifecycle

A simplified lifecycle is:

```text
connection request
  -> backend created
  -> authentication / startup negotiation
  -> session established
  -> protocol messages
  -> transactions and SQL execution
  -> client disconnect / administrative termination
  -> backend exits
```

The backend normally exists for the lifetime of the client connection and can execute many transactions during that lifetime. Backend lifetime and transaction lifetime are therefore different operational dimensions.

## 1.3.3 Backend Responsibilities

A client backend can perform or coordinate:

- frontend/backend protocol processing
- authentication/session initialization
- parsing, rewriting, planning, and execution
- transaction and MVCC participation
- lock acquisition and waiting
- shared-buffer access
- private-memory allocation
- temporary-file I/O
- WAL generation for changes that require WAL
- result/error delivery to the client

The backend is not merely a socket handler; it is the primary execution environment for the client session.

## 1.3.4 Backend Identity and `pg_stat_activity`

PostgreSQL 18 exposes one row per server process in `pg_stat_activity`. For client backends, important fields include `pid`, database/user/application identity, connection timestamps, transaction/query timestamps, state, wait events, transaction identifiers/horizons, and query information. The `backend_type` field distinguishes client backends from auxiliary and worker processes.

```sql
SELECT
    pid,
    backend_type,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    backend_xid,
    backend_xmin,
    query_id,
    query
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY backend_start;
```

`query_id` is not necessarily populated: PostgreSQL does not compute query identifiers by default unless `compute_query_id` is enabled or another module supplies them.

## 1.3.5 Backend States

For client backends, `pg_stat_activity.state` can report states including:

- `active`
- `idle`
- `idle in transaction`
- `idle in transaction (aborted)`
- `fastpath function call`
- `disabled`

`active` does not mean the process is consuming CPU. An active backend can be waiting on a lock, I/O, IPC, a timeout, or another wait event. Always interpret `state` together with `wait_event_type` and `wait_event`.

## 1.3.6 Idle vs Idle in Transaction

```text
idle
  -> waiting for a new client command
  -> no open transaction implied

idle in transaction
  -> waiting for a client command
  -> transaction remains open
```

Long-lived idle-in-transaction sessions can retain locks and old transaction horizons and can delay cleanup of obsolete row versions. Dashboards must therefore separate ordinary idle sessions from idle-in-transaction sessions.

`idle_in_transaction_session_timeout` can be a useful guardrail, but it must be introduced with application-aware testing rather than used as a substitute for correct transaction handling.

## 1.3.7 Backend Wait Events

Wait events are a primary diagnostic signal.

```sql
SELECT
    wait_event_type,
    wait_event,
    count(*) AS backends
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND wait_event IS NOT NULL
GROUP BY wait_event_type, wait_event
ORDER BY backends DESC;
```

A latency incident with many active backends and low CPU may be a lock, I/O, client, or IPC wait problem rather than insufficient compute capacity.

## 1.3.8 Backend PID as the Correlation Key

The backend PID connects database and operating-system evidence:

```text
PID
 +-- pg_stat_activity
 +-- pg_locks
 +-- PostgreSQL log_line_prefix / logs
 +-- pg_stat_io backend type context
 +-- OS CPU / RSS / scheduling / open files
 +-- administrative cancellation or termination
```

Meaningful `application_name` values make this correlation far more useful during incidents.

## 1.3.9 Backend Private Memory

Each backend has private process memory in addition to PostgreSQL shared memory. PostgreSQL organizes allocations through memory contexts.

The current session can inspect its own contexts with `pg_backend_memory_contexts`:

```sql
SELECT name, ident, type, level,
       total_bytes, free_bytes, used_bytes
FROM pg_backend_memory_contexts
ORDER BY total_bytes DESC;
```

For another backend, `pg_log_backend_memory_contexts(pid)` can request that the target backend log its memory contexts. Use it deliberately: it can produce substantial log output.

## 1.3.10 Query Memory Is Operation- and Concurrency-Dependent

`work_mem` is a base limit for individual query operations such as sorts and hash tables before temporary-file spilling. A complex query can have several memory-consuming operations, and many sessions can execute them concurrently. Hash operations can use a limit derived from `work_mem * hash_mem_multiplier`.

Parallel query further multiplies resource demand because parallel workers are separate processes and applicable resource limits are generally applied to each worker.

Therefore this model is unsafe:

```text
RAM - shared_buffers = safe work_mem pool
```

Use a concurrency-aware model instead:

```text
active sessions
  x memory-consuming plan nodes
  x worker multiplicity
  x workload mix
  + backend/session overhead
  + maintenance/replication/extension memory
  + OS headroom
```

Do not raise `work_mem` globally to solve one spilling query without modeling aggregate memory risk.

## 1.3.11 Temporary Buffers and Temporary Files

`temp_buffers` is session-local memory used for temporary tables and is allocated as needed. Query execution can also create temporary files for operations such as sorts and hashes that exceed their in-memory limits.

These are distinct concepts. `temp_file_limit` limits temporary-file space used by an individual PostgreSQL process for supported temporary-file categories; it does not limit disk space occupied by explicit temporary tables.

Backend troubleshooting should therefore distinguish private memory, temporary buffers, and temporary-file I/O.

## 1.3.12 Backend and Query Processing

A backend's SQL path is conceptually:

```text
frontend message
   -> parse
   -> analyze / rewrite
   -> plan / optimize
   -> execute
   -> results / command completion
```

Prepared statements and the extended query protocol can separate parse/bind/execute phases and allow plan reuse. The complete query-processing architecture is covered later in Chapter 1; this section focuses on the backend as the process in which those stages execute.

## 1.3.13 Backend and Transactions

A long-lived backend can execute many transactions:

```text
backend lifetime
  +-- transaction 1 -> COMMIT
  +-- transaction 2 -> ROLLBACK
  +-- transaction 3 -> COMMIT
```

Operational monitoring must therefore track at least `backend_start`, `xact_start`, and `query_start` independently. A connection can be old but healthy; a transaction that is unexpectedly old can be dangerous even if the connection itself is expected to be persistent.

## 1.3.14 Backend and MVCC Horizons

`backend_xid` identifies the backend's top-level transaction ID when present, while `backend_xmin` exposes the backend's current xmin horizon. These fields are useful during vacuum, bloat, and transaction-age investigations because a backend can contribute to retention of older tuple visibility requirements.

Do not terminate a backend solely because `backend_xmin` is present. Correlate transaction age, workload purpose, vacuum impact, locks, and business consequences.

## 1.3.15 Backend and Locking

A backend can hold locks while executing or while waiting for its client. Use `pg_blocking_pids()` to identify blockers before escalating to termination.

```sql
SELECT
    pid,
    application_name,
    state,
    xact_start,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blocking_pids,
    query
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND cardinality(pg_blocking_pids(pid)) > 0;
```

A blocking chain should be traced to its root blocker; killing downstream waiters usually does not remove the cause.

## 1.3.16 Connection Capacity and Backend Multiplication

Every direct client connection creates a backend process, so connection demand affects process count, memory, scheduling, file descriptors, and shared PostgreSQL structures. PostgreSQL's official guidance notes that excessive connections can contribute to memory pressure and that reducing `max_connections` and using external pooling can be preferable in appropriate workloads.

Capacity planning should include:

- peak and steady-state connections
- application autoscaling multiplier
- connection-pool sizes
- administrative/reserved access
- backend private memory
- concurrent query memory
- parallel workers
- host/container process and memory limits

## 1.3.17 Production Failure Pattern — Connection Storm

```text
application scale-out / restart
   -> simultaneous connection attempts
   -> rapid backend creation
   -> authentication + process + memory pressure
   -> connection/latency failures
   -> application retries
   -> larger storm
```

The durable fix is demand control: pool sizing, retry backoff/jitter, connection budgeting, and database capacity engineering. Raising `max_connections` alone can increase the failure domain.

## 1.3.18 Production Failure Pattern — Backend Memory Pressure

Many concurrent backends executing sort/hash-heavy plans can drive aggregate memory far beyond what a single `work_mem` value suggests. Parallel workers can amplify the effect further.

Symptoms can include host/container memory pressure, swapping where enabled, kernel OOM intervention, backend/server disruption, and severe latency.

Investigation should correlate active session count, plans, `work_mem`, `hash_mem_multiplier`, parallelism, OS RSS, container limits, and temporary-file activity.

## 1.3.19 Linux OOM Risk

On Linux, host memory overcommit and the OOM killer are part of PostgreSQL reliability engineering. PostgreSQL documentation recommends addressing PostgreSQL-caused memory pressure through configuration—including memory parameters and connection count—and discusses stricter kernel overcommit as an option for reducing OOM risk.

Containerized PostgreSQL additionally requires awareness of cgroup/container memory limits; a host with free memory does not guarantee the PostgreSQL container has remaining memory headroom.

## 1.3.20 Safe Backend Intervention

Prefer PostgreSQL administrative functions to arbitrary OS signals:

```sql
SELECT pg_cancel_backend(<pid>);
SELECT pg_terminate_backend(<pid>);
```

`pg_cancel_backend()` requests cancellation of the current query. `pg_terminate_backend()` terminates the session. Privilege rules apply.

Before terminating a production backend, capture enough evidence to identify ownership, transaction state, blocking relationships, SQL, and business impact. Termination is incident mitigation, not root-cause remediation.

## 1.3.21 Monitoring Strategy

Track and trend:

- total client backends
- connection utilization and connection rate
- active / idle / idle-in-transaction counts
- oldest transaction and query ages
- wait-event distribution
- blockers and blocked-session counts
- `backend_xmin`/old transaction horizons during vacuum incidents
- application/user/database distribution
- host/container RSS and memory pressure
- temporary-file generation
- CPU/run-queue pressure
- backend termination and crash events

Do not reduce backend health to one metric such as connection percentage or active-session count.

## 1.3.22 Alerting Strategy

Useful alerts include sustained connection saturation, connection-rate anomalies, idle-in-transaction age, transaction-age breaches, blocking chains affecting SLOs, abnormal wait concentration, temporary-file surges, and host/container memory pressure.

Thresholds should be based on workload baselines, SLO impact, and remaining recovery headroom rather than universal fixed values.

## 1.3.23 Troubleshooting Workflow

```text
DB latency / connection incident
  -> identify client backend population
  -> group by application, user, database, state
  -> inspect transaction/query age
  -> inspect wait events
  -> identify blockers
  -> inspect memory and temp I/O
  -> correlate PID with OS/container telemetry
  -> identify workload owner and root cause
  -> mitigate safely
  -> verify recovery
```

Useful first-pass query:

```sql
SELECT
    application_name,
    state,
    wait_event_type,
    count(*) AS sessions,
    max(now() - xact_start) FILTER (WHERE xact_start IS NOT NULL) AS oldest_xact
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY application_name, state, wait_event_type
ORDER BY sessions DESC;
```

## 1.3.24 Production Case Study — Kubernetes Pool Multiplication

An application scales from 20 to 60 pods. Each pod is configured for a 100-connection pool, creating a theoretical demand of 6,000 sessions even though workload throughput did not triple proportionally.

The database approaches its connection limit and memory/scheduling overhead rises.

**Root cause:** database connection capacity was planned per pod rather than across the entire autoscaled fleet.

**Corrective actions:** establish a global connection budget, right-size per-pod pools, use pooling where appropriate, preserve administrative headroom, implement retry backoff, and load-test autoscaling events.

**Reliability lesson:** application horizontal scaling and PostgreSQL backend scaling are coupled capacity dimensions.

## 1.3.25 Production Case Study — Forgotten Transaction

An application error path leaves a backend idle in transaction for hours. Vacuum cleanup is delayed and locks may remain held. Operators repeatedly terminate the session, but the condition returns.

**Root cause:** defective application transaction lifecycle handling.

**Corrective actions:** fix commit/rollback handling, use meaningful `application_name`, add transaction-age alerting, evaluate `idle_in_transaction_session_timeout`, and preserve diagnostic evidence before emergency termination.

**Reliability lesson:** the backend is often the visible endpoint of an application lifecycle defect; durable remediation must fix the session owner.

## 1.3.26 SRE/DBRE Best Practices

1. Treat backend count as a finite capacity dimension.
2. Separate connection age, transaction age, and query age.
3. Separate idle from idle-in-transaction sessions.
4. Use `backend_type` when classifying `pg_stat_activity` rows.
5. Use wait events before assuming active sessions are CPU-bound.
6. Tag connections with meaningful `application_name` values.
7. Trace blocking chains to the root blocker.
8. Model `work_mem` and hash memory at workload concurrency, not session count alone.
9. Include parallel workers in memory and CPU capacity models.
10. Monitor temporary-file I/O as well as backend RSS.
11. Maintain a global application connection budget.
12. Load-test connection storms and autoscaling events.
13. Prefer pooling over simply increasing `max_connections` when architecture warrants it.
14. Use PostgreSQL cancellation/termination functions for controlled intervention.
15. Treat recurring backend problems as application, query, or capacity defects requiring RCA.

## 1.3.28 Section Summary

A PostgreSQL client backend is a dedicated operating-system process that executes work for one client session while coordinating through PostgreSQL shared state. Backend health cannot be understood from connection count alone: state, transaction age, query age, wait events, locks, private memory, temporary I/O, application ownership, and OS/container resources must be correlated.

### SRE/DBRE Principle

> Treat every PostgreSQL backend as part of an end-to-end session and resource lifecycle. Diagnose what the process is doing, waiting for, retaining, and consuming before deciding how to remediate it.
