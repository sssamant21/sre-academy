## 1.3.1 Purpose

PostgreSQL uses a process-per-connection server architecture. The primary `postgres` server process listens for client connections and creates a dedicated backend server process for each accepted client session. Once established, the client communicates with its backend without the primary server process mediating ordinary SQL requests.

```text
                         postgres
                    primary server process
                             |
               +-------------+-------------+
               |             |             |
               v             v             v
           Backend 1     Backend 2     Backend 3
               |             |             |
               v             v             v
           Client A      Client B      Client C
```

This process model is fundamental to PostgreSQL capacity planning, connection management, memory behavior, troubleshooting, observability, and failure isolation.

## 1.3.2 Backend Process Lifecycle

A simplified client-session lifecycle is:

```text
Client connection request
          |
          v
Primary postgres accepts connection
          |
          v
Dedicated backend process created
          |
          v
Authentication / session establishment
          |
          v
SQL request processing
          |
          v
Transaction / query activity
          |
          v
Client disconnects
          |
          v
Backend exits
```

The backend exists for the lifetime of the client connection.

## 1.3.3 Backend Responsibilities

A client backend performs database work on behalf of its session. Its responsibilities include processing frontend/backend protocol messages, parsing and planning SQL as required, executing statements, participating in transactions and locking, accessing shared buffers and shared server state, generating WAL for applicable changes, and returning results or errors to the client.

The backend is therefore not simply a network connection handler. It is a complete PostgreSQL execution context for the client session.

## 1.3.4 Backend and Shared Memory

Backends are separate operating-system processes, but PostgreSQL is not a set of isolated databases per connection. Backends cooperate through PostgreSQL shared memory and synchronization mechanisms.

```text
 Backend A ----+
 Backend B ----+----> Shared PostgreSQL State
 Backend C ----+          |
                          +-- Shared Buffers
                          +-- WAL Buffers
                          +-- Locks / synchronization
                          +-- Shared statistics/state
```

This architecture provides process isolation while still allowing sessions to operate on the same database cluster safely and concurrently.

## 1.3.5 Backend Private Memory

Each backend also maintains process-private memory. PostgreSQL organizes much of this memory through memory contexts whose lifetimes can correspond to operations such as a session, transaction, query, or executor activity.

PostgreSQL exposes the current session's backend memory contexts through `pg_backend_memory_contexts`.

```sql
SELECT
    name,
    type,
    level,
    total_bytes,
    free_bytes,
    used_bytes
FROM pg_backend_memory_contexts
ORDER BY total_bytes DESC;
```

Because private memory is multiplied across active processes, connection count and per-query memory settings must be capacity-planned together.

## 1.3.6 Backend Resource Multiplication

A common production mistake is to evaluate memory parameters as though only one query or one backend will use them.

Conceptually:

```text
Per-backend memory
       x
Concurrent active backends
       x
Memory-consuming operations per query
       =
Potential aggregate memory pressure
```

This is particularly important for sort, hash, maintenance, and parallel-processing workloads. The exact memory behavior depends on workload and execution plans, so SRE capacity planning must use concurrency-aware models rather than simple parameter multiplication alone.

## 1.3.7 Backend States

Backend activity is visible through `pg_stat_activity`.

Common session states include active, idle, idle in transaction, idle in transaction (aborted), and disabled where applicable.

A practical query is:

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
ORDER BY backend_start;
```

Backend state must be interpreted together with transaction age, query age, and wait events.

## 1.3.8 Idle vs Idle in Transaction

These two states have very different operational meanings.

```text
idle
  -> backend is waiting for another client command

idle in transaction
  -> transaction remains open while backend waits for client
```

Long-lived idle-in-transaction sessions can retain transaction snapshots, hold locks, interfere with vacuum cleanup, increase bloat risk, and create operational instability.

Therefore an SRE dashboard should never combine all non-active sessions into a generic "idle connections" metric.

## 1.3.9 Backend Wait Events

A backend can be active from the application's perspective while waiting internally for another resource.

Examples of wait categories include locks, lightweight locks, I/O, client activity, IPC, timeout, and other PostgreSQL-defined wait-event classes.

```sql
SELECT
    wait_event_type,
    wait_event,
    count(*) AS sessions
FROM pg_stat_activity
WHERE wait_event IS NOT NULL
GROUP BY wait_event_type, wait_event
ORDER BY sessions DESC;
```

Wait-event analysis is one of the most useful ways to distinguish CPU execution from blocked or stalled backend activity.

## 1.3.10 Backend Process Titles

On supported Unix-like systems PostgreSQL updates process titles so operating-system tools such as `ps` can identify server processes and client-session activity.

Typical process information can expose the database user, database, client host, and current activity. This gives DBRE teams a valuable correlation path between SQL-level telemetry and operating-system process telemetry.

## 1.3.11 Backend PID as an Operational Identifier

Each backend has an operating-system process ID exposed as `pid` in PostgreSQL monitoring views.

This allows correlation across:

```text
pg_stat_activity
       |
       +--> PostgreSQL logs
       +--> pg_locks
       +--> OS process metrics
       +--> tracing / monitoring
       +--> administrative actions
```

The PID is therefore an important troubleshooting key.

## 1.3.12 Backend and Transactions

A backend executes transactions for its client session.

```text
Backend
   |
   +-- BEGIN
   |     |
   |     +-- statements
   |     +-- locks
   |     +-- MVCC snapshot/state
   |     +-- WAL generation where required
   |
   +-- COMMIT / ROLLBACK
```

Transaction lifetime is not the same as backend lifetime. A backend can execute many transactions over a single long-lived connection.

## 1.3.13 Backend and Locking

Backends acquire PostgreSQL locks as needed. A backend waiting for another transaction can create a blocking chain.

```text
Backend A
   |
   +-- holds lock
           |
           v
       Backend B waits
           |
           v
       Backend C waits
```

A single forgotten transaction can therefore affect many otherwise healthy backend processes.

## 1.3.14 Backend and Query Execution

Within a backend, query processing conceptually follows:

```text
Frontend protocol message
        |
        v
SQL processing
        |
        +-- Parse
        +-- Rewrite
        +-- Plan / Optimize
        +-- Execute
        |
        v
Result / command status
        |
        v
Frontend
```

Prepared statements and extended-query protocol behavior can alter which stages are repeated for subsequent executions, but the backend remains the session's server-side execution context.

## 1.3.15 Frontend/Backend Protocol

PostgreSQL uses a message-based frontend/backend protocol over TCP/IP and Unix-domain sockets. PostgreSQL 18 documents protocol version 3.2 while retaining compatibility with protocol 3.0 clients.

For SREs, the important architectural principle is:

```text
Client / Frontend
       |
       | PostgreSQL protocol
       v
Backend / Server Process
```

Network connectivity, authentication, protocol behavior, backend availability, and SQL execution are separate stages of the connection path.

## 1.3.16 Connection Capacity

Because PostgreSQL uses a backend process per normal client connection, connection limits influence operating-system process count and database resource consumption.

A high `max_connections` value is not free capacity.

Production sizing should consider:

- backend process overhead
- private backend memory
- shared-memory structures
- file descriptors
- CPU scheduling
- lock and transaction state
- application connection behavior
- reserved administrative capacity
- background and worker processes

Connection pooling is often preferable to allowing an application fleet to create an unbounded number of direct PostgreSQL sessions.

## 1.3.17 Connection Storm Failure Scenario

A common failure pattern is:

```text
Application restart / traffic spike
            |
            v
Thousands of connection attempts
            |
            v
Rapid backend creation
            |
            +--> CPU scheduling pressure
            +--> authentication overhead
            +--> memory growth
            +--> connection-slot exhaustion
            |
            v
Database latency increases
            |
            v
Application retries
            |
            +------------------+
                               |
                               v
                         Storm worsens
```

This is a feedback loop. Raising `max_connections` without controlling client behavior can increase the blast radius rather than solve the underlying problem.

## 1.3.18 Failure Scenario — Idle in Transaction

An application begins a transaction and then stops issuing SQL while leaving the connection open.

```text
BEGIN
  |
  +-- query
  |
  +-- application pauses
          |
          v
   idle in transaction
          |
          +-- transaction remains open
          +-- locks may remain
          +-- old snapshot/horizon may remain relevant
          |
          v
   vacuum / concurrency impact
```

Operational response should identify the application and root cause rather than simply terminating sessions repeatedly.

## 1.3.19 Failure Scenario — Blocking Backend

Symptoms may include many active application requests but low CPU utilization.

Investigation finds one backend holding a lock while many others wait.

The correct interpretation is not "PostgreSQL needs more CPU." The bottleneck is concurrency control.

Useful investigation should correlate `pg_stat_activity`, `pg_locks`, transaction age, wait events, and application ownership.

## 1.3.20 Failure Scenario — Backend Memory Pressure

A workload can create many simultaneously active backends executing memory-intensive plans.

```text
High connection concurrency
          +
Sort/hash-heavy plans
          +
Large per-operation memory
          |
          v
Aggregate process memory growth
          |
          v
OS memory pressure / swapping / OOM risk
```

The remediation is workload- and plan-aware capacity control, not simply increasing PostgreSQL memory parameters.

## 1.3.21 Monitoring Strategy

Production monitoring should include:

- total backends
- active backends
- idle backends
- idle-in-transaction backends
- oldest transaction age
- oldest query age
- backend creation/connection rate
- wait-event distribution
- blocking chains
- connection utilization versus configured limits
- per-process and instance memory pressure
- CPU and run-queue pressure
- application-name distribution

Metrics should be segmented by database, user, application, and workload where useful.

## 1.3.22 Alerting Strategy

Useful alerts include sustained connection utilization near operational limits, abnormal connection-rate spikes, long-running idle-in-transaction sessions, long-running transactions, severe blocking chains, unusual wait-event concentration, and host memory pressure associated with backend concurrency.

Thresholds should be derived from production baselines and SLO impact rather than universal fixed numbers.

## 1.3.23 Troubleshooting Workflow

```text
Application reports DB problem
          |
          v
Check connection utilization
          |
          v
Classify backend states
          |
          v
Check transaction/query age
          |
          v
Check wait events
          |
          v
Check blocking relationships
          |
          v
Check CPU / memory / OS process pressure
          |
          v
Correlate by application/user/database
          |
          v
Identify root cause
```

This workflow prevents a common operational mistake: treating every session problem as a query-performance problem.

## 1.3.24 Recovery and Remediation

Possible remediation actions depend on the diagnosed failure and can include fixing application connection leaks, correcting transaction handling, tuning connection pools, enforcing appropriate session or transaction timeouts, terminating a confirmed harmful backend under an approved incident procedure, fixing blocking application logic, or resizing infrastructure when genuine capacity limits are reached.

Administrative termination should be treated as incident mitigation, not as a substitute for correcting the root cause.

## 1.3.25 Automation

Useful DBRE automation can continuously classify backend states, identify oldest transactions, detect idle-in-transaction sessions, build blocking trees, track connection utilization, calculate connection churn, correlate application names with incidents, and preserve diagnostic snapshots before remediation.

Automation should produce actionable context rather than a generic "too many connections" alert.

## 1.3.26 Production Case Study — Connection Pool Misconfiguration

An application deployment increases every pod's database pool from 20 to 100 connections. With 60 application pods, theoretical demand rises from 1,200 to 6,000 connections.

PostgreSQL begins experiencing connection saturation and host resource pressure even though normal query throughput has not increased proportionally.

### Root cause

Connection capacity was planned per application instance rather than globally across the application fleet.

### Corrective actions

- reduce per-pod pool size
- define a global connection budget
- reserve administrative connections
- monitor pool wait time and PostgreSQL session count together
- load-test deployment scaling behavior

### Reliability lesson

> PostgreSQL connection capacity must be planned across the complete application fleet, not independently by each service or pod.

## 1.3.27 Production Case Study — Forgotten Transaction Blocks Maintenance

A backend remains idle in transaction for hours after an application error path fails to commit or roll back.

The session retains transaction state and contributes to cleanup/concurrency problems. Operators repeatedly terminate the session, but it returns after the next application error.

### Root cause

Application transaction lifecycle handling is defective.

### Corrective actions

- repair application transaction handling
- add appropriate transaction/session guardrails
- alert on transaction age
- tag connections with meaningful `application_name`
- preserve evidence before termination

### Reliability lesson

> A backend process is often only the visible endpoint of an application lifecycle problem. Sustainable remediation must fix the owner of the session behavior.

## 1.3.28 SRE/DBRE Best Practices

1. Treat connection count as a capacity dimension.
2. Maintain administrative connection headroom.
3. Use meaningful `application_name` values.
4. Monitor active, idle, and idle-in-transaction sessions separately.
5. Monitor transaction age independently from query age.
6. Use wait events to classify backend stalls.
7. Correlate PostgreSQL backend PIDs with OS and log telemetry.
8. Detect blocking chains automatically.
9. Size memory with concurrency in mind.
10. Prefer controlled connection pooling for large application fleets.
11. Load-test connection storms and application scaling events.
12. Avoid solving connection saturation only by raising `max_connections`.
13. Use timeouts carefully and according to workload requirements.
14. Preserve diagnostic evidence before terminating problem sessions when possible.
15. Correct application transaction and connection leaks at their source.

## 1.3.30 Section Summary

The PostgreSQL backend process is the server-side execution context for a client session. PostgreSQL's process-per-connection model provides isolation and straightforward process-level observability, but it also makes connection count, private memory, transaction lifecycle, lock behavior, operating-system resources, and connection pooling important reliability concerns.

The central SRE/DBRE principle is:

> A PostgreSQL backend should be monitored as part of an end-to-end session lifecycle. Connection state, transaction age, query activity, waits, locks, memory, and application ownership must be correlated before deciding how to remediate a problem.
