# Chapter 1 — PostgreSQL Architecture and Internals

## 1.4 — PostgreSQL Postmaster and Process Lifecycle Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 / PostgreSQL 18 official documentation

## 1.4.1 Purpose

PostgreSQL is a process-oriented database server. The main `postgres` server process—historically called the **postmaster**—owns the instance lifecycle: it establishes core shared resources, listens for client connections, starts and supervises server processes, coordinates shutdown, and reacts to abnormal child-process termination.

For SRE/DBRE teams, this lifecycle matters because a PostgreSQL instance is not one monolithic process. It is a supervised process ecosystem whose members cooperate through shared memory, synchronization primitives, WAL, storage, and operating-system resources.

```text
                         postgres
                  main server / postmaster
                             |
        +--------------------+--------------------+
        |                    |                    |
        v                    v                    v
 client backends       auxiliary processes   background workers
        |                    |                    |
        +--------------------+--------------------+
                             |
                             v
                 shared memory / IPC / storage
```

This section focuses on supervision and lifecycle. Detailed backend behavior, memory, IPC, background processes, and connection architecture are covered in later dedicated sections.

## 1.4.2 Main Server Process

The `postgres` executable is the PostgreSQL database server. A running server instance manages one PostgreSQL database cluster/data directory. Multiple PostgreSQL instances can run on the same host when they use distinct data directories and non-conflicting communication endpoints.

The main server process remains alive while individual client backends and other child processes are created and terminated according to workload and configuration.

Operationally, distinguish:

```text
PostgreSQL cluster
    = database collection + cluster-wide metadata stored in one data directory

PostgreSQL server instance
    = running process ecosystem managing that cluster
```

## 1.4.3 Startup Lifecycle

A simplified server startup model is:

```text
postgres / pg_ctl / service manager starts server
        |
        v
read configuration and command-line settings
        |
        v
validate PGDATA, permissions, ports and runtime environment
        |
        v
allocate main shared memory and synchronization resources
        |
        v
initialize server subsystems
        |
        v
start required auxiliary processes / workers
        |
        v
enter normal service and accept connections
```

Startup can fail before the server becomes available if configuration, permissions, storage, IPC, memory, ports, shared libraries, or recovery state are invalid.

The PostgreSQL log is the primary source for determining which startup phase failed.

## 1.4.4 Server States During Startup and Recovery

A PostgreSQL process can exist before the server is ready for ordinary application traffic. Startup may include crash recovery, archive recovery, or standby recovery before normal read/write service is available.

This is an important readiness distinction:

```text
process exists
    !=
server accepts connections
    !=
server is writable
    !=
application is healthy
```

Health checks should therefore validate the service state required by the workload rather than merely checking for a `postgres` PID.

## 1.4.5 Client Backend Lifecycle

For normal client sessions, PostgreSQL uses a dedicated backend process per connection.

```text
client requests connection
        |
        v
main server accepts request
        |
        v
backend process is established
        |
        v
authentication / startup negotiation
        |
        v
session SQL and transactions
        |
        v
client disconnect / termination
        |
        v
backend exits
```

Once the connection is established, the backend performs the session's database work. The main server process does not execute ordinary SQL on behalf of every connected client.

## 1.4.6 Auxiliary and Background Process Lifecycle

PostgreSQL starts specialized processes for instance-wide functions. The exact set depends on configuration and operating state and can include checkpoint, background writing, WAL writing, autovacuum, logging, archiving, WAL summarization, recovery, replication, logical replication, parallel workers, and extension-defined workers.

Do not assume every process is present on every instance or at every moment. Some are conditional, configuration-dependent, dynamically created, or recovery-role specific.

Process identity should be verified using PostgreSQL monitoring data such as `pg_stat_activity.backend_type` together with operating-system process information.

## 1.4.7 Background Worker Lifecycle

PostgreSQL provides infrastructure for background workers. Workers can be registered at server startup, and supported code can also register dynamic workers. Depending on their registration and capabilities, workers can attach to shared memory and may connect to databases.

Worker capacity is finite. `max_worker_processes` is an instance-level resource shared by worker-based functionality. Parallel query, logical replication, and extension workers therefore cannot be capacity-planned independently.

```text
                     worker capacity
                           |
            +--------------+--------------+
            |              |              |
        parallel       logical        extension /
        workers       replication      custom
                       workers         workers
```

## 1.4.8 Shared Resource Initialization

The main server establishes the shared infrastructure needed by cooperating PostgreSQL processes. PostgreSQL's main shared-memory region contains shared buffers and other common server data.

On current Unix-like systems the default main shared-memory implementation is generally anonymous `mmap`; PostgreSQL also uses operating-system IPC mechanisms and dynamic shared memory where needed. Exact mechanisms are platform- and configuration-dependent.

This distinction matters operationally because generic advice to increase System V shared-memory limits is not automatically correct for modern Linux installations.

## 1.4.9 Semaphores and Platform Differences

PostgreSQL requires synchronization facilities, but their implementation differs by platform. PostgreSQL 18 uses POSIX semaphores on Linux and FreeBSD, while other supported Unix-derived platforms can use System V semaphores.

When System V semaphores are used, requirements depend on configured connection and worker capacity, including values such as `max_connections`, `autovacuum_worker_slots`, `max_wal_senders`, and `max_worker_processes`.

The runtime-computed value can be inspected before startup where applicable:

```bash
postgres -D "$PGDATA" -C num_os_semaphores
```

A `semget: No space left on device` error refers to semaphore capacity, not necessarily filesystem capacity.

## 1.4.10 Process and Resource Capacity

The PostgreSQL process budget includes more than client connections:

```text
client backends
+ auxiliary processes
+ autovacuum workers
+ WAL senders
+ parallel workers
+ logical replication workers
+ extension/background workers
+ recovery/replication processes where applicable
```

Production capacity planning must correlate PostgreSQL configuration with operating-system process limits, file descriptors, memory, IPC resources, CPU scheduling capacity, container/cgroup limits, and storage.

## 1.4.11 Process Visibility

Use PostgreSQL and OS telemetry together.

```sql
SELECT
    pid,
    backend_type,
    usename,
    datname,
    state,
    wait_event_type,
    wait_event,
    backend_start,
    xact_start,
    query_start,
    query
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

`backend_type` is particularly useful because `pg_stat_activity` can include client backends and several PostgreSQL process classes.

At the OS layer, correlate PIDs with CPU, RSS, I/O, scheduling state, open files, cgroup/container limits, and PostgreSQL logs.

## 1.4.12 Controlled Shutdown Modes

PostgreSQL supports three server shutdown modes:

- **smart** — stop accepting new connections and wait for existing sessions to disconnect; online backup activity is also allowed to finish.
- **fast** — reject new connections, terminate existing sessions after rolling back active transactions, and shut down cleanly. This is the normal administrative shutdown mode in many operational procedures.
- **immediate** — terminate server processes without normal database shutdown processing; crash recovery is required on the next startup.

A shutdown runbook must name the intended mode explicitly. “Restart PostgreSQL” is not sufficiently precise for production operations.

## 1.4.13 Clean Shutdown vs Crash Recovery

A clean shutdown coordinates server processes and leaves the cluster in a state that does not require crash recovery at the next startup.

An immediate shutdown, host crash, power failure, OOM termination, or other abrupt server failure can require WAL-based crash recovery.

```text
clean stop
   -> controlled shutdown
   -> normal next startup

unclean stop
   -> WAL recovery required
   -> recovery time depends on outstanding recovery work and I/O capacity
```

SREs should monitor unexpected recovery because it is evidence of an abnormal previous termination even when PostgreSQL successfully recovers.

## 1.4.14 Child Process Failure Semantics

PostgreSQL processes cooperate through shared state. An unexpected abnormal exit of a server process can therefore be treated as a possible shared-memory integrity event.

The main server can terminate other server processes and reinitialize shared state through crash recovery rather than allowing potentially corrupted shared state to continue serving requests.

This behavior is an important reason not to use arbitrary operating-system `SIGKILL` against PostgreSQL backends.

## 1.4.15 Supported Query Cancellation and Session Termination

Use PostgreSQL-supported administrative interfaces when possible.

Cancel the current query while preserving the session:

```sql
SELECT pg_cancel_backend(<pid>);
```

Terminate a session:

```sql
SELECT pg_terminate_backend(<pid>);
```

Before intervention, identify the backend owner, transaction state, blocking relationships, business impact, and whether rollback could be expensive.

OS-level signals should be reserved for documented operational cases where PostgreSQL-supported mechanisms are unavailable or inappropriate.

## 1.4.16 Service Manager Supervision

Production PostgreSQL should normally be supervised by the platform's supported service mechanism—for example systemd, a container orchestrator, or the database platform's service controller.

Avoid simultaneously configuring competing restart managers around the same PostgreSQL instance. Restart loops can destroy diagnostic evidence and repeatedly trigger crash recovery without correcting the underlying failure.

A useful operational distinction is:

```text
PostgreSQL process supervision
        +
platform service supervision
        +
application readiness
```

Each layer should have a clearly defined responsibility.

## 1.4.17 systemd IPC Lifecycle Risk

On systems using systemd, PostgreSQL documentation warns that `RemoveIPC` can remove IPC resources when a non-system PostgreSQL operating-system account fully logs out. Distribution packages commonly avoid this by creating `postgres` as a system user, but source-built/custom deployments must validate the configuration.

Symptoms can include apparently unexpected dynamic shared-memory errors.

Production validation should ensure the PostgreSQL service account and systemd IPC lifecycle are compatible.

## 1.4.18 Linux Memory Overcommit and OOM

PostgreSQL process lifecycle can also be disrupted by host or container memory exhaustion. On Linux, memory overcommit and the OOM killer can terminate PostgreSQL processes when the host cannot satisfy memory demand.

In containers and Kubernetes, cgroup memory limits create an additional hard boundary. A pod can be OOM-killed even when the underlying node still has free memory.

Monitor:

- host available memory and swap behavior
- PostgreSQL process RSS
- container working set and memory limit
- OOM/OOMKilled events
- connection concurrency
- parallel worker concurrency
- memory-intensive query activity

Treat OOM termination as a database availability incident, not simply a host event.

## 1.4.19 Huge Pages

PostgreSQL can request huge pages for the main shared-memory area using `huge_pages`. The actual state is exposed by `huge_pages_status`.

If `huge_pages=on`, inability to allocate the required huge pages prevents server startup. With `huge_pages=try`, PostgreSQL can fall back when huge-page allocation is unavailable.

Huge-page changes therefore belong in tested startup/capacity procedures, not ad hoc production tuning.

## 1.4.20 Failure Scenario — Connection Storm

```text
application replicas increase
        |
        v
connection attempts increase
        |
        v
backend process count rises
        |
        +--> authentication/startup overhead
        +--> memory pressure
        +--> CPU scheduling pressure
        +--> connection-slot exhaustion
        |
        v
latency / failures
        |
        v
application retries amplify storm
```

The durable fix is connection-budget and pool control, not automatically increasing `max_connections`.

## 1.4.21 Failure Scenario — SIGKILL of a Backend

An operator sends `SIGKILL` to a PostgreSQL backend to stop a query.

```text
backend dies abnormally
        |
        v
main server detects unexpected child death
        |
        v
shared-state integrity cannot be assumed
        |
        v
other server processes can be terminated
        |
        v
crash recovery / service interruption
```

Use `pg_cancel_backend()` for query cancellation or `pg_terminate_backend()` for controlled session termination when appropriate.

## 1.4.22 Failure Scenario — Startup IPC Error

PostgreSQL fails during startup with a shared-memory or semaphore error.

Do not immediately conclude that the host is out of RAM or disk. Determine the failing IPC mechanism and platform first.

For example:

```text
shmget failure
   -> shared_memory_type / System V limits / requested size

semget "No space left on device"
   -> System V semaphore limits, not filesystem space
```

On Linux with default PostgreSQL 18 IPC choices, traditional System V tuning is often not the relevant first action.

## 1.4.23 Failure Scenario — Restart Loop

A platform liveness probe is configured too aggressively during crash recovery. PostgreSQL starts replaying WAL but the probe declares the instance unhealthy and repeatedly kills/restarts it.

Result:

```text
recovery starts
   -> probe timeout
   -> process killed
   -> recovery restarts
   -> availability never restored
```

Readiness/liveness thresholds must accommodate expected startup and recovery behavior. Recovery progress should be diagnosed rather than interrupted repeatedly.

## 1.4.24 Monitoring Strategy

Monitor at least:

- main server process availability
- server restart count and reason
- unexpected crash-recovery events
- backend count and connection utilization
- backend types
- process creation/connection rate
- worker utilization
- WAL sender utilization
- long transactions and idle-in-transaction sessions
- PostgreSQL child-process crash messages
- host/container CPU and memory pressure
- OOM events
- file-descriptor utilization
- IPC/shared-memory startup failures
- service-manager restart loops

A PID-alive check alone is insufficient.

## 1.4.25 Alerting Strategy

High-value alerts include sustained connection saturation, abnormal connection creation rate, repeated PostgreSQL restarts, unexpected crash recovery, child-process crash loops, OOM termination, worker exhaustion, file-descriptor pressure, and startup failures caused by configuration or IPC resources.

Alert severity should follow user impact and recovery risk. A successful automatic restart after a crash still warrants investigation when the event is unexpected.

## 1.4.26 Troubleshooting Workflow

```text
PostgreSQL unavailable / unstable
        |
        v
identify current server state
        |
        +-- stopped
        +-- starting
        +-- recovering
        +-- accepting connections
        +-- read-only standby/recovery
        +-- writable primary
        |
        v
inspect PostgreSQL logs
        |
        v
inspect service-manager / container events
        |
        v
check child-process failures / OOM
        |
        v
check configuration, shared memory, IPC, ports, storage
        |
        v
check connection and worker pressure
        |
        v
identify failure domain before restart/intervention
```

Preserve logs and process/platform evidence before repeated restarts whenever the availability situation permits.

## 1.4.27 Recovery Principles

Recovery depends on the failure domain. Appropriate actions can include reducing connection pressure, correcting application pools, fixing OS/container limits, correcting configuration, restoring storage capacity, terminating a harmful session through supported interfaces, allowing crash recovery to complete, or performing a controlled restart.

Do not use restart as a universal remediation. A restart can clear symptoms while preserving the defect that caused them.

## 1.4.28 Automation

DBRE automation should capture a diagnostic snapshot around PostgreSQL lifecycle events:

```text
server state and uptime
restart reason / service-manager event
PostgreSQL log tail
backend count by backend_type
connection utilization
oldest transaction
worker utilization
host/container memory
OOM events
file-descriptor usage
storage capacity/latency
```

Automation should detect restart loops and suppress destructive repeated recovery actions rather than blindly restarting an unhealthy server forever.

## 1.4.29 Production Case Study — Kubernetes Recovery Loop

A PostgreSQL pod is restarted after node-level disruption. The database must perform crash recovery before becoming ready. A liveness probe has a short failure threshold and begins killing the container before recovery completes.

### Root cause

The platform treated database recovery time as application process failure.

### Corrective actions

- separate startup/readiness/liveness semantics
- provide sufficient startup tolerance for recovery
- monitor PostgreSQL recovery progress and logs
- validate storage latency during recovery
- prevent repeated termination of a progressing recovery process

### Reliability lesson

> Database lifecycle health checks must understand recovery state. A process that is not yet ready can still be healthy and making essential recovery progress.

## 1.4.30 SRE/DBRE Best Practices

1. Treat the PostgreSQL process tree as a reliability subsystem.
2. Distinguish process-alive, connection-ready, recovery, read-only, and writable states.
3. Use supported PostgreSQL shutdown modes and document which mode each runbook uses.
4. Prefer `pg_cancel_backend()` and `pg_terminate_backend()` over arbitrary OS kills.
5. Do not use `SIGKILL` as a routine query-management mechanism.
6. Monitor unexpected child-process crashes and crash recovery.
7. Validate Linux/container OOM behavior and memory limits.
8. Validate platform-specific shared-memory and semaphore behavior before changing kernel settings.
9. Validate systemd `RemoveIPC` behavior for custom/source deployments.
10. Treat `max_worker_processes` as shared instance capacity.
11. Maintain connection and worker headroom.
12. Test smart, fast, and immediate shutdown behavior outside production.
13. Test crash recovery and realistic startup duration.
14. Ensure orchestrator probes do not interrupt legitimate recovery.
15. Preserve diagnostic evidence before repeated restarts.

```text
[ ] Are restart-loop protections in place?
```

## 1.4.32 Section Summary

PostgreSQL's main `postgres` process supervises a process ecosystem composed of client backends, auxiliary processes, and background workers sharing database and operating-system resources. The lifecycle includes startup, connection handling, normal operation, controlled shutdown, abnormal process failure, and crash recovery.

The central SRE/DBRE principle is:

> A PostgreSQL instance is healthy only when its supervised process ecosystem is in the correct service state. Process existence alone is not readiness, and repeated restart is not root-cause remediation.
