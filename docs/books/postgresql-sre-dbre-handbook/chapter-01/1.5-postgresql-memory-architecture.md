## 1.5.1 Purpose

PostgreSQL memory is not one monolithic cache. Production behavior is the result of instance-wide shared memory, per-backend/session memory, per-query operation memory, maintenance memory, dynamic shared memory, temporary buffers, extension allocations, and the operating system's own memory and filesystem cache.

```text
Host RAM
  |
  +-- Operating System / Filesystem Cache
  |
  +-- PostgreSQL Main Shared Memory
  |     +-- shared_buffers
  |     +-- WAL buffers and shared state
  |     +-- locks / process coordination structures
  |     +-- extension shared allocations
  |
  +-- Backend / Session Memory
  |     +-- session state
  |     +-- executor state
  |     +-- work_mem consumers
  |     +-- temp_buffers
  |
  +-- Maintenance Memory
  |     +-- maintenance_work_mem
  |     +-- autovacuum_work_mem
  |
  +-- Dynamic Shared Memory
        +-- parallel query / worker coordination
```

The key SRE/DBRE principle is that PostgreSQL memory capacity must be modeled under concurrency, not by adding configuration values once.

## 1.5.2 Main Shared Memory

At server startup PostgreSQL establishes a main shared-memory area that can be accessed by cooperating server processes. `shared_buffers` is a major component, but the shared-memory area also contains other PostgreSQL control and coordination structures.

PostgreSQL 18 exposes `shared_memory_size` as a runtime-computed value for the size of the main shared-memory area.

Useful checks:

```sql
SHOW shared_buffers;
SHOW shared_memory_size;
SHOW shared_memory_type;
```

`pg_shmem_allocations` can be used by appropriately privileged roles to inspect named allocations from the main shared-memory segment. It does not include allocations made through dynamic shared memory.

```sql
SELECT name,
       pg_size_pretty(size) AS size,
       pg_size_pretty(allocated_size) AS allocated_size
FROM pg_shmem_allocations
ORDER BY size DESC;
```

## 1.5.3 shared_buffers

`shared_buffers` controls the amount of memory PostgreSQL uses for shared database buffers. PostgreSQL documentation identifies 25% of system memory as a reasonable starting point for a dedicated server with at least 1 GB of RAM, while emphasizing that workload testing is required and that PostgreSQL also relies on the operating-system cache.

This is a starting point, not a universal production target.

```text
Backend requests page
        |
        v
PostgreSQL Buffer Manager
        |
        +-- buffer hit --> shared_buffers
        |
        +-- buffer miss --> storage / OS cache --> shared_buffers
```

Increasing `shared_buffers` is therefore not equivalent to assigning all available host RAM to PostgreSQL caching.

## 1.5.4 Operating-System Cache

PostgreSQL deliberately operates with the operating system's filesystem cache. A page read from a PostgreSQL relation may therefore be served from OS cache even when PostgreSQL reports that it was not already resident in `shared_buffers`.

SRE investigations must distinguish:

```text
PostgreSQL buffer hit
        !=
physical storage read in every case
```

A PostgreSQL buffer miss can still be satisfied quickly by the operating-system cache.

## 1.5.5 Per-Backend Memory

Every backend process requires private memory for session state, query execution, catalog/cache structures, protocol handling, and other backend-local allocations.

This is one reason `max_connections` is a capacity parameter rather than merely an access-control setting.

Conceptually:

```text
Total PostgreSQL memory
  ≈ shared memory
  + sum(active backend private memory)
  + query-operation memory
  + worker memory
  + maintenance/autovacuum memory
  + dynamic shared memory
  + OS/cache requirements
```

This is intentionally a capacity model rather than an exact formula; actual allocations depend on workload and execution plans.

## 1.5.6 work_mem

`work_mem` is a base limit used by individual query operations such as sorts and hash tables before PostgreSQL spills work to temporary files. It is not a per-session total memory cap.

A single query can contain multiple memory-consuming plan nodes, and many sessions can execute such nodes concurrently.

```text
Concurrent sessions
       ×
operations per query
       ×
work_mem-related allocation
       =
potentially large aggregate memory demand
```

Hash operations can use more than the base `work_mem` value according to `hash_mem_multiplier`.

For this reason, setting `work_mem = 1GB` does not mean a session can consume only 1 GB.

## 1.5.7 temp_buffers

`temp_buffers` controls the maximum memory a session can use for temporary-table buffers. These buffers are session-local and apply to temporary tables rather than ordinary shared-buffer caching.

Because the setting is per session, high connection counts must be considered when assessing its capacity risk.

## 1.5.8 maintenance_work_mem

`maintenance_work_mem` provides memory for maintenance operations such as VACUUM, CREATE INDEX, and ALTER TABLE ADD FOREIGN KEY. Maintenance operations are generally less concurrent than normal query operations, so this value can often be larger than `work_mem`, but concurrency must still be modeled.

## 1.5.9 autovacuum_work_mem

Autovacuum workers can use `autovacuum_work_mem`. When it is `-1`, PostgreSQL uses `maintenance_work_mem` for autovacuum workers.

Capacity planning must consider concurrent workers rather than evaluating one worker in isolation.

```text
autovacuum worker memory
       ×
concurrent workers
       =
possible aggregate maintenance memory
```

## 1.5.10 Dynamic Shared Memory

PostgreSQL supports dynamic shared memory in addition to the main shared-memory region. It is important for features that require cooperating processes, including parallel processing.

`dynamic_shared_memory_type` selects the implementation available on the platform. `min_dynamic_shared_memory` can reserve dynamic shared memory at startup for parallel-query use.

## 1.5.11 Huge Pages

PostgreSQL can request explicit huge pages for its main shared-memory area on supported platforms. Huge pages can reduce page-table overhead and CPU time associated with memory management for large shared-memory allocations.

Relevant settings include:

```sql
SHOW huge_pages;
SHOW huge_pages_status;
SHOW huge_page_size;
SHOW shared_memory_size_in_huge_pages;
```

On Linux, PostgreSQL documentation distinguishes explicit huge pages from Transparent Huge Pages (THP) and notes that THP has caused performance degradation for some PostgreSQL workloads and Linux versions.

## 1.5.12 Linux Memory Overcommit and OOM Risk

Host-level memory behavior can directly affect PostgreSQL availability. Excessive backend/query memory combined with Linux overcommit can result in the kernel invoking the OOM killer.

A dangerous pattern is:

```text
high max_connections
       +
high work_mem
       +
parallel queries
       +
maintenance/autovacuum activity
       +
application traffic spike
       ->
host memory pressure
       ->
swap / reclaim pressure
       ->
latency
       ->
OOM risk
```

PostgreSQL documentation specifically recommends considering lower `shared_buffers`, `work_mem`, `hash_mem_multiplier`, or connection counts when PostgreSQL is causing memory exhaustion, and notes that external connection pooling can be preferable to very high `max_connections`.

## 1.5.13 Memory and Connection Pooling

Connection pooling is also a memory-control mechanism.

```text
10,000 application connections
           |
           v
       PgBouncer
           |
           v
hundreds of controlled PostgreSQL backends
```

Reducing active PostgreSQL backend count can lower private-process memory, reduce scheduling pressure, and make aggregate query-memory demand more predictable.

## 1.5.14 Memory and Parallel Query

Parallel query can create additional worker processes and shared-memory requirements. Memory planning must therefore account for concurrent parallel plans as well as ordinary backends.

A configuration that appears safe under serial execution may become unsafe when many sessions simultaneously obtain parallel workers.

## 1.5.15 Memory and Temporary I/O

When query operations cannot remain within their memory budget, PostgreSQL can use temporary files. This transforms memory pressure into storage I/O pressure.

```text
insufficient operation memory
        ->
sort/hash spill
        ->
temporary files
        ->
storage I/O
        ->
query latency
        ->
possible shared storage contention
```

Therefore memory tuning and storage-I/O analysis must be performed together.

## 1.5.16 Storage I/O Path

The simplified read path is:

```text
Executor
   |
   v
Buffer Manager
   |
   +-- shared buffer hit --> return page
   |
   +-- miss
         |
         v
   filesystem / OS cache
         |
         +-- cached --> memory copy to shared buffer
         |
         +-- not cached --> storage I/O --> OS cache --> shared buffer
```

The simplified dirty-page path is:

```text
Backend modifies buffered page
        |
        v
shared buffer becomes dirty
        |
        +-- background writer may write it
        +-- checkpointer writes required dirty buffers
        +-- backend may sometimes participate in writes
        |
        v
filesystem / storage stack
```

WAL durability is a separate but related path and is covered in Section 1.12. Buffer replacement and caching are covered deeply in Section 1.15, while checkpoint/background writing is covered in Section 1.16.

## 1.5.17 Memory Monitoring

Memory observability should combine PostgreSQL and operating-system telemetry.

PostgreSQL checks:

```sql
SHOW shared_buffers;
SHOW work_mem;
SHOW hash_mem_multiplier;
SHOW maintenance_work_mem;
SHOW autovacuum_work_mem;
SHOW temp_buffers;
SHOW max_connections;
SHOW max_worker_processes;
SHOW max_parallel_workers;
SHOW huge_pages_status;
```

Shared-memory allocation inspection:

```sql
SELECT name, size, allocated_size
FROM pg_shmem_allocations
ORDER BY size DESC;
```

OS monitoring should include RSS, total available memory, swap, page faults, memory pressure/reclaim, OOM events, and container/cgroup limits where applicable.

## 1.5.18 Alerting Guidance

Do not alert on a single PostgreSQL memory parameter. Alert on symptoms and capacity boundaries such as sustained host/container memory pressure, swap activity, OOM events, abnormal backend growth, temporary-file growth, sudden concurrency changes, and failure to obtain required shared memory.

Thresholds must be based on the deployment model and workload baseline rather than copied blindly between environments.

## 1.5.19 Failure Scenario — work_mem Multiplication

Assume an administrator raises `work_mem` globally to improve one reporting query. The query improves, but production later experiences a concurrency spike.

```text
larger work_mem
   × many plan nodes
   × many active sessions
   -> aggregate allocation surge
   -> OS memory pressure
   -> swapping / OOM
   -> database latency or process termination
```

Corrective actions include reducing the global value, using targeted session/role settings for known workloads, controlling concurrency, reviewing execution plans, and using pooling where appropriate.

## 1.5.20 Failure Scenario — Shared Memory Startup Failure

PostgreSQL startup can fail when the operating system cannot provide the requested shared-memory or IPC resources. The PostgreSQL startup diagnostics should be read carefully; for example, System V shared-memory or semaphore errors are kernel-resource problems rather than ordinary disk-space failures.

Recovery must address the actual OS resource constraint or safely reduce the PostgreSQL resource requirement.

## 1.5.21 Failure Scenario — OOM Killer

When the operating system terminates a PostgreSQL process because of memory exhaustion, do not treat the killed process as the root cause.

Investigate:

- active connection count
- workload concurrency
- `work_mem` and `hash_mem_multiplier`
- parallel workers
- maintenance/autovacuum activity
- extension memory use
- host/container limits
- swap and reclaim behavior
- application connection storms

The recovery action should remove the capacity trigger before simply restarting traffic at full load.

## 1.5.22 Troubleshooting Workflow

```text
Memory alarm / OOM / latency
        |
        v
Check host/container memory and OOM logs
        |
        v
Check PostgreSQL connection and worker concurrency
        |
        v
Inspect memory-related configuration
        |
        v
Identify high-memory query plans / temp spills
        |
        v
Check maintenance and autovacuum concurrency
        |
        v
Validate pooling and application connection behavior
        |
        v
Mitigate safely
        |
        v
Load-test permanent configuration changes
```

## 1.5.23 Configuration Safety Rules

- Do not size `work_mem` by multiplying it only by `max_connections`; plan-node concurrency matters.
- Do not assign nearly all host RAM to `shared_buffers`; PostgreSQL relies on OS memory as well.
- Do not increase `max_connections` without modeling backend and query memory.
- Do not tune memory independently of parallelism.
- Do not ignore container/cgroup limits when PostgreSQL runs in containers or Kubernetes.
- Prefer workload-specific settings when a small class of queries requires unusually high memory.
- Validate changes under realistic concurrency before production rollout.

## 1.5.24 Production Capacity Model

A practical DBRE capacity model should reserve memory for the OS and filesystem cache first, then account for fixed/shared PostgreSQL memory, expected backend private memory, realistic concurrent query operations, maintenance/autovacuum workers, parallel workers, extensions, monitoring agents, and a safety margin.

Use measured workload percentiles rather than assuming every configured maximum occurs continuously; separately model credible worst-case bursts.

## 1.5.25 Automation

Automated checks can capture memory-risk configuration and runtime state:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
  'shared_buffers',
  'work_mem',
  'hash_mem_multiplier',
  'maintenance_work_mem',
  'autovacuum_work_mem',
  'temp_buffers',
  'max_connections',
  'max_worker_processes',
  'max_parallel_workers',
  'huge_pages'
)
ORDER BY name;
```

Automation should compare configuration with observed concurrency and host/container limits, not merely enforce fixed parameter values.

## 1.5.26 Production Case Study — Reporting Workload Destabilizes OLTP

An OLTP database also serves large analytical reports. A global increase in `work_mem` reduces report spills during testing. In production, multiple reports overlap with peak application traffic and parallel workers. Aggregate process memory rises sharply, the host begins reclaiming memory, and OLTP latency increases.

The architectural cause is not simply "PostgreSQL needs more RAM." The issue is uncontrolled multiplication of per-operation memory under concurrency.

A durable remediation can combine lower global `work_mem`, higher targeted settings for the reporting role or session, report concurrency control, query/index optimization, connection pooling, and capacity validation.

## 1.5.27 SRE/DBRE Production Checklist

- [ ] Host/container memory limit documented
- [ ] OS/cache reserve documented
- [ ] `shared_buffers` validated against workload
- [ ] `work_mem` modeled under concurrent plan operations
- [ ] `hash_mem_multiplier` included in risk analysis
- [ ] connection count and pooling model documented
- [ ] maintenance/autovacuum concurrency modeled
- [ ] parallel-worker memory considered
- [ ] temporary-file behavior monitored
- [ ] huge-page configuration verified where used
- [ ] OOM events monitored
- [ ] memory-pressure runbook tested
- [ ] configuration changes load-tested

## 1.5.28 Section Summary

PostgreSQL memory architecture spans shared memory, backend-local memory, query-operation memory, maintenance memory, dynamic shared memory, and operating-system caching. The most dangerous production mistakes come from treating per-operation or per-session parameters as fixed instance-wide allocations.

The SRE/DBRE must model memory as a concurrency problem and connect memory behavior to connections, query plans, parallelism, temporary I/O, vacuum, checkpoints, and storage latency.

### SRE/DBRE Principle

> Memory safety is determined by workload concurrency and execution behavior, not by any single PostgreSQL memory parameter.
