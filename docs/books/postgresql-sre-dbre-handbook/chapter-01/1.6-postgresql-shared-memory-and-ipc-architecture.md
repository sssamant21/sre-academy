# Chapter 1 — PostgreSQL Architecture and Internals

## 1.6 — PostgreSQL Shared Memory and IPC Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.6.1 Purpose

PostgreSQL uses a process-based architecture. Independent backend, auxiliary, and worker processes therefore require shared state plus operating-system inter-process communication (IPC) and synchronization mechanisms. Shared memory is part of PostgreSQL's control plane as well as its caching architecture: failures in this layer can prevent startup, break parallel work, or destabilize an otherwise healthy SQL workload.

This section focuses on the SRE/DBRE operational model: main shared memory, dynamic shared memory, semaphores, huge pages, platform differences, systemd IPC lifecycle, capacity coupling, monitoring, failure scenarios, troubleshooting, recovery, and automation guardrails.


## 1.6.3 Main Shared Memory

At startup PostgreSQL establishes a main shared-memory region containing `shared_buffers` and many server-wide structures. PostgreSQL 18 exposes the runtime-computed `shared_memory_size` value for the main shared-memory area.

```sql
SHOW shared_memory_size;
SHOW shared_buffers;
SHOW shared_memory_type;
```

`shared_memory_type` selects the implementation for the main shared-memory region. Supported values include `mmap`, `sysv`, and `windows`, depending on platform. On Unix-like platforms the normal/default design uses anonymous `mmap` for the large main region; selecting `sysv` for the main region is generally discouraged because it can require non-default kernel resource settings.

## 1.6.4 Shared Buffers and Other Allocations

`shared_buffers` is usually the largest visible consumer of main shared memory, but it is not the whole region. PostgreSQL and extensions allocate additional server-wide structures for coordination and state.

`pg_shmem_allocations` exposes named allocations in the main shared-memory segment:

```sql
SELECT name,
       pg_size_pretty(size) AS size,
       pg_size_pretty(allocated_size) AS allocated_size
FROM pg_shmem_allocations
ORDER BY allocated_size DESC;
```

This view does not report dynamic shared-memory allocations, so it must not be interpreted as a complete inventory of all memory shared between PostgreSQL processes.

## 1.6.5 Dynamic Shared Memory

PostgreSQL also supports dynamic shared memory (DSM) for runtime consumers such as parallel processing.

```text
startup
  -> main shared memory
  -> optional preallocated dynamic shared memory

runtime
  -> additional DSM segments as workload requires
```

`dynamic_shared_memory_type` selects the DSM implementation. Depending on platform, PostgreSQL supports mechanisms including POSIX shared memory, System V shared memory, Windows shared memory, and an mmap-backed implementation. PostgreSQL documentation generally discourages the mmap DSM implementation for normal production use because it can introduce repeated filesystem writeback I/O.

`min_dynamic_shared_memory` reserves memory at startup for parallel-query use. If that area is insufficient, new parallel work can request additional DSM from the operating system at runtime.

## 1.6.6 Huge Pages

Explicit huge pages can reduce page-table and memory-management overhead for PostgreSQL's large main shared-memory allocation.

Relevant PostgreSQL 18 settings include:

```sql
SHOW huge_pages;
SHOW huge_pages_status;
SHOW huge_page_size;
SHOW shared_memory_size_in_huge_pages;
```

`huge_pages` supports `try`, `on`, and `off`. With `on`, failure to obtain the required huge pages prevents server startup. With `try`, PostgreSQL falls back if the request cannot be satisfied.

PostgreSQL 18 documents explicit huge-page support for the main shared-memory area on Linux and Windows. On Linux, explicit PostgreSQL huge pages require `shared_memory_type = mmap`. `shared_memory_size_in_huge_pages` is a Linux-specific computed value useful for pre-start capacity planning.

Explicit huge pages must not be confused with Linux Transparent Huge Pages (THP). PostgreSQL documentation notes that THP has caused performance degradation for some PostgreSQL workloads/Linux versions and currently discourages it, while explicit huge pages can be beneficial when configured correctly.

## 1.6.7 IPC and Semaphore Architecture

PostgreSQL requires operating-system IPC facilities, specifically shared memory and semaphores. Unix-derived systems commonly provide System V IPC, POSIX IPC, or both; Windows provides its own mechanisms.

The exact semaphore behavior is platform-specific. PostgreSQL 18 uses POSIX semaphores on Linux and FreeBSD. Other supported Unix-derived platforms can use System V semaphores.

When System V semaphores are used, required semaphore capacity is affected by process limits including:

- `max_connections`
- `autovacuum_worker_slots`
- `max_wal_senders`
- `max_worker_processes`

PostgreSQL 18 exposes the runtime-computed `num_os_semaphores` requirement. It can be inspected before startup:

```bash
postgres -D "$PGDATA" -C num_os_semaphores
```

Do not apply old PostgreSQL semaphore formulas blindly to PostgreSQL 18; the current release uses `autovacuum_worker_slots` in this capacity calculation.

## 1.6.8 Linux and System V Resource Guidance

On modern Linux, default shared-memory settings are normally adequate when the default `mmap` main shared-memory implementation is used. Linux does not use System V semaphores for PostgreSQL's normal semaphore implementation.

System V limits become more important when `shared_memory_type = sysv`, when a System V DSM implementation is selected, on platforms that use System V semaphores, or when many PostgreSQL instances/applications compete for IPC resources.

Therefore an error containing `shmget` or `semget` must be interpreted in the context of the deployed platform and configured IPC implementation rather than assuming every PostgreSQL server needs large Linux `kernel.shmmax`/semaphore tuning.

## 1.6.9 systemd RemoveIPC

On systems using systemd, IPC lifecycle is part of PostgreSQL reliability. PostgreSQL documentation warns that `RemoveIPC` can remove IPC objects when the PostgreSQL operating-system account fully logs out if that account is not treated as a system user.

A characteristic failure mode is apparently random disappearance of dynamic shared-memory objects used by parallel query, producing warnings/errors when PostgreSQL tries to access or remove them.

Production requirements:

- run PostgreSQL under an appropriate system/service account;
- validate the distribution's systemd/logind behavior;
- do not manually remove PostgreSQL IPC objects while the server is running;
- include IPC lifecycle configuration in host-hardening reviews.

## 1.6.10 Configuration Coupling

Shared-memory and IPC capacity cannot be tuned parameter-by-parameter in isolation.

```text
shared_buffers --------------------> main shared-memory footprint
extensions/shared allocations ---->

max_connections ------------------+
autovacuum_worker_slots ----------+--> process/semaphore capacity
max_wal_senders ------------------+
max_worker_processes -------------+

parallel workload --------------------> DSM demand
huge_pages ---------------------------> startup/OS reservation
```

A connection, worker, extension, or shared-buffer change can therefore require a restart and can change infrastructure prerequisites even when application SQL is unchanged.

## 1.6.11 Startup Failure Domain

Shared-memory and IPC errors can prevent PostgreSQL from starting before it accepts a single client query.

```text
configuration/infrastructure change
          -> restart
          -> shared memory / semaphore / huge-page allocation
          -> allocation failure
          -> startup failure
          -> database unavailable
```

Always preserve the exact PostgreSQL startup error. Messages often identify whether the problem is huge pages, System V shared memory, semaphore capacity, permissions, address space, or another kernel resource.

## 1.6.12 Runtime Failure Domain

IPC failures are not limited to startup. Runtime problems can include:

- DSM allocation failure during parallel workloads;
- IPC objects removed unexpectedly by host policy;
- host/container memory exhaustion;
- extension shared-memory defects;
- worker/process limits preventing expected work;
- OOM termination of PostgreSQL processes.

The incident may surface as query failure, reduced parallelism, backend termination, crash recovery, or full service interruption depending on the failed resource/process.

## 1.6.13 Linux Memory Overcommit and OOM

Main shared memory is only one component of the PostgreSQL memory envelope. Private backend memory, per-operation query memory, workers, maintenance, logical decoding, extensions, and the operating system must all fit within physical/container limits.

```text
OS + agents
+ PostgreSQL main shared memory
+ backend private memory
+ concurrent work_mem/hash consumers
+ autovacuum/maintenance memory
+ parallel workers and DSM
+ replication/logical decoding
+ extensions
+ filesystem cache
+ safety headroom
```

Container and Kubernetes deployments must use the cgroup memory limit as the relevant hard capacity boundary rather than host RAM alone.

## 1.6.14 Monitoring

A production shared-memory/IPC dashboard should combine PostgreSQL and OS/container telemetry.

PostgreSQL checks:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
  'shared_buffers',
  'shared_memory_type',
  'dynamic_shared_memory_type',
  'min_dynamic_shared_memory',
  'huge_pages',
  'huge_page_size',
  'max_connections',
  'autovacuum_worker_slots',
  'max_worker_processes',
  'max_wal_senders'
)
ORDER BY name;
```

Also capture:

- `shared_memory_size`;
- `shared_memory_size_in_huge_pages` on Linux;
- `huge_pages_status`;
- `pg_shmem_allocations`;
- backend and worker counts;
- PostgreSQL startup/crash logs;
- DSM/IPC errors.

OS/container telemetry should include available memory, RSS/PSS where useful, swap/reclaim, OOM events, cgroup memory pressure, huge-page pool state, process/file limits, and platform-specific IPC limits when relevant.

## 1.6.15 Alerting

Alert on risk and failure, not merely on large configuration values.

Useful warning conditions include sustained memory pressure, declining headroom, unexpected swap/reclaim, huge-page reservation below a planned `huge_pages=on` requirement, and worker/process capacity nearing a workload-specific limit.

Critical conditions include PostgreSQL OOM kills, startup failure caused by IPC/shared-memory allocation, repeated DSM allocation failures affecting workload, and severe host/container memory exhaustion.

## 1.6.16 Failure Scenario — Huge Pages Prevent Startup

An administrator changes `huge_pages` from `try` to `on` without reserving enough huge pages.

```text
restart
  -> PostgreSQL requests explicit huge pages
  -> OS cannot satisfy requirement
  -> startup fails
```

Recovery is to correct the huge-page reservation or deliberately roll back the policy. Repeated restarts do not solve the capacity mismatch.

## 1.6.17 Failure Scenario — systemd Removes IPC

A PostgreSQL service account is configured in a way that allows logind to remove its IPC objects after logout. Later, parallel-query activity encounters missing shared-memory objects.

The correct remediation is host/service-account and `RemoveIPC` configuration, followed by validation of PostgreSQL health. Deleting additional IPC objects or changing SQL plans does not address the cause.

## 1.6.18 Failure Scenario — System V Capacity Mismatch

On a platform/configuration that uses System V IPC, connection/worker limits are increased and PostgreSQL can no longer allocate required IPC resources during restart.

The DBRE response is to use the PostgreSQL 18 computed requirements and platform documentation, adjust the appropriate kernel resource or roll back PostgreSQL demand, and then validate startup. Do not copy kernel values from another operating system or an older PostgreSQL release.

## 1.6.20 Recovery Principles

Never attempt to resolve IPC pressure by deleting PostgreSQL data files or blindly removing live IPC objects.

Safe recovery maps the symptom to the actual failure domain:

- insufficient huge pages → reserve the required pages or roll back huge-page policy;
- System V limit → adjust the relevant supported kernel limit or reduce demand;
- cgroup/container memory exhaustion → increase capacity or reduce PostgreSQL/workload memory demand;
- systemd IPC removal → correct service-account/logind configuration;
- extension shared-memory issue → validate extension compatibility/configuration and rollback safely;
- DSM pressure → investigate workload parallelism, worker capacity, memory limits, and IPC implementation.

Restart-required changes must be coordinated with HA, replication, and application availability procedures.

## 1.6.21 Automation and Guardrails

Configuration/IaC pipelines should validate before rollout:

- physical or container memory limit;
- `shared_buffers` and total main shared-memory requirement;
- huge-page requirement when enforced;
- `max_connections`;
- `autovacuum_worker_slots`;
- `max_wal_senders`;
- `max_worker_processes`;
- extension shared-memory requirements;
- expected parallel/DSM workload;
- platform-specific IPC prerequisites;
- restart requirement and rollback value.

Where possible, capture pre-start computed values such as `num_os_semaphores` and `shared_memory_size_in_huge_pages` in host validation automation.

## 1.6.22 Production Case Study — Capacity Change Breaks Restart

A team raises connection and worker limits and schedules a PostgreSQL restart. On a platform using System V semaphore limits, the new process envelope exceeds available IPC capacity and startup fails.

A weak response repeatedly restarts the service. A DBRE response reads the exact startup error, identifies the semaphore implementation, calculates PostgreSQL 18 requirements, adjusts the supported OS limit or rolls back the database setting, restores service, and adds pre-deployment capacity validation.

### RCA

```text
PostgreSQL process-limit change
   -> increased IPC requirement
   -> OS capacity not validated
   -> restart-time allocation failure
   -> database outage
```

## 1.6.23 Production Best Practices

1. Treat shared memory and IPC as infrastructure dependencies of PostgreSQL.
2. Keep the default `mmap` main shared-memory implementation unless a validated requirement justifies another choice.
3. Do not apply System V tuning where the deployed platform/configuration does not use it.
4. Use PostgreSQL 18 computed requirements rather than old semaphore formulas.
5. Validate explicit huge pages before enforcing `huge_pages=on`.
6. Distinguish explicit huge pages from THP.
7. Validate systemd `RemoveIPC` behavior for PostgreSQL service accounts.
8. Include cgroup/container memory limits in capacity planning.
9. Inventory extensions that allocate shared memory or workers.
10. Preserve startup logs and exact IPC errors during incidents.
11. Never remove PostgreSQL IPC objects manually while the server is running.
12. Test restart and rollback after memory/process-limit changes.

## 1.6.25 Section Summary

PostgreSQL's process architecture depends on shared memory and operating-system IPC for server-wide state and synchronization. PostgreSQL 18 normally uses anonymous `mmap` for the large main shared-memory region on Unix-like systems, supports dynamic shared memory for runtime consumers such as parallel work, and uses platform-specific semaphore implementations.

For SRE/DBRE teams, the important production lesson is that IPC requirements are platform- and configuration-dependent. Shared buffers, worker and connection limits, huge pages, dynamic shared memory, extensions, systemd behavior, and container/host limits must be validated as one reliability system.

### SRE/DBRE Principle

> Shared-memory and IPC failures are infrastructure failures inside the database architecture. Diagnose the exact PostgreSQL implementation, platform resource, and workload dependency before changing kernel or database settings.
