## 1.6 — PostgreSQL Shared Memory and IPC Architecture

## 1.6.1 Purpose

PostgreSQL uses a process-based architecture. Independent backend and background processes therefore require mechanisms for sharing instance-wide state and coordinating concurrent access to shared resources. PostgreSQL combines shared memory with operating-system inter-process communication (IPC) and synchronization facilities to provide that coordination.

This section explains the architecture from an SRE/DBRE perspective: what is shared, how processes coordinate, which operating-system resources matter, how configuration affects capacity, what can fail, and how to diagnose shared-memory and IPC incidents safely.

## 1.6.2 Architectural Model

```text
                    PostgreSQL Instance
                           |
              +------------+------------+
              |                         |
              v                         v
        Backend Processes        Background Processes
              |                         |
              +------------+------------+
                           |
                           v
                    Shared Memory
                           |
        +------------------+------------------+
        |                  |                  |
        v                  v                  v
  Shared Buffers      Shared State      WAL/Control State
        |                  |                  |
        +------------------+------------------+
                           |
                           v
                  IPC / Synchronization
                           |
                OS Memory + Semaphores
```

Shared memory is not simply a cache. It contains database buffers and other server-wide data structures required for coordination among PostgreSQL processes.

## 1.6.3 Main Shared Memory Region

PostgreSQL allocates a main shared-memory region at server startup. Its contents include shared buffers and numerous shared data structures required by the server and loaded extensions.

The runtime parameter `shared_memory_size` reports the size of the main shared-memory area, rounded to the nearest megabyte.

```sql
SHOW shared_memory_size;
SHOW shared_buffers;
```

The main shared-memory implementation is controlled by `shared_memory_type`. On supported Unix-like platforms PostgreSQL normally uses anonymous `mmap` for the large main region rather than requiring the entire allocation to use System V shared memory.

## 1.6.4 Shared Buffers as a Major Consumer

`shared_buffers` controls the amount of memory PostgreSQL dedicates to its shared database buffer cache. It is generally the largest component of the main shared-memory region.

```text
Storage
   |
   v
Buffer Manager
   |
   v
+---------------------+
|   shared_buffers    |
| shared database     |
| pages               |
+---------------------+
   ^       ^       ^
   |       |       |
Backend Backend Background
```

`shared_buffers` is a startup parameter. Increasing it therefore changes PostgreSQL's startup-time memory requirement and requires a server restart.

PostgreSQL also relies on the operating-system cache, so allocating nearly all physical RAM to `shared_buffers` is not a sound production strategy.

## 1.6.5 Shared Memory Beyond Shared Buffers

The main shared-memory area also contains numerous server-wide structures. PostgreSQL exposes these allocations through `pg_shmem_allocations`.

```sql
SELECT
    name,
    size,
    allocated_size
FROM pg_shmem_allocations
ORDER BY allocated_size DESC;
```

This view is valuable during capacity analysis because it shows allocations made by PostgreSQL and extensions in the main shared-memory segment.

Important limitation: `pg_shmem_allocations` does not include allocations made through PostgreSQL's dynamic shared-memory infrastructure.

## 1.6.6 Dynamic Shared Memory

Some operations require shared memory whose lifetime or size is not suitable for permanent startup allocation. PostgreSQL therefore supports dynamic shared memory (DSM).

```text
PostgreSQL startup
      |
      +--> Main shared memory
      |
Runtime workload
      |
      +--> Dynamic shared memory
               |
               +--> parallel execution and other consumers
```

`dynamic_shared_memory_type` selects the operating-system mechanism used for dynamic shared memory. Supported implementations depend on platform and can include POSIX, System V, Windows, and mmap-backed mechanisms.

`min_dynamic_shared_memory` can reserve dynamic shared memory at startup for parallel queries. If that area is insufficient, PostgreSQL can request additional dynamic shared memory from the operating system at runtime.

## 1.6.7 Huge Pages

PostgreSQL can request huge pages for the main shared-memory area on supported platforms.

```text
Normal pages
many page-table entries
        |
        v
higher translation-management overhead

Huge pages
fewer page-table entries
        |
        v
potentially lower memory-management overhead
```

The `huge_pages` setting supports `try`, `on`, and `off`. With `on`, failure to obtain the required huge pages prevents PostgreSQL from starting. With `try`, PostgreSQL falls back when huge pages cannot be allocated.

Useful checks include:

```sql
SHOW huge_pages;
SHOW huge_pages_status;
SHOW shared_memory_size_in_huge_pages;
```

Huge-page configuration must be capacity-planned and tested before production rollout.

## 1.6.8 IPC and Semaphores

Because PostgreSQL uses multiple processes, it requires operating-system IPC facilities. PostgreSQL documentation specifically identifies shared memory and semaphores as required IPC resources.

Semaphores and related synchronization primitives help processes coordinate access to shared state.

On systems using System V semaphores, required semaphore capacity depends on configured process limits such as:

- `max_connections`
- `autovacuum_worker_slots`
- `max_wal_senders`
- `max_worker_processes`

PostgreSQL exposes the computed requirement through `num_os_semaphores` where applicable.

For startup planning:

```bash
postgres -D "$PGDATA" -C num_os_semaphores
```

## 1.6.9 Configuration Coupling

Shared-memory and IPC capacity cannot be tuned parameter-by-parameter in isolation.

```text
max_connections --------+
autovacuum workers -----+--> process / synchronization capacity
max_wal_senders --------+
max_worker_processes ----+

shared_buffers ----------+--> main shared-memory footprint
extensions --------------+
other shared structures -+

parallel workloads -------> dynamic shared memory
```

This is why a seemingly simple increase in connection or worker limits can have operating-system resource consequences.

## 1.6.10 Startup Failure Domain

A shared-memory or IPC problem can prevent PostgreSQL from starting at all.

Typical sequence:

```text
Configuration change
       |
       v
PostgreSQL restart
       |
       v
Shared-memory / IPC allocation fails
       |
       v
Server fails to start
       |
       v
Database unavailable
```

Errors mentioning `shmget` or `semget` should immediately direct the investigation toward kernel IPC resources and PostgreSQL memory/process configuration rather than toward SQL workload troubleshooting.

## 1.6.11 Linux Memory Overcommit and OOM Risk

Shared-memory sizing is only one component of PostgreSQL memory safety. PostgreSQL processes also consume private and workload-dependent memory. Linux memory overcommit and the OOM killer can therefore become part of the failure domain when total memory demand exceeds available resources.

SRE capacity planning should model at least:

```text
OS + agents
+ PostgreSQL main shared memory
+ backend private memory
+ concurrent work_mem operations
+ maintenance workers
+ autovacuum workers
+ parallel workers
+ logical decoding
+ extension memory
+ filesystem cache requirement
+ safety headroom
```

Do not estimate PostgreSQL memory requirement as `shared_buffers + work_mem` alone.

## 1.6.12 Monitoring

A production shared-memory/IPC dashboard should include:

- total host/container memory
- PostgreSQL process RSS/PSS where available
- swap activity
- OOM events
- `shared_memory_size`
- `shared_buffers`
- huge-page status and availability
- backend/process counts
- worker counts
- dynamic shared-memory related failures
- PostgreSQL startup errors
- kernel IPC errors

Useful SQL:

```sql
SELECT
    name,
    pg_size_pretty(size) AS size,
    pg_size_pretty(allocated_size) AS allocated_size
FROM pg_shmem_allocations
ORDER BY allocated_size DESC;
```

and:

```sql
SELECT name, setting, unit
FROM pg_settings
WHERE name IN (
    'shared_buffers',
    'shared_memory_type',
    'dynamic_shared_memory_type',
    'min_dynamic_shared_memory',
    'huge_pages',
    'max_connections',
    'max_worker_processes',
    'max_wal_senders'
)
ORDER BY name;
```

## 1.6.13 Alerting Strategy

Do not alert on shared-memory configuration values simply because they are large. Alert on capacity and failure risk.

Recommended alert classes include:

```text
Warning:
- sustained memory pressure
- swap activity where swap is not expected
- declining memory headroom
- huge-page reservation below planned requirement
- process/worker capacity approaching configured limits

Critical:
- PostgreSQL OOM kill
- PostgreSQL startup failure due to shared memory or semaphore allocation
- severe host/container memory exhaustion
- repeated dynamic shared-memory allocation failures
```

Thresholds must be derived from workload baselines and infrastructure limits rather than copied blindly between systems.

## 1.6.14 Troubleshooting Workflow

When shared-memory or IPC failure is suspected:

```text
1. Preserve PostgreSQL and OS logs
2. Identify whether failure occurred at startup or runtime
3. Check host/container memory and OOM history
4. Inspect shared-memory configuration
5. Inspect connection and worker limits
6. Check kernel IPC/huge-page capacity where relevant
7. Review recent configuration or extension changes
8. Validate actual shared-memory allocations
9. Correct the limiting resource or configuration
10. Restart only when required and according to change procedure
11. Validate database, replication, and application health
```

Useful PostgreSQL checks:

```sql
SHOW shared_memory_size;
SHOW shared_buffers;
SHOW huge_pages;
SHOW huge_pages_status;
SHOW max_connections;
SHOW max_worker_processes;
SHOW max_wal_senders;
```

At the OS layer, use platform-supported tools to inspect memory, huge pages, IPC resources, process limits, cgroup/container limits, and OOM events.

## 1.6.15 Recovery Principles

A shared-memory/IPC incident should not be "fixed" by deleting PostgreSQL runtime or data files.

Safe recovery focuses on correcting the actual resource mismatch:

```text
Insufficient IPC capacity
        -> adjust supported OS resource limit or reduce PostgreSQL demand

Insufficient huge pages with huge_pages=on
        -> correct reservation or safely change huge-page policy

Excessive configured shared memory
        -> correct PostgreSQL sizing

Container memory limit too small
        -> correct container capacity or PostgreSQL workload/configuration
```

All restart-required changes must be coordinated with HA/failover and application availability procedures.

## 1.6.16 Automation and Configuration Guardrails

Infrastructure and configuration automation should validate memory-sensitive changes before rollout.

Guardrails should check:

- physical or container memory limit
- planned `shared_buffers`
- huge-page requirement when enabled
- `max_connections`
- worker-process limits
- extension shared-memory requirements
- expected parallel workload
- memory headroom
- restart requirement

Configuration pipelines should reject values that violate established platform capacity policies.

## 1.6.17 Production Case Study — Restart Fails After Capacity Change

Scenario:

```text
Increase connection/worker configuration
        |
        v
Restart PostgreSQL
        |
        v
OS IPC/resource allocation failure
        |
        v
PostgreSQL does not start
```

A weak response repeatedly restarts PostgreSQL.

A DBRE response reads the startup error, correlates the changed PostgreSQL process limits with OS IPC limits, calculates the required resource capacity, applies the supported correction or rolls back the configuration, then validates startup and workload health.

The lesson is that PostgreSQL configuration and operating-system resource capacity form one reliability system.

## 1.6.18 Production Best Practices

1. Treat shared-memory settings as infrastructure capacity decisions.
2. Maintain memory headroom for backend, worker, OS, and filesystem-cache requirements.
3. Do not increase `max_connections` without evaluating process, memory, and IPC impact.
4. Use connection pooling where it improves connection-capacity control.
5. Validate huge-page configuration before enforcing `huge_pages=on`.
6. Monitor OOM and swap behavior at the operating-system/container layer.
7. Inventory extensions that allocate shared memory.
8. Keep restart procedures and rollback values documented.
9. Test configuration changes in representative environments.
10. Never manipulate PostgreSQL internal files as a remedy for IPC allocation failures.

## 1.6.20 Section Summary

PostgreSQL's process-based architecture depends on shared memory and operating-system IPC to coordinate independent backend and background processes. The main shared-memory area contains shared buffers and server-wide structures, while dynamic shared memory supports runtime requirements such as parallel processing. Semaphores and other synchronization facilities coordinate access to shared state.

For SRE/DBRE teams, the critical principle is that PostgreSQL memory configuration, connection limits, worker limits, extensions, huge pages, operating-system IPC resources, and infrastructure memory limits must be capacity-planned as a single system.

### SRE/DBRE Principle

> Shared memory is part of PostgreSQL's control plane as well as its caching architecture. A shared-memory or IPC capacity mistake can become an availability incident before a single application query is executed.
