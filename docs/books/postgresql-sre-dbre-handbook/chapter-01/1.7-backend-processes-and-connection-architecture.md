# Chapter 1 — PostgreSQL Architecture and Internals

## 1.7 — Backend Processes and Connection Architecture

**Status:** Draft → Technical Review Pending  
**Validation baseline:** PostgreSQL 18.x official documentation

> Reconstruction note: The surviving handbook sequence identifies 1.7 as “Backend Processes and Connection …”. This reconstruction uses **Backend Processes and Connection Architecture** as the working title pending final Chapter 1 Technical Review.

## 1.7.1 Purpose

PostgreSQL uses a process-per-connection client/server architecture. A supervising `postgres` process accepts connection attempts and PostgreSQL establishes a dedicated backend process for each normal client session. The backend then performs authentication/session initialization, accepts frontend protocol messages, executes SQL on behalf of that client, and returns results.

```text
Client / Application
        |
        v
TCP/IP or Unix-domain socket
        |
        v
postgres supervisor
        |
        v
Dedicated backend process
        |
        +-- authentication/session state
        +-- transactions
        +-- parsing/planning/execution
        +-- locks
        +-- local memory
        +-- access to shared memory
        |
        v
Database resources
```

This architecture gives PostgreSQL strong process isolation, but it also means that connection count is a capacity dimension rather than merely a configuration number.

## 1.7.2 Connection Establishment Lifecycle

A simplified lifecycle is:

```text
Connection request
      |
      v
Listener accepts request
      |
      v
Backend startup begins
      |
      v
Startup message / protocol negotiation
      |
      v
pg_hba.conf evaluation
      |
      v
Authentication
      |
      v
Session initialization
      |
      v
ReadyForQuery
      |
      v
Normal SQL traffic
      |
      v
Session termination
```

The startup message identifies the requested user and database and the protocol version. PostgreSQL then evaluates its configuration and authentication requirements before allowing the session to enter normal operation.

## 1.7.3 Frontend/Backend Protocol

PostgreSQL communication between clients and server backends is message based and can operate over TCP/IP or Unix-domain sockets.

The protocol has distinct startup and normal-operation phases. After successful startup and authentication, clients send queries or other protocol messages and the backend returns results, errors, notices, parameter status, and other responses.

PostgreSQL 18 introduces frontend/backend protocol version 3.2 while retaining compatibility with protocol 3.0 clients.

## 1.7.4 Listener Architecture

Important listener controls include:

```text
listen_addresses
port
unix_socket_directories
```

`listen_addresses` determines which network interfaces accept TCP/IP connection attempts. `port` determines the listening TCP port, normally 5432. Unix-domain sockets provide local IPC connectivity where configured.

These settings determine reachability; they do not replace authentication or authorization controls.

## 1.7.5 Authentication Architecture

A PostgreSQL client requests a database user identity. PostgreSQL authentication establishes whether that client may connect as the requested role.

Authentication policy is principally driven by `pg_hba.conf`, where rules can be selected according to connection type, client address, database, and role.

```text
Incoming connection
       |
       v
Connection type / source / DB / role
       |
       v
pg_hba.conf rule match
       |
       v
Authentication method
       |
       +-- success -> session initialization
       |
       +-- failure -> reject connection
```

SRE teams should treat authentication failures, network failures, DNS/TLS failures, and exhausted connection slots as separate failure domains.

## 1.7.6 Connection Capacity

`max_connections` defines the maximum number of concurrent database connections. PostgreSQL sizes some resources based directly on this setting, including shared-memory resources.

Therefore:

```text
Higher max_connections
        !=
Free scalability
```

Increasing connection capacity can increase memory and kernel-resource requirements and can allow more concurrent work to compete for CPU, locks, buffers, WAL, and storage I/O.

## 1.7.7 Reserved Connection Capacity

PostgreSQL provides emergency/reserved connection mechanisms through:

- `reserved_connections`
- `superuser_reserved_connections`

`reserved_connections` can reserve slots for roles granted `pg_use_reserved_connections`, while `superuser_reserved_connections` preserves final emergency capacity for superusers.

Production systems should protect administrative access so a connection storm does not prevent DBRE/SRE intervention.

## 1.7.8 Backend Resource Model

Each backend has process-local state and memory while also accessing shared PostgreSQL structures.

```text
Backend process
   |
   +-- process-local memory
   +-- session settings
   +-- transaction state
   +-- query execution state
   +-- temporary allocations
   |
   +--> shared buffers
   +--> WAL buffers/shared WAL state
   +--> lock structures
   +--> shared statistics/state
```

This is why connection count and workload concurrency must be considered together.

## 1.7.9 Connection Pooling Architecture

For high-concurrency application fleets, connection pooling can decouple application concurrency from PostgreSQL backend-process concurrency.

```text
Many application clients
          |
          v
      Pooling layer
          |
          v
Smaller controlled backend population
          |
          v
      PostgreSQL
```

Pooling is not simply a performance optimization. It can be a reliability control that limits backend creation, memory amplification, authentication churn, and concurrency pressure.

Pooling behavior and PgBouncer are covered in dedicated later material.

## 1.7.10 Monitoring

Core session visibility comes from `pg_stat_activity`.

```sql
SELECT
    pid,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity;
```

DBRE dashboards should monitor at least:

- total connections
- active connections
- idle connections
- idle-in-transaction sessions
- connection utilization versus usable capacity
- connection creation rate
- authentication failures
- connection latency
- backend age
- transaction age
- wait-event distribution
- application/role/database connection distribution
- pool utilization when a pooler is used

## 1.7.11 Alerting

Alerting should be based on sustained risk rather than isolated spikes.

Recommended alert categories include:

```text
Connection utilization approaching capacity
Reserved/emergency slots being consumed
Rapid connection creation / connection storm
Long-lived idle-in-transaction sessions
Abnormal authentication failure rate
Pool saturation or queue growth
Backend count correlated with memory pressure
```

Thresholds should be environment-specific and capacity-tested rather than copied blindly between systems.

## 1.7.12 Failure Scenario — Connection Exhaustion

A common production chain is:

```text
Application connection leak or storm
        |
        v
Backend population rises
        |
        v
Connection slots exhausted
        |
        v
New application sessions rejected
        |
        v
Retries increase
        |
        v
Additional connection pressure
```

Unbounded retries can turn an initial application defect into a database-wide availability event.

## 1.7.13 Failure Scenario — Too Many Backends

Even before `max_connections` is reached:

```text
Backend concurrency rises
      |
      +--> memory pressure
      +--> CPU scheduling pressure
      +--> lock contention
      +--> cache churn
      +--> storage concurrency
      +--> WAL pressure
      |
      v
Latency rises
```

The reliability objective is therefore not “maximize allowed connections”; it is “control useful database concurrency.”

## 1.7.14 Failure Scenario — Idle in Transaction

An application can leave a transaction open while doing no useful database work.

```text
BEGIN
  |
  v
Transaction remains open
  |
  v
Session becomes idle in transaction
  |
  +--> locks may remain held
  +--> MVCC cleanup horizon can be affected
  +--> dead tuples can remain non-removable
  +--> operational risk increases
```

SRE monitoring must distinguish ordinary idle sessions from `idle in transaction` sessions.

## 1.7.15 Troubleshooting Workflow

When connection-related symptoms appear:

1. Confirm server reachability and listener configuration.
2. Separate DNS/network/TLS failures from PostgreSQL rejection.
3. Check current connection utilization and reserved capacity.
4. Inspect `pg_stat_activity` by database, user, application, client, state, and wait event.
5. Identify connection storms, leaks, long-lived sessions, and idle-in-transaction sessions.
6. Check pooler saturation and queueing if pooling is present.
7. Correlate backend growth with memory, CPU, storage, locks, and WAL behavior.
8. Review PostgreSQL logs for authentication or connection-limit errors.
9. Correct the source of excess concurrency before simply increasing `max_connections`.

## 1.7.16 Recovery

Recovery depends on the failure mode. Possible controlled actions include:

- stop or throttle the offending application workload
- correct pool limits
- terminate clearly abandoned sessions after impact analysis
- restore reserved administrative access
- remediate connection leaks
- apply transaction/session timeouts where appropriate
- resize connection capacity only after memory and concurrency modeling

Killing sessions indiscriminately can cause application retries, rollbacks, lock churn, and a second connection storm.

## 1.7.17 Automation

Useful automation includes:

```text
connection utilization dashboards
application/user/database cardinality reports
idle-in-transaction detection
long-transaction detection
pool saturation alerts
connection-storm rate alerts
capacity trend reports
configuration drift checks
```

Automation should surface risk and apply safe guardrails; destructive session termination should require carefully defined policy.

## 1.7.18 Production Case Study — Connection Storm

Consider an application deployment that introduces a connection leak:

```text
New application version
      -> connections not returned/closed
      -> backend count rises
      -> pool/database slots approach exhaustion
      -> requests fail
      -> clients retry
      -> connection attempts accelerate
      -> database and application latency rise
```

A weak response is to immediately double `max_connections`.

A DBRE response is to stabilize retries and application traffic, preserve administrative access, identify the leaking application population, inspect pool behavior, measure memory/concurrency pressure, remediate the leak, and only then reassess whether the configured connection capacity is appropriate.

## 1.7.19 SRE/DBRE Best Practices

- Treat connection capacity as a reliability budget.
- Preserve emergency administrative connection slots.
- Use pooling where application concurrency substantially exceeds useful database concurrency.
- Monitor connection rate as well as connection count.
- Tag connections with meaningful `application_name` values.
- Detect long-lived and idle-in-transaction sessions.
- Use bounded retries with backoff at the application layer.
- Capacity-test changes to `max_connections`.
- Correlate backend population with memory, CPU, lock, WAL, and I/O pressure.
- Maintain a documented connection-exhaustion runbook.

## 1.7.20 Section Summary

PostgreSQL's backend and connection architecture is fundamental to production reliability. Each normal client session maps to a backend process, making connections part of the database's process, memory, CPU, lock, and I/O capacity model.

The SRE/DBRE objective is therefore not simply to keep connection counts below `max_connections`; it is to maintain controlled, observable, and recoverable database concurrency while preserving emergency administrative access.

### SRE/DBRE Principle

> Connections are workload. A PostgreSQL connection limit is a capacity boundary, not a target utilization level.
