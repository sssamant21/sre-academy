# Chapter 1 — PostgreSQL Architecture and Internals

## 1.7 — Backend Processes and Connection Architecture

**Status:** Technical Review  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.7.1 Purpose

PostgreSQL uses a process-per-user/client model: a supervising server process listens for connection requests and starts a dedicated backend process for each normal client connection. That backend owns the client session, performs authentication and session initialization, receives frontend/backend protocol messages, executes SQL, and returns results.

```text
Client / Application
        |
        v
TCP/IP or Unix-domain socket
        |
        v
postgres supervisor / postmaster role
        |
        v
Dedicated backend process
        |
        +-- authentication and session state
        +-- transaction state
        +-- parser / planner / executor activity
        +-- locks and snapshots
        +-- private memory contexts
        +-- shared-memory access
        |
        v
Database resources
```

The process boundary provides useful isolation, but it also makes connection count a database capacity dimension rather than merely a configuration value.

## 1.7.2 Connection Establishment Lifecycle

PostgreSQL documents connection establishment as a supervisor/backend lifecycle. A simplified production model is:

```text
Connection request
      |
      v
Server listener receives request
      |
      v
Dedicated backend process starts
      |
      v
Startup negotiation
      |
      +--> optional SSL/GSS negotiation
      |
      v
StartupMessage
      |
      v
pg_hba.conf selection
      |
      v
Authentication
      |
      v
Session initialization / parameter status
      |
      v
ReadyForQuery
      |
      v
Normal protocol operation
      |
      v
Session termination
```

The startup request includes the requested database/user and protocol information. Authentication can require one or several protocol exchanges depending on the configured method.

## 1.7.3 Frontend/Backend Protocol

PostgreSQL client/server communication is message based. The protocol has a startup phase followed by normal operation. During normal operation, clients can use the simple-query protocol or the extended-query protocol, and PostgreSQL also defines COPY, asynchronous notification, cancellation, and termination flows.

PostgreSQL 18 introduced frontend/backend protocol version 3.2 while maintaining compatibility mechanisms for earlier protocol 3.x clients. Production tooling should not assume that every driver immediately negotiates the newest minor protocol version.

The important DBRE distinction is:

```text
network connection established
        !=
authentication complete
        !=
session ready
        !=
query successfully executing
```

Connection troubleshooting must identify the stage that failed.

## 1.7.4 Listener Architecture

Important listener controls include:

```text
listen_addresses
port
unix_socket_directories
```

`listen_addresses` controls TCP/IP interfaces on which PostgreSQL listens. `port` controls the TCP port, normally 5432. Unix-domain sockets provide local connectivity on supported platforms.

Listener reachability does not replace authentication or authorization. A TCP socket can be reachable while PostgreSQL still rejects the requested identity/database under `pg_hba.conf`.

## 1.7.5 Authentication Architecture

A client requests a PostgreSQL role identity during startup. `pg_hba.conf` selects the authentication rule based on connection characteristics. PostgreSQL uses the **first matching HBA record**; there is no fallback to later records if authentication fails under that selected rule.

```text
Incoming connection
       |
       v
connection type / source / database / role
       |
       v
first matching pg_hba.conf record
       |
       v
authentication method
       |
       +-- success -> session initialization
       |
       +-- failure -> connection rejected
```

SRE teams should separate DNS/network, TLS/GSS negotiation, HBA selection, authentication, authorization, and capacity rejection into different failure domains.

## 1.7.6 Backend Identity and Lifecycle

Once connected, a backend has a server-side PID. Client libraries such as libpq can expose the PID, and PostgreSQL exposes backend activity through `pg_stat_activity`.

A backend's lifecycle can include:

```text
startup
 -> authentication
 -> idle
 -> active query
 -> transaction
 -> wait
 -> idle in transaction
 -> more work
 -> disconnect
```

A backend that is not consuming CPU can still be operationally significant. It can hold transaction state, snapshots, locks, prepared state, temporary resources, or connection capacity.

## 1.7.7 Connection Capacity

`max_connections` establishes the configured concurrent connection ceiling and influences server resource allocation. Increasing it is not free scalability.

```text
Higher max_connections
        |
        +--> more possible backend processes
        +--> larger shared resource requirements
        +--> greater private-memory exposure
        +--> more scheduling concurrency
        +--> more lock / buffer / I/O competition
```

Capacity planning should distinguish the configured ceiling from the useful concurrency the workload and infrastructure can actually sustain.

## 1.7.8 Reserved Connection Capacity

PostgreSQL provides protected connection capacity through `reserved_connections` and `superuser_reserved_connections`.

When ordinary connection slots are exhausted, roles with `pg_use_reserved_connections` can use the reserved tier; the final superuser-reserved tier remains restricted to superusers. These settings should be treated as incident-response capacity rather than normal application capacity.

Production runbooks should verify that operational access remains possible during a connection storm.

## 1.7.9 Backend Resource Model

Each backend owns private process/session state while coordinating through shared PostgreSQL structures.

```text
Backend process
   |
   +-- memory contexts
   +-- session settings
   +-- transaction / snapshot state
   +-- executor state
   +-- temporary allocations
   |
   +--> shared buffers
   +--> WAL/shared WAL state
   +--> lock manager
   +--> shared statistics and control state
```

This is why backend population, query complexity, parallelism, and workload concurrency must be modeled together.

PostgreSQL 18 adds useful per-backend observability, including per-backend I/O and WAL statistics functions. These can help distinguish one expensive backend from instance-wide pressure.

## 1.7.10 Connection Pooling Architecture

Connection pooling can decouple application-client concurrency from PostgreSQL backend concurrency.

```text
Many application clients
          |
          v
      Pooling layer
          |
          v
Controlled PostgreSQL backend population
          |
          v
      PostgreSQL
```

Pooling is a reliability control as well as a performance technique. It can limit backend creation, authentication churn, memory amplification, and uncontrolled database concurrency.

A pooler does not eliminate capacity planning: pool size, queue depth, transaction semantics, prepared statements, session state, failover behavior, and application retry policy still matter. PgBouncer is covered in later dedicated material.

## 1.7.11 Monitoring

`pg_stat_activity` is the primary server-side view for backend/session activity.

```sql
SELECT
    pid,
    backend_type,
    usename,
    datname,
    application_name,
    client_addr,
    backend_start,
    xact_start,
    query_start,
    state,
    wait_event_type,
    wait_event,
    backend_xid,
    backend_xmin,
    query_id,
    query
FROM pg_stat_activity
ORDER BY backend_start;
```

PostgreSQL 18 also exposes `leader_pid`, which helps associate parallel workers and parallel logical-replication apply workers with their leaders.

Useful companion views/functions include:

- `pg_stat_ssl` for TLS connection state
- `pg_stat_gssapi` for GSSAPI connection state
- `pg_stat_get_backend_io()` for per-backend I/O statistics in PostgreSQL 18
- `pg_stat_get_backend_wal()` for per-backend WAL statistics in PostgreSQL 18
- `pg_backend_memory_contexts` for the current session's memory contexts
- `pg_log_backend_memory_contexts(pid)` for controlled investigation of another backend's memory contexts

Access to detailed activity for other users is security restricted; operational monitoring roles should be designed deliberately, for example with appropriate built-in monitoring privileges rather than unnecessary superuser use.

## 1.7.12 Monitoring Model

A production dashboard should track at least:

- total and usable connection capacity
- active / idle / idle-in-transaction sessions
- connection creation rate
- authentication and startup failures
- backend age and transaction age
- wait-event distribution
- sessions by database, role, application, and client
- TLS/GSS state where relevant
- backend memory and I/O outliers
- connection-pool utilization and queueing
- host/container memory and process pressure

Do not rely only on `count(*) FROM pg_stat_activity`. Connection count without state, age, ownership, and wait context is incomplete.

## 1.7.13 Alerting

Recommended alert classes include:

```text
Warning
- sustained connection utilization approaching usable capacity
- rapid backend creation rate
- growing pool queue depth
- long-lived idle-in-transaction sessions
- abnormal authentication/startup failure rate
- backend population correlated with memory pressure

Critical
- ordinary application connection slots exhausted
- reserved operational capacity being consumed unexpectedly
- connection storm causing widespread application failures
- backend growth associated with OOM or severe resource saturation
```

Thresholds should be derived from tested workload capacity and pool design, not copied from another environment.

## 1.7.14 Failure Scenario — Connection Exhaustion

```text
Application leak / storm
        |
        v
Backend population rises
        |
        v
Ordinary slots exhausted
        |
        v
New sessions rejected
        |
        v
Clients retry aggressively
        |
        v
More startup pressure and wider outage
```

Unbounded retries can amplify a connection defect into an availability incident.

## 1.7.15 Failure Scenario — Too Many Runnable Backends

A database can become unhealthy before reaching `max_connections`.

```text
Backend concurrency rises
      |
      +--> CPU scheduling pressure
      +--> memory amplification
      +--> lock contention
      +--> cache churn
      +--> storage concurrency
      +--> WAL pressure
      |
      v
Latency and timeout rate rise
```

The reliability objective is controlled useful concurrency, not maximum allowed concurrency.

## 1.7.16 Failure Scenario — Idle in Transaction

An application can leave a transaction open while no query is running.

```text
BEGIN
  -> query completes
  -> client stops issuing SQL
  -> backend state = idle in transaction
       |
       +--> locks may remain held
       +--> old snapshot/transaction horizon may remain relevant
       +--> vacuum cleanup can be delayed
       +--> connection capacity remains consumed
```

This state must be distinguished from ordinary `idle` sessions.

Where application semantics allow it, `idle_in_transaction_session_timeout` can provide a guardrail. It should be introduced with application testing rather than enabled blindly.

## 1.7.17 Failure Scenario — Backend Memory Outlier

A single backend can consume abnormal private memory because of query execution, extension behavior, or session state. PostgreSQL 18's backend-level observability makes this easier to investigate.

A safe workflow is to correlate the PID with query/wait state, per-backend I/O/WAL activity, and memory-context information before terminating it. Frequent calls to `pg_log_backend_memory_contexts()` can generate substantial logging overhead and should not be used as continuous polling.

## 1.7.18 Troubleshooting Workflow

When connection-related symptoms appear:

1. Identify whether failure is before TCP/socket establishment, during protocol negotiation, during authentication, at connection-capacity admission, or after session startup.
2. Confirm listener reachability and server state.
3. Inspect PostgreSQL logs for startup/authentication/capacity errors.
4. Check ordinary, reserved, and superuser-reserved capacity.
5. Inspect `pg_stat_activity` by database, role, application, client, state, transaction age, and wait event.
6. Identify connection storms, leaks, long transactions, and idle-in-transaction sessions.
7. Inspect pool queueing and pool limits when a pooler exists.
8. Correlate backend growth with CPU, memory, locks, I/O, WAL, and OOM/cgroup telemetry.
9. Use backend-specific PostgreSQL 18 statistics where they can isolate outliers.
10. Correct the source of excess concurrency before increasing `max_connections`.

## 1.7.19 Safe Backend Intervention

PostgreSQL provides `pg_cancel_backend(pid)` to request cancellation of the current query and `pg_terminate_backend(pid [, timeout])` to terminate a session. These are different operational actions.

Prefer the least disruptive intervention that meets the incident objective:

```text
bad query, session otherwise useful
        -> consider cancel

abandoned / dangerous session
        -> consider terminate after impact analysis
```

Termination rolls back an open transaction and can trigger application reconnect/retry behavior. Only authorized roles can signal other backends, and superuser backends have additional protection.

## 1.7.20 Recovery

Controlled recovery can include:

- throttle or stop the offending application population
- suppress retry storms
- correct pool limits
- cancel an isolated harmful query
- terminate clearly abandoned sessions after impact analysis
- restore protected administrative access
- remediate connection leaks
- apply transaction/session timeouts where appropriate
- resize connection capacity only after memory and concurrency modeling

Indiscriminate session termination can produce rollbacks, reconnect storms, and a second outage wave.

## 1.7.21 Automation and Guardrails

Useful automation includes:

```text
connection utilization dashboards
connection-start rate alerts
application/user/database cardinality reports
idle-in-transaction detection
long-transaction detection
pool queue and saturation alerts
reserved-capacity monitoring
per-backend outlier reports
configuration drift checks
```

Automated destructive termination should be rare and governed by explicit, tested policy. Detection and traffic-control automation are generally safer first-line controls.

## 1.7.22 Production Case Study — Connection Storm

An application release introduces a connection leak:

```text
new application version
 -> connections not returned/closed
 -> backend count rises
 -> database slots approach exhaustion
 -> requests fail
 -> clients retry
 -> connection-start rate accelerates
 -> CPU/memory/startup pressure rises
```

A weak response is to immediately double `max_connections`.

A DBRE response first stabilizes retry behavior and application traffic, confirms protected administrative access, identifies the leaking application population through `application_name`/client/session data, inspects pool behavior, measures backend resource pressure, remediates the leak, and then reassesses the correct capacity envelope.

## 1.7.23 Production Best Practices

1. Treat connection capacity as a reliability budget.
2. Preserve reserved emergency/operational capacity.
3. Use meaningful `application_name` values.
4. Monitor connection creation rate as well as connection count.
5. Use pooling when application concurrency substantially exceeds useful database concurrency.
6. Keep retries bounded and use backoff/jitter at the application layer.
7. Detect long transactions and idle-in-transaction sessions.
8. Capacity-test `max_connections` changes with realistic memory and workload concurrency.
9. Correlate backend population with CPU, memory, lock, WAL, and I/O pressure.
10. Maintain and exercise a connection-exhaustion runbook.
11. Use least-privilege monitoring and backend-signaling roles.
12. Test pooler and client behavior during PostgreSQL failover/restart, not only steady state.

## 1.7.25 Section Summary

PostgreSQL's backend and connection architecture is fundamental to production reliability. Each normal client connection maps to a dedicated backend process, making connection population part of the database's process, memory, CPU, lock, WAL, and I/O capacity model.

PostgreSQL 18 adds useful backend-level observability, but the operational principle remains the same: identify the connection/session lifecycle stage, control useful concurrency, preserve protected administrative access, and diagnose backend state before intervening.

### SRE/DBRE Principle

> Connections are workload. A PostgreSQL connection limit is a capacity boundary, not a target utilization level.
