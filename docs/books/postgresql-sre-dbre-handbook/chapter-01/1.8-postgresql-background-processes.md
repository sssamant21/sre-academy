# Chapter 1 — PostgreSQL Architecture and Internals

## 1.8 — PostgreSQL Background Processes

**Status:** Technical Review  
**Title status:** Recovered from locked Chapter 1 sequence  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.8.1 Purpose

PostgreSQL is a multi-process database system. In addition to client backends, an instance can run auxiliary processes, specialized server processes, and background workers responsible for durability, checkpointing, buffer cleaning, vacuum coordination, WAL handling, recovery, replication, logging, incremental-backup support, parallel execution, logical replication, and extension functionality.

For SRE/DBRE operations, monitor these subsystems by function and progress, not merely by PID existence. A PostgreSQL instance can remain reachable while archiving, replication, vacuum, checkpointing, or another subsystem is degraded and accumulating risk.

## 1.8.2 PostgreSQL 18 Process Taxonomy

PostgreSQL documentation distinguishes several process classes:

- **Backend process** — acts on behalf of a client session.
- **Auxiliary process** — performs a specific internal background task for the instance.
- **Background worker** — runs PostgreSQL- or extension-supplied code in a separate server-managed process and can attach to shared memory and optionally connect to databases.
- **Specialized server processes** — for example WAL senders, which are special backend processes rather than auxiliary processes.

PostgreSQL 18 documents the auxiliary-process set as including the autovacuum launcher (but not autovacuum workers), background writer, checkpointer, logger, startup process, WAL archiver, WAL receiver, WAL summarizer, and WAL writer. The exact process set depends on server role, configuration, workload, and enabled features.

This terminology matters during incident response: do not call every non-client PostgreSQL process a background worker.

## 1.8.3 Process Architecture Map

```text
postgres primary server process
 |
 +-- client backend processes
 |
 +-- auxiliary processes
 |    +-- checkpointer
 |    +-- background writer
 |    +-- WAL writer
 |    +-- autovacuum launcher
 |    +-- logger (when logging collector is used)
 |    +-- archiver (when WAL archiving is active)
 |    +-- startup/recovery process (during recovery/standby operation)
 |    +-- WAL receiver (streaming standby)
 |    +-- WAL summarizer (when summarize_wal is enabled)
 |
 +-- specialized / background worker processes
      +-- WAL senders
      +-- autovacuum workers
      +-- logical replication workers
      +-- replication slot synchronization worker where applicable
      +-- parallel workers
      +-- PostgreSQL 18 I/O workers where applicable
      +-- extension background workers
```

## 1.8.4 Checkpointer

The checkpointer coordinates checkpoints. A checkpoint establishes a recovery boundary and ensures the required dirty heap and index pages are written according to PostgreSQL checkpoint semantics.

Checkpoint activity must be monitored together with WAL generation and storage performance. Excessively frequent checkpoints increase write pressure and can increase WAL volume through additional full-page images; slow checkpoint completion can create sustained storage pressure.

PostgreSQL 18 exposes dedicated checkpointer statistics through `pg_stat_checkpointer`. Detailed checkpoint architecture is covered in Section 1.16.

## 1.8.5 Background Writer

The background writer writes dirty shared buffers in the background so reusable clean buffers are more likely to be available to backends. It is distinct from the checkpointer and does not replace checkpoint durability responsibilities.

Important settings include `bgwriter_delay`, `bgwriter_lru_maxpages`, and `bgwriter_lru_multiplier`. Use `pg_stat_bgwriter` and `pg_stat_io` with OS/cloud storage telemetry to understand write pressure.

## 1.8.6 WAL Writer

The WAL writer writes WAL records from shared memory to WAL files. It is only one component of WAL durability: commit behavior, WAL flushing, storage synchronization, and backend activity also participate in the durability path.

Monitor WAL generation, writes, flushes, synchronization latency, `pg_stat_wal`, PostgreSQL 18 I/O statistics, and underlying storage together. Detailed WAL architecture is covered in Section 1.12.

## 1.8.7 Autovacuum Launcher and Workers

Autovacuum consists of a persistent launcher plus worker processes. The launcher schedules work across databases; workers execute automatic `VACUUM` and/or `ANALYZE` as required.

PostgreSQL 18 adds `autovacuum_worker_slots`, which defines the number of autovacuum worker slots reserved at server start and permits `autovacuum_max_workers` to be adjusted at runtime up to that limit. Running autovacuum workers do not count against `max_connections` or `superuser_reserved_connections`.

Correlate worker occupancy with dead tuples, table churn, transaction-ID/multixact age, long transactions, maintenance I/O, and per-table autovacuum settings. Detailed vacuum architecture is covered in Section 1.17.

## 1.8.8 WAL Archiver

When WAL archiving is enabled, the archiver processes completed WAL segments using `archive_command` or `archive_library`. Persistent archive failure can cause unarchived WAL to accumulate and eventually create a primary-storage incident.

`archive_mode` is a server-start setting. PostgreSQL 18 supports `off`, `on`, and `always`; `always` also enables archiving during archive recovery or standby mode.

Monitor `pg_stat_archiver`, PostgreSQL logs, archive destination health, WAL generation rate, and `pg_wal` capacity together. Detailed archiver architecture is covered in Section 1.23.

## 1.8.9 Startup / Recovery Process

During crash recovery, archive recovery, or standby operation, the startup process applies WAL and advances recovery. A standby can be alive while replay is stalled, waiting for WAL, or unable to keep pace with incoming WAL.

Process existence therefore does not prove recovery health. Measure replay progress and relevant recovery wait events.

## 1.8.10 WAL Receiver

A streaming standby uses a WAL receiver to receive WAL from its upstream server. Diagnose receiver health with `pg_stat_wal_receiver`, logs, receive positions, connectivity, and network/storage telemetry.

A connected receiver does not prove replay is healthy; WAL may be received and flushed while the startup process falls behind applying it.

## 1.8.11 WAL Senders

WAL senders are special backend processes used for physical streaming replication and replication-protocol clients, including logical replication. They are not part of PostgreSQL's documented auxiliary-process set.

Use `pg_stat_replication`, replication slots, LSN positions, and `max_wal_senders` capacity to monitor the sending side. Detailed replication architecture is covered in Sections 1.18 and 1.24.

## 1.8.12 WAL Summarizer — PostgreSQL 18

The WAL summarizer is an auxiliary process used to create WAL summary files required by PostgreSQL incremental backup functionality. It is enabled with:

```text
summarize_wal = on
```

WAL summaries are stored under `pg_wal/summaries`. `wal_summary_keep_time` controls automatic retention of old summary files.

Important observability functions include:

```sql
SELECT * FROM pg_get_wal_summarizer_state();
SELECT * FROM pg_available_wal_summaries();
```

Incremental-backup readiness must include summarizer progress and summary retention, not merely process presence.

## 1.8.13 Logical Replication Workers

Logical replication uses server-managed launcher/apply infrastructure, with synchronization and parallel-apply workers where applicable. Logical replication health is independent from physical replication health.

Monitor subscription state, apply progress, worker availability, errors/conflicts, replication slots, retained WAL, and subscriber capacity. Detailed logical replication architecture is covered in Section 1.20.

## 1.8.14 Parallel Workers

Parallel query and eligible maintenance operations can use parallel workers. Worker availability is constrained by PostgreSQL worker settings and concurrent demand, so a plan can launch fewer workers than planned.

Monitor workers planned versus launched, CPU, memory, I/O, and global worker capacity. Detailed parallel-processing architecture is covered in Section 1.21.

## 1.8.15 PostgreSQL 18 I/O Workers

PostgreSQL 18 introduces an asynchronous I/O subsystem. PostgreSQL monitoring exposes I/O-worker activity/wait events where applicable. This is a major-version-specific architectural change and should be included in PostgreSQL 18 production baselines and upgrade comparisons.

Do not apply PostgreSQL 17-and-earlier I/O assumptions unchanged to PostgreSQL 18.

## 1.8.16 Extension Background Workers

PostgreSQL allows extensions to register background workers that can attach to shared memory and optionally connect to databases. Native background-worker code runs inside the PostgreSQL server environment and carries significant robustness and security implications.

Production extension policy should include approved binaries, version compatibility, security review, restart behavior, worker capacity, rollback planning, and upgrade testing. Detailed extension architecture is covered in Section 1.22.

## 1.8.17 Observing Process Types

Use `pg_stat_activity.backend_type` to classify PostgreSQL server processes:

```sql
SELECT pid, backend_type, datname, usename, state,
       wait_event_type, wait_event
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

On Unix-like platforms, PostgreSQL also updates process titles visible through tools such as `ps`, which is useful for correlating database process identity with OS CPU, memory, I/O, and scheduling telemetry.

Do not build monitoring that depends on a hard-coded process list without accounting for role, configuration, PostgreSQL major version, and extensions.

## 1.8.19 Wait Events

Background and auxiliary processes normally spend substantial time waiting. PostgreSQL 18 exposes process-specific wait events including main-loop waits for the archiver, autovacuum launcher, background writer, checkpointer, WAL sender/receiver, WAL writer, logical replication processes, slot synchronization, I/O workers, and WAL summarizer.

A wait event is context, not automatically an incident. The operational question is whether the subsystem is making the progress required by the workload, RPO/RTO, and SLO.

## 1.8.20 Logging and Correlation

A production logging standard should make process class and PID easy to correlate with database and OS telemetry. PostgreSQL `log_line_prefix` supports `%p` for process ID and `%b` for backend type.

Example:

```text
%m [%p] %b %d %u
```

## 1.8.21 SRE/DBRE Monitoring Model

```text
Subsystem                 Progress / risk signal
----------------------------------------------------------------
Checkpointer              frequency, cause, write/sync time, I/O
Background writer         buffers written, backend writes, I/O
WAL writer / WAL path     WAL rate, write/flush/sync latency
Autovacuum                workers, dead tuples, XID/MXID age
Archiver                  failures, last success, pg_wal growth
Startup/recovery          receive/replay progress and waits
WAL receiver              connection and receive progress
WAL sender                send/flush/replay positions, lag
WAL summarizer            summarized/pending LSN, summary retention
Logical replication       apply progress, errors, slot retention
Parallel workers          planned/launched workers, saturation
I/O workers               AIO progress/waits and storage behavior
Extension workers         health, restart behavior, extension metrics
```

## 1.8.22 Alerting Principles

Prefer impact- and progress-based alerts:

- repeated archive failures plus increasing `pg_wal` usage
- physical replay or logical apply not advancing
- inactive replication consumer plus increasing retained WAL
- transaction-ID/multixact age approaching safety thresholds
- autovacuum backlog growing while workers remain saturated
- checkpoint pressure degrading workload latency
- WAL summarizer not advancing when incremental backups depend on it
- critical extension worker repeatedly restarting
- worker-capacity exhaustion affecting replication or parallel workloads

Thresholds must be workload- and environment-specific.

## 1.8.23 Failure Scenarios

### Archiver failure

```text
archive destination unavailable
 -> archive attempts fail
 -> unarchived WAL retained
 -> pg_wal grows
 -> primary availability risk
```

Restore the archive mechanism and verify backlog drain. Never manually delete required WAL from `pg_wal`.

### Autovacuum worker saturation

Large tables can occupy all available workers for extended periods, delaying maintenance elsewhere. Investigate worker activity, table statistics, oldest transactions, XID/MXID age, I/O, and per-table settings before increasing concurrency.

### Checkpoint pressure

High WAL generation, checkpoint settings, and constrained storage can combine to create sustained write/fsync pressure. Use `pg_stat_checkpointer`, `pg_stat_wal`, `pg_stat_io`, logs, and storage telemetry.

### Receive vs replay stall

Localize replication delay across generation, send, network, receive, flush, and replay. Do not describe every delay as one generic lag metric.

### WAL summarizer / incremental-backup gap

If incremental backups depend on WAL summaries, insufficient summary coverage can make an incremental backup impossible even while the database is healthy. Validate summarizer state, available summaries, and `wal_summary_keep_time` against the backup schedule.

## 1.8.24 Troubleshooting Workflow

1. Identify the affected subsystem and expected process type.
2. Confirm whether the process should exist for the current role/configuration.
3. Inspect logs and `pg_stat_activity.backend_type`.
4. Inspect subsystem-specific statistics.
5. Measure progress over time, not only one snapshot.
6. Check CPU, memory, filesystem capacity, IOPS, latency, network, and worker capacity.
7. Identify accumulated downstream state: WAL, dead tuples, XID age, lag, dirty buffers, or summary backlog.
8. Correct the root dependency before restarting PostgreSQL unnecessarily.
9. Verify backlog drains and SLO behavior returns to baseline.
10. Preserve evidence for RCA.

## 1.8.25 Recovery Guardrails

```text
DO NOT manually delete pg_wal files.
DO NOT terminate internal PostgreSQL processes casually.
DO NOT disable autovacuum globally as routine tuning.
DO NOT force repeated checkpoints as generic troubleshooting.
DO NOT restart merely to clear a symptom without understanding recovery impact.
DO NOT assume process existence proves subsystem health.
```

## 1.8.26 Automation Opportunities

Safe automation should prioritize detection and evidence collection:

```text
archive failure -> pg_stat_archiver + WAL capacity/growth
replication stall -> sender/receiver/replay positions + slots
checkpoint anomaly -> checkpointer/WAL/I/O statistics
vacuum risk -> XID/MXID age + vacuum progress + oldest transactions
incremental backup risk -> WAL summarizer state + available summaries
worker restart loop -> backend types + logs + extension state
```

Destructive automated remediation requires stronger safeguards and explicit policy.

## 1.8.27 Production Case Study — WAL Filesystem Growth

The database remains online while `pg_wal` usage rises rapidly. Deleting WAL files is unsafe.

A DBRE response is to measure WAL generation, inspect archiving, inspect replication slots and physical/logical consumers, check backup/recovery activity, identify the exact retention mechanism, restore or intentionally change that dependency with recovery consequences understood, and verify retained WAL drains safely.

The architectural lesson is that WAL growth is a symptom; archiving, replication, slots, backup/recovery activity, or exceptional WAL generation may be the cause.


## 1.8.29 Section Summary

PostgreSQL background operation is implemented by several distinct process classes. PostgreSQL 18's auxiliary-process terminology, WAL summarizer, asynchronous-I/O architecture, autovacuum worker-slot model, and expanded observability should be reflected explicitly in production runbooks.

The SRE/DBRE objective is not merely to confirm that a process exists. It is to verify that each durability, maintenance, replication, recovery, and worker subsystem is progressing at the rate required to protect availability, performance, RPO/RTO, and recoverability.

### SRE/DBRE Principle

> Monitor PostgreSQL background processes by **function, progress, backlog, and failure consequence** — not by PID existence alone.
