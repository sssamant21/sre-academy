# Chapter 1 — PostgreSQL Architecture and Internals

## 1.8 — PostgreSQL Background Processes

**Status:** Draft → Technical Review Pending  
**Title status:** Recovered from locked Chapter 1 sequence  
**Validation baseline:** PostgreSQL 18.x official documentation

## 1.8.1 Purpose

PostgreSQL is a multi-process database system. In addition to client backend processes, an instance runs auxiliary and background processes responsible for durability, checkpointing, buffer cleaning, vacuum coordination, WAL handling, recovery, replication, logging, and extensibility.

For SRE/DBRE operations, these processes should be treated as separate reliability domains. A database can remain reachable while one subsystem is degraded, and the resulting backlog can later become a storage, latency, replication, or availability incident.

```text
                         postgres
                            |
       +--------------------+--------------------+
       |                    |                    |
       v                    v                    v
 Client Backends      Auxiliary Processes   Background Workers
                            |
       +--------------------+-----------------------------+
       |          |          |          |                 |
       v          v          v          v                 v
 Checkpointer  BgWriter   WAL Writer  Autovacuum       Archiver
                                                    / Replication
```

## 1.8.2 Process Taxonomy

PostgreSQL documentation distinguishes several related process categories.

- **Backend process** — acts on behalf of a client session.
- **Auxiliary process** — performs a specific internal background task for the PostgreSQL instance.
- **Background worker** — runs PostgreSQL- or extension-supplied code in a separate process and can attach to shared memory and optionally connect to a database.

Operationally, the exact process set depends on configuration, server role, enabled features, and extensions.

## 1.8.3 Core Auxiliary Processes

Important PostgreSQL 18 auxiliary processes include the background writer, checkpointer, WAL writer, autovacuum launcher, logger when logging collector is enabled, startup process during recovery, WAL archiver when archiving is enabled, WAL receiver on streaming standbys, and WAL summarizer where applicable.

Some other PostgreSQL features create workers or specialized server processes, including WAL senders, logical replication workers, parallel workers, and extension background workers.

## 1.8.4 Checkpointer

The checkpointer coordinates checkpoints. During a checkpoint, PostgreSQL ensures that dirty data pages required by the checkpoint are flushed and establishes a recovery boundary in WAL.

Checkpoints occur automatically based primarily on checkpoint timing and WAL-volume conditions, and can also be requested explicitly.

```text
Dirty shared buffers
        |
        v
   Checkpointer
        |
        +--> spread checkpoint writes over time
        |
        v
Persistent data files
        |
        v
Recovery boundary advances
```

Checkpoint behavior is a major SRE concern because overly frequent or I/O-constrained checkpoints can create latency spikes and additional WAL/I/O pressure.

PostgreSQL 18 exposes dedicated checkpointer statistics through `pg_stat_checkpointer`.

## 1.8.5 Background Writer

The background writer writes dirty shared buffers so that reusable clean buffers are more likely to be available to server processes.

Its purpose is not to replace checkpoints. It performs incremental background cleaning, while the checkpointer has checkpoint-specific durability responsibilities.

```text
Shared Buffers
     |
     +-- clean pages
     |
     +-- dirty pages
             |
             v
      Background Writer
             |
             v
         File system
```

Important configuration includes:

```text
bgwriter_delay
bgwriter_lru_maxpages
bgwriter_lru_multiplier
```

PostgreSQL exposes background-writer statistics through `pg_stat_bgwriter` and relevant I/O information through `pg_stat_io`.

## 1.8.6 WAL Writer

The WAL writer periodically writes WAL buffers to WAL files. WAL durability also involves backend commit behavior and WAL flushing rules, so the WAL writer must not be viewed as the only component responsible for durable commits.

Conceptually:

```text
Transactions
     |
     v
WAL records
     |
     v
WAL buffers
     |
     +--> WAL writer / backend WAL activity
     |
     v
pg_wal
     |
     v
Durability / recovery / replication
```

WAL generation, write, flush, synchronization, and storage latency must be monitored together.

## 1.8.7 Autovacuum Launcher and Workers

Autovacuum consists of a persistent launcher plus worker processes. The launcher schedules work across databases; workers inspect tables and execute automatic `VACUUM` and/or `ANALYZE` when required.

```text
Autovacuum Launcher
        |
        +--> Worker 1 --> database/table maintenance
        +--> Worker 2 --> database/table maintenance
        +--> Worker N --> database/table maintenance
```

The launcher and workers have different roles. Worker capacity is bounded by autovacuum configuration, and long-running maintenance on large tables can consume available workers and delay maintenance elsewhere.

SREs should correlate autovacuum activity with dead tuples, transaction-ID age, table growth, I/O capacity, lock waits, and worker saturation.

Detailed vacuum and transaction-ID architecture is covered in Section 1.17.

## 1.8.8 WAL Archiver

When WAL archiving is enabled, the archiver copies completed WAL segments to the configured archive destination through the configured archive mechanism.

```text
pg_wal
  |
  v
completed WAL segment
  |
  v
Archiver
  |
  v
Archive destination
```

An archiver failure does not necessarily stop ordinary SQL immediately. Instead, unarchived WAL can accumulate in `pg_wal`. If the condition persists until the WAL filesystem fills, it can become a primary-database availability incident.

This makes archive failure a classic delayed-impact SRE failure mode.

Monitor `pg_stat_archiver`, PostgreSQL logs, archive-destination health, and WAL filesystem capacity together.

## 1.8.9 Startup Process and Recovery

During crash recovery or standby recovery, PostgreSQL uses a startup process to perform recovery work and apply WAL.

On a streaming standby, recovery cooperates with WAL-receive mechanisms to obtain and replay WAL.

```text
Archived/local/streamed WAL
            |
            v
      Startup / Recovery
            |
            v
        WAL replay
            |
            v
      Consistent standby
```

A standby can therefore be alive at the operating-system level while recovery is waiting for WAL or while replay is lagging. Process existence alone is not a sufficient health check.

## 1.8.10 WAL Receiver

A streaming standby uses a WAL receiver process to receive WAL from an upstream server.

Operational health requires more than checking whether the receiver process exists. DBREs should examine receive position, replay position, lag, connection state, upstream WAL availability, and storage/replay throughput.

`pg_stat_wal_receiver` provides WAL-receiver information on a standby.

## 1.8.11 WAL Sender Processes

WAL sender processes stream WAL or logical replication data to connected replicas or replication clients.

WAL senders are created as needed and are governed by replication configuration such as `max_wal_senders`.

For physical replication, monitor sender state and LSN positions through `pg_stat_replication` on the primary.

```text
Primary WAL
    |
    v
WAL Sender
    |
    v
Network
    |
    v
WAL Receiver
    |
    v
Standby recovery
```

## 1.8.12 Logical Replication Processes

Logical replication uses background infrastructure including a logical replication launcher and apply/worker processes. Exact worker behavior depends on PostgreSQL version and subscription activity.

Logical replication must be monitored independently from physical streaming replication because a PostgreSQL instance can have healthy physical replication while a logical subscription is delayed or failed.

Detailed logical replication architecture is covered in Section 1.20.

## 1.8.13 Parallel Workers

Parallel query execution can create parallel worker processes. These workers cooperate with a leader process to execute portions of a parallel plan.

Worker availability is constrained by PostgreSQL worker settings and current system usage. Therefore, a plan may be parallel-capable without receiving the expected number of workers at runtime.

Detailed parallel-processing architecture is covered in Section 1.21.

## 1.8.14 Extension Background Workers

PostgreSQL provides a background-worker framework that allows extensions to run user-supplied C code in server-managed processes. Such workers can attach to PostgreSQL shared memory and may connect internally to databases.

This capability is powerful but introduces reliability and security risk because extension code executes inside the PostgreSQL server environment.

Production policy should therefore require extension review, version compatibility validation, controlled rollout, rollback planning, and observation of worker restart behavior.

Detailed extension architecture is covered in Section 1.22.

## 1.8.15 Observing PostgreSQL Process Types

`pg_stat_activity` exposes a `backend_type` field that identifies many PostgreSQL process types.

```sql
SELECT
    pid,
    backend_type,
    datname,
    usename,
    state,
    wait_event_type,
    wait_event
FROM pg_stat_activity
ORDER BY backend_type, pid;
```

Examples can include:

```text
client backend
autovacuum launcher
autovacuum worker
background writer
checkpointer
archiver
startup
walreceiver
walsender
walwriter
walsummarizer
logical replication launcher
logical replication worker
parallel worker
```

Extension-provided workers can introduce additional backend types.

At the operating-system layer, `ps` can also identify many PostgreSQL process titles.

## 1.8.16 Process-Specific Statistics

A production monitoring platform should use PostgreSQL's specialized statistics rather than relying only on process existence.

Important sources include:

```text
pg_stat_activity
pg_stat_io
pg_stat_bgwriter
pg_stat_checkpointer
pg_stat_wal
pg_stat_archiver
pg_stat_replication
pg_stat_wal_receiver
pg_stat_replication_slots
pg_stat_subscription
pg_stat_subscription_stats
```

The applicable views depend on role and enabled features.

## 1.8.17 Wait Events

Internal PostgreSQL processes expose wait events through the activity monitoring infrastructure. Examples include main-loop waits for the archiver, autovacuum launcher, background writer, checkpointer, WAL receiver, WAL sender, WAL writer, startup/recovery, and logical replication processes.

A wait event is context, not automatically an error. Many background processes normally spend substantial time waiting for work.

The correct question is not simply:

```text
Is the process waiting?
```

but:

```text
Is the process making the progress required by the workload and SLO?
```

## 1.8.18 Logging Background Processes

For incident correlation, PostgreSQL logging can include backend type and process ID in `log_line_prefix`.

Example design:

```text
%m [%p] %b %d %u
```

where `%b` represents backend type and `%p` process ID.

A production logging standard should allow operators to correlate errors with the responsible PostgreSQL process class.

## 1.8.19 SRE Monitoring Model

Monitor background processes by **function and progress**, not only by PID.

```text
Process / subsystem      Primary SRE signal
------------------------------------------------
Checkpointer              checkpoint frequency/duration/I/O
Background writer         buffer cleaning/write activity
WAL writer                WAL write/flush pressure
Autovacuum                worker use, dead tuples, XID age
Archiver                  archive failures + pg_wal growth
Startup/recovery          replay progress and recovery waits
WAL receiver              receive progress and connectivity
WAL sender                replication state and LSN lag
Logical replication       apply progress/errors
Parallel workers          worker availability/execution behavior
Extension workers         process health + extension-specific metrics
```

## 1.8.20 Alerting Principles

Avoid alerts such as:

```text
"background process exists"
```

as the primary health model.

Prefer alerts tied to impact or stalled progress, for example:

```text
archive failures increasing + pg_wal utilization rising
replication replay not advancing
transaction-ID age approaching safety threshold
autovacuum backlog increasing
checkpoint duration approaching checkpoint interval
WAL/storage latency above established baseline
critical extension worker repeatedly restarting
```

Thresholds should be workload- and environment-specific rather than copied blindly between systems.

## 1.8.21 Failure Scenario — Archiver Failure

```text
Archive destination unavailable
          |
          v
Archiver cannot archive WAL
          |
          v
Unarchived WAL retained
          |
          v
pg_wal usage grows
          |
          v
Filesystem approaches full
          |
          v
Primary availability risk
```

### Investigation

```sql
SELECT * FROM pg_stat_archiver;
```

Then correlate with:

```text
PostgreSQL logs
pg_wal filesystem utilization
archive destination health
archive command/library errors
WAL generation rate
```

### Recovery principle

Restore the archive path/mechanism safely and confirm successful archival resumes before treating the incident as resolved. Do not manually delete required WAL from `pg_wal` as a space-recovery shortcut.

## 1.8.22 Failure Scenario — Autovacuum Worker Saturation

```text
Several large tables require vacuum
          |
          v
Workers occupied for long periods
          |
          v
Other tables wait
          |
          v
Dead tuples / XID age increase
          |
          v
Bloat or wraparound risk
```

Investigate active autovacuum workers, table statistics, transaction age, long-running transactions, maintenance I/O, and per-table autovacuum configuration before increasing worker counts. More workers can increase concurrent I/O and memory pressure.

## 1.8.23 Failure Scenario — Checkpoint Pressure

```text
High WAL generation
       +
checkpoint configuration
       +
slow storage
       |
       v
checkpoint pressure
       |
       v
write/fsync latency
       |
       v
application latency
```

Use `pg_stat_checkpointer`, `pg_stat_io`, `pg_stat_wal`, storage telemetry, and logs to distinguish checkpoint frequency from slow checkpoint execution.

## 1.8.24 Failure Scenario — Standby Receiver or Replay Stalls

```text
Primary generating WAL
          |
          v
network / sender / receiver
          |
          v
standby WAL receive
          |
          v
replay
```

A failure can occur at any stage. Compare send, receive, flush, and replay progress rather than describing all replication delay as a single generic "lag" metric.

## 1.8.25 Troubleshooting Workflow

When a PostgreSQL background subsystem appears unhealthy:

1. Identify the affected process type.
2. Determine whether the process should exist for the current server role/configuration.
3. Check PostgreSQL logs for process-specific errors.
4. Inspect `pg_stat_activity` and relevant wait events.
5. Inspect the subsystem-specific statistics view.
6. Verify progress over time, not only a single snapshot.
7. Check CPU, memory, filesystem capacity, IOPS, latency, and network dependencies.
8. Identify downstream accumulation such as WAL, dead tuples, replication lag, or dirty buffers.
9. Correct the root dependency before restarting PostgreSQL unnecessarily.
10. Validate backlog drain and return to baseline after remediation.

## 1.8.26 Recovery Guardrails

During background-process incidents:

```text
DO NOT delete pg_wal files manually.
DO NOT terminate internal PostgreSQL processes casually.
DO NOT restart the database merely to clear a symptom without understanding the backlog.
DO NOT disable autovacuum globally as a routine performance fix.
DO NOT force repeated checkpoints as a generic troubleshooting step.
DO NOT assume a running process proves subsystem health.
```

A forced restart can convert a degraded subsystem into a larger availability event and can hide evidence needed for RCA.

## 1.8.27 Automation Opportunities

Safe automation should focus first on detection and evidence collection.

Examples:

```text
archive failure -> capture pg_stat_archiver + WAL filesystem usage
replication stall -> capture sender/receiver/replay LSN positions
checkpoint anomaly -> capture checkpointer/WAL/I/O statistics
vacuum risk -> capture XID age + table vacuum statistics
worker restart loop -> capture logs + backend types + extension state
```

Automatic destructive remediation should require much stronger safeguards than automatic diagnosis.

## 1.8.28 Production Case Study — WAL Filesystem Growth

### Symptom

The database remains online, but `pg_wal` utilization rises rapidly.

### Weak response

```text
Delete old WAL files to recover disk space.
```

This is unsafe.

### DBRE investigation

```text
1. Measure WAL generation rate.
2. Check pg_stat_archiver.
3. Check replication slots and retained WAL.
4. Check standby/replication health.
5. Check archive destination and errors.
6. Determine which subsystem is retaining WAL.
7. Restore the failed dependency.
8. Verify retained WAL begins draining safely.
```

The important architectural lesson is that `pg_wal` growth is a symptom. The retaining subsystem may be archiving, replication, slots, backup/recovery activity, or unusually high WAL generation.

## 1.8.29 Production Readiness Checklist

```text
□ Required PostgreSQL process types are understood for each server role
□ Background-process logs are identifiable by PID/backend type
□ Checkpointer metrics are collected
□ Background-writer and I/O metrics are collected
□ WAL generation/write metrics are collected
□ Autovacuum workers and XID age are monitored
□ Archiver success/failure is monitored where archiving is enabled
□ pg_wal filesystem capacity is monitored
□ Physical replication send/receive/replay progress is monitored
□ Logical replication is monitored separately where used
□ Worker-capacity settings are documented
□ Extension background workers are inventoried
□ Restart behavior of critical extensions is tested
□ Incident runbooks prohibit unsafe WAL deletion
□ Alerts detect stalled progress and growing backlogs
□ Recovery validation confirms backlog drain after remediation
```

## 1.8.30 SRE/DBRE Principle

> A PostgreSQL background process is healthy only when the subsystem it serves is making the required progress. Process existence alone is not a production health signal.

## 1.8.31 Section Summary

PostgreSQL background and auxiliary processes distribute essential database responsibilities across specialized operating-system processes. Checkpointing, buffer cleaning, WAL handling, vacuum coordination, archiving, recovery, replication, parallel execution, logical replication, and extension workloads each have distinct operational signals and failure modes.

For SRE/DBRE teams, the correct monitoring model is therefore:

```text
Process identity
      +
Process state
      +
Subsystem statistics
      +
Progress over time
      +
Resource dependencies
      +
Backlog / downstream impact
      =
Operational health
```
