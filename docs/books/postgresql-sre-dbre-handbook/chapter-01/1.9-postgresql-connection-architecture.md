# Chapter 1 — PostgreSQL Architecture and Internals

## 1.9 — PostgreSQL Connection Architecture

**Status:** Technical Review  
**Title status:** Locked Master TOC v1.0  
**Validation baseline:** PostgreSQL 18.4 official documentation

## 1.9.1 Purpose

PostgreSQL uses a client/server connection model. A production connection is not simply a TCP socket: it passes through network reachability, listener configuration, optional TLS negotiation, PostgreSQL startup protocol, host-based authentication, database authorization, backend process creation, and session initialization.

```text
Application / Client
        |
        v
DNS / Network / Load Balancer / Pooler
        |
        v
TCP/IP or Unix-domain Socket
        |
        v
PostgreSQL Listener
        |
        v
Startup / SSL negotiation
        |
        v
pg_hba.conf rule selection
        |
        v
Authentication
        |
        v
Database CONNECT + role/object authorization
        |
        v
Backend Process / Session
        |
        v
SQL Workload
```

For SRE/DBRE operations, each stage is a distinct failure domain and should be diagnosed separately.

## 1.9.2 PostgreSQL Client/Server Connection Model

The PostgreSQL server program is `postgres`. PostgreSQL normally creates a separate backend server process for each accepted client connection. After establishment, the client communicates with its associated backend without the supervising server process executing the client's SQL workload.

This process-per-connection model makes connection count a database, memory, operating-system, and reliability concern.

## 1.9.3 Connection Endpoints

PostgreSQL can accept connections through TCP/IP and Unix-domain sockets.

Important server settings include:

```text
listen_addresses
port
unix_socket_directories
```

`listen_addresses` determines which TCP/IP interfaces accept connection attempts. PostgreSQL 18 defaults it to `localhost`. The standard PostgreSQL TCP port is `5432`. These listener settings are server-start parameters.

A production SRE must distinguish:

```text
Server not listening
        !=
Network cannot reach server
        !=
TLS negotiation failure
        !=
Authentication rejected
        !=
Database CONNECT denied
        !=
Connection slots exhausted
```

## 1.9.4 Connection Startup Protocol

A PostgreSQL frontend opens a connection and sends startup information identifying the requested user, database, protocol version, and optional startup parameters. SSL/GSS negotiation can occur before the normal startup message depending on client/server configuration.

Conceptually:

```text
TCP / Socket established
        |
        +--> optional SSL/GSS negotiation
        |
        v
Startup Message
        |
        +-- user
        +-- database
        +-- protocol version
        +-- optional parameters
        |
        v
Authentication exchange
        |
        v
Backend/session initialization
```

Connection troubleshooting should preserve this ordering because failures at different stages have different causes and logs.

## 1.9.5 pg_hba.conf Architecture

Client authentication policy is primarily controlled by `pg_hba.conf`.

Each authentication record matches properties including connection type, requested database, requested user, and client address/network where applicable, then selects an authentication method.

The **first matching HBA record is used**. PostgreSQL does not fall through to later rules when authentication under the selected rule fails. This ordering is operationally critical.

Example conceptual policy:

```text
# TYPE    DATABASE  USER       ADDRESS        METHOD
hostssl   appdb     app_role   10.20.0.0/16   scram-sha-256
hostssl   all       dba_role   10.30.1.0/24   scram-sha-256
```

Use `pg_hba_file_rules` to inspect parsed rules and detect syntax/configuration errors. On Unix-like systems, HBA changes are re-read at startup or after SIGHUP/configuration reload; Windows applies HBA changes to subsequent new connections immediately.

## 1.9.6 Authentication Architecture

PostgreSQL supports multiple authentication mechanisms, including SCRAM-SHA-256, GSSAPI, SSPI, peer, LDAP, RADIUS, certificate, PAM, OAuth, and platform-specific methods.

For password authentication, SCRAM-SHA-256 is the modern target architecture. PostgreSQL 18 deprecates MD5-encrypted passwords; new deployments should not design around MD5 password storage.

Authentication answers:

```text
Who is attempting to connect?
```

Authorization answers:

```text
What may the authenticated role access or perform?
```

These are separate controls.

## 1.9.7 Database CONNECT Authorization

Passing `pg_hba.conf` authentication is not sufficient. A role must also have permission to connect to the requested database.

Production access design therefore combines:

```text
HBA authentication policy
        +
Database CONNECT privilege
        +
Role / schema / object privileges
```

A PostgreSQL connection is associated with one database. A client cannot directly access multiple databases through one connection; separate connections are required.

## 1.9.8 Connection Capacity Architecture

Important PostgreSQL 18 settings include:

```text
max_connections
reserved_connections
superuser_reserved_connections
```

`max_connections` defines the maximum concurrent server connections. PostgreSQL sizes some resources directly from this setting, including shared-memory requirements, so increasing it is not a free scalability mechanism.

`reserved_connections` preserves slots for roles granted `pg_use_reserved_connections`. `superuser_reserved_connections` preserves the final emergency slots for superusers after ordinary and reserved-role capacity is exhausted.

Conceptually:

```text
max_connections
      |
      +-- normal connection capacity
      +-- reserved_connections
      +-- superuser_reserved_connections (final emergency reserve)
```

Operational monitoring must distinguish configured maximum from **usable application capacity**. Emergency slots should never be treated as ordinary pool capacity.

On a physical standby, `max_connections` must be configured at least as high as on the primary; otherwise queries cannot be accepted on the standby after recovery reaches the relevant parameter state.

## 1.9.9 Why High Connection Counts Matter

Because PostgreSQL normally uses a backend process per connection, excessive sessions can create pressure across multiple domains:

```text
Connections increase
      |
      +-- backend processes increase
      +-- potential private memory increases
      +-- scheduler/process overhead increases
      +-- lock/session state increases
      +-- authentication/startup churn increases
      +-- aggregate work_mem exposure increases
      |
      v
Database reliability risk
```

The correct response to application scale is therefore not automatically to raise `max_connections`.

## 1.9.10 Connection Pooling Architecture

A connection pooler can decouple application concurrency from PostgreSQL backend concurrency.

```text
Application instances
   |   |   |   |   |
   +---+---+---+---+
           |
           v
      Connection Pooler
           |
      controlled backend
       connection count
           |
           v
       PostgreSQL
```

PgBouncer is a common production pooler. Pool sizing must be based on database CPU, memory, I/O, workload concurrency, transaction behavior, and failover design rather than matching application thread or pod counts.

Poolers introduce their own failure domains: pool exhaustion, queue growth, authentication/configuration mismatch, transaction-vs-session pooling incompatibility, stale writer routing after failover, and retry amplification.

## 1.9.11 Client-Side Connection Controls

PostgreSQL clients such as libpq support host lists, ports, SSL behavior, authentication requirements, target-session selection, and `connect_timeout`.

A production client should avoid unbounded connection-establishment waits. Timeouts and retry behavior must fit inside application request deadlines and HA/failover objectives.

Bad pattern:

```text
request
  -> connection attempt waits too long
  -> application threads accumulate
  -> retries multiply
  -> connection storm
```

Better pattern:

```text
bounded timeout
  + controlled retry
  + exponential backoff
  + jitter
  + pooling
  + failover-aware routing
```

## 1.9.12 TLS and Network Security

Remote database connections should use encryption and server identity verification appropriate to the threat model.

```text
Network segmentation
        |
        v
TLS encryption
        |
        v
Server identity validation
        |
        v
Client authentication
        |
        v
Database authorization
```

Encryption does not replace authentication, and authentication does not replace network policy. Production standards should explicitly define accepted client TLS modes and certificate-validation requirements rather than relying on client defaults.

## 1.9.13 Session State and Pooling Semantics

Once connected, a backend can hold session-specific state including transactions, GUC overrides, prepared statements, temporary objects, advisory/session locks, and LISTEN state.

This matters when poolers use transaction pooling because successive application transactions can run on different PostgreSQL backends. Applications must not depend on session affinity unless the pooling mode guarantees it.

## 1.9.14 Monitoring Connections

`pg_stat_activity` is a primary operational view for connection/session analysis.

```sql
SELECT
    datname,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    count(*) AS sessions
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY
    datname, usename, application_name, client_addr,
    state, wait_event_type, wait_event
ORDER BY sessions DESC;
```

SRE monitoring should distinguish at least active, idle, idle-in-transaction, waiting/blocked, long-running transactions, authentication failures, connection creation rate, and remaining admission headroom.

Do not count auxiliary processes and background workers as ordinary application sessions when analyzing client connection demand.

## 1.9.15 Connection Utilization and Headroom

A simplistic indicator is:

```text
current client sessions / max_connections
```

but production alerting should use usable application capacity after preserving `reserved_connections` and `superuser_reserved_connections`.

More useful questions are:

```text
How many normal slots remain?
Are reserved-role slots being consumed?
Is final superuser emergency capacity still available?
Is the pool queue growing before PostgreSQL itself reaches max_connections?
```

Thresholds should be derived from pool architecture and recovery requirements rather than copied between systems.

## 1.9.16 Idle-in-Transaction Risk

An `idle in transaction` session is not equivalent to an ordinary idle connection. An open transaction can retain snapshots and locks and delay MVCC cleanup depending on its age and activity.

```text
Application begins transaction
        |
        v
Application stops issuing SQL
        |
        v
Session remains idle in transaction
        |
        +-- transaction age increases
        +-- locks may remain held
        +-- cleanup horizon may be constrained
        |
        v
Production degradation
```

Monitor both count and age. `idle_in_transaction_session_timeout` can be an effective guardrail when application semantics have been tested for it.

## 1.9.17 Connection Storm Failure Scenario

A common incident occurs after an application restart, network recovery, or database failover:

```text
Database briefly unavailable
        |
        v
Many application instances retry
        |
        v
Simultaneous TCP/TLS/authentication attempts
        |
        v
Backend creation spike
        |
        v
CPU / memory pressure
        |
        v
Connections become slower
        |
        v
More retries
        |
        v
Retry storm
```

Controls include pooling, bounded retry, exponential backoff, jitter, startup rate limiting, and preserved database connection headroom.

## 1.9.18 Connection Exhaustion Failure Scenario

Symptoms can include errors that remaining slots are reserved or that connection capacity is exhausted.

Investigation sequence:

```text
1. Confirm server/listener reachability.
2. Check current client connection count and admission headroom.
3. Group sessions by user, database, application, and client source.
4. Identify idle and idle-in-transaction sessions.
5. Check pool occupancy and queue depth.
6. Identify recent deployment/retry storms or connection leaks.
7. Preserve emergency administrative access.
8. Reduce demand before increasing max_connections.
```

Do not restart PostgreSQL merely to clear sessions unless the incident requires it and the recovery impact is understood.

## 1.9.19 Authentication Failure Troubleshooting

Classify connection failures by layer:

```text
connection refused
    -> listener/endpoint problem

network timeout
    -> routing/firewall/network/LB problem

TLS/certificate error
    -> encryption/identity configuration

no pg_hba.conf entry
    -> HBA policy mismatch

password authentication failed
    -> credential/authentication issue

role does not exist
    -> role provisioning/connection-string issue

database does not exist
    -> database/connection-string issue

CONNECT denied
    -> database authorization

remaining slots reserved / too many connections
    -> admission capacity, pool, or session leak
```

Correlate client errors with PostgreSQL logs and network/pool telemetry.

## 1.9.20 Safe HBA Change Procedure

Production HBA changes should follow a controlled workflow:

```text
Review requested access
        |
        v
Apply least-privilege rule in correct order
        |
        v
Validate parsed HBA rules
        |
        v
Reload where required
        |
        v
Verify intended connection
        |
        v
Verify unintended access remains denied
        |
        v
Record and audit change
```

Useful validation:

```sql
SELECT line_number, type, database, user_name, address, auth_method, error
FROM pg_hba_file_rules
ORDER BY line_number;
```

After editing on Unix-like systems:

```sql
SELECT pg_reload_conf();
```

A non-null `error` in `pg_hba_file_rules` must be investigated before considering the change successful.

## 1.9.21 SRE Alerting Model

Recommended connection-domain alert categories include connection utilization approaching normal usable capacity, loss of reserved administrative headroom, abnormal connection creation rate, authentication failure spikes, idle-in-transaction age, pool saturation/queue growth, connection latency, TLS/certificate expiry risk, and repeated retry storms.

Alerts should identify the responsible database, role, application, pool, and client source where telemetry permits.

## 1.9.22 Automation Guardrails

Safe automation can collect connection inventory, classify session states, identify oldest transactions, validate HBA parsing, calculate admission headroom, correlate authentication failures, and compare pool limits with database capacity.

Risky automation includes indiscriminately terminating sessions whenever a threshold is exceeded. Before termination, automation should understand ownership, transaction state, business criticality, lock impact, and whether the workload will immediately reconnect.

## 1.9.23 Production Case Study — Connection Leak

```text
Application deployment
      |
      v
Pool / connection lifecycle defect
      |
      v
Connections steadily increase
      |
      v
Normal connection headroom exhausted
      |
      v
New application requests fail
```

A disciplined DBRE response is:

```text
preserve admin access
      -> identify sessions by application_name/user/client_addr
      -> inspect pool metrics
      -> determine idle vs active vs transaction state
      -> stop the source of connection growth
      -> safely drain/terminate unnecessary sessions if required
      -> correct pool configuration/lifecycle
      -> validate recovery
      -> add growth/headroom alerting
```

Simply increasing `max_connections` can hide the leak while increasing future shared-resource and memory exposure.

## 1.9.24 Production Readiness Checklist

- `listen_addresses`, port, and socket paths intentionally configured
- network paths/firewalls/load balancers documented
- TLS and server-identity policy documented
- `pg_hba.conf` under controlled change management
- HBA ordering and `pg_hba_file_rules` validation understood
- SCRAM-SHA-256 migration/status understood
- database `CONNECT` privileges reviewed
- `max_connections` capacity justified
- `reserved_connections` and final superuser slots protected
- standby `max_connections` compatibility validated
- pooler architecture and pooling mode documented
- pool limits aligned with database capacity
- client connection timeout configured
- retry/backoff/jitter behavior tested
- `application_name` populated where practical
- idle-in-transaction monitoring/guardrails enabled
- authentication failures monitored
- normal and emergency connection headroom alerted separately
- failover/reconnect behavior load-tested
- emergency administrative connection runbook tested

## 1.9.25 SRE/DBRE Principle

> A PostgreSQL connection is a resource-allocation and reliability event, not merely a network socket. Production connection architecture must control admission, authentication, authorization, backend concurrency, retries, pooling, and emergency headroom as one system.
