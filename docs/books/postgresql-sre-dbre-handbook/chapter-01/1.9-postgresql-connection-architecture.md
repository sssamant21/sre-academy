# Chapter 1 — PostgreSQL Architecture and Internals

## 1.9 — PostgreSQL Connection Architecture

**Status:** Draft → Technical Review Pending  
**Title status:** Recovered from locked Master TOC v1.0 sequence  
**Validation baseline:** PostgreSQL 18.x official documentation

## 1.9.1 Purpose

PostgreSQL uses a client/server connection model. A production connection is not simply a TCP socket: it passes through network reachability, listener configuration, optional TLS negotiation, PostgreSQL startup protocol, host-based authentication, role/database authorization, backend process creation, and session initialization.

```text
Application / Client
        |
        v
DNS / Network / Load Balancer / Pooler
        |
        v
TCP/IP or Unix-domain Socket
        |
        v
PostgreSQL Listener
        |
        v
Startup Message
        |
        v
pg_hba.conf Rule Selection
        |
        v
Authentication
        |
        v
Role + Database Authorization
        |
        v
Backend Process / Session
        |
        v
SQL Workload
```

For SRE/DBRE operations, each stage is a distinct failure domain.

## 1.9.2 PostgreSQL Client/Server Connection Model

The PostgreSQL server program is `postgres`. It accepts client connections and PostgreSQL normally creates a separate backend server process for each connection. After connection establishment, the client communicates with its associated backend process.

This process-per-connection model makes connection count a database, memory, operating-system, and reliability concern.

## 1.9.3 Connection Endpoints

PostgreSQL can accept connections through TCP/IP and Unix-domain sockets.

Important server settings include:

```text
listen_addresses
port
unix_socket_directories
```

`listen_addresses` determines which TCP/IP interfaces accept connection attempts. PostgreSQL 18 defaults this setting to `localhost`. The standard PostgreSQL TCP port is `5432`.

A production SRE must distinguish:

```text
Server not listening
        !=
Network cannot reach server
        !=
Authentication rejected
        !=
Database authorization rejected
        !=
Connection slots exhausted
```

## 1.9.4 Connection Startup Protocol

A PostgreSQL frontend opens a connection and sends a startup message identifying information such as the requested database, user, and protocol version. The server evaluates the request and determines whether authentication is required.

Conceptually:

```text
TCP / Socket established
        |
        v
Startup Message
        |
        +-- user
        +-- database
        +-- protocol version
        +-- optional startup parameters
        |
        v
Authentication negotiation
        |
        v
Session initialization
```

TLS negotiation can precede the normal startup exchange when SSL/TLS is used.

## 1.9.5 pg_hba.conf Architecture

Client authentication policy is primarily controlled by `pg_hba.conf`.

Each authentication record matches properties including:

```text
connection type
requested database
requested user
client address/network
```

and selects an authentication method.

The first matching HBA record is used. PostgreSQL does not fall through to later records when authentication using the selected rule fails.

This ordering is operationally critical.

Example conceptual policy:

```text
# TYPE  DATABASE  USER       ADDRESS        METHOD
hostssl appdb     app_role   10.20.0.0/16   scram-sha-256
hostssl all       dba_role   10.30.1.0/24   scram-sha-256
```

Production changes should be validated with `pg_hba_file_rules` before or immediately after reload.

## 1.9.6 Authentication Architecture

PostgreSQL supports multiple authentication mechanisms, including SCRAM-SHA-256, GSSAPI, SSPI, peer, LDAP, RADIUS, certificate, PAM, OAuth, and other platform-specific mechanisms.

For password authentication, SCRAM-SHA-256 is the modern preferred mechanism. MD5-encrypted password support is deprecated in PostgreSQL 18 and should not be the target architecture for new deployments.

Authentication answers:

```text
Who is attempting to connect?
```

Authorization answers:

```text
What may that authenticated role access or perform?
```

These must not be treated as the same control.

## 1.9.7 Database CONNECT Authorization

Passing `pg_hba.conf` authentication is not sufficient by itself. A role must also be permitted to connect to the requested database.

Production access design should therefore consider both:

```text
HBA authentication policy
        +
Database CONNECT privilege
        +
Role/object privileges
```

This layered model allows network/authentication controls and database authorization controls to remain separate.

## 1.9.8 Connection Capacity Architecture

Important PostgreSQL 18 settings include:

```text
max_connections
reserved_connections
superuser_reserved_connections
```

`max_connections` defines the maximum concurrent server connections. PostgreSQL sizes some resources based on this value, so increasing it is not a free scalability mechanism.

`reserved_connections` can preserve slots for roles granted `pg_use_reserved_connections`, while `superuser_reserved_connections` maintains final emergency capacity for superusers.

Conceptually:

```text
max_connections
      |
      +-- normal application capacity
      +-- reserved_connections
      +-- superuser_reserved_connections
```

Emergency connection capacity should be deliberately protected in production.

## 1.9.9 Why High Connection Counts Matter

Because PostgreSQL normally uses a backend process per connection, excessive sessions can create pressure across multiple domains:

```text
Connections increase
      |
      +-- backend processes increase
      +-- per-session memory potential increases
      +-- scheduler/process overhead increases
      +-- lock/session state increases
      +-- authentication churn may increase
      |
      v
Database reliability risk
```

The correct response to application scale is therefore not automatically to raise `max_connections`.

## 1.9.10 Connection Pooling Architecture

A connection pooler can decouple application concurrency from PostgreSQL backend concurrency.

```text
Application instances
   |   |   |   |   |
   +---+---+---+---+
           |
           v
      Connection Pooler
           |
      controlled backend
       connection count
           |
           v
       PostgreSQL
```

PgBouncer is a common production pooler. Pool sizing must be based on database capacity, workload behavior, transaction characteristics, and failover design rather than simply matching application thread counts.

## 1.9.11 Client-Side Connection Controls

PostgreSQL client libraries such as libpq support connection controls including host lists, ports, SSL behavior, authentication requirements, and `connect_timeout`.

A production client should avoid unbounded connection establishment waits. Timeouts and retry behavior must be coordinated with application request deadlines and HA/failover behavior.

Bad pattern:

```text
request
  -> connection attempt waits too long
  -> application threads accumulate
  -> retries multiply
  -> connection storm
```

Better pattern:

```text
bounded timeout
  + controlled retry
  + jitter/backoff
  + connection pooling
  + failover-aware routing
```

## 1.9.12 TLS and Network Security

Remote database connections should be designed with encryption and server identity verification appropriate to the environment.

The connection security path can include:

```text
Network segmentation
        |
        v
TLS encryption
        |
        v
Server certificate validation
        |
        v
Client authentication
        |
        v
Database authorization
```

Encryption does not replace authentication, and authentication does not replace network policy.

## 1.9.13 Session State

Once connected, each backend has session-specific state. Examples include transaction state, configuration overrides, prepared statements, temporary objects, and session-level locks.

This matters when using poolers because pooling modes may change whether application requests consistently return to the same PostgreSQL backend.

Applications must not assume session affinity unless the connection architecture guarantees it.

## 1.9.14 Monitoring Connections

`pg_stat_activity` is a primary operational view for connection and session analysis.

Example:

```sql
SELECT
    datname,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event,
    count(*) AS sessions
FROM pg_stat_activity
GROUP BY
    datname,
    usename,
    application_name,
    client_addr,
    state,
    wait_event_type,
    wait_event
ORDER BY sessions DESC;
```

SRE monitoring should distinguish at least:

```text
active
idle
idle in transaction
waiting/blocked
long-running transactions
connection establishment failures
connection utilization
```

## 1.9.15 Connection Utilization

A useful capacity indicator is connection utilization relative to configured capacity.

Conceptually:

```text
connection utilization = current sessions / max_connections
```

However, alerting must preserve reserved and superuser emergency capacity rather than treating every configured slot as normal application capacity.

Operational thresholds should be derived from the environment's pool architecture and recovery requirements rather than copied blindly between systems.

## 1.9.16 Idle-in-Transaction Risk

An `idle in transaction` session is not equivalent to an ordinary idle connection.

A session that leaves a transaction open can retain snapshots and locks and can interfere with vacuum cleanup depending on what the transaction has done and its age.

Typical failure chain:

```text
Application begins transaction
        |
        v
Application stops issuing SQL
        |
        v
Session remains idle in transaction
        |
        +-- transaction age increases
        +-- locks may remain held
        +-- MVCC cleanup may be constrained
        |
        v
Production degradation
```

Monitoring should therefore track both count and age.

## 1.9.17 Connection Storm Failure Scenario

A common production incident occurs after an application restart or database failover:

```text
Database briefly unavailable
        |
        v
Many application instances retry
        |
        v
Simultaneous authentication attempts
        |
        v
Backend process creation spike
        |
        v
CPU / memory pressure
        |
        v
Connections become slower
        |
        v
More retries
        |
        v
Retry storm
```

Controls include connection pooling, bounded retry, exponential backoff, jitter, startup rate limiting, and preserving database connection headroom.

## 1.9.18 Connection Exhaustion Failure Scenario

Symptoms may include errors indicating that remaining connection slots are reserved or that the server has reached its connection capacity.

Investigation sequence:

```text
1. Confirm server reachability
2. Check current connection count
3. Group sessions by user/database/application/client
4. Identify idle and idle-in-transaction sessions
5. Check pool configuration
6. Identify recent deployment/retry storms
7. Preserve emergency administrative access
8. Reduce demand before increasing capacity
```

Do not immediately restart PostgreSQL simply to clear sessions unless the incident conditions make that necessary and the impact is understood.

## 1.9.19 Authentication Failure Troubleshooting

Connection failures should be classified by layer.

```text
Connection refused / timeout
    -> listener/network/firewall/routing

no pg_hba.conf entry
    -> HBA policy mismatch

password authentication failed
    -> credential/authentication issue

user does not exist
    -> role provisioning issue

database does not exist
    -> database/connection-string issue

too many connections / reserved slots
    -> capacity/pooling/session leak
```

Server logs often contain additional information and should be correlated with client errors.

## 1.9.20 Safe HBA Change Procedure

Production HBA changes should follow a controlled workflow:

```text
Review requested access
        |
        v
Apply least-privilege rule
        |
        v
Validate syntax/rules
        |
        v
Reload configuration
        |
        v
Verify intended connection
        |
        v
Verify unintended access remains denied
        |
        v
Record change
```

Useful checks include:

```sql
SELECT *
FROM pg_hba_file_rules
WHERE error IS NOT NULL;
```

and a configuration reload when required:

```sql
SELECT pg_reload_conf();
```

## 1.9.21 SRE Alerting Model

Recommended connection-domain alert categories include:

- connection utilization approaching usable capacity
- loss of reserved administrative headroom
- abnormal connection creation rate
- authentication failure spike
- idle-in-transaction session age
- unusually high active session count
- pool saturation or queue growth
- connection latency increase
- TLS/certificate expiry risk where applicable
- repeated client retry storms

Alerts should identify the responsible database, role, application, pool, and client source where telemetry permits.

## 1.9.22 Automation Guardrails

Safe automation may:

```text
collect connection inventory
classify session states
identify oldest transactions
validate HBA parsing
check connection headroom
correlate authentication failures
compare pool size with database capacity
```

Risky automation includes indiscriminately terminating sessions whenever a threshold is exceeded.

Before termination, automation should understand ownership, transaction state, business criticality, lock impact, and whether the workload will immediately reconnect.

## 1.9.23 Production Case Study — Connection Leak

Scenario:

```text
Application deployment
      |
      v
Connection pool misconfiguration
      |
      v
Connections steadily increase
      |
      v
max_connections approached
      |
      v
New requests fail to connect
```

A disciplined DBRE response is:

```text
preserve admin access
      -> identify sessions by application_name/user/client_addr
      -> inspect pool metrics
      -> determine idle vs active vs transaction state
      -> stop the source of connection growth
      -> safely drain/terminate unnecessary sessions if required
      -> correct pool configuration
      -> validate recovery
      -> add alerting on connection growth and headroom
```

Simply increasing `max_connections` can hide the leak and increase future memory/resource risk.

## 1.9.24 Production Readiness Checklist

- `listen_addresses` intentionally configured
- network paths/firewalls documented
- TLS policy documented
- `pg_hba.conf` under controlled change management
- SCRAM-SHA-256 migration/status understood
- database `CONNECT` privileges reviewed
- `max_connections` capacity justified
- reserved administrative slots protected
- connection pooler architecture documented
- pool limits aligned with database capacity
- client connection timeout configured
- retry/backoff/jitter behavior tested
- `application_name` populated where practical
- idle-in-transaction monitoring enabled
- authentication failures monitored
- connection headroom alerting enabled
- failover connection behavior tested
- emergency connection runbook tested

## 1.9.25 SRE/DBRE Principle

> A PostgreSQL connection is a resource allocation and reliability event, not merely a network socket. Production connection architecture must control admission, authentication, backend concurrency, retries, pooling, and emergency headroom as one system.
