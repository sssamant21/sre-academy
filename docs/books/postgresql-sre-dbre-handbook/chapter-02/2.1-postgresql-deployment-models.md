# 2.1 - PostgreSQL Deployment Models

PostgreSQL can be deployed through several architectural models, ranging from a single self-managed database server to highly automated managed-cloud and Kubernetes platforms. For an SRE/DBRE, selecting the deployment model is an availability, operability, recovery, security, performance, and cost decision, not simply an installation choice.

A production PostgreSQL deployment should be selected by evaluating RTO/RPO, workload characteristics, scaling requirements, operational ownership, regulatory requirements, failure domains, upgrade strategy, backup/recovery, observability, and organizational expertise.

## 2.1.1 Deployment Model Overview

The major deployment models covered throughout this handbook are:

| Deployment model | PostgreSQL ownership | Infrastructure ownership | Typical use |
| --- | --- | --- | --- |
| Self-managed VM/bare metal | Organization | Organization | Maximum control |
| Self-managed cloud VM | Organization | Shared with cloud provider | Cloud infrastructure with PostgreSQL control |
| Managed PostgreSQL | Cloud/provider | Provider | Reduced operational burden |
| PostgreSQL HA cluster | Organization/provider | Depends on platform | Mission-critical HA |
| PostgreSQL on Kubernetes | Organization/operator | Shared | Cloud-native/platform engineering |
| Containerized standalone PostgreSQL | Organization | Organization | Development/testing or specialized deployments |

The fundamental difference is the operational responsibility boundary.

With self-managed PostgreSQL, the SRE/DBRE owns almost the entire database lifecycle. With managed services, portions of infrastructure, backup, patching, HA, and recovery are transferred to the service provider.

## 2.1.2 Self-Managed PostgreSQL

A traditional self-managed deployment runs PostgreSQL directly on physical servers, virtual machines, private-cloud VMs, or public-cloud compute instances.

Examples include PostgreSQL running on Amazon EC2, Azure Virtual Machines, or Google Compute Engine.

The organization controls:

```text
Operating System
      |
      v
PostgreSQL Packages
      |
      v
PostgreSQL Configuration
      |
      v
Storage / Filesystem
      |
      v
Replication / HA
      |
      v
Backup / Recovery
      |
      v
Monitoring / Alerting
```

This model provides the greatest control but also creates the largest operational responsibility.

### SRE/DBRE Responsibilities

The database/platform team typically owns:

- OS preparation and hardening
- PostgreSQL installation
- Filesystem design
- Memory and CPU tuning
- WAL configuration
- Replication
- HA orchestration
- Backups
- PITR
- Patching
- Major-version upgrades
- Monitoring
- Security
- Capacity management
- Failure recovery

### Advantages

Self-managed PostgreSQL provides maximum flexibility for specialized requirements such as:

- Custom extensions
- Unusual storage architectures
- Specialized operating-system tuning
- Custom replication designs
- Dedicated hardware
- Strict performance engineering
- Customized HA orchestration

### Operational Disadvantage

The organization owns substantially more failure modes.

Examples include:

- VM failure
- Disk failure
- Filesystem corruption
- PostgreSQL crash
- Replication failure
- Backup failure
- Network partition
- OS problem
- Kernel problem
- Capacity exhaustion
- Upgrade failure

Each requires an operational strategy.

## 2.1.3 Bare-Metal PostgreSQL

Bare-metal PostgreSQL runs directly on physical servers.

```text
Physical Server
      |
      +-- CPU
      +-- RAM
      +-- NVMe / SAN
      +-- Network
           |
           v
        Linux OS
           |
           v
       PostgreSQL
```

Bare metal eliminates the virtualization layer and can provide predictable performance for extremely demanding workloads.

Typical candidates include:

- Very large transactional databases
- Latency-sensitive financial systems
- High-throughput database platforms
- Specialized storage architectures

However, hardware lifecycle management becomes an organizational responsibility.

The SRE team must plan for:

- Hardware failures
- Spare capacity
- Server replacement
- Firmware
- RAID/storage controllers
- Network redundancy
- Physical disaster recovery

For most organizations, cloud VMs or managed PostgreSQL platforms provide a more favorable operational trade-off.

## 2.1.4 PostgreSQL on Virtual Machines

Virtual machines remain one of the most common self-managed deployment models.

```text
Hypervisor / Cloud
        |
        v
Virtual Machine
        |
        +-- CPU
        +-- Memory
        +-- Network
        +-- Block Storage
                |
                v
             Linux
                |
                v
           PostgreSQL
```

Cloud examples include Amazon EC2, Azure Virtual Machines, and Google Compute Engine.

This architecture combines infrastructure automation with full PostgreSQL control.

A typical production HA topology might be:

```text
                   Application
                       |
                       v
                 Load Balancer
                       |
             +---------+---------+
             |                   |
             v                   v
        PostgreSQL           PostgreSQL
          Primary              Standby
             |                   ^
             +---- WAL Stream ---+
```

Additional standby nodes can provide read scaling or disaster recovery.

## 2.1.5 Managed PostgreSQL Services

Managed PostgreSQL transfers significant operational responsibility to a cloud provider.

Important examples covered later in this handbook include:

- Amazon RDS for PostgreSQL
- Amazon Aurora PostgreSQL-Compatible Edition
- Azure Database for PostgreSQL
- Google Cloud SQL for PostgreSQL

The responsibility model becomes approximately:

| Organization owns | Cloud provider owns |
| --- | --- |
| Schema | Physical infrastructure |
| Queries | Virtualization |
| Indexes | Managed storage |
| Application connections | Platform automation |
| Database configuration, where exposed | Backup infrastructure |
| Workload tuning | HA infrastructure |
| Capacity decisions | Service maintenance |
| Data lifecycle |  |

Configuration flexibility varies by service.

Managed does not mean operationally maintenance-free.

The DBRE still owns problems such as:

- Inefficient SQL
- Missing or inappropriate indexes
- Connection storms
- Transaction problems
- Lock contention
- Table/index bloat
- Workload capacity
- Database parameter decisions
- Application retry behavior
- Replication-lag implications
- Cost optimization

This distinction is extremely important. Managed PostgreSQL removes portions of infrastructure administration. It does not remove database reliability engineering.

## 2.1.6 Amazon RDS for PostgreSQL

Amazon Web Services provides PostgreSQL through Amazon RDS.

A simplified architecture is:

```text
Application
     |
     v
RDS Endpoint
     |
     v
PostgreSQL Instance
     |
     +-- Managed Storage
     +-- Automated Backups
     +-- Monitoring
     +-- Optional Multi-AZ
```

RDS reduces operational responsibilities including portions of infrastructure provisioning, automated backups, maintenance, instance replacement, and HA management when configured appropriately.

However, teams must understand the service's control boundaries rather than assuming self-managed PostgreSQL procedures apply unchanged.

The dedicated AWS RDS chapter will cover these differences in depth.

## 2.1.7 Amazon Aurora PostgreSQL

Aurora PostgreSQL uses a substantially different storage and service architecture from conventional self-managed PostgreSQL.

Conceptually:

```text
                 Aurora Cluster
                       |
          +------------+------------+
          |                         |
       Writer                    Readers
          |                         |
          +------------+------------+
                       |
                       v
             Distributed Storage
```

This architecture changes several operational assumptions around storage, replication, failover, backups, read scaling, and recovery.

Therefore, Aurora should not simply be treated as "PostgreSQL installed on AWS."

The handbook gives Aurora its own dedicated chapter for this reason.

## 2.1.8 Azure Database for PostgreSQL

Microsoft provides managed PostgreSQL through Azure Database for PostgreSQL.

The service provides cloud-managed capabilities around infrastructure, backups, maintenance, monitoring, and availability while customers retain responsibility for workload-level database engineering.

A common logical architecture is:

```text
Application / AKS / VM
          |
          v
Azure Database for PostgreSQL
          |
          +-- Compute
          +-- Managed Storage
          +-- Backup
          +-- HA
          +-- Monitoring
```

The dedicated Azure chapter will address Azure-specific HA, networking, maintenance, backup, monitoring, and scaling considerations.

## 2.1.9 Google Cloud SQL for PostgreSQL

Google Cloud provides managed PostgreSQL through Cloud SQL.

Conceptually:

```text
Application / GKE / Compute
             |
             v
       Cloud SQL Endpoint
             |
             v
         PostgreSQL
             |
      +------+------+------+
      |      |             |
   Storage Backup         HA
```

As with other managed services, Cloud SQL changes the responsibility boundary while leaving database workload engineering with the customer.

The Google Cloud chapter later in the handbook covers those operational differences.

## 2.1.10 PostgreSQL on Kubernetes

PostgreSQL can also run as a stateful workload on Kubernetes.

A simplified architecture is:

```text
Kubernetes Cluster
        |
        +-- PostgreSQL Primary Pod
        +-- PostgreSQL Replica Pod
        +-- PostgreSQL Replica Pod
        +-- Operator
                |
                v
        Cluster Lifecycle
```

Persistent storage is normally provided through persistent volumes rather than container-local filesystems.

Production deployments commonly rely on PostgreSQL-aware operators such as CloudNativePG or other mature PostgreSQL operators.

An operator may automate portions of provisioning, replication, failover, backup, recovery, upgrades, and configuration management.

However, Kubernetes introduces another distributed system underneath PostgreSQL.

The SRE must now understand interactions between PostgreSQL, Kubernetes, CSI storage, networking, scheduling, and the operator.

For this reason, PostgreSQL on Kubernetes receives a dedicated chapter later in the handbook.

## 2.1.11 Standalone vs. High-Availability Deployment

A standalone database has a single PostgreSQL server:

```text
Application
     |
     v
PostgreSQL
```

Failure of that server can make the database unavailable until it is recovered.

A production HA architecture introduces standby systems:

```text
                    Application
                         |
                         v
                   DB Endpoint
                         |
                         v
                    Primary
                         |
                  WAL Streaming
                         |
              +----------+----------+
              v                     v
          Standby 1             Standby 2
```

The standby architecture can support high availability, disaster recovery, read workloads, backup offloading, and maintenance strategies.

HA architecture is covered extensively later in the handbook.

## 2.1.12 Single-Region vs. Multi-Region

Another architectural decision concerns failure domains.

Single-region deployments can protect against individual host or availability-zone failures:

```text
Region A

AZ-1                 AZ-2
Primary  --------->  Standby
```

Multi-region architecture can protect against broader regional failures:

```text
Region A                         Region B

Primary -----------------------> DR Standby
          WAL / replication
```

Multi-region architecture introduces network latency, replication lag, increased cost, greater operational complexity, and potentially non-zero data-loss exposure with asynchronous replication.

The design must therefore align with business RPO and RTO.

## 2.1.13 Deployment Model and RPO/RTO

Deployment selection should begin with reliability objectives.

Consider a business requirement such as:

```text
RPO <= 5 minutes
RTO <= 15 minutes
```

The architecture must be capable of satisfying both.

A standalone PostgreSQL instance may not meet those objectives.

An HA deployment could instead provide:

```text
Primary
   |
   +-- synchronous/asynchronous standby
   +-- continuous WAL archiving
   +-- tested recovery procedures
```

The key word is tested.

Having a standby or backup does not prove that the required recovery objective can be achieved.

## 2.1.14 SRE Deployment Selection Matrix

| Requirement | Self-managed VM | Managed PostgreSQL | Kubernetes |
| --- | --- | --- | --- |
| PostgreSQL control | Very high | Medium | High |
| OS control | High | Low | Node/platform dependent |
| Operational burden | High | Lower | High |
| Customization | Very high | Limited by service | High |
| Infrastructure automation | High | Very high | Very high |
| HA complexity owned by team | High | Lower | Medium-high |
| Specialized extensions | Strong | Service dependent | Strong |
| Portability | High | Medium | High |
| Platform expertise required | PostgreSQL + OS | PostgreSQL + cloud | PostgreSQL + Kubernetes |
| Time to deploy | Medium | Fast | Medium |

There is no universally superior model.

The correct architecture depends on organizational requirements.

## 2.1.15 Production Selection Criteria

Before choosing a PostgreSQL deployment model, the architecture review should evaluate at least:

| Area | Criteria |
| --- | --- |
| Reliability | RPO, RTO, availability targets, failure domains, backup requirements, disaster recovery |
| Performance | CPU, memory, storage latency, IOPS, throughput, connection volume, transaction rate, database size |
| Operations | Patching, upgrades, monitoring, alerting, incident response, capacity management, automation |
| Security | Network isolation, encryption, authentication, secrets management, auditing, regulatory requirements |
| Platform | Cloud strategy, Kubernetes maturity, infrastructure standards, IaC tooling |
| Cost | Compute, storage, IOPS, backup, replicas, cross-region traffic, licenses/support, engineering effort |

## 2.1.16 Common Architecture Mistakes

### Choosing Kubernetes Only Because the Organization Uses Kubernetes

Running applications on Kubernetes does not automatically mean databases should run there.

Database storage, failover, backup, recovery, and operational maturity must be evaluated independently.

### Assuming Managed PostgreSQL Requires No DBRE Expertise

Managed services remove infrastructure responsibilities, not SQL, schema, workload, capacity, or application reliability problems.

### Deploying a Single Server for a Critical Workload

If the business requires high availability, the architecture must remove or mitigate single points of failure.

### Building HA Without Testing Failover

An architecture diagram does not prove recoverability.

### Designing Backup Without Restore Testing

A successful backup job does not prove the database can be recovered within the required RTO.

## 2.1.17 Monitoring Requirements by Deployment Model

Regardless of platform, an SRE should monitor PostgreSQL workload health.

Core signals include:

- Availability
- Connections
- Transactions
- Query latency
- CPU
- Memory
- Storage
- IOPS
- WAL generation
- Replication lag
- Locks
- Deadlocks
- Checkpoints
- Autovacuum
- Table/index bloat
- Backup success
- Recovery readiness

Platform-specific telemetry should then be added.

```text
Self-managed
    +-- OS + filesystem + PostgreSQL

Managed service
    +-- Cloud metrics + PostgreSQL

Kubernetes
    +-- Kubernetes + storage + operator + PostgreSQL
```

Observability must cover the entire dependency chain.

## 2.1.18 Failure-Domain Thinking

A production DBRE should evaluate failures by layer.

```text
Application
     |
Connection / Proxy
     |
PostgreSQL
     |
Operating Platform
     |
Storage
     |
Network
     |
Availability Zone
     |
Region
```

For every layer, ask:

What happens if this component disappears right now?

That question frequently exposes architecture weaknesses more effectively than reviewing only the normal operating path.

## 2.1.19 Deployment Decision Example

Consider a business application with:

| Factor | Requirement |
| --- | --- |
| Database size | 2 TB |
| Peak TPS | 8,000 |
| Availability target | 99.99% |
| RPO | Less than 1 minute |
| RTO | Less than 10 minutes |
| Operations team | Small |
| Cloud strategy | AWS |

A managed architecture such as RDS PostgreSQL or Aurora PostgreSQL may deserve strong consideration because the small operations team can transfer portions of infrastructure and HA management to AWS.

However, the final decision still requires testing:

- Workload compatibility
- Extension requirements
- Performance
- Failover behavior
- Recovery
- Cost
- Operational constraints

Architecture should follow requirements, not product preference.

## 2.1.21 Key Takeaways

PostgreSQL supports many deployment patterns, but the database engine is only one part of the production system.

The deployment model determines who owns infrastructure failures, how HA is implemented, how backups and recovery operate, what level of PostgreSQL control is available, and how much operational complexity the organization assumes.

For SRE/DBRE teams, the core principle is:

Choose the PostgreSQL deployment model from reliability and operational requirements first, and technology preference second.

A well-designed PostgreSQL platform must therefore connect:

```text
Business Requirements
        |
        v
SLO / RPO / RTO
        |
        v
Deployment Model
        |
        v
HA + Backup + DR
        |
        v
Monitoring + Alerting
        |
        v
Automation
        |
        v
Failure Testing
        |
        v
Production Readiness
```
