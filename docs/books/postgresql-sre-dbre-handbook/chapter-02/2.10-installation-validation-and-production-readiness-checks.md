# 2.10 — Installation Validation and Production Readiness Checks

**Status:** Production Ready / Complete

A PostgreSQL installation is not production-ready merely because the server starts and accepts a `psql` connection. Production acceptance must prove that the correct PostgreSQL build is running, the intended cluster and configuration are active, storage and durability protections are correct, authentication behaves as designed, operational tooling works, observability is available, and backup/recovery capabilities are ready before application traffic is admitted.

This section defines the SRE/DBRE production acceptance gate after installation and initial configuration.

## 2.10.1 Production readiness philosophy

The validation model is:

```text
Installed
   ↓
Initialized
   ↓
Configured
   ↓
Started
   ↓
Validated
   ↓
Operationally Ready
   ↓
Production Traffic
```

Never collapse `Started` and `Production Ready` into the same state.

A healthy process can still have the wrong binary version, wrong PGDATA, unsafe authentication, disabled durability, missing backup, broken monitoring, insufficient storage, or configuration drift.

## 2.10.2 Capture installation identity

Validate the client and server software independently.

```bash
postgres --version
psql --version
pg_config --version
```

Then verify the connected server:

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
```

For automation, prefer `server_version_num` rather than parsing the human-readable `version()` string.

Capture package-manager or image metadata as part of the deployment evidence so the exact vendor build can be reconstructed later.

## 2.10.3 Validate executable paths

Multiple PostgreSQL major versions may coexist on a host. Confirm that service definitions and administrative shells resolve the intended binaries.

```bash
command -v postgres
command -v pg_ctl
command -v psql
command -v pg_config
pg_config --bindir
```

Do not assume the first binary in `PATH` is the binary used by the running service.

The production manifest should record the server executable path and package/image version.

## 2.10.4 Validate cluster identity

Confirm the server is using the intended cluster:

```sql
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

At the operating-system level:

```bash
cat "$PGDATA/PG_VERSION"
stat "$PGDATA"
df -h "$PGDATA"
df -i "$PGDATA"
```

If WAL is on separate storage, validate it independently.

A successful connection to the wrong cluster is still a failed deployment.

## 2.10.5 Validate server readiness

Use PostgreSQL-aware readiness checks:

```bash
pg_isready
```

Specify target details in production automation rather than relying on shell defaults:

```bash
pg_isready -h db-host.example -p 5432 -d postgres
```

Readiness is one gate only. It confirms server connection status; it does not prove that the application can authenticate, required schemas exist, backups work, or production configuration is correct.

## 2.10.6 Validate SQL connectivity

Perform an authenticated SQL connection using the intended administrative path:

```bash
psql -h db-host.example -p 5432 -d postgres -U approved_admin
```

Then execute a minimal validation set:

```sql
SELECT current_database(), current_user;
SELECT version();
SELECT now();
```

Validate both Unix-domain-socket and TCP paths where both are part of the operational design.

## 2.10.7 Validate configuration state

Inspect critical runtime settings from `pg_settings`, not only the configuration files:

```sql
SELECT name,
       setting,
       unit,
       source,
       sourcefile,
       sourceline,
       context,
       pending_restart
FROM pg_settings
WHERE name IN (
  'data_directory',
  'listen_addresses',
  'port',
  'max_connections',
  'shared_buffers',
  'wal_level',
  'fsync',
  'synchronous_commit',
  'full_page_writes',
  'archive_mode',
  'logging_collector',
  'autovacuum'
)
ORDER BY name;
```

Confirm that there are no unintended restart-pending changes:

```sql
SELECT name, setting, source
FROM pg_settings
WHERE pending_restart;
```

Production promotion should stop if a critical expected configuration is not yet effective.

## 2.10.8 Validate configuration files

Inspect PostgreSQL's parsed view of the configuration files:

```sql
SELECT sourcefile,
       sourceline,
       name,
       setting,
       applied,
       error
FROM pg_file_settings
WHERE error IS NOT NULL
ORDER BY seqno;
```

Also review unapplied entries when investigating precedence:

```sql
SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings
WHERE applied = false
ORDER BY seqno;
```

An unapplied row can be caused by a later override and is not automatically an error; interpret it with configuration order and `pg_settings`.

## 2.10.9 Validate authentication policy

Test authentication from representative network locations and identities.

Validation must include both positive and negative cases:

```text
Approved admin identity          → allowed
Approved application identity    → allowed
Approved replication identity    → allowed where applicable
Unauthorized identity            → denied
Unauthorized source network      → denied
Non-TLS connection               → denied where TLS is mandatory
```

Do not consider `pg_hba.conf` validated merely because an administrator can connect.

Confirm that no temporary broad `trust` or unrestricted network rule remains from installation.

## 2.10.10 Validate TLS where required

Where TLS is part of the production design, verify it from the client session.

Within `psql`:

```text
\conninfo
```

or inspect connection/security information through approved client tooling.

Validate certificate identity, expiry monitoring, protocol policy, and application connection strings according to organizational security requirements.

## 2.10.11 Validate data checksums

PostgreSQL 18 enables data checksums by default for newly initialized clusters unless explicitly disabled.

Verify the running cluster:

```sql
SHOW data_checksums;
```

Do not infer checksum state solely from the `initdb` command or automation template.

For offline checksum verification, PostgreSQL provides `pg_checksums`. The cluster must be shut down cleanly before using the utility for cluster-wide checksum checking or enable/disable operations.

Do not take a production database offline solely to run `pg_checksums` as a routine deployment check unless that offline validation is explicitly part of the approved commissioning procedure.

## 2.10.12 Validate durability settings

Confirm critical durability settings:

```sql
SHOW fsync;
SHOW full_page_writes;
SHOW synchronous_commit;
```

Do not promote a production database with `fsync = off` merely because a benchmark performed better.

If synchronous replication is required, validate the replication architecture and effective synchronous-standby policy rather than assuming `synchronous_commit` alone proves HA durability.

## 2.10.13 Validate WAL configuration

Review:

```sql
SHOW wal_level;
SHOW max_wal_size;
SHOW min_wal_size;
SHOW checkpoint_timeout;
SHOW archive_mode;
```

Where WAL archiving is required, validate the archive mechanism and observe successful archival before declaring PITR readiness.

If a separate WAL directory is used, confirm its mount, ownership, free space, monitoring, and startup dependency.

## 2.10.14 Validate storage capacity and filesystem health

At minimum capture:

```bash
df -h
df -i
findmnt
```

Validate:

```text
PGDATA capacity
WAL capacity
Tablespace capacity
Backup staging capacity where applicable
Filesystem/inode headroom
Expected mount points
Mount persistence across reboot
Ownership and permissions
Storage monitoring
```

Do not accept a deployment whose database path silently falls back to the root filesystem because an expected mount is absent.

## 2.10.15 Validate tablespaces

If tablespaces exist:

```sql
SELECT spcname,
       pg_tablespace_location(oid)
FROM pg_tablespace
ORDER BY spcname;
```

Confirm every external tablespace path is mounted, accessible, protected, backed up as required, and monitored.

Tablespace storage is part of the cluster's availability boundary.

## 2.10.16 Validate logging

Generate a controlled test event and confirm it appears in the intended logging pipeline.

Validate:

```text
PostgreSQL log destination
File/journald/syslog/collector behavior
Central log forwarding
Timestamp/time zone
Host/cluster identity
Rotation
Retention
Disk consumption controls
Sensitive-data policy
```

A logging configuration that writes locally but never reaches the monitoring platform is not operationally complete.

## 2.10.17 Validate monitoring and metrics

Before production traffic, monitoring should cover at least:

```text
Server availability
Connection utilization
Transaction rate
Long-running transactions
Idle-in-transaction sessions
Lock waits
Database size and growth
Filesystem utilization
WAL generation and retention
Checkpoint behavior
Replication lag where applicable
Autovacuum activity
Dead tuples
Cache / I/O behavior
Query latency
Backup status
Archive failures
PostgreSQL restarts
```

Confirm the monitoring system is receiving current data and that dashboards identify the correct environment and cluster.

## 2.10.18 Validate alerting

A dashboard is not an alerting system.

Test representative alert routes before go-live. At minimum validate alerting for:

```text
PostgreSQL unavailable
Disk/WAL filesystem capacity risk
Replication lag or replica unavailable
Backup failure
WAL archival failure
Connection saturation
Critical monitoring-agent failure
```

Use controlled test conditions rather than creating a dangerous real production failure.

Confirm notification routing, ownership, escalation, and runbook links.

## 2.10.19 Validate backup readiness

A production database should not accept critical workload data until backup architecture is established.

Validate:

```text
Backup target
Credentials / IAM
Encryption
Retention
Schedule
Failure alerting
Backup catalog / metadata
Base backup process
WAL archive dependency for PITR
Off-host or remote durability where required
```

For physical base backups, PostgreSQL provides `pg_basebackup`.

Do not equate "backup command completed" with recoverability.

## 2.10.20 Validate backup integrity

PostgreSQL provides `pg_verifybackup` to verify a base backup against its backup manifest.

Use it where applicable as part of the backup validation pipeline.

Backup verification improves confidence but does not replace a restore test. A production readiness process should include a tested restore/recovery procedure appropriate to the platform.

## 2.10.21 Validate recovery readiness

Before go-live, document and test the recovery path for the environment.

Confirm:

```text
Where backups are stored
Who can restore them
Required credentials
How a replacement server is provisioned
How WAL is retrieved for PITR
How recovery targets are specified
How application traffic is redirected
How restored data is validated
RPO target
RTO target
```

A backup without a known recovery procedure is incomplete reliability engineering.

## 2.10.22 Validate replication and HA where applicable

For a primary/standby architecture, validate:

```text
Standby connected
Expected streaming state
Replication lag within baseline
Replication slots where required
WAL retention policy
Synchronous/asynchronous policy
Read-only standby behavior
Failover mechanism
Client routing after failover
Monitoring and alerting
```

Perform failover testing in an approved environment before relying on the architecture for production availability.

## 2.10.23 Validate autovacuum

Confirm:

```sql
SHOW autovacuum;
```

Then inspect worker/activity visibility after workload begins.

Do not disable autovacuum as part of initial deployment tuning.

The production monitoring baseline must include vacuum/freeze health because transaction-ID exhaustion and table/index bloat are lifecycle risks, not merely performance concerns.

## 2.10.24 Validate extension requirements

Inventory installed extensions:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Compare against the approved application/platform manifest.

Do not install unapproved extensions merely because they are available on the host. Extensions can introduce shared libraries, privileges, upgrade dependencies, and compatibility constraints.

## 2.10.25 Validate locale and encoding

Confirm database encoding and locale-related properties required by the application.

```sql
SHOW server_encoding;
```

For database-specific properties, inspect the database catalog as appropriate to the deployed PostgreSQL release.

Compare results with the initialization manifest. Locale/collation mismatches discovered before production data arrives are much easier to correct than after go-live.

## 2.10.26 Validate time synchronization and time zone

Confirm operating-system time synchronization and PostgreSQL time-zone policy.

```sql
SHOW TimeZone;
SELECT now();
```

SRE teams commonly standardize server-side operational timestamps around UTC while allowing applications to render user-local time as needed.

Whatever policy is selected must be documented and consistent across database, hosts, monitoring, and logs.

## 2.10.27 Validate resource limits

Check operating-system and service-manager limits for the PostgreSQL runtime identity.

Review:

```text
Open files
Processes/tasks
Memory limits
Locked memory where relevant
Shared memory / huge pages where used
Core dump policy
OOM behavior
```

A server that works under an empty workload may fail under concurrency if service limits are too restrictive.

## 2.10.28 Validate restart and reboot behavior

Test controlled PostgreSQL restart:

```text
Application drain / maintenance condition
        ↓
Controlled PostgreSQL shutdown
        ↓
Service startup
        ↓
Readiness check
        ↓
SQL validation
        ↓
Monitoring validation
```

Also validate host reboot behavior in an appropriate pre-production environment when PostgreSQL is expected to start automatically after reboot.

Confirm required data, WAL, and tablespace mounts are available before the service starts.

## 2.10.29 Validate administrative access

Confirm the DBRE/SRE team has a tested administrative path independent of the application account.

Validate:

```text
Approved DBA role
Break-glass procedure
Host/platform access where applicable
Secret retrieval
Audit trail
Network path
Runbook ownership
```

Do not discover during an outage that all database access depends on the failed application path.

## 2.10.30 Validate least privilege

Review roles before go-live:

```sql
SELECT rolname,
       rolsuper,
       rolcreaterole,
       rolcreatedb,
       rolcanlogin,
       rolreplication
FROM pg_roles
ORDER BY rolname;
```

Confirm application accounts do not have unnecessary superuser, role-management, database-creation, or replication privileges.

Validate schema/table/default privileges according to the application's access model.

## 2.10.31 Validate application connectivity

Test using the actual application connection architecture:

```text
Application subnet / namespace
        ↓
DNS / service discovery
        ↓
Load balancer / proxy / pooler if used
        ↓
TLS
        ↓
pg_hba.conf
        ↓
Authentication
        ↓
Database / schema permissions
```

A successful DBA connection from localhost does not validate application readiness.

## 2.10.32 Validate connection pooling where used

If PgBouncer or another approved pooler is part of the architecture, validate:

```text
Pooler health
Authentication
TLS
Pool mode
Connection limits
Timeouts
Server reset behavior
Failover behavior
Monitoring
```

Test the full application path, not only direct PostgreSQL access.

## 2.10.33 Controlled smoke test

Run a small application-safe smoke test before production traffic.

Example in a dedicated validation database/schema:

```sql
CREATE TABLE sre_install_validation (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now(),
    payload text NOT NULL
);

INSERT INTO sre_install_validation(payload)
VALUES ('production-readiness-test');

SELECT * FROM sre_install_validation;

UPDATE sre_install_validation
SET payload = 'updated'
WHERE id = 1;

DELETE FROM sre_install_validation
WHERE id = 1;

DROP TABLE sre_install_validation;
```

Do not run intrusive validation objects in application schemas without approval.

The smoke test verifies basic DDL/DML, transaction, WAL, and permission paths, but it is not a performance benchmark.

## 2.10.34 Performance baseline

Capture a baseline before application load so future incidents have a comparison point.

Useful evidence includes:

```text
CPU and memory
Storage latency / IOPS / throughput
Connection count
Checkpoint statistics
WAL generation rate
Simple SQL latency
Network latency
Database size
```

`pgbench` can be useful for controlled benchmarking, but do not run a heavy synthetic benchmark against a production database without explicit capacity and change approval.

## 2.10.35 Source-build regression validation

For PostgreSQL built from source, the official regression test suite provides additional validation.

Before installation, `make check` can run tests against a temporary installation. Against an installed server, PostgreSQL supports `make installcheck` / `make installcheck-parallel` in the appropriate build/test context.

Do not run regression suites casually against a production cluster: the tests can create and drop test databases and cluster-wide objects. Use dedicated validation environments.

This becomes essential during incidents, audits, rebuilds, upgrades, and disaster recovery.

## 2.10.37 Failure scenarios

### FS-2.10-01 — Correct client, wrong server version

`psql --version` reports the expected release but `SHOW server_version` does not. Stop promotion and identify the service binary and target host/port. Never use client version as proof of server version.

### FS-2.10-02 — Wrong PGDATA

The service starts successfully but `SHOW data_directory` identifies an unexpected cluster. Stop application traffic, preserve both clusters, correct service configuration, and validate before restart.

### FS-2.10-03 — Missing storage mount

PostgreSQL starts on an unintended local directory because the expected mount was absent. Stop immediately before writes accumulate, protect the unintended files, restore the correct mount, and follow a controlled reconciliation/recovery procedure.

### FS-2.10-04 — Checksum policy mismatch

`SHOW data_checksums` differs from the approved manifest. Do not ignore it. Determine whether the cluster was initialized incorrectly and resolve before production promotion.

### FS-2.10-05 — Backup configured but unverified

The scheduled job reports success but no restore/manifest verification has been performed. Keep the readiness gate open until backup integrity and recovery procedure are demonstrated to the required standard.

### FS-2.10-06 — Monitoring works, alerts do not

Metrics appear on dashboards but test alerts never reach the on-call destination. Treat alert routing as failed production readiness and correct notification ownership/escalation before go-live.

### FS-2.10-07 — HBA allows unintended network

A negative authentication test unexpectedly succeeds. Isolate exposure, correct network/HBA policy, reload safely, retest both allowed and denied paths, and review whether credentials were exposed.

### FS-2.10-08 — Restart leaves pending configuration

After restart, expected settings are still incorrect. Inspect `pg_settings.source`, service command-line options, includes, `postgresql.auto.conf`, and environment-specific configuration.

## 2.10.38 Production go-live gate

Do not admit production traffic until all mandatory controls are green.

```text

[ ] Correct binaries/service definition
[ ] Correct PGDATA
[ ] Correct configuration paths
[ ] Server readiness successful
[ ] Administrative SQL connectivity successful
[ ] Application-path connectivity successful
[ ] Authentication positive/negative tests passed
[ ] TLS validated where required
[ ] Critical runtime configuration verified
[ ] No unexplained pending restart settings
[ ] Durability controls verified
[ ] Checksum state verified
[ ] WAL/archive configuration validated
[ ] PGDATA/WAL/tablespace storage validated
[ ] Capacity/headroom validated
[ ] Logging validated end to end
[ ] Monitoring receiving current metrics
[ ] Alert routing tested
[ ] Backup process operational
[ ] Backup integrity/recovery validation completed to policy
[ ] HA/replication validated where applicable
[ ] Autovacuum enabled
[ ] Extensions match approved manifest
[ ] Locale/encoding validated
[ ] Time synchronization/time zone validated
[ ] Resource/service limits validated
[ ] Restart/reboot behavior validated as required
[ ] Administrative/break-glass access tested

[ ] Controlled smoke test passed
[ ] Rollback/recovery runbook available
[ ] Deployment evidence captured
```

## 2.10.39 SRE/DBRE sign-off model

A mature production deployment separates technical completion from production acceptance.

```text
Installation Complete
        ↓
DBRE Technical Validation
        ↓
Security / Access Validation
        ↓
Backup / Recovery Validation
        ↓
Monitoring / Alert Validation
        ↓
Application Smoke Test
        ↓
Production Readiness Sign-Off
        ↓
Traffic Enablement
```

The exact approval model varies by organization, but the engineering evidence should remain reproducible and auditable.

## 2.10.40 Golden production principle

A PostgreSQL deployment is ready only when the team can answer **yes** to all four questions:

```text
Can we run it safely?
Can we observe it?
Can we recover it?
Can we reproduce it?
```

If any answer is no, the installation is not yet production-ready.

## SRE/DBRE takeaway

Production readiness is an operational proof, not an installation status. Validate the running server, effective configuration, storage, security, durability, observability, backup/recovery, HA, application connectivity, and administrative access before admitting critical traffic.

The final objective is not merely a PostgreSQL process that starts. It is a PostgreSQL service that can be operated, diagnosed, protected, restored, and reproduced reliably.

Validated against PostgreSQL 18 official documentation for server/client version information, `pg_config`, `pg_isready`, runtime settings, data checksums and `pg_checksums`, server utilities, and regression testing.
