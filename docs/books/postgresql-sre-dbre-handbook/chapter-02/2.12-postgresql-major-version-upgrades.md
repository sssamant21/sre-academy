# 2.12 — PostgreSQL Major-Version Upgrades

**Status:** Production Ready / Complete

PostgreSQL major-version upgrades are lifecycle migrations, not routine binary patching. Major releases can introduce catalog, compatibility, behavior, extension, optimizer, and operational changes. Unlike minor updates, major upgrades require a supported data migration method such as logical dump/restore, `pg_upgrade`, or replication-based migration.

This section defines a production SRE/DBRE framework for planning, testing, executing, validating, and recovering from PostgreSQL major-version upgrades.

## Major versus minor upgrade

For PostgreSQL 10 and later, the first component is the major version. Moving from PostgreSQL 17 to 18 is a major upgrade; moving from 18.3 to 18.4 is a minor update.

Minor releases retain storage compatibility within a major release. Major releases may change internal structures and user-visible behavior, so the old data directory must not simply be started as the new major version.

```text
Minor update
18.3 → 18.4
Stop → replace/update binaries → start

Major upgrade
17 → 18
Migration required
```

## Supported migration architectures

PostgreSQL provides three broad approaches:

```text
Major Upgrade
    ├── Logical dump / restore
    ├── pg_upgrade
    └── Replication-based migration
```

The correct method depends on database size, downtime objective, platform, extension compatibility, HA architecture, storage capacity, rollback requirement, and operational maturity.

## Method 1 — Logical dump and restore

A logical upgrade exports database definitions and data from the old cluster and loads them into a new cluster running the target major version.

Typical tools include:

```text
pg_dump
pg_dumpall
pg_restore
psql
```

A logical upgrade provides a clean target cluster and can be useful when changing platform architecture or intentionally reorganizing the database.

Advantages:

- clean new cluster
- strong separation from the old cluster
- opportunity to redesign storage/configuration
- useful across platforms where physical reuse is inappropriate

Tradeoffs:

- potentially long dump/restore duration
- potentially large outage without a synchronization strategy
- index creation and constraint validation can extend runtime
- requires sufficient temporary storage and operational time

Use newer-version dump utilities where PostgreSQL documentation recommends doing so, and test the exact dump/restore path before production.

## Method 2 — pg_upgrade

`pg_upgrade` upgrades an existing PostgreSQL cluster to a later major version without performing a traditional logical dump and restore of all user data.

The basic architecture is:

```text
Old PostgreSQL Binaries + Old Cluster
                ↓
         Compatibility Check
                ↓
       New PostgreSQL Binaries
                +
       Initialized New Cluster
                ↓
            pg_upgrade
                ↓
        New PostgreSQL Cluster
```

Always run the `pg_upgrade` binary from the **new** PostgreSQL installation.

## pg_upgrade precheck

Before the maintenance window, run:

```bash
pg_upgrade \
  --old-bindir=/usr/pgsql-17/bin \
  --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/postgresql/17/data \
  --new-datadir=/postgresql/18/data \
  --check
```

`--check` performs compatibility checks without changing the cluster and can identify manual actions required for the upgrade.

Treat a successful `--check` as a required production gate, not as optional convenience.

## pg_upgrade transfer modes

PostgreSQL 18 supports multiple transfer approaches, including copy, link, clone where supported, copy-file-range where supported, and swap mode.

### Copy mode

Data files are copied to the new cluster.

Operational characteristics:

- requires additional storage
- preserves the old cluster independently
- typically slower than metadata-oriented modes

### Link mode

```bash
pg_upgrade --link ...
```

Link mode uses hard links rather than copying all relation files.

Advantages:

- fast
- low additional storage requirement

Critical consequence: after the upgraded cluster is started, the old cluster is no longer safe as an independent rollback source because both clusters reference the same underlying files.

Do not advertise link mode as an easy rollback architecture.

### Clone mode

```bash
pg_upgrade --clone ...
```

Where the operating system/filesystem supports it, clone mode can provide speed and storage advantages without the same old-cluster modification consequence as link mode.

Validate filesystem support during rehearsal.

### Swap mode — PostgreSQL 18

PostgreSQL 18 adds `--swap`, which swaps data directories rather than copying or linking files and can be especially fast for clusters containing many relations.

```bash
pg_upgrade --swap ...
```

This mode is operationally destructive to the old cluster once file transfer begins; the old cluster is no longer safe to start. Treat it as a one-way cutover unless an independent rollback artifact exists.

PostgreSQL recommends appropriate synchronization handling for this mode; validate the exact PostgreSQL 18 procedure during rehearsal.

## Parallel processing

`pg_upgrade` supports parallel processing with `--jobs`:

```bash
pg_upgrade --jobs=8 ...
```

PostgreSQL 18 can also process upgrade checks in parallel. Choose concurrency based on CPU, storage, filesystem, and workload characteristics rather than blindly matching the largest available core count.

## Target cluster initialization

Before `pg_upgrade`, initialize the new target cluster with compatible initialization properties.

```bash
/usr/pgsql-18/bin/initdb -D /postgresql/18/data
```

Review compatibility requirements carefully, including checksums and other initialization characteristics.

PostgreSQL 18 enables data checksums by default for newly initialized clusters. `pg_upgrade` requires compatible checksum settings, so when upgrading a source cluster without checksums, the target initialization may need PostgreSQL 18's `--no-data-checksums` option to match the source.

Never assume the target `initdb` defaults match an older source cluster.

## Extensions and external modules

Extensions are one of the highest-risk major-upgrade dependencies.

Inventory before the upgrade:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

For each extension verify:

```text
Target PostgreSQL major-version support
Target package availability
Shared-library availability
Required extension upgrade path
Known compatibility issues
Post-upgrade ALTER EXTENSION requirements
```

Install required target-version shared libraries before running `pg_upgrade`. Do not recreate extension schemas blindly in the new cluster when `pg_upgrade` is responsible for migrating catalog definitions.

External modules and custom C extensions require special care because `pg_upgrade` cannot guarantee their binary compatibility.

## Release-note review

Read the target major-version migration notes and all intervening major-version release notes.

For an upgrade such as:

```text
PostgreSQL 14 → PostgreSQL 18
```

review the migration/compatibility material for 15, 16, 17, and 18.

Capture application-impacting changes, removed/deprecated behavior, changed defaults, SQL semantics, authentication changes, extension changes, planner changes, replication behavior, and operational changes.

## Application compatibility testing

A successful database upgrade does not prove application compatibility.

Test:

- connection drivers
- ORMs
- SQL syntax
- prepared statements
- stored procedures/functions
- extensions
- authentication
- TLS
- migrations
- ETL/batch jobs
- monitoring agents
- backup agents
- CDC/connectors
- connection pools

Use production-like data distribution and query patterns where feasible.

## Upgrade rehearsal

Every important production major upgrade should be rehearsed.

```text
Production-like Backup / Clone
          ↓
Build Target Environment
          ↓
Run pg_upgrade --check
          ↓
Execute Full Upgrade
          ↓
Measure Duration
          ↓
Run Post-upgrade Steps
          ↓
Application Validation
          ↓
Performance Validation
          ↓
Rollback Rehearsal
```

Record timings for shutdown, upgrade, synchronization, startup, post-processing, validation, and rollback decision points.

## Pre-upgrade inventory

Capture at minimum:

```sql
SELECT version();
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW server_encoding;
SHOW data_checksums;
```

Inventory databases:

```sql
SELECT datname
FROM pg_database
WHERE datallowconn
ORDER BY datname;
```

Extensions:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Replication slots:

```sql
SELECT slot_name, slot_type, active
FROM pg_replication_slots;
```

Tablespaces:

```sql
SELECT spcname, pg_tablespace_location(oid)
FROM pg_tablespace;
```

Also record configuration, roles, database-level settings, role-level settings, installed packages, service definitions, backup state, HA topology, monitoring configuration, and external dependencies.

## Capacity planning

Major upgrades can require significant temporary storage.

Capacity planning must include:

```text
Old PGDATA
New PGDATA
Tablespaces
WAL
Temporary upgrade output
Logical dumps if used
Backups / snapshots
Filesystem headroom
Post-upgrade WAL growth
```

Do not begin a copy-mode upgrade without verified capacity for both old and new clusters plus operational headroom.

## Backup and rollback gate

Before production cutover, require a verified recovery artifact appropriate to the architecture.

Possible protections include:

- tested physical backup
- storage snapshot with PostgreSQL-consistent procedure
- logical backup
- preserved old cluster in copy-mode architecture
- replica or migration target

A backup is not a rollback plan unless the team knows how long restoration will take and has validated the recovery path.

## Production pg_upgrade workflow

A controlled workflow is:

```text
Change Freeze
    ↓
Confirm Backup / Recovery Gate
    ↓
Confirm Target Binaries + Extensions
    ↓
Final Replication / HA Checks
    ↓
Stop Application Writes
    ↓
Drain Connections
    ↓
Stop Old PostgreSQL Cluster
    ↓
Run pg_upgrade
    ↓
Execute Required Post-upgrade Scripts
    ↓
Restore / Reconcile Configuration
    ↓
Start PostgreSQL 18
    ↓
Database Validation
    ↓
Application Smoke Test
    ↓
Performance / Replication Validation
    ↓
Open Traffic
    ↓
Enhanced Monitoring
```

Do not let automation skip gates merely because a command returned exit code zero.

## Configuration migration

Do not blindly copy an old `postgresql.conf` over the target major version.

Instead:

1. preserve the old configuration as evidence;
2. start from the target-version configuration model;
3. migrate intentional settings;
4. validate every non-default parameter against target-version documentation;
5. review renamed, removed, changed, or newly defaulted parameters;
6. reconcile `postgresql.auto.conf` deliberately;
7. review `pg_hba.conf` and authentication behavior;
8. validate include-file paths and service startup options.

Major upgrades are an opportunity to remove obsolete tuning rather than perpetuate it indefinitely.

## PostgreSQL 18 statistics preservation

PostgreSQL 18 enhances `pg_upgrade` to preserve optimizer statistics, reducing the historical post-upgrade period where planner performance could be degraded until statistics were rebuilt.

This does not eliminate post-upgrade performance validation. Extended statistics are not preserved in the same way, and schema/behavior changes can still alter query plans.

Monitor query latency, plan changes, CPU, I/O, cache behavior, and workload-specific KPIs after cutover.

## Post-upgrade scripts and actions

`pg_upgrade` can generate scripts for required post-upgrade processing. Treat these as part of the upgrade, not optional cleanup.

Run generated scripts exactly as required by the tool output and preserve their execution logs in the change record.

Also review whether extensions require:

```sql
ALTER EXTENSION extension_name UPDATE;
```

Do this only according to the extension's documented upgrade path.

## Replication and standby upgrades

Physical replication requires version-compatible architecture. Plan how standby servers will be recreated or upgraded as part of the major-version migration.

For `pg_upgrade` standby procedures, validate checkpoint synchronization and follow PostgreSQL's documented standby-upgrade process.

Do not assume replication slots, standby configuration, WAL paths, or external archive tooling automatically survive every upgrade path.

## Logical replication upgrade considerations

Logical replication can support low-downtime major-version migrations because logical replication can operate between different major versions.

A conceptual architecture is:

```text
PostgreSQL 17 Publisher
          ↓
    Logical Replication
          ↓
PostgreSQL 18 Subscriber
          ↓
      Catch Up
          ↓
    Stop Writes
          ↓
     Final Sync
          ↓
      Cutover
```

This can reduce cutover downtime substantially but adds operational complexity around sequences, DDL, replication coverage, large objects, extensions, and application cutover.

PostgreSQL 18 also has documented procedures for upgrading logical replication clusters. Logical-slot migration support depends on the source version and topology, so validate the exact path against PostgreSQL 18 documentation.

## Sequence synchronization in logical migrations

Logical replication of table data does not mean application sequence state can be ignored.

Before cutover, validate and synchronize sequences where required by the migration design. Failure to do so can cause primary-key collisions after the new cluster becomes writable.

## DDL governance during logical migration

During a logical-replication migration window, uncontrolled schema changes can break synchronization or create divergence.

Establish a DDL freeze or a controlled mechanism to apply compatible schema changes to both source and target until cutover.

## Post-upgrade validation

Immediately verify:

```sql
SELECT version();
SELECT current_database();
SHOW data_directory;
SHOW server_version;
SHOW data_checksums;
```

Validate database inventory, roles, extensions, tablespaces, configuration, authentication, replication, backup integration, monitoring, scheduled jobs, and application connectivity.

## Data validation

Use risk-appropriate checks such as:

- critical table row counts
- business-level aggregates
- schema/object inventory
- extension inventory
- application read/write smoke tests
- key sequence values
- representative query results

Do not attempt an expensive full-table count of every production relation merely to create a checkbox if a safer validation strategy exists.

## Performance validation

Compare pre- and post-upgrade baselines:

```text
Transaction throughput
Query latency percentiles
CPU utilization
Storage latency / IOPS
Buffer/cache behavior
Lock waits
Connection utilization
Checkpoint behavior
WAL generation
Autovacuum behavior
Replication lag
Application error rate
```

A technically successful upgrade can still be a production failure if workload performance regresses materially.

## Monitoring and alerting

Use enhanced monitoring during and after cutover for:

- PostgreSQL process availability
- connection failures
- authentication failures
- application errors
- query latency
- CPU/memory pressure
- storage latency and capacity
- WAL generation
- checkpoint pressure
- replication lag
- failed background workers
- autovacuum issues
- backup failures
- extension errors

Correlate anomalies with the upgrade timestamp and configuration changes.

## Rollback architecture

Rollback depends heavily on the migration method.

### Dump/restore

The source cluster remains independently available until intentionally retired, assuming writes were not allowed to diverge after cutover.

### pg_upgrade copy mode

The old cluster remains physically separate, but rollback still requires strict control of writes and application state after cutover.

### pg_upgrade link mode

Once the new cluster starts, the old cluster must not be treated as a safe independent rollback source.

### pg_upgrade swap mode

Once file transfer begins, the old cluster is destructively modified and must not be treated as a safe rollback source.

### Logical replication

Rollback or reverse migration requires explicit design. Once writes occur on the target, simply pointing applications back can lose or diverge data unless reverse synchronization or another recovery mechanism exists.

The rollback decision point must therefore be defined **before** the upgrade.

## Failure scenarios

### FS-2.12-01 — pg_upgrade --check fails

Do not bypass the check. Resolve incompatible extensions, data types, configuration, initialization properties, libraries, or other reported blockers. Re-run the check until clean.

### FS-2.12-02 — Missing extension library

Stop the upgrade workflow. Install the target-major compatible extension package/library and validate its documented upgrade path before continuing.

### FS-2.12-03 — Insufficient disk space

Do not begin data transfer. Increase capacity, clean only approved non-database files, or select a tested migration mode with appropriate storage characteristics.

### FS-2.12-04 — Target starts but application fails

Keep traffic closed. Validate driver compatibility, authentication, SQL behavior, extension state, configuration, and application logs. Roll back according to the predetermined decision threshold if the issue cannot be resolved safely inside the window.

### FS-2.12-05 — Severe performance regression

Protect service objectives. Compare query plans, statistics, configuration, planner behavior, extension state, I/O, and target-version changes. Do not assume every regression is fixed by running ANALYZE blindly; diagnose evidence first.

### FS-2.12-06 — Standby does not rejoin

Keep HA status degraded and traffic policy conservative. Validate version, timeline, WAL availability, replication configuration, slots, authentication, and standby rebuild requirements.

### FS-2.12-07 — Logical migration is not caught up at cutover

Do not cut over. Measure replication lag and remaining synchronization work, resolve blockers, and extend/reschedule the window rather than accepting silent data loss.

### FS-2.12-08 — Link/swap upgrade needs rollback after destructive point

Do not start the old cluster. Recover from the independent backup/snapshot or execute the predesigned recovery architecture. Starting an unsafe old cluster can further damage recoverability.

## Production case study — checksum mismatch on PostgreSQL 18 target

A team initializes a PostgreSQL 18 target cluster with defaults and attempts `pg_upgrade` from an older source cluster that does not use data checksums. PostgreSQL 18 enables checksums by default for new clusters, creating an initialization mismatch.

The team stops, rebuilds the target cluster with initialization properties compatible with the source, reruns `pg_upgrade --check`, and only then proceeds.

The lesson is simple: **never assume target-version initdb defaults are compatible with the source cluster.**

## Production case study — fast upgrade without safe rollback

A team selects `pg_upgrade --link` to meet a short maintenance window but documents rollback as “restart the old PostgreSQL service.” After the new cluster starts, that rollback assumption is no longer valid because link mode reuses the same underlying relation files.

A production-grade plan would establish an independent backup/snapshot and a tested restore path before entering the destructive portion of the upgrade.

## Production case study — logical upgrade with sequence collision

A low-downtime migration replicates table data successfully to the target major version. The team cuts over without validating sequence state. New inserts on the target generate values that collide with existing keys.

The corrective design adds sequence inventory and synchronization to the cutover checklist and validates application-generated keys before traffic release.

## SRE/DBRE golden rules

1. A major upgrade is a migration, not a patch.
2. Read every relevant major-version migration note.
3. Rehearse the exact production method.
4. Run `pg_upgrade --check` well before downtime when using pg_upgrade.
5. Treat extensions as first-class upgrade dependencies.
6. Validate target `initdb` properties; defaults can change between majors.
7. Do not confuse a successful database start with a successful application upgrade.
8. Define the rollback point before entering the maintenance window.
9. Link and swap modes require independent recovery protection.
10. Keep the old environment until the production acceptance window is complete and the retention policy allows retirement.
