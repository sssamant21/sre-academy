# 2.18 — Replication and High-Availability Upgrade Strategy

**Status:** Production Ready / Complete

PostgreSQL upgrades in highly available environments must preserve more than database availability. They must preserve the correctness of replication, WAL continuity, failover capability, replication slots, standby topology, application routing, and recovery objectives throughout the change.

This section defines the SRE/DBRE production strategy for upgrading PostgreSQL clusters that use physical streaming replication, log shipping, synchronous replication, logical replication, and HA orchestration.

## 2.18.1 Upgrade architecture

A typical HA topology is:

```text
Applications
     ↓
Load Balancer / Proxy / Service Endpoint
     ↓
Primary PostgreSQL
     ├── Physical Standby A
     ├── Physical Standby B
     └── Logical Subscribers / CDC Consumers
```

Every upgrade plan must identify which replication relationships can survive the version transition directly and which must be rebuilt or migrated.

## 2.18.2 Physical versus logical replication across major versions

Physical streaming replication operates on PostgreSQL's physical WAL/storage representation and should not be used as a generic cross-major-version migration mechanism.

Logical replication operates on logical row changes and PostgreSQL explicitly supports it as a method for upgrading between major versions.

For major-version upgrades, the principal strategies are therefore:

```text
pg_upgrade + rebuild/synchronize physical standbys

or

logical replication from old major → new major
```

Choose the strategy according to downtime tolerance, database size, extension compatibility, rollback requirements, operational complexity, and RPO/RTO.

## 2.18.3 pg_upgrade with physical standbys

`pg_upgrade` documents a method for rapidly upgrading streaming-replication and log-shipping standbys when link mode is used. Rather than running `pg_upgrade` independently on each standby, the upgraded primary can be used with `rsync` to synchronize the standby layout.

Before the primary upgrade, verify that old standbys are caught up. PostgreSQL recommends comparing the latest checkpoint locations with `pg_controldata` after controlled shutdown.

Also ensure that `wal_level` on the new primary is not `minimal` when standbys will be used.

## 2.18.4 Standby preparation

Before upgrading an HA cluster:

- install the target PostgreSQL binaries on every node
- install required extension shared libraries on every target node
- validate storage and tablespace topology
- preserve standby-specific configuration
- validate replication authentication
- confirm old standbys are synchronized
- record replication slot state
- record WAL positions and timeline
- validate archive health where log shipping/PITR is used
- establish the rollback point

Do not begin the primary upgrade while a required standby is materially behind unless the approved strategy explicitly accounts for it.

## 2.18.5 Standby configuration preservation

Standby synchronization procedures can overwrite or remove configuration files. Preserve required files before synchronization, including as applicable:

```text
postgresql.conf
included configuration files
postgresql.auto.conf
pg_hba.conf
standby connection configuration
archive/recovery settings
HA-agent configuration
```

After synchronization, reconcile them against the new major-version parameter set rather than blindly restoring an obsolete configuration.

## 2.18.6 Tablespaces and relocated WAL

When using PostgreSQL's documented `rsync` standby-upgrade technique, external tablespaces require corresponding synchronization operations. If `pg_wal` is relocated outside the data directories, that storage must also be synchronized.

A standby upgrade is incomplete if only PGDATA is considered.

## 2.18.7 Rebuilding standbys

When the documented rapid standby-upgrade path is not suitable, the simpler and often safer production strategy is to recreate physical standbys after the new primary is running.

Conceptual workflow:

```text
Upgrade Primary
      ↓
Validate New Primary
      ↓
Create Fresh Base Backup
      ↓
Provision New Standby
      ↓
Start Streaming Replication
      ↓
Validate Catch-up
      ↓
Repeat for Additional Standbys
      ↓
Restore HA Quorum
```

This uses more time and network/storage bandwidth but reduces complexity and avoids carrying questionable standby state forward.

## 2.18.8 Synchronous replication

If synchronous replication is configured, model the effect of taking each standby out of service. A poor maintenance sequence can cause transaction commits to block if the required synchronous standby set is unavailable.

Before maintenance, inspect the effective synchronous-replication policy and validate which standbys are currently participating.

Never remove synchronous nodes from service without understanding the commit-acknowledgement requirement.

## 2.18.9 HA orchestrators

Patroni, repmgr, Pacemaker, Kubernetes operators, cloud automation, proxies, DNS, and custom failover systems introduce another control plane around PostgreSQL.

The upgrade runbook must define:

```text
Who controls PostgreSQL start/stop?
Who may promote a standby?
Who updates endpoints?
Who performs health checks?
Who may automatically restart nodes?
Who owns maintenance mode?
```

Disable or place automation into the vendor-supported maintenance state where necessary so that an orchestrator does not interpret intentional upgrade activity as a production failure and perform an unwanted failover.

Validate orchestrator-specific procedures against that project's official documentation in addition to PostgreSQL documentation.

## 2.18.10 Logical replication for low-downtime upgrades

PostgreSQL supports logical replication between different major versions. This enables an old-version publisher to feed a new-version subscriber while applications continue writing to the old primary.

Typical architecture:

```text
Old PostgreSQL Primary
        │
        │ logical replication
        ▼
New PostgreSQL Cluster
        │
        ├── validation
        ├── catch-up
        └── production cutover
```

Once synchronization is complete and replication lag is acceptably low, writes are controlled, final changes are applied, sequence/DDL state is reconciled, and applications are redirected to the new cluster.

PostgreSQL notes that such a switch can reduce upgrade downtime to seconds, but the operational design remains workload-dependent.

## 2.18.11 Logical replication limitations

Logical replication does not make every database object automatically equivalent between source and target.

The upgrade plan must explicitly handle items such as:

```text
Schema/DDL changes
Sequences
Large objects where applicable to the migration design
Extensions
Roles and privileges
Tables not included in publications
Replica identity requirements
Unsupported or restricted object behavior
```

Do not treat row replication as a complete cluster migration.

## 2.18.12 Sequence synchronization

Sequences are a classic cutover risk in logical migrations. Their state is not continuously replicated like ordinary table changes.

Before final promotion, reconcile sequence values so that new writes on the target cannot reuse values already allocated on the source.

The exact method must be rehearsed and should account for application write behavior during the cutover window.

## 2.18.13 DDL freeze

Logical replication does not automatically reproduce arbitrary schema changes on the subscriber.

Establish a DDL/change freeze before and during the final migration period unless a tested process exists to apply every schema change consistently to both sides.

The change record should define ownership for emergency DDL during the freeze.

## 2.18.14 Logical replication slots and PostgreSQL 17+

PostgreSQL 18 `pg_upgrade` can migrate logical replication slots when the old cluster is PostgreSQL 17 or later and documented prerequisites are satisfied. Clusters older than PostgreSQL 17 do not receive this slot-migration behavior.

For publisher upgrades, PostgreSQL requires conditions including:

```text
wal_level = logical on the new cluster
sufficient max_replication_slots
required output plugins installed
old slots usable
transactions/messages replicated to subscribers
subscriptions temporarily disabled as documented
```

Do not assume slot migration succeeded. Validate slot state explicitly after the upgrade.

## 2.18.15 Subscription upgrade state

PostgreSQL 18 can also migrate subscription dependencies through `pg_upgrade` when the old subscriber is PostgreSQL 17 or later, subject to documented prerequisites.

Validate subscription-table state, replication origins, target configuration, and `max_active_replication_origins` before the upgrade.

Logical-replication cluster upgrades involve multiple nodes and not all operations are transactional. PostgreSQL therefore recommends backups before performing the procedure.

## 2.18.16 Logical replication failover

PostgreSQL supports failover-capable logical replication slots. A subscription configured with failover support can synchronize its logical slot state to a physical standby of the publisher so subscriptions can continue after that standby is promoted.

Because synchronization is asynchronous, validate that required failover slots are actually synchronized before relying on them during maintenance or failover.

PostgreSQL 18 also uses `synchronized_standby_slots` and standby-side slot synchronization configuration to protect logical failover-slot continuity in appropriate architectures.

## 2.18.17 Replication slot inventory

Before upgrade, capture:

```sql
SELECT slot_name,
       slot_type,
       database,
       active,
       restart_lsn,
       confirmed_flush_lsn,
       wal_status
FROM pg_replication_slots
ORDER BY slot_name;
```

Also identify every external consumer associated with logical slots. An inactive forgotten slot can retain WAL and create storage pressure during a long maintenance window.

## 2.18.18 Physical replication monitoring

During the maintenance cycle, monitor the primary using views such as `pg_stat_replication` and validate standby replay using appropriate recovery functions/views.

Track:

```text
connection state
sent/write/flush/replay positions
replication lag
WAL retention
receiver state
replay state
timeline changes
slot state
archive health
```

Do not declare HA restored merely because a standby process is running.

## 2.18.19 Logical replication monitoring

Monitor subscriptions, replication workers, replication slots, and table synchronization state.

Validate:

```text
subscription enabled state
worker connectivity
initial table synchronization
apply progress
slot retention
replication origin/progress
conflicts
source/target row and business-level reconciliation
```

A zero-error log is not proof that the migration dataset is complete.

## 2.18.20 Application routing

Upgrade design must include the layer that routes application traffic:

```text
DNS
VIP
Load balancer
PgBouncer
HAProxy
Kubernetes Service
Cloud endpoint
Application connection string
Secrets/configuration
```

Test routing before the maintenance window. Know TTLs, connection-pool behavior, long-lived sessions, retry logic, and whether clients can accidentally reconnect to the old primary after cutover.

## 2.18.21 Split-brain prevention

A major-version migration can create two writable PostgreSQL systems containing nearly identical data.

Production cutover must have a single-writer rule:

```text
Old primary writable
        ↓
Write freeze / fencing
        ↓
Final synchronization
        ↓
Old primary fenced
        ↓
New primary writable
```

Do not rely solely on application configuration to prevent old-cluster writes. Use network, endpoint, permission, or infrastructure fencing appropriate to the platform.

## 2.18.22 Failover during an upgrade

Define the response before the window begins.

If the old primary fails before the point of no return, the safest action may be to restore service on the old-version HA topology and postpone the upgrade.

If failure occurs after the new primary has accepted production writes, rollback may require data reconciliation rather than simple endpoint reversal.

Never improvise failover ownership while both old and new clusters are partially active.

## 2.18.23 Backup and PITR gate

Before changing the HA topology, validate:

```text
Recent recoverable backup
WAL archive continuity
Restore procedure
Recovery target process
Backup coverage for tablespaces
Backup location independent of upgrade hosts
Credential/access availability
```

After successful major-version cutover, establish and validate a new backup/PITR baseline for the new cluster rather than assuming old-version backups satisfy the new production recovery plan.

## 2.18.24 Failure scenarios

### FS-2.18-01 — Standby is behind before pg_upgrade

Stop the upgrade gate. Determine whether the standby is required for the selected strategy, restore replication health, verify checkpoint/WAL state, and only proceed once the runbook's synchronization requirement is met.

### FS-2.18-02 — Synchronous commits block during maintenance

Protect availability. Inspect synchronous-standby configuration and current replication state. Restore a qualifying synchronous standby or execute the pre-approved temporary policy change with explicit durability impact understood.

### FS-2.18-03 — HA orchestrator promotes a node during planned shutdown

Fence traffic, establish which node is authoritative, stop conflicting automation, validate timelines and writes, and recover to a single-primary topology before continuing.

### FS-2.18-04 — Logical subscriber has not caught up at cutover

Do not promote merely because the maintenance deadline arrived. Keep the source authoritative, identify lag cause, restore replication throughput, and delay cutover or execute the approved alternative migration plan.

### FS-2.18-05 — Sequence collision after logical cutover

Stop affected writes, identify sequence/table inconsistency, advance sequence state safely, validate uniqueness and application impact, and perform reconciliation before reopening traffic.

### FS-2.18-06 — Logical slot retains excessive WAL

Identify the consumer and slot health, protect filesystem headroom, restore consumer progress or execute the approved slot recovery decision. Never drop a required slot solely to reclaim space without understanding data-loss/reseed consequences.

### FS-2.18-07 — New primary works but standbys fail to start

Keep the new primary protected, inspect version/configuration/extensions/storage/tablespaces/WAL synchronization, and rebuild standbys if necessary. Do not declare the upgrade fully production-complete until the required HA posture is restored.

### FS-2.18-08 — Writes occur on old cluster after cutover

Treat as a data-divergence incident. Fence the old cluster immediately, preserve evidence, identify affected transactions, reconcile data under an approved recovery plan, and do not blindly merge conflicting datasets.

## 2.18.25 Recovery workflow

```text
Upgrade / Replication Failure
          ↓
Fence Conflicting Writers
          ↓
Identify Authoritative Primary
          ↓
Preserve WAL + Cluster State
          ↓
Determine Upgrade Point of No Return
          ↓
Validate Replication / Slots / Timeline
          ↓
Restore Old HA or Stabilize New HA
          ↓
Rebuild / Resynchronize Standbys
          ↓
Validate Backup + PITR
          ↓
Validate Application Routing
          ↓
Controlled Traffic Restoration
```

## 2.18.26 Automation

Automation should capture and validate:

```text
PostgreSQL versions
primary/standby roles
replication topology
synchronous standby policy
slot inventory
publication/subscription inventory
WAL/archive state
replication lag
checkpoint/replay positions
extension versions
storage/tablespaces
application endpoints
backup status
HA orchestrator state
```

Automated gates should fail closed when topology differs from the approved upgrade manifest.

Do not automate promotion simply because an upgrade command succeeded.

## 2.18.27 Production case study — upgrade succeeds, HA does not

A team upgrades the primary successfully and validates application connectivity. The change is declared complete even though both physical standbys are still offline. Several hours later the primary host fails, turning what should have been a routine host incident into a database outage.

Corrective action establishes two distinct gates:

```text
Database Upgrade Successful
        ≠
HA Production Readiness Complete
```

The production change closes only after the required standby count, replication health, failover path, monitoring, backup, and application routing are validated.

## 2.18.28 Production case study — low-downtime logical upgrade

A large cluster cannot tolerate the downtime required for a traditional migration. A new major-version cluster is built in parallel, schema and extensions are prepared, logical replication performs the bulk synchronization, and application validation runs against the target.

During final cutover:

```text
Freeze DDL
Control application writes
Wait for replication catch-up
Synchronize sequences
Validate critical data
Fence old primary
Redirect endpoint
Validate writes and reads
Establish target HA
Validate new backups
```

The reduced downtime comes from moving most data while the source remains online, but operational complexity increases. The migration succeeds because cutover, rollback, sequence handling, routing, and single-writer fencing were rehearsed beforehand.

## 2.18.30 SRE/DBRE takeaway

A PostgreSQL HA upgrade is a topology migration, not merely a server upgrade.

The SRE/DBRE must protect:

```text
Data correctness
Single-primary ownership
WAL continuity
Replication health
Failover capability
Replication slots
Application routing
RPO/RTO
Backup recoverability
```

The upgrade is complete only when the target PostgreSQL version is healthy **and** the required HA and recovery posture has been restored.
