# 2.2 — PostgreSQL Binary and Package Installation

**Status:** Production Ready / Complete

For most production deployments, PostgreSQL binary packages provide the cleanest operational lifecycle because they integrate with the operating system's package, dependency, security-update, and service-management mechanisms.

## Package-source governance

Use an approved repository and record repository configuration, package names, versions, architecture, signing/trust configuration, and dependency versions. Do not mix distribution PostgreSQL packages and alternate PostgreSQL repositories without an explicit migration plan.

## Pre-install checks

Validate OS release, architecture, repository reachability, disk capacity, filesystem/mount state, time synchronization, DNS, service account policy, security controls, and whether another PostgreSQL installation already exists.

## Installation pattern

Exact commands are distribution-specific. Install server binaries and required client/contrib packages through the approved package manager, then verify executable and package versions before initializing a cluster.

```bash
postgres --version
psql --version
initdb --version
pg_ctl --version
```

Do not assume installing packages automatically means a correctly initialized or production-secured cluster exists; packaging behavior differs by platform.

## Versioned binaries

Keep old and new major-version binaries independently identifiable during major upgrades. `pg_upgrade` must be run using the new server's binary and requires paths to both old and new executable directories.

## Extensions

Install extension shared libraries/packages compatible with the exact target PostgreSQL major version. During `pg_upgrade`, required target-version shared objects must exist before the upgrade; do not blindly create duplicate extension schemas in the new cluster.

## Service integration

Inspect the package-provided service unit or platform service mechanism. Verify the expected PGDATA/configuration path, service identity, startup behavior, restart policy, limits, environment, and log routing before production enablement.

## Patch governance

Package installation and patching must use controlled repositories and change records. Validate package dependency changes before applying them to production. Minor PostgreSQL updates do not require a major-version data migration, but still require controlled restart/HA procedures and validation.

## Failure scenarios

- Wrong repository/version installed: stop before initialization and correct package source.
- Conflicting binaries in PATH: use explicit versioned paths and clean environment configuration.
- Missing extension package: block upgrade/cutover until compatible library is installed.
- Package update unexpectedly changes service behavior: compare service definitions and restore approved configuration before traffic.

## Production checklist

- [ ] Repository approved
- [ ] Package signatures/trust configured
- [ ] Exact PostgreSQL version recorded
- [ ] Server/client utilities verified
- [ ] Versioned binary paths known
- [ ] Service integration inspected
- [ ] Required extensions available
- [ ] Package update/rollback procedure documented
