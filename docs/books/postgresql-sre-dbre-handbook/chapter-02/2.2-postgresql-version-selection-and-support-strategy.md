# 2.2 — PostgreSQL Version Selection and Support Strategy

**Status:** Complete / Production Ready

Selecting a PostgreSQL version is a production lifecycle and reliability decision. SRE/DBRE teams must consider community support lifetime, security fixes, application and extension compatibility, operating-system support, managed-service availability, upgrade complexity, and the organization's ability to test and maintain the selected release.

## Versioning and support policy

PostgreSQL releases a new major version approximately once per year and supports each major version for five years. Minor releases deliver bug, security, and data-corruption fixes and are normally released at least quarterly. Production systems should run a supported major version and remain current on its minor releases.

For PostgreSQL 10 and later, the first component is the major version and the second component is the minor release. For example, `18.3` to `18.4` is a minor update, while `17` to `18` is a major upgrade. Before PostgreSQL 10, the first two components identified the major release.

As of August 2026, the community-supported production major versions are PostgreSQL 18, 17, 16, 15, and 14. PostgreSQL 14 reaches its final community release on November 12, 2026, making it a near-term lifecycle risk for new long-lived deployments.

## Minor-version strategy

The production standard should be:

```text
Supported Major Version
        +
Current Minor Release
```

Minor upgrades normally do not require dump/restore. Stop the server, install the updated binaries, and restart using the existing data directory. Always review the release notes because a particular minor release can require additional actions.

Minor releases can contain security fixes, corruption fixes, and important reliability corrections. Deferring minor updates indefinitely creates avoidable operational risk.

## Major-version strategy

Major PostgreSQL releases can introduce internal-format, system-catalog, and user-visible compatibility changes. Major-version transitions therefore require a supported migration procedure rather than simply replacing server binaries.

Principal approaches include:

- dump/restore using `pg_dump`, `pg_dumpall`, and restore tooling;
- `pg_upgrade`;
- logical replication or another carefully engineered replication-based migration.

Review the migration documentation and release notes for the target release and all intervening major versions before upgrading.

## `pg_upgrade` production controls

`pg_upgrade` migrates an existing cluster to a newly initialized target PostgreSQL cluster. Treat it as a controlled migration procedure rather than a simple in-place binary replacement.

Before production execution:

```text
pg_upgrade --check
        ↓
Extension compatibility
        ↓
Configuration compatibility
        ↓
Representative upgrade rehearsal
        ↓
Backup / recovery validation
        ↓
Production change
        ↓
Post-upgrade validation
```

External modules and extensions must be compatible with the target PostgreSQL installation. PostgreSQL cannot automatically prove every aspect of third-party binary compatibility, so extension validation is a mandatory upgrade gate.

A useful PostgreSQL 18 example is data checksums: PostgreSQL 18 `initdb` enables data checksums by default, while `pg_upgrade` requires compatible checksum settings between clusters. This demonstrates why target-version migration notes must be reviewed rather than applying a generic upgrade procedure blindly.

## Logical-replication upgrade strategy

Logical replication can be used across PostgreSQL major versions and can support low-downtime migrations. It should not, however, be treated as a guaranteed zero-downtime upgrade mechanism.

Production planning must address:

- schema and DDL synchronization;
- sequence synchronization;
- table replication eligibility;
- initial data synchronization;
- replication slots and subscriptions;
- output-plugin compatibility;
- WAL configuration;
- replication lag;
- write quiescing and cutover;
- application connection switching;
- rollback criteria;
- post-cutover validation.

The achievable outage depends on workload behavior and the migration architecture.

## Version-selection criteria

The newest PostgreSQL release is not automatically the correct production choice. Evaluate:

```text
PostgreSQL release maturity
        +
Application certification
        +
Driver compatibility
        +
Extension compatibility
        +
Operating-system support
        +
Cloud-provider availability
        +
Backup-tool compatibility
        +
Monitoring compatibility
        +
Organizational testing
        +
Remaining support lifetime
```

Maintain an enterprise certification matrix covering applications, JDBC/ODBC/libpq and other drivers, connection pools, extensions, backup tooling, HA tooling, monitoring, operating-system images, disaster-recovery procedures, and performance baselines.

## Extension and application compatibility

Maintain an inventory of required extensions and their versions. Examples can include PostGIS, `pg_stat_statements`, `pg_cron`, `pg_partman`, pgvector, TimescaleDB, and custom extensions.

For each target PostgreSQL major release, verify extension availability and the supported extension upgrade path. Managed services require an additional check against the cloud provider's supported extension catalog.

Application certification must test more than connection establishment. Validate authentication, TLS, prepared statements, transactions, data types, application SQL, connection pooling, failover/reconnect behavior, bulk operations, CDC/ETL integrations, and migration frameworks.

## EOL governance

Do not wait for PostgreSQL end-of-life to begin migration planning. A practical internal lifecycle model is:

```text
> 24 months before EOL   Normal operation
18–24 months            Begin upgrade planning
12–18 months            Certify target version
6–12 months             Execute production upgrades
< 6 months              Escalated lifecycle risk
EOL                     Unsupported / policy exception
```

These windows are organizational guardrails, not PostgreSQL community requirements.

Running an unsupported release creates security, reliability, compliance, ecosystem-compatibility, and emergency-upgrade risk.

## Managed PostgreSQL lifecycle

For Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL, evaluate both PostgreSQL community lifecycle and provider lifecycle.

The provider controls service-specific version availability, maintenance behavior, upgrade mechanisms, supported extensions, and retirement policy. Community support dates alone do not define the complete lifecycle of a managed PostgreSQL deployment.

## Enterprise version standardization

Avoid uncontrolled version fragmentation. Maintain an approved catalog such as:

```text
Preferred
Supported
Migration
Deprecated
Unsupported
```

Encode approved versions into infrastructure-as-code modules and platform policies where practical so deprecated or unsupported versions cannot be introduced accidentally.

## Inventory, monitoring, and alerting

Maintain an accurate production inventory containing environment, instance/cluster, PostgreSQL major/minor version, minor-version compliance, EOL date, owner, extension inventory, and upgrade status.

Recommended lifecycle signals include:

```text
postgresql_version
minor_version_compliance
days_until_eol
unsupported_instance_count
upgrade_required
upgrade_test_status
extension_compatibility_status
```

Alerting should identify versions entering the upgrade-planning window, versions approaching EOL, unsupported instances, and required security-related minor updates.

## Failure scenario — EOL without an upgrade

A database repeatedly deferred until EOL can turn a planned lifecycle operation into an emergency when a security or reliability issue appears. The root cause is not simply an old PostgreSQL version; it is failure of lifecycle management.

Corrective controls are inventory, EOL forecasting, target-version certification, an owned upgrade backlog, scheduled execution, and compliance reporting.

## Failure scenario — premature adoption

The opposite failure occurs when a newly released major version is placed into production before required applications, drivers, extensions, backup tooling, or operational procedures have been certified.

The production rule is therefore: newest does not automatically mean production-ready for a particular workload.

## Mandatory production controls

1. Maintain an approved-version catalog.
2. Automatically inventory actual server versions.
3. Track EOL well before support expires.
4. Maintain an application/driver/extension/tool compatibility matrix.
5. Require `pg_upgrade --check` when `pg_upgrade` is selected.
6. Rehearse major upgrades in a representative non-production environment.
7. Record expected duration, rollback criteria, and recovery procedures.
8. Validate backups and restoration before the production change.
9. Validate application behavior and performance after the upgrade.
10. Retire old clusters only after the rollback window closes.

## SRE/DBRE production checklist

- [ ] Major version is community-supported.
- [ ] Remaining support lifetime is acceptable.
- [ ] Current-minor-release policy is defined.
- [ ] Application and drivers are certified.
- [ ] Required extensions are certified.
- [ ] Backup, HA, and monitoring tooling are certified.
- [ ] Operating system and cloud platform support are verified.
- [ ] Performance baseline is established.
- [ ] Failover behavior is tested where applicable.
- [ ] Backup and restore are tested.
- [ ] Major-upgrade path is documented.
- [ ] `pg_upgrade --check` is included when applicable.
- [ ] EOL date is recorded and monitored.
- [ ] Lifecycle alerts exist.
- [ ] Operational owner is assigned.
- [ ] Upgrade rehearsal is completed.
- [ ] Rollback/recovery criteria are documented.

## Key takeaway

PostgreSQL version management is a continuous reliability discipline:

```text
Select
  ↓
Certify
  ↓
Deploy
  ↓
Patch
  ↓
Monitor lifecycle
  ↓
Test next major
  ↓
Upgrade
  ↓
Validate
  ↓
Retire old version
```

The production standard is to run a supported PostgreSQL major version, stay current on its minor releases, continuously track EOL, validate the complete application and extension ecosystem, and begin the next major-version lifecycle well before support expires.
