# 2.21 — Production Monitoring, Observability, and Alerting Baseline

**Status:** Production Ready / Complete

A PostgreSQL installation or upgrade is not production-ready until the operating team can detect availability failures, workload saturation, storage pressure, query regressions, locking, WAL problems, replication degradation, vacuum risk, backup failures, and abnormal resource behavior before they become prolonged incidents.

This section establishes the SRE/DBRE monitoring and alerting baseline for PostgreSQL 18 after installation, patching, or major-version upgrade.

## 2.21.1 Observability architecture

A production monitoring model should combine PostgreSQL-native statistics with host/platform and application telemetry:

```text
Application SLI/SLO Telemetry
          ↓
PostgreSQL Activity + Statistics
          ↓
OS / VM / Container Metrics
          ↓
Storage + Network Metrics
          ↓
HA / Replication / Backup Telemetry
          ↓
Central Metrics + Logs + Traces
          ↓
Dashboards → Alerts → Runbooks → Incident Response
```

PostgreSQL statistics alone do not provide the complete physical I/O picture because operating-system caching and storage layers also influence observed behavior. Correlate database and host metrics.

## 2.21.2 PostgreSQL 18 monitoring surfaces

Core PostgreSQL 18 views and facilities include:

```text
pg_stat_activity
pg_stat_database
pg_stat_io
pg_stat_wal
pg_stat_checkpointer
pg_stat_bgwriter
pg_stat_replication
pg_stat_replication_slots
pg_stat_wal_receiver
pg_stat_archiver
pg_stat_all_tables / pg_stat_user_tables
pg_stat_all_indexes / pg_stat_user_indexes
pg_stat_ssl
pg_locks
progress views
pg_stat_statements (supplied extension)
```

PostgreSQL 18 additionally exposes per-backend I/O statistics through `pg_stat_get_backend_io()` and expands `pg_stat_io` with byte-oriented I/O reporting and WAL I/O activity.

## 2.21.3 Statistics configuration

Review the runtime statistics settings:

```sql
SHOW track_activities;
SHOW track_counts;
SHOW track_io_timing;
SHOW track_wal_io_timing;
SHOW compute_query_id;
```

`track_activities` and `track_counts` are fundamental monitoring controls. `track_counts` is also important to autovacuum behavior.

I/O timing can provide valuable latency evidence but has timing-call overhead. Measure and enable it according to platform policy rather than assuming it is free.

## 2.21.4 Availability monitoring

Monitor PostgreSQL at several layers:

```text
Process/service state
TCP endpoint reachability
PostgreSQL protocol readiness
Authentication
Simple SQL execution
Application transaction path
```

`pg_isready` is useful for checking server connection status:

```bash
pg_isready -h db.example.internal -p 5432 -d postgres
```

Do not equate `pg_isready` success with complete application health. A server can accept connections while suffering lock contention, replication failure, storage saturation, or severe query latency.

## 2.21.5 Session and workload activity

Use `pg_stat_activity` to understand current server activity:

```sql
SELECT pid,
       usename,
       datname,
       application_name,
       client_addr,
       state,
       wait_event_type,
       wait_event,
       xact_start,
       query_start,
       query
FROM pg_stat_activity
WHERE backend_type = 'client backend'
ORDER BY query_start NULLS LAST;
```

Monitor:

```text
active sessions
idle sessions
idle-in-transaction sessions
long-running transactions
long-running queries
waiting sessions
connection storms
unexpected clients
application connection distribution
```

Idle-in-transaction sessions deserve particular attention because they can retain snapshots and locks and interfere with maintenance.

## 2.21.6 Database-level workload metrics

`pg_stat_database` provides database-wide counters useful for workload and reliability monitoring.

Track trends such as:

```text
transactions committed / rolled back
blocks read / cache hits
temporary files and bytes
deadlocks
sessions
session time
active time
idle-in-transaction time
sessions terminated by cause
```

Use rates and trends rather than alerting blindly on lifetime cumulative counters.

## 2.21.7 I/O monitoring with pg_stat_io

PostgreSQL 18 `pg_stat_io` reports cluster-wide I/O by backend type, object, and context. PostgreSQL 18 includes byte counts and WAL I/O rows.

Example:

```sql
SELECT backend_type,
       object,
       context,
       reads,
       read_bytes,
       read_time,
       writes,
       write_bytes,
       write_time,
       fsyncs,
       fsync_time,
       evictions
FROM pg_stat_io
ORDER BY backend_type, object, context;
```

Interpret this together with operating-system/storage telemetry.

Signals worth investigating include:

```text
rising read/write latency
large client-backend write activity
large client-backend fsync activity
high eviction rates
unexpected temporary-relation I/O
abnormal WAL I/O
storage queue saturation
```

## 2.21.8 PostgreSQL 18 per-backend I/O

PostgreSQL 18 provides `pg_stat_get_backend_io()` for per-backend I/O statistics.

This is valuable when cluster-level I/O rises and the SRE needs to correlate resource consumption with specific database sessions or workload classes.

Use it alongside `pg_stat_activity`, query identifiers, application names, and host-level I/O evidence.

## 2.21.9 WAL monitoring

`pg_stat_wal` provides cluster-wide WAL activity counters such as WAL records, full-page images, bytes generated, and WAL-buffer-full events.

Monitor WAL generation rate rather than only cumulative totals.

Unexpected WAL growth can result from:

```text
bulk writes
index creation/rebuild
VACUUM-related activity
large UPDATE/DELETE workloads
full-page images after checkpoints
logical replication workloads
application behavior changes
```

Correlate WAL generation with archive throughput, replication lag, slot retention, and filesystem headroom.

## 2.21.10 Checkpoint monitoring

PostgreSQL 18 exposes checkpointer statistics through `pg_stat_checkpointer`.

Track:

```text
timed checkpoints
requested checkpoints
checkpoint completion behavior
buffers written
write time
sync time
```

A high rate of requested checkpoints or abnormal checkpoint I/O should trigger investigation into WAL volume, `max_wal_size`, checkpoint configuration, storage latency, and workload changes.

Do not tune checkpoint parameters solely to make one metric look better; evaluate durability, recovery time, WAL, and storage impact together.

## 2.21.11 Query monitoring with pg_stat_statements

The supplied `pg_stat_statements` module tracks planning and execution statistics for SQL statements.

It requires loading through `shared_preload_libraries` and query identifiers must be available.

Useful dimensions include:

```text
calls
total / mean / min / max execution time
planning time
rows
shared/local/temp block activity
WAL generated
JIT behavior
parallel worker behavior
```

Use it to identify queries responsible for high total database load as well as individual high-latency statements.

A query executed millions of times at modest latency can be more expensive than one rare slow query.

## 2.21.12 Query-latency SLOs

Monitor latency at both database and application levels.

Recommended operational views include:

```text
P50
P95
P99
maximum / outliers
error rate
throughput
```

Do not derive percentile latency from `pg_stat_statements` mean values. Use an appropriate metrics/APM/query-observation system when true latency distributions are required.

After upgrades, compare the same workload windows against the pre-upgrade baseline.

## 2.21.13 Lock monitoring

Use `pg_locks` together with `pg_stat_activity` to identify lock contention and blockers.

Production monitoring should detect:

```text
sessions waiting on locks
long blocker chains
DDL blocking application traffic
idle-in-transaction blockers
unexpected advisory-lock contention
```

Alerting should focus on sustained user impact rather than every short-lived lock wait.

## 2.21.14 Long-running transactions

Example:

```sql
SELECT pid,
       usename,
       datname,
       state,
       now() - xact_start AS transaction_age,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Thresholds must reflect workload type. A reporting query or maintenance job can legitimately run longer than an OLTP transaction.

Use role/database/application-specific thresholds where possible.

## 2.21.15 Autovacuum and table health

Monitor table statistics for:

```text
live tuples
dead tuples
last vacuum / autovacuum
last analyze / autoanalyze
vacuum/analyze counts
modification rates
transaction-ID age
```

Example:

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Do not use a single dead-tuple percentage as the only vacuum alert. Table size, workload rate, vacuum duration, freeze age, and bloat risk all matter.

## 2.21.16 Transaction ID wraparound monitoring

Monitor database and relation transaction age well before PostgreSQL reaches emergency anti-wraparound behavior.

Example database inventory:

```sql
SELECT datname,
       age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

Define warning and critical thresholds with substantial safety margin and an associated runbook.

A wraparound alert is a reliability priority, not routine housekeeping.

## 2.21.17 Replication monitoring

On the primary, use `pg_stat_replication` to monitor WAL sender and standby state.

Track:

```text
standby connectivity
sent/write/flush/replay positions
byte/time lag
sync_state
unexpected disconnects
```

On standbys, monitor WAL receiver and replay state.

Do not rely on one generic "replication lag" number. Differentiate transport, write, flush, and replay delay when diagnosing a problem.

## 2.21.18 Replication slot monitoring

Use `pg_replication_slots` and `pg_stat_replication_slots` where applicable.

Alert on:

```text
inactive required slots
excessive retained WAL
slot invalidation
consumer failure
unexpected slots
logical decoding spill/stream behavior where relevant
```

A forgotten inactive slot can retain enough WAL to exhaust storage.

## 2.21.19 WAL archive monitoring

`pg_stat_archiver` exposes archive success/failure statistics.

Do not assume that `last_archived_wal` proves every older WAL segment was archived; PostgreSQL documentation explicitly notes that archive order is not guaranteed in all circumstances.

Monitor both PostgreSQL archive statistics and the external archive destination.

Alert on sustained archive failure, archive backlog, and loss of recovery headroom.

## 2.21.20 Backup monitoring

Monitor the backup system independently of PostgreSQL availability.

Track:

```text
last successful backup
backup duration
backup size
WAL/archive continuity
retention
repository/storage capacity
backup verification
restore-test age
PITR validation
```

A green backup job is not equivalent to proven recoverability. Periodic restore testing is part of the SRE control.

## 2.21.21 Storage monitoring

Alert on:

```text
filesystem utilization
inode utilization
storage latency
IOPS / throughput saturation
queue depth
read-only filesystem events
mount failures
PGDATA capacity
WAL capacity
tablespace capacity
backup/archive capacity
```

Capacity alerts should provide enough lead time for remediation. Waiting for 95–100% utilization is generally too late for a high-write PostgreSQL system.

## 2.21.22 Memory monitoring

Correlate host/container memory with PostgreSQL configuration and workload concurrency.

Observe:

```text
resident memory
swap activity
OOM events
connection count
parallel workers
maintenance operations
temporary-file growth
workload concurrency
```

Do not estimate PostgreSQL memory consumption simply as `shared_buffers + work_mem`. `work_mem` can be consumed by multiple operations in multiple concurrent sessions.

## 2.21.23 CPU monitoring

Track total CPU, load/run queue, CPU steal where applicable, and PostgreSQL process utilization.

High CPU should be correlated with:

```text
active sessions
query identifiers
query plans
parallelism
vacuum/analyze
checkpoint/WAL behavior
application throughput
```

Alert on sustained saturation and SLO impact rather than isolated short spikes.

## 2.21.24 Connection monitoring

Monitor current connections relative to effective capacity:

```sql
SELECT state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY state
ORDER BY state;
```

Track:

```text
connection utilization
connection creation rate
pool utilization
reserved connection headroom
idle sessions
idle-in-transaction sessions
authentication failures
```

A connection alert should distinguish legitimate concurrency growth from connection leaks or retry storms.

## 2.21.25 Temporary-file monitoring

Unexpected temporary-file growth often indicates sorts, hashes, materialization, or other operations exceeding available working memory.

Monitor database temporary-file counts/bytes, query telemetry, and filesystem headroom.

Do not respond automatically by globally increasing `work_mem`; that can amplify memory pressure under concurrency.

## 2.21.26 Progress monitoring

PostgreSQL provides progress views for operations including:

```text
ANALYZE
VACUUM
CREATE INDEX / REINDEX
CLUSTER / VACUUM FULL
COPY
base backup
```

Use progress reporting during upgrades and remediation work to distinguish a slow operation from a stalled one.

## 2.21.27 Logging baseline

Metrics and logs should complement each other.

A production logging baseline should provide enough information to investigate:

```text
startup/shutdown
FATAL/PANIC/errors
slow statements
lock waits/deadlocks
autovacuum behavior
checkpoints
connections/disconnections as required
authentication failures
archive failures
replication failures
```

Avoid globally logging every statement on high-throughput systems without considering performance, disk consumption, and sensitive-data exposure.

## 2.21.28 Alert design principles

Every production alert should answer:

```text
What user/reliability risk exists?
What threshold or condition triggered?
How long must it persist?
What context is attached?
Who owns it?
What runbook should be executed?
What constitutes recovery?
```

Prefer symptom/SLO alerts plus carefully chosen cause alerts over hundreds of unactionable metric alarms.

## 2.21.29 Recommended alert families

At minimum, define actionable alerts for:

- PostgreSQL unavailable / SQL health failure
- application database error-rate or latency SLO breach
- connection saturation
- long-running or idle-in-transaction sessions
- sustained lock blocking / deadlocks
- CPU saturation
- memory/OOM/swap risk
- PGDATA/WAL/tablespace capacity
- abnormal I/O latency
- excessive temporary files
- checkpoint pressure
- WAL generation anomaly
- WAL archive failure
- replication disconnect/lag
- replication-slot WAL retention
- autovacuum/freeze-age risk
- backup failure or backup staleness
- restore/PITR validation staleness
- configuration drift where monitored

Thresholds should be workload-specific and tuned from baseline data.

## 2.21.30 Multi-window alerting

Avoid paging for every transient spike.

A useful pattern is:

```text
Warning → lower threshold, longer context / ticket
Critical → sustained SLO or safety risk / page
Emergency → imminent data availability or durability risk
```

Examples of emergency-class conditions can include imminent disk exhaustion, transaction-ID wraparound danger, loss of all required HA replicas, or inability to archive WAL when recovery objectives depend on it.

## 2.21.31 Post-upgrade stabilization dashboard

After a patch or major upgrade, maintain a focused dashboard comparing baseline and current behavior:

```text
Availability
TPS
P50/P95/P99 application latency
Database error rate
Connections
CPU / memory
Storage latency and capacity
WAL rate
Checkpoints
Temporary files
Locks / deadlocks
Autovacuum
Replication lag
Archive status
Backup status
Top SQL
```

Use equivalent workload periods when comparing pre- and post-change data.

## 2.21.32 Statistics reset caveat

PostgreSQL statistics are cumulative and can be reset, but resetting them can affect operational interpretation.

PostgreSQL warns that `pg_stat_reset()` also resets counters used by autovacuum to determine vacuum/analyze needs. A database-wide `ANALYZE` is recommended after such a reset.

Do not reset production statistics simply to obtain a clean dashboard unless the operational consequences are understood and approved.

Also remember that unclean shutdown, base-backup startup, and PITR can reset cumulative statistics, so monitoring systems should tolerate counter resets.

## 2.21.33 Security of monitoring data

Detailed session/query information is security-sensitive.

PostgreSQL restricts visibility of some statistics. Superusers and appropriately privileged roles such as `pg_read_all_stats` can view broader activity information.

Grant monitoring privileges using least privilege. Protect exported query text and labels because they can contain identifiers or sensitive application context.

## 2.21.34 Failure scenarios

### FS-2.21-01 — Database is reachable but application latency is critical

Correlate application latency with active sessions, waits, blockers, top SQL, CPU, I/O, WAL/checkpoints, connection pool state, and recent changes. Do not treat endpoint availability as recovery.

### FS-2.21-02 — Disk usage rises rapidly because of WAL

Inspect WAL generation, archive health, replication slots, standby lag, and write workload. Protect filesystem headroom first. Do not delete WAL files manually from `pg_wal`.

### FS-2.21-03 — Replication lag alert fires after maintenance

Determine whether lag is transport, write, flush, or replay related. Inspect storage, WAL generation, standby workload, network, recovery conflicts, and replication state before rebuilding the standby.

### FS-2.21-04 — CPU reaches 100%

Identify workload concurrency and high-total-time SQL, inspect plans and parallelism, correlate with maintenance jobs, and protect application SLOs. Scaling CPU without identifying a runaway query or retry storm can hide the root cause.

### FS-2.21-05 — Temporary files surge

Identify responsible queries and execution plans, inspect sort/hash behavior and workload changes, verify storage headroom, and tune queries/indexes/statistics or scoped memory settings based on evidence.

### FS-2.21-06 — Backup dashboard is green but restore fails

Treat recoverability as degraded. Preserve existing backup/WAL data, determine why restore validation failed, repair the backup chain/process, and prove recovery before closing the incident.

### FS-2.21-07 — Alert storm after upgrade

Compare alert thresholds and metric semantics between PostgreSQL versions, validate collector compatibility, identify true regressions, and suppress only demonstrably invalid/noisy alarms. Do not silence broad database monitoring to make the change appear stable.

### FS-2.21-08 — Monitoring query creates database load

Reduce collection frequency or query cost, use appropriate native views/counters, avoid expensive full-catalog scans, and validate exporter behavior. Observability must not become a reliability incident itself.

```text
        ↓
Confirm User Impact
        ↓
Check PostgreSQL Availability
        ↓
Check pg_stat_activity + Waits
        ↓
Check Connections / Locks
        ↓
Check CPU / Memory / Storage
        ↓

        ↓

        ↓

        ↓

        ↓

```

## 2.21.36 Automation

Automate collection and validation of the core signals, but preserve raw evidence around incidents and changes.

A production platform should automate:

```text
metric collection
log collection
health probes
dashboard provisioning
alert rules
runbook links
maintenance silences with expiry
baseline comparisons
backup validation evidence
replication topology checks
capacity forecasting
```

Monitoring configuration should be version controlled and reviewed like database configuration.

## 2.21.37 Production case study — inactive replication slot fills WAL disk

A logical consumer stops, but its replication slot remains active in configuration and retains WAL. The database itself remains healthy until the WAL filesystem approaches exhaustion.

A mature monitoring design detects the problem through a combination of slot state, retained WAL, WAL generation rate, and filesystem forecast rather than waiting for disk-full failure.

Corrective controls:

```text
slot ownership inventory
consumer health monitoring
retained-WAL alerting
filesystem forecasting
runbook for abandoned/failed consumers
```

Never drop a slot automatically without understanding whether the consumer can tolerate loss of its retained WAL position.

## 2.21.38 Production case study — post-upgrade query regression

After a major upgrade, availability and CPU look normal, but P99 application latency increases. `pg_stat_statements`, application telemetry, and plan analysis isolate a small set of high-impact queries whose execution behavior changed.

The team validates statistics, compares execution plans, checks I/O and cache behavior, and applies targeted remediation rather than globally changing planner parameters.

The lesson is that production acceptance requires workload-level observability, not merely infrastructure health.

## 2.21.40 SRE/DBRE takeaway

PostgreSQL monitoring should answer four questions quickly:

```text
Is the database available?
Is the workload meeting its SLO?
What resource or database mechanism is limiting it?
Can the system recover safely if it fails?
```

The production monitoring model therefore combines application symptoms with PostgreSQL activity/statistics, host and storage telemetry, replication, WAL/archive state, and backup/recovery evidence.

An installation or upgrade is not complete until these signals are visible, actionable alerts are in place, and responders have tested runbooks for the failures those alerts represent.
