# 2.22 — Routine Maintenance, VACUUM, ANALYZE, and Database Health

**Status:** Production Ready / Complete

A PostgreSQL installation is not production-ready merely because the server starts and monitoring is enabled. PostgreSQL requires continuous maintenance of MVCC dead tuples, planner statistics, visibility maps, transaction ID age, indexes, logs, and storage health. In most production systems, autovacuum is the primary mechanism for VACUUM and ANALYZE and should remain enabled.

## Maintenance architecture

```text
Application Workload
        ↓
INSERT / UPDATE / DELETE
        ↓
MVCC Tuple Versions
        ↓
Autovacuum / Autoanalyze
        ↓
Space Reuse + Visibility Map
Planner Statistics + Freeze
        ↓
Stable Query Plans
Controlled XID Age
Healthy Storage Growth
```

The SRE/DBRE objective is not to run maintenance commands on a fixed schedule blindly. It is to prove that maintenance keeps pace with workload change.

## Why VACUUM is required

Routine VACUUM serves several important purposes:

1. reclaim or reuse storage occupied by obsolete row versions;
2. maintain planner statistics when combined with ANALYZE;
3. update the visibility map, supporting index-only scans;
4. prevent transaction ID and multixact ID wraparound problems.

Standard VACUUM normally operates alongside ordinary reads and writes. `VACUUM FULL`, by contrast, rewrites the table, requires additional temporary disk capacity, and takes an `ACCESS EXCLUSIVE` lock. It should not be the routine answer to table growth.

## Autovacuum baseline

Autovacuum is enabled by default and is strongly recommended for production clusters.

Important settings include:

```text
autovacuum
autovacuum_max_workers
autovacuum_naptime
autovacuum_vacuum_threshold
autovacuum_vacuum_scale_factor
autovacuum_analyze_threshold
autovacuum_analyze_scale_factor
autovacuum_vacuum_insert_threshold
autovacuum_vacuum_insert_scale_factor
autovacuum_vacuum_cost_delay
autovacuum_vacuum_cost_limit
autovacuum_freeze_max_age
log_autovacuum_min_duration
```

Do not disable autovacuum globally to solve a short-term performance problem. Doing so can convert temporary I/O pressure into table bloat, stale statistics, and eventually wraparound risk.

## Workload-aware thresholds

Default scale-factor behavior may be too slow for very large, frequently modified tables. A large table can accumulate a substantial number of dead tuples before a percentage-based threshold is reached.

Use table-specific storage parameters when evidence shows that a table needs a more aggressive maintenance policy.

Example pattern:

```sql
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_analyze_scale_factor = 0.01
);
```

These numbers are examples only. Tune them from table size, write rate, dead-tuple generation, vacuum duration, available I/O, and business latency objectives.

## Monitoring table maintenance

A useful table-level view is:

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_vacuum,
       last_autovacuum,
       last_analyze,
       last_autoanalyze,
       vacuum_count,
       autovacuum_count,
       analyze_count,
       autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Do not use `n_dead_tup` as an exact physical count. Statistics views are operational indicators and should be interpreted with table size, workload, maintenance history, and storage behavior.

PostgreSQL 18 adds cumulative time statistics for VACUUM, autovacuum, ANALYZE, and autoanalyze in the table statistics views. These provide useful evidence for identifying maintenance-heavy tables and quantifying background maintenance cost.

## VACUUM progress

For active standard VACUUM operations:

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

Use progress information to determine the phase, relation, scanned blocks, vacuumed blocks, and index-processing behavior rather than assuming a long-running vacuum is hung.

PostgreSQL 18 can also report cost-delay timing for VACUUM when `track_cost_delay_timing` is enabled.

## ANALYZE and planner statistics

`ANALYZE` samples table data and stores planner statistics in PostgreSQL's statistics catalogs. Accurate statistics are critical to row-count estimates, join ordering, access-path selection, and overall plan quality.

```sql
ANALYZE orders;
```

or:

```sql
VACUUM (ANALYZE) orders;
```

Do not respond to every slow query by immediately changing planner settings. First verify whether the underlying statistics are current and representative.

## Partitioned tables

Partitioned tables require special operational attention. Autovacuum processes individual partitions, but it does not automatically analyze the partitioned parent based on changes occurring only in its partitions.

For workloads whose plans depend on parent-level statistics, schedule or trigger manual ANALYZE of the partitioned parent when the distribution changes materially.

Example:

```sql
ANALYZE parent_partitioned_table;
```

This should be part of ingestion, bulk-load, partition-rotation, or deployment automation where appropriate.

## Foreign and temporary tables

Autovacuum does not automatically analyze foreign tables because PostgreSQL cannot generally determine when their external data changes. Where the foreign data wrapper supports ANALYZE and query planning depends on those statistics, establish an explicit maintenance schedule.

Temporary tables are not serviced by autovacuum. Sessions using heavily modified temporary tables may need explicit VACUUM or ANALYZE as appropriate.

## Transaction ID wraparound

Wraparound prevention is a reliability requirement, not optional performance tuning.

Monitor database XID age:

```sql
SELECT datname,
       age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

Monitor relation-level age when investigating a database:

```sql
SELECT n.nspname,
       c.relname,
       age(c.relfrozenxid) AS xid_age
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','m')
ORDER BY xid_age DESC
LIMIT 50;
```

Alert well before emergency anti-wraparound behavior or shutdown protection becomes relevant. Thresholds must leave enough time for the largest tables to be vacuumed under degraded conditions.

## Long-running transactions and vacuum

Old transactions can prevent removal of row versions that remain potentially visible to those snapshots.

Investigate long-running transactions:

```sql
SELECT pid,
       usename,
       datname,
       state,
       xact_start,
       query_start,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Also monitor `idle in transaction` sessions. An application connection that remains in a transaction unnecessarily can become a maintenance and bloat problem even if it consumes little CPU.

## Replication slots and cleanup pressure

Replication slots can retain WAL and, depending on slot type and configuration, can also affect cleanup horizons. Monitor slot state and retention rather than treating slots as passive metadata.

```sql
SELECT slot_name,
       slot_type,
       active,
       restart_lsn,
       confirmed_flush_lsn
FROM pg_replication_slots;
```

A stale slot can become a disk-capacity incident. Slot ownership and lifecycle must be part of SRE/DBRE governance.

## VACUUM FULL

`VACUUM FULL` rewrites a table and returns unused space to the operating system, but it requires an exclusive table lock and extra disk space while the rewrite occurs.

Use it only after evaluating whether physical shrinkage is actually required.

```sql
VACUUM (FULL, ANALYZE) target_table;
```

Before production execution validate:

```text
Expected lock duration
Table and index size
Available free space
Application outage impact
Replica/WAL impact
Backup status
Rollback/recovery plan
Maintenance window
```

Routine standard VACUUM should normally prevent VACUUM FULL from becoming routine maintenance.

## Bloat investigation

Do not equate every large table with bloat. PostgreSQL deliberately keeps reusable free space inside relations.

Investigate:

```text
Table growth versus business data growth
Dead-tuple trends
Update/delete rate
Vacuum frequency and duration
Long transactions
HOT update behavior
Index growth
Free-space reuse
Storage headroom
```

Only then decide whether normal vacuuming, tuning, reindexing, table rewriting, partition redesign, or application changes are appropriate.

## Index maintenance

Indexes can also require maintenance. PostgreSQL documents routine reindexing as a maintenance task, but indiscriminate periodic REINDEX of every index is not a good production policy.

Investigate index health when there is evidence of abnormal growth, corruption, changed collation behavior, or workload-driven inefficiency.

Choose online/concurrent maintenance approaches where supported and required by availability objectives, and validate the additional resource cost.

## Logging maintenance

PostgreSQL log files are also an operational storage dependency. Ensure log rotation, retention, collection, and filesystem monitoring prevent logging from exhausting database storage.

Keep WAL, database files, backups, and logs separated or quota-controlled where architecture permits so one uncontrolled stream does not consume all critical capacity.

## I/O impact of maintenance

VACUUM can generate substantial I/O. Monitor maintenance against foreground workload latency rather than maximizing maintenance throughput without constraints.

Useful evidence includes:

```text
pg_stat_io
pg_stat_progress_vacuum
pg_stat_progress_analyze
Host IOPS and throughput
Storage latency
CPU utilization
Checkpoint behavior
WAL generation
Application P95/P99 latency
```

PostgreSQL 18 adds additional VACUUM/ANALYZE observability, including delay-time reporting and richer verbose output. Use those facilities to determine whether maintenance is constrained by cost delay, I/O, CPU, locks, or workload contention.

## Maintenance windows versus continuous maintenance

Autovacuum is designed to react to workload changes continuously. A fixed nightly maintenance job is not a substitute for a healthy autovacuum system on a high-write database.

Scheduled jobs remain useful for activities such as:

```text
Manual ANALYZE of partitioned parents
Foreign-table ANALYZE
Targeted maintenance after bulk loads
Controlled REINDEX operations
Health audits
Backup verification
Log housekeeping
```

The preferred model is continuous automatic maintenance plus targeted scheduled remediation.

## Alerting baseline

Create alerts for conditions such as:

```text
XID age approaching operational threshold
Multixact age risk
Autovacuum disabled unexpectedly
Tables with rapidly growing dead tuples
No successful vacuum on high-churn tables
No ANALYZE after major data change
Long-running transactions
Idle-in-transaction sessions
Blocked or repeatedly cancelled autovacuum
Storage utilization / inode pressure
Unexpected table or index growth
Stale replication slots / WAL retention
Maintenance consuming abnormal I/O
Log filesystem growth
```

Avoid a single universal dead-tuple threshold for all tables. Alerting should consider relation size and change rate.

## Troubleshooting workflow

```text
Performance / Growth / XID Alert
             ↓
Identify Database + Relation
             ↓
Check Table Statistics
             ↓
Check Active Vacuum / Analyze
             ↓
Check Long Transactions + Locks
             ↓
Check Autovacuum Configuration
             ↓
Check Storage + I/O
             ↓
Check Planner Statistics
             ↓
Check Slots / Replication
             ↓
Apply Targeted Remediation
             ↓
Validate Trend Recovery
```

## Failure scenarios

### FS-2.22-01 — Autovacuum disabled globally

Re-enable it unless there is an explicitly engineered alternative. Assess XID age, dead tuples, planner statistics, storage growth, and tables requiring immediate maintenance. Do not assume re-enabling the daemon instantly removes accumulated debt.

### FS-2.22-02 — Large table never catches up with vacuum

Inspect write rate, thresholds, worker availability, cost limits/delays, storage throughput, locks, long transactions, and table-specific settings. Tune from evidence rather than repeatedly launching competing manual vacuums.

### FS-2.22-03 — XID age alert becomes critical

Protect database availability. Identify the oldest databases and relations, remove blockers safely, ensure autovacuum can run, and execute targeted vacuuming according to the anti-wraparound runbook. Avoid unnecessary workload or DDL that interferes with recovery.

### FS-2.22-04 — VACUUM FULL blocks production traffic

Determine whether the operation can be safely cancelled and whether cancellation consequences are acceptable. Restore application availability first, then redesign the space-reclamation plan with explicit locking and maintenance-window analysis.

### FS-2.22-05 — Query plans regress after bulk load

Check last analyze timestamps and data-distribution change. Run targeted ANALYZE, validate plans with EXPLAIN, and consider statistics-target or extended-statistics changes only when evidence requires them.

### FS-2.22-06 — Partitioned parent has stale statistics

Run manual ANALYZE on the partitioned parent and validate representative plans. Add the operation to partition/data-load automation so the condition does not recur.

### FS-2.22-07 — Autovacuum repeatedly blocked by DDL locks

Identify conflicting lock holders and maintenance/deployment patterns. Protect wraparound safety, reschedule or redesign conflicting DDL, and alert on repeated cancellation or starvation.

### FS-2.22-08 — Log or maintenance activity exhausts storage

Reduce the immediate source safely, restore filesystem headroom, verify WAL and database health, and correct retention/capacity policy. Never delete PostgreSQL internal files manually to free space.

## Recovery validation

After remediation validate that the underlying trend has changed:

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Validate XID age again and observe it over time. Confirm storage utilization, application latency, WAL behavior, and autovacuum worker activity.

A one-time successful VACUUM is not proof that maintenance is healthy; the system must continue to keep pace under normal workload.

## Automation

Automate collection of maintenance health indicators and produce ranked exception reports rather than running destructive maintenance automatically.

A production maintenance controller may evaluate:

```text
Relation size
Dead-tuple ratio and growth
Last vacuum / analyze
XID age
Autovacuum duration
Write rate
Long transaction age
Lock blockers
Storage headroom
Replication-slot retention
Application latency
```

Safe automation can recommend or trigger standard VACUUM/ANALYZE within approved bounds. High-impact actions such as `VACUUM FULL`, table rewrites, index rebuilds, or terminating sessions should require explicit policy and safeguards.

## Production case study — percentage threshold on a very large table

A multi-terabyte table receives continuous updates. Default percentage-based thresholds allow a large absolute number of changed rows to accumulate before autovacuum runs. Dead tuples increase, vacuum duration grows, and application latency becomes less predictable.

The DBRE team lowers table-specific scale factors, validates storage capacity, monitors vacuum duration and dead-tuple trends, and confirms that maintenance now keeps pace with the write workload.

The lesson is that autovacuum configuration must scale with table size and change rate.

## Production case study — idle transaction causes persistent bloat

A connection pool leaves a session `idle in transaction` for many hours. Autovacuum runs successfully but cannot reclaim row versions still required by the old snapshot. Table and index sizes continue growing.

The team identifies the old transaction through `pg_stat_activity`, corrects the application transaction lifecycle, introduces `idle_in_transaction_session_timeout` where appropriate, and alerts on transaction age.

The lesson is that vacuum symptoms can originate in application behavior rather than autovacuum configuration.

## SRE/DBRE takeaway

Healthy PostgreSQL maintenance is a continuous control loop:

```text
Observe workload change
        ↓
Vacuum + Analyze
        ↓
Measure effectiveness
        ↓
Detect maintenance debt
        ↓
Remove blockers / tune safely
        ↓
Validate recovery
        ↓
Continue monitoring
```

The goal is not zero dead tuples or minimum possible relation size. The goal is a stable system in which maintenance reliably keeps pace with workload, planner statistics remain useful, storage growth is understood, and transaction ID age stays comfortably inside safe operating limits.
