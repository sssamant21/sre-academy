# 2.3 — Linux Operating System Preparation

**Status:** Production Ready / Complete

Linux is part of PostgreSQL's reliability architecture. Production preparation must establish a supported, secure, observable, and capacity-tested operating-system baseline rather than applying generic tuning values.

## Production objectives

The Linux platform must provide predictable CPU scheduling, memory management, filesystem and storage behavior, networking, process management, IPC, file descriptors, time synchronization, security controls, and service management.

```text
Application
    ↓
PostgreSQL
    ↓
Linux Kernel
    ↓
Filesystem / Page Cache
    ↓
Block Storage
    ↓
Physical / Cloud Infrastructure
```

A failure at any lower layer can surface as a PostgreSQL incident.

## Platform and capacity planning

Use a maintained Linux distribution whose lifecycle is compatible with the PostgreSQL platform. Typical enterprise choices include RHEL-family distributions, Ubuntu LTS, Debian, SUSE, and supported cloud images.

Size CPU, memory, storage capacity, IOPS, throughput, latency, network bandwidth, and failure capacity from workload requirements. CPU utilization alone is not a capacity model; correlate CPU, run queue, I/O wait, storage latency, PostgreSQL active sessions, and query latency.

Large multi-socket systems require NUMA awareness. Inspect topology with `lscpu` and, where available, `numactl --hardware`. Do not apply generic NUMA tuning without workload and platform validation.

## Memory architecture

Physical RAM is shared by PostgreSQL shared memory, backend/private memory, maintenance and parallel workers, the Linux page cache, kernel memory, and other host processes.

A simplified model is:

```text
Physical RAM
 ├── PostgreSQL shared memory / shared_buffers
 ├── Backend/private query memory
 ├── Maintenance and parallel workers
 ├── Linux page cache
 ├── Kernel
 └── Monitoring/security/other processes
```

Approximately 25% of RAM can be a reasonable starting point for `shared_buffers` on a dedicated database server, but this is not a universal sizing formula. PostgreSQL also relies on operating-system caching, and workload testing is required.

Do not estimate total memory simply as `shared_buffers + max_connections × work_mem`. A query can contain multiple memory-consuming sort/hash operations and parallel workers can increase aggregate demand.

## Linux overcommit, OOM, and swap

Linux memory overcommit can result in the OOM killer terminating PostgreSQL processes when memory is exhausted. Investigate `shared_buffers`, `work_mem`, `hash_mem_multiplier`, maintenance workloads, connection count, parallelism, other processes, and cgroup/container limits.

Useful diagnostics include:

```bash
dmesg -T | grep -i -E 'oom|killed process'
journalctl -k | grep -i oom
free -h
vmstat 1
```

Strict overcommit configuration such as `vm.overcommit_memory=2` can be appropriate in some environments, but it must not be applied blindly. Excessive connection counts should also trigger evaluation of `max_connections` and external connection pooling.

Disabling swap everywhere is not a universal PostgreSQL rule. Swap can provide protection against OOM, while sustained active swapping can cause severe latency. Monitor swap-in/out and memory pressure and design the host so PostgreSQL's active working set is not continuously paged to disk.

## Huge pages and Transparent Huge Pages

PostgreSQL supports explicit Linux HugeTLB pages through `huge_pages = try|on|off`; `try` is the normal default. `shared_memory_size_in_huge_pages` can be used to estimate requirements. With `huge_pages=on`, PostgreSQL cannot start if the required huge pages cannot be allocated.

Linux Transparent Huge Pages (THP) are distinct from explicit HugeTLB pages. PostgreSQL currently discourages THP for PostgreSQL workloads because it has caused performance degradation for some users on some Linux versions. Establish a tested platform policy based on the PostgreSQL release, Linux distribution/kernel, vendor guidance, and measured workload behavior.

## Kernel and IPC resources

Do not copy legacy PostgreSQL tuning recipes containing arbitrary values for `kernel.shmmax`, `kernel.shmall`, `kernel.sem`, `vm.dirty_ratio`, `vm.swappiness`, or `vm.overcommit_memory`.

Modern Linux defaults are normally adequate for many PostgreSQL installations. Change kernel parameters only when the resource constraint or reliability objective is understood and the change is validated.

### systemd RemoveIPC

Validate systemd IPC cleanup behavior. PostgreSQL service accounts created by distribution packages are normally system accounts, which avoids premature IPC cleanup. If the database account is not treated as a system account, validate whether `RemoveIPC=no` is required by the platform design.

Production control:

```text
postgres is a system account
        OR
systemd RemoveIPC behavior is explicitly validated
```

## File descriptors and process limits

Inspect host and PostgreSQL service limits:

```bash
ulimit -n
ulimit -u
cat /proc/$(pgrep -o postgres)/limits
systemctl show postgresql | grep -E 'LimitNOFILE|LimitNPROC'
```

`max_files_per_process` should not be treated as a generic tuning target. When `Too many open files` occurs, investigate PostgreSQL usage plus per-process and system-wide OS limits.

## PostgreSQL service account and PGDATA security

Run PostgreSQL using a dedicated operating-system account, commonly `postgres`, following least privilege. `initdb` must run as the account that will own the server and must not run as root.

For an owner-only cluster, reference permissions are directories `0700` and files `0600`. Where group-read access is deliberately enabled, PostgreSQL supports directories `0750` and files `0640`. Distribution/package conventions still take precedence where applicable.

## Filesystem and storage architecture

A production design may separate PGDATA, WAL, tablespaces, logs, and archive staging when doing so provides capacity or performance isolation. Separation also creates additional mount dependencies, so every filesystem must be monitored.

When PGDATA resides on a dedicated mounted filesystem, avoid using the mount-point root itself as PGDATA. Create a PostgreSQL-owned directory beneath it, for example:

```text
/data
 └── postgresql
      └── 18
           └── data   ← PGDATA
```

XFS and ext4 are common choices, but neither should be declared universally superior. Prioritize supported POSIX behavior, integrity, durability, measured latency, operational standards, and recovery capability.

Monitor PGDATA, WAL, tablespaces, logs, archive destinations, temporary space, filesystem capacity, and inode usage independently.

```bash
df -h
df -i
du -xsh /path/*
lsblk
findmnt
```

Capacity planning must include database data, indexes, WAL, temporary operations, vacuum/rewrite operations, index builds, upgrade workspace, logs, growth, and operational safety headroom.

### WAL capacity rule

A rapidly growing `pg_wal` can be caused by replication slots, archiving failures, unhealthy standbys, backup processes, or high WAL generation. Never manually delete active files from `pg_wal` as a disk-space workaround. Diagnose and correct the retention cause.

## Storage performance

Evaluate latency, IOPS, throughput, queue depth, and utilization using Linux and cloud-provider metrics.

```bash
iostat -xz 1
pidstat -d 1
sar -d 1
lsblk
```

High query latency with normal CPU but elevated I/O latency and device queues is a storage investigation, not automatically a SQL or CPU-sizing problem.

## Network, DNS, and time

Validate PostgreSQL client, replication, backup, monitoring, HA, and DR network paths. Monitor latency, packet loss, retransmissions, interface errors, bandwidth, and connection failures.

DNS is a database dependency when applications or HA systems use hostnames. Validate resolver behavior from the same network context as the application.

All production PostgreSQL hosts require reliable time synchronization through an approved service such as chrony or the platform equivalent. Clock consistency is essential for log correlation, monitoring, auditing, certificate validation, and incident reconstruction.

## Security hardening

Use least privilege, restricted SSH, host firewalling, security patching, protected secrets, correct filesystem ownership, audit controls, and SELinux/AppArmor where applicable. Do not disable SELinux or AppArmor simply to make PostgreSQL start; diagnose the policy/context failure and correct it.

## OS observability baseline

Useful incident tools include:

```bash
uptime
free -h
vmstat 1
mpstat -P ALL 1
pidstat 1
iostat -xz 1
df -h
df -i
lsblk
ss -s
journalctl
dmesg
```

Monitor CPU utilization/run queue/steal, memory pressure, swap activity, OOM events, filesystem and inode capacity, storage latency/IOPS/throughput/queue, network errors/retransmits, clock synchronization, mount availability, kernel events, and PostgreSQL service health.

Prefer warning, critical, and forecasted-exhaustion capacity alerts rather than relying only on a single static threshold.

## Production failure scenarios

### FS-2.3-01 — PostgreSQL terminated by Linux OOM

Detect kernel OOM events, restore memory availability, validate PostgreSQL recovery, and correct the underlying connection, query-memory, parallelism, host-process, or capacity issue.

### FS-2.3-02 — WAL filesystem exhaustion

Investigate replication slots, archiver state, standby health, backup activity, and WAL generation. Never delete WAL manually.

### FS-2.3-03 — Storage latency degradation

Correlate query latency with I/O latency, queue depth, throughput, and provider storage metrics before changing PostgreSQL or CPU configuration.

### FS-2.3-04 — Swap thrashing

Identify the source of memory pressure and reduce or redistribute memory demand rather than merely clearing swap.

### FS-2.3-05 — Incorrect filesystem ownership or permissions

Validate the complete path with `namei -l`, inspect ownership, and restore permissions appropriate to the installation model. Never use `chmod 777` as a PostgreSQL repair procedure.

### FS-2.3-06 — DNS degradation

Validate resolver latency and correctness from the application path when connection latency rises while PostgreSQL itself remains healthy.

### FS-2.3-07 — File descriptor exhaustion

Inspect process and system limits and determine the cause of file consumption before raising limits.

### FS-2.3-08 — Filesystem/device failure

Treat kernel filesystem or block-device errors as potential data-integrity events. Inspect kernel logs and storage health before returning the database to service.

### FS-2.3-09 — OS listen-queue exhaustion

Connection bursts can exceed the operating-system socket listen queue before PostgreSQL services them. Investigate PostgreSQL availability, connection count, pooler behavior, application retry storms, the OS listen queue, and `net.core.somaxconn`. Do not simply raise `somaxconn` without understanding the connection storm.

## Recovery workflow

```text
Alert
 ↓
Identify affected layer
 ↓
Protect database integrity
 ↓
Stop/redirect traffic if required
 ↓
Correct OS/storage condition
 ↓
Validate filesystem/storage
 ↓
Validate PostgreSQL startup/recovery
 ↓
Validate WAL and replication
 ↓
Validate application
 ↓
Restore traffic
 ↓
Capture RCA
```

Data integrity takes priority over restoring traffic quickly.

## Automation and configuration drift

Automate the approved OS baseline, repositories, packages, service account, filesystems/mounts, justified kernel policy, security policy, monitoring, and validation through tools such as Terraform, Ansible, cloud-init, or image pipelines.

Continuously detect drift in OS/kernel versions, mount configuration, sysctl, service limits, security controls, package versions, monitoring agents, and time synchronization. Correct the automation source of truth rather than normalizing undocumented manual production changes.

## Key takeaways

Linux is not merely the place where PostgreSQL binaries run; it is part of the database reliability architecture.

The SRE/DBRE standard is:

> Do not apply generic Linux “PostgreSQL tuning” values blindly. Establish a supported OS baseline, measure the workload, understand the failure mode, change only what has an engineering justification, and validate the result.

A production-ready Linux platform must combine capacity engineering, memory safety, durable storage, predictable networking, security, observability, automation, drift management, and tested recovery.
