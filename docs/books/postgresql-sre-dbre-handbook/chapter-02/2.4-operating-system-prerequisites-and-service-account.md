# 2.4 — Operating-System Prerequisites and PostgreSQL Service Account

**Status:** Production Ready / Complete

PostgreSQL reliability depends on the host beneath it. Production deployment therefore requires explicit OS prerequisites and a dedicated PostgreSQL runtime identity.

## Dedicated server owner

The PostgreSQL server must run as an unprivileged operating-system user. `initdb` must be executed by the user that will own the server process and refuses to run as root.

If a root-owned parent path is required, create the target directory administratively, assign ownership to the PostgreSQL user, then initialize as that user.

## Host readiness

Validate CPU/memory sizing, storage, filesystem/mounts, swap policy, process/file limits, time synchronization, DNS, hostname resolution, network routes, firewall controls, entropy/crypto dependencies, locale availability, and OS patch state.

## Directory ownership

Apply least privilege to PGDATA, WAL, tablespaces, log directories, socket directories, and backup staging. Avoid broad writable permissions. PostgreSQL's cluster files contain sensitive database data and credentials/configuration metadata.

## Time and DNS

Clock synchronization is operationally important for logs, TLS/certificates, distributed troubleshooting, backups, and HA orchestration. DNS and hostname behavior must be deterministic for application, replication, monitoring, and backup paths.

## Resource limits

Validate service-level and OS-level limits under expected connection and workload volume. Do not make arbitrary kernel tuning changes without evidence and platform guidance.

## Filesystem and mounts

Ensure required mounts are present before PostgreSQL starts. A missing mount can expose an empty underlying directory and create a dangerous split storage state. Automate mount dependencies in service orchestration where appropriate.

## Monitoring

Monitor CPU, memory pressure, swap, load/run queue, filesystem utilization, inode usage, latency, IOPS/throughput, filesystem errors, network errors, time synchronization, and service state alongside PostgreSQL metrics.

## Failure scenarios

- PostgreSQL started as root: prohibited; correct service identity.
- PGDATA owned by wrong account: stop service and correct ownership deliberately.
- Required mount missing: prevent startup until storage is restored.
- Time drift: correct host time source and validate HA/logging impact.
- Resource limits too low: change through controlled OS/service configuration and retest.

## Production checklist

- [ ] Dedicated unprivileged PostgreSQL account
- [ ] Directory ownership verified
- [ ] Required mounts verified
- [ ] Capacity/inodes validated
- [ ] Time synchronization healthy
- [ ] DNS/network/firewall validated
- [ ] Resource limits reviewed
- [ ] Host monitoring enabled
- [ ] OS patch baseline recorded
