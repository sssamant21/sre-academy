# 2.4 — PostgreSQL Package-Based Installation

**Status:** Production Ready / Complete

Package-based installation is the preferred deployment method for most self-managed PostgreSQL environments because it integrates PostgreSQL with the operating system package manager, dependency management, service management, security updates, and standardized filesystem conventions.

For SRE/DBRE teams, successful installation means more than getting a `postgres` process running. A production installation must be repeatable, version-controlled, secure, observable, upgradeable, and recoverable.

```text
Approved PostgreSQL Version
        ↓
Approved Repository
        ↓
Package Installation
        ↓
Cluster Initialization
        ↓
Filesystem / Permissions
        ↓
Service Configuration
        ↓
Security Baseline
        ↓
Validation
        ↓
Monitoring
        ↓
Production Readiness
```

## Package-based vs. source installation

Package installation normally provides dependency management, standardized binaries, service integration, predictable package inventory, security-update integration, and simpler patch management. Source builds provide additional build-time control but transfer more lifecycle responsibility to the organization.

Production standard: use an approved package repository unless a documented technical requirement requires a custom source build.

## Repository and lifecycle governance

Linux distributions may provide PostgreSQL through their native repositories. PGDG also provides PostgreSQL packages for major Linux families. Repository selection is an architectural and lifecycle decision.

```text
OS lifecycle
      ≠
PostgreSQL community lifecycle
      ≠
PGDG/distribution package lifecycle
```

Standardize the approved repository, PostgreSQL major version, minor-release policy, and package-management ownership. Do not mix distribution packages, PGDG packages, manually downloaded packages, and custom binaries without an explicit design reason.

Validate repository provenance, signing keys, package signatures, TLS access, package inventory, and administrative privileges. Never disable signature verification simply to make an installation succeed.

## Version control and pinning

Production systems must not move between PostgreSQL major versions accidentally. Minor package updates within an approved major are fundamentally different from a major-version transition.

Track the approved major version, installed minor version, available package version, EOL date, and upgrade status. Repository policy must also prevent beta, release-candidate, development-snapshot, and unsupported PostgreSQL packages from being selected for production.

## Pre-installation validation

Validate the Linux baseline from section 2.3 before installing PostgreSQL:

```bash
cat /etc/os-release
uname -r
lscpu
free -h
df -h
df -i
lsblk
findmnt
timedatectl
```

Confirm supported OS and architecture, memory, storage, filesystems, DNS, time synchronization, repository access, firewall/security policy, and the PostgreSQL service-account strategy.

## RHEL / Rocky Linux / AlmaLinux

For Red Hat-family systems, PostgreSQL may come from the distribution repository or PGDG. When PGDG is selected, obtain the repository configuration from the current official PGDG instructions for the exact OS release, architecture, and PostgreSQL major version. Do not preserve an old repository RPM URL indefinitely in a production runbook.

A conceptual PostgreSQL 18 PGDG installation is:

```bash
# Configure the approved current PGDG repository for this OS/architecture
sudo dnf install postgresql18-server
```

Resolve distribution module/repository conflicts according to the current supported packaging instructions. The package installation does not by itself prove that a database cluster has been initialized.

PGDG RPM installations commonly provide version-specific setup tooling. A typical pattern is:

```bash
sudo /usr/pgsql-18/bin/postgresql-18-setup initdb
sudo systemctl enable postgresql-18
sudo systemctl start postgresql-18
```

Validate the actual package and service names on the target platform rather than copying commands from another PostgreSQL major release.

## Debian / Ubuntu

Debian-family systems commonly use APT. If a specific PostgreSQL major version is required, make it explicit rather than relying on the distribution default.

Current PGDG repository setup can use the `postgresql-common` helper:

```bash
sudo apt install -y postgresql-common
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh
sudo apt update
sudo apt install postgresql-18
```

Debian-family packaging includes cluster-management utilities such as:

```bash
pg_lsclusters
pg_createcluster
pg_ctlcluster
pg_dropcluster
```

Package installation may create a default cluster depending on packaging behavior and configuration. Production automation must know whether installation also initialized and/or started a cluster.

## Package installation vs. cluster initialization

These are separate lifecycle events:

```text
Install PostgreSQL binaries
          ↓
Initialize database cluster
          ↓
Configure PostgreSQL
          ↓
Start database
          ↓
Validate production readiness
```

**Package installed ≠ PostgreSQL cluster initialized ≠ PostgreSQL production-ready.**

`initdb` creates the database cluster and must run as the operating-system account that will own the PostgreSQL server, not as root. Initialization must occur only after the intended PGDATA/storage architecture has been confirmed.

## PostgreSQL 18 data checksums

PostgreSQL 18 changed `initdb` so data checksums are enabled by default. Initialization records should therefore capture PostgreSQL version, PGDATA, locale, encoding, superuser, authentication choices, data-checksum state, WAL location, and initialization options.

Validate after initialization:

```sql
SHOW data_checksums;
```

Checksum state is also important for future upgrade planning.

## Service management and crash recovery

Package-based PostgreSQL should integrate with the platform service manager, normally systemd.

```bash
systemctl list-unit-files | grep postgres
systemctl status postgresql-18
systemctl cat postgresql-18
journalctl -u postgresql-18
```

Do not guess the service name in automation.

A service that takes time to start is not necessarily hung. After an unclean shutdown PostgreSQL may perform WAL crash recovery before accepting connections. Inspect PostgreSQL logs and recovery progress before repeatedly restarting a service or changing systemd timeout settings.

## Process, listener, and version validation

Validate PostgreSQL processes and listening sockets:

```bash
ps -ef | grep '[p]ostgres'
ss -lntp | grep 5432
```

Do not assume a fresh installation should listen on every interface. Remote access must be deliberately configured through PostgreSQL authentication/listener settings and network controls.

Validate binary paths and versions explicitly:

```bash
command -v psql
command -v postgres
readlink -f "$(command -v psql)"
psql --version
postgres --version
```

Then validate the actual running server:

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
SHOW listen_addresses;
SHOW port;
```

Multiple PostgreSQL major versions can coexist during upgrades. Never assume the first `psql`, `postgres`, `pg_dump`, `pg_restore`, `pg_basebackup`, or `pg_upgrade` in `$PATH` is the intended version. Treat each utility according to its documented cross-version compatibility requirements.

## PGDATA ownership and permissions

Validate the active PGDATA from PostgreSQL and inspect filesystem ownership:

```bash
ls -ld "$PGDATA"
namei -l "$PGDATA"
```

Do not repair PostgreSQL permissions with broad permissions such as `chmod -R 777`. Follow the package/distribution and PostgreSQL ownership model.

## Client and extension packages

Administrative or application hosts may need client utilities such as `psql`, `pg_dump`, `pg_restore`, and `pg_isready` without the database server package. Install server, client, contrib, extension, development, and debug packages deliberately rather than treating them as one bundle.

Do not install compiler/development packages on production database hosts unless required by the deployment design.

## Connectivity and security baseline

Validate local connectivity before exposing the database remotely:

```bash
sudo -u postgres psql
pg_isready
```

Example SQL validation:

```sql
SELECT current_database();
SELECT current_user;
SELECT version();
SHOW data_directory;
```

`pg_isready` verifies PostgreSQL connection status; it does not prove application, schema, replication, backup, or performance health.

Before enabling remote traffic, validate `listen_addresses`, `pg_hba.conf`, authentication methods, TLS policy, firewall/security groups, database roles, service-account permissions, and filesystem security. Never solve an authentication problem by globally changing production authentication to `trust`.

## Package updates and minor releases

Package management becomes part of PostgreSQL patching. Use a controlled lifecycle:

```text
Release available
      ↓
Release-note review
      ↓
Security/risk assessment
      ↓
Non-production validation
      ↓
Backup/recovery readiness
      ↓
Change window
      ↓
Package update
      ↓
Restart where required
      ↓
Post-change validation
```

Explicitly define whether unattended OS update mechanisms may update PostgreSQL packages or restart the service. Database lifecycle control must remain deliberate even when security patching is automated.

## Installation logging and monitoring

Capture repository configuration, package versions, package-manager history, initialization output, service logs, PostgreSQL startup logs, and automation output.

Examples include:

```bash
dnf history
journalctl -u postgresql-18
```

or the appropriate APT history on Debian-family systems.

Establish monitoring immediately for PostgreSQL service/process state, readiness, port availability, filesystem capacity, WAL capacity, memory, CPU, storage latency, logs, and connection failures.

## Production failure scenarios

### FS-2.4-01 — Repository unavailable

Investigate DNS, proxy, firewall, TLS, repository configuration, metadata, and certificate chain. Do not bypass repository security controls.

### FS-2.4-02 — Wrong PostgreSQL major version installed

Stop before onboarding production data, inspect installed packages and repositories, correct repository/version policy, and install the approved major version using a controlled procedure.

### FS-2.4-03 — Service fails after installation

Inspect systemd and PostgreSQL logs, then validate PGDATA, permissions, configuration syntax, port conflicts, filesystem availability/capacity, Huge Pages, SELinux/AppArmor, and crash-recovery state. Do not repeatedly restart without identifying the cause.

### FS-2.4-04 — Port 5432 already in use

Use `ss -lntp` to identify the owner. Another PostgreSQL cluster/version or another service may legitimately own the port. Do not kill the process automatically.

### FS-2.4-05 — Package dependency/repository conflict

Common causes include mixed repositories, distribution module conflicts, old PostgreSQL packages, extension dependencies, and unsupported OS releases. Restore a consistent package model rather than using unsafe dependency overrides.

### FS-2.4-06 — Packages installed but cluster not initialized

Confirm the intended PGDATA and storage architecture, then use the platform's approved initialization procedure. Never initialize blindly on a host that may contain an existing cluster.

### FS-2.4-07 — Service starts against wrong PGDATA

Validate `SHOW data_directory` and correlate it with the systemd/package configuration before allowing application traffic.

### FS-2.4-08 — Authentication failure after installation

Validate `SHOW hba_file`, listener settings, and the matching HBA rule. Do not globally switch authentication to `trust`.

### FS-2.4-09 — Pre-release PostgreSQL package accidentally deployed

A development repository or incorrect package selector may install a beta, RC, or snapshot. Stop onboarding, preserve evidence, determine whether a cluster was initialized or received data, correct repository policy, and choose a safe remediation or migration path.

## Recovery workflow

```text
Installation failure
       ↓
Stop repeated changes
       ↓
Capture package/service logs
       ↓
Identify failure layer
       ↓
Repository / Package / Filesystem /
Initialization / Permissions /
Configuration / Security / Port
       ↓
Correct root cause
       ↓
Validate package inventory
       ↓
Validate PGDATA
       ↓
Validate service and PostgreSQL
       ↓
Validate security and monitoring
       ↓

```

## Automation and idempotency

Represent installation through approved tooling such as Terraform, Ansible, cloud-init, or image pipelines. Encode OS version, repository, PostgreSQL major version, required packages, service name, PGDATA architecture, initialization policy, security baseline, and monitoring.

Automation must be idempotent. Running it again must never reinitialize PGDATA, overwrite an existing cluster, silently change the PostgreSQL major version, change repository ownership unexpectedly, reset authentication, or destroy existing database state.

## Configuration drift

Monitor installed PostgreSQL packages, repository configuration, major/minor version, service unit, PGDATA, dependencies, extension packages, and relevant OS packages. Undocumented manual package changes must not silently become the production standard.

## Key takeaways

Package-based installation should produce a controlled PostgreSQL platform, not merely installed binaries.

```text
Approved Version
      ↓
Trusted Repository
      ↓
Explicit Package
      ↓
Controlled Initialization
      ↓
Secure Configuration
      ↓
Service Integration
      ↓
Validation
      ↓
Monitoring
      ↓
Lifecycle Management
```

**Package installed ≠ PostgreSQL cluster initialized ≠ PostgreSQL production-ready.**

Never allow the package manager to choose the PostgreSQL major version accidentally, and never treat a successful `systemctl start` as proof of production readiness.

The installation is complete only when the running server version, binary paths, PGDATA, checksum state where applicable, service, permissions, security, monitoring, patch policy, and recovery readiness have all been verified.
