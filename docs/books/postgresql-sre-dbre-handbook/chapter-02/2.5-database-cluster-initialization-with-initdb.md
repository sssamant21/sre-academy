# 2.5 — Database Cluster Initialization with initdb

**Status:** Production Ready / Complete

`initdb` creates a PostgreSQL database cluster: PGDATA, shared catalogs, and the initial `postgres`, `template1`, and `template0` databases. Initialization choices become durable cluster properties and must be controlled in production.

## Runtime identity

Run `initdb` as the operating-system user that will own the PostgreSQL server process. Do not run it as root.

## Production initialization

Example pattern:

```bash
/usr/pgsql-18/bin/initdb -D /pgdata/18/data
```

Choose locale, encoding, authentication, checksums, WAL directory, and other initialization options deliberately rather than relying on defaults without review.

## PostgreSQL 18 checksum default

PostgreSQL 18 enables data checksums by default for newly initialized clusters. The option `--no-data-checksums` disables them.

This matters especially for `pg_upgrade`: source and target checksum settings must match. When upgrading an older non-checksum cluster to PostgreSQL 18, target initialization may therefore require `--no-data-checksums`, unless checksum state is deliberately changed through a supported offline process.

## Authentication initialization

`initdb` can prepopulate `pg_hba.conf` using `--auth`, `--auth-local`, and `--auth-host`. Do not use `trust` in production merely because it is convenient; PostgreSQL documentation warns that `trust` should be used only when all relevant local users are trusted.

## Durability

Do not use `initdb --no-sync` for production. PostgreSQL documents it as useful for testing but unsafe for production initialization because a subsequent OS crash can leave the data directory corrupt.

`--no-sync-data-files` is primarily intended for tools that separately guarantee synchronization and is not a routine production shortcut.

## Locale and encoding

Select locale provider/locale and encoding intentionally because they affect collation, sorting, character behavior, and application compatibility. Capture them as cluster metadata and test application assumptions.

## WAL directory

If WAL is placed outside PGDATA, treat that location as a first-class cluster dependency for startup, backup, recovery, monitoring, standby synchronization, and upgrades.

## Post-init validation

Capture and validate initialization output and later verify:

```sql
SHOW data_directory;
SHOW server_encoding;
SHOW data_checksums;
```

Also inspect `pg_hba.conf`, `postgresql.conf`, filesystem permissions, and service configuration before network exposure.

## Failure scenarios

- `initdb` run as root: stop; use the PostgreSQL service owner.
- Wrong locale/encoding: rebuild before production data is loaded unless a supported migration is explicitly designed.
- Wrong checksum state for `pg_upgrade`: reinitialize target correctly or use the supported offline checksum procedure.
- `trust` authentication left in production: replace with approved authentication before exposure.
- `--no-sync` used for production build: reinitialize safely rather than accepting uncertain durability.
