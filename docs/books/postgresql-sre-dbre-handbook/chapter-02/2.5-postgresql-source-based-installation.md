# 2.5 — PostgreSQL Source-Based Installation

**Status:** Production Ready / Complete

PostgreSQL can be compiled and installed directly from source. For production SRE/DBRE environments, source installation is an exception architecture: use it when a documented engineering requirement cannot be satisfied adequately by approved binary packages.

A source build transfers responsibilities normally handled by package maintainers to the organization, including build-toolchain governance, dependency management, regression testing, artifact provenance, security patching, extension compatibility, deployment, rollback, and reproducibility.

```text
Approved PostgreSQL Release
          ↓
Verified Source
          ↓
Controlled Build Environment
          ↓
Approved Toolchain
          ↓
Compile
          ↓
Regression / Extension Tests
          ↓
Build Manifest
          ↓
Immutable Artifact
          ↓
Checksum + Provenance
          ↓
Artifact Repository
          ↓
Non-Production Validation
          ↓
Production Promotion
          ↓
Runtime Validation
          ↓
Monitoring / Patching
```

## When source installation is appropriate

Legitimate cases include PostgreSQL core or extension development, controlled testing of patches, custom instrumentation, specialized compiler/build requirements, unsupported packaging environments, research/benchmarking, and internally maintained reproducible builds.

Do not choose source installation merely because it appears more configurable. Before approval, document why packages cannot satisfy the requirement, required customizations, security implications, build ownership, patch ownership, extension compatibility, monitoring integration, upgrade strategy, and rollback strategy.

The central ownership question is: **Who owns this PostgreSQL binary for its entire production lifetime?**

## Platform and build-host validation

Validate the target platform, CPU architecture, OS, compiler, required libraries, build tooling, filesystems, and PostgreSQL platform support. Compilation success alone does not prove that the platform is an approved production platform.

A mature architecture separates build and runtime environments:

```text
BUILD ENVIRONMENT
      ↓
Compile / Test / Validate
      ↓
ARTIFACT REPOSITORY
      ↓
Controlled Promotion
      ↓
PRODUCTION DATABASE HOST
```

Production database hosts should consume approved artifacts rather than download source and compile PostgreSQL locally as the normal deployment model.

## Reproducibility and source provenance

Capture PostgreSQL release/source identity, checksum, commit/tag where applicable, compiler and build-system versions, dependencies, build options, compiler flags, installation prefix, CI build ID, build timestamp, regression-test results, extension-test results, and artifact checksum.

Use official PostgreSQL release source for production unless an explicitly approved patch/fork is required. Production policy must exclude beta, release-candidate, development-snapshot, arbitrary branch-tip, and unapproved patched builds.

Protect the full supply chain:

```text
PostgreSQL Project
       ↓
Source Distribution
       ↓
Integrity Verification
       ↓
Build Environment
       ↓
Compiler / Dependencies
       ↓
Build Artifact
       ↓
Production
```

Use controlled build access, trusted toolchains, dependency governance, artifact checksums, CI/CD audit trails, and an artifact repository. Where supported by the organization's software supply-chain platform, add build provenance/attestation or cryptographic artifact signing.

## Build dependencies and feature governance

Build requirements depend on the selected PostgreSQL features. Potential dependencies include OpenSSL, GSSAPI/Kerberos, LDAP, PAM, ICU, LZ4, Zstandard, Tcl, gettext/NLS, and other feature-specific libraries.

Do not install every development library and accept whatever features the build system discovers. Define required capabilities, required build options, approved dependency versions, and a reproducible build specification.

## Make and Meson build workflows

PostgreSQL 18 documents both Make- and Meson-based source-build workflows. Standardize one tested build system/toolchain for production artifacts rather than allowing ad hoc variation.

Traditional Make workflow:

```bash
./configure --prefix=/opt/postgresql/18
make
make install
```

Meson workflow conceptually uses a separate build directory and an explicit prefix, followed by Ninja/Meson build, test, and install operations.

`/opt/postgresql/<major>` is an enterprise layout example used by this handbook, not a PostgreSQL requirement. PostgreSQL's traditional default source installation prefix is `/usr/local/pgsql` unless changed.

## Source, build, installation, and data separation

Maintain clear lifecycle boundaries:

```text
Source Tree
     ≠
Build Tree
     ≠
Installation Tree
     ≠
PGDATA
```

Example:

```text
/build/postgresql/postgresql-18.x/   source/build
/opt/postgresql/18/                  installed software
/data/postgresql/18/data/            PGDATA
```

Software lifecycle and database-data lifecycle are separate.

## Build options and compiler policy

Document every non-default build option. Production build manifests should record security/authentication/compression/internationalization features and whether debugging or assertions are enabled.

Do not copy aggressive compiler flags such as `-O3`, `-march=native`, or `-flto` from generic tuning guides without platform testing. CPU-specific compilation can reduce portability and cause runtime failures on different processor generations.

## Privilege and ownership model

Build and regression-test PostgreSQL under an unprivileged build identity. Controlled privilege escalation may be used for the installation step when writing to a privileged software prefix.

A strong production ownership model is:

```text
Privileged software-management identity
              ↓ owns
PostgreSQL installation tree

postgres runtime identity
              ↓ owns
PGDATA
```

The PostgreSQL runtime account should not require permission to replace its own server executable.

## Regression testing and release gates

Compilation success is not production validation. Require appropriate PostgreSQL regression tests, additional-module tests where used, extension tests, and platform/security validation before artifact promotion.

```text
Compile
   ↓
Core Regression Tests
   ↓
Additional Module Tests
   ↓
Extension Tests
   ↓
Security / Platform Validation
   ↓
Artifact Creation
```

Unexpected test failures must be understood and resolved rather than accepted because most tests passed.

The build specification should also explicitly define whether contrib/additional modules, documentation, development headers, or other source-tree components belong in the artifact; a basic build must not be assumed to mean every source-tree component is installed.

## Build metadata with pg_config

Capture installed-build metadata:

```bash
/opt/postgresql/18/bin/pg_config --version
/opt/postgresql/18/bin/pg_config --configure
/opt/postgresql/18/bin/pg_config --bindir
/opt/postgresql/18/bin/pg_config --libdir
```

This is valuable for extension builds, troubleshooting, and artifact verification.

## Artifact promotion

Use a build-once/promote model:

```text
                  ┌→ DEV
                  │
Source → Artifact ├→ QA
                  │
                  ├→ STAGING
                  │
                  └→ PROD
```

Promote the same tested binary artifact through environments. Environment-specific configuration can differ; the PostgreSQL binary artifact should not be independently rebuilt for each production host.

## Cluster initialization

Installing source-built PostgreSQL software does not create a database cluster.

```text
Software Installed
       ≠
Database Cluster Initialized
```

Initialize only after the intended PGDATA/storage architecture is confirmed, using the dedicated PostgreSQL runtime account. Initialization policy must define PGDATA, locale, encoding, superuser, authentication, checksum state, and WAL architecture.

For PostgreSQL 18, validate the checksum behavior after initialization:

```sql
SHOW data_checksums;
SHOW data_directory;
```

## Service integration

A custom source installation may require the platform team to create and maintain service integration. Do not treat a partial example systemd unit as production-ready.

A production service definition must explicitly address user/group, versioned binary paths, PGDATA, startup and shutdown semantics, recovery-safe startup timeout, restart policy, resource limits, logging, environment, dependencies, and security hardening.

A badly designed timeout/restart policy can repeatedly terminate PostgreSQL while legitimate WAL crash recovery is running. Inspect recovery and PostgreSQL logs before restarting a slow-starting service.

## Runtime and library validation

Validate explicit binaries rather than relying only on `$PATH`:

```bash
/opt/postgresql/18/bin/postgres --version
/opt/postgresql/18/bin/psql --version
```

Then validate the running server:

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
```

Where appropriate on Linux, inspect runtime library resolution:

```bash
ldd /opt/postgresql/18/bin/postgres
```

Confirm that expected dependencies load from approved locations at approved versions. Apply similar validation to compiled extension libraries where relevant.

## Multiple versions and extension compatibility

Versioned prefixes can support side-by-side PostgreSQL releases, for example `/opt/postgresql/17` and `/opt/postgresql/18`. During upgrades and recovery, use explicit paths for `postgres`, `pg_ctl`, `psql`, `pg_dump`, `pg_restore`, `pg_basebackup`, and `pg_upgrade` as appropriate.

Extensions may depend on the PostgreSQL major version, server headers, compiler, ABI/API expectations, external libraries, and build options. Build and test PostgreSQL plus required extensions as a controlled artifact set. Do not assume a shared extension library can simply be copied between major versions.

## Minor releases and security patching

A source-built fleet requires its own release pipeline:

```text
New PostgreSQL Release / Security Advisory
              ↓
Impact Assessment
              ↓
Obtain + Verify Source
              ↓
Rebuild
              ↓
Regression Tests
              ↓
Extension Compatibility
              ↓
Artifact
              ↓
Staging
              ↓
Production Change Window
              ↓
Deploy / Restart
              ↓
Validate
```

The organization effectively becomes its own package maintainer. Security-release monitoring and rebuild ownership must be established before source installation is approved.

## Major-version upgrades

Never replace one major version's binaries with another and point the new server directly at the old major version's PGDATA. Use a supported major-upgrade mechanism such as `pg_upgrade`, logical replication, or dump/restore according to the architecture and later Chapter 2 upgrade guidance.

## Rollback architecture

Retain the previous approved PostgreSQL binaries, build manifest, dependency information, extension artifacts, service definition, configuration, artifact checksum/provenance, and deployment record.

A known-good rollback artifact must already exist before deployment. Rebuilding the previous version during an incident is not a rollback strategy.

## Monitoring, security, and drift

Source installations require monitoring beyond package inventory. Track running server version, binary path/checksum, PGDATA, service unit, shared-library paths, extension versions, build manifest, artifact identity, and deployment version.

Example drift validation:

```bash
sha256sum /opt/postgresql/18/bin/postgres
/opt/postgresql/18/bin/postgres --version
/opt/postgresql/18/bin/pg_config --configure
```

Correlate with the running server:

```sql
SELECT version();
SHOW server_version;
SHOW data_directory;
```

Monitor PostgreSQL security releases and vulnerabilities affecting dependencies such as TLS/authentication/compression libraries and extensions. A source build does not automatically receive a patched PostgreSQL binary when the operating-system package manager updates unrelated packages.

## Production failure scenarios

### FS-2.5-01 — Missing build dependency
Identify the requested capability and approved development dependency, correct the controlled build environment, rerun configuration, and verify the feature is enabled.

### FS-2.5-02 — Required feature omitted
Correct the build specification and dependencies, rebuild, rerun regression/security tests, and promote a new artifact. Do not attempt to solve a compile-time omission solely with runtime configuration.

### FS-2.5-03 — Regression tests fail
Investigate compiler, OS/platform, locale, timezone, dependencies, build options, source modifications, and test environment. Production promotion remains blocked until the failure is understood.

### FS-2.5-04 — Wrong binary resolved from PATH
Use `command -v`, resolved paths, and explicit versioned binary locations during sensitive operations.

### FS-2.5-05 — Shared-library resolution failure
Inspect executable/extension dependencies and dynamic-linker configuration. Correct the controlled dependency model rather than blindly modifying global library paths.

### FS-2.5-06 — Wrong PGDATA
Validate `SHOW data_directory` and correlate it with the service definition before allowing application traffic.

### FS-2.5-07 — Custom source/patch cannot be reproduced
Treat this as a serious reliability/security failure. Preserve source control, patch history, build manifests, CI definitions, artifact repositories, and reproducible dependencies.

### FS-2.5-08 — CPU-specific build fails on production hardware
Deploy an artifact compiled for the approved production CPU baseline and correct compiler-policy/build validation.

### FS-2.5-09 — Security release not rebuilt/deployed
Establish security-release monitoring, ownership, rebuild automation, testing, and controlled deployment. This is an organizational lifecycle failure as well as a technical one.

### FS-2.5-10 — Custom systemd unit interrupts crash recovery
Stop the restart loop, inspect PostgreSQL recovery logs/state, correct timeout/restart semantics, allow recovery to complete, and validate database consistency before restoring traffic.

## Recovery workflow

```text
Failure Detected
      ↓
Identify Layer
      ↓
Source / Build / Dependency / Artifact /
Library / Service / PGDATA / Configuration
      ↓
Protect Database State
      ↓
Stop Uncontrolled Deployment / Restarts
      ↓
Restore Known-Good Artifact if Appropriate
      ↓
Validate Binary / Dependencies
      ↓
Validate PostgreSQL Startup and PGDATA
      ↓
Validate Extensions
      ↓
Validate Application
      ↓
Document RCA
```

Do not perform an ad hoc production rebuild during an incident when a known-good artifact recovery path exists.

## Build automation and IaC

A production pipeline should fetch and verify the approved source, build in a controlled container/VM, install approved dependencies, configure and compile, run regression/extension/security tests, generate a build manifest, create/checksum/attest the artifact, store it centrally, validate it in non-production, and promote that same artifact to production.

Infrastructure/configuration management should define PostgreSQL version, source/artifact identity, checksum, installation prefix, service account, PGDATA, service definition, library configuration, security baseline, and monitoring.

## Production case study — custom extension platform

An unsafe pattern is compiling PostgreSQL and a C extension on developer laptops and copying files to production. This creates compiler drift, dependency drift, poor provenance, inconsistent extension binaries, difficult patching, and weak rollback.

A production model uses source control, controlled CI, approved PostgreSQL release source, extension source, pinned toolchain, regression/extension tests, checksummed/attested artifacts, an artifact repository, staging validation, and controlled production promotion.

The lesson: **source installation becomes safe only when the build system itself is operated as production infrastructure.**

## Production case study — emergency security release

A source-managed fleet must convert a security advisory into a controlled rebuild/test/promotion workflow. Without automation and explicit ownership, source-managed environments can take longer to patch than package-managed fleets. That operational latency must be considered in the architecture decision.

## Key takeaways

Use package-based installation unless source installation solves a documented engineering requirement.

Never make direct compilation on production database hosts the normal deployment model. Separate source, build tree, installation tree, and PGDATA. Treat compilation success as only one build step; regression testing is a release gate.

Treat the compiled PostgreSQL binary as an immutable, versioned production artifact. Build once, test it, and promote that same artifact through staging and production. Maintain explicit security-patching, dependency, extension, rollback, and lifecycle-management processes.

```text
Source-based PostgreSQL
          =
Database Engineering
          +
Software Build Engineering
          +
Supply-Chain Security
          +
Release Engineering
          +
SRE/DBRE Operations
```
