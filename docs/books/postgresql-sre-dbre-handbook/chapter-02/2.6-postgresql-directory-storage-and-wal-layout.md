# 2.6 — PostgreSQL Directory, Storage, and WAL Layout

**Status:** Production Ready / Complete

Production PostgreSQL storage design must account for PGDATA, WAL, tablespaces, filesystem behavior, capacity, durability, backup coverage, and recovery requirements.

## Core physical layout

```text
PostgreSQL Cluster
├── PGDATA
│   ├── base
│   ├── global
│   ├── pg_xact
│   ├── pg_tblspc
│   └── pg_wal (or link/relocated location)
└── User tablespaces → external directories
```

Do not manually edit PostgreSQL-managed files inside a live cluster.

## PGDATA

Protect PGDATA with correct ownership, restrictive permissions, adequate capacity/inodes, supported filesystem semantics, backup coverage, and monitoring. Avoid colocating unrelated application files in PGDATA.

## WAL

WAL is fundamental to crash recovery, replication, archiving, and PITR. If WAL is placed on separate storage, monitor and protect that filesystem with the same seriousness as PGDATA. A missing or full WAL filesystem can stop database progress.

## Tablespaces

Tablespaces point PostgreSQL objects to additional filesystem locations. Every tablespace becomes part of the physical cluster footprint and must be included in backup, recovery, upgrade, monitoring, and standby procedures.

## Capacity planning

Track utilization, inode usage, growth, WAL generation, archive backlog, temporary files, maintenance headroom, and upgrade headroom. Avoid operating production filesystems near exhaustion.

## Performance

Measure storage latency, IOPS, throughput, queueing, fsync behavior, and workload-specific response rather than assuming a storage class is sufficient from nominal specifications.

## Mount safety

Ensure expected mounts are present before PostgreSQL starts. Service dependencies or readiness checks should prevent PostgreSQL from writing into an unintended underlying directory when a mount is absent.

## Backup and recovery

The physical storage map must be documented so backups and restore procedures include PGDATA, external tablespaces, and relocated WAL where applicable. Snapshot strategies spanning multiple filesystems require consistency controls.

## Monitoring and alerting

Alert on capacity, inode pressure, abnormal latency, filesystem errors, read-only/degraded mounts, WAL/archive growth, and missing mounts. Correlate host storage telemetry with PostgreSQL I/O and WAL statistics.

## Failure scenarios

- WAL filesystem full: protect service, restore capacity, inspect archiving/replication causes.
- Tablespace mount missing: stop unsafe startup/use and restore correct mount.
- PGDATA capacity exhaustion: do not delete PostgreSQL files manually; identify safe remediation.
- Storage latency spike: correlate workload, checkpoints/WAL, host queueing, and backend I/O.

## Production checklist

- [ ] PGDATA mapped
- [ ] WAL location mapped
- [ ] Tablespaces inventoried
- [ ] Filesystem/mount sources documented
- [ ] Capacity/inode headroom approved
- [ ] Storage performance baseline captured
- [ ] Backup coverage validated
- [ ] Monitoring/alerts active
- [ ] Upgrade storage headroom modeled
