# 2.9 — Service Startup, Shutdown, and Process Management

**Status:** Production Ready / Complete

Production PostgreSQL startup and shutdown must be controlled, observable, and integrated with the operating system or orchestration platform. Abrupt process handling can extend crash recovery or create avoidable incidents.

## Service management

Use the platform's supported service manager or an approved orchestration mechanism. Verify service identity, PGDATA/config paths, environment, resource limits, mount dependencies, startup ordering, restart behavior, and log routing.

## pg_ctl

`pg_ctl` can initialize, start, stop, restart, reload, promote, and report server status. Use explicit data/config paths and preserve command output in maintenance workflows.

## Shutdown modes

PostgreSQL supports controlled shutdown behaviors with different connection/transaction implications. Select the appropriate mode for the operational objective and understand the impact before using it. Avoid using operating-system kill escalation as the normal shutdown mechanism.

## Maintenance shutdown

Before planned maintenance:

```text
Announce/change gate → Stop/drain application writes → Drain connections
→ Verify replication/backup state → Controlled PostgreSQL shutdown
→ Verify process stopped → Perform maintenance
```

For major upgrades, follow the exact `pg_upgrade` shutdown and synchronization requirements.

## Startup validation

After startup verify process/service health, PostgreSQL logs, connectivity, recovery state, databases, extensions, storage mounts, WAL/archive status, replication, monitoring, backups, and application smoke tests before declaring service healthy.

## Reload versus restart

Not every configuration change requires restart. Use PostgreSQL's setting metadata/documentation to determine whether a parameter can be reloaded or requires restart. Do not restart production unnecessarily.

## Crash recovery

If PostgreSQL terminates unexpectedly, preserve logs and evidence. Allow normal crash recovery unless documented recovery procedures require intervention. Never delete WAL or control files to force startup.

## Process safety

Do not manually kill individual PostgreSQL background/server processes as a routine operational action. PostgreSQL manages a coordinated process architecture; unexpected child-process failures can cause broader restart/recovery behavior.

## Monitoring and alerting

Monitor service availability, restart count, startup duration, crash recovery, connection failures, background process failures, storage/mount state, replication, and application readiness.

## Failure scenarios

- Service will not start: inspect logs, configuration, permissions, ports, mounts, WAL/storage, and recovery state.
- Shutdown hangs: identify sessions/transactions and use the approved escalation path rather than immediately forcing OS termination.
- Repeated restart loop: disable unsafe automatic cycling, preserve evidence, diagnose root cause.
- Startup on missing mount: stop immediately and restore correct storage before allowing writes.

## Production checklist

- [ ] Service definition reviewed
- [ ] PostgreSQL runs as approved OS owner
- [ ] Mount dependencies enforced
- [ ] Startup/shutdown commands documented
- [ ] Reload vs restart understood
- [ ] Maintenance drain procedure documented
- [ ] Startup validation scripted
- [ ] Crash evidence retained
- [ ] Service/restart monitoring enabled
