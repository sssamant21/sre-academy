## 3.1.1 Purpose

PostgreSQL database administration is the operational discipline of managing databases and the objects contained within them while maintaining:

- availability
- security
- performance
- recoverability
- data integrity
- operational consistency

For an SRE, DBRE, or production DBA, database administration extends well beyond executing commands such as:

```sql
CREATE DATABASE;
```

or:

```sql
CREATE TABLE example_table (
    id bigint PRIMARY KEY
);
```

Production administration requires understanding how PostgreSQL databases relate to the PostgreSQL cluster, how schemas provide namespaces, how ownership and privileges are enforced, how objects depend on one another, how administrative operations interact with active workloads, and how changes can be performed safely.

This chapter establishes the operational foundation for managing:

- databases
- schemas
- tables
- indexes
- sequences
- views
- materialized views
- functions
- procedures
- extensions
- tablespaces
- privileges
- ownership
- dependencies
- object maintenance

The central principle is:

> Database administration is change management applied to a live data system.

## 3.1.2 PostgreSQL Administrative Hierarchy

A PostgreSQL deployment can be viewed logically as:

```text
PostgreSQL Database Cluster
|
|-- Cluster-Level Objects
|   |-- Roles
|   |-- Databases
|   `-- Tablespaces
|
|-- Database
|   |
|   |-- Schema
|   |   |-- Tables
|   |   |-- Indexes
|   |   |-- Views
|   |   |-- Materialized Views
|   |   |-- Sequences
|   |   |-- Functions
|   |   |-- Procedures
|   |   |-- Types
|   |   `-- Other schema objects
|   |
|   `-- Additional Schemas
|
`-- Additional Databases
```

A PostgreSQL database cluster contains one or more databases managed by a PostgreSQL server installation.

A client session connects to one database.

Within a database, schemas provide namespaces for organizing objects.

Example:

```text
PostgreSQL Cluster
|
`-- production
    |
    |-- public
    |   |-- customers
    |   `-- products
    |
    |-- billing
    |   |-- invoices
    |   `-- payments
    |
    `-- reporting
        |-- monthly_sales
        `-- customer_summary
```

A schema-qualified reference therefore looks like:

```sql
SELECT *
FROM billing.invoices;
```

Explicit schema qualification is particularly valuable in:

- administrative scripts
- migrations
- deployment automation
- security-sensitive operations
- troubleshooting
- production runbooks

## 3.1.3 Database Boundaries

A PostgreSQL connection operates against a single database.

Objects in another database cannot normally be referenced directly through ordinary PostgreSQL SQL syntax.

This differs from schemas.

Within the connected database, a session can access objects in multiple schemas when the role has the required privileges.

Therefore:

```text
Cluster
  |
  |-- Database A
  |     |-- Schema A
  |     `-- Schema B
  |
  `-- Database B
```

A session connected to Database A can access Schema A and Schema B but does not automatically gain SQL access to objects in Database B.

This distinction is important when designing:

- application boundaries
- multi-tenant environments
- migrations
- logical backups
- access controls
- disaster recovery
- database consolidation

## 3.1.4 Cluster-Level Versus Database-Local Objects

Not every PostgreSQL object belongs to a particular database.

Administrators must distinguish between cluster-wide and database-local state.

Cluster-level objects include:

- roles
- databases
- tablespaces

Database-local objects include:

- schemas
- tables
- indexes
- views
- materialized views
- sequences
- functions
- procedures
- types
- extensions and their member objects

This distinction matters during:

- migrations
- backup and restore
- disaster recovery
- privilege management
- database cloning
- automation
- database retirement

A backup of a single database should not automatically be assumed to contain every cluster-level object or configuration required to reconstruct an entire PostgreSQL environment.

Recovery procedures must therefore account for both database-local state and required cluster-level state.

## 3.1.5 Connecting to the Correct Database

A PostgreSQL session connects to a specific database.

Example:

```bash
psql \
  -h db.example.com \
  -p 5432 \
  -U app_admin \
  -d production
```

Verify the current database:

```sql
SELECT current_database();
```

Verify session identity:

```sql
SELECT
    current_user,
    session_user;
```

For production administration, use a preflight query such as:

```sql
SELECT
    current_database(),
    current_user,
    session_user,
    inet_server_addr(),
    inet_server_port();
```

This should become habitual before performing high-impact operations.

The target should always be understood as:

```text
Environment
   |
   v
Cluster / Instance
   |
   v
Database
   |
   v
Schema
   |
   v
Object
```

## 3.1.7 Database Size and Capacity

Current database:

```sql
SELECT
    pg_size_pretty(
        pg_database_size(current_database())

```

All databases:

```sql
SELECT
    datname,
    pg_size_pretty(pg_database_size(datname)) AS database_size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;
```

Database capacity should be monitored as a trend rather than examined only during storage incidents.

Track:

```text

      |

      |-- Weekly Growth
      |-- Monthly Growth
      |
      |-- Table Growth
      |-- Index Growth
      |-- WAL Growth
      `-- Available Storage
```

Capacity planning must also consider temporary storage requirements associated with:

- index creation
- reindexing
- maintenance
- query spills
- WAL generation
- backup/restore
- replication
- schema migrations
- platform-specific storage behavior

## 3.1.8 Schema Discovery and `search_path`

List schemas:

```text
\dn
```

Using SQL:

```sql
SELECT
    schema_name,
    schema_owner
FROM information_schema.schemata
ORDER BY schema_name;
```

Inspect the active search path:

```sql
SHOW search_path;
```

The search path controls resolution of unqualified object names.

For example:

```sql
SELECT *
FROM orders;
```

requires PostgreSQL to resolve which `orders` object is intended.

Explicit qualification:

```sql
SELECT *
FROM sales.orders;
```

removes that ambiguity.

For production automation and administrative operations, explicit schema qualification should generally be preferred where practical.

### Security Consideration

`search_path` is also a security concern.

Allowing untrusted users to create objects in schemas present in another user's search path can introduce object-resolution risks.

Production schema design should therefore consider both namespace convenience and security boundaries.

Useful `psql` commands include:

```text

\di
\dv
\dm
\ds
\df
```

SQL-based discovery is preferable for automation.

Tables:

```sql
SELECT
    schemaname,
    tablename,
    tableowner

```

Indexes:

```sql
SELECT
    schemaname,

```

Administrative automation should generally use documented system catalogs, Information Schema, and statistics views rather than parsing human-oriented `psql` output.

## 3.1.10 Ownership Is Fundamental

PostgreSQL objects have owners.

Ownership carries administrative authority that is different from ordinary access privileges.

The owner normally has inherent authority to alter or drop the object and can grant appropriate privileges to other roles.

Production ownership should therefore be deliberately designed.

A useful model is:

```text
Human / Application Login
           |
           v
Application or Operator Role
           |
           v
Granted Privileges
           |
           v
NOLOGIN Owner Role
           |
           v
Schema / Database Objects
```

Example:

```sql
CREATE ROLE billing_owner NOLOGIN;
CREATE ROLE billing_app LOGIN;
```

Objects can then be owned by:

```text
billing_owner
```

while the application receives only the privileges it requires.

This separates object ownership from runtime application access and reduces the need for application accounts to own production objects.

## 3.1.11 Ownership and Privileges Are Different

Consider:

```sql
GRANT
    SELECT,
    INSERT,
    UPDATE,
    DELETE
ON TABLE billing.invoices
TO billing_app;
```

This grants specific privileges.

It does not make `billing_app` the owner.

Likewise:

```sql
GRANT USAGE
ON SCHEMA billing
TO billing_app;
```

permits schema lookup/access according to PostgreSQL's privilege model.

It does not automatically grant privileges on every object contained in the schema.

Production authorization therefore needs to consider:

```text
Database Privileges
        |
        v
Schema Privileges
        |
        v
Table/Object Privileges
        |
        v
Sequence Privileges
        |
        v
Function/Procedure Privileges
        |
        v
Default Privileges for Future Objects
```

Ownership and privileges will be covered in depth later in Chapter 3.

## 3.1.12 `pg_database_owner`

Modern PostgreSQL also provides the predefined role:

```text
pg_database_owner
```

Its implicit member is the owner of the current database.

The role can own objects and receive privileges, allowing template-based privileges or ownership to follow the owner of a database created from that template.

In current PostgreSQL releases, the `public` schema is initially owned by `pg_database_owner`.

This behavior is important when designing:

- database ownership
- template databases
- schema ownership
- delegated administration

It will be examined in greater depth in later sections.

## 3.1.13 Object Dependencies

PostgreSQL tracks dependencies among database objects.

For example:

```text
Table
 |-- Indexes
 |-- Constraints
 |-- Sequences
 |-- Views
 |-- Materialized Views
 `-- Other dependent objects
```

Attempting:

```sql
DROP TABLE customers;
```

may fail when other objects depend on the table.

Using:

```sql
DROP TABLE customers CASCADE;
```

can remove dependent objects recursively.

Therefore:

> Never use `CASCADE` merely to make a dependency error disappear.

Before using `CASCADE`:

- inspect the dependency error
- identify dependent objects
- understand the dependency chain
- determine application impact
- verify recovery options
- obtain appropriate approval
- execute only after understanding the blast radius

A useful technique is to first issue the `DROP` without `CASCADE` and inspect PostgreSQL's dependency details.

## 3.1.14 DDL Is a Production Change

Commands such as:

```sql
ALTER TABLE ...
CREATE INDEX ...
DROP TABLE ...
ALTER TABLE ... ADD COLUMN ...
```

are not merely SQL syntax.

They are production operational events.

Depending on the command, subcommand, PostgreSQL version, object size, and workload, DDL may:

- acquire heavyweight locks
- wait behind existing transactions
- block concurrent work
- create lock queues
- increase I/O
- increase CPU utilization
- generate WAL
- require additional storage
- affect replicas
- increase recovery workload
- invalidate cached metadata/plans
- affect application latency

Therefore:

> Every production DDL operation should be evaluated for locking, duration, resource consumption, replication impact, rollback/recovery strategy, and application impact before execution.

## 3.1.15 DDL Lock Requirements Are Command-Specific

Do not assume:

```text
DDL = ACCESS EXCLUSIVE
```

for every operation.

Lock requirements depend on the exact command, subcommand, and PostgreSQL version.

Some administrative operations require strong locks, while others use weaker lock modes.

The production rule is:

> Determine the lock mode required by the exact PostgreSQL command or subcommand before executing it against a production object.

This should be validated against the documentation for the PostgreSQL version being operated.

## 3.1.16 Transactional DDL

Many PostgreSQL schema-level DDL operations can participate in transactions.

Example:

```sql
BEGIN;

CREATE TABLE test_admin (
    id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now()
);

ROLLBACK;
```

The table creation is rolled back.

This is valuable for controlled database changes.

However:

> Do not generalize transactional behavior to every PostgreSQL administrative command.

Important exceptions exist.

For example:

```sql
CREATE DATABASE example_database;
```

and:

```sql
DROP DATABASE example_database;
```

cannot execute inside a transaction block.

Always verify the behavior of the exact command against the documentation for the PostgreSQL version being operated.

## 3.1.17 Inspecting Active Workload

Before significant production changes:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY query_start;
```

This helps identify:

- active transactions
- long-running statements
- idle sessions
- idle-in-transaction sessions
- waiting sessions
- potentially conflicting workloads

## 3.1.18 Lock Inspection

Inspect current locks:

```sql
SELECT
    pid,
    locktype,
    relation::regclass,
    mode,
    granted
FROM pg_locks
WHERE database = (
    SELECT oid
    FROM pg_database
    WHERE datname = current_database()
)
ORDER BY granted, pid;
```

`pg_locks` is valuable for understanding the lock state of the system.

However, manually reconstructing blocker relationships from `pg_locks` can be difficult.

For live production troubleshooting, PostgreSQL provides:

```sql
pg_blocking_pids()
```

which should normally be preferred when identifying sessions blocking a particular backend.

## 3.1.19 Production Blocker Detection

A useful production query is:

```sql
SELECT
    a.pid AS blocked_pid,
    a.usename,
    a.application_name,
    a.state,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    now() - a.query_start AS wait_duration,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;
```

This provides:

- blocked PID
- blocking PID or PIDs
- application
- wait type
- wait event
- wait duration
- SQL

During an incident, this can quickly establish:

```text
Who is blocked?
        |
        v
Who is blocking them?
        |
        v
How long?
        |
        v
Which application?
        |
        v
Which SQL?
```

## 3.1.20 Long-Running Transactions

Inspect transaction age:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Long-running transactions can contribute to:

- DDL lock waits
- delayed vacuum cleanup
- old snapshot retention
- dead tuple accumulation
- table/index bloat
- operational maintenance delays
- transaction ID management pressure

Before major object administration, DBREs should understand the active transaction landscape.

## 3.1.21 Idle-in-Transaction Sessions

An especially important state is:

```text
idle in transaction
```

Inspect:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    xact_start,
    state_change,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;
```

A typical failure pattern is:

```text
Application
    |
    v
BEGIN
    |
    v
Execute SQL
    |
    v
Fails to COMMIT / ROLLBACK
    |
    v
Session becomes idle in transaction
    |
    v
Old transaction remains open
```

Potential consequences include:

```text
Locks retained
      +
Old snapshot retained
      |
      v
VACUUM cleanup constrained
      |
      v
Dead tuples accumulate
      |
      v
Table/index growth
      |
      v
Potential production impact
```

Production environments should monitor idle-in-transaction duration.

Where appropriate, evaluate:

```sql
idle_in_transaction_session_timeout
```

according to application behavior and operational requirements.

## 3.1.22 Defensive Administrative Session Settings

Production administrative sessions should avoid waiting indefinitely.

For an appropriate DDL operation:

```sql
SET lock_timeout = '5s';
```

This limits how long the statement waits to acquire each required lock.

A statement timeout can also provide an execution boundary:

```sql
SET statement_timeout = '30min';
```

PostgreSQL 18 additionally provides:

```sql
SET transaction_timeout = '30min';
```

where appropriate for the operational workflow.

These settings serve different purposes:

```text
lock_timeout
    |
    v
Maximum wait for lock acquisition

statement_timeout
    |
    v
Maximum statement duration

transaction_timeout
    |
    v
Maximum transaction duration
```

Values must be chosen according to the operation.

Do not blindly apply example values.

For administrative work, session-scoped settings are generally safer than indiscriminately configuring global timeout values that affect all sessions.

A useful principle is:

> Fail safely rather than wait indefinitely while creating a production lock queue.

## 3.1.23 Production DDL Failure Pattern

Consider:

```sql
ALTER TABLE orders
ADD COLUMN source_system text;
```

Suppose another transaction holds a conflicting lock.

The sequence can become:

```text
Application Transaction
        |
        v
Holds Conflicting Lock
        |
        v
DDL Requests Lock
        |
        v
DDL Waits
        |
        v
Additional Sessions Queue
        |
        v
Application Latency Rises
        |
        v
Potential Incident
```

The operational danger is therefore not limited to the DDL statement itself.

A waiting DDL session can participate in a broader lock queue.

Mitigation:

```text
Preflight lock analysis
        +
lock_timeout
        +
Low-risk change window
        +
Active monitoring
        +
Cancellation procedure
        +
Recovery plan
```

## 3.1.24 Database Statistics

`pg_stat_database` provides database-level workload statistics.

Example:

```sql
SELECT
    datname,
    numbackends,
    xact_commit,
    xact_rollback,
    blks_read,
    blks_hit,
    tup_returned,
    tup_fetched,
    tup_inserted,
    tup_updated,
    tup_deleted,
    deadlocks
FROM pg_stat_database
WHERE datname IS NOT NULL
ORDER BY datname;
```

Important signals include:

| Signal | Operational Use |
| --- | --- |
| `numbackends` | Current database connections |
| `xact_commit` | Committed transaction counter |
| `xact_rollback` | Rolled-back transaction counter |
| `blks_read` | Disk block reads |
| `blks_hit` | Buffer-cache hits |
| Tuple counters | Workload activity |
| `deadlocks` | Deadlock occurrence |

Most statistics in `pg_stat_database` are cumulative counters rather than instantaneous rates.

Monitoring systems should therefore calculate delta or rate over time where appropriate.

SRE dashboards must also account for statistics resets.

## 3.1.25 Object Storage Monitoring

Identify large relations:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS object_name,
    pg_size_pretty(
        pg_total_relation_size(c.oid)
    ) AS total_size
FROM pg_class AS c
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm', 'p')
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;
```

This can identify large:

- ordinary tables
- materialized views
- partitioned tables

For storage planning, understand:

```text
Table Data
    +
TOAST Data
    +
Indexes
    =
Total Relation Footprint
```

Object size affects:

- DDL planning
- index operations
- backup
- restore
- replication
- migration
- maintenance
- storage capacity
- recovery duration

## 3.1.29 Failure Scenario — DDL Blocked by an Application

### Change

```sql
ALTER TABLE orders
ADD COLUMN source_system text;
```

### Symptom

The command does not complete.

### Step 1 — Check Activity

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY query_start;
```

### Step 2 — Identify Blockers

```sql
SELECT
    a.pid AS blocked_pid,
    a.application_name,
    pg_blocking_pids(a.pid) AS blocking_pids,
    now() - a.query_start AS wait_duration,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;
```

### Step 3 — Determine Impact

Do not immediately terminate the blocking backend.

First determine:

- who owns it
- what application is using it
- whether it is processing a critical transaction
- whether the DDL can safely be cancelled instead
- what the impact of terminating the blocker would be

### Step 4 — Recover Safely

Depending on the situation:

- cancel DDL
- allow blocker to finish
- coordinate application transaction termination

Never terminate production database sessions blindly.

## 3.1.31 Failure Scenario — Destructive `CASCADE`

An administrator runs:

```sql
DROP TABLE customer CASCADE;
```

The command succeeds.

However, dependent objects may also be removed.

Correct production procedure:

```text
DROP without CASCADE
        |
        v
Read dependency error
        |
        v
Inventory dependencies
        |
        v
Determine blast radius
        |
        v
Validate recovery
        |
        v
Obtain approval
        |
        v
Execute controlled change
```

The production principle is:

> Dependency errors provide information. Do not automatically bypass them.

```sql
WHERE datname = current_database()
ORDER BY query_start;
```

### Step 4 — Inspect Long Transactions

```sql
SELECT
    pid,
    usename,
    application_name,
    now() - xact_start AS transaction_age,
    state,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

### Step 5 — Check Blockers

```sql
SELECT
    a.pid AS blocked_pid,
    a.application_name,
    pg_blocking_pids(a.pid) AS blocking_pids,
    now() - a.query_start AS wait_duration,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;
```

### Step 6 — Check Object Size

```sql
SELECT
    pg_size_pretty(
        pg_total_relation_size('schema.table')
    );
```

### Step 7 — Review Dependencies

Determine which indexes, constraints, views, materialized views, sequences, functions, triggers, and other objects depend on the target.

### Step 8 — Determine Lock Requirements

Verify the lock behavior of the exact PostgreSQL command/subcommand.

### Step 9 — Validate Recovery

Before destructive or high-risk operations, answer:

> If this change fails or causes application impact, exactly how will we recover?

### Step 10 — Configure Defensive Session Behavior

Where appropriate:

```sql
SET lock_timeout = '5s';
SET statement_timeout = '30min';
```

And, where appropriate on PostgreSQL 18:

```sql
SET transaction_timeout = '30min';
```

Use environment-specific values.

### Step 11 — Execute

Perform the approved change.

Observe:

- database health
- application health
- locks

- errors
- replication
- CPU
- I/O
- storage
- object state

### Step 13 — Validate

Confirm:

- expected schema/object state
- privileges
- application functionality
- replication health
- no unexpected lock queues
- no unexpected errors

### Step 14 — Record

Capture:

- change ID
- timestamp
- environment
- database

- operator / automation identity
- SQL / migration version
- execution duration

## 3.1.34 Production Case Study — Large Table DDL

### Scenario

A production team needs to add a column to a heavily accessed `orders` table.

The table is approximately 2 TB and receives continuous application traffic.

The proposed SQL is:

```sql
ALTER TABLE orders
ADD COLUMN source_system text;
```

The statement looks simple.

The DBRE does not immediately execute it.

Instead:

```text
Verify Environment
        |
        v
Verify Database
        |
        v
Verify Schema/Table
        |
        v
Confirm PostgreSQL Version
        |
        v
Determine Exact ALTER Behavior
        |
        v
Determine Required Lock
        |
        v
Inspect Object Size
        |
        v
Inspect Active Transactions
        |
        v
Inspect Blockers
        |
        v
Check Replication
        |
        v
Check Storage
        |
        v
Validate Recovery Plan
        |
        v
Configure Defensive Timeouts
        |
        v
Execute During Approved Window
        |
        v
Monitor Database + Application
        |
        v
Validate
```

A short `lock_timeout` prevents the administrative session from waiting indefinitely behind a conflicting transaction.

If the lock cannot be obtained safely, the change fails quickly rather than creating an extended production lock queue.

### Lesson

The SQL statement was simple.

The production operation was not.

This distinction is fundamental to PostgreSQL SRE/DBRE practice.

## 3.1.35 SRE/DBRE Production Principles

### Principle 1 — Know the Target

Always validate:

```text
Environment -> Cluster -> Database -> Schema -> Object
```

### Principle 2 — Separate Ownership from Runtime Access

Application login roles should not automatically become permanent owners of production objects.

### Principle 3 — Understand Dependencies

Never assume an object exists independently.

### Principle 4 — Understand Exact Lock Behavior

DDL should be treated as a concurrency event.

### Principle 5 — Understand Object Size

A change that completes instantly on a 10 MB table may behave very differently on a multi-terabyte relation.

### Principle 6 — Understand Active Transactions

Long-running and idle-in-transaction sessions can materially change the risk of administrative operations.

### Principle 7 — Define Recovery Before Execution

Before making the change, answer:

> If this fails halfway through or causes production impact, what exactly will we do?

### Principle 8 — Monitor During the Change

Observe:

- locks
- transactions
- replication
- storage
- database health
- application health

### Principle 9 — Prefer Repeatable Administration

Move repeated administrative procedures toward version-controlled automation.

### Principle 10 — Treat Production DDL as a Reliability Event

DDL must receive the same operational discipline applied to other production infrastructure changes.
