# 3.10 — PostgreSQL Sequence and Identity Column Administration

**Chapter:** 3 — PostgreSQL Database and Object Administration

**Status:** Draft COMPLETE → Technical Review COMPLETE → Production Review COMPLETE → Canonical Edition

**Audience:** PostgreSQL DBA / DBRE / SRE / Platform Engineering

**Scope:** PostgreSQL sequences, `SERIAL`, identity columns, privileges, capacity, migration, replication, HA/DR, monitoring, troubleshooting, and recovery.

This canonical edition establishes the production standard for sequence and identity-column administration in PostgreSQL.

## 3.10.1 Operational Purpose

PostgreSQL sequences are specialized database objects that generate numeric values efficiently under concurrent workloads. They commonly support surrogate primary keys, order identifiers, transaction/event identifiers, batch identifiers, identity columns, and legacy `SERIAL` / `BIGSERIAL` columns.

A sequence is an independent object with its own state, data type, start value, increment, minimum and maximum values, cache, cycle behavior, owner, privileges, and dependencies. For DBRE/SRE operations, sequence state is part of application data-integrity and availability architecture.

## 3.10.2 Creating Sequences

Basic creation:

```sql
CREATE SEQUENCE app.order_id_seq;
```

Explicit production definition:

```sql
CREATE SEQUENCE app.order_id_seq
    AS bigint
    START WITH 1
    INCREMENT BY 1
    MINVALUE 1
    NO MAXVALUE
    CACHE 1
    NO CYCLE;
```

Use `bigint` for most production identifier sequences unless a smaller range is explicitly justified.

## 3.10.3 Sequence Architecture

A sequence stores state separately from table rows. Calls to `nextval()` advance the sequence object, not the table. The table default, identity column, or application code consumes sequence values and inserts them into rows.

This separation is the source of many operational behaviors: gaps, non-transactional advancement, cache loss after crash, replication considerations, and sequence/table drift.

## 3.10.4 nextval()

`nextval()` atomically advances a sequence and returns the next value.

```sql
SELECT nextval('app.order_id_seq');
```

It is safe under concurrency because PostgreSQL coordinates sequence advancement independently of application transaction overlap.

## 3.10.5 Sequence Values Are Not Transactional Row State

Sequence advancement is not rolled back when a transaction aborts. If a transaction calls `nextval()` and later rolls back, the consumed value remains consumed.

This is normal PostgreSQL behavior and must be accepted in production designs.

## 3.10.6 Sequence Gaps Are Normal

Gaps can be caused by rollbacks, failed inserts, `ON CONFLICT`, cached values, application retries, crashes, failovers, migrations, and manual `setval()` operations. Gap-free requirements should not use ordinary PostgreSQL sequences.

## 3.10.7 Sequences Are Not Gapless Business Counters

Do not use sequences for legally gapless invoice numbers, audit numbers, or regulatory counters unless the business explicitly accepts gaps. Gapless counters require a different serialized design with different performance and availability tradeoffs.

## 3.10.8 currval()

`currval()` returns the most recent value obtained by `nextval()` in the current session.

```sql
SELECT currval('app.order_id_seq');
```

It fails if the session has not called `nextval()` for that sequence.

## 3.10.9 lastval()

`lastval()` returns the last sequence value obtained by the current session, regardless of which sequence produced it. Avoid it in production application code when multiple sequences may be used; prefer explicit sequence names or `INSERT ... RETURNING`.

## 3.10.10 Prefer INSERT ... RETURNING

Applications should usually retrieve generated identifiers with `INSERT ... RETURNING`.

```sql
INSERT INTO app.orders (customer_id, total_amount)
VALUES (42, 100.00)
RETURNING order_id;
```

This is safer than guessing sequence state after the insert.

## 3.10.11 setval()

`setval()` changes sequence state manually.

```sql
SELECT setval('app.order_id_seq', 1000000);
```

Use it for controlled realignment, migrations, recovery, and cutovers. Treat it as production DDL-like state change requiring review.

## 3.10.12 setval() Third Argument

The third argument controls whether the supplied value has already been used.

```sql
SELECT setval('app.order_id_seq', 100, true);  -- next nextval returns 101
SELECT setval('app.order_id_seq', 100, false); -- next nextval returns 100
```

Incorrect use can create duplicate-key incidents.

## 3.10.13 setval() Is Not Rolled Back

Like `nextval()`, `setval()` is not rolled back by transaction abort. Test remediation SQL carefully and avoid wrapping sequence correction logic in a false sense of transactional safety.

## 3.10.14 ALTER SEQUENCE ... RESTART vs setval()

`ALTER SEQUENCE ... RESTART` changes restart behavior and can have different locking/semantic implications than `setval()`. Use explicit runbooks for sequence resets and confirm expected next values before releasing traffic.

## 3.10.15 Traditional Sequence-Backed Defaults

A table column can use a sequence-backed default:

```sql
CREATE SEQUENCE app.orders_order_id_seq;

CREATE TABLE app.orders (
    order_id bigint DEFAULT nextval('app.orders_order_id_seq') PRIMARY KEY,
    customer_id bigint NOT NULL
);
```

This is the manual form behind many legacy `SERIAL` patterns.

## 3.10.16 SERIAL and BIGSERIAL

`SERIAL` and `BIGSERIAL` are shorthand that create an integer column, a sequence, a default expression, and ownership dependency. They remain common in older schemas, but modern designs should usually prefer SQL-standard identity columns.

## 3.10.17 Identity Columns

Identity columns are the modern declarative syntax:

```sql
CREATE TABLE app.orders (
    order_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL
);
```

Identity columns make generated-value intent clearer than legacy `SERIAL` shorthand.

## 3.10.18 GENERATED ALWAYS vs BY DEFAULT

`GENERATED ALWAYS` prevents ordinary user-supplied values unless explicitly overridden. `GENERATED BY DEFAULT` allows user-supplied values when needed.

Choose `ALWAYS` for strong generated-key enforcement and `BY DEFAULT` for migration or integration flexibility.

## 3.10.19 Identity Does Not Guarantee Uniqueness

Identity generation does not itself guarantee uniqueness. Use a primary key or unique constraint when uniqueness is required.

## 3.10.20 Identity Columns vs Generated Columns

Identity columns generate sequence-backed numeric values. Generated columns compute values from expressions. They solve different problems and should not be treated as interchangeable.

## 3.10.21 Inspecting Identity Columns

Inspect identity metadata through information schema and catalogs.

```sql
SELECT table_schema, table_name, column_name, is_identity, identity_generation
FROM information_schema.columns
WHERE table_schema = 'app'
  AND is_identity = 'YES';
```

## 3.10.22 Inspecting Sequences

Inventory sequence objects regularly.

```sql
SELECT schemaname, sequencename, data_type, start_value, min_value,
       max_value, increment_by, cycle, cache_size, last_value
FROM pg_sequences
WHERE schemaname = 'app';
```

## 3.10.23 Do Not Misinterpret last_value

`last_value` is sequence state, not necessarily the last committed table row. It may reflect cached or advanced values. Do not use it alone to infer application data correctness.

## 3.10.24 Discovering the Associated Sequence

Use `pg_get_serial_sequence()` to discover the sequence associated with a table column.

```sql
SELECT pg_get_serial_sequence('app.orders', 'order_id');
```

This works for serial-style and identity-backed columns where PostgreSQL can identify the association.

## 3.10.25 Sequence Object Ownership

A sequence has an owning database role. Ownership controls who can alter or drop it. Object owner is separate from business ownership and from `OWNED BY` dependency.

## 3.10.26 OWNED BY

`OWNED BY` links a sequence lifecycle to a table column.

```sql
ALTER SEQUENCE app.orders_order_id_seq
OWNED BY app.orders.order_id;
```

This dependency helps PostgreSQL drop the sequence when the owning column is dropped.

## 3.10.27 Object Owner vs OWNED BY

The owner role controls privileges on the sequence object. `OWNED BY` defines dependency on a table column. Production reviews must inspect both.

## 3.10.28 Sequence Privileges

Applications usually need `USAGE` on sequences to call `nextval()`.

```sql
GRANT USAGE ON SEQUENCE app.orders_order_id_seq TO app_writer;
```

Avoid broad grants. Apply least privilege and default privileges for future sequences.

## 3.10.29 Existing vs Future Sequence Grants

Grants on existing sequences do not automatically apply to future sequences. Use both current grants and default privileges.

```sql
GRANT USAGE ON ALL SEQUENCES IN SCHEMA app TO app_writer;
ALTER DEFAULT PRIVILEGES IN SCHEMA app
GRANT USAGE ON SEQUENCES TO app_writer;
```

## 3.10.30 Sequence Caching

Sequence cache improves performance by reducing sequence state writes.

```sql
ALTER SEQUENCE app.order_id_seq CACHE 100;
```

Higher cache values can increase gaps after crash or failover. Choose cache based on throughput, gap tolerance, and operational requirements.

## 3.10.31 Cached Values and Ordering

Cached sequence values do not guarantee commit order. Multiple sessions can reserve values and commit in a different order. Never use sequence values as a proxy for event time or commit order.

## 3.10.32 Cached Values and setval()

Manual sequence changes can interact with cached values held by sessions. For high-risk realignment, coordinate traffic drain or application restart where necessary.

## 3.10.33 Sequence IDs Are Not Commit Order

Sequence identifiers are allocation order, not commit order. Use timestamps, commit timestamps where appropriate, WAL ordering, or explicit ordering columns for ordering semantics.

## 3.10.34 Sequence Contention

Very high-throughput workloads can create sequence contention or visibility in performance profiles. Mitigations include appropriate cache, sharded key strategies, UUID/ULID-style identifiers where suitable, and workload-specific redesign.

## 3.10.35 ALTER SEQUENCE on Hot Workloads

`ALTER SEQUENCE` changes production state. Review lock behavior, application expectations, replicas, and cached values before altering hot sequences.

## 3.10.36 Sequence Exhaustion

Sequence exhaustion occurs when the sequence reaches its maximum or minimum value. Integer-backed sequences are common risk points in older systems.

## 3.10.37 Monitor Time to Exhaustion

Track remaining values and burn rate.

```sql
SELECT schemaname, sequencename, last_value, max_value,
       max_value - last_value AS remaining_values
FROM pg_sequences
WHERE schemaname = 'app';
```

Burn-rate monitoring is more useful than a static remaining-value threshold.

## 3.10.38 Exhaustion Alerting

Alert on projected exhaustion before the emergency window. Use warning, critical, and emergency thresholds based on observed allocation rate and remediation time.

## 3.10.39 integer vs bigint

`integer` identity or serial columns can run out in high-growth systems. Prefer `bigint` for production surrogate keys unless storage and compatibility constraints justify `integer`.

## 3.10.40 Integer-to-Bigint Remediation

Integer-to-bigint changes can be operationally expensive. Plan migrations with backfills, dual-write or shadow-column strategies where needed, index/constraint rebuild planning, replication impact assessment, and rollback criteria.

## 3.10.41 CYCLE

`CYCLE` allows a sequence to wrap around after reaching its bound. Avoid it for identifiers that must remain unique over table lifetime.

## 3.10.42 Descending Sequences

Descending sequences are valid but require clear bounds and monitoring.

```sql
CREATE SEQUENCE app.reverse_id_seq
    AS bigint
    START WITH -1
    INCREMENT BY -1
    MINVALUE -9223372036854775808
    MAXVALUE -1
    NO CYCLE;
```

## 3.10.43 Sequence/Table Drift

Drift occurs when the sequence's next value can collide with existing table rows. Causes include manual inserts, bulk loads, restores, logical replication cutovers, incorrect `setval()`, and application overrides.

## 3.10.44 Never Blindly Repair With MAX(id)

`MAX(id)` repair can be unsafe under concurrent writes and can target the wrong table or sequence. Always lock or otherwise coordinate writes, identify the correct sequence, and verify expected next value.

## 3.10.45 Safe Sequence Realignment

A typical controlled realignment pattern is:

```sql
BEGIN;
LOCK TABLE app.orders IN SHARE ROW EXCLUSIVE MODE;
SELECT setval(
    pg_get_serial_sequence('app.orders', 'order_id'),
    COALESCE((SELECT max(order_id) FROM app.orders), 0) + 1,
    false
);
COMMIT;
```

Adapt locking and value semantics to the workload and sequence definition.

## 3.10.46 Bulk Data Migration

Bulk loads can introduce explicit identifiers and create drift. Migration runbooks must include sequence discovery, pre-load state capture, post-load realignment, duplicate checks, and application validation.

## 3.10.47 Identity Columns During Migration

Identity columns may require `OVERRIDING SYSTEM VALUE` when loading explicit values into `GENERATED ALWAYS` columns.

```sql
INSERT INTO app.orders (order_id, customer_id)
OVERRIDING SYSTEM VALUE
VALUES (1001, 42);
```

## 3.10.48 Backup and Restore

Backups must preserve sequence state. After restore, validate sequence/table alignment before opening write traffic.

## 3.10.49 Logical Replication

Logical replication does not treat sequence state the same way as table row changes. Cutover plans must explicitly synchronize sequences to avoid collisions.

## 3.10.50 Logical Replication Cutover

Before cutover, stop writes or establish a controlled write boundary, compare source and target maximum identifiers, set target sequences above the source high-water mark, and validate inserts before releasing traffic.

## 3.10.51 Blue/Green and Cross-Platform Migration

Blue/green and cross-platform migrations must treat sequence state as a cutover asset. Include sequence inventory, current values, ownership, identity metadata, grants, and post-cutover validation.

## 3.10.52 Physical Replication and HA

Physical replication replays sequence state through WAL, but failover can still expose cached-value gaps and application ordering assumptions. Validate behavior after promotion.

## 3.10.53 DR Promotion Validation

After DR promotion, validate writable role state, sequence advancement, identity defaults, sequence privileges, and representative inserts before returning full traffic.

## 3.10.54 Multi-Writer Architectures

Multi-writer architectures require collision avoidance. Options include disjoint ranges, node-specific increments/offsets, external ID generation, UUID/ULID-style keys, or application-level key services.

## 3.10.55 External Use of Sequence Values

External systems should not reserve sequence values without clear ownership and failure handling. If values are generated outside insert paths, define expiry, rollback, audit, and reconciliation behavior.

## 3.10.56 Unlogged Sequences

Unlogged sequences do not provide the same durability guarantees as logged sequence state. Avoid them unless the application explicitly accepts reset/loss semantics after crash or failover.

## 3.10.57 IF NOT EXISTS Is Not Schema Convergence

`CREATE SEQUENCE IF NOT EXISTS` avoids an error but does not confirm that the existing sequence has the expected type, bounds, cache, ownership, privileges, or dependencies. Use explicit schema verification.

## 3.10.58 Sequence Security

Treat sequences as writable state. Incorrect `USAGE`, `SELECT`, or ownership grants can reveal values, allow unexpected advancement, or permit unsafe alteration. Apply least privilege and audit grants.

## 3.10.59 Dependency Inventory

Maintain inventory of tables, columns, sequences, identity definitions, ownership, grants, defaults, and dependencies.

```sql
SELECT n.nspname, c.relname AS sequence_name, pg_get_userbyid(c.relowner) AS owner
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'S';
```

## 3.10.60 Monitoring Model

Monitor sequence exhaustion, drift risk, failed duplicate-key inserts, permission errors, invalid defaults, migration deltas, logical-replication cutover readiness, and ownership/grant drift.

## 3.10.61 Alerting

Alert on projected exhaustion, duplicate-key errors caused by sequence drift, sequence permission failures, replication/cutover mismatch, failed realignment jobs, and unexpected changes to sequence definitions.

## 3.10.62 Failure Scenario — Sequence Behind Table

Symptom: inserts fail with duplicate-key errors because the sequence emits values already present in the table. Response: stop or coordinate writes, confirm the associated sequence, realign safely, validate inserts, and document the root cause.

## 3.10.63 Failure Scenario — Sequence Exhaustion

Symptom: `nextval()` fails because the sequence reached its bound. Response: assess type and bounds, stop unsafe retries, migrate to a larger type or new key strategy, and restore service with a tested plan.

## 3.10.64 Failure Scenario — Incorrect Sequence Reset

Symptom: manual `setval()` creates collisions or jumps unexpectedly. Response: freeze the affected path, inspect current sequence/table state, repair with reviewed SQL, and identify who/what changed state.

## 3.10.65 Failure Scenario — Permission Denied

Symptom: application inserts fail because the writer lacks sequence privileges. Response: grant minimum required sequence privileges, fix default privileges, and add deployment checks for future sequences.

## 3.10.66 Failure Scenario — Logical Cutover Collision

Symptom: after migration cutover, target emits identifiers already used by replicated data. Response: stop writes, compare high-water marks, reset target sequences, validate, and resume only after collision risk is removed.

## 3.10.67 Failure Scenario — Wrong Ordering Assumption

Symptom: downstream systems assume sequence values represent commit order or event time. Response: correct the model, add proper ordering columns or event timestamps, and repair consumers.

## 3.10.68 Failure Scenario — Future Sequence Missing Privileges

Symptom: a new table deploys successfully but inserts fail because future sequence privileges were not configured. Response: fix grants for existing sequence, configure default privileges, and add release validation.

## 3.10.69 Emergency Troubleshooting Workflow

Emergency flow: identify the failing table and column, discover the associated sequence, inspect current table maximum and sequence next behavior, check privileges and ownership, validate recent migrations or restores, repair under controlled locking/traffic policy, and verify application inserts.

## 3.10.70 Production Change Runbook

A sequence change runbook should include purpose, affected table/column, current sequence definition, dependency inventory, privilege impact, replication/cutover impact, reviewed SQL, lock/traffic plan, validation queries, rollback plan, monitoring, and post-change evidence.

## 3.10.71 Production Checklist

Before production use, confirm `bigint` where appropriate, explicit identity/default semantics, primary key or uniqueness enforcement, `OWNED BY` dependencies, least-privilege grants, default privileges, exhaustion monitoring, migration procedures, and cutover validation.

## 3.10.72 Common Anti-Patterns

Common anti-patterns include using sequences for gapless counters, assuming sequence values equal commit order, using `MAX(id)` repairs without coordination, forgetting future grants, ignoring logical-replication sequence state, using `integer` identifiers for high-growth tables, and treating `IF NOT EXISTS` as schema validation.

## 3.10.73 SRE / DBRE Production Standard

Sequences and identity columns must be managed as production state. Every critical sequence should have defined ownership, dependency mapping, privilege policy, monitoring, exhaustion forecast, migration/cutover procedure, and emergency repair runbook.

## 3.10.74 Key Takeaways

Sequences are fast, concurrent, independent state objects. Gaps are normal. Sequence changes are not rolled back like row data. Identity columns improve clarity but do not replace constraints. Logical replication and migrations require explicit sequence handling. SRE/DBRE teams must monitor exhaustion and drift before they become incidents.
