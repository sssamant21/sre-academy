# 3.11 — PostgreSQL Views and Materialized Views Administration

**Edition:** Revised Final / Canonical Edition

**Chapter:** 3 — PostgreSQL Database and Object Administration

**Status:** Draft COMPLETE → Technical Review COMPLETE → Production Review COMPLETE → Canonical Edition

**Audience:** PostgreSQL DBA / DBRE / SRE / Platform Engineering

**Scope:** PostgreSQL 14–18; version-sensitive behavior must be validated against the deployed major version.

This canonical edition establishes the production operating standard for PostgreSQL views and materialized views.

## 3.11.1 Operational Purpose

Views and materialized views form a derived data layer between PostgreSQL's physical schema and consumers. A view provides abstraction, reusable query logic, security interfaces, stable database APIs, compatibility layers, and controlled column exposure. A materialized view adds physical storage of a query result and is useful when expensive computations can be precomputed and some staleness is acceptable.

Production principle: a view is an interface; a materialized view is an interface plus stored derived state that must be operated.

## 3.11.2 View vs Materialized View

| Characteristic | View | Materialized view |
| --- | --- | --- |
| Stores query definition | Yes | Yes |
| Stores result rows | No | Yes |
| Reflects base-table changes | When queried | Only after refresh |
| Requires refresh | No | Yes |
| Supports indexes on derived result | No | Yes |
| Freshness management | Usually not required | Required |
| Storage capacity | Minimal metadata | Potentially substantial |
| Primary use | Abstraction/interface | Precomputation |

Do not create a materialized view merely because a query is slow. First investigate indexes, statistics, join strategy, large scans, predicates, data modeling, memory/temp pressure, and workload contention.

## 3.11.3 Creating Production Views

Use explicit schemas and clear column lists.

```sql
CREATE VIEW reporting.customer_orders AS
SELECT c.customer_id,
       c.customer_name,
       o.order_id,
       o.created_at,
       o.total_amount
FROM app.customers c
JOIN app.orders o ON o.customer_id = c.customer_id;
```

A production view should have a named owner, documented purpose, dependency review, privilege model, and change procedure.

## 3.11.4 Explicit Columns Are the Production Standard

Avoid `SELECT *` in view definitions. Explicit columns prevent accidental interface changes, reduce dependency ambiguity, and make reviews safer.

## 3.11.5 Treat Views as Database APIs

Views consumed by applications, reports, ETL, or external users are database APIs. Treat changes to view columns, types, nullability, semantics, filters, joins, and row counts as API changes.

## 3.11.6 CREATE OR REPLACE VIEW

`CREATE OR REPLACE VIEW` can update a view definition, but it has compatibility rules. It is not a universal safe-change mechanism. Review output columns and consumer expectations before using it in production.

## 3.11.7 Schema Compatibility Is Not Semantic Compatibility

A view can keep the same column names and types while changing meaning. Semantic changes require review, tests, communication, and rollout planning.

## 3.11.8 Version Breaking View Changes

For breaking changes, create a new versioned view such as `reporting.customer_orders_v2`, migrate consumers, observe usage, then retire the old view through a controlled deprecation process.

## 3.11.9 PostgreSQL Dependency Tracking

PostgreSQL tracks dependencies between views and referenced objects. Use catalog inspection before altering or dropping base objects.

```sql
SELECT dependent_ns.nspname AS dependent_schema,
       dependent_view.relname AS dependent_view
FROM pg_depend d
JOIN pg_rewrite r ON r.oid = d.objid
JOIN pg_class dependent_view ON dependent_view.oid = r.ev_class
JOIN pg_namespace dependent_ns ON dependent_ns.oid = dependent_view.relnamespace
WHERE d.refobjid = 'app.orders'::regclass;
```

## 3.11.10 Database Dependencies Are Not the Whole Dependency Graph

PostgreSQL cannot see all BI dashboards, application code, ETL jobs, exports, notebooks, alerts, or partner integrations that consume a view. Maintain an external consumer inventory for production-facing views.

## 3.11.11 Ownership

View and materialized-view ownership controls who can alter, replace, refresh, or drop objects. Use service roles or schema-owner roles rather than individual human owners.

## 3.11.12 View Privileges

Grant the minimum required privileges.

```sql
GRANT SELECT ON reporting.customer_orders TO analytics_reader;
```

Do not grant base-table access when a view is intended to be the security boundary.

## 3.11.13 Default View Security Context

By default, PostgreSQL views usually execute with the privileges of the view owner. This can intentionally expose controlled data, but it can also create accidental privilege bypass if the owner has broad base-table privileges.

## 3.11.14 security_invoker

`security_invoker` makes a view check permissions as the invoking user rather than the view owner.

```sql
CREATE VIEW reporting.customer_orders
WITH (security_invoker = true) AS
SELECT ...;
```

Use it when consumers should need permissions on underlying objects.

## 3.11.15 security_barrier

`security_barrier` can prevent the planner from pushing user-supplied predicates in ways that could leak information through side effects or evaluation order.

```sql
CREATE VIEW reporting.secure_orders
WITH (security_barrier = true) AS
SELECT ...;
```

Use it for security-sensitive filtering interfaces after testing plan impact.

## 3.11.16 security_invoker vs security_barrier

`security_invoker` controls whose privileges are checked. `security_barrier` controls optimization behavior around security-sensitive predicates. They solve different problems and may be combined when appropriate.

## 3.11.17 Views and Row-Level Security

Views interact with row-level security through ownership, invoker/definer behavior, base-table policies, and version-specific PostgreSQL behavior. Test actual effective visibility for each role.

## 3.11.18 RLS Regression Testing

Every security-sensitive view should have regression tests for allowed rows, denied rows, role behavior, owner changes, policy changes, and query plans where relevant.

## 3.11.19 Functions Inside Views

Functions inside views inherit volatility, security, search path, leakproof, and privilege considerations. Avoid unsafe `SECURITY DEFINER` functions and unqualified object references.

## 3.11.20 Automatically Updatable Views

Simple views can be automatically updatable when PostgreSQL can map writes back to one base table.

```sql
CREATE VIEW app.active_customers AS
SELECT customer_id, customer_name, status
FROM app.customers
WHERE status = 'ACTIVE';
```

Test `INSERT`, `UPDATE`, and `DELETE` behavior explicitly before exposing writable views.

## 3.11.21 WITH CHECK OPTION

`WITH CHECK OPTION` ensures writes through a view satisfy the view predicate.

```sql
CREATE VIEW app.active_customers AS
SELECT customer_id, customer_name, status
FROM app.customers
WHERE status = 'ACTIVE'
WITH CHECK OPTION;
```

## 3.11.22 LOCAL vs CASCADED

`LOCAL` checks only the current view condition. `CASCADED` checks conditions through dependent views. Use explicit behavior for layered writable views.

## 3.11.23 Temporary and Recursive Views

Temporary views are session-scoped and useful for controlled workflows. Recursive views should be reviewed carefully for performance, termination, and operational cost.

## 3.11.24 Materialized View Architecture

A materialized view stores a query result as a relation. It has storage, can have indexes, requires refresh, can become stale, consumes vacuum/analyze capacity, and must be considered in backup, restore, HA, and capacity planning.

## 3.11.25 Creating a Materialized View

```sql
CREATE MATERIALIZED VIEW reporting.daily_order_summary AS
SELECT date_trunc('day', created_at)::date AS order_date,
       count(*) AS order_count,
       sum(total_amount) AS total_amount
FROM app.orders
GROUP BY 1;
```

Define ownership, refresh cadence, freshness SLO, indexes, and consumer expectations before production use.

## 3.11.26 WITH NO DATA

`WITH NO DATA` creates the materialized-view definition without populating rows.

```sql
CREATE MATERIALIZED VIEW reporting.daily_order_summary AS
SELECT ...
WITH NO DATA;
```

Use it to separate object creation from initial population in controlled deployments.

## 3.11.27 Inventory with pg_matviews

```sql
SELECT schemaname, matviewname, matviewowner, ispopulated, definition
FROM pg_matviews
WHERE schemaname = 'reporting';
```

Maintain inventory of refresh owners, schedules, freshness SLOs, indexes, size, dependencies, and consumers.

## 3.11.28 Standard Refresh

```sql
REFRESH MATERIALIZED VIEW reporting.daily_order_summary;
```

A standard refresh can block readers depending on operation state and should be scheduled with availability requirements in mind.

## 3.11.29 Refresh Authorization Is Version-Sensitive

Privileges and ownership requirements around refresh operations are version-sensitive. Validate behavior against the deployed PostgreSQL major version and the exact role model.

## 3.11.30 Refresh WITH NO DATA

`REFRESH MATERIALIZED VIEW ... WITH NO DATA` marks the materialized view unpopulated. Consumers must not rely on it until it is refreshed with data.

## 3.11.31 Standard Refresh and Reader Availability

Standard refresh may make the materialized view unavailable for normal reads during refresh. Use only when reader blocking is acceptable or when maintenance windows cover the impact.

## 3.11.32 Concurrent Refresh

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY reporting.daily_order_summary;
```

Concurrent refresh permits reads while refresh is running, but it still consumes CPU, memory, I/O, WAL, temp space, locks, and time.

## 3.11.33 Concurrent Refresh Prerequisites

Concurrent refresh requires the materialized view to be populated and to have at least one suitable unique index that covers all rows and is not partial or expression-based.

## 3.11.34 Initial Population

A materialized view created `WITH NO DATA` must be populated with a standard refresh before concurrent refresh can be used.

## 3.11.35 One Refresh per Materialized View

Only one refresh of a materialized view should run at a time. Use scheduler locks, advisory locks, or job coordination to prevent overlap.

## 3.11.36 Standard vs Concurrent Decision

Choose standard refresh when reader downtime is acceptable and operational simplicity matters. Choose concurrent refresh when reader availability is required and prerequisites are met.

## 3.11.37 Concurrent Refresh Still Consumes Resources

Concurrent refresh is not free. Monitor query runtime, temp files, WAL, replication lag, I/O, CPU, locks, and downstream freshness impact.

## 3.11.38 Indexing Materialized Views

Materialized views can and often should have indexes based on consumer queries and concurrent refresh requirements.

```sql
CREATE UNIQUE INDEX daily_order_summary_date_uidx
ON reporting.daily_order_summary (order_date);
```

## 3.11.39 Index Cost

Indexes on materialized views improve reads but add refresh cost, storage, WAL, and maintenance. Keep the index set minimal and evidence-based.

## 3.11.40 Statistics

Analyze materialized views after refresh when needed so the planner has accurate statistics.

```sql
ANALYZE reporting.daily_order_summary;
```

## 3.11.41 Ordering Is Not Guaranteed

An `ORDER BY` inside a materialized-view definition does not guarantee consumer query ordering. Consumers must use their own `ORDER BY`.

## 3.11.42 Define a Freshness SLO

Every production materialized view needs a freshness SLO, such as “data no more than 15 minutes old during business hours.” Scheduler success alone is not freshness.

## 3.11.43 Track Refresh Metadata

Track last refresh start, end, status, duration, row count when useful, error text, and staleness.

```sql
CREATE TABLE ops.matview_refresh_log (
    matview_name text NOT NULL,
    refresh_started_at timestamptz NOT NULL,
    refresh_finished_at timestamptz,
    status text NOT NULL,
    error_message text
);
```

## 3.11.44 Monitor Freshness, Not Just Scheduler Success

A job may succeed late, refresh too slowly, or produce stale results. Monitor the age of data as seen by consumers.

## 3.11.45 Availability, Freshness, and Correctness Are Different

A materialized view can be available but stale, fresh but incorrect, or correct but unavailable. SLOs and alerts must distinguish these dimensions.

## 3.11.46 Refresh Runtime SLO

Track refresh duration against an expected window. Runtime growth often signals data growth, statistics drift, missing indexes, temp pressure, or plan regression.

## 3.11.47 Prevent Retry Storms

Failed refresh jobs should use backoff, locking, error classification, and operator notification. Blind retries can saturate the primary and worsen incidents.

## 3.11.48 Capacity Planning

Refresh planning must account for result size, base-table scan cost, temp files, sorting, hashing, indexes, WAL, replication lag, storage, locks, autovacuum interaction, and backup/restore impact.

## 3.11.49 Refresh and HA

Refreshes on a primary generate WAL and can affect replicas. Validate failover behavior, replica lag, and post-promotion freshness before relying on materialized-view data.

## 3.11.50 Coordinate Heavy Operations

Avoid overlapping materialized-view refreshes with backups, vacuum-heavy windows, reindexing, large ETL loads, major batch jobs, or planned failovers unless capacity has been proven.

## 3.11.51 View Performance

Views are expanded into the surrounding query by the planner. Poor performance may come from base-table access, joins, filters, statistics, nested view complexity, or security-barrier behavior.

## 3.11.52 Nested Views

Nested views can hide complexity, degrade performance, confuse ownership, and make dependency changes risky. Limit nesting depth and inspect fully expanded query behavior.

## 3.11.53 Definition Inspection

Use `pg_get_viewdef()` for view definitions.

```sql
SELECT pg_get_viewdef('reporting.customer_orders'::regclass, true);
```

## 3.11.54 Search Path Discipline

Use schema-qualified object names in production view definitions. Avoid relying on mutable `search_path` behavior.

## 3.11.55 Views as Compatibility Layers

Views can preserve old interfaces during table refactors, migrations, and blue/green deployments. Treat compatibility views as owned products with deprecation dates.

## 3.11.56 Blue/Green View Deployment

For view changes, create new versions, run dual validation, migrate consumers, monitor usage, and remove old versions only after confirmed retirement.

## 3.11.57 Blue/Green Materialized Views

For materialized views, build the new MV separately, populate and index it, reconcile results, switch consumers, monitor, then retire the old MV.

## 3.11.58 Result Reconciliation

Reconcile row counts, aggregate totals, key coverage, sample rows, freshness timestamps, and known business invariants before switching consumers.

## 3.11.59 Logical Replication and Migration

Views are schema objects and materialized views are stored derived state. Migration plans must include definitions, indexes, privileges, refresh strategy, and post-cutover validation.

## 3.11.60 Backup and Restore

Backups include materialized-view storage, which can increase backup size. After restore, validate population state, freshness, indexes, permissions, and refresh jobs.

## 3.11.61 Disaster Recovery

DR runbooks must define whether materialized views are restored as-is, refreshed after promotion, or temporarily considered stale. Applications must know the stale-data policy.

## 3.11.62 Stale-Data Failure Policy

Define whether consumers should continue serving stale data, fail closed, show warnings, or switch sources when materialized-view freshness exceeds SLO.

## 3.11.63 Failure Scenario — Refresh Pileup

Overlapping refreshes saturate the database. Recovery: stop duplicate jobs, identify blockers, add scheduler locking, and review refresh duration and cadence.

## 3.11.64 Failure Scenario — Security Regression

A view exposes rows or columns unexpectedly. Recovery: revoke access if necessary, inspect owner/security options/RLS, fix definition, add regression tests, and audit access.

## 3.11.65 Failure Scenario — MV Available but Stale

Consumers can read the MV, but freshness SLO is breached. Recovery: communicate stale state, repair scheduler or refresh issue, validate data, and improve freshness monitoring.

## 3.11.66 Failure Scenario — Concurrent Refresh Saturates Primary

Concurrent refresh preserves reads but can overload primary resources. Recovery: cancel if needed, throttle or reschedule, tune indexes/query, and revise capacity model.

## 3.11.67 Failure Scenario — Semantic Regression

A view change keeps the same columns but changes meaning. Recovery: roll back or version the view, validate consumers, and strengthen semantic tests.

## 3.11.68 Failure Scenario — CASCADE Blast Radius

`DROP ... CASCADE` can remove dependent views unexpectedly. Recovery: restore definitions, validate consumers, and require dependency review for destructive changes.

## 3.11.69 Failure Scenario — Storage Exhaustion

A materialized view or refresh consumes unexpected disk/temp space. Recovery: stop refresh if needed, free space, validate database health, and add capacity guardrails.

## 3.11.70 Failure Scenario — Incorrect RLS Assumption

Consumers see too much or too little data because view security and RLS behavior were misunderstood. Recovery: test effective role behavior, adjust security options/policies, and add regression coverage.

## 3.11.71 Troubleshooting Regular Views

Troubleshooting flow: inspect definition, check dependencies, confirm owner and privileges, test as the consumer role, run `EXPLAIN`, verify RLS behavior, inspect nested views, and validate semantic expectations.

## 3.11.72 Troubleshooting Materialized Views

Troubleshooting flow: inspect `pg_matviews`, check `ispopulated`, validate indexes, review refresh logs, measure freshness, run refresh manually in a controlled window, monitor locks/resources, and verify consumer query plans.

## 3.11.73 Production Monitoring Matrix

| Area | Signals |
| --- | --- |
| View security | privileges, owner, security options, RLS tests |
| Dependencies | base tables, functions, nested views, consumers |
| MV freshness | data age, last successful refresh, scheduler state |
| MV refresh | duration, failures, locks, temp files, WAL, I/O |
| MV storage | relation size, index size, growth rate |
| Consumers | query latency, errors, stale-data behavior |

## 3.11.74 Recommended SRE Metrics

Track materialized-view freshness age, refresh duration, refresh success/failure, refresh overlap prevention, relation size, temp bytes, WAL impact, replication lag, consumer query latency, and security regression test status.

## 3.11.75 Alerting

Alert on freshness SLO breach, refresh failure, excessive refresh runtime, overlapping refresh attempts, storage thresholds, replica lag caused by refresh, security test failure, and consumer error spikes.

## 3.11.76 Production Change Checklist

Before changing a view or MV, confirm purpose, consumers, owner, privileges, RLS/security behavior, dependency graph, performance plan, rollback strategy, deployment order, validation queries, and monitoring.

## 3.11.77 Canonical Deployment Runbook

A deployment runbook should include reviewed SQL, explicit schema-qualified definitions, consumer inventory, preflight dependency checks, role-based access tests, plan/performance validation, refresh/capacity plan for MVs, rollout steps, rollback steps, and post-change observation.

## 3.11.78 Common Production Anti-Patterns

Anti-patterns include `SELECT *` in views, using MVs to hide unresolved query problems, missing freshness SLOs, blind refresh retries, untested RLS assumptions, deep nested views, `DROP ... CASCADE` without dependency review, and unowned reporting interfaces.

## 3.11.79 SRE / DBRE Operating Standard

Views and materialized views must be operated as production interfaces. Every production view/MV should have ownership, purpose, dependency inventory, security model, consumer inventory, test coverage, deployment process, rollback plan, and operational monitoring.

## 3.11.80 Key Production Rules

Views are APIs. Materialized views are stored derived state. Explicit columns are mandatory. Security behavior must be tested as real roles. Materialized views need freshness SLOs, refresh coordination, capacity planning, and stale-data policy. Breaking changes require versioned rollout and consumer migration.
