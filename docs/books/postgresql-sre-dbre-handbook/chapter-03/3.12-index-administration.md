# 3.12 — PostgreSQL Index Administration and Management

**Edition:** Revised Final / Canonical Edition

**Chapter:** 3 — PostgreSQL Database and Object Administration

**Status:** Draft COMPLETE → Technical Review COMPLETE → Production Review COMPLETE → Canonical Edition

This canonical edition establishes the production standard for PostgreSQL index design, deployment, monitoring, maintenance, troubleshooting, corruption detection, rebuilding, and retirement. The source draft was labeled 3.9, but the locked Chapter 3 structure reserves 3.9 for constraints and 3.12 for index administration; this section is therefore normalized to 3.12.

## 3.12.1 Indexes as Production Infrastructure

Indexes are not only query-performance objects. In production they affect latency, write cost, WAL generation, storage, cache utilization, VACUUM, replication, CDC, constraints, and availability.

The lifecycle is workload analysis → query plan review → index design → testing → safe deployment → verification → monitoring → maintenance → keep, rebuild, or retire.

The production objective is to maintain the smallest effective index set that satisfies performance, integrity, replication, and operational requirements.

## 3.12.2 Index Benefits vs Cost

An index can transform a large sequential scan into a targeted lookup of candidate tuple locations, but every index adds storage, INSERT/UPDATE/DELETE work, WAL volume, VACUUM overhead, cache footprint, backup cost, and maintenance burden.

More indexes do not mean a better database. The right index set is workload-specific and should be proven by plans, metrics, and operational behavior.

## 3.12.3 PostgreSQL Index Access Methods

PostgreSQL includes several built-in access methods:

| Method | Typical workload |
| --- | --- |
| B-tree | Equality, range, ordering |
| Hash | Equality |
| GiST | Extensible multidimensional and operator searches |
| SP-GiST | Partitioned search structures |
| GIN | Multi-valued and searchable components |
| BRIN | Large physically correlated datasets |

The correct method depends on query operators, data distribution, access pattern, and write pattern, not only the column data type.

## 3.12.4 B-tree

B-tree is PostgreSQL's default general-purpose index.

```sql
CREATE INDEX idx_orders_customer_id
ON app.orders (customer_id);
```

B-tree commonly supports equality predicates, range predicates, and ordering requirements:

```sql
WHERE customer_id = 12345;
WHERE created_at >= DATE '2026-01-01';
ORDER BY created_at;
```

## 3.12.5 The Planner Decides Whether an Index Is Used

The existence of an index does not force PostgreSQL to use it. The planner compares estimated costs for sequential scans, index scans, bitmap scans, joins, ordering, correlation, selectivity, and available memory.

Use `EXPLAIN (ANALYZE, BUFFERS)` to validate real behavior before and after index changes.

## 3.12.6 Multicolumn B-tree Indexes

Column order matters. A multicolumn B-tree index is usually strongest when equality predicates appear on leading columns and range predicates appear after them.

```sql
CREATE INDEX idx_orders_customer_status_created
ON app.orders (customer_id, status, created_at);
```

A query filtering on `customer_id`, `status`, and `created_at` can benefit directly. A query filtering only on `created_at` usually cannot use this index as effectively.

## 3.12.7 PostgreSQL 18 B-tree Skip Scan

PostgreSQL 18 can use B-tree skip scan for some multicolumn indexes when the query lacks equality on the leading column but later columns are selective. This improves some historical limitations, but it is not a reason to ignore column-order design. Validate with plans on the target PostgreSQL version.

## 3.12.8 Multicolumn Behavior Depends on Access Method

Multicolumn behavior is access-method specific. B-tree, GiST, GIN, BRIN, SP-GiST, and hash indexes do not all behave the same way with column order, operator support, or filtering. SRE/DBRE review must evaluate the method, operator class, predicate, and workload together.

## 3.12.9 UNIQUE Indexes and Constraints

Unique constraints are enforced by unique indexes. Prefer declarative constraints for data integrity semantics:

```sql
ALTER TABLE app.users
ADD CONSTRAINT users_email_key UNIQUE (email);
```

Use unique indexes directly when the index form is required, such as a partial unique index:

```sql
CREATE UNIQUE INDEX users_active_email_uidx
ON app.users (email)
WHERE deleted_at IS NULL;
```

## 3.12.10 Partial Indexes

Partial indexes index only rows matching a predicate.

```sql
CREATE INDEX orders_open_created_idx
ON app.orders (created_at)
WHERE status = 'OPEN';
```

They are valuable when a small subset of rows is queried frequently, but they are only useful when the query predicate matches the index predicate closely enough for the planner to prove applicability.

## 3.12.11 Partial-Index Predicate Matching

PostgreSQL does not perform arbitrary theorem proving for partial indexes. Parameterized predicates can prevent use of a partial index because the planner cannot prove the parameter always satisfies the predicate. Production standards should include query-shape validation for partial indexes.

## 3.12.12 Expression Indexes

Expression indexes store computed values.

```sql
CREATE INDEX users_lower_email_idx
ON app.users (lower(email));
```

They support queries using the same expression, but they add write cost because the expression must be computed and maintained on data changes.

## 3.12.13 Covering Indexes with INCLUDE

`INCLUDE` columns allow B-tree indexes to cover more queries without making included columns part of the search key.

```sql
CREATE INDEX orders_customer_created_inc_idx
ON app.orders (customer_id, created_at)
INCLUDE (total_amount, status);
```

Use included columns sparingly. Wide covering indexes can reduce heap access but increase storage, cache pressure, WAL, and write amplification.

## 3.12.14 Index-Only Scans and MVCC

Index-only scans require the visibility map to show that heap pages are all-visible. They are most effective on stable, vacuumed data. A covering index does not guarantee an index-only scan; MVCC visibility still matters.

## 3.12.15 GIN

GIN indexes are useful for multi-valued data such as arrays, JSONB, and full-text search.

```sql
CREATE INDEX documents_body_gin_idx
ON app.documents USING gin (body_tsv);

CREATE INDEX events_payload_gin_idx
ON app.events USING gin (payload jsonb_path_ops);
```

GIN indexes can be large and expensive to maintain. Monitor write latency, pending-list behavior, index size, and autovacuum impact.

## 3.12.16 GiST

GiST indexes support extensible operator classes, including geometric, range, exclusion, and similarity-style workloads. They are powerful but operator-class dependent; validate exact operators and plans.

## 3.12.17 SP-GiST

SP-GiST supports partitioned search structures such as tries, quadtrees, and other non-balanced partitioning models. Use it only when the operator class and data distribution match the workload.

## 3.12.18 Hash

Hash indexes support equality lookups. B-tree often remains the default equality choice because it also supports ordering and range use cases. Choose hash only when its behavior is specifically justified and validated.

## 3.12.19 BRIN

BRIN indexes summarize ranges of heap pages and are useful for very large physically correlated tables, such as append-heavy time-series tables.

```sql
CREATE INDEX metrics_created_brin_idx
ON app.metrics USING brin (created_at);
```

BRIN indexes are small and cheap relative to B-tree indexes but are approximate and lossy.

## 3.12.20 BRIN Is Lossy

A BRIN match identifies page ranges, not exact rows. PostgreSQL must recheck heap tuples. Expect bitmap heap scans and rechecks. Poor correlation or broad ranges can make BRIN ineffective.

## 3.12.21 BRIN pages_per_range

`pages_per_range` controls the granularity of BRIN summaries. Smaller ranges can improve precision but increase index size and maintenance. Larger ranges reduce index size but may increase false positives.

```sql
CREATE INDEX metrics_created_brin_idx
ON app.metrics USING brin (created_at) WITH (pages_per_range = 32);
```

## 3.12.22 BRIN Requires Correlation

BRIN is strongest when physical order correlates with the indexed value. For frequently updated or randomly inserted data, correlation can decay. Monitor `pg_stats.correlation`, plans, and scan efficiency.

## 3.12.23 Operator Classes

Operator classes define which operators an index supports. Production index design must include the access method, operator class, and query operators.

```sql
CREATE INDEX users_name_pattern_idx
ON app.users (name text_pattern_ops);
```

## 3.12.24 Text, Collation, and Pattern Searches

Text indexing depends on collation and pattern type. Prefix searches, case-insensitive matching, trigram matching, and full-text search require different designs. Do not assume a generic B-tree index will accelerate every `LIKE`, `ILIKE`, or search expression.

## 3.12.25 Standard CREATE INDEX

Standard `CREATE INDEX` takes locks that permit reads but block writes on the table. Use it only when downtime or write blocking is acceptable.

```sql
CREATE INDEX idx_orders_created_at
ON app.orders (created_at);
```

## 3.12.26 CREATE INDEX CONCURRENTLY

`CREATE INDEX CONCURRENTLY` avoids blocking normal writes for most of the build, making it the default production choice for large or active tables.

```sql
CREATE INDEX CONCURRENTLY idx_orders_created_at
ON app.orders (created_at);
```

It takes longer, uses more resources, and has special failure modes.

## 3.12.27 Concurrent Build Lifecycle

A concurrent build performs multiple phases and waits for transactions that could affect correctness. It can appear idle while waiting. Monitor `pg_stat_progress_create_index`, active transactions, locks, I/O, WAL, replication lag, and table activity.

## 3.12.28 Transaction-Block Restriction

`CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, and `REINDEX INDEX CONCURRENTLY` cannot run inside a transaction block. Migration frameworks must execute these statements outside explicit transactions.

## 3.12.29 One Concurrent Build Per Table

PostgreSQL allows only one concurrent index build at a time on a table. Queue index work per table and avoid overlapping automation that repeatedly retries blocked builds.

## 3.12.30 Long-Transaction Preflight

Before a concurrent build, identify long-running transactions, old snapshots, idle-in-transaction sessions, replication slots, and prepared transactions.

```sql
SELECT pid, usename, state, xact_start, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## 3.12.31 Lock Preflight and Monitoring

Review existing locks before DDL and monitor waiting sessions during the build.

```sql
SELECT locktype, relation::regclass, mode, granted, pid
FROM pg_locks
WHERE relation = 'app.orders'::regclass;
```

## 3.12.32 Session-Level DDL Guardrails

Set conservative timeouts for schema changes.

```sql
SET lock_timeout = '5s';
SET statement_timeout = '2h';
SET idle_in_transaction_session_timeout = '1min';
```

Choose values based on the change window, table size, workload, and rollback plan.

## 3.12.33 Parallel Index Creation

PostgreSQL can use parallel workers for some index builds. Parallelism can reduce elapsed time but increase CPU, memory, I/O, and WAL pressure. Coordinate with workload peaks and maintenance windows.

## 3.12.34 Monitoring Index-Build Progress

Use `pg_stat_progress_create_index` to monitor phase, blocks, tuples, lockers, and partition progress.

```sql
SELECT pid, datname, relid::regclass, index_relid::regclass, phase,
       blocks_done, blocks_total, tuples_done, tuples_total
FROM pg_stat_progress_create_index;
```

## 3.12.35 Infrastructure Monitoring During Build

During index builds, monitor CPU saturation, read/write IOPS, queue depth, WAL generation, checkpoint pressure, replication lag, temp usage, disk free space, and application latency. Index builds are infrastructure events, not only database DDL.

## 3.12.36 Capacity Planning

Capacity planning must include the new index size, temporary build space, WAL volume, replica replay capacity, backup impact, autovacuum interaction, and failure cleanup. Avoid running close to disk limits.

## 3.12.37 WAL and Replication

Index builds generate WAL and must be replayed by replicas. A build that is safe on primary CPU can still break RPO/RTO assumptions through replica lag. Monitor `pg_stat_replication`, WAL archive health, replication slots, and downstream consumers.

## 3.12.38 Managed PostgreSQL

Managed services may add limits or different observability surfaces for storage autoscaling, I/O credits, maintenance windows, replicas, parameters, and extensions. Validate behavior against the provider documentation before production execution.

## 3.12.39 Invalid Indexes

A failed concurrent build can leave an invalid index. Invalid indexes consume storage and may still have maintenance implications.

```sql
SELECT n.nspname, c.relname, i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE NOT i.indisvalid OR NOT i.indisready;
```

## 3.12.40 Failed Concurrent UNIQUE Indexes

A failed concurrent unique index build can leave behind an invalid index that may still enforce uniqueness during later phases. Treat failed unique builds as high-risk until explicitly cleaned up.

## 3.12.41 Failed-Build Recovery

Recovery usually means identifying the invalid index, confirming it is not constraint-owned, dropping it with the correct method, resolving the cause, and retrying only after preflight checks pass.

```sql
DROP INDEX CONCURRENTLY IF EXISTS app.idx_orders_created_at;
```

## 3.12.42 Index Size Monitoring

Track index size by relation and over time.

```sql
SELECT schemaname, relname, indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;
```

## 3.12.43 Index Usage

Use `pg_stat_user_indexes` as one input, not as the only decision source.

```sql
SELECT schemaname, relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
```

## 3.12.44 Why idx_scan = 0 Is Not a Drop Decision

`idx_scan = 0` can occur because the statistics reset, the workload has not appeared yet, the index supports rare critical queries, the index backs a constraint, the index supports future incident response, or the planner uses another path temporarily. Require workload evidence before dropping.

## 3.12.45 Index Retirement Quarantine

Retirement should follow a quarantine process: identify candidates, verify not constraint-owned, verify no critical workload dependency, observe over a full workload cycle, test in lower environments, prepare rollback, drop safely, and continue monitoring.

## 3.12.46 Duplicate and Redundant Indexes

Duplicate indexes waste storage and write capacity. Redundancy is nuanced: `(a, b)` may make `(a)` redundant for some workloads but not all ordering, uniqueness, predicate, or INCLUDE cases. Review definitions, constraints, predicates, and plans before removal.

## 3.12.47 Over-Indexing

Over-indexing increases write amplification, WAL, bloat, cache pressure, vacuum time, backup size, restore time, and failover replay time. A healthy production database has enough indexes, not all possible indexes.

## 3.12.48 HOT Updates

Heap-only tuple updates can avoid index updates when no indexed columns change and page space is available. Excessive indexing reduces HOT opportunities and can increase update cost.

## 3.12.49 Index Bloat

Index bloat increases storage and can degrade cache efficiency and scan performance. Causes include churn, deletes, updates, poor fillfactor choices, and long-running transactions. Track size trends and rebuild when justified.

## 3.12.50 REINDEX

`REINDEX` rebuilds indexes but can take strong locks depending on scope and form.

```sql
REINDEX INDEX app.idx_orders_created_at;
```

Use carefully in production and prefer concurrent forms when availability requires it.

## 3.12.51 REINDEX CONCURRENTLY

`REINDEX CONCURRENTLY` rebuilds indexes with reduced blocking.

```sql
REINDEX INDEX CONCURRENTLY app.idx_orders_created_at;
```

It still needs capacity, time, monitoring, and cleanup planning.

## 3.12.52 REINDEX CONCURRENTLY Restrictions

Concurrent reindexing has restrictions, including transaction-block limitations and limitations for some system catalogs, temporary tables, and partitioned object patterns. Validate the exact PostgreSQL version behavior.

## 3.12.53 Reindex Capacity Planning

Plan for duplicate index storage during rebuild, WAL volume, replica replay, I/O saturation, autovacuum competition, backup impact, and failure cleanup. Do not start a rebuild without a disk-free-space threshold and abort criteria.

## 3.12.54 DROP INDEX

Standard `DROP INDEX` removes an index and may block depending on dependencies and locks.

```sql
DROP INDEX app.idx_orders_created_at;
```

Use only after dependency and workload review.

## 3.12.55 DROP INDEX CONCURRENTLY

`DROP INDEX CONCURRENTLY` reduces blocking for production drops.

```sql
DROP INDEX CONCURRENTLY app.idx_orders_created_at;
```

It cannot run inside a transaction block, cannot use `CASCADE`, and cannot be used directly on constraint-owned indexes.

## 3.12.56 Constraint-Owned Indexes

Primary key, unique, and exclusion constraints own supporting indexes. Do not drop those indexes directly. Change the constraint intentionally if the integrity rule must change.

## 3.12.57 Foreign-Key Indexes

PostgreSQL does not automatically create indexes on foreign-key referencing columns. Missing FK-side indexes can cause slow parent deletes/updates and lock amplification.

```sql
CREATE INDEX CONCURRENTLY orders_customer_id_idx
ON app.orders (customer_id);
```

## 3.12.58 Replica Identity and CDC

Logical replication and CDC may require replica identity. Primary keys or suitable unique indexes often support efficient row identification. Changing indexes can affect downstream replication and consumers.

## 3.12.59 Index Corruption vs Invalid Index

An invalid index is a catalog/build-state issue. Corruption means index contents are physically or logically inconsistent. Treat corruption as an incident: preserve evidence, stop unsafe automation, validate replicas, and choose repair steps deliberately.

## 3.12.60 Integrity Checking

Use appropriate tools and extensions, such as `amcheck` where available, to verify index integrity.

```sql
CREATE EXTENSION IF NOT EXISTS amcheck;
SELECT bt_index_check('app.idx_orders_created_at'::regclass);
```

Run checks with awareness of cost, lock behavior, and production impact.

## 3.12.61 Partitioned Tables

Partitioned tables require index strategy per partition and, where supported, partitioned indexes at the parent level. Validate uniqueness rules, partition key requirements, maintenance sequencing, and attach/detach workflows.

## 3.12.62 Fillfactor

Index fillfactor reserves free space and can reduce page splits for write-heavy indexes at the cost of larger indexes.

```sql
CREATE INDEX orders_created_idx
ON app.orders (created_at) WITH (fillfactor = 90);
```

Tune only with workload evidence.

## 3.12.63 Planner Statistics

Index usefulness depends on statistics. Run `ANALYZE` after major data changes and monitor stale stats, skew, correlation, extended statistics needs, and row-estimate errors.

```sql
CREATE STATISTICS orders_customer_status_stats
ON customer_id, status
FROM app.orders;
ANALYZE app.orders;
```

## 3.12.64 Index Design Workflow

The production workflow is: identify workload, capture representative SQL, examine plans, identify predicates and ordering, choose method and columns, test with realistic data, estimate build cost, deploy safely, verify plans, monitor effects, and document ownership.

## 3.12.65 Hypothetical Indexes

Hypothetical indexes can help evaluate planner choices without building real indexes when extensions such as HypoPG are available. Treat them as planning aids only; they do not measure build cost, write cost, bloat, or real runtime behavior.

## 3.12.66 Production Index Risk Classification

Classify index work by table size, write rate, availability requirement, uniqueness, partitioning, replication, managed-service limits, rollback complexity, and consumer dependencies. Higher-risk index work needs explicit change control and real-time monitoring.

## 3.12.67 Production Preflight SQL

Preflight should cover table size, index size, active transactions, locks, replication lag, invalid indexes, disk space, and candidate duplicate indexes.

```sql
SELECT pg_size_pretty(pg_total_relation_size('app.orders')) AS table_total_size;

SELECT pid, state, xact_start, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

SELECT application_name, state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

## 3.12.68 Production Go / No-Go Checklist

Go only when the index definition is reviewed, the expected plan improvement is proven, capacity is sufficient, replication can absorb WAL, migration tooling can run outside a transaction if needed, rollback is defined, monitoring is active, and owners are available.

## 3.12.69 Abort Criteria

Abort or pause when lock waits threaten the application, disk free space falls below threshold, replication lag breaches SLO, WAL archive backs up, application latency degrades materially, or unexpected invalid/corrupt index states appear.

## 3.12.70 Failure Scenario — Blocking Build

A standard `CREATE INDEX` blocks writes on a busy table. Recovery is to cancel the build, confirm lock release, evaluate partial work, and reschedule with `CREATE INDEX CONCURRENTLY` if availability requires it.

## 3.12.71 Failure Scenario — Concurrent Build Saturates I/O

A concurrent build can saturate storage and degrade the workload. Mitigate by scheduling during lower traffic, tuning maintenance resources, limiting concurrent maintenance, and aborting when SLOs are threatened.

## 3.12.72 Failure Scenario — Build Waits for Old Transaction

Concurrent builds can wait for old transactions. Identify the blocking transaction, coordinate safely with application owners, and terminate only according to incident policy.

## 3.12.73 Failure Scenario — Invalid Index After Cancellation

Cancellation of a concurrent build can leave an invalid index. Detect it, drop it concurrently when eligible, fix the root cause, and retry only after new preflight checks.

## 3.12.74 Failure Scenario — Failed Concurrent UNIQUE Build

Duplicate data can cause a concurrent unique build to fail after expensive work. Precheck duplicates, define cleanup steps, and treat leftover invalid unique indexes carefully.

## 3.12.75 Failure Scenario — Disk Exhaustion

Index builds and rebuilds can exhaust disk. Recovery includes canceling work if necessary, freeing space, validating database health, checking replicas and archiving, and rescheduling with capacity controls.

## 3.12.76 Failure Scenario — Replica Lag Explosion

A large index build can generate WAL faster than replicas replay it. Monitor lag continuously, pause downstream-sensitive activity if needed, and avoid failover until replicas are consistent with the recovery plan.

## 3.12.77 Failure Scenario — Blind Automation Retry

Automation that retries failed index work without state inspection can repeat failures or amplify damage. Automation must inspect invalid indexes, locks, capacity, and previous errors before retrying.

## 3.12.78 Failure Scenario — Too Many Indexes

Adding indexes for every slow query can degrade writes and maintenance. Establish review standards, require evidence, and retire unused or redundant indexes through quarantine.

## 3.12.79 Failure Scenario — Planner Ignores Index

If the planner ignores a new index, check selectivity, stale statistics, correlation, predicate mismatch, operator class, collation, cost settings, parameterization, and whether the query actually benefits.

## 3.12.80 Failure Scenario — idx_scan = 0 Drop

Dropping an index solely because `idx_scan = 0` can break rare but critical workloads or constraints. Use a full workload cycle and dependency review before removal.

## 3.12.81 Failure Scenario — REINDEX Runs Out of Space

Concurrent rebuilds may require space for both old and new indexes. If space runs out, stop work, clean up safely, verify invalid objects, and revise capacity estimates.

## 3.12.82 Failure Scenario — Maintenance Window Ends

If an index build exceeds the window, decide whether to continue or cancel based on current phase, blocking risk, resource pressure, replica lag, and rollback cost.

## 3.12.83 Failure Scenario — Corruption

Index corruption requires incident handling. Confirm symptoms, avoid unsafe repeated retries, check replicas and backups, run integrity tooling where safe, and repair with `REINDEX` or failover/recovery as appropriate.

## 3.12.84 Production Deployment Workflow

A production deployment should include change ticket, reviewed SQL, preflight, owner confirmation, session guardrails, execution, progress monitoring, application checks, plan verification, replica checks, documentation update, and post-change observation.

## 3.12.85 Monitoring Matrix

| Area | Signals |
| --- | --- |
| Build progress | `pg_stat_progress_create_index` phase and counters |
| Locks | waiting sessions, blockers, lock modes |
| Workload | latency, errors, throughput |
| Storage | free space, IOPS, queue depth |
| WAL | generation, archive backlog |
| Replication | write/flush/replay lag, slots |
| Index health | invalid indexes, size, bloat, corruption checks |

## 3.12.86 Production Alerting

Alert on blocked DDL, long-running index builds, invalid indexes, disk thresholds, replication lag, WAL archive backlog, unexpected application latency increase, and failed maintenance automation.

## 3.12.87 Common Production Anti-Patterns

Common anti-patterns include creating indexes without plan evidence, adding indexes for every query, ignoring write cost, using standard builds on hot tables, dropping `idx_scan = 0` indexes blindly, ignoring replica lag, failing to clean invalid indexes, and automating retries without state checks.

## 3.12.88 SRE/DBRE Production Standard

Every production index must have a purpose, owner, expected workload, verified plan, deployment method, rollback plan, monitoring plan, and retirement criteria. Index work is a reliability change and should follow production change-management discipline.

## 3.12.89 Key Takeaways

Indexes improve reads but impose write, storage, WAL, cache, vacuum, and replication costs. Access method and operator class matter. Concurrent operations reduce blocking but add complexity. Invalid indexes, corruption, replica lag, and over-indexing are operational risks. Evidence-based design and lifecycle management are the SRE/DBRE standard.

## 3.12.90 Final Production Standard

PostgreSQL index administration must be treated as an end-to-end production lifecycle: design only for proven workloads, deploy with safe DDL patterns, monitor during and after execution, maintain based on evidence, recover deliberately from failed builds or corruption, and retire indexes only after dependency and workload validation.
