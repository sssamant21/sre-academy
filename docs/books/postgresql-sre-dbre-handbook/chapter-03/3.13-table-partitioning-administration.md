## 3.13.1 Purpose and Operational Context

PostgreSQL declarative partitioning divides one logical table into multiple physical relations according to a partition key.

                   orders
              Partitioned Table
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
 orders_2026_01 orders_2026_02 orders_2026_03
        │            │            │
     Physical     Physical     Physical
      Table        Table        Table

Rows inserted through the partitioned parent are routed to an appropriate leaf partition.

Partitioning can provide major operational advantages for:

large tables;
time-series/event workloads;
predictable data lifecycle and retention;
query partition pruning;
archival;
partition-level maintenance;
controlled removal of historical data.

However:

Partitioning is not automatically a performance optimization.

A badly chosen partition key or excessive number of partitions can increase planning cost, memory consumption, catalog complexity, DDL complexity, and operational risk.

The decision to partition must therefore be driven by measurable workload requirements.

## 3.13.2 When to Partition

Strong candidates commonly exhibit several characteristics:

Large and continuously growing table
             +
Queries naturally restrict a partition key
             +
Predictable data lifecycle
             +
Large maintenance operations
             +
Retention/archival requirements

Example:

orders = 5 TB
growth = 150 GB/month

Queries:
  mostly last 7–30 days

Retention:
  7 years

Monthly range partitioning may provide a useful operational boundary.

Partitioning should not be introduced merely because a table contains millions of rows.

Before partitioning, evaluate whether the problem can instead be solved through:

Correct indexes
Query optimization
Statistics
Autovacuum tuning
Storage/capacity improvements
Schema improvements
## 3.13.3 Declarative Partitioning Strategies

PostgreSQL provides three primary declarative partitioning methods:

                 PARTITION BY
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        RANGE        LIST        HASH
RANGE

Best suited to ordered ranges such as:

Date
Timestamp
Sequence ranges
Business periods
LIST

Best suited to discrete categories such as:

Region
Country
Business unit
Tenant category
HASH

Useful when relatively even distribution is desired and range-based lifecycle management is not the primary requirement.

## 3.13.4 RANGE Partitioning

Example:

CREATE TABLE orders (
    order_id      bigint NOT NULL,
    customer_id   bigint NOT NULL,
    order_date    date NOT NULL,
    amount        numeric(12,2)
)
PARTITION BY RANGE (order_date);

Create partitions:

CREATE TABLE orders_2026_01
PARTITION OF orders
FOR VALUES FROM ('2026-01-01')
           TO ('2026-02-01');

CREATE TABLE orders_2026_02
PARTITION OF orders
FOR VALUES FROM ('2026-02-01')
           TO ('2026-03-01');

Range boundaries are:

FROM = inclusive
TO   = exclusive

Therefore:

2026-01-01 <= order_date < 2026-02-01

belongs to orders_2026_01.

Using exclusive upper bounds is particularly useful for contiguous calendar partitions.

## 3.13.5 Multi-Column RANGE Partitioning

PostgreSQL permits multiple partition-key columns.

Example:

CREATE TABLE measurements (
    region_id    integer,
    measured_at  timestamptz,
    value        numeric
)
PARTITION BY RANGE (region_id, measured_at);

Multi-column range boundaries follow the ordering semantics of the combined partition key. They should not be interpreted as independent rectangular ranges for each column.

Because these definitions are easier to misunderstand and automate incorrectly, use them only when the workload genuinely requires them.

## 3.13.6 LIST Partitioning

Example:

CREATE TABLE customer_events (
    event_id    bigint,
    region      text,
    event_time  timestamptz NOT NULL
)
PARTITION BY LIST (region);

Partitions:

CREATE TABLE customer_events_us
PARTITION OF customer_events
FOR VALUES IN ('US');

CREATE TABLE customer_events_ca
PARTITION OF customer_events
FOR VALUES IN ('CA');

CREATE TABLE customer_events_uk
PARTITION OF customer_events
FOR VALUES IN ('UK');

LIST partitioning is useful when the domain consists of a manageable number of known categories.

Avoid designs that create a separate partition for extremely high-cardinality values without a demonstrated operational reason.

## 3.13.7 NULL Partition Keys

Nullable partition keys require explicit design.

For example, LIST partitioning can explicitly accommodate NULL:

CREATE TABLE customer_events_unknown
PARTITION OF customer_events
FOR VALUES IN (NULL);

Alternatively, a DEFAULT partition may handle values not mapped to another explicit partition where applicable.

Production design must answer:

Can partition key be NULL?
       │
   ┌───┴────┐
  NO       YES
   │         │
NOT NULL   Explicit routing strategy

Never discover nullable partition-key behavior through an ingestion failure.

## 3.13.8 HASH Partitioning

Example:

CREATE TABLE customer_activity (
    customer_id bigint NOT NULL,
    event_time  timestamptz NOT NULL,
    payload     jsonb
)
PARTITION BY HASH (customer_id);

Four partitions:

CREATE TABLE customer_activity_p0
PARTITION OF customer_activity
FOR VALUES WITH (MODULUS 4, REMAINDER 0);

CREATE TABLE customer_activity_p1
PARTITION OF customer_activity
FOR VALUES WITH (MODULUS 4, REMAINDER 1);

CREATE TABLE customer_activity_p2
PARTITION OF customer_activity
FOR VALUES WITH (MODULUS 4, REMAINDER 2);

CREATE TABLE customer_activity_p3
PARTITION OF customer_activity
FOR VALUES WITH (MODULUS 4, REMAINDER 3);

Conceptually:

               customer_activity
                      │
             HASH(customer_id)
                      │
          ┌──────┬────┴────┬──────┐
          ▼      ▼         ▼      ▼
         p0     p1        p2     p3

Hash partitioning can provide useful distribution, but it is generally less natural for time-based archival and retention.

## 3.13.9 Selecting the Partition Key

The partition key is the most important architectural decision.

It should align with:

Query predicates
Data lifecycle
Retention
Data distribution
Maintenance boundaries
Application behavior

Example:

SELECT *
FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '7 days';

Partitioning by order_date can allow PostgreSQL to eliminate irrelevant historical partitions.

Partitioning the same table by an unrelated key may provide little benefit for this workload.

Canonical Rule

Choose the partition key from observed query and lifecycle patterns—not merely from cardinality or perceived distribution.

## 3.13.10 Partition-Key Stability

A good partition key is normally relatively stable.

PostgreSQL permits an UPDATE that changes the partition key. If the new value belongs to another partition, the row can move between partitions.

Partition A
    │
UPDATE partition key
    │
    ▼
Partition B

This affects:

Concurrency
Triggers
WAL
Logical replication
CDC
Application behavior

Before selecting a mutable column as a partition key, test the complete write path.

## 3.13.11 Partition-Key Expressions

Partition keys may use supported expressions, but expression-based partitioning increases complexity around:

Query predicates
Pruning
Constraint design
Uniqueness
Automation
Troubleshooting

Prefer simple partition keys unless an expression solves a clearly demonstrated requirement.

## 3.13.12 Partition Granularity

Time-based partitioning commonly requires choosing among:

Hourly
Daily
Weekly
Monthly
Quarterly
Yearly

Suppose ten years of data are retained:

Daily   ≈ 3,650 partitions
Monthly ≈   120 partitions
Yearly  ≈    10 partitions

Too coarse can mean:

Large indexes
Large maintenance units
Less precise retention
More data scanned per relevant partition

Too fine can mean:

Excessive relation count
More indexes
Planning overhead
Catalog overhead
Automation complexity

There is no universal PostgreSQL partition-size or partition-count target.

Choose granularity using measurements.

## 3.13.13 Future Partition Count Is a Capacity Dimension

Do not benchmark only today's hierarchy.

If:

Current partitions = 100

but retention eventually produces:

Projected partitions = 5,000

test the projected state.

Partition count interacts with:

Indexes
Planning
Backend memory
DDL
Monitoring
Backup
Restore
Catalog operations

A system that performs well during year one may behave very differently at maximum retention.

## 3.13.14 Time-Zone Architecture

Every time-based partition design must define:

Partition-key data type
Partition-bound timezone
Automation timezone
Business/reporting timezone

Example:

Column:      event_time timestamptz
Bounds:      UTC
Automation:  UTC
Reporting:   America/New_York

UTC is often operationally simpler, but business requirements may require another model.

Whatever model is chosen must be explicit and consistent.

## 3.13.15 Calendar Boundary Safety

Partition automation must correctly handle:

February 28
February 29
30-day months
31-day months
Year boundaries
DST spring transition
DST fall transition

Do not assume:

CURRENT_TIMESTAMP + INTERVAL '30 days'

means "next calendar month."

Calculate calendar boundaries explicitly.

## 3.13.16 DEFAULT Partition

A DEFAULT partition receives rows that do not match another explicit partition.

CREATE TABLE orders_default
PARTITION OF orders
DEFAULT;

Architecture:

Incoming row
     │
     ▼
Explicit partition match?
     │
 ┌───┴───┐
YES      NO
 │        │
 ▼        ▼
Partition DEFAULT

A DEFAULT partition can protect ingestion from missing-partition failures.

But it can also hide broken automation.

Production Principle

Treat DEFAULT as an exception queue, not as permanent uncontrolled storage.

For strictly managed time-based hierarchies, the expected row count may often be zero.

## 3.13.17 DEFAULT Partition Monitoring

Monitor:

Row count
Total size
Growth rate
Minimum partition key
Maximum partition key

Unexpected growth may indicate:

Missing future partition
Incorrect bound
Automation failure
Unexpected source data

A rapidly growing DEFAULT partition should be treated as a partition-management incident.

## 3.13.19 Partition Pruning

Partition pruning allows PostgreSQL to eliminate irrelevant partitions.

Example:

SELECT *
FROM orders
WHERE order_date >= DATE '2026-02-01'
  AND order_date <  DATE '2026-03-01';

Instead of scanning:

Jan
Feb
Mar
Apr
...

PostgreSQL may need only:

Feb

Conceptually:

Query predicate
      │
      ▼
Partition bounds
      │
      ▼
Prune irrelevant partitions
      │
      ▼
Access relevant partitions
## 3.13.20 Pruning Is Not Indexing

These solve different problems.

Partition pruning
       │
       ▼
Which partitions?

Index selection
       │
       ▼
How are rows found inside them?

A query can successfully prune to one 500-GB partition and still perform an expensive sequential scan.

Partitioning does not eliminate the need for good indexing.

## 3.13.21 Plan-Time and Execution-Time Pruning

Pruning may occur at different stages.

Plan-time pruning
       │
       ▼
Partitions removed during planning

Execution-time pruning
       │
       ▼
Partitions removed when parameter
values become available

Execution-time pruning is especially relevant for parameterized plans and prepared statements.

## 3.13.22 Verify Pruning

Never assume pruning works.

Use:

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE order_date >= DATE '2026-02-01'
  AND order_date < DATE '2026-03-01';

Inspect:

Partitions/subplans accessed
Planning time
Execution time
Rows
Buffers
Index access

Test the SQL actually generated by the application—not merely simplified DBA test queries.

## 3.13.23 Prepared Statements and Application Plans

Applications commonly use:

Prepared statements
ORM-generated SQL
Connection pools
Parameterized queries

Therefore test:

Literal SQL
Prepared SQL
Real application SQL
Generic/custom planning behavior
Execution-time pruning

A query that performs perfectly with literals in psql does not prove the production application will behave identically.

## 3.13.24 Partition-Wise Join and Aggregation

PostgreSQL can use partition-wise joins and partition-wise aggregation for suitable workloads.

Relevant planner controls include:

enable_partitionwise_join
enable_partitionwise_aggregate

Conceptually:

Table A              Table B
 Jan ─────────────── Jan
 Feb ─────────────── Feb
 Mar ─────────────── Mar

Partition-wise processing can improve some workloads, but may increase planning time and memory requirements.

Enable or tune these features based on measured workload behavior.

## 3.13.25 Sub-Partitioning

A partition may itself be partitioned.

Example:

orders
 │
 ├── 2026
 │    ├── Jan
 │    ├── Feb
 │    └── Mar
 │
 └── 2027
      ├── Jan
      ├── Feb
      └── Mar

Or:

orders
 │
 ├── US
 │    ├── Jan
 │    └── Feb
 │
 └── EU
      ├── Jan
      └── Feb

Sub-partition only when it provides a demonstrated benefit. Every hierarchy level increases operational complexity.

## 3.13.26 Partitioned Index Architecture

An index defined on a partitioned parent represents an index hierarchy.

Partitioned index
       │
       ├── Child index — Jan
       ├── Child index — Feb
       └── Child index — Mar

Actual index storage resides on the physical partitions.

Example:

CREATE INDEX idx_orders_customer
ON orders (customer_id);

Index consistency across all leaf partitions is a production invariant.

## 3.13.27 Production Index Creation

A critical limitation is that a concurrent index build cannot simply be performed as one CREATE INDEX CONCURRENTLY operation across the partitioned parent.

For large existing hierarchies, use the documented pattern where appropriate:

Create parent index ON ONLY
          │
          ▼
Parent initially invalid
          │
          ▼
CREATE INDEX CONCURRENTLY
on individual partitions
          │
          ▼
Validate child indexes
          │
          ▼
ATTACH PARTITION indexes
          │
          ▼
Parent becomes valid

For hundreds or thousands of partitions, automate this as a resumable workflow.

## 3.13.28 Index Health

Do not assume:

Index exists = Index healthy

Inspect index state where appropriate, including:

indisvalid
indisready

A failed concurrent build can leave an index object that is not operationally healthy.

Monitor:

Missing indexes
Invalid indexes
Definition drift
Unattached indexes
## 3.13.29 PRIMARY KEY and UNIQUE Constraints

Partitioned uniqueness has important restrictions.

A unique or primary-key constraint intended to enforce uniqueness across a partitioned table must satisfy PostgreSQL's requirements concerning the partition key.

Example:

PARTITION BY RANGE(order_date)

An application requiring globally unique:

order_id

must validate whether the desired constraint can be represented directly.

A design may require:

PRIMARY KEY (order_id, order_date)

depending on the schema.

This can affect application semantics.

## 3.13.30 Global Index Limitation

PostgreSQL does not provide a general-purpose global index spanning all partitions in the same sense offered by some other database platforms.

This affects:

Global uniqueness
Primary-key architecture
Cross-partition lookups
Migration from Oracle/other systems
Application assumptions

Resolve global uniqueness requirements before migrating a production table to partitioning.

## 3.13.31 Foreign Keys

Partitioned-table designs must explicitly test referential integrity.

Example:

orders
   ▲
   │ FK
order_items

A retention operation against an old orders partition may interact with dependent data.

Before implementing partition-based retention, validate:

FK dependency graph
Detach behavior
Drop behavior
Locking
Dependent retention
Recovery

Partition lifecycle and referential lifecycle must agree.

## 3.13.32 Triggers and Row Movement

Triggers require testing across:

Parent
Leaf partitions
INSERT routing
Partition-key UPDATE
Row movement

Do not infer current declarative-partition trigger behavior from old inheritance-based partitioning implementations.

Use the exact deployed PostgreSQL version during certification.

## 3.13.33 Attach an Existing Table

A standalone table can be prepared and attached.

Create standalone table
        │
        ▼
Load data
        │
        ▼
Create indexes
        │
        ▼
Create matching CHECK constraint
        │
        ▼
Validate
        │
        ▼
ATTACH PARTITION

Example:

ALTER TABLE orders
ATTACH PARTITION orders_2026_09
FOR VALUES FROM ('2026-09-01')
           TO ('2026-10-01');
## 3.13.34 Avoid Expensive ATTACH Validation

Without proof that the candidate data satisfies its new partition bound, PostgreSQL may need to scan the table during attachment.

A matching validated CHECK constraint can allow PostgreSQL to avoid such a scan when it proves the required condition.

For a multi-hundred-GB partition, this difference can be operationally significant.

Production Pattern
Standalone partition
        │
        ▼
Matching CHECK constraint
        │
        ▼
Validate before change window
        │
        ▼
ATTACH
## 3.13.35 DEFAULT Partition and ATTACH

If a DEFAULT partition exists, adding a new explicit partition may require PostgreSQL to verify that the DEFAULT partition does not contain conflicting rows.

A massive DEFAULT partition can therefore turn a seemingly simple attach into an expensive operation.

Before ATTACH:

Inspect DEFAULT
Validate candidate
Validate bounds
Validate locks

## 3.13.37 Fail Fast Rather Than Block Indefinitely

For automated maintenance, a safer model is often:

Try DDL
   │
   ▼
Lock unavailable within budget?
   │
 ┌─┴─┐
NO  YES
│     │
Run  Abort
      │
      ▼
    Alert
      │
      ▼
  Retry safely

The appropriate lock budget is workload-specific.

## 3.13.38 DETACH Partition

A partition can be separated from the hierarchy:

ALTER TABLE orders
DETACH PARTITION orders_2020_01;

Lifecycle:

Partitioned hierarchy
        │
        ▼
DETACH
        │
        ▼
Standalone table
        │
        ├── Validate
        ├── Archive
        ├── Backup
        └── Recover if necessary

This provides a useful recovery boundary.

## 3.13.39 Concurrent DETACH

Supported PostgreSQL versions provide concurrent detach capabilities with documented restrictions.

Where applicable:

ALTER TABLE orders
DETACH PARTITION orders_2020_01
CONCURRENTLY;

Do not assume it is valid for every hierarchy or configuration.

Validate behavior against the exact PostgreSQL major version.

## 3.13.40 Interrupted Concurrent DETACH

Concurrent detach may involve an intermediate state.

Supported versions provide finalization semantics such as:

ALTER TABLE orders
DETACH PARTITION orders_2020_01
FINALIZE;

SRE runbooks must include interrupted-operation recovery.

## 3.13.41 DROP Partition

Historical data can be removed structurally:

DROP TABLE orders_2020_01;

Compared with:

DELETE FROM orders
WHERE order_date >= DATE '2020-01-01'
  AND order_date <  DATE '2020-02-01';

partition removal can avoid enormous row-level deletion work, dead tuples, subsequent vacuum cleanup, and index cleanup.

However:

Fast data removal does not mean lock-free data removal.

Understand the exact lock requirements before production execution.

## 3.13.42 Safe Retention Architecture

For important datasets, prefer:

Retention candidate
       │
       ▼
Read actual catalog bound
       │
       ▼
Compare retention cutoff
       │
       ▼
Check dependencies
       │
       ▼
DETACH
       │
       ▼
Validate
       │
       ▼
Archive / quarantine
       │
       ▼
DROP

Never decide destructive retention from a partition name alone.

## 3.13.43 Two Independent Destructive Checks

Before removal, validate independently:

Actual partition bound
          +
Retention policy cutoff

Example danger:

Table name:
orders_2020_01

Actual catalog bound:
2026-01-01 → 2026-02-01

Name-based automation could destroy current data.

Canonical Rule

Destructive partition automation must fail closed.

## 3.13.44 Quarantine Before DROP

For high-value datasets, consider:

DETACH
   │
   ▼
Quarantine interval
   │
   ▼
DROP

The interval should be determined from recovery requirements, storage cost, and business criticality.

This provides time to discover an incorrect retention action before physical destruction.

## 3.13.45 Separate Provisioning and Retention Automation

Prefer separate control paths:

Partition Provisioner
       │
       └── CREATE / validation

Partition Retention Controller
       │
       └── DETACH / archive / DROP

This reduces blast radius.

Where practical, use separate database privileges as well.

A partition creator does not inherently need destructive retention privileges.

## 3.13.46 Idempotent Automation

Every lifecycle operation should tolerate retries.

Calculate desired state
       │
       ▼
Read catalog
       │
       ▼
Compare actual state
       │
       ▼
Already correct?
    ┌──┴──┐
   YES    NO
    │      │
 Verify   Change
           │
           ▼
         Verify

Automation should never infer success merely from an object name.

## 3.13.47 Single-Flight Automation

Avoid multiple controllers modifying the same hierarchy simultaneously.

Potential collision:

Controller A ── CREATE
                    ▲
                    │
Controller B ───────┘

Likewise, provisioning and retention should not unexpectedly collide.

Use orchestration or carefully designed locking where appropriate.

## 3.13.48 Future Partition Runway

Do not wait until a partition is required.

Example policy:

Current month
    │
    ├── September
    ├── October
    ├── November
    └── December

Maintain multiple future partitions according to the workload's risk tolerance.

Monitor the remaining runway.

Example:

90 days → Healthy
60 days → Warning
30 days → Critical
0 days  → Incident

These are examples; define actual thresholds from the production SLO.

## 3.13.51 Autovacuum and Partition Lifecycle

Partitions frequently have different activity profiles:

HOT
 │
 ├── Heavy INSERT/UPDATE
 ├── Frequent ANALYZE
 └── Active vacuum

WARM
 │
 ├── Limited changes
 └── Moderate maintenance

COLD
 │
 ├── Business data effectively immutable
 └── Freeze/health maintenance still required

Tune maintenance according to measured lifecycle behavior.

## 3.13.52 Historical Partitions Are Not Maintenance-Free

A read-only business partition still participates in PostgreSQL transaction-ID management.

Monitor:

relfrozenxid age
Autovacuum state
Anti-wraparound activity

Do not casually disable autovacuum on historical partitions.

Cold does not mean exempt from database health maintenance.

## 3.13.53 Partition Size Monitoring

Track:

Partition
Rows
Table size
Index size
Total size
Growth/day
Dead tuples
Last vacuum
Last analyze
Freeze age

Example:

SELECT
    c.oid::regclass AS partition_name,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class AS c
JOIN pg_inherits AS i
  ON i.inhrelid = c.oid
WHERE i.inhparent = 'orders'::regclass
ORDER BY pg_total_relation_size(c.oid) DESC;

There is no universal PostgreSQL recommendation that every partition must be a particular number of gigabytes.

Define internal targets from operational requirements.

## 3.13.55 Catalog-Based Inventory

pg_class

pg_index

Canonical Principle

## 3.13.56 Planning Scalability

A large number of partitions can increase planning overhead.

Example:

Execution Time = 20 ms
Planning Time  = 400 ms

The execution plan may look efficient while user-facing latency remains poor.

Monitor both.

Capacity tests should also include concurrent sessions because plan structures can amplify backend memory consumption.

A production migration commonly resembles:

Existing table
      │
      ▼

      │
      ▼
Create new parent/partitions
      │
      ▼
Backfill / attach
      │
      ▼
Synchronize new writes
      │

## 3.13.80 Canonical Engineering Principles
Partition only to solve a demonstrated problem.
Prefer declarative partitioning.
Select the partition key from real query and lifecycle patterns.
Prefer stable partition keys.
Choose granularity using measured workload behavior.
Model the mature hierarchy, not only today's partition count.
Define explicit timezone semantics for time-based partitioning.
Test calendar, DST, leap-day, and year boundaries.
Treat DEFAULT as an exception path.
Monitor DEFAULT continuously.
Verify pruning rather than assuming it.
Test real application and prepared SQL.
Distinguish pruning from indexing.
Monitor planning time as well as execution time.
Maintain consistent indexes across every leaf.
Detect invalid indexes, not merely missing indexes.
Resolve global uniqueness before implementation.
Validate FK and trigger behavior.
Understand row movement caused by partition-key updates.
Prevalidate large candidate partitions before ATTACH.
Understand lock behavior for every lifecycle DDL operation.
Fail automated DDL safely when lock budgets are exceeded.
Prefer DETACH before destructive DROP when recovery requirements justify it.
Validate actual catalog bounds before retention.
Make destructive automation fail closed.
Separate provisioning and destructive lifecycle permissions where practical.
Maintain future partition runway.
Alert before coverage is exhausted.
Make automation idempotent.
Avoid uncontrolled concurrent lifecycle controllers.
Maintain an automation audit trail.
Treat parent and leaf statistics deliberately.
Maintain vacuum and freeze health across historical partitions.
Monitor size, growth, skew, and count.
Validate WAL and replica impact.
Explicitly certify logical replication and CDC.
Define downstream semantics for structural retention.
Test backup and restore at representative future scale.
Validate routing and pruning after restore.
Verify automation after DR promotion.
Treat migration to partitioning as a production migration.
Reconcile data before cutover completion.
Maintain a tested rollback boundary.
Inject failures into partition automation before production.
Maintain dashboards, alerts, SLOs, and an incident runbook.
