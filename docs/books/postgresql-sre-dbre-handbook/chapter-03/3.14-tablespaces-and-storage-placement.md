# 3.14 — Tablespaces and Storage Placement
**Edition:** Revised Final / Canonical Edition
**Chapter:** 3 — PostgreSQL Database and Object Administration
**Status:** COMPLETE — CANONICAL EDITION
**Validated scope:** PostgreSQL 14–18
**Audience:** PostgreSQL DBA, DBRE, SRE, Platform Engineer

This canonical edition incorporates the Draft, Technical Review, and Production Review findings. It treats tablespaces not simply as SQL objects, but as part of the PostgreSQL storage, availability, backup, replication, disaster-recovery, and operational reliability architecture.

## 3.14.1 Tablespace Architecture

A PostgreSQL tablespace is a cluster-wide database object that associates PostgreSQL storage with a filesystem location selected by the administrator.

PostgreSQL identifies two principal reasons for tablespaces: extending storage when the original filesystem becomes constrained, and placing objects on storage with different performance characteristics.

Conceptually:

PostgreSQL Cluster
        │
        ├── pg_default
        │       └── PGDATA/base
        │
        ├── pg_global
        │       └── PGDATA/global
        │
        └── User Tablespaces
                │
                ├── data_hot
                ├── index_hot
                ├── archive_ts
                └── temp_ts

The fundamental abstraction is:

Database object
      │
      ▼
Tablespace
      │
      ▼
Filesystem
      │
      ▼
Volume / Storage System

A tablespace therefore provides placement, not storage performance by itself.

## 3.14.2 The Reliability Boundary

This is the most important production principle:

A tablespace may live outside PGDATA, but it remains an integral part of the PostgreSQL cluster.

User-defined tablespaces depend on metadata stored in the primary data directory. PostgreSQL warns that tablespaces cannot be treated as independent collections of files, cannot simply be attached to another cluster, and cannot be backed up independently. Loss of a tablespace can make the cluster unreadable or prevent startup.

Therefore:

PostgreSQL Reliability Boundary
             │
             ├── PGDATA
             ├── WAL
             ├── data_hot
             ├── index_hot
             └── archive_ts

Every persistent tablespace must satisfy the cluster's durability, availability, monitoring, backup, HA, and recovery requirements.

## 3.14.3 Built-In Tablespaces

Every PostgreSQL cluster contains:

pg_default
pg_global

pg_default is the default storage location for ordinary database objects when another tablespace has not been selected.

Its underlying cluster storage normally resides beneath:

PGDATA/base

pg_global contains cluster-wide system relations and corresponds to:

PGDATA/global

These are PostgreSQL-managed built-in tablespaces and should not be treated as ordinary administrator-created tablespaces.

## 3.14.4 User-Defined Tablespace Physical Layout

Example:

CREATE TABLESPACE data_hot
LOCATION '/postgres/data_hot';

Internally:

pg_tablespace
      │
      ▼
Tablespace OID
      │
      ▼
PGDATA/pg_tblspc/<OID>
      │
      ▼
Symbolic link
      │
      ▼
/postgres/data_hot

PostgreSQL uses symbolic links beneath PGDATA/pg_tblspc for user-defined tablespaces.

The physical directory therefore exists outside PGDATA, while PostgreSQL retains the cluster metadata necessary to interpret it.

## 3.14.5 Creating a Tablespace

First provision the storage at the operating-system layer.

Example:

mkdir -p /postgres/data_hot
chown postgres:postgres /postgres/data_hot
chmod 700 /postgres/data_hot

Then:

CREATE TABLESPACE data_hot
LOCATION '/postgres/data_hot';

Production preflight:

Absolute path                     ✓
Directory exists                  ✓
Directory empty                   ✓
Correct OS owner                  ✓
Permissions validated             ✓
Correct filesystem mounted        ✓
Expected device mounted           ✓
Storage persistent                ✓
Capacity validated                ✓
Performance tier validated        ✓
Monitoring enabled                ✓
Backup coverage established       ✓
HA/DR design established          ✓

CREATE TABLESPACE cannot execute inside a transaction block.

That matters for migration frameworks that automatically issue:

BEGIN;

CREATE TABLESPACE ...;

COMMIT;

Such automation must execute tablespace creation outside its normal transactional DDL wrapper.

## 3.14.6 Naming and Ownership

Names beginning with:

pg_

are reserved for system tablespaces.

PostgreSQL tablespace ownership and filesystem ownership are separate concepts:

PostgreSQL tablespace owner
             ≠
Filesystem directory owner

The PostgreSQL role owns the database object.

The PostgreSQL operating-system account must have the required filesystem access.

Creating a tablespace requires superuser privileges, while use of an existing tablespace can subsequently be delegated.

Example:

GRANT CREATE
ON TABLESPACE data_hot
TO app_owner;

Apply least privilege.

Application runtime roles normally should not administer storage placement.

## 3.14.7 Cluster-Wide Scope

Tablespaces are cluster-wide objects rather than database-local objects.

Conceptually:

PostgreSQL Cluster
       │
       ├── database_A ──┐
       ├── database_B ──┼──► data_hot
       └── database_C ──┘

Consequently, checking one database is insufficient when determining whether a tablespace can be retired.

Inventory all databases before tablespace decommissioning.

## 3.14.8 Tablespace Inventory

List tablespaces:

SELECT
    oid,
    spcname,
    pg_get_userbyid(spcowner) AS owner,
    pg_tablespace_location(oid) AS location,
    pg_size_pretty(pg_tablespace_size(oid)) AS size
FROM pg_tablespace
ORDER BY spcname;

From psql:

\db

For operational monitoring, avoid unnecessarily aggressive polling of expensive storage-size functions on extremely large environments.

## 3.14.9 Creating Tables in a Tablespace
CREATE TABLE orders (
    order_id bigint,
    customer_id bigint,
    order_date date,
    amount numeric
)
TABLESPACE data_hot;

Placement becomes:

orders
   │
   ▼
data_hot
   │
   ▼
/postgres/data_hot

Verify:

SELECT
    c.relname,
    COALESCE(t.spcname, 'database default') AS tablespace
FROM pg_class c
LEFT JOIN pg_tablespace t
       ON t.oid = c.reltablespace
WHERE c.relname = 'orders';
## 3.14.10 Separating Table and Index Storage

Tables and indexes can occupy different tablespaces.

CREATE TABLE orders (
    order_id bigint,
    customer_id bigint,
    order_date date
)
TABLESPACE data_hot;
CREATE INDEX idx_orders_customer
ON orders(customer_id)
TABLESPACE index_hot;

Architecture:

orders
   │
   ▼
data_hot

idx_orders_customer
   │
   ▼
index_hot

This can be useful when the underlying storage tiers have genuinely different performance characteristics.

Do not separate indexes merely because the feature exists.

## 3.14.11 Constraint-Backed Indexes

Indexes supporting applicable constraints can also have deliberate tablespace placement.

For example, PostgreSQL supports constructs involving:

USING INDEX TABLESPACE index_hot

for supported PRIMARY KEY, UNIQUE, and exclusion-constraint index creation scenarios.

This matters when index storage is deliberately separated from heap storage.

## 3.14.12 Materialized Views and Auxiliary Storage

Storage inventory should not consider only ordinary tables.

Production capacity planning may need to include:

Tables
Indexes
Materialized views
Partitions
TOAST
TOAST indexes
Temporary objects

Large materialized views can consume significant storage and deserve explicit placement review.

## 3.14.13 TOAST-Aware Capacity Planning

Large PostgreSQL values can be moved into associated TOAST relations.

Therefore:

Visible table
     │
     ├── Heap
     ├── TOAST
     ├── Indexes
     └── TOAST indexes

Capacity planning for large relations should account for the complete physical footprint rather than only the visible heap.

This is particularly important for workloads containing:

jsonb
large text
arrays
documents
large payloads
## 3.14.14 default_tablespace

default_tablespace controls the default tablespace for eligible newly created persistent objects when an explicit TABLESPACE clause is absent.

SET default_tablespace = 'data_hot';

Then:

CREATE TABLE transactions (
    transaction_id bigint,
    created_at timestamptz
);

may use data_hot.

Placement logic:

Explicit TABLESPACE?
      │
   ┌──┴──┐
  YES    NO
   │      │
Use it   default_tablespace

If the configured tablespace does not exist, PostgreSQL can fall back to the database's default tablespace.

Avoid casually setting default_tablespace globally because future object placement can change without explicit DDL.

## 3.14.15 Temporary Tablespaces

Temporary objects are controlled separately through:

temp_tablespaces

not default_tablespace.

Example:

SET temp_tablespaces = 'temp01,temp02';

Temporary storage can include:

Temporary tables
Temporary indexes
Sort spill files
Hash spill files
Other temporary query files

When multiple temporary tablespaces are configured, PostgreSQL can distribute temporary objects/files among them.

Architecture:

Query
 │
 ├── Sort
 ├── Hash
 └── Temporary relation
          │
          ▼
    temp_tablespaces
       ┌──┴──┐
       ▼     ▼
    temp01 temp02
## 3.14.16 Temporary Storage Is Still a Production Dependency

A dedicated temporary tablespace can isolate temporary I/O, but it creates another resource that can become exhausted.

Monitor:

Temp bytes
Temp files
Free capacity
Growth
Read/write latency
IOPS
Throughput
Workload generating spills

Failure pattern:

Large query
    │
    ▼
Sort/hash spill
    │
    ▼
Temp filesystem
    │
    ▼
100% full
    │
    ▼
Query failures

Do not fix recurring temporary-space exhaustion only by expanding storage. Investigate the queries, concurrency, execution plans, and memory configuration generating the spills.

## 3.14.17 Database-Level Tablespace

A database can have its own default tablespace:

CREATE DATABASE analytics
TABLESPACE analytics_ts;

Conceptual precedence for object placement is:

Explicit object TABLESPACE
            │
            ▼
default_tablespace / temp_tablespaces
            │
            ▼
Database tablespace

default_tablespace itself does not determine where CREATE DATABASE places the database. Database creation has its own tablespace/template semantics.

## 3.14.18 Partitioned Tables and Tablespaces

Tablespaces integrate naturally with partition lifecycle management.

orders
 │
 ├── orders_2026_08 → hot_ts
 ├── orders_2026_07 → hot_ts
 ├── orders_2026_06 → warm_ts
 ├── orders_2025_12 → archive_ts
 └── orders_2025_11 → archive_ts

This enables storage tiering according to data lifecycle.

A partitioned parent contains no ordinary table data to physically move. Its tablespace can instead influence the default placement of subsequently created partitions.

An important operational subtlety is that a tablespace recorded on the partitioned parent can continue affecting future partitions even if session-level default_tablespace settings later change.

Therefore partition automation must validate actual placement, not merely current session configuration.

## 3.14.19 Hot / Warm / Cold Architecture

A self-managed PostgreSQL environment might deliberately use:

                     PostgreSQL
                         │
           ┌─────────────┼─────────────┐
           ▼             ▼             ▼
          HOT           WARM          COLD
           │             │             │
       Fast SSD      Standard SSD   Lower-cost
           │             │             │
     Current data     Older data    Historical

But:

Cold means lower access frequency or lower performance requirements—not disposable.

Durable PostgreSQL tablespaces still require reliable persistent storage.

## 3.14.20 Tablespaces Do Not Make Storage Faster

A tablespace named:

fast_ts

is not intrinsically fast.

Actual behavior is determined by:

Tablespace
    │
    ▼
Filesystem
    │
    ▼
Volume
    │
    ▼
Storage subsystem
    │
    ▼
Latency / IOPS / throughput

Multiple tablespaces residing on the same logical filesystem frequently provide little meaningful physical I/O isolation. PostgreSQL itself notes the limited value of using multiple tablespaces on a single logical filesystem for this purpose.

## 3.14.21 Tablespace-Specific Planner and I/O Parameters

PostgreSQL supports tablespace-specific configuration including:

seq_page_cost
random_page_cost
effective_io_concurrency
maintenance_io_concurrency

These can override corresponding global settings for objects stored in that tablespace.

Example:

ALTER TABLESPACE fast_ts
SET (
    random_page_cost = 1.1,
    effective_io_concurrency = 200
);

Those values are illustrative—not universal recommendations.

## 3.14.23 Moving a Table

Existing tables can be relocated:

ALTER TABLE orders
SET TABLESPACE archive_ts;

The table's data is moved to the destination tablespace.

Its indexes are not automatically moved with it.

Therefore:

ALTER TABLE ... SET TABLESPACE
            │
            ▼
        Table moves

Indexes
   │
   └── remain in their existing locations

This is a critical production distinction.

## 3.14.24 Moving an Index

Move an index independently:

ALTER INDEX idx_orders_customer
SET TABLESPACE index_hot;

This permits architectures such as:

Table  → standard storage
Index  → high-performance storage

provided measurements justify the additional complexity.

## 3.14.25 Bulk Tablespace Migration

## 3.14.26 Treat Large Moves as Production Events

A multi-terabyte tablespace move is not simply a metadata change.

Treat it as:

DDL
 +
Physical data movement
 +
Locking
 +
Storage workload
 +
WAL/replication consideration
 +
Application-risk event

Monitor during execution:

Storage latency
IOPS
Throughput
Queue depth
Application P95/P99
Lock waits
WAL generation
Replica lag
Destination free space

At normal production wal_level settings, storage-rewrite operations must remain compatible with the system's recovery/replication requirements. Do not assume a fixed WAL multiplier; measure the workload in the target environment.

## 3.14.27 Migration Abort Criteria

Define abort criteria before beginning.

Example:

Abort further migration if:

Application P99 > approved SLO
Replica lag > approved threshold
Storage latency > approved threshold
Critical lock wait > approved budget
Destination capacity < reserve
Storage errors detected

Exact values belong to the application's SLO and infrastructure policy.

## 3.14.28 Capacity Headroom

If:

Relation footprint = 2 TB
Destination free   = 2.1 TB

the move should not automatically be considered safe.

Account for:

Heap
TOAST
Indexes if moving
Concurrent growth
Temporary activity
Filesystem reserve
Operational headroom

Storage changes should never consume the destination to the edge of exhaustion.

## 3.14.31 Forecast-Based Alerting

Percentage thresholds are useful, but runway is often more valuable.

Example:

Free capacity = 500 GB
Growth        = 100 GB/day

Estimated runway ≈ 5 days

Compare:

Storage A:
88% used
Growth = 1 GB/day

Storage B:
65% used
Growth = 500 GB/day

Storage B may be the more urgent production risk.

Use:

Utilization
     +
Growth rate
     +
Time to exhaustion

rather than utilization alone.

## 3.14.35 Never Auto-Create Missing Tablespace Paths

If:

/postgres/data_hot

is missing, do not blindly execute:

mkdir -p /postgres/data_hot

and restart PostgreSQL.

The real issue could be:

Volume not attached
Mount failure
Storage outage
Filesystem corruption
Wrong host
DR mapping error

Recover the expected storage rather than manufacturing an empty replacement path.

## 3.14.36 Read-Only Filesystem Failure

Storage faults can result in a filesystem becoming read-only.

Storage/filesystem error
        │
        ▼
Filesystem read-only
        │
        ▼
PostgreSQL writes fail

Alert on:

Mount state
Unexpected read-only state
Filesystem errors
Kernel storage errors
Device errors

not just disk usage.

## 3.14.37 Physical Relation Location

Use PostgreSQL-supported functions rather than guessing relation paths.

SELECT pg_relation_filepath('orders');

The relation's filenode can change through operations such as rewrites or reindexing while the logical database object remains the same.

Do not build automation that assumes:

relation OID = permanent physical filename
## 3.14.38 pg_tblspc Safety

Do not manually alter tablespace symbolic links while PostgreSQL is running.

PostgreSQL explicitly warns against this.

Normal relocation:

PostgreSQL-supported DDL

Exceptional recovery:

Break-glass procedure
        │
        ▼
Peer review
        │
        ▼
PostgreSQL stopped
        │
        ▼
Offline storage/link work
        │
        ▼
Validation

Manual offline relocation is exceptional administration, not normal storage management.

## 3.14.39 Dropping a Tablespace

A tablespace must be empty before it can be dropped.

DROP TABLESPACE archive_ts;

Because tablespaces are cluster-wide, inventory all databases first.

Production workflow:

Candidate tablespace
       │
       ▼
Inventory all databases
       │
       ▼
Move/remove permanent objects
       │
       ▼
Check temporary use
       │
       ▼

       │
       ▼

       │
       ▼

       │
       ▼

       │

## 3.14.40 Physical Replication

Tablespace architecture is part of physical HA design.

Conceptually:

PRIMARY                       STANDBY
   │                             │
   ├── PGDATA                    ├── PGDATA
   ├── data_hot                  ├── data_hot
   ├── index_hot                 ├── index_hot
   └── archive_ts                └── archive_ts

A standby is not operationally ready merely because WAL streaming is healthy.

Failover testing must prove that required tablespace-backed relations remain accessible after promotion.

## 3.14.41 Logical Replication

Logical replication does not reproduce the publisher's physical filesystem architecture.

Therefore:

Publisher
table → archive_ts

does not imply:

Subscriber
table → archive_ts

Subscriber storage placement and capacity must be designed independently.

Failure example:

Publisher properly tiered
       │
       ▼
Logical changes replicated
       │
       ▼
Subscriber uses default storage
       │
       ▼
Default filesystem fills
## 3.14.42 Tablespaces and WAL Are Different Storage Concepts

Tablespaces place database relation storage.

They do not inherently relocate PostgreSQL WAL.

Conceptually:

PGDATA
  │
  ├── pg_wal
  ├── base
  └── pg_tblspc
          │
          └── User tablespace links

Do not conflate tablespace design with WAL-storage design.

## 3.14.43 Backup Architecture

Tablespaces cannot simply be backed up independently from the cluster.

A PostgreSQL-consistent backup must account for:

PGDATA
   +
All required tablespaces
   +
Required WAL

according to the backup method being used.

A backup system reporting:

SUCCESS

is insufficient unless tablespace coverage is known.

## 3.14.44 Multi-Volume Snapshot Consistency

Suppose:

PGDATA     → Volume A
data_hot   → Volume B
archive_ts → Volume C

Independent snapshots of A, B, and C at unrelated recovery points should not automatically be assumed to form a valid PostgreSQL backup.

Backup procedures must establish a PostgreSQL-consistent recovery point across all required storage and WAL.

A storage snapshot is a storage primitive. A PostgreSQL backup is a recoverable database state.

## 3.14.45 Tablespace-Aware Restore

Restore infrastructure may use different paths.

## 3.14.47 Expanded Failure Surface

Suppose:

PGDATA     → Volume A
data_hot   → Volume B
index_hot  → Volume C
archive_ts → Volume D

The workload may now depend on:

A + B + C + D

Tablespaces can improve capacity and performance isolation while increasing the number of infrastructure dependencies.

This tradeoff must be included in architecture review.

## 3.14.66 Production Best Practices
Use tablespaces only for demonstrated capacity, performance, or lifecycle requirements.
Treat every persistent tablespace as part of the PostgreSQL reliability boundary.
Document its underlying physical storage.
Validate the actual filesystem/device rather than directory existence.
Never automatically recreate a missing tablespace path.
Ensure required storage is mounted before PostgreSQL starts.
Keep durable PostgreSQL data on durable storage.
Monitor capacity, growth, and time to exhaustion.
Monitor storage latency and saturation.
Monitor read-only and filesystem-error conditions.
Include inode/file capacity where relevant.
Maintain desired-state object-placement policy.
Detect placement drift automatically.
Account for heap, indexes, TOAST, partitions, and auxiliary storage.
Remember that moving a table does not automatically move its indexes.
Treat large storage migrations as controlled production changes.
Define migration abort criteria beforehand.
Maintain destination capacity headroom.
Monitor WAL and replica lag during major moves.
Validate query plans after significant storage changes.
Benchmark tablespace-specific planner parameters.
Give temporary storage independent monitoring.
Inventory all databases before tablespace retirement.
Drop PostgreSQL dependencies before decommissioning storage.
Never manually delete relation files.
Never manipulate pg_tblspc while PostgreSQL is running.
Treat offline manual relocation as break-glass administration.
Include tablespaces in physical HA design.
Design logical-subscriber storage independently.
Make backup architecture tablespace-aware.
Prove multi-volume backup consistency.
Maintain restore-path mapping.
Test actual restores.
Validate all storage after failover.
Test Kubernetes secondary-volume behavior where applicable.
Use managed-service-native storage architecture.
Audit significant placement changes.
Maintain tablespace/storage SLOs.
Maintain a tested incident runbook.
Reassess whether tablespace complexity still provides measurable value.

## 3.14.68 Canonical Reliability Principle

The entire section can be reduced to one operational rule:

PostgreSQL tablespaces separate physical placement; they do not separate reliability responsibility.

A production tablespace is ready only when all of the following are understood and validated:

PostgreSQL metadata
        +
Object placement
        +
Filesystem
        +
Device / storage tier
        +
Capacity runway
        +
I/O performance
        +
Planner behavior
        +
WAL / replication
        +
Backup
        +
Restore
        +
HA / DR
        +
Monitoring
        +
Incident recovery

That is the DBRE/SRE standard for using tablespaces safely in production.
