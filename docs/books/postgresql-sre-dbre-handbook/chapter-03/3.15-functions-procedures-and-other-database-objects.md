## 3.15.1 Operational Purpose

PostgreSQL functions and procedures allow executable logic to live inside the database.

They must be treated simultaneously as:

Stored Routine
     │
     ├── Application code
     ├── Database object
     ├── Security interface
     ├── Transaction participant
     ├── Workload generator
     └── Operational dependency

A single routine can influence:

Correctness
Security
CPU
Memory
I/O
Locks
Transactions
WAL
Replication
Connection usage
Availability

Production rule: Treat stored routines as deployable production code executing inside PostgreSQL—not merely as SQL convenience wrappers.

## 3.15.2 Functions vs Procedures

PostgreSQL supports both functions and procedures.

Characteristic	Function	Procedure
Definition	CREATE FUNCTION	CREATE PROCEDURE
Typical invocation	SELECT, expressions, SQL statements	CALL
Function-style return value	Yes	No
OUT/INOUT parameters	Supported	Supported
SQL-expression use	Yes	No
Transaction termination	No	Possible only under qualifying rules
Typical purpose	Computation/query/API logic	Operational/workflow logic

Example function:

CREATE FUNCTION app.calculate_tax(
    p_amount numeric,
    p_rate numeric
)
RETURNS numeric
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT p_amount * p_rate;
$$;

Invocation:

SELECT app.calculate_tax(100, 0.07);

Procedure:

CREATE PROCEDURE maintenance.process_batch()
LANGUAGE plpgsql
AS $$
BEGIN
    -- operational logic
END;
$$;

Invocation:

CALL maintenance.process_batch();

## 3.15.4 Routine Identity

PostgreSQL supports overloading.

These can coexist:

app.lookup_customer(bigint)
app.lookup_customer(text)

Operational identity is based on:

Schema
  +
Routine name
  +
Input argument types

Use the complete identity when performing:

ALTER
DROP
GRANT
REVOKE
COMMENT
Dependency analysis
Troubleshooting

Do not identify production routines by name alone.

## 3.15.5 Output Parameters and Identity

Output parameters do not provide routine identity in the same way as input argument types.

Therefore operations against overloaded functions should use PostgreSQL's identity-argument representation.

For inventory:

SELECT
    n.nspname,
    p.proname,
    pg_get_function_identity_arguments(p.oid)
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace;

This avoids ambiguity in operational tooling.

## 3.15.6 Overloading Is Also a Security Concern

Function overloading
        │

## 3.15.7 Default-Argument Ambiguity

Consider:

    integer,
    integer DEFAULT 42
)

A call such as:

can become ambiguous.

Routine API evolution must therefore consider existing call-resolution behavior before introducing overloaded signatures or defaults.

## 3.15.11 SQL Functions

Prefer a simple SQL function when procedural logic is unnecessary.

CREATE FUNCTION reporting.total_customer_sales(
    p_customer_id bigint
)
RETURNS numeric
LANGUAGE sql
STABLE
AS $$
    SELECT COALESCE(sum(amount), 0)
    FROM app.sales
    WHERE customer_id = p_customer_id;
$$;

Avoid converting straightforward relational operations into unnecessarily complex PL/pgSQL.

## 3.15.12 PL/pgSQL

PL/pgSQL provides:

Variables
Conditionals
Loops
Dynamic SQL
Exceptions
Cursors
Diagnostics

Example:

CREATE FUNCTION app.customer_status(
    p_customer_id bigint
)
RETURNS text
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    v_status text;
BEGIN
    SELECT c.status
      INTO v_status
      FROM app.customers AS c
     WHERE c.customer_id = p_customer_id;

    RETURN v_status;
END;
$$;

Complexity inside the database should remain deliberate and supportable.

## 3.15.15 Volatility Categories

PostgreSQL supports:

VOLATILE
STABLE
IMMUTABLE
VOLATILE

The function may produce different results even within a statement and may have side effects.

VOLATILE is the default.

STABLE

The function promises that, for the same arguments, its result remains stable within a single statement, although it may change between statements.

IMMUTABLE

The function promises that the same arguments always produce the same result independent of database state.

Example:

CREATE FUNCTION app.celsius_to_fahrenheit(
    p_celsius numeric
)
RETURNS numeric
LANGUAGE sql
IMMUTABLE
AS $$
    SELECT (p_celsius * 9 / 5) + 32;
$$;
## 3.15.16 Side Effects Require VOLATILE

If a function has side effects, classify it appropriately as VOLATILE.

Do not declare:

STABLE
IMMUTABLE

merely to influence planner behavior.

Planner metadata describes truth; it is not a tuning knob to falsify.

## 3.15.17 Incorrect IMMUTABLE Is a Correctness Failure

        │
        ▼

        │
        ▼
Incorrect optimization
        │
        ▼

## 3.15.18 Null-Input Semantics

PostgreSQL supports:

CALLED ON NULL INPUT

as the normal/default behavior.

The function receives null arguments and must handle them.

Alternatively:

RETURNS NULL ON NULL INPUT

or:

STRICT

instructs PostgreSQL that applicable null input produces a null result without invoking the function.

Example:

CREATE FUNCTION app.safe_upper(text)
RETURNS text
LANGUAGE sql
IMMUTABLE
STRICT
AS $$
    SELECT upper($1);
$$;

Use STRICT only when semantically correct.

## 3.15.19 SECURITY INVOKER

The normal/default model is:

Caller
   │
   ▼
Routine
   │
   ▼
Caller privileges

Use SECURITY INVOKER when privilege elevation is unnecessary.

This should normally be the preferred security model.

## 3.15.20 SECURITY DEFINER

A SECURITY DEFINER function executes with the privileges of its owner.

Caller
   │
   ▼
SECURITY DEFINER
   │
   ▼
Owner privileges
   │
   ▼
Protected objects

This can provide a narrow privileged API.

It can also create a privilege-escalation path.

Every SECURITY DEFINER routine requires explicit security review.

## 3.15.21 Secure search_path

A privileged routine must not resolve objects through an unsafe search path.

A production pattern is:

CREATE FUNCTION secure.get_customer(
    p_customer_id bigint
)
RETURNS text
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, secure, pg_temp
AS $$
DECLARE
    v_name text;
BEGIN
    SELECT c.customer_name
      INTO v_name
      FROM app.customers AS c
     WHERE c.customer_id = p_customer_id;

    RETURN v_name;
END;
$$;

Application objects remain explicitly qualified.

The key security model is:

Trusted schemas
      │
      ▼
Explicit object resolution
      │
      ▼
pg_temp deliberately placed last
      │
      ▼
Reduced masking risk
## 3.15.22 search_path Alone Is Not Enough

Schema qualification
       +

## 3.15.23 Restrict PUBLIC EXECUTE

Sensitive routines should not rely on default execution privileges.

Use:

REVOKE ALL
ON FUNCTION secure.get_customer(bigint)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION secure.get_customer(bigint)
TO application_reader;

Use the complete routine identity.

## 3.15.24 Atomic Privileged-Routine Deployment

Where possible, create the routine and establish its security configuration in one transaction.

BEGIN;

CREATE FUNCTION secure.get_customer(bigint)
RETURNS text
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, secure, pg_temp
AS $$
...
$$;

REVOKE ALL
ON FUNCTION secure.get_customer(bigint)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION secure.get_customer(bigint)
TO application_reader;

COMMIT;

This avoids an unnecessary exposure window.

## 3.15.27 Default Privileges

Default privileges apply according to the role creating future objects.

For an owner/creator role, a production pattern to remove the normal global default PUBLIC EXECUTE for future functions is:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;

Do not assume:

... IN SCHEMA app
REVOKE EXECUTE ...

can remove a privilege inherited from the global default.

Default-privilege behavior must be validated against the deployed PostgreSQL version and actual creator role.

## 3.15.28 FUNCTIONS vs ROUTINES

PostgreSQL terminology and supported ALTER DEFAULT PRIVILEGES syntax have evolved across releases.

Because this handbook covers PostgreSQL 14–18:

Validate FUNCTIONS/ROUTINES syntax and behavior against the deployed major version before standardizing automation.

## 3.15.29 Positive and Negative Security Tests

Do not test only:

Authorized role succeeds

Also prove:

Unauthorized role fails
Direct protected-object access fails
RLS cannot be bypassed unexpectedly
Temporary object cannot alter privileged resolution
Malicious input is safely handled
Unauthorized dynamic target is rejected

Security testing should include production-equivalent roles.

## 3.15.30 LEAKPROOF

PostgreSQL supports the LEAKPROOF function property.

It affects security-sensitive planning involving mechanisms such as:

Row-Level Security
security_barrier views

It represents a strong security assertion about function behavior and is restricted accordingly.

Never use LEAKPROOF as a performance hint.

Only declare it when the function genuinely satisfies PostgreSQL's security requirements.

## 3.15.31 Procedures and Transaction Control

Functions cannot end transactions.

Procedures can execute transaction-control commands only under qualifying PostgreSQL invocation conditions.

Conceptually:

CALL proc1()
    │
    ▼
CALL proc2()
    │
    ▼
CALL proc3()

can permit transaction control where PostgreSQL's rules are satisfied.

But an intervening command such as:

CALL proc1()
    │
    ▼
SELECT function()
    │
    ▼
CALL proc3()

changes the call context and can make transaction control unavailable deeper in the chain.

## 3.15.32 Transaction Control Is Context-Sensitive

Do not design procedures under the assumption:

Procedure
    =
COMMIT/ROLLBACK always allowed

Instead validate:

Invocation context
Call chain
Outer transaction
SECURITY DEFINER status
Procedure SET clauses
Exception blocks

against the deployed PostgreSQL version.

## 3.15.33 SECURITY DEFINER Procedure Restriction

A SECURITY DEFINER procedure cannot execute transaction-control statements.

Therefore:

Need privilege elevation
       +
Need internal COMMIT/ROLLBACK

requires architectural reconsideration rather than combining both features blindly.

## 3.15.34 Procedure SET Clause and Transactions

Procedure-level SET configuration can also restrict transaction-control behavior.

Therefore this design:

Procedure
  +
SET configuration
  +
COMMIT/ROLLBACK

must be validated against PostgreSQL's procedure rules before implementation.

## 3.15.35 COMMIT AND CHAIN

For qualifying procedural transaction workflows PostgreSQL also supports patterns such as:

COMMIT AND CHAIN;

and:

ROLLBACK AND CHAIN;

which begin the next transaction with transaction characteristics carried forward as defined by PostgreSQL.

These can be useful for controlled batch processing.

## 3.15.40 Dynamic SQL

PL/pgSQL supports dynamic execution.

Prefer:

EXECUTE format(
    'SELECT count(*) FROM %I.%I',
    p_schema,
    p_table
);

rather than:

EXECUTE 'SELECT count(*) FROM '
        || p_schema || '.' || p_table;

For data values, prefer parameterization:

EXECUTE
    'SELECT customer_name
       FROM app.customers
      WHERE customer_id = $1'
INTO v_name
USING p_customer_id;
## 3.15.41 Identifier Safety vs Value Safety

Use:

format('%I', identifier)

for identifiers where appropriate.

Use:

USING

for data values where possible.

These solve different problems.

## 3.15.42 Injection Safety ≠ Authorization

A safely quoted object can still be an unauthorized target.

Therefore privileged dynamic SQL requires:

Input
  │
  ▼
Syntax safe?
  │
  ▼
Target authorized?
  │
  ▼
Operation allowed?
  │
  ▼
Execute

Use allowlists or equivalent authorization controls for sensitive dynamic operations.

## 3.15.43 Dynamic SQL Planning

PL/pgSQL dynamic EXECUTE is planned at execution rather than simply relying on the normal reusable-plan behavior of static statements.

This can be useful when:

Object names change
Parameter distributions vary materially
Dynamic plans are intentional

but it adds planning overhead.

Use dynamic SQL because the operation requires it, not by default.

Transaction termination is restricted
while inside the applicable block

Do not wrap every statement in unnecessary exception handling.

## 3.15.48 CREATE OR REPLACE FUNCTION

Use:

CREATE OR REPLACE FUNCTION ...

for compatible changes.

However, it cannot simply transform an existing function into an incompatible identity/return contract.

Important changes such as:

Function name
Input argument types
Return type

## 3.15.49 Replace vs Drop/Recreate

These are not operationally equivalent:

CREATE OR REPLACE
        ≠
DROP + CREATE

Dropping destroys the existing object identity and can affect dependencies.

Prefer replacement when the intended compatible change permits it.

## 3.15.50 Replacement Does Not Prove Safety

## 3.15.54 Planner COST

Functions can specify execution COST.

Typical defaults differ between internal/C-language functions and functions written in other languages.

Do not modify cost merely to force the planner toward a preferred plan.

Tune it only when measurements justify a more accurate estimate.

## 3.15.55 Set-Returning ROWS

Set-returning functions can specify estimated rows.

Without a better declaration, PostgreSQL uses a default estimate.

Incorrect cardinality estimates can cause poor join strategies and other plan problems.

For important SRFs:

Measure actual cardinality
        │
        ▼
Compare planner estimate
        │
        ▼
Adjust only if justified
## 3.15.56 Parallel Safety

PostgreSQL supports:

PARALLEL UNSAFE
PARALLEL RESTRICTED
PARALLEL SAFE

User-defined functions default conservatively to PARALLEL UNSAFE unless declared otherwise.

Do not mark a routine safe merely to obtain parallel plans.

Incorrect declarations can cause failures or incorrect behavior.

## 3.15.57 Sequence Access and Parallelism

Operations involving sequence state can affect parallel-safety classification.

Routines using sequence operations must be reviewed before being declared parallel-safe.

Again:

Parallel-safety metadata is a correctness promise.

## 3.15.58 Function Call Cardinality

Consider:

SELECT
    customer_id,
    app.customer_score(customer_id)

If there are:

then potentially:

occur.

If each function performs three SQL statements:

2,000,000
    ×
3
 =
6,000,000 internal SQL operations

This can overwhelm PostgreSQL.

## 3.15.66 Deadlock Retry

PostgreSQL detects deadlocks and aborts one participant.

A bounded retry may be appropriate for an idempotent transaction.

Do not implement:

deadlock
   │
   ▼
infinite immediate retry

Use bounded retries and investigate persistent deadlocks as a design problem.

## 3.15.67 Lock Ordering

Where multiple objects are modified, use consistent access ordering where practical.

Transaction A:
table_1 → table_2

Transaction B:
table_1 → table_2

is generally safer than conflicting ordering.

Routine design should explicitly consider lock topology.

## 3.15.68 Lock Budget

For critical operational routines define acceptable lock-wait behavior.

Possible controls:

lock_timeout
statement_timeout
application timeout
scheduler timeout

There is no universal correct value.

The correct setting derives from workload criticality and recovery behavior.

## 3.15.71 Cancellation vs Termination

Distinguish:

SELECT pg_cancel_backend(...);

from:

SELECT pg_terminate_backend(...);

Cancellation targets the current query.

Termination ends the backend session.
