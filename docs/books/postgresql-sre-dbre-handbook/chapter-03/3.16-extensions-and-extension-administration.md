## 3.16.1 Purpose

PostgreSQL extensions package related database functionality so it can be installed, versioned, upgraded, and removed as a unit.

An extension may provide:

Functions
Data types
Operators
Operator classes
Views
Tables
Procedures
Foreign-data wrappers
Access methods
Background-worker functionality
Native shared libraries

The central SRE/DBRE principle is:

A PostgreSQL extension is both a database dependency and, in many cases, a server-runtime dependency.

Production administration must therefore consider much more than CREATE EXTENSION.

## 3.16.3 Extension Scope

Extensions are installed per database.

CREATE EXTENSION pg_trgm;

installs pg_trgm into the current database.

Conceptually:

PostgreSQL Cluster
       │
       ├── appdb
       │     └── pg_trgm ✓
       │
       ├── reporting
       │     └── pg_trgm ✗
       │
       └── analytics
             └── pg_trgm ✓

Installation in one database does not automatically install the extension in every database.

PostgreSQL also permits extensions to be installed in template1, in which case databases subsequently created from that template can inherit them.

For managed production environments, explicit desired-state management is generally preferable to casually modifying template1.

## 3.16.4 Available vs. Installed

Two distinct states must be understood:

Extension files available
          ≠
Extension installed in database

Discover available extensions:

SELECT
    name,
    default_version,
    installed_version,
    comment
FROM pg_available_extensions
ORDER BY name;

Discover installed extensions:

SELECT
    extname,
    extversion
FROM pg_extension
ORDER BY extname;

This distinction becomes critical during:

Restore
Failover
Container replacement
Host rebuild
Disaster recovery
PostgreSQL major upgrade
## 3.16.5 Extension Version Discovery

Use:

SELECT
    name,
    version,
    installed,
    superuser,
    trusted,
    relocatable,
    schema,
    requires
FROM pg_available_extension_versions
ORDER BY name, version;

This provides information about available versions and extension properties.

Production rule:

Never assume that because an extension is available, the version required by the application is also available.

## 3.16.6 Extension Inventory

A useful installed-extension inventory is:

SELECT
    e.extname,
    e.extversion,
    pg_get_userbyid(e.extowner) AS owner,
    n.nspname AS extension_schema,
    e.extrelocatable,
    a.default_version,
    a.comment
FROM pg_extension AS e
JOIN pg_namespace AS n
  ON n.oid = e.extnamespace
LEFT JOIN pg_available_extensions AS a
  ON a.name = e.extname
ORDER BY e.extname;

Do not confuse:

PostgreSQL version
Extension package/library version
Extension SQL/catalog version

They are separate operational dimensions.

## 3.16.7 Installing Extensions

Basic installation:

CREATE EXTENSION pg_trgm;

Explicit version:

CREATE EXTENSION extension_name
VERSION 'approved_version';

Explicit schema where supported:

CREATE EXTENSION extension_name
SCHEMA extensions;

Production installation should control:

Name
Version
Schema
Owner
Dependencies
Privileges
Runtime package
Configuration
HA compatibility
DR availability
## 3.16.8 Extension Schemas

Many extensions support explicit schema placement.

Example:

CREATE SCHEMA extensions;

CREATE EXTENSION extension_name
SCHEMA extensions;

But not every extension supports arbitrary placement or relocation.

Check:

SELECT
    extname,
    extrelocatable
FROM pg_extension
ORDER BY extname;

A relocatable extension may support:

ALTER EXTENSION extension_name
SET SCHEMA extensions;

Do not assume all extensions can be moved.

## 3.16.9 Extensions Are Not Schema-Qualified

An extension's member objects may live in a schema, but the extension name itself is not schema-qualified.

Therefore:

pg_trgm

is the extension identity—not:

extensions.pg_trgm

pg_extension.extnamespace identifies the schema containing most or all of the extension's exported objects.

## 3.16.10 Extension Ownership

Inspect ownership:

SELECT
    e.extname,
    pg_get_userbyid(e.extowner) AS owner,
    e.extversion,
    n.nspname AS schema
FROM pg_extension e
JOIN pg_namespace n
  ON n.oid = e.extnamespace
ORDER BY e.extname;

Recommended model:

Platform / DBA controlled role
              │
              ▼
           Extension
              │
              ▼
 Application roles consume functionality

Application runtime roles should normally not own infrastructure-level extensions.

Ownership changes and lifecycle operations must remain controlled.

## 3.16.11 Trusted Extensions

PostgreSQL extension metadata can designate an extension as trusted.

A trusted extension can generally be installed by a user with sufficient database CREATE privileges without requiring full PostgreSQL superuser authority.

However:

Trusted does not mean risk-free, organization-approved, or exempt from security review.

These are separate concepts:

PostgreSQL trusted flag
          ≠
Enterprise security approval
## 3.16.12 Extension Security Boundary

Extensions may introduce executable database or native code.

Potential components include:

Functions
Procedures
Triggers
Native libraries
Background workers
FDWs
Types
Operators
Access methods

Therefore:

CREATE EXTENSION
ALTER EXTENSION UPDATE

must be treated as software deployment events.

Third-party extensions require particular scrutiny.

## 3.16.14 Installation-Schema Security

Privileged extension installation must not operate through attacker-controlled schemas.

Review:

Target schema
     │
     ▼
Schema owner
     │
     ▼
CREATE privileges
     │
     ▼
Trusted users only?

Production invariant:

Schemas used for privileged extension installation, updates, and dependencies must not be writable by untrusted roles.

## 3.16.15 search_path Security

An unqualified object reference can resolve through search_path.

Privileged extension code
          │
          ▼
Unqualified reference
          │
          ▼
search_path
       ┌──┴──┐
       ▼     ▼
 Expected   Attacker-created
 object     object
               │
               ▼
         Privilege abuse

This is particularly important for privileged functions.

Production review must examine:

search_path
Schema ownership
Schema CREATE privileges
Temporary schemas
Function ownership
## 3.16.16 PostgreSQL 14 vs. 15+ Schema Security

Production environments supporting PostgreSQL 14–18 must account for historical differences in default public schema privileges.

Clusters upgraded from older releases may retain permissions that differ from newly initialized PostgreSQL 15+ environments.

Inspect actual privileges rather than assuming defaults:

SELECT
    nspname,
    nspowner,
    nspacl
FROM pg_namespace
WHERE nspname = 'public';

Security posture should be based on actual catalog state.

## 3.16.17 SECURITY DEFINER Functions

Extensions providing SECURITY DEFINER functions require additional review because those functions execute with the privileges of their owner.

Review:

SECURITY DEFINER?
        │
        ▼
Function owner
        │
        ▼
Secure search_path?
        │
        ▼
EXECUTE grants
        │
        ▼
Least privilege?

Extension approval does not automatically imply that every privileged function should be executable by every application role.

## 3.16.19 Extension Member Objects

PostgreSQL tracks objects belonging to extensions through its dependency infrastructure.

Conceptually:

Extension
   │
   ├── Function
   ├── Type
   ├── Operator
   ├── View
   └── Table

Membership can be changed through supported operations such as:

ALTER EXTENSION extension_name
ADD FUNCTION some_function(integer);

These are advanced operations and should be change-controlled.

## 3.16.20 Removing an Object From Extension Membership

For example:

ALTER EXTENSION extension_name
DROP FUNCTION some_function(integer);

removes the object's membership in the extension.

It does not mean the same thing as:

DROP FUNCTION some_function(integer);

This distinction is operationally important.

## 3.16.21 Do Not Modify Extension-Owned Objects Casually

Avoid manual customization of extension implementation objects.

Extension object
      │
      ▼
Manual modification
      │
      ▼
Works temporarily
      │
      ▼
ALTER EXTENSION UPDATE
      │
      ▼
Modification replaced/conflicts

Prefer documented extension configuration interfaces.

## 3.16.22 Extension Configuration Tables

Some extensions own tables containing configuration or user data that must receive special treatment during logical dump/restore.

pg_extension exposes:

extconfig
extcondition

for extension configuration-table handling.

Conceptually:

Extension
   │
   ├── Implementation objects
   │      └── Recreated from package
   │
   └── Configuration/user data
          └── Must survive logical migration

This is important when validating logical backup and restore behavior.

## 3.16.23 Updating Extensions

Standard update:

ALTER EXTENSION extension_name
UPDATE;

Explicit target:

ALTER EXTENSION extension_name
UPDATE TO 'approved_version';

PostgreSQL executes extension-provided update scripts.

Therefore:

PostgreSQL can execute a provided update path; it cannot invent one that the extension package does not provide.

## 3.16.24 Explicit Target Versions

Without TO, PostgreSQL attempts to update toward the extension package's configured default version.

For reproducible production deployments, explicit target versions are often preferable:

ALTER EXTENSION extension_name
UPDATE TO 'approved_version';

This prevents package differences between environments from silently selecting different target versions.

## 3.16.25 Never Fake an Extension Upgrade

Never do:

UPDATE pg_extension
SET extversion = 'new_version'
WHERE extname = 'extension_name';

That modifies metadata without executing required update scripts.

Result:

Catalog version = new
        │
        ▼
Objects/configuration = old
        │
        ▼
Inconsistent database state

Use supported extension lifecycle commands only.

## 3.16.26 Do Not Assume Downgrades Exist

A forward update path:

1.9 → 2.0

does not imply:

2.0 → 1.9

exists.

Consequently, rollback may require:

Backup restore
Snapshot restore
Replica-based recovery
Database rebuild
Application rollback

depending on the extension and architecture.

## 3.16.27 Binary Extensions

Some extensions require native shared libraries.

DATABASE
   │
   └── pg_extension + member objects

SERVER
   │
   ├── Control file
   ├── SQL scripts
   ├── Shared library
   └── Package

Therefore:

Database metadata alone is insufficient to operate a native extension.

## 3.16.28 Three-Version Model

Production inventories should distinguish:

PostgreSQL major/minor version
             │
             ▼
Extension package/library version
             │
             ▼
Extension SQL/catalog version

Troubleshooting only extversion can miss runtime-package drift.

## 3.16.29 shared_preload_libraries

Some extensions/modules require PostgreSQL startup configuration such as:

shared_preload_libraries = 'required_library'

The exact requirement depends on the extension.

Deployment may therefore require:

      │
      ▼
Configure preload
      │
      ▼
Restart PostgreSQL
      │
      ▼
CREATE / UPDATE EXTENSION
      │
      ▼
Validate

## 3.16.30 Restart Requirements

Different extension changes have different operational consequences.

## 3.16.38 Physical Replication

Physical replication reproduces database state, but does not provision missing OS/container packages.

Failover candidates require:

PostgreSQL compatibility        ✓
Extension package               ✓
Shared library                  ✓
Package version                 ✓
Preload configuration           ✓
Required GUCs                   ✓

A standby with zero replication lag is not necessarily extension-ready.

## 3.16.39 Failover Validation

Weak test:

Promote standby
SELECT 1;
PASS

Strong test:

Promote standby
      │
      ▼
Reconnect application
      │
      ▼
Execute extension-dependent workload
      │
      ▼
Validate functions/types/operators
      │
      ▼
Validate performance

Extension functionality must be included in HA certification.

## 3.16.40 Logical Replication

Logical replication does not install extension packages on subscribers.

If publisher schema depends on extension-provided:

Types
Functions
Operators
Other schema objects

the subscriber may require a compatible extension installation before schema/data operations succeed.

Subscriber readiness must be validated independently.

## 3.16.41 Backup Architecture

Separate:

DATABASE BACKUP
     │
     ├── Physical backup
     └── Logical dump

SOFTWARE RECOVERY
     │
     ├── Extension package
     ├── Shared libraries
     ├── Configuration
     └── Approved versions

Neither physical nor logical database backup should be assumed to preserve the external software repository required to rebuild an extension runtime.

## 3.16.45 PostgreSQL Major Upgrades

Extensions are a formal upgrade gate.

Target PostgreSQL
      │
      ▼
Extension compatibility matrix
      │
      ├── Supported?
      ├── Package available?
      ├── Library compatible?
      ├── Update path?
      ├── Preload compatible?
      └── Application tested?
              │
              ▼
           GO / NO-GO

A single unsupported critical extension can block the PostgreSQL major upgrade.

Extension analysis belongs near the beginning of upgrade planning.

## 3.16.46 Dropping an Extension

Basic removal:

DROP EXTENSION extension_name;

This removes extension member objects.

Default behavior is restrictive when dependencies prevent removal.

Treat:

DROP EXTENSION extension_name CASCADE;

as a high-risk destructive operation.

Production principle:

Never use CASCADE simply to make a dependency error disappear.
