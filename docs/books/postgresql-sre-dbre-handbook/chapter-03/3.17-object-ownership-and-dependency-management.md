# 3.17 — Object Ownership and Dependency Management
**Edition:** Revised Final / Canonical Edition
**Chapter:** 3 — PostgreSQL Database and Object Administration
**Status:** COMPLETE — Canonical Edition
**Validation target:** PostgreSQL 14–18
**Audience:** PostgreSQL DBA, DBRE, SRE, Platform Engineer

This canonical edition incorporates the Draft, Technical Review, and Production Review findings. It establishes the production model for PostgreSQL object ownership, dependency management, role retirement, destructive DDL, ownership drift, automation, and recovery.

## 3.17.1 Purpose

Every PostgreSQL object exists within two important administrative relationships:

ROLE
  │
  ▼
OWNS OBJECT
  │
  ▼
OBJECT PARTICIPATES
IN DEPENDENCIES
  │
  ▼
ALTER / DROP / REASSIGN
  │
  ▼
POTENTIAL BLAST RADIUS

Ownership answers:

Who controls this object?

Dependencies answer:

What other database objects can be affected if this object changes or disappears?

Production operations introduce a third dimension:

What applications, pipelines, reports, scripts, or external systems depend on the object even though PostgreSQL cannot see them?

Therefore:

Production Object Lifecycle
          =
Ownership
    +
PostgreSQL Dependencies
    +
External Dependencies
## 3.17.2 Ownership Is Not a Privilege

PostgreSQL ownership is fundamentally different from privileges granted through GRANT.

Conceptually:

OBJECT OWNER
     │
     ├── Controls object lifecycle
     ├── Can ALTER object
     ├── Can DROP object
     └── Controls privileges

An application role can use a table without owning it.

Example:

GRANT SELECT, INSERT, UPDATE, DELETE
ON app.orders
TO app_runtime;

The desired architecture is:

app_owner
    │
    ▼
app.orders

app_runtime
    │
    └── required DML privileges

not:

app_runtime
    │
    ▼
owns app.orders
Production principle

Solve access requirements with privileges. Do not grant ownership merely to solve an access problem.

## 3.17.3 Four Distinct Security Concepts

Production administration must distinguish:

AUTHENTICATION
     │
     ▼
Can the identity connect?
     
ROLE MEMBERSHIP
     │
     ▼
Which roles can it inherit/become?
     
PRIVILEGES
     │
     ▼
Which operations can it perform?
     
OWNERSHIP
     │
     ▼
Who controls object lifecycle?

Confusing these concepts leads to over-privileged applications and unstable ownership architecture.

## 3.17.4 Production Ownership Architecture

Preferred pattern:

               db_owner
                NOLOGIN
                   │
                   ▼
                Database
                   │
                   ▼
               app_owner
                NOLOGIN
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Schema     Tables    Functions
        │          │          │
        └──────────┼──────────┘
                   ▼
            Runtime Roles
              privileges
                 only

Example:

CREATE ROLE db_owner NOLOGIN;
CREATE ROLE app_owner NOLOGIN;

CREATE ROLE migration_role LOGIN;
CREATE ROLE app_runtime LOGIN;
CREATE ROLE app_readonly LOGIN;

Then establish controlled membership as required:

GRANT app_owner TO migration_role;

Exact membership behavior should be validated for the deployed PostgreSQL major version, particularly across PostgreSQL 14–18 where role-membership capabilities evolved.

## 3.17.5 Why Stable NOLOGIN Owners Matter

Avoid:

john.smith
    │
    ▼
owns 900 production objects

because eventually:

Employee leaves
      │
      ▼
Account retirement
      │
      ▼
DROP ROLE fails
      │
      ▼
Emergency ownership migration

Prefer:

app_owner NOLOGIN
      │
      ▼
Stable ownership

Human, application, and CI/CD credentials can change without forcing ownership changes across the database.

## 3.17.6 Deterministic Deployment Ownership

A migration pipeline should deliberately establish the role under which DDL executes.

Example:

SELECT current_user, session_user;

SET ROLE app_owner;

CREATE TABLE app.orders (
    order_id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now()
);

RESET ROLE;

Conceptually:

CI/CD Login
    │
    ▼
SET ROLE
    │
    ▼
app_owner
    │
    ▼
CREATE OBJECT
    │
    ▼
Owner = app_owner

A pipeline should validate current_user before critical DDL.

## 3.17.9 Relation Ownership Inventory
SELECT
    n.nspname AS schema_name,
    c.relname AS object_name,
    c.relkind,
    pg_get_userbyid(c.relowner) AS owner
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relname;

This identifies ownership for many relation-like objects.

## 3.17.10 Schema Ownership Inventory
SELECT
    nspname AS schema_name,
    pg_get_userbyid(nspowner) AS owner
FROM pg_namespace
WHERE nspname NOT LIKE 'pg_%'
  AND nspname <> 'information_schema'
ORDER BY nspname;

Schema ownership must be evaluated together with:

Owner
CREATE privileges
USAGE privileges
Default privileges
search_path exposure
## 3.17.11 Database Ownership Inventory
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner
FROM pg_database
ORDER BY datname;

Database ownership is not required merely to connect.

Separate:

Database ownership
CONNECT privilege
TEMPORARY privilege

Applications normally require appropriate access, not database ownership.

## 3.17.12 Function Ownership Inventory
SELECT
    n.nspname AS schema_name,
    p.proname AS function_name,
    pg_get_function_identity_arguments(p.oid) AS arguments,
    pg_get_userbyid(p.proowner) AS owner,
    p.prosecdef AS security_definer
FROM pg_proc AS p
JOIN pg_namespace AS n
  ON n.oid = p.pronamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, p.proname;

Functions should be identified by signature:

app.calculate_total(integer, numeric)

not simply:

app.calculate_total

because PostgreSQL supports overloaded functions.

## 3.17.14 Type Ownership Inventory
SELECT
    n.nspname AS schema_name,
    t.typname AS type_name,
    pg_get_userbyid(t.typowner) AS owner
FROM pg_type AS t
JOIN pg_namespace AS n
  ON n.oid = t.typnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, t.typname;

Catalog output requires interpretation because PostgreSQL creates some types internally as part of other objects.

## 3.17.15 Changing Ownership

Targeted ownership transfer uses object-specific ALTER ... OWNER TO.

Examples:

ALTER TABLE app.orders
OWNER TO app_owner;
ALTER SCHEMA app
OWNER TO app_owner;
ALTER DATABASE appdb
OWNER TO db_owner;

Ownership-transfer prerequisites vary somewhat by object class.

Production automation should therefore not assume identical checks for every ALTER ... OWNER TO operation.

## 3.17.16 Sequence OWNER TO vs. OWNED BY

These operations are fundamentally different.

Role ownership:

ALTER SEQUENCE app.orders_id_seq
OWNER TO app_owner;

means:

app_owner
    │
    ▼
owns sequence object

Whereas:

ALTER SEQUENCE app.orders_id_seq
OWNED BY app.orders.order_id;

establishes a dependency:

orders.order_id
      │
      ▼
orders_id_seq

Therefore:

OWNER TO
    ≠
OWNED BY

This distinction is critical for sequence lifecycle automation.

## 3.17.17 Identity and Serial Sequences

Identity columns and historical serial patterns can create table-column/sequence relationships.

Operationally:

Table
  │
  ▼
Column
  │
  ▼
Sequence

Before:

Dropping columns
Moving tables
Changing ownership
Migrating schemas
Rebuilding sequences

inspect the actual dependency relationships.

## 3.17.18 Default Privileges

Existing privileges and future-object privileges are separate concerns.

Example:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT ON TABLES
TO app_readonly;

Inventory:

SELECT
    pg_get_userbyid(d.defaclrole) AS owner_role,
    n.nspname AS schema_name,
    d.defaclobjtype,
    d.defaclacl
FROM pg_default_acl AS d
LEFT JOIN pg_namespace AS n
  ON n.oid = d.defaclnamespace
ORDER BY 1, 2, 3;

Important distinction:

Existing object ACL
        ≠
Default privileges
for future objects
## 3.17.19 Default-Privilege Failure Pattern

A common production failure:

Old owner retired
      │
      ▼
Existing objects reassigned
      │
      ▼
Existing application access works
      │
      ▼
New table created
      │
      ▼
Expected grants missing
      │
      ▼
Permission denied

Ownership migration is therefore incomplete without default-privilege review.

## 3.17.20 Bulk Ownership Migration

For controlled bulk reassignment:

REASSIGN OWNED BY old_role
TO app_owner;

PostgreSQL also permits multiple source roles:

REASSIGN OWNED BY
    old_role_1,
    old_role_2
TO app_owner;

Inventory source roles individually before consolidation.

## 3.17.21 Scope of REASSIGN OWNED

A crucial operational rule:

Current database objects
        +
Relevant shared objects

can be affected, but a single invocation does not migrate ordinary objects in every database across the cluster.

Therefore:

database_A
database_B
database_C

must each be considered during role retirement.

## 3.17.22 What REASSIGN OWNED Does Not Solve

REASSIGN OWNED primarily addresses ownership.

It does not constitute complete cleanup of:

Explicit grants
Default privileges
Role memberships
All dependency relationships

Therefore:

REASSIGN OWNED
      ≠
Complete role retirement
## 3.17.23 DROP OWNED
DROP OWNED BY old_role;

is a potentially destructive operation.

It can:

Drop objects owned by role
        +
Revoke privileges held by role

within its applicable scope.

Therefore:

DROP OWNED is destructive DDL, not merely a grant-cleanup command.

## 3.17.24 DROP OWNED ... CASCADE

This is particularly dangerous:

DROP OWNED BY old_role CASCADE;

Dependency recursion can affect objects beyond the obvious ownership set.

Production rule:

Never add CASCADE simply because DROP OWNED failed.

A failure should trigger dependency analysis.

## 3.17.26 PostgreSQL Dependency Architecture

PostgreSQL records relationships among database objects.

Examples:

VIEW
 │
 └── TABLE

FOREIGN KEY
 │
 └── REFERENCED TABLE

INDEX
 │
 └── TABLE

TRIGGER
 │
 ├── TABLE
 │
 └── FUNCTION

EXTENSION MEMBER
 │
 └── EXTENSION

PARTITION
 │
 └── PARTITIONED TABLE

These relationships allow PostgreSQL to protect structural integrity during object deletion.

## 3.17.27 pg_depend

Many database-local dependency relationships are represented in:

pg_depend

Important dimensions include:

classid
objid
objsubid

refclassid
refobjid
refobjsubid

deptype

Conceptually:

Dependent object/subobject
          │
          ▼
       pg_depend
          │
          ▼
Referenced object/subobject

The subid fields matter because dependencies can involve columns and other subobjects.

## 3.17.28 pg_shdepend

Dependencies involving shared objects such as roles are represented through:

pg_shdepend

Conceptually:

Role / shared object
        │
        ▼
    pg_shdepend
        │
        ├── database_A
        ├── database_B
        └── shared objects

This is why role cleanup cannot safely rely only on inspecting a single database.

## 3.17.29 Dependency Types

PostgreSQL distinguishes dependency semantics internally.

Important categories include concepts such as:

NORMAL
AUTO
INTERNAL
EXTENSION
AUTO_EXTENSION
PARTITION_PRIMARY
PARTITION_SECONDARY

These relationships do not all behave identically.

They influence:

Independent drop behavior
CASCADE requirements
Automatic lifecycle
Parent-controlled lifecycle
Extension lifecycle
Partition lifecycle

A production dependency analyzer must therefore understand dependency type—not merely count dependency rows.

## 3.17.30 Normal Dependencies

Conceptually:

Dependent Object
      │
      ▼
Referenced Object

Dropping the referenced object may require:

CASCADE

if the dependent object still exists.

Views referencing tables are a familiar example of PostgreSQL-managed dependency behavior.

## 3.17.31 Automatic Dependencies

Some objects are automatically associated with the lifecycle of another object.

Conceptually:

Parent
  │
  ▼
Automatically dependent object

Such objects may disappear automatically when the parent is removed.

Therefore:

Dependency exists

does not always mean:

Independent application object
## 3.17.32 Internal Dependencies

Some objects are implementation components of another PostgreSQL object.

Conceptually:

Owning object
     │
     ▼
Internal component

PostgreSQL may require lifecycle operations to occur through the owning object rather than independently through the internal component.

## 3.17.33 Extension Dependencies

Extension members participate in extension dependency semantics:

Extension
   │
   ├── Functions
   ├── Types
   ├── Operators
   └── Other objects

Do not normalize ownership or remove extension member objects blindly.

Lifecycle should normally be managed through:

CREATE EXTENSION
ALTER EXTENSION
DROP EXTENSION

and documented extension procedures.

## 3.17.34 Partition Dependencies

Partitioning introduces parent-controlled relationships:

Partitioned Table
       │
       ├── Partition A
       ├── Partition B
       └── Partition C

and potentially:

Partitioned Index
       │
       ├── Partition Index A
       └── Partition Index B

Before destructive DDL, inspect actual catalogs rather than inferring relationships from object names.

## 3.17.35 RESTRICT

The production-safe default is:

DROP TABLE target RESTRICT;

or simply the default restrictive behavior where applicable.

Operational pattern:

DROP / RESTRICT
      │
      ▼
Dependency error
      │
      ▼
Read DETAIL
      │
      ▼
Investigate dependencies
Canonical principle

A dependency error is useful safety information—not an obstacle to bypass.

## 3.17.36 DDL CASCADE

Example:

DROP TABLE target CASCADE;

means PostgreSQL may recursively remove dependent objects required by its dependency system.

It does not simply mean:

Delete everything conceptually related

The exact effect depends on dependency semantics.

## 3.17.37 DDL CASCADE vs. Foreign-Key Cascading

Do not confuse:

DROP TABLE parent CASCADE;

with:

FOREIGN KEY (...)
REFERENCES parent(...)
ON DELETE CASCADE;

They operate at different layers:

DDL CASCADE
     │
     ▼
Database-object lifecycle

FK ON DELETE CASCADE
     │
     ▼
Row/data lifecycle

This terminology must remain explicit in operational change plans.

## 3.17.38 DROP SCHEMA ... CASCADE

Example:

DROP SCHEMA app CASCADE;

is a critical destructive operation.

A dependency may exist outside the schema:

app.orders
    ▲
    │
reporting.order_summary

Therefore namespace removal can have cross-schema impact.

## 3.17.39 DROP TYPE ... CASCADE

A type may support:

Table columns
Functions
Operators
Views
Domains
Other types

Therefore:

DROP TYPE some_type CASCADE;

may have substantial blast radius and requires formal dependency review.

## 3.17.40 PostgreSQL Dependencies vs. Application Dependencies

PostgreSQL may know:

View → Table
FK → Table
Index → Table
Extension member → Extension
Partition → Parent

It generally cannot know every external relationship such as:

Microservice → Table
ETL job → Function
BI dashboard → View
Script → Sequence
ORM → Column
Kafka/CDC pipeline → Table
External report → Materialized view

Therefore:

A successful DROP ... RESTRICT does not prove an object is unused.

It only proves PostgreSQL did not find a dependency that blocks that operation.

## 3.17.41 Dynamic SQL Blind Spot

Consider:

Function
   │
   ▼
Dynamic SQL
   │
   ▼
Runtime object reference

Dynamic references may not appear in the catalog dependency graph in the way an operator expects.

Critical-object analysis may therefore require:

Catalog dependency analysis
          +

          +

## 3.17.42 Function Dependency Analysis

Before dropping foundational objects, review functions and procedures that may reference them.

Pay particular attention to:

Dynamic SQL
PL/pgSQL EXECUTE
Constructed identifiers
Configuration-driven object names
Cross-schema references

However:

PostgreSQL catalog parity
        ≠
Complete operational identity parity

Secrets/certificates

## 3.17.48 Backup and Restore

A restore should not be certified solely because:

works.

Validate:

Schema owners

Sequence owners
Function owners
SECURITY DEFINER owners

Privileges
Default privileges
Role memberships
Deployment workflow

## 3.17.49 Cross-Environment Restore

      │

## 3.17.52 Ownership Drift

Typical causes:

Manual DDL
Incorrect SET ROLE
Migration-tool configuration
Restore
Ad hoc DBA changes
CI/CD credential changes
Ownership migration

Example:

Expected:
app.orders → app_owner

Actual:
app.orders → ci_runner

Ownership drift should be continuously observable.

## 3.17.53 Drift Severity
Severity	Example
Critical	Unexpected SECURITY DEFINER owner
High	Production schema/table owned by personal login
High	CI/CD account owns application object

## 3.17.54 Dependency Monitoring

Do not alert simply because new pg_depend rows exist.

Dependencies are normal.

Instead detect conditions such as:

Deprecated object gained new dependents
Object scheduled for removal still has dependents
Unexpected cross-schema dependency
Retiring role still owns objects
Deprecated extension still has consumers

The goal is to monitor unmanaged dependency risk, not dependency existence.

Maintain an ownership desired-state manifest.
Detect ownership drift.

Monitor schema ownership.

Inventory all relevant object classes.

Inventory shared-object dependencies.

The canonical operational rule is:
