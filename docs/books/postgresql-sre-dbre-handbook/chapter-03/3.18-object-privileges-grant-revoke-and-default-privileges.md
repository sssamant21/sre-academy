## 3.18.1 Purpose

PostgreSQL authorization is not simply a collection of GRANT statements.

A production authorization model must govern:

Identity
   │
   ▼
Role membership
   │
   ▼
Effective role
   │
   ▼
Database / schema access
   │
   ▼
Object privileges
   │
   ▼
RLS and special authority
   │
   ▼
Effective database authority

The operational objective is:

Grant capabilities to functional roles, assign identities to those roles, separate ownership from runtime access, govern future objects with default privileges, and continuously validate effective—not merely direct—access.

## 3.18.2 Ownership Is Not a Privilege

The distinction established in 3.17 is fundamental:

OWNERSHIP
    ≠
OBJECT PRIVILEGES

Ownership provides inherent authority over an object's lifecycle.

Privileges determine how other roles may use that object.

Recommended:

ALTER TABLE app.orders
OWNER TO app_owner;

GRANT SELECT, INSERT, UPDATE, DELETE
ON app.orders
TO app_readwrite;

Architecture:

app_owner
   │
   └── OWNS
          │
          ▼
      app.orders
          ▲
          │
          └── USES
                │
          app_readwrite

PostgreSQL treats object modification/destruction authority as inherent in ownership rather than an ordinary grantable privilege.

Canonical rule

Ownership controls lifecycle; privileges control use.

## 3.18.3 Production Role Architecture

Recommended:

                         app_owner
                          NOLOGIN

                             ▼
                      APPLICATION
                         OBJECTS
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼

           SELECT        Required DML    Controlled DDL
             │               │               │

         Analysts       Application       Deployment

Avoid:

human1 ──► tables
human2 ──► tables

Prefer:

Identity
   │

   │
   ▼

This greatly improves provisioning, auditing, revocation, offboarding, and disaster recovery.

## 3.18.4 PostgreSQL Privilege Types

Common privileges include:

Privilege	Purpose
SELECT	Read data
INSERT	Insert rows
UPDATE	Modify rows
DELETE	Delete rows
TRUNCATE	Truncate relations
REFERENCES	Create foreign-key references
TRIGGER	Create triggers
MAINTAIN	Perform supported maintenance operations on applicable PostgreSQL versions
USAGE	Use schemas, sequences, types, languages, etc.
CREATE	Create objects where applicable
CONNECT	Connect to database
TEMPORARY	Create temporary tables
EXECUTE	Execute functions/procedures

Privileges are object-type-specific.

Version rule

Because this handbook covers PostgreSQL 14–18, version-sensitive privileges such as MAINTAIN must be capability/version checked before being used in automation.

## 3.18.5 Table Privileges

Typical read-only role:

GRANT SELECT
ON app.orders
TO app_readonly;

Typical runtime role:

GRANT SELECT, INSERT, UPDATE, DELETE
ON app.orders
TO app_readwrite;

Migration requirement:

GRANT REFERENCES
ON app.customers
TO app_migration;

Do not automatically use:

GRANT ALL PRIVILEGES ...

Instead:

Use ALL PRIVILEGES only when the role genuinely requires every privilege applicable to that object type.

Explicit grants are generally easier to review and audit.

## 3.18.6 Schema Privileges

Two critical schema privileges are:

USAGE
CREATE

USAGE permits object lookup/access in the schema, subject to privileges on the contained objects.

Example:

GRANT USAGE
ON SCHEMA app
TO app_readonly;

Then:

GRANT SELECT
ON app.orders
TO app_readonly;

Authorization layers:

Database
   │
   ▼
Schema USAGE
   │
   ▼
Object privilege

A table privilege does not eliminate the need for required schema access.

## 3.18.7 Schema CREATE

CREATE allows object creation in a schema.

Therefore:

GRANT CREATE
ON SCHEMA app
TO app_runtime;

is substantially more powerful than USAGE.

Normal runtime applications should generally have:

USAGE

not:

CREATE

unless runtime DDL is explicitly required.

## 3.18.8 Schema CREATE and search_path

This becomes a security issue when an untrusted role can create objects in a schema trusted through search_path.

Untrusted role
      │
      ▼
CREATE on schema
      │
      ▼
Creates conflicting object
      │
      ▼
Trusted search_path
resolves object
      │
      ▼
Unexpected behavior /
possible privilege escalation
Production invariant

Schemas trusted through search_path must not be writable by untrusted roles.

## 3.18.9 The public Schema

Never determine public schema security posture solely from the PostgreSQL server version.

Databases upgraded from older PostgreSQL releases can retain historical privileges.

Inspect the actual ACL.

Where appropriate after impact analysis:

REVOKE CREATE
ON SCHEMA public
FROM PUBLIC;

PostgreSQL documentation specifically discusses the security implications of writable schemas and the historical public schema behavior.

## 3.18.10 Database Privileges

Important database privileges:

CONNECT
CREATE
TEMPORARY

Example:

GRANT CONNECT
ON DATABASE appdb
TO app_runtime;

Runtime applications normally require CONNECT, but generally not database CREATE.

Also remember that successful connection involves more than CONNECT:

LOGIN capability
       +
Authentication / pg_hba rules
       +
CONNECT
       =
Connection eligibility
## 3.18.11 PUBLIC

PUBLIC represents every PostgreSQL role.

It is effectively a pseudo-role:

                 PUBLIC
              /    |    \
             /     |     \
          role1  role2  role3

Therefore:

GRANT SELECT
ON app.reference_codes
TO PUBLIC;

is broad access.

Production rule

Every PUBLIC privilege must be treated as an intentional security decision.

## 3.18.12 Important Built-In PUBLIC Defaults

PostgreSQL provides certain default privileges to PUBLIC.

Important examples include:

Object	Typical built-in PUBLIC privilege
Database	CONNECT, TEMPORARY
Function/procedure	EXECUTE
Procedural language	USAGE
Type/domain	USAGE

Other object classes commonly receive no corresponding default PUBLIC privileges.

These defaults matter because:

ACL = NULL

does not necessarily mean:

Nobody has access

It can mean PostgreSQL's built-in default ACL applies.

## 3.18.13 Sequence Privileges

Sequence permissions are a common source of production failures.

Relevant privileges include:

USAGE
SELECT
UPDATE

Example:

GRANT USAGE
ON SEQUENCE app.orders_id_seq
TO app_readwrite;

A critical PostgreSQL rule:

Table privileges do not automatically grant privileges on sequences used by that table.

Thus:

INSERT granted
      │
      ▼
INSERT executes
      │
      ▼
nextval()
      │
      ▼
permission denied for sequence

is entirely possible.

## 3.18.14 Sequence Privilege Semantics

Conceptually:

USAGE
   │
   └── allows sequence value operations such
       as nextval/currval as defined by PostgreSQL

SELECT
   │
   └── sequence read/currval-related capability

UPDATE
   │
   └── sequence state modification capability

Grant only what the workload requires.

For existing sequences:

GRANT USAGE
ON ALL SEQUENCES IN SCHEMA app
TO app_readwrite;

For future sequences, use default privileges.

## 3.18.15 Function and Procedure Privileges

Functions/procedures use:

EXECUTE

Example:

GRANT EXECUTE
ON FUNCTION app.calculate_total(bigint)
TO app_runtime;

Always include signatures where overloads are possible.

## 3.18.16 Sensitive Functions and PUBLIC EXECUTE

Functions/procedures can receive EXECUTE for PUBLIC through PostgreSQL defaults.

For sensitive functions:

BEGIN;

CREATE FUNCTION ...;

REVOKE ALL
ON FUNCTION app.secure_function(...)
FROM PUBLIC;

GRANT EXECUTE
ON FUNCTION app.secure_function(...)
TO approved_role;

COMMIT;

This avoids leaving an unnecessary exposure window. PostgreSQL documentation explicitly recommends same-transaction revocation where maximum security is required.

## 3.18.17 SECURITY DEFINER

SECURITY DEFINER functions require stricter controls because they execute with the function owner's authority.

Production safety requires:

Stable owner
    +
Secure search_path
    +
Restricted EXECUTE
    +
No unintended PUBLIC access
    +
Reviewed function definition
    =
Controlled SECURITY DEFINER

Treat such functions as privilege boundaries, not merely stored code.

## 3.18.18 Column-Level Privileges

PostgreSQL supports column-level privileges such as:

SELECT
INSERT
UPDATE
REFERENCES

Example:

GRANT SELECT (employee_id, employee_name)
ON hr.employees
TO reporting_role;

Or:

GRANT UPDATE (status)
ON app.orders
TO order_processor;

But this is incorrect as a restriction strategy:

GRANT SELECT
ON hr.employees
TO analyst;

REVOKE SELECT (salary)
ON hr.employees
FROM analyst;

The table-level SELECT remains authoritative.

Rule

Do not attempt to use a column-level revoke to subtract access already granted at table level.

## 3.18.19 Functional Roles

Preferred:

CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE app_readwrite NOLOGIN;

GRANT USAGE
ON SCHEMA app
TO app_readonly, app_readwrite;

GRANT SELECT
ON ALL TABLES IN SCHEMA app
TO app_readonly;

GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_readwrite;

GRANT app_readonly TO analyst_login;
GRANT app_readwrite TO application_login;

This separates:

Identity
   ≠
Access policy
   ≠
Ownership
## 3.18.20 Role Membership and Inheritance

Membership alone must not be analyzed without considering the PostgreSQL version and membership/inheritance semantics.

The effective model is:

Login role
    │
    ▼
Membership graph
    │
    ▼
Inheritance semantics
    │
    ▼
Immediately usable authority

PostgreSQL releases within the 14–18 support range have evolved role-membership behavior, so cross-version automation must not assume identical membership semantics.

## 3.18.21 session_user, current_user, and SET ROLE

Always distinguish:

session_user

from:

current_user

Example:

SELECT
    session_user,
    current_user;

After:

SET ROLE app_owner;

the effective role context changes.

This is especially important for:

Migrations
Ownership
GRANT provenance
Default privileges
SECURITY DEFINER troubleshooting
## 3.18.22 Deterministic Migration Pattern

Recommended:

SET ROLE app_owner;

CREATE TABLE app.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);

RESET ROLE;

Why?

Deployment Login
       │
       ▼
SET ROLE
       │
       ▼
app_owner
       │
       ├── predictable ownership
       └── predictable default privileges

This directly connects 3.17 ownership governance with 3.18 privilege governance.

## 3.18.23 Effective Privileges Are Additive

A role may obtain access through:

Direct ACL
    +
Role membership
    +
Nested membership
    +
PUBLIC
    +
Predefined roles
    +
Ownership
    +
Special authority

Therefore:

REVOKE SELECT
ON app.orders
FROM user1;

does not prove user1 lost access.

They may still obtain it through another path.

## 3.18.24 Predefined Roles

PostgreSQL provides predefined roles that can materially change effective authority.

Important examples include:

pg_read_all_data
pg_write_all_data

pg_monitor
pg_read_all_settings
pg_read_all_stats
pg_stat_scan_tables

pg_signal_backend

pg_read_server_files
pg_write_server_files
pg_execute_server_program

Privilege audits must include predefined-role membership.

## 3.18.25 Broad Data Roles

A role may appear to lack direct table access while still receiving broad access through:

pg_read_all_data

or:

pg_write_all_data

Therefore:

No direct table ACL
       ≠
No table access

Also, broad read access and RLS bypass are separate concepts.

Do not assume broad data-reading roles automatically imply unrestricted RLS bypass.

## 3.18.26 Powerful Server Roles

Treat membership in:

pg_read_server_files
pg_write_server_files
pg_execute_server_program

as highly privileged.

These roles expose capabilities outside ordinary table authorization and can create significant security risk.

Production invariant
Ordinary application role
          │
          └── MUST NOT receive
              server-file/program roles
## 3.18.27 Special Role Attributes

Object ACL analysis is incomplete without role attributes.

Inspect:

SUPERUSER
CREATEDB
CREATEROLE
REPLICATION
BYPASSRLS
LOGIN

For example:

ACL says no SELECT
       │
       ▼
Role is SUPERUSER
       │
       ▼
ACL conclusion invalid

Special authority must therefore be reported separately.

## 3.18.28 WITH GRANT OPTION

Example:

GRANT SELECT
ON app.orders
TO reporting_admin
WITH GRANT OPTION;

This grants:

SELECT
   +
Authority to delegate SELECT

Treat this as security administration.

Production invariant

Runtime application roles should not normally receive WITH GRANT OPTION.

## 3.18.29 Grantor Provenance

ACLs track:

Grantee
Privilege
Grant option
Grantor

For sensitive authorization changes, make grant provenance deterministic:

SET ROLE app_owner;

GRANT SELECT
ON app.orders
TO app_readonly;

RESET ROLE;

This makes audits and later revocation analysis substantially clearer.

## 3.18.30 REVOKE

Basic:

REVOKE UPDATE
ON app.orders
FROM app_runtime;

But after revocation, verify effective access.

Example:

SELECT has_table_privilege(
    'app_runtime',
    'app.orders',
    'UPDATE'
);

Do not equate:

REVOKE succeeded

with:

Effective access removed
## 3.18.31 REVOKE GRANT OPTION FOR

To remove delegation while retaining access:

REVOKE GRANT OPTION FOR SELECT
ON app.orders
FROM reporting_admin;

Result:

Before
──────
SELECT
+
Can delegate

After
─────
SELECT
+
Cannot delegate
## 3.18.32 Grant Chains

Example:

app_owner
    │
    │ SELECT WITH GRANT OPTION
    ▼
role_A
    │
    │ SELECT
    ▼
role_B
    │
    ▼
Application

Revoking role_A's authority may affect downstream access.

This must be understood before using CASCADE.

## 3.18.33 REVOKE ... CASCADE

Treat:

REVOKE ... CASCADE;

as high-risk authorization DDL.

Use:

Inventory grant chain
       │
       ▼
Identify consumers
       │
       ▼
Assess blast radius
       │
       ▼
Prefer RESTRICT-first analysis
       │
       ▼
Approve
       │
       ▼
Execute
       │
       ▼
Validate

A privilege cascade can create a production outage just as easily as an object dependency cascade.

## 3.18.34 Default Privileges

ALTER DEFAULT PRIVILEGES controls privileges assigned to future objects.

Example:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT
ON TABLES
TO app_readonly;

It does not retroactively modify existing objects.

## 3.18.35 Existing vs. Future Objects

Production setup generally requires both:

GRANT SELECT
ON ALL TABLES IN SCHEMA app
TO app_readonly;

and:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT
ON TABLES
TO app_readonly;

Model:

GRANT ON ALL TABLES
       │
       ▼
Existing objects

ALTER DEFAULT PRIVILEGES
       │
       ▼
Future objects
Canonical rule

Every production privilege policy must define behavior for both existing and future objects.

## 3.18.36 Creator-Specific Default Privileges

This is one of PostgreSQL's most important operational rules.

Default privileges are tied to the role creating the object.

Suppose:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT
ON TABLES
TO app_readonly;

but CI/CD creates the table as:

migration_login

without switching to app_owner.

The expected default may not apply.

Therefore:

Configured creator
       =
Actual current_user

must be deterministic.

## 3.18.37 Default Privileges Are Database-Local

Default privilege configuration is database-local.

Do not assume:

appdb1 configured
      │
      ▼
appdb2 automatically configured

Each database requires its own desired authorization state.

## 3.18.38 Global vs. Per-Schema Defaults

Default privileges can include global and per-schema policy.

Conceptually:

Global defaults
      +
Schema-specific defaults
      =
Creation-time privilege state

Per-schema defaults are additive to applicable global defaults.

Do not design:

Broad global GRANT
       +
Per-schema REVOKE
       =
Restriction

without verifying PostgreSQL's actual default-privilege semantics.

## 3.18.39 Sequence Default Privileges

Existing sequences:

GRANT USAGE
ON ALL SEQUENCES IN SCHEMA app
TO app_readwrite;

Future sequences:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT USAGE
ON SEQUENCES
TO app_readwrite;

Together:

Existing sequences
        +
Future sequences
        =
Stable application behavior
## 3.18.40 Function Default Privileges

Security-sensitive environments may remove default PUBLIC execution for functions created by a controlled owner.

Example:

ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
REVOKE EXECUTE
ON FUNCTIONS
FROM PUBLIC;

Then grant EXECUTE deliberately.

Always test the policy with actual newly created functions.

## 3.18.41 Inspecting Default Privileges

Use:

SELECT
    pg_get_userbyid(d.defaclrole) AS creator_role,
    n.nspname AS schema_name,
    d.defaclobjtype,
    d.defaclacl
FROM pg_default_acl AS d
LEFT JOIN pg_namespace AS n
       ON n.oid = d.defaclnamespace
ORDER BY 1, 2, 3;

Production audits should track:

Database
Creator
Schema
Object type
Grantee
Privilege
Grant option
## 3.18.42 ACL Inspection

Example:

SELECT
    n.nspname AS schema_name,
    c.relname AS object_name,
    pg_get_userbyid(c.relowner) AS owner,
    c.relacl
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname NOT IN
      ('pg_catalog', 'information_schema')
ORDER BY 1, 2;

But never treat ACL text as a trivial string.

Conceptually:

grantee = privileges / grantor

and grant options are represented separately within ACL semantics.

Use catalog-aware parsing.

## 3.18.43 Null ACL Does Not Mean No Access

This is critical.

ACL = NULL

can mean:

Use PostgreSQL built-in default ACL

rather than:

No privileges

For example, a function with a null ACL can still have default PUBLIC EXECUTE.

Canonical security rule

Never interpret a null ACL as "nobody has access."

## 3.18.44 Owner Grant Authority

Owners inherently possess authority over their objects and effectively hold grant capability even when this is not represented like an ordinary explicit ACL grant.

Therefore:

No explicit grant option in ACL

does not imply:

Owner cannot delegate

Ownership must be part of every effective-authority analysis.

## 3.18.45 Privilege Verification Functions

Prefer PostgreSQL's privilege-evaluation functions over manually decoding ACL strings.

Examples:

    'app.orders',
    'SELECT'
);
SELECT has_schema_privilege(
    'app_runtime',
    'app',
    'USAGE'
);

    'app_runtime',
    'appdb',

Also useful:

has_sequence_privilege()
has_function_privilege()
has_type_privilege()
has_tablespace_privilege()
pg_has_role()

These are particularly useful for automated post-deployment checks.

## 3.18.46 RLS and Object Privileges

Object privileges answer:

May the role SELECT from this table?

RLS answers:

Which rows may the role access?

Effective access therefore involves:

Object privilege
       +
RLS policy
       +
Ownership behavior
       +
BYPASSRLS
       +
Superuser authority
       =
Effective row access

An RLS policy does not itself grant the underlying table privilege.
