# 3.19 — Object Maintenance and Schema Change Operations

**Edition:** Revised Final / Canonical Edition

**Chapter:** 3 — PostgreSQL Database and Object Administration

**Status:** COMPLETE — Canonical Edition

## 3.19.1 Purpose and Scope

PostgreSQL production schemas continuously evolve. Applications introduce columns, indexes, constraints, partitions, data types, and new access patterns, while existing objects require maintenance to preserve performance, integrity, storage efficiency, and reliability.

For an SRE or DBRE, a schema change is not simply a DDL statement. It is a **production change capable of affecting locking, concurrency, WAL generation, replication, storage, query plans, application compatibility, CDC pipelines, and availability**.

This section defines the production-safe framework for PostgreSQL object maintenance and schema evolution.

It covers:

* Tables and columns
* Constraints
* Index creation and rebuilding
* Statistics maintenance
* VACUUM operations
* Storage reclamation
* Table rewrites
* Object renaming and schema movement
* Dependencies
* Large-table migrations
* Lock-aware DDL
* Backfills
* Online and low-downtime techniques
* Application/database deployment sequencing
* Replication and CDC protection
* Monitoring and alerting
* Failure handling
* Rollback and forward recovery
* Automation
* Change governance

> **SRE/DBRE principle:** A syntactically valid PostgreSQL DDL statement is not necessarily a production-safe DDL statement.

---

## 3.19.2 Production Schema-Change Risk Model

Every schema change should be evaluated across the following dimensions:

| Dimension     | Production question                                             |
| ------------- | --------------------------------------------------------------- |
| Locking       | Which lock will PostgreSQL acquire?                             |
| Duration      | How long might that lock or operation last?                     |
| Rewrite       | Will PostgreSQL rewrite the table or indexes?                   |
| Storage       | How much temporary storage may be required?                     |
| WAL           | How much WAL might the operation generate?                      |
| Replication   | Can physical replicas keep up?                                  |
| CDC           | Can logical replication consumers keep up?                      |
| Application   | Can old and new application versions coexist?                   |
| Recovery      | Can the operation be rolled back, resumed, or repaired forward? |
| Observability | Can the operator determine whether production remains healthy?  |

Additional considerations include:

* Long-running transactions
* Dependency chains
* Connection-pool behavior
* Autovacuum interaction
* Query-plan changes
* Backup/PITR posture
* Migration idempotency
* Maintenance-window requirements

The correct production question is not:

> “Will this SQL execute?”

It is:

> **“What happens to the production system while this SQL executes, and what happens if it fails halfway?”**

---

## 3.19.3 Production Risk Classification

Schema changes should be classified before execution.

| Risk         | Typical examples                                                   | Production handling                         |
| ------------ | ------------------------------------------------------------------ | ------------------------------------------- |
| **LOW**      | Add nullable column, small metadata change                         | Automated deployment with safeguards        |
| **MEDIUM**   | Concurrent index, `NOT VALID` constraint, controlled backfill      | Monitored deployment                        |
| **HIGH**     | Large validation, substantial backfill, risky type conversion      | DBRE review + controlled window             |
| **CRITICAL** | Multi-TB rewrite, `VACUUM FULL`, destructive/high-impact migration | Maintenance window + explicit recovery plan |

Risk should be calculated from:

```text
Lock strength
      +
Object size
      +
Rewrite behavior
      +
Expected duration
      +
Storage requirement
      +
WAL generation
      +
Replica impact
      +
CDC impact
      +
Application compatibility
      +
Recovery difficulty
```

Identical SQL can have radically different production risk on a 10 MB relation and a 10 TB relation.

## 3.19.4 PostgreSQL DDL Locking

Different `ALTER TABLE` operations require different lock levels. Unless PostgreSQL explicitly documents a weaker lock for a particular subcommand, `ALTER TABLE` acquires `ACCESS EXCLUSIVE`.

When multiple subcommands are executed together, PostgreSQL acquires the strongest lock required by any of them.

`ACCESS EXCLUSIVE` conflicts with essentially all access to the affected relation.

Before production DDL, inspect activity:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Inspect locks:

```sql
SELECT
    l.pid,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation,
    a.usename,
    a.application_name,
    a.query_start,
    a.query
FROM pg_locks l
LEFT JOIN pg_stat_activity a
       ON a.pid = l.pid
WHERE l.relation IS NOT NULL
ORDER BY l.granted, a.query_start;
```

## 3.19.5 Bounded Lock Acquisition

Production DDL should not normally wait indefinitely for a lock.

Example:

```sql
SET lock_timeout = '5s';
SET statement_timeout = '30min';
```

These are examples only. Values must reflect workload characteristics and SLOs.

The desired behavior is:

```text
Request DDL lock
       |
       v
Acquired within approved threshold?
       |
   +---+---+
   |       |
  YES      NO
   |       |
Execute   Abort
           |
           v
      Find blocker
           |
           v
     Reassess/retry
```

> **Production principle:** Failing a migration is normally preferable to unexpectedly freezing application traffic.

Do not automatically terminate the blocking backend. First determine what transaction it represents and the business impact of terminating it.

## 3.19.6 The DDL Lock-Queue Failure Pattern

One of the most dangerous schema-change incidents is:

```text
Transaction A
holds incompatible lock
        |
        v
DDL B requests strong lock
        |
        v
DDL B waits
        |
        v
Application C waits behind B
        |
        v
Application D
        |
        v
Application E
        |
        v
Connection pool exhaustion
```

The DDL may consume almost no CPU while still causing a major outage.

Find blockers:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    now() - query_start AS duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

If migration DDL is causing the queue, the preferred response is generally:

```text
Application latency rising
          |
          v
Identify lock queue
          |
          v
DDL causing downstream blocking?
          |
          v
Cancel DDL when appropriate
          |
          v
Allow application traffic to drain
          |
          v
Investigate original blocker
          |
          v
Retry change safely
```

> **Protect application availability before protecting the migration.**

## 3.19.7 Pre-Change Object Assessment

Before modifying a relation:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    pg_size_pretty(pg_relation_size(c.oid)) AS relation_size,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'app'
  AND c.relname = 'orders';
```

Inspect table and index size:

```sql
SELECT
    pg_size_pretty(pg_relation_size('app.orders')) AS table_size,
    pg_size_pretty(pg_indexes_size('app.orders')) AS indexes_size,
    pg_size_pretty(pg_total_relation_size('app.orders')) AS total_size;
```

Inspect tuple estimates and maintenance state:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
WHERE relid = 'app.orders'::regclass;
```

Production assessment should follow:

```text
Object
  |
  v
Size / row count
  |
  v
Dependencies
  |
  v
Current locks
  |
  v
Long transactions
  |
  v
Required DDL lock
  |
  v
Rewrite?
  |
  v
Storage/WAL impact
  |
  v
Replica/CDC impact
  |
  v
Application compatibility
  |
  v
Recovery strategy
```

## 3.19.8 Adding Columns

A basic nullable-column addition:

```sql
ALTER TABLE app.orders
ADD COLUMN source_system text;
```

is normally substantially safer than operations requiring existing rows to be physically rewritten.

A critical modern PostgreSQL optimization applies to **non-volatile defaults**.

For example:

```sql
ALTER TABLE app.orders
ADD COLUMN status text DEFAULT 'pending';
```

PostgreSQL can store the evaluated non-volatile default in metadata rather than immediately rewriting every existing row.

Therefore:

```text
ADD COLUMN
   |
   +-- nullable/simple column -----------> generally no rewrite
   |
   +-- non-volatile DEFAULT -------------> generally no rewrite
   |
   +-- volatile DEFAULT -----------------> rewrite required
```

Example of a volatile default:

```sql
ALTER TABLE app.orders
ADD COLUMN migration_timestamp timestamptz
DEFAULT clock_timestamp();
```

Such a definition requires existing rows to receive individually evaluated values and can trigger a table rewrite.

The distinction is **non-volatile versus volatile**, not merely “constant versus non-constant.”

---

## 3.19.9 Generated and Special Columns

Modern PostgreSQL also requires operators to distinguish generated-column behavior.

Conceptually:

```text
ADD COLUMN
   |
   +-- stored generated column ----------> rewrite
   |
   +-- virtual generated column ---------> no table rewrite
   |
   +-- identity/special definitions -----> evaluate rewrite behavior
```

Stored generated values must be materialized.

For large relations, generated-column behavior must therefore be included in the migration risk assessment rather than assuming every `ADD COLUMN` is metadata-only.

## 3.19.10 Expand-and-Contract Schema Evolution

For application-facing schemas, prefer backward-compatible evolution.

Suppose:

```text
old_column
```

must become:

```text
new_column
```

Avoid immediately destroying the old interface.

Use:

```text
EXPAND
   |
   v
Add new object
   |
   v
Deploy compatible application
   |
   v
Dual write if necessary
   |
   v
Backfill historical data
   |
   v
Validate
   |
   v
Switch reads
   |
   v
Observe
   |
   v
CONTRACT
   |
   v
Remove obsolete object
```

This provides a crucial property:

> The application can often be rolled back without rolling back the database expansion.

## 3.19.11 Production Deployment Sequence

For substantial schema evolution:

```text
Release N
   |
   v
Expand database
   |
   v
Deploy app supporting old + new
   |
   v
Start new writes / dual writes
   |
   v
Backfill
   |
   v
Validate
   |
   v
Switch reads
   |
   v
Observe
   |
   v
Release N+1
   |
   v
Stop old writes
   |
   v
Observe
   |
   v
Contract database
```

Database migrations should therefore be treated as a compatibility protocol across releases rather than always as a single deployment event.

## 3.19.12 Large-Table Backfills

Avoid uncontrolled operations such as:

```sql
UPDATE app.orders
SET new_status = old_status
WHERE new_status IS NULL;
```

against a very large hot table.

Large updates can cause:

* High WAL generation
* Dead tuples
* Table and index bloat
* Replica lag
* Storage growth
* Autovacuum pressure
* Buffer-cache churn
* I/O contention
* Long transactions

Prefer batches:

```sql
UPDATE app.orders
SET new_status = old_status
WHERE id >= :low_id
  AND id < :high_id
  AND new_status IS NULL;
```

Commit between batches.

---

## 3.19.13 Feedback-Controlled Backfills

A production backfill should behave as a controlled workload:

```text
Execute batch
     |
     v
Commit
     |
     v
Measure
     |
     +-- CPU
     +-- I/O latency
     +-- WAL rate
     +-- replica lag
     +-- CDC lag
     +-- lock waits
     +-- application P95/P99
     |
     v
Healthy?
  +--+--+
  |     |
 YES    NO
  |     |
Next   Reduce batch /
batch  pause migration
```

For very large systems, adaptive throttling is preferable to blindly executing a fixed number of rows per second.

Large migration automation should support:

```text
PAUSE
RESUME
STOP
```

without losing progress.

## 3.19.14 Changing Column Data Types

Example:

```sql
ALTER TABLE app.orders
ALTER COLUMN external_id TYPE bigint
USING external_id::bigint;
```

Column type changes commonly require rewriting the table and rebuilding affected indexes.

However, PostgreSQL can avoid the table rewrite in specific documented cases, including certain binary-compatible transformations where the `USING` expression does not alter stored contents.

Indexes can still require rebuilding depending on whether PostgreSQL can prove they remain semantically valid.

For large relations, evaluate:

* Relation size
* Index size
* Required lock
* Conversion cost
* Rewrite behavior
* Temporary storage
* WAL
* Replica lag
* CDC impact
* Duration

For high-risk conversions, prefer:

```text
Add new typed column
        |
        v
Dual write
        |
        v
Backfill gradually
        |
        v
Validate
        |
        v
Create required indexes
        |
        v
Switch reads
        |
        v
Observe
        |
        v
Retire old column
```

---

## 3.19.15 ANALYZE After Type Changes

PostgreSQL removes column statistics when `SET DATA TYPE` is performed.

Therefore, after an appropriate type migration:

```sql
ANALYZE app.orders;
```

should normally be included in the post-change plan.

A technically successful schema migration can still create a production incident if query planning deteriorates because statistics are stale or absent.

## 3.19.16 Adding Constraints Safely

Direct constraint creation can require expensive historical validation.

For supported constraints, PostgreSQL provides the `NOT VALID` pattern.

Example:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT orders_amount_check
CHECK (amount >= 0)
NOT VALID;
```

Then:

```sql
ALTER TABLE app.orders
VALIDATE CONSTRAINT orders_amount_check;
```

Operational model:

```text
Install NOT VALID constraint
          |
          v
New/changed rows protected
          |
          v
Historical validation later
          |
          v
Constraint fully validated
```

Validation can use a less restrictive locking strategy than performing all validation during initial constraint installation.

Exact `NOT VALID` support and semantics depend on constraint form and PostgreSQL version and must be verified for the target deployment.

---

## 3.19.17 Foreign-Key Validation

A useful large-table pattern is:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES app.customers(id)
NOT VALID;
```

Then separately:

```sql
ALTER TABLE app.orders
VALIDATE CONSTRAINT orders_customer_fk;
```

This separates constraint installation from historical verification.

The operator must still evaluate:

* Referencing-table load
* Referenced-table load
* Required locks
* Validation scan cost
* I/O
* Application latency

`NOT VALID` reduces migration risk; it does not eliminate production cost.

---

## 3.19.18 Creating Unique Constraints with Reduced Write Blocking

Instead of building a unique constraint's backing index while holding a long restrictive lock, a useful production pattern is:

```sql
CREATE UNIQUE INDEX CONCURRENTLY
orders_external_id_uidx
ON app.orders (external_id);
```

After successful validation:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT orders_external_id_key
UNIQUE USING INDEX orders_external_id_uidx;
```

The index must satisfy PostgreSQL's requirements for use as a constraint.

This separates expensive index construction from the relatively short constraint-attachment operation.

---

## 3.19.19 CREATE INDEX Versus CREATE INDEX CONCURRENTLY

Standard creation:

```sql
CREATE INDEX orders_created_at_idx
ON app.orders (created_at);
```

is simpler and usually faster, but interferes with writes in ways that can be unacceptable on busy production tables.

For online production workloads:

```sql
CREATE INDEX CONCURRENTLY orders_created_at_idx
ON app.orders (created_at);
```

allows normal writes to continue while the index is built.

Tradeoffs include:

* More work
* Longer duration
* Multiple phases/scans
* Waiting for transactions/snapshots
* Additional CPU and I/O
* Special transaction restrictions
* Possible invalid index after failure

`CREATE INDEX CONCURRENTLY` cannot be executed inside a normal transaction block.

Only one concurrent index build can run on a given table at a time.

---

## 3.19.20 Invalid Concurrent Indexes

A failed concurrent index operation can leave an invalid index.

Detect:

```sql
SELECT
    indexrelid::regclass AS index_name,
    indisvalid,
    indisready
FROM pg_index
WHERE NOT indisvalid;
```

Do not assume that an index is usable simply because its name exists.

An invalid index may still impose write overhead.

Investigate the cause before dropping, retrying, or rebuilding the index.

Migration automation must explicitly detect this state before retrying.

## 3.19.22 REINDEX Operations

Traditional rebuilding:

```sql
REINDEX INDEX app.orders_created_at_idx;
```

can require restrictive locking.

Where supported:

```sql
REINDEX INDEX CONCURRENTLY app.orders_created_at_idx;
```

is usually better suited to actively written production relations.

Concurrent reindexing:

* Reduces write disruption
* Performs additional work
* Takes longer
* Has operational restrictions
* Cannot be run inside a normal transaction block
* Is not supported for every possible index scenario

Monitor concurrent reindexing through:

```sql
SELECT *
FROM pg_stat_progress_create_index;
```

## 3.19.23 Dropping Columns

Example:

```sql
ALTER TABLE app.orders
DROP COLUMN legacy_code;
```

A critical PostgreSQL behavior is:

```text
DROP COLUMN
     !=
Immediate filesystem-space recovery
```

The column becomes unavailable logically, but PostgreSQL does not necessarily shrink the physical relation immediately.

Before dropping:

1. Remove application usage.
2. Verify database dependencies.
3. Verify ETL/reporting usage.
4. Verify CDC consumers.
5. Observe through a deprecation period.
6. Confirm backup/PITR posture.
7. Execute the destructive change.

---

## 3.19.24 Destructive-Change Quarantine

Operations such as:

```sql
DROP TABLE ...;
DROP COLUMN ...;
DROP ... CASCADE;
```

should receive additional governance.

Recommended lifecycle:

```text
Stop new usage
      |
      v
Dependency verification
      |
      v
Deprecation period
      |
      v
Final usage verification
      |
      v
Backup/PITR confirmation
      |
      v
Explicit approval
      |
      v
Destructive DDL
```

`CASCADE` should be treated as high-risk by default.

> Never use `CASCADE` simply to make a failed DDL statement succeed.

Every dependent object scheduled for removal must be understood.

## 3.19.25 Renaming Objects

Example:

```sql
ALTER TABLE app.orders
RENAME COLUMN customer_ref TO customer_id;
```

or:

```sql
ALTER TABLE app.orders
RENAME TO customer_orders;
```

Renaming can be inexpensive internally while immediately breaking external consumers.

Potential dependencies include:

* Application SQL
* ORMs
* Stored procedures/functions
* Views
* ETL
* BI/reporting
* CDC
* Monitoring
* Backup scripts
* Operational tooling

For application-facing objects, expand-and-contract migration is generally safer than immediate rename.

## 3.19.26 Moving Objects Between Schemas

Example:

```sql
ALTER TABLE staging.orders
SET SCHEMA app;
```

Before moving an object, validate:

* Qualified SQL references
* `search_path`
* Views
* Functions
* Privileges
* Ownership
* ETL
* Monitoring
* Backup tooling
* CDC integrations

A metadata-oriented change can still have broad operational consequences.

## 3.19.28 VACUUM

PostgreSQL MVCC leaves obsolete tuple versions after updates and deletes.

Routine:

```sql
VACUUM app.orders;
```

makes reusable space available and performs essential maintenance.

Normally, autovacuum should handle this continuously.

Monitor:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Do not disable autovacuum globally as a routine performance workaround.

Doing so creates serious bloat and transaction-ID-wraparound risk.

---

## 3.19.29 VACUUM FULL

`VACUUM FULL` is fundamentally different:

```sql
VACUUM FULL app.orders;
```

It rewrites the relation and returns unused space to the operating system.

It also:

* Requires `ACCESS EXCLUSIVE`
* Prevents normal concurrent access
* Can take significant time
* Requires additional working storage
* Produces substantial I/O

Therefore:

> **`VACUUM FULL` is not routine production maintenance.**

Use it only when its benefits justify the disruption and an appropriate maintenance strategy exists.

## 3.19.30 ANALYZE and Planner Statistics

Large migrations can materially change data distribution.

Use when appropriate:

```sql
ANALYZE app.orders;
```

or:

```sql
VACUUM (ANALYZE) app.orders;
```

Monitor:

```sql
SELECT
    relname,
    last_analyze,
    last_autoanalyze,
    analyze_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY last_analyze NULLS FIRST;
```

Post-change query-plan validation is part of migration validation.

## 3.19.32 Table-Rewrite Risk

A rewrite can produce:

```text
ALTER TABLE
     |
     v
Full relation rewrite
     |
     v
Heavy I/O
     |
     v
New physical representation
     |
     v
Index work
     |
     v
WAL generation
     |
     v
Replica/CDC lag
     |
     v
Storage pressure
```

Before starting rewrite-heavy maintenance, calculate storage headroom.

Conceptually:

```text
Free storage
     -
Temporary relation/index growth
     -
Expected WAL growth
     -
Replication-slot exposure
     -
Operational safety reserve
     =
Usable migration headroom
```

If adequate headroom cannot be demonstrated:

> **Do not start the migration.**

Avoid universal free-space percentages. Requirements depend on object size, workload, WAL behavior, replication, and platform architecture.

---

## 3.19.33 MVCC and Long-Running Transactions

Rewrite-heavy operations can interact with existing MVCC snapshots and long-running transactions.

Before major maintenance, inspect:

```sql
SELECT
    pid,
    usename,
    application_name,
    xact_start,
    now() - xact_start AS age,
    state,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Pay particular attention to:

* Long reporting queries
* Idle-in-transaction sessions
* Batch workloads
* Long-running application transactions

These can delay maintenance, hold snapshots, increase bloat, and complicate lock acquisition.

## 3.19.34 WAL and Physical Replication

Large migrations can generate substantial WAL.

Monitor:

```sql
SELECT
    application_name,
    client_addr,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)
    ) AS replay_lag_bytes
FROM pg_stat_replication;
```

Migration control should follow:

```text
Migration
   |
   v
Replica lag acceptable?
   |
 +---+---+
 |       |
YES      NO
 |       |
Continue Throttle
          |
          v
      Still increasing?
          |
       +--+--+
       |     |
      NO    YES
       |     |
    Continue STOP/PAUSE
```

Thresholds must reflect service RPO/RTO and replica freshness requirements.

## 3.19.35 Logical Replication and CDC

Inspect logical replication slots:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn
FROM pg_replication_slots;
```

A dangerous production chain is:

```text
Large migration
      |
      v
High WAL generation
      +
CDC consumer stalled
      |
      v
Replication slot retains WAL
      |
      v
pg_wal growth
      |
      v
Storage exhaustion
```

Replication-slot and CDC health must therefore be checked:

* Before the migration
* During the migration
* After the migration

## 3.19.36 Autovacuum Interaction

Large backfills create obsolete tuples.

Conceptually:

```text
Millions of UPDATEs
       |
       v
New tuple versions
       |
       v
Old versions become dead
       |
       v
VACUUM workload increases
```

Monitor:

```sql
SELECT
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

A migration plan must account for the cleanup workload it creates.

## 3.19.37 Transaction Boundaries

Many DDL operations can participate in transactions:

```sql
BEGIN;

ALTER TABLE app.orders
ADD COLUMN migration_test text;

ROLLBACK;
```

However, some maintenance operations, including important concurrent index operations, cannot execute inside a normal transaction block.

Migration frameworks must understand operation-specific transaction semantics rather than automatically wrapping every migration in one transaction.

---

## 3.19.38 Migration Idempotency and Resume Safety

Production automation must assume retries.

Every migration should answer:

```text
What happens if it runs twice?
What happens if it fails halfway?
How is partial completion detected?
Can it resume?
Can it be safely retried?
```

Recommended state model:

```text
NOT_STARTED
     |
     v
RUNNING
     |
     +------> FAILED
     |
     +------> PARTIAL
                 |
                 v
             RESUMABLE
                 |
                 v
             VALIDATING
                 |
                 v
              COMPLETE
```

Automation must inspect database state before retrying operations such as concurrent index creation.

---

## 3.19.39 Recovery Models

Production migrations require more than a generic “rollback plan.”

## Transactional rollback

Where supported:

```text
BEGIN
  |
DDL
  |
Failure
  |
ROLLBACK
```

## Application rollback

With backward-compatible schema expansion:

```text
Database expansion
       |
Application deployment
       |
Application failure
       |
Rollback application
       |
Expanded schema remains compatible
```

## Forward recovery

For partially completed large migrations:

```text
Partial migration
       |
Correct issue
       |
Resume migration
       |
Validate
```

Forward recovery is often safer than reversing millions or billions of already migrated rows.

## Restore/PITR recovery

Reserved for destructive or catastrophic failures where logical repair is not safe.

Useful signals include:

| Signal              | Concern                   |
| ------------------- | ------------------------- |
| Lock wait           | Application/DDL blocking  |

| CDC lag             | Downstream inconsistency  |

## 3.19.42 Failure Scenario — DDL Blocks Production

### Symptoms

* Application latency rises
* Connections accumulate
* Lock waits increase
* DDL appears stalled

### Investigation

```sql
SELECT
    pid,
    pg_blocking_pids(pid),
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state <> 'idle';
```

### Response

1. Identify the blocking chain.
2. Determine whether migration DDL is amplifying the queue.
3. Cancel the DDL when protecting availability requires it.
4. Allow application traffic to recover.
5. Investigate the original blocker.
6. Retry during a safer period.
7. Improve timeout controls.

---

## 3.19.43 Failure Scenario — Replica Lag Explosion

Symptoms:

```text
Primary healthy
      |
WAL increasing
      |
Replica lag increasing
      |
Read replica becoming stale
```

Response:

1. Measure lag.
2. Reduce migration throughput.
3. Pause if lag continues growing.
4. Determine replica bottleneck.
5. Resume only when sufficient capacity exists.

Do not judge migration health from the writer alone.

---

## 3.19.44 Failure Scenario — WAL/CDC Storage Exhaustion

Potential chain:

```text
Backfill/rewrite
      |
High WAL
      |
Inactive/stalled logical consumer
      |
Slot retains WAL
      |
Storage growth
      |
Critical disk pressure
```

Response:

1. Stop or throttle migration.
2. Identify retained WAL.
3. Determine CDC/slot health.
4. Restore downstream consumption where possible.
5. Protect database storage.
6. Resume only after adequate headroom is restored.

---

## 3.19.45 Failure Scenario — Invalid Concurrent Index

Detect:

```sql
SELECT
    indexrelid::regclass,
    indisvalid,
    indisready
FROM pg_index
WHERE NOT indisvalid;
```

Response:

1. Determine why the build failed.
2. Do not blindly retry.
3. Decide whether to drop or rebuild the invalid index.
4. Recheck locks, capacity, and workload.
5. Retry safely.
6. Validate index state afterward.

---

## 3.19.46 Failure Scenario — Backfill Overload

Symptoms:

* CPU saturation
* Storage latency
* WAL spike
* Replica/CDC lag
* Dead-tuple growth
* Application latency

Response:

```text
Reduce batch size
      |
Increase pacing
      |
Observe
      |
Still unhealthy?
   +--+--+
   |     |
  NO    YES
   |     |
Resume  PAUSE
```

A migration should yield to production workload.

---

## 3.19.47 Failure Scenario — Application Incompatibility

Typical failure:

```text
Database change
      |
Old application instance remains
      |
Old SQL contract broken
      |
Production errors
```

Prevention:

```text
Backward-compatible expansion
       |
Application rollout
       |
Migration
       |
Observation
       |
Contract later
```

Schema and application releases must be designed together.

## 3.19.48 Production Case Study — Large Foreign Key

Assume:

```text
orders       = 800 million rows
customers    = 40 million rows
```

Instead of immediately validating everything:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES app.customers(id)
NOT VALID;
```

Observe production.

Then:

```sql
ALTER TABLE app.orders
VALIDATE CONSTRAINT orders_customer_fk;
```

Confirm:

```sql
SELECT
    conname,
    convalidated
FROM pg_constraint
WHERE conname = 'orders_customer_fk';
```

Expected final state:

```text
convalidated = true
```

The expensive historical validation has been separated from initial constraint installation.

---

## 3.19.49 Production Case Study — Adding an Indexed Column

Requirement:

```text
Add source_system
Populate historical data
Index it
Enable application queries
```

Safe sequence:

```text
ADD nullable column
       |
Deploy compatible application
       |
Start writing new values
       |
Batch historical backfill
       |
Monitor WAL/replicas/CDC
       |
ANALYZE
       |
CREATE INDEX CONCURRENTLY
       |
Validate index
       |
Enable query path
       |
Observe
```

Do not combine all phases into one giant transaction.

## 3.19.50 Production Case Study — Multi-TB Type Migration

Suppose:

```text
customer_id varchar
```

must become:

```text
customer_id bigint
```

For a multi-terabyte table, direct conversion may be operationally unacceptable.

Alternative:

```sql
ALTER TABLE app.orders
ADD COLUMN customer_id_bigint bigint;
```

Then:

```text
Dual write
    |
Batch backfill
    |
Validate conversion
    |
Build indexes concurrently
    |
Update constraints
    |
Switch reads
    |
Observe
    |
Stop old writes
    |
Deprecation period
    |
Remove old column
```

This converts one dangerous operation into multiple controllable phases.

## 3.19.51 Operational Decision Matrix

| Operation                | Primary risk           | Preferred production approach             |
| ------------------------ | ---------------------- | ----------------------------------------- |
| Add nullable column      | Lock acquisition       | Short bounded DDL                         |
| Add non-volatile default | Lock acquisition       | Verify behavior; bounded DDL              |
| Add volatile default     | Rewrite                | Avoid direct operation on huge hot tables |
| Stored generated column  | Rewrite                | Assess size/capacity first                |
| Add foreign key          | Validation/locking     | `NOT VALID` → `VALIDATE`                  |
| Add unique constraint    | Index construction     | Concurrent unique index → attach          |
| Create index             | Write interference     | `CREATE INDEX CONCURRENTLY`               |
| Rebuild index            | Locking                | `REINDEX CONCURRENTLY` where supported    |
| Drop column              | Compatibility          | Expand/contract                           |
| Rename column            | Compatibility          | Expand/contract                           |
| Change type              | Rewrite                | New column + backfill for large tables    |
| Massive update           | WAL/bloat              | Batched adaptive migration                |
| VACUUM                   | Resource usage         | Autovacuum/routine VACUUM                 |
| VACUUM FULL              | Exclusive lock/rewrite | Controlled maintenance window             |

This matrix is guidance. PostgreSQL version, relation type, workload, size, and architecture always matter.

## 3.19.58 Golden Rules

1. **Know the lock before executing DDL.**
2. **Know whether PostgreSQL will rewrite the relation.**
3. **Measure the object before changing it.**
4. **Check long-running transactions first.**
5. **Use bounded lock waits.**
6. **Prefer additive changes over destructive changes.**
7. **Use expand-and-contract for application-facing schemas.**
8. **Batch large data migrations.**
9. **Make backfills throttleable and resumable.**
10. **Use concurrent index operations where appropriate.**
11. **Use `NOT VALID` and separate validation where supported.**
12. **Monitor physical replicas.**
13. **Monitor logical replication and CDC.**
14. **Account for temporary disk and WAL requirements.**
15. **Never use `CASCADE` without dependency review.**
16. **Refresh statistics when required.**
17. **Validate query plans after material changes.**
18. **Design recovery before execution.**
19. **Prefer forward recovery when reversal is more dangerous.**
20. **Treat schema changes as production deployments.**

## 3.19.59 SRE/DBRE Mental Model

Before approving any significant PostgreSQL schema operation, answer:

```text
What lock does it need?

Will it rewrite the relation?

How long can it run?

How much temporary storage does it need?

How much WAL can it generate?

Can replicas keep up?

Can CDC consumers keep up?

Can old application versions survive it?

Can the operation be paused?

Can it be resumed?

What happens if it fails halfway?

How will we know production is unhealthy?

What is our stop condition?

How do we recover?
```

If these questions cannot be answered, the production change is not ready.

## 3.19.60 Key Takeaways

PostgreSQL object maintenance and schema evolution are **reliability-engineering operations**, not merely SQL administration.

The safest operational lifecycle is:

```text
UNDERSTAND
    |
    v
MEASURE
    |
    v
CLASSIFY RISK
    |
    v
TEST
    |
    v
PRE-CHECK
    |
    v
EXECUTE WITH GUARDRAILS
    |
    v
MONITOR
    |
    v
VALIDATE
    |
    v
STABILIZE
    |
    v
COMPLETE
```

The core SRE/DBRE principle is:

> **Never judge a PostgreSQL schema change only by whether the SQL succeeds. Judge it by whether the database, replicas, downstream consumers, and application remain reliable throughout the change and after it completes.**
