## 3.2.1 Purpose

Creating, modifying, and removing databases are fundamental PostgreSQL administrative operations. The primary commands are `CREATE DATABASE`, `ALTER DATABASE`, and `DROP DATABASE`; their syntax is simple, but their production consequences affect availability, ownership, security, connection management, encoding, locale, collation, templates, tablespaces, WAL, replication, backups, recovery, monitoring, automation, and external integrations.

For an SRE, DBRE, or production DBA, a PostgreSQL database is a managed production resource with a lifecycle: requirement, design, provision, secure, validate, operate, modify, monitor, retire, and recover if required.

## 3.2.2 PostgreSQL Database Creation Architecture

A PostgreSQL database exists inside a PostgreSQL database cluster. Database creation is performed by cloning an existing database, normally `template1` unless another template is specified.

Conceptually:

```text
PostgreSQL Cluster
|
+-- template0
+-- template1
+-- postgres
|
+-- application_db
+-- reporting_db
`-- analytics_db
```

The selected template can influence the contents and characteristics of the new database. Template administration is covered in Section 3.3.

## 3.2.3 Database Creation Privileges

A role creating a database normally requires superuser privileges or the `CREATEDB` role attribute.

```sql
CREATE ROLE db_provisioner
LOGIN
CREATEDB;

SELECT
    rolname,
    rolsuper,
    rolcreatedb,
    rolcanlogin
FROM pg_roles
ORDER BY rolname;
```

Do not grant `CREATEDB` to application runtime identities without a specific reviewed requirement. Database creation should normally be limited to DBA identities, DBRE automation, provisioning services, and approved administrative roles.

## 3.2.4 Provisioning Identity Versus Database Owner

The identity provisioning a database does not have to become its permanent owner. A production model separates provisioning identity, database owner, and application runtime identity.

```sql
CREATE ROLE application_db_owner NOLOGIN;

CREATE DATABASE application_db
OWNER application_db_owner;
```

When specifying another role as owner, the provisioning identity must satisfy PostgreSQL ownership and role requirements, including the ability to `SET ROLE` to the requested owner unless operating with the necessary superuser authority.

## 3.2.5 Basic Database Creation

```sql
CREATE DATABASE application_db;

SELECT
    datname,
    pg_get_userbyid(datdba) AS owner
FROM pg_database
WHERE datname = 'application_db';
```

Successful execution confirms that PostgreSQL created the database. It does not prove that the database satisfies production requirements.

## 3.2.6 Database Naming Standards

Database names should be consistent, predictable, automation-friendly, unambiguous, and aligned with organizational standards. Examples include `orders_prod`, `orders_stage`, `orders_dev`, `billing_prod`, `billing_stage`, and `billing_dev`.

Avoid unnecessarily complex quoted identifiers such as:

```sql
CREATE DATABASE "Production Billing Database";
```

Prefer simple identifiers where standards permit:

```sql
CREATE DATABASE billing_prod;
```

## 3.2.7 Encoding

Encoding can be specified during database creation.

```sql
CREATE DATABASE application_db
ENCODING 'UTF8';

CREATE DATABASE application_db
WITH
    TEMPLATE template0
    ENCODING 'UTF8';
```

Encoding must be considered together with locale, collation, character classification, and template selection.

## 3.2.8 Locale and Collation Design

Locale and collation influence sorting, comparison behavior, character classification, indexes involving collatable values, and application-visible ordering.

```sql
SELECT
    datname,
    encoding,
    datcollate,
    datctype
FROM pg_database
ORDER BY datname;
```

These choices require special attention for multilingual applications, migrations, deterministic sorting requirements, operating-system upgrades, and collation-library changes.

## 3.2.9 template1

`template1` is normally the default template. Objects intentionally added to `template1` can be propagated into subsequently created databases.

```sql
CREATE DATABASE application_db
TEMPLATE template1;
```

Changes to `template1` should be deliberate, controlled, documented, and version-aware.

## 3.2.10 template0

`template0` provides a pristine baseline and should not be modified.

```sql
CREATE DATABASE application_db
WITH
    TEMPLATE template0
    ENCODING 'UTF8';
```

Use `template0` when desired database characteristics cannot safely be derived from `template1`.

## 3.2.11 Template Concurrency

Creating a database from a template/source database requires PostgreSQL to obtain a stable source. Existing connections to the source can prevent the operation.

```sql
CREATE DATABASE new_db TEMPLATE production_db;
```

Do not treat this as a general-purpose online database copy mechanism. For production cloning and migration, use backup, recovery, replication, or platform-specific cloning technology appropriate to the requirement.

## 3.2.12 PostgreSQL 18 Database Copy Strategies

PostgreSQL 18 supports database creation strategies including `WAL_LOG` and `FILE_COPY`.

```sql
CREATE DATABASE application_db
WITH
    STRATEGY = WAL_LOG;

CREATE DATABASE application_db
WITH
    STRATEGY = FILE_COPY;
```

`WAL_LOG` is the normal default. `FILE_COPY` can reduce WAL volume for large templates but forces checkpoints before and after database creation and can affect system performance.

## 3.2.13 PostgreSQL 18 file_copy_method

PostgreSQL 18 includes `file_copy_method`, which affects applicable file-copy operations such as `CREATE DATABASE ... STRATEGY = FILE_COPY` and `ALTER DATABASE ... SET TABLESPACE`. SRE/DBRE teams should validate this behavior against representative production storage before relying on it for large-scale provisioning.

## 3.2.14 Connection Limits

A database-specific connection limit can be configured:

```sql
CREATE DATABASE application_db
CONNECTION LIMIT 100;

SELECT
    datname,
    datconnlimit
FROM pg_database
WHERE datname = 'application_db';
```

A value of `-1` means no database-specific connection limit. Effective connection availability also depends on authentication, `CONNECT` privilege, role capabilities, cluster `max_connections`, reserved connection capacity, and pooling architecture.

## 3.2.15 Provisioning with Connections Disabled

PostgreSQL allows a database to be created with connections disabled:

```sql
CREATE DATABASE application_db
ALLOW_CONNECTIONS false;

ALTER DATABASE application_db
ALLOW_CONNECTIONS true;
```

This supports controlled provisioning where schemas, extensions, ownership, privileges, default privileges, monitoring, backup, and validation are completed before application onboarding.

## 3.2.16 Tablespace Selection During Creation

Where supported:

```sql
CREATE DATABASE application_db
TABLESPACE application_ts;
```

Tablespaces affect physical storage placement. Managed platforms may restrict or abstract tablespace behavior, so cloud-specific behavior must be validated separately against official vendor documentation.

## 3.2.17 CREATE DATABASE Is Not Transactional

`CREATE DATABASE` cannot execute inside a transaction block.

```sql
BEGIN;
CREATE DATABASE application_db;
COMMIT;
```

Transaction rollback cannot be used as the primary recovery mechanism for database provisioning. Use preflight checks, creation, validation, and controlled cleanup or recovery if the result is incorrect.

## 3.2.18 Post-Creation Validation

Immediately after creation, validate catalog state and then validate connectivity after connections are enabled.

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner,
    encoding,
    datcollate,
    datctype,
    datallowconn,
    datconnlimit
FROM pg_database
WHERE datname = 'application_db';

SELECT
    current_database(),
    current_user,
    session_user;

SHOW search_path;
```

Production provisioning should validate identity, ownership, encoding, locale, connection policy, schemas, extensions, privileges, configuration, monitoring, backup, and recovery before application onboarding.

## 3.2.19 ALTER DATABASE

`ALTER DATABASE` manages database-level properties including rename, ownership change, connection-limit changes, allowing/disallowing connections, database-specific configuration, tablespace movement, and collation-version administration. Each subcommand has different privilege, locking, connection, storage, and risk characteristics.

## 3.2.20 Changing Database Ownership

```sql
ALTER DATABASE application_db
OWNER TO application_db_owner;

SELECT
    datname,
    pg_get_userbyid(datdba) AS owner
FROM pg_database
WHERE datname = 'application_db';
```

Changing database ownership does not automatically redesign ownership of schemas, tables, sequences, functions, privileges, or default privileges inside the database.

## 3.2.21 Renaming a Database

```sql
ALTER DATABASE application_db
RENAME TO orders_db;
```

The currently connected database cannot be renamed. Connect to `postgres` or another database first. A rename affects connection strings, secrets, environment variables, connection pools, ETL/ELT, monitoring, backup/restore automation, scheduled jobs, CI/CD, scripts, external integrations, documentation, and inventory.

## 3.2.22 Changing the Connection Limit

```sql
ALTER DATABASE application_db
CONNECTION LIMIT 200;

SELECT
    datname,
    datconnlimit
FROM pg_database
WHERE datname = 'application_db';
```

Before increasing limits, evaluate application pool size, application replica count, jobs, administrative connections, monitoring connections, cluster `max_connections`, and pooler capacity.

## 3.2.23 Database-Specific Configuration

```sql
ALTER DATABASE application_db
SET statement_timeout = '5min';

SHOW statement_timeout;

ALTER DATABASE application_db
RESET statement_timeout;

ALTER DATABASE application_db
RESET ALL;
```

Choose configuration scope deliberately: cluster, database, role, role plus database, session, or transaction. Use the narrowest appropriate scope.

## 3.2.24 Allowing and Disallowing Connections

```sql
ALTER DATABASE application_db
ALLOW_CONNECTIONS false;

ALTER DATABASE application_db
ALLOW_CONNECTIONS true;

SELECT
    datname,
    datallowconn
FROM pg_database
WHERE datname = 'application_db';
```

Disabling connections can support provisioning, retirement, maintenance, and migration cutover, but it is only one part of production quiescence.

## 3.2.25 Changing the Default Tablespace

```sql
ALTER DATABASE application_db
SET TABLESPACE new_tablespace;
```

This is a storage migration, not merely a metadata change. PostgreSQL moves tables and indexes in the old default tablespace to the new default tablespace; objects explicitly located elsewhere are not moved merely because the default changes. No one can be connected to the database during the operation.

Preflight should evaluate database size, current objects, target storage capacity, tablespace permissions, I/O capacity, duration, outage, backup/recovery, and storage health.

## 3.2.26 Collation Version Administration

PostgreSQL tracks collation-version information. After operating-system, libc, ICU, or collation-provider changes, administrators may need:

```sql
ALTER DATABASE application_db
REFRESH COLLATION VERSION;
```

Refreshing the recorded version does not itself repair indexes or other objects whose ordering assumptions changed. Identify provider changes, affected collations, dependent objects, rebuild requirements, repair/rebuild work, and validation before refreshing the recorded version.

## 3.2.27 Inspecting Database Connections

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = 'application_db'
ORDER BY query_start;

SELECT
    datname,
    count(*) AS connections
FROM pg_stat_activity
WHERE datname = 'application_db'
GROUP BY datname;
```

Unexpected sessions should be treated as evidence of incomplete dependency discovery.

## 3.2.28 Terminating Database Sessions

```sql
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = 'application_db'
  AND pid <> pg_backend_pid();
```

Session termination can roll back active transactions, interrupt jobs, cause application errors, and create reconnect storms. Inspect and understand sessions before terminating them.

## 3.2.29 Application Reconnect Storms

Terminating sessions while an application pool remains active can create a loop of disconnect, reconnect, terminate, reconnect. The correct sequence is to stop writes, drain or stop applications, disable reconnect behavior, prevent new database connections, inspect remaining sessions, and terminate only when required.

## 3.2.30 Dropping a Database

```sql
DROP DATABASE application_db;
```

`DROP DATABASE` permanently removes the database and contained objects. Treat it as a destructive production infrastructure operation with no transactional rollback and independent recovery requirements.

## 3.2.31 DROP DATABASE Is Not Transactional

`DROP DATABASE` cannot execute inside a transaction block and cannot be rolled back by `ROLLBACK`. Use change control, target verification, recovery validation, and post-drop observation.

## 3.2.32 Dropping the Current Database Is Not Allowed

PostgreSQL does not allow dropping the database to which the session is connected. Connect to `postgres` or another administrative database before issuing the command.

## 3.2.33 DROP DATABASE IF EXISTS

```sql
DROP DATABASE IF EXISTS application_db;
```

`IF EXISTS` makes missing-object handling safer by emitting a notice instead of an error when the database is absent. It does not make dropping an existing production database safe.

## 3.2.34 DROP DATABASE ... WITH (FORCE)

```sql
DROP DATABASE application_db
WITH (FORCE);
```

`FORCE` attempts to terminate existing connections, but it is not unconditional. Prepared transactions, active logical replication slots, subscriptions, or un-terminable connections can prevent completion. Normal retirement should not begin with `FORCE`.

## 3.2.35 Prepared Transactions

Prepared transactions require special attention during retirement.

```sql
SELECT
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
WHERE database = 'application_db';
```

No `pg_stat_activity` sessions does not mean the database has no transactional state. Never arbitrarily commit or roll back an unknown prepared transaction.

## 3.2.36 Logical Replication Dependencies

Database retirement must consider subscriptions, replication slots, publishers, subscribers, and external CDC consumers. Logical replication slots can retain WAL or represent active downstream dependencies. Identify topology and ownership, coordinate shutdown, remove replication state safely, and validate before continuing retirement.

## 3.2.37 Pre-Drop Dependency Model

A pre-drop assessment should consider application sessions, reconnects, scheduled jobs, ETL/ELT, reporting, prepared transactions, logical replication, CDC consumers, backups, monitoring, and external integrations. Unexpected activity should pause the retirement until ownership and purpose are understood.

## 3.2.38 Recovery Validation Before Destruction

Do not accept "backup exists" as sufficient evidence of recoverability. Validate backup completion, required recovery point, retention, encryption keys, credentials, documented restore procedure, restore dependencies, and recovery test evidence.

## 3.2.39 Production Database Creation Runbook

### Step 1 - Define requirements

Document name, environment, application, provisioning identity, owner role, encoding, locale, template, copy strategy, connection limit, connection policy, tablespace, backup, recovery, and monitoring requirements.

### Step 2 - Verify target cluster

```sql
SELECT
    current_database(),
    current_user,
    session_user,
    inet_server_addr(),
    inet_server_port();
```

### Step 3 - Verify provisioning privileges

```sql
SELECT
    rolname,
    rolsuper,
    rolcreatedb,
    rolcanlogin
FROM pg_roles
WHERE rolname = current_user;
```

### Step 4 - Verify owner role

```sql
SELECT
    rolname,
    rolcanlogin
FROM pg_roles
WHERE rolname = 'application_db_owner';
```

### Step 5 - Check existence

```sql
SELECT datname
FROM pg_database
WHERE datname = 'application_db';
```

### Step 6 - Validate template

Determine whether `template1`, `template0`, or an approved custom template is required. Check source-template activity where relevant.

### Step 7 - Assess capacity

For substantial template databases evaluate source size, storage, I/O, WAL, replication, checkpoint impact, and expected duration.

### Step 8 - Create

```sql
CREATE DATABASE application_db
WITH
    OWNER = application_db_owner
    ENCODING = 'UTF8'
    CONNECTION LIMIT = 100;
```

Add explicit `TEMPLATE`, `LOCALE`, `TABLESPACE`, `STRATEGY`, and `ALLOW_CONNECTIONS` only according to validated requirements.

### Step 9 - Validate catalog

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner,
    encoding,
    datcollate,
    datctype,
    datallowconn,
    datconnlimit
FROM pg_database
WHERE datname = 'application_db';
```

### Step 10 - Configure

Apply required schemas, ownership, privileges, default privileges, approved extensions, and database settings.

### Step 11 - Integrate operations

Configure backup, monitoring, alerting, logging, recovery, automation, and inventory.

### Step 12 - Enable application access

```sql
ALTER DATABASE application_db
ALLOW_CONNECTIONS true;
```

### Step 13 - Application validation

Confirm connectivity, authentication, privileges, schema access, workload behavior, monitoring, and backup enrollment.

## 3.2.40 Production Database Rename Runbook

### Step 1 - Inventory dependencies

Identify applications, secrets, pools, jobs, ETL/ELT, monitoring, backups, restore automation, CI/CD, scripts, integrations, and inventory.

### Step 2 - Coordinate application change

Prepare new connection configuration.

### Step 3 - Connect to another database

Connect to `postgres` or another administrative database.

### Step 4 - Inspect target connections

```sql
SELECT
    pid,
    usename,
    application_name,
    state
FROM pg_stat_activity
WHERE datname = 'application_db';
```

### Step 5 - Perform approved rename

```sql
ALTER DATABASE application_db
RENAME TO orders_db;
```

### Step 6 - Update dependencies

Update consumers and operational systems.

### Step 7 - Validate

Confirm application connectivity, jobs, monitoring, backup, automation, and external integrations.

## 3.2.41 Production Database Drop Runbook

### Step 1 - Confirm identity

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner,
    pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database
WHERE datname = 'application_db';
```

### Step 2 - Confirm authorization

Record application owner, database owner, change record, retention requirement, recovery requirement, and approval. Consider independent second-engineer validation for critical databases.

### Step 3 - Validate recovery

Confirm backup, recovery point, retention, restore procedure, encryption keys, credentials, and recovery test evidence.

### Step 4 - Stop application writes

Quiesce write activity.

### Step 5 - Drain applications

Stop or drain services and disable automatic reconnect behavior where required.

### Step 6 - Prevent new connections

```sql
ALTER DATABASE application_db
ALLOW_CONNECTIONS false;
```

### Step 7 - Inspect sessions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query
FROM pg_stat_activity
WHERE datname = 'application_db';
```

### Step 8 - Inspect prepared transactions

```sql
SELECT
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
WHERE database = 'application_db';
```

### Step 9 - Inspect logical replication

Identify subscriptions, logical replication slots, CDC consumers, and replication dependencies.

### Step 10 - Terminate remaining sessions if approved

```sql
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE datname = 'application_db'
  AND pid <> pg_backend_pid();
```

### Step 11 - Final destructive verification

Run the identity check again immediately before deletion.

### Step 12 - Drop

```sql
DROP DATABASE application_db;
```

Use `FORCE` only when specifically justified and its limitations are understood.

### Step 13 - Verify removal

```sql
SELECT datname
FROM pg_database
WHERE datname = 'application_db';
```

Expected result: `0 rows`.

### Step 14 - Observe

Monitor failed application connections, failed jobs, pipeline errors, monitoring alerts, and unexpected consumer activity.

### Step 15 - Clean up

Remove or update monitoring, alerts, backup jobs, secrets, connection pools, automation, service discovery, documentation, and inventory.

### Step 16 - Close change

Record drop timestamp, operator, approval, backup reference, recovery point, validation, unexpected consumers, and cleanup completion.

## 3.2.42 Failure Scenario - Wrong Database Owner

If a database is accidentally created under an administrator identity, inspect ownership and correct it:

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner
FROM pg_database
WHERE datname = 'application_db';

ALTER DATABASE application_db
OWNER TO application_db_owner;
```

Then separately validate schema, table, sequence, function, privilege, and default privilege ownership.

## 3.2.43 Failure Scenario - Rename Breaks Applications

A rename such as `ALTER DATABASE billing RENAME TO billing_prod;` can break applications still connecting to `billing`. Prevent this with dependency inventory, coordinated configuration change, connection validation, and monitoring.

## 3.2.44 Failure Scenario - Reconnect Storm During Retirement

If sessions are terminated while the application remains active, the pool may reconnect repeatedly. Correct the sequence by stopping or draining the application, preventing new connections, inspecting remaining sessions, and terminating only when required.

## 3.2.45 Failure Scenario - Prepared Transaction Blocks Retirement

`pg_stat_activity` can show no meaningful sessions while `pg_prepared_xacts` still contains a prepared transaction. Pause retirement, identify the distributed transaction owner, and coordinate resolution.

## 3.2.46 Failure Scenario - Logical Replication Dependency

A retired application database may still act as a logical-replication source. Dropping it without examining replication can disrupt CDC pipelines, audit systems, data warehouses, migrations, or downstream consumers.

## 3.2.47 Failure Scenario - Wrong Database Dropped

Wrong-environment or wrong-target drops are catastrophic. Prevent them with environment separation, least privilege, explicit identity checks, protected database lists, change approval, validated recovery, second-person verification, and automation guardrails.

## 3.2.48 Destructive Automation Guardrails

Database-drop automation should validate environment, cluster, database, protected database list, production status, recovery evidence, dependencies, and final confirmation. At minimum, protect `template0`, `template1`, `postgres`, and organization-defined critical databases.

## 3.2.49 Two-Person Destructive Validation

For critical production environments, require independent validation of environment, cluster, database, owner, size, application, backup, recovery point, and approval before execution. This is an organizational production control, not a PostgreSQL requirement.

## 3.2.50 Monitoring and Audit

Monitor database availability, size, growth rate, connection count, connection saturation, transaction activity, backup status, replication health, ownership drift, configuration drift, unexpected creation, and unexpected removal. Controlled environments should emit audit or change events for `CREATE DATABASE`, `ALTER DATABASE`, and `DROP DATABASE` where supported.

## 3.2.51 Production Case Study - Safe Database Retirement

### Scenario

An application migrates from `orders_v1` to `orders_v2`. The DBRE does not immediately execute `DROP DATABASE orders_v1`; instead, they confirm migration, inventory consumers, inspect sessions, scheduled jobs, prepared transactions, logical replication, validate backup and recovery point, stop writes, drain the application, prevent new connections, observe, verify identity again, drop, observe after deletion, and clean up.

During observation, a reporting job is discovered still connecting to `orders_v1`, so the drop is stopped and the reporting dependency is migrated first.

### Lesson

Unexpected activity is evidence that dependency inventory is incomplete. A good DBRE process treats it as information rather than something to terminate blindly.

## 3.2.53 SRE/DBRE Production Principles

1. Design before creating.
2. Separate provisioning, owner, runtime, and administrative identities.
3. Understand database creation cost.
4. Validate before onboarding applications.
5. Treat rename as infrastructure change.
6. Treat tablespace movement as storage migration.
7. Drain before terminating sessions.
8. Investigate unexpected consumers.
9. Validate recovery before destruction.
10. Verify destructive targets twice.
11. Protect critical databases through automation.
12. Observe after deletion.

## 3.2.54 Section Summary

PostgreSQL provides three fundamental database lifecycle operations: `CREATE DATABASE`, `ALTER DATABASE`, and `DROP DATABASE`. Production reliability requires a broader model that includes database identity, ownership, encoding, locale and collation, template, copy strategy, connection controls, security, storage, replication, monitoring, backup, recovery, dependency management, and lifecycle automation.

Core operational principles: design before creating, validate before modifying, drain before disrupting, verify recoverability before destroying, and treat database lifecycle operations as production infrastructure changes.
