## 3.20.1 Purpose and Scope

PostgreSQL is a catalog-driven database system. Databases, schemas, relations, columns, indexes, constraints, functions, types, ownership, privileges, dependencies, partitions, extensions, security policies, and logical-replication configuration are represented through PostgreSQL metadata.

For SREs and DBREs, this metadata forms the database's operational control plane.

It answers questions such as:

What objects exist?
Where do they exist?
Who owns them?
What privileges are effective?
What depends on an object?
Are indexes valid and ready?
Are constraints validated?
Is RLS enabled?
What policies apply?
How is a table partitioned?
What is its replica identity?
What extensions are installed?
What is published or subscribed?
Has production drifted from its intended state?

The production objective is not merely to learn PostgreSQL catalog tables. It is to build a reliable process for:

DISCOVER
   |
   v
UNDERSTAND
   |
   v
VALIDATE
   |
   v
COMPARE
   |
   v
CHANGE SAFELY
   |
   v
VALIDATE AGAIN
   |
   v
MONITOR FOR DRIFT

SRE/DBRE principle: Read PostgreSQL metadata to understand database state; change that state through supported PostgreSQL SQL and DDL interfaces.

## 3.20.2 PostgreSQL Metadata Architecture

Three major metadata interfaces should be distinguished:

PostgreSQL Metadata
        |
        +-- information_schema
        |       |
        |       +-- SQL-standard
        |       +-- portable
        |       +-- privilege-aware
        |
        +-- pg_catalog
        |       |
        |       +-- PostgreSQL-specific
        |       +-- deep object metadata
        |       +-- OIDs/dependencies
        |
        +-- PostgreSQL views/functions
                |
                +-- pg_tables
                +-- pg_indexes
                +-- pg_policies
                +-- pg_roles
                +-- pg_stat_*
                +-- pg_get_*()
                +-- privilege functions

Use the least implementation-dependent interface that provides the information required.

Need standard portable metadata?
          |
          +--> information_schema

Need PostgreSQL-specific metadata?
          |
          +--> pg_catalog / PostgreSQL views
## 3.20.3 information_schema

information_schema implements SQL-standard metadata views.

Example:

SELECT
    table_schema,
    table_name,
    table_type
FROM information_schema.tables
WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
ORDER BY table_schema, table_name;

It is useful for:

Portable tooling
Tables and columns
Standard constraints
Standard privilege information
Application-oriented metadata discovery

However, many information-schema views expose information according to the privileges and ownership of the current user.

Therefore:

No row returned
      !=
Object definitely does not exist

It can instead mean:

Object absent
     OR
Object not visible to this identity

A governance collector requiring authoritative inventory must have appropriate visibility.

## 3.20.4 pg_catalog

pg_catalog contains PostgreSQL's system catalogs and many built-in database objects.

Examples include:

pg_class
pg_attribute
pg_namespace
pg_index
pg_constraint
pg_depend
pg_database
pg_proc
pg_type
pg_extension
pg_policy
pg_publication
pg_subscription

PostgreSQL implicitly searches pg_catalog when it is absent from search_path, before explicitly listed schemas. Explicitly placing it in search_path allows its search position to be controlled.

For administrative automation, explicit qualification is often preferable:

SELECT *
FROM pg_catalog.pg_class;

This reduces dependence on session-specific name resolution.

## 3.20.5 Database-Local and Cluster-Wide Metadata

Most PostgreSQL catalogs describe objects in the current database.

Some catalogs are shared across the PostgreSQL cluster.

Conceptually:

PostgreSQL Cluster
        |
        +-- Shared metadata
        |       |
        |       +-- databases
        |       +-- roles
        |       +-- tablespaces
        |       +-- shared dependencies
        |
        +-- Database A
        |       |
        |       +-- relations
        |       +-- columns
        |       +-- constraints
        |       +-- local dependencies
        |
        +-- Database B
                |
                +-- independent local catalogs

Important shared metadata includes catalogs such as:

pg_database
pg_authid
pg_tablespace
pg_shdepend

A metadata collector connected only to the postgres database cannot inventory every database-local relation in the cluster.

Production inventory should enumerate relevant databases and collect local metadata from each one.

## 3.20.6 Object Identifiers — OIDs

PostgreSQL uses OIDs extensively to identify catalog objects.

Example:

SELECT
    oid,
    relname,
    relkind
FROM pg_class
WHERE relname = 'orders';

Catalog relationships commonly use OIDs:

pg_class.oid
      |
      +--> pg_attribute.attrelid
      +--> pg_index.indrelid
      +--> pg_constraint.conrelid

OIDs are excellent runtime identifiers.

They should not normally be used as durable external object identifiers across:

Dump/restore
Independent clusters
Rebuilds
Environment migrations
Long-lived Git baselines

Use:

Durable identity
      |
      +-- environment/cluster
      +-- database
      +-- schema
      +-- object type
      +-- object name
      +-- signature where necessary

Runtime identity
      |
      +-- OID
## 3.20.7 regclass and Related Alias Types

PostgreSQL provides object-identifier alias types including:

regclass
regtype
regproc
regprocedure
regnamespace
regrole

Example:

SELECT 'app.orders'::regclass;

Then:

SELECT
    oid,
    relname
FROM pg_class
WHERE oid = 'app.orders'::regclass;

For automation, prefer schema-qualified names:

'app.orders'::regclass

rather than:

'orders'::regclass

because the latter depends on name resolution and search_path.

## 3.20.8 pg_namespace — Schema Metadata

Schemas are represented through pg_namespace.

SELECT
    oid,
    nspname,
    nspowner::regrole AS owner
FROM pg_namespace
ORDER BY nspname;

Production inventory should identify:

Unexpected schemas
Incorrect owners
Legacy schemas
Application objects in inappropriate namespaces
Unexpected objects in public
Suspicious system-like schema names

Avoid user-created names beginning with pg_.

## 3.20.9 pg_class — Relation Metadata

pg_class is one of PostgreSQL's central catalogs.

It describes relation-like objects including:

Tables
Indexes
Sequences
TOAST tables
Views
Materialized views
Composite types
Foreign tables
Partitioned tables
Partitioned indexes

Example:

SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relpersistence,
    c.relowner::regrole AS owner,
    c.relrowsecurity,
    c.relforcerowsecurity,
    c.relreplident,
    c.relispartition
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n.nspname, c.relname;
## 3.20.10 Understanding relkind

Important values include:

relkind	Object
r	Ordinary table
i	Index
S	Sequence
t	TOAST table
v	View
m	Materialized view
c	Composite type
f	Foreign table
p	Partitioned table
I	Partitioned index

Automation should identify object types from documented metadata rather than naming conventions.

## 3.20.11 pg_attribute — Column Metadata

Columns are primarily represented through pg_attribute.

SELECT
    a.attnum,
    a.attname,
    pg_catalog.format_type(a.atttypid, a.atttypmod) AS data_type,
    a.attnotnull,
    a.attidentity,
    a.attgenerated,
    a.attisdropped
FROM pg_attribute a
WHERE a.attrelid = 'app.orders'::regclass
  AND a.attnum > 0
ORDER BY a.attnum;

attnum > 0 excludes PostgreSQL system columns.

A normal logical-column inventory should generally use:

AND a.attnum > 0
AND NOT a.attisdropped

Dropped columns can remain represented internally with:

attisdropped = true

and may be useful during forensic or physical-layout investigations.

## 3.20.12 Defaults and Generated Expressions

Column defaults and generation expressions are represented through pg_attrdef.

Use PostgreSQL's expression deparser:

SELECT
    a.attname,
    pg_get_expr(d.adbin, d.adrelid) AS expression
FROM pg_attribute a
JOIN pg_attrdef d
  ON d.adrelid = a.attrelid
 AND d.adnum = a.attnum
WHERE a.attrelid = 'app.orders'::regclass;

Do not attempt to interpret PostgreSQL internal expression-tree representations manually when supported deparsing functions exist.

## 3.20.13 Metadata Deparsing Functions

Important functions include:

pg_get_expr()
pg_get_viewdef()
pg_get_indexdef()
pg_get_constraintdef()
pg_get_functiondef()
pg_get_triggerdef()
pg_get_partkeydef()

Examples:

SELECT pg_get_viewdef('app.active_orders'::regclass, true);
SELECT pg_get_indexdef(indexrelid)
FROM pg_index
WHERE indrelid = 'app.orders'::regclass;
SELECT
    conname,
    pg_get_constraintdef(oid, true)
FROM pg_constraint
WHERE conrelid = 'app.orders'::regclass;

These are preferable to reverse-engineering internal catalog structures.

## 3.20.14 pg_index — Index Metadata

pg_index describes index-specific properties.

SELECT
    i.indexrelid::regclass AS index_name,
    i.indrelid::regclass AS table_name,
    i.indisunique,
    i.indisprimary,
    i.indisvalid,
    i.indisready,
    i.indisclustered,
    i.indisreplident,
    pg_get_indexdef(i.indexrelid) AS definition
FROM pg_index i
WHERE i.indrelid = 'app.orders'::regclass;

Two fields require particular attention:

indisvalid
     |
     +--> valid for query/constraint use

indisready
     |
     +--> ready to receive inserts/updates

They are not interchangeable.

This distinction matters particularly during concurrent index operations.

## 3.20.15 Detecting Index Metadata Anomalies
SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    idx.relname AS index_name,
    i.indisvalid,
    i.indisready
FROM pg_index i
JOIN pg_class idx
  ON idx.oid = i.indexrelid
JOIN pg_class t
  ON t.oid = i.indrelid
JOIN pg_namespace n
  ON n.oid = t.relnamespace
WHERE NOT i.indisvalid
   OR NOT i.indisready
ORDER BY n.nspname, t.relname, idx.relname;

The response depends on the actual state.

Do not treat:

indisvalid = false

and:

indisready = false

as equivalent failures.

## 3.20.16 pg_constraint — Constraint Metadata

Constraint metadata is represented through pg_constraint.

SELECT
    conname,
    contype,
    convalidated,
    condeferrable,
    condeferred,
    pg_get_constraintdef(oid, true) AS definition
FROM pg_constraint
WHERE conrelid = 'app.orders'::regclass;

Common application-visible constraint categories include:

PRIMARY KEY
UNIQUE
FOREIGN KEY
CHECK
EXCLUSION

but tooling should interpret contype according to the documentation for the deployed PostgreSQL version rather than assuming this list is permanently exhaustive.

## 3.20.17 Detecting Unvalidated Constraints
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    con.conname,
    con.contype,
    con.convalidated,
    pg_get_constraintdef(con.oid, true) AS definition
FROM pg_constraint con
JOIN pg_class c
  ON c.oid = con.conrelid
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE NOT con.convalidated
ORDER BY n.nspname, c.relname;

This can expose an incomplete migration:

ADD CONSTRAINT ... NOT VALID
              |
              v
VALIDATE CONSTRAINT never completed
## 3.20.18 pg_depend — Database-Local Dependencies

pg_depend records dependency relationships among database objects.

Conceptually:

Referenced object
      |
      +--> dependent object
      +--> dependent object
      +--> dependent object

PostgreSQL uses these relationships to implement dependency-aware operations such as DROP ... RESTRICT and DROP ... CASCADE.

Dependency records include identifiers such as:

classid
objid
objsubid
refclassid
refobjid
refobjsubid
deptype

These can refer to different catalogs and even subobjects.

Therefore dependency investigation should not assume one simplistic query can translate every dependency into a complete human-readable graph.

## 3.20.19 Dependency Types

Dependency semantics are represented through deptype.

Important concepts include:

NORMAL
AUTO
INTERNAL
EXTENSION

Different dependency types have different lifecycle semantics.

Before destructive DDL, understand not merely:

Does a dependency exist?

but:

What kind of dependency is it?
## 3.20.20 pg_shdepend — Shared Dependencies

Shared-object dependencies are represented through pg_shdepend.

This is particularly important for:

Roles
Tablespaces
Ownership
ACL relationships
Policies and shared objects

For example:

DROP ROLE legacy_app;

can fail because that role owns or has privileges on objects in multiple databases.

The correct operational response is to inventory and remediate those dependencies through supported commands—not modify pg_shdepend.

## 3.20.21 Ownership Metadata

For relations:

SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relowner::regrole AS owner
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY 1, 2;

Production governance should detect:

Objects owned by personal login roles
Objects owned by obsolete service accounts
Unexpected ownership changes
Mixed ownership inside application schemas
Elevated roles owning unnecessary objects

A common architecture is:

NOLOGIN owner role
      |
      +--> owns schema
      +--> owns tables
      +--> owns sequences
      +--> owns functions

Application login
      |
      +--> receives privileges
      +--> does not own objects
## 3.20.22 Effective Privilege Metadata

Authorization must distinguish:

Ownership
   ≠
Explicit grant
   ≠
Role-inherited privilege
   ≠
PUBLIC privilege
   ≠
Default privilege
   ≠
RLS authorization

Raw ACL fields such as:

relacl
nspacl
datacl
proacl

are useful for forensic inspection.

For effective-access verification, supported privilege functions are often preferable:

SELECT has_table_privilege(
    'app_runtime',
    'app.orders',
    'SELECT'
);
SELECT has_schema_privilege(
    'app_runtime',
    'app',
    'USAGE'
);

A security audit should account for privileges inherited through role membership and grants to PUBLIC.

## 3.20.23 Database Metadata

pg_database is shared cluster-wide.

SELECT
    oid,
    datname,
    datdba::regrole AS owner,
    pg_encoding_to_char(encoding) AS encoding,
    datcollate,
    datctype,
    datallowconn,
    datconnlimit
FROM pg_database
ORDER BY datname;

Inventory should detect:

Unexpected databases
Wrong owners
Connection-disabled databases
Unexpected connection limits
Encoding/locale inconsistencies
Legacy databases awaiting retirement
## 3.20.24 Functions and Procedures

Functions and procedures are primarily represented through pg_proc.

SELECT
    n.nspname AS schema_name,
    p.proname,
    p.prokind,
    p.proowner::regrole AS owner,
    pg_get_function_identity_arguments(p.oid) AS arguments
FROM pg_proc p
JOIN pg_namespace n
  ON n.oid = p.pronamespace
WHERE n.nspname = 'app'
ORDER BY p.proname;

PostgreSQL supports overloaded functions.

Therefore:

schema + function name

is not always a durable identity.

Use:

schema + function name + argument signature

where required.

## 3.20.25 Function Security Metadata

Function reviews should consider:

Owner
Language
Volatility
Parallel safety
Execution privileges
SECURITY DEFINER
Configuration settings
search_path
Dependencies

Retrieve definitions through:

SELECT pg_get_functiondef(
    'app.calculate_total(integer)'::regprocedure
);

SECURITY DEFINER functions deserve particular attention because their metadata can directly affect privilege boundaries.

PostgreSQL type metadata includes:

Base types

## 3.20.27 Sequence Metadata

Sequence relations appear in pg_class, with sequence-specific information available through PostgreSQL sequence catalogs/views.

For operator-friendly inspection:

SELECT *
FROM pg_sequences
WHERE schemaname = 'app';

Sequence metadata matters during:

Identity migrations
Schema migration
Restore validation
Ownership changes
Cross-environment comparison
Sequence-exhaustion analysis
## 3.20.28 Partition Metadata

Important partition metadata includes:

pg_inherits
pg_partitioned_table
pg_class

For operational discovery:

SELECT *
FROM pg_partition_tree('app.orders');

Use metadata to detect:

Missing expected partitions
Incorrect attachment
Unexpected leaf partitions
Partition-bound drift
Incorrect ownership
Index/constraint drift across partitions

A missing production partition can be an availability incident even when CPU, memory, and storage are healthy.

## 3.20.29 Row-Level Security Metadata

pg_class exposes:

relrowsecurity
relforcerowsecurity

Find RLS-enabled tables:

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.relrowsecurity,
    c.relforcerowsecurity
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')
  AND c.relrowsecurity;

pg_policy is the underlying catalog.

For operator-facing inspection, pg_policies is generally easier:

SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd,
    qual,
    with_check
FROM pg_policies
ORDER BY schemaname, tablename, policyname;
## 3.20.30 RLS as Security Metadata

An unexpected transition from:

RLS enabled

to:

RLS disabled

can be a security event rather than ordinary configuration drift.

Production response:

RLS change
    |
    v
Approved deployment?
   / \
 YES  NO
 |     |
Validate Security investigation

Metadata monitoring should therefore assign higher severity to unauthorized RLS and policy changes.

## 3.20.31 Replica Identity Metadata

pg_class.relreplident represents replica-identity mode.

Typical values:

d = default
n = nothing
f = full
i = index

Inspect:

SELECT
    n.nspname,
    c.relname,
    c.relreplident
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p')
ORDER BY 1, 2;

When:

relreplident = i

correlate with:

pg_index.indisreplident

to identify the selected replica-identity index.

Replica identity is a critical CDC contract and should be validated after schema changes affecting keys or indexes.

## 3.20.32 Publication Metadata

Logical-replication publication configuration is represented through catalogs including:

pg_publication
pg_publication_rel
pg_publication_namespace

Example:

SELECT
    pubname,
    pubowner::regrole AS owner,
    puballtables,
    pubinsert,
    pubupdate,
    pubdelete,
    pubtruncate
FROM pg_publication;

Production inventory should validate relevant publication semantics, including where applicable:

Published operations
Table membership
Schema membership
Row filters
Column lists
Partition publication behavior

Therefore:

Table belongs to publication

does not necessarily imply:

All rows and columns are published exactly as expected
## 3.20.33 Subscription Metadata

Subscriber configuration must receive the same operational attention as publications.

Important metadata includes:

pg_subscription
pg_subscription_rel

Use these to inspect:

Subscription existence
Enabled state
Publication association
Connection/configuration metadata
Relation synchronization state

Sensitive subscription metadata must be handled carefully and should not be unnecessarily exposed through broad monitoring roles or logs.

## 3.20.34 Subscription Runtime Health

Configuration metadata and runtime health are different.

CONFIGURATION
"What should exist?"
       |
       +--> pg_subscription
       +--> pg_subscription_rel

RUNTIME
"Is it operating?"
       |
       +--> pg_stat_subscription

A subscription can exist correctly while replication is unhealthy.

This establishes a broader SRE principle:

Catalog state
     !=
Runtime health

Both must be evaluated.

## 3.20.37 Extension-Owned Objects

Dependency metadata identifies objects belonging to extensions.

Conceptually:

Extension
   |
   +--> functions
   +--> types
   +--> operators
   +--> views

Extension-managed objects should normally be managed through supported extension operations rather than modified independently.

pg_description

SELECT obj_description('app.orders'::regclass);

## 3.20.39 TOAST Metadata

pg_class.reltoastrelid identifies an associated TOAST relation where applicable.

SELECT
    c.oid::regclass AS table_name,
    c.reltoastrelid,
    CASE
        WHEN c.reltoastrelid <> 0
        THEN c.reltoastrelid::regclass::text
    END AS toast_relation
FROM pg_class c
WHERE c.oid = 'app.orders'::regclass;

This is useful when investigating:

Large text/JSON values
Unexpected storage consumption
Bloat
Vacuum behavior

TOAST relations should not normally be manipulated independently.

## 3.20.40 Catalog Hints Versus Authoritative State

Some catalog fields are optimization hints or are maintained lazily.

Therefore:

Catalog hint
    !=
always exact instantaneous state

Where exact state matters, inspect the authoritative supporting catalog.

For example, do not rely only on:

pg_class.relhasindex

when the actual index inventory and validity can be inspected through:

pg_index
## 3.20.41 Catalog Safety — Production Prohibition

System catalogs physically resemble ordinary PostgreSQL relations, but PostgreSQL depends on precise catalog relationships and invariants.

Normal administration must follow:

READ catalogs
     |
     v
UNDERSTAND state
     |
     v
CHANGE through supported SQL/DDL

Do not treat operations such as these as normal remediation:

UPDATE pg_catalog.pg_class ...;

DELETE FROM pg_catalog.pg_attribute ...;

INSERT INTO pg_catalog.pg_constraint ...;

Use supported interfaces such as:

CREATE
ALTER
DROP
GRANT
REVOKE
COMMENT
REINDEX
VACUUM
ANALYZE
ALTER EXTENSION

Production rule: Do not directly INSERT, UPDATE, or DELETE PostgreSQL system-catalog rows as routine production administration.

## 3.20.56 Metadata Troubleshooting — Duplicate Names

PostgreSQL can have:

public.orders
app.orders
archive.orders

Detect:

SELECT
    c.relname,
    array_agg(n.nspname ORDER BY n.nspname) AS schemas,
    count(*) AS object_count
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p', 'v', 'm')
GROUP BY c.relname
HAVING count(*) > 1
ORDER BY c.relname;

This is especially useful for search_path incidents.

## 3.20.71 Golden Rules
Understand metadata before changing database objects.
Use information_schema when standard portable metadata is sufficient.
Use PostgreSQL catalogs/views for PostgreSQL-specific administration.
Remember that metadata visibility can depend on privileges.
Do not interpret “not visible” as “does not exist.”
Use schema-qualified object identities in automation.
Use OIDs for runtime catalog relationships, not durable cross-system identity.
Use regclass, regtype, and related alias types appropriately.
Use pg_get_*() functions instead of manually decoding internal trees.
Do not assume object existence means object validity.
Distinguish indisvalid from indisready.
Check unvalidated constraints after migrations.
Understand dependencies before destructive DDL.
Remember shared dependencies can cross databases.
Separate ownership from effective privilege.
Include inherited and PUBLIC privileges in security reviews.
Treat unexpected RLS changes as security-relevant.
Treat replica identity and publication/subscription configuration as CDC contracts.
Distinguish catalog configuration from runtime health.
Inventory extensions before upgrades and after restores.
Baseline logical metadata, not volatile internal state.
Validate collector completeness before declaring drift.
Use metadata contracts in schema deployment pipelines.
Capture metadata before and after important changes.
Treat custom catalog queries as PostgreSQL-version-dependent code.
Use metadata snapshots for incident forensics.
Do not directly modify system catalogs during routine production administration.
Remediate through supported PostgreSQL SQL and DDL interfaces.

For any metadata investigation, ask:

Which cluster?

Which database?

Which schema?

What object type?

What is the durable identity?

What depends on it?

Are its indexes valid and ready?

Is RLS configured correctly?

What is its replica identity?

Does CDC depend on it?

Is it extension-managed?

Does current metadata match expected state?

Is the metadata snapshot complete?

Is runtime health consistent with configuration?

Did this change come from an approved deployment?

If these questions cannot be answered, the object's production state is not fully understood.
