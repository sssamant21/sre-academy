**Edition:** Revised Final / Canonical Edition

**Status:** COMPLETE — Canonical Edition

## 3.21.1 Purpose and Scope

PostgreSQL MVCC deliberately creates multiple row versions. An UPDATE normally creates a new tuple version, while a DELETE makes an existing tuple obsolete rather than immediately removing its physical storage.

Once obsolete tuple versions are no longer visible to any transaction, PostgreSQL can reclaim their space through VACUUM. Vacuuming also contributes to visibility-map maintenance and protects PostgreSQL against transaction-ID and MultiXact-ID wraparound.

For an SRE/DBRE, object health therefore cannot be reduced to:

How large is the table?

The production questions are:

Is the object growing abnormally?

Are dead tuples accumulating?

Is VACUUM keeping pace?

Is ANALYZE keeping statistics current?

Are transactions preventing cleanup?

Are prepared transactions retaining state?

Are replication slots retaining xmin/catalog_xmin?

Is WAL being retained by slots?

Are XID and MultiXact horizons safe?

Are indexes healthy?

Is TOAST responsible for significant growth?

Are partitions healthy?

Is the problem bloat, maintenance debt,
capacity pressure, or corruption?

Does physical storage actually need reclamation?

What is the least disruptive remediation?

The central production rule is:

Dead tuples are not the same thing as bloat; bloat is not the same thing as corruption; and none of these conditions automatically justifies VACUUM FULL.

## 3.21.3 MVCC and Dead Tuples

Conceptually:

Original tuple
     |
     | UPDATE
     v
Old tuple version --------+
                          |
New tuple version         |
                          |
                    old snapshot?
                     /        \
                   YES        NO
                    |          |
                 retain     eventually
                            reclaimable

A tuple cannot simply be removed because another transaction may still need to see its older version.

Therefore some dead tuples are a normal consequence of PostgreSQL operation.

## 3.21.4 Dead Tuples ≠ Bloat

Suppose:

Table size       = 500 GB
Live tuples      = 2 billion
Dead tuples      = 20 million

This does not establish:

severe bloat

Instead evaluate:

Dead tuple ratio
       +
Absolute dead-tuple count
       +
Physical relation size
       +
Growth rate
       +
Write/churn rate
       +
Vacuum frequency
       +
Free-space reuse
       +
Application impact

A high-churn table can continuously create and reuse free space while maintaining a stable physical footprint.

That can be healthy steady-state PostgreSQL behavior.

## 3.21.5 What Is Bloat?

Operationally, harmful bloat exists when a relation occupies materially more physical storage than the workload reasonably requires and that condition causes or threatens meaningful operational impact.

Conceptually:

Physical relation
+---------------------------------------+
| Live tuples                           |
| Dead tuples                           |
| Reusable free space                   |
| Page overhead                         |
| Alignment/padding                     |
+---------------------------------------+

Not every byte outside live tuple data is waste.

Distinguish:

Reusable internal space
        !=
Space immediately reclaimable
to the filesystem

and:

Unused space
        !=
Production incident

## 3.21.7 Standard VACUUM

Routine VACUUM normally makes storage occupied by removable dead tuples available for reuse.

Dead tuple
    |
    v
VACUUM
    |
    v
Tuple removable?
   / \
 NO  YES
 |    |
retain mark space reusable

Standard vacuum does not normally compact all surviving rows into the beginning of the relation.

Under suitable conditions PostgreSQL can truncate empty pages from the end of a table, but this is different from a full physical rewrite.

Therefore:

VACUUM completed
      !=
Relation must become smaller
## 3.21.8 Healthy Steady-State Space Reuse

Example:

Table = 500 GB
     |

     |
     v

     |
     v

     |
     v
Reusable space
     |
     v
Future tuples reuse pages
     |
     v

This is usually preferable to repeatedly shrinking and regrowing the relation.

The SRE objective is:

Controlled physical growth
        +
Maintenance keeping pace
        +
Healthy reusable capacity

rather than minimum possible file size.

## 3.21.9 Basic Table Health Statistics

Start with inexpensive cumulative statistics:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_mod_since_analyze,
    n_ins_since_vacuum,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count,
    analyze_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

n_live_tup and n_dead_tup are estimates.

They are useful for:

Triage
Trending
Prioritization

They are not exact physical page measurements.

## 3.21.10 Dead-Tuple Percentage
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    round(
        100.0 * n_dead_tup /
        NULLIF(n_live_tup + n_dead_tup, 0),
        2
    ) AS dead_tuple_pct,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY dead_tuple_pct DESC NULLS LAST;

        |
        v
Investigate

## 3.21.12 Relation Footprint
SELECT
    n.nspname AS schema_name,
    c.relname,
    pg_size_pretty(pg_relation_size(c.oid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(c.oid)) AS indexes_size,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(c.oid) DESC;

## 3.21.18 Basic Index Inventory
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;

Do not conclude:

idx_scan = 0
       |
       v
DROP INDEX

A zero value can result from statistics resets, seasonal workloads, rare queries, standby usage, recent creation, or specialized operational requirements.

Constraint dependencies must also be checked.

## 3.21.19 B-tree Inspection

For targeted B-tree analysis:

SELECT *
FROM pgstatindex(
    'app.orders_customer_id_idx'::regclass
);

Metrics such as:

avg_leaf_density
leaf_fragmentation

require workload context.

Do not convert a fragmentation metric directly into:

REINDEX required

without evaluating growth, workload, fillfactor, page splits, and actual performance/storage impact.

## 3.21.20 GIN Health

For suitable GIN indexes:

SELECT *

## 3.21.21 HOT Updates

Heap-Only Tuple updates can reduce index churn when PostgreSQL can update a row without creating new index entries.

Conceptually:

UPDATE
  |
  +--> HOT possible
  |       |
  |       +--> heap version created
  |            without equivalent index churn
  |
  +--> HOT unavailable
          |
          +--> heap churn
          +--> index churn

HOT behavior is influenced by factors including:

Whether indexed values are modified
Page free space
Relation storage configuration
Workload pattern

Low HOT effectiveness on update-heavy tables can contribute to index maintenance pressure.

## 3.21.22 Fillfactor

A lower table fillfactor intentionally reserves page space.

This can increase the opportunity for HOT updates in suitable workloads.

But:

Lower fillfactor
      |
      +--> more free page space
      +--> potentially more HOT updates
      +--> potentially larger base relation

Therefore:

Lower fillfactor is a workload tradeoff, not a universal anti-bloat setting.

Measure before and after changing it.

Autovacuum is a core production subsystem.

Think of it as:

Vacuum demand

Available maintenance capacity

Index count
Tuple width
TOAST activity

Workers

Storage I/O
Storage latency
Vacuum cost controls

## 3.21.25 Autovacuum Trigger Model

Conceptually, vacuum eligibility is based on a threshold involving:

autovacuum_vacuum_threshold
        +
autovacuum_vacuum_scale_factor × relation tuples

Modern PostgreSQL also provides a maximum threshold capability, allowing large-table trigger growth to be capped where configured.

Conceptually:

effective threshold
       =
minimum of
(
 threshold + scale factor × tuples,
 configured maximum threshold
)

Operators must validate exact semantics against the deployed PostgreSQL version.

## 3.21.26 Insert-Triggered Vacuum

Vacuum is not relevant only to update/delete workloads.

Modern PostgreSQL provides controls including:

autovacuum_vacuum_insert_threshold
autovacuum_vacuum_insert_scale_factor

This matters because vacuum also contributes to:

Freezing
Visibility-map maintenance
Index-only-scan opportunities
Wraparound protection

Therefore:

Append-only workload
       !=
VACUUM unnecessary

## 3.21.31 Vacuum History

    relname,
    last_vacuum,
    last_autovacuum,

    autovacuum_count

## 3.21.34 Long-Running Transactions
SELECT
    pid,
    usename,
    datname,
    state,
    xact_start,
    backend_xmin,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

xact_start identifies long transactions.

backend_xmin is especially important when determining whether a backend is holding an old visibility horizon relevant to vacuum cleanup.

Therefore:

Old transaction
      !=
Automatically the oldest cleanup blocker
## 3.21.35 idle in transaction
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    xact_start,
    backend_xmin,
    state_change,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

These sessions can retain transaction state without doing useful work.

Where appropriate, evaluate preventive controls such as:

idle_in_transaction_session_timeout
statement_timeout
lock_timeout

These must be workload-specific.

## 3.21.41 Transaction-ID Health

Transaction-ID wraparound is a database availability risk.

Monitor cluster-wide:

SELECT
    datname,
    age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;

Do not restrict this only to application databases.

## 3.21.42 Relation-Level XID Health
SELECT
    n.nspname AS schema_name,
    c.relname,
    age(c.relfrozenxid) AS xid_age,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 50;

This helps identify relations contributing to the database freeze horizon.

## 3.21.43 XID Risk Relative to Configuration

Avoid one universal threshold such as:

age(datfrozenxid) > 1 billion

Instead evaluate relative to configured freeze limits such as:

autovacuum_freeze_max_age
vacuum_freeze_table_age
vacuum_freeze_min_age

Conceptually:

XID utilization
      =
current age
-------------------
configured safety age

Alerts must fire early enough for operators to investigate, remove blockers, and complete required vacuum work.

## 3.21.44 XID Alert Headroom

+ blocker removal

## 3.21.46 MultiXact Health

MultiXact wraparound requires equivalent attention.

Database level:

SELECT
    datname,
    mxid_age(datminmxid) AS multixact_age
FROM pg_database
ORDER BY mxid_age(datminmxid) DESC;

The parallel model is:

XID	MultiXact

relfrozenxid	relminmxid

## 3.21.47 ANALYZE Health

Physical maintenance alone is insufficient.

SELECT
    schemaname,
    relname,
    n_mod_since_analyze,
    last_analyze,
    last_autoanalyze,
    analyze_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC;

A physically healthy relation can still perform poorly because planner statistics are stale.

Remember that cumulative statistics can reset.

Therefore:

analyze_count = 0

does not necessarily mean:

ANALYZE has never occurred

External monitoring should preserve history.

## 3.21.48 Partitioned Tables

Partitioned workloads require parent and child maintenance awareness.

Partitioned parent
      |
      +--> parent statistics
      |
      +--> partition A vacuum/analyze
      +--> partition B vacuum/analyze
      +--> partition C vacuum/analyze

Partitioned parent tables can require explicit ANALYZE because changes in child partitions do not automatically guarantee that parent-level planner statistics are refreshed as needed.

This can produce:

Healthy child partitions
        |
        v
Stale parent statistics
        |
        v
Poor query planning

## 3.21.51 TOAST Health

Large values can move much of an object's physical footprint into TOAST storage.

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS heap_size,
    pg_size_pretty(
        CASE
            WHEN c.reltoastrelid <> 0
            THEN pg_relation_size(c.reltoastrelid)
            ELSE 0
        END
    ) AS toast_size
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
ORDER BY
    CASE
        WHEN c.reltoastrelid <> 0
        THEN pg_relation_size(c.reltoastrelid)
        ELSE 0
    END DESC;

For JSONB, large text, arrays, and frequently modified toasted values, TOAST may dominate physical growth.

TOAST relations also participate in vacuum/autovacuum behavior.

## 3.21.52 Temporary Tables

Autovacuum cannot maintain another session's temporary tables.

Applications using long-lived temporary tables may require explicit:

VACUUM;
ANALYZE;

where appropriate.

This matters for ETL, staging, and analytical workloads.

## 3.21.55 Invalid Indexes
SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    idx.relname AS index_name,
    i.indisvalid,
    i.indisready
FROM pg_index i
JOIN pg_class idx
  ON idx.oid = i.indexrelid
JOIN pg_class t
  ON t.oid = i.indrelid
JOIN pg_namespace n
  ON n.oid = t.relnamespace
WHERE NOT i.indisvalid
   OR NOT i.indisready
ORDER BY 1, 2, 3;

Invalid indexes belong in routine administrative health checks.

## 3.21.56 Unvalidated Constraints
SELECT
    n.nspname,
    c.relname,
    con.conname,
    con.contype
FROM pg_constraint con
JOIN pg_class c
  ON c.oid = con.conrelid
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE NOT con.convalidated
ORDER BY 1, 2;

This often identifies incomplete migration workflows.

## 3.21.57 VACUUM FULL

VACUUM FULL rewrites the table into a compact physical representation and can return unused storage to the operating system.

But it is a disruptive operation.

Production considerations include:

ACCESS EXCLUSIVE lock
Relation rewrite
Temporary storage requirement
Heavy I/O
Potentially long duration
WAL generation
Replica work
Backup/PITR implications
Application availability

It is not routine maintenance.

## 3.21.59 Rollback Versus Fallback

For large physical maintenance operations:

Rollback
   |
   +--> transactional rollback where supported

Fallback
   |
   +--> cancel/stop safely
   +--> restore service
   +--> rebuild
   +--> recover/restore where necessary

Do not promise instant rollback for multi-terabyte maintenance.

Use a realistic rollback/fallback plan.

## 3.21.76 Golden Rules
Dead tuples are normal consequences of MVCC.
Dead tuples are not automatically bloat.
Bloat is not corruption.
A large table is not automatically bloated.
A large index is not automatically bloated.
Trend object growth instead of relying on snapshots.
Treat n_dead_tup as an estimate.
Use inexpensive evidence before physical scans.
Use pgstattuple_approx before deeper scans where appropriate.
Use pgstattuple selectively.
Treat autovacuum as production capacity.
Keep autovacuum enabled unless an explicit maintenance design replaces it.
Tune large/high-churn tables individually when justified.
Account for insert-triggered vacuum.
Use backend_xmin when diagnosing cleanup blockers.
Monitor idle in transaction.
Check prepared transactions during difficult cleanup incidents.
Never terminate a backend solely because it is old.
Separate slot tuple/catalog retention from WAL retention.
Never drop a replication slot solely because it is inactive or old.
Monitor XID and MultiXact age continuously.
Alert relative to configured safety limits and maintenance duration.
Treat wraparound risk as an availability incident.
Monitor VACUUM and ANALYZE.
Remember partitioned parents can require explicit ANALYZE.
Inspect heap, indexes, and TOAST together.
Use HOT/fillfactor analysis for update-heavy workloads.
Do not infer index removal from one idx_scan snapshot.
Use integrity tools for corruption investigation, not bloat measurement.
Do not use VACUUM FULL as routine maintenance.
Require a production gate for relation rewrites.
Account for lock, disk, WAL, replicas, CDC, and backups.
Account for maintenance storage headroom.
Prefer partition lifecycle operations for suitable retention workloads.
Do not assume OS/superuser access on managed PostgreSQL.
Correlate PostgreSQL metrics with cloud/platform metrics.
Automate detection aggressively and destructive remediation conservatively.
Validate database, application, replication, and storage after maintenance.
Observe through a representative workload cycle.
Fix the root cause rather than repeatedly rewriting the symptom.
## 3.21.77 SRE/DBRE Mental Model

For every suspected bloat or maintenance incident, ask:

What is actually unhealthy?

Is the object growing?

How fast?

Are dead tuples rising?

Is that normal churn?

Is VACUUM keeping pace?

Is autovacuum capacity sufficient?

What is backend_xmin?

Are there idle transactions?

Are there prepared transactions?

Is a slot retaining xmin/catalog_xmin?

Is a slot retaining excessive WAL?

What is XID age?

What is MultiXact age?

Are statistics current?

Are indexes healthy?

How effective are HOT updates?

Is TOAST responsible for the growth?

Is the object partitioned?

Is corruption actually suspected?

Is application SLO affected?

Is storage headroom threatened?

Does physical space need to return to the OS?

Will the relation simply regrow?

What is the least disruptive safe remediation?

How will we prove the remediation worked?

If these questions have not been answered, a destructive maintenance decision is premature.
