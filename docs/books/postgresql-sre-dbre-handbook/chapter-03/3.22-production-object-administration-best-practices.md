This canonical edition incorporates the technical and production-review corrections and establishes the Chapter 3 production standard for PostgreSQL object administration.

## 3.22.1 Purpose

Production PostgreSQL object administration is not simply the execution of valid SQL.

An operation can be syntactically correct and still cause:

application downtime;
lock queues and connection-pool exhaustion;
data-integrity failures;
privilege escalation or access loss;
excessive WAL generation;
replica or CDC lag;
storage exhaustion;
failed deployments;
irreversible destructive changes.

The governing principle is:

Every production object change is a reliability change. Evaluate locking, dependencies, security, scale, application compatibility, replication, recoverability, observability, and rollback before execution.

The production lifecycle is:

Intent
  ↓
Desired State
  ↓
Current-State Inventory
  ↓
Dependency Analysis
  ↓
Security + Lock + Scale Analysis
  ↓
Application Compatibility
  ↓
Replication / CDC Analysis
  ↓
WAL / Storage Assessment
  ↓
Risk Classification
  ↓
Testing
  ↓
Rollback / Fallback
  ↓
Abort Criteria
  ↓
Controlled Execution
  ↓
Progress Monitoring
  ↓
Validation
  ↓
Observation Window
  ↓
Audit + Git Reconciliation
  ↓
Drift Monitoring
## 3.22.2 Production Object Administration Principles

Every production change must answer:

WHAT is changing?
WHY is it changing?
WHO owns the object?
WHO uses it?
WHAT depends on it?
WHAT privileges are involved?
WHAT locks are required?
HOW large is the object?
WILL PostgreSQL scan or rewrite data?
WHAT WAL might be generated?
WHAT happens to replicas?
WHAT happens to CDC?
CAN old and new applications coexist?
WHAT happens if the operation fails?
HOW do we abort safely?
HOW do we recover?
HOW do we prove success?

For high-risk changes, inability to answer these questions means:

The change is not production-ready.

## 3.22.3 Classify Changes by Production Risk

Do not classify risk by how complicated the SQL looks.

Class A — Routine

Examples:

COMMENT
Known low-impact metadata changes
Reviewed minor privilege corrections
Class B — Controlled

Examples:

CREATE INDEX CONCURRENTLY
Constraint deployment
Partition attachment
Moderate backfill
Ownership restructuring
Class C — High Risk

Examples:

Large ALTER TABLE
Large type conversion
Large REINDEX
Large backfill
Partition restructuring
Class D — Destructive / Availability Sensitive

Examples:

DROP TABLE
DROP COLUMN
TRUNCATE
DROP ... CASCADE
VACUUM FULL
Large blocking table rewrite

Risk determines:

Review depth
Testing requirements
Maintenance window
Approval
Monitoring
Abort thresholds
Recovery planning
Observation period
## 3.22.4 Stable Production Ownership

Avoid personal login roles owning production objects.

Prefer:

                 Application Objects
                         ↑
                    app_owner
                         ↑
              controlled deployment
                         ↑
                    db_deployer

Runtime roles remain separate:

app_runtime
app_readonly
app_reporting
db_maintain

The operating principle is:

Identity
   ≠
Ownership
   ≠
Deployment authority
   ≠
Runtime privilege
   ≠
Maintenance authority

This makes personnel changes, credential rotation, and access revocation much safer.

## 3.22.5 Avoid Routine Superuser Administration

Routine administration should use the minimum authority required.

PostgreSQL supports granular privileges including MAINTAIN, while the predefined pg_maintain role can perform maintenance operations on relations without making every operator an unrestricted superuser.

Prefer:

Runtime role
     |
     +── DML

Maintenance role
     |
     +── maintenance authority

Deployment/owner role
     |
     +── controlled DDL

Emergency administrative role
     |
     +── exceptional use
## 3.22.6 Secure Schema Governance

Schemas are security and administration boundaries.

Use intentional schemas such as:

app
integration
reporting
audit
staging

Review creation privileges carefully.

Where appropriate:

REVOKE CREATE ON SCHEMA public FROM PUBLIC;

PostgreSQL's search_path behavior makes writable schemas particularly important: adding a schema to the search path effectively trusts users who can create objects there.

## 3.22.7 Treat search_path as Security Configuration

Administrative automation should normally schema-qualify objects:

SELECT *
FROM app.orders;

rather than relying on:

SELECT *
FROM orders;

especially for:

Migrations
Administrative scripts
SECURITY DEFINER functions
Security-sensitive operations
Automation

The production rule is:

Operational SQL should not depend on an ambiguous namespace.

## 3.22.8 Secure SECURITY DEFINER Functions

A SECURITY DEFINER function executes using its owner's privileges.

Therefore validate:

Trusted owner
Restricted EXECUTE privilege
Safe search_path
Schema-qualified references
Reviewed function body
No untrusted writable namespace

Where appropriate:

REVOKE EXECUTE
ON FUNCTION app.admin_function(...)
FROM PUBLIC;

and explicitly grant execution to approved roles.

A privileged function with unsafe name resolution can become a privilege-escalation path.

## 3.22.9 Standardize Object Naming

Production names should communicate purpose.

Prefer:

orders
orders_pkey
orders_customer_id_idx
orders_customer_fk
orders_status_chk

Avoid:

table1
idx1
orders_new
orders_old2
orders_final
orders_final_final

Version history belongs in:

Git
Migration history
Change records
Backups/PITR

not in permanent object-name suffixes.

## 3.22.10 Production DDL Requires Lock Analysis

Before DDL determine:

Required lock
Potential conflicting locks
Existing blockers
Maximum lock wait
Expected lock hold time
Application impact
Abort condition

PostgreSQL's ACCESS EXCLUSIVE table lock conflicts with all other table-level lock modes; commands such as DROP TABLE, TRUNCATE, VACUUM FULL, and ordinary REINDEX can acquire it.

The key principle is:

Execution time
      ≠
Lock risk
## 3.22.11 Inspect Blocking Relationships

Useful inspection:

SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.client_addr,
    a.state,
    a.xact_start,
    now() - a.xact_start AS xact_age,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
   OR a.xact_start IS NOT NULL
ORDER BY a.xact_start NULLS LAST;

The operating model is:

Blocked DDL
    ↓
Identify blocker
    ↓
Identify transaction
    ↓
Identify application/business operation
    ↓
Wait / cancel / reschedule

Never terminate a transaction merely because it inconveniences a deployment.

## 3.22.12 Check idle in transaction

Before significant DDL:

SELECT
    pid,
    usename,
    application_name,
    xact_start,
    now() - xact_start AS xact_age,
    state,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

Old transactions can retain locks and database state far longer than expected.

## 3.22.13 Check Prepared Transactions

Where two-phase transactions are enabled or possible:

SELECT *
FROM pg_prepared_xacts;

The readiness gate becomes:

Active transactions
        +
Idle transactions
        +
Prepared transactions
        +
Lock blockers
        =
DDL readiness assessment
## 3.22.14 Use Transactional DDL Correctly

Many PostgreSQL schema operations can participate in transactions.

Example:

BEGIN;

ALTER TABLE app.orders ...;

COMMIT;

This provides valuable atomicity.

But:

Transactional DDL is not non-blocking DDL.

Locks may remain held until transaction end.

Avoid:

BEGIN
  ↓
DDL
  ↓
manual investigation
  ↓
coffee
  ↓
more validation
  ↓
COMMIT

Prefer:

Prepare validation
      ↓
BEGIN
      ↓
DDL
      ↓
Immediate bounded validation
      ↓
COMMIT / ROLLBACK
## 3.22.15 Bound Lock Waiting

Where appropriate:

BEGIN;

SET LOCAL lock_timeout = '5s';

ALTER TABLE ...;

COMMIT;

The actual value must be workload-specific.

The objective is not:

Eventually acquire lock

but:

Acquire lock within
an operationally safe window
## 3.22.16 Understand Timeout Differences

lock_timeout limits time waiting to acquire a lock.

statement_timeout limits overall statement execution time.

For suitable migration sessions:

SET LOCAL lock_timeout = '5s';
SET LOCAL statement_timeout = '30min';

may provide guardrails.

Also evaluate:

idle_in_transaction_session_timeout

for administrative and migration sessions where abandoned transactions are a risk.

Do not copy timeout values blindly between environments.

## 3.22.17 Watch the Lock Queue

A dangerous production pattern is:

DDL requests lock
       ↓
DDL waits
       ↓
New application requests queue
       ↓
Connection pool saturates
       ↓
Timeouts
       ↓
Retries
       ↓
More pressure
       ↓
Outage

A blocked DDL session can therefore become a queue amplifier.

Abort criteria should consider both the DDL wait and application sessions queuing behind it.

## 3.22.18 Include Connection Pools in Change Planning

For high-impact DDL monitor:

Pool utilization
Database connections
Waiting sessions
Request latency
Timeouts
Retry rate

Database lock health alone is not sufficient.

The application may already be failing while the database itself appears available.

## 3.22.19 Prefer Concurrent Index Creation Where Appropriate

Standard index creation can block writes.

For suitable production workloads:

CREATE INDEX CONCURRENTLY orders_customer_id_idx
ON app.orders(customer_id);

can allow normal writes to continue while PostgreSQL builds the index.

However, concurrent builds require more work, involve multiple phases, can wait for transactions, and cannot run inside a transaction block.

Therefore:

CONCURRENTLY
      ≠
zero production impact
## 3.22.20 Capacity-Plan Index Builds

Before a large index build evaluate:

Table size
Expected index size
CPU
Storage I/O
Temporary storage
WAL generation
Replication lag
CDC lag
Current traffic
Transaction age

A non-blocking operation can still cause an availability incident through resource exhaustion.

## 3.22.21 Monitor Index Progress

Where supported:

SELECT *
FROM pg_stat_progress_create_index;

PostgreSQL exposes progress information for CREATE INDEX and REINDEX operations through this view.

Monitor progress together with:

CPU
I/O latency
WAL
Storage
Replica lag
Application P95/P99
## 3.22.22 Detect Invalid Indexes

Concurrent index failures can leave invalid indexes.

Check:

SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    i.relname AS index_name,
    x.indisvalid,
    x.indisready,
    x.indislive
FROM pg_index x
JOIN pg_class i
  ON i.oid = x.indexrelid
JOIN pg_class t
  ON t.oid = x.indrelid
JOIN pg_namespace n
  ON n.oid = t.relnamespace
WHERE NOT x.indisvalid
   OR NOT x.indisready
   OR NOT x.indislive;

Never assume a failed migration returned the catalog to its original state.

## 3.22.23 Reindex Carefully

For suitable production cases evaluate:

REINDEX INDEX CONCURRENTLY app.orders_customer_id_idx;

rather than immediately using blocking REINDEX.

But capacity, WAL, progress, replication, and failure-state monitoring remain necessary.

## 3.22.24 Protect Constraint-Supporting Indexes

Before dropping an index determine whether it participates in:

PRIMARY KEY
UNIQUE constraint
EXCLUSION constraint
Replica identity

An index can be:

Performance infrastructure
        +
Integrity infrastructure
        +
Replication infrastructure

Do not classify indexes solely from query-performance statistics.

## 3.22.25 Analyze Dependencies Before Destructive DDL

Before:

DROP TABLE
DROP COLUMN
DROP VIEW
DROP TYPE
DROP FUNCTION
DROP SCHEMA

inventory dependencies.

Include:

Constraints
Indexes
Views
Materialized views
Functions
Triggers
Generated columns
Expression indexes
Policies
Applications
CDC
ETL/reporting

Do not discover the dependency graph by casually adding:

CASCADE

to a failed production command.

## 3.22.26 Treat CASCADE as Blast-Radius Approval

A dependency error is valuable information.

DROP fails
   ↓
Dependencies discovered
   ↓
Investigate
   ↓
Determine intentional blast radius
   ↓
Controlled migration

The production principle is:

CASCADE is not an error-handling strategy.

## 3.22.27 Prefer Expand-and-Contract Schema Changes

For application-facing changes:

EXPAND
   ↓
Add compatible structure
   ↓
Deploy application capable of both models
   ↓
BACKFILL / MIGRATE
   ↓
CUTOVER
   ↓
OBSERVE
   ↓
CONTRACT
   ↓
Remove deprecated structure

This is especially important with rolling deployments where old and new application instances coexist.

## 3.22.28 Preserve Application-Version Compatibility

During a rolling deployment:

OLD APPLICATION ─┐
                 ├── compatible database schema
NEW APPLICATION ─┘

should generally remain possible during transition.

Avoid migrations that instantly make the previous application version unusable unless the deployment architecture guarantees atomic cutover.

## 3.22.29 Kubernetes Schema-Change Pattern

A production-safe pattern is commonly:

Expand database
      ↓
Deploy compatible application
      ↓
Migrate/backfill
      ↓
Observe
      ↓
Stop old behavior
      ↓
Contract database later

This reduces coupling between pod rollout and destructive schema changes.

## 3.22.30 Classify Type Changes by Rewrite Behavior

Before:

ALTER TABLE app.orders
ALTER COLUMN ...
TYPE ...;

determine whether the specific conversion is:

Metadata / binary-compatible
            or
Physical relation rewrite

Never estimate ALTER COLUMN TYPE risk from syntax alone.

A rewrite can affect:

Lock duration
I/O
Storage
WAL
Replica lag
CDC
Maintenance window
## 3.22.31 Treat Defaults as Version- and Expression-Specific

Do not apply obsolete universal rules such as:

ADD COLUMN DEFAULT
      =
always rewrites table

Behavior depends on PostgreSQL version and the particular default/expression.

Always validate against the deployed version and actual change.

## 3.22.32 Deploy NOT NULL Deliberately

For very large tables, consider whether nullability validation can be staged using version-appropriate PostgreSQL mechanisms.

The goal is:

Establish data invariant
       ↓
Validate safely
       ↓
Establish final constraint

rather than forcing the most expensive validation into the most sensitive deployment moment.

## 3.22.33 Stage Constraint Validation Where Supported

For supported constraint types:

ALTER TABLE app.orders
ADD CONSTRAINT orders_customer_fk
FOREIGN KEY (customer_id)
REFERENCES app.customers(id)
NOT VALID;

Then:

ALTER TABLE app.orders
VALIDATE CONSTRAINT orders_customer_fk;

This separates constraint installation from historical-row validation.

Do not assume NOT VALID is supported identically for every constraint type. Check the exact PostgreSQL semantics.

## 3.22.34 Foreign Keys Require Workload Analysis

Before deploying a large FK evaluate:

Parent size
Child size
Existing orphan data
Write rate
Parent UPDATE/DELETE patterns
Supporting indexes
Validation cost
Lock behavior

PostgreSQL does not automatically create an index on referencing columns merely because a foreign key exists.

Whether such an index is needed remains workload-dependent.

## 3.22.35 Do Not Disable Integrity Casually

Avoid operational shortcuts such as:

Drop the FK temporarily
Disable the trigger
Remove the constraint
Recreate it later

without explicit:

Data validation
Change ownership
Recovery procedure
Observation

Temporary integrity removal can create permanent corruption.

## 3.22.36 Treat Large Backfills as Production Workloads

A large:

UPDATE ...

can create:

CPU
I/O
WAL
Index writes
Trigger execution
Dead tuples
Replica lag
CDC lag
Autovacuum demand

Therefore:

Backfill
   ≠
simple migration statement
## 3.22.37 Inventory Triggers Before Backfills

A row update may execute:

BEFORE triggers
AFTER triggers
Constraint triggers
Audit logic
Derived writes
Notifications
Cross-table operations

Therefore:

Backfill cost
     =
Base DML
+ Index maintenance
+ Trigger cost
+ WAL
+ Replica work
+ Vacuum debt
## 3.22.38 Rate-Control Large Backfills

Prefer:

Batch
  ↓
Commit
  ↓
Measure
  ↓
Continue / slow / pause

Measure:

Application latency
CPU
I/O
WAL
Replica lag
CDC lag
Dead tuples

The objective is not maximum migration throughput.

It is maximum safe throughput.

## 3.22.39 Make Backfills Restartable

Use durable checkpoints.

Prefer stable key/range batching where practical:

WHERE id > :last_processed_id
ORDER BY id
LIMIT :batch_size;

rather than increasingly expensive large OFFSET pagination.

A failed migration should resume from a known checkpoint rather than restart from row one.

## 3.22.40 Backfill Completion Includes Cleanup

After the final batch evaluate:

ANALYZE needed?
Autovacuum healthy?
Dead tuples declining?
Bloat acceptable?
Replica caught up?
CDC caught up?
Application healthy?

The last committed batch is not necessarily the end of the production change.

## 3.22.41 Partition Administration Requires Lifecycle Engineering

Automate:

Create future partition
        ↓
Validate bounds
        ↓
Create indexes
        ↓
Apply privileges
        ↓
Attach
        ↓
Monitor
        ↓
Retention boundary
        ↓
Archive / detach / drop

Never discover at the partition boundary that the next partition does not exist.

## 3.22.42 Partition Operations Still Have Locks

Before:

ATTACH PARTITION
DETACH PARTITION
DROP PARTITION

evaluate:

Parent locks
Child locks
Constraint validation
Indexes
Foreign keys
Traffic
Replication

Partitioning reduces lifecycle cost; it does not make every administrative operation lock-free.

## 3.22.43 Pre-Build Partitions Where Practical

Prefer:

Prepare partition
      ↓
Validate bounds
      ↓
Load/backfill if required
      ↓
Build indexes
      ↓
Apply privileges
      ↓
Attach

rather than doing all expensive work at cutover time.

## 3.22.44 Validate Partitioned Indexes

Do not assume:

Parent index exists
       =
Every partition is correctly indexed

Validate expected child indexes and attachment state across partitions.

## 3.22.45 Govern Privileges as Object State

Every object deployment must answer:

Who owns it?
Who can connect?
Who can resolve its schema?
Who can read it?
Who can write it?
Who can execute it?
Who can maintain it?
Who can alter/drop it?

Access often follows:

LOGIN
  ↓
DATABASE CONNECT
  ↓
SCHEMA USAGE
  ↓
OBJECT PRIVILEGE
  ↓
DEPENDENT SEQUENCE/FUNCTION
  ↓

## 3.22.46 Use Group Roles

Prefer:

app_ro
app_rw
app_admin
db_maintain

and grant login roles membership.

Avoid large collections of direct per-user object grants.

This improves:

Access review
Revocation
Auditing
Role rotation
Least privilege
## 3.22.47 Govern Default Privileges

Existing-object grants do not automatically solve future-object access.

Use intentional:

ALTER DEFAULT PRIVILEGES ...

design.

But remember that default privileges depend on the role creating future objects.

Therefore test the real deployment path:

CI/CD identity
     ↓
SET ROLE?
     ↓
Effective creator
     ↓
Object owner
     ↓
Default privileges
## 3.22.48 Detect Owner and Privilege Drift

Examples:

Expected owner = app_owner
Actual owner   = developer_login

or:

Existing tables → app_ro has SELECT
New table       → app_ro missing SELECT

Automated health checks should detect both.

## 3.22.49 Validate Privileges as Runtime Roles

Do not validate access only as:

superuser
postgres
object owner

Test as:

Application role
Read-only role
Deployment role
Maintenance role

Production validation asks:

Can the intended principal perform exactly the intended operation?

## 3.22.50 Include Row-Level Security

For RLS-protected tables inspect policies:

SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd
FROM pg_policies
ORDER BY schemaname, tablename, policyname;

Changes to:

Ownership
Roles
Policies
Tables
Application identities

can change effective access behavior.

## 3.22.51 Administer Sequences Explicitly

For sequence-backed identifiers validate:

Sequence exists
Correct owner
Correct dependency
Correct privileges
Correct table/column relationship

Table privileges do not automatically guarantee every sequence privilege an application may require.

## 3.22.52 Prefer Identity Columns for New Designs

For modern schemas consider SQL-standard identity columns:

GENERATED ALWAYS AS IDENTITY

or:

GENERATED BY DEFAULT AS IDENTITY

where appropriate.

Existing serial schemas remain common and must still be administered correctly.

## 3.22.53 Treat Ownership Changes as Security Changes

An:

ALTER ... OWNER TO ...

operation can change:

DDL authority
Drop/alter authority
Operational responsibility
SECURITY DEFINER behavior

Ownership transfer is therefore not merely metadata cleanup.

## 3.22.54 Include Event Triggers in DDL Analysis

Event triggers may implement:

DDL auditing
Security controls
Policy enforcement
Metadata capture

Identical DDL can therefore behave differently between environments when event-trigger configuration differs.

Include event-trigger parity in advanced production assessments.

## 3.22.58 Idempotency Does Not Prove Correctness

Statements such as:

CREATE TABLE IF NOT EXISTS ...

can be useful.

But:

Object exists
      ≠
Object matches desired definition

Automation must validate semantic state, not merely suppress duplicate-object errors.

## 3.22.59 Do Not Hide Migration Failures

Avoid broad patterns such as:

"already exists — ignore"

because the object could be:

Correct
Wrong definition
Wrong owner
Wrong schema
Partially created
Left from failed deployment

Inspect state explicitly.

## 3.22.60 Replication Is Part of Object Administration

Schema changes can affect:

Physical replicas
Logical replication
CDC
Kafka connectors
ETL
Data warehouses
Search synchronization
Audit pipelines

A database change is therefore often a distributed-system change.

## 3.22.61 Protect Replica Identity

Inspect where relevant:

SELECT
    n.nspname,
    c.relname,
    c.relreplident
FROM pg_class c
JOIN pg_namespace n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'p');

Changes to:

Primary keys
Unique indexes
Replica identity
Table structure

may change CDC behavior.

## 3.22.62 Check Publication Membership

Where logical replication is used:

SELECT *
FROM pg_publication_tables
ORDER BY pubname, schemaname, tablename;

Review changes involving:

Tables
Columns
Replica identity
Partition topology
Publication membership

against downstream consumers.

## 3.22.63 Maintain a CDC Contract

Before changing a replicated object ask:

Table renamed?
Schema renamed?
Column removed?
Column renamed?
Column type changed?
Primary key changed?
Replica identity changed?
Publication changed?
Partition behavior changed?
Consumer compatible?

A successful primary-database deployment is not successful if the downstream data pipeline breaks.

## 3.22.64 Budget WAL

Large:

Backfills
Index builds
Reindexes
Table rewrites
Bulk loads

can produce substantial WAL.

Monitor:

WAL generation
Archive backlog
Replica lag
Replication slots
CDC lag
Storage
Network throughput

Define acceptable limits before execution.

## 3.22.65 Storage Headroom Must Include Maintenance

Do not calculate storage only from steady-state database size.

Allow for:

Temporary index copies
Table rewrites
WAL growth
Retained WAL
Maintenance workspace
Replica/CDC backlog

A migration can fail from storage exhaustion even when normal database capacity is healthy.

## 3.22.66 Backup Is Not a Rollback Plan

Before destructive DDL, asking:

Do we have a backup?

is insufficient.

Ask:

How long does restore take?
Can PITR reach the required point?
Where will recovery occur?
How does application reconnect?
How much reconciliation is required?
Does this satisfy RTO/RPO?

Recoverability must be operationally usable.

## 3.22.67 Prefer Reversible Changes

Where practical:

ADD before DROP
Create before replace
Expand before contract
Detach before destroy
Deprecate before remove

A compatibility window often provides a much safer recovery path than immediate destruction.

## 3.22.68 Define Abort Criteria Before Execution

Examples:

Abort / pause if:

Lock wait exceeds threshold
Application P99 exceeds threshold
Error rate rises materially
Connections approach unsafe limit
Replica lag exceeds threshold
CDC lag exceeds threshold
WAL backlog exceeds threshold
Storage headroom falls below threshold
Unexpected blocker appears
Operation stops progressing

Thresholds must be environment-specific.

Monitoring without predetermined decision criteria is weaker than real change control.

## 3.22.82 Production Anti-Patterns

Avoid:

DDL worked in dev
    → run directly in prod

Transactional DDL
    → therefore harmless

CONCURRENTLY
    → zero impact

Dependency error
    → add CASCADE

Old column unused
    → DROP immediately

idx_scan = 0
    → DROP INDEX

Need maintenance
    → use superuser

Need access
    → GRANT ALL

Table privileges correct
    → application access must work

Migration failed
    → ignore existing object

Large UPDATE
    → just let it finish

Have backup
    → rollback solved

Maintenance window
    → unsafe operation becomes safe

SQL succeeded
    → production change succeeded
## 3.22.83 Production Golden Rules
Treat production DDL as reliability engineering.
Know the lock before executing the statement.
Analyze lock queues, not only statement duration.
Check long, idle, and prepared transactions.
Keep transactional DDL transactions short.
Bound lock waiting where appropriate.
Include connection pools in lock-risk analysis.
Use stable ownership roles rather than personal accounts.
Separate runtime, maintenance, deployment, and ownership authority.
Apply least privilege.
Treat ownership changes as security changes.
Secure schemas and search_path.
Harden privileged SECURITY DEFINER functions.
Schema-qualify operational SQL.
Standardize object naming.
Keep historical state in Git—not _old objects.
Analyze dependencies before destructive changes.
Never use CASCADE without explicit blast-radius approval.
Prefer expand-and-contract migrations.
Preserve old/new application compatibility during rollout.
Classify whether a schema change scans or rewrites data.
Treat large backfills as controlled workloads.
Make long migrations rate-controlled and restartable.
Include trigger cost in DML estimates.
Stage constraint validation where PostgreSQL supports it.
Analyze foreign-key indexes and workload behavior.
Protect indexes supporting integrity or replica identity.
Use concurrent index operations where appropriate—but capacity-plan them.
Monitor long administrative operations.
Detect invalid indexes after failed concurrent operations.
Govern default privileges.
Validate access using actual runtime roles.
Include RLS in security validation.
Administer sequences and identity relationships explicitly.
Automate partition lifecycle before boundaries arrive.
Analyze locks for partition operations.
Maintain metadata baselines.
Treat Git/migrations as the source of intent.
Never confuse idempotent syntax with correct desired state.
Treat replication and CDC as schema consumers.
Protect replica identity.
Budget WAL and storage for maintenance.
Define abort criteria before starting.
A backup is not a rollback plan.
Validate recovery against RTO/RPO.
Monitor database, application, replication, and platform together.
Validate the intended performance outcome—not just object existence.
Require an observation window for significant changes.
Audit emergency manual DDL and reconcile it into Git.
Automate observation aggressively and destructive action conservatively.

## 3.22.85 Final Production Standard

The final operating principle for Chapter 3 is:

A PostgreSQL object change is complete only when the desired database state exists, the application remains healthy, security remains correct, dependencies remain valid, replication and CDC remain healthy, recovery remains possible, the production outcome has been validated, and the resulting state is represented in the system of record.

Production DBRE work therefore does not end with:

ALTER TABLE

CREATE INDEX

GRANT

VACUUM

COMMIT

It ends with:

UNDERSTOOD
    +
CONTROLLED
    +
OBSERVED
    +
VALIDATED
    +
RECOVERABLE
    +
AUDITABLE
