## 3.23.1 Purpose

Database and object administration failures must be treated as reliability events, not merely failed SQL commands.

Typical incidents include:

DDL blocked
Deadlock
Lock timeout
Long transaction
Idle-in-transaction session
Prepared transaction
Failed schema migration
Partial migration
Invalid/corrupt index
Constraint validation failure
Dependency failure
Accidental DROP / CASCADE
Unexpected table rewrite
Storage/WAL pressure
Backfill overload
Partition failure
Privilege/ownership drift
RLS failure
Sequence drift
Replication lag
CDC failure
Application/schema incompatibility

The DBRE objective is:

Restore service safely, preserve data integrity and security, recover the correct database state, validate all dependent systems, determine root cause, and prevent recurrence.

The canonical lifecycle is:

DETECT
   ↓
CLASSIFY SEVERITY
   ↓
CONTAIN
   ↓

   ↓

   ↓
DIAGNOSE
   ↓

   ↓

   ↓

## 3.23.2 Understand the Failure State First

Four states must be distinguished:

FAILED
  └── statement or operation returned failure

BLOCKED
  └── operation is waiting

SLOW
  └── operation is progressing slowly

BROKEN
  └── resulting database/application state
      is unusable or incorrect

Also distinguish:

Statement failed
      ≠
Transaction rolled back
      ≠
Migration rolled back
      ≠
Database unchanged

A failed migration may have already changed production.

## 3.23.3 Golden Troubleshooting Rule

Diagnose before changing production state unless immediate intervention is required to prevent a larger availability, integrity, security, or storage incident.

Avoid reflexively executing:

pg_terminate_backend()
DROP
CASCADE
REINDEX
VACUUM FULL
Disable trigger
Disable constraint
Disable RLS
Drop replication slot
Restart database

First establish:

What failed?
What changed?
Which object?
Which transaction?
Which application?
What is blocked?
Is data at risk?
Is security affected?
Is replication affected?
Can intervention make recovery harder?

## 3.23.10 Inspect Active Sessions
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    datname,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    backend_type,
    query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST,
         query_start NULLS LAST;

Look for:

Long transactions
Long queries
Idle-in-transaction
Lock waits
Migration sessions
Unexpected clients
## 3.23.11 DDL Blocked by Locks

Identify waiting sessions:

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blocking_pids,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Then inspect locks:

SELECT
    l.pid,
    a.usename,
    a.application_name,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation,
    l.transactionid,
    l.virtualxid,
    a.wait_event_type,
    a.wait_event,
    a.query
FROM pg_locks l
LEFT JOIN pg_stat_activity a
       ON a.pid = l.pid
ORDER BY l.granted, l.pid;
## 3.23.12 Find the Root Blocker

Do not stop at the immediate blocker.

Session A
   ↓ blocks
Session B
   ↓ blocks
DDL C
   ↓ queues
Application D/E/F

Troubleshooting must trace:

Waiting session
      ↓
Immediate blocker
      ↓
Blocker's blocker
      ↓
Root blocker

Killing the wrong session may accomplish nothing.

## 3.23.13 Lock Queue Amplification

A dangerous sequence is:

Application transaction
        ↓
holds lock
        ↓
DDL waits
        ↓
new application requests queue
        ↓
pool saturates
        ↓
timeouts
        ↓
retries
        ↓
outage

Monitor application connection pools during every serious lock incident.

## 3.23.14 Long Transactions
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

Determine:

Application owner
Read/write state
Business operation
Rollback cost
Retry behavior

before terminating anything.

## 3.23.15 idle in transaction
SELECT
    pid,
    usename,
    application_name,
    xact_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

Potential effects:

Locks retained
Old snapshots retained
Vacuum interference
DDL blockage
Connection consumption

Repeatedly killing these sessions is not remediation. Correct the application's transaction handling and evaluate an appropriate idle_in_transaction_session_timeout.

## 3.23.16 Prepared Transactions
SELECT *
FROM pg_prepared_xacts;

Prepared transactions can survive the original client connection.

Do not execute:

COMMIT PREPARED '...';

or:

ROLLBACK PREPARED '...';

until ownership and distributed-transaction state are understood.

## 3.23.17 Deadlocks

Topology:

Transaction A
holds X
waits Y
    ↑
    │
    ↓
Transaction B
holds Y
waits X

PostgreSQL detects deadlocks and aborts one participating transaction.

The durable remediation is generally:

Consistent resource ordering
+
Short transactions
+
Bounded retry where appropriate

Remember:

Deadlock retry is mitigation; transaction redesign is remediation.

## 3.23.18 Lock Timeout

A lock timeout can mean the safety mechanism worked:

DDL
 ↓
cannot acquire lock
within safe window
 ↓
statement cancelled
 ↓
application protected

Do not automatically increase lock_timeout.

Investigate the blocker first.

## 3.23.19 Statement Timeout

A timeout can result from:

Table scan
Rewrite
Constraint validation
Large index operation
Slow I/O
Resource contention
Lock waiting

Determine whether the operation was:

Working
Waiting
Blocked
Resource-starved

before extending the timeout.

## 3.23.20 Cancellation Before Termination

When appropriate, prefer:

SELECT pg_cancel_backend(<pid>);

before:

SELECT pg_terminate_backend(<pid>);

Conceptually:

pg_cancel_backend()
       ↓
cancel current query

pg_terminate_backend()
       ↓
terminate session
       ↓
open transaction rolls back

Termination may therefore trigger additional recovery work.

## 3.23.22 Transaction-Aborted State

Inside an explicit transaction, many errors leave the transaction unusable until rollback.

Example:

BEGIN;

ALTER TABLE ...;
-- ERROR

ROLLBACK;

Migration tooling must distinguish:

Statement error
      vs
Aborted transaction
      vs
Previously committed migration state
## 3.23.23 Failed CREATE INDEX CONCURRENTLY

A failed concurrent index build can leave an invalid index. PostgreSQL documents failures such as uniqueness violations and deadlocks as cases that can leave such state.

Inspect:

SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    i.relname AS index_name,
    x.indisvalid,
    x.indisready,
    x.indislive
FROM pg_index x
JOIN pg_class i
  ON i.oid = x.indexrelid
JOIN pg_class t
  ON t.oid = x.indrelid
JOIN pg_namespace n
  ON n.oid = t.relnamespace
WHERE NOT x.indisvalid
   OR NOT x.indisready
   OR NOT x.indislive;
## 3.23.24 Invalid Does Not Mean Irrelevant

Before removing an invalid index determine whether it is:

Unique
Constraint-related
Replica-identity-related
Application-relevant

An invalid unique index created concurrently can have special enforcement behavior during failed builds.

Therefore:

Never automatically drop every invalid index discovered by monitoring.

Investigate its origin and dependency state first.

## 3.23.25 Monitor Index Progress
SELECT
    pid,
    datname,
    relid::regclass AS table_name,
    index_relid::regclass AS index_name,
    command,
    phase,
    lockers_total,
    lockers_done,
    current_locker_pid,
    blocks_total,
    blocks_done,
    tuples_total,
    tuples_done
FROM pg_stat_progress_create_index;

Progress information can distinguish a genuinely stalled operation from one waiting for transactions or processing a large relation.

## 3.23.26 Failed REINDEX CONCURRENTLY

Inspect:

Original index
*_ccnew
*_ccold
Validity
Dependencies
Constraint relationships

PostgreSQL may leave temporary indexes after failed concurrent reindex operations.

Do not blindly drop objects based solely on _ccnew or _ccold naming.

Determine which phase failed and follow version-appropriate recovery procedures.

## 3.23.27 Suspected Index Corruption

Distinguish:

INVALID
   ≠
CORRUPT

For suspected structural corruption, use version-appropriate PostgreSQL integrity tooling such as:

amcheck
pg_amcheck

where applicable.

Response:

Capture evidence
      ↓
Determine affected objects
      ↓
Integrity check
      ↓
Assess replicas/backups
      ↓
Determine REINDEX/recovery strategy

Do not perform random reindexing before understanding the failure domain.

## 3.23.28 Unique Constraint Failure

If uniqueness deployment fails:

SELECT
    candidate_key,
    count(*)
FROM app.target_table
GROUP BY candidate_key
HAVING count(*) > 1;

Determine whether duplicates represent:

Bad historical data
Legitimate business duplicates
Incorrect uniqueness requirement
Migration race

Never delete business data solely to make the migration pass.

## 3.23.29 Foreign Key Failure

Find potential orphan rows:

SELECT c.*
FROM app.child c
LEFT JOIN app.parent p
       ON p.id = c.parent_id
WHERE c.parent_id IS NOT NULL
  AND p.id IS NULL;

Then determine the correct business treatment:

Correct
Map
Archive
Delete

through appropriate data governance.

## 3.23.30 NOT NULL Failure

If:

ALTER COLUMN ... SET NOT NULL

fails, inspect:

SELECT count(*)
FROM app.target_table
WHERE target_column IS NULL;

Then:

Understand NULL population
      ↓
Backfill/correct safely
      ↓
Validate
      ↓
Retry

Do not weaken a legitimate integrity requirement merely because historical data violates it.

## 3.23.31 Constraint Validation Failure

For supported staged constraints:

ADD ... NOT VALID
       ↓
correct historical data
       ↓
VALIDATE CONSTRAINT

NOT VALID is not universal across all constraint forms; validate the exact PostgreSQL behavior for the deployed version.

Constraint failures are valuable data-quality evidence.

## 3.23.32 Dependency Failure

If:

DROP

RENAME

fails because of dependencies, investigate:

Views
Materialized views
Functions
Triggers
Rules
Constraints
Generated expressions
Indexes
Extension ownership

Use dependency information from supported catalog inspection such as pg_depend and pg_shdepend.

Never directly modify dependency catalogs.

## 3.23.33 CASCADE Is Not Troubleshooting

Never use:

DROP failed
   ↓
add CASCADE

as a generic recovery procedure.

Instead:

Dependency discovered
      ↓
Inventory blast radius
      ↓
Determine intended change
      ↓
Redesign migration
## 3.23.34 Accidental DROP / CASCADE

Immediately:

STOP further DDL
      ↓
Preserve evidence
      ↓
Determine committed state
      ↓
Identify affected objects/data
      ↓
Assess application impact
      ↓
Choose recovery

Recovery options include:

Recreate definition
Restore from Git/migrations
Recover through PITR
Reconcile data
## 3.23.35 Prefer Isolated PITR Recovery Where Appropriate

A powerful recovery pattern is:

Production continues
       │
       └──────────────┐
                      ▼
                PITR instance
                      ↓
               recover object/data
                      ↓
                   validate
                      ↓
                 reconcile
                      ↓
              controlled repair

This can avoid rolling the entire production database backward.

Before full-database PITR ask:

What valid writes would be lost?
What is RPO?
What is RTO?
Can isolated recovery solve the problem?
## 3.23.36 Rename and External Consumer Failures

Potential consumers include:

CDC

Monitoring
Scripts

Therefore:

Database dependency healthy
          ≠
External consumer healthy

## 3.23.38 Storage Emergency

Determine the source:

WAL
Temporary files
Index build
Table rewrite
Backfill
Replication slot
Archive backlog

Then:

Stop nonessential maintenance
      ↓
Contain growth
      ↓
Increase capacity if appropriate
      ↓
Correct root cause
Critical Rule

Never manually delete PostgreSQL files—including files under pg_wal—as an ad-hoc response to storage pressure.

## 3.23.39 Temporary-File Pressure

Administrative operations can generate temporary storage through:

Sorts
Index creation
Validation queries
Migration queries

Monitor temporary-file and storage behavior during large operations.

Do not solve slow maintenance by blindly increasing memory parameters beyond safe physical capacity.

Typical progression:

Large UPDATE
     ↓
new row versions
     ↓
WAL
     ↓
index writes
     ↓
trigger work
     ↓
dead tuples
     ↓
vacuum debt
     ↓
replica lag
     ↓

Respond:

Pause
 ↓
Recover
 ↓
Reduce batch
 ↓
Reduce rate
 ↓
Resume

## 3.23.41 Backfill Must Be Restartable

Track:

Last successful checkpoint
Processed range
Remaining range
Retry semantics
Idempotency

Prefer stable key/range checkpoints where appropriate.

A failure after multiple committed batches means production is already partially migrated.

## 3.23.42 Post-Backfill MVCC and Autovacuum

After a large update/delete, inspect:

Dead tuples
Autovacuum activity
Autoanalyze
Long transactions
Table/index growth
Statistics freshness

Physical storage does not necessarily shrink immediately after rows become dead.

Do not confuse pending vacuum cleanup with permanent bloat.

## 3.23.43 Statistics Regression

A migration can be functionally successful but cause performance regression.

Investigate:

Query plans
Statistics freshness
Data distribution
Index usage
Partition pruning

Where appropriate:

ANALYZE app.target_table;

then re-evaluate representative query plans.

## 3.23.44 Partition Attach Failure

Possible causes:

Rows outside bounds
Overlapping bounds
Column mismatch
Constraint mismatch
Lock conflict
Default-partition conflict

Treat partition attachment as both:

Data-validation event
        +
Locking event

not merely metadata administration.

## 3.23.45 Missing Partition

When insertion fails because no partition accepts the row:

Capture partition key
       ↓
Compare bounds
       ↓
Determine provisioning failure
       ↓
Create correct partition
       ↓
Create/attach indexes
       ↓
Apply privileges
       ↓
Validate
       ↓
Resume workload

Do not create an arbitrary catch-all partition solely to suppress the error.

## 3.23.46 Partition Detach Failure

If a concurrent detach is interrupted, do not assume nothing changed.

Inspect the actual partition state and use version-appropriate completion/recovery procedures before retrying.

## 3.23.47 Permission Failure

Trace the complete access chain:

LOGIN
  ↓
CONNECT
  ↓
Role membership
  ↓
INHERIT / SET ROLE
  ↓
Schema USAGE
  ↓
Object privilege
  ↓

## 3.23.48 Default Privilege Drift

Pattern:

Old tables work
New table fails

Check:

Object creator
Object owner
Deployment identity
SET ROLE
ALTER DEFAULT PRIVILEGES

Default privileges are sensitive to the role creating the object.

      vs
ACTUAL OWNER

## 3.23.50 search_path Failure

      vs

## 3.23.51 SECURITY DEFINER Failure

Inspect:

Function owner
EXECUTE privilege
search_path
Referenced schemas
Referenced objects
Role changes
Ownership changes

## 3.23.52 Row-Level Security Failure

If table privileges appear correct but access differs:

Runtime role
      ↓
Table owner
      ↓
RLS enabled?
      ↓
FORCE RLS?
      ↓
Policies
      ↓
BYPASSRLS?

Inspect:

SELECT
    schemaname,
    tablename,
    policyname,
    permissive,
    roles,
    cmd
FROM pg_policies
ORDER BY schemaname, tablename, policyname;

Object privileges and row visibility are separate security layers.

## 3.23.53 Sequence Permission Failure

If:

SELECT works
INSERT fails
permission denied for sequence

inspect:

Sequence privilege
Sequence owner
Role membership
Column default
Identity relationship

Grant only the authority required.

## 3.23.54 Sequence Drift

After imports/manual inserts:

sequence value
      <
existing generated IDs

may cause duplicate-key failures.

Before adjusting sequence state, account for:

Concurrent writers
Identity behavior
Sequence ownership
Current sequence state
Existing maximum

Do not blindly execute setval(MAX(id)) against an active production workload.

## 3.23.55 Extension-Owned Objects

Before altering or dropping unfamiliar objects determine whether they are:

Application-owned
Extension-owned
System-managed

Manual modification of extension-owned objects can break extension lifecycle operations.

## 3.23.56 System Catalog Safety

Catalogs such as:

pg_class
pg_attribute
pg_index
pg_constraint
pg_depend

are excellent diagnostic sources.

But:

Do not repair normal production object failures by directly updating PostgreSQL system catalogs.

Use supported DDL and recovery mechanisms.

## 3.23.57 Replica Lag After Administration

Monitor:

Storage
Network

## 3.23.59 CDC Failure After Schema Change

Replica identity
Publication
Column rename/drop
Type change
Partition behavior
Subscriber schema
Connector schema
Consumer compatibility

## 3.23.60 Replication Slot WAL Growth

Pattern:

Consumer behind
      ↓
slot retains WAL
      ↓
storage grows
      ↓
database availability risk

But:

DROP SLOT
      ↓
consumer may lose restart position
      ↓
resynchronization may be required

Therefore slot deletion is a pipeline-recovery decision, not a disk-cleanup command.

## 3.23.62 Database Restart Decision

What persistent state remains?

## 3.23.81 Canonical Golden Rules
Stabilize service before optimizing repair.
Preserve evidence whenever operationally possible.
Know the PostgreSQL version and platform.
Establish the incident timeline.
Distinguish failed, blocked, slow, and broken.
Distinguish statement failure from transaction and migration state.
Trace lock chains to the root blocker.
Include connection pools in lock incidents.
Prefer query cancellation before session termination when sufficient.
Understand rollback cost before terminating writers.
Treat recurring deadlocks as design defects.
Never increase timeouts blindly.
Inspect catalog state after failed migrations.
Treat invalid indexes carefully.
Distinguish invalidity from corruption.
Treat constraint failures as data-quality evidence.
Never use CASCADE as automatic troubleshooting.
Prefer isolated PITR recovery when appropriate.
Understand table scan/rewrite behavior.
Never manually delete PostgreSQL/WAL files as ad-hoc repair.
Rate-control and checkpoint backfills.
Include MVCC/autovacuum debt in migration recovery.
Validate statistics and plans after major data changes.
Treat partition failures as data and locking events.
Diagnose the complete privilege chain.
Include RLS, ownership, search_path, functions, and sequences.
Do not directly modify system catalogs for ordinary repair.
Treat physical replication, logical replication, and CDC separately.
Treat replication-slot deletion as a pipeline-recovery decision.
Preserve application/schema compatibility during rolling deployment.
Restart only when the failure mechanism justifies restart.
Define abort criteria before risky remediation.
Validate database, application, replication, and infrastructure independently.
Require an observation window.
Reconcile emergency changes into Git.
Separate mitigation from remediation.
Convert incidents into durable prevention.
Automate detection more aggressively than destructive recovery.
A successful SQL command does not prove system recovery.
An incident is closed only when the system is correct, healthy, recoverable, and understood.

## 3.23.83 Final Production Standard

The governing standard for PostgreSQL database/object troubleshooting is:

A production database incident is not resolved when the error disappears. It is resolved when service is restored, database state is correct, integrity and security are preserved, applications are healthy, replication and CDC are healthy or converging safely, recovery remains possible, the root cause is understood, and preventive controls have been established.

The troubleshooting mindset therefore moves from:

ERROR
  ↓
GUESS
  ↓
CHANGE

to:

DETECT
  ↓
EVIDENCE
  ↓
DIAGNOSE
  ↓
CONTAIN
  ↓
MITIGATE
  ↓
RECOVER
  ↓
VALIDATE
  ↓
OBSERVE
  ↓
REMEDIATE
  ↓
PREVENT

That is the production DBRE standard.
