3.23 — Database/Object Administration Troubleshooting and Failure Scenarios
Technical Review

Review stage: Technical Review
Draft reviewed: 3.23 — Draft
Technical baseline: PostgreSQL 18/current documentation
Review result: PASS WITH REQUIRED TECHNICAL HARDENING

The draft is strong and already follows the correct DBRE incident model. The Technical Review should preserve its structure while tightening PostgreSQL semantics, adding missing failure states, and making several diagnostic procedures safer for production use.

1. Technical Review Objectives

The section must distinguish four fundamentally different states:

FAILED
  │
  ├── statement failed
  │
  ├── transaction aborted
  │
  ├── operation partially completed
  │
  └── database state changed before failure

BLOCKED
  │
  └── operation has not failed;
      it is waiting

SLOW
  │
  └── operation is progressing,
      but slower than expected

BROKEN
  │
  └── resulting object/catalog/
      application state is unusable

These must not be treated as equivalent.

2. Strengthen the First Principle

The Draft says:

Diagnose before changing state.

Keep this, but strengthen it to:

Diagnose before changing state, unless immediate action is required to prevent a larger availability, integrity, security, or storage incident.

Production response therefore becomes:

Incident
   ↓
Immediate existential risk?
   ├── YES → stabilize first
   │          ↓
   │       preserve whatever
   │       evidence remains
   │
   └── NO  → capture evidence
              ↓
           diagnose

This prevents evidence collection from delaying necessary containment.

3. Add Transaction-State Awareness

One important technical gap is distinguishing:

Statement failure
       vs
Transaction failure

Inside a transaction:

BEGIN;

ALTER TABLE ...;
-- ERROR

SELECT ...;

many errors leave the transaction in an aborted state until:

ROLLBACK;

or recovery through an appropriate savepoint strategy.

Troubleshooting must explicitly ask:

Did only the statement fail?

or

Is the surrounding transaction now aborted?

This is especially important for migration frameworks.

4. Add Autocommit Awareness

A failed migration behaves differently depending on whether commands were executed:

Single transaction
       vs
Autocommit
       vs
Multiple explicit transactions
       vs
Concurrent DDL outside transaction

Example:

CREATE TABLE      ✓ committed
ALTER TABLE       ✓ committed
CREATE INDEX
CONCURRENTLY      ✗
GRANT             not executed

can leave substantial production state behind.

The canonical troubleshooting process must identify transaction boundaries before attempting recovery.

5. Lock Diagnosis Needs Lock-Type Visibility

pg_blocking_pids() is excellent for identifying blockers, but advanced diagnosis should also inspect pg_locks.

Add:

SELECT
    l.pid,
    a.usename,
    a.application_name,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation,
    l.transactionid,
    l.virtualxid,
    a.wait_event_type,
    a.wait_event,
    a.query
FROM pg_locks l
LEFT JOIN pg_stat_activity a
       ON a.pid = l.pid
ORDER BY l.granted, l.pid;

This helps distinguish:

Relation lock
Transaction ID lock
Virtual transaction lock
Tuple lock
Object lock
6. Do Not Assume the Visible Blocker Is the Root Blocker

Production lock chains can look like:

Session A
   ↓ blocks
Session B
   ↓ blocks
DDL C
   ↓ causes
Application D/E/F/G to queue

Terminating B may not solve the incident because A is the root blocker.

Add explicit lock-chain analysis:

Waiting session
      ↓
Immediate blocker
      ↓
Blocker's blocker
      ↓
Root blocker

This is an important DBRE distinction.

7. Deadlock Section — Technically Confirmed

The draft correctly states that PostgreSQL detects deadlocks and aborts one participant. PostgreSQL explicitly documents this behavior and warns that applications should not rely on which transaction will be selected as the victim.

Add another important principle:

Deadlock retry
      ≠
Deadlock remediation

Applications may retry transactions after appropriate retryable failures, but recurring deadlocks indicate transaction-ordering or concurrency design problems.

8. Add deadlock_timeout / Lock Logging Awareness

For production diagnosis, include:

deadlock_timeout
log_lock_waits

as relevant PostgreSQL configuration controls.

The section should explain that these are diagnostic/operational controls and must not be changed casually across a production cluster simply to troubleshoot one event.

9. Strengthen CREATE INDEX CONCURRENTLY Failure Handling

The Draft is correct.

PostgreSQL 18 documents that concurrent index creation:

performs multiple phases;
waits for relevant transactions;
can fail from deadlock or uniqueness violations;
can leave an invalid index;
leaves that index consuming update overhead;
cannot run inside a transaction block.

Keep:

SELECT
    n.nspname,
    t.relname,
    i.relname,
    x.indisvalid,
    x.indisready,
    x.indislive
...

but add a critical warning.

10. Invalid Unique Indexes Have Special Behavior

This is important enough to call out explicitly.

During concurrent creation of a unique index, uniqueness enforcement can begin before the index is finally marked valid. If the later build phase fails, the invalid index can continue enforcing uniqueness.

Therefore:

INVALID
   ≠
operationally irrelevant

Never automatically drop an invalid unique index without understanding whether applications are currently relying on its uniqueness enforcement.

11. Add Failed REINDEX CONCURRENTLY

The Draft discusses failed concurrent creation but needs a dedicated concurrent-reindex scenario.

PostgreSQL may leave temporary invalid indexes with names such as:

index_ccnew
index_ccold
index_ccnew1
index_ccold2

after interrupted or failed concurrent reindex operations. Current PostgreSQL documentation describes these transient objects and their cleanup semantics.

Add:

REINDEX CONCURRENTLY failure
          ↓
Inspect original index
          ↓
Inspect *_ccnew / *_ccold
          ↓
Determine which build phase failed
          ↓
Follow documented cleanup
          ↓
Validate surviving index

Never blindly drop all _cc* objects.

12. Distinguish Regular and Concurrent REINDEX

Regular REINDEX can acquire ACCESS EXCLUSIVE, while REINDEX ... CONCURRENTLY is designed to reduce blocking and uses less restrictive locking, at the cost of additional work and operational complexity.

Troubleshooting should therefore ask:

Was this:

REINDEX
or
REINDEX CONCURRENTLY?

before reasoning about lock impact.

13. Add Index Corruption as a Separate Failure Class

Invalidity and corruption are not the same thing.

Invalid index
     ≠
Corrupt index

Add a separate scenario:

Wrong query results suspected
Index corruption suspected
Index structure inconsistent

For supported checks, introduce:

amcheck extension
pg_amcheck utility

as PostgreSQL-native integrity tooling.

Do not tell operators that REINDEX is automatically the first response before establishing what is actually corrupted.

14. Constraint Validation Section Needs Precision

The staged model is good:

ADD ... NOT VALID
        ↓
Correct historical data
        ↓
VALIDATE CONSTRAINT

Keep it.

But explicitly state:

NOT VALID availability depends on the constraint form; it is not a universal option for every PostgreSQL constraint.

PostgreSQL supports staged validation for applicable constraint types, and existing-index techniques can also reduce blocking for some unique/primary-key deployment patterns.

15. Add NOT NULL Troubleshooting

A missing scenario is:

ALTER COLUMN ... SET NOT NULL fails

Typical reason:

existing NULL values

Troubleshooting:

SELECT count(*)
FROM app.target_table
WHERE target_column IS NULL;

Then:

Determine why NULLs exist
       ↓
Correct/backfill safely
       ↓
Validate
       ↓
Retry constraint

Do not replace a legitimate NOT NULL requirement with a weaker schema simply because deployment failed.

16. Add Unique/Primary-Key Constraint Failure

Separate from unique-index creation.

Possible failures:

Duplicate existing values
Invalid supporting index
Incompatible index definition
NULL semantics mismatch

Troubleshooting must distinguish:

Business data violation
      vs
Incorrect proposed constraint
      vs
Migration implementation problem
17. Dependency Troubleshooting Should Use Catalogs

The Draft says to inventory dependencies. Good.

Add explicit tooling around:

pg_depend
pg_shdepend

plus supported PostgreSQL inspection facilities.

But add the rule:

Do not directly modify dependency catalogs.

Catalogs are diagnostic evidence, not repair tables.

18. Add View/Function Dependency Failures

Common production migration:

ALTER COLUMN TYPE
        ↓
ERROR because view/rule depends on column

or:

      ↓
dependent object exists

Troubleshooting should identify:

Trigger

before redesigning the migration.

19. Strengthen Accidental DROP Recovery

The Draft correctly suggests alternate-instance PITR.

This is a very strong production pattern:

Production DB
    continues
       │
       └──── PITR restore
                ↓
          isolated recovery DB
                ↓
          extract required state
                ↓
             validate
                ↓
       controlled reconciliation

Keep this prominently.

It often avoids unnecessarily rolling the entire production database backward for one accidentally removed object.

20. Add Schema Rename Failure Scenarios

Include:

ALTER TABLE ... RENAME
ALTER SCHEMA ... RENAME
ALTER COLUMN ... RENAME

Potential consumers:

Application SQL
Views
Functions
ETL
CDC

Monitoring
Scripts

PostgreSQL may preserve internal dependency relationships while external consumers still break.

This distinction is crucial:

Database dependency valid
          ≠
External consumer compatible
21. Add Object Type Mismatch

A surprisingly common automation failure:

Expected:
app.orders = TABLE

Actual:
app.orders = VIEW

or:

Expected:
schema object absent

Actual:
object exists under another relkind

Use catalog inspection before blindly retrying object creation.

22. Backfill Troubleshooting Needs MVCC Awareness

The Draft correctly discusses dead tuples.

Strengthen with:

Large UPDATE
     ↓
new row versions
     +
old row versions
     ↓
WAL
     ↓
vacuum debt
     ↓
table/index growth

Operators must not expect PostgreSQL to immediately shrink the physical table when rows are updated or deleted.

This ties 3.23 directly to 3.21.

23. Add Autovacuum Interaction

After a large migration, investigate:

n_dead_tup
last_autovacuum
last_autoanalyze
vacuum progress
long-running transactions

Do not diagnose post-backfill table growth solely as permanent bloat while cleanup is still pending.

24. Add Statistics Regression

A schema/data migration may succeed yet cause:

Bad execution plans
Latency spike
Sequential scans
Wrong join strategy

because statistics are stale or data distribution changed.

Troubleshooting flow:

Migration succeeds
       ↓
Application slows
       ↓
Check query plans
       ↓
Check statistics freshness
       ↓
ANALYZE if appropriate
       ↓
Re-test
25. Partition Failure Section — Strong, Add Default Partition

The Draft correctly covers partition-bound validation.

Also inspect the default partition.

When attaching a new partition, PostgreSQL may need to scan the default partition to verify that rows belonging to the new partition are not present there unless appropriate constraints allow the scan to be avoided.

This can transform an apparently metadata-oriented operation into a significant production event.

26. Add Partition Routing Failure Diagnostics

For:

ERROR:
no partition of relation ...
found for row

capture the actual partition key.

Then compare:

Incoming key
     vs
Existing bounds
     vs
Expected lifecycle calendar

Do not immediately create a catch-all partition without determining why partition provisioning failed.

28. Add Function/Procedure Privilege Failures

Permission troubleshooting should also include:

EXECUTE on function/procedure

Table permissions alone are not sufficient for many applications.

31. Sequence Troubleshooting Needs Drift Detection

Another common failure:

duplicate key violates primary key

after imports, manual inserts, or sequence manipulation.

Possible cause:

Sequence value
      <
Existing maximum identifier

Where sequence semantics apply, investigate the relationship between:

sequence state
table maximum
identity/default configuration

before using setval().

Never blindly set a production sequence to MAX(id) without understanding concurrent writes.

32. Logical Replication Section Needs Subscriber-Side Diagnosis

The Draft focuses primarily on publisher changes.

Add:

Publisher healthy
       ↓
Subscriber apply worker failing
       ↓
Subscription stopped/blocked

Inspect version-appropriate subscription statistics and logs.

Schema compatibility across publisher/subscriber must be part of the diagnosis.

33. Replication Slot Troubleshooting Needs Retention Risk

Keep the warning against dropping slots casually.

Strengthen:

Inactive slot
     ↓
retains WAL
     ↓
storage grows
     ↓
database availability risk

but:

DROP SLOT
     ↓
consumer may lose restart position
     ↓
resynchronization may be required

Therefore slot deletion is a data-pipeline recovery decision, not a disk-cleanup command.

34. Physical Replica and Logical Consumer Lag Must Be Separated

Do not treat all replication lag identically.

Physical replica lag
        vs
Logical replication lag
        vs
External CDC connector lag

have different:

Diagnostics
Recovery procedures
Failure semantics
RPO implications

The canonical section should maintain this distinction.

35. WAL Troubleshooting Must Explicitly Prohibit File Deletion

The Draft already warns against manually deleting WAL.

Upgrade this to a boxed production rule:

Never manually delete files from pg_wal as an ad-hoc response to storage pressure.

Instead diagnose:

Replication slots
Archive failures
Replica lag
Long-running backup
High write workload
Large migration

and use supported recovery mechanisms.

36. Add Temporary-File Exhaustion

Object administration can create large temporary workloads from:

Index builds

37. Add maintenance_work_mem Misconfiguration

Index builds and maintenance operations may be affected by maintenance memory configuration.

But troubleshooting must avoid:

Index slow
   ↓
Set maintenance_work_mem huge

PostgreSQL notes that increasing maintenance memory can improve index creation only while adequate physical memory remains; excessive allocation can cause swapping and worsen performance.

38. Add Cancellation vs Termination Semantics

The Draft correctly prefers:

pg_cancel_backend()

before:

pg_terminate_backend()

when cancellation is enough.

Make the distinction explicit:

pg_cancel_backend
      ↓
requests cancellation
of current query

pg_terminate_backend
      ↓
terminates session
      ↓
open transaction rolls back

Termination can therefore trigger substantial rollback work.

39. Add Rollback Progress Awareness

After terminating a large writer:

Session terminated
      ≠
System instantly recovered

Rollback/recovery effects may continue to consume:

CPU
I/O
Locks
WAL-related activity

depending on the operation and environment.

Do not declare the incident resolved immediately after terminating the PID.

41. Add Extension-Object Failure Scenario

Troubleshooting should distinguish:

Application object
       vs

3.23 — Database/Object Administration Troubleshooting and Failure Scenarios
Production Review

Review stage: Production Review
Previous gates: Draft ✅ · Technical Review ✅
Review objective: Validate that 3.23 can function as a real production DBRE/SRE incident runbook
Decision: APPROVED WITH PRODUCTION HARDENING

The Technical Review established PostgreSQL correctness. This Production Review focuses on what happens at 2:00 AM during an actual incident: containment, decision authority, evidence preservation, application impact, rollback, recovery, escalation, and proving that the system is truly healthy afterward.

1. Production Review Standard

A technically correct troubleshooting procedure is not automatically production-safe.

Every incident response must optimize for:

1. Data integrity
2. Service availability
3. Security
4. Blast-radius containment
5. Recoverability
6. Evidence preservation
7. Replication/CDC integrity
8. Application correctness
9. Root-cause elimination

The governing principle is:

Do not turn a database incident into a larger incident through an unbounded recovery action.

2. Establish Incident Severity First

Before changing production state, classify impact.

SEV-1 — Critical

Examples:

Data corruption suspected
Accidental destructive DDL
Major production outage
Storage exhaustion imminent
Database unavailable
Broad privilege/security exposure
Recovery/PITR required
SEV-2 — Major

Examples:

DDL blocking production traffic
Connection pool saturation
Major latency increase
Replica materially behind
CDC stopped
Large migration overloading production
SEV-3 — Limited

Examples:

Migration safely failed
Invalid noncritical index
Single-role privilege problem
Maintenance operation failure
Limited object drift

Severity determines escalation, communication, approval, and recovery authority.

3. Separate Containment, Mitigation, Recovery, and Remediation

These are different activities.

CONTAINMENT
     ↓
Stop blast radius from growing

MITIGATION
     ↓
Restore acceptable service

RECOVERY
     ↓
Restore correct system/data state

REMEDIATION
     ↓
Remove root cause

PREVENTION
     ↓
Reduce recurrence probability

Example:

DDL blocks application
        ↓
Cancel DDL
        │
        └── MITIGATION
                ↓
Application recovers
                ↓
Redesign migration
                │
                └── REMEDIATION
                        ↓
Add lock preflight + lock_timeout
                        │
                        └── PREVENTION

Do not close an incident after mitigation alone.

4. Define Incident Command

For SEV-1/SEV-2 database incidents, establish explicit ownership.

Incident Commander
        │
        ├── DBRE / DBA
        ├── Application owner
        ├── Platform/SRE
        ├── Replication/data-pipeline owner
        └── Cloud/provider support if required

One person should coordinate production-changing decisions.

Avoid:

DBA kills session
Application restarts pods
SRE restarts database
Pipeline team resets CDC

simultaneously without coordination.

That can destroy the evidence needed to understand the original failure.

pg_stat_replication
pg_replication_slots
pg_stat_user_tables
pg_stat_user_indexes

pg_trigger
pg_policies

Also capture:

Connection-pool metrics
CPU
Memory
I/O
Storage
WAL behavior
Replica lag
CDC lag
Deployment/change ID
Incident timeline

Production rule:

Capture enough evidence to explain the incident later, but never delay critical containment merely to collect perfect evidence.

6. Establish the Change Correlation

Check:

Manual DDL

Correlation does not prove causation, but it gives the incident team a strong starting hypothesis.

7. Production Lock Incident Runbook

For blocked production DDL:

DDL WAITING
    ↓
Identify waiting PID
    ↓
Identify immediate blocker
    ↓
Trace blocker chain
    ↓
Find root blocker
    ↓
Identify owning application
    ↓
Assess business transaction
    ↓
Choose action

Possible actions:

Wait
Cancel waiting DDL
Cancel blocker query
Terminate blocker session
Stop deployment
Reduce application traffic
Reschedule change
Preferred Production Order

Where feasible:

1. Cancel unnecessary waiting DDL
2. Observe application recovery
3. Cancel blocker query if appropriate
4. Terminate blocker only with impact understood

Do not start with:

3.23.11 DDL Blocked by Locks

Identify waiting sessions:

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blocking_pids,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Then inspect locks:

SELECT
    l.pid,
    a.usename,
    a.application_name,
    l.locktype,
    l.mode,
    l.granted,
    l.relation::regclass AS relation,
    l.transactionid,
    l.virtualxid,
    a.wait_event_type,
    a.wait_event,
    a.query
FROM pg_locks l
LEFT JOIN pg_stat_activity a
       ON a.pid = l.pid
ORDER BY l.granted, l.pid;

    usename,
    application_name,
    xact_start,
    now() - xact_start AS transaction_age,

WHERE state = 'idle in transaction'

3.23.16 Prepared Transactions

FROM pg_prepared_xacts;

3.23.17 Deadlocks

Topology:

Transaction A
holds X
waits Y
    ↑
    │
    ↓
Transaction B
holds Y
waits X

PostgreSQL detects deadlocks and aborts one participating transaction.

The durable remediation is generally:

Consistent resource ordering
+
Short transactions
+
Bounded retry where appropriate

Remember:

Deadlock retry is mitigation; transaction redesign is remediation.

3.23.23 Failed CREATE INDEX CONCURRENTLY

A failed concurrent index build can leave an invalid index. PostgreSQL documents failures such as uniqueness violations and deadlocks as cases that can leave such state.

Inspect:

SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    i.relname AS index_name,
    x.indisvalid,
    x.indisready,
    x.indislive
FROM pg_index x
JOIN pg_class i
  ON i.oid = x.indexrelid
JOIN pg_class t
  ON t.oid = x.indrelid
JOIN pg_namespace n
  ON n.oid = t.relnamespace
WHERE NOT x.indisvalid
   OR NOT x.indisready
   OR NOT x.indislive;

3.23.83 Final Production Standard

The governing standard for PostgreSQL database/object troubleshooting is:

A production database incident is not resolved when the error disappears. It is resolved when service is restored, database state is correct, integrity and security are preserved, applications are healthy, replication and CDC are healthy or converging safely, recovery remains possible, the root cause is understood, and preventive controls have been established.

The troubleshooting mindset therefore moves from:

ERROR
  ↓
GUESS
  ↓
CHANGE

to:

DETECT
  ↓
EVIDENCE
  ↓
DIAGNOSE
  ↓
CONTAIN
  ↓
MITIGATE
  ↓
RECOVER
  ↓
VALIDATE
  ↓
OBSERVE
  ↓
REMEDIATE
  ↓
PREVENT

That is the production DBRE standard.
