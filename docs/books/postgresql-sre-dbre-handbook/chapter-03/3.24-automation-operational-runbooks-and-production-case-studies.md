PostgreSQL's current documentation supports the core operating model used here: repetitive maintenance can and should be automated, but administrators remain responsible for ensuring that automation actually runs successfully.

## 3.24.1 Purpose and Operating Principle

Production PostgreSQL administration must evolve from individual commands into a controlled operational system.

INTENT
  ↓
DESIRED STATE
  ↓
DISCOVERY
  ↓
PLAN
  ↓
PREFLIGHT
  ↓
RISK GATE
  ↓
EXECUTE
  ↓
OBSERVE
  ↓
VERIFY
  ↓
RECONCILE
  ↓
AUDIT

The objective is not maximum automation.

The objective is:

Automate repeatable detection and bounded operations aggressively, while applying progressively stronger controls as blast radius, irreversibility, availability risk, security impact, or recovery complexity increases.

## 3.24.2 Production Automation Risk Model

Every administrative workflow SHALL be classified before execution.

Class	Type	Examples	Default
A	Observation	Inventory, health checks, drift detection	Automatic
B	Bounded maintenance	ANALYZE, approved VACUUM, future partition creation	Guarded automation
C	High-impact change	ALTER TABLE, index operations, backfills	Change gate
D	Destructive/recovery	DROP, CASCADE, PITR, slot deletion	Explicit authorization

The governing rule is:

AUTOMATE DETECTION
      ↓
AUTOMATE DIAGNOSIS
      ↓
AUTOMATE SAFE PREPARATION
      ↓
GUARD STATE CHANGES
      ↓
HUMAN-GATE DESTRUCTIVE RECOVERY
## 3.24.3 Desired-State Administration

Production automation SHOULD operate against a declared desired state stored in version control or an equivalent authoritative system.

           GIT / DESIRED STATE
                    │
                    ▼
              NORMALIZATION
                    │
                    ▼
ACTUAL DB ───────► DIFF
                    │
                    ▼
              DRIFT CLASSIFY
                    │
                    ▼
                   PLAN

Drift includes:

missing objects;
unexpected objects;
incorrect definitions;
ownership drift;
privilege drift;
default-privilege drift;
missing partitions;
invalid indexes;
unexpected constraints;
unmanaged production changes.

Raw textual DDL comparison should not be the only mechanism. PostgreSQL metadata and definition functions should be used where appropriate to produce semantically meaningful comparisons.

## 3.24.4 Idempotency

State-changing automation SHOULD be idempotent wherever practical.

The intended model is:

CURRENT STATE
      +
DESIRED STATE
      ↓
REQUIRED DELTA ONLY

not:

Blindly execute the same DDL again

An automation job must determine whether its requested state already exists before changing production.

## 3.24.6 Preconditions and Postconditions

A production operation is modeled as:

PRECONDITION
      ↓
ACTION
      ↓
POSTCONDITION

Example:

Storage sufficient
No unacceptable blocker

## 3.24.7 Environment Guard

Before every state-changing operation, prove the target identity.

SELECT
    current_database(),
    current_user,
    session_user,
    pg_is_in_recovery();

Also establish, using platform/environment metadata:

Environment
Cluster
Account / subscription / project
Region
Database
Writer endpoint
Change ID

Required behavior:

IDENTITY VERIFIED
      ↓
CONTINUE

IDENTITY AMBIGUOUS
      ↓
FAIL CLOSED

Automation must never guess that it has reached production, staging, or the correct writer.

## 3.24.8 Automation Identity

Every automated connection SHOULD be attributable.

Record:

Change ID

Generic production identities such as admin, postgres, or script reduce auditability.

## 3.24.9 Role Separation

Production administration should separate responsibilities:

              OWNER ROLE
                  │
          owns database objects

             DEPLOY ROLE
                  │
        performs approved DDL

            RUNTIME ROLE
                  │
       application operations

          MONITORING ROLE
                  │
          read-only telemetry

           RECOVERY ROLE
                  │
       emergency/recovery work

PostgreSQL ownership is itself powerful: object owners inherently control alteration/destruction of their objects, while object privileges are separately granted to other roles.

Application runtime roles should not normally own their database objects.

## 3.24.10 Secrets and Credential Safety

Never place database credentials in:

Git
shell history
command-line parameters
automation logs
incident transcripts
runbook screenshots

Use the organization's approved secrets mechanism.

Highly privileged recovery credentials should be isolated from normal maintenance automation.

## 3.24.11 Concurrency Guard

Two automation instances must not independently modify the same administrative target.

JOB A ─┐
       ├── app.orders ──► CONFLICT
JOB B ─┘

Possible controls include:

Deployment serialization
Job ownership records
Distributed orchestration
PostgreSQL advisory locks

The chosen mechanism must have well-defined ownership, timeout, failure, and recovery semantics.

## 3.24.12 Blast-Radius Control

State-changing jobs must have explicit scope.

Prefer:

   ↓

## 3.24.15 Privilege Drift

Validate effective access across applicable:

DATABASE
SCHEMA
TABLE
SEQUENCE
FUNCTION
PROCEDURE
TYPE

PostgreSQL exposes different privileges for different object classes; for example, tables, schemas, sequences, functions, databases, and types do not share identical privilege sets.

Drift detection must identify both:

MISSING PRIVILEGE

and:

EXCESSIVE PRIVILEGE

Least privilege requires detecting both directions.

## 3.24.16 Runtime Authorization Validation

Catalog inspection alone is not enough.

Effective access can depend on:

Direct grants
Role membership
INHERIT
SET ROLE
Ownership
Schema access
RLS policies

The strongest validation is a representative transaction executed through the actual application identity.

Do not validate application authorization only as a superuser.

## 3.24.17 Default Privilege Automation

Default privileges require special care.

They affect future objects, not already-existing objects, and at creation time PostgreSQL uses the default privileges of the current creating role rather than automatically inheriting the defaults configured for roles of which that creator is merely a member.

Therefore:

DEFAULT PRIVILEGES FOR app_owner
               ≠
OBJECT CREATED BY ci_role

unless the deployment role model explicitly produces that state.

Automation must validate:

Who creates the object?
Who owns it afterward?
Which defaults apply?
What does runtime receive?
## 3.24.18 Invalid Index Detection

Monitor:

SELECT
    n.nspname AS schema_name,
    t.relname AS table_name,
    i.relname AS index_name,
    x.indisvalid,
    x.indisready,
    x.indislive
FROM pg_index x
JOIN pg_class i ON i.oid = x.indexrelid
JOIN pg_class t ON t.oid = x.indrelid
JOIN pg_namespace n ON n.oid = t.relnamespace
WHERE NOT x.indisvalid
   OR NOT x.indisready
   OR NOT x.indislive;

But never implement:

INVALID INDEX
      ↓
AUTOMATIC DROP

Instead:

DETECT
  ↓
CLASSIFY
  ↓
DETERMINE ORIGIN
  ↓
ASSESS DEPENDENCIES
  ↓
SELECT RECOVERY

Index validity, usage, bloat, redundancy, and corruption are different concepts and must not be collapsed into one simplistic "health" value.

## 3.24.23 Independent Partition Coverage Monitoring

Provisioning and monitoring should not share one failure domain.

PARTITION CREATOR
       │
       ▼
Database

INDEPENDENT COVERAGE CHECK
       │
       ▼
Alerting

This detects:

expired credentials
disabled job
partial execution
silent automation failure

Create partitions early enough to allow failure, escalation, repair, and validation before the boundary is reached.

## 3.24.24 Partition Retention

Retention is higher risk than provisioning.

Use:

POLICY
  ↓

  ↓
DETACH
  ↓

  ↓
VERIFY
  ↓

## 3.24.25 Bloat and Dead-Tuple Monitoring

Use statistics as operational signals.

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

Do not equate:

n_dead_tup

directly with an exact physical bloat percentage.

Use trends and multiple signals.

## 3.24.26 Autovacuum Automation

Autovacuum should normally be monitored and tuned, not replaced by a simplistic nightly VACUUM cron job.

Routine vacuuming supports multiple responsibilities, including space reuse, planner/statistical health, visibility-map maintenance, and protection against transaction-ID and multixact-ID wraparound.

Monitor:

Dead-tuple growth
Autovacuum activity
Analyze freshness
Long transactions
Transaction-ID age
Multixact age
Workload changes
## 3.24.27 VACUUM FULL

VACUUM FULL is exceptional maintenance.

Unlike ordinary VACUUM, it rewrites the relation and requires an ACCESS EXCLUSIVE lock. PostgreSQL recommends generally favoring standard VACUUM over VACUUM FULL for routine operation.

Required preflight:

Lock/outage impact
Disk headroom
Runtime
WAL impact
Replica impact
Application impact
Recovery path

Never automate:

bloat threshold exceeded
        ↓
VACUUM FULL

without a strong change gate.

## 3.24.28 Maintenance Progress Monitoring

Use PostgreSQL progress views where supported.

Examples include:

SELECT * FROM pg_stat_progress_vacuum;

and progress reporting for index creation/reindexing and other supported maintenance operations. PostgreSQL reports ordinary VACUUM through pg_stat_progress_vacuum, while VACUUM FULL is represented through cluster-style progress reporting because it rewrites the relation.

## 3.24.30 Long Transactions and Lock Monitoring

Automate detection of:

Long transactions
Idle-in-transaction sessions
Blocking chains
DDL waits
Prepared transactions
Old snapshots

Example:

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blockers,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

Do not automatically terminate sessions merely because they exceed a universal duration threshold.

## 3.24.34 CREATE INDEX CONCURRENTLY Runbook

Use when its trade-offs are appropriate.

CREATE INDEX CONCURRENTLY ...

PostgreSQL permits normal writes during a concurrent build, but the operation performs additional work, involves multiple waits/scans, and can leave an invalid index after failure. Only one concurrent index build can operate on a table at a time, and CREATE INDEX CONCURRENTLY cannot execute inside a transaction block.

Monitor:

SELECT *
FROM pg_stat_progress_create_index;

and simultaneously monitor:

CPU
I/O
WAL
Disk
Replica lag
P99
Connection pool

Failure does not mean "automatically drop the index."

Inspect its exact state first.

## 3.24.37 Adaptive Throttling

## 3.24.49 Production Case Study — Failed Concurrent Unique Index

A concurrent unique index build encounters duplicate data.

Potential outcome:

BUILD FAILURE
     ↓
INVALID INDEX REMAINS

Do not blindly drop it.

Determine:

Catalog state
Uniqueness behavior
Dependencies
Failure cause
Disk impact

PostgreSQL documents that a failed concurrent unique build can leave an invalid index and that uniqueness enforcement can already have affected concurrent operations before final validity is reached.

Repair the data through an approved business/data process, then execute the appropriate cleanup/retry strategy.

## 3.24.64 Production Alert Philosophy

Avoid alerting only on isolated numbers.

Prefer:

SIGNAL
   +
TREND
   +
CONTEXT
   +
RISK

Example:

Dead tuples increasing
       +
Vacuum ineffective
       +
Long transaction exists
       ↓
ACTIONABLE RISK

Another:

Replication slot retaining WAL
       +
Storage runway shrinking
       ↓
ACTIONABLE RISK

## 3.24.66 Canonical Golden Rules
Automate detection more aggressively than destructive repair.
Prove the target environment before changing it.
Prove writer identity before executing write-side administration.
Use desired-state reconciliation instead of blind command execution.
Make automation idempotent wherever practical.
Provide dry-run/plan mode for significant changes.
Define preconditions and postconditions.
Limit blast radius explicitly.
Serialize conflicting administrative operations.
Separate owner, deployment, runtime, monitoring, and recovery responsibilities.
Never expose credentials through automation artifacts.
Treat ownership as production state.
Detect both missing and excessive privileges.
Validate access through the actual runtime identity.
Remember that default privileges depend on the object-creating role.
Never automatically drop an invalid index merely because it is invalid.
Never automatically delete business data to satisfy a constraint.
Sequence gaps are not corruption.
Monitor sequence exhaustion proactively.
Provision partitions ahead of need.
Monitor partition coverage independently from partition creation.
Human-gate destructive retention.
Treat bloat statistics as signals, not exact physical truth.
Monitor and tune autovacuum rather than casually replacing it.
Monitor transaction-ID and multixact aging.
Treat VACUUM FULL as exceptional maintenance.
Put safety gates around REINDEX.
Understand DDL lock behavior before execution.
Use lock_timeout and statement_timeout deliberately rather than interchangeably.
Remember that CREATE INDEX CONCURRENTLY has important transaction, failure, and concurrency semantics.
Make backfills bounded, checkpointed, restartable, and observable.
Use adaptive throttling when production load determines safe throughput.
Build pause/resume/abort controls into long-running automation.
Define execution budgets before starting.
Include application SLOs in database change decisions.
Monitor connection pools and retry storms.
Include physical replication, logical replication, CDC, and WAL/archive health in change validation.
Never automatically drop replication slots because storage is high.
Bound and redact automated evidence collection.
Validate rollback as carefully as rollout.
Prefer the smallest safe recovery scope.
Test restores—not merely backups.
Reconcile emergency production changes back into source control.
Monitor the automation system itself.
Use dead-man monitoring for critical scheduled jobs.
Record an auditable before/change/after trail.
Treat safe aborts as guardrail successes when they protect production.
Convert recurring incidents into monitoring, controls, or automation.
Require stronger authorization as irreversibility increases.
Automation succeeds only when the resulting production state is correct, healthy, secure, observable, and recoverable.
