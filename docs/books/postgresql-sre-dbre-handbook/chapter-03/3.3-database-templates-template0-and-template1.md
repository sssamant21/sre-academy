## 3.3.1 Purpose

PostgreSQL database templates define the baseline from which new databases are created. `CREATE DATABASE` normally copies `template1`, while `template0` preserves the pristine PostgreSQL baseline. For SREs and DBREs, templates are provisioning infrastructure, not casual administrative databases.

## 3.3.2 How PostgreSQL Creates a Database

PostgreSQL creates a database by copying a source database. By default, that source is `template1`.

```sql
CREATE DATABASE application_db;
```

Objects in the source database can be copied into the new database, including schemas, functions, types, extensions, object ownership, and object ACLs. Database-level configuration parameters and database-level `GRANT` permissions are not copied from the template database, so post-creation validation remains mandatory.

## 3.3.3 `template1`

`template1` is PostgreSQL's normal default database template.

```sql
CREATE DATABASE application_db;

CREATE DATABASE application_db
TEMPLATE template1;
```

Site-local additions to `template1` can standardize future databases, but every addition expands the blast radius for future provisioning.

## 3.3.4 `template0`

`template0` is the pristine standard template. It is not an empty database; it is the clean PostgreSQL baseline created during cluster initialization.

```sql
CREATE DATABASE application_db
WITH
    TEMPLATE template0
    ENCODING 'UTF8';
```

`template0` should not be modified during normal administration.

## 3.3.5 Why PostgreSQL Needs Two Standard Templates

`template1` provides the normal site baseline. `template0` preserves the original clean baseline. This separation allows site defaults while retaining a known-good source for clean restores and specialized locale or encoding creation.

## 3.3.6 Comparing `template0` and `template1`

| Characteristic | `template0` | `template1` |
| --- | --- | --- |
| Primary purpose | Pristine baseline | Default creation template |
| Used by normal `CREATE DATABASE` | No | Yes |
| Site customization | Do not modify | Supported when governed |
| Normal connections | Disabled | Allowed |
| Marked as template | Yes | Yes |
| Alternate locale/encoding use | Important | More constrained |
| Operational treatment | Hard protected | Governed infrastructure |

## 3.3.7 The `postgres` Database

`initdb` creates `template0`, `template1`, and `postgres`. The `postgres` database is intended as a normal default connection database for users, administrative utilities, and tools. Administrators should connect to `postgres` or another administrative database for operations that cannot be performed while connected to the target database.

## 3.3.8 Inspecting Template Databases

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner,
    datistemplate,
    datallowconn,
    encoding,
    datcollate,
    datctype
FROM pg_database
WHERE datname IN ('template0', 'template1')
ORDER BY datname;
```

Expected baseline: `template0` and `template1` are marked as templates; `template0` normally disallows connections.

## 3.3.9 `datistemplate`

`pg_database.datistemplate` indicates whether a database is intended as a template for `CREATE DATABASE`.

```sql
ALTER DATABASE organization_template
IS_TEMPLATE true;

ALTER DATABASE organization_template
IS_TEMPLATE false;
```

If set, a database can be cloned by roles with `CREATEDB`. If not set, cloning is limited to superusers and the database owner.

## 3.3.10 `datallowconn`

`pg_database.datallowconn` controls whether new connections are allowed.

```sql
SELECT
    datname,
    datallowconn
FROM pg_database
WHERE datname IN ('template0', 'template1');

ALTER DATABASE org_template_v1
ALLOW_CONNECTIONS false;
```

Setting `ALLOW_CONNECTIONS false` prevents new connections but does not terminate existing sessions.

## 3.3.11 Why `template0` Must Remain Pristine

If `template0` is modified, the clean baseline is lost and specialized database creation, restores, and operational assumptions can be affected. Automation should hard-deny routine modification of `template0` except under a reviewed recovery procedure.

## 3.3.12 Locale and Encoding

When copying `template1`, encoding and locale settings normally must match the template. Use `template0` when a different compatible locale or encoding is required.

```sql
CREATE DATABASE international_db
WITH
    TEMPLATE template0
    ENCODING 'UTF8';
```

## 3.3.13 `template0` and Logical Restore

`template0` is useful for creating clean targets for logical restore because it avoids site-local objects that may have been added to `template1`.

```sql
CREATE DATABASE restore_target
TEMPLATE template0;
```

## 3.3.14 Source Database Concurrency

When PostgreSQL copies a source database, no other sessions can be connected to that source at the start of the operation. During the copy, new source connections are prevented. This matters especially for custom templates.

## 3.3.15 Do Not Use Templates as Online Database Copying

Although this is valid syntax, it is not a general-purpose online database copy mechanism:

```sql
CREATE DATABASE new_db
TEMPLATE source_db;
```

For production cloning, refresh, migration, and disaster recovery, choose backup/restore, physical recovery, logical replication, platform snapshots, managed-service clone mechanisms, or migration tooling.

## 3.3.16 Controlled Customization of `template1`

Before adding anything to `template1`, ask whether every future database should inherit it. If the answer is no, the object probably belongs in provisioning automation, migrations, or a custom template instead.

## 3.3.17 Keep `template1` Minimal

A minimal `template1` reduces upgrade coupling, extension dependencies, security blast radius, provisioning surprises, and environment drift. Complex baselines should normally be delivered through version-controlled automation or dedicated custom templates.

## 3.3.18 Template Blast Radius

A database-local mistake affects one database. A template mistake can affect every database created afterward, and the impact may be discovered days or weeks later. Template changes require infrastructure-level review.

## 3.3.19 Database-Level Privileges Are a Special Case

Do not assume template security equals complete new database security. Explicitly validate database `CONNECT`, `CREATE`, and `TEMPORARY` privileges, schemas, object ownership, object ACLs, default privileges, and runtime roles after provisioning.

## 3.3.20 Extension Management

Extensions in a template become dependencies for future databases. Validate that each extension is required broadly, supported on the target PostgreSQL version, available in every environment, version-aligned, upgrade-tested, and security-reviewed.

## 3.3.21 Custom Template Databases

Organizations may create dedicated templates.

```sql
CREATE DATABASE org_template_v1
TEMPLATE template0;

ALTER DATABASE org_template_v1
IS_TEMPLATE true;
```

A custom template should be treated as production provisioning infrastructure.

## 3.3.22 Protecting Custom Templates

A strong lifecycle is: build template, validate contents, create a validation database, validate the produced database, resolve existing sessions, disable connections, mark as template, and release for provisioning use.

## 3.3.23 Versioned Custom Templates

Prefer versioned names such as `org_template_v1`, `org_template_v2`, and `org_template_v3` instead of repeatedly mutating a single template name. Versioning improves reproducibility, auditability, incident analysis, rollback analysis, and provisioning consistency.

## 3.3.24 Released Template Versions Should Be Immutable

Once a template version is released as an approved baseline, avoid silently changing it. Create a new version for a new baseline so databases created from the same version name actually share the same provenance.

## 3.3.25 Template Provenance

Provisioning systems should record which baseline created each database: database name, template, template version, PostgreSQL version, creation timestamp, provisioning pipeline version, Git commit, extension baseline, security baseline, and change/request ID.

## 3.3.26 Template Inventory

For every governed template, record owner, PostgreSQL version, encoding, locale, collation, `datistemplate`, `datallowconn`, extensions, schemas, functions, types, owners, ACLs, default privileges, creation date, last change, Git commit, pipeline version, and validation status.

## 3.3.27 Template Fingerprinting

Mature environments should build a normalized fingerprint from extensions, schemas, functions, types, owners, ACLs, and default privileges. Fingerprints make drift detection objective.

## 3.3.28 Drift Detection

Template drift occurs when live database state differs from the approved baseline. Detect drift through scheduled inventory, fingerprint comparison, extension version checks, object ownership checks, and change-record reconciliation.

## 3.3.29 Template Security Model

Template security should prevent accidental runtime use, unauthorized DDL, unwanted extension changes, owner drift, ACL drift, and unreviewed changes to `datistemplate` or `datallowconn`.

## 3.3.30 Template as Code

Treat template definitions as code. The source of truth should live in version control, and the database template should be a reproducible artifact built and validated from that source.

## 3.3.31 Template Change Audit

Every production template change should capture who changed it, what changed, when, why, the target template, old baseline, new baseline, change ticket, Git commit, pipeline version, validation database, validation result, and rollback plan.

## 3.3.32 Template Change Workflow

Recommended workflow: change request, eligibility test, blast-radius assessment, security review, dependency review, upgrade compatibility review, non-production build, validation database, produced-baseline validation, peer review, approval, production build, fingerprint, and release.

## 3.3.33 Production Template Change Runbook

### Step 1 — Confirm cluster

```sql
SELECT
    current_database(),
    current_user,
    session_user,
    inet_server_addr(),
    inet_server_port();
```

### Step 2 — Inspect template metadata

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS owner,
    datistemplate,
    datallowconn,
    encoding,
    datcollate,
    datctype
FROM pg_database
WHERE datname = 'template1';
```

### Step 3 — Inventory current baseline

Capture extensions, schemas, functions, types, ownership, object ACLs, and default privileges.

### Step 4 — Apply eligibility test

Ask whether every future database created from this template should inherit the change.

### Step 5 — Assess blast radius

Determine who creates databases from the template, how often, which environments use it, and what happens if the change is wrong.

### Step 6 — Test in non-production

Build the proposed template state outside production first.

### Step 7 — Create validation database

```sql
CREATE DATABASE template_validation_db
TEMPLATE test_template;
```

### Step 8 — Validate

Check expected objects, extensions, versions, ownership, ACLs, locale, encoding, absence of unexpected objects, and absence of application data.

### Step 9 — Peer review

Have another qualified engineer validate critical changes.

### Step 10 — Apply approved production change

Use controlled automation where possible.

### Step 11 — Create production validation database

```sql
CREATE DATABASE template_validation_db
TEMPLATE template1;
```

### Step 12 — Compare against baseline

Validate normalized inventory and fingerprint.

### Step 13 — Remove validation database

Follow the destructive-operation procedures from Section 3.2.

### Step 14 — Record change

Capture template version, fingerprint, Git commit, operator, timestamp, change ticket, and validation result.

## 3.3.34 PostgreSQL Major-Version Upgrades

Templates are part of the major-upgrade validation surface. Review extensions, functions, types, collations, privileges, template flags, and baseline intent during every major-version lifecycle.

## 3.3.35 Managed PostgreSQL Considerations

Managed services may restrict superuser capabilities, access to system databases, template modification, extensions, ownership, catalog administration, and provisioning mechanisms. Validate exact behavior against official vendor documentation before applying self-managed runbooks.

## 3.3.36 Failure Scenario — Accidental Object in `template1`

An administrator connects to `template1` and creates `test_schema`. Later databases inherit it. Lesson: template failures can have delayed and expanding blast radius.

## 3.3.37 Failure Scenario — Privilege Assumption

An administrator changes database-level privileges on `template1` and assumes new databases inherit them. PostgreSQL does not copy database-level `GRANT` permissions as template contents. Always validate database-level security during provisioning.

## 3.3.38 Failure Scenario — Extension Version Drift

If `org_template_v2` contains extension version 1.5 in development but 1.3 in production, migrations can fail after provisioning. Mitigate with template versioning, fingerprinting, extension inventory, and environment drift detection.

## 3.3.39 Failure Scenario — Active Template Session

If an unexpected session is connected to a custom template, database creation from that template can fail.

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    query
FROM pg_stat_activity
WHERE datname = 'org_template_v2';
```

Investigate before terminating sessions; unexpected template traffic may reveal application, monitoring, administrative, or automation misuse.

## 3.3.40 Failure Scenario — Polluted `template1`

If unauthorized state is added to `template1`, the incident scope includes the contamination window and every database created afterward. Freeze provisioning, capture template state, determine the window, identify affected databases, repair the template, validate, remediate affected databases, and resume provisioning only after review.

## 3.3.41 Recovery of a Polluted `template1`

A polluted `template1` can be rebuilt from `template0` under a controlled recovery procedure, but this is high risk. Validate backups, freeze provisioning, capture inventory, identify contamination, repair or recreate the template, restore the approved baseline, validate, remediate affected databases, and resume provisioning.

## 3.3.42 Template Incident Runbook

Freeze provisioning, capture template state, establish timeline, identify affected databases, assess security impact, validate recovery options, repair or replace the template from the approved baseline, create a validation database, compare fingerprints, remediate already-created databases, resume provisioning, and complete a post-incident review.

## 3.3.43 Template Automation Guardrails

Automation should classify targets as normal database, `template1`, custom template, or `template0`. Normal databases follow normal controls; `template1` and custom templates require template workflows; `template0` should be denied for routine changes.

## 3.3.44 Production Monitoring

Monitor template metadata, ownership, `datistemplate`, `datallowconn`, unexpected sessions, extension inventory, schemas, functions, types, object ownership, ACL drift, default privilege drift, encoding, locale, collation, fingerprints, and provisioning failures.

## 3.3.45 Production Case Study — Versioned Enterprise Template

An organization standardizes hundreds of databases with approved extensions, operations schema, utility functions, security baseline, and monitoring objects. The DBRE team moves from ad hoc provisioning to Git baselines, versioned custom templates, validation databases, fingerprints, immutable releases, and provenance records. Existing databases are upgraded separately rather than silently changing the meaning of an old template version.

## 3.3.46 SRE/DBRE Production Principles

1. Hard-protect `template0`.
2. Keep `template1` minimal.
3. Ask whether every future database should inherit the change.
4. Do not assume all privileges propagate.
5. Keep templates free of runtime data.
6. Protect custom templates from connections.
7. Version complex baselines.
8. Freeze released versions.
9. Record provenance.
10. Fingerprint templates.
11. Detect drift continuously.
12. Validate by provisioning.
13. Review templates during upgrades.
14. Freeze provisioning during template incidents.
15. Remediate downstream databases.

## 3.3.47 Template Reliability Architecture

```text
template0 (hard protected)
        v
version-controlled baseline
        v
custom template vN
        v
validation database
        v
fingerprint + approval
        v
immutable release
        v
application databases
        v

```

## 3.3.48 Section Summary

PostgreSQL's template architecture starts with `template0` as the pristine baseline and `template1` as the default site template. Normal databases are created from `template1`; clean specialized databases and logical restore targets often use `template0`; enterprise standardization should use version-controlled definitions, custom templates, validation databases, fingerprints, approvals, immutable releases, provenance, and drift detection.

The core operational rules are: protect `template0`, keep `template1` minimal and governed, treat templates as provisioning infrastructure, validate templates by creating databases from them, record which template produced each database, and freeze provisioning during template incidents.
