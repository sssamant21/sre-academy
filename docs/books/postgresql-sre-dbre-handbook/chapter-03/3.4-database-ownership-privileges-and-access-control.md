## 3.4.1 Purpose

PostgreSQL schemas provide database-local namespaces for objects such as tables, views, materialized views, sequences, functions, procedures, types, domains, and operators. They organize objects, separate names, define ownership boundaries, and shape privilege boundaries. For SRE/DBRE teams, schemas are part of the security architecture.

## 3.4.2 Schemas Are Database-Local Namespaces

Schemas exist inside one database. The same schema name in two databases represents two independent namespaces. `database_a.application.orders` and `database_b.application.orders` are different objects because a PostgreSQL connection accesses one database at a time.

## 3.4.3 Creating a Schema

```sql
CREATE SCHEMA application;

CREATE SCHEMA application
AUTHORIZATION application_owner;

SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
WHERE n.nspname = 'application';
```

Ownership is a security decision because the owner has fundamental control over the namespace.

## 3.4.4 Reserved Schema Names

Schema names beginning with `pg_` are reserved for PostgreSQL system purposes. Avoid organizational names such as `pg_application`, `pg_company`, `pg_reporting`, or `pg_operations`.

## 3.4.5 Schema Ownership

Every schema has an owner.

```sql
SELECT
    nspname,
    pg_get_userbyid(nspowner) AS owner
FROM pg_namespace
ORDER BY nspname;
```

A strong model separates ownership, migration, and runtime identities. The application runtime identity should normally not own the application schema.

## 3.4.6 Recommended Production Role Model

Use distinct roles where practical: an ownership role such as `application_owner`, a controlled deployment role such as `migration_role`, and a runtime role such as `application_runtime`. Runtime roles normally need `CONNECT`, schema `USAGE`, required DML, sequence privileges, and function `EXECUTE`; they should not normally have schema `CREATE` or object ownership.

## 3.4.7 Schema Privileges

The two primary schema privileges are `USAGE` and `CREATE`.

```sql
GRANT USAGE
ON SCHEMA application
TO application_runtime;

GRANT CREATE
ON SCHEMA application
TO migration_role;
```

`USAGE` permits access to objects by name, subject to object privileges. `CREATE` permits new objects in the schema and is much more powerful.

## 3.4.8 USAGE Is Not Complete Object Authorization

Schema `USAGE` does not grant table, sequence, function, or other object privileges.

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA application
TO application_runtime;
```

Effective authorization can also depend on role membership, column privileges, row-level security, function `EXECUTE`, sequence privileges, and ownership.

## 3.4.9 CREATE Establishes a Trust Relationship

A role with `CREATE` on a schema can introduce names into that namespace. If a privileged session searches that schema, it is trusting users who can create there. A writable schema should not appear casually in privileged `search_path` values.

## 3.4.10 The public Schema

Every database normally contains `public`. Historically, many applications placed all objects there, but `public` should not automatically be treated as the application schema. Production databases often use dedicated schemas such as `application`, `reporting`, `operations`, and `audit`.

## 3.4.11 PostgreSQL 15+ and public

PostgreSQL 15 introduced safer defaults for newly initialized databases, including `pg_database_owner` ownership for `public`. Upgraded or restored databases may retain older characteristics, so inspect actual state rather than inferring from server version.

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
WHERE n.nspname = 'public';
```

## 3.4.12 Hardening public

Where arbitrary users should not create objects in `public`, revoke `CREATE` after dependency review.

```sql
REVOKE CREATE
ON SCHEMA public
FROM PUBLIC;
```

Review existing objects, application dependencies, deployment assumptions, role dependencies, extension behavior, and legacy workflows before changing production estates.

## 3.4.13 pg_database_owner

`pg_database_owner` represents the owner of the current database.

```sql
SELECT
    datname,
    pg_get_userbyid(datdba) AS database_owner
FROM pg_database
WHERE datname = current_database();

SELECT
    nspname,
    pg_get_userbyid(nspowner) AS schema_owner
FROM pg_namespace
WHERE nspname = 'public';
```

## 3.4.14 Schema-Qualified Names

`application.customers` explicitly names schema and object. `customers` is unqualified and requires PostgreSQL to resolve the name through the active namespace search rules.

## 3.4.15 Understanding search_path

```sql
SHOW search_path;
```

A common default is `"$user", public`. PostgreSQL searches schemas in order and uses the first matching visible object. Schema ordering is operationally significant.

## 3.4.16 $user

The special path entry `"$user"` represents a schema whose name matches `CURRENT_USER`, if such a schema exists and is usable. If it does not exist or is not usable, PostgreSQL ignores that path entry during normal resolution.

## 3.4.17 Effective Search Path

```sql
SELECT current_schemas(true);
SELECT current_schemas(false);
SELECT current_schema();
```

`current_schema()` identifies the first effective schema in the path and is important before unqualified DDL.

## 3.4.18 pg_catalog

System objects are stored primarily in `pg_catalog`. PostgreSQL searches `pg_catalog` even when it is not explicitly listed in `search_path`. Security-sensitive code should not rely casually on uncontrolled ambient search paths.

## 3.4.19 Temporary Schemas and pg_temp

Temporary schemas are represented by names such as `pg_temp_3`; users normally reference the session temporary namespace as `pg_temp`. Temporary-schema lookup has special rules and differs by object class, which matters for security-sensitive code.

## 3.4.20 Current Schema and Unqualified Object Creation

Unqualified objects are created in the current schema, the first existing and usable schema in the effective `search_path`.

```sql
SET search_path TO application, public;

CREATE TABLE orders (
    order_id bigint PRIMARY KEY
);
```

If the current schema lacks `CREATE`, PostgreSQL errors rather than silently skipping to a later schema.

## 3.4.21 Session-Level search_path

```sql
SET search_path TO application, public;
SHOW search_path;
SELECT current_schemas(true);
```

This is session state, not persistent role or database configuration.

## 3.4.22 Database-Level search_path

```sql
ALTER DATABASE application_db
SET search_path TO application, public;
```

Persistent role/database settings can be inspected through `pg_db_role_setting`, but the truth for a live session is still `SHOW search_path`.

## 3.4.23 Role-Level search_path

```sql
ALTER ROLE application_runtime
SET search_path TO application, public;
```

This can provide predictable startup behavior, but it may be too broad when the same role connects to multiple databases.

## 3.4.24 Role-in-Database Configuration

```sql
ALTER ROLE application_runtime
IN DATABASE application_db
SET search_path TO application, public;
```

This is often preferable for roles that connect to multiple databases because it gives finer-grained startup configuration.

## 3.4.25 Configuration Precedence

Persistent configuration can come from system defaults, database settings, role settings, role-in-database settings, and session/application `SET` commands. The more specific applicable setting wins, but troubleshoot live sessions directly.

```sql
SELECT current_database();
SELECT current_user;
SELECT session_user;
SHOW search_path;
SELECT current_schema();
SELECT current_schemas(true);
```

## 3.4.26 SET ROLE Does Not Reload Role Defaults

`SET ROLE` changes the current role but does not automatically reload startup defaults from `ALTER ROLE ... SET`. Validate persistent role configuration with a new connection established as the intended role.

## 3.4.27 Persistent Changes Require Reconnect Validation

After persistent configuration changes, establish a new session and validate startup state.

```sql
ALTER ROLE application_runtime
IN DATABASE application_db
SET search_path TO application, pg_catalog;
```

## 3.4.28 Connection Pools

Do not assume session-level `SET search_path` behaves like permanent configuration across PgBouncer, JDBC pools, framework pools, application server pools, or cloud proxies. Validate through the same pool/proxy path used by production.

## 3.4.29 Search-Path-Dependent vs Schema-Qualified SQL

Search-path-dependent SQL is concise but session-dependent and potentially ambiguous. Schema-qualified SQL is explicit and easier to troubleshoot. Critical DDL, migration SQL, administrative automation, and security-sensitive SQL should generally prefer explicit qualification.

## 3.4.30 Migration DDL Should Prefer Explicit Schemas

```sql
CREATE TABLE application.orders (
    order_id bigint PRIMARY KEY
);

CREATE INDEX orders_customer_idx
ON application.orders(customer_id);
```

Explicit schemas reduce namespace risk, though unqualified functions, operators, and types can still depend on `search_path`.

## 3.4.31 Empty search_path as a Defensive Mode

```sql
SET search_path = '';
```

This defensive mode is useful during incident response, security investigation, legacy database assessment, migration validation, and cross-environment inspection.

## 3.4.32 Security Risk — Writable Schema in search_path

Putting a writable schema into a privileged `search_path` establishes a trust relationship with users who can create objects there. Treat this as security architecture, not convenience configuration.

## 3.4.33 SECURITY DEFINER Functions

`SECURITY DEFINER` functions execute with the privileges of the function owner. Use controlled paths and put `pg_temp` last.

```sql
CREATE FUNCTION admin.secure_operation()
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
BEGIN
    NULL;
END;
$$;
```

## 3.4.34 Function EXECUTE Privileges

Restrict `EXECUTE` on privileged functions to approved roles. A safe owner and safe `search_path` are not enough if broad execution is granted accidentally.

## 3.4.35 Object Shadowing

Object shadowing occurs when a later or intended object name is hidden by an earlier object in the effective path. Search-path design should make object resolution predictable and auditable.

## 3.4.36 Operator and Type Resolution

Types, functions, and operators also use schema resolution rules. Qualified operator syntax exists for exact operator selection.

```sql
SELECT 3 OPERATOR(pg_catalog.+) 4;
```

## 3.4.37 Extension Schemas

Extensions may install objects into `public`, dedicated extension schemas, or schemas specified at installation time. Extension placement affects security, search path, upgrade behavior, and migration portability.

## 3.4.38 Reporting and Operations Schemas

Separate reporting and operations schemas can isolate read models, monitoring objects, operational functions, and support utilities from application-owned transactional schemas.

## 3.4.39 Audit Schemas

Audit schemas should have explicit ownership, restricted `CREATE`, controlled writes, predictable grants, and careful retention/recovery practices.

## 3.4.40 Schema Inventory Queries

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

Inventory should distinguish system schemas, extension schemas, application schemas, and unexpected schemas.

## 3.4.41 Schema Privilege Audit

Use `has_schema_privilege` and catalog inspection to validate expected `USAGE` and `CREATE` grants.

```sql
SELECT
    has_schema_privilege('application_runtime', 'application', 'USAGE') AS usage,
    has_schema_privilege('application_runtime', 'application', 'CREATE') AS create_privilege;
```

## 3.4.42 Ownership Changes

```sql
ALTER SCHEMA application
OWNER TO new_owner;
```

This is a security change, not just metadata maintenance. Review privileges, dependencies, application impact, and approvals.

## 3.4.43 Schema Drift

Unexpected schemas such as `debug`, `old_migration`, or `test_schema` can indicate failed migrations, manual work, incomplete cleanup, temporary troubleshooting, unauthorized change, or deployment drift.

## 3.4.44 search_path Drift

`search_path` is production configuration. Track expected values for application runtime roles, migration roles, reporting roles, operational automation, and privileged functions.

## 3.4.45 Correlated Security Drift

Correlate schema, owner, ACL, role membership, `search_path`, and `SECURITY DEFINER` functions. An unexpected schema plus broad `CREATE` plus a privileged search path is much more serious than any one signal alone.

## 3.4.46 Drift Severity Model

Use severity tiers: informational for expected system/extension schemas, warning for undocumented non-writable schemas, high for unexpected application schemas, and critical for unexpected writable schemas in privileged search paths.

## 3.4.47 Troubleshooting — Relation Does Not Exist

```sql
SELECT current_database();
SELECT current_user, session_user;
SHOW search_path;
SELECT current_schema();
SELECT current_schemas(true);

SELECT
    schemaname,
    tablename
FROM pg_tables
WHERE tablename = 'customers';
```

The relation may exist in a schema the session does not search.

## 3.4.48 Troubleshooting — Permission Denied for Schema

```sql
SELECT has_schema_privilege(current_user, 'application', 'USAGE');
SELECT has_table_privilege(current_user, 'application.customers', 'SELECT');
```

Both schema `USAGE` and appropriate object privileges are normally required, subject to additional controls such as RLS and column privileges.

## 3.4.49 Failure Scenario — Wrong Object Resolved

If both `public.settings` and `application.settings` exist and `search_path = public, application`, an unqualified query can use the wrong object. Prevent this with explicit qualification, controlled paths, and restricted `CREATE`.

## 3.4.50 Failure Scenario — Runtime Role Has CREATE

A runtime role granted `CREATE` on an application schema can modify a trusted namespace if compromised. Revoke the grant after impact assessment and audit objects created by that role.

```sql
REVOKE CREATE
ON SCHEMA application
FROM application_runtime;
```

## 3.4.51 Failure Scenario — Migration Uses Wrong Schema

Unqualified migration DDL can create objects in the wrong schema when the deployment session has an unexpected current schema. Use qualified DDL, migration preflight, and post-deployment validation.

## 3.4.52 Wrong-Schema Deployment Recovery

If objects were created in the wrong schema, freeze further deployment, inventory wrong-schema objects, analyze dependencies, choose move/rollback/redeploy, validate ownership and privileges, validate the application, and resume carefully.

## 3.4.53 Failure Scenario — Unsafe SECURITY DEFINER

Unsafe `SECURITY DEFINER` functions combine elevated privileges, uncontrolled `search_path`, and untrusted `CREATE`. Prevent this with controlled ownership, trusted paths, `pg_temp` last, qualified references, restricted execution, and continuous audit.

## 3.4.54 Destructive Operation — DROP SCHEMA

```sql
DROP SCHEMA application;
DROP SCHEMA application CASCADE;
```

`CASCADE` can recursively remove dependent objects. Never use `DROP SCHEMA ... CASCADE` as a troubleshooting shortcut.

## 3.4.55 Schema-Drop Incident Recovery

If a production schema is dropped, stop affected writes/workflows, establish the timeline, determine removed objects and dependency impact, validate backup/PITR, select a recovery method, restore in isolation when appropriate, validate security, and perform controlled production recovery.

## 3.4.56 Production Schema Provisioning Runbook

Create the schema with explicit ownership, restrict `CREATE`, grant runtime `USAGE`, grant required object privileges, configure future-object privileges, set an appropriate path, reconnect, validate effective path and privileges, test through production pooling/proxy paths, and record the baseline.

```sql
CREATE SCHEMA application
AUTHORIZATION application_owner;

GRANT USAGE
ON SCHEMA application
TO application_runtime;

ALTER ROLE application_runtime
IN DATABASE application_db
SET search_path TO application, pg_catalog;
```

## 3.4.57 Production Migration Preflight

Before DDL, compare live session values with expected configuration.

```sql
SELECT current_database();
SELECT current_user;
SELECT session_user;
SHOW search_path;
SELECT current_schema();
SELECT current_schemas(true);
```

Stop migration if database, role, schema, path, or privilege assumptions are false.

## 3.4.58 Upgrade, Restore, and Migration Validation

After major upgrades, logical restores, PITR, cross-environment migrations, and cloud migrations, validate schema inventory, owners, `USAGE`, `CREATE`, `PUBLIC` privileges, `search_path`, role settings, role-in-database settings, `SECURITY DEFINER` functions, function `EXECUTE`, and object ownership.

## 3.4.59 Managed PostgreSQL Considerations

Core schema and `search_path` semantics apply across PostgreSQL deployments, but managed platforms can differ in superuser capabilities, ownership operations, predefined administrative roles, extensions, security administration, and automation.

## 3.4.60 Monitoring and Alerting

Audit schema creation/deletion, ownership changes, `CREATE` grants, `USAGE` grants, `PUBLIC` privileges, unexpected schemas, `search_path` changes, role configuration changes, role-in-database changes, `SECURITY DEFINER` functions, function `EXECUTE` grants, and objects created by runtime roles.

## 3.4.61 Automation Guardrails

Automation should validate expected cluster, database, role, schema, owner, `search_path`, safe `CREATE` privileges, and absence of unexpected naming collisions before applying changes. Fail deployments when critical assumptions are false.

## 3.4.62 Schema-as-Code

Schema architecture should be reproducible from version-controlled definitions: schemas, grants, roles, validation SQL, ownership checks, privilege checks, `SECURITY DEFINER` checks, and `search_path` checks.

## 3.4.63 Production Case Study — search_path Deployment Failure

A migration runs `CREATE TABLE orders (...)` while the deployment session has `search_path = public`. The object becomes `public.orders`, but runtime searches `application`, causing `relation "orders" does not exist`. Explicit namespaces and preflight validation prevent this class of failure.

## 3.4.64 SRE/DBRE Production Principles

1. Treat schema ownership as security architecture.
2. Separate owner, deployer, and runtime identities.
3. Separate `USAGE` from `CREATE`.
4. Treat `CREATE` as trust.
5. Inspect `public`.
6. Treat `search_path` as production configuration.
7. Prefer schema-qualified critical SQL.
8. Understand `pg_temp`.
9. Protect `SECURITY DEFINER` functions.
10. Validate persistent changes with new sessions.
11. Test through connection pools.
12. Guard destructive schema operations.
13. Detect correlated drift.
14. Revalidate after upgrades and restores.
15. Automate migration preflight.

## 3.4.65 Schema Reliability Architecture

```text
Database
  v
Schemas
  v
Ownership + USAGE + CREATE
  v
search_path
  v
Object resolution
  v
Object privileges + role security
  v
Application behavior
  v
Drift / audit / monitoring
```

For privileged functions: controlled owner, trusted `search_path`, `pg_temp` last, restricted `EXECUTE`, qualified sensitive references, and audit.

```sql

SELECT

    nspacl

AUTHORIZATION application_owner;

SELECT
    COALESCE(d.datname, 'ALL DATABASES') AS database_name,
    COALESCE(r.rolname, 'ALL ROLES') AS role_name,
    s.setconfig
FROM pg_db_role_setting AS s
LEFT JOIN pg_database AS d
    ON d.oid = s.setdatabase
LEFT JOIN pg_roles AS r
    ON r.oid = s.setrole
ORDER BY 1, 2;
```

## 3.4.67 Section Summary

PostgreSQL schemas provide namespaces within a database, but production behavior depends on ownership, `USAGE`, `CREATE`, `search_path`, object privileges, and role membership. The most important security relationship is that untrusted `CREATE` plus a searched schema plus unqualified references creates risk. Mature systems use dedicated schemas, controlled ownership, restricted `CREATE`, explicit runtime `USAGE`, controlled paths, schema-qualified critical SQL, migration preflight, `SECURITY DEFINER` controls, runtime validation, drift detection, and automation guardrails.
