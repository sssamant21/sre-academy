# 3.5 — PostgreSQL Schemas and Namespace Architecture

PostgreSQL schemas provide the namespace architecture within a database. Although schemas are often described simply as containers used to organize database objects, their production role is substantially broader.

Schemas influence:

* Object organization
* Object-name resolution
* Security boundaries
* Ownership
* Role-based access control
* Application isolation
* Multi-application database design
* Extension deployment
* Operational troubleshooting
* Migration and deployment behavior

For a DBA, SRE, or DBRE, understanding schemas therefore requires understanding both the SQL abstraction and the PostgreSQL namespace implementation underneath it.

---

## 3.5.1 PostgreSQL Schema Architecture

A PostgreSQL cluster contains one or more databases. Each database contains one or more schemas, and schemas contain database objects.

Conceptually:

```text
PostgreSQL Cluster
│
├── Database A
│   │
│   ├── pg_catalog
│   ├── information_schema
│   ├── public
│   ├── application_a
│   │   ├── tables
│   │   ├── indexes
│   │   ├── views
│   │   ├── sequences
│   │   ├── functions
│   │   └── types
│   │
│   └── application_b
│       ├── tables
│       ├── views
│       ├── sequences
│       └── functions
│
└── Database B
    └── ...
```

A PostgreSQL connection operates within a single database. Schemas provide namespaces inside that database.

This distinction is important:

```text
Cluster
   ↓
Database
   ↓
Schema
   ↓
Object
```

PostgreSQL roles are different: roles are cluster-wide objects rather than objects belonging to an individual database.

---

## 3.5.2 Why PostgreSQL Uses Schemas

Schemas solve several important architectural problems.

### Object organization

Instead of placing every application object in one namespace:

```text
public.customer
public.order
public.invoice
public.audit
```

an enterprise database can organize objects by application or responsibility:

```text
sales.customer
sales.order

billing.invoice
billing.payment

audit.event_log
```

### Name isolation

Different schemas can contain objects with identical names.

For example:

```text
sales.customer
archive.customer
reporting.customer
```

These objects are independent because their fully qualified names are different.

### Security boundaries

Schema privileges can control which roles may access the namespace or create objects inside it.

### Application isolation

Multiple applications can use one database while maintaining separate namespaces.

Example:

```text
database: enterprise

schemas:
    crm
    billing
    reporting
    integration
    audit
```

This architecture does not provide the same isolation as separate databases, but it can provide useful logical and privilege boundaries when designed carefully.

---

## 3.5.3 Fully Qualified Object Names

A PostgreSQL object can be referenced using its schema-qualified name.

```sql
SELECT *
FROM sales.customer;
```

The structure is:

```text
schema.object
```

Examples include:

```text
app.orders
billing.invoice
audit.event_log
reporting.monthly_sales
```

Schema qualification is particularly valuable in:

* Administrative scripts
* Migration scripts
* Security-sensitive SQL
* Stored code
* Troubleshooting
* Multi-schema environments
* Automation

It removes ambiguity about which object PostgreSQL should resolve.

---

## 3.5.4 Namespace Internals — `pg_namespace`

Internally, PostgreSQL represents schemas as namespaces.

The system catalog responsible for namespaces is:

```text
pg_namespace
```

Important columns include:

```text
oid
nspname
nspowner
nspacl
```

Conceptually:

```text
SQL Schema
     │
     ▼
pg_namespace
     │
     ├── oid
     ├── nspname
     ├── nspowner
     └── nspacl
```

A DBRE can inspect namespaces with:

```sql
SELECT
    n.oid,
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

This is useful when investigating:

* Schema ownership
* Unexpected namespaces
* Permission problems
* Extension-created schemas
* Deployment drift
* Security configuration

## 3.5.5 System Schemas

A PostgreSQL database normally contains several important system-related schemas.

### `pg_catalog`

`pg_catalog` contains PostgreSQL's system catalogs and many built-in functions, operators, and types.

Examples include:

```text
pg_class
pg_attribute
pg_namespace
pg_database
pg_roles
pg_proc
```

DBAs and DBREs frequently query these catalogs for PostgreSQL-specific operational information.

---

### `information_schema`

`information_schema` provides SQL-standard metadata views.

For example:

```sql
SELECT
    table_schema,
    table_name
FROM information_schema.tables;
```

It is useful when portability and SQL-standard metadata access are desirable.

For PostgreSQL-specific troubleshooting, the native `pg_catalog` catalogs usually provide substantially more implementation detail.

---

### `public`

A new database normally contains a schema named:

```text
public
```

Historically, PostgreSQL environments commonly allowed users to create objects in `public`.

Production engineers must not assume that this is universally true.

Modern PostgreSQL defaults are more restrictive, while databases upgraded from older PostgreSQL releases can retain historical privileges.

Always inspect the actual privileges.

For example:

```sql
SELECT
    nspname,
    nspacl
FROM pg_namespace
WHERE nspname = 'public';
```

Or test a specific role:

```sql
SELECT has_schema_privilege(
    'app_runtime',
    'public',
    'CREATE'
);
```

Where organizational policy requires it, `CREATE` may be removed:

```sql
REVOKE CREATE
ON SCHEMA public
FROM PUBLIC;
```

However, this change should be validated against existing applications, extensions, migrations, and deployment tooling before being applied to an established production database.

---

### Temporary schemas

PostgreSQL can create temporary namespaces associated with sessions that use temporary objects.

These can appear with names similar to:

```text
pg_temp_*
pg_toast_temp_*
```

They should not be confused with permanent application schemas.

---

### `pg_toast`

PostgreSQL uses TOAST infrastructure to manage large attribute values that cannot conveniently remain inline in the normal table tuple.

Associated internal objects can reside under PostgreSQL-managed TOAST namespaces.

Application administrators should not treat these as ordinary application schemas.

---

## 3.5.6 Creating a Schema

A basic schema can be created with:

```sql
CREATE SCHEMA app;
```

A schema can also be assigned directly to an owner:

```sql
CREATE SCHEMA app
AUTHORIZATION app_owner;
```

Ownership matters because the schema owner has significant control over the namespace.

For production systems, ownership should be deliberately designed rather than left as an accidental result of whichever login executed the deployment.

---

## 3.5.7 Production Ownership Architecture

A strong production pattern separates:

```text
Object ownership
```

from:

```text
Runtime application access
```

For example:

```text
app_owner
   │
   ├── NOLOGIN
   ├── owns schema
   └── owns application objects

app_runtime
   │
   ├── LOGIN
   └── receives only required privileges
```

Example:

```sql
CREATE ROLE app_owner NOLOGIN;

CREATE ROLE app_runtime LOGIN;

CREATE SCHEMA app
AUTHORIZATION app_owner;
```

Then grant the runtime identity only what the application requires:

```sql
GRANT USAGE
ON SCHEMA app
TO app_runtime;
```

This prevents the application runtime identity from automatically having the broad authority associated with object ownership.

### Production principle

```text
Runtime identity ≠ Object owner
```

where practical.

This separation improves:

* Least privilege
* Credential rotation
* Operational governance
* Deployment control
* Incident containment
* Privilege auditing

---

## 3.5.8 `USAGE` Versus `CREATE`

Schema privileges must not be confused with object privileges.

Two important schema privileges are:

```text
USAGE
CREATE
```

### USAGE

```sql
GRANT USAGE
ON SCHEMA app
TO app_runtime;
```

`USAGE` allows a role to access objects within the namespace, assuming it also has the necessary privileges on those objects.

It does not automatically grant access to every table.

### CREATE

```sql
GRANT CREATE
ON SCHEMA app
TO deployment_role;
```

`CREATE` allows the role to create objects within the schema.

Production application runtime roles often do not require this privilege.

A useful separation is:

```text
deployment_role
      │
      └── CREATE

app_runtime
      │
      └── USAGE
```

---

## 3.5.9 Schema Privileges Do Not Replace Object Privileges

Consider:

```sql
GRANT USAGE
ON SCHEMA app
TO app_runtime;
```

This alone does not grant:

```text
SELECT
INSERT
UPDATE
DELETE
TRUNCATE
REFERENCES
TRIGGER
EXECUTE
```

on contained objects.

Object privileges must be granted separately.

Example:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_runtime;
```

For sequences:

```sql
GRANT USAGE, SELECT
ON ALL SEQUENCES IN SCHEMA app
TO app_runtime;
```

The resulting authorization chain is conceptually:

```text
Role
 │
 ├── USAGE ON SCHEMA
 │
 └── required privilege ON OBJECT
          │
          ▼
       Access
```

Both layers may matter.

---

## 3.5.10 Future Objects and Default Privileges

One of the most frequent production authorization failures occurs after a deployment creates new objects.

Suppose an administrator runs:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_runtime;
```

Existing tables receive the privileges.

Later:

```sql
CREATE TABLE app.new_feature (...);
```

The application can then fail with:

```text
ERROR: permission denied for table new_feature
```

because `ON ALL TABLES IN SCHEMA` affected the objects existing when the command was executed.

Future objects require default privileges.

For example:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLES
TO app_runtime;
```

For future sequences:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT USAGE, SELECT
ON SEQUENCES
TO app_runtime;
```

### Critical DBRE rule

Default privileges depend on the role that creates the future object.

Therefore:

```text
Expected object creator
        │
        ▼
ALTER DEFAULT PRIVILEGES FOR ROLE ...
```

must be aligned correctly.

Configuring default privileges for the wrong role is a common reason that deployments appear correctly configured but newly created tables still produce permission failures.

In `psql`, inspect default privileges with:

```text
\ddp
```

## 3.5.11 `search_path`

When SQL references an object without specifying its schema:

```sql
SELECT *
FROM orders;
```

PostgreSQL must determine which `orders` object is intended.

The schema search path controls this resolution.

Inspect it with:

```sql
SHOW search_path;
```

A common value might resemble:

```text
"$user", public
```

PostgreSQL searches candidate namespaces according to the effective search path until it finds the requested object.

For example:

```text
search_path

app
 ↓
shared
 ↓
public
```

Given:

```text
app.orders
shared.orders
public.orders
```

the unqualified reference:

```sql
SELECT *
FROM orders;
```

can resolve differently depending on the effective `search_path`.

---

## 3.5.12 Current Schema and Effective Search Path

Useful diagnostics include:

```sql
SHOW search_path;
```

```sql
SELECT current_schema();
```

and:

```sql
SELECT current_schemas(true);
```

`current_schema()` identifies the first valid schema in the search path.

`current_schemas(true)` is particularly useful operationally because it can show implicitly searched schemas as well.

This distinction matters when troubleshooting object resolution.

---

## 3.5.13 Special Behavior of `pg_catalog`

`pg_catalog` receives special treatment during name resolution.

If `pg_catalog` is not explicitly listed in `search_path`, PostgreSQL searches it implicitly before explicitly listed path entries.

Therefore:

```sql
SHOW search_path;
```

does not always tell the entire story about every namespace participating in effective resolution.

For incident analysis, use:

```sql
SELECT current_schemas(true);
```

alongside:

```sql
SHOW search_path;
```

---

## 3.5.14 `search_path` as a Security Boundary

`search_path` is not merely a developer convenience.

A schema included in the search path can become a trust boundary when other users are allowed to create objects in that schema.

Consider:

```text
search_path = app, shared, public
```

If an untrusted role can create objects in `shared`, it may be able to introduce objects whose names collide with unqualified references.

Conceptually:

```text
Application SQL
      │
      ▼
unqualified object name
      │
      ▼
search_path
      │
      ├── app
      ├── shared   ← writable?
      └── public
```

This creates an object-shadowing risk.

### Production rule

Do not place schemas writable by untrusted users in security-sensitive search paths.

For critical administrative and security-sensitive operations, schema qualification is strongly preferred.

Instead of:

```sql
SELECT *
FROM orders;
```

prefer:

```sql
SELECT *
FROM app.orders;
```

when explicit resolution is appropriate.

---

## 3.5.15 Application-Level Search Paths

A controlled application configuration may set a deliberate search path.

For example:

```sql
ALTER ROLE app_runtime
SET search_path = app, pg_catalog;
```

This can simplify application SQL while providing predictable namespace resolution.

However, production teams should carefully consider:

* Which schemas are included
* Who owns them
* Who has `CREATE`
* Whether application migrations rely on another path
* Whether stored functions rely on unqualified objects
* Whether extensions introduce dependencies

Changing `search_path` in an existing production environment without dependency analysis can break applications.

---

## 3.5.16 Object Shadowing Failure Scenario

Assume:

```text
search_path = shared, app, public
```

and these functions exist:

```text
shared.calculate_price()
app.calculate_price()
```

The application calls:

```sql
SELECT calculate_price();
```

The function PostgreSQL resolves can depend on the effective search path and function-resolution rules.

### Symptoms

Possible symptoms include:

* Unexpected application behavior
* Incorrect business logic
* Function-not-found errors
* Security anomalies
* Different behavior between environments
* Deployment-dependent failures

### Investigation

Start with:

```sql
SHOW search_path;
```

Then:

```sql
SELECT current_schema();
```

and:

```sql
SELECT current_schemas(true);
```

Find matching functions:

```sql
SELECT
    n.nspname AS schema_name,
    p.proname AS function_name
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE p.proname = 'calculate_price';
```

Then inspect ownership and privileges on the relevant namespaces.

### Remediation

Depending on the root cause:

* Correct `search_path`
* Remove inappropriate `CREATE` privileges
* Schema-qualify references
* Correct application configuration
* Remove or rename unintended objects
* Correct deployment behavior

## 3.5.17 Deployment Privilege Failure Scenario

### Incident

A release creates:

```text
app.new_feature
```

The application starts returning:

```text
permission denied for table new_feature
```

Older tables continue working.

### Likely cause

Existing-object grants were configured:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_runtime;
```

but default privileges were never established for the role creating new objects.

### Investigation

Check table privileges:

```sql
SELECT
    table_schema,
    table_name,
    grantee,
    privilege_type
FROM information_schema.table_privileges
WHERE table_schema = 'app'
  AND table_name = 'new_feature';
```

Determine ownership:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
  AND tablename = 'new_feature';
```

Inspect default privileges:

```text
\ddp
```

### Remediation

Correct the existing object's grants and then configure the correct default privileges for the role that creates future objects.

## 3.5.18 Schema Discovery

List application-oriented schemas:

```sql
SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
WHERE n.nspname NOT LIKE 'pg_%'
  AND n.nspname <> 'information_schema'
ORDER BY n.nspname;
```

List all namespaces when performing deeper diagnostics:

```sql
SELECT
    n.oid,
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

The second query is often preferable during incident response because filtering system namespaces too early can hide useful evidence.

---

## 3.5.19 Schema Privilege Troubleshooting

Check whether the current role has `USAGE`:

```sql
SELECT has_schema_privilege(
    current_user,
    'app',
    'USAGE'
);
```

Check `CREATE`:

```sql
SELECT has_schema_privilege(
    current_user,
    'app',
    'CREATE'
);
```

Check another role:

```sql
SELECT has_schema_privilege(
    'app_runtime',
    'app',
    'USAGE'
);
```

A complete authorization investigation should consider:

```text
Login role
    │
    ▼
Role memberships
    │
    ▼
Schema privileges
    │
    ▼
Object privileges
    │
    ▼
Object ownership
    │
    ▼
Default privileges
```

Checking only one of these layers can produce an incomplete diagnosis.

## 3.5.20 Production Schema Governance

Enterprise environments should establish explicit schema governance.

At minimum, define:

```text
Schema
  │
  ├── Purpose
  ├── Owner
  ├── Deployment role
  ├── Runtime roles
  ├── CREATE policy
  ├── USAGE policy
  ├── Default privileges
  └── search_path policy
```

Avoid unmanaged patterns such as:

```text
Every user → CREATE on shared schemas
Every application → owns its objects
Every workload → relies on public
Every query → relies on implicit resolution
```

A more controlled model is:

```text
                  app_owner
                      │
              owns schema/objects
                      │
          ┌───────────┴───────────┐
          │                       │
 deployment_role             app_runtime
          │                       │
      migrations             runtime DML
                                  │
                            least privilege
```

## 3.5.21 Monitoring and Auditing

Schema configuration changes relatively infrequently, making configuration drift detection especially valuable.

DBRE teams should periodically identify:

* Unexpected schemas
* Unexpected schema owners
* Runtime roles with `CREATE`
* `PUBLIC` privileges inconsistent with policy
* Application schemas writable by unrelated roles
* Unexpected `search_path` settings
* Ownership drift
* Missing default privileges
* Extension-created namespaces
* Orphaned schemas
* Deployment identities with excessive privileges

Example inventory:

```sql
SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

This inventory can be incorporated into compliance and configuration-drift automation.

## 3.5.22 Production Troubleshooting Runbook

When an application reports:

```text
relation does not exist
```

```text
permission denied for schema
```

```text
permission denied for table
```

or unexpectedly accesses the wrong object, begin with the following sequence.

### Step 1 — Confirm identity

```sql
SELECT
    current_user,
    session_user;
```

### Step 2 — Inspect search path

```sql
SHOW search_path;
```

### Step 3 — Inspect effective namespaces

```sql
SELECT current_schema();

SELECT current_schemas(true);
```

### Step 4 — Confirm schema existence and ownership

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

### Step 5 — Validate schema privileges

```sql
SELECT has_schema_privilege(
    current_user,
    'app',
    'USAGE'
);
```

### Step 6 — Validate object privileges

```sql
SELECT has_table_privilege(
    current_user,
    'app.orders',
    'SELECT'
);
```

### Step 7 — Verify the intended object exists

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE tablename = 'orders';
```

### Step 8 — Check for duplicate names

```sql
SELECT
    schemaname,
    tablename
FROM pg_tables
WHERE tablename = 'orders'
ORDER BY schemaname;
```

### Step 9 — Check default privileges

For deployment-related failures:

```text
\ddp
```

### Step 10 — Compare environments

If production behaves differently from staging, compare:

```text
schema ownership
schema ACLs
object ownership
role membership
default privileges
search_path
database-level role settings
extension schemas
deployment identity
```

Do not assume that identical DDL implies identical authorization behavior.

## 3.5.23 Common Production Anti-Patterns

### Anti-pattern 1 — Everything in `public`

This makes ownership, application separation, and privilege governance unnecessarily difficult.

### Anti-pattern 2 — Runtime users own schemas

Compromising an application credential can then provide substantially more control than the application requires.

### Anti-pattern 3 — Runtime users have `CREATE`

Most applications need DML access, not the ability to create arbitrary database objects.

### Anti-pattern 4 — Blind reliance on `search_path`

Unqualified names can create ambiguity and security risk.

### Anti-pattern 5 — Grants only for existing tables

Future deployments subsequently fail because default privileges were omitted.

### Anti-pattern 6 — Assuming `public` privileges

Actual privileges can differ according to PostgreSQL version, database history, template configuration, and previous administrative changes.

### Anti-pattern 7 — Manually modifying system namespaces

PostgreSQL-managed namespaces and objects should not be manipulated as though they were application schemas.

---

## 3.5.24 SRE/DBRE Production Checklist

Before approving a schema architecture for production, verify:

* [ ] Application schemas have explicit purposes.
* [ ] Schema owners are controlled roles.
* [ ] Runtime accounts do not unnecessarily own schemas.
* [ ] Runtime accounts do not unnecessarily receive `CREATE`.
* [ ] Required `USAGE` privileges are configured.
* [ ] Table privileges follow least privilege.
* [ ] Sequence privileges are configured where required.
* [ ] Future-object default privileges are configured.
* [ ] Default privileges correspond to the actual object-creating role.
* [ ] `public` privileges have been explicitly reviewed.
* [ ] Application `search_path` is documented.
* [ ] Writable schemas are not unnecessarily trusted through `search_path`.
* [ ] Security-sensitive SQL uses explicit schema qualification where appropriate.
* [ ] Schema ownership is monitored for drift.
* [ ] Schema ACLs are periodically audited.
* [ ] Deployment and runtime roles are separated where practical.
* [ ] Recovery and migration procedures preserve ownership and grants.

## 3.5.25 Production Design Pattern

A mature application namespace architecture commonly resembles:

```text
PostgreSQL Database
│
├── pg_catalog
├── information_schema
├── public
│
├── app
│   │
│   ├── Owner: app_owner (NOLOGIN)
│   ├── Deployment: controlled migration role
│   ├── Runtime: app_runtime
│   ├── Runtime CREATE: NO
│   ├── Runtime USAGE: YES
│   ├── Object privileges: least privilege
│   └── Default privileges: explicitly managed
│
├── reporting
│   ├── Owner: reporting_owner
│   └── Read-oriented roles
│
└── audit
    ├── Owner: audit_owner
    └── tightly controlled access
```

The key principle is:

```text
Schemas are not merely organizational containers.

They are part of PostgreSQL's
namespace,
ownership,
authorization,
deployment,
and security architecture.
```

---

## 3.5.26 Key Takeaways

1. PostgreSQL schemas provide namespaces inside a database.

2. Schemas are internally represented through `pg_namespace`.

3. Different schemas can contain objects with identical names.

4. `search_path` determines how many unqualified object references are resolved.

5. `search_path` must be treated as a security consideration when writable schemas are involved.

6. `USAGE ON SCHEMA` does not automatically grant privileges on objects inside the schema.

7. `CREATE ON SCHEMA` should normally be restricted to controlled roles.

8. Production object ownership should preferably be separated from runtime application identities.

9. Grants on existing objects do not automatically solve privileges for future objects.

10. `ALTER DEFAULT PRIVILEGES` must be configured for the role that will create those future objects.

11. `public` schema privileges must be inspected rather than assumed, particularly across PostgreSQL versions and upgraded databases.

12. `pg_catalog`, `information_schema`, temporary namespaces, and PostgreSQL-managed namespaces have different operational purposes from application schemas.

13. Schema-qualified SQL reduces ambiguity and is particularly valuable for administration, migrations, automation, and security-sensitive operations.

14. Schema ownership, ACLs, default privileges, and `search_path` should be treated as auditable production configuration.

---

## 3.5.27 Final Production Standard

For enterprise PostgreSQL environments, the recommended baseline is:

```text
Dedicated application schema
          +
Controlled NOLOGIN owner
          +
Separate deployment identity
          +
Least-privilege runtime role
          +
Explicit schema privileges
          +
Explicit object privileges
          +
Correct default privileges
          +
Controlled search_path
          +
Schema-qualified critical SQL
          +
Continuous privilege/ownership auditing
```

This model provides a strong foundation for secure, predictable, and operationally manageable PostgreSQL namespace administration.
