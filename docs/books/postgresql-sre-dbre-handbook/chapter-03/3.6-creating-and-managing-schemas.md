# 3.6 — Creating and Managing Schemas

PostgreSQL schemas provide logical namespaces within a database. Creating a schema is straightforward, but operating schemas safely in production requires deliberate control over naming, ownership, privileges, deployment identities, dependencies, backup and recovery, and eventual retirement.

For DBA, SRE, and DBRE teams, schema administration should therefore be treated as a lifecycle-management responsibility rather than a collection of isolated DDL commands.

---

## 3.6.1 Schema Lifecycle

A production schema normally follows a lifecycle such as:

```text
Requirement
    │
    ▼
Schema Design
    │
    ▼
Naming and Ownership
    │
    ▼
CREATE SCHEMA
    │
    ▼
Privilege Configuration
    │
    ▼
Default Privileges
    │
    ▼
Application Deployment
    │
    ▼
Monitoring / Drift Detection
    │
    ▼
Change Management
    │
    ▼
Retirement
    │
    ▼
Dependency Analysis
    │
    ▼
DROP SCHEMA
```

Each stage should be controlled, documented, auditable, and recoverable.

---

## 3.6.2 Production Schema Naming Standards

Schema names should be predictable, stable, descriptive, and aligned with an application or business domain.

Prefer:

```text
billing
reporting
audit
integration
customer
```

Avoid temporary or person-specific names such as:

```text
john_schema
new_schema
test123
temp_app
```

PostgreSQL reserves schema names beginning with `pg_` for system purposes.

Application schemas should therefore not use names such as:

```text
pg_application
pg_sales
pg_company
```

A useful enterprise standard is:

```text
lowercase
+
descriptive
+
stable
+
domain-oriented
+
non-personal
```

---

## 3.6.3 Creating a Schema

The basic command is:

```sql
CREATE SCHEMA app;
```

The executing role becomes the schema owner unless another owner is explicitly specified.

Verify the result:

```sql
SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
WHERE n.nspname = 'app';
```

In `psql`:

```text
\dn
```

Production environments should generally define ownership explicitly rather than allowing it to depend accidentally on whichever administrative account executed the command.

---

## 3.6.4 Database Privilege Required for Schema Creation

Creating a schema requires appropriate `CREATE` privilege on the database.

A useful preflight check is:

```sql
SELECT has_database_privilege(
    current_user,
    current_database(),
    'CREATE'
);
```

When schema creation fails, verify database privileges before assuming that the problem is a schema ACL.

Also verify the operating identity:

```sql
SELECT
    session_user,
    current_user,
    current_role;
```

This becomes particularly important when role inheritance or `SET ROLE` is involved.

---

## 3.6.5 Creating a Schema with Explicit Ownership

Create a dedicated owner:

```sql
CREATE ROLE app_owner NOLOGIN;
```

Then create the namespace:

```sql
CREATE SCHEMA app
AUTHORIZATION app_owner;
```

Conceptually:

```text
app_owner
    │
    └── owns
         │
         ▼
      schema app
```

Creating a schema owned by another role also requires the executing identity to possess the necessary authority to act as that owner.

Production automation should validate this explicitly rather than relying on broad superuser privileges.

---

## 3.6.6 Production Role Architecture

A strong enterprise pattern separates:

```text
Ownership
Deployment
Runtime
```

For example:

```text
                     app_owner
                      NOLOGIN
                         │
                         ▼
                 schema / objects
                         ▲
                         │
                controlled SET ROLE
                         │
                   app_deployer
                         │
                    migrations


                    app_runtime
                         │
                  application DML
```

This provides three distinct responsibilities.

### Owner role

```text
app_owner
```

Owns the schema and application objects.

### Deployment role

```text
app_deployer
```

Authenticates the migration/deployment process and obtains only the authority required to perform controlled DDL.

### Runtime role

```text
app_runtime
```

Executes normal application operations and should generally not own production objects or perform arbitrary DDL.

---

## 3.6.7 Deterministic Deployment Ownership

This is a critical production rule.

Suppose:

```sql
GRANT CREATE
ON SCHEMA app
TO app_deployer;
```

and the deployment runs:

```sql
CREATE TABLE app.orders (...);
```

Do not assume that the new table will automatically be owned by `app_owner`.

Object ownership follows the effective role performing object creation.

Therefore production migrations should deliberately establish the intended effective identity.

For example:

```sql
SET ROLE app_owner;

CREATE TABLE app.orders (
    order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now()
);

RESET ROLE;
```

The exact membership and `SET ROLE` architecture should follow organizational security policy.

Before migration execution, verify:

```sql
SELECT
    session_user,
    current_user,
    current_role;
```

Conceptually:

```text
Authenticated Identity
        │
        ▼
session_user
        │
        ▼
Role Membership / SET ROLE
        │
        ▼
current_user
        │
        ▼
Object Creation
        │
        ▼
Object Ownership
```

Ownership must be deterministic.

---

## 3.6.8 Creating Objects in the Intended Schema

Prefer explicitly qualified migration DDL:

```sql
CREATE TABLE app.customer (
    customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_name text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Avoid relying unnecessarily on:

```sql
CREATE TABLE customer (...);
```

because unqualified object creation depends on the effective schema search path.

A migration running under an unexpected `search_path` can accidentally create:

```text
public.customer
```

instead of:

```text
app.customer
```

Production migrations should therefore use deterministic schema qualification.

---

## 3.6.9 Granting Schema Privileges

Grant namespace access:

```sql
GRANT USAGE
ON SCHEMA app
TO app_runtime;
```

Grant object-creation capability only when necessary:

```sql
GRANT CREATE
ON SCHEMA app
TO app_deployer;
```

These privileges have different purposes:

```text
USAGE
   │
   └── access objects through namespace

CREATE
   │
   └── create objects in namespace
```

Application runtime roles should normally not receive `CREATE` unless runtime DDL is a genuine application requirement.

---

## 3.6.10 Object Privileges

Schema access does not automatically grant access to contained tables.

For example:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA app
TO app_runtime;
```

Sequence access may also be required:

```sql
GRANT USAGE, SELECT
ON ALL SEQUENCES IN SCHEMA app
TO app_runtime;
```

For a read-only role:

```sql
GRANT USAGE
ON SCHEMA app
TO app_readonly;

GRANT SELECT
ON ALL TABLES IN SCHEMA app
TO app_readonly;
```

Authorization should therefore be considered in layers:

```text
Role
 │
 ├── Schema privilege
 │
 └── Object privilege
       │
       ▼
Effective Access
```

---

## 3.6.11 Future Objects and Default Privileges

Existing-object grants do not automatically grant equivalent access to objects created later.

For future tables:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLES
TO app_runtime;
```

For future sequences:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT USAGE, SELECT
ON SEQUENCES
TO app_runtime;
```

For future read-only access:

```sql
ALTER DEFAULT PRIVILEGES
FOR ROLE app_owner
IN SCHEMA app
GRANT SELECT
ON TABLES
TO app_readonly;
```

The critical relationship is:

```text
Object-Creating Role
        │
        ├── determines ownership
        └── determines applicable
            default privileges
```

Default privileges configured for the wrong role are a common cause of deployment-time authorization failures.

Inspect them in `psql` with:

```text
\ddp
```

---

## 3.6.12 Inspecting Schema Ownership

Use:

```sql
SELECT
    n.oid,
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
ORDER BY n.nspname;
```

For application-oriented namespaces:

```sql
SELECT
    n.nspname AS schema_name,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
WHERE n.nspname NOT LIKE 'pg_%'
  AND n.nspname <> 'information_schema'
ORDER BY n.nspname;
```

In `psql`:

```text
\dn+
```

Schema ownership should be included in configuration-drift auditing.

## 3.6.13 Renaming a Schema

Rename with:

```sql
ALTER SCHEMA app
RENAME TO application;
```

A schema rename is technically simple but operationally significant.

Potential dependencies include:

```text
Application SQL
Stored code
ETL pipelines
BI queries
Monitoring
Migration tooling
Automation
search_path
Connection initialization
```

The production workflow should therefore resemble:

```text
Dependency Discovery
        │
        ▼
Non-Production Test
        │
        ▼
Application Coordination
        │
        ▼
Change Window
        │
        ▼
ALTER SCHEMA
        │
        ▼
Validation
        │
        ▼
Rollback / Completion
```

A schema rename should be treated as an application-impacting change.

---

## 3.6.14 Changing Schema Ownership

Use:

```sql
ALTER SCHEMA app
OWNER TO app_owner;
```

Then verify:

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner
FROM pg_namespace AS n
WHERE n.nspname = 'app';
```

Ownership transfer requires appropriate authority over both the existing schema and target owner.

Critically:

```text
Changing schema owner
        ≠
Changing owners of all
objects inside schema
```

The contained objects must be audited separately.

---

## 3.6.15 Auditing Object Ownership

Tables:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;
```

Sequences:

```sql
SELECT
    schemaname,
    sequencename,
    sequenceowner
FROM pg_sequences
WHERE schemaname = 'app'
ORDER BY sequencename;
```

A schema may therefore look like:

```text
app                    → app_owner
app.customer           → app_owner
app.orders             → app_deployer
app.old_table          → former_dba
```

This is ownership drift even though the schema itself has the correct owner.

---

## 3.6.16 `REASSIGN OWNED`

PostgreSQL provides:

```sql
REASSIGN OWNED BY old_role TO app_owner;
```

This is a role-oriented ownership operation—not a schema-oriented operation.

Do not interpret it as:

```text
Change objects in app schema
from old_role to app_owner
```

Its impact can extend to objects owned by the source role outside the intended schema, and shared-object ownership must also be considered.

It does not automatically solve every privilege or default-privilege relationship associated with the old role.

### High-Risk DBRE Rule

Before `REASSIGN OWNED`:

```text
Identify source role
       │
       ▼
Inventory ownership
       │
       ▼
Review complete scope
       │
       ▼
Validate target owner
       │
       ▼
Change approval
       │
       ▼
REASSIGN OWNED
       │
       ▼
Post-change audit
```

Do not use it as a shortcut for poorly understood ownership drift.

---

## 3.6.17 `DROP OWNED`

`DROP OWNED` is fundamentally different:

```sql
DROP OWNED BY old_role;
```

Conceptually:

```text
REASSIGN OWNED
       │
       └── ownership migration


DROP OWNED
       │
       └── object removal /
           privilege cleanup
```

`DROP OWNED` should be treated as a potentially destructive role-retirement operation.

It must not be confused with ownership transfer.

Using:

```sql
DROP OWNED BY old_role CASCADE;
```

can increase the blast radius through dependencies and therefore requires particularly careful review.

---

## 3.6.18 Revoking Schema Privileges

Remove creation capability:

```sql
REVOKE CREATE
ON SCHEMA app
FROM app_runtime;
```

Remove namespace access:

```sql
REVOKE USAGE
ON SCHEMA app
FROM app_runtime;
```

Privilege revocation should be tested carefully.

A role may still possess table privileges while becoming unable to access the object because the required namespace access has been removed.

---

## 3.6.19 Dropping a Schema

An empty schema can be removed with:

```sql
DROP SCHEMA app;
```

or:

```sql
DROP SCHEMA IF EXISTS app;
```

`IF EXISTS` prevents an error when the schema is absent.

It does **not** make the operation inherently safe.

---

## 3.6.20 `DROP SCHEMA ... RESTRICT`

For controlled production operations, begin with:

```sql
DROP SCHEMA app RESTRICT;
```

When dependencies prevent removal, PostgreSQL returns an error rather than silently destroying them.

The correct response is:

```text
DROP ... RESTRICT
       │
       ▼
Dependency Error
       │
       ▼
INVESTIGATE
```

not:

```text
Dependency Error
       │
       ▼
Retry with CASCADE
```

A dependency error is valuable safety information.

---

## 3.6.21 `DROP SCHEMA ... CASCADE`

PostgreSQL also permits:

```sql
DROP SCHEMA app CASCADE;
```

This is a high-risk operation.

`CASCADE` should not be interpreted as:

```text
delete only objects physically
inside this schema
```

Dependencies can cross namespace boundaries.

Therefore objects outside the target schema may potentially be affected through dependency chains.

### Production Safety Gate

Before approving `CASCADE`:

```text
CASCADE requested
       │
       ▼
Object inventory complete?
       │
       ▼
Dependency analysis complete?
       │
       ▼
External consumers checked?
       │
       ▼
Recovery validated?
       │
       ▼
Change approved?
       │
       ▼
EXECUTE
```

If any safety gate fails, do not proceed.

---

## 3.6.22 Schema Retirement Workflow

A production schema should be retired through a controlled process:

```text
Identify Schema
      │
      ▼
Confirm Business Owner
      │
      ▼
Stop New Deployments / Writes
      │
      ▼
Inventory Objects
      │
      ▼
Analyze Dependencies
      │
      ▼
Check External Consumers
      │
      ▼
Validate Backup / Recovery
      │
      ▼
Remove Application References
      │
      ▼
Test RESTRICT
      │
      ▼
Change Approval
      │
      ▼
DROP
      │
      ▼
Post-Change Validation
```

Starting with:

```sql
DROP SCHEMA app CASCADE;
```

is not an acceptable production retirement strategy.

## 3.6.23 Inventory Before Removal

Tables:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;
```

Views:

```sql
SELECT
    schemaname,
    viewname,
    viewowner
FROM pg_views
WHERE schemaname = 'app'
ORDER BY viewname;
```

Sequences:

```sql
SELECT
    schemaname,
    sequencename,
    sequenceowner
FROM pg_sequences
WHERE schemaname = 'app'
ORDER BY sequencename;
```

Functions:

```sql
SELECT
    n.nspname AS schema_name,
    p.proname AS function_name,
    pg_get_userbyid(p.proowner) AS owner
FROM pg_proc AS p
JOIN pg_namespace AS n
    ON n.oid = p.pronamespace
WHERE n.nspname = 'app'
ORDER BY p.proname;
```

For complex production systems, this object inventory is only the beginning. Cross-schema and external dependencies must also be evaluated.

---

## 3.6.24 Logical Schema Backup

A schema can be selected for logical export using `pg_dump`.

For example:

```bash
pg_dump -n app database_name > app.sql
```

This can be useful for:

```text
Logical migration
Development refresh
Selective export
Controlled object movement
Certain recovery workflows
```

However:

```text
Schema-targeted pg_dump
          ≠
Guaranteed self-contained
recovery unit
```

Objects selected from one schema can depend on objects outside that selection.

A schema-targeted logical dump must therefore not automatically be treated as an independent disaster-recovery backup.

---

## 3.6.25 Backup Architecture Versus Schema Export

Production recovery architecture should distinguish:

```text
Schema Logical Export
         │
         └── selective logical use cases
```

from:

```text
Database Backup / Physical Backup / PITR
         │
         └── disaster recovery architecture
```

A selective schema export does not replace the overall database backup and point-in-time recovery strategy.

Recovery procedures must be tested.

---

## 3.6.26 Security Metadata During Recovery

Restoring tables alone does not constitute a complete schema recovery.

Validate:

```text
Schema owner
Object owners
Schema ACLs
Object ACLs
Default privileges
Sequences
Functions
Types
Dependencies
Role assumptions
search_path behavior
```

For example:

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
WHERE n.nspname = 'app';
```

A successful data restore can still result in an application outage if ownership or authorization differs from the original environment.

---

## 3.6.27 Transactional DDL

Many PostgreSQL schema-management operations can participate in transactions.

For controlled testing:

```sql
BEGIN;

ALTER SCHEMA app
RENAME TO application;

-- validation

ROLLBACK;
```

This can provide useful rollback capability.

However:

```text
Transactional
      ≠
Operationally Risk-Free
```

Applications, connection pools, migration systems, monitoring, and other external consumers can still be affected by namespace changes.

Transactional rollback is an additional control—not a substitute for change management.

## 3.6.28 Failure Scenario — Wrong Schema Owner

### Symptom

```text
ERROR: permission denied for schema app
```

### Investigation

```sql
SELECT
    session_user,
    current_user,
    current_role;
```

Then:

```sql
SELECT
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
WHERE n.nspname = 'app';
```

Check:

```sql
SELECT has_schema_privilege(
    current_user,
    'app',
    'CREATE'
);
```

Possible causes include:

* Wrong deployment role
* Missing role membership
* Missing `CREATE`
* Ownership drift
* Incorrect `SET ROLE`
* ACL changes

Fix the intended role model rather than granting broad access as a shortcut.

---

## 3.6.29 Failure Scenario — Wrong Object Owner After Deployment

### Expected

```text
app.orders
owner = app_owner
```

### Actual

```text
app.orders
owner = app_deployer
```

### Root cause

The deployment connected as:

```text
session_user = app_deployer
current_user = app_deployer
```

and never established the intended owner identity.

### Detection

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;
```

### Remediation

First correct the deployment identity architecture.

Then remediate ownership after carefully inventorying the affected objects.

Do not compensate by granting excessive privileges to the application runtime account.

---

## 3.6.30 Failure Scenario — New Tables Are Inaccessible

### Symptom

Existing tables work while newly deployed tables return:

```text
permission denied for table new_feature
```

### Likely cause

Default privileges are absent or configured for the wrong object-creating role.

Check ownership:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app';
```

Check access:

```sql
SELECT has_table_privilege(
    'app_runtime',
    'app.new_feature',
    'SELECT'
);
```

Inspect defaults:

```text
\ddp
```

Correct both the existing object's privileges and future-object defaults.

---

## 3.6.31 Failure Scenario — Object Created in Wrong Schema

### Expected

```text
app.orders
```

### Actual

```text
public.orders
```

Investigate:

```sql
SHOW search_path;

SELECT current_schema();

SELECT current_schemas(true);
```

Find all candidate objects:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE tablename = 'orders';
```

The preferred prevention is schema-qualified migration DDL:

```sql
CREATE TABLE app.orders (...);
```

---

## 3.6.32 Failure Scenario — Schema Rename Breaks Application

After:

```sql
ALTER SCHEMA app
RENAME TO application;
```

the application reports:

```text
relation does not exist
```

Investigate:

* Hard-coded schema qualification
* Application configuration
* `search_path`
* Connection-pool initialization
* Stored code
* ETL
* Reporting
* Monitoring
* Deployment automation

Schema renames require coordinated application validation.

## 3.6.33 Failure Scenario — Role Retirement

Suppose:

```text
old_deployer
```

must be removed.

Do not immediately execute:

```sql
DROP ROLE old_deployer;
```

or:

```sql
DROP OWNED BY old_deployer CASCADE;
```

Use:

```text
Inventory Ownership
       │
       ▼
Inventory Grants
       │
       ▼
Determine Replacement Owner
       │
       ▼
Reassign Required Ownership
       │
       ▼
Handle Privileges / Default ACLs
       │
       ▼
Validate Applications
       │
       ▼
Remove Obsolete Access
       │
       ▼
DROP ROLE
```

Role retirement is an ownership, privilege, and dependency operation.

## 3.6.34 Automation and Infrastructure as Code

Schema administration should preferably be managed through repeatable, version-controlled deployment mechanisms.

Automation should be:

```text
Version controlled
Peer reviewed
Deterministic
Auditable
Environment tested
Ownership aware
Privilege aware
Dependency aware
```

The desired state should explicitly describe:

```text
Schema name
Schema owner
Deployment identity
Runtime identities
Schema privileges
Object privileges
Default privileges
search_path policy
```

Destructive reconciliation should not be automatic.

An unexpected schema detected by automation should trigger investigation rather than an automatic:

```sql
DROP SCHEMA ... CASCADE;
```

## 3.6.35 Schema Drift Detection

Production teams should periodically compare intended state with PostgreSQL state.

```text
Desired State                PostgreSQL

Schema            <──────>   pg_namespace
Owner             <──────>   nspowner
Schema ACL        <──────>   nspacl
Object ownership  <──────>   system catalogs
Default ACLs      <──────>   pg_default_acl
Privileges        <──────>   effective privilege checks
```

Important drift conditions include:

* Unexpected schema
* Unexpected owner
* Runtime role gains `CREATE`
* Human account owns application objects
* Obsolete deployment role owns new objects
* ACL changes
* Missing default privileges
* Unexpected `PUBLIC` access

Most schema drift belongs in configuration/security review rather than immediate paging unless availability or security is actively threatened.

## 3.6.36 Production Preflight Runbook

Before significant schema administration:

```sql
-- Operating identity
SELECT
    session_user,
    current_user,
    current_role;

-- Database CREATE privilege
SELECT has_database_privilege(
    current_user,
    current_database(),
    'CREATE'
);

-- Schema metadata
SELECT
    n.oid,
    n.nspname,
    pg_get_userbyid(n.nspowner) AS owner,
    n.nspacl
FROM pg_namespace AS n
WHERE n.nspname = 'app';

-- Effective schema privileges
SELECT
    has_schema_privilege(
        current_user,
        'app',
        'USAGE'
    ) AS usage,
    has_schema_privilege(
        current_user,
        'app',
        'CREATE'
    ) AS create_privilege;

-- Namespace resolution
SHOW search_path;

SELECT current_schemas(true);
```

Then inspect object ownership:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;
```

For deployment privilege issues:

```text
\ddp
```

This provides a consistent DBRE starting point before making changes.

## 3.6.37 Production Change Checklist

### Before Creating

* [ ] Confirm schema purpose.
* [ ] Validate naming standard.
* [ ] Define the owner role.
* [ ] Define deployment identity.
* [ ] Define runtime identities.
* [ ] Verify database `CREATE`.
* [ ] Define schema privileges.
* [ ] Define object privileges.
* [ ] Define default privileges.
* [ ] Document `search_path` behavior.
* [ ] Ensure ownership will be deterministic.

### Before Modifying

* [ ] Verify `session_user` and `current_user`.
* [ ] Verify current schema owner.
* [ ] Inventory contained objects.
* [ ] Audit contained-object owners.
* [ ] Identify application dependencies.
* [ ] Evaluate `search_path` impact.
* [ ] Test outside production.
* [ ] Define rollback.
* [ ] Obtain appropriate change approval.

### Before Dropping

* [ ] Confirm business approval.
* [ ] Stop new deployments and writes where required.
* [ ] Inventory all objects.
* [ ] Analyze dependencies.
* [ ] Check external consumers.
* [ ] Validate backup/recovery.
* [ ] Test with `RESTRICT`.
* [ ] Review any proposed `CASCADE`.
* [ ] Confirm recovery capability.
* [ ] Perform post-change validation.

## 3.6.38 Common Production Anti-Patterns

### Runtime identity owns application objects

This weakens least-privilege architecture.

### Human administrator owns application objects

Personnel and account lifecycle changes then become database ownership problems.

### Runtime role receives unnecessary `CREATE`

A compromised application credential gains unnecessary DDL capability.

### Deployment ownership is accidental

Objects end up owned by whichever role happened to run the migration.

### Default privileges are omitted

Future tables break while existing tables continue working.

### Unqualified migration DDL

Objects can be created in unintended namespaces.

### Schema owner changed without object-owner audit

The schema looks correct while contained objects retain obsolete ownership.

### `REASSIGN OWNED` used as a schema command

Its role-oriented scope can affect more than intended.

### `DROP OWNED` confused with ownership transfer

This can become destructive.

### Failed `RESTRICT` automatically followed by `CASCADE`

This defeats PostgreSQL's dependency protection.

### Schema logical export treated as full DR

Cross-schema dependencies and broader database recovery requirements are overlooked.

                              ▼

## 3.6.40 Key Takeaways

1. Schema administration is a lifecycle-management responsibility.

2. Production schema names should be stable, descriptive, and governed.

3. Application schema names must not use PostgreSQL's reserved `pg_` prefix.

4. Schema creation requires appropriate database-level `CREATE` privilege.

5. Production schemas should use explicitly controlled owners.

6. Ownership, deployment, and runtime responsibilities should be separated where practical.

7. Object ownership follows the effective creating identity.

8. A deployment role receiving schema `CREATE` does not automatically create objects owned by the schema owner.

9. Default privileges must align with the actual object-creating role.

10. Schema privileges and object privileges are separate authorization layers.

11. Changing a schema's owner does not automatically change ownership of contained objects.

12. `REASSIGN OWNED` is role-oriented and can have a broader scope than one schema.

13. `DROP OWNED` is potentially destructive and is not an ownership-transfer mechanism.

14. Schema renames should be treated as application-impacting changes.

15. `DROP ... RESTRICT` should be used as an important dependency safety mechanism.

16. `DROP ... CASCADE` requires explicit blast-radius analysis and validated recovery.

17. Schema-targeted `pg_dump` output should not automatically be considered a self-contained disaster-recovery unit.

18. Recovery must validate ownership, privileges, default ACLs, dependencies, and namespace behavior—not merely restored data.

19. Schema state should be version controlled and monitored for configuration drift.

20. Destructive schema lifecycle operations require change control and tested recovery.
