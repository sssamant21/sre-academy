## 3.7.1 Tables as Production Objects

PostgreSQL tables are the primary persistent relational structures used to store application data. In production, however, a table is substantially more than a collection of columns and rows.

A production table combines:

```text
Application Table
       │
       ├── Logical Design
       │     ├── Columns
       │     ├── Data types
       │     ├── Constraints
       │     └── Keys
       │
       ├── Physical Storage
       │     ├── Heap
       │     ├── Pages
       │     ├── TOAST
       │     └── Indexes
       │
       ├── MVCC
       │     ├── Tuple versions
       │     ├── HOT
       │     └── VACUUM
       │
       └── Operations
             ├── Statistics
             ├── Locks
             ├── WAL
             ├── Replication
             ├── Backup
             └── Capacity
```

Poor table architecture can contribute to excessive I/O, bloat, autovacuum pressure, locking, replication lag, storage exhaustion, difficult migrations, and application outages.

Table design is therefore a reliability concern as well as a data-modeling concern.

## 3.7.2 Logical Table Architecture

A PostgreSQL table belongs to a database and schema:

```text
PostgreSQL Cluster
        │
        ▼
     Database
        │
        ▼
      Schema
        │
        ▼
       Table
        │
        ├── Columns
        ├── Constraints
        ├── Indexes
        ├── Triggers
        ├── Statistics
        └── Dependencies
```

A fully qualified table name is:

```text
schema.table
```

Examples:

```text
app.customer
sales.orders
billing.invoice
audit.event_log
```

Production migrations should generally use schema-qualified object names when deterministic namespace resolution matters.

## 3.7.3 Creating a Production Table

Example:

```sql
CREATE TABLE app.customer (
    customer_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,

    customer_name text NOT NULL,

    email text,

    created_at timestamptz
        NOT NULL
        DEFAULT now()
);
```

This definition contains multiple architectural decisions:

```text
customer_id
    ├── bigint
    ├── identity generation
    └── primary key

customer_name
    ├── text
    └── NOT NULL

email
    └── nullable text

created_at
    ├── timestamptz
    ├── NOT NULL
    └── DEFAULT now()
```

Each should be intentional.

## 3.7.4 PostgreSQL Table Catalog Architecture

PostgreSQL represents table metadata through several system catalogs.

Important catalogs include:

```text
pg_class
pg_attribute
pg_type
pg_namespace
pg_constraint
pg_index
pg_statistic
```

Conceptually:

```text
Schema
  │
  ▼
pg_namespace
  │
  ▼
Table
  │
  ▼
pg_class
  │
  ├── Columns ───────► pg_attribute
  ├── Constraints ───► pg_constraint
  ├── Indexes ───────► pg_index / pg_class
  └── Statistics ────► pg_statistic
```

Understanding these relationships is useful for advanced diagnostics, automation, migrations, dependency analysis, and catalog investigations.

## 3.7.5 Inspecting `pg_class`

`pg_class` contains metadata for relations including tables, indexes, sequences, views, and materialized views.

```sql
SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    pg_get_userbyid(c.relowner) AS owner,
    c.relpersistence
FROM pg_class AS c
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'app'
ORDER BY c.relname;
```

The SQL-level abstraction:

```text
TABLE
```

ultimately maps to PostgreSQL relation metadata.

## 3.7.6 Inspecting Columns

Column metadata is represented through `pg_attribute`.

```sql
SELECT
    a.attnum,
    a.attname AS column_name,
    format_type(a.atttypid, a.atttypmod) AS data_type,
    a.attnotnull
FROM pg_attribute AS a
JOIN pg_class AS c
    ON c.oid = a.attrelid
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'app'
  AND c.relname = 'customer'
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY a.attnum;
```

For portable metadata discovery, `information_schema.columns` is also useful.

## 3.7.7 Heap Storage

Ordinary PostgreSQL tables use heap storage.

Conceptually:

```text
Table
 │
 ▼
Heap Relation
 │
 ├── Page 0
 ├── Page 1
 ├── Page 2
 ├── ...
 └── Page N
```

Indexes exist as separate relations:

```text
Heap Table
    │
    ├────────► B-tree
    ├────────► GIN
    ├────────► GiST
    └────────► BRIN
```

An index therefore does not normally transform the heap itself into index order.

## 3.7.8 PostgreSQL Pages

PostgreSQL stores table and index data in fixed-size pages.

A standard PostgreSQL build normally uses an 8 KiB block size, although this is a build-time characteristic and should be verified when necessary.

A heap page conceptually contains:

```text
Page
 │
 ├── Page header
 ├── Item identifiers
 ├── Free space
 └── Tuple data
```

Page behavior affects:

* Buffer-cache efficiency
* I/O
* Tuple placement
* HOT updates
* VACUUM
* Bloat
* Corruption analysis

## 3.7.9 MVCC Tuple Lifecycle

PostgreSQL uses Multi-Version Concurrency Control.

An update generally creates another tuple version rather than simply overwriting the existing row in place.

The lifecycle should be understood as:

```text
Current Tuple
     │
     ▼
UPDATE / DELETE
     │
     ▼
Old Tuple Version
     │
     ▼
Still visible to a relevant transaction?
     │
   YES ─────────────► Retain
     │
    NO
     │
     ▼
Removable
     │
     ▼
VACUUM cleanup / space reuse
```

An old tuple version is therefore not necessarily immediately removable.

Long-lived transactions can prevent cleanup from advancing.

## 3.7.10 HOT Updates

PostgreSQL can sometimes use Heap-Only Tuple (HOT) updates.

HOT can reduce index churn when conditions permit.

Conceptually:

```text
UPDATE
   │
   ├── index-relevant values unchanged?
   ├── index conditions compatible?
   └── same-page space available?
             │
             ▼
          HOT possible
```

HOT is an optimization opportunity rather than something an administrator directly enables for each update.

Monitor:

```sql
SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC;
```

A lower table fillfactor can increase the opportunity for same-page updates in appropriate workloads.

## 3.7.11 Permanent Tables

The normal table type is permanent:

```sql
CREATE TABLE app.orders (
    order_id bigint PRIMARY KEY
);
```

Permanent tables participate in PostgreSQL's normal WAL and durability architecture.

They are the normal choice for persistent business data.

## 3.7.12 UNLOGGED Tables

PostgreSQL supports:

```sql
CREATE UNLOGGED TABLE app.stage_data (
    id bigint,
    payload jsonb
);
```

Unlogged tables can reduce WAL-related overhead.

However, they have materially different reliability characteristics.

```text
UNLOGGED
    │
    ├── reduced WAL overhead
    ├── not crash-safe
    ├── contents can be truncated after crash recovery
    └── contents are not replicated to physical standbys
```

### Production Rule

Do not use UNLOGGED for data that must survive PostgreSQL crashes or be present on physical standby servers.

It is a durability decision, not merely a performance optimization.

## 3.7.13 Temporary Tables

Temporary tables are session-oriented:

```sql
CREATE TEMP TABLE session_work (
    id bigint,
    payload jsonb
);
```

They are useful for:

* ETL
* Intermediate transformations
* Reporting
* Batch processing
* Temporary calculations

PostgreSQL autovacuum cannot process temporary tables belonging to application sessions.

For a heavily populated temporary table used in complex queries, the session may need:

```sql
ANALYZE session_work;
```

after significant data changes.

## 3.7.14 Table Ownership

Inspect table ownership:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app'
ORDER BY tablename;
```

The preferred architecture remains:

```text
app_owner
    │
    └── owns
         │
         ▼
      app.orders


app_runtime
    │
    └── granted required DML
```

Runtime application identities should generally not own production tables.

## 3.7.15 Deterministic Ownership

Suppose a migration authenticates as:

```text
app_deployer
```

and executes:

```sql
CREATE TABLE app.orders (...);
```

Object ownership follows the effective creating identity.

Therefore production deployment architecture should deliberately control:

```sql
SELECT
    session_user,
    current_user,
    current_role;
```

The long-term solution to ownership drift is deterministic deployment identity, not repeated post-deployment ownership repair.

## 3.7.16 Table Privileges

Example runtime access:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON app.orders
TO app_runtime;
```

Read-only access:

```sql
GRANT SELECT
ON app.orders
TO app_readonly;
```

Ownership and privileges are separate concepts.

Existing-table privileges must also be paired with appropriate default privileges for future tables where required.

## 3.7.17 Row Identity Strategy

Every important mutable business table should have a deliberate row-identification strategy.

Absence of stable identity can complicate:

* UPDATE / DELETE targeting
* Referential integrity
* CDC
* Logical replication
* Data reconciliation
* Deduplication
* Incident repair
* Cross-system synchronization

This does not mean every PostgreSQL relation universally requires a primary key.

It means lack of row identity should be an explicit design decision rather than an accident.

## 3.7.18 Primary Keys

Example:

```sql
CREATE TABLE app.orders (
    order_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,

    created_at timestamptz
        NOT NULL
        DEFAULT now()
);
```

A primary key enforces uniqueness and non-nullability for its key columns and creates an appropriate unique B-tree index.

Primary keys are especially valuable for OLTP and replication-oriented tables.

## 3.7.19 Identity Columns

PostgreSQL supports:

```sql
id bigint GENERATED ALWAYS AS IDENTITY
```

and:

```sql
id bigint GENERATED BY DEFAULT AS IDENTITY
```

Identity provides generated values.

It does not by itself guarantee uniqueness.

The distinction is:

```text
IDENTITY
    │
    └── generated value


PRIMARY KEY / UNIQUE
    │
    └── uniqueness enforcement
```

Therefore a common production design is:

```sql
id bigint
    GENERATED ALWAYS AS IDENTITY
    PRIMARY KEY
```

Identity state must also be considered during logical migrations, restores, synchronization, and failback procedures.

## 3.7.20 Foreign Keys

Example:

```sql
CREATE TABLE app.orders (
    order_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,

    customer_id bigint NOT NULL,

    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES app.customer(customer_id)
);
```

Foreign keys enforce referential integrity.

A critical PostgreSQL operational rule is:

```text
Creating a foreign key does not automatically create an index on its referencing columns.
```

For some workloads:

```sql
CREATE INDEX idx_orders_customer_id
ON app.orders(customer_id);
```

may be appropriate.

Evaluate referencing-side indexing based on:

* Parent DELETE
* Parent key UPDATE
* Join patterns
* Child-table size
* Referential-check cost
* Write overhead

Do not create indexes blindly, but do not overlook this decision.

## 3.7.21 NOT NULL and CHECK

Example:

```sql
CREATE TABLE app.payment (
    payment_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,

    amount numeric(18,2) NOT NULL,

    status text NOT NULL,

    CHECK (amount >= 0)
);
```

Constraints protect data invariants regardless of which application or process writes the table.

Application validation alone should not replace database constraints when the invariant must always hold.

## 3.7.22 Data Type Selection

Data types affect:

* Correctness
* Storage
* Indexes
* Comparison semantics
* Planner behavior
* CPU
* Application compatibility

Examples:

```text
Large numeric identifier   → bigint where scale requires
Instant in time            → timestamptz
Arbitrary text             → text
Exact decimal requirement  → appropriately designed numeric
Boolean state              → boolean
```

Type selection should express semantics rather than simply using whichever type is most familiar.

Changing types on large production tables should be treated as potentially significant DDL.

## 3.7.23 NULL Semantics

NULL represents an unknown or absent value.

It is not:

```text
''
0
false
```

A column should be nullable only when absence is valid.

Prefer:

```sql
customer_name text NOT NULL
```

when every valid row requires a value.

Nullability is part of the data contract.

## 3.7.24 Defaults

Example:

```sql
created_at timestamptz
    NOT NULL
    DEFAULT now()
```

Defaults provide a value when an insert omits a column.

A default is not a constraint.

For example:

```sql
status text DEFAULT 'NEW'
```

does not prevent:

```text
INVALID
UNKNOWN
ABC
```

from being inserted.

Use constraints when allowed values must be enforced.

## 3.7.25 TOAST Architecture

PostgreSQL uses TOAST mechanisms to handle large variable-length values.

Conceptually:

```text
Heap Tuple
    │
    ├── normal inline attributes
    │
    └── large attribute
             │
             ▼
           TOAST
             │
             ├── compression where applicable
             └── out-of-line storage where applicable
```

TOAST can become operationally important for:

* text
* bytea
* json
* jsonb
* other large variable-length values

A table's main heap size may therefore tell only part of the storage story.

## 3.7.26 Correct Table Size Accounting

For production capacity work, inspect multiple dimensions:

```sql
SELECT
    pg_size_pretty(
        pg_relation_size('app.orders')
    ) AS main_fork,

    pg_size_pretty(
        pg_table_size('app.orders')
    ) AS table_storage,

    pg_size_pretty(
        pg_indexes_size('app.orders')
    ) AS indexes,

    pg_size_pretty(
        pg_total_relation_size('app.orders')
    ) AS total;
```

Conceptually:

```text
pg_relation_size
       │
       └── specified relation/fork storage


pg_table_size
       │
       └── table-related storage
           including TOAST,
           excluding indexes


pg_indexes_size
       │
       └── associated indexes


pg_total_relation_size
       │
       └── complete table footprint
```

Do not use only `pg_relation_size()` when performing complete capacity analysis.

## 3.7.27 Table Statistics

A useful operational view is:

```sql
SELECT
    schemaname,
    relname,
    seq_scan,
    idx_scan,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC;
```

Important interpretation rules:

```text
n_live_tup
n_dead_tup
      │
      └── estimates
```

and activity counters such as:

```text
seq_scan
idx_scan
n_tup_ins
n_tup_upd
n_tup_del
```

are cumulative statistics that can reset.

Monitoring systems should therefore use rates, deltas, and trends where appropriate.

## 3.7.28 Bloat

MVCC updates and deletes can leave tuple versions that later become removable.

Persistent storage inefficiency can eventually produce bloat.

Possible symptoms include:

* Relation growth
* Increasing I/O
* Poor cache efficiency
* Longer scans
* Increased maintenance work

But:

```text
high n_dead_tup
       ≠
confirmed bloat
```

A better model is:

```text
Dead tuple estimates
       +
Relation growth
       +
Vacuum behavior
       +
Workload churn
       +
Long transactions
       +
Storage measurements
       │
       ▼
Bloat assessment
```

Bloat should be measured, not guessed.

## 3.7.29 VACUUM

VACUUM is fundamental to PostgreSQL table health.

```text
INSERT / UPDATE / DELETE
          │
          ▼
      Tuple versions
          │
          ▼
Versions become removable
          │
          ▼
        VACUUM
          │
          ├── enables space reuse
          ├── maintains visibility information
          └── protects transaction lifecycle
```

Autovacuum should normally remain enabled.

It is important not only for dead-tuple cleanup but also for transaction-ID and multixact wraparound protection.

Globally disabling autovacuum as a generic performance optimization is unsafe.

## 3.7.30 ANALYZE

ANALYZE collects statistics used by PostgreSQL's query planner.

```sql
ANALYZE app.orders;
```

Poor or stale statistics can contribute to inaccurate cardinality estimates and inefficient query plans.

Automatic analyze normally handles this based on configured thresholds, but major data-distribution changes can justify additional investigation.

## 3.7.31 Per-Table Autovacuum Tuning

Large or high-churn tables may require table-specific tuning.

Example:

```sql
ALTER TABLE app.orders
SET (
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_analyze_scale_factor = 0.01
);
```

These are examples, not universal recommendations.

Tune using:

* Table size
* Update/delete rate
* Insert rate
* Dead tuple generation
* Vacuum duration
* I/O capacity
* Transaction-ID consumption
* Observed autovacuum behavior

A single configuration should not be copied blindly across every table.

## 3.7.32 Fillfactor

Example:

```sql
ALTER TABLE app.orders
SET (fillfactor = 80);
```

A lower fillfactor leaves additional page space available for future tuples.

For appropriate update-heavy workloads:

```text
Lower fillfactor
       │
       ├── more same-page update opportunity
       ├── potentially more HOT updates
       └── greater storage footprint
```

It should be workload-driven.

## 3.7.33 Tablespaces

Example:

```sql
CREATE TABLE app.orders (
    order_id bigint PRIMARY KEY
)
TABLESPACE application_data;
```

Tablespaces provide storage-location control in self-managed PostgreSQL.

A tablespace is not automatically:

* a backup boundary
* an HA boundary
* a replication boundary
* a storage tier

without corresponding infrastructure design.

Managed PostgreSQL services can impose different storage restrictions and are covered in their dedicated chapters.

## 3.7.34 DDL Locking

Table DDL can acquire strong locks.

For example:

```sql
ALTER TABLE app.orders
ADD COLUMN source_system text;
```

may appear operationally trivial while lock acquisition causes significant application impact.

A common failure pattern is:

```text
Long-running transaction
          │
          ▼
DDL requests lock
          │
          ▼
DDL waits
          │
          ▼
Application queries queue
          │
          ▼
Connection pool saturation
          │
          ▼
Application outage
```

DDL risk therefore includes lock acquisition, not merely execution time.

## 3.7.35 Defensive `lock_timeout`

For appropriate controlled migrations, consider an explicit timeout:

```sql
SET lock_timeout = '5s';

ALTER TABLE app.orders
ADD COLUMN source_system text;
```

The value is only an example.

Production policy should determine the acceptable timeout.

The principle is:

```text
Controlled failure
       >
Unbounded lock waiting
```

for many automated deployment scenarios.

## 3.7.36 Finding Blocked Sessions

Use:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Then inspect transaction age and blocker details:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

Incident response should determine:

* Who is blocked?
* Who is blocking?
* How old is the blocker?
* What transaction owns it?
* What will roll back?
* Which application owns it?

Do not terminate a backend merely because it appears in a blocking chain.

## 3.7.37 DDL Rewrite Risk

Some table changes can require substantial physical work while others can be metadata-oriented or optimized.

Behavior varies by:

* Exact `ALTER TABLE` operation
* PostgreSQL major version
* Data type
* Default expression
* Constraints
* Table state

Therefore:

```text
Determine lock and rewrite behavior for the exact operation and exact PostgreSQL major version.
```

Never infer production safety simply from the apparent simplicity of the SQL syntax.

## 3.7.38 Large-Table DDL Preflight

Before changing a significant table:

```sql
SELECT
    pg_size_pretty(
        pg_table_size('app.orders')
    ) AS table_storage,

    pg_size_pretty(
        pg_indexes_size('app.orders')
    ) AS indexes,

    pg_size_pretty(
        pg_total_relation_size('app.orders')
    ) AS total;
```

Then evaluate:

* Active transactions
* Blocking sessions
* Lock requirements
* Rewrite requirements
* Write rate
* Available storage
* Expected WAL
* Replica lag
* Backup/recovery state
* Application traffic

A 10 MB table and a 10 TB table should not receive identical operational procedures.

## 3.7.39 Replica Identity

Logical replication and CDC systems require sufficient information to identify changed rows.

PostgreSQL supports replica identity modes including:

* DEFAULT
* USING INDEX
* FULL
* NOTHING

Inspect:

```sql
SELECT
    n.nspname,
    c.relname,
    c.relreplident
FROM pg_class AS c
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'app'
  AND c.relname = 'orders';
```

DEFAULT normally uses the primary key when available.

For certain workloads:

```sql
ALTER TABLE app.orders
REPLICA IDENTITY FULL;
```

may be required.

But FULL should not be a universal workaround because it can increase WAL and downstream processing requirements.

A stable key is generally preferable when the data model permits one.

## 3.7.40 CDC Production Preflight

For tables participating in logical replication or CDC:

```text
Row identity
      │
      ▼
Primary key available?
      │
      ▼
Replica identity
      │
      ▼
UPDATE / DELETE requirements
      │
      ▼
CDC behavior
      │
      ▼
WAL impact
      │
      ▼
Downstream reconciliation
```

Changes to primary keys or replica identity should therefore be reviewed with downstream data pipelines, not only the PostgreSQL application team.

## 3.7.41 VACUUM FULL

VACUUM FULL rewrites a table and requires strong locking.

Example:

```sql
VACUUM FULL app.orders;
```

It can return unused storage to the operating system, but it should not be treated as routine MVCC maintenance.

Before execution:

```text
Confirmed reclaimable bloat?
       │
       ▼
OS-level reclamation required?
       │
       ▼
Required free space available?
       │
       ▼
Locking window acceptable?
       │
       ▼
WAL/replica impact acceptable?
       │
       ▼
Approved maintenance window
```

Ordinary VACUUM/autovacuum remains the normal cleanup mechanism.

## 3.7.42 Failure Scenario — Long Transaction Prevents Cleanup

A vacuum problem may actually be a transaction-lifecycle problem.

```text
Long-running transaction
         │
         ▼
Old snapshot remains relevant
         │
         ▼
Old tuple versions cannot
be removed as expected
         │
         ▼
Vacuum cleanup horizon stalls
         │
         ▼
Storage / maintenance pressure
```

Investigate:

```sql
SELECT
    pid,
    usename,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Do not immediately blame autovacuum configuration.

## 3.7.43 Failure Scenario — Rapid Table Growth

Identify large relations:

```sql
SELECT
    schemaname,
    relname,
    pg_size_pretty(
        pg_total_relation_size(relid)
    ) AS total_size,
    n_live_tup,
    n_dead_tup
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 20;
```

Determine whether growth is caused by:

* Live data
* Indexes
* TOAST
* Bloat
* Unexpected ingestion
* Retention failure

A large table is not automatically a bloated table.

## 3.7.44 Failure Scenario — UNLOGGED Data Loss

```text
UNLOGGED table
       │
       ▼
PostgreSQL crash
       │
       ▼
Crash recovery
       │
       ▼
Contents truncated / unavailable
       │
       ▼
Application expected persistence
       │
       ▼
Incident
```

Root cause:

UNLOGGED was selected as a performance optimization without accepting its durability model.

Prevention:

Classify data durability requirements before selecting table persistence.

## 3.7.45 Failure Scenario — Missing Foreign-Key Index

```text
Parent DELETE / UPDATE
        │
        ▼
Referential check
        │
        ▼
Large child table
        │
        ▼
No suitable referencing index
        │
        ▼
Expensive lookup
        │
        ▼
Longer transaction
        │
        ▼
Latency / locking impact
```

Review foreign-key indexing during schema design rather than waiting for an incident.

## 3.7.46 Failure Scenario — Wrong Table Owner

Expected:

```text
app.orders → app_owner
```

Actual:

```text
app.orders → migration_user
```

Detect:

```sql
SELECT
    schemaname,
    tablename,
    tableowner
FROM pg_tables
WHERE schemaname = 'app';
```

Correct the deployment identity architecture first.

Repeatedly repairing ownership after every deployment treats the symptom rather than the cause.

## 3.7.47 Failure Scenario — DDL Lock Incident

Change:

```sql
ALTER TABLE app.orders
ADD COLUMN source_system text;
```

Application requests begin timing out.

Investigate:

```sql
SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    state,
    xact_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database();
```

Determine the blocking chain before terminating any backend.

Prevention includes:

* Exact lock analysis
* `lock_timeout` where appropriate
* Long-transaction detection
* Representative testing
* Controlled deployment windows
* Application and replica monitoring

## 3.7.48 Monitoring Baseline

A useful table-health inventory is:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    seq_scan,
    idx_scan,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_autovacuum,
    last_autoanalyze,
    pg_size_pretty(
        pg_total_relation_size(relid)
    ) AS total_size
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

Interpret this as an operational baseline, not a complete diagnostic by itself.

## 3.7.49 Alerting Strategy

Avoid universal alerts such as:

```text
n_dead_tup > 100000
```

because the operational meaning depends on table size and workload.

Prefer signals such as:

* Storage exhaustion forecast
* Table growth anomaly
* Dead-tuple trend/ratio
* Autovacuum unable to keep pace
* Transaction-ID age
* Long-running transactions
* Lock wait duration
* Blocking chains
* Vacuum duration
* Query latency
* Replication lag

Alerts should identify reliability risk rather than merely PostgreSQL activity.

## 3.7.50 Capacity Planning

Production table capacity is approximately a combination of:

```text
Main Relation
      +
TOAST
      +
Indexes
      +
Growth
      +
Bloat
      +
Maintenance Headroom
      +
Migration Headroom
      =
Storage Requirement
```

Capacity planning should answer:

* How large is the table now?
* How quickly is it growing?
* How large are the indexes?
* How much TOAST storage exists?
* What drives growth?
* What is the retention model?
* How much maintenance headroom is required?
* When will thresholds be reached?

Trend-based forecasting should happen before disk pressure becomes an incident.

## 3.7.53 Common Production Anti-Patterns

### Runtime role owns tables

Violates the intended separation between ownership and application access.

### Human accounts own application tables

Personnel lifecycle becomes database ownership lifecycle.

### Identity assumed to guarantee uniqueness

Generated values and uniqueness enforcement are different mechanisms.

### Foreign key created without indexing review

Large child-table referential operations can become expensive.

### Every column nullable

Important data invariants move unnecessarily into application code.

### Unqualified migration DDL

Objects can be created in unintended schemas.

### UNLOGGED used as generic performance tuning

Durability and standby behavior are sacrificed without explicit approval.

### Autovacuum disabled

MVCC cleanup and wraparound protection are endangered.

### VACUUM FULL used routinely

Heavy locking and table rewrites become normal maintenance.

### Bloat inferred only from `n_dead_tup`

An estimate is mistaken for a diagnosis.

### Capacity measured only with `pg_relation_size`

Indexes and TOAST are overlooked.

### Fixed autovacuum settings copied to every table

Different workloads receive inappropriate thresholds.

### Large DDL executed without lock analysis

A schema migration becomes an availability incident.

### CDC enabled without replica-identity review

UPDATE/DELETE behavior and WAL requirements become unexpected.

## 3.7.57 Key Takeaways

1. PostgreSQL tables are logical, physical, and operational objects simultaneously.
2. Ordinary PostgreSQL tables use heap storage organized into pages.
3. MVCC creates tuple versions; old versions are not necessarily immediately removable.
4. HOT can reduce index maintenance when the required conditions are satisfied.
5. Permanent, temporary, and unlogged tables have different reliability characteristics.
6. UNLOGGED is a durability and HA decision, not merely a performance option.
7. Production ownership should be deterministic and separated from runtime application access.
8. Important mutable business tables should have a deliberate row-identity strategy.
9. Identity generation does not itself enforce uniqueness.
10. Foreign keys do not automatically create referencing-column indexes.
11. Constraints should enforce important data invariants close to the data.
12. TOAST can represent a substantial portion of a table's storage.
13. Capacity analysis must account for table storage, TOAST, indexes, growth, and maintenance headroom.
14. `n_live_tup` and `n_dead_tup` are estimates.
15. PostgreSQL statistics counters must be interpreted with reset and time-window context.
16. Autovacuum is fundamental to MVCC cleanup and transaction lifecycle safety.
17. VACUUM FULL is exceptional maintenance and requires significant operational planning.
18. Long-running transactions can prevent vacuum cleanup from progressing.
19. DDL lock queues can create application outages even when the DDL itself is inexpensive.
20. Exact lock and rewrite behavior must be validated for the specific DDL operation and PostgreSQL version.
21. Replica identity must be deliberately designed for logical replication and CDC.
22. Table monitoring should use trends and risk indicators rather than universal fixed thresholds.
23. Large-table changes require representative testing, rollback planning, and production change control.
24. Table health cannot be inferred from a single metric.
25. Table architecture is directly connected to PostgreSQL reliability.
