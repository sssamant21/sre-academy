## 3.8.1 Purpose

Columns define the contract between PostgreSQL storage, application code, data integrity, query planning, replication, and downstream consumers.

A column change is not a small change merely because the SQL statement is short. In production, column administration must account for data type semantics, defaults, generated expressions, table rewrites, locks, WAL volume, replica lag, CDC behavior, backfills, constraints, indexes, privileges, and application compatibility.

## 3.8.2 Production Principle

Treat every column definition as part of the application and data reliability contract.

Before changing a production column, identify the business meaning, selected data type, nullability, default behavior, generated or identity semantics, dependent objects, lock and rewrite behavior, backfill strategy, rollback or roll-forward path, validation criteria, and observation window.

## 3.8.3 Data Type Selection

PostgreSQL provides rich built-in data types. Production selection should prefer the most precise type that matches the domain while avoiding unnecessary constraints that make future evolution difficult.

| Requirement | Common type | Production note |
| --- | --- | --- |
| Surrogate integer key | `bigint` or identity column | Prefer headroom for long-lived systems. |
| Exact financial value | `numeric(p, s)` | Avoid floating-point types for exact money math. |
| Approximate measurement | `double precision` | Accept rounding behavior explicitly. |
| Short bounded code | `text` plus `CHECK` or domain | Avoid arbitrary `varchar(n)` unless the limit is meaningful. |
| Timestamp with real-world instant | `timestamptz` | Prefer for event time across time zones. |
| Local civil time | `timestamp without time zone` | Use only when local-time semantics are intended. |
| Semi-structured data | `jsonb` | Index and validate intentionally; do not use as a schema escape hatch. |
| Distributed identifier | `uuid` | Useful across systems; understand index locality and generation strategy. |

## 3.8.4 Avoid Ambiguous Type Semantics

The type name is not enough. Document the semantic contract:

- whether `timestamp` values are UTC instants or local business times;
- whether strings are identifiers, labels, free text, or enum-like values;
- whether numeric values are exact quantities or measurements;
- whether JSON fields are governed by application schema;
- whether arrays are acceptable or a child table would be more reliable.

## 3.8.5 Numeric Types

Use integer types for counts and identifiers, `numeric` for exact decimal values, and floating-point types only where approximate arithmetic is acceptable.

For production schemas:

- avoid `integer` for ever-growing surrogate keys when long service life is expected;
- avoid `real` or `double precision` for balances, invoices, or settlement values;
- define scale and precision for externally visible financial values;
- document unit semantics for measurements.

## 3.8.6 Text and Length Limits

`text`, `varchar`, and `varchar(n)` are common production choices. A length limit should express a real contract, not a habit.

Use `varchar(n)` when a downstream protocol, standard, user interface, or external system imposes a genuine maximum length. Otherwise, prefer `text` with domain validation, application validation, or a targeted `CHECK` constraint.

## 3.8.7 Date and Time Types

Use `timestamptz` for events that occurred at a specific instant. Use `timestamp without time zone` only when the value intentionally represents local civil time without an absolute instant.

Production guidance:

- store ingestion time, event time, and business-effective time separately when they differ;
- avoid relying on server-local time zone assumptions;
- be explicit about time zones at application boundaries;
- test daylight-saving and historical-time behavior when business rules depend on local time.

## 3.8.8 JSON and JSONB

`jsonb` is useful for flexible attributes, integration payloads, and evolving metadata. It is not a substitute for data modeling.

Use `jsonb` when the shape is genuinely variable, the payload is secondary to relational identity, indexing needs are understood, and application-level validation is enforced.

Avoid using `jsonb` when fields are required for joins, constraints, frequent filters, privilege decisions, retention rules, or CDC contracts.

## 3.8.9 UUID Columns

The PostgreSQL `uuid` type stores standard UUID values. UUIDs are useful for distributed ID generation and cross-system references.

Production considerations:

- random UUIDs can reduce index locality compared with monotonic keys;
- current PostgreSQL documentation includes native UUID generation support for UUIDv4 and UUIDv7;
- older PostgreSQL versions and deployments may depend on extensions or application-side generation;
- validate generation strategy before using UUIDs as hot primary keys.

## 3.8.10 Column Defaults

A column default is used when an `INSERT` omits the column or explicitly requests `DEFAULT`.

```sql
ALTER TABLE app.orders
ALTER COLUMN status SET DEFAULT 'pending';
```

Changing a default affects future writes only. It does not update existing rows.

## 3.8.11 Defaults Are Not Backfills

Do not confuse a default change with historical data repair.

```sql
ALTER TABLE app.orders
ALTER COLUMN status SET DEFAULT 'pending';
```

This does not change existing `NULL` values. If existing rows must be changed, use a bounded backfill with batching, monitoring, and abort criteria.

## 3.8.12 Adding Columns

Adding a nullable column without a default is usually the lowest-risk pattern.

```sql
ALTER TABLE app.orders
ADD COLUMN fulfillment_state text;
```

Production preflight:

- identify expected lock behavior;
- confirm application compatibility with missing or `NULL` values;
- check long-running transactions;
- set `lock_timeout` and `statement_timeout`;
- verify replication and CDC impact.

## 3.8.13 Adding Columns With Defaults

Current PostgreSQL can add a column with a nonvolatile constant default without rewriting every existing row immediately. The default is represented efficiently and applied as existing rows are read or later rewritten.

```sql
ALTER TABLE app.orders
ADD COLUMN source text DEFAULT 'web';
```

This optimization does not mean every default is low risk. Volatile defaults or designs that force row updates can still create long operations, WAL volume, storage pressure, and replica lag.

## 3.8.14 Volatile Defaults

Volatile defaults such as `clock_timestamp()` require special care when adding columns to existing large tables.

Safer pattern:

```sql
ALTER TABLE app.events
ADD COLUMN first_seen_at timestamptz;

ALTER TABLE app.events
ALTER COLUMN first_seen_at SET DEFAULT clock_timestamp();
```

Then backfill existing rows in controlled batches if historical values are required.

## 3.8.15 Backfill Pattern

Large column backfills should follow:

Batch -> Commit -> Measure -> Continue / Throttle / Pause.

Example pattern:

```sql
UPDATE app.orders
SET fulfillment_state = 'pending'
WHERE fulfillment_state IS NULL
  AND id >= 100000
  AND id < 110000;
```

Operational controls:

- batch by primary key or another stable ordering column;
- commit between batches;
- measure WAL generation, replica lag, CDC lag, CPU, I/O, and application latency;
- pause when abort thresholds are reached;
- preserve a roll-forward path.

## 3.8.16 Nullability

Nullability is part of the data contract.

Use `NULL` when the value is unknown, inapplicable, or intentionally absent. Use `NOT NULL` when the business rule requires a value for every row.

Do not add `NOT NULL` to large existing tables casually. Validate data first and plan the lock and scan behavior for the PostgreSQL version in use.

## 3.8.17 Adding NOT NULL Safely

A production pattern for an existing large table is:

1. Add the column as nullable.
2. Deploy application writes for the column.
3. Backfill existing rows in batches.
4. Add and validate a supporting check when appropriate.
5. Apply `SET NOT NULL` after data is proven valid.

The exact lock and scan behavior is version-sensitive. Validate against the target PostgreSQL version before execution.

## 3.8.18 Changing a Column Type

Changing a column's data type can rewrite the table, rebuild dependent indexes, affect constraints, and break applications or CDC consumers.

```sql
ALTER TABLE app.orders
ALTER COLUMN amount TYPE numeric(12,2)
USING amount::numeric(12,2);
```

Before changing type:

- prove all existing values can convert safely;
- inspect defaults and constraints that reference the column;
- inspect indexes, views, functions, publications, and application code;
- estimate lock duration, rewrite size, WAL, and replica lag;
- prepare rollback or roll-forward.

## 3.8.19 Rename Columns

Column renames can break application SQL, ORM mappings, BI reports, views, functions, logical replication consumers, and exports.

```sql
ALTER TABLE app.orders
RENAME COLUMN state TO fulfillment_state;
```

Prefer expand-and-contract when external consumers cannot change atomically:

1. Add the new column.
2. Dual-write or derive values.
3. Migrate readers.
4. Validate parity.
5. Retire the old column after an observation window.

## 3.8.20 Dropping Columns

Dropping a column is destructive metadata change. It removes access to the column and can invalidate dependent objects.

```sql
ALTER TABLE app.orders
DROP COLUMN legacy_code;
```

Use `CASCADE` only after explicit dependency review and recovery validation.

```sql
-- Destructive: requires dependency inventory and approved recovery plan.
ALTER TABLE app.orders
DROP COLUMN legacy_code CASCADE;
```

## 3.8.21 Generated Columns

A generated column is computed from other columns. Current PostgreSQL supports generated columns as a first-class table feature.

```sql
CREATE TABLE app.order_lines (
    order_line_id bigint GENERATED ALWAYS AS IDENTITY,
    quantity integer NOT NULL,
    unit_price numeric(12,2) NOT NULL,
    line_total numeric(12,2) GENERATED ALWAYS AS (quantity * unit_price) STORED
);
```

Use generated columns when the value must remain derived from row data and direct writes should not override it.

## 3.8.22 Defaults vs Generated Columns

Defaults and generated columns solve different problems.

| Feature | Default | Generated column |
| --- | --- | --- |
| When evaluated | Insert when value is omitted | When row is written or read, depending on kind |
| Can reference other columns | No | Yes, with restrictions |
| Can be overridden directly | Usually yes | No, except `DEFAULT` keyword |
| Can use volatile functions | Defaults may use volatile expressions | Generation expression must be immutable |
| Typical use | Initial value | Derived value |

## 3.8.23 Generated Column Restrictions

Generated column behavior is version-sensitive. In current PostgreSQL documentation:

- generation expressions must use immutable functions;
- generation expressions cannot use subqueries;
- a generated column cannot reference another generated column;
- a generated column cannot have a default or identity definition;
- a generated column cannot be part of a partition key;
- inheritance and partitioning impose generation-status compatibility rules.

Validate target-version behavior before using generated columns in migrations or cross-version restore workflows.

## 3.8.24 Stored vs Virtual Generated Columns

Current PostgreSQL documentation distinguishes stored and virtual generated columns. Stored generated columns occupy storage and are computed when rows are written. Virtual generated columns occupy no storage and are computed when rows are read.

Do not assume all supported PostgreSQL versions provide the same generated-column options. Older supported versions may only support stored generated columns.

## 3.8.25 Generated Columns and Replication

Generated columns can affect logical replication, CDC, and downstream schemas.

Production checklist:

- verify whether the generated column appears in publication output for the target version and configuration;
- confirm downstream consumers understand derived-column semantics;
- validate restore and migration behavior;
- test partitioned-table behavior if partitions define different generation expressions.

## 3.8.26 Catalog Inspection

Use catalog inspection for evidence, not as a substitute for documented DDL.

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    a.attname AS column_name,
    pg_catalog.format_type(a.atttypid, a.atttypmod) AS data_type,
    a.attnotnull AS not_null,
    a.attgenerated AS generated_kind,
    pg_get_expr(d.adbin, d.adrelid) AS default_expression
FROM pg_attribute a
JOIN pg_class c
    ON c.oid = a.attrelid
JOIN pg_namespace n
    ON n.oid = c.relnamespace
LEFT JOIN pg_attrdef d
    ON d.adrelid = a.attrelid
   AND d.adnum = a.attnum
WHERE n.nspname = 'app'
  AND c.relkind IN ('r', 'p')
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY n.nspname, c.relname, a.attnum;
```

Catalog columns and meanings can evolve. Prefer documented functions such as `format_type()` and `pg_get_expr()` when rendering internal metadata.

## 3.8.27 Column Dependency Review

Before changing a column, inventory dependencies:

```sql
SELECT
    pg_describe_object(d.classid, d.objid, d.objsubid) AS dependent_object,
    d.deptype
FROM pg_depend d
WHERE d.refobjid = 'app.orders'::regclass
  AND d.refobjsubid = (
      SELECT attnum
      FROM pg_attribute
      WHERE attrelid = 'app.orders'::regclass
        AND attname = 'legacy_code'
        AND NOT attisdropped
  )
ORDER BY dependent_object;
```

Treat dependency output as evidence requiring review. Do not automatically drop dependent objects from a catalog query.

## 3.8.28 SQL Safety Classification

| Operation | Risk class | Notes |
| --- | --- | --- |
| Add nullable column | State changing | Usually lower risk but still requires lock and app compatibility checks. |
| Set default | State changing | Future rows only; validate expression volatility. |
| Backfill values | State changing | Batch, commit, measure, and throttle. |
| Set `NOT NULL` | State changing | Validate scan and lock behavior for target version. |
| Change type | High impact | May rewrite table and affect dependent objects. |
| Rename column | High impact | Application and downstream compatibility risk. |
| Drop column | Destructive | Requires dependency inventory and recovery validation. |
| Drop column `CASCADE` | Critical destructive | Requires explicit authorization and blast-radius review. |

## 3.8.29 Monitoring

During column changes, monitor blocked and blocking sessions, long-running transactions, DDL duration, WAL generation, replica replay lag, logical replication slot lag, CDC consumer lag, table and index growth, autovacuum delay, application error rate, and application P95/P99 latency.

## 3.8.30 Alerting

Alert when a column migration is waiting on locks beyond the planned threshold, a backfill exceeds WAL or lag thresholds, transitional state persists beyond the approved window, application errors increase after a column contract change, or CDC lag exceeds abort criteria.

## 3.8.31 Failure Scenario - Default Assumed to Backfill Existing Rows

Symptom: new writes behave correctly, but existing rows still contain `NULL`.

Root cause: default changes apply to future writes and do not repair historical data.

Recovery:

1. Confirm affected rows.
2. Backfill in bounded batches.
3. Validate row counts and application behavior.
4. Add constraints only after data is correct.

## 3.8.32 Failure Scenario - Type Change Rewrites a Hot Table

Symptom: DDL holds locks, replicas lag, WAL spikes, and application latency increases.

Immediate mitigation:

- cancel or terminate only the migration session if safe;
- confirm lock release;
- verify replica recovery;
- reschedule with a safer expand-and-contract or shadow-column approach.

## 3.8.33 Failure Scenario - Generated Column Breaks Restore or Downstream Consumers

Symptom: restore, replication, or CDC validation fails after a generated-column deployment.

Response:

- confirm target PostgreSQL version support;
- inspect generation expressions and partition behavior;
- validate publication and downstream schema expectations;
- roll forward with compatible schema or rollback to the prior contract.

## 3.8.34 Production Change Runbook

Purpose: safely modify production columns.

Scope: data type, default, nullability, generated column, rename, and drop operations.

Required privileges: table ownership or controlled deployment role with sufficient privileges.

Preflight:

- verify target database, schema, table, and column;
- inspect dependencies;
- classify operation as read-only, state-changing, high-impact, or destructive;
- estimate locks, runtime, WAL, storage, and replication impact;
- verify backups and restore path;
- set `lock_timeout` and `statement_timeout`;
- define abort thresholds.

Execution:

- apply the lowest-risk compatible DDL;
- run large backfills in bounded batches;
- monitor locks, lag, errors, and latency;
- pause when thresholds are exceeded.

Validation:

- verify schema definition;
- verify row counts and data correctness;
- verify application behavior;
- verify replicas and CDC consumers;
- observe for the agreed window;
- reconcile schema changes in Git or the migration system.

## 3.8.35 Managed PostgreSQL Boundaries

Core column semantics apply across PostgreSQL platforms, but managed services can differ in superuser privileges, extension availability for UUID generation or custom types, storage and I/O scaling, backup and PITR controls, replication and CDC implementation, maintenance windows, parameter management, and observability surfaces.

Validate provider-specific operational controls before executing high-impact column changes on Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL, Azure Database for PostgreSQL, Google Cloud SQL for PostgreSQL, or PostgreSQL on Kubernetes.

## 3.8.36 SRE / DBRE Production Standard

Column administration is production contract management. A column change is complete only when the database definition, data values, application behavior, dependencies, replication, monitoring, recovery path, and Git/migration state all agree.

## 3.8.37 Key Takeaways

1. Choose data types for semantics, not habit.
2. Defaults affect future writes; they are not historical backfills.
3. Generated columns are derived values with version-sensitive restrictions.
4. Type changes, renames, and drops require dependency and application review.
5. Large backfills should be batched, measured, and throttled.
6. Destructive column operations require explicit approval and proven recovery.
