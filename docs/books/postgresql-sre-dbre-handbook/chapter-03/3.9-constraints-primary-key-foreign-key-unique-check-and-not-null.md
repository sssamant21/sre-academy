## 3.9.1 Constraints as a Reliability Boundary

PostgreSQL constraints enforce rules about data stored in the database. In production systems, they form an important reliability boundary between every writer and trusted data: applications, APIs, ETL, CDC, batch jobs, migrations, and administrative SQL all eventually meet PostgreSQL's integrity rules.

```text
Applications / APIs / ETL / CDC / Batch / Migrations / Admin SQL
        │
        ▼
   PostgreSQL constraints
        │
        ├── NOT NULL
        ├── CHECK
        ├── UNIQUE
        ├── PRIMARY KEY
        ├── FOREIGN KEY
        └── EXCLUDE
        │
        ▼
   Trusted Data
```

Application validation and database constraints solve complementary problems. Application validation improves workflows and user experience. Database constraints protect invariants regardless of which writer reaches the database.

## 3.9.2 Constraint Types

The principal PostgreSQL constraint mechanisms are:

| Constraint | Purpose |
| --- | --- |
| `NOT NULL` | Requires a column value. |
| `CHECK` | Enforces a row-level Boolean condition. |
| `UNIQUE` | Prevents duplicate key combinations. |
| `PRIMARY KEY` | Establishes unique, non-null row identity. |
| `FOREIGN KEY` | Enforces relationships between tables. |
| `EXCLUDE` | Prevents operator-defined conflicting rows. |

Production schemas commonly combine several constraint types.

## 3.9.3 PostgreSQL Version Awareness

Constraint capabilities evolve across PostgreSQL releases. This matters particularly for `NOT VALID`, `NULLS NOT DISTINCT`, `ALTER TABLE` behavior, constraint enforcement options, catalog attributes, and lock behavior.

Before applying an advanced constraint migration:

```sql
SHOW server_version;
```

Production rule: validate the exact syntax, lock behavior, and supported constraint features against the deployed PostgreSQL major version. Do not assume procedures developed for PostgreSQL 18 work identically on PostgreSQL 14, 15, 16, or 17.

## 3.9.4 NOT NULL

Example:

```sql
CREATE TABLE app.customer (
    customer_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    customer_name text NOT NULL,
    created_at timestamptz
        NOT NULL
        DEFAULT now()
);
```

`NOT NULL` expresses that absence is not a valid state. A production schema should deliberately distinguish required values from optional values. Do not make columns nullable merely because application code currently supplies them. Nullability is part of the database contract.

## 3.9.5 NULL Semantics

SQL `NULL` represents unknown or absent information. It is not equivalent to an empty string, zero, `false`, or the literal string `'NULL'`. This distinction becomes especially important with constraints.

## 3.9.6 CHECK Constraints

Example:

```sql
CREATE TABLE app.product (
    product_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    product_name text NOT NULL,
    price numeric(12,2) NOT NULL,
    CONSTRAINT chk_product_price
        CHECK (price > 0)
);
```

The constraint protects `price > 0` regardless of which application or process inserts the row.

## 3.9.7 CHECK and NULL

A crucial PostgreSQL rule is that `CHECK (price > 0)` does not itself prohibit `price = NULL`, because a check constraint is violated when its expression evaluates to false; a null result does not constitute the same violation.

If price must exist and must be positive:

```sql
price numeric(12,2)
    NOT NULL
    CHECK (price > 0)
```

Use `NOT NULL` to enforce presence and `CHECK` to enforce the valid domain when both are required.

## 3.9.8 Multi-Column CHECK Constraints

A `CHECK` condition can reference multiple columns of the same row.

```sql
CREATE TABLE app.subscription (
    subscription_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    start_date date NOT NULL,
    end_date date,
    CONSTRAINT chk_subscription_dates
        CHECK (
            end_date IS NULL
            OR end_date >= start_date
        )
);
```

This enforces that `end_date` is absent or greater than or equal to `start_date`.

## 3.9.9 CHECK Constraint Design Rule

`CHECK` constraints should normally represent invariants derived from the row being constrained. Cross-table relationships belong in foreign keys, not check expressions that depend on independently changing data elsewhere. PostgreSQL expects check conditions to continue to hold for stored rows.

## 3.9.10 Constraint Naming

Use deterministic names. Recommended conventions include:

```text
pk_<table>
fk_<table>_<parent>
uq_<table>_<business_key>
chk_<table>_<rule>
ex_<table>_<rule>
```

Examples include `pk_orders`, `fk_orders_customer`, `uq_customer_external_id`, and `chk_payment_amount`. Good naming improves incident response, migrations, automation, monitoring, dependency analysis, and error interpretation.

## 3.9.11 UNIQUE Constraints

Example:

```sql
CREATE TABLE app.customer (
    customer_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    email text,
    CONSTRAINT uq_customer_email
        UNIQUE (email)
);
```

PostgreSQL normally implements a unique constraint with a unique B-tree index. Do not create an additional identical unique index merely because the table already has a `UNIQUE` constraint.

## 3.9.12 UNIQUE and NULL

By default, null values are normally treated as distinct for uniqueness purposes. Two null email values can satisfy an ordinary unique constraint. Where supported by the deployed PostgreSQL version, this can be changed:

```sql
CONSTRAINT uq_customer_external_id
    UNIQUE NULLS NOT DISTINCT (external_id)
```

Explicitly define the required NULL semantics when nullable columns participate in business uniqueness.

## 3.9.13 Composite UNIQUE Constraints

Example:

```sql
CREATE TABLE app.user_permission (
    user_id bigint NOT NULL,
    resource_id bigint NOT NULL,
    permission text NOT NULL,
    CONSTRAINT uq_user_permission
        UNIQUE (user_id, resource_id, permission)
);
```

Individual values can repeat while the combination remains unique.

## 3.9.14 PRIMARY KEY

Example:

```sql
CREATE TABLE app.orders (
    order_id bigint
        GENERATED ALWAYS AS IDENTITY,
    customer_id bigint NOT NULL,
    CONSTRAINT pk_orders
        PRIMARY KEY (order_id)
);
```

A primary key provides uniqueness, non-nullability, designated row identity, and a supporting unique index. A table has one primary-key constraint, although that constraint can contain multiple columns.

## 3.9.15 Composite Primary Keys

Example:

```sql
CREATE TABLE app.order_line (
    order_id bigint NOT NULL,
    line_number integer NOT NULL,
    product_id bigint NOT NULL,
    quantity integer NOT NULL,
    CONSTRAINT pk_order_line
        PRIMARY KEY (order_id, line_number)
);
```

Composite identity such as `(order_id, line_number)` affects foreign keys, index width, joins, CDC, logical replication, application APIs, and storage.

## 3.9.16 PRIMARY KEY vs UNIQUE

A primary key is unique, non-null, and designated as row identity. A unique constraint represents an additional uniqueness invariant. A table can have multiple unique constraints but only one primary-key constraint.

## 3.9.17 FOREIGN KEY

Example parent:

```sql
CREATE TABLE app.customer (
    customer_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    customer_name text NOT NULL
);
```

Example child:

```sql
CREATE TABLE app.orders (
    order_id bigint
        GENERATED ALWAYS AS IDENTITY
        PRIMARY KEY,
    customer_id bigint NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES app.customer(customer_id)
);
```

PostgreSQL prevents non-null child references from pointing to nonexistent parent identities according to the foreign-key match semantics.

## 3.9.18 Referenced-Key Requirements

A foreign key must reference an appropriate unique identity, commonly a primary key or unique constraint. Qualifying non-partial unique indexes can also satisfy PostgreSQL's referenced-key requirements in applicable configurations. The fundamental requirement is that PostgreSQL can uniquely identify the referenced row.

## 3.9.19 Foreign-Key NULL Semantics

The default foreign-key behavior is `MATCH SIMPLE`. For a simple one-column foreign key, a null referencing value does not require a matching parent row. Therefore a nullable `customer_id bigint` with a foreign key does not make the relationship mandatory. If every order must have a customer, `customer_id bigint NOT NULL` is also required.

## 3.9.20 Composite Foreign Keys and MATCH FULL

Composite foreign keys introduce additional NULL semantics. `MATCH SIMPLE` is the default. `MATCH FULL` means either all referencing columns are null or the complete key must satisfy the relationship. For key architecture such as `(region_id, customer_id)`, evaluate `MATCH FULL` together with appropriate `NOT NULL` requirements when partial-null combinations must be prohibited.

## 3.9.21 Foreign Keys Do Not Automatically Index the Child

Given:

```sql
FOREIGN KEY (customer_id)
REFERENCES app.customer(customer_id)
```

PostgreSQL does not automatically create:

```sql
CREATE INDEX idx_orders_customer_id
ON app.orders(customer_id);
```

Review whether such an index is needed for parent deletes, parent key updates, child lookups, joins, referential checks, and large child tables. Do not blindly index every foreign key: indexes consume storage, write I/O, WAL, CPU, vacuum work, and cache.

## 3.9.22 Referential Actions

PostgreSQL supports referential actions including `NO ACTION`, `RESTRICT`, `CASCADE`, `SET NULL`, and `SET DEFAULT`.

```sql
CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES app.customer(customer_id)
    ON DELETE RESTRICT
```

or:

```sql
ON DELETE CASCADE
```

These choices encode business behavior directly into the database.

## 3.9.23 NO ACTION vs RESTRICT

Do not treat `NO ACTION` and `RESTRICT` as purely stylistic synonyms. `NO ACTION` can participate in deferred checking when the foreign key is deferrable. `RESTRICT` prevents the referenced operation without the same deferral behavior. Choose deliberately.

## 3.9.24 SET DEFAULT

With `customer_id bigint DEFAULT 0` and `ON DELETE SET DEFAULT`, the resulting default value must still satisfy the foreign key. `SET DEFAULT` does not mean the operation always succeeds.

## 3.9.25 CASCADE Fan-Out

A customer with millions of orders and `ON DELETE CASCADE` can turn one parent delete into millions of child deletes, large transactions, WAL growth, index maintenance, dead tuples, long lock duration, replica lag, and expensive rollback. Before destructive operations, determine cascade fan-out across the entire dependency chain.

## 3.9.26 Deferrable Constraints

Selected PostgreSQL constraints can be declared deferrable. Potentially deferrable constraints include `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, and `EXCLUDE`. `NOT NULL` and `CHECK` are not deferrable in the same manner.

```sql
CONSTRAINT uq_example_code
    UNIQUE (code)
    DEFERRABLE INITIALLY DEFERRED
```

## 3.9.27 Immediate vs Deferred

A deferrable constraint can use `INITIALLY IMMEDIATE` or `INITIALLY DEFERRED`. Within a transaction:

```sql
SET CONSTRAINTS ALL DEFERRED;
SET CONSTRAINTS uq_example_code DEFERRED;
```

may change when applicable checks occur.

## 3.9.28 Deferred Constraint Failure at COMMIT

With deferred constraints, individual statements can succeed while a temporary violation exists. The final check may occur at `COMMIT`, and the transaction can fail then. Applications must therefore treat `COMMIT` itself as an operation that can fail.

## 3.9.29 Deferrable Constraints and ON CONFLICT

Deferrability can interact with application upsert architecture. Do not assume a deferrable uniqueness or primary-key constraint can always serve as the conflict arbiter for `INSERT ... ON CONFLICT ...`. Applications relying heavily on `ON CONFLICT` should verify the chosen constraint and index architecture before deployment.

## 3.9.30 EXCLUDE Constraints

Exclusion constraints prevent conflicting rows according to specified operators. Classic examples include overlapping reservations, temporal ranges, scheduling conflicts, spatial relationships, and other operator-defined incompatibility rules. Their operator-class and indexing requirements should be evaluated carefully.

## 3.9.31 Adding Constraints to Existing Tables

Adding a constraint during table creation and adding one to a multi-terabyte production table are operationally different. Before adding a constraint, determine PostgreSQL version, constraint type, table size, existing violations, required locks, validation requirements, index requirements, I/O headroom, application traffic, replication health, and rollback strategy.

## 3.9.32 Constraint Deployment Preflight

Start with:

```sql
SHOW server_version;
```

Measure the table:

```sql
SELECT
    pg_size_pretty(pg_table_size('app.orders')) AS table_storage,
    pg_size_pretty(pg_indexes_size('app.orders')) AS indexes,
    pg_size_pretty(pg_total_relation_size('app.orders')) AS total;
```

Inspect existing constraints:

```sql
SELECT
    conname,
    contype,
    convalidated,
    condeferrable,
    condeferred,
    pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'app.orders'::regclass
ORDER BY conname;
```

## 3.9.33 NOT VALID

For supported constraint types and PostgreSQL versions, `NOT VALID` can separate constraint installation from validation of historical rows.

```sql
ALTER TABLE app.orders
ADD CONSTRAINT chk_orders_amount
CHECK (amount >= 0)
NOT VALID;
```

Historical validation is postponed, while applicable new or changed rows are protected. This is particularly valuable for large existing tables.

## 3.9.34 NOT VALID Is Version-Sensitive

Do not assume `NOT VALID` applies uniformly to every constraint type on every PostgreSQL release. Established large-table use cases include `CHECK` and `FOREIGN KEY`. Newer PostgreSQL versions provide additional constraint-management capabilities. Check exact PostgreSQL major-version documentation before relying on `NOT VALID` for a particular constraint type.

## 3.9.35 NOT VALID Is Transitional State

An unvalidated constraint should normally represent deployment in progress, not a permanent forgotten state. After adding the constraint: install, protect new changes, find historical violations, remediate, validate, and verify. Track validation as part of deployment completion.

## 3.9.36 Finding Unvalidated Constraints

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    con.conname AS constraint_name,
    con.contype,
    pg_get_constraintdef(con.oid) AS definition
FROM pg_constraint AS con
JOIN pg_class AS c
    ON c.oid = con.conrelid
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE NOT con.convalidated
ORDER BY n.nspname, c.relname, con.conname;
```

This query belongs in periodic DBRE integrity audits.

## 3.9.37 VALIDATE CONSTRAINT

After historical violations have been addressed:

```sql
ALTER TABLE app.orders
VALIDATE CONSTRAINT chk_orders_amount;
```

This proves that existing data satisfies the constraint. The operational model is: add `NOT VALID`, immediately protect applicable new changes, clean historical data, validate, and verify.

## 3.9.38 Validation Scan vs Table Rewrite

Do not confuse validation with rewriting table storage. `VALIDATE CONSTRAINT` reads and verifies data; it does not imply a table rewrite. Validation can nevertheless consume significant I/O, CPU, buffer-cache capacity, and storage bandwidth, especially for very large tables.

## 3.9.39 Validation Locking

Constraint validation can generally use weaker locking than some direct constraint-addition operations, but exact locks depend on constraint type, `ALTER TABLE` operation, referencing and referenced tables, and PostgreSQL major version. Do not assume `VALIDATE CONSTRAINT` means no locking.

## 3.9.40 Large Foreign-Key Deployment

For a large table:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id)
REFERENCES app.customer(customer_id)
NOT VALID;
```

Detect historical orphan rows:

```sql
SELECT
    o.customer_id,
    count(*) AS orphan_rows
FROM app.orders AS o
LEFT JOIN app.customer AS c
    ON c.customer_id = o.customer_id
WHERE o.customer_id IS NOT NULL
  AND c.customer_id IS NULL
GROUP BY o.customer_id
ORDER BY orphan_rows DESC
LIMIT 100;
```

After remediation:

```sql
ALTER TABLE app.orders
VALIDATE CONSTRAINT fk_orders_customer;
```

This can be substantially safer than discovering historical integrity problems during a direct validation operation.

## 3.9.41 Concurrent UNIQUE Constraint Deployment

Large busy tables require special consideration when introducing uniqueness. PostgreSQL can support the pattern: create a unique index concurrently, verify it, then attach it as a unique constraint.

```sql
CREATE UNIQUE INDEX CONCURRENTLY
    ux_customer_external_id
ON app.customer(external_id);

ALTER TABLE app.customer
ADD CONSTRAINT uq_customer_external_id
UNIQUE USING INDEX ux_customer_external_id;
```

This pattern can reduce write-blocking during index construction.

## 3.9.42 Concurrent Primary-Key Deployment

A similar approach can be evaluated for introducing a primary key using an appropriate qualifying unique index: validate intended primary-key columns, create an appropriate unique index concurrently, verify the index, attach it as the primary key, and verify constraints. Exact prerequisites and locking must be checked against the PostgreSQL version. Primary-key columns must also satisfy non-nullability requirements.

## 3.9.43 Duplicate Detection Before Unique Enforcement

Before building uniqueness:

```sql
SELECT
    external_id,
    count(*)
FROM app.customer
GROUP BY external_id
HAVING count(*) > 1
ORDER BY count(*) DESC;
```

Find duplicates before the production change window where practical. Define uniqueness semantics, find duplicates, remediate, build the unique index, verify, and attach the constraint. Nullable business keys require explicit NULL-semantics analysis.

## 3.9.44 Concurrent Index Failure

`CREATE INDEX CONCURRENTLY` can fail and leave an index that is not valid for normal use. Do not assume an index exists because it successfully built.

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS index_name,
    i.indisvalid,
    i.indisready
FROM pg_index AS i
JOIN pg_class AS c
    ON c.oid = i.indexrelid
JOIN pg_namespace AS n
    ON n.oid = c.relnamespace
WHERE n.nspname = 'app'
  AND c.relname = 'ux_customer_external_id';
```

Do not attach an invalid index to a production constraint.

## 3.9.45 Constraint and Index Dependencies

Primary keys, unique constraints, and exclusion constraints have supporting index architecture. Foreign keys reference a unique identity, but the child-side index is not automatic. Indexes supporting logical constraints should not be managed as unrelated performance objects.

## 3.9.46 Do Not Drop Constraint-Owned Indexes Blindly

Before `DROP INDEX`, determine whether the index supports a primary key, unique constraint, or exclusion constraint. If the logical goal is to remove or alter a constraint, manage the constraint through PostgreSQL dependency architecture instead of trying to bypass it.

## 3.9.47 Constraint Catalog Architecture

The key catalog is `pg_constraint`.

```sql
SELECT
    conname,
    contype,
    convalidated,
    condeferrable,
    condeferred,
    pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'app.orders'::regclass
ORDER BY conname;
```

Catalog capabilities can evolve across PostgreSQL versions, so advanced automation should be version-aware.

## 3.9.48 Constraint Violation Observability

Constraint failures can reveal application regressions, race conditions, bad ETL, migration defects, retry/idempotency problems, unexpected nulls, or referential ordering issues. Common error classes include duplicate key, foreign-key violation, check violation, and not-null violation. These errors should be observable through application and database monitoring.

## 3.9.49 Do Not Alert on Every Violation

A constraint violation does not automatically equal an incident. An application may deliberately attempt an insert and handle a uniqueness conflict. Prefer monitoring violation rate, rate deviation, critical constraint, affected service, rollback rate, user impact, and pipeline failure. Alert on abnormal behavior rather than isolated expected events.

## 3.9.50 Failure Scenario — Application-Only Uniqueness

Two sessions can both check for absent data and then both insert if the database does not enforce uniqueness. Prevent this with a database uniqueness constraint:

```sql
ALTER TABLE app.customer
ADD CONSTRAINT uq_customer_external_id
UNIQUE (external_id);
```

Database uniqueness protects against concurrency races that application prechecks alone cannot reliably eliminate.

## 3.9.51 Failure Scenario — CHECK Allows Unexpected NULL

Schema:

```sql
price numeric(12,2)
    CHECK (price > 0)
```

Expectation: price is always positive. Actual permitted state: `price = NULL`. Correct design when presence is mandatory:

```sql
price numeric(12,2)
    NOT NULL
    CHECK (price > 0)
```

## 3.9.52 Failure Scenario — Orphaned Rows

Detection:

```sql
SELECT
    o.order_id,
    o.customer_id
FROM app.orders AS o
LEFT JOIN app.customer AS c
    ON c.customer_id = o.customer_id
WHERE o.customer_id IS NOT NULL
  AND c.customer_id IS NULL;
```

Possible causes include no foreign key, a constraint that remained `NOT VALID`, historical bad data, migration bypass, or incorrect loading order. Use referential constraints where strict integrity is required.

## 3.9.53 Failure Scenario — Missing Foreign-Key Index

A parent delete or update can require an expensive referential check against a huge child table when no useful child index exists. This can lengthen the transaction and affect locks or latency. Foreign-key indexing belongs in production schema review.

## 3.9.54 Failure Scenario — Massive CASCADE

Before deleting a parent, count direct children:

```sql
SELECT count(*)
FROM app.orders
WHERE customer_id = 12345;
```

Direct children may not tell the complete story. Assess the full cascade path through child, grandchild, and additional dependency chains.

## 3.9.55 Failure Scenario — Validation Saturates Storage

`VALIDATE CONSTRAINT` can produce a large sequential verification workload. Read I/O rises, storage latency rises, and application latency can increase. Monitor storage latency, IOPS, throughput, CPU, buffer pressure, application latency, locks, and replica lag. Do not reflexively terminate the validating backend without evaluating transaction and change-management consequences.

## 3.9.56 Failure Scenario — Forgotten NOT VALID

A deployment may add:

```sql
ALTER TABLE app.orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id)
REFERENCES app.customer(customer_id)
NOT VALID;
```

Months later, `convalidated = false`. Historical integrity was never established. Deployment completion should require validation or an explicitly accepted exception.

## 3.9.57 Failure Scenario — Concurrent Index Build Fails

`CREATE UNIQUE INDEX CONCURRENTLY` can fail because of duplicate data, interruption, or another build failure. An invalid index can remain, and automation may incorrectly assume success because the object exists. Always verify index validity before the next migration step.

## 3.9.58 Failure Scenario — Deferred Failure at COMMIT

Deferred constraints can allow temporary violations during a transaction and then fail at `COMMIT`. Applications using deferred constraints must handle commit errors explicitly.

## 3.9.59 Foreign-Table Warning

Constraints declared for foreign-table architectures should not automatically be assumed to provide the same PostgreSQL-local enforcement guarantees as constraints on ordinary local tables. Before relying on them, understand the FDW behavior, remote database enforcement, and planner assumptions. Treat foreign-table integrity as a separate architecture review.

## 3.9.61 Production Preflight Runbook

Before significant constraint DDL:

```sql
SHOW server_version;

SELECT
    pg_size_pretty(pg_table_size('app.orders')) AS table_storage,
    pg_size_pretty(pg_indexes_size('app.orders')) AS indexes,
    pg_size_pretty(pg_total_relation_size('app.orders')) AS total;

SELECT
    conname,
    contype,
    convalidated,
    condeferrable,
    condeferred,
    pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'app.orders'::regclass;

SELECT
    pid,
    usename,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

SELECT
    pid,
    pg_blocking_pids(pid) AS blocking_pids,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Evaluate existing invalid data, duplicate keys, orphan rows, table size, write rate, required locks, validation scan, index strategy, cascade fan-out, I/O headroom, replication, rollback, and monitoring.

## 3.9.63 Monitoring Baseline

Production constraint monitoring should include runtime violations and rollbacks, schema state such as `NOT VALID` constraints and dependencies, and change signals such as DDL locks, validation work, index validity, and I/O impact.

Recommended signals include duplicate-key error rate, foreign-key violation rate, check violation rate, not-null violation rate, transaction rollback rate, unvalidated constraints, invalid indexes, DDL lock waits, long validation operations, storage latency, application latency, and replica lag.

## 3.9.64 Common Production Anti-Patterns

Common anti-patterns include integrity only in application code, `CHECK` used without understanding nulls, assuming a nullable foreign key makes a relationship mandatory, creating foreign keys without child-index review, selecting `CASCADE` automatically, assuming `SET DEFAULT` always succeeds, enabling deferrability without application awareness, adding huge constraints without preflight, using `NOT VALID` and forgetting validation, treating validation as zero-cost, confusing validation with table rewrite, adding unique constraints directly when concurrent index strategy is more appropriate, assuming concurrent index success because the object exists, treating constraint-owned indexes as unrelated, indexing every foreign key blindly, and ignoring PostgreSQL-version differences.

## 3.9.68 Key Takeaways

1. PostgreSQL constraints are part of the database reliability boundary.
2. Application validation complements rather than replaces database integrity enforcement.
3. `NOT NULL` expresses mandatory data presence.
4. `CHECK` constraints protect row-level invariants.
5. `CHECK` alone does not prohibit nulls.
6. `UNIQUE` constraints protect business uniqueness.
7. NULL behavior under `UNIQUE` must be deliberately designed.
8. Primary keys provide designated unique, non-null row identity.
9. Foreign keys enforce cross-table relationships.
10. A foreign key alone does not necessarily make participation mandatory.
11. Composite foreign keys require explicit consideration of match semantics.
12. PostgreSQL does not automatically create child-side foreign-key indexes.
13. Foreign-key indexes should be workload-driven rather than blindly created.
14. Referential actions encode important business behavior.
15. `SET DEFAULT` does not bypass referential integrity.
16. Cascading operations can produce very large transactions.
17. Deferrable constraints can move integrity failures to transaction commit.
18. Application upsert architecture must account for deferrable uniqueness behavior.
19. Exclusion constraints support operator-defined conflict rules.
20. Large-table constraint deployment is operational work, not merely schema syntax.
21. `NOT VALID` can separate constraint installation from historical validation for supported constraints.
22. `NOT VALID` capabilities are PostgreSQL-version-sensitive.
23. Unvalidated constraints should normally be transitional state.
24. `VALIDATE CONSTRAINT` is a real production workload.
25. Constraint validation is not synonymous with a table rewrite.
26. Exact locking must be evaluated for the constraint operation and PostgreSQL version.
27. Large unique or primary-key deployments should evaluate concurrent index construction followed by `USING INDEX`.
28. Concurrent index builds must be verified before subsequent migrations.
29. Duplicate and orphan detection should occur before production constraint enforcement where practical.
30. Constraint-owned indexes must be managed through PostgreSQL dependency architecture.
31. Constraint violation rates can reveal application and pipeline defects.
32. Constraint monitoring should focus on abnormal rates and user impact.
33. Cascade fan-out must be assessed across the full dependency chain.
34. Foreign-table constraints require separate enforcement analysis.
35. Production constraint changes require preflight, monitoring, rollback, and post-change verification.
36. Data integrity engineering is a core PostgreSQL SRE/DBRE responsibility.
