## 4.1.1 Purpose and Scope

PostgreSQL storage architecture is the layer that translates logical database objects—databases, schemas, tables, indexes, sequences, materialized views, and other relations—into persistent physical storage.

For an application developer, storage may appear simply as:

Database
   ↓
Tables
   ↓
Rows

For an SRE or DBRE, the production model is considerably broader:

                    PostgreSQL Storage
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   Data Structures       WAL & Temp       Infrastructure
        │                  │                  │
     Heaps                WAL              Filesystems
     Indexes          Temp files           Volumes
     TOAST           Replication            IOPS
     FSM / VM          retention          Throughput
     Tablespaces                          Latency
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ▼
                       Reliability

Storage failures can directly affect:

database availability;
transaction durability;
query latency;
replication;
recovery;
maintenance;
backup operations;
application SLOs.

Storage engineering is therefore not simply disk allocation. It is a continuous discipline involving architecture, capacity, performance, forecasting, observability, maintenance, recovery, and automation.

## 4.1.2 PostgreSQL Storage Reliability Model

A production PostgreSQL storage system should be evaluated across three dimensions:

                 PostgreSQL Storage Reliability
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
       CAPACITY           PERFORMANCE         OPERATIONS
          │                   │                   │
      Used space             IOPS                 WAL
      Free space          Throughput             VACUUM
      Growth rate          Latency               REINDEX
      Headroom             Queueing              Backups
      Forecasting          I/O waits             Temp files
          │                   │                   │
          └───────────────────┼───────────────────┘
                              ▼
                         RELIABILITY

These dimensions are related but not interchangeable.

A PostgreSQL server can have:

60% storage free

and still suffer severe performance degradation because storage latency or IOPS are saturated.

Conversely, a high-performance storage device can still cause an availability incident if capacity is exhausted.

Therefore:

Storage capacity and storage performance must be monitored and managed independently.

## 4.1.3 Logical and Physical Storage

Applications interact with PostgreSQL through a logical hierarchy:

PostgreSQL Cluster
│
├── Database
│   │
│   ├── Schema
│   │   ├── Table
│   │   ├── Index
│   │   ├── Sequence
│   │   └── Materialized View
│   │
│   └── ...
│
└── Database

The operating system does not store these objects using this logical hierarchy directly.

PostgreSQL maps logical objects into physical storage structures:

Logical PostgreSQL Object
           │
           ▼
     Catalog Metadata
           │
           ▼
      Relation Storage
           │
           ▼
         Forks
           │
           ▼
         Pages
           │
           ▼
     Physical Files
           │
           ▼
 Filesystem / Volume

Understanding this mapping is essential when troubleshooting storage growth, corruption, tablespace exhaustion, bloat, or I/O performance.

## 4.1.4 PostgreSQL Data Directory

The PostgreSQL data directory is commonly referenced through PGDATA.

A PostgreSQL database cluster in this context means a collection of databases managed by one PostgreSQL server instance. It should not be confused with a distributed computing cluster.

A typical data directory contains structures similar to:

PGDATA/
│
├── base/
├── global/
├── pg_commit_ts/
├── pg_dynshmem/
├── pg_logical/
├── pg_multixact/
├── pg_notify/
├── pg_replslot/
├── pg_serial/
├── pg_snapshots/
├── pg_stat/
├── pg_stat_tmp/
├── pg_subtrans/
├── pg_tblspc/
├── pg_twophase/
├── pg_wal/
├── pg_xact/
│
├── PG_VERSION
└── postmaster.pid

Important locations include:

Location	Purpose	Production concern
base/	Default tablespace database files	Database growth
global/	Cluster-wide relations	System integrity
pg_wal/	Write-ahead log	WAL retention/exhaustion
pg_tblspc/	Tablespace links	External filesystem capacity
pg_replslot/	Replication-slot state	WAL retention
pg_xact/	Transaction commit status	Critical metadata
pg_multixact/	Multi-transaction state	Transaction maintenance
pg_twophase/	Prepared transaction state	Long-lived prepared transactions

The exact contents vary by PostgreSQL version and configuration.

## 4.1.5 Configuration Files and PGDATA

Files such as:

postgresql.conf
pg_hba.conf
pg_ident.conf

are traditionally associated with the PostgreSQL data directory.

However, administrators must not assume that configuration files always reside inside PGDATA.

PostgreSQL permits configuration and data locations to differ.

For production troubleshooting, determine the actual configuration locations rather than editing whichever configuration file happens to exist in the data directory.

Useful inspection includes:

SHOW data_directory;

SHOW config_file;

SHOW hba_file;

SHOW ident_file;

This prevents a surprisingly common operational error: modifying the wrong PostgreSQL configuration file.

## 4.1.6 Database Physical Storage

For databases using the default tablespace, relation storage normally resides beneath:

$PGDATA/base/<database_oid>/

For example:

PGDATA/
└── base/
    ├── 1/
    ├── 5/
    ├── 16384/
    └── 24576/

These directory names correspond to internal database identifiers rather than database names.

The mapping can be inspected through:

SELECT
    oid,
    datname
FROM pg_database
ORDER BY oid;

For filesystem investigations, administrators must map identifiers back to PostgreSQL catalog objects before drawing conclusions about what is consuming storage.

## 4.1.7 Relations

PostgreSQL uses the concept of a relation for many storage-backed objects.

Examples include:

Tables
Indexes
Sequences
Materialized views
TOAST tables
System catalogs

A critical distinction is:

Relation OID
     │
     └── Logical/catalog identity

Physical relation identifier
     │
     └── relfilenumber

Do not assume:

relation OID == physical filename

A PostgreSQL operation can replace or rewrite the underlying physical relation while the logical object remains the same.

For production filesystem analysis, this distinction is important.

## 4.1.8 Relation Forks

A PostgreSQL relation can consist of several forks.

The principal forks are:

Fork	Purpose
Main	Actual table or index data
FSM	Free Space Map
VM	Visibility Map
Init	Initialization state for unlogged relations

A simplified representation:

Relation
│
├── Main Fork
│
├── Free Space Map
│
├── Visibility Map
│
└── Init Fork        ← where applicable

At the filesystem level this can resemble:

16384
16384_fsm
16384_vm

The supporting forks become particularly important when analyzing VACUUM behavior, free-space reuse, and index-only scans.

## 4.1.9 PostgreSQL Pages and Blocks

Relations are divided into fixed-size pages, commonly called blocks.

Standard PostgreSQL builds normally use:

BLCKSZ = 8192 bytes
       = 8 KiB

Page size is a compile-time characteristic, so 8 KiB should be treated as the standard/default build behavior rather than an immutable universal constant.

Conceptually:

Relation
│
├── Page 0
│   ├── Tuple
│   ├── Tuple
│   └── Tuple
│
├── Page 1
│   ├── Tuple
│   └── Tuple
│
└── Page N

Pages are fundamental to:

buffer management;
sequential scans;
index operations;
VACUUM;
checkpoints;
caching;
physical I/O.

Understanding page architecture is therefore foundational to PostgreSQL storage-performance analysis.

## 4.1.10 Relation File Segmentation

Large PostgreSQL relations are not represented by a single indefinitely growing operating-system file.

With standard PostgreSQL build parameters, relation forks are normally segmented into files of approximately 1 GiB.

For example:

16384
16384.1
16384.2
16384.3
16384.4

Therefore:

The size of one operating-system file does not necessarily represent the size of the PostgreSQL relation.

Use PostgreSQL's storage-size functions for database analysis rather than manually summing filesystem files.

## 4.1.11 Heap Storage

Ordinary PostgreSQL tables use heap storage.

Conceptually:

Table
  │
  ▼
Heap Relation
  │
  ├── Page
  │    ├── Tuple
  │    ├── Tuple
  │    └── Tuple
  │
  └── Page

PostgreSQL's MVCC architecture means an update commonly results in different tuple versions:

UPDATE
  │
  ├── Existing tuple version
  │
  └── New tuple version

PostgreSQL also provides optimizations such as Heap-Only Tuple updates when eligibility requirements are met.

Over time, obsolete tuple versions can become dead tuples.

This creates an important storage lifecycle:

INSERT / UPDATE / DELETE
          ↓
Tuple versions
          ↓
Dead tuples
          ↓
VACUUM
          ↓
Space becomes reusable

If cleanup and space reuse do not keep pace with workload behavior:

Heavy UPDATE/DELETE
        ↓
Dead tuples
        ↓
Increasing relation footprint
        ↓
Potential bloat
        ↓
Higher storage consumption
        ↓
More I/O
        ↓
Higher latency

MVCC is therefore directly connected to capacity management.

## 4.1.12 Index Storage

Indexes are independent relations and consume storage separately from table heaps.

For example:

orders
│
├── Heap
│
├── Primary-key index
│
├── customer_id index
│
├── created_at index
└── status index

A 500 GB heap does not imply that the table consumes only 500 GB.

Actual storage can include:

Heap
  +
Indexes
  +
TOAST
  +
Auxiliary forks

Indexes can themselves become a significant or dominant component of the database footprint.

This makes index design a capacity-management concern as well as a query-performance concern.

## 4.1.13 TOAST Storage

PostgreSQL uses TOAST — The Oversized-Attribute Storage Technique to handle values that cannot efficiently fit within ordinary heap-page constraints.

TOAST-able values may be compressed and/or stored out-of-line depending on their size and configured storage strategy.

Conceptually:

Main Table
│
├── normal data
├── normal data
└── TOAST reference
        │
        ▼
   TOAST Relation
        │
        └── Large value

Types commonly associated with large TOAST-able values include:

text
bytea
json
jsonb

However, values of these types do not automatically reside out-of-line.

Capacity investigations involving document-style or large-payload workloads should explicitly consider TOAST consumption.

## 4.1.14 Tablespaces

Tablespaces allow PostgreSQL objects to reside outside the default storage location.

For example:

PostgreSQL
│
├── Default Tablespace
│       └── /pgdata
│
├── FAST Tablespace
│       └── /nvme
│
└── ARCHIVE Tablespace
        └── /archive

This creates an important production requirement:

Every filesystem or volume backing a PostgreSQL tablespace must be monitored independently.

Consider:

/pgdata       45% used
/nvme         71% used
/archive      98% used    ← INCIDENT

Monitoring only PGDATA would miss the actual capacity problem.

Tablespace monitoring must therefore include:

Capacity
Growth
Latency
IOPS
Throughput
Availability

for every underlying storage location.

## 4.1.15 Write-Ahead Log Storage

PostgreSQL uses Write-Ahead Logging to support durability and crash recovery.

WAL normally resides beneath:

PGDATA/pg_wal/

Simplified transaction flow:

Application Transaction
          │
          ▼
Database Modification
          │
          ▼
WAL Generated
          │
          ▼
WAL Persisted
          │
          ▼
Dirty Data Pages
Eventually Written

WAL storage is a major production capacity concern.

## 4.1.16 WAL Generation vs. WAL Retention

These concepts must not be confused:

WAL generation
      ≠
WAL retention
Normal lifecycle
Transactions
     ↓
WAL generated
     ↓
Replication/archive requirements satisfied
     ↓
Older WAL recycled or removed
Retention failure
Transactions
      ↓
WAL generated
      ↓
Replication / archive / slot requirement
      ↓
WAL cannot yet be removed
      ↓
pg_wal grows
      ↓
Filesystem pressure
      ↓
Database availability risk

Potential contributors include:

replication slots;
lagging standbys;
failed WAL archiving;
high write workloads;
bulk operations;
backup/recovery activity;
checkpoint/full-page-write behavior.

Production monitoring must therefore measure both WAL generation rate and retained WAL footprint.

## 4.1.17 Temporary Storage

PostgreSQL may use temporary files when operations cannot be completed within available memory.

Typical sources include:

Sorts
Hash operations
Aggregations
Materialization
Temporary tables
Index operations
Complex analytical queries

For example:

Large Query
    ↓
Large Sort
    ↓
Insufficient memory
    ↓
Temporary-file spill
    ↓
Disk I/O
    ↓
Potential latency increase

At sufficient scale:

Temporary-file growth
        ↓
Storage pressure
        ↓
I/O saturation
        ↓
Filesystem exhaustion

Temporary-file monitoring is therefore both a capacity and performance requirement.

## 4.1.18 PostgreSQL Buffer Cache and Storage

PostgreSQL maintains frequently accessed database pages through its buffer manager and shared_buffers.

A simplified model is:

                    Query
                      │
                      ▼
             PostgreSQL Buffer Manager
                      │
                shared_buffers
                 /         \
              HIT           MISS
               │              │
               │              ▼
               │       Filesystem I/O
               │              │
               │       OS caching/storage
               │              │
               └──────────────┤
                              ▼
                         Page returned

The operating system can also cache filesystem data independently.

Storage behavior therefore interacts with:

shared_buffers
working-set size
OS caching
query access patterns
index efficiency
checkpoint behavior
autovacuum
concurrency
storage latency
IOPS
throughput

A PostgreSQL system with substantial free disk space can still be storage-bound.

## 4.1.19 Capacity Is More Than Database Size

A dangerous capacity-planning model is:

Database = 2 TB

Provisioned storage = 2.5 TB

This ignores operational storage requirements.

A more realistic model is:

Required Storage
      =
Steady-State Data
      +
Indexes
      +
TOAST
      +
Expected Growth
      +
Bloat Allowance
      +
WAL Headroom
      +
Temporary-Space Headroom
      +
Maintenance Headroom
      +
Operation-Specific Transient Capacity
      +
Safety Margin

Transient requirements can arise during operations such as:

CREATE INDEX
REINDEX
VACUUM FULL
CLUSTER
large COPY
bulk loads
table rewrites
schema migrations
logical migrations
backup/recovery
pg_repack where used

Therefore:

Capacity planning must consider peak operational demand, not merely steady-state database size.

## 4.1.20 Capacity vs. Performance

Production storage planning must answer two separate questions.

Capacity
Do we have enough GB/TB?
Performance
Can storage provide the required:
IOPS
throughput
latency?

For example:

Allocated:       10 TB
Used:             3 TB
Free:             7 TB

does not establish that storage is healthy.

If storage latency is excessive or workload demand exceeds available IOPS, PostgreSQL can still perform poorly.

A complete storage assessment includes:

Dimension	Question
Capacity	How much storage exists?
Utilization	How much is consumed?
Growth	How quickly is it increasing?
IOPS	Can required operations be sustained?
Throughput	Can required data volume be moved?
Latency	How long does each I/O take?
Queueing	Is storage demand accumulating?
Headroom	Can abnormal demand be absorbed?
Recovery	Can recovery workloads be sustained?
## 4.1.21 Capacity Must Be Trend-Based

Percentage utilization alone is insufficient.

Consider:

DATABASE A
----------
Utilization:      80%
Free:             2 TB
Growth:           5 GB/day

versus:

DATABASE B
----------
Utilization:      65%
Free:             500 GB
Growth:           125 GB/day

Database B is potentially the more urgent production risk.

Therefore:

Capacity Risk
     =
Current Utilization
     +
Free Capacity
     +
Growth Rate
     +
Growth Acceleration
     +
Time to Threshold
## 4.1.22 Time-to-Exhaustion Forecasting

A simple initial forecast is:

Daily Growth
    =
Current Used Storage - Previous Used Storage
--------------------------------------------
                Days

Then:

Days to Exhaustion
        =
Available Capacity
------------------
Average Daily Growth

More operationally useful:

Days to Warning
       =
Capacity Available Before Warning Threshold
-------------------------------------------
Average Daily Growth

Production dashboards should ideally expose:

storage_used_bytes
storage_free_bytes

daily_growth_bytes
weekly_growth_bytes
monthly_growth_bytes

days_to_warning
days_to_critical
days_to_exhaustion

Forecasts should subsequently account for:

non-linear growth;
seasonality;
application releases;
bulk loads;
retention-policy changes;
maintenance operations;
abnormal WAL generation;
abnormal temporary storage.
## 4.1.23 Example Capacity Risk Zones

Organizations may establish internal operating thresholds such as:

Utilization	Example State	Typical Response
<70%	Normal	Monitor trend
70–80%	Watch	Review forecast
80–90%	Warning	Capacity plan required
90–95%	Critical	Immediate remediation
>95%	Emergency	Protect availability

These are example operational thresholds, not PostgreSQL-defined requirements.

Thresholds should reflect:

Growth velocity
Provisioning lead time
Volume expansion capability
Workload criticality
Maintenance requirements
Recovery requirements
Cloud/platform constraints

A rapidly growing database may require intervention long before 80%.

## 4.1.26 Core Storage Size Queries
Database sizes
SELECT
    datname,
    pg_size_pretty(pg_database_size(datname)) AS database_size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;
Table storage breakdown
SELECT
    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_size,
    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS indexes_size,
    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_size;

Conceptually:

pg_relation_size()
       ↓
Individual relation fork

pg_table_size()
       ↓
Table + TOAST + auxiliary storage

pg_indexes_size()
       ↓
Indexes

pg_total_relation_size()
       ↓
Table-associated storage + indexes
Largest user tables
SELECT
    schemaname,
    relname,
    pg_size_pretty(
        pg_total_relation_size(
            format('%I.%I', schemaname, relname)::regclass
        )
    ) AS total_size
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(
    format('%I.%I', schemaname, relname)::regclass
) DESC
LIMIT 20;
Tablespaces
SELECT
    spcname,
    pg_tablespace_location(oid)
FROM pg_tablespace;

These are starting points. Production investigations should combine relation-level information with filesystem and storage-platform telemetry.

## 4.1.30 Disk-Full Emergency Principle

A PostgreSQL disk-full event should be treated as:

A database reliability incident—not a generic filesystem cleanup task.

The response model should be:

ALERT
  ↓
Identify affected filesystem
  ↓
Determine consumer
  ↓
Determine growth source
  ↓
Protect database availability
  ↓
Expand storage or perform known-safe remediation
  ↓
Correct root cause
  ↓
Validate PostgreSQL
  ↓
Restore operational headroom
  ↓
Post-incident review

Administrators should not attempt emergency recovery by blindly deleting PostgreSQL-managed files.

In particular, do not treat files beneath locations such as:

base/
global/
pg_wal/
pg_xact/
pg_multixact/

as ordinary disposable filesystem data.

Manual removal can lead to corruption, loss of recoverability, or database failure.

Are all tablespace filesystems monitored?
What are current read/write latencies?
Are IOPS approaching a platform limit?
Is throughput approaching a platform limit?
How many days remain before warning?
How many days remain before critical capacity?
How many days remain before exhaustion?
Is there sufficient maintenance headroom?
Can storage be expanded online?
How long does expansion normally take?
Is storage autoscaling configured where supported?
Is there a tested disk-full runbook?
Are storage alerts mapped to owners and escalation procedures?

If these questions cannot be answered quickly from monitoring, SQL queries, dashboards, and runbooks, storage operations are not yet mature.

## 4.1.35 Key Production Principles

1. Monitor growth, not merely utilization.

70% full + 1 GB/day

is a different risk from:

70% full + 200 GB/day

2. Capacity and performance are separate.

Free space does not guarantee acceptable I/O performance.

3. Monitor every tablespace.

PGDATA capacity alone is insufficient.

4. Understand WAL generation and WAL retention separately.

High generation does not automatically mean abnormal retained WAL.

5. Include transient operational storage.

Maintenance and migration operations can substantially increase temporary capacity requirements.

6. Never blindly delete PostgreSQL-managed files.

Disk-full remediation must preserve database integrity.

7. Forecast exhaustion before alert thresholds are reached.

Days-to-warning and days-to-exhaustion are stronger SRE signals than percentage alone.

8. Correlate PostgreSQL and infrastructure telemetry.

Neither layer alone provides the complete storage-performance picture.

9. Preserve operational headroom.

PostgreSQL requires room for normal growth, WAL, temporary files, maintenance, recovery, and unexpected workload changes.

10. Treat storage as part of the database SLO.

Capacity, latency, throughput, and recoverability directly influence service reliability.
