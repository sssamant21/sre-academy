# 4.10 -- Temporary Files and Temporary Storage Management

**Status:** Complete -- Revised Final / Canonical Edition

**Workflow:** Draft -> Technical Review -> Production Review -> Revised Final / Canonical Edition

**Chapter:** Chapter 4 -- PostgreSQL Storage Architecture and Capacity Management

Temporary storage is transient, but it is a production reliability resource. Poorly controlled temporary workloads can exhaust storage, saturate I/O, increase query latency, consume excessive memory, and interfere with OLTP, backup, maintenance, and failover operations.

## 4.10.1 Production Objectives

PostgreSQL temporary-storage engineering must balance memory, capacity, I/O performance, query latency, and application SLOs. The objective is not to eliminate temporary files. Disk spilling is a normal execution mechanism; the objective is to prevent temporary work from becoming an uncontrolled reliability event.

```text
                    QUERY WORKLOAD
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       MEMORY         CAPACITY          I/O
          |              |              |
     Avoid OOM       Avoid disk      Avoid storage
                     exhaustion       saturation
          +--------------+--------------+
                         |
                         v
                  QUERY LATENCY
                         |
                         v
                 APPLICATION SLO
```

## 4.10.2 Sources of Temporary Storage

PostgreSQL temporary-storage consumption can come from several mechanisms:

- Executor temporary files for sorts, hash joins, hash aggregation, DISTINCT, ORDER BY, materialization/intermediate results, held cursors, and parallel query operations.
- Explicit temporary relations created with `CREATE TEMP TABLE` and temporary indexes.
- Other subsystems, including logical decoding, that can spill working data to local storage when relevant memory thresholds are exceeded.

These categories must not be treated as one resource.

## 4.10.3 Executor Temporary Files vs. TEMP Tables

This distinction is operationally critical. `temp_file_limit` limits qualifying temporary files used by a PostgreSQL process, but disk space consumed by explicit temporary tables is excluded from this limit.

```text
                   temp_file_limit
                         |
              +----------+----------+
              |                     |
              v                     v
       Executor temp files      TEMP tables
              |                     |
           COUNTED              NOT COUNTED
```

A system protected from a pathological executor spill is not automatically protected from an application creating very large TEMP relations.

## 4.10.4 Physical Temporary-File Layout

For the default tablespace, PostgreSQL executor temporary files are normally placed under:

```text
$PGDATA/base/pgsql_tmp/
```

For another tablespace, temporary files use that tablespace's `pgsql_tmp` area. If this resides on the same filesystem as persistent database storage, temporary workload can compete with PGDATA for both capacity and I/O.

## 4.10.5 Why PostgreSQL Spills to Disk

Sort, hash, aggregation, and other executor operations use memory while their working set remains within the applicable memory budget. When the working set cannot remain in memory, PostgreSQL can use temporary storage. Disk spilling is therefore not inherently a fault.

Repeated or excessive spilling is a signal to examine query design, execution plans, statistics, indexes, memory, concurrency, parallelism, and storage capability.

## 4.10.6 `work_mem`

`work_mem` establishes the base memory available to applicable query operations, such as sorts and hash tables, before temporary-file usage can become necessary. Multiple operations can exist in one query, and many sessions can perform such work concurrently.

```sql
SHOW work_mem;
```

`work_mem` is not a per-session memory ceiling. Do not calculate PostgreSQL memory simply as `work_mem * max_connections`.

## 4.10.7 Concurrency and Parallel Query

Memory risk increases with workload concurrency and can be amplified by parallel execution. A useful risk model considers concurrent memory-consuming operations, per-operation memory allowance, and parallel-execution effects. This is not an exact memory formula; actual consumption depends on execution plans, active nodes, hash behavior, parallel workers, session concurrency, maintenance, and other PostgreSQL/OS requirements.

## 4.10.8 `hash_mem_multiplier`

Hash operations can use a memory ceiling derived from:

```text
work_mem * hash_mem_multiplier
```

Check both settings when reviewing hash-intensive workloads:

```sql
SHOW work_mem;
SHOW hash_mem_multiplier;
```

## 4.10.9 `temp_buffers`

Explicit temporary tables introduce another memory control: `temp_buffers`, which governs session-local buffers used for accessing temporary tables. TEMP-heavy applications therefore have several resource dimensions: physical relation storage, temporary indexes, `temp_buffers`, and executor temporary files.

## 4.10.10 Avoid Indiscriminate Global `work_mem` Increases

Do not globally increase `work_mem` merely because temporary files exist. Less temporary I/O can come at the cost of substantially higher aggregate memory consumption, OS memory pressure, swap, OOM conditions, and database instability.

Use this workflow instead:

```text
Measure -> Identify query -> Inspect plan -> Determine concurrency
        -> Optimize query/index/statistics -> Evaluate targeted memory change
        -> Load test -> Monitor
```

## 4.10.11 Workload-Specific Memory Governance

Different workloads should not necessarily share identical memory settings. Role-level or transaction-local tuning can provide safer isolation for reporting or ETL workloads.

```sql
ALTER ROLE reporting_user SET work_mem = '64MB';
```

For a controlled operation:

```sql
BEGIN;
SET LOCAL work_mem = '256MB';
-- controlled analytical operation
COMMIT;
```

Values are illustrative only and must come from workload testing and concurrency analysis.

## 4.10.12 `temp_file_limit`

`temp_file_limit` is an important production circuit breaker. It limits the temporary-file disk space a PostgreSQL process can consume at one instant; `-1` means unlimited.

```sql
SHOW temp_file_limit;
```

Treat it as a per-process blast-radius control, not a cluster-wide quota and not a TEMP-table quota.

## 4.10.13 `temp_tablespaces`

`temp_tablespaces` controls placement of temporary tables and indexes and temporary files used for large sorts and other query processing.

```sql
SHOW temp_tablespaces;
SET temp_tablespaces = 'temp_ts';
```

A dedicated temporary tablespace can isolate temporary capacity and I/O from persistent database storage.

## 4.10.14 Multiple Temporary Tablespaces

Multiple tablespaces can be configured:

```sql
SET temp_tablespaces = 'temp01,temp02,temp03';
```

This provides placement distribution opportunities, but it is not sophisticated automatic I/O tiering and does not replace capacity planning. Every underlying storage location requires monitoring.

## 4.10.15 Dedicated Temporary Storage

Dedicated temporary storage may provide capacity isolation, I/O isolation, independent monitoring, a different storage tier, and reduced PGDATA blast radius. It also creates an additional filesystem, mount, failure domain, monitoring requirement, IaC dependency, and capacity plan.

Use dedicated temporary storage to solve a measured production problem rather than as a universal requirement.

## 4.10.16 Mount Validation

For self-managed PostgreSQL, validate the expected mount, device/filesystem, capacity, read/write state, ownership, permissions, and tablespace path. Directory existence alone does not prove that the intended filesystem is mounted. A failed `/pgtemp` mount can otherwise cause PostgreSQL to write into the underlying root filesystem and create a host-wide capacity incident.

## 4.10.17 Monitoring with `pg_stat_database`

Use database-level temporary-file statistics:

```sql
SELECT
    datname,
    temp_files,
    temp_bytes,
    pg_size_pretty(temp_bytes) AS cumulative_temp_written
FROM pg_stat_database
ORDER BY temp_bytes DESC;
```

Collect deltas over time for workload baselining and anomaly detection.

## 4.10.18 `temp_bytes` Is Not Current Disk Occupancy

`temp_bytes` represents cumulative temporary-file bytes written over the statistics interval. It does not represent the amount of temporary data currently present on disk.

Use PostgreSQL statistics for temporary I/O activity and filesystem/storage telemetry for current disk occupancy. These are separate measurements.

## 4.10.19 Temporary-Write Rate

A useful workload metric is:

```text
(temp_bytes(T2) - temp_bytes(T1)) / delta_time
```

This approximates temporary bytes written per unit time and is useful for baselining, anomaly detection, batch comparison, query-change analysis, and I/O forecasting. Temporary-write rate is not filesystem-growth rate.

## 4.10.20 Capacity Runway

If the temporary filesystem is genuinely filling, calculate:

```text
Available temporary capacity / positive net occupancy growth rate
= approximate capacity runway
```

Use actual filesystem occupancy growth, not `temp_bytes`, because temporary files can be created and removed while cumulative bytes written continue to rise.

## 4.10.21 Capacity and I/O Are Separate Failure Modes

A temporary filesystem can have ample free capacity and still cause an incident through I/O saturation. Monitor capacity metrics such as used GB, free GB, occupancy growth, and runway separately from performance metrics such as IOPS, throughput, read/write latency, queue depth, and storage utilization.

## 4.10.22 `log_temp_files`

`log_temp_files` can help identify material temporary-file creation.

```sql
SHOW log_temp_files;
```

Choose a threshold that balances diagnostic visibility with log volume. Do not copy one threshold universally across environments.

## 4.10.23 Query-Level Spill Analysis

For a known query:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

Inspect sort methods and disk usage, hash buckets/batches/memory usage, cardinality estimates, joins, aggregation, parallelism, and actual-versus-estimated rows. Hash spills and sort spills do not necessarily appear identically in `EXPLAIN` output.

## 4.10.24 Optimize Before Expanding Memory

Investigate execution plans, cardinality estimates, statistics, indexes, join strategy, aggregation, ORDER BY requirements, result-set size, partition pruning, parallelism, application query design, and concurrency before treating `work_mem` as the fix.

Possible remediation includes an appropriate index, updated statistics, query rewrite, reduced result set, improved partition pruning, concurrency control, workload scheduling, targeted memory tuning, or increased temporary-storage capability.

## 4.10.25 Maintenance Memory Is Different

Applicable maintenance operations use `maintenance_work_mem`; `work_mem` is not the only relevant memory control. Maintenance-related resource incidents must be diagnosed according to the actual operation and memory path.

## 4.10.26 Logical Decoding

Systems using logical decoding or CDC should consider `logical_decoding_work_mem`. Logical decoding can spill decoded changes to disk when its working memory threshold is exceeded. Treat this as a separate temporary-storage source from ordinary executor spill.

## 4.10.27 Temporary Tables and Connection Pools

Temporary tables are session-oriented. An application request ending does not necessarily end the underlying PostgreSQL session when connection pooling is used. Applications using TEMP objects must understand session lifetime, pooling mode, `ON COMMIT` behavior, TEMP-object lifecycle, and cleanup expectations.

## 4.10.28 Capacity Engineering

Peak capacity should account for simultaneously active temporary files, temporary relations, other temporary consumers, and safety margin. I/O volume should be modeled separately using temporary bytes per execution and execution count. Do not multiply spill size by duration as though it directly represented disk occupancy.

## 4.10.29 Concurrency Is a Major Risk Multiplier

Individually acceptable queries can become dangerous under high concurrency. The correct remediation may be connection-pool control, reporting queues, batch scheduling, application concurrency limits, or workload governance rather than additional PostgreSQL memory.

## 4.10.30 Production Monitoring Dashboard

| Domain | Metric |
|---|---|
| Database | `temp_files` delta |
| Database | `temp_bytes` delta |
| Workload | Temp GB/hour |
| Capacity | Used GB / used % / free GB |
| Capacity | Net occupancy growth / runway |
| Storage | IOPS / throughput / latency / queue depth |
| Query | Largest and repeated spilling queries |
| Concurrency | Concurrent spilling sessions |
| Memory | `work_mem`, `hash_mem_multiplier`, `temp_buffers` |
| Guardrail | `temp_file_limit` |
| Placement | `temp_tablespaces` |
| Application | Reporting/ETL/batch concurrency |

## 4.10.31 Alerting Model

Alert on multiple dimensions rather than relying only on a filesystem percentage. Useful alerts include abnormal temp-write rate, unusually large or repeated spills, high temporary-filesystem utilization, low free GB, rapidly rising occupancy, capacity runway below the intervention window, elevated storage latency, sustained throughput/IOPS saturation, unusual reporting/ETL concurrency, and temporary-storage-related query failures.

## 4.10.32 Production Change Preflight

Before a large reporting, analytical, ETL, migration, or batch workload:

- Capture baseline temp activity and filesystem occupancy.
- Confirm free capacity and storage throughput headroom.
- Review the execution plan and identify sorts/hashes.
- Validate cardinality estimates.
- Test a representative workload and measure spill volume/runtime.
- Estimate concurrency and parallelism.
- Review `work_mem`, `hash_mem_multiplier`, `temp_file_limit`, and `temp_tablespaces`.
- Check application concurrency controls and overlapping backup/maintenance jobs.
- Define monitoring frequency, warning threshold, abort criteria, responsible operator, and fallback action.

## 4.10.33 Abort Criteria

Predefine stop conditions such as capacity runway below the approved response window, storage latency or database/application latency violating SLOs, sustained storage saturation, unexpected concurrency, spill materially exceeding the tested baseline, or application error rates exceeding thresholds.

## 4.10.34 Temporary-Storage Incident Runbook

1. Confirm the affected PostgreSQL instance and filesystem/tablespace.
2. Measure used/free capacity and actual filesystem occupancy growth.
3. Calculate capacity runway.
4. Check storage latency, IOPS, throughput, and queue depth.
5. Identify the affected database and calculate `temp_files`/`temp_bytes` deltas.
6. Review temporary-file logging and identify active expensive queries.
7. Identify reporting, ETL, and batch workloads and measure concurrency.
8. Check `work_mem`, `hash_mem_multiplier`, `temp_file_limit`, and `temp_tablespaces`.
9. Identify TEMP-table-heavy sessions.
10. Inspect execution plans and parallelism.
11. Check recent query/application changes.
12. Protect remaining storage.
13. Pause or cancel optional runaway workload if approved.
14. Reduce uncontrolled concurrency.
15. Expand storage if safely supported.
16. Repair query, index, or statistics issues.
17. Apply targeted memory tuning only when justified.
18. Confirm filesystem occupancy stabilizes and storage latency recovers.
19. Confirm database/application SLO recovery.
20. Update capacity forecasts, complete RCA, and implement prevention actions.

## 4.10.35 Emergency Actions

Prefer to calculate runway, identify the workload, protect remaining capacity, pause/cancel optional work if approved, reduce concurrency, expand safely if necessary, and then fix the root cause.

Do not immediately increase global `work_mem` massively, delete PostgreSQL files, move live storage manually, or restart PostgreSQL without diagnosis.

## 4.10.36 Never Manually Clean Active PostgreSQL Temp Files

Do not implement generic cleanup such as:

```bash
rm -f "$PGDATA"/base/pgsql_tmp/*
```

Identify the workload/backend, control or cancel it if approved, allow PostgreSQL to manage file lifecycle, and validate capacity recovery. PostgreSQL-managed temporary files are not generic operating-system scratch files.

## 4.10.37 Backup and Maintenance Interaction

Temporary executor files are not durable application data requiring backup. However, high-spill workloads can compete with backup and maintenance for CPU, memory, storage I/O, storage queues, and network resources. Validate headroom before overlapping major reporting, ETL, index maintenance, and backup activity.

## 4.10.38 HA and Failover

Temporary query spill is local execution state, but after failover the application workload moves to the new primary. Failover infrastructure must therefore support the production temporary workload it may inherit. HA capacity planning should include CPU, memory, persistent storage, WAL, temporary storage, I/O capability, and network.

## 4.10.39 Kubernetes

For PostgreSQL on Kubernetes, explicitly determine where temporary files live, PVC versus ephemeral storage, StorageClass, capacity, IOPS/throughput, node ephemeral-storage limits, pod eviction behavior, volume topology, AZ placement, operator support, failover behavior, and backup interaction. Use only layouts supported by the PostgreSQL operator and tested lifecycle procedures.

## 4.10.40 Managed PostgreSQL

Managed PostgreSQL services preserve the fundamental concepts of query spill, memory, concurrency, temporary relations, storage capacity, I/O, and query optimization, but they may abstract or restrict direct filesystem and tablespace management. Use provider-supported mechanisms for Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL.

## 4.10.41 Infrastructure as Code

Dedicated temporary storage should be reproducible through IaC: storage volume, filesystem, mount configuration, startup dependency, ownership/permissions, tablespace, `temp_tablespaces`, monitoring, and alerts. Prevent configuration drift across primary, standby, DR, and replacement hosts.

## 4.10.42 Automation Boundaries

Safe to automate: metrics collection, rate calculations, filesystem capacity, occupancy growth, runway, IOPS/throughput/latency, large-spill detection, query correlation, tablespace health, mount validation, concurrency anomalies, and forecasting.

Require approval for query cancellation, memory parameter changes, `temp_file_limit`, `temp_tablespaces`, concurrency changes, storage expansion, tablespace changes, and temporary-placement changes.

Never generic-automate deletion of PostgreSQL temp files, automatic `work_mem` increases after spill, killing every spilling query, automatic PostgreSQL restart because temp storage is high, or ad hoc live-storage relocation.

## 4.10.43 Production Case Study -- Reporting Concurrency Storm

Five reports spilling roughly 20 GB each may be manageable. If an application change allows 50 concurrent reports, aggregate sorts and hashes can saturate temporary I/O, lengthen query runtime, increase overlap, and create a positive feedback loop. The root cause may be uncontrolled reporting concurrency rather than insufficient `work_mem`.

Correct response: restore concurrency control, reduce optional workload, allow the storage queue to recover, analyze query plans, tune individual workloads, and establish permanent guardrails.

## 4.10.44 Production Case Study -- Shared PGDATA Exhaustion

When PGDATA and temporary files share a filesystem, a large analytical batch can consume capacity needed by persistent database storage. Calculate runway, identify and pause/cancel the batch if approved, allow PostgreSQL cleanup, confirm recovery, review `temp_file_limit` and workload concurrency, and evaluate dedicated temporary storage. Do not delete `base/pgsql_tmp/*` manually.

## 4.10.45 Production Case Study -- Unsafe `work_mem` Increase

Increasing `work_mem` globally from a conservative value to a very large value can reduce spill while causing aggregate RAM pressure under peak concurrency. Restore a safe baseline, profile the spilling workload, measure concurrency, optimize the query, use role/session-specific tuning, load test, and monitor both memory and temporary I/O.

## 4.10.46 SRE/DBRE Production Checklist

- Establish normal and peak `temp_files`/`temp_bytes` rates.
- Monitor actual filesystem occupancy, free GB, occupancy growth, and runway.
- Monitor IOPS, throughput, latency, and queue depth.
- Identify top spilling queries and configure an appropriate `log_temp_files` policy.
- Review `work_mem`, `hash_mem_multiplier`, `temp_buffers`, and `temp_file_limit`.
- Account separately for explicit TEMP relations.
- Review `temp_tablespaces` and monitor every underlying storage location.
- Validate dedicated-storage mounts, ownership, and permissions.
- Monitor reporting/ETL concurrency and test high-spill workloads.
- Define abort criteria and coordinate with backup/maintenance windows.
- Validate failover capacity.
- Never manually delete active PostgreSQL temporary files.
- Avoid indiscriminate global memory increases.
- Use IaC for dedicated storage and maintain a tested incident runbook.
- Complete RCA after significant temporary-storage incidents.

## 4.10.47 Canonical Rules

1. Temporary files are normal PostgreSQL execution behavior.
2. Excessive or uncontrolled temporary resource consumption is the reliability problem.
3. Executor temporary files and explicit TEMP relations are different resource classes.
4. `work_mem` is not a per-session memory ceiling.
5. Multiple plan operations, sessions, and parallel workers can amplify memory demand.
6. Hash workloads must account for `hash_mem_multiplier`.
7. TEMP-table-heavy workloads must consider `temp_buffers`.
8. Do not globally increase `work_mem` simply because queries spill.
9. Optimize query plans, statistics, indexes, and concurrency first.
10. Use workload-specific memory settings where justified.
11. `temp_file_limit` is a per-process circuit breaker, not a cluster-wide quota.
12. Explicit temporary-table storage is not protected by `temp_file_limit`.
13. `temp_tablespaces` can isolate temporary capacity and I/O.
14. Multiple temporary tablespaces provide placement distribution, not automatic tiering.
15. Dedicated temp storage improves isolation but creates another failure dependency.
16. Validate the actual mount, not merely the directory.
17. `temp_bytes` represents cumulative temporary I/O, not current disk occupancy.
18. Temporary-write rate and filesystem-growth rate are different metrics.
19. Use actual filesystem occupancy growth for capacity-runway calculations.
20. Monitor storage performance as well as capacity.
21. Storage saturation can cause an incident before disk exhaustion.
22. Use `EXPLAIN ANALYZE` and workload telemetry to identify spill causes.
23. Concurrency can be more dangerous than any single large query.
24. High-spill production operations require preflight and abort criteria.
25. Never manually delete active PostgreSQL-managed temporary files as routine remediation.
26. Coordinate temporary-heavy workloads with backups and maintenance.
27. Failover infrastructure must support inherited temporary workloads.
28. Kubernetes temporary-storage architecture must account for PVC, ephemeral storage, topology, eviction, and operator behavior.
29. Managed PostgreSQL requires provider-supported monitoring and remediation.
30. Automate observation aggressively; automate destructive remediation conservatively.
31. Temporary storage is a first-class PostgreSQL SRE/DBRE capacity and performance domain.
