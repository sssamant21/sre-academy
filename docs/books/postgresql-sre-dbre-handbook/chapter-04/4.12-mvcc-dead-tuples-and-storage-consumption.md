# 4.12 -- MVCC, Dead Tuples, and Storage Consumption

**Status:** Draft

**Workflow:** Draft -> Technical Review -> Production Review -> Revised Final / Canonical Edition

**Chapter:** Chapter 4 -- PostgreSQL Storage Architecture and Capacity Management

## 4.12.1 Purpose

PostgreSQL Multi-Version Concurrency Control (MVCC) allows readers and writers to operate concurrently by preserving multiple row versions when necessary. This concurrency model has a direct storage consequence: UPDATE and DELETE operations can leave older tuple versions physically present until they are no longer required by any relevant visibility horizon and can be cleaned up.

For SREs and DBREs, dead tuples are therefore not merely a maintenance statistic. Their creation rate, retention time, cleanup rate, and interaction with table growth are part of production storage-capacity engineering.

## 4.12.2 MVCC and Physical Tuple Versions

A simplified lifecycle is:

```text
Original row version
        |
      UPDATE
        |
   +----+----+
   |         |
   v         v
Old tuple   New tuple
version     version
   |
   v
May remain visible to
older transactions
   |
   v
Eventually no longer needed
   |
   v
Becomes removable
   |
   v
VACUUM / pruning lifecycle
   |
   v
Space can become reusable
```

DELETE follows a similar principle: the row becomes logically deleted for appropriate snapshots, but its tuple version can remain physically present until PostgreSQL can safely remove it.

## 4.12.3 Why PostgreSQL Keeps Old Versions

PostgreSQL transactions operate against snapshots. A transaction may need to see a row version that another transaction has already updated or deleted. PostgreSQL therefore cannot immediately overwrite or physically remove every previous version when DML occurs.

This is a fundamental tradeoff of MVCC:

```text
High concurrency
      +
Non-blocking snapshot reads
      |
      v
Multiple tuple versions
      |
      v
Cleanup responsibility
```

The cleanup mechanism is part of normal PostgreSQL operation, not evidence of a design defect.

## 4.12.4 Live, Dead, and Reusable Are Different States

Do not collapse tuple storage into only live and free.

A useful model is:

```text
LIVE
 |
 | UPDATE / DELETE
 v
OLD VERSION
 |
 | visibility horizons advance
 v
DEAD / REMOVABLE
 |
 | cleanup
 v
REUSABLE SPACE
```

A tuple version that is old is not necessarily immediately removable, and removable space is not necessarily immediately returned to the operating system.

## 4.12.5 UPDATE Storage Amplification

An UPDATE commonly creates a new tuple version while retaining the old version until it can be cleaned up. A high-update workload can therefore produce significant physical write and storage churn even when row count remains stable.

Example:

```text
Logical rows remain ~100 million
        |
Heavy UPDATE workload
        |
New tuple versions continuously created
        |
Old versions accumulate until cleanup
        |
Physical storage can grow
```

This is why row-count stability does not imply storage-size stability.

## 4.12.6 DELETE Storage Behavior

A DELETE changes logical visibility but does not normally remove relation bytes immediately.

```sql
DELETE FROM events
WHERE event_time < now() - interval '365 days';
```

A large purge can create a large population of obsolete tuple versions that must pass through the MVCC and vacuum lifecycle before their space becomes reusable.

This operation can also generate substantial WAL, index work, replication traffic, and subsequent vacuum workload.

## 4.12.7 HOT and Update Churn

Heap-Only Tuple updates can reduce index churn when PostgreSQL can place the new version on the same page and no indexed column requiring index maintenance changes. HOT can materially improve update-heavy workloads, but it does not remove the need to manage obsolete heap tuple versions.

Operationally, HOT eligibility is influenced by page free space, indexed columns, fillfactor, and workload shape. Detailed optimization belongs in later performance and vacuum discussions.

## 4.12.8 Dead Tuples and Table Growth

Dead tuples can contribute to relation growth when tuple creation outpaces cleanup and reuse.

```text
Tuple creation rate
        >
Cleanup / reuse rate
        |
        v
Dead versions accumulate
        |
        v
Existing pages become less useful
        |
        v
Relation extends
        |
        v
Filesystem consumption grows
```

However, total relation size alone does not prove dead-tuple accumulation or bloat. Storage diagnosis must correlate workload, tuple statistics, vacuum activity, internal reuse, indexes, TOAST, and infrastructure capacity.

## 4.12.9 Long-Running Transactions

A long-running transaction can retain an old snapshot and delay removal of tuple versions that would otherwise become reclaimable.

```text
High DML churn
      +
Long transaction
      |
      v
Old visibility horizon retained
      |
      v
Old tuple versions remain necessary
      |
      v
Cleanup delayed
      |
      v
Storage pressure
```

This makes transaction age a storage-capacity signal, not merely a session-management metric.

## 4.12.10 Idle in Transaction

Sessions that remain `idle in transaction` can preserve transaction state and should be monitored in production.

Useful investigation:

```sql
SELECT
    pid,
    usename,
    datname,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Do not automatically terminate old sessions without understanding application ownership, rollback implications, locks, and retry behavior.

## 4.12.11 Vacuum Horizons and Cleanup Eligibility

VACUUM cannot remove a tuple version merely because an administrator considers it old. PostgreSQL must determine that the version is no longer required by relevant transactional and replication-related horizons.

Therefore:

```text
VACUUM running
      !=
Every old tuple immediately removable
```

This distinction is critical when troubleshooting a table that continues to grow despite frequent autovacuum activity.

## 4.12.12 Replication and Retention Horizons

Logical replication, replication slots, standby behavior, and other retention horizons can affect how aggressively PostgreSQL can advance cleanup-related state. These mechanisms must be investigated when storage accumulation appears inconsistent with ordinary transaction activity.

Detailed replication architecture belongs in dedicated replication chapters; this section treats these mechanisms only as storage-lifecycle dependencies.

## 4.12.13 Dead Tuple Statistics

`pg_stat_user_tables` provides useful estimates:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_live_tup` and `n_dead_tup` are estimates. They should be used as operational signals and trends rather than exact byte accounting.

## 4.12.14 Dead Tuple Ratio

A dead-tuple ratio can be useful as one signal:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    round(
        100.0 * n_dead_tup /
        NULLIF(n_live_tup + n_dead_tup, 0),
        2
    ) AS dead_tuple_pct
FROM pg_stat_user_tables
ORDER BY dead_tuple_pct DESC NULLS LAST;
```

Do not use one universal percentage as an automatic incident threshold. A small percentage on a multi-terabyte table can represent significant storage, while a high percentage on a tiny table may be operationally irrelevant.

## 4.12.15 Correlating Dead Tuples with Physical Size

Combine tuple estimates with relation size:

```sql
SELECT
    s.schemaname,
    s.relname,
    s.n_live_tup,
    s.n_dead_tup,
    pg_size_pretty(pg_total_relation_size(s.relid)) AS total_size,
    s.last_autovacuum
FROM pg_stat_user_tables s
ORDER BY pg_total_relation_size(s.relid) DESC;
```

This helps prioritize investigation but still does not prove bloat. Detailed bloat analysis follows in Section 4.14.

## 4.12.16 Churn Rate Matters More Than a Snapshot

A dead-tuple count should be interpreted as a time series.

```text
Dead tuples at T1
Dead tuples at T2
Dead tuples at T3
        |
        v
Creation rate vs cleanup rate
```

Healthy high-churn tables can repeatedly create and clean large numbers of dead tuples. A rising backlog is more concerning than a high but stable count that is regularly processed.

## 4.12.17 Storage Consumption Model

A practical model for an MVCC-heavy relation is:

```text
Live tuple footprint
+
Old tuple versions awaiting cleanup
+
Reusable internal free space
+
Indexes
+
TOAST
+
Relation metadata/forks
```

Infrastructure planning must then add WAL, temporary workload, maintenance headroom, backup behavior, and future growth.

## 4.12.18 Index Consequences

UPDATE and DELETE workloads affect indexes as well as the heap. Index entries associated with obsolete row versions have their own cleanup lifecycle. An MVCC-heavy table can therefore experience both heap and index growth.

Do not assume that reducing heap dead tuples automatically makes indexes physically minimal. Section 4.14 treats index bloat separately.

## 4.12.19 TOAST Consequences

Updates to large values can create churn in associated TOAST relations and indexes. For workloads with large JSON, text, bytea, document, or other toastable values, inspect TOAST growth separately from the main heap.

## 4.12.20 Monitoring Model

A production MVCC-storage dashboard should correlate:

| Domain | Signals |
|---|---|
| Tuple lifecycle | live/dead tuple estimates |
| DML | insert/update/delete rates |
| HOT | HOT update activity |
| Vacuum | last vacuum/autovacuum, counts, duration where available |
| Transactions | oldest transaction, idle-in-transaction age |
| Relations | heap/index/TOAST size and growth |
| Capacity | used %, free GB, growth, runway |
| Storage | IOPS, throughput, latency |
| WAL | generation rate |
| Replication | lag and slot/retention health |
| Application | query latency, errors, batch activity |

## 4.12.21 Alerting Principles

Avoid simplistic rules such as:

```text
n_dead_tup > 1,000,000 => critical
```

Prefer context-aware alerting based on dead-tuple backlog trend, relation size, churn rate, time since successful vacuum, transaction age, physical growth, storage runway, I/O pressure, replication health, and application SLO impact.

Detailed alert thresholds belong in Section 4.20.

## 4.12.22 Failure Scenario -- Long Transaction Prevents Cleanup

Symptoms:

- UPDATE/DELETE workload remains high;
- dead tuple estimates increase;
- autovacuum runs repeatedly;
- relation size grows;
- one transaction has been open for many hours or days.

Response:

1. Identify the oldest transactions and their owners.
2. Determine whether the transaction is still required.
3. Review locks and rollback/retry impact.
4. Coordinate termination only when operationally safe.
5. Observe vacuum progress after the horizon advances.
6. Confirm dead-tuple backlog and storage growth stabilize.
7. Fix the application/session behavior that allowed the transaction to remain open.

## 4.12.23 Failure Scenario -- Bulk Purge Creates Storage Pressure

A large DELETE removes hundreds of millions of rows. Logical row count falls sharply, but physical table size remains high while WAL generation, replica lag, and vacuum work increase.

Correct interpretation: the purge initiated a storage lifecycle; it did not complete physical reclamation.

Response:

1. Verify transaction completion.
2. Monitor WAL and replicas.
3. Monitor dead tuple backlog and vacuum.
4. Confirm sufficient free storage for ongoing workload and cleanup.
5. Determine whether internal space will be reused.
6. Evaluate physical reclamation only if it is operationally required.

## 4.12.24 Failure Scenario -- Autovacuum Runs but Backlog Grows

If autovacuum is active but dead tuples and relation size continue to grow, investigate whether cleanup throughput is lower than tuple-generation rate or whether horizons prevent removal.

Review workload churn, transaction age, autovacuum worker capacity, table-specific thresholds, vacuum cost behavior, I/O saturation, lock conflicts, indexes, TOAST, and replication-related retention.

Detailed tuning follows in Section 4.13.

## 4.12.25 Production Runbook -- Rising Dead Tuple Backlog

1. Identify relations with the fastest-growing dead-tuple backlog.
2. Measure heap, index, TOAST, and total size.
3. Determine INSERT/UPDATE/DELETE rates.
4. Check last vacuum/autovacuum activity.
5. Identify oldest transactions and idle-in-transaction sessions.
6. Review replication and retention horizons where relevant.
7. Check storage free capacity and runway.
8. Check IOPS, throughput, latency, and application SLOs.
9. Determine whether vacuum is blocked, delayed, or simply under-capacity.
10. Resolve blockers using approved operational procedures.
11. Tune vacuum only after identifying the limiting mechanism.
12. Continue monitoring until backlog growth becomes stable or negative.
13. Update capacity forecasts and application remediation actions.

## 4.12.26 Automation Boundaries

Safe automation includes dead-tuple trending, transaction-age monitoring, relation-growth collection, vacuum-history collection, capacity-runway calculation, replication-lag correlation, and identification of top-churn tables.

Require approval for terminating sessions, changing autovacuum parameters, initiating large manual VACUUM operations, performing purges, or running rewrite/compaction operations.

Never generic-automate backend termination or destructive reclamation solely from `n_dead_tup` thresholds.

## 4.12.27 SRE/DBRE Production Rules

1. MVCC intentionally preserves multiple tuple versions when required for visibility.
2. UPDATE and DELETE can create obsolete physical tuple versions.
3. Logical row-count reduction does not imply immediate filesystem reduction.
4. An old tuple version is not necessarily immediately removable.
5. Cleanup eligibility depends on PostgreSQL visibility and retention horizons.
6. Long-running transactions can materially delay cleanup.
7. `idle in transaction` can become a storage-reliability concern.
8. VACUUM running does not prove that all old tuples can be removed.
9. Dead-tuple counts are estimates and must be interpreted as trends.
10. Dead-tuple percentages require relation-size and workload context.
11. Row-count stability does not imply physical-size stability.
12. High UPDATE rates can create significant storage amplification.
13. HOT can reduce some index churn but does not eliminate heap tuple lifecycle management.
14. Heap, indexes, and TOAST must be monitored separately.
15. A rising dead-tuple backlog indicates creation exceeds effective cleanup or cleanup is blocked.
16. Autovacuum effectiveness matters more than autovacuum presence.
17. Large purges create WAL, replication, vacuum, and capacity consequences.
18. Physical relation size alone does not prove bloat.
19. Capacity planning must include MVCC churn and cleanup lag.
20. Automate observation aggressively and destructive remediation conservatively.
