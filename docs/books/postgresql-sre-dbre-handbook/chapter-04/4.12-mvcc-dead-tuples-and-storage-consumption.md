# 4.12 -- MVCC, Dead Tuples, and Storage Consumption

**Status:** Complete -- Revised Final / Canonical Edition

**Workflow:** Draft -> Technical Review -> Production Review -> Revised Final / Canonical Edition

## Purpose

PostgreSQL MVCC preserves row versions needed by concurrent snapshots. UPDATE and DELETE therefore have direct physical-storage consequences: old tuple versions can remain until PostgreSQL determines they are no longer required and cleanup can make their space reusable.

## MVCC Storage Lifecycle

```text
INSERT -> live tuple
UPDATE -> old version + new version
DELETE -> logically removed version
             |
             v
      visibility horizons
             |
             v
      removable/dead tuple
             |
             v
       pruning / VACUUM
             |
             v
       reusable space
```

An old tuple is not automatically removable, and reusable space is not automatically filesystem-free space.

## UPDATE, DELETE, and HOT

UPDATE commonly creates a new heap tuple version while retaining the old version until cleanup is safe. DELETE changes visibility but normally does not immediately remove physical bytes. HOT updates can reduce index churn when PostgreSQL can keep the update chain on-page and avoid required index changes, but HOT does not eliminate heap-version cleanup.

## Cleanup Horizons

Long-running transactions and other PostgreSQL retention horizons can delay removal of old versions. `idle in transaction` sessions are therefore storage-reliability signals as well as session-management concerns. VACUUM being active does not prove that every old tuple is currently removable.

```sql
SELECT pid, usename, datname, state, xact_start,
       now() - xact_start AS transaction_age,
       wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## Dead-Tuple Diagnostics

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       n_tup_ins, n_tup_upd, n_tup_del, n_tup_hot_upd,
       last_vacuum, last_autovacuum,
       vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_live_tup` and `n_dead_tup` are estimates. Use trends rather than treating them as exact byte accounting.

A ratio can help prioritize investigation, but must be interpreted with relation size and churn:

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup /
             NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_tuple_pct
FROM pg_stat_user_tables
ORDER BY dead_tuple_pct DESC NULLS LAST;
```

## Storage Amplification

Row-count stability does not imply storage stability. A high-update table can continually create new versions while cleanup lags. Heap, indexes, and TOAST can all grow and must be measured separately.

A rising dead-tuple backlog means tuple creation exceeds effective cleanup, or cleanup is blocked by visibility/retention horizons. Physical size alone does not prove bloat.

## Monitoring and Alerting

Correlate live/dead tuple trends, DML rates, HOT activity, vacuum history, oldest transaction, relation/index/TOAST growth, filesystem or PVC capacity, runway, storage latency, WAL generation, replication lag, and application SLOs.

Avoid universal alarms such as `n_dead_tup > 1000000`. A small percentage on a multi-terabyte relation can be significant while a high percentage on a tiny table may not be operationally important.

## Production Failure Scenarios

**Long transaction prevents cleanup:** identify the oldest transaction and owner, evaluate rollback and retry impact, safely advance the blocking horizon, then verify vacuum and storage trends recover.

**Bulk purge creates pressure:** monitor WAL, replicas, dead-tuple backlog, vacuum, I/O, and free capacity. A completed DELETE begins a storage lifecycle; it does not guarantee physical reclamation.

**Autovacuum runs but backlog grows:** compare tuple-generation rate with effective cleanup and inspect long transactions, locks, worker capacity, I/O pressure, table-specific vacuum settings, indexes, TOAST, and retention horizons.

## Rising Dead-Tuple Runbook

1. Identify fastest-growing dead-tuple backlogs.
2. Measure heap, index, TOAST, and total size.
3. Determine DML churn.
4. Review vacuum/autovacuum activity.
5. Find oldest transactions and idle-in-transaction sessions.
6. Review relevant replication/retention horizons.
7. Check storage runway and I/O performance.
8. Resolve blockers using approved procedures.
9. Tune vacuum only after identifying the limiting mechanism.
10. Monitor until backlog growth stabilizes or becomes negative.
11. Update capacity forecasts and application remediation.

## Automation Boundaries

Automate tuple trending, transaction-age detection, relation growth, vacuum history, capacity runway, and replication correlation. Require approval for session termination, large manual vacuuming, purges, autovacuum changes, and rewrite operations. Never terminate backends or trigger destructive reclamation solely from a dead-tuple threshold.

## Canonical Production Rules

1. MVCC intentionally preserves multiple tuple versions when visibility requires them.
2. UPDATE and DELETE can create obsolete physical versions.
3. Old does not mean immediately removable.
4. Long transactions can materially delay cleanup.
5. VACUUM presence does not prove cleanup effectiveness.
6. Dead-tuple statistics are estimates and should be trended.
7. High UPDATE rates can create substantial storage amplification.
8. HOT reduces some index churn but does not eliminate heap cleanup.
9. Heap, indexes, and TOAST require separate observation.
10. Large purges create WAL, replication, vacuum, and capacity consequences.
11. Physical relation size alone does not prove bloat.
12. Capacity planning must include MVCC churn and cleanup lag.
13. Automate observation aggressively and destructive remediation conservatively.
