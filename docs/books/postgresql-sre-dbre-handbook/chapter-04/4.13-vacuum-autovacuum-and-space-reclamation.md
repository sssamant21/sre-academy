# 4.13 -- VACUUM, Autovacuum, and Space Reclamation

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

VACUUM is a core PostgreSQL correctness, performance, and capacity mechanism. It reclaims obsolete tuple space for reuse, maintains visibility information, and participates in transaction-ID safety. Autovacuum automates this work and ANALYZE based on configurable thresholds.

## Architecture

```text
DML churn -> obsolete tuples -> VACUUM eligibility
                                |
                     +----------+----------+
                     |                     |
                 manual VACUUM         autovacuum
                     |                     |
                     +----------+----------+
                                v
                   reusable space / visibility
```

Routine VACUUM generally reuses space internally; it is not a general file-compaction operation. `VACUUM FULL` rewrites a relation, takes an `ACCESS EXCLUSIVE` lock, and requires additional working storage.

## Autovacuum Trigger Model

Autovacuum decisions depend on table activity and configured thresholds/scale factors. Large and high-churn relations often need table-specific tuning rather than relying blindly on cluster defaults. Insert-heavy tables also require vacuum consideration for freezing and visibility maintenance.

Review effective settings before changing them:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name LIKE 'autovacuum%'
   OR name IN ('vacuum_cost_limit','vacuum_cost_delay');
```

## Monitoring

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       last_vacuum, last_autovacuum,
       vacuum_count, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Where supported by the deployed PostgreSQL version, use progress views for active vacuum work and correlate with transaction age, relation size, storage I/O, WAL, replication lag, and application latency.

## Production Tuning Principles

- Tune from measured churn and cleanup throughput, not folklore.
- Prefer per-table settings for exceptional relations.
- Ensure workers and cost limits can keep up without saturating storage.
- Investigate long transactions and lock conflicts before simply making vacuum more aggressive.
- Preserve enough I/O and CPU headroom for foreground workload.
- Treat anti-wraparound vacuum as a correctness requirement, not optional maintenance.

## Space Reclamation

Routine VACUUM makes dead space reusable and can truncate empty trailing pages when safe. It cannot remove arbitrary free pages from the middle of a relation. If permanent physical shrinkage is required, evaluate a controlled rewrite with locking, WAL, replica, I/O, and peak-capacity analysis.

## Failure Scenarios

**Vacuum cannot keep up:** dead tuples and relation growth rise despite frequent runs. Compare DML generation with cleanup throughput and inspect worker availability, cost throttling, I/O, locks, long transactions, and table settings.

**Vacuum blocked by old horizon:** find old transactions and retention dependencies; resolve them safely before escalating vacuum tuning.

**Emergency anti-wraparound activity:** do not disable or repeatedly cancel protective vacuum. Reduce competing workload and remediate the root cause while preserving transaction-ID safety.

**Rewrite during low disk:** stabilize or expand capacity before `VACUUM FULL`; the rewrite can need substantial additional space.

## Operational Runbook

1. Identify affected relations and churn.
2. Confirm dead/live tuple trends and vacuum history.
3. Check oldest transactions and blocking locks.
4. Check storage I/O, free capacity, and runway.
5. Check replication/HA state.
6. Determine whether the problem is eligibility, scheduling, throughput, or configuration.
7. Apply the least invasive table-specific correction.
8. Monitor cleanup rate and application SLOs.
9. Validate that backlog and growth normalize.
10. Record durable tuning and capacity changes.

## Automation Boundaries

Automate observation, trend analysis, and detection of missed/ineffective vacuum. Require approval for aggressive parameter changes, backend termination, manual high-impact vacuum, and rewrites. Never disable autovacuum globally as a routine performance workaround.

## Canonical Production Rules

1. VACUUM is part of PostgreSQL reliability and capacity engineering.
2. Autovacuum effectiveness matters more than mere enablement.
3. Routine VACUUM primarily enables internal reuse.
4. `VACUUM FULL` is a controlled rewrite, not routine maintenance.
5. Long transactions can prevent effective cleanup.
6. Large/high-churn tables may need table-specific settings.
7. Anti-wraparound vacuum is a correctness safeguard.
8. Tune from measured churn, cleanup throughput, and resource headroom.
9. Protect foreground SLOs while ensuring maintenance can keep up.
10. Never manually delete relation files to reclaim space.
