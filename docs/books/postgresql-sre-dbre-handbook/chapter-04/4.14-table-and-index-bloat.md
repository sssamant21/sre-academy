# 4.14 -- Table and Index Bloat

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Bloat is excess physical allocation or inefficient page utilization relative to the useful workload state. It must not be diagnosed from relation size alone. PostgreSQL intentionally keeps reusable internal space, and that space can be economically useful when a relation will regrow.

## Bloat Model

```text
DML churn + delayed cleanup + page/index behavior
                    |
                    v
          inefficient allocation
                    |
          +---------+---------+
          |                   |
      heap effects         index effects
```

Heap and index bloat are separate problems and can require different remediation.

## Causes

Common contributors include heavy UPDATE/DELETE churn, vacuum falling behind, long-running transactions, unsuitable fillfactor for update-heavy workloads, index churn, one-time purges, changing workload patterns, and repeated growth/reclamation cycles.

## Diagnosis

Start with size and workload trends rather than a single percentage:

```sql
SELECT schemaname, relname, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
       last_autovacuum
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC;
```

Use supported extensions or deeper page-level tooling only when approved and understood. Estimates of bloat are model-dependent; validate suspected bloat against growth history, DML churn, vacuum behavior, query performance, and expected future reuse.

## Table vs. Index

A table can have a healthy heap and inefficient indexes, or the reverse. Measure heap, indexes, and TOAST separately. Do not perform a heap rewrite when an index is the actual problem.

## Remediation Strategy

1. Fix the cause before reclaiming space.
2. Determine whether reusable capacity will be needed again.
3. For vacuum backlog, restore effective routine cleanup.
4. For index-specific problems, evaluate supported reindexing strategies and production locking behavior.
5. For permanent table downsizing, evaluate a controlled rewrite only after capacity and lock preflight.
6. Validate replicas, WAL, backup, and I/O impact.

## Failure Scenarios

**False-positive bloat:** a large table after a purge is rewritten even though it will rapidly regrow. Result: locking, WAL, I/O, and risk without durable savings.

**Index bloat misdiagnosed as heap bloat:** an intrusive table rewrite is planned without measuring indexes independently.

**Reclamation before root-cause repair:** relation is compacted, but long transactions or inadequate vacuum remain, so bloat returns.

## Monitoring and Alerting

Track relation/index size trends, dead tuple trends, DML churn, vacuum effectiveness, transaction age, query latency, index usage, filesystem runway, and I/O. Alert on sustained abnormal growth and operational impact, not a universal bloat percentage.

## Production Rules

1. Physical size alone does not prove bloat.
2. Reusable space is not automatically waste.
3. Diagnose heap and indexes independently.
4. Fix the cause before compaction.
5. Evaluate regrowth before returning space to the OS.
6. Rewrites and reindex operations require locking, WAL, I/O, replica, and capacity review.
7. Never use emergency file deletion as bloat remediation.
8. Trend recurrence after remediation to prove the fix is durable.
