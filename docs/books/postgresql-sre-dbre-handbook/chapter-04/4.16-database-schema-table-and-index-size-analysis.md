# 4.16 -- Database, Schema, Table, and Index Size Analysis

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Reliable storage analysis requires consistent definitions of database, relation, table, index, and total object size. Different PostgreSQL size functions answer different questions and must be labeled correctly in dashboards and runbooks.

## Core Functions

```sql
SELECT pg_size_pretty(pg_database_size(current_database()));
SELECT pg_size_pretty(pg_relation_size('public.orders'));
SELECT pg_size_pretty(pg_table_size('public.orders'));
SELECT pg_size_pretty(pg_indexes_size('public.orders'));
SELECT pg_size_pretty(pg_total_relation_size('public.orders'));
```

`pg_relation_size` measures a selected relation fork by default; `pg_table_size` includes table storage components but not indexes; `pg_indexes_size` measures attached indexes; `pg_total_relation_size` combines table and index storage.

## Largest Relations

```sql
SELECT n.nspname AS schema_name,
       c.relname AS relation_name,
       pg_relation_size(c.oid) AS heap_bytes,
       pg_indexes_size(c.oid) AS index_bytes,
       pg_total_relation_size(c.oid) AS total_bytes
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind IN ('r','m')
ORDER BY total_bytes DESC;
```

## Schema Aggregation

Schema totals should be calculated from well-defined object sets and must avoid accidental double counting. Decide whether the report includes tables, materialized views, indexes, TOAST, partition children, and other relation types, then document that definition.

## Partitioned Objects

A partitioned parent is not equivalent to the sum of its children for every size function. Capacity reports for partitioned workloads should enumerate leaf partitions and aggregate intentionally. Track hot partitions independently because growth and maintenance risk are often uneven.

## Index Analysis

Measure indexes individually before deciding that a table is the storage problem. Large unused or duplicate-looking indexes require workload and dependency validation before removal; usage statistics can reset and do not alone prove an index is unnecessary.

## Production Reporting

Maintain top-N reports for databases, schemas, tables, indexes, TOAST-heavy objects, fastest-growing objects, and objects with abnormal day-over-day change. Persist raw bytes for calculation and render human-readable units only for presentation.

## Failure Scenarios

**Double-counted schema capacity:** table totals already include indexes and are added again to separate index totals. Define aggregation semantics explicitly.

**Partition parent appears tiny:** monitoring records only the parent and misses child partitions. Enumerate partitions.

**Large index dropped from weak evidence:** low usage since a recent stats reset is mistaken for permanent non-use. Validate business/query dependencies and observation period.

## Production Rules

1. Know exactly what each size function includes.
2. Store raw byte values for trending.
3. Label dashboard definitions explicitly.
4. Separate heap, indexes, and TOAST where diagnosis requires it.
5. Handle partitions deliberately.
6. Avoid double counting in schema/database aggregation.
7. Never drop objects solely because they are large.
8. Correlate size with growth, workload, vacuum, and capacity runway.
