# 4.18 -- IOPS, Throughput, Latency, and Storage Performance

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

PostgreSQL storage performance is governed by workload access patterns, cache behavior, IOPS, throughput, latency, concurrency, queueing, WAL durability, checkpoints, background maintenance, and platform limits. Capacity and performance must be engineered separately.

## Core Concepts

- **IOPS:** number of I/O operations per second.
- **Throughput:** bytes transferred per second.
- **Latency:** time to complete an I/O.
- **Queue depth:** outstanding work waiting for storage.

Small random OLTP I/O can be IOPS/latency-sensitive while scans, backups, rewrites, and bulk operations can be throughput-sensitive.

## PostgreSQL Workload Sources

Storage demand comes from foreground reads/writes, WAL flushes, checkpoints, background writer activity, VACUUM, index builds/rebuilds, sorts and hashes that spill, backups, replication, bulk loads, and relation rewrites.

## Observability

Use PostgreSQL statistics available for the deployed version together with operating-system, hypervisor, cloud-volume, or managed-service metrics. Correlate storage latency with database wait events, checkpoints, WAL behavior, query latency, and application SLOs.

Where available, `pg_stat_io` provides PostgreSQL I/O statistics by backend/object/context; validate column semantics against the deployed major version.

## Performance Diagnosis

```text
Application latency
       |
       v
Database wait / query profile
       |
       v
Cache vs physical I/O
       |
       v
IOPS / throughput / latency / queue
       |
       v
Storage or workload bottleneck
```

Do not infer storage saturation from high IOPS alone; high IOPS with low latency can be healthy. Likewise, low IOPS with high latency can indicate a serious problem.

## Failure Scenarios

**Checkpoint I/O storm:** latency rises periodically with heavy dirty-buffer flushing. Review checkpoint cadence, WAL generation, storage capability, and workload bursts.

**Maintenance saturation:** VACUUM, backup, index build, or rewrite competes with foreground workload. Throttle/reschedule based on SLO and capacity.

**Cloud limit reached:** volume throughput or IOPS ceiling is exhausted despite available disk space. Scale performance capability, not merely capacity.

## Production Runbook

1. Establish the incident time window.
2. Confirm application/database latency symptoms.
3. Inspect PostgreSQL waits and query workload.
4. Check cache/read/write behavior and maintenance activity.
5. Check storage latency, IOPS, throughput, and queue depth.
6. Compare with provisioned/platform limits.
7. Identify concurrent backup, vacuum, checkpoint, bulk, or rewrite activity.
8. Reduce optional pressure or scale storage performance safely.
9. Validate recovery at database and application layers.
10. Preserve evidence for RCA.

## Production Rules

1. Capacity headroom does not guarantee performance headroom.
2. Interpret IOPS, throughput, latency, and queueing together.
3. Correlate infrastructure metrics with PostgreSQL waits and workload.
4. Separate OLTP latency sensitivity from bulk throughput demand.
5. Include maintenance and backup in performance budgets.
6. Validate cloud/provider performance ceilings.
7. Alert on sustained impact and SLO risk rather than raw IOPS alone.
