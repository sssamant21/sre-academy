# 4.19 -- Storage Monitoring, Metrics, and Observability

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Storage observability must connect PostgreSQL object behavior to the actual storage platform and application SLOs. No single PostgreSQL view or infrastructure metric provides a complete capacity or performance picture.

## Observability Layers

```text
Application SLOs
      |
PostgreSQL workload and waits
      |
Relations / WAL / temp / vacuum
      |
Filesystem / PVC / cloud volume
      |
Hardware or managed-service limits
```

## Required Metric Domains

**Capacity:** used %, free bytes, total bytes, growth rate, runway, inode availability where relevant.

**Objects:** database, table, index, TOAST, tablespace sizes and growth.

**MVCC/Vacuum:** live/dead tuple estimates, DML churn, vacuum/autovacuum activity, oldest transactions.

**WAL:** generation, retained volume, archive health, replication slots and relevant retention signals.

**Temporary storage:** temp files/bytes trends plus actual temp filesystem occupancy where separated.

**Performance:** read/write latency, IOPS, throughput, queueing, PostgreSQL I/O/wait statistics.

**HA:** replication lag, standby storage capacity, failover readiness.

## Dashboard Design

Provide fleet, cluster, database, and relation drill-down. Show current value, historical trend, rate of change, and relevant limit on the same view where possible. Preserve raw units for calculation and use human-readable units for display.

Key panels should include top-growing objects, storage runway, WAL/temp growth, dead-tuple/vacuum trends, oldest transaction, I/O latency, provisioned performance vs actual, and application latency.

## Data Quality

Monitoring must detect gaps, resets, stale exporters, counter resets, changed database identities, and unit mismatches. A silent monitoring failure during a storage incident is itself a reliability risk.

## Failure Scenarios

**Database metrics only:** relation growth looks normal while the filesystem fills from WAL/temp/other consumers.

**Infrastructure only:** disk growth is visible but operators cannot identify the PostgreSQL object or workload responsible.

**Counter reset mistaken for improvement:** statistics reset causes apparent drops. Preserve reset metadata and use infrastructure truth for capacity.

## Production Rules

1. Correlate PostgreSQL and infrastructure telemetry.
2. Monitor every independent storage domain.
3. Persist history sufficient for forecasting and RCA.
4. Show absolute values, rates, and limits.
5. Detect telemetry gaps and resets.
6. Tie storage signals to application SLOs.
7. Maintain top-growing-object views.
8. Treat monitoring configuration as production code with review and version control.
