# 4.2 — PostgreSQL Data Directory and Physical Layout

**Workflow Stage:** Revised Final / Canonical Edition
**Chapter:** Chapter 4 — PostgreSQL Storage Architecture and Capacity Management
**Audience:** PostgreSQL DBA / DBRE / SRE / Platform Engineer
**Status:** **Complete**

---

## 4.2.1 Purpose and Scope

The PostgreSQL data directory is the physical foundation of a PostgreSQL database cluster. It contains relation files, transaction metadata, Write-Ahead Log (WAL), replication state, runtime state, tablespace references, and other information required for PostgreSQL to operate and recover safely.

For an SRE or DBRE, understanding this layout is essential when investigating:

* unexpected database growth;
* filesystem capacity alerts;
* WAL growth and retention;
* replication-slot problems;
* tablespace exhaustion;
* transaction-state issues;
* temporary-file growth;
* startup failures;
* crash recovery;
* backup and restore;
* storage migrations;
* filesystem failures;
* PostgreSQL upgrades.

The central operational rule is:

> **`PGDATA` is PostgreSQL-managed state. Never treat its contents as ordinary files that can be deleted simply because storage is low.**

The correct production sequence is:

```text
Observe
   ↓
Identify filesystem
   ↓
Identify physical consumer
   ↓
Map to PostgreSQL component
   ↓
Determine root cause
   ↓
Choose supported remediation
   ↓
Validate PostgreSQL
   ↓
Restore operational headroom
```

---

## 4.2.2 PostgreSQL Database Cluster

In PostgreSQL terminology, a **database cluster** is a collection of databases managed by one PostgreSQL server instance.

```text
PostgreSQL Server
        │
        ▼
   Data Directory
        │
        ├── Database A
        ├── Database B
        ├── Database C
        ├── Cluster metadata
        ├── Transaction state
        └── WAL
```

This differs from the infrastructure meaning of *cluster* used by Kubernetes or distributed database platforms.

A PostgreSQL data directory represents one PostgreSQL database cluster.

---

## 4.2.3 Identifying the Active Data Directory

`PGDATA` is commonly used as an environment variable identifying the data directory.

However:

```text
Shell PGDATA
     ≠
Guaranteed active PostgreSQL data directory
```

The authoritative database-side check is:

```sql
SHOW data_directory;
```

or:

```sql
SELECT current_setting('data_directory');
```

Before investigating filesystem consumption, always verify the actual data directory used by the running PostgreSQL instance.

---

## 4.2.4 Configuration Location vs. Data Location

Do not assume that:

```text
postgresql.conf
pg_hba.conf
pg_ident.conf
```

must reside inside `PGDATA`.

PostgreSQL installations can separate configuration files from database storage.

Verify the active paths:

```sql
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
```

For example:

```text
data_directory
    /pgdata/postgresql

config_file
    /etc/postgresql/postgresql.conf

hba_file
    /etc/postgresql/pg_hba.conf
```

This distinction is especially important with distribution packages, containers, Kubernetes operators, and configuration-management systems.

---

## 4.2.5 High-Level Physical Layout

A typical PostgreSQL data directory contains structures similar to:

```text
PGDATA/
│
├── base/
├── global/
├── pg_commit_ts/
├── pg_dynshmem/
├── pg_logical/
├── pg_multixact/
├── pg_notify/
├── pg_replslot/
├── pg_serial/
├── pg_snapshots/
├── pg_stat/
├── pg_stat_tmp/
├── pg_subtrans/
├── pg_tblspc/
├── pg_twophase/
├── pg_wal/
├── pg_xact/
│
├── PG_VERSION
├── postgresql.auto.conf
├── postmaster.opts
└── postmaster.pid
```

Exact contents vary with PostgreSQL version, configuration, and runtime state.

Operationally, think of the directory as:

```text
PGDATA
 │
 ├── Relation storage
 ├── Cluster-wide metadata
 ├── Transaction state
 ├── WAL
 ├── Replication state
 ├── Tablespace references
 ├── Statistics/runtime state
 └── Server/runtime metadata
```

## 4.2.6 `base/` — Default Tablespace Database Storage

For databases using the default tablespace, database-specific relation files are stored beneath:

```text
PGDATA/base/<database_oid>/
```

Example:

```text
base/
├── 1/
├── 5/
├── 16384/
└── 24576/
```

Map database OIDs through:

```sql
SELECT
    oid AS database_oid,
    datname
FROM pg_database
ORDER BY oid;
```

Conceptually:

```text
Logical database
       ↓
Database OID
       ↓
base/<database_oid>/
       ↓
Relation files
```

The numeric directory directly beneath `base/` identifies a database, not a relation.

---

## 4.2.7 `global/` — Cluster-Wide Relations

`global/` contains relations shared across the PostgreSQL cluster rather than belonging to a single database.

```text
base/
  ↓
database-specific relations

global/
  ↓
cluster-wide relations
```

`global/` is critical PostgreSQL-managed storage and must never be treated as a filesystem cleanup target.

---

## 4.2.8 Logical Identity vs. Physical Identity

One of the most important physical-storage distinctions is:

```text
Relation OID
     │
     └── Logical/catalog identity

Physical filenode / relfilenumber
     │
     └── Physical storage identity
```

Do not assume:

```text
relation OID == physical filename
```

Operations that rewrite a relation can change its physical storage identity while preserving the logical PostgreSQL object.

This distinction is essential during filesystem investigations.

---

## 4.2.9 Logical Relation → Physical File Mapping

PostgreSQL provides supported functions for mapping logical objects to physical storage.

### Physical filenode

```sql
SELECT
    pg_relation_filenode('public.orders'::regclass);
```

### Relative physical path

```sql
SELECT
    pg_relation_filepath('public.orders'::regclass);
```

Conceptually:

```text
public.orders
      ↓
PostgreSQL catalog
      ↓
physical filenode
      ↓
relative storage path
```

This is safer than manually assuming a numeric filesystem name corresponds to a relation OID.

---

## 4.2.10 Physical File → Logical Relation Mapping

PostgreSQL also provides a reverse mapping mechanism:

```sql
pg_filenode_relation()
```

Conceptually:

```text
Filesystem file
      ↓
Filenode
      +
Tablespace
      ↓
pg_filenode_relation()
      ↓
PostgreSQL relation
```

This supports an important SRE workflow:

```text
Filesystem alert
      ↓
Large physical file
      ↓
Identify tablespace/database
      ↓
Determine filenode
      ↓
Map to PostgreSQL relation
      ↓
Identify application object
```

Physical-to-logical mapping should be preferred over guessing file ownership.

---

## 4.2.11 Relation Forks

A PostgreSQL relation can contain several physical forks.

| Fork | Purpose                                    |
| ---- | ------------------------------------------ |
| Main | Primary table/index data                   |
| FSM  | Free Space Map                             |
| VM   | Visibility Map                             |
| Init | Initialization fork for unlogged relations |

Example:

```text
16384
16384_fsm
16384_vm
16384_init
```

Conceptually:

```text
Relation
│
├── Main
├── FSM
├── VM
└── Init       where applicable
```

The FSM helps PostgreSQL locate pages with reusable free space.

The VM tracks page visibility information important to VACUUM and index-only scans.

The initialization fork is associated with unlogged relations.

These structures are examined in greater detail in Section 4.3.

---

## 4.2.12 Relation Segmentation

Large relations are divided into multiple operating-system files.

With standard PostgreSQL build parameters, relation segments are normally approximately 1 GiB.

For example:

```text
16384
16384.1
16384.2
16384.3
```

Therefore:

```bash
ls -lh 16384
```

does not necessarily reveal the complete relation size.

Additionally, the relation may have:

```text
16384_fsm
16384_vm
```

and associated indexes and TOAST relations.

Prefer PostgreSQL sizing functions for logical capacity analysis.

---

## 4.2.13 Important `pg_relation_filepath()` Limitation

`pg_relation_filepath()` is useful for locating a relation, but it should not be interpreted as an inventory of every physical file associated with that relation.

Conceptually:

```text
pg_relation_filepath()
        ↓
main relation path
        │
        ├── segment .1 may exist
        ├── segment .2 may exist
        ├── _fsm may exist
        ├── _vm may exist
        └── _init may exist
```

Therefore:

> **Use physical path functions for mapping and PostgreSQL size functions for capacity measurement.**

---

## 4.2.14 Relation Size Functions

A useful storage breakdown is:

```sql
SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    ) AS main_relation,
    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_storage,
    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS indexes,
    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_storage;
```

Conceptually:

```text
pg_relation_size()
       ↓
individual relation fork

pg_table_size()
       ↓
table-associated storage including
TOAST and auxiliary forks

pg_indexes_size()
       ↓
associated indexes

pg_total_relation_size()
       ↓
table-associated storage + indexes
```

Filesystem inspection and PostgreSQL sizing functions answer different questions and should be used together.

---

## 4.2.15 `pg_wal/` — Write-Ahead Log

WAL normally resides beneath:

```text
PGDATA/pg_wal/
```

WAL supports:

* transaction durability;
* crash recovery;
* physical replication;
* point-in-time recovery;
* backup/recovery workflows.

Conceptually:

```text
Transaction
    ↓
Database modification
    ↓
WAL generated
    ↓
WAL persisted
    ↓
Recovery / replication / archival
```

`pg_wal` requires independent capacity monitoring because abnormal retention can consume substantial storage.

---

## 4.2.16 WAL Generation vs. WAL Retention

Always distinguish:

```text
WAL generation
      ≠
WAL retention
```

Normal lifecycle:

```text
Transactions
     ↓
WAL generated
     ↓
Replication/archive requirements satisfied
     ↓
Older WAL recycled or removed
```

Retention problem:

```text
WAL generated
     ↓
Slot / replica / archive requirement
     ↓
WAL remains required
     ↓
pg_wal grows
     ↓
Filesystem pressure
```

Potential causes include:

* replication slots;
* lagging standbys;
* failed WAL archiving;
* unusually high write volume;
* bulk operations;
* backup/recovery activity;
* configuration interacting with WAL retention.

---

## 4.2.17 Never Manually Clean `pg_wal`

This is **not** an acceptable disk-full remediation:

```bash
rm -f $PGDATA/pg_wal/*
```

The correct approach is:

```text
pg_wal growth
     ↓
Determine why WAL remains required
     ↓
Slot?
Replica?
Archive failure?
Workload spike?
     ↓
Correct root cause
     ↓
Allow PostgreSQL to manage WAL lifecycle
```

Blind deletion can destroy required recovery state and turn a capacity incident into a database-recovery incident.

---

## 4.2.18 `pg_xact/`

`pg_xact/` stores transaction commit-status information required by PostgreSQL transaction visibility and MVCC.

```text
PGDATA/
└── pg_xact/
```

This is critical internal metadata.

It must never be manually cleaned to recover disk space.

---

## 4.2.19 `pg_multixact/`

`pg_multixact/` stores MultiXact state used when multiple transactions need to be represented in connection with tuple locking.

Operationally, it is relevant to:

* row locking;
* VACUUM;
* transaction-age maintenance;
* MultiXact wraparound protection.

It is PostgreSQL-managed internal state and must not be manually deleted.

---

## 4.2.20 `pg_subtrans/`

`pg_subtrans/` contains subtransaction status information.

Subtransactions may arise from:

* savepoints;
* exception handling;
* nested transactional behavior.

The directory is PostgreSQL-managed and should not be manually manipulated.

---

## 4.2.21 `pg_commit_ts/`

`pg_commit_ts/` stores commit timestamp information when commit-timestamp tracking is enabled.

Its storage significance depends on configuration and workload.

As with other internal transaction metadata, PostgreSQL should manage its lifecycle.

---

## 4.2.22 `pg_replslot/` — Replication Slot State

`pg_replslot/` contains persistent replication-slot state.

```text
PGDATA/
└── pg_replslot/
       ├── slot_a/
       └── slot_b/
```

A replication slot can create two distinct storage-related risks:

```text
Replication Slot
       │
       ├── WAL retention
       │
       └── VACUUM cleanup horizon
```

A stopped or lagging consumer can cause required WAL to remain available:

```text
Consumer stops
      ↓
Slot remains
      ↓
Required WAL retained
      ↓
pg_wal grows
      ↓
Capacity risk
```

---

## 4.2.23 Replication Slot Diagnostics

Initial slot inspection:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn,
    xmin,
    catalog_xmin
FROM pg_replication_slots;
```

A useful WAL-distance diagnostic is:

```sql
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            restart_lsn
        )
    ) AS wal_distance_from_restart_lsn
FROM pg_replication_slots
WHERE restart_lsn IS NOT NULL;
```

This represents LSN distance and should not be interpreted as an exact measurement of physical bytes currently occupying `pg_wal`.

For PostgreSQL versions exposing the relevant columns, also inspect indicators such as:

```text
wal_status
safe_wal_size
```

because they provide additional information about slot/WAL risk.

---

## 4.2.24 Replication Slot Safety

Do not use this generic remediation:

```text
Slot retaining WAL
       ↓
DROP SLOT
```

Before modifying or dropping a slot, determine:

* who owns it;
* whether it is physical or logical;
* which system consumes it;
* whether the consumer will recover;
* whether CDC/logical replication requires reinitialization;
* whether required WAL can safely be lost;
* the RPO/recovery implications.

The correct process is:

```text
Large slot-related WAL retention
          ↓
Identify consumer
          ↓
Determine recovery strategy
          ↓
Coordinate with owner
          ↓
Apply supported remediation
          ↓
Validate replication/CDC
```

---

## 4.2.25 `pg_logical/`

`pg_logical/` contains state associated with logical decoding and logical replication infrastructure.

Logical replication can indirectly become a storage-capacity concern:

```text
Logical consumer lag
       ↓
Replication slot cannot advance
       ↓
WAL retained
       ↓
pg_wal growth
```

Logical replication health should therefore be correlated with WAL capacity monitoring.

---

## 4.2.26 `pg_tblspc/` — Tablespace References

`pg_tblspc/` contains references to non-built-in PostgreSQL tablespaces.

Conceptually:

```text
PGDATA/
└── pg_tblspc/
      │
      ├── <tablespace_oid> ──► /storage/fast
      └── <tablespace_oid> ──► /storage/archive
```

This means PostgreSQL storage may span several independent filesystems:

```text
PGDATA filesystem
       +
FAST tablespace filesystem
       +
ARCHIVE tablespace filesystem
```

Therefore:

> **Monitoring only the `PGDATA` filesystem is insufficient when tablespaces exist.**

---

## 4.2.27 Tablespace Inspection

List tablespaces:

```sql
SELECT
    oid,
    spcname,
    pg_tablespace_location(oid) AS location
FROM pg_tablespace
ORDER BY spcname;
```

Each tablespace should be independently monitored for:

* capacity;
* free bytes;
* growth;
* latency;
* IOPS;
* throughput;
* filesystem errors;
* availability.

Do not manually redefine or manipulate `pg_tblspc` links as part of routine storage remediation.

Use PostgreSQL-supported tablespace procedures and documented maintenance workflows.

---

## 4.2.28 Tablespace Physical Layout

A non-default tablespace introduces another physical mapping layer:

```text
PGDATA/
└── pg_tblspc/
       │
       └── <tablespace_oid>
                │
                ▼
        External location
                │
                ▼
      PostgreSQL-version-specific
             directory
                │
                ▼
         <database_oid>/
                │
                ▼
          Relation files
```

Storage investigations may therefore require both:

```text
tablespace OID
       +
database OID
       +
physical filenode
```

to map the filesystem path to a logical PostgreSQL object.

---

## 4.2.29 Temporary Files and `pgsql_tmp`

PostgreSQL creates temporary files for operations that cannot remain entirely in memory.

Examples include:

* sorts;
* hash operations;
* materialization;
* temporary relations;
* index creation;
* analytical queries.

Temporary files can appear in PostgreSQL-managed `pgsql_tmp` locations associated with the applicable tablespace.

Conceptually:

```text
Large query
    ↓
Memory insufficient
    ↓
Temporary spill
    ↓
pgsql_tmp
    ↓
Storage I/O
```

Temporary-file growth can cause both latency and capacity incidents.

---

## 4.2.30 Temporary Storage Monitoring

Database-level telemetry includes:

```sql
SELECT
    datname,
    temp_files,
    pg_size_pretty(temp_bytes) AS temp_written
FROM pg_stat_database
ORDER BY temp_bytes DESC;
```

These values are cumulative.

Therefore:

```text
temp_bytes
     ↓
Historical total

Δ temp_bytes / time
     ↓
Temporary-write rate
     ↓
Operationally useful signal
```

During an incident, determine whether the temporary workload is associated with:

* a new analytical query;
* execution-plan changes;
* increased concurrency;
* memory configuration;
* index creation;
* maintenance activity.

Do not blindly delete active PostgreSQL temporary files.

---

## 4.2.31 `pg_twophase/`

`pg_twophase/` stores state associated with prepared transactions used by two-phase commit.

Inspect prepared transactions with:

```sql
SELECT *
FROM pg_prepared_xacts;
```

Long-lived prepared transactions can retain transactional resources and complicate maintenance.

Do not manually clean this directory.

---

## 4.2.32 `pg_notify/`

`pg_notify/` contains internal state related to PostgreSQL asynchronous notification mechanisms such as:

```sql
LISTEN channel_name;
```

and:

```sql
NOTIFY channel_name;
```

It is PostgreSQL-managed state and should not be manually manipulated.

---

## 4.2.33 Statistics and Runtime State

Directories such as:

```text
pg_stat/
pg_stat_tmp/
```

may be associated with statistics/runtime state depending on PostgreSQL version and configuration.

SRE monitoring should primarily use PostgreSQL-supported statistics interfaces rather than filesystem inspection.

Examples include:

```text
pg_stat_database
pg_stat_user_tables
pg_stat_user_indexes
pg_stat_io
pg_stat_wal
pg_stat_replication
```

Availability and details depend on PostgreSQL version.

---

## 4.2.34 `PG_VERSION`

`PG_VERSION` identifies the PostgreSQL major version associated with the data directory.

For example:

```bash
cat $PGDATA/PG_VERSION
```

might return:

```text
18
```

This is important during:

* startup troubleshooting;
* upgrades;
* recovery;
* filesystem migration;
* accidental data-directory selection.

A data directory from one PostgreSQL major version must not simply be attached to incompatible server binaries.

Use supported major-version upgrade or migration procedures.

---

## 4.2.35 `postmaster.pid`

While PostgreSQL is running, `postmaster.pid` contains information associated with the active server.

A dangerous troubleshooting pattern is:

```text
PostgreSQL will not start
       ↓
postmaster.pid exists
       ↓
Delete it
```

Instead:

```text
Startup conflict
      ↓
Check PostgreSQL processes
      ↓
Check service manager
      ↓
Verify PID
      ↓
Verify PGDATA
      ↓
Confirm no server is using directory
      ↓
Determine whether PID file is stale
      ↓
Only then remediate
```

Two PostgreSQL server processes must never be allowed to operate against the same data directory.

---

## 4.2.36 `postmaster.opts`

`postmaster.opts` records startup command-line options.

It can assist troubleshooting, but the complete startup configuration may involve:

```text
systemd/service manager
        +
container command
        +
environment
        +
PostgreSQL configuration
        +
startup options
```

Do not interpret `postmaster.opts` in isolation.

---

## 4.2.37 `postgresql.auto.conf`

Settings changed with:

```sql
ALTER SYSTEM
```

are written to:

```text
postgresql.auto.conf
```

When investigating effective configuration, consider:

```text
postgresql.conf
       +
included configuration
       +
postgresql.auto.conf
       +
startup parameters
```

Use PostgreSQL itself to determine effective values:

```sql
SELECT
    name,
    setting,
    source,
    sourcefile,
    sourceline
FROM pg_settings
WHERE name = 'shared_buffers';
```

This is generally safer than reasoning from configuration files alone.

---

## 4.2.38 Physical Storage Mapping Toolkit

A production SRE/DBRE should be comfortable with the following toolkit:

```sql
-- Active data directory
SHOW data_directory;

-- Configuration locations
SHOW config_file;
SHOW hba_file;
SHOW ident_file;

-- Database OIDs
SELECT
    oid,
    datname
FROM pg_database
ORDER BY oid;

-- Tablespaces
SELECT
    oid,
    spcname,
    pg_tablespace_location(oid)
FROM pg_tablespace
ORDER BY spcname;

-- Relation physical filenode
SELECT
    pg_relation_filenode('public.orders'::regclass);

-- Relation relative physical path
SELECT
    pg_relation_filepath('public.orders'::regclass);

-- Relation storage
SELECT
    pg_size_pretty(
        pg_total_relation_size('public.orders')
    );

-- Replication slots
SELECT *
FROM pg_replication_slots;
```

The operational objective is to move confidently between:

```text
PostgreSQL logical object
        ↕
PostgreSQL catalog
        ↕
Physical path
        ↕
Filesystem
        ↕
Storage platform
```

---

## 4.2.39 Filesystem Investigation

Operating-system commands are useful for identifying capacity problems.

Typical Linux examples include:

```bash
df -h
```

for filesystem capacity and:

```bash
df -i
```

for inode usage.

Directory analysis can use controlled commands such as:

```bash
du -sh <path>
```

The production rule is:

> **Filesystem tools tell you where bytes are consumed. PostgreSQL metadata tells you what those bytes mean.**

Use both.

---

## 4.2.40 Disk-Full Severity Model

Organizations should classify capacity incidents by both utilization and time remaining.

Example policy:

| Forecast                       | Example Severity |
| ------------------------------ | ---------------- |
| >30 days to exhaustion         | Advisory         |
| 14–30 days                     | Warning          |
| 7–14 days                      | High             |
| <7 days                        | Critical         |
| <24 hours                      | Emergency        |
| Writes failing/filesystem full | SEV-1 candidate  |

These are example operational thresholds, not PostgreSQL-defined limits.

The stronger SRE signal is:

```text
Time remaining before service impact
```

---

## 4.2.41 Disk-Full Incident Priority

When PostgreSQL storage approaches exhaustion:

```text
1. Protect database integrity
          ↓
2. Protect recoverability
          ↓
3. Stop uncontrolled growth
          ↓
4. Obtain safe additional capacity
          ↓
5. Correct root cause
          ↓
6. Restore operational headroom
          ↓
7. Validate database and replicas
```

The immediate goal is not simply to free a few gigabytes.

It is to prevent database failure without compromising durability or recovery.

---

## 4.2.42 Disk-Full Decision Tree

```text
                    STORAGE ALERT
                          │
                          ▼
                Which filesystem?
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
       PGDATA         Tablespace       External
          │               │           archive/
          │               │            backup
          └───────┬───────┘
                  ▼
          PostgreSQL consumer
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
     DATA        WAL        TEMP
       │          │          │
       ▼          ▼          ▼
 Relation      Why WAL      Which
 growth?       retained?    workload?
       │          │          │
       └──────────┼──────────┘
                  ▼
              Root cause
                  │
                  ▼
         Supported remediation
                  │
                  ▼
           Restore headroom
                  │
                  ▼
             Validation
```

**Classification comes before deletion.**

---

## 4.2.43 Data-Growth Incident Path

When `base/` or a tablespace is growing:

```text
Storage growth
      ↓
Which database?
      ↓
Which relation?
      ↓
Heap / index / TOAST?
      ↓
Expected growth?
   ┌──────┴──────┐
  YES            NO
   │              │
   ▼              ▼
Capacity      Investigate
planning      workload/bloat
```

Investigate questions such as:

* Was a bulk load performed?
* Did retention change?
* Was a new index created?
* Did a table rewrite occur?
* Did a migration duplicate data?
* Is table/index bloat increasing?

---

## 4.2.44 WAL-Growth Incident Path

When `pg_wal` grows:

```text
pg_wal growth
     ↓
Generation unusually high?
     ↓
Retention abnormal?
     ↓
Replication slot?
     ↓
Replica lag?
     ↓
Archive failure?
     ↓
Backup/recovery?
     ↓
Root cause
```

Never make manual WAL deletion part of this decision tree.

---

## 4.2.45 Temporary-Storage Incident Path

```text
Temporary storage growth
        ↓
Which database?
        ↓
Which workload?
        ↓
Sort/hash/materialization?
        ↓
Expected?
     ┌────┴────┐
    YES        NO
     │          │
     ▼          ▼
Capacity    Query/plan
review      investigation
```

Correlate temporary-write rate with workload, query plans, memory configuration, and storage latency.

## 4.2.47 Storage Expansion Decision

If exhaustion is approaching:

```text
Can root cause be corrected
before storage exhaustion?
        │
     ┌──┴──┐
    YES    NO
     │      │
     ▼      ▼
Correct   Expand
cause     storage
     │      │
     └──┬───┘
        ▼
Restore headroom
        ↓
Permanent remediation
```

In many production incidents, adding capacity first is safer than attempting aggressive cleanup under time pressure.

## 4.2.48 Volume Expansion vs. Filesystem Expansion

Increasing the underlying volume does not necessarily increase usable filesystem capacity automatically.

Conceptually:

```text
Cloud/block volume
       ↓
Block device
       ↓
Partition/LVM
       ↓
Filesystem
       ↓
PostgreSQL-visible capacity
```

For example:

```text
Volume:       500 GB → 1 TB
Filesystem:   still 500 GB
```

is possible.

Always validate the complete storage stack after expansion.

Environment-specific commands belong in platform runbooks.

## 4.2.54 Automation Principles

Good candidates for automation include:

```text
✓ Collect database sizes
✓ Collect relation sizes
✓ Collect tablespace locations
✓ Calculate growth rates
✓ Forecast exhaustion
✓ Detect WAL anomalies
✓ Detect replication-slot risk
✓ Detect temporary-file spikes
✓ Attach diagnostic context to alerts
✓ Open incidents/tickets
```

Dangerous automation includes:

```text
✗ Delete WAL automatically
✗ Drop replication slots automatically
✗ Delete relation files automatically
✗ Delete transaction metadata
✗ Remove unknown PostgreSQL files
```

The production principle is:

> **Automate observation, correlation, forecasting, and diagnosis aggressively. Treat destructive remediation as a separately controlled operation.**

## 4.2.55 Production Anti-Patterns

### Anti-pattern 1 — Deleting WAL

```bash
rm -f $PGDATA/pg_wal/*
```

**Risk:** recovery and replication failure.

### Anti-pattern 2 — Dropping a slot because WAL is large

```text
Large WAL
   ↓
DROP SLOT
```

**Risk:** replication/CDC reinitialization or data continuity impact.

### Anti-pattern 3 — Blindly deleting `postmaster.pid`

```text
PID file exists
      ↓
delete
```

**Risk:** multiple servers accessing the same data directory.

### Anti-pattern 4 — Monitoring only `PGDATA`

```text
PGDATA 50%
      ↓
Everything healthy
```

while:

```text
Tablespace 99%
```

### Anti-pattern 5 — Assuming volume expansion solved capacity

```text
Volume expanded
      ↓
Incident closed
```

without validating filesystem capacity.

### Anti-pattern 6 — Deleting unknown numeric files

```text
Large file named 24576
        ↓
Delete
```

**Risk:** deleting a PostgreSQL relation.

## 4.2.56 Post-Remediation Validation

A storage incident is not resolved simply because free space has increased.

Validate:

```text
Filesystem capacity
        ↓
PostgreSQL availability
        ↓
Read/write capability
        ↓
WAL behavior
        ↓
Replication
        ↓
Archiving
        ↓
Tablespaces
        ↓
Application connectivity
        ↓
Storage latency
```

At minimum confirm:

* PostgreSQL accepts connections;
* expected databases are available;
* read/write transactions succeed where applicable;
* replication is healthy;
* WAL growth has normalized;
* archive failures are resolved;
* tablespaces remain accessible;
* free capacity exceeds the operational threshold;
* storage performance is healthy;
* the original growth mechanism is controlled.

## 4.2.57 Restore Headroom, Not Merely Service

This is not sufficient:

```text
Disk full
   ↓
Free 5 GB
   ↓
PostgreSQL works
   ↓
Close incident
```

If the database is growing at 10 GB/hour, the incident remains active.

The correct completion criteria are:

```text
Service restored
       +
Root cause controlled
       +
Operational headroom restored
       +
Capacity forecast acceptable
       =
Incident resolved
```

## 4.2.60 Key Production Principles

**1. Verify the actual data directory.**

```sql
SHOW data_directory;
```

Do not rely solely on shell environment variables.

**2. Separate configuration location from data location.**

Use PostgreSQL to identify the active files.

**3. Do not equate relation OIDs with physical filenames.**

Use supported mapping functions.

**4. Use PostgreSQL functions for relation sizing.**

Filesystem files alone do not provide the complete logical size.

**5. Monitor every tablespace independently.**

A healthy `PGDATA` filesystem does not guarantee storage health.

**6. Treat WAL growth as a symptom requiring diagnosis.**

Never blindly delete WAL.

**7. Treat replication slots as both WAL-retention and cleanup-horizon concerns.**

Understand the consumer before remediation.

**8. Investigate temporary storage through the workload.**

Do not treat active PostgreSQL temporary files as generic cleanup targets.

**9. Verify the entire expansion stack.**

```text
Volume → Device → Filesystem → PostgreSQL
```

**10. Restore operational headroom before closing an incident.**

A few newly freed gigabytes do not constitute sustainable recovery.
