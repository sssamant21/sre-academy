# 4.20 -- Storage Alerting and Capacity Thresholds

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Storage alerts must provide enough lead time for safe intervention. Static utilization percentages are useful but insufficient; production alerting should combine utilization, absolute free capacity, growth rate, runway, performance, workload context, and expansion lead time.

## Alert Model

```text
Current utilization
+ free bytes
+ growth velocity
+ runway
+ I/O health
+ workload/maintenance context
= operational severity
```

## Severity Design

Use environment-specific thresholds. Warning should create planning time; critical should trigger immediate investigation while safe remediation options remain; emergency indicates imminent SLO or availability risk. Thresholds must reflect volume size, workload burstiness, largest credible operation, storage scaling constraints, and on-call response time.

## Predictive Alerts

Examples of useful conditions include runway below expansion lead time, abnormal acceleration in growth, WAL/temp volume approaching reserved envelope, sustained high storage latency, vacuum backlog plus shrinking runway, and replica storage divergence.

Do not page solely because a large relation crosses an arbitrary size.

## Alert Content

Every actionable storage alert should identify cluster/environment, affected volume/tablespace where known, current used/free capacity, recent growth rate, estimated runway, top growth contributors where available, related I/O health, and a runbook link or first-response procedure.

## Failure Scenarios

**80% alert arrives too late:** high growth consumes remaining capacity before change approval. Add runway-based alerting.

**Percent alert too noisy:** large stable volumes remain above threshold for months. Combine percentage with free bytes and trajectory.

**No alert on separate WAL volume:** aggregate database capacity is healthy. Alert independently by failure domain.

## Response Procedure

1. Validate telemetry.
2. Calculate free bytes and runway.
3. Identify growth source.
4. Check WAL/temp/maintenance separately.
5. Check I/O and application impact.
6. Determine expansion or workload-control options.
7. Escalate before emergency headroom is consumed.
8. Verify recovery and update forecast.

## Production Rules

1. Alert before safe remediation options disappear.
2. Use percentage, free bytes, and runway together.
3. Alert independent storage domains independently.
4. Include performance alerts as well as capacity alerts.
5. Make alerts actionable and runbook-linked.
6. Tune thresholds from actual workload and expansion lead time.
7. Review false positives, false negatives, and incident learnings regularly.
