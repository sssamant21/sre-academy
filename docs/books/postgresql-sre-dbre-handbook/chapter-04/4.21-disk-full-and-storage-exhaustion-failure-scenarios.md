# 4.21 -- Disk-Full and Storage-Exhaustion Failure Scenarios

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Storage exhaustion is a high-severity PostgreSQL failure domain. Effects depend on which storage domain fills and which operation needs space. Prevention and early stabilization are safer than improvising destructive cleanup after capacity reaches zero.

## Failure Domains

Potential exhaustion points include the main data filesystem, tablespace volumes, `pg_wal`, temporary-storage locations, Kubernetes PVC/ephemeral storage, managed-service allocated storage, and supporting backup/archive destinations.

## Symptoms

Expect write failures, transaction errors, inability to extend relations, WAL/archive pressure, temp-file failures, maintenance failures, degraded latency, replica problems, or database availability impact. Exact behavior depends on the failing path and operation.

## First Response

```text
Alert -> validate volume -> free bytes/runway
      -> identify growth source
      -> protect remaining capacity
      -> expand/control workload
      -> recover safely
```

1. Confirm the actual full/near-full storage domain.
2. Measure free bytes and current growth.
3. Identify top PostgreSQL and non-PostgreSQL consumers.
4. Check WAL, temp, tablespaces, logs, and active maintenance separately.
5. Stop optional growth-producing work when approved.
6. Expand storage using supported mechanisms where possible.
7. Resolve retention/vacuum/transaction blockers safely.
8. Restore service and validate writes, replication, backup, and application SLOs.

## Critical Safety Rules

Never manually delete PostgreSQL relation files, WAL segments, FSM/VM/TOAST files, or unknown files from PGDATA to create space. Do not blindly run `VACUUM FULL` on an almost-full volume; a rewrite can require additional working space. Do not disable durability or safety mechanisms as an improvised capacity fix.

## Scenario -- WAL Volume Fills

Investigate WAL generation, archive failures, replication slots, standby/consumer health, and retention settings. Fix the retaining cause or safely increase capacity. Never remove PostgreSQL-managed WAL manually.

## Scenario -- Temp Storage Fills

Identify spill-heavy queries and concurrency, stop optional offenders when safe, restore capacity, and tune plans/workload-specific memory rather than globally raising `work_mem` without concurrency analysis.

## Scenario -- Tablespace Fills

Identify objects on the affected tablespace, growth source, and supported expansion/migration options. Other volumes being healthy does not protect an exhausted tablespace.

## Scenario -- Kubernetes Storage Pressure

Determine whether the issue is PVC capacity, node ephemeral storage, quota, StorageClass limits, or underlying cloud-volume performance/capacity. Use operator- and platform-supported expansion/recovery procedures.

## Post-Incident

Preserve timeline and telemetry, identify why forecast/alerting failed or why remediation lagged, update capacity model and thresholds, remove temporary mitigations, validate backups/replicas, and create durable prevention actions.

## Production Rules

1. Treat disk-full risk as an availability incident.
2. Identify the exact storage failure domain first.
3. Stabilize growth before aggressive reclamation.
4. Prefer supported expansion over risky emergency compaction when available.
5. Never manually delete PostgreSQL-managed files.
6. Validate replication, backups, and application writes after recovery.
7. Every storage-exhaustion incident requires RCA and forecast/alert review.
