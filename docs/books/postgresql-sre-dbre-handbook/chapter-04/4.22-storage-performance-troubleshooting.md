# 4.22 -- Storage Performance Troubleshooting

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Storage troubleshooting must distinguish a true storage bottleneck from query, locking, memory, checkpoint, WAL, vacuum, backup, or concurrency problems that merely present as I/O symptoms.

## Troubleshooting Flow

```text
Application symptom
      |
PostgreSQL workload/waits
      |
Cache and physical I/O
      |
Storage metrics and limits
      |
Concurrent maintenance
      |
Root cause and remediation
```

## Step 1 -- Define the Symptom

Record start time, affected services/databases, read vs write impact, latency/error profile, and whether the issue is continuous or periodic. Preserve a baseline comparison.

## Step 2 -- PostgreSQL Evidence

Review active sessions, wait events, slow queries, checkpoints, WAL behavior, vacuum, temp spills, and available I/O statistics for the deployed PostgreSQL version. Avoid assuming every slow query is storage-bound.

## Step 3 -- Infrastructure Evidence

Inspect read/write latency, IOPS, throughput, queue depth, burst/balance metrics where applicable, filesystem/PVC health, device errors, and provisioned limits. Correlate timestamps with PostgreSQL and application telemetry.

## Common Patterns

**Random-read latency:** poor cache locality, large working set, inefficient plans, or storage latency.

**Write latency:** WAL flush pressure, checkpoint activity, storage saturation, or platform limits.

**Periodic spikes:** checkpoints, backups, scheduled batch, vacuum, snapshots, or external platform activity.

**High queue with flat throughput:** possible storage ceiling or overloaded device.

**High IOPS with healthy latency:** not automatically a problem.

## Remediation Hierarchy

1. Remove or throttle optional concurrent pressure.
2. Correct pathological queries/plans or spill behavior.
3. Correct checkpoint/vacuum scheduling or configuration when evidence supports it.
4. Increase storage IOPS/throughput or redesign storage placement when limits are real.
5. Re-test against application SLOs.

## Failure Scenarios

**Storage upgraded but problem remains:** root cause was query amplification. Always prove the bottleneck first.

**Global memory increase hides spills but causes memory pressure:** tune workload-specific settings and plans with concurrency analysis.

**Maintenance repeatedly causes latency incidents:** incorporate maintenance into capacity budgets and scheduling.

## Production Rules

1. Troubleshoot from correlated timestamps and layers.
2. Prove storage saturation before scaling storage.
3. Interpret latency, IOPS, throughput, and queue together.
4. Include WAL, checkpoints, vacuum, temp, backups, and rewrites in analysis.
5. Validate remediation at the application SLO layer.
6. Preserve incident evidence for recurrence analysis.
