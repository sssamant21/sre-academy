# 4.23 -- Emergency Storage Recovery and Remediation

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Emergency storage recovery prioritizes data integrity, service stabilization, and preservation of safe recovery options. The fastest-looking action is not always the safest action.

## Incident Priorities

```text
Protect integrity -> stop uncontrolled growth -> restore headroom
-> restore service -> validate HA/backup -> permanent remediation
```

## Triage

1. Declare ownership and incident severity.
2. Identify the exact volume/tablespace/storage service at risk.
3. Measure free bytes, growth rate, and estimated runway.
4. Identify top growth sources: relations, WAL, temp, logs, backups, batch/maintenance.
5. Check application errors, replication, and storage performance.
6. Preserve telemetry and command history.

## Stabilization Options

Prefer reversible and supported actions: pause optional batch/ETL/purge/index-build work, throttle high-growth workloads, fix failed WAL archiving/consumers, resolve approved transaction blockers, or expand storage using platform-supported procedures.

Do not improvise deletion inside PGDATA or `pg_wal`.

## Reclamation Decision

Only after stabilization, determine whether storage is live data, reusable relation space, removable external artifacts, temporary workload, retained WAL, or genuine bloat. Select remediation appropriate to that category. Rewrites require working capacity and change control.

## Recovery Validation

Validate successful writes/commits, checkpoints/WAL health, replication, archive/backup operation, vacuum recovery, storage latency, application SLOs, and restored runway. Continue heightened monitoring until growth is understood and stable.

## Managed and Kubernetes Environments

Use provider-supported storage modification and recovery for managed PostgreSQL. In Kubernetes, validate PVC expansion, filesystem resize, StorageClass/operator behavior, node ephemeral storage, topology, and failover implications. Never bypass the operator by manipulating database files directly.

## Failure Scenarios

**Manual WAL deletion:** can destroy recoverability or prevent normal operation. Fix the retention cause instead.

**Emergency `VACUUM FULL`:** can fail from insufficient working space and create locking/I/O/WAL pressure. Expand/stabilize first.

**Restart as cleanup:** restart does not generally solve persistent relation/WAL capacity causes and can complicate an already fragile incident.

## Post-Recovery

Remove temporary throttles carefully, reconcile data/replicas/backups, update forecast and alerts, document root cause and contributing factors, and create prevention actions with owners and dates.

## Production Rules

1. Data integrity outranks cosmetic space reclamation.
2. Stabilize before optimizing.
3. Prefer reversible, supported actions.
4. Never manually delete PostgreSQL-managed data or WAL files.
5. Protect HA and backup capability throughout recovery.
6. Validate the application, not only the filesystem.
7. Require RCA after emergency storage intervention.
