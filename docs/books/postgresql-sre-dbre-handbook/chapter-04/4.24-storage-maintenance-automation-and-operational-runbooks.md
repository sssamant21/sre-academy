# 4.24 -- Storage Maintenance, Automation, and Operational Runbooks

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose

Storage operations should be repeatable, observable, version-controlled, and safe to execute under pressure. Automation should aggressively collect evidence and forecast risk while destructive actions remain gated by explicit production controls.

## Maintenance Program

Routine operations should include capacity/growth review, top-growing-object analysis, vacuum/MVCC health, WAL/temp review, storage performance review, tablespace/volume health, backup/replication correlation, and validation of alert/runbook readiness.

## Automation Architecture

```text
Collectors -> metrics/history -> analysis/forecast
                         |
                         v
                    alerts/runbooks
                         |
              +----------+----------+
              |                     |
       safe automation       approved actions
```

## Safe Automation

Automate database/relation/index/TOAST sizing, dead-tuple trends, vacuum history, oldest-transaction detection, WAL/temp metrics, filesystem/PVC/provider capacity, growth/runway forecasting, I/O telemetry, replication correlation, and report generation.

## Approval-Gated Automation

Require explicit controls for backend termination, large DELETE/TRUNCATE, `VACUUM FULL`, CLUSTER, REINDEX, tablespace moves, object drops, storage changes with availability impact, and major autovacuum changes.

## Runbook Standard

Every storage runbook should define purpose, scope, prerequisites, permissions, preflight, exact commands/queries, expected output, go/no-go criteria, monitoring, abort conditions, rollback/recovery, validation, escalation, and evidence to retain.

## Example Capacity Review

1. Review fleet capacity and runway.
2. Identify top-growing clusters and objects.
3. Review WAL/temp anomalies.
4. Review dead tuples, vacuum, and oldest transactions.
5. Review storage latency and provisioned limits.
6. Review upcoming migrations/maintenance.
7. Open capacity/remediation work before warning runway is breached.
8. Record decisions and forecast changes.

## Change Safety

High-impact maintenance must have an owner, maintenance window where required, replication/HA validation, backup/recovery readiness, capacity preflight, application monitoring, abort criteria, and post-change validation.

## Failure Scenarios

**Automation runs `VACUUM FULL` at 90%:** unsafe because the operation may need additional space and strong locking. Automation should alert and recommend controlled options instead.

**Runbook has commands but no abort criteria:** operators continue while latency and replica lag deteriorate. Define measurable stop conditions.

**Monitoring automation silently fails:** capacity history disappears. Monitor the monitoring pipeline and alert on stale data.

## Production Rules

1. Automate evidence collection and forecasting first.
2. Gate destructive actions.
3. Version-control runbooks and configuration.
4. Test runbooks outside incidents.
5. Include rollback, abort, HA, backup, and SLO validation.
6. Monitor automation health itself.
7. Review automation after every relevant incident.
