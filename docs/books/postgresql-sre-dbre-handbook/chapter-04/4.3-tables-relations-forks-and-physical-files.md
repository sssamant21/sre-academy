## 4.3.1 Purpose and Scope

Section 4.2 established how a PostgreSQL cluster maps into PGDATA, database directories, tablespaces, WAL, and supporting state.

This section moves one level deeper:

PostgreSQL Cluster
       ↓
Database
       ↓
Logical Relation
       ↓
Physical Filenode
       ↓
Fork
       ↓
Segment
       ↓
Page / Block

Understanding this hierarchy is essential for:

storage-capacity analysis;
table, index, and TOAST growth;
filesystem investigations;
VACUUM and visibility behavior;
unlogged and temporary relations;
partitioned storage;
relation rewrites;
index builds and rebuilds;
WAL and replication impact;
backup and recovery;
corruption investigations;
production capacity forecasting.

The central production principle is:

A PostgreSQL table is not necessarily one physical file. A single logical table can involve multiple relations, forks, segments, indexes, TOAST structures, and even multiple tablespaces.

## 4.3.2 What Is a PostgreSQL Relation?

PostgreSQL uses relation as a broad internal concept for objects represented through its catalog and relation infrastructure.

Operationally important relation types include:

Relations
│
├── Ordinary tables
├── Indexes
├── Sequences
├── Materialized views
├── TOAST tables
├── Partitioned tables
├── Partitioned indexes
└── Internal/catalog relations

Not every relation has conventional local physical storage.

For example:

Partitioned table
       ↓
Logical hierarchy
       ↓
Rows physically stored
in leaf partitions

Similarly, a normal view has a catalog representation but does not contain a conventional heap storing the result rows.

Therefore:

Relation
   ≠
Always one physical data file
## 4.3.3 Relation Types in pg_class

pg_class is central to relation-level storage investigations.

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relpersistence
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
ORDER BY n.nspname, c.relname;

Important relkind values include:

relkind	Meaning
r	Ordinary table
i	Index
S	Sequence
t	TOAST table
v	View
m	Materialized view
c	Composite type
f	Foreign table
p	Partitioned table
I	Partitioned index

Always determine the relation type before interpreting its storage behavior.

## 4.3.4 Relation Persistence

pg_class.relpersistence identifies the relation's persistence model.

p → permanent
u → unlogged
t → temporary

Conceptually:

Relation
   │
   ├── Permanent
   │      └── normal PostgreSQL durability model
   │
   ├── Unlogged
   │      └── different WAL/recovery semantics
   │
   └── Temporary
          └── session-oriented lifecycle

Do not confuse PostgreSQL relation persistence with infrastructure storage persistence.

For example:

Permanent PostgreSQL table
          +
Ephemeral infrastructure volume
          ≠
Unlogged PostgreSQL table

They are separate architectural concepts.

## 4.3.5 Relation Access Methods

Relations that use storage access methods expose the associated access method through pg_class.relam.

Example:

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    c.relpersistence,
    am.amname AS access_method
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
LEFT JOIN pg_am AS am
  ON am.oid = c.relam
ORDER BY n.nspname, c.relname;

Conceptually:

Relation
    ↓
Access Method
    ↓
Physical Organization

A heap table and a B-tree index are both relations, but their internal page organization is fundamentally different.

Detailed page architecture follows in Section 4.4.

## 4.3.6 Logical Table vs. Physical Storage

Consider:

CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    customer_id bigint NOT NULL,
    notes text
);

Logically:

orders

Physically, PostgreSQL may require:

orders
│
├── Heap relation
│    ├── Main fork
│    ├── FSM fork
│    └── VM fork
│
├── Primary-key index relation
│
├── Additional index relations
│
└── TOAST relation where required
     └── TOAST index

Each sufficiently large fork may then be divided into multiple physical segment files.

Therefore:

One SQL table
      ↓
Potentially several relations
      ↓
Potentially several forks
      ↓
Potentially many OS files
## 4.3.7 Relation OID

A PostgreSQL relation has an object identifier.

SELECT
    'public.orders'::regclass::oid;

or:

SELECT
    c.oid,
    n.nspname,
    c.relname
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE n.nspname = 'public'
  AND c.relname = 'orders';

The OID represents the relation's catalog identity.

However:

Relation OID
      ≠
Guaranteed physical filename

This distinction is critical for production tooling.

## 4.3.8 Physical Filenode

For physically stored relations, PostgreSQL maps the logical object to physical storage.

Useful functions include:

SELECT
    pg_relation_filenode('public.orders'::regclass);

and:

SELECT
    pg_relation_filepath('public.orders'::regclass);

A useful combined diagnostic is:

SELECT
    c.oid AS relation_oid,
    c.relname,
    c.relfilenode,
    pg_relation_filenode(c.oid) AS current_filenode,
    pg_relation_filepath(c.oid) AS filepath
FROM pg_class AS c
WHERE c.oid = 'public.orders'::regclass;

Conceptually:

Logical relation
      ↓
Catalog identity
      ↓
Current physical filenode
      ↓
Physical relation path

pg_relation_filenode() should generally be preferred over blindly assuming that pg_class.relfilenode directly represents every physical mapping case.

## 4.3.9 OID vs. Physical Identity

A relation rewrite can preserve logical identity while changing physical identity.

orders
OID = X
   │
   ├── Before rewrite
   │      filenode = A
   │
   └── After rewrite
          filenode = B

Operations that can involve physical rewrites include, depending on the exact command and PostgreSQL version:

VACUUM FULL;
CLUSTER;
certain ALTER TABLE operations.

Therefore:

Never permanently bind a PostgreSQL logical object to a previously observed physical filenode.

Production monitoring should treat:

Logical identity
      ↓
Stable monitoring identity

Physical filenode
      ↓
Current diagnostic attribute
## 4.3.10 Bidirectional Physical Mapping

Production SREs should be able to investigate in both directions.

Logical → Physical
public.orders
      ↓
OID
      ↓
Tablespace
      ↓
Filenode
      ↓
Fork
      ↓
Segment
      ↓
Filesystem
Physical → Logical

PostgreSQL provides:

pg_filenode_relation()

For example, in the appropriate database:

SELECT
    pg_filenode_relation(0, 24576);

Conceptually:

Tablespace
    +
Filenode
    ↓
pg_filenode_relation()
    ↓
Logical relation

For non-default tablespaces, use the appropriate tablespace OID.

This reverse mapping is especially valuable during filesystem incidents.

## 4.3.11 Relation Fork Architecture

A PostgreSQL relation can contain multiple forks:

Relation
│
├── MAIN
├── FSM
├── VM
└── INIT

Not every relation has every fork.

Each fork has a different purpose and must remain under PostgreSQL's control.

## 4.3.12 Main Fork

The main fork contains the primary contents of the relation.

For a heap table:

Main fork
    ↓
Heap pages
    ↓
Tuple versions

For an index:

Main fork
    ↓
Index-access-method pages

Typical segmented filenames may resemble:

24576
24576.1
24576.2

The term main fork therefore does not imply that the relation is necessarily a heap.

## 4.3.13 Free Space Map — FSM

The Free Space Map records information about available space within relation pages.

Typical naming:

24576_fsm

Conceptually:

INSERT / UPDATE
       ↓
Need reusable page space
       ↓
FSM
       ↓
Candidate page

The FSM helps PostgreSQL locate pages with usable space without scanning every page.

It should not be interpreted as an exact byte-for-byte ledger of free space on every page.

The FSM is PostgreSQL-managed internal state.

## 4.3.14 Visibility Map — VM

The Visibility Map records page-level visibility information.

Typical naming:

24576_vm

It contains two important states:

Visibility Map
      │
      ├── all-visible
      └── all-frozen

Conceptually:

Heap page
   │
   ├── all-visible
   │       ↓
   │   visibility optimization
   │   and index-only scan support
   │
   └── all-frozen
           ↓
       VACUUM/freeze optimization

The VM is important for:

VACUUM efficiency;
freezing;
index-only scans.

However:

Visibility Map
      ≠
Replacement for MVCC
visibility rules

It records conditions under which PostgreSQL can safely avoid certain heap or freezing work.

## 4.3.15 Initialization Fork — INIT

The initialization fork is associated with unlogged relations.

Typical naming:

24576_init

Conceptually:

Unlogged Relation
       │
       ├── Main
       ├── FSM
       ├── VM
       └── Init

The init fork provides the state used to reinitialize an unlogged relation after crash recovery.

This is part of the different durability model of unlogged relations.

## 4.3.16 Unlogged Relations

Example:

CREATE UNLOGGED TABLE staging_events (
    id bigint,
    payload jsonb
);

Unlogged relations reduce WAL requirements for their data compared with ordinary permanent relations, but the trade-off is substantial.

Conceptually:

Unlogged relation
       ↓
Crash / unclean shutdown
       ↓
Contents cannot be recovered
like a normal permanent relation
       ↓
Relation reinitialized

Before using UNLOGGED, evaluate:

Can the data be lost?
Can it be reconstructed?
How long will reconstruction take?
What happens during failover?
What is the replication model?
What is the backup/recovery model?
What RPO applies?

The governing production rule is:

Do not choose UNLOGGED simply to reduce WAL. Use it only when losing and rebuilding the relation's contents is acceptable to the application recovery model.

## 4.3.17 Temporary Relations vs. Temporary Files

A temporary table is a PostgreSQL relation.

CREATE TEMP TABLE session_work (
    id bigint,
    value text
);

A temporary query spill file is execution workspace.

Therefore:

Temporary Relation
       ≠
Temporary Query Spill File

They have different:

lifecycle;
ownership;
storage behavior;
monitoring;
troubleshooting paths.

This distinction is particularly important during temporary-storage incidents.

## 4.3.18 Fork Naming

Conceptually, relation files may use patterns such as:

<filenode>
<filenode>_fsm
<filenode>_vm
<filenode>_init

Segmented forks can resemble:

<filenode>
<filenode>.1
<filenode>.2

<filenode>_fsm
<filenode>_fsm.1

<filenode>_vm
<filenode>_vm.1

These names are PostgreSQL internal storage representations.

Do not build destructive automation around filesystem naming conventions.

## 4.3.19 Relation Segments

PostgreSQL divides sufficiently large relation forks into multiple segment files.

Conceptually:

Relation Fork
      │
      ├── Segment 0
      ├── Segment 1
      ├── Segment 2
      └── Segment N

The segment size is derived from PostgreSQL build parameters:

RELSEG_SIZE × BLCKSZ

With standard PostgreSQL build parameters, this is normally approximately:

1 GiB

Example:

24576
24576.1
24576.2
24576.3

Therefore:

One operating-system file
        ≠
Complete relation size
## 4.3.20 Segment-to-Block Relationship

At the next layer:

Relation
   ↓
Fork
   ↓
Segment
   ↓
Block / Page

Conceptually:

Relation block number
        ↓
Determine segment
        ↓
Determine block within segment

Under the standard segmentation model, the segment is derived from the relation block number and RELSEG_SIZE.

This creates the transition to Section 4.4, which examines PostgreSQL pages, blocks, and tuples.

## 4.3.21 Never Measure a Relation From One Segment

Suppose:

1.0G   24576
1.0G   24576.1
1.0G   24576.2
700M   24576.3

Looking only at:

24576 = 1 GB

would substantially underestimate the main fork.

The logical table may additionally contain:

FSM
VM
TOAST
TOAST index
application indexes

Use PostgreSQL size functions for logical capacity analysis.

## 4.3.22 Fork-Specific Size Inspection

PostgreSQL can report individual fork sizes:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders', 'main')
    ) AS main_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'fsm')
    ) AS fsm_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'vm')
    ) AS vm_size;

For an applicable unlogged relation:

SELECT
    pg_size_pretty(
        pg_relation_size('public.staging_events', 'init')
    ) AS init_size;

This is safer than manually reconstructing fork sizes from filesystem files.

## 4.3.23 Table Storage Is More Than the Heap

A useful logical model is:

Application Table
       │
       ├── Table-associated storage
       │      ├── Heap/main relation
       │      ├── Auxiliary forks
       │      └── TOAST
       │
       └── Index relations

Consequently, table size can mean several different things.

PostgreSQL provides different size functions for these perspectives.

## 4.3.24 pg_relation_size()

pg_relation_size() reports the disk space used by a specified fork of one relation.

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    );

By default, this reports the main fork.

Use it when asking:

How large is this specific physical relation/fork?

## 4.3.25 pg_table_size()

pg_table_size() provides the broader table-associated storage footprint while excluding indexes.

SELECT
    pg_size_pretty(
        pg_table_size('public.orders')
    );

It includes table-associated auxiliary storage and TOAST where applicable.

Conceptually:

pg_relation_size()
       ↓
specific relation/fork perspective

pg_table_size()
       ↓
broader table-associated storage
excluding indexes
## 4.3.26 pg_indexes_size()

Use:

SELECT
    pg_size_pretty(
        pg_indexes_size('public.orders')
    );

to measure indexes associated with the table.

This matters because production databases can have:

Index storage
      >
Heap/table storage

especially with many, wide, or specialized indexes.

## 4.3.27 pg_total_relation_size()

For the broadest table-centric measurement:

SELECT
    pg_size_pretty(
        pg_total_relation_size('public.orders')
    );

The operational model is:

pg_table_size(table)
        +
pg_indexes_size(table)
        =
pg_total_relation_size(table)

This is usually the safest starting measurement for total table footprint.

## 4.3.28 Allocated Storage vs. Live Data

A critical capacity distinction is:

pg_total_relation_size()
       ↓
Allocated PostgreSQL storage

NOT necessarily
       ↓
Useful live application data

Physical storage can include space associated with:

live tuples;
dead tuples;
reusable free space;
TOAST;
indexes;
index bloat;
page-level fragmentation.

Therefore:

Relation size alone cannot determine how much space is reclaimable.

Detailed bloat and VACUUM analysis belongs in later sections.

## 4.3.29 TOAST Architecture

PostgreSQL uses TOAST—The Oversized-Attribute Storage Technique—to handle values that cannot efficiently remain inline within ordinary tuples.

Common candidates include large:

TEXT
BYTEA
JSON / JSONB
arrays
other variable-length values

Conceptually:

Large attribute
      ↓
Column storage strategy
      ↓
TOAST processing where required
      ↓
Inline / compressed /
out-of-line representation

Do not assume:

Large value
    =
Always compressed
    =
Always externalized

The actual behavior depends on datatype capabilities, storage strategy, value size, compression behavior, and PostgreSQL configuration/version.

## 4.3.30 TOAST Storage Strategies

PostgreSQL supports storage strategies including:

PLAIN
MAIN
EXTERNAL
EXTENDED

Conceptually:

Column value
      ↓
Storage strategy
      ↓
Can it be compressed?
Can it move out-of-line?
      ↓
Heap / TOAST representation

Inspect column storage properties through PostgreSQL catalogs:

SELECT
    a.attname,
    a.attstorage
FROM pg_attribute AS a
WHERE a.attrelid = 'public.orders'::regclass
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY a.attnum;

Detailed TOAST tuning should be performed only with a clear understanding of workload and datatype behavior.

## 4.3.31 TOAST Relations

A table can have an associated TOAST relation identified through:

pg_class.reltoastrelid

Inspect it:

SELECT
    c.oid,
    c.relname,
    c.reltoastrelid
FROM pg_class AS c
WHERE c.oid = 'public.orders'::regclass;

Map the TOAST relation:

SELECT
    c.oid,
    n.nspname,
    c.relname
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = (
    SELECT reltoastrelid
    FROM pg_class
    WHERE oid = 'public.orders'::regclass
);

Conceptually:

Application table
       ↓
reltoastrelid
       ↓
TOAST relation
       ↓
TOAST index
## 4.3.32 TOAST Capacity Risk

A table may appear modest when only its main heap is examined.

For example:

Main/Heap      250 GB
TOAST          900 GB
Indexes        150 GB
---------------------
Total          1.30 TB

This is particularly relevant for workloads storing:

documents;
JSON payloads;
API messages;
large text;
binary objects.

The investigation model is:

Table growing
      ↓
Heap?
TOAST?
Indexes?
      ↓
Which component changed?
      ↓
Which application behavior caused it?
## 4.3.33 Indexes Are Independent Relations

Indexes are independent PostgreSQL relations.

Application Table
       │
       ├── Heap/table relation
       │
       ├── Primary-key index
       ├── Secondary index
       ├── GIN/GiST/BRIN/etc.
       └── TOAST index

Inspect indexes:

SELECT
    i.indexrelid::regclass AS index_name,
    am.amname AS access_method,
    pg_size_pretty(
        pg_relation_size(i.indexrelid)
    ) AS index_size
FROM pg_index AS i
JOIN pg_class AS ic
  ON ic.oid = i.indexrelid
JOIN pg_am AS am
  ON am.oid = ic.relam
WHERE i.indrelid = 'public.orders'::regclass
ORDER BY pg_relation_size(i.indexrelid) DESC;

Index access methods can have substantially different storage characteristics.

## 4.3.34 Large Index Does Not Mean Bad Index

Suppose:

Heap       300 GB
Indexes    1.1 TB
Total      1.4 TB

The correct response is not:

Indexes large
     ↓
Delete indexes

Investigate:

Which indexes are largest?
Which access methods?
Which queries use them?
Do they enforce constraints?
Are any redundant?
Is bloat suspected?
What is the write overhead?

Size alone is not sufficient justification for dropping an index.

## 4.3.35 Materialized Views

A normal view stores a query definition.

A materialized view physically stores query results.

Normal View
     ↓
Stored definition

Materialized View
     ↓
Stored relation
     +
Optional indexes

Materialized views therefore contribute directly to capacity consumption.

Their refresh strategy can also create significant transient storage and workload effects.

## 4.3.36 Partitioned Tables

Consider:

orders
   │
   ├── orders_2024
   ├── orders_2025
   ├── orders_2026
   └── orders_2027

The parent partitioned table represents the logical hierarchy.

Rows are stored in leaf partitions.

Therefore:

Parent relation size
       ≠
Total logical dataset size

A top-N query against ordinary relations may identify large physical partitions but does not automatically aggregate the complete partition hierarchy.

## 4.3.37 Partitions Can Span Tablespaces

Partitions can reside in different tablespaces.

For example:

orders
   │
   ├── orders_2024 → tablespace_archive
   ├── orders_2025 → tablespace_archive
   ├── orders_2026 → tablespace_primary
   └── orders_2027 → tablespace_primary

Thus:

One logical partitioned table
        ↓
Potentially multiple filesystems

Production capacity monitoring must account for this.

## 4.3.38 Partitioned Indexes

Partitioned indexes similarly form logical hierarchies:

Parent partitioned index
          │
          ├── Child index A
          ├── Child index B
          └── Child index C

Physical storage resides in child indexes.

The parent should not be treated as the total physical size of the complete index hierarchy.

## 4.3.39 Partition Capacity Monitoring

For large partitioned datasets, monitor:

Total hierarchy size
Largest partition
Growth per partition
Indexes per partition
Tablespace per partition
Partition creation rate
Retention/drop rate
Future-partition capacity

Useful operational questions include:

Which partition is growing?
Is retention working?
Will the next partition fit?
Is one tablespace filling faster?
## 4.3.40 Sequences, Views, and Foreign Tables

Sequences are specialized PostgreSQL relations and normally consume little capacity.

Normal views do not physically store their result rows as ordinary heap relations.

Foreign tables describe data accessed through a foreign data wrapper rather than ordinary local heap storage.

Therefore:

pg_class entry
      ≠
Guaranteed ordinary local storage

Always interpret storage behavior together with relkind.

## 4.3.41 Relation Rewrites

Some PostgreSQL operations create replacement physical storage for a relation.

Conceptually:

Existing relation
      ↓
Rewrite operation
      ↓
Old physical storage
      +
New physical storage
      ↓
Replacement

Examples include:

VACUUM FULL;
CLUSTER;
certain ALTER TABLE operations.

A rewrite can change the relation's physical filenode.

Therefore physical mappings must be rediscovered afterward.

## 4.3.42 Index Builds and Rebuilds

Index operations should be distinguished from heap-table rewrites.

Storage-intensive index operations include:

CREATE INDEX
REINDEX

Conceptually:

Storage-intensive maintenance
│
├── Table/heap rewrites
│
│   ├── VACUUM FULL
│   ├── CLUSTER
│   └── certain ALTER TABLE operations
│
├── Index builds/rebuilds
│
│   ├── CREATE INDEX
│   └── REINDEX
│
└── Copy/migration operations

These operations have different locking, storage, WAL, and recovery characteristics.

## 4.3.43 Peak Maintenance Capacity

A dangerous assumption is:

Final object will fit
       ↓
Operation is safe

Production planning must instead consider:

Existing storage
       +
New/rewrite/rebuild storage
       +
Temporary workspace
       +
WAL requirements
       +
Normal concurrent growth
       +
Safety margin
       =
Potential peak requirement

Not every operation consumes all components identically.

The exact PostgreSQL command and version must be evaluated.

## 4.3.44 Example Maintenance Capacity Risk

Suppose:

Table        800 GB
Indexes      300 GB
Free space   150 GB

Normal operations may still work.

But a rewrite or rebuild operation may require substantially more transient capacity than the available 150 GB.

Therefore:

Maintenance capacity planning must use peak expected consumption, not only the final post-maintenance relation size.

## 4.3.45 WAL Amplification

Large storage operations can also generate significant WAL.

The amount depends on factors such as:

operation type;
relation persistence;
WAL configuration;
full-page-write behavior;
checkpoints;
concurrent workload;
PostgreSQL version.

Conceptually:

Large maintenance
       │
       ├── Local storage I/O
       └── WAL generation
               ↓
       Replication / archive

Do not use a fixed universal WAL multiplier.

Measure and plan for the actual environment.

## 4.3.46 Downstream Maintenance Impact

A large relation operation can affect:

Primary storage
      │
      ├── WAL
      ├── Physical replicas
      ├── WAL archive
      ├── Logical decoding
      ├── CDC pipelines
      └── Network throughput

The primary can remain operational while:

Replica lag increases
Archive falls behind
CDC latency rises
Network saturates

Production maintenance must therefore be evaluated across the complete replication and recovery path.

Before large storage-intensive maintenance, measure:

target relation size;

index size;
tablespace capacity;
filesystem free space;
normal growth rate;
expected rewrite/build requirements;
temporary-space requirements;
WAL headroom;
WAL archive health;
replica lag;
replica replay capacity;

## 4.3.49 Relation Growth Investigation

A useful first-pass query is:

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    pg_size_pretty(pg_relation_size(c.oid)) AS main_relation,
    pg_size_pretty(pg_table_size(c.oid)) AS table_storage,
    pg_size_pretty(pg_indexes_size(c.oid)) AS indexes,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_storage
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND n.nspname !~ '^pg_toast'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;

This ranks large ordinary physical tables.

TOAST bytes remain represented in pg_table_size() and pg_total_relation_size() for their owning tables.

For partitioned tables, perform hierarchy-aware analysis separately.

## 4.3.50 Growth Attribution

A storage increase should be correlated with:

Row-count estimates
INSERT rate
UPDATE rate
DELETE rate

## 4.3.51 Growth vs. Bloat

Increasing relation size does not necessarily mean proportional business-data growth.

Potential contributors include:

Live tuples
Dead tuples
TOAST growth
Index bloat
Page fragmentation
Large updates
Retention changes
Maintenance effects

Therefore:

Storage growth
      ≠
Automatically live-data growth

Later sections address VACUUM and bloat in detail.

## 4.3.56 Safe Automation

Good automation candidates include:

✓ Inventory relations
✓ Collect relation sizes
✓ Track table/index ratios
✓ Track TOAST-heavy relations
✓ Aggregate partition hierarchy sizes
✓ Track current physical mappings
✓ Track growth rates
✓ Forecast exhaustion
✓ Detect abnormal growth
✓ Attach logical identity to filesystem alerts
✓ Preflight maintenance capacity
✓ Correlate maintenance with WAL/replication impact

Physical mappings should be rediscovered rather than treated as permanent.

## 4.3.57 Dangerous Automation

Do not automate:

✗ Delete relation segments
✗ Delete _fsm files
✗ Delete _vm files
✗ Delete _init files
✗ Replace relation files
✗ Restore arbitrary relation files
✗ Drop indexes solely because they are large
✗ Run VACUUM FULL automatically because a table grew
✗ Run REINDEX automatically because an index is large

The principle is:

Automate observation, correlation, forecasting, and diagnosis aggressively. Place destructive or rewrite-heavy remediation behind explicit operational controls.

## 4.3.58 Backup and Recovery Boundary

A PostgreSQL relation file is not a standalone backup unit.

Therefore:

Copy one relation file
       ≠
Valid PostgreSQL table backup

and:

Restore arbitrary relation file
       ≠
General PostgreSQL recovery

Physical state depends on:

Catalog metadata
Transaction state
WAL/recovery state
Forks
TOAST
Indexes
Cluster consistency

Use PostgreSQL-supported backup and recovery mechanisms.

## 4.3.59 Filesystem Snapshot Consistency

Storage snapshots require consistency planning.

Suppose:

PGDATA      → Volume A
pg_wal      → Volume B
Tablespace  → Volume C

Independent snapshots at different times:

A → T1
B → T2
C → T3

cannot automatically be assumed to constitute a valid recovery set.

Snapshot architecture must account for:

crash consistency;
cross-volume consistency;
WAL availability;
PostgreSQL recovery requirements;
backup procedure.

Detailed backup architecture belongs in the backup and recovery chapters.

## 4.3.60 Production Anti-Patterns
Anti-pattern 1 — Filename equals table OID
24576
  ↓
Must be table OID 24576

without catalog validation.

Anti-pattern 2 — One segment equals relation size
24576 = 1 GB
therefore table = 1 GB

while other segments exist.

Anti-pattern 3 — Heap equals total footprint
Heap = 200 GB
therefore table = 200 GB

while TOAST and indexes consume another 800 GB.

Anti-pattern 4 — Large index equals unnecessary index

Size does not establish usefulness.

Anti-pattern 5 — Storage growth equals live-data growth

Bloat, TOAST, indexes, and maintenance can contribute.

Anti-pattern 6 — Filenodes never change

Rewrite operations can change them.

Anti-pattern 7 — Final object fits, therefore maintenance is safe

Peak transient requirements may be substantially larger.

Anti-pattern 8 — Primary healthy means maintenance is healthy

Replicas, archives, or CDC consumers may be falling behind.

Anti-pattern 9 — Physical file copy equals backup

PostgreSQL requires consistent cluster/recovery state.
