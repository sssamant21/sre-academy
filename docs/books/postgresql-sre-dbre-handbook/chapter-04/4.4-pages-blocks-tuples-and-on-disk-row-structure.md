## 4.4.2 Pages and Blocks

PostgreSQL organizes table and index storage into fixed-size pages, also commonly called blocks.

With a standard PostgreSQL build:

BLCKSZ = 8192 bytes
       = 8 KiB

Verify rather than assume:

SHOW block_size;

or:

SELECT current_setting('block_size');

Conceptually:

Relation
   ↓
Segment
   ↓
Block 0
Block 1
Block 2
...
Block N

For the standard build:

1 block = 1 page = 8 KiB

The block size is a build-time property rather than an ordinary runtime tuning parameter.

## 4.4.3 Relation Size vs. Page Count

A useful conceptual approximation is:

Relation Size
      ≈
Number of Pages
      ×
Block Size

PostgreSQL exposes pg_class.relpages, but this is catalog/planner information and may not be perfectly current.

Example:

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname,
    c.relpages,
    current_setting('block_size')::bigint AS block_size,
    pg_size_pretty(pg_relation_size(c.oid)) AS relation_size
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = 'public.orders'::regclass;

Use:

relpages
   ↓
Planner/catalog estimate

versus:

pg_relation_size()
   ↓
Operational storage measurement

Do not treat relpages as an exact real-time block counter.

## 4.4.4 Canonical PostgreSQL Page Layout

A PostgreSQL page contains five conceptual regions:

+----------------------------------------------------+
| PageHeaderData                                     |
+----------------------------------------------------+
| ItemIdData                                         |
| ItemIdData                                         |
| ItemIdData                                         |
| ...                                                |
+----------------------------------------------------+
|                                                    |
|                   FREE SPACE                       |
|                                                    |
+----------------------------------------------------+
| Tuple / Item N                                     |
| ...                                                |
| Tuple / Item 2                                     |
| Tuple / Item 1                                     |
+----------------------------------------------------+
| Special Space                                      |
+----------------------------------------------------+

The canonical areas are:

1. Page header
2. Item identifier array
3. Free space
4. Stored items
5. Special space

For ordinary heap pages, special space is normally unused.

Index access methods can use special space for access-method-specific metadata.

## 4.4.5 Page Header

For the standard PostgreSQL page layout, PageHeaderData occupies 24 bytes.

Important fields include:

Field	Purpose
pd_lsn	LSN associated with the page's most recent change
pd_checksum	Page checksum information
pd_flags	Page state flags
pd_lower	End of item identifier area
pd_upper	Beginning of tuple/item area
pd_special	Beginning of special space
pd_pagesize_version	Page-size/layout information
pd_prune_xid	Hint related to pruning eligibility

Conceptually:

Page
 │
 ├── pd_lsn
 │      ↓
 │     WAL
 │
 ├── pd_checksum
 │      ↓
 │   Integrity
 │
 ├── pd_lower / pd_upper
 │      ↓
 │   Free space
 │
 ├── pd_special
 │      ↓
 │   Access-method metadata
 │
 └── pd_prune_xid
        ↓
      Pruning

This page header connects storage, WAL, integrity, and MVCC cleanup.

## 4.4.6 Page Free-Space Boundaries

The page layout can be visualized as:

Page Start
    │
    ▼
Page Header
    │
Item Identifiers
    │
    ▼
 pd_lower
    │
    │
    │   FREE SPACE
    │
    ▼
 pd_upper
    │
Tuple Data
    │
    ▼
pd_special
    │
Special Space
    ▼
Page End

Item identifiers grow forward from the beginning of the page.

Tuple storage grows backward from the end of the usable page.

Therefore:

Item identifiers
       ↓

<----- Free Space ----->

       ↑
Tuple storage

As tuples are added, the free-space region contracts.

## 4.4.7 Item Identifiers

Heap tuples are referenced through item identifiers, often called line pointers.

A standard ItemIdData entry occupies 4 bytes.

Conceptually:

ItemId 1 ─────────► Tuple A
ItemId 2 ─────────► Tuple B
ItemId 3 ─────────► Tuple C

This indirection is important.

PostgreSQL does not need to represent a tuple simply as:

raw byte offset

Instead:

Page number
    +
Item identifier number
    ↓
Tuple location

This becomes the foundation for ctid.

## 4.4.8 Why Item Identifiers Matter

Tuple bytes can be rearranged during page-space management while PostgreSQL retains the item-slot abstraction.

Conceptually:

CTID
 │
 ├── Block Number
 │
 └── Item Number
          │
          ▼
       ItemId
          │
          ▼
        Tuple

This indirection also becomes important for HOT chains and page pruning.

## 4.4.9 Heap Tuple Structure

An application row stored in a normal PostgreSQL table becomes a heap tuple.

Conceptually:

Heap Tuple
│
├── Heap tuple header
├── Optional NULL bitmap
├── Alignment/padding
└── Attribute data

The fixed heap tuple header is normally 23 bytes before optional bitmap/alignment/user data.

Consequently:

SUM(column values)
       ≠
Physical tuple size
## 4.4.10 Heap Tuple Header

Important tuple-header concepts include:

HeapTupleHeaderData
│
├── t_xmin
├── t_xmax
├── command/transaction-related information
├── t_ctid
├── t_infomask2
├── t_infomask
└── t_hoff

t_hoff identifies where the actual user data begins.

The physical tuple may additionally contain:

NULL bitmap
alignment padding
variable-length metadata
attribute data

This overhead must be considered in storage-density calculations.

## 4.4.11 xmin

xmin identifies the transaction associated with inserting a particular tuple version.

Conceptually:

Transaction T1
     ↓
INSERT
     ↓
Tuple V1
xmin = T1

Visibility cannot be determined from xmin alone.

PostgreSQL also considers:

transaction state;
snapshot;
tuple flags;
MVCC rules.
## 4.4.12 xmax

xmax participates in representing tuple state associated with operations such as:

UPDATE;
DELETE;
row locking;
MultiXact-related state.

Therefore avoid the oversimplification:

xmax
 =
deleting transaction

A safer model is:

xmax
  ↓
Part of PostgreSQL's
tuple-state/MVCC machinery

Raw tuple-header values should not be interpreted without the associated PostgreSQL semantics.

## 4.4.13 MVCC and Tuple Versions

PostgreSQL MVCC normally avoids simply overwriting an existing row version during an UPDATE.

Suppose:

Tuple V1
xmin = T1
status = NEW

Then:

UPDATE orders
SET status = 'SHIPPED'
WHERE order_id = 100;

can conceptually produce:

Old Tuple V1
xmin = T1
xmax = T2
status = NEW

        +

New Tuple V2
xmin = T2
status = SHIPPED

Thus:

One logical row
      ↓
Multiple physical
tuple versions over time

This is one of the foundations of PostgreSQL storage behavior.

## 4.4.14 UPDATE Storage Lifecycle

A useful production model is:

UPDATE
   ↓
Create new tuple version
   ↓
Old version remains temporarily
   ↓
MVCC visibility horizon advances
   ↓
Old version becomes removable
   ↓
Pruning / VACUUM
   ↓
Space becomes reusable

Therefore high UPDATE rates can generate:

Heap churn
+
Index churn
+
WAL
+
Dead tuples
+
VACUUM work

even when the application's logical row count remains unchanged.

## 4.4.15 DELETE Storage Lifecycle

DELETE similarly does not normally mean immediate removal of physical bytes.

DELETE
   ↓
Tuple becomes logically deleted
   ↓
Old version may remain physically present
   ↓
MVCC visibility determines when removable
   ↓
VACUUM / pruning
   ↓
Space becomes reusable

Therefore:

DELETE does not normally imply immediate filesystem-space reclamation.

## 4.4.16 Dead Tuples

A simplified lifecycle is:

Live Tuple
    ↓
UPDATE / DELETE
    ↓
Old Tuple Version
    ↓
No longer required by snapshots
    ↓
Dead / removable tuple
    ↓
Pruning / VACUUM
    ↓
Reusable relation space

The crucial distinction is:

Reusable PostgreSQL space
         ≠
Filesystem free space

Normal VACUUM primarily enables PostgreSQL to reuse relation space.

It does not normally shrink the entire relation back to its smallest possible physical size.

## 4.4.17 ctid

PostgreSQL exposes a physical tuple-version locator through the ctid system column.

Example:

SELECT
    ctid,
    order_id,
    status
FROM public.orders
LIMIT 10;

A value such as:

(125,7)

means conceptually:

Block/Page = 125
Item Slot  = 7

Therefore:

ctid
 =
(block number, item identifier)
## 4.4.18 ctid Is Not an Application Identifier

Never use ctid as a permanent business or application key.

An UPDATE can create a new tuple version with a different ctid.

Physical rewrites can also change tuple locations.

Therefore:

ctid
   =
Physical tuple-version locator

but:

ctid
   ≠
Stable logical identity

Use a real primary/business key for application identity.

## 4.4.19 HOT — Heap-Only Tuple Updates

PostgreSQL can optimize some UPDATE operations using Heap-Only Tuple (HOT) updates.

HOT generally requires:

Updated columns do not require
new ordinary index entries
          +
New tuple version can fit
on the same heap page

Modern PostgreSQL also treats summarizing indexes such as BRIN specially when determining HOT eligibility.

Conceptually:

Heap Page
│
├── Tuple V1
│      ↓
├── Tuple V2
│      ↓
└── Tuple V3

with an index entry capable of reaching the HOT chain without requiring ordinary new index entries for each qualifying update.

## 4.4.20 HOT Chain

A more accurate physical model is:

Index Entry
     │
     ▼
Original ItemId
     │
     ▼
Tuple V1
     │
     ▼
Tuple V2
     │
     ▼
Tuple V3

As older versions become unnecessary, PostgreSQL can prune the chain and maintain appropriate redirect information.

HOT can therefore reduce:

index writes;
index churn;
index-bloat pressure;
associated WAL;
UPDATE cost.

It can also allow obsolete intermediate tuple versions to be pruned without always waiting for a later full VACUUM cycle.

## 4.4.21 HOT Is Conditional

Do not assume:

UPDATE
   =
HOT UPDATE

HOT depends on:

Index requirements
       +
Same-page free space
       +
Tuple/page state

If insufficient page space exists:

UPDATE
   ↓
New tuple version elsewhere
   ↓
Ordinary index maintenance
may be required

This makes page free space an important part of update performance.

## 4.4.22 fillfactor

fillfactor can reserve page space for future tuple versions.

Example:

CREATE TABLE frequently_updated (
    id bigint PRIMARY KEY,
    state text,
    payload text
)
WITH (fillfactor = 80);

Conceptually:

Page
 ↓
~80% initial packing target
 ↓
Remaining update headroom
 ↓
Potentially more
same-page updates

This can improve HOT opportunities for suitable update-heavy workloads.

## 4.4.23 fillfactor Trade-Off

Lower fillfactor:

More page headroom
      ↓
Potentially more HOT
      ↓
More initial storage

Higher fillfactor:

Denser packing
      ↓
Better initial capacity efficiency
      ↓
Less update headroom

Therefore:

fillfactor is a workload-specific trade-off, not a universal bloat-remediation setting.

Inspect current options:

SELECT
    n.nspname AS schema_name,
    c.relname,
    c.reloptions
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = 'public.orders'::regclass;
## 4.4.24 Production Guardrail for fillfactor

Before changing it, establish:

Update frequency
Current HOT behavior
Row width
Indexed columns
Current storage footprint
Expected additional capacity
Maintenance implications
Representative test results

The decision path should be:

Update-heavy workload
       ↓
HOT opportunity poor
       ↓
Same-page space constrained
       ↓
Evaluate fillfactor
       ↓
Test
       ↓
Controlled deployment

Do not change fillfactor merely because dead tuples exist.

## 4.4.25 NULL Bitmap and Alignment

A tuple may contain a NULL bitmap when required.

Conceptually:

Tuple
│
├── Header
├── NULL bitmap
├── Alignment
└── Attributes

PostgreSQL also aligns values according to datatype/platform requirements.

Thus:

Column A
Column B
Padding
Column C

may consume more space than:

logical size(A)
+
logical size(B)
+
logical size(C)

Schema layout can therefore influence physical row size.

## 4.4.26 Variable-Length Attributes

Types such as:

text
varchar
bytea
jsonb
arrays

use variable-length representations.

Physical representation may differ from logical application size because values can be:

Inline
Compressed
Out-of-line through TOAST

depending on datatype, storage strategy, size, and PostgreSQL behavior.

## 4.4.27 TOAST and Page Architecture

A logical row can contain data larger than can reasonably fit inline within one heap page.

PostgreSQL addresses this through TOAST.

Conceptually:

Logical Row
    │
    ├── Normal attributes
    │       ↓
    │    Heap tuple
    │
    └── Large value
            ↓
        TOAST processing
            ↓
        Possibly compressed /
        stored out-of-line

Therefore a table-growth investigation must not examine only its heap.

Always consider:

Heap
+
TOAST
+
Indexes
## 4.4.28 Four Layers of Storage Consumption

A useful capacity model separates four layers.

Layer 1 — Logical payload
Application column values
Layer 2 — Tuple representation
Logical payload
      +
Tuple header
      +
NULL bitmap
      +
Alignment
      +
Variable-length representation
Layer 3 — Page representation
Tuples
   +
Page header
   +
Item identifiers
   +
Free space
Layer 4 — Complete relation footprint
Heap pages
    +
Dead/reusable space
    +
TOAST
    +
Indexes

Therefore:

Application payload
      ≠
Tuple size
      ≠
Heap size
      ≠
Total table footprint

This distinction is essential for capacity planning.

## 4.4.29 Physical Row-Size Investigation

pg_column_size() can help investigate physical representations.

For example:

SELECT
    pg_column_size(t)
FROM public.orders AS t
LIMIT 10;

Sampling can help estimate typical row representation:

SELECT
    avg(pg_column_size(t)) AS avg_sample_row_size
FROM (
    SELECT *
    FROM public.orders
    TABLESAMPLE SYSTEM (1)
) AS t;

But this does not directly calculate complete table storage because it does not itself account for the complete impact of:

page overhead;
line pointers;
dead tuples;
free space;
indexes;
total TOAST behavior.

Use it as a diagnostic input, not a complete capacity formula.

## 4.4.30 Page Density

A page can contain:

Live tuples
Dead/removable tuples
Reusable free space
Page metadata
Item identifiers

Two tables with the same allocated size can therefore have very different useful-data density.

Table A
1 TB
High useful-data density

Table B
1 TB
Large dead/free-space component

This affects both capacity and performance.

## 4.4.31 Page Density and Performance

Suppose two tables contain the same useful logical data:

Table A → 1 million pages
Table B → 2 million pages

A sequential scan may have to process substantially more pages for Table B.

Conceptually:

Poor useful-data density
       ↓
More pages
       ↓
More buffer usage
       ↓
More I/O
       ↓
Longer scans

Bloat can therefore become both:

Capacity problem
+
Performance problem
## 4.4.32 Page Compaction, Pruning, and VACUUM

These concepts must remain distinct.

Page compaction
Reorganize page storage
       ↓
Consolidate available space
Page pruning
Remove tuple versions
that are no longer required
from a page
VACUUM
Broader relation-level
maintenance and cleanup

They interact, but they are not interchangeable terms.

## 4.4.33 pd_prune_xid

The page header includes pd_prune_xid, which acts as a hint related to potential pruning work.

Conceptually:

Tuple churn
     ↓
Old tuple versions
     ↓
Pruning opportunity
     ↓
pd_prune_xid helps
identify potential work

It is not an exact dead-tuple counter.

## 4.4.34 VACUUM and Reusable Space

A simplified lifecycle is:

INSERT
   ↓
Live tuple
   ↓
UPDATE / DELETE
   ↓
Old tuple versions
   ↓
Visibility horizon advances
   ↓
Versions become removable
   ↓
Pruning / VACUUM
   ↓
Space reusable

The critical production principle remains:

Normal VACUUM primarily makes space reusable by PostgreSQL; it does not generally return all reclaimed relation space to the filesystem.

## 4.4.35 Why a Large DELETE May Not Reduce Disk Usage

Suppose:

Table before DELETE = 500 GB
Logical data deleted = 200 GB

A user might expect:

500 GB
  ↓
300 GB

Instead, the storage behavior can resemble:

500 GB relation
      ↓
DELETE
      ↓
Tuple versions become obsolete
      ↓
VACUUM
      ↓
Internal space becomes reusable
      ↓
Relation remains ~500 GB

This may be completely normal.

## 4.4.36 Two Different Space-Reclamation Requirements

During an incident, determine what is actually required.

Requirement A — PostgreSQL needs reusable space
Need future INSERT/UPDATE capacity
       ↓
Internal reusable space
may solve the problem
Requirement B — Infrastructure needs capacity returned
Need filesystem/cloud
storage actually reduced
       ↓
Physical reclamation /
rewrite strategy may be needed

These are fundamentally different operational objectives.

## 4.4.37 Long Transactions and Storage

Long-running transactions can constrain MVCC cleanup.

Long transaction
      ↓
Old snapshot remains relevant
      ↓
Old tuple versions remain needed
      ↓
Cleanup constrained
      ↓
Dead tuples accumulate
      ↓
Relation growth

This means an application transaction-management problem can become a storage incident.

Diagnostic query:

SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
## 4.4.38 Do Not Automatically Kill Long Transactions

Detection should be automated.

Termination should normally require context.

Before terminating a backend, determine:

Application owner
Transaction purpose
Read vs. write
Locks held
Rollback cost
Business impact
Recovery behavior

Avoid generic automation such as:

transaction_age > X
       ↓
pg_terminate_backend()

without workload-specific policy and safeguards.

## 4.4.39 Replication and Cleanup Horizons

Depending on the architecture, cleanup can also be influenced by:

logical decoding;
replication slots;
standby feedback;
long-running consumers;
downstream CDC.

Conceptually:

Downstream requirement
       ↓
Old database state retained
       ↓
Cleanup constrained
       ↓
Storage pressure

Capacity investigations must therefore include replication state where relevant.

## 4.4.40 Heap Statistics

pg_stat_user_tables provides useful operational statistics.

Example:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

These are operational statistics and estimates.

They are not exact physical page inventories.

## 4.4.41 Estimated Dead-Tuple Ratio

A useful triage query is:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    CASE
        WHEN n_live_tup + n_dead_tup > 0
        THEN round(
            100.0 * n_dead_tup /
            (n_live_tup + n_dead_tup),
            2
        )
    END AS estimated_dead_tuple_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

This metric must be labeled correctly:

Estimated dead-tuple ratio

not:

Exact table bloat percentage

because:

Dead tuple count estimate
        ≠
Physical wasted-byte percentage
## 4.4.42 Dead Tuples Are Normal

Do not alert simply because dead tuples exist.

The production concern is:

Dead tuple generation rate
         >
Cleanup rate
         ↓
Persistent accumulation
         ↓
Operational impact

Useful correlations include:

Dead tuple trend
+
Relation growth
+
Autovacuum activity
+
Transaction age
+
Replication state

Trend-based monitoring is preferable to arbitrary universal thresholds.

## 4.4.43 HOT Monitoring

For update-heavy relations:

SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    CASE
        WHEN n_tup_upd > 0
        THEN round(
            100.0 * n_tup_hot_upd / n_tup_upd,
            2
        )
    END AS hot_update_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_tup_upd DESC;

Do not create a universal rule such as:

HOT < 80% = critical

Instead establish workload baselines.

Example:

Historical normal = 65–75%
After deployment  = 12%

That regression is much more informative than an arbitrary global threshold.

## 4.4.44 HOT Regression Investigation

Use:

HOT ratio drops
      ↓
Check UPDATE volume
      ↓
Check newly indexed columns
      ↓
Check new indexes
      ↓
Check row-width changes
      ↓
Check fillfactor
      ↓
Check table/index growth
      ↓
Check WAL
      ↓

A HOT regression may originate from application or schema changes rather than from PostgreSQL configuration.

## 4.4.45 UPDATE Amplification Failure Chain

A production failure can develop as:

Application UPDATE surge
          ↓
Tuple versions increase
          ↓
HOT opportunities insufficient
          ↓
Heap + index writes increase
          ↓
WAL increases
          ↓
Dead tuples increase
          ↓
VACUUM workload increases
          ↓
Relation pages increase
          ↓
Buffer efficiency declines
          ↓
Storage I/O increases
          ↓
Query latency increases
          ↓
Capacity pressure

This chain connects PostgreSQL page internals directly to application-facing reliability.

## 4.4.46 Index Pages

Indexes are also page-oriented relations, but their page interpretation depends on the access method.

PostgreSQL Page Framework
          │
    ┌─────┼───────────┐
    ▼     ▼           ▼
  Heap   B-tree     GIN/GiST/BRIN

Therefore:

Heap-page interpretation
       ≠
B-tree interpretation
       ≠
GIN/GiST/BRIN interpretation

Do not apply heap-tuple assumptions directly to index pages.

## 4.4.47 Shared Buffers

PostgreSQL normally accesses relation pages through its buffer manager.

Storage
   ↓
Page
   ↓
Shared Buffer
   ↓
Backend
   ↓
Modification
   ↓
Dirty Buffer
   ↓
Eventually written
to storage

This connects page architecture with:

shared_buffers;
cache efficiency;
checkpoints;
background writer activity;
storage latency.
## 4.4.48 Dirty Pages and WAL

When a backend modifies a page:

Clean Buffer
      ↓
Modification
      ↓
Dirty Buffer

PostgreSQL generates WAL describing changes as required.

The write-ahead rule means the WAL necessary to recover a page change must reach the required durable state before the corresponding dirty data page can safely be persisted in a way that would violate that ordering.

Conceptually:

Modify page in memory
       ↓
Generate WAL
       ↓
WAL durability ordering
       ↓
Dirty page write

The data page itself does not need to be synchronously written to its relation file for every transaction commit.

## 4.4.49 pd_lsn

The page header's pd_lsn connects a page to WAL/recovery state.

Conceptually:

Page
 │
 ├── pd_lsn
 │      ↓
 │     WAL
 │
 └── pd_checksum
        ↓
     Integrity

This is one reason low-level page analysis and WAL/recovery concepts are tightly related.

## 4.4.50 Full-Page Images

When full-page writes are applicable, the first relevant modification of a page after a checkpoint can require a full-page image in WAL.

Conceptually:

Checkpoint
    ↓
Page modified
    ↓
Full-page image may be logged
    ↓
Protection against
partial-page-write hazards
during recovery

This can increase WAL volume, especially under write-intensive workloads.

Do not use a fixed universal WAL multiplier for capacity planning.

## 4.4.51 WAL Amplification and Downstream Impact

Page/tuple churn can propagate:

UPDATE / DELETE
       ↓
Heap/index changes
       ↓
WAL
       ↓
 ┌─────┼─────────────┐
 ▼     ▼             ▼
Replica Archive      CDC

Potential symptoms:

Replica lag
Archive backlog
CDC lag
pg_wal growth
Network pressure

A relation-growth incident can therefore become a replication or recovery-risk incident.

## 4.4.52 Replication Slot Storage Risk

A stalled logical consumer can cause:

Consumer stops
      ↓
Replication slot retains WAL
      ↓
pg_wal grows
      ↓
Filesystem pressure

This is distinct from relation growth.

Always classify PostgreSQL storage consumption:

Storage Growth
     │
     ├── Heap
     ├── TOAST
     ├── Indexes
     ├── pg_wal
     └── Temporary/other storage

Do not assume all database disk growth is table bloat.

## 4.4.53 Page Checksums

Where enabled, PostgreSQL data checksums can help detect certain forms of page corruption.

Conceptually:

Where supported in the target environment/version, inspect state using:

Checksums provide detection.

They do not automatically repair corrupted pages.

## 4.4.56 pageinspect

PostgreSQL's pageinspect extension can expose low-level page information for specialist diagnostics.

Where approved:

CREATE EXTENSION IF NOT EXISTS pageinspect;

Example page header inspection:

SELECT *
FROM page_header(
    get_raw_page('public.orders', 0)
);

Example heap-page inspection:

SELECT *
FROM heap_page_items(
    get_raw_page('public.orders', 0)
);

Potential uses include:

page-layout analysis;
HOT-chain investigation;
corruption investigation;
internals research;
controlled lab validation.
## 4.4.57 pageinspect Guardrail

pageinspect is a privileged low-level diagnostic facility.

Its output can expose internal tuple information independently of normal application-level visibility assumptions.

Use it for:

Specialist DBA/DBRE diagnostics
Controlled investigations
Lab analysis

Do not use it for:

Routine full-table monitoring
Application access
Automated page repair
Automated corruption remediation

Inspection does not equal repair.

## 4.4.60 Production Growth Triage

For unexpected table growth, begin with:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';

Then measure:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    ) AS main_relation,
    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_storage,
    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS indexes,
    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_storage;

Interpret:

Live tuples ↑
     ↓
Business-data growth?

Dead tuples ↑
     ↓
Cleanup/MVCC problem?

Indexes ↑ disproportionately
     ↓
Index churn/bloat?

Table storage ↑ disproportionately
     ↓
Heap or TOAST?

Classification comes before remediation.

      ↓

      ↓

      ↓

## 4.4.65 Large DELETE Preflight

A DELETE used to solve a storage problem must not create a larger WAL/storage problem.

## 4.4.80 Canonical Production Principles
PostgreSQL storage is page-oriented.
The standard PostgreSQL page is normally 8 KiB; verify the actual server configuration.
A page contains metadata and line pointers in addition to tuples.
Application payload size is not physical tuple size.
MVCC can create multiple physical versions of one logical row.
UPDATE generally creates a new tuple version rather than simply overwriting the old one.
DELETE does not normally return filesystem space immediately.
Normal VACUUM primarily enables internal space reuse.
ctid is a physical tuple-version locator, not a permanent identifier.
HOT can reduce index-maintenance and WAL pressure, but it is conditional.
fillfactor trades packing density for update headroom.
Dead tuples are normal; persistent accumulation and operational impact are the concern.
Dead-tuple ratios are not exact bloat percentages.
Long transactions and replication horizons can become capacity problems.
Heap, TOAST, indexes, and WAL must be distinguished during storage incidents.
Page density affects both capacity and query performance.
Large DELETE operations can increase WAL and worsen storage pressure.
Capacity should be forecast by growth rate and runway, not percentage alone.
Checksum and invalid-page errors are data-integrity incidents.
pageinspect is a diagnostic tool, not a repair mechanism.
Managed PostgreSQL preserves the logical concepts but may hide physical storage.
Automate diagnosis and forecasting more aggressively than destructive remediation.
