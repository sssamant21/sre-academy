# 4.5 — Heap Storage Architecture

**Workflow Stage:** Revised Final / Canonical Edition
**Chapter:** Chapter 4 — PostgreSQL Storage Architecture and Capacity Management
**Audience:** PostgreSQL DBA / DBRE / SRE / Platform Engineer
**Status:** COMPLETE

This canonical edition incorporates the Draft, Technical Review corrections, and Production Review hardening. It establishes how ordinary PostgreSQL heap tables store and locate tuple versions, how the FSM and VM support storage management, how HOT and VACUUM interact with heap pages, and how these internals translate into production capacity, performance, WAL, replication, and incident-management decisions.

## 4.5.1 Purpose and Scope

Section 4.4 established the physical structure inside a PostgreSQL page:

Page / Block
     ↓
Item Identifier
     ↓
Heap Tuple
     ↓
Tuple Header + Attributes

Section 4.5 moves one level higher:

Logical Table
     ↓
Heap Relation
     ↓
Main / FSM / VM
     ↓
Heap Pages
     ↓
Tuple Versions
     ↓
MVCC / HOT / VACUUM

The governing production principle is:

Heap capacity cannot be understood from logical row counts alone. Physical behavior depends on tuple versions, page utilization, free-space reuse, VACUUM effectiveness, HOT behavior, TOAST, indexes, WAL, and transaction/replication horizons.

## 4.5.2 What Is a PostgreSQL Heap?

Ordinary PostgreSQL tables use heap storage.

"Heap" does not refer to a memory heap. It means PostgreSQL does not maintain the table's physical row layout in a permanent application-defined logical order.

Therefore:

Heap
  ≠
Primary-key ordering

Heap
  ≠
Timestamp ordering

Heap
  ≠
Guaranteed insertion ordering

Heap
  ≠
Random storage

A more accurate description is:

A PostgreSQL heap is an unordered collection of pages containing physical tuple versions.

Physical placement is influenced by:

Free-space availability
INSERT behavior
UPDATE behavior
HOT
VACUUM/pruning
fillfactor
Bulk loading
Table rewrites
CLUSTER history
## 4.5.3 Heap Storage Hierarchy

For an ordinary heap table:

Database
   ↓
Table
   ↓
Heap Relation
   ↓
Fork
   ↓
Segment
   ↓
Page / Block
   ↓
Item Identifier
   ↓
Heap Tuple Version

The principal heap-storage forks discussed here are:

Heap Relation
     │
     ├── MAIN
     │     ↓
     │   Heap pages
     │
     ├── FSM
     │     ↓
     │   Free-space information
     │
     └── VM
           ↓
         Visibility/freeze information

Other fork behavior, including the initialization fork associated with unlogged relations, belongs to the broader relation architecture established in Section 4.3.

## 4.5.4 Heap and Indexes

For an ordinary heap table, row versions reside in the heap.

Indexes provide auxiliary access paths:

Index
  ↓
TID
  ↓
Heap Page
  ↓
Heap Tuple Version

Therefore:

Heap
   =
Base row-version storage

Index
   =
Access structure

This distinction becomes critical when diagnosing storage:

Heap growth
    ≠
Index growth

and the two may require different remediation.

## 4.5.5 Physical Tuple Location — TID and ctid

A physical heap tuple version is identified by a tuple identifier:

TID
 │
 ├── Block Number
 └── Offset / Item Number

PostgreSQL exposes the current tuple version's physical locator through ctid.

Example:

SELECT
    ctid,
    order_id,
    status
FROM public.orders
LIMIT 10;

A result such as:

(245,17)

means conceptually:

Block 245
    ↓
Item Identifier 17
    ↓
Heap Tuple Version

The critical rule is:

A TID identifies a physical tuple version, not the permanent logical identity of an application row.

An UPDATE or table rewrite can change ctid.

Never use it as a durable application identifier.

## 4.5.6 Logical Rows vs. Physical Tuple Versions

Suppose the application sees:

order_id = 100
status   = SHIPPED

Over time PostgreSQL may have stored:

Tuple V1
status = NEW

      ↓ UPDATE

Tuple V2
status = PROCESSING

      ↓ UPDATE

Tuple V3
status = SHIPPED

MVCC determines which version is visible to a particular transaction.

Therefore:

One logical row
       ↓
Potentially multiple
physical heap tuples
over its lifetime

This is one of the central reasons stable logical row counts do not imply stable physical storage.

## 4.5.7 INSERT into a Heap

A simplified INSERT path is:

INSERT
   ↓
Determine tuple-space requirement
   ↓
Find candidate page using
free-space information
   ↓
Verify actual page space
   │
   ├── sufficient
   │      ↓
   │   Insert tuple
   │
   └── insufficient/no candidate
          ↓
      Find another page
      or extend relation

PostgreSQL therefore does not necessarily append every INSERT to the absolute physical end of the heap.

Existing reusable page space can be used.

## 4.5.8 Free Space Map — FSM

Searching every page in a multi-terabyte heap for insertion space would be prohibitively expensive.

PostgreSQL therefore maintains the Free Space Map.

Heap Pages
     ↓
Available page space
     ↓
FSM
     ↓
Candidate-page search

The FSM is stored in the relation's fsm fork.

Conceptually:

orders
│
├── main
│     ↓
│   Heap pages
│
├── fsm
│     ↓
│   Free-space information
│
└── vm
      ↓
    Visibility information
## 4.5.9 FSM Is Compact and Approximate

The FSM should not be interpreted as an exact byte-for-byte capacity inventory.

It maintains a compact, quantized representation useful for page selection.

Actual page space
      ↓
Compact FSM representation
      ↓
Candidate page
      ↓
Actual page checked

Therefore:

FSM
  ≠
Exact page accounting

FSM
  ≠
Bloat percentage

FSM
  ≠
Capacity forecast

The heap page itself remains authoritative when PostgreSQL attempts an insertion.

## 4.5.10 FSM Organization

Internally, FSM information is organized hierarchically so PostgreSQL can efficiently locate pages satisfying free-space requirements.

Conceptually:

                 FSM
                  │
            Summary levels
                  │
          ┌───────┴───────┐
          ▼               ▼
       Region A         Region B
          │               │
      Heap Pages       Heap Pages

This avoids scanning millions of heap pages merely to locate reusable space.

## 4.5.11 Free Space Is Not Automatically Bloat

A page can contain free space because of:

Intentional fillfactor
Tuple cleanup
Historical allocation
Expected update headroom
Fragmentation

Therefore:

Free space
    ≠
Automatically wasted space

A frequently updated relation may benefit from available page space because it improves the probability of same-page tuple updates.

## 4.5.12 UPDATE in Heap Storage

PostgreSQL generally implements an UPDATE by creating a new tuple version.

Tuple V1
   ↓
UPDATE
   ↓
Tuple V2

The old tuple remains until MVCC rules permit its removal.

The update can follow one of two broad paths:

UPDATE
  │
  ├── HOT
  │     ↓
  │   Same heap page
  │
  └── Non-HOT
        ↓
      Ordinary index maintenance
      as required

This creates the foundation for heap churn.

## 4.5.13 Heap Churn

A high-change workload can produce:

INSERT
UPDATE
UPDATE
DELETE
      ↓
Tuple creation
      +
Obsolete tuple versions
      +
Pruning
      +
VACUUM
      +
Free-space reuse

This is operationally useful to think of as heap churn.

A table can therefore show:

Logical rows
500M → 500M

while simultaneously experiencing:

Heap writes ↑
Index writes ↑
WAL ↑
Dead tuples ↑
VACUUM work ↑

Thus:

Stable row count does not mean stable storage workload.

## 4.5.14 HOT — Heap-Only Tuple Updates

HOT is an important PostgreSQL optimization for qualifying UPDATEs.

A robust conceptual definition is:

HOT can be used when the update does not require new index entries for the affected indexes and the new tuple version can be stored on the same heap page.

Conceptually:

Index Entry
     ↓
Heap Page
     ↓
Tuple V1
     ↓
Tuple V2
     ↓
Tuple V3

This can reduce:

Index writes
Index churn
Index-bloat pressure
Associated WAL
Update cost

HOT does not eliminate the heap update itself or all WAL.

## 4.5.15 HOT Is Page-Local

A fundamental HOT requirement is:

Old Tuple
     +
New Tuple
     ↓
Same Heap Page

If insufficient room exists:

Heap Page A
     ↓
Tuple V1

UPDATE

Heap Page B
     ↓
Tuple V2

HOT cannot simply continue across pages.

This directly connects HOT opportunity with page free space and fillfactor.

## 4.5.16 HOT Chains and Pruning

HOT updates can create tuple chains:

Index
  ↓
Root ItemId
  ↓
Tuple V1
  ↓
Tuple V2
  ↓
Tuple V3

When obsolete versions become removable, PostgreSQL can prune the chain.

A redirect line pointer can preserve reachability:

Index
  ↓
Root ItemId
  ↓
Redirect
  ↓
Surviving HOT Tuple

This connects:

Item identifiers
      +
HOT
      +
Page pruning

into one storage mechanism.

## 4.5.17 fillfactor and Heap Storage

fillfactor controls the target packing density used when initially filling heap pages.

For example:

CREATE TABLE frequently_updated (
    id bigint PRIMARY KEY,
    state text,
    payload text
)
WITH (fillfactor = 80);

Conceptually:

Heap Page
    ↓
~80% initial packing target
    ↓
Remaining update headroom
    ↓
Potentially greater
same-page UPDATE opportunity

Lower values trade storage density for update headroom.

## 4.5.18 fillfactor Is Not a Bloat-Repair Command

Do not use:

Heap large
    ↓
Lower fillfactor

as a generic response.

Lower fillfactor can:

Improve page-local update headroom

but can also:

Increase initial relation footprint
Increase number of pages
Increase potential scan work

Before changing it, evaluate:

UPDATE frequency
HOT behavior
Row width
Indexes
Current page pressure
Storage cost
Expected future churn
Representative testing
## 4.5.19 Visibility Map — VM

The heap relation's visibility map tracks two page-level properties:

Heap Page
   │
   ├── ALL-VISIBLE
   │
   └── ALL-FROZEN

The VM is stored in the vm fork.

It supports:

Index-only scan optimization
      +
VACUUM efficiency
      +
Freezing-related maintenance
## 4.5.20 All-Visible

An all-visible page satisfies PostgreSQL's page-level visibility conditions such that its tuples can be treated as visible to all current and future transactions under the relevant rules.

Operationally:

Index tuple
     ↓
Heap page identified
     ↓
VM says all-visible
     ↓
Heap visibility visit
can generally be avoided

This is central to index-only scans.

## 4.5.21 All-Frozen

All-frozen represents a stronger state related to transaction-ID/MultiXact freezing requirements.

Conceptually:

Heap Page
    ↓
No tuples require
future freezing work
under applicable rules

The relationship is:

ALL-FROZEN
     ↓
implies
     ↓
ALL-VISIBLE

but:

ALL-VISIBLE
     ↓
does not necessarily imply
     ↓
ALL-FROZEN
## 4.5.22 VM Is Conservative Metadata

A page not marked all-visible does not mean every tuple on that page is invisible or unhealthy.

It means PostgreSQL cannot use the VM's all-visible optimization for that page at that time.

Therefore:

Low VM coverage
    ≠
Automatically corruption
or bloat

Write-heavy workloads naturally affect VM state.

## 4.5.23 Heap Modifications and VM State

Conceptually:

Page all-visible
      ↓
Heap modification
      ↓
All-visible assumption
no longer valid
      ↓
VM state cleared as required
      ↓
VACUUM later verifies page
      ↓
All-visible state may return

Therefore:

Write churn ↑
      ↓
All-visible coverage may ↓
      ↓
Heap visibility checks may ↑

This creates a direct relationship between write behavior and some read paths.

## 4.5.24 Index Scan vs. Index-Only Scan

Normal index access commonly follows:

Index
  ↓
TID
  ↓
Heap
  ↓
Tuple

For an index-only scan:

Index contains required data
          +
Heap page is all-visible
          ↓
Heap visibility visit
may be avoided

Both conditions matter.

VM coverage alone cannot make an arbitrary query an index-only scan.

## 4.5.25 Index-Only Scan Regression

A production pattern can be:

UPDATE workload ↑
       ↓
VM all-visible coverage ↓
       ↓
Index-only scan
Heap Fetches ↑
       ↓
Buffer/storage work ↑
       ↓
Query latency ↑

Treat this as a hypothesis and validate with query plans.

For a safe candidate query:

EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;

Because EXPLAIN ANALYZE executes the query, use plain EXPLAIN first when execution itself could be expensive or unsafe.

## 4.5.26 Page Pruning

Page pruning performs page-local cleanup of obsolete tuple versions when PostgreSQL can safely do so.

Conceptually:

Heap Page
   ↓
Obsolete versions
   ↓
Pruning
   ↓
HOT-chain cleanup /
space consolidation

Pruning can occur outside a full VACUUM scan.

Therefore:

Tuple version disappeared
      ≠
VACUUM necessarily
removed it
## 4.5.27 VACUUM and Heap Storage

VACUUM is a normal component of PostgreSQL heap operation.

Its responsibilities include, depending on circumstances:

Process obsolete tuple state
        ↓
Enable space reuse
        ↓
Maintain free-space information
        ↓
Maintain visibility information
        ↓
Perform transaction-ID /
MultiXact freezing work
        ↓
Clean dead index references
as applicable

The essential model is:

MVCC
  ↓
Old tuple versions
  ↓
Pruning / VACUUM
  ↓
Reusable storage

Autovacuum is therefore core PostgreSQL infrastructure, not optional housekeeping.

## 4.5.28 VACUUM Is Not General Heap Compaction

Normal VACUUM does not generally move all surviving tuples together into the smallest possible set of pages.

A heap may remain:

Used
Free
Used
Free
Used

after VACUUM.

Therefore:

VACUUM
   ↓
Internal reuse

does not generally mean:

VACUUM
   ↓
Smallest possible relation file

This distinction is fundamental to PostgreSQL capacity management.

## 4.5.29 Historical Heap Extent

Suppose a heap grows to:

2 TB

and later large amounts of data are deleted.

After cleanup:

2 TB allocated relation
      ↓
Large amount of
internally reusable space

may still be normal.

A useful concept is the previously allocated or historical heap extent.

Do not treat this as a formal PostgreSQL high-water-mark structure.

## 4.5.30 Relation Tail Truncation

There is an important qualification.

Under suitable conditions, VACUUM can remove empty pages from the physical end of a relation.

Used
Used
Empty
Empty
Empty
   ↓
Potential tail truncation

But:

Used
Free
Used
Free
Used

cannot simply be returned to the filesystem without reorganizing surviving tuples.

Tail truncation is conditional and can be affected by locking and concurrent workload.

Therefore:

VACUUM completed
      ≠
Physical shrink guaranteed
## 4.5.31 Heap Bloat

A useful operational definition is:

Heap bloat is allocated heap storage that is inefficiently utilized relative to useful live data and workload requirements.

Possible contributors include:

Obsolete/dead tuple storage
Reusable free space
Historical allocation
Fragmentation
Update churn
Cleanup lag

But:

Intentional fillfactor headroom
       ≠
Automatically pathological bloat

and:

Free space
       ≠
Automatically wasted capacity
## 4.5.32 No Single Authoritative Bloat Percentage

PostgreSQL does not expose one universally authoritative built-in:

heap_bloat_pct

Different approaches estimate or inspect bloat using:

Catalog statistics
Tuple-width assumptions
Page inspection
Sampling
Extensions
Rewrite comparisons

Always label the result appropriately:

Estimated bloat

versus:

Measured physical characteristic

Do not treat n_dead_tup percentage as exact byte-level bloat.

## 4.5.33 Heap Capacity Model

At a particular observation point:

Heap Allocation
      │
      ├── Live tuple storage
      ├── Obsolete/dead tuple storage
      ├── Reusable free space
      ├── Intentional reserved space
      └── Page/item metadata

Then complete table storage adds:

Heap
  +
TOAST
  +
Indexes

And infrastructure capacity may additionally include:

WAL
Temporary files
Other relations/databases
Backups/platform overhead

Therefore:

Logical payload
      ≠
Heap size
      ≠
Table size
      ≠
Database storage
## 4.5.34 Small Page-Level Effects Become Large

Suppose a very large heap has:

100 million pages

If each page carried an average:

1 KiB

of genuinely unnecessary or unusable capacity, the aggregate effect would be approximately:

~95 GiB

At multi-terabyte scale, small page-level inefficiencies become material.

But remember:

Free space intentionally reserved for future updates should not automatically be classified as waste.

## 4.5.35 Heap Size Functions

For the main heap fork:

SELECT pg_size_pretty(
    pg_relation_size('public.orders', 'main')
);

For individual auxiliary forks:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders', 'main')
    ) AS main_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'fsm')
    ) AS fsm_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'vm')
    ) AS vm_size;

FSM/VM sizes are useful for internals analysis but are not normally first-line capacity KPIs.

## 4.5.36 Complete Table Footprint

Use:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    ) AS main_fork,

    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_storage,

    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS index_storage,

    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_storage;

Conceptually:

pg_relation_size()
      ↓
Selected relation fork
(default main)

pg_table_size()
      ↓
Table + associated TOAST
excluding indexes

pg_indexes_size()
      ↓
Indexes

pg_total_relation_size()
      ↓
Table + TOAST + indexes

This distinction is mandatory during storage investigations.

## 4.5.37 Heap Block Count

For the main fork:

SELECT
    pg_relation_size('public.orders', 'main')
      / current_setting('block_size')::bigint
      AS main_fork_blocks;

This derives the block count represented by the main-fork size.

Do not confuse it with:

pg_class.relpages

which is catalog/planner information and may be an estimate rather than a current physical measurement.

## 4.5.38 Sequential Scans and Heap Size

At the logical level, a sequential scan processes heap blocks through PostgreSQL's buffer/I/O machinery.

Heap
 ↓
Page 0
 ↓
Page 1
 ↓
...
 ↓
Page N

Poor heap density can therefore mean:

More pages
   ↓
More blocks potentially processed
   ↓
More buffer/I/O work
   ↓
Potentially higher latency

Actual performance also depends on:

Cache residency
Storage throughput
Parallelism
CPU
Predicate cost
Tuple width
Concurrency

Do not assume a strictly linear relationship between relation size and query latency.

## 4.5.39 Long Transactions and Cleanup Horizons

Long-running transactions or old snapshots can constrain tuple cleanup.

UPDATE / DELETE
       ↓
Obsolete tuple versions
       ↓
Old snapshot remains relevant
       ↓
Versions cannot yet be removed
       ↓
Cleanup constrained
       ↓
Heap growth

Production query:

SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    backend_xmin,
    xact_start,
    query_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
## 4.5.40 Idle-in-Transaction Risk

A particularly important pattern is:

BEGIN
  ↓
Application query
  ↓
Connection left
idle in transaction
  ↓
Transaction remains open
  ↓
Cleanup horizon may be affected

Investigate:

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    state_change,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

Persistent idle transactions should be corrected at the application, pool, or timeout-policy level rather than handled only through repeated manual termination.

## 4.5.41 Safe Backend Termination

Do not automate:

Old transaction
      ↓
Kill

Before terminating:

Identify application
      ↓
Determine transaction purpose
      ↓
Read or write?
      ↓
Locks held?
      ↓
Rollback cost?
      ↓
Business impact?
      ↓

      ↓

## 4.5.42 Heap Cleanup vs. WAL Retention

Two different storage mechanisms must remain separate.

Heap cleanup horizon
Old transaction/snapshot
       ↓
Tuple versions remain relevant
       ↓
Heap cleanup constrained
WAL retention
Replication/CDC consumer behind
       ↓
Slot requires older WAL
       ↓
WAL retained
       ↓
pg_wal pressure

They can occur together, but:

Heap growth
     ≠
WAL retention

Diagnosis must identify both independently.

## 4.5.43 Replication Slot Risk

Where logical replication or CDC exists:

SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn

A stalled consumer can produce:

Consumer behind
      ↓
Slot retains WAL
      ↓
pg_wal grows
      ↓
Filesystem capacity falls

Before doing so, determine:

Consumer owner

Potential data loss
Business impact
## 4.5.44 Heap and WAL

For ordinary logged heap tables:

INSERT / UPDATE / DELETE
          ↓
Heap changes
          +
Index changes
          ↓
WAL

Consequences can propagate to:

WAL archives
Physical replicas
Logical replication
CDC
Network
Recovery workload

HOT may reduce index-related write/WAL work, but it does not eliminate WAL for the heap modification.

Unlogged and temporary relations have different WAL/durability semantics and should not be treated identically to ordinary logged tables.

## 4.5.45 Large DELETE Risk

A large DELETE can create:

DELETE
   ↓
Tuple churn
   ↓
WAL surge
   ↓
Replica lag
   ↓
CDC lag
   ↓
Slot WAL retention
   ↓
Additional storage pressure

Therefore a purge intended to solve capacity can temporarily make capacity worse.

## 4.5.46 Large DELETE Preflight

Before a large purge:

Estimate rows and data affected.
Estimate transaction duration.
Determine whether batching is appropriate.
Check database/storage headroom.
Check WAL headroom.
Check replicas.
Check replication slots.
Check CDC/logical consumers.
Check archive capacity.
Estimate VACUUM impact.
Determine whether internal reuse solves the actual problem.
Determine whether physical shrink is really required.
Define stop conditions.
Define rollback/recovery procedures.

The production principle is:

Logical deletion, internal PostgreSQL space reuse, and physical storage reclamation are three different outcomes.

## 4.5.47 Heap Growth Classification

Classify physical growth before remediation:

Observation	Investigation Direction
Rows ↑, heap ↑ proportionally	Logical/business growth
Rows stable, heap ↑ rapidly	Churn, cleanup, bloat
Heap stable, indexes ↑	Index growth/churn
pg_table_size ↑ faster than heap	TOAST investigation
Dead tuples persistently ↑	Cleanup falling behind
HOT sharply ↓	Schema/workload/page-space change
Heap stable, pg_wal ↑	WAL retention
Disk ↑ after DELETE	WAL + reusable-space analysis

This prevents unrelated storage mechanisms from being treated as one problem.

## 4.5.51 Dead Tuple Monitoring

Use:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

Dead tuples are expected under MVCC.

The production problem is:

Dead tuple generation rate
         >
Cleanup rate
         ↓
Persistent accumulation

Trend them with heap growth and maintenance behavior.

## 4.5.52 Autovacuum Effectiveness

Do not conclude:

Autovacuum process exists
      =
Cleanup healthy

Instead:

Dead tuples accumulating
        ↓
Is autovacuum starting?
        ↓
Is it completing?
        ↓
How long does it take?
        ↓
Is churn faster than cleanup?
        ↓
Is cleanup horizon constrained?
        ↓
Is I/O limiting it?
        ↓
Are table-specific settings appropriate?

Autovacuum effectiveness must be evaluated relative to workload.

## 4.5.53 Large Tables and Autovacuum Thresholds

Percentage-based scale factors can translate into large absolute tuple counts on very large relations.

Therefore evaluate:

Scale factor
     +
Absolute threshold
     +
Table size
     +
Churn rate

rather than copying a global configuration blindly.

Large/high-churn tables may justify table-specific tuning after measurement and testing.

## 4.5.54 HOT Monitoring

For update-heavy relations:

SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    CASE
        WHEN n_tup_upd > 0
        THEN round(
            100.0 * n_tup_hot_upd / n_tup_upd,
            2
        )
    END AS hot_update_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_tup_upd DESC;

Do not use a universal HOT threshold.

Instead compare:

Historical baseline
       ↓
Current behavior
       ↓
Deployment/schema timeline

Example:

Historical HOT = 70%
Current HOT    = 12%

after a new index is a meaningful signal.

   ↓

## 4.5.58 CLUSTER

CLUSTER rewrites a table according to a selected index's ordering.

Use it only when the expected access/locality benefit justifies the operational cost.

## 4.5.61 Partitioning and Heap Lifecycle

A partitioned table can transform:

One enormous relation

into:

Partitioned Table
      │
      ├── Heap Partition A
      ├── Heap Partition B
      ├── Heap Partition C
      └── Heap Partition D

For retention-oriented workloads, appropriate partitioning can sometimes replace:

DELETE hundreds of millions of rows

with lifecycle operations such as:

Detach/drop expired partition

when application semantics permit.

However:

Partitioning does not eliminate MVCC, VACUUM, HOT behavior, or bloat within each ordinary heap partition.

## 4.5.83 Canonical Production Principles
Ordinary PostgreSQL tables use heap storage.
Heap storage is unordered, not inherently random.
Physical tuple identity is not logical row identity.
The FSM helps PostgreSQL locate candidate pages with reusable space.
FSM information is compact and should not be treated as exact bloat accounting.
The VM maintains all-visible and all-frozen page-level information.
All-frozen implies all-visible, but all-visible does not necessarily imply all-frozen.
VM state contributes to index-only-scan efficiency.
UPDATE normally creates a new heap tuple version.
HOT can reduce index-maintenance overhead when its conditions are satisfied.
HOT is page-local.
Page free space can be useful operational capacity, not waste.
fillfactor trades packing density for update headroom.
Page pruning and VACUUM are related but distinct mechanisms.
VACUUM is part of normal heap operation.
Normal VACUUM primarily enables internal reuse rather than general compaction.
VACUUM may conditionally truncate empty relation-tail pages.
Dead tuple percentage is not exact heap-bloat percentage.
PostgreSQL has no single authoritative built-in heap-bloat percentage.
Heap, TOAST, indexes, and WAL must be measured separately.
Long transactions and old snapshots can become storage problems.
Replication-slot WAL retention is distinct from heap cleanup constraints.
Large DELETE operations can temporarily increase storage pressure.
Logical deletion, reusable PostgreSQL space, and physical reclamation are different outcomes.
VACUUM FULL and CLUSTER are controlled rewrite operations.
A rewrite requires capacity to execute the rewrite safely.
Partitioning can improve lifecycle operations but does not eliminate per-partition heap maintenance.
Capacity management requires time-series growth and runway forecasting.
Alert severity should consider remediation lead time.
Managed PostgreSQL preserves heap semantics while potentially hiding physical storage details.
Automate observation and diagnosis more aggressively than destructive remediation.
Incident closure requires validated recovery, not merely lower disk utilization.
