# 4.6 — Free Space Map and Visibility Map

**Workflow Stage:** Revised Final / Canonical Edition

**Audience:** PostgreSQL DBA / DBRE / SRE / Platform Engineer

## 4.6.1 Overview

A PostgreSQL heap relation needs efficient answers to two different questions:

WRITE PATH
"Where might enough reusable
space exist for a tuple?"

READ / MAINTENANCE PATH
"Which heap pages have known
visibility or freezing properties?"

Scanning every heap page whenever either question arises would be prohibitively expensive for large relations.

PostgreSQL therefore maintains two important auxiliary relation forks:

                       HEAP RELATION
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
            MAIN            FSM            VM
             │               │              │
         Heap pages      Free-space      Visibility /
                          metadata       freeze metadata

They solve fundamentally different problems:

Structure	Primary Purpose
FSM — Free Space Map	Helps locate heap pages with sufficient reusable space
VM — Visibility Map	Records page-level all-visible and all-frozen state

A useful canonical mental model is:

FSM → "Where might this tuple fit?"

VM  → "What visibility/freezing
       properties are known for this page?"

Neither structure should be interpreted as a general table-health score.

## 4.6.2 Relation Fork Architecture

For an ordinary heap relation, PostgreSQL may maintain:

orders
│
├── main
├── fsm
└── vm

These are separate forks of the same relation.

The main fork contains the actual heap pages.

The FSM and VM contain PostgreSQL-managed auxiliary metadata.

Their sizes can be inspected:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders', 'main')
    ) AS main_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'fsm')
    ) AS fsm_size,
    pg_size_pretty(
        pg_relation_size('public.orders', 'vm')
    ) AS vm_size;

FSM/VM fork size itself is rarely a useful production health metric.

## 4.6.3 Free Space Map Purpose

Heap pages frequently contain reusable space.

Conceptually:

Heap

Page 0 → almost full
Page 1 → substantial free space
Page 2 → moderate free space
Page 3 → full
Page 4 → substantial free space

When PostgreSQL needs a page capable of accepting a tuple, scanning the entire relation would be inefficient.

The FSM provides compact metadata that helps PostgreSQL locate candidate pages.

Tuple placement needed
        ↓
Free-space lookup where required
        ↓
FSM identifies candidate area/page
        ↓
Actual heap page checked
        ↓
Tuple placement

The actual heap page remains authoritative.

## 4.6.4 FSM Information Is Quantized

The FSM is not an exact byte-by-byte inventory of every page.

Conceptually:

Actual page free space
        ↓
Compact free-space category
        ↓
FSM representation

Therefore:

FSM value
   ≠
Exact authoritative
free-byte count

Instead, the information is sufficiently precise to help PostgreSQL answer:

Which pages might satisfy this space requirement?

This compact representation keeps FSM overhead small.

## 4.6.5 FSM Search Architecture

The FSM is organized as a hierarchical maximum-value search structure.

Conceptually:

                       ROOT
                    max below
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
          Region A            Region B
          max below           max below
             │                   │
       ┌─────┴─────┐       ┌─────┴─────┐
       ▼           ▼       ▼           ▼
     Pages       Pages   Pages       Pages

Higher levels summarize the maximum free-space category represented below them.

This allows PostgreSQL to avoid:

Check page 0
Check page 1
Check page 2
...
Check page 100,000,000

when searching for reusable space.

## 4.6.6 FSM Pages Are Not Heap Pages

Do not assume:

FSM block N
     =
metadata for heap block N

FSM pages belong to the auxiliary FSM fork and represent the internal search structure.

Therefore:

Heap block 500
      ≠
FSM block 500

The mapping between heap pages and FSM information is managed internally by PostgreSQL.

## 4.6.7 FSM and INSERT

A simplified production-safe model is:

INSERT
   ↓
PostgreSQL requires
tuple-placement space
   ↓
Existing insertion target /
free-space mechanisms /
relation extension
may participate
   ↓
Tuple stored

The FSM is important when PostgreSQL needs to locate reusable heap space, but it should not be taught as an invariant first operation for every INSERT.

The canonical rule is:

The FSM enables efficient discovery of potentially reusable heap pages when free-space lookup is required.

## 4.6.8 FSM and Relation Extension

If PostgreSQL cannot use a suitable existing page, the relation may need to extend.

Conceptually:

Suitable reusable page
        │
   ┌────┴────┐
   ▼         ▼
 YES         NO
   │          │
   ▼          ▼
Reuse      Relation may
page       extend

Do not interpret this as a rigid implementation algorithm. Concurrency and internal insertion strategies affect actual behavior.

## 4.6.9 FSM and UPDATE

UPDATE creates a new tuple version under PostgreSQL MVCC.

Space therefore matters.

However, HOT updates require special treatment.

Existing tuple
      ↓
UPDATE
      ↓
HOT conditions satisfied?
      +
Enough room on SAME page?
      ↓
HOT update possible

The key rule is:

HOT requires sufficient space on the existing tuple's heap page. Searching the FSM for another page cannot make an otherwise impossible HOT update possible.

For general tuple placement outside that same-page requirement, normal free-space mechanisms can become relevant.

## 4.6.10 FSM and HOT Behavior

This creates an important production relationship:

Page headroom
     ↓
Same-page UPDATE opportunity
     ↓
HOT opportunity
     ↓
Less index maintenance
     ↓
Potentially less WAL /
storage amplification

This is one reason fillfactor can be important for update-heavy workloads.

## 4.6.11 FSM and fillfactor

Example:

CREATE TABLE update_heavy (
    id bigint PRIMARY KEY,
    status text,
    payload text
)
WITH (fillfactor = 80);

The lower fillfactor intentionally leaves page headroom.

8 KiB Heap Page

┌────────────────────────────┐
│                            │
│        Tuple Data          │
│                            │
├────────────────────────────┤
│ Intentional Free Space     │
└────────────────────────────┘

That free space may improve the chance that future tuple versions remain on the same page.

Therefore:

Free page space
      ≠
Automatically wasted space
## 4.6.12 FSM and VACUUM

UPDATE and DELETE workloads can create obsolete tuple versions.

Conceptually:

Tuple churn
    ↓
Obsolete/dead tuple versions
    ↓
Pruning / VACUUM
    ↓
Reusable page space
    ↓
FSM can represent
available space
    ↓
Future tuple placement

Normal VACUUM does not generally shrink the relation file simply because internal space becomes reusable.

## 4.6.13 Reusable Space vs. Physical Shrink

Consider a 1-TB relation.

After a large DELETE and subsequent cleanup:

Before

[USED][USED][USED][USED]

After

[USED][FREE][USED][FREE]

The physical relation may remain approximately:

1 TB

while containing substantial reusable internal space.

This leads to one of the most important storage rules in PostgreSQL:

A relation remaining the same physical size after VACUUM does not mean that VACUUM failed to make internal space reusable.

## 4.6.14 Aggregate Free Space vs. Usable Free Space

Suppose:

Page A → 600 bytes free
Page B → 900 bytes free
Page C → 500 bytes free
Page D → 700 bytes free

and the incoming tuple requires:

2 KiB

Aggregate free space exists, but none of these pages can accommodate the tuple.

Therefore:

Aggregate free space
        ≠
Usable space for every
incoming tuple

This is a critical distinction in fragmentation analysis.

## 4.6.15 FSM Is Not a Bloat Calculator

Never use:

Free space = bloat

as a universal rule.

Free space may represent:

Intentional fillfactor headroom
Normal post-VACUUM reuse capacity
Historical allocation
Fragmentation
Expected update space

Even detailed FSM inspection answers:

"What free space does PostgreSQL currently represent?"

not:

"Exactly how much storage should be reclaimed?"

Bloat requires broader workload and storage analysis.

## 4.6.16 Visibility Map Purpose

The Visibility Map records page-level visibility and freezing properties.

For each heap page, PostgreSQL maintains two important bits:

Heap Page
   │
   ├── ALL-VISIBLE
   │
   └── ALL-FROZEN

These support important optimizations involving:

Index-only scans
VACUUM
Freezing

The VM is therefore fundamentally different from the FSM.

## 4.6.17 VM Is Page-Level Metadata

The VM does not maintain a visibility record for every tuple.

Instead:

Heap Page
     ↓
Two compact VM bits

Conceptually:

Bit 1 → ALL-VISIBLE
Bit 2 → ALL-FROZEN

Therefore:

VM
  ≠
Tuple-by-tuple visibility database

It is compact page-level metadata.

## 4.6.18 All-Visible State

When PostgreSQL establishes the all-visible property for a heap page, applicable operations can use the VM rather than performing ordinary per-tuple heap visibility checks.

The most familiar benefit is index-only scanning.

Conceptually:

Index
  ↓
Find index entry
  ↓
Referenced heap page
  ↓
VM says ALL-VISIBLE?
   │
   ├── YES
   │     ↓
   │ Visibility information
   │ available without ordinary
   │ heap tuple visibility visit
   │
   └── NO
         ↓
      Heap visibility
      check required

This can materially reduce heap I/O.

## 4.6.19 Index-Only Scan Requirements

VM state alone does not create an index-only scan.

Three separate questions matter:

1. Can the index satisfy
   the query's required data?

2. Does the planner choose
   an index-only path?

3. Can VM state avoid
   heap visibility visits?

Therefore:

Efficient Index-Only Scan
          =
Suitable index
      +
Planner decision
      +
Useful VM state
      +
Runtime conditions
## 4.6.20 Heap Fetches

Consider:

EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, status
FROM public.orders
WHERE customer_id = 1001;

An index-only scan may report:

Heap Fetches: ...

Low Heap Fetches can indicate that many required visibility checks were satisfied without heap access.

High Heap Fetches can indicate more heap work.

But:

Heap Fetches is not a direct VM coverage percentage.

It depends on the specific execution, including:

Index entries visited
Rows returned
Heap-page distribution
Visibility state
Concurrent modifications
Execution behavior

Likewise:

Heap Fetches = 0

for one query does not prove that the entire table is all-visible.

## 4.6.21 All-Frozen State

The VM also records whether a heap page is all-frozen.

Conceptually:

Heap Page
    ↓
Existing tuples satisfy
applicable freezing conditions
    ↓
ALL-FROZEN

The fundamental relationship is:

ALL-FROZEN
     ↓
implies
     ↓
ALL-VISIBLE

but:

ALL-VISIBLE
     ↓
does NOT imply
     ↓
ALL-FROZEN

This distinction is fundamental to PostgreSQL VACUUM architecture.

## 4.6.22 All-Frozen Is Not Permanent

A page can later be modified.

Therefore:

ALL-FROZEN
     ↓
Page modified later
     ↓
Previous page state may
no longer apply

All-frozen should be understood as the current state of the existing tuples under applicable freezing rules, not a permanent property of the physical page.

## 4.6.23 VM State Is Conservative

An unset all-visible bit does not mean:

All tuples are invisible

and does not mean:

Page is corrupt

It means PostgreSQL cannot currently rely on that page-level optimization.

Therefore:

VM bit unset
     ≠
Database health failure

This matters greatly for high-churn relations.

## 4.6.24 Writes and VM State

A page may reach useful all-visible state and later be modified.

Conceptually:

Page becomes ALL-VISIBLE
        ↓
INSERT / UPDATE / DELETE
affects page
        ↓
Existing visibility property
may no longer hold
        ↓
VM state cleared as required
        ↓
Later maintenance
re-establishes state
where appropriate

This creates an important relationship between write activity and read behavior.

## 4.6.25 VACUUM and the VM

VACUUM is the primary operational mechanism for examining heap state and establishing useful visibility/freezing information where conditions permit.

Conceptually:

VACUUM
   ↓
Examine relevant heap state
   ↓
Visibility conditions satisfied?
   ↓
ALL-VISIBLE can be established

and:

Applicable freezing
conditions satisfied?
       ↓
ALL-FROZEN can be established

However, the canonical rule should not be interpreted as saying VACUUM is the only PostgreSQL operation capable of affecting VM state.

## 4.6.26 VM and VACUUM Page Skipping

Visibility-map information can allow VACUUM to avoid unnecessary work.

But whether a page can be skipped depends on:

VACUUM purpose
Visibility state
Freeze requirements
Transaction/MultiXact age
VACUUM options
PostgreSQL version behavior

Therefore avoid simplistic rules such as:

ALL-VISIBLE
     =
VACUUM always skips page

or:

ALL-FROZEN
     =
VACUUM never visits page again

The correct principle is:

VACUUM can use VM information to avoid heap-page work when the page state and maintenance operation permit it.

## 4.6.27 Static vs. High-Churn Relations

Consider a historical relation:

INSERT once
Few UPDATEs
Few DELETEs

Over time it may develop stable:

High all-visible coverage
        +
High all-frozen coverage

A transactional table may instead experience:

Continuous INSERT
Continuous UPDATE
Continuous DELETE
        ↓
Frequent VM state changes

Therefore:

There is no universal VM percentage that defines a healthy PostgreSQL table.

Expected state is workload-dependent.

## 4.6.28 Partitioned Tables

Each ordinary heap partition is a separate relation and therefore maintains its own storage state.

Conceptually:

orders
 │
 ├── orders_2026_06
 │      ├── MAIN
 │      ├── FSM
 │      └── VM
 │
 ├── orders_2026_07
 │      ├── MAIN
 │      ├── FSM
 │      └── VM
 │
 └── orders_2026_08
        ├── MAIN
        ├── FSM
        └── VM

This creates useful operational differences:

Historical partition
        ↓
Low write churn
        ↓
Stable VM state

Active partition
        ↓
High write churn
        ↓
Dynamic VM state

Monitor them accordingly.

## 4.6.29 TOAST and Other Relations

A TOAST table is itself a PostgreSQL relation with its own physical storage.

Therefore:

User Table
    │
    ├── Main heap storage
    │
    └── TOAST relation
             ↓
        Separate storage

A capacity investigation must not assume the main heap explains all table growth.

Use:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    ) AS main_relation,

    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_storage,

    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS index_storage,

    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_storage;
## 4.6.30 FSM/VM and Indexes

The heap FSM/VM concepts described here should not be interpreted as universal metadata for every index access method.

Indexes have their own storage structures and access-method-specific behavior.

Therefore:

Heap FSM / VM
      ≠
Universal free-space /
visibility metadata
for every relation type

This section is primarily concerned with heap storage.

## 4.6.31 Catalog-Level Visibility Estimate

pg_class exposes information that can help estimate all-visible coverage.

Example:

SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relpages,
    c.relallvisible,
    CASE
        WHEN c.relpages > 0
        THEN round(
            100.0 * c.relallvisible / c.relpages,
            2
        )
    END AS estimated_all_visible_pct
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = 'public.orders'::regclass;

Interpret this as a high-level catalog-derived indicator.

Do not treat it as an exact transactional snapshot of every current VM bit.

## 4.6.32 Deep FSM Inspection

Where approved, PostgreSQL's pg_freespacemap extension can provide deeper visibility into FSM-reported free space.

Its purpose is:

pg_freespacemap
       ↓
Inspect PostgreSQL's
free-space information

It can assist with:

Unexpected relation extension
Fragmentation analysis
Tuple-size/reuse analysis
Advanced storage investigation

It is not a bloat calculator.

## 4.6.33 Deep VM Inspection

Where approved, pg_visibility can inspect visibility-map and related page visibility information.

Conceptually:

pg_visibility
       ↓
VM/page visibility
investigation

It is appropriate when normal evidence points toward a visibility-related issue.

It should not replace continuous monitoring.

Use cases include:

Page-layout investigation
Tuple-header analysis
Storage-internals debugging
Corruption investigation

It belongs at the deepest troubleshooting level.

A safe hierarchy is:

LEVEL 1
Statistics / metrics
       ↓
LEVEL 2
Plans / catalogs /
relation sizes
       ↓
LEVEL 3
pg_freespacemap /
pg_visibility /
pageinspect

Do not automatically execute:

Privileges available?
Security policy permits it?
Change process satisfied?

This is particularly important on managed PostgreSQL platforms.

## 4.6.36 Never Manipulate FSM/VM Files Manually

FSM and VM are PostgreSQL-managed auxiliary relation forks.

Never perform generic repair actions such as:

✗ rm <relfilenode>_fsm
✗ rm <relfilenode>_vm
✗ truncate fork files
✗ zero VM/FSM pages
✗ edit fork bytes
✗ copy fork files manually

Their internal recovery/reconstruction semantics must not be interpreted as permission for filesystem manipulation.

If corruption is suspected:

Preserve evidence
      ↓
Review PostgreSQL errors/logs
      ↓
Check storage/platform events
      ↓
Identify affected objects
      ↓
Assess replicas/backups
      ↓
Use supported recovery
## 4.6.37 Production Troubleshooting Principle

During an incident, do not start with:

FSM?
VM?

Start with:

Then:

          │                   │
          ▼                   ▼
    What is growing?      Which query?
          │                   │
    ┌─────┼─────┐             ▼

  HEAP  TOAST  WAL             │

## 4.6.40 Long Transactions and VACUUM

Long-lived transactions can constrain PostgreSQL cleanup behavior.

Check:

SELECT
    pid,
    usename,
    application_name,
    state,
    backend_xmin,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

Also inspect idle-in-transaction sessions:

SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

The operational chain can be:

Long-lived snapshot
      ↓
Cleanup constrained
      ↓
Dead tuples persist
      ↓
Heap growth /
maintenance impact

FSM/VM tuning cannot fix an application that holds transactions open unnecessarily.

## 4.6.41 Autovacuum Effectiveness

Do not ask only:

"Did autovacuum run?"

Ask:

"Is autovacuum keeping pace with tuple churn?"

Example:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';

Correlate:

Tuple churn
Dead tuples
Heap growth
VACUUM frequency
VACUUM duration
I/O pressure
Transaction age
## 4.6.42 Never Disable Autovacuum as a Generic Fix

A dangerous sequence is:

VACUUM creates I/O
      ↓
Disable autovacuum

This can produce:

Dead tuple accumulation
Heap growth
Visibility degradation
Transaction-ID age risk
Emergency maintenance

Tune maintenance based on evidence.

Do not globally disable the mechanism to hide its resource consumption.

## 4.6.46 Production Scenario — False Bloat Diagnosis

Observed:

Substantial page free space

But:

fillfactor = 75
UPDATE workload high
HOT ratio strong
Heap growth stable
Latency healthy

Conclusion:

Free space
    ↓
Useful update headroom

Aggressively repacking the table could worsen write amplification.

## 4.6.47 Production Scenario — Wrong Storage Component

Observed:

Database storage
+300 GB/day

Breakdown:

Heap       +10 GB/day
Indexes     +5 GB/day
WAL       +285 GB/day

The root cause may instead be:

Replication/CDC consumer stalled
       ↓
WAL retained

FSM analysis would be irrelevant.

Therefore:

Always identify which storage component is growing before beginning heap-level investigation.

Large values
    ↓
TOAST storage
    ↓

MAIN

## 4.6.49 Capacity Runway

Storage-internals analysis does not replace capacity management.

Suppose:

Current usage = 8.5 TB
Critical limit = 9.0 TB
Growth = 100 GB/day

Then:

Remaining = 500 GB

500 / 100
≈ 5 days runway

The incident requires parallel tracks:

TRACK A
Restore safe headroom

TRACK B
Determine root cause

Never allow a deep FSM/VM investigation to consume the remaining storage runway.

## 4.6.51 Alerting Strategy

Avoid alerts such as:

FSM > 1 GB

or:

VM coverage < 80%

without workload context.

Prefer consequence-based alerts.

Example:

Heap growth acceleration
+
Logical rows stable
+
Dead tuples rising
+
Capacity runway shrinking

or:

Index-only scan
+
Heap Fetches sharply rising
+

## 4.6.58 Canonical Rules

The following rules should be retained by DBAs, DBREs, and SREs:

FSM and VM solve different problems.
FSM helps PostgreSQL locate reusable heap-page space.
FSM information is compact and quantized rather than exact free-byte accounting.
The actual heap page remains authoritative.
FSM uses a hierarchical search structure rather than requiring heap-wide scanning.
HOT requires space on the same heap page; another FSM candidate cannot make an update HOT.
Normal VACUUM can make space reusable without shrinking the relation.
Aggregate free space does not guarantee that an individual tuple can fit.
Free space is not automatically bloat.
fillfactor can intentionally preserve useful page headroom.
VM stores page-level all-visible and all-frozen information.
VM is not a tuple-by-tuple visibility database.
All-frozen implies all-visible; all-visible does not imply all-frozen.
All-frozen state is not permanent if the page is later modified.
VM state can help index-only scans avoid heap visibility work.
VM state alone does not cause the planner to choose an index-only scan.
Heap Fetches is not a VM coverage percentage.
Low VM coverage is not automatically unhealthy for a high-churn table.
VACUUM uses VM state to avoid work where applicable.
Autovacuum effectiveness must be measured against workload churn.
Long transactions can affect cleanup and storage behavior.
Historical and active partitions can have very different expected VM states.
FSM/VM fork sizes are rarely useful alert thresholds by themselves.
Always distinguish heap, TOAST, indexes, and WAL during capacity incidents.
Use pg_freespacemap, pg_visibility, and pageinspect only when deeper evidence warrants them.
Never manipulate FSM or VM files manually.
Restore capacity headroom in parallel with root-cause investigation when runway is short.
Validate application performance after database remediation.
