## 4.7.1 Overview

PostgreSQL stores heap tuples in fixed-size pages. In standard builds, the default block size is commonly 8 KiB.

Applications, however, routinely need to store variable-length values much larger than what can conveniently remain inside a heap tuple:

TEXT
VARCHAR
BYTEA
JSON / JSONB
XML
Arrays
Large application payloads

PostgreSQL handles oversized variable-length attributes using TOAST — The Oversized-Attribute Storage Technique.

At a high level:

Application Row
      ↓
Heap tuple becomes sufficiently large
      ↓
PostgreSQL applies TOAST rules
according to column storage strategy
      ↓
Compression and/or externalization
      ↓
Smaller inline heap representation

TOAST is a normal part of PostgreSQL storage architecture—not an error condition or a synonym for bloat.

For SRE/DBRE teams, TOAST can materially affect:

Heap storage
TOAST storage
Indexes
Query latency
CPU
Buffer/I/O behavior
WAL
Replication
CDC
VACUUM
Backup/recovery
Capacity
Cost
## 4.7.2 Why PostgreSQL Needs TOAST

A heap page contains structures such as:

┌─────────────────────────────────┐
│ Page Header                     │
├─────────────────────────────────┤
│ Item Identifiers                │
│                                 │
│          Free Space             │
│                                 │
├─────────────────────────────────┤
│ Heap Tuples                     │
└─────────────────────────────────┘

Now consider:

id       → small
status   → small
metadata → very large JSONB

PostgreSQL cannot treat arbitrarily large values as ordinary inline tuple contents.

TOAST allows sufficiently large variable-length attributes to be:

Compressed
     and/or
Stored outside the parent heap tuple

Conceptually:

Parent Heap Tuple
┌──────────────────────────┐
│ id                       │
│ status                   │
│ TOAST representation     │
└────────────┬─────────────┘
             │
             ▼
        TOAST Relation
        ┌──────────────┐
        │ chunk 0      │
        │ chunk 1      │
        │ chunk 2      │
        │ ...          │
        └──────────────┘
## 4.7.3 Block Size Is Not the TOAST Threshold

A critical distinction is:

PostgreSQL block size
        ≠
TOAST tuple target

Do not teach:

Attribute > 8 KiB
      ↓
TOAST

as the algorithm.

TOAST processing is driven by overall tuple-size pressure against PostgreSQL's internal TOAST targets.

Conceptually:

Heap tuple assembled
       ↓
Tuple sufficiently small?
    ┌──┴──┐
    ▼     ▼
   YES    NO
    │      │
    ▼      ▼
 Normal   Apply TOAST
 storage  mechanisms

The exact thresholds and internal constants are implementation-, build-, and version-sensitive and should not become production alert thresholds.

## 4.7.4 TOAST Is Transparent to SQL

An application can execute:

SELECT metadata
FROM public.orders
WHERE id = 1001;

without knowing whether metadata is:

Inline + uncompressed
Inline + compressed
External + uncompressed
External + compressed

PostgreSQL reconstructs the logical value when required.

This abstraction is valuable, but it also means applications can generate substantial physical storage and I/O without explicitly interacting with a "large-value storage" API.

## 4.7.5 TOAST-Capable Types

TOAST primarily applies to variable-length types whose internal representation supports it.

Common examples include:

text
varchar
bytea
json
jsonb
xml
arrays

Actual behavior depends on:

Data type
Value size
Overall tuple size
Column storage strategy
Compressibility
PostgreSQL version/build

Not every large-looking logical value necessarily becomes externally stored.

## 4.7.6 The TOAST Relation

A table with TOAST-capable attributes can have an associated TOAST relation.

Conceptually:

public.orders
      │
      ├── Parent heap
      ├── Application indexes
      │
      └── TOAST relation
              │
              └── TOAST index

The TOAST relation is a separate PostgreSQL-managed relation.

This creates a fundamental capacity rule:

The parent heap alone does not necessarily represent the complete physical footprint of a PostgreSQL table.

## 4.7.7 Finding the TOAST Relation

Use PostgreSQL catalogs:

SELECT
    c.oid,
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.reltoastrelid,
    t.relname AS toast_relation
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
LEFT JOIN pg_class AS t
  ON t.oid = c.reltoastrelid
WHERE c.oid = 'public.orders'::regclass;

The internal TOAST relation normally resides under:

pg_toast

However:

TOAST relation exists
        ≠
Large amount of data
currently stored externally

Do not diagnose a problem from reltoastrelid alone.

## 4.7.8 TOAST Is a Real Relation

Conceptually:

Parent Heap
     ↓
Separate TOAST Relation
     ↓
Separate physical storage
     +
Separate index

Because TOAST storage is relation-backed, it participates in PostgreSQL storage behavior including:

MVCC-related lifecycle
VACUUM
WAL
Buffer access
Physical capacity

This becomes especially important for high-churn large-value workloads.

## 4.7.9 External Value Chunking

Large external values are divided into ordered chunks stored as rows in the TOAST relation.

Conceptually:

Large Value X
      │
      ▼
┌───────────────────────┐
│   Large logical value │
└───────────────────────┘
      │
      ▼
    TOAST
      │
 ┌────┼────┬────┬─────┐
 ▼    ▼    ▼    ▼     ▼
 0    1    2    3    ...

A conceptual TOAST tuple contains:

chunk_id
chunk_seq
chunk_data

where:

chunk_id
   ↓
Identifies the external value

chunk_seq
   ↓
Identifies chunk ordering

chunk_data
   ↓
Stores chunk payload
## 4.7.10 TOAST Index Architecture

The associated TOAST index supports efficient chunk retrieval.

Conceptually:

Parent heap tuple
       ↓
External TOAST pointer
       ↓
TOAST index
       ↓
(chunk_id, chunk_seq)
       ↓
Ordered TOAST rows
       ↓
Logical value reconstructed

The TOAST index is real physical storage and must be considered during detailed capacity analysis.

## 4.7.11 Do Not Hard-Code Chunk Size

TOAST chunks are sized so multiple chunk tuples can be stored efficiently within PostgreSQL pages.

Do not establish a permanent operational rule such as:

Every TOAST chunk
=
exactly N bytes

Chunk sizing depends on PostgreSQL implementation/build details and tuple overhead.

The durable architectural rule is:

External TOAST values are represented as relatively small ordered chunks stored in a separate TOAST relation.

## 4.7.12 TOAST Is Not the Large Object Facility

PostgreSQL also has a separate Large Object facility.

Therefore:

TOAST
   ≠
PostgreSQL Large Object API

TOAST automatically supports storage of attributes in ordinary table rows.

Large Objects are explicitly managed through their own database interfaces and structures.

Large text, jsonb, and bytea columns normally remain ordinary table attributes whose physical representation may involve TOAST.

## 4.7.13 Storage Strategies

TOAST-capable columns support four storage strategies:

Strategy	Compression	External Storage
PLAIN	No	No
MAIN	Yes	Possible
EXTERNAL	No	Yes
EXTENDED	Yes	Yes

These strategies control the choices PostgreSQL can make when reducing tuple size.

## 4.7.14 PLAIN

PLAIN prevents compression and external storage.

PLAIN
  ↓
Inline representation
  ↓
No TOAST compression
  ↓
No externalization

It is appropriate only for types and values where inline representation is valid and expected.

Do not casually apply it to potentially large columns.

## 4.7.15 MAIN

MAIN permits compression and prefers inline storage.

However:

MAIN
  ≠
Guaranteed inline

External storage remains possible when PostgreSQL cannot otherwise make the tuple sufficiently small.

Canonical rule:

MAIN favors keeping values inline but does not prohibit external TOAST storage.

## 4.7.16 EXTERNAL

EXTERNAL permits out-of-line storage while preventing TOAST compression.

EXTERNAL
    ↓
No compression
    ↓
External storage allowed

This can be useful for specialized workloads, including cases where compression/decompression behavior is undesirable.

But:

EXTERNAL
   ≠
Automatically faster

Benchmark against representative data and access patterns.

## 4.7.17 EXTENDED

EXTENDED permits both compression and external storage and is commonly used for TOAST-capable data types.

Conceptually:

Large attribute
      ↓
Compression may be used
      ↓
Externalization may be used
      ↓
Heap tuple reduced

It provides PostgreSQL broad flexibility in representing oversized values.

## 4.7.18 Inspecting Storage Strategies
SELECT
    a.attname,
    a.attstorage
FROM pg_attribute AS a
WHERE a.attrelid = 'public.orders'::regclass
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY a.attnum;

The catalog uses internal codes representing the column's storage strategy.

Treat this as configuration information—not proof of how every current value is physically represented.

## 4.7.19 Changing Storage Strategy

Example:

ALTER TABLE public.orders
ALTER COLUMN metadata
SET STORAGE EXTERNAL;

or:

ALTER TABLE public.orders
ALTER COLUMN metadata
SET STORAGE EXTENDED;

A critical operational rule is:

Changing the storage strategy does not mean all historical values are immediately rewritten into the new representation.

The policy affects future storage decisions when values are subsequently stored or rewritten according to PostgreSQL behavior.

## 4.7.20 Compression Strategy vs. Compression Method

These are different concepts:

STORAGE STRATEGY
PLAIN
MAIN
EXTERNAL
EXTENDED

versus:

COMPRESSION METHOD
Algorithm used when
compression is attempted

PostgreSQL versions/builds can support configurable compression methods such as pglz and, where built with support, lz4.

Always verify support against the exact:

PostgreSQL version
Build
Managed-service offering

before designing a production change.

## 4.7.21 Changing Compression Does Not Automatically Rewrite History

Do not assume:

ALTER COLUMN compression
        ↓
All existing values
immediately recompressed

Existing physical representations generally remain until values are subsequently rewritten through applicable PostgreSQL operations.

If the objective is to transform historical data, a separate rewrite strategy may be necessary.

That rewrite can have major production consequences.

## 4.7.22 Compression Is Data-Dependent

Compare:

Repeated textual JSON

with:

Encrypted payload
Compressed binary
High-entropy data

Their compression behavior may differ dramatically.

Therefore:

Same logical size
      ≠
Same physical size

Capacity planning must use representative production-shaped data.

## 4.7.23 Application Compression and Encryption

A subtle production case is:

Application changes
plain JSON
    ↓
encrypted/precompressed payload

Even if business data volume remains constant:

Compressibility ↓
      ↓
TOAST compression effectiveness ↓
      ↓
Physical storage ↑
      ↓
Potential WAL / network ↑

This can look like a PostgreSQL storage regression while actually originating in an application payload change.

## 4.7.24 Detoasting

When PostgreSQL needs an externally stored or compressed value, it may need to reconstruct the logical value.

Conceptually:

Query requires attribute
       ↓
External/compressed representation
       ↓
Fetch required TOAST data
       ↓
Reconstruct
       ↓
Decompress where necessary
       ↓
Executor consumes value

This is commonly referred to as detoasting.

It can consume:

CPU
Memory
Buffer activity
Storage I/O
## 4.7.25 Detoasting Is Demand-Driven

PostgreSQL does not necessarily reconstruct every TOASTed value simply because a row is accessed.

Consider:

SELECT id, status
FROM public.orders
WHERE id = 1001;

If metadata is a very large TOASTed value but is not needed, PostgreSQL can often avoid retrieving the full value.

This is why query projection matters.

## 4.7.26 Avoid Unnecessary Large-Column Retrieval

Prefer:

SELECT id, status
FROM public.orders
WHERE customer_id = 1001;

when those are the only required attributes.

Avoid unnecessary:

SELECT *
FROM public.orders
WHERE customer_id = 1001;

on tables containing large:

JSONB
TEXT
BYTEA
Arrays
Documents

The production chain can be:

SELECT *
    ↓
Large attribute requested
    ↓
TOAST access / detoasting
    ↓
CPU / I/O ↑
    ↓
Result size ↑
    ↓
Network ↑
    ↓
Application latency ↑
## 4.7.27 ORM Risk

ORM-generated SQL can unintentionally retrieve every mapped column.

Example model:

id
customer_id
status
created_at
metadata JSONB
document BYTEA

API needs:

id
status

but ORM executes the equivalent of:

SELECT *

Potential result:

Unnecessary TOAST access
       +
Large network response

For latency-sensitive applications, inspect the actual generated SQL.

## 4.7.28 TOAST and JSONB

Large JSONB is a common TOAST workload.

Example:

CREATE TABLE events (
    event_id bigint PRIMARY KEY,
    event_time timestamptz NOT NULL,
    payload jsonb NOT NULL
);

As payloads grow:

JSONB size ↑
      ↓
Tuple pressure ↑
      ↓
Compression/externalization ↑
      ↓
TOAST footprint can ↑

But storage analysis must also include JSONB indexes.

## 4.7.29 JSONB Indexes Can Dominate Storage

Suppose:

Parent heap       300 GB
TOAST             600 GB
GIN indexes       1.4 TB

Total storage pressure is not primarily a TOAST problem.

For large JSONB workloads, always inspect:

Parent heap
TOAST heap
TOAST index
GIN indexes
Expression indexes
Other application indexes

Physical design must be evaluated as a whole.

## 4.7.30 TOAST and UPDATE

PostgreSQL MVCC creates a new row version for UPDATE.

Conceptually:

Old heap tuple
      ↓
UPDATE
      ↓
New heap tuple version

Large external attributes can materially affect the physical work associated with this operation.

However, the critical question is:

Did the large attribute itself change?

## 4.7.31 Unchanged External Values

An UPDATE of unrelated columns does not inherently require PostgreSQL to create a new physical copy of every unchanged external TOAST value.

Therefore:

UPDATE status
      ≠
Automatically rewrite
unchanged 100-KiB JSONB

This distinction is essential when estimating write amplification.

## 4.7.32 Changed Large Values

If the large attribute itself changes:

Large value A
      ↓
UPDATE
      ↓
Large value B

new physical TOAST storage can be required.

Potential consequences:

TOAST writes ↑
TOAST index work ↑
WAL ↑
Replication traffic ↑
CDC workload ↑
VACUUM workload ↑
Storage growth ↑

Large-value churn is therefore a significant capacity concern.

## 4.7.33 TOAST and HOT

TOAST can influence the size of the inline heap tuple.

Smaller inline tuples can influence available page space.

Therefore TOAST can indirectly affect page-space conditions relevant to HOT.

But:

TOAST
   ≠
HOT eligibility

HOT also depends on conditions such as:

Whether indexed columns changed
Same-page space availability
Tuple/page state
PostgreSQL HOT rules

Canonical rule:

TOAST can influence the physical conditions relevant to HOT but does not determine HOT eligibility.

## 4.7.34 DELETE and Obsolete TOAST Storage

DELETE and large-value UPDATE activity can leave physical versions that eventually become obsolete under MVCC.

Conceptually:

Large-value churn
       ↓
Obsolete physical versions
       ↓
Visibility horizon advances
       ↓
VACUUM/autovacuum
       ↓
Space can become reusable

The same fundamental MVCC rules that affect the parent heap also matter for TOAST storage lifecycle.

## 4.7.35 VACUUM and TOAST

Normal VACUUM can make obsolete storage reusable.

But:

Reusable space
      ≠
Immediate physical
file shrink

Therefore:

TOAST relation remains 900 GB

after VACUUM does not automatically mean VACUUM failed.

Future writes may reuse internal space.

## 4.7.36 Reuse vs. Physical Reclaim

These are different objectives.

REUSE
  ↓
Existing allocated storage
can service future writes

versus:

PHYSICAL RECLAIM
       ↓
Allocated storage returned
outside the relation

Many healthy PostgreSQL workloads benefit from reuse without needing physical shrink.

## 4.7.37 Large TOAST Does Not Mean Bloat

Never use:

Large TOAST relation
       =
Bloat

A large TOAST relation may simply contain large amounts of legitimate live application data.

A stronger bloat hypothesis requires evidence such as:

Logical payload stable
+
Physical TOAST growth
+
High UPDATE/DELETE churn
+
Cleanup constraints
+
Reusable/dead-space evidence

Even then, determine whether reuse is sufficient before considering a rewrite.

## 4.7.38 Long Transactions

Long-lived transactions can constrain cleanup.

Check:

SELECT
    pid,
    usename,
    application_name,
    state,
    backend_xmin,
    xact_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;

And:

SELECT
    pid,
    usename,
    application_name,
    xact_start,
    now() - xact_start AS transaction_age,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;

Possible production chain:

Long-lived snapshot
       ↓
Cleanup horizon constrained
       ↓
Obsolete versions persist
       ↓
Heap / TOAST reuse delayed
       ↓
Storage growth
## 4.7.39 Do Not Automatically Kill Old Transactions

An old transaction should trigger investigation, not automatic termination.

Determine:

Application owner
Business function
Lock impact
Cleanup impact
Rollback cost
Retry behavior
Availability risk

before terminating a backend.

Detection can be automated.

Destructive remediation should be controlled.

## 4.7.40 Autovacuum Effectiveness

Use:

SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';

Do not ask merely:

Did autovacuum run?

Ask:

Is autovacuum keeping pace with the workload?

Correlate:

Tuple churn
Dead tuples
Relation growth
Vacuum frequency
Vacuum duration
I/O
Transaction age
## 4.7.41 Never Disable Autovacuum as a Generic Fix

This is unsafe:

Autovacuum generates I/O
        ↓
Disable autovacuum

Potential consequences:

Dead versions accumulate
Storage growth ↑
Visibility maintenance degrades
Transaction-ID age risk ↑
Emergency maintenance

Tune maintenance based on evidence.

## 4.7.42 pg_column_size() — Correct Interpretation

Example:

SELECT
    pg_column_size(metadata)
FROM public.orders
WHERE id = 1001;

This is useful for value-level sizing analysis.

But:

pg_column_size(value)
       ≠
Complete physical cost
of the attribute

It should not be interpreted as including every:

TOAST tuple
TOAST index entry
Page overhead
MVCC version
Free/reusable byte
WAL record

Use relation-size functions for physical capacity accounting.

## 4.7.43 Relation Size Functions

A useful hierarchy is:

pg_relation_size()
      ↓
Specific relation/fork storage

pg_table_size()
      ↓
Table-related storage,
including auxiliary TOAST
storage, excluding the
table's application indexes

pg_indexes_size()
      ↓
Indexes associated with
the table

pg_total_relation_size()
      ↓
Complete table-related
storage including indexes

Example:

SELECT
    pg_size_pretty(
        pg_relation_size('public.orders')
    ) AS main_relation,

    pg_size_pretty(
        pg_table_size('public.orders')
    ) AS table_storage,

    pg_size_pretty(
        pg_indexes_size('public.orders')
    ) AS index_storage,

    pg_size_pretty(
        pg_total_relation_size('public.orders')
    ) AS total_storage;

For capacity incidents, pg_total_relation_size() is a useful starting point, followed by decomposition.

## 4.7.44 Direct TOAST Breakdown

For a suspected table:

SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    t.relname AS toast_relation,

    pg_size_pretty(
        pg_relation_size(c.oid)
    ) AS main_heap_size,

    CASE
        WHEN c.reltoastrelid <> 0
        THEN pg_size_pretty(
            pg_relation_size(c.reltoastrelid)
        )
    END AS toast_heap_size,

    CASE
        WHEN c.reltoastrelid <> 0
        THEN pg_size_pretty(
            pg_total_relation_size(c.reltoastrelid)
        )
    END AS toast_total_size,

    pg_size_pretty(
        pg_indexes_size(c.oid)
    ) AS parent_index_size,

    pg_size_pretty(
        pg_total_relation_size(c.oid)
    ) AS total_table_size

FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
LEFT JOIN pg_class AS t
  ON t.oid = c.reltoastrelid
WHERE c.oid = 'public.orders'::regclass;

Remember:

TOAST heap
      ≠
TOAST total

because the latter includes its associated index footprint.

## 4.7.45 Canonical Capacity Decomposition

For table-level analysis:

TABLE TOTAL
   │
   ├── Parent heap
   ├── Parent indexes
   ├── TOAST heap
   └── TOAST index

Then evaluate separately at the database/platform level:

WAL
Temporary files
Replication retention
Backups/snapshots

Do not combine unrelated storage components into a single "TOAST problem."

## 4.7.46 Growth Rate Matters More Than Absolute Size

Compare:

TOAST size = 1 TB
Growth     = 1 GB/day

with:

TOAST size = 100 GB
Growth     = 50 GB/hour

The second situation may be much more urgent.

Production monitoring should emphasize:

Δ storage / Δ time

and deviations from historical baseline.

## 4.7.47 Payload Distribution

A single average can hide important behavior.

Example:

P50   8 KiB

P99 700 KiB

A small population of very large objects may dominate:

Use sampled distributions or percentiles where practical.

## 4.7.50 TOAST and WAL

Large-value writes can affect several physical structures:

Parent heap
TOAST heap
TOAST index
Application indexes

Changes to these structures can generate WAL.

But:

Logical payload size
      ≠
Exact WAL volume

WAL also depends on factors such as:

Operation
Indexes
Full-page images
Checkpoint behavior
Compression/settings
PostgreSQL version

Measure WAL empirically.

## 4.7.51 Physical Replication

For physical streaming replication:

Primary physical changes
       ↓
WAL
       ↓
Network transport
       ↓
Replica replay

Large-value write surges can therefore contribute to:

WAL rate ↑
Network pressure ↑
Replay pressure ↑
Replica lag ↑

Monitor replication during large-value migrations, backfills, and rewrites.

## 4.7.52 Logical Replication and CDC

Physical TOAST chunks are not equivalent to logical change events.

The correct conceptual boundary is:

Heap + TOAST
physical representation
        ↓
Logical decoding
        ↓
Logical row-change representation
        ↓
Subscriber / CDC consumer

The downstream representation can depend on:

Replica identity
Publication configuration
Changed columns
Logical-decoding protocol/plugin
PostgreSQL version
Consumer behavior

Therefore:

100-KiB TOAST value
      ≠
Guaranteed 100-KiB
CDC event

Measure the actual pipeline.

## 4.7.53 Replication Slot Capacity Risk

A critical production failure mode is:

Large-value write surge
       ↓
WAL generation ↑
       ↓
CDC consumer cannot keep pace
       ↓
Replication slot lag ↑
       ↓
WAL retained
       ↓
Primary storage consumption ↑
       ↓
Disk/capacity incident

In this case, retained WAL may be the immediate storage consumer—not the TOAST relation itself.

## 4.7.54 Never Drop a Replication Slot as a Generic Disk Fix

Do not automate:

Disk low
   ↓
DROP SLOT

Dropping a replication slot can break CDC continuity and may require downstream resynchronization.

Instead:

Identify slot owner
      ↓
Check consumer
      ↓
Assess recoverability
      ↓
Protect capacity
      ↓
Apply approved recovery
## 4.7.55 Backup and Restore

TOAST contributes to the database's data footprint, but backup impact depends on backup technology.

Consider:

Physical backup
Logical backup
Incremental backup
Snapshots
Managed-service backup

Do not assume every backup copies the complete physical TOAST relation on every run.

The production requirement is:

Validate backup and recovery using the actual technology deployed.

## 4.7.56 Logical Dumps vs. Physical TOAST Layout

Tools such as pg_dump operate at the logical database layer.

Therefore:

Physical storage
Heap + TOAST chunks

is different from:

Logical dump
Logical table values

A dump should not be expected to mirror the physical TOAST relation layout.

## 4.7.57 Recovery Validation

A successful backup job does not prove recoverability.

Test:

Backup completion
Restore completion
Restore duration
Database startup
Data consistency
Application validation
RPO
RTO

This is particularly important for databases containing large amounts of large-value data.

## 4.7.58 Partitioned Tables

Each ordinary partition can maintain its own TOAST relation when required.

Conceptually:

events
 │
 ├── events_2026_07
 │      ├── heap
 │      └── TOAST
 │
 └── events_2026_08
        ├── heap
        └── TOAST

This creates useful operational differences:

Historical partition
      ↓
Low churn
Stable growth

Active partition
      ↓
High INSERT/UPDATE
High TOAST growth

Monitor active and historical partitions separately.

## 4.7.60 Production Scenario — Payload Expansion

## 4.7.85 Canonical Rules
TOAST is a normal part of PostgreSQL storage architecture.
TOAST addresses overall tuple-size pressure, not merely values exceeding an 8-KiB page.
Block size and TOAST thresholds are different concepts.
TOAST may compress values, externalize them, or both.
TOAST behavior is transparent to ordinary SQL.
A TOAST relation is a separate PostgreSQL-managed relation.
The existence of a TOAST relation does not prove large external storage is currently present.
External values are represented as ordered chunks.
The TOAST index supports locating those chunks.
Do not hard-code a universal TOAST chunk size.
TOAST is different from PostgreSQL's Large Object facility.
PLAIN, MAIN, EXTERNAL, and EXTENDED represent different storage strategies.
MAIN prefers inline storage but does not guarantee it.
EXTERNAL is a specialized tradeoff, not a universal performance optimization.
Storage strategy and compression method are different controls.
Compression-method availability depends on PostgreSQL version/build/provider.
Changing storage or compression configuration does not automatically transform every historical value.
Compression effectiveness is data-dependent.
Application encryption/precompression can materially alter PostgreSQL physical storage behavior.
Detoasting is generally demand-driven.
Avoid retrieving large columns unnecessarily.
SELECT * and ORM projection can materially affect large-value read performance.
Large JSONB storage analysis must include its indexes.
Unrelated UPDATEs do not inherently require every unchanged external value to be physically copied.
Changed large values can substantially amplify storage, WAL, replication, and maintenance work.
TOAST can influence inline tuple size but does not determine HOT eligibility.
VACUUM can make obsolete TOAST storage reusable without shrinking the relation.
Reusable space and physically reclaimed space are different concepts.
A large TOAST relation is not automatically bloated.
Long transactions can delay cleanup of obsolete storage.
Autovacuum effectiveness must be measured against workload churn.
pg_column_size() is not complete physical TOAST accounting.
Always distinguish parent heap, TOAST heap, TOAST index, application indexes, and WAL.
Growth rate and deviation from baseline are usually more useful than absolute TOAST size.
Payload distributions can matter more than averages.
Physical storage growth and WAL growth must be measured separately.
Physical TOAST representation and logical CDC representation are different layers.
Replication-slot lag can convert a large-value workload into a WAL-capacity incident.
Never drop a replication slot merely as a generic disk-space fix.
Backup impact depends on the backup technology being used.
Recovery capability must be proven through restore testing.
Partitioned tables should be analyzed at partition level when appropriate.
Large values do not automatically belong in object storage.
VACUUM FULL is not a generic TOAST remediation.
Compression and storage-strategy changes require benchmarking and change control.
Large rewrites require explicit capacity, WAL, locking, and replication planning.
Automate observation aggressively; automate destructive remediation cautiously.
Protect capacity in parallel with root-cause investigation when runway is short.
Validate both database and application behavior after remediation.
TOAST evidence should explain the incident—not replace systematic diagnosis.
