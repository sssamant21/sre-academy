## 4.8.1 Overview

PostgreSQL tablespaces provide a mechanism for controlling the physical storage location of database objects.

By default, PostgreSQL stores database objects within the cluster's normal storage hierarchy beneath PGDATA. A user-defined tablespace allows selected objects to reside in another filesystem location while PostgreSQL continues to manage them as ordinary database objects.

Conceptually:

PostgreSQL Cluster
        │
        ├── pg_default
        │      └── Default database storage
        │
        ├── pg_global
        │      └── Shared system catalogs
        │
        └── User Tablespaces
               │
               ├── ts_hot
               │     └── High-performance storage
               │
               ├── ts_archive
               │     └── Capacity storage
               │
               └── ts_temp
                     └── Temporary-work storage

Tablespaces are primarily a physical storage-placement mechanism.

They do not inherently provide:

High availability
Replication
Backup
Partitioning
Sharding
Security isolation
Automatic hot/cold tiering

Their value comes from intentionally mapping PostgreSQL objects to storage resources with different capacity, performance, cost, or operational characteristics.

## 4.8.2 Tablespaces Are Cluster-Wide Objects

A PostgreSQL tablespace belongs to the database cluster, rather than to a single database.

Multiple databases within the cluster can potentially use the same tablespace when privileges and object configuration permit.

PostgreSQL Cluster
       │
       ├── Database A ──┐
       ├── Database B ──┼──► ts_hot
       └── Database C ──┘

This has an important administrative consequence:

Tablespace lifecycle management must consider usage across the cluster.

A tablespace should not be decommissioned based only on inspection of one database.

## 4.8.3 Built-In Tablespaces

PostgreSQL initializes two built-in tablespaces:

pg_default
pg_global
pg_default

pg_default represents the cluster's normal default storage.

Conceptually:

PGDATA
   │
   └── base/
         │
         ├── Database A
         ├── Database B
         └── Database C
pg_global

pg_global contains shared relations associated with the PostgreSQL cluster rather than one particular database.

Conceptually:

PGDATA
   │
   └── global/
          │
          └── Shared cluster catalogs

These built-in tablespaces should not be treated like ordinary custom filesystem tablespaces.

## 4.8.4 Inspecting Tablespaces

Tablespace metadata is stored in pg_tablespace.

SELECT
    oid,
    spcname,
    spcowner::regrole AS owner,
    pg_tablespace_location(oid) AS location
FROM pg_tablespace
ORDER BY spcname;

Typical inventory:

pg_default
pg_global
ts_hot
ts_archive
ts_temp

This catalog is the starting point for PostgreSQL-level tablespace inventory.

## 4.8.5 Creating a User-Defined Tablespace

Example:

CREATE TABLESPACE ts_hot
LOCATION '/postgres/hot';

PostgreSQL does not provision the underlying infrastructure.

The production sequence is:

Provision storage
       ↓
Create filesystem
       ↓
Configure persistent mount
       ↓
Create empty directory
       ↓
Configure ownership/permissions
       ↓
Validate storage
       ↓
CREATE TABLESPACE

The location must satisfy PostgreSQL's filesystem requirements and should use an intentional absolute path.

## 4.8.6 Filesystem Preparation

For a self-managed Linux deployment, an example might be:

mkdir -p /postgres/hot
chown postgres:postgres /postgres/hot
chmod 700 /postgres/hot

The actual permissions should follow the organization's operating-system security standards.

Do not use:

chmod 777 /postgres/hot

as a generic workaround.

Tablespace directories are database infrastructure and should remain tightly controlled.

## 4.8.7 pg_tblspc

PostgreSQL represents user-defined tablespaces through:

$PGDATA/pg_tblspc/

Conceptually:

PGDATA
  │
  └── pg_tblspc
         │
         └── tablespace OID
                  │
                  ▼
            external location

On normal Unix-like installations this involves symbolic links into the configured tablespace locations.

Critical Safety Rule

Never manually edit, remove, recreate, or repoint pg_tblspc entries as routine administration or ad hoc incident recovery.

Tablespace lifecycle should be managed through PostgreSQL-supported operations and controlled infrastructure procedures.

## 4.8.8 Creating Tables in a Tablespace

Example:

CREATE TABLE audit_history (
    audit_id   bigint GENERATED ALWAYS AS IDENTITY,
    event_time timestamptz NOT NULL,
    payload    jsonb NOT NULL
)
TABLESPACE ts_archive;

Logical structure:

Database
   │
   └── audit_history
           │
           ▼
       ts_archive
           │
           ▼
     Capacity Storage

The table remains part of the same database.

Only its physical placement changes.

## 4.8.9 Index Placement

Indexes may be placed independently.

CREATE INDEX idx_orders_customer
ON orders(customer_id)
TABLESPACE ts_hot;

This enables:

orders heap
     │
     ▼
 ts_capacity

orders index
     │
     ▼
   ts_hot

Such designs can be useful when index access dominates the workload, but the performance benefit must be demonstrated against the actual physical storage topology.

A different tablespace name does not automatically mean a different physical I/O path.

## 4.8.10 TOAST Placement

Large PostgreSQL values may use TOAST storage.

A physical table can therefore involve:

Table
  │
  ├── Heap
  ├── Associated TOAST relation
  └── Ordinary indexes

When performing capacity analysis, always include:

Heap
+
TOAST
+
Indexes

rather than relying on heap size alone.

For example:

Heap          100 GB
TOAST         700 GB
Indexes       250 GB
-------------------
Total        1.05 TB

Ignoring TOAST can severely underestimate migration and capacity requirements.

## 4.8.11 Moving an Existing Table

An existing table can be moved:

ALTER TABLE public.orders
SET TABLESPACE ts_hot;

This is a physical storage operation, not merely a catalog rename.

Conceptually:

Source Tablespace
       │
       ▼
     orders
       │
       ▼
Destination Tablespace

PostgreSQL relocates the applicable table storage to the destination tablespace.

## 4.8.12 Indexes Do Not Automatically Follow

A crucial operational rule is:

Moving a table does not automatically move its ordinary indexes to the same tablespace.

Indexes must be handled separately where required.

ALTER INDEX public.idx_orders_customer
SET TABLESPACE ts_hot;

Therefore migration inventory must distinguish:

Table heap
TOAST
Indexes

and define the desired destination for each component.

## 4.8.13 Partitioned Tables

A partitioned parent table does not contain ordinary heap data in the same way as its physical partitions.

Suppose:

events
 │
 ├── events_2026_06
 ├── events_2026_07
 └── events_2026_08

Changing the parent:

ALTER TABLE events
SET TABLESPACE ts_archive;

does not physically migrate existing partitions.

Existing physical partitions must be moved explicitly when required.

Example:

ALTER TABLE events_2025_01
SET TABLESPACE ts_archive;

This distinction is essential for lifecycle-management architectures.

## 4.8.14 Tablespaces and Partition Lifecycle

Tablespaces can work particularly well with partitioning.

Example:

                    events
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Current       Recent       Historical
      Partition     Partition      Partition
          │            │            │
          ▼            ▼            ▼
       ts_hot      ts_standard   ts_archive
          │            │            │
          ▼            ▼            ▼
       Fast SSD       SSD        Capacity

This can support intentional hot/warm/cold placement.

PostgreSQL does not automatically move partitions based on age or activity. Lifecycle movement must be designed and operated explicitly.

## 4.8.15 Bulk Tablespace Movement

PostgreSQL supports bulk administrative movement.

For example:

ALTER TABLE ALL IN TABLESPACE old_ts
SET TABLESPACE new_ts;

Indexes can similarly be handled with appropriate ALTER INDEX ... ALL IN TABLESPACE operations.

These commands can have a significant blast radius.

Production preference:

Inventory
   ↓
Classify
   ↓
Canary
   ↓
Measure
   ↓
Batch
   ↓
Validate
   ↓
Continue

rather than automatically moving every object at once.

## 4.8.16 Database Default Tablespace

A database can be created with a specified tablespace:

CREATE DATABASE analytics
TABLESPACE analytics_ts;

That tablespace becomes the database's default physical placement where another applicable tablespace has not been selected.

Conceptually:

analytics
    │
    ├── Database catalogs
    │
    └── Default object placement
                │
                ▼
         analytics_ts
## 4.8.17 default_tablespace

PostgreSQL provides:

SHOW default_tablespace;

and allows:

SET default_tablespace = 'ts_hot';

to influence placement of subsequently created applicable objects when the object definition does not explicitly specify a tablespace.

An empty value means PostgreSQL uses the applicable database default.

Important

default_tablespace affects new object placement.

It does not migrate existing objects.

## 4.8.18 temp_tablespaces

Temporary objects and certain temporary files can be directed through:

SHOW temp_tablespaces;

Multiple tablespaces may be configured:

SET temp_tablespaces = 'ts_temp_1,ts_temp_2';

Conceptually:

Temporary workload
        │
    ┌───┴────┐
    ▼        ▼
ts_temp_1  ts_temp_2

This can help distribute temporary-storage activity across suitable resources.

## 4.8.19 Temporary Storage Is Production Storage

Temporary does not mean operationally unimportant.

A large analytical query can cause:

Large sort/hash
       ↓
Memory exceeded
       ↓
Disk spill
       ↓
Temporary storage
       ↓
Capacity / I/O pressure

Monitor:

Temporary bytes
Temporary files
Filesystem capacity
Storage latency
Throughput
Query spill behavior

A full temporary tablespace can still cause production query failures.

## 4.8.20 Tablespace Privileges

Tablespaces have owners and privileges.

Example:

GRANT CREATE
ON TABLESPACE ts_hot
TO application_owner;

Use least privilege.

Tablespace permissions control the ability to place objects in that storage location.

They do not replace:

Database privileges
Schema privileges
Table privileges
Row-level security
Encryption
Operating-system security
Cloud IAM

A tablespace is not an application security boundary.

## 4.8.21 Storage Failure Domains

Consider:

PostgreSQL
   │
   ├── PGDATA       → Volume A
   ├── ts_hot       → Volume B
   └── ts_archive   → Volume C

This provides placement flexibility but also creates multiple storage dependencies.

Failure of:

Volume B

can affect all relations depending on ts_hot, even when:

PGDATA

and:

Volume C

remain healthy.

Tablespace design must therefore consider storage availability as well as performance.

## 4.8.22 Capacity Monitoring

Tablespace capacity must be monitored at the underlying storage layer.

Example:

pg_default    55% used
ts_hot        96% used
ts_archive    43% used

A server-wide average can conceal the critical condition.

Monitor per storage location:

Capacity used
Capacity free
Growth rate
Capacity runway
IOPS
Throughput
Latency
Queue depth
Filesystem errors
Mount health
## 4.8.23 Capacity Runway

A mature capacity model includes runway.

Remaining usable capacity
÷
Recent growth rate
=
Approximate runway

Example:

Free capacity = 600 GB
Growth        = 150 GB/day

Runway ≈ 4 days

Compare:

Storage A
82% full
10 GB/month growth

with:

Storage B
65% full
200 GB/day growth

Storage B may represent the more urgent production risk.

## 4.8.25 Critical Failure Scenario — Missing Mount

One of the most dangerous self-managed tablespace incidents occurs when the expected filesystem is not mounted.

Expected:

/postgres/hot
      │
      ▼
2-TB dedicated volume

After reboot:

/postgres/hot
      │
      ▼
Directory on root filesystem

The path may still exist.

Therefore:

Directory exists

does not prove:

Correct storage mounted

## 4.8.27 Tablespace-Full Failure Scenario

Potential sequence:

Tablespace fills
      ↓
Relation/index cannot extend
      ↓
SQL operation fails
      ↓
Transaction fails
      ↓
Application errors

A tablespace-specific exhaustion event can therefore become an application outage even while other PostgreSQL storage remains healthy.

## 4.8.28 Tablespace-Full Incident Runbook
1. Confirm the capacity alert.
2. Identify the underlying storage.
3. Identify the PostgreSQL tablespace.
4. Calculate remaining capacity.
5. Calculate runway.
6. Identify largest objects.
7. Identify fastest-growing objects.
8. Check recent deployments/backfills.
9. Check temporary activity.
10. Check WAL separately.
11. Check storage health.
12. Protect remaining capacity.
13. Expand storage where safe and supported.
14. Control abnormal workload growth.
15. Move objects only when justified.
16. Validate PostgreSQL.
17. Validate replicas and CDC.
18. Validate the application.
19. Confirm growth normalized.
20. Update capacity forecast and runbook.

During an emergency, capacity protection and root-cause investigation should proceed in parallel.

## 4.8.29 Large Relation Move Is a Production Migration

Treat:

ALTER TABLE orders
SET TABLESPACE ts_capacity;

as a production storage migration.

Potential effects include:

Locking
Application availability
Storage reads/writes
WAL
Replication
Destination capacity
Backup contention
Runtime

Do not execute a multi-terabyte movement casually because the SQL syntax appears simple.

## 4.8.30 Migration Preflight

Before a large movement:

1. Confirm business/technical reason.
2. Measure heap size.
3. Measure TOAST size.
4. Measure indexes.
5. Identify source storage.
6. Identify destination storage.
7. Verify destination capacity.
8. Verify destination performance.
9. Verify storage health.
10. Review locking.
11. Estimate runtime.
12. Establish WAL baseline.
13. Check archive capacity.
14. Check replicas.
15. Check CDC/replication slots.
16. Review backup schedule.
17. Define maintenance window.
18. Define abort criteria.
19. Define fallback/recovery procedure.
20. Define validation criteria.
## 4.8.31 Locking Guardrail

A storage migration can fail operationally before significant data movement occurs.

Example:

ALTER TABLE
     ↓
Waiting for lock
     ↓
Sessions queue
     ↓
Connection pool fills
     ↓
Application degradation

Before execution determine:

Required lock
Blocking sessions
Expected wait
Application timeout
Maintenance strategy

Where appropriate, use operational guardrails such as:

lock_timeout
statement_timeout
Application traffic control
Blocking-session monitoring

according to the change plan.

## 4.8.32 Destination Capacity

Never assume source space disappears before destination space is needed.

For a large migration, destination planning must include:

Heap
+
TOAST
+
Objects intentionally moved
+
Operational headroom

and separately consider:

WAL
Archive storage
Replica storage
Backup impact

Do not run a migration with destination capacity sized exactly to the estimated relation size.

## 4.8.33 WAL Impact

Large tablespace operations can create substantial WAL activity.

However:

Relation size
      ≠
Exact WAL size

Do not use a simplistic 1:1 formula.

Instead establish:

Normal WAL/hour

and monitor:

Migration WAL/hour

during a canary or representative test.

Watch:

WAL generation
Archive backlog
Network throughput
Replica receive rate
Replica replay rate
Replication-slot retention
## 4.8.34 Physical Replication

A tablespace migration on a primary can affect physical standbys through WAL processing and storage activity.

Monitor:

Replication lag
Replay lag
WAL receive rate
Replay rate
Network throughput
Replica I/O
Replica capacity
Archive backlog

Migration success is not:

Primary command completed

if the operation leaves the standby far behind and materially degrades the required RPO/RTO posture.

## 4.8.35 Logical Replication and CDC

Logical replication does not reproduce the publisher's filesystem-placement policy.

Therefore:

Publisher
orders → ts_hot

       logical changes

Subscriber
orders → ts_standard

is valid conceptually.

Publisher and subscriber storage can be optimized independently.

During large maintenance operations, still monitor:

Replication slots
Retained WAL
Connector health
Consumer lag
Downstream throughput

where relevant.

## 4.8.39 Storage-Latency Failure Scenario

Suppose:

Heap
 ↓
ts_standard

Critical index
 ↓
ts_hot

If ts_hot develops severe latency:

Index I/O slows
      ↓
Query latency rises
      ↓
Connections remain busy longer
      ↓
Pool pressure increases
      ↓
Application latency rises

The SQL plan itself may remain perfectly valid.

Correlate PostgreSQL performance telemetry with storage telemetry.

## 4.8.40 Read-Only Filesystem Failure

A filesystem can become read-only because of underlying storage or operating-system problems.

Potential behavior:

Existing reads appear healthy
           ↓
Write/extension operation occurs
           ↓
Operation fails

Investigate:

PostgreSQL logs
Filesystem state
Kernel/storage errors
Affected relations
Application write failures

before assuming logical database corruption.

## 4.8.41 Do Not Manipulate Relation Files

Never attempt generic emergency repairs such as:

Edit pg_tblspc
Repoint tablespace links

PostgreSQL physical storage is coordinated with:

Catalog metadata
WAL
MVCC
Relation state
Recovery state

Use supported PostgreSQL backup, recovery, and administrative procedures.

## 4.8.47 Kubernetes

Tablespaces can exist in containerized PostgreSQL environments, but they create additional storage dependencies.

Conceptually:

PostgreSQL Pod
      │
      ├── PGDATA PVC
      ├── ts_hot PVC
      └── ts_archive PVC

Reliability now depends on:

PVC lifecycle
StorageClass
Volume topology
Availability zone
Pod scheduling
Volume attachment
Operator reconciliation
Backup
Failover

Use tablespaces only through the lifecycle explicitly supported by the PostgreSQL operator and storage platform.

## 4.8.48 Kubernetes Failure Scenario

Consider:

Primary pod fails
       ↓
Replacement pod scheduled
       ↓
PGDATA volume attaches
       ↓
Tablespace volume cannot attach

The database cannot be considered successfully recovered merely because PGDATA is available.

All required tablespace storage belongs to the database availability architecture.

## 4.8.49 Managed PostgreSQL Services

Self-managed tablespace architecture should not automatically be applied to managed PostgreSQL.

Examples include Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL.

Managed platforms control much of the underlying storage lifecycle.

Use provider-supported:

Storage scaling
Performance controls
I/O metrics
Backup
Recovery
High availability
Monitoring

rather than assuming arbitrary filesystem placement is available.

## 4.8.50 Aurora PostgreSQL

Aurora particularly requires a different storage mental model:

PostgreSQL-compatible database
            ↓
       Aurora service
            ↓
Distributed Aurora storage architecture

Traditional self-managed concepts such as:

Attach filesystem A
Create ts_hot
Attach filesystem B
Create ts_archive

are not the appropriate Aurora capacity-management model.

Aurora capacity and I/O engineering should use Aurora-supported service controls and telemetry.

## 4.8.57 Canonical Rules
Tablespaces control physical storage placement.
Tablespaces are cluster-wide PostgreSQL objects.
pg_default and pg_global are built-in tablespaces.
Custom tablespace infrastructure must exist before PostgreSQL creates the tablespace.
Never manipulate pg_tblspc as routine administration or generic recovery.
Tables and ordinary indexes can reside in different tablespaces.
Moving a table does not automatically move its ordinary indexes.
Include TOAST when calculating table capacity and migration requirements.
Changing a partitioned parent's tablespace does not move existing physical partitions.
Tablespaces and partitioning solve different problems but can work together effectively.
default_tablespace affects applicable new-object placement rather than existing objects.
Temporary tablespaces require capacity and performance monitoring.
Tablespaces do not provide HA, replication, backup, sharding, or security isolation.
Tablespace availability depends on underlying storage availability.
Monitor capacity per underlying storage location.
Use capacity runway in addition to percentage thresholds.
A missing mount is a critical PostgreSQL storage risk.
Verify the correct storage before PostgreSQL startup.
A tablespace-full condition can cause application failures even when other storage is healthy.
Treat large tablespace moves as production storage migrations.
Analyze locking before migration.
Use canary and batched migration when blast radius is significant.
Measure WAL rather than assuming a fixed relationship with relation size.
Monitor replicas and CDC during significant storage operations.
Coordinate large migrations with backup and other I/O-intensive workloads.
Backup architecture must explicitly support tablespaces.
Recovery testing—not successful backup completion—proves recoverability.
Document tablespace mappings for disaster recovery.
Never delete PostgreSQL physical relation files to solve capacity problems.
Decommission PostgreSQL tablespace metadata before removing underlying storage.
Performance benefits depend on the actual physical storage topology.
Cost optimization must preserve availability, durability, performance, RPO, and RTO.
Use IaC/configuration management for reproducible storage infrastructure where practical.
Use operator-supported lifecycle management for Kubernetes tablespaces.
Use provider-supported storage models for managed PostgreSQL.
Validate storage, PostgreSQL, replication, backup, and application health after every significant placement change.
