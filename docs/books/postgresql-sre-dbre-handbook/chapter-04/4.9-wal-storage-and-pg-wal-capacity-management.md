## 4.9.1 Overview

PostgreSQL Write-Ahead Logging (WAL) is fundamental to:

Transaction durability
Crash recovery
Physical replication
WAL archiving
Point-in-time recovery
Physical backup/recovery
Logical decoding
Logical replication
CDC

The fundamental write-ahead rule is:

Database change
      ↓
Generate WAL record
      ↓
Persist required WAL
      ↓
Transaction durability requirement satisfied
      ↓
Modified data page may reach storage later

WAL is therefore database recovery state, not ordinary application logging.

For an SRE/DBRE, pg_wal is one of PostgreSQL's most important capacity and availability domains.

A pg_wal capacity incident can rapidly become a database outage.

## 4.9.2 WAL Storage Location

In a standard PostgreSQL cluster, WAL is stored under:

$PGDATA/pg_wal/

Typical physical layout:

PGDATA
 │
 ├── base/
 ├── global/
 ├── pg_tblspc/
 ├── pg_multixact/
 ├── pg_replslot/
 ├── pg_stat/
 │
 └── pg_wal/
       │
       ├── WAL segment files
       └── archive_status/

Older PostgreSQL versions used:

pg_xlog

Modern PostgreSQL uses:

pg_wal
Critical Rule

Never treat pg_wal as a generic log directory.

Do not configure:

logrotate
tmpwatch
cron cleanup
filesystem cleanup scripts

to delete PostgreSQL WAL files.

## 4.9.3 WAL Segments

PostgreSQL stores WAL as sequential segment files.

A commonly used default segment size is:

16 MB

However, WAL segment size is selected when the PostgreSQL cluster is initialized and therefore should not be hard-coded into production automation.

Discover it:

SELECT bytes_per_wal_segment
FROM pg_control_init();

Human-readable:

SELECT pg_size_pretty(bytes_per_wal_segment)
FROM pg_control_init();
Canonical Rule

Discover the WAL segment size from the cluster; never assume every PostgreSQL installation uses 16-MB segments.

## 4.9.4 WAL Segment Names

A segment may look like:

000000010000000A000000FE

The filename encodes information associated with the WAL timeline and position.

Administrators should use PostgreSQL-supported functions rather than deriving operational state manually from filenames.

For example:

SELECT pg_current_wal_lsn();

and:

SELECT pg_walfile_name(pg_current_wal_lsn());
## 4.9.5 Log Sequence Numbers

PostgreSQL identifies WAL positions with Log Sequence Numbers (LSNs).

Example:

0/16B6C50

Conceptually:

WAL Stream
────────────────────────────────────────────►

LSN A        LSN B        LSN C        LSN D

LSNs are central to:

WAL measurement
Physical replication
Logical replication
Backup
Recovery
PITR
Replication-slot analysis
## 4.9.6 Measuring WAL Generation

Capture an LSN:

SELECT
    now() AS captured_at,
    pg_current_wal_lsn() AS current_lsn;

Capture it again after a known interval.

Then calculate:

SELECT pg_wal_lsn_diff(
    'LSN_AT_T2',
    'LSN_AT_T1'
);

Operational model:

LSN at T1
    ↓
LSN at T2
    ↓
LSN difference
    ↓
WAL bytes generated
    ↓
Divide by elapsed time
    ↓
WAL generation rate

Do not estimate WAL generation merely by counting files currently in pg_wal.

## 4.9.7 WAL Generation Rate

A critical production metric is:

WAL generated / unit of time

For example:

Normal workload
20 GB/hour

versus:

Bulk migration
250 GB/hour

WAL generation directly affects:

pg_wal capacity
Archive throughput
Replication
CDC
Network bandwidth
Backup/PITR
Storage I/O

Every production cluster should establish:

Average WAL/hour
P95 WAL/hour
Peak WAL/hour
WAL/day
## 4.9.8 What Generates WAL?

Common WAL-generating activity includes:

INSERT
UPDATE
DELETE
Index changes
DDL
Bulk loads
CREATE INDEX
REINDEX
Table rewrites
VACUUM FULL
CLUSTER
Tablespace moves
Backfills

WAL volume depends on workload and PostgreSQL behavior.

Never assume:

100 GB changed data
       =
100 GB WAL

## 4.9.9 WAL Generation, Retention, and Recycling

When pg_wal becomes large, distinguish three concepts:

                  pg_wal SIZE
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   GENERATION      RETENTION      RECYCLING
       │              │              │
  New WAL being   Existing WAL    Segments no
  produced         still needed    longer needed
       │              │           but retained
       ▼              ▼           for reuse
 Workload         Archive
 Rewrite          Slots
 Bulk load        Replica
 Maintenance      Recovery
                  CDC

This distinction is fundamental.

A large pg_wal directory does not automatically mean PostgreSQL is leaking disk space.

## 4.9.10 WAL Recycling

When old WAL segments are no longer required, PostgreSQL can recycle them for future WAL use rather than continually deleting and recreating files.

Therefore:

High-WAL event ends
        ↓
Workload returns to normal
        ↓
pg_wal does not necessarily
immediately shrink dramatically

Some of the remaining space may represent normal WAL recycling behavior.

## 4.9.11 min_wal_size

min_wal_size influences how much WAL PostgreSQL tends to retain for recycling when those segments are no longer required for another reason.

It does not mean:

Minimum filesystem size

and it does not mean:

Guaranteed pg_wal directory size

Think of it as part of PostgreSQL's WAL recycling policy.

## 4.9.12 max_wal_size

This is one of the most commonly misunderstood WAL parameters.

max_wal_size is a soft WAL/checkpoint management target.

It is not a hard pg_wal capacity ceiling.

Therefore:

max_wal_size = 10 GB

does not mean:

pg_wal <= 10 GB

PostgreSQL can retain substantially more WAL.

Canonical Rule

Never size the WAL filesystem by assuming max_wal_size represents the maximum possible pg_wal footprint.

## 4.9.13 Why pg_wal Can Exceed max_wal_size

Reasons include:

Archive backlog
Replication slots
Slow/down replicas
Logical decoding
CDC consumers
Backup/recovery requirements
High WAL generation
Checkpoint behavior
wal_keep_size

Therefore the correct incident question is not:

Why did PostgreSQL ignore max_wal_size?

It is:

Why is this WAL being generated or retained?

## 4.9.14 wal_keep_size

wal_keep_size provides minimum older-WAL retention intended to help streaming standbys catch up.

Conceptually:

Primary
  │
  ├── Current WAL
  ├── Recent WAL
  └── WAL retained for standby catch-up

It is a minimum, not a maximum.

wal_keep_size
      ≠
maximum pg_wal size

It is also not a complete HA guarantee.

A sufficiently lagging standby may need:

WAL archive
Replication slot
Alternative recovery source
New base backup

depending on the architecture.

## 4.9.15 Checkpoints and WAL

Important checkpoint-related parameters include:

checkpoint_timeout
checkpoint_completion_target
max_wal_size
min_wal_size

Checkpoints influence:

Write I/O
WAL recycling
Full-page images
Crash-recovery duration
Runtime performance

Increasing max_wal_size may reduce WAL-driven checkpoint frequency, but can increase the amount of recovery work after a crash.

Therefore checkpoint tuning is a reliability/performance tradeoff.

## 4.9.16 Full-Page Writes

With normal crash-safety behavior, PostgreSQL may write a full-page image to WAL the first time a page is modified after a checkpoint when required.

Conceptually:

Checkpoint
    ↓
First modification of page
    ↓
Full-page image may enter WAL
    ↓
Additional WAL

Consequently, checkpoint behavior can influence WAL volume.

Do not disable durability mechanisms merely to reduce WAL generation.

## 4.9.17 WAL Compression

Where supported by the deployed PostgreSQL version, WAL compression can reduce the size of applicable WAL records, including full-page images.

Potential benefits:

Reduced WAL volume
Reduced archive bandwidth
Reduced replication bandwidth
Reduced storage pressure

Potential tradeoff:

Additional CPU

Evaluate against the real workload.

## 4.9.18 WAL Write Path

Simplified transaction path:

Application
     ↓
SQL transaction
     ↓
PostgreSQL buffers
     ↓
WAL records generated
     ↓
WAL buffers
     ↓
WAL storage
     ↓
Required persistence
     ↓
COMMIT acknowledged

Relevant durability settings include:

fsync
synchronous_commit
wal_sync_method

These are reliability settings and must not be changed casually to solve latency.

## 4.9.19 WAL Storage Performance

Important metrics:

Write latency
Sync latency
IOPS
Throughput
Queue depth
Storage errors
Filesystem state

Failure chain:

Storage latency
      ↓
WAL persistence latency
      ↓
Commit latency
      ↓
Transaction latency
      ↓
Application latency

WAL storage should therefore be part of any investigation into slow commits.

## 4.9.20 Dedicated WAL Storage

Some self-managed deployments use dedicated WAL storage:

              PostgreSQL
              ┌────┴────┐
              ▼         ▼
            DATA        WAL
              │          │
          Volume A    Volume B

Potential advantages:

I/O isolation
Independent capacity
Predictable latency
Separate performance tier

But this also introduces another critical failure domain.

WAL volume failure
        ↓
WAL unavailable
        ↓
Database availability/recovery affected

Use dedicated WAL storage only when supported by measurable reliability or performance requirements.

## 4.9.21 WAL Is Not a Tablespace

Tablespaces and WAL solve different problems.

TABLESPACE
     ↓
Relation placement

pg_wal
     ↓
Database WAL storage

You do not use:

CREATE TABLESPACE

to relocate WAL.

## 4.9.22 WAL Archiving

When WAL archiving is configured:

PostgreSQL
    ↓
pg_wal
    ↓
Archive mechanism
    ↓
WAL Archive

Archived WAL may support:

PITR
Backup recovery
Disaster recovery
Recovery history

Archiving therefore creates another critical throughput and capacity dependency.

## 4.9.23 Archive Failure

Consider:

WAL generation = 100 GB/hour
Archive         = 0 GB/hour

Backlog:

+100 GB/hour

Eventually:

pg_wal capacity exhausted

A remote archive failure can therefore become a local PostgreSQL availability incident.

## 4.9.24 Archive Throughput Failure

Archiving does not need to fail completely to create a problem.

Example:

WAL generation       100 GB/hour
Archive throughput    70 GB/hour
--------------------------------
Net accumulation       30 GB/hour

The archive process may technically be succeeding while the system is still heading toward exhaustion.

Production Requirement
Sustainable archive throughput
              >
Sustainable WAL generation

Temporary bursts are acceptable only when sufficient headroom exists and the archive can subsequently catch up.

## 4.9.25 Archive Monitoring

Use PostgreSQL statistics such as:

SELECT *
FROM pg_stat_archiver;

Monitor:

Archived count
Failed count
Last successful archive
Last archive failure
Time since last successful archive
Archive throughput
WAL generation rate
Archive backlog
Archive destination capacity

Cumulative failure counts alone are not sufficient.

## 4.9.26 Replication Slots

Replication slots can retain WAL needed by:

Physical standby
Logical replication
Logical decoding
CDC

Failure model:

PostgreSQL generates WAL
         ↓
Consumer stops
         ↓
Slot stops advancing
         ↓
Required WAL retained
         ↓
pg_wal grows
         ↓
Filesystem fills

Replication slots are therefore both a recovery feature and a capacity dependency.

## 4.9.27 Production Slot Ownership

Every production slot must have:

Slot name
Slot type
Consumer
Owner
Criticality
Expected lag
Retention threshold
Recovery procedure
Reinitialization procedure

Example:

Slot	Consumer	Owner	Criticality	Recovery
ha_standby_01	HA standby	DBRE	Critical	Rebuild standby
orders_cdc	CDC	Data Platform	High	Resnapshot/reinitialize
analytics	Analytics	Data Engineering	Medium	Reinitialize

There should be no ownerless production replication slots.

## 4.9.28 Measuring Slot-Retained WAL

Example:

SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    confirmed_flush_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(
            pg_current_wal_lsn(),
            restart_lsn
        )
    ) AS retained_wal
FROM pg_replication_slots
WHERE restart_lsn IS NOT NULL;

Example output:

Slot                Retained WAL
--------------------------------
standby_01                 2 GB
orders_cdc               850 GB
analytics_cdc             15 GB

This immediately identifies the dominant retention source.

## 4.9.29 wal_status

Where supported, pg_replication_slots exposes:

reserved
extended
unreserved
lost

Production interpretation:

reserved
   ↓
Required WAL safely retained

extended
   ↓
Retention extends beyond normal
max_wal_size expectations

unreserved
   ↓
Required WAL is at risk /
no longer guaranteed

lost
   ↓
Required WAL has been lost;
slot cannot continue normally

Suggested operational severity:

reserved    → Normal
extended    → Investigate
unreserved  → High
lost        → Critical
## 4.9.30 safe_wal_size

Where available, safe_wal_size provides a powerful predictive signal for bounded slot retention.

Conceptually:

safe_wal_size
      ↓
Additional WAL that can be written
before slot WAL availability is threatened

Approximate:

safe_wal_size
÷
Current WAL generation rate
=
Slot safety runway

Example:

safe_wal_size = 300 GB
WAL rate      = 75 GB/hour

Slot runway ≈ 4 hours
## 4.9.31 Two Capacity Runways

A mature system should track two different concepts.

Filesystem Runway
Free filesystem capacity
÷
Net WAL accumulation rate
=
Filesystem runway

Answers:

How long before WAL storage fills?

Slot Safety Runway
safe_wal_size
÷
WAL generation rate
=
Approximate slot safety runway

Answers:

How long before the lagging consumer risks losing required WAL?

These are different reliability risks.

## 4.9.32 max_slot_wal_keep_size

By default, replication-slot retention can represent a major capacity risk.

max_slot_wal_keep_size can bound slot-driven WAL retention.

Conceptually:

Unlimited retention
       ↓
Protect consumer
       ↓
Risk primary storage

versus:

Bounded retention
       ↓
Protect primary storage
       ↓
Risk lagging consumer
       ↓
Possible reinitialization

This is a reliability tradeoff.

The value should be derived from:

WAL generation rate
Consumer outage tolerance
Available capacity
Recovery time
Reinitialization time
RPO/RTO

not selected arbitrarily.

## 4.9.33 Checkpoint-Aware Slot Enforcement

Slot WAL retention limits are enforced in relation to checkpoint processing.

Therefore do not assume:

Slot reaches exact byte threshold
        ↓
Required WAL instantly disappears

Operational monitoring must account for checkpoint timing.

## 4.9.34 Idle Slot Guardrails

Where supported, PostgreSQL provides controls for invalidating qualifying replication slots after prolonged inactivity.

These can protect against abandoned slots but can also force consumer reinitialization.

They supplement—not replace—

Slot ownership
Consumer monitoring
Capacity monitoring
Retention limits
Recovery runbooks
## 4.9.35 Never Drop a Slot Blindly

Do not respond to WAL pressure automatically with:

SELECT pg_drop_replication_slot('orders_cdc');

First determine:

Who owns the consumer?
Is it recoverable?
Does it need the retained WAL?
Can it catch up?
What happens if WAL is lost?
Does it require resnapshot/reinitialization?
What is the downstream consistency impact?

Dropping a slot is a recovery decision, not ordinary disk cleanup.

## 4.9.36 Physical Replication

WAL drives physical streaming replication.

Primary
   │
   ▼
WAL
   │
   ▼
Standby

Monitor:

sent_lsn
write_lsn
flush_lsn
replay_lsn
write lag
flush lag
replay lag
Network throughput
Replica storage latency
Replica CPU

Distinguish:

Transport lag

from:

Replay lag

A standby can receive WAL quickly but replay it slowly.

## 4.9.37 Logical Replication and CDC

Logical consumers are particularly important operationally.

PostgreSQL
     ↓
Logical replication slot
     ↓
CDC
     ↓
Kafka / Streaming
     ↓
Warehouse / Search / Analytics

If CDC stops:

CDC failure
     ↓
Slot stops advancing
     ↓
WAL retained
     ↓
Primary storage pressure
Canonical Principle

A downstream CDC outage can become an upstream PostgreSQL availability incident.

PostgreSQL and downstream CDC monitoring must therefore be correlated.

## 4.9.38 CDC Recovery Validation

When a failed CDC connector restarts, do not declare the incident resolved simply because:

Connector = Running

Validate:

Slot advancing
confirmed_flush_lsn advancing
Retained WAL declining
CDC lag declining
Downstream processing healthy
Data consistency validated
## 4.9.39 WAL Capacity Model

Production headroom should account for:

Normal/recycled WAL footprint
+
Peak WAL burst
+
Archive outage tolerance
+
Replica catch-up tolerance
+
Slot-retention allowance
+
Backup/recovery requirements
+
Operational safety margin

These components may overlap.

This is a planning framework, not an exact PostgreSQL allocation formula.

## 4.9.40 Example Capacity Engineering

Suppose:

Peak WAL generation      = 150 GB/hour
Archive outage objective = 6 hours

Simplified archive exposure:

150 × 6
=
900 GB

Then consider:

CDC outage tolerance
Replica lag tolerance
Normal WAL footprint
Operational margin

A 200-GB WAL filesystem would clearly be inconsistent with that six-hour archive-failure objective.

Capacity must derive from failure tolerance, not normal utilization alone.

## 4.9.41 Filesystem Capacity Runway

When net accumulation is positive:

Free WAL capacity
÷
Net accumulation rate
=
Approximate runway

Example:

Free capacity       = 500 GB
WAL generation      = 180 GB/hour
Archive throughput  = 80 GB/hour

Net accumulation    = 100 GB/hour

Runway ≈ 5 hours

This is far more actionable during an incident than disk percentage alone.

WARNING

HIGH

Thresholds must reflect:

Filesystem utilization

Example:

System A
90% full

## 4.9.47 WAL Capacity Incident Classification

When pg_wal grows unexpectedly:

                    pg_wal GROWTH
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
         WAL GENERATION        WAL RETENTION
              │                     │
       ┌──────┼──────┐       ┌──────┼───────┐
       ▼      ▼      ▼       ▼      ▼       ▼
     Bulk   App    Rewrite  Archive Slot   Replica
     load   load            backlog lag     lag
       │      │      │       │      │       │
       └──────┴──────┴───────┴──────┴───────┘
                         │
                         ▼
                  Both may occur

Then separately determine whether part of the observed directory footprint represents normal recycling.

## 4.9.49 Emergency Action Hierarchy

Prefer reversible and integrity-preserving actions:

1. Safely expand capacity.
2. Restore archiving.
3. Restore CDC consumer.
4. Restore replica.
5. Pause optional high-WAL workload.
6. Reduce optional ingestion if approved.
7. Recalculate runway.
8. Consider destructive consumer-reset actions only
   after understanding downstream consequences.

Do not immediately:

Delete WAL
Drop slot
Disable archiving
Reset WAL
## 4.9.50 Absolute Safety Rule — Never Delete WAL

Never execute generic cleanup such as:

rm -f $PGDATA/pg_wal/*

Never manually remove selected "old" WAL files because the filesystem is nearly full.

Potential consequences include:

Crash-recovery failure
Startup failure
Replication failure
PITR loss
Backup/recovery failure
Data-loss risk
Correct Response
Capacity pressure
      ↓
Preserve WAL
      ↓
Calculate runway
      ↓
Identify generation/retention owner
      ↓
Add safe capacity if required
      ↓
Fix root cause
      ↓
Allow PostgreSQL to manage WAL
## 4.9.51 pg_resetwal Is Not Capacity Management

pg_resetwal must not be treated as:

Disk-full cleanup utility

or:

Routine WAL repair

It is an exceptional recovery/support utility with potentially serious consequences.

It does not belong in the normal pg_wal capacity incident workflow.

## 4.9.58 WAL Archive Capacity

## 4.9.80 Canonical Rules
WAL is database durability and recovery state—not ordinary log data.
pg_wal is critical PostgreSQL storage.
Never manually delete files from pg_wal.
Never use pg_resetwal as routine capacity remediation.
Discover WAL segment size rather than assuming 16 MB.
Use LSN differences and PostgreSQL statistics to measure WAL generation.
Establish normal, P95, and peak WAL-generation baselines.
Distinguish WAL generation, retention, and recycling.
A large pg_wal directory does not automatically indicate a leak.
min_wal_size influences WAL recycling.
max_wal_size is a soft checkpoint-related target—not a hard pg_wal limit.
wal_keep_size is minimum standby-oriented retention—not maximum WAL retention.
Archive failures can cause local WAL exhaustion.
Archive throughput must sustainably keep pace with WAL generation.
Replication slots can retain very large amounts of WAL.
Every production replication slot must have an owner and recovery procedure.
Monitor retained WAL per slot.
Monitor wal_status where supported.
Monitor safe_wal_size where supported.
Track filesystem runway and slot safety runway separately.
Bounded slot retention protects the primary at the potential cost of consumer reinitialization.
Never drop a replication slot without understanding downstream consequences.
A CDC failure can become a PostgreSQL availability incident.
Physical replica lag belongs in WAL capacity monitoring.
Network throughput belongs in WAL architecture.
WAL storage latency can directly affect transaction latency.
Dedicated WAL storage creates another critical failure domain.
High-WAL maintenance requires production preflight and abort criteria.
Capacity must be engineered for failure tolerance, not only normal workload.
Runway is more actionable than percentage-used alone.
Capacity expansion can buy incident-response time but does not replace root-cause remediation.
Backup success alone does not prove PITR recoverability.
Test restore and PITR procedures regularly.
Archive retention must align with RPO/RTO and backup lifecycle.
Use version-aware monitoring because PostgreSQL WAL observability evolves.
Use provider-supported storage controls on managed PostgreSQL.
Use operator-supported storage architecture on Kubernetes.
Automate monitoring aggressively but destructive WAL actions conservatively.
Protect durability and recoverability before reclaiming storage.
Every WAL incident ends only after capacity, archive, replication, CDC, recovery, and application health are validated.
