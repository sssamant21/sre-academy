# 5.1 -- PostgreSQL Transaction Architecture and Fundamentals

**Status:** Complete -- Revised Final / Canonical Edition

## Purpose
PostgreSQL transactions define atomic units of database work and provide the foundation for MVCC, isolation, locking, durability, and recovery. A transaction may be explicit or implicitly created around a statement.

## Architecture
```text
Client -> transaction boundary -> statements -> MVCC/locks -> WAL/durability -> COMMIT or ROLLBACK
```

`BEGIN` starts an explicit transaction block; `COMMIT` makes its effects durable according to configured durability semantics; `ROLLBACK` abandons its changes. PostgreSQL assigns transaction identity as required rather than treating every read-only transaction identically to a write transaction.

## Production Guidance
Keep transactions short, deterministic, and bounded. Avoid network calls, user interaction, or uncontrolled batch processing inside open transactions. Define retry behavior for concurrency errors at the application transaction boundary.

## Monitoring
Use `pg_stat_activity` to track `xact_start`, state, wait events, query age, and application identity. Alert on transaction age using workload-specific thresholds.

## Failure Scenarios
Long transactions retain resources and visibility horizons; abandoned `idle in transaction` sessions can block maintenance; oversized transactions increase rollback, WAL, replication, and lock impact.

## SRE/DBRE Rules
1. Transaction boundaries are reliability boundaries.
2. Minimize transaction duration without violating correctness.
3. Monitor transaction age and state.
4. Design retries at the whole-transaction level when required.
5. Never terminate production transactions solely because they are old; identify ownership and impact first.
