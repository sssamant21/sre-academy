# 5.15 -- Row-Level Locks and Row Locking Behavior

**Status:** Complete -- Revised Final / Canonical Edition

PostgreSQL row-level locks coordinate concurrent modification of individual rows. `UPDATE`, `DELETE`, and explicit locking clauses can wait when another transaction holds a conflicting row lock. Row locks do not generally block plain reads, but they can serialize writers to hot rows.

## Hot-Row Pattern
```text
many workers -> same row -> row-lock queue -> latency -> timeout/retry storm
```

## Production Guidance
Reduce hot-row designs, keep transactions short, update rows in consistent order, and use `NOWAIT` or `SKIP LOCKED` only when their semantics match the application. `SKIP LOCKED` provides a queue-like work distribution behavior, not a general consistent view.

## Rules
1. Writer/writer contention can dominate even when CPU is low.
2. Avoid centralized counters/hot rows where possible.
3. Define lock ordering.
4. Bound retries.
5. Monitor row-lock wait symptoms through activity/wait telemetry.
