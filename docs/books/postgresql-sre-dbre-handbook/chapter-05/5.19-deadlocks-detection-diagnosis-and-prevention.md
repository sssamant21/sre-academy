# 5.19 -- Deadlocks: Detection, Diagnosis, and Prevention

**Status:** Complete -- Revised Final / Canonical Edition

A deadlock occurs when transactions form a dependency cycle in which each waits for another. PostgreSQL detects deadlocks and aborts one transaction so progress can continue.

```text
T1 holds A -> waits B
T2 holds B -> waits A
        => cycle => deadlock victim aborted
```

## Prevention
Acquire shared resources in a consistent order, shorten transactions, avoid unnecessary lock scope, and design application retries for deadlock victims. `deadlock_timeout` affects when PostgreSQL performs deadlock checking/log-related behavior; it is not a substitute for fixing recurring lock-order defects.

## Monitoring
Track database deadlock counters, server logs, affected SQL, objects, transaction age, application version, and recurrence rate.

## Rules
1. Deadlocks are correctness-preserving aborts, but recurring deadlocks are application/design incidents.
2. Retry the complete transaction when safe.
3. Standardize lock ordering.
4. Preserve deadlock log evidence.
5. Do not mask recurring deadlocks with infinite retries.
