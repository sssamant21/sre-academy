# 5.2 -- Transaction Lifecycle: BEGIN, COMMIT, ROLLBACK, and SAVEPOINT

**Status:** Complete -- Revised Final / Canonical Edition

## Lifecycle
```sql
BEGIN;
-- statements
SAVEPOINT before_step;
-- risky step
ROLLBACK TO SAVEPOINT before_step;
COMMIT;
```
A transaction moves from start through statement execution to commit or rollback. After an error inside a transaction block, PostgreSQL normally requires rollback of the failed transaction state or rollback to an appropriate savepoint before useful work continues.

## Production Design
Use savepoints deliberately; excessive subtransaction use adds complexity and overhead. Never leave transactions open while waiting for external systems or human input. Treat commit acknowledgement loss as an ambiguous-outcome problem: applications must avoid blindly replaying non-idempotent business operations.

## Operational Checks
Track transaction age, state, blocked time, rollback rate, application name, and error patterns. During incidents identify whether a session is active, waiting, idle, or idle in transaction before intervention.

## Rules
1. Explicitly define transaction ownership.
2. Keep rollback paths tested.
3. Use savepoints for scoped recovery, not as a substitute for transaction design.
4. Handle uncertain commit outcomes with application-level idempotency/reconciliation.
5. Termination is an operational change requiring impact analysis.
