# 5.20 -- Long-Running Transactions and idle in transaction

**Status:** Complete -- Revised Final / Canonical Edition

Long transactions can retain locks, snapshots, old tuple visibility horizons, resources, and operational uncertainty. `idle in transaction` means the backend is not currently executing a query but remains inside an open transaction.

```sql
SELECT pid, usename, application_name, state, xact_start,
       now()-xact_start AS xact_age, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

## Prevention
Use transaction-scoped application design, connection-pool hygiene, `idle_in_transaction_session_timeout` where appropriate, and bounded request lifetimes. Test timeout behavior before production enforcement.

## Incident Rule
Do not kill every old transaction. Determine owner, locks, rollback cost, business operation, retry safety, and whether the transaction is actually causing the incident.

## Rules
1. Transaction age is a first-class SRE metric.
2. Idle in transaction is not the same as ordinary idle.
3. Bound application transaction lifetimes.
4. Use timeouts as guardrails, not substitutes for code fixes.
5. RCA repeated offenders by service/query pattern.
