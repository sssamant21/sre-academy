# 5.25 -- Production Transaction, Locking, and Deadlock Case Studies

**Status:** Complete -- Revised Final / Canonical Edition

## Case 1 -- Idle Transaction Blocks DDL
A deployment waits on a schema change while an application session has remained idle in transaction. Response: identify the root session and owner, evaluate rollback/retry impact, safely end or complete the transaction, drain the lock queue, then fix transaction lifecycle and timeout policy.

## Case 2 -- Opposite Update Order Deadlocks
Two services update account A then B versus B then A. PostgreSQL detects the cycle and aborts one transaction. Response: standardize resource ordering, implement bounded transaction retries, preserve deadlock logging, and concurrency-test the fix.

## Case 3 -- Hot Queue Row
Hundreds of workers contend on the same coordination row. CPU is moderate but latency is extreme. Response: identify row-lock waits, redesign work distribution, cap worker concurrency, and use appropriate queue semantics such as carefully designed `SKIP LOCKED` processing where correctness permits.

## Case 4 -- Long Analytics Snapshot Causes Cleanup Pressure
A multi-hour reporting transaction on a high-churn primary retains an old snapshot. Dead versions and storage grow. Response: bound analytics duration, evaluate replica/offload architecture, monitor transaction age, and verify cleanup catches up after the horizon advances.

## Case 5 -- Wraparound Risk
Database XID age approaches protective thresholds while old prepared/open transactions and I/O pressure impede maintenance. Response: protect capacity, resolve old transaction horizons safely, allow anti-wraparound vacuum to complete, monitor freeze progress, and correct the operational control failure.

## Canonical Lessons
- Concurrency incidents are often queueing problems, not CPU problems.
- Transaction duration multiplies lock and MVCC risk.
- Consistent lock ordering prevents a major class of deadlocks.
- Retry behavior is part of transaction correctness.
- XID/MultiXact age is a mandatory safety metric.
- Automation should collect evidence faster than humans, while destructive remediation remains controlled.
