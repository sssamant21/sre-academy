# 5.3 -- ACID Properties and PostgreSQL Transaction Guarantees

**Status:** Complete -- Revised Final / Canonical Edition

## ACID Model
- **Atomicity:** a transaction commits as a unit or its database changes are rolled back.
- **Consistency:** database constraints plus correct application logic preserve declared invariants.
- **Isolation:** concurrent transactions observe behavior defined by PostgreSQL's isolation semantics.
- **Durability:** committed changes survive failures according to WAL, synchronous-commit, storage, and replication configuration.

ACID does not mean every business workflow is automatically correct. Cross-service consistency, retries, duplicate requests, external side effects, and asynchronous replication require explicit design.

## Production Guidance
Document durability and RPO requirements before changing `synchronous_commit` or replication policy. Use database constraints for enforceable invariants. Test application behavior under aborts, serialization failures, deadlocks, failover, and ambiguous client disconnects.

## Rules
1. Do not weaken durability without an explicit business decision.
2. Isolation level does not replace application correctness.
3. Constraints are part of the consistency architecture.
4. Failover and client retries must preserve idempotency.
5. Validate ACID assumptions under failure, not only normal execution.
