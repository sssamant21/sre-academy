# 5.4 -- MVCC Architecture and Tuple Versioning

**Status:** Complete -- Revised Final / Canonical Edition

PostgreSQL MVCC lets transactions work from snapshots while concurrent writers create new row versions. Readers generally do not block writers merely because they read the same rows, but writers can still conflict with writers and explicit locks can introduce blocking.

```text
old tuple -> UPDATE -> old version + new version -> visibility rules -> cleanup/reuse
```

Tuple headers carry transaction-related metadata used in visibility decisions. Old versions cannot always be removed immediately because another snapshot may still need them.

## Production Consequences
High UPDATE/DELETE churn creates dead versions, WAL, vacuum demand, and potential storage growth. Long transactions can delay cleanup. HOT can reduce some index churn when its requirements are satisfied.

## Monitoring
Correlate `pg_stat_user_tables` live/dead tuple estimates, update/HOT-update counters, vacuum activity, transaction age, relation growth, WAL rate, and I/O.

## Rules
1. MVCC concurrency has storage and maintenance costs.
2. Old does not mean immediately removable.
3. Row-count stability does not imply low churn.
4. Diagnose long snapshots when cleanup lags.
5. Do not classify all reusable space as bloat.
