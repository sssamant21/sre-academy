# 5.7 -- Transaction Isolation Levels

**Status:** Complete -- Revised Final / Canonical Edition

PostgreSQL exposes Read Committed, Repeatable Read, and Serializable behavior; Read Uncommitted is treated as Read Committed. Isolation determines which concurrent effects a transaction can observe and which anomalies or retry conditions applications must handle.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- business transaction
COMMIT;
```

## Selection
Use the weakest level that safely preserves the application's invariants, but never choose solely for speed. Higher isolation can require application retries and may increase contention-related aborts.

## Production Validation
Test concurrent scenarios, not just single-session correctness. Record isolation requirements per workload and monitor serialization failures, deadlocks, latency, transaction age, and lock waits.

## Rules
1. Isolation is a correctness contract.
2. Read Uncommitted does not provide weaker semantics than Read Committed in PostgreSQL.
3. Retryable concurrency errors are expected design inputs.
4. Do not globally raise isolation without workload testing.
5. Encode invariants with constraints/locking/serializable semantics as appropriate.
