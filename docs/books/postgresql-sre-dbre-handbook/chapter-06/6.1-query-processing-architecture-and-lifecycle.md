# 6.1 -- PostgreSQL Query Processing Architecture and Lifecycle

**Status:** Complete -- Revised Final / Canonical Edition

PostgreSQL query processing converts SQL text into validated structures, an optimized execution plan, and executor operations that produce or modify rows. The production lifecycle is client request -> parse -> analyze -> rewrite -> plan/optimize -> execute -> return results/commit effects.

SRE/DBRE diagnosis must locate latency in the correct phase: connection/queueing, planning, lock waits, execution CPU, buffer/cache access, physical I/O, temporary spill, WAL generation, client transfer, or commit. Never label all database latency as query execution time.

Use `pg_stat_activity` for active/waiting sessions, `EXPLAIN` for plan structure, `EXPLAIN ANALYZE` only with production safety review, and workload telemetry such as `pg_stat_statements` for aggregate query behavior. Query tuning starts with evidence and a reproducible baseline, not parameter guessing.

**Canonical rules:** preserve SQL correctness; separate planning from execution; correlate database and infrastructure telemetry; test changes with representative data and concurrency; define rollback before production plan changes.
