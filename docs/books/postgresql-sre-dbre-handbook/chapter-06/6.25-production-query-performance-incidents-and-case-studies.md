# 6.25 -- Production Query Performance Incidents and Case Studies

**Status:** Complete -- Revised Final / Canonical Edition

## Case 1 -- Cardinality regression
A selective OLTP query changes to a costly join after data distribution shifts. Diagnosis finds severe estimated-vs-actual error on correlated predicates. Remediation refreshes statistics, adds targeted extended statistics, validates the new plan under representative parameters, and adds estimate-error monitoring for the query family.

## Case 2 -- Memory tuning causes fleet pressure
A reporting query spills to disk, so `work_mem` is raised globally. Concurrent sessions multiply memory use and cause host/container pressure. Recovery reverts the global change, tunes the reporting workload at narrower scope, improves the plan, and adds concurrency-aware memory capacity review.

## Case 3 -- Parallel query contention
A large analytical query gains latency from parallelism in isolation but saturates CPU when many copies run concurrently. Remediation balances worker limits/workload concurrency and evaluates total throughput rather than single-query speed.

## Case 4 -- Plan-sensitive prepared statement
Common parameters perform well while rare values are extremely slow under a generic plan. Diagnosis compares parameter classes and custom/generic plans; remediation is validated through the actual driver/pooler path.

## Case 5 -- Storage latency mistaken for SQL regression
Plans remain stable but physical read latency rises. Database buffer-read telemetry correlates with infrastructure storage latency. The incident is resolved at the storage layer rather than by rewriting correct SQL.

**Chapter principle:** tune the complete workload and reliability envelope, not an isolated plan screenshot.
