# 6.3 -- Query Planner and Optimizer Architecture

**Status:** Complete -- Revised Final / Canonical Edition

PostgreSQL uses a cost-based planner to compare feasible paths for scans, joins, ordering, aggregation, parallelism, and other operations. The planner depends on SQL semantics, relation/index metadata, statistics, configuration, estimated row counts, and cost parameters.

The cheapest estimated plan is not guaranteed to be the fastest measured plan because estimates model reality rather than perfectly observe it. Large estimated-vs-actual row differences are a primary diagnostic signal.

Production tuning should fix root causes before forcing planner behavior: stale or insufficient statistics, correlated predicates, inappropriate indexes, data skew, parameter-sensitive workloads, memory spill, or inaccurate hardware cost assumptions. Planner enable/disable settings are diagnostic tools, not preferred permanent tuning mechanisms.
