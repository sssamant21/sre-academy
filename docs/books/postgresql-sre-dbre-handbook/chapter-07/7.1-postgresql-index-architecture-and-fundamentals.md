# 7.1 — PostgreSQL Index Architecture and Fundamentals

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Establish the production mental model for PostgreSQL indexes: access methods, index tuples, planner selection, maintenance cost, and reliability tradeoffs.

## Canonical Guidance

PostgreSQL indexes accelerate selective access but add write, WAL, vacuum, cache, and storage overhead. Index design must therefore start from workload evidence rather than a rule that every predicate needs an index. B-tree is the default access method and serves equality, range, ordering, and many common lookup patterns. Other access methods exist because different data structures and operators require different search strategies.

```sql
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

SELECT schemaname, relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;
```

The planner may correctly choose a sequential scan even when a usable index exists. Selection depends on estimated rows, table/index size, correlation, caching assumptions, and planner costs. SRE/DBRE teams should evaluate execution plans and workload frequency before adding, removing, or rebuilding indexes.

## Production Review

- Measure read benefit against write and storage amplification.
- Validate index usage with plans and cumulative statistics.
- Keep statistics current; an index cannot compensate for fundamentally wrong cardinality estimates.
- Treat index creation and rebuilds as production changes with lock, I/O, WAL, replication, and free-space implications.
- Never delete PostgreSQL index files at the filesystem layer.

## Failure Scenario

A team adds indexes for every frequently filtered column. Reads improve initially, but write latency, WAL generation, vacuum work, storage use, and checkpoint pressure increase. Remediation is workload-driven consolidation and removal of genuinely redundant indexes after a safe observation period.

## SRE/DBRE Runbook

1. Identify the expensive query family.
2. Capture `EXPLAIN (ANALYZE, BUFFERS)` safely.
3. Validate selectivity and statistics.
4. Compare candidate index designs.
5. Estimate build I/O, WAL, lock, replication, and storage impact.
6. Deploy with an appropriate production-safe method.
7. Validate latency and resource impact after deployment.

## Production Rules

1. Indexes are workload structures, not free acceleration.
2. Planner choice is authoritative evidence; index existence is not proof of usefulness.
3. Optimize the complete read/write lifecycle.
4. Validate every significant index change before and after production deployment.
