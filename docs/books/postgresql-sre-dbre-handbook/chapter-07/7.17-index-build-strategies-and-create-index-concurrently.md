# 7.17 — Index Build Strategies and CREATE INDEX CONCURRENTLY

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Build production indexes while controlling lock, I/O, WAL, runtime, and failure risk.

## Canonical Guidance

A regular `CREATE INDEX` can block writes while the index is built. `CREATE INDEX CONCURRENTLY` reduces write blocking but performs more work, takes longer, has operational restrictions, and can leave an invalid index after failure.

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer
ON orders (customer_id);
```

## Preflight

Estimate relation size, free space, IOPS/throughput, WAL generation, replica lag tolerance, transaction duration, and maintenance window. Check for long-running transactions that can delay phases of a concurrent build.

## Failure Handling

If a concurrent build fails, inspect catalog state and error cause before retrying. An invalid index may require dropping/rebuilding according to the production runbook.

## Production Rules

1. `CONCURRENTLY` means lower write-lock impact, not zero operational impact.
2. Large builds are storage and replication events.
3. Define abort criteria and rollback before execution.
