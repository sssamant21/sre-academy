# 7.19 — Index Bloat, Fragmentation, and Storage Efficiency

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Diagnose index growth and inefficient space use without equating every large index with bloat.

## Canonical Guidance

Indexes grow with table growth, key width, included columns, churn, page occupancy, and dead entries. Some free space is useful for future writes. Bloat diagnosis therefore requires trend, workload, relation size, table churn, vacuum behavior, and performance evidence.

```sql
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC;
```

## Remediation Ladder

1. Confirm the index is needed.
2. Confirm growth is abnormal relative to workload.
3. Correct vacuum/churn/root causes where applicable.
4. Consider rebuild only when benefit justifies cost.
5. Validate post-change latency, size, WAL, and replication.

## Production Rules

1. Large is not synonymous with bloated.
2. Rebuilds treat symptoms unless growth causes are understood.
3. Index storage efficiency is part of capacity planning.
