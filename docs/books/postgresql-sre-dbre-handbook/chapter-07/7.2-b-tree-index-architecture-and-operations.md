# 7.2 — B-Tree Index Architecture and Operations

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Cover B-tree behavior as PostgreSQL's primary general-purpose index method.

## Architecture

B-tree indexes maintain ordered keys and support equality, range, `BETWEEN`, `IN`, null tests, many prefix-pattern cases, and ordered retrieval when operator classes permit. Their ordered structure makes them central to OLTP indexing.

```sql
CREATE INDEX idx_orders_created_at ON orders (created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE created_at >= now() - interval '1 day'
ORDER BY created_at;
```

## Design Guidance

High-selectivity predicates often benefit, but selectivity is not the only factor. Large result sets can make sequential access cheaper. Key width, update frequency, duplicate distribution, table correlation, and cache behavior affect cost.

## Operational Risks

B-tree indexes consume storage and generate maintenance work on INSERT/UPDATE/DELETE. Page splits, dead index tuples, changing data distribution, and workload churn can contribute to growth and degraded locality. Do not infer bloat from size alone.

## Monitoring

Use `pg_stat_user_indexes`, relation-size functions, query plans, latency, buffer behavior, and workload change history together. Compare index growth with table growth and write volume.

## Production Rules

1. B-tree is the default, not automatically the best method for every operator.
2. Leading key design should follow real predicate and ordering patterns.
3. Large index maintenance requires WAL, replication, storage, and I/O headroom.
4. Rebuild only when evidence supports it.
