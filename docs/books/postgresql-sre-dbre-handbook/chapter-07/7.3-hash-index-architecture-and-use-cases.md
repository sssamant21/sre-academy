# 7.3 — Hash Index Architecture and Use Cases

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Define where PostgreSQL hash indexes fit and where B-tree remains preferable.

## Canonical Guidance

Hash indexes store hash codes and support equality comparisons. They do not provide ordered traversal or range semantics. Use them only when an equality-focused workload demonstrates a practical advantage over alternatives.

```sql
CREATE INDEX idx_session_token_hash
ON sessions USING HASH (session_token);
```

## Production Review

Before selecting hash, compare B-tree behavior for the same workload. Consider index size, cache behavior, operator requirements, uniqueness requirements, operational familiarity, and future query evolution. A specialized access method should have a measurable reason to exist.

## Monitoring and Failure Modes

Track query latency, plan choice, `idx_scan`, write overhead, index size, and workload changes. A common design failure is adopting hash simply because the predicate uses equality while ignoring ordering, range, uniqueness, or mixed-query requirements.

## Production Rules

1. Hash is equality-specific.
2. Do not select an access method by name or intuition; benchmark the workload.
3. Preserve operational simplicity unless specialization provides measurable value.
