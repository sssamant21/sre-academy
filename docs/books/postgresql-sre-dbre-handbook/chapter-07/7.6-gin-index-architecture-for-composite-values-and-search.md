# 7.6 — GIN Index Architecture for Composite Values and Search

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Explain GIN inverted indexes for values containing multiple searchable components, including arrays, JSON-oriented workloads, and full-text search operator classes.

## Architecture

GIN stores entries for component values and is powerful for containment and membership-style predicates. The benefit can come with heavier write/build cost and larger maintenance requirements than simpler indexes.

```sql
CREATE INDEX idx_documents_tags_gin
ON documents USING GIN (tags);
```

## Production Review

Validate the operator class and actual predicates. Measure insert/update latency, pending-list behavior where relevant, index size, vacuum interaction, WAL, and query benefit. Bulk ingest and write-heavy systems require special attention.

## Failure Scenario

A broad GIN index accelerates JSON containment queries but materially increases ingest latency and storage. Remediation may include a narrower expression index, different operator class, workload separation, or removal of unused search paths.

## Production Rules

1. GIN is excellent for component membership/containment patterns, not universally for JSON or arrays.
2. Include write amplification in capacity planning.
3. Test bulk-load and steady-state behavior separately.
