# 7.7 — BRIN Index Architecture for Very Large Tables

**Status:** Complete — Revised Final / Canonical Edition

## Purpose

Use BRIN effectively on very large relations where indexed values correlate with physical row order.

## Architecture

BRIN summarizes value ranges for consecutive table blocks rather than indexing every row. This can make BRIN dramatically smaller than tuple-oriented indexes, but effectiveness depends heavily on physical correlation and predicate selectivity.

```sql
CREATE INDEX idx_events_created_brin
ON events USING BRIN (created_at);
```

## Design Guidance

Append-oriented time-series tables are common candidates. Evaluate `pg_stats.correlation`, table size, range selectivity, and the access pattern. BRIN may reduce blocks visited without behaving like a point-lookup B-tree.

## Operations

Monitor plan selection, blocks read, index size, table ordering drift, and query latency. Reassess after large out-of-order loads or major data reorganization.

## Production Rules

1. BRIN effectiveness depends on correlation with physical layout.
2. Small index size does not guarantee selective execution.
3. Benchmark against sequential and B-tree alternatives using production-scale data.
