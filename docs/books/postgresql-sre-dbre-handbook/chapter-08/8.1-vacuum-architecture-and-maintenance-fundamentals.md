# 8.1 — Vacuum Architecture and Maintenance Fundamentals

Status: **COMPLETE — CANONICAL**

## Purpose
PostgreSQL vacuuming is a core MVCC reliability mechanism. It makes storage from obsolete row versions reusable, maintains visibility information, participates in statistics maintenance, and protects the cluster from transaction-ID and multixact aging hazards.

## Architecture
Normal DML does not overwrite every old row version immediately. UPDATE and DELETE can leave obsolete tuple versions whose physical storage can become reusable only after they are no longer visible to any relevant transaction. VACUUM evaluates that lifecycle and performs the maintenance required for safe reuse and long-term transaction-ID operation.

## Production guidance
- Keep autovacuum enabled and prove its effectiveness with telemetry.
- Distinguish routine VACUUM from VACUUM FULL; the latter is a rewrite and should not be routine maintenance.
- Monitor dead-tuple accumulation, oldest transaction horizons, relation freeze age, vacuum frequency and duration, and I/O impact.
- Treat vacuum lag as a reliability signal, not merely a housekeeping issue.
- Never manually remove PostgreSQL relation files to reclaim space.

## SRE checks
Establish baselines for churn, cleanup throughput, vacuum duration, worker occupancy, table growth, freeze age, and storage runway. Investigate sustained divergence between tuple creation and cleanup rates.
