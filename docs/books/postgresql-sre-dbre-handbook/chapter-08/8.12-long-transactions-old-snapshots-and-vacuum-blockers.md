# 8.12 — Long Transactions, Old Snapshots, and Vacuum Blockers

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** VACUUM, Autovacuum, Bloat, and Maintenance  
**Baseline:** PostgreSQL 18  
**Status:** CANONICAL

## 8.12.1 Purpose

PostgreSQL uses MVCC to allow readers and writers to operate concurrently. As part of that design, PostgreSQL must retain older tuple versions while an active visibility horizon could still require them.

A critical production principle follows:

> **VACUUM can execute successfully while still being unable to reclaim every dead tuple that operators expect it to remove.**

Long-lived transactions, old snapshots, prepared transactions, replication-slot horizons, and—where applicable—standby feedback can prevent cleanup horizons from advancing. Operational consequences can include persistent dead-tuple retention, table and index growth, reduced vacuum effectiveness, increased storage consumption, degraded cache efficiency, longer maintenance operations, transaction-age pressure, and eventually increased XID wraparound risk.

This section establishes a production methodology for identifying these conditions and distinguishing them from ordinary autovacuum-capacity problems. Detailed XID wraparound mechanics remain in Section 8.10; detailed multixact mechanics remain in Section 8.11.

## 8.12.2 MVCC and the Cleanup Horizon

```text
Session A
BEGIN;
SELECT ...;

       |
       | snapshot established
       | transaction remains open
       v

-------------------------------------------------- time -->

Session B
UPDATE / DELETE;
COMMIT;

       |
       v

VACUUM
       |
       +---- finds obsolete tuple versions
       |
       +---- can PostgreSQL prove that no relevant
            visibility horizon still requires them?
                     |
                +----+----+
                |         |
               NO        YES
                |         |
             RETAIN     RECLAIM
```

From an application perspective, an old row version may appear obsolete immediately after an `UPDATE` or `DELETE`. From PostgreSQL's perspective:

```text
Application-obsolete != Immediately vacuum-removable
```

VACUUM must honor MVCC visibility requirements.

## 8.12.3 Long Query Is Not the Same as Long Transaction

Always distinguish query lifetime from transaction lifetime. A query can finish while its transaction remains open, including sessions reported as `idle in transaction`.

Operational investigations should examine `xact_start`, `query_start`, `state_change`, `state`, `backend_xid`, and `backend_xmin` rather than relying only on query duration.

An apparently inactive connection may represent a more important vacuum concern than a currently executing query.

## 8.12.4 First-Line Transaction Investigation

Begin with an observational query:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    state_change,
    clock_timestamp() - xact_start AS transaction_age,
    backend_xid,
    backend_xmin,
    wait_event_type,
    wait_event,
    LEFT(query, 200) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

This establishes the oldest transactions, application ownership, session state, transaction duration, XID/xmin information, and wait state. Do not terminate a backend simply because it appears at the top of this result. This is a discovery query, not a kill list.

## 8.12.5 Idle-in-Transaction Sessions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    xact_start,
    state_change,
    clock_timestamp() - xact_start AS transaction_age,
    clock_timestamp() - state_change AS idle_duration,
    backend_xid,
    backend_xmin,
    LEFT(query, 200) AS last_query
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
ORDER BY xact_start;
```

Typical causes include missing `COMMIT`/`ROLLBACK`, exception paths, connection-pool misuse, application stalls, interactive sessions, external calls inside a transaction, or unnecessarily broad transaction scope.

No query currently executing does not mean no transaction is open.

## 8.12.6 Investigating `backend_xmin`

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    backend_xid,
    backend_xmin,
    CASE WHEN backend_xmin IS NOT NULL THEN age(backend_xmin) END AS xmin_age,
    LEFT(query, 200) AS query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC NULLS LAST;
```

`backend_xmin` represents the backend's current xmin horizon when one is present. An unusually old value can contribute to retention of tuple versions and should be correlated with the affected workload before declaring it the blocker.

Correlate the affected relation, DML history, dead-tuple trend, vacuum activity, and transaction timing before assigning causality.

## 8.12.7 Transaction-ID Age

Wall-clock duration alone does not express transaction-age risk.

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    backend_xid,
    backend_xmin,
    CASE WHEN backend_xid IS NOT NULL THEN age(backend_xid) END AS xid_age,
    CASE WHEN backend_xmin IS NOT NULL THEN age(backend_xmin) END AS xmin_age,
    LEFT(query, 200) AS query
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL
   OR backend_xmin IS NOT NULL
ORDER BY GREATEST(
    COALESCE(age(backend_xid), 0),
    COALESCE(age(backend_xmin), 0)
) DESC;
```

Monitor wall-clock age, XID age, and xmin age together. A short-lived transaction on a very high-throughput system can span more XIDs than a much older transaction on a quiet system.

## 8.12.8 Prepared Transactions

```sql
SELECT
    transaction,
    gid,
    prepared,
    owner,
    database,
    age(transaction) AS xid_age
FROM pg_prepared_xacts
ORDER BY age(transaction) DESC;
```

An unexpectedly old prepared transaction is a serious operational signal. Never blindly execute `COMMIT PREPARED` or `ROLLBACK PREPARED`.

```text
Detect old prepared transaction
        ↓
Identify GID
        ↓
Identify owner/application
        ↓
Determine distributed transaction state
        ↓
Coordinate with transaction owner
        ↓
COMMIT PREPARED or ROLLBACK PREPARED
        ↓
Verify horizon advancement
```

## 8.12.9 Replication Slots

```sql
SELECT
    slot_name,
    slot_type,
    database,
    active,
    active_pid,
    inactive_since,
    xmin,
    catalog_xmin,
    restart_lsn,
    confirmed_flush_lsn,
    CASE WHEN xmin IS NOT NULL THEN age(xmin) END AS xmin_age,
    CASE WHEN catalog_xmin IS NOT NULL THEN age(catalog_xmin) END AS catalog_xmin_age
FROM pg_replication_slots
ORDER BY GREATEST(
    COALESCE(age(xmin), 0),
    COALESCE(age(catalog_xmin), 0)
) DESC;
```

Interpret these separately:

- `xmin` — tuple-retention visibility horizon.
- `catalog_xmin` — catalog tuple-retention horizon.
- `restart_lsn` — WAL-retention horizon, not a tuple-visibility horizon.
- `inactive_since` — evidence about how long a slot has been inactive.

Never drop a replication slot solely because it is old or inactive. Determine the consumer, whether it still exists, whether it is temporarily disconnected, and whether dropping the slot would require a rebuild or resynchronization.

## 8.12.10 Standby Queries and `hot_standby_feedback`

An important retention source can exist outside the primary.

```text
Long query on standby
        ↓
old standby snapshot
        ↓
hot standby feedback
        ↓
xmin communicated upstream
        ↓
primary retains tuple versions
        ↓
primary-table bloat can increase
```

Check:

```sql
SHOW hot_standby_feedback;
```

Tradeoff:

```text
hot_standby_feedback = off
  → primary can clean aggressively
  → standby queries may be canceled by recovery conflicts

hot_standby_feedback = on
  → fewer recovery-conflict cancellations
  → primary may retain dead tuples longer
```

Absence of a suspicious long transaction on the primary does not prove that no old visibility horizon exists. Replication topology may be involved.

## 8.12.11 Correlating Dead-Tuple Accumulation

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 30;
```

`n_dead_tup` is an estimate, not an exact physical tuple count. Prefer trends over a single snapshot. High `n_dead_tup` alone does not prove that autovacuum is broken.

## 8.12.12 Is VACUUM Running?

PostgreSQL 18 exposes standard VACUUM progress through `pg_stat_progress_vacuum`:

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    max_dead_tuple_bytes,
    dead_tuple_bytes,
    num_dead_item_ids
FROM pg_stat_progress_vacuum;
```

The PostgreSQL 18 column names above are intentional; `max_dead_item_ids` is not a PostgreSQL 18 column.

VACUUM executed does not mean every obsolete tuple was reclaimed, and dead tuples remaining does not mean autovacuum failed.

## 8.12.13 Capacity Problem vs. Visibility Problem

```text
Capacity problem:
Dead tuples generated faster than VACUUM processes them
→ VACUUM CAN remove tuples but cannot keep up.

Visibility problem:
VACUUM has sufficient capacity but an old visibility horizon exists
→ VACUUM MUST preserve certain tuple versions.
```

Do not tune workers, memory, or cost settings as the primary response to a visibility-horizon problem. More maintenance capacity does not remove an MVCC visibility requirement.

## 8.12.14 Repeated Manual VACUUM

Repeatedly running standard VACUUM does not resolve an old visibility horizon. If a snapshot or other retention horizon still requires tuple versions, PostgreSQL must continue preserving them. Resolve the horizon holder first, then verify that VACUUM cleanup recovers.

## 8.12.15 Do Not Jump to `VACUUM FULL`

Do not use `VACUUM FULL` as the first response to a cleanup-horizon incident. `VACUUM FULL` rewrites the relation and requires an `ACCESS EXCLUSIVE` lock. Standard VACUUM can coexist with normal DML and is the routine maintenance mechanism.

A visibility-horizon problem should first be solved by identifying and safely resolving the horizon holder. `VACUUM FULL` is also not the appropriate VACUUM operation for XID-exhaustion recovery.

## 8.12.16 Safe Session Remediation

```sql
SELECT pg_cancel_backend(<pid>);
SELECT pg_terminate_backend(<pid>);
```

`pg_cancel_backend()` cancels the current query while the session can survive. `pg_terminate_backend()` terminates the backend and causes an open transaction to roll back. An idle-in-transaction session may require termination because no active query exists to cancel.

Production workflow:

```text
Identify PID
    ↓
Identify user/application
    ↓
Confirm transaction age and XID/xmin significance
    ↓
Determine rollback impact
    ↓
Coordinate with owner
    ↓
Terminate only if justified
    ↓
Verify rollback and horizon movement
    ↓
Verify VACUUM recovery
```

## 8.12.17 Operational Risk Classification

```text
SAFE / OBSERVATIONAL
pg_stat_activity
pg_stat_user_tables
pg_stat_progress_vacuum
pg_prepared_xacts
pg_replication_slots
SHOW hot_standby_feedback

CONTROLLED
pg_cancel_backend()

DISRUPTIVE
pg_terminate_backend()

HIGH-RISK / STATE-CHANGING
COMMIT PREPARED
ROLLBACK PREPARED
DROP replication slot
VACUUM FULL
```

Never present the last group as automatic remediation.

## 8.12.18 Prevention

`idle_in_transaction_session_timeout` can terminate sessions that remain idle inside an open transaction. A production policy may use a conservative global default with role- or application-specific settings.

Applications should keep transaction scope small, commit promptly, roll back on exceptions, avoid external calls or user interaction inside transactions, and return pooled connections in a clean transaction state.

`statement_timeout` limits statement execution time; it does not by itself bound the lifetime of a transaction after the statement completes.

## 8.12.19 Routine Cleanup Incident vs. XID Emergency

Do not treat every long transaction or old `backend_xmin` as an XID-wraparound emergency. Long-lived horizons can cause bloat and reduced vacuum effectiveness well before the cluster reaches wraparound danger.

Escalation to the XID emergency procedure must be based on transaction-age and runway measurements described in Section 8.10.

## 8.12.20 Relationship to Multixact

Do not apply the XID blocker model blindly to multixact. Running transactions matter to multixact cleanup only when they could participate in relevant multixacts, and replication slots do not directly hold back MXID cleanup in the same way. Detailed MXID mechanics and protection belong to Section 8.11.

## 8.12.21 PostgreSQL 18 Observability

PostgreSQL 18 table statistics provide cumulative maintenance timing information including `total_vacuum_time`, `total_autovacuum_time`, `total_analyze_time`, and `total_autoanalyze_time`. Use these for trend analysis together with transaction horizons, dead-tuple estimates, vacuum frequency, and progress information.

## 8.12.23 Production Runbook

1. Identify old transactions and their owners.
2. Inspect old `backend_xid` and `backend_xmin` horizons.
3. Check `idle in transaction` and `idle in transaction (aborted)` sessions.
4. Check old prepared transactions.
5. Check replication-slot `xmin`, `catalog_xmin`, `inactive_since`, and WAL-retention state.
6. Check `hot_standby_feedback` and standby workload where relevant.
7. Correlate affected tables using `pg_stat_user_tables`; treat `n_dead_tup` as an estimate.
8. Check active VACUUM operations through `pg_stat_progress_vacuum`.
9. Classify the problem as a visibility constraint, maintenance-capacity problem, or both.
10. Validate application/replication ownership before any disruptive action.
11. Remediate the confirmed horizon holder safely.
12. Verify horizon advancement, VACUUM recovery, dead-tuple trajectory, transaction-age trajectory, and storage/performance stabilization.

Do not declare recovery merely because an offending PID disappeared.

## 8.12.24 Managed PostgreSQL and Kubernetes

The same PostgreSQL-level diagnostic model applies to self-managed PostgreSQL, Kubernetes PostgreSQL, Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL-Compatible, Azure Database for PostgreSQL, and Google Cloud SQL for PostgreSQL.

Use PostgreSQL catalog evidence to identify the blocker, but validate platform-specific privileges and replication ownership before terminating sessions, changing parameters, or modifying replication slots. Provider-specific remediation belongs in the corresponding platform runbooks.

## 8.12.25 Operational Anti-Patterns

Avoid:

- Killing every long-running query.
- Equating query age with transaction age.
- Treating every old transaction as an XID emergency.
- Assuming high `n_dead_tup` proves autovacuum failure.
- Treating `n_dead_tup` as an exact physical tuple count.
- Repeated VACUUM runs without horizon checks.
- Using `VACUUM FULL` as the first response.
- Dropping replication slots based only on age or inactivity.
- Ignoring standby feedback.
- Resolving prepared transactions without ownership validation.
- Increasing autovacuum capacity before identifying visibility constraints.
- Treating XID and MXID blockers identically.
- Waiting for wraparound warnings before monitoring transaction age.

## 8.12.26 Production Checklist

### Detection

- [ ] Check oldest transactions.
- [ ] Check `backend_xid` age.
- [ ] Check `backend_xmin` age.
- [ ] Check idle-in-transaction sessions.
- [ ] Check prepared transactions.
- [ ] Check replication-slot horizons and inactivity.
- [ ] Check `hot_standby_feedback` where applicable.
- [ ] Check estimated dead-tuple trends.
- [ ] Check VACUUM activity and progress.
- [ ] Check XID/MXID age where applicable.

### Diagnosis

- [ ] Identify application/service owner.
- [ ] Distinguish query age from transaction age.
- [ ] Determine which cleanup horizon is old.
- [ ] Correlate the horizon with affected relations.
- [ ] Distinguish visibility constraint from capacity problem.
- [ ] Determine XID vs. MXID vs. routine cleanup incident.
- [ ] Assess rollback/termination impact.
- [ ] Validate replication dependencies.

### Remediation

- [ ] Coordinate with the application/service owner.
- [ ] End unnecessary transactions safely.
- [ ] Resolve prepared transactions correctly.
- [ ] Resolve stale slots only after consumer validation.
- [ ] Address standby feedback/query behavior where relevant.
- [ ] Allow or execute appropriate standard VACUUM.
- [ ] Verify horizon advancement and maintenance recovery.

### Prevention

- [ ] Define transaction-duration SLOs.
- [ ] Alert on idle-in-transaction sessions.
- [ ] Monitor oldest `backend_xmin` and `backend_xid`.
- [ ] Monitor prepared-transaction age.
- [ ] Monitor replication-slot horizons.
- [ ] Monitor dead-tuple trends and VACUUM runtime.
- [ ] Configure appropriate transaction timeouts.
- [ ] Fix application transaction boundaries.
- [ ] Document legitimate long-running transaction exceptions.

## 8.12.27 Key Takeaway

> **VACUUM cannot reclaim tuple versions that PostgreSQL must still preserve for an existing visibility horizon.**

When dead tuples accumulate despite active vacuuming, the key production question is:

> **Can VACUUM safely reclaim the tuple versions we expect it to reclaim, and if not, which transaction, snapshot, prepared transaction, replication slot, or standby-derived horizon is preventing cleanup from advancing?**

This distinction separates a maintenance-capacity problem from an MVCC cleanup-horizon problem and prevents inappropriate responses such as repeatedly increasing autovacuum capacity, killing unrelated queries, dropping replication slots, or running `VACUUM FULL`.
