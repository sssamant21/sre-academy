# 8.14 — Heap Bloat Architecture, Detection, and Interpretation

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** VACUUM, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **COMPLETE — CANONICAL**

## 8.14.1 Purpose

PostgreSQL heap bloat is often described simply as unused space inside a table. That definition is insufficient for production operations.

A PostgreSQL heap naturally contains live tuples, dead tuple versions, reusable free space, page and tuple metadata, alignment overhead, and intentionally reserved free space.

A large relation is therefore not automatically bloated, and a relation containing many dead tuples is not automatically suffering from persistent heap bloat.

The production question is:

> **Does the relation contain materially more allocated heap capacity than its sustainable workload requires, is that excess capacity unlikely to be reused, and is it creating enough operational cost to justify remediation?**

The diagnostic lifecycle is:

```text
MVCC churn
    |
    v
dead tuple versions
    |
    v
VACUUM cleanup
    |
    v
internally reusable capacity
    |
    +--> reused by workload
    |        |
    |        v
    |   healthy working capacity
    |
    +--> persistently unused
             |
             v
     possible heap bloat
             |
             v
      operational impact
             |
             v
     remediation decision
```

Dead tuples, reusable free space, and persistent heap bloat are related conditions, but they are not equivalent.

## 8.14.2 MVCC and Heap Growth

PostgreSQL uses MVCC to allow concurrent readers and writers. An `UPDATE` generally creates a new tuple version. A `DELETE` makes an existing version obsolete rather than immediately removing its physical storage.

An old version cannot be reclaimed while an active visibility horizon might still require it. After the tuple becomes removable, VACUUM can reclaim its storage for internal reuse.

This behavior is normal PostgreSQL architecture.

## 8.14.3 Heap Page Architecture

PostgreSQL stores heap relations in fixed-size pages. A standard PostgreSQL build normally uses 8 KiB pages, although block size is configurable at build time.

Physical footprint includes page headers, item identifiers, tuple headers, alignment, tuple data, and reusable free space. Consequently, relation size must not be interpreted as application payload size without understanding PostgreSQL storage layout.

## 8.14.4 Dead Tuples Are Not Heap Bloat

A table with many dead tuples has cleanup work. It does not automatically have persistent heap bloat. If VACUUM removes the dead tuple versions and subsequent inserts or updates reuse the released capacity, the relation may be operating at a healthy steady-state footprint.

```text
dead tuples != heap bloat
```

Dead tuples primarily describe MVCC churn and cleanup demand. Heap bloat is an interpretation of physical allocation relative to sustainable workload requirements.

## 8.14.5 Reusable Capacity Is Not Automatically Waste

After standard VACUUM, dead tuple storage becomes internally reusable capacity while the pages normally remain allocated to the relation.

For a high-churn table, this may be desirable. If the workload repeatedly consumes and releases the same working capacity, physically shrinking the relation can simply cause PostgreSQL to extend it again.

The correct question is whether free capacity is part of the normal working envelope or persistent capacity that the workload is unlikely to reuse.

## 8.14.6 Standard VACUUM and Physical Size

Standard VACUUM can reclaim removable dead tuple versions, make heap space reusable, perform appropriate index cleanup, update visibility and freeze information, and update maintenance state. It generally does not compact the entire relation.

Therefore, an unchanged relation size after a successful VACUUM does not mean VACUUM failed.

## 8.14.7 Tail Truncation

Standard VACUUM can sometimes return physical storage to the operating system when completely empty pages exist at the end of a relation. PostgreSQL normally permits this behavior through `vacuum_truncate = true`.

Tail truncation can require an `ACCESS EXCLUSIVE` lock. PostgreSQL exposes a `truncating heap` phase through `pg_stat_progress_vacuum` when VACUUM is performing this work.

Tail truncation is not equivalent to full-table compaction.

## 8.14.8 Why Interior Free Space Remains

VACUUM can make dead storage inside heap pages reusable, but it cannot simply remove pages from the physical middle of a relation without relocating tuples.

A table can therefore have low dead-tuple count, substantial reusable free space, and a large physical footprint after successful VACUUM. Physical compaction requires a different class of operation.

## 8.14.9 Heap Bloat Is Often Historical

Heap bloat commonly reflects workload history: a table grows, UPDATE or DELETE activity creates old versions, VACUUM later reclaims those versions, reusable space remains, and the physical relation stays large.

If future workload reuses the capacity, the footprint may be appropriate. If it remains persistently unused, historical heap bloat becomes more plausible.

## 8.14.10 Common Causes

Persistent excess heap allocation can result from sustained update churn, large delete operations, old transactions or snapshots, prepared transactions, retained replication horizons, standby feedback, insufficient autovacuum capacity, storage limitations that slow VACUUM, poor reuse characteristics, historical workload peaks, or permanent data-retention reductions.

Diagnosis must precede reclamation.

## 8.14.11 Fillfactor Is Not Bloat

A table can deliberately reserve page capacity through `fillfactor`. For update-heavy relations, this can improve the probability of HOT updates.

```text
intentional free capacity != accidental bloat
```

A bloat assessment must include the relation's configured fillfactor.

## 8.14.12 HOT and Heap Storage

Heap-Only Tuple updates can reduce update amplification when sufficient free space exists on the same heap page and index conditions permit HOT. HOT does not eliminate heap tuple versions; it reduces some index and cleanup amplification associated with updates.

## 8.14.13 PostgreSQL 18 HOT Nuance

Ordinary indexes referencing a modified column can prevent a qualifying update from using HOT. PostgreSQL 18 has an important nuance for summarizing indexes such as BRIN: because they summarize page ranges rather than containing conventional tuple references in the same manner, changes to BRIN-indexed columns do not necessarily prevent HOT.

HOT analysis should therefore consider index type rather than relying only on whether an updated column participates in any index.

## 8.14.14 First-Level Screening: Physical Size

Start with actual physical footprint:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(c.oid)) AS index_size,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 50;
```

This identifies large relations. It does not prove bloat.

## 8.14.15 Dead-Tuple Screening

Inspect cumulative statistics:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 50;
```

`n_live_tup` and `n_dead_tup` are estimates. They are useful screening and trend signals, not byte-exact measurements.

## 8.14.16 Ratios Require Context

A dead-tuple ratio can help prioritize investigation, but it should not drive remediation. Production prioritization should consider absolute bytes, relation size, dead tuple volume, growth rate, maintenance cost, and workload impact.

## 8.14.17 Catalog Estimates

Useful screening signals include `pg_class.relpages`, `pg_class.reltuples`, `pg_stat_user_tables.n_live_tup`, and `pg_stat_user_tables.n_dead_tup`.

`relpages` and `reltuples` are planner-maintained estimates and can become stale between maintenance or other operations that refresh them. Do not treat them as byte-exact measurements. For current physical relation size, use functions such as `pg_relation_size()` and `pg_total_relation_size()`.

## 8.14.18 Evidence Hierarchy

Use increasingly expensive evidence only when necessary:

```text
relation size
      |
      v
catalog/statistics screening
      |
      v
time-series growth analysis
      |
      v
cleanup/blocker analysis
      |
      v
pgstattuple_approx
      |
      v
pgstattuple when justified
      |
      v
workload + fillfactor + reuse analysis
      |
      v
bloat classification
```

A full physical scan should not be the first diagnostic action on a multi-terabyte production table.

## 8.14.19 `pgstattuple`

Where the `pgstattuple` extension is installed and the caller has appropriate privileges:

```sql
SELECT *
FROM pgstattuple('public.orders'::regclass);
```

The function reports physical composition including `table_len`, tuple counts and lengths, dead-tuple counts and lengths, and free-space metrics.

`pgstattuple()` performs a full relation scan. On very large production relations this can create meaningful storage I/O. Before running it, evaluate current business workload, storage latency, IOPS, throughput, queue depth, relation size, and diagnostic necessity.

Treat it as a controlled production diagnostic.

## 8.14.20 `pgstattuple_approx`

For large relations, consider:

```sql
SELECT *
FROM pgstattuple_approx('public.orders'::regclass);
```

Conceptually:

```text
pgstattuple
    |
    +--> full relation scan
    +--> exact physical inspection

pgstattuple_approx
    |
    +--> avoids scanning eligible pages
    +--> exact dead-tuple information
    +--> approximate live-tuple information
    +--> approximate free-space information
```

`pgstattuple_approx()` can provide lower-cost evidence before deciding whether a complete physical scan is justified.

## 8.14.21 `free_percent` Is Not Bloat Percentage

Do not translate `free_percent` directly into an authoritative bloat percentage. Some free capacity may be intentionally reserved by fillfactor, actively reused, useful for HOT updates, or normal workload headroom.

Prefer terminology such as `potentially reclaimable heap capacity` or `estimated excess heap allocation` until workload analysis establishes that the capacity is genuinely unnecessary.

## 8.14.22 Time-Series Evidence

One snapshot is weaker than a trend. Track heap size, total relation size, live tuples, dead tuples, insert/update/delete rates, HOT update rate, VACUUM frequency, autovacuum frequency, and physical free-space estimates over time.

If physical allocation continues growing while durable logical data remains comparatively stable, persistent excess allocation becomes increasingly plausible.

## 8.14.23 Growth Versus Bloat

The governing question is:

> **Did physical growth correspond to durable logical growth?**

Physical growth that tracks durable data growth may be legitimate. Physical growth that significantly outpaces logical growth under heavy churn deserves investigation.

## 8.14.24 Large DELETE Operations

A large `DELETE` followed by standard VACUUM can leave the table near its previous physical size because the released storage becomes internally reusable.

Before considering reclamation, determine whether future workload is likely to reuse the capacity.

If an application periodically removes the entire contents of a table, `TRUNCATE` may be architecturally more appropriate than deleting every row individually, subject to its locking, transactional, foreign-key, and application semantics. This is a narrow use case, not a generic replacement for `DELETE`.

## 8.14.25 Operational Cost of Heap Bloat

Persistent excess heap allocation can increase storage consumption, sequential-scan work, cache pressure, backup footprint, restore footprint, maintenance duration, storage I/O, and infrastructure cost.

A large relation does not automatically imply a performance problem. The operational impact must be measured.

## 8.14.26 Capacity Analysis

Capacity planning should consider current allocated heap, expected logical growth, expected churn, reusable internal capacity, index footprint, TOAST footprint, rewrite working capacity, and required safety headroom.

Rewrite-style operations can temporarily require substantial additional storage for replacement relation data and associated structures. Storage headroom must be explicitly validated before remediation.

## 8.14.27 Heap, Index, and TOAST Are Separate

A logical PostgreSQL table can consume storage through heap, indexes, and TOAST. A large `pg_total_relation_size()` does not reveal which component dominates.

Inspect separately:

```sql
SELECT
    pg_size_pretty(pg_relation_size('public.orders')) AS heap_size,
    pg_size_pretty(pg_indexes_size('public.orders')) AS index_size,
    pg_size_pretty(pg_total_relation_size('public.orders')) AS total_size;
```

Index bloat is addressed in Section 8.15. Do not recommend heap remediation when the primary excess footprint is actually index storage.

## 8.14.28 Autovacuum Can Be Healthy While Historical Bloat Exists

Autovacuum is not designed to keep every table at its minimum possible physical size. Autovacuum can therefore be functioning correctly while persistent historical heap bloat still exists.

## 8.14.29 Autovacuum Failure Can Create Historical Bloat

If maintenance cannot keep pace with churn, dead tuples can accumulate, the heap can expand, and later VACUUM can reclaim dead tuples while the physical footprint remains.

Rewriting the relation without correcting the maintenance problem can simply cause the heap to expand again.

Fix the cause before treating the physical symptom.

## 8.14.30 Check Cleanup Horizons Before Blaming Autovacuum

VACUUM can run while retained visibility horizons prevent expected cleanup. Before increasing autovacuum aggressiveness, investigate long-running transactions, old snapshots, prepared transactions, replication-slot `xmin`, `catalog_xmin`, and `hot_standby_feedback` where relevant.

Sections 8.12 and 8.13 cover these mechanisms in detail.

## 8.14.31 Fillfactor Investigation

Inspect relation options:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.reloptions
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.oid = 'public.orders'::regclass;
```

A reduced fillfactor can deliberately create free capacity. Do not classify this capacity as waste without evaluating the relation's update pattern and HOT behavior.

## 8.14.32 HOT Effectiveness

Inspect update statistics:

```sql
SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    CASE
        WHEN n_tup_upd > 0
        THEN round(100.0 * n_tup_hot_upd / n_tup_upd, 2)
        ELSE 0
    END AS hot_update_pct
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';
```

A low HOT ratio on a high-update relation can justify investigation into indexed-column changes, index types, page-local free capacity, fillfactor, and tuple width. It does not by itself prove heap bloat.

## 8.14.33 Production Classification

### Class A — Healthy Churn

Dead tuples fluctuate, VACUUM keeps pace, capacity is reused, and physical growth tracks workload.

**Action:** Monitor.

### Class B — Cleanup Backlog

Dead tuples rise, VACUUM is insufficient or blocked, and the heap expands.

**Action:** Correct cleanup throughput or blocker conditions first.

### Class C — Persistent Historical Heap Bloat

Dead tuples are controlled, persistent free capacity is large, logical workload is stable or reduced, physical footprint remains excessive, and capacity is unlikely to be reused.

**Action:** Quantify operational benefit and evaluate controlled reclamation.

### Class D — Intentional Working Capacity

Free capacity is significant, update churn is high, capacity is reused, HOT/reuse benefits exist, and physical size is stable.

**Action:** Usually retain the capacity.

A valid production conclusion can therefore be:

```text
No remediation recommended.
Observed internal free capacity is consistent with the relation's
high-churn workload and is being reused.
```

## 8.14.35 Do Not Rewrite from One Metric

Avoid rules such as `dead tuples > 20% => VACUUM FULL`, `free space > 30% => rewrite`, or `table > 500 GB => bloated`.

These rules ignore absolute bytes, workload churn, future growth, fillfactor, HOT behavior, cleanup health, retained horizons, locking, storage capacity, and operational benefit.

There is no universal production heap-bloat percentage.

## 8.14.36 When Physical Reclamation May Merit Evaluation

Physical reclamation becomes more reasonable when material excess allocation exists, the logical working set has permanently reduced, capacity is unlikely to be reused, operational cost is meaningful, the underlying cause is corrected, rewrite risk is acceptable, and storage headroom is sufficient.

Potential examples include permanent archival, retention-policy reduction, one-time bulk deletion, historical workload contraction, or exceptional growth caused by a maintenance failure that has since been corrected.

The execution mechanisms belong in Section 8.16.

## 8.14.37 Rewrite-Class Operations

Physical compaction can involve operations such as `VACUUM FULL`, `CLUSTER`, or table-rewriting forms of `ALTER TABLE`.

These operations can require `ACCESS EXCLUSIVE` locking, substantial I/O, additional temporary disk capacity, WAL generation, replication traffic, and maintenance windows.

Section 8.14 does not prescribe these operations. Its responsibility is to establish whether persistent heap bloat actually exists and whether physical reclamation merits evaluation. Section 8.16 covers controlled reclamation strategy.

## 8.14.38 When Not to Shrink

Avoid physical reclamation merely because reusable capacity exists when the workload is expected to regrow, update churn will reuse the capacity, storage headroom is healthy, rewrite risk exceeds benefit, diagnosis relies only on estimates, intentional fillfactor explains the capacity, or underlying cleanup problems remain unresolved.

Shrinking a relation that immediately grows again creates unnecessary I/O, WAL, locking, replication traffic, backup churn, and operational risk without durable benefit.

## 8.14.39 Production Investigation Workflow

1. Establish physical footprint: heap, indexes, TOAST, and total.
2. Establish logical workload: live tuples and insert/update/delete/HOT rates.
3. Establish cleanup health: dead tuples, VACUUM history, autovacuum history, maintenance frequency, and active progress.
4. Check cleanup blockers using Sections 8.12 and 8.13.
5. Inspect fillfactor, autovacuum overrides, and vacuum settings.
6. Compare physical size, logical data, dead tuples, and workload churn over time.
7. Use `pgstattuple_approx` when justified and escalate to `pgstattuple` only when stronger evidence is necessary and production I/O impact is acceptable.
8. Quantify operational cost across storage, I/O, cache, backup/restore, maintenance, and query impact.
9. Report potentially reclaimable capacity in bytes as well as percentages.
10. Classify as healthy churn, cleanup backlog, persistent historical heap bloat, or intentional working capacity.
11. Correct the cause before reclamation.
12. Evaluate physical reclamation separately.

## 8.14.40 Production Finding Format

A production finding should include relation identity, current heap and total size, logical-data trend, live/dead tuple estimates, physical free-space evidence, fillfactor, workload churn, HOT behavior, VACUUM history, cleanup blockers, estimated reclaimable bytes, operational impact, verified cause, and recommendation.

Recommendations should be one of: monitor, correct maintenance cause, retain reusable capacity, or evaluate controlled reclamation under Section 8.16.

## 8.14.41 Example: Persistent Historical Bloat

A 2 TB heap with stable logical row count, low dead-tuple count, high persistent free capacity, `fillfactor = 100`, a recent permanent deletion of approximately 800 GB, unlikely regrowth, and critical storage utilization is a strong candidate for persistent historical heap bloat.

Physical reclamation may merit evaluation.

## 8.14.42 Example: Useful Working Capacity

A 2 TB heap with stable logical row count, controlled dead tuples, significant free capacity, `fillfactor = 75`, very high update churn, strong HOT effectiveness, continuous capacity reuse, and healthy storage utilization can reasonably be classified as useful working capacity.

No reclamation may be warranted.

## 8.14.43 Production Principles

1. Dead tuples are not synonymous with heap bloat.
2. Reusable free capacity is not automatically wasted capacity.
3. Standard VACUUM normally makes space reusable rather than physically compacting the table.
4. An unchanged relation size does not mean VACUUM failed.
5. Tail truncation is different from full-table compaction.
6. Heap bloat often represents historical workload conditions.
7. Physical size alone cannot prove bloat.
8. Dead-tuple percentage alone cannot prove bloat.
9. `free_percent` is not an authoritative bloat percentage.
10. Catalog statistics are screening evidence, not exact physical measurements.
11. `n_live_tup`, `n_dead_tup`, `relpages`, and `reltuples` are estimates.
12. Use actual size functions for physical-size reporting.
13. Use `pgstattuple_approx` before a full physical scan when appropriate.
14. Treat `pgstattuple` as a controlled diagnostic on large production relations.
15. Time-series evidence is stronger than one snapshot.
16. Separate legitimate logical growth from physical amplification.
17. Fillfactor-created capacity can be intentional.
18. HOT can reduce update amplification but does not eliminate heap versions.
19. Consider index type when interpreting HOT eligibility.
20. Separate heap, index, and TOAST storage before selecting remediation.
21. Investigate cleanup blockers before blaming autovacuum throughput.
22. Correct the maintenance cause before physically shrinking the table.
23. Do not automate rewrites from a bloat percentage.
24. Report potentially reclaimable capacity in bytes as well as percentages.
25. Validate rewrite storage headroom before recommending reclamation.
26. A valid investigation can conclude that no remediation is required.
27. Do not optimize PostgreSQL for the smallest theoretical table size.
28. Optimize for sustainable, reusable, observable storage efficiency.

## 8.14.45 Key Takeaway

The central SRE/DBRE rule is:

> **Do not remediate heap bloat from a percentage alone. Establish that excess allocated capacity is persistent, unlikely to be reused, operationally significant, and caused by a condition that has either been corrected or will not immediately recreate the bloat.**

The objective is not the smallest possible PostgreSQL table. The objective is a stable, reusable, observable, sustainable, and operationally efficient heap footprint.
