# 8.15 — Index Bloat, Dead Index Tuples, and Index Cleanup

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** VACUUM, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **COMPLETE — CANONICAL**

## 8.15.1 Purpose

PostgreSQL index bloat is frequently diagnosed too simplistically.

A large index is not automatically bloated.

An index containing obsolete tuple references is not automatically suffering from persistent bloat.

An index that does not shrink after VACUUM is not necessarily unhealthy.

The production question is:

> **Does the index contain persistent physical inefficiency relative to its durable key set and workload, and is that inefficiency creating enough storage, maintenance, or query cost to justify structural remediation?**

The operating model is:

```text
DML workload
     |
     v
index tuple churn
     |
     v
obsolete index versions
     |
     +--> B-tree opportunistic cleanup
     +--> VACUUM index cleanup
     +--> space reuse
     |
     v
physical index state
     |
     +--> efficient / reusable
     |        |
     |        v
     |      healthy
     |
     +--> persistently inefficient
              |
              v
       operational impact
              |
              v
       remediation decision
```

Index tuple churn, dead index entries, reusable index capacity, and persistent index bloat are related conditions, but they are not equivalent.

---

## 8.15.2 Heap and Index Maintenance Are Related but Different

A heap tuple can be referenced by multiple indexes.

```text
heap tuple
    |
    +--> index A
    +--> index B
    +--> index C
```

MVCC updates create new heap tuple versions.

When an update cannot use HOT and requires new index entries, the update can create successor physical tuples across the table's indexes.

A heavily indexed, update-intensive table can therefore create substantial index churn even when its logical row count remains stable.

---

## 8.15.3 HOT Is a Major Index-Churn Boundary

```text
UPDATE
   |
   v
HOT eligible?
 /          \
yes          no
 |            |
 v            v
new heap    new heap version
version       +
without       successor index
new index     tuples as required
tuples            |
 |                v
 v          greater index churn
lower
index churn
```

Successful HOT updates avoid creating new index tuples for that update.

Consequently, two tables with similar UPDATE rates can generate very different index-maintenance pressure depending on indexed columns, index types, fillfactor, page-local free space, tuple width, and HOT eligibility.

Low HOT effectiveness is therefore an important diagnostic signal for index growth, but it is not itself proof of index bloat.

---

## 8.15.4 Dead Heap Tuples and Index Entries

When a heap tuple version becomes globally removable, associated index entries can eventually be removed.

PostgreSQL must preserve safe ordering between index cleanup and heap TID reuse.

```text
heap version becomes removable
          |
          v
associated index references
must become safe to remove
          |
          v
index cleanup
          |
          v
heap storage/TID can safely
participate in later reuse
```

Index cleanup is therefore part of PostgreSQL's MVCC correctness and maintenance model, not merely cosmetic storage cleanup.

---

## 8.15.5 Standard VACUUM and Index Cleanup

Standard VACUUM can process table indexes as part of dead-tuple cleanup.

```text
heap scan
   |
identify removable tuples
   |
   v
index cleanup
   |
   v
heap cleanup
```

VACUUM does not normally rebuild the entire index.

Instead, routine maintenance removes obsolete index entries where appropriate and allows existing index structures to reuse available capacity.

```text
VACUUM index cleanup
!=
REINDEX
```

VACUUM is routine cleanup. REINDEX is structural reconstruction.

---

## 8.15.6 `INDEX_CLEANUP AUTO`

The normal PostgreSQL behavior is:

```sql
VACUUM (INDEX_CLEANUP AUTO) public.orders;
```

`AUTO` is the default.

When very few dead tuples exist, PostgreSQL can decide that processing every index would cost more than the expected cleanup benefit.

Therefore VACUUM can complete successfully even when some index cleanup is skipped.

---

## 8.15.7 `INDEX_CLEANUP ON`

Operators can request:

```sql
VACUUM (INDEX_CLEANUP ON) public.orders;
```

`ON` tells VACUUM to perform index cleanup when dead tuples exist rather than allowing `AUTO` to skip it based on its normal optimization.

This should not be interpreted as a universally stronger or better VACUUM.

For relations with many large indexes, forced index processing can increase I/O, maintenance duration, CPU use, and storage queueing.

`AUTO` should remain the normal production setting unless evidence justifies an override.

---

## 8.15.8 `INDEX_CLEANUP OFF`

PostgreSQL also supports:

```sql
VACUUM (INDEX_CLEANUP OFF) public.orders;
```

This skips index cleanup.

It can be useful in exceptional circumstances where completing urgent heap maintenance is more important than routine index cleanup.

Repeated use can allow obsolete index entries and inefficient allocation to persist.

```text
VACUUM taking too long
        |
        v
INDEX_CLEANUP OFF everywhere
```

is not an acceptable general tuning strategy.

---

## 8.15.9 Vacuum Failsafe and Index Cleanup

When transaction-ID or multixact safety becomes urgent, PostgreSQL's VACUUM failsafe can bypass nonessential maintenance work, including index cleanup, so anti-wraparound work can complete faster.

Operators should not imitate failsafe behavior as routine performance tuning.

---

## 8.15.10 B-tree Bottom-Up Deletion

PostgreSQL B-tree indexes include bottom-up index deletion.

It targets obsolete index versions generated by UPDATE version churn.

```text
UPDATE workload
      |
      v
successor physical versions
      |
      v
obsolete B-tree tuples accumulate
      |
      v
version-churn page split anticipated
      |
      v
bottom-up deletion
      |
      v
obsolete tuples removed
      |
      v
page split may be avoided
```

This mechanism is particularly important when an index was not logically modified by the UPDATE but still accumulated physical tuple versions because the table update required successor index tuples.

---

## 8.15.11 Bottom-Up Deletion Does Not Replace VACUUM

Bottom-up deletion is targeted and opportunistic.

It does not provide the same whole-relation maintenance guarantees as VACUUM.

PostgreSQL still requires VACUUM to perform broader cleanup and maintain the safety relationship between heap tuple reuse and obsolete index references.

---

## 8.15.12 Simple B-tree Deletion

B-tree indexes can also perform opportunistic simple deletion of entries already marked `LP_DEAD`.

```text
index scan
    |
identifies dead entry
    |
marks LP_DEAD
    |
later page pressure
    |
simple deletion
    |
space reused
```

This differs from bottom-up deletion. Simple deletion depends on prior scans identifying dead entries. Bottom-up deletion specifically targets version-churn tuples when PostgreSQL anticipates page pressure.

---

## 8.15.13 B-tree Deduplication

B-tree indexes can deduplicate groups of tuples with identical key values.

```text
key A -> TID1
key A -> TID2
key A -> TID3
key A -> TID4
```

can conceptually become:

```text
key A -> [TID1, TID2, TID3, TID4]
```

Where applicable, deduplication can reduce physical index size, page-split pressure, cache consumption, and index VACUUM overhead.

Deduplication is normally enabled where PostgreSQL determines that it is safe.

---

## 8.15.14 Deduplication Is Definition-Dependent

Deduplication is not available for every B-tree index.

Eligibility depends on factors including index definition, datatype, collation, and operator-class semantics.

Indexes containing `INCLUDE` columns cannot use B-tree deduplication. Certain datatypes and collation semantics also prevent deduplication.

Therefore similar logical key definitions do not guarantee similar physical index size.

---

## 8.15.15 Unique Indexes and Deduplication

Deduplication is not limited conceptually to ordinary nonunique workloads.

PostgreSQL can use deduplication in some unique-index situations to absorb temporary physical version churn while preserving uniqueness semantics.

Operators should therefore avoid assuming that UNIQUE automatically implies no deduplication behavior without checking PostgreSQL's access-method rules for the deployed version.

---

## 8.15.16 B-tree Page Splits

When a B-tree leaf page cannot accommodate a new tuple, PostgreSQL can split it.

```text
full leaf page
      |
      v
page split
    /    \
page A  page B
```

Splits can propagate upward, and a root split can increase tree height.

Page splits are normal B-tree behavior. The concern is sustained churn, poor space reuse, and persistent physical growth.

---

## 8.15.17 Empty Versus Sparse Pages

Completely empty B-tree pages can become reusable.

A more difficult pattern is:

```text
Page 1: 5% occupied
Page 2: 8% occupied
Page 3: 4% occupied
Page 4: 7% occupied
```

These pages are not empty. They can remain allocated even though physical occupancy is poor.

This is one documented pattern where a B-tree can remain materially larger than its durable key set requires.

---

## 8.15.18 Large Index Does Not Mean Bloated Index

```text
large index != bloated index
```

A large index can be legitimate because of large row count, wide keys, multiple key columns, included columns, high cardinality, access-method characteristics, legitimate data growth, or workload requirements.

Index size is a screening signal, not a diagnosis.

---

## 8.15.19 Index Inventory

```sql
SELECT
    schemaname,
    relname AS table_name,
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 50;
```

This identifies which indexes consume the most capacity. It does not identify which indexes are bloated.

---

## 8.15.20 Heap-to-Index Footprint

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(c.oid)) AS indexes_size,
    pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
ORDER BY pg_indexes_size(c.oid) DESC
LIMIT 50;
```

A table whose indexes consume several times its heap size deserves architectural review. It still does not prove bloat.

---

## 8.15.21 Index Count as a Capacity Factor

```sql
SELECT
    schemaname,
    tablename,
    count(*) AS index_count
FROM pg_indexes
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
GROUP BY schemaname, tablename
ORDER BY index_count DESC, schemaname, tablename;
```

A heavily indexed table can incur substantially greater write amplification, WAL generation, cache consumption, VACUUM index work, storage growth, and replication traffic.

---

## 8.15.22 Usage Statistics Are Not Bloat Statistics

`pg_stat_user_indexes` includes `idx_scan`, `idx_tup_read`, and `idx_tup_fetch`.

These describe index usage. They do not measure bloat.

Likewise, `idx_scan = 0` does not prove an index can safely be removed.

Before considering removal, account for statistics resets, rare workloads, reporting jobs, failover or emergency queries, schema dependencies, constraints, replica identity, and application semantics.

---

## 8.15.23 Constraint and Dependency Protection

Before recommending removal of a low-usage index, determine whether it supports a primary key, unique constraint, exclusion constraint, replica identity, or application-enforced uniqueness assumptions.

PostgreSQL does not automatically create an index on the referencing columns of a foreign key. However, an appropriate referencing-side index can be operationally important when parent rows are updated or deleted because PostgreSQL must locate referencing rows efficiently.

Low `idx_scan` is never sufficient evidence for `DROP INDEX`.

---

## 8.15.24 Physical B-tree Inspection with `pgstatindex`

```sql
SELECT *
FROM pgstatindex('public.orders_created_at_idx');
```

Useful B-tree information can include:

```text
index_size
tree_level
leaf_pages
empty_pages
deleted_pages
avg_leaf_density
leaf_fragmentation
```

These metrics provide stronger physical evidence than index size alone. They remain diagnostic signals, not automatic remediation thresholds.

---

## 8.15.25 Production Cost of Physical Inspection

Physical index inspection should not automatically be the first action on a multi-hundred-GB or multi-terabyte index.

Before running broad inspection, consider index size, current workload, storage latency, storage throughput, IOPS, queue depth, maintenance window, and diagnostic necessity.

---

## 8.15.26 Leaf Density

Average B-tree leaf density can help identify inefficient physical occupancy.

A persistently large index with stable logical key count, poor density, low expected reuse, and meaningful storage pressure is stronger evidence than index size alone.

However, low leaf density is not an automatic REINDEX trigger.

---

## 8.15.27 Fragmentation

`pgstatindex()` can expose physical statistics such as `leaf_fragmentation`.

Treat this as evidence about physical organization. Do not interpret it automatically as corruption or as proof that REINDEX is immediately required.

---

## 8.15.28 Index Bloat and Corruption Are Different

```text
Index bloat
    |
    v
storage / performance /
maintenance efficiency

Index corruption
    |
    v
structural / correctness /
integrity risk
```

Both can eventually lead to REINDEX, but the diagnosis, severity, and operational response differ substantially.

---

## 8.15.29 `amcheck` and `pg_amcheck`

When index corruption is suspected, PostgreSQL provides integrity-checking facilities through `amcheck` and `pg_amcheck`.

These should be used when evidence suggests possible structural inconsistency, storage corruption, hardware problems, software defects, or incorrect index contents.

Do not launch expensive integrity checks merely because an index is large or physically sparse.

---

## 8.15.30 Index Growth Trends

A concerning pattern is:

```text
logical row/key count: stable
index size:            steadily increasing
```

combined with substantial UPDATE or DELETE churn.

The governing question is:

> **Did physical index growth materially exceed durable logical or key-set growth?**

---

## 8.15.31 Long Transactions and Index Cleanup

Long-running transactions and retained visibility horizons can indirectly delay index cleanup.

```text
old visibility horizon retained
        |
        v
heap versions remain potentially visible
        |
        v
related index entries cannot yet
be treated as globally removable
        |
        v
cleanup delayed
```

The retained visibility horizon is the underlying mechanism.

---

## 8.15.32 Index Bloat Is Workload-Specific

Potential contributors include update-heavy workloads, low HOT eligibility, frequent deletes, long visibility horizons, large numbers of indexes, page-split patterns, sparse surviving key ranges, historical data reduction, maintenance backlog, and definitions that cannot benefit from B-tree deduplication.

---

## 8.15.33 Non-B-tree Indexes

B-tree-specific concepts such as leaf density, bottom-up deletion, simple deletion, B-tree deduplication, and B-tree page splits must not be applied blindly to GIN, GiST, SP-GiST, or hash indexes.

For non-B-tree access methods, use access-method-specific investigation and monitor physical size with the maintenance semantics appropriate to that access method.

---

## 8.15.34 Why REINDEX Can Reclaim B-tree Bloat

`REINDEX` constructs a new physical index from table data and replaces the old index structure.

```text
old index
   |
   v
build replacement
from durable table data
   |
   v
new index structure
   |
   v
replace old structure
```

A new B-tree no longer contains the old index's accumulated sparse or inefficient physical layout.

---

## 8.15.35 VACUUM Versus REINDEX

```text
VACUUM
  |
  +--> routine MVCC cleanup
  +--> removes obsolete index tuples
  +--> permits space reuse
  +--> does not globally compact index

REINDEX
  |
  +--> structural rebuild
  +--> creates replacement index
  +--> removes accumulated sparse layout
  +--> requires controlled execution
```

Routine VACUUM remains the normal maintenance mechanism. REINDEX is targeted remediation.

---

## 8.15.36 REINDEX Locking

A conventional REINDEX requires strong locking and can block production access to the object.

Before recommending normal REINDEX, evaluate object size, query workload, write workload, lock duration, maintenance window, dependent operations, and recovery strategy.

Detailed execution belongs in Section 8.17.

---

## 8.15.37 `REINDEX CONCURRENTLY`

```sql
REINDEX INDEX CONCURRENTLY public.orders_created_at_idx;
```

Concurrent reindexing reduces blocking of normal DML compared with conventional REINDEX.

It should not be described as risk-free online maintenance. It involves additional work, multiple processing phases, longer duration, transaction waits, additional disk requirements, WAL and replication impact, and operational caveats.

---

## 8.15.38 REINDEX Capacity Planning

A rebuild can require old and replacement index structures to coexist for part of the operation.

Production capacity planning must account for existing index, replacement index, WAL, replication effects, and operational safety headroom.

---

## 8.15.39 Do Not Reindex from a Percentage

Avoid rules such as:

```text
leaf density < 70% => REINDEX
estimated bloat > 30% => REINDEX
index > 100 GB => REINDEX
```

These ignore absolute reclaimable bytes, index usefulness, logical growth, future workload, maintenance health, locking, storage headroom, WAL, replication, and expected performance benefit.

No single metric is a universal production REINDEX threshold.

---

## 8.15.40 Do Not Blanket-Reindex on a Schedule

Avoid generic maintenance policies such as:

```text
REINDEX every production table every Sunday
```

Periodic REINDEX can be appropriate for specific workload patterns, but it is not a universal PostgreSQL requirement.

Use evidence-driven targeting.

---

## 8.15.41 Persistent Bloat Versus Unnecessary Index

Two independent questions exist:

```text
Is the index useful?
Is the index physically efficient?
```

```text
                    Efficient        Bloated
                    ---------        -------
Useful index          keep           repair
Unnecessary index     review/drop    review/drop
```

An unnecessary index should not automatically be rebuilt merely because it is bloated.

---

## 8.15.42 Duplicate and Overlapping Indexes

Before rebuilding a large index, investigate whether it should exist.

Look for exact duplicates, redundant manually created indexes, obsolete application indexes, overlapping leading-column patterns, and indexes potentially subsumed by others.

This is an index-governance investigation, not a bloat diagnosis.

---

## 8.15.43 Production Classification

### Class A — Healthy Index Churn

DML churn is present, VACUUM/B-tree cleanup keeps pace, and physical size is stable.

**Action:** Monitor.

### Class B — Index Cleanup Backlog

Obsolete-version generation exceeds cleanup capacity.

**Action:** Correct maintenance, blocker, or storage limitations first.

### Class C — Persistent B-tree Bloat

The durable key set is stable or reduced, the index remains oversized, physical occupancy is inefficient, capacity is unlikely to be reused, and operational cost is measurable.

**Action:** Evaluate controlled REINDEX under Section 8.17.

### Class D — Legitimately Large Index

The durable key set is large, index design is appropriate, physical efficiency is acceptable, and growth tracks workload.

**Action:** No bloat remediation.

### Class E — Index-Governance Finding

The index is large but has little justified workload value or a redundant definition.

**Action:** Evaluate safe removal or redesign.

Class E is not a bloat subtype.

### Class F — Possible Corruption

Structural or correctness evidence exists.

**Action:** Escalate through integrity investigation using appropriate PostgreSQL verification tooling.

---

## 8.15.44 Production Investigation Workflow

1. Inventory index size, heap size, total index footprint, index count, and access method.
2. Establish workload value from usage statistics, query plans, constraint role, replica identity, and application dependencies.
3. Establish DML churn from INSERT, UPDATE, DELETE, and HOT update rates.
4. Establish cleanup health from dead-tuple trends, VACUUM history, active VACUUM progress, and `INDEX_CLEANUP` behavior.
5. Check retained horizons, including long transactions, old snapshots, prepared transactions, replication horizons, and standby feedback.
6. Compare historical index growth with durable row/key growth.
7. Obtain B-tree physical evidence with `pgstatindex()` when justified.
8. Separate bloat from corruption.
9. Review duplicate, overlapping, obsolete, and constraint-backed indexes.
10. Quantify potentially reclaimable bytes, storage cost, cache pressure, query impact, maintenance duration, and write amplification.
11. Classify the finding.
12. Correct root cause before rebuilding.
13. Move only persistent, operationally significant bloat to Section 8.17 for controlled structural remediation.

---

## 8.15.45 Production Finding Format

A production finding should contain index name, table name, access method, current size, heap size, historical size trend, durable logical/key growth, index usage, constraint/dependency role, DML churn, HOT behavior, VACUUM/index-cleanup health, retained-horizon analysis, physical evidence, estimated potentially reclaimable capacity, operational impact, root cause, classification, and recommendation.

Use absolute bytes as well as percentages when describing potentially reclaimable capacity.

---

## 8.15.46 Example — Healthy Large Index

```text
index size:       800 GB
table size:       4 TB
logical growth:   strong
idx_scan:         very high
leaf density:     acceptable
index growth:     tracks table growth
VACUUM:           healthy
```

Classification: legitimately large index.

Recommendation: no bloat remediation; continue capacity monitoring.

---

## 8.15.47 Example — Persistent B-tree Bloat

```text
index size:          800 GB
logical key set:     stable
index growth:        +300 GB
historical UPDATE:   high
dead tuples:         currently controlled
leaf density:        persistently poor
future reuse:        low
storage pressure:    high
```

Classification: persistent B-tree bloat candidate.

Recommendation: validate root cause and storage headroom, then evaluate controlled REINDEX under Section 8.17.

---

## 8.15.48 Example — Cleanup Backlog

```text
index size:       rising rapidly
dead tuples:      rising
autovacuum:       active
storage latency:  high
VACUUM duration:  increasing
```

Classification: index cleanup backlog.

Recommendation: restore cleanup throughput and resolve the underlying storage or maintenance limitation before considering REINDEX.

---

## 8.15.49 Example — Index-Governance Finding

```text
index size:        400 GB
validated usage:   negligible
definition:        redundant
constraint role:   none
replica identity:  no
```

Classification: index-governance issue.

Recommendation: evaluate safe index removal rather than spending maintenance resources rebuilding an index that should not exist.

---

## 8.15.50 Example — No Remediation Required

```text
index size:       large
logical growth:   proportional
workload value:   high
physical density: acceptable
cleanup:          healthy
storage:          within plan
```

Conclusion: no remediation recommended. Index growth is consistent with durable data growth, physical occupancy is acceptable, and workload benefit justifies the current footprint.

---

## 8.15.51 Production Principles

1. **Large index does not mean bloated index.**
2. **Dead index entries do not automatically mean persistent bloat.**
3. **VACUUM index cleanup is not REINDEX.**
4. **`INDEX_CLEANUP AUTO` is the normal production behavior.**
5. **Do not routinely force `INDEX_CLEANUP ON`.**
6. **Do not routinely use `INDEX_CLEANUP OFF` to shorten VACUUM.**
7. **VACUUM failsafe may bypass nonessential index work during correctness emergencies.**
8. **HOT eligibility materially affects index churn.**
9. **Bottom-up deletion reduces B-tree version-churn pressure.**
10. **Bottom-up deletion does not replace VACUUM.**
11. **Simple deletion can opportunistically remove `LP_DEAD` entries.**
12. **B-tree deduplication can reduce duplicate-key storage and maintenance pressure.**
13. **Deduplication availability depends on index definition, datatype, and collation.**
14. **Page splits are normal B-tree behavior.**
15. **Persistent poor occupancy, not page splitting alone, is the concern.**
16. **Completely empty B-tree pages can be reused.**
17. **Sparse nonempty pages can remain allocated.**
18. **Index size must be compared with durable logical growth.**
19. **Usage statistics are not bloat statistics.**
20. **`idx_scan = 0` is not sufficient evidence for removal.**
21. **Validate constraint and replica-identity dependencies before removal.**
22. **Referencing-side foreign-key indexes are not automatically created by PostgreSQL.**
23. **Physical inspection should follow inexpensive screening.**
24. **Leaf density is evidence, not a universal threshold.**
25. **Fragmentation is not corruption.**
26. **Bloat and corruption require different investigation paths.**
27. **Do not apply B-tree metrics blindly to other index access methods.**
28. **REINDEX is controlled structural remediation.**
29. **Conventional REINDEX can impose significant locking.**
30. **`REINDEX CONCURRENTLY` reduces blocking but is not risk-free.**
31. **Validate disk, WAL, and replication capacity before rebuilding.**
32. **Never trigger REINDEX from one percentage.**
33. **Avoid blanket scheduled REINDEX jobs.**
34. **Correct maintenance problems before rebuilding.**
35. **Review whether an index should exist before compacting it.**
36. **An unnecessary index is an index-governance problem, not merely bloat.**
37. **Report potentially reclaimable capacity in absolute bytes.**
38. **A valid investigation can conclude that no remediation is required.**
39. **The objective is not the smallest possible index.**
40. **The objective is a useful, correct, maintainable, and operationally efficient index.**

## 8.15.53 Key Takeaway

Index bloat is not simply a large index, and it is not simply dead index tuples.

```text
DML workload
     |
     v
HOT eligibility
   /       \
 high       low
 |           |
 v           v
less       greater
index      index-version
churn       churn
               |
               v
       obsolete index tuples
               |
       +-------+--------+
       |       |        |
       v       v        v
   bottom-up simple   VACUUM
   deletion   deletion cleanup
       \       |        /
        \      |       /
         v     v      v
          index-space reuse
                 |
            +----+----+
            |         |
            v         v
        efficient   persistently
          state     inefficient
                       |
                       v
               operational impact?
                   /         \
                  no         yes
                  |           |
                  v           v
               monitor     evaluate
                           structural
                           remediation
```

The central SRE/DBRE rule is:

> **Do not REINDEX because an index is large or because one diagnostic metric looks poor. Establish that physical allocation is persistently inefficient relative to the durable key set, that routine PostgreSQL cleanup is not restoring acceptable efficiency, and that the expected operational benefit exceeds the locking, I/O, storage, WAL, and replication cost of structural remediation.**

The objective is not the smallest possible index.

The objective is an index that remains correct, useful, maintainable, space-efficient, and operationally sustainable under the production workload.
