# 8.16 — VACUUM FULL, Table Rewrites, and Physical Space Reclamation

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** VACUUM, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **COMPLETE — CANONICAL**

## 8.16.1 Purpose

Routine PostgreSQL maintenance should normally rely on standard `VACUUM`.

Standard VACUUM removes reclaimable dead tuple versions, performs index cleanup where appropriate, and makes space reusable inside the existing relation.

Sometimes internal reuse is not enough.

A relation may retain persistent excess physical allocation after a major permanent data deletion, workload contraction, historical autovacuum or cleanup problems, previously retained visibility horizons, one-time exceptional growth, schema evolution, or retention-policy changes.

In those situations, operators may evaluate a physical table rewrite.

> **A table rewrite is not routine vacuum maintenance. It is a controlled storage-reclamation event with locking, disk, WAL, replication, I/O, duration, and availability implications.**

## 8.16.2 Standard VACUUM Versus `VACUUM FULL`

```text
Standard VACUUM
      |
      +--> in-place maintenance
      +--> removes reclaimable dead tuples
      +--> makes internal space reusable
      +--> normally retains physical relation layout

VACUUM FULL
      |
      +--> rewrites relation
      +--> creates replacement physical storage
      +--> copies surviving tuples
      +--> rebuilds associated indexes
      +--> replaces old physical structure
      +--> can return substantial capacity to filesystem
```

Therefore:

```text
VACUUM != VACUUM FULL
```

`VACUUM FULL` should not be viewed as a stronger version of routine VACUUM.

## 8.16.3 Why Standard VACUUM Usually Does Not Shrink the Table

Standard VACUUM can make free areas reusable, but it does not normally move all surviving tuples into a new compact sequence of pages.

Therefore:

```text
VACUUM succeeded
+
relation size unchanged
```

is normal PostgreSQL behavior.

## 8.16.4 Standard VACUUM Tail Truncation

There is an important exception. Standard VACUUM can sometimes return completely empty pages from the physical end of a heap relation to the operating system when truncation is enabled and safe.

It does not generally compact free space scattered through the interior of the relation. Reclaiming that capacity requires tuple movement or a physical rewrite.

## 8.16.5 What `VACUUM FULL` Does

`VACUUM FULL` writes a new physical copy of the table containing surviving tuples in a compact representation. The old physical copy remains required until the replacement is successfully constructed.

That architecture explains both the physical-reclamation benefit and the temporary capacity requirement.

## 8.16.6 TOAST Processing

Large PostgreSQL tables can have significant data stored in associated TOAST relations. Capacity analysis must therefore consider the main heap, TOAST heap, TOAST indexes, and ordinary indexes rather than examining only the visible heap.

`VACUUM FULL` processes the associated TOAST relation as part of the supported FULL operation. For tables containing large `text`, `jsonb`, `bytea`, arrays, or other variable-width values, ignoring TOAST can materially underestimate maintenance capacity requirements.

## 8.16.7 Aggressive Freezing During FULL

A table rewrite performed by `VACUUM FULL` already performs aggressive tuple freezing. Adding `FREEZE` does not provide an additional rewrite mode for FULL.

This is not a reason to use `VACUUM FULL` for anti-wraparound maintenance. Routine and anti-wraparound VACUUM remain the appropriate mechanisms for transaction-ID safety.

## 8.16.8 Appropriate Use Cases

A physical rewrite may merit evaluation when persistent excess allocation is proven, capacity is unlikely to be reused, operational benefit is meaningful, the root cause is understood and corrected or accepted, a maintenance window exists, and sufficient capacity is available.

Typical examples include permanent deletion of a large fraction of a table, a one-time retention-policy reduction, historical bloat after a resolved maintenance incident, long-term workload contraction, or substantial storage pressure where physical reclamation has durable value.

## 8.16.9 Poor Use Cases

Do not use `VACUUM FULL` merely because `n_dead_tup` is temporarily high, ordinary VACUUM did not shrink the file, a table exceeds an arbitrary size threshold, reusable space exists inside the heap, a dashboard reports a bloat percentage, autovacuum is behind, or a cleanup blocker still exists.

Correct the underlying problem first.

## 8.16.10 `ACCESS EXCLUSIVE` Locking

`VACUUM FULL` requires an `ACCESS EXCLUSIVE` lock on the table being processed. This is a primary production safety constraint because it conflicts with normal reads, writes, and many other table operations.

For large production relations, the lock can directly create an availability event.

## 8.16.11 Lock Acquisition Versus Lock Holding

Two different risks must be evaluated:

1. Can `ACCESS EXCLUSIVE` be acquired safely?
2. Can the application tolerate that lock for the full rewrite duration?

Passing one gate does not imply passing the other.

## 8.16.12 Lock Queue Risk

A rewrite waiting for `ACCESS EXCLUSIVE` behind a conflicting transaction can become part of a blocking chain. New application work can then queue behind the waiting rewrite request and create an availability incident.

Operators should avoid allowing rewrite commands to wait indefinitely for production locks.

## 8.16.13 Preflight Activity Inspection

Before maintenance, inspect active transactions:

```sql
SELECT
    pid,
    usename,
    application_name,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;
```

Investigate unexpected long transactions, idle-in-transaction sessions, maintenance operations, DDL, batch workloads, and lock waiters. Do not terminate production sessions merely to make a rewrite start without an approved operational decision.

## 8.16.14 Lock Timeout Guardrail

A maintenance session can use an explicitly approved `lock_timeout`, for example:

```sql
SET lock_timeout = '5s';
```

The value is illustrative only. The objective is to fail lock acquisition safely rather than wait indefinitely and create a blocking queue. Prefer session-scoped maintenance settings.

## 8.16.15 Statement Timeout

A large physical rewrite can legitimately run for a long period. Before maintenance, review the effective `statement_timeout`. A generic application timeout can accidentally terminate an approved maintenance operation.

Any adjustment should normally be scoped to the maintenance session and change process rather than made globally.

## 8.16.16 Disk-Space Requirement

`VACUUM FULL` requires additional disk capacity because PostgreSQL constructs replacement storage before releasing the old physical representation.

Capacity planning must consider existing heap, existing TOAST, existing indexes, replacement structures, WAL allowance, temporary overhead, and an operational safety margin.

## 8.16.17 Why a Fixed 2× Formula Is Unsafe

Avoid universal formulas such as `free disk >= table size` or `free disk >= 2 × table size` without understanding what the table-size number includes.

Actual requirements depend on heap size, TOAST footprint, index footprint, tablespaces, WAL behavior, concurrent workload, storage architecture, filesystem overhead, and rewrite method.

Capacity should be modeled from measured bytes.

## 8.16.18 Capacity Preflight

```sql
SELECT
    pg_size_pretty(pg_relation_size('public.orders')) AS heap_size,
    pg_size_pretty(pg_indexes_size('public.orders')) AS indexes_size,
    pg_size_pretty(pg_total_relation_size('public.orders')) AS total_size;
```

`pg_total_relation_size()` is useful because it includes associated storage such as indexes and TOAST. Also identify the tablespace, underlying filesystem or volume, actual free bytes, maximum storage capacity, and autoscaling constraints where applicable.

## 8.16.19 WAL Impact

A large rewrite can generate significant WAL. Operational effects can include archive pressure, network traffic, replication traffic, WAL storage consumption, and replica replay pressure.

Exact WAL volume depends on configuration and operation characteristics. Do not estimate it from a universal relation-size multiplier.

## 8.16.20 Replication Impact

If primary WAL generation exceeds replication transport or standby replay capacity, replication lag can grow.

Before maintenance, evaluate HA requirements, RPO/RTO, synchronous replication where applicable, replication slots, WAL retention, archive throughput, and read-replica freshness.

## 8.16.21 Replica Safety Thresholds

Define warning and escalation criteria before starting. Thresholds must be environment-specific and should reflect the approved HA and RPO objectives.

## 8.16.22 Storage I/O Impact

A rewrite can generate substantial reads, writes, index-build I/O, WAL writes, and checkpoint pressure.

For cloud block storage, verify IOPS limits, throughput limits, latency, queue depth, and burst behavior. A PostgreSQL operation can be logically correct while overwhelming the storage platform.

## 8.16.23 CPU and Memory

Rewrite operations can also consume CPU, maintenance memory, shared-buffer/cache capacity, checkpointer resources, and background-writer resources. Index rebuilding can materially increase CPU and I/O demand.

Do not model `VACUUM FULL` as a disk-only operation.

## 8.16.24 Progress Reporting

Ordinary VACUUM reports through `pg_stat_progress_vacuum`. `VACUUM FULL` is different because it performs a table rewrite; progress is exposed through `pg_stat_progress_cluster` along with CLUSTER operations.

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    command,
    phase,
    heap_tuples_scanned,
    heap_tuples_written,
    heap_blks_total,
    heap_blks_scanned,
    index_rebuild_count
FROM pg_stat_progress_cluster;
```

## 8.16.25 `VACUUM FULL` Progress Phases

Relevant progress phases include:

```text
initializing
      |
      v
seq scanning heap
      |
      v
writing new heap
      |
      v
swapping relation files
      |
      v
rebuilding index
      |
      v
performing final cleanup
```

Additional phases exposed by `pg_stat_progress_cluster` can be associated with CLUSTER-specific execution strategies and should not automatically be interpreted as `VACUUM FULL` phases.

## 8.16.26 Do Not Estimate Completion from Heap Scan Alone

A rewrite that has scanned most of the heap may still require substantial time for writing the new heap, relation swap, index rebuilding, and final cleanup.

Therefore 90% of the heap scanned does not necessarily mean 90% of wall-clock duration is complete.

## 8.16.27 Integrated Monitoring

Monitor `pg_stat_progress_cluster` together with CPU, storage latency, IOPS, throughput, queue depth, free disk, WAL rate, replica lag, and application latency.

A rewrite is an end-to-end infrastructure event.

## 8.16.28 Cancellation and Abort Criteria

Do not terminate a long rewrite casually. Cancellation can discard substantial completed work and still leave operational effects such as generated WAL, replica lag, consumed maintenance time, I/O pressure, and workload disruption.

However, completion is not always safer. Predefine conditions that require escalation or cancellation evaluation, such as imminent storage exhaustion, critical replication failure, unacceptable application impact, unexpected lock behavior, or infrastructure instability.

## 8.16.29 Transactional Protection

PostgreSQL provides transactional correctness while the rewrite is executing, but transactionally protected does not mean operationally free to fail.

A successfully committed rewrite is complete; it is not an operation that can simply be rolled back afterward.

## 8.16.30 `CLUSTER`

`CLUSTER` is another table-rewrite operation. Its primary additional purpose is to physically reorder table rows according to an index.

`CLUSTER` also has significant locking and capacity requirements.

## 8.16.31 `VACUUM FULL` Versus `CLUSTER`

`VACUUM FULL` focuses on compacting physical representation and reclaiming persistent excess allocation. `CLUSTER` rewrites and physically orders the table according to a chosen index, with compaction occurring as part of that rewrite.

Use CLUSTER when physical ordering provides a justified workload benefit. For some workloads, deliberate periodic reclustering can be appropriate because subsequent updates gradually reduce the original physical ordering.

## 8.16.32 Table-Rewriting `ALTER TABLE`

Some forms of `ALTER TABLE` require a complete table rewrite; many do not. Rewrite requirements depend on the specific operation and PostgreSQL version.

Examples can include certain data-type conversions, generated-column operations, volatile default expressions, and storage/access-method changes. Always verify the specific DDL against documentation for the deployed PostgreSQL major version.

## 8.16.33 Storage Settings Do Not Always Rewrite Existing Rows

A configuration or storage-strategy change does not necessarily rewrite all existing tuples immediately. Some changes affect future tuple writes without reconstructing all existing rows.

Avoid broad assumptions that a storage setting change always implies a full rewrite.

## 8.16.34 Dropped Columns and Physical Space

`DROP COLUMN` normally changes the logical schema without immediately rewriting every existing row. Existing physical storage can persist until rows are naturally replaced or a later legitimate table rewrite reconstructs the relation.

A rewrite can reclaim physical space formerly occupied by the dropped column.

## 8.16.35 Do Not Invent Schema Changes to Reclaim Bloat

A legitimate `ALTER TABLE` rewrite may incidentally reclaim historical physical space. That does not justify creating unnecessary schema changes merely to force a rewrite.

Schema design and bloat remediation are separate concerns.

## 8.16.36 `TRUNCATE` as an Architectural Alternative

For transient or staging tables where the intended operation is to remove all rows, evaluate whether:

```sql
TRUNCATE TABLE public.staging_data;
```

matches application semantics better than deleting every row followed by VACUUM and possible later rewrite.

`TRUNCATE` has different locking, MVCC, trigger, foreign-key, and transactional behavior. It is an architectural alternative, not a generic DELETE replacement.

## 8.16.37 Root Cause Before Rewrite

Before approving physical reclamation, identify why the relation became oversized. Possible causes include a one-time bulk delete, historical workload peak, autovacuum undersizing, long visibility horizon, storage saturation, maintenance configuration, retention-policy change, or application architecture.

Ask whether the root cause has been corrected or intentionally accepted. If not, a rewrite may provide only temporary benefit.

## 8.16.38 Reuse Forecast

The key question is not simply whether 500 GB can be reclaimed. It is how quickly PostgreSQL will need that capacity again.

Standard VACUUM intentionally makes space reusable. Returning capacity to the filesystem only to extend the relation again shortly afterward can create unnecessary maintenance work and future I/O.

## 8.16.39 Durability of Benefit

Include expected benefit duration in the decision. Estimated potentially reclaimable capacity, expected regrowth, and expected benefit duration are more useful than a bloat percentage alone.

## 8.16.40 Rewrite Decision Model

A rewrite candidate should satisfy all of the following:

1. Persistent excess allocation is proven.
2. Capacity is unlikely to be reused soon.
3. Operational benefit is meaningful.
4. Root cause is corrected or intentionally accepted.
5. Locking is feasible.
6. Storage headroom is sufficient.
7. WAL and replication impact are acceptable.
8. I/O capacity is sufficient.
9. A maintenance window and monitoring plan exist.

## 8.16.41 Production Classification

### Class A — No Rewrite Required

Internal free capacity is reusable and likely to be consumed again.

**Action:** Retain and monitor.

### Class B — Root Cause Unresolved

Persistent excess allocation exists, but the maintenance or workload cause remains active.

**Action:** Correct the root cause first.

### Class C — Controlled Rewrite Candidate

Persistent excess allocation is proven, capacity is unlikely to be reused, operational benefit is material, and root cause is corrected.

**Action:** Plan controlled reclamation.

### Class D — Urgent Capacity Risk

Storage pressure is severe and persistent bloat represents meaningful reclaimable capacity.

**Action:** Escalate urgently, but do not bypass rewrite capacity or locking requirements.

### Class E — Architectural Alternative Preferred

Partition dropping, retention redesign, `TRUNCATE`, lifecycle management, or another architecture change provides a better long-term solution.

**Action:** Prefer the architectural correction.

## 8.16.42 Urgency Does Not Eliminate Headroom Requirements

Severe storage pressure can simultaneously increase the need for reclamation and make `VACUUM FULL` less feasible because the rewrite itself needs additional working capacity.

Capacity expansion, architectural removal, partition lifecycle operations, or another recovery strategy may need to occur first.

## 8.16.44 Go/No-Go Gates

Proceed only when evidence supports the rewrite, the root cause is handled, capacity is sufficient, lock acquisition and duration are acceptable, WAL capacity is acceptable, replicas are healthy, storage is healthy, the maintenance window is active, monitoring is available, and the abort plan is ready.

Otherwise the correct decision is **NO-GO**.

## 8.16.45 Progress Query

```sql
SELECT
    p.pid,
    p.datname,
    p.relid::regclass AS relation,
    p.command,
    p.phase,
    p.heap_blks_total,
    p.heap_blks_scanned,
    p.heap_tuples_scanned,
    p.heap_tuples_written,
    p.index_rebuild_count
FROM pg_stat_progress_cluster AS p;
```

Combine this with infrastructure telemetry rather than using it as the sole monitoring source.

## 8.16.46 Post-Rewrite Validation

After successful completion, validate correctness, capacity, performance, and replication separately.

Confirm the relation is accessible, expected indexes are present and valid, application reads and writes succeed, relation size changed as expected, storage metrics normalized, replicas recovered, WAL retention is normalizing, and database logs are clean.

## 8.16.47 Before/After Evidence

```sql
SELECT
    pg_size_pretty(pg_relation_size('public.orders')) AS heap_size,
    pg_size_pretty(pg_indexes_size('public.orders')) AS indexes_size,
    pg_size_pretty(pg_total_relation_size('public.orders')) AS total_size;
```

Document before and after heap, index, and total sizes, plus the actual capacity reclaimed.

## 8.16.48 Planner Statistics

After a rewrite, review planner-statistics freshness and query behavior. Run `ANALYZE` when required by the approved operation, statistics are stale, post-maintenance validation indicates it is needed, or the maintenance plan explicitly includes it.

Do not assume every physical rewrite universally requires an additional manual ANALYZE. Detailed statistics policy belongs in Section 8.18.

## 8.16.49 Do Not Automate `VACUUM FULL`

Never implement threshold-only automation such as:

```text
if bloat > 30%
then VACUUM FULL
```

Automation may discover candidates, collect evidence, measure storage, forecast growth, identify blockers, estimate benefit, and produce a change plan. It should not automatically execute a strongly blocking physical rewrite solely because a metric crosses a threshold.

## 8.16.50 Managed PostgreSQL Considerations

Managed PostgreSQL does not remove rewrite mechanics. Additional platform factors can include storage autoscaling, storage maximums, IOPS tiers, throughput tiers, burst capacity, WAL architecture, backup/PITR behavior, replica topology, and failover design.

Always validate provider-specific limits before a large rewrite.

## 8.16.51 Kubernetes PostgreSQL Considerations

For PostgreSQL on Kubernetes, verify PVC free bytes, PVC maximum capacity, storage-class expansion behavior, volume throughput, volume IOPS, node health, pod scheduling, replica topology, and backup activity.

A nearly full PVC should be treated as a hard production risk. Do not assume storage expansion will complete quickly enough to rescue an already-running rewrite.

## 8.16.52 Example — No Rewrite Required

```text
heap:                       1.5 TB
potentially reclaimable:    250 GB
disk utilization:           52%
update churn:               high
expected regrowth:          <30 days
maintenance window:         difficult
```

**Conclusion:** No rewrite recommended. Reusable internal capacity is expected to be consumed again by normal workload growth, so physical reclamation would not provide durable operational benefit.

## 8.16.53 Example — Controlled Rewrite Candidate

```text
heap:                       3.0 TB
potentially reclaimable:    1.8 TB
cause:                      completed retention reduction
future regrowth:            low
disk utilization:           86%
maintenance window:         approved
replicas:                   healthy
capacity model:             passed
root cause:                 resolved
```

**Classification:** Controlled Rewrite Candidate.

Proceed to approved physical-reclamation planning with explicit locking, capacity, WAL, replication, monitoring, and abort controls.

## 8.16.54 Example — Root Cause First

```text
heap:                       2 TB
dead tuples:                rapidly rising
autovacuum:                 cannot keep pace
storage latency:            severe
potentially reclaimable:    high
```

**Classification:** Root Cause Unresolved.

Do not begin with `VACUUM FULL`. Restore routine maintenance throughput, resolve storage or blocker conditions, then reassess persistent excess allocation.

## 8.16.55 Example — Urgent Capacity Risk

```text
total relation footprint:   4 TB
potentially reclaimable:    2 TB
filesystem utilization:     94%
free rewrite headroom:      insufficient
```

**Classification:** Urgent Capacity Risk.

Do not assume `VACUUM FULL` is safe merely because reclaimable space exists. Evaluate storage expansion, lifecycle deletion, partition-level alternatives, or another safe capacity-restoration path before rewrite.

## 8.16.59 Key Takeaway

> **Do not use `VACUUM FULL` merely because standard VACUUM did not reduce a relation's physical size. Use a rewrite only when persistent excess allocation is proven, that capacity is unlikely to be reused, the underlying cause has been addressed, and the expected benefit justifies the `ACCESS EXCLUSIVE` lock, temporary storage, WAL, replication, I/O, and maintenance-window cost.**

Physical reclamation should be evidence-driven, capacity-modeled, lock-controlled, observable, failure-aware, and validated afterward.

The objective is not simply to make the table smaller. The objective is to reclaim physical capacity durably and safely without converting a storage-efficiency problem into a database availability incident.
