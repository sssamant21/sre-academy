# 8.17 — REINDEX and Index Maintenance Strategy

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **COMPLETE — CANONICAL**

## 8.17.1 Purpose

PostgreSQL indexes require maintenance, but `REINDEX` is not routine cleanup for every large, old, or heavily used index.

PostgreSQL already maintains indexes through mechanisms including VACUUM index cleanup, B-tree bottom-up deletion, simple B-tree deletion, B-tree deduplication, page reuse, and access-method-specific maintenance.

`REINDEX` is structural maintenance.

The production question is not whether an index is large. It is whether rebuilding the index provides enough correctness, storage, or performance benefit to justify its locking, transaction-wait, disk, CPU, I/O, WAL, replication, and maintenance cost.

> **REINDEX should be evidence-driven structural maintenance, not a default response to index size, age, or a single diagnostic metric.**

## 8.17.2 What REINDEX Does

`REINDEX` rebuilds an index from the data in its parent table and replaces the old physical index with a newly constructed structure.

This can address persistent physical inefficiency, certain corruption scenarios, invalid indexes, changed storage parameters, and physical-layout degradation.

## 8.17.3 REINDEX Versus VACUUM

`VACUUM` performs routine MVCC cleanup, removes dead index tuples where appropriate, enables internal page reuse, and preserves the existing index structure.

`REINDEX` constructs a replacement index, replaces the existing physical index, and resets its physical layout.

Therefore, `VACUUM` and `REINDEX` solve different operational problems.

## 8.17.4 Primary REINDEX Scenarios

REINDEX may be appropriate for persistent physical inefficiency, corruption, changed index storage parameters, invalid-index recovery, or a demonstrated recurring workload pattern where rebuilding provides durable benefit.

## 8.17.5 Large Does Not Mean Bloated

Do not create universal policies such as `index > 100 GB => REINDEX`, `index age > 1 year => REINDEX`, or `estimated bloat > 30% => REINDEX`.

A multi-terabyte index can be healthy. A much smaller index can be structurally inefficient. Size is evidence of capacity consumption, not proof of bloat.

## 8.17.6 Evidence Before Action

The production sequence should be:

```text
problem detected
      |
      v
physical/integrity evidence
      |
      v
index dependency and usefulness
      |
      v
root cause
      |
      v
maintenance method
      |
      v
capacity + availability assessment
      |
      v
approved execution
```

Begin with evidence, not the remediation command.

## 8.17.7 Bloat and Corruption Are Different Problems

Persistent bloat is primarily an efficiency problem involving capacity, performance, and maintenance efficiency.

Corruption is primarily a correctness problem involving structural integrity, data access, and availability.

A bloat case should normally pass a benefit-versus-cost test. A corruption incident may require urgent repair even when no storage savings are expected.

## 8.17.8 Integrity Escalation

If corruption is suspected, prioritize impact assessment, database logs, index validity, `amcheck` or `pg_amcheck` where applicable, storage and hardware health, operator-class and collation considerations where relevant, replica comparison where appropriate, and recent infrastructure or software changes.

REINDEX may repair the affected index. It does not establish or correct the underlying cause of corruption.

## 8.17.9 Access-Method Boundary

Do not apply B-tree-specific reasoning universally. PostgreSQL supports multiple index access methods including B-tree, Hash, GiST, SP-GiST, GIN, and BRIN.

B-tree leaf density, page splits, bottom-up deletion, deduplication, and physical locality are not universal index properties. Use access-method-specific diagnostics and PostgreSQL guidance.

## 8.17.10 Standard REINDEX

Example:

```sql
REINDEX INDEX public.orders_created_at_idx;
```

Standard REINDEX uses strong exclusive locking on the index while rebuilding it. Table reads can continue, while `INSERT`, `UPDATE`, and `DELETE` operations that require index maintenance can block.

The parent table should not simply be described as receiving an `ACCESS EXCLUSIVE` lock for ordinary `REINDEX INDEX`.

## 8.17.11 Application Impact of Standard REINDEX

Even when reads continue, blocked writers can create longer transactions, connection-pool pressure, timeouts, retries, and application degradation.

A high-write service can therefore experience a serious availability impact during standard REINDEX.

## 8.17.12 REINDEX CONCURRENTLY

Example:

```sql
REINDEX INDEX CONCURRENTLY
    public.orders_created_at_idx;
```

Concurrent REINDEX rebuilds an index while allowing normal table DML to continue.

> **Concurrent REINDEX reduces DML blocking but increases execution complexity, duration, resource consumption, transaction coordination, and failure-recovery requirements.**

It should not be described as zero-downtime or risk-free.

## 8.17.13 Standard Versus Concurrent REINDEX

Standard REINDEX generally has less coordination overhead and completes faster, but it blocks affected writes.

`REINDEX CONCURRENTLY` allows normal DML to continue, uses weaker locking, performs two table scans per rebuilt index, waits for relevant transactions, usually takes longer, and is operationally more complex.

Availability is the primary reason to choose the concurrent path.

## 8.17.14 Concurrent Locking

Ordinary REINDEX uses an `ACCESS EXCLUSIVE` lock on the index. Concurrent REINDEX uses weaker index locking, including `SHARE UPDATE EXCLUSIVE`, allowing normal table DML to continue.

However, DML-friendly does not mean DDL-conflict-free. Schema modifications and other index operations can still conflict.

## 8.17.15 One Concurrent Build per Table

Only one concurrent index build can operate on a particular table at a time. Serialize concurrent index maintenance for indexes on the same parent table.

## 8.17.16 Avoid Overlapping DDL

Do not independently schedule `REINDEX CONCURRENTLY`, `ALTER TABLE`, `CREATE INDEX CONCURRENTLY`, or constraint changes on the same table without explicit coordination.

## 8.17.17 Concurrent REINDEX Architecture

At a high level, concurrent REINDEX initializes, waits for relevant writers, builds the replacement index, waits for writers before validation, validates replacement state, waits for old snapshots, switches index roles, waits for readers as required, and retires the old index.

The exact internal sequence should always be interpreted through PostgreSQL's documented progress phases for the deployed version.

## 8.17.18 Important Progress Phases

Relevant concurrent REINDEX waiting phases include:

- waiting for writers before build;
- waiting for writers before validation;
- waiting for old snapshots;
- waiting for readers before marking dead;
- waiting for readers before dropping.

A backend can be healthy while spending substantial time waiting for another transaction.

## 8.17.19 Long Transactions Matter

Concurrent REINDEX can wait for existing writers, transactions with relevant snapshots, long-running queries, sessions using old index state, and conflicting maintenance.

A waiting phase with little visible progress does not necessarily mean the operation is hung.

## 8.17.20 Long Transactions and VACUUM

A long-running REINDEX also contributes to the broader long-transaction environment. REINDEX planning should consider overall maintenance health, not only the target index.

## 8.17.21 Preflight Transaction Review

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;
```

Investigate long-running transactions, idle-in-transaction sessions, long reports, batch workloads, DDL, and maintenance sessions. Do not automatically terminate a transaction merely because REINDEX is waiting for it.

## 8.17.22 Transaction-Block Restrictions

`REINDEX INDEX CONCURRENTLY` cannot run inside a transaction block.

Transaction-block support varies by REINDEX scope and mode. Validate the exact command against the deployed PostgreSQL version rather than assuming all REINDEX forms behave identically.

## 8.17.23 Progress Reporting

REINDEX reports progress through `pg_stat_progress_create_index`.

```sql
SELECT
    pid,
    datname,
    relid::regclass AS table_name,
    index_relid::regclass AS index_name,
    command,
    phase,
    lockers_total,
    lockers_done,
    current_locker_pid,
    blocks_total,
    blocks_done,
    tuples_total,
    tuples_done
FROM pg_stat_progress_create_index;
```

## 8.17.24 Progress Counters Are Phase-Dependent

Do not interpret `blocks_done / blocks_total` or tuple counters as a universal percentage for the entire REINDEX operation. Later transaction waits, index-state transitions, and cleanup phases can remain after a scan is nearly complete.

## 8.17.25 Blocker Investigation

When `current_locker_pid` is populated, correlate it with `pg_stat_activity`:

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE pid = <current_locker_pid>;
```

Determine transaction owner, business purpose, age, expected completion, application impact, and whether termination is authorized. A blocker PID is evidence, not permission to terminate a backend.

## 8.17.26 Disk Headroom

Concurrent rebuilding requires old and replacement structures to coexist during part of the operation.

Capacity planning should consider the existing index, replacement index, temporary/transient overhead, WAL allowance, and operational safety margin.

Do not start a 700 GB rebuild simply because exactly 700 GB is free.

## 8.17.27 Measure Actual Index Size

```sql
SELECT
    c.oid::regclass AS index_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS index_size
FROM pg_class AS c
WHERE c.oid = 'public.orders_created_at_idx'::regclass;
```

Use actual bytes for capacity planning rather than percentage-free storage alone.

## 8.17.28 WAL Impact

REINDEX can generate significant WAL. Monitor WAL generation rate, WAL filesystem usage, archive throughput, replication traffic, and replication-slot retention.

Do not use a universal index-size-to-WAL formula.

## 8.17.29 Replication Impact

If REINDEX WAL generation exceeds downstream transport or replay capacity, replica lag can grow.

Before maintenance, review replica health, replica lag, replication slots, WAL retention, archive throughput, synchronous-replication implications, and HA/RPO requirements.

## 8.17.30 Define Replica Limits Before Execution

Define warning and escalation thresholds before starting maintenance. Thresholds are environment-specific and should reflect approved HA/RPO requirements.

## 8.17.31 CPU and Storage I/O

A concurrent rebuild can combine normal workload, table scans, index construction, concurrent DML index maintenance, and WAL generation.

Monitor CPU, memory pressure, IOPS, throughput, storage latency, queue depth, buffer-cache behavior, and application latency.

## 8.17.32 Failed Concurrent REINDEX — `_ccnew`

A failed concurrent rebuild can leave an invalid replacement index with a transient name containing `_ccnew`, possibly with a numeric suffix.

Identify and validate the transient index, verify dependencies, correct the failure cause, remove only the confirmed invalid transient object, and retry only after preflight passes.

Do not delete an object based on its name alone.

## 8.17.33 Failed Concurrent REINDEX — `_ccold`

A different failure state can leave an invalid old index containing `_ccold` after the replacement succeeded but the old index could not be removed.

Validate the replacement first, then remove only the confirmed obsolete old invalid object.

`_ccnew` and `_ccold` represent materially different recovery situations.

## 8.17.34 Never Automate Transient-Index Deletion by Name

Never implement automatic deletion solely because an index name contains `_ccnew` or `_ccold`.

Before destructive cleanup verify `pg_index` validity state, replacement index, constraint dependencies, replica identity, index definition, application dependency, and failure phase.

## 8.17.35 Unique Index Considerations

Concurrent unique-index operations require special care. Verify existing uniqueness, constraint relationships, concurrent-write behavior, and the failure-recovery procedure.

Treat failed concurrent unique-index operations as controlled integrity events rather than simple planner-usage problems.

## 8.17.36 Constraint-Backed Indexes

Before rebuilding or removing an index, determine whether it supports a primary key, unique constraint, exclusion constraint, replica identity, or application uniqueness behavior.

Also evaluate foreign-key workload implications before removing a supporting index.

## 8.17.37 Replica Identity

An index used as replica identity can be critical for logical replication, CDC, and downstream change processing.

An index can appear unimportant from ordinary query statistics while remaining operationally essential.

## 8.17.38 Exclusion Constraints

Indexes supporting exclusion constraints have restrictions on concurrent REINDEX. Do not assume `REINDEX CONCURRENTLY` works for every constraint-backed index.

## 8.17.39 REINDEX TABLE

```sql
REINDEX TABLE public.orders;
```

Table scope rebuilds applicable indexes associated with the table. Associated TOAST indexes are also included according to PostgreSQL REINDEX semantics.

Use table scope only when rebuilding the applicable index set is justified.

## 8.17.40 REINDEX INDEX

For one confirmed problem index, targeted `REINDEX INDEX` or `REINDEX INDEX CONCURRENTLY` is normally preferable to table-level maintenance.

Production maintenance should use the smallest justified scope.

## 8.17.41 Schema Scope

`REINDEX SCHEMA` can affect many indexes and associated TOAST-index work can expand the true maintenance scope. Treat schema-wide reindexing as a substantial maintenance event.

## 8.17.42 Database Scope

Database-level reindexing can rebuild a large number of indexes and should be treated as major maintenance. System catalog indexes are handled separately through system reindexing.

## 8.17.43 System Catalog Indexes

`REINDEX SYSTEM` is a specialized administrative operation for system-catalog indexes and belongs to a separate recovery procedure.

Do not include system-catalog reindexing in routine application-index automation. `REINDEX SYSTEM CONCURRENTLY` is not supported.

## 8.17.44 Temporary Tables

For temporary tables PostgreSQL uses the non-concurrent rebuild path because other sessions cannot access the temporary relation. Concurrent rebuilding provides no availability benefit.

## 8.17.45 Partitioned Tables and Indexes

A logical partitioned index can represent physical indexes distributed across partitions. Maintenance should be evaluated at the actual child-index level where appropriate.

Detailed partition-maintenance strategy is covered in Section 8.19.

## 8.17.46 Fillfactor Changes

Changing B-tree `fillfactor` can justify a rebuild so the new physical structure reflects the target setting.

Do not lower fillfactor generically. Lower fillfactor deliberately leaves more page headroom and can increase initial index size; it should be justified by workload behavior.

## 8.17.47 Tablespace Migration

REINDEX can participate in moving index storage to another tablespace, combining structural rebuild with storage-placement change.

For broad REINDEX scopes, validate exact tablespace semantics for the deployed PostgreSQL version.

## 8.17.48 `reindexdb`

PostgreSQL provides `reindexdb` as an administrative wrapper around REINDEX operations. It supports different scopes and relevant concurrent workflows.

Utility options and parallel behavior are version-sensitive. Validate exact PostgreSQL 18 options before incorporating them into automation.

## 8.17.49 Parallel Maintenance

Parallel rebuild work can reduce total batch duration but increases CPU, I/O, WAL, replication pressure, and connection usage.

More jobs do not provide free speed. Parallelism must be capacity-tested.

## 8.17.50 Periodic REINDEX

Periodic REINDEX can be justified for demonstrated recurring workload patterns, especially where B-tree physical degradation repeatedly produces measurable cost.

It should be evidence-based rather than indiscriminately calendar-driven across all production indexes.

## 8.17.51 Do Not Blanket-Reindex Production

Avoid universal policies such as `REINDEX DATABASE every Sunday` or `rebuild every index monthly` without workload evidence.

A calendar is not evidence of index degradation.

## 8.17.52 Remove or Redesign Before Rebuilding

Before rebuilding an inefficient index, ask whether the index should exist.

A required but persistently inefficient index may be a rebuild candidate. An unnecessary or duplicate index should be routed through governance and dependency review instead of being rebuilt.

## 8.17.53 Root Cause Before Rebuild

Potential causes of recurring B-tree inefficiency include skewed delete patterns, high update/version churn, sparse surviving key ranges, low HOT eligibility, long-running transactions, maintenance backlog, workload contraction, index design, and fillfactor/workload mismatch.

Ask whether the same workload will recreate the inefficient structure after REINDEX.

## 8.17.54 Benefit Duration

Quantify current size, expected rebuilt size, potentially reclaimable capacity, expected regrowth, and expected duration of benefit.

Reclaimable bytes alone are insufficient.

## 8.17.55 Production Classification

### Class A — Healthy / No REINDEX

No material structural problem is established. **Action:** Monitor.

### Class B — Cleanup or Workload Root Cause Unresolved

Persistent inefficiency exists, but the underlying cause remains active. **Action:** Correct the cause and reassess.

### Class C — Standard REINDEX Candidate

Rebuild is justified and write blocking is acceptable within an approved maintenance window. **Action:** Plan standard REINDEX.

### Class D — Concurrent REINDEX Candidate

Rebuild is justified, but normal DML must remain available. **Action:** Plan `REINDEX CONCURRENTLY` with additional capacity and transaction-wait controls.

### Class E — Remove or Redesign Instead

The index is unnecessary, duplicative, or structurally inappropriate. **Action:** Route through index-governance review.

### Integrity Escalation — Suspected Corruption

Correctness or structural integrity is in question. **Action:** Escalate through the integrity/corruption incident path.

## 8.17.56 Standard REINDEX Decision

Standard REINDEX is generally appropriate when a rebuild is required, write blocking is acceptable, an approved maintenance window exists, and the simpler rebuild path is preferable.

## 8.17.57 Concurrent REINDEX Decision

Concurrent REINDEX is generally appropriate when a rebuild is required, normal DML must continue, longer duration is acceptable, additional resource load is acceptable, and transaction waits are understood.

## 8.17.58 Four Production Gates

### Gate 1 — Evidence

Is REINDEX actually required?

### Gate 2 — Dependency

Is the index required, and what depends on it?

### Gate 3 — Availability

Can writes block, or must normal DML continue?

### Gate 4 — Capacity

Can storage, CPU, I/O, WAL, and replicas safely sustain the rebuild?

Only when all required gates pass should execution proceed.

## 8.17.59 Go/No-Go Model

Proceed only when the problem is proven, the index role is understood, the index remains required, root cause is understood, the rebuild method is selected, blocking/waiting risk is acceptable, disk is sufficient, CPU/I/O capacity is acceptable, WAL capacity is sufficient, replicas are healthy, monitoring is prepared, and failure recovery is understood.

Otherwise the decision is **NO-GO**.

## 8.17.61 Monitoring During REINDEX

Monitor PostgreSQL through `pg_stat_progress_create_index`, `pg_stat_activity`, and `pg_locks`.

Monitor CPU, memory, IOPS, throughput, storage latency, queue depth, free disk, WAL generation, archive health, replication slots, replica receive/replay lag, application latency, transaction latency, error rate, connection-pool pressure, timeouts, and retries.

Treat REINDEX as an end-to-end service event.

## 8.17.62 Abort and Escalation Criteria

Define thresholds before execution. Examples include free disk below the approved margin, critical WAL accumulation, replica lag beyond HA/RPO limits, severe storage latency, unexpected writer blocking, application error-rate escalation, concurrent rebuild failure, unexpected invalid-index state, or infrastructure instability.

Threshold values must be environment-specific.

## 8.17.63 Post-Rebuild Correctness Validation

Verify that the expected index exists and is valid, constraints remain intact, replica identity remains intact, application reads and writes succeed, no unexpected invalid transient index remains, and database logs are clean.

A smaller index is not sufficient proof of successful maintenance.

## 8.17.64 Post-Rebuild Performance Validation

Verify index size, query plans, query latency, application latency, storage latency, IOPS, throughput, WAL normalization, and replica catch-up.

Compare actual results with the maintenance hypothesis.

## 8.17.65 Before/After Size Evidence

```sql
SELECT
    c.oid::regclass AS index_name,
    pg_size_pretty(pg_relation_size(c.oid)) AS index_size
FROM pg_class AS c
WHERE c.oid = 'public.orders_created_at_idx'::regclass;
```

Document before size, expected after size, actual after size, estimated reclaimable capacity, and actual reclaimed capacity.

## 8.17.66 Example — Standard REINDEX Candidate

A confirmed 180 GB persistently bloated index whose root cause is corrected, with an offline application window, sufficient disk headroom, and healthy replicas is a **Class C — Standard REINDEX Candidate**.

## 8.17.67 Example — Concurrent REINDEX Candidate

A confirmed 650 GB persistently bloated index on a 24x7 write-heavy application, with sufficient disk headroom, controlled long transactions, and healthy replicas is a **Class D — Concurrent REINDEX Candidate**.

## 8.17.68 Example — No REINDEX

A 1.2 TB index whose logical growth is proportional, physical evidence is healthy, usage is high, and storage pressure is acceptable is a **Class A — Healthy / No REINDEX** finding.

## 8.17.69 Example — Remove Instead of Rebuild

A 400 GB index with negligible usage, no constraint role, no replica-identity role, and a confirmed duplicate definition is a **Class E — Remove or Redesign Instead** finding.

## 8.17.70 Example — Root Cause First

A 900 GB index with significant bloat, persistent long transactions, severe VACUUM backlog, and high storage latency is **Class B — Cleanup or Workload Root Cause Unresolved**. Correct those conditions before rebuilding and then reassess persistent inefficiency.

## 8.17.71 Example — Suspected Corruption

When query errors and integrity evidence suggest corruption, classify the incident as **Integrity Escalation — Suspected Corruption**. Correctness takes precedence over storage-reclamation economics.

## 8.17.72 Example — Failed Concurrent Rebuild

If `REINDEX CONCURRENTLY` fails and a transient invalid index remains, stop automatic cleanup, identify original and transient indexes, inspect `pg_index`, verify constraints and replica identity, determine `_ccnew` versus `_ccold` state, confirm which index is valid, remove only the confirmed obsolete/invalid object, correct the failure cause, and retry only after preflight passes.

## 8.17.76 Key Takeaway

The REINDEX decision should first distinguish suspected corruption from ordinary physical inefficiency. For non-corruption cases, prove the physical problem, verify the index is still required, understand the root cause, determine whether writes may block, select standard or concurrent REINDEX accordingly, pass capacity and availability gates, execute through an approved change, and validate afterward.

> **Do not REINDEX merely because an index is large, old, or associated with a single poor diagnostic metric. Rebuild when a correctness problem or persistent physical inefficiency has been established, the index is still required, and the selected method provides sufficient benefit to justify its locking, transaction-wait, storage, CPU, I/O, WAL, replication, and availability cost.**

The goal is to keep required indexes correct, valid, space-efficient, workload-appropriate, and operationally sustainable.
