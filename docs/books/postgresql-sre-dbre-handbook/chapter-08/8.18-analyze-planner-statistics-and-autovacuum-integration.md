**Edition:** Revised Final / Canonical

## 8.18.1 Purpose

PostgreSQL query planning depends heavily on statistics describing table cardinality and data distribution. `ANALYZE` is planner-maintenance infrastructure: it samples data and refreshes the statistical model used for selectivity, cardinality, join ordering, scan selection, aggregation, and other planning decisions.

> **ANALYZE does not clean dead tuples. Its purpose is to keep PostgreSQL's statistical view of data sufficiently accurate for reliable execution-plan decisions.**

## 8.18.2 VACUUM and ANALYZE Solve Different Problems

`VACUUM` maintains MVCC storage state through dead-tuple cleanup, reusable-space management, visibility maintenance, and freezing. `ANALYZE` samples data and updates planner statistics. They are often run together, but they solve different operational problems.

## 8.18.3 What ANALYZE Collects

Depending on column type and distribution, statistics can include null fraction, average width, estimated distinct values, most-common values and frequencies, histograms, and correlation. These statistics are approximate by design; fresh statistics do not imply exact estimates.

## 8.18.4 `pg_statistic` and `pg_stats`

Raw planner statistics are stored in `pg_statistic`. Direct access is restricted because statistics can reveal information about table contents. For normal operational inspection, prefer `pg_stats`.

```sql
SELECT
    schemaname,
    tablename,
    attname,
    null_frac,
    n_distinct,
    most_common_vals,
    most_common_freqs,
    histogram_bounds,
    correlation
FROM pg_stats
WHERE schemaname = 'public'
  AND tablename = 'orders';
```

Treat value-distribution statistics as potentially sensitive operational metadata.

## 8.18.5 Planner Statistics Are Estimates

Fresh statistics can still produce imperfect cardinality estimates when distributions are skewed, columns are correlated, expressions transform values, data changes rapidly, statistics targets are too low, or predicates involve related columns.

## 8.18.6 Why Cardinality Estimation Matters

Large differences between estimated and actual rows can lead to poor join algorithms, scan choices, join order, aggregation strategies, and memory assumptions. Cardinality-estimation quality is therefore one of the first areas to inspect when a query plan appears structurally wrong.

## 8.18.7 Using EXPLAIN to Validate Estimates

Use `EXPLAIN` to inspect planner estimates without executing a query. Where safe, `EXPLAIN (ANALYZE, BUFFERS)` can compare estimates with actual execution.

> **`EXPLAIN ANALYZE` executes the statement.**

Do not use it casually against production `INSERT`, `UPDATE`, `DELETE`, `MERGE`, or other statements with side effects.

## 8.18.8 Evidence of Statistics Problems

Evidence can include major estimated-versus-actual row differences combined with poor join choices, unexpected scans, unstable plans, recent bulk loads or large deletes, strong skew, or materially changed distributions. A bad plan alone is not proof of stale statistics.

## 8.18.9 Manual ANALYZE

```sql
ANALYZE public.orders;
```

For targeted columns:

```sql
ANALYZE public.orders (customer_id, status, created_at);
```

Use the smallest justified scope when troubleshooting a specific estimation problem.

## 8.18.10 ANALYZE Locking and Resource Impact

`ANALYZE` requires a read-oriented lock and normally runs concurrently with ordinary non-DDL application activity. It is much less disruptive than `VACUUM FULL`, `CLUSTER`, table rewrites, or standard `REINDEX`. It still consumes CPU, memory, reads, shared-buffer activity, and storage I/O, so large maintenance passes remain capacity-sensitive.

## 8.18.11 Automatic ANALYZE

Autovacuum infrastructure also performs automatic `ANALYZE`. PostgreSQL tracks inserted, updated, and deleted tuples and schedules statistics refresh when the analyze trigger is reached.

## 8.18.12 Automatic ANALYZE Trigger Formula

The trigger is based on:

```text
autovacuum_analyze_threshold
+
autovacuum_analyze_scale_factor × number of tuples
```

PostgreSQL 18 defaults are `autovacuum_analyze_threshold = 50` and `autovacuum_analyze_scale_factor = 0.1`, or approximately 50 modified rows plus 10% of table size.

## 8.18.13 Large-Table Problem

For a one-billion-row table, a 0.10 scale factor contributes roughly 100 million modifications to the trigger. For large, high-value tables, that can permit statistics to become materially stale before automatic analysis runs.

## 8.18.14 Per-Table Analyze Tuning

```sql
ALTER TABLE public.orders
SET (
    autovacuum_analyze_scale_factor = 0.01,
    autovacuum_analyze_threshold = 5000
);
```

This is illustrative, not universal. Tune from table size, modification rate, distribution volatility, query sensitivity, and available maintenance capacity.

## 8.18.15 Do Not Copy Analyze Settings Between Tables

A multi-terabyte high-churn fact table and a small reference table do not have the same statistics-refresh requirements. Avoid applying one analyze scale factor or threshold everywhere without workload evidence.

## 8.18.16 Statistics Freshness Observability

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_mod_since_analyze,
    last_analyze,
    last_autoanalyze,
    analyze_count,
    autoanalyze_count
FROM pg_stat_all_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n_mod_since_analyze DESC;
```

Use these fields as evidence about maintenance behavior rather than as isolated pass/fail indicators.

## 8.18.17 Freshness Is Workload-Relative

Do not create a universal rule such as `last_analyze > 24 hours => stale`. A read-only table can remain representative for months, while a fast-changing table can become stale in minutes. The key question is whether the distribution has changed enough to affect planner decisions.

## 8.18.18 Bulk Loads

After major `COPY`, ETL, migration, or bulk-insert operations, explicitly analyze when critical query traffic will begin before automatic maintenance is likely to catch up.

## 8.18.19 Large Deletes

Large deletes can materially change cardinality, value frequencies, selectivity, and distinct-value distribution. `ANALYZE` refreshes planner knowledge; it does not compact the table or reclaim operating-system space.

## 8.18.20 Large Updates

Large updates can dramatically change value distribution while row count remains almost unchanged. Stable table size does not imply statistically stable data.

## 8.18.21 Data Distribution Matters More Than Row Count Alone

A predicate value moving from a tiny fraction of rows to a large fraction can invalidate old selectivity assumptions even when total row count changes little. Statistics maintenance must therefore account for distribution change, not only row-count change.

## 8.18.22 `default_statistics_target`

Higher statistics targets can improve estimates for difficult distributions but increase analysis work, statistics size, and potentially planning cost. Do not raise the global target as the first response to one poorly estimated column.

## 8.18.23 Per-Column Statistics Target

```sql
ALTER TABLE public.orders
ALTER COLUMN customer_id
SET STATISTICS 1000;

ANALYZE public.orders;
```

The value is illustrative. Prefer targeted changes where evidence identifies a specific column.

## 8.18.24 Statistics Target Is Not a Knob to Maximize

Higher is not automatically better. Increase statistical detail when evidence shows that the current representation is insufficient for important planner decisions.

## 8.18.25 Correlated Columns

Ordinary statistics are largely per-column. Related predicates such as `country = 'US' AND state = 'NC'` violate independence assumptions and can produce poor combined selectivity estimates.

## 8.18.26 Extended Statistics

`CREATE STATISTICS` can model selected relationships using functional dependencies, multivariate distinct counts, multivariate most-common-value lists, and expression statistics.

## 8.18.27 Functional Dependency Example

```sql
CREATE STATISTICS orders_customer_region_stats
    (dependencies)
ON customer_id, region_id
FROM public.orders;

ANALYZE public.orders;
```

Creating the statistics object does not populate it; `ANALYZE` must collect the data.

## 8.18.28 Multivariate MCV Example

```sql
CREATE STATISTICS orders_status_channel_stats
    (mcv)
ON status, channel
FROM public.orders;

ANALYZE public.orders;
```

Use this when recurring evidence shows correlated categorical combinations are misestimated.

## 8.18.29 Extended Statistics Are Targeted

PostgreSQL cannot create extended-statistics objects for every possible column combination. Identify candidates from recurring cardinality errors, workload patterns, schema knowledge, and bad plans.

## 8.18.30 Extended Statistics Limitations

Do not treat extended statistics as a universal join-cardinality solution. Their usefulness is bounded by the planner cases supported by the deployed PostgreSQL version.

## 8.18.31 Expression Statistics

Expression statistics can help when transformed values are not modeled adequately by base-column statistics. Create them only for demonstrated estimation problems.

## 8.18.32 Partitioned Tables

`ANALYZE` can gather parent-level statistics by sampling rows from partitions. Parent-level statistics require special operational attention because automatic maintenance of partitions does not guarantee fresh statistics on the partitioned parent.

## 8.18.33 Partitioned Parents and Autovacuum

Autovacuum does not process partitioned tables themselves, although it processes their ordinary table partitions. Manual `ANALYZE` of the partitioned parent can therefore be necessary when the distribution across partitions changes significantly. Detailed partition maintenance is covered in Section 8.19.

## 8.18.34 Inheritance Parents

Inheritance parents can have a similar gap when only children receive modifications. Manual `ANALYZE` may be needed to refresh hierarchy-wide statistics.

## 8.18.35 Empty Tables

When a table being analyzed is completely empty, PostgreSQL does not replace existing statistics with a new empty set; existing statistics can remain. Account for this during truncate/reload and transient-empty-state troubleshooting.

## 8.18.36 Foreign Tables

Foreign tables are analyzed only when explicitly selected, and the foreign-data wrapper must support `ANALYZE`. Do not assume normal automatic statistics behavior applies to every foreign table.

## 8.18.37 Materialized Views

`ANALYZE` can collect statistics for materialized views. After a large `REFRESH MATERIALIZED VIEW`, evaluate whether statistics should be refreshed before critical query workloads resume.

## 8.18.38 `VACUUM ANALYZE`

```sql
VACUUM (ANALYZE) public.orders;
```

This combines two maintenance responsibilities. Needing a statistics refresh does not automatically mean vacuum is also required; use standalone `ANALYZE` when planner statistics are the actual problem.

## 8.18.39 Post-REINDEX Statistics

Do not automatically run `ANALYZE` after every `REINDEX`. Reindexing changes physical index structure; analyzing refreshes statistical representation of data distributions. Treat these as separate maintenance decisions.

## 8.18.40 Post-`VACUUM FULL` Statistics

A physical rewrite and a statistics refresh are separate concepts. Review statistics freshness as part of post-maintenance validation rather than assuming a rewrite proves statistics are current.

## 8.18.41 Progress Reporting

PostgreSQL exposes active analysis through `pg_stat_progress_analyze`. Use it for large tables, broad manual maintenance, maintenance-window monitoring, and investigation of apparently slow analysis.

## 8.18.42 Progress Monitoring

Use the documented PostgreSQL 18 fields in `pg_stat_progress_analyze`, including relation identity, phase, sampled/processed block information, and extended-statistics progress where exposed. Progress fields are version-sensitive; interpret them against the deployed major version.

## 8.18.43 ANALYZE Resource Cost

Sampling is not free. Concurrent analysis across large environments can create storage reads, CPU load, cache displacement, and contention with application scans. Schedule with infrastructure headroom.

## 8.18.44 `BUFFER_USAGE_LIMIT`

PostgreSQL 18 supports `BUFFER_USAGE_LIMIT` for controlling the Buffer Access Strategy ring used by `ANALYZE`. Use it only after validating workload behavior and cache impact; larger settings can improve maintenance speed while also evicting useful shared-buffer pages.

## 8.18.45 `SKIP_LOCKED`

`ANALYZE (SKIP_LOCKED)` can avoid waiting when a relation cannot initially be locked. It does not guarantee that every later lock or sampling action will be nonblocking. Any skipped relation remains statistically unrefreshed and requires follow-up.

## 8.18.46 Ownership and Privileges

PostgreSQL 18 ordinarily requires `MAINTAIN` privilege to analyze a table, while documented database-owner behavior also applies. Automation should use minimum required privileges rather than broad superuser access.

## 8.18.47 Statistics and Sensitive Data

Statistics can expose common values, frequencies, histograms, and distributions. Avoid indiscriminately exporting detailed planner statistics to broadly accessible monitoring systems.

## 8.18.48 Detecting Autoanalyze Lag

A table is an analyze-lag candidate when modifications accumulate rapidly, `last_autoanalyze` is old relative to churn, estimates degrade, and automatic analysis cannot keep pace. This classification requires workload context, not a universal threshold.

## 8.18.49 Statistics Health Classification

**Class A — Healthy:** statistics maintenance keeps pace with distribution change. Monitor.

**Class B — Autoanalyze Lag:** statistics become stale before automatic analysis catches up. Tune per-table analyze thresholds and scale factors.

**Class C — Manual Refresh Required:** a bulk load, transformation, partition operation, or maintenance event requires immediate refresh. Run approved targeted `ANALYZE`.

**Class D — Statistics Detail Insufficient:** statistics are fresh but estimates remain poor. Evaluate per-column targets or extended statistics.

**Class E — Query/Model Problem:** statistics are reasonably accurate but the plan remains poor. Continue query, index, schema, or planner investigation instead of repeatedly analyzing.

## 8.18.50 Production Decision Model

```text
poor plan
   |
   v
row estimates wrong?
  /          \
 no          yes
 |            |
 v            v
other       statistics fresh?
cause          /       \
              no       yes
              |         |
              v         v
           ANALYZE   enough detail?
                       /       \
                      no       yes
                      |         |
                      v         v
              target/extended  investigate
                statistics     other cause
```

## 8.18.51 Do Not Use ANALYZE as a Generic Performance Fix

Slow queries can result from storage latency, locking, CPU saturation, poor indexing, inefficient SQL, memory pressure, bad joins, bloat, or concurrency. Use `ANALYZE` when planner statistics are plausibly involved, not as a universal response to latency.

## 8.18.52 Production Preflight for Manual ANALYZE

```text
[ ] Target relation confirmed
[ ] Reason for manual ANALYZE documented
[ ] Recent distribution change reviewed
[ ] last_analyze checked
[ ] last_autoanalyze checked
[ ] n_mod_since_analyze reviewed
[ ] Estimated-versus-actual evidence reviewed
[ ] Table/partition scope selected
[ ] Production workload reviewed
[ ] I/O headroom acceptable
[ ] Privileges validated
[ ] Progress monitoring prepared
[ ] Post-ANALYZE plan validation prepared
```

## 8.18.53 Post-ANALYZE Validation

Do not stop when the command completes. Confirm statistics timestamps changed, row estimates improved where expected, plan shape changed appropriately if statistics were causal, and workload performance improved. If estimates remain poor, investigate targets, correlation, extended statistics, expressions, partition statistics, and query structure.

## 8.18.54 Example — Large Table Autoanalyze Lag

An 800-million-row high-churn table with rapidly increasing `n_mod_since_analyze`, old `last_autoanalyze`, and worsening estimates is a **Class B — Autoanalyze Lag** candidate. Evaluate a lower per-table scale factor and appropriate threshold instead of relying on repeated emergency manual analysis.

## 8.18.55 Example — Bulk Load

A table growing from 50 million to 250 million rows immediately before critical reporting is a **Class C — Manual Refresh Required** case. Run targeted `ANALYZE` after the controlled load rather than waiting for the normal automatic cycle.

## 8.18.56 Example — Correlated Columns

Fresh single-column statistics combined with a large estimate error on strongly correlated predicates is a **Class D — Statistics Detail Insufficient** case. Evaluate an appropriate extended-statistics object instead of repeatedly analyzing with the same statistical definition.

## 8.18.57 Example — ANALYZE Is Not the Problem

Fresh statistics, accurate row estimates, and a reasonable plan combined with severe storage latency is a **Class E — Query/Model Problem** from the statistics-maintenance perspective. Do not keep rerunning `ANALYZE`; investigate the storage bottleneck.

## 8.18.58 Production Principles

1. **ANALYZE maintains planner statistics; VACUUM maintains MVCC storage state.**
2. **Planner statistics remain approximate even when fresh.**
3. **Cardinality estimation strongly affects plan quality.**
4. **Use `pg_stats` for ordinary statistics inspection.**
5. **Treat `pg_statistic` as sensitive internal metadata.**
6. **Do not assume a bad plan means stale statistics.**
7. **Compare estimated and actual rows when safe and appropriate.**
8. **Remember that `EXPLAIN ANALYZE` executes the statement.**
9. **Automatic ANALYZE is part of autovacuum infrastructure.**
10. **Automatic-analyze triggering uses a base threshold plus scale factor.**
11. **Large tables may require per-table analyze tuning.**
12. **Do not copy analyze settings blindly between tables.**
13. **Statistics freshness is workload-relative.**
14. **Bulk loads can justify immediate ANALYZE.**
15. **Large DELETE/UPDATE operations can materially change distributions.**
16. **Stable table size does not imply stable distribution.**
17. **Raise statistics targets only when evidence supports it.**
18. **Prefer targeted per-column changes over unnecessary global increases.**
19. **Use extended statistics for demonstrated cross-column estimation problems.**
20. **Extended-statistics objects require ANALYZE to populate data.**
21. **Extended statistics do not solve every join-estimation problem.**
22. **Partitioned-parent statistics require special attention.**
23. **Automatic maintenance of partitions does not guarantee fresh parent statistics.**
24. **Inheritance parents can have similar statistics-refresh gaps.**
25. **Foreign tables require explicit and FDW-supported ANALYZE.**
26. **Materialized views may need statistics refresh after large refreshes.**
27. **`VACUUM ANALYZE` combines two separate maintenance responsibilities.**
28. **REINDEX does not automatically mean ANALYZE is required.**
29. **Physical table rewrites and statistics freshness are separate concepts.**
30. **Use `pg_stat_progress_analyze` for long-running ANALYZE monitoring.**
31. **ANALYZE still consumes CPU and I/O.**
32. **`SKIP_LOCKED` requires follow-up for skipped relations.**
33. **Use minimum required maintenance privileges.**
34. **Do not expose sensitive value-distribution statistics unnecessarily.**
35. **Validate improved estimates after ANALYZE when statistics were the suspected cause.**
36. **Do not use ANALYZE as a generic response to every slow query.**

## 8.18.60 Key Takeaway

The central SRE/DBRE rule is:

> **Do not run ANALYZE simply because a query is slow. Run or tune ANALYZE when evidence shows PostgreSQL's planner statistics are stale, insufficiently detailed, or not being refreshed quickly enough for the rate and nature of data-distribution change.**

The objective is to keep planner statistics fresh enough, detailed enough, targeted enough, and operationally affordable to support reliable execution-plan decisions.
