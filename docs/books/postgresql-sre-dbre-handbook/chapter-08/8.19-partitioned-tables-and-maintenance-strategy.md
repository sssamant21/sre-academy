# 8.19 — Partitioned Tables and Maintenance Strategy

**Edition:** Revised Final / Canonical Edition  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **CANONICAL**

## 8.19.1 Purpose

Partitioning changes the operational unit of PostgreSQL maintenance. A partitioned workload is a hierarchy consisting of a logical partitioned parent and physical partitions that can have different vacuum, statistics, transaction-age, bloat, index, and lifecycle requirements.

> **Operate partitioned tables as hierarchies of independently maintained physical relations while separately protecting parent-level statistics, partition coverage, transaction-age safety, retention correctness, and operational dependencies.**

## 8.19.2 Partitioned Parent vs. Physical Partitions

A declaratively partitioned parent primarily represents partitioning metadata and row-routing rules. Rows reside in physical partitions. Maintenance must distinguish parent-level hierarchy statistics, bounds, lifecycle, routing, and partitioned indexes from physical-partition dead tuples, vacuum, analyze, freezing, heap bloat, and physical indexes.

## 8.19.3 Partitioning Changes Maintenance; It Does Not Remove It

Partitioning can reduce maintenance scope and improve control over vacuum duration, statistics, index maintenance, bloat remediation, retention, archival, maintenance windows, and recovery scope. It does not eliminate maintenance; it changes the unit on which maintenance is performed.

## 8.19.4 Maintenance Must Follow the Partition Workload

Partitions can have radically different workloads. Active partitions may receive continuous INSERT, UPDATE, and DELETE traffic while historical partitions are nearly immutable. The same maintenance configuration should not automatically be applied to every partition.

## 8.19.5 Operational Lifecycle Classification

A useful operational model classifies partitions as HOT, WARM, COLD, ARCHIVE CANDIDATE, or EXPIRED. These are SRE/DBRE lifecycle classifications rather than PostgreSQL object types.

## 8.19.6 Hot-Partition Strategy

Monitor `n_live_tup`, `n_dead_tup`, `n_mod_since_analyze`, `last_vacuum`, `last_autovacuum`, `last_analyze`, and `last_autoanalyze` together with transaction age, storage growth, index health, and application workload. Production automation should discover partition relationships through PostgreSQL catalogs rather than naming conventions alone.

## 8.19.7 Per-Partition Autovacuum Tuning

Physical partitions can have different autovacuum settings. Tune from partition size, modification rate, dead-tuple generation, statistics sensitivity, and maintenance capacity. Do not copy one tuning profile blindly across the hierarchy.

## 8.19.8 Partition Size Is an Operational Design Decision

Very large partitions can recreate long vacuum, large-index, recovery, I/O, and blast-radius problems. Extremely small partitions can increase relation count, catalog overhead, planning overhead, DDL overhead, and orchestration complexity. Choose partition granularity appropriate to workload, retention, and maintenance lifecycle.

## 8.19.9 Partition Count Is a Capacity Dimension

Partition count affects catalogs, query planning, monitoring, DDL, maintenance orchestration, backup/restore, incident investigation, and automation. Track partition-count growth as capacity data and avoid inventing a universal maximum.

## 8.19.10 Autovacuum and Partitioned Parents

Autovacuum processes ordinary table partitions but does not process the partitioned parent itself in the same way. Healthy child partitions therefore do not automatically imply healthy parent-level statistics.

## 8.19.11 Parent-Level ANALYZE

When hierarchy-level planner statistics require refresh, use an approved targeted `ANALYZE` on the parent. PostgreSQL can sample the partition hierarchy to build parent-level statistics. Do not infer parent-statistics freshness solely from child `last_autoanalyze` values.

## 8.19.12 VACUUM and Partition Hierarchies

When a partitioned table is specified to `VACUUM`, PostgreSQL can process its partitions unless `ONLY` restricts scope. Because physical cleanup work belongs to physical partitions, determine whether the requirement concerns one partition, several partitions, or the complete hierarchy before execution.

> **Know the recursive scope of a maintenance command before executing it against a partitioned parent.**

## 8.19.13 Targeted Partition VACUUM

Maintenance can be scoped directly to a physical partition. Combine VACUUM and ANALYZE only when both dead-tuple/storage maintenance and statistics refresh are justified. Prefer the smallest justified scope.

## 8.19.14 Partition ATTACH Lifecycle

A controlled lifecycle is: create standalone table, load data, validate data, prepare partition constraint, ATTACH PARTITION, and validate the hierarchy. Attaching a large populated relation can materially alter hierarchy-level distribution, so validate new-partition statistics, parent statistics, important query estimates, and pruning.

## 8.19.15 ATTACH Validation Scans

PostgreSQL may scan a candidate relation during ATTACH to verify its rows satisfy the intended bound. For large pre-populated candidates, an appropriate validated matching CHECK constraint can allow PostgreSQL to prove compatibility and potentially avoid the validation scan.

## 8.19.16 DEFAULT Partition and ATTACH

If a DEFAULT partition exists, PostgreSQL can need to prove that rows for a newly attached range are not already in the DEFAULT partition. A large DEFAULT partition can therefore make lifecycle DDL expensive. Appropriate constraints can sometimes avoid unnecessary validation scans.

## 8.19.17 DEFAULT Partition Risk

A DEFAULT partition can protect write availability but also conceal missing-partition or routing failures.

> **A DEFAULT partition is both a routing safety mechanism and an operational debt detector. Unexpected growth should be treated as a partition-lifecycle alert.**

## 8.19.18 DEFAULT Partition Monitoring

Monitor row count, relation size, growth rate, recent inserts, and accumulated-data age. Unexpected growth should trigger investigation of missing future partitions, bounds, application data, automation failures, and unexpected key values.

## 8.19.19 DETACH PARTITION

DETACH can support archival, retention, maintenance isolation, export, and lifecycle transitions. Before detaching, review locking, dependencies, application queries, retention requirements, backup/archive state, downstream consumers, and post-detach ownership.

## 8.19.20 DETACH PARTITION CONCURRENTLY

Where supported and appropriate, concurrent detach can reduce lock impact but is not operationally free. PostgreSQL 18 restrictions include transaction-block and DEFAULT-partition constraints, waits for transactions using the hierarchy, multi-phase behavior, and possible `FINALIZE` recovery after interruption. Verify exact state before recovery DDL.

## 8.19.21 DETACH Before Destructive Removal

Where appropriate, use ACTIVE → DETACH → validate → archive/export → retention approval → DROP to create an intermediate validation point before irreversible removal.

## 8.19.22 Partition Removal vs. Massive DELETE

When retention boundaries align with partitions, partition-level removal can avoid the dead-tuple population created by equivalent row-by-row deletion and reduce subsequent vacuum/index pressure.

## 8.19.23 DROP Is Destructive

Before destructive removal verify exact relation identity, catalog-verified partition bounds, retention policy, legal/compliance requirements, backup/archive requirements, dependencies, replication/downstream implications, recovery requirements, and approval. Never derive retention eligibility solely from a partition name.

## 8.19.24 Partition Rotation

Manage future, hot, warm, cold, archive-candidate, detached/archived, and expired states as a controlled lifecycle rather than emergency DDL.

## 8.19.25 Pre-Create Future Partitions

Automation should verify future partitions, non-overlapping and intended gap-free bounds, indexes, ownership, grants, storage configuration, and tablespace policy where applicable. Future-coverage horizons are workload-specific.

## 8.19.26 Future-Coverage Decision Model

Compare current time and partition boundaries against required future coverage. If coverage is insufficient, alert or prepare and validate the required partition before the boundary arrives.

## 8.19.27 Freeze Age Is Per Physical Relation

Historical partitions still require transaction-ID correctness maintenance. Monitor relation XID age and associated TOAST age where applicable rather than assuming cold relations are maintenance-free.

## 8.19.28 Cold Does Not Mean Maintenance-Free

> **Immutable business data is not equivalent to maintenance-free PostgreSQL storage.**

Anti-wraparound maintenance is a correctness requirement rather than merely a performance optimization.

## 8.19.29 Multixact Age

Where workloads create multixacts, monitor `relminmxid` using `mxid_age()` as well as transaction-ID age. Chapter 8's earlier multixact and anti-wraparound principles continue to apply to physical partitions.

## 8.19.30 Indexes in a Partition Hierarchy

A partitioned index on the parent represents an index hierarchy, while physical indexes exist on physical partitions. Different partitions can develop very different index churn and bloat.

## 8.19.31 Identify Index Type Before Maintenance

Do not confuse a partitioned parent index with a physical leaf-partition index. Concurrent maintenance capabilities differ. Identify the exact relation, relation type, hierarchy relationship, physical size, and problem evidence before selecting maintenance.

## 8.19.32 Targeted REINDEX

When evidence identifies one physical partition index as the problem, use the smallest justified scope. Apply the locking, capacity, WAL, replication, runtime, failure-recovery, and post-validation controls established in Section 8.17.

## 8.19.33 Building Indexes Across Existing Partitions

Partitioned-index operations require special planning. For large hierarchies, controlled workflows can build or maintain physical partition indexes, validate them, attach them to the partitioned-index hierarchy where appropriate, and then validate parent index state. Verify exact PostgreSQL-version semantics before production execution.

## 8.19.34 Bloat Is Partition-Specific

Inspect partition size, dead tuples, heap condition, index size, index condition, write churn, and bloat evidence per physical partition. Hierarchy-level totals can conceal a single unhealthy hot partition or unexpectedly large DEFAULT partition.

## 8.19.35 Partition Discovery

Prefer catalog-based discovery. `pg_inherits` represents direct parent-child relationships. Multi-level partitioning requires recursive traversal rather than assuming a single hierarchy level.

## 8.19.36 Recursive Partition Inventory

Operational tooling for multi-level partitioning should preserve root, parent, child, hierarchy depth, partition bounds, and relation type so automation knows exactly which physical object it is evaluating.

## 8.19.37 Partition Size Inventory

Use raw byte values from PostgreSQL size functions for thresholds, trending, calculations, and alerting. Human-readable formatting is useful for reports but should not be the primary machine metric.

## 8.19.38 Partition Health Model

For every physical partition collect identity, parent, bounds, hierarchy depth, lifecycle state, size, row estimate, dead tuples, modifications since analyze, vacuum/analyze history, XID age, multixact age, and index health.

## 8.19.39 Maintenance Matrix

HOT partitions receive high maintenance attention; WARM partitions normal maintenance; COLD partitions correctness-driven maintenance; ARCHIVE candidates validation and lifecycle handling; EXPIRED partitions removal only after approval. This is an operational framework, not a PostgreSQL default policy.

## 8.19.40 Partition Skew

Monitor unexpectedly uneven partition sizes. Possible causes include workload skew, poor boundaries, DEFAULT accumulation, incorrect routing, unexpected key distributions, and lifecycle failures.

## 8.19.41 Partition Pruning Does Not Prove Maintenance Health

Good pruning is a query-planning/execution property. Untouched partitions can still accumulate transaction-age risk, stale statistics, bloat, oversized indexes, and lifecycle problems.

> **Good query pruning is not evidence of hierarchy-wide maintenance health.**

## 8.19.42 Partition DDL and Locking

ATTACH, DETACH, DROP, and ALTER operations are production DDL. Verify exact PostgreSQL 18 locking semantics, identify conflicting workload, define timeout/abort policy, execute through approved controls, and validate afterward.

## 8.19.43 Lock-Timeout Guardrail

A controlled maintenance session can use an appropriate `lock_timeout` where organizational policy permits it. A timeout limits waiting; it does not make unsafe DDL safe.

## 8.19.44 Maintenance Windows

Partitioning can reduce maintenance-window scope by allowing targeted work on one physical partition rather than an entire multi-terabyte hierarchy. Use that advantage intentionally when evidence permits narrow scope.

## 8.19.45 WAL and Replication Impact

Index rebuilds, rewrites, bulk loads, data movement, and retention workflows can affect WAL generation, archive throughput, replica replay, replication slots, storage, network, and recovery objectives even when scoped to a partition.

## 8.19.46 Backup and Recovery

Before destructive lifecycle operations determine whether recovery depends on base backups, PITR, logical exports, object-storage archives, warehouse copies, compliance archives, or downstream systems. Retention policy and recovery policy must agree.

## 8.19.47 Maintenance Automation

Safe automation candidates include partition discovery, hierarchy inventory, future-boundary checks, DEFAULT growth monitoring, size trending, statistics freshness, dead tuples, XID/multixact age, index-health discovery, and lifecycle classification.

## 8.19.48 Automation Safety Boundary

Automate discovery, measurement, trending, classification, alerting, and recommendations aggressively. Keep VACUUM, ANALYZE, REINDEX, ATTACH, and DETACH controlled according to operational policy. Strongly gate DROP, destructive retention, large rewrites, and irreversible lifecycle actions.

> **Destructive partition lifecycle operations must not be triggered solely by simplistic thresholds or partition names.**

## 8.19.49 Production Preflight

Confirm parent and physical targets, relation type, catalog bounds, hierarchy depth, lifecycle state, size, dead tuples, statistics, parent statistics, XID/TOAST age, multixact age, indexes, DEFAULT state, future coverage, workload, locks/timeouts, I/O, WAL/replication, backup/recovery, retention/compliance, dependencies, recovery approach, monitoring, and post-change validation.

## 8.19.50 Post-Maintenance Validation

Validate the state the operation was intended to produce: attachment/detachment, bounds, statistics, dead tuples, freeze age, index state, DEFAULT health, future coverage, replicas, WAL backlog, application queries, and planner estimates as applicable. Operational success is validated system state, not merely a successful SQL return code.

## 8.19.51 Failure Scenario — Missing Future Partition

If partition automation fails and a new boundary arrives, inserts can fail or rows can accumulate in DEFAULT. Controls are pre-creation, coverage validation, boundary alerts, and DEFAULT monitoring.

## 8.19.52 Failure Scenario — Hot-Partition Autovacuum Lag

High UPDATE/DELETE rates can outpace autovacuum. Check blocker horizons, worker activity, per-partition settings, worker capacity, and I/O capacity. Do not simply disable autovacuum.

## 8.19.53 Failure Scenario — Stale Parent Statistics

A large attached partition can leave child statistics healthy while parent statistics remain stale. When evidence confirms this condition, run approved parent ANALYZE and revalidate estimates and plans.

## 8.19.54 Failure Scenario — DEFAULT Partition Explosion

A missing expected partition can cause DEFAULT to absorb traffic, grow rapidly, and make future lifecycle DDL more expensive. Treat unexpected DEFAULT growth as an incident signal.

## 8.19.55 Failure Scenario — Incorrect Retention Removal

Prevent accidental deletion through exact relation identity, catalog-verified bounds, retention approval, backup/archive verification, dependency review, and destructive-action guardrails. Never trust a partition name as the sole retention control.

## 8.19.56 Failure Scenario — Excessive Partition Count

Slow inventory, complex orchestration, expensive DDL, catalog pressure, planning overhead, difficult troubleshooting, and fragile automation can indicate excessive partition granularity. Evaluate lifecycle and partition design before simply adding infrastructure.

## 8.19.57 Failure Scenario — Cold Partition Approaching Freeze Risk

Cold historical partitions can receive little operational attention while XID or multixact age grows. Verify `relfrozenxid`, associated TOAST state, `relminmxid`, autovacuum/anti-wraparound activity, blocker horizons, and controlled maintenance requirements.

## 8.19.58 Production Principles

1. Partitioning changes the unit of maintenance; it does not eliminate maintenance.
2. Treat physical partitions as independent maintenance objects.
3. Treat the partitioned parent as a separate hierarchy-level operational object.
4. Healthy child statistics do not guarantee healthy parent statistics.
5. Understand recursive VACUUM and ANALYZE scope before operating on a parent.
6. Prefer the smallest justified physical maintenance scope.
7. Classify partitions by workload and lifecycle.
8. Do not copy one autovacuum configuration blindly across all partitions.
9. Partition size and count are operational capacity dimensions.
10. Monitor future partition coverage and DEFAULT partitions explicitly.
11. Use catalog-based discovery rather than naming assumptions.
12. Evaluate vacuum, statistics, XID/multixact age, heap, and index health per physical partition.
13. Cold data still requires anti-wraparound correctness.
14. Distinguish partitioned indexes from physical partition indexes before maintenance.
15. ATTACH can require validation scans and DEFAULT-partition consideration.
16. DETACH and DROP have different operational characteristics.
17. Never derive retention eligibility solely from a partition name.
18. Validate backup, recovery, compliance, and downstream requirements before removal.
19. Partition-level maintenance can still affect WAL and replicas.
20. Good pruning does not prove maintenance health.
21. Automate evidence collection aggressively while safety-gating destructive lifecycle actions.
22. Validate resulting system state after maintenance.
23. Design partition maintenance as a lifecycle rather than emergency commands.

## 8.19.59 SRE/DBRE Checklist

Review hierarchy inventory, parent identity, physical partitions, multi-level relationships, bounds, lifecycle state, hot partitions, size/count/skew trends, dead tuples, vacuum/analyze history, modifications, parent statistics, XID/TOAST age, multixact age, index type/health, DEFAULT state, future coverage, per-partition autovacuum settings, maintenance scope, ATTACH/DETACH behavior, DDL locks, WAL/replication, backup/recovery, retention/compliance, destructive-action gates, and post-maintenance validation.

## 8.19.60 Key Takeaway

> **Do not manage a partitioned table as though it were one physical table. Maintain physical partitions according to their individual workload and lifecycle while separately protecting parent-level statistics, partition coverage, transaction-age safety, retention correctness, and operational dependencies.**

The objective is a small maintenance blast radius, predictable lifecycle, healthy active partitions, safe historical partitions, accurate planner statistics, anti-wraparound protection, controlled retention, and bounded automation rather than simply creating more partitions.
