# 8.2 — MVCC Cleanup, Dead Tuples, and Reusable Space

Status: **COMPLETE — CANONICAL**

## Purpose

PostgreSQL's Multi-Version Concurrency Control (MVCC) allows readers and writers to operate concurrently by maintaining multiple row versions when necessary. This architecture provides strong transactional concurrency, but obsolete row versions must eventually be identified, cleaned up, and their storage made reusable.

An `UPDATE` normally creates a new row version rather than overwriting the existing tuple. A `DELETE` makes a row logically obsolete without immediately removing its physical tuple. Once an obsolete tuple is no longer visible to any relevant transaction, PostgreSQL can reclaim its storage through vacuum and related heap-maintenance mechanisms.

Dead tuples are therefore a normal consequence of PostgreSQL MVCC. They become an operational concern when tuple-generation rates consistently exceed sustainable cleanup capacity.

## MVCC row-version lifecycle

A simplified lifecycle is:

```text
INSERT
  |
  v
Live tuple
  |
  | UPDATE / DELETE
  v
Old tuple version
  |
  | potentially visible to an existing snapshot
  v
Retained tuple version
  |
  | no longer visible to relevant transactions
  v
Dead tuple
  |
  | VACUUM / heap cleanup
  v
Reusable space
```

PostgreSQL cannot safely reclaim an old tuple simply because an UPDATE or DELETE occurred. MVCC visibility rules determine when reclamation becomes safe.

## Sources of dead tuples

Ordinary `UPDATE` operations generally create new tuple versions, while `DELETE` operations logically remove rows without immediately removing their physical tuples. High-frequency UPDATE workloads can therefore produce significant tuple churn even when logical row counts remain relatively constant.

Common high-churn tables include job and workflow state, queues, sessions, counters, operational metadata, frequently updated JSON documents, and status-tracking tables.

## Dead tuples versus bloat

Dead tuples and bloat are related but distinct concepts. A dead tuple is an obsolete row version eligible, or eventually eligible, for cleanup. Bloat describes inefficient physical storage consumption relative to useful data and expected reusable space.

A healthy high-churn table can continuously create and clean dead tuples. The production question is not whether a table contains dead tuples, but whether PostgreSQL can sustainably clean obsolete tuples at least as quickly as the workload creates them.

## Reusable space versus physical disk reclamation

Standard `VACUUM` primarily makes storage occupied by dead tuples available for reuse by PostgreSQL. Future inserts and updates can consume that reusable space rather than extending the relation.

`DELETE` followed by standard `VACUUM` therefore does not imply that an equivalent amount of filesystem space will immediately be returned to the operating system. Standard VACUUM can, however, truncate completely empty pages from the physical end of a relation when conditions permit. Extensive physical compaction generally requires a rewrite operation such as `VACUUM FULL`.

## Cleanup horizons and blockers

VACUUM must respect PostgreSQL visibility and cleanup horizons. Conditions capable of retaining old horizons include long-running transactions, `idle in transaction` sessions, old prepared transactions, replication slots, standby-related retention mechanisms, and long-lived snapshots.

A running VACUUM does not necessarily mean that every obsolete tuple can be reclaimed. Repeated manual vacuuming will not resolve a retained cleanup horizon while the underlying blocker remains.

## Heap-page reuse and pruning

PostgreSQL stores heap tuples in fixed-size pages. Once obsolete storage becomes reusable, future tuples can use free space within those pages even if the physical relation remains the same size.

PostgreSQL can also perform page-local pruning when accessing heap pages and conditions permit. Pruning can remove obsolete tuple-chain members and improve page-local reuse, but it is complementary to VACUUM rather than a replacement for it. VACUUM has broader responsibilities involving heap cleanup, index cleanup, visibility information, freezing, maintenance statistics, and transaction-ID and multixact protection.

## HOT updates

PostgreSQL can perform a Heap-Only Tuple (HOT) update when eligibility requirements are satisfied. HOT is particularly valuable when modified columns do not require new ordinary index entries and sufficient space exists on the same heap page.

HOT can reduce index-maintenance overhead, but it does not eliminate MVCC tuple versions or cleanup requirements. Insufficient page space and updates affecting indexed values can reduce HOT opportunities. Table `fillfactor` can influence how much page space remains available for future updates.

## Operational statistics

A useful starting point is `pg_stat_user_tables`:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

These statistics should be treated as operational estimates and trends rather than exact physical tuple inventories.

A dead-tuple percentage can help identify relations requiring investigation, but it must not become a universal alert threshold. Always evaluate absolute counts, ratios, workload churn, relation size, and storage trajectory together.

## Measure churn rates

Track INSERT, UPDATE, DELETE, and HOT-update rates together with dead-tuple growth, vacuum frequency and duration, table growth, and index growth. If autovacuum executes but the dead-tuple backlog continues increasing, investigate whether maintenance capacity is keeping pace with workload churn.

Potential causes include unsuitable autovacuum thresholds, insufficient worker capacity, vacuum throttling, storage I/O contention, retained cleanup horizons, high UPDATE/DELETE rates, and vacuum cancellation or lock interference.

## Heap and index effects

Tuple churn affects both heap and indexes. Operational reviews should correlate heap size, total and individual index sizes, UPDATE and DELETE volume, HOT effectiveness, and vacuum behavior. A relation with manageable heap behavior can still develop disproportionate index growth.

## Long-running transactions

An ordinary idle connection and an `idle in transaction` connection have different operational implications. A long-lived open transaction can contribute to holding back cleanup horizons.

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Very old transactions should be investigated even when they consume little CPU.

## Monitoring active VACUUM

Regular VACUUM activity, including autovacuum workers performing VACUUM, can be observed through:

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

`VACUUM FULL` rewrites the relation and reports progress through `pg_stat_progress_cluster` instead.

## SRE diagnostic workflow

When dead tuples increase unexpectedly:

1. Identify affected relations and their live/dead tuple estimates.
2. Measure INSERT, UPDATE, DELETE, and HOT-update rates.
3. Check recent and active vacuum activity.
4. Identify old and idle-in-transaction sessions.
5. Investigate prepared transactions and replication-related retained horizons when relevant.
6. Track heap, index, database, and filesystem growth.
7. Observe whether the cleanup backlog returns toward baseline after peak traffic.

The critical question is whether the problem is cleanup capacity, workload volume, or a retained horizon.

## Common failure patterns

### Cleanup cannot match churn

When UPDATE/DELETE generation exceeds sustainable cleanup throughput, dead tuples accumulate, relations grow, I/O pressure increases, and query performance can deteriorate. `VACUUM FULL` should not be the automatic response; determine why routine maintenance cannot maintain steady state.

### Large DELETE but disk does not shrink

Standard VACUUM may successfully make substantial storage reusable internally while filesystem utilization changes little. Before considering a rewrite, determine whether the space will be reused, whether immediate filesystem reclamation is necessary, whether enough temporary storage exists, and whether the application can tolerate rewrite locking.

### Cleanup blocked by an old transaction

If an old transaction retains the cleanup horizon while UPDATE/DELETE activity continues, VACUUM may be unable to reclaim all obsolete versions. Increasing VACUUM frequency does not solve the retained horizon; find and resolve the blocker.

## Production monitoring model

Monitor `n_dead_tup`, `n_live_tup`, UPDATE and DELETE rates, HOT updates, last autovacuum, autovacuum count, oldest transaction age, heap and index growth, free storage, vacuum duration, and active vacuum progress.

No individual metric is sufficient. Production monitoring should correlate workload churn, cleanup throughput, retained horizons, physical growth, and storage runway.

## Production principles

1. Dead tuples are normal; uncontrolled accumulation is not.
2. MVCC correctness takes precedence over immediate physical cleanup.
3. Routine VACUUM primarily makes storage reusable rather than shrinking relations.
4. Standard VACUUM can sometimes return empty tail pages to the operating system.
5. Cleanup capacity must sustainably match workload churn.
6. Long-running transactions and retained horizons can prevent effective cleanup.
7. High-churn relations may require table-specific autovacuum tuning.
8. Dead-tuple percentage alone is not an adequate health metric.
9. Heap and index behavior must be evaluated together.
10. HOT efficiency can materially reduce index-maintenance pressure.
11. `VACUUM FULL` is a controlled rewrite, not routine dead-tuple maintenance.
12. Storage runway should be monitored before maintenance debt becomes an availability incident.

## SRE checklist

```text

[ ] Check recent autovacuum activity
[ ] Inspect active VACUUM progress
[ ] Identify long-running transactions
[ ] Identify idle-in-transaction sessions
[ ] Check prepared transactions when relevant
[ ] Evaluate replication-related cleanup horizons
[ ] Measure HOT-update effectiveness
[ ] Compare heap and index growth
[ ] Measure storage runway
[ ] Determine whether cleanup catches up after peak traffic
[ ] Do not assume standard VACUUM must shrink the relation
[ ] Do not use VACUUM FULL without explicit operational justification
```

## Key takeaway

PostgreSQL MVCC deliberately trades immediate physical row removal for transactional concurrency. The production objective is not zero dead tuples. It is to keep tuple-generation rate within sustainable cleanup capacity while transaction horizons continue to advance and sufficient storage runway remains available.

When cleanup cannot keep pace—or retained horizons prevent reclamation—the resulting maintenance debt can become heap growth, index growth, I/O pressure, degraded query performance, transaction-ID risk, and ultimately an availability problem.
