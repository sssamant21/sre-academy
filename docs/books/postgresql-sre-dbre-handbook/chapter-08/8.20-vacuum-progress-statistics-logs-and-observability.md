# 8.20 — Vacuum Progress, Statistics, Logs, and Observability

**Edition:** Revised Final / Canonical  
**Book:** PostgreSQL SRE & DBRE Handbook  
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance  
**Technical Baseline:** PostgreSQL 18  
**Status:** **COMPLETE — CANONICAL**

## 8.20.1 Purpose

Vacuum health cannot be determined from a single PostgreSQL metric.

A production system can show active autovacuum workers while still accumulating dead tuples, transaction ID age, MultiXact age, cleanup backlog, index cleanup work, WAL pressure, replication impact, storage pressure, and maintenance contention.

Conversely, a large dead-tuple estimate does not automatically mean autovacuum is unhealthy.

Production observability must separate activity, progress, effectiveness, and efficiency.

> **Do not classify vacuum health from worker activity, dead-tuple count, or maintenance recency alone. Determine whether maintenance is progressing, reducing backlog, advancing correctness horizons, keeping pace with workload churn, and doing so within acceptable CPU, I/O, WAL, replication, and application-impact limits.**

## 8.20.2 Observability Layers

A production vacuum-observability model should use multiple layers:

```text
Layer 1 — Current maintenance activity
Layer 2 — Active maintenance progress
Layer 3 — Relation-level cumulative statistics
Layer 4 — Transaction-age safety
Layer 5 — Cleanup blockers and retained horizons
Layer 6 — PostgreSQL-native I/O and WAL telemetry
Layer 7 — Logs and historical maintenance evidence
Layer 8 — Infrastructure and storage telemetry
Layer 9 — Replica and application impact
```

No single layer is sufficient.

## 8.20.3 Current Maintenance Activity

`pg_stat_activity` is the first source for identifying active maintenance sessions.

```sql
SELECT
    pid,
    datname,
    usename,
    application_name,
    backend_type,
    state,
    xact_start,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE backend_type IN ('autovacuum worker', 'autovacuum launcher')
   OR query ILIKE '%vacuum%'
ORDER BY query_start NULLS LAST;
```

This provides context for autovacuum workers, manual VACUUM, long-running maintenance, wait events, and current query text. Maintenance visibility alone is not proof of maintenance health.

## 8.20.4 Autovacuum Worker Identification

Autovacuum workers should preferably be identified by backend type:

```sql
SELECT
    pid,
    datname,
    backend_type,
    state,
    query_start,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY query_start;
```

Operational questions include how many workers are active, which databases they are servicing, how long they have been active, what they are waiting on, and which relations they are maintaining.

## 8.20.5 Activity and Waiting Are Separate

Backend state and wait-event status are separate concepts. A backend can be `active` while also having a non-null `wait_event`, meaning it is executing work but currently waiting for something. A long-running VACUUM should therefore be interpreted together with its wait event.

## 8.20.6 `pg_stat_progress_vacuum`

PostgreSQL 18 exposes progress for standard VACUUM operations through `pg_stat_progress_vacuum`.

`VACUUM FULL` is different. Its progress is reported through `pg_stat_progress_cluster` because `VACUUM FULL` performs a table rewrite rather than standard VACUUM processing.

## 8.20.7 PostgreSQL 18 Vacuum Progress Query

```sql
SELECT
    p.pid,
    p.datname,
    p.relid::regclass AS relation,
    p.phase,
    p.heap_blks_total,
    p.heap_blks_scanned,
    p.heap_blks_vacuumed,
    p.index_vacuum_count,
    p.max_dead_tuple_bytes,
    p.dead_tuple_bytes,
    p.num_dead_item_ids,
    p.indexes_total,
    p.indexes_processed,
    p.delay_time
FROM pg_stat_progress_vacuum AS p
ORDER BY p.pid;
```

## 8.20.8 PostgreSQL 18 Vacuum Phases

The PostgreSQL 18 VACUUM phases are:

```text
initializing
scanning heap
vacuuming indexes
vacuuming heap
cleaning up indexes
truncating heap
performing final cleanup
```

Production dashboards and alerts should use the exact phase names for the deployed major version.

## 8.20.9 No Universal VACUUM Percentage

`heap_blks_scanned / heap_blks_total` describes heap-scan progress, not end-to-end maintenance completion. After heap scanning, PostgreSQL can still perform index vacuuming, heap vacuuming, index cleanup, heap truncation, and final cleanup.

> **Vacuum progress counters must be interpreted within the current phase rather than converted blindly into one universal percentage.**

## 8.20.10 `heap_blks_total`

`heap_blks_total` represents the number of heap blocks present when the VACUUM scan begins. It should be interpreted as scan-start relation size rather than as a continuously expanding denominator.

## 8.20.11 `heap_blks_scanned`

`heap_blks_scanned` tracks heap scan progress. Blocks skipped using visibility-map information can still count toward scan progress, so a block counted as scanned does not necessarily mean full physical inspection occurred. It should not be treated as physical I/O volume.

## 8.20.12 `heap_blks_vacuumed`

`heap_blks_vacuumed` tracks heap cleanup progress where applicable. It should not be expected to equal `heap_blks_scanned` or advance smoothly because pages without relevant cleanup work can be skipped.

## 8.20.13 Dead-Item Accounting in PostgreSQL 18

PostgreSQL 18 uses byte-oriented dead-item accounting in vacuum progress. Important fields include:

```text
max_dead_tuple_bytes
dead_tuple_bytes
num_dead_item_ids
```

These are maintenance-work counters, not exact current table dead-row counts.

## 8.20.14 `max_dead_tuple_bytes`

`max_dead_tuple_bytes` represents the amount of dead-item information VACUUM can accumulate before another index-vacuum cycle may be required. It should not be interpreted as a table bloat threshold.

## 8.20.15 `dead_tuple_bytes`

`dead_tuple_bytes` represents the amount of dead-item information currently accumulated during the present collection interval. It is not equivalent to `n_dead_tup`.

## 8.20.16 `num_dead_item_ids`

`num_dead_item_ids` counts dead item identifiers collected during the current collection interval. Dead item IDs are not the same as an exact current dead-row population.

## 8.20.17 Index Vacuum Cycles

`index_vacuum_count` records how many index-vacuum cycles have occurred. A value greater than one is not automatically a failure; repeated cycles can occur when dead-item information reaches available maintenance capacity.

Review relation size, dead-item volume, number of indexes, maintenance memory, duration, and resource cost before drawing conclusions.

## 8.20.18 Index Progress

PostgreSQL 18 provides `indexes_total` and `indexes_processed`. These fields are particularly useful during `vacuuming indexes` and `cleaning up indexes`.

## 8.20.19 `delay_time`

PostgreSQL 18 exposes `delay_time` for VACUUM progress. It represents cumulative time spent sleeping because of cost-based vacuum delay when the appropriate delay-timing tracking is enabled. A zero value must be interpreted in the context of timing configuration.

## 8.20.20 Final Cleanup Phase

During `performing final cleanup`, VACUUM can perform final metadata and maintenance tasks such as free-space map cleanup, relation-statistics updates, and reporting maintenance information to the cumulative statistics system. Heap scan completion is therefore not VACUUM completion.

## 8.20.21 Current Progress Versus Historical Health

`pg_stat_progress_vacuum` answers what VACUUM is doing right now. Historical maintenance health requires `pg_stat_all_tables`, external monitoring history, and logs.

## 8.20.22 `pg_stat_all_tables`

A PostgreSQL 18 relation-maintenance query is:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_ins_since_vacuum,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count,
    total_vacuum_time,
    total_autovacuum_time,
    last_analyze,
    last_autoanalyze,
    analyze_count,
    autoanalyze_count,
    total_analyze_time,
    total_autoanalyze_time
FROM pg_stat_all_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema')
ORDER BY n_dead_tup DESC;
```

## 8.20.23 Dead Tuples Are Estimates

`n_dead_tup` is an estimate. It should not be interpreted as an exact dead-row count or as proof of autovacuum failure. It is an operational signal that must be combined with trend and workload context.

## 8.20.24 Dead Tuple Ratio

A useful derived metric is:

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    round(
        100.0 * n_dead_tup /
        NULLIF(n_live_tup + n_dead_tup, 0),
        2
    ) AS dead_tuple_pct
FROM pg_stat_all_tables
WHERE n_dead_tup > 0
ORDER BY dead_tuple_pct DESC;
```

Because both values are estimates, `dead_tuple_pct` should be treated as contextual telemetry rather than a universal alert threshold.

## 8.20.25 Absolute and Relative Backlog

A small table can have a high dead-tuple percentage but little absolute work, while a multi-billion-row table can have a lower percentage but a much larger maintenance burden. Always consider absolute backlog and relative backlog together.

## 8.20.26 `n_ins_since_vacuum`

PostgreSQL 18 exposes `n_ins_since_vacuum`, which estimates rows inserted since the relation was last vacuumed. This provides useful context for insert-heavy workloads where maintenance demand exists even when dead-tuple pressure is not dominant.

## 8.20.27 Maintenance Recency

`last_vacuum` and `last_autovacuum` show maintenance recency. Recency is workload-relative: a static table might not need frequent maintenance, while a high-churn table may require maintenance many times per hour.

## 8.20.28 Maintenance Counts

`vacuum_count`, `autovacuum_count`, `analyze_count`, and `autoanalyze_count` indicate operation frequency. They do not prove maintenance effectiveness, acceptable cost, sufficient cleanup, or safe transaction-age runway.

## 8.20.29 PostgreSQL 18 Maintenance Timing

PostgreSQL 18 provides cumulative maintenance timing fields:

```text
total_vacuum_time
total_autovacuum_time
total_analyze_time
total_autoanalyze_time
```

These allow operators to distinguish maintenance frequency from maintenance cost.

## 8.20.30 Cleanup Throughput

A more useful production question than whether autovacuum ran is whether cleanup throughput is keeping pace with maintenance demand. PostgreSQL does not expose one native vacuum-throughput metric; this is a derived SRE/DBRE model built from dead-tuple trends, maintenance cadence, operation duration, relation size, workload rate, and resource usage.

## 8.20.31 Backlog Trend

Historical trend is more useful than a single snapshot. Repeated backlog growth despite recurring maintenance is more concerning than one isolated high estimate.

> **The important question is whether the backlog recovers toward a sustainable baseline after maintenance or grows across maintenance cycles.**

## 8.20.32 Healthy Sawtooth Pattern

A healthy high-churn relation can show recurring dead-tuple accumulation followed by cleanup. This can be healthy when peaks remain bounded and recovery remains effective.

## 8.20.33 Unhealthy Recovery Pattern

A concerning pattern is one where each maintenance cycle recovers less effectively, for example:

```text
10M -> VACUUM -> 6M
20M -> VACUUM -> 15M
40M -> VACUUM -> 34M
```

Possible causes include worker saturation, insufficient maintenance throughput, retained cleanup horizons, excessive churn, storage limitations, repeated cancellation, or insufficient maintenance memory.

## 8.20.34 PostgreSQL-Native I/O Observability

PostgreSQL 18 provides `pg_stat_io`, which can expose I/O behavior by backend type and context. For vacuum investigations, useful dimensions include autovacuum workers and the `vacuum` I/O context where applicable.

This can provide PostgreSQL-native evidence for reads, writes, bytes, buffer reuse, evictions, and I/O timing.

## 8.20.35 I/O Timing Caveat

Timing fields depend on the relevant timing configuration. A zero read or write time must not automatically be interpreted as zero I/O latency because timing collection may be disabled.

## 8.20.36 PostgreSQL and Infrastructure Evidence

Storage diagnosis should combine PostgreSQL-native I/O evidence with host/cloud telemetry such as CPU, IOPS, throughput, latency, queue depth, and filesystem utilization before concluding that storage is the limiting factor.

## 8.20.37 Storage Latency Example

If VACUUM is active, heap scanning is slow, CPU is moderate, PostgreSQL I/O is elevated, storage latency is severe, and queue depth is high, the limiting factor may be storage capacity rather than vacuum configuration. Do not increase autovacuum aggressiveness blindly.

## 8.20.38 Transaction ID Age

Dead-tuple backlog and wraparound risk are different dimensions.

```sql
SELECT
    datname,
    age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

## 8.20.39 Relation-Level XID Age

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    age(c.relfrozenxid) AS xid_age
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 100;
```

Including `t` allows TOAST relations to participate in correctness investigations.

## 8.20.40 `relfrozenxid`

`relfrozenxid` is a primary relation-level input to anti-wraparound monitoring. A relation with advancing age and poor freeze progress requires investigation even when dead-tuple backlog is low.

## 8.20.41 MultiXact Age

MultiXact safety must be monitored separately. Use `mxid_age()` for MultiXact IDs rather than ordinary `age()`.

## 8.20.42 Database-Level XID and MXID Monitoring

```sql
SELECT
    datname,
    age(datfrozenxid) AS xid_age,
    mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

## 8.20.43 Relation-Level MXID Monitoring

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    mxid_age(c.relminmxid) AS mxid_age
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY mxid_age(c.relminmxid) DESC
LIMIT 100;
```

## 8.20.44 XID and MXID Are Separate

Always preserve the distinction that XID safety is not the same as MXID safety. A database can be healthy in one dimension and unhealthy in the other.

## 8.20.45 Transaction-Age Runway

PostgreSQL exposes age and configuration data but does not directly expose hours until an incident. Runway is a derived SRE metric based on current age, age growth rate, maintenance effectiveness, and configured safety limits.

## 8.20.46 Cleanup Horizons

VACUUM cleanup can be constrained by long-running transactions, old snapshots, prepared transactions, replication-slot `xmin`, replication-slot `catalog_xmin`, and standby feedback. VACUUM running while dead tuples remain can therefore indicate a horizon problem rather than insufficient execution.

## 8.20.47 Long Transactions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    now() - xact_start AS xact_age,
    backend_xmin,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Focus on workload-relative significance rather than a universal age threshold.

## 8.20.48 Idle in Transaction

Sessions in `idle in transaction` can retain transactional state while doing no useful database work. Review state, `xact_start`, `backend_xmin`, application identity, client, and query. Do not terminate automatically; first establish ownership and business impact.

## 8.20.49 Prepared Transactions

```sql
SELECT
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
ORDER BY prepared;
```

Unexpected old prepared transactions can retain transaction state and should be investigated.

## 8.20.50 Replication Slot Observability

```sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    inactive_since,
    restart_lsn,
    confirmed_flush_lsn,
    xmin,
    catalog_xmin,
    invalidation_reason
FROM pg_replication_slots;
```

Interpret fields according to their specific retention role.

## 8.20.51 Row Cleanup Versus WAL Retention

Do not merge all slot retention into one concept:

```text
xmin / catalog_xmin
-> tuple or catalog cleanup retention

restart_lsn
-> WAL retention
```

These can generate different incidents and require different remediation.

## 8.20.52 Inactive Replication Slots

> **Do not drop an inactive replication slot merely because it is inactive.**

Determine owner, consumer, expected activity, CDC impact, recovery implications, WAL retention impact, and row-retention impact first.

## 8.20.53 Standby Behavior Without Feedback

Without `hot_standby_feedback`, primary VACUUM cleanup can remove row versions still needed by standby queries, producing recovery conflicts and possible standby-query cancellation.

## 8.20.54 Standby Behavior With Feedback

With `hot_standby_feedback`, the standby can report its cleanup horizon upstream, reducing some standby conflicts while delaying primary cleanup and potentially contributing to upstream bloat. This is an availability-versus-cleanup tradeoff, not a universal recommendation.

## 8.20.55 Standby Conflict Observability

On standby servers inspect `pg_stat_database_conflicts`. Relevant counters include `confl_tablespace`, `confl_lock`, `confl_snapshot`, `confl_bufferpin`, and `confl_deadlock`.

## 8.20.56 Replication Lag and Cleanup Conflict Are Different

Low replication lag does not prove there are no standby cleanup conflicts, and high replication lag does not prove VACUUM caused it. Use separate evidence for receive lag, replay lag, recovery conflicts, and feedback behavior.

## 8.20.57 Lock Investigation

```sql
SELECT
    a.pid,
    a.usename,
    a.application_name,
    a.state,
    a.query_start,
    a.wait_event_type,
    a.wait_event,
    pg_blocking_pids(a.pid) AS blocking_pids,
    a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;
```

This identifies candidate blockers.

## 8.20.58 Do Not Automatically Kill Blockers

Before intervention establish owner, business purpose, transaction age, impact, rollback consequence, and recovery path. Observability should support safe decisions rather than destructive automation.

## 8.20.59 Blocker Classification

Production findings should distinguish:

```text
C1 — Transaction / snapshot horizon
C2 — Replication-slot xmin or catalog_xmin
C3 — Standby-feedback horizon
C4 — Prepared-transaction horizon
```

## 8.20.60 Autovacuum Logging

PostgreSQL provides `log_autovacuum_min_duration` for logging autovacuum and automatic ANALYZE activity. PostgreSQL 18 defaults to `10min`. Setting it to `0` logs every qualifying action; `-1` disables this logging.

## 8.20.61 Logging Is an Observability Control

Changing `log_autovacuum_min_duration` changes what evidence is logged. It does not directly change vacuum speed.

## 8.20.62 Skipped Maintenance Logging

When autovacuum logging is enabled rather than disabled, PostgreSQL can also report certain actions skipped because of conditions such as conflicting locks or relation removal during maintenance. These logs provide evidence for repeated maintenance failures.

## 8.20.63 Logging Strategy

Avoid both no useful maintenance logs and permanently logging every maintenance action without regard to volume. Choose thresholds based on workload, incident-response needs, log-ingestion cost, and retention policy.

## 8.20.64 PostgreSQL WAL Observability

Maintenance investigations should include PostgreSQL-native WAL telemetry where appropriate. Relevant sources include `pg_stat_wal` and `pg_stat_replication`. Correlate maintenance with WAL generation, replica receive/replay behavior, slot retention, and downstream lag.

## 8.20.65 WAL and Tuple Retention Are Separate

Maintain this distinction:

```text
restart_lsn
-> WAL retention

xmin/catalog_xmin
-> row/catalog cleanup retention
```

## 8.20.66 Infrastructure Metrics

Correlate maintenance with CPU utilization and saturation, disk IOPS and throughput, disk latency, queue depth, filesystem utilization, memory pressure, and network throughput.

## 8.20.67 Storage Capacity

Monitor free capacity along with latency. Maintenance can interact with WAL growth, index maintenance, logging, table rewrites, temporary work, and retained WAL from replication slots.

## 8.20.68 Replica Health

Maintenance success on the primary is not enough. Validate primary health, WAL pressure, replica receive, replica replay, and standby query conflicts.

## 8.20.69 Application Observability

Correlate maintenance with query latency, transaction latency, timeout rate, retry rate, connection-pool pressure, and application error rate. A maintenance change that improves cleanup but causes unacceptable application degradation is not successful.

## 8.20.70 Autovacuum Worker Saturation

A stronger saturation signal is all workers persistently active together with growing maintenance backlog, relations waiting for maintenance, or increasing XID/MXID age. A single instant with all workers busy is insufficient evidence.

## 8.20.71 Cross-Database Maintenance Pressure

Autovacuum workers are scheduled across databases within the PostgreSQL instance. One database with heavy maintenance demand can therefore affect maintenance opportunities in another.

## 8.20.72 Maintenance Effectiveness

Evaluate VACUUM by result. Ask whether dead-tuple backlog declined, `relfrozenxid` and `relminmxid` advanced where expected, blocker horizons moved, maintenance completed, resource pressure remained acceptable, and replicas and applications remained healthy.

## 8.20.73 Effectiveness Versus Efficiency

Effectiveness asks whether maintenance accomplished the required cleanup or correctness result. Efficiency asks what CPU, I/O, WAL, time, replication, and service cost it required. Effective-but-too-expensive and cheap-but-ineffective are both production problems with different remediations.

## 8.20.74 Vacuum Health Classification

### Class A — Healthy Maintenance

Backlog is bounded, maintenance completes, XID/MXID runway is healthy, and resource cost is acceptable.

### Class B — Cleanup Lag

Dead tuples accumulate while VACUUM remains active and cleanup does not keep pace. Investigate churn, thresholds, worker capacity, maintenance memory, cost throttling, and infrastructure.

### Class C — Cleanup Blocked

Subtypes:

```text
C1 — Transaction / snapshot horizon
C2 — Slot xmin / catalog_xmin
C3 — Standby-feedback horizon
C4 — Prepared-transaction horizon
```

### Class D — Transaction-Age Risk

Subtypes:

```text
D-XID
D-MXID
```

Treat these as correctness risks.

### Class E — Maintenance Resource Saturation

Maintenance progresses but CPU, I/O, WAL, replication, or service impact is unacceptable.

### Class F — Observability Gap

Logs, history, or metrics are insufficient to prove maintenance outcome. Improve telemetry before aggressive tuning.

## 8.20.75 Production Decision Model

```text

        |
        v
```

## 8.20.76 Dashboard — Relation Health

For critical relations, useful dashboard fields include relation size, `n_live_tup`, `n_dead_tup`, dead-tuple ratio, `n_ins_since_vacuum`, `last_vacuum`, `last_autovacuum`, vacuum counts, cumulative vacuum time, XID age, MXID age, current VACUUM phase, and duration.

Not every field requires an alert; many are diagnostic context.

## 8.20.77 Dashboard — Instance Health

Useful instance-level indicators include active autovacuum workers, persistent worker saturation, oldest database and relation XID age, oldest MXID age, longest transaction, oldest idle-in-transaction session, oldest prepared transaction, slot row-retention horizons, WAL slot retention, standby conflict rate, replication lag, WAL generation rate, PostgreSQL vacuum I/O, storage latency, queue depth, CPU, and free storage.

## 8.20.78 PostgreSQL-Native Observability Sources

Important PostgreSQL 18 sources include:

```text
pg_stat_progress_vacuum
pg_stat_progress_cluster
pg_stat_all_tables
pg_stat_activity
pg_locks
pg_stat_io
pg_stat_wal
pg_stat_replication
pg_replication_slots
pg_stat_database_conflicts
pg_prepared_xacts
pg_database
pg_class
```

These should be combined with infrastructure monitoring rather than replaced by it.

## 8.20.79 Alerting Versus Dashboarding

Dashboard-oriented signals include current phase, heap scan progress, dead-tuple percentage, vacuum count, and current worker count. Alert inputs can include persistent backlog growth, shrinking XID/MXID runway, repeated maintenance failure, persistent worker saturation with backlog, retained cleanup horizons, severe resource saturation, and replica health degradation.

Detailed alert design belongs in Section 8.21.

## 8.20.80 Avoid Static Universal Thresholds

Avoid universal rules such as `dead tuples > 1M => critical` or `dead tuple ratio > 10% => critical` without workload context.

Use absolute backlog, relative backlog, growth rate, recovery rate, maintenance cadence, XID/MXID runway, and business criticality together.

## 8.20.81 Rate-of-Change Monitoring

Rates are often more useful than isolated values. Examples include dead-tuple growth per minute, dead-tuple recovery per maintenance cycle, XID age growth, MXID age growth, WAL generation rate, and replication lag growth.

## 8.20.82 Maintenance Runway

Maintenance runway is a derived SRE model combining current state, growth rate, cleanup effectiveness, available maintenance capacity, and correctness limits. This enables intervention before hard limits are reached.

## 8.20.83 Statistics Reset Awareness

PostgreSQL cumulative statistics can be reset. Counts and cumulative timing must therefore be interpreted relative to the statistics collection horizon. Long-term analysis should retain external time-series history.

## 8.20.84 Monitoring-System History

Monitoring history should support detection of gradual cleanup degradation, increasing maintenance duration, worker saturation, growing XID/MXID age, recurring blockers, rising WAL retention, storage capacity exhaustion, and changing replica impact.

## 8.20.85 Production Baselines

Create workload-specific baselines for normal dead-tuple range, VACUUM frequency and duration, maintenance cost, XID age, MXID age, WAL generation, replica lag, and storage latency.

## 8.20.87 Example — Healthy High-Churn Table

A high-churn table can have periodically high dead tuples, frequent autovacuum, backlog recovery after maintenance, healthy XID/MXID age, healthy storage latency, and no application impact. This is Class A — Healthy Maintenance. No tuning is required; continue trend monitoring.

## 8.20.88 Example — Cleanup Lag

If autovacuum is continuously active, dead tuples are increasing, recovery after VACUUM is weak, no significant retained horizons are present, storage is healthy, and workers are persistently saturated, classify as Class B — Cleanup Lag. Investigate workload churn, worker capacity, per-table settings, vacuum memory, cost throttling, and maintenance throughput before changing configuration.

## 8.20.89 Example — Transaction Horizon

If autovacuum is running, dead tuples remain high, an old transaction retains `backend_xmin`, storage is healthy, and workers are available, classify as Class C1 — Transaction / Snapshot Horizon. Identify the transaction owner and business purpose before remediation.

## 8.20.90 Example — Slot Cleanup Horizon

If autovacuum is active, backlog persists, a slot is inactive, slot `xmin` is old, and `restart_lsn` is acceptable, classify as Class C2 — Slot xmin Retention. Investigate slot ownership and consumer state; do not drop the slot based on inactivity alone.

## 8.20.91 Example — Standby Feedback Retention

If primary cleanup is delayed, `hot_standby_feedback` is enabled, a standby query is long-running, replica lag is low, and primary bloat is increasing, classify as Class C3 — Standby Feedback Horizon. Evaluate the tradeoff between standby-query continuity and upstream cleanup.

## 8.20.92 Example — XID Risk

If dead tuples are moderate, autovacuum is active, XID age is rapidly increasing, MXID age is healthy, and safety runway is shrinking, classify as Class D-XID — Transaction ID Risk. Treat it as a correctness priority.

## 8.20.93 Example — MXID Risk

If dead tuples are low, XID age is healthy, MXID age is rapidly increasing, and lock churn is high, classify as Class D-MXID — MultiXact Risk. Investigate MultiXact generation and freezing separately from ordinary XID health.

## 8.20.94 Example — Storage Bottleneck

If VACUUM is active, progress is slow, backlog is increasing, CPU is moderate, `pg_stat_io` shows high read activity, disk latency is severe, and queue depth is high, classify as Class E — Maintenance Resource Saturation. Investigate storage capacity and workload contention before increasing autovacuum concurrency or aggressiveness.

## 8.20.95 Example — Observability Gap

If autovacuum logs and historical metrics are unavailable, current VACUUM is inactive, dead-tuple snapshot is high, and prior trend is unknown, classify as Class F — Observability Gap. Establish sufficient telemetry before aggressive maintenance changes.

## 8.20.96 Post-Change Validation — Maintenance

Verify that VACUUM completed, expected phase progression was observed, and there were no unexpected cancellations or skipped maintenance events.

## 8.20.97 Post-Change Validation — Effectiveness

Verify that dead-tuple backlog recovered, relevant freeze horizons advanced, blocking horizons cleared, and maintenance cadence is sustainable.

## 8.20.98 Post-Change Validation — Infrastructure

Verify that CPU, I/O, storage latency, WAL pressure, and replica health remained acceptable.

## 8.20.99 Post-Change Validation — Service

Verify query latency, transaction latency, application errors, and connection pressure. A maintenance change is not successful merely because VACUUM finishes faster.

## 8.20.100 No Vacuum Tuning Required

If dead tuples periodically rise, autovacuum regularly reduces backlog, XID/MXID runway is healthy, resource impact is low, replicas are healthy, and applications are healthy, the correct conclusion can be:

> **No vacuum tuning required. Continue trend monitoring.**

## 8.20.101 Production Principles

1. Autovacuum activity is not proof of maintenance health.
2. Separate activity, progress, effectiveness, and efficiency.
3. Use `pg_stat_progress_vacuum` for standard VACUUM progress.
4. Use `pg_stat_progress_cluster` for `VACUUM FULL` progress.
5. Use exact PostgreSQL phase names for the deployed major version.
6. Do not invent one universal VACUUM completion percentage.
7. Interpret heap counters within the current phase.
8. Understand PostgreSQL 18 dead-item byte accounting.
9. Use index progress counters during index-related phases.
10. Interpret `delay_time` with timing-configuration awareness.
11. Use `pg_stat_all_tables` for cumulative relation-maintenance context.
12. Treat `n_live_tup` and `n_dead_tup` as estimates.
13. Use absolute and relative backlog together.
14. Include `n_ins_since_vacuum` for insert-heavy workloads.
15. Use maintenance counts and cumulative maintenance time together.
16. Measure cleanup throughput against workload demand.
17. Use backlog trend rather than one snapshot.
18. A sawtooth dead-tuple pattern can be healthy.
19. Failure to recover after maintenance is more concerning than dead tuples alone.
20. Use `pg_stat_io` as PostgreSQL-native maintenance evidence.
21. Correlate PostgreSQL I/O with cloud or host telemetry.
22. Do not interpret zero timing counters without checking timing configuration.
23. Monitor XID and MXID age separately.
24. Use `age()` for XIDs and `mxid_age()` for MultiXacts.
25. Include TOAST relations when correctness investigations require them.
26. Estimate transaction-age runway before correctness limits become emergencies.
27. Investigate retained cleanup horizons.
28. Long transactions can make active VACUUM ineffective.
29. Idle-in-transaction sessions require ownership-aware investigation.
30. Prepared transactions can retain maintenance horizons.
31. Distinguish slot `xmin`/`catalog_xmin` from `restart_lsn`.
32. Do not drop inactive slots based on inactivity alone.
33. Understand the `hot_standby_feedback` cleanup-versus-query tradeoff.
34. Use `pg_stat_database_conflicts` for standby conflict evidence.
35. Do not confuse standby conflicts with replication lag.
36. Use blocker evidence before intervention.
37. Do not automatically terminate blocking sessions.
38. Use autovacuum logs for historical evidence.
39. Remember PostgreSQL 18's `log_autovacuum_min_duration = 10min` default.
40. Logging changes observability, not vacuum speed.
41. Monitor skipped and canceled maintenance.
42. Monitor PostgreSQL-native WAL and replication telemetry.
43. Validate primary and replica health.
44. Correlate maintenance with application latency and errors.
45. Treat persistent worker saturation plus backlog as the stronger saturation signal.
46. Consider cross-database maintenance demand.
47. Measure maintenance effectiveness and efficiency separately.
48. Use evidence before changing worker count, vacuum memory, or cost delay.
49. Use workload-specific classifications and baselines.
50. Avoid universal dead-tuple thresholds.
51. Use rate-of-change and runway where possible.
52. Preserve external time-series history across statistics resets.
53. Insufficient observability is itself a production finding.
54. No tuning required is a valid outcome.
55. Observability should support safe decisions, not destructive automation.

## 8.20.103 Key Takeaway

Production vacuum observability should answer whether maintenance is running, progressing, effective, keeping pace, blocked by retained horizons, safe from an XID/MXID perspective, affordable from a resource perspective, and healthy for replicas and applications.

> **Do not classify vacuum health from worker activity, dead-tuple count, or maintenance recency alone. Determine whether maintenance is progressing, reducing backlog, advancing correctness horizons, keeping pace with workload churn, and doing so within acceptable CPU, I/O, WAL, replication, and application-impact limits.**

The objective is not merely that autovacuum is running. The objective is sufficient cleanup throughput, bounded backlog, safe XID/MXID runway, acceptable resource cost, and a healthy primary, replicas, and application.
