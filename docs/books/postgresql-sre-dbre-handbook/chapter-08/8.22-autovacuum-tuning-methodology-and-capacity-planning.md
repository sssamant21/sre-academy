# 8.22 --- Autovacuum Tuning Methodology and Capacity Planning

**Edition:** Revised Final / Canonical Edition **Book:** PostgreSQL SRE
& DBRE Handbook **Chapter 8:** Vacuum, Autovacuum, Bloat, and
Maintenance **Technical Baseline:** PostgreSQL 18 **Status:**
**CANONICAL**

## 8.22.1 Purpose

Autovacuum tuning is not the process of making VACUUM run as
aggressively as possible.

The objective is to provide enough maintenance capacity to:

-   keep dead-tuple backlog bounded;
-   maintain visibility-map health;
-   advance XID and MXID freeze horizons;
-   prevent avoidable bloat;
-   maintain planner statistics;
-   protect wraparound safety;
-   avoid storage exhaustion;
-   minimize interference with foreground workloads.

The central SRE/DBRE principle is:

> **Tune autovacuum from measured maintenance demand, cleanup
> effectiveness, correctness runway, and available resource
> capacity---not from isolated parameter values or generic tuning
> recipes.**

------------------------------------------------------------------------

## 8.22.2 Autovacuum Is a Capacity System

Autovacuum should be treated as a background maintenance service with
finite capacity.

Conceptually:

``` text
maintenance demand
       |
       v
autovacuum scheduling
       |
       v
worker capacity
       |
       v
CPU / memory / I/O / WAL
       |
       v
cleanup throughput
```

If:

``` text
maintenance demand
>
sustainable cleanup capacity
```

the backlog grows.

------------------------------------------------------------------------

## 8.22.3 Tuning Starts With Diagnosis

Do not begin with:

``` text
increase autovacuum_max_workers
```

or:

``` text
lower autovacuum_vacuum_scale_factor
```

Begin with:

``` text
What problem are we solving?
```

Examples:

-   VACUUM triggers too late.
-   Workers are unavailable.
-   VACUUM runs but cannot keep pace.
-   VACUUM is blocked by old horizons.
-   VACUUM is intentionally throttled.
-   Maintenance memory causes repeated index cycles.
-   Storage is saturated.
-   XID/MXID runway is shrinking.
-   One high-churn relation needs different settings.

Each requires a different response.

------------------------------------------------------------------------

## 8.22.4 Separate Triggering From Throughput

Two dimensions must be distinguished:

``` text
When does maintenance start?
```

and:

``` text
How quickly can it complete?
```

Triggering is influenced by parameters such as:

``` text
autovacuum_vacuum_threshold
autovacuum_vacuum_scale_factor
autovacuum_vacuum_insert_threshold
autovacuum_vacuum_insert_scale_factor
autovacuum_analyze_threshold
autovacuum_analyze_scale_factor
```

Throughput is influenced by:

-   worker availability;
-   vacuum cost delay;
-   vacuum cost limit;
-   maintenance memory;
-   storage capability;
-   CPU;
-   concurrent maintenance demand;
-   blockers.

A trigger problem should not be solved only by adding workers.

------------------------------------------------------------------------

## 8.22.5 Tuning Workflow

A production tuning workflow should follow:

``` text
1. Measure workload churn
2. Measure backlog
3. Measure maintenance cadence
4. Measure maintenance duration
5. Identify blockers
6. Measure resource usage
7. Check XID/MXID runway
8. Classify the limiting factor
9. Change the smallest justified setting
10. Validate outcome
```

Do not tune multiple unrelated controls simultaneously unless there is
an emergency.

------------------------------------------------------------------------

## 8.22.6 Baseline Before Change

Before tuning, capture:

-   table size;
-   estimated live tuples;
-   estimated dead tuples;
-   inserts since vacuum;
-   update/delete rate;
-   last autovacuum;
-   autovacuum frequency;
-   average maintenance duration;
-   cumulative maintenance time;
-   worker utilization;
-   XID age;
-   MXID age;
-   storage latency;
-   WAL generation;
-   replica impact;
-   application latency.

Without a baseline, improvement cannot be demonstrated reliably.

------------------------------------------------------------------------

## 8.22.7 Workload Segmentation

Not all relations need the same maintenance policy.

Useful categories include:

``` text
low churn
moderate churn
high churn
append-heavy
update-heavy
delete-heavy
very large
small but latency-sensitive
partitioned time-series
```

Autovacuum tuning should follow the workload profile.

------------------------------------------------------------------------

## 8.22.8 Global Versus Per-Table Configuration

Prefer global settings for:

-   safe instance-wide defaults;
-   worker infrastructure;
-   broad cost controls.

Prefer per-table settings when:

-   one relation is unusually large;
-   one relation has extreme churn;
-   table behavior differs significantly from the fleet;
-   a global change would create unnecessary maintenance elsewhere.

The general rule is:

> **Use the narrowest configuration scope that solves the measured
> problem.**

------------------------------------------------------------------------

## 8.22.9 Trigger Formula

For update/delete-driven vacuum triggering, the effective threshold
conceptually follows:

``` text
vacuum threshold
+
vacuum scale factor × table size
```

For large tables, the scale-factor component can dominate.

This means a seemingly small scale factor can still require millions of
tuple changes before maintenance starts.

------------------------------------------------------------------------

## 8.22.10 Large-Table Trigger Effect

Example:

``` text
table rows: 1,000,000,000
scale factor: 0.20
```

can imply a very large change count before the scale-factor component is
reached.

Therefore:

> **Large relations frequently require lower per-table scale factors
> than small relations.**

The exact value must be workload-derived.

------------------------------------------------------------------------

## 8.22.11 Threshold Plus Scale Factor

Avoid treating scale factor alone as the trigger.

The fixed threshold component still contributes.

Conceptually:

``` text
effective trigger
=
fixed threshold
+
scale-factor component
```

When analyzing a table, calculate the actual effective trigger rather
than discussing only the configured percentage.

------------------------------------------------------------------------

## 8.22.12 High-Churn Relations

For a high-churn relation, ask:

``` text
How quickly is dead-tuple backlog created?
```

Then compare with:

``` text
How often does autovacuum trigger?
How long does cleanup require?
How much backlog remains after cleanup?
```

If backlog consistently grows between cycles, triggering may be too late
or throughput may be insufficient.

------------------------------------------------------------------------

## 8.22.13 Do Not Over-Vacuum Small Tables

Lowering scale factors globally can cause many small tables to be
maintained unnecessarily often.

Potential consequences include:

-   extra I/O;
-   extra CPU;
-   additional WAL;
-   more worker scheduling pressure.

Per-table tuning often avoids this.

------------------------------------------------------------------------

## 8.22.14 Insert-Heavy Tables

Insert-heavy workloads require special consideration.

Even with few dead tuples, VACUUM can still be useful for:

-   visibility-map maintenance;
-   freezing;
-   index-only scan eligibility;
-   transaction-age safety.

Do not classify:

``` text
few dead tuples
```

as:

``` text
no vacuum requirement
```

------------------------------------------------------------------------

## 8.22.15 ANALYZE Is a Separate Tuning Dimension

Autovacuum and autoanalyze share infrastructure but solve different
problems.

A table can have:

``` text
healthy vacuum cadence
```

while suffering from:

``` text
stale planner statistics
```

or vice versa.

Tune analyze thresholds separately when evidence requires it.

------------------------------------------------------------------------

## 8.22.16 Worker Capacity

Autovacuum maintenance capacity depends partly on concurrent workers.

Relevant settings include:

``` text
autovacuum_max_workers
autovacuum_worker_slots
```

Worker count should not be increased merely because all workers are
occasionally busy.

A stronger signal is:

``` text
workers persistently near capacity
+
maintenance backlog growing
+
relations waiting
```

------------------------------------------------------------------------

## 8.22.17 More Workers Are Not Free

Increasing worker concurrency can increase:

-   CPU demand;
-   storage IOPS;
-   storage throughput;
-   cache pressure;
-   WAL generation;
-   replica pressure.

Therefore:

``` text
more workers
```

does not always mean:

``` text
more useful throughput
```

especially when storage is already saturated.

------------------------------------------------------------------------

## 8.22.18 Worker Capacity Planning

Worker planning should consider:

``` text
number of high-churn databases
+
number of high-churn relations
+
average vacuum duration
+
maintenance arrival rate
+
available CPU/I/O capacity
```

The system should have enough capacity to prevent an ever-growing
maintenance queue.

------------------------------------------------------------------------

## 8.22.19 Queueing Perspective

Conceptually:

``` text
maintenance requests arrive
          |
          v
workers service them
```

If service time becomes long and arrival rate remains high:

``` text
queue length grows
```

This is a capacity problem even if each individual VACUUM eventually
completes.

------------------------------------------------------------------------

## 8.22.20 Cost-Based Delay

Autovacuum uses cost-based throttling to reduce interference with
foreground workload.

Important controls include:

``` text
autovacuum_vacuum_cost_delay
autovacuum_vacuum_cost_limit
```

These influence how aggressively maintenance consumes I/O-related
resources.

When multiple autovacuum workers are active, PostgreSQL balances the
configured autovacuum cost limit among workers so that aggregate
autovacuum cost-limit behavior remains bounded by the configured budget.
Consequently, adding workers does not imply that each worker receives an
independent full copy of the global autovacuum cost budget.

------------------------------------------------------------------------

## 8.22.21 Cost Delay Tradeoff

Too much throttling can cause:

``` text
long VACUUM duration
+
backlog accumulation
```

Too little throttling can cause:

``` text
high maintenance I/O
+
foreground latency
```

The correct objective is not minimum VACUUM duration.

It is:

> **Sufficient cleanup throughput with acceptable foreground impact.**

------------------------------------------------------------------------

## 8.22.22 Diagnose Before Reducing Delay

Before reducing cost delay, verify:

-   VACUUM is actually cost-throttled;
-   storage has unused capacity;
-   application workload can tolerate additional maintenance I/O;
-   replicas can tolerate resulting WAL activity.

Do not assume every slow VACUUM is slow because of cost delay.

------------------------------------------------------------------------

## 8.22.23 Cost Limit Capacity

Increasing the cost limit permits more maintenance work before
throttling sleep occurs.

However:

``` text
higher cost limit
```

can shift the bottleneck into:

-   storage latency;
-   CPU;
-   WAL;
-   replication;
-   application response time.

Measure the effect after change.

------------------------------------------------------------------------

## 8.22.24 Maintenance Memory

Autovacuum maintenance memory affects the amount of cleanup state that a
worker can hold.

Relevant configuration includes:

``` text
autovacuum_work_mem
maintenance_work_mem
```

The exact precedence and PostgreSQL 18 semantics is defined by the
PostgreSQL 18 technical baseline.

------------------------------------------------------------------------

## 8.22.25 Repeated Index Vacuum Cycles

A useful diagnostic signal is:

``` text
index_vacuum_count > 1
```

in `pg_stat_progress_vacuum`.

Repeated cycles can indicate that dead-item information exceeds
available maintenance-memory capacity.

For PostgreSQL 18 diagnostics, correlate `index_vacuum_count` with
progress information such as `dead_tuple_bytes` and
`max_dead_tuple_bytes` where applicable. Repeated index cycles are
evidence that should be interpreted together with the relation's
dead-item volume, index count, and available maintenance memory.

This does not automatically mean memory must be increased.

Also consider:

-   dead-tuple volume;
-   number of indexes;
-   table size;
-   available RAM;
-   concurrent workers.

------------------------------------------------------------------------

## 8.22.26 Memory Multiplies by Concurrency

Capacity planning must consider:

``` text
per-worker memory
×
concurrent workers
```

not only one worker.

A safe per-worker value can become unsafe when multiplied across many
simultaneous maintenance workers.

------------------------------------------------------------------------

## 8.22.27 Maintenance Memory Budget

Conceptually:

``` text
memory budget
=
foreground database memory
+
autovacuum worker memory
+
manual maintenance memory
+
parallel-operation memory
+
OS/cache requirements
```

Avoid sizing autovacuum memory in isolation.

------------------------------------------------------------------------

## 8.22.28 Storage Capacity Is Often the Real Limit

If storage is already saturated:

``` text
increase workers
```

can worsen performance without increasing effective cleanup throughput.

Inspect:

-   PostgreSQL I/O;
-   read/write latency;
-   IOPS;
-   throughput;
-   queue depth;
-   storage utilization.

------------------------------------------------------------------------

## 8.22.29 Storage Headroom

A healthy maintenance system should retain enough storage headroom to
absorb:

-   workload peaks;
-   autovacuum activity;
-   WAL growth;
-   index maintenance;
-   replication retention;
-   emergency maintenance.

Capacity planning should not assume normal average utilization is
sufficient.

------------------------------------------------------------------------

## 8.22.30 CPU Headroom

VACUUM can consume CPU through:

-   tuple visibility checks;
-   index processing;
-   page processing;
-   checksums where applicable;
-   compression or storage-layer effects.

Worker concurrency should be constrained by sustainable CPU headroom as
well as I/O capacity.

------------------------------------------------------------------------

## 8.22.31 WAL Capacity

Maintenance operations can influence WAL generation.

Capacity planning should include:

``` text
maintenance WAL
+
foreground WAL
+
archive capacity
+
replica receive/replay capacity
+
slot retention
```

A maintenance change that is safe on the primary can still overload
downstream systems.

------------------------------------------------------------------------

## 8.22.32 Replica Capacity

Before materially increasing maintenance aggressiveness, verify:

-   replica receive rate;
-   replay capacity;
-   network bandwidth;
-   storage capability;
-   standby query behavior.

The primary should not be tuned in isolation from its replicas.

------------------------------------------------------------------------

## 8.22.33 Blockers Are Not Capacity Problems

Long transactions, prepared transactions, slot horizons, and standby
feedback can prevent cleanup.

In this condition:

``` text
more workers
+
more memory
+
less cost delay
```

may not solve the problem.

Classify blockers before tuning throughput.

------------------------------------------------------------------------

## 8.22.34 XID/MXID Safety Overrides Routine Tuning

Correctness risk has priority over ordinary efficiency tuning.

If XID or MXID runway is shrinking dangerously:

``` text
protect wraparound safety first
```

then optimize routine cost after safety is restored.

------------------------------------------------------------------------

## 8.22.35 Per-Table Reloptions

High-churn tables can use relation-level autovacuum settings.

PostgreSQL 18 supports relation-level autovacuum controls covering, as
applicable:

-   vacuum threshold;
-   vacuum scale factor;
-   vacuum maximum threshold;
-   insert threshold;
-   insert scale factor;
-   analyze threshold;
-   analyze scale factor;
-   vacuum cost delay;
-   vacuum cost limit;
-   freeze and multixact-freeze parameters.

Use relation-level overrides when a table's measured maintenance profile
differs materially from the fleet. Record the effective settings and
verify them after change rather than assuming instance defaults remain
in effect.

------------------------------------------------------------------------

## 8.22.36 Example --- Large High-Churn Table

Suppose:

``` text
table rows:       very large
updates/hour:     high
dead tuple trend: increasing
autovacuum:       running
workers:          available
storage:          healthy
blockers:         none
```

Likely investigation:

``` text
trigger may be too late
or
per-table cleanup throughput may be insufficient
```

Potential response:

-   calculate effective trigger;
-   lower per-table scale factor if justified;
-   validate resulting vacuum frequency;
-   verify I/O impact.

------------------------------------------------------------------------

## 8.22.37 Example --- Worker Saturation

``` text
workers:          persistently at effective maximum
backlog:          increasing across databases
storage latency:  healthy
CPU:              available
```

Potential conclusion:

``` text
worker capacity may be insufficient
```

A controlled worker increase may be appropriate after memory and
downstream capacity review.

------------------------------------------------------------------------

## 8.22.38 Example --- Storage Saturation

``` text
workers:          all busy
dead tuples:      increasing
disk latency:     severe
queue depth:      high
CPU:              moderate
```

Incorrect response:

``` text
increase autovacuum workers
```

Likely outcome:

``` text
more competing I/O
```

Correct direction:

``` text
restore storage headroom
or reduce competing demand
before increasing concurrency
```

------------------------------------------------------------------------

## 8.22.39 Example --- Cost Throttling

``` text
VACUUM progress:  steady but slow
delay_time:       high
storage latency:  low
CPU:              available
foreground load:  healthy
backlog:          increasing
```

Potential conclusion:

``` text
cost throttling may be limiting cleanup throughput
```

A controlled reduction in delay or increase in cost limit may be
evaluated.

------------------------------------------------------------------------

## 8.22.40 Example --- Retained Horizon

``` text
VACUUM:           frequent
dead tuples:      persistent
old transaction:  present
backend_xmin:     old
storage:          healthy
workers:          available
```

Conclusion:

``` text
not primarily an autovacuum capacity problem
```

Resolve the retained horizon first.

------------------------------------------------------------------------

## 8.22.41 Example --- Repeated Index Cycles

``` text
large relation
many indexes
index_vacuum_count: multiple
VACUUM duration: high
memory headroom: available
```

Potential investigation:

``` text
autovacuum memory may be contributing
to repeated index-cleanup cycles
```

Any memory increase must still be evaluated against worker concurrency
and total instance RAM.

------------------------------------------------------------------------

## 8.22.42 Capacity Model

A simple operational model is:

``` text
required maintenance capacity
>=
maintenance demand
+
safety margin
```

Demand can be estimated from:

``` text
tuple churn
+
insert volume
+
freeze work
+
index cleanup
+
analyze demand
```

Capacity comes from:

``` text
workers
×
effective per-worker throughput
```

subject to shared CPU, memory, I/O, and WAL limits.

------------------------------------------------------------------------

## 8.22.43 Maintenance Utilization

Conceptually:

``` text
maintenance utilization
=
required maintenance work
/
available maintenance capacity
```

Persistent utilization near or above sustainable capacity means queueing
and backlog become increasingly likely.

This is a derived SRE/DBRE model rather than a PostgreSQL-native metric.

------------------------------------------------------------------------

## 8.22.44 Capacity Headroom

Avoid operating maintenance continuously at theoretical maximum.

Maintain headroom for:

-   traffic bursts;
-   bulk loads;
-   large deletes;
-   unexpected high churn;
-   schema changes;
-   failover recovery;
-   delayed replica consumers.

------------------------------------------------------------------------

## 8.22.45 Forecasting

Capacity planning should forecast:

``` text
data growth
+
transaction growth
+
write amplification
+
number of relations
+
number of databases
```

A configuration that works today may fail after six months of growth.

------------------------------------------------------------------------

## 8.22.46 Growth Scenarios

Create at least:

``` text
Current
Expected Growth
Peak / Stress
```

scenarios.

For each estimate:

-   relation sizes;
-   change rate;
-   expected trigger counts;
-   worker occupancy;
-   maintenance duration;
-   storage utilization;
-   WAL rate;
-   XID/MXID growth.

------------------------------------------------------------------------

## 8.22.47 Bulk Operations

Bulk loads, backfills, migrations, large deletes, and resynchronizations
can create temporary maintenance demand far above normal baseline.

Capacity planning should include:

``` text
normal operating capacity
```

and:

``` text
planned-event capacity
```

Do not size only from quiet-day averages.

------------------------------------------------------------------------

## 8.22.48 Partitioned Tables

Partitioning can distribute maintenance work across smaller physical
relations.

However:

-   many active partitions can increase maintenance scheduling demand;
-   old partitions may need little routine maintenance;
-   newest partitions may need aggressive table-specific settings;
-   parent statistics require separate consideration.

Tune partitions according to lifecycle and churn.

------------------------------------------------------------------------

## 8.22.49 Hot and Cold Partition Policy

Example:

``` text
current partition:
high churn
lower thresholds
frequent maintenance

recent partition:
moderate churn
moderate maintenance

historical partition:
mostly immutable
minimal routine maintenance
correctness monitoring retained
```

This can reduce unnecessary background work.

------------------------------------------------------------------------

## 8.22.50 Tuning One Parameter at a Time

Whenever practical:

``` text
change
    |
    v
observe
    |
    v
validate
    |
    v
next change
```

Changing workers, memory, scale factor, and cost delay simultaneously
makes causal analysis difficult.

------------------------------------------------------------------------

## 8.22.51 Change Window

Autovacuum tuning does not always require downtime, but production
changes still require:

-   baseline capture;
-   risk assessment;
-   change record;
-   monitoring;
-   rollback criteria.

Dynamic configuration does not mean risk-free configuration.

------------------------------------------------------------------------

## 8.22.52 Validation Window

Do not judge success immediately after changing a parameter.

Observe enough maintenance cycles to determine whether:

-   trigger cadence changed as intended;
-   backlog declined;
-   resource usage remained acceptable;
-   application latency remained healthy;
-   replicas remained healthy.

------------------------------------------------------------------------

## 8.22.53 Success Criteria

A successful tuning change should demonstrate:

``` text
backlog bounded or declining
+
maintenance cadence sustainable
+
XID/MXID runway healthy
+
resource cost acceptable
+
service health preserved
```

------------------------------------------------------------------------

## 8.22.54 Rollback Criteria

Rollback or revise a change when it causes:

-   unacceptable application latency;
-   storage saturation;
-   CPU saturation;
-   replica instability;
-   excessive WAL pressure;
-   worker starvation elsewhere;
-   memory pressure.

------------------------------------------------------------------------

## 8.22.55 No Tuning Required

A valid conclusion is:

``` text
autovacuum frequency appropriate
backlog recovers
XID/MXID runway healthy
workers have headroom
I/O healthy
application healthy
```

Result:

> **No tuning required. Preserve the current configuration and continue
> trend monitoring.**

------------------------------------------------------------------------

## 8.22.56 Anti-Patterns

Avoid:

``` text
Disable autovacuum because it uses I/O.

Set extremely low scale factors everywhere.

Increase workers whenever all workers are busy.

Increase memory without multiplying by concurrency.

Set cost delay to zero without impact analysis.

Raise freeze limits to reduce maintenance frequency.

Run VACUUM FULL as routine tuning.

Use one configuration for all tables.

Tune from one snapshot.

Tune around blockers.
```

------------------------------------------------------------------------

## 8.22.59 Production Principles

1.  **Autovacuum is a capacity system.**
2.  **Tune from measured demand rather than recipes.**
3.  **Separate maintenance triggering from maintenance throughput.**
4.  **Baseline before changing configuration.**
5.  **Classify workload by churn and relation size.**
6.  **Prefer the narrowest tuning scope that solves the problem.**
7.  **Large tables often require different trigger settings from small
    tables.**
8.  **Calculate effective thresholds rather than discussing scale factor
    alone.**
9.  **Do not over-vacuum the entire fleet to solve one hot table.**
10. **Insert-heavy relations still require vacuum maintenance.**
11. **ANALYZE tuning is separate from VACUUM tuning.**
12. **Worker utilization alone is not worker saturation.**
13. **More workers consume more CPU, memory, I/O, and WAL capacity.**
14. **Capacity planning must consider maintenance queueing.**
15. **Cost delay trades maintenance throughput for foreground
    protection.**
16. **Do not reduce throttling without available resource headroom.**
17. **Maintenance memory must be multiplied by concurrency.**
18. **Repeated index vacuum cycles are evidence, not automatic proof of
    insufficient memory.**
19. **Storage is frequently the real maintenance bottleneck.**
20. **Maintain CPU and storage headroom.**
21. **Include WAL and replica capacity in maintenance planning.**
22. **Blockers are not solved by additional vacuum capacity.**
23. **XID/MXID safety overrides routine efficiency concerns.**
24. **Use per-table configuration for exceptional relations.**
25. **Validate PostgreSQL-version-specific reloptions before use.**
26. **Capacity must exceed sustained maintenance demand with safety
    margin.**
27. **Maintenance utilization is a derived SRE model.**
28. **Forecast future data and transaction growth.**
29. **Plan for bulk operations and workload bursts.**
30. **Tune partition maintenance by lifecycle.**
31. **Change one major variable at a time when practical.**
32. **Dynamic settings are not risk-free settings.**
33. **Validate over multiple maintenance cycles.**
34. **Define success and rollback criteria before change.**
35. **No tuning required is a valid outcome.**
36. **Do not disable autovacuum as a routine performance workaround.**
37. **Do not raise correctness limits merely to reduce maintenance.**
38. **Do not use VACUUM FULL as routine autovacuum tuning.**
39. **Do not tune from one snapshot.**
40. **Measure cleanup effectiveness after every material change.**

``` text
validate cleanup effectiveness
      |
      v
validate resource and service impact
```

The central SRE/DBRE rule is:

> **Tune autovacuum from measured maintenance demand, cleanup
> effectiveness, correctness runway, and available resource
> capacity---not from isolated parameter values or generic tuning
> recipes.**

The objective is not:

``` text
make VACUUM run faster
```

The objective is:

``` text
maintenance demand
       |
       v
sustainable maintenance capacity
       |
       v
bounded backlog
       |
       v
safe XID/MXID runway
       |
       v
acceptable infrastructure cost
       |
       v
healthy replicas
       |
       v
healthy applications
```
