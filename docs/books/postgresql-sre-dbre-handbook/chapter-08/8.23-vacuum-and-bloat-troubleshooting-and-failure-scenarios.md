# 8.23 — Vacuum and Bloat Troubleshooting and Failure Scenarios

**Edition:** Revised Final / Canonical Edition
**Book:** PostgreSQL SRE & DBRE Handbook
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance
**Technical Baseline:** PostgreSQL 18
**Status:** **COMPLETE — CANONICAL**

---

## 8.23.1 Purpose

Vacuum incidents should not be diagnosed by changing one autovacuum parameter, terminating a maintenance worker, rebuilding indexes, or running `VACUUM FULL` simply because a relation is large.

A production investigation must establish:

* what symptom is occurring;
* which relations and databases are affected;
* whether maintenance is being triggered;
* whether maintenance is making progress;
* whether completed maintenance is effective;
* whether a cleanup horizon is being retained;
* whether maintenance demand exceeds sustainable capacity;
* whether heap or index growth is involved;
* whether XID or MultiXact correctness runway is shrinking;
* whether replication is contributing to retention;
* whether application behavior is the underlying cause;
* and which remediation provides the required recovery with the lowest production risk.

The governing principle is:

> **Diagnose maintenance failure from evidence before changing maintenance behavior.**

A practical troubleshooting sequence is:

```text
symptom
   ↓
scope
   ↓
evidence
   ↓
maintenance state
   ↓
cleanup effectiveness
   ↓
blocking horizon
   ↓
resource capacity
   ↓
correctness runway
   ↓
root cause
   ↓
lowest-risk remediation
   ↓
validation
   ↓
new steady state
```

The objective is not merely to make VACUUM run.

The objective is to restore a sustainable maintenance system while preserving correctness, availability, capacity, and application performance.

---

# Part I — Troubleshooting Model

## 8.23.2 Separate Symptoms from Root Causes

Common symptoms include:

* increasing dead tuples;
* increasing relation size;
* increasing index size;
* frequent autovacuum activity;
* autovacuum apparently not running;
* long-running autovacuum;
* VACUUM completing without expected cleanup;
* repeated index-vacuum cycles;
* increasing XID age;
* increasing MultiXact age;
* storage growth;
* elevated I/O latency;
* increased CPU consumption;
* WAL spikes;
* replica lag;
* application latency during maintenance;
* inability to return relation space to the filesystem.

None of these observations proves a root cause.

For example:

```text
Symptom:
dead tuples increasing

Possible causes:
    |
    +-- maintenance trigger too late
    +-- insufficient worker availability
    +-- insufficient cleanup throughput
    +-- old transaction retaining a cleanup horizon
    +-- idle-in-transaction session
    +-- prepared transaction
    +-- replication-slot retention
    +-- standby-related horizon retention
    +-- workload churn exceeds maintenance capacity
    +-- maintenance repeatedly interrupted
    +-- relation-specific configuration
    +-- storage saturation
    +-- application transaction design
```

The responder must determine which branch is supported by evidence.

---

## 8.23.3 Determine Whether This Is Actually a Vacuum Problem

Do not infer causality from correlation.

For example:

```text
high CPU
```

does not prove:

```text
autovacuum caused the CPU pressure
```

Similarly:

```text
large table
```

does not prove:

```text
severe heap bloat
```

and:

```text
VACUUM completed but the file did not shrink
```

does not prove:

```text
VACUUM failed
```

Standard VACUUM primarily makes reusable space available within the relation. Physical shrinking is a different maintenance objective.

The troubleshooting process must therefore distinguish:

```text
logical cleanup
physical reuse
physical reclamation
statistics maintenance
freeze maintenance
index maintenance
```

before choosing remediation.

---

## 8.23.4 Establish Incident Scope

Determine whether the problem affects:

```text
one relation
one partition
multiple relations
one schema
one database
multiple databases
the entire PostgreSQL instance
```

Then classify the suspected failure domain:

```text
Triggering
Worker capacity
Cleanup throughput
Blocking horizon
Replication retention
Storage / I/O
CPU
Memory
WAL / replication
XID correctness
MXID correctness
Heap structure
Index structure
Configuration
Application workload
```

Avoid instance-wide configuration changes when the evidence points to a single relation.

# Part II — Initial Evidence Collection

## 8.23.5 Capture a Production Triage Snapshot

Capture configuration and incident context before making changes.

```sql
SELECT
    current_database() AS database_name,
    current_timestamp AS captured_at,
    current_setting('server_version') AS server_version,
    current_setting('autovacuum') AS autovacuum,
    current_setting('autovacuum_max_workers') AS autovacuum_max_workers,
    current_setting('autovacuum_worker_slots') AS autovacuum_worker_slots,
    current_setting('autovacuum_naptime') AS autovacuum_naptime,
    current_setting('autovacuum_vacuum_threshold') AS vacuum_threshold,
    current_setting('autovacuum_vacuum_scale_factor') AS vacuum_scale_factor,
    current_setting('autovacuum_vacuum_max_threshold') AS vacuum_max_threshold,
    current_setting('autovacuum_vacuum_insert_threshold') AS vacuum_insert_threshold,
    current_setting('autovacuum_vacuum_insert_scale_factor') AS vacuum_insert_scale_factor;
```

The evidence snapshot allows later comparison between:

```text
before
change
after
```

and prevents the investigation from depending on memory or assumptions.

---

## 8.23.6 Identify Relations with Cleanup Backlog

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    n_ins_since_vacuum,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 50;
```

Treat `n_live_tup` and `n_dead_tup` as estimates.

A single snapshot is useful for triage, but maintenance-capacity diagnosis requires time-series deltas.

---

## 8.23.7 Calculate Dead-Tuple Ratio

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    round(
        100.0 * n_dead_tup
        / NULLIF(n_live_tup + n_dead_tup, 0),
        2
    ) AS dead_tuple_pct,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY dead_tuple_pct DESC NULLS LAST;
```

Do not use percentage alone.

Evaluate:

```text
absolute backlog
+
relative backlog
+
relation size
+
growth rate
+
maintenance cadence
+
post-maintenance recovery
+
business criticality
```

A high percentage on a small relation and a lower percentage on a multi-billion-row relation can represent very different operational risks.

---

## 8.23.8 Find Active VACUUM Operations

```sql
SELECT
    p.pid,
    p.datname,
    p.relid::regclass AS relation,
    p.phase,
    p.heap_blks_total,
    p.heap_blks_scanned,
    p.heap_blks_vacuumed,
    p.index_vacuum_count,
    p.num_dead_item_ids,
    p.dead_tuple_bytes,
    p.max_dead_tuple_bytes,
    p.indexes_total,
    p.indexes_processed,
    p.delay_time
FROM pg_stat_progress_vacuum AS p;
```

In PostgreSQL 18, regular VACUUM operations, including autovacuum workers, are represented through `pg_stat_progress_vacuum`.

`VACUUM FULL` is a table rewrite and its progress belongs to the cluster/table-rewrite progress mechanism rather than ordinary VACUUM progress.

---

## 8.23.9 Determine Whether VACUUM Is Progressing

Collect multiple samples.

Example:

```text
T0:
heap_blks_scanned = 2,000,000

T1:
heap_blks_scanned = 2,400,000

T2:
heap_blks_scanned = 2,900,000
```

indicates forward progress.

Compare that with:

```text
T0 = 2,000,000
T1 = 2,000,000
T2 = 2,000,000
```

A static counter requires investigation, but does not by itself prove the worker is stuck.

Determine:

* current phase;
* wait event;
* index-processing state;
* cost-delay behavior;
* I/O condition;
* lock condition;
* whether another phase-specific counter is moving.

Do not terminate maintenance based only on elapsed runtime.

# Part III — Autovacuum Is Not Running

## 8.23.10 Verify Autovacuum Configuration

Check:

```sql
SHOW autovacuum;
SHOW autovacuum_max_workers;
SHOW autovacuum_worker_slots;
SHOW autovacuum_naptime;
```

Inspect relation-level overrides:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.reloptions
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm')
  AND c.reloptions IS NOT NULL
ORDER BY 1, 2;
```

Relation-level configuration can explain behavior that appears inconsistent with instance defaults.

---

## 8.23.11 Determine Whether the Vacuum Trigger Has Been Reached

PostgreSQL 18 has distinct triggering paths.

For update/delete-driven autovacuum, the effective trigger is conceptually:

```text
calculated threshold
=
autovacuum_vacuum_threshold
+
autovacuum_vacuum_scale_factor × reltuples
```

with PostgreSQL 18's maximum-threshold cap:

```text
effective threshold
=
min(
    calculated threshold,
    autovacuum_vacuum_max_threshold
)
```

when the maximum threshold is enabled.

Therefore:

```text
dead tuples exist
```

does not necessarily mean:

```text
autovacuum should already have started
```

Calculate the effective trigger.

---

## 8.23.12 Insert-Driven Vacuum Trigger

Insert-heavy relations require a separate troubleshooting path.

PostgreSQL 18 uses the insert-driven trigger conceptually as:

```text
vacuum insert threshold
=
autovacuum_vacuum_insert_threshold
+
autovacuum_vacuum_insert_scale_factor
× number of tuples
× unfrozen portion of the table
```

This is different from the update/delete dead-tuple trigger.

Therefore diagnose:

```text
update/delete workload
        |
        v
ordinary vacuum trigger

insert-heavy workload
        |
        v
insert-driven vacuum trigger
```

Do not conclude that autovacuum scheduling is wrong until the applicable trigger has been evaluated.

Insert-driven vacuum remains important even when few dead tuples exist because VACUUM also contributes to freezing and visibility-map maintenance.

---

## 8.23.13 Worker Slots Versus Concurrent Workers

PostgreSQL 18 distinguishes:

```text
autovacuum_worker_slots
```

from:

```text
autovacuum_max_workers
```

Operationally:

```text
autovacuum_worker_slots
=
reserved backend-slot ceiling for autovacuum workers

autovacuum_max_workers
=
configured concurrent worker limit
```

The effective worker capacity cannot exceed the available worker-slot ceiling.

Do not inspect `autovacuum_max_workers` alone when diagnosing apparent worker starvation.

---

## 8.23.14 Check Active Worker Utilization

```sql
SELECT
    pid,
    datname,
    backend_type,
    state,
    wait_event_type,
    wait_event,
    query_start,
    query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY query_start;
```

If effective worker capacity remains continuously occupied while eligible maintenance accumulates, worker availability may contribute to the incident.

However:

> **All autovacuum workers being busy does not prove that increasing worker concurrency is the correct remediation.**

The actual constraint may be:

* storage;
* CPU;
* maintenance memory;
* blocking horizons;
* very large maintenance units;
* cost throttling;
* or workload generation rate.

---

# Part IV — VACUUM Runs but Cleanup Is Ineffective

## 8.23.15 Scheduling Failure Versus Cleanup Failure

Distinguish:

```text
VACUUM did not start
```

from:

```text
VACUUM started but could not remove the expected tuples
```

The first points toward triggering, worker availability, or configuration.

The second frequently points toward retained visibility horizons or insufficient maintenance throughput.

---

## 8.23.16 Investigate Long-Running Transactions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    backend_xmin,
    wait_event_type,
    wait_event,
    now() - xact_start AS transaction_age,
    left(query, 300) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

An old transaction can retain a snapshot that prevents tuple versions from becoming removable.

Before terminating a transaction, determine:

```text
application owner
transaction purpose
business operation
rollback impact
retry behavior
dependency chain
current production impact
```

Backend termination is a remediation action, not a diagnostic query.

---

## 8.23.17 Idle-in-Transaction Sessions

Pay particular attention to:

```text
state = idle in transaction
```

A common failure sequence is:

```text
application begins transaction
        ↓
query executes
        ↓
application leaves transaction open
        ↓
old snapshot remains
        ↓
cleanup horizon cannot advance
        ↓
dead tuples remain
        ↓
VACUUM appears ineffective
        ↓
heap/index growth continues
```

The incident response should address both:

```text
immediate retained horizon
+
application behavior that created it
```

Otherwise the condition is likely to recur.

---

## 8.23.18 Prepared Transactions

Inspect:

```sql
SELECT
    transaction,
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
ORDER BY prepared;
```

Old prepared transactions can retain transaction horizons.

Do not blindly execute:

```sql
COMMIT PREPARED 'gid';
```

or:

```sql
ROLLBACK PREPARED 'gid';
```

A prepared transaction belongs to a two-phase commit workflow.

Resolution requires knowledge of:

* transaction coordinator;
* intended outcome;
* application state;
* external participants;
* duplicate-processing risk;
* rollback consequences.

---

# Part V — Replication Retention

## 8.23.19 Inspect Replication Slots

```sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    xmin,
    catalog_xmin,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots
ORDER BY slot_name;
```

Interpret the fields separately:

```text
xmin
    ↓
tuple-cleanup retention horizon

catalog_xmin
    ↓
catalog-tuple cleanup horizon

restart_lsn
    ↓
WAL retention horizon
```

`confirmed_flush_lsn` is associated with logical replication-slot progress and is not expected to have equivalent meaning for every slot type.

Do not collapse all replication-slot retention into one generic "slot lag" condition.

---

## 8.23.20 Never Drop a Slot Merely Because It Is Inactive

An inactive slot may belong to:

* a temporarily disconnected replica;
* disaster-recovery infrastructure;
* a logical subscriber;
* a change-data-capture pipeline;
* a maintenance process;
* an intentionally paused consumer.

Before removing a slot determine:

```text
owner
consumer
purpose
last known activity
expected reconnect behavior
rebuild requirements
data-loss implications
RPO impact
RTO impact
```

Dropping a required slot can force downstream recovery or reconstruction.

---

## 8.23.21 PostgreSQL 18 Inactive-Slot Prevention

PostgreSQL 18 provides:

```text
idle_replication_slot_timeout
```

as a mechanism for invalidating replication slots that remain inactive beyond a configured period.

This is a **preventive architecture control**, not an incident shortcut.

Before enabling it, evaluate whether the replication design intentionally allows consumers to remain disconnected for longer periods.

Use the distinction:

```text
incident remediation
    ↓
identify and validate the slot owner

long-term prevention
    ↓
evaluate idle_replication_slot_timeout
```

Never use timeout configuration to compensate for unknown slot ownership.

---

# Part VI — VACUUM Cannot Keep Up

## 8.23.22 Compare Maintenance Demand with Cleanup Capacity

The fundamental capacity relationship is:

```text
maintenance demand
versus
sustainable maintenance capacity
```

If:

```text
dead-tuple generation rate
>
sustainable cleanup rate
```

then backlog grows even when autovacuum is functioning as designed.

This is primarily a capacity problem.

---

## 8.23.23 Identify High-Churn Relations

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    autovacuum_count,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY (n_tup_upd + n_tup_del) DESC
LIMIT 50;
```

Use time-series deltas when estimating workload rates.

Cumulative counters alone do not show whether the workload currently generates:

```text
100 dead tuples/second
```

or:

```text
100,000 dead tuples/second
```

---

## 8.23.24 Trigger Problem Versus Throughput Problem

Use this decision:

```text
Does maintenance start too late?
        |
       yes
        |
        v
investigate trigger configuration

Does maintenance start appropriately
but backlog continues growing?
        |
       yes
        |
        v
investigate throughput,
blocking horizons,
and resource capacity
```

Lowering scale factors cannot repair a system where VACUUM already runs continuously but cannot keep pace.

---

# Part VII — VACUUM Is Too Slow

## 8.23.25 Check Storage Capacity

VACUUM is storage-intensive.

Correlate PostgreSQL progress with infrastructure signals:

* read latency;
* write latency;
* IOPS;
* throughput;
* queue depth;
* storage throttling;
* burst-credit exhaustion where applicable;
* filesystem capacity;
* cloud-volume limits.

A worker can be healthy but slow because the underlying storage system cannot provide sufficient throughput.

---

## 8.23.26 Check Cost-Based Throttling

Inspect:

```sql
SHOW vacuum_cost_delay;
SHOW vacuum_cost_limit;
SHOW autovacuum_vacuum_cost_delay;
SHOW autovacuum_vacuum_cost_limit;
```

Long runtime does not automatically mean the worker is stuck.

Autovacuum may be intentionally throttled.

Correlate:

```text
runtime
+
progress
+
delay_time
+
storage utilization
+
application latency
```

before changing cost controls.

---

## 8.23.27 Vacuum Buffer Usage

PostgreSQL 18 exposes:

```text
vacuum_buffer_usage_limit
```

which controls the buffer-access-strategy size used by VACUUM and ANALYZE.

Inspect:

```sql
SHOW vacuum_buffer_usage_limit;
```

This setting is another capacity dimension.

Increasing it can potentially improve maintenance behavior for some workloads, but an excessively large buffer strategy can compete with useful application pages.

Therefore:

> **Do not increase `vacuum_buffer_usage_limit` merely because VACUUM is slow.**

First determine whether the actual constraint is buffer behavior rather than storage, throttling, blocking, or maintenance memory.

---

## 8.23.28 Repeated Index-Vacuum Cycles

Inspect:

```text
index_vacuum_count
dead_tuple_bytes
max_dead_tuple_bytes
```

Repeated index-vacuum cycles can indicate that the dead-item information being processed exceeds the effective maintenance-memory capacity available to the worker.

For autovacuum, evaluate:

```text
autovacuum_work_mem
```

and remember that when it is `-1`, the worker inherits:

```text
maintenance_work_mem
```

Do not evaluate the per-worker number in isolation.

Capacity planning must consider:

```text
effective memory per worker
×
concurrent workers
```

along with other PostgreSQL and operating-system memory demand.

---

# Part VIII — High CPU During VACUUM

## 8.23.29 Prove CPU Attribution

Do not infer causality from coincident timing.

Correlate:

```text
PostgreSQL backend PID
+
pg_stat_progress_vacuum
+
OS process CPU
+
application workload
+
checkpoint activity
+
WAL activity
+
other maintenance
```

If application backends are consuming most CPU, changing autovacuum configuration may not address the incident.

---

## 8.23.30 Index Maintenance Cost

Relations with many large indexes can make maintenance more expensive.

Inventory indexes:

```sql
SELECT
    indexrelid::regclass AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan
FROM pg_stat_user_indexes
WHERE relid = 'schema.table_name'::regclass
ORDER BY pg_relation_size(indexrelid) DESC;
```

Do not interpret low `idx_scan` as automatic permission to drop an index.

Consider:

* statistics-reset timing;
* unique constraints;
* primary keys;
* infrequent business workloads;
* reporting cycles;
* disaster-recovery processes;
* application releases;
* specialized queries.

---

# Part IX — Disk Keeps Growing

## 8.23.31 Reusable Space Is Not Filesystem Reclamation

A common incorrect conclusion is:

```text
VACUUM completed
+
table file did not shrink
=
VACUUM failed
```

Standard VACUUM primarily makes space reusable inside the relation.

Therefore distinguish:

```text
internal reusable space
```

from:

```text
physical filesystem reclamation
```

before escalating to a rewrite.

---

## 8.23.32 Historical Growth Versus Active Growth

Ask:

```text
Is the relation still growing?
```

or:

```text
Did it stabilize after a historical workload spike?
```

A relation may remain physically large while containing space that PostgreSQL can reuse.

Size alone does not establish active bloat growth.

Trend the relation over time.

---

## 8.23.33 VACUUM FULL Safety Gate

`VACUUM FULL` is not routine vacuum remediation.

It performs a physical rewrite and requires strong locking.

Before approving it document:

```text
business justification
measured reclaimable-space objective
working-space requirement
lock window
application impact
WAL impact
replica impact
monitoring plan
abort criteria
post-operation validation
```

Use it only when physical reclamation is genuinely required and the operational consequences are acceptable.

---

# Part X — Index Bloat and Structural Problems

## 8.23.34 Separate Index Conditions

These conditions are not equivalent:

```text
large index
≠
bloated index
≠
unused index
≠
corrupt index
```

A large index may be appropriate for the data volume.

A bloated index may contain inefficient physical space utilization.

An unused index is a workload/governance question.

A corrupt index is a correctness problem.

Each requires different evidence and remediation.

---

## 8.23.35 When REINDEX May Be Appropriate

Evaluate:

```text
physical size
growth trend
index type
workload pattern
query impact
structural evidence
rebuild cost
available storage
locking requirements
WAL generation
replica impact
```

before rebuilding.

Do not perform broad index rebuilds simply because relation size is high.

---

## 8.23.36 REINDEX Production Safety

Evaluate whether normal or concurrent rebuilding is appropriate.

A concurrent rebuild reduces some blocking behavior but introduces:

* additional work;
* additional runtime;
* additional storage demand;
* additional WAL;
* possible invalid intermediate index states following failure;
* operational cleanup requirements.

Use the smallest justified scope.

---

# Part XI — XID Wraparound Risk

## 8.23.37 XID Risk Is a Correctness Incident

Check database-level age:

```sql
SELECT
    datname,
    age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

Then identify old relations:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname,
    c.relkind,
    age(c.relfrozenxid) AS xid_age
FROM pg_class AS c
JOIN pg_namespace AS n
  ON n.oid = c.relnamespace
WHERE c.relkind IN ('r', 'm', 't')
ORDER BY age(c.relfrozenxid) DESC
LIMIT 100;
```

Transaction-ID exhaustion is not an ordinary performance incident.

Correctness runway takes priority.

---

## 8.23.38 Investigate Why Freeze Progress Is Failing

Potential causes include:

```text
maintenance throughput insufficient
old transaction
idle-in-transaction session
prepared transaction
retained replication horizon
storage saturation
maintenance interruption
large maintenance units
incorrect configuration
application behavior
```

Do not respond only by increasing `autovacuum_freeze_max_age`.

That changes a boundary; it does not repair the underlying maintenance failure.

---

## 8.23.39 Vacuum Failsafe

Vacuum failsafe behavior exists to prioritize transaction-ID safety when age becomes dangerously high.

Operationally:

```text
normal maintenance
        ↓
maintenance falling behind
        ↓
forced anti-wraparound maintenance
        ↓
failsafe behavior
        ↓
native emergency protection
```

Failsafe behavior is not a desired operating state.

> **Failsafe activation represents serious maintenance debt and shrinking correctness runway.**

Production monitoring and intervention should occur well before the system depends on failsafe behavior.

---

## 8.23.40 Emergency XID Recovery

When transaction-ID exhaustion risk becomes severe, follow a correctness-first recovery sequence.

Investigate and resolve retained horizons such as:

* old running transactions;
* old prepared transactions;
* stale or problematic replication slots where appropriate.

Then perform standard VACUUM.

A database-wide standard VACUUM is the simplest recovery approach when appropriate.

When recovery time must be reduced, targeted standard VACUUM of the oldest relations can be used as part of the recovery strategy.

Do **not** substitute `VACUUM FULL` for standard VACUUM in this recovery path.

The goal is to advance freezing and restore transaction-ID runway, not to reclaim filesystem space.

---

# Part XII — MultiXact Risk

## 8.23.41 Check MXID Age Independently

```sql
SELECT
    datname,
    mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY mxid_age(datminmxid) DESC;
```

Healthy XID age does not imply healthy MultiXact age.

Monitor both dimensions independently.

---

## 8.23.42 Investigate Lock-Heavy Workloads

MultiXact generation can be associated with row-level locking patterns.

Investigate workloads involving operations such as:

```sql
SELECT ...
FOR UPDATE;
```

and related row-locking behavior.

Track:

```text
MXID generation rate
oldest MXID
freeze progress
lock-heavy workload
pg_multixact growth
```

Treat MultiXact exhaustion risk as a correctness condition.

---

# Part XIII — Replica Lag During Maintenance

## 8.23.43 Correlate Maintenance with WAL

Monitor:

```sql
SELECT *
FROM pg_stat_wal;
```

and:

```sql
SELECT
    application_name,
    state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    write_lag,
    flush_lag,
    replay_lag
FROM pg_stat_replication;
```

Compare rates over time.

A single snapshot is rarely enough to establish causality.

---

## 8.23.44 Replica Lag Is Not Automatically a Vacuum Problem

Possible concurrent causes include:

* application write bursts;
* bulk ingestion;
* index creation;
* checkpoints;
* network limitations;
* replica storage constraints;
* long-running replica queries;
* maintenance;
* infrastructure saturation.

Establish temporal and quantitative correlation before attributing replica lag to vacuum.

# Part XIV — Autovacuum and Application Latency

## 8.23.45 Do Not Disable Autovacuum as the First Response

Disabling autovacuum can transform a transient performance complaint into:

```text
dead-tuple accumulation
        ↓
heap/index growth
        ↓
stale statistics
        ↓
freeze debt
        ↓
XID/MXID risk
        ↓
emergency maintenance
```

Instead determine whether the contention is caused by:

```text

CPU
memory
WAL
locks
buffer pressure
maintenance concurrency
cost configuration
application workload
```

Then tune the correct dimension.

---

## 8.23.46 Controlled Mitigation

Potential evidence-driven controls include:

```text
relation-specific trigger adjustment
relation-specific cost controls
worker-capacity adjustment
maintenance-memory adjustment
vacuum-buffer adjustment
storage-capacity improvement
workload scheduling
application transaction correction
index rationalization
```

Change one major dimension at a time whenever incident severity allows.

This preserves causal evidence.

# Part XV — VACUUM Appears Stuck

## 8.23.47 Phase-Aware Troubleshooting

```sql
SELECT
    p.pid,
    p.relid::regclass AS relation,
    p.phase,
    p.heap_blks_total,
    p.heap_blks_scanned,
    p.heap_blks_vacuumed,
    p.index_vacuum_count,
    p.indexes_total,
    p.indexes_processed,
    p.dead_tuple_bytes,
    p.max_dead_tuple_bytes,
    p.delay_time,
    a.wait_event_type,
    a.wait_event
FROM pg_stat_progress_vacuum AS p
LEFT JOIN pg_stat_activity AS a
  ON a.pid = p.pid;
```

Interpret progress according to phase.

A counter that does not move during one phase may not be the relevant progress indicator for that phase.

---

## 8.23.48 Do Not Kill VACUUM Based Only on Runtime

Ask:

```text
Is progress advancing?
Is correctness-critical maintenance involved?
Is the worker blocked?
Is the worker intentionally throttled?
Is storage saturated?
Is application impact severe?
How much work has already completed?
Will autovacuum simply restart the work?
What happens to correctness runway if it is terminated?
```

Termination requires an operational justification.

Runtime alone is insufficient.

# Part XVI — Manual Maintenance

## 8.23.49 Targeted Standard VACUUM

A targeted standard VACUUM can be appropriate when:

* immediate cleanup assistance is required;
* a retained horizon has been removed;
* autovacuum scheduling is insufficient for current recovery needs;
* post-incident cleanup is required;
* transaction-age runway needs recovery.

Baseline example:

```sql
VACUUM (VERBOSE) schema.table_name;
```

If planner statistics also require refresh:

```sql
VACUUM (VERBOSE, ANALYZE) schema.table_name;
```

Do not add `ANALYZE` automatically when the incident objective is only tuple cleanup.

---

## 8.23.50 `SKIP_LOCKED` Is Not Fully Non-Blocking VACUUM

PostgreSQL supports:

```sql
VACUUM (SKIP_LOCKED) schema.table_name;
```

but `SKIP_LOCKED` must not be interpreted as:

```text
VACUUM can no longer block
```

There are operations during VACUUM for which locking can still occur, including index-related work.

With `VACUUM ANALYZE`, additional relation, partition, inheritance, or foreign-table processing can also involve locking behavior.

For partitioned targets, inability to acquire the necessary lock at the parent level can affect processing of the associated partitions.

If `SKIP_LOCKED` is used operationally, record:

```text
why skipping was acceptable
what could be skipped
whether the complete maintenance objective was achieved
how skipped work will be revisited
```

Do not use it to hide a persistent locking problem.

# Part XIX — Production Remediation Hierarchy

## 8.23.53 Prefer the Lowest-Risk Effective Remediation

A useful order is:

```text
1. remove a confirmed blocker safely

2. correct application transaction behavior

3. correct relation-specific maintenance settings

4. correct maintenance-throughput constraints

5. increase infrastructure/resource capacity where justified

6. perform targeted standard maintenance

7. perform targeted structural maintenance

8. perform blocking physical rewrite only when justified
```

Do not start at step 8 merely because it appears decisive.

# Part XXII — Common Troubleshooting Mistakes

## 8.23.61 Anti-Patterns

Avoid:

1. disabling autovacuum because application queries are slow;
2. increasing workers without measuring resource capacity;
3. lowering scale factors globally because one table has high churn;
4. ignoring PostgreSQL 18's maximum vacuum threshold;
5. ignoring the separate insert-driven vacuum trigger;
6. assuming high `n_dead_tup` alone proves failure;
7. assuming large relations are automatically bloated;
8. assuming standard VACUUM should shrink files;
9. running `VACUUM FULL` as routine cleanup;
10. dropping inactive replication slots without identifying consumers;
11. terminating transactions without application context;
12. resolving prepared transactions without transaction-coordinator context;
13. killing a long VACUUM without examining progress;
14. increasing maintenance memory without calculating worker concurrency;
15. increasing `vacuum_buffer_usage_limit` without evaluating buffer pressure;
16. rebuilding every index because one index appears inefficient;
17. treating large, bloated, unused, and corrupt indexes as the same condition;
18. treating XID/MXID risk as ordinary performance incidents;
19. treating `SKIP_LOCKED` as a guarantee that VACUUM cannot block;
20. changing multiple tuning dimensions simultaneously without necessity;
21. closing an incident immediately after a maintenance command succeeds;
22. failing to verify the new steady state.

# Part XXIV — Production Troubleshooting Principles

## 8.23.63 Core Principles

> **A running VACUUM is not proof that cleanup is effective.**

> **A long VACUUM is not proof that VACUUM is stuck.**

> **A large relation is not proof of bloat.**

> **A large index is not automatically bloated, unused, or corrupt.**

> **Space not returned to the filesystem is not proof that standard VACUUM failed.**

> **Autovacuum tuning cannot repair a cleanup horizon retained by an old transaction or required replication state.**

> **Increasing worker concurrency without underlying resource capacity can make both maintenance and application performance worse.**

> **XID and MultiXact maintenance failures are correctness risks, not merely performance problems.**

> **`SKIP_LOCKED` does not make VACUUM universally non-blocking.**

> **`VACUUM FULL` is a controlled physical rewrite, not routine vacuum troubleshooting.**

> **A completed maintenance command is not proof that an incident is resolved.**

> **The incident is resolved only when maintenance behavior returns to a sustainable steady state.**

---

## 8.23.64 Correctness Before Efficiency

Use the operational priority:

```text
correctness
    >
availability
    >
capacity
    >
performance
    >
efficiency
```

This is an SRE/DBRE prioritization model rather than a PostgreSQL-defined severity hierarchy.

When XID or MXID runway becomes dangerous, correctness recovery takes precedence over ordinary optimization.

---

## 8.23.65 Evidence Before Configuration

The troubleshooting sequence should remain:

```text
observe
   ↓
measure
   ↓
form causal hypothesis
   ↓
change
   ↓
validate
```

not:

```text
observe symptom
   ↓
change several parameters
   ↓
hope
```

Configuration changes must have an expected mechanism of improvement.

---

## 8.23.66 Relation-Specific Before Instance-Wide

If one high-churn table requires earlier maintenance, prefer evaluating relation-level controls before globally increasing maintenance activity across thousands of healthy relations.

Global settings should represent an appropriate fleet baseline.

Exceptions should be justified by relation behavior.

---

## 8.23.67 Capacity Before Concurrency

Before increasing worker concurrency ask:

```text
Does storage have headroom?
Does CPU have headroom?
Does memory have headroom?
Can WAL generation increase safely?
Can replicas absorb the additional work?
Will application latency remain acceptable?
```

Worker capacity without infrastructure capacity is not additional useful maintenance capacity.

# Part XXVI — Escalation Model

## 8.23.69 Escalate When Correctness Runway Is Shrinking

Escalation is warranted when:

```text
XID/MXID age rising
+
maintenance unable to recover
+
remaining runway shrinking
```

even if application latency remains normal.

Correctness incidents can develop before customer-facing symptoms appear.

---

## 8.23.70 Escalate When Capacity Recovery Is Failing

Escalate when:

```text
backlog grows across maintenance cycles
+
VACUUM completes
+
post-VACUUM baseline worsens
```

This indicates that normal maintenance no longer restores a sustainable baseline.

---

## 8.23.71 Escalate Destructive Maintenance Separately

Actions such as:

```text
VACUUM FULL
broad REINDEX
dropping replication slots
terminating business transactions
resolving prepared transactions
```

require explicit operational ownership and safety review.

They should not be hidden inside automated troubleshooting.

# Part XXVIII — Final Takeaway

## 8.23.73 Troubleshooting Objective

Vacuum and bloat troubleshooting is fundamentally an exercise in **maintenance-flow diagnosis**.

The responder must establish whether PostgreSQL:

```text
did not become eligible for maintenance,

became eligible but lacked a worker,

started maintenance too late,

ran maintenance but lacked throughput,

ran maintenance but was intentionally throttled,

ran maintenance but was constrained by storage,

ran maintenance but lacked effective memory,

ran maintenance but was blocked by a retained horizon,

completed maintenance but new churn recreated the backlog,

successfully reclaimed reusable space without physically shrinking the relation,

maintained the heap while a separate index problem remained,

or approached an XID/MXID correctness boundary.
```

The production objective is not simply:

```text
make VACUUM run
```

and it is not simply:

```text
make the table smaller
```

The objective is:

```text
effective cleanup
+
sustainable maintenance capacity
+
XID/MXID correctness
+
controlled heap/index growth
+
acceptable infrastructure consumption
+
healthy replication
+
protected application performance
```

A production vacuum incident is closed only when the evidence demonstrates that the maintenance system has returned to a sustainable state.
