# 8.24 — Maintenance Automation and Production Runbooks

**Edition:** Revised Final / Canonical Edition
**Book:** PostgreSQL SRE & DBRE Handbook
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance
**Technical Baseline:** PostgreSQL 18
**Status:** COMPLETE — CANONICAL

---

## 8.24.1 Purpose

PostgreSQL maintenance automation should reduce repetitive operational work without turning potentially destructive database actions into unattended scripts.

PostgreSQL already automates routine `VACUUM` and `ANALYZE` through autovacuum. External automation should complement PostgreSQL's native maintenance mechanisms rather than replace or unnecessarily compete with them.

A production maintenance system should automate:

```text
observe
    ↓
collect
    ↓
classify
    ↓
prioritize
    ↓
recommend
    ↓
execute approved safe operations
    ↓
validate
    ↓
record
```

while retaining explicit human authorization for operations whose locking, correctness, recovery, or capacity characteristics can materially affect production.

The governing principle is:

> **Automate evidence collection and low-risk maintenance aggressively; automate disruptive remediation conservatively.**

---

# Part I — Automation Architecture

## 8.24.2 Native Maintenance First

PostgreSQL autovacuum is the primary mechanism for routine automatic `VACUUM` and `ANALYZE`.

External schedulers should not routinely duplicate:

```text
autovacuum
+
external full-database VACUUM
```

without a demonstrated operational requirement.

Unnecessary duplicate maintenance can create:

* additional I/O;
* increased WAL generation;
* CPU contention;
* redundant scans;
* longer maintenance queues;
* connection pressure;
* replica pressure;
* harder incident attribution.

External automation is most valuable for:

```text
health assessment
correctness monitoring
exception handling
partition-parent ANALYZE
post-load maintenance
restore/upgrade statistics recovery
controlled targeted maintenance
maintenance validation
reporting
capacity forecasting
governance
```

---

## 8.24.3 Maintenance Control Plane

A production design should separate:

```text
Collection
     ↓
Evaluation
     ↓
Decision
     ↓
Execution
     ↓
Verification
     ↓
Audit
```

These stages should not be collapsed into one opaque shell script.

A failed collector must not accidentally authorize remediation.

A failed execution must not be recorded as successful.

A successful command must not be treated as a successful maintenance outcome until the intended database state is validated.

---

## 8.24.4 Handbook Automation Safety Classes

The following classes are an SRE/DBRE handbook operational model. They are **not PostgreSQL-defined terminology**.

### Class A — Read-Only

Strong candidates for unattended automation:

```text
statistics collection
VACUUM progress collection
XID/MXID age collection
replication-slot inspection
long-transaction detection
prepared-transaction inspection
storage telemetry
I/O telemetry
WAL telemetry
relation-size collection
maintenance history
alert evaluation
capacity forecasting
```

### Class B — Controlled Low-Risk Maintenance

Potential candidates for policy-controlled automation:

```text
targeted standard VACUUM
targeted ANALYZE
partition-parent ANALYZE
post-load ANALYZE
approved vacuumdb maintenance
approved age-targeted maintenance
```

These operations still require preflight and validation gates.

### Class C — High-Impact Maintenance

Require stronger controls and normally an approval workflow:

```text
large maintenance campaigns
large-scale REINDEX CONCURRENTLY
broad manual VACUUM campaigns
autovacuum configuration changes
worker-concurrency changes
maintenance-memory changes
```

### Class D — Destructive or Materially Blocking

Ordinary unattended automation must not execute:

```text
VACUUM FULL
non-concurrent REINDEX on critical production relations
DROP replication slot
terminate application backend
COMMIT PREPARED
ROLLBACK PREPARED
DROP TABLE
TRUNCATE
forced failover
```

Default policy:

```text
Class A → automate

Class B → automate with explicit policy gates

Class C → approval workflow

Class D → explicit human authorization
```

# Part II — Maintenance Controller

## 8.24.5 Controller Responsibilities

A production maintenance controller should determine:

1. what requires maintenance;
2. why it requires maintenance;
3. whether PostgreSQL is already handling it;
4. whether a retained horizon prevents cleanup;
5. whether infrastructure has sufficient headroom;
6. whether correctness runway requires escalation;
7. whether the target is the intended database role;
8. whether the operation is permitted automatically;
9. whether execution succeeded;
10. whether the intended database condition improved;
11. whether the system reached a sustainable steady state.

Avoid:

```text
metric > threshold
      ↓
run command
```

Use:

```text
metric
  ↓
persistence
  ↓
context
  ↓
classification
  ↓
safety gates
  ↓
action
  ↓
validation
```

---

## 8.24.6 Maintenance Inventory

Maintain inventory metadata containing at least:

```text
environment
cluster/service
instance
database
schema
relation
relation type
partition status
business criticality
owner
maintenance policy
approved maintenance window
expected churn
expected size
special reloptions
automation class

```

Without ownership, topology, and criticality information, automation cannot make sufficiently safe production decisions.

# Part III — Read-Only Health Collection

## 8.24.7 Relation Maintenance Snapshot

```sql
SELECT
    current_database() AS database_name,
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    n_ins_since_vacuum,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    last_analyze,
    last_autoanalyze,
    vacuum_count,
    autovacuum_count,
    analyze_count,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Store snapshots over time.

Cumulative statistics should be converted into interval deltas before they are interpreted as workload or maintenance rates.

---

## 8.24.8 PostgreSQL 18 Maintenance-Time Telemetry

PostgreSQL 18 exposes cumulative maintenance timing in the table statistics views.

Collect:

```sql
SELECT
    schemaname,
    relname,
    total_vacuum_time,
    total_autovacuum_time,
    total_analyze_time,
    total_autoanalyze_time
FROM pg_stat_user_tables
ORDER BY total_autovacuum_time DESC;
```

These values are cumulative.

Automation should calculate:

```text
current cumulative value
-
previous cumulative value
=
interval maintenance time
```

rather than interpreting the total as current resource consumption.

This helps distinguish:

```text
maintenance frequency
```

from:

```text
maintenance time consumption
```

and improves maintenance capacity planning.

---

## 8.24.9 XID Health Collection

```sql
SELECT
    datname,
    age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

Collect transaction-age correctness independently from dead-tuple monitoring.

Low dead-tuple counts do not prove that transaction-age maintenance is healthy.

---

## 8.24.10 MultiXact Health Collection

```sql
SELECT
    datname,
    mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY mxid_age(datminmxid) DESC;
```

Track XID and MXID independently.

Do not infer healthy MultiXact state from healthy XID age.

---

## 8.24.11 Active VACUUM Collection

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    num_dead_item_ids,
    dead_tuple_bytes,
    max_dead_tuple_bytes,
    indexes_total,
    indexes_processed,
    delay_time
FROM pg_stat_progress_vacuum;
```

Repeated snapshots can reveal:

```text
scan progress
heap-vacuum progress
index-processing progress
dead-item processing
delay behavior
maintenance duration
```

Do not alert merely because VACUUM has been running for a long time.

Prefer:

```text
long runtime
+
unexpected lack of progress
+
operational consequence
```

---

## 8.24.12 Cost-Delay Timing

The `delay_time` field should not be interpreted without checking whether cost-delay timing is being tracked.

Collect:

```sql
SHOW track_cost_delay_timing;
```

When timing collection is disabled, a zero or unavailable delay measurement must not be interpreted as proof that no vacuum cost-delay throttling occurred.

Automation should record the configuration state with the telemetry.

# Part IV — Cleanup Blockers and Retained Horizons

## 8.24.13 Long-Running Transactions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    backend_xmin,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    left(query, 500) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Automation may:

```text
detect
classify
alert
identify owner
correlate maintenance impact
attach evidence
```

It should not automatically terminate a transaction solely because an age threshold was crossed.

---

## 8.24.14 Idle-in-Transaction Sessions

Detect sessions in:

```text
idle in transaction
```

and classify severity using:

```text
transaction age
backend_xmin
relation churn
dead-tuple growth
XID runway
business criticality
application ownership
```

Transaction age alone is insufficient to determine operational severity.

---

## 8.24.15 Prepared Transactions

```sql
SELECT
    transaction,
    gid,
    prepared,
    owner,
    database
FROM pg_prepared_xacts
ORDER BY prepared;
```

Automation may identify old prepared transactions and their maintenance consequences.

Automation must not independently choose between:

```text
COMMIT PREPARED
```

and:

```text
ROLLBACK PREPARED
```

Resolution belongs to the transaction-coordination and application-recovery process.

---

## 8.24.16 Replication Slots

```sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    xmin,
    catalog_xmin,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots
ORDER BY slot_name;
```

Interpret separately:

```text
xmin
→ tuple-cleanup horizon

catalog_xmin
→ catalog-cleanup horizon

restart_lsn
→ WAL-retention horizon
```

Automation should distinguish these failure modes rather than issuing one generic "replication slot problem" alert.

Never implement:

```text
active = false
    ↓
DROP SLOT
```

as an automation policy.

# Part V — Target Selection

## 8.24.17 Do Not Select Targets from Dead-Tuple Percentage Alone

A maintenance candidate policy may consider:

```text
absolute dead tuples
dead-tuple percentage
relation size
churn rate
time since maintenance
maintenance duration
XID/MXID age
business criticality
cleanup trend
```

A useful handbook conceptual model is:

```text
maintenance priority
=
correctness risk
+
cleanup debt
+
growth rate
+
business impact
```

This is an SRE/DBRE policy model, not a PostgreSQL formula.

---

## 8.24.18 Exclude Relations Already Being Maintained

Before launching manual maintenance, determine whether PostgreSQL or another controller is already maintaining the target.

Avoid:

```text
autovacuum
+
scheduled VACUUM
+
operator VACUUM
```

all attempting to address the same maintenance condition.

Native maintenance activity must be part of target selection.

---

## 8.24.19 Relation-Level Policies

Prefer explicit policies such as:

```text
Tier 0 — critical OLTP
Tier 1 — high churn
Tier 2 — standard
Tier 3 — archival
Tier 4 — controlled manual maintenance
```

Apply different:

```text
thresholds
windows
concurrency
validation periods
escalation policies
```

rather than one global maintenance policy.

# Part VI — `vacuumdb` Automation

## 8.24.20 Role of `vacuumdb`

`vacuumdb` is PostgreSQL's command-line utility for performing `VACUUM` and related `ANALYZE` operations.

It is useful for operational automation because it provides database, table, schema, analysis, age-selection, concurrency, and buffer-control options without requiring a custom maintenance client for every workflow.

Relevant capabilities include:

```text
database targeting
table targeting
schema targeting
ANALYZE
ANALYZE-only
staged ANALYZE
parallel jobs
minimum XID age
minimum MXID age
missing-statistics selection
buffer-usage control
verbose reporting
connection parameters
```

---

## 8.24.21 Basic Targeted Maintenance

```bash
vacuumdb \
  --dbname=appdb \
  --table='public.orders' \
  --verbose
```

Do not embed passwords directly in shell command arguments.

Use approved libpq authentication and secret-management mechanisms for the environment.

---

## 8.24.22 VACUUM and ANALYZE

When both operations are intentionally required:

```bash
vacuumdb \
  --dbname=appdb \
  --table='public.orders' \
  --analyze \
  --verbose
```

Do not automatically add ANALYZE to every cleanup operation.

Tuple cleanup and planner-statistics maintenance have related but distinct objectives.

---

## 8.24.23 Analyze-Only Automation

```bash
vacuumdb \
  --dbname=appdb \
  --table='public.orders' \
  --analyze-only \
  --verbose
```

Useful scenarios include:

```text
large data load
major distribution change
partition lifecycle event
statistics recovery
```

when tuple cleanup is not the primary objective.

---

## 8.24.24 Analyze in Stages

For appropriate restore, upgrade, or severe statistics-recovery scenarios:

```bash
vacuumdb \
  --dbname=appdb \
  --analyze-in-stages
```

This should not be the ordinary recurring ANALYZE strategy for a healthy database.

Where the workflow and privileges support it, PostgreSQL 18 can also target objects missing statistics:

```bash
vacuumdb \
  --dbname=appdb \
  --analyze-in-stages \
  --missing-stats-only
```

Use this deliberately; do not assume the required restricted statistics visibility is available to every maintenance identity.

---

## 8.24.25 XID-Age Targeted Maintenance

For a controlled age-based maintenance campaign:

```bash
vacuumdb \
  --dbname=appdb \
  --min-xid-age=<approved_age> \
  --verbose
```

This allows PostgreSQL to select relations based on transaction-ID age.

It can be preferable to maintaining a separate external relation-selection implementation for appropriate age-based campaigns.

However:

```text
XID age threshold
≠
complete XID incident diagnosis
```

The correctness and blocker analysis from 8.23 remains mandatory when transaction-age runway is deteriorating.

---

## 8.24.26 MultiXact-Age Targeted Maintenance

For controlled MultiXact-age maintenance:

```bash
vacuumdb \
  --dbname=appdb \
  --min-mxid-age=<approved_age> \
  --verbose
```

Again:

```text
MXID threshold
    ↓
candidate selection
```

does not replace:

```text
correctness diagnosis
+
retained-horizon investigation
+
capacity analysis
+
post-maintenance validation
```

---

## 8.24.27 Buffer Usage Control

Where a specific controlled operation requires a different vacuum buffer strategy:

```bash
vacuumdb \
  --dbname=appdb \
  --table='public.orders' \
  --buffer-usage-limit='8MB' \
  --verbose
```

Do not blindly increase the buffer-usage limit.

A larger strategy may improve some maintenance workloads but can also increase pressure on useful shared-buffer contents.

Prefer evidence-driven per-operation control where appropriate rather than changing a server-wide value solely for one maintenance campaign.

---

# Part VII — Parallel Maintenance

## 8.24.28 `vacuumdb --jobs`

Parallel jobs can reduce elapsed maintenance time while increasing concurrent demand.

Conceptually:

```text
more jobs
    ↓
more concurrent maintenance
    ↓
potentially lower wall-clock duration
    ↓
higher aggregate resource consumption
```

Before increasing job count evaluate:

```text
CPU
storage latency
IOPS
throughput
WAL generation
replica capacity
connection capacity
application latency
```

`vacuumdb --jobs=N` creates concurrent database connections. Connection headroom must therefore be part of the maintenance capacity calculation.

---

## 8.24.29 Capacity Before Concurrency

Never encode:

```text
jobs = CPU count
```

as a universal rule.

Storage, WAL, replica capacity, or database connection capacity may become limiting before CPU.

A controller should enforce:

```text
configured maximum
+
current infrastructure headroom
+
connection headroom
+
workload window
+
target criticality
```

before permitting parallel maintenance.

Do not combine broad parallel-job automation with `VACUUM FULL` as a routine production pattern.

`VACUUM FULL` remains separately gated because of its rewrite, locking, disk-space, and concurrency characteristics.

# Part VIII — Partition and Temporary-Table Maintenance

## 8.24.30 Partitioned Parent Statistics

Autovacuum processes physical partitions as ordinary tables, but it does not automatically analyze the partitioned parent based on changes occurring in those partitions.

Therefore maintain an explicit policy for parent-level `ANALYZE` where planner behavior requires parent statistics.

Example:

```sql
ANALYZE public.events;
```

Possible triggers:

```text
new partition attached
large partition loaded
major distribution change
retention event
bulk correction
statistics-age policy
```

---

## 8.24.31 Partition Lifecycle Hook

A controlled workflow can use:

```text
create partition
      ↓
load
      ↓
validate
      ↓
attach
      ↓
ANALYZE affected partition when needed
      ↓
ANALYZE parent when justified
      ↓
validate representative plans
```

Event-driven maintenance is often preferable to waiting for a generic clock-based job after a known partition lifecycle event.

---

## 8.24.32 Hierarchy Scope Must Be Explicit

Automation generating `VACUUM` or `ANALYZE` commands against inheritance or partition hierarchies must explicitly understand intended scope.

Where supported by the command and required by the workflow, use `ONLY` when child processing is not intended.

Do not assume:

```text
parent target
=
parent-only maintenance
```

without verifying the command semantics.

---

## 8.24.33 Temporary Tables

Temporary tables require a separate maintenance model.

Autovacuum cannot manage another session's temporary tables as ordinary persistent relations.

Long-lived sessions that create large or heavily modified temporary tables may therefore require explicit `VACUUM` or `ANALYZE` behavior from the owning session or application.

External automation should not assume it can maintain temporary relations using the same controller used for persistent application tables.

# Part IX — Scheduling

## 8.24.34 Scheduler Options

Maintenance can be orchestrated using approved infrastructure such as:

```text
cron
systemd timers
enterprise schedulers
Kubernetes CronJobs
cloud-native schedulers
workflow orchestration platforms
```

The scheduler should invoke version-controlled maintenance logic rather than become the maintenance-policy implementation itself.

Prefer:

```text
scheduler
    ↓
version-controlled maintenance program
    ↓
PostgreSQL
```

---

## 8.24.35 Maintenance Windows

Not every standard VACUUM or ANALYZE requires a low-traffic window.

Higher-impact work should nevertheless consider:

```text
business traffic
batch workloads
ETL
backups
checkpoints
replication
deployments
other maintenance
```

Avoid a maintenance storm in which independent jobs all start at the same clock boundary.

Use controlled staggering or jitter where appropriate.

---

## 8.24.36 Timeouts

Automated jobs should have appropriate operational boundaries.

Consider:

```text
connection timeout
statement timeout
lock timeout
job-runtime timeout
scheduler timeout
```

Timeouts must match the expected operation.

A timeout shorter than legitimate maintenance duration creates repeated maintenance failures rather than safety.

# Part X — Concurrency and Idempotency

## 8.24.37 Prevent Duplicate Runs

Use an appropriate concurrency mechanism so:

```text
previous run still active
+
next schedule fires
```

does not create overlapping maintenance campaigns.

Possible controls include:

```text
scheduler concurrency policy
distributed lock
database advisory lock
job-state table
orchestration-platform lease
```

The locking mechanism must fail safely.

---

## 8.24.38 Per-Target Ownership

Prevent multiple workers from independently selecting the same relation.

A target can transition conceptually through:

```text
eligible
   ↓
claimed
   ↓
running
   ↓
validating
   ↓
complete
```

or:

```text
running
   ↓
failed
   ↓
reevaluation
```

Target ownership should be observable and auditable.

---

## 8.24.39 Idempotency Is a Production Requirement

Distributed systems frequently encounter ambiguous outcomes.

Automation must tolerate cases where a previous operation:

```text
never started
started and failed
started and disconnected
completed but validation failed
completed but status recording failed
```

Do not respond by blindly repeating the command.

Use:

```text
rediscover current database state
        ↓
determine whether action remains necessary
        ↓
claim target
        ↓
execute
        ↓
validate actual database state
        ↓
record outcome
```

The database's current state is authoritative.

Scheduler history alone is not.

# Part XI — Retry Policy

## 8.24.40 Classify Failures Before Retrying

### Potentially Retryable

```text
temporary connection failure
scheduler interruption
short transient infrastructure failure
```

### Requires Reevaluation

```text
lock conflict
statement timeout
resource saturation
replica degradation
unexpected runtime
role/topology change
```

### Do Not Blindly Retry

```text
permission failure
invalid relation
incorrect configuration
insufficient disk
correctness alert
unexpected SQL error
safety-gate failure
```

---

## 8.24.41 Bounded Backoff

Use bounded retry behavior:

```text
attempt 1
   ↓
delay
   ↓
rediscover state
   ↓
attempt 2 if still appropriate
   ↓
longer delay
   ↓
rediscover state
   ↓
final bounded attempt
   ↓
escalate
```

Use jitter where multiple automation workers could otherwise retry simultaneously.

Always define a hard retry ceiling.

---

# Part XII — Preflight Safety Gates

## 8.24.42 Standard VACUUM Preflight

Before launching targeted manual VACUUM, verify:

```text
target still exists
target still requires maintenance
no equivalent maintenance already active
correct environment selected
correct database selected
correct relation selected
expected server role confirmed
permissions valid
storage sufficiently healthy
replication sufficiently healthy
application impact acceptable
correctness state understood
```

If the target no longer requires maintenance:

```text
skip safely
```

rather than executing because an earlier scheduler snapshot selected it.

---

## 8.24.43 HA and Failover Awareness

Before execution, establish that the connection is to the intended PostgreSQL role.

A PostgreSQL-side signal is:

```sql
SELECT pg_is_in_recovery();
```

This should be combined with the authoritative topology information from the HA platform, managed service, operator, or service-discovery system.

A production gate should conceptually require:

```text
expected environment
+
expected database
+
expected endpoint
+
expected server role
+
approved action
=
execution permitted
```

A role mismatch should produce:

```text
STOP + REEVALUATE
```

not automatic continuation.

`pg_is_in_recovery()` is a useful PostgreSQL safety signal, not a complete topology-management system.

---

## 8.24.44 Infrastructure Headroom Gate

Example policy:

```text
if storage latency is critical:
    defer optional performance-driven maintenance

if replica lag is critical:
    defer optional high-WAL maintenance

if connection capacity is exhausted:
    do not launch additional parallel jobs

if XID/MXID correctness runway is critical:
    escalate rather than defer blindly

if application incident is active:
    follow incident-specific maintenance policy
```

Correctness maintenance may need to proceed when ordinary optimization work should be deferred.

# Part XIII — Execution Logging

## 8.24.45 Every Automated Action Requires an Audit Record

Record:

```text
run ID
environment
database
server role
target
reason
policy
command class
start time
end time
duration
exit status
preflight result
validation result
retry count
automation version
operator/approver where applicable
```

The system should be able to answer:

> **Why did automation touch this relation?**

without reconstructing the event from shell history.

---

## 8.24.46 PostgreSQL Autovacuum Logging

`log_autovacuum_min_duration` can provide server-side evidence about autovacuum activity.

Depending on configuration and event type, useful evidence can include:

```text
completed maintenance
maintenance duration/details
maintenance skipped because of conflicting locks
maintenance affected by concurrently disappearing relations
```

Feed relevant events into the maintenance history and failure-classification pipeline.

Distinguish:

```text
maintenance not eligible
maintenance eligible but not scheduled
maintenance running
maintenance completed
maintenance skipped/conflicted
maintenance completed but ineffective
```

Do not collapse these states into one generic "autovacuum failure."

Logging levels must also consider production log volume.

# Part XIV — Post-Execution Validation

## 8.24.47 Exit Code Is Not the Success Criterion

Do not define:

```text
command returned 0
=
maintenance objective achieved
```

For VACUUM validate:

```text
cleanup trend improved
maintenance debt reduced
correctness runway improved where applicable
```

For ANALYZE validate:

```text
statistics refreshed
planner behavior validated where required
```

For structural maintenance validate:

```text
expected structural outcome achieved
application healthy
replication healthy
capacity healthy
```

---

## 8.24.48 Validation Window

Some maintenance outcomes require observation over time.

Use:

```text
T0 = pre-maintenance baseline

T1 = immediate post-action state

T2 = representative workload interval

T3 = subsequent expected maintenance cycle
```

A sustainable steady state matters more than an immediately successful command.

# Part XV — Production Runbook RB-VAC-001

## 8.24.49 High Dead-Tuple Backlog

**Trigger**

Sustained dead-tuple accumulation with failed recovery.

**Objective**

Determine whether the condition is primarily:

```text
trigger
worker
throughput
blocker
replication
resource
application
```

related.

**Procedure**

1. capture relation statistics;
2. inspect active VACUUM;
3. calculate effective maintenance trigger;
4. inspect relation reloptions;
5. inspect worker availability;
6. inspect long transactions;
7. inspect prepared transactions;
8. inspect replication slots;
9. inspect I/O and CPU;
10. compare tuple generation and cleanup rates;
11. classify root cause;
12. execute the lowest-risk effective remediation;
13. validate through a representative workload interval.

**Safety rule**

Do not automatically run `VACUUM FULL`.

# Part XVI — Production Runbook RB-VAC-002

## 8.24.50 Autovacuum Not Running

**Trigger**

A relation appears maintenance-eligible but expected autovacuum activity is absent.

**Checks**

```text
autovacuum enabled
track_counts enabled
effective update/delete threshold
effective insert threshold
relation reloptions
worker availability
current maintenance
relation type
```

Escalate when:

```text
eligible backlog continues growing
+
maintenance does not occur
+
correctness or capacity runway deteriorates
```

# Part XVII — Production Runbook RB-VAC-003

## 8.24.51 VACUUM Running but Ineffective

Inspect:

```text
progress phase
long transactions
idle-in-transaction sessions
prepared transactions
replication xmin
catalog_xmin
new workload churn
```

If a retained horizon is identified:

```text
identify owner
    ↓
assess business impact
    ↓
resolve through approved process
    ↓
allow/rerun cleanup
    ↓
validate
```

Do not repeatedly launch additional VACUUM workers against a horizon that cannot advance.

# Part XVIII — Production Runbook RB-VAC-004

## 8.24.52 XID Runway Degradation

**Trigger**

Transaction-age runway crosses the organization's warning or critical policy.

**Immediate evidence**

```text
database XID age
oldest relation XID ages
old transactions
prepared transactions
relevant retained horizons
active anti-wraparound maintenance
maintenance progress
```

Priority:

```text
correctness
>
normal performance optimization
```

For a controlled age-targeted campaign, `vacuumdb --min-xid-age` may assist target selection.

It does not replace diagnosis.

Use standard VACUUM for XID recovery.

Do not substitute `VACUUM FULL`.

# Part XIX — Production Runbook RB-VAC-005

## 8.24.53 MultiXact Runway Degradation

**Trigger**

MXID age approaches policy thresholds or fails to recover.

Inspect:

```text
database MXID age
relation MXID age
lock-heavy workloads
freeze progress
maintenance capacity
MultiXact growth
```

A controlled campaign may use `vacuumdb --min-mxid-age` where appropriate.

Treat MultiXact exhaustion as a correctness condition.

Healthy XID age does not prove healthy MXID age.

## 8.24.54 Long Transaction Blocking Cleanup

**Trigger**

An old transaction or snapshot materially retains cleanup.

Procedure:

```text
identify PID
identify application
identify owner
determine transaction purpose
determine rollback impact
determine retry behavior
evaluate maintenance impact
obtain authorization if termination is required
```

Automation may collect and correlate this evidence.

Ordinary maintenance automation must not blindly terminate the backend.

identify consumer

# Part XXII — Production Runbook RB-VAC-008

## 8.24.56 Partition Parent Statistics

**Trigger**

Partition lifecycle or distribution changes may make parent-level statistics stale.

Procedure:

1. identify the affected parent;
2. validate partition changes;
3. analyze the affected partition when appropriate;
4. run controlled parent `ANALYZE` when justified;
5. inspect statistics state;
6. validate representative plans for critical workloads.

This is a strong candidate for event-driven automation.

# Part XXIII — Production Runbook RB-VAC-009

## 8.24.57 Maintenance Causing Resource Pressure

**Trigger**

Maintenance correlates with:

```text
high storage latency
high CPU
WAL pressure
replica lag
connection pressure
application latency
```

Procedure:

1. prove maintenance attribution;
2. inspect active workers/jobs;
3. inspect maintenance phase;
4. inspect storage;
5. inspect cost-delay behavior;
6. inspect concurrency;
7. inspect buffer strategy;
8. inspect WAL/replication;
9. inspect connection consumption;
10. reduce only the responsible dimension;
11. validate application recovery;
12. validate maintenance sustainability.

Do not disable autovacuum as the default response.

## 8.24.58 Emergency Disk Pressure

**Trigger**

Storage utilization threatens database availability.

Separate:

```text

table/index growth
temporary files
logs
replication-slot WAL retention
historical heap/index size
active bloat growth
```

before selecting remediation.

Do not assume:

```text
disk pressure
=
VACUUM FULL required
```

# Part XXV — Automation Guardrails

## 8.24.59 Hard Safety Gates

Automation should refuse high-impact actions when required context is missing.

Examples:

```text
unknown owner
unknown business criticality
unknown replication consumer
unknown transaction purpose
unknown server role
insufficient disk headroom
unhealthy replica
active incident
unapproved maintenance window
unverified target
```

Safe result:

```text
STOP + ESCALATE
```

not:

```text
BEST GUESS + EXECUTE
```

---

## 8.24.60 Explicit Allowlist

Where automatic targeted maintenance is permitted, use an explicit allowlist containing fields such as:

```text
database
schema
relation
allowed action
maximum concurrency
maximum runtime
maintenance window
approval class
```

Database accessibility does not imply authorization for every maintenance operation.

---

## 8.24.61 Kill Switch

A production maintenance platform must provide a documented kill switch.

Distinguish:

```text
stop scheduling new work
```

from:

```text
terminate work already executing
```

A kill switch should normally be able to:

```text
prevent new work
prevent retries
preserve evidence
freeze queue advancement
```

Whether an already-running database operation should be cancelled must follow the action-specific safety policy.

Blind cancellation is not automatically safer than allowing an operation to complete.

# Part XXXIV — Canonical Automation Principles

## 8.24.78 Principle 1 — Automate Evidence First

The highest-value maintenance automation is often:

```text
collect
correlate
classify
forecast
```

rather than automatic remediation.

---

## 8.24.79 Principle 2 — Native Maintenance First

Do not build external automation that unnecessarily competes with PostgreSQL autovacuum.

Use external automation for exceptions, governance, lifecycle events, validation, correctness monitoring, and operations requiring context unavailable to native autovacuum.

---

## 8.24.80 Principle 3 — Correctness Overrides Schedule

A maintenance window must not justify ignoring dangerous XID or MXID runway.

Correctness-critical maintenance follows correctness policy rather than convenience scheduling.

---

## 8.24.81 Principle 4 — Capacity Before Concurrency

More workers or jobs are beneficial only when the underlying CPU, storage, WAL, replica, and connection capacity can support the additional work.

> **Parallelism is a capacity decision, not a scheduler convenience.**

---

## 8.24.82 Principle 5 — Idempotency Before Retry

When execution state is uncertain:

```text
rediscover
before
retry
```

Do not trust scheduler state over database state.

---

## 8.24.83 Principle 6 — Validate Outcomes

```text
command success
≠
maintenance success
```

A maintenance action succeeds operationally only when the intended database condition improves.

---

## 8.24.84 Principle 7 — Destructive Actions Require Humans

Ordinary automation should stop at the safety boundary.

Use:

```text
evidence
    ↓
recommendation
    ↓
approval
    ↓
controlled execution
```

for destructive or materially blocking operations.

## 8.24.86 Final Takeaway

Production PostgreSQL maintenance automation should not be designed as a collection of scheduled `VACUUM` commands.

It should be designed as a **maintenance control system**.

That system must understand:

```text
correctness
maintenance eligibility
cleanup effectiveness
retained horizons
worker capacity
storage capacity
CPU and memory
connection capacity
WAL and replication
topology role
application impact
relation criticality
maintenance history
```

before deciding what to do.

The strongest production model is:

```text
native PostgreSQL automation
+
continuous evidence collection
+
risk-aware external orchestration
+
targeted low-risk remediation
+
explicit destructive-action gates
+
idempotent execution
+
post-action validation
+
auditable runbooks
```

The objective is not maximum automation.

The objective is:

> **maximum safe automation with deterministic escalation when human judgment is required.**
