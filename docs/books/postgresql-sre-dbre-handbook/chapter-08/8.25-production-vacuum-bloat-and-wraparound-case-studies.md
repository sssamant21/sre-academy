# 8.25 — Production Vacuum, Bloat, and Wraparound Case Studies

**Edition:** Revised Final / Canonical Edition
**Book:** PostgreSQL SRE & DBRE Handbook
**Chapter 8:** Vacuum, Autovacuum, Bloat, and Maintenance
**Technical Baseline:** PostgreSQL 18
**Status:** COMPLETE — CANONICAL

---

## 8.25.1 Purpose

Production PostgreSQL maintenance incidents rarely begin with a clean diagnosis.

The first signal is usually indirect:

```text
database storage increasing
query latency increasing
autovacuum running continuously
WAL volume increasing
replica lag increasing
dead tuples accumulating
transaction age increasing
maintenance taking longer
disk capacity decreasing
```

None of these observations independently establishes root cause.

A production SRE/DBRE must move through:

```text
symptom
   ↓
scope
   ↓
correctness assessment
   ↓
evidence
   ↓
competing hypotheses
   ↓
failure classification
   ↓
lowest-risk remediation
   ↓
validation
   ↓
prevention
```

This section converts the architecture, diagnostics, tuning methodology, troubleshooting procedures, and automation controls from Sections 8.1–8.24 into production case studies.

The objective is not to memorize a command for each symptom.

The objective is to determine:

> **What condition prevents PostgreSQL maintenance from reaching or preserving a safe, sustainable steady state?**

---

# Part I — Production Investigation Model

## 8.25.2 Standard Investigation Framework

Every production maintenance case should answer:

1. What changed?
2. What is the production impact?
3. Which databases and relations are affected?
4. Is correctness at risk?
5. Is maintenance running?
6. Is running maintenance actually effective?
7. What retained horizons or resource constraints exist?
8. What evidence identifies the failure mechanism?
9. What is the lowest-risk effective remediation?
10. How will sustainable recovery be proven?
11. What prevents recurrence?

Do not start with:

```text
Which VACUUM command should I run?
```

Start with:

```text
What is preventing the maintenance system
from maintaining a safe steady state?
```

---

## 8.25.3 Evidence Hierarchy

Use evidence approximately in this order:

```text
correctness state
        ↓
maintenance state
        ↓
retained horizons
        ↓
relation statistics
        ↓
maintenance progress
        ↓
locks and transactions
        ↓
WAL and replication
        ↓
infrastructure capacity
        ↓
application behavior
```

Infrastructure evidence is essential, but it does not replace PostgreSQL-side evidence.

---

## 8.25.4 Production Priority Hierarchy

Use the handbook operating hierarchy:

```text
correctness
>
availability
>
capacity
>
performance
>
efficiency
```

This hierarchy is defined by this handbook; it is not PostgreSQL terminology.

An XID-wraparound threat therefore requires a different response from ordinary heap bloat even when the latter consumes more storage.

---

## 8.25.5 Activity, Progress, Effectiveness, and Sustainability

These are separate questions.

```text
Is maintenance active?
        ↓
Is it making progress?
        ↓
Is that progress producing the required outcome?
        ↓
Can the outcome be sustained under production workload?
```

Therefore:

```text
VACUUM running
≠
VACUUM effective
```

and:

```text
VACUUM completed
≠
maintenance problem solved
```

# Part II — Case Study 1: High Dead-Tuple Backlog Despite Active Autovacuum

## 8.25.6 Situation

A high-volume `orders` table receives continuous updates and deletes.

Monitoring reports:

```text
n_live_tup ≈ 180 million
n_dead_tup ≈ 46 million

autovacuum:
    active

storage:
    growing

application:
    increasing read latency
```

The initial conclusion is:

> Autovacuum is not working.

That conclusion is unsupported until maintenance progress and workload churn are measured.

---

## 8.25.7 Relation Evidence

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    n_ins_since_vacuum,
    n_mod_since_analyze,
    last_vacuum,
    last_autovacuum,
    vacuum_count,
    autovacuum_count
FROM pg_stat_user_tables
WHERE schemaname = 'public'
  AND relname = 'orders';
```

Take repeated samples rather than interpreting a single snapshot.

---

## 8.25.8 VACUUM Progress

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    num_dead_item_ids,
    dead_tuple_bytes,
    max_dead_tuple_bytes,
    indexes_total,
    indexes_processed,
    delay_time
FROM pg_stat_progress_vacuum
WHERE relid = 'public.orders'::regclass;
```

Repeated observations show the worker advancing.

The failure is therefore not simply:

```text
VACUUM absent
```

---

## 8.25.9 Derive Maintenance Demand and Capacity

PostgreSQL does not expose one canonical metric called:

```text
cleanup throughput
```

An SRE/DBRE can derive an operational estimate using interval observations of:

```text
table-statistics deltas
maintenance timing
VACUUM progress
logs
workload churn
```

For example, an illustrative analysis may estimate:

```text
derived dead-tuple generation:
    ~4.8M/hour

derived sustainable cleanup:
    ~3.1M/hour
```

These are calculated operational estimates, not native PostgreSQL metrics.

The important relationship is:

```text
maintenance demand
>
sustainable maintenance capacity
```

---

## 8.25.10 Root Cause

**Failure class:** `V-THROUGHPUT`

Autovacuum is active, but sustainable cleanup capacity is below workload demand.

Possible contributing factors include:

```text
relation size
storage latency
cost-delay throttling
index-maintenance work
worker availability
CPU
memory
WAL
replication pressure
concurrent application load
```

---

## 8.25.11 Remediation

Do not immediately:

```text
disable autovacuum
run VACUUM FULL
set extreme worker counts
```

Instead:

1. verify retained horizons;
2. measure infrastructure headroom;
3. inspect effective table-level autovacuum settings;
4. determine whether maintenance starts early enough;
5. measure sustainable maintenance throughput;
6. consider controlled targeted standard VACUUM where backlog recovery is justified;
7. adjust maintenance capacity only within sustainable infrastructure limits;
8. validate application impact.

---

## 8.25.12 Validation

Recovery requires:

```text
maintenance throughput
≥
new maintenance demand
```

for a representative interval.

A one-time reduction in `n_dead_tup` is not sufficient.

# Part III — Case Study 2: Autovacuum Runs but a Long Transaction Retains Cleanup

## 8.25.13 Situation

A large `customer_event` table shows persistent dead tuples.

Autovacuum repeatedly runs.

Increasing autovacuum frequency has not resolved the backlog.

---

## 8.25.14 Investigate Transactions

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    backend_xmin,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    left(query, 500) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Evidence identifies:

```text
state:
    idle in transaction

transaction age:
    17 hours

application:
    reporting-service
```

---

## 8.25.15 Root Cause

**Failure class:** `V-BLOCKER`

The retained transaction/snapshot prevents the cleanup horizon from advancing sufficiently.

Therefore:

```text
more VACUUM
≠
solution
```

while the underlying visibility requirement remains.

---

## 8.25.16 Remediation

1. identify the transaction owner;
2. determine whether the work is legitimate;
3. assess commit/rollback/termination impact;
4. use the approved application incident procedure;
5. resolve the transaction only with appropriate authorization;
6. allow cleanup to resume;
7. observe subsequent VACUUM behavior.

Automation may identify and escalate the blocker.

Routine maintenance automation should not blindly terminate application sessions.

---

## 8.25.17 Validation

Validate the mechanism:

```text
retaining transaction/snapshot resolved
        ↓
oldest required xmin horizon advances
        ↓
VACUUM can reclaim newly removable tuples
        ↓
cleanup backlog declines
```

Then fix the application behavior or transaction-control gap that permitted the condition.

---

# Part IV — Case Study 3: Replication Slot Retains Cleanup and WAL

## 8.25.18 Situation

A production database reports:

```text
database storage increasing
WAL storage increasing
dead tuples accumulating
```

Application workload has not materially increased.

---

## 8.25.19 Inspect Replication Slots

```sql
SELECT
    slot_name,
    slot_type,
    active,
    active_pid,
    xmin,
    catalog_xmin,
    restart_lsn,
    confirmed_flush_lsn,
    wal_status,
    safe_wal_size
FROM pg_replication_slots
ORDER BY slot_name;
```

An expected logical replication slot is inactive and has stopped advancing.

---

## 8.25.20 Interpret Slot Horizons Separately

Do not treat every field as equivalent.

```text
xmin
→ tuple-cleanup retention horizon

catalog_xmin
→ catalog-cleanup retention horizon

restart_lsn
→ WAL-retention requirement
```

One stalled slot may therefore create multiple operational consequences.

---

## 8.25.21 Root Cause

**Failure class:** `V-REPLICATION`

The consumer stopped advancing its slot.

PostgreSQL retains state required by the consumer.

Repeatedly increasing VACUUM activity does not remove that requirement.

---

## 8.25.22 Unsafe Response

Never automate:

```text
slot inactive
    ↓
DROP SLOT
```

because:

```text
inactive
≠
abandoned
≠
safe to drop
```

The slot may belong to a valid consumer that requires recovery.

---

## 8.25.23 Remediation

1. identify the consumer;
2. identify its service owner;
3. determine why consumption stopped;
4. quantify cleanup and WAL consequences;
5. establish whether the consumer can recover;
6. restore the consumer where appropriate;
7. drop or recreate a slot only through an approved replication recovery procedure.

---

## 8.25.24 Preventive Slot Controls

PostgreSQL 18 provides `idle_replication_slot_timeout` as a possible preventive architecture control.

Use it only where the replication architecture, ownership model, recovery procedure, and allowed inactivity period make automatic invalidation acceptable.

It is not an incident shortcut.

Do not convert:

```text
consumer ownership decision
```

into:

```text
aggressive timeout configuration
```

merely to relieve current disk pressure.

---

## 8.25.25 Validation

Validate independently:

```text
consumer advancement
cleanup horizons
WAL retention
disk utilization
replication health
```

Do not close the incident because only one metric recovered.

---

# Part V — Case Study 4: Database Approaching XID Wraparound

## 8.25.26 Situation

Monitoring reports rapidly increasing transaction-ID age.

The organization's critical correctness threshold has been crossed.

This is not an ordinary performance incident.

---

## 8.25.27 Establish XID Runway

```sql
SELECT
    datname,
    age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY age(datfrozenxid) DESC;
```

The first questions are:

```text
How much correctness runway remains?

Why is freezing not advancing?
```

---

## 8.25.28 Search for Retention and Maintenance Failures

Investigate:

```text
old transactions
idle-in-transaction sessions
prepared transactions
replication horizons
old relation ages
autovacuum activity
maintenance progress
worker capacity
storage capacity
maintenance configuration
```

Suppose the investigation identifies an old prepared transaction together with a sustained maintenance backlog.

---

## 8.25.29 Root Cause

**Failure classes:**

```text
V-XID
+
V-BLOCKER
```

The incident is now a correctness event.

---

## 8.25.30 Recovery Priority

Use:

```text
correctness recovery
>
normal maintenance efficiency
>
ordinary performance optimization
```

Optional maintenance and workload should not be allowed to consume resources needed for critical correctness recovery.

---

## 8.25.31 Recovery Sequence

Use:

```text
establish remaining XID runway
        ↓
identify retained horizons/blockers
        ↓
resolve justified blockers
        ↓
restore freezing progress
        ↓
run standard VACUUM at justified scope
        ↓
validate age reduction
        ↓
prove sustainable prevention
```

After retained horizons and blocking conditions are addressed, database-wide standard VACUUM can be a straightforward recovery approach when broad freezing progress is required.

When risk is concentrated in particular relations, targeted standard VACUUM of the oldest relations can reduce recovery time if target selection is well understood.

---

## 8.25.32 Do Not Use VACUUM FULL for XID Recovery

Do not use:

```text
VACUUM FULL
```

as an XID-exhaustion recovery mechanism.

`VACUUM FULL` is a relation rewrite with materially different locking, disk, WAL, replication, and availability consequences.

The XID problem is freezing/correctness progress, not physical compaction.

---

## 8.25.33 VACUUM FREEZE Is Not a Horizon Bypass

Do not assume:

```text
VACUUM FREEZE
=
emergency override
```

`VACUUM FREEZE` requests more aggressive freezing behavior.

It does not bypass MVCC visibility requirements or retained cleanup horizons.

Therefore:

```text
FREEZE
≠
override retained snapshot
```

and:

```text
FREEZE
≠
replacement for root-cause diagnosis
```

---

## 8.25.34 XID-Age Target Selection

A controlled maintenance campaign may use:

```bash
vacuumdb \
  --dbname=appdb \
  --min-xid-age=<approved_age> \
  --verbose
```

This helps select relations by XID age.

It does not determine why XID age became unsafe.

```text
age selector
≠
incident diagnosis
```

---

## 8.25.35 Validation

Confirm:

```text
database XID age decreases
oldest relation ages decrease
retained horizon removed
freezing progress restored
autovacuum returns to sustainable operation
correctness runway increases
```

Then determine why preventive controls failed.

---

# Part VI — Case Study 5: MultiXact Risk Hidden by Healthy XID Age

## 8.25.36 Situation

The XID dashboard appears healthy.

However, MultiXact age continues increasing in a workload with heavy row locking and concurrent updates.

---

## 8.25.37 Evidence

```sql
SELECT
    datname,
    mxid_age(datminmxid) AS mxid_age
FROM pg_database
ORDER BY mxid_age(datminmxid) DESC;
```

Then investigate relation-level MultiXact age and lock-heavy workload behavior.

---

## 8.25.38 Root Cause

**Failure class:** `V-MXID`

XID and MultiXact maintenance are separate correctness dimensions.

Therefore:

```text
healthy XID
≠
healthy MXID
```

---

## 8.25.39 Controlled MXID Target Selection

Where justified:

```bash
vacuumdb \
  --dbname=appdb \
  --min-mxid-age=<approved_age> \
  --verbose
```

can prioritize relations by MultiXact age.

Again:

```text
age selector
≠
root-cause diagnosis
```

---

## 8.25.40 Prevention

Maintain independent:

```text
XID runway monitoring
MXID runway monitoring
```

Do not collapse both into one generic vacuum-age metric.

# Part VII — Case Study 6: Large Table Misdiagnosed as Bloat

## 8.25.41 Situation

A production table occupies hundreds of gigabytes.

The incident report states:

> The table is bloated because it is large.

That conclusion is unsupported.

---

## 8.25.42 Separate Size from Physical Inefficiency

A large relation may contain a large amount of legitimate live data.

Therefore:

```text
large table
≠
bloated table
```

Similarly:

```text
large index
≠
bloated index
≠
unused index
≠
corrupt index
```

---

## 8.25.43 Evidence

Collect:

```text
live tuples
dead tuples
relation size
index size
historical size
workload churn
retention history
maintenance history
query behavior
```

Suppose evidence shows:

```text
live rows:
    steadily increasing

dead tuples:
    low

storage growth:
    proportional to business-data growth
```

---

## 8.25.44 Root Cause

There is no demonstrated maintenance failure.

The dominant condition is:

```text
legitimate data growth
```

not heap bloat.

---

## 8.25.45 Correct Response

Do not run `VACUUM FULL` merely because the relation is large.

Instead evaluate:

```text
capacity forecasting
retention
partitioning where justified
storage planning
query design
index strategy
```

---

# Part VIII — Case Study 7: DELETE Does Not Reduce Filesystem Usage

## 8.25.46 Situation

A retention process deletes approximately 70% of an old table.

Standard VACUUM completes.

Filesystem usage does not fall proportionally.

---

## 8.25.47 Interpretation

Standard VACUUM normally makes dead-row space reusable within PostgreSQL.

It does not generally rewrite the entire relation merely to return internal free space to the operating system.

Therefore:

```text
DELETE
+
standard VACUUM
=
space potentially reusable by PostgreSQL
```

does not imply:

```text
filesystem shrinks proportionally
```

---

## 8.25.48 Root Cause

There may be no maintenance failure.

The misunderstanding is between:

```text
logical deletion
```

```text
internal reusable space
```

and:

```text
physical filesystem reclamation
```

---

## 8.25.49 Decision Point

Ask:

```text
Will future table activity reuse the space?
```

If yes, internal reuse may be the preferable production outcome.

If physical reclamation is operationally necessary, evaluate rewrite-based alternatives independently.

---

## 8.25.50 VACUUM FULL Safety Gate

Before approving `VACUUM FULL`, evaluate:

```text
maintenance window
ACCESS EXCLUSIVE locking
additional working disk
table and index size
application impact
WAL
replication
runtime
failure recovery
```

Physical shrinkage is not automatically worth the operational cost.

---

# Part IX — Case Study 8: Index Growth After Heavy Churn

## 8.25.51 Situation

A table is operationally healthy after VACUUM, but an important B-tree index remains significantly larger than historical expectations.

Query performance has also degraded.

---

## 8.25.52 Do Not Jump Directly to REINDEX

Investigate:

```text
index-size history
table-size history
workload pattern
index usage
index structure
query plans
maintenance history
```

Distinguish:

```text
legitimate index size
index bloat
unused index
incorrect index
corrupt index
```

---

## 8.25.53 Root Cause

Evidence confirms persistent index physical inefficiency after a workload change.

**Failure class:** `V-INDEX`

---

## 8.25.54 REINDEX Decision

Compare:

```text
REINDEX
```

with:

```text
REINDEX CONCURRENTLY
```

across:

```text
locking
write availability
runtime
number of phases/scans
disk
CPU
WAL
replication
failure behavior
recovery
```

Ordinary REINDEX can materially block production activity.

`REINDEX CONCURRENTLY` reduces write-blocking but performs additional work and has operational restrictions.

Do not infer:

```text
CONCURRENTLY
=
risk free
```

---

## 8.25.55 Concurrent Reindex Failure

If concurrent reindexing fails:

```text
REINDEX CONCURRENTLY failure
        ↓
inspect resulting index state
        ↓
identify invalid/incomplete index artifacts
        ↓
determine appropriate recovery
        ↓
retry only after reevaluation
```

Do not blindly replay structural maintenance.

---

## 8.25.56 Validation

Verify:

```text
index structurally healthy
expected physical result achieved
queries use intended index
query latency improves where expected
replication recovers
capacity remains healthy
```

File-size reduction alone does not prove success.

---

# Part X — Case Study 9: VACUUM Causes Production I/O Pressure

## 8.25.57 Situation

During peak traffic:

```text
storage latency rises
application latency rises
VACUUM is active
```

The initial proposal is:

> Disable autovacuum.

That response is too broad.

---

## 8.25.58 Prove Attribution

Correlate:

```text
VACUUM phase
VACUUM progress
maintenance timing
storage latency
IOPS
throughput
CPU
WAL
replication
application latency
```

If interpreting `delay_time`, first check:

```sql
SHOW track_cost_delay_timing;
```

A zero `delay_time` does not prove no cost-delay sleeping if timing collection is disabled.

---

## 8.25.59 Determine the Maintenance Path

Before interpreting cost behavior, identify whether the work is:

```text
autovacuum
manual VACUUM
parallel/manual VACUUM
```

Then inspect the effective cost-delay configuration for that path.

Manual VACUUM and autovacuum should not automatically be assumed to have identical throttling behavior.

---

## 8.25.60 Root Cause

**Failure class:** `V-IO`

Evidence shows:

```text
application demand
+
maintenance demand
>
sustainable storage capacity
```

The issue is not that VACUUM exists.

The issue is that combined demand exceeds sustainable infrastructure capacity.

---

## 8.25.61 Remediation

Evaluate:

```text
cost-based delay
worker concurrency
manual maintenance concurrency
maintenance scheduling
buffer behavior
storage capacity
workload timing
```

Reduce or reschedule the responsible pressure without allowing maintenance debt to become unbounded.

---

## 8.25.62 Validation

Success requires:

```text
application latency acceptable
```

and:

```text
maintenance remains capable of keeping up
```

Application recovery at the cost of indefinitely increasing maintenance debt is not a sustainable fix.

---

# Part XI — Case Study 10: Excessive Autovacuum Worker Concurrency

## 8.25.63 Situation

A high-churn database has accumulated maintenance debt.

Worker concurrency is increased substantially.

Initially cleanup accelerates.

Then:

```text
storage latency increases
WAL increases
replica lag increases
application latency increases
```

---

## 8.25.64 Understand PostgreSQL 18 Worker Controls

Distinguish:

```text
autovacuum_worker_slots
```

from:

```text
autovacuum_max_workers
```

`autovacuum_worker_slots` represents the reserved worker-slot ceiling.

`autovacuum_max_workers` controls the configured concurrent autovacuum-worker limit within that capacity.

Evaluate actual worker activity rather than reasoning from one parameter alone.

---

## 8.25.65 Effective Resource Exposure

Evaluate:

```text
worker concurrency
×
effective maintenance memory
×
CPU demand
×
storage demand
×
WAL generation
×
replication impact
```

For memory, inspect `autovacuum_work_mem`.

When it is `-1`, effective behavior inherits `maintenance_work_mem`.

---

## 8.25.66 Root Cause

**Failure classes:**

```text
V-CONFIG
+
V-IO
```

Concurrency was increased beyond sustainable infrastructure capacity.

---

## 8.25.67 Lesson

More workers can increase maintenance throughput only until another resource becomes limiting.

> **Capacity before concurrency.**

---

# Part XII — Case Study 11: Autovacuum Trigger Too Late for a Large Relation

## 8.25.68 Situation

A very large table changes steadily but by a relatively small percentage of its total population.

Maintenance starts later than the workload can tolerate.

---

## 8.25.69 Update/Delete-Driven Trigger

Conceptually evaluate:

```text
vacuum threshold
=
autovacuum_vacuum_threshold
+
autovacuum_vacuum_scale_factor
×
relation tuple estimate
```

The effective relation configuration matters.

Do not inspect only:

```text
autovacuum_vacuum_scale_factor
```

in isolation.

---

## 8.25.70 Insert-Driven Trigger

Insert-driven maintenance has a separate trigger model.

Conceptually evaluate:

```text
insert vacuum threshold
=
autovacuum_vacuum_insert_threshold
+
autovacuum_vacuum_insert_scale_factor
×
relation tuple estimate
×
unfrozen-page proportion
```

Do not combine the update/delete and insert-driven triggers into one formula.

---

## 8.25.71 Root Cause

**Failure class:** `V-TRIGGER`

The configuration is valid but poorly matched to relation scale and workload churn.

---

## 8.25.72 Remediation

Prefer evidence-driven relation-level configuration when the problem is relation-specific.

The objective is:

```text
maintenance starts early enough
to prevent sustained backlog
```

without creating unnecessary maintenance pressure.

---

## 8.25.73 Validation

Observe multiple maintenance cycles:

```text
trigger reached
    ↓
maintenance begins
    ↓
backlog remains bounded
    ↓
resource impact remains acceptable
```

One successful VACUUM does not validate a trigger change.

---

# Part XIII — Case Study 12: Partitioned Parent Has Stale Statistics

## 8.25.74 Situation

Physical partitions receive normal maintenance.

Queries against the partitioned parent develop poor cardinality estimates.

---

## 8.25.75 Investigation

Check:

```text
partition statistics
parent statistics
partition lifecycle
data-distribution changes
representative query plans
```

The partitions themselves are maintained.

The partitioned parent's statistics are stale.

---

## 8.25.76 Root Cause

The missing operational process is:

```text
parent-level statistics maintenance
```

This should not be misclassified as failure of partition-level autovacuum.

---

## 8.25.77 Remediation

Where justified:

```sql
ANALYZE public.events;
```

Then validate representative plans.

Integrate parent-statistics maintenance into appropriate:

```text
partition creation
bulk load
attach
retention
major distribution change
```

workflows.

# Part XIV — Case Study 13: Maintenance Automation Loses Outcome Certainty

## 8.25.78 Situation

A Kubernetes maintenance job initiates PostgreSQL maintenance.

The orchestration pod then loses connectivity or terminates unexpectedly.

The scheduler records failure.

A retry is prepared.

---

## 8.25.79 Unsafe Assumption

Do not assume:

```text
scheduler failure
=
database operation never occurred
```

Loss of the orchestration process or its visibility does not by itself establish whether the PostgreSQL operation:

```text
completed
failed
was cancelled
or remains active
```

The outcome is uncertain until PostgreSQL state is rediscovered.

---

## 8.25.80 Root Cause

The operational failure is:

```text
automation outcome uncertainty
+
insufficient idempotency control
```

not necessarily a PostgreSQL maintenance failure.

---

## 8.25.81 Correct Recovery

```text
orchestrator loses certainty
        ↓
outcome = UNKNOWN
        ↓
rediscover PostgreSQL state
        ↓
inspect active maintenance
        ↓
inspect target state
        ↓
determine whether action is still required
        ↓
retry only when justified
```

The database's current state is authoritative.

---

## 8.25.82 Prevention

Implement:

```text
scheduler concurrency control
per-target ownership
database-state rediscovery
bounded retry
backoff and jitter
audit trail
kill switch
```

Idempotency is a production requirement, not an optional scheduler feature.

---

# Part XV — Case Study 14: Failover During Scheduled Maintenance

## 8.25.83 Situation

A maintenance controller reconnects through an endpoint that changed during an HA event.

The maintenance action is intended only for the primary.

---

## 8.25.84 PostgreSQL Role Signal

A useful PostgreSQL-side check is:

```sql
SELECT pg_is_in_recovery();
```

This is a role signal.

It is not a complete HA topology-management system.

---

## 8.25.85 Complete Execution Gate

Use:

```text
PostgreSQL role evidence
+
managed-service/operator/HA topology
+
expected endpoint
+
expected database
+
approved action
=
execution permitted
```

If:

```text
expected role
≠
observed role
```

then:

```text
STOP
    ↓
rediscover topology
    ↓
reevaluate target
```

A successful SQL connection alone does not prove that the intended database role was reached.

# Part XVI — Case Study 15: VACUUM FULL Proposed During Critical Disk Pressure

## 8.25.86 Situation

Filesystem utilization is critical.

A large table appears physically inefficient.

The proposal is:

> Run VACUUM FULL immediately to recover disk.

That may make the incident worse.

---

## 8.25.87 Decompose Storage First

Determine the dominant storage consumer:

```text
heap
indexes
WAL
temporary files
logs
replication retention
legitimate data growth
reclaimable historical allocation
```

The correct remediation depends on the actual consumer.

---

## 8.25.88 Rewrite Risk

Before `VACUUM FULL`, establish:

```text
available free space
rewrite working-space requirement
relation/index size
ACCESS EXCLUSIVE lock impact
WAL impact
replication impact
runtime
failure-recovery plan
```

A rewrite requires additional working space while the old relation still exists during processing.

Therefore:

```text
disk almost full
    ↓
VACUUM FULL immediately
```

is a dangerous anti-pattern.

---

## 8.25.89 Safer Decision Flow

```text
disk pressure
    ↓
identify actual consumer
    ↓
stop abnormal growth where possible
    ↓
protect availability
    ↓
restore operational headroom
    ↓
evaluate physical reclamation separately
```

# Part XVII — Case Study 16: Anti-Wraparound Autovacuum During an Incident

## 8.25.90 Situation

Application latency is elevated.

The immediate proposal is:

```text
terminate autovacuum
```

to recover resources.

---

## 8.25.91 Correct First Question

Do not begin with:

```text
Why is VACUUM consuming resources?
```

Begin with:

```text
Why did PostgreSQL require
correctness-protection maintenance
during this incident?
```

## 8.25.92 Establish Correctness State

Collect:

```text

database MXID age
old relation ages
maintenance phase
maintenance progress
old transactions
prepared transactions
replication horizons
storage capacity
```

---

## 8.25.93 Safety Rule

Anti-wraparound maintenance must not be treated as ordinary optional background work.

Blindly terminating correctness-protection maintenance can improve immediate resource availability while allowing correctness runway to continue shrinking.

## 8.25.94 Response

Use:

        ↓
remove avoidable competing work
        ↓
protect required correctness maintenance
        ↓
increase safe capacity where necessary
        ↓
validate age recovery

If cancellation is considered at all, it requires explicit understanding of remaining correctness runway and a concrete recovery plan.

# Part XVIII — Case Study 17: VACUUM FULL Progress Appears Missing

## 8.25.96 Situation

An approved `VACUUM FULL` is running during a maintenance window.

An operator checks:

```text
pg_stat_progress_vacuum
```

and does not see the operation.

The incident channel reports:

> VACUUM disappeared or is stuck.

---

## 8.25.97 Root Cause

The wrong progress interface is being inspected.

Ordinary VACUUM reports through:

```text
pg_stat_progress_vacuum
```

`VACUUM FULL` performs a table rewrite and its progress is reported through:

```text
pg_stat_progress_cluster
```

---

## 8.25.98 Correct Investigation

For ordinary VACUUM:

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

For rewrite-based progress such as `VACUUM FULL`:

```sql
SELECT *
FROM pg_stat_progress_cluster;
```

Correlate progress with:

```text
locks
storage
WAL
replication
application availability
```

---

## 8.25.99 Lesson

```text
missing from expected monitoring view
≠
operation absent
```

Observability must understand the implementation class of the maintenance operation.

# Part XIX — Privilege Failure Case

## 8.25.100 Maintenance Fails Before Doing Work

A maintenance controller attempts an approved operation and receives an authorization error.

Do not classify this immediately as:

```text
VACUUM failure
REINDEX failure
maintenance engine failure
```

Determine whether the execution identity has the PostgreSQL privileges required for the requested operation.

---

## 8.25.101 Failure Classification

**Failure class:** `V-PRIVILEGE`

Definition:

> Maintenance or diagnostic work cannot execute because the operational identity lacks the PostgreSQL privileges required for the action.

Keep this distinct from `V-CONFIG`.

---

## 8.25.102 Response

Use:

```text
identify requested operation
        ↓
identify execution identity
        ↓
inspect required privileges
        ↓
compare actual privileges
        ↓
correct least-privilege authorization
        ↓
retry through normal safety gate
```

Do not solve authorization failures by granting broad administrative privileges without justification.

# Part XXI — Handbook Failure Taxonomy

## 8.25.104 Failure Classes

The following taxonomy is defined by this handbook.

| Class           | Meaning                                                       |
| --------------- | ------------------------------------------------------------- |
| `V-TRIGGER`     | Maintenance starts too late or eligibility is poorly matched  |
| `V-WORKER`      | Worker availability or scheduling-capacity problem            |
| `V-THROUGHPUT`  | Cleanup throughput below workload demand                      |
| `V-BLOCKER`     | Transaction/snapshot/prepared transaction retains cleanup     |
| `V-REPLICATION` | Replication horizon or WAL-retention problem                  |
| `V-IO`          | Storage limits maintenance or application workload            |
| `V-CPU`         | CPU limits sustainable maintenance                            |
| `V-MEMORY`      | Maintenance-memory pressure or poor resource configuration    |
| `V-WAL`         | Maintenance/workload creates unsustainable WAL pressure       |
| `V-HEAP`        | Heap physical-efficiency problem                              |
| `V-INDEX`       | Index structural or physical-efficiency problem               |
| `V-XID`         | Transaction-ID correctness risk                               |
| `V-MXID`        | MultiXact correctness risk                                    |
| `V-CONFIG`      | Configuration mismatched to workload or capacity              |
| `V-APP`         | Application behavior creates or amplifies maintenance failure |
| `V-PRIVILEGE`   | Execution identity lacks required PostgreSQL privileges       |

Multiple failure classes can coexist.

Do not force a compound incident into one category when evidence supports several interacting mechanisms.

# Part XXV — RCA Quality Gate

## 8.25.114 Weak Versus Strong RCA

Weak:

> Autovacuum was slow.

Stronger:

> Sustained update/delete churn exceeded the relation's effective cleanup throughput during peak storage contention, causing maintenance debt to grow despite active autovacuum workers.

Weak:

> VACUUM did not remove tuples.

Stronger:

> An application transaction retained an old MVCC snapshot, preventing the cleanup horizon from advancing sufficiently for VACUUM to remove otherwise obsolete tuple versions.

Weak:

> PostgreSQL consumed disk.

Stronger:

> A logical replication consumer stopped advancing its slot, retaining WAL from its required restart position while replication cleanup horizons also delayed removal of obsolete database state.

+

+

# Part XXX — Core Production Principles

## 8.25.124 Principle 1 — Symptoms Are Not Root Causes

```text
dead tuples
disk growth
long VACUUM
high CPU
replica lag
```

are observations.

They become diagnoses only when supported by causal evidence.

---

## 8.25.125 Principle 2 — Active Maintenance Does Not Prove Effective Maintenance

```text
VACUUM running
```

does not prove:

```text
cleanup horizon advancing
```

or:

```text
maintenance throughput sufficient
```

Measure outcomes.

---

## 8.25.126 Principle 3 — Bloat Is Not Size

```text
large
≠
bloated
```

Physical inefficiency must be established using appropriate evidence.

---

## 8.25.127 Principle 4 — Reusable Space Is Not Reclaimed Filesystem Space

Standard VACUUM and rewrite-based physical reclamation solve different operational problems.

Do not select a rewrite merely because ordinary VACUUM did not shrink the relation file.

---

## 8.25.128 Principle 5 — Correctness Has Priority

XID and MXID incidents can become correctness failures.

Treat them differently from ordinary maintenance-efficiency problems.

---

## 8.25.129 Principle 6 — Remove Retained Horizons Before Adding Maintenance Force

When cleanup is blocked:

```text
more workers
more VACUUM
more memory
```

may not solve the problem.

Identify the retained horizon first.

---

## 8.25.130 Principle 7 — Capacity Before Concurrency

Maintenance concurrency consumes real resources.

Increase it only when the infrastructure can sustainably support the resulting demand.

---

## 8.25.131 Principle 8 — Idempotency Before Retry

When an automation controller loses outcome certainty:

```text
rediscover state
before
replaying action
```

Scheduler history is not authoritative database state.

---

## 8.25.132 Principle 9 — Correct Monitoring Interface Matters

```text
ordinary VACUUM
→ pg_stat_progress_vacuum

VACUUM FULL
→ pg_stat_progress_cluster
```

An operation missing from the wrong progress view does not prove that it stopped.

---

## 8.25.133 Principle 10 — Validate Steady State

The strongest recovery condition is:

```text
maintenance demand
≤
sustainable maintenance capacity
```

while correctness, application health, and infrastructure headroom remain acceptable.
