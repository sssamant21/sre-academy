# 8.3 — Standard VACUUM Internals and Processing Phases

Status: **COMPLETE — CANONICAL**

## Purpose

Standard `VACUUM` is PostgreSQL's primary routine mechanism for reclaiming storage occupied by obsolete row versions, maintaining heap and index structures, updating visibility information, advancing freezing work, and keeping relation metadata current.

For production operations, VACUUM should not be viewed as one monolithic task. It moves through identifiable processing phases, and those phases expose different resource demands, progress indicators, and failure modes.

The useful SRE question is not merely how long VACUUM has been running, but what phase it is executing, what resource is limiting that phase, and whether maintenance throughput is sufficient for the workload.

## Standard VACUUM versus VACUUM FULL

Standard `VACUUM` operates against the existing relation, normally permits concurrent `SELECT`, `INSERT`, `UPDATE`, and `DELETE`, reclaims dead-tuple storage primarily for internal reuse, maintains visibility information, performs freezing work, performs index cleanup when appropriate, can truncate empty pages from the physical end of the relation, and can generate substantial I/O.

`VACUUM FULL` is fundamentally different. It rewrites the relation, requires an `ACCESS EXCLUSIVE` lock, and requires additional disk space while the replacement relation is constructed. It should not be the routine response to dead tuples.

## Standard VACUUM processing model

A useful high-level model is:

```text
Initialize
   |
   v
Scan heap
   |
   +--> prune/defragment pages where required
   +--> identify dead item identifiers
   +--> perform eligible freezing
   |
   v
Vacuum indexes
   |
   v
Vacuum heap
   |
   +--> potentially return to heap scanning
   |
   v
Clean up indexes
   |
   v
Optionally truncate heap tail
   |
   v
Final cleanup
   |
   +--> maintain free-space information
   +--> update relation statistics
   +--> report cumulative statistics
   |
   v
Complete
```

PostgreSQL exposes this lifecycle through `pg_stat_progress_vacuum`.

## VACUUM progress phases

PostgreSQL reports these standard VACUUM phases:

```text
initializing
scanning heap
vacuuming indexes
vacuuming heap
cleaning up indexes
truncating heap
performing final cleanup
```

These phase names should be used directly in operational dashboards and troubleshooting runbooks rather than inferring progress solely from elapsed runtime.

## `initializing`

During `initializing`, VACUUM prepares to begin substantive heap work. This phase is normally brief. If it persists unexpectedly, correlate the backend with wait-event and lock information from `pg_stat_activity` and `pg_locks`.

```sql
SELECT
    pid,
    wait_event_type,
    wait_event,
    state,
    query
FROM pg_stat_activity
WHERE pid = <vacuum_pid>;
```

## `scanning heap`

During `scanning heap`, VACUUM progresses through the heap. It can prune pages, defragment pages when required, identify obsolete tuple references, perform eligible freezing work, and use visibility information to avoid unnecessary page inspection.

The primary progress counters are `heap_blks_total` and `heap_blks_scanned`.

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count
FROM pg_stat_progress_vacuum;
```

### Understanding `heap_blks_scanned`

`heap_blks_scanned` is not a count of physical storage reads. PostgreSQL can use the visibility map to skip blocks without physically inspecting them, while those blocks still contribute to the progress counter. Treat it as progress through the heap address space, not as a direct I/O measurement.

### Visibility-map page skipping

The visibility map allows PostgreSQL to identify heap pages that do not require particular kinds of maintenance. Page skipping reduces unnecessary work and also supports index-only scans when heap visibility checks can safely be avoided.

## Identifying dead items

During heap scanning, VACUUM identifies dead tuple item identifiers that may require coordinated index and heap cleanup. PostgreSQL must clean index references before reclaiming heap structures in ways that would invalidate those references.

Conceptually:

```text
Heap scan
   |
   v
Dead item identified
   |
   v
Store dead item identifier
   |
   v
Remove corresponding index references
   |
   v
Complete heap cleanup
```

## Dead-item working memory

PostgreSQL 18 exposes `max_dead_tuple_bytes`, `dead_tuple_bytes`, and `num_dead_item_ids` through `pg_stat_progress_vacuum`. These provide visibility into the working set used to remember dead items discovered during heap scanning.

For manual VACUUM the relevant memory limit is associated with `maintenance_work_mem`; autovacuum can use `autovacuum_work_mem` when explicitly configured.

## Repeated index-vacuum cycles

If PostgreSQL cannot retain information about all discovered dead tuples for the complete heap scan, it can perform an intermediate index-vacuum cycle and then resume scanning.

```text
scanning heap
      |
      v
dead-item capacity reached
      |
      v
vacuuming indexes
      |
      v
vacuuming heap
      |
      v
resume scanning heap
```

Therefore `index_vacuum_count > 1` is not inherently an error. Repeated cycles can, however, materially increase index I/O and maintenance cost. Correlate `index_vacuum_count`, `dead_tuple_bytes`, `max_dead_tuple_bytes`, and `num_dead_item_ids` with VACUUM memory settings.

## `vacuuming indexes`

During `vacuuming indexes`, PostgreSQL removes index references associated with dead heap tuples. Useful fields include `indexes_total`, `indexes_processed`, and `index_vacuum_count`.

On tables with large or numerous indexes, this phase can represent a significant portion of total VACUUM cost.

## `INDEX_CLEANUP`

VACUUM supports `INDEX_CLEANUP AUTO`, `ON`, and `OFF`. `AUTO` allows PostgreSQL to avoid unnecessary index scans when the benefit of removing very few dead tuples would not justify the cost.

```sql
VACUUM (INDEX_CLEANUP ON) large_table;
VACUUM (INDEX_CLEANUP OFF) large_table;
```

Repeatedly disabling index cleanup on frequently modified tables can allow index maintenance debt and bloat to accumulate. `INDEX_CLEANUP OFF` should be an intentional operational choice, not a routine performance workaround.

## Parallel VACUUM

Standard VACUUM can parallelize eligible index processing.

```sql
VACUUM (PARALLEL 4) large_table;
```

Parallelism applies to eligible index work rather than the primary heap scan. The requested worker count is not guaranteed because actual workers depend on index eligibility, PostgreSQL parallel-worker limits, and runtime capacity.

Parallel maintenance can increase CPU and I/O consumption. `maintenance_work_mem` remains a limit for the overall parallel utility command rather than being independently multiplied for every worker.

## `vacuuming heap`

After index references have been processed, PostgreSQL can enter `vacuuming heap`. This is distinct from `scanning heap`.

During heap vacuuming PostgreSQL completes heap-side cleanup associated with dead items whose index references have been handled. `heap_blks_vacuumed` advances during this phase for indexed relations. Blocks with no relevant dead tuples can be skipped, so the counter can move in large increments.

If `heap_blks_scanned < heap_blks_total`, PostgreSQL can then return to `scanning heap` and continue discovery.

## `cleaning up indexes`

After the heap scan and required index/heap vacuum cycles are complete, VACUUM can enter `cleaning up indexes`. This is a final index-maintenance phase and should not be confused with `vacuuming indexes`.

Progress can be followed with `indexes_total` and `indexes_processed`.

## `truncating heap`

VACUUM may enter `truncating heap` when completely empty pages exist at the physical end of the relation. Successful truncation can return those tail pages to the operating system.

Heap truncation requires an `ACCESS EXCLUSIVE` lock for the truncation activity. Standard VACUUM does not hold that lock for its entire execution.

For latency-sensitive systems where tail truncation creates unacceptable contention, it can be disabled without disabling VACUUM itself:

```sql
VACUUM (TRUNCATE OFF) large_table;
```

The server-level `vacuum_truncate` setting and table storage parameters also influence this behavior.

## `performing final cleanup`

The final reported phase is `performing final cleanup`. During this phase PostgreSQL performs final maintenance including free-space-map work, updating relation statistics in `pg_class`, and reporting statistics to the cumulative statistics system.

`heap_blks_scanned = heap_blks_total` therefore does not mean that the VACUUM operation has fully completed. Index cleanup, truncation, and final cleanup can still remain.

## Free Space Map maintenance

The Free Space Map (FSM) tracks available space within heap pages so PostgreSQL can find pages capable of accepting new tuples without scanning the entire relation.

```text
Dead tuple cleaned
       |
       v
Reusable page capacity
       |
       v
FSM reflects available space
       |
       v
Future INSERT / UPDATE can reuse page
```

This is one reason standard VACUUM remains valuable even when the physical relation does not shrink.

## Visibility Map maintenance

VACUUM maintains visibility information. Heap pages can become `all-visible` and, when appropriate, `all-frozen`. These states reduce future maintenance work and support index-only scans.

Visibility-map health therefore affects both maintenance efficiency and query execution efficiency.

## Freezing

VACUUM also performs transaction-ID and multixact aging protection. During heap processing PostgreSQL can freeze sufficiently old transaction information.

Freezing is a correctness responsibility of VACUUM, not an optional storage optimization. Routine vacuuming must provide enough coverage over time to prevent transaction-ID and multixact wraparound risk.

## Monitoring VACUUM progress

A production-friendly PostgreSQL 18 query is:

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    max_dead_tuple_bytes,
    dead_tuple_bytes,
    num_dead_item_ids,
    indexes_total,
    indexes_processed,
    delay_time
FROM pg_stat_progress_vacuum
ORDER BY pid;
```

## Understanding `delay_time`

PostgreSQL 18 exposes `delay_time` as accumulated time VACUUM has spent sleeping because of cost-based throttling. Meaningful values require `track_cost_delay_timing = on`; otherwise the field remains zero. Associated parallel-worker sleep time is included.

This helps distinguish deliberately throttled VACUUM from expensive processing or resource waits.

## Calculating heap-scan progress

```sql
SELECT
    pid,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    round(
        100.0 * heap_blks_scanned /
        NULLIF(heap_blks_total, 0),
        2
    ) AS heap_scan_pct
FROM pg_stat_progress_vacuum;
```

Interpret this as heap-scan progress, not total VACUUM completion percentage.

## VACUUM I/O characteristics

Standard VACUUM can generate substantial I/O, including heap reads and writes, index reads and writes, visibility-map activity, free-space-map activity, and WAL generation.

A table with multiple large indexes can make index maintenance a dominant VACUUM cost.

The production objective is not to finish every VACUUM as fast as physically possible. The objective is to maintain sufficient cleanup throughput while protecting foreground workload stability.

## Diagnosing a long heap scan

When VACUUM remains in `scanning heap`, investigate relation size, heap progress, cost-based delay, storage latency, concurrent I/O pressure, freezing workload, and backend wait events.

Do not infer physical storage reads directly from `heap_blks_scanned`.

## Diagnosing slow index vacuuming

When VACUUM remains in `vacuuming indexes`, investigate index count and size, dead-item volume, `index_vacuum_count`, `indexes_total`, `indexes_processed`, storage latency, parallel VACUUM eligibility, and VACUUM memory capacity.

For heavily indexed relations, index maintenance can dominate total runtime.

## Diagnosing repeated index cycles

If `index_vacuum_count` becomes high while VACUUM remains active, correlate it with `max_dead_tuple_bytes`, `dead_tuple_bytes`, `num_dead_item_ids`, and the applicable VACUUM memory setting.

Repeated cycles can indicate that the dead-item working set cannot be retained for the complete heap scan. This is not inherently a failure, but excessive cycling can materially increase maintenance cost.

## Diagnosing truncation contention

If VACUUM enters `truncating heap` and experiences contention, inspect locks and backend wait state:

```sql
SELECT
    a.pid,
    a.query,
    a.wait_event_type,
    a.wait_event,
    l.mode,
    l.granted
FROM pg_stat_activity a
JOIN pg_locks l
  ON l.pid = a.pid
WHERE a.pid = <vacuum_pid>;
```

If truncation repeatedly disrupts latency-sensitive workloads, evaluate disabling truncation rather than disabling VACUUM.

## VACUUM and TOAST

VACUUM normally processes the associated TOAST relation when applicable. Specialized maintenance can control `PROCESS_MAIN` and `PROCESS_TOAST` independently.

Capacity analysis should consider the main heap, indexes, TOAST relation, and TOAST indexes when large out-of-line values are present.

## Page-skipping controls

`DISABLE_PAGE_SKIPPING` exists for unusual circumstances where normal visibility-map page skipping should not be trusted. It is not a normal performance-tuning option and should be reserved for exceptional diagnostic or recovery scenarios.

## `SKIP_LOCKED`

`VACUUM (SKIP_LOCKED) table_name` can avoid waiting at the beginning of relation processing when a conflicting lock prevents the relation from being acquired. It does not make VACUUM universally nonblocking; related objects and later stages can still encounter waits.

Treat `SKIP_LOCKED` as maintenance scheduling behavior, not a zero-blocking guarantee.

## Failure pattern — VACUUM appears stuck

Before cancelling a long-running VACUUM, establish its current phase, heap scan progress, heap vacuum progress, index progress, index-vacuum count, dead-item working set, delay time, wait event, storage latency, and lock state.

A long-running VACUUM may simply be scanning a very large heap, processing large indexes, performing repeated memory-driven index cycles, intentionally sleeping due to cost-based throttling, waiting for a lock, or being limited by storage throughput.

Cancelling without understanding the current phase can discard useful maintenance progress without addressing the root cause.

## Failure pattern — heap scan complete but VACUUM continues

`heap_blks_scanned = heap_blks_total` does not imply total completion. Remaining work can include index vacuum, heap vacuum, final index cleanup, heap truncation, and final cleanup.

Do not calculate total VACUUM completion solely from heap-scan percentage.

## Failure pattern — VACUUM causes query latency

VACUUM can compete with production workload for storage and CPU resources. A common pattern is increased heap/index I/O, higher storage queue depth, increased foreground I/O latency, and corresponding application latency.

Potential responses include tuning cost-based throttling, adjusting autovacuum resource policy, increasing storage throughput, increasing sustainable maintenance capacity, avoiding large maintenance backlogs, and scheduling exceptional manual maintenance appropriately.

Permanently suppressing VACUUM is not a sustainable solution.

## Production monitoring model

Correlate at least:

| Signal | Operational meaning |
|---|---|
| `phase` | current VACUUM processing stage |
| `heap_blks_total` | heap size at scan start |
| `heap_blks_scanned` | progress through heap address space |
| `heap_blks_vacuumed` | heap blocks vacuumed |
| `index_vacuum_count` | completed index-vacuum cycles |
| `max_dead_tuple_bytes` | dead-item storage capacity |
| `dead_tuple_bytes` | current collected dead-item data |
| `num_dead_item_ids` | current dead item identifiers |
| `indexes_total` | indexes requiring current processing |
| `indexes_processed` | current index-phase progress |
| `delay_time` | cost-delay sleep time when tracking is enabled |
| wait event | blocking/resource state |
| relation/index size | physical maintenance scope |
| storage latency | infrastructure bottleneck signal |

No individual metric should be interpreted in isolation.

## SRE diagnostic workflow

When VACUUM is unexpectedly slow:

1. Determine the current phase from `pg_stat_progress_vacuum`.
2. Determine backend wait state from `pg_stat_activity`.
3. Assess heap progress using `heap_blks_scanned / heap_blks_total`.
4. Assess index behavior using `index_vacuum_count`, `indexes_total`, and `indexes_processed`.
5. Assess dead-item memory using `dead_tuple_bytes`, `max_dead_tuple_bytes`, and `num_dead_item_ids`.
6. Assess throttling using `delay_time`, `track_cost_delay_timing`, and vacuum cost configuration.
7. Correlate storage latency, IOPS, throughput, CPU, buffer activity, and WAL volume.
8. Decide whether intervention is justified; do not cancel useful maintenance solely because elapsed runtime is high.

## Production principles

1. Standard VACUUM is a multi-phase maintenance pipeline.
2. Heap scanning and heap vacuuming are distinct operations.
3. Index processing can occur multiple times when dead-item memory is insufficient for the complete scan.
4. 100% heap-scan progress does not mean VACUUM is complete.
5. `heap_blks_scanned` is not a physical-read counter.
6. Visibility-map skipping can substantially reduce physical work.
7. VACUUM performs freezing as part of database correctness.
8. Index cleanup may be skipped dynamically when PostgreSQL determines the work is not worthwhile.
9. Repeatedly disabling index cleanup can create future index-bloat problems.
10. Parallel VACUUM accelerates eligible index work, not the primary heap scan.
11. Parallel maintenance can materially increase CPU and I/O consumption.
12. Tail truncation can return disk space but requires `ACCESS EXCLUSIVE` locking during truncation.
13. Cost-based delay intentionally exchanges maintenance speed for workload stability.
14. `delay_time` requires cost-delay timing tracking to provide meaningful measurements.
15. VACUUM progress should be correlated with wait events and infrastructure telemetry.

## SRE checklist

```text
[ ] Identify current VACUUM phase
[ ] Check heap blocks scanned versus total
[ ] Check heap blocks vacuumed
[ ] Check index_vacuum_count
[ ] Check dead_tuple_bytes
[ ] Check max_dead_tuple_bytes
[ ] Check num_dead_item_ids
[ ] Check indexes_total and indexes_processed
[ ] Check delay_time
[ ] Verify track_cost_delay_timing when interpreting delay_time
[ ] Check backend wait events
[ ] Check table and index sizes
[ ] Check storage latency, IOPS, and throughput
[ ] Check for repeated index-vacuum cycles
[ ] Check VACUUM memory configuration
[ ] Check whether truncation is creating lock contention
[ ] Include TOAST maintenance when relevant
[ ] Avoid cancelling maintenance without identifying the bottleneck
```

## Key takeaway

Standard VACUUM is best understood as a production maintenance pipeline: discover obsolete storage, coordinate index cleanup, reclaim heap capacity, maintain visibility and freezing state, optionally reclaim empty tail pages, and publish updated maintenance metadata.

Elapsed runtime alone provides little diagnostic value. Effective SRE/DBRE troubleshooting asks what phase VACUUM is executing, how far that phase has progressed, whether it is processing, deliberately throttled, waiting, or resource constrained, whether repeated index cycles are occurring, and whether maintenance throughput can keep pace with tuple churn.
