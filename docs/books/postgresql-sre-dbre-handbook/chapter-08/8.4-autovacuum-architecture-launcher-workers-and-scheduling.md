# 8.4 — Autovacuum Architecture: Launcher, Workers, and Scheduling

Status: **COMPLETE — CANONICAL**

## Purpose

Autovacuum is PostgreSQL's built-in background maintenance subsystem for automatically executing `VACUUM` and `ANALYZE` when relations require maintenance. It is fundamental to production PostgreSQL because MVCC continuously creates maintenance work through inserts, updates, deletes, transaction-ID aging, and changing planner statistics.

Autovacuum helps PostgreSQL reclaim storage occupied by obsolete row versions for reuse, maintain heap and index structures, maintain visibility information, refresh planner statistics, freeze aging transaction IDs and multixacts, prevent transaction-ID wraparound, and distribute maintenance continuously rather than allowing large cleanup backlogs to accumulate.

Autovacuum should be understood as a coordinated maintenance architecture rather than a single process:

```text
PostgreSQL instance
        |
        v
Autovacuum launcher
        |
        v
Autovacuum workers
        |
        v
Databases
        |
        v
Eligible relations
        |
        +--> VACUUM
        +--> ANALYZE
        +--> VACUUM + ANALYZE
```

For an SRE/DBRE, the important question is not merely whether autovacuum is enabled. The important question is whether the subsystem has enough scheduling opportunity, worker capacity, memory, CPU, I/O throughput, and cleanup-horizon progress to keep maintenance demand under control.

## 8.4.1 Why Autovacuum Exists

PostgreSQL's MVCC architecture continuously creates maintenance requirements. Updates and deletes create obsolete tuple versions, inserts and modifications change planner statistics, and all transactions contribute to transaction-ID aging.

```text
workload creates maintenance demand
              |
              v
relations become eligible
              |
              v
autovacuum schedules workers
              |
              v
VACUUM / ANALYZE execute
              |
              v
maintenance debt reduced
```

For stable long-term operation:

```text
maintenance capacity >= maintenance demand
```

must remain approximately true. Otherwise maintenance backlog grows even when autovacuum itself is technically enabled.

## 8.4.2 Autovacuum Is a Multiprocess Architecture

The autovacuum subsystem primarily consists of a persistent launcher plus worker processes:

```text
PostgreSQL
    |
    +--> Autovacuum launcher
             |
             +--> Autovacuum worker
             +--> Autovacuum worker
             +--> Autovacuum worker
```

The launcher coordinates scheduling. Workers perform the actual maintenance. A running launcher does not prove sufficient maintenance capacity, and all workers being active can indicate saturation rather than health.

## 8.4.3 The Autovacuum Launcher

The autovacuum launcher is a persistent PostgreSQL auxiliary process that coordinates worker starts across databases. It does not perform the table-level VACUUM itself.

Conceptually, the launcher selects databases, requests workers, distributes starts over time, and revisits databases continuously. This separation between scheduling and maintenance execution is important when diagnosing autovacuum capacity problems.

## 8.4.4 Autovacuum Workers

Workers execute the maintenance. A worker connects to a database and evaluates relations to determine whether automatic VACUUM, ANALYZE, or both are required.

```text
Launcher
   |
   v
Worker starts
   |
   v
Connect to database
   |
   v
Evaluate relations
   |
   +--> Table A -> VACUUM
   +--> Table B -> ANALYZE
   +--> Table C -> VACUUM + ANALYZE
```

Workers represent the actual execution capacity of the subsystem.

## 8.4.5 Dependency on Statistics Collection

Normal autovacuum eligibility decisions depend on PostgreSQL's cumulative statistics system. Therefore `track_counts` must be enabled for normal autovacuum operation. PostgreSQL enables it by default.

The subsystem uses accumulated activity information such as inserts, updates, deletes, and changes since analysis when deciding whether relations require maintenance. These are statistics and estimates used for scheduling decisions, not exact physical inventories of heap tuples.

## 8.4.6 Database-Level Scheduling

The launcher distributes worker starts across databases. The primary scheduling parameter is `autovacuum_naptime`, which defaults to `1min` in PostgreSQL 18.

The launcher attempts to arrange starts so each database is considered approximately once per `autovacuum_naptime`, spreading worker starts across the interval when multiple databases exist. With `N` databases, starts are distributed approximately across `autovacuum_naptime / N` intervals.

This is scheduling behavior, not a guarantee that every database or table completes all required maintenance during that interval.

## 8.4.7 Understanding `autovacuum_naptime`

`autovacuum_naptime = 1min` does not mean every table is vacuumed once per minute. Actual table maintenance still depends on relation eligibility, threshold calculations, worker availability, maintenance duration, competing databases, competing relations, and wraparound-prevention requirements.

Reducing `autovacuum_naptime` alone therefore does not necessarily solve an autovacuum backlog.

## 8.4.8 PostgreSQL 18 Worker-Slot Architecture

PostgreSQL 18 separates `autovacuum_worker_slots` from `autovacuum_max_workers`.

```text
autovacuum_worker_slots
        |
        v
reserved worker infrastructure
        |
        v
autovacuum_max_workers
        |
        v
allowed concurrent workers
```

`autovacuum_worker_slots` establishes the available worker-slot ceiling at server startup. `autovacuum_max_workers` controls how many workers may actually run concurrently within that ceiling.

## 8.4.9 `autovacuum_worker_slots`

`autovacuum_worker_slots` specifies the number of backend slots reserved for autovacuum workers. In PostgreSQL 18 the default is typically `16`, though the server can initialize a lower value if operating-system resource limits require it.

This is a server-start parameter. For example, `autovacuum_worker_slots = 16` means the server has infrastructure reserved for up to sixteen autovacuum worker slots. It does not mean sixteen workers will normally run.

## 8.4.10 `autovacuum_max_workers`

`autovacuum_max_workers` controls the maximum number of concurrent autovacuum workers, excluding the launcher. The PostgreSQL 18 default is `3`.

For example:

```text
autovacuum_worker_slots = 16
autovacuum_max_workers  = 6
```

means the reserved worker ceiling is sixteen while six workers are permitted to run concurrently. If `autovacuum_max_workers` is configured above `autovacuum_worker_slots`, the excess value does not create additional usable worker capacity.

PostgreSQL 18's separation of reserved worker slots from active concurrency allows operators to change `autovacuum_max_workers` within the reserved ceiling without restarting solely to enlarge the active worker limit.

## 8.4.11 Worker Saturation

A common production failure pattern is worker saturation. If all available workers are occupied by long-running maintenance on large relations, additional eligible tables must wait for a worker to become available.

```text
long-running maintenance
        |
        v
all workers occupied
        |
        v
other eligible relations wait
        |
        v
maintenance debt increases
```

Several large relations becoming eligible at similar times can therefore delay unrelated maintenance. Worker saturation should be treated as a capacity signal.

## 8.4.12 Multiple Workers in One Database

PostgreSQL does not impose a one-autovacuum-worker-per-database limit. Multiple workers can operate in one database concurrently on different relations. Workers coordinate to avoid unnecessarily repeating maintenance already being handled by another worker.

Concentration of workers in one database can temporarily reduce capacity available to other databases.

## 8.4.13 Workers and Connection Limits

Autovacuum workers do not consume normal client connection slots governed by `max_connections` or `superuser_reserved_connections`. Nevertheless, they consume real infrastructure resources including CPU, memory, buffer activity, storage I/O, WAL bandwidth, and operating-system process resources.

Maintenance capacity is therefore not free merely because workers do not use application connection slots.

## 8.4.14 Autovacuum Worker Memory

Autovacuum worker memory is controlled by `autovacuum_work_mem`, which is a per-worker maximum. Its default is `-1`, meaning autovacuum uses `maintenance_work_mem` instead.

This creates an important capacity relationship:

```text
per-worker maintenance memory
             x
concurrent workers
             =
potential aggregate memory exposure
```

PostgreSQL documentation specifically warns that aggregate maintenance memory can scale with the number of concurrent autovacuum workers. Worker concurrency should therefore never be tuned independently from host memory capacity.

## 8.4.15 Worker Concurrency and Storage Capacity

Increasing worker count does not automatically increase useful maintenance throughput. If storage and CPU have spare capacity, more workers may improve cleanup throughput. If storage is already saturated, additional workers can increase concurrent I/O, deepen queues, raise latency, and slow both foreground workloads and maintenance.

The correct worker count is therefore a capacity-planning decision, not a simple "more is better" parameter.

## 8.4.16 Autovacuum Backlog

PostgreSQL does not expose one authoritative metric equivalent to "number of tables waiting for autovacuum." Backlog is inferred from multiple signals such as rising `n_dead_tup` estimates, old `last_autovacuum` timestamps, workers continuously at the configured concurrency limit, increasing relation sizes, and increasing maintenance durations.

`n_dead_tup` is an estimate and trend signal. It should not be treated as an exact count of physically removable tuples.

## 8.4.17 Observing Workers

Running autovacuum workers can be identified through `pg_stat_activity`:

```sql
SELECT
    pid,
    datname,
    backend_type,
    state,
    wait_event_type,
    wait_event,
    query_start,
    now() - query_start AS runtime,
    query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY query_start;
```

This shows how many workers are active, which databases they are servicing, how long they have been running, whether they are waiting, and what maintenance operation they are performing.

## 8.4.18 Observing the Launcher

The launcher appears in backend information as `autovacuum launcher`; workers appear as `autovacuum worker`. The launcher is normally persistent while worker processes appear and disappear according to maintenance scheduling.

The presence of the launcher confirms scheduling infrastructure exists. It does not prove that maintenance throughput is sufficient.

## 8.4.19 Monitoring Worker VACUUM Progress

When an autovacuum worker is performing VACUUM, its progress appears in `pg_stat_progress_vacuum`:

```sql
SELECT *
FROM pg_stat_progress_vacuum;
```

This exposes standard VACUUM phases including `initializing`, `scanning heap`, `vacuuming indexes`, `vacuuming heap`, `cleaning up indexes`, `truncating heap`, and `performing final cleanup`.

Correlating `pg_stat_activity` with `pg_stat_progress_vacuum` provides much stronger evidence than runtime alone.

## 8.4.20 Logging Autovacuum Activity

Autovacuum activity can be logged with `log_autovacuum_min_duration`. In PostgreSQL 18 the default is `10min`.

- `0` logs every automatic VACUUM and ANALYZE operation.
- `-1` disables duration-based autovacuum logging.
- A temporary value such as `1s` can provide detailed visibility during troubleshooting.

When logging is enabled at a value other than `-1`, PostgreSQL can also report automatic maintenance actions skipped because of conflicting locks or concurrently dropped relations. Aggressive logging should be balanced against log volume.

## 8.4.21 Table Eligibility

A worker does not vacuum every relation in its database. It evaluates whether each relation meets automatic maintenance criteria.

Eligibility is influenced by update/delete activity, insert activity, table size, thresholds, scale factors, PostgreSQL 18's maximum vacuum threshold control, statistics changes, and transaction-ID or multixact aging.

The exact trigger formulas belong in Section 8.5.

## 8.4.22 VACUUM and ANALYZE Are Separate Decisions

Automatic VACUUM and automatic ANALYZE use related but distinct eligibility calculations. A relation may require VACUUM only, ANALYZE only, or both.

Cleanup health and planner-statistics freshness are therefore related but distinct concerns. A system can have adequate vacuum activity while planner statistics are stale, or vice versa.

## 8.4.23 Anti-Wraparound Maintenance Has Priority

Autovacuum is part of PostgreSQL's correctness architecture, not merely a performance feature. Even when normal autovacuum is disabled with `autovacuum = off`, PostgreSQL can still launch autovacuum processes when required to prevent transaction-ID wraparound.

Therefore `autovacuum = off` does not guarantee that no autovacuum workers will appear. Anti-wraparound maintenance can override normal autovacuum disablement because transaction-ID wraparound protection is mandatory for database correctness.

## 8.4.24 Why Disabling Autovacuum Is Dangerous

Disabling autovacuum because maintenance causes I/O may reduce immediate background activity, but maintenance debt continues to accumulate. Obsolete tuples accumulate, reusable-space recovery declines, index cleanup debt can grow, planner statistics can become stale, and transaction IDs continue aging.

The safer response is to identify the actual bottleneck: eligibility thresholds, worker capacity, worker memory, cost-based throttling, storage throughput, CPU, cleanup horizons, or workload design.

## 8.4.25 Scheduling Across Many Databases

Database count affects launcher scheduling. A high database count can create scheduling pressure even when individual databases are relatively small.

Capacity planning should consider database count, high-churn relation count, maintenance frequency, maintenance duration, and worker concurrency rather than storage size alone.

## 8.4.26 Large Relations and Worker Occupancy

A worker vacuuming a very large relation can remain occupied for a substantial period. Several concurrent large-table VACUUMs can consume the entire worker pool and delay other eligible maintenance.

Long-running autovacuum workers should not automatically be terminated. First determine their phase, progress, wait state, storage throughput, and whether the worker is making useful progress.

## 8.4.27 Worker-Starvation Failure Pattern

Potential worker-starvation indicators include:

```text
active_workers ~= autovacuum_max_workers
+
old last_autovacuum timestamps
+
rising n_dead_tup estimates
+
relation growth
+
long worker runtimes
```

Possible responses include increasing worker concurrency if infrastructure permits, improving storage throughput, tuning high-churn relations, adjusting eligibility thresholds, reducing maintenance duration, correcting cleanup-horizon blockers, and improving worker memory where repeated index cycles are significant.

## 8.4.28 Storage-Saturation Failure Pattern

A different failure mode occurs when additional worker concurrency increases simultaneous I/O and pushes storage into saturation. In that case query latency and maintenance latency can both increase.

Here the bottleneck is storage capacity rather than worker availability, and adding more workers can worsen the condition.

## 8.4.29 Memory-Pressure Failure Pattern

High `autovacuum_work_mem` combined with a large `autovacuum_max_workers` can create significant maintenance-memory exposure. This must be evaluated together with `shared_buffers`, application backends, `work_mem`, parallel execution, the OS page cache, and other PostgreSQL processes.

Worker-count tuning must include aggregate memory analysis.

## 8.4.30 Worker Inventory Query

```sql
SELECT
    backend_type,
    count(*) AS processes
FROM pg_stat_activity
WHERE backend_type IN (
    'autovacuum launcher',
    'autovacuum worker'
)
GROUP BY backend_type
ORDER BY backend_type;
```

This provides a quick snapshot of the active autovacuum process architecture.

## 8.4.31 Detailed Worker Inspection

```sql
SELECT
    pid,
    datname,
    backend_type,
    query_start,
    now() - query_start AS runtime,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE backend_type = 'autovacuum worker'
ORDER BY runtime DESC;
```

Use this to identify long-running workers, waiting workers, database concentration, and potentially expensive maintenance operations. Runtime alone should not determine whether a worker is unhealthy.

## 8.4.32 Correlating Workers With Table Statistics

```sql
SELECT
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    last_autovacuum,
    autovacuum_count,
    last_autoanalyze,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

The useful operational picture comes from combining worker activity, maintenance history, dead-tuple trends, relation growth, and workload churn rather than treating any single statistic as definitive.

## 8.4.33 Autovacuum as a Capacity System

A useful SRE model is:

```text
workload
   |
   v
maintenance demand
   |
   v
eligible relations
   |
   v
launcher scheduling
   |
   v
worker availability
   |
   v
VACUUM / ANALYZE
   |
   v
maintenance completed
```

For stable production operation:

```text
long-term maintenance throughput >= long-term maintenance generation rate
```

If maintenance demand continuously exceeds capacity, backlog grows and the system can experience relation growth, increasing dead-tuple estimates, stale planner statistics, longer maintenance operations, index cleanup debt, and increasing wraparound pressure.

## 8.4.34 What Increasing Workers Actually Changes

Increasing `autovacuum_max_workers` increases potential maintenance concurrency. It does not automatically make an individual VACUUM faster, increase disk throughput, increase CPU capacity, remove long-running transaction blockers, change relation eligibility thresholds, reduce application tuple churn, eliminate index bloat, or fix insufficient maintenance memory.

Diagnosis must precede configuration changes.

## 8.4.35 SRE Diagnostic Workflow

When autovacuum appears to be falling behind:

1. Verify `autovacuum`, `track_counts`, `autovacuum_worker_slots`, `autovacuum_max_workers`, `autovacuum_naptime`, and `autovacuum_work_mem`.
2. Inventory active workers through `pg_stat_activity`.
3. Inspect worker VACUUM progress through `pg_stat_progress_vacuum`.
4. Identify accumulating maintenance debt using `n_dead_tup` trends, `last_autovacuum`, `autovacuum_count`, and relation/index growth.
5. Determine whether workers are continuously saturated.
6. Inspect CPU, memory, storage latency, IOPS, throughput, and WAL activity.
7. Check cleanup-horizon blockers such as long transactions, idle-in-transaction sessions, prepared transactions, and replication-related retention.
8. Classify the bottleneck as scheduling, worker concurrency, eligibility, memory, CPU, storage, throttling, or cleanup horizon.
9. Tune the actual bottleneck rather than increasing workers blindly.

## 8.4.36 Production Monitoring Model

| Signal | Operational interpretation |
|---|---|
| Launcher presence | Scheduler availability |
| Active workers | Current maintenance concurrency |
| `autovacuum_worker_slots` | Reserved worker ceiling |
| `autovacuum_max_workers` | Allowed active concurrency |
| `autovacuum_naptime` | Database scheduling cadence |
| Worker runtime | Maintenance duration |
| Worker wait events | Blocking/resource state |
| VACUUM phase | Current execution stage |
| `last_autovacuum` | Maintenance recency |
| `autovacuum_count` | Historical execution activity |
| `last_autoanalyze` | Statistics-maintenance recency |
| `n_dead_tup` trend | Estimated maintenance-debt signal |
| Relation growth | Physical capacity consequence |
| Storage latency | I/O capacity signal |
| CPU utilization | Compute contention |
| Memory usage | Worker-concurrency risk |

No individual metric proves autovacuum health. The important question is whether maintenance debt is stable, shrinking, or continuously increasing.

## 8.4.37 Production Principles

1. Autovacuum is a multiprocess maintenance subsystem.
2. The launcher schedules work; workers execute it.
3. Worker availability is finite production capacity.
4. `autovacuum_naptime` is a database scheduling parameter, not a per-table vacuum interval.
5. Multiple workers can operate in one database.
6. Large relations can occupy workers long enough to delay unrelated maintenance.
7. PostgreSQL 18 separates reserved worker slots from active worker concurrency.
8. `autovacuum_max_workers` cannot provide concurrency beyond `autovacuum_worker_slots`.
9. Increasing workers helps only when supporting CPU, memory, and storage capacity exists.
10. Autovacuum worker memory exposure grows with concurrency.
11. Normal autovacuum eligibility depends on statistics collection.
12. VACUUM and ANALYZE eligibility are separate decisions.
13. Dead-tuple statistics are estimates and should be interpreted as trends.
14. Anti-wraparound maintenance can occur even when normal autovacuum is disabled.
15. Disabling autovacuum is not a sustainable response to maintenance I/O.
16. Worker presence does not prove maintenance health.
17. Maintenance capacity must be evaluated against maintenance demand.
18. Tune the bottleneck rather than blindly increasing worker count.

## 8.4.39 Key Takeaway

Autovacuum is best understood as a production maintenance capacity system:

```text
maintenance demand
       |
       v
relation eligibility
       |
       v
launcher scheduling
       |
       v
worker availability
       |
       v
VACUUM / ANALYZE throughput
       |
       v
maintenance debt reduced
```

A healthy PostgreSQL system requires appropriate eligibility, sufficient scheduling frequency, sufficient worker concurrency, sufficient worker memory, sufficient CPU and I/O, and advancing cleanup horizons so that maintenance capacity remains at least equal to maintenance demand over sustained workloads.

When autovacuum falls behind, the useful operational question is whether maintenance is constrained by scheduling, worker availability, eligibility, memory, CPU, storage, throttling, or cleanup horizons. That classification is the foundation for safe autovacuum tuning.
