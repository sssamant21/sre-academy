# 8.5 — Autovacuum Trigger Thresholds and Scale Factors

Status: **COMPLETE — CANONICAL**

## Purpose

Autovacuum does not continuously vacuum every table. PostgreSQL determines whether a relation requires automatic `VACUUM` or `ANALYZE` by comparing accumulated table activity with configurable trigger thresholds.

For an SRE/DBRE, the most important distinction is:

**Eligibility is not execution.**

Crossing a trigger makes a relation eligible for automatic maintenance. Worker availability and autovacuum scheduling still determine when maintenance actually begins.

## Automatic Maintenance Trigger Categories

PostgreSQL evaluates separate maintenance conditions for update/delete-driven VACUUM, insert-driven VACUUM, ANALYZE driven by row changes, and mandatory maintenance driven by transaction-ID or multixact aging. The first three are workload-driven eligibility mechanisms; anti-wraparound maintenance is a correctness mechanism and can override ordinary thresholds.

## Update/Delete VACUUM Trigger

For normal update/delete-driven VACUUM, PostgreSQL 18 uses an effective threshold based on:

```text
MIN(
    autovacuum_vacuum_max_threshold,
    autovacuum_vacuum_threshold
    + autovacuum_vacuum_scale_factor * reltuples
)
```

`autovacuum_vacuum_threshold` provides a fixed base, `autovacuum_vacuum_scale_factor` makes the threshold proportional to table size, `autovacuum_vacuum_max_threshold` places a ceiling on the calculated threshold, and `reltuples` is PostgreSQL's estimated relation row count.

PostgreSQL 18 defaults are:

```text
autovacuum_vacuum_threshold     = 50
autovacuum_vacuum_scale_factor  = 0.20
autovacuum_vacuum_max_threshold = 100000000
```

Setting `autovacuum_vacuum_max_threshold = -1` disables the maximum ceiling.

For approximately 10,000 rows, the traditional calculation is `50 + (0.20 * 10,000) = 2,050`. Because PostgreSQL maintenance statistics and row counts are estimates, this should be treated as an operational threshold rather than an exact transactional boundary.

## Why Scale Factors Matter

The scale factor causes the trigger to grow with table size. For a billion-row relation, the traditional default calculation would be approximately 200 million tuple changes. PostgreSQL 18's maximum threshold prevents the normal trigger from increasing indefinitely with relation size.

For example, with one billion estimated rows and the PostgreSQL 18 defaults, the traditional calculation is 200,000,050 while the effective threshold is capped at 100,000,000.

The default ceiling is not a recommendation that every large production relation should accumulate 100 million obsolete tuples. High-churn tables can require substantially lower table-specific thresholds.

## `reltuples` and Maintenance Statistics Are Estimates

Autovacuum does not execute an exact `COUNT(*)` whenever it evaluates maintenance eligibility. The population used in threshold calculations is derived from `pg_class.reltuples`, which is an estimate.

```sql
SELECT
    oid::regclass AS relation,
    reltuples,
    relpages
FROM pg_class
WHERE oid = 'public.orders'::regclass;
```

Useful maintenance statistics are available from `pg_stat_user_tables`:

```sql
SELECT
    relid,
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    last_autovacuum,
    autovacuum_count,
    last_autoanalyze,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

`n_live_tup` and `n_dead_tup` are estimates. PostgreSQL's cumulative maintenance statistics are eventually consistent operational counters rather than transactionally exact values.

## Estimating the VACUUM Trigger

A baseline diagnostic query can join `pg_stat_user_tables.relid` directly to `pg_class.oid`:

```sql
SELECT
    s.relid,
    s.schemaname,
    s.relname,
    c.reltuples,
    s.n_dead_tup,
    current_setting('autovacuum_vacuum_threshold')::numeric AS base_threshold,
    current_setting('autovacuum_vacuum_scale_factor')::numeric AS scale_factor,
    current_setting('autovacuum_vacuum_max_threshold')::numeric AS max_threshold
FROM pg_stat_user_tables AS s
JOIN pg_class AS c
  ON c.oid = s.relid
ORDER BY s.n_dead_tup DESC;
```

Production tooling must account for relation-level overrides and the special `-1` maximum-threshold semantics before treating a calculated threshold as authoritative.

## Insert-Driven VACUUM

PostgreSQL also supports VACUUM eligibility based on inserts. Conceptually, the trigger uses:

```text
autovacuum_vacuum_insert_threshold
+ autovacuum_vacuum_insert_scale_factor
  * reltuples
  * proportion of pages not all-frozen
```

The proportion not all-frozen is derived from `1 - relallfrozen / relpages`.

PostgreSQL 18 defaults are:

```text
autovacuum_vacuum_insert_threshold    = 1000
autovacuum_vacuum_insert_scale_factor = 0.20
```

Setting `autovacuum_vacuum_insert_threshold = -1` disables insert-count-based VACUUM triggering for that configuration scope.

Insert-heavy relations can still benefit from VACUUM because it contributes to visibility-map maintenance, tuple freezing, all-visible/all-frozen state, and reduced future anti-wraparound work even when update/delete churn is minimal.

## ANALYZE Trigger Formula

Automatic ANALYZE uses a separate threshold:

```text
autovacuum_analyze_threshold
+ autovacuum_analyze_scale_factor * reltuples
```

PostgreSQL 18 defaults are:

```text
autovacuum_analyze_threshold    = 50
autovacuum_analyze_scale_factor = 0.10
```

For approximately one million rows, the default threshold is roughly 100,050 row changes. Because VACUUM and ANALYZE use separate calculations, ANALYZE can become eligible before normal update/delete VACUUM.

This distinction matters operationally: VACUUM addresses MVCC/storage maintenance while ANALYZE refreshes planner statistics.

## Large High-Churn Tables

A large relation with a 20% scale factor can accumulate substantial maintenance demand before reaching its trigger. Production tuning should therefore consider table size, update/delete rate, row width, index count, VACUUM duration, storage capacity, and acceptable maintenance debt rather than relying only on global defaults.

The fixed threshold is most significant for small relations, the scale factor increasingly dominates larger relations, and PostgreSQL 18's maximum threshold can become the controlling limit for very large relations.

## Per-Table Overrides

Autovacuum settings can be overridden at relation level:

```sql
ALTER TABLE public.orders SET (
    autovacuum_vacuum_threshold = 1000,
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_max_threshold = 1000000,
    autovacuum_analyze_threshold = 1000,
    autovacuum_analyze_scale_factor = 0.02
);
```

This allows high-churn relations to receive workload-specific maintenance without applying the same policy globally. Detailed per-table tuning is covered in Section 8.6.

Inspect relation storage parameters with:

```sql
SELECT
    c.oid::regclass AS relation,
    c.reloptions
FROM pg_class AS c
WHERE c.relkind IN ('r', 'm')
  AND c.reloptions IS NOT NULL
ORDER BY c.oid::regclass::text;
```

Always determine effective relation configuration before diagnosing trigger behavior.

## TOAST Relations

Large-value workloads can generate substantial activity in TOAST relations. VACUUM-related autovacuum controls have TOAST-specific storage-parameter variants, including vacuum threshold, scale factor, maximum threshold, insert threshold, and insert scale factor controls.

Maintenance analysis may therefore need to consider both the application relation and its TOAST relation. TOAST maintenance should not be confused with an independent TOAST ANALYZE policy.

## Partitioned Tables

Partitioned parents do not directly contain tuples. Autovacuum processes the individual partitions containing actual data. Autovacuum does not automatically ANALYZE the partitioned parent in the same manner, so manual `ANALYZE parent_table;` can be necessary when partition distributions change materially. Detailed partition maintenance is covered in Section 8.19.

## Temporary Tables

Autovacuum cannot maintain temporary tables belonging to another session. Workloads using long-lived, heavily modified temporary tables may need the owning session to execute `VACUUM` or `ANALYZE` when maintenance or planner-statistics freshness requires it.

## Anti-Wraparound Maintenance Overrides Normal Thresholds

Ordinary tuple-change thresholds are not the only reason PostgreSQL starts VACUUM. Transaction-ID and multixact aging can force maintenance for correctness. A table can therefore receive anti-wraparound maintenance even when its normal tuple-change threshold has not been reached.

Detailed freezing and wraparound behavior is covered in Sections 8.10 and 8.11.

## Production Failure Patterns

### Large Relation Vacuums Too Late

A large relation combined with a large scale factor can produce a large effective trigger, increasing maintenance debt and eventually creating longer VACUUM operations. Responses can include lowering table-specific scale factors or maximum thresholds, adjusting fixed thresholds, validating worker capacity, and validating storage capacity.

The objective is often smaller, earlier maintenance instead of large, delayed cleanup.

### Small High-Churn Table Vacuums Frequently

A small relation with high modification activity can repeatedly cross its threshold. This is not automatically unhealthy. If each operation is inexpensive, frequent maintenance may be exactly what keeps the relation healthy. Evaluate runtime, CPU, I/O, dead-tuple control, relation growth, and foreground impact rather than `autovacuum_count` alone.

### Planner Statistics Become Stale

A relation can have acceptable VACUUM behavior while ANALYZE occurs too infrequently. Symptoms can include poor cardinality estimates, unexpected join strategies, inappropriate sequential scans, and plan instability. Diagnose `autovacuum_analyze_*` independently from `autovacuum_vacuum_*`.

## Eligibility Versus Execution

If a relation exceeds its threshold but `last_autovacuum` remains old, the problem may not be the trigger. The relation can already be eligible while waiting for launcher scheduling or worker availability.

The diagnostic sequence should be:

```text
Has threshold been reached?
        |
       yes
        |
        v
Is a worker available?
        |
        v
Is maintenance scheduled/running?
        |
        v
Is it making progress?
```

This prevents threshold tuning from being used to solve a worker-capacity problem.

## SRE Diagnostic Workflow

When a relation appears overdue for maintenance:

1. Inspect `reltuples`, live/dead tuple estimates, modification counters, and maintenance timestamps.
2. Inspect global VACUUM, insert-VACUUM, and ANALYZE trigger settings.
3. Inspect relation-level and relevant TOAST overrides.
4. Calculate approximate effective thresholds.
5. Determine whether the relation is eligible.
6. If eligible but not running, investigate launcher scheduling and worker saturation.
7. Check CPU, memory, storage latency, IOPS, throughput, and WAL pressure.
8. Evaluate transaction-ID/multixact age independently from normal tuple thresholds.
9. Tune the actual constraint rather than changing scale factors indiscriminately.

## Production Principles

1. Autovacuum eligibility is formula driven.
2. Eligibility does not guarantee immediate execution.
3. VACUUM and ANALYZE use separate trigger calculations.
4. Update/delete VACUUM combines a fixed threshold and scale factor.
5. PostgreSQL 18 adds a maximum ceiling for the normal update/delete VACUUM trigger.
6. `-1` disables that maximum ceiling.
7. Large scale factors can create substantial maintenance debt on large relations.
8. `reltuples`, `n_live_tup`, and `n_dead_tup` are estimates.
9. Maintenance statistics are eventually consistent.
10. Insert-only relations can still require VACUUM.
11. ANALYZE thresholds should be tuned independently when statistics change rapidly.
12. Per-table configuration is often safer than aggressive global tuning.
13. TOAST relations may require separate VACUUM consideration.
14. Partitioned parents require special ANALYZE consideration.
15. Temporary tables are outside normal autovacuum maintenance.
16. Anti-wraparound maintenance can override normal tuple-change thresholds.
17. Threshold tuning must be evaluated together with worker and infrastructure capacity.

## Key Takeaway

The critical operational distinction is that reaching a threshold means a relation is **eligible for maintenance**, not that maintenance has already started.

PostgreSQL 18 improves large-table behavior through `autovacuum_vacuum_max_threshold`, but the default ceiling is not automatically the correct threshold for every production relation.

Safe trigger tuning requires evaluating table size, workload churn, effective trigger, worker capacity, maintenance duration, CPU/memory/storage capacity, and cleanup horizons as one maintenance system.

The objective is not to minimize the number of autovacuum operations. The objective is to ensure maintenance occurs early and efficiently enough that long-term maintenance capacity remains at least equal to maintenance demand without creating unacceptable foreground workload impact.
