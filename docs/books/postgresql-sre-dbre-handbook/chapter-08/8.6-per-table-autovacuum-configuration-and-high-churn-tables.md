# 8.6 — Per-Table Autovacuum Configuration and High-Churn Tables

Status: **COMPLETE — CANONICAL**

## Purpose

Global autovacuum settings establish the default maintenance policy for a PostgreSQL instance. Production databases, however, contain relations with very different sizes, modification rates, row widths, index footprints, access patterns, and operational importance.

A configuration suitable for a small reference table can be inadequate for a large transactional table receiving millions of modifications per hour. PostgreSQL therefore supports relation-level autovacuum configuration.

Per-table configuration is an **exception-management mechanism**. The objective is not to customize every relation. It is to identify relations whose maintenance characteristics differ materially from the global baseline and tune those relations deliberately.

## Why Per-Table Configuration Matters

Consider three relations:

```text
Table A
50,000 rows
low churn

Table B
20,000,000 rows
moderate churn

Table C
800,000,000 rows
very high churn
```

Applying the same scale factor to all three can produce radically different maintenance behavior. Global defaults should remain the baseline; exceptional high-churn relations can use measured table-specific policies.

## What Is a High-Churn Relation?

High churn means sustained modification activity. Common examples include queues, workflow-state tables, session tables, order/status tables, task-state tables, frequently updated account or patient state, and mutable operational fact tables.

The resulting maintenance demand can include dead tuple generation, index maintenance, visibility-map changes, planner-statistics changes, and transaction-ID aging. A single high-churn relation can therefore become a maintenance bottleneck even while most of the database remains healthy.

## Identify Candidates Before Tuning

Do not begin by changing configuration. First identify where maintenance demand is being generated.

```sql
SELECT
    relid,
    schemaname,
    relname,
    n_live_tup,
    n_dead_tup,
    n_tup_ins,
    n_tup_upd,
    n_tup_del,
    n_tup_hot_upd,
    n_tup_newpage_upd,
    last_autovacuum,
    autovacuum_count,
    last_autoanalyze,
    autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Useful signals include sustained dead-tuple growth, high UPDATE/DELETE rate, large relation size, long VACUUM duration, and an old `last_autovacuum`. No single statistic proves that a relation requires custom tuning.

## Measure Physical Size

```sql
SELECT
    s.relid,
    s.schemaname,
    s.relname,
    pg_size_pretty(pg_relation_size(s.relid)) AS heap_size,
    pg_size_pretty(pg_indexes_size(s.relid)) AS index_size,
    pg_size_pretty(pg_total_relation_size(s.relid)) AS total_size,
    s.n_live_tup,
    s.n_dead_tup,
    s.n_tup_upd,
    s.n_tup_del,
    s.last_autovacuum
FROM pg_stat_user_tables AS s
ORDER BY pg_total_relation_size(s.relid) DESC;
```

Large size alone is not sufficient evidence for aggressive autovacuum tuning.

## Measure Churn as a Rate

Cumulative counters are more useful when sampled over time. For example, if `n_tup_upd` increases from 900,000,000 to 904,000,000 in one hour, the approximate update rate is 4,000,000 updates/hour.

For capacity planning, the change in counters over an observation interval is generally more useful than the cumulative count itself.

## Inspect Existing Relation Overrides

```sql
SELECT
    c.oid::regclass AS relation,
    c.reloptions
FROM pg_class AS c
WHERE c.relkind IN ('r', 'm')
  AND c.reloptions IS NOT NULL
ORDER BY c.oid::regclass::text;
```

Always establish the effective configuration before diagnosing trigger behavior.

## Primary Per-Table Trigger Controls

For most high-churn tuning, begin with:

```text
autovacuum_vacuum_threshold
autovacuum_vacuum_scale_factor
autovacuum_vacuum_max_threshold

autovacuum_analyze_threshold
autovacuum_analyze_scale_factor
```

Depending on workload, insert-driven controls may also matter:

```text
autovacuum_vacuum_insert_threshold
autovacuum_vacuum_insert_scale_factor
```

These settings control maintenance **eligibility**.

## Additional Per-Table Controls

PostgreSQL 18 also supports relation-level controls including:

```text
autovacuum_enabled
autovacuum_vacuum_cost_delay
autovacuum_vacuum_cost_limit
autovacuum_freeze_min_age
autovacuum_freeze_max_age
autovacuum_freeze_table_age
autovacuum_multixact_freeze_min_age
autovacuum_multixact_freeze_max_age
autovacuum_multixact_freeze_table_age
vacuum_index_cleanup
vacuum_truncate
```

Many corresponding TOAST controls are also available. These parameters affect different maintenance layers and should not be customized merely because they exist.

## Tuning Hierarchy

A useful production hierarchy is:

```text
1. measure workload
2. evaluate VACUUM trigger
3. evaluate ANALYZE trigger
4. evaluate insert trigger if relevant
5. evaluate worker capacity
6. evaluate VACUUM execution cost
7. evaluate HOT / fillfactor / index design
8. evaluate advanced VACUUM behavior
9. evaluate freeze controls only with explicit wraparound understanding
```

## Large High-Churn Example

Assume `orders_current` has about 300,000,000 rows, 4,000,000 updates/hour, and 500,000 deletes/hour. A 20% scale factor represents a percentage component of about 60,000,000 tuple changes before considering PostgreSQL 18's maximum threshold.

An illustrative table-specific configuration might be:

```sql
ALTER TABLE public.orders_current SET (
    autovacuum_vacuum_threshold = 5000,
    autovacuum_vacuum_scale_factor = 0.005,
    autovacuum_vacuum_max_threshold = 2000000
);
```

These values are illustrative only, not recommended defaults. Production values should come from measured workload and maintenance capacity.

## Convert Thresholds into Time-to-Trigger

Suppose the effective threshold is 2,000,000 tuples and qualifying churn is 500,000 tuples/hour. The approximate trigger runway is:

```text
2,000,000 / 500,000 ≈ 4 hours
```

This creates a more operational question: can this relation safely accumulate approximately four hours of maintenance debt? The approximation is not an autovacuum scheduling guarantee because statistics are approximate, workloads vary, and worker scheduling still determines when maintenance actually starts.

## Maintenance-Debt Budget

A useful SRE model is:

```text
observed churn rate
       |
       v
acceptable maintenance debt
       |
       v
target trigger runway
       |
       v
relation-specific threshold
```

The table-specific trigger should be designed around an operational objective rather than an arbitrary percentage.

## Fixed Threshold, Scale Factor, and Maximum Threshold

For large relations, a smaller scale factor can create earlier eligibility. PostgreSQL 18's `autovacuum_vacuum_max_threshold` can also establish an upper bound on the normal update/delete trigger so that the trigger does not keep increasing indefinitely as the relation grows.

## Tune ANALYZE Independently

A high-churn relation can require frequent planner-statistics refresh even when physical cleanup remains healthy.

```sql
ALTER TABLE public.orders_current SET (
    autovacuum_analyze_threshold = 1000,
    autovacuum_analyze_scale_factor = 0.005
);
```

Such values are illustrative. More frequent ANALYZE may be justified where distributions change rapidly, recently inserted data dominates queries, selectivity changes materially, or stale statistics create plan instability.

## HOT Updates

Heap-only tuple (HOT) updates can reduce index-maintenance overhead. HOT eligibility depends on multiple conditions, including whether modified columns require index changes and whether sufficient space exists on the heap page for the new row version.

Useful PostgreSQL 18 statistics include `n_tup_upd`, `n_tup_hot_upd`, and `n_tup_newpage_upd`.

```sql
SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,
    n_tup_newpage_upd,
    CASE
        WHEN n_tup_upd = 0 THEN 0
        ELSE round(100.0 * n_tup_hot_upd / n_tup_upd, 2)
    END AS hot_update_pct
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC;
```

A low HOT percentage on a heavily updated relation may indicate additional index-maintenance demand. HOT reduces some maintenance overhead but does not eliminate MVCC tuple versions or the need for VACUUM.

## Fillfactor and Update-Heavy Relations

Lowering table fillfactor leaves additional page space available for future updates and can increase the opportunity for HOT updates.

```sql
ALTER TABLE public.orders_current
SET (fillfactor = 80);
```

This is not guaranteed to produce HOT updates, and lower fillfactor also increases storage footprint. Changing fillfactor does not itself rewrite the existing table; the new storage policy influences future tuple placement.

## Per-Table Cost Controls

PostgreSQL supports `autovacuum_vacuum_cost_delay` and `autovacuum_vacuum_cost_limit` at relation level.

```sql
ALTER TABLE public.orders_current SET (
    autovacuum_vacuum_cost_delay = 2,
    autovacuum_vacuum_cost_limit = 1000
);
```

These controls affect **how aggressively** automatic VACUUM consumes resources. They do not determine when the table becomes eligible. Workers using explicit relation-specific cost settings also interact differently with the normal global autovacuum cost-balancing behavior.

Detailed cost tuning is covered in Section 8.7.

## Advanced Index Cleanup Control

PostgreSQL supports `vacuum_index_cleanup` with behavior such as `AUTO`, `ON`, or `OFF`. Disabling index cleanup can reduce work performed by a VACUUM operation, but it is not a generic performance optimization. Repeatedly suppressing index cleanup on frequently modified relations can allow substantial index bloat to accumulate.

## VACUUM Truncation Control

The relation-level `vacuum_truncate` setting controls whether VACUUM attempts to truncate completely empty pages from the end of a relation when possible. It does not change autovacuum eligibility.

## Do Not Tune from Size Alone

A 500 GB append-mostly historical relation can require less maintenance than a 100 GB relation that is continuously updated. Maintenance demand should be evaluated from relation characteristics, modification rate, and cleanup cost—not size alone.

## Maintenance Duration Must Fit the Workload

If a table becomes eligible every 30 minutes but each VACUUM takes 90 minutes, threshold tuning alone cannot stabilize the system. The operator may need to investigate storage performance, VACUUM throttling, worker capacity, excessive indexes, cleanup blockers, schema design, or workload churn.

The core long-term requirement is:

```text
sustained maintenance completion capacity
                >=
sustained maintenance generation rate
```

A lower trigger is useful only when PostgreSQL has sufficient capacity to process the resulting maintenance.

## Too-Aggressive Tuning

A relation can also be maintained more aggressively than necessary. Possible symptoms include nearly continuous automatic VACUUM, unnecessary heap/index scans, elevated I/O, higher CPU consumption, excessive worker occupancy, and increased foreground latency.

The objective is to vacuum early enough to control maintenance debt without creating unacceptable resource or application impact.

## Change One Dimension at a Time

When possible, avoid simultaneously changing vacuum scale factor, analyze scale factor, cost delay, cost limit, fillfactor, and worker count. Establish a baseline, make one controlled change, observe multiple cycles, compare, and only then make the next change if justified.

## Capture a Production Baseline

Before tuning, capture relation size, index size, `reltuples`, `n_live_tup`, `n_dead_tup`, INSERT/UPDATE/DELETE rates, HOT update percentage, `last_autovacuum`, `autovacuum_count`, `last_autoanalyze`, `autoanalyze_count`, VACUUM duration, CPU, storage latency, IOPS, throughput, and foreground query latency.

## Disabling Autovacuum Per Table

PostgreSQL allows:

```sql
ALTER TABLE public.example SET (
    autovacuum_enabled = false
);
```

This should rarely be treated as a routine performance optimization. Disabling ordinary per-table autovacuum transfers maintenance responsibility to the operating team. The replacement process must define who performs VACUUM, when maintenance runs, how failures are detected, how statistics are maintained, how missed maintenance is recovered, and how transaction-ID risk is monitored.

Disabling ordinary autovacuum does not remove PostgreSQL's anti-wraparound responsibility. Enabling autovacuum for a table also does not by itself create ordinary automatic maintenance when the global autovacuum subsystem is disabled.

## Freeze Controls Require Stronger Safety Review

Relation-level freeze controls affect correctness-related maintenance. Per-table settings cannot be used to bypass PostgreSQL's system-wide wraparound safety boundaries. Relation-level maximum-age settings cannot simply raise a table above applicable global safety limits.

Treat freeze settings as correctness-sensitive configuration, distinct from ordinary VACUUM trigger tuning. Detailed freezing behavior is covered in Sections 8.10 and 8.11.

## TOAST-Aware Tuning

Large-value workloads can shift substantial storage and maintenance activity into TOAST relations.

```sql
SELECT
    c.oid::regclass AS table_name,
    c.reltoastrelid::regclass AS toast_table
FROM pg_class AS c
WHERE c.oid = 'public.orders_current'::regclass;
```

Where PostgreSQL provides an equivalent `toast.*` storage parameter, TOAST maintenance can be controlled separately. When an explicit TOAST override is not supplied, applicable main-table settings can govern the associated TOAST behavior.

## Leaf-Partition Tuning

Partitioned parents do not directly contain tuples. Maintenance settings should therefore be evaluated at the leaf partitions that store the data. A current high-churn partition and an older mostly static partition can legitimately have different maintenance profiles.

Detailed partition maintenance is covered in Section 8.19.

## Index Count Matters

A high-churn relation with many indexes can make VACUUM significantly more expensive. Investigate heap size, number of indexes, index sizes, UPDATE pattern, HOT rate, and unused indexes. Autovacuum tuning should not hide poor index design.

## Configuration Sprawl

Relation-level settings can become configuration debt. Treat per-table autovacuum configuration as production configuration. Each exception should ideally have a relation, owner, reason, baseline, old values, new values, expected result, implementation date, review date, and rollback values.

## Production Change Record

A useful change record includes:

```text
Relation:
public.orders_current

Reason:
Sustained high UPDATE/DELETE churn

Observed problem:
Maintenance debt increases between VACUUM cycles

Baseline:
- effective trigger
- trigger runway
- dead-tuple trend
- VACUUM duration
- CPU
- storage I/O
- foreground latency

Change:
- previous reloptions
- new reloptions

Expected result:
Earlier maintenance eligibility and stable maintenance debt

Validation:
Observe multiple VACUUM cycles

Rollback:
Restore previous reloptions
```

## Resetting Per-Table Configuration

```sql
ALTER TABLE public.orders_current RESET (
    autovacuum_vacuum_threshold,
    autovacuum_vacuum_scale_factor,
    autovacuum_vacuum_max_threshold,
    autovacuum_analyze_threshold,
    autovacuum_analyze_scale_factor
);
```

After reset, the relation returns to applicable inherited/default behavior.

## Validate Configuration After Change

```sql
SELECT
    c.oid::regclass AS relation,
    c.reloptions
FROM pg_class AS c
WHERE c.oid = 'public.orders_current'::regclass;
```

Then observe whether trigger runway changes, autovacuum frequency changes, maintenance debt stabilizes, VACUUM duration remains manageable, I/O remains acceptable, and query latency remains acceptable.

## High-Churn Tuning Workflow

1. Identify candidates using churn rate, dead-tuple trend, physical size, and maintenance runtime.
2. Capture a before-state across table, index, workload, VACUUM, and infrastructure metrics.
3. Resolve global and relation-level effective configuration.
4. Calculate the approximate effective trigger.
5. Convert the trigger into approximate runway using observed qualifying churn.
6. Define acceptable maintenance debt.
7. Apply the minimum necessary override.
8. Observe multiple maintenance cycles.
9. Verify that maintenance completion capacity is at least equal to maintenance generation rate.
10. Document the result or roll back.

## Failure Pattern — Correct Trigger, Insufficient Workers

A table can have appropriate trigger settings and still fall behind because all workers are occupied. This is primarily a worker-capacity or scheduling problem, not a threshold problem. Use the architecture from Section 8.4 when diagnosing it.

## Failure Pattern — Storage Saturation

Aggressive thresholds combined with multiple active workers can create storage saturation and foreground latency. Trigger policy and storage capacity must be evaluated together.

## Failure Pattern — Index Maintenance Dominates

A high-churn relation with many large indexes may experience expensive VACUUM cycles even when heap cleanup appears manageable. Threshold tuning alone does not solve fundamentally excessive index-maintenance demand.

## Failure Pattern — Configuration Sprawl

Repeated incident-driven tuning can produce many undocumented relation overrides with no explanation for why the values differ. Relation-level overrides should therefore be periodically reviewed and removed when the original workload condition no longer exists.

## Production Principles

1. **Global settings are the baseline; per-table settings are justified exceptions.**
2. **Tune from maintenance demand, not relation size alone.**
3. **Measure modification activity as a rate.**
4. **Convert thresholds into approximate trigger runway.**
5. **Define an acceptable maintenance-debt budget.**
6. **Use PostgreSQL 18's maximum threshold to establish upper bounds where appropriate.**
7. **Tune VACUUM and ANALYZE independently.**
8. **Trigger settings control eligibility; cost settings control execution aggressiveness.**
9. **HOT and fillfactor can reduce maintenance pressure but do not replace VACUUM.**
10. **Index design is part of high-churn maintenance design.**
11. **TOAST relations can require separate investigation.**
12. **Leaf partitions may require lifecycle-specific maintenance policies.**
13. **Do not disable autovacuum without a replacement maintenance system.**
14. **Treat freeze controls as correctness-sensitive configuration.**
15. **Do not repeatedly disable index cleanup as a generic performance optimization.**
16. **Observe multiple maintenance cycles before judging a change.**
17. **Preserve rollback values.**
18. **Document and periodically review relation-level exceptions.**
19. **A lower trigger is useful only if sufficient maintenance capacity exists.**
20. **Sustained maintenance completion capacity must meet or exceed sustained maintenance generation rate.**

## Key Takeaway

The central question in per-table autovacuum tuning is not:

```text
What scale factor should this table use?
```

It is:

```text
At the current maintenance-generation rate,
how much maintenance debt can this relation
safely accumulate before becoming eligible
for maintenance?
```

Then determine whether the system can process that work fast enough.

The sustainable state is:

```text
maintenance completion capacity
            >=
maintenance generation rate
```

Per-table overrides are successful only when they make maintenance more predictable while keeping CPU, memory, storage, WAL, worker utilization, and foreground query latency within acceptable operating limits.

Tune exceptional relations deliberately, measure the result over multiple maintenance cycles, and retain only changes supported by production evidence.
