# 8.7 — Vacuum Cost-Based Delay, Throttling, and Resource Control

Status: **CANONICAL**

## Purpose

`VACUUM` performs essential PostgreSQL maintenance, but maintenance consumes real system resources. Large or frequent vacuum activity can create buffer activity, storage reads and writes, WAL-related work, CPU consumption, index-maintenance work, and cache pressure.

PostgreSQL provides **cost-based vacuum delay** to regulate how aggressively maintenance consumes resources. The objective is not to make VACUUM slow. The objective is to balance maintenance completion speed against foreground workload impact.

For SRE/DBRE operations, cost-based vacuum tuning is therefore a **resource-governance mechanism**.

## 8.7.1 Eligibility and Throttling Are Different

Autovacuum trigger parameters determine **when** a relation becomes eligible for maintenance. Cost parameters determine **how aggressively** maintenance runs once it begins.

A table can become eligible quickly but still be vacuumed conservatively. Likewise, a table can have a relatively high trigger threshold but run aggressively once VACUUM begins. Do not use trigger parameters and cost parameters interchangeably.

## 8.7.2 The Cost-Based Vacuum Model

During VACUUM and ANALYZE, PostgreSQL maintains an internal cost balance representing estimated I/O work. Different operations add different amounts to that balance. When the accumulated cost reaches the configured limit, PostgreSQL normally sleeps according to the configured delay and then resumes maintenance.

The mechanism deliberately uses estimated costs rather than attempting to enforce an exact IOPS or MB/s ceiling. Cost-based vacuum delay is therefore **throttling**, not storage QoS.

## 8.7.3 Core Cost Parameters

| Parameter | PostgreSQL 18 default | Purpose |
|---|---:|---|
| `vacuum_cost_delay` | `0ms` | Delay used by ordinary cost-controlled VACUUM |
| `vacuum_cost_limit` | `200` | Cost accumulated before delaying |
| `vacuum_cost_page_hit` | `1` | Cost for a buffer-cache hit |
| `vacuum_cost_page_miss` | `2` | Cost for a page requiring a read |
| `vacuum_cost_page_dirty` | `20` | Cost for dirtying a previously clean page |
| `autovacuum_vacuum_cost_delay` | `2ms` | Autovacuum-specific delay |
| `autovacuum_vacuum_cost_limit` | `-1` | Use `vacuum_cost_limit` unless overridden |

The defaults are a starting point, not a universal production optimum. Effective tuning depends on workload, storage, table size, index footprint, maintenance debt, and foreground latency requirements.

## 8.7.4 Manual VACUUM and Autovacuum

PostgreSQL 18 defaults `vacuum_cost_delay` to `0ms`, disabling ordinary cost-based delay. Consequently, a manually initiated `VACUUM public.orders;` can operate much more aggressively than a normal autovacuum worker.

Autovacuum has its own `autovacuum_vacuum_cost_delay`, whose PostgreSQL 18 default is `2ms`. Autovacuum therefore normally operates with cost-based throttling enabled even though ordinary manually initiated VACUUM normally does not.

Never compare manual and autovacuum runtimes without examining their effective resource controls.

## 8.7.5 Cost Limits and Page Accounting

`vacuum_cost_limit` defines how much estimated cost can accumulate before cost-based delay normally occurs. A lower limit causes delays more frequently; a higher limit permits more work between delays. It does not directly specify IOPS, throughput, CPU percentage, or execution time.

PostgreSQL uses three principal page-cost categories:

- `vacuum_cost_page_hit = 1`: page already present in shared buffers.
- `vacuum_cost_page_miss = 2`: page must be brought into the buffer pool.
- `vacuum_cost_page_dirty = 20`: VACUUM dirties a previously clean page.

These values are accounting weights. One cost unit does not mean one I/O or one millisecond.

## 8.7.6 Autovacuum Cost Balancing

`autovacuum_vacuum_cost_limit` defaults to `-1`, which means the regular `vacuum_cost_limit` is used.

PostgreSQL does not normally give every autovacuum worker an independent full global cost budget. It distributes the configured autovacuum cost limit across eligible workers, helping keep aggregate background maintenance pressure more stable as worker concurrency changes.

Worker concurrency and cost controls must therefore be considered together.

## 8.7.7 Per-Table Cost Overrides

Relations can override `autovacuum_vacuum_cost_delay` and `autovacuum_vacuum_cost_limit` through storage parameters.

```sql
ALTER TABLE public.orders_current SET (
    autovacuum_vacuum_cost_delay = 1,
    autovacuum_vacuum_cost_limit = 1000
);
```

These values are illustrative, not recommendations. Workers processing relations with explicit table-level cost settings are excluded from ordinary autovacuum cost balancing in important ways. Widespread per-table overrides can therefore make aggregate maintenance resource consumption harder to predict.

Treat overrides as production configuration and retain the relation, rationale, baseline, intended resource envelope, owner, implementation date, review date, and rollback values.

## 8.7.8 Cost Delay Can Be Temporarily Suppressed

Reaching `vacuum_cost_limit` does not mean VACUUM must immediately sleep under every circumstance. Some VACUUM operations hold critical locks and should complete promptly, so PostgreSQL can postpone cost-based sleeping while such work is in progress.

The accumulated cost can temporarily exceed the configured limit. Once delaying becomes safe again, PostgreSQL derives the sleep interval from the accumulated cost balance, subject to its documented bound.

This reinforces an important principle: `vacuum_cost_limit` is not a hard resource boundary. Cost-based throttling is cooperative resource control, not an exact I/O governor.

## 8.7.9 VACUUM Failsafe Can Override Normal Throttling

PostgreSQL contains vacuum failsafe behavior designed to reduce transaction-ID or multixact wraparound risk. When failsafe behavior activates, completing protective VACUUM work becomes more important than normal maintenance throttling, and cost-based delay can be disabled.

Depending on the failsafe involved, PostgreSQL can also bypass nonessential work, and the normal Buffer Access Strategy can be disabled.

Do not assume configured vacuum throttling will continue protecting application latency once a database enters failsafe territory. Preventing maintenance debt from reaching that state is far safer than relying on emergency cleanup.

## 8.7.10 Faster and Slower Are Both Tradeoffs

Making VACUUM more aggressive can shorten runtime while increasing I/O pressure, CPU consumption, cache pressure, and foreground latency. Conversely, excessive throttling can cause maintenance throughput to fall below the rate at which new debt is generated.

A worker can remain continuously active while the table falls further behind. `VACUUM is running` does not prove `VACUUM is keeping up`.

A sustainable system requires:

```text
maintenance completion capacity >= maintenance generation rate
```

while foreground workload impact remains acceptable.

## 8.7.11 Storage Is a Guardrail

When adjusting vacuum aggressiveness, observe read and write latency, queue depth, IOPS, throughput, disk utilization, and instance or VM storage bandwidth.

Cloud and managed environments can impose ceilings based on provisioned IOPS, disk tier, throughput limits, instance bandwidth, burst-credit models, and network-attached storage.

If foreground demand plus maintenance demand exceeds storage capability, cost tuning merely changes how contention is distributed. It cannot manufacture storage capacity.

## 8.7.12 Buffer Cache Pressure

VACUUM and ANALYZE use a Buffer Access Strategy intended to reduce disruption to the normal shared-buffer working set. PostgreSQL 18 provides `vacuum_buffer_usage_limit`; its default is `2MB`, and its effective value is constrained relative to `shared_buffers`.

A larger buffer-usage limit can improve some maintenance workloads but can also increase the risk that useful application pages are displaced. This is a different resource-control dimension from cost-based delay: cost settings govern pacing, while `vacuum_buffer_usage_limit` governs the shared-buffer footprint.

Manual VACUUM and ANALYZE can override the strategy where supported:

```sql
VACUUM (BUFFER_USAGE_LIMIT '64MB') public.orders;
```

Measure application cache behavior and query latency before and after substantial changes.

## 8.7.13 Parallel VACUUM and Cost Delay

Parallel VACUUM can use parallel workers for eligible index maintenance, but cost-based delay still applies. Parallel workers participate in cost accounting and sleep according to the work they perform.

Parallelism and cost-based delay are separate resource-control mechanisms. Detailed parallel VACUUM behavior is covered in Section 8.8.

## 8.7.14 Resource-Control Layers

Production VACUUM behavior is governed by several interacting layers:

- trigger settings — when maintenance starts;
- worker availability — execution concurrency;
- cost settings — maintenance pacing;
- maintenance memory — working capacity;
- buffer strategy — shared-buffer footprint;
- storage capability — physical throughput ceiling.

Changing one layer may not resolve the actual bottleneck.

## 8.7.15 Busy OLTP Systems and Maintenance Windows

For latency-sensitive OLTP systems, VACUUM must make steady progress without causing sustained CPU, storage, or latency saturation. Measure maintenance debt, vacuum progress and runtime, application latency, and infrastructure headroom; make the smallest justified adjustment and observe several comparable cycles.

During an explicit maintenance window, foreground workload may be reduced and more maintenance capacity may be available. Manual VACUUM already normally runs without cost delay, so account for that before additionally increasing parallelism, memory, or other resource controls.

## 8.7.16 Emergency Catch-Up

A relation with severe maintenance debt may require accelerated cleanup. Evaluate current application load, dead-tuple trajectory, active maintenance, storage headroom, worker saturation, index footprint, cleanup blockers, transaction-ID and multixact age, and proximity to failsafe conditions.

Do not simply apply extreme cost values because a table is bloated. If old snapshots, prepared transactions, replication horizons, or other cleanup blockers prevent tuple removal, a faster VACUUM cannot remove the underlying blocker.

## 8.7.17 Failure Patterns

### Autovacuum continuously active but falling behind

Possible causes include excessive throttling, insufficient I/O capacity, large index footprint, cleanup blockers, worker contention, insufficient maintenance memory, or table growth exceeding capacity assumptions. Do not assume cost delay is the only cause.

### VACUUM hurts foreground latency

Investigate active autovacuum workers, table-level cost overrides, manual VACUUM, parallel VACUUM, checkpoint activity, storage queue depth, IOPS and throughput ceilings, and possible failsafe activity.

### More workers increase I/O pressure

Increasing `autovacuum_max_workers` can increase maintenance concurrency. When storage is the bottleneck, however, more workers can produce greater storage pressure and higher latency. Global cost balancing helps control normal workers, but table-level overrides can change aggregate behavior.

## 8.7.18 Observing Cost Delay

PostgreSQL 18 provides `pg_stat_progress_vacuum.delay_time` for observing time spent in cost-based delay when timing collection is enabled.

Before relying on it:

```sql
SHOW track_cost_delay_timing;
```

Interpret `delay_time` together with total runtime, VACUUM phase, blocks scanned and vacuumed, index processing, storage telemetry, and the maintenance-debt trajectory. Parallel-worker delay can contribute to the reported value.

A high `delay_time` does not automatically mean the configuration is wrong; it means throttling is materially contributing to runtime.

A useful progress query is:

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    indexes_total,
    indexes_processed,
    delay_time
FROM pg_stat_progress_vacuum
ORDER BY pid;
```

## 8.7.19 Inspect Effective Configuration

```sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_settings
WHERE name IN (
    'vacuum_cost_delay',
    'vacuum_cost_limit',
    'vacuum_cost_page_hit',
    'vacuum_cost_page_miss',
    'vacuum_cost_page_dirty',
    'autovacuum_vacuum_cost_delay',
    'autovacuum_vacuum_cost_limit',
    'vacuum_buffer_usage_limit',
    'track_cost_delay_timing'
)
ORDER BY name;
```

Also inspect `pg_class.reloptions` before assuming global settings control a particular relation.

## 8.7.20 Before/After Validation

Before changing cost controls, capture VACUUM runtime, `delay_time`, dead-tuple trajectory, blocks processed, CPU, storage latency, IOPS, throughput, queue depth, and foreground P95/P99 latency.

After the change, collect the same measurements over multiple comparable maintenance cycles. A successful change improves maintenance capacity without exceeding the acceptable foreground-resource envelope.

## 8.7.21 Production Tuning Workflow

1. Establish whether maintenance is behind by comparing debt generation with cleanup progress.
2. Determine whether throttling contributes materially by inspecting effective cost configuration and `delay_time`.
3. Check infrastructure headroom: CPU, storage latency, IOPS, throughput, queue depth, and platform limits.
4. Check competing work: autovacuum workers, manual VACUUM, checkpoints, backups, and heavy application I/O.
5. Check cleanup blockers such as old snapshots, replication horizons, and prepared transactions.
6. Inspect relation-level overrides in `pg_class.reloptions`.
7. Check transaction-ID, multixact, and failsafe risk.
8. Make the smallest justified adjustment; avoid changing multiple resource dimensions simultaneously unless the remediation explicitly requires it.
9. Observe multiple comparable maintenance cycles.
10. Keep or roll back the change based on evidence.

## 8.7.22 Production Principles

1. **Cost controls govern maintenance aggressiveness, not eligibility.**
2. **Manual VACUUM and autovacuum can have materially different throttling.**
3. **Cost units are accounting weights, not exact IOPS or latency measurements.**
4. **Lower delay or higher cost limit generally increases maintenance aggressiveness.**
5. **More aggressive VACUUM can improve completion time while harming foreground workload.**
6. **Excessive throttling can allow maintenance debt to grow even while workers remain active.**
7. **Normal autovacuum workers participate in global cost balancing.**
8. **Per-table cost overrides require aggregate-capacity analysis.**
9. **Critical operations can temporarily postpone cost-based sleeping.**
10. **Vacuum failsafe can disable normal cost throttling.**
11. **`vacuum_buffer_usage_limit` controls shared-buffer footprint rather than maintenance pacing.**
12. **Parallel VACUUM does not eliminate cost-based throttling.**
13. **Storage telemetry is necessary because vacuum cost settings are not a hard I/O governor.**
14. **Production changes require baselines, validation, ownership, and rollback.**

## 8.7.24 Key Takeaway

Cost-based vacuum delay controls the **resource intensity** of PostgreSQL maintenance. Production behavior depends not only on cost settings but also on worker capacity, maintenance memory, buffer footprint, storage capability, cleanup blockers, and failsafe state.

A sustainable system requires:

```text
maintenance completion capacity >= maintenance generation rate
```

while foreground latency, CPU utilization, storage latency, IOPS, and throughput remain inside the application's acceptable operating envelope.

The best vacuum cost configuration is neither the one that makes VACUUM finish fastest nor the one that minimizes maintenance resource consumption. It is the configuration that allows PostgreSQL to complete maintenance reliably while preventing both maintenance debt and foreground workload interference from becoming unacceptable.
