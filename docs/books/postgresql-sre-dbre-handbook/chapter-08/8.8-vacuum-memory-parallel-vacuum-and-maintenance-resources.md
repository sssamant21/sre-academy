# 8.8 — Vacuum Memory, Parallel Vacuum, and Maintenance Resources

Status: **CANONICAL**

## Purpose

VACUUM performance is governed by more than autovacuum trigger thresholds and cost-based throttling. Once VACUUM begins, its ability to complete maintenance efficiently depends on maintenance memory, autovacuum worker memory, dead-tuple identifier capacity, table and index characteristics, parallel index-maintenance capability, worker availability, CPU capacity, storage bandwidth and latency, shared-buffer behavior, concurrent maintenance activity, and cost-based throttling.

The central production relationship is:

```text
maintenance resources
        |
        v
VACUUM processing capacity
        |
        v
maintenance completion rate
```

Increasing resources can improve maintenance throughput, but more resources do not automatically mean better production behavior. Additional memory, workers, or parallelism can move the bottleneck to CPU, storage, cache capacity, or total system memory.

For SRE/DBRE operations, vacuum resource tuning is therefore a **capacity-planning and resource-governance problem**, not merely a parameter-tuning exercise.

## 8.8.1 The VACUUM Resource Model

| Resource dimension | Server-level control | Operation/session-level control |
|---|---|---|
| Manual maintenance working memory | `maintenance_work_mem` | session configuration |
| Autovacuum working memory | `autovacuum_work_mem` | autovacuum configuration |
| Parallel maintenance ceiling | `max_parallel_maintenance_workers` | `VACUUM (PARALLEL n)` |
| Global parallel-worker capacity | `max_parallel_workers`, `max_worker_processes` | runtime availability |
| Parallel index eligibility | `min_parallel_index_scan_size` | index characteristics |
| Buffer-strategy footprint | `vacuum_buffer_usage_limit` | `BUFFER_USAGE_LIMIT` |
| VACUUM pacing | vacuum cost GUCs | session/table-specific controls |
| Autovacuum concurrency | autovacuum worker controls | relation eligibility/workload |
| Physical CPU/I/O capacity | infrastructure | infrastructure |

These controls interact operationally but are not interchangeable.

## 8.8.2 `maintenance_work_mem`

`maintenance_work_mem` controls memory available to supported maintenance operations such as VACUUM, CREATE INDEX, and some ALTER TABLE operations. The PostgreSQL 18 default is `64MB`.

It is normally reasonable for this setting to be larger than `work_mem` because the concurrency model is different. Production sizing must nevertheless consider total memory exposure across concurrent database activity.

## 8.8.3 Why VACUUM Needs Maintenance Memory

During standard VACUUM, PostgreSQL scans the heap and identifies dead item identifiers requiring subsequent cleanup. Those identifiers must be retained so corresponding index entries can be processed.

The amount of available maintenance memory influences how much dead-item information VACUUM can retain before index processing must occur. This becomes especially important for very large or heavily updated tables and relations with multiple large indexes.

## 8.8.4 Repeated Index-Vacuum Cycles

If VACUUM cannot retain all necessary dead-item identifiers during a heap scan, index processing can occur multiple times:

```text
heap scan
    |
    v
dead-item capacity reached
    |
    v
vacuum indexes
    |
    v
vacuum heap
    |
    v
resume heap scan
    |
    v
repeat if necessary
```

Repeated index-vacuum cycles can increase elapsed VACUUM time, index I/O, CPU consumption, storage bandwidth demand, and interference with foreground workload. This does not mean every long VACUUM is memory constrained; repeated index-vacuum cycles are a diagnostic signal when evaluating maintenance-memory capacity.

## 8.8.5 Version Note — PostgreSQL 17+

PostgreSQL 17 introduced an important VACUUM memory-management change. Older releases had a practical historical limitation in memory used to retain dead-tuple identifiers during VACUUM even when maintenance memory was configured above 1 GB. PostgreSQL 17 changed the underlying representation and removed that historical silent 1-GB limitation.

Do not carry pre-17 VACUUM memory assumptions into PostgreSQL 17 or PostgreSQL 18 operations without validation. This handbook uses PostgreSQL 18 as its primary baseline.

## 8.8.6 `autovacuum_work_mem`

Autovacuum has a dedicated maintenance-memory control, `autovacuum_work_mem`. The PostgreSQL 18 default is `-1`, which means autovacuum workers use `maintenance_work_mem` as their applicable maintenance-memory limit.

This setting is operationally important because continuous background maintenance and manually controlled maintenance may require different memory envelopes.

## 8.8.7 Aggregate Autovacuum Memory Exposure

If `maintenance_work_mem = 1GB` and `autovacuum_work_mem = -1`, capacity planning must not treat several concurrent autovacuum workers as having only a single 1-GB maintenance-memory exposure.

The relevant model is applicable per-worker memory ceiling multiplied by concurrent autovacuum workers. This does not mean every worker immediately allocates its entire ceiling; it means concurrent maintenance processes can consume memory independently within their applicable limits.

This matters particularly on smaller instances, memory-constrained VMs, Kubernetes deployments, and high-concurrency autovacuum configurations.

## 8.8.8 Why a Separate `autovacuum_work_mem` Can Help

Operators may require substantial memory for controlled manual maintenance while wanting tighter limits for continuously running background workers. A separate `autovacuum_work_mem` permits that distinction.

There is no universal ratio between these settings. Values must be derived from relation sizes, churn, worker concurrency, maintenance behavior, available RAM, foreground workload, and infrastructure headroom.

## 8.8.9 Configured Memory Is a Ceiling

A configuration such as `autovacuum_work_mem = 512MB` does not imply that each worker immediately consumes 512 MB of resident memory. Treat configured maintenance memory as an applicable ceiling rather than a guaranteed allocation, while still modeling plausible concurrent exposure for capacity planning.

## 8.8.10 PostgreSQL Memory Is a System-Wide Capacity Problem

A simplified memory model includes shared buffers, backend/process memory, foreground `work_mem` exposure, autovacuum maintenance exposure, manual maintenance exposure, parallel/background process overhead, OS/filesystem requirements, and operational safety margin.

Increasing maintenance memory can improve VACUUM efficiency while reducing headroom elsewhere. A successful maintenance optimization must improve the database as a whole.

## 8.8.11 Kubernetes and Container Memory

For PostgreSQL running inside Kubernetes, the operational memory boundary may be the pod/container limit rather than physical node RAM. PostgreSQL memory parameters do not translate directly into exact Kubernetes working-set consumption; they are configuration limits and resource controls contributing to aggregate process behavior.

Evaluate them together with pod memory requests and limits, `shared_buffers`, connection count, query-memory exposure, autovacuum concurrency, sidecar/operator overhead, container working set, memory-pressure events, and OOM history. A VACUUM optimization that materially increases OOM risk is not successful.

# Parallel VACUUM

## 8.8.12 What Parallel VACUUM Actually Parallelizes

A critical distinction is:

> **Parallel VACUUM does not parallelize the heap scan.**

Parallel workers can participate in eligible **index vacuuming and index cleanup** phases. This distinction is essential when diagnosing why adding parallel workers does not reduce every phase of VACUUM runtime.

## 8.8.13 `VACUUM (PARALLEL n)`

Manual VACUUM can request a parallel-worker ceiling:

```sql
VACUUM (
    PARALLEL 4
) public.orders;
```

The value specifies a maximum requested degree of parallelism for eligible VACUUM index processing. It does not guarantee that four workers will execute.

## 8.8.14 Parallel-VACUUM Eligibility

Actual parallelism depends on indexes supporting parallel VACUUM, eligible index sizes, `min_parallel_index_scan_size`, `max_parallel_maintenance_workers`, `max_parallel_workers`, `max_worker_processes`, and current worker availability. The number of workers is also constrained by the number of indexes eligible for parallel processing.

Parallel VACUUM is therefore fundamentally **index-oriented**.

## 8.8.15 `min_parallel_index_scan_size`

Despite its name, `min_parallel_index_scan_size` also participates in determining whether an index can be used for parallel VACUUM. The PostgreSQL 18 default is `512kB`.

Small indexes may therefore not participate in parallel VACUUM even when a command requests several workers. This is an important troubleshooting parameter when requested parallelism does not appear.

## 8.8.16 `max_parallel_maintenance_workers`

`max_parallel_maintenance_workers` establishes the maximum number of parallel workers that supported maintenance operations can start. The PostgreSQL 18 default is `2`. Setting it to `0` disables parallel workers for supported utility operations.

A command such as `VACUUM (PARALLEL 8) public.orders;` cannot create eight effective parallel maintenance workers when server-level or global worker ceilings permit fewer.

## 8.8.17 Broader Worker Limits

Relevant settings include `max_parallel_maintenance_workers`, `max_parallel_workers`, and `max_worker_processes`. Runtime worker availability matters as well.

Therefore configured parallelism, available parallelism, and observed parallelism are not necessarily equal.

## 8.8.18 Parallel Maintenance Memory Semantics

For supported parallel utility work, `maintenance_work_mem` applies to the utility command as a whole rather than simply becoming an independent full allowance for every parallel worker.

Thus `maintenance_work_mem = 1GB` with `VACUUM (PARALLEL 4)` does not imply a simplistic leader-plus-four-workers calculation of `5 × 1GB` maintenance memory for that VACUUM.

This distinction is important because parallel query memory can behave differently. Shared command-level maintenance memory does not, however, mean parallel maintenance has no additional resource cost.

## 8.8.19 Parallelism Amplifies CPU and I/O Demand

Parallel VACUUM can shorten eligible index-maintenance phases by increasing concurrency. More workers can increase CPU concurrency, index I/O concurrency, and storage-bandwidth demand.

When infrastructure has sufficient headroom this can help. When it does not, CPU or storage saturation can increase foreground P95/P99 latency. The production objective is sufficient maintenance throughput with acceptable system-wide resource consumption, not maximum parallelism.

## 8.8.20 Parallel VACUUM and Cost-Based Delay

Parallel VACUUM does not bypass the cost-control model described in Section 8.7. Parallel controls govern execution concurrency while cost controls govern execution pacing. Changing one does not eliminate the other.

## 8.8.21 `VACUUM FULL` Is Different

Do not transfer parallel standard-VACUUM assumptions to `VACUUM FULL`. `VACUUM FULL` rewrites the relation and requires an `ACCESS EXCLUSIVE` lock. Standard VACUUM normally performs in-place maintenance while allowing ordinary concurrent access.

# Buffer Resources

## 8.8.22 Buffer Access Strategy

VACUUM and ANALYZE normally use a Buffer Access Strategy intended to limit disruption to the ordinary shared-buffer working set. PostgreSQL 18 provides `vacuum_buffer_usage_limit` with a default of `2MB`.

For a nonzero value, the documented range is `128kB–16GB`, and PostgreSQL constrains the effective value to no more than one-eighth of `shared_buffers` when necessary. A value of `0` allows the operation to use shared buffers without the normal special VACUUM buffer-strategy limit.

## 8.8.23 `BUFFER_USAGE_LIMIT`

Manual VACUUM can override the applicable buffer-usage limit where supported:

```sql
VACUUM (
    BUFFER_USAGE_LIMIT '64MB'
) public.orders;
```

This changes the maintenance operation's shared-buffer strategy footprint. It does not replace `maintenance_work_mem`, vacuum cost controls, or parallel-worker controls.

## 8.8.24 Larger Buffer Footprints Are Not Automatically Better

A larger maintenance buffer footprint can improve VACUUM or ANALYZE performance in some workloads, but it can also increase displacement of application pages and foreground cache misses. The correct success metric is system-wide performance rather than VACUUM runtime alone.

# Production Failure Scenarios

## 8.8.25 Failure Pattern — Too Little Maintenance Memory

Symptoms may include a large VACUUM, high dead-item volume, multiple index-vacuum cycles, and long maintenance runtime.

Investigate effective `maintenance_work_mem`, effective `autovacuum_work_mem`, PostgreSQL major version, `index_vacuum_count`, dead-item identifier usage, table size, index count and size, VACUUM phases, and storage latency. Do not increase memory solely because VACUUM is slow; first establish evidence that maintenance-memory capacity contributes materially to repeated processing.

## 8.8.26 Failure Pattern — Excessive Autovacuum Memory Exposure

High `autovacuum_work_mem` combined with many concurrent workers can create unsafe aggregate exposure. Symptoms may include rising PostgreSQL resident memory, shrinking OS/cache headroom, host memory pressure, swap activity, Kubernetes memory-pressure events, OOM termination, or degraded foreground workload performance.

Possible remediation includes reducing the per-worker ceiling, reducing maintenance concurrency, increasing infrastructure capacity, or changing the maintenance strategy.

## 8.8.27 Failure Pattern — Parallel VACUUM Makes the System Slower

A parallel VACUUM may finish more quickly while CPU usage, storage latency, and foreground P95/P99 worsen. Reducing parallelism can therefore be the correct production action even when it increases VACUUM elapsed time.

## 8.8.28 Failure Pattern — Requested Parallelism Does Not Appear

If `VACUUM (PARALLEL 8) public.orders;` produces few or no parallel workers, investigate eligible indexes, index sizes, `min_parallel_index_scan_size`, `max_parallel_maintenance_workers`, `max_parallel_workers`, `max_worker_processes`, and runtime worker availability.

`PARALLEL` specifies an upper bound, not a worker guarantee.

# Observability

## 8.8.29 Observe VACUUM Memory and Index Cycles

A production diagnostic query is:

```sql
SELECT
    pid,
    datname,
    relid::regclass AS relation,
    phase,
    heap_blks_total,
    heap_blks_scanned,
    heap_blks_vacuumed,
    index_vacuum_count,
    max_dead_tuple_bytes,
    dead_tuple_bytes,
    num_dead_item_ids,
    indexes_total,
    indexes_processed
FROM pg_stat_progress_vacuum
ORDER BY pid;
```

`index_vacuum_count` shows completed index-vacuum cycles. `max_dead_tuple_bytes` shows the maximum memory available for dead-item identifiers, `dead_tuple_bytes` shows current memory occupied by them, and `num_dead_item_ids` shows dead-item identifiers accumulated since the previous index-vacuum cycle.

Together these fields provide useful evidence when determining whether maintenance-memory capacity contributes to repeated index processing. They are version-sensitive and should be interpreted using documentation for the deployed PostgreSQL major version.

## 8.8.30 Inspect Maintenance Configuration

```sql
SELECT
    name,
    setting,
    unit,
    source
FROM pg_settings
WHERE name IN (
    'maintenance_work_mem',
    'autovacuum_work_mem',
    'autovacuum_max_workers',
    'max_parallel_maintenance_workers',
    'max_parallel_workers',
    'max_worker_processes',
    'min_parallel_index_scan_size',
    'vacuum_buffer_usage_limit',
    'vacuum_cost_delay',
    'vacuum_cost_limit'
)
ORDER BY name;
```

Configuration inspection should precede tuning.

## 8.8.31 Infrastructure Telemetry

PostgreSQL statistics alone are insufficient for resource-capacity analysis. Collect CPU utilization and saturation, resident and available memory, swap activity, container working set, OOM events, storage read/write latency, IOPS, throughput, queue depth, and foreground P95/P99 latency.

For cloud platforms also consider instance bandwidth, disk IOPS and throughput limits, burst-credit behavior, storage tier, and VM/database-instance memory ceilings. Parallelism cannot overcome a saturated infrastructure boundary.

# Capacity Planning

## 8.8.32 Memory Capacity Envelope

A conservative planning model is:

```text
baseline PostgreSQL memory
+
foreground workload exposure
+
autovacuum maintenance exposure
+
manual maintenance exposure
+
parallel/background overhead
+
OS/container requirements
+
safety headroom
<=
available memory
```

This is a capacity envelope, not an exact allocation formula. Actual consumption must be validated through runtime telemetry.

## 8.8.33 Maintenance Throughput Envelope

Effective maintenance capacity emerges from maintenance memory, worker availability, eligible parallelism, CPU capacity, storage capacity, buffer strategy, and cost controls. A resource change can expose the next bottleneck, so tuning should be iterative.

# Production Change Procedure

## 8.8.34 Step 1 — Identify the Actual Bottleneck

Determine whether maintenance is constrained by maintenance memory, CPU, storage, cost throttling, worker availability, parallel eligibility, cleanup blockers, or index footprint. Do not begin with a parameter assumption.

## 8.8.35 Step 2 — Inspect Effective Memory Settings

Check `maintenance_work_mem` and `autovacuum_work_mem`, and determine which applies to the operation under investigation.

## 8.8.36 Step 3 — Examine VACUUM Progress

Inspect `phase`, `index_vacuum_count`, `max_dead_tuple_bytes`, `dead_tuple_bytes`, and `num_dead_item_ids`. Look for evidence of repeated index processing.

## 8.8.37 Step 4 — Establish Memory Headroom

Measure PostgreSQL process memory, host/container memory, OS/cache headroom, swap behavior, Kubernetes working set, memory-pressure events, and OOM history.

## 8.8.38 Step 5 — Establish CPU and Storage Headroom

Before adding parallelism, determine whether CPU and storage can absorb additional concurrency. Measure CPU, storage latency, IOPS, throughput, queue depth, and foreground latency.

## 8.8.39 Step 6 — Inspect Parallel Eligibility and Capacity

Check eligible indexes, index sizes, `min_parallel_index_scan_size`, `max_parallel_maintenance_workers`, `max_parallel_workers`, `max_worker_processes`, and runtime worker availability.

## 8.8.40 Step 7 — Make the Smallest Justified Change

Possible controlled changes include adjusting `autovacuum_work_mem`, `maintenance_work_mem`, requested VACUUM parallelism, parallel-maintenance limits, or buffer usage. Avoid changing memory, parallelism, cost delay, worker concurrency, and buffer strategy simultaneously unless the remediation explicitly requires a coordinated change.

## 8.8.41 Step 8 — Observe Comparable Maintenance Cycles

Compare VACUUM runtime, index-vacuum cycles, dead-item capacity, memory consumption, CPU, storage behavior, foreground latency, and maintenance-debt trajectory. One faster VACUUM is insufficient evidence.

## 8.8.42 Step 9 — Retain or Roll Back

Retain the change only when evidence shows that overall system behavior improved: maintenance throughput improves, maintenance debt remains controlled, memory remains safe, CPU and storage remain healthy, and foreground latency remains acceptable.

# Production Principles

## 8.8.43 Canonical Operating Principles

1. **VACUUM resource tuning is a capacity problem, not merely a parameter problem.**
2. **`maintenance_work_mem` and `autovacuum_work_mem` have different operational scopes.**
3. **Autovacuum memory exposure must be evaluated across concurrent workers.**
4. **Configured maintenance memory is a ceiling rather than guaranteed resident allocation.**
5. **PostgreSQL 17 changed VACUUM dead-item memory behavior, so pre-17 assumptions must not be carried forward blindly.**
6. **Insufficient maintenance memory can contribute to repeated index-vacuum cycles.**
7. **`index_vacuum_count` is an important diagnostic signal for repeated index processing.**
8. **Parallel VACUUM does not parallelize the heap scan.**
9. **Parallel workers participate in eligible index vacuuming and index cleanup.**
10. **`VACUUM (PARALLEL n)` defines a maximum request, not a worker guarantee.**
11. **Actual parallelism depends on eligible indexes, index size, configured worker ceilings, and runtime availability.**
12. **`min_parallel_index_scan_size` also participates in parallel-VACUUM index eligibility.**
13. **`maintenance_work_mem` is treated at the utility-command level for supported parallel maintenance rather than simply multiplied by every parallel worker.**
14. **Parallel maintenance can nevertheless materially increase CPU and I/O demand.**
15. **Cost-based delay remains relevant to parallel VACUUM.**
16. **`vacuum_buffer_usage_limit` controls buffer-strategy footprint rather than maintenance working memory.**
17. **A faster VACUUM is not a successful optimization if it creates memory pressure, storage saturation, or unacceptable foreground latency.**
18. **Every production change requires baseline measurements, validation, ownership, and rollback criteria.**

## 8.8.45 Key Takeaway

VACUUM maintenance capacity emerges from interacting resources: maintenance memory, worker capacity, parallel index processing, CPU, storage, buffer strategy, and cost controls. No single parameter determines maintenance performance.

The sustainable objective remains:

```text
maintenance completion capacity
             >=
maintenance generation rate
```

while memory pressure, CPU saturation, storage latency, and foreground P95/P99 latency remain inside the application's acceptable operating envelope.

For production PostgreSQL, the best maintenance configuration is not the configuration with the largest `maintenance_work_mem`, the most parallel workers, or the shortest individual VACUUM runtime. It is the configuration that gives VACUUM enough resources to remain ahead of maintenance debt **without allowing maintenance itself to become a resource-exhaustion event**.
