# 8.9 — Visibility Map, All-Visible, and All-Frozen Pages

Status: **CANONICAL**

## Purpose

PostgreSQL's visibility map is compact page-level metadata that connects VACUUM efficiency, heap-page skipping, transaction-ID freezing, anti-wraparound maintenance, index-only scans, query I/O, workload churn, and maintenance capacity.

Every heap relation has a visibility map containing two bits per heap page: **all-visible** and **all-frozen**. These states let PostgreSQL avoid work that would otherwise require reading or modifying heap pages. The production objective is not to maximize VM percentages blindly, but to determine whether visibility coverage is appropriate for the workload.

## 8.9.1 Visibility Map Architecture

Each heap relation has a separate `_vm` visibility-map fork alongside its main heap and, where applicable, `_fsm` free-space-map fork. The VM stores two bits per heap page and is therefore much smaller than the heap. Indexes do not have visibility maps.

## 8.9.2 All-Visible

The all-visible bit certifies PostgreSQL's all-visible condition for the heap page. Operationally, no tuple on that page requires ordinary VACUUM cleanup, the page can often be skipped by VACUUM, and index-only scans can use the VM to avoid heap visibility checks.

## 8.9.3 All-Frozen

The all-frozen bit indicates that tuples on the page no longer require normal future transaction-ID freezing until the page is modified. This reduces future aggressive and anti-wraparound freezing work.

A core VM invariant is:

```text
all-frozen => all-visible
```

An all-visible page need not be all-frozen.

## 8.9.4 Conservative Semantics

The visibility map is conservative. A set bit means PostgreSQL has certified the condition. A clear bit means the VM does not currently certify it; it does not necessarily prove that the underlying page could not satisfy the condition.

VACUUM establishes VM bits after safely determining page state. Tuple insertion, update, deletion, or tuple locking can invalidate applicable visibility/freezing state.

## 8.9.5 VACUUM Page Skipping

The VM is a major source of information that allows VACUUM to avoid unnecessary heap-page work. However, a page skipped by VACUUM was not necessarily skipped because it was all-visible; PostgreSQL can skip pages for additional reasons.

Normal and aggressive VACUUM have different objectives. An all-visible but not all-frozen page may require no ordinary cleanup while still requiring future freezing work. An all-frozen page can avoid the corresponding freezing work until modified.

## 8.9.6 PostgreSQL 18 Eager Freezing

PostgreSQL 18 allows normal VACUUM to eagerly process some pages that are all-visible but not all-frozen, distributing freezing work across routine maintenance instead of deferring all of it to later aggressive VACUUM operations.

A relevant PostgreSQL 18 control is:

```text
vacuum_max_eager_freeze_failure_rate = 0.03
```

The default represents a 3% failure-rate threshold. A value of `0` disables eager scanning. Detailed freezing policy is covered in Section 8.10.

## 8.9.7 Visibility Map and Index-Only Scans

Indexes generally do not contain sufficient MVCC visibility information to prove tuple visibility. A normal index path commonly requires a heap visibility check. An index-only scan can consult the VM; when the referenced heap page is all-visible, PostgreSQL can avoid that heap visibility lookup.

An `Index Only Scan` does not guarantee zero heap access. Inspect the runtime `Heap Fetches` value.

Example:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT order_id, customer_id, order_date
FROM public.orders
WHERE customer_id = 10042;
```

Correlate `Heap Fetches` with buffer activity, relation churn, and recent VACUUM activity.

## 8.9.8 Workload-Dependent Coverage

Mostly immutable relations such as historical partitions can accumulate high stable all-visible coverage after VACUUM. High-churn OLTP relations can repeatedly lose visibility state as application activity modifies pages.

There is no universal healthy all-visible or all-frozen percentage. Interpret coverage according to write rate, UPDATE/DELETE churn, partition age, relation lifecycle, VACUUM cadence, retained horizons, freezing state, and index-only-scan expectations.

Low all-visible coverage is not automatically evidence of autovacuum failure.

## 8.9.9 Relation-Level Estimates

`pg_class.relallvisible` estimates the number of pages marked all-visible. `pg_class.relallfrozen` estimates pages marked all-frozen. `relpages` estimates total relation pages.

A useful inventory query is:

```sql
SELECT
    n.nspname AS schema_name,
    c.relname AS table_name,
    c.relpages,
    c.relallvisible,
    c.relallfrozen,
    round(100.0 * c.relallvisible / NULLIF(c.relpages, 0), 2) AS all_visible_pct,
    round(100.0 * c.relallfrozen / NULLIF(c.relpages, 0), 2) AS all_frozen_pct
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND c.relpages > 0
ORDER BY c.relpages DESC;
```

These values are useful estimates for fleet inventory, ranking, and trend analysis, not exact VM inspection.

## 8.9.10 `pg_visibility`

The supplied `pg_visibility` extension provides deeper VM and page-level inspection, including summaries, consistency checks, and a privileged VM-repair mechanism.

Where policy permits:

```sql
CREATE EXTENSION IF NOT EXISTS pg_visibility;
```

Most inspection functions require an appropriately privileged role such as superuser or the documented `pg_stat_scan_tables` capability. `pg_truncate_visibility_map()` is more tightly restricted. Managed-service privilege mappings must be validated separately.

Use an escalation hierarchy:

```text
pg_class estimates
    -> pg_visibility_map_summary()
    -> page-level VM inspection
    -> heap-reading consistency checks
    -> repair operation
```

Start with metadata and summaries and escalate only when evidence warrants deeper inspection.

Example summary:

```sql
SELECT *
FROM pg_visibility_map_summary('public.orders'::regclass);
```

Targeted page-level inspection:

```sql
SELECT *
FROM pg_visibility_map('public.orders'::regclass)
LIMIT 100;
```

VM-only inspection can be materially cheaper than diagnostics that must also read heap pages.

## 8.9.11 `PD_ALL_VISIBLE`

PostgreSQL also maintains the heap page-header flag `PD_ALL_VISIBLE`, physically distinct from the all-visible bit in the separate VM. They normally correspond, but disagreement does not automatically prove corruption. Crash-recovery state, concurrent changes during inspection, or actual inconsistency can produce observable differences.

## 8.9.12 Integrity Checks

`pg_visibility` provides `pg_check_visible()` and `pg_check_frozen()`. These are integrity diagnostics, not ordinary VM-percentage analysis. Results indicating tuples that violate all-visible or all-frozen VM claims should be treated as potentially serious integrity concerns.

## 8.9.13 Repair Safety Gate

**Visibility-map truncation is a repair operation, not routine VACUUM tuning.**

`pg_truncate_visibility_map()` removes the relation's VM information. Subsequent VACUUM must re-establish visibility information, potentially causing substantial relation-wide maintenance work.

Do not truncate a VM merely because index-only scans show heap fetches, all-visible coverage is lower than expected, VACUUM is slow, or a relation appears bloated.

Similarly:

```sql
VACUUM (DISABLE_PAGE_SKIPPING) public.orders;
```

is an exceptional diagnostic/recovery control for cases where page-skipping information may be unreliable. It is not routine performance tuning.

## 8.9.14 Production Failure Patterns

### Index Only Scan Performs Many Heap Fetches

Investigate all-visible coverage, modification rate, recent VACUUM activity, retained horizons, and whether the workload is inherently high churn. The index can be suitable while VM state prevents heap-free execution.

### Static Table Has Low All-Visible Coverage

For a supposedly immutable relation, check recent writes, VACUUM history, maintenance cancellations, retained horizons, and workload assumptions before escalating to integrity investigation.

### High All-Visible but Low All-Frozen Coverage

This can be normal. It means much of the relation requires no ordinary cleanup but has not reached equivalent frozen-page coverage. Interpret it using relation age, transaction rate, freeze thresholds, VACUUM history, PostgreSQL version, and eager-freezing behavior.

### Visibility Coverage Repeatedly Collapses

Investigate UPDATE/DELETE rates, INSERT locality, tuple locking, HOT-update behavior, page reuse, and partition lifecycle. The VM may be behaving exactly as designed.

## 8.9.15 VM Is Not Bloat

Visibility state and physical space utilization are different concepts. Low all-visible coverage does not prove heap bloat, and a bloated relation can contain all-visible pages. Heap bloat is covered in Section 8.14.

The visibility map also differs from the free space map: the VM tracks visibility/freezing metadata, while the FSM tracks reusable free space for tuple placement.

## 8.9.16 Production Investigation Workflow

1. Define whether the symptom is slow VACUUM, poor index-only-scan efficiency, unexpected VM coverage, freezing workload, or suspected inconsistency.
2. Characterize relation size, write rate, UPDATE/DELETE rate, indexes, partition lifecycle, and expected mutability.
3. Inspect `relpages`, `relallvisible`, and `relallfrozen` as low-cost estimates.
4. Correlate VACUUM/autovacuum history and dead-tuple trajectory.
5. Correlate workload churn.
6. Use `pg_visibility_map_summary()` when deeper inspection is justified.
7. For query concerns, use `EXPLAIN (ANALYZE, BUFFERS)` and inspect `Heap Fetches`.
8. Check retained transaction and replication-related horizons where relevant.
9. Escalate to integrity checks only when evidence suggests inconsistency.
10. Use repair controls only with documented evidence, impact assessment, maintenance planning, monitoring, and recovery strategy.

## 8.9.17 Canonical Production Principles

1. Every heap relation has a visibility map; indexes do not.
2. The VM stores all-visible and all-frozen bits per heap page.
3. All-frozen implies all-visible; all-visible does not imply all-frozen.
4. VM state is conservative.
5. VACUUM establishes VM bits; tuple changes can invalidate them.
6. VM information helps VACUUM avoid unnecessary page work.
7. PostgreSQL 18 eager freezing distributes some freezing work across routine VACUUM operations.
8. All-visible information enables suitable index-only scans to avoid heap visibility checks.
9. An Index Only Scan can still perform heap fetches.
10. VM coverage is workload dependent; there is no universal healthy percentage.
11. `relallvisible` and `relallfrozen` are estimates, not exact VM scans.
12. `pg_visibility` provides progressively deeper visibility and integrity inspection.
13. `PD_ALL_VISIBLE` disagreement does not automatically prove corruption.
14. Integrity-check failures are different from low VM coverage.
15. VM truncation and `DISABLE_PAGE_SKIPPING` are exceptional repair/diagnostic controls, not routine tuning.
16. Visibility-map state is not equivalent to bloat or free-space state.

## 8.9.19 Key Takeaway

The visibility map lets PostgreSQL remember whether a heap page is all-visible and whether it is all-frozen. Those facts influence VACUUM page skipping, freezing workload, anti-wraparound maintenance, and index-only-scan efficiency.

The critical distinctions are:

```text
all-frozen => all-visible
all-visible != all-frozen
Index Only Scan != zero heap fetches
low VM coverage != autovacuum failure
visibility state != bloat
```

The production objective is to understand whether observed visibility coverage is appropriate for the relation's workload and maintenance history, not to maximize VM percentages blindly.
