## 1.10 — Built-in Data Types

**Edition:** Revised Final / Canonical  
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

- Explain what a Python data type represents.
- Identify the major built-in Python data types used in everyday engineering.
- Distinguish numeric, text, sequence, mapping, set, binary, and null-related types.
- Inspect an object's type with `type()`.
- Test type relationships appropriately with `isinstance()`.
- Distinguish mutable and immutable built-in types.
- Explain Python's dynamic and strong typing characteristics.
- Understand hashability and its relationship to dictionaries and sets.
- Distinguish text from binary data.
- Select built-in types according to application semantics and ownership requirements.
- Troubleshoot common production problems involving incorrect type assumptions.

---

### 1.10.1 Objects and Types

As established in Section 1.9, Python variables are names bound to objects. Every Python object has a type.

```python
count = 10
environment = "production"
servers = ["db01", "db02"]

print(type(count))
print(type(environment))
print(type(servers))
```

A type determines important aspects of an object's behavior, including the operations it supports, mutability, comparison behavior, hashability, and interaction with other objects.

---

### 1.10.2 Python Is Dynamically Typed

Python is dynamically typed. A name does not require a permanently fixed runtime type:

```python
result = 200
result = "success"
result = {"status": "success"}
```

The objects have types; the name `result` is rebound to different objects. Dynamic typing does not mean Python objects lack types.

---

### 1.10.3 Python Is Strongly Typed

Python is commonly described as strongly typed because it generally does not silently reinterpret unrelated objects for incompatible operations.

```python
count = 10
message = "20"
# count + message  # TypeError
result = count + int(message)
```

The phrase *strongly typed* has no single universally agreed formal definition; here it is practical engineering terminology for Python's relatively strict treatment of incompatible runtime types.

---

### 1.10.4 Major Built-in Type Families

| Family | Important Built-in Types |
|---|---|
| Numeric | `int`, `float`, `complex` |
| Boolean | `bool` |
| Text | `str` |
| Sequences | `list`, `tuple`, `range` |
| Mapping | `dict` |
| Sets | `set`, `frozenset` |
| Binary | `bytes`, `bytearray`, `memoryview` |
| Null/special value | `NoneType` / `None` |

This is an intentionally selective engineering classification rather than the complete Python built-in type hierarchy. Python also exposes runtime types associated with functions, classes, modules, iterators, exceptions, context managers, and other constructs.

---

### 1.10.5 Integer Type — `int`

Integers represent whole numbers and are immutable. Python integers are not limited to conventional signed 32-bit or 64-bit ranges; their precision can expand subject to available memory and implementation constraints.

```python
retry_count = 3
port = 5432
large_number = 10 ** 100
```

Detailed numeric behavior is covered in Section 1.11.

---

### 1.10.6 Floating-Point Type — `float`

Floating-point values represent real-number approximations.

```python
cpu_usage = 72.5
latency_seconds = 0.125
print(0.1 + 0.2)
```

Many decimal fractions cannot be represented exactly in binary floating point. Applications requiring exact decimal arithmetic should evaluate facilities such as `decimal.Decimal`.

---

### 1.10.7 Complex Numbers — `complex`

Python directly supports immutable complex numbers:

```python
value = 3 + 4j
print(value.real)
print(value.imag)
```

They are useful in mathematical, scientific, signal-processing, and engineering workloads.

---

### 1.10.8 Boolean Type — `bool`

Python provides `True` and `False`. `bool` is a subclass of `int`:

```python
print(isinstance(True, int))  # True
print(True + True)           # 2
```

Production code should normally use Boolean values to represent logical state rather than treating them as ordinary integers. Boolean semantics are covered in Section 1.13.

---

### 1.10.9 Text Type — `str`

A `str` object is an immutable sequence of Unicode characters, represented as Unicode code points. Python has no separate character type; indexing a string produces another `str` object.

```python
name = "Python"
print(name[0])
print(type(name[0]))
```

Strings are fundamental to configuration, logging, APIs, file processing, command-line interfaces, database applications, and automation. Section 1.12 covers strings in depth.

---

### 1.10.10 Lists — `list`

A list is an ordered, mutable sequence.

```python
servers = ["db01", "db02", "db03"]
servers.append("db04")
```

Lists may contain objects of different types. Use lists when order matters, duplicates are allowed, indexed access is useful, and the collection needs to change.

---

### 1.10.11 Tuples — `tuple`

A tuple is an ordered, immutable sequence, but tuple immutability applies to the tuple's structure rather than recursively to every referenced object.

```python
record = ("production", ["db01"])
record[1].append("db02")
```

The tuple remains structurally unchanged while the referenced list is mutated.

---

### 1.10.12 Range Objects — `range`

`range` represents an immutable sequence of integers and is commonly used for iteration.

```python
for port in range(8000, 8005):
    print(port)
```

A range represents its sequence compactly rather than constructing an ordinary list containing every integer.

---

### 1.10.13 Dictionaries — `dict`

A dictionary is a mutable mapping of hashable keys to values.

```python
config = {
    "environment": "production",
    "timeout": 30,
    "retries": 3,
}
```

Modern Python dictionaries preserve insertion order as part of the language specification.

---

### 1.10.14 Sets — `set`

A set is a mutable collection of distinct hashable objects.

```python
expected = {"db01", "db02", "db03"}
running = {"db01", "db03"}
missing = expected - running
```

Sets are useful for membership tests, duplicate elimination, intersections, unions, and differences. Set display or iteration order should not be treated as a stable application ordering contract.

---

### 1.10.15 Frozen Sets — `frozenset`

`frozenset` provides immutable set semantics. Unlike `set`, `frozenset` is immutable and hashable, so it can be used as a dictionary key or as an element of another set or `frozenset`.

```python
permissions = {
    frozenset({"read", "write"}): "editor"
}
```

---

### 1.10.16 Binary Data — `bytes`

`bytes` represents an immutable sequence of bytes. Text and binary data are different domains.

```python
message = "hello"
payload = message.encode("utf-8")
decoded = payload.decode("utf-8")
```

Production applications should make encoding boundaries explicit.

---

### 1.10.17 Mutable Binary Data — `bytearray`

`bytearray` is a mutable sequence of bytes.

```python
payload = bytearray(b"ABC")
payload[0] = 90
```

It is useful when binary data must be modified in place.

---

### 1.10.18 Memory Views — `memoryview`

`memoryview` exposes data through Python's buffer protocol without necessarily copying the underlying data.

```python
payload = bytearray(b"ABCDEF")
view = memoryview(payload)
view[0] = 90
```

A `memoryview` may be read-only or writable. It does not independently determine the mutability of underlying storage. Writable views can modify the referenced buffer; read-only views cannot.

---

### 1.10.19 `None` and `NoneType`

`None` is Python's singleton value commonly used to represent absence or no result.

```python
connection = None

if connection is None:
    print("No connection")
```

`None` is not semantically equivalent to `0`, `False`, `""`, `[]`, or `{}`. Section 1.14 covers null semantics in depth.

---

### 1.10.20 Inspecting Types with `type()`

`type()` returns an object's type.

```python
value = 100
print(type(value))
```

Exact type comparison can be appropriate when exact type identity is genuinely required, but it is often unnecessarily restrictive when subclasses are acceptable.

---

### 1.10.21 Type Checking with `isinstance()`

`isinstance()` supports inheritance-aware runtime checking.

```python
value = 10.5
if isinstance(value, (int, float)):
    print("numeric input")
```

It is generally preferable to exact `type()` comparison when subclasses are valid. Runtime checks should still be deliberate; APIs often benefit from accepting objects that provide required behavior rather than unnecessarily restricting callers to one concrete implementation.

---

### 1.10.22 Mutability Overview

| Type | Mutable? |
|---|---:|
| `int` | No |
| `float` | No |
| `complex` | No |
| `bool` | No |
| `str` | No |
| `tuple` | No |
| `range` | No |
| `list` | Yes |
| `dict` | Yes |
| `set` | Yes |
| `frozenset` | No |
| `bytes` | No |
| `bytearray` | Yes |
| `memoryview` | View may be read-only or writable |
| `NoneType` | No |

Mutability matters because shared references to mutable objects expose changes across application components.

---

### 1.10.23 Hashability

A hashable object has a hash value that remains stable during its lifetime and supports equality comparison. Objects that compare equal must have the same hash value.

Hashable objects can be dictionary keys and set members. Common hashable objects include integers, strings, bytes, `frozenset`, and many tuples. Lists, dictionaries, and sets are unhashable.

A tuple is not automatically hashable merely because its outer structure is immutable:

```python
valid_key = ("db01", 5432)
invalid_key = ("db01", ["primary"])
```

The second tuple cannot serve as a normal dictionary key because its contained list is unhashable.

---

### 1.10.24 Choosing the Right Built-in Type

Use a `list` when order and mutation matter; a `tuple` when positional structure should remain fixed; a `dict` for key/value relationships; a `set` for uniqueness and set operations; `frozenset` for immutable set semantics; `str` for text; and binary types for encoded or arbitrary binary data.

Choosing types according to semantics improves readability and reduces accidental misuse.

### 1.10.25 Production Example — Configuration Data

```python
config = {
    "environment": "production",
    "port": 5432,
    "timeout": 30.0,
    "ssl_enabled": True,
    "replicas": ["db02", "db03"],
    "tags": {"database", "production"},
}
```

The types communicate useful semantics: integer port, numeric timeout, Boolean state, ordered replicas, and unique tags.

---

### 1.10.26 Production Example — API Payload Validation

External systems may provide unexpected runtime types.

```python
payload = {"service": "payments", "retries": 3}
retries = payload.get("retries")

if isinstance(retries, bool) or not isinstance(retries, int):
    raise TypeError("retries must be an integer")
```

The explicit Boolean rejection matters because `bool` subclasses `int`. Production validation should express domain semantics, not merely broad runtime inheritance relationships.

---

### 1.10.27 Production Example — Text Versus Bytes

```python
message = "production"
payload = message.encode("utf-8")
```

A useful boundary model is application text → encode → bytes → external boundary, and external bytes → decode → application text. Encoding decisions should be explicit at system boundaries.

---

### 1.10.28 Production Example — Lists Versus Sets

```python
expected_nodes = ["db01", "db02", "db03"]
running_nodes = ["db01", "db03"]

missing = set(expected_nodes) - set(running_nodes)
```

Selecting a type whose native operations match the problem often produces simpler and more expressive code.

---

### 1.10.29 Common Type Mistakes

Common mistakes include assuming dynamic typing means no types, expecting automatic string-to-number conversion, overusing exact type checks, forgetting that `bool` subclasses `int`, treating text and bytes as interchangeable, assuming tuples are recursively immutable or always hashable, depending on set order, and ignoring ownership of shared mutable structures.

---

### 1.10.30 Troubleshooting Type Problems

When a type-related production failure occurs:

1. Inspect the actual type with `type(value)`.
2. Inspect the value with `repr(value)`.
3. Inspect external boundaries such as APIs, environment variables, command-line arguments, configuration files, databases, queues, CSV files, and network protocols.
4. Inspect explicit conversions such as `int()`, `float()`, `str()`, and `bool()`.
5. Check whether shared mutable state changed unexpectedly.
6. Verify validation expresses domain requirements.
7. Build a minimal reproduction.

```python
value = "3"
print(type(value))
print(value + value)            # 33
print(int(value) + int(value))  # 6
```

---

### 1.10.31 Production Engineering Rules

1. Every Python object has a type.
2. Think about names and object types separately.
3. Dynamic typing does not mean absence of types.
4. Use explicit conversions across representation boundaries.
5. Choose types according to domain semantics.
6. Understand mutability and ownership of shared data.
7. Do not assume immutable containers recursively contain immutable state.
8. Use `isinstance()` when inheritance-aware checking is intended.
9. Use exact type checks only when exact identity is required.
10. Remember that `bool` subclasses `int`.
11. Keep text and binary data conceptually separate.
12. Make encoding and decoding boundaries explicit.
13. Do not rely on set ordering.
14. Understand hashability before using dictionary keys or set members.
15. Treat external data as untrusted with respect to value and type.
16. Validate according to domain semantics.
17. Prefer types whose operations naturally represent the problem.
18. Consider object ownership whenever mutable state is shared.
19. Use `repr()` and `type()` when troubleshooting ambiguous values.
20. Prefer clear data models over clever mixtures of unrelated types.

### 1.10.36 Key Takeaways

Python is dynamically typed, but every runtime object has a definite type. Important built-in families include numeric types, Boolean values, text, sequences, mappings, sets, binary types, and `None`.

Choosing a type is not merely a storage decision. A type influences supported operations, mutability, equality and hashing behavior, collection semantics, representation boundaries, and ownership expectations.

The central engineering principle is:

> **Choose Python types according to the semantics and ownership of the data, not merely according to what can hold the value.**

That principle produces code that is easier to understand, validate, troubleshoot, test, and maintain.
