# Chapter 1 — Python Fundamentals and Development Environment

## 1.12 — Strings

**Edition:** Revised Final / Canonical

**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

- Explain Python's `str` text model.
- Create and manipulate string values safely.
- Understand string immutability, indexing, and slicing.
- Search, split, join, transform, and format strings.
- Distinguish Unicode code points, user-perceived characters, and encoded bytes.
- Apply Unicode case folding and normalization when domain requirements call for them.
- Distinguish `str` from `bytes`.
- Encode and decode text explicitly at system boundaries.
- Validate externally supplied text.
- Avoid unsafe string construction around SQL, subprocesses, paths, URLs, and structured formats.
- Protect sensitive textual data.
- Troubleshoot common Unicode, encoding, whitespace, and parsing problems.

---

## 1.12.1 What Is a Python String?

Python uses the built-in `str` type to represent Unicode text.

```python
service = "payments"
environment = "production"
message = "Database connection established"
```

These values are strings:

```python
print(type(service))
```

Output:

```text
<class 'str'>
```

A Python string is an immutable sequence of Unicode code points.

Unlike languages that provide a separate character type, indexing a Python string produces another `str`:

```python
language = "Python"

print(language[0])
print(type(language[0]))
```

Output:

```text
P
<class 'str'>
```

---

## 1.12.2 Creating String Literals

Single and double quotes both create ordinary strings:

```python
service = 'payments'
environment = "production"
```

Choose whichever improves readability:

```python
message = "Service isn't ready"
quote = 'The status is "healthy"'
```

Projects should apply a consistent formatting convention rather than attaching different semantics to the two forms.

---

## 1.12.3 Triple-Quoted Strings

Triple-quoted literals can span multiple physical lines:

```python
message = """Deployment completed.
Application health checks passed.
Traffic has been restored."""
```

Triple single quotes are also supported:

```python
message = '''Deployment completed.
Application health checks passed.'''
```

Newlines and indentation can become part of the resulting value, so inspect multiline text carefully when exact whitespace matters.

Triple-quoted strings are also used for docstrings.

---

## 1.12.4 Empty Strings

An empty string contains no code points:

```python
value = ""

print(len(value))
```

Output:

```text
0
```

Empty strings are falsy:

```python
if not value:
    print("empty")
```

An empty string and `None` represent different semantic states:

```text
""      empty text
None    absence/no value
```

`None` is covered in Section 1.14.

---

## 1.12.5 Strings Are Immutable

Strings cannot be modified in place:

```python
name = "python"
name[0] = "P"
```

This raises `TypeError`.

Instead, construct another string and rebind the name:

```python
name = "python"
name = "P" + name[1:]

print(name)
```

Output:

```text
Python
```

String methods likewise normally produce new strings:

```python
environment = "PRODUCTION"
normalized = environment.lower()

print(environment)
print(normalized)
```

Output:

```text
PRODUCTION
production
```

Conceptually:

```text
environment ──► "PRODUCTION"

normalized  ──► "production"
```

This follows the object and name-binding model established earlier in Chapter 1.

---

## 1.12.6 String Length

For a Python `str`, `len()` returns the number of Unicode code points in the string.

```python
service = "payments"

print(len(service))
```

Output:

```text
8
```

This count is not necessarily the number of user-perceived characters and is not the number of bytes required by an encoded representation.

For example:

```python
text = "café"

print(len(text))
print(len(text.encode("utf-8")))
```

Typical output:

```text
4
5
```

A useful production distinction is:

```text
Unicode code-point count
          ≠
user-perceived character count
          ≠
encoded byte count
```

This matters for database limits, protocols, storage constraints, APIs, and text validation.

---

## 1.12.7 String Indexing

Strings support zero-based indexing:

```python
name = "Python"

print(name[0])
print(name[1])
```

Output:

```text
P
y
```

Negative indexes count from the end:

```python
print(name[-1])
print(name[-2])
```

Output:

```text
n
o
```

An invalid index raises `IndexError`:

```python
name[100]
```

---

## 1.12.8 String Slicing

Slicing extracts part of a string:

```python
text = "production"

print(text[0:4])
```

Output:

```text
prod
```

General form:

```python
string[start:stop:step]
```

The `stop` position is excluded.

Examples:

```python
text = "production"

print(text[:4])
print(text[4:])
print(text[::2])
print(text[::-1])
```

Slicing is valuable for known textual layouts, but it should not replace a proper parser when the external format is structured or variable.

---

## 1.12.9 Concatenation

Strings can be combined with `+`:

```python
service = "payment"
suffix = "-api"

name = service + suffix

print(name)
```

Output:

```text
payment-api
```

Because strings are immutable, repeatedly concatenating many fragments can create intermediate strings.

For collections of fragments, `str.join()` is generally clearer and can avoid unnecessary intermediate construction.

---

## 1.12.10 String Repetition

The `*` operator repeats a string:

```python
separator = "-" * 40

print(separator)
```

This is useful for simple formatting and test data.

Externally controlled repetition counts should be bounded when they could produce unexpectedly large allocations.

---

## 1.12.11 Membership Tests

Use `in` and `not in`:

```python
message = "database connection failed"

if "failed" in message:
    print("failure detected")
```

Membership testing is case-sensitive:

```python
print("ERROR" in "error")
```

Output:

```text
False
```

---

## 1.12.12 String Comparison

Equality comparison is straightforward:

```python
environment = "production"

print(environment == "production")
```

Strings also support lexicographic ordering:

```python
print("api" < "worker")
```

Ordinary string ordering follows Unicode code-point ordering semantics.

It should not be assumed to provide linguistically correct collation for every language or locale.

---

## 1.12.13 Case Conversion and Caseless Matching

Common transformations include:

```python
text = "Python Engineering"

print(text.lower())
print(text.upper())
print(text.title())
print(text.capitalize())
print(text.swapcase())
```

For Unicode-aware caseless matching, `casefold()` is often more appropriate than `lower()`:

```python
left = "Straße"
right = "STRASSE"

print(left.casefold() == right.casefold())
```

Output:

```text
True
```

Case conversion is not universally appropriate.

Do not normalize the case of credentials, cryptographic material, identifiers, or protocol values unless their specification explicitly permits it.

---

## 1.12.14 Removing Surrounding Characters

`strip()` removes characters from both ends:

```python
value = "  production  "

print(value.strip())
```

Output:

```text
production
```

Related methods are:

```python
value.lstrip()
value.rstrip()
```

A critical distinction is that the argument to `strip()` describes characters to remove, not an exact prefix or suffix.

Therefore:

```python
value.strip("abc")
```

does not mean:

```text
remove the exact substring "abc"
```

For exact prefix or suffix removal, use `removeprefix()` or `removesuffix()`.

---

## 1.12.15 Prefix and Suffix Tests

Use:

```python
filename = "application.log"

print(filename.startswith("application"))
print(filename.endswith(".log"))
```

Output:

```text
True
True
```

Tuples are supported:

```python
filename.endswith((".log", ".txt", ".json"))
```

These methods usually communicate intent better than manually slicing fixed positions.

---

## 1.12.16 Exact Prefix and Suffix Removal

Use `removeprefix()`:

```python
resource = "prod-database"

clean = resource.removeprefix("prod-")

print(clean)
```

Output:

```text
database
```

Use `removesuffix()`:

```python
filename = "server.log"

print(filename.removesuffix(".log"))
```

Output:

```text
server
```

If the requested prefix or suffix is absent, the value is returned unchanged.

---

## 1.12.17 Finding Text

`find()` returns the lowest matching index or `-1`:

```python
message = "database timeout"

print(message.find("timeout"))
```

`index()` performs a similar search but raises `ValueError` when the substring is absent.

For a simple existence test, prefer:

```python
"timeout" in message
```

rather than:

```python
message.find("timeout") != -1
```

because the membership expression communicates the intent directly.

---

## 1.12.18 Counting Occurrences

Use `count()`:

```python
message = "error,error,warning,error"

print(message.count("error"))
```

Output:

```text
3
```

`count()` counts non-overlapping occurrences.

Substring counts should not automatically be treated as semantic event counts when the underlying input is structured.

---

## 1.12.19 Replacing Text

Use `replace()` for literal replacement:

```python
message = "environment=dev"

updated = message.replace("dev", "production")

print(updated)
```

Output:

```text
environment=production
```

Literal replacement is not structural editing.

Blind replacement can corrupt:

```text
JSON
YAML
SQL
URLs
configuration files
```

When a format has a parser, parse the structure and modify the intended field.

---

## 1.12.20 Splitting Strings

`split()` has two important operating modes.

When no separator is supplied, runs of whitespace are grouped:

```python
command = "kubectl   get    pods"

print(command.split())
```

Output:

```text
['kubectl', 'get', 'pods']
```

Leading and trailing whitespace does not create empty fields in this mode.

With an explicit separator:

```python
servers = "db01,db02,db03"

print(servers.split(","))
```

Output:

```text
['db01', 'db02', 'db03']
```

Consecutive explicit separators can produce empty fields:

```python
print("db01,,db03".split(","))
```

Output:

```text
['db01', '', 'db03']
```

Therefore:

```text
split()
```

and:

```text
split(separator)
```

have deliberately different parsing semantics.

---

## 1.12.21 Limiting Splits

Use `maxsplit` when the remainder must remain intact:

```python
record = "ERROR:database:connection failed"

level, component, message = record.split(":", 2)
```

This is useful when the final field may contain the delimiter.

It should not replace a parser for standardized structured formats.

---

## 1.12.22 Splitting from the Right

`rsplit()` is useful when the significant separator is near the end:

```python
resource = "customer:service:instance"

prefix, instance = resource.rsplit(":", 1)

print(prefix)
print(instance)
```

Output:

```text
customer:service
instance
```

---

## 1.12.23 Splitting Lines

Use `splitlines()` for line-oriented text:

```python
output = """pod-1 Running
pod-2 Pending
pod-3 Running"""

lines = output.splitlines()

print(lines)
```

This is generally preferable to assuming that all external text uses exactly `"\n"` for line boundaries.

---

## 1.12.24 Joining Strings

`join()` combines strings using a separator:

```python
servers = ["db01", "db02", "db03"]

value = ",".join(servers)

print(value)
```

Output:

```text
db01,db02,db03
```

The separator owns the operation:

```python
",".join(servers)
```

For many fragments, joining is generally preferable to repeated immutable concatenation.

---

## 1.12.25 f-Strings

Formatted string literals provide concise interpolation:

```python
service = "payments"
replicas = 3

message = f"service={service}, replicas={replicas}"

print(message)
```

Output:

```text
service=payments, replicas=3
```

Expressions can appear in replacement fields:

```python
healthy = 4
total = 5

print(f"healthy={healthy}/{total}")
```

f-strings are excellent for controlled presentation and diagnostics.

They are **not** substitutes for context-aware escaping or parameterization.

---

## 1.12.26 Format Specifications

f-strings support format specifications:

```python
latency = 12.34567

print(f"{latency:.2f} ms")
```

Output:

```text
12.35 ms
```

Grouping:

```python
requests = 1_250_000

print(f"{requests:,}")
```

Output:

```text
1,250,000
```

Percentage formatting:

```python
ratio = 0.875

print(f"{ratio:.1%}")
```

Output:

```text
87.5%
```

Formatting changes presentation, not the underlying numeric value.

---

## 1.12.27 `str.format()`

Python also supports:

```python
message = "service={}, status={}".format(
    "payments",
    "healthy",
)
```

Named replacement fields are available:

```python
message = "service={service}, status={status}".format(
    service="payments",
    status="healthy",
)
```

This remains common in existing Python applications.

For straightforward new interpolation, f-strings are often easier to read.

---

## 1.12.28 Percent-Style Formatting and Logging

Existing code may contain:

```python
message = "service=%s status=%s" % (
    "payments",
    "healthy",
)
```

Percent-style formatting remains relevant when maintaining existing applications.

It is especially important not to mechanically replace logging calls such as:

```python
logger.info(
    "service=%s status=%s",
    service,
    status,
)
```

with preformatted strings solely for stylistic reasons.

Logging APIs can use deferred formatting, avoiding unnecessary message construction when the relevant log level is disabled.

---

## 1.12.29 Conversion with `str()`

`str()` creates a textual representation:

```python
port = 5432

text = str(port)

print(text)
print(type(text))
```

Output:

```text
5432
<class 'str'>
```

Once converted to strings:

```python
print(str(10) + str(20))
```

Output:

```text
1020
```

The values now participate in string concatenation rather than numeric addition.

---

## 1.12.30 `str()` Versus `repr()`

`str()` generally targets readable presentation.

`repr()` generally provides a more developer-oriented representation.

```python
value = "prod\napi"

print(str(value))
print(repr(value))
```

The second form exposes the embedded newline:

```text
'prod\napi'
```

This makes:

```python
print(repr(value))
```

particularly useful when diagnosing:

- leading spaces;
- trailing spaces;
- tabs;
- carriage returns;
- newlines;
- escape sequences.

---

## 1.12.31 Escape Sequences

Backslash escape sequences represent special characters:

```python
message = "line1\nline2"
tabbed = "name\tstatus"
quoted = "She said \"ready\""
```

Common sequences include:

| Escape | Meaning |
|---|---|
| `\n` | Newline |
| `\t` | Horizontal tab |
| `\\` | Backslash |
| `\'` | Single quote |
| `\"` | Double quote |
| `\r` | Carriage return |

Invisible characters frequently explain file, protocol, command-output, and cross-platform text problems.

---

## 1.12.32 Raw String Literals

Raw string notation reduces backslash escape processing:

```python
pattern = r"\d+\.\d+"
```

This is useful for regular-expression patterns and some path-like literals.

Raw strings are a source-code literal feature, not a separate runtime string type.

They still have lexical restrictions. For example, a raw string literal cannot end with an odd number of backslashes because of how the closing quote is parsed.

---

## 1.12.33 Unicode Text

Python `str` supports Unicode text:

```python
english = "hello"
spanish = "hola"
japanese = "こんにちは"
emoji = "🚀"
```

Unicode support does not imply that:

- every external system uses the same encoding;
- every visually identical string has the same code-point sequence;
- ordinary ordering implements human-language collation;
- every user-perceived character corresponds to one code point.

Those concerns must be handled according to the application's text model.

---

## 1.12.34 Unicode Code Points

Use `ord()` to obtain the code point represented by a one-character string:

```python
print(ord("A"))
```

Output:

```text
65
```

Use `chr()` for the reverse mapping:

```python
print(chr(65))
```

Output:

```text
A
```

These functions are useful when investigating character-level Unicode behavior.

---

## 1.12.35 Unicode Normalization

Visually equivalent text can sometimes have different Unicode code-point representations.

Python provides normalization through `unicodedata`:

```python
import unicodedata

normalized = unicodedata.normalize(
    "NFC",
    text,
)
```

Normalization can matter for:

- search;
- deduplication;
- identifiers;
- text comparison;
- data integration.

When an application requires both normalization and caseless comparison, the two operations may need to be combined according to the application's comparison policy.

For example:

```python
import unicodedata


def comparison_key(value):
    return unicodedata.normalize(
        "NFC",
        value,
    ).casefold()
```

This is an application policy, not a universal rule.

`casefold()` alone does not guarantee that canonically different Unicode representations become identical.

Likewise, do not normalize text blindly when the original code-point sequence is meaningful.

---

## 1.12.36 Text and Bytes Are Different

Python deliberately separates text from binary data:

```python
text = "database"
binary = b"database"

print(type(text))
print(type(binary))
```

Output:

```text
<class 'str'>
<class 'bytes'>
```

The fundamental boundary is:

```text
          encode
str  ─────────────► bytes
     ◄─────────────
          decode
```

Keeping this boundary explicit is one of the most important rules in production Python text processing.

---

## 1.12.37 Encoding Text

Convert text to bytes with `encode()`:

```python
message = "database ready"

payload = message.encode("utf-8")

print(payload)
```

Output:

```text
b'database ready'
```

UTF-8 is appropriate for many modern interfaces, but the actual encoding must follow the external system's contract.

Do not guess when a protocol, file format, database, or legacy system specifies another encoding.

---

## 1.12.38 Decoding Bytes

Convert bytes to text with `decode()`:

```python
payload = b"database ready"

message = payload.decode("utf-8")

print(message)
```

Output:

```text
database ready
```

If the byte sequence is incompatible with the selected encoding, decoding can raise `UnicodeDecodeError`.

That failure often indicates an incorrect interface assumption or invalid input and should not automatically be suppressed.

---

## 1.12.39 Encoding Error Policies

Encoding and decoding support configurable error handling:

```python
text.encode(
    "ascii",
    errors="strict",
)
```

or:

```python
payload.decode(
    "utf-8",
    errors="replace",
)
```

Policies such as `replace` and `ignore` can alter or discard information.

Production systems should choose deliberately whether invalid input should be:

```text
rejected
repaired
replaced
quarantined
preserved as raw data
```

Encoding errors are frequently data-quality or interface-contract signals.

---

## 1.12.40 Production Example — Environment Variables

Environment variables are textual inputs:

```python
import os

raw_timeout = os.getenv(
    "TIMEOUT_SECONDS",
    "30",
)
```

Conversion and domain validation are separate operations:

```python
try:
    timeout_seconds = int(raw_timeout)
except ValueError as exc:
    raise ValueError(
        "TIMEOUT_SECONDS must be an integer"
    ) from exc

if timeout_seconds <= 0:
    raise ValueError(
        "TIMEOUT_SECONDS must be greater than zero"
    )
```

The boundary is:

```text
external text
     │
     ▼
   parsing
     │
     ▼
typed value
     │
     ▼
domain validation
```

Successful parsing does not prove that a value is acceptable.

## 1.12.41 Production Example — Logging

Parameterized logging remains useful:

```python
logger.info(
    "service=%s environment=%s status=%s",
    service,
    environment,
    status,
)
```

Where the logging platform supports structured fields, structured logging can provide stronger machine-readable semantics.

User-controlled text also deserves attention because newlines and control characters can make plain-text logs misleading or difficult to parse.

Most importantly, never log sensitive values merely because they are strings.

Examples include:

```text
passwords
API keys
access tokens
session tokens
private keys
credential-bearing connection strings
```

## 1.12.42 Production Example — SQL

Do not construct SQL by interpolating untrusted values:

```python
query = (
    f"SELECT * FROM users "
    f"WHERE name = '{username}'"
)
```

This can create SQL-injection vulnerabilities.

Use the database driver's parameterization mechanism.

For a driver using `%s` markers:

```python
cursor.execute(
    "SELECT * FROM users WHERE name = %s",
    (username,),
)
```

Placeholder syntax varies by driver.

The important rule is:

> **SQL values should be supplied through the database driver's parameterization mechanism rather than manually quoted into SQL text.**

String formatting is not SQL parameterization.

---

## 1.12.43 Production Example — Subprocesses

Avoid building shell command strings from untrusted input:

```python
command = f"grep {user_value} application.log"
```

When shell features are unnecessary, prefer an argument sequence:

```python
import subprocess

subprocess.run(
    ["grep", user_value, "application.log"],
    check=True,
)
```

For ordinary direct executable invocation, a useful default is:

```text
shell=False
+
argument sequence
```

This keeps arguments separate from shell syntax when Python is directly executing the target program.

Platform-specific behavior still matters. On Windows, for example, batch files can involve system-shell processing even when Python did not explicitly request `shell=True`.

When launching platform-specific command formats with untrusted input, review the relevant subprocess and operating-system semantics.

Do not enable `shell=True` merely to make command construction easier.

---

## 1.12.44 Production Example — File Paths

Avoid manually joining ordinary filesystem path components with string concatenation:

```python
path = base + "/" + filename
```

Prefer path-aware APIs:

```python
from pathlib import Path

path = Path(base) / filename
```

`pathlib.Path` is a strong default for ordinary filesystem path construction and manipulation.

However, path normalization and platform semantics can matter. `pathlib` is not a universal drop-in replacement for every low-level `os.path`, `str`, or `bytes` path use case.

Treat filesystem paths according to filesystem semantics rather than as arbitrary text.

---

## 1.12.45 Production Example — URLs

URLs are structured data.

Avoid uncontrolled construction such as:

```python
url = base_url + "?q=" + query
```

Dynamic components may contain reserved characters that require URL-specific encoding.

Use URL-aware libraries when parsing, encoding, or assembling dynamic URL components.

The broader rule is:

```text
structured data
      ≠
arbitrary string
```

---

## 1.12.46 Production Example — Delimited Input

For a deliberately simple comma-delimited configuration value:

```python
raw = "db01, db02,db03"

servers = [
    item.strip()
    for item in raw.split(",")
    if item.strip()
]
```

Result:

```text
["db01", "db02", "db03"]
```

This is appropriate only because the input grammar is intentionally simple.

Do not generalize this approach to CSV. CSV can contain quoting, embedded delimiters, embedded newlines, and other syntax that requires a CSV parser.

## 1.12.47 String Classification Methods

Useful predicates include:

```python
value.isalpha()
value.isdigit()
value.isdecimal()
value.isnumeric()
value.isalnum()
value.isspace()
value.islower()
value.isupper()
value.isidentifier()
value.isascii()
```

These methods have defined Unicode-aware semantics.

For example:

```python
value.isdigit()
```

does not mean:

```text
value is a valid application integer
```

If an application requires an integer, parse according to the accepted format and enforce the required domain constraints.

---

## 1.12.48 Application-Specific Validation

Suppose a service name may contain only lowercase ASCII letters, digits, and hyphens.

A domain-specific validator makes that policy explicit:

```python
def valid_service_name(value):
    if not value:
        return False

    allowed = set(
        "abcdefghijklmnopqrstuvwxyz"
        "0123456789-"
    )

    return all(
        char in allowed
        for char in value
    )
```

For more complex grammars, regular expressions or dedicated parsers may be appropriate.

The governing principle is:

> **Validate text according to the application's grammar rather than whichever generic string predicate appears closest.**

---

## 1.12.49 Whitespace Is More Than ASCII Space

Text may contain:

- spaces;
- tabs;
- newlines;
- carriage returns;
- Unicode whitespace characters.

For example:

```python
value = "production\n"
```

is not equal to:

```python
"production"
```

When invisible whitespace is suspected:

```python
print(repr(value))
```

is often the fastest diagnostic.

---

## 1.12.50 Newline Differences

Common line-ending representations include:

```text
\n
\r\n
```

High-level file APIs can often perform appropriate newline handling.

For in-memory line-oriented text:

```python
text.splitlines()
```

is generally preferable to assuming every source uses exactly one newline convention.

Do not globally rewrite line endings unless the data contract requires it.

---

## 1.12.51 Secrets Are Strings Too

Consider:

```python
username = "service-user"
password = "sensitive-value"
```

Both values have the same runtime type:

```text
str
```

but radically different security semantics.

Therefore:

```text
runtime type
      ≠
data sensitivity
```

Avoid exposing secrets through:

- application logs;
- exception messages;
- traces;
- URLs;
- configuration dumps;
- diagnostic output;
- metrics labels;
- audit events.

Security decisions must follow the meaning and sensitivity of the data.

---

## 1.12.52 String Processing and Memory

Because strings are immutable, transformations generally create new string values:

```python
text = (
    text
    .strip()
    .lower()
    .replace("_", "-")
)
```

For ordinary workloads this is often perfectly reasonable.

With extremely large strings or high-frequency processing, repeated intermediate allocations can affect CPU and memory usage.

Optimize only after measurement identifies string processing as a meaningful bottleneck.

## 1.12.53 Common String Mistakes

### Assuming strings are mutable

They are immutable.

### Confusing code-point count with encoded byte count

```python
len(text)
```

and:

```python
len(text.encode("utf-8"))
```

answer different questions.

### Assuming code-point count always equals visible-character count

Some user-perceived characters can involve multiple code points.

### Treating `str` and `bytes` as interchangeable

Encoding boundaries must be explicit.

### Using `strip("prefix")` for exact prefix removal

Use `removeprefix()`.

### Assuming `lower()` is sufficient for every caseless comparison

Unicode-aware applications may require `casefold()` and potentially normalization according to their comparison policy.

### Assuming explicit `split()` separators behave like whitespace splitting

They use different rules.

### Using f-strings for SQL values

Use driver parameterization.

### Building shell commands from untrusted text

Prefer direct execution with argument sequences when a shell is unnecessary.

### Parsing structured data through ad hoc string manipulation

Use an appropriate parser.

### Logging sensitive strings

Sensitivity is semantic, not type-based.

### Assuming visually identical Unicode strings have identical representations

Normalization can matter.

### Ignoring invisible whitespace

Inspect `repr()`.

### Assuming string ordering is locale-aware

Ordinary comparison follows Unicode ordering semantics.

### Assuming every path is ordinary text

Filesystem and platform semantics can matter.

## 1.12.54 Troubleshooting String Problems

A systematic troubleshooting sequence helps avoid guesswork.

### Step 1 — Inspect the Runtime Type

```python
print(type(value))
```

Determine whether the object is:

```text
str
bytes
None
another type
```

### Step 2 — Inspect `repr()`

```python
print(repr(value))
```

This exposes many hidden characters.

### Step 3 — Inspect Length

```python
print(len(value))
```

If encoded size matters:

```python
print(len(value.encode("utf-8")))
```

### Step 4 — Inspect Code Points

```python
for char in value:
    print(char, hex(ord(char)))
```

This can expose unexpected Unicode representations.

### Step 5 — Investigate Normalization

```python
import unicodedata

normalized = unicodedata.normalize(
    "NFC",
    value,
)
```

Apply normalization only when it belongs to the application's comparison or storage policy.

### Step 6 — Trace Encoding Boundaries

Determine:

```text
where bytes entered
        ↓
which encoding was expected
        ↓
where decoding occurred
        ↓
where text was processed
        ↓
where encoding occurred again
```

### Step 7 — Inspect Whitespace

Look for:

```text
spaces
tabs
CR
LF
CRLF
Unicode whitespace
```

### Step 8 — Verify Splitting Rules

Check whether the code uses:

```python
text.split()
```

or:

```python
text.split(separator)
```

because their empty-field and whitespace behavior differs.

### Step 9 — Review Parsing Assumptions

Determine whether a dedicated parser should replace manual string manipulation.

### Step 10 — Review Security Context

Identify whether externally controlled text enters:

```text
SQL
shell commands
URLs
logs
filesystem paths
structured documents
```

Each context has its own safety rules.

## 1.12.55 Production Engineering Rules

1. Use `str` for Unicode text.
2. Remember that strings are immutable.
3. Distinguish code-point count, user-perceived characters, and encoded byte count.
4. Keep `str` and `bytes` boundaries explicit.
5. Specify encodings at external boundaries.
6. Prefer UTF-8 when the interface permits it, but follow the actual data contract.
7. Do not suppress encoding failures without understanding the consequences.
8. Use `repr()` to investigate invisible text.
9. Use `casefold()` when appropriate for Unicode-aware caseless matching.
10. Combine normalization and case folding only when the application's comparison policy requires it.
11. Do not normalize security-sensitive or specification-defined values blindly.
12. Use `removeprefix()` and `removesuffix()` for exact removal.
13. Understand the difference between `split()` and `split(separator)`.
14. Prefer `join()` when combining collections of fragments.
15. Use f-strings for controlled presentation, not context-sensitive escaping.
16. Never use string interpolation as SQL parameterization.
17. Prefer direct subprocess execution with argument sequences when a shell is unnecessary.
18. Review platform-specific subprocess behavior when security depends on exact invocation semantics.
19. Use path-aware APIs for ordinary filesystem operations.
20. Do not assume path abstractions are interchangeable in every low-level use case.
21. Use URL-aware tools for dynamic URL components.
22. Use dedicated parsers for structured formats.
23. Validate text according to the application's grammar.
24. Treat environment variables and other external strings as untrusted input.
25. Protect secrets regardless of their Python type.
26. Do not assume ordinary string ordering provides locale-aware collation.
27. Optimize heavy string processing only after measurement.

## 1.12.60 Key Takeaways

Python strings are:

```text
Unicode text
+
immutable
+
sequence-oriented
```

Production string handling requires several additional distinctions:

```text
code points
      ≠
user-perceived characters
      ≠
encoded bytes
```

Text entering or leaving a system should have explicit boundaries:

```text
external bytes/text
        │
        ▼
 decode / interpret
        │
        ▼
    Python str
        │
        ├── normalize when required
        ├── parse
        ├── validate
        ├── transform
        └── process
        │
        ▼
 encode / serialize
        │
        ▼
external representation
```

The runtime type alone does not describe the rules governing a string.

The same `str` type can represent:

```text
username
password
SQL fragment
URL
filesystem path
JSON document
log message
environment variable
human-language text
```

Each has different parsing, validation, security, normalization, and handling requirements.

A useful production model is:

```text
string correctness
       =
text representation
       +
Unicode semantics
       +
encoding
       +
structure
       +
validation
       +
security context
       +
data sensitivity
```

The central engineering principle is:

> **Treat strings as Unicode text with domain-specific meaning, not as a universal container for every structured, binary, sensitive, or external representation.**
