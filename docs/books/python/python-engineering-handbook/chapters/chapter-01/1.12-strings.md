# Chapter 1 — Python Fundamentals and Development Environment

## 1.12 — Strings

**Edition:** Revised Final / Canonical

**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

- Explain Python's `str` text model.
- Create and manipulate string values safely.
- Understand string immutability, indexing, and slicing.
- Search, split, join, transform, and format strings.
- Distinguish Unicode code points, user-perceived characters, and encoded bytes.
- Apply Unicode case folding and normalization when domain requirements call for them.
- Distinguish `str` from `bytes`.
- Encode and decode text explicitly at system boundaries.
- Validate externally supplied text.
- Avoid unsafe string construction around SQL, subprocesses, paths, URLs, and structured formats.
- Protect sensitive textual data.
- Troubleshoot common Unicode, encoding, whitespace, and parsing problems.

---

## 1.12.1 What Is a Python String?

Python uses the built-in `str` type to represent Unicode text.

```python
service = "payments"
environment = "production"
message = "Database connection established"
```

A Python string is an immutable sequence of Unicode code points. Unlike languages that provide a separate character type, indexing a Python string produces another `str`.

---

## 1.12.2 Creating String Literals

Single and double quotes both create ordinary strings. Choose whichever improves readability and apply a consistent project formatting convention.

---

## 1.12.3 Triple-Quoted Strings

Triple-quoted literals can span multiple physical lines. Newlines and indentation can become part of the resulting value, so inspect multiline text carefully when exact whitespace matters. Triple-quoted strings are also used for docstrings.

---

## 1.12.4 Empty Strings

An empty string contains no code points and is falsy. An empty string and `None` represent different semantic states: `""` means empty text, while `None` represents absence/no value. `None` is covered in Section 1.14.

---

## 1.12.5 Strings Are Immutable

Strings cannot be modified in place. Instead, construct another string and rebind the name. String methods likewise normally produce new strings.

---

## 1.12.6 String Length

For a Python `str`, `len()` returns the number of Unicode code points in the string. This count is not necessarily the number of user-perceived characters and is not the number of bytes required by an encoded representation.

```text
Unicode code-point count
          ≠
user-perceived character count
          ≠
encoded byte count
```

This matters for database limits, protocols, storage constraints, APIs, and text validation.

---

## 1.12.7 String Indexing

Strings support zero-based and negative indexing. An invalid index raises `IndexError`.

---

## 1.12.8 String Slicing

Slicing extracts part of a string using `string[start:stop:step]`; the stop position is excluded. Slicing is valuable for known textual layouts but should not replace a proper parser when an external format is structured or variable.

---

## 1.12.9 Concatenation

Strings can be combined with `+`. Because strings are immutable, repeatedly concatenating many fragments can create intermediate strings. For collections of fragments, `str.join()` is generally clearer and can avoid unnecessary intermediate construction.

---

## 1.12.10 String Repetition

The `*` operator repeats a string. Externally controlled repetition counts should be bounded when they could produce unexpectedly large allocations.

---

## 1.12.11 Membership Tests

Use `in` and `not in` for membership tests. Membership testing is case-sensitive.

---

## 1.12.12 String Comparison

String equality is straightforward. Ordering is lexicographic and follows Unicode code-point ordering semantics; it should not be assumed to provide linguistically correct collation for every language or locale.

---

## 1.12.13 Case Conversion and Caseless Matching

Common transformations include `lower()`, `upper()`, `title()`, `capitalize()`, and `swapcase()`. For Unicode-aware caseless matching, `casefold()` is often more appropriate than `lower()`.

Do not normalize the case of credentials, cryptographic material, identifiers, or protocol values unless their specification explicitly permits it.

---

## 1.12.14 Removing Surrounding Characters

`strip()` removes characters from both ends. Its argument describes characters to remove, not an exact prefix or suffix. For exact removal, use `removeprefix()` or `removesuffix()`.

---

## 1.12.15 Prefix and Suffix Tests

Use `startswith()` and `endswith()`; tuples of alternatives are supported. These methods usually communicate intent better than manually slicing fixed positions.

---

## 1.12.16 Exact Prefix and Suffix Removal

Use `removeprefix()` and `removesuffix()`. If the requested prefix or suffix is absent, the value is returned unchanged.

---

## 1.12.17 Finding Text

`find()` returns the lowest matching index or `-1`; `index()` raises `ValueError` when the substring is absent. For simple existence tests, prefer `sub in text`.

---

## 1.12.18 Counting Occurrences

`count()` counts non-overlapping occurrences. Substring counts should not automatically be treated as semantic event counts when the underlying input is structured.

---

## 1.12.19 Replacing Text

`replace()` performs literal replacement. Literal replacement is not structural editing; parse structured formats and modify the intended field.

---

## 1.12.20 Splitting Strings

`split()` has two important modes. Without a separator, runs of whitespace are grouped and leading/trailing whitespace does not create empty fields. With an explicit separator, consecutive separators can produce empty fields.

---

## 1.12.21 Limiting Splits

Use `maxsplit` when the remainder must remain intact. It should not replace a parser for standardized structured formats.

---

## 1.12.22 Splitting from the Right

`rsplit()` is useful when the significant separator is near the end.

---

## 1.12.23 Splitting Lines

Use `splitlines()` for line-oriented text rather than assuming every source uses exactly `"\n"`.

---

## 1.12.24 Joining Strings

`join()` combines strings using a separator and is generally preferable to repeated immutable concatenation for collections of fragments.

---

## 1.12.25 f-Strings

Formatted string literals provide concise interpolation and are excellent for controlled presentation and diagnostics. They are not substitutes for context-aware escaping or parameterization.

---

## 1.12.26 Format Specifications

f-strings support precision, grouping, percentage, alignment, and other presentation specifications. Formatting changes presentation, not the underlying value.

---

## 1.12.27 `str.format()`

`str.format()` remains common in existing applications. For straightforward new interpolation, f-strings are often easier to read.

---

## 1.12.28 Percent-Style Formatting and Logging

Percent-style formatting remains relevant in existing applications and in logging APIs that support deferred formatting. Do not mechanically replace deferred logging calls with eagerly preformatted strings.

---

## 1.12.29 Conversion with `str()`

`str()` creates a textual representation. Once numeric values are converted to strings, they participate in string operations rather than numeric arithmetic.

---

## 1.12.30 `str()` Versus `repr()`

`str()` generally targets readable presentation, while `repr()` generally provides a more developer-oriented representation. `repr()` is particularly useful for diagnosing hidden whitespace and escape sequences.

---

## 1.12.31 Escape Sequences

Backslash escape sequences represent special characters such as newline, tab, carriage return, quotes, and backslashes. Invisible characters frequently explain file, protocol, command-output, and cross-platform text problems.

---

## 1.12.32 Raw String Literals

Raw string notation reduces backslash escape processing. Raw strings are a source-code literal feature, not a separate runtime type, and retain lexical restrictions such as not ending with an odd number of backslashes.

---

## 1.12.33 Unicode Text

Python `str` supports Unicode text. Unicode support does not imply that every external system uses the same encoding, visually identical strings have identical code-point sequences, ordinary ordering provides human-language collation, or every perceived character is one code point.

---

## 1.12.34 Unicode Code Points

Use `ord()` to obtain a code point from a one-character string and `chr()` for the reverse mapping.

---

## 1.12.35 Unicode Normalization

Visually equivalent text can have different Unicode representations. Python provides normalization through `unicodedata.normalize()`.

When an application requires both normalization and caseless comparison, normalization and `casefold()` may need to be combined according to the application's comparison policy. `casefold()` alone does not make canonically different Unicode representations identical. Do not normalize blindly when the original code-point sequence is meaningful.

---

## 1.12.36 Text and Bytes Are Different

Python deliberately separates text from binary data:

```text
          encode
str  ─────────────► bytes
     ◄─────────────
          decode
```

Keeping this boundary explicit is one of the most important rules in production Python text processing.

---

## 1.12.37 Encoding Text

Convert text to bytes with `encode()`. UTF-8 is appropriate for many modern interfaces, but the actual encoding must follow the external system's contract.

---

## 1.12.38 Decoding Bytes

Convert bytes to text with `decode()`. Incompatible byte sequences can raise `UnicodeDecodeError`; this often indicates an incorrect interface assumption or invalid input and should not automatically be suppressed.

---

## 1.12.39 Encoding Error Policies

Encoding and decoding support configurable error handling. Policies such as `replace` and `ignore` can alter or discard information. Production systems should deliberately decide whether invalid input is rejected, repaired, replaced, quarantined, or preserved as raw data.

---

## 1.12.40 Production Example — Environment Variables

Environment variables are textual inputs. Parsing and domain validation are separate operations. Successful parsing does not prove that a value is acceptable.

---

## 1.12.41 Production Example — Logging

Parameterized logging is useful, and structured fields can provide stronger machine-readable semantics. User-controlled text may contain control characters. Never log sensitive values merely because they are strings.

---

## 1.12.42 Production Example — SQL

Do not construct SQL by interpolating untrusted values. Use the database driver's parameterization mechanism; placeholder syntax varies by driver.

> **SQL values should be supplied through the database driver's parameterization mechanism rather than manually quoted into SQL text.**

String formatting is not SQL parameterization.

---

## 1.12.43 Production Example — Subprocesses

Avoid building shell command strings from untrusted input. When shell features are unnecessary, prefer `shell=False` with an argument sequence. Platform-specific behavior still matters; on Windows, batch files can involve system-shell processing. Review subprocess security guidance when invocation semantics affect safety.

---

## 1.12.44 Production Example — File Paths

Prefer `pathlib.Path` for ordinary filesystem path construction and manipulation. It is not universally a drop-in replacement for every low-level `os.path`, `str`, or `bytes` path use case. Treat filesystem paths according to filesystem semantics rather than as arbitrary text.

---

## 1.12.45 Production Example — URLs

URLs are structured data. Use URL-aware libraries when parsing, encoding, or assembling dynamic components.

```text
structured data
      ≠
arbitrary string
```

---

## 1.12.46 Production Example — Delimited Input

Simple delimiter splitting is appropriate only when the input grammar is deliberately simple. Do not generalize it to CSV, which requires a CSV parser because quoting, embedded delimiters, and embedded newlines are possible.

---

## 1.12.47 String Classification Methods

Useful predicates include `isalpha()`, `isdigit()`, `isdecimal()`, `isnumeric()`, `isalnum()`, `isspace()`, `islower()`, `isupper()`, `isidentifier()`, and `isascii()`. Their Unicode-aware semantics do not automatically equal application validation.

---

## 1.12.48 Application-Specific Validation

Validate text according to the application's grammar rather than whichever generic string predicate appears closest. Use dedicated parsers or regular expressions where appropriate.

---

## 1.12.49 Whitespace Is More Than ASCII Space

Text can contain spaces, tabs, newlines, carriage returns, and Unicode whitespace. When invisible whitespace is suspected, `repr()` is often the fastest diagnostic.

---

## 1.12.50 Newline Differences

Common line endings include `\n` and `\r\n`. High-level file APIs can often perform appropriate newline handling. Do not globally rewrite line endings unless the data contract requires it.

---

## 1.12.51 Secrets Are Strings Too

The runtime type does not describe data sensitivity. Passwords, tokens, keys, credential-bearing connection strings, and other secrets require protection from logs, traces, URLs, configuration dumps, metrics labels, and diagnostics.

---

## 1.12.52 String Processing and Memory

Because strings are immutable, transformations generally create new values. With extremely large strings or high-frequency processing, repeated intermediate allocations can affect CPU and memory. Optimize only after measurement identifies a meaningful bottleneck.

---

## 1.12.53 Common String Mistakes

Common mistakes include assuming strings are mutable; confusing code-point, perceived-character, and byte counts; mixing `str` and `bytes`; using `strip()` for exact prefix removal; assuming `lower()` is sufficient for all caseless comparison; misunderstanding `split()` modes; using f-strings for SQL; constructing shell commands from untrusted input; parsing structured data ad hoc; logging secrets; ignoring Unicode normalization; overlooking invisible whitespace; assuming locale-aware ordering; and treating every path as ordinary text.

---

## 1.12.54 Troubleshooting String Problems

Use a systematic sequence: inspect runtime type, inspect `repr()`, inspect length and encoded size, inspect code points, investigate normalization, trace encoding boundaries, inspect whitespace, verify splitting rules, review parsing assumptions, and review the security context in which external text is used.

---

## 1.12.55 Production Engineering Rules

1. Use `str` for Unicode text.
2. Remember that strings are immutable.
3. Distinguish code-point count, user-perceived characters, and encoded byte count.
4. Keep `str` and `bytes` boundaries explicit.
5. Specify encodings at external boundaries.
6. Prefer UTF-8 when the interface permits it, but follow the actual data contract.
7. Do not suppress encoding failures without understanding the consequences.
8. Use `repr()` to investigate invisible text.
9. Use `casefold()` when appropriate for Unicode-aware caseless matching.
10. Combine normalization and case folding only when the application's comparison policy requires it.
11. Do not normalize security-sensitive or specification-defined values blindly.
12. Use `removeprefix()` and `removesuffix()` for exact removal.
13. Understand the difference between `split()` and `split(separator)`.
14. Prefer `join()` when combining collections of fragments.
15. Use f-strings for controlled presentation, not context-sensitive escaping.
16. Never use string interpolation as SQL parameterization.
17. Prefer direct subprocess execution with argument sequences when a shell is unnecessary.
18. Review platform-specific subprocess behavior when security depends on exact invocation semantics.
19. Use path-aware APIs for ordinary filesystem operations.
20. Do not assume path abstractions are interchangeable in every low-level use case.
21. Use URL-aware tools for dynamic URL components.
22. Use dedicated parsers for structured formats.
23. Validate text according to the application's grammar.
24. Treat environment variables and other external strings as untrusted input.
25. Protect secrets regardless of their Python type.
26. Do not assume ordinary string ordering provides locale-aware collation.
27. Optimize heavy string processing only after measurement.

## 1.12.60 Key Takeaways

Python strings are Unicode text, immutable, and sequence-oriented. Production string handling requires explicit distinctions among code points, user-perceived characters, and encoded bytes. Text entering or leaving a system requires explicit interpretation, validation, normalization where appropriate, parsing, processing, and serialization boundaries.

A useful production model is:

```text
string correctness
       =
text representation
       +
Unicode semantics
       +
encoding
       +
structure
       +
validation
       +
security context
       +
data sensitivity
```

The central engineering principle is:

> **Treat strings as Unicode text with domain-specific meaning, not as a universal container for every structured, binary, sensitive, or external representation.**
