# Chapter 1 --- Python Fundamentals and Development Environment

## 1.13 --- Boolean Values

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   Explain Python's `bool` type and the values `True` and `False`.
-   Distinguish explicit Boolean values from general truth-value
    testing.
-   Identify common truthy and falsy values.
-   Use `bool()` deliberately.
-   Apply `and`, `or`, and `not` correctly.
-   Understand short-circuit evaluation and operand-return behavior.
-   Use comparisons and chained comparisons safely.
-   Explain the relationship between `bool` and `int`.
-   Distinguish `False`, `None`, zero, and empty values when the domain
    requires it.
-   Parse external Boolean configuration safely.
-   Design readable predicates and production guard conditions.
-   Avoid common Boolean and truthiness mistakes.

------------------------------------------------------------------------

## 1.13.1 What Is a Boolean Value?

Python uses the built-in `bool` type to represent two logical values:

``` python
enabled = True
maintenance_mode = False
```

The only Boolean objects are:

``` python
True
False
```

Boolean values are appropriate when the domain itself is genuinely
two-state:

``` text
enabled / disabled
healthy / unhealthy
allowed / denied
matched / not matched
```

A useful engineering principle is:

> **Use Boolean values to represent explicit two-state conditions; do
> not rely on truthiness when the domain requires distinguishing false,
> empty, zero, missing, or invalid states.**

------------------------------------------------------------------------

## 1.13.2 The `bool` Type

Use `type()` when inspecting a Boolean value:

``` python
type(True)
type(False)
```

Both are instances of `bool`:

``` python
isinstance(True, bool)
isinstance(False, bool)
```

Production code rarely needs exact Boolean-type checks unless an interface
specifically requires an actual Boolean rather than a merely truthy or falsy
value. At schema or API boundaries, validate the contract explicitly.

------------------------------------------------------------------------

## 1.13.3 Boolean Literals Are Case-Sensitive

Python's Boolean literals are exactly:

``` python
True
False
```

These are invalid names for Boolean literals:

``` text
true
false
TRUE
FALSE
```

External systems may use different textual conventions. Those strings
must be parsed according to the external interface contract.

------------------------------------------------------------------------

## 1.13.4 Comparisons Produce Boolean Results

For Python's built-in types, comparison expressions normally produce
Boolean values. User-defined rich comparison methods may return
non-Boolean values; when such a result is used in a Boolean context,
Python applies truth-value testing to it.

``` python
cpu_percent > 80
status_code == 200
attempts <= max_attempts
service_name != ""
```

For example:

``` python
status_code = 200
healthy = status_code == 200

print(healthy)
```

Output:

``` text
True
```

This makes comparisons natural building blocks for guards, validation,
filtering, and control flow.

------------------------------------------------------------------------

## 1.13.5 Truth-Value Testing

Python permits objects to participate directly in Boolean contexts:

``` python
if value:
    ...
```

The object does not have to be an instance of `bool`.

Python determines whether the object is truthy or falsy according to its
truth-value semantics.

This distinction is fundamental:

``` text
Boolean object
      ≠
arbitrary object used in a Boolean context
```

------------------------------------------------------------------------

## 1.13.6 Common Falsy Values

Common built-in falsy values include:

``` python
False
None
0
0.0
0j
""
b""
[]
()
{}
set()
range(0)
```

Objects can also define custom truth-value behavior.

Objects are considered truthy unless their type defines falsiness
through `__bool__()` returning `False` or, when `__bool__()` is absent,
through `__len__()` returning zero.

------------------------------------------------------------------------

## 1.13.7 Empty Does Not Mean Missing

Consider:

``` python
value = ""
```

and:

``` python
value = None
```

Both are falsy, but they need not mean the same thing.

A domain may define:

``` text
None  → value was not supplied
""    → value was supplied but is empty
```

Similarly:

``` text
0      → legitimate numeric zero
None   → missing numeric value
False  → explicit negative Boolean state
```

Collapsing these states through generic truthiness can destroy
information.

------------------------------------------------------------------------

## 1.13.8 `bool()` Conversion

The `bool()` constructor converts a value according to Python's standard
truth-value testing rules:

``` python
bool(1)
bool(0)
bool("production")
bool("")
bool([1])
bool([])
bool(None)
```

Typical results:

``` text
True
False
True
False
True
False
False
```

`bool()` does not parse human-readable Boolean text.

------------------------------------------------------------------------

## 1.13.9 The `bool("false")` Trap

A common configuration mistake is:

``` python
enabled = bool("false")
```

The result is:

``` text
True
```

Why?

Because `"false"` is a non-empty string.

The same applies to:

``` python
bool("0")
bool("no")
bool("disabled")
```

All are `True` because they are non-empty strings.

Production configuration must parse accepted Boolean tokens explicitly.

------------------------------------------------------------------------

## 1.13.10 Explicit Boolean Parsing

A small parser can make configuration semantics explicit:

``` python
def parse_bool(value: str) -> bool:
    normalized = value.strip().casefold()

    if normalized in {"true", "1", "yes", "on"}:
        return True

    if normalized in {"false", "0", "no", "off"}:
        return False

    raise ValueError(f"invalid Boolean value: {value!r}")
```

The accepted tokens are a domain decision.

Do not silently accept arbitrary spellings unless the interface specification
requires them. For configuration systems, document the accepted tokens and fail
closed on unrecognized values.

------------------------------------------------------------------------

## 1.13.11 Logical `not`

The `not` operator always produces a Boolean result:

``` python
not True
not False
not ""
not "production"
```

Examples:

``` python
connected = False

if not connected:
    reconnect()
```

Prefer expressions whose meaning remains clear when negated.

------------------------------------------------------------------------

## 1.13.12 Logical `and`

The `and` operator evaluates its left operand first.

If that operand is falsy, Python returns it without evaluating the right
operand. Otherwise, Python evaluates and returns the right operand.

Therefore:

``` python
True and True
```

returns `True`, but `and` does not always return a `bool`.

Example:

``` python
result = "primary" and "ready"
print(result)
```

Output:

``` text
ready
```

------------------------------------------------------------------------

## 1.13.13 Logical `or`

The `or` operator evaluates its left operand first.

If that operand is truthy, Python returns it without evaluating the
right operand. Otherwise, Python evaluates and returns the right
operand.

Example:

``` python
name = configured_name or "default-service"
```

This can be useful, but it also collapses all falsy values.

If an empty string has different meaning from a missing value, use an
explicit test instead.

------------------------------------------------------------------------

## 1.13.14 `and` and `or` Return Operands

This rule deserves explicit attention:

``` text
and / or
    ↓
return selected operands
    ↓
not necessarily bool
```

Examples:

``` python
[] or ["default"]
"ready" and 42
0 or 10
```

This behavior supports concise expressions but can create subtle bugs
when developers assume the result must be `True` or `False`.

Use `bool(expression)` when an actual Boolean result is required.

------------------------------------------------------------------------

## 1.13.15 Short-Circuit Evaluation

`and` and `or` short-circuit.

For `and`, the right side is evaluated only if the left side is truthy:

``` python
if connection is not None and connection.is_ready():
    ...
```

For `or`, the right side is evaluated only if the left side is falsy:

``` python
cached = cache.get(key)
value = cached or load_default()
```

Short-circuiting is useful for guards, but side effects hidden inside
Boolean expressions can reduce readability.

------------------------------------------------------------------------

## 1.13.16 Guarding Potentially Unsafe Operations

Short-circuiting can guard operations that are valid only under certain
conditions:

``` python
if denominator != 0 and numerator / denominator > threshold:
    alert()
```

Another example:

``` python
if user is not None and user.is_active:
    authorize(user)
```

Keep guard expressions readable. Complex validation often deserves named
intermediate predicates.

------------------------------------------------------------------------

## 1.13.17 Operator Precedence

Logical operators have different precedence:

``` text
not
and
or
```

Comparisons bind more tightly than these logical operators.

For example:

``` python
ready and healthy or override
```

may be legal but can be harder to review safely.

Use parentheses when they make intent clearer:

``` python
(ready and healthy) or override
```

Readability is more important than demonstrating knowledge of precedence
rules.

------------------------------------------------------------------------

## 1.13.18 Equality with Boolean Values

Code such as:

``` python
if enabled == True:
    ...
```

is normally unnecessary.

Prefer:

``` python
if enabled:
    ...
```

Similarly:

``` python
if not enabled:
    ...
```

is usually clearer than:

``` python
if enabled == False:
    ...
```

However, explicit equality or identity checks may be appropriate when
the domain must distinguish an actual Boolean from other truthy or falsy
values.

------------------------------------------------------------------------

## 1.13.19 When Explicit Boolean Identity Matters

Suppose an API can return:

``` text
True
False
None
```

Then:

``` python
if result:
    ...
```

cannot distinguish `False` from `None`.

Explicit tests can preserve the states:

``` python
if result is True:
    ...
elif result is False:
    ...
else:
    ...
```

Use this deliberately when the contract genuinely contains multiple
semantic states.

------------------------------------------------------------------------

## 1.13.20 Boolean Values and `None`

`False` and `None` are both falsy, but they are not equivalent:

``` python
False == None
```

is `False`.

Their meanings are usually different:

``` text
False → explicit negative state
None  → absent / unknown / not supplied / no value
```

Section 1.14 covers `None` and null semantics in depth.

------------------------------------------------------------------------

## 1.13.21 Boolean Values and Numeric Zero

Zero is falsy:

``` python
bool(0)
```

but zero may be valid business data.

Consider:

``` python
replica_count = 0
```

This may mean:

``` text
explicitly scale to zero
```

rather than:

``` text
value is missing
```

Avoid:

``` python
if not replica_count:
    replica_count = default_count
```

when zero is a valid configured value.

Prefer an explicit missing-value test:

``` python
if replica_count is None:
    replica_count = default_count
```

------------------------------------------------------------------------

## 1.13.22 Boolean Values and Empty Collections

Empty collections are falsy:

``` python
bool([])
bool({})
bool(set())
```

This is convenient:

``` python
if not errors:
    print("No errors")
```

But an empty collection may differ from missing data:

``` text
[]   → query completed and returned no items
None → query did not run, value unavailable, or not supplied
```

The correct distinction depends on the interface contract.

------------------------------------------------------------------------

## 1.13.23 `bool` Is a Subclass of `int`

In Python:

``` python
isinstance(True, int)
```

is `True`.

Also:

``` python
True == 1
False == 0
```

The Python data model defines `bool` as a subtype of `int`; Boolean values
behave like the integers `0` and `1` in almost all numeric contexts. Production
code should nevertheless preserve their distinct semantic meaning.

A Boolean is usually a condition, not a count.

------------------------------------------------------------------------

## 1.13.24 Arithmetic with Boolean Values

Because of the `bool`/`int` relationship:

``` python
True + True
```

produces:

``` text
2
```

and:

``` python
False + True
```

produces:

``` text
1
```

This can occasionally be useful for counting predicates:

``` python
checks = [
    disk_ok,
    memory_ok,
    network_ok,
]

passed = sum(checks)
```

However, if the values originate outside trusted application logic,
validate their types rather than assuming every numeric `0` or `1` is
semantically Boolean.

------------------------------------------------------------------------

## 1.13.25 Type Validation at API Boundaries

Python equality can blur Boolean and integer values:

``` python
True == 1
False == 0
```

If an API field requires a real Boolean, validate that contract
explicitly.

For example:

``` python
def require_bool(value: object) -> bool:
    if not isinstance(value, bool):
        raise TypeError("expected a Boolean value")
    return value
```

This is different from asking whether a value is truthy.

------------------------------------------------------------------------

## 1.13.26 Comparisons

Common comparison operators include:

``` text
==
!=
<
<=
>
>=
```

Each comparison expresses a predicate:

``` python
healthy = latency_ms < 500
eligible = age >= minimum_age
retry_allowed = attempts < max_attempts
```

Prefer meaningful predicate names when an expression is reused or when
the condition is operationally significant.

------------------------------------------------------------------------

## 1.13.27 Chained Comparisons

Python supports chained comparisons:

``` python
0 <= utilization <= 100
```

This is equivalent in intent to testing both bounds while evaluating the
middle expression according to Python's chained-comparison semantics.

It is often clearer than:

``` python
utilization >= 0 and utilization <= 100
```

Use chained comparisons when they express the domain rule naturally.

------------------------------------------------------------------------

## 1.13.28 Equality Versus Identity

Equality:

``` python
a == b
```

asks whether values compare equal.

Identity:

``` python
a is b
```

asks whether both references identify the same object.

For Boolean logic, use ordinary truth testing when appropriate. Use
`is None` for `None`. Explicit `is True` or `is False` should be
reserved for cases where exact Boolean state matters.

------------------------------------------------------------------------

## 1.13.29 Membership Tests as Predicates

Membership operations produce Boolean results:

``` python
environment in {"prod", "staging"}
role not in denied_roles
```

These often make validation rules clearer than long equality chains:

``` python
if environment == "prod" or environment == "staging":
    ...
```

Prefer a set or other appropriate collection when testing membership in
a known group.

------------------------------------------------------------------------

## 1.13.30 Predicate Functions

A predicate function answers a condition:

``` python
def is_healthy(status_code: int) -> bool:
    return 200 <= status_code < 300
```

Good predicate functions:

-   have clear semantics;
-   return a Boolean deliberately;
-   avoid surprising side effects;
-   are easy to test;
-   encode one meaningful rule.

------------------------------------------------------------------------

## 1.13.31 Predicate Naming

Names often communicate Boolean intent through prefixes such as:

``` text
is_
has_
can_
should_
supports_
requires_
```

Examples:

``` python
is_ready
has_capacity
can_retry
should_rotate
supports_tls
requires_restart
```

Names should describe the condition that `True` represents.

Avoid ambiguous names such as:

``` text
status
flag
value
state
```

when a more precise predicate name is available.

------------------------------------------------------------------------

## 1.13.32 Positive Boolean Names

Positive names are usually easier to reason about:

``` python
is_enabled
```

rather than:

``` python
is_not_disabled
```

Double negatives increase cognitive load:

``` python
if not is_not_ready:
    ...
```

Prefer conditions that remain understandable under `not`.

------------------------------------------------------------------------

## 1.13.33 Boolean Parameters

Functions with Boolean parameters can become difficult to read:

``` python
deploy(True, False)
```

The call site does not explain what the values mean.

Keyword arguments improve clarity:

``` python
deploy(
    dry_run=True,
    wait=False,
)
```

When a parameter represents more than two meaningful modes, an enum or
another explicit type may model the domain better than multiple Boolean
flags.

------------------------------------------------------------------------

## 1.13.34 Multiple Boolean Flags and Invalid States

Suppose a design uses:

``` python
read_only = True
read_write = True
```

If these modes are mutually exclusive, independent Booleans permit
invalid combinations.

A better model may be:

``` text
READ_ONLY
READ_WRITE
DISABLED
```

The design principle is:

> **Do not use several independent Boolean flags when the domain is
> actually one multi-state value.**

------------------------------------------------------------------------

## 1.13.35 Bitwise Operators Are Not Logical Operators

Python also provides bitwise operators:

``` text
&
|
^
~
```

Do not casually substitute them for:

``` text
and
or
not
```

For ordinary application control flow:

``` python
if ready and healthy:
    ...
```

is different in semantics from:

``` python
if ready & healthy:
    ...
```

Bitwise operators do not provide the same short-circuit behavior and can
interact differently with non-Boolean operands and overloaded types.

------------------------------------------------------------------------

## 1.13.36 Custom Truthiness

User-defined classes can participate in truth-value testing through
`__bool__()`.

For example:

``` python
class HealthResult:
    def __init__(self, healthy: bool) -> None:
        self.healthy = healthy

    def __bool__(self) -> bool:
        return self.healthy
```

Then:

``` python
result = HealthResult(True)

if result:
    ...
```

Custom truthiness should be intuitive and unsurprising.

------------------------------------------------------------------------

## 1.13.37 Truthiness Through `__len__()`

If a class does not define `__bool__()`, Python can use `__len__()` for
truth-value testing.

Conceptually:

``` text
length == 0  → falsy
length > 0   → truthy
```

Container-like types commonly use this behavior.

Custom types should not use surprising length semantics merely to
influence Boolean contexts.

------------------------------------------------------------------------

## 1.13.38 Production Example --- Feature Flags

A feature flag is naturally Boolean when it truly has two states:

``` python
if feature_enabled:
    run_new_path()
else:
    run_existing_path()
```

At configuration boundaries, parse and validate the value explicitly.

Do not use:

``` python
feature_enabled = bool(os.getenv("FEATURE_ENABLED"))
```

because any non-empty value, including `"false"`, becomes `True`.

------------------------------------------------------------------------

## 1.13.39 Production Example --- Environment Configuration

A safer environment-variable parser:

``` python
import os


def parse_bool(value: str) -> bool:
    normalized = value.strip().casefold()

    if normalized in {"true", "1", "yes", "on"}:
        return True

    if normalized in {"false", "0", "no", "off"}:
        return False

    raise ValueError(f"invalid Boolean value: {value!r}")


raw = os.getenv("ENABLE_CACHE")

if raw is None:
    enable_cache = False
else:
    enable_cache = parse_bool(raw)
```

This distinguishes:

``` text
missing variable
      from
present valid Boolean text
      from
present invalid text
```

------------------------------------------------------------------------

## 1.13.40 Production Example --- JSON and API Payloads

JSON has native Boolean values:

``` json
{
  "enabled": false
}
```

After JSON parsing, validate the application's schema and domain
contract.

Do not automatically treat these as equivalent:

``` json
false
0
"false"
null
""
```

They represent different JSON values and may carry different application
meanings.

------------------------------------------------------------------------

## 1.13.41 Production Example --- Database Results

Database fields may expose:

``` text
TRUE
FALSE
NULL
```

depending on schema and driver behavior.

Application code should preserve the distinction when `NULL` is
semantically meaningful:

``` python
if value is True:
    ...
elif value is False:
    ...
elif value is None:
    ...
```

Do not collapse nullable Boolean data into a two-state result unless the
application has an explicit rule for doing so.

------------------------------------------------------------------------

## 1.13.42 Production Example --- Health Checks

A health decision can be expressed as a predicate:

``` python
def is_healthy(
    *,
    status_code: int,
    latency_ms: float,
    dependency_ready: bool,
) -> bool:
    return (
        200 <= status_code < 300
        and latency_ms < 500
        and dependency_ready
    )
```

For operational systems, the Boolean decision should often be
accompanied by diagnostic context explaining *why* a check failed.

A Boolean alone may be insufficient for observability. Preserve a stable
reason code or diagnostic message separately when operators need to understand
why the decision was false. Preserve a stable
reason code or diagnostic message separately when operators need to
understand why the decision was false.

------------------------------------------------------------------------

## 1.13.43 Production Example --- Retry Decisions

Retry logic often combines several predicates:

``` python
can_retry = (
    attempts < max_attempts
    and error_is_transient
    and not deadline_exceeded
    and not cancelled
)
```

A named predicate makes the policy easier to inspect than repeating the
full expression in several locations.

Retry policy should still define backoff, jitter, deadlines,
idempotency, and observability separately.

------------------------------------------------------------------------

## 1.13.44 Production Example --- Optional Numeric Configuration

Suppose zero is valid:

``` python
max_workers = 0
```

Avoid:

``` python
workers = max_workers or default_workers
```

because zero is replaced.

If only `None` means "use the default":

``` python
workers = (
    default_workers
    if max_workers is None
    else max_workers
)
```

This preserves domain semantics.

------------------------------------------------------------------------

## 1.13.45 Production Example --- Collections

Suppose a query returns:

``` python
servers = []
```

Then:

``` python
if not servers:
    ...
```

correctly tests whether the collection is empty.

But if the API can also return `None`, determine whether these mean
different things:

``` text
[]   → successful query, no servers
None → unavailable / not queried / missing
```

Do not erase the distinction accidentally.

------------------------------------------------------------------------

## 1.13.46 Boolean Expressions and Side Effects

Avoid Boolean expressions that hide important side effects:

``` python
connected or reconnect()
```

Although legal, this may be less obvious than:

``` python
if not connected:
    reconnect()
```

Short Boolean expressions are valuable when they improve clarity, not
merely when they reduce line count.

------------------------------------------------------------------------

## 1.13.47 Boolean Expressions and Expensive Work

Short-circuiting can avoid unnecessary work:

``` python
if cache_enabled and expensive_cache_lookup(key):
    ...
```

But do not rely on clever ordering alone to hide poorly structured
expensive operations.

When performance matters, measure the actual workload and make execution
policy explicit.

------------------------------------------------------------------------

## 1.13.48 Boolean Expressions and Exceptions

Short-circuit guards can prevent invalid operations:

``` python
if payload is not None and validate(payload):
    ...
```

However, a Boolean expression should not be used to suppress unexpected
exceptions.

Validation failures, unavailable dependencies, malformed input, and
programming errors may require different handling.

------------------------------------------------------------------------

## 1.13.49 Boolean Values in Logging

Prefer logs that expose the semantic condition:

``` python
logger.info(
    "cache configuration",
    extra={
        "cache_enabled": cache_enabled,
        "cache_ready": cache_ready,
    },
)
```

Avoid ambiguous output where a bare Boolean lacks context:

``` text
status=True
```

A field name should explain what `True` means.

Never include secrets merely because they influence a Boolean decision.

------------------------------------------------------------------------

## 1.13.50 Boolean Values in Metrics

Boolean states can sometimes be represented numerically in monitoring
systems:

``` text
1 → true
0 → false
```

The metric name and documentation must define the mapping.

Avoid high-cardinality labels containing arbitrary Boolean-related
context. Prefer a stable metric schema and retain detailed failure
reasons in appropriate diagnostic signals.

------------------------------------------------------------------------

## 1.13.51 Boolean Values in Serialization

When a format has a native Boolean type, use it.

For JSON:

``` json
{"enabled": true}
```

is preferable to:

``` json
{"enabled": "true"}
```

unless the external contract explicitly requires a string.

Preserve type information across system boundaries whenever possible.

------------------------------------------------------------------------

## 1.13.52 Validation Versus Truthiness

Consider:

``` python
if payload.get("enabled"):
    ...
```

This tests truthiness, not schema validity.

It does not prove that the field is a Boolean.

If the contract requires a Boolean:

``` python
value = payload["enabled"]

if not isinstance(value, bool):
    raise TypeError("enabled must be a Boolean")
```

Then use the validated value.

------------------------------------------------------------------------

## 1.13.53 Defaults and Truthiness

This pattern is concise:

``` python
name = supplied_name or default_name
```

It is correct only when every falsy supplied value should trigger the
default.

If only absence should trigger a default:

``` python
name = default_name if supplied_name is None else supplied_name
```

The correct choice depends on domain semantics, not syntax preference.

------------------------------------------------------------------------

## 1.13.54 Tri-State Domains

Some domains naturally contain three states:

``` text
true
false
unknown
```

or:

``` text
enabled
disabled
inherit
```

A plain Boolean cannot represent all three without an additional
convention.

Possible models include:

``` python
bool | None
```

or an enum.

Do not force a multi-state domain into a Boolean if doing so makes state
meaning ambiguous.

`None` and null semantics are covered in Section 1.14.

------------------------------------------------------------------------

## 1.13.55 Common Boolean Mistakes

Common mistakes include:

1.  Assuming `bool("false")` is `False`.
2.  Treating every falsy value as missing.
3.  Replacing valid zero values with defaults.
4.  Collapsing empty collections and unavailable results.
5.  Assuming `and` and `or` always return `bool`.
6.  Using `&` and `|` as substitutes for `and` and `or`.
7.  Writing unnecessary `== True` or `== False` comparisons.
8.  Using `is` for ordinary value equality.
9.  Forgetting that `bool` is a subclass of `int`.
10. Accepting `0` and `1` as API Booleans without checking the contract.
11. Using several flags for a single multi-state domain.
12. Giving Boolean variables ambiguous names.
13. Hiding side effects in short-circuit expressions.
14. Using truthiness instead of schema validation.
15. Serializing native Boolean values as strings without a contract
    requirement.

------------------------------------------------------------------------

## 1.13.56 Troubleshooting Boolean Problems

A systematic troubleshooting sequence is:

1.  Inspect the runtime value.
2.  Inspect the runtime type.
3.  Use `repr()` for textual configuration.
4.  Determine whether the code is testing truthiness or exact type.
5.  Check whether zero or empty values are legitimate.
6.  Check whether `None` has distinct meaning.
7.  Inspect `and`/`or` operand-return behavior.
8.  Confirm short-circuit assumptions.
9.  Review operator precedence.
10. Check for bitwise/logical operator confusion.
11. Inspect external parsing rules.
12. Verify API or serialization schema.
13. Review nullable database fields.
14. Inspect custom `__bool__()` or `__len__()` behavior.
15. Confirm that the domain is actually two-state.

Useful diagnostics:

``` python
print(repr(value))
print(type(value))
print(bool(value))
print(isinstance(value, bool))
```

These answer different questions and should not be treated as
interchangeable.

------------------------------------------------------------------------

## 1.13.57 Production Engineering Rules

1.  Use `bool` for genuine two-state conditions.
2.  Distinguish explicit Boolean values from general truthiness.
3.  Do not use `bool()` to parse Boolean text.
4.  Parse external Boolean tokens explicitly.
5.  Reject invalid Boolean configuration rather than guessing.
6.  Preserve the distinction between `False` and `None` when the domain
    requires it.
7.  Preserve valid numeric zero values.
8.  Preserve meaningful empty collections and strings.
9.  Remember that `and` and `or` return operands.
10. Use `bool()` when an actual Boolean result is required from a
    truthy/falsy expression.
11. Use short-circuit evaluation for clear guards.
12. Avoid hiding important side effects inside Boolean expressions.
13. Prefer readable parentheses when precedence could be misread.
14. Avoid unnecessary `== True` and `== False`.
15. Use `is None` for `None`.
16. Use `is True` or `is False` only when exact Boolean state matters.

### Solution 2 --- Configuration Parser

``` python
def parse_bool(value: str) -> bool:
    normalized = value.strip().casefold()

    true_values = {"true", "yes", "1", "on"}
    false_values = {"false", "no", "0", "off"}

    if normalized in true_values:
        return True

    if normalized in false_values:
        return False

    raise ValueError(f"invalid Boolean value: {value!r}")
```

    *,

    transient_error: bool,

        and transient_error
        and not cancelled

### Solution 10 --- Health Decision

``` python
from dataclasses import dataclass


@dataclass(frozen=True)
class HealthResult:
    healthy: bool
    reasons: tuple[str, ...]


def check_health(
    *,
    status_code: int,
    latency_ms: float,
    dependency_ready: bool,
) -> HealthResult:
    reasons: list[str] = []

    if not 200 <= status_code < 300:
        reasons.append("unexpected status code")

    if latency_ms >= 500:
        reasons.append("latency threshold exceeded")

    if not dependency_ready:
        reasons.append("dependency unavailable")

    return HealthResult(
        healthy=not reasons,
        reasons=tuple(reasons),
    )
```

The Boolean supports a simple decision while the diagnostic data
supports operations and troubleshooting.

## 1.13.62 Key Takeaways

Python's Boolean model is small:

``` text
True
False
```

but Boolean contexts are broader:

``` text
explicit bool
      +
truth-value testing
      +
short-circuit operators
      +
comparisons
      +
domain semantics
```

Production correctness depends on preserving meaning:

``` text
false
   ≠
missing
   ≠
zero
   ≠
empty
   ≠
invalid
```

External boundaries require explicit parsing and validation:

``` text
external value
      │
      ▼
parse
      │
      ▼
validate type/domain
      │
      ▼
Boolean decision
```

The central engineering principle is:

> **Use Boolean values to represent explicit two-state conditions; do
> not rely on truthiness when the domain requires distinguishing false,
> empty, zero, missing, or invalid states.**
