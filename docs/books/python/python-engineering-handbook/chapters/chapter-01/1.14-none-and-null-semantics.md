# Chapter 1 --- Python Fundamentals and Development Environment

## 1.14 --- `None` and Null Semantics

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   Explain what `None` represents in Python and identify its type.
-   Use `is None` and `is not None` correctly.
-   Distinguish absence from `False`, zero, empty strings, and empty
    collections.
-   Design functions and APIs with explicit optional-value semantics.
-   Understand implicit and explicit `None` returns.
-   Use sentinel objects when `None` is a valid domain value.
-   Model optional values with modern type annotations.
-   Translate null-like values safely across JSON, databases,
    configuration, and APIs.
-   Avoid production bugs caused by collapsing missing, empty, false,
    and invalid states.
-   Troubleshoot unexpected `None` values systematically.

> **Central engineering principle:** `None` should represent an
> intentional absence of a value. Do not use generic truth-value testing
> when the domain requires distinguishing absence from valid falsy data.

------------------------------------------------------------------------

### 1.14.1 What Is `None`?

`None` is Python's built-in singleton object for representing the
absence of a value.

``` python
result = None
```

It is commonly used when:

-   a value is not available;
-   an operation intentionally has no result;
-   an optional argument was not supplied;
-   a lookup did not find a value;
-   an external system returned a null value;
-   an application needs an explicit "no value" state.

`None` is a real Python object. It is not an empty string, zero,
`False`, or an undefined variable.

------------------------------------------------------------------------

### 1.14.2 `None` Is a Singleton

`None` is the sole instance of `NoneType` and is used as a singleton value.

``` python
first = None
second = None

print(first is second)
```

Output:

``` text
True
```

This singleton property is why identity tests are the normal way to
check for `None`.

``` python
if value is None:
    ...
```

------------------------------------------------------------------------

### 1.14.3 The Type of `None`

The type of `None` is `NoneType`.

``` python
print(type(None))
```

Output:

``` text
<class 'NoneType'>
```

Modern Python also exposes `NoneType` as `types.NoneType`.

``` python
from types import NoneType

print(isinstance(None, NoneType))
```

For ordinary application code, explicit `NoneType` checks are rarely
necessary. Identity testing is normally clearer.

------------------------------------------------------------------------

### 1.14.4 `None` Is Not the Same as `False`

`None` and `False` are both falsy, but they communicate different
states.

``` python
bool(None)
bool(False)
```

Both evaluate to `False`, but:

``` python
None is False
```

is `False`.

Consider:

``` python
feature_enabled = False
feature_enabled = None
```

These can mean very different things:

-   `False` --- the feature is explicitly disabled;
-   `None` --- the setting is absent, unknown, or not yet resolved.

Production systems should preserve this distinction when it matters.

------------------------------------------------------------------------

### 1.14.5 `None` Is Not Numeric Zero

Zero is a valid numeric value.

``` python
retry_count = 0
```

`None` can represent that no retry count was supplied.

``` python
retry_count = None
```

This is unsafe when zero is valid:

``` python
if not retry_count:
    print("No retry count configured")
```

It collapses `0` and `None`.

Prefer:

``` python
if retry_count is None:
    print("No retry count configured")
```

------------------------------------------------------------------------

### 1.14.6 `None` Is Not an Empty String

An empty string is still a string.

``` python
username = ""
```

`None` represents absence:

``` python
username = None
```

Those states may have different operational meanings:

-   `None` --- field omitted or unknown;
-   `""` --- field supplied but empty.

Do not collapse them unless the application contract explicitly defines
them as equivalent.

------------------------------------------------------------------------

### 1.14.7 `None` Is Not an Empty Collection

An empty collection is a present collection containing no elements.

``` python
servers = []
```

`None` can mean that the collection was never loaded or is unavailable.

``` python
servers = None
```

For example:

``` python
if servers is None:
    load_servers()
elif not servers:
    print("Server list loaded, but it is empty")
```

This preserves two distinct states.

------------------------------------------------------------------------

### 1.14.8 Truthiness Can Hide Null Semantics

Because `None` is falsy, this code may be too broad:

``` python
if not value:
    ...
```

It also matches many valid falsy values, including:

``` python
False
0
0.0
""
[]
{}
set()
```

When the requirement is specifically "value is absent," use:

``` python
if value is None:
    ...
```

------------------------------------------------------------------------

### 1.14.9 Testing with `is None`

The standard form is:

``` python
if value is None:
    ...
```

For the opposite condition:

``` python
if value is not None:
    ...
```

These tests communicate singleton identity directly and avoid invoking
user-defined equality behavior.

------------------------------------------------------------------------

### 1.14.10 Why `== None` Is Discouraged

This works for many ordinary values:

``` python
if value == None:
    ...
```

but it is not the preferred form.

Objects can define custom equality behavior through `__eq__()`.

``` python
class Example:
    def __eq__(self, other):
        print("equality executed")
        return False
```

An equality test can therefore execute application-defined logic.

Identity testing does not ask the object whether it considers itself
equal to `None`.

Prefer:

``` python
value is None
```

This also follows Python style guidance.

------------------------------------------------------------------------

### 1.14.11 `None` in Boolean Contexts

`None` is falsy:

``` python
bool(None)
```

returns:

``` text
False
```

That is useful when broad truth-value semantics are intended.

``` python
if result:
    process(result)
```

But it is not a substitute for explicit absence testing when other falsy
values are valid.

------------------------------------------------------------------------

### 1.14.12 Functions That Return `None`

A function can explicitly return `None`.

``` python
def record_event(event: str) -> None:
    print(event)
    return None
```

More commonly, the explicit return is omitted:

``` python
def record_event(event: str) -> None:
    print(event)
```

If execution reaches the end of a function without executing a `return`
statement, Python returns `None`.

------------------------------------------------------------------------

### 1.14.13 Bare `return`

A bare `return` also returns `None`.

``` python
def validate(value: str) -> None:
    if not value:
        return

    print("valid")
```

The early return exits the function without carrying a separate result
value.

------------------------------------------------------------------------

### 1.14.14 Accidental `None` Returns

Implicit `None` can become a production defect when a function was
expected to return a value on every path.

``` python
def get_region(environment: str):
    if environment == "prod":
        return "us-east-1"
```

For another environment:

``` python
region = get_region("staging")
```

`region` becomes `None`.

A downstream failure may occur much later.

``` python
region.upper()
```

Possible result:

``` text
AttributeError: 'NoneType' object has no attribute 'upper'
```

Make return behavior explicit.

``` python
def get_region(environment: str) -> str:
    if environment == "prod":
        return "us-east-1"

    raise ValueError(f"Unsupported environment: {environment}")
```

------------------------------------------------------------------------

### 1.14.15 Optional Function Results

Sometimes absence is part of the function contract.

``` python
def find_owner(service: str) -> str | None:
    owners = {
        "api": "platform",
        "database": "dbre",
    }

    return owners.get(service)
```

Callers should handle both states deliberately.

``` python
owner = find_owner("cache")

if owner is None:
    print("Owner not found")
else:
    print(owner)
```

------------------------------------------------------------------------

### 1.14.16 Optional Type Annotations

Modern Python can express an optional value using a union with `None`.

``` python
def lookup_port(service: str) -> int | None:
    ...
```

This communicates that the function may return either:

-   an `int`;
-   `None`.

For older typing styles, the equivalent form is:

``` python
from typing import Optional

def lookup_port(service: str) -> Optional[int]:
    ...
```

For a Python 3.14-targeted codebase, `T | None` is generally concise and
clear.

------------------------------------------------------------------------

### 1.14.17 Type Hints Do Not Enforce Runtime Values

This annotation:

``` python
def lookup_port(service: str) -> int | None:
    ...
```

does not itself enforce the return type at runtime.

Type hints support:

-   static analysis;
-   IDE assistance;
-   code review;
-   documentation;
-   automated tooling.

Runtime validation requires separate logic when necessary.

------------------------------------------------------------------------

### 1.14.18 Optional Parameters

A parameter can intentionally accept `None`.

``` python
def connect(timeout: float | None = None) -> None:
    ...
```

The API must define what `None` means.

For example:

-   use the client default;
-   wait indefinitely;
-   inherit a parent configuration;
-   disable a timeout.

Ambiguous `None` semantics make APIs difficult to operate safely.

------------------------------------------------------------------------

### 1.14.19 `None` as a Default Argument

`None` is commonly used as a safe default when the function needs to
create a mutable object.

``` python
def collect(values: list[str] | None = None) -> list[str]:
    if values is None:
        values = []

    values.append("event")
    return values
```

This avoids sharing one mutable default across calls.

------------------------------------------------------------------------

### 1.14.20 Why Mutable Defaults Are Different

Avoid:

``` python
def collect(values=[]):
    values.append("event")
    return values
```

The default list is created once when the function definition is
executed, so calls that use the default can share state.

Prefer:

``` python
def collect(values: list[str] | None = None) -> list[str]:
    if values is None:
        values = []

    values.append("event")
    return values
```

Here `None` acts as a signal to allocate a new list for that call.

------------------------------------------------------------------------

### 1.14.21 When `None` Is a Valid Input

Using `None` as a default sentinel is not sufficient when `None` itself
is a meaningful value.

Suppose an update API supports:

``` python
set_value(None)
```

to explicitly clear a stored value.

The function must distinguish:

1.  argument omitted;
2.  argument supplied as `None`.

A dedicated sentinel is appropriate.

------------------------------------------------------------------------

### 1.14.22 Sentinel Objects

A unique sentinel object can represent "not supplied."

``` python
_MISSING = object()

def update_setting(value=_MISSING):
    if value is _MISSING:
        print("No update requested")
    elif value is None:
        print("Explicitly clear setting")
    else:
        print(f"Set value to {value}")
```

This creates three distinct states without overloading `None`.

------------------------------------------------------------------------

### 1.14.23 Sentinel Identity

Sentinels should normally be tested by identity.

``` python
if value is _MISSING:
    ...
```

A freshly created object is unique by identity, which makes it suitable
for an internal sentinel.

Keep private sentinels private unless they are intentionally part of a
public API. For public APIs, define and document sentinel behavior deliberately
rather than exposing an incidental module-private implementation detail.

------------------------------------------------------------------------

### 1.14.24 Choosing Between `None` and a Sentinel

Use `None` when:

-   absence is a legitimate state;
-   `None` is not otherwise a valid supplied value;
-   the meaning is clear in the API contract.

Use a dedicated sentinel when:

-   `None` is valid data;
-   omitted and explicitly-null inputs must differ;
-   a defaulting operation must distinguish "not provided" from
    "provided as null."

------------------------------------------------------------------------

### 1.14.25 Missing, Null, Empty, and Invalid

Production systems frequently need at least four distinct states.

  State     Example              Meaning
  --------- -------------------- ---------------------------
  Missing   field not supplied   no input
  Null      `None`               explicit absence
  Empty     `""`, `[]`           supplied but empty
  Invalid   malformed value      supplied but unacceptable

These states should not be collapsed automatically.

For example, an API patch operation may interpret them differently:

-   missing field --- leave existing value unchanged;
-   null field --- clear existing value;
-   empty string --- set value to empty;
-   invalid value --- reject request.

------------------------------------------------------------------------

### 1.14.26 Tri-State Semantics

A Boolean domain can sometimes require three states:

``` python
enabled: bool | None
```

Possible meanings:

``` text
True  -> explicitly enabled
False -> explicitly disabled
None  -> unspecified / inherit
```

This is useful for inherited configuration, but the semantics must be
documented.

If the domain grows beyond a small, stable set of states, an enumeration
or richer model may be clearer.

------------------------------------------------------------------------

### 1.14.27 Defaulting with `or`

This pattern is concise:

``` python
timeout = supplied_timeout or 30
```

but it uses truthiness, not null semantics.

If `0` is valid:

``` python
supplied_timeout = 0
timeout = supplied_timeout or 30
```

`timeout` becomes `30`.

If only `None` means "use the default," write that rule explicitly:

``` python
timeout = 30 if supplied_timeout is None else supplied_timeout
```

------------------------------------------------------------------------

### 1.14.28 Null-Coalescing Logic in Python

Python does not use a dedicated null-coalescing operator for ordinary
expressions.

A conditional expression is explicit:

``` python
effective_timeout = (
    default_timeout
    if configured_timeout is None
    else configured_timeout
)
```

This differs from:

``` python
effective_timeout = configured_timeout or default_timeout
```

because the latter also replaces valid falsy values.

------------------------------------------------------------------------

### 1.14.29 `dict.get()` and `None`

A dictionary lookup using `get()` returns `None` by default when the key
is absent.

``` python
config = {"region": "us-east-1"}

value = config.get("timeout")
```

`value` is `None`.

But this becomes ambiguous if the dictionary explicitly stores `None`.

``` python
config = {"timeout": None}
```

Both cases produce:

``` python
config.get("timeout") is None
```

If the distinction matters, test membership.

``` python
if "timeout" not in config:
    print("missing")
elif config["timeout"] is None:
    print("explicitly null")
```

------------------------------------------------------------------------

### 1.14.30 `dict.get()` with a Sentinel

A sentinel can distinguish an absent key from a key mapped to `None`.

``` python
_MISSING = object()

value = config.get("timeout", _MISSING)

if value is _MISSING:
    print("missing")
elif value is None:
    print("explicitly null")
```

This pattern is especially useful in patch/update logic.

------------------------------------------------------------------------

### 1.14.31 `None` in JSON

Python's standard `json` module maps JSON `null` to Python `None`.

``` python
import json

payload = json.loads('{"timeout": null}')

print(payload["timeout"] is None)
```

When encoding:

``` python
json.dumps({"timeout": None})
```

the corresponding JSON value is `null`.

Remember that a missing JSON property and a property explicitly set to
`null` are structurally different inputs.

------------------------------------------------------------------------

### 1.14.32 JSON Missing Versus `null`

Consider:

``` json
{}
```

and:

``` json
{
  "timeout": null
}
```

After parsing, code should preserve the distinction when the API
contract requires it.

``` python
if "timeout" not in payload:
    print("not supplied")
elif payload["timeout"] is None:
    print("explicit null")
```

This distinction is critical in PATCH-style APIs and configuration
updates.

------------------------------------------------------------------------

### 1.14.33 `None` and Database `NULL`

Many Python database drivers represent SQL `NULL` as Python `None` when
reading nullable values and accept `None` when binding a SQL null parameter.

Conceptually:

``` text
SQL NULL <-> Python None
```

The exact conversion and binding behavior is driver- and API-specific and
should be verified against the database adapter in use.

Application code should not confuse SQL `NULL` with:

-   numeric zero;
-   empty text;
-   `False`;
-   an absent application field.

------------------------------------------------------------------------

### 1.14.34 SQL `NULL` Semantics Are Not Python `None` Semantics

Python and SQL use different evaluation models.

In Python:

``` python
value is None
```

tests identity.

In SQL, null checks use:

``` sql
column_name IS NULL
```

not:

``` sql
column_name = NULL
```

Do not transfer Python comparison assumptions directly into SQL.

Use parameterized SQL rather than constructing SQL text manually.

------------------------------------------------------------------------

### 1.14.35 Production Example --- Database Query Result

Suppose a nullable database column stores a maintenance-window duration.

``` python
duration = row["maintenance_minutes"]

if duration is None:
    use_default_window()
elif duration == 0:
    disable_maintenance_window()
else:
    schedule_window(duration)
```

Here:

-   `None` means no explicit duration;
-   `0` has a separate business meaning;
-   positive values specify a duration.

Truthiness would incorrectly merge the first two states.

------------------------------------------------------------------------

### 1.14.36 Production Example --- Configuration Inheritance

Consider a child service that can inherit a timeout.

``` python
def effective_timeout(
    child_timeout: int | None,
    parent_timeout: int,
) -> int:
    if child_timeout is None:
        return parent_timeout

    return child_timeout
```

Now `0` can remain meaningful if the contract permits it.

------------------------------------------------------------------------

### 1.14.37 Production Example --- Feature Configuration

A tri-state feature setting can represent inheritance.

``` python
def resolve_feature(
    local: bool | None,
    inherited: bool,
) -> bool:
    if local is None:
        return inherited

    return local
```

This preserves:

-   `True`;
-   `False`;
-   unspecified.

------------------------------------------------------------------------

### 1.14.38 Production Example --- PATCH Semantics

Suppose an API accepts:

``` json
{
  "description": null
}
```

The contract might define:

-   field missing --- leave description unchanged;
-   field `null` --- clear description;
-   field string --- replace description.

Python code can preserve the distinction:

``` python
_MISSING = object()

description = payload.get("description", _MISSING)

if description is _MISSING:
    pass
elif description is None:
    clear_description()
else:
    update_description(description)
```

------------------------------------------------------------------------

### 1.14.39 Production Example --- Environment Variables

Environment variables are text when present.

``` python
import os

raw_timeout = os.getenv("APP_TIMEOUT")
```

`os.getenv()` returns its `default` argument when the variable is absent.
Because that default is `None` unless supplied explicitly, an ordinary
`os.getenv("NAME")` call returns `None` for an absent variable.

``` python
if raw_timeout is None:
    timeout = 30
else:
    timeout = int(raw_timeout)
```

An empty environment variable is different:

``` text
APP_TIMEOUT=
```

In that case, `raw_timeout` is an empty string, not `None`.

The application should decide whether empty text is valid, invalid, or
equivalent to absence.

------------------------------------------------------------------------

### 1.14.40 Production Example --- CLI Inputs

Command-line parsers may use `None` to represent an option that was not
supplied, depending on parser configuration.

Application code should define whether:

-   omitted option;
-   empty argument;
-   explicit false value;
-   explicit zero;

have different meanings.

Do not use truthiness when those states must remain distinct.

------------------------------------------------------------------------

### 1.14.41 Production Example --- Cache Lookups

A cache lookup returning `None` can be ambiguous if `None` is itself a
valid cached value.

Unsafe contract:

``` python
value = cache.get(key)

if value is None:
    load_from_database()
```

If cached `None` is meaningful, the code cannot distinguish a cache miss
from a cached null value.

Use an API with an explicit hit/miss signal or a sentinel.

``` python
_MISSING = object()
value = cache.get(key, _MISSING)

if value is _MISSING:
    value = load_from_database()
```

------------------------------------------------------------------------

### 1.14.42 Production Example --- Kubernetes and Cloud Configuration

Infrastructure automation frequently consumes optional configuration.

``` python
replicas: int | None
```

The application might define:

-   `None` --- use platform default;
-   `0` --- intentionally scale to zero;
-   positive integer --- requested replica count.

This is a classic case where:

``` python
if not replicas:
```

is unsafe.

Prefer:

``` python
if replicas is None:
    ...
```

and validate numeric constraints separately.

------------------------------------------------------------------------

### 1.14.43 Production Example --- Retry Configuration

Consider:

``` python
max_retries: int | None
```

Possible contract:

-   `None` --- use global default;
-   `0` --- do not retry;
-   positive integer --- retry up to that count.

Resolution should preserve zero.

``` python
effective_retries = (
    global_retries
    if max_retries is None
    else max_retries
)
```

------------------------------------------------------------------------

### 1.14.44 Production Example --- Optional Timestamps

An optional timestamp might represent an event that has not happened.

``` python
from datetime import datetime

completed_at: datetime | None = None
```

Check explicitly:

``` python
if completed_at is None:
    print("not completed")
```

Do not replace a meaningful domain state with a fabricated timestamp
merely to avoid handling `None`.

------------------------------------------------------------------------

### 1.14.45 Production Example --- Optional Error Information

A result may contain optional diagnostic data.

``` python
def report(error: str | None) -> None:
    if error is None:
        print("No error recorded")
    else:
        print(error)
```

If an empty string is invalid diagnostic data, validate that separately
rather than treating it automatically as `None`.

------------------------------------------------------------------------

### 1.14.46 API Boundary Validation

External inputs need explicit validation.

Suppose a field permits:

``` text
integer or null
```

Do not accept every falsy value as null.

``` python
def validate_limit(value: object) -> int | None:
    if value is None:
        return None

    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("limit must be an integer or None")

    if value < 0:
        raise ValueError("limit must be non-negative")

    return value
```

The explicit Boolean rejection matters because `bool` is a subtype of
`int`.

------------------------------------------------------------------------

### 1.14.47 Normalize at Boundaries

If an external protocol uses another null marker, normalize it
deliberately at the boundary.

For example, a legacy input might use:

``` text
N/A
```

Do not scatter special-case handling throughout business logic.

``` python
def parse_optional_text(raw: str) -> str | None:
    if raw == "N/A":
        return None

    return raw
```

Only perform this conversion if the external contract explicitly defines
that marker as absence.

------------------------------------------------------------------------

### 1.14.48 Do Not Invent Null Equivalence

It is tempting to normalize all of these to `None`:

``` text
""
"null"
"NULL"
"N/A"
"-"
0
False
```

That is unsafe unless the interface specification explicitly defines
them as equivalent.

Different systems use these values differently.

Production normalization should be contract-driven. Perform it once at the owning
boundary where possible, then pass a well-defined internal representation downstream.

------------------------------------------------------------------------

### 1.14.49 `None` and Serialization

Serialization formats differ in how they represent absence.

For example:

-   JSON has `null`;
-   SQL has `NULL`;
-   environment variables may represent absence by the variable not
    existing;
-   command-line interfaces may represent absence by an omitted option.

Do not assume every external null representation has identical
semantics.

Translate at boundaries according to the protocol contract.

------------------------------------------------------------------------

### 1.14.50 Omitting Versus Serializing `None`

An API client may need to distinguish:

``` python
{"description": None}
```

from:

``` python
{}
```

The first may serialize as:

``` json
{"description": null}
```

The second omits the property entirely.

For update APIs, those requests may produce different outcomes.

Serialization code should preserve the intended operation.

------------------------------------------------------------------------

### 1.14.51 `None` in Data Models

A field typed as optional should have documented semantics.

Weak model:

``` python
owner: str | None
```

without explaining what `None` means.

Better contract:

``` text
owner = None
means the service currently has no assigned owner.
```

The type describes allowed values; documentation describes their
meaning.

------------------------------------------------------------------------

### 1.14.52 Nullability Is a Domain Decision

Do not make every field nullable simply because `None` is convenient.

Ask:

-   Can the value legitimately be absent?
-   Is absence temporary or permanent?
-   Does missing differ from explicit null?
-   Should the operation fail instead?
-   Is a richer state model more accurate?

Excessive nullability pushes complexity into every consumer.

------------------------------------------------------------------------

### 1.14.53 Fail Fast Versus Return `None`

Returning `None` is appropriate when absence is an expected outcome.

Example:

``` python
def find_service(name: str) -> Service | None:
    ...
```

Raising an exception may be more appropriate when absence indicates a
violated invariant.

Example:

``` python
def require_service(name: str) -> Service:
    service = find_service(name)

    if service is None:
        raise LookupError(f"Required service not found: {name}")

    return service
```

Choose the contract intentionally.

------------------------------------------------------------------------

### 1.14.54 Avoid Long Chains of Optional Values

Code that repeatedly propagates `None` can become difficult to reason
about.

``` python
service = find_service(name)

if service is None:
    return None

owner = find_owner(service)

if owner is None:
    return None
```

Sometimes this is correct. But if the values are required for the
operation, validate them near the boundary and fail with useful context.

Do not let unexpected `None` values travel deep into the system.

------------------------------------------------------------------------

### 1.14.55 Assertions Are Not Input Validation

Avoid relying on:

``` python
assert value is not None
```

for validation of untrusted or operational input.

Assertions are intended for debugging/internal invariant checks rather than
required input validation. In optimized execution (`-O`), `assert` statements
are removed, so correctness must not depend on them.

Use explicit validation for required runtime behavior.

``` python
if value is None:
    raise ValueError("value is required")
```

------------------------------------------------------------------------

### 1.14.56 Narrowing Optional Values

Explicit checks also help static type analysis.

``` python
name: str | None = get_name()

if name is None:
    raise ValueError("name is required")

print(name.upper())
```

After the check, a type checker can often treat `name` as `str` on the
remaining path.

------------------------------------------------------------------------

### 1.14.57 `None` and Object Attributes

An attribute initialized to `None` often represents lifecycle state.

``` python
class ConnectionManager:
    def __init__(self) -> None:
        self.connection = None
```

The design should define:

-   when the attribute becomes non-`None`;
-   whether it can return to `None`;
-   what operations are legal in each state.

If lifecycle states become complex, an explicit state model may be
better than several nullable attributes.

------------------------------------------------------------------------

### 1.14.58 `None` and Dataclasses

Optional dataclass fields should communicate real domain optionality.

``` python
from dataclasses import dataclass
from datetime import datetime

@dataclass
class Job:
    name: str
    completed_at: datetime | None = None
```

Here `None` can naturally mean that the job has not completed.

Avoid nullable fields when the object should never be valid without the
value.

------------------------------------------------------------------------

### 1.14.59 `None` and Function Side Effects

Functions whose purpose is a side effect commonly return `None`.

``` python
def write_audit_record(message: str) -> None:
    print(message)
```

Callers should not invent success semantics from that return value.

Unsafe:

``` python
if write_audit_record("started"):
    print("success")
```

A `None` return says nothing about success beyond the function's
documented exception behavior.

If the caller needs a result, design one explicitly.

------------------------------------------------------------------------

### 1.14.60 Fluent APIs and In-Place Operations

Some Python operations mutate an object and return `None` rather than
returning the mutated object.

For example:

``` python
values = [3, 1, 2]
result = values.sort()
```

Afterward:

``` python
values
```

is sorted, while:

``` python
result is None
```

is `True`.

Do not assume every mutating operation returns the object for chaining.

------------------------------------------------------------------------

### 1.14.61 Common `None` Mistake --- Assigning an In-Place Result

Incorrect:

``` python
values = [3, 1, 2]
values = values.sort()
```

Now `values` is `None`.

Correct:

``` python
values = [3, 1, 2]
values.sort()
```

Or create a new sorted list:

``` python
values = sorted(values)
```

------------------------------------------------------------------------

### 1.14.62 Common `None` Mistake --- Missing Return

Incorrect:

``` python
def build_url(host: str):
    url = f"https://{host}"
```

The function returns `None`.

Correct:

``` python
def build_url(host: str) -> str:
    url = f"https://{host}"
    return url
```

------------------------------------------------------------------------

### 1.14.63 Common `None` Mistake --- Truthiness Collapse

Unsafe:

``` python
if not port:
    port = 443
```

If `0` has a defined meaning, it is overwritten.

Safer null-specific logic:

``` python
if port is None:
    port = 443
```

Then validate whether zero is permitted separately.

------------------------------------------------------------------------

### 1.14.64 Common `None` Mistake --- Dereferencing Too Early

Unsafe:

``` python
owner = find_owner(service)
print(owner.upper())
```

If `find_owner()` can return `None`, the caller must handle that
contract.

``` python
owner = find_owner(service)

if owner is None:
    raise LookupError("owner not found")

print(owner.upper())
```

------------------------------------------------------------------------

### 1.14.65 Common `None` Mistake --- Hiding Errors with Defaults

This may hide a configuration defect:

``` python
region = config.get("region") or "us-east-1"
```

It silently treats:

-   missing;
-   `None`;
-   empty string;

as the same state.

If empty region names are invalid:

``` python
if "region" not in config:
    region = "us-east-1"
else:
    region = config["region"]

    if region is None or region == "":
        raise ValueError("region must be a non-empty string")
```

Defaults should not conceal invalid supplied values.

------------------------------------------------------------------------

### 1.14.66 Common `None` Mistake --- Excessive Optionality

A function returning `None` for every failure can destroy diagnostic
information.

Weak:

``` python
def load_config(path: str) -> dict | None:
    try:
        ...
    except Exception:
        return None
```

Now callers cannot distinguish:

-   file missing;
-   permission denied;
-   malformed content;
-   programming error.

Use exceptions, structured results, or narrower failure handling when
diagnostic distinctions matter.

------------------------------------------------------------------------

### 1.14.67 Troubleshooting Unexpected `None`

When a `NoneType` error appears, locate where the value became `None`.

Example:

``` text
AttributeError: 'NoneType' object has no attribute '...'
```

Investigate systematically:

1.  identify the variable that is `None`;
2.  inspect its assignment path;
3.  inspect the function's documented return contract;
4.  check for missing `return` statements;
5.  check dictionary `.get()` calls;
6.  check optional database columns;
7.  check JSON `null`;
8.  check missing environment variables;
9.  check in-place methods whose return value was assigned;
10. check broad exception handlers that return `None`;
11. determine whether `None` is expected or indicates a defect.

Fix the source or contract rather than adding arbitrary `None` checks
downstream.

------------------------------------------------------------------------

### 1.14.68 Logging Optional Values

Logs should preserve the difference between absence and empty data when
operationally important.

For example:

``` python
logger.info(
    "resolved service configuration",
    extra={
        "timeout": timeout,
        "owner": owner,
    },
)
```

Avoid converting all absent values into ambiguous strings such as
`"N/A"` before structured logging unless the logging schema explicitly
requires it.

Structured null values are often easier to query consistently. When absence affects
an operational decision, preserve a stable reason/status field as well so operators can
distinguish expected absence from lookup failure, invalid input, or unresolved state.

------------------------------------------------------------------------

### 1.14.69 Metrics and `None`

Metric systems generally require concrete numeric or categorical values
rather than Python objects.

Do not send `None` blindly to a metrics backend.

Instead define the telemetry model.

For example:

``` text
configuration_present{field="timeout"} 0
```

or omit a measurement according to the monitoring contract.

Avoid high-cardinality labels that encode arbitrary missing-value
context.

------------------------------------------------------------------------

### 1.14.70 Production Engineering Rules

1.  Use `None` for intentional absence, not as a generic error bucket.
2.  Test specifically with `is None` and `is not None`.
3.  Do not use truthiness when zero, `False`, empty text, or empty
    collections are valid.
4.  Document what `None` means in public interfaces.
5.  Use `T | None` when absence is part of a typed contract.
6.  Remember that type hints do not enforce runtime values.
7.  Use `None` defaults to avoid shared mutable defaults when `None` is
    not valid input.
8.  Use a dedicated sentinel when omitted and explicitly `None` must
    differ.
9.  Preserve missing, null, empty, and invalid as separate states when
    the domain requires it.
10. Normalize external null markers at system boundaries.
11. Do not invent null equivalence without a protocol or business rule.
12. Preserve missing versus JSON `null` in update APIs.
13. Treat SQL `NULL` according to SQL semantics, not Python equality
    semantics.
14. Do not let unexpected `None` values propagate deep into the
    application.
15. Do not use assertions as required production input validation.
16. Avoid assigning the return value of in-place methods that
    intentionally return `None`.
17. Make optional return behavior explicit.
18. Fail with useful context when absence violates an invariant.
19. Preserve diagnostic information instead of converting every failure
    to `None`.
20. Validate nullable configuration independently from defaulting logic.

### 1.14.75 Key Takeaways

-   `None` is Python's singleton object for representing absence.
-   The type of `None` is `NoneType`.
-   Test for `None` with identity: `is None` and `is not None`.
-   `None`, `False`, zero, empty strings, and empty collections are not
    semantically interchangeable.
-   Truthiness is broader than null testing.
-   Functions without a returned value produce `None`.
-   Optional return values should be part of an explicit function
    contract.
-   `T | None` expresses optionality to readers and static tooling.
-   `None` is a useful mutable-default sentinel only when `None` is not
    itself meaningful input.
-   Dedicated sentinel objects distinguish omitted arguments from
    explicit `None`.
-   Missing, null, empty, and invalid are often separate production
    states.
-   JSON `null`, SQL `NULL`, omitted configuration, and Python `None`
    require deliberate boundary translation.
-   Defaults should not silently overwrite valid falsy values.
-   Unexpected `None` should be traced to its source rather than patched
    repeatedly downstream.
-   Nullability is a domain-model decision, not merely a coding
    convenience.

> **Central engineering principle:** `None` should represent an
> intentional absence of a value. Preserve that meaning across function
> contracts, configuration, APIs, databases, serialization, and
> operational tooling.
