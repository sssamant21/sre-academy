# Chapter 1 --- Python Fundamentals and Development Environment

## 1.15 --- Operators and Expressions

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   Distinguish operators, operands, expressions, and statements.
-   Use Python's arithmetic, comparison, logical, identity, membership,
    bitwise, and assignment operators correctly.
-   Explain operator precedence, associativity, and evaluation order.
-   Use parentheses to make production expressions easier to reason
    about.
-   Understand short-circuit evaluation and operand-return behavior.
-   Apply chained comparisons without duplicating evaluation.
-   Distinguish equality from identity.
-   Recognize operator overloading and reflected operations.
-   Understand assignment expressions and augmented assignment.
-   Identify common numeric, collection, Boolean, and null-related
    operator traps.
-   Design expressions that are explicit, testable, and operationally
    safe.

> **Central engineering principle:** An expression should communicate
> the intended computation and decision rules clearly. Correct
> precedence is necessary, but production code should not force readers
> to reconstruct complex precedence, coercion, side effects, or
> overloaded behavior mentally.

------------------------------------------------------------------------

### 1.15.1 Operators, Operands, and Expressions

An **operator** describes an operation.

``` python
+
```

An **operand** is a value on which an operator acts.

``` python
10 + 5
```

Here:

-   `+` is the operator;
-   `10` and `5` are operands;
-   `10 + 5` is an expression.

An **expression** is syntax that evaluates to a value.

``` python
total + tax
```

Expressions can contain literals, names, function calls, attribute
access, indexing, comprehensions, and operators.

------------------------------------------------------------------------

### 1.15.2 Expressions Versus Statements

An expression produces a value.

``` python
2 * 8
```

An assignment statement binds a value to a name.

``` python
capacity = 2 * 8
```

The right-hand side is an expression:

``` python
2 * 8
```

The complete line is an assignment statement.

Understanding this distinction becomes important when reading function
calls, conditional expressions, comprehensions, assignment expressions,
and more advanced Python syntax.

------------------------------------------------------------------------

### 1.15.3 Major Operator Families

Python operators commonly used in application code include:

  Family                  Examples
  ----------------------- -------------------------------------
  Arithmetic              `+`, `-`, `*`, `/`, `//`, `%`, `**`
  Matrix multiplication   `@`
  Comparison              `<`, `<=`, `>`, `>=`, `==`, `!=`
  Logical                 `not`, `and`, `or`
  Identity                `is`, `is not`
  Membership              `in`, `not in`
  Bitwise                 `&`, `|`, `^`, `~`, `<<`, `>>`
  Assignment              `=`
  Augmented assignment    `+=`, `-=`, `*=`, `/=`, and others
  Assignment expression   `:=`

The correct operator depends on the domain semantics, not merely on
whether an expression happens to produce the desired result for one test
value.

------------------------------------------------------------------------

### 1.15.4 Addition

Numeric addition uses `+`.

``` python
total = 10 + 5
```

The same operator is also defined for some other types.

Strings:

``` python
full_name = "data" + "base"
```

Lists:

``` python
combined = [1, 2] + [3, 4]
```

The meaning of an operator depends on the operand types and their
supported operations.

------------------------------------------------------------------------

### 1.15.5 Subtraction

Use `-` for subtraction.

``` python
remaining = capacity - used
```

Unary minus negates a numeric value.

``` python
delta = -5
```

Binary subtraction and unary negation use the same symbol in different
syntactic roles.

------------------------------------------------------------------------

### 1.15.6 Multiplication

Use `*` for numeric multiplication.

``` python
bytes_total = blocks * block_size
```

Some sequence types also support repetition.

``` python
separator = "-" * 40
```

Be careful when sequence repetition involves mutable nested objects.

``` python
rows = [[0] * 3] * 4
```

The inner list references are shared rather than independently created.

Prefer:

``` python
rows = [[0] * 3 for _ in range(4)]
```

when independent rows are required.

------------------------------------------------------------------------

### 1.15.7 True Division

The `/` operator performs true division.

``` python
average = total / count
```

For ordinary integer operands, the result is a floating-point value.

``` python
5 / 2
```

produces:

``` text
2.5
```

Validate the divisor when zero is possible.

``` python
if count == 0:
    raise ValueError("count must be non-zero")

average = total / count
```

------------------------------------------------------------------------

### 1.15.8 Floor Division

The `//` operator performs floor division.

``` python
pages = records // page_size
```

For negative values, "floor" matters.

``` python
-5 // 2
```

produces:

``` text
-3
```

It does not truncate toward zero.

This distinction matters in algorithms involving negative offsets,
timestamps, coordinates, or financial calculations.

------------------------------------------------------------------------

### 1.15.9 Modulo

The `%` operator computes a remainder consistent with Python's
floor-division rules.

``` python
remainder = records % page_size
```

A common pattern is periodic selection.

``` python
if sequence_number % 10 == 0:
    checkpoint()
```

For numeric operands where the operation is defined, Python maintains
the relationship associated with floor division and modulo.

Do not assume another language's negative-remainder behavior is
identical to Python's.

------------------------------------------------------------------------

For integer operands, floor division and modulo satisfy
`x == (x // y) * y + (x % y)` when `y != 0`. For other numeric types, use
the semantics documented by that type.

------------------------------------------------------------------------

### 1.15.10 Exponentiation

Use `**` for exponentiation.

``` python
capacity = 2 ** 10
```

Exponentiation has important precedence behavior. The power operator binds
more tightly than unary operators on its left, while its right operand can be
a unary expression. The power operator binds
more tightly than unary operators on its left, while its right operand can be
a unary expression.

``` python
-2 ** 2
```

is interpreted as:

``` python
-(2 ** 2)
```

and therefore produces `-4`.

Use parentheses when the intended base is negative:

``` python
(-2) ** 2
```

which produces `4`.

------------------------------------------------------------------------

### 1.15.11 Unary Plus and Minus

Unary operators act on a single operand.

``` python
positive = +value
negative = -value
```

Unary plus is uncommon in ordinary application code but can participate
in numeric protocols.

Unary minus is widely used for signed quantities.

------------------------------------------------------------------------

### 1.15.12 Matrix Multiplication

Python provides `@` and `@=` for matrix multiplication protocols.

``` python
result = left @ right
```

Built-in scalar numeric types do not use `@` as ordinary multiplication.

Libraries and custom types can define matrix multiplication behavior.

Do not substitute `@` for `*`; they represent different operator
protocols.

------------------------------------------------------------------------

### 1.15.13 Comparison Operators

Python comparison operators include:

``` python
<
<=
>
>=
==
!=
```

Examples:

``` python
cpu_percent > 80
retry_count == 0
version != expected_version
```

Comparison operations normally produce Boolean results, although
user-defined types can customize rich comparison behavior.

------------------------------------------------------------------------

### 1.15.14 Equality

Use `==` to test equality.

``` python
actual == expected
```

Equality asks whether two operands compare equal according to their type
behavior.

It does not ask whether they are the same object.

------------------------------------------------------------------------

### 1.15.15 Inequality

Use `!=` to test inequality.

``` python
status != "ready"
```

For user-defined types, comparison behavior can be customized.

Production code should avoid assuming that every comparison is a trivial
field-by-field operation.

------------------------------------------------------------------------

### 1.15.16 Ordering Comparisons

Ordering operators are:

``` python
<
<=
>
>=
```

Example:

``` python
if latency_ms >= threshold_ms:
    alert()
```

Not every pair of Python objects is meaningfully orderable.

For example, unrelated values should not be sorted by inventing
arbitrary conversions unless the application explicitly defines an
ordering rule.

------------------------------------------------------------------------

### 1.15.17 Chained Comparisons

Python supports chained comparisons.

``` python
0 <= utilization <= 100
```

This expresses a range naturally.

It is conceptually similar to:

``` python
0 <= utilization and utilization <= 100
```

but the middle expression in a comparison chain is evaluated only once.

This matters when the middle operand is a function call or another
expression with cost or side effects.

------------------------------------------------------------------------

### 1.15.18 Do Not Duplicate Expensive Comparison Operands

Less desirable:

``` python
minimum <= read_metric() and read_metric() <= maximum
```

`read_metric()` can execute twice.

Prefer:

``` python
minimum <= read_metric() <= maximum
```

if one evaluation is intended.

For maximum clarity, especially when the value is needed later:

``` python
metric = read_metric()

if minimum <= metric <= maximum:
    ...
```

------------------------------------------------------------------------

### 1.15.19 Equality Versus Identity

Equality:

``` python
left == right
```

asks whether values compare equal.

Identity:

``` python
left is right
```

asks whether both references point to the same object.

These are different questions.

------------------------------------------------------------------------

### 1.15.20 Identity Operators

Python provides:

``` python
is
is not
```

The most important routine use is singleton testing.

``` python
if value is None:
    ...
```

Do not use `is` as a general replacement for `==`.

------------------------------------------------------------------------

### 1.15.21 Do Not Use Identity for Numeric or String Equality

Avoid:

``` python
if status is "ready":
    ...
```

Use:

``` python
if status == "ready":
    ...
```

Likewise, do not depend on object caching or interning for numeric
equality.

Implementation optimizations must not become application correctness
rules.

------------------------------------------------------------------------

### 1.15.22 Membership Operators

Use `in` and `not in` for membership tests.

``` python
if environment in {"prod", "staging"}:
    ...
```

``` python
if service not in allowed_services:
    ...
```

Membership behavior depends on the container or object's protocol.

------------------------------------------------------------------------

### 1.15.23 Dictionary Membership Tests Keys

For dictionaries:

``` python
config = {
    "timeout": 30,
    "retries": 3,
}
```

this tests keys:

``` python
"timeout" in config
```

To search values explicitly:

``` python
30 in config.values()
```

Do not confuse dictionary key membership with value membership.

------------------------------------------------------------------------

### 1.15.24 Logical `not`

`not` performs logical negation based on truth-value testing.

``` python
if not healthy:
    ...
```

Unlike `and` and `or`, `not` returns a Boolean value.

``` python
not []
```

produces:

``` text
True
```

------------------------------------------------------------------------

### 1.15.25 Logical `and`

`and` evaluates its left operand first.

If the left operand is falsy, that operand is returned and the right
operand is not evaluated.

Otherwise, the right operand is evaluated and returned.

``` python
result = left and right
```

This behavior enables short-circuit guards.

------------------------------------------------------------------------

### 1.15.26 Logical `or`

`or` evaluates its left operand first.

If the left operand is truthy, that operand is returned and the right
operand is not evaluated.

Otherwise, the right operand is evaluated and returned.

``` python
result = configured_value or default_value
```

This is useful only when all falsy configured values should trigger the
fallback.

If only `None` means "use the default," use an explicit `None` check.

------------------------------------------------------------------------

### 1.15.27 `and` and `or` Return Operands

Consider:

``` python
name = configured_name or "default"
```

The result is not necessarily a Boolean.

``` python
"" or "default"
```

returns:

``` text
"default"
```

Likewise:

``` python
"ready" and 42
```

returns:

``` text
42
```

Do not describe `and` and `or` as operators that always return `True` or
`False`.

------------------------------------------------------------------------

### 1.15.28 Short-Circuit Evaluation

Short-circuiting means an operand may not be evaluated.

``` python
if connection is not None and connection.is_ready():
    ...
```

If `connection is None`, Python does not evaluate:

``` python
connection.is_ready()
```

This can safely guard an operation.

------------------------------------------------------------------------

### 1.15.29 Short-Circuiting and Side Effects

Avoid hiding important side effects inside logical expressions.

Harder to read:

``` python
ready and publish_event()
```

Clearer:

``` python
if ready:
    publish_event()
```

Short expressions can be elegant, but production code should optimize
for clarity and predictable maintenance.

------------------------------------------------------------------------

### 1.15.30 Operator Precedence

Operator precedence determines how an expression is grouped when
parentheses do not make grouping explicit.

For example:

``` python
2 + 3 * 4
```

is interpreted as:

``` python
2 + (3 * 4)
```

because multiplication binds more tightly than addition.

The result is `14`.

------------------------------------------------------------------------

### 1.15.31 Parentheses Override Default Grouping

Use parentheses to express intended grouping.

``` python
(2 + 3) * 4
```

produces `20`.

Parentheses are also valuable even when they are not strictly required.

Compare:

``` python
enabled and retries > 0 or force
```

with:

``` python
(enabled and retries > 0) or force
```

The second form communicates the intended decision structure more
clearly.

------------------------------------------------------------------------

### 1.15.32 Practical Precedence Order

A useful high-level ordering, from tighter to looser binding for common
operators, is:

1.  calls, indexing, attribute access;
2.  exponentiation;
3.  unary `+`, `-`, `~`;
4.  `*`, `@`, `/`, `//`, `%`;
5.  `+`, `-`;
6.  shifts `<<`, `>>`;
7.  bitwise `&`;
8.  bitwise `^`;
9.  bitwise `|`;
10. comparisons, membership, identity;
11. `not`;
12. `and`;
13. `or`;
14. conditional expression;
15. assignment expression `:=`;
16. `lambda`.

This is a practical guide, not a substitute for parentheses when an
expression is non-obvious.

------------------------------------------------------------------------

### 1.15.33 Associativity

When operators have the same precedence, associativity helps determine
grouping.

Many binary arithmetic operators group left to right.

``` python
20 - 5 - 3
```

is interpreted as:

``` python
(20 - 5) - 3
```

Exponentiation is different in its chaining behavior.

``` python
2 ** 3 ** 2
```

is interpreted as:

``` python
2 ** (3 ** 2)
```

------------------------------------------------------------------------

### 1.15.34 Evaluation Order

Python evaluates expressions according to defined language rules,
including left-to-right evaluation of expression components in many
common constructs.

For example:

``` python
first() + second()
```

evaluates `first()` before `second()`.

However, code should not exploit evaluation order to hide coupled side
effects.

Prefer explicit steps when ordering is operationally important.

``` python
left = first()
right = second()
result = left + right
```

------------------------------------------------------------------------

### 1.15.35 Function Arguments and Evaluation

Arguments are evaluated before the function is called.

``` python
process(load_config(), read_state())
```

Both argument expressions must be evaluated before `process()` begins.

When evaluation is expensive, stateful, or failure-prone, separate steps
may improve observability.

``` python
config = load_config()
state = read_state()
process(config, state)
```

------------------------------------------------------------------------

### 1.15.36 Conditional Expressions

Python provides a conditional expression:

``` python
result = value_if_true if condition else value_if_false
```

Example:

``` python
tier = "critical" if utilization >= 90 else "normal"
```

Only the selected result expression is evaluated.

Use conditional expressions for compact, readable choices---not deeply
nested decision trees.

------------------------------------------------------------------------

### 1.15.37 Avoid Nested Conditional Expressions

Possible but difficult to scan:

``` python
status = "critical" if x > 90 else "warning" if x > 70 else "normal"
```

Prefer ordinary control flow when multiple branches carry operational
meaning.

``` python
if x > 90:
    status = "critical"
elif x > 70:
    status = "warning"
else:
    status = "normal"
```

------------------------------------------------------------------------

### 1.15.38 Assignment Expressions

The assignment expression operator is:

``` python
:=
```

It evaluates an expression and assigns the result to a name as part of a
larger expression.

Example:

``` python
if (count := len(records)) > 1000:
    print(f"large batch: {count}")
```

An assignment expression does not create a new scope. In ordinary cases,
the target follows the current scope's normal binding rules. Comprehensions
have additional assignment-expression scope restrictions and should be
reviewed separately when `:=` is used inside them.

------------------------------------------------------------------------

### 1.15.39 Use Assignment Expressions Deliberately

Assignment expressions can avoid duplicate work.

Without one:

``` python
match = pattern.search(text)

if match:
    process(match)
```

With one:

``` python
if match := pattern.search(text):
    process(match)
```

Both can be readable.

Do not use `:=` merely to make code shorter. Use it when binding and
testing one computed value together improves clarity.

------------------------------------------------------------------------

### 1.15.40 Parentheses and Assignment Expressions

Assignment expressions have syntax restrictions intended to prevent
ambiguity.

A common explicit form is:

``` python
if (count := len(records)) > limit:
    ...
```

Parentheses often make the binding target and surrounding comparison
easier to understand.

------------------------------------------------------------------------

### 1.15.41 Assignment Is Not Equality

Assignment:

``` python
status = "ready"
```

binds a value.

Equality:

``` python
status == "ready"
```

compares values.

The assignment expression:

``` python
status := read_status()
```

is a third construct with its own syntax and use cases.

Keep these concepts separate.

------------------------------------------------------------------------

### 1.15.42 Augmented Assignment

Augmented assignment combines an operation with assignment.

``` python
count += 1
```

Other examples include:

``` python
total -= adjustment
size *= factor
mask |= flag
```

Augmented assignment is not always equivalent in object behavior to
spelling the binary operation and assignment separately.

------------------------------------------------------------------------

### 1.15.43 Augmented Assignment and Mutation

For mutable objects, augmented assignment may mutate the existing object
in place.

Example:

``` python
values = [1, 2]
alias = values

values += [3]
```

Both names still refer to the same list, which now contains:

``` python
[1, 2, 3]
```

Contrast this with:

``` python
values = values + [3]
```

which creates a new list and rebinds `values`.

This distinction matters when aliases exist.

------------------------------------------------------------------------

### 1.15.44 Immutable Values and Augmented Assignment

For immutable objects such as integers:

``` python
count = 1
count += 1
```

the name is rebound to the result of the operation.

There is no in-place mutation of the original integer object.

Do not infer mutation semantics solely from the `+=` spelling; behavior
depends on the operand type and supported operator protocol.

------------------------------------------------------------------------

### 1.15.45 Bitwise AND

Use `&` for bitwise AND on integer-like operands.

``` python
permissions = mask & required
```

It is also overloaded by various libraries and custom types.

Do not confuse `&` with logical `and`.

------------------------------------------------------------------------

### 1.15.46 Bitwise OR

Use `|` for bitwise OR.

``` python
combined = read_flag | write_flag
```

The `|` symbol also participates in other type-specific language/library
semantics, such as set union and union type expressions.

Context and operand types determine the operation.

------------------------------------------------------------------------

### 1.15.47 Bitwise XOR

Use `^` for bitwise exclusive OR.

``` python
result = left ^ right
```

XOR is useful for bit masks and specialized algorithms.

It is not Python syntax for exponentiation.

Exponentiation uses:

``` python
**
```

------------------------------------------------------------------------

### 1.15.48 Bitwise NOT

Use `~` for bitwise inversion.

``` python
inverted = ~mask
```

For integers, Python's behavior corresponds to its integer bitwise
model.

Do not use `~` as a replacement for logical `not`.

For Boolean logical negation, use:

``` python
not value
```

------------------------------------------------------------------------

### 1.15.49 Shift Operators

Left shift:

``` python
value << count
```

Right shift:

``` python
value >> count
```

These are common in bit masks, binary protocols, permissions, compact
encodings, and low-level algorithms.

Use named constants and explanatory structure when raw bit manipulation
would otherwise be difficult to review.

------------------------------------------------------------------------

### 1.15.50 Logical Versus Bitwise Operators

Logical:

``` python
and
or
not
```

Bitwise:

``` python
&
|
^
~
```

They are not interchangeable.

Logical operators use truth-value semantics and `and`/`or`
short-circuit.

Bitwise operators evaluate their operands and apply type-specific
operator behavior.

This distinction is especially important in code using arrays, data
frames, query-expression libraries, or custom domain objects.

------------------------------------------------------------------------

### 1.15.51 Boolean Values and Bitwise Operators

Because `bool` is a subtype of `int`, some bitwise operations on Boolean
values have Boolean-specific behavior.

However, production Boolean logic should normally use:

``` python
and
or
not
```

when logical semantics are intended.

In Python 3.14, applying bitwise inversion `~` to a Boolean is
deprecated and is scheduled to become an error in Python 3.16.

Use:

``` python
not flag
```

for Boolean negation.

------------------------------------------------------------------------

### 1.15.52 Operator Overloading

Python types can customize many operators.

Conceptually:

``` python
left + right
```

may invoke special methods associated with addition.

For a user-defined class:

``` python
class Capacity:
    def __init__(self, value: int) -> None:
        self.value = value

    def __add__(self, other):
        ...
```

Operator syntax therefore does not guarantee built-in numeric behavior.

Review the operand types and their contracts. At plugin, SDK, ORM, array,
query-builder, and other extension boundaries, treat overloaded operators as
executable type-defined behavior rather than harmless punctuation; they can
allocate, perform expensive computation, build deferred expressions, or raise
domain-specific exceptions.

------------------------------------------------------------------------

### 1.15.53 Special Methods and Operators

Common operator-related special methods include:

``` text
__add__
__sub__
__mul__
__truediv__
__floordiv__
__mod__
__pow__
__eq__
__lt__
__contains__
__and__
__or__
__lshift__
```

These methods participate in Python's data model.

Application code normally uses operator syntax rather than calling these
special methods directly.

------------------------------------------------------------------------

### 1.15.54 Reflected Operations

Binary operator protocols can give the right operand an opportunity to
handle an operation when appropriate.

For addition, the reflected method is:

``` python
__radd__
```

This is important when designing interoperable numeric or domain types.

Do not assume only the left operand's implementation can influence a
binary operation.

------------------------------------------------------------------------

### 1.15.55 In-Place Operator Protocols

Augmented assignment can use in-place special methods such as:

``` python
__iadd__
```

when supported.

If an in-place implementation is unavailable or declines the operation,
Python can fall back according to the relevant binary operator protocol.

This is another reason `x += y` should not be described as mere textual
shorthand for `x = x + y`.

------------------------------------------------------------------------

### 1.15.56 `NotImplemented` in Operator Methods

A binary special method can return:

``` python
NotImplemented
```

to indicate that it does not implement the operation for the supplied
operand combination.

This allows Python's operator dispatch machinery to try appropriate
alternatives, including reflected operations where applicable.

`NotImplemented` is a special singleton value for operator dispatch. It
is not the same as raising `NotImplementedError`.

------------------------------------------------------------------------

In Python 3.14, evaluating `NotImplemented` in a Boolean context raises
`TypeError`. Operator implementations should return it only for documented
operator dispatch rather than testing its truth value.

------------------------------------------------------------------------

### 1.15.57 `NotImplemented` Versus `NotImplementedError`

These are different concepts.

`NotImplemented`:

``` python
return NotImplemented
```

is used by certain binary operation/comparison protocols to signal
unsupported operand handling.

`NotImplementedError`:

``` python
raise NotImplementedError
```

is an exception commonly used when an operation or subclass
implementation has not been provided.

Do not substitute one for the other.

------------------------------------------------------------------------

### 1.15.58 Comparison Overloading

User-defined types can implement rich comparison methods such as:

``` text
__lt__
__le__
__eq__
__ne__
__gt__
__ge__
```

This means:

``` python
left == right
```

can execute application-defined code.

Keep equality operations side-effect free where possible and define
clear comparison semantics for domain types.

------------------------------------------------------------------------

### 1.15.59 Membership Protocol Behavior

Membership testing:

``` python
item in container
```

can use type-specific membership behavior.

Custom classes may implement `__contains__()`.

If `__contains__()` is unavailable, Python can fall back to iteration via
`__iter__()`, and then to the older sequence protocol using `__getitem__()`
with integer indices starting at zero.

Membership may therefore be more than a constant-time hash lookup;
understand the container's complexity and semantics.

------------------------------------------------------------------------

### 1.15.60 Expressions Can Raise Exceptions

An expression is not guaranteed to produce a value successfully.

Examples:

``` python
10 / 0
```

can raise `ZeroDivisionError`.

``` python
config["missing"]
```

can raise `KeyError`.

``` python
int("invalid")
```

can raise `ValueError`.

Production expression design must account for expected failure modes.

------------------------------------------------------------------------

### 1.15.61 Avoid Exception-Prone Work Hidden in Dense Expressions

Harder to troubleshoot:

``` python
result = transform(load(path).strip()) if path else default
```

Clearer when failures matter operationally:

``` python
if path:
    raw = load(path)
    cleaned = raw.strip()
    result = transform(cleaned)
else:
    result = default
```

The expanded form gives logging, validation, metrics, and exception
handling natural locations.

------------------------------------------------------------------------

### 1.15.62 Expressions and Side Effects

An expression may call functions with side effects.

``` python
current + read_and_update_counter()
```

When correctness depends on evaluation order, state mutation, network
calls, database writes, or external effects, split the operation into
named steps.

Expressions should not hide an operational workflow.

------------------------------------------------------------------------

### 1.15.63 Expressions and Expensive Work

Avoid repeating expensive expressions.

Less desirable:

``` python
if calculate_capacity() > minimum and calculate_capacity() < maximum:
    ...
```

Prefer:

``` python
capacity = calculate_capacity()

if minimum < capacity < maximum:
    ...
```

This is clearer, avoids duplicate work, and produces a value that can be
logged or inspected.

------------------------------------------------------------------------

### 1.15.64 Expressions and `None`

Do not use truthiness when the expression must preserve valid falsy
values.

Unsafe:

``` python
timeout = configured_timeout or 30
```

if zero is meaningful.

Prefer:

``` python
timeout = (
    30
    if configured_timeout is None
    else configured_timeout
)
```

Operator choice must preserve domain semantics.

------------------------------------------------------------------------

### 1.15.65 Expressions and Floating-Point Equality

Exact equality can be inappropriate for results of floating-point
calculations.

``` python
0.1 + 0.2 == 0.3
```

may be `False` because many decimal fractions cannot be represented
exactly as binary floating-point values.

For approximate numeric comparison, use a domain-appropriate tolerance
or facilities such as `math.isclose()`.

Do not globally replace equality with approximate comparison; exact
equality remains correct for domains where exact representation and
equality are required.

------------------------------------------------------------------------

### 1.15.66 Expressions and Decimal Arithmetic

Financial or other decimal-sensitive domains may use `decimal.Decimal`.

Do not mix binary floating-point assumptions into decimal-domain
calculations.

``` python
from decimal import Decimal

price = Decimal("19.95")
tax = Decimal("1.60")
total = price + tax
```

Operator syntax can look identical while the underlying numeric
semantics differ.

------------------------------------------------------------------------

### 1.15.67 Expressions and Large Integers

Python integers have arbitrary precision subject to available memory.

``` python
value = 10 ** 100
```

This avoids fixed-width integer overflow behavior found in many
languages.

However, enormous integer operations can still consume significant CPU
and memory.

Do not treat arbitrary precision as unlimited computational capacity.

The same rule applies to externally controlled exponentiation and shift
counts. Validate bounds before operations such as `base ** exponent` or
`value << shift` when untrusted or unconstrained inputs could trigger
excessive CPU or memory consumption.

### 1.15.68 Production Example --- Capacity Threshold

Readable:

``` python
if 0 <= utilization_percent <= 100:
    ...
else:
    raise ValueError("utilization must be between 0 and 100")
```

A chained comparison communicates the domain constraint directly.

### 1.15.69 Production Example --- Disk Alerting

``` python
warning_threshold = 75
critical_threshold = 85

if usage_percent >= critical_threshold:
    severity = "critical"
elif usage_percent >= warning_threshold:
    severity = "warning"
else:
    severity = "normal"
```

Do not compress operational severity logic into a dense nested
expression merely to reduce line count.

### 1.15.70 Production Example --- Retry Decision

``` python
should_retry = (
    attempt < max_attempts
    and error.retryable
    and not shutdown_requested
)
```

Parentheses and one condition per line make the decision rule easier to
review.

If any condition performs expensive work or has side effects, compute it
separately.

### 1.15.71 Production Example --- Configuration Default

``` python
effective_replicas = (
    default_replicas
    if configured_replicas is None
    else configured_replicas
)
```

This preserves a configured value of zero when scale-to-zero is valid.

### 1.15.72 Production Example --- Membership Validation

``` python
allowed_environments = {
    "development",
    "staging",
    "production",
}

if environment not in allowed_environments:
    raise ValueError(f"unsupported environment: {environment}")
```

Membership expresses the rule more directly than a long chain of
equality comparisons.

### 1.15.73 Production Example --- Feature Eligibility

``` python
eligible = (
    account_active
    and region in supported_regions
    and plan in eligible_plans
)
```

This expression is readable because each operand is already a meaningful
predicate.

Avoid embedding unrelated lookups, mutations, or network operations
directly into the Boolean expression.

### 1.15.74 Production Example --- Bit Flags

``` python
READ = 0b001
WRITE = 0b010
ADMIN = 0b100

permissions = READ | WRITE

can_write = bool(permissions & WRITE)
```

Named masks make the expression easier to understand than unexplained
numeric literals.

For higher-level application permissions, an enum or dedicated
authorization model may be clearer than raw bit arithmetic.

### 1.15.75 Production Example --- Batch Calculation

Suppose each worker processes a fixed number of records.

``` python
batch_count = (
    total_records + batch_size - 1
) // batch_size
```

This integer ceiling-division pattern assumes positive values and a
non-zero `batch_size`.

Validate those assumptions.

``` python
if total_records < 0:
    raise ValueError("total_records cannot be negative")

if batch_size <= 0:
    raise ValueError("batch_size must be positive")
```

``` python
offset = page_number * page_size
```

Validate page semantics explicitly.

``` python
if page_number < 0:
    raise ValueError("page_number cannot be negative")

if page_size <= 0:
    raise ValueError("page_size must be positive")
```

Arithmetic expressions should not carry unstated input assumptions.

``` python
healthy = (

    and connection.is_ready()
```

If `is_ready()` performs network I/O, consider separating it so latency

``` python
while chunk := stream.read(8192):
    process(chunk)
```

This can be a concise pattern when an empty result is the documented

If other falsy values carry different meanings, use a more explicit

### 1.15.80 Production Example --- Avoid Duplicate Parsing

``` python
if (match := pattern.search(message)) is not None:
    process_match(match)
```

This both preserves the result and avoids executing the search twice.

The explicit `is not None` is useful when a match object's truth-value

### 1.15.81 Operator Behavior Across Types

The same operator can behave differently across types.

``` python
1 + 2
"1" + "2"
[1] + [2]
```

All use `+`, but the semantics differ.

Production code should make operand types and contracts sufficiently
clear that operator behavior is not surprising.

------------------------------------------------------------------------

### 1.15.82 Mixed Numeric Types

Python supports interactions among several numeric types, but the
resulting coercion and precision behavior depends on the types involved.

Avoid casually mixing:

-   binary floating point;
-   decimal arithmetic;
-   fractions;
-   third-party numeric scalar types.

For precision-sensitive systems, define the numeric representation at
the domain boundary.

------------------------------------------------------------------------

### 1.15.83 Avoid Clever Operator Tricks

Code such as:

``` python
enabled and start() or fallback()
```

may rely on operand-return behavior in ways that are difficult to
maintain and can fail when `start()` returns a falsy value.

Prefer explicit control flow:

``` python
if enabled:
    result = start()
else:
    result = fallback()
```

Clarity is more valuable than reducing a decision to one expression.

------------------------------------------------------------------------

### 1.15.84 Parenthesize for Humans

Even when precedence is known, parentheses can document intent.

Prefer:

``` python
if (is_admin or is_owner) and account_active:
    ...
```

over relying on every reviewer to reconstruct:

``` python
if is_admin or is_owner and account_active:
    ...
```

These expressions do not mean the same thing, and the parenthesized form
makes the intended grouping explicit.

------------------------------------------------------------------------

### 1.15.85 Keep Expressions Reviewable

An expression becomes harder to maintain when it combines too many
concerns:

``` python
result = (
    transform(fetch(key))
    if enabled and key in cache and cache[key] is not None
    else fallback()
)
```

Consider decomposing:

``` python
cached_value = cache.get(key)

if enabled and cached_value is not None:
    fetched = fetch(key)
    result = transform(fetched)
else:
    result = fallback()
```

The exact decomposition depends on intended semantics, but each named
step creates a place for validation, diagnostics, and testing.

------------------------------------------------------------------------

### 1.15.86 Security-Sensitive Comparisons

Ordinary equality operators are not automatically appropriate for every
security-sensitive comparison.

For secrets such as authentication tokens or message authentication
codes, use the comparison facility recommended by the relevant security
API, such as a constant-time comparison function when required.

Do not build custom "constant-time" logic from ordinary operators unless
you fully control and understand the threat model and implementation.

------------------------------------------------------------------------

### 1.15.87 Expressions at API Boundaries

External values should be parsed and validated before participating in
business expressions.

Avoid:

``` python
if payload["retries"] < 5:
    ...
```

before validating the field's presence, type, and allowed range.

Prefer a boundary step:

``` python
retries = validate_retries(payload)
```

followed by domain logic:

``` python
if retries < 5:
    ...
```

This separates input correctness from business decisions.

------------------------------------------------------------------------

### 1.15.88 Expressions in Observability Code

Avoid expressions that accidentally change program behavior merely to
produce logs or metrics.

For example, do not call an expensive or state-changing function twice:

``` python
logger.info("capacity=%s", calculate_capacity())

if calculate_capacity() > threshold:
    ...
```

Prefer:

``` python
capacity = calculate_capacity()

logger.info("capacity=%s", capacity)

if capacity > threshold:
    ...
```

The observed value and the decision now refer to the same evaluation.

------------------------------------------------------------------------

### 1.15.89 Common Operator Mistakes

Common mistakes include:

1.  using `is` instead of `==` for value equality;
2.  using `== None` instead of `is None`;
3.  assuming `and` and `or` always return Boolean values;
4.  using `or` defaults when valid falsy values exist;
5.  confusing `^` with exponentiation;
6.  confusing bitwise operators with logical operators;
7.  forgetting negative floor-division behavior;
8.  misunderstanding exponentiation precedence;
9.  duplicating expensive or side-effecting expressions;
10. relying on implicit precedence in complicated Boolean logic;
11. assigning the result of an in-place method that returns `None`;
12. assuming augmented assignment never mutates;
13. assuming operator syntax has identical semantics across types;
14. using exact floating-point equality where approximate comparison is
    required;
15. hiding exceptions or side effects inside dense expressions;
16. using unvalidated external values directly in expressions;
17. assuming arbitrary-precision integers imply unlimited resource
    usage;
18. confusing `NotImplemented` with `NotImplementedError`.

------------------------------------------------------------------------

### 1.15.90 Troubleshooting Operator and Expression Problems

When an expression produces an unexpected result:

1.  identify each operand and its runtime type;
2.  confirm the operator's semantics for those types;
3.  add parentheses to make grouping explicit;
4.  check operator precedence;
5.  check associativity where relevant;
6.  inspect evaluation order and short-circuit behavior;
7.  check whether an operand expression is evaluated more than once;
8.  check for side effects;
9.  check custom operator methods;
10. check mutation and aliasing around augmented assignment;
11. check `None`, falsy values, and defaulting assumptions;
12. check numeric representation and precision;
13. check exception paths;
14. reduce the expression to smaller named steps;
15. reproduce with minimal inputs;
16. add tests around boundary and negative cases.

Do not "fix" an unexplained expression merely by adding casts or
changing operators until the underlying semantics are understood.

------------------------------------------------------------------------

### 1.15.91 Production Engineering Rules

1.  Choose operators based on domain semantics.
2.  Use `==` for value equality and `is` for identity.
3.  Use `is None` and `is not None` for `None`.
4.  Remember that `and` and `or` return operands.
5.  Use short-circuiting deliberately.
6.  Do not hide critical side effects in Boolean expressions.
7.  Preserve valid falsy values when defaulting.
8.  Use chained comparisons for clear range checks.
9.  Avoid evaluating expensive or stateful expressions multiple times.
10. Use parentheses when grouping is not immediately obvious.
11. Do not depend on implementation interning for correctness.
12. Distinguish logical operators from bitwise operators.
13. Use `not`, not `~`, for Boolean negation.
14. Treat `+=` and other augmented assignments as type-dependent
    operations.
15. Understand aliasing before mutating shared objects.
16. Keep overloaded operator semantics unsurprising.
17. Return `NotImplemented` appropriately from unsupported binary
    operator implementations.
18. Do not confuse `NotImplemented` with `NotImplementedError`.
19. Validate divisors and arithmetic domain assumptions.
20. Treat floating-point equality according to the numeric domain.
21. Define precision-sensitive numeric representations deliberately.
22. Validate external inputs before business expressions.
23. Split dense expressions when failures or operations need
    observability.
24. Reuse computed values when logs and decisions must describe the same
    evaluation.
25. Prefer maintainability over clever operator tricks.

### 1.15.96 Key Takeaways

-   Operators act on operands to form expressions.
-   Operator behavior depends on operand types and Python's data model.
-   `/` and `//` have different division semantics.
-   Floor division rounds toward negative infinity.
-   `**` performs exponentiation and has precedence behavior worth
    understanding.
-   Comparisons, identity tests, and membership tests answer different
    questions.
-   `and` and `or` short-circuit and return operands rather than always
    returning Boolean values.
-   Chained comparisons can improve clarity and avoid repeated
    evaluation of a middle expression.
-   Parentheses are documentation for humans as well as grouping syntax.
-   Evaluation order should not be used to hide coupled side effects.
-   Conditional expressions and assignment expressions are useful when
    they improve clarity.
-   Augmented assignment can mutate mutable objects and therefore affect
    aliases.
-   Logical and bitwise operators are not interchangeable.
-   Operator overloading means familiar syntax can invoke type-specific
    behavior.
-   `NotImplemented` participates in operator dispatch and is not
    `NotImplementedError`.
-   Numeric syntax can look identical across types while precision and
    coercion semantics differ.
-   Dense expressions are harder to validate, observe, and troubleshoot.
-   Production expressions should preserve domain distinctions such as
    `None`, zero, empty, and `False`.
-   External values should be validated before they participate in
    business expressions.
-   Reusing a computed value keeps decisions, logs, and metrics
    consistent.
-   Clear expressions are preferable to clever expressions.

> **Central engineering principle:** Use operators to express domain
> rules, not to compress them. When precedence, overloading, mutation,
> side effects, or failure behavior makes an expression difficult to
> reason about, decompose it into explicit, named steps.
