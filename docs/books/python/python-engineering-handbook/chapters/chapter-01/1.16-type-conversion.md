# Chapter 1 --- Python Fundamentals and Development Environment

## 1.16 --- Type Conversion

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   distinguish implicit numeric conversion from explicit type
    conversion;
-   use Python's core conversion constructors safely;
-   convert external text without hiding invalid input;
-   reason about precision, truncation, truth-value conversion, and
    lossy conversions;
-   design production conversion logic with validation, observability,
    and explicit failure behavior;
-   avoid conversion bugs involving `bool`, `None`, bytes, collections,
    and configuration data.

------------------------------------------------------------------------

### 1.16.1 Type Conversion and Domain Boundaries

Type conversion transforms a value from one representation or type into
another.

``` python
port = int("5432")
timeout = float("2.5")
label = str(42)
```

In production systems, conversion often marks a trust boundary:

``` text
external representation
        ↓
parse / convert
        ↓
validate
        ↓
canonical domain value
        ↓
business logic
```

Conversion and validation are different. `int("500")` proves that the
text is an integer representation; it does not prove that 500 is a valid
replica count.

``` python
replicas = int(raw_replicas)
if not 1 <= replicas <= 20:
    raise ValueError("replicas must be between 1 and 20")
```

------------------------------------------------------------------------

### 1.16.2 Implicit Versus Explicit Conversion

Python performs limited coercion between compatible numeric types:

``` python
result = 10 + 2.5
assert isinstance(result, float)
```

It does not generally guess conversions between unrelated
representations:

``` python
# TypeError
# "10" + 5
```

Convert explicitly:

``` python
total = int("10") + 5
```

Explicit conversion makes representation changes reviewable.

------------------------------------------------------------------------

### 1.16.3 Core Conversion Constructors

Common constructors include `int()`, `float()`, `complex()`, `bool()`,
`str()`, `bytes()`, `bytearray()`, `list()`, `tuple()`, `set()`,
`frozenset()`, and `dict()`.

A constructor being able to accept a value does not mean that it is the
correct parser for an external protocol. The interface contract should
define which representations are accepted.

------------------------------------------------------------------------

### 1.16.4 Integer Conversion

``` python
a = int("42")
b = int(42.9)
c = int(True)
```

Invalid integer text raises `ValueError`; unsupported inputs can raise
`TypeError`.

For finite floats, `int()` truncates the fractional part toward zero:

``` python
int(3.9)    # 3
int(-3.9)   # -3
```

This is not rounding. Use the domain's required rounding policy instead.

Integer strings can use an explicit base:

``` python
int("1010", 2)   # 10
int("ff", 16)    # 255
int("0xff", 0)   # 255
```

Only accept bases and representations that the interface intentionally
supports.

For conversion protocols, `int(x)` uses `x.__int__()` when defined and can
fall back to `x.__index__()`. In Python 3.14, `int()` no longer delegates to
`__trunc__()`.

CPython also applies a configurable limit to certain conversions between
decimal/other non-power-of-two integer strings and integers to mitigate
denial-of-service risks. Code processing hostile numeric text should rely on
runtime safeguards **and** enforce application-level field-size and range
limits.

------------------------------------------------------------------------

### 1.16.5 Floating-Point and Decimal Conversion

``` python
timeout = float("2.5")
```

Binary floating-point cannot exactly represent every decimal fraction.
For exact decimal domains, convert authoritative decimal text directly
to `Decimal`:

``` python
from decimal import Decimal

price = Decimal("19.99")
```

Avoid an unnecessary float intermediary:

``` python
# Avoid when exact decimal semantics matter:
# Decimal(float(raw_price))
```

`Decimal(float_value)` converts the actual binary floating-point value
exactly; it does not reconstruct the decimal text that may originally have
produced that float. When decimal text is authoritative, construct `Decimal`
directly from that text.

Conversion mechanisms must match domain precision requirements.

------------------------------------------------------------------------

### 1.16.6 Boolean Conversion

`bool(value)` performs truth-value testing.

``` python
bool(1)        # True
bool(0)        # False
bool("")       # False
bool("false")  # True
```

`bool()` is **not** a textual Boolean parser. Every non-empty string is
truthy.

For environment variables or textual APIs, define an explicit token
contract:

``` python
def parse_bool(text: str) -> bool:
    token = text.strip().lower()

    if token in {"true", "1", "yes", "on"}:
        return True
    if token in {"false", "0", "no", "off"}:
        return False

    raise ValueError("invalid boolean token")
```

Fail on unrecognized values unless the interface specification
explicitly defines another policy.

------------------------------------------------------------------------

### 1.16.7 `bool` and Integer Domains

`bool` is a subtype of `int`, so:

``` python
int(True)   # 1
int(False)  # 0
isinstance(True, int)  # True
```

That language relationship does not mean that a Boolean is semantically
valid where the domain expects a quantity.

A strict boundary can reject it:

``` python
def require_int(value: object) -> int:
    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("expected integer")
    return value
```

Subclass acceptance is an API-design decision.

------------------------------------------------------------------------

### 1.16.8 String Conversion Is Not Serialization

`str()` creates a textual representation:

``` python
text = str(25)
```

Do not assume `str(obj)` is a stable machine interchange format.

``` python
import json

payload = {"healthy": True, "replicas": 3}
encoded = json.dumps(payload)
```

Use the serializer defined by the protocol.

------------------------------------------------------------------------

### 1.16.9 Text and Bytes

Encode text into bytes with an explicit encoding:

``` python
payload = "database-ready".encode("utf-8")
```

Decode bytes using the expected encoding:

``` python
text = payload.decode("utf-8")
```

Invalid sequences can raise `UnicodeDecodeError`. Encoding and error
policy are part of the data contract.

`bytes()` has input-dependent semantics:

``` python
bytes(4)  # four zero-valued bytes
```

It does not mean `b"4"`.

------------------------------------------------------------------------

### 1.16.10 Collection Conversion

`list()` and `tuple()` materialize iterables:

``` python
numbers = list(range(5))
coordinates = tuple([10, 20])
```

Materializing a generator consumes it and stores the results in memory.

``` python
values = (n * n for n in range(5))
materialized = list(values)
```

Do not eagerly materialize an unbounded or unexpectedly large stream.

A tuple does not recursively freeze nested mutable objects.

------------------------------------------------------------------------

### 1.16.11 Sets and Information Loss

``` python
roles = set(["reader", "writer", "reader"])
```

Set conversion can remove duplicate information and changes sequence
semantics. It can also fail when elements are unhashable.

Set conversion discards sequence position/order as a semantic guarantee.

Use `frozenset()` when immutable set semantics are required.

Do not use set conversion when duplicates or sequence order are
business-significant.

------------------------------------------------------------------------

### 1.16.12 Dictionary Conversion

`dict()` accepts mappings and suitable key-value iterables:

``` python
pairs = [("host", "db01"), ("port", 5432)]
config = dict(pairs)
```

`dict(existing_mapping)` creates a shallow copy; nested mutable objects
can remain shared.

Repeated keys can be overwritten by later entries. If duplicate keys are
invalid, detect them before constructing the dictionary.

------------------------------------------------------------------------

### 1.16.13 Conversion Can Be Lossy

Examples:

``` python
int(3.99)       # fractional information lost
set([1, 1, 2])  # duplicate information lost
int("00123")    # representation information lost
```

Before a lossy conversion, ask whether the discarded information
matters.

Identifiers such as account IDs, postal codes, telephone numbers, opaque
resource IDs, and version-like tokens may look numeric while still
belonging to the string domain.

------------------------------------------------------------------------

### 1.16.14 `None` and Missingness

`None` represents absence.

``` python
str(None)   # "None"
bool(None)  # False
```

Those conversions do not make absence a valid domain string or Boolean.

Preserve missingness explicitly:

``` python
def normalize_port(raw: str | None) -> int | None:
    if raw is None:
        return None
    return int(raw)
```

Do not accidentally collapse `None`, empty strings, zero, and `False`
when the domain distinguishes them.

------------------------------------------------------------------------

### 1.16.15 Defaults Versus Invalid Values

Defaults usually belong to missingness policy.

Avoid silently replacing malformed input:

``` python
# Risky:
try:
    timeout = int(raw_timeout)
except ValueError:
    timeout = 30
```

Prefer:

``` python
if raw_timeout is None:
    timeout = 30
else:
    timeout = int(raw_timeout)
```

Now missing input gets the default while malformed present input fails.

------------------------------------------------------------------------

### 1.16.16 Handling Conversion Errors

Catch only errors you can meaningfully translate:

``` python
def parse_port(raw: str) -> int:
    try:
        port = int(raw)
    except ValueError as exc:
        raise ValueError("port must be an integer") from exc

    if not 1 <= port <= 65535:
        raise ValueError("port must be between 1 and 65535")

    return port
```

Conceptually, `ValueError` often indicates an unacceptable value or
representation for an otherwise supported operation, while `TypeError`
indicates an unsupported object/type. Exact behavior is API-specific.

Do not hide deterministic malformed input behind broad exception
handling.

------------------------------------------------------------------------

### 1.16.17 Normalize Once at the Owning Boundary

Avoid repeated conversion:

``` python
# Avoid:
if int(config["workers"]) > 10:
    ...
logger.info("workers=%s", int(config["workers"]))
```

Prefer:

``` python
workers = int(config["workers"])

if workers > 10:
    ...
logger.info("workers=%s", workers)
```

A production architecture commonly looks like:

``` text
environment / JSON / CLI / DB / message
                    ↓
             boundary parser
                    ↓
           validated domain model
                    ↓
             business logic
```

------------------------------------------------------------------------

### 1.16.18 Environment Variables

Environment variables are strings when present.

``` python
import os

raw_workers = os.getenv("WORKERS")

if raw_workers is None:
    workers = 4
else:
    workers = int(raw_workers)

if not 1 <= workers <= 64:
    raise ValueError("WORKERS must be between 1 and 64")
```

Malformed configuration should normally be visible during startup or
reload rather than silently normalized into a default.

------------------------------------------------------------------------

For startup and reload configuration failures, emit a bounded, non-secret
diagnostic identifying the affected field. If malformed configuration prevents
safe operation, fail initialization rather than silently substituting a value.

---

### 1.16.19 JSON and API Boundaries

JSON decoding already produces Python values corresponding to JSON
representations:

``` python
import json

payload = json.loads('{"enabled": true, "count": 3}')
assert payload["enabled"] is True
assert payload["count"] == 3
```

If an API schema requires a JSON integer, do not automatically broaden
it to accept numeric strings.

``` python
def parse_replica_count(value: object) -> int:
    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("replicas must be a JSON integer")
    if not 1 <= value <= 20:
        raise ValueError("replicas must be between 1 and 20")
    return value
```

Strict versus coercive parsing is part of the public contract.

------------------------------------------------------------------------

### 1.16.20 Command-Line Conversion

Text-native interfaces can intentionally convert at the parser:

``` python
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--workers", type=int, default=4)
args = parser.parse_args()
```

Constructor conversion does not replace domain validation.

------------------------------------------------------------------------

### 1.16.21 Database Boundaries

Database drivers commonly return Python values according to database and
driver type mappings.

Avoid unnecessary conversion chains such as:

``` python
count = int(str(row["count"]))
```

when the driver already returns an integer.

Unnecessary coercion can hide schema mismatches.

------------------------------------------------------------------------

### 1.16.22 Enumerated Values

Normalize only according to a documented contract:

``` python
mode = raw_mode.strip().lower()

if mode not in {"safe", "fast"}:
    raise ValueError("unsupported mode")
```

For a larger domain:

``` python
from enum import Enum

class Mode(str, Enum):
    SAFE = "safe"
    FAST = "fast"

mode = Mode(raw_mode)
```

Unsupported values should fail rather than silently becoming
undocumented modes.

------------------------------------------------------------------------

### 1.16.23 Dates and Times

Parse date/time text using a parser appropriate to the contract:

``` python
from datetime import datetime

timestamp = datetime.fromisoformat(raw_timestamp)
```

Then separately validate domain requirements such as timezone awareness,
permitted ranges, and normalization policy.

Parsing and domain validation remain separate concerns.

------------------------------------------------------------------------

### 1.16.24 Exact Decimal Data

``` python
from decimal import Decimal, InvalidOperation

def parse_amount(raw: str) -> Decimal:
    try:
        amount = Decimal(raw)
    except InvalidOperation as exc:
        raise ValueError("invalid decimal amount") from exc

    if amount < 0:
        raise ValueError("amount cannot be negative")

    return amount
```

Use a conversion mechanism that preserves the precision contract.

------------------------------------------------------------------------

### 1.16.25 Collection Element Conversion

Container conversion does not validate element domains.

``` python
ports = [int(value) for value in raw_ports]

if any(not 1 <= port <= 65535 for port in ports):
    raise ValueError("invalid port")
```

For large streams, consider lazy conversion:

``` python
converted = (int(value) for value in raw_values)
```

Lazy conversion reduces eager materialization but moves possible
conversion failures to consumption time.

------------------------------------------------------------------------

### 1.16.26 Conversion Order Matters

``` python
raw = "3.9"
value = int(float(raw))
```

This accepts decimal text and then truncates it, whereas:

``` python
# ValueError
# int("3.9")
```

does not.

Do not chain conversions merely to force unsupported input through.
Every intermediate representation should be intentional.

------------------------------------------------------------------------

### 1.16.27 Custom Conversion Protocols

User-defined and third-party types can participate in conversion
behavior.

Operations such as:

``` python
int(obj)
float(obj)
str(obj)
bytes(obj)
```

can invoke type-defined protocols.

At plugin, SDK, ORM, scientific-computing, and extension boundaries,
treat conversion as executable type-defined behavior rather than
necessarily trivial copying. It can allocate, compute, or raise
domain-specific exceptions.

------------------------------------------------------------------------

### 1.16.28 Conversion and Logging

String conversion is often triggered by diagnostics:

``` python
logger.info("object=%s", obj)
```

Type-defined representations can be expensive, fragile, or
secret-bearing.

Do not expose credentials, tokens, private keys, or sensitive payloads
merely because an object is converted to text.

Prefer structured redaction before conversion.

------------------------------------------------------------------------

### 1.16.29 Observability for Conversion Failures

Useful errors identify the field, expected representation, and domain
constraint without leaking secrets:

``` text
WORKERS must be an integer between 1 and 64
```

High-volume systems can use bounded metrics:

``` text
input_conversion_failures_total{field="replicas",source="api"}
```

Do not place raw values, IDs, exception strings, or other unbounded data
in metric labels.

------------------------------------------------------------------------

### 1.16.30 Conversion and Retry Policy

Retrying deterministic malformed input does not repair it.

``` text
malformed representation → reject / quarantine / dead-letter / operator fix
transient dependency      → retry may be appropriate
```

Do not turn parsing failures into retry storms.

Message consumers should deserialize, normalize, validate, and only then
apply business side effects according to the platform's delivery and
error policy.

------------------------------------------------------------------------

### 1.16.31 Canonical Internal Types

Define one internal representation for each domain concept:

``` text
worker count       → int
feature state      → bool
price              → Decimal
timestamp          → timezone-aware datetime
resource ID        → str
payload bytes      → bytes
```

Convert external forms at boundaries and keep canonical types inside the
application.

------------------------------------------------------------------------

### 1.16.32 Type Annotations and Dataclasses

Annotations document transitions but do not perform runtime conversion:

``` python
def parse_workers(raw: str) -> int:
    ...
```

A typed configuration object can hold normalized values:

``` python
from dataclasses import dataclass

@dataclass(frozen=True)
class ServiceConfig:
    workers: int
    timeout_seconds: float
    debug: bool
```

Construct it only after parsing and validation.

------------------------------------------------------------------------

### 1.16.33 Schema Libraries and Coercion

Validation/modeling libraries differ in coercion behavior.

Teams should decide whether a boundary is:

-   strict;
-   coercive;
-   partially coercive;
-   temporarily compatible with legacy representations.

Do not assume a type annotation automatically means strict runtime
acceptance. Test the actual schema behavior.

Strict parsing is often preferable for machine contracts; controlled
coercion can be appropriate for text-native environment variables and
CLI arguments.

------------------------------------------------------------------------

### 1.16.34 Security Boundaries

Overly permissive conversion expands the set of inputs treated as valid.

Security-sensitive boundaries should:

-   define accepted representations narrowly;
-   reject ambiguity;
-   enforce size and range limits;
-   avoid dynamic evaluation;
-   preserve auditability.

Never use `eval()` as a general conversion mechanism for untrusted
input.

``` python
# Never for untrusted input:
# value = eval(raw_value)
```

Use a format-specific parser such as `json.loads()` when JSON is the
contract.

------------------------------------------------------------------------

### 1.16.35 `ast.literal_eval()` Is Not a Wire Format

`ast.literal_eval()` can process supported Python literal/container
syntax without evaluating arbitrary Python expressions, but it is not a
substitute for a defined interchange format.

For APIs and persistent interchange, use the format specified by the
contract. Untrusted parsers still require resource and input-size
controls.

------------------------------------------------------------------------

Python's documentation warns against calling `ast.literal_eval()` on
untrusted data because relatively small inputs can cause excessive memory,
stack, or CPU consumption. A parser that avoids arbitrary code execution can
still require resource controls.

---

### 1.16.36 Resource Limits During Conversion

Conversion can consume substantial resources:

-   materializing huge iterables;
-   constructing very large integers from text;
-   decoding large byte strings;
-   parsing deeply nested structures;
-   allocating large byte arrays.

A syntactically valid value can still be operationally unsafe.

Apply request, field, range, depth, and size limits appropriate to the
boundary.

------------------------------------------------------------------------

### 1.16.37 Copy Semantics

Some conversions create a new outer container:

``` python
a = [1, 2, 3]
b = list(a)

assert a is not b
```

Nested objects can remain shared:

``` python
a = [[1], [2]]
b = list(a)
b[0].append(99)

print(a)
```

Conversion is not automatically a deep copy.

------------------------------------------------------------------------

### 1.16.38 Round Trips and Idempotence

A conversion round trip may lose representation:

``` python
raw = "00123"
restored = str(int(raw))

print(restored)  # "123"
```

Do not assume:

``` text
A → B → A
```

reconstructs the original.

Likewise, normalization is not automatically idempotent. Define and test
round-trip or idempotence requirements explicitly.

------------------------------------------------------------------------

### 1.16.39 Unicode, Files, and Binary Protocols

Encoding, decoding, and Unicode normalization are separate operations.

``` python
payload = text.encode("utf-8")
text = payload.decode("utf-8")
```

Open text files with an explicit encoding:

``` python
with open("config.txt", "r", encoding="utf-8") as handle:
    text = handle.read()
```

Binary protocols should use the protocol's binary decoding rules rather
than being arbitrarily decoded as text.

------------------------------------------------------------------------

### 1.16.40 Production Configuration Example

``` python
from dataclasses import dataclass
import os

def parse_bool(text: str) -> bool:
    token = text.strip().lower()

    if token in {"true", "1", "yes", "on"}:
        return True
    if token in {"false", "0", "no", "off"}:
        return False

    raise ValueError("invalid Boolean token")

@dataclass(frozen=True)
class ServiceConfig:
    workers: int
    timeout_seconds: float
    debug: bool

def load_config() -> ServiceConfig:
    raw_workers = os.getenv("WORKERS")
    raw_timeout = os.getenv("TIMEOUT_SECONDS")
    raw_debug = os.getenv("DEBUG", "false")

    workers = 4 if raw_workers is None else int(raw_workers)
    timeout = 30.0 if raw_timeout is None else float(raw_timeout)
    debug = parse_bool(raw_debug)

    if not 1 <= workers <= 64:
        raise ValueError("WORKERS must be between 1 and 64")
    if timeout <= 0:
        raise ValueError("TIMEOUT_SECONDS must be positive")

    return ServiceConfig(workers, timeout, debug)
```

This separates defaults, conversion, validation, and canonical
representation.

### 1.16.41 Optional Value Example

``` python
def parse_optional_port(raw: str | None) -> int | None:
    if raw is None:
        return None

    port = int(raw)

    if not 1 <= port <= 65535:
        raise ValueError("port must be between 1 and 65535")

    return port
```

The states remain distinct:

``` text
missing         → None
valid present   → int
invalid present → exception
```

### 1.16.42 Duplicate-Key-Safe Mapping Conversion

If duplicate configuration keys are invalid:

``` python
def pairs_to_dict(pairs):
    result = {}

    for key, value in pairs:
        if key in result:
            raise ValueError(f"duplicate key: {key!r}")
        result[key] = value

    return result
```

Validate before a normal `dict(pairs)` construction can erase evidence
of the duplicate.

### 1.16.43 Common Mistakes

1.  Parsing `"false"` with `bool()`.
2.  Treating `int()` as a rounding operation.
3.  Converting identifiers to numbers because they contain digits.
4.  Silently defaulting malformed present configuration.
5.  Treating `str()` as machine serialization.
6.  Assuming collection conversion validates element types.
7.  Converting `None` into the literal string `"None"`.
8.  Materializing unbounded iterables.
9.  Accepting `bool` as an integer quantity when the domain forbids it.
10. Using `eval()` as a parser.
11. Repeatedly converting the same raw value in business logic.
12. Logging raw malformed input without redaction or size controls.
13. Retrying deterministic parsing failures.
14. Assuming shallow conversion creates independent nested state.
15. Broadening API contracts through undocumented coercion.

------------------------------------------------------------------------

### 1.16.44 Troubleshooting Conversion Failures

Investigate in this order:

1.  Identify the boundary: environment, CLI, HTTP, database, message,
    file, or SDK.
2.  Inspect the actual runtime type.
3.  Inspect a safe, redacted representation when necessary.
4.  Confirm the accepted external representation.
5.  Reproduce the smallest conversion independently.
6.  Check domain validation separately.
7.  Look for upstream schema or contract changes.
8.  Check whether large inputs are creating CPU, memory, or latency
    pressure.
9.  Confirm whether the failure is deterministic or transient.
10. Verify that logs and metrics expose the failure without leaking
    data.

------------------------------------------------------------------------

### 1.16.45 Production Engineering Rules

1.  Convert at explicit system boundaries.
2.  Separate conversion from domain validation.
3.  Preserve `None` when absence is meaningful.
4.  Do not parse textual Booleans with `bool()`.
5.  Do not use `int()` when the requirement is rounding.
6.  Use decimal conversion for exact decimal domains.
7.  Treat encoding and decoding as protocol operations.
8.  Do not treat `str()` as a serialization format.
9.  Preserve identifiers as text when representation matters.
10. Define strict versus coercive parsing as part of the interface
    contract.
11. Reject malformed present values rather than silently defaulting
    them.
12. Apply range, size, depth, and resource limits.
13. Treat custom conversion methods as executable type-defined behavior.
14. Keep sensitive values out of diagnostics.
15. Use bounded metrics for conversion failures.
16. Do not retry deterministic malformed input indefinitely.
17. Normalize once into canonical internal types.
18. Test lossy and round-trip conversions.
19. Understand copy and materialization behavior.
20. Never use `eval()` as a general parser for untrusted input.

### 1.16.49 Quick Reference

  Requirement                     Preferred approach
  ------------------------------- -----------------------------
  text integer                    `int(raw)`
  text float                      `float(raw)`
  exact decimal                   `Decimal(raw)`
  textual Boolean                 explicit token parser
  truth-value testing             `bool(value)`
  display text                    `str(value)` or formatting
  text to bytes                   `text.encode(encoding)`
  bytes to text                   `payload.decode(encoding)`
  iterable to list                `list(iterable)`
  iterable to tuple               `tuple(iterable)`
  unique set semantics            `set(iterable)`
  immutable set semantics         `frozenset(iterable)`
  key-value pairs                 `dict(pairs)`

  strict machine API              require schema-native types
  untrusted Python-looking text   never use `eval()`

### 1.16.50 Key Takeaways

-   Conversion changes representation; validation decides domain
    acceptability.
-   Python performs limited numeric coercion but does not generally
    guess conversions between unrelated representations.
-   `int()` truncates finite floats toward zero and is not a rounding
    function.
-   `bool()` performs truth-value testing and is not a textual Boolean
    parser.
-   `str()` is textual representation, not general serialization.
-   Text/byte conversion requires an encoding contract.
-   Collection conversion can affect duplicates, memory, copying, and
    failure timing.
-   Lossy conversion must be intentional.
-   `None`, empty, zero, and `False` can represent different domain
    states.
-   Strict versus coercive conversion is an interface-design decision.
-   Normalize external representations once at the owning boundary.
-   Apply domain and resource limits to external input.
-   Conversion failures should be observable without leaking sensitive
    data.
-   Deterministic malformed input should not cause retry storms.
-   Canonical internal types reduce repeated coercion and ambiguity.

> **Central engineering principle:** Convert external representations
> into explicit canonical domain types at controlled boundaries,
> validate them before business use, and never let convenient coercion
> erase distinctions that matter to correctness, security, or
> operations.
