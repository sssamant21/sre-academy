# Chapter 1 --- Python Fundamentals and Development Environment

## 1.17 --- Input and Output

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   distinguish program input/output from persistence, serialization,
    and logging;
-   use `input()`, `print()`, formatting, and file objects correctly;
-   understand standard input, standard output, and standard error;
-   work safely with text and binary streams;
-   choose explicit encodings and newline behavior for files;
-   use context managers to manage I/O resources;
-   recognize buffering, flushing, partial-write, and broken-pipe
    concerns;
-   design production I/O boundaries with validation, observability,
    security, and failure handling.

------------------------------------------------------------------------

### 1.17.1 What Input and Output Mean

Input is data entering a program. Output is data leaving it.

Typical input sources include:

-   keyboard or terminal input;
-   files;
-   pipes;
-   environment-derived streams;
-   subprocess output;
-   network clients and APIs;
-   database drivers;
-   message consumers.

Typical output destinations include:

-   terminals;
-   files;
-   pipes;
-   logs;
-   subprocess input;
-   network services;
-   databases;
-   message producers.

At a system boundary, raw I/O should normally be followed by parsing and
validation before the value reaches business logic.

``` text
external source
      ↓
     I/O
      ↓
decode / parse
      ↓
validate
      ↓
canonical domain value
      ↓
business logic
```

The reverse path should intentionally format, serialize, encode, and
write the result required by the destination contract.

------------------------------------------------------------------------

### 1.17.2 Standard Streams

Command-line programs conventionally have three standard streams:

``` text
stdin   → standard input
stdout  → standard output
stderr  → standard error
```

Python exposes them through `sys`:

``` python
import sys

sys.stdin
sys.stdout
sys.stderr
```

These are stream objects rather than special syntax.

A program can therefore receive input from a terminal or a pipe without
its business logic needing to know which one supplied the bytes or text.

------------------------------------------------------------------------

### 1.17.3 Reading Interactive Input with `input()`

`input()` reads a line of text from standard input:

``` python
name = input("Name: ")
print(f"Hello, {name}")
```

The returned value is a string.

``` python
workers = int(input("Workers: "))
```

Conversion can fail:

``` python
try:
    workers = int(input("Workers: "))
except ValueError:
    print("Workers must be an integer.")
```

For production services, interactive prompting is usually inappropriate.
Configuration, APIs, files, or orchestration interfaces are generally
better automation boundaries.

------------------------------------------------------------------------

`input()` removes the trailing newline from the line it reads. If EOF is
reached before data is read, it raises `EOFError`.

---

### 1.17.4 Prompts and Non-Interactive Execution

A command can run:

``` text
interactively
from a pipeline
under a scheduler
inside a container
under systemd
in CI/CD
```

Do not assume a human is attached to standard input.

A production command should define what happens when required input is
absent or standard input is closed.

------------------------------------------------------------------------

### 1.17.5 Basic Output with `print()`

``` python
print("service started")
print("workers:", 4)
```

`print()` converts its objects to text and writes them to a text stream.

Useful parameters include:

``` python
print("a", "b", "c", sep=",")
print("done", end="\n")
```

A destination can be selected with `file=`:

``` python
import sys

print("fatal configuration error", file=sys.stderr)
```

------------------------------------------------------------------------

### 1.17.6 `stdout` Versus `stderr`

Separate normal program output from diagnostics.

``` python
import sys

print('{"status":"ok"}')
print("warning: cache unavailable", file=sys.stderr)
```

This matters in pipelines:

``` text
program stdout → downstream parser
program stderr → operator diagnostics
```

Mixing warnings into machine-readable standard output can corrupt the
downstream protocol.

------------------------------------------------------------------------

For automation-facing CLIs, document the channel contract explicitly. If the
`stdout` contract is machine-readable, keep progress messages, warnings, and
operator diagnostics on `stderr`, and keep exit-code meanings stable across
releases.

---

### 1.17.7 Formatting Output

Python supports several formatting approaches.

F-strings are usually clear for application code:

``` python
host = "db01"
port = 5432

message = f"connecting to {host}:{port}"
```

Formatting controls presentation:

``` python
latency_ms = 12.34567
print(f"latency_ms={latency_ms:.2f}")
```

Formatting is not the same as serialization. Machine interfaces should
use the format required by their protocol.

------------------------------------------------------------------------

### 1.17.8 `repr()` and Debug Representations

`repr()` produces a representation intended primarily for debugging or
developer-oriented inspection:

``` python
value = "line1\nline2"
print(repr(value))
```

Do not assume `repr()` is:

-   a stable wire format;
-   safe for secrets;
-   bounded in size;
-   guaranteed to be machine-parseable.

Custom objects can define their own representation behavior.

------------------------------------------------------------------------

### 1.17.9 Structured Machine Output

If a command promises JSON, emit JSON rather than Python
representations:

``` python
import json

result = {
    "status": "ok",
    "replicas": 3,
}

print(json.dumps(result))
```

Keep human diagnostics on `stderr` if `stdout` is reserved for the
machine contract.

------------------------------------------------------------------------

### 1.17.10 Opening Files

Use `open()` to create a file object:

``` python
with open("config.txt", "r", encoding="utf-8") as handle:
    content = handle.read()
```

Common modes include:

``` text
r   read
w   write, truncating an existing file
a   append
x   exclusive creation
b   binary mode modifier
t   text mode modifier
+   updating: reading and writing
```

File mode is part of the safety contract. Opening an existing file with
`"w"` can destroy its previous contents immediately.

------------------------------------------------------------------------

### 1.17.11 Context Managers

Prefer context managers for owned file resources:

``` python
with open("report.txt", "w", encoding="utf-8") as handle:
    handle.write("ready\n")
```

The file is closed when the block exits, including when an exception
propagates.

Explicit lifecycle management prevents leaked descriptors and makes
ownership clear.

------------------------------------------------------------------------

### 1.17.12 Text Mode and Binary Mode

Text mode works with `str`:

``` python
with open("notes.txt", "r", encoding="utf-8") as handle:
    text = handle.read()
```

Binary mode works with `bytes`:

``` python
with open("payload.bin", "rb") as handle:
    payload = handle.read()
```

Do not arbitrarily decode a binary protocol as text. Use the protocol's
defined decoding rules.

------------------------------------------------------------------------

### 1.17.13 Encoding

Text must be encoded into bytes for storage or transmission.

``` python
text = "database ready"
payload = text.encode("utf-8")
```

Bytes are decoded into text:

``` python
restored = payload.decode("utf-8")
```

For persistent or interoperable text files, specify the intended
encoding explicitly:

``` python
with open("data.txt", "w", encoding="utf-8") as handle:
    handle.write("ready\n")
```

Do not let an unspecified platform default become an accidental data
format.

------------------------------------------------------------------------

### 1.17.14 Encoding Errors

Decoding invalid bytes can raise `UnicodeDecodeError`; encoding text
into an incompatible encoding can raise `UnicodeEncodeError`.

``` python
payload.decode("utf-8")
```

Do not automatically suppress invalid data with a permissive error
policy. Choose error handling according to the data contract.

Silent replacement can hide upstream corruption.

------------------------------------------------------------------------

### 1.17.15 Newline Handling

Text files can encounter different newline conventions across systems.

Python text I/O supports newline translation and configurable newline
behavior.

For application-owned portable text files, define the format
intentionally rather than depending on undocumented platform behavior.

For formats such as CSV, follow the library's documented file-opening
requirements.

------------------------------------------------------------------------

Python text I/O supports universal-newline processing and configurable
newline translation through the `newline` argument. The precise behavior
depends on whether `newline` is `None`, an empty string, or a specific line
terminator.

---

### 1.17.16 Reading an Entire File

``` python
with open("small.txt", "r", encoding="utf-8") as handle:
    content = handle.read()
```

This is simple but materializes the entire remaining file in memory.

Use it only when the expected size is bounded and appropriate.

------------------------------------------------------------------------

### 1.17.17 Iterating Over a Text File

For large line-oriented files:

``` python
with open("events.log", "r", encoding="utf-8") as handle:
    for line in handle:
        process(line)
```

Iteration avoids loading the entire file at once.

The program still needs controls for:

-   maximum line size;
-   malformed records;
-   encoding failures;
-   partial processing;
-   downstream backpressure.

Streaming reduces memory pressure; it does not remove operational risk.

------------------------------------------------------------------------

### 1.17.18 `read()`, `readline()`, and `readlines()`

Examples:

``` python
handle.read()
handle.readline()
handle.readlines()
```

`readlines()` can materialize all remaining lines in memory.

Choose an API based on the size and access pattern of the data rather
than convenience alone.

------------------------------------------------------------------------

### 1.17.19 Writing Text

``` python
with open("status.txt", "w", encoding="utf-8") as handle:
    handle.write("healthy\n")
```

`write()` returns the number of characters written for text streams.

Multiple writes can make intent clearer:

``` python
with open("report.txt", "w", encoding="utf-8") as handle:
    handle.write("service=db\n")
    handle.write("status=healthy\n")
```

For structured formats, use a serializer rather than manually assembling
fragile syntax.

------------------------------------------------------------------------

### 1.17.20 Writing Binary Data

``` python
payload = b"\x00\x01\x02"

with open("payload.bin", "wb") as handle:
    handle.write(payload)
```

Binary mode avoids text encoding and newline translation.

Binary protocols should be produced by protocol-aware encoders or
libraries.

------------------------------------------------------------------------

### 1.17.21 Buffering

I/O is often buffered for efficiency.

A call that writes data at the Python layer does not necessarily mean
the data has already reached the final physical storage device or remote
consumer.

Buffering behavior depends on the stream and environment.

This distinction matters for:

-   interactive output;
-   subprocess pipelines;
-   crash-sensitive writes;
-   durability assumptions.

------------------------------------------------------------------------

### 1.17.22 Flushing

A flush asks a buffered stream to push buffered data to the next layer:

``` python
print("starting...", flush=True)
```

or:

``` python
handle.flush()
```

Flushing is not automatically equivalent to durable storage.

For filesystem durability requirements, the application must understand
the operating system and filesystem durability model rather than
treating `flush()` as a transaction guarantee.

------------------------------------------------------------------------

### 1.17.23 File Position and Seeking

Seekable files expose a current position.

``` python
with open("data.bin", "rb") as handle:
    header = handle.read(8)
    handle.seek(0)
    again = handle.read(8)
```

Not every stream is seekable. Pipes and some wrapped streams can be
forward-only.

Code intended for generic streams should not assume `seek()` is
available.

------------------------------------------------------------------------

### 1.17.24 Standard Input as a Stream

Instead of `input()`, stream-oriented tools can iterate over
`sys.stdin`:

``` python
import sys

for line in sys.stdin:
    process(line)
```

This works naturally with pipelines and redirected files.

Do not assume the stream is small.

------------------------------------------------------------------------

### 1.17.25 Standard Output as a Stream

``` python
import sys

sys.stdout.write("ready\n")
```

`print()` is usually more convenient for human-readable text, while
direct stream operations can be useful when an interface needs precise
behavior.

Do not close standard streams merely because your function did not
create them.

Resource ownership matters.

------------------------------------------------------------------------

### 1.17.26 End of File

Reads can encounter end-of-file rather than data.

For example:

``` python
line = handle.readline()

if line == "":
    print("EOF")
```

Interactive `input()` raises `EOFError` when it reaches EOF without
reading data.

Production commands should define EOF behavior rather than repeatedly
waiting for input that can never arrive.

------------------------------------------------------------------------

### 1.17.27 I/O Exceptions

I/O can fail because of:

-   missing files;
-   permission problems;
-   invalid paths;
-   closed streams;
-   broken pipes;
-   full filesystems;
-   quota limits;
-   device errors;
-   encoding problems;
-   network or remote-storage failures.

Catch exceptions only when the application can add useful policy or
context.

Avoid:

``` python
try:
    ...
except Exception:
    pass
```

Silent I/O failure can produce data loss while making the operation
appear successful.

------------------------------------------------------------------------

### 1.17.28 `OSError` and Related Exceptions

Many operating-system I/O failures surface through `OSError` or one of
its subclasses, such as:

``` text
FileNotFoundError
PermissionError
IsADirectoryError
NotADirectoryError
FileExistsError
BlockingIOError
BrokenPipeError
```

Handle the conditions your interface can meaningfully recover from.

Do not classify every `OSError` as transient.

------------------------------------------------------------------------

### 1.17.29 Broken Pipes

A command writing to a pipeline can discover that the downstream reader
has closed its end.

That can surface as `BrokenPipeError`.

A CLI should define its expected broken-pipe behavior. Avoid converting
a normal downstream termination into noisy repeated retries.

Pipeline semantics are different from durable-message delivery
semantics.

------------------------------------------------------------------------

### 1.17.30 Partial and Incremental I/O

Low-level and non-blocking I/O APIs can read or write less data than
requested.

High-level buffered file objects hide many of these details, but
production code using sockets, raw descriptors, subprocess pipes, or
non-blocking streams must follow the specific API's completion contract.

Never assume one low-level write equals complete delivery unless the API
guarantees it.

------------------------------------------------------------------------

For raw and other low-level I/O, a write can complete only partially and its
return value must be checked. Python's high-level buffered binary and text I/O
layers provide stronger retry behavior, while non-blocking I/O can still
signal that an operation would block. Follow the completion contract of the
specific stream API.

---

### 1.17.31 File Paths Are External Input

A path supplied by a user, request, archive, or message is untrusted
input.

Security-sensitive file handling should consider:

-   path traversal;
-   absolute versus relative paths;
-   symbolic links;
-   race conditions;
-   file ownership and permissions;
-   allowed root directories;
-   overwrite behavior.

Do not construct privileged paths from unvalidated input.

------------------------------------------------------------------------

### 1.17.32 Safe Output Replacement

Directly writing an important existing file with `"w"` can leave it
empty or partially written if the process fails.

A common replacement pattern is:

``` text
create temporary file in appropriate location
        ↓
write complete content
        ↓
flush as required by durability policy
        ↓
close
        ↓
atomically replace destination where platform/filesystem semantics support it
```

The exact durability and atomicity guarantees are platform-specific.

Do not call a workflow "atomic" without understanding the filesystem and
failure model.

------------------------------------------------------------------------

When replacing an existing production file, define the replacement file's
ownership, permissions, and metadata policy explicitly. A temporary file can
be created with different permissions from the destination, so successful
content replacement alone does not prove that the resulting security metadata
is correct.

---

When replacing an existing production file, explicitly define the replacement
file's ownership, permissions, and metadata policy. A temporary file can have
different permissions from the destination, so successful content replacement
alone does not prove that the resulting security metadata is correct.

---

### 1.17.33 Append Is Not a General Transaction Mechanism

Append mode is convenient for some workloads:

``` python
with open("events.txt", "a", encoding="utf-8") as handle:
    handle.write("event\n")
```

It does not by itself provide:

-   record transactions;
-   cross-process coordination;
-   corruption recovery;
-   exactly-once delivery;
-   durable distributed logging.

Use a storage system appropriate to the required guarantees.

------------------------------------------------------------------------

### 1.17.34 Temporary Files

Use the standard library's temporary-file facilities rather than
inventing predictable names:

``` python
import tempfile

with tempfile.TemporaryFile(mode="w+t", encoding="utf-8") as handle:
    handle.write("temporary data")
    handle.seek(0)
    print(handle.read())
```

Temporary-file behavior and lifecycle differ across platforms and APIs.

Security-sensitive code should not create predictable temporary paths in
shared writable directories.

------------------------------------------------------------------------

### 1.17.35 CSV Output

Use the `csv` module for CSV rather than manual delimiter joining:

``` python
import csv

with open("report.csv", "w", encoding="utf-8", newline="") as handle:
    writer = csv.writer(handle)
    writer.writerow(["service", "status"])
    writer.writerow(["database", "healthy"])
```

Correct quoting and newline behavior are format concerns best delegated
to the library.

------------------------------------------------------------------------

### 1.17.36 JSON Files

``` python
import json

payload = {
    "service": "database",
    "healthy": True,
}

with open("status.json", "w", encoding="utf-8") as handle:
    json.dump(payload, handle)
```

Reading:

``` python
with open("status.json", "r", encoding="utf-8") as handle:
    payload = json.load(handle)
```

Parsing valid JSON does not prove the resulting object satisfies the
application schema. Validate the domain after deserialization.

------------------------------------------------------------------------

### 1.17.37 Logging Is Not `print()` with a Timestamp

Production services should normally use a logging framework for
operational events.

``` python
import logging

logger = logging.getLogger(__name__)
logger.info("service started")
```

Logging provides concepts such as:

-   severity;
-   handlers;
-   formatting;
-   routing;
-   filtering;
-   structured context.

Use `print()` for an intentional program-output contract, not as an
automatic substitute for production logging.

------------------------------------------------------------------------

### 1.17.38 Keep Secrets Out of Output

Never assume a value is safe to emit merely because it is available.

Sensitive examples include:

-   passwords;
-   API tokens;
-   private keys;
-   session secrets;
-   connection strings containing credentials;
-   protected personal or business data.

Redact or omit sensitive fields before formatting, logging, or writing
them.

------------------------------------------------------------------------

### 1.17.39 Output Size Is a Resource Concern

Unbounded output can:

-   fill disks;
-   exhaust log quotas;
-   block pipes;
-   increase network costs;
-   overwhelm downstream parsers;
-   create memory pressure when buffered.

Apply size, rate, retention, and rotation policies at the appropriate
layer.

------------------------------------------------------------------------

### 1.17.40 Input Size Is a Resource Concern

Do not treat syntactically valid input as operationally safe.

Examples include:

-   a multi-gigabyte text file;
-   one enormous line;
-   deeply nested JSON;
-   an unexpectedly large binary payload;
-   an endless stream.

Enforce limits appropriate to the interface before or while consuming
data.

------------------------------------------------------------------------

### 1.17.41 Timeouts and Blocking I/O

Some I/O operations can block for an unbounded or unexpectedly long
time.

Files, pipes, subprocesses, sockets, remote filesystems, and service
clients have different timeout models.

Where latency bounds matter, use APIs that support the required timeout,
cancellation, or non-blocking behavior.

Do not invent retry loops around blocking operations without
understanding the underlying completion semantics.

------------------------------------------------------------------------

### 1.17.42 Backpressure

A producer can generate data faster than a consumer can accept it.

Backpressure can appear as:

-   blocked writes;
-   growing buffers;
-   memory growth;
-   queue accumulation;
-   increasing latency.

Production I/O design should define how producers react:

``` text
block
buffer within a bound
shed load
reject
persist elsewhere
apply flow control
```

Unbounded buffering merely moves the failure.

------------------------------------------------------------------------

### 1.17.43 Retry Policy

Retry only failures that are plausibly transient and only when replay is
safe.

Before retrying an output operation, ask:

``` text
Did the destination receive none, some, or all of the data?
Can the operation be repeated safely?
Is there an idempotency mechanism?
```

A timeout does not always prove that the remote side performed no work.

------------------------------------------------------------------------

### 1.17.44 Idempotency and Output

For external side effects, retry safety depends on the destination
contract.

Examples:

``` text
write temporary file then replace     → can support controlled replacement
HTTP request with idempotency key      → API-specific
database transaction                   → database-specific
message publish                        → broker/client semantics
```

Do not claim exactly-once behavior merely because application code
retries carefully.

------------------------------------------------------------------------

### 1.17.45 Observability

Useful I/O telemetry can include:

``` text
io_operations_total{operation="read",result="success"}
io_operations_total{operation="write",result="error"}
io_bytes_total{direction="read"}
io_bytes_total{direction="write"}
io_operation_duration_seconds
```

Keep metric dimensions bounded.

Logs can record:

-   operation type;
-   safe resource category;
-   bounded error classification;
-   duration;
-   byte count when appropriate.

Avoid raw payloads, secrets, and high-cardinality identifiers unless
explicitly required and safely governed.

------------------------------------------------------------------------

Do not place raw paths, payload fragments, credentials, customer identifiers,
or unbounded exception text into metric labels. For logs, record only the
minimum safe resource identity needed for diagnosis and apply the system's
redaction and retention policy.

---

### 1.17.46 File Descriptor Ownership

A function should know whether it owns a stream.

If a function opens a file, it usually owns closing it.

If a caller passes a stream:

``` python
def write_report(handle):
    handle.write("ready\n")
```

the function should not normally close it unless that ownership transfer
is part of the API contract.

This principle also applies to standard streams, sockets, database
connections, and other I/O resources.

------------------------------------------------------------------------

### 1.17.47 Dependency Injection with File-Like Objects

Accepting file-like objects can improve testability:

``` python
def write_status(handle, status: str) -> None:
    handle.write(f"status={status}\n")
```

Test with an in-memory stream:

``` python
from io import StringIO

buffer = StringIO()
write_status(buffer, "healthy")

assert buffer.getvalue() == "status=healthy\n"
```

This separates formatting logic from filesystem access.

------------------------------------------------------------------------

### 1.17.48 In-Memory Text Streams

`io.StringIO` provides a text stream in memory:

``` python
from io import StringIO

stream = StringIO()
stream.write("hello")
stream.seek(0)

assert stream.read() == "hello"
```

It is useful for testing and temporary text processing, but large
in-memory streams still consume memory.

------------------------------------------------------------------------

### 1.17.49 In-Memory Binary Streams

`io.BytesIO` provides an in-memory binary stream:

``` python
from io import BytesIO

stream = BytesIO()
stream.write(b"\x01\x02")
stream.seek(0)

assert stream.read() == b"\x01\x02"
```

Use text or binary stream types according to the contract.

------------------------------------------------------------------------

### 1.17.50 Separating I/O from Business Logic

Avoid embedding every concern in one function:

``` python
def process_file(path):
    ...
```

Prefer layers:

``` text
open/read
   ↓
parse
   ↓
validate
   ↓
domain operation
   ↓
format/serialize
   ↓
write
```

This makes each stage easier to test and makes failure ownership
clearer.

------------------------------------------------------------------------

### 1.17.51 Example: Safe Configuration Reader

``` python
from pathlib import Path

def read_worker_count(path: Path) -> int:
    raw = path.read_text(encoding="utf-8").strip()
    workers = int(raw)

    if not 1 <= workers <= 64:
        raise ValueError("worker count must be between 1 and 64")

    return workers
```

The steps are explicit:

``` text
read text
→ normalize representation
→ convert
→ validate
→ return canonical int
```

Production callers can add policy for missing files, permissions, and
startup failure.

------------------------------------------------------------------------

### 1.17.52 Example: Machine-Readable CLI Output

``` python
import json
import sys

def emit_result(result: dict) -> None:
    json.dump(result, sys.stdout)
    sys.stdout.write("\n")

def emit_error(message: str) -> None:
    print(message, file=sys.stderr)
```

This preserves `stdout` for the machine contract and `stderr` for
diagnostics.

Error messages still require redaction and bounded size.

------------------------------------------------------------------------

### 1.17.53 Example: Streaming Line Processor

``` python
from collections.abc import Iterable, Iterator

def normalize_lines(lines: Iterable[str]) -> Iterator[str]:
    for line in lines:
        value = line.strip()

        if not value:
            continue

        yield value
```

The function operates on an iterable rather than owning a file. The
caller can supply a file, standard input, or test data.

------------------------------------------------------------------------

### 1.17.54 Example: Bounded Line Input

For hostile or externally controlled files, a line-oriented application
may need an explicit maximum record size rather than assuming every line
is safe.

The exact implementation depends on the stream API and whether the
system must reject, truncate, quarantine, or stream oversized records.

Do not silently truncate records unless the interface explicitly defines
that behavior.

------------------------------------------------------------------------

### 1.17.55 Example: JSON Read and Validation Boundary

``` python
import json
from pathlib import Path

def load_config(path: Path) -> dict:
    with path.open("r", encoding="utf-8") as handle:
        payload = json.load(handle)

    if not isinstance(payload, dict):
        raise ValueError("configuration root must be an object")

    return payload
```

Deserialization and domain validation remain separate.

A real production schema should validate required fields, types, ranges,
and cross-field invariants.

------------------------------------------------------------------------

### 1.17.56 Example: Controlled File Replacement

A simplified same-filesystem replacement pattern can use a temporary
file and `os.replace()`.

The production implementation must additionally define:

-   destination permissions;
-   temporary-file location;
-   cleanup behavior;
-   crash behavior;
-   durability requirements;
-   concurrent-writer policy;
-   filesystem assumptions.

Atomic namespace replacement and durable persistence are different
guarantees.

------------------------------------------------------------------------

For `os.replace()`, Python documents a successful replacement as atomic on
POSIX. The operation can fail when source and destination are on different
filesystems. This namespace atomicity is distinct from durable persistence of
file contents and directory metadata.

---

### 1.17.57 Example: Output Contract for Automation

A useful command contract can define:

``` text
stdout     machine-readable result
stderr     diagnostics
exit code  success/failure category
```

For example:

``` python
import json
import sys

def main() -> int:
    try:
        result = {"status": "healthy"}
        print(json.dumps(result))
        return 0
    except ValueError:
        print("invalid input", file=sys.stderr)
        return 2

if __name__ == "__main__":
    raise SystemExit(main())
```

Automation becomes more reliable when each channel has an explicit
purpose.

------------------------------------------------------------------------

### 1.17.58 Common Mistakes

1.  Using `input()` in a service that must run unattended.
2.  Mixing diagnostics into machine-readable `stdout`.
3.  Using `print()` as the only production logging mechanism.
4.  Opening an important existing file with `"w"` without considering
    failure.
5.  Omitting the encoding for an interoperable text format.
6.  Reading an unbounded file entirely into memory.
7.  Assuming `flush()` means durable storage.
8.  Assuming every stream supports seeking.
9.  Ignoring EOF behavior.
10. Swallowing I/O exceptions.
11. Treating every `OSError` as retryable.
12. Assuming one low-level write guarantees full delivery.
13. Trusting externally supplied paths.
14. Logging secrets or raw payloads.
15. Allowing unbounded output or buffering.
16. Retrying ambiguous side effects without idempotency.
17. Closing a stream owned by the caller.
18. Treating append mode as a transaction system.
19. Assuming JSON parsing performs application validation.

### 1.17.59 Troubleshooting I/O Problems

1.  Identify the source and destination.

3.  Confirm encoding and newline expectations.
4.  Check file mode and resource ownership.
5.  Inspect permissions, path, capacity, and quota.
6.  Determine whether EOF or a broken pipe is expected.
7.  Check whether buffering delays visible output.
8.  Determine whether the operation is blocking or timing out.
9.  Check input/output size and backpressure.
10. Separate parsing errors from transport errors.
11. Determine whether partial side effects may already exist.
12. Verify retry safety and idempotency.
13. Inspect bounded metrics and redacted diagnostics.
14. Reproduce with the smallest safe input.
15. Verify platform/filesystem assumptions when atomicity or durability

Opening an existing file with `"w"` truncates it, so a failure after

### 1.17.65 Key Takeaways

-   Input and output are system boundaries, not merely convenience
    functions.
-   `stdin`, `stdout`, and `stderr` have distinct operational roles.
-   `input()` returns text and is mainly appropriate for interactive
    programs.
-   Machine-readable `stdout` should not be polluted with diagnostics.
-   Text and binary streams have different contracts.
-   Explicit encoding prevents platform defaults from becoming
    accidental data formats.
-   Context managers make owned-resource lifecycle explicit.
-   Large inputs and outputs require bounds and streaming strategies.
-   Buffer flushing is not automatically durable persistence.
-   EOF, broken pipes, partial I/O, blocking, and backpressure are
    normal I/O concerns.
-   Paths, payloads, and output destinations can be security boundaries.
-   Retry safety depends on whether side effects can be replayed safely.
-   Logging, serialization, formatting, and program output are related
    but distinct responsibilities.
-   File replacement atomicity and storage durability are different
    guarantees.
-   Production I/O should be observable without leaking sensitive data.

> **Central engineering principle:** Treat every I/O boundary as an
> explicit contract: define representation, ownership, limits, failure
> behavior, security, observability, and delivery guarantees before data
> crosses it.
