# Chapter 1 --- Python Fundamentals and Development Environment

## 1.18 --- Comments and Documentation

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   use comments to explain intent, constraints, and non-obvious
    decisions;
-   distinguish comments, docstrings, API documentation, runbooks, and
    architecture records;
-   write useful module, class, function, and method docstrings;
-   document public contracts, exceptions, side effects, units,
    ownership, and operational assumptions;
-   avoid stale, redundant, misleading, and sensitive documentation;
-   maintain documentation as part of production engineering
    reliability.

------------------------------------------------------------------------

### 1.18.1 Why Documentation Matters

Source code tells Python what to execute. Documentation tells
developers, reviewers, operators, and users what they need to know to
use and change the system safely.

Useful documentation communicates purpose, assumptions, invariants,
units, failure behavior, side effects, compatibility constraints,
operational hazards, and the reasons behind non-obvious engineering
decisions.

A system can be technically correct and still be operationally dangerous
when its important constraints are undocumented.

### 1.18.2 Comments Versus Documentation

A Python comment begins with `#`:

``` python
# Retry only failures classified as transient.
```

Documentation is broader and can include comments, docstrings, README
files, API references, architecture documents, runbooks, decision
records, examples, and release notes.

Put information where its audience and lifecycle can be managed rather
than forcing every explanation into source comments.

### 1.18.3 Explain Why, Not Merely What

Poor:

``` python
count += 1  # Add one.
```

Better:

``` python
count += 1  # Count only records successfully persisted.
```

Code already communicates implementation. Comments should add intent,
constraints, or reasoning that is not obvious from the code itself.

Python's lexical rules are precise: a comment begins with `#` when the
character is not inside a string literal and ends at the end of the physical
line. The comment is ignored by Python's syntax. A `#` inside a string is
ordinary string data.

Python's lexical rules are precise: a comment begins with `#` when that
character is not inside a string literal, and the comment extends to the end
of the physical line. A `#` inside a string is ordinary string data.

### 1.18.4 Comments Must Remain True

A stale comment can actively mislead:

``` python
# Retry three times.
for attempt in range(10):
    ...
```

When behavior changes, update or remove its documentation in the same
change.

### 1.18.5 Avoid Commented-Out Code

Do not preserve obsolete implementations as large comment blocks.
Version control already records history. Commented-out code becomes
stale, creates noise, and obscures the active implementation.

### 1.18.6 Actionable TODOs

Prefer:

``` python
# TODO(PROJ-1842): Remove v2 compatibility after all producers migrate to v3.
```

over:

``` python
# TODO: fix this
```

A useful TODO identifies the action, reason, tracking reference when
applicable, and removal condition.

### 1.18.7 Comments Are Not Enforcement

A comment cannot enforce an invariant:

``` python
# replicas must be positive
replicas = config["replicas"]
```

Use code:

``` python
if replicas < 1:
    raise ValueError("replicas must be positive")
```

Keep comments for the reason behind a rule when the reason is
non-obvious.

### 1.18.8 Security and Sensitive Information

Never place real passwords, tokens, private keys, credentials, customer
data, or other secrets in comments, docstrings, examples, or runbooks
that are not specifically controlled for that information.

Repositories, diffs, caches, generated documentation, and review systems
can retain documentation after source files change.

### 1.18.9 What a Docstring Is

A docstring is a string literal used to document a module, class,
function, method, or other supported object:

``` python
def calculate_total(items):
    """Return the total price of all items."""
```

Python can expose it through `__doc__` and documentation tools such as
`help()`.

For modules, functions, classes, and methods, the runtime docstring is the
string literal used as the first statement in the object's definition. That
string becomes the object's `__doc__` attribute. A string literal placed
arbitrarily later in a function body is not the function's runtime docstring.

### 1.18.10 Function Docstrings

``` python
def normalize_username(value: str) -> str:
    """Return a normalized username."""
    return value.strip().lower()
```

For non-trivial public functions, document caller-visible semantics such
as accepted inputs, units, return behavior, exceptions, mutation, side
effects, I/O, and relevant concurrency or security constraints.

### 1.18.11 Module and Class Docstrings

Module:

``` python
"""Utilities for validating application startup configuration."""
```

Class:

``` python
class RetryPolicy:
    """Define retry limits and backoff parameters for transient failures."""
```

Describe the abstraction and its contract. Avoid duplicating an entire
system architecture inside source docstrings.

### 1.18.12 One-Line and Multi-Line Docstrings

A concise callable can use:

``` python
def is_enabled() -> bool:
    """Return whether the feature is enabled."""
```

A richer contract can use:

``` python
def load_records(path):
    """Load validated records from path.

    The input must contain UTF-8 JSON Lines. Blank lines are ignored.
    Invalid records raise ValueError before they are returned.
    """
```

The summary should be meaningful and additional paragraphs should
describe information needed by callers.

For a multi-line docstring, the Python documentation and PEP 257 convention
use a concise summary line followed by a blank line and then the extended
description. One-line docstrings conventionally keep their closing triple
quotes on the same line.

For a multi-line docstring, Python's documented convention uses a concise
summary line, then a blank line, then the extended description. A one-line
docstring conventionally keeps its closing triple quotes on the same line.

### 1.18.13 Type Annotations and Documentation

Annotations and documentation complement each other:

``` python
def connect(host: str, port: int, timeout: float) -> Connection:
    """Open a connection using timeout seconds."""
```

The annotation communicates the Python type. The docstring communicates
that `timeout` is measured in seconds.

### 1.18.14 Document Units

Production interfaces should make units explicit.

Common sources of defects include:

-   seconds versus milliseconds;
-   bytes versus KiB/MiB/GiB;
-   percentages versus fractions;
-   UTC versus local time;
-   absolute versus relative quantities.

Place units close to the interface that consumes or returns the value.

### 1.18.15 Document Return and Absence Semantics

``` python
def find_user(user_id: str) -> User | None:
    """Return the user, or None when no matching user exists."""
```

Document sentinel values and special return states when callers must
distinguish them from failures.

### 1.18.16 Document Exceptions

``` python
def parse_port(raw: str) -> int:
    """Parse a TCP port.

    Raises:
        ValueError: If raw is not an integer from 1 through 65535.
    """
```

Document stable caller-visible failures rather than every theoretical
internal exception.

### 1.18.17 Document Side Effects and Mutation

Callers should know whether an operation writes files, changes a
database, sends messages, performs network I/O, changes process state,
acquires locks, or mutates caller-owned objects.

``` python
def normalize_in_place(values: list[str]) -> None:
    """Normalize each element of values in place."""
```

Mutation and side effects are part of the API contract.

### 1.18.18 Document Ownership and Lifecycle

``` python
def write_report(handle) -> None:
    """Write the report without closing the caller-owned stream."""
```

For resource-oriented APIs, clarify who opens, owns, closes, reuses, and
releases resources.

### 1.18.19 Document Idempotency and Retry Semantics

If an operation is safe to repeat, document the actual guarantee. Do not
claim idempotency unless all relevant externally visible side effects
satisfy it.

Retry documentation should distinguish deterministic failures from
failures that may be transient and should call out ambiguous completion
when relevant.

### 1.18.20 Document Time Semantics

Time-oriented APIs may need to specify timezone, awareness, precision,
accepted format, inclusive/exclusive boundaries, and clock source.

``` python
def expire_at(timestamp: datetime) -> None:
    """Schedule expiration at an aware UTC timestamp."""
```

### 1.18.21 Document Ordering and Concurrency

If callers depend on ordering, state whether order is guaranteed.

For stateful components, document relevant concurrency behavior such as
thread-safe, not thread-safe, concurrent-read safe, single-task
ownership, or external synchronization requirements.

Only promise guarantees the implementation and tests actually support.

### 1.18.22 Performance and Capacity Comments

Useful:

``` python
# Cap the batch to bound peak memory during deserialization.
MAX_BATCH_SIZE = 1000
```

Avoid unsupported claims such as:

``` python
# This always completes in 5 ms.
```

Document workload and environment context for measured performance
claims.

### 1.18.23 Compatibility Workarounds

``` python
# COMPAT(PROJ-2110): Keep v2 parsing until all producers use schema v3.
```

A compatibility comment should explain why the branch exists, who still
depends on it, and when it can be removed.

### 1.18.24 Algorithms and Invariants

For complex algorithms, explain the invariant or reasoning rather than
narrating every line:

``` python
# Move the lower bound only after validating the midpoint so all indices below
# low remain known-invalid.
```

For standard algorithms, a concise reference can be more maintainable
than a large embedded tutorial.

### 1.18.25 External Constraints

``` python
# Keep below the upstream proxy's 60-second idle timeout.
REQUEST_TIMEOUT_SECONDS = 55
```

Where practical, reference the owning specification, configuration,
issue, or architecture decision. Preserve enough context that the
constraint remains understandable if a link changes.

### 1.18.26 `help()` and `__doc__`

Python's built-in `help()` can display documentation:

``` python
help(str)
help(my_function)
```

Docstrings can also be inspected:

``` python
print(my_function.__doc__)
```

Docstrings are runtime-visible documentation data. Do not use them as an
application data store or place secrets in them.

PEP 257 also recognizes *attribute docstrings* and *additional docstrings*
that documentation-processing tools may extract. These extra string literals
are not assigned to an object's `__doc__` attribute by the bytecode compiler,
so do not describe them as ordinary runtime docstrings.

### 1.18.27 Documentation Conventions

Projects commonly standardize docstring formatting for parameters,
returns, exceptions, examples, attributes, and notes.

Consistency and tooling compatibility matter more than mixing multiple
styles arbitrarily.

PEP 257 defines widely used Python docstring conventions. A project's
adopted standard remains the operational source of truth.

### 1.18.28 Public Versus Internal APIs

Public interfaces generally need stronger documentation than tiny local
helpers.

Public contracts may need purpose, parameters, units, return semantics,
exceptions, side effects, compatibility, concurrency behavior, and
examples.

Documentation volume should follow risk and audience rather than a
quota.

### 1.18.29 Do Not Document the Obvious

A docstring that merely repeats a clear function name and signature may
add little value.

Clear names, types, and structure are documentation too. Use prose for
information they cannot express effectively.

### 1.18.30 Refactor Instead of Over-Commenting

If a block requires many comments to explain basic control flow, improve
the structure.

Prefer:

``` python
workers = load_worker_count(config)
```

over a long sequence of comments narrating parsing, validation, and
default selection.

### 1.18.31 Examples in Documentation

Examples should use safe placeholder data, match the current interface,
avoid undocumented behavior, and be tested when practical.

Stale examples are dangerous because users often copy them directly.

### 1.18.32 Documentation Tests

Python's `doctest` module can execute suitably formatted interactive
examples from docstrings or text files.

Executable examples can reduce drift but do not replace a complete test
strategy.

`doctest` recognizes interactive-style examples according to its expected
syntax and compares their actual output with the documented expected output.
It can inspect examples in docstrings and in suitably structured text files;
it does not automatically make every fenced documentation example executable.

### 1.18.33 Static Analysis and Documentation Tooling

Linters and documentation generators can detect missing or malformed
documentation, broken references, and style inconsistencies.

Automation can enforce structure. It cannot prove that prose is
truthful, complete, safe, or operationally useful.

### 1.18.34 Documentation in Code Review

Review documentation whenever behavior changes.

Ask whether the change modified:

-   an interface contract;
-   an exception;
-   a unit or default;
-   ownership;
-   side effects;
-   retry behavior;
-   compatibility;
-   examples;
-   operator procedures.

Documentation drift is a review defect.

### 1.18.35 Documentation and Version Control

Versioning documentation with code provides reviewable history,
attribution, release-specific context, and easier rollback analysis.

External operational documentation can live elsewhere, but it still
needs ownership, versioning, and a clear relationship to the system
version.

Production documentation should identify an authoritative source when the
same operational fact appears in multiple places. For example, a generated API
reference may be authoritative for a schema while a runbook is authoritative
for an operator procedure. If duplicated documentation cannot be eliminated,
define which source wins when the copies disagree and make derived copies
traceable to it.

Treat conflicting documentation as an operational defect. Operators should not
have to guess which of two incompatible procedures is current.

### 1.18.36 Documentation Ownership and Freshness

Important documents need ownership.

Freshness should be supported by evidence such as code review, tested
examples, link checking, release review, or scheduled runbook
validation.

A recent "last updated" date alone does not prove correctness.

### 1.18.37 Production Runbooks

A production runbook should normally define:

``` text
purpose
scope
prerequisites
permissions
prechecks
procedure
verification
rollback
failure handling
stop conditions
escalation
observability
```

Critical recovery procedures should not exist only as source comments.

### 1.18.38 Architecture Decision Records

Architecture decision records preserve context, decisions, alternatives,
tradeoffs, consequences, and status.

They are often a better home for system-level reasoning than multi-page
source comments.

### 1.18.39 API Documentation

API documentation should focus on externally observable behavior:

``` text
request and response schemas
authentication and authorization
error semantics
pagination
rate limits
idempotency
versioning
compatibility
examples
```

Do not expose implementation details as guarantees unless they are
deliberately part of the contract.

### 1.18.40 Configuration Documentation

Production configuration should document key name, type, default, range,
unit, reload/restart behavior, scope, precedence, security
classification, and deprecation state where applicable.

Example:

``` text
REQUEST_TIMEOUT_SECONDS
type: integer
default: 30
range: 1–55
unit: seconds
reload: restart required
```

The implementation should enforce documented constraints.

### 1.18.41 Error Documentation

Actionable error documentation explains the condition, meaning, retry
safety, recommended action, and diagnostic location.

Do not expose sensitive internals merely to make an error more verbose.

### 1.18.42 Deprecation Documentation

When an interface is deprecated, document what is deprecated, its
replacement, migration path, deprecation version/date, and intended
removal version/date when known.

Use the project's warning and release-note mechanisms in addition to a
docstring for public interfaces.

Commands intended for production runbooks should be safe to copy only in
the context explicitly documented around them. Use placeholders for environment,
account, cluster, database, namespace, region, and resource identifiers rather
than embedding accidental production targets. For destructive commands, include
a precheck that proves the selected target and a verification step that confirms
the intended result.

Do not publish a command whose safety depends on an undocumented shell state,
working directory, cloud account, Kubernetes context, database session, or
implicit default.

### 1.18.43 Dangerous Operations

High-risk procedures such as truncation, credential rotation, failover,
schema migration, reindexing, and production restore require explicit
blast radius, prerequisites, rollback expectations, maintenance
requirements, verification, and stop conditions.

`# be careful` is not an operational control.

### 1.18.44 Performance and Concurrency Workarounds

For unusual optimization or concurrency code, document the observed
problem, the invariant that must remain true, where supporting evidence
lives, and when the workaround can be reconsidered.

Example:

``` python
# Lock order is always cache_lock -> index_lock to avoid lock-order inversion.
```

Support correctness-critical comments with tests, assertions, or
structural controls where practical.

### 1.18.45 Database and Distributed-System Documentation

Database code may need transaction-boundary, isolation, locking, and
retry assumptions.

Distributed-system documentation may need delivery semantics,
idempotency, ordering, timeouts, retry ownership, deduplication,
consistency, and failure domains.

Do not imply guarantees stronger than the underlying system provides.

### 1.18.46 Cloud and Kubernetes Documentation

Operational documentation can capture IAM permissions, namespaces,
resource limits, storage classes, cloud regions, failover behavior,
dependencies, secret ownership, and maintenance requirements.

Keep environment-specific values out of reusable library docstrings
unless they are genuinely part of the library contract.

### 1.18.47 Documentation and Observability

Runbooks should tell operators how to verify behavior using relevant
metrics, logs, traces, health checks, status endpoints, database
queries, queue depth, or error counters.

Avoid making a fragile dashboard URL the only description of the signal.

### 1.18.48 Documentation and Incident Response

After an incident, update documentation when the event reveals a missing
precheck, unsafe command, unclear rollback, undocumented dependency,
missing metric, or ambiguous escalation path.

The goal is to reduce recurrence and operator uncertainty.

For high-risk operational documentation, record enough metadata to support
controlled use: supported system/version, environment scope, owner, required
privilege level, validation evidence, and review trigger. A review trigger may
be a software upgrade, platform migration, incident finding, interface change,
or scheduled operational validation.

Do not treat a review date as an approval to execute an otherwise unverified
procedure. Execution still requires current prechecks and environment-specific
validation.

### 1.18.49 Documentation and Change Management

Production-change documentation may identify scope, owner, risk,
maintenance window, prechecks, implementation steps, verification,
rollback, and communication requirements.

The technical procedure should be reproducible and reviewable.

### 1.18.50 Documentation and Copyright

Technical documentation must respect copyright and licensing.

Do not copy substantial vendor documentation, books, articles, or
training material into a handbook merely because it is publicly
accessible.

Prefer original explanation, original examples, concise attribution
where needed, and links or references to authoritative sources.

### 1.18.51 Vendor Documentation as a Source

Use authoritative vendor documentation to verify version-specific
behavior.

A production handbook should distinguish:

``` text
vendor/language guarantee
documented platform behavior
local engineering policy
observed implementation behavior
```

Explain operational meaning in original language rather than lightly
rewriting source prose.

### 1.18.52 Source Review

Technical source review should ask:

1.  Is the source authoritative?
2.  Does it match the target version?
3.  Is the behavior guaranteed or merely observed?
4.  Is it platform-specific?
5.  Has it changed in recent releases?
6.  Is local policy being confused with vendor behavior?

Source quality is part of documentation quality.

### 1.18.53 Documentation Anti-Patterns

Avoid:

1.  comments that merely restate code;
2.  stale comments;
3.  commented-out code;
4.  unmanaged TODOs;
5.  secrets in comments or docstrings;
6.  undocumented units;
7.  undocumented side effects or mutation;
8.  unclear resource ownership;
9.  unsupported idempotency or concurrency claims;
10. implementation details presented as public guarantees;
11. giant source comments that belong in architecture documentation;
12. runbooks without verification or rollback;
13. stale examples;
14. duplicated documentation with no source of truth;
15. copied vendor prose;
16. documentation quotas that create meaningless docstrings;
17. critical documents with no owner or lifecycle.

### 1.18.54 Troubleshooting Documentation Problems

When documentation appears incorrect:

1.  identify the exact interface or behavior;
2.  inspect or reproduce the current implementation;
3.  determine the supported runtime/version;
4.  check authoritative sources;
5.  separate external guarantees from local policy;
6.  inspect tests and schemas;
7.  check relevant code history;
8.  identify the document owner;
9.  correct documentation and behavior together when required;
10. add tests or validation that reduce future drift;
11. remove obsolete duplicates;
12. verify examples;
13. review security and copyright implications;
14. publish through the normal review process.

### 1.18.55 Production Engineering Rules

1.  Comment intent and constraints, not obvious syntax.
2.  Keep comments synchronized with behavior.
3.  Delete dead commented-out code.
4.  Track actionable TODOs.
5.  Never place secrets in comments or docstrings.
6.  Enforce invariants in code.
7.  Document units at interface boundaries.
8.  Document meaningful return and absence semantics.
9.  Document stable caller-visible exceptions.
10. Document side effects, mutation, and ownership.
11. Document idempotency and retry semantics only when they are real.
12. State ordering and concurrency guarantees when callers depend on
    them.
13. Give compatibility workarounds an exit condition.
14. Keep public API documentation focused on externally visible
    behavior.
15. Test important examples when practical.
16. Review documentation in the same change as behavior.
17. Give operational documentation ownership and lifecycle.
18. Include verification and rollback in production runbooks.
19. Verify version-specific claims against authoritative sources.
20. Write original explanations rather than copying source material.

### 1.18.60 Key Takeaways

-   Comments should explain intent, constraints, and non-obvious
    reasoning.
-   Stale comments and examples can cause incorrect engineering
    decisions.
-   Docstrings document Python objects and can be exposed through
    `help()` and `__doc__`.
-   Type annotations do not communicate every semantic detail.
-   Units, exceptions, side effects, mutation, ownership, ordering,
    concurrency, retry behavior, and idempotency can be part of an
    interface contract.
-   Documentation belongs where its audience and lifecycle can be
    managed.
-   Production runbooks require prerequisites, verification, rollback,
    and failure handling.
-   Documentation must avoid secrets and unnecessary sensitive
    information.
-   Important documentation needs ownership, review, and freshness
    controls.
-   Authoritative sources should verify version-specific technical
    behavior.
-   Vendor guarantees and local policy should remain distinguishable.
-   Technical documentation should use original explanation and respect
    copyright.

> **Central engineering principle:** Document the contract and the
> reason: preserve the information a future developer or operator needs
> to use, change, and recover the system safely, and keep that
> information synchronized with the behavior it describes.
