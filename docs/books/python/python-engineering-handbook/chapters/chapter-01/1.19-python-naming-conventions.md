# Chapter 1 --- Python Fundamentals and Development Environment

## 1.19 --- Python Naming Conventions

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   choose Python names that communicate intent and domain meaning;
-   distinguish language rules from community naming conventions;
-   apply conventional naming styles to modules, packages, classes,
    functions, methods, variables, constants, exceptions, and internal
    interfaces;
-   understand the significance of leading and trailing underscores;
-   recognize Python special names and name-mangling behavior;
-   avoid shadowing built-ins and creating misleading identifiers;
-   design stable names for public APIs, configuration, observability,
    and production automation;
-   review naming as part of maintainability, compatibility, and
    operational safety.

------------------------------------------------------------------------

### 1.19.1 Why Naming Matters

Names are one of the primary interfaces between source code and its
readers.

Consider:

``` python
x = 30
```

versus:

``` python
request_timeout_seconds = 30
```

Both assignments are valid Python. The second communicates substantially
more meaning.

Good names help developers understand:

-   what a value represents;
-   what unit it uses;
-   whether an object is mutable;
-   what an operation does;
-   which abstraction owns a responsibility;
-   whether an interface is public or internal;
-   which domain concept the code represents.

Naming is therefore not cosmetic. It affects readability, review
quality, debugging, maintenance, and production safety.

------------------------------------------------------------------------

### 1.19.2 Syntax Rules Versus Naming Conventions

Python defines lexical rules that determine whether an identifier is
valid.

Engineering teams additionally use naming conventions to make valid
names consistent and understandable.

For example, both of these can be syntactically valid identifiers:

``` python
customer_count
CustomerCount
```

The appropriate form depends on what the name represents.

Do not confuse a style convention with a language requirement.

------------------------------------------------------------------------

### 1.19.3 Identifier Fundamentals

Python identifiers are names used for objects such as:

``` text
variables
functions
classes
modules
parameters
attributes
```

Simple examples:

``` python
user
retry_count
calculate_total
DatabaseConnection
```

Identifiers cannot be arbitrary punctuation or whitespace.

Exact lexical rules, Unicode behavior, normalization, and reserved-name
semantics should be treated as language-version-specific behavior and
verified against the Python language reference during source review.

------------------------------------------------------------------------

Python 3.14 names are case-sensitive and may contain ASCII letters,
underscores, digits after the first character, and qualifying non-ASCII
characters. Non-ASCII identifiers are validated using Python's XID-based rules
and are normalized to Unicode NFKC during parsing. Therefore visually distinct
source spellings can normalize to the same identifier.

For production code, valid Unicode syntax and project naming policy are separate
questions. A project can deliberately require a narrower identifier character
set for readability, interoperability, searchability, or security review.

### 1.19.4 Keywords Are Reserved

Python keywords cannot be used as ordinary identifiers:

``` python
# Invalid
class = "premium"
```

Use a meaningful alternative:

``` python
account_class = "premium"
```

When an external API or schema uses a Python keyword, adapt the local
Python name without weakening the external contract.

------------------------------------------------------------------------

Python also has *soft keywords*. In Python 3.14, `match`, `case`, and `_`
have special meaning in pattern-matching contexts, and `type` has special
meaning in a `type` statement. Outside the grammar contexts where they are soft
keywords, they can still behave as ordinary names.

Do not describe soft keywords as globally reserved identifiers.

### 1.19.5 Use Descriptive Names

Prefer names that communicate purpose:

``` python
retry_count = 3
database_url = load_database_url()
active_users = get_active_users()
```

Avoid vague names:

``` python
data
thing
value
obj
temp
stuff
```

Short generic names can be appropriate in narrow contexts, but they
should not force readers to reverse-engineer meaning.

------------------------------------------------------------------------

### 1.19.6 Name the Domain Concept

A strong name reflects the business or technical concept represented by
the object:

``` python
claim_id
invoice_total
replica_count
shard_size_bytes
request_deadline
```

This is more durable than naming variables after temporary
implementation details.

Prefer:

``` python
pending_events
```

over:

``` python
list2
```

------------------------------------------------------------------------

### 1.19.7 Include Units When They Matter

A name can make units explicit:

``` python
timeout_seconds
latency_ms
memory_bytes
retention_days
```

This reduces ambiguity at system boundaries.

Weak:

``` python
timeout = 5000
```

Clearer:

``` python
timeout_ms = 5000
```

Do not encode units redundantly when the surrounding type or abstraction
makes them impossible to misunderstand, but favor explicitness at
configuration, API, storage, and operational boundaries.

------------------------------------------------------------------------

### 1.19.8 Functions Should Usually Describe Actions

Functions commonly perform operations, so verb-oriented names are
useful:

``` python
load_config()
validate_request()
calculate_total()
publish_event()
close_connection()
```

A function name should help a caller predict its purpose.

Avoid:

``` python
process()
handle()
do_work()
run_thing()
```

unless the surrounding abstraction makes the operation genuinely clear.

------------------------------------------------------------------------

### 1.19.9 Predicate Names

Functions returning Boolean conditions should read naturally:

``` python
is_ready()
has_permission()
can_retry()
should_refresh()
```

Example:

``` python
if should_retry(error):
    retry_request()
```

The name makes the condition understandable without inspecting the
implementation.

------------------------------------------------------------------------

### 1.19.10 Avoid Misleading Predicate Names

Do not name a function as if it returns a Boolean when it performs a
major side effect:

``` python
def is_database_ready():
    restart_database()
    return True
```

A caller reasonably expects `is_database_ready()` to inspect state
rather than restart a service.

Names form expectations about behavior.

------------------------------------------------------------------------

### 1.19.11 Classes Usually Represent Concepts

Class names commonly use a noun or noun phrase:

``` python
RetryPolicy
DatabaseConnection
InvoiceProcessor
ClusterHealth
```

A class name should communicate the abstraction represented by its
instances.

Avoid names such as:

``` python
Manager
Helper
Utility
Processor
```

when they conceal rather than clarify responsibility.

Such suffixes are not inherently wrong, but the complete name should
still identify a coherent role.

------------------------------------------------------------------------

### 1.19.12 Exception Names

Exception classes should communicate the failure condition:

``` python
ConfigurationError
AuthenticationError
SchemaValidationError
RetryLimitExceeded
```

The `Error` suffix is conventional when the class represents an error.

Exception names are part of the diagnostic and API vocabulary of a
system, so choose them carefully.

------------------------------------------------------------------------

### 1.19.13 Module Names

Module names should be concise and descriptive:

``` text
config.py
validation.py
retry.py
serialization.py
```

Avoid filenames that reveal little about responsibility:

``` text
utils2.py
misc.py
stuff.py
common_new.py
```

A module named `utils.py` can become an uncontrolled collection of
unrelated functions. Prefer cohesive modules organized around
responsibilities.

------------------------------------------------------------------------

### 1.19.14 Package Names

Package names should communicate a stable namespace:

``` text
billing
observability
storage
authentication
```

Choose names that remain meaningful as implementation details evolve.

Avoid unnecessary abbreviations and names that collide confusingly with
standard-library or third-party packages.

------------------------------------------------------------------------

PEP 8 recommends short, all-lowercase module names; underscores may be
used when they improve module-name readability. Package names should likewise
be short and all lowercase, with underscores discouraged.

For CapWords names, PEP 8's stated acronym convention capitalizes all letters
of the acronym; for example, `HTTPServerError` rather than `HttpServerError`.
A project may choose another documented convention for its own code, but that
choice should not be presented as PEP 8's rule.

### 1.19.15 Variable Naming

Variables commonly use lowercase words separated by underscores:

``` python
request_id = "abc-123"
max_retries = 5
current_user = load_user()
```

The name should reflect what the value means at that point in the
program.

------------------------------------------------------------------------

### 1.19.16 Parameter Naming

Parameters are part of a callable interface:

``` python
def connect(host: str, port: int, timeout_seconds: float):
    ...
```

Use names that make calls understandable.

With keyword arguments:

``` python
connect(
    host="db.internal",
    port=5432,
    timeout_seconds=5.0,
)
```

parameter names can become part of the public API.

Renaming them may therefore have compatibility consequences.

------------------------------------------------------------------------

### 1.19.17 Keyword Arguments Make Names Observable

Consider:

``` python
def create_user(email, enabled=True):
    ...
```

A caller may write:

``` python
create_user(email="user@example.com", enabled=False)
```

Changing `enabled` to `active` can break callers that pass it by
keyword.

Treat public parameter names as interface design, not merely internal
style.

------------------------------------------------------------------------

### 1.19.18 Constants

Project-level constants are commonly written using uppercase words
separated by underscores:

``` python
DEFAULT_TIMEOUT_SECONDS = 30
MAX_RETRY_COUNT = 5
SUPPORTED_SCHEMA_VERSION = 3
```

Python does not make such names immutable.

The convention communicates that the value should be treated as a
constant by the program.

------------------------------------------------------------------------

### 1.19.19 Constants Are Not Enforcement

This:

``` python
MAX_RETRIES = 5
```

does not prevent later assignment:

``` python
MAX_RETRIES = 10
```

Naming communicates intent; it does not create runtime immutability.

Use appropriate program structure, reviews, tests, and types when
stronger controls are required.

------------------------------------------------------------------------

### 1.19.20 Internal Names and a Leading Underscore

A single leading underscore conventionally signals that a name is
intended for internal use:

``` python
_internal_cache = {}
```

or:

``` python
def _normalize_key(value):
    ...
```

This is primarily an API and readability convention.

It tells users and maintainers that the name is not intended as a stable
public interface.

------------------------------------------------------------------------

A leading underscore has one language/tooling-visible consequence in
addition to its API convention: when a module does not define an overriding
`__all__`, `from module import *` excludes names beginning with an underscore.
For deliberate public APIs, PEP 8 recommends explicitly declaring exported
names with `__all__` where appropriate while still marking internal interfaces
with a leading underscore.

### 1.19.21 Internal Does Not Mean Secret

A leading underscore is not an access-control mechanism.

Code can still access:

``` python
module._internal_cache
```

Use the convention to communicate API intent, not to protect sensitive
data or enforce authorization.

------------------------------------------------------------------------

### 1.19.22 Trailing Underscores

A trailing underscore can avoid conflicts with keywords or established
names:

``` python
class_ = "premium"
```

Use it when it improves clarity and follows the project's conventions.

Do not add trailing underscores arbitrarily.

------------------------------------------------------------------------

### 1.19.23 Double Leading Underscores

Names beginning with two underscores inside class definitions can
participate in Python's name-mangling mechanism:

``` python
class Connection:
    def __init__(self):
        self.__state = "new"
```

This behavior is intended primarily to reduce accidental name collisions
in subclasses.

It should not be treated as a security boundary.

Exact transformation rules and edge cases should be verified against the
Python language reference during technical review.

------------------------------------------------------------------------

For a class-private name, Python's mangling applies to an identifier that
starts with at least two underscores and does not end with two or more
underscores. The class name, with leading underscores removed, is incorporated
into the transformed name. Mangling is performed independently of whether the
resulting name is actually used as an instance attribute.

The mechanism exists to reduce accidental clashes, particularly with
subclasses; it does not make the resulting name inaccessible.

### 1.19.24 Name Mangling Is Not Privacy

Do not assume:

``` python
self.__token
```

makes a sensitive value private or inaccessible.

Name mangling changes how the attribute name is represented to reduce
accidental collisions. It does not provide confidentiality or
authorization.

Security boundaries require actual security controls.

------------------------------------------------------------------------

### 1.19.25 Double-Leading and Double-Trailing Names

Names such as:

``` python
__init__
__str__
__iter__
__enter__
__exit__
```

have special meanings defined by Python's data model and protocols.

These names are often called special names or "dunder" names.

Do not invent new double-leading-and-double-trailing names for ordinary
application semantics. Reserve that namespace for documented Python
behavior.

------------------------------------------------------------------------

### 1.19.26 Do Not Invent Dunder Protocols

Avoid:

``` python
def __company_validate__(self):
    ...
```

for a normal application method.

Prefer:

``` python
def validate(self):
    ...
```

Invented dunder names can conflict with future language or ecosystem
conventions and falsely imply participation in a Python protocol.

------------------------------------------------------------------------

### 1.19.27 `self`

Instance methods conventionally use `self` as the first parameter:

``` python
class User:
    def disable(self):
        ...
```

The name is conventional rather than a special keyword.

Following the convention makes Python code immediately recognizable to
other developers and compatible with common documentation and tooling
expectations.

------------------------------------------------------------------------

### 1.19.28 `cls`

Class methods conventionally use `cls`:

``` python
class User:
    @classmethod
    def from_record(cls, record):
        return cls(...)
```

As with `self`, this is a strong convention rather than a reserved
keyword.

------------------------------------------------------------------------

### 1.19.29 Avoid Shadowing Built-ins

Avoid unnecessarily reusing built-in names:

``` python
list = []
str = "value"
id = "abc"
```

This can make later code surprising:

``` python
list("abc")
```

may fail because `list` no longer refers to the built-in constructor.

Prefer:

``` python
users = []
message = "value"
user_id = "abc"
```

------------------------------------------------------------------------

### 1.19.30 Shadowing Is Scope-Dependent

Reusing a built-in name does not permanently modify Python itself.

The effect depends on scope and name resolution.

Even when technically safe in a narrow context, avoid shadowing when it
makes code harder to read or maintain.

------------------------------------------------------------------------

### 1.19.31 Avoid Ambiguous Single-Character Names

Names such as:

``` text
l
O
I
```

can be confused visually with:

``` text
1
0
```

Prefer clearer alternatives.

Short names such as `i`, `j`, `x`, or `y` may still be reasonable in
tightly scoped mathematical, indexing, or conventional contexts.

------------------------------------------------------------------------

### 1.19.32 Abbreviations

Prefer widely understood abbreviations:

``` python
http_status
cpu_count
db_connection
api_client
```

Avoid organization-specific abbreviations that force new maintainers to
decode the name.

If an abbreviation is central to the domain, document it once and use it
consistently.

------------------------------------------------------------------------

### 1.19.33 Acronyms and Capitalization

Choose one project convention for acronyms and apply it consistently.

For example:

``` python
HttpClient
ApiResponse
user_id
```

may be easier to read and compose than inconsistent variants scattered
across the codebase.

Consistency is especially valuable in generated documentation, APIs, and
search.

------------------------------------------------------------------------

### 1.19.34 Plural Names for Collections

A collection name should normally suggest plurality:

``` python
users = []
failed_requests = []
node_addresses = set()
```

A singular name for a collection can mislead:

``` python
user = [user1, user2]
```

Use names that communicate both domain meaning and shape when practical.

------------------------------------------------------------------------

### 1.19.35 Mapping Names

Mappings benefit from names that describe the relationship:

``` python
user_by_id = {}
region_by_code = {}
connection_by_host = {}
```

This can be clearer than:

``` python
users = {}
```

when the lookup key matters to understanding the algorithm.

------------------------------------------------------------------------

### 1.19.36 Counts, Limits, and Indices

Distinguish quantities:

``` python
retry_count
max_retries
current_index
worker_limit
```

Do not use the same vague term for current state and configured
capacity.

Production bugs can result when a limit, count, index, and size are
treated as interchangeable concepts.

------------------------------------------------------------------------

### 1.19.37 Boolean Variables

Boolean names should read naturally:

``` python
is_enabled = True
has_access = False
should_retry = can_retry(error)
```

Avoid inverted or ambiguous names:

``` python
not_disabled
no_error
flag
status
```

Positive predicates are generally easier to reason about:

``` python
if is_enabled:
    ...
```

------------------------------------------------------------------------

### 1.19.38 Avoid Encoding Types in Names

Python code normally does not need names such as:

``` python
user_list
name_str
count_int
```

when the type is obvious and not part of the domain meaning.

Prefer:

``` python
users
name
count
```

However, words such as `bytes`, `seconds`, or `ids` may express
important semantics rather than implementation types.

------------------------------------------------------------------------

### 1.19.39 Names and Type Hints

Type hints can reduce pressure to encode implementation types into
names:

``` python
users: list[User]
```

The identifier communicates domain meaning while the annotation
communicates the expected type.

Names and types should complement rather than duplicate each other.

------------------------------------------------------------------------

### 1.19.40 Scope Affects Naming

A short local variable can be acceptable when its meaning is immediately
visible:

``` python
for user in users:
    send_notification(user)
```

A module-level or public name usually needs more context because it is
read farther from its definition.

Naming precision should increase with scope, lifetime, and API exposure.

------------------------------------------------------------------------

### 1.19.41 Temporary Variables

Temporary variables should still communicate purpose:

``` python
normalized_email = email.strip().lower()
```

rather than:

``` python
tmp = email.strip().lower()
```

`tmp` is acceptable only when the temporary nature itself is the
relevant meaning and the scope is extremely narrow.

------------------------------------------------------------------------

### 1.19.42 Avoid Historical Names

A name can become wrong after implementation changes.

Example:

``` python
mysql_connection = connect_to_postgresql()
```

Historical names create false assumptions.

Rename objects when their meaning changes unless compatibility
requirements prevent it.

------------------------------------------------------------------------

### 1.19.43 Avoid Implementation-Leaking Names

Prefer domain-oriented names:

``` python
customer_repository
```

over implementation-specific names:

``` python
postgres_customer_table_helper
```

when callers should not depend on the storage implementation.

Expose implementation details in names only when those details are
genuinely part of the contract.

------------------------------------------------------------------------

### 1.19.44 Public API Naming

Public names should be:

-   descriptive;
-   stable;
-   consistent;
-   difficult to misinterpret;
-   compatible with future evolution.

Changing a public class, function, method, parameter, attribute, or
module name can break consumers.

Naming is therefore part of compatibility management.

------------------------------------------------------------------------

### 1.19.45 Renaming Public Interfaces

A production rename may require:

1.  introducing the new name;
2.  retaining a compatibility alias;
3.  documenting deprecation;
4.  updating callers;
5.  emitting an appropriate warning when policy requires it;
6.  measuring remaining usage;
7.  removing the old name only after the compatibility window.

Do not treat a public rename as a purely cosmetic refactor.

------------------------------------------------------------------------

### 1.19.46 Aliases

Aliases can preserve compatibility:

``` python
new_api = implementation
old_api = new_api
```

But aliases can also prolong confusing terminology.

Use them intentionally, document which name is canonical, and define the
migration lifecycle.

------------------------------------------------------------------------

### 1.19.47 Names in Configuration

Configuration names are operational interfaces:

``` text
REQUEST_TIMEOUT_SECONDS
DATABASE_POOL_SIZE
MAX_RETRY_COUNT
```

A configuration key can be referenced by:

``` text
deployment manifests
CI/CD systems
Terraform
Helm
runbooks
monitoring
support procedures
customer environments
```

Renaming it can have a much larger blast radius than renaming a local
Python variable.

------------------------------------------------------------------------

### 1.19.48 Environment Variable Naming

Environment variables are commonly uppercase:

``` text
APP_ENV
DATABASE_URL
REQUEST_TIMEOUT_SECONDS
```

Use a stable project prefix when collision risk exists:

``` text
PAYMENTS_REQUEST_TIMEOUT_SECONDS
```

Do not encode secrets directly into variable names. The name should
identify the setting, not reveal its value.

------------------------------------------------------------------------

### 1.19.49 CLI Option Naming

Command-line option names are user-facing APIs:

``` text
--request-timeout
--max-retries
--dry-run
```

Choose names that are clear in documentation and shell history.

Renaming a CLI option can break automation even if the underlying Python
function is unchanged.

------------------------------------------------------------------------

### 1.19.50 Database and Schema Naming

Database identifiers may outlive application code.

A table, column, index, stream, or schema name can become embedded in:

``` text
queries
ETL pipelines
BI reports
CDC systems
monitoring
backups
runbooks
external integrations
```

Treat persistent-data names as durable contracts.

Do not rename them casually.

------------------------------------------------------------------------

### 1.19.51 Event and Message Naming

Events should describe something that happened:

``` text
order_created
payment_authorized
user_disabled
```

Commands commonly describe requested actions:

``` text
create_order
authorize_payment
disable_user
```

Keeping event and command vocabulary distinct can improve
distributed-system clarity.

------------------------------------------------------------------------

### 1.19.52 Metrics Naming

Metric names should communicate what is measured and use stable
dimensions.

Examples:

``` text
requests_total
request_duration_seconds
queue_depth
```

Avoid ambiguous metrics:

``` text
count
time
errors
```

Metric names become operational APIs consumed by dashboards, alerts,
queries, and automation.

------------------------------------------------------------------------

### 1.19.53 Log Field Naming

Structured log fields should be stable and consistent:

``` text
request_id
trace_id
user_id
operation
error_code
duration_ms
```

Avoid using multiple names for the same concept:

``` text
requestId
req_id
request_identifier
```

within one observability platform unless compatibility requires it.

------------------------------------------------------------------------

### 1.19.54 Error and Reason Codes

Stable machine-readable reason codes should be named independently of
human-readable messages.

Example:

``` python
reason_code = "RATE_LIMITED"
message = "Request rate exceeded the current policy."
```

Applications can depend on the stable code while operators receive a
useful diagnostic message.

------------------------------------------------------------------------

### 1.19.55 Names in Kubernetes and Cloud Automation

Infrastructure names can encode operational scope:

``` text
payments-api
payments-worker
prod-search-data
```

Use a documented convention for dimensions such as:

``` text
application
environment
region
role
resource type
```

Do not overload names with every possible metadata field when labels,
tags, or annotations provide a better structured mechanism.

------------------------------------------------------------------------

### 1.19.56 Names and Security Boundaries

Names such as:

``` python
_admin_only()
__secret
private_token
```

do not create authorization boundaries.

Security must be enforced through permissions, authentication,
authorization, secret-management systems, process boundaries, and other
real controls.

Naming can communicate intent but cannot enforce it.

------------------------------------------------------------------------

### 1.19.57 Names and Logging Safety

A variable name can accidentally encourage unsafe logging:

``` python
credentials
auth_header
access_token
```

The solution is not to hide the meaning with a vague name. Keep the name
clear and enforce logging/redaction controls.

Security through ambiguous naming is not security.

------------------------------------------------------------------------

### 1.19.58 Names and Secrets

Do not embed secret values in identifiers:

``` text
API_KEY_abc123
PASSWORD_supersecret
```

Identifiers can appear in logs, traces, exception messages, debug
output, metrics, and source-control history.

Use identifiers that describe secret purpose:

``` text
PAYMENTS_API_TOKEN
DATABASE_PASSWORD
```

and obtain the value through an approved secret-management mechanism.

------------------------------------------------------------------------

### 1.19.59 Generated Names

Generated identifiers should be designed for their purpose.

Questions include:

``` text
Must the identifier be globally unique?
Must it be sortable?
Must it hide creation time?
Must it be human-readable?
Will it appear in URLs or logs?
Is case sensitivity safe?
Can it be regenerated deterministically?
```

Do not choose an identifier format solely because its name "looks
unique."

------------------------------------------------------------------------

### 1.19.60 Naming and Unicode

Python supports identifiers beyond ASCII.

Unicode identifiers can be legitimate, especially in localized or
domain-specific software.

For broadly maintained production code, teams should establish a
deliberate policy considering:

-   readability across contributors;
-   keyboard availability;
-   visual confusability;
-   searchability;
-   tooling;
-   interoperability;
-   security review.

Do not assume that "valid Python identifier" automatically means
"appropriate project identifier."

------------------------------------------------------------------------

### 1.19.61 Case Sensitivity

Python names are case-sensitive:

``` python
user
User
USER
```

are distinct identifiers.

Do not rely on case alone to distinguish unrelated concepts when doing
so would make the code difficult to read.

------------------------------------------------------------------------

### 1.19.62 Naming Across Serialization Boundaries

External formats may use different naming conventions:

``` json
{
  "userId": "123"
}
```

while Python code may use:

``` python
user_id
```

Use an explicit serialization boundary rather than forcing external
naming rules throughout internal Python code.

Preserve the external contract exactly where interoperability requires
it.

------------------------------------------------------------------------

### 1.19.63 Naming Across APIs

A Python client may translate:

``` text
requestTimeoutSeconds
```

into:

``` python
request_timeout_seconds
```

The translation should be explicit, documented, and tested.

Avoid accidental renaming that silently changes external payloads.

------------------------------------------------------------------------

### 1.19.64 Naming Across Database Boundaries

Database conventions and Python conventions may differ.

For example:

``` text
database column: created_at
Python attribute: created_at
```

can map directly, while other systems may require explicit aliases.

Choose consistency when practical, but do not sacrifice an established
external contract merely to satisfy local style.

------------------------------------------------------------------------

### 1.19.65 Naming Across Legacy Systems

Legacy systems often contain awkward names.

Do not automatically propagate legacy terminology into every new layer.

Create a translation boundary when doing so improves clarity:

``` python
legacy_record["CUST_NO"] -> customer_id
```

Document the mapping and test it.

------------------------------------------------------------------------

### 1.19.66 Naming and Refactoring Tools

Modern IDEs and language tools can safely rename many Python symbols,
but dynamic language features can limit certainty.

Potentially affected areas include:

``` text
reflection
getattr()/setattr()
string-based imports
configuration
templates
serialization
plugins
external callers
database queries
CLI scripts
```

Search and test beyond direct static references before declaring a
rename safe.

------------------------------------------------------------------------

### 1.19.67 Dynamic Attribute Access

Code such as:

``` python
getattr(obj, field_name)
```

makes a string part of the naming contract.

Renaming the attribute definition without updating string-based
references can cause runtime failures that static refactoring tools may
not detect.

Treat dynamic names as explicit dependencies.

------------------------------------------------------------------------

### 1.19.68 Naming and Serialization

Serialized attribute or field names can become durable data contracts.

Changing:

``` text
customer_id
```

to:

``` text
client_id
```

may require schema migration or backward-compatible decoding.

Internal refactoring does not automatically make persisted data safe to
rename.

------------------------------------------------------------------------

### 1.19.69 Naming and Observability Compatibility

Renaming:

``` text
metric names
log fields
span attributes
alert labels
dashboard variables
```

can break operational tooling.

Before changing an observability name, search its downstream consumers.

Operational names deserve compatibility review.

------------------------------------------------------------------------

### 1.19.69.1 Production Rename Safety Gate

Before renaming a production-visible identifier, classify its blast radius.
Check public Python APIs and keyword arguments, serialized or persisted data,
database objects, configuration and environment variables, CLI automation,
metrics and log fields, dashboards and alerts, deployment/IaC definitions,
runbooks, external integrations, and dynamic string-based lookups.

For high-impact renames, record the old name, new canonical name,
compatibility mechanism, affected consumers, rollout order, validation
evidence, owner, and removal condition. Passing unit tests alone is not
sufficient evidence that an externally visible rename is safe.

### 1.19.70 Naming and Searchability

Names should be searchable.

A distinctive, stable term such as:

``` text
request_timeout_seconds
```

is easier to locate across:

``` text
source code
configuration
documentation
runbooks
dashboards
deployment manifests
tickets
```

than several inconsistent synonyms.

Shared vocabulary improves incident response.

------------------------------------------------------------------------

### 1.19.71 One Concept, One Preferred Term

If the system uses:

``` text
customer
client
account holder
subscriber
```

for the same concept without distinction, developers may assume
differences that do not exist.

Define a preferred domain vocabulary.

Use different terms only when they represent genuinely different
concepts.

------------------------------------------------------------------------

### 1.19.71.1 Naming Authority and Vocabulary Governance

Production systems frequently repeat the same concept across source code,
configuration, APIs, schemas, dashboards, alerts, runbooks, and tickets. Teams
should identify the authoritative vocabulary for important domain and
operational terms.

When multiple names exist for the same concept, identify the canonical term,
document required external or legacy aliases, define where translation occurs,
and prevent new interfaces from introducing additional synonyms without
review. Treat conflicting terminology in operational documentation as a
maintainability defect.

### 1.19.72 Avoid Premature Generality in Names

Names such as:

``` python
GenericManager
UniversalProcessor
CommonHandler
```

often indicate an abstraction whose responsibility is unclear.

Name the responsibility the code actually has today.

Broaden the name only when the abstraction genuinely broadens.

------------------------------------------------------------------------

### 1.19.73 Naming Factory Functions

Factory functions should communicate what they create or how:

``` python
create_client()
build_retry_policy()
load_connection_from_env()
```

Names such as:

``` python
get_object()
make_thing()
```

hide important semantics.

If a factory caches or returns an existing instance, the name and
documentation should avoid falsely implying that a new object is always
created.

------------------------------------------------------------------------

### 1.19.74 `get_` Prefixes

Python does not require accessor methods to start with `get_`.

Prefer the clearest interface for the abstraction.

For example, a property may expose:

``` python
user.email
```

while an operation involving I/O may use:

``` python
fetch_user()
load_user()
```

A name can communicate whether work is local, remote, cached, or
potentially expensive.

------------------------------------------------------------------------

### 1.19.75 `fetch`, `load`, `read`, and `get`

Teams may distinguish verbs such as:

``` text
get   -> obtain an available value
load  -> construct/read from a source
fetch -> retrieve from a remote or external system
read  -> consume from a stream/file/device
```

These distinctions are project conventions, not Python language rules.

If adopted, define them and apply them consistently.

------------------------------------------------------------------------

### 1.19.76 `create`, `ensure`, and `upsert`

These names imply different semantics:

``` text
create -> establish a new resource
ensure -> make sure a desired state exists
upsert -> update existing or insert missing
```

Do not name an operation `create_*` if it silently overwrites existing
resources unless that behavior is an explicit contract.

Names should expose meaningful side-effect semantics.

------------------------------------------------------------------------

### 1.19.77 Destructive Operation Names

Destructive methods should be difficult to mistake:

``` python
delete_user()
truncate_table()
drop_index()
purge_cache()
```

Avoid vague names:

``` python
clean()
reset()
fix()
```

when the operation destroys persistent state.

Operational safety benefits from explicit verbs.

------------------------------------------------------------------------

### 1.19.78 Dry-Run Naming

Automation that supports preview mode should use clear terminology:

``` python
dry_run=True
```

or an explicit planning operation:

``` python
plan_changes()
apply_changes()
```

Do not use ambiguous flags such as:

``` python
test=True
```

if the flag controls whether production mutations occur.

------------------------------------------------------------------------

### 1.19.79 Negative Boolean Flags

Avoid interfaces such as:

``` python
disable_validation=False
```

when a positive form is clearer:

``` python
validate=True
```

Double negatives are harder to reason about:

``` python
if not disable_validation:
```

Prefer positive semantics where possible.

------------------------------------------------------------------------

### 1.19.80 Naming and Default Behavior

A name should not conceal a surprising default.

For example:

``` python
delete_records()
```

should not unexpectedly mean "delete every record in production" when
called without arguments.

Safe APIs combine clear names with explicit parameters, validation, and
production safeguards.

Naming supports safety but cannot replace it.

------------------------------------------------------------------------

### 1.19.81 Naming Review Checklist

Before approving a name, ask:

1.  Does it describe the correct domain concept?
2.  Is the meaning clear without reading distant implementation code?
3.  Are units explicit where ambiguity matters?
4.  Does the verb match the operation?
5.  Does a Boolean read naturally?
6.  Is the name public or internal?
7.  Does it shadow a built-in unnecessarily?
8.  Is an abbreviation broadly understood?
9.  Does the name leak an implementation detail?
10. Is it already an external compatibility contract?
11. Does another subsystem use a different term for the same concept?
12. Could a rename break configuration, serialization, metrics, or
    automation?
13. Does the name imply a security guarantee that does not exist?
14. Is a destructive operation unmistakable?
15. Can developers and operators search for the term consistently?

------------------------------------------------------------------------

### 1.19.82 Common Naming Anti-Patterns

Avoid:

1.  vague names such as `data`, `thing`, and `stuff`;
2.  unexplained abbreviations;
3.  inconsistent terms for the same concept;
4.  type-encoded names that duplicate annotations;
5.  Boolean names with confusing negatives;
6.  functions whose names hide major side effects;
7.  shadowing built-ins without a good reason;
8.  invented dunder names;
9.  treating leading underscores as access control;
10. implementation-specific public names without need;
11. unitless operational settings;
12. historical names that no longer match behavior;
13. `utils.py` as an unlimited dumping ground;
14. public parameter renames without compatibility analysis;
15. metric and log-field renames without downstream review;
16. vague destructive verbs;
17. secret values embedded in identifiers;
18. dynamic string-based names ignored during refactoring;
19. external field names changed accidentally during serialization;
20. naming rules applied mechanically without considering domain
    meaning.

------------------------------------------------------------------------

### 1.19.82.1 Naming Standard Lifecycle

A production naming standard should have an owner and change process.
High-impact conventions should record scope, canonical terminology,
compatibility requirements, approved exceptions, migration expectations,
validation or linting mechanisms where practical, and review triggers.

A review date alone is not approval to rename an interface. Current consumers,
environment scope, compatibility requirements, and rollout safeguards must be
validated before a production naming change is executed.

### 1.19.83 Troubleshooting a Naming Problem

When a name appears misleading:

1.  identify the concept the code actually represents;
2.  identify every scope where the name is visible;
3.  determine whether it is public, persisted, serialized, configured,
    logged, measured, or externally consumed;
4.  search direct and dynamic references;
5.  inspect tests and documentation;
6.  identify compatibility constraints;
7.  choose the canonical replacement term;
8.  define aliases or migration behavior if needed;
9.  update code, tests, documentation, configuration, and observability;
10. verify downstream consumers;
11. deprecate old public names when appropriate;
12. remove compatibility aliases only after migration is complete.

------------------------------------------------------------------------

### 1.19.84 Production Engineering Rules

1.  Prefer domain meaning over implementation history.
2.  Use descriptive names at public and operational boundaries.
3.  Make units explicit where ambiguity creates risk.
4.  Use verbs that accurately communicate side effects.
5.  Use positive, readable Boolean names.
6.  Treat public parameter names as API contracts.
7.  Treat configuration keys as operational contracts.
8.  Treat serialized field names as data contracts.
9.  Treat metric and log-field names as observability contracts.
10. Avoid unnecessary built-in shadowing.
11. Do not invent application-specific dunder names.
12. Do not treat underscores as security controls.
13. Keep destructive operation names explicit.
14. Give compatibility aliases a migration lifecycle.
15. Search dynamic and string-based references during renames.
16. Use one preferred term for one domain concept.
17. Avoid ambiguous abbreviations.
18. Keep names searchable across code and operations.
19. Separate external naming conventions at explicit boundaries.
20. Review naming changes for compatibility before production rollout.

### 1.19.89 Key Takeaways

-   Naming is part of software design, not merely formatting.
-   Python language rules determine what identifiers are valid; project
    conventions determine how valid identifiers should communicate
    meaning.
-   Good names reflect domain concepts, units, side effects, and
    interface intent.
-   Public parameter names can be compatibility contracts.
-   Leading underscores communicate internal API intent but do not
    enforce privacy.
-   Double-leading underscores participate in name mangling but do not
    create a security boundary.
-   Documented dunder names belong to Python protocols; application code
    should not invent its own dunder namespace.
-   Avoid unnecessary shadowing of built-ins.
-   Names should become more descriptive as scope and API exposure
    increase.
-   Configuration keys, database identifiers, serialized fields, CLI
    options, metric names, and log fields can all become long-lived
    interfaces.
-   Production renames require compatibility and downstream-consumer
    analysis.
-   Explicit destructive verbs improve operational safety.
-   A shared domain vocabulary improves code review, debugging,
    documentation, observability, and incident response.

> **Central engineering principle:** A name is a promise about meaning.
> Choose names that make correct use natural, make dangerous behavior
> obvious, and remain understandable across code, APIs, data,
> configuration, and operations.
