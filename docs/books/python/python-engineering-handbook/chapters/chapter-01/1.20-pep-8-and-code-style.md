# Chapter 1 --- Python Fundamentals and Development Environment

## 1.20 --- PEP 8 and Code Style

**Edition:** Revised Final / Canonical\
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

-   explain the purpose and practical role of PEP 8;
-   distinguish Python language requirements from style conventions;
-   apply consistent indentation, whitespace, line layout, naming,
    import, and documentation practices;
-   recognize where project conventions may intentionally extend or
    differ from PEP 8;
-   use automated formatting and linting without treating tools as
    substitutes for engineering judgment;
-   review Python code for readability, maintainability, API clarity,
    and production safety;
-   establish a practical code-style baseline for team and production
    repositories.

------------------------------------------------------------------------

### 1.20.1 What PEP 8 Is

PEP 8 is Python's widely used style guide for Python code. It provides
conventions for writing source code that is consistent and readable
across projects.

It addresses indentation, line layout, whitespace, imports, naming,
comments, documentation strings, programming recommendations, and
interface conventions.

PEP 8 is not the Python grammar. A program can be syntactically valid
and still violate common style conventions.

``` python
x=1+2
```

is valid Python, but:

``` python
x = 1 + 2
```

is easier to scan and follows conventional spacing.

The engineering objective is not cosmetic uniformity for its own sake.
Consistent style reduces unnecessary cognitive load so reviewers can
focus on behavior, correctness, security, reliability, and
maintainability.

### 1.20.2 Style Is Not Syntax

Python syntax determines whether source code can be parsed and executed.
Style determines how valid source code is presented to humans.

``` python
def calculate(x,y):
    return x+y
```

A clearer form is:

``` python
def calculate(x, y):
    return x + y
```

A production code review should distinguish syntax errors, runtime
defects, logic defects, type issues, security issues, style issues, and
project-convention issues.

### 1.20.3 Consistency Has Multiple Levels

Style consistency exists across the Python ecosystem, organization,
repository, module, and local code.

PEP 8 provides a strong ecosystem baseline. Organizations commonly
extend it with conventions for logging, exception handling,
configuration, typing, testing, security, APIs, observability, and
repository structure.

The useful rule is simple: make intentional conventions explicit and
enforce them consistently.

### 1.20.4 Readability Is an Engineering Requirement

Production software is read during feature development, peer review,
incident response, debugging, security review, upgrades, migrations,
on-call handoffs, performance investigations, refactoring, and audits.

Readable code improves operational recovery because engineers can reason
about behavior faster under pressure.

### 1.20.5 Indentation

Python uses indentation as part of block structure. Use four spaces per
indentation level for ordinary Python code.

``` python
def process_request(request):
    if request.is_valid:
        persist_request(request)
        publish_event(request)
```

Avoid visually inconsistent indentation and configure editors to insert
spaces consistently.

### 1.20.6 Continuation Lines

Long expressions should be laid out so their structure is obvious.

``` python
result = calculate_capacity(
    current_usage_bytes=current_usage_bytes,
    growth_rate=growth_rate,
    forecast_days=forecast_days,
)
```

For conditions:

``` python
if (
    cluster_is_healthy
    and storage_has_capacity
    and replication_is_current
):
    start_migration()
```

### 1.20.7 Prefer Parentheses for Multi-Line Expressions

Implicit continuation inside parentheses, brackets, and braces is
generally clearer than explicit backslash continuation.

``` python
total = (
    base_cost
    + storage_cost
    + network_cost
    + support_cost
)
```

Parenthesized expressions are easier to modify and review.

### 1.20.8 Closing Delimiters and Trailing Commas

Use a consistent closing-delimiter style for multi-line structures.

``` python
supported_regions = [
    "us-east-1",
    "us-west-2",
    "eu-west-1",
]
```

Trailing commas in multi-line structures produce smaller diffs and
simplify future additions.

Remember that in a single-item tuple the comma is semantically
significant:

``` python
value = (1,)
```

### 1.20.9 Line Length

PEP 8 provides line-length guidance, but production teams should treat
line width as a readability and tooling decision rather than compressing
meaningful code merely to satisfy a number.

Do not shorten descriptive names just to fit a line. Restructure wide
expressions instead.

``` python
request_timeout_seconds = calculate_request_timeout(
    service_tier=service_tier,
    retry_policy=retry_policy,
)
```

Repository formatter configuration should establish one predictable
policy.

### 1.20.10 Binary Operators and Long Conditions

Long mathematical and Boolean expressions should make operators visually
easy to follow.

``` python
total_cost = (
    compute_cost
    + storage_cost
    + network_cost
    + support_cost
)
```

``` python
can_deploy = (
    tests_passed
    and security_scan_passed
    and change_approved
)
```

Consistency matters more than manual improvisation.

### 1.20.11 Blank Lines

Blank lines communicate logical structure. Use them to separate
top-level definitions and meaningful phases inside functions.

Do not insert blank lines after every statement; excessive vertical
spacing fragments related logic.

### 1.20.12 Whitespace Around Operators and Assignment

Prefer:

``` python
total = subtotal + tax
remaining = capacity - used
ratio = used / capacity
retry_count = 3
```

Keyword arguments and unannotated defaults normally omit spaces around
`=`:

``` python
connect(timeout_seconds=30)

def connect(timeout_seconds=30):
    ...
```

Annotated defaults use conventional spacing:

``` python
def connect(timeout_seconds: int = 30) -> None:
    ...
```

Automated formatters should own these deterministic details where
possible.

### 1.20.13 Avoid Extraneous Whitespace

Prefer:

``` python
records = [1, 2, 3]
result = calculate(value)
mapping["key"]
```

Avoid decorative whitespace that obscures normal Python structure.

### 1.20.14 Multiple Statements on One Line

Avoid compressing independent statements:

``` python
load(); validate(); publish()
```

Prefer:

``` python
load()
validate()
publish()
```

Likewise, avoid hiding substantial logic after a colon. Vertical
structure improves review and instrumentation.

### 1.20.15 Import Placement

Imports normally appear near the beginning of a module after module
documentation and before ordinary module-level definitions.

``` python
import logging
from pathlib import Path

from company_platform.metrics import record_metric
```

Local imports can be appropriate for specific technical reasons, but
they should be intentional.

### 1.20.16 One Module Per Import Statement

Prefer:

``` python
import json
import logging
import pathlib
```

rather than:

``` python
import json, logging, pathlib
```

Separate imports are easier to scan, sort, modify, and review.

### 1.20.17 Import Grouping

A common organization separates standard-library, third-party, and local
application imports.

``` python
import logging
from pathlib import Path

import requests

from platform_service.config import load_config
from platform_service.metrics import record_metric
```

Automated import sorting can enforce a predictable policy.

### 1.20.18 Avoid Wildcard Imports

Avoid:

``` python
from module import *
```

Prefer explicit imports:

``` python
from module import parse_config, validate_config
```

Explicit dependencies improve readability, static analysis, refactoring,
and debugging.

### 1.20.19 Absolute and Relative Imports

Use import forms that make package relationships understandable.

``` python
from billing.validation import validate_invoice
```

or, where appropriate inside a package:

``` python
from .validation import validate_invoice
```

Avoid import behavior that accidentally depends on the current working
directory or ad hoc `sys.path` mutation.

### 1.20.20 Do Not Hide Import Failures

This can conceal defects:

``` python
try:
    import optional_library
except Exception:
    optional_library = None
```

When handling a genuinely optional dependency, catch the failure you
intend to handle and distinguish absence from a broken installation.

### 1.20.21 Naming Style Recap

Section 1.19 covers naming conventions in depth. Common Python forms
include:

``` text
module_name
package_name
function_name
method_name
variable_name
ClassName
ExceptionName
CONSTANT_NAME
_internal_name
```

Do not duplicate naming policy inconsistently across repositories.

### 1.20.22 Public and Internal Interfaces

A leading underscore conventionally marks an internal interface:

``` python
def _normalize_record(record):
    ...
```

This is not an access-control boundary. Public API names, parameters,
exceptions, and behavior should be treated as compatibility contracts.

### 1.20.23 Comments Explain Why

Useful comments explain decisions, constraints, invariants,
compatibility requirements, safety conditions, or operational
workarounds.

``` python
# Keep the previous generation for one deployment cycle so rollback
# can restore the prior configuration without rebuilding artifacts.
retain_previous_generation()
```

Avoid comments that merely translate syntax:

``` python
# Increment retry count
retry_count += 1
```

### 1.20.24 Keep Comments Accurate

An outdated comment confidently communicates false information.

When behavior changes, update nearby comments and documentation in the
same change. Code review should treat misleading comments as defects.

### 1.20.25 Docstrings

Docstrings document modules, classes, functions, methods, and other
supported objects.

``` python
def calculate_free_capacity(total_bytes: int, used_bytes: int) -> int:
    """Return the number of unused bytes."""
    return total_bytes - used_bytes
```

Public API documentation may need purpose, parameters, return values,
exceptions, side effects, units, constraints, and lifecycle behavior.

### 1.20.26 Multi-Line Docstrings

More complex APIs may require multi-line documentation:

``` python
def rotate_credentials(account_id: str) -> str:
    """Rotate credentials for an account.

    Creates a new credential, validates it, updates the active
    reference, and returns the new credential identifier.

    Raises:
        CredentialRotationError: If validation or activation fails.
    """
    ...
```

Documentation should describe the contract rather than narrating every
implementation step.

### 1.20.27 Documentation Must Match Behavior

If documentation says a function raises an error for negative input but
the implementation silently clamps the value, the documentation and
implementation disagree.

That is an API correctness problem, not merely a writing issue.

### 1.20.28 Source Encoding and Quote Style

Modern Python source is commonly UTF-8. Avoid unnecessary encoding
complexity.

Python supports single- and double-quoted strings. A project may
standardize on one form or delegate the choice to an automated
formatter.

Do not create review churn over formatter-owned quote choices.

### 1.20.29 Avoid Meaningless Style Churn

A change that reformats thousands of unrelated lines while modifying
production logic makes review harder.

Prefer separating broad mechanical formatting from behavioral changes.
Large formatting migrations should not obscure functional diffs or
incident work.

### 1.20.30 Comparisons to `None`

Use identity tests:

``` python
if value is None:
    ...
```

``` python
if value is not None:
    ...
```

Avoid `value == None`. Identity directly expresses the sentinel check
and avoids arbitrary equality behavior.

### 1.20.31 Boolean Comparisons and Truthiness

Prefer:

``` python
if service_ready:
    start()
```

over:

``` python
if service_ready == True:
    start()
```

But truthiness must preserve domain meaning.

``` python
if records:
```

means the collection is non-empty.

``` python
if records is not None:
```

means a value was provided, including an empty collection.

Do not collapse `None`, `False`, `0`, empty strings, and empty
containers when the domain distinguishes them.

### 1.20.32 Exception Handling Style

Catch the narrowest exception set matching the recovery policy.

Prefer:

``` python
try:
    config = load_config(path)
except ConfigFileNotFoundError:
    use_default_config()
```

Avoid bare `except` unless the design genuinely requires handling
`BaseException`-level conditions.

### 1.20.33 Do Not Silence Exceptions

Avoid:

``` python
try:
    publish_event(event)
except Exception:
    pass
```

If a failure is intentionally non-fatal, preserve observability and
catch the intended failure class.

``` python
try:
    publish_event(event)
except EventPublishError:
    logger.exception(
        "event publication failed",
        extra={"event_id": event.id},
    )
```

### 1.20.34 Keep `try` Blocks Focused

A broad `try` block makes it harder to identify which statement produced
the handled exception.

Place only the operations that belong to the intended exception policy
inside the protected region.

### 1.20.35 Clear Return Contracts

Avoid unnecessary Boolean control flow:

``` python
def is_eligible(user):
    return user.active and user.verified
```

But do not compress complex decisions into unreadable expressions.

Functions should also make optional or implicit `None` return paths
clear through implementation, typing, and documentation.

### 1.20.36 Avoid Mutable Default Arguments

Python evaluates default argument expressions when the function definition executes, not independently for every call. A mutable default object can therefore be shared across calls.

Do not write:

``` python
def add_record(record, records=[]):
    records.append(record)
    return records
```

The list is created once and reused.

Prefer:

``` python
def add_record(record, records=None):
    if records is None:
        records = []

    records.append(record)
    return records
```

This is a correctness issue as well as a style recommendation.

### 1.20.37 Sentinel Defaults

When `None` is a valid input, use a dedicated sentinel:

``` python
_UNSET = object()

def update_timeout(timeout=_UNSET):
    if timeout is _UNSET:
        return load_default_timeout()

    return timeout
```

The interface should preserve semantic distinctions.

### 1.20.38 Named Functions Versus Assigned Lambdas

If a callable needs a stable descriptive name, prefer `def`.

``` python
def normalize_name(value):
    return value.strip().lower()
```

Lambdas remain useful for small anonymous callables passed directly to
another API.

### 1.20.39 Function Size and Nesting

A function can be perfectly formatted and still be too large, coupled,
or difficult to test.

Warning signs include deep nesting, unrelated responsibilities, repeated
side effects, hidden global state, and many Boolean control parameters.

Guard clauses can reduce nesting when they make prerequisites and
failure paths clearer.

### 1.20.40 Comprehensions

Use comprehensions for straightforward transformations:

``` python
active_ids = [
    user.id
    for user in users
    if user.active
]
```

When a comprehension contains nested loops, multiple conditions, side
effects, or complex error handling, an explicit loop is often easier to
operate and debug.

### 1.20.41 Side Effects in Expressions

Avoid hiding important side effects inside expressions.

Prefer:

``` python
values = load_values()
cache.update(values)
```

over expressions that combine mutation and condition testing merely for
compactness.

Named steps provide natural locations for validation, logging, metrics,
and exception handling.

### 1.20.42 Units and Thresholds

Production values should communicate units.

Weak:

``` python
if latency > 500:
    alert()
```

Clearer:

``` python
MAX_ACCEPTABLE_LATENCY_MS = 500

latency_ms = measure_latency_ms()

if latency_ms > MAX_ACCEPTABLE_LATENCY_MS:
    alert()
```

Names make operational policy discoverable.

### 1.20.43 Magic Values

Not every literal needs a constant. Policy values, protocol values, and
repeated state strings deserve names or stronger models when doing so
reduces ambiguity.

Configuration may be more appropriate than a constant when values vary
by environment.

### 1.20.44 Logging Style

Logging should be readable, stable, and operationally useful.

``` python
logger.info(
    "deployment completed",
    extra={
        "deployment_id": deployment_id,
        "service": service_name,
    },
)
```

The project's observability standard should define field naming,
cardinality, redaction, and correlation behavior.

### 1.20.45 Never Log Secrets

Do not expose passwords, tokens, authorization headers, private keys,
session credentials, or connection strings containing credentials.

Representations such as `__repr__` also require redaction because they
frequently appear in logs, exceptions, notebooks, and debuggers.

### 1.20.46 Formatting Does Not Equal Quality

Perfectly formatted code can still contain SQL injection, broken
authorization, race conditions, unsafe retries, resource leaks, and
incorrect business logic.

Formatting is one quality control, not a correctness proof.

### 1.20.47 Automated Formatters

Automated formatters reduce subjective formatting debates and
consistently handle layout.

Teams should control formatter behavior through versioned project
configuration and CI rather than relying on individual editor defaults.

### 1.20.48 Linters

Linters can identify unused imports, undefined names, suspicious
comparisons, import issues, complexity concerns, unsafe constructs, and
style inconsistencies.

Enable rules with a clear engineering purpose. A ruleset producing large
volumes of low-value warnings teaches developers to ignore it.

### 1.20.49 Formatter, Linter, Type Checker, Tests

These tools solve different problems:

``` text
formatter    -> source representation
linter       -> suspicious patterns and policy diagnostics
type checker -> static type analysis
tests        -> behavioral verification
security     -> security-focused analysis
```

A repository should avoid conflicting ownership of the same
deterministic rule.

### 1.20.50 Reproducible Tooling

Formatter and linter versions can change behavior.

Production repositories should control tool versions through locked
development dependencies, pinned CI images, or another reproducible
mechanism.

Keep style configuration in version control rather than undocumented IDE
settings.

### 1.20.51 Editor, Pre-Commit, and CI Alignment

Editors can provide format-on-save, lint feedback, type checking, and
whitespace diagnostics.

Fast local checks can catch deterministic problems before CI.

CI remains the authoritative shared enforcement point.

Developers should be able to reproduce CI checks locally without
guessing.

### 1.20.52 Style Suppressions

Suppressions should be narrow, intentional, and reviewable.

Avoid globally disabling a useful rule because one line is inconvenient.

A suppression is a policy exception and deserves a reason when the
context is not obvious.

### 1.20.53 Generated and Vendored Code

Generated code should be controlled through its generator, not
hand-edited repeatedly to satisfy style.

Vendored third-party code should generally retain upstream form unless
the project has a deliberate maintenance strategy.

Mass-formatting vendored code complicates upgrades and provenance
review.

### 1.20.54 Legacy Repository Adoption

Possible migration strategies include:

``` text
format everything once
format touched files
format selected directories
adopt rules incrementally
```

A whole-repository migration establishes a clean baseline but creates a
large history boundary. Incremental adoption reduces immediate churn but
can preserve mixed style for a long time.

Choose intentionally.

### 1.20.55 Code Review

Automate deterministic rules so human reviewers can focus on:

-   abstraction;
-   naming;
-   control flow;
-   failure paths;
-   API stability;
-   security;
-   units and domain states;
-   observability;
-   production risk.

Repository style belongs to the project rather than individual reviewer
preference.

### 1.20.56 Project Rules and PEP 8

PEP 8 is a baseline, not a reason to break compatibility or reduce
clarity.

Projects may intentionally diverge because of public API compatibility,
generated code, framework conventions, mathematical notation, historical
interfaces, domain schemas, or formatter policy.

Exceptions should be intentional and understandable.

### 1.20.57 Public API Compatibility

Renaming a public function, class, import path, or keyword parameter
merely to make it look more conventional can break callers.

Style cleanup does not automatically justify compatibility breaks.

Use deprecation and migration policy where required.

### 1.20.58 External Naming Conventions

External systems may use conventions different from internal Python
code.

A JSON API may use `requestId` while Python uses `request_id`.
Environment variables may use `REQUEST_TIMEOUT_SECONDS` while Python
uses `request_timeout_seconds`.

Boundary adapters can preserve both conventions without corrupting
either contract.

### 1.20.59 Infrastructure and Database Identifiers

Python automation interacts with PostgreSQL, Snowflake, Elasticsearch,
Kafka, Kubernetes, cloud resources, and other systems whose identifiers
may have their own rules.

Preserve exact external identifiers where required while keeping
internal Python names clear.

Do not normalize an external name in a way that changes its meaning.

### 1.20.60 Test Code Style

Tests are production engineering assets.

Test names should describe behavior:

``` python
def test_expired_token_is_rejected():
    ...
```

Test structure should make setup, action, and assertion easy to
identify.

Unreadable tests weaken the safety net.

### 1.20.61 Async Code

Asynchronous code benefits from explicit lifecycle, timeout,
cancellation, and cleanup behavior.

Do not hide important `await` operations or background task ownership
inside dense expressions.

Formatting cannot substitute for correct asynchronous semantics.

### 1.20.62 Context Managers and Resource Lifetimes

Use context managers when they make ownership explicit:

``` python
with path.open("r", encoding="utf-8") as file:
    content = file.read()
```

The same principle applies to transactions, locks, temporary
directories, sessions, and other resources.

### 1.20.63 Type Annotation Style

Annotations should improve interface clarity.

``` python
def calculate_utilization(
    used_bytes: int,
    total_bytes: int,
) -> float:
    ...
```

When type expressions become difficult to understand, consider a named
alias or dedicated model.

This handbook targets Python 3.14, so examples should favor current
syntax unless compatibility is being taught explicitly.

### 1.20.64 Modern Syntax

New syntax is not automatically clearer.

Pattern matching, assignment expressions, advanced typing forms, and
other modern features should be adopted when they improve the code and
fit the real runtime compatibility contract.

### 1.20.65 Assignment Expressions

Assignment expressions can reduce duplication in narrow cases:

``` python
while chunk := stream.read(chunk_size):
    process(chunk)
```

Avoid combining assignment, multiple conditions, side effects, and
complex calls in one dense expression.

### 1.20.66 Data Transformation Pipelines

Prefer visible stages:

``` python
raw_data = load(path)
parsed_data = parse(raw_data)
transformed_data = transform(parsed_data)
validated_data = validate(transformed_data)
output = publish(validated_data)
```

over:

``` python
output = publish(validate(transform(parse(load(path)))))
```

Visible stages improve failure localization, logging, metrics, testing,
and debugging.

### 1.20.67 Style and Observability

Readable code creates natural telemetry boundaries.

Instrument meaningful domain stages rather than every line. Keep
telemetry field names stable and avoid high-cardinality identifiers in
metric labels unless the observability design explicitly supports them.

### 1.20.68 Error Messages

Error messages should be concise, actionable, and contextual.

``` python
raise ValueError(
    f"timeout_seconds must be non-negative; received {timeout_seconds}"
)
```

Do not include secrets in exceptions. Distinguish operator diagnostics
from user-facing messages when necessary.

### 1.20.69 Validation Boundaries

Validation should be visible where external or untrusted data becomes
trusted domain data.

``` python
def create_batch(batch_size: int) -> Batch:
    if batch_size <= 0:
        raise ValueError("batch_size must be greater than zero")

    return Batch(size=batch_size)
```

Do not bury critical validation inside unrelated processing.

### 1.20.70 Security-Sensitive Code

Security-sensitive logic should favor explicit, testable policy.

Complex authorization belongs in a dedicated abstraction rather than
being scattered across handlers.

Readable security code is easier to audit, but readability alone does
not prove correctness.

### 1.20.71 Concurrency and Transactions

Synchronization and transaction boundaries should be visible.

``` python
with state_lock:
    current_generation = state.generation
    state.generation += 1
```

``` python
with database.transaction():
    order_id = create_order(order)
    reserve_inventory(order)
    record_audit_event(order_id)
```

Style should expose ownership; technical review must still verify
semantics.

### 1.20.72 Retry Policy

Production retry code should make retryable errors, maximum attempts,
backoff, jitter, deadlines, idempotency, and observability discoverable.

Clean formatting cannot compensate for an unsafe retry policy.

### 1.20.72.1 Production Retry Safety

Retries must be bounded by a maximum attempt count, an overall deadline, or both. For remote mutations, retry only when the operation is safe to repeat or when an idempotency mechanism protects against duplicate effects. Distributed clients should normally use backoff with jitter so a shared failure does not produce synchronized retry storms.

### 1.20.73 Configuration

Avoid scattering raw environment lookups throughout business logic.

Prefer a validated configuration boundary that centralizes parsing,
defaults, validation, secret handling, and environment mapping.

### 1.20.74 Global State

Mutable global state deserves caution because it introduces lifecycle,
concurrency, invalidation, testing, and memory questions.

A simple module-level dictionary can represent an architectural
decision.

### 1.20.75 Data Classes and Enums

Data classes and enums can make structured domain data and bounded
states clearer.

Use them when they represent real concepts rather than merely to satisfy
a style preference.

### 1.20.76 API Boundaries

APIs should be easy to call correctly.

Prefer meaningful keyword arguments when positional values are
ambiguous:

``` python
create_backup(
    database_name="orders",
    retention_days=30,
    verify=True,
)
```

Multiple positional Boolean arguments are especially difficult to
review.

### 1.20.77 Keyword-Only Parameters

Keyword-only parameters can make important options explicit:

``` python
def connect(
    host: str,
    port: int,
    *,
    timeout_seconds: float,
    verify_tls: bool,
):
    ...
```

Use parameter semantics to improve API clarity and compatibility.

### 1.20.78 Properties and Cost Expectations

A property looks inexpensive and local.

Avoid properties that unexpectedly perform slow network I/O, large
computation, or destructive mutations.

API syntax creates expectations about cost and side effects.

### 1.20.79 Operational Scripts

Operational scripts can affect production and deserve disciplined style.

Make target environment, destructive operations, dry-run behavior,
authentication source, validation, timeouts, retries, logging, exit
status, verification, and rollback assumptions visible.

"Temporary" scripts often become permanent infrastructure.

### 1.20.80 CLI Entry Points

Keep significant business logic out of the main guard.

``` python
def main() -> int:
    run()
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

This makes process behavior testable and separates import from
execution.

### 1.20.81 Import-Time Side Effects

Avoid opening database connections, performing network requests,
starting threads, writing files, or mutating remote systems during
module import.

Import-time work makes testing, tooling, startup, and failure handling
harder to reason about.

### 1.20.82 Production Example: Capacity Check

Weak:

``` python
if d/t*100>75: alert()
```

Production-oriented:

``` python
CAPACITY_REVIEW_THRESHOLD_PERCENT = 75.0

disk_usage_percent = (
    used_disk_bytes / total_disk_bytes * 100
)

if disk_usage_percent >= CAPACITY_REVIEW_THRESHOLD_PERCENT:
    trigger_capacity_review(
        disk_usage_percent=disk_usage_percent,
    )
```

The second version exposes units, policy, computation, decision, and
operation.

### 1.20.83 Production Example: Retry

``` python
MAX_ATTEMPTS = 5

for attempt_number in range(1, MAX_ATTEMPTS + 1):
    try:
        send()
        break
    except RetryablePublishError:
        if attempt_number == MAX_ATTEMPTS:
            raise

        delay_seconds = calculate_backoff(attempt_number)
        sleep(delay_seconds)
```

A complete implementation may additionally require jitter, deadlines,
idempotency, cancellation, metrics, and structured logging.

### 1.20.84 Production Example: Configuration Parsing

``` python
def load_timeout_seconds() -> int:
    raw_timeout = os.getenv("REQUEST_TIMEOUT_SECONDS", "30")

    try:
        timeout_seconds = int(raw_timeout)
    except ValueError as exc:
        raise ConfigurationError(
            "REQUEST_TIMEOUT_SECONDS must be an integer"
        ) from exc

    if timeout_seconds <= 0:
        raise ConfigurationError(
            "REQUEST_TIMEOUT_SECONDS must be greater than zero"
        )

    return timeout_seconds
```

The additional structure creates an explicit validated boundary.

### 1.20.85 Production Example: Elasticsearch Query

Dense nested dictionaries are difficult to review during incidents.

Prefer formatting that exposes query structure:

``` python
query = {
    "query": {
        "bool": {
            "filter": [
                {"term": {"status": "active"}},
                {
                    "range": {
                        "date": {
                            "gte": start_date,
                            "lte": end_date,
                        }
                    }
                },
            ]
        }
    }

```

For larger queries, dedicated builders or typed models may improve
maintainability.

### 1.20.86 Production Example: Kubernetes Automation

``` python
for pod in pods:
    if pod.status.phase == "Running":
        continue

    logger.warning(
        "pod is not running",
        extra={
            "namespace": pod.metadata.namespace,
            "pod_name": pod.metadata.name,
            "phase": pod.status.phase,
        },
    )
```

The structure exposes the operational context needed for
troubleshooting.

### 1.20.87 Production Example: Snowflake Administration

Administrative automation should separate validated identifiers and
allowed configuration values from SQL construction.

The exact safe construction mechanism depends on the database client and
whether a value is an identifier or bindable data.

Readable code should make the trust boundary obvious.

### 1.20.88 Dry Run and Verification

Infrastructure automation should make no-mutation behavior explicit.

``` python
if dry_run:
    logger.info(
        "dry run: would resize warehouse",
        extra={
            "warehouse": warehouse_name,
            "target_size": target_size,
        },
    )
    return
```

After mutation, verify desired state:

``` python
apply_change()
verify_change()
```

Do not equate a successful API response with completed desired state.

### 1.20.89 Rollback Visibility

If rollback exists, make recovery ownership understandable:

``` python
previous_state = capture_current_state()

try:
    apply_change()
    verify_change()
except ChangeError:
    restore_state(previous_state)
    raise
```

Real rollback may require more complex handling, but it should not be
hidden.

### 1.20.90 Idempotent Automation

When an operation is intended to be idempotent, make the current-state
check explicit:

``` python
if current_size == target_size:
    logger.info("warehouse already at requested size")
    return
```

Avoid unnecessary mutations.

### 1.20.91 Timeouts and Units

Remote calls should not accidentally depend on unbounded defaults.

``` python
response = client.get(
    endpoint,
    timeout=REQUEST_TIMEOUT_SECONDS,
)
```

Use names such as `timeout_seconds`, `latency_ms`, `memory_limit_mib`,
and `shard_size_bytes` where units matter.

### 1.20.92 Financial and Identifier Semantics

Names should expose representation:

``` python
amount_cents
amount_usd
price_decimal
```

Likewise distinguish:

``` python
user_id
account_id
request_id
trace_id
deployment_id
```

Avoid generic `id` when multiple identifier domains coexist.

### 1.20.93 Boolean and Collection Names

Collections are commonly plural:

``` python
users
records
failed_requests
```

Boolean names should read naturally:

``` python
is_ready
has_capacity
can_retry
should_refresh
```

Positive Boolean names often avoid confusing double negatives.

### 1.20.94 State and Feature Flags

Meaningful states should be modeled explicitly when that reduces invalid
combinations.

Feature flags should communicate scope and have ownership, rollout,
observability, and removal plans.

Old flags become permanent complexity when unmanaged.

### 1.20.95 TODOs and Temporary Workarounds

Deferred work should remain actionable.

A project may require issue references:

``` python
# TODO(PROJ-1842): Remove compatibility path after v2 clients are retired.
```

Temporary workarounds should explain why they exist and what permits
removal.

### 1.20.96 SQL, JSON, Regex, and Shell Boundaries

Embedded SQL should remain readable and parameterized according to the
database driver.

Complex JSON payloads should be decomposed when validation and
transformation become difficult to see.

Complex regular expressions should be named and documented by accepted
language or intent.

Shell execution should use structured process APIs with explicit
argument boundaries where possible.

### 1.20.96.1 Production Shell and Subprocess Safety

For production process execution, prefer structured argument lists:

```python
subprocess.run(
    ["tool", "--target", target_name],
    check=True,
    timeout=COMMAND_TIMEOUT_SECONDS,
)
```

Avoid `shell=True` when any command content is untrusted or externally controlled. If shell interpretation is genuinely required, treat quoting, environment inheritance, executable selection, timeout behavior, exit status, and captured output as explicit security and reliability concerns.

### 1.20.97 Resource Cleanup

Resource ownership should be visible for files, database connections,
transactions, locks, temporary directories, sessions, and processes.

Use context managers or explicit lifecycle APIs where appropriate.

### 1.20.98 Production Guards

High-risk automation can require explicit environment and approval
guards.

``` python
if environment == "production" and not change_approved:
    raise ChangeApprovalRequiredError()
```

Do not hide safety policy in a generically named `check()` helper.

### 1.20.99 Assertions

Do not use `assert` as the sole validation mechanism for untrusted
external input or mandatory authorization.

Distinguish internal invariants from external validation and security
controls.

### 1.20.100 Error Recovery

Recovery paths should be as readable as success paths.

A production reader should be able to identify what failed, what is
retryable, what rolls back, what is logged, and what reaches the caller.

### 1.20.101 Metrics and Structured Logging

Metric labels require cardinality discipline. Avoid casually using
request IDs, user IDs, raw URLs, or free-form error messages as labels.

Structured logging should use stable event meaning and searchable
context.

### 1.20.102 Exception Chaining

When translating exceptions, preserve causal context where appropriate:

``` python
try:
    value = int(raw_value)
except ValueError as exc:
    raise ConfigurationError(
        "retry count must be an integer"
    ) from exc
```

Do not expose sensitive low-level details to untrusted users.

### 1.20.103 Error Taxonomy

Do not convert every failure into a generic `RuntimeError("failed")`
when callers need to distinguish configuration, authentication, timeout,
capacity, validation, conflict, or not-found conditions.

Conversely, do not create exception hierarchies with no recovery or
diagnostic purpose.

### 1.20.104 Loop `else`, `try` `else`, and `finally`

Python provides constructs such as loop `else`, `try` `else`, and
`finally`.

Use them when they make control flow clearer to the intended
maintainers. Do not use syntax features mechanically merely because they
are considered Pythonic.

### 1.20.105 Async Lifecycle

Async iteration, async context managers, and background tasks require
explicit ownership.

For background work, answer:

-   who waits for it;
-   who cancels it;
-   where exceptions are observed;
-   what happens at shutdown;
-   whether tasks can accumulate.

Naming and structure should make lifecycle responsibilities
discoverable.

### 1.20.106 Caching and Lazy Initialization

Caching introduces key, expiration, invalidation, size, concurrency, and
failure semantics.

Lazy initialization introduces state transitions and may require
synchronization.

Readable syntax does not automatically make either pattern thread-safe.

### 1.20.107 Dependency Lifetimes

Dependencies may live for a process, application, request, transaction,
or operation.

Code should make those lifetimes understandable. Creating a database
client inside every record-processing call may be visually simple but
operationally inefficient.

### 1.20.108 Performance and Memory

Do not sacrifice readability for speculative micro-optimization.

Measure first.

Also remember that compact syntax can have different memory behavior:

``` python
records = [transform(record) for record in huge_dataset]
```

materializes a list, while a generator expression has different
evaluation and reuse semantics.

Choose based on workload and contract.

### 1.20.109 Batching and Pagination

High-volume processing should expose batch size and pagination behavior.

``` python
for batch in iter_batches(records, batch_size=1000):
    process_batch(batch)
```

Operational controls such as batch size affect memory, throughput, API
limits, transaction duration, and recovery.

### 1.20.110 Repeated Computation

Do not repeat expensive or stateful calculations merely for compactness.

``` python
usage_percent = calculate_usage()

if usage_percent > 75:
    logger.warning(
        "capacity threshold exceeded",
        extra={"usage_percent": usage_percent},
    )
```

The decision and telemetry now use the same measured value.

### 1.20.111 Distributed-System Identifiers

Use distinct names for idempotency keys, request IDs, operation IDs,
trace IDs, and span IDs.

These identifiers have different semantics and lifecycles. Generic
naming creates diagnostic confusion.

### 1.20.112 Pure Functions and Side Effects

Pure functions are often easy to test and reason about, but not every
function should be pure.

Avoid hiding mutations inside names that imply calculation or
inspection.

Names should help callers predict whether an operation reads or changes
state.

### 1.20.113 Properties Versus Methods

A property such as:

``` python
cluster.status
```

looks inexpensive and local.

A method such as:

``` python
cluster.fetch_status()
```

better signals remote work.

API surface style should match performance and failure expectations.

### 1.20.114 Serialization and Encoding Boundaries

Use names that distinguish representations:

``` python
raw_payload
parsed_payload
validated_request
response_bytes
response_text
encoded_payload
```

Do not let one generic variable silently change representations through
a long function.

### 1.20.115 Optional Values and Defaulting

Handle optional values deliberately:

``` python
customer = repository.find_customer(customer_id)

if customer is None:
    raise CustomerNotFoundError(customer_id)
```

Be careful with:

``` python
timeout = configured_timeout or DEFAULT_TIMEOUT
```

If zero is valid and only `None` means missing, use an explicit `None`
check.

### 1.20.116 Collections and Ordering

At API boundaries, document whether a collection is mutated, consumed
once, ordered, duplicate-preserving, or fully materialized.

If semantic order matters, make sorting explicit.

### 1.20.117 Callbacks and Decorators

Callbacks should communicate when they run and whether they can block,
raise, mutate, run concurrently, or execute repeatedly.

Decorators can hide substantial behavior such as retries, transactions,
caching, or return-type changes. Name and document them accordingly.

Decorator ordering can affect semantics and is not merely visual style.

### 1.20.118 Framework and Third-Party Conventions

Frameworks may impose conventions that differ from generic Python style.

Follow framework requirements while keeping ordinary code consistent
with repository policy.

Create adapters around third-party APIs only when they add real domain,
validation, observability, compatibility, or testability value.

### 1.20.119 Documentation Examples and Copy/Paste Safety

Users copy examples.

Documentation code should avoid teaching unsafe defaults, real-looking
secrets, destructive actions without context, or production network
calls without relevant timeout and validation guidance.

Distinguish minimal teaching examples from production-oriented examples
when omissions matter.

### 1.20.120 Review Automation

A mature pull-request pipeline can automate deterministic checks:

``` text
formatter check
    ↓
linter
    ↓
type checker
    ↓
tests
    ↓
security/static analysis
    ↓
human review
```

Human review remains necessary for architecture, behavior, risk, and
context.

### 1.20.121 Auto-Fixes and Tool Upgrades

Review automated fixes. They may alter imports, syntax, or constructs
beyond simple whitespace.

Treat major formatter and linter upgrades as controlled changes. Review
release notes, changed defaults, Python-version support, and
repository-wide output changes.

### 1.20.122 Style Policy Ownership

A production repository should have a clear owner for style policy.

Policy changes should be deliberate, version controlled, and independent
of whichever reviewer happens to comment first.

### 1.20.123 Style Debt

Style debt accumulates when conventions vary, lint is broadly disabled,
formatting is manual, comments become stale, public APIs are
inconsistent, generated code is mixed with maintained code, or CI
disagrees with local tooling.

It increases the cost and risk of future changes.

### 1.20.124 Complexity Metrics

Function length, file length, cyclomatic complexity, and documentation
percentage can be useful signals but should not become simplistic
targets.

Do not split coherent logic into artificial helpers merely to satisfy a
number.

### 1.20.125 Style and Cognitive Load

Every inconsistency consumes reader attention.

Automate trivial consistency so human attention remains available for
meaningful differences in behavior and risk.

### 1.20.126 Style and Onboarding

A documented baseline should answer:

-   how to format code;
-   which command runs lint;
-   whether type hints are required;
-   how imports are organized;
-   which Python version is supported;
-   what CI enforces;
-   how suppressions work.

The best onboarding experience is one where repository tooling and
documentation agree.

### 1.20.127 AI-Generated and Copied Code

AI-generated code should pass the same gates as human-written code.

Polished formatting, annotations, and docstrings do not prove semantics,
security, performance, compatibility, licensing/provenance, or
operational safety.

Copied code should likewise be reviewed for provenance, runtime
compatibility, dependency assumptions, security, and tests.

### 1.20.128 Copyright Awareness

PEP 8 and Python documentation can be consulted for factual rules and
conventions.

Handbook prose should explain those rules in original instructional
language rather than reproducing substantial source passages.

Later copyright review should verify originality and attribution where
direct quotation is necessary.

### 1.20.129 Practical Team Standard

A practical production standard is:

1.  Start from PEP 8.
2.  Define project-specific conventions in version control.
3.  Automate deterministic formatting.
4.  Lint for high-signal problems.
5.  Keep local tools and CI aligned.
6.  Control tool versions.
7.  Preserve public compatibility.
8.  Prefer explicit production behavior.
9.  Treat suppressions as reviewed exceptions.
10. Never confuse formatting compliance with correctness.

### 1.20.130 Production Engineering Rules

For production Python code:

1.  Optimize style for human comprehension.
2.  Use four-space indentation consistently.
3.  Keep imports explicit and organized.
4.  Avoid wildcard imports in ordinary application code.
5.  Use meaningful names with units where needed.
6.  Use `is None` and `is not None` for sentinel checks.
7.  Preserve domain distinctions instead of overusing truthiness.
8.  Avoid mutable default arguments.
9.  Keep exception boundaries narrow and observable.
10. Do not swallow unexpected failures.
11. Keep destructive operations explicit.
12. Make timeouts, retries, and thresholds reviewable.
13. Keep secrets out of logs and representations.
14. Separate mechanical formatting from behavioral changes.
15. Automate deterministic formatting.
16. Use linting, typing, testing, and security checks for their distinct
    purposes.
17. Keep repository policy in version control.
18. Align editor, local, pre-commit, and CI behavior.
19. Review tool-generated fixes.
20. Prefer compatibility and correctness over cosmetic purity.

### 1.20.135 Key Takeaways

-   PEP 8 is a style guide, not the Python grammar.
-   Consistency reduces cognitive load and improves maintainability.
-   Readability has direct production value during reviews and
    incidents.
-   Formatting rules should be automated where possible.
-   Human review should focus on behavior, architecture, safety, and
    clarity.
-   Project conventions can extend or intentionally differ from general
    guidance.
-   Public compatibility outranks cosmetic cleanup.
-   Truthiness, exception handling, defaults, and imports can cross from
    style into correctness.
-   Operational code should expose units, thresholds, retries, timeouts,
    mutation, verification, and rollback.
-   Style tooling, type checking, testing, and security analysis solve
    different problems.
-   A perfectly formatted program can still be insecure or incorrect.
-   Production-grade Python style makes important behavior easy to see.

> **Central engineering principle:** Code style is successful when it
> makes correct behavior easier to understand, unsafe behavior easier to
> notice, and team maintenance easier to sustain.
