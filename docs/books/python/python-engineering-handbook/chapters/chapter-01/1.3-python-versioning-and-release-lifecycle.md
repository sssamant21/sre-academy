# Chapter 1 — Python Fundamentals and Development Environment

## 1.3 — Python Versioning and Release Lifecycle

**Workflow Stage:** Technical + Source Review Complete

Production Python engineering requires deliberate management of the Python runtime lifecycle. A Python version is not merely a developer preference: it affects language features, standard-library behavior, security support, dependency compatibility, container images, native extensions, operating-system packages, CI/CD pipelines, and production supportability.

A reliable organization therefore treats the Python runtime as a **managed production dependency**.

### 1.3.1 Why Python Version Management Matters

```text
Application
    │
    ▼
Python Dependencies
    │
    ▼
Python Runtime
    │
    ▼
Operating System / Container Image
    │
    ▼
Infrastructure
```

Changing the Python runtime can expose removed or deprecated behavior, dependency incompatibilities, native-extension problems, performance changes, standard-library differences, packaging changes, and platform compatibility issues. Not upgrading eventually creates security and supportability risk.

Runtime management therefore balances stability, compatibility, security, supportability, and upgrade velocity.

### 1.3.2 Understanding Python Version Numbers

A Python release such as `3.14.2` can be understood as:

```text
3 . 14 . 2
│   │    │
│   │    └── Micro version
│   │
│   └────── Minor / feature-release series
│
└────────── Major version
```

`3.14.2` is a maintenance release within the Python 3.14 feature series. In operational communication, saying only “Python 3” is generally insufficient. Record at least the feature release and, where reproducibility matters, the exact micro release.

### 1.3.3 Current Feature-Release Cadence

Under Python's current release model, a new feature release is scheduled approximately every **12 months**. Production organizations should therefore treat runtime lifecycle planning as recurring annual engineering work rather than an occasional platform migration.

Feature releases can introduce language and standard-library features, interpreter changes, performance improvements, deprecations, C API changes, and packaging implications. Moving from one feature series to the next should be treated as a compatibility event rather than merely a patch operation.

### 1.3.4 Maintenance Releases

Within a supported feature series, maintenance releases provide fixes appropriate to that lifecycle phase. Organizations should have a controlled mechanism for adopting supported maintenance releases rather than permanently pinning production to the initial release of a feature series.

Maintenance updates should still pass appropriate automated tests and deployment validation.

### 1.3.5 Python Release Lifecycle

The official lifecycle model uses these states:

```text
Feature
   │
   ▼
Prerelease
   │
   ▼
Bugfix
   │
   ▼
Security
   │
   ▼
End of Life
```

For Python 3.13 and newer under the current policy, the bugfix phase is approximately **two years**, followed by security-only maintenance until approximately **five years** after the initial release. During the security phase, releases are source-only and issued as needed for applicable security fixes.

Exact dates are release-specific and must always be checked against the official release schedule for the relevant Python series.

### 1.3.6 End of Life Is an Operational Risk

**End of life means upstream support for that Python release series has ended. Continued application execution does not imply continued upstream support.**

An end-of-life runtime introduces security, dependency, vendor-support, operating-system, container-image, compliance, and upgrade-complexity risks. Long-delayed upgrades also create larger compatibility jumps.

A good production principle is: **runtime upgrades should be routine maintenance, not emergency modernization projects**.

### 1.3.7 Development and Prerelease Versions

Before a final feature release, development commonly progresses through alpha, beta, and release-candidate stages before final release.

```text
Alpha → Beta → Release Candidate → Final
```

Production systems should generally run supported final releases unless a deliberate engineering requirement justifies otherwise. Mature teams can use prereleases in CI to discover future compatibility problems before production adoption.

### 1.3.8 Prerelease Testing as an Engineering Practice

A project can test current production versions while also running a compatibility job against an upcoming Python release. This can expose removed APIs, deprecation failures, dependency incompatibilities, native-extension build failures, changed tests, and packaging problems before the migration becomes urgent.

### 1.3.9 Runtime Version Versus Application Version

The Python runtime and application have independent lifecycles. Deployment identity should ideally make the application version, Python runtime version, dependency set, and build artifact identifiable. This improves reproducibility, rollback, and incident analysis.

### 1.3.10 Dependency Compatibility

Runtime upgrades are dependency-graph events. Teams should validate framework support, database drivers, native extensions, build tooling, test frameworks, observability libraries, and other dependencies against the target Python version.

A runtime can be available upstream while a critical dependency is not yet compatible.

### 1.3.11 Native Extensions Increase Upgrade Sensitivity

Native dependencies add Python-version, CPython API/ABI, operating-system, CPU-architecture, compiler/toolchain, and binary-distribution considerations. Production upgrade testing should reproduce the actual target platform rather than relying only on a developer workstation.

### 1.3.12 Operating-System Python Versus Application Python

Linux distributions can use Python for operating-system tooling. Engineers should avoid casually replacing or modifying a distribution-managed interpreter.

```text
Operating-System Python → Managed with the OS ecosystem
Application Python      → Managed for application requirements
```

Applications should have a clearly controlled runtime rather than implicitly depending on whichever `python` executable happens to be globally available.

### 1.3.13 Verify the Executable

Systems can contain multiple interpreters. Diagnostics should verify both executable resolution and version.

```bash
command -v python3
python3 --version
```

Inside Python:

```python
import sys

print(sys.executable)
print(sys.version)
```

**Verify the executable, not only the version string.**

### 1.3.14 Virtual Environments and Version Boundaries

A virtual environment is associated with an interpreter installation. When changing the runtime, prefer creating a fresh environment and reinstalling declared dependencies rather than attempting to transform an old environment across interpreter versions.

```text
New Python Runtime
       │
       ▼
Create New Environment
       │
       ▼
Install Declared Dependencies
       │
       ▼
Run Validation
```

### 1.3.15 Containers and Runtime Versioning

Containers make runtime selection explicit but do not eliminate lifecycle responsibility. The runtime remains part of the image supply chain: base image → Python runtime → dependencies → application → deployable image.

An aging base image can continue reproducing an unsupported or vulnerable foundation even while application code is actively maintained.

### 1.3.16 Floating Versus Controlled Runtime References

`FROM python:3` permits broader feature-version movement than `FROM python:3.14`. However, **feature-version control is not the same as immutable artifact identity**: a tag such as `python:3.14` remains mutable. Environments requiring stronger reproducibility can use immutable image digests and controlled rebuild processes.

Detailed image-pinning strategy belongs in the container chapter.

### 1.3.17 Python Compatibility Metadata

Projects can declare supported Python versions using project metadata. A typical minimum-version declaration is:

```toml
[project]
requires-python = ">=3.12"
```

Compatibility metadata should represent tested support. Avoid unnecessary upper bounds unless there is a genuine, demonstrated incompatibility, because speculative upper bounds can create avoidable dependency-resolution problems.

### 1.3.18 Minimum Supported Python Version

Organizations should establish an approved runtime policy. Without governance, services and automation can drift across many Python versions, increasing CI complexity, security exposure, dependency fragmentation, and operational support burden.

An approved runtime matrix can identify the preferred current release, temporarily supported previous releases, upgrade candidates, and runtimes requiring exceptions or retirement.

### 1.3.19 Production Upgrade Workflow

A controlled feature-version upgrade can follow:

```text
Inventory
   │
   ▼
Compatibility Review
   │
   ▼
Dependency Validation
   │
   ▼
Build New Runtime
   │
   ▼
Automated Tests
   │
   ▼
Performance / Security Validation
   │
   ▼
Staging
   │
   ▼
Canary / Controlled Rollout
   │
   ▼
Production
   │
   ▼
Burn-In
   │
   ▼
Retire Old Runtime
```

The exact stages should reflect system criticality, but runtime upgrades should produce evidence before broad production rollout.

### 1.3.20 Inventory and Compatibility Review

Before an upgrade, identify applications, Python versions and builds, container images, dependencies, native extensions, operating systems, CPU architectures, CI pipelines, and deployment targets. Then review application syntax, deprecations and removals, framework support, database drivers, native extensions, build tooling, and observability integrations.

Deprecation warnings should be treated as early migration evidence rather than ignored until they become blockers.

### 1.3.21 Build Fresh Artifacts

Avoid mutating the production runtime in place. Prefer a new container image, virtual environment, VM image, or other immutable deployment artifact while retaining the known-good previous artifact for rollback.

### 1.3.22 Automated and Performance Validation

Validation can include unit, integration, API, database, contract, security, packaging, startup, and shutdown tests. Runtime changes can also affect CPU, memory, startup time, latency, throughput, garbage-collection behavior, and worker efficiency, so performance-sensitive systems should use representative measurements.

A runtime upgrade that passes only `python --version` has not been meaningfully validated.

### 1.3.23 Staging and Controlled Production Rollout

Staging should validate meaningful integrations such as configuration, secrets, databases, external APIs, messaging, health probes, graceful shutdown, observability, and background workloads. Production rollout can use canary, rolling, blue/green, or phased deployment where architecture permits.

### 1.3.24 Burn-In and Rollback

A successful deployment is not automatically a successful upgrade. During burn-in, observe error rates, latency, CPU, memory, restarts, OOM events, worker failures, database errors, dependency failures, native crashes, and business functionality.

Before deployment, preserve a practical rollback path including the previous runtime, application artifact, dependency set, container image, and known-good configuration where applicable.

### 1.3.25 Avoid Combining Major Changes

Changing the Python runtime, framework, database driver, OS base image, application architecture, and schema simultaneously makes root-cause isolation and rollback unnecessarily difficult. Separate major runtime, dependency, infrastructure, and application changes when practical.

### 1.3.26 CI/CD Version Matrix

CI should reflect the project's runtime support policy. Current production runtimes can be required, the next migration target can become required before adoption, and future prerelease compatibility can initially be informational. This allows compatibility work to begin before production deadlines.

### 1.3.27 Infrastructure Automation and Runtime Drift

SRE/DBRE automation may execute from laptops, bastion hosts, CI runners, Kubernetes jobs, automation servers, cloud functions, and VMs. If these environments provide different runtimes, behavior can drift. Operational tooling should therefore define and verify its runtime requirements.

### 1.3.28 Managed Platform Lifecycles

Serverless and other managed platforms can expose their own Python runtime availability and deprecation schedules. Teams must therefore track two related but distinct lifecycles:

```text
Python Upstream Lifecycle
        +
Platform Runtime Lifecycle
```

A provider deadline can create operational urgency independently of the exact upstream Python timeline.

### 1.3.29 Kubernetes Runtime Governance

Kubernetes permits workloads to use different Python container images, which can create runtime sprawl. Mature platforms can govern this through approved base images, image scanning, dependency policies, CI controls, runtime inventory, deployment metadata, and automated lifecycle detection.

Kubernetes does not solve runtime lifecycle management automatically.

### 1.3.30 Runtime Inventory for SRE

During incidents, engineers should be able to identify the Python implementation, version, build, executable, dependencies, container image, architecture, and application release. Diagnostic metadata must not expose credentials, tokens, or sensitive configuration.

### 1.3.31 Runtime Lifecycle Monitoring

Runtime lifecycle can be tracked as an operational concern using application identity, runtime version, upstream support state, platform support state, upgrade owner, target version, and upgrade deadline. This turns end-of-life from a surprise into planned engineering work.

### 1.3.32 Security Patch Strategy

A healthy operating model allows supported security and maintenance updates to move through automated validation and controlled deployment without requiring a major modernization project every time.

Immutable artifacts still require rebuilding when underlying runtime or operating-system components need updates. **Immutable does not mean permanently unchanged; it means replacing artifacts predictably rather than modifying deployed artifacts unpredictably in place.**

### 1.3.33 Common Production Anti-Patterns

Common failures include treating “still runs” as equivalent to “supported,” maintaining no runtime inventory, upgrading directly in production, reusing old virtual environments across interpreter changes, ignoring native dependencies or deprecation warnings, using floating runtime references without understanding rebuild behavior, never rebuilding containers, and combining runtime migrations with unrelated high-risk changes.

### 1.3.34 Production Upgrade Checklist

Before a Python feature-version upgrade, identify the current and target runtime, verify upstream and provider support, review release notes and deprecations, validate frameworks and dependencies, validate native extensions and platform architecture, build a fresh artifact, run automated/security/performance validation as appropriate, validate observability and lifecycle behavior, deploy to staging, define rollback, use controlled production rollout, monitor burn-in, retire the old runtime, and update runtime inventory.

### 1.3.35 SRE/DBRE Operational Principle

Python runtime lifecycle management belongs to reliability engineering because runtime failure can affect application availability, security, automation reliability, database operations, incident response, deployment safety, cloud operations, and compliance.

**The automation runtime is part of the production system.** It should receive the same lifecycle discipline expected from other production dependencies.

### 1.3.36 Key Takeaways

A Python runtime is a managed production dependency, not merely a developer workstation choice. Engineers should understand feature releases, maintenance releases, prereleases, bugfix support, security-only support, and end of life.

Production runtime management should follow inventory → policy → compatibility testing → controlled upgrade → verification → lifecycle monitoring.

A reliable organization knows which Python versions it operates, knows which are supported, tests future versions before adoption, validates dependencies and native extensions, builds fresh deployment artifacts, performs controlled rollouts, maintains rollback capability, monitors lifecycle state, and deliberately retires unsupported versions.

**Python runtime upgrades should be routine, observable, reversible engineering work—not emergency projects triggered by end-of-life deadlines.**
