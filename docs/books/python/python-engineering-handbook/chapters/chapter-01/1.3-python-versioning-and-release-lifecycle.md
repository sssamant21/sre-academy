# Chapter 1 — Python Fundamentals and Development Environment

## 1.3 — Python Versioning and Release Lifecycle

**Edition:** Revised Final / Canonical

Production Python engineering requires deliberate management of the Python runtime lifecycle. A Python version is not merely a developer preference: it affects language features, standard-library behavior, security support, dependency compatibility, container images, native extensions, operating-system packages, CI/CD pipelines, and production supportability.

A reliable organization therefore treats the Python runtime as a **managed production dependency**.

### 1.3.1 Why Python Version Management Matters

Changing the Python runtime can expose removed or deprecated behavior, dependency incompatibilities, native-extension problems, performance changes, standard-library differences, packaging changes, and platform compatibility issues. Not upgrading eventually creates security and supportability risk. Runtime management therefore balances stability, compatibility, security, supportability, and upgrade velocity.

### 1.3.2 Understanding Python Version Numbers

For `3.14.2`, `3` is the major version, `14` the minor/feature-release series, and `2` the micro version. `3.14.2` is a maintenance release within Python 3.14. In operational communication, record at least the feature release and, where reproducibility matters, the exact micro release.

### 1.3.3 Current Feature-Release Cadence

Under Python's current release model, a new feature release is scheduled approximately every **12 months**. Production organizations should treat runtime lifecycle planning as recurring annual engineering work. Feature releases can introduce language and standard-library features, interpreter changes, performance improvements, deprecations, C API changes, and packaging implications. A feature-version upgrade is therefore a compatibility event, not merely a patch operation.

### 1.3.4 Maintenance Releases

Within a supported feature series, maintenance releases provide fixes appropriate to that lifecycle phase. Organizations should have a controlled mechanism for adopting supported maintenance releases rather than permanently pinning production to the initial release. Maintenance updates should still pass automated tests and deployment validation.

### 1.3.5 Python Release Lifecycle

The official lifecycle model uses these states:

```text
Feature → Prerelease → Bugfix → Security → End of Life
```

For Python 3.13 and newer under the current policy, the bugfix phase is approximately **two years**, followed by security-only maintenance until approximately **five years** after the initial release. During the security phase, releases are source-only and issued as needed for applicable security fixes. These durations describe current upstream policy, not an immutable rule. Exact dates are release-specific and must be checked against the official schedule.

### 1.3.6 End of Life Is an Operational Risk

**End of life means upstream support for that Python release series has ended. Continued application execution does not imply continued upstream support.** An EOL runtime introduces security, dependency, vendor-support, operating-system, container-image, compliance, and upgrade-complexity risks. Runtime upgrades should be routine maintenance, not emergency modernization projects.

### 1.3.7 Development and Prerelease Versions

Development commonly progresses through alpha, beta, release-candidate, and final stages. Production systems should generally use supported final releases unless a deliberate requirement justifies otherwise. Mature teams can use prereleases in CI to discover future compatibility problems before production adoption.

### 1.3.8 Prerelease Testing

Testing upcoming Python releases can expose removed APIs, deprecation failures, dependency incompatibilities, native-extension build failures, changed tests, and packaging problems before migration becomes urgent. Future-version CI can initially be informational and become required as migration approaches.

### 1.3.9 Runtime Version Versus Application Version

The Python runtime and application have independent lifecycles. Deployment identity should make the application version, Python runtime, dependency set, and build artifact identifiable to improve reproducibility, rollback, and incident analysis.

### 1.3.10 Dependency Compatibility

Runtime upgrades are dependency-graph events. Validate framework support, database drivers, native extensions, build tooling, test frameworks, observability libraries, and other dependencies against the target Python version. A runtime can be available upstream while a critical dependency remains incompatible.

### 1.3.11 Native Extensions

Native dependencies add Python-version, CPython API/ABI, operating-system, CPU-architecture, compiler/toolchain, and binary-distribution considerations. Production upgrade testing should reproduce the actual target platform rather than relying only on a developer workstation.

### 1.3.12 Operating-System Python Versus Application Python

Linux distributions can use Python for operating-system tooling. Avoid casually replacing or modifying a distribution-managed interpreter. Applications should have a clearly controlled runtime rather than implicitly depending on whichever `python` executable happens to be globally available.

### 1.3.13 Verify the Executable

Systems can contain multiple interpreters. Verify both executable resolution and version:

```bash
command -v python3
python3 --version
```

```python
import sys
print(sys.executable)
print(sys.version)
```

**Verify the executable, not only the version string.**

### 1.3.14 Virtual Environments and Version Boundaries

A virtual environment is associated with an interpreter installation. When changing runtime, create a fresh environment and reinstall declared dependencies rather than attempting to transform an old environment across interpreter versions.

### 1.3.15 Containers and Runtime Versioning

Containers make runtime selection explicit but do not eliminate lifecycle responsibility. The runtime remains part of the image supply chain. An aging base image can reproduce an unsupported or vulnerable foundation even while application code is actively maintained.

### 1.3.16 Floating Versus Controlled Runtime References

`FROM python:3` permits broader feature-version movement than `FROM python:3.14`, but feature-version control is not immutable artifact identity: a tag such as `python:3.14` remains mutable. Environments requiring stronger reproducibility can use immutable image digests and controlled rebuild processes.

### 1.3.17 Python Compatibility Metadata

Projects can declare supported Python versions:

```toml
[project]
requires-python = ">=3.12"
```

Compatibility metadata should represent tested support. Avoid unnecessary upper bounds unless a genuine demonstrated incompatibility exists.

### 1.3.18 Minimum Supported Python Version

Organizations should establish an approved runtime policy. Without governance, services and automation drift across many Python versions, increasing CI complexity, security exposure, dependency fragmentation, and support burden. Maintain an approved runtime matrix covering preferred, temporarily supported, upgrade-candidate, and retirement-required runtimes.

### 1.3.19 Production Upgrade Workflow

A controlled feature-version upgrade should follow:

```text
Inventory → Compatibility Review → Dependency Validation → Build New Runtime
→ Automated Tests → Performance/Security Validation → Staging
→ Controlled Rollout → Production → Burn-In → Retire Old Runtime
```

Runtime upgrades should produce evidence before broad production adoption.

### 1.3.20 Inventory and Compatibility Review

Identify applications, Python versions/builds, images, dependencies, native extensions, operating systems, architectures, CI pipelines, and deployment targets. Review application syntax, deprecations/removals, frameworks, drivers, native extensions, build tooling, and observability integrations. Treat deprecation warnings as early migration evidence.

### 1.3.21 Build Fresh Artifacts

Avoid mutating production runtimes in place. Prefer a new container image, virtual environment, VM image, or other deployment artifact while retaining the known-good previous artifact for rollback.

### 1.3.22 Automated and Performance Validation

Validation can include unit, integration, API, database, contract, security, packaging, startup, and shutdown tests. Runtime changes can affect CPU, memory, startup time, latency, throughput, garbage collection, and worker efficiency. A runtime upgrade that passes only `python --version` has not been meaningfully validated.

### 1.3.23 Staging and Controlled Rollout

Staging should validate configuration, secrets, databases, external APIs, messaging, health probes, graceful shutdown, observability, and background workloads. Production rollout can use canary, rolling, blue/green, or phased deployment where architecture permits.

### 1.3.24 Burn-In and Rollback

Observe error rates, latency, CPU, memory, restarts, OOM events, worker failures, database errors, dependency failures, native crashes, and business functionality during burn-in. Preserve a practical rollback path including the previous runtime, application artifact, dependency set, image, and known-good configuration where applicable.

### 1.3.25 Avoid Combining Major Changes

Changing runtime, framework, database driver, OS base image, application architecture, and schema simultaneously makes diagnosis and rollback difficult. Separate major runtime, dependency, infrastructure, and application changes when practical.

### 1.3.26 CI/CD Version Matrix

CI should reflect runtime support policy. Production runtimes can be required, the next migration target can become required before adoption, and future prerelease compatibility can initially be informational.

### 1.3.27 Infrastructure Automation and Runtime Drift

SRE/DBRE automation may run from laptops, bastions, CI runners, Kubernetes jobs, automation servers, cloud functions, and VMs. Operational tooling should define and verify its runtime requirements so behavior does not silently drift by execution location.

### 1.3.28 Managed Platform Lifecycles

Teams must track both **Python upstream lifecycle** and **platform runtime lifecycle**. Provider deprecation schedules can create operational deadlines independently of upstream Python dates.

### 1.3.29 Kubernetes Runtime Governance

Kubernetes can create runtime sprawl. Mature platforms can govern Python through approved base images, image scanning, dependency policies, CI controls, runtime inventory, deployment metadata, and automated lifecycle detection.

### 1.3.30 Runtime Inventory for SRE

During incidents, engineers should be able to identify implementation, version, build, executable, dependencies, container image, architecture, and application release. Diagnostic metadata must not expose credentials, tokens, or sensitive configuration.

### 1.3.31 Runtime Lifecycle Monitoring

Track application identity, runtime version, upstream support state, platform support state, upgrade owner, target version, and upgrade deadline. This turns EOL from a surprise into planned engineering work.

### 1.3.32 Security Patch Strategy

Supported security and maintenance updates should move through automated validation and controlled deployment. Immutable artifacts still require rebuilding when runtime or OS components need updates. **Immutable does not mean permanently unchanged; it means replacing artifacts predictably rather than modifying deployed artifacts unpredictably in place.**

### 1.3.33 Common Production Anti-Patterns

Avoid treating “still runs” as “supported,” lacking runtime inventory, upgrading directly in production, reusing old virtual environments across interpreter changes, ignoring native dependencies or deprecations, uncontrolled floating runtime references, never rebuilding containers, and combining runtime migrations with unrelated high-risk changes.

### 1.3.34 Production Upgrade Checklist

Before a feature-version upgrade, identify current/target runtime, verify upstream/provider support, review release notes and deprecations, validate dependencies/native extensions/platform architecture, build a fresh artifact, run appropriate automated/security/performance validation, validate observability, deploy to staging, define rollback, use controlled rollout, monitor burn-in, retire the old runtime, and update inventory.

### 1.3.35 SRE/DBRE Operational Principle

Runtime lifecycle management belongs to reliability engineering because runtime state affects application availability, security, automation reliability, database operations, incident response, deployment safety, cloud operations, and compliance. **The automation runtime is part of the production system.**

### 1.3.36 Key Takeaways

A Python runtime is a managed production dependency. Production runtime management should follow inventory → policy → compatibility testing → controlled upgrade → verification → lifecycle monitoring. Current cadence and support periods must be periodically revalidated against upstream policy.

**Python runtime upgrades should be routine, observable, reversible engineering work—not emergency projects triggered by end-of-life deadlines.**
