# Chapter 1 — Python Fundamentals and Development Environment

## 1.4 — Installing Python

**Workflow Stage:** Technical + Source Review Complete

Installing Python is easy. Installing Python correctly, reproducibly, securely, and maintainably for a production engineering environment requires considerably more thought.

A workstation, CI runner, Linux server, container, Kubernetes workload, and managed cloud environment may all require Python, but they should not automatically use the same installation strategy.

> **Treat the Python runtime as a managed dependency with an explicit owner, version, source, lifecycle, and upgrade path.**

### 1.4.1 Installation Is an Engineering Decision

A production installation should move from runtime requirements through trusted distribution selection, controlled installation, executable verification, application isolation, validation, runtime identity, and lifecycle management. Installation method affects upgrades, security maintenance, reproducibility, dependency management, troubleshooting, automation, and rollback.

### 1.4.2 Determine the Runtime Requirement

Before installing Python, identify the implementation, approved feature version, operating system, CPU architecture, execution environment, ownership boundary, and upgrade mechanism. For most workloads in this handbook the implementation is CPython, but the approved version must still be explicit.

Avoid vague requirements such as `Install Python 3`; use the application's tested runtime policy.

### 1.4.3 Identify the Installation Context

Python may run on developer workstations, CI/CD runners, Linux or Windows hosts, macOS, containers, Kubernetes, cloud VMs, bastions, automation hosts, serverless systems, or other managed platforms. Installation strategy should follow the execution environment and ownership model.

### 1.4.4 Trusted Runtime Sources

Use a trusted source whose ownership, update mechanism, provenance, and support model are understood. Examples include a CPython distribution obtained through an official Python-supported channel, an operating-system distribution, an approved container base image, an organization-controlled repository or base image, an approved runtime manager, or a provider-managed runtime.

Python is executable software; runtime installation is part of the software supply chain.

### 1.4.5 Inspect Before Installing

Before adding another interpreter, determine what already exists.

```bash
command -v python
command -v python3
type -a python3
python3 --version
```

From Python:

```python
import platform
import sys

print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
```

Executable identity matters because multiple runtimes may coexist and shell `PATH` resolution determines which executable runs.

### 1.4.6 Operating-System Python Versus Application Python

Many Linux distributions provide Python as part of the operating-system ecosystem. It may support package-management tooling, administrative utilities, system scripts, or vendor tooling.

> **Do not casually replace, remove, or overwrite a distribution-managed Python runtime.**

```text
OS-Managed Python       → Operating-system lifecycle
Application Python      → Application/platform lifecycle
```

Application requirements should not silently take ownership of an OS-managed interpreter.

### 1.4.7 Linux Installation Strategies

Linux environments commonly use distribution packages, a separately managed application runtime, or an image-based runtime. The choice depends on required Python version, distribution support, isolation requirements, security policy, deployment architecture, and patch-management processes.

Package managers install the Python build provided by their repository; that version is not necessarily the application's preferred feature version. Always verify the resulting executable and version.

Do not blindly copy installation commands across distributions. Verify OS release, architecture, package source, target version, privileges, and change policy first.

### 1.4.8 Building CPython from Source

CPython can be built from source when an approved package does not satisfy a requirement or when specialized runtime engineering requires it. A source build transfers lifecycle responsibility to the team, including build dependencies, compiler/toolchain, configuration, security updates, installation prefix, reproducibility, and rollback.

When installing an additional interpreter on Unix-like systems, official Python guidance recommends `make altinstall` rather than `make install` because `make install` can overwrite or masquerade the generic `python3` executable.

A conceptual controlled build is:

```bash
./configure --prefix=/opt/python/<version>
make
sudo make altinstall
```

The exact prefix and build flags are organizational choices. The production rule is: **do not let a source installation unexpectedly take ownership of the system's generic `python3` command.**

### 1.4.9 Validate Source-Built Capabilities

Build-time library availability affects runtime capabilities. A successful compile and `python --version` do not prove that every required standard-library extension is usable.

Validate workload-required capabilities such as TLS, compression, database libraries, and other extensions. For example:

```python
import platform
import ssl
import sys

print(platform.python_implementation())
print(platform.python_version())
print(sys.executable)
print(ssl.OPENSSL_VERSION)
```

Treat a production runtime build as an artifact that is built, tested, recorded, and promoted.

### 1.4.10 Windows Installation and Runtime Management

For current CPython on Windows, official Python documentation recommends the **Python Install Manager**, available through Python-supported distribution channels including Python.org and the Microsoft Store. It provides a modern mechanism for installing, discovering, and selecting Python runtimes.

Conceptually:

```text
Python Install Manager
        │
        ├── Install runtimes
        ├── List runtimes
        ├── Select runtimes
        └── Manage runtime lifecycle
```

Useful inspection can include:

```powershell
py list
```

and normal runtime verification such as:

```powershell
python --version
```

From Python, verify `sys.executable` and `sys.version` rather than assuming shell resolution is correct.

### 1.4.11 Legacy Windows Launcher

Older Windows environments may contain the previous Python launcher for Windows. Current Python documentation marks that legacy launcher as deprecated and superseded by the Python Install Manager. Do not design new enterprise runtime-management standards around legacy launcher behavior.

When supporting older systems, inventory the actual installation mechanism and runtime-selection behavior before changing it.

### 1.4.12 macOS

macOS environments should distinguish operating-system components from application/development Python. Teams may use an official supported distribution mechanism, an approved package manager, or an approved runtime-management tool according to organizational policy.

Do not build application assumptions around an unspecified system interpreter. Verify:

```bash
command -v python3
python3 --version
```

and inspect `sys.executable` where exact identity matters.

### 1.4.13 Runtime Version Managers

Runtime managers can help maintain multiple Python versions for development and CI. They are useful for multi-version testing and project-specific interpreter selection, but they do not replace dependency management, virtual environments, lifecycle policy, or production governance.

```text
Version Manager      → Which Python interpreter?
Virtual Environment  → Which project dependency environment?
```

### 1.4.14 Virtual Environments

After selecting the intended interpreter, application development should generally use an isolated environment.

```bash
python3 -m venv .venv
```

On a POSIX-style shell, activation commonly looks like:

```bash
source .venv/bin/activate
```

Virtual environments are isolated, disposable state. They should be reproducible from declared dependencies, are not intended to be source-controlled as deployment artifacts, and should be recreated when the interpreter or environment location changes rather than copied between machines.

```text
Python Interpreter
       │
       ▼
Create .venv
       │
       ▼
Install Declared Dependencies
       │
       ▼
Use Environment
       │
       ▼
Recreate When Runtime/Location Changes
```

### 1.4.15 Prefer `python -m pip`

When interpreter association matters, prefer:

```bash
python -m pip install <package>
```

or an explicitly versioned interpreter where appropriate, for example:

```bash
python3.14 -m pip install <package>
```

This reduces ambiguity when several Python installations coexist. Verify association with:

```bash
python --version
python -m pip --version
```

A `ModuleNotFoundError` can result from packages being installed into a different interpreter environment from the one executing the application.

### 1.4.16 Respect Externally Managed Environments

Modern distribution-managed Python installations may contain an `EXTERNALLY-MANAGED` marker. This tells Python-specific package-management tools that the global interpreter environment is owned by another package manager, commonly the operating-system distribution.

```text
EXTERNALLY-MANAGED detected
           │
           ▼
Respect system ownership boundary
           │
           ▼
Use virtual environment / supported application mechanism
```

Do not teach bypassing this protection as a normal application installation procedure. If an environment is externally managed, first use an isolated application environment or the distribution's supported package mechanism.

Likewise, avoid casual `sudo pip install ...` usage that mixes application dependency ownership with OS-managed package state.

### 1.4.17 Containers

For containerized applications, Python should normally be part of the image build rather than manually installed into running containers.

```text
Build Definition
      │
      ▼
Base Image / Python Runtime
      │
      ▼
Dependencies
      │
      ▼
Application
      │
      ▼
Image
```

When the runtime changes, modify the build definition, build a new image, test it, and deploy it. Do not rely on interactive modification of running containers. Detailed image tags, digests, hardening, and scanning belong in Chapter 35.

### 1.4.18 Kubernetes

Kubernetes normally receives the application Python runtime from the container image.

```text
Kubernetes Deployment
        │
        ▼
Container Image
        │
        ▼
Python Runtime
        │
        ▼
Application
```

A runtime upgrade therefore normally means building and deploying a new image, not using `kubectl exec` to install Python manually.

Also distinguish **Python on the Kubernetes node** from **Python inside the application container**. They are separate environments; the pod does not normally use the worker node's Python installation.

### 1.4.19 Cloud VMs and Managed Runtimes

A cloud VM should be treated as a managed operating-system host: determine whether Python is OS-managed, whether a separate application runtime is required, how patches are applied, and whether infrastructure is immutable or long-lived.

For managed/serverless runtimes, the provider supplies the runtime environment, but the application team still owns runtime selection, compatibility testing, dependency compatibility, provider-deprecation response, and migration planning.

Managed does not mean lifecycle-free.

### 1.4.20 CI/CD Runtime Consistency

CI environments should follow the application's declared runtime policy. Avoid development, CI, staging, and production silently using unrelated runtime versions. CI logs should expose the active implementation and version so compatibility evidence is auditable.

### 1.4.21 CPU Architecture

Installation must account for architecture such as x86_64/AMD64 and ARM64/AArch64. Architecture affects native extensions, binary wheels, containers, cloud instances, and multi-architecture Kubernetes clusters.

```python
import platform
print(platform.machine())
```

Capture architecture in runtime inventory where operationally relevant.

### 1.4.22 Baseline Installation Verification

After installation, verify runtime identity and workload-required capabilities:

```python
import platform
import sys

print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("architecture:", platform.machine())
```

Basic shell checks such as `python3 --version`, `python3 -m pip --version`, and `python3 -c "import sys; print(sys.executable)"` prove basic availability, not application readiness.

Production validation may additionally require TLS, database, native-extension, application, and integration testing.

### 1.4.23 Permissions and Ownership

Installation privileges and application execution privileges are separate concerns. An application should not require root privileges merely because runtime installation required administrative privileges.

Avoid application designs requiring write access to system runtime directories or global package directories. Do not solve ownership problems by broadly weakening filesystem permissions.

### 1.4.24 Reproducibility and Runtime Provenance

Prefer version-controlled and automated runtime definitions over undocumented manual production installation. Runtime provenance can include:

```text
Implementation
Version
Distribution Source
Base Image
Build Pipeline
CPU Architecture
Operating System
Build Date
Artifact Identity
Compiler / Build Toolchain (for source builds)
Build Configuration (where relevant)
```

This evidence is valuable during security response, CVE remediation, audits, native-extension failures, and runtime upgrades.

### 1.4.25 Keep Runtime, Dependencies, and Deployment Separate

Maintain conceptual separation:

```text
Install Python Runtime
        │
        ▼
Create Project Environment
        │
        ▼
Install Project Dependencies
        │
        ▼
Install / Deploy Application
```

A successful Python installation does not by itself establish production readiness.

### 1.4.26 Common Production Anti-Patterns

Avoid installing an arbitrary latest runtime without compatibility evidence, replacing OS Python for application convenience, verifying only a version string without executable identity, globally mixing application dependencies with OS package state, using privileged `pip` casually, manually modifying production hosts or running containers without reproducible definitions, ignoring CPU architecture, leaving runtime lifecycle without an owner, and treating interpreter startup as sufficient validation.

### 1.4.27 Troubleshoot Before Reinstalling

When Python appears missing or broken, determine the failed layer first. Investigate executable presence, `PATH`, interpreter selection, virtual environment, support status, dependencies, native extensions, shared libraries, architecture, permissions, and externally managed environment restrictions.

`python: command not found` can indicate absence, PATH problems, a different executable name, an inactive environment, or a changed container image. `ModuleNotFoundError` may indicate a wrong interpreter or environment rather than a need to reinstall Python.

> **Identify the failed layer before changing the runtime.**

### 1.4.28 Engineering Rules

1. Treat Python as a managed production dependency.
2. Select the runtime from tested application compatibility policy.
3. Use trusted runtime sources with understood provenance and lifecycle.
4. Respect ownership of distribution-managed Python.
5. Verify executable identity as well as version.
6. Keep application dependencies separate from OS package ownership.
7. Prefer reproducible, disposable project environments.
8. Use `python -m pip` when interpreter association matters.
9. Respect `EXTERNALLY-MANAGED` boundaries.
10. Avoid uncontrolled privileged package installation.
11. Build runtime changes reproducibly.
12. Do not modify running containers as an installation strategy.
13. Validate CPU architecture and native dependencies.
14. Validate workload-required runtime capabilities.
15. Record runtime provenance.
16. Define patch, upgrade, and retirement ownership.
17. Diagnose environment failures before reinstalling Python.
18. Keep runtime installation, dependency installation, and application deployment separate.

### 1.4.29 Key Takeaways

Production installation is a lifecycle:

```text
Requirements
     │
     ▼
Trusted Runtime Source
     │
     ▼
Controlled Installation
     │
     ▼
Executable Verification
     │
     ▼
Application Isolation
     │
     ▼
Capability Validation
     │
     ▼
Runtime Provenance
     │
     ▼
Lifecycle Management
```

The critical ownership boundary is `Operating-System Python ≠ Application Python`. The critical troubleshooting boundary is `Python Runtime ≠ Virtual Environment ≠ Installed Dependencies ≠ Application`.

> **Install Python in a way that is trusted, reproducible, isolated where appropriate, verifiable, upgradeable, and clearly owned.**
