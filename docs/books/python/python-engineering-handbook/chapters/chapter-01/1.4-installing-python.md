# Chapter 1 — Python Fundamentals and Development Environment

## 1.4 — Installing Python

**Edition:** Revised Final / Canonical

Installing Python is straightforward. Installing Python **correctly, reproducibly, securely, and maintainably for production engineering** requires considerably more thought.

A developer workstation, CI runner, Linux server, Windows host, container, Kubernetes workload, cloud VM, and managed platform may all require Python, but they should not automatically use the same installation strategy.

> **Treat the Python runtime as a managed dependency with an explicit owner, version, source, lifecycle, and upgrade path.**

### 1.4.1 Installation Is an Engineering Decision

Production installation should move from runtime requirements through trusted distribution selection, controlled installation, executable verification, application isolation, capability validation, runtime identity, and lifecycle management. Installation method affects upgrades, security maintenance, reproducibility, dependency management, troubleshooting, automation, and rollback.

### 1.4.2 Determine the Runtime Requirement

Before installing Python, determine the implementation, approved feature version, operating system, CPU architecture, execution environment, ownership boundary, and upgrade mechanism. For most workloads in this handbook the implementation is CPython, but the approved version must still be explicit. Avoid vague requirements such as `Install Python 3`; use the application's tested runtime policy.

### 1.4.3 Identify the Installation Context

Python may run on developer workstations, CI/CD runners, Linux or Windows hosts, macOS, containers, Kubernetes, cloud VMs, bastions, automation hosts, serverless systems, or managed platforms. Installation strategy should follow the execution environment and ownership model.

### 1.4.4 Use Trusted Runtime Sources

Use a runtime source whose ownership, provenance, update mechanism, and support model are understood. Appropriate sources can include a CPython distribution obtained through an official Python-supported channel, an operating-system distribution, approved container base image, organization-controlled repository/base image, approved runtime manager, or provider-managed runtime.

Do not assume that downloading directly from one source is universally preferable to a supported OS/platform mechanism. **Python installation is part of the software supply chain.**

### 1.4.5 Inspect Before Installing

Before adding another interpreter, determine what already exists:

```bash
command -v python
command -v python3
type -a python3
python3 --version
```

```python
import platform
import sys
print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
```

### 1.4.6 Executable Resolution Matters

A system may contain several Python executables. Shell `PATH` resolution determines which one runs. **Verify the executable, not only the version string.** Use `command -v python3`, `python3 --version`, and `sys.executable` where exact identity matters.

### 1.4.7 Operating-System Python Versus Application Python

Many Linux distributions provide Python for OS tooling. **Do not casually replace, remove, or overwrite a distribution-managed Python runtime.** Maintain the ownership boundary: OS-managed Python follows the operating-system lifecycle; application Python follows the application/platform lifecycle.

### 1.4.8 Why Replacing System Python Is Dangerous

Manually replacing an OS-managed interpreter can change compatibility for package managers, administrative utilities, system scripts, and vendor tooling unrelated to the application. Prefer providing an application runtime separately rather than taking ownership of an OS-managed interpreter.

### 1.4.9 Linux Installation Strategies

Linux environments commonly use distribution packages, a separately managed application runtime, or an image-based runtime. The choice depends on required version, distribution support, isolation, security policy, deployment architecture, and patch management.

### 1.4.10 Operating-System Package Managers

OS package managers install the Python build supplied by their repository—not necessarily the application's preferred feature version. A Debian-family example is:

```bash
sudo apt update
sudo apt install python3
```

Commands differ by distribution. Always verify the installed executable and version.

### 1.4.11 Do Not Blindly Copy Installation Commands

Before executing installation commands, verify operating system, distribution version, CPU architecture, package source, target Python version, required privileges, and change policy. This is particularly important on production systems.

### 1.4.12 Building CPython from Source

Source builds can be appropriate when approved packages do not satisfy requirements or specialized runtime engineering is needed. A source build transfers responsibility for build dependencies, compiler/toolchain, configuration, security updates, installation prefix, reproducibility, and rollback to the team.

### 1.4.13 Use Safe Source Installation Boundaries

When installing an additional interpreter on Unix-like systems, official Python guidance recommends `make altinstall` rather than `make install`, because the latter can overwrite or masquerade the generic `python3` executable.

```bash
./configure --prefix=/opt/python/<version>
make
sudo make altinstall
```

The exact prefix and flags are organizational choices. **Do not let a source installation unexpectedly take ownership of the system's generic `python3` command.**

### 1.4.14 Source-Build Dependencies Matter

CPython functionality depends partly on build-time libraries. A successful compilation can still lack workload-required capabilities such as TLS/SSL, compression, SQLite, readline, or other extensions. `Build Succeeded` does not mean `Runtime Fully Validated`.

### 1.4.15 Validate Source-Built Runtimes

```python
import platform
import ssl
import sys
print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("tls:", ssl.OPENSSL_VERSION)
```

Treat a production runtime as an artifact that is built, tested, recorded, and promoted.

### 1.4.16 Windows Installation and Runtime Management

For current CPython on Windows, official Python documentation recommends the **Python Install Manager** as the modern Python-provided mechanism for installing and managing runtimes. It can install, list, select, and manage runtimes. Useful inspection includes:

```powershell
py list
python --version
```

Verify `sys.executable` and `sys.version` rather than assuming shell resolution is correct.

### 1.4.17 Legacy Windows Launcher

Older Windows systems may contain the previous Python launcher for Windows. Current Python documentation treats that older launcher model as legacy/deprecated and superseded by the Python Install Manager. Do not design new enterprise runtime-management standards around legacy launcher behavior.

### 1.4.18 macOS

Distinguish OS components from application/development Python. Teams may use an official supported distribution mechanism, approved package manager, or approved runtime-management mechanism. Do not build application assumptions around an unspecified system interpreter; verify `command -v python3`, `python3 --version`, and `sys.executable` where needed.

### 1.4.19 Runtime Version Managers

Runtime managers help maintain multiple Python versions for development and CI, but do not replace dependency management, virtual environments, lifecycle policy, or production governance. A runtime manager answers **which interpreter?**; a virtual environment answers **which project dependency environment?**

### 1.4.20 Runtime Manager Versus Virtual Environment

A project can select a Python runtime, create a virtual environment from that runtime, and then install project dependencies. Keeping these layers distinct prevents environment-management problems.

### 1.4.21 Create an Application Virtual Environment

```bash
python3 -m venv .venv
```

On a POSIX-style shell:

```bash
source .venv/bin/activate
```

Activation syntax differs by platform/shell. Verify `python --version` and `sys.executable` afterward.

### 1.4.22 Treat Virtual Environments as Disposable State

Virtual environments should generally be considered isolated, reproducible, disposable, and recreatable. Recreate them when the interpreter or location changes rather than copying them between machines/platforms. **Treat virtual environments as reproducible disposable state, not artifacts that must survive runtime replacement.**

### 1.4.23 Prefer `python -m pip`

When interpreter association matters, prefer:

```bash
python -m pip install <package>
```

or an explicitly versioned interpreter where appropriate. This reduces ambiguity when several Python installations coexist.

### 1.4.24 Verify `pip` Association

Use:

```bash
python --version
python -m pip --version
```

A `ModuleNotFoundError` can result from packages being installed into a different interpreter environment from the one executing the application.

### 1.4.25 Respect `EXTERNALLY-MANAGED`

Distribution-managed installations may contain an `EXTERNALLY-MANAGED` marker indicating that the global interpreter environment is owned by another package manager. Respect this boundary and use a virtual environment or supported application mechanism rather than treating the protection as something to bypass routinely.

### 1.4.26 Avoid Casual Privileged `pip` Installation

Commands such as `sudo pip install ...` can mix application package ownership with OS-managed Python state. Keep OS packages under the OS package manager and application dependencies in an application environment.

### 1.4.27 Installing Python in Containers

For containerized applications, Python should normally be part of the image build. Runtime changes should modify the build definition, produce a new image, validate it, and deploy it. Detailed image tagging, digest pinning, non-root execution, scanning, and hardening belong in Chapter 35.

### 1.4.28 Do Not Modify Running Containers as an Installation Strategy

Interactive installation or upgrade inside a running container creates state not represented by the image definition and normally disappears when the container is replaced. **Container runtime changes belong in the build pipeline, not in interactive production shell history.**

### 1.4.29 Python in Kubernetes

Kubernetes normally receives the application's Python runtime from the container image. A Python upgrade therefore normally means updating the image build, testing, deploying, and performing a controlled rollout—not manually installing Python with `kubectl exec`.

### 1.4.30 Kubernetes Node Python Versus Container Python

Python on the Kubernetes worker node and Python inside the application container are separate environments. A pod normally uses the runtime included in its container filesystem rather than the worker node's Python installation.

### 1.4.31 Python on Cloud Virtual Machines

Treat a cloud VM as a managed OS host. Determine whether Python is OS-managed, whether a separate application runtime is required, how security updates are applied, how Python is upgraded, and whether infrastructure is immutable or long-lived. For immutable infrastructure, prefer rebuilding and replacing VM images over uncontrolled mutation.

### 1.4.32 Managed and Serverless Runtimes

Providers may supply Python runtimes, but application teams still own runtime selection, compatibility testing, dependency compatibility, deprecation response, and migration planning. **Managed does not mean lifecycle-free.**

### 1.4.33 CI/CD Runtime Consistency

Development, CI, staging, and production should follow a declared runtime policy. Exact artifacts may differ, but compatibility should be intentional and CI output should expose the active runtime so evidence is auditable.

### 1.4.34 CPU Architecture

Installation must account for architecture such as x86_64/AMD64 and ARM64/AArch64, particularly for native extensions, binary wheels, containers, cloud instances, and multi-architecture Kubernetes clusters.

```python
import platform
print(platform.machine())
```

### 1.4.35 32-Bit and 64-Bit Environments

Architecture can affect addressable memory, native packages, binary compatibility, and external libraries. Verify it explicitly where relevant rather than inferring it from the Python version.

### 1.4.36 Verify the Installation

```python
import platform
import sys
print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("architecture:", platform.machine())
```

Then validate workload-required capabilities and application behavior.

### 1.4.37 Minimal Runtime Health Check

`python3 --version`, `python3 -m pip --version`, and `python3 -c "import sys; print(sys.executable)"` establish basic runtime availability, not application compatibility, database connectivity, TLS behavior, native-extension compatibility, or production readiness.

### 1.4.38 TLS Verification

```python
import ssl
print(ssl.OPENSSL_VERSION)
```

For workloads using HTTPS, cloud APIs, database TLS, or package repositories, TLS capability is part of runtime readiness. Detailed TLS security belongs in later chapters.

### 1.4.39 Installation Permissions

Installation privileges and application execution privileges are separate concerns. An application should not require elevated privileges merely because installing the runtime required administrative access.

### 1.4.40 Filesystem Ownership

Avoid application execution unexpectedly requiring write access to system runtime directories, global package directories, or protected OS paths. Do not solve ownership problems by broadly weakening filesystem controls.

### 1.4.41 Installation Reproducibility

Prefer version-controlled definitions, automated builds, validation, artifacts, and controlled deployment over undocumented manual host changes. Possible mechanisms include Dockerfiles, VM image pipelines, configuration management, infrastructure automation, and CI build definitions.

### 1.4.42 Record Runtime Provenance

Useful provenance includes implementation, version, distribution source, base image, build pipeline, CPU architecture, operating system, build date, and artifact identity. For source builds, also consider compiler/build toolchain and build configuration. This evidence supports security response, CVE remediation, audits, native-extension troubleshooting, and upgrades.

### 1.4.43 Security Considerations

A production runtime belongs to the software supply chain. Use trusted sources, controlled versions, provenance, security updates, artifact validation, and lifecycle ownership. The interpreter is software and must be maintained.

### 1.4.44 Runtime Installation Is Not Dependency Installation

Keep these layers separate: install Python runtime → create project environment → install project dependencies → install/deploy application.

### 1.4.45 Runtime Installation Is Not Application Deployment

A successfully installed interpreter does not establish production readiness. Dependencies, configuration, secrets, observability, testing, security, capacity, deployment strategy, rollback, and operational ownership remain necessary.

### 1.4.46 Common Installation Anti-Patterns

Avoid arbitrary latest-version installation without compatibility evidence, replacing OS Python, unknown executable identity, global application dependencies, casual privileged `pip`, routinely bypassing `EXTERNALLY-MANAGED`, manual production installation, modifying running containers, ignoring architecture, missing lifecycle ownership, and treating a version check as sufficient validation.

### 1.4.47 Production Installation Decision Model

Choose installation strategy based on execution context: approved local/runtime-management strategy for development; OS ownership analysis and OS package or separate managed runtime for hosts/VMs; approved image-based runtime for containers/Kubernetes; and provider-supported runtime for managed platforms. In every case verify runtime, isolate application state where appropriate, validate, record identity, and manage lifecycle.

### 1.4.48 Production Installation Checklist

Before declaring a runtime ready, verify owner, implementation/version, upstream/platform support, architecture, trusted source, provenance, OS ownership boundary, documented/reproducible installation, executable/version, required capabilities, package tooling, application isolation, `EXTERNALLY-MANAGED` handling, dependency path, security/update mechanism, upgrade path, rebuild/rollback strategy, and lifecycle ownership.

### 1.4.49 SRE/DBRE Troubleshooting Model

When Python appears missing or broken, investigate executable presence, `PATH`, interpreter selection, virtual environment, support status, dependencies, native extensions, shared libraries, architecture, permissions, and externally managed environment restrictions before reinstalling.

### 1.4.50 Diagnose Before Reinstalling

`python: command not found` can indicate absence, PATH problems, a different executable name, inactive environment, runtime removal, shell changes, or a changed container image. `ModuleNotFoundError` may indicate a wrong interpreter/environment. **Identify the failed layer before changing the runtime.**

### 1.4.51 Engineering Rules for Installing Python

1. Treat Python as a managed production dependency.
2. Select the runtime from tested application compatibility policy.
3. Use trusted sources with understood provenance and lifecycle.
4. Respect ownership of distribution-managed Python.
5. Verify executable identity as well as version.
6. Keep application dependencies separate from OS package ownership.
7. Prefer reproducible, disposable project environments.
8. Use `python -m pip` when interpreter association matters.
9. Respect `EXTERNALLY-MANAGED` boundaries.
10. Avoid uncontrolled privileged package installation.
11. Use safe boundaries for source-built runtimes.
12. Build runtime changes reproducibly.
13. Do not modify running containers as an installation strategy.
14. Distinguish Kubernetes node Python from container Python.
15. Validate architecture and native dependency compatibility.
16. Test workload-required runtime capabilities.
17. Record runtime provenance.
18. Define patch, upgrade, and retirement ownership.
19. Diagnose environment failures before reinstalling Python.
20. Keep runtime installation, dependency installation, and application deployment separate.

### 1.4.52 Key Takeaways

Production installation follows requirements → trusted runtime source → controlled installation → executable verification → application isolation → capability validation → runtime provenance → lifecycle management.

The critical ownership boundary is **Operating-System Python ≠ Application Python**. The critical troubleshooting boundary is **Python Runtime ≠ Virtual Environment ≠ Installed Dependencies ≠ Application**. The critical Kubernetes boundary is **Python on Kubernetes Node ≠ Python inside Application Container**.

> **Install Python in a way that is trusted, reproducible, isolated where appropriate, verifiable, upgradeable, and clearly owned.**
