# Chapter 1 — Python Fundamentals and Development Environment

## 1.5 — Python Interpreter and REPL

**Workflow Stage:** Technical + Source Review Complete
**Chapter Canonical Progress:** `4/25`

The Python interpreter executes Python code. One of the simplest ways to interact with it is through Python's **interactive mode**, commonly described as a REPL: Read, Evaluate, Print, Loop.

> **Use interactive Python for controlled exploration and diagnosis; use reproducible programs and automation for repeatable production operations.**

### 1.5.1 Interpreter Execution Modes

The interpreter can execute interactive input, source files, command strings, modules, and standard input. This handbook normally assumes CPython unless another implementation is explicitly identified.

### 1.5.2 Starting Interactive Mode

Depending on the environment, an interactive interpreter may be started with `python` or `python3`. Verify runtime identity when it matters:

```bash
command -v python3
python3 --version
```

```python
import platform
import sys
print(platform.python_implementation())
print(platform.python_version())
print(sys.executable)
```

Do not assume a command name uniquely identifies the intended runtime.

### 1.5.3 Interactive Prompts

In normal interactive mode, `sys.ps1` defaults to `>>> ` and `sys.ps2` defaults to `... `. These prompts can be customized and are not Python source syntax.

```text
>>> 2 + 2
4
```

A compound statement normally uses the continuation prompt:

```text
>>> for number in range(3):
...     print(number)
...
0
1
2
```

### 1.5.4 Read–Evaluate–Print–Loop

REPL is a useful conceptual model for interactive Python:

```text
Input → Read → Evaluate → Display Result → Next Input
```

An expression can produce a displayed value, while a statement such as assignment normally does not:

```text
>>> total = 10 + 20
>>> total
30
```

### 1.5.5 Interactive State and Reproducibility

Names created in a session remain available while the process continues. This is convenient but can hide dependencies on previous imports, assignments, working directory, environment variables, and other accumulated state.

> **When a result matters, reproduce it from a clean interpreter process.**

A script or fresh `python -c` invocation may behave differently from a long-lived interactive session.

### 1.5.6 Runtime and Import Inspection

Useful diagnostics include:

```python
import platform
import sys
print(platform.python_implementation())
print(platform.python_version())
print(sys.executable)
print(sys.version)
print(sys.platform)
```

For many modules, inspect origin with:

```python
import package_name
print(package_name.__file__)
```

Inspect the import search path with:

```python
import sys
for path in sys.path:
    print(path)
```

Not every module necessarily has a meaningful `__file__`; detailed import mechanics belong in Chapter 5.

### 1.5.7 Object Inspection

Interactive exploration commonly uses `type()`, `dir()`, `repr()`, and, in normal site-initialized sessions, `help()`.

```python
value = "python"
print(type(value))
print(repr(value))
```

`dir()` is useful for exploration but should not be treated as a formal public API contract.

`help()` is normally added to the built-in namespace by the automatically imported `site` module. It may not be available in the same way when Python is started with options such as `-S` that suppress normal `site` initialization.

### 1.5.8 Interactive `_` Convenience

In the standard interactive interpreter, `_` normally refers to the most recently displayed expression result:

```text
>>> 20 * 5
100
>>> _
100
```

Treat this as an interactive convenience, not application-programming state on which production logic should depend.

### 1.5.9 Syntax Errors, Exceptions, and Tracebacks

Interactive mode provides immediate feedback for syntax errors and runtime exceptions. A traceback communicates execution frames, source locations, exception type, and message. Read the execution path as well as the final exception line.

Fast interactive feedback is useful for diagnosis, but it is not a substitute for automated testing or structured error handling.

### 1.5.10 Interrupting and Exiting

A terminal interrupt, commonly `Ctrl+C`, typically surfaces as `KeyboardInterrupt`. Interruption does not guarantee that no external side effects occurred before the interrupt.

In the normal interactive interpreter, EOF commonly exits the session. On Unix-like terminals this is typically `Ctrl+D`; on Windows it is typically `Ctrl+Z` followed by Enter.

`exit()` and `quit()` are conveniences normally added by `site` for interactive use. They are not the preferred application termination mechanism and may not be available under startup modes that suppress `site`, such as `-S`.

### 1.5.11 Executing Code with `-c`

Python can execute a command string:

```bash
python3 -c "print('hello')"
python3 -c "import sys; print(sys.executable)"
python3 -c "import ssl; print(ssl.OPENSSL_VERSION)"
```

With `-c`, `sys.argv[0]` is `-c`. The current directory is placed at the beginning of the module search path, which can matter when diagnosing unexpected imports. Current CPython 3.14 also automatically dedents the command supplied to `-c`.

Keep `-c` operations small and auditable. Move substantial logic into version-controlled source files.

### 1.5.12 Executing Modules with `-m`

Python can locate a module through normal import machinery and execute it as `__main__`:

```bash
python3 -m <module>
```

Examples include:

```bash
python3 -m pip
python3 -m venv
```

For an executable package, the model is:

```text
python -m package
       │
       ▼
Locate Package
       │
       ▼
Execute package.__main__
```

Detailed module and package execution semantics belong in Chapter 5.

### 1.5.13 Standard Input and Interactive Input

Interactive terminal input and non-interactive standard input are different execution contexts. When Python reads commands interactively from a terminal, it processes interactive input incrementally. When source is supplied as a script or through non-interactive standard input, it is handled as script input rather than as a normal terminal REPL session.

For substantial automation, prefer version-controlled source over complex piped program text.

### 1.5.14 Interactive Mode After Execution with `-i`

The `-i` option can enter interactive mode after executing a script, `-c` command, or `-m` module. This can be valuable for inspecting state after execution or a failure.

```bash
python3 -i diagnostic.py
```

This is a powerful diagnostic mode because the resulting session can expose live program state. Treat it as privileged interactive access. `PYTHONSTARTUP` is not processed for this post-execution interactive mode.

### 1.5.15 Isolated Mode as a Diagnostic Tool

CPython's `-I` isolated mode reduces influence from user-specific environment state. Among its restrictions, it ignores `PYTHON*` environment variables and excludes user site-packages and the script directory from `sys.path`.

This can help test whether user packages, environment variables, or local path injection contribute to unexpected behavior.

Do not assume that success in isolated mode alone establishes production correctness; use it to narrow a hypothesis.

### 1.5.16 REPL Versus Script

Use interactive Python for exploration, quick validation, runtime inspection, small calculations, API discovery, and troubleshooting. Use source files for repeatable logic, testing, code review, version control, deployment, automation, and production operations.

> **An operationally important command should not exist only in terminal history.**

### 1.5.17 Production Interactive Safety

Interactive Python in production may inherit the application's filesystem permissions, database credentials, cloud role, Kubernetes service account, network access, and other capabilities.

> **Interactive Python in production is privileged operational access, not a harmless debugging shell.**

Prefer observation before mutation:

```text
Observe → Collect Evidence → Form Hypothesis → Validate → Approved Change
```

### 1.5.18 Database, Cloud, and Kubernetes Safety

A Python session connected to a database can create transactions, locks, DML, DDL, and other persistent effects. Prefer read-only diagnostics where possible, verify the target database, understand transaction boundaries, and avoid leaving sessions idle in transaction.

Before cloud mutations, verify cloud/partition, account/subscription/project, region, identity, target resource, and operation.

Inside Kubernetes, do not assume a pod's service account is read-only. Its effective permissions depend on RBAC and any external credentials available to the workload.

### 1.5.19 Secrets and Sensitive Data

Do not casually print passwords, tokens, cloud credentials, database connection strings, private keys, session tokens, or secret environment variables. Interactive output may be captured by terminal logging, session recording, screen sharing, or troubleshooting artifacts.

Prefer metadata, counts, schema, types, redacted samples, or synthetic examples instead of unnecessary production records.

Do not dump an entire environment in production merely to inspect one value. Inspect the required non-sensitive key explicitly.

### 1.5.20 Preserve Incident Evidence

Interactive experimentation can change the environment being investigated. Collect relevant evidence before mutation when possible. If an interactive experiment reveals a useful fix, reproduce it cleanly and convert it into a version-controlled change, test, automation, or runbook.

A mature operational lifecycle is:

```text
Interactive Discovery
        │
        ▼
Clean Reproduction
        │
        ▼
Version-Controlled Change
        │
        ▼
Test and Review
        │
        ▼
Controlled Deployment
```

### 1.5.21 Environment Context Matters

Interactive behavior can depend on current working directory, environment variables, `PATH`, virtual environment, installed packages, startup configuration, user identity, and container image.

Inspect the working directory with:

```python
import os
print(os.getcwd())
```

Inspect a specific non-sensitive environment variable with:

```python
import os
print(os.environ.get("APP_ENV"))
```

Avoid indiscriminately printing all environment variables in production.

### 1.5.22 Import and Capability Validation

Small clean-process diagnostics can answer narrow questions:

```bash
python3 -c "import package_name"
python3 -c "import ssl; print(ssl.OPENSSL_VERSION)"
python3 -c "import platform; print(platform.machine())"
python3 -c "import sys; print(sys.version)"
```

A successful import proves only that the selected interpreter can resolve and load the package sufficiently to complete import; it does not establish overall application health.

### 1.5.23 Performance and Memory Observations

The REPL is useful for quick observations but not controlled benchmarking. Results can be affected by warm caches, accumulated imports, interactive state, sample size, and system load.

Likewise, a long-lived interactive namespace can retain object references. Memory behavior in an old session may differ from a clean application process.

Important performance or memory findings should be reproduced with proper benchmarking or profiling techniques covered later in the handbook.

### 1.5.24 Common Anti-Patterns

Avoid assuming `python` is the intended interpreter; treating accumulated interactive state as reproducible; running unreviewed production mutations; printing secrets; pasting sensitive records unnecessarily; leaving database transactions open; executing destructive cloud operations without target verification; treating successful import as application health; using quick REPL timing as a benchmark; writing substantial production logic only as `python -c`; or assuming interruption rolled back external side effects.

### 1.5.25 Production Checklist

Before interactive production use:

```text
[ ] Verify Python executable
[ ] Verify runtime version
[ ] Verify environment
[ ] Verify execution identity
[ ] Verify target account/project/subscription
[ ] Verify database/cluster/resource target
[ ] Prefer read-only diagnostics
[ ] Avoid exposing secrets
[ ] Avoid unnecessary sensitive data
[ ] Understand transaction boundaries
[ ] Understand external side effects
[ ] Capture evidence before mutation
[ ] Use approved change procedures
[ ] Reproduce important findings cleanly
[ ] Convert repeatable fixes into code/runbooks
```

### 1.5.26 SRE/DBRE Troubleshooting Pattern

```text
Identify Runtime
      │
      ▼
Identify Environment
      │
      ▼
Identify Execution Identity
      │
      ▼
Inspect Relevant State
      │
      ▼
Collect Evidence
      │
      ▼
Form Hypothesis
      │
      ▼
Run Minimal Safe Test
      │
      ▼
Reproduce Cleanly
      │
      ▼
Implement Controlled Fix
```

This preserves the speed of interactive troubleshooting without abandoning operational discipline.

### 1.5.27 Engineering Rules

1. Verify which interpreter is running.
2. Treat interactive state as temporary.
3. Use interactive mode for exploration and diagnosis.
4. Use source-controlled programs for repeatable operations.
5. Keep `python -c` commands small and auditable.
6. Use `python -m` when execution should be associated with a selected interpreter.
7. Inspect module location and search path when diagnosing imports.
8. Use `-i` deliberately when post-execution state inspection is required.
9. Consider `-I` when isolating environment/user-package effects.
10. Prefer clean-process reproduction for important findings.
11. Treat production interactive access as privileged access.
12. Prefer read-only diagnostics before mutation.
13. Verify execution identity and target environment.
14. Protect secrets and sensitive data.
15. Understand database transactions and external side effects.
16. Capture evidence before changing incident state.
17. Convert useful interactive discoveries into tests, automation, or runbooks.

### 1.5.28 Key Takeaways

Python's interactive mode, commonly called a REPL, provides a rapid feedback loop for learning, exploration, runtime inspection, and troubleshooting.

The important production boundary is:

```text
Interactive Discovery
          ≠
Repeatable Production Automation
```

Prefer:

```text
Explore → Understand → Reproduce → Codify → Test → Review → Deploy
```

> **Use interactive Python to learn and diagnose quickly, but move important production behavior into reproducible, reviewed, and auditable code.**
