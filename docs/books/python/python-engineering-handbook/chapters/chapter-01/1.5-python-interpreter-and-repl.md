# Chapter 1 — Python Fundamentals and Development Environment

## 1.5 — Python Interpreter and REPL

**Edition:** Revised Final / Canonical

The Python interpreter executes Python code. One of the simplest ways to interact with it is through Python's **interactive mode**, commonly described as a **REPL**: Read, Evaluate, Print, Loop.

Interactive Python is invaluable for learning, experimentation, runtime inspection, troubleshooting, and rapid validation. In production engineering, however, interactive execution must be treated with the same discipline as any other privileged operational interface.

> **Use interactive Python for controlled exploration and diagnosis; use reproducible programs and automation for repeatable production operations.**

### 1.5.1 The Python Interpreter

The interpreter executes interactive input, source files, command strings, modules, and standard input. This handbook normally assumes CPython unless another implementation is explicitly identified.

### 1.5.2 Interactive Mode and the REPL

Python's official documentation describes the interpreter's **interactive mode**. REPL is the common conceptual description of its interaction cycle:

```text
Read → Evaluate → Print → Loop
```

REPL should not be mistaken for a separate Python language subsystem.

### 1.5.3 Starting Interactive Python

Depending on the environment, start with `python` or `python3`. Verify runtime identity when it matters:

```bash
command -v python3
python3 --version
```

```python
import platform
import sys
print(platform.python_implementation())
print(platform.python_version())
print(sys.executable)
```

> **Do not assume a command name uniquely identifies the intended Python runtime.**

### 1.5.4 Primary and Continuation Prompts

In normal interactive mode, `sys.ps1` and `sys.ps2` normally default to `>>> ` and `... ` and can be customized.

```text
>>> 2 + 2
4
```

```text
>>> for number in range(3):
...     print(number)
...
0
1
2
```

The prompts are interactive conventions, not Python source syntax.

### 1.5.5 Expressions and Statements

Expressions can produce displayed values while statements such as assignment normally do not:

```text
>>> total = 10 + 20
>>> total
30
```

### 1.5.6 Interactive State

Names created in a session remain available while the interpreter process continues. That state is process-local unless explicitly persisted elsewhere.

### 1.5.7 Interactive State Can Hide Dependencies

Long-running sessions can accumulate imports, variables, changed objects, working-directory state, cached data, and open connections.

> **When a result matters, reproduce it from a clean interpreter process.**

### 1.5.8 Inspecting Runtime Identity

```python
import platform
import sys
print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("platform:", sys.platform)
print(sys.version)
```

### 1.5.9 Inspecting Module Origin

For many modules:

```python
import package_name
print(package_name.__file__)
```

This can reveal whether the module came from the expected virtual environment, global installation, source tree, or another package location. Not every module exposes a meaningful `__file__`.

### 1.5.10 Inspecting the Import Search Path

```python
import sys
for path in sys.path:
    print(path)
```

Detailed import mechanics belong in Chapter 5.

### 1.5.11 Inspecting Objects

Interactive exploration commonly uses `type()`, `dir()`, `repr()`, and `help()`. `dir()` is useful for exploration but should not be treated as a formal public API contract.

### 1.5.12 Interactive `help()`

In a normal environment initialized through `site`:

```python
help(str)
help(len)
```

`help()` is normally made available through `site`; startup modes such as `-S` can change this environment. Treat it as a normal interactive convenience rather than an unconditional startup guarantee.

### 1.5.13 `type()`

```text
>>> type(10)
<class 'int'>
>>> type("hello")
<class 'str'>
```

### 1.5.14 `id()` and Object Identity

`id(object)` returns an integer representing an object's identity during its lifetime. Do not treat it as a portable application-level memory-address contract.

### 1.5.15 `repr()` Versus User-Facing Output

```text
>>> value = "hello\nworld"
>>> value
'hello\nworld'
>>> print(value)
hello
world
```

Object representation and formatted user output are different concerns.

### 1.5.16 Interactive `_` Convenience

In the standard interactive interpreter, `_` normally refers to the most recently displayed expression result:

```text
>>> 20 * 5
100
>>> _
100
```

Do not build application logic around interactive `_` state.

### 1.5.17 Multiline Interactive Input

```text
>>> if True:
...     print("ready")
...
ready
```

Interactive compound input differs operationally from executing a normal source file.

### 1.5.18 Syntax Errors

Interactive mode provides immediate syntax feedback. Fast feedback is useful, but it is not a substitute for automated tests.

### 1.5.19 Runtime Exceptions

Syntactically valid code can still fail during execution. Detailed exception handling belongs in Chapter 7.

### 1.5.20 Reading Tracebacks

A traceback provides execution frames, source locations, exception type, and message. Read both the execution path and the final exception information.

### 1.5.21 Interrupting Interactive Execution

A terminal interrupt, commonly `Ctrl+C`, typically surfaces as `KeyboardInterrupt`. Interrupting execution does not automatically reverse database writes, API calls, file changes, or other external side effects.

### 1.5.22 Exiting Interactive Python

Common EOF behavior is:

```text
Unix-like systems → Ctrl+D
Windows           → Ctrl+Z, then Enter
```

`exit()` and `quit()` are conveniences normally provided through `site` initialization. They should not be the architectural basis for application termination and may differ under startup modes such as `-S`.

### 1.5.23 Executing a Command with `-c`

```bash
python3 -c "print('hello')"
python3 -c "import sys; print(sys.executable)"
python3 -c "import ssl; print(ssl.OPENSSL_VERSION)"
```

Use `-c` for small, auditable operations.

### 1.5.24 Important `-c` Runtime Context

With `-c`, `sys.argv[0]` is `-c`, and the current directory participates at the beginning of the module search path. This can matter when diagnosing unexpected imports. Current CPython 3.14 also automatically dedents the supplied command; production logic should not unnecessarily depend on version-specific command-string formatting behavior.

### 1.5.25 Keep `-c` Commands Small

Move substantial logic involving complex quoting, branching, database mutations, cloud changes, or multiple external calls into version-controlled source files.

### 1.5.26 Executing Modules with `-m`

```bash
python3 -m <module>
python3 -m pip
python3 -m venv
```

Python locates the module through import machinery and executes it as `__main__`, keeping execution associated with the selected interpreter.

### 1.5.27 Executing Packages with `-m`

An executable package can provide a `__main__` module:

```text
python -m package → locate package → execute package.__main__
```

Detailed semantics belong in Chapter 5.

### 1.5.28 Standard Input Versus Interactive Input

Interactive terminal/TTY input and non-interactive standard input are different execution contexts. Interactive input is processed incrementally; piped or redirected source is handled as script-style input. Prefer version-controlled source for substantial automation.

### 1.5.29 Interactive Mode After Execution with `-i`

`-i` can enter interactive mode after executing a script, `-c` command, or `-m` module:

```bash
python3 -i diagnostic.py
```

This can be valuable for inspecting post-execution state.

### 1.5.30 `-i` Is Powerful Production Access

Post-execution interactive access may expose application objects, imported modules, configuration, connections, credentials, and runtime state. Treat `python -i` against production workloads as privileged operational access. `PYTHONSTARTUP` is not processed for this post-execution interactive mode.

### 1.5.31 Isolated Mode with `-I`

```bash
python3 -I
```

Isolated mode reduces influence from user-specific state. Among its restrictions, it ignores `PYTHON*` environment variables and excludes user site-packages and the script directory from the module search path. It can help determine whether environment variables, user packages, or local path injection contribute to a problem.

### 1.5.32 REPL Versus Script

Use interactive Python for exploration, quick validation, runtime inspection, small calculations, API discovery, and troubleshooting. Use source files for repeatable logic, testing, code review, version control, deployment, automation, and production operations.

> **An important production command should not exist only in someone's terminal history.**

### 1.5.33 Interactive Python as a Troubleshooting Tool

Interactive execution can answer which Python is running, which package was imported, where it came from, what `sys.path` contains, which architecture and TLS library are active, and whether a module can import.

### 1.5.34 Production Interactive Safety

Interactive Python in production can inherit application identity, cloud roles, database credentials, filesystem access, network access, Kubernetes service accounts, and secret access.

> **Interactive Python in production is privileged operational access, not a harmless debugging shell.**

### 1.5.35 Read-Only Diagnostics First

Prefer:

```text
Observe → Collect Evidence → Form Hypothesis → Minimal Safe Test → Validate → Approved Change
```

### 1.5.36 Database Safety

A Python session connected to a database can execute SELECT, DML, DDL, locks, transactions, stored procedures, and external calls. Prefer read-only access where possible, verify the target database, understand transaction boundaries, avoid idle-in-transaction sessions, and use approved procedures for mutations.

### 1.5.37 Cloud Safety

Before cloud mutations, verify cloud/partition, account/subscription/project, region, identity, target resource, and operation. For repeatable remediation, prefer reviewed automation with guardrails.

### 1.5.38 Kubernetes Safety

A Python process inside a Kubernetes workload may inherit a service account, cloud workload identity, mounted credentials, network access, and application secrets. Verify effective identity and permissions before interactive operations.

### 1.5.39 Protect Secrets

Do not casually print passwords, API tokens, cloud credentials, database connection strings, private keys, session tokens, or secret environment variables. Interactive output can be captured by terminal logging, session recording, screen sharing, tickets, and incident notes.

### 1.5.40 Protect Sensitive Production Data

Prefer metadata, counts, schema, types, redacted samples, or synthetic examples when they are sufficient. Avoid unnecessarily copying regulated or confidential production records into interactive sessions.

### 1.5.41 Environment Variables

Inspect required non-sensitive keys explicitly:

```python
import os
print(os.environ.get("APP_ENV"))
```

Avoid routinely dumping the complete environment because it may contain credentials.

### 1.5.42 Current Working Directory

```python
import os
print(os.getcwd())
```

The working directory can affect relative paths, command behavior, configuration discovery, and aspects of import resolution.

### 1.5.43 Startup Environment Matters

Interactive behavior can depend on working directory, environment variables, PATH, virtual environment, installed packages, startup configuration, user identity, and container image. Record these differences before concluding that Python itself behaves differently.

### 1.5.44 Import Validation

```bash
python3 -c "import package_name"
```

A successful import proves only that the selected interpreter can resolve and load the package sufficiently for import to complete. It does not establish overall application health.

### 1.5.45 Runtime Capability Checks

```bash
python3 -c "import ssl; print(ssl.OPENSSL_VERSION)"
python3 -c "import platform; print(platform.machine())"
python3 -c "import sys; print(sys.version)"
python3 -c "import sys; print(sys.executable)"
```

Each should answer a narrow operational question.

### 1.5.46 Preserve Incident Evidence

Interactive mutation can alter the environment being investigated. Collect relevant evidence before changing application or runtime state when practical.

### 1.5.47 Reproduce Important Findings

Move successful interactive discoveries through clean reproduction, version-controlled change, automated test, review, and controlled deployment.

### 1.5.48 Avoid Interactive Remediation Drift

A mature SRE process captures valuable interactive discoveries in code, tests, automation, monitoring, runbooks, or documentation rather than leaving fixes only in shell history.

### 1.5.49 Interactive Performance Testing

The interactive interpreter is useful for quick observations but not controlled benchmarking. Warm caches, imports, accumulated state, sample size, background load, and measurement technique can distort conclusions.

### 1.5.50 Interactive Memory Observations

A long-lived interactive namespace can retain object references. Memory observed in an old REPL may differ from a clean application process.

### 1.5.51 Clean-Process Validation

Important observations should progress from interactive discovery to a clean process, repeatable diagnostic, and automated test.

### 1.5.52 Common Interactive Anti-Patterns

Avoid assuming `python` is the intended runtime; treating accumulated state as reproducible; unreviewed production mutation; printing secrets; pasting unnecessary sensitive records; leaving database transactions open; cloud mutation without identity verification; assuming pod access is harmless; treating successful import as application health; treating REPL timing as a benchmark; large `python -c` production programs; assuming `Ctrl+C` rolls back external effects; and interactive fixes without codification.

### 1.5.53 Production Interactive Checklist

```text
[ ] Verify Python executable
[ ] Verify runtime implementation/version
[ ] Verify virtual/application environment
[ ] Verify execution identity
[ ] Verify account/subscription/project
[ ] Verify region where relevant
[ ] Verify database/cluster/resource target
[ ] Understand effective permissions
[ ] Prefer read-only diagnostics
[ ] Avoid exposing secrets
[ ] Avoid unnecessary sensitive data
[ ] Understand transaction boundaries
[ ] Understand external side effects
[ ] Capture evidence before mutation
[ ] Use approved change procedures
[ ] Reproduce important findings cleanly
[ ] Convert repeatable fixes into code/tests/runbooks
```

### 1.5.54 SRE/DBRE Troubleshooting Pattern

```text
Identify Runtime
      ↓
Identify Environment
      ↓
Identify Execution Identity
      ↓
Identify Target
      ↓
Inspect Relevant State
      ↓
Collect Evidence
      ↓
Form Hypothesis
      ↓
Run Minimal Safe Test
      ↓
Reproduce Cleanly
      ↓
Implement Controlled Fix
```

### 1.5.55 Engineering Rules for the Interpreter and REPL

1. Verify which interpreter is running.
2. Treat REPL as the common conceptual term for Python interactive mode.
3. Treat interactive state as temporary.
4. Use interactive mode for exploration and diagnosis.
5. Use source-controlled programs for repeatable operations.
6. Remember that normal prompts are customizable and are not source syntax.
7. Keep `python -c` commands small and auditable.
8. Account for working-directory import effects when using `-c`.
9. Use `python -m` when module execution should be associated with a selected interpreter.
10. Inspect module origin and `sys.path` when diagnosing imports.
11. Use `-i` deliberately when post-execution inspection is required.
12. Consider `-I` when isolating user/environment influences.
13. Prefer clean-process reproduction for important findings.
14. Treat production interactive access as privileged access.
15. Prefer read-only diagnostics before mutation.
16. Verify execution identity and target environment.
17. Protect secrets and sensitive data.
18. Understand database transactions and external side effects.
19. Remember that interruption does not automatically undo external changes.
20. Capture evidence before modifying incident state.
21. Convert useful interactive discoveries into tests, automation, or runbooks.

### 1.5.56 Key Takeaways

Python's interactive mode provides a rapid feedback loop commonly described as:

```text
Read → Evaluate → Print → Loop
```

The production boundary is:

```text
Interactive Discovery ≠ Repeatable Production Automation
```

Prefer:

```text
Explore → Understand → Reproduce → Codify → Test → Review → Deploy
```

> **Use interactive Python to learn and diagnose quickly, but move important production behavior into reproducible, reviewed, tested, and auditable code.**
