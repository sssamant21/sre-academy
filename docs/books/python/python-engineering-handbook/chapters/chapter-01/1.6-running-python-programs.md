# Chapter 1 — Python Fundamentals and Development Environment

## 1.6 — Running Python Programs

**Edition:** Revised Final / Canonical

Installing Python establishes a runtime. Running an application adds an execution context: the selected interpreter, application artifact, dependencies, arguments, environment, working directory, identity, standard streams, external dependencies, resource limits, and supervisor can all influence behavior.

> **Run Python programs through explicit, reproducible execution paths with known runtime identity, configuration, working directory, permissions, and failure behavior.**

### 1.6.1 Running a Source File

A source file can be executed with an explicitly selected interpreter:

```bash
python3 hello.py
```

The execution path is caller or supervisor → Python executable → source file → program execution → output, side effects, and exit status. The command used to launch the program is part of its runtime identity.

### 1.6.2 Runtime Identity

Commands such as `python app.py`, `python3 app.py`, `python3.14 app.py`, and `.venv/bin/python app.py` may select different runtimes. Verify the actual interpreter when it matters:

```python
import sys
print(sys.executable)
print(sys.version)
```

Do not begin diagnosing application behavior without establishing which interpreter launched the process.

### 1.6.3 Source-File Execution Model

A simplified CPython model is source file → read source → compile → code objects/bytecode → execute. CPython bytecode is an implementation detail rather than a stable application compatibility interface.

### 1.6.4 Top-Level Execution and `__main__`

Python assigns `__name__ == "__main__"` to the top-level execution environment. That environment can arise from source-file execution, `-m`, `-c`, standard input, or interactive execution.

A common engineering convention is:

```python
def main() -> int:
    print("application starting")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

A `main()` function is not a Python requirement. It creates a clear boundary for application entry, testing, lifecycle control, and exit-status handling.

### 1.6.5 Import-Time Execution Safety

Python executes a module's top-level statements when that module is initialized. Avoid architectures where merely importing application code unexpectedly causes destructive or irreversible external work such as database mutation, cloud changes, file deletion, or job execution.

> **Importing application code should not unexpectedly perform destructive operational work.**

Detailed import behavior belongs in Chapter 5.

### 1.6.6 Command-Line Arguments

Python exposes user-program arguments through `sys.argv`:

```python
import sys
print(sys.argv)
```

The meaning of `sys.argv[0]` depends on invocation mode. For ordinary source-file execution it identifies the script path/name exposed to the program; `-c` uses `-c`.

When interpreter-level invocation details matter, `sys.orig_argv` preserves the original arguments passed to the Python executable, while `sys.argv` contains arguments exposed to the user program after interpreter options are processed.

Production programs should validate required arguments, allowed values, defaults, and error behavior. Detailed CLI architecture belongs in Chapter 24.

### 1.6.7 Environment Variables and Secrets

Programs commonly receive configuration through the process environment:

```python
import os
print(os.environ.get("APP_ENV"))
```

Do not indiscriminately print the complete environment in production. It may contain passwords, tokens, connection strings, cloud credentials, API keys, or other secrets. Inspect only values required for diagnosis and redact sensitive data.

### 1.6.8 Current Working Directory

Inspect the current working directory with:

```python
import os
print(os.getcwd())
```

Relative paths depend on process context and may behave differently under an interactive shell, service manager, scheduler, container, or CI runner. A production application should deliberately define path-resolution behavior.

### 1.6.9 Script Directory and `sys.path`

For ordinary source-file execution such as `python3 app.py`, Python normally places the script directory at the beginning of the module search path. When the script path is a symbolic link, Python resolves the link when determining this path behavior.

Do not confuse the current working directory with the directory containing the script; they can differ. Detailed import-path mechanics belong in Chapter 5.

### 1.6.10 Process Identity and Least Privilege

A Python process runs with an operating-system identity and corresponding filesystem, network, credential, and resource permissions. Installation may require administrative privileges; routine application execution generally should not.

> **Do not run a Python service as root merely to bypass an unresolved permissions problem.**

Use a deliberate least-privilege service identity appropriate to the workload.

### 1.6.11 Standard Streams

Python exposes standard text streams through `sys.stdin`, `sys.stdout`, and `sys.stderr`. `input()` normally reads through standard input, `print()` normally writes to standard output, and diagnostics can use standard error.

```python
import sys
print("normal output")
print("diagnostic output", file=sys.stderr)
```

These stream objects may be redirected or replaced and should not be assumed to map permanently to a physical terminal. In production they may be captured by service managers, container runtimes, Kubernetes, CI/CD systems, or logging infrastructure.

### 1.6.12 Stream Buffering and `-u`

Output buffering can affect when logs become visible, particularly when output is redirected to a pipe or collector.

```bash
python3 -u app.py
```

The `-u` option changes buffering behavior for standard output and standard error; it does not make standard input unbuffered. Use it deliberately when the operational environment requires more immediate output visibility.

### 1.6.13 Exit Status

Operating systems and supervisors use process status to determine success or failure. Conventionally, status `0` represents success and nonzero values represent failure or another application-defined condition. Specific meanings are platform and application conventions; keep exit codes intentional, documented, and reasonably portable.

Exit status matters to shells, CI/CD, service managers, Kubernetes Jobs, schedulers, workflow engines, and monitoring systems.

### 1.6.14 `sys.exit()` and `SystemExit`

`sys.exit()` raises `SystemExit` rather than directly invoking an unconditional low-level process termination primitive. Therefore normal `finally` cleanup can execute, `SystemExit` can be intercepted, and calling `sys.exit()` from a non-main thread does not by itself terminate the entire process.

A clean pattern is:

```python
import sys


def main() -> int:
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

Passing a non-integer, non-`None` object such as a string normally writes that object to standard error and produces failure status `1`. Larger applications should generally use explicit logging and documented status handling.

### 1.6.15 Unhandled Exceptions

For an uncaught exception other than `SystemExit`, Python invokes its unhandled-exception machinery, including `sys.excepthook`, and a non-interactive program normally terminates unsuccessfully.

> **Do not catch every exception merely to force exit status `0`.**

Swallowing a business failure and reporting process success can cause schedulers and supervisors to record failed work as successful.

### 1.6.16 Module and Package Execution with `-m`

Python can locate a module using normal import machinery and execute it as the top-level `__main__` environment:

```bash
python3 -m package.module
```

If an executable package is supplied, Python executes the package's `__main__` module.

An operationally relevant distinction is that `python script.py` normally leads the import search path with the script directory, while `python -m package.module` leads it with the current working directory. This difference can explain unexpected module resolution.

### 1.6.17 Shell Wrappers

Python programs are often launched through shell scripts, adding another execution layer. Each layer can affect environment variables, working directory, signals, exit status, quoting, and `PATH`.

Keep wrapper scripts small, explicit, and auditable.

### 1.6.18 Shebangs and Runtime Selection

On Unix-like systems, executable scripts can use a shebang such as:

```text
#!/usr/bin/env python3
```

This asks the environment to locate `python3` through `PATH`. An explicit managed interpreter path instead makes runtime selection deployment-specific. Neither strategy is universally superior; choose according to deployment architecture and runtime-governance requirements.

Current Windows Python tooling can also recognize supported Unix-style shebang forms for launcher/runtime selection, but native shebang execution remains fundamentally associated with Unix-like executable-script behavior.

Avoid hard-coded developer-specific interpreter paths as production contracts.

### 1.6.19 Virtual-Environment Execution

Activation is primarily shell convenience. A virtual environment's interpreter can be invoked directly without first activating it.

Unix-like example:

```bash
.venv/bin/python app.py
```

Windows virtual environments use different executable locations, so this exact path is not cross-platform syntax. Services and automation can often invoke the intended environment interpreter directly.

### 1.6.20 Python Versus Supervisor Responsibilities

> **Python defines interpreter and language behavior; surrounding platforms define additional process-lifecycle behavior around Python.**

Those surrounding layers include the operating system, shell, `systemd`, container runtime, Kubernetes, schedulers, CI/CD platforms, and managed cloud services.

Do not mistake scheduler retry rules, Kubernetes Job semantics, `systemd` restart policy, or container signal propagation for Python language guarantees.

### 1.6.21 Linux Services

A Linux service manager such as `systemd` may define the executable, working directory, service user, configuration, restart policy, and resource controls.

Production execution must not depend on undocumented interactive-shell initialization such as `.bashrc`, aliases, shell functions, or a developer's manually activated environment. This is a common cause of "works manually, fails as a service" incidents.

### 1.6.22 Containers

A container should define application startup through reproducible image and deployment configuration: container image → entrypoint/command → Python runtime → application.

Avoid unnecessary wrapper-shell layers because they can complicate signal handling, exit-code propagation, quoting, and process ownership. Detailed container engineering belongs in Chapter 35.

### 1.6.23 Kubernetes

Kubernetes starts the workload according to container image and workload configuration. Execution context may come from environment variables, ConfigMaps, Secrets, mounted files, service accounts, workload identity, and external services.

For batch workloads such as Jobs, process exit status is especially important: Python program → exit status → container status → job outcome. Do not swallow application failure and return success merely to keep a container looking healthy.

### 1.6.24 Scheduled Programs and Overlap

Python programs may run under cron, systemd timers, Kubernetes CronJobs, CI/CD schedules, cloud schedulers, or workflow engines. Scheduled execution should explicitly define runtime, working directory, configuration, credentials, timeout, logging, exit behavior, and concurrency policy.

If jobs can overlap, determine whether concurrent execution is safe. Uncontrolled overlap can create duplicate work, lock contention, API pressure, corruption, or unnecessary cost.

### 1.6.25 Retries and Idempotency

Operational programs may be retried by applications or external supervisors. Ask:

> **If this program executes twice, what happens?**

Where feasible, retryable automation should converge on a known correct state rather than create duplicated or conflicting side effects. Detailed retry, backoff, jitter, and idempotency design belongs in later reliability and SRE chapters.

### 1.6.26 Timeouts and Graceful Termination

Long-running programs should account for network waits, database queries, locks, child processes, and other operations that can block indefinitely. Supervisors may request termination during deployments, scaling, shutdown, maintenance, or node drain.

A deliberate shutdown lifecycle is termination requested → stop accepting new work → finish or safely stop current work → flush required state → close resources → exit. Exact signal behavior depends on workload and platform design.

### 1.6.27 Child Processes

Python applications can launch child processes, introducing responsibilities for exit status, timeouts, signals, output capture, cleanup, and failure propagation. Detailed subprocess management belongs in Chapter 25.

### 1.6.28 CI/CD Execution

CI/CD should use an explicitly provisioned and supported Python runtime: provision approved runtime → install declared dependencies → run program/tests → capture exit status.

Do not rely on an undocumented interpreter that happens to exist on a runner.

### 1.6.29 Managed Cloud Runtimes

A managed or serverless platform may control process launch, but the application team still owns compatibility with runtime version, entry-point or handler contract, configuration, timeouts, memory, concurrency, and error semantics.

> **Provider-managed execution does not eliminate application lifecycle responsibility.**

### 1.6.30 Production Execution Context

A useful production model is:

```text
Python Runtime
      +
Application Artifact
      +
Dependencies
      +
Arguments
      +
Environment
      +
Working Directory
      +
Import Path
      +
Filesystem
      +
Execution Identity
      +
Network
      +
External Services
      +
Resource Limits
```

Two systems can execute identical source code and behave differently because one or more execution-context dimensions changed.

### 1.6.31 "Works Manually" Is Not Production Evidence

A developer shell may have a different `PATH`, activated environment, working directory, configuration, and identity from the production supervisor.

The right question is not merely "Does the program run?" It is:

> **Does the program run correctly under the same execution context used in production?**

### 1.6.32 Production Execution Troubleshooting

Use a layered sequence: identify invocation → Python runtime → application artifact → execution identity → working directory → arguments/configuration → dependencies/import path → standard streams/exit status → external dependencies → resource/platform constraints → reproduce under production-like context → implement controlled fix.

Avoid reinstalling Python before identifying which layer failed.

### 1.6.33 Minimal Execution Diagnostic

A focused diagnostic can record useful non-secret execution context:

```python
import os
import platform
import sys

print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("cwd:", os.getcwd())
print("argv:", sys.argv)
```

When original interpreter arguments matter:

```python
print("original argv:", sys.orig_argv)
```

Do not automatically dump the complete environment or credentials.

### 1.6.35 Common Execution Anti-Patterns

Avoid assuming `python` selects the intended runtime; destructive import-time behavior; blindly indexing `sys.argv`; dumping the full process environment; accidental working-directory dependencies; running as root to avoid fixing permissions; swallowing exceptions and returning success; complex undocumented exit-code schemes; depending on interactive shell initialization; excessive shell-wrapper layers; hard-coded developer interpreter paths; treating virtual-environment activation as mandatory; uncontrolled scheduled-job overlap; blind retries of non-idempotent operations; ignoring termination behavior; depending on an undocumented CI runtime; and treating "works manually" as production proof.

### 1.6.36 SRE/DBRE Execution Model

For operational diagnosis, ask: who launched the process → how was Python invoked → which runtime executed → which artifact executed → which identity executed it → what was the working directory/import context → which arguments and configuration applied → what did stdout/stderr report → what exit status was returned → which external dependency or platform constraint failed → can the behavior be reproduced under production-like conditions?

### 1.6.37 Engineering Rules

1. Make interpreter selection explicit.
2. Verify runtime identity before diagnosis.
3. Understand the top-level `__main__` environment.
4. Use a clear application entry point where appropriate.
5. Avoid unintended destructive import-time side effects.
6. Understand `sys.argv` in the actual invocation mode.
7. Use `sys.orig_argv` when original interpreter invocation details matter.
8. Validate program arguments.
9. Treat environment variables as execution context and protect secrets.
10. Understand working-directory and import-path assumptions.
11. Run applications with least privilege.
12. Treat Python standard streams as redirectable process interfaces.
13. Use `-u` deliberately and remember it concerns stdout/stderr rather than stdin.
14. Preserve meaningful exit status.
15. Remember that `sys.exit()` raises `SystemExit`.
16. Do not hide failures by reporting success.
17. Understand file execution versus `-m` import-path behavior.
18. Keep shell wrappers simple and auditable.
19. Choose shebang/runtime selection according to deployment architecture.
20. Avoid developer-specific interpreter paths.
21. Treat virtual-environment activation as shell convenience, not a runtime requirement.
22. Separate Python guarantees from supervisor/platform behavior.
23. Do not depend on interactive shell initialization in production.
24. Make container, Kubernetes, scheduler, and CI execution reproducible.
25. Evaluate retries, idempotency, overlap, timeouts, and shutdown behavior.
26. Reproduce incidents under production-like execution context.
27. Version-control the execution architecture.

### 1.6.38 Key Takeaways

Running Python is not merely `python app.py`. Production behavior emerges from the supervisor/user/scheduler, invocation, Python runtime, application entry point, and execution context—including arguments, environment, working directory, import path, identity, filesystem, network, external services, and resource limits—before finally producing application behavior, standard-stream output, and exit status.

> **A Python program must be evaluated under the execution context that actually launches it in production.**

> **Python defines interpreter and language behavior; the operating system and surrounding platforms add process-lifecycle behavior.**

> **Make Python program execution explicit, reproducible, observable, least-privileged, and capable of reporting failure correctly.**
