# Chapter 1 — Python Fundamentals and Development Environment

## 1.6 — Running Python Programs

**Workflow Stage:** Technical + Source Review Complete
**Chapter Canonical Progress:** `5/25`

Installing Python establishes a runtime. Running an application adds an execution context: the selected interpreter, application artifact, arguments, environment, working directory, identity, standard streams, external dependencies, resource limits, and supervisor all influence behavior.

> **Run Python programs through explicit, reproducible execution paths with known runtime identity, configuration, working directory, permissions, and failure behavior.**

### 1.6.1 Basic Source-File Execution

A source file can be executed with an explicitly selected interpreter:

```bash
python3 hello.py
```

Conceptually:

```text
Caller / Supervisor
       │
       ▼
Python Executable
       │
       ▼
Source File
       │
       ▼
Program Execution
       │
       ▼
Output / Side Effects / Exit Status
```

The command used to launch the program is part of its runtime identity. `python`, `python3`, a feature-specific executable, and a virtual-environment interpreter may identify different runtimes.

### 1.6.2 Verify the Runtime

Useful diagnostics include:

```python
import sys
print(sys.executable)
print(sys.version)
```

Do not diagnose application behavior before establishing which interpreter actually launched the process.

### 1.6.3 Top-Level Execution and `__main__`

Python assigns `__name__ == "__main__"` to the top-level execution environment. That environment can arise from a directly executed source file and also from other top-level invocation modes such as `-m`, `-c`, standard input, or interactive execution.

A common application convention is:

```python
def main() -> int:
    print("application starting")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

A `main()` function is an engineering convention rather than a Python requirement. It provides a clear entry point, supports testing, reduces unintended import-time execution, and creates an explicit location for exit-status handling.

### 1.6.4 Keep Imports Operationally Safe

Python executes a module's top-level statements when that module is initialized. Application modules should therefore avoid destructive or irreversible work merely as a consequence of import when that behavior is not intentionally part of module initialization.

Prefer placing top-level application execution behind an explicit entry-point boundary.

> **Importing application code should not unexpectedly perform destructive operational work.**

Detailed import behavior belongs in Chapter 5.

### 1.6.5 Command-Line Arguments

Python exposes user-program arguments through `sys.argv`:

```python
import sys
print(sys.argv)
```

For ordinary script execution, `sys.argv[0]` identifies the script path/name as exposed to the program. Other invocation modes use different element-zero semantics; for example, `-c` uses `-c`.

When interpreter-level invocation details matter, `sys.orig_argv` preserves the original arguments passed to the Python executable, while `sys.argv` contains the arguments presented to the user program after interpreter options have been processed.

Production programs should validate required arguments, allowed values, defaults, and error behavior. Detailed CLI architecture belongs in Chapter 24.

### 1.6.6 Environment Variables

Programs commonly receive configuration through the process environment:

```python
import os
print(os.environ.get("APP_ENV"))
```

Do not indiscriminately print the complete environment in production. It may contain passwords, tokens, connection strings, cloud credentials, or other secrets. Inspect only values required for diagnosis and redact sensitive data.

### 1.6.7 Current Working Directory

Inspect the current working directory with:

```python
import os
print(os.getcwd())
```

Relative paths depend on process context and may behave differently under an interactive shell, service manager, scheduler, container, or CI runner.

A production application should deliberately define path-resolution behavior rather than accidentally depend on the directory from which an engineer happened to start it.

### 1.6.8 Script Directory and `sys.path`

For ordinary source-file execution such as:

```bash
python3 app.py
```

Python normally places the script directory at the beginning of the module search path. When the script path is a symbolic link, Python resolves the link when determining this path behavior.

This differs from invocation modes such as `-m`, `-c`, and interactive execution and can explain environment-dependent import results.

Detailed import-path mechanics remain in Chapter 5.

### 1.6.9 Process Identity and Least Privilege

A Python process runs with an operating-system identity and corresponding filesystem, network, credential, and resource permissions.

Installation may require administrative privileges; routine application execution generally should not.

> **Do not run a Python service as root merely to bypass an unresolved permissions problem.**

Use a deliberate least-privilege service identity appropriate to the workload.

### 1.6.10 Standard Input, Output, and Error

Python exposes standard text streams through `sys.stdin`, `sys.stdout`, and `sys.stderr`.

`input()` normally reads through standard input, `print()` normally writes to standard output, and interpreter diagnostics commonly use standard error. These Python stream objects may be redirected or replaced and should not be assumed to map permanently to a physical terminal.

```python
import sys
print("normal output")
print("diagnostic output", file=sys.stderr)
```

In production these streams may be captured by service managers, container runtimes, Kubernetes, CI/CD systems, or logging infrastructure.

### 1.6.11 Stream Buffering and `-u`

Output buffering can affect when logs become visible, particularly when output is redirected to a pipe or log collector.

```bash
python3 -u app.py
```

The `-u` option changes buffering behavior for standard output and standard error; it does not make standard input unbuffered.

Use unbuffered execution deliberately when the operational environment requires more immediate output visibility rather than applying it blindly to every workload.

### 1.6.12 Exit Status Is an Operational Contract

Operating systems and supervisors use process status to determine success or failure. Conventionally, status `0` represents success and nonzero values represent failure or another application-defined condition.

Specific meanings are platform and application conventions. Keep exit codes intentional, documented, and reasonably portable; many environments expect values within `0–127`.

Exit status matters to shells, CI/CD, service managers, Kubernetes Jobs, schedulers, workflow engines, and monitoring systems.

### 1.6.13 `sys.exit()` and `SystemExit`

`sys.exit()` raises the `SystemExit` exception rather than directly invoking an unconditional low-level process termination primitive.

Consequences include:

- normal `finally` cleanup can execute;
- `SystemExit` can be intercepted;
- invoking `sys.exit()` from a non-main thread does not by itself terminate the entire process.

A common pattern is:

```python
import sys


def main() -> int:
    return 0


if __name__ == "__main__":
    sys.exit(main())
```

Passing a non-integer, non-`None` object such as a string to `sys.exit()` normally causes that object to be written to standard error and produces failure status `1`. For larger applications, explicit and documented return/exit-code handling is usually clearer.

### 1.6.14 Unhandled Exceptions

For an uncaught exception other than `SystemExit`, Python invokes its unhandled-exception machinery, including `sys.excepthook`, and a non-interactive program normally terminates unsuccessfully.

Do not catch every exception merely to force status `0`.

A dangerous pattern is:

```text
Business Operation Fails
        │
        ▼
Exception Swallowed
        │
        ▼
Process Reports Success
        │
        ▼
Scheduler Records Success
```

Production programs must preserve meaningful failure semantics.

### 1.6.15 Module and Package Execution with `-m`

Python can locate a module using normal import machinery and execute it as the top-level `__main__` environment:

```bash
python3 -m package.module
```

If an executable package is supplied, Python executes the package's `__main__` module.

An operationally relevant path distinction is:

```text
python script.py
    → script directory leads the import search path

python -m package.module
    → current working directory leads the import search path
```

This difference can explain otherwise surprising import behavior.

Detailed package execution belongs in Chapter 5.

### 1.6.16 Shell Wrappers

Python programs are often launched through shell scripts, adding another execution layer:

```text
Scheduler / Service
       │
       ▼
Shell
       │
       ▼
Python
       │
       ▼
Application
```

Each layer can affect environment variables, working directory, signals, exit status, quoting, and `PATH`.

Keep wrapper scripts small, explicit, and auditable.

### 1.6.17 Shebangs and Runtime Selection

On Unix-like systems, executable scripts can use a shebang such as:

```text
#!/usr/bin/env python3
```

This asks the environment to locate `python3` through `PATH`.

Conceptually:

```text
/usr/bin/env python3
       → PATH-selected runtime

explicit managed interpreter path
       → deployment-selected runtime
```

Neither strategy is universally superior. Choose according to deployment architecture and runtime-governance requirements.

Current Windows Python tooling can also recognize supported Unix-style shebang forms for launcher/runtime selection, but native shebang execution remains fundamentally associated with Unix-like executable-script behavior.

Avoid hard-coded developer-specific interpreter paths as production contracts.

### 1.6.18 Virtual-Environment Execution

Activation is primarily shell convenience. A virtual environment's interpreter can be invoked directly without first activating the environment.

Unix-like example:

```bash
.venv/bin/python app.py
```

Windows virtual environments use different executable locations, so do not treat this exact path as cross-platform syntax.

Conceptually:

```text
Activation
    │
    ▼
Adjust Shell Environment
    │
    ▼
python Resolves to Environment Runtime
```

Services and automation can often invoke the intended environment interpreter directly.

### 1.6.19 Python Versus Supervisor Responsibilities

Python defines interpreter and language behavior. Additional process-lifecycle behavior is supplied by surrounding layers such as the operating system, shell, service manager, container runtime, Kubernetes, CI/CD platform, or cloud service.

```text
Platform / Supervisor
        │
        ▼
Process Lifecycle
        │
        ▼
Python Runtime
        │
        ▼
Application
```

Do not mistake scheduler retry rules, Kubernetes Job semantics, `systemd` restart policy, or container signal propagation for Python language guarantees.

### 1.6.20 Linux Services

A Linux service manager such as `systemd` may define the executable, working directory, service user, configuration, restart policy, and resource controls.

Production execution must not depend on undocumented interactive-shell initialization such as `.bashrc`, aliases, shell functions, or a developer's manually activated environment.

This is a common cause of "works manually, fails as a service" incidents.

### 1.6.21 Containers

A container should define application startup through reproducible image and deployment configuration:

```text
Container Image
      │
      ▼
Entrypoint / Command
      │
      ▼
Python Runtime
      │
      ▼
Application
```

Avoid unnecessary wrapper-shell layers because they can complicate signal handling, exit-code propagation, quoting, and process ownership.

Detailed container engineering belongs in Chapter 35.

### 1.6.22 Kubernetes

Kubernetes normally starts the Python workload according to container image and workload configuration. Configuration may come from environment variables, ConfigMaps, Secrets, mounted files, workload identity, and external services.

For batch workloads such as Jobs, process exit status is especially important:

```text
Python Program
      │
      ▼
Exit Status
      │
      ▼
Container Status
      │
      ▼
Job Outcome
```

Do not swallow application failure and return success merely to keep a container looking healthy.

Detailed Kubernetes deployment behavior belongs later in the handbook.

### 1.6.23 Scheduled Programs

Python programs may run under cron, systemd timers, Kubernetes CronJobs, CI/CD schedules, cloud schedulers, or workflow engines.

Scheduled execution should explicitly define runtime, working directory, configuration, credentials, timeout, logging, exit behavior, and concurrency policy.

If jobs can overlap, determine whether concurrent execution is safe. Uncontrolled overlap can create duplicate work, lock contention, API pressure, corruption, or unnecessary cost.

### 1.6.24 Retries and Idempotency

Operational programs may be retried by applications or external supervisors. Ask:

> **If this program executes twice, what happens?**

Where feasible, retryable automation should converge on a known correct state rather than create duplicated or conflicting side effects.

Detailed retry, backoff, and idempotency design belongs in later reliability and SRE chapters.

### 1.6.25 Timeouts and Graceful Termination

Long-running programs should account for network waits, database queries, locks, child processes, and other operations that can block indefinitely.

Supervisors may request termination during deployments, scaling, shutdown, maintenance, or node drain. A well-designed service should have deliberate shutdown behavior appropriate to its workload.

Detailed signal handling, subprocess management, and reliability patterns belong in later chapters.

### 1.6.26 CI/CD Execution

CI/CD should use an explicitly provisioned and supported Python runtime:

```text
Pipeline
   │
   ▼
Provision Approved Runtime
   │
   ▼
Install Declared Dependencies
   │
   ▼
Run Program / Tests
   │
   ▼
Capture Exit Status
```

Do not rely on an undocumented interpreter that happens to exist on a runner.

### 1.6.27 Managed Cloud Runtimes

A managed or serverless platform may control process launch, but the application team still owns compatibility with runtime version, entry-point/handler contract, configuration, timeouts, memory, concurrency, and error semantics.

> **Provider-managed execution does not eliminate application lifecycle responsibility.**

### 1.6.28 Production Execution Context

A useful production model is:

```text
Python Runtime
      +
Application Artifact
      +
Dependencies
      +
Arguments
      +
Environment
      +
Working Directory
      +
Filesystem
      +
Execution Identity
      +
Network
      +
External Services
      +
Resource Limits
```

Two systems can execute identical source code and behave differently because one or more execution-context dimensions changed.

### 1.6.29 "Works Manually" Is Not Production Evidence

A common failure pattern is:

```text
Engineer Shell
   │
   ├── Different PATH
   ├── Activated Environment
   ├── Different Directory
   └── Different Identity
   │
   ▼
Program Works
```

while the actual supervisor uses another context and fails.

The right question is:

> **Does the program run correctly under the same execution context used in production?**

Investigate systematically:

       │
       ▼
Identify Python Runtime

       ▼

       │
       ▼

       │
       ▼

       │

       │

### 1.6.31 Minimal Execution Diagnostic

A focused diagnostic can record non-secret execution context:

```python
import os
import platform
import sys

print("implementation:", platform.python_implementation())
print("version:", platform.python_version())
print("executable:", sys.executable)
print("cwd:", os.getcwd())
print("argv:", sys.argv)
```

Add only evidence relevant to the hypothesis. Do not dump credentials or the complete process environment.

### 1.6.33 Engineering Rules

1. Make interpreter selection explicit.
2. Use a clear application entry point where appropriate.
3. Avoid unintended destructive import-time side effects.
4. Understand `sys.argv` in the actual invocation mode.
5. Validate application arguments.
6. Treat environment variables as execution context and protect secrets.
7. Understand working-directory and import-path assumptions.
8. Run applications with least privilege.
9. Treat Python standard streams as redirectable process interfaces.
10. Use `-u` deliberately and understand that it affects stdout/stderr rather than stdin.
11. Preserve meaningful exit status.
12. Remember that `sys.exit()` raises `SystemExit`.
13. Do not hide failures by returning success.
14. Understand file execution versus `-m` import-path behavior.
15. Keep shell wrappers simple and auditable.
16. Choose shebang/runtime selection according to deployment architecture.
17. Treat virtual-environment activation as shell convenience, not a runtime requirement.
18. Separate Python guarantees from supervisor/platform behavior.
19. Do not depend on interactive shell initialization in production.
20. Make container, Kubernetes, scheduler, and CI execution reproducible.
21. Evaluate retries, idempotency, overlap, timeouts, and shutdown behavior.
22. Reproduce incidents under production-like execution context.
23. Version-control the execution architecture.

### 1.6.34 Key Takeaways

Running Python is not merely:

```text
python app.py
```

The production model is:

```text
Supervisor / User / Scheduler
            │
            ▼
Invocation
            │
            ▼
Python Runtime
            │
            ▼
Application Entry Point
            │
            ▼
Execution Context
            │
            ├── Arguments
            ├── Environment
            ├── Working Directory
            ├── Import Path
            ├── Identity
            ├── Filesystem
            ├── Network
            └── Resource Limits
            │
            ▼
Application Behavior
            │
            ▼
stdout / stderr / Exit Status
```

> **A Python program must be evaluated under the execution context that actually launches it in production.**

The central engineering principle is:

> **Make Python program execution explicit, reproducible, observable, least-privileged, and capable of reporting failure correctly.**
