# Chapter 1 — Python Fundamentals and Development Environment

## 1.7 — Source Files and Encoding

**Workflow Stage:** Technical + Source Review Complete
**Chapter Canonical Progress:** `6/25`

Python source begins as bytes stored in a file or supplied through another input mechanism. Before Python can tokenize, parse, compile, and execute that source, the bytes must be decoded into Unicode source text according to Python's source-encoding rules.

```text
Source Bytes
     │
     ▼
Determine Source Encoding
     │
     ▼
Decode to Unicode Source Text
     │
     ▼
Physical / Logical Line Processing
     │
     ▼
Lexical Analysis and Tokens
     │
     ▼
Parsing / Compilation
     │
     ▼
Execution
```

> **Treat Python source as controlled Unicode text stored through a predictable encoding, repository policy, and build toolchain—not as an arbitrary sequence of bytes.**

### 1.7.1 Source Bytes, Characters, and Encoding

Files contain bytes; source code is interpreted as characters. An encoding defines how characters are represented as bytes, while decoding converts those bytes back into characters.

```text
Characters → Encoding → Bytes
Bytes      → Decoding → Characters
```

If source bytes cannot be decoded using the determined source encoding, Python reports a `SyntaxError` before normal application execution begins.

### 1.7.2 Unicode Source Text

After decoding, Python's lexical analysis operates on Unicode source characters. Python source can therefore contain non-ASCII text in places permitted by the language grammar, including string literals, comments, and valid identifiers.

The lexical source-character model permits Unicode code points subject to Python's lexical rules; the NUL control character is not permitted in source text.

Unicode is the character model. UTF-8 is one encoding capable of representing Unicode characters. Do not treat those terms as interchangeable.

### 1.7.3 UTF-8 Is the Default Source Encoding

Python 3 uses UTF-8 as the default source encoding.

For example, a correctly UTF-8-encoded source file can contain:

```python
city = "Zürich"
message = "こんにちは"
```

without an explicit encoding declaration.

For modern production Python repositories:

> **Standardize source files on UTF-8 unless a verified compatibility requirement requires another supported source encoding.**

### 1.7.4 Source-Encoding Declarations

Python can recognize an encoding declaration in a comment near the beginning of the source file. A conventional editor-compatible form is:

```python
# -*- coding: utf-8 -*-
```

A simpler matching form is:

```python
# coding: utf-8
```

The language recognizes an encoding comment matching its documented `coding[=:]...` form rather than only these two literal spellings.

For ordinary UTF-8 Python 3 source, an explicit declaration is normally unnecessary because UTF-8 is already the default.

### 1.7.5 Encoding-Declaration Placement

An encoding declaration can be recognized on the first or second source line.

If it appears on the second line, the first line must also be a comment-only line. A Unix-style shebang satisfies that condition:

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-

print("ready")
```

For normal UTF-8 source, this can usually be simplified to:

```python
#!/usr/bin/env python3

print("ready")
```

because UTF-8 is already the default.

### 1.7.6 A Declaration Describes Bytes; It Does Not Convert Them

This line:

```python
# coding: utf-8
```

does not convert the file to UTF-8. It declares how Python should decode the source bytes.

```text
Declared Encoding
        ≠
Actual Byte Encoding
        │
        ▼
Decoding Failure / Incorrect Interpretation
```

Repository tooling must ensure that the actual bytes match the declared encoding.

### 1.7.7 UTF-8 BOM Behavior

UTF-8 does not require a byte order mark (BOM).

When Python determines the source encoding to be UTF-8, an initial UTF-8 BOM byte sequence (`EF BB BF`) is ignored rather than treated as Python syntax.

This language behavior does not mean repositories should add BOMs unnecessarily. A production repository can standardize on BOM-free UTF-8 to reduce editor and toolchain variability.

> **Language acceptance and repository policy are separate concerns.**

### 1.7.8 Other Unicode Encodings

Unicode text can be represented by encodings such as UTF-8, UTF-16, and UTF-32, but this does not mean every Unicode codec should be treated as an interchangeable Python source-file format.

Python source decoding follows the language's source-encoding rules and declared codec behavior. For production engineering, UTF-8 should remain the repository standard unless a specific supported compatibility requirement has been tested and documented.

UTF-8 maximizes interoperability with Git, editors, linters, build systems, containers, CI/CD systems, and common Unix tooling.

### 1.7.9 Source Decoding Precedes Execution

The processing boundary is:

```text
Read Source Bytes
       │
       ▼
Determine Encoding
       │
       ▼
Decode Source
       │
       ▼
Lex / Parse / Compile
       │
       ▼
Execute Program
```

If source decoding fails, application business logic never starts.

This distinction matters operationally: a source-decoding `SyntaxError` is a source/artifact problem, not evidence that the application's database, API, or business logic failed.

### 1.7.10 Source Encoding Versus Runtime Data Encoding

Source encoding and runtime data encoding are separate boundaries:

```text
application.py
      │
      ▼
Python Source Encoding
```

versus:

```text
customers.csv / API Payload / Message
      │
      ▼
Runtime Data Encoding
```

A UTF-8 Python source file can intentionally process data encoded using another format. Source encoding does not automatically determine how application data is decoded.

Runtime file I/O belongs primarily in Chapter 8.

### 1.7.11 Source Encoding Versus Terminal and Filesystem Behavior

Do not assume one encoding setting controls all interfaces:

```text
Source Contents
File Names
Terminal I/O
Environment Variables
Network Payloads
Database Text
```

A valid Unicode string can be represented correctly in Python while a terminal or downstream system displays or encodes it differently.

Troubleshoot encoding problems at the interface where bytes cross into or out of text.

### 1.7.12 Physical and Logical Lines

Python's lexical model distinguishes physical source lines from logical lines used to form statements.

A useful conceptual pipeline is:

```text
Physical Source Lines
        │
        ▼
Explicit / Implicit Line Joining
        │
        ▼
Logical Lines
        │
        ▼
Tokens
```

Detailed statement grammar, indentation, and line joining belong in Section 1.8. This section establishes the source-representation boundary.

### 1.7.13 Newline Recognition and Normalization

Python's lexical processing recognizes common end-of-line forms including LF, CRLF, and CR and normalizes them for lexical processing.

This language behavior is distinct from repository policy.

A repository can still standardize on a single line-ending convention—commonly LF—to reduce:

```text
False Diffs
Merge Noise
Generated-File Differences
Cross-Platform Surprises
```

### 1.7.14 Repository Line-Ending Policy

Source normalization should be controlled by repository configuration rather than undocumented workstation preferences.

```text
Repository Policy
      │
      ▼
Git / Editors / CI
      │
      ▼
Predictable Working Trees and Builds
```

`.gitattributes` can be used to establish repository-controlled text and line-ending behavior appropriate to supported platforms.

### 1.7.15 Editor Configuration

Editors can affect encoding, line endings, final newline behavior, indentation, whitespace, and Unicode input.

Projects should automate these conventions where practical rather than require every engineer to remember local settings manually.

A final newline is generally desirable for conventional text-processing and version-control behavior, even though its absence is not normally a Python-runtime catastrophe.

### 1.7.16 Unicode Identifiers

Python supports non-ASCII identifiers subject to its identifier rules.

Non-ASCII identifiers are validated according to Python's Unicode identifier rules and normalized using **NFKC normalization during parsing**.

Conceptually:

```text
Identifier Source Characters
          │
          ▼
Identifier Validation
          │
          ▼
NFKC Normalization
          │
          ▼
Identifier Used by Parser
```

This means visually or textually different Unicode spellings can normalize to the same identifier representation.

### 1.7.17 Identifier Normalization Does Not Normalize Runtime Strings

The normalization applied to identifiers during lexical processing does **not** imply that ordinary string values are automatically normalized.

For example, application data can contain visually equivalent Unicode text represented by different code-point sequences.

```text
Identifier Normalization
        ≠
Automatic Runtime String Normalization
```

Applications that require normalized external text must define that behavior deliberately.

### 1.7.18 Unicode in Strings, Comments, and Documentation

UTF-8 source can naturally contain international text:

```python
message = "Déploiement terminé"

# Café service configuration
```

This is routine and useful.

Using broad Unicode in application text is different from choosing unusual identifiers. Production identifier conventions should consider readability, keyboard accessibility, code review, tooling, and team supportability.

### 1.7.19 Invisible and Confusable Unicode

Some Unicode characters are invisible or visually similar to other characters. They can create code-review confusion, copy/paste problems, or security concerns.

This is primarily an engineering and source-security concern rather than a claim that Python rejects every unusual character.

Production standards should discourage intentionally confusing source and should use review/static-analysis controls appropriate to the organization's risk model.

### 1.7.20 Visual Equality Is Not String Equality

Unicode text that looks identical can sometimes contain different code-point sequences, such as precomposed characters versus a base character followed by combining marks.

This matters for runtime application data:

```text
Looks the Same
      ≠
Necessarily Same Code-Point Sequence
```

Do not infer runtime string normalization from Python's identifier-normalization rules.

### 1.7.21 Whitespace and Source Appearance

Whitespace is not merely visual formatting in Python. Indentation participates in the language grammar.

Tabs, spaces, formfeed behavior, explicit/implicit line joining, and indentation semantics are handled in Section 1.8.

For source-file engineering, remember:

> **Visually aligned text does not prove that the underlying source characters are equivalent.**

### 1.7.22 Generated Python Source

Systems that generate `.py` files introduce another source pipeline:

```text
Generator Input
      │
      ▼
Generator
      │
      ▼
Python Source Text
      │
      ▼
Encoding / Newline Policy
      │
      ▼
Validation
      │
      ▼
Python Runtime
```

Generated source should be deterministic, correctly encoded, syntactically valid, and reproducible through the build process.

Untrusted input must not be allowed to become arbitrary executable Python source.

### 1.7.23 Externally Obtained Source

Code copied or obtained from web pages, email, tickets, chat, documents, archives, or legacy repositories may contain unexpected encoding, smart punctuation, invisible characters, transformed whitespace, or confusable characters.

Treat externally obtained source as untrusted executable text until its provenance and contents are understood.

### 1.7.24 Copy/Paste and Rich-Text Transformations

A visually correct snippet can contain characters such as:

```text
Smart Quotes
Non-Breaking Spaces
Unicode Dashes
Directionality Marks
Look-Alike Characters
```

For example, ASCII quotation marks used as Python string delimiters are not interchangeable with typographic quotation marks inserted by rich-text software.

Use source-aware editors for code.

### 1.7.25 Source Provenance and Artifact Identity

Encoding correctness does not prove that the source is the intended artifact.

Operationally ask:

```text
Which Repository?
Which Branch?
Which Commit?
Which Build?
Which Package / Image?
Which Deployed Artifact?
```

A syntactically valid UTF-8 file can still be the wrong version of the application.

### 1.7.26 Do Not Casually Edit Deployed Source

A dangerous operational pattern is:

```text
Incident
   │
   ▼
Engineer Modifies Deployed .py File
   │
   ▼
Service Recovers
   │
   ▼
Repository / Build Artifact Unchanged
```

This creates artifact drift.

Prefer:

```text
Diagnose
   │
   ▼
Version-Controlled Change
   │
   ▼
Review / Test
   │
   ▼
Build
   │
   ▼
Controlled Deployment
```

If emergency procedures permit live modification, they must include explicit reconciliation back to the authoritative source.

### 1.7.27 Containers and Kubernetes Source Drift

Production container images should normally be treated as immutable artifacts. Editing Python source inside a running container creates state that can disappear on restart and differ across replicas.

```text
Pod A → Canonical Image Source
Pod B → Manually Modified Source
Pod C → Canonical Image Source
```

This replica drift can produce intermittent and difficult-to-reproduce failures.

Use the source repository and image build/deployment pipeline as the normal authoritative change path.

### 1.7.28 Source Files, Secrets, and Sensitive Data

Do not embed production credentials directly in source:

```python
password = "production-password"
```

Source is commonly committed, reviewed, copied, cached, archived, built into artifacts, scanned, and distributed. Removing a visible secret later does not guarantee that it disappeared from repository history or downstream artifacts.

Likewise, avoid embedding real production or regulated records in examples, comments, fixtures, or debugging constants. Prefer synthetic or properly sanitized data.

### 1.7.29 Executable Source Is a Security Boundary

A `.py` file is executable code, not harmless text.

Before running source from an unknown or external origin, consider:

```text
Who Produced It?
Was It Reviewed?
Was It Modified?
Which Identity Will Execute It?
Which Credentials Will It Inherit?
Which Systems Can It Reach?
```

A controlled path is:

```text
Acquire
   │
   ▼
Verify Provenance
   │
   ▼
Inspect / Review
   │
   ▼
Static / Compilation Checks
   │
   ▼
Test in Controlled Environment
   │
   ▼
Approve
   │
   ▼
Execute / Deploy
```

### 1.7.30 Compilation Checks with `py_compile`

Python's `py_compile` module can compile source files explicitly:

```bash
python3 -m py_compile app.py
```

This can detect source that cannot be compiled by the selected interpreter. The command normally creates bytecode cache output (`.pyc`) as part of compilation, so it should not be described as a completely side-effect-free inspection operation.

The command-line interface reports failure when named source files cannot be compiled.

### 1.7.31 Compilation Success Is Not Application Health

Successful compilation demonstrates only that the selected interpreter could compile the source.

It does not prove:

```text
Dependencies Are Installed
Imports Will Succeed in Application Context
Configuration Is Correct
Database Is Reachable
Network Is Healthy
Permissions Are Correct
Business Logic Is Correct
Application Is Production-Ready
```

Therefore:

```text
Source Compiles
      ≠
Application Healthy
```

Keep conclusions proportional to the validation performed.

### 1.7.32 Source Inspection

When source corruption or encoding problems are suspected, useful questions include:

```text
Is this the expected artifact?
Which encoding is present?
Is there a UTF-8 BOM?
Are line endings unexpected?
Are suspicious Unicode characters present?
Are the source bytes corrupted?
```

Start with minimally invasive evidence collection. Byte-level inspection is useful when ordinary source-aware tools cannot explain the discrepancy.

### 1.7.33 Source Permissions

When Python is explicitly invoked on a source path, the runtime identity must be able to access/read the required source and parent path components according to operating-system rules.

Direct executable-script invocation introduces additional platform requirements such as executable permission and shebang/process-launch behavior.

Do not solve permission failures by granting broad access without diagnosing file ownership, groups, modes, directory permissions, mount behavior, runtime identity, and relevant security controls.

### 1.7.34 Production Source Should Normally Be Immutable

Production applications generally should not rewrite their own Python source files at runtime.

Self-modifying deployed source complicates:

```text
Integrity
Rollback
Scaling
Replica Consistency
Security
Observability
Reproducibility
```

Mutable application state belongs in deliberately designed state/configuration systems rather than ordinary source files.

### 1.7.35 Build and Deployment Artifacts

The deployed representation may differ from a developer's working tree:

```text
Git Repository
      │
      ▼
Build Pipeline
      │
      ▼
Wheel / Package / Container
      │
      ▼
Deployment
```

Production troubleshooting should identify the deployed artifact and trace it back to an authoritative source revision rather than assume it matches a current local checkout.

### 1.7.36 CI/CD and Cross-Platform Source Behavior

Source problems may surface only in CI/CD because developer and build environments differ in checkout behavior, generated files, tool versions, line-ending conversion, or other source transformations.

A cross-platform repository should define predictable policies for:

```text
UTF-8 Source
Line Endings
Editor Behavior
Generated Files
Executable Scripts
Validation
```

The durable fix is deterministic repository/build policy rather than workstation-specific repair.

### 1.7.37 Production Source-File Checklist

```text
[ ] Python source standardized on UTF-8
[ ] Encoding declarations used only when required
[ ] Encoding declaration placement is valid
[ ] Declared encoding matches actual bytes
[ ] UTF-8 BOM policy is deliberate
[ ] Line endings follow repository policy
[ ] Final newline policy followed
[ ] No suspicious invisible/confusable source characters
[ ] No accidental rich-text punctuation
[ ] Unicode identifiers follow team readability standards
[ ] No embedded credentials
[ ] No unnecessary production data
[ ] Generated source deterministic
[ ] External source provenance understood
[ ] File permissions appropriate
[ ] Repository controls normalization
[ ] CI performs appropriate source validation
[ ] Deployed artifact traceable to source revision
[ ] Running hosts/containers are not manually drifting
```

### 1.7.38 Common Anti-Patterns

1. Assuming visual appearance proves encoding correctness.
2. Declaring UTF-8 while storing another encoding.
3. Adding encoding declarations mechanically.
4. Treating a BOM as required for UTF-8.
5. Mixing repository line endings unpredictably.
6. Relying only on developer-local Git normalization.
7. Editing source in rich-text software.
8. Ignoring suspicious invisible or confusable Unicode.
9. Assuming identifier normalization also normalizes runtime strings.
10. Embedding secrets in source.
11. Embedding real production data in examples.
12. Executing unknown source without provenance review.
13. Treating successful `py_compile` as application health.
14. Assuming `py_compile` performs no filesystem writes.
15. Manually editing production containers or hosts.
16. Allowing replicas to run different source.
17. Generating Python without deterministic encoding/newline policy.
18. Assuming source encoding controls runtime data encoding.
19. Treating workstation behavior as proof of CI/deployment behavior.
20. Fixing permissions with excessive access instead of diagnosing ownership.

### 1.7.39 SRE/DBRE Troubleshooting Pattern

```text
Identify Deployed Artifact
        │
        ▼
Verify Repository / Commit / Image
        │
        ▼
Inspect Source Encoding
        │
        ▼
Inspect Declaration / BOM if Relevant
        │
        ▼
Inspect Line Endings / Unexpected Characters
        │
        ▼
Validate Permissions / Runtime Identity
        │
        ▼
Compile with Selected Interpreter if Appropriate
        │
        ▼
Compare with Known-Good Source
        │
        ▼
Reproduce Through Build Pipeline
        │
        ▼
Correct the Source of Drift
```

Source troubleshooting should preserve evidence and distinguish language behavior from repository, operating-system, editor, and deployment behavior.

### 1.7.40 Engineering Rules

1. Treat Python source as encoded Unicode text.
2. Standardize production source on UTF-8.
3. Remember that UTF-8 is Python 3's default source encoding.
4. Use encoding declarations only when they serve a real requirement.
5. Follow the exact first/second-line declaration rules.
6. Ensure declarations match actual source bytes.
7. Understand Python's initial UTF-8 BOM handling while maintaining a deliberate repository BOM policy.
8. Distinguish source encoding from runtime data, terminal, and filesystem encoding boundaries.
9. Distinguish physical lines from logical lines.
10. Separate Python newline normalization from repository line-ending policy.
11. Understand NFKC normalization of non-ASCII identifiers.
12. Do not assume runtime strings are automatically normalized.
13. Treat invisible/confusable Unicode as a source-review and security concern.
14. Keep repository normalization deterministic.
15. Keep generated source deterministic and validated.
16. Review externally obtained source before execution.
17. Never embed production credentials in source.
18. Avoid embedding sensitive production data.
19. Treat executable source as a security boundary.
20. Keep production artifacts immutable where practical.
21. Do not create replica drift through manual source editing.
22. Use compilation checks as one validation layer, not proof of health.
23. Remember that `py_compile` normally creates bytecode cache output.
24. Diagnose permission failures rather than overgrant access.
25. Trace deployed artifacts to authoritative source revisions.
26. Reproduce source transformations through CI/build pipelines.

### 1.7.41 Key Takeaways

Python source processing begins with bytes and must establish valid Unicode source text before lexical analysis and compilation can proceed:

```text
Source Bytes
     │
     ▼
Source Encoding
     │
     ▼
Unicode Source Text
     │
     ▼
Physical / Logical Lines
     │
     ▼
Tokens
     │
     ▼
Parsing / Compilation
     │
     ▼
Execution
```

For modern Python engineering:

> **UTF-8 is the normal source-file encoding and should be the production repository standard unless a documented compatibility requirement says otherwise.**

Production source engineering also includes:

```text
Encoding
   +
Unicode Safety
   +
Line-Ending Policy
   +
Repository Normalization
   +
Permissions
   +
Source Provenance
   +
Artifact Integrity
   +
Build Reproducibility
```

The operational principle is:

> **Treat Python source as a controlled, reviewable, reproducible executable artifact—not merely as text that happens to end in `.py`.**
