# Chapter 1 — Python Fundamentals and Development Environment

## 1.7 — Source Files and Encoding

**Edition:** Revised Final / Canonical

Python source begins as bytes. Before Python can tokenize, parse, compile, and execute that source, those bytes must be interpreted as Unicode source text according to Python's source-encoding rules.

```text
Source Bytes
     │
     ▼
Determine Source Encoding
     │
     ▼
Decode to Unicode Source Text
     │
     ▼
Physical / Logical Line Processing
     │
     ▼
Lexical Analysis and Tokens
     │
     ▼
Parsing / Compilation
     │
     ▼
Execution
```

This makes source-file engineering more than a matter of choosing a `.py` filename. Encoding, Unicode behavior, line endings, repository normalization, source provenance, permissions, artifact identity, and build reproducibility can all affect production correctness.

> **Treat Python source as controlled Unicode text stored through a predictable encoding, repository policy, and build toolchain—not as an arbitrary sequence of bytes.**

### 1.7.1 Source Bytes and Characters

A conventional Python source file uses the `.py` suffix. At the storage layer, the file contains bytes. Humans and the Python language reason about characters. An encoding defines the mapping between characters and bytes, and decoding performs the reverse transformation.

Correct source interpretation depends on Python determining an appropriate source encoding and successfully decoding the underlying bytes.

### 1.7.2 Unicode Source Text

After source decoding, Python's lexical analysis operates on Unicode source characters. Source can contain non-ASCII text where permitted by Python's grammar, including string literals, comments, documentation, and valid identifiers.

Unicode defines characters and code points. An encoding such as UTF-8 defines how those characters are represented as bytes. Unicode and UTF-8 are related concepts, but they are not interchangeable terms.

### 1.7.3 Source-Character Boundary

Python's lexical processing operates on decoded Unicode source text subject to the language's lexical rules. The NUL control character is not permitted in Python source. Not every file that contains bytes can therefore become valid Python source.

### 1.7.4 UTF-8 Is the Default Source Encoding

Python 3 uses UTF-8 as its default source encoding. A correctly UTF-8-encoded source file can contain international text without an explicit encoding declaration.

> **Standardize Python source on UTF-8 unless a verified compatibility requirement requires another supported source encoding.**

UTF-8 provides strong interoperability with Git, editors, linters, build systems, CI/CD, containers, code-review systems, and common Unix tooling.

### 1.7.5 Source-Encoding Declarations

Python supports a source-encoding declaration in a comment near the beginning of the file. Common forms include:

```python
# -*- coding: utf-8 -*-
```

and:

```python
# coding: utf-8
```

Python's recognition rule is based on the documented `coding[=:]...` encoding-comment pattern rather than only those two literal examples. For ordinary UTF-8 Python 3 source, an explicit declaration is normally unnecessary because UTF-8 is already the default.

### 1.7.6 Encoding-Declaration Placement

An encoding declaration can be recognized on the first or second source line. If it occurs on the second line, the first line must also be a comment-only line. This supports Unix-style executable scripts:

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-

print("ready")
```

When normal UTF-8 source is used, the explicit declaration can generally be omitted.

### 1.7.7 Encoding Declarations Describe Reality

An encoding declaration does not convert a file into the named encoding. It tells Python how the source bytes should be decoded. Editors, generators, repository tooling, and build pipelines must ensure that the physical source bytes follow the intended encoding.

> **An encoding declaration describes the file; it does not transform the file.**

### 1.7.8 Source-Decoding Failure

Source decoding occurs before normal application execution. If Python cannot decode the source according to the determined source encoding, the failure is reported as a `SyntaxError`. Application business logic has not started at this point, so diagnose the source/artifact layer first.

### 1.7.9 UTF-8 BOM Behavior

UTF-8 does not require a byte order mark. When Python determines that source is UTF-8, an initial UTF-8 BOM (`EF BB BF`) is ignored rather than interpreted as Python syntax.

This language behavior should be distinguished from repository policy. A production repository can and generally should standardize on BOM-free UTF-8 unless a defined toolchain requires otherwise.

### 1.7.10 Other Unicode Encodings

Unicode text can be represented using encodings such as UTF-8, UTF-16, and UTF-32, but that does not mean every Unicode codec should be treated as an interchangeable Python source-file format. Python source decoding follows the language's source-encoding rules and the behavior of the selected source codec.

For production engineering, UTF-8 should remain the repository standard unless another supported encoding is required, tested, and documented.

### 1.7.11 Source Encoding Versus Runtime Data Encoding

Source encoding and runtime data encoding are separate boundaries. A UTF-8 Python source file can intentionally process data encoded differently. Source encoding does not automatically determine the encoding used for data files, API payloads, messages, database data, or external documents. Runtime file and data serialization behavior belongs primarily in Chapter 8.

### 1.7.12 Source Encoding Versus Terminal Encoding

A string can exist correctly in Python while a terminal or downstream logging destination renders it incorrectly. When diagnosing text problems, distinguish whether Python can decode the source, represent the string, encode it for the destination, and whether the display system can render it.

### 1.7.13 Source Encoding Versus Filesystem Behavior

Source encoding does not define how the operating system represents filenames or other process interfaces. Do not assume one encoding setting controls source contents, filenames, terminal I/O, environment variables, network payloads, and database text. Diagnose encoding problems at the boundary where bytes are converted to or from text.

### 1.7.14 Physical and Logical Lines

Python's lexical model distinguishes physical source lines from logical lines used to form statements.

```text
Physical Source Lines
        │
        ▼
Explicit / Implicit Line Joining
        │
        ▼
Logical Lines
        │
        ▼
Tokens
```

Detailed explicit/implicit line joining, indentation, and statement syntax belong in Section 1.8.

### 1.7.15 Newline Recognition and Repository Policy

Python's lexical processing recognizes LF, CRLF, and CR end-of-line forms and normalizes them for lexical processing. This language behavior is distinct from repository policy.

A production repository should define a predictable line-ending policy to reduce false diffs, merge noise, generated-file differences, and cross-platform surprises.

### 1.7.16 Git, `.gitattributes`, and Source Normalization

Git can transform line endings depending on repository and client configuration. Critical source normalization should not rely exclusively on individual developer settings. A repository can use `.gitattributes` to establish text and line-ending behavior appropriate to supported platforms.

> **Make source normalization a repository property rather than an undocumented workstation preference.**

### 1.7.17 Editor Configuration and Final Newline

Editors can influence encoding, line endings, final newline behavior, indentation, whitespace, and Unicode input. Projects should automate source conventions where practical. Text source files should generally end with a newline for conventional tooling behavior, although a missing final newline is normally not a catastrophic Python runtime problem.

### 1.7.18 Unicode Identifiers

Python permits non-ASCII identifiers subject to its Unicode identifier rules. Non-ASCII identifier text is validated using Python's Unicode identifier rules and normalized using **NFKC normalization during parsing**.

Different source character sequences can potentially normalize to the same identifier representation. Language capability does not automatically make every Unicode identifier a good production choice; teams should consider readability, keyboard accessibility, code review, searchability, tooling, and operational support.

### 1.7.19 Identifier Normalization Versus Runtime Strings

Python's NFKC normalization of identifiers does **not** mean ordinary runtime strings are automatically normalized. Applications that require normalized external text must define and apply that behavior deliberately.

### 1.7.20 Unicode in Strings, Comments, and Documentation

Unicode text in strings, comments, and documentation is routine in UTF-8 source. Internationalized applications may legitimately require many writing systems. This is separate from the engineering question of identifier naming conventions.

### 1.7.21 Invisible and Confusable Unicode

Some Unicode characters are invisible or visually similar to other characters. Unexpected invisible or confusable characters can create code-review confusion, copy/paste problems, tooling differences, or security concerns.

Treat suspicious characters as a source-review and security concern. The appropriate response is coding standards, review, and suitable static-analysis/security controls—not an assumption that Python rejects every visually unusual character.

### 1.7.22 Unicode String Normalization

Runtime text can have multiple code-point representations that render similarly, such as precomposed characters versus a base character followed by combining marks. Visual equality therefore does not guarantee code-point equality. This is separate from Python's identifier normalization.

### 1.7.23 Whitespace Is Source Data

Whitespace characters are part of the source representation, and indentation has syntactic meaning in Python. Visually aligned text does not prove that underlying source characters are equivalent. Detailed indentation, tabs, formfeeds, line joining, and statement syntax belong in Section 1.8.

### 1.7.24 Generated Python Source

Systems that generate `.py` files introduce another source pipeline. Generated source should be deterministic, correctly encoded, syntactically valid, reproducible, and reviewable where appropriate. Untrusted input must not be allowed to become arbitrary executable Python source.

### 1.7.25 Externally Obtained Source and Copy/Paste

Source obtained from web pages, email, tickets, chat, documents, legacy repositories, or archives may contain unexpected encodings, smart punctuation, invisible characters, transformed whitespace, or confusable Unicode. Treat externally obtained source as untrusted executable text until its provenance and contents are understood. Use source-aware editors for code.

### 1.7.26 Source Provenance and Artifact Identity

A valid UTF-8 file is not necessarily the correct file. Operationally identify the repository, branch, commit, producer, review state, build, package/image, and deployed artifact.

Production execution may involve several transformations:

```text
Git Repository
      │
      ▼
Build Pipeline
      │
      ▼
Wheel / Package / Container
      │
      ▼
Deployment
```

Troubleshooting should identify the deployed artifact rather than assume it matches an engineer's current working tree.

### 1.7.27 Do Not Casually Edit Deployed Source

Manual modification of deployed `.py` files creates artifact drift. Prefer diagnosis followed by a version-controlled change, review/testing, build, and controlled deployment. If an emergency process permits live modification, it must include explicit reconciliation back to the authoritative source.

### 1.7.28 Container and Kubernetes Source Immutability

Production container images should normally be treated as immutable artifacts. Editing Python source inside a running container creates state that can disappear on restart and differ across replicas. In Kubernetes, replica drift can produce intermittent behavior that is extremely difficult to diagnose.

Use the source repository and image build/deployment pipeline as the normal authoritative change path.

### 1.7.29 Source Files, Secrets, and Sensitive Data

Do not embed production credentials directly in source. Source files are commonly committed, reviewed, copied, cached, archived, built into images, scanned, and distributed. Removing a visible secret later does not guarantee that it disappeared from repository history or downstream artifacts.

Likewise, avoid embedding real production or regulated records in examples, tests, comments, docstrings, debugging constants, or fixtures. Prefer synthetic or appropriately sanitized data.

### 1.7.30 Executable Source Is a Security Boundary

A Python source file is executable code. Before running unfamiliar source, consider who produced it, whether it was reviewed or modified, which identity will execute it, which credentials it will inherit, and which files, networks, and systems it can access.

> **Readable text is not equivalent to safe code.**

A controlled path includes provenance verification, review, static/compilation checks, testing in a controlled environment, approval, and controlled execution/deployment.

### 1.7.31 Compilation Checks with `py_compile`

Python provides the `py_compile` module for explicitly compiling source files:

```bash
python3 -m py_compile app.py
```

This can detect source that the selected interpreter cannot compile. The operation normally creates bytecode cache output in `__pycache__`, so it should not be described as completely side-effect-free inspection.

### 1.7.32 Compilation Success Is Not Application Health

Successful compilation demonstrates only that the selected interpreter could compile the source. It does not prove that dependencies are installed, imports work in deployment context, configuration is valid, databases and networks are reachable, permissions are correct, business logic is correct, or the application is production-ready.

> **Source compiles ≠ application healthy.**

Keep conclusions proportional to the validation performed.

### 1.7.33 Source Inspection and Byte-Level Diagnostics

When source corruption or encoding problems are suspected, determine whether the file is the expected artifact, which encoding is present, whether a declaration matches the bytes, whether an initial BOM exists, whether line endings are unexpected, and whether suspicious Unicode or corruption is present.

Start with minimally invasive inspection and preserve incident evidence. Byte-level inspection is useful when source-aware tools cannot explain the discrepancy.

### 1.7.34 Source File Permissions and Least Privilege

When Python is explicitly invoked on a source path, the runtime identity must be able to access the source according to operating-system filesystem rules. Direct executable-script invocation can introduce additional platform requirements such as execute permission, shebang interpretation, parent-directory access, mount behavior, and security policy.

Do not solve permission problems by running as root, using overly broad modes such as `chmod 777`, or disabling security controls. Diagnose ownership, groups, modes, parent directories, runtime identity, mounts, and security controls, then grant only required access.

### 1.7.35 Production Source Should Normally Be Immutable

A production application generally should not rewrite its own Python source. Self-modifying deployed source complicates integrity, rollback, scaling, replica consistency, security, observability, and reproducibility. Mutable application state belongs in deliberately designed state or configuration systems.

### 1.7.36 CI/CD Source Validation

CI/CD can validate encoding/decoding, compilation, formatting, linting, static analysis, tests, generated-file consistency, and security checks before deployment. No single check proves application correctness; value comes from layered validation.

### 1.7.37 Cross-Platform Repository Design

Repositories used across Linux, macOS, and Windows should define predictable behavior for UTF-8 source, line endings, editor behavior, generated files, executable scripts, and validation. Cross-platform engineering requires the repository and build system to eliminate unnecessary environment-dependent transformations.

### 1.7.38 Production Source-File Checklist

```text
[ ] Python source standardized on UTF-8
[ ] Encoding declarations used only when required
[ ] Encoding declaration placement is valid
[ ] Declared encoding matches actual bytes
[ ] UTF-8 BOM policy is deliberate
[ ] Line endings follow repository policy
[ ] Final newline policy followed
[ ] Physical/logical line behavior understood where relevant
[ ] No suspicious invisible/confusable source characters
[ ] No accidental rich-text punctuation
[ ] Unicode identifiers follow team readability standards
[ ] Runtime strings are not assumed to be normalized
[ ] No embedded production credentials
[ ] No unnecessary sensitive production data
[ ] Generated source deterministic
[ ] External source provenance understood
[ ] Source permissions appropriate
[ ] Repository controls normalization
[ ] CI performs appropriate source validation
[ ] Compilation checks interpreted correctly
[ ] Deployed artifact traceable to source revision
[ ] Running hosts/containers are not manually drifting
```

### 1.7.39 Common Source-File Anti-Patterns

1. Assuming visual appearance proves encoding correctness.
2. Declaring UTF-8 while storing another encoding.
3. Adding encoding declarations mechanically.
4. Treating a BOM as required for UTF-8.
5. Mixing repository line endings unpredictably.
6. Relying only on developer-local Git normalization.
7. Editing source in rich-text software.
8. Ignoring suspicious invisible or confusable Unicode.
9. Assuming identifier normalization also normalizes runtime strings.
10. Embedding secrets in source.
11. Embedding real production data in examples.
12. Executing unknown source without provenance review.
13. Treating successful `py_compile` as application health.
14. Assuming `py_compile` performs no filesystem writes.
15. Manually editing production containers or hosts.
16. Allowing replicas to run different source.
17. Generating Python without deterministic encoding/newline policy.
18. Assuming source encoding controls runtime data encoding.
19. Treating workstation behavior as proof of CI/deployment behavior.
20. Fixing permissions with excessive access instead of diagnosing ownership.

```text
        │

```

The diagnostic rule is:

> **Identify whether the failure belongs to source representation, Python syntax/compilation, artifact identity, filesystem access, or deployment state before changing the environment.**

### 1.7.41 Engineering Rules for Source Files

1. Treat Python source as encoded Unicode text.
2. Standardize production Python source on UTF-8.
3. Remember that UTF-8 is Python 3's default source encoding.
4. Use encoding declarations only when they serve a real requirement.
5. Follow the exact first/second-line encoding-declaration rules.
6. Ensure declarations match the actual source bytes.
7. Understand Python's initial UTF-8 BOM behavior and maintain a deliberate repository BOM policy.
8. Distinguish source encoding from runtime data, terminal, and filesystem encoding boundaries.
9. Distinguish physical lines from logical lines.
10. Separate Python newline normalization from repository line-ending policy.
11. Make source normalization repository-controlled.
12. Understand NFKC normalization of non-ASCII identifiers.
13. Do not assume identifier normalization applies to runtime strings.
14. Treat suspicious invisible/confusable Unicode as a source-review concern.
15. Keep generated source deterministic.
16. Review externally obtained source before execution.
17. Never embed production credentials in source.
18. Avoid embedding sensitive production data.
19. Treat executable source as a security boundary.
20. Preserve source provenance.
21. Trace deployed artifacts to authoritative source revisions.
22. Keep production artifacts immutable where practical.
23. Do not create replica drift through manual source editing.
24. Use compilation checks as one validation layer.
25. Remember that `py_compile` normally creates bytecode cache output.
26. Do not interpret successful compilation as application health.
27. Diagnose permission failures rather than overgrant access.
28. Reproduce source transformations through CI/build pipelines.
29. Preserve incident evidence before modifying suspected source.
30. Keep source changes reviewable, reproducible, and deployable through controlled paths.

### 1.7.42 Key Takeaways

Python source processing begins with bytes:

```text
Source Bytes
     │
     ▼
Source Encoding
     │
     ▼
Unicode Source Text
     │
     ▼
Physical / Logical Lines
     │
     ▼
Tokens
     │
     ▼
Parsing / Compilation
     │
     ▼
Execution
```

For modern Python engineering:

> **UTF-8 is the normal source-file encoding and should be the production repository standard unless a documented compatibility requirement says otherwise.**

Production source engineering also includes encoding, Unicode safety, line-ending policy, repository normalization, permissions, source provenance, artifact integrity, and build reproducibility.

The security principle is:

> **A Python source file is executable code; readable text is not automatically trusted code.**

The operational principle is:

> **The deployed source must remain traceable to an authoritative repository revision and reproducible through the build and deployment pipeline.**

And the central engineering principle remains:

> **Treat Python source as a controlled, reviewable, reproducible executable artifact—not merely as text that happens to end in `.py`.**
