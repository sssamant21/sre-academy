# Chapter 1 — Python Fundamentals and Development Environment

## 1.9 — Variables and Name Binding

**Edition:** Revised Final / Canonical  
**Target Runtime:** Python 3.14

### Learning Objectives

After completing this section, you will be able to:

- Explain why Python variables are **names bound to objects**.
- Describe assignment, binding, and rebinding.
- Distinguish object identity, type, and value.
- Explain the difference between `is` and `==`.
- Distinguish rebinding from mutation.
- Recognize aliasing and shared mutable state.
- Understand shallow and deep copying.
- Explain Python's function-argument binding model.
- Understand namespaces and the LEGB name-resolution model.
- Use `global` and `nonlocal` appropriately.
- Explain `del`, object lifetime, reference counting, cyclic garbage collection, and weak references at an introductory level.
- Troubleshoot production problems involving shared state and object ownership.

---

## 1.9.1 Variables Are Names Bound to Objects

A common introductory explanation describes a variable as a container that stores a value. That model is convenient initially, but it becomes misleading when programs use mutable objects, function arguments, aliases, or shared state.

A more accurate Python mental model is:

> **A variable is a name that is bound to an object.**

```python
x = 10
```

Conceptually:

```text
Namespace

x ────────────────► integer object representing 10
```

Python evaluates the expression on the right and binds the name `x` to the resulting object. The name is not the object, nor does it contain the object. It provides a way to refer to that object from a namespace.

---

## 1.9.2 Objects Have Identity, Type, and Value

Every Python object has an **identity**, a **type**, and a **value or state**.

```python
count = 10
print(count)
print(type(count))
print(id(count))
```

The exact number returned by `id()` is runtime-specific and should not be relied upon. The **object** has a type; names are not permanently associated with one type.

```python
value = 100
print(type(value))
value = "production"
print(type(value))
```

A precise description is that `value` was rebound from an integer object to a string object.

---

## 1.9.3 Assignment Creates Bindings

A basic assignment has the form:

```python
name = expression
```

Conceptually:

```text
Evaluate expression
       │
       ▼
Obtain resulting object
       │
       ▼
Bind target name
```

Assignment does not inherently copy an object, mutate an existing object, or permanently associate a type with a name. It establishes or changes a binding.

---

## 1.9.4 Rebinding

A name can later be bound to another object.

```python
status = "pending"
status = "complete"
```

The string `"pending"` was not transformed into `"complete"`; `status` was rebound to another object. Python's dynamic typing allows names to be rebound to different objects. It does not mean that an existing object arbitrarily changes its type.

---

## 1.9.5 Aliasing: Multiple Names, One Object

Assignment does not automatically create a copy.

```python
servers = ["db01", "db02"]
active_servers = servers
print(servers is active_servers)
```

Output:

```text
True
```

Both names refer to the same list. This relationship is commonly called **aliasing**. Aliasing is normal Python behavior; it becomes dangerous when multiple parts of an application unintentionally share mutable state.

---

## 1.9.6 Rebinding Versus Mutation

Rebinding and mutation are fundamentally different operations.

```python
servers = ["db01", "db02"]
backup = servers
servers = ["db03"]
```

Only `servers` is rebound; `backup` still refers to the original list.

By contrast:

```python
servers = ["db01", "db02"]
backup = servers
servers.append("db03")
```

Here the existing list object is modified, so both names observe the mutation.

> **Did this operation rebind a name, or mutate an existing object?**

This is one of the most useful debugging questions in Python.

---

## 1.9.7 Mutable and Immutable Objects

Common immutable types include `int`, `float`, `bool`, `str`, `bytes`, `tuple`, and `frozenset`. Common mutable types include `list`, `dict`, `set`, `bytearray`, and many ordinary user-defined class instances.

```python
count = 10
count = count + 1
```

The integer representing `10` is not changed; `count` is rebound to the result.

```python
items = ["a", "b"]
items.append("c")
```

The existing list is mutated.

### Immutable Containers Can Reference Mutable Objects

```python
record = ("prod", ["db01"])
record[1].append("db02")
print(record)
```

Output:

```text
('prod', ['db01', 'db02'])
```

The tuple's structure remains unchanged, but the list referenced by the tuple was mutated.

---

## 1.9.8 Identity Versus Equality

`==` asks whether objects compare as equal. `is` asks whether both expressions identify the same object.

```python
a = [1, 2, 3]
b = a
c = [1, 2, 3]

print(a == b)
print(a is b)
print(a == c)
print(a is c)
```

Output:

```text
True
True
True
False
```

Use equality for value comparison and identity when identity itself matters, especially with singleton sentinels:

```python
if result is None:
    ...
```

Do not depend on integer caching, string interning, or similar runtime optimizations.

---

## 1.9.9 Assignment Does Not Copy Objects

```python
original = {"environment": "production", "retries": 3}
working = original
working["retries"] = 5
print(original["retries"])
```

Output:

```text
5
```

Both names refer to the same dictionary. Independent state must be created deliberately when required.

---

## 1.9.10 Shallow Copies

A shallow copy creates a new outer container while retaining references to contained objects.

```python
original = ["db01", "db02"]
working = original.copy()
working.append("db03")
```

Nested state may still be shared:

```python
original = {"database": {"host": "db01", "port": 5432}}
working = original.copy()
working["database"]["host"] = "db02"
print(original["database"]["host"])
```

Output:

```text
db02
```

---

## 1.9.11 Deep Copies

`copy.deepcopy()` can be used when recursively independent state is appropriate.

```python
from copy import deepcopy

original = {"database": {"host": "db01", "port": 5432}}
working = deepcopy(original)
working["database"]["host"] = "db02"
```

Deep copying is not a universal solution. It can consume significant CPU and memory, duplicate more state than intended, interact with custom copy behavior, and be unsuitable for external resources or synchronization primitives. Prefer clear ownership and fresh object construction when those better represent the design.

---

## 1.9.12 Function Arguments and Parameter Binding

When a function is called, Python evaluates the argument expressions and binds the function's parameter names to the resulting objects in the function's local namespace.

```python
def add_server(servers):
    servers.append("db03")

cluster = ["db01", "db02"]
add_server(cluster)
print(cluster)
```

The parameter and caller's name refer to the same list during the call, so mutation is observable by the caller.

```python
def replace_servers(servers):
    servers = ["db99"]

cluster = ["db01", "db02"]
replace_servers(cluster)
print(cluster)
```

The local parameter is rebound; the caller's binding is unchanged. This model is more precise than simplistic "pass-by-value" or "pass-by-reference" terminology.

---

## 1.9.13 Mutable Default Arguments

Default expressions are evaluated when the function definition executes.

```python
def register_server(server, servers=[]):
    servers.append(server)
    return servers
```

The same default list can therefore be reused across calls. A common pattern for fresh per-call state is:

```python
def register_server(server, servers=None):
    if servers is None:
        servers = []
    servers.append(server)
    return servers
```

Mutable defaults are not inherently invalid, but persistent shared state should be intentional and documented.

---

## 1.9.14 Namespaces

A namespace maps names to objects. Python uses multiple namespaces, including local namespaces, enclosing function namespaces, module/global namespaces, and the built-in namespace. This allows different parts of a program to use the same textual name without necessarily referring to the same binding.

---

## 1.9.15 Scope and LEGB Name Resolution

For ordinary function-level name resolution, **LEGB** provides a useful mental model:

```text
L ── Local
E ── Enclosing function scopes
G ── Global / module
B ── Built-ins
```

LEGB is effective for the ordinary cases introduced here. Some constructs, including class and annotation scopes, have additional name-resolution rules covered later in the handbook.

---

## 1.9.16 Enclosing Scope

```python
def outer():
    environment = "production"

    def inner():
        print(environment)

    inner()

outer()
```

Because `inner()` has no local binding named `environment`, Python can resolve the name from its enclosing function scope. This behavior forms part of the foundation for closures.

---

## 1.9.17 The `global` Statement

```python
status = "starting"

def update():
    global status
    status = "running"

update()
print(status)
```

`global` directs assignment to the module-global binding. It should be used deliberately. Large amounts of writable global state increase coupling and can make applications harder to test, reason about, run concurrently, reuse, and troubleshoot.

---

## 1.9.18 The `nonlocal` Statement

`nonlocal` allows a nested function to target an existing binding in an enclosing non-global scope.

```python
def make_counter():
    count = 0

    def increment():
        nonlocal count
        count += 1
        return count

    return increment
```

A `nonlocal` name must resolve to an existing binding in an enclosing non-global scope. If no such binding exists, Python raises `SyntaxError`.

---

## 1.9.19 Assignment Targets

Assignment targets are not limited to simple names.

```python
a, b = 10, 20
first, *middle, last = [1, 2, 3, 4, 5]
config["timeout"] = 30
server.status = "ready"
```

Attribute and subscription assignments interact with the behavior of their target objects and are not equivalent to binding a simple local name.

---

## 1.9.20 Augmented Assignment

Augmented assignment has its own semantics and can perform an in-place operation when supported.

```python
a = [1, 2]
b = a
a += [3]

print(a)
print(b)
print(a is b)
```

Output:

```text
[1, 2, 3]
[1, 2, 3]
True
```

This is another practical reason to understand both object mutability and name binding.

---

## 1.9.21 Deleting a Name with `del`

For a simple name target, `del` removes the binding from the applicable namespace. It does not force immediate object destruction.

```python
a = [1, 2, 3]
b = a
del a
print(b)
```

The list remains reachable through `b`.

---

## 1.9.22 Object Lifetime

Removing or rebinding one name does not necessarily make an object unreachable.

```python
servers = ["db01", "db02"]
active = servers
servers = None
```

The list remains reachable through `active`. Application correctness should generally not depend on the exact instant at which memory is reclaimed.

---

## 1.9.23 CPython Reference Counting

CPython uses **reference counting as a primary object-lifetime mechanism and supplements it with cyclic garbage collection**. When the final strong reference to many ordinary objects disappears, CPython can commonly reclaim them promptly.

> **Reference-count timing is a CPython implementation characteristic, not a portable application lifecycle guarantee.**

Other Python implementations may use different memory-management strategies. Production code should not depend on immediate object destruction for correctness.

---

## 1.9.24 Cyclic Garbage Collection

Reference counting alone is insufficient for unreachable reference cycles. CPython supplements reference counting with cyclic garbage collection to identify and reclaim appropriate unreachable cycles.

> **Reference counting alone is not the complete Python memory-management model.**

Detailed garbage-collector behavior is covered later in the handbook.

---

## 1.9.25 Resource Lifetime Is Not Memory Lifetime

External resources such as files, sockets, database connections, transactions, and locks require explicit lifecycle management.

```python
with open("config.txt", encoding="utf-8") as file:
    content = file.read()
```

> **Memory reclamation and resource cleanup are related concerns, but they are not interchangeable.**

---

## 1.9.26 Weak References

Python's `weakref` module supports references that do not, by themselves, prevent eligible objects from being reclaimed.

```python
import weakref

class Service:
    pass

service = Service()
reference = weakref.ref(service)
print(reference() is service)
del service
print(reference())
```

Not every Python object supports weak references. Weak references are useful in specialized designs such as caches, object registries, metadata associations, and observer-style systems. They should not compensate for unclear ownership.

---

## 1.9.27 Production Example: Configuration Aliasing

```python
default_config = {"timeout": 30, "retries": 3}
worker_config = default_config
worker_config["timeout"] = 120
```

Both names refer to the same dictionary. If independent outer state is intended, create it deliberately. For nested configurations, remember that shallow copying may not provide sufficient isolation.

---

## 1.9.28 Production Example: Nested Manifest Mutation

```python
base_manifest = {
    "metadata": {
        "labels": {
            "app": "worker"
        }
    }
}

prod_manifest = base_manifest.copy()
prod_manifest["metadata"]["labels"]["environment"] = "prod"
```

Because the copy is shallow, nested structures remain shared. Depending on the application, safer approaches include fresh construction, controlled deep copies, immutable models, serialization boundaries, or dedicated builder functions.

> **Who owns this mutable state, and where is mutation allowed?**

---

## 1.9.29 Production Example: Function Mutation Contracts

```python
def normalize_config(config):
    config["environment"] = config["environment"].lower()
    return config
```

This mutates its argument. A non-mutating alternative can copy or reconstruct state first. Neither design is universally correct; ownership and mutation behavior should be deliberate, documented, and testable.

---

## 1.9.30 Shared State and Concurrency

Aliasing becomes particularly important when mutable state is accessed concurrently. If multiple threads, asynchronous tasks, callbacks, or components mutate the same object, synchronization or architectural controls may be required.

> **Which execution contexts hold references to this mutable object?**

Thread safety, atomicity, synchronization, process isolation, and asynchronous coordination are covered in later concurrency chapters.

---

## 1.9.31 Naming and Rebinding Practices

Python permits names to be rebound freely, but repeatedly changing the conceptual meaning of a name can reduce clarity.

Prefer descriptive names such as `retry_count`, `deployment_status`, and `deployment_result`. Dynamic typing provides flexibility; it should not reduce semantic clarity.

---

## 1.9.32 Avoid Unnecessary Built-in Shadowing

Bindings such as:

```python
list = [1, 2, 3]
str = "hello"
id = 100
```

can hide useful built-ins in the applicable scope. Prefer descriptive alternatives such as `items`, `message`, and `record_id`.

---

## 1.9.33 Common Failure Patterns

Common production mistakes include:

- mistaking assignment for copying;
- confusing mutation with rebinding;
- using `is` for ordinary value comparison;
- depending on integer caching, string interning, or `id()` representation;
- accidental mutable default arguments;
- treating `del` as forced destruction;
- relying on garbage collection for resource cleanup;
- excessive writable global state.

---

## 1.9.34 Troubleshooting Name-Binding Problems

When state changes unexpectedly:

1. Determine whether objects are shared using identity checks during debugging.
2. Find mutations such as `append()`, `extend()`, `update()`, `clear()`, item assignment, or attribute assignment.
3. Find rebinding statements.
4. Inspect function boundaries and mutation contracts.
5. Determine whether assignment, shallow copy, deep copy, or fresh construction is being used.
6. Inspect the applicable scope and binding.
7. Build a minimal reproducible example.

`id()` can help inspect identity within a process during debugging, but it must not be used as a persistent or distributed identifier.

---

## 1.9.35 Production Engineering Rules

1. Think in terms of **names bound to objects**.
2. Remember that assignment does not imply copying.
3. Distinguish rebinding from mutation.
4. Use `==` for value equality and `is` for identity.
5. Prefer `is None` and `is not None` for `None`.
6. Understand the ownership of important mutable objects.
7. Treat shared mutable state as an explicit design decision.
8. Do not assume shallow copies recursively isolate state.
9. Use deep copying only when its semantics are appropriate.
10. Make function mutation contracts clear.
11. Avoid accidental mutable default arguments.
12. Limit writable global state.
13. Use `nonlocal` only when enclosing closure state is intentional.
14. Avoid unnecessary built-in shadowing.
15. Do not depend on object interning or caching behavior.
16. Do not use `id()` as a durable application identifier.
17. Treat CPython reference-count timing as implementation behavior.
18. Do not depend on garbage-collection timing for correctness.
19. Manage external resources explicitly.
20. When debugging state, trace **names, objects, references, ownership, and mutation separately**.

## 1.9.38 Exercise Solutions

Solutions should demonstrate the following principles:

- rebinding one name does not rebind another name;
- aliases observe mutation of their shared object;
- equality and identity answer different questions;
- shallow copies can retain nested aliases;
- functions can construct independent results instead of mutating caller-owned inputs;
- parameter rebinding remains local;
- `None` sentinels can avoid accidental mutable-default reuse;
- LEGB determines ordinary function-level name resolution;
- `nonlocal` can intentionally update enclosing closure state;
- nested configuration ownership should be explicit rather than accidental.

## 1.9.39 Production Checklist

Before modifying shared state, ask:

- Who owns this object?
- Is it mutable?
- Who else holds a reference?
- Is this operation rebinding or mutation?
- Does this function mutate caller-owned state?
- Is copying necessary?
- If copied, is shallow copying sufficient?
- Are nested objects still shared?
- Is state shared across requests, threads, tasks, callbacks, or workers?
- Is global or closure state appropriate?
- Does correctness depend on garbage-collection timing?
- Are files, sockets, locks, transactions, and database connections explicitly managed?

## 1.9.40 Key Takeaways

The central Python model is:

```text
Namespace
    │
    └── name ─────────► object
```

Assignment establishes or changes bindings. Multiple names may identify one object, and for mutable objects changes can therefore be observed through multiple aliases.

Rebinding and mutation are different operations. Equality and identity answer different questions. Function parameters follow the same binding model: Python evaluates argument expressions and binds parameter names to the resulting objects.

Namespaces and scope determine how names are resolved. LEGB provides the principal model for ordinary function-level resolution, while `global` and `nonlocal` explicitly affect assignment targets in their respective scopes.

Finally, name lifetime, object lifetime, and external-resource lifetime must not be confused. Production applications should use explicit resource-management mechanisms and should not depend on garbage-collection timing.

> **When reasoning about Python state, trace names, objects, bindings, ownership, and mutation separately.**

That model scales from small scripts to production APIs, database tooling, automation frameworks, cloud services, and distributed workers.
