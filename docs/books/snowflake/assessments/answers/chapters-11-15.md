# Answers: Chapters 11–15

Version: v1.2.0  
Status: Production Release  
Last reviewed: 2026-08-15

1. The trigger starts the event, contributing factors increase likelihood or impact, and root cause explains the underlying failure mechanism.
2. UTC time, observation/action, owner, evidence identifier, configuration change and result.
3. Continue evidence collection, monitor stability, record the temporary mitigation and expiry, assign root-cause work and validate recurrence controls.
4. Review and declarative state improve repeatability, auditability, drift detection and rollback.
5. Passwords, private keys, tokens, OAuth secrets, MFA material and sensitive connection strings.
6. Restore the last approved grant state, validate identity/role/object access, audit impact, and add policy/testing that detects destructive privilege drift.
7. An SLI is a measured signal, an SLO is its target, and an alert threshold decides when response is required.
8. Operators must know who acts and whether the displayed state is current enough for decisions.
9. Investigate trends, workload timing and capacity before SLO failure; a reversible scheduling or isolation change may be justified, not an emergency resize.
10. Joins can amplify/shuffle rows, aggregations hold/group state, and windows sort/partition data; each produces different operator evidence.
11. Local/remote spill, partitions/bytes scanned, operator duration, rows, queueing, cache and comparable warehouse/data context.
12. Performance does not override correctness; validate result equivalence before accepting optimization.
13. Executive KPIs summarize business/service outcomes; diagnostics explain technical causes.
14. Without source, latency and owner, the number cannot be interpreted, trusted or acted upon.
15. Preserve workload-level SLOs and present an aggregate only with weighting, scope and caveats; do not hide divergent service performance.
