## 1.1.1 Introduction

Modern infrastructure is increasingly controlled through software APIs.

Cloud and platform services expose APIs for creating and managing resources such as:

* Networks
* Subnets
* Routing
* Firewalls
* Virtual machines
* Load balancers
* Kubernetes clusters
* Databases
* Storage
* DNS
* IAM
* Encryption keys
* Monitoring resources

This makes it possible to manage infrastructure programmatically rather than relying primarily on manual console operations.

**Infrastructure as Code (IaC)** is the practice of defining, provisioning, and managing infrastructure through machine-readable configuration or programmatic definitions.

Instead of maintaining instructions such as:

```text
1. Create the production network.
2. Create three private subnets.
3. Configure routing.
4. Create security groups.
5. Create an EKS cluster.
6. Create worker nodes.
7. Create PostgreSQL.
8. Configure monitoring.
```

the infrastructure itself can be represented through code.

A simplified Terraform example is:

```hcl
resource "aws_vpc" "production" {
  cidr_block = "10.20.0.0/16"

  tags = {
    Name        = "production-vpc"
    Environment = "production"
  }
}
```

The infrastructure definition can then participate in engineering processes such as version control, review, testing, security analysis, automation, and change governance.

---

# 1.1.2 Why Infrastructure as Code Exists

Consider an organization operating:

```text
Development
Staging
Production
Disaster Recovery
```

Without IaC, administrators might manually construct each environment.

A typical workflow could involve:

```text
Cloud Console
     |
     v
Create Network
     |
     v
Create Subnets
     |
     v
Configure Routing
     |
     v
Create Security Groups
     |
     v
Launch Compute
     |
     v
Create Database
     |
     v
Configure Monitoring
```

This can work for small environments.

At production scale, however, several problems emerge.

---

# 1.1.3 Human Error

Manual infrastructure operations are vulnerable to inconsistent configuration.

For example:

```text
Staging
Instance Type: m6i.large
```

and:

```text
Production
Instance Type: m6i.xlarge
```

may intentionally differ.

But another administrator might accidentally configure:

```text
Production
Instance Type: m6i.4xlarge
```

Without an authoritative configuration source, determining whether that difference is intentional can become difficult.

IaC makes infrastructure intent explicit and reviewable.

---

# 1.1.4 Configuration Drift

Suppose a security rule managed through Terraform is intended to allow:

```text
TCP/443
Source: 10.0.0.0/8
```

During troubleshooting, someone manually changes the remote infrastructure to:

```text
TCP/443
Source: 0.0.0.0/0
```

The running infrastructure now differs from its intended configuration.

This is an example of **configuration drift**.

Drift can result from:

* Manual console changes
* Cloud CLI operations
* Emergency remediation
* External automation
* Other infrastructure-management systems
* Changes to remote objects
* Provider or service behavior

Drift does not necessarily mean that an engineer acted incorrectly. During an incident, a manual change may be legitimate.

The operational requirement is to **detect, understand, and reconcile** the difference.

```text
Intended Configuration
        |
        v
Observed Difference
        |
        v
Investigation
        |
        +---- Expected?
        |
        +---- Emergency change?
        |
        +---- Unauthorized change?
        |
        +---- External automation?
        |
        v
Reconciliation
```

Drift detection should not be assumed to be instantaneous or universal; behavior depends on Terraform operations, provider behavior, configuration, and the remote system.

---

# 1.1.5 Reproducibility

One of IaC's most important benefits is reproducibility.

Instead of relying on:

```text
Documentation
+
Screenshots
+
Tickets
+
Tribal Knowledge
+
Engineer Memory
```

infrastructure definitions can be stored in source control.

Reusable definitions can then support multiple environments:

```text
Reusable Infrastructure
        |
        +------> Development
        |
        +------> Staging
        |
        +------> Production
        |
        +------> Disaster Recovery
```

The environments do not need to be identical.

Production may intentionally have:

* Greater capacity
* Multi-AZ deployment
* Longer backup retention
* Stronger monitoring
* Additional security controls
* Different scaling policies

The goal is **controlled consistency**, not blind duplication.

---

# 1.1.6 Declarative Infrastructure

Terraform primarily follows a **declarative configuration model**.

An engineer describes the infrastructure that should be managed.

For example:

```hcl
resource "aws_instance" "application" {
  ami           = "ami-example"
  instance_type = "t3.large"
}
```

The engineer does not normally write procedural instructions such as:

```text
Connect to AWS
Call EC2 API
Create instance
Wait for instance
Capture instance ID
Record instance metadata
```

Terraform and its providers determine the operations required to manage the declared resources.

This distinction can be summarized as:

```text
Imperative

"Perform these steps."
```

versus:

```text
Declarative

"Manage infrastructure with this configuration."
```

# 1.1.7 Terraform's Operational Model

A beginner-friendly explanation often says:

```text
Desired State
     |
     v
Terraform
     |
     v
Infrastructure
```

That is useful conceptually but incomplete.

A more accurate model is:

```text
Terraform Configuration
          |
          +----------------+
          |                |
          v                v
    Terraform State    Providers
          |                |
          |                v
          |         Remote APIs / Objects
          |                |
          +-------+--------+
                  |
                  v
            Terraform Plan
                  |
                  v
         Proposed Operations
                  |
                  v
           terraform apply
```

Terraform planning involves more than directly comparing a configuration file with the cloud.

Terraform uses information including:

* Configuration
* State
* Provider behavior
* Resource relationships
* Information obtained about remote objects

to determine proposed infrastructure operations.

---

# 1.1.8 Terraform State

Terraform **state** is fundamental to Terraform's operation.

Suppose the configuration contains:

```hcl
resource "aws_instance" "application" {
  ...
}
```

Terraform identifies that resource using an address such as:

```text
aws_instance.application
```

The cloud platform may identify the actual object as:

```text
i-0123456789abcdef0
```

Terraform state maintains the relationship between the Terraform resource instance and the corresponding remote object.

Conceptually:

```text
Terraform Configuration

aws_instance.application
          |
          v
     Terraform State
          |
          v
Remote Infrastructure Object

i-0123456789abcdef0
```

State also contains resource attributes and metadata Terraform needs for infrastructure-management operations.

Therefore Terraform state is not merely an optional cache.

It is critical Terraform metadata.

---

# 1.1.9 State Is a Production Asset

In production environments, state should be treated as critical operational data.

A mature design typically considers:

```text
Terraform
    |
    v
Remote State
    |
    +---- Access Control
    |
    +---- Encryption
    |
    +---- Backup / Recovery
    |
    +---- Auditability
    |
    +---- Locking where supported
```

The exact capabilities depend on the configured backend or Terraform execution platform.

State locking, for example, should not be assumed to exist for every possible backend.

Production Terraform state should generally not depend solely on a file stored on an engineer's workstation.

---

# 1.1.10 Sensitive Information in State

Terraform state may contain sensitive infrastructure information and, depending on the resources and providers involved, secret values.

Therefore:

```text
terraform.tfstate
```

must not be treated like an ordinary configuration artifact.

Production controls should consider:

* Encryption
* Least-privilege access
* Audit logging
* Backup
* Recovery
* Environment isolation
* Secure remote storage

State files should generally not be committed to normal Git repositories.

A common repository safeguard is:

```gitignore
*.tfstate
*.tfstate.*
```

However, `.gitignore` is only one defensive control and does not replace proper state architecture.

---

# 1.1.11 Dependency Management

Terraform automatically derives many infrastructure dependencies from references.

For example:

```hcl
resource "aws_subnet" "application" {
  vpc_id = aws_vpc.production.id
}
```

creates an implicit relationship:

```text
aws_vpc.production
        |
        v
aws_subnet.application
```

Terraform uses these relationships to construct a dependency graph and determine appropriate operation ordering.

Explicit dependencies can also be declared when a required dependency cannot be inferred from normal references.

Dependency management becomes especially important as infrastructure grows into hundreds or thousands of managed objects.

---

# 1.1.12 Version-Controlled Infrastructure

IaC enables infrastructure configuration to be stored in systems such as Git.

For example:

```text
terraform/
│
├── modules/
│   ├── networking/
│   ├── kubernetes/
│   ├── database/
│   └── monitoring/
│
└── environments/
    ├── development/
    ├── staging/
    └── production/
```

A production change can then be proposed through a pull request.

For example:

```diff
- instance_type = "m6i.large"
+ instance_type = "m6i.xlarge"
```

Reviewers can evaluate:

```text
Who requested this change?

Why?

Which environment is affected?

What resources will change?

Will anything be replaced?

Will anything be destroyed?

What is the blast radius?

What is the cost impact?

What is the recovery plan?
```

This provides much stronger governance than undocumented manual changes.

---

# 1.1.13 Git Reversion Is Not Infrastructure Rollback

An important production distinction is:

```text
Git Revert
    ≠
Infrastructure Rollback
```

Git can restore an earlier **configuration**.

That does not guarantee that the underlying infrastructure can be returned to its previous condition.

For example:

```text
Database
100 GB
   |
   v
500 GB
```

Reverting the Terraform configuration to:

```text
100 GB
```

does not guarantee that the cloud service supports shrinking the database storage.

Similarly, restoring code for a deleted stateful resource does not restore the lost data.

The handbook therefore distinguishes:

### Configuration Reversion

Returning infrastructure configuration to an earlier version.

### Infrastructure Recovery

Returning the actual service, infrastructure, and—where applicable—data to a known-good operational condition.

Infrastructure recovery may require:

* Terraform changes
* Provider-specific recovery
* Snapshot restoration
* Database recovery
* Resource recreation
* Traffic changes
* DNS changes
* Manual intervention

---

# 1.1.14 Terraform Plan

One of Terraform's most important operational capabilities is generating an execution plan.

```bash
terraform plan
```

allows engineers to inspect proposed changes before applying them.

A plan may indicate operations such as:

```text
Create
Update
Replace
Destroy
```

Production engineers should not ask only:

> Is the Terraform code valid?

They should ask:

> What infrastructure operations will this configuration cause?

---

# 1.1.15 Speculative and Saved Plans

A normal:

```bash
terraform plan
```

generates a plan for review.

Terraform can also save a plan:

```bash
terraform plan -out=tfplan
```

and subsequently apply that saved plan:

```bash
terraform apply tfplan
```

This distinction matters in CI/CD.

A mature workflow may use:

```text
Pull Request
     |
     v
Terraform Plan
     |
     v
Plan Artifact
     |
     v
Review / Approval
     |
     v
Controlled Apply
```

Production pipelines must also account for concurrent changes and the possibility that assumptions may become stale between planning and execution.

---

# 1.1.16 Terraform Validate

The command:

```bash
terraform validate
```

checks whether a Terraform configuration is syntactically valid and internally consistent.

It should **not** be interpreted as:

```text
"The infrastructure deployment will succeed."
```

Validation does not prove that remote cloud operations will succeed.

A stronger pipeline might contain:

```text
terraform fmt -check
        |
        v
terraform validate
        |
        v
Static Analysis
        |
        v
Security / Policy Checks
        |
        v
terraform plan
```

Each control addresses a different class of risk.

A mature infrastructure workflow should generally be stronger than:

A production model may instead use:

   |
   +---- Security Analysis

   +---- Policy Evaluation
   |
   +---- Cost Analysis
   |
   +---- Terraform Plan
   |

Technical Review
   |
   v
Risk / Blast-Radius Review
   |
   v
Approval
   |
   v
Controlled Apply
   |

Post-Apply Validation
   |

The exact controls depend on organizational requirements and infrastructure criticality.

# 1.1.18 Direct Production Applies

Routine unmanaged production execution from engineer workstations introduces risks such as:

* Unreviewed changes
* Inconsistent credentials
* Different Terraform versions
* Different provider versions
* Local environment differences
* Interrupted execution
* Weak auditability
* Excessive privileges

Where practical, production organizations commonly prefer controlled automation:

```text
Engineer
   |
   v
Git
   |
   v
CI/CD
   |
   v
Controlled Identity
   |
   v
Terraform
   |
   v
Production
```

Direct operations may still be required for:

* Initial bootstrap
* Incident response
* Recovery
* Break-glass procedures

Such changes should be controlled, documented, and reconciled afterward.

---

# 1.1.19 Blast Radius

Automation increases speed.

It can also increase blast radius.

A small configuration change may affect many resources:

```text
One-Line Change
      |
      v
Terraform Plan
      |
      v
200 Resource Operations
      |
      v
Production Impact
```

Production plan review should therefore consider:

* Creates
* Updates
* Replacements
* Destructions
* Dependencies
* Data risk
* Availability risk
* Network impact
* Security impact
* Cost impact

The ability to automate a change does not mean that the change is safe.

---

# 1.1.20 Failed Apply and Partial Infrastructure Changes

A critical Terraform operational principle is:

> A Terraform apply should not be treated as one atomic transaction covering the entire infrastructure deployment.

For example:

```text
Resource A ---- SUCCESS

Resource B ---- SUCCESS

Resource C ---- FAILED

Resource D ---- NOT CREATED
```

The environment may now be partially changed.

The correct operational response is not automatically:

```bash
terraform destroy
```

Instead:

```text
Apply Failure
      |
      v
Assess
      |
      v
Inspect Error
      |
      v
Inspect Infrastructure
      |
      v
Inspect State
      |
      v
Determine Safe Recovery
      |
      v
Generate New Plan
```

Understanding partial failure is essential to operating Terraform safely.

---

# 1.1.21 Destructive Change Protection

Critical resources deserve additional safeguards.

Examples include:

* Databases
* Persistent storage
* Kubernetes clusters
* Networking
* Encryption keys
* DNS
* Identity systems
* Message brokers

Production protection can combine:

```text
Terraform Lifecycle Controls
           +
Provider-Native Deletion Protection
           +
Policy Controls
           +
Approval Gates
           +
Backups
           +
Recovery Procedures
```

No single control should be treated as a substitute for data protection or recovery planning.

---

# 1.1.22 Credentials and Least Privilege

Terraform often requires significant cloud permissions.

Production automation should therefore follow least-privilege principles.

Where supported, organizations may prefer:

```text
CI/CD
  |
  v
Federated / Short-Lived Identity
  |
  v
Cloud Role
  |
  v
Terraform Provider
  |
  v
Infrastructure APIs
```

rather than long-lived administrator credentials.

Different identities may be appropriate for:

```text
Development
Staging
Production
Bootstrap
Recovery
```

Terraform should receive only the permissions necessary for its intended operations.

---

# 1.1.23 Secret Management

Terraform configuration should not be treated as a secrets vault.

Avoid:

```hcl
database_password = "ProductionPassword123"
```

inside source-controlled configuration.

Terraform can integrate with secret-management systems, but engineers must consider whether secret values can appear in:

* Configuration
* Variables
* State
* Plans
* Logs
* CI/CD artifacts

The fundamental principle is:

```text
Terraform
    ≠
Secret Management System
```

Secret-handling architecture will be covered in detail later in the handbook.

---

# 1.1.24 Version Management

Production Terraform environments should control versions of:

```text
Terraform CLI
Providers
Modules
```

Uncontrolled dependency changes can introduce unexpected behavior.

A safer lifecycle is:

```text
Version Change
      |
      v
Test
      |
      v
Plan
      |
      v
Review
      |
      v
Controlled Promotion
```

Provider dependency locking and module-version management become important production practices.

# 1.1.25 Infrastructure as Code and Disaster Recovery

IaC can significantly improve infrastructure reconstruction.

Without IaC:

```text
Documentation
+
Screenshots
+
Tickets
+
Engineer Knowledge
        |
        v
Manual Reconstruction
```

With IaC:

```text
Version-Controlled Infrastructure
        |
        v
Controlled Deployment
        |
        v
Infrastructure Reconstruction
```

However:

```text
IaC ≠ Disaster Recovery
```

Complete recovery may also require:

```text
Terraform Repository
+
Terraform State
+
Cloud Access
+
Database Backups
+
Storage Backups
+
Secrets
+
Certificates
+
DNS
+
Application Artifacts
+
External Dependencies
+
Recovery Runbooks
```

Terraform can recreate infrastructure.

It cannot recreate data that was never protected.

# 1.1.26 Infrastructure as Code and SRE

Infrastructure as Code aligns closely with Site Reliability Engineering.

A simplified progression is:

```text
Manual Operations
      |
      v
Codified Infrastructure
      |
      v
Repeatability
      |
      v
Automation
      |
      v
Reduced Operational Toil
      |
      v
Greater Operational Consistency
```

However, IaC does not automatically create reliability.

Poor Terraform engineering can create:

* Large blast radius
* Fragile modules
* Failed deployments
* Security exposure
* State incidents
* Operational complexity

Reliable IaC requires disciplined engineering and operations.

# 1.1.27 Infrastructure as Code and FinOps

IaC also provides opportunities for cost governance.

Consider:

```diff
- instance_type = "m6i.large"
+ instance_type = "m6i.8xlarge"
```

Because the change exists as code, CI/CD or external tooling can potentially evaluate its cost implications before deployment.

Organizations may integrate:

* Cost estimation
* Mandatory tagging
* Instance restrictions
* Budget controls
* Policy checks
* Approval requirements

Cost analysis is not guaranteed automatically by Terraform itself; it generally requires additional tooling or platform capabilities.

# 1.1.33 Break-Glass Operations

Normal automation may occasionally be unavailable or too slow during a severe production incident.

Organizations should define controlled break-glass procedures.

```text
Production Incident
       |
       v
Normal Workflow Unavailable
       |
       v
Authorized Break-Glass
       |
       v
Emergency Change
       |
       v
Service Recovery
       |
       v
Document Change
       |
       v
Reconcile Terraform
       |
       v
Post-Incident Review
```

Break-glass access should answer:

* Who can authorize it?
* Who can execute it?
* Which credentials are used?
* How is activity audited?
* How is temporary access revoked?
* How are emergency changes reconciled?

Emergency operations should be controlled rather than improvised.

# 1.1.34 Post-Apply Validation

Infrastructure delivery is not complete merely because:

```text
terraform apply
```

returns successfully.

Production deployment should include operational verification.

```text
terraform apply
      |
      v
Resource Validation
      |
      +---- Health
      +---- Connectivity
      +---- Security
      +---- Monitoring
      +---- Database Access
      +---- Application Dependencies
      |
      v
Production Verification
```

A technically successful infrastructure operation can still produce an unhealthy service.

# 1.1.35 Observability and Auditability

Infrastructure automation is itself a production system.

Organizations may monitor signals such as:

* Plan failures
* Apply failures
* Apply duration
* Policy failures
* Security findings
* State-lock contention
* Drift findings
* Deployment frequency
* Change failure rate

Production workflows should also make it possible to determine:

```text
Who requested the change?

Who reviewed it?

What changed?

What plan was evaluated?

Who approved it?

Which identity applied it?

When was it applied?

Did it succeed?

Was production validated?
```

Evidence may come from Git, CI/CD, Terraform execution systems, cloud audit logs, and change-management platforms.

---

# 1.1.36 Production Ownership

Infrastructure as Code requires clear ownership.

A production organization should be able to answer:

```text
Who owns the Terraform repositories?

Who owns shared modules?

Who owns remote state?

Who controls provider upgrades?

Who reviews production plans?

Who responds to failed applies?

Who investigates drift?

Who owns break-glass procedures?

Who owns Terraform disaster recovery?
```

Automation without ownership creates operational risk.

# 1.1.42 Key Takeaways

Infrastructure as Code transforms infrastructure management from primarily manual administration into a software-engineering-style discipline.

The fundamental lifecycle is:

```text
Infrastructure Requirement
          |
          v
Infrastructure Code
          |
          v
Version Control
          |
          v
Validation
          |
          v
Review
          |
          v
Plan
          |
          v
Controlled Deployment
          |
          v
Verification
          |
          v
Operations
```

Remember these principles:

1. Infrastructure can be represented through machine-readable definitions.
2. Infrastructure configuration can be version controlled and reviewed.
3. Terraform primarily uses a declarative configuration model.
4. Terraform state is fundamental to mapping managed resources to remote objects.
5. State must be protected as critical production metadata.
6. Drift must be detected, understood, and reconciled.
7. `terraform validate` does not prove that deployment will succeed.
8. Terraform plans must be reviewed for actual infrastructure impact.
9. Automation can dramatically increase blast radius.
10. Terraform apply can leave partially changed infrastructure when operations fail.
11. Git configuration reversion is not the same as infrastructure recovery.
12. Production Terraform should use controlled credentials and least privilege.
13. Secrets require deliberate handling because they can reach configuration, plans, logs, or state.
14. Successful apply does not eliminate the need for post-deployment validation.
15. IaC can strengthen disaster recovery but does not replace backups or recovery planning.
16. Terraform automation itself requires observability, auditability, ownership, and recovery procedures.
17. Reliable IaC combines automation with disciplined SRE and production-engineering practices.

---

# Production Engineering Principle

> **Infrastructure should be treated with the same engineering discipline as production software: versioned, reviewed, tested, secured, observable, auditable, and recoverable.**

And for Terraform specifically:

> **A successful `terraform apply` means Terraform completed the requested operations; it does not by itself prove that the resulting production service is healthy, secure, or operationally correct.**
