## 1.2.1 Introduction

Infrastructure can be created and managed through many interfaces:

* Cloud management consoles
* Command-line interfaces
* APIs
* SDKs
* Shell scripts
* Configuration-management systems
* Infrastructure as Code
* Managed cloud services
* Kubernetes controllers and operators

Manual infrastructure management is not inherently wrong.

Experienced engineers routinely use consoles and command-line tools for:

* Investigation
* Troubleshooting
* Verification
* Learning
* Incident response
* Recovery
* Bootstrap operations
* One-time administrative tasks
* Break-glass procedures

The operational problem appears when large production environments depend primarily on repeated human procedures and undocumented changes.

Consider a production platform containing:

```text
Production Platform
│
├── VPC
├── Subnets
├── Route Tables
├── NAT Gateways
├── Security Groups
├── Load Balancers
├── Kubernetes
├── Databases
├── Kafka
├── Caches
├── Object Storage
├── IAM
├── Encryption Keys
├── DNS
├── Secrets
└── Monitoring
```

Creating this environment once manually may be manageable.

Maintaining it consistently across:

```text
Development
+
QA
+
Staging
+
Production
+
Disaster Recovery
```

creates a much larger engineering challenge.

The number of resources, dependencies, engineers, environments, changes, and failure scenarios increases rapidly.

Infrastructure as Code helps address this scaling problem by moving repeatable infrastructure intent into machine-readable definitions.

---

# 1.2.2 Manual Does Not Mean Bad

A critical principle is:

> **Manual infrastructure management is not automatically poor infrastructure management.**

A skilled engineer can create highly reliable infrastructure manually.

Likewise, poorly engineered Terraform can create unreliable infrastructure automatically.

The comparison should therefore not be:

```text
Manual
   vs.
Automation
```

as though one is inherently good and the other inherently bad.

The more useful distinction is:

```text
Repeated Human Implementation
           |
           v
Human-Driven Consistency
```

versus:

```text
Codified Infrastructure
           |
           v
Automated + Reviewable Consistency
```

As infrastructure scale increases, relying exclusively on human memory and procedural discipline becomes increasingly difficult.

---

# 1.2.3 Infrastructure as Code vs. Terraform

Infrastructure as Code is the broader engineering practice.

Terraform is one implementation of that practice.

```text
Infrastructure as Code
        |
        v
Engineering Practice
```

```text
Terraform
        |
        v
IaC Technology
```

Not every IaC technology provides exactly the same capabilities.

Features such as:

* State management
* Dependency graphs
* Drift identification
* Planning
* Resource import

are implementation-specific.

This handbook focuses primarily on Terraform while retaining the broader IaC engineering principles.

# 1.2.4 Human Error

Repeated manual infrastructure operations create opportunities for human error.

Suppose the standard database configuration requires:

```text
Encryption        Enabled
Backups           14 days
Monitoring        Enabled
Deletion Protect  Enabled
```

Three databases are created manually.

The result becomes:

| Setting             | DB-A    | DB-B     | DB-C     |
| ------------------- | ------- | -------- | -------- |
| Encryption          | Enabled | Enabled  | Enabled  |
| Backups             | 14 days | 7 days   | 14 days  |
| Monitoring          | Enabled | Disabled | Enabled  |
| Deletion Protection | Enabled | Enabled  | Disabled |

All three databases may appear operational.

But their reliability characteristics differ.

IaC makes these properties easier to standardize and review.

However:

> **IaC reduces some repetitive human errors; it does not eliminate human error.**

A configuration error can itself become automated.

```text
Manual Error
     |
     v
One Resource
```

may become:

```text
Terraform Error
      |
      v
Reusable Module
      |
      v
Many Resources
```

Automation can therefore increase the blast radius of systematic mistakes.

# 1.2.5 Configuration Consistency

Infrastructure resources often contain many configuration properties.

A production database might require:

```text
Engine Version
Instance Size
Storage
Encryption
Backup Retention
Maintenance Window
Parameter Group
Subnet Group
Security Groups
Monitoring
Logging
Deletion Protection
High Availability
Tags
```

IaC makes these requirements machine-readable.

Reusable modules can further standardize them.

However:

```text
IaC Enables Consistency
```

does not mean:

```text
IaC Guarantees Consistency
```

Differences can still arise through:

* Different variables
* Different module versions
* Different provider versions
* Manual changes
* External automation
* Environment-specific overrides
* State differences

Consistency remains an engineering responsibility.

# 1.2.6 Configuration Drift

Suppose production is intended to contain:

```text
Security Group

TCP/443
Source: 10.0.0.0/8
```

During an incident, an engineer changes it to:

```text
TCP/443
Source: 0.0.0.0/0
```

The actual infrastructure now differs from the intended configuration.

This is configuration drift.

Drift can originate from:

* Console changes
* CLI operations
* Scripts
* APIs
* Incident remediation
* Security automation
* Autoscalers
* Kubernetes controllers
* Managed services
* Other IaC systems

Drift is therefore not necessarily caused by a human.

---

# 1.2.7 Terraform Does Not Continuously Reconcile Everything

Terraform should not be confused with a continuously running controller.

Simply having Terraform configuration does not mean Terraform is continuously watching every remote resource.

A simplified model is:

```text
Terraform Configuration
        |
        v
Terraform Operation
        |
        v
Provider Reads Remote Objects
        |
        v
Relevant Differences Identified
        |
        v
Terraform Plan
```

Organizations that require ongoing drift detection generally need:

* Scheduled Terraform operations
* CI/CD automation
* Terraform execution platforms
* External drift-detection systems

Drift management is therefore an operational process.

---

# 1.2.8 Intended Configuration, State, and Actual Infrastructure

Production Terraform requires understanding three different concepts.

### Terraform Configuration

Represents the intended Terraform-managed configuration.

```text
Terraform Configuration
        |
        v
Intended Managed Configuration
```

### Terraform State

Maintains Terraform resource mappings, attributes, and operational metadata.

```text
Terraform State
        |
        v
Resource Mapping / Metadata
```

### Remote Infrastructure

Represents the actual cloud or platform objects.

```text
AWS / Azure / GCP / Kubernetes
        |
        v
Actual Remote Infrastructure
```

Operational correctness depends on keeping these appropriately aligned.

An organization may designate its Git repository as the authoritative source for **intended Terraform-managed configuration**, but the repository alone does not describe every aspect of current production reality.

# 1.2.9 Tribal Knowledge

Manual infrastructure frequently becomes dependent on individual engineers.

Examples include:

```text
"Ask Alex how networking works."

"Priya knows the database configuration."

"Only Sam understands production."
```

This creates operational risk when an engineer:

```text
Takes Vacation
Gets Sick
Changes Team
Leaves Organization
```

Infrastructure knowledge should not exist exclusively in human memory.

IaC can move substantial infrastructure intent into version-controlled configuration.

However, Terraform does not replace architecture documentation.

A mature system combines:

```text
Architecture Documentation
          +
Terraform Configuration
          +
Operational Runbooks
```

# 1.2.10 Documentation Drift

Manual environments often depend heavily on written procedures.

Initially:

```text
Documentation
      =
Infrastructure
```

Over time:

```text
Documentation
      |
      | changes slowly
      v

Actual Infrastructure
      |
      | changes frequently
      v

Documentation ≠ Reality
```

Documentation remains essential.

But documentation describing infrastructure is not equivalent to an executable infrastructure definition.

Documentation should explain:

* Architecture
* Design rationale
* Failure domains
* Dependencies
* Ownership
* Recovery strategy

Terraform should express the infrastructure implementation Terraform manages.

# 1.2.11 Reproducibility

One of IaC's strongest benefits is improved reproducibility.

Instead of reconstructing infrastructure from:

```text
Documentation
+
Screenshots
+
Tickets
+
Cloud History
+
Engineer Knowledge
```

teams can use version-controlled infrastructure definitions.

However:

```text
Same Terraform Code
        ≠
Guaranteed Identical Infrastructure Forever
```

Reproducibility may also depend on:

* Terraform version
* Provider versions
* Module versions
* Variables
* Machine images
* External APIs
* Credentials
* Secrets
* Quotas
* Available instance types
* DNS
* Certificates
* Data

The stronger engineering principle is:

> **IaC substantially improves reproducibility when its versions, inputs, dependencies, and external prerequisites are controlled.**

# 1.2.12 Environment Snowflakes

A snowflake environment develops unique characteristics through accumulated uncontrolled configuration.

```text
Development
    |
    +---- Known Configuration

Staging
    |
    +---- Known Configuration
    +---- Manual Changes

Production
    |
    +---- Emergency Changes
    +---- Unique IAM
    +---- Undocumented Routing
    +---- Unknown Exceptions
```

Eventually:

```text
Dev ≠ Staging ≠ Production
```

However:

```text
Intentional Difference
        ≠
Snowflake
```

Production may intentionally use:

* Larger capacity
* Multi-AZ deployment
* Stronger security
* Longer backup retention
* More monitoring
* Different scaling

The anti-pattern is an **uncontrolled or unexplained difference**.

```text

      |
      v

      v

      |
      v
```

* Security approvals
* Architecture review
* Change windows
* Quota requests
* Compliance requirements

From an SRE perspective, toil tends to be work that is:

```text
Manual
Repetitive
Automatable
Tactical
Without Enduring Value
Growing with Service Scale
```

Not every manual task is toil.

Investigating a unique production failure, for example, may require substantial manual engineering without being toil.

Repeatedly performing:

```text

Create Subnets
Create Security Groups
Create IAM
Configure Monitoring
Apply Tags
Configure Backups
```

across many environments is a much stronger example.

IaC shifts work from:

```text
Repeated Manual Implementation
```

toward:

```text
Architecture
Automation
Testing
Review
Security
Reliability
Recovery
```

* Module design
* Testing

* Provider upgrades
* Terraform upgrades
* Security
* Policy
* Documentation
* Drift management
* Recovery


# 1.2.16 Infrastructure Scale

Manual operations may be manageable for:

```text
1 Account
1 Region
10 Resources
1 Engineer
```

The model becomes much harder with:

```text
50 Accounts
20 Regions
5,000 Resources
100 Engineers
```

As scale increases, organizations face more:

* Changes
* Dependencies
* Drift
* Permissions
* Security requirements
* Audit requirements
* Cost controls
* Recovery complexity

Terraform helps address these problems but also develops scaling concerns of its own, including:

* Large states
* Large dependency graphs
* Long plans
* Long applies
* Provider API limits
* Team concurrency

Automation must itself be architected for scale.

# 1.2.25 Idempotency

An important infrastructure automation concept is **idempotency**.

Conceptually, once the intended condition has been reached, repeating an idempotent operation should not continually create unintended additional changes.

Suppose the intended infrastructure is:

```text
One VPC
```

A naive script that repeatedly performs:

```text
Create VPC
```

might create multiple VPCs.

A state-aware declarative system aims to determine whether the managed object already exists and whether a change is required.

A healthy Terraform workflow often aims toward:

```text
Apply
  |
  v
Intended Configuration Reached
  |
  v
Plan Again
  |
  v
No Unexpected Changes
```

This does not mean every Terraform configuration will always produce a perfectly empty subsequent plan.

Provider behavior, external systems, computed attributes, and configuration design can affect results.

Persistent unexplained changes deserve investigation.

# 1.2.26 Scripts vs. Terraform

Scripts remain extremely valuable.

For example:

```bash
aws ec2 create-vpc ...
aws ec2 create-subnet ...
```

Scripts are often procedural:

```text
Perform Operation A
Then Operation B
Then Operation C
```

Terraform provides a primarily declarative, state-aware resource-management model.

General-purpose scripts often require engineers to implement more of:

* Resource discovery
* State tracking
* Change detection
* Idempotency
* Dependency handling
* Error recovery

This distinction is not absolute.

Scripts can be idempotent, and declarative systems may contain procedural behavior.

The tools solve overlapping but different problems.

---

# 1.2.27 Partial Failure Exists in Both Models

Partial infrastructure failure is not unique to Terraform.

A manual change might produce:

```text
Route Change          SUCCESS
Security Change       SUCCESS
Load Balancer Change  FAILED
DNS Change            NOT STARTED
```

The environment is partially changed.

Terraform operations can also fail partway through.

Therefore every production change system requires:

```text
Change
   |
   v
Execute
   |
   v
Verify
   |
   v
Failure?
   |
   +---- No ---> Complete
   |
   +---- Yes --> Assess / Recover
```

Automation does not remove the need for recovery engineering.

# 1.2.28 Brownfield Infrastructure

Many organizations adopt Terraform after infrastructure already exists.

This is a **brownfield environment**.

For example:

```text
Existing Production
│
├── 20 VPCs
├── 50 Databases
├── 15 Kubernetes Clusters
├── 400 Security Groups
├── 800 IAM Roles
└── Thousands of Resources
```

Terraform adoption should not automatically mean:

```text
Delete Everything
      |
      v
Rebuild
```

Existing infrastructure can often be progressively brought under Terraform management.

Before adopting existing infrastructure, teams should understand what exists.


# 1.2.31 Resource Risk Classification

Infrastructure should be classified according to operational risk.

| Class         | Examples                     | Typical Risk |
| ------------- | ---------------------------- | ------------ |
| Stateless     | Compute, some load balancers | Lower        |

# 1.2.33 Import Does Not Mean Recreate

The objective of adopting existing infrastructure is usually:

```text
Existing Resource
       |
       v
Terraform Management
```

not:

```text
Existing Resource
       |
       v

       |
       v
```

# 1.2.34 First Plan After Adoption

The first Terraform plan after adopting an existing production resource deserves exceptional scrutiny.

An ideal result may approach:

```text
No Changes
```

or contain only explicitly understood differences.

If the plan shows:

```text
50 to change
12 to replace
4 to destroy
```

the correct response is not:

```text
Apply
```

It is:

```text
STOP
  |
  v
Investigate
```

Every unexpected replacement or destruction must be understood before Terraform modifies existing production infrastructure.

# 1.2.35 Ownership Boundaries Between Controllers

Modern infrastructure may have several automation systems.

For example:

```text
Terraform
    |
    +---- VPC
    +---- Subnets
    +---- Kubernetes Cluster
    +---- IAM
```

```text
GitOps
    |
    +---- Deployments
    +---- Services
    +---- Application Configuration
```

```text
Autoscaler
    |
    +---- Dynamic Capacity
```

Problems occur when multiple controllers compete over the same property.

Example:

```text
Terraform
    |
    +---- desired_capacity = 5

Autoscaler
    |
    +---- desired_capacity = 10
```

Ownership must be deliberate.

> **Two independent controllers should not casually fight over the same infrastructure property.**

# 1.2.38 Destructive Changes

Any production plan containing:

```text
destroy
```

or:

```text
replace
```

for critical infrastructure deserves explicit investigation.

Reviewers should ask:

```text

Could data be lost?

Will downtime occur?

Is deletion protection enabled?

Is backup verified?

Can traffic be drained?

What is the recovery path?
```

A technically valid plan can still be operationally unacceptable.

# 1.2.39 Shared Module Blast Radius

Reusable modules improve consistency.

They also create shared failure domains.

```text
Shared Module
     |
     +---- Development
     +---- Staging
     +---- Production-A
     +---- Production-B
```

A defective module release may affect every consumer.

Shared modules therefore require:

```text
Versioning
+
Testing
+
Review
+
Controlled Promotion
```

Reuse increases leverage.

Leverage increases potential blast radius.

# 1.2.41 State Boundaries

Brownfield adoption raises an architectural question:

> Which resources should belong to which Terraform state?

One giant state can create:

```text
Large Blast Radius
Long Plans
Concurrency Problems
Complex Ownership
```

Excessive fragmentation can create:

```text
Dependency Complexity
Operational Overhead
Many Pipelines
Difficult Coordination
```

State boundaries should consider:

* Environment
* Ownership
* Security
* Failure domain
* Deployment frequency
* Resource lifecycle
* Dependencies
* Recovery requirements

There is no universal state size that is correct for every organization.

# 1.2.43 Separation of Duties

```text
Author
Reviewer
Approver
Executor
```

Terraform workflows can support these controls through surrounding systems such as:

* Git
* CI/CD
* Identity platforms
* Change-management systems

Terraform itself does not automatically implement organizational separation of duties.

# 1.2.45 RTO and Infrastructure Reconstruction

Suppose:

```text
RTO = 4 Hours
```

but manual infrastructure reconstruction requires:

```text
Networking       2 hours
Kubernetes       2 hours
Database Setup   1 hour
Security         1 hour
Monitoring       1 hour
Validation       2 hours
```

Infrastructure reconstruction alone can exceed the recovery objective.

IaC can reduce reconstruction time.

But IaC does not guarantee an RTO.

A more complete model is:

```text
RTO Requirement
      |
      v
Recovery Architecture
      |
      +---- Infrastructure
      +---- Data
      +---- Applications
      +---- Dependencies
      +---- Validation
      |
      v
Recovery Test
      |
      v
Measured Recovery Time
```

Only testing provides meaningful evidence that the recovery target can be achieved.

---

# 1.2.46 Disaster Recovery Testing

A production recovery exercise should test questions such as:

```text
Can Terraform initialize?

Can state be accessed or restored?

Are providers available?

Are modules available?

Do recovery credentials work?

Are machine images available?

Are quotas sufficient?

Can databases be restored?

Can secrets be recovered?

Can DNS be changed?

Can applications reconnect?
```

A Terraform repository that has never participated in a recovery exercise should not automatically be assumed to provide reliable disaster recovery.

---

# 1.2.47 Terraform Is Also a Recovery Dependency

Once Terraform manages critical infrastructure, Terraform itself becomes part of the recovery chain.

Potential dependencies include:

```text
Git
CI/CD
Terraform CLI
Provider Registry
Module Registry
State Backend
Credentials
Cloud APIs
```

A major incident may affect one or more of these systems.

Recovery architecture should therefore consider controlled alternatives and break-glass procedures.

---

# 1.2.48 Multi-Cloud Complexity

Terraform can provide a common infrastructure-management workflow across:

```text
AWS
Azure
Google Cloud
Kubernetes
```

However:

```text
Common Terraform Workflow
        ≠
Common Cloud Architecture
```

AWS, Azure, and Google Cloud retain different:

* Networking semantics
* IAM models
* Managed services
* Failure domains
* APIs
* Quotas

Terraform does not eliminate the need for provider-specific expertise.

# 1.2.49 Compliance and Governance

Machine-readable infrastructure can support automated evaluation of requirements such as:

```text
Encryption Enabled
Public Access Disabled
Required Tags Present
Backups Enabled
Logging Enabled
Approved Regions
Approved Instance Types
```

A mature governance model may combine:

```text
Terraform
+
Policy as Code
+
Cloud-Native Guardrails
+
Identity Controls
+
Logging
+
Evidence Collection
+
Human Governance
```

Terraform contributes to compliance engineering.

It does not constitute compliance by itself.

---

# 1.2.50 Console and CLI Use

A production Terraform handbook should not teach:

> Never use the cloud console.

Nor should it teach:

> Never use the cloud CLI.

These tools remain essential.

The stronger principle is:

> **Use consoles and CLIs for visibility, investigation, diagnostics, verification, and controlled operations; avoid allowing unmanaged changes to become the permanent infrastructure-management model.**

The interface is not the problem.

Unmanaged change is.

# 1.2.54 Production Adoption Checklist

Before adopting an existing production resource into Terraform:

* [ ] Identify its owner.
* [ ] Identify dependent applications.
* [ ] Determine whether it is stateful.
* [ ] Verify backups where appropriate.
* [ ] Determine deletion risk.
* [ ] Determine replacement risk.
* [ ] Identify the appropriate Terraform state.
* [ ] Define Terraform configuration.
* [ ] Control Terraform/provider/module versions.
* [ ] Import or adopt using the supported workflow.
* [ ] Generate a Terraform plan.
* [ ] Investigate unexpected changes.
* [ ] Investigate every unexpected replacement.
* [ ] Investigate every unexpected destruction.
* [ ] Verify lifecycle and provider-native protections.
* [ ] Validate the resource after adoption.
* [ ] Document ownership.
* [ ] Establish future change procedures.
* [ ] Establish drift handling.
* [ ] Establish recovery procedures.

# 1.2.56 Production Engineering Principles

### Principle 1

> **Manual infrastructure operations are useful; unmanaged infrastructure changes are dangerous.**

### Principle 2

> **Infrastructure as Code reduces repetitive human implementation but does not eliminate human judgment or human error.**

### Principle 3

> **Automation can reduce repetitive mistakes while increasing the blast radius of systematic mistakes.**

### Principle 4

> **Terraform configuration should be treated as the authoritative definition of intended Terraform-managed infrastructure, while state and actual remote infrastructure must also be understood operationally.**

### Principle 5

> **Architecture documentation, Terraform configuration, and operational runbooks solve different problems and should complement one another.**

### Principle 6

> **Understand existing infrastructure before attempting to automate or import it.**

### Principle 7

> **Unexpected replacement or destruction during brownfield adoption is a stop-and-investigate condition.**

### Principle 8

> **Two automation systems should not casually compete to manage the same infrastructure property.**

### Principle 9

> **Emergency changes are legitimate when necessary, but they must eventually be reconciled with the intended managed configuration.**

### Principle 10

> **Infrastructure recovery must be tested; IaC alone does not prove recoverability.**

# 1.2.57 Key Takeaways

The problems with manual infrastructure management become increasingly significant as infrastructure and organizational scale grow.

Major challenges include:

1. Human error
2. Configuration inconsistency
3. Configuration drift
4. Tribal knowledge
5. Documentation drift
6. Poor reproducibility
7. Environment snowflakes
8. Slow repetitive provisioning
9. Operational toil
10. Scaling complexity
11. Weak change context
12. Limited peer review
13. Security inconsistency
14. IAM inconsistency
15. Metadata inconsistency
16. Cost-control challenges
17. Orphaned resources
18. Dependency complexity
19. Partial-change failures
20. Disaster-recovery complexity
21. RTO impact
22. Multi-cloud complexity
23. Compliance overhead
24. Auditability challenges

Infrastructure as Code addresses many of these problems by moving infrastructure intent into machine-readable, reviewable, version-controlled definitions.

But:

```text
IaC
 ≠
Automatic Reliability
```

and:

```text
Terraform
 ≠
Automatic Governance
```

The desired operating model is:

```text
        |
        v
```

# Production Engineering Principle

> **The goal of Terraform adoption is not to automate infrastructure as quickly as possible. The goal is to establish controlled, reproducible, reviewable, secure, and recoverable infrastructure management without creating unacceptable production risk.**

For existing environments:

> **Understand before importing, plan before applying, and investigate every unexpected replacement or destruction before allowing Terraform to modify production infrastructure.**
