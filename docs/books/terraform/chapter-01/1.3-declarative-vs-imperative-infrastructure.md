# 1.3 — Declarative vs. Imperative Infrastructure

**Terraform SRE & Cloud Infrastructure Engineering Handbook**
**Chapter 1 — Infrastructure as Code and Terraform Fundamentals**

**Status:** Draft
**Workflow Stage:** Draft

---

## 1.3.1 Introduction

Infrastructure automation can generally be approached through two broad programming models:

```text
Imperative
```

and:

```text
Declarative
```

Understanding the difference is fundamental to understanding Terraform.

An **imperative** approach focuses primarily on the operations required to reach a result.

A **declarative** approach focuses primarily on describing the intended configuration.

At a high level:

```text
Imperative
    |
    v
"Perform these operations"
```

versus:

```text
Declarative
    |
    v
"Manage infrastructure toward this configuration"
```

Terraform primarily follows the declarative model.

However, this distinction should not be treated as absolute. Real infrastructure systems frequently combine declarative and imperative behavior, and engineers still need to understand the operations that a declarative tool intends to perform.

---

# 1.3.2 Imperative Infrastructure

Imperative infrastructure automation specifies a sequence of actions.

For example:

```text
1. Create VPC
2. Create subnet
3. Create security group
4. Create instance
5. Attach storage
6. Configure DNS
```

The engineer determines:

```text
WHAT operations must occur
+
WHEN they occur
+
IN WHAT ORDER
```

Conceptually:

```text
Current Infrastructure
        |
        v
Operation 1
        |
        v
Operation 2
        |
        v
Operation 3
        |
        v
Target Infrastructure
```

Shell scripts and general-purpose programs are commonly used this way.

---

# 1.3.3 Imperative Example

Consider creating an AWS VPC using the AWS CLI.

A simplified command might be:

```bash
aws ec2 create-vpc \
  --cidr-block 10.20.0.0/16
```

The instruction says:

> Create a VPC.

The command describes an operation.

If the same command is executed again without additional logic, another VPC may be created.

The script therefore may need logic such as:

```text
Does the VPC already exist?
        |
        +---- Yes ---> Use Existing
        |
        +---- No ----> Create VPC
```

As automation becomes more sophisticated, the script may need to manage:

* Resource discovery
* Existing resource identifiers
* Error handling
* Dependencies
* Retries
* Updates
* Deletion
* Partial failures
* Idempotency

This logic is the responsibility of the automation author unless provided by another framework or API.

---

# 1.3.4 Declarative Infrastructure

A declarative approach expresses the intended managed configuration.

For example:

```hcl
resource "aws_vpc" "production" {
  cidr_block = "10.20.0.0/16"
}
```

The configuration describes a managed VPC.

The engineer is not directly scripting:

```text
Call CreateVpc API
Store ID
Check Status
Determine Update API
```

Instead, Terraform evaluates configuration, prior state information, and information obtained from the provider to determine what actions are needed.

Conceptually:

```text
Configuration
     |
     v
Terraform
     |
     +---- Current / Prior Information
     |
     +---- Provider
     |
     v
Determine Proposed Actions
     |
     v
Plan
     |
     v
Apply
```

This is one of Terraform's core abstractions.

---

# 1.3.5 Desired State — A Terminology Caution

Terraform is frequently explained using the term **desired state**.

The term is useful, but it can also cause confusion.

Some systems continuously reconcile actual infrastructure toward a desired state.

Terraform normally operates when explicitly invoked or when an external platform invokes it.

Therefore:

```text
Terraform Configuration
        |
        v
Desired / Intended Managed Configuration
```

does not automatically imply:

```text
Continuous Reconciliation Loop
```

A more precise phrase throughout this handbook is:

> **intended Terraform-managed configuration**

Terraform attempts to determine the operations required to move managed infrastructure toward that configuration when Terraform runs.

---

# 1.3.6 Imperative vs. Declarative — Basic Comparison

| Characteristic      | Imperative                      | Declarative                                      |
| ------------------- | ------------------------------- | ------------------------------------------------ |
| Primary focus       | Operations                      | Intended configuration                           |
| Engineer specifies  | How to perform work             | What should be managed                           |
| Sequencing          | Often explicit                  | Often dependency-derived                         |
| State handling      | Often custom/tool-specific      | Terraform provides state mechanisms              |
| Change detection    | Often custom                    | Built into Terraform workflow                    |
| Idempotency         | Must be designed/tool-supported | Strongly supported by resource model             |
| Dependency handling | Often explicit                  | Frequently inferred                              |
| Review model        | Script/code review              | Configuration + plan review                      |
| Repeated execution  | Depends on implementation       | Intended to converge without unnecessary changes |
| Examples            | Shell/CLI/API programs          | Terraform and other declarative systems          |

These are general tendencies rather than universal rules.

# 1.3.7 The Important Difference: Operations vs. Configuration

Suppose the objective is:

```text
Production Server

Instance Type: m6i.large
Subnet: private-a
Encryption: enabled
```

An imperative workflow might say:

```text
1. Search for server
2. If absent, create server
3. Find subnet
4. Attach network
5. Enable encryption
6. Verify result
```

A declarative Terraform configuration might say:

```hcl
resource "aws_instance" "application" {
  instance_type = "m6i.large"
  subnet_id     = aws_subnet.private_a.id
}
```

The engineer describes managed resource configuration.

Terraform and the provider determine the required lifecycle operations.

---

# 1.3.8 Declarative Does Not Mean Terraform Knows Business Intent

This distinction is extremely important.

Suppose configuration contains:

```hcl
instance_type = "m6i.24xlarge"
```

Terraform can reason that the configuration requests that instance type.

Terraform generally cannot determine whether:

```text
m6i.24xlarge
```

is:

* Too expensive
* Too large
* Against company policy
* Architecturally inappropriate
* Unnecessary for the workload

Terraform knows the declared configuration.

It does not inherently know all organizational intent.

Therefore:

```text
Declarative
    ≠
Correct
```

Engineering review remains necessary.

---

# 1.3.9 Declarative Does Not Mean Safe

Consider:

```hcl
resource "aws_s3_bucket" "data" {
  bucket = "production-data-example"
}
```

An engineer later changes configuration or lifecycle in a way that causes Terraform to propose destructive behavior.

The configuration remains declarative.

The operation may still be dangerous.

Therefore:

```text
Declarative
    ≠
Safe
```

Production Terraform still requires:

```text
Plan
  |
  v
Review
  |
  v
Risk Assessment
  |
  v
Approval
  |
  v
Apply
  |
  v
Validation
```

---

# 1.3.10 Declarative Does Not Mean No Execution Order

A common misconception is:

> Declarative infrastructure has no execution order.

Terraform still needs to perform operations in a valid order.

For example:

```hcl
resource "aws_vpc" "production" {
  cidr_block = "10.20.0.0/16"
}

resource "aws_subnet" "application" {
  vpc_id     = aws_vpc.production.id
  cidr_block = "10.20.10.0/24"
}
```

The subnet depends on the VPC.

Terraform can derive:

```text
VPC
 |
 v
Subnet
```

The engineer did not manually write:

```text
Step 1
Create VPC

Step 2
Create Subnet
```

but execution sequencing still exists.

The distinction is that Terraform constructs much of the ordering from resource dependencies.

---

# 1.3.11 Dependency Graph

Terraform constructs a dependency graph to reason about relationships between resources.

Consider:

```text
VPC
 |
 +---- Subnet A
 |       |
 |       +---- Application
 |
 +---- Subnet B
         |
         +---- Database
```

Terraform can use these relationships when determining operation order.

Independent resources may also be processed concurrently when appropriate.

This is one reason declarative resource relationships are powerful.

The configuration describes relationships, and Terraform derives much of the execution graph.

---

# 1.3.12 Implicit Dependencies

Terraform commonly discovers dependencies through references.

Example:

```hcl
resource "aws_subnet" "application" {
  vpc_id = aws_vpc.production.id
}
```

Because the subnet references:

```text
aws_vpc.production.id
```

Terraform can infer that the subnet depends on the VPC.

This is an **implicit dependency**.

Conceptually:

```text
aws_vpc.production
        |
        v
aws_subnet.application
```

Implicit dependencies are generally preferable when the relationship can naturally be expressed through resource references because the configuration communicates the actual data relationship.

---

# 1.3.13 Explicit Dependencies

Sometimes a dependency exists that Terraform cannot infer from normal references.

Terraform provides mechanisms such as:

```hcl
depends_on = [
  aws_vpc.production
]
```

for explicitly declaring certain dependencies.

However, explicit dependencies should not be used simply to force arbitrary ordering when a proper resource relationship can be expressed naturally.

Unnecessary explicit dependencies can make the dependency graph more conservative and harder to understand.

---

# 1.3.14 Terraform Cannot Infer Every Dependency

Terraform understands configuration relationships.

It does not automatically understand every operational relationship.

For example:

```text
Database Schema Migration
        |
        v
Application Deployment
```

or:

```text
DNS Change
    |
    v
External Customer Migration
```

or:

```text
Firewall Change
      |
      v
Partner Connectivity Validation
```

These may be critical production dependencies even when Terraform's resource graph does not represent them.

Therefore:

> **Terraform's dependency graph is not a complete model of the production system.**

---

# 1.3.15 Idempotency

Declarative infrastructure is closely associated with idempotent behavior.

Conceptually:

```text
Desired:

One Managed VPC
```

After infrastructure reaches the intended configuration:

```text
terraform plan
```

should ideally produce:

```text
No changes.
```

Running the workflow again should not repeatedly create another equivalent resource.

This property makes repeatable automation significantly easier.

However, real Terraform plans may still show changes because of:

* Drift
* Provider behavior
* Computed values
* External controllers
* Unstable inputs
* Configuration changes
* Provider defects

Idempotency is an important design objective, not a reason to ignore unexpected plans.

---

# 1.3.16 Convergence

A useful related concept is **convergence**.

The infrastructure begins in some current condition:

```text
State A
```

Terraform configuration expresses:

```text
State B
```

Terraform determines proposed actions:

```text
State A
   |
   v
Plan
   |
   v
Apply
   |
   v
State B
```

After convergence, another plan should ideally contain no unexpected infrastructure changes.

Persistent non-convergence may indicate an ownership or configuration problem.

---

# 1.3.17 Current State Is More Complicated Than a State File

A common beginner explanation is:

```text
Terraform compares desired state
with terraform.tfstate.
```

That explanation is useful initially but incomplete for production engineering.

Terraform may interact with:

```text
Configuration
     +
Prior State
     +
Provider
     +
Remote APIs
```

to determine proposed actions.

Therefore Terraform state should not be treated as a perfect copy of reality.

The remote platform contains the actual infrastructure objects.

State helps Terraform map configuration addresses to managed remote objects and retain relevant information.

This distinction becomes critical in later chapters on state and drift.

---

# 1.3.18 Plan as the Operational Bridge

The Terraform plan is one of the most important consequences of the declarative model.

The engineer defines:

```text
Intended Configuration
```

Terraform determines:

```text
Proposed Operations
```

The plan bridges these concepts:

```text
Configuration
      |
      v
Terraform Evaluation
      |
      v
PLAN
      |
      +---- Create
      +---- Update
      +---- Replace
      +---- Destroy
      |
      v
Apply
```

Production engineers should therefore not review only Terraform code.

They must also review what Terraform proposes to do.

---

# 1.3.19 Code Review vs. Plan Review

Suppose an engineer changes:

```hcl
instance_type = "m6i.large"
```

to:

```hcl
instance_type = "m6i.xlarge"
```

Code review shows the intended configuration change.

Plan review reveals the operational consequence.

Depending on resource and provider behavior, the plan may indicate:

```text
Update in place
```

or:

```text
Replacement
```

These have very different production implications.

Therefore:

```text
Code Review
     +
Plan Review
     =
Stronger Infrastructure Review
```

Neither should automatically substitute for the other.

---

# 1.3.20 Resource Replacement

Declarative configuration can hide significant operational consequences behind a small code change.

Consider:

```text
One-Line Configuration Change
            |
            v
Terraform Plan
            |
            v
Resource Replacement
```

Replacement may mean:

```text
Create New
+
Destroy Old
```

or another provider-specific lifecycle sequence.

For stateless resources this may be manageable.

For stateful resources it may mean:

```text
Downtime
Data Migration
Data Loss Risk
Recovery Complexity
```

This is why production Terraform engineering focuses heavily on the plan rather than assuming a declarative change is harmless.

---

# 1.3.21 Imperative Automation Can Be Idempotent

It is incorrect to teach:

```text
Imperative = Not Idempotent
```

A well-designed script can implement:

```text
Discover
   |
   v
Compare
   |
   v
Change Only If Required
```

and become highly repeatable.

Likewise, declarative systems can exhibit unstable behavior when:

* Inputs constantly change
* Providers return inconsistent values
* External systems modify resources
* Ownership is ambiguous

The distinction concerns the programming model, not an absolute quality guarantee.

---

# 1.3.22 Declarative Systems Still Perform Imperative Operations

Terraform configuration is primarily declarative.

But cloud infrastructure ultimately changes through operations.

For example:

```text
Terraform Configuration
        |
        v
Provider
        |
        v
Cloud API
        |
        +---- Create
        +---- Read
        +---- Update
        +---- Delete
```

The declarative abstraction does not eliminate imperative operations.

It moves much of the operation-selection logic into Terraform and its providers.

This is a critical mental model:

> **Declarative configuration describes the target; execution still occurs through concrete operations.**

---

# 1.3.23 Provider Role

Terraform itself does not directly understand every AWS, Azure, Google Cloud, Kubernetes, or SaaS API.

Providers implement resource-specific interactions.

Conceptually:

```text
Terraform Configuration
        |
        v
Terraform Core
        |
        v
Provider
        |
        v
Remote API
```

The provider understands how a Terraform resource maps to remote platform behavior.

Therefore provider behavior is part of the operational model.

A declarative Terraform configuration does not isolate engineers completely from provider semantics.

---

# 1.3.24 Provider Semantics Matter

Suppose two resources contain conceptually similar configuration:

```text
Resource A
property = "new-value"
```

and:

```text
Resource B
property = "new-value"
```

The first provider operation might allow:

```text
Update In Place
```

while the second may require:

```text
Replacement
```

Declarative syntax alone does not tell engineers the full operational consequence.

The plan and provider documentation matter.

---

# 1.3.25 Hidden Operational Complexity

Declarative infrastructure simplifies how infrastructure is expressed.

It does not make infrastructure itself simple.

A line such as:

```hcl
engine_version = "..."
```

may ultimately trigger:

```text
API Validation
Maintenance Operation
Service Restart
Failover
Replacement
Downtime
```

depending on the managed service.

Production engineers must therefore understand:

```text
Terraform Semantics
        +
Provider Semantics
        +
Cloud Service Semantics
```

This three-layer model will recur throughout the handbook.

---

# 1.3.26 Declarative Infrastructure and Drift

Suppose configuration specifies:

```text
instance_type = m6i.large
```

but someone manually changes the remote instance to:

```text
m6i.xlarge
```

The systems now disagree:

```text
Terraform Configuration
m6i.large

Remote Infrastructure
m6i.xlarge
```

When Terraform evaluates the managed resource, it may propose reconciliation toward the configuration.

But the production question is:

> Which value is actually intended?

If the manual change was accidental:

```text
Restore Configuration
```

may be appropriate.

If the manual change was an approved emergency fix:

```text
Update Terraform Configuration
```

may be appropriate.

Declarative infrastructure does not eliminate the need to determine intent.

---

# 1.3.27 Declarative Infrastructure and Multiple Controllers

Consider:

```text
Terraform
    |
    +---- desired_capacity = 5
```

while an autoscaler manages:

```text
desired_capacity = 10
```

Both systems are behaving according to their own configuration.

The result may be:

```text
Terraform
   |
   v
5

Autoscaler
   |
   v
10

Terraform
   |
   v
5
```

This is a controller conflict.

Declarative systems require clear ownership boundaries.

A property should generally have one authoritative management mechanism unless coordination is deliberately designed.

---

# 1.3.28 Declarative Does Not Mean Self-Healing

Another common misconception is:

> If infrastructure is declarative, Terraform automatically repairs it.

Not necessarily.

If an engineer deletes a managed resource manually, Terraform will not automatically recreate it merely because configuration exists unless Terraform is subsequently executed through an appropriate workflow.

Therefore:

```text
Declarative Configuration
        ≠
Always-On Self-Healing
```

Self-healing requires an execution/reconciliation mechanism.

---

# 1.3.29 Terraform vs. Kubernetes Reconciliation

Kubernetes provides a useful conceptual contrast.

A Kubernetes controller commonly operates in a continuous reconciliation loop:

```text
Desired Configuration
        |
        v
Controller
        |
        v
Observe
        |
        v
Reconcile
        |
        +------+
        |      |
        +<-----+
```

Terraform typically follows:

```text
Configuration
      |
      v
terraform plan / apply
      |
      v
Infrastructure
```

and stops until another Terraform operation occurs.

Both approaches are declarative, but their runtime reconciliation models differ.

This distinction prevents a major Terraform misconception.

# 1.3.30 Declarative Infrastructure and Human Approval

Declarative automation works particularly well with controlled change workflows.

For example:

```text
Engineer
   |
   v
Modify Configuration
   |
   v
Pull Request
   |
   v
Terraform Plan
   |
   v
Peer Review
   |
   v
Approval
   |
   v
Terraform Apply
```

This combines automation with human judgment.

The objective is not:

```text
Remove Humans
```

but:

```text
Move Humans Toward
Architecture
Review
Risk Decisions
Exceptions
Recovery
```

# 1.3.31 Imperative Operations During Incidents

Even in a Terraform-managed environment, imperative commands may be appropriate during incidents.

Example:

```text
Production Outage
       |
       v
Emergency CLI Change
       |
       v
Service Restored
```

That may be faster and safer than modifying an unfamiliar automation pipeline during an emergency.

But the lifecycle should continue:

```text
Emergency Operation
        |
        v
Restore Service
        |
        v
Record Change
        |
        v
Determine Intended End State
        |
        v
Reconcile Terraform
```

Declarative infrastructure and imperative emergency operations can coexist when governance is clear.

---

# 1.3.32 Greenfield Example

For new infrastructure:

```text
Terraform Configuration
        |
        v
Plan
        |
        v
Review
        |
        v
Apply
        |
        v
Infrastructure Created
```

The declarative model is straightforward because Terraform manages the lifecycle from the beginning.

This is a **greenfield** deployment.

---

# 1.3.33 Brownfield Example

Existing infrastructure creates a more complex problem.

```text
Existing Production VPC
        |
        v
Write Matching Terraform Configuration
        |
        v
Import / Adopt
        |
        v
Plan
        |
        v
Compare Intended vs. Existing
```

The goal should normally be:

```text
Existing Resource
        |
        v
Managed Declaratively
```

without unexpected recreation.

Declarative adoption therefore requires careful discovery of the existing configuration.

---

# 1.3.34 Declarative Brownfield Risk

Suppose an existing production database uses:

```text
Storage = 2 TB
Encryption = Existing Key
Deletion Protection = Enabled
```

but Terraform configuration accidentally describes:

```text
Storage = 500 GB
Encryption = Different Key
Deletion Protection = Disabled
```

Terraform is doing exactly what declarative systems are designed to do:

```text
Current
   |
   v
Move Toward Declared Configuration
```

The problem is that the declared configuration is wrong.

Therefore:

> **In brownfield adoption, the quality of the declared configuration is itself a production safety boundary.**

# 1.3.35 Declarative Infrastructure and Policy

Machine-readable configuration enables automated policy evaluation.

For example:

```text
Terraform Configuration
        |
        v
Policy Check
        |
        +---- Encryption?
        +---- Approved Region?
        +---- Required Tags?
        +---- Public Exposure?
        |
        v
Pass / Fail
```

This is one of the operational advantages of declarative infrastructure.

However, policy systems still depend on correctly defined organizational requirements.

# 1.3.36 Declarative Infrastructure and Testing

Terraform configuration can participate in multiple validation layers.

For example:

```text
Formatting
    |
    v
Validation
    |
    v
Static Analysis
    |
    v
Security Analysis
    |
    v
Policy Evaluation
    |
    v
Plan
    |
    v
Plan Review
    |
    v
Apply
    |
    v
Post-Deployment Validation
```

Declarative configuration makes infrastructure easier to subject to repeatable automated checks.

# 1.3.37 Imperative vs. Declarative Failure Models

Imperative failure:

```text
Step 1    SUCCESS
Step 2    SUCCESS
Step 3    FAILED
Step 4    NOT RUN
```

The operator or program must determine how to continue or recover.

Declarative Terraform failure:

```text
Plan
 |
 v
Apply
 |
 +---- Resource A SUCCESS
 +---- Resource B SUCCESS
 +---- Resource C FAILED
```

Terraform records relevant state as operations proceed, but the environment may still be partially changed.

The next action may involve:

```text
Investigate
   |
   v
Correct Root Cause
   |
   v
Plan Again
   |
   v
Continue / Recover
```

Declarative does not mean transactional infrastructure deployment.

---

# 1.3.38 Terraform Is Not a Database Transaction

A dangerous assumption is:

```text
terraform apply
      |
      v
Everything Succeeds
OR
Everything Rolls Back
```

Terraform generally should not be treated as providing database-style atomic transaction semantics across infrastructure resources.

An apply may partially succeed.

For example:

```text
VPC          CREATED
Subnet       CREATED
Security     CREATED
Database     FAILED
```

The environment may remain partially provisioned.

Production runbooks must account for partial execution.

---

# 1.3.39 Rollback Is Not Automatically Simple

Another misconception is:

```text
Git Revert
    |
    v
terraform apply
    |
    v
Infrastructure Restored Exactly
```

Reverting configuration can be useful, but infrastructure rollback may be complicated by:

* Destructive changes
* Data migration
* Provider behavior
* Irreversible operations
* External dependencies
* Replacement
* Changed remote state

Therefore production Terraform requires **recovery planning**, not just source-code rollback.

---

# 1.3.40 Declarative Infrastructure and Observability

A declarative configuration tells engineers what should be managed.

It does not tell them whether the resulting service is healthy.

For example:

```text
Terraform Apply
      |
      v
Database Exists
```

does not necessarily mean:

```text
Application Can Connect
Queries Perform Correctly
Replication Is Healthy
Backups Work
SLO Is Met
```

Infrastructure deployment must therefore be followed by operational validation.

---

# 1.3.41 Configuration Correctness vs. Service Correctness

This distinction is fundamental:

```text
Terraform Correct
      ≠
Service Healthy
```

A Terraform apply may complete successfully while:

* Application traffic fails
* DNS propagation is incomplete
* Firewall rules block dependencies
* Database performance degrades
* Certificates are wrong
* Monitoring is missing

Terraform validates infrastructure management operations.

SRE validates service behavior.

---

# 1.3.43 Production Anti-Patterns

```text

     |
     v
Automatically Safe
```

False.

```text
    |
    v

```

without understanding the proposed actions.

```text

        |
        v
Plan Replaces Database
```

The plan matters.

---

## Anti-Pattern 4 — Terraform Is Always-On Reconciliation

```text
Resource Drift
      |
      v
Terraform Automatically Repairs
```

Not unless an appropriate Terraform execution workflow runs.

---

## Anti-Pattern 5 — Declarative Means No Dependencies

Terraform still has an execution graph and operational dependencies.

---

## Anti-Pattern 6 — Terraform Knows Business Intent

```text
Configuration Accepted
        |
        v
Architecture Must Be Correct
```

False.

---

## Anti-Pattern 7 — Multiple Controllers Own the Same Property

```text
Terraform
    |
    v
Property
    ^
    |
Autoscaler
```

without intentional coordination.

---

## Anti-Pattern 8 — Apply Is Atomic

```text
Everything Changes
OR
Nothing Changes
```

Infrastructure applies can partially succeed.

---

## Anti-Pattern 9 — Git Revert Equals Infrastructure Rollback

Configuration rollback and operational recovery are related but not identical.

---

## Anti-Pattern 10 — Terraform Success Equals Service Success

```text
Apply Complete
     |
     v
Production Healthy
```

This must be validated, not assumed.

# 1.3.44 SRE Perspective

From an SRE perspective, declarative infrastructure provides a valuable control mechanism.

Instead of repeatedly asking:

```text
Which commands should we execute?
```

teams can increasingly ask:

```text
What configuration should production have?
```

Then:

```text
What changes will Terraform make
to reach that configuration?
```

Then:

```text
What operational risk do those
changes create?
```

Finally:

```text
Did the service remain healthy
after the change?
```

This progression is central to production Terraform engineering.

# 1.3.45 Production Engineering Principles

### Principle 1

> **Imperative automation describes operations; declarative infrastructure primarily describes intended managed configuration.**

### Principle 2

> **Declarative does not mean safe, correct, self-healing, or continuously reconciled.**

### Principle 3

> **Terraform's plan is the operational bridge between declarative configuration and real infrastructure changes.**

### Principle 4

> **Review both the configuration and the proposed operations.**

### Principle 5

> **Terraform can infer infrastructure dependencies, but it cannot infer every application or business dependency.**

### Principle 6

> **Declarative systems still execute concrete create, read, update, and delete operations through providers and APIs.**

### Principle 7

> **Idempotency and convergence are engineering objectives; unexplained repeated changes should be investigated.**

### Principle 8

> **A property should have a clearly defined management owner to prevent competing controllers.**

### Principle 9

> **Terraform apply should not be treated as an atomic database transaction.**

### Principle 10

> **Terraform success demonstrates neither complete infrastructure correctness nor application health; production validation remains necessary.**

# 1.3.46 Key Takeaways

Imperative and declarative infrastructure represent different approaches to automation.

Imperative infrastructure focuses primarily on:

```text
HOW
```

while declarative infrastructure focuses primarily on:

```text
WHAT
```

Terraform primarily uses a declarative model:

```text
Configuration
      |
      v
Terraform Evaluation
      |
      v
Plan
      |
      v
Provider Operations
      |
      v
Remote Infrastructure
```

The declarative model provides important advantages:

* Repeatability
* Resource relationships
* Dependency inference
* Change planning
* Idempotent workflows
* Reviewability
* Policy integration
* Automation
* Brownfield lifecycle management

But it does not eliminate operational engineering.

Production engineers must still understand:

```text
Configuration
+
Terraform State
+
Terraform Plan
+
Provider Behavior
+
Cloud Service Behavior
+
Dependencies
+
Failure Modes
+
Recovery
+
Service Health
```

The central production principle is:

> **Declare the intended infrastructure, inspect how Terraform intends to achieve it, control the execution, and verify the resulting service.**
