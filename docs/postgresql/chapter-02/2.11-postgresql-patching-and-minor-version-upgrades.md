# 2.11 — PostgreSQL Patching and Minor-Version Upgrades

**Status:** Production Ready / Complete

PostgreSQL minor releases are maintenance releases within the same major version. They contain bug fixes, security fixes, and corrections for important defects, including in some cases data-corruption risks. PostgreSQL recommends running the current minor release for a supported major version.

For PostgreSQL 10 and later, the major version is the first number and the minor version is the second number. For example, upgrading from PostgreSQL 18.3 to 18.4 is a minor-version upgrade; moving from 17.x to 18.x is a major-version upgrade and requires a different migration process.

## 2.11.1 Minor versus major upgrade architecture

```text
PostgreSQL 18.3 → 18.4
        |
        +-- Minor release
        +-- Same data-directory format
        +-- No dump/restore normally required
        +-- No pg_upgrade required
        +-- Stop server → replace/update binaries → start server

PostgreSQL 17.x → 18.x
        |
        +-- Major upgrade
        +-- Data format/system catalog changes possible
        +-- pg_upgrade, dump/restore, or replication migration required
```

PostgreSQL guarantees storage compatibility between minor releases of the same major version. The normal minor-upgrade procedure is therefore to stop the server, install the updated binaries, and restart using the existing data directory.

This simplicity must not be confused with zero operational risk. Release notes can contain required post-update actions, extension considerations, replication concerns, or fixes relevant to a specific workload.

## 2.11.2 PostgreSQL patch-management policy

A production organization should maintain an explicit PostgreSQL patch policy covering:

```text
Supported major versions
Current approved minor release
Security-release handling
Patch assessment SLA
Non-production validation
Production maintenance windows
HA rollout order
Rollback strategy
Backup/recovery prerequisites
Extension compatibility
Post-patch verification
Evidence and audit retention
```

PostgreSQL major versions are supported by the community for approximately five years. Once a major version reaches end of life, it no longer receives community bug or security fixes. Minor-version patching therefore does not replace lifecycle planning for major-version upgrades.

## 2.11.3 Always read cumulative release notes

Before applying a minor update, review the target release notes and every skipped minor release.

Example:

```text
Current: PostgreSQL 18.1
Target:  PostgreSQL 18.4

Review:
18.2 release notes
18.3 release notes
18.4 release notes
```

PostgreSQL minor releases are cumulative, so it is not necessary to install every intermediate binary release. However, skipped releases can contain manual post-update instructions that remain relevant.

The operational rule is:

> You may skip intermediate minor binaries, but you must not skip understanding their release notes and required remediation steps.

## 2.11.4 Pre-patch inventory

Before patching, capture the actual production state.

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
SHOW data_directory;
SHOW config_file;
```

Inventory installed extensions:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Capture replication state where applicable:

```sql
SELECT application_name,
       client_addr,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn
FROM pg_stat_replication;
```

Capture cluster/database size and critical configuration evidence as appropriate to the environment.

## 2.11.5 Pre-patch readiness gate

Do not begin production patching until the following are understood:

- current PostgreSQL server and client package versions
- target minor release
- target release notes and skipped-release notes
- operating-system/package repository state
- extension and shared-library compatibility
- replication/HA topology
- maintenance-window impact
- backup and recovery state
- storage headroom
- monitoring health
- application connection/retry behavior
- rollback path
- required post-update SQL or reindex actions

A recent backup is valuable, but the stronger production requirement is a **known recoverable state** supported by tested restore procedures.

## 2.11.6 Backup and recovery prerequisite

Before patching a critical cluster, confirm that the backup/recovery architecture is healthy.

Depending on the platform this can include:

```text
Successful recent base backup or platform snapshot
Healthy WAL archival
Known restore procedure
PITR capability where required
Validated backup retention
Recovery credentials and access
Available recovery infrastructure
```

A patch window is not the time to discover that backups have silently failed for several days.

## 2.11.7 Package-based minor upgrade

For packaged PostgreSQL installations, use the supported operating-system/vendor repository and package manager. The exact package names and commands vary by Linux distribution and PostgreSQL repository.

Conceptual workflow:

```text
Confirm repository
      ↓
Resolve target package version
      ↓
Stop/drain database safely
      ↓
Update PostgreSQL packages
      ↓
Verify installed binaries
      ↓
Start PostgreSQL
      ↓
Validate server version
      ↓
Execute required release-note actions
      ↓
Application validation
```

Do not blindly execute a full operating-system update during a database patch unless the change scope intentionally includes all resulting package updates.

## 2.11.8 Source-installed minor upgrade

For source-built PostgreSQL, build and install the target minor release using compatible build options and the organization's controlled software-supply process.

The database server must be stopped before replacing the binaries used by that instance.

Do not run a new PostgreSQL server binary against the production data directory until the intended binary installation, library dependencies, extensions, and configuration have been validated.

## 2.11.9 Safe standalone patch workflow

For a standalone PostgreSQL instance:

```text
Change Approved
     ↓
Release Notes Reviewed
     ↓
Backup / Recovery Verified
     ↓
Application Writes Drained
     ↓
Database Stopped Cleanly
     ↓
PostgreSQL Binaries Updated
     ↓
Binary Version Verified
     ↓
Database Started
     ↓
Server Logs Reviewed
     ↓
SQL Validation
     ↓
Required Post-Update Actions
     ↓
Application Smoke Test
     ↓
Monitoring Observation
     ↓
Close Change
```

Because a standalone server has no database-level failover target, the maintenance window must account for full database unavailability during the stop/update/start interval.

## 2.11.10 HA/streaming-replication patch strategy

A high-availability topology can reduce application downtime, but the rollout must respect the HA technology, failover manager, synchronous-replication policy, load balancer, and organizational runbook.

A common rolling pattern is:

```text
Primary + Standby A + Standby B

1. Validate replication health
2. Patch one standby
3. Restart and validate it
4. Confirm it catches up
5. Repeat for remaining standby
6. Perform controlled switchover/failover if appropriate
7. Patch former primary
8. Rejoin and validate
9. Confirm final topology and replication health
```

Do not treat this sequence as universal. Patroni, Pacemaker, repmgr, Kubernetes operators, cloud services, and custom orchestration can impose different safe procedures.

PostgreSQL minor releases maintain storage compatibility within a major version, which supports mixed minor versions temporarily during a controlled rolling update, but the desired steady state is the same approved minor release across the topology. Release notes must be reviewed for version-specific replication concerns.

## 2.11.11 Extension and shared-library compatibility

Extensions can introduce patch risk beyond PostgreSQL core.

Inventory:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Also identify externally installed shared libraries, preload libraries, procedural languages, backup agents, monitoring agents, and authentication modules.

Review:

```text
shared_preload_libraries
session_preload_libraries
local_preload_libraries
```

Do not assume that updating the PostgreSQL package automatically updates every extension package or shared object required by the cluster.

## 2.11.12 Release-note remediation

Minor releases occasionally require additional action beyond binary replacement.

Examples of possible release-note actions include:

```text
REINDEX of affected indexes
Catalog correction SQL
Extension package update
Configuration change
Replication-specific remediation
Operating-system/library update
```

These actions are version-specific. Never invent them from a generic patch runbook; derive them from the release notes for the releases crossed by the upgrade.

As a concrete PostgreSQL 18 example, PostgreSQL 18.3 included a catalog-correction instruction for users upgrading from certain earlier 18.x releases. This demonstrates why cumulative release-note review is mandatory even though the underlying data directory is minor-version compatible.

## 2.11.13 Pre-patch SQL evidence

Capture evidence appropriate to the environment:

```sql
SELECT now(), version();

SELECT datname,
       numbackends,
       xact_commit,
       xact_rollback,
       blks_read,
       blks_hit
FROM pg_stat_database
ORDER BY datname;
```

For replication:

```sql
SELECT application_name,
       state,
       sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS byte_lag
FROM pg_stat_replication;
```

Capture long-running transactions and active workload before draining traffic so that shutdown behavior is predictable.

## 2.11.14 Clean shutdown

Use the service manager or approved HA orchestrator rather than killing PostgreSQL processes.

Examples may include:

```bash
systemctl stop postgresql
```

or a version/cluster-specific unit, or:

```bash
pg_ctl -D "$PGDATA" stop -m fast
```

The exact method must match the platform.

Never use `kill -9` as the normal patch shutdown mechanism. An immediate process kill forces crash recovery at the next startup and adds unnecessary risk to a planned maintenance event.

## 2.11.15 Binary verification

After package installation but before declaring success, confirm which binary is actually installed and which server is actually running.

```bash
postgres --version
pg_config --version
psql --version
```

After startup:

```sql
SELECT version();
SHOW server_version;
```

Do not rely only on the `psql` client version. Client and server binaries can differ.

## 2.11.16 Post-patch startup validation

Immediately after startup validate:

```sql
SELECT now(), version();
SHOW data_directory;
SHOW config_file;
```

Check server logs for:

```text
recovery messages
FATAL/PANIC errors
missing shared libraries
invalid parameters
authentication failures
WAL/archive errors
replication errors
extension load failures
```

Confirm readiness:

```bash
pg_isready
```

`pg_isready` proves that the server is accepting or responding to connection attempts; it does not prove that the application workload is healthy. Continue with SQL and application validation.

## 2.11.17 Post-patch database validation

Validate at minimum:

```text
Server version
Database connectivity
Expected databases
Critical roles
Extensions
Application schema access
Read/write operations
Replication
WAL archival
Backup integration
Monitoring
Scheduled jobs
Connection poolers
```

Representative checks:

```sql
SELECT datname FROM pg_database ORDER BY datname;

SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Use application-specific smoke queries for critical business paths rather than relying only on `SELECT 1`.

## 2.11.18 Replication validation

On the primary:

```sql
SELECT application_name,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn
FROM pg_stat_replication;
```

On a standby:

```sql
SELECT pg_is_in_recovery();
SELECT pg_last_wal_receive_lsn();
SELECT pg_last_wal_replay_lsn();
```

Verify that replication resumes and lag returns to the expected operational range after each node is patched.

## 2.11.19 Monitoring and alerting during patching

Observe the same production signals used during normal operation, especially:

```text
Database availability
Connection errors
CPU
Memory
Disk latency
Filesystem capacity
WAL generation
WAL archival failures
Replication lag
Checkpoint behavior
Lock waits
Transaction latency
Query latency
Application error rate
Connection-pool saturation
```

Do not close the patch change immediately after PostgreSQL starts. Maintain an observation period appropriate to workload criticality and traffic patterns.

## 2.11.20 Rollback strategy

Minor-version rollback must be designed before patching.

Because PostgreSQL minor releases share the same storage format within a major version, binary rollback can sometimes appear straightforward. However, do not assume that downgrading binaries is always operationally safe after the new minor version has run.

Release notes may describe fixes, catalog changes, extension changes, or required post-update actions that affect rollback decisions.

A production rollback plan should specify:

```text
Trigger criteria
Old package/binary availability
Configuration compatibility
Extension compatibility
HA topology state
Data/recovery implications
Release-note constraints
Validation after rollback
```

If rollback safety is uncertain, prefer a tested recovery or failover strategy rather than improvising a binary downgrade.

## 2.11.21 Failure scenarios

### FS-2.11-01 — PostgreSQL does not start after patch

Protect the data directory. Review PostgreSQL and service-manager logs, binary/library paths, configuration compatibility, shared libraries, extensions, permissions, and package state. Do not initialize a new cluster over the existing PGDATA.

### FS-2.11-02 — Wrong PostgreSQL binary is started

Compare `SELECT version()`, process executable paths, service unit definitions, PATH, package inventory, and PGDATA. Correct service ownership of the intended binary before admitting traffic.

### FS-2.11-03 — Extension library missing

Keep the node out of production service. Install the compatible extension package/shared object for the target PostgreSQL build, validate preload configuration, restart if required, and verify extension functionality.

### FS-2.11-04 — Replication does not resume

Inspect primary and standby logs, WAL receiver/sender state, slots, authentication, TLS, timeline state, archive availability, and version-specific release notes. Do not repeatedly rebuild the standby until the failure mode is understood.

### FS-2.11-05 — Application errors increase after patch

Correlate errors with database logs, driver behavior, authentication, connection pools, query plans, extension behavior, and release-note changes. Use the predefined rollback or failover decision criteria.

### FS-2.11-06 — Required release-note SQL was missed

Stop change closure. Assess whether the omitted action can be executed safely online, validate all databases/templates it applies to, execute under change control, and repeat post-patch validation.

### FS-2.11-07 — Patch repository installs unexpected major version

Stop immediately and keep the service offline until package state is understood. Never point a different major-version server at an existing cluster as a patching shortcut. Restore the approved packages or execute a proper major-upgrade plan.

## 2.11.22 SRE/DBRE patch automation

A mature automation pipeline can implement:

```text
Discover current version
        ↓
Determine approved target minor
        ↓
Fetch release-note policy
        ↓
Validate backup / HA health
        ↓
Drain node
        ↓
Stop PostgreSQL safely
        ↓
Install pinned packages
        ↓
Verify binary version
        ↓
Start PostgreSQL
        ↓
Run SQL health checks
        ↓
Run release-specific remediation
        ↓
Validate replication
        ↓
Run application smoke tests
        ↓
Observe telemetry
        ↓
Return node to service
```

Automation must pin the intended major/minor package family and fail closed if repository resolution produces an unexpected major version.

## 2.11.24 Production case study — skipped minor releases

A cluster is upgraded directly from PostgreSQL 18.1 to a later 18.x minor release. The binary update succeeds and PostgreSQL starts normally, so the team initially declares success. Later they discover that an intermediate release contained a required catalog remediation for installations crossing that version boundary.

The root cause is not that PostgreSQL disallowed skipping minor binaries; minor releases are cumulative. The failure is that the team skipped the **operational instructions** in the intervening release notes.

Corrective actions:

```text
Make release-note review mandatory
Record every skipped release
Extract manual actions into the change plan
Automate pre/post SQL checks where safe
Require evidence before closing the change
```

## 2.11.25 Production case study — rolling HA patch

A three-node streaming-replication cluster must receive a security minor update with minimal application interruption. The team validates replication, patches one standby, waits for it to catch up, patches the second standby, performs a controlled role transition according to the HA runbook, patches the former primary, then validates replication and application traffic across the final topology.

The important reliability principle is not merely "patch standbys first". It is to maintain a known healthy failover target throughout the maintenance operation and validate each node before progressing.

## 2.11.26 Golden production principles

1. Keep supported PostgreSQL major versions on their current approved minor release.
2. Treat every minor release as a controlled production change even though no data migration is normally required.
3. Read all release notes crossed by the update.
4. Verify recoverability before patching.
5. Patch and validate one HA node at a time when the architecture permits.
6. Never confuse client binary version with server version.
7. Validate extensions and shared libraries explicitly.
8. Execute version-specific post-update actions before declaring success.
9. Observe application and database telemetry after startup.
10. Do not improvise rollback after the patch has begun.
