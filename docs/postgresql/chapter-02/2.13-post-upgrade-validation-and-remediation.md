# 2.13 — Post-Upgrade Validation and Remediation

**Status:** Production Ready / Complete

A PostgreSQL major-version upgrade is not complete when the new server starts. The SRE/DBRE completion point is reached only after the upgraded cluster, applications, extensions, statistics, indexes, replication, backup/recovery systems, monitoring, security controls, and workload behavior have been validated and any required remediation has been completed.

This section defines the production post-upgrade validation and remediation process for PostgreSQL 18.

## 2.13.1 Post-upgrade operating model

```text
Upgrade completes
      ↓
Server startup validation
      ↓
Cluster identity + configuration validation
      ↓
Database / object validation
      ↓
Extension + library validation
      ↓
Statistics / planner validation
      ↓
Index / collation remediation
      ↓
Replication / HA validation
      ↓
Backup / PITR validation
      ↓
Application smoke + performance tests
      ↓
Monitoring observation period
      ↓
Production acceptance
```

Never declare an upgrade successful based only on `pg_isready` or the ability to open a `psql` session.

## 2.13.2 Validate server identity

Confirm the server version and cluster identity immediately after startup:

```sql
SELECT version();
SHOW server_version;
SHOW server_version_num;
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
```

Also verify the expected service, port, host, and cluster are receiving application connections. This prevents a false-positive validation against the wrong PostgreSQL instance.

## 2.13.3 Validate databases and cluster objects

Inventory databases:

```sql
SELECT datname,
       pg_get_userbyid(datdba) AS owner,
       datallowconn,
       datconnlimit
FROM pg_database
ORDER BY datname;
```

Validate expected roles, schemas, tables, sequences, views, materialized views, functions, procedures, and other application-critical objects.

For large estates, compare a pre-upgrade inventory with the destination rather than relying on manual spot checks.

## 2.13.4 Validate configuration

Major releases can introduce new parameters, remove parameters, change defaults, or change parameter behavior. Do not copy an old `postgresql.conf` over a new cluster blindly.

Validate runtime state:

```sql
SELECT name,
       setting,
       unit,
       source,
       sourcefile,
       sourceline,
       context,
       pending_restart
FROM pg_settings
ORDER BY name;
```

Review especially:

```text
connections
memory
WAL
checkpoints
replication
logging
autovacuum
planner settings
timeouts
SSL / authentication
shared_preload_libraries
```

Check pending restart parameters:

```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE pending_restart;
```

## 2.13.5 Validate authentication and security

Confirm that `pg_hba.conf`, `pg_ident.conf`, TLS configuration, certificates, password authentication, external identity integrations, and firewall/security-group rules still behave as intended.

Test both positive and negative access paths:

```text
Expected application connection → succeeds
Expected DBA connection         → succeeds
Unauthorized source             → denied
Unauthorized role               → denied
Non-TLS path where prohibited   → denied
```

Do not treat a successful superuser connection as proof that application authentication is correct.

## 2.13.6 Validate extensions

Extensions are one of the highest-risk areas of major upgrades.

Inventory installed extensions:

```sql
SELECT extname, extversion
FROM pg_extension
ORDER BY extname;
```

Compare installed and available versions:

```sql
SELECT name,
       default_version,
       installed_version
FROM pg_available_extensions
WHERE installed_version IS NOT NULL
ORDER BY name;
```

For `pg_upgrade`, required extension shared libraries for the new PostgreSQL binary must be installed before the upgrade. `pg_upgrade` can also generate follow-up scripts when extension updates are required.

Where the extension provides a supported upgrade path:

```sql
ALTER EXTENSION extension_name UPDATE;
```

Do not automatically update every extension without reviewing vendor/project compatibility notes and testing application behavior.

External extensions such as PostGIS or vendor modules require their own compatibility validation in addition to PostgreSQL core validation.

## 2.13.7 Validate shared preload libraries

Review:

```sql
SHOW shared_preload_libraries;
```

Confirm that every required module has a PostgreSQL 18-compatible binary and that PostgreSQL logs contain no library-loading failures.

A missing preload library can prevent startup or silently remove important monitoring/security functionality if configuration was changed to bypass it.

## 2.13.8 Statistics after pg_upgrade

PostgreSQL 18 `pg_upgrade` can transfer most optimizer statistics unless `--no-statistics` is used. This significantly improves post-upgrade plan stability compared with older releases, but not every category of statistics is transferred.

PostgreSQL documentation specifically notes that extended statistics created with `CREATE STATISTICS`, extension-provided custom statistics, and cumulative statistics are not all preserved.

Follow the scripts/instructions generated by `pg_upgrade`.

A recommended staged process from PostgreSQL 18 documentation is:

```bash
vacuumdb --all --analyze-in-stages --missing-stats-only
vacuumdb --all --analyze-only
```

The first command rapidly generates minimum planner statistics for relations missing them; the second refreshes broader statistics and cumulative state.

Do not assume that statistics transfer eliminates all post-upgrade ANALYZE requirements.

## 2.13.9 Validate query plans

Compare representative critical queries with the pre-upgrade baseline.

Use:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
```

where executing the query safely is appropriate.

Watch for:

```text
unexpected sequential scans
changed join order
cardinality estimation errors
large execution-time regressions
increased temporary I/O
increased buffer reads
new lock behavior
changed parallel plans
```

A plan change is not automatically a regression; PostgreSQL 18 includes planner improvements. Evaluate actual workload latency, resource consumption, and correctness.

## 2.13.10 PostgreSQL 18 migration-specific remediation

Every major upgrade must review the release notes for the destination and every skipped major release.

For PostgreSQL 18 specifically, migration notes include changes that can require operational remediation.

One important example involves full-text search and `pg_trgm`. PostgreSQL 18 changed full-text search to use the cluster's default collation provider when reading configuration files and dictionaries rather than always using libc. PostgreSQL recommends reindexing indexes related to full-text search and `pg_trgm` after `pg_upgrade` when the new behavior can differ for clusters using non-libc providers such as ICU or builtin.

Do not blindly reindex every production index. Identify affected objects, estimate storage/I/O/time, choose an appropriate reindex strategy, and monitor replication and disk impact.

## 2.13.11 Validate indexes

Check application-critical indexes and any rebuild scripts generated by `pg_upgrade`.

PostgreSQL warns that tables referenced by required rebuild scripts generally should not be accessed until those rebuild operations complete because results or performance can be incorrect.

Operational workflow:

```text
Review pg_upgrade output
       ↓
Identify rebuild scripts
       ↓
Identify affected relations
       ↓
Prevent unsafe application access
       ↓
Execute required rebuilds
       ↓
Validate indexes
       ↓
Return workload to service
```

For large indexes, plan disk headroom and replication WAL volume before using concurrent rebuild methods.

## 2.13.12 Validate sequences and identity behavior

Confirm application-critical sequences and identity columns after migration, especially when logical replication was used for the major upgrade.

Logical replication does not make sequence state a generic transparent cutover problem. Ensure destination sequence values are synchronized before writes are redirected.

Validate high-risk sequences against table values and application allocation behavior.

## 2.13.13 Validate replication and HA

For physical replication, verify all standbys are attached to the upgraded primary or have been rebuilt/resynchronized according to the chosen upgrade method.

Example checks:

```sql
SELECT application_name,
       client_addr,
       state,
       sync_state,
       sent_lsn,
       write_lsn,
       flush_lsn,
       replay_lsn
FROM pg_stat_replication;
```

On a standby:

```sql
SELECT pg_is_in_recovery();
SELECT pg_last_wal_receive_lsn();
SELECT pg_last_wal_replay_lsn();
```

Validate:

```text
replication connectivity
WAL receive/replay
replication lag
synchronous replication state
replication slots
archive behavior
failover tooling
VIP/DNS/proxy routing
read-only application routing
```

A production upgrade is not complete while HA protection is degraded unless that degraded state is explicitly accepted and time-bounded.

## 2.13.14 Validate logical replication

If logical replication was part of the upgrade strategy, verify subscriptions, publications, table synchronization, replication origin state, sequence handling, and cutover completeness.

Inspect subscriptions and subscription statistics appropriate to the deployed topology.

Do not remove the old publisher until the rollback decision point has passed and the new environment is independently recoverable.

## 2.13.15 Validate WAL and archiving

Check:

```sql
SHOW wal_level;
SHOW archive_mode;
SHOW archive_command;
```

If archive-based recovery is used, prove that new PostgreSQL 18 WAL is reaching the archive destination.

Do not infer archive health solely from the absence of PostgreSQL errors. Validate the destination and restore workflow.

## 2.13.16 Establish a new backup baseline

After a major upgrade, create a new backup baseline using the organization's approved PostgreSQL 18-compatible backup system.

Validate:

```text
full/base backup succeeds
WAL archival succeeds
backup catalog is correct
encryption works
retention policy applies
restore tooling supports PostgreSQL 18
restore test succeeds
PITR procedure is updated
```

Do not depend indefinitely on pre-upgrade backups as the primary recovery strategy for the upgraded environment.

## 2.13.17 Validate checksums

PostgreSQL 18 enables checksums by default for newly initialized clusters, but `pg_upgrade` requires the old and new clusters to have compatible checksum settings. Therefore, verify actual runtime state rather than assuming the PostgreSQL 18 default:

```sql
SHOW data_checksums;
```

Record the result in the upgrade evidence.

## 2.13.18 Validate logging and observability

Confirm that PostgreSQL logs are reaching the intended destination and that monitoring systems recognize the upgraded instance.

Validate dashboards and alerts for:

```text
availability
connections
CPU
memory
storage
I/O latency
WAL generation
checkpoint behavior
replication lag
locks/deadlocks
long-running transactions
autovacuum
query latency
errors
backup failures
archive failures
```

Check monitoring extensions and agents for PostgreSQL 18 compatibility.

## 2.13.19 Validate application connectivity

Application smoke testing should include more than SELECT 1.

Test representative paths:

```text
connect/authenticate
read
insert
update
delete/rollback where safe
transaction commit
prepared statements
connection pooling
stored functions/procedures
application migrations
background workers/jobs
reporting queries
```

Validate client drivers and ORMs against PostgreSQL 18 behavior.

## 2.13.20 Validate performance against baseline

Compare post-upgrade telemetry with a known pre-upgrade baseline:

```text
P50 / P95 / P99 query latency
transactions per second
CPU utilization
read/write IOPS
I/O latency
cache hit behavior
WAL generation rate
checkpoint frequency/duration
temporary-file usage
connection count
lock waits
replication lag
autovacuum duration
```

Do not immediately tune every changed metric. First distinguish expected PostgreSQL 18 behavior from genuine regression.

## 2.13.21 Validate scheduled jobs and external integrations

Confirm that operational dependencies still work:

```text
backup jobs
ETL jobs
cron/systemd jobs
logical replication
FDWs
monitoring exporters
connection poolers
secrets rotation
certificate renewal
maintenance automation
schema migration tooling
reporting platforms
```

A database can be healthy while its surrounding operational ecosystem is broken.

## 2.13.22 Validate foreign data wrappers

For FDW-based integrations, confirm that required extension libraries exist and that remote connections, authentication, mappings, and representative queries succeed.

Review extension/vendor compatibility when the FDW is external to PostgreSQL core.

## 2.13.23 Validate collation state

Major operating-system or library changes can alter collation behavior independently of PostgreSQL itself.

Inspect database and collation versions where relevant and investigate mismatch warnings. Reindex affected indexes when required by PostgreSQL documentation and the selected collation provider.

Treat collation remediation as a correctness issue, not merely a warning-cleanup task.

## 2.13.24 Validate autovacuum and transaction age

After upgrade, ensure autovacuum is active and that transaction-ID/multixact age remains healthy.

Example inventory:

```sql
SELECT datname,
       age(datfrozenxid) AS xid_age
FROM pg_database
ORDER BY xid_age DESC;
```

Monitor autovacuum activity, dead tuples, freeze progress, and long-running transactions during the post-upgrade observation window.

## 2.13.25 Failure scenarios

### FS-2.13-01 — PostgreSQL starts but application latency spikes

Compare query plans, statistics, cache warm-up, I/O, CPU, connection behavior, and PostgreSQL 18 planner changes. Complete required ANALYZE operations and remediate only after evidence identifies the cause.

### FS-2.13-02 — Extension cannot load

Keep affected workloads isolated. Verify PostgreSQL 18-compatible shared libraries, package versions, extension control files, preload configuration, and vendor compatibility. Do not force an incompatible binary into the new server.

### FS-2.13-03 — Required pg_upgrade rebuild script was skipped

Identify affected relations immediately, restrict unsafe access, execute the required script under controlled conditions, validate the objects, and review whether any workload used them before remediation.

### FS-2.13-04 — Standby does not reconnect

Validate PostgreSQL version, data state, WAL timeline, replication configuration, authentication, slots, and upgrade method. Rebuild the standby when required rather than improvising filesystem-level fixes.

### FS-2.13-05 — New WAL is not archived

Treat the cluster as having degraded recoverability. Correct archive configuration/credentials/path issues, verify archival resumes, and prove the recovery chain before closing the upgrade.

### FS-2.13-06 — Query plans regress after upgrade

Capture representative plans and runtime evidence. Verify statistics first, review release-note planner changes, inspect indexes and extended statistics, then tune queries/configuration only where justified.

### FS-2.13-07 — Authentication failures after cutover

Validate endpoint routing, `pg_hba.conf`, TLS, certificates, DNS, role/password state, pooler configuration, and client parameters. Avoid weakening HBA rules as a quick workaround.

### FS-2.13-08 — Sequence collision after logical cutover

Stop affected writes, determine the correct sequence high-water mark, synchronize sequence state safely, validate uniqueness/application behavior, and resume writes only after confirming the collision risk is removed.

## 2.13.26 Rollback decision framework

Rollback should be driven by predefined acceptance criteria, not emotion during an incident.

Rollback triggers can include:

```text
unrecoverable application incompatibility
critical extension incompatibility
severe correctness issue
unacceptable sustained performance regression
HA cannot be restored in the allowed window
backup/recovery cannot be established
security control failure
```

Before rollback, understand the upgrade method's reversibility.

`pg_upgrade --link` and PostgreSQL 18 `--swap` modes change rollback characteristics significantly. Once the new cluster has been started or file ownership/layout has been changed according to the selected mode, the old cluster cannot necessarily be treated as an untouched rollback target.

Replication-based migrations also require a plan for writes that occurred after cutover.

## 2.13.27 Post-upgrade observation window

Maintain an explicit observation period before retiring the old environment or deleting upgrade artifacts.

During the window, track:

```text
availability
error rate
query latency
resource saturation
WAL / checkpoints
replication
backup/archive health
autovacuum
application incidents
extension behavior
scheduled jobs
```

The length of the observation period should reflect business criticality, workload cycles, rollback architecture, storage cost, and change-management policy.

## 2.13.28 Automation

Automate repeatable validation wherever practical.

A post-upgrade validation pipeline can collect:

```text
server version
cluster/database inventory
extensions
runtime settings
pending restarts
replication state
archive status
checksum state
transaction age
backup result
smoke-test result
baseline performance comparison
```

Automation should generate evidence, not merely a green/red status. Preserve enough output for SRE review and incident investigation.

## 2.13.30 SRE/DBRE production principle

The correct definition of upgrade success is not:

```text
PostgreSQL 18 started.
```

It is:

```text
PostgreSQL 18 is running the intended workload correctly,
securely, recoverably, observably, and within the agreed
performance and availability objectives.
```

A major-version upgrade remains an active production change until the database and its surrounding operational ecosystem have passed that standard.
