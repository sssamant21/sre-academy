# 2.14 — Upgrade Rollback and Backout Strategy

**Status:** Production Ready / Complete

A PostgreSQL upgrade is not production-ready merely because the forward migration succeeds. The SRE/DBRE plan must define exactly how service will be restored if the new major version fails functional, performance, compatibility, replication, or operational validation.

Rollback must be designed before the upgrade begins. The valid backout mechanism depends on the upgrade method and, critically, whether writes have already been accepted on the upgraded cluster.

## Rollback architecture

```text
Upgrade Plan
    ↓
Select Upgrade Method
    ↓
Define Point of No Return
    ↓
Preserve Recoverable Source
    ↓
Perform Upgrade
    ↓
Validate New Cluster
    ↓
 ┌───────────────┐
 │ Accept?       │
 └──────┬────────┘
     Yes│       No
        ↓        ↓
 Production   Backout Decision
                 ↓
       Restore / Reverse Cutover
```

The safest rollback is usually the one prepared and tested before cutover rather than improvised during an incident.

## Core production rule

Never assume that an old PostgreSQL cluster can simply be restarted after the upgraded cluster has accepted writes.

For `pg_upgrade`, rollback behavior depends on the selected file-transfer mode. In particular, link-based approaches can make reuse of the old cluster unsafe after the new cluster has started because old and new clusters may share underlying data files.

For logical-replication migrations, the old publisher can remain intact during synchronization, but after cutover the application write direction and data divergence must be explicitly managed. PostgreSQL logical replication does not automatically provide bidirectional rollback.

## Define the point of no return

Every change record must identify a clear point of no return.

Examples include:

- starting a new cluster after `pg_upgrade --link` has linked source files
- deleting or modifying the old cluster
- allowing production writes on the new cluster without a reverse replication path
- changing application schemas in a way incompatible with the old version
- rotating credentials or endpoints without retaining a tested recovery path
- removing the source environment or its backups

The point of no return should be explicit in the runbook and acknowledged before execution crosses it.

## Rollback methods by upgrade architecture

### Dump and restore

A dump/restore major upgrade creates a separate target cluster. The original cluster can remain available as a rollback source until it is intentionally retired.

However, once the target begins accepting writes, simply routing traffic back to the source loses those new transactions unless they are separately reconciled.

Backout options include:

1. stop writes to the new cluster and accept loss of post-cutover changes under an approved business decision;
2. reconcile post-cutover changes back to the source through a tested migration mechanism;
3. restore a backup or PITR copy representing an agreed recovery point;
4. perform a forward fix on the target when that is safer than reverse migration.

The selected option must be established before cutover.

### pg_upgrade default copy mode

With ordinary copy mode, the old cluster remains physically separate from the new cluster. Preserve it until the validation window is complete.

Before rollback:

```text
Stop application writes
Stop / isolate new cluster
Confirm old cluster has not been modified
Restore old configuration / service endpoint
Start old cluster
Validate database
Redirect application
Validate application
```

Any writes accepted by the new cluster after cutover require an explicit data-loss or reconciliation decision.

### pg_upgrade link mode

Link mode requires special caution.

If `pg_upgrade --check` was used, the source cluster is unmodified and can be restarted.

If the upgrade aborts before linking begins, the source remains reusable.

If linking occurred but the new cluster was never started, follow the exact PostgreSQL `pg_upgrade` recovery instructions for the affected version before attempting to reuse the old cluster.

Once the new cluster has been started after a link-mode upgrade, assume that the old cluster cannot be safely restarted. Restore the old environment from a protected backup if rollback is required.

**Production rule:** do not use `--link` unless the rollback design explicitly accounts for this behavior.

### pg_upgrade clone mode

Where supported, clone mode can provide speed and space advantages without the same shared-file write hazard as link mode. Nevertheless, preserve the source cluster and validate the exact filesystem/platform behavior during rehearsal. Do not treat clone support as universal.

### pg_upgrade swap mode

PostgreSQL 18 adds `--swap`. This mode changes how old and new data directories are exchanged and has strict filesystem requirements. Treat it as a distinct upgrade architecture in the runbook. Rehearse the exact rollback steps on the same filesystem technology before production use and preserve an independent backup regardless of swap semantics.

### Logical replication migration

Logical replication is attractive for low-downtime major upgrades because PostgreSQL supports replication between different major versions.

Typical forward flow:

```text
Old PostgreSQL Publisher
          ↓
Logical Replication
          ↓
New PostgreSQL Subscriber
          ↓
Catch Up
          ↓
Write Freeze
          ↓
Final Synchronization
          ↓
Application Cutover
```

Rollback is not automatic after the application begins writing to the new cluster.

A production backout strategy must decide whether to:

- maintain a tested reverse logical-replication path;
- freeze writes during the validation window;
- capture post-cutover changes for reconciliation;
- accept an explicitly approved RPO;
- or perform a forward fix rather than reverse cutover.

Logical replication does not replicate schema/DDL automatically, and sequence state is not replicated. These limitations must be included in both forward and rollback procedures.

## Pre-upgrade rollback prerequisites

Before the production upgrade, verify:

```text
[ ] Source cluster health validated
[ ] Source PostgreSQL version recorded
[ ] Target PostgreSQL version recorded
[ ] Upgrade method recorded
[ ] Upgrade mode recorded
[ ] Point of no return documented
[ ] Last known-good backup validated
[ ] Restore procedure tested
[ ] PITR capability verified where required
[ ] WAL/archive continuity verified
[ ] Old binaries/packages preserved or reproducible
[ ] Old configuration captured
[ ] pg_hba.conf and TLS configuration captured
[ ] Extension inventory captured
[ ] Application endpoint rollback documented
[ ] DNS / proxy / service discovery rollback documented
[ ] Credential rollback requirements documented
[ ] HA/failover topology rollback documented
[ ] Replication slot/subscription state captured
[ ] Tablespace paths captured
[ ] Rollback decision authority identified
[ ] Business RPO/RTO accepted
```

A backup that has never been restored is not sufficient evidence for a production rollback plan.

## Preserve the source environment

Do not immediately delete:

```text
Old PGDATA
Old PostgreSQL binaries
Old configuration
Old extension packages
Old service definitions
Old container image / AMI / VM image
Old infrastructure manifests
```

Preserve them for the agreed observation period unless the upgrade method makes the old PGDATA unsafe to reuse.

Even when the source cluster cannot be directly restarted, preserving its metadata and artifacts greatly improves incident response.

## Backup and PITR safety net

Take or validate a recoverable backup according to the organization's backup architecture before the upgrade.

The recovery plan should answer:

```text
What backup will be used?
What WAL is required?
Where is the backup stored?
How long will restore take?
Who can access it?
Has restoration been tested?
What exact recovery point is acceptable?
```

For major upgrades, establish a fresh backup baseline on the new major version after production acceptance. Do not rely indefinitely on a backup chain whose operational assumptions belong to the retired version.

## Application write freeze

A write freeze creates a deterministic cutover boundary.

Conceptual sequence:

```text
Drain / Pause Application Writes
          ↓
Record Final Source Position
          ↓
Complete Upgrade / Synchronization
          ↓
Validate Target
          ↓
Switch Endpoint
          ↓
Controlled Application Validation
          ↓
Open Writes
```

Keep the period between opening writes and final acceptance as controlled as practical. Once writes begin on the new cluster, rollback becomes a data-consistency problem, not just an infrastructure switch.

## Cutover evidence

Capture evidence at the cutover boundary:

- timestamp
- source and target versions
- database sizes
- row-count or business-control totals where appropriate
- replication positions / LSN evidence
- sequence values where logical replication is used
- application deployment version
- active endpoint
- connection counts
- error rates
- critical query results
- backup/WAL state

This evidence helps determine what changed after cutover and what must be reconciled during a rollback.

## Rollback decision criteria

Define measurable rollback triggers before the maintenance window.

Examples:

```text
Database cannot start reliably
Critical extension unavailable
Application cannot authenticate
Critical transaction path fails
Unacceptable data inconsistency
Replication cannot be restored
Sustained severe latency regression
Uncontrolled CPU / memory / I/O saturation
Backup or WAL archiving is broken
Critical security control is missing
Required HA capability is unavailable
```

Not every issue requires rollback. Minor query-plan regressions, statistics warm-up, or a correctable configuration issue may be safer to remediate forward.

The incident commander and database lead should evaluate elapsed time, data divergence, RPO/RTO, and rollback risk before invoking backout.

## Rollback decision matrix

| Condition | Preferred action |
|---|---|
| Failure before source is modified | Abort and restore source service |
| pg_upgrade check fails | Correct issue; source remains production |
| Copy-mode target fails before writes | Return to preserved source |
| Link-mode target started | Do not restart old cluster; restore protected source backup |
| Logical target fails before cutover | Keep source authoritative and repair target |
| Logical target fails after new writes | Freeze writes; evaluate reverse sync/reconciliation/RPO |
| Minor configuration issue | Prefer forward remediation when low risk |
| Severe data-integrity concern | Stop writes immediately and protect evidence |

## Generic controlled rollback workflow

```text
Rollback Trigger
      ↓
Declare Incident / Freeze Changes
      ↓
Stop Application Writes
      ↓
Protect Current Target State
      ↓
Determine Safe Recovery Source
      ↓
Validate Old Cluster or Restore Backup
      ↓
Validate Configuration + Extensions
      ↓
Start Recovery Cluster
      ↓
Database Health Validation
      ↓
Redirect Endpoint
      ↓
Application Validation
      ↓
Open Writes
      ↓
Monitor Intensively
      ↓
Reconcile / RCA
```

Never destroy the failed target immediately. Preserve logs and state required for root-cause analysis unless doing so threatens recovery.

## Endpoint rollback

Database rollback is incomplete until applications are correctly routed.

Inventory all connection paths:

```text
DNS
Load balancer
Proxy / PgBouncer
Kubernetes Secret / ConfigMap
Application environment variables
JDBC / libpq connection strings
Service discovery
Firewall / security groups
TLS certificates
Monitoring and backup targets
```

Use stable service endpoints where possible so cutover and rollback do not require widespread application redeployment.

## Connection pool considerations

Connection pools can retain sessions to the old or new server after endpoint changes.

During cutover/backout:

1. stop or drain application writes;
2. drain/restart connection pools as required;
3. switch the database endpoint;
4. establish fresh sessions;
5. verify server identity and version from application paths;
6. reopen traffic gradually.

A DNS change alone does not guarantee that existing pooled connections have moved.

## Schema compatibility and rollback

Application/schema changes can make database rollback impossible even if the old database is intact.

Use expand/contract migration patterns where practical:

```text
Add backward-compatible schema
Deploy compatible application
Upgrade database
Validate
Remove deprecated schema later
```

Avoid irreversible DDL during the immediate upgrade window unless it is essential and its recovery method is tested.

Logical replication requires particular care because DDL is not automatically replicated to subscribers.

## Sequence synchronization

Logical replication does not replicate sequence state.

Before logical-replication cutover, inventory and synchronize sequences as required by the application. If a reverse cutover is possible, define how sequence values will remain collision-safe in both directions.

Failure to handle sequences can create duplicate-key incidents after rollback even when table rows appear synchronized.

## Large objects and unsupported objects

Inventory database features that may require special handling under the chosen migration method. Validate extensions, large objects, replication identities, unlogged objects, generated data, and external dependencies during rehearsal.

Do not assume that successful row replication proves full application equivalence.

## HA rollback strategy

For a physical-replication HA topology, the upgrade plan must include all nodes.

Do not leave production in an undocumented mixed-major physical streaming topology. PostgreSQL physical replication is tied to compatible server/storage formats; major-version migrations require an explicit supported upgrade approach.

The backout runbook should identify:

```text
Primary recovery node
Standby rebuild method
Replication slot handling
Synchronous replication policy
VIP / proxy / endpoint reversal
Failover manager state
Monitoring topology
Backup source
```

Rebuild or re-establish standbys according to the chosen major-upgrade method rather than assuming old standbys can attach to the upgraded primary.

## Logical replication upgrade considerations

PostgreSQL 18 can migrate certain logical replication state through `pg_upgrade` when the old cluster is PostgreSQL 17 or later and documented prerequisites are satisfied.

Before relying on this capability, validate:

- `wal_level = logical` on the new publisher;
- sufficient replication-slot capacity;
- required output plugins installed;
- logical slots are healthy and caught up;
- subscription table states and replication origins meet requirements;
- the exact publisher/subscriber upgrade sequence is rehearsed.

Logical replication cluster upgrades involve multiple non-transactional steps, so PostgreSQL explicitly recommends backups.

## Failure scenarios

### FS-2.14-01 — pg_upgrade --link target fails after startup

Do not restart the old cluster. Treat the old shared-file state as unsafe and recover from the protected backup or another independently preserved recovery source.

### FS-2.14-02 — Application fails immediately after copy-mode cutover

Freeze writes, stop new connections, validate that the source cluster remains independent and unchanged, restore the original endpoint, validate the source, and reopen traffic under the rollback plan.

### FS-2.14-03 — Logical migration fails after new writes

Immediately freeze writes. Measure divergence. Determine whether reverse replication/reconciliation was prepared and safe. If not, make an explicit RPO/business decision before reverting endpoints.

### FS-2.14-04 — Query performance collapses after upgrade

Check statistics, plans, extension behavior, configuration drift, JIT/parallel behavior, collation/index requirements, and PostgreSQL release-note migration changes. Prefer a forward fix if data divergence makes rollback riskier than remediation.

### FS-2.14-05 — New cluster cannot archive WAL

Treat broken recoverability as a production-readiness failure. Fix archive configuration promptly or invoke rollback if the recovery objective cannot be met within the approved risk window.

### FS-2.14-06 — Old cluster was accidentally deleted too early

Stop nonessential changes. Protect the target and available backups. Validate restore/PITR capability and escalate because the intended fast-backout path no longer exists.

### FS-2.14-07 — Sequence collision after reverse cutover

Stop affected writes, identify sequence/table divergence, establish safe sequence values above existing keys, reconcile missing rows, and validate all sequence-backed critical tables before reopening traffic.

### FS-2.14-08 — Endpoint rollback succeeds but errors continue

Check pooled/stale connections, DNS caches, proxy targets, secrets, TLS, application replicas, and background workers. Verify server identity from each application path rather than assuming the endpoint switch propagated.

Upgrade automation should generate a rollback manifest containing:

```text

Target PGDATA

Configuration hashes
Endpoint before/after

```

Automation must not automatically delete the source cluster immediately after a successful upgrade.

Destructive cleanup should be a separate, explicitly approved lifecycle action after the observation period and backup validation.

## Production rollback rehearsal

Before a major upgrade, perform a rehearsal with production-like data and topology.

Measure:

```text
Upgrade duration
Application validation duration
Rollback decision time
Database restore/start time
Endpoint reversal time
Connection pool recovery time
Replication rebuild time
Backup restore throughput
Total RTO
Potential RPO
```

The rehearsal should intentionally trigger at least one failure so the team practices the backout path rather than only the happy path.

## Production case study — link-mode misunderstanding

A team selects `pg_upgrade --link` to minimize downtime. The new cluster starts and application validation discovers a critical extension problem. Operators assume they can simply restart the old cluster.

That is unsafe because starting the new cluster can modify files shared with the old cluster.

Correct architecture:

```text
Pre-upgrade tested backup
        ↓
pg_upgrade --link
        ↓
Target startup
        ↓
Failure
        ↓
Do NOT restart old PGDATA
        ↓
Restore protected source copy
        ↓
Validate
        ↓
Application rollback
```

The lesson is that upgrade speed and rollback simplicity are separate design dimensions.

## Production case study — logical replication rollback gap

A low-downtime migration uses logical replication from PostgreSQL 16 to PostgreSQL 18. Replication reaches zero practical lag, the application switches to PostgreSQL 18, and writes are opened. Twenty minutes later a critical application incompatibility appears.

The old PostgreSQL 16 source no longer contains those twenty minutes of new transactions. A simple DNS reversal would cause data loss.

A correct plan would have defined one of the following before cutover:

```text
Reverse replication
Controlled write freeze through acceptance
Change capture + reconciliation
Approved bounded RPO
Forward-fix strategy
```

The lesson is that low-downtime upgrade does not automatically mean low-risk rollback.

## Cleanup after successful observation period

Only after formal acceptance:

1. verify new-cluster backups and restore capability;
2. verify WAL/archive/PITR health;
3. verify HA and replica rebuilds;
4. close upgrade-related incidents;
5. archive configuration and evidence;
6. remove temporary replication artifacts if appropriate;
7. decommission old infrastructure through change control;
8. securely delete obsolete credentials/data according to policy;
9. update CMDB/inventory/runbooks;
10. complete upgrade RCA/lessons learned.

Do not let the old cluster remain indefinitely as an unmanaged cost or security risk.

## SRE/DBRE golden rule

A major PostgreSQL upgrade is not reversible merely because the old server still exists.

Rollback safety depends on:

```text
Upgrade method
File-transfer mode
Whether target has started
Whether target accepted writes
Data divergence
Schema compatibility
Replication direction
Backup recoverability
Endpoint architecture
Business RPO/RTO
```

The production goal is not simply to have a rollback command. It is to maintain a verified path to a known-good, transactionally understood state.
