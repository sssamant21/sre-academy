# 2.15 — Upgrade Testing, Rehearsal, and Change Management

**Status:** Production Ready / Complete

A PostgreSQL upgrade should never be treated as a production-only execution event. The safest upgrade is one that has already been performed repeatedly against a representative copy of the environment, with measured timings, documented failure points, validated rollback boundaries, and explicit operational ownership.

This section defines the SRE/DBRE framework for testing and rehearsing PostgreSQL minor and major upgrades before production execution.

## 2.15.1 Why upgrade rehearsal is mandatory

Major PostgreSQL releases can introduce catalog, planner, SQL, configuration, extension, and application-visible compatibility changes. PostgreSQL explicitly recommends testing client applications on the new version and reviewing the migration notes for every intervening major release.

A production upgrade therefore requires more than proving that PostgreSQL starts.

The rehearsal must demonstrate that:

```text
Binaries are compatible
Data can be migrated safely
Extensions are compatible
Configuration is valid
Applications function correctly
Performance remains acceptable
HA and replication work
Backups and recovery work
Monitoring remains functional
Rollback is executable
The maintenance window is realistic
```

## 2.15.2 Upgrade test environments

Use the highest-fidelity environment practical for the risk of the database.

Preferred hierarchy:

```text
Production-like rehearsal environment
        ↓
Restored recent production backup
        ↓
Production schema + representative data
        ↓
Schema-only compatibility environment
```

PostgreSQL's `pg_upgrade` documentation specifically recommends creating a schema-only copy with dummy data for deployment testing. For performance and duration validation, however, realistic data volume is also necessary.

Never expose production credentials, secrets, or regulated data in an uncontrolled rehearsal environment.

## 2.15.3 Establish the source baseline

Before testing, capture the current production baseline.

Record at minimum:

```text
PostgreSQL major/minor version
Operating system and architecture
Package/build source
PGDATA and tablespaces
Database sizes
Largest relations
Extension inventory
Shared libraries
Configuration
HBA and identity mappings
Replication topology
Replication slots
Backup configuration
WAL/archive configuration
Connection count and poolers
Peak CPU / memory / IOPS / latency
Critical query latency
Transaction throughput
Autovacuum behavior
Application dependencies
```

Useful SQL:

```sql
SELECT version();

SELECT extname, extversion
FROM pg_extension
ORDER BY extname;

SELECT datname, pg_database_size(datname)
FROM pg_database
WHERE datallowconn
ORDER BY pg_database_size(datname) DESC;

SELECT name, setting, unit, source
FROM pg_settings
ORDER BY name;
```

The baseline becomes the comparison point for the upgraded environment.

## 2.15.4 Review all relevant release notes

When skipping major versions, review the migration and compatibility notes for every intervening PostgreSQL major release, not only the destination version.

Build a compatibility register:

| Area | Current behavior | New behavior | Action | Owner |
|---|---|---|---|---|
| SQL/API | Baseline | Changed | Application test | App team |
| Configuration | Existing | Renamed/removed/default changed | Config remediation | DBRE |
| Extension | Existing version | Target-supported version | Upgrade/install | DBRE |
| Authentication | Existing method | New behavior | Security test | Security/DBRE |
| Planner | Existing plans | Possible plan changes | Performance test | DBRE/App |

No unresolved critical compatibility item should enter the production change window.

## 2.15.5 Extension compatibility testing

Extensions and custom modules are a major upgrade dependency.

Inventory them:

```sql
SELECT extname,
       extversion,
       nspname AS schema
FROM pg_extension e
JOIN pg_namespace n ON n.oid = e.extnamespace
ORDER BY extname;
```

Confirm that the destination PostgreSQL version has compatible extension binaries and shared libraries.

PostgreSQL `pg_upgrade` requires external modules to be binary compatible with the new server, but it cannot prove all external-module compatibility itself. The required shared object files must be installed for the new server before upgrade execution.

Where the extension provides an upgrade path, test it explicitly:

```sql
ALTER EXTENSION extension_name UPDATE;
```

Do not assume that successfully installing an extension package proves that its SQL upgrade scripts, custom data types, operators, indexes, or background workers behave correctly.

## 2.15.6 pg_upgrade preflight rehearsal

For `pg_upgrade`, run the destination-version `pg_upgrade` binary.

Perform preflight checks before the production window:

```bash
pg_upgrade \
  --old-bindir=/usr/pgsql-17/bin \
  --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/postgresql/17/data \
  --new-datadir=/postgresql/18/data \
  --check
```

If production will use a specific transfer mode, include that mode during `--check` so mode-specific compatibility is tested.

Examples:

```bash
pg_upgrade --check --link ...
pg_upgrade --check --clone ...
pg_upgrade --check --swap ...
```

PostgreSQL 18 can parallelize database checks using `--jobs`, which should also be tested if it will be used in production.

Capture every warning and generated remediation script as a change artifact.

## 2.15.7 Test the exact production upgrade mode

Do not rehearse copy mode and then unexpectedly use link, clone, or swap mode in production.

The operational and rollback characteristics differ.

```text
Copy
  Higher temporary storage demand
  Old cluster remains independent

Link
  Fast and storage-efficient
  Old cluster becomes unsafe to reuse after new cluster starts

Clone
  Fast where filesystem cloning is supported
  Old cluster remains independent

Swap (PostgreSQL 18)
  Potentially very fast for many relations
  Old cluster becomes unusable once transfer begins
```

Test filesystem prerequisites, tablespaces, WAL layout, permissions, and rollback consequences for the selected mode.

## 2.15.8 Checksum compatibility

PostgreSQL 18 enables data checksums by default for newly initialized clusters unless explicitly disabled.

`pg_upgrade` requires compatible checksum settings between source and destination clusters.

Verify the source:

```sql
SHOW data_checksums;
```

Initialize the destination accordingly and validate it before running `pg_upgrade`.

Do not discover a checksum mismatch during the production maintenance window.

## 2.15.9 Rehearse using realistic data volume

Upgrade duration depends on far more than database size.

Measure:

```text
Number of databases
Number of relations
Number of indexes
Number of tablespaces
Number of large objects
Extension count
Catalog size
Filesystem performance
CPU availability
Selected pg_upgrade mode
Parallel jobs
Post-upgrade rebuild requirements
Analyze duration
Application validation duration
```

Run at least one rehearsal with production-scale or representative data if the maintenance window depends on accurate timing.

## 2.15.10 Build a timed runbook

Measure each phase separately.

Example:

```text
T+00  Change starts
T+05  Application write freeze confirmed
T+10  Final backup/WAL checks complete
T+15  Old PostgreSQL stopped
T+20  pg_upgrade begins
T+45  pg_upgrade completes
T+50  Generated remediation begins
T+65  New PostgreSQL starts
T+70  DB validation complete
T+80  Application smoke tests complete
T+90  Traffic restored
T+120 Observation checkpoint
```

These are illustrative timings only. Production estimates must come from the organization's rehearsals.

Track expected, rehearsal, and actual duration for continuous improvement.

## 2.15.11 Application compatibility testing

Test the real application stack against the destination PostgreSQL version before production cutover.

Validate:

```text
Connection establishment
TLS/authentication
Connection pooling
Prepared statements
Transactions
Stored procedures/functions
ORM behavior
DDL migrations
Read/write workflows
Batch jobs
ETL pipelines
Reporting
Background workers
Administrative tools
Backup tools
Monitoring exporters
```

A successful `SELECT 1` is not an application certification.

## 2.15.12 Query-plan and performance testing

Major versions can change planner and executor behavior.

Build a representative query corpus from critical application paths and observed production workload.

Compare:

```text
Execution latency
Planning latency
Plan shape
Index selection
Join strategy
Rows estimated vs actual
Temporary I/O
Buffer usage
CPU utilization
WAL generation
Lock behavior
```

Use controlled `EXPLAIN (ANALYZE, BUFFERS)` testing where safe and appropriate.

PostgreSQL 18 `pg_upgrade` preserves most optimizer statistics by default, reducing the historical post-upgrade cold-statistics problem. However, not all statistics are transferred. Extended statistics and cumulative statistics still require appropriate regeneration/validation.

Follow PostgreSQL-generated post-upgrade instructions and test the required `vacuumdb`/ANALYZE operations during rehearsal.

## 2.15.13 Test generated post-upgrade scripts

`pg_upgrade` can generate scripts or instructions for required rebuilds and extension updates.

Treat these as mandatory upgrade artifacts.

During rehearsal:

```text
Capture them
Review them
Estimate runtime
Run them
Validate results
Add them to the production runbook
```

PostgreSQL warns that tables referenced in required rebuild scripts can produce incorrect results or poor performance until the rebuild work is completed.

Do not reopen full application traffic before mandatory rebuild steps are understood and completed.

## 2.15.14 HA and standby rehearsal

For streaming-replication environments, test the complete topology, not only the primary.

Validate:

```text
Primary upgrade
Standby recreation or supported synchronization method
Timeline behavior
Replication connectivity
Replication lag
Replication slots
Synchronous replication
Failover tooling
Read-only traffic
Monitoring
Backup execution
```

Rehearse a controlled failover after the upgrade when HA is part of the production architecture.

The objective is to prove that the upgraded environment is highly available, not merely that the primary starts.

## 2.15.15 Logical-replication upgrade rehearsal

For low-downtime cross-major upgrades using logical replication, test:

```text
Initial synchronization duration
Ongoing replication lag
Publication/subscription scope
DDL synchronization procedure
Sequence synchronization
Large-object handling where relevant
Cutover write freeze
Final lag-to-zero validation
Endpoint switch
Application validation
Rollback/divergence handling
```

Logical replication supports replication between different PostgreSQL major versions, making it useful for low-downtime upgrades, but schema/DDL and operational state require separate management.

## 2.15.16 Backup and recovery rehearsal

Before production approval, prove that backup and recovery work with the destination version.

Test:

```text
New full backup
WAL archiving
Backup catalog registration
Restore to isolated environment
Point-in-time recovery
Recovery target validation
Backup monitoring
Retention policy
```

Do not treat a successful upgrade as complete while the new cluster has no proven recovery path.

## 2.15.17 Rollback rehearsal

A rollback plan that has never been tested is only a hypothesis.

Rehearse the actual rollback mechanism appropriate to the upgrade method.

Measure:

```text
Decision time
Traffic drain time
Endpoint reversal
Old-cluster recovery/start time
Application reconnection time
Data-loss exposure
Validation duration
```

Explicitly document the point of no return for link/swap modes and the data-divergence boundary for logical-replication migrations.

## 2.15.18 Failure injection

Where practical, intentionally test controlled failures in rehearsal.

Examples:

```text
Missing extension library
Insufficient disk space
Incorrect destination permissions
Invalid configuration
Authentication failure
Standby fails to attach
Archive command failure
Application smoke test failure
Performance regression
Upgrade exceeds maintenance window
```

The goal is not to create chaos for its own sake. It is to confirm that operators recognize the failure, stop at the correct gate, and execute the documented recovery path.

## 2.15.19 Change-management gates

A production upgrade should have explicit gates.

### Gate 1 — Design approved

Upgrade method, target version, downtime model, rollback architecture, and ownership approved.

### Gate 2 — Compatibility approved

Release notes, extensions, application dependencies, tooling, OS/platform, and configuration reviewed.

### Gate 3 — Rehearsal passed

Representative upgrade completed successfully within the expected window.

### Gate 4 — Recovery proven

Backup restore and rollback/recovery path validated.

### Gate 5 — Production readiness approved

Runbook, communications, monitoring, staffing, and decision authority confirmed.

### Gate 6 — Cutover authorization

Final health, backup, replication, storage, and application checks pass immediately before execution.

No-go at any gate should stop the upgrade.

## 2.15.20 Go/no-go criteria

Example go criteria:

```text
pg_upgrade --check clean or accepted findings documented
Required extension versions available
Destination configuration validated
Rehearsal completed successfully
Maintenance window has adequate margin
Backup and restore proven
Rollback tested
HA strategy tested
Application certification complete
Performance within accepted thresholds
Monitoring and alerting ready
All critical owners available
```

Example no-go criteria:

```text
Unresolved pg_upgrade blocker
Unsupported extension
Unexplained corruption/checksum issue
Backup or restore failure
Insufficient disk capacity
Replication unhealthy before change
Unresolved severe query regression
Rollback not executable
Critical application team unavailable
Maintenance window insufficient
```

## 2.15.21 Change freeze and concurrency control

Prevent unrelated changes from invalidating the rehearsal.

During the controlled pre-upgrade period, govern:

```text
Schema migrations
Extension changes
OS/package changes
Storage changes
Configuration changes
Application releases
Network/security changes
HA topology changes
```

If a material production change occurs after the final rehearsal, assess whether the rehearsal must be repeated.

## 2.15.22 Communication plan

Define communication before the maintenance window.

Include:

```text
Change owner
DBRE/SRE executor
Application owner
Infrastructure owner
Security/network owner if required
Incident commander
Rollback decision authority
Business stakeholder
Communication channel
Status update interval
Escalation path
```

Operators should not debate authority during a failed upgrade.

## 2.15.25 Automation

Automate repeatable checks rather than relying on memory.

A mature upgrade pipeline can automate:

```text
Version inventory
Extension inventory
Configuration export/diff
Database-size inventory
pg_upgrade --check
Disk-capacity validation
Checksum-state validation
Backup verification
Replication-health validation
Upgrade timing capture
Post-upgrade SQL checks
Smoke tests
Performance comparison
Evidence packaging
```

Automation must stop on failed gates. It must not blindly continue through a destructive step because the previous command returned an unexpected result.

## 2.15.26 Failure scenarios

### FS-2.15-01 — Rehearsal exceeds the maintenance window

Do not hope production will be faster. Investigate the slow phase, evaluate parallelism or another upgrade method, increase the approved window, or redesign for lower downtime.

### FS-2.15-02 — Extension missing on destination

Stop. Install and validate a supported destination extension version. Repeat `pg_upgrade --check` and the full extension/application test path.

### FS-2.15-03 — Query performance regresses after upgrade

Compare plans and statistics, complete required ANALYZE/rebuild work, review destination release behavior, and remediate before production approval.

### FS-2.15-04 — Backup restore test fails

Production upgrade is no-go. Repair the backup/recovery chain and prove recovery before rescheduling.

### FS-2.15-05 — Rehearsal succeeds but production changed afterward

Assess configuration, schema, extensions, packages, data volume, and topology changes. Repeat affected rehearsal stages when the delta can alter upgrade behavior.

### FS-2.15-06 — HA works but failover fails

Do not certify production readiness. Fix topology, replication, fencing/routing, or automation and repeat the failover test.

### FS-2.15-07 — Upgrade succeeds but application certification fails

Keep traffic closed or execute rollback according to the decision gate. Database startup alone is not success.

### FS-2.15-08 — Upgrade hits an unexpected pg_upgrade rebuild requirement

Stop application promotion until the generated remediation is understood. Execute and validate required rebuilds before reopening affected workloads.

## 2.15.28 SRE/DBRE golden rule

The production maintenance window should not be the first time the team discovers how the upgrade behaves.

The desired lifecycle is:

```text
Design
  ↓
Inventory
  ↓
Compatibility Review
  ↓
Build Representative Environment
  ↓
Preflight
  ↓
Full Rehearsal
  ↓
Failure / Rollback Rehearsal
  ↓
Performance + Application Certification
  ↓
Recovery Certification
  ↓
Go / No-Go Review
  ↓
Production Execution
  ↓
Post-Upgrade Observation
  ↓
Lessons Learned
```

A PostgreSQL upgrade is production-ready only when the organization has evidence that it can upgrade, validate, recover, and roll back within agreed reliability objectives.
