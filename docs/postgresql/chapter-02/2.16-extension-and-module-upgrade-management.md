# 2.16 — Extension and Module Upgrade Management

**Status:** Production Ready / Complete

PostgreSQL extensions and externally loaded modules are part of the database runtime and must be treated as first-class dependencies during patching and major-version upgrades. A successful PostgreSQL binary or data upgrade does not prove that extension code, SQL objects, shared libraries, preload modules, operator classes, data types, or extension-owned objects are compatible with the target server.

## Why extension management is an SRE/DBRE concern

Extensions can introduce SQL objects, background workers, custom data types, operators, access methods, functions, libraries, hooks, foreign data wrappers, and planner/executor behavior. C-language extensions are especially sensitive to server-version and build compatibility because their shared libraries must match the target PostgreSQL environment.

PostgreSQL `pg_upgrade` explicitly requires external module shared-object files used by the old cluster to be installed for the new server. `pg_upgrade` cannot prove that every external module is binary compatible, so compatibility must be established independently.

## Extension inventory

Before any upgrade, inventory installed extensions in every database:

```sql
SELECT extname,
       extversion,
       extnamespace::regnamespace AS schema,
       extrelocatable
FROM pg_extension
ORDER BY extname;
```

Compare installed versions with versions available to the target server:

```sql
SELECT name,
       default_version,
       installed_version
FROM pg_available_extensions
ORDER BY name;
```

For detailed version paths:

```sql
SELECT name,
       version,
       installed,
       superuser,
       trusted,
       relocatable,
       requires
FROM pg_available_extension_versions
ORDER BY name, version;
```

Inventory must be database-specific because extensions are registered in individual databases.

## Dependency manifest

Maintain an upgrade manifest containing at minimum:

```text
Extension name
Installed version
Target-supported version
Database(s)
Schema
Package / repository source
Shared-library requirement
Preload requirement
Dependencies
Upgrade path
Owner
Vendor / community support status
Rollback method
Validation test
```

Do not discover extension dependencies during the production outage.

## Shared libraries and pg_upgrade

Before running `pg_upgrade`, install target-version-compatible shared libraries for extensions and custom modules in the new PostgreSQL installation.

Do not pre-create the extension SQL definitions in the new cluster merely because the library has been installed. `pg_upgrade` migrates the catalog definitions from the old cluster. PostgreSQL documents that extension shared-object files should be installed for the new server, while extension schema definitions should not be loaded separately because they will be duplicated from the old cluster.

If extension updates are available, `pg_upgrade` can report required follow-up actions and generate post-upgrade scripts.

## Preload modules

Inventory configuration such as:

```sql
SHOW shared_preload_libraries;
SHOW session_preload_libraries;
SHOW local_preload_libraries;
```

A missing or incompatible `shared_preload_libraries` module can prevent PostgreSQL from starting. Before the production upgrade, confirm that every required preload library exists in the target installation and supports the target PostgreSQL major version.

Never copy an old `.so` or DLL into a new PostgreSQL installation merely to make startup succeed unless the module provider explicitly supports that binary combination.

## Extension update paths

PostgreSQL extension upgrades use extension-supplied update scripts.

```sql
ALTER EXTENSION extension_name UPDATE;
```

A specific target can be requested:

```sql
ALTER EXTENSION extension_name UPDATE TO 'target_version';
```

This works only when the extension provides a valid update path from the installed version to the requested version.

Determine available paths before the change window. Do not assume that every old extension version can jump directly to the latest release.

## Extension version verification

After PostgreSQL upgrade, compare installed and available extension versions:

```sql
SELECT e.extname,
       e.extversion AS installed_version,
       a.default_version
FROM pg_extension e
LEFT JOIN pg_available_extensions a
       ON a.name = e.extname
ORDER BY e.extname;
```

A difference does not automatically mean `ALTER EXTENSION UPDATE` should be executed. Review the extension's release notes, compatibility requirements, and application dependencies first.

## Upgrade ordering

The correct order depends on the extension, but the general production workflow is:

```text
Inventory extensions/modules
          ↓
Read PostgreSQL migration notes
          ↓
Read extension/vendor compatibility notes
          ↓
Install target PostgreSQL binaries
          ↓
Install compatible extension packages/libraries
          ↓
Run pg_upgrade --check where applicable
          ↓
Perform PostgreSQL upgrade
          ↓
Execute generated post-upgrade actions
          ↓
Upgrade extension SQL definitions where required
          ↓
Rebuild/reindex extension-dependent objects where required
          ↓
Validate application behavior
```

Never create a universal automated `ALTER EXTENSION ... UPDATE` loop for production without per-extension validation.

## Package-management considerations

On package-managed Linux systems, PostgreSQL extensions may be distributed as packages tied to a PostgreSQL major version. The exact package naming and repository model vary by distribution and vendor.

The DBRE upgrade plan must verify:

- package availability for the target PostgreSQL major version
- exact extension release supplied by the repository
- package dependencies
- whether an OS/package update will unexpectedly update the extension
- whether target packages install shared libraries into the expected PostgreSQL library directory
- whether package removal can affect the old cluster during rollback

Keep old-version extension packages available until rollback is formally closed.

## Source-built extensions

For source-built modules, record the source revision, compiler/toolchain, build flags, PostgreSQL development headers, dependency libraries, and artifact checksum.

Rebuild against the target PostgreSQL version rather than reusing an unverified old binary.

Where the extension provides regression tests, run them against a representative target environment before production deployment.

## Extension configuration tables

Some extensions designate configuration tables whose contents are included by logical backup tools. Understand which state belongs to the extension and how it is preserved by the chosen upgrade method.

Do not assume that reinstalling extension binaries recreates extension-managed application data.

## Dump/restore upgrades

Logical dump/restore requires the target system to have the extension control files, installation scripts, shared libraries, and dependencies available when the dump recreates extensions.

A restore can fail even though PostgreSQL itself is healthy if a required extension is absent from the target installation.

Test the complete restore using the same extension artifacts planned for production.

## Logical-replication upgrades

Logical replication does not eliminate extension compatibility requirements. The target database must have compatible schemas, types, functions, operators, and extension-owned objects required by replicated tables and applications.

DDL is not automatically replicated by built-in logical replication. Extension installation or upgrade must therefore be managed explicitly on the target.

Test extension-defined data types and objects carefully before cutover.

## Extension ownership and privileges

`ALTER EXTENSION` requires ownership of the extension. Some extension installation operations require superuser privileges; PostgreSQL also supports trusted extensions that can be installed by users with appropriate database privileges.

Production automation should use the minimum privilege necessary and should not grant broad superuser access simply to simplify extension deployment.

## Security review

Treat extensions as executable supply-chain dependencies.

Review:

```text
Artifact source
Maintainer/vendor
Supported PostgreSQL versions
Release integrity
Package signatures/checksums where applicable
C-language/native code
Superuser requirements
Background workers
Filesystem/network access
Known security advisories
Update history
```

Only approved extension sources should be permitted in production.

## Extension-dependent indexes and objects

Major PostgreSQL or extension releases can require rebuilding indexes or other objects that depend on changed operator classes, collations, data types, or extension behavior.

`pg_upgrade` reports rebuild/reindex cases it knows about and can generate scripts for required post-upgrade work. Treat these scripts as mandatory change artifacts, review them before execution, and do not expose affected objects to unrestricted production use until required rebuilds complete.

## Monitoring and alerting

Monitor during and after extension upgrades for:

- PostgreSQL startup failures caused by preload libraries
- `could not load library` errors
- undefined symbols / binary loading failures
- extension SQL upgrade errors
- invalid indexes or failed rebuilds
- background worker crashes
- query-plan regressions
- increased error rate from extension functions
- replication apply failures involving extension-defined types
- unexpected package/version drift
- extension version mismatch across HA nodes

Extension health must be part of the post-upgrade observation window.

## Failure scenarios

### FS-2.16-01 — Target extension package is unavailable

Stop the upgrade before production cutover. Do not remove the extension from production merely to satisfy the upgrade. Select a supported target version, obtain/build a validated artifact, replace the dependency through an application migration, or postpone the PostgreSQL upgrade.

### FS-2.16-02 — PostgreSQL will not start after upgrade because a preload library is missing

Keep traffic isolated. Confirm the target-version module package and library path, install the compatible artifact, validate configuration, and perform a controlled restart. Do not copy the old binary blindly.

### FS-2.16-03 — pg_upgrade reports missing libraries

Treat the check as a blocker. Install compatible target libraries and rerun `pg_upgrade --check`. Do not bypass the check by deleting catalog references unless an approved extension-removal migration has been completed.

### FS-2.16-04 — ALTER EXTENSION UPDATE fails

Capture the error and preserve transactional state. Review the extension's supported upgrade path and update scripts. Do not manually modify `pg_extension.extversion` to pretend the upgrade succeeded.

### FS-2.16-05 — Extension update causes query regression

Compare plans and extension behavior against rehearsal baselines. Apply the extension-specific rollback if supported, restore/cut back according to the upgrade rollback plan, or remediate affected indexes/configuration. Do not assume PostgreSQL core rollback alone reverses extension SQL changes.

### FS-2.16-06 — HA nodes have inconsistent extension libraries

Stop rolling promotion until all candidate nodes have the same approved extension artifact set. A standby that can replay WAL is not automatically safe to promote if required runtime libraries are absent or incompatible.

### FS-2.16-07 — Dump restore fails at CREATE EXTENSION

Install the required target-compatible extension files and restart the restore from the documented recovery point. Validate extension availability before retrying the production migration.

### FS-2.16-08 — Logical replication target lacks extension-defined type

Pause cutover. Install/configure the compatible extension and schema on the target, validate table definitions and replication, then resume only after consistency is proven.

## Rollback strategy

Extension rollback must be designed together with PostgreSQL rollback.

Record whether the extension supports downgrade scripts. Many extensions support forward updates but do not provide a safe downgrade path.

Before upgrading an extension, determine whether rollback requires:

```text
ALTER EXTENSION downgrade path (if explicitly supported)
Database restore
Cluster rollback
Application rollback
Rebuild of extension-dependent objects
Package/library rollback
```

Never assume `ALTER EXTENSION UPDATE` is reversible.

## Automation

Automate inventory and validation, not blind mutation.

Useful automation should:

1. enumerate `pg_extension` in every database;
2. capture installed versions and owners;
3. query available target versions;
4. verify target package/library availability;
5. compare extension inventories across HA nodes;
6. detect preload dependencies;
7. run `pg_upgrade --check` where applicable;
8. archive generated pg_upgrade reports/scripts;
9. execute only approved extension updates;
10. run extension-specific smoke tests;
11. record final versions as change evidence.

## Production case study — missing extension library

A major PostgreSQL upgrade is rehearsed successfully on a simplified database but production contains an additional C-language extension loaded by one application database. During the production `pg_upgrade --check`, the new installation cannot find the required shared library.

Because the team treats `--check` as a hard gate, the upgrade is stopped before downtime begins. The target-version extension package is built and tested, the rehearsal environment is updated to match production inventory, and the upgrade is rescheduled.

The failure becomes a controlled pre-change finding instead of a production outage.

## Production case study — automatic extension update causes regression

An automation pipeline updates every extension to its available default version immediately after a PostgreSQL major upgrade. One extension changes planner behavior and a critical query regresses.

The remediation is to separate PostgreSQL major-version migration from extension-version changes unless the extension update is required for compatibility. Each extension update receives an explicit compatibility review, test case, rollback decision, and change record.

The SRE principle is simple: reduce simultaneous variables during a high-risk database upgrade.

## Golden production principle

PostgreSQL core, extensions, modules, and their operating-system artifacts form one runtime dependency graph.

A cluster is not upgrade-ready merely because `postgres --version` is correct. It is upgrade-ready only when every required extension and module is supported, installable, tested, observable, and recoverable on the target platform.
