# 2.17 — Tablespace and Storage Upgrade Considerations

**Status:** Production Ready / Complete

PostgreSQL major-version upgrades are not only binary and catalog migrations. The storage topology of the source cluster — PGDATA, WAL, user-defined tablespaces, mount points, filesystems, capacity, permissions, and standby storage — is part of the upgrade architecture and must be inventoried, validated, and rehearsed.

## 2.17.1 Storage topology before an upgrade

Create a complete storage map before changing the cluster:

```text
PostgreSQL Cluster
├── PGDATA
├── pg_wal (inside PGDATA or relocated)
├── pg_default
├── pg_global
└── User-defined tablespaces
    ├── tablespace_1 → filesystem / volume A
    └── tablespace_2 → filesystem / volume B
```

Inventory tablespaces from PostgreSQL:

```sql
SELECT oid,
       spcname,
       pg_tablespace_location(oid) AS location
FROM pg_tablespace
ORDER BY spcname;
```

Also inventory filesystem capacity and mount state at the operating-system layer.

## 2.17.2 Tablespaces are cluster dependencies

PostgreSQL tablespaces define alternative filesystem locations for database objects. They are registered cluster-wide and cannot be treated as independent databases or detachable storage units.

A missing tablespace filesystem can therefore make objects unavailable and can jeopardize startup, upgrade, backup, or recovery operations.

Production rule: include every user-defined tablespace in the same change, backup, monitoring, recovery, and upgrade scope as PGDATA.

## 2.17.3 Tablespace directory requirements

A tablespace location must be an absolute path to an existing directory owned by the PostgreSQL operating-system user. PostgreSQL does not create the target directory for `CREATE TABLESPACE`.

Example:

```bash
mkdir -p /pgdata/tablespaces/fast_data
chown postgres:postgres /pgdata/tablespaces/fast_data
```

```sql
CREATE TABLESPACE fast_data
LOCATION '/pgdata/tablespaces/fast_data';
```

Do not manually manipulate the internal contents of a live tablespace directory.


## 2.17.5 Capacity planning for upgrade modes

Storage requirements differ substantially by upgrade method.

### pg_upgrade copy mode

Copy mode requires space for a separate new cluster and copied relation data. Capacity planning must include PGDATA and all tablespaces, plus operational headroom.

### pg_upgrade link mode

Link mode avoids full data copying by using hard links. The old and new cluster data directories must satisfy PostgreSQL's same-filesystem requirements for this mode. Link mode also changes rollback characteristics: once the new cluster is started, shared files can make the old cluster unsafe to reuse.

### pg_upgrade clone mode

Clone mode uses filesystem cloning where supported and can provide link-like speed and space advantages without making the old cluster unusable merely because the new cluster starts. Support depends on the operating system/filesystem.

### pg_upgrade swap mode

PostgreSQL 18 adds `--swap`, which moves/swaps directory structures rather than performing the traditional data transfer. It can be especially fast for clusters with many relations, but it destructively modifies the old cluster once file transfer begins. It also imposes same-filesystem constraints for the old and new data directories.

Treat `--swap` as a production architecture choice requiring explicit rollback and filesystem review, not simply a performance flag.

## 2.17.6 Run mode-specific checks

Always perform `pg_upgrade --check` before the production upgrade. When planning link, clone, copy-file-range, or swap mode, run the check with the intended transfer-mode option so PostgreSQL performs relevant mode-specific validation.

Conceptually:

```bash
pg_upgrade \
  --old-bindir=/usr/pgsql-OLD/bin \
  --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/pgdata/OLD \
  --new-datadir=/pgdata/18 \
  --check
```

Use actual installation paths and the intended transfer mode from the approved runbook.

## 2.17.7 WAL outside PGDATA

If `pg_wal` has been relocated, treat that filesystem as an explicit upgrade dependency.

Validate:

```text
Mount availability
Ownership and permissions
Capacity
Latency
Backup/recovery design
Standby topology
Synchronization procedure
```

PostgreSQL's `pg_upgrade` synchronization guidance explicitly notes that relocated WAL directories must also be handled when preparing standby servers.

## 2.17.8 Tablespaces and standby upgrades

For physical standby reuse around `pg_upgrade`, PostgreSQL documents synchronization procedures that require the corresponding tablespace directories to be synchronized as well as the main data directory. Relocated WAL directories also require synchronization.

A production HA runbook must therefore map each primary tablespace to its standby-side storage and confirm that mount points, permissions, capacity, and filesystem behavior are compatible before the maintenance window.

Do not assume synchronizing PGDATA alone creates a valid upgraded standby when external tablespaces exist.

## 2.17.9 Storage synchronization and durability

By default, `pg_upgrade` waits for upgraded-cluster files to be safely synchronized to storage. PostgreSQL 18 supports synchronization methods including `fsync` and, on Linux, `syncfs` with documented caveats.

The `--no-sync` option can reduce test duration but weakens crash safety during the upgrade operation. It should not be used as a routine production optimization.

Production principle:

```text
Upgrade speed must not silently replace durability.
```

## 2.17.10 Tablespace performance characteristics

Tablespaces may exist because workloads require different storage performance characteristics. PostgreSQL allows tablespace-specific planner and I/O options such as `seq_page_cost`, `random_page_cost`, `effective_io_concurrency`, and `maintenance_io_concurrency`.

An upgrade or storage migration must preserve or deliberately redesign the performance intent of those tablespaces.

Validate after cutover:

```sql
SELECT spcname, spcoptions
FROM pg_tablespace
ORDER BY spcname;
```

A logically correct upgrade can still become a production performance incident if a high-I/O tablespace is accidentally placed on a slower storage tier.

## 2.17.11 Moving storage during a major upgrade

Combining a PostgreSQL major-version upgrade with a storage-platform migration increases risk because it changes two major variables simultaneously.

When both are required, explicitly test:

```text
Throughput
Read latency
Write latency
fsync latency
Checkpoint behavior
WAL generation and flush
Vacuum performance
Backup duration
Restore duration
Application query latency
```

Prefer separating the changes when operationally practical. If they must be combined, the rehearsal environment should use the target storage architecture.

## 2.17.12 Database default tablespace changes

PostgreSQL supports changing a database's default tablespace with `ALTER DATABASE ... SET TABLESPACE`, subject to documented restrictions. This physically moves objects in the database's old default tablespace while objects already residing in other tablespaces are unaffected.

Do not use this casually as part of an upgrade window. Moving large databases can create substantial I/O, time, and capacity requirements and should be planned as a storage migration in its own right.

## 2.17.13 Backup and snapshot considerations

A storage snapshot is useful only if it produces a recoverable PostgreSQL state under the chosen backup design.

For clusters using multiple filesystems or tablespaces, crash-consistent snapshots must account for consistency across the relevant storage set. PostgreSQL's `pg_upgrade` documentation notes that filesystem snapshots or copy-on-write copies used to preserve a cluster must be created simultaneously or while the server is down.

Do not assume independent snapshots of PGDATA and multiple tablespaces automatically form a valid rollback image.

## 2.17.14 Monitoring during storage-sensitive upgrades

Monitor:

```text
Filesystem utilization
Inode utilization
Read/write latency
IOPS
Throughput
Queue depth
WAL write/flush latency
Checkpoint behavior
Disk errors
Filesystem errors
Mount state
Tablespace availability
Backup/archive status
Replication lag
```

Correlate storage metrics with PostgreSQL logs and database wait/activity telemetry.

## 2.17.15 Alerting gates

Upgrade go/no-go gates should include:

- insufficient free capacity
- inode exhaustion risk
- degraded or read-only filesystem
- missing tablespace mount
- wrong ownership or permissions
- abnormal storage latency
- storage errors
- missing WAL filesystem
- incomplete backup coverage
- failed snapshot validation
- standby tablespace mismatch

A storage alert during the upgrade should be treated as a database reliability event, not merely an infrastructure warning.

## 2.17.16 Failure scenarios

### FS-2.17-01 — Tablespace mount missing before upgrade

Stop the upgrade. Confirm the correct mount source, ownership, and expected PostgreSQL tablespace path. Do not allow PostgreSQL to operate against an unintended empty mount-point directory.

### FS-2.17-02 — Upgrade runs out of disk space

Stop safely according to the selected upgrade method. Preserve old and new cluster state, identify which filesystem exhausted capacity, and follow the method-specific recovery procedure. Do not delete old-cluster files simply to create emergency space unless the rollback point has been formally abandoned.

### FS-2.17-03 — Wrong storage tier after cutover

Protect the workload from overload, compare storage topology with the approved manifest, evaluate latency and throughput, and decide whether to correct storage placement or back out according to the production decision gate.

### FS-2.17-04 — Standby starts without synchronized tablespace data

Remove it from service. Rebuild or resynchronize using the approved PostgreSQL standby-upgrade procedure and validate all external tablespaces before rejoining HA service.

### FS-2.17-05 — Link-mode rollback attempted after new cluster start

Do not blindly start the old cluster. Link mode can leave old and new clusters sharing relation files; follow PostgreSQL's documented reversion procedure and the pre-approved rollback runbook.

### FS-2.17-06 — Swap-mode upgrade fails after transfer begins

Treat the old cluster as destructively modified. Do not improvise a restart of it. Follow the PostgreSQL 18 `pg_upgrade --swap` recovery guidance and restore from the protected rollback mechanism if required.

### FS-2.17-07 — Relocated WAL filesystem unavailable

Do not continue cutover. Restore the expected WAL storage, verify ownership and durability, inspect PostgreSQL logs, and validate cluster state before startup.

## 2.17.17 Recovery workflow

```text
Storage / Tablespace Failure
          ↓
Stop Upgrade or Traffic Promotion
          ↓
Protect Existing Cluster State
          ↓
Identify PGDATA / WAL / Tablespace Impact
          ↓
Validate Mounts + Filesystems + Ownership
          ↓
Determine Upgrade Mode / Point of No Return
          ↓
Restore Storage or Invoke Approved Rollback
          ↓
Validate PostgreSQL Startup
          ↓
Validate Tablespaces + Relations
          ↓
Validate WAL / Replication / Backup
          ↓
Application Validation
          ↓
Controlled Production Promotion
```

## 2.17.18 Automation and IaC

Automation should inventory and validate storage before upgrade execution.

A production pipeline should verify:

```text
Expected PGDATA
Expected WAL location
Expected tablespace list
Expected mount sources
Expected filesystem types
Minimum free capacity
Minimum inode headroom
Ownership and permissions
Upgrade-mode filesystem requirements
Backup/snapshot completion
Standby storage topology
```

Fail closed when the discovered topology differs from the approved manifest.

Do not automate destructive storage cleanup as an automatic response to an upgrade failure.

## 2.17.19 Production case study — forgotten tablespace

A cluster's PGDATA is copied to the target server and the team believes the upgrade dataset is complete. During validation, application queries fail because a large index and historical partition set reside in a user-defined tablespace on a separate volume that was not included in the migration plan.

Corrective actions:

```text
Inventory pg_tablespace before every migration
Map logical tablespaces to physical storage
Include external paths in backup and migration scope
Validate target mounts before PostgreSQL startup
Add tablespace checks to automated readiness gates
```

The lesson is simple: PGDATA alone does not necessarily describe the complete physical storage footprint of a PostgreSQL cluster.

## 2.17.20 Production case study — capacity underestimated for copy mode

A rehearsal uses a smaller dataset and succeeds. Production uses `pg_upgrade` copy mode on a multi-terabyte cluster with several tablespaces, but the target filesystems do not have enough space for the additional cluster copy plus operational headroom.

The upgrade stops mid-window.

Corrective actions include capacity modeling from production relation sizes, tablespace-by-tablespace headroom checks, rehearsal with representative scale, and explicit go/no-go capacity gates.

## 2.17.22 SRE/DBRE takeaway

PostgreSQL storage is part of the database architecture, not a transparent infrastructure layer.

For every upgrade, think in terms of the complete physical cluster:

```text
PGDATA
+ WAL
+ Tablespaces
+ Filesystems
+ Mounts
+ Capacity
+ Durability
+ Standby Storage
+ Backup / Recovery
```

An upgrade is production-ready only when every storage dependency is known, protected, validated, monitored, and recoverable.
