# 2.19 — Backup, Recovery, and PITR Readiness During Upgrades

**Status:** Production Ready / Complete

A PostgreSQL upgrade is not production-ready merely because the new server starts. The upgrade must preserve a known recovery path before, during, and after the change. For SRE/DBRE teams, backup and recovery readiness is therefore a formal upgrade gate.

## 2.19.1 Recovery-first upgrade principle

Before any upgrade, answer four questions:

```text
What is the last known-good recovery point?
How will we recover the old cluster?
How will we recover the new cluster after cutover?
What are the tested RPO and RTO for each phase?
```

If these cannot be answered with tested procedures and evidence, the production upgrade should not begin.

## 2.19.2 PostgreSQL backup architectures

PostgreSQL documents three fundamental backup approaches:

```text
SQL dump
Filesystem-level backup
Continuous archiving / PITR
```

Each solves a different problem. Upgrade planning must know which mechanisms are available and what each can actually recover.

## 2.19.3 Logical backups

Logical backups use tools such as `pg_dump` and `pg_dumpall`.

Examples:

```bash
pg_dump -Fc -d appdb -f appdb.dump
pg_dumpall --globals-only > globals.sql
```

Logical backups are useful for portability, object-level restore, migration validation, and dump/restore major upgrades.

For major-version dump/restore, PostgreSQL recommends using newer-version dump programs where practical because they contain current fixes and improvements and can read supported older server versions.

Logical dumps are not a substitute for every physical recovery requirement, especially for large clusters with aggressive RTO objectives.

## 2.19.4 Physical backup and PITR

Continuous archiving combines a physical base backup with the WAL required to replay changes to a desired recovery point.

Conceptually:

```text
Base Backup
     +
Archived WAL
     ↓
Restore Cluster
     ↓
Replay WAL
     ↓
Recover to Target Time / LSN / Transaction
```

An upgrade runbook should verify that WAL archiving is healthy before entering the maintenance window when PITR is part of the recovery architecture.

## 2.19.5 Pre-upgrade backup gate

Before production upgrade execution:

- confirm the backup completed successfully
- confirm backup scope includes PGDATA and all required tablespaces
- confirm relocated WAL/storage dependencies are understood
- confirm archived WAL continuity where PITR is required
- confirm backup encryption and access controls
- confirm retention will protect the rollback window
- confirm the backup is readable by the intended restore tooling
- confirm a recent restore test exists
- record recovery identifiers and timestamps in the change record

A dashboard showing `backup succeeded` is not sufficient evidence by itself.

## 2.19.6 Restore validation

The strongest backup validation is a successful restore.

A recovery rehearsal should verify:

```text
Cluster starts
Expected databases exist
Expected roles exist
Critical relations are readable
Application smoke tests pass
Recovery target is correct
Tablespaces resolve correctly
Extensions are available
Configuration is restored intentionally
Backup/WAL chain is complete
```

Where possible, automate restore testing on a recurring basis outside the upgrade window.

## 2.19.7 Backup consistency with tablespaces

Clusters with user-defined tablespaces have storage outside the main PGDATA tree. Filesystem snapshot/copy strategies must maintain a consistent cluster-wide image.

PostgreSQL's `pg_upgrade` guidance notes that filesystem snapshots or copy-on-write copies used to preserve the old cluster must be created simultaneously or while the database server is down.

Do not independently snapshot multiple database filesystems at unrelated times and assume they form a valid PostgreSQL rollback image.

## 2.19.8 Upgrade method and rollback backup design

### Dump/restore

The logical dump is itself the migration source, but production rollback still requires protection of the old server and a clear write-control strategy.

### pg_upgrade copy mode

The old cluster remains physically separate. Preserve it until production acceptance, but remember that writes made after cutover exist only in the new cluster unless separately replicated or captured.

### pg_upgrade link mode

Link mode can share relation files between old and new clusters. Once the new cluster starts, the old cluster cannot simply be assumed safe to restart. A separate protected backup/snapshot is especially valuable.

### pg_upgrade clone mode

Clone mode preserves better old-cluster rollback characteristics than link mode where filesystem support exists, but rollback still requires write-divergence planning.

### pg_upgrade swap mode

PostgreSQL 18 `--swap` destructively modifies the old cluster once transfer begins. A pre-upgrade protected recovery copy is therefore a critical rollback control.

### Logical replication

The old source remains online during synchronization, but after write cutover the two clusters can diverge. Backup does not solve reverse synchronization by itself. The rollback design must define how post-cutover writes are handled.

## 2.19.9 RPO and RTO by upgrade phase

Define recovery objectives for at least:

```text
Before maintenance
During old-cluster shutdown
During pg_upgrade / migration
Immediately after new-cluster startup
After application cutover
During observation window
After old-cluster retirement
```

RPO/RTO may differ across these phases. Record those differences rather than using one generic disaster-recovery number.

## 2.19.10 Protecting the rollback copy

A rollback copy should be protected from accidental mutation and cleanup.

Controls may include:

```text
Read-only snapshot policy
Separate backup account/project
Retention lock where appropriate
Explicit change-ticket identifier
Deletion protection
Restricted IAM / filesystem permissions
Documented expiration date
```

Do not let automated housekeeping delete the only known-good pre-upgrade recovery point during the observation window.

## 2.19.11 WAL archiving validation

Where continuous archiving is used, monitor archive success before and after the upgrade.

Useful PostgreSQL evidence can include archive statistics and server logs. The exact validation depends on the configured archive mechanism.

Verify that the new major version is configured to continue the intended archive policy after cutover. Configuration should not be copied blindly; it must be reviewed for the target version and environment.

## 2.19.12 Timeline awareness

Recovery and promotion can create new PostgreSQL timelines. Backup and recovery tooling must retain the timeline history and WAL required by the recovery policy.

SRE teams should understand that a promoted recovery instance is not merely the same WAL stream continuing unchanged.

Timeline-aware recovery testing is especially important in environments with repeated failover, PITR, or disaster-recovery exercises.

## 2.19.13 Post-upgrade backup baseline

After a successful major-version upgrade, create and validate a new backup baseline for the new cluster according to the organization's recovery architecture.

Do not rely indefinitely on the pre-upgrade backup as the primary recovery mechanism for the new production version.

Post-cutover flow:

```text
Upgrade Complete
      ↓
Functional Validation
      ↓
Create New Backup Baseline
      ↓
Validate WAL Archiving / Backup Jobs
      ↓
Perform Restore Validation
      ↓
Begin Normal Retention Cycle
      ↓
Retire Old Recovery Assets Only After Approval
```

## 2.19.14 Configuration and secrets in recovery

A database backup does not automatically guarantee recovery of the entire service.

The recovery architecture should also protect or reproduce:

```text
postgresql.conf and includes
pg_hba.conf
pg_ident.conf
TLS certificates/keys
service definitions
backup credentials
archive credentials
monitoring configuration
extension packages
OS/package manifests
IaC and automation
connection-routing configuration
```

Secrets should remain in the approved secrets-management platform rather than being embedded in database backup scripts.

## 2.19.15 Backup monitoring

Monitor at least:

```text
Backup success/failure
Backup age
Backup duration
Backup size
Restore-test age
WAL archive failures
WAL archive backlog
Repository/storage capacity
Retention status
Encryption/access failures
Snapshot completion
Cross-region/cross-account copy status where applicable
```

A backup alert should indicate recoverability risk, not merely job execution status.

## 2.19.16 Upgrade-specific alerting gates

Block or pause the upgrade when:

- the required pre-upgrade backup failed
- the backup is older than the approved threshold
- WAL archiving is broken for a PITR-dependent system
- backup storage is unhealthy
- required tablespaces are not covered
- the restore procedure is untested beyond policy limits
- rollback snapshot creation failed
- backup credentials are unavailable
- the recovery copy cannot be located or verified

## 2.19.17 Failure scenarios

### FS-2.19-01 — Backup job reports success but restore fails

Stop the production upgrade if still pre-cutover. Preserve evidence, identify the restore failure, repair the backup chain/tooling, and produce a verified recovery point before proceeding.

### FS-2.19-02 — WAL archive failure discovered before upgrade

Do not proceed with a PITR-dependent upgrade plan. Restore archive health, verify continuity, and confirm recovery readiness before the change window continues.

### FS-2.19-03 — Tablespace omitted from snapshot scope

Treat the snapshot as insufficient for cluster rollback. Create a cluster-consistent protected copy covering all storage or choose another validated backup method.

### FS-2.19-04 — New cluster fails after link-mode cutover

Do not blindly restart the old cluster. Follow the documented `pg_upgrade` reversion procedure and use the protected pre-upgrade recovery copy when required.

### FS-2.19-05 — New cluster fails after swap-mode transfer begins

The old cluster has been destructively modified by design. Follow PostgreSQL's documented swap-mode recovery guidance or restore from the protected rollback asset.

### FS-2.19-06 — Application writes occur after logical-replication cutover and rollback is requested

Freeze or control writes, quantify divergence, and execute the approved reverse-sync/data-reconciliation strategy. A pre-cutover backup alone does not contain the new writes.

### FS-2.19-07 — Backup retention cleanup removes old cluster too early

Stop automated cleanup, preserve remaining recovery assets, reassess rollback capability, and extend retention until production acceptance criteria are satisfied.

## 2.19.18 Recovery decision workflow

```text
Upgrade Incident
      ↓
Protect Both Cluster States
      ↓
Stop / Control Application Writes
      ↓
Determine Upgrade Method + Point of No Return
      ↓
Assess Old Cluster Reusability
      ↓
Assess New Cluster Recoverability
      ↓
Select Lowest-Risk Recovery Path
      ↓
Restore / Revert / Rebuild
      ↓
Database Integrity Validation
      ↓
Application Validation
      ↓
Controlled Traffic Restoration
```

## 2.19.19 Automation and IaC

An upgrade pipeline should fail closed unless recovery prerequisites are satisfied.

Automated gates can validate:

```text
Latest backup timestamp
Backup job status
Backup artifact existence
WAL archive health
Tablespace inventory coverage
Snapshot identifiers
Retention expiration
Restore-test timestamp
Required credentials/access
Recovery runbook version
```

Automation should record immutable evidence in the change record where possible.

Do not automate deletion of the old cluster as part of the same irreversible upgrade step. Retirement should occur only after a separate acceptance gate.

## 2.19.20 Production case study — successful backup, unusable recovery

A team enters a major-version maintenance window after the backup dashboard reports success. A rollback is later required, but the restore fails because a required extension package is unavailable on the recovery host and an external tablespace was not included in the recovery procedure.

Corrective actions:

```text
Restore-test complete services, not just backup files
Inventory extensions and external storage
Version-control recovery dependencies
Add tablespace coverage checks
Maintain tested recovery infrastructure
```

The lesson is that backup success and recoverability are different measurements.

## 2.19.21 Production case study — no post-upgrade backup

A major upgrade succeeds and the old cluster is retained temporarily, but no new-version backup baseline is created. Several days later a production error requires PITR. The organization discovers that the expected new-version backup/WAL workflow was never enabled after cutover.

Corrective actions include making post-upgrade backup activation a mandatory acceptance criterion, validating WAL archival immediately after startup, creating a new baseline, and performing a restore test before retiring the old recovery path.

## 2.19.22 Production readiness checklist

- [ ] Recovery owner assigned
- [ ] RPO/RTO documented for upgrade phases
- [ ] Pre-upgrade backup completed
- [ ] Backup artifact independently verified
- [ ] Restore test within policy
- [ ] PGDATA covered
- [ ] Tablespaces covered
- [ ] WAL/PITR architecture healthy
- [ ] Backup storage capacity healthy
- [ ] Backup encryption/access validated
- [ ] Upgrade-method rollback behavior documented
- [ ] Protected rollback copy created where required
- [ ] Logical-replication divergence strategy documented where applicable
- [ ] Recovery configuration dependencies captured
- [ ] Retention exceeds observation/rollback window
- [ ] Post-upgrade backup baseline planned
- [ ] Post-upgrade WAL archive validation planned
- [ ] Restore test for new cluster scheduled/automated
- [ ] Old recovery assets protected from premature deletion

## 2.19.23 SRE/DBRE takeaway

The production question is not:

```text
Did the backup job succeed?
```

It is:

```text
Can we recover the correct PostgreSQL service,
within the required RPO/RTO,
at every stage of this upgrade?
```

Upgrade readiness requires a verified pre-upgrade recovery point, method-aware rollback architecture, healthy WAL/PITR where required, complete tablespace coverage, protected recovery assets, and a new validated backup baseline after cutover.
