# 2.20 — Post-Upgrade Performance Monitoring and Stabilization

**Chapter:** PostgreSQL Installation, Configuration, Patching, and Upgrades  
**Status:** Production Ready / Complete  
**Validation baseline:** PostgreSQL 18 official documentation

## Purpose

A PostgreSQL upgrade is not operationally complete when the new server starts or when application traffic is restored. It is complete only after the database demonstrates stable correctness, performance, durability, replication health, and application behavior under representative production load.

This section defines the SRE/DBRE stabilization process after minor and major PostgreSQL upgrades. It complements the immediate functional validation in Section 2.13 by focusing on sustained workload behavior, regression detection, observability, acceptance gates, and evidence-based closure of the change.

## 2.20.1 Stabilization objectives

The post-upgrade stabilization period must answer five questions:

1. Is the database functionally correct under real application traffic?
2. Has workload performance returned to the approved baseline or an understood new baseline?
3. Are PostgreSQL background processes, WAL, checkpoints, vacuum, replication, and storage behaving normally?
4. Are there new query-plan, extension, configuration, or resource regressions?
5. Is the system sufficiently stable to close the change and retire rollback assets?

Do not declare an upgrade successful solely because PostgreSQL accepts connections.

## 2.20.2 Establish the pre-upgrade baseline

Before an upgrade, capture a workload baseline over a representative period. At minimum record:

- transactions per second and business request rate;
- query latency, including P50, P95, and P99 where available;
- top SQL by total execution time, mean execution time, calls, rows, and I/O;
- CPU utilization, run queue, memory pressure, swap activity, and load average;
- storage latency, IOPS, throughput, queue depth, and free capacity;
- PostgreSQL connection counts and session states;
- lock waits, deadlocks, and long-running transactions;
- WAL generation rate and checkpoint behavior;
- autovacuum and ANALYZE activity;
- replication lag and replication-slot retention;
- application error and timeout rates;
- backup/archive health;
- cache behavior and major read/write workload characteristics.

The baseline must include normal workload seasonality. Comparing a Monday peak after an upgrade with a Sunday maintenance window is not a meaningful performance comparison.

## 2.20.3 PostgreSQL 18 statistics behavior after pg_upgrade

PostgreSQL 18 changes an important historical upgrade behavior: `pg_upgrade` transfers most optimizer statistics unless `--no-statistics` is specified.

However, not every statistic is transferred. Extended statistics created with `CREATE STATISTICS`, extension-defined custom statistics, and cumulative runtime statistics are examples that require separate consideration. PostgreSQL therefore still instructs administrators to regenerate missing and cumulative information after the upgrade.

A production workflow should include the post-upgrade commands generated or recommended by `pg_upgrade`. For optimizer statistics, PostgreSQL 18 documents the staged approach:

```bash
vacuumdb --all --analyze-in-stages --missing-stats-only
vacuumdb --all --analyze-only
```

Do not blindly replace the output or instructions generated by the actual `pg_upgrade` run with a static runbook. Preserve and review the generated post-upgrade scripts and output for the specific cluster.

## 2.20.4 Validate statistics and planner readiness

Check that important application relations have usable statistics and that critical extended-statistics objects have been recollected as required.

Useful checks include:

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_analyze,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC;
```

Review extended statistics definitions:

```sql
SELECT schemaname,
       statistics_name,
       tablename,
       attnames,
       exprs
FROM pg_stats_ext
ORDER BY schemaname, tablename, statistics_name;
```

Where workload behavior or PostgreSQL instructions require it, run targeted `ANALYZE` rather than waiting for a performance incident:

```sql
ANALYZE VERBOSE schema_name.table_name;
```

For partitioned tables, validate parent-level statistics explicitly. PostgreSQL documentation notes that autovacuum does not automatically analyze a partitioned parent merely because its partitions changed, so manual `ANALYZE` may be necessary.

## 2.20.5 Monitor database activity

Use `pg_stat_activity` to understand current sessions, transaction age, wait events, and long-running work:

```sql
SELECT pid,
       usename,
       datname,
       application_name,
       client_addr,
       state,
       wait_event_type,
       wait_event,
       xact_start,
       query_start,
       state_change,
       query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY query_start NULLS LAST;
```

Pay particular attention to:

- unexpected connection growth;
- sessions stuck `idle in transaction`;
- new wait-event patterns;
- long-running transactions;
- application reconnect storms;
- background-worker failures;
- sessions connected to the wrong database endpoint after cutover.

## 2.20.6 Compare database-level workload metrics

`pg_stat_database` provides a high-level view of workload and failure behavior:

```sql
SELECT datname,
       numbackends,
       xact_commit,
       xact_rollback,
       blks_read,
       blks_hit,
       tup_returned,
       tup_fetched,
       tup_inserted,
       tup_updated,
       tup_deleted,
       conflicts,
       deadlocks,
       temp_files,
       temp_bytes
FROM pg_stat_database
WHERE datname IS NOT NULL;
```

Use rates and deltas rather than interpreting cumulative counters as instantaneous values. Record the statistics-reset timestamp so comparisons are valid.

## 2.20.7 Query performance and pg_stat_statements

Where approved and installed, `pg_stat_statements` is one of the most useful tools for detecting SQL regressions. It tracks planning and execution statistics for SQL statements. The module must be configured through `shared_preload_libraries`, which requires a restart when adding or removing it.

Example regression review:

```sql
SELECT queryid,
       calls,
       total_exec_time,
       mean_exec_time,
       rows,
       shared_blks_hit,
       shared_blks_read,
       temp_blks_written,
       query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 25;
```

Compare the same business workload before and after the upgrade. Investigate material changes in:

- mean and tail latency;
- total execution time;
- execution count;
- shared-buffer reads;
- temporary-file usage;
- WAL generated by write-heavy statements where available;
- planner behavior and plan shape.

A different execution plan is not automatically a regression. Evaluate runtime, resource consumption, cardinality estimates, concurrency behavior, and workload impact.

## 2.20.8 Investigate query-plan regressions

For a suspected regression, capture the plan safely:

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT ...;
```

`EXPLAIN ANALYZE` executes the statement. Never run it casually against destructive or high-impact production SQL. For write statements, use a safe test environment or a carefully controlled transaction only when rollback semantics and side effects are fully understood.

Compare:

- scan methods;
- join order and join algorithms;
- estimated versus actual rows;
- buffer reads and hits;
- temporary spill behavior;
- parallel execution;
- changed planner settings;
- index availability and validity;
- statistics quality.

Do not respond to every plan change by disabling planner features globally. Correct stale statistics, configuration drift, invalid indexes, schema differences, or workload-specific issues first.

## 2.20.9 PostgreSQL 18 I/O observability

PostgreSQL 18 provides detailed cumulative I/O statistics through `pg_stat_io` and expands I/O observability, including additional byte-level and backend-related information.

Use it to determine whether a post-upgrade slowdown is driven by database I/O behavior rather than SQL alone:

```sql
SELECT *
FROM pg_stat_io
ORDER BY backend_type, object, context;
```

Correlate PostgreSQL counters with operating-system or cloud storage metrics such as latency, throughput, IOPS, throttling, queue depth, burst balance, and filesystem capacity.

## 2.20.10 WAL and checkpoint stabilization

Review WAL generation and checkpoint behavior after traffic is restored:

```sql
SELECT * FROM pg_stat_wal;
SELECT * FROM pg_stat_checkpointer;
```

Investigate unexpected changes in:

- WAL bytes generated per unit of workload;
- checkpoint frequency;
- checkpoint write/sync time;
- write amplification;
- archive backlog;
- replica replay lag;
- retained WAL caused by slots or disconnected replicas.

A workload can appear healthy at the application layer while silently accumulating WAL or archive risk.

## 2.20.11 Locking and concurrency

Review lock contention during stabilization:

```sql
SELECT a.pid,
       a.usename,
       a.state,
       a.wait_event_type,
       a.wait_event,
       a.xact_start,
       a.query_start,
       pg_blocking_pids(a.pid) AS blocking_pids,
       a.query
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0
ORDER BY a.query_start;
```

Escalate unexpected blocker chains, deadlocks, long transactions, DDL lock waits, or transaction-age growth. An upgrade may expose changed application concurrency, connection-pool behavior, or previously hidden slow plans.

## 2.20.12 Autovacuum and table health

Validate that autovacuum workers are operating and that transaction-ID protection is healthy:

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_vacuum,
       last_autovacuum,
       last_analyze,
       last_autoanalyze,
       autovacuum_count,
       autoanalyze_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Also monitor database and relation transaction ages. Never disable autovacuum as a generic response to post-upgrade CPU or I/O load. Diagnose the workload and tune deliberately.

## 2.20.13 Replication stabilization

For physical streaming replication, validate sender state and lag:

```sql
SELECT application_name,
       client_addr,
       state,
       sync_state,
       write_lag,
       flush_lag,
       replay_lag
FROM pg_stat_replication;
```

For logical replication, review subscription workers and statistics using the PostgreSQL 18 monitoring views appropriate to the topology.

Validate:

- all expected replicas are connected;
- synchronous standbys satisfy the intended policy;
- replay progresses continuously;
- replication slots are active as expected;
- retained WAL does not grow without bound;
- logical subscriptions have no unexpected apply errors;
- failover tooling sees the correct primary and replicas.

## 2.20.14 Application-level stabilization

Database health must be correlated with application health. Track:

- HTTP/gRPC error rates;
- database connection failures;
- transaction retries;
- request latency percentiles;
- job or queue backlog;
- connection-pool saturation;
- ORM/driver errors;
- authentication/TLS failures;
- business transaction success rates.

The database may report normal CPU and TPS while a specific application path is failing because of changed SQL behavior, permissions, extensions, drivers, or connection routing.

## 2.20.15 Configuration-drift validation

Compare the effective post-upgrade configuration with the approved configuration rather than only comparing configuration files.

Useful queries include:

```sql
SELECT name, setting, unit, source, sourcefile, sourceline, pending_restart
FROM pg_settings
ORDER BY name;
```

Review especially:

- memory settings;
- WAL and checkpoint settings;
- autovacuum parameters;
- connection limits;
- planner parameters;
- logging and statistics settings;
- replication settings;
- `shared_preload_libraries`;
- TLS/authentication-related configuration;
- parameters that changed defaults between major releases.

Do not copy an old `postgresql.conf` wholesale into a new major release. Reconcile settings against the new version and preserve an auditable configuration baseline.

## 2.20.16 Stabilization windows

Define the stabilization window before the change. A typical production process uses multiple gates:

**Immediate gate — first 15–30 minutes**

- PostgreSQL remains available;
- application connectivity succeeds;
- no critical database errors;
- replicas reconnect;
- WAL/archive flow is healthy;
- core transactions succeed.

**Short gate — first 1–4 hours**

- latency and throughput remain within agreed thresholds;
- no growing lock, WAL, storage, connection, or replication backlog;
- top SQL is understood;
- no persistent application-error increase.

**Workload-cycle gate — one representative peak period**

- peak traffic is handled normally;
- batch/ETL/reporting jobs succeed;
- maintenance processes behave normally;
- backups and archiving complete successfully.

**Final acceptance gate**

- no unresolved severity-1/2 upgrade issue;
- SLOs are satisfied;
- regression exceptions have owners and approved remediation;
- recovery assets remain valid until the rollback deadline;
- monitoring evidence is attached to the change record.

The exact durations must follow the organization's workload, RTO/RPO, change policy, and risk classification.

## 2.20.17 Suggested alerting during stabilization

Temporarily tighten observation after an upgrade, but avoid creating noisy alerts without operational meaning. High-value conditions include:

- database unavailable;
- sustained application database errors;
- P95/P99 latency regression beyond approved tolerance;
- CPU saturation or sustained run-queue pressure;
- storage latency or throttling;
- filesystem capacity risk;
- connection saturation;
- long-running or idle-in-transaction sessions;
- deadlock increase;
- blocking exceeding the service threshold;
- replica lag or disconnected standby;
- inactive or unexpectedly retained replication slot;
- WAL archive failure;
- abnormal checkpoint behavior;
- transaction-ID age risk;
- failed backup or restore-validation job.

Thresholds should be based on service objectives and established workload baselines, not universal fixed numbers.

## 2.20.18 Rollback and remediation decision model

A performance regression does not always require immediate rollback. Classify it.

**Rollback candidate**

- correctness or durability risk;
- sustained SLO breach with no safe mitigation;
- severe application incompatibility;
- unrecoverable replication/HA failure within the change window;
- security or authentication failure affecting service availability;
- rapidly increasing resource condition likely to cause outage.

**Remediation candidate**

- isolated query-plan regression with a safe correction;
- missing statistics;
- configuration drift;
- extension configuration issue;
- connection-pool tuning issue;
- non-critical monitoring or logging gap.

The rollback procedure must follow the upgrade method documented in Section 2.14. In particular, `pg_upgrade` copy, link, clone, and swap modes have different implications for the usability of the old cluster. Never assume the old data directory is a valid rollback target without confirming the selected upgrade method and whether the new cluster has been started or files have been transferred.

## 2.20.19 Failure scenarios

### Scenario A — P99 latency rises after cutover

1. Confirm application traffic and connection routing.
2. Compare top SQL before and after the upgrade.
3. Check plan changes and cardinality estimates.
4. Validate statistics, including extended statistics.
5. Check I/O, temporary spills, CPU, locks, and concurrency.
6. Apply the smallest safe remediation.
7. Roll back only if the regression breaches the defined backout criteria.

### Scenario B — CPU increases but TPS does not

Investigate query-plan changes, repeated reconnect/authentication work, parallelism, background maintenance, extension behavior, and increased calls per business transaction. CPU alone does not identify the cause.

### Scenario C — replica lag grows after upgrade

Check WAL generation, network/storage latency, replay wait events, replica resource pressure, long-running replica queries, slots, and HA configuration. Confirm that the replica was upgraded/rebuilt using a supported procedure.

### Scenario D — performance degrades while statistics appear present

Remember that PostgreSQL 18 `pg_upgrade` preserves most optimizer statistics, not every statistics category. Check extended statistics, cumulative statistics, schema changes, indexes, configuration, and representative plans before concluding that statistics are complete.

### Scenario E — storage consumption grows unexpectedly

Check WAL retention, archive failures, inactive slots, temporary files, logging volume, relation growth, and upgrade artifacts. Do not delete WAL or PostgreSQL data files manually.

## 2.20.20 Automation

Automate evidence collection where practical. A post-upgrade job can capture:

- PostgreSQL version and recovery role;
- effective configuration and pending-restart settings;
- database and connection statistics;
- top SQL statistics;
- I/O, WAL, checkpoint, vacuum, and replication statistics;
- lock/blocking state;
- transaction-age indicators;
- extension inventory and versions;
- storage capacity;
- backup/archive status;
- application SLO metrics.

Store snapshots with timestamps and change identifiers so pre/post comparisons are reproducible.

Automation must not automatically execute high-risk tuning, terminate sessions, rebuild indexes, drop replication slots, or initiate rollback merely because a threshold is crossed. Those actions require context and controlled operational policy.

## 2.20.21 Production acceptance checklist

Before marking stabilization complete, verify:

- [ ] PostgreSQL version and cluster identity are correct.
- [ ] Application connectivity and business transactions are healthy.
- [ ] Error rate is at or below the approved threshold.
- [ ] P50/P95/P99 latency is within the approved baseline or exception.
- [ ] Throughput is consistent with expected workload.
- [ ] Top SQL regressions have been reviewed.
- [ ] Required post-upgrade statistics work is complete.
- [ ] CPU, memory, I/O, and storage are stable.
- [ ] WAL generation and checkpoints are healthy.
- [ ] No unexplained blocker chains or deadlock increase exists.
- [ ] Autovacuum and transaction-age protection are healthy.
- [ ] Physical/logical replication is healthy where applicable.
- [ ] Replication slots are understood and bounded.
- [ ] WAL archiving and backup jobs are healthy.
- [ ] Effective configuration has been reconciled.
- [ ] Extensions and preload libraries are healthy.
- [ ] Monitoring and alerting are operational.
- [ ] A representative peak workload has completed successfully.
- [ ] Rollback assets are retained until the approved backout deadline.
- [ ] Change evidence and residual risks are documented.

## 2.20.22 SRE/DBRE production principles

1. **Startup is not success.** Stabilization is part of the upgrade.
2. **Baseline before changing.** Without a baseline, regression claims are weak.
3. **Use rates, percentiles, and workload context.** Raw cumulative counters can mislead.
4. **Correlate database, host, storage, and application telemetry.** PostgreSQL metrics alone do not describe the full service.
5. **Treat statistics as an explicit upgrade concern.** PostgreSQL 18 improves preservation, but not every statistics category is transferred.
6. **Do not tune by folklore.** Diagnose the bottleneck and test the remediation.
7. **Keep rollback constraints visible.** Upgrade mode determines what backout options remain safe.
8. **Require evidence before closure.** Production readiness is a measurable gate, not a declaration.
