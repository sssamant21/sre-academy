# 2.23 — Log Management, Diagnostics, and Operational Troubleshooting

**Status:** Production Ready / Complete

PostgreSQL logs and runtime statistics are complementary sources of production evidence. Logs explain events, failures, checkpoints, authentication problems, long-running statements, lock-related behavior, recovery activity, and maintenance operations, while statistics views describe the current and cumulative state of the database. A production SRE/DBRE operating model must collect both without allowing observability itself to create a reliability, security, or storage incident.

## 2.23.1 Operational evidence architecture

```text
Application Symptoms
        ↓
PostgreSQL Logs + Runtime Statistics
        ↓
Host / Storage / Network Telemetry
        ↓
Query and Lock Analysis
        ↓
Root-Cause Hypothesis
        ↓
Controlled Remediation
        ↓
Validation + Incident Evidence
```

Never troubleshoot PostgreSQL from a single metric or log line when correlated evidence is available.

## 2.23.2 PostgreSQL logging destinations

PostgreSQL supports logging to destinations including `stderr`, `csvlog`, `jsonlog`, and `syslog`; Windows can also use `eventlog`.

Example:

```conf
log_destination = 'stderr,jsonlog'
logging_collector = on
```

Choose the destination according to the organization's log pipeline, parser, retention, security, and incident-response requirements.

Structured formats such as JSON or CSV can simplify centralized ingestion, but the logging design must be load-tested and monitored.

## 2.23.3 Logging collector

When `logging_collector` is enabled, PostgreSQL captures messages sent to stderr and writes them to log files.

```conf
logging_collector = on
log_directory = 'log'
log_filename = 'postgresql-%Y-%m-%d_%H%M%S.log'
```

`logging_collector` is a server-start setting. Treat changes to it as restart-requiring configuration changes.

## 2.23.4 Log rotation and filesystem protection

A production logging policy must prevent PostgreSQL logs from exhausting the filesystem.

Review:

```conf
log_rotation_age = '1d'
log_rotation_size = '100MB'
```

Values are environment-specific. Monitor log volume and filesystem headroom rather than relying only on rotation configuration.

If logs share storage with database data or WAL, log growth can become a database availability event. Prefer an architecture where log retention cannot silently consume critical PGDATA or WAL capacity.

## 2.23.5 Log permissions and sensitive information

PostgreSQL logs can contain usernames, database names, client addresses, SQL text, object names, errors, and potentially application data or bind parameters depending on configuration.

Keep log files and centralized log systems access-controlled. Avoid world-readable PostgreSQL logs.

Do not enable verbose SQL or parameter logging without a privacy and security review.

## 2.23.6 Production log identity

Use `log_line_prefix` or structured logging fields to make events attributable.

A useful operational identity can include:

```text
timestamp
process ID
session ID
user
database
application name
client address
transaction ID where useful
query ID where useful
```

The exact prefix must fit the log platform and security requirements.

PostgreSQL 18 also adds additional logging capabilities such as client IP output through the `%L` log-line-prefix escape.

## 2.23.7 Connection diagnostics

PostgreSQL 18 provides more granular `log_connections` configuration than earlier boolean-only behavior.

Connection troubleshooting should correlate:

```text
DNS / network reachability
TLS negotiation
authentication
pg_hba.conf match
role state
database CONNECT privilege
connection pool behavior
server connection capacity
```

Do not interpret every connection failure as a database outage.

## 2.23.8 Slow-query logging

`log_min_duration_statement` can log statements whose execution exceeds a configured duration.

Example:

```conf
log_min_duration_statement = '1s'
```

The threshold must reflect workload characteristics and observability capacity. Setting it too low on a busy system can generate excessive log volume and overhead.

Use slow-query logs together with `pg_stat_statements`, `EXPLAIN`, application traces, and host/storage telemetry.

## 2.23.9 Query identifiers

PostgreSQL can compute query identifiers through `compute_query_id`, allowing correlation across statistics, `EXPLAIN`, and logs when configured appropriately.

```conf
compute_query_id = auto
```

Query IDs are especially useful for grouping normalized workload behavior without depending only on raw SQL text.

## 2.23.10 Error logging

Review settings such as:

```text
log_min_messages
log_min_error_statement
log_error_verbosity
```

Higher verbosity can be useful during incident investigation but can increase log volume and potentially expose more context.

Use temporary diagnostic increases deliberately and return to the approved baseline after the incident.

## 2.23.11 Checkpoint and WAL diagnostics

Checkpoint and WAL behavior should be correlated with database latency and storage telemetry.

PostgreSQL can log checkpoint activity, and runtime statistics provide additional evidence through views such as:

```text
pg_stat_checkpointer
pg_stat_wal
pg_stat_io
```

Investigate spikes in write latency, WAL generation, checkpoint pressure, storage queueing, and application latency together.

## 2.23.12 Lock diagnostics

When sessions appear hung or transactions time out, identify blockers rather than terminating random backends.

Useful sources include:

```text
pg_stat_activity
pg_locks
pg_blocking_pids()
```

Example:

```sql
SELECT pid,
       usename,
       datname,
       state,
       wait_event_type,
       wait_event,
       query_start,
       query
FROM pg_stat_activity
WHERE state <> 'idle';
```

PostgreSQL 18 also provides `log_lock_failures` for supported lock acquisition failures, adding another diagnostic signal where appropriate.

## 2.23.13 Long-running and idle transactions

Long transactions can affect vacuum, row-version cleanup, transaction ID horizons, replication behavior, and operational maintenance.

Inspect transaction age:

```sql
SELECT pid,
       usename,
       datname,
       state,
       xact_start,
       now() - xact_start AS transaction_age,
       wait_event_type,
       wait_event,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Treat `idle in transaction` sessions as application or operational defects when they remain open beyond the expected transaction lifecycle.

## 2.23.14 Autovacuum diagnostics

Correlate:

```text
pg_stat_all_tables
pg_stat_progress_vacuum
PostgreSQL logs
transaction age
replication slots
long transactions
storage I/O
```

Enable and tune autovacuum logging deliberately where additional visibility is required.

Do not disable autovacuum to suppress load or log noise.

## 2.23.15 Progress reporting

PostgreSQL 18 exposes progress views for operations including:

```text
ANALYZE
CLUSTER
COPY
CREATE INDEX
VACUUM
BASE_BACKUP
```

Use progress views before concluding that a long maintenance operation is stalled.

## 2.23.16 I/O diagnostics

PostgreSQL 18 provides detailed cumulative I/O statistics through `pg_stat_io`, alongside host-level tools such as `iostat`, `vmstat`, and platform storage metrics.

A production investigation should answer:

```text
Is latency CPU-bound?
Is the workload waiting on storage?
Is WAL I/O the bottleneck?
Are checkpoints driving writes?
Is vacuum or maintenance competing for I/O?
Is the operating system swapping?
Is the storage service throttling?
```

Database and host telemetry must be correlated before tuning PostgreSQL parameters.

## 2.23.17 Replication diagnostics

For physical and logical replication, investigate:

```text
pg_stat_replication
pg_stat_wal_receiver
pg_stat_replication_slots
pg_stat_subscription
pg_stat_subscription_stats
pg_stat_archiver
PostgreSQL logs
network telemetry
WAL generation and retention
```

Replication lag is a symptom, not a root cause. Determine whether lag originates from WAL generation, network transfer, receiver behavior, replay, storage latency, conflicts, locks, or subscriber workload.

## 2.23.18 Recovery diagnostics

During startup or crash recovery, do not repeatedly restart PostgreSQL because recovery appears slow.

Inspect PostgreSQL logs, recovery progress signals, storage performance, WAL availability, archive restore behavior, and host health.

`log_startup_progress_interval` can provide progress messages for supported long-running startup operations.

## 2.23.19 Disk-full diagnostics

A full filesystem can prevent PostgreSQL from writing data, WAL, temporary files, or logs.

Validate:

```bash
df -h
df -i
```

Then identify the affected PostgreSQL path:

```text
PGDATA
pg_wal
tablespace
log directory
temporary-file location
archive destination
backup staging area
```

Do not delete PostgreSQL internal files manually to recover emergency space.

## 2.23.20 Temporary-file diagnostics

Large sorts, hashes, materialization, index operations, or other workloads can create temporary files when memory is insufficient for an operation.

Monitor temporary-file behavior through database statistics and configured logging. Investigate workload, plans, concurrency, and memory configuration before simply increasing `work_mem` globally.

## 2.23.21 Diagnostic SQL toolkit

### Active sessions

```sql
SELECT pid, usename, datname, application_name,
       client_addr, state, wait_event_type, wait_event,
       xact_start, query_start, query
FROM pg_stat_activity
ORDER BY query_start NULLS LAST;
```

### Blocking relationships

```sql
SELECT pid,
       pg_blocking_pids(pid) AS blocking_pids,
       query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

### Database-level activity

```sql
SELECT datname,
       numbackends,
       xact_commit,
       xact_rollback,
       blks_read,
       blks_hit,
       temp_files,
       temp_bytes,
       deadlocks
FROM pg_stat_database
ORDER BY datname;
```

### Table health

```sql
SELECT schemaname,
       relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

These are diagnostic starting points, not substitutes for workload-specific analysis.

## 2.23.22 Troubleshooting workflow

```text
Detect Symptom
      ↓
Define Blast Radius
      ↓
Check Recent Changes
      ↓
Inspect PostgreSQL Logs
      ↓
Inspect pg_stat_activity / Waits / Locks
      ↓
Inspect Database Statistics
      ↓
Inspect CPU / Memory / Disk / Network
      ↓
Correlate Application Telemetry
      ↓
Form Root-Cause Hypothesis
      ↓
Apply Lowest-Risk Mitigation
      ↓
Validate Recovery
      ↓
Perform RCA and Permanent Fix
```

Avoid changing multiple PostgreSQL settings simultaneously during an incident unless the recovery plan specifically requires it.

## 2.23.23 Failure scenarios

### FS-2.23-01 — PostgreSQL log filesystem fills

Protect database availability first. Determine log-growth source, preserve required incident evidence, rotate/archive safely, restore headroom, and correct logging or retention configuration. Do not delete WAL or database relation files.

### FS-2.23-02 — Slow-query logging overwhelms log pipeline

Raise or disable the temporary diagnostic threshold through the approved change path, preserve representative evidence, verify database and log-pipeline health, then use targeted statistics and sampling for deeper investigation.

### FS-2.23-03 — Application sessions appear hung

Check wait events and blocking relationships. Identify the root blocker and transaction owner before considering cancellation or termination. Preserve SQL, transaction age, lock graph, and application context for RCA.

### FS-2.23-04 — PostgreSQL startup appears stuck

Inspect startup/recovery logs and storage/WAL state. Do not repeatedly kill and restart the server. Determine whether recovery, synchronization, WAL restore, or storage latency is progressing.

### FS-2.23-05 — Replication lag rises rapidly

Compare WAL generation, sender/receiver state, replay position, slot retention, network health, storage latency, and standby workload. Avoid rebuilding the replica until the actual failure mode is understood.

### FS-2.23-06 — Disk usage grows unexpectedly

Identify whether growth comes from relations, indexes, WAL, replication slots, temporary files, logs, tablespaces, or backups. Apply component-specific remediation rather than generic file deletion.

### FS-2.23-07 — High CPU after deployment

Correlate deployment time with `pg_stat_activity`, `pg_stat_statements`, query plans, connection count, waits, and application traffic. Roll back or mitigate the application/database change according to impact and evidence.

### FS-2.23-08 — Monitoring query causes production overhead

Stop or reduce the expensive monitoring workload, identify the collector/query responsible, optimize collection frequency and SQL, and enforce an observability budget.

## 2.23.24 Monitoring the monitoring system

Observability components themselves can fail or overload PostgreSQL.

Monitor:

```text
Exporter query duration
Monitoring connection count
Log collector health
Log shipping lag
Telemetry ingestion lag
Monitoring storage growth
Dashboard freshness
Alert delivery failures
```

Do not assume silence means health when the monitoring pipeline itself may be broken.

## 2.23.25 Alert design

Alerts should identify actionable reliability conditions rather than every metric deviation.

High-value categories include:

```text
Database unavailable
Storage critical
WAL/archive failure
Replication unhealthy
Backup failure
Long blocking chain
Transaction age / wraparound risk
Connection exhaustion
Abnormal error rate
Sustained latency regression
Autovacuum failure or severe backlog
Monitoring pipeline failure
```

Use warning and critical thresholds that reflect workload baselines, capacity, RPO/RTO, and operational response time.

## 2.23.26 Automation

Automate evidence collection for common incidents without automating destructive remediation blindly.

A diagnostic bundle can collect:

```text
PostgreSQL version
uptime
configuration identity
pg_stat_activity
blocking relationships
pg_stat_database
pg_stat_io
pg_stat_wal
replication state
archiver state
vacuum health
filesystem utilization
CPU / memory / I/O summary
recent PostgreSQL errors
recent deployment/change metadata
```

Sanitize credentials, SQL text, bind values, and sensitive application data before storing or sharing diagnostic bundles.

## 2.23.27 Production case study — blocking transaction mistaken for database outage

Application requests begin timing out. CPU and storage remain normal, but several sessions wait on locks. `pg_blocking_pids()` identifies one long-running transaction holding the required lock while its application session is idle in transaction.

The SRE team captures the blocker, transaction age, SQL, affected sessions, and application owner; performs the approved termination; validates transaction recovery; and works with the application team to correct transaction handling and timeout policy.

The lesson: diagnose waits before scaling infrastructure or restarting PostgreSQL.

## 2.23.28 Production case study — observability causes disk pressure

A temporary troubleshooting change lowers `log_min_duration_statement` dramatically during peak traffic. Log volume rises rapidly and threatens the filesystem.

The immediate mitigation is to restore the approved threshold and recover log-storage headroom. The permanent corrective action introduces time-bounded diagnostic configuration, log-volume alerts, centralized retention controls, and a change checklist requiring observability-impact review.

## 2.23.30 SRE/DBRE takeaway

Production PostgreSQL troubleshooting should be evidence-driven:

```text
Logs tell you what happened.
Statistics tell you what PostgreSQL is doing.
Waits tell you what work is blocked on.
Host telemetry tells you what the platform is doing.
Application telemetry tells you what users experience.
```

The strongest diagnosis comes from correlating all five.

Observability must also be engineered as a production workload. Logging, statistics collection, exporters, and diagnostic queries should provide enough evidence for rapid incident response without becoming a new source of CPU pressure, I/O pressure, security exposure, or disk exhaustion.
