# 2.24 — Production Operations Checklist and Chapter Runbook

**Status:** Production Ready / Complete

This section closes Chapter 2 by converting installation, configuration, patching, upgrades, validation, maintenance, monitoring, backup/recovery, HA, and troubleshooting into a repeatable SRE/DBRE operating model.

## 2.24.1 Production lifecycle

```text
Plan
  ↓
Install / Provision
  ↓
Initialize
  ↓
Configure
  ↓
Validate
  ↓
Protect with Backup + HA
  ↓
Observe
  ↓
Maintain / Patch
  ↓
Upgrade
  ↓
Validate + Stabilize
  ↓
Continuously Improve
```

A PostgreSQL production deployment is not complete when the server merely accepts connections. It is complete when its configuration, security, durability, observability, recovery, maintenance, and change-management controls are validated and owned.

## 2.24.2 Installation acceptance gate

Verify before production onboarding:

- approved PostgreSQL major/minor version
- supported operating system and architecture
- trusted package/source provenance
- PostgreSQL service account ownership
- PGDATA identity and permissions
- WAL and tablespace locations
- filesystem capacity and inode headroom
- data checksums state
- locale and encoding
- server startup/shutdown behavior
- configuration-file locations
- extensions and shared libraries
- network/listener configuration
- TLS/authentication policy

Example validation:

```sql
SELECT version();
SHOW data_directory;
SHOW config_file;
SHOW hba_file;
SHOW server_encoding;
SHOW data_checksums;
```

## 2.24.3 Configuration acceptance gate

Production configuration must be declared, reviewed, version controlled, and runtime-verified.

Validate:

```sql
SELECT name,
       setting,
       unit,
       source,
       sourcefile,
       sourceline,
       context,
       pending_restart
FROM pg_settings
ORDER BY name;
```

Review configuration-file errors before reload where possible using `pg_file_settings`, and validate HBA/identity mapping rules using PostgreSQL's inspection views.

Do not consider a configuration change successful solely because automation updated a file.

## 2.24.4 Security gate

Confirm:

```text
Least-privilege database roles

TLS policy
Credential/secret management
Administrative access path
Audit/logging requirements
```

Authentication, network controls, database privileges, and operating-system permissions must be treated as layered controls.

## 2.24.5 Durability and WAL gate

Review the production durability architecture:

```text

full_page_writes
synchronous_commit
wal_level
checkpoint configuration
WAL capacity
WAL archive configuration
archive health
replication requirements
storage durability
```

Do not weaken durability parameters as an undocumented performance optimization.

## 2.24.6 Backup and recovery gate

PostgreSQL documentation describes SQL dump, filesystem-level backup, and continuous archiving/PITR as fundamental backup approaches. Production design should use the method or combination that satisfies business RPO/RTO.

Operational requirements:

- scheduled backups
- WAL archive monitoring where PITR is required
- backup retention policy
- off-host/off-failure-domain protection as required
- encryption/access control
- tablespace coverage
- restore automation
- restore testing
- documented recovery targets
- post-restore validation

A backup is not operationally trusted until recovery has been tested.

## 2.24.7 HA and replication gate

For HA deployments validate:

```text
Primary identity
Standby identity
Streaming state
Replication lag
Replication slots
Synchronous replication policy
Failover mechanism
Fencing / split-brain protection
Client routing
Standby storage topology
Backup behavior during failover
Monitoring and alerting
```

Perform controlled failover exercises before declaring the platform production-ready.

## 2.24.8 Monitoring baseline

PostgreSQL 18 provides extensive cumulative and dynamic monitoring facilities. The production baseline should include:

```text
pg_stat_activity
pg_stat_database
pg_stat_io
pg_stat_wal
pg_stat_checkpointer
pg_stat_bgwriter
pg_stat_replication
pg_stat_replication_slots
pg_stat_archiver
pg_stat_all_tables
pg_stat_all_indexes
lock monitoring
progress views
```

Where approved, use `pg_stat_statements` for workload-level query analysis.

Host telemetry should include CPU, memory, storage capacity, I/O latency, filesystem state, network health, process health, and operating-system events.

## 2.24.9 Alerting baseline

Alert on symptoms that require action rather than every metric movement.

Core conditions include:

- PostgreSQL unavailable
- connection exhaustion
- excessive query latency
- lock/blocking incident
- long transaction
- idle-in-transaction session
- filesystem capacity risk
- inode exhaustion risk
- abnormal I/O latency
- replication lag
- replication slot WAL retention
- WAL archive failure
- backup failure
- autovacuum/freeze risk
- XID/multixact age risk
- checksum/storage errors
- repeated crash/recovery
- unexpected configuration drift

Every critical alert should map to an owner and runbook.

## 2.24.11 VACUUM and wraparound protection

Autovacuum should normally remain enabled. PostgreSQL vacuuming is required for tuple-space reuse, planner statistics, visibility-map maintenance, and transaction/multixact wraparound protection.

Monitor table and database age and investigate long transactions, abandoned replication slots, or configuration that prevents vacuum progress.

Do not wait for an anti-wraparound emergency before treating age as an operational risk.

## 2.24.12 Patch runbook

For minor-version patching:

```text
Review release notes
      ↓
Assess security / bug impact
      ↓
Validate extension/package compatibility
      ↓
Confirm backup + recovery
      ↓
Test in representative environment
      ↓
Schedule maintenance / HA strategy
      ↓
Update binaries/packages
      ↓
Restart as required
      ↓
Validate version + database health
      ↓
Observe application and platform
```

Minor-version updates within a PostgreSQL major release normally preserve on-disk compatibility, but release notes and required post-update actions must still be reviewed.

## 2.24.13 Major-upgrade runbook

Choose an approved architecture:

```text
Dump / Restore
pg_upgrade
Logical-replication migration
```

Production major upgrades require:

- compatibility assessment
- application certification
- extension validation
- storage/capacity planning
- `pg_upgrade --check` where applicable
- backup and PITR readiness
- rollback design
- rehearsal
- timed runbook
- HA/replication plan
- cutover/fencing plan
- post-upgrade validation
- stabilization window

Never make the first full-scale execution the production maintenance window.

## 2.24.15 Troubleshooting framework

Use a consistent sequence:

```text
Detect
  ↓
Protect availability/data
  ↓
Establish timeline
  ↓
Identify recent changes
  ↓
Collect PostgreSQL evidence
  ↓
Collect OS/storage/network evidence
  ↓
Form and test hypotheses
  ↓
Mitigate
  ↓
Validate recovery
  ↓

  ↓

```

Do not begin by randomly changing PostgreSQL parameters during an incident.

## 2.24.16 Core diagnostic SQL

Current activity:

```sql
SELECT pid,
       usename,
       datname,
       application_name,
       client_addr,
       state,
       wait_event_type,
       wait_event,
       xact_start,
       query_start,
       query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY query_start NULLS LAST;
```

Long transactions:

```sql
SELECT pid,
       usename,
       datname,
       state,
       now() - xact_start AS xact_age,
       query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Database activity:

```sql
SELECT datname,
       numbackends,
       xact_commit,
       xact_rollback,
       blks_read,
       blks_hit,
       temp_files,
       temp_bytes,
       deadlocks
FROM pg_stat_database
ORDER BY datname;
```

Replication:

```sql
SELECT application_name,
       client_addr,
       state,
       sync_state,
       write_lag,
       flush_lag,
       replay_lag
FROM pg_stat_replication;
```

These queries are starting points; interpretation must account for workload and architecture.

## 2.24.17 Incident severity model

A practical DBRE classification:

```text
SEV-1  Data integrity risk or broad production outage
SEV-2  Major degradation / HA or recovery protection impaired
SEV-3  Limited degradation with workaround
SEV-4  Non-urgent defect, maintenance, or optimization
```

Severity definitions should ultimately align with organizational incident policy and business SLOs.

## 2.24.18 Production failure scenarios

### FS-2.24-01 — Database unavailable after maintenance

Protect data state, inspect service/PostgreSQL logs, validate configuration and storage mounts, confirm port/process state, determine whether startup entered crash recovery, and execute the approved rollback if recovery exceeds the change window.

### FS-2.24-02 — Connection exhaustion

Preserve administrative access, identify connection sources and session states, inspect long/idle transactions, check pooling/retry behavior, and avoid blindly increasing `max_connections` without memory/capacity analysis.

### FS-2.24-03 — Disk usage grows unexpectedly

Determine whether growth comes from relations, WAL, retained replication slots, logs, temporary files, tablespaces, or another filesystem consumer. Protect WAL/PGDATA headroom first, then remediate the root cause.

### FS-2.24-04 — Replication lag after change

Inspect primary WAL generation, standby receive/write/flush/replay state, network/storage performance, long-running standby queries, configuration changes, and replication-slot state before choosing a corrective action.

### FS-2.24-05 — Query latency regression

Compare workload, execution plans, statistics, locks, I/O, cache behavior, CPU, memory, configuration, and recent schema/index changes. Use the pre-change baseline when available.

### FS-2.24-06 — Backup succeeds but restore fails

Treat this as loss of recovery assurance. Preserve evidence, repair the backup process, perform a new backup, repeat the restore test, and do not mark recovery controls healthy until the restored database is validated.

### FS-2.24-07 — Autovacuum cannot keep up

Identify the affected relations, dead-tuple/update rate, long transactions, freeze age, worker availability, I/O constraints, and table-specific configuration. Tune based on workload evidence rather than disabling autovacuum.

### FS-2.24-08 — Configuration drift discovered

Determine the effective value and source using `pg_settings`; inspect configuration files, includes, `postgresql.auto.conf`, database/role defaults, and startup options. Reconcile to the declared baseline through the approved change process.

## 2.24.19 Recovery readiness scorecard

A production cluster should be able to answer **yes** to all of these:

- Can we restore the latest backup?
- Can we recover to an approved point in time where required?
- Do we know our measured restore duration?
- Are all tablespaces protected?
- Is required WAL available?
- Are backup failures alerted?
- Are restore tests recurring?
- Is failover tested for HA deployments?
- Is the rollback procedure documented for changes?
- Does the team know who makes the recovery decision?

If these answers are unknown, recovery readiness is incomplete.

## 2.24.20 Automation model

Automate repetitive checks, but preserve explicit decision gates for destructive or high-risk operations.

Good automation targets:

```text
Configuration validation
Backup execution/status
Restore-test workflows
Replication checks
Capacity checks
Vacuum/freeze monitoring
Patch inventory
Version inventory
Extension inventory
Upgrade prechecks
Post-change validation
Drift detection

```

Automation must fail visibly. A silent failed backup or monitoring job is worse than no automation because it creates false confidence.

## 2.24.24 SRE/DBRE takeaway

Production PostgreSQL reliability comes from disciplined lifecycle management rather than a single configuration setting or tool.

Install deliberately. Configure from declared state. Validate runtime behavior. Back up and prove recovery. Monitor symptoms and causes. Maintain vacuum health. Patch consistently. Rehearse major upgrades. Design rollback before change. Preserve evidence. Automate repeatable checks. Learn from incidents.

That operating loop is the foundation for every later PostgreSQL SRE/DBRE topic in this handbook.
