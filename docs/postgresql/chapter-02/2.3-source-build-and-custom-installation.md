# 2.3 — PostgreSQL Source Build and Custom Installation

**Status:** Production Ready / Complete

Source installation is appropriate when production requirements cannot be met by approved binary packages, but it transfers more lifecycle responsibility to the SRE/DBRE organization.

## When to use a source build

Examples include specialized compile-time options, controlled custom prefixes, engineering/testing needs, or platforms without appropriate packages. Avoid source builds merely for familiarity when a maintained package is sufficient.

## Build lifecycle

```text
Approved source → Verify provenance → Dependencies → Configure
→ Build → Test → Install → Initialize separately → Validate → Package/automate
```

Use a versioned installation prefix so multiple major versions can coexist during upgrade work.

## Build controls

Record source version, source provenance, compiler/toolchain, configure options, dependency versions, installation prefix, build/test results, and installed artifacts. Reproducibility is a production requirement.

## Runtime identity

Building/installing software and running the database server are separate concerns. PostgreSQL must run under an unprivileged server owner; do not run the server or `initdb` as root.

## Upgrade compatibility

For `pg_upgrade`, source-built target binaries must use compile-time settings compatible with the old cluster. `pg_upgrade` performs compatibility checks, but custom modules remain the operator's responsibility.

## External modules

Rebuild or obtain every required C/shared-library extension for the target major version. Validate ABI/API compatibility and extension upgrade procedures before production cutover.

## Operational integration

A custom installation must still provide service management, log handling, environment management, monitoring, backup integration, security hardening, patch tracking, and uninstall/rollback procedures.

## Failure scenarios

- Build flags differ from approved manifest: reject artifact and rebuild.
- Missing dependency after deployment: fix packaging/dependency process rather than modifying production ad hoc.
- `pg_upgrade --check` reports incompatible build characteristics: stop and rebuild target correctly.
- Custom extension unavailable for target major: block upgrade or redesign dependency.

## Production checklist

- [ ] Source provenance verified
- [ ] Versioned prefix used
- [ ] Build configuration captured
- [ ] Tests passed
- [ ] Artifact reproducible
- [ ] Runtime service integration implemented
- [ ] Custom extensions validated
- [ ] Upgrade compatibility rehearsed
- [ ] Patch process documented
