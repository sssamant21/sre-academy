# 2.7 — Directory and Filesystem Planning

**Status:** Production Ready / Complete

PostgreSQL directory and filesystem design is a reliability decision, not merely a choice of where to place `PGDATA`. The storage architecture must account for the data directory, WAL, tablespaces, backups and archives, temporary workload behavior, filesystem semantics, capacity growth, latency, failure domains, monitoring, recovery, and future upgrades.

A production design should be documented before cluster initialization so that the database is not forced into an accidental storage layout that later becomes difficult to migrate.

## Storage architecture

PostgreSQL normally stores cluster files under `PGDATA`. A cluster's complete storage footprint can also include tablespaces outside `PGDATA` and, when configured, WAL outside the main data directory.

```text
PostgreSQL Cluster Storage
          |
          +-- PGDATA
          |    +-- base/
          |    +-- global/
          |    +-- pg_wal/  (default)
          |    +-- pg_tblspc/
          |    +-- control / transaction state
          |    +-- configuration (traditional layout)
          |
          +-- Optional external WAL storage
          |
          +-- Optional tablespaces
               +-- table data
               +-- index data
               +-- selected databases/objects
```

Do not treat external tablespaces or WAL as independent data. They are dependencies of the same PostgreSQL cluster and must be included in backup, recovery, monitoring, capacity, and disaster-recovery design.

## PGDATA planning

Choose an explicit, standardized data-directory layout. Examples include package-managed paths such as `/var/lib/pgsql/data` or an organization-specific layout such as:

```text
/postgresql/18/data
/postgresql/18/wal
/postgresql/archive
/postgresql/backup
/postgresql/log
```

The exact paths are organizational choices rather than PostgreSQL requirements.

When using a secondary mounted filesystem, do not normally use the filesystem's top-level mount point itself as `PGDATA`. Create an owned directory below the mount point and place the data directory inside it. This reduces permission problems, helps operations such as `pg_upgrade`, and makes a missing/offline mount easier to detect safely.

Example:

```text
/data                         filesystem mount
└── postgresql                postgres-owned parent
    └── 18
        └── data              PGDATA
```

## Ownership and permissions

The PostgreSQL operating-system account should own the data directory and the directories that PostgreSQL must write to.

Example validation:

```bash
ls -ld /data/postgresql
ls -ld /data/postgresql/18/data
stat /data/postgresql/18/data
```

Avoid broad permissions such as `chmod 777`. Filesystem access is part of the database security boundary.

Automation should verify owner, group, mode, mount identity, filesystem type, and expected path before starting PostgreSQL.

## Filesystem selection

PostgreSQL generally requires filesystem behavior with appropriate POSIX semantics. Filesystem choice should be based on supported platform combinations, operational experience, durability guarantees, latency, recovery characteristics, snapshot behavior, observability, and vendor support rather than assumptions that a filesystem change alone will automatically improve PostgreSQL performance.

Evaluate at least:

- durability and `fsync` behavior;
- latency under sustained and burst I/O;
- filesystem and storage vendor support;
- crash-recovery behavior;
- snapshot/backup integration;
- monitoring and failure visibility;
- online expansion procedures;
- mount and remount behavior;
- operational familiarity and recovery tooling.

Benchmark the complete production storage stack rather than relying on generic filesystem rankings.

## WAL storage planning

By default, WAL is stored under `PGDATA/pg_wal`. WAL is written sequentially and is fundamental to durability and crash recovery.

A separate WAL location can be selected during initialization, for example:

```bash
initdb \
  -D /postgresql/18/data \
  --waldir=/postgresql/18/wal
```

Separating WAL can be useful when the architecture provides a genuine independent performance or capacity benefit. It also introduces another critical dependency: if the WAL filesystem is missing or fails, the database cannot be treated as healthy merely because the main data filesystem remains available.

Do not separate WAL solely because an old tuning guide recommends it. On modern shared storage, SAN, cloud block storage, or virtualized platforms, two logical mount points may still share the same physical failure and performance domain.

Validate the actual storage topology.

## WAL capacity

WAL capacity must account for normal write rate, checkpoints, replication, archival, backup activity, bulk loads, index builds, maintenance, logical/physical replication slots, and abnormal retention.

Monitor at minimum:

```text
pg_wal filesystem utilization
WAL generation rate
WAL archive failures
replication lag
replication slot retained WAL
checkpoint behavior
filesystem latency
```

Do not size `pg_wal` only from normal daily averages. A failed archive destination or inactive replication slot can cause retained WAL to grow until storage is exhausted.

## Tablespace architecture

Tablespaces provide named filesystem locations for database objects.

Example operating-system preparation:

```bash
mkdir -p /postgresql/tablespaces/fastspace
chown postgres:postgres /postgresql/tablespaces/fastspace
```

Then:

```sql
CREATE TABLESPACE fastspace
LOCATION '/postgresql/tablespaces/fastspace';
```

The location must already exist, be empty, use an absolute path, and be owned appropriately by the PostgreSQL operating-system user.

Tablespaces can support capacity management and differentiated storage tiers, but they increase operational complexity. A tablespace is not independently portable or independently recoverable from its cluster. Losing a tablespace can make database objects unreadable and can affect the cluster's ability to function.

Use tablespaces only when they solve a documented requirement.

## Tablespace dependency model

```text
PGDATA
  |
  +-- pg_tblspc/
         |
         +-- link --> /storage/fastspace
         |
         +-- link --> /storage/archive_space
```

The symbolic links under `PGDATA/pg_tblspc` connect PostgreSQL to non-built-in tablespaces. Never manually change these links while PostgreSQL is running.

Inventory tablespaces with SQL:

```sql
SELECT
    spcname,
    spcowner::regrole,
    pg_tablespace_location(oid)
FROM pg_tablespace;
```

## Avoid unnecessary tablespace proliferation

Creating many tablespaces on the same underlying filesystem generally does not create independent I/O or failure domains. It can instead increase backup, migration, upgrade, monitoring, and recovery complexity.

For every tablespace, document:

```text
Name
Purpose
Filesystem / volume
Storage class
Capacity
Expected growth
Objects/databases using it
Backup coverage
DR mapping
Monitoring
Owner
Recovery procedure
```

## Capacity and headroom

A PostgreSQL filesystem must have enough space not only for current relation size but also for operational amplification.

Capacity planning should include:

```text
Current database footprint
+ expected data growth
+ indexes
+ TOAST
+ WAL
+ temporary files
+ VACUUM / maintenance behavior
+ REINDEX / CREATE INDEX workspace
+ pg_upgrade requirements
+ logical migration overlap
+ backup / restore staging where applicable
+ safety headroom
```

There is no universal percentage that is correct for every workload. Establish warning and critical thresholds from growth rate, expansion lead time, workload volatility, and the amount of space required for the largest credible maintenance or recovery operation.

A volume at 80% utilization with slow growth and instant expansion may present less risk than one at 60% that grows rapidly and requires a multi-day storage change process.

## Capacity forecasting

Track both utilization and rate of change.

```text
Days to exhaustion = usable free capacity / recent growth rate
```

This is a planning indicator rather than a PostgreSQL formula. Forecast separately for PGDATA, WAL, each tablespace, archive storage, and backup staging.

Alert on both static thresholds and forecasted exhaustion.

## Inode planning

Capacity is not only bytes. Filesystem inode exhaustion can prevent PostgreSQL from creating required files even when `df -h` shows free space.

Validate:

```bash
df -h
df -i
```

Include inode monitoring where the filesystem design makes inode exhaustion plausible.

## I/O latency and throughput planning

PostgreSQL storage behavior includes sequential reads/writes, random reads, WAL writes and flushes, checkpoints, background writing, vacuum, index creation, temporary I/O, and backup/restore activity.

Measure the storage system under realistic concurrency. Important operating-system/storage indicators include:

```text
read latency
write latency
fsync / flush latency
IOPS
throughput
queue depth
utilization
I/O errors/timeouts
```

Correlate host/storage telemetry with PostgreSQL wait events, checkpoints, WAL generation, query latency, and workload changes.

Do not use one universal IOPS target for every PostgreSQL workload.

## Temporary I/O

Sorts, hashes, index builds, maintenance, and other operations can spill to disk. A database with enough permanent-data capacity can still experience severe latency or filesystem exhaustion because of temporary I/O.

Monitor temporary-file activity and tune memory only after considering workload concurrency. Increasing per-operation memory settings without concurrency analysis can move the failure from disk pressure to memory pressure.

## NFS

PostgreSQL can use NFS when the storage stack provides the required semantics. PostgreSQL 18 documentation requires NFS client mounts used for PostgreSQL storage to use the `hard` option. A `soft` mount can turn interrupted network operations into I/O errors that PostgreSQL does not transparently retry.

On platforms that provide it, PostgreSQL documentation strongly recommends the NFS server `sync` export behavior so client durability operations reach permanent storage as expected.

An NFS design must therefore include explicit validation of:

```text
client mount options
server export options
network redundancy
latency
failure behavior
monitoring
storage durability
vendor support
recovery procedures
```

A `hard` mount can cause database processes to wait for extended periods during network/storage outages. Monitoring and incident procedures must distinguish blocked storage I/O from a PostgreSQL software hang.

## Mount safety

A dangerous failure mode occurs when a database filesystem is expected at `/data`, the mount is absent, and PostgreSQL writes into the underlying root filesystem path instead.

Use deployment controls that verify the intended filesystem is actually mounted before PostgreSQL starts.

Conceptual validation:

```bash
findmnt /data/postgresql
findmnt /postgresql/18/wal
```

Service management can also express mount dependencies where appropriate.

Do not validate only that the directory exists. Validate that the expected storage is mounted at the expected location.

## Storage identifiers

Prefer stable device/mount identifiers according to platform standards. Device names that can change across reboot or reattachment create avoidable risk.

Document the mapping:

```text
PostgreSQL path
→ mount point
→ filesystem
→ logical volume / cloud volume
→ physical/storage service
→ failure domain
```

This mapping is invaluable during latency incidents and disaster recovery.

## Cloud and virtualized storage

On cloud and virtualized platforms, a filesystem path does not reveal the actual storage characteristics. Document the storage service/class, provisioned capacity, IOPS/throughput model, burst behavior, encryption, snapshot capability, expansion constraints, attachment limits, availability-zone dependency, and monitoring metrics.

Avoid assuming that two volumes represent independent physical devices or independent failure domains unless the platform architecture guarantees it.

## Backup and recovery implications

Backup design must include all cluster storage dependencies.

For physical backups this means the main data directory and all tablespaces must be represented consistently. Backup/restore tooling such as `pg_basebackup` can remap tablespace locations during a plain-format backup/restore workflow when required.

A filesystem snapshot is not automatically a valid PostgreSQL backup merely because it captures files. Snapshot consistency, WAL requirements, multi-volume coordination, and the selected PostgreSQL backup method must be understood and tested.

## Upgrade implications

Filesystem planning affects major-version upgrades. `pg_upgrade` may require old and new clusters to coexist, and some modes have filesystem-specific requirements. Tablespaces and external storage add mapping and capacity considerations.

Before an upgrade, document:

```text
old PGDATA
new PGDATA
old/new binary locations
all tablespaces
WAL locations
available free space
backup/rollback storage
filesystem compatibility
mount dependencies
```

Capacity for upgrades must be planned before the change window.

## Monitoring and alerting

Monitor every filesystem required by PostgreSQL, not only `/` or the main `PGDATA` volume.

Minimum production coverage:

```text
PGDATA utilization and growth
WAL utilization and growth
all tablespace utilization and growth
inode utilization where relevant
read/write latency
I/O errors and timeouts
mount availability
filesystem read-only transitions
WAL archive failures
replication-slot WAL retention
backup-storage capacity
```

Alerting should identify the affected PostgreSQL cluster and mount point and provide enough context for an operator to distinguish capacity, latency, mount, archive, and replication-retention problems.

## Failure scenarios

### FS-2.7-01 — PGDATA filesystem nearly full

Protect availability first. Identify growth sources, largest databases/relations, temporary activity, WAL/tablespace placement, and expansion options. Avoid deleting PostgreSQL files manually. Expand storage or remove data only through safe database/application procedures.

### FS-2.7-02 — WAL filesystem fills

Identify WAL generation and retention causes, including archive failure and replication slots. Do not manually delete WAL segment files from `pg_wal`. Restore archive/replication health or expand storage according to the incident runbook.

### FS-2.7-03 — Tablespace mount disappears

Stop uncontrolled restart attempts and protect the remaining data. Restore the correct storage/mount and verify filesystem integrity, ownership, and tablespace links before controlled database recovery.

### FS-2.7-04 — PostgreSQL writes to an unmounted underlying directory

Stop PostgreSQL safely, identify where files were written, restore the expected mount, and follow a data-reconciliation/recovery plan. Do not simply mount a filesystem over newly written files and restart without investigation.

### FS-2.7-05 — NFS outage

Determine whether PostgreSQL processes are blocked on storage I/O. Restore network/storage service and validate filesystem health and PostgreSQL recovery. Do not repeatedly kill processes merely because they appear hung while a hard-mounted NFS service is unavailable.

### FS-2.7-06 — Filesystem becomes read-only

Treat this as a storage/OS incident. Preserve evidence, inspect kernel and storage errors, restore filesystem health, and then perform controlled PostgreSQL startup/recovery validation.

### FS-2.7-07 — Latency spike without capacity exhaustion

Correlate storage telemetry, PostgreSQL waits, checkpoints, WAL, backup activity, maintenance, temporary I/O, and neighboring workloads. Capacity percentage alone does not describe storage health.

### FS-2.7-08 — Inode exhaustion

Identify file-count growth and the affected filesystem. Do not remove PostgreSQL-managed files manually. Correct the underlying capacity/filesystem issue using an approved recovery plan.

## Recovery workflow

```text
Storage Alert / Database Failure
          ↓
Identify affected cluster
          ↓
Map path → mount → volume → failure domain
          ↓
Protect PostgreSQL data
          ↓
Check mount / filesystem / storage health
          ↓
Check capacity + inodes + latency
          ↓
Check WAL / tablespace dependencies
          ↓
Restore storage service or capacity
          ↓
Controlled PostgreSQL startup/recovery
          ↓
Validate database + replication + archive
          ↓
Validate application
          ↓
Document RCA and capacity correction
```

Never use manual deletion of files inside `PGDATA`, `pg_wal`, or tablespace directories as a generic disk-space recovery technique.

## Automation and IaC

Infrastructure automation should define and validate:

```text
filesystem/volume identity
mount point
filesystem type
mount options
owner/group/mode
PGDATA path
WAL path
all tablespace paths
capacity
IOPS/throughput where applicable
backup policy
monitoring policy
service mount dependencies
```

Before PostgreSQL startup, automation should fail closed if an expected critical mount is absent or points to the wrong storage.

## Production case study — WAL growth exhausts storage

A database has normal WAL generation but a replication consumer fails. A physical or logical replication slot continues retaining WAL. The WAL filesystem grows until the server reaches critical free space.

A production response is to identify the retaining slot and consumer, determine whether the consumer can safely resume or must be rebuilt/removed according to replication policy, restore sufficient capacity, and verify replication and archive health. The operator must not solve the incident by deleting files directly from `pg_wal`.

The preventive controls are WAL-generation monitoring, slot-retention monitoring, filesystem forecasting, consumer health alerts, and a documented slot lifecycle policy.

## Production case study — missing mount after reboot

A host reboots and the PostgreSQL data volume fails to mount. The mount-point directory still exists on the root filesystem. Without mount validation, a service can potentially start against the wrong path or create unexpected files.

The production design uses explicit mount dependencies and pre-start validation of filesystem identity. PostgreSQL startup fails closed until the intended volume is mounted.

The lesson is that **directory existence is not proof of storage identity**.

## Golden production principle

A PostgreSQL storage design is production-ready only when the team can answer all of these questions:

```text
Where is every byte of cluster-critical data stored?
What storage service/device backs each path?
What happens if each filesystem disappears?
How quickly is each filesystem growing?
How is WAL retention bounded and monitored?
How are tablespaces backed up and restored?
Can PostgreSQL start only when the correct mounts exist?
Can the cluster be rebuilt or restored with the same layout?
Is there enough headroom for maintenance, upgrades and recovery?
```

Directory and filesystem planning should therefore be treated as part of PostgreSQL reliability architecture, not a post-installation housekeeping task.
