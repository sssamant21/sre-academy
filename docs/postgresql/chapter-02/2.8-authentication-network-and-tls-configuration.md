# 2.8 — Authentication, Network, and TLS Configuration

**Status:** Production Ready / Complete

PostgreSQL should not be exposed to production networks until listener scope, `pg_hba.conf`, authentication, TLS, firewall/security-group rules, and administrative access have been reviewed together.

## Listener scope

Configure `listen_addresses` and port deliberately. Binding PostgreSQL broadly does not itself authorize connections, but it expands network exposure and must be paired with restrictive host/network controls and `pg_hba.conf`.

## pg_hba.conf

Rules are evaluated in order. Keep entries specific, documented, and least-privileged. Separate application, administration, replication, monitoring, and local access patterns where useful.

Do not use `trust` for production network access. PostgreSQL's `initdb` documentation warns to use trust only when relevant users can genuinely be trusted.

## Authentication

Prefer approved strong authentication appropriate to the environment. Manage database passwords/secrets outside source code and rotate them through a controlled process. Review authentication changes when upgrading PostgreSQL because capabilities/defaults can evolve.

## TLS

Where policy requires encryption in transit, configure server certificates/keys, protocol/cipher policy, certificate rotation, client verification as appropriate, and monitoring for expiration. Protect private keys with restrictive filesystem permissions.

## Network controls

Use layered controls: routing/VPC/VNet policy, firewall/security groups, host firewall where applicable, PostgreSQL listener scope, `pg_hba.conf`, authentication, and TLS. Do not treat any single layer as the entire security model.

## Administrative access

Restrict superuser and operational access. Prefer named identities and audited paths. Avoid sharing application credentials for administration.

## Reload and validation

After HBA/config changes, reload as appropriate and test both allowed and denied connection paths. Validate from the actual application/replication/monitoring networks.

## Monitoring

Monitor authentication failures, connection spikes, TLS/certificate state, unexpected source networks, rejected connections, and privileged-access events according to organizational policy.

## Failure scenarios

- Accidental broad HBA rule: immediately restrict access and review connection/audit evidence.
- Certificate expiration: rotate through tested procedure and validate clients.
- Application authentication failure after change: verify rule ordering, user/database/source address, secret, TLS mode, and logs.
- Replication blocked: validate dedicated replication HBA/network/TLS path without weakening application security.

## Production checklist

- [ ] Listener scope approved
- [ ] HBA rules least-privileged
- [ ] No inappropriate `trust`
- [ ] Authentication method approved
- [ ] Secrets management integrated
- [ ] TLS policy implemented where required
