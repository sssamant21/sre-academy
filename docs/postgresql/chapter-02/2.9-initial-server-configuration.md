# 2.9 — Initial Server Configuration (`postgresql.conf`, `pg_hba.conf`, `pg_ident.conf`)

**Status:** Production Ready / Complete

After installation, cluster initialization, filesystem planning, and service setup, PostgreSQL must be configured for the intended production workload and security model. This section establishes the SRE/DBRE baseline for PostgreSQL configuration files, configuration precedence, safe reload/restart procedures, validation, drift control, troubleshooting, and automation.

## Configuration architecture

PostgreSQL configuration is layered. Production engineers must understand both where a value is defined and which value is actually effective.

```text
Compiled / Built-in Defaults
          ↓
postgresql.conf
          ↓
Included Configuration Files
          ↓
postgresql.auto.conf / ALTER SYSTEM
          ↓
Database / Role Defaults
          ↓
Session / Client Overrides
```

Command-line server options can also override configuration-file settings and normally require a restart to change.

Never diagnose configuration solely by reading one file. Validate the effective runtime value and its source.

## Core configuration files

The primary configuration files are:

```text
postgresql.conf   Server runtime configuration
pg_hba.conf       Client authentication rules
pg_ident.conf     External-to-database user-name mappings
```

By default these are associated with the cluster configuration, although PostgreSQL supports relocating configuration files through its file-location settings and startup options.

Validate effective locations:

```sql
SHOW config_file;
SHOW hba_file;
SHOW ident_file;
SHOW data_directory;
```

Do not assume that the configuration files are physically inside PGDATA on every platform or packaging model.

## postgresql.conf

`postgresql.conf` defines cluster-wide server defaults for areas such as connections, memory, WAL, checkpoints, logging, autovacuum, replication, query planning, timeouts, SSL, and background workers.

Example baseline fragments:

```conf
listen_addresses = '10.0.10.25'
port = 5432
max_connections = 200
shared_buffers = '4GB'
logging_collector = on
log_min_duration_statement = '1s'
timezone = 'UTC'
```

These are examples, not universal production values. Capacity and workload settings must be engineered for the actual server, workload, connection architecture, HA design, and operating environment.

## Parameter types and units

PostgreSQL parameters may be boolean, string, integer, floating-point, or enumerated values. Many numeric parameters accept explicit units.

Prefer explicit units where they improve clarity:

```conf
statement_timeout = '30s'
work_mem = '16MB'
maintenance_work_mem = '1GB'
```

Avoid ambiguous configuration generated by scripts that do not understand the parameter's implicit unit.

## Configuration precedence

A frequent production failure is changing a value in `postgresql.conf` and finding that PostgreSQL continues to use another value.

Common causes include:

```text
A later duplicate entry
An included file
postgresql.auto.conf
ALTER DATABASE
ALTER ROLE
Session SET
Server command-line -c option
```

Inspect runtime configuration using `pg_settings`:

```sql
SELECT name,
       setting,
       unit,
       source,
       sourcefile,
       sourceline,
       context,
       pending_restart
FROM pg_settings
WHERE name = 'max_connections';
```

This should be a standard DBRE troubleshooting technique.

## Duplicate settings

If the same parameter appears multiple times in configuration-file processing, the later applicable setting wins.

This makes uncontrolled append-only configuration dangerous. A configuration-management system that repeatedly appends settings can create hidden overrides and operational confusion.

Production automation should generate deterministic configuration rather than accumulating duplicate entries.

## Configuration include architecture

PostgreSQL supports modular configuration through:

```conf
include 'shared.conf'
include_if_exists 'local.conf'
include_dir 'conf.d'
```

A production pattern can separate concerns:

```text
postgresql.conf
      ↓
conf.d/
  00-base.conf
  10-memory.conf
  20-connections.conf
  30-wal.conf
  40-logging.conf
  50-replication.conf
  90-environment.conf
```

Files in an `include_dir` are processed in filename order according to PostgreSQL's documented rules, so naming should make precedence intentional and reviewable.

Version-control configuration templates and environment-specific overlays. Do not allow undocumented local overrides to become permanent production state.

## postgresql.auto.conf and ALTER SYSTEM

`ALTER SYSTEM` changes cluster-wide parameter defaults by writing to `postgresql.auto.conf`.

Example:

```sql
ALTER SYSTEM SET log_min_duration_statement = '1s';
SELECT pg_reload_conf();
```

Reset a value:

```sql
ALTER SYSTEM RESET log_min_duration_statement;
```

Reset all ALTER SYSTEM entries only through an approved change because it can remove unrelated configuration:

```sql
ALTER SYSTEM RESET ALL;
```

`postgresql.auto.conf` is read in addition to `postgresql.conf`, and its settings can override values from `postgresql.conf`.

Production policy must decide whether `ALTER SYSTEM` is an approved configuration path. If infrastructure-as-code owns the configuration, uncontrolled ALTER SYSTEM changes create drift.

Do not manually edit `postgresql.auto.conf` as the normal administrative workflow.

## Parameter change contexts

Not every parameter can be changed the same way. `pg_settings.context` describes the required context.

Important classes include:

```text
internal             Not directly changeable
postmaster           Requires server restart
sighup               Applied by configuration reload
superuser-backend    New sessions after reload; privileged
backend              New sessions after reload
superuser            Session-settable with required privilege
user                 Session-settable by ordinary users
```

Before changing a parameter, inspect its context:

```sql
SELECT name, setting, context, pending_restart
FROM pg_settings
WHERE name IN (
  'shared_buffers',
  'max_connections',
  'work_mem',
  'log_min_duration_statement'
);
```

Do not schedule an unnecessary restart for a SIGHUP parameter, and do not assume a reload will activate a `postmaster` parameter.

## Reload versus restart

For reloadable parameters:

```sql
SELECT pg_reload_conf();
```

or:

```bash
pg_ctl reload -D "$PGDATA"
```

A reload sends SIGHUP through the server so configuration files are reread. Some parameters require restart and will not become effective from reload alone.

Identify pending restart requirements:

```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE pending_restart;
```

A production change record should explicitly classify every parameter as reloadable, new-session-only, or restart-required.

## Pre-validating configuration files

Use `pg_file_settings` before reload when possible:

```sql
SELECT sourcefile,
       sourceline,
       name,
       setting,
       applied,
       error
FROM pg_file_settings
WHERE error IS NOT NULL
   OR applied = false
ORDER BY seqno;
```

`pg_file_settings` describes the current contents of the configuration files and can identify syntax errors, invalid values, and entries overridden later in processing.

Do not interpret every `applied = false` row as an error; a later duplicate can legitimately override an earlier entry. Inspect `error`, source order, and runtime state together.

## pg_hba.conf

`pg_hba.conf` controls client authentication. Treat it as security policy, not merely connection configuration.

A production design should define rules by connection type, source network, database, role, and authentication method.

Conceptual examples:

```conf
local   all          postgres                     peer
hostssl appdb        app_role     10.20.0.0/16     scram-sha-256
hostssl replication  repl_role    10.30.0.0/24     scram-sha-256
```

Do not copy these addresses or role names blindly. Rules must reflect the actual network and identity architecture.

Keep broad rules below specific rules because HBA processing is order-sensitive. Avoid overly permissive entries such as unrestricted `trust` access in production.

Validate HBA configuration with PostgreSQL's inspection facilities and test both expected-success and expected-denial paths before production promotion.

## pg_ident.conf

`pg_ident.conf` maps authenticated external operating-system or certificate identities to PostgreSQL database roles when an authentication method uses user-name mapping.

Use mappings only when required by the authentication architecture. Keep mappings narrow, documented, and version controlled.

Do not create broad identity mappings that effectively bypass intended role separation.

## Network exposure

`listen_addresses` controls which interfaces accept TCP connections; `pg_hba.conf` controls which matching clients may authenticate. These are separate security layers.

A safe production model combines:

```text
Network Firewall / Security Group
          ↓
listen_addresses
          ↓
TLS Policy
          ↓
pg_hba.conf
          ↓
PostgreSQL Authentication
          ↓
Database Privileges
```

Do not rely on any single layer as the entire access-control model.

## Memory configuration baseline

Important parameters include:

```text
shared_buffers
work_mem
maintenance_work_mem
autovacuum_work_mem
effective_cache_size
huge_pages
```

Avoid formulas that blindly assign fixed percentages without accounting for workload concurrency, connection count, parallel execution, maintenance operations, extensions, operating-system memory, and HA agents.

`work_mem` is especially dangerous when interpreted as a per-server memory allocation. It can be consumed by multiple query operations and multiple concurrent sessions.

Memory tuning is covered in greater depth elsewhere in the handbook; initial configuration should establish conservative, tested values and monitoring.

## Connection configuration baseline

Important settings include:

```text
listen_addresses
port
max_connections
superuser_reserved_connections
reserved_connections
unix_socket_directories
```

Do not increase `max_connections` as the default response to connection pressure. Evaluate pooling, transaction behavior, idle sessions, application concurrency, and memory impact.

## WAL and durability baseline

Initial production configuration must explicitly review:

```text
wal_level
fsync
synchronous_commit
full_page_writes
max_wal_size
min_wal_size
checkpoint_timeout
archive_mode
archive_command / archive_library
```

Do not disable durability controls such as `fsync` or `full_page_writes` in production merely to improve benchmark throughput.

HA, PITR, replication, and backup architecture determine the appropriate WAL configuration.

## Logging baseline

A production cluster should establish intentional logging before application traffic begins.

Review:

```text
log_destination
logging_collector
log_directory
log_filename
log_line_prefix
log_connections
log_disconnections
log_min_duration_statement
log_lock_waits
log_checkpoints
log_autovacuum_min_duration
```

Logging must balance incident visibility, security/privacy, disk consumption, and performance overhead.

Avoid enabling extremely verbose statement logging globally without understanding workload volume and sensitive-data exposure.

## Autovacuum baseline

Do not disable autovacuum as an initial tuning technique.

Review:

```text
autovacuum
autovacuum_max_workers
autovacuum_naptime
autovacuum_vacuum_scale_factor
autovacuum_analyze_scale_factor
autovacuum_vacuum_cost_limit
```

The initial goal is a safe baseline. Table-specific tuning should be driven by workload evidence, table growth, dead tuples, freeze age, and vacuum duration.

## Timeout baseline

Production environments should intentionally evaluate timeouts such as:

```text
statement_timeout
lock_timeout
idle_in_transaction_session_timeout
idle_session_timeout
transaction_timeout
```

Do not impose a universal low `statement_timeout` at cluster level without considering maintenance, ETL, migrations, backups, and administrative operations. Where appropriate, use database-, role-, or application-specific defaults.

## Role and database configuration overrides

PostgreSQL supports persistent defaults at database and role scope.

Example:

```sql
ALTER DATABASE appdb SET statement_timeout = '60s';
ALTER ROLE app_user SET statement_timeout = '30s';
```

These settings normally take effect for new sessions.

Use scoped configuration when a setting is genuinely workload-specific. Avoid creating an undocumented hierarchy of global, database, role, and session overrides that becomes impossible to reason about.

## Runtime validation

After applying a configuration change, verify the effective state:

```sql
SHOW shared_buffers;
SHOW max_connections;
SHOW log_min_duration_statement;
```

For richer evidence:

```sql
SELECT name,
       setting,
       unit,
       source,
       sourcefile,
       sourceline,
       context,
       pending_restart
FROM pg_settings
WHERE name IN (
  'shared_buffers',
  'max_connections',
  'log_min_duration_statement'
);
```

The production validation record should capture intended value, effective value, source, reload/restart state, and application impact.

## Configuration drift detection

Monitor configuration drift between declared infrastructure and runtime PostgreSQL state.

Useful evidence includes:

```sql
SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings
ORDER BY name;
```

Track unexpected `postgresql.auto.conf` changes, manual file edits, role/database overrides, package-generated configuration, and service command-line options.

A mature SRE platform compares effective configuration with a version-controlled baseline rather than merely checksumming one file.

## Monitoring and alerting

Monitor configuration-related conditions such as:

- restart-required settings pending for too long
- configuration reload errors
- unexpected server restart after a change
- authentication failures after HBA modification
- sudden connection rejection
- logging destination failure or filesystem growth
- configuration drift from approved baseline
- unauthorized ALTER SYSTEM changes
- unexpected change in critical durability, replication, security, or memory parameters

Configuration changes should be correlated with performance and availability telemetry so incidents can be tied rapidly to recent changes.

## Failure scenarios

### FS-2.9-01 — Changed parameter has no effect

Inspect `pg_settings.source`, `sourcefile`, `sourceline`, `context`, and `pending_restart`. Check `postgresql.auto.conf`, includes, role/database overrides, and startup command-line options.

### FS-2.9-02 — Reload reports success but value is unchanged

Determine whether the parameter requires restart or only affects new sessions. Inspect `pg_file_settings` for invalid or overridden entries.

### FS-2.9-03 — Invalid configuration after edit

Do not repeatedly restart the production server. Validate the files, inspect `pg_file_settings` where the running instance is available, review PostgreSQL logs, correct the invalid entry, then perform a controlled reload or restart.

### FS-2.9-04 — ALTER SYSTEM unexpectedly overrides IaC

Identify the value in `postgresql.auto.conf`, confirm change ownership, remove/reset it through the approved workflow, reload/restart as required, and reconcile the incident with configuration governance.

### FS-2.9-05 — HBA change locks out administrators

Maintain a tested break-glass access path appropriate to the platform. Restore the last known-good HBA policy through controlled host/platform access, reload configuration, test administrative authentication, and document the incident.

### FS-2.9-06 — Connection surge after max_connections increase

Protect database stability first. Evaluate memory pressure, backend count, CPU, connection pooling, application retry behavior, and reserved administrative capacity. Revert or reduce the change if it threatens reliability.

### FS-2.9-07 — Logging change fills filesystem

Reduce or correct the logging policy, preserve required incident evidence, rotate/archive logs safely, restore filesystem headroom, and validate that PostgreSQL and WAL storage are not endangered.

### FS-2.9-08 — Configuration requires restart during peak traffic

Do not restart solely because a setting is pending. Assess urgency, HA/failover capability, maintenance window, application impact, rollback, and post-restart validation before execution.

```text
Change Requirement
       ↓
Identify Parameter + Scope
       ↓
Check PostgreSQL 18 Documentation
       ↓
Check Context / Restart Requirement
       ↓
Capacity + Security Impact Review
       ↓
Prepare Rollback
       ↓
Change Version-Controlled Configuration
       ↓
Pre-Validate Files
       ↓
Reload or Controlled Restart
       ↓
Validate Effective pg_settings
       ↓
Validate Logs / Metrics / Application
       ↓

```

## Automation and IaC

Configuration management should define ownership of:

```text
postgresql.conf
included configuration files
pg_hba.conf
pg_ident.conf
service startup options
ALTER SYSTEM policy
role/database defaults
```

Automation should render deterministic files, validate syntax and supported parameters, preserve secure permissions, compare changes before deployment, identify restart requirements, perform controlled reload/restart, verify runtime values, and roll back from a known-good configuration when validation fails.

Never allow two independent automation systems to own the same configuration layer without explicit precedence and reconciliation rules.

## Production case study — hidden ALTER SYSTEM override

An SRE changes `max_connections` in `postgresql.conf`, restarts PostgreSQL, and observes that the expected value is still not active. Investigation of `pg_settings` shows that the active value comes from `postgresql.auto.conf`, created months earlier through `ALTER SYSTEM`.

The incident demonstrates why configuration troubleshooting must inspect effective runtime source rather than assume that `postgresql.conf` is authoritative.

Corrective actions include defining an ALTER SYSTEM governance policy, auditing `postgresql.auto.conf`, adding drift detection, and recording parameter source in change validation.

## Production case study — unsafe HBA deployment

A broad `pg_hba.conf` rewrite is deployed without pre-validation and legitimate application connections begin failing. The SRE team restores the last known-good policy, reloads PostgreSQL, validates administrative and application connection paths, then deploys the intended rules incrementally.

The lesson is that authentication configuration requires both syntax validation and functional access-path testing.

## SRE/DBRE takeaway

PostgreSQL configuration is not a single-file activity. Production state is the result of configuration files, include order, `postgresql.auto.conf`, server startup options, database/role defaults, and session overrides.

The reliable operating model is:

```text
Declare
  ↓
Review
  ↓
Pre-Validate
  ↓
Apply
  ↓
Reload / Restart only as required
  ↓
Verify Effective Runtime State
  ↓
Observe Application + Platform
  ↓
Detect Drift
```

A PostgreSQL configuration change is complete only when the intended value is proven effective and the database remains healthy.
